## Problem

[§11.2.1](../spec/11_policy-and-controls.md#1121-billing-event-stream) describes its billing event stream as suitable for invoice-grade billing, and an operator cannot price a tenant's usage from it today.

- No billing event carries pod time. §11.2.1 lists `pod_minutes` and does not say which event carries it, and the gateway sets it on no event it emits.
- A pod's cost depends on its CPU, memory, and storage, and no event states them. The operator also redefines a resource class at any time, so a class name alone does not state what a pod held.
- The code holds the class values. [§5.2](../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes) names `small`, `medium`, and `large` and gives no quantities, the controller carries built-in quantities, and the `SandboxTemplate` CRD (the Kubernetes custom resource the controller creates a pool's pods from) refuses any other class name.
- A tenant's owned pool, which [`tenant-derived-runtimes-design.md`](tenant-derived-runtimes-design.md) adds under [DR-5](tenant-derived-runtimes-design.md#dr-5-owned-pools) (owned pools), keeps pods that serve no session: warm pods, pods in the reserved hold between one tenant's sessions, and the capacity-reservation pods that DR-10 marks `spec.reserved`, and a shared pool keeps pinned idle pods that only one tenant can claim (§5.2 **Pinned idle inventory.**). Both appear only in a per-pool metric with no tenant.
- Stored bytes have a quota ([§11.2](../spec/11_policy-and-controls.md#112-budgets-and-quotas)) and no billing event, and legal-hold escrow copies ([§12.8](../spec/12_storage-architecture.md#128-compliance-interfaces) Phase 3.5) have neither. The `artifact_store` ledger, a Postgres table with one row per stored artifact, holds every size and lifetime the bill needs, and nothing compares it with the object store, which holds bytes the ledger does not count.

## Scope

This design covers resource classes as deployment configuration, the resource fields on session pod usage, a periodic `pool.idle_usage` event for owned pools and for pinned idle pods on shared pools, a periodic `storage.usage` event computed from the `artifact_store` ledger and from the legal-hold escrow records, a daily reconciliation of that ledger against the object store, and a per-tenant metric that estimates Postgres-held data.

The following are outside it:

- Prices, currencies, invoices, and rating. Lenny records quantities, and the operator's billing system prices them.
- Token metering, which §11.2 already covers.
- Activity evidence bytes, which [`forensics-evidence-preservation-design.md`, "Volume and cost"](forensics-evidence-preservation-design.md#volume-and-cost) meters as `evidence.usage`.
- Extended resources such as GPUs in a class. A class here holds CPU, memory, and ephemeral storage.
- Node-level costs that no pod requests, such as DaemonSets, the kubelet reserve, and idle node capacity.
- The tmpfs size caps the pod builder applies ([§6.4](../spec/06_warm-pod-model.md#64-pod-filesystem-layout)). The pod builder is the controller code in `pkg/controller/sandbox/podspec` that builds each agent pod's specification. The class check under "Checks at load" reads the same values the builder uses, and those values are unchanged.

Relationship to other designs:

- [`tenant-derived-runtimes-design.md`](tenant-derived-runtimes-design.md) supplies `ownerTenantId` on the pool row ([DR-5](tenant-derived-runtimes-design.md#dr-5-owned-pools)), the `spec.reserved` mark ([DR-10](tenant-derived-runtimes-design.md#dr-10-capacity-reservation)), and the warm store storage request, `warmCloneBytes`, under DR-11, which [DR-9's "Warm clones"](tenant-derived-runtimes-design.md#warm-clones) carries. On an owned pool that request is the template's value plus the grant entry's `maxWarmCloneBytes`, and on a platform pool a `platform-admin` sets it on the pool row for the operator's entries. `pool.idle_usage` depends on DR-5, and [its "Not verified" bullet](tenant-derived-runtimes-design.md#not-verified) on idle billing now points here. Its DR-10 section ["Reporting"](tenant-derived-runtimes-design.md#reporting) attributes a tenant's reserved idle cost through `pool.idle_usage` and points here, because `lenny_warmpool_idle_pod_minutes` carries no tenant.
- [`runtime-routing-design.md`](runtime-routing-design.md) removes the experiment fields from billing events and adds the session's routing labels ([RT-3](runtime-routing-design.md#rt-3-routing-labels)), and [`runtime-revisions-design.md`](runtime-revisions-design.md) adds the session's runtime revision ([RV-2](runtime-revisions-design.md#rv-2-selection)). `session.pod_usage` carries both in its common envelope, and `pool.idle_usage` reports each revision's pod set separately ([RV-3](runtime-revisions-design.md#rv-3-pods)).

Those volumes are outside the artifact ledger in either namespace.

## High-level design

Lenny records what each tenant uses so that an operator's billing system can price it, and today those records leave out most of what costs money: the time a session holds a pod, how large that pod is, warm pods kept for one tenant, and stored bytes. This design adds those quantities to Lenny's billing events. Each session reports, per pod and per hour by default, how long it held the pod and the CPU, memory, and disk the pod reserved. Warm pods that wait for one tenant are reported under that tenant, and stored data such as workspaces and checkpoints is reported as bytes held over time. A daily check compares Lenny's storage records with the object store and lowers a bill that counted bytes the store no longer holds.

Lenny records quantities, and the operator's billing system prices them. Some costs reach no tenant: warm pods on shared pools that wait for no particular tenant, node capacity no pod requests, and data held in Postgres. A pod is billed the disk it reserves whether it uses it or not, and the storage figures come from Lenny's own records, which differ from the provider's bill in ways the daily check reports and does not correct.

The rest of this section states each part in the design's terms, which "Terms" above defines.

**Resource classes in configuration (BR-1).** The chart's `resourceClasses` map holds every class, and the binaries hold none. The chart renders the map into the `lenny-resource-classes` ConfigMap, which the controller and the gateway read at startup and refuse to start without. The gateway refuses a pool or runtime write that names an undefined class, and the controller creates no pod for one. A class states the whole pod's resources.

**Session pod time (BR-2).** `session.pod_usage` reports one pod-binding window per event, cut at each release and at each usage interval boundary, with the pod's effective CPU, memory, and ephemeral storage requests and limits. The gateway records each window in `session_pod_windows` at bind and release, and the emitter turns closed windows into events. On a concurrent pod, a session's share of the pod is per slot.

**Idle pods (BR-3).** The WarmPoolController accrues the minutes of pods that serve no session in `pool_usage_accrual`, and the emitter reports them as `pool.idle_usage`. An owned pool's idle pods are attributed to its owning tenant with `pool_ownership: owned`, and a shared pool's pinned idle pods to the pinned tenant with `pool_ownership: shared_pinned`. The unpinned idle pods of shared pools reach no tenant.

**Stored bytes (BR-4 and BR-6).** `storage.usage` reports bytes held and byte-hours per tenant, store, and artifact type: from the artifact ledger with `store: artifact`, and from the legal-hold escrow records with `store: escrow`, which continues after the tenant's deletion until the hold ends. The watermark keeps the tombstone sweep from deleting a ledger row before its last hours are billed.

**Reconciliation (BR-5).** A daily task compares the artifact ledger with the object store and reports each kind of difference as a metric. It emits a `billing_correction` only to lower a bill for bytes the store does not hold, after two consecutive runs confirm the difference. The same task sets a per-tenant estimate of Postgres-held data as a gauge, with no billing event.

**Writing the events (BR-2).** Every periodic event carries `usage_window_key`, and both insert paths into the billing table, `Append` for the direct write and `InsertFromStream` for the flush from the Redis stream, absorb a duplicate key without drawing a sequence number, so a window retried after a failover is billed once. The emitter records progress only after it reads an event back from Postgres, so a crash delays an event and loses none.

```
 Chart resourceClasses ──> ConfigMap lenny-resource-classes ──> controller (creates pods), gateway (checks writes)

 Gateway bind and release ──> session_pod_windows ──┐
 WarmPoolController ────────> pool_usage_accrual ───┤

 legal_hold_escrow_records ─────────────────────────┘

 Daily reconciliation: artifact_store ledger <──compare──> object store ──> metrics, alerts, billing_correction (lowers only)
```

## Design

### Resource classes in configuration

**Source.** The binaries hold no class. The chart's `values.yaml` ships a top-level `resourceClasses` map and a `defaultResourceClass`, with the values the code holds today:

```yaml
resourceClasses:
  small:
    requests: { cpu: 250m, memory: 1Gi }
    limits:   { cpu: "1",  memory: 1Gi }
  medium:
    requests: { cpu: 500m, memory: 2Gi }
    limits:   { cpu: "2",  memory: 2Gi }
  large:
    requests: { cpu: "1",  memory: 4Gi }
    limits:   { cpu: "4",  memory: 4Gi }
defaultResourceClass: medium
```

An operator changes a class's values, adds a class, or removes one. Helm merges maps, so an operator removes a shipped class by setting it to `null`. The chart renders the map into one ConfigMap, `lenny-resource-classes`, which the controller and the gateway mount and read at startup (decision 8). The gateway and controller Deployments carry a `checksum/resource-classes` pod annotation computed from the rendered ConfigMap, so a `helm upgrade` that changes a class rolls both. The `--resource-class` flag and `controller.resourceClasses` go, and no deployment exists that needs them.

**Fields.** A class holds `requests.cpu`, `requests.memory`, `limits.cpu`, and `limits.memory`, all required, and optional `requests.ephemeral-storage` and `limits.ephemeral-storage`. Its name is a DNS label of at most 63 characters, because it appears as a metric label value and in billing events.

**Checks at load.** The controller and the gateway each refuse to start, with `CONFIG_INVALID` naming the class and the field, when the file is absent, the map is empty, a required field is missing, a request exceeds its limit, `defaultResourceClass` names no class, or a class's memory limit does not exceed the tmpfs reservation. The controller computes the reservation from the size caps the pod builder applies, as `TmpfsReservationMiB` does today, and the comparison follows decision 7.

**Checks at write.** The gateway refuses a write that names an undefined class with `400 VALIDATION_ERROR`, naming the field and listing the defined classes. This covers a pool's `resourceClass` on `POST` and `PUT /v1/admin/pools` and on bootstrap, a runtime's `allowedResourceClasses` and `defaultPoolConfig.resourceClass`, and the equivalent fields on a tenant-derived runtime and its owned pool. The `SandboxTemplate` CRD loses its enum, because the API server cannot read deployment configuration, and §4.6.1's **CRD validation:** sentence changes to name the gateway check.

**Checks at reconcile.** A template can name a class that a later configuration change removed. The controller creates no pod for it, sets the pool condition `ResourceClassUndefined` with the class name (§5.2 places pool conditions such as `PoolWarmingUp` on the pool's `SandboxTemplate`), and increments `lenny_resource_class_undefined_total{pool}`, and the alert `ResourceClassUndefined` fires. Running pods keep their resources. The fallback to unconstrained containers goes.

**Container mapping.** Decision 7 settles how a class maps to containers. A class states the pod's total. On a sidecar pod the adapter container takes `adapterResources`, a chart value, and the runtime container takes the class less that value. An embedded pod's single container takes the whole class. The tmpfs check runs against the runtime container's memory limit.

**Changing a class.** A change applies to pods created after the controller restarts with the new file. A pod keeps the resources it was created with until it ends, which is why every usage event records the pod's actual resources.

**Listing.** `GET /v1/admin/resource-classes` returns the loaded table to `platform-admin` and `tenant-admin`, so a tenant writing a derived runtime can see the names it may use.

**Embedded stack.** `lenny up` applies manifests rendered from the chart under `presets/dev.yaml`, so the embedded stack receives the same ConfigMap and the same defaults through that render, and `TestEmbeddedManifestsMatchDevProfileRender` holds the copy to the chart. The embedded catalog and agent placement name `small`, and a test checks that every class name in `pkg/embedded/stack` is defined in the rendered ConfigMap.

### Resource fields on usage events

**Carrier.** A new event type, `session.pod_usage`, carries a session's pod time, one event per pod-binding window (decision 6). A window opens when the session binds a pod and closes at the first of the release of that binding (suspend, terminal state, eviction, or a resume onto another pod) or the next boundary of `billing.usageIntervalSeconds`, default 3600 and minimum 300, aligned to UTC. A session that moves between pods produces separate windows for each pod. `session.completed` carries no `pod_minutes`.

**Fields.** `session.pod_usage` carries the common envelope (`tenant_id`, `user_id`, `session_id`, `environment_id`, `routing`, `runtime_revision`, and `labels`). `environment_id` is the existing §11.2.1 attribution field for the session's environment, and `labels` holds the client's session labels. `routing` holds the session's routing labels ([RT-3](runtime-routing-design.md#rt-3-routing-labels)), in place of the `experiment_id` and `variant_id` fields that [`runtime-routing-design.md`](runtime-routing-design.md) removes. `runtime_revision` is the revision the session ran on the window's pod ([RV-2](runtime-revisions-design.md#rv-2-selection)). A session changes revision only when it resumes after its revision is retired ([RV-6](runtime-revisions-design.md#rv-6-sessions-over-time)), and that resume binds another pod and so opens a new window. The event also carries these fields:

| Field | Type | Meaning |
| :-- | :-- | :-- |
| `pod_minutes` | float64 | The session's bound time on the pod within the window |
| `window_start`, `window_end` | RFC 3339 | The window's bounds |
| `window_reason` | string | `interval` or `release` |
| `pod_uid` | string | The pod's Kubernetes UID (unique identifier), so a consumer can group a shared pod's windows |
| `pool_name` | string | The pool the pod belongs to |
| `runtime_name` | string | The runtime the session runs |
| `resource_class` | string | The class the pod was created with |
| `isolation_profile` | string | `standard`, `sandboxed`, or `microvm` |
| `cpu_request_millicores`, `cpu_limit_millicores` | uint64 | The pod's effective CPU request and limit |
| `memory_request_bytes`, `memory_limit_bytes` | uint64 | The pod's effective memory request and limit |
| `ephemeral_storage_request_bytes` | uint64 | The pod's effective ephemeral storage request, which includes the pool's `warmCloneBytes` on a platform pool or an owned pool |
| `ephemeral_storage_limit_bytes` | uint64 | Absent when no container sets one |
| `max_concurrent_sessions` | uint32 | The pod's slot capacity: the pool's `sessionPolicy.maxConcurrentSessions` when the pod was created, recorded on the pod so that a later pool change does not alter it |
| `usage_window_key` | string | The idempotency key described under "Writing periodic events" |

**Effective values.** The gateway reads the pod object at bind and computes each effective value with the formula Kubernetes uses for scheduling and quota (`PodRequests` and `PodLimits` in `k8s.io/component-helpers/resource`). It sums the values of the regular containers and of the native sidecar init containers. For each regular init container, it adds that container's value to the values of the native sidecar init containers declared before it. The effective value is the larger of the first sum and the largest of the init container figures, plus `spec.overhead` from the RuntimeClass. A CPU or memory value that the pod sets in `spec.resources` replaces the container figure before the overhead is added, and the overhead is added to a limit only when that limit is non-zero. It stores the values on the binding, so the release path does not read the pod again. The values are what the pod holds, whatever decision 7 settles about how a class maps to containers.

**Concurrent pods.** On a concurrent pod, one with `maxConcurrentSessions` above 1, each session's window reports its own bound time and the pod's full resources. The apportioning rule is per slot: a session's share is its `pod_minutes` times the pod's resources divided by `max_concurrent_sessions`, so the shares of the sessions on one pod never sum above the pod's cost. On an owned pool, the emitter computes the empty slots of each pod that serves at least one session from the pod's `session_pod_windows` rows and reports them in `pool.idle_usage` as `idle_slot_pod_minutes`. On a shared pool, empty slots stay with the operator.

**Ephemeral storage.** The bill uses the reserved ephemeral storage, which is the pod's effective request and which the scheduler reserves on the node (decision 10). The events record no measured disk use, so no component reads kubelet statistics for billing and the design adds no `nodes/stats` or `nodes/proxy` grant. A pod whose containers request no ephemeral storage bills only its pool's `warmCloneBytes`, or no disk when it has none. Decision 10 bills the whole effective request, so the store request follows the pod's other resources. On a platform pool, which is a shared pool, a session window carries the store request of the operator's entries, a pinned idle pod reports it under `shared_pinned`, and an unpinned idle pod's request reaches no tenant. On an owned pool the owning tenant is billed for the whole request, the part that covers the base's entries included. The owner settled that the owning tenant pays for this part too (decision 15). Memory-backed tmpfs counts against memory and is absent from this figure.

**Durability.** The gateway writes each open window to a `session_pod_windows` row (`tenant_id`, `session_id`, `pod_uid`, `opened_at`, the resource fields, `closed_at`, and `emitted_at`) in the transaction that records the binding, and sets `closed_at` in the transaction that records the release. A leader-elected task under `lenny-gateway-leader` emits each window whose interval has passed or whose `closed_at` is set. When no release recorded a close, the task closes the window at the earliest of the session's terminal or suspend transition, the same session's next binding, the time the pod was quarantined, and the pod's deletion time. A window therefore never covers quarantine, which the operator pays for under [forensics decision 16](forensics-evidence-preservation-design.md#decisions) and which that design keeps out of `pod_minutes` by stopping it at the terminal transition. A resumed session's window on its old pod also ends before its window on the new pod opens.

**Emitter progress.** The emitter sets `emitted_at` only after it reads the window's `usage_window_key` back from `billing_events` in Postgres. An `Append` that returns after the event landed in the Redis stream or the in-memory buffer leaves the window pending, because a replica crash loses the in-memory buffer, and the next cycle appends the event again under the idempotent insert in "Writing periodic events". Each emitter persists its progress per subject: `emitted_at` on each `session_pod_windows` row, an emitted mark on each `pool_usage_accrual` row, and, for `storage.usage`, a watermark per tenant, `store`, and `artifact_type`. A gateway crash therefore delays an event and loses none.

**Erasure and teardown.** §12.8 step 5 closes and emits every pending window of the erased user's sessions, so step 15 pseudonymizes those events with the user's other billing events. An emitter that writes a window for a user whose erasure has started writes the §12.8 pseudonym in place of `user_id`, which covers a window that closes after step 5. The `DeleteByUser` sequence deletes the user's `session_pod_windows` rows after emission. Tenant deletion Phase 4 deletes the tenant's `session_pod_windows` and `pool_usage_accrual` rows and its `storage.usage` watermarks for `store: artifact`. The emitters write events for a tenant whose `TenantState` is `disabling` as usual and write no event once `TenantState` is `deleting`, because Phase 4 deletes the tenant's billing events. The `store: escrow` emitter is the exception, and "Legal-hold escrow copies" states when it writes.

**`GET /v1/usage`.** The handler reads `usagestore`, so the emitter also calls `usagestore.Record` after each committed `session.pod_usage`, `pool.idle_usage`, and `storage.usage`, keyed by `usage_window_key` so that a retried window records once. `totalPodMinutes` and a new `podMinutes` on each `byTenant` and `byRuntime` entry sum the recorded `session.pod_usage` minutes. The report gains `idlePodMinutes` from `pool.idle_usage` and `storageByteHours` from `storage.usage` across both stores. `GET /v1/sessions/{id}/usage` and `GET /v1/admin/environments/{name}/usage` sum `pod_minutes` from the `billing_events` table, so they include `session.pod_usage` with no change to either handler.

### `pool.idle_usage`

**What it counts.** The event reports pod minutes that serve no session, per window of `billing.usageIntervalSeconds`. Its `pool_ownership` field names the subject:

- `owned`: the pods of an owned pool, attributed to the pool's `ownerTenantId` (decision 2).
- `shared_pinned`: the pinned idle pods of a shared pool (§5.2 **Pinned idle inventory.**), attributed to the tenant in each pod's `lenny.dev/tenant-id` label (decision 11). A shared pool produces one event per pinned tenant, and the event carries `idle_pod_minutes`, `unsampled_minutes`, and `pod_count_max` and none of the other counts. The unpinned pods of a shared pool reach no tenant, and the operator bears them.

`tenant_id` is the tenant the subject is attributed to, and `user_id` and `session_id` are absent. The event's fields are `pool_name`, `runtime_name`, `runtime_revision`, `pool_ownership`, `window_start`, `window_end`, `usage_window_key`, the resource fields of `session.pod_usage` without the session ones, and these counts:

| Field | Pods counted |
| :-- | :-- |
| `warming_pod_minutes` | Pods created and not yet in the `idle` phase |
| `idle_pod_minutes` | With `pool_ownership: owned`, pods in the `idle` phase, claimable and pinned. With `pool_ownership: shared_pinned`, the tenant's pinned idle pods |
| `hold_pod_minutes` | Pods whose claim is in the `reserved` hold between sessions (§4.6.1 **Reserved hold**) |
| `draining_pod_minutes` | Pods draining with no session |
| `reserved_pod_minutes` | The part of the preceding counts on pods marked `spec.reserved` under [DR-10](tenant-derived-runtimes-design.md#dr-10-capacity-reservation) |
| `idle_slot_pod_minutes` | The empty slots of concurrent pods that serve at least one session, in pod minutes, under "Concurrent pods" |
| `unsampled_minutes` | Minutes of the window that no sample covered within `billing.idleAccrualMaxGapSeconds` (the gap cap, default 600, under "Accrual"), which bill nothing |
| `pod_count_max` | The largest number of such pods at one sample |

A pod that holds a session is billed through `session.pod_usage` and is absent here. A pod in the `failed` phase and a quarantined pod are absent, because the platform and the operator bear those (forensics decision 16). A pool whose pods carry different resources in one window, after a class change, produces one event per distinct set of resource values. A pool that keeps several pod sets during a rollout ([RV-3](runtime-revisions-design.md#rv-3-pods)) produces one event per pod set, and `runtime_revision` names the revision the pod set was built from, so an operator can tell a rollout's extra pods apart from the pool's usual ones.

**Accrual.** The WarmPoolController already integrates idle pods on each reconcile. It gains a durable accrual in a `pool_usage_accrual` table, keyed by pool, runtime revision, tenant, window start, and a hash of the resource values, holding `tenant_id`, `pool_ownership`, minutes per state, `unsampled_minutes`, and the last sample's time and counts. When the controller creates an accrual row, it takes the tenant from the pool row's owner on an owned pool and from the pod's pin label on a shared pool, so the last window of a deleted pool or a drained pinned pod still has a tenant. Each reconcile adds the minutes since the last persisted sample, using the counts at that sample, so a restart or leader change continues the integral from the persisted sample. The following rules hold the integral under failure:

- Each write is an update conditional on the `last_sample_at` the controller read. During a leader overlap, the second writer matches no row, rereads, and adds nothing for the interval the first writer counted.
- An interval that crosses a window boundary is split at the boundary, and each part accrues to its own window.
- An interval longer than `billing.idleAccrualMaxGapSeconds`, default 600, accrues its first `billing.idleAccrualMaxGapSeconds` at the earlier counts, and the rest goes to `unsampled_minutes`, so counts that went stale during an outage do not bill the outage.
- A window is ready for emission only after a sample at or after its end, or after the pool's deletion, which the controller records as a final sample.

The controller already holds a Postgres connection for the `agent_pod_state` mirror. The gateway's leader-elected task converts each closed window into one `pool.idle_usage` event (decision 9). `lenny_warmpool_idle_pod_minutes` stays as it is.

**Ownership.** Until [DR-5](tenant-derived-runtimes-design.md#dr-5-owned-pools) lands, no pool has an owner, and every `pool.idle_usage` event carries `pool_ownership: shared_pinned`.

### `storage.usage`

**What it counts.** For each tenant, `store`, and `artifact_type` with a live row in the window or a row deleted in it, the event reports, per window of `billing.usageIntervalSeconds`:

| Field | Type | Meaning |
| :-- | :-- | :-- |
| `store` | string | `artifact` for the `artifact_store` ledger, and `escrow` for the legal-hold escrow records (decision 14) |
| `artifact_type` | string | The ledger's `artifact_type` value, or the escrow record's `resource_type` on `store: escrow` |
| `bytes_held_start`, `bytes_held_end` | uint64 | Sum of the row sizes over rows live at each bound |
| `byte_hours` | float64 | Sum over rows of the row's size times the hours of the row's life inside the window |
| `legal_hold_byte_hours` | float64 | The part of `byte_hours` on rows with `legal_hold` set, absent on `store: escrow` |
| `bytes_written`, `bytes_deleted` | uint64 | Sizes of rows created, and of rows soft-deleted or released, in the window |
| `object_count_end` | uint64 | Live rows at the window's end |
| `window_start`, `window_end`, `usage_window_key` | | As for the other periodic events |

On `store: artifact`, a row's size is `artifact_size_bytes`, and its life runs from `created_at` to `soft_deleted_at`, or to the window's end when it is live. Checkpoint reservations without an `artifact_store` row are quota reservations and are absent. A checkpoint reservation is the storage quota the gateway charges for a checkpoint before its bytes land and its row exists (§11.2 **Storage quota enforcement mechanism.**). `user_id` and `session_id` are absent.

**Rows the sweep would remove.** The tombstone sweep deletes a row 24 hours after its deletion by default, and a stalled emitter would then lose a deleted row's last hours. The sweep therefore also requires `soft_deleted_at` to precede the watermark for the row's tenant and `artifact_type`, which is the end of the last window whose `storage.usage` event the emitter has read back from `billing_events` in Postgres. The emitter advances the watermark only after that read, so an event held in the Redis stream or the in-memory buffer does not release a tombstone. A stalled emitter keeps tombstones, and `StorageUsageEmitterStalled` fires when the watermark is older than 2 windows.

**Legal-hold escrow copies.** §12.8 Phase 3.5 copies a force-deleted tenant's held resources to `legal-hold-escrow/{original_tenant_id}/{resourceType}/{resourceId}` in the region's escrow bucket and writes a `legal_hold_escrow_records` row for each copy. `storage.usage` bills those copies to the original tenant as `store: escrow`, whoever set the hold (decision 14). The record gains `escrow_object_bytes`, which the migrator writes with the size of the object it wrote, and a row's life runs from `migrated_at` to `released_at`, or to the window's end while the hold stands. The tenant's `TenantState` reaches `deleted`, and the tenant keeps its tombstone row, its tenant ID, and its billing sequence (§12.8 Phase 4), so the escrow emitter writes these events under that tenant ID after Phase 4 completes, with windows starting at the earliest `migrated_at`. Phase 4 therefore deletes none of them, and a tenant whose `billingErasurePolicy` is not `exempt` keeps only its escrow events. Under `billingErasurePolicy: exempt`, Phase 4 keeps the tenant's billing events until `billing.retentionDays` ages them out. The escrow watermark per tenant and `resource_type` sits beside the records in the regional platform Postgres, outside the stores Phase 4 deletes, and the emitter deletes it once every record of the tenant is released and its last window is read back. The escrow garbage-collection (GC) release deletes no record, so a released row stays readable for its last window.

The forensics security-hold copies are a different mechanism. [`forensics-evidence-preservation-design.md`](forensics-evidence-preservation-design.md) writes them, under its proposal [FE-3](forensics-evidence-preservation-design.md#fe-3-platform-only-holds-and-a-security-retention-class), to the `security-hold/` prefix of the same bucket, keeps its own records, and makes the operator pay for them under its decision 16. The escrow emitter reads `legal_hold_escrow_records` alone, so no security-hold copy reaches `storage.usage`. The daily reconciliation below lists the artifact bucket and leaves the escrow bucket out.

**Daily reconciliation.** A leader-elected gateway task compares the ledger with the object store once a day, from `billing.storageReconciliation.source`:

- `listing`, the default: `ListObjectVersions` and `ListMultipartUploads` under each `/{tenant_id}/` prefix, rate-limited by `billing.storageReconciliation.requestsPerSecond`.
- `inventory`: the provider's inventory report (S3 Inventory, Cloud Storage inventory reports, or Azure Blob inventory), read from the location the operator configures. MinIO uses `listing`.

For each tenant and object type it reports, under `lenny_storage_reconciliation_difference_bytes{tenant_id, kind}` and `..._objects`, the kinds `missing_object` (a live row with no current object), `orphan_object` (a current object with no row), `tombstoned` (a current object whose row is soft-deleted), `size_mismatch`, `noncurrent_version`, `delete_marker`, and `incomplete_multipart`. `StorageLedgerDrift` fires when `missing_object`, `orphan_object`, or `size_mismatch` exceeds `billing.storageReconciliation.alertFraction` of the tenant's ledger bytes, default 0.01, on consecutive runs. The task writes `storage.reconciliation_completed` to the audit log with the totals.

**Stale views.** A listing or an inventory report is older than the ledger it is compared with. `cataloging.Put`, `RecordPut`, and `Copy` write the object before the row, and an inventory report lags by up to a day, so an artifact written near the snapshot appears in one source and not the other. Each run therefore records its snapshot time, which is the start of its listing or the generation time of the inventory report, and compares only rows whose `created_at` precedes the snapshot time less `billing.storageReconciliation.marginSeconds`, default 3600. A row becomes a confirmed `missing_object` or an overstated `size_mismatch` only when a direct `HEAD` on its key agrees on two consecutive runs. A run that receives any listing or inventory error for a tenant, or whose candidate `missing_object` bytes exceed `billing.storageReconciliation.maxMissingFraction` of the tenant's ledger bytes, default 0.05, aborts for that tenant, writes no correction, and fires `StorageReconciliationAborted`.

**Corrections.** A confirmed `missing_object` means the ledger billed bytes the store did not hold. The task emits a `billing_correction` with reason `STORAGE_RECONCILIATION` against each `storage.usage` event since the last run that saw the object, with the row's bytes removed, sets `reconciliation_missing_at` on the row so that later `storage.usage` events leave it out, and fires `StorageLedgerMissingObject` naming the tenant and the key. The task never deletes or soft-deletes a row. The operator decides whether to soft-delete the row through the guarded path in §12.5 (**GC concurrency model (single-writer + soft-delete guard).**), which lowers the quota counter. A confirmed `size_mismatch` with the ledger larger is corrected and alerted the same way. Reconciliation never raises a tenant's bill, so an orphan or a larger object is reported and left to the operator (decision 12).

Each correction starts from the event's current values, which are those of its latest correction when one exists and the original's otherwise, because §11.2.1 applies corrections to one original in sequence order with the latest taking precedence, and a correction computed from the original would undo an earlier one. `STORAGE_RECONCILIATION` is a Category 1 code, and a correction of a periodic event carries the full replacement set of the corrected event's quantity fields. One run can correct every hourly event since the object was last seen, so `BillingCorrectionRateHigh` computes its rate over corrections with other reason codes, and `StorageLedgerDrift` and `StorageLedgerMissingObject` alert on `STORAGE_RECONCILIATION` corrections.

**Cases the ledger misses.** The ledger counts the current object of each artifact it records. The object store bills for more, and the reconciliation reports what it can see:

- **Versioning.** A deleted or overwritten object leaves a noncurrent version for the expiry period, 1 day on MinIO under §12.5, and a delete marker. The ledger stops counting at deletion. The reconciliation reports both kinds, and the operator prices them as overhead or sets a shorter expiry.
- **Lifecycle rules and manual deletes.** An operator's lifecycle rule or a manual delete removes an object the ledger still counts. The reconciliation reports it as `missing_object`, corrects the bill once confirmed, and leaves the row to the operator.
- **Soft-deleted objects.** A soft delete tags the object and leaves it in the bucket until the tombstone sweep's hard prune, 24 hours later by default, and the ledger stops counting at `soft_deleted_at`. The provider bills those bytes, and the reconciliation reports them as `tombstoned`.
- **Abandoned multipart uploads.** A gateway that crashes during a multipart upload leaves parts the ledger never recorded, and the provider bills them until they are aborted. The chart's lifecycle Job installs no abort rule. MinIO removes stale uploads under its own `stale_uploads_expiry` setting, and a cloud store needs an `AbortIncompleteMultipartUpload` lifecycle rule or its equivalent, which the operator guide names with a 1-day period. The reconciliation reports what remains.
- **Activity evidence.** `EvidenceStore` batches are metered as `evidence.usage` by the forensics design and are absent from `storage.usage`.
- **Git mirror stores.** `lenny-git-mirror` holds repositories on persistent volumes shared across tenants. Their bytes are reported per volume by `kubelet_volume_stats_used_bytes` and reach no tenant's bill.
- **Postgres-held data.** Session messages, session logs, the session tree archive, the audit log, and agent memory (`session_messages`, `session_logs`, `session_tree_archive`, `audit_log`, and `agent_memory`) are rows in Postgres. Their size per tenant can only be estimated, because TOAST, compression, indexes, WAL, and replicas do not divide by tenant. Under decision 13, no billing event carries them. The daily reconciliation task sets the gauge `lenny_postgres_tenant_bytes_estimate{tenant_id}` from `pg_column_size` summed per tenant over those tables, reading one tenant at a time on the read replica when one is configured and on the primary otherwise, and the operator decides from monitoring whether to price it. The gauge carries one series per tenant and no table label, so its cardinality grows with tenants alone, as §16's cardinality statement requires.
- **Pod ephemeral disk.** Billed as the reserved ephemeral storage on `session.pod_usage` and `pool.idle_usage`, with no measured use (decision 10).
- **Forensic security-hold copies.** Security-hold copies under the `security-hold/` prefix of the escrow bucket and held evidence are paid by the operator (forensics decision 16), so they are absent from tenant events and reported by the forensics design's metrics. The §12.8 legal-hold escrow copies are billed as `store: escrow` under "Legal-hold escrow copies".

### Writing periodic events

`session.pod_usage`, `pool.idle_usage`, and `storage.usage` are appended through the `EventStore` with the per-tenant sequence of §11.2.1 and its Redis and in-memory fallbacks. Each carries `usage_window_key`, a SHA-256 over the event type, tenant, subject (session and pod, pool and revision, or store and artifact type), window start, and resource hash. The billing table gains a unique index on `(tenant_id, usage_window_key)`, partial on a present key.

`Append` and `InsertFromStream` both insert with `ON CONFLICT DO NOTHING` and no conflict target, which absorbs a duplicate on the `usage_window_key` index and on the `stream_entry_id` index alike. A named target absorbs a duplicate on its own index alone, and a duplicate on the other raises 23505, Postgres's unique-violation error. From `InsertFromStream`, `flushEntries` then stops at the rejected entry, and every later entry in the tenant's Redis billing stream waits behind it. From `Append`, the failover pipeline treats the error as a primary failure and routes the duplicate to the stream. A duplicate insert returns the committed row, and a Tier 2 test pins both paths with a duplicate key. The current code has no `usage_window_key` and therefore no second index to collide on, so this is a requirement of the design, and `BUILD-GAPS.md` carries no finding for it.

`nextval` runs before the insert, so a no-op insert would still consume a sequence number, and §11.2.1 states that a gap indicates lost events and should trigger replay. Both paths therefore look up `usage_window_key` in the insert transaction before drawing `nextval`, and a found key ends the transaction with no number drawn. Two concurrent inserts of one key can still both draw a number, and the loser leaves a gap. §11.2.1 gains the rule that a gap a replay leaves empty is benign, as a rollback gap is today. A leader that re-runs a window after a failover therefore inserts nothing twice, and the table stays insert-only. A wrong event is changed only by a `billing_correction`.

The §11.2.1 null/absent contract extends to the new fields, each present only on the event types above. §11.2.1's description of `tenant_id` as the tenant "that owns the session" becomes the tenant the event is billed to, because `pool.idle_usage` and `storage.usage` have no session.

An operator-initiated correction of a new event type always takes the dual-control path, because the `billing.dualControlThreshold` sum adds tokens and pod minutes and has no unit for bytes.

## Residual risks

- **Idle sampling.** Idle accrual changes only at reconciles, and a change between them is approximated by the earlier count.
- **Reserved disk.** A pod is billed its reserved ephemeral storage whether it writes nothing or fills the reservation, and a pod with no ephemeral storage request bills no disk beyond `warmCloneBytes`.
- **Provider bills differ.** `byte_hours` from the ledger leaves out noncurrent versions, delete markers, minimum storage durations on cold storage classes, request charges, and egress. The reconciliation reports noncurrent versions and delete markers, and the operator prices the rest.
- **Apportioning shared pods.** The per-slot share charges a session for its slot whatever the session uses, and empty slots on shared pools reach no tenant.
- **Unsampled idle time.** Idle minutes beyond the gap cap bill nothing, so a long controller outage leaves idle cost with the operator.
- **Missing rows left to the operator.** A confirmed `missing_object` keeps its row and its quota charge until the operator acts on the alert.
- **Unattributed costs.** Node-level costs and the share of a node that no pod requests reach no event.
- **Stalled emitter.** The tombstone watermark holds rows while the emitter is stalled, so `artifact_store` grows until the alert is handled.
- **Reconciliation cost.** Listing a large bucket takes time and requests, and an inventory report lags by up to a day or more, depending on the provider, so a difference can persist for that long.
- **Visibility to tenants.** A tenant's `billing-viewer`, the role that reads its tenant's usage and metering data, reads the class sizes, pod UIDs, and pool names in its own events.
- **Postgres-held data.** Session messages, logs, the tree archive, the audit log, and agent memory reach no bill, and the per-tenant gauge is an estimate that can be far from the storage cost. The daily `pg_column_size` pass adds read load on Postgres.
- **Owned pools wait on DR-5.** `pool.idle_usage` reports subjects with `pool_ownership: shared_pinned` alone until [DR-5](tenant-derived-runtimes-design.md#dr-5-owned-pools) lands. The unpinned idle pods of shared pools stay the operator's.
- **Pinned idle pods.** A tenant sees a figure with `pool_ownership: shared_pinned` for pods the platform kept for it and that it did not ask to keep. The operator decides whether to price it.
- **Escrow billed after deletion.** `store: escrow` events arrive under a tenant ID whose `TenantState` is `deleted`, until the hold is cleared, so the operator's billing system keeps that account open to receive them. The tenant is billed for every escrowed hold, including one the operator set.

## Decisions

The owner has settled decisions 1 to 15, and the design above is written to them. Decisions 6 to 15 each state the settled option, its cost, and the alternative the owner rejected.

- **Decision 1: pricing by actual resources.** Settled. Billing lets an operator price usage by actual resources, and events record the resource class name and the pod's actual resources, because an operator can redefine a class at any time.
- **Decision 2: idle billing for owned pools.** Settled. A periodic billing event reports a tenant's owned pools' idle and reserved pod minutes, attributed to the owning tenant. This is `pool.idle_usage`. Decision 11 extends it to pinned idle pods on shared pools.
- **Decision 3: storage usage.** Settled, and amended by the owner with decision 10. A periodic `storage.usage` event per tenant and artifact type from the `artifact_store` ledger, as bytes held and byte-hours, with a daily reconciliation against the object store that reports differences as a metric and an alert and emits `billing_correction` where appropriate. The design states the cases the ledger misses, bills pod ephemeral disk by its request with sampled use, and leaves forensic escrow copies to the operator under [forensics decision 16](forensics-evidence-preservation-design.md#decisions). The amendment, in the owner's words "bill reserved disk only", bills pod ephemeral disk by its reserved request and removes sampled use. The forensic escrow copies this decision names are the security-hold copies, and decision 14 bills the separate §12.8 legal-hold escrow copies.
- **Decision 4: resource classes in configuration.** Settled, in the owner's words "Ability to override the default classes is important. In fact, I think there shouldn't be any values hardcoded in the code." The code holds no class, the chart ships `small`, `medium`, and `large` as defaults an operator changes or replaces, the embedded stack carries the same defaults, a pool naming an undefined class is refused at write, the controller checks each class against the tmpfs reservation, and the specification states the classes as chart defaults and defines the override.
- **Decision 5: resource fields on session usage.** Settled. Session usage events carrying `pod_minutes` gain the class name, the pod's actual CPU and memory requests and limits at the time, the isolation profile, and, for a pod serving several sessions, its `maxConcurrentSessions`.
