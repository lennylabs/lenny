## Problem

"Terms", after "Scope", defines the vocabulary this document uses.

A person who works with a coding agent often types a correction while the agent is busy: "use the staging database instead", or "skip the tests for now". Most agent harnesses accept such a message at any time and fold it into the agent's work at its next model step, after the tool calls it is running finish **[external]**. Claude Code, the Claude Agent SDK, Codex, Cursor, and the Vercel AI SDK behave this way by default. They also offer a mode that holds the message until the agent's turn ends, and a mode that stops the agent and sends the message next.

Lenny offers only the queue and interrupt modes, and the tree offers neither in the form the specification states **[source]**:

- The specification buffers every message that arrives while a tool call is in flight, and the only mid-turn delivery it defines interrupts the runtime ([§7.2](../spec/07_session-lifecycle.md#72-interactive-session-model), "Message delivery routing", paths 4 and 5).
- The gateway executor pairs each message with one `response` through a turn token, discards a `response` that no message caused, and holds the session's delivery lock for the whole turn. A message sent mid-turn waits for the running turn to end before anything answers it, and a parent session's `lenny/send_message` call blocks until the child's turn ends.
- `capabilities.injection.modes` appears in runtime declarations, and no section says what a mode means.

The wire protocol between the adapter and the runtime does not cause any of this: the `CH-MSGSOCK` card already requires a runtime to handle a `message` that arrives before a pending `tool_result`. The alternation comes from the gateway's delivery policy, its executor, and the runtime SDKs.

The owner asked for a general machinery that covers today's cases and later ones. This design gives every message a delivery intent, lets each runtime declare the intents it accepts, gives every message an explicit state from acceptance to consumption, and keeps the gateway's custody of a message until the runtime reports that it consumed it. The non-interrupting mode the harnesses default to becomes the intent `steer`, which a runtime declares when it can take a message at any time.

A person who watches a coding agent also expects to see what it does while a turn runs: the tool it runs, the plan it follows, the text it writes, and the questions its harness asks before it runs a command. Every harness surveyed on 2026-11-10 streams these **[external]**. Lenny's path from the runtime to the client carries none of them in a form a client can use **[source]**. The gateway's executor drops every runtime frame other than `response` and an approval-gated `tool_call`, the `status` frame included. An output part cannot grow while it streams. `lenny/output` reaches the gateway on a different link from the stdout frames and skips the `PostAgentOutput` interceptors and the transcript. A harness's permission request for a tool that Lenny does not route has no way to reach the client. "MD-15" to "MD-21" add these reports.

## Scope

**Added:**

- Delivery intents `steer`, `queue`, and `interrupt` on every message, with a rule for adding intents ("MD-1" and "MD-14").
- The definition of `capabilities.injection.modes` as the intents a runtime accepts, and `capabilities.injection.defaultMode` ("MD-2").
- Inbox states, custody until consumption, at-least-once delivery up to consumption, deduplication by message id, and the `consumed_unrecorded` state that reports a message consumed after the checkpoint a session resumes from ("MD-3").
- Turn accounting on `CH-MSGSOCK`: `response` lists the message ids it consumed, a `consumed` frame reports consumption during a turn, and a `response` that no message caused is accepted ("MD-4").
- Retraction: a runtime may retract a message it generated, by id, and receives `retracted`, `too_late`, or `unknown` ("MD-11"). A client may retract a message it sent through `DELETE /v1/sessions/{id}/messages/{messageId}` and the generated MCP tool ("MD-7", O5).
- A drain call in the runtime SDKs that returns the messages queued for a session between model steps ("MD-12").
- The session events `message_state` and `turn_end`, and per-message delivery receipts on REST and MCP ("MD-7").
- Two rules for sessions created on a provider surface. Client tools are offered only in turns a client request caused, and a turn that no client request caused never appears in a provider-surface response ("MD-8", O3).
- Activity: the `activity` frame and SessionEvent kind, with an open `kind`, the operations `start`, `update`, `patch`, `append`, and `end`, turn and session lifetimes, recording that the runtime asks for under a rate cap, a size cap, and the current state of open activities on attach ("MD-15", A2, A3, A7, and A10).
- Streaming output: the stdout `output` frame as the only output path, with `append`, `end`, and `reset` on a streaming part ("MD-16", A5 and A6).
- Reasoning as a `reasoning_trace` part with `signature`, `encrypted`, and `redacted`, or as a `thinking` activity, as the runtime chooses ("MD-17", A1).
- File parts that name a workspace path, which the adapter uploads to the artifact store ("MD-18", A11).
- `lenny/request_approval`, which brings a harness's own permission requests into the tool-use approval path, with a policy for unattended sessions ("MD-19", A4).
- The session events `turn_start`, `usage`, and `activity`, and `status` and `usage` on `turn_end` ("MD-20", A8).
- The projection of each report on REST, MCP, A2A, the provider surfaces, and AG-UI, under the rule that every report translates to AG-UI without loss ("MD-21", G3).

**Changed:**

- The [§7.2](../spec/07_session-lifecycle.md#72-interactive-session-model) delivery paths are rewritten as named paths keyed on the turn state and the intent ("MD-5"). The `ready_for_input` term leaves the specification (O1).
- The envelope's `delivery` member takes intents in place of `immediate` and `queued` ("MD-1").
- The executor's turn token and the turn-long delivery lock are replaced by a writer, a frame reader, and a turn waiter ("MD-6").
- `POST /v1/sessions/{id}/messages` and `lenny/send_message` return receipts at once, with consumption and output reported as session events ("MD-7").
- The client-tools hold rule applies only to runtimes that do not declare `steer`, and the cold-history builder gains an ordering rule ("MD-10").
- An inbox delivery to a held session on a provider surface is delivered on arrival under the ordinary intent rules, in place of waiting for the next client turn ("MD-8", O3).
- The reference runtime declarations of [§26](../spec/26_reference-runtime-catalog.md#26-reference-runtime-catalog) ("MD-13").
- `response.output` carries only the parts the runtime has not already emitted on an `output` frame ("MD-16").
- The executor's frame reader routes every runtime frame and no longer blocks while a tool call awaits approval ("MD-6", "MD-19").
- §13's exception to gateway-mediated file delivery for checkpoint packs extends to the packs of output files, under the checkpoint capability model ("MD-18").

**Removed:**

- The executor's turn token (`attachConn.token`) and the rule that discards a `response` with no registered turn.
- The synchronous `output` member of the REST message response.
- The delivery timeout of 30 seconds that §7.2 measures against a consumption acknowledgement no frame carries.
- `lenny/output`, whose output reaches the gateway on its own link ("MD-16", A6).

**Out of scope:**

- Steering by a provider-surface client. A Chat Completions, Responses, or Messages API client cannot correct its own running turn, because each request is one turn, as the provider APIs define it ("MD-8").
- Scheduled delivery, priority ordering, context-only messages, and the other future cases of "MD-14". The machinery accommodates them, and none ships in v1.
- Retraction of output and session events. Output already streamed cannot be recalled, and output the gateway has not yet sent to a client is ignored for now ("MD-11", "Blast radius"). A runtime's `reset` of a part that is still streaming is not a retraction, and "MD-16" states it.
- Activity on the provider surfaces, and Messages API event types for it, which a later version may add behind a request header ("MD-21", A9).
- Relay of a delegated child session's activity into its parent's stream ("MD-15", A7).
- An AG-UI endpoint. v1 states the projection and builds no adapter ("MD-21", G3).
- Multi-thread sessions, which the owner left out of v1 under G2. `threadId` keeps its v1 meaning.
- The fix of each tree defect as a separate change. The owner decided that the defects under "Defects found while verifying" are fixed later under a holistic plan.

## Terms

| Term | Meaning |
| :-- | :-- |
| Message | One `MessageEnvelope` of type `message` that a sender addresses to a session: a client message, an inter-session message, or a system message. |
| Delivery intent (intent) | The value of a message's `delivery` member, which states when the message reaches the runtime relative to the runtime's current turn: `steer`, `queue`, or `interrupt`. |
| `steer` | Deliver the message now, without interrupting. The runtime reads it at its next model step, after the tool calls it is running finish, and places it after their results. Without a running turn, the message starts one. |
| `queue` | Hold the message until the runtime's current turn ends, then deliver it as the start of a new turn. |
| `interrupt` | Stop the runtime's current work at a safe point, then deliver the message as the start of a new turn. |
| Default intent | The intent a message takes when its sender names none: the runtime's `defaultMode`, which is `steer` when the runtime declares `steer` and `queue` otherwise. |
| Turn | The runtime's work from the delivery of a message to an idle runtime, or from output the runtime starts on its own, until its next `response` frame. |
| Open turn | A turn whose `response` has not arrived. The gateway tracks it per session from the frames it writes and reads ("MD-4"). |
| Unsolicited response | A `response` that closes a turn the runtime started on its own, for example after background work or a child's result. |
| Causing message | The message whose delivery opened a turn. A turn the runtime starts on its own has no causing message. |
| Client request | A message from the session's client on any client surface: REST, MCP, Chat Completions, Responses, or the Messages API. A turn whose causing message is a client request is caused by that request. A turn caused by another session's message, a system message, or an external message is not caused by a client request. |
| Consumption | The runtime's acceptance of a delivered message into its own handling: the message entered its model history, or the runtime acted on it without a model call. The runtime reports it by message id. |
| Inbox | The gateway's per-session store of messages it has accepted and not yet released: the session inbox of §7.2, extended to hold delivered messages until consumption ("MD-3"). |
| Inbox state | One of `pending`, `delivered`, `consumed`, `consumed_unrecorded`, `retracted`, `expired`, `dropped`, and `superseded`, defined in "MD-3". |
| Retraction | A sender's request that the gateway never deliver a message it sent. It succeeds only while the message is `pending`, and for a client tool call only while the call is pending on a REST or MCP session ("MD-11"). |
| Retraction result | The answer to one retracted id: `retracted`, `too_late` (the recipient already received it, or the surface cannot withdraw it), or `unknown` (the id names nothing this sender may retract). |
| Custody | The gateway's obligation to keep a message and redeliver it until the runtime reports its consumption (O4). |
| Drain call | The runtime SDK call that returns the messages queued in the runtime process for a session while a handler runs ("MD-12"). |
| Provider surfaces | The Chat Completions, Responses, and Messages API surfaces, whose clients follow a provider's API. |
| Activity | A runtime's report of what it is doing, keyed by an `id` the runtime chooses, which the gateway shows to clients and keeps out of model history ("MD-15"). |
| Activity kind | The open string `kind` of an activity. "MD-15" lists the conventional kinds, and a custom kind takes the `x-<vendor>/` prefix. |
| Open activity | An activity that has started and has not ended. |
| Recorded activity | An activity started with `record: true`, whose final state the gateway writes to the transcript when it ends ("MD-15"). |
| Streaming part | An output part emitted with `status: "streaming"`, which later `output` frames grow by its `id` until it ends or is reset ("MD-16"). |
| File part | A `file` output part that names a workspace path, which the adapter uploads to the artifact store before the gateway releases the part ("MD-18"). |
| Output file | The stored copy of a file part's file: an `output_files` row with the file's chunk list, and the packs that hold its chunks ("MD-18"). |
| Export | The copy of one file part's file to the artifact store over the `ExportOutputFile` stream, from the gateway's `ExportStart` to `ExportReady` or a failure ("MD-18"). |
| `exportTimeoutSeconds` | The pool setting, 900 seconds by default, counted from an export's `ExportStart`, after which an export that has not reached `ExportReady` fails. The same span, counted from a part's first frame, bounds a part's wait for the export cap ("MD-18", "Clocks"). |
| Export cap and export queue | A session runs at most `files.maxConcurrentExports` exports at once, 2 by default. A file part over that cap waits in the session's export queue, which holds at most `files.maxQueuedExports` parts, 8 by default ("MD-18", "Copy"). |
| `output_file_exports` | The gateway's durable record of each file part, a Postgres table keyed by session and part, with the export's state, its clocks, its quota reservation, the coordination generation that drives it and guards every change to the row, and its failure notice until the runtime acknowledges it ("MD-18", "Export record"). |
| Unopened part | A file part that the adapter relays with the member `unopened: true` because it already holds its cap of open export descriptors for the session. The gateway refuses exactly the parts that carry the marker, with `too_many_exports` ("MD-18", "Freeze"). |
| `ExportAbort` | The message with which the gateway ends a failing export on the `ExportOutputFile` stream, with the failure reason, in place of the `Checkpoint` stream's `CheckpointAbort` ("MD-18", "Refusals"). |
| Seal window ceiling | The chart value `gateway.workspaceSealMaxDurationCeilingSeconds`, 600 seconds by default, which the gateway reads as `--workspace-seal-max-duration-ceiling-seconds`. No pool and no runtime may set a seal window above it, and the chart computes the default claim orphan timeout from it ("MD-18", "Seal window"). |
| `suspend_hold_expired` | The failure reason of a file part that still waits for the export cap when the hold of `maxSuspendedPodHoldSeconds` on an explicitly suspended session ends ("MD-18", "Export lifecycle"). |
| Pack nonce | The random 128-bit value the adapter writes into the footer of every pack it builds, for checkpoints and exports alike, so no two packs share a pack ID ("MD-18", "Copy"). |
| `Repr-Digest` | The HTTP header of RFC 9530 that carries a digest of the full representation a response selects, whatever its content coding and range. `GET /v1/blobs/{ref}` sends the output file's whole-file SHA-256 in it ("MD-18", "Download"). |
| `output_failed` | The frame the adapter writes to the runtime, and the session event the gateway emits, when a file part fails, with the reason, so the runtime can emit the file again. The gateway keeps each notice until the runtime acknowledges it with `output_failed_ack`, and sends it again after a resume ("MD-18", "Failure notice"). |
| `CH-OUTPUTFILE` | The channel this design adds for the `ExportOutputFile` stream on the gateway's gRPC link to the adapter ("MD-18", "Channel"). |
| Harness approval | A permission request that a harness raises for a tool it runs itself, which the runtime forwards with `lenny/request_approval` ("MD-19"). |
| AG-UI | The Agent-User Interaction Protocol, an open event protocol between agent backends and user interfaces that CopilotKit maintains. Version 1.0 was published on 2026-09-17 **[external]**. |

## High-level design

Every message a session receives says when it should reach the runtime. A message marked `steer` goes to the runtime at once, and the runtime reads it at its next model step without stopping what it is doing. A message marked `queue` waits until the runtime finishes its current turn. A message marked `interrupt` stops the runtime's work and goes next. Most clients name no intent: the message takes the runtime's preference, which is `steer` for a runtime that declares it. A client that wants another behaviour sets one field on that message.

The gateway keeps each message from the moment it accepts it until the runtime reports that it consumed it, and records the message's state along the way. A send call answers as soon as the message is written to the runtime or held, and the client follows consumption and output on the session's event stream. Because the runtime reports which messages each reply consumed, the gateway no longer assumes one reply per message: one turn can consume several messages, and a runtime can reply without any new message.

The rest of this section states each part in the design's terms, which "Terms" above defines.

**Intents (MD-1).** The envelope's `delivery` member carries `steer`, `queue`, or `interrupt`. Absent means the default intent. The values mirror the Claude Agent SDK's `priority` values `next`, `later`, and `now`.

**Declaration (MD-2).** `capabilities.injection.modes` lists the intents a runtime accepts, and must include `queue`. `steer` is available at every integration level, and `interrupt` requires Full. `defaultMode` names the runtime's preference. An explicit intent the runtime does not declare is refused.

**States and custody (MD-3).** A message is `pending` while the gateway holds it, `delivered` once written to the runtime, and `consumed` once the runtime reports it. It may also end `retracted`, `expired`, or `dropped`, and `superseded` is reserved for a later intent. Custody ends when the runtime reports consumption (O4). The gateway redelivers a `delivered` message after a pod loss, and the adapter and the SDK drop a message id they have already consumed. A message consumed after the checkpoint a session resumes from is not redelivered: it becomes `consumed_unrecorded`, and its sender decides whether to send it again.

**Turn accounting (MD-4).** `response` gains `consumed`, a list of message ids. A new `consumed` frame reports consumption during a turn (O2). A `response` with no message to attribute is an unsolicited response and is recorded. The gateway tracks an open turn from the frames it writes and reads, which replaces `ready_for_input` (O1).

**Delivery paths (MD-5).** §7.2's numbered paths become named paths: the reply path, the dead-letter path, the resume path, the direct path, the steer path, the interrupt path, and the queue path.

**Executor (MD-6).** A writer delivers an envelope and returns. A reader routes every frame. A turn waiter lets a caller that needs a turn's output wait for the turn that consumed its message. The delivery lock covers the routing decision and the write, and never a turn.

**REST and MCP (MD-7).** A send returns one receipt per message at once. `message_state` and `turn_end` events report consumption and turn ends.

**Provider surfaces (MD-8).** A request remains one turn. The adapter waits for the turn that consumed its message. An inbox delivery to a held session is delivered on arrival under the ordinary intent rules. A turn that no client request caused carries no client tools, and its output never appears in a provider-surface response (O3).

**Inter-session messages, system messages, and delegation (MD-9).** `lenny/send_message` carries an intent and returns at once. A parent can redirect a running child with `steer`.

**Client tools (MD-10).** A `steer` runtime receives inbox deliveries while client calls are pending and places them after the results. A turn that an inbox delivery causes carries no client tools (O3). The cold-history builder never places an entry between calls and their results.

**Retraction (MD-11).** A runtime writes a `retract` frame naming ids it generated and receives a `retract_result` frame with `retracted`, `too_late`, or `unknown` for each. A pending client tool call on REST or MCP is cancelled and the client receives a retraction event. A returned call on a provider surface cannot be withdrawn, so the answer there is `too_late`. A message the runtime sent to another session is retracted while it is `pending` in the recipient's inbox and is `too_late` once delivered. Output and session events are not retracted in v1.

**SDKs (MD-12).** The drain call returns messages queued behind the running handler. The SDK reports consumption, drops duplicate ids, and can write an unsolicited response.

**Reference runtimes (MD-13).** `claude-code`, `codex`, and `chat` declare `steer`. The others declare `queue` and `interrupt` until their harnesses' steering is verified.

**Extension (MD-14).** A new intent states its gateway behaviour per turn state, its runtime obligation, and its states, and is declared when the runtime has to act on it.

During a turn the runtime also reports what it is doing. Activity frames show tools, plans, steps, and other progress, and the gateway keeps the current state of every open activity, so a client that connects mid-turn sees it. Output streams as the model writes it. Reasoning is content or activity, as the runtime chooses. A file the agent produces is copied to the artifact store and offered to the client as a download. A harness's own permission requests reach the client through the approval flow that Lenny's tools use. Every report translates to AG-UI without loss.

**Activity (MD-15).** An `activity` frame starts, updates, patches, appends to, or ends an activity by `id`. `kind` is open, and conventions name the common kinds. The gateway keeps open activities and sends them on attach, records an activity in the transcript only when the runtime asks, caps recorded activity per minute, and closes a turn's open activities when the turn ends. The adapter caps a frame at 1 MiB and merges rapid updates.

**Output (MD-16).** The stdout `output` frame is the only output path. A streaming part grows by `append`, ends by `end`, and is discarded by `reset`. `lenny/output` is removed.

**Reasoning (MD-17).** A `reasoning_trace` part carries the provider's signature or encrypted value and enters the transcript. A `thinking` activity shows reasoning without recording it.

**Files (MD-18).** A `file` part names a workspace path. The adapter freezes the file with a reflink clone where the filesystem allows one, splits it into the content-addressed chunks of the incremental checkpoint design, skips chunks the session's checkpoints already hold, and uploads the rest in packs of at most 32 MiB against grants the gateway signs, sharing the session's checkpoint grant window. The gateway replaces the path with a `lenny-blob://` reference and renders downloads from the packs. The limit is 5 GiB, a runtime can lower it, and the file has the session's retention. An export has its own deadline and outlives its turn, at session end it finishes in the time the seal checkpoint leaves in the seal window, and a file part that fails reaches the runtime as `output_failed`, which the gateway keeps until the runtime acknowledges it, so the runtime can emit the file again.

**Harness approvals (MD-19).** `lenny/request_approval` sends a harness's permission request through the `tool_use` approval path, and a declared policy answers for unattended sessions.

**Turn and usage events (MD-20).** `turn_start` and `usage` events are added, and `turn_end` carries a status and usage. Usage comes from the gateway's metering and from the runtime's report, each labelled with its source.

**Surfaces (MD-21).** Each report has a projection on REST, MCP, and A2A, provider surfaces carry output and reasoning only, and every report has a lossless AG-UI projection, through a `CUSTOM` event where AG-UI has none.

## Current state

### Specification

**Envelope [source].** §15.4.1 "`MessageEnvelope` — Unified Message Format" defines `delivery` as an optional closed enum "controlling interrupt behaviour": `"immediate"` ("Interrupt the running agent and deliver now"), `"queued"` ("Buffer for next natural pause"), and absent, which equals `"queued"`. Unknown values are refused with `400 INVALID_DELIVERY_VALUE`. `from.kind` is a closed enum of `client`, `agent`, `system`, and `external`, and the adapter overwrites any runtime-supplied `from`. Sender-supplied ids must be unique within the tenant, and the gateway keeps a deduplication window of seen ids (`messaging.deduplicationWindowSeconds`, 3600 seconds by default). The section's closing paragraph calls the envelope future-proof for "all future conversational patterns without schema changes".

**Receipts [source].** §15.4.1 "`delivery_receipt` acknowledgement schema" gives `status` the values `delivered` ("runtime consumed"), `queued`, `dropped`, `expired`, `rate_limited`, and `error`. `message_expired` reaches the sender session's event stream with the reasons `dlq_ttl_expired`, `durable_inbox_ttl_expired`, and `target_terminated`.

**Wire contract [source].** The `CH-MSGSOCK` card of §28.5.3 lists the runtime-to-adapter frames `session_started`, `response`, `tool_call`, `heartbeat_ack`, `status`, and `set_tracing_context`. Under **Inbound: `tool_result`**, "Delivery semantics" states: "Other inbound messages (`heartbeat`, additional `message` content) may arrive before the `tool_result` — the agent must handle interleaved delivery." **Outbound: `response`** carries `output` and an optional `error`, and nothing in the card pairs one `response` with one `message`. **Outbound: `heartbeat_ack`** requires `busy: true` while the runtime handles a message, runs a tool call, does background work outside a turn, or waits on children.

**Capabilities [source].** §5.1 "Runtime" shows `injection: {supported: true, modes: [immediate, queued]}` in its YAML and defines only `supported`: "`capabilities.injection` declares whether the runtime supports mid-session message delivery." `multi_turn` requires `injection.supported: true`. No section defines `modes`. The CRD comment on `InjectionCapabilityCRD.Modes` (`pkg/apis/lenny/v1alpha1/runtime_types.go`) reads "`immediate` interrupts a suspended session to deliver, `queued` buffers the message for the next runtime turn", which matches neither §15.4.1 nor §7.2.

**Delivery paths [source].** §7.2 "Message delivery routing — seven paths" evaluates paths in order:

- Path 1 resolves an outstanding `lenny/request_input` by `inReplyTo`.
- Path 2 writes the message when the runtime is available, meaning its adapter reports `ready_for_input`. The receipt is `delivered` "only after confirmed stdin consumption" within a delivery timeout of 30 seconds, and otherwise the message falls through to the inbox. The "`ready_for_input` — normative definition for concurrent tool execution" requires that no tool call is in flight and that the runtime is reading stdin, and routes "a message arriving while any tool call is in flight" to path 5.
- Path 3 buffers while the session is `input_required`, even under `delivery: "immediate"`.
- Path 4 is the only mid-turn delivery: under `delivery: "immediate"` with a tool call in flight, the gateway calls the adapter's `Interrupt`, the adapter writes `interrupt_request` on `CH-RUNTIMEOPS`, and the message follows the acknowledgement at Full level or follows at once at Basic and Standard.
- Path 5 buffers in the session inbox while the runtime is busy and delivers in FIFO order at the next `ready_for_input`.
- Path 6 resumes a `suspended` session, with **Delivery of held messages.**, which delivers every held message of the inbox and the DLQ before each path-2 message, one at a time and oldest first, and removes an entry only after the runtime consumed it.
- Path 7 sends a message for a terminal or recovering session to the dead-letter handling.

The durable inbox's "Explicit ACK" row removes an entry after delivery and requires the adapter to keep a `delivered_message_ids` set of the last 1000 ids in checkpoint state, suppressing redelivered duplicates and counting them on `lenny_inbox_duplicate_suppressed_total`.

**Unstated signals [source].** §29.3 "Interactive message send" step 8 records that "the specification does not state which channel and which message carry the adapter's report that the runtime is `ready_for_input` and its acknowledgement that the runtime consumed the written message".

**SDKs [source].** §15.7 "Runtime Author SDKs" defines `Handler.OnMessage(ctx, Message) (Reply, error)` and busy holds for work after a handler returns, including "the rest of a turn whose Reply is streaming and not final".

**Reference runtimes [source].** §26.2 declares `multi_turn` with `modes: [immediate, queued]` for the coding-agent runtimes, §26.7 `chat` and §26.10 `openai-assistants` declare `[immediate]`, and §26.8, §26.9, and §26.11 declare `[immediate, queued]`. Every reference runtime is Full level (§26.1). §26.3 "Bootstrap behavior" pipes each message to `claude` and states nothing about a message that arrives while `claude` works.

**Client surfaces [source].** §15.1 routes `POST /v1/sessions/{id}/messages` through the §7.2 paths. §15 "Open Responses conversation sessions" serves a continuation warm only when its response is the session's newest completed response, and a concurrent continuation runs cold. §15 "Built-in adapter single-shot compute model" runs one turn per Chat Completions request.

## MD-1 Delivery intents

**Values [design].** `delivery` on the `MessageEnvelope` takes `steer`, `queue`, or `interrupt`, or is absent. `immediate` and `queued` leave the enum, because Lenny has no deployments to keep. An unknown value is refused with `400 INVALID_DELIVERY_VALUE`, whose message lists the defined values.

| Intent | Meaning | Claude Agent SDK `priority` | Codex | Cursor |
| :-- | :-- | :-- | :-- | :-- |
| `steer` | Deliver now and do not interrupt. The runtime reads the message at its next model step and places it after the results of the tool calls it is running. Without an open turn, the message starts one. | `next`, the default | `turn/steer` | `delivery: "steer"` |
| `queue` | Hold until the open turn ends, then deliver as the start of the next turn. | `later` | Tab-queued input | Tab-queued follow-up |
| `interrupt` | Stop the open turn at a safe point, then deliver as the start of the next turn. | `now` without background work | `turn/interrupt`, then `turn/start` | Second Enter |

Claude Code's `now` first moves background-capable work to the background and lets Claude read the message in the same turn. Lenny's `interrupt` does not, because the gateway cannot move a runtime's work. A runtime that can do so is a future intent ("MD-14").

**Default [design, S2].** A message without `delivery` takes the default intent of the session's revision: its `injection.defaultMode` when set, `steer` when the revision declares it, and `queue` otherwise. The gateway writes the resolved intent into the envelope it delivers and the inbox entry it records, so a runtime and a reader of the transcript see the intent that applied.

**Override [design, S2].** A sender sets `delivery` on one message to override the default. REST takes it per message in the batch, MCP `send_message` and the agent-facing `lenny/send_message` take it in the message, and the `lenny session send` command gains `--delivery`. Provider surfaces take no override ("MD-8").

**Unsupported intents [design].** A message whose explicit intent the revision does not declare is refused before it is held: `422 DELIVERY_MODE_UNSUPPORTED` on REST and MCP, with the declared intents in `details`, and a receipt with `status: "error"` and `reason: "delivery_mode_unsupported"` on `lenny/send_message`. A refusal is explicit, because degrading `steer` to `queue` would delay a correction a person expects the agent to read now, and degrading `interrupt` to `steer` would let work the sender meant to stop continue.

**Ordering [design].** Messages of one intent reach the runtime in the order the gateway accepted them. A `steer` message overtakes `queue` messages that are still `pending`, as the harnesses' steered messages overtake their queued ones.

## MD-2 Runtime declaration

```yaml
capabilities:
  interaction: multi_turn
  injection:
    supported: true
    modes: [steer, queue, interrupt]
    defaultMode: steer
```

**[design, S10]**

- `modes` lists the intents the runtime accepts. When `supported` is true, `modes` must contain `queue`, because every injecting runtime takes a message at the start of a turn. Registration refuses an unknown value, a list without `queue`, and a non-empty list with `supported: false`.
- `steer` declares the obligations of MDR-5: the runtime reads `message` frames at any time, during a turn, while adapter-local, platform, connector, and approval-held tool calls run, while it is blocked in `lenny/request_input`, and while client calls are pending, and it places each message in its model history only at a point the model API accepts. It reports consumption with `consumed` frames and `response.consumed` ("MD-4"). `steer` is available at every integration level, because it uses `CH-MSGSOCK` alone.
- `interrupt` declares that the runtime handles `interrupt_request` on `CH-RUNTIMEOPS`, ends its open turn with a `response` once it acknowledges, and keeps the interrupted work's tool calls paired with results, for example by recording an error result for a call it abandons. Registration refuses `interrupt` on a runtime whose `integrationLevel` is below `full`, and the existing check of the observed level at the first session applies.
- `defaultMode` is optional and must be one of `modes`. A runtime that declares `steer` but prefers `queue` sets it, as Gemini CLI queues by default although it can steer.
- The fields are versioned and gateway-read under RV-1, so the session's revision decides. The per-tenant capability override may keep a subset of `modes` that still contains `queue`, as RV-1 states for `injection.modes`, and may set `defaultMode` to one of the remaining intents. When an override removes the revision's `defaultMode`, the default falls back to the rule of "MD-1".
- The CRD comment on `InjectionCapabilityCRD.Modes` states the meaning above.

## MD-3 Inbox states and custody

**States [design, G1].**

| State | Meaning | Receipt status |
| :-- | :-- | :-- |
| `pending` | Accepted and held by the gateway: in the session inbox or the DLQ, waiting for the turn state its intent requires, for a resume, or for a session to start. | `queued` |
| `delivered` | Written to the session's `CH-ATTACH` stream for the runtime, and not yet reported consumed. | `delivered` |
| `consumed` | Reported consumed by the runtime in a `consumed` frame or a `response`. Custody ends, and the entry leaves the inbox (O4). | Reported by event |
| `consumed_unrecorded` | Reported consumed, after which the session resumed from a checkpoint taken before the consumption, so the restored runtime does not hold the message. It is not redelivered (O4). | Reported by event |
| `expired` | Its TTL elapsed while the session was in a recovering state, or the session ended before consumption. | `expired`, or the `message_expired` event |
| `dropped` | Evicted by inbox or DLQ overflow. | `dropped` |
| `retracted` | Retracted by its sender while `pending` ("MD-11"). It is never delivered. | Reported by event |
| `superseded` | Reserved for a later intent that replaces a `pending` message ("MD-14"). No v1 path produces it. | Reported by event |

Transitions: `pending` to `delivered`, `retracted`, `expired`, or `dropped`; `delivered` to `consumed` or `expired`, and back to `pending` when a redelivery is due; `consumed` to `consumed_unrecorded` on a resume from a checkpoint taken before the consumption. `consumed_unrecorded` is final, and `consumed` is final unless such a resume occurs. A `delivered` message is never `retracted` or `dropped`, because the runtime already holds it, and a redelivery returns it to `pending` only inside the gateway's redelivery step, where no retraction can intervene: the step holds the session's delivery lock.

**Records [design, MDR-1].** Each inbox entry carries the message id, the sender's `from.kind` and `from.id`, the resolved intent, the state, the acceptance time, and the time of each transition. The transcript row of the message, which SD-1 "Reading client messages" gives a sender and a delivery state, carries the same state and intent, so `GET /v1/sessions/{id}/messages` reports them. The transcript row keeps the state after the inbox entry is released, and for a consumed message it also records the consumption's position in the session's sequence of consumption reports, which the gateway assigns in the order the session's stream relays them.

**Custody [design, S4, O4].** Delivery no longer removes an inbox entry. The entry moves to `delivered` and stays until the runtime reports consumption. When the gateway records the consumption, custody ends and the entry leaves the inbox, whether or not a checkpoint has recorded the consumption. In the durable inbox, `pending` entries stay in the Redis list, and an entry moves at delivery into a per-session Redis hash keyed by message id, which the coordinating replica reads on lease acquisition, and leaves the hash at consumption. The in-memory inbox keeps the same states in memory, and its documented loss window on a coordinator crash is unchanged.

**Redelivery [design].** The gateway redelivers every `delivered` entry, and never a consumed message (O4), oldest first and ahead of `pending` entries:

- after a resume onto a new pod (§7.3), once the session is `running` again;
- after a coordinator handoff with the durable inbox, once the new coordinator holds the lease. The runtime process is the same one, so the adapter suppresses ids it has already written to that process.

**Consumption after a checkpoint [design, O4].** A runtime restored from a checkpoint lacks every message it consumed after that checkpoint, and the gateway does not resend those messages, because a consumed message can have caused side effects that the checkpoint does not undo, for example a push. When a session resumes from a checkpoint, the coordinating replica reads the checkpoint's consumed set through the IC-4 catalog and takes the newest id in it that the gateway recorded as consumed. Every message whose consumption the gateway recorded after that id moves to `consumed_unrecorded`, oldest first. When no id in the set qualifies, every message the session consumed moves. Each move emits `message_state` with `state: "consumed_unrecorded"` and `reason: "checkpoint_restore"` on the session's event stream, and, for a message from another session, on the sending session's event stream as well, as `message_expired` reaches a sender today. A client or a parent that reads the event decides whether to send the content again, as a new message with a new id.

**Deduplication [design].** Because only `delivered` entries are redelivered, deduplication covers two cases. After a coordinator handoff, the runtime process is the same one and may already hold a redelivered entry. After a resume, the restored runtime may hold an entry whose consumption report the pod loss cut off, when the checkpoint was taken after the runtime consumed it. The adapter keeps, per session, the ids it has written to the current runtime process for the first case, and for the second the ids the runtime reported consumed, bounded to the last 1000, kept in report order, and carried in the checkpoint. The consumed set replaces the `delivered_message_ids` set of the durable inbox's "Explicit ACK" row, and it no longer filters consumed messages, which are never redelivered. On a redelivery the adapter drops an id in either set and counts it on `lenny_inbox_duplicate_suppressed_total`, and for an id from the consumed set it relays a `consumed` frame, so the entry leaves custody. The runtime SDKs keep the ids each session consumed and drop a repeated id ("MD-12"), which covers a runtime whose own persisted history records a consumption that neither the gateway nor the checkpoint's set records. The gateway's existing deduplication window still refuses a reused sender-supplied id.

**Expiry [design].** A `pending` entry keeps today's TTL rules. A `delivered` entry has no TTL while the session lives, because the runtime holds it. When the session ends, its `pending` and `delivered` entries become `expired` with `reason: "target_terminated"`, and the sender is notified as §15.4.1 states today.

## MD-4 Turn accounting

**`response.consumed` [design, S5].** The `response` frame gains `consumed`, an array of message ids that the runtime consumed in the turn the frame closes and has not reported in a `consumed` frame:

```json
{
  "type": "response",
  "sessionId": "sess_01J9...",
  "output": [{ "type": "text", "inline": "Switched to the staging database and reran the migration." }],
  "consumed": ["msg_01J9A", "msg_01J9B"]
}
```

**`consumed` frame [design, O2].** A runtime that declares `steer` writes `{"type": "consumed", "sessionId": "sess_01J9...", "ids": ["msg_01J9B"]}` when it consumes messages during a turn. The adapter relays it on `CH-ATTACH` as it relays `response`, and `consumed` joins the session-scoped frame types the adapter's demultiplexer routes by `sessionId` (`sessionScopedFrameTypes` in `pkg/adapter/attach.go`). A runtime that does not declare `steer` need not write it. The frame is a `CH-MSGSOCK` message, so no channel is added and the §28.3 registers are unchanged.

**Attribution without `consumed` [design, MDR-8].** A `response` without `consumed` is attributed to the oldest `delivered` message of the session, which then becomes `consumed`. That is today's pairing for a runtime that handles one message per turn, so a Basic runtime writes nothing new. A runtime that declares `steer` must send `consumed`, and a `response` from it without the member consumed nothing.

**Unsolicited responses [design, S5].** A `response` that finds no `delivered` message to attribute, and carries no `consumed` ids, closes a turn the runtime started on its own. The gateway records its output in the transcript, emits its `output` events and a `turn_end` event with `unsolicited: true`, and counts it on `lenny_unsolicited_response_total{runtime, runtime_revision}`. An id in `consumed` that names no `delivered` message of the session is logged as a protocol error and ignored.

**Open turn [design, O1].** The gateway's session state records whether a turn is open:

- A turn opens when the gateway writes a message while no turn is open, and when the runtime emits output, a `tool_call`, or a `consumed` frame while no turn is open. A `retract` frame ("MD-11") opens no turn, because it produces no work for the session, and an `activity` frame opens none ("MD-15"). An `output` frame is output and opens a turn ("MD-16").
- A turn closes on the runtime's `response`, and on the end of the runtime process.

The open turn replaces `ready_for_input` as the condition a `queue` message waits for. A runtime that writes no `response` keeps its turn open, as it keeps a turn open today, and the session's idle and heartbeat rules apply to it unchanged. The turn ordinal increments at each opening, and `turn_end` events carry it.

**Errors [design].** A `response` with `error` closes the turn as a failed turn, and the messages it lists in `consumed` are `consumed`. A message the failed turn did not consume stays `delivered`, and the runtime may consume it later. The gateway reads `error`, which the executor ignores today (client-tools design, "Defects found while verifying").

## MD-5 Delivery paths

§7.2 "Message delivery routing" is rewritten as named paths, evaluated in order, where the first match wins **[design]**. Names in place of numbers let a later path join the list without renumbering its neighbours, as the specification's naming law asks of channel identifiers.

| Path | Condition | Action | Receipt |
| :-- | :-- | :-- | :-- |
| Reply path | `inReplyTo` matches an outstanding `lenny/request_input`. | Resolve the call. No write. | `delivered` |
| Dead-letter path | The session is terminal, recovering, or pre-running. | As old path 7 and the dead-letter table state. | As today |
| Resume path | The session is `suspended`. | Hold the message and resume the session as old path 6 states, then apply the rows below to the resumed runtime. | `delivered` on synchronous delivery, otherwise `queued` |
| Direct path | No turn is open, or the message is a results message. | Write now. | `delivered` |
| Steer path | A turn is open and the intent is `steer`. | Write now. | `delivered` |
| Interrupt path | A turn is open, the intent is `interrupt`, and the session is not `input_required`. | Hold the message, call the adapter's `Interrupt`, and write the message when the interrupted turn's `response` arrives. When `interrupt_acknowledged` does not arrive within the `interrupt_request` deadline, the message continues as `queue`. | `queued` |
| Queue path | A turn is open and the intent is `queue`, or the intent is `interrupt` and the session is `input_required`. | Hold until the turn's `response`. | `queued` |

The session stays `running` on the interrupt path. The `POST /v1/sessions/{id}/interrupt` route keeps its meaning and moves the session to `suspended`.

**Delivery of held messages [design].** At each turn end, after each commit to `running`, and after each adoption of a `running` session, the coordinating replica writes the held entries whose intent now permits a write, oldest first by acceptance time across the inbox and the DLQ. For a runtime that does not declare `steer`, it writes one entry and waits for the next turn end before the next, so each held message is its own turn as today. For a `steer` runtime it writes every eligible entry, and the runtime may consume them in one turn. Held deliveries no longer precede every direct-path write: a held entry that is eligible is written before the new message at the same delivery point, which keeps acceptance order.

**Client tools [design, S6].** For a session with pending client calls, the client-message rules of [CT-5](client-tools-design.md#ct-5-pending-calls-and-the-hold-rule) run before the paths. For a runtime that does not declare `steer`, inbox deliveries are held as CT-5 and the client-tools design's O3 state. For a `steer` runtime they take the paths above ("MD-10").

**Successor pointers [design].** Each numbered path keeps a pointer in §7.2 to its named successor: path 1 to the reply path, path 2 to the direct path, path 3 and path 5 to the queue path, path 4 to the interrupt path, path 6 to the resume path, and path 7 to the dead-letter path. The proposal retargets the specification's citations of path numbers, in §7.3, §10.1.2, §11.1, §15, §15.4.1, and §29.3 among others, to the names.

**Removed rules [design, O1].** The `ready_for_input` definition, the delivery timeout of 30 seconds and its fall-through to the inbox, and the `input_required` overlap rule between old paths 3 and 5 leave §7.2. §29.3 step 8 is rewritten: the adapter relays `consumed` and `response`, and the gateway derives the open turn from them.

## MD-6 Executor, lock, and waiting

**Writer [design, S9].** `PodExecutor` gains `Deliver(ctx, sessionID, []Envelope) ([]WriteResult, error)`, which writes each envelope on the session's `CH-ATTACH` stream and returns once the writes succeed or the stream fails. It takes no turn token, and a write is allowed while a turn is open. `attachConn.token`, `acquireTurn`, and the turn registration leave `podstream.go`.

**Reader [design].** The stream's reader routes every frame: `consumed` and `response` update inbox states and the open-turn state through one session-scoped recorder, `response` and `output` frames go to the transcript and the event stream under "MD-16", `activity` frames go to "MD-15", and an unsolicited response is recorded under "MD-4". Nothing is discarded for want of a waiter. An approval-required `tool_call` and a `lenny/request_approval` call wait off the reader's goroutine, so the reader keeps reading during an approval (MDR-22, MDF-8).

**Turn waiter [design].** `AwaitConsumingTurn(ctx, sessionID, messageID) (TurnResult, error)` returns the `response` of the turn that consumed the message, or the failed turn's error. The provider-surface adapters and replay use it. A waiter that stops waiting leaves nothing registered on the stream, because the reader's routing does not depend on waiters.

**Delivery lock [design, MDR-4].** `deliveryLocks` covers classification, the inbox write, and the `Deliver` call, and is released before any wait for a turn. The lock still serializes held-message delivery against the message paths on one replica, which is the purpose `sessionserver.go` states for it.

**Classification [design].** `messagerouting.Classify` takes the session row, the open-turn state, the input-wait state, the resolved intent, the revision's declared intents, and whether the message is a results message, and returns a named path. Its comment that a synchronous executor is ready by construction leaves with the turn token.

## MD-7 REST and MCP

**Send [design, S3].** `POST /v1/sessions/{id}/messages` answers with `deliveryReceipts`, one per message in the batch, in the order sent, and no `output` member. `delivered` now means that the gateway wrote the message for the runtime. The receipt answers once the message is written or held, without waiting for consumption or output. The client-facing MCP `send_message` tool and the agent-facing `lenny/send_message` return the same receipt. The §15.4.1 description of `delivered` changes from "runtime consumed" to "written for the runtime; consumption is reported by the `message_state` event".

**Events [design].** The `SessionEvent` registry of §15 gains these kinds:

| Kind | Payload | Fires when |
| :-- | :-- | :-- |
| `message_state` | `{ "messageId", "state", "intent", "fromKind", "turn"?, "reason"? }` | A message of the session changes state, including to `retracted` and to `consumed_unrecorded`. A move to `consumed_unrecorded` also reaches the sending session's stream for a message from another session ("MD-3"). The payload carries no content. |
| `turn_end` | `{ "turn", "consumed": [ids], "unsolicited": bool, "error"? }` | A `response` closes a turn. |

"MD-15" adds `activity`, and "MD-20" adds `turn_start` and `usage` and extends `turn_end`. The registry is closed, so the additions take the `SessionEvent` schema revision the registry requires. The session's `output` events carry the turn's output as they do today. Adapters that do not list the kinds in `SupportedEventKinds` do not receive them, under the registry's dispatch-filter rule.

**Client retraction [design, O5].** Under O5, a client retracts its own `pending` message: `DELETE /v1/sessions/{id}/messages/{messageId}` runs the retraction of "MD-11" for a message the caller sent to the session and answers `200` with `{ "messageId", "result" }`, where `result` is `retracted`, `too_late`, or `unknown`. A message the caller did not send answers `unknown`, under MDR-11. The MCP tool is generated from the route under §15.2.1 rule 4.

**Clients [design].** The Go client SDK, the `lenny session send` command, and the web playground read output from the event stream. `lenny session send` without an attached stream prints the receipt and exits, as §24 states today.

## MD-8 Provider surfaces

A Chat Completions, Responses, or Messages API request is one turn, because its client follows the provider's API, where a request is a turn **[design]**:

- The adapter writes the request's message through the paths of "MD-5" with no intent the request can set. A cold turn reaches a new session through the direct path. A warm turn reaches a session whose newest response has completed (§15 "Open Responses conversation sessions" condition 3 and AM-5 condition 3), so the only turn that can be open is one that no request on this surface caused, such as a turn another session's message caused. With no open turn, the message takes the direct path. With such a turn open, it takes the steer path on a runtime that declares `steer` and the queue path, which waits for the turn's `response`, on any other runtime (O3).
- The adapter waits with `AwaitConsumingTurn` for the turn that consumed the request's message, and returns that turn's output from the point the runtime consumed the message. A turn the message opened returns all its output. For a message steered into a running turn, the response carries the output that follows the `consumed` frame listing the message, or, when only the turn's `response` lists it, that `response`'s own output. A `steer` runtime may consume inbox deliveries in the same turn, and their ids appear in the turn's `consumed` list. Only the client's message decides which turn answers the request.
- A second request during a running turn that a request on the same surface caused behaves as it does today: on Responses it runs cold, on the Messages API an identical retry joins the running turn through AM-5's in-flight join and any other request runs cold, and on Chat Completions every request is its own session.
- A Chat Completions session is released after its turn, so its `pending` entries expire with `target_terminated`.
- The Responses cold walk of a conversation's transcript includes consumed inbox deliveries as entries carrying their `from` object, with the output of the turns they caused, so a cold runtime reads what the warm runtime read. The Messages API and Chat Completions take their history from the client, and the gateway adds nothing to it.

**Delivery on arrival [design, O3].** A message from another session to a session created on a provider surface is delivered on arrival under the ordinary intent rules of "MD-1" and "MD-5", and the provider surfaces add no handling of their own. On a held session between client requests no turn is open, so the message takes the direct path and opens a turn. No delivery waits for the client's next request. Two rules keep such a turn away from the provider-surface client:

1. **Client tools only in turns a client request caused.** A turn caused by another session's message, a system message, or an external message carries no `conversation.clientTools` and no `conversation.toolChoice`, and a `response` of such a turn that carries `clientToolCalls` fails the check of [CT-4](client-tools-design.md#ct-4-response-validation) with `no_tools_declared`. A client request steered into such a turn carries its own `conversation.clientTools` in its envelope, so the runtime may call those tools from the point it consumes the request, and the turn's `response` returns the calls to that request's client.
2. **No such turn in a provider-surface response.** A turn that no client request caused never appears in a provider-surface response. Its output goes to the transcript and to the session's REST and MCP event streams. It writes no response record and no conversation digest and takes no response ordinal, so the warm conditions of the client's next request are unaffected. The client's next response is the output of the turn its own message caused, under the `consumed` attribution of "MD-4" and the cut point stated above.

Tool-use approvals in such a turn work through the approvals API as on any session. Elicitation and `lenny/request_input` stay refused on those surfaces, as AM-6 states for the Messages API, whatever caused the turn.

**Scenarios [design, O3].** A message reaches a session created on a provider surface other than through the client's own requests in these cases:

- Asynchronous delegation, the main case. A runtime served on the Messages API or Responses delegates a child, replies to its client, and the child later finishes or sends the parent a message through `lenny/send_message` after that reply. The parent runtime takes the message in a turn of its own. The client sees that turn on the session's REST and MCP event streams, and in a provider response only when the runtime refers to it in a later turn the client caused.
- The same session used from REST or MCP, through the session id the response headers carry. A REST or MCP client message causes a turn whose output reaches the REST and MCP streams and no provider-surface response.
- A sibling's message under the `siblings` messaging scope of §7.2.

## MD-9 Inter-session messages, system messages, and delegation

**Inter-session messages [design].** `lenny/send_message` carries `delivery` in its message and resolves the target's default intent when absent. The cross-tenant check, the messaging scope, the rate limits, and the `PreMessageDelivery` interceptor run before the intent check, as §7.2 orders them today. The call returns its receipt once the message is written or held, so a sender never waits for the target's turn. The sender learns of expiry from `message_expired` as today.

**Delegation [design].** A parent can redirect a running child with `steer`, for example "stop exploring the cache layer and fix the failing test", without cancelling it and losing its work. A parent that wants the child to stop first sends `interrupt`, when the child's runtime declares it. A child's `task` from `lenny/delegate_task` is the child's first message and starts its first turn, so no intent applies to it. A parent answers a child's `lenny/request_input` through the reply path, unchanged. A parent blocked in `lenny/await_children` that declares `steer` receives inter-session messages during the wait. One that does not receives them at its turn end, which matches today's buffering while `await_children` is in flight. A child's message to a parent created on a provider surface is delivered on arrival, and the turn it causes follows the two rules of "MD-8" (O3). The subtree deadlock detector of §8 and the delegation lease's `messagingRateLimit` are unchanged.

**System messages [design].** A message the gateway itself originates carries `from.kind: system` and takes the target's default intent unless the mechanism that sends it names one. v1 defines no new system message. "MD-14" lists the candidates.

**External senders [design].** A message routed through a connector carries `from.kind: external` and follows the same rules as an inter-session message.

**Sender kind [design].** The adapter writes `from` as today, and the inbox entry and the transcript row record it (MDR-1), so a runtime that weighs a client's correction above an agent's suggestion can tell them apart.

## MD-10 Client tools

The client-tools design's revision 2 already scopes its hold rule to runtimes that do not declare `steer` ("Steer-declaring runtimes" under CT-5) and adds the history rule ("Order of history entries" under CT-7). This part states the delivery machinery's side of both.

**Inbox deliveries while calls are pending [design, S6].** For a runtime that declares `steer`, an inbox delivery to a session with pending client calls takes the paths of "MD-5". The session has no open turn after the turn that returned the calls, so the message is written at once and opens a turn. That turn carries no `conversation.clientTools`, because no client request caused it (O3, rule 1 of "MD-8"). The runtime holds the message, places it after the results when they arrive, and reports its consumption then, or acts on it without a model call. CTR-4 of the client-tools design narrows to runtimes that do not declare `steer`, for which T5's hold and that design's O3 stand. CTR-5 holds unchanged, because the calls themselves stay session data and the held message is in the gateway's custody until consumed ("MD-3").

**Client messages [design, S7].** A client message without the pending results is refused on every surface. On REST and MCP a message that sets `abandonPendingToolCalls: true` is a results message whose results are the "cancelled by client" error results, with the client's text as `input`. A results message takes the direct path whatever the open-turn state, because a `steer` runtime may be holding an inbox delivery behind the pending calls.

**Retraction [design, S8].** A runtime that no longer wants some or all of its pending calls retracts them by their runtime ids with the `retract` frame of "MD-11". On REST and MCP the calls are cancelled and the client receives a retraction event. On provider surfaces the answer is `too_late`, the client still sends results, and the runtime ignores them.

**Cold-history ordering [design, S6, MDR-7].** The cold-history builder, which the client-tools design's CT-7 and AM-4 use, places each entry by the turn and the position at which the runtime consumed it, from `consumed` frames and `response.consumed`. An entry consumed while client calls were pending moves to after the entry that carries their results, as CT-7 "Order of history entries" requires, and entries that move keep their relative order. An entry reported only on a `response` is placed after the output that turn streamed before the `response`, and before the `response`'s own output. The builder never places an entry between an assistant entry that carries calls and the entry that carries their results.

## MD-11 Retraction

The owner settled S8 on 2026-11-09: a runtime may retract any message it generated. Retraction is one operation in the delivery machinery, keyed by id, and it changes only what no recipient has received **[design, S8, MDR-10]**.

### Request and result

A runtime writes a `retract` frame on `CH-MSGSOCK`, inside or outside a turn:

```json
{ "type": "retract", "sessionId": "sess_01J9...", "retractId": "rt_1", "ids": ["tc_7", "msg_01J9X"] }
```

The adapter relays it on `CH-ATTACH` to the stream of the session it names, as a session-scoped frame ("Blast radius"). The gateway answers with a `retract_result` frame, which the adapter writes to the runtime as it writes every envelope the gateway sends:

```json
{
  "type": "retract_result",
  "sessionId": "sess_01J9...",
  "retractId": "rt_1",
  "results": [
    { "id": "tc_7", "result": "too_late" },
    { "id": "msg_01J9X", "result": "retracted" }
  ]
}
```

- `results` holds one entry per requested id, in request order, with `result` set to `retracted`, `too_late`, or `unknown`.
- `retracted`: the item will never reach its recipient. A repeated retraction of an id already retracted answers `retracted`, so a runtime may retry after a lost answer.
- `too_late`: the recipient already received the item, the item reached a final state another way, or the surface cannot withdraw it. Nothing changes.
- `unknown`: the id names nothing this session may retract (MDR-11).
- The frames add no channel, so the §28.3 registers and the naming law are unaffected. A runtime that never writes `retract` never receives `retract_result`.

### What a runtime may retract

| Item | Id the runtime names | `retracted` when | `too_late` when | Effect of `retracted` |
| :-- | :-- | :-- | :-- | :-- |
| A pending client tool call on a REST or MCP session | The call's runtime `id` from `clientToolCalls` | The call is still in the session's pending set. | A results message cleared the set first. | The gateway removes the call from the pending set with the conditional write [CT-5](client-tools-design.md#ct-5-pending-calls-and-the-hold-rule) uses for results, and emits a `tool_use` event with `target: "client"` and phase `retracted`. The next results message answers exactly the calls that remain, and one that names a retracted call is refused with `409 CLIENT_TOOL_CALLS_RETRACTED`. When no call remains, the session has no pending calls. |
| A client tool call on a provider surface (Messages, Chat Completions, or Responses) | The call's runtime `id` | Never. | Always. | None. A returned call cannot be withdrawn on these surfaces: the pending set stays, the client sends results as the provider's API requires, and the runtime ignores them. |
| A message the runtime sent to another session through `lenny/send_message`, to its parent, a child, or a sibling | The `messageId` of the receipt, or the id the runtime supplied | The message is `pending` in the recipient's inbox or DLQ. | The message is in any other state: `delivered`, `consumed`, `expired`, or `dropped`. | The entry moves to `retracted` and leaves the store, it is never delivered, and the recipient's event stream receives `message_state` with `retracted` and no content. |
| Output and session events | None, because output parts and events carry no id | Never in v1. | Not applicable. | Ignored for now ("Blast radius"). Output already streamed to a client cannot be recalled. A part still streaming can be discarded with `reset` ("MD-16"), which is not a retraction. |
| Anything else: a child's `task` from `lenny/delegate_task`, a `tool_call`, another sender's message, or an id the gateway does not know | Any | Never. | Never. | `unknown`. A runtime stops a child with `lenny/cancel_child`. |

A retracted `interrupt` message is never delivered, and an interrupt the gateway already requested for it proceeds, because the runtime may already be stopping.

### Ordering

A message retraction runs on the recipient's coordinating replica under the recipient's delivery lock, which the message paths and the delivery of held messages also take ("MD-6"), so a retraction and a write of the same entry never interleave: the one that takes the lock first wins. The gateway routes a retraction to the recipient as it routes the `lenny/send_message` call that sent the message, including the forwarding to a coordinating replica on another gateway replica. A client-call retraction and a results message race on the session row's conditional write, and exactly one of them takes effect.

### Audit and interceptors

Each retraction that changes state writes the audit event `message.retracted`, or `client_tool_call.retracted` for a call, naming the retracting session and principal, the item's id and kind, the recipient session, the surface, and the result (MDR-12). The counter `lenny_retraction_total{kind, result}` counts every result, including `too_late` and `unknown`, so an operator can see a runtime that retracts often or names ids it does not own. Audit records carry no message content.

No interceptor phase runs on a retraction. A retraction removes content from a recipient's path and adds none, and the retracted content already passed `PreMessageDelivery` for a message, or `PostAgentOutput` for a call's arguments, when it was sent. A deployer who needs to observe retractions reads the audit event.

### Blast radius

The owner asked for retraction of messages other than client calls if its blast radius is small. It is small for messages, because "MD-3" already gives every inbox entry a state and a lock-held transition, and a runtime's message to another session lives in one place:

| Component | Change | Size |
| :-- | :-- | :-- |
| Inbox store (`sessioninbox`, in memory, on the Redis list, and in the DLQ sorted set) | The `retracted` state and one transition from `pending`. Removing a `pending` entry uses the removal the store already performs at delivery and expiry. | Small |
| Outbound queue | None. Lenny has no outbound queue: a runtime's `lenny/send_message` lands in the recipient's inbox or DLQ, so a retraction has one place to look. | None |
| Routing to the recipient | The retraction reuses the send path's classification read and its forwarding to the coordinating replica. | Small |
| Session row (client tools) | Removal of ids from the pending set by the conditional write CT-5 defines. | Small |
| Executor | The reader routes `retract` to a retraction handler, and the writer sends `retract_result`. | Small |
| Adapter | `retract` joins `sessionScopedFrameTypes` in `pkg/adapter/attach.go`, so the demultiplexer relays it to its own session's stream alone. Without the entry, a frame type outside the set passes through to every Attach stream on the pod as a protocol-level frame. `attachRecvLoop` writes `retract_result` as it writes every envelope the gateway sends. | Small |
| Runtime SDKs | A `Retract` call ("MD-12"). | Small |
| Audit, events, and metrics | The audit events `message.retracted` and `client_tool_call.retracted`, the `retracted` value on `message_state` and `tool_use`, and `lenny_retraction_total`. | Small |

Output and session events are not small, so they are ignored for now. Output parts and events carry no id a runtime could name. An `output` event fans out at once to every outbound channel of the session, enters the event store's replay sequence, and enters the transcript, and the provider adapters fold it into response records. Recalling one part would need ids on parts, a tombstone in the replay sequence, and a rule for channels that already received it. "MD-14" lists it as a future case.

## MD-12 Runtime SDKs

**Drain call [design].** The Go, Python, and TypeScript SDKs add a call on the handler's context, `DrainMessages(ctx) []Message` in Go, `drain_messages()` in Python, and `drainMessages()` in TypeScript. It returns, in arrival order, the messages that reached the runtime for the session while the handler runs, and removes them from the session's queue. A model loop calls it between model steps, after the step's tool results are in hand, and appends what it returns after those results. The SDK treats every returned message as consumed, writes a `consumed` frame for their ids, and keeps them out of a later `OnMessage`.

**Consumption reporting [design].** The SDK writes `consumed` on the `response` it writes for an `OnMessage` call, listing that call's message and any drained message not yet reported. A handler that declares `steer` and never calls the drain call degrades to queue-until-turn-end inside the SDK: the queued messages wait for the next `OnMessage`, and the runtime is still correct.

**Deduplication [design].** The SDK keeps the ids each session consumed, bounded to the last 1000, and drops a message whose id is among them. A runtime that persists its own history keeps the set with it, so a restored runtime drops the redeliveries "MD-3" sends.

**Unsolicited responses [design].** The SDK adds `Respond(ctx, sessionID, Reply)`, which writes a `response` outside an `OnMessage` call, for a runtime that finishes background work and wants to report it.

**Retraction [design, S8].** The SDK adds `Retract(ctx, sessionID, ids) ([]RetractResult, error)` in Go, and `retract()` in Python and TypeScript. It writes a `retract` frame with a fresh `retractId`, waits for the matching `retract_result` under the caller's context, and returns one result per id. A context that ends first returns an error, and a retry is safe because retraction is idempotent.

**Busy reporting [design].** A handler that holds a drained message across a wait for client results takes a busy hold only while it works. Holding a message is not work, so the session idles and suspends as §15.7 states.

**Activity, output, files, and approvals [design].** The SDKs add `ReportActivity(ctx, Activity)` in Go, `report_activity()` in Python, and `reportActivity()` in TypeScript, which write `activity` frames, with helpers for each operation and an `End` that sets the final status. `Output` writes the `output` frame, with a streaming writer that emits `append`, `end`, and `reset`. A file helper emits a `file` part by workspace path with a fresh part `id`. The SDKs report the `output_failed` frame of "MD-18" to the runtime through `OnOutputFailed(ctx, OutputFailure)` in Go, `on_output_failed()` in Python, and `onOutputFailed()` in TypeScript, with the part `id` and the reason, so a runtime can emit the file again. When the handler returns, the SDK writes `output_failed_ack` with the part `id`, and it drops a later notice for a part `id` it has already acknowledged, because the gateway sends an unacknowledged notice again after a resume. `RequestApproval` calls `lenny/request_approval` and returns the decision. The client SDKs keep events as `{type, data}` strings, so the new kinds reach applications with no client SDK release, and typed helpers for the conventional kinds are optional.

## MD-14 Future use cases and the extension rule

**Cases the machinery covers [design].** None ships in v1.

| Case | How it fits |
| :-- | :-- |
| Scheduled delivery | A `deliverAt` member keeps a message `pending` until a time. The gateway alone acts on it, so no runtime declares it. |
| Priority ordering | A `priority` member orders `pending` entries of one intent. Gateway-only. |
| Context-only messages | An intent `append` delivers a message the runtime adds to its history without starting a turn, as the Claude Agent SDK's `shouldQuery: false` does. Declared, because the runtime acts on it. |
| Background, then steer | An intent that asks the runtime to move its running work to the background and read the message in the same turn, as Claude Code's `now` does with a human origin. Declared. |
| Child completion and system notices | `system` messages from the gateway, such as a child's completion, a budget warning, or a deadline, delivered with the target's default intent, as Claude Code folds task notifications into a turn. |
| Consumption notices to senders | A `message_state` event on the sending session's stream for every state change, beyond the move to `consumed_unrecorded` that v1 already reports there, and a notice when a target goes idle, as Claude Code's `notify_when_idle` does. |
| Replacement | An intent that supersedes the sender's earlier `pending` message with a new one. It uses the `superseded` state. |
| Retraction of output | Ids on output parts and events, a tombstone in the event replay sequence, and a rule for channels that already received a part, so a runtime can recall output the gateway has not yet sent to a client. S8 leaves it for later ("MD-11"). |
| External participants | Connector messages with `from.kind: external`, steered into a running session. |

**Extension rule [design, G1].** An addition to the machinery satisfies all of these:

1. A behaviour that applies whatever the intent, such as a delivery time or an order, is its own envelope member. A behaviour that changes when the runtime receives a message relative to its turn is an intent.
2. An intent states the gateway's action for each turn state of "MD-5" and the receipt it gives.
3. An intent the runtime must act on is declared in `injection.modes`, and the gateway sends it only to a declaring revision. A gateway-only intent is never declared and is listed in the §15.4.1 enum alone.
4. An intent states the runtime's obligation, including where the message goes in model history and how its consumption is reported.
5. An intent uses the states of "MD-3", and adds a state only when no existing state expresses its outcome. A new state states its transitions and its receipt.
6. The enum stays closed: an unknown intent is refused with `400 INVALID_DELIVERY_VALUE`, and registration refuses an unknown declared intent.
7. A new intent comes with a conformance case in §15.4.6 and a mapping row on each surface that exposes it.

## MD-15 Activity

The owner settled A2, A3, A7, and A10 on 2026-11-10 and kept the activity `kind` open-ended under conventions. Activity is the runtime's own report of what it is doing. The gateway shows it to clients, keeps the current state of every open activity, and keeps it out of model history **[design]**.

### Frame

```json
{
  "type": "activity",
  "sessionId": "sess_01J9...",
  "op": "start",
  "id": "act_7",
  "kind": "tool",
  "lifetime": "turn",
  "record": true,
  "parentId": "act_2",
  "agent": "explorer",
  "summary": "Running npm test",
  "detail": { "toolKind": "execute", "command": "npm test", "output": "" }
}
```

| Field | Set on | Meaning |
| :-- | :-- | :-- |
| `id` | Every frame | The runtime's identifier for the activity, unique within the session. |
| `op` | Every frame | `start`, `update`, `patch`, `append`, or `end`. |
| `kind` | `start` | An open string. "Conventional kinds" lists the kinds clients can rely on, and a custom kind takes the `x-<vendor>/` prefix that custom `MessagePart` types use. The gateway checks no `detail` schema for any kind. |
| `lifetime` | `start` | `turn`, the default, or `session`. A `turn` activity ends with its turn. A `session` activity, such as a plan, spans turns. |
| `record` | `start` | `true` asks the gateway to write the activity's final state to the transcript when it ends ("Recording"). The default is `false`. |
| `parentId` | `start` | The id of an enclosing activity, for nesting, such as a tool run inside a step or a subagent. |
| `agent` | `start` | The name of the harness-internal subagent that produced the activity. |
| `status` | `start`, `update`, `end` | `active`, the default on `start`, then `completed`, `failed`, or `cancelled` on `end`. |
| `summary` | `start`, `update`, `end` | A one-line text for display. |
| `detail` | `start`, `update`, `end` | Any JSON value, a string included. |
| `patch` | `patch` | An RFC 6902 JSON Patch applied to `detail` when `detail` is an object or an array. |
| `path` and `text` | `append` | `text` is appended to the string at the RFC 6901 JSON Pointer `path` inside `detail`. An empty `path` names `detail` itself when `detail` is a string. |

`kind`, `lifetime`, `record`, `parentId`, and `agent` are fixed at `start`. A frame that changes one is dropped with the reason `immutable_field`.

### Operations

| `op` | Effect |
| :-- | :-- |
| `start` | Creates the activity. An `id` the session already used is dropped with the reason `duplicate_id`. |
| `update` | Replaces `summary`, `detail`, and `status` with the values the frame carries. A member the frame omits keeps its value. |
| `patch` | Applies `patch` to `detail`. The gateway applies the patch to its own copy before it forwards the frame, and a patch that fails to apply is dropped with the reason `patch_failed` and reaches no client (A3). |
| `append` | Appends `text` to the string at `path`. A `path` that names no string is dropped with the reason `invalid_target`. JSON Patch has no string append, so `append` covers growing text such as a command's output. |
| `end` | Sets the final `status`, and optionally a final `summary` and `detail`, and closes the activity. A frame for an ended `id` is dropped with the reason `ended_id`. |

A frame for an `id` the session never started is dropped with the reason `unknown_id`. Every drop is counted on `lenny_activity_dropped_total{runtime, runtime_revision, reason}`, and the gateway emits an `activity` event with `op: "lost"`, the `id`, and the reason, so a client knows its copy of that activity missed a change.

### Conventional kinds

The kinds below are conventions that runtime authors and clients share. A runtime may send any kind.

| Kind | Meaning | Conventional `detail` members |
| :-- | :-- | :-- |
| `tool` | A tool the harness runs itself, such as its shell or file editor. A tool call that Lenny routes is reported by the `tool_use` event and never as activity. | `toolKind` (the Agent Client Protocol values `read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, and `other`), `title`, `toolUseId` (the harness's call id), `input`, `output` (a string, grown by `append`), `changes` (`[{path, change: add \| modify \| delete, diff?}]`), and `locations` (`[{path, line?}]`). |
| `plan` | The agent's plan or todo list. One per session, with `lifetime: session`, replaced by `update` or changed by `patch`. A plan proposed for the user's approval is an elicitation ("MD-19"). | `entries` (`[{id?, content, status: pending \| in_progress \| completed, priority?}]`). |
| `step` | A named phase of the agent's work. | `name`. |
| `thinking` | Reasoning shown as status ("MD-17"). | `text` (grown by `append`), `durationMs`, and `estimatedTokens`. |
| `subagent` | A subagent the harness runs inside its own process, such as a Claude Code task. Activities the subagent produces name it in `agent` and its activity in `parentId`. | `name` and `description`. |
| `compaction` | The harness compacting its context. | `tokensBefore` and `tokensAfter`. |
| `context` | The fill of the model's context window. | `usedTokens` and `windowTokens`. |
| `diff` | The workspace changes of a turn. | `files` (`[{path, additions, deletions}]`). |
| `hook` | A harness hook run. | `event`, `name`, and `output`. |
| `retry` | A model or tool call the harness retries. | `attempt`, `reason`, and `delayMs`. |
| `notice` | A message for the user that is not conversation content. | `severity` (`info`, `warning`, or `error`), `title`, and `description`. |
| `waiting` | The harness waits on something outside Lenny. | `on`. |
| `mode` | The harness changed its mode, such as a plan mode. | `mode`. |
| `model` | The harness changed its model. | `model`. |

### Turn and close rules

- Activity never opens or closes a turn ("MD-4"). The gateway stamps each activity event with `turn`, the ordinal of the open turn, when a turn is open.
- When a turn closes, every open activity of that turn with `lifetime: turn` ends `cancelled` with `reason: "turn_ended"`. When the runtime process ends, every open activity ends `cancelled` with `reason: "runtime_exit"`. When the session ends, every open `session` activity ends `cancelled` with `reason: "session_ended"`. A client spinner therefore always stops.
- Activity counts as agent work for idle suspension, as §6.2 counts `agent_output` and `tool_use`.

### Current state and attach (A2)

The gateway keeps the current state of every open activity of a session in a Redis hash keyed by activity id, on the session's data shard, so any gateway replica that coordinates the session holds it. The hash is bounded by `activity.maxOpen` (default 256) and `activity.snapshotMaxBytes` (default 8 MiB) per session. A `start` past either bound is dropped with the reason `open_limit`.

On every attach and every resume, after the replayed events, the gateway sends one `activity` event with `op: "snapshot"` that lists every open activity, with a fresh `SeqNum` as the synthesized frames of §10.4 "Coordinator-handoff reattach" take. Activity events are volatile events under §10.4 "volatile vs. reconstructible events": a resume whose range lost only activity events receives the snapshot and no `gap_detected` for them. When the replay ring must evict, it evicts first an activity event whose `id` has a later event in the ring, so activity does not push other events out of the ring.

### Recording (A2)

Activity stays out of the transcript unless the runtime starts it with `record: true`. When a recorded activity ends, the gateway writes one transcript row with the role `activity` that carries the activity's `kind`, `summary`, `detail`, final `status`, `agent`, `parentId`, `turn`, and its start and end times, at the position of its `start`. Intermediate updates are not recorded.

`activity.recordPerMinute` (default 60, operator-configurable) caps the recorded rows per session per minute. A recorded activity that ends over the cap is still shown live, and the gateway writes one marker row for the minute that states how many activities it did not record, and counts them on `lenny_activity_unrecorded_total`.

Recorded rows never reach a model: the cold-history builders of CT-7 and AM-4, conversation input, and SD-1's `GET /v1/sessions/{id}/messages?from=client` skip them. `GET /v1/sessions/{id}/transcript` returns them. Transcript retention, [§12.8](../spec/12_storage-architecture.md#128-compliance-interfaces) erasure, and legal holds apply to them as to every transcript row.

### Adapter rules

- **Size (A10).** The adapter parses each `activity` frame and drops one larger than `activity.maxFrameBytes` (default 1 MiB, operator-configurable) with the reason `oversize`. The session continues. Activity has no blob references: content larger than the cap is a file part ("MD-18") that an activity names by path.
- **Coalescing.** The adapter holds the newest `update` per `id` for at most `activity.minIntervalMs` (default 250 ms) and concatenates consecutive `append` frames to the same `id` and `path`. It never holds `start`, `patch`, or `end`, and before it relays any other session-scoped frame of the session it relays every held frame in the order of their newest writes. Coalescing therefore skips intermediate states and never reorders an activity against output, `tool_call`, `consumed`, or `response`.
- **Routing.** `activity` and `output` join `sessionScopedFrameTypes` in `pkg/adapter/attach.go`, so the demultiplexer relays them to their own session's stream alone.

### Gateway rules

- **Interceptors.** A new interceptor phase, `PostAgentActivity`, receives each activity frame as JSON before the gateway applies and forwards it. `MODIFY` may change `summary`, `detail`, `patch`, and `text`, and may not change `id`, `kind`, `op`, `parentId`, or `status`. `REJECT` drops the frame, writes the audit record other phases write, and never fails the turn. A rejected `end` still closes the activity, with its `summary` and `detail` removed, so the close rule holds. The phase follows the failure policy each interceptor declares, as the other phases do. `PostAgentOutput` does not fit, because its payload is `MessagePart[]`.
- **Trust.** Activity is the runtime's claim about itself. No audit record, policy decision, budget, or approval reads it.
- **Opt-out.** A subscriber passes `activity: "none"` on `lenny/attach_session` and on `GET /v1/sessions/{id}/events` to receive no activity events. The default delivers them.

### Child sessions (A7)

A delegated child session's activity stays on the child's stream. The parent's `tool_use` event for `lenny/delegate_task` carries `childSessionId`, and a client that wants the child's detail attaches to the child. A subagent that a harness runs inside its own process is a `subagent` activity of the session, because Lenny learns of it only from the harness.

## MD-16 Output streaming

The owner settled A5 and A6 on 2026-11-10 **[design]**.

**One path (A6).** A runtime emits output on the stdout `output` frame, at every integration level. `lenny/output` leaves the platform tool set, and the runtime SDKs' `Output` call writes the frame. `response.output` carries only the parts the runtime has not already emitted on an `output` frame. Every output therefore reaches the gateway on the session's `CH-MSGSOCK` frames, in write order, and passes the same interceptor and transcript rules.

```json
{ "type": "output", "sessionId": "sess_01J9...", "parts": [{ "id": "p1", "type": "text", "status": "streaming", "inline": "Found" }] }
{ "type": "output", "sessionId": "sess_01J9...", "parts": [{ "op": "append", "id": "p1", "inline": " the failing test." }] }
{ "type": "output", "sessionId": "sess_01J9...", "parts": [{ "op": "end", "id": "p1" }] }
```

**Part operations (A5).**

| Entry | Effect |
| :-- | :-- |
| A `MessagePart` without `op` | A whole part with `status: "complete"`, the default, or the start of a streaming part with `status: "streaming"`, which then needs an `id`. |
| `{op: "append", id, inline}` | Appends `inline` to a streaming part of type `text` or `reasoning_trace`. |
| `{op: "end", id, status?}` | Ends a streaming part with `status` `complete`, the default, or `failed`. |
| `{op: "reset", id}` | Discards a streaming part, for example when the harness retries a model call halfway through. Clients remove what they rendered of it, and neither the transcript nor `PostAgentOutput` ever receives it. |

A streaming part still open when its turn closes ends `failed`, except a file part whose export is in progress or that waits for the export cap, which ends by the export's own outcome or at one of the deadlines of "MD-18", "Clocks" ("MD-18", "Export lifecycle"). A `reset` is not a retraction under "MD-11": it applies only to a part that has not completed, and the part never reaches the transcript.

**Turn.** An `output` frame opens a turn when none is open, as output opens one under "MD-4".

**Interceptors (A5).** `PostAgentOutput` runs once on each completed part, before the part reaches the transcript. On a session whose interceptor chain includes a `PostAgentOutput` interceptor, the gateway holds a streaming part's deltas and releases the completed, intercepted part as one event, so the policy sees every byte before any client does and streaming is lost on that session. A session with no such interceptor receives the deltas as they arrive.

**Transcript.** The transcript records each completed part once, at the position of its first frame, which is the position the cold-history builder of "MD-10" reads.

**Events.** The `output` SessionEvent carries the frame's entries, so a client applies `append`, `end`, and `reset` as the runtime wrote them. An adapter that does not declare `outputDeltas` in its outbound capabilities receives each part once, completed.

## MD-17 Reasoning

The owner settled A1 on 2026-11-10: "I think it could be either, depending on what the runtime implements." The runtime chooses where its reasoning goes, declares nothing, and Lenny does not convert one form into the other **[design]**.

- **As content.** The runtime emits a `reasoning_trace` output part, the registry type of §28.5.3 that AM-6 maps to a Messages API `thinking` block. The part gains `signature` (an opaque string the provider issued), `encrypted` (an opaque provider value), and `redacted` (`true` when the provider withheld the text, in which case `inline` is absent and `encrypted` carries the provider's data). The part streams under "MD-16", passes `PostAgentOutput`, and enters the transcript, cold history, and derive history. A `MODIFY` may not change `signature` or `encrypted`, and a `MODIFY` that changes the `inline` of a part carrying `signature` removes the signature, because the provider refuses an altered block.
- **As activity.** The runtime emits a `thinking` activity whose `detail.text` carries the reasoning. It stays out of the transcript unless recorded, and it never reaches a model or a provider surface.

A runtime has to emit reasoning as content when a Messages API client must send thinking blocks back with their signatures, or when the reasoning must survive in the transcript and in cold history.

## MD-18 Files

The owner settled A11 on 2026-11-10: the file goes "straight to storage", the size limit is a "5 GiB default. Runtimes can lower it", and the file has the "same retention as the session". Under A12, also of 2026-11-10, an output file is copied with the chunks, packs, and grants of [`incremental-checkpoint-design.md`](incremental-checkpoint-design.md). A file the agent produces for the user is copied into the artifact store and offered as a download. Its bytes never travel on stdout, on `CH-ATTACH`, or through the gateway **[design]**.

**Part.** A `file` part may name a workspace path in place of `inline` or `ref`:

```json
{ "type": "file", "id": "p9", "path": "out/report.parquet", "name": "report.parquet", "mimeType": "application/vnd.apache.parquet" }
```

`path` is relative to the session's workspace root and is mutually exclusive with `inline` and `ref`. A part that names a path requires an `id`. Part ids are unique per session: the gateway refuses a file part whose `id` the session already used, and the part ends `failed` with the reason `duplicate_part_id`. Small files can still be sent inline under §28.5.3's rules.

**Freeze.** When the adapter reads the part from stdout, it opens the file without following any path a runtime can swap. It holds a directory descriptor of the session's workspace root and opens `path` with `openat2` and `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` from that descriptor, so the open fails for a path that leaves the root, for a path with a symlink in any component, and for a magic link under `/proc`. It runs the regular-file check and records the file's identity with `fstat` on the descriptor it opened, and it clones or reads from that descriptor, so the file it checked is the file it copies. A failed open or check ends the part `failed` with the reason `file_not_found`, `outside_workspace`, `symlink_in_path`, or `not_regular_file`. A path through a symlink is refused even when the symlink's target lies inside the workspace, because the adapter cannot tell a safe symlink from one the runtime will swap. The adapter freezes a part when it reads it, whether the part's export starts at once or waits for the export cap ("Copy"), so it holds at most `files.maxQueuedExports` plus `files.maxConcurrentExports` open export descriptors per session, 10 at the defaults. The gateway passes both caps to the adapter with the session's other settings at bind. The adapter's count of open export descriptors is authoritative. The adapter does not open a file part beyond that count and relays it with the member `unopened: true`, an unopened part, and the gateway refuses exactly the parts that carry the marker, with `too_many_exports`, without a count of its own. The adapter sets or removes the member on every file part it relays, so a value the runtime writes has no effect. The adapter closes a part's descriptor and removes its clone when the part's export ends, whatever its outcome, and when it receives `output_failed` for the part, whether or not the gateway ever opened an `ExportOutputFile` stream for it, so a part that fails while it waits for the export cap, for example with `queue_timeout`, frees its place. The adapter then freezes the file's content:

- When the spool passed the reflink probe of [IC-1](incremental-checkpoint-design.md#capture) and the file is at least `reflinkMinBytes` (1 MiB), the adapter clones it with `FICLONE` into `/workspace/staging/export/{session_id}/{adapter_id}`, where `adapter_id` is an id the adapter mints for the export. The clone's name never carries the runtime's part id, so no part id can name a path. A clone shares the file's disk blocks and takes about 1 ms for 2 GiB on the measured nodes, so later writes by the runtime do not reach the copy. Export clones count against the spool cap of [IC-7](incremental-checkpoint-design.md#ic-7-size-limits-and-drain-budgets) and may use at most `exportSpoolFraction` of it, a constant of 0.5, so that a checkpoint's capture pass always has at least half of the spool. The clones of parts waiting for the export cap count against that share as well as the clones of running exports. On a reflink pool, a file larger than the remaining export share, 256 MiB at the default `checkpointCaptureBudgetBytes` of 512 MiB, is not cloned: the adapter reads it in place with the identity check of the next item (A21). The adapter removes the clone when the export ends, whatever its outcome.
- Otherwise the adapter reads the file in place and compares the file's identity, the device, inode, size, `mtime` and `ctime` in nanoseconds, and mode of IC's "Change detection", recorded with `fstat` when it opened the file, with `fstat` after the read. A part that waits for the export cap is read when its export starts, so a change in that wait also ends it `failed`. On a difference it ends the part `failed` with the reason `file_changed`, so the runtime can emit it again. It also applies IC's racy rule: when the file's `mtime` falls within `racyWindow` (2 s) before the read would start, an unchanged identity does not prove the content unchanged, so the adapter starts the read only once `racyWindow` has passed since that `mtime`. The check cannot see a write that changes no identity field, such as a write through a memory mapping that the kernel has not yet written back, and the whole-file SHA-256 that `ExportReady` carries is computed from the bytes read, so such a write can reach the stored copy ("Limits"). `FICLONE` works under runc on XFS with `reflink=1` and on Btrfs, and returns `EOPNOTSUPP` under gVisor and Kata on the measured nodes **[source]**, so sandboxed and microvm pools take this path.

**Copy.** The gateway records the part when it reads it from the session's stream ("Export record"), and when the part's export starts it opens an `ExportOutputFile` stream to the adapter on the channel `CH-OUTPUTFILE` ("Channel"). The stream follows the gateway-driven grant and confirm structure of the `Checkpoint` stream ([IC-3](incremental-checkpoint-design.md#ic-3-checkpoint-stream)) and reuses its pack messages. A session runs at most `files.maxConcurrentExports` exports at once, 2 by default, because the exports of a session share one grant window and gain no upload bandwidth from running in parallel, while each running export holds a quota reservation and a share of the spool. A file part over that cap waits in the session's export queue, which holds at most `files.maxQueuedExports` parts, 8 by default. The adapter's descriptor cap bounds the queue: the gateway refuses with the reason `too_many_exports` exactly the unopened parts of "Freeze", so a runtime cannot hold an unbounded number of open files and clones in the adapter, and the gateway's queue and the adapter's open descriptors cannot disagree. A waiting part stays `streaming`, and the waiting parts start oldest first as the session's exports end.

**Clocks.** Two deadlines bound a file part, and the gateway records the instant each one counts from in the part's `output_file_exports` row ("Export record"). `first_frame_at` is the instant the gateway read the part's first frame from the session's stream, and a part still waiting for the export cap `exportTimeoutSeconds` after it fails with `queue_timeout`. `started_at` is the instant the gateway sent `ExportStart`, and an export that has not reached `ExportReady` `exportTimeoutSeconds` after it fails with `export_timeout`. A part therefore ends within twice `exportTimeoutSeconds` of its first frame. The export's own deadline starts at `ExportStart` rather than at the first frame, so a part that waited for the cap still gets the whole deadline for its copy.

1. `ExportStart` names the session, the part, the path, the effective limit, and `pack_target_bytes`, and the gateway sets the part's row to `exporting` with `started_at`. The effective limit is the smaller of the operator's `files.maxBytes` (default 5 GiB) and the revision's `capabilities.output.maxFileBytes`.
2. The adapter answers `ExportProbe` with the file's size and `estimated_new_bytes`, the bytes of chunks its dedup set does not hold. The gateway refuses a file over the limit with the reason `too_large`, and reserves `estimated_new_bytes` against the tenant's storage quota with §11.2's atomic reservation, as a checkpoint reserves its estimate ([IC-4](incremental-checkpoint-design.md#quota)), recording it as `reserved_bytes` on the part's row, or refuses with `quota_exceeded`. The pod's estimate does not bound what the export can write: the gateway applies §11.2's signing-time headroom check to each grant of the export, and refuses to sign a grant whose length would carry the export's granted total past its reservation plus the tenant's remaining headroom, so an adapter that reports zero new bytes still cannot exceed the quota.
3. The adapter splits the frozen file into chunks with the content-defined chunking of [IC-2](incremental-checkpoint-design.md#ic-2-storage-format): a minimum of 256 KiB, an average of 1 MiB, and a maximum of 4 MiB, each named by the SHA-256 of its bytes and compressed with zstd unless compression saves less than 3%. It skips every chunk its dedup set holds, and it checks each chunk against the dedup set when it packs the chunk, so a chunk that a checkpoint confirmed while the export ran, the seal's included, is referenced rather than uploaded. The dedup set is the one a checkpoint uses: chunks of the session's retained snapshots, of the snapshot it started from, of its unreferenced packs under lease, and of its earlier output files ("Retention"). A chunk enters the dedup set only after the gateway has confirmed its pack with `PackCommitted`, so a checkpoint never references a chunk of an export whose pack upload is still in flight, and the reverse. `Resume` and `CheckpointStart` carry the session's output-file chunk lists and its leased packs, so the dedup set of a new pod includes them. A file that a checkpoint already captured therefore uploads only the chunks that changed since that checkpoint.
4. The adapter packs the new chunks into packs with a 16 MiB target and the 32 MiB `packMaxBytes` bound, writes a random 128-bit nonce into each pack's footer, as it does for a checkpoint's packs ([IC-2](incremental-checkpoint-design.md#packs)), and declares each with `PackReady` (`pack_id`, `length`, and `content_md5`). The nonce makes every pack the adapter builds distinct, so no two packs share a pack ID (A18). The gateway first checks the declared length: a length of zero ends the export with the reason `pack_empty`, and a length over `packMaxBytes` with `pack_too_large`, and nothing is signed. It then resolves the pack ID against the session's own object key, `(tenant_id, owner_session_id, pack_id)`:
   - When the catalog holds that key and the pack is in the session's allowed set, the gateway answers "already stored", with the message `PackStored`, and the adapter skips that upload and references the pack. This is the resend of a pack the adapter built, after a `PackCommitted` that the stream lost, because the adapter resends the pack with the same nonce.
   - When the catalog holds that key in any other state, a soft-deleted row included, the gateway signs nothing and ends the export with the reason `pack_key_held`, as S1 states. A soft-deleted row keeps its key until the tombstone sweep removes it, so the key stays held for that time.
   - When the catalog holds no row for that key, the gateway checks the packs in the session's allowed set that another session owns, which are the packs of a derived session's starting snapshot. A match is answered `PackStored`, and the session's reference names that pack's owner. These keys are consulted for the "already stored" answer only and never lead to a grant.
   - Any other pack is answered `PackGrant`, a single-key `PUT` grant for `/{tenant_id}/checkpoints/{session_id}/packs/{pack_id}` that signs `Content-Length`, `Content-MD5`, and the server-side encryption headers of [§13.2.3](../spec/13_security-model.md#1323-checkpoint-capability-model).

   The answers reveal nothing outside the session's own keys and its allowed set, which the session may already read.
5. The adapter uploads each pack and sends `PackCommitted`. The gateway checks the object's length with `StatObject` and records the pack as a checkpoint records one, in state `unreferenced` with a lease, and adds its bytes to `confirmed_bytes` on the part's row in the same transaction. Its charge draws down the export's reservation and does not add to it.
6. The adapter sends `ExportReady` with the file's chunk list, each chunk's offset and length in the file and its pack ID, the referenced pack IDs, and the SHA-256 of the whole file. The gateway treats this metadata as untrusted. It checks that the chunk offsets are contiguous from 0, that each chunk's length is at most the 4 MiB maximum chunk and matches the length the pack's footer lists for that chunk, and that the lengths sum to the size from `ExportProbe`, which is within the effective limit. These checks catch a missing or overlapping chunk. It runs the reference closure check of [IC-4](incremental-checkpoint-design.md#reference-closure). A closure failure answers `ReferenceRefused` with the offending pack IDs, and the adapter evicts their chunks from its dedup set, uploads the chunks again in new packs, and sends `ExportReady` again. The gateway then writes the `output_files` row, which records for each chunk its pack ID and its offset within the pack and records the whole-file SHA-256, its `output_file_packs` references, and the state `ready` on the part's row in one transaction. It releases the rest of the reservation by the guarded update of "Export record", sets `ref` to the file's `lenny-blob://` URI and `sha256` to the whole-file SHA-256, releases the part to `PostAgentOutput` as complete, and closes the stream.

A failed stream leaves the confirmed packs under lease. A retry of the export reuses their chunks, because the retry's dedup set holds the chunks of the session's confirmed packs under lease, as a failed checkpoint attempt's chunks are reused (R3 of that design). The adapter never rebuilds a pack to reuse it: the chunks a retry has to upload again go into new packs, with new nonces, new pack IDs, and new grants. The part ends `failed` with the reason the stream carried.

**Refusals.** The gateway ends a failing export with `ExportAbort`, which carries the reason, in place of the `CheckpointAbort` of the `Checkpoint` stream. The reasons it sends on the stream are `too_large`, `quota_exceeded`, `pack_empty`, `pack_too_large`, `pack_key_held`, `export_timeout`, `seal_timeout`, and `pod_evicted`. The adapter answers `ExportAbort` by removing the clone and closing the stream, and the part ends `failed` with the same reason. A `PostAgentOutput` `REJECT` and the scanner's hash mismatch of "Turn close and interceptors" come after step 6 has closed the stream, so they reach the adapter only as the `output_failed` frame, with the reasons `rejected` and `digest_mismatch`.

**Export record.** The gateway records each file part in `output_file_exports` when it reads the part from the session's stream. The table is keyed by `(session_id, part_id)` and holds `tenant_id`, `state` (`queued`, `exporting`, `ready`, or `failed`), `first_frame_at`, `started_at`, `reserved_bytes`, `confirmed_bytes`, `reservation_released_at`, `coordination_generation`, the generation of the coordinator that drives the export, `failure_reason`, and `notice_acked_at`. The reservation follows §11.2 as a checkpoint's does. Step 2 takes it with the atomic Redis increment and records `reserved_bytes`. Every party that ends the export, the success and failure arms, a new coordinator, and the §12.5 backstop for a row of a terminal session, releases it with one guarded `UPDATE ... SET reservation_released_at = now() WHERE session_id = $1 AND part_id = $2 AND coordination_generation = $3 AND reservation_released_at IS NULL`, and applies the counter decrement, `reserved_bytes − confirmed_bytes`, only when that update changed the row (**Reservation release is exactly-once and guarded.**). The generation guard applies to every release and every state transition of the row: each update carries `AND coordination_generation = $gen`, where `$gen` is the writing coordinator's own generation, or for the backstop the generation it read from the row, so a coordinator that a handoff replaced changes no row and releases no reservation (MDR-34). `Rehydrate` adds `reserved_bytes − confirmed_bytes` over the rows whose `reservation_released_at` is null, so a rebuilt counter still holds every outstanding export reservation (**The relative decrement is rebuild-safe.**). A new coordinator reads the session's rows after the pod acknowledges its fence. It takes over each unreleased reservation by writing its own generation to the row with an update guarded by `coordination_generation < $gen`, without reserving again, reopens `ExportOutputFile` for each `exporting` row, keeps each `queued` row waiting, and applies `exportTimeoutSeconds` from `started_at` and from `first_frame_at` as "Clocks" states. A stream that the adapter cancels when it acknowledges the new coordinator's fence is not a failure for the previous coordinator: that coordinator stops the stream without releasing the reservation, changing the row, or sending `output_failed`, and the new coordinator carries the export on. A row lives as long as the session's other records.

**Turn close and interceptors.** A file part whose export is in progress is exempt from the rule of "MD-16" that a streaming part open at turn close ends `failed`, and a part that waits for the export cap counts as exporting for that exemption. It ends by the export's own outcome, or at a deadline of "Clocks". On a session whose interceptor chain has no `PostAgentOutput` interceptor, clients see the part until step 6 with `status: "streaming"` and its `name`, `mimeType`, and `sizeBytes`. On a session whose chain has one, clients receive nothing about the part, neither a placeholder nor its name or size, until the interceptor answers, so MDR-21 holds. Later frames are not held behind the export, and the part keeps the position of its first frame. A `REJECT` from `PostAgentOutput`, which may read the file through `ref` to scan it, withholds the part with the reason `rejected` and deletes the `output_files` row, after `EnsureCopied` when a hold covers the session ("Retention"), and pack reclamation removes any pack that nothing else references. When the scanner reads the whole file through `ref`, the gateway hashes the bytes it serves and compares the result with the whole-file SHA-256 that `ExportReady` carried. On a mismatch it refuses the part at the `PostAgentOutput` stage as a `REJECT`, with the reason `digest_mismatch`, and the deletion that follows a `REJECT` runs. This is the only place the gateway compares the whole-file hash, because it is the only read of the whole file that precedes release (A20).

**Deadlines.** `exportTimeoutSeconds` is a pool setting, 900 seconds by default, counted from `ExportStart` ("Clocks"). At the default 5 GiB limit it allows an average of about 5.7 MiB/s from `ExportStart` to `ExportReady`, which is about a fifth of the slowest whole-workspace rate the checkpoint benchmarks measured, 5.9 GiB in 208 s on 2 CPUs under gVisor, and it bounds how long a failed export can hold a quota reservation and a spool clone. When it passes, the gateway fails the part with the reason `export_timeout`, releases the export's unused reservation, and sends `ExportAbort`, and the adapter removes the clone. A confirmed pack is kept under its pack lease, `packLeaseSeconds`, a gateway setting of 1800 seconds by default ([IC-4](incremental-checkpoint-design.md#catalog)). Pool admission refuses a pool unless `packLeaseSeconds` is at least twice the larger of `checkpointAttemptTimeoutSeconds` and `exportTimeoutSeconds`, so a retry that runs a whole deadline after a timed-out attempt or export still finds the packs that attempt confirmed. The lease is extended each time an `ExportReady`, a `SnapshotReady`, or an "already stored" answer references the pack, so a pack a retry is about to reference does not expire under it.

**Seal window (A19, A23).** `maxWorkspaceSealDurationSeconds` is the pool setting of §7.1, and under A19 it is also a runtime field, versioned and gateway-read under RV-1. A session's effective value is its seal window, resolved in this order: the value in the session's revision, then the value on its pool, then the gateway flag `--workspace-seal-max-duration-seconds` (300 seconds by default), each at most the seal window ceiling. The pool value is a field of the pool record that the admin pool API writes, checked by `validatePoolForStore` in `pkg/gateway/externalapi/admin/pools.go` and by the bootstrap pool validation in `bootstrap.go`, and it is mirrored wherever the gateway reads the pool record. A tenant-derived runtime's owned pool copies it from its template pool under "Template copy" of [`tenant-derived-runtimes-design.md`](tenant-derived-runtimes-design.md), because it is not a pool setting a tenant may write; the tenant sets the runtime field instead. The chart value `gateway.workspaceSealMaxDurationCeilingSeconds`, the seal window ceiling, bounds both: pool admission refuses a pool, and a runtime write refuses a runtime, whose value exceeds it. The chart renders the ceiling as the gateway flag `--workspace-seal-max-duration-ceiling-seconds` (`LENNY_WORKSPACE_SEAL_MAX_DURATION_CEILING_SECONDS`), because the gateway runs both pool admission and runtime writes, and the gateway refuses at startup a `--workspace-seal-max-duration-seconds` above it. A runtime write also refuses a value that is not greater than `delegation.usageQuiescenceTimeoutSeconds`, the rule §8.3 **Return on completion** states for a pool's value, because the runtime's value replaces the pool's in the terminal pipeline that rule protects. A tenant-derived runtime may set the field within the same bounds. The ceiling defaults to 600 seconds, twice the default seal window, so a runtime whose workspace or exports need more time can double the seal's retry window, and at 600 seconds the computed claim orphan timeout below stays at today's 900 seconds. A session's terminal pipeline budget is its own seal window plus the release allowance of 30 s, and the bound a deployment check reads is the ceiling plus the allowance, 630 seconds at the defaults. The readers of the window follow from that split. The seal's retry window, the terminal context of the pipeline, and the post-terminal window of §7.1 **Post-terminal window:** rule 1, which the session store caps, take the session's own budget. The `CH-ATTACH` stream-failure report, whose bound the gateway sets before it reads the session, and the shutdown wait of §10.1 **Terminal pipelines at process exit.**, which covers sessions with different windows, take the ceiling plus the allowance. `sessionserver.TerminalPipelineBudgetFor` keeps its signature, and its callers pass the window that applies.

**Post-terminal deadline (A22).** §7.1 **Post-terminal window:** rule 1 caps a session's post-terminal window at its own terminal pipeline budget, and a session's budget depends on its seal window, so one store-wide cap cannot be exact. The gateway's terminal write, which sets `terminated_at`, also sets `post_terminal_until` on the session row to `terminated_at` plus the session's terminal pipeline budget, computed from the session's effective seal window, which the gateway reads from the session's revision and pool. §7.1 **Gateway-owned terminal writes:** makes the gateway the only writer of a terminal state, so every terminal row carries the column. `InPostTerminalWindow` and `HoldsPod` (`pkg/gateway/session/sessionstore/terminal_mark.go`), the Postgres store's slot queries, and the retention collector (`pkg/gateway/storage/retentiongc`) compare the time against `post_terminal_until` in place of `terminated_at` plus a cap, so the store option `WithPostTerminalCap` and the collector option `PostTerminalCap` are removed. A terminal row that names a pod and records no release and no `post_terminal_until` counts as holding its pod, because a window held too long only delays the pod's reuse, while a window ended too early frees a pod whose seal or export may still read its workspace. The window still ends at once when the gateway records the release, as rule 1 states. The platform has no deployments, so no existing row needs a value.

**Pool admission and the `claimOrphanTimeout` bound (A23).** §5.2 **Slot assignment atomicity** says that pool admission refuses a pool whose configuration does not meet the `claimOrphanTimeout` bound, and no window that bound reads is a pool field in the tree (F-5.2.57). Under this design the bound reads the seal window ceiling: pool admission refuses a pool whose `maxWorkspaceSealDurationSeconds` exceeds the ceiling, and the gateway's startup check, or the chart's computed default, makes `claimOrphanTimeout` and the stale-slot terminal age exceed the ceiling plus the release allowance by at least one second. Every admitted pool therefore meets the bound. The other windows the bound guards, the launch window of `maxFinalizingTimeoutSeconds` and the `resuming` watchdog, stay gateway flags that the startup check already reads. The §5.2 sentence is rewritten to state that pool admission refuses a pool whose seal window exceeds the ceiling, which is how a pool meets the bound, in place of a pool-admission check with no input. Proposal MD-D lands this rewrite and the pool field and closes F-5.2.57.

The windows that §5.2 **Slot assignment atomicity** guards are the launch, which `maxFinalizingTimeoutSeconds` bounds (600 s by default), a restore in `resuming`, which the `resuming` watchdog bounds (300 s), and the terminal pipeline, whose bound the chart takes as the ceiling plus 30 s. When the operator does not set `controller.claimOrphanTimeoutSeconds`, the chart renders into the controller's `--claim-orphan-timeout` and the gateway's `--slot-reaper-terminal-age` the larger of 900 seconds and one second more than the largest of those windows, rounded up to a whole minute. At the default ceiling that is 631 seconds rounded to 660, so the default stays 900 seconds, and a ceiling of 900 seconds gives 960 seconds. The chart computes from the defaults of the finalizing and `resuming` deadlines, which it does not render, so the gateway's startup check `validateSlotReaperFlags` still verifies the terminal age it runs with, an explicitly set value included, against the deadlines in effect and the ceiling plus the release allowance, and the chart still fails to render an explicit value below that floor.

**Export lifecycle (A15, A19).** An export, or a part that waits for the export cap, ends in these cases besides its own outcome:

- **Seal (A19).** At session end the seal checkpoint runs first. It and the session's exports share one window, the session's seal window, counted from the start of the seal, which keeps its meaning as the retry window for object-store failures of the seal export. The gateway signs no export grant while the seal checkpoint runs, so the checkpoint has the whole grant window, as on a drain. The seal checkpoint captures the workspace, which holds every exported file, and the seal and the exports share one dedup set, so the seal uploads an exported file's chunks once, and an export that continues after it references the chunks the seal confirmed at step 3 and finishes its bookkeeping. Exports still running, and parts still waiting for the export cap, when the seal checkpoint ends finish in the time the seal leaves in the window, and waiting parts start as running exports end. Under an effective `checkpointPolicy` of `none`, which takes no seal snapshot, the exports get the whole window. When the window ends, each part still exporting or waiting fails with `seal_timeout`. The terminal pipeline budget stays the seal window plus the release allowance of 30 s, as §7.1 states it, because the exports end inside the seal window. Three cases upload an exported file's bytes apart from the seal:
  - A file that the runtime changed or deleted after it emitted the part is exported from its clone. The clone's chunks are not in the seal snapshot, which captured the file's later content or no file, so they upload separately.
  - An export pack whose grant is outstanding when the seal starts is not yet confirmed, so its chunks are outside the dedup set and the seal may upload them again. The gateway signs no export grant while the seal checkpoint runs, so at most one grant window of packs, 128 MiB at the default window, is uploaded twice.
  - Under an effective `checkpointPolicy` of `none`, no seal snapshot stores any chunk, so each export uploads every chunk its dedup set does not hold.
- **Drain.** On a preStop drain of the agent pod, the eviction checkpoint runs first, within `evictionCheckpointCapSeconds`, and the gateway signs no export grant while it runs, so the checkpoint has the whole grant window. Exports then continue only with the budget the checkpoint leaves in the drain's checkpoint stage. An `ExportOutputFile` stream never uses the stream-drain stage of §10.1.7: an export still running when the checkpoint stage ends fails with `pod_evicted`, and so does each part still waiting for the export cap at that point. A gateway replica's own preStop drain does not wait for its export streams, which the session's next coordinator reopens.
- **Idle suspension.** An export in progress, and a part that waits for the export cap, count as agent work for idle suspension, as activity does under "MD-15", so a session does not suspend while one of its files is being copied.
- **Explicit suspend.** A client or an admin who suspends a session through `POST /v1/sessions/{id}/interrupt` does not end its exports. The session moves to `suspended` as that route states, and the exports continue on the pod the suspension holds, under their own deadlines, because an export is the adapter's work rather than the runtime's. When the hold of `maxSuspendedPodHoldSeconds` ends, each part still waiting for the export cap fails with `suspend_hold_expired`, and the gateway starts no further export. It releases the pod only after the exports already started end. Each of them started before the hold ended and fails at `exportTimeoutSeconds` from its `ExportStart`, so the release comes at most `exportTimeoutSeconds` after the hold ends, 900 seconds at the default. A failure while the session is suspended reaches the runtime after the resume ("Failure notice").
- **Coordinator handoff.** When the pod acknowledges the new coordinator's fence, the adapter cancels the session's open `Checkpoint` and `ExportOutputFile` streams of the previous generation ("Grant window"). The cancellation is not a failure for the previous coordinator, which stops each such stream without releasing its reservation, changing its row, or sending `output_failed`, and its own updates no longer match the row's generation ("Export record"). The new coordinator then takes over the session's `output_file_exports` rows ("Export record") and reopens `ExportOutputFile` for each part that is still exporting. The adapter reuses its clone and its confirmed packs, and the export continues from step 2 without a second reservation. When the clone is gone, the part fails with `clone_lost`.
- **Pod loss.** The part fails with `pod_lost`, and the gateway releases the export's unused reservation.

Every terminal outcome settles the reservation exactly once by the guarded update of "Export record": success settles it at step 6, and a failure, a timeout, a `REJECT`, and a pod loss release what the confirmed packs did not draw down.

**Failure notice (A15).** When a file part fails, the gateway sets the part's row to `failed` with `failure_reason`, emits the session event `output_failed`, and sends the frame `output_failed` on `CH-ATTACH`, which the adapter writes to the runtime as it writes every envelope the gateway sends:

```json
{ "type": "output_failed", "sessionId": "sess_01J9...", "id": "p9", "reason": "file_changed" }
```

The runtime acknowledges the notice with the frame `output_failed_ack`, which the runtime SDKs write after `OnOutputFailed` returns ("MD-12"), and the adapter relays it to the gateway as a session-scoped frame:

```json
{ "type": "output_failed_ack", "sessionId": "sess_01J9...", "id": "p9" }
```

The gateway records the acknowledgement as `notice_acked_at` on the part's row. A notice without an acknowledgement stays on the row, and the gateway sends the frame again after each resume of the session and after a coordinator handoff, until the runtime acknowledges it or the session reaches a terminal state, so a failure that a pod loss or a suspension cut off reaches the restored runtime. A runtime receives no frame after the session's terminal transition, so a part that fails at the seal reaches clients through the event alone.

| Kind | Payload | Fires when |
| :-- | :-- | :-- |
| `output_failed` | `{ "partId", "partType": "file", "reason", "turn"? }` | A file part ends `failed`. The part's own `output` entry also ends `failed` with the same reason. |

The reasons are `duplicate_part_id`, `too_many_exports`, `file_not_found`, `outside_workspace`, `symlink_in_path`, `not_regular_file`, `file_changed`, `too_large`, `quota_exceeded`, `pack_empty`, `pack_too_large`, `pack_key_held`, `queue_timeout`, `export_timeout`, `seal_timeout`, `pod_evicted`, `suspend_hold_expired`, `clone_lost`, `pod_lost`, `rejected`, `digest_mismatch`, and the reason a failed stream carried. A runtime that receives the frame can emit the file again as a new part with a new `id`. On a session with a `PostAgentOutput` interceptor, the event reaches clients only for a part the interceptor has already answered, because clients have received nothing about an earlier one.

**Channel.** `ExportOutputFile` is a new conversation on `LNK-POD-GRPC`, the gateway's gRPC link to the adapter, so it takes its own channel under the specification's naming law: `CH-OUTPUTFILE`, a mnemonic for the output-file copy, which shares no stem with `CH-CHECKPOINT` or any other channel on the gateway-to-pod boundary and uses neither reserved word. Its register row in §28.3 names `LNK-POD-GRPC`, the `gateway-to-pod` boundary, the state plane, the gateway as dialler, authority on both sides, gRPC, and the vocabulary "Output-file copy to object storage". Its contract card states generation fencing as the other fenced gateway-to-pod channels do: the pod rejects a stream that carries a generation other than the one it holds for the session, cancels the session's open stream of the previous generation when it acknowledges a new coordinator's fence, and the new coordinator completes the handoff protocol before it reopens one. An export takes no pod-wide operation lock, so the `CH-OBJSTORE` row in §28.5.5 and §28's statement that the operation lock bounds the transfer `CH-OBJSTORE` carries change to name the export transfer as one the lock does not bound. A claim-register row with status `ABSENT` records the channel until the code lands.

**Grant window (A12, A13, A14, A17).** The gateway counts the outstanding pack grants of a session across its `Checkpoint` and `ExportOutputFile` streams against one window, the pool's effective `checkpointGrantWindow`: the per-pool override `SandboxTemplate.checkpointGrantWindow` when set, at most 8, and otherwise the gateway's default of 4. The gateway refuses at startup a `--checkpoint-grant-window` (`LENNY_CHECKPOINT_GRANT_WINDOW`) above 8, as admission refuses a pool override above 8, so the default window cannot exceed the bound either. The counter lives on the session's coordinating replica. On a coordinator handoff, the new coordinator cannot see which grants the previous one signed, and the pod accepts the previous coordinator's RPCs until it acknowledges the new coordinator's fence (§10.1.2, step 2). The new coordinator therefore counts the session's whole window as outstanding until the grant TTL, `checkpointCapabilityTTLSeconds` (30 s), has passed since the pod acknowledged the fence. When the adapter acknowledges the fence, it cancels the session's open `Checkpoint` and `ExportOutputFile` streams of the previous generation, so the previous coordinator signs no grant after the acknowledgement, and every grant it signed before expires within that count. A compromised pod can therefore write at most the pool's effective window times `packMaxBytes` of chosen bytes at once, 128 MiB by default and at most 256 MiB, which is the bound of S5. Today's bound is `checkpointGrantWindow × partialChunkSizeBytes`, 4 × 16 MiB, so the pack format doubles it by default. The bound limits a burst of chosen bytes in the session's own prefix, which the tenant's quota pays for and garbage collection reclaims. An export slows the pre-copy and upload passes of a concurrent checkpoint of the same session, which share the window. During a checkpoint's capture pass the adapter pauses export reading, hashing, and compression, so an export does not compete with the capture for disk and CPU while a Full-level runtime is quiesced, and uploads of packs the export already built continue. The export takes no quiesce and no pod-wide operation lock.

**Size (A11b).** The default of 5 GiB is a policy limit. No single upload approaches the object store's 5 GiB limit for one `PUT`, because every pack is at most 32 MiB. The tenant's quota and the pool's `workspaceSizeLimitBytes`, which already bounds the file inside the workspace, also apply. `capabilities.output.maxFileBytes` is versioned and gateway-read under RV-1, and it can only lower the operator's limit.

**Download.** The gateway renders an output file from its chunk list and packs with its own object-store credentials, as [IC-5](incremental-checkpoint-design.md#download) renders the workspace download, and verifies the SHA-256 of each chunk as a restore does (S4). `GET /v1/blobs/{ref}` serves it with the file's `mimeType` and accepts a `Range` header, which the row's chunk offsets and pack offsets resolve to the byte ranges of the packs that hold the range, so an interrupted download resumes. S4's check of every chunk it serves is the storage-integrity guarantee: a corrupt or substituted pack fails the read of the chunk it holds (A20). The whole-file SHA-256 that `ExportReady` carried is metadata. The gateway publishes it as `sha256` on the released file part and in a `Repr-Digest` header (RFC 9530) on every response of `GET /v1/blobs/{ref}`, as `Repr-Digest: sha-256=:<base64 digest>:`, so a client can verify its download end to end. `Repr-Digest` describes the full representation whatever its content coding and range, so a `206` response to a `Range` request carries the same value and a client that assembled ranges can still verify the file. `Content-Digest` describes the bytes of each response's content, which for a `206` response is the range alone, so it does not fit. The gateway itself compares the hash only on the scanner's read of "Turn close and interceptors". The whole-file hash cannot detect a compromised pod, which writes both the chunk list and the hash, and the `ExportReady` checks catch missing or overlapping chunks. An adapter that orders chunks wrongly is caught by the tier 1 and tier 10 tests. `GET /v1/sessions/{id}/artifacts` lists the file. "MD-21" states the other surfaces.

**Retention (A11c, A16).** The `lenny-blob://` URI of an output file takes the session's retention as its `ttl`, in place of the 1-hour live-delivery default of §28.5.3. The `output_files` row lives for the session's retention, and its `output_file_packs` references keep its packs alive: pack reclamation ([IC-6](incremental-checkpoint-design.md#ic-6-retention-garbage-collection-erasure-and-legal-hold)) counts them beside `checkpoint_snapshot_packs`, so a pack that a rotated snapshot shared with an output file stays. Erasure under §12.8 deletes the file's row, and a legal hold on the session keeps it. Under A16, a security hold whose `include` lists `artifacts` covers output files under FE-3, and it copies an output file's packs and its `output_files` row to escrow, as IC-6 copies a held snapshot's packs. The §12.8 legal-hold escrow handles a pack-backed item, a snapshot or an output file, the same way: it copies every pack the item references and the item's row. Every path that deletes an `output_files` row, the deletion after a `REJECT` included, calls `EnsureCopied` first, and the refusal for `digest_mismatch` takes the `REJECT` path.

**Security model.** §13's "File delivery" row names checkpoint chunk objects as the exception to gateway-mediated delivery. The packs of output files are checkpoint packs under the same capability model: keys under the session's own pack prefix, the `PUT` method alone, a signed `Content-Length` and `Content-MD5` of at most `packMaxBytes`, a short expiry, and no `LIST`, `DELETE`, or multipart capability (R5 of that design). The pod holds no object-store credential, and naming a chunk hash grants no read (R6).

**Performance.** The incremental checkpoint design's benchmarks bear on exports **[source]**:

- Reading dominates on sandboxed and microvm pools. A 4 KiB file costs 5 to 13 µs to read under runc and on a Kata block volume, and 46 to 129 µs under gVisor and on Kata's shared file system. A large file is read sequentially, and its export time is then set by the hashing and compression CPU and the upload bandwidth, which those benchmarks did not measure for a single large file ("Validation owed").
- The adapter's CPUs matter. With 2 CPUs in place of 4, the first checkpoint of a 5.9 GiB checkout under gVisor took 208 s against 139 s.
- Deployer levers that speed exports as they speed checkpoints: gVisor's pod-share mount hint, which made restore 3.2 times faster, Kata's `virtio_fs_cache = "metadata"`, and a Kata block volume, which measured close to runc.
- Deduplication removes most of the cost of exporting a file that a checkpoint already captured, and a retry after a failure uploads only the chunks that no confirmed pack holds.

**Isolation profiles.** The export works on `standard`, `sandboxed` (gVisor), and `microvm` (Kata) pools, because it uses the reads, the egress policy, and the pack grants that checkpoints use under every isolation profile ([§13.2](../spec/13_security-model.md#132-network-isolation), NET-071). Only the reflink clone is limited to runc on a filesystem that supports it. The freeze also needs `openat2` with its resolve flags in the adapter's kernel or sandbox, which "Validation owed" lists for gVisor and Kata.

## MD-19 Harness approvals

The owner settled A4 on 2026-11-10. Coding harnesses ask permission before running their own tools, for example Claude Code's `can_use_tool`, Codex's `item/*/requestApproval`, and the Agent Client Protocol's `session/request_permission` **[external]**. Lenny's tool-use approval path (SO-5a) covers only tools that Lenny routes **[source]**, so today an adapter has to approve a harness's tools automatically or leave the harness waiting **[design]**.

**Tool.** The platform MCP server gains `lenny/request_approval`, which a Standard or Full runtime calls for a harness's request:

```json
{ "toolUseId": "toolu_01A", "tool": "Bash", "input": { "command": "rm -rf build/" }, "title": "Delete the build directory", "reason": "Clean rebuild requested" }
```

It returns `{ "decision": "approved" | "denied", "updatedInput"?, "message"?, "source": "client" | "policy" }`. `updatedInput` carries a client's edit of the input, which the harness applies, as Claude Code's `updatedInput` and AG-UI's `editedArgs` do **[external]**.

**Path.** The gateway emits a `tool_use` event with `target: "harness"` and phase `requested`, approval required, which takes the projection approval-required `tool_use` events take today: MCP `elicitation/create`, and the REST routes `POST /v1/sessions/{id}/tool-use/{toolCallId}/approve` and `.../deny`. The approve route accepts `updatedInput`. The call blocks until a decision or the approval timeout of SO-5a.

**Unattended sessions.** The session create request takes `harnessApprovals: { "allowTools": [...], "unattended": "deny" | "allow" }`, with a default on the runtime revision. A tool in `allowTools` is approved at once without asking. When no client answers within the approval timeout, the gateway answers with `unattended`, which defaults to `deny`. A tenant's policy may narrow both members. Each decision writes the approval audit record SO-5a writes, with `source`.

**Boundary.** The harness runs the tool inside the pod, so Lenny relays the decision and cannot enforce it. The sandbox and the egress policy remain the security boundary, and the approval is a user-facing gate.

**Reader.** The approval waits off the session's frame reader, so frames keep flowing while a harness or a Lenny tool waits for approval (MDF-8).

**Questions.** A harness's structured question to the user, such as Claude Code's AskUserQuestion, and a plan proposed for approval, such as Codex plan mode or Claude Code's ExitPlanMode, are elicitations through `lenny/request_elicitation`, and their answers return through the elicitation path.

## Worked example

Alice, of tenant `acme`, runs the `claude-code` runtime through REST. Its revision declares `modes: [steer, queue, interrupt]`.

1. Alice sends "Run the migration against the dev database." No turn is open, so the message `msg_A` takes the direct path, its receipt is `delivered`, and a turn opens. Claude Code starts running shell commands.
2. Alice sends "Use the staging database instead." with no `delivery`. The default is `steer`, a turn is open, and the steer path writes `msg_B` at once. The receipt is `delivered`. Claude Code reads it when the running command finishes, and the adapter writes `consumed` with `msg_B`. Alice's event stream shows `message_state` `consumed` for `msg_B`.
3. Alice sends "Afterwards, write a summary." with `delivery: "queue"`. The queue path holds `msg_C`, and the receipt is `queued`.
4. A child session that the agent started sends "Schema check passed." through `lenny/send_message` with no `delivery`, which steers it into the running turn. The child's call returns `delivered` at once.
5. The agent had earlier sent its other child, which is suspended waiting for a resume, "Also run the slow integration suite." as `msg_D`, held `pending` in that child's DLQ. Having switched databases, the agent writes `retract` with `msg_D`. The entry is still `pending`, so it becomes `retracted`, the agent receives `retracted`, and the audit log records `message.retracted`. A second id in the same frame names a message the first child already consumed, and its result is `too_late`.
6. The runtime ends the turn with a `response` whose `consumed` lists `msg_A` and the child's message. Alice receives `turn_end` with turn 1 and those ids. The turn end makes `msg_C` eligible, the gateway writes it, and turn 2 starts.
7. The pod is lost during turn 2 after the runtime consumed `msg_C`, and before a checkpoint recorded it. The session resumes from the checkpoint taken after turn 1, whose consumed set ends with the child's message. The gateway recorded the consumption of `msg_C` after that message, so under O4 `msg_C` is not redelivered and moves to `consumed_unrecorded`. Alice's event stream shows `message_state` with `consumed_unrecorded` for `msg_C`, and she sends "Afterwards, write a summary." again as a new message, which the restored runtime takes as a new turn.

A second example covers a provider surface under O3. Bob, of tenant `acme`, uses the Anthropic SDK against a runtime whose revision declares `steer`, `conversationInput`, and `clientTools`, on a pool with `conversationContinuity: "platform"`.

1. Bob sends a request with a client tool `open_ticket` and "Investigate the failing build." The runtime delegates a child to bisect the failure and replies "I started a bisect." The gateway returns the reply, stores the digest, and holds the session.
2. The child finishes and sends the parent "The regression is in commit 4f2a." No turn is open, so the message takes the direct path and opens a turn. Its envelope carries no `conversation.clientTools`. The runtime writes a summary of the finding, which reaches the transcript and the session's REST and MCP event streams. No Messages response carries it, and the turn writes no response record and no digest.
3. Bob sends his next request while that turn runs. Its history up to the last assistant message matches the stored digest, so it is a warm turn, and its message takes the steer path with its `conversation.clientTools`. The runtime writes `consumed` for the message, answers, and ends the turn with a call to `open_ticket`. Bob's response carries the output that followed the `consumed` frame and a `tool_use` block, with `stop_reason: "tool_use"`.

A third example covers what Alice sees during a turn. Her session runs `claude-code`, whose adapter uses `stream-json`, and her deployment configures no `PostAgentOutput` interceptor.

1. Alice sends "Fix the flaky test and export the failure report." The gateway emits `turn_start` with turn 3.
2. Claude Code writes its todo list. The adapter writes `activity` `start` for `plan_1` with `kind: plan`, `lifetime: session`, and three entries, and Alice's client draws the list.
3. Claude Code runs `npm test`. The adapter writes `activity` `start` for `act_9` with `kind: tool` and `record: true`, then `append` frames that grow `detail.output`, which it merges every 250 ms. The command needs approval, so the adapter calls `lenny/request_approval` and Alice approves it on the REST approve route. Frames keep flowing while she decides.
4. Alice's laptop sleeps and her client reconnects. It receives the replayed events and one `activity` snapshot with `plan_1` and `act_9`, so it redraws both.
5. The test ends. The adapter writes `end` for `act_9` with `status: completed`, the gateway writes its final state to the transcript, and a `patch` marks the plan's first entry completed.
6. Claude Code writes its explanation, which streams as `output` `append` entries to part `p4` and ends with `end`. The transcript records `p4` once, after `PostAgentOutput`.
7. Claude Code writes a 200 MB failure report to `out/failures.parquet` and emits a `file` part with that path. Alice's pool runs runc on XFS, and the file fits the export share of the spool, so the adapter clones the file into its spool at once. Alice's client shows the part as `streaming` with its name and size while the adapter chunks the clone, skips the chunks the last checkpoint already stored, and uploads about 12 packs of 16 MiB, four at a time. The turn could end first, and the part would still finish, because an export outlives its turn. The gateway confirms each pack, checks the references, sets `ref`, and releases the part, and Alice downloads the file with `GET /v1/blobs/{ref}`.
8. The runtime writes its `response`. The gateway emits `usage` events with `source: gateway` for each proxied model call during the turn, and `turn_end` with `status: completed` and the turn's usage. `plan_1` stays open, because its lifetime is the session.

## Limits

- **Runtime cooperation.** `steer` works only as well as the runtime's placement of messages. The gateway cannot check that a runtime places a message after tool results, and the conformance cases of §15.4.6 test it against recorded model requests.
- **In-memory inbox.** Custody survives a coordinator crash only with the durable inbox. With `messaging.durableInbox: false`, the documented loss window of §7.2 applies to `pending` and `delivered` entries alike.
- **Duplicates after a restore.** Consumed messages are never redelivered, so a duplicate arises only from a redelivered `delivered` entry that the restored runtime already holds: one it consumed before the checkpoint and had not yet reported. A runtime that does not persist its consumed ids with its history can read such a message twice. The SDK's set covers a runtime whose history the SDK holds, and the adapter's checkpointed set covers a consumption the runtime reported before the checkpoint, up to its bound of 1000 ids.
- **Consumption after the last checkpoint is not replayed.** Under O4, a runtime restored from a checkpoint lacks the messages it consumed after that checkpoint, and the gateway reports them `consumed_unrecorded` in place of resending them. A sender that does not read the event loses the message's effect on the runtime's history.
- **Late consumption reports.** A runtime that declares `queue` alone reports consumption only on `response`, so its messages stay `delivered` for the whole turn.
- **Agent interrupts.** Any sender within the messaging scope can send `interrupt` to a target that declares it, so a sibling can stop another's turn. Rate limits and scope bound it, and the audit record names the sender.
- **Provider surfaces do not steer.** A user of a Chat Completions, Responses, or Messages client cannot correct a running turn, because those APIs have no request for it.
- **Other turns are outside provider responses.** Under O3, the output of a turn that no client request caused reaches the transcript and the REST and MCP event streams, and no provider-surface response. A client that reads only its provider responses learns of such a turn only when the runtime refers to it in a later turn the client caused. A cold continuation on the Messages API takes its history from the client, so it lacks such a turn.
- **A client request can wait for another turn.** Under O3, on a runtime that does not declare `steer`, a client request that arrives during a turn another session's message caused waits for that turn's `response`, and a non-streaming client's timeout bounds the wait.
- **Retraction is not recall.** A retraction succeeds only before delivery. A message a recipient received, a client tool call a provider-surface client holds, and output already streamed stay where they are, and the runtime receives `too_late`. A REST or MCP client that already started a retracted call's tool learns of the retraction only from the event, and the tool's side effects stand.
- **Output is not retracted.** Under S8, retraction of output and session events is ignored for now ("MD-11", "Blast radius").
- **Activity is the runtime's claim.** The gateway cannot check that an activity describes what the runtime does, so nothing that decides policy, audit, or billing reads it.
- **A pod loss loses unended activity.** Open activities end `cancelled` with `runtime_exit`, and the restored runtime starts its own.
- **Interceptors cost streaming.** A session with a `PostAgentOutput` interceptor receives each part once, completed (A5).
- **Harness approvals are not enforced.** The harness runs the tool, and Lenny relays the decision ("MD-19"). A Basic runtime has no platform MCP server, so it cannot call `lenny/request_approval`.
- **Runtime-reported usage needs Full level.** `llm_request_completed` travels on `CH-RUNTIMEOPS`, so a Basic or Standard runtime that calls a provider directly reports no usage.
- **Files changed during an export without a clone.** On a pool without reflink clones, which includes every sandboxed and microvm pool, a file the runtime changes while the adapter reads it ends the part `failed` with `file_changed`, and the runtime has to emit it again ("MD-18"). The check sees only changes to the file's identity. A write through a memory mapping that the kernel has not yet written back changes no identity field, so the stored copy can hold a mix of old and new bytes, and its whole-file SHA-256 matches that copy (MDR-29).
- **Symlinks in an exported path.** The adapter refuses a path with a symlink in any component, including one whose target lies inside the workspace, so a runtime exports the file by its real path ("MD-18", "Freeze").
- **Exports share the checkpoint grant window.** A large export slows the pre-copy and upload passes of a concurrent checkpoint of the same session, which keeps the S5 bound (A12). During a checkpoint's capture pass the export's reading, hashing, and compression wait (A17).
- **Large files on a reflink pool are not cloned.** On a reflink pool, a file larger than the remaining export share of the spool, 256 MiB at the default `checkpointCaptureBudgetBytes` of 512 MiB, is read in place with the identity check and is not cloned, and the clones of parts waiting for the export cap also count against the share. Such a file ends `file_changed` when the runtime changes it during the read, as on a pool without clones (A21).
- **Exports have a deadline.** An export that does not reach `ExportReady` within `exportTimeoutSeconds` of its `ExportStart` fails, a part that waits for the export cap fails after `exportTimeoutSeconds` from its first frame, a session runs at most `files.maxConcurrentExports` exports at once, and its queue holds at most `files.maxQueuedExports` parts, so a large file on a slow pool has to be split or exported from a pool with a longer deadline.
- **Exports end with the seal window.** At session end an export gets the time the seal checkpoint leaves in the session's seal window, 300 seconds by default and at most the ceiling of 600, and the whole window under `checkpointPolicy: none`. An export still running when the window ends fails with `seal_timeout`, so a runtime that emits a large file shortly before the session ends can lose it. A runtime that needs more time sets a longer `maxWorkspaceSealDurationSeconds` within the ceiling (A19).
- **Some exported bytes upload apart from the seal.** The seal uploads an exported file's chunks once, with three exceptions. A file that the runtime changed or deleted after it emitted the part is exported from its clone, whose chunks the seal snapshot does not hold. An export pack whose grant is outstanding when the seal starts is not yet confirmed, so the seal may upload its chunks again, at most one grant window of packs. Under `checkpointPolicy: none`, no seal snapshot stores any chunk (A19).
- **The whole-file hash is not a defence.** The gateway compares the whole-file SHA-256 only on a `PostAgentOutput` scanner's read. A compromised pod writes both the chunk list and the hash, so the hash detects no tampering by the pod, and S4's per-chunk check is the storage-integrity guarantee (A20).
- **Failure notices need an acknowledgement.** A runtime that does not use the SDKs and never writes `output_failed_ack` receives each notice again after every resume until the session ends.
- **The grant window grows with the pack format.** S5's bound rises from 4 × 16 MiB today to 4 × 32 MiB by default, and to 8 × 32 MiB on a pool that sets the largest override (A13, A14).

## Alternatives rejected

- **A steer special case.** A boolean `steer` beside `immediate` and `queued` would leave queueing, interruption, and later intents as separate rules. The owner directed a general per-message model.
- **Steer by default for every runtime.** A runtime that does not read its input mid-turn would receive messages its SDK queues, which matches `queue` while reporting `delivered`, and a Basic runtime that reads one message per turn would gain nothing.
- **Delivering mid-turn to every runtime between tool calls.** The adapter cannot observe tool calls inside a runtime's own process, and §29.3 records that no frame carries the signal.
- **One `response` per `message`, with steered messages folded into the next `response`.** A runtime that consumes several messages in one turn would owe several `response` frames, and output with no causing message would still be discarded.
- **A send call that waits for the consuming turn.** A REST caller would wait for a turn that may run many minutes, and an agent's `lenny/send_message` would block its own model loop. The event stream carries the outcome.
- **Holding inbox deliveries to a provider-surface session until the next client turn.** Revision 1 recommended it, so that a delivery would join work a client is waiting for. A message to an idle held session then waited for the client's next request or its TTL, and every provider surface needed a hold of its own. Delivery on arrival with the two rules of "MD-8" keeps the turn away from the client with no surface-specific hold (O3).
- **Custody until a checkpoint records the consumption.** Revision 1 recommended it, so that a restored runtime would receive again a message it consumed after its checkpoint. The redelivery can repeat side effects that the checkpoint does not undo, and a runtime that never checkpoints would keep every consumed message in the inbox until the session ends. The `consumed_unrecorded` report leaves the choice to resend with the sender (O4).
- **Gateway-side ordering of steered messages into model history.** The gateway does not see the runtime's model requests, and only the runtime knows where its model steps fall.
- **Activity as a flag on `output`.** Every consumer of `output` would have to check the flag: the transcript, cold history, the provider adapters, `TaskRecord`, and `PostAgentOutput`. A consumer that missed it would put display state into a model's history.
- **A closed list of activity kinds.** The owner asked for an open `kind` governed by conventions, so a runtime can report what its harness reports without a Lenny release.
- **Transient activity with no current state.** A client that attaches mid-turn would see nothing until the next update, and the short replay buffers would lose the rest.
- **Every activity update in the transcript.** A test run can produce thousands of updates, which would push other events out of the replay buffers and grow the transcript. The runtime chooses what to record, and only final states are recorded (A2).
- **Blob references for large activity.** The owner decided that activity frames are not stored as files (A10). A large result is a file part.
- **Files through stdout.** A stdout line is limited to 50 MiB, base64 grows binary content by a third, and a large file would hold every later frame of the runtime behind it (A11).
- **Files through the gateway.** Streaming the bytes through the gateway would let an interceptor scan them in flight, at the cost of gateway bandwidth for every file. The owner chose the direct upload (A11a), and an interceptor reads the stored object through `ref`.
- **One `PUT` per file.** Revision 3 proposed it. A grant of up to 5 GiB breaks the incremental checkpoint design's S5 bound of `checkpointGrantWindow × packMaxBytes`, a file over 5 GiB would need the multipart capability R5 withholds, a failed upload would start again from nothing, and content a checkpoint already stored would be uploaded again (A12).
- **A grant window of its own for exports.** It would keep exports from slowing checkpoint uploads and double the bytes a compromised pod can write at once (A12).
- **Removing the per-pool grant window override.** It would make S5's bound one constant, at the cost of a setting the tree already carries on `SandboxTemplate`. A maximum of 8 keeps the bound stated (A13).
- **Path checks by resolved path, as `ExportPaths` does.** A check on a resolved path followed by a read by path leaves a window in which the runtime can swap a component for a symlink. Opening beneath a directory descriptor and reading the descriptor that was checked closes it ("MD-18", "Freeze").
- **Pack IDs from content alone.** Revision 5 named a pack by the SHA-256 of bytes that the adapter's input determined, so a pack the adapter rebuilt had the ID of the pack it rebuilt, and S1 had to either refuse a rebuilt pack whose key the catalog held or answer it from rows outside the allowed set. The pack nonce makes every pack distinct, so a rebuilt file gets new pack IDs and new grants, and the "already stored" answer is left for a resend (A18).
- **Narrowing S1 and reviving soft-deleted pack rows.** A rebuilt pack whose row was soft-deleted would be revived and leased again in place of a new upload. A soft-deleted row keeps its key for `gc.tombstoneRetentionSeconds` while the object delete or the §12.5 backstop sweep is still pending, so the object behind a revived row can be deleted after the fact, and a snapshot or an output file would reference a missing pack (A18).
- **Waiting for exports up to `exportTimeoutSeconds` at the seal.** Revision 5 did so. The wait could reach 900 seconds past the seal window, which §7.1's terminal pipeline budget did not cover, and neither an operator nor a runtime could shorten it. Exports now end inside the seal window (A19).
- **A separate export wait after the seal checkpoint.** Revision 6 first gave exports still running after the seal checkpoint their own wait, the runtime field `files.sealExportWaitSeconds`, 120 seconds by default under a ceiling of 900 seconds, as A19 first recorded. An exported file lies in the workspace, which the seal checkpoint captures whole, and the seal and the exports share one dedup set, so the seal stores the file's chunks and an export that continues after it only finishes its bookkeeping. A wait beyond the seal window would therefore cover no transfer the seal does not already make, while it raised the terminal pipeline budget to 1230 seconds at the defaults and the claim orphan timeout to 1260 seconds. The owner replaced it on 2026-11-10 (A19).
- **Verifying the whole-file SHA-256 on the first full read.** Revision 5 did so, with a `checksum_mismatch` failure that deleted the file. S4's per-chunk check already detects corrupt or substituted storage, a compromised pod writes the hash it is checked against, and the check added a deletion path for held material. Publishing the hash lets a client verify end to end (A20).
- **An AG-UI endpoint in v1.** AG-UI is run-based and re-sends state on each run, while Lenny is session-based, and it would be a fourth client surface (G3).

Further observations bear on this design and are recorded for the specification owner without filing:

- The durable inbox's "Explicit ACK" row requires the adapter to keep a `delivered_message_ids` set in checkpoint state. No code in `pkg/adapter` keeps one, and `lenny_inbox_duplicate_suppressed_total` has a catalog entry and no producer. "MD-3" replaces the set with the consumed set.

- The REST message response returns the turn's `output` synchronously, which the Go client SDK reads. "MD-7" removes it.
- The §5.1 "Standalone Runtime" example declares `interaction: one_shot` with `injection.modes`, although a `one_shot` runtime consumes one message.
- The activity proposal of 2026-11-10 assumed a built-in scrubber of leased credentials on output. No such scrubber exists for output, so activity relies on `PostAgentActivity` interceptors as output relies on `PostAgentOutput`.
