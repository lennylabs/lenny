## Problem

A runtime author needs to know where the runtime's working directory is, where to keep conversation state, where scratch space is, and which paths the platform owns. Today the answer depends on the session. [§6.4 Pod Filesystem Layout](../spec/06_warm-pod-model.md#64-pod-filesystem-layout) puts the working directory at `/workspace/slots/{sessionId}/current/`, session files at `/sessions/{sessionId}/`, and an artifacts tree at `/artifacts/{sessionId}/`, and it requires the runtime to derive its working directory from the session identifier **[source]**. The credential file sits at `/run/lenny/slots/{sessionId}/credentials.json` ([§13.1](../spec/13_security-model.md#131-pod-security)) **[source]**. Every one of these paths changes when a session's identifier changes, which happens on every derive.

Absolute paths are written into the workspace by the tools an agent runs. A Python virtual environment records its interpreter path in its scripts, CMake refuses a build directory whose cache names another source path, Bazel keys its output base on the workspace path, `compile_commands.json` lists absolute paths, and a git worktree records its location in its `.git` file **[inference]**. A derived session restores the source's workspace under a new identifier, so each of these breaks. A harness that keys its state by working directory, as Claude Code keys its project transcripts, finds no state after a derive **[inference]**.

[`session-isolation-design.md`](session-isolation-design.md) revision 3 gives each slot its own volumes and mounts each whole into one slot container ("SI-1"), so a slot sees only its own session's trees. With that, the session identifier in the path no longer separates anything: each slot container has one session at a time. Revision 3 kept the old paths so that runtimes would derive their working directory unchanged, and it had to defend the session directory against renames because the volume root is writable by the slot **[source]**.

A second structure sits beside the sidecar pod. The embedded deployment model of [§4.7.10 Deployment Model](../spec/04_system-components.md#4710-deployment-model) runs a first-party runtime inside the adapter's own process, in one container, with no runtime supervisor **[source]**. That process holds the adapter's gateway service-account token and its gateway credentials, and it runs at the agent UID **[source]**. Every design that touches the pod carries a separate row for it: the egress design's identity exception, the peer-check exception of [§4.7.11](../spec/04_system-components.md#4711-adapter-agent-security-boundary) item 1, the `SIGSTOP` checkpoint path, the in-process broker of IC revision 13, and the supervisor refusals of the derive and derived-runtime designs **[source]**. Its name also collides with Embedded Mode, the `lenny up` local stack of [§17.4](../spec/17_deployment-topology.md#174-local-development-mode-lenny-dev), which is an unrelated feature **[source]**.

A third structure starts a runtime before it has a session. A runtime that declares `capabilities.preConnect: true` is launched at warm-up, is pointed at its workspace when a session binds, and is torn down through `DemoteSDK` when the session's files would change what it read at start ([§6.1 What a Pre-Warmed Pod Looks Like](../spec/06_warm-pod-model.md#61-what-a-pre-warmed-pod-looks-like)) **[source]**. It adds a pod state, `sdk_connecting`, a watchdog, a per-runtime list of blocking paths, a demotion circuit breaker with an admin override, and a second meaning of "warm pod" **[source]**.

The pool fields that size a pod also carry names that no longer say what they count: `sessionPolicy.maxConcurrentSessions` counts sessions on one pod at once, beside `recycle.maxSessionsPerPod`, which counts them over the pod's life, and `acknowledgeProcessLevelIsolation` acknowledges sharing that is no longer process-level under slot containers **[source]**.

The owner decided on 2026-11-12 to remove the embedded deployment model and the pre-launched runtimes, to give the runtime the same paths on every pod at every slot count, to rename the pool fields, and to move the pod blueprint and the layout into this design.

## Scope

In scope:

- The containers of an agent pod, the only kind of pod a runtime runs on since AR removed `type: mcp` runtimes and service mode ("PL-1").
- The removal of the embedded deployment model and of everything that exists only for it ("PL-2").
- The runtime-visible filesystem layout, the reserved `/lenny` root, and the adapter's own paths ("PL-3").
- The removal of `/artifacts`, and the rule for files a runtime offers to the user ("PL-4").
- The volumes of a pod, their medium, size limit, owner, and mounts, and the eviction behaviour ("PL-5").
- The runtime-facing environment and the contract a runtime author relies on ("PL-6").
- What the layout gains ("PL-7").
- The removal of pre-launched runtimes from the pod and the pool: the warm pod's meaning, the launch at bind, the pod state, and the pool controls that existed for them ("PL-8"). The capability itself leaves under [`runtime-protocol-design.md`](runtime-protocol-design.md) decision D6.
- The pool settings that size a pod's volumes, and the renames of `acknowledgeSharedPod` and `maxConcurrentSessionsPerPod` ("PL-9").
- Project quotas on slot volumes: the node agent `lenny-quota-agent` that detects and assigns them, and the adapter's use of them in the disk watch ("PL-10"). [`placement-design.md`](placement-design.md) places the agent as a named node agent and admits it.

Non-goals:

- Slot UIDs, socket names, the file-descriptor broker, the supervisor's worker protocol, the slot release, liveness, and resources. [`session-isolation-design.md`](session-isolation-design.md) keeps them.
- Node placement, node classes, the placement fields a pod renders, and the user namespace requirement on runc pools. [`placement-design.md`](placement-design.md) owns them, and [`session-isolation-design.md`](session-isolation-design.md) states what user namespaces give slot isolation.
- What is written into the workspace and by whom: the `lenny-materialize` helper, the setup protocol with descriptors, archive extraction, the git steps of SI O11, the warm-up checkout and its reflink rebuild, fetch grants, and the order of restore and overlay. [`workspace-materialization-design.md`](workspace-materialization-design.md) owns them. This design states only the names they reserve and the volumes they use.
- Checkpoint capture, storage, and restore. [`incremental-checkpoint-design.md`](incremental-checkpoint-design.md) owns them, and this design states only which paths a checkpoint covers.
- Embedded Mode, the `lenny up` local stack. It stays, and only its echo seed changes ("PL-2").
- `netagent`'s volumes and files, which [`egress-and-git-design.md`](egress-and-git-design.md) owns. This design lists them so the blueprint is complete.

## Terms

| Term | Meaning |
| :-- | :-- |
| Runtime-visible path | A path that the runtime process, its children, and setup commands see inside a slot container. "PL-3" lists every one. |
| Workspace volume | The per-slot volume `slot-<n>-workspace`, mounted directly at `/workspace` in slot container `n`. It is the session's working tree. |
| Session volume | The per-slot volume `slot-<n>-session`, mounted at `/session`. It holds the runtime's private per-session state, such as harness transcripts and conversation state. |
| Reserved root | `/lenny`, a path the specification reserves for platform mounts in a slot container. A runtime image puts nothing under it. |
| Adapter view | The paths under `/adapter` at which the adapter container mounts slot volumes and its own volumes. No slot container sees them. |
| Embedded deployment model | The `deploymentModel: embedded` value of the `Runtime` resource, under which a first-party runtime links the adapter as a library and runs as the pod's only container ([§4.7.10](../spec/04_system-components.md#4710-deployment-model)). This design removes it. |
| Embedded Mode | The `lenny up` local stack of [§17.4](../spec/17_deployment-topology.md#174-local-development-mode-lenny-dev). It is unrelated to the embedded deployment model and stays. |
| Output file | A file that a runtime offers to the user by emitting a `file` part that names a workspace path ([MD-18](message-delivery-design.md#md-18-files)). |
| Per-slot disk watch | The adapter's check of each slot volume's use, which fails the slot's session and runs the slot release at `adapter.diskWatchThresholdPercent` of the volume's `sizeLimit`, 90% by default ([SI-10](session-isolation-design.md#si-10-what-stays-shared)). It reads `fstatfs` on a volume that a project quota bounds ("PL-10") and where the runtime reports the volume, keeps a running total from the change tracker where the tracker runs, and walks the volume elsewhere (O8, "PL-5"). |
| Project quota | A limit and a usage count that an XFS or ext4 filesystem mounted with `prjquota` keeps for every inode carrying one project ID. A write past the hard limit fails with `ENOSPC` or `EDQUOT`, and `statfs` on a directory of the project reports the limit and the usage ("PL-10") **[measured]**. |
| `lenny-quota-agent` | The node agent that detects project quotas on its node, labels the node `lenny.dev/project-quota`, and assigns a project and a hard limit slightly below `sizeLimit` to each slot volume that quotas can bound (D25, "PL-10"). It runs as a DaemonSet in `lenny-node-agents` with `CAP_SYS_ADMIN` and a `hostPath` of the kubelet's `pods` directory, is not privileged, and runs under its own seccomp profile and a Landlock restriction (D28). |
| Reserved name | A name at the top of `/workspace` that the platform uses for its own transient work and that a runtime does not create: `.lenny-canary`, `.lenny-build`, `.lenny-prestage`, `.lenny-overlay-<id>`, and `.lenny-discard-<id>` ("PL-3"). Checkpoints, downloads, and exports skip them. |
| Warm pod | A pod whose infrastructure is ready: its containers run, its slot supervisors have answered, its shared volumes are filled, and its warm-up checkouts are staged. No runtime process runs in it before a session binds ("PL-8"). |
| Shared pod | A pod that can serve more than one session at the same time: a pod with `sessionPolicy.maxConcurrentSessionsPerPod` above 1. [`placement-design.md`, "PM-4"](placement-design.md#pm-4-placement-requirements) defines the `sharedPod` field that reports it. |
| `acknowledgeSharedPod` | The pool's `sessionPolicy` field, renamed from `acknowledgeProcessLevelIsolation`, that a deployer sets to `true` to run a pool with `maxConcurrentSessionsPerPod` above 1 ("PL-9"). |
| Pod Security Standards Restricted | The Kubernetes Pod Security Standards profile named Restricted, which every agent-pod namespace enforces. This design writes the full name so that it is not read as a data class: the data classes are Public, Internal, Confidential, and Secret ([`tenant-security-settings-design.md`, "TSS-8"](tenant-security-settings-design.md#tss-8-data-classes)). |
| Kata block-plain | A Kata pool whose node runtime presents each disk-backed `emptyDir` to the guest as its own ext4 block device, so every disk-backed volume root starts as `root:root` `0755` with a `lost+found` directory **[measured]**. The deployer states the mode in the chart value `kata.emptyDirMode` ("PL-5"). |

## High-level design

Every agent pod has the same containers. The adapter runs in its own container. `netagent` runs beside it where the egress design renders it: a pool whose `egressProfile` is `internet` bypasses `netagent`, and the egress design decides whether its pods run one. Each slot has its own container, which starts the runtime supervisor as its first process, and the supervisor starts a fresh runtime process for each session, when the session binds. A pod with one slot has one slot container. Init containers stage the platform's binaries before anything else starts, and a separate init container, `lenny-store-fill`, then fills the warm repository stores under its own UID, holding no credential, so no container that holds a platform credential parses repository data. No other arrangement exists: the embedded deployment model, under which a runtime ran inside the adapter's process, is removed, and the first-party echo runtime that used it becomes an ordinary runtime that declares a `command` and uses the Go SDK. `type: mcp` runtimes and service mode are removed as well, so every runtime runs on this pod, and every runtime container is a slot container with the broker and the release Sweep.

A warm pod is a pod whose infrastructure is ready. No runtime process runs on it before a session binds: the supervisor launches the runtime after the session's workspace is materialized and its setup commands have run. The pre-launched runtimes of `capabilities.preConnect`, with their demotion path, their pod state, and their pool controls, are removed.

Inside a slot container a runtime sees the same paths on every pod, whatever the pool's slot count and whatever the session. `/workspace` is the session's working tree and the runtime's working directory. It is the workspace volume itself, so nothing sits between the volume root and the working tree, and no path carries the session's identifier. `/session` holds the runtime's private state for the session, such as harness transcripts, and is checkpointed together with the workspace but kept out of the working tree and out of workspace downloads. `/tmp` is private scratch space on disk, and `HOME` is `/tmp/home`. `/dev/shm` is private to the slot. Under `/lenny` the platform mounts read-only content: the runtime's shared assets, the warm repository stores, and its own binaries. `/run/lenny` holds the manifest and the session's credentials. Runtime images put nothing under `/lenny`, `/workspace`, or `/session`, because the mounts hide whatever is there. A few names at the top of `/workspace` belong to the platform's transient work, such as the warm-up checkouts that wait there for the next session.

The adapter mounts each slot's volumes under `/adapter/slots/<n>/`, and its own spool under `/adapter/spool`, so no adapter path can be mistaken for a runtime path.

`/artifacts` is removed. The adapter created and deleted a directory there for every session, and nothing else wrote, captured, or served it. A file reaches the user when the runtime emits a `file` part that names it, which the message-delivery design already specifies.

Each disk-backed volume carries a size limit, which a pool setting sets, and the pod requests ephemeral storage equal to their sum plus its resource class's own request, 1 GiB in the shipped classes, for the containers' writable layers and logs. The kubelet evicts the whole pod when any one of them exceeds its limit, so the adapter watches each slot's volumes and fails that slot's session at 90% of a limit by default, before the kubelet acts. It reads a volume's use from `statfs` where a project quota bounds the volume or the runtime reports it, keeps a running total from the checkpoint's change tracker where the tracker runs, and walks the volume through the slot's broker every 10 s elsewhere. Where the node's filesystem has project quotas, a node agent gives each slot volume of runc pods with user namespaces, of Kata virtio-fs pods, and gVisor's `/tmp` a quota slightly below its size limit, so the slot's own writes fail before the kubelet evicts the pod, and the adapter reads the volume's use in one call.

The spool is one volume for the pod, with a generous configurable size. Each slot's checkpoint room is reserved in it, and the slots share the rest for staging uploads.

The pool fields that size a pod take names that say what they count. `sessionPolicy.maxConcurrentSessionsPerPod` is the number of sessions one pod serves at once and the number of slot containers it renders. `acknowledgeSharedPod` is the deployer's acknowledgment that such a pod's slots still share some resources, and its validation error lists them.

Where the kernel lacks Landlock the agent refuses to start, labels nothing, and raises its alert, unless the chart value `quotaAgent.requireLandlock`, `true` by default, is `false`. The orchestrator chose that default, the profile's delivery through the `seccomp-install` init container, and the admission rule that refuses an agent pod without the profile, and the owner confirmed them later on 2026-11-14 ("2. ok"). The same answers confirmed the agent's placement and rights ("Ok on the rest"). | The owner's message of 2026-11-14 | PL-10, PLR-24, "Limits", "Validation owed", "Non-specification changes", "Tests" |
| D29 | How the quota agent's figures reach monitoring (2026-11-15). | Revision 13 had the agent serve one metrics port, `quotaAgent.metricsPort`, open to the monitoring scraper alone, for the owner's review. The owner asked for an elaboration and answered "3: ok" to the alternative: the agent serves no port and writes its figures, the volumes it bound, its assignment errors, its Landlock state, and its detection result, as the annotation `lenny.dev/quota-agent-status` on its own node, which the admission policy allows beside the `lenny.dev/project-quota` label and nothing else; `lenny-ops` exports them as metrics and raises `QuotaAgentUnavailable`. `quotaAgent.metricsPort`, the NetworkPolicy ingress, the seccomp profile's listening calls, and the Landlock TCP rule leave. | The owner's message of 2026-11-15, item 3 | PL-10, PLR-24, "Specification changes", "Non-specification changes", "Documentation", "Tests", "Validation owed" |

## Open decisions

The owner settled O1 to O7 on 2026-11-12 by accepting each recommendation, with refinements to O4 and O7 (D5), and O8 on 2026-11-13 in a revised form (D12). Egress decision 61 superseded O5 on 2026-11-13 (D11). The owner settled O9 on 2026-11-13 as (a) (D20), and the spike it asked for led to D25 on 2026-11-14. O10, which that spike raised, was settled on 2026-11-14 as (a) (D26). Each settled decision keeps its options and reasoning as the record of the choice.

**O1. How the runtime learns its paths. Settled.**

- (a) Fixed constants that the specification states, with the supervisor starting each runtime process in `/workspace`.
- (b) Environment variables, such as `LENNY_WORKSPACE_DIR` and `LENNY_SESSION_DIR`, set at launch.
- (c) Manifest fields in `/run/lenny/adapter-manifest.json`.
- (d) Constants, plus environment variables that repeat them for discoverability.

**Settled 2026-11-12: (a).** Variables and manifest fields exist so that a value can differ between pods, and these values never differ. A runtime author sets harness variables in the Runtime's `env`, such as `CLAUDE_CONFIG_DIR=/session/claude`, and `env` holds literal values with no expansion ([§5.1](../spec/05_runtime-registry-and-pool-model.md#51-runtime), **`env`**) **[source]**, so a constant is the only value it can use there. Variables in (b) and (d) invite code that reads them, which then cannot be tested against a second value, and they add a source that can disagree with the mount table. `session_start` keeps `sessionId` as data, `credentialsPath` keeps its field with the constant value `/run/lenny/credentials.json` so that its presence still says whether a credential file exists, and DR-12's `cwd` keeps naming the session's working folder under `/workspace`.

**O2. The rule for files a runtime offers to the user. Settled.**

[§26.2](../spec/26_reference-runtime-catalog.md#262-shared-patterns-for-coding-agent-runtimes) states that `/workspace/output/` "is provided for agents to write artifacts that should survive session teardown and be recoverable via `GET /v1/sessions/{id}/artifacts`" and that "Agents MUST write intended outputs here", and §26.3 says files under it "are sealed as session artifacts" **[source]**. Nothing in the tree implements either, the directory was a sibling of `/workspace/slots/` that no mount provided, and `GET /v1/sessions/{id}/artifacts` lists catalog rows and reads nothing from the pod ([`message-delivery-design.md`, "Current state"](message-delivery-design.md#tree)) **[source]**. MD-18 exports a file when the runtime emits a `file` part that names its workspace path **[source]**.

- (a) One rule: a file reaches the user as an output file only when the runtime emits a `file` part naming it. The platform defines no output directory. A runtime may keep its own `output/` folder, and it emits a part for each file in it. The whole workspace stays downloadable through `GET /v1/sessions/{id}/workspace`.
- (b) Keep `/workspace/output/` as a platform directory, and have the adapter export every file in it as an output file at session end.
- (c) Both.

**Settled 2026-11-12: (a).** MD-18 already covers every path in the workspace, with its size limit, export cap, freeze, and failure notice, and it lets a runtime offer a file mid-session. Under (b) the seal would export files the runtime never announced, outside MD-18's per-part accounting, and a directory under `/workspace` would be a platform convention nested in a tree that D2 says the platform leaves empty. The reference runtimes adopt (a) in their wrappers.

**O3. The medium of `/tmp`. Settled.**

- (a) Memory-backed, as today, with a `sizeLimit` of 256Mi. The kubelet sizes a memory-backed `emptyDir` to its `sizeLimit`, so a write past it fails with `ENOSPC` rather than evicting the pod **[inference]**. Its pages count against the slot container's hard memory limit (SI O4 (a)).
- (b) Disk-backed with its own `sizeLimit`, inside the per-slot disk watch.

**Settled 2026-11-12: (b).** `HOME` points into `/tmp` under O4, and `HOME` collects package caches for npm, pip, Go modules, and Cargo, which can exceed 256Mi. Under (a) those caches consume the slot's memory, and an out-of-memory kill makes the slot dead for the pod's life ([SI-4](session-isolation-design.md#si-4-slot-liveness-and-the-slot-count)). Under (b) an overflow is caught by the same disk watch that already guards `/workspace` and `/session`. The cost of (b) is that a write burst that outruns the watch evicts the whole pod, which the watch already risks for `/workspace`, and that scratch data reaches the node disk, which node-level disk encryption covers as it covers `/workspace` ([§6.4](../spec/06_warm-pod-model.md#64-pod-filesystem-layout), **Data-at-rest protection:**).

**O4. `HOME`. Settled.**

The supervisor starts each launch from an empty environment with a fixed `PATH`, the Runtime's `env`, and the platform's variables, so `HOME` is unset today, and the root filesystem is read-only **[source]**. A tool that writes under `~` therefore fails or writes into a read-only image path.

- (a) The supervisor sets `HOME=/tmp` as a platform variable, and a `HOME` pair in the Runtime's `env` replaces it, as an `env` `PATH` pair replaces the fixed `PATH`.
- (b) `HOME` stays unset, and each runtime sets it in `env`.
- (c) A separate `/home` volume.

**Settled 2026-11-12: (a), with `HOME=/tmp/home`.** The owner's refinement: "HOME=/tmp/home, created by the supervisor, owned by the slot UID, and mode 0700. The runtime `env` can override it. Harness state goes to /session." A home directory of its own, rather than `/tmp` itself, keeps dotfiles and caches out of the scratch directory that other tools list and clean, and mode `0700` matches what tools such as `ssh` require of a home. It gives every tool a writable home that the slot release sweeps and no checkpoint carries, which is where package caches belong. (b) leaves each runtime author to find the same answer. (c) adds a path outside D2's list.

**O5. Who fills the repository stores. Settled.**

[SI-1](session-isolation-design.md#si-1-pod-layout) lists "the warm-clone fill, the init step that fills `lenny-warm-clones` before any regular container starts, as spike 2 ran it" **[source]**. DR-11 has the adapter fill each store before the pod reports ready, through `netagent`, and has the adapter delete a withheld store before anything runs for a session ([`tenant-derived-runtimes-design.md`, "Warm stores"](tenant-derived-runtimes-design.md#warm-stores)) **[source]**.

- (a) The adapter fills the stores, as DR-11 states, on `lenny-git-stores` mounted read-write at `/adapter/git-stores`, running the pinned git from `lenny-bin` mounted read-only at `/adapter/bin`.
- (b) An init container fills the stores under its own UID, as SI-1 states.

**Settled 2026-11-12: (a).** Under (b) the stores' files and directories belong to the init container's UID, which no running container holds, so the adapter cannot delete a withheld store, and §13.1 reserves the adapter UID for the container named `adapter` ([§13.1](../spec/13_security-model.md#131-pod-security), **Container identity.**) **[source]**. A bare store records no absolute path, so it serves alternates at `/lenny/git-stores` in the slots although the adapter wrote it at `/adapter/git-stores` **[inference]**. SI O11 forbids the adapter git work on slot repositories, and the fill works on stores, which no slot can write.

**Superseded 2026-11-13 by D11.** The egress design's decision 61 found that the fill parses untrusted git input at the adapter UID, against the materialization design's rule that no platform-privileged process parses untrusted content, and the owner chose a separate `lenny-store-fill` container. The reason (b) was rejected, that no running container could delete a withheld store, is answered by the adapter's read-write mount, which it uses only to delete: `lenny-store-fill` writes with a dedicated store GID as its group and group-writable directories, and the adapter, whose primary group is the same GID, can unlink what the fill wrote ("PL-3", D17).

**O6. Where the new size limits are set. Settled.**

- (a) Pool settings beside `workspaceSizeLimitBytes`: `sessionSizeLimitBytes`, 256Mi by default, and `tmpSizeLimitBytes`, 1Gi by default under O3 (b).
- (b) Chart values for every pool.

**Settled 2026-11-12: (a).** `workspaceSizeLimitBytes` is a pool setting today ([§4.4.4](../spec/04_system-components.md#444-checkpoint-slos-and-scheduling), **Hard workspace size limit.**) **[source]**, and a harness's transcript size and a toolchain's cache size vary with the runtime that the pool serves. The 256Mi default keeps today's cap for session files ([§6.4](../spec/06_warm-pod-model.md#64-pod-filesystem-layout)). O7's `shmSizeLimitBytes` joins them, and "PL-9" lists the three settings.

**Changed 2026-11-14 (D27).** The owner raised the default of `sessionSizeLimitBytes` to 1 GiB, after asking whether the defaults should rise because storage is relatively cheap. The 256Mi of (a) is the earlier default.

**O7. `/dev/shm` per slot. Settled.**

The pod renders one memory-backed `dshm` volume of 64Mi at `/dev/shm`, mounted into the adapter and the runtime container (`pkg/controller/sandbox/podspec/volumes.go`) **[source]**. SI-10 measured that a slot read another slot's `0666` file in `/dev/shm`, in pods built for that spike **[measured]**.

- (a) One `slot-<n>-dshm` volume per slot, mounted only into its slot container, and none in the adapter.
- (b) One volume for the pod, mounted into every slot container.

**Settled 2026-11-12: (a), with a pool setting for its size.** The owner added "a pool setting for the per-slot /dev/shm size (for example `shmSizeLimitBytes`, default 64Mi), counted in slot memory." POSIX shared memory objects are files on the filesystem at `/dev/shm`, so a per-slot volume makes them private to the slot, while System V objects and POSIX message queues stay shared through the pod's IPC namespace **[inference]**. The adapter has no use for the runtime's shared memory. SI-10's IPC paragraph then narrows to System V objects and message queues. The AWS run of 2026-11-12 still shared one `/dev/shm` between slots, because its pods used the earlier layout **[measured]**, so the per-slot volume is owed validation. "PL-9" states the setting.

**O8. How the per-slot disk watch measures a volume. Settled 2026-11-13 in a revised form (D12).**

On runc, `statfs` on an `emptyDir` reports the whole node filesystem **[measured]**, so the watch cannot read a volume's use from the filesystem. The kubelet counts a volume by walking it, and it counts a reflink clone at its full size **[measured]**. The adapter's own mount cannot descend into a slot-owned directory of mode `0700`, and it does not mount `/tmp` at all.

- (a) A walk through the slot's broker: the adapter walks each watched volume as the checkpoint walks a workspace, listing directories and statting entries in parallel through broker-passed directory descriptors, with the broker's `statat` as the fallback on `EACCES` ([IC-1](incremental-checkpoint-design.md#ic-1-capture-in-passes), "The walk"). It counts each inode once, at the larger of its logical size rounded up to 4,096 bytes and its allocated blocks, so its figure is never below the kubelet's. The broker gains a `tmp` root for this walk alone.
- (b) Project quotas where the node filesystem has them: the kubelet then assigns each `emptyDir` a project and reads its use from the quota, and the adapter would read the same figure.
- (c) (a) on every pod, and (b) in its place where a node offers project quotas the adapter can read.

**Recommendation of revision 2: (a) for the first release, with (c) as a refinement once validated.** (a) works on every runtime and every node filesystem with machinery the checkpoint already has, and it counts reflink clones as the kubelet does. Its cost is a walk per interval: the pstat walk measured 0.5 µs per entry on runc, 1.0 µs on Kata block-plain, 3.1 µs on gVisor's pod-share mount, 9.8 µs on gVisor's default mount, and 12.7 µs on Kata virtio-fs **[measured]**, so a 200,000-entry workspace costs about 0.1 s on runc and about 2.6 s on Kata virtio-fs per pass. A writer faster than the interval can still pass the kubelet's limit between two passes, which "Limits" states. Whether a pod can read its own project quota without a privilege the adapter does not hold is unverified.

The owner asked whether free space can be read without walking. The answer, by runtime: `statfs` reports the volume under gVisor's pod-share mount **[measured]**, and should under Kata `block-plain`, where each volume is its own ext4 device in the guest **[inference]**; elsewhere `statfs` reports the node filesystem, but the change tracker already reports every path that changes, so a running total can follow the writes between walks. The revised option:

- (d) `statfs` where it reports the volume; a running total kept from the change tracker's events where the tracker runs, with a periodic recalibration walk; a walk every 10 s only where neither applies; and project quotas as a later refinement.

**Settled 2026-11-13: (d)** (D12). It reacts to a write within the tracker's event latency where the tracker runs, and costs one `statfs` call where the runtime reports the volume, so the full walk's cost falls only on the volumes neither covers. `statfs` on Kata `block-plain` is owed to validation, and the watch walks there until it is measured. "PL-5" states the mechanism.

**Measured 2026-11-14.** On Kata `block-plain` the guest's `statfs` tracks each volume's usage exactly, bytes under a mode-`000` directory included, and reports the node filesystem's size rather than a limit **[measured]**, so method 1 of "PL-5" applies there for usage. O10 states the gap between that figure and the kubelet's. Project quotas, the later refinement of (d), are adopted under D25 ("PL-10").

**O9. How the disk watch treats a directory whose owner cannot list it. Settled 2026-11-13: (a) (D20).**

A session can write files into a directory and then set the directory's mode to deny its owner read, such as `0300` or `0000`. The walk lists a directory with `getdents` on a descriptor that the broker opens as the slot UID, and the broker's `statat` stats named entries only, so neither can enumerate such a directory **[inference]**. The watch's figure then misses the bytes beneath it, and a recalibration walk drops them from a running total, while the kubelet counts them and evicts the whole pod when the volume passes its `sizeLimit` **[inference]**. `statfs`, where the runtime reports the volume, counts them. A checkpoint records such a directory as `metadata_only` ([SI-6](session-isolation-design.md#si-6-checkpoint-restore-export-and-cleanup)), and the Sweep restores owner access before it descends at release.

- (a) Accept the miss as a residual risk of shared pods, stated in "Limits" here and in session isolation: one slot can evict the pod by this route. The mitigations are `statfs` where the runtime reports the volume, project quotas once validated, and on Kata `block-plain` the per-volume block device, whose size bounds the volume's writes **[inference]**. "Validation owed" measures the miss on each runtime.
- (b) Give the walk the Sweep's remedy: a new broker operation adds owner read and search to such a directory during the session, and the walk then lists it. It changes a live session's modes, which a runtime can observe, and adds an operation to the broker's closed set.
- (c) Fail the session when a walk meets a directory its owner cannot list on a volume the watch walks. It closes the route at the cost of failing a session that uses such a mode for another reason.

**Recommendation: (a).** The route harms only pods with several slots, which the deployer already acknowledges as sharing pod-wide eviction (`acknowledgeSharedPod`), and it needs a session that hides bytes on purpose. (b) widens the broker for a case the kubelet already bounds, and (c) fails sessions for a mode choice.

**Settled 2026-11-13: (a)** (D20). The miss is a stated residual risk of shared pods ("Limits"). The owner asked for a spike on how project quotas would be used where a node offers them, detected automatically, which "Validation owed" lists. The threshold is the chart value `adapter.diskWatchThresholdPercent`, 90 by default (D23).

**Spike and correction, 2026-11-14.** The spike measured that Kata `block-plain` backs each volume with a sparse `disk.img` sized to the node filesystem, 64 GB on its node, rather than to `sizeLimit` **[measured]**. The device's size therefore does not bound the volume's writes, and the guest's `statfs` reports the node filesystem's size, so it reports no limit, which corrects the inference of (a) above. The guest's `statfs` does count the bytes under a directory its owner cannot list **[measured]**, so the mitigation on Kata `block-plain` is that `statfs`, as on gVisor's pod-share mount. The owner adopted automatic project quotas (D25, "PL-10"), which count those bytes on runc with user namespaces, gVisor's default mount, and Kata virtio-fs. The residual risk remains on runc without user namespaces, on a node without project quotas or without a ready agent, and on a volume the agent reaches during a session, until that slot's next release.

**O10. The gap between the guest's figure and the kubelet's on Kata `block-plain`. Settled 2026-11-14: (a) (D26).**

The kubelet counts a Kata `block-plain` volume by the allocated blocks of its `disk.img`, which ran about 53 MiB above the guest's `statfs` figure at every step the spike measured: 117 MiB against 64 MiB, 167 MiB against 114 MiB, and 103 MiB against 50 MiB **[measured]**. The difference fits the ext4 metadata the guest writes into the image, which the guest's `statfs` leaves out **[inference]**. The watch's figure there therefore runs about 53 MiB below the kubelet's. At the defaults that is within the 10% margin of the 10 GiB workspace volume and the 1 GiB `/tmp`, and larger than the 25.6 MiB margin of the 256 MiB session volume, so a session volume can pass its `sizeLimit` in the kubelet's count before the watch trips.

- (a) The watch adds a fixed allowance on Kata `block-plain` pods, the chart value `kata.blockPlainOverheadBytes`, 64 MiB by default, to the guest's figure before it compares it with the threshold.
- (b) The controller adds the same allowance to the `sizeLimit` it renders for each disk-backed volume of a Kata `block-plain` pod, and to the pod's ephemeral-storage request, so the session keeps its full size.
- (c) State the gap as a limit of Kata `block-plain` and change nothing.

**Recommendation: (a).** It keeps the rendered limits and the bill unchanged and closes the gap with one constant, at the cost of 64 MiB of each `block-plain` volume. (b) raises every `block-plain` pod's request. Whether the overhead depends on the node filesystem's size, which sets the image's size, is owed to validation, and the allowance follows it.

**Settled 2026-11-14: (a).** The owner answered "ok" (D26). The watch adds `kata.blockPlainOverheadBytes`, 64 MiB by default, to the guest's figure on every disk-backed volume of a Kata `block-plain` pod before it compares the figure with the threshold, as "PL-5" states. The same day the session volume's default became 1 GiB (D27), whose 10% margin of 102.4 MiB also exceeds the measured gap, so at the defaults no volume depends on the allowance; the allowance still covers a pool that sets a smaller volume, and a volume whose kubelet overhead grows with the node filesystem.

## PL-1 Pod blueprint

**Agent pod.** A pod with slot count `N` has these containers, in start order **[design]**:

| Container | Kind | UID | Runs | Owner |
| :-- | :-- | :-- | :-- | :-- |
| `lenny-bin-stage` | Init container | A stage UID, neither the adapter's nor a slot's | Copies `lenny-supervisor`, `lenny-materialize`, and the pinned static `git` from the platform's digest-pinned images into `lenny-bin`, each with mode `0111`, and exits. It replaces `lenny-supervisor-stage`. | This design |
| `netagent` | Native sidecar, rendered where the egress design renders it | Its own | The egress and git endpoint. It scopes each slot's connections to that slot's session and writes each slot's `delivery: file` credentials to its `slot-<n>-netcred` volume. | [Egress design](egress-and-git-design.md) |
| `lenny-store-fill` | Init container, after `netagent` has started | Its own store-fill UID, with the store GID as its primary group (D17) | `lenny-store-fill`, a Lenny Go program from a digest-pinned platform image, which runs the pinned `git` from `/lenny/bin` to fill each store on the pod's warm list through `netagent` and to check out each store's pristine tree, and exits. It holds no service-account token and no gateway credential, and mounts only `lenny-git-stores` read-write, `lenny-bin` read-only, and `netagent`'s pod-wide volume read-only at `/run/netagent`, which holds the CA bundle, the git configuration, and the network descriptor that the egress design places there. `netagent` attributes its UID as the platform fill and applies the fill's authorization. | `adapter` | Regular | The adapter UID, with the store GID as its primary group (D17) | `lenny-adapter`. It talks to the gateway, fills `lenny-assets` before READY, deletes a withheld store and its pristine tree, and reaches slot files through each slot's broker. It runs no git and parses no repository data. | SI, this design for its mounts |
| `runtime-<n>`, for `n` from 0 to `N-1` | Regular | Slot `n`'s UID and GID | `/lenny/bin/lenny-supervisor run --socket @lenny-supervise-<n> ...` as PID 1, with `workingDir: /workspace`. | `keepalive` | Regular | Its own | Sleeps until SIGTERM, so a quarantined pod keeps its volumes. | [Forensics design](forensics-evidence-preservation-design.md) |

The image of each slot container is the runtime's `image`. The supervisor reads no file from it and ignores its `ENTRYPOINT`, `CMD`, and `ENV` ([§4.7.10](../spec/04_system-components.md#4710-deployment-model), **Runtime supervisor.**) **[source]**, so the image needs only the runtime's own files. Staging every platform binary mode `0111` makes each one non-dumpable from `execve`, as the materialization study measured for the helper **[measured]**. The supervisor then gains the same property, which keeps a runtime process under the same UID from reading the supervisor's descriptors through `/proc` **[inference]**. The supervisor already sits on the untrusted side of the boundary ([§4.7.11](../spec/04_system-components.md#4711-adapter-agent-security-boundary) item 8), so no requirement rests on this.

The reference MCP bridge ships with the runtime SDKs and in the runtime image, as [`runtime-protocol-design.md`](runtime-protocol-design.md#open-decisions) settled O4 (a), so `lenny-bin` holds no bridge and no `lenny-tools` init container exists.

**Every slot container runs the supervisor.** The supervisor is PID 1 of every slot container, and every runtime container is a slot container, because AR removed the service-mode and `type: mcp` pods that revision 2 rendered with their own runtime containers (D16). Every pod therefore has the broker, through which the adapter reaches the runtime's files as the slot UID, and the release Sweep, and no pod runs a runtime image's own entrypoint. The supervisor launches the Runtime's `command`, so `command` is required on every runtime (PLR-2).

**Pod-wide settings.** `shareProcessNamespace`, `hostPID`, `hostNetwork`, and `hostIPC` stay false. Every container keeps today's security context: non-root, every capability dropped, no privilege escalation, the RuntimeDefault seccomp profile, and a read-only root filesystem **[source]**. The namespace enforces Pod Security Standards Restricted. The pod sets no pod-level `supplementalGroups`, and it sets no `fsGroup` except on Kata block-plain ("PL-5", PLR-10).

**Placement fields.** The pod also carries the fields that [`placement-design.md`, "PM-5"](placement-design.md#pm-5-rendering) renders: `hostUsers`, the node class and tenant affinity, the tolerations, the priority class, and the `lenny.dev/node-class` label. That design owns them. The priority class is the agent priority class of the pod's node class, `lenny-agent-<class>`, or `lenny-reserved` on a reserved pod. In particular, runc pools run with user namespaces (`hostUsers: false`), on by default for the standard class, and the adapter checks `/proc/self/uid_map` before READY on a pod rendered with them ([`placement-design.md`, "PM-1"](placement-design.md#pm-1-node-classes-and-presets)). What user namespaces give slot isolation, such as a distinct host UID range per pod for per-UID kernel limits, is stated in [`session-isolation-design.md`](session-isolation-design.md). Slots inside a pod keep distinct UIDs inside the pod's range, and the `lenny-store-fill` UID maps within the same range.

## PL-2 Removal of the embedded deployment model

**What is removed (D1).**

- The `deploymentModel` field and its `embedded` value on the `Runtime` resource, the CRD, the gateway's runtime registry and backup export, and every reader of the field: the pod builder's dispatch and `buildEmbedded`, the RuntimeReconciler's validation that refuses `requireSoPeercred: false` on an embedded runtime, the supervisor predicate `runsSupervisor`, and the qualifier "on a `deploymentModel: sidecar` runtime" wherever it appears.
- `pkg/adapter/embedded.go`, `embedded_sdkwarm.go`, and `adapter.InProcessRuntime` and `SDKWarmInProcessRuntime`, which are the embedded runtime loop and its pre-launched variant.
- The `embedded` value of `pkg/checkpoint`'s `Level`, `pkg/adapter/embeddedcheckpoint`, and what remains of the `SIGSTOP` path, as IC-9 states.
- The in-process broker of IC revision 13 ("IC-1", **Embedded pods.**, and IC-9's second bullet), which existed only so that an embedded pod could run the broker's operations without a supervisor.
- Every embedded branch in the specification, listed under "Specification changes", and the embedded rows of the egress, connector-authorization, forensics, billing, session-derive, tenant-derived, runtime-revisions, IC, and RP designs, listed under "Instructions for reviewers of other designs".
- SI O6, because no embedded pool exists.

**What replaces the embedded runtimes.** `cmd/runtimes/echo-embedded` becomes a runtime built on the Go runtime SDK (`sdks/runtime/go`) that declares a `command` and runs under the supervisor in a slot container. The echo loop of `pkg/runtimekit/echocore` already runs in `cmd/runtimes/echo` over `CH-MSGSOCK` **[source]**, so the echo runtime keeps its behaviour. `cmd/runtimes/preconnect-echo` existed to exercise pre-launched runtimes, which D9 removes, so it is deleted rather than rewritten ("PL-8").

**Embedded Mode.** `lenny up` stays. Its echo seed (`pkg/embedded/stack`) changes from the `runtime-echo-embedded` image with `deploymentModel: embedded` to an echo image whose Runtime declares `command`, placed on a pod with the adapter and a slot container (PLR-14). The stack already runs sidecar runtimes: §17.4's walkthrough registers a runtime with `command` against the embedded gateway **[source]**.

**What is lost, and why it is acceptable.**

| Lost | Why it is acceptable |
| :-- | :-- |
| One container per pod. The adapter container costs about 50 MB of memory ([§4.7.10](../spec/04_system-components.md#4710-deployment-model) trade-off table) **[source]**. | Every runtime but the first-party echo binaries already pays it, and SI's slot containers already put a separate adapter on every session-mode pod. The resource class states the pod's total (billing decision 7), so the adapter's share comes out of a class the deployer sizes. |
| An in-process call between adapter and runtime, replaced by a hop over a local Unix socket for each frame, which costs well under a millisecond **[inference]**. | A frame's other costs, an LLM call or a tool's run, are larger by orders of magnitude. The embedded model's "Recommended for" row names "First-party runtimes where latency matters" **[source]**, and no runtime in the tree depends on that latency. |
| Shipping one Go binary that is both adapter and runtime. | The runtime image now holds only the runtime, and the platform ships the adapter and the supervisor, which is what every third-party runtime already does. |

**What is gained.**

- **The agent leaves the adapter's process.** An embedded runtime ran inside the adapter, in a container that mounts the gateway-audience service-account token and holds the gateway credentials, at the agent UID **[source]**. A bug in the runtime, or code it ran, could read them. With the runtime in its own container under its own UID, the egress design's exception for embedded runtimes, whose "egress identity and tokens" sat "at the agent UID, so P3 fails" before `netagent` existed **[source]**, has no case left, and neither has §4.7.11's exception that a runtime with no adapter-agent socket boundary needs no peer check.
- **Fewer branches.** Each design and section that touches the pod loses its embedded row: the checkpoint path, the broker's transport, the credential mount rule of §13.1, the teardown rows of §28.5.3, the supervisor refusals of SD-P4 and DR-8, the container mapping of billing decision 7, and the freeze order of the forensics runbook.
- **One blueprint.** Every session-mode agent pod is the pod of "PL-1".
- **No name clash.** "Embedded" names only Embedded Mode, the local stack.

## PL-3 Runtime-visible filesystem layout

**The paths (D2).** Inside every slot container of every pod, whatever its slot count and whatever its session **[design]**:

| Path | Volume | Medium | Size limit setting | Written by | Runtime may write | Checkpointed |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| `/workspace` | `slot-<n>-workspace`, mounted at its root | Disk | `workspaceSizeLimitBytes` (pool, 10 GiB by default under [IC decision D3](incremental-checkpoint-design.md#decisions)) | The runtime, setup commands, and `lenny-materialize` as the slot UID; restore through the broker | Yes | Yes, except the reserved names below |
| `/session` | `slot-<n>-session`, mounted at its root | Disk | `sessionSizeLimitBytes` (pool, 1Gi by default, O6 and D27) | The runtime as the slot UID; restore through the broker | Yes | Yes, in the same snapshot as `/workspace` |
| `/tmp` | `slot-<n>-tmp` | Disk (O3) | `tmpSizeLimitBytes` (pool, 1Gi by default, O6) | The runtime; the supervisor creates `/tmp/home` | Yes | No; the Sweep empties it at each slot release |
| `/dev/shm` | `slot-<n>-dshm` (O7) | Memory, counted in the slot's memory | `shmSizeLimitBytes` (pool, 64Mi by default, O7) | The runtime | Yes | No; the Sweep empties it |
| `/run/lenny` | `slot-<n>-run` | Memory | None, as today | The adapter | No (read-only mount) | No |
| `/lenny/assets` | `lenny-assets` | Disk | The assets' total size plus 64 MiB, a tenant-derived runtime's appended assets included ("PL-5", D24) | The adapter, before READY | No (read-only mount) | No |
| `/lenny/git-stores` | `lenny-git-stores` | Disk | `warmCloneBytes` (DR-11), covering the stores and their pristine trees | `lenny-store-fill`, before any regular container starts (D11) | No (read-only mount) | No |
| `/lenny/bin` | `lenny-bin` | Disk | None | `lenny-bin-stage` | No (read-only mount, files `0111`) | No |
| `/run/netagent` | `netagent`'s pod-wide volume | As the egress design states | As the egress design states | `netagent`, with the files every slot shares, the network descriptor `network.json` and the git configuration `gitconfig` among them, and no session's value | No | No |
| `/run/netagent/credentials` | `slot-<n>-netcred` (PLR-22) | Memory | 8 MiB | `netagent`, with every value that belongs to the slot's session: the binding list `bindings.json`, the `delivery: file` credentials, `netrc`, the session's git configuration include file, one commit identity file per VCS pool of the session, which the include file selects per repository with git's `includeIf "hasconfig:remote.*.url:<pattern>"`, the files of federated bindings, and the coordination generation | No (read-only mount) | No |

**`/run/netagent`.** The pod-wide volume holds only what every slot shares: the trust bundle, the pod-wide git configuration `/run/netagent/gitconfig`, and the network descriptor `/run/netagent/network.json`, which holds the endpoints, the CA bundle path, the `NO_PROXY` list, the launch variables, and a pointer to the session's binding list. Every value that belongs to one session sits on that slot's own `slot-<n>-netcred` volume, mounted at `/run/netagent/credentials`: the binding list `bindings.json`, with each binding's name, hosts, delivery, and file path; the `delivery: file` values; the `netrc` file; the session's git configuration include file, which the pod-wide git configuration names by an include path under `/run/netagent/credentials`; the files and variable values of a federated binding; and the session's coordination generation. Every path the pod-wide files name lies under `/run/netagent/credentials`, which is the same in every slot because each slot mounts its own volume there, so the pod-wide files name no session's bindings, and a slot reads its own session's values and no other slot's. `NETRC` names `/run/netagent/credentials/netrc` on every pod, and the file is empty when the session has no Basic binding. The `inject` placeholder is the profile's constant `lenny-injected` and never a per-binding value, so no launch variable depends on a session ([`egress-and-git-design.md`, "Injected configuration"](egress-and-git-design.md#injected-configuration)) **[design]**.

**`/workspace`.** The workspace volume is mounted at `/workspace` directly. It is the runtime's working directory: the slot container's `workingDir` is `/workspace`, so the supervisor and every process it launches start there. DR-12's `workingDirectory`, when a plan sets one, names a folder under `/workspace` and reaches the runtime as `cwd` on `session_start` **[source]**. Nothing is nested between the volume root and the working tree: no `current/` directory, no session-identifier directory, and no permanent platform directory.

`/workspace` is a mount point, so the session cannot rename or remove it: spike 2 measured `EACCES` when a slot renamed its own volume root and `EBUSY` on the mount point **[measured]**. This retires SI-1's hazard that a slot could rename or replace the session directory an adapter created, and the second sentence of SIR-7, which made every adapter operation reopen the session root from the volume root: there is no session root below the volume root.

**Reserved names.** The platform's transient work in `/workspace` uses only these names at the volume root, and a runtime does not create them **[design]**:

| Name | Created by | Exists | Removed by |
| :-- | :-- | :-- | :-- |
| `.lenny-canary` | The supervisor, at container start | From start until the start-up Sweep, before READY | The start-up Sweep ("PL-5") |
| `.lenny-prestage` | `lenny-materialize`, at warm-up and after each slot release | Until the next session binds | The bind, which adopts its trees by rename and renames the rest aside ([WM-15](workspace-materialization-design.md#wm-15-warm-up-checkout-and-reflink-rebuild)) |
| `.lenny-discard-<id>` | `lenny-materialize`, at bind | Until a background `discard` run deletes it, or the slot release | `discard`, or the release Sweep (WM-15) |
| `.lenny-build` | `lenny-materialize`, during a run that builds a git source | During the run | The run itself, or `discard` ([WM-8](workspace-materialization-design.md#wm-8-atomicity-under-the-fixed-layout)) |
| `.lenny-overlay-<id>` | `lenny-materialize`, during a mid-session overlay | During the run | The run itself, or `discard` (WM-8) |

`<id>` is an identifier the adapter chooses for the run, which carries no slot-written byte. Checkpoints, the change tracker, workspace downloads, exports, and output files skip these names at the volume root. A session that creates an entry with one of them has it skipped too, which the runtime-author contract of "PL-6" states. The empty-workspace rule of [WM-7](workspace-materialization-design.md#wm-7-ordering-and-collisions) allows `.lenny-prestage`, and every name is gone after a slot release, because the Sweep empties the volume.

A mount hides whatever the image has at the same path. A runtime image that ships content under `/workspace` loses it on every pod. Content a session should start with belongs in the Runtime's `workspaceDefaults`, which `lenny-materialize` writes at materialization ([`workspace-materialization-design.md`](workspace-materialization-design.md)).

**`/session`.** The runtime keeps its private per-session state here: a harness's transcripts and conversation state, and anything else it needs to continue the session after a resume. The directory is singular, because a slot container serves one session at a time (SI D4). It is checkpointed atomically with `/workspace`, in the same snapshot, and it is kept out of the working tree, so it never appears in `GET /v1/sessions/{id}/workspace`, in an output file, or in a `from: start` derive's copied plan. A derive `from: latest` restores it with the workspace, as a resume does ([IC-5](incremental-checkpoint-design.md#ic-5-restore-derive-download-and-seal)).

`/session` is disk-backed with its own `sizeLimit`, where §6.4 gives `/sessions/` a tmpfs today **[source]**:

- A tmpfs page counts against the memory cgroup of the process that writes it **[inference]**. A restore writes session files through broker descriptors from the adapter, so SI-6 had to charge one session-file cap to the adapter's memory for each slot and take it from each slot's share **[source]**. On disk that charge does not exist.
- A slot's own transcript growth counted against its hard memory limit, and an out-of-memory kill makes the slot dead for the pod's life (SI-4) **[source]**.
- `FICLONE` needs the source and the spool on one filesystem **[measured]**, so a disk-backed `/session` lets the checkpoint clone large session files into the spool as it clones workspace files, where a tmpfs file had to be read in full.
- Transcripts carry the same class of data as the workspace, which already lives on node disk under node-level disk encryption ([§6.4](../spec/06_warm-pod-model.md#64-pod-filesystem-layout), **Data-at-rest protection:**) **[source]**.

Runtimes point their harness's state directory at `/session`, for example `CLAUDE_CONFIG_DIR=/session/claude` for Claude Code, in the Runtime's `env`. They do not point `HOME` at it, because `HOME` collects package caches and tool state that should not be checkpointed or count against the session's state limit.

**`/tmp` and `HOME`.** `/tmp` is private to the slot, disk-backed with its own `sizeLimit` (O3), swept at every slot release, and not checkpointed. `HOME` is `/tmp/home` (O4): the supervisor creates the directory as the slot UID with mode `0700` before each launch and each setup command that runs with the launch environment, so a fresh home exists for every session after the Sweep. A `HOME` pair in the Runtime's `env` replaces the platform's value, and the supervisor then creates nothing.

**`/dev/shm`.** Each slot container has its own memory-backed `/dev/shm`, sized by the pool's `shmSizeLimitBytes` (O7). Its pages count against the slot container's memory, so the pool's validation counts the size in the slot's memory, and a write past the size fails with `ENOSPC` **[inference]**. POSIX shared memory objects are therefore private to the slot. System V objects and POSIX message queues remain shared through the pod's IPC namespace, which `acknowledgeSharedPod` lists ("PL-9").

**`/lenny`.** The specification reserves `/lenny` in every slot container. A runtime image puts nothing under it, and the platform mounts only these read-only volumes there (PLR-6):

- `/lenny/assets` holds the runtime's `sharedAssets` of type `artifact` and `inline`, which [§5.1](../spec/05_runtime-registry-and-pool-model.md#51-runtime) and [`runtime-revisions-design.md`](runtime-revisions-design.md) describe. The adapter writes them before READY, with directories `0755` and files `0444` (SI-7). The volume is mounted on every pod, empty when the runtime declares no such asset, so a runtime cannot treat the path as writable scratch space. `gitRepository` entries of `sharedAssets` go onto the warm list and reach `/lenny/git-stores` ([`tenant-derived-runtimes-design.md`, "Warm stores"](tenant-derived-runtimes-design.md#warm-stores)) **[source]**. On a tenant-derived runtime's owned pool, `/lenny/assets` holds the base revision's files and the tenant's appended `inline` and `artifact` files side by side, and a tenant file never replaces or shadows a base file, because the tenant's write is refused at a conflicting path (D24) **[design]**.
- `/lenny/git-stores` holds the warm repository stores, which `lenny-store-fill` writes under its own UID with the store GID as the group and a umask of `0002` (D17). The store GID is a dedicated GID, the chart value `storeFill.gid`, 29100 by default, and it is the primary group (`runAsGroup`) of both the adapter and `lenny-store-fill`. The chart refuses a value inside the slot GID range or equal to the GID of any other agent-pod container or to `kata.volumeGid`, and `lenny-pod-security` refuses it as the `runAsGroup` or `runAsUser` of any other container, ephemeral containers included, and in `supplementalGroups`, which no agent pod sets (PLR-10). Sharing the adapter's primary group with the fill exposes nothing else of the adapter's: the fill mounts no volume of the adapter's other than `lenny-git-stores`, its other mounts are `lenny-bin` and `netagent`'s `/run/netagent`, both read-only, no slot container holds the GID, and the fill is an init container that has exited before the adapter starts **[design]**. Directories come out `0775` and object files `0444`, and after each fill an explicit mode pass over the store and its pristine tree sets directories to `0775`, regular files to `0444`, and executable files to `0555`, and clears every setuid and setgid bit, so nothing in the volume grants write to the other class and nothing carries a set-ID bit. Every slot reads the stores through the other class and no slot can write them, which the read-only mount enforces in any case. Every agent-pod container runs with `allowPrivilegeEscalation: false`, which `pkg/controller/sandbox/podspec/security_context.go` sets on each container **[source]**, so a set-ID bit that reached the volume would not change the identity of a process that executes the file. The pod specification gives the store GID to the adapter and the fill as their primary group, so the mechanism needs no supplementary group and holds under either `supplementalGroupsPolicy`, `Strict` included, because Kubernetes has no container-level supplementary groups and the pod sets no pod-level list (PLR-10). No slot container holds the GID through the pod's specification. A runtime image's own `/etc/group` is outside the webhook's view: under the kubelet's default `supplementalGroupsPolicy: Merge` a slot image can name any GID, the store GID included, as SI's spike measured **[measured]**, and such a slot gains only group write on a volume that its read-only mount keeps it from writing, which the stress test suite of "Validation owed" checks. The adapter deletes a withheld store and its pristine tree through the group class on its read-write mount, and the deletion follows no symbolic link: it opens each directory with `openat2` and `RESOLVE_NO_SYMLINKS | RESOLVE_BENEATH | RESOLVE_NO_XDEV` relative to a directory descriptor beneath the volume root, removes each entry with `unlinkat` relative to its parent's descriptor, and reads no file. On a Kata `block-plain` pod the volume root carries the setgid bit and the dedicated volume GID, so `lenny-store-fill` creates each store's directory and its pristine tree's directory, sets their group to the store GID and clears their setgid bit before it writes into them, and every entry below then carries the store GID as on every other pod ([SI-1](session-isolation-design.md#si-1-pod-layout)) **[design]**. Each store is a bare repository at `/lenny/git-stores/<hash>`, named by a hash of its normalized URL, and its pristine tree, a checkout of the store's commit, sits beside it at `/lenny/git-stores/<hash>.tree` (WM-15). A slot repository names a store's `objects` directory in `objects/info/alternates` as an absolute path under `/lenny/git-stores`. Under SI O11, as settled on 2026-11-12, every git step on a slot repository runs as the slot UID through the supervisor's worker, so only slot containers need the path to resolve. The adapter, which runs no git on slot repositories, reads `objects/info/alternates` as a file through the broker when it captures a workspace and never follows it.
- `/lenny/bin` holds `lenny-supervisor`, `lenny-materialize`, and the pinned static `git`, staged with mode `0111` by `lenny-bin-stage`. A runtime can execute them and cannot read them. The materialization study measured that an exec-only helper is non-dumpable from `execve` **[measured]**.

**`/run/lenny`.** Unchanged as a mount: the slot's run volume, read-only, holding the adapter manifest at `/run/lenny/adapter-manifest.json` and the session's credential file. The credential file moves from `/run/lenny/slots/{sessionId}/credentials.json` to `/run/lenny/credentials.json`, because the volume belongs to one slot and no runtime-visible path carries a session identifier. `session_start` keeps `credentialsPath`, with that constant as its value (O1), and omits it when the session has no credential file. [`llm-upstreams-and-cost-budgets-design.md`](llm-upstreams-and-cost-budgets-design.md) removes direct LLM delivery mode, the file's LLM use, so the file exists only if a VCS path still uses it, which that design leaves to validation.

**No session identifier in any path.** No runtime-visible path contains a session identifier. `session_start` still carries `sessionId` as data: the identifier the runtime logs and reports under, and the key its own state can use.

**The adapter's view.** The adapter mounts under `/adapter` (PLR-9) **[design]**:

| Adapter path | Volume | Mode | Use |
| :-- | :-- | :-- | :-- |
| `/adapter/slots/<n>/workspace` | `slot-<n>-workspace` | Read-write | The start-up canary and the release's removal step. Every other access, the disk watch included, goes through slot `n`'s broker (SIR-8). |
| `/adapter/slots/<n>/session` | `slot-<n>-session` | Read-write | The same as the workspace. |
| `/adapter/slots/<n>/run` | `slot-<n>-run` | Read-write | The manifest and the credential file, which the adapter writes `0444` (SI-7). |
| `/adapter/spool` | `lenny-spool` | Read-write | Slot `n`'s checkpoint spool at `/adapter/spool/<n>/checkpoint/`, export clones at `/adapter/spool/<n>/export/`, and upload staging at `/adapter/spool/<n>/staging/`. |
| `/adapter/assets` | `lenny-assets` | Read-write | Filling `sharedAssets` before READY. |
| `/adapter/git-stores` | `lenny-git-stores` | Read-write | Deleting a withheld store with its pristine tree by unlinking its entries relative to directory descriptors that follow no symbolic link, before anything runs for the session (D11). The adapter reads no file in the volume, the pristine trees included. |

The adapter also keeps its existing mounts outside these trees: the projected service-account token at `/var/run/secrets/lenny.dev/serviceaccount`, the object-store CA bundle at `/etc/lenny/objectstore-ca`, and `netagent`'s pod-wide volume read-only at `/run/netagent` **[source]**. `netagent` mounts that volume read-write, every slot container, the adapter, and `lenny-store-fill` mount it read-only, and no other container mounts it. It mounts neither `slot-<n>-tmp` nor `slot-<n>-dshm`.

**Path translation.** A path in a frame, such as a file part's `path`, is a path in the slot container, or relative to `/workspace` where MD-18 says so. The adapter maps the prefix `/workspace/` to slot `n`'s `workspace` broker root and `/session/` to its `session` broker root, and sends the rest as a path relative to that root in an `fs` request ([SI-5](session-isolation-design.md#si-5-the-supervisor-file-descriptor-broker)). A path under any other prefix is refused, and so is a path whose first component is a reserved name. The broker's roots are `workspace`, `session`, and `tmp`, rendered as `--fs-root workspace=/workspace --fs-root session=/session --fs-root tmp=/tmp`. The adapter uses the `tmp` root only for the disk watch's walk (O8), and no frame path translates to it. The `artifacts` root of SI revision 3 is removed **[design]**.

## PL-4 Removals and the output-file rule

**`/artifacts` (D3).** The verification under "Current state" shows that the adapter creates and removes `/artifacts/{sessionId}` and nothing else uses it **[source]**. These leave:

- the `artifacts` volume and its mounts in `podspec`, and SI revision 3's `slot-<n>-artifacts` volume and `artifacts` broker root;
- `--artifacts-root`, `Server.ArtifactsRoot`, and the `Artifacts` field and mode of `slotlayout`;
- `/artifacts` in the supervisor's Sweep list;
- `/artifacts` in FE-5's step 4 and in §6.4, §4.7.10 **Sweep.**, §15.4.5, and §26.

`slotlayout` itself shrinks to nothing that depends on a session identifier and can be deleted once the slot volumes replace the per-session trees, because every path it derived is now a constant or an `/adapter` path.

**Other paths that leave.** `/workspace/slots/`, `/workspace/staging/`, the `.staging` directory under the workspace, `/workspace/shared/`, `/workspace/warm-clones/`, `/sessions/`, `/run/lenny/slots/`, and `/lenny-supervisor`. Each is replaced as "PL-3" states.

**Output files (O2).** A file reaches the user as an output file only when the runtime emits a `file` part naming its path under `/workspace` ([MD-18](message-delivery-design.md#md-18-files)). §26.2's `/workspace/output/` convention and §26.3's "Any files written under `/workspace/output/` are sealed as session artifacts" are removed, and §24.18's scaffold stops generating the convention. A reference runtime may still write its outputs to a folder of its own, and its wrapper emits a part for each file it offers.

`netagent`'s pod-wide volume, the projected token volumes, and the object-store CA volume are as their designs and §13.1 state, except that `lenny-store-fill` also mounts `netagent`'s pod-wide volume read-only at `/run/netagent` (PLR-21), and `keepalive` mounts nothing. The egress design owns `slot-<n>-netcred`'s contents, and this design names and mounts it. IC-8's gVisor pod-share annotation names `slot-<n>-workspace`, `slot-<n>-session`, and `lenny-spool`, the volumes that both a slot container and the adapter read through views that must agree, or that the adapter clones between ([IC-8](incremental-checkpoint-design.md#ic-8-checkpoint-policy-interval-and-change-tracker)).

**Volume roots.** On runc and gVisor the kubelet creates each `emptyDir` root as `root:root` with mode `0777`, or `1777` under the pod-share annotation **[measured]**. Neither the slot nor the adapter can change the root's mode. Under this layout the workspace and session roots are the runtime's own directories, so the root's mode lets the runtime create entries there, which is what a working directory needs. The slot release's handling of a `1777` root stays in [SI-3](session-isolation-design.md#si-3-runtime-processes-slot-release-and-setup-commands).

**Kata block-plain (D8).** On Kata block-plain each disk-backed `emptyDir` is its own ext4 device in the guest, and without `fsGroup` its root comes up `root:root` `0755`, which the slot cannot write **[measured]**. A Kata block-plain pod therefore sets `fsGroup` to the platform's dedicated volume GID, a GID that differs from every slot's GID and from the adapter's, and that no container runs under. The AWS run used 29000 **[measured]**. Under it, disk roots come up `root:<GID>` `2775`, `lost+found` comes up `2770`, and memory roots come up `3777` **[measured]**. The run of 2026-11-12 found that slots stay apart: no path reaches another slot's volumes, and the GID opens another slot's object only when its owner has made it group-accessible, which mode `0666` already allows **[measured]**. It also found these side effects, which the design accepts and states **[measured]**:

- Every process in the pod carries the GID, so a slot can read files of mode `0640` and `0660` in the shared read-only volumes. The adapter writes `lenny-assets` with modes that do not rely on the group (directories `0755`, files `0444`), and `lenny-store-fill` grants nothing through the other class, so every slot already reads both volumes through it. The store volume's group write serves only the adapter's deletion of withheld stores, and the slots' read-only mounts keep them from using it.
- The adapter can read and write a slot's group-accessible files through its own mount. It must not rely on that, and it reaches slot files only through the broker, as on every other pod.
- A broker restore drops the setgid bit from directories, which is the only fidelity loss the run measured.
- A slot can remove, replace, or write into `lost+found` through the GID. The release's emptiness check therefore requires `lost+found` to be empty, rather than skipping it, and fails the slot otherwise (PLR-20). The Sweep removes the slot-owned entries in it first.

**Which pods are Kata block-plain.** The Kata volume mode is a property of the nodes' Kata configuration, so the deployer states it in the chart: `kata.emptyDirMode` is `virtio-fs`, the default, or `block-plain`, and it applies to every pod of the `microvm` isolation profile, which maps to one `RuntimeClass`. `kata.volumeGid` is the dedicated volume GID, 29000 by default, the value the AWS run used **[measured]**; the chart refuses a value inside the slot GID range that SI's slot GID base and the largest slot count give, or equal to the adapter's GID or the GID of any other agent-pod container. When `kata.emptyDirMode` is `block-plain`, the controller renders `fsGroup: <kata.volumeGid>` on every `microvm` pod. `lenny-pod-security` reads the same two chart values: it admits `fsGroup` only on a pod whose `runtimeClassName` is the `microvm` profile's class while `kata.emptyDirMode` is `block-plain`, and only with `kata.volumeGid` ([`placement-design.md`, "PM-6"](placement-design.md#pm-6-enforcement)). No other pod sets it (PLR-10). A deployer who sets `block-plain` on nodes whose Kata configuration uses virtio-fs gets pods whose processes carry the GID with no effect on the volume roots, and the reverse leaves the slots unable to write their volume roots, which the start-up canary reports as a failed slot.

**Start-up canary (PLR-13).** The canary proves that the adapter's own mount of a slot volume and the slot's mount show the same volume, which the release's removal step and the reflink clones into the spool depend on. SI D10's text moved it to the slot's run volume, which the slot mounts read-only, so the supervisor cannot write it there. It is placed on the two volumes that the adapter also mounts, `/workspace` and `/session`, and it runs once, at container start. The pod starts in this order **[design]**:

1. Before any regular container starts, `lenny-bin-stage` stages the binaries. `netagent` starts as a native sidecar where the egress design renders it, and its startup probe passes once it serves and has run its slot-attribution check, whose result the controller records in the pool's status ([`egress-and-git-design.md`, "Slot attribution and fetch grants"](egress-and-git-design.md#slot-attribution-and-fetch-grants)). `lenny-store-fill` then fills the stores and their pristine trees through `netagent`. A failed fill fails the init container, and with the pod's `restartPolicy: Never` the pod fails, which DR-11's fill failure handling reads.
2. On a pod rendered with user namespaces, the adapter checks `/proc/self/uid_map` and fails the pod with `user_namespace_missing` when it is the host's identity map ([SI-11](session-isolation-design.md#si-11-user-namespaces-and-landlock)). The adapter fills `lenny-assets`.
3. The supervisor pins its broker roots, writes `.lenny-canary` at the root of `/workspace` and of `/session`, and sends `ready`.
4. The adapter pins each root's device and mount ID through the broker, and sees both canaries through `/adapter/slots/<n>/workspace` and `/adapter/slots/<n>/session`. A missing canary means the two containers do not share a view of the volume, and the slot fails, as SIR-19 states.
5. The adapter runs IC-1's reflink probe for each pair of a slot volume and the spool, which leaves a probe file in the slot volume ([IC-1](incremental-checkpoint-design.md#ic-1-capture-in-passes)).
6. The adapter sends the start-up `sweep`, which removes both canaries and the probe files, and checks that each slot volume is empty. It then chooses each slot volume's disk-watch method, taking a volume as quota-bound when `fstatfs` reports a project's limit ("PL-10", PLR-25).
7. Only then does the first warm-up checkout run (WM-15), so the empty-workspace rule and the staged trees never meet a canary. The run ends at the pod's warm-up checkout timeout, the runtime revision's `prestageTimeoutSeconds`, else the pool's, else `adapter.prestageTimeoutSeconds`, 900 seconds by default, and skips every entry it has not staged by then, so this step delays READY by at most that timeout.
8. On a pod that contributes to a platform chunk set, the adapter captures the contribution after the warm-up checkouts are staged, through the broker, before any session has bound to the pod ([`incremental-checkpoint-design.md`, "Platform chunk sets"](incremental-checkpoint-design.md#platform-chunk-sets); SIR-38). A contributing pod reports READY later by the contribution's time.
9. The adapter reports READY once every slot has passed these steps, its warm-up checkouts are staged, and any contribution has ended.

No session sees a canary, and the canary never coexists with a reserved name of a later step. The setup log moves to a pipe under the materialization study's decision B ([WM-3](workspace-materialization-design.md#wm-3-the-protocol)).

**Eviction.** The kubelet evicts the whole pod when one disk-backed `emptyDir` exceeds its `sizeLimit` **[measured]** **[external]**, which ends every slot's session. The adapter's per-slot disk watch fails the offending slot's session and runs its release at `adapter.diskWatchThresholdPercent` of the volume's limit, 90% by default, before the kubelet acts ([SI-10](session-isolation-design.md#si-10-what-stays-shared)). The watch covers `slot-<n>-workspace`, `slot-<n>-session`, and `slot-<n>-tmp`. On a volume that a project quota bounds, a write past the quota fails with `ENOSPC` or `EDQUOT` and evicts nothing ("PL-10") **[measured]**. A memory-backed volume with a `sizeLimit` is sized to that limit by the kubelet, so a write past it fails with `ENOSPC` and evicts nothing **[inference]**.

**What a trip does (PLR-23).** When a watched volume reaches the threshold, `adapter.diskWatchThresholdPercent` of its `sizeLimit`, the adapter fails the slot's session. When the session's effective checkpoint policy is `full` and the slot's `checkpointCaptureBudgetBytes` in the spool has room, it first takes a best-effort checkpoint, whose failure does not delay the end. The session then ends `failed` with the reason `workspace_size_limit` and the error code `WORKSPACE_SIZE_LIMIT_EXCEEDED`, a new code, and the slot release runs **[design]**. The reason is the one the specification already gives a checkpoint skipped for size ([§4.4.4](../spec/04_system-components.md#444-checkpoint-slos-and-scheduling), **Hard workspace size limit.**) **[source]**. This design states the trigger, and [`session-lifecycle-design.md`](session-lifecycle-design.md) states the transition. The owner confirmed the trip as written on 2026-11-13 (D21). The threshold is the chart value `adapter.diskWatchThresholdPercent`, 90 by default, and the chart refuses to render a value below 50 or above 95 (D23).

**How the watch measures a volume (O8, D12).** The watch keeps each slot volume's use against the threshold of its `sizeLimit`, by the first of these methods that applies to the volume **[design]**:

1. **`statfs`, where a project quota bounds the volume or the runtime reports it.** On a volume that a project quota bounds, `fstatfs` on the slot's broker-passed root descriptor reports the project's limit and usage, and the adapter reads the used blocks ("PL-10") **[measured]**. Under gVisor's pod-share annotation, `statfs` reports each annotated volume on its own **[measured]**, so the adapter calls `fstatfs` on the root descriptor of `/workspace` and `/session` and reads the used blocks. Under Kata `block-plain` each disk-backed volume is its own ext4 device in the guest, whose `statfs` tracks the volume's usage exactly and reports the node filesystem's size rather than a limit **[measured]**, so the adapter reads the used blocks of `/workspace`, `/session`, and `/tmp` there and adds `kata.blockPlainOverheadBytes`, 64 MiB by default, to each figure before it compares it with the threshold, which covers the gap to the kubelet's figure that O10 states (D26). Elsewhere, `statfs` on an `emptyDir` with no project quota reports the whole node filesystem **[measured]**, so this method applies there only through a quota.
2. **A running total from the change tracker, where the tracker runs.** The adapter reads the tracker's events as they arrive, and each event feeds both the checkpoint's dirty set ([IC-1](incremental-checkpoint-design.md#ic-1-capture-in-passes)) and the watch. The watch keeps, per volume, the counted size of each inode, built by a recalibration walk, and on each event it stats the dirty path relative to its broker-passed directory descriptor and adjusts the total by the difference, counting a hard-linked inode once. It recalibrates by a full walk every `adapter.diskWatchRecalibrationSeconds`, 300 s by default, and at once when the tracker reports an overflow or reaches its event cap, because a missed event leaves the total wrong until the next walk. A checkpoint walk does not replace a recalibration walk (D21): it skips the reserved names and the `checkpointExcludes` subtrees, whose bytes the watch counts. The running total covers only the subtrees the tracker watches. The reserved names at the top of `/workspace`, the subtrees that `checkpointExcludes` keeps out of the tracker, and any directory the tracker could not watch are measured by a walk every `adapter.diskWatchIntervalSeconds` and added to the total. A tracker that IC-8 marks degraded, after a failed watch or a failed cross-check, switches its volumes to method 3 until the adapter restarts the tracker and a recalibration walk rebuilds the total. The tracker watches the brokered volumes, `/workspace` and `/session`, on the runtimes where IC-8's `auto` setting turns it on.
3. **A walk every `adapter.diskWatchIntervalSeconds`, 10 s by default, elsewhere.** This covers `/tmp` on every runtime where `statfs` does not report it, and every volume where neither of the methods above applies. A walk goes through the slot's broker as IC-1's walk does: it lists each directory with `getdents` on a broker-passed or broker-derived directory descriptor, stats the entries in parallel relative to it with `AT_SYMLINK_NOFOLLOW`, and falls back to the broker's `statat` for a directory that refuses it with `EACCES`. The adapter's own mount cannot do this, because it cannot search a slot-owned directory of mode `0700`, and it does not mount `/tmp`. A pass that exceeds the interval starts the next at once. The walk's cost is IC's: 0.5 µs per entry on runc and 12.7 µs on Kata virtio-fs **[measured]**, so a 200,000-entry workspace takes about 0.1 s and 2.6 s per pass.

A walk and the running total count each inode once, by device and inode number, at the larger of its logical size rounded up to 4,096 bytes and its allocated blocks. A reflink clone therefore counts at its full size, as the kubelet counts it, and the figure is never below the kubelet's. Reserved names count, because their bytes are on the volume. The broker's `tmp` root serves only `open` of a directory and `statat`, for this walk alone ([SI-5](session-isolation-design.md#si-5-the-supervisor-file-descriptor-broker)).

**Project quotas (D25).** Where the node's filesystem has project quotas and `lenny-quota-agent` runs, the slot volumes of runc pods with user namespaces and of Kata virtio-fs pods, and `/tmp` under gVisor, carry a project quota slightly below their `sizeLimit`, and the watch reads them by method 1 with no walk. "PL-10" states the agent, the volumes it bounds, and when the adapter takes a volume as quota-bound.

**Reflink clones and the spool.** The kubelet counts a reflink clone at its full size against `sizeLimit`: three `FICLONE` copies of 200 MiB into a spool limited to 300Mi evicted the pod with almost no new disk use **[measured]**. A clone's bytes count against the volume that holds the clone. The spool is therefore one pod-wide volume whose `sizeLimit` is the pool's `spoolSizeLimitBytes`, 16 GiB by default, and the adapter's own accounting stops a write well before the kubelet's limit (PLR-11, D13) **[design]**:

- The adapter uses 1/`spoolHeadroomFactor` of `spoolSizeLimitBytes`, so with IC-7's factor of 2 it uses 8 GiB of the 16 GiB default, and the rest is headroom for clones the kubelet counts at full size.
- In that share it reserves each slot's `checkpointCaptureBudgetBytes`, a pool setting of 512 MiB by default, for that slot's checkpoint spool and export clones ([IC-7](incremental-checkpoint-design.md#ic-7-size-limits-and-drain-budgets)).
- The slots share the rest as upload staging. A source that does not fit waits for room, and a wait that reaches the run's deadline fails with `details.reason: "staging_timeout"`. The gateway refuses an upload larger than the pool's staging space when it is uploaded, with `staging_limit` ([WM-4](workspace-materialization-design.md#wm-4-the-plan-the-adapter-builds)).
- Pool admission refuses a pool whose usable share, less every slot's capture budget, is below WM's `minStagingBytes`, a constant of 1 GiB. At the defaults the staging space is 7.5 GiB on a pod with one slot and 6 GiB on a pod with four.
- The adapter accounts every file by logical size, and a clone or copy larger than its slot's remaining capture budget is not made, as IC-7 states. A slot whose workspace holds a reflink clone, such as a file a restore cloned, an upload the helper cloned from staging, or a file of a warm-up checkout rebuilt from a pristine tree (WM-15), is charged the same way, and the watch counts it so.

**Ephemeral storage (D15, D18).** The controller renders each disk-backed volume's `sizeLimit` and an ephemeral-storage request equal to their sum plus the resource class's own request: per slot, `workspaceSizeLimitBytes`, `sessionSizeLimitBytes`, and `tmpSizeLimitBytes`, and for the pod, `spoolSizeLimitBytes`, `warmCloneBytes`, and the `sizeLimit` of `lenny-assets`. `lenny-bin` carries no limit and adds nothing, because only `lenny-bin-stage` writes it, with the release's fixed binaries (PLR-12). The whole request sits on the adapter container, set after the class's resources are applied, as DR-11 already adds `warmCloneBytes` there **[source]**, so the scheduler and the namespace quota count it once. No other container carries an ephemeral-storage request. The slot containers, `netagent`, and `keepalive` carry none, and neither do the init containers `lenny-bin-stage` and `lenny-store-fill`, whose writes land on `emptyDir` volumes the sum already counts, so the init containers never raise the pod's effective ephemeral-storage request. Each resource class carries its own `requests.ephemeral-storage`, 1 GiB in the shipped classes and configurable per class, for the containers' writable layers and logs, which no volume's `sizeLimit` counts; the controller adds it once per pod to the sum on the adapter container (D18, the billing design's BR-Q1 settled as (a) in [`billing-resource-attribution-design.md`](billing-resource-attribution-design.md)). At the defaults the volumes of a pod with one slot add 10 GiB, 1 GiB, 1 GiB, and 16 GiB, 28 GiB, and the shipped class adds 1 GiB, so the pod requests 29 GiB plus its stores and its assets; each further slot adds 12 GiB (D27). The tree renders neither the workspace volume's `sizeLimit` nor any agent-pod ephemeral-storage request today **[source]**. [`incremental-checkpoint-design.md`](incremental-checkpoint-design.md#decisions) recomputes the §17.8.2 quota defaults and the §10.1 drain tiers under its D3. Billing decision 10 bills pod disk as reserved ephemeral storage, so the request is also the bill.

**Drains.** A pod's slots take their eviction checkpoints one after another on a drain, so the waits that depend on a pod's checkpoints scale with its slot count. The agent-pod grace floor counts one capped checkpoint for every slot, and the gateway's wait for the pod's `CheckpointBarrierAck` and a gateway replica's preStop wait each allow `maxConcurrentSessionsPerPod × evictionCheckpointCapSeconds` for the pod, as [IC-7](incremental-checkpoint-design.md#ic-7-size-limits-and-drain-budgets) states. A disk-watch walk does not join the checkpoint queue.

**Credentials and modes.** The adapter writes the manifest and the credential file into `slot-<n>-run` with mode `0444`, and the mount boundary keeps every other slot out, as SI-7 states. No slot's access relies on group permissions, on Kata block-plain included. The one use of a group is the adapter's deletion of withheld stores in `lenny-git-stores` through the store GID ("PL-3", D17).

## PL-6 Runtime-facing environment and the runtime-author contract

**How the runtime learns its paths (O1).** The paths are constants that the specification states, and the supervisor starts every runtime process in `/workspace`. No environment variable or manifest field repeats them.

**The launch environment.** The supervisor builds each launch's environment from nothing, as today: a fixed `PATH`, the Runtime's `env`, and the platform's variables ([§4.7.10](../spec/04_system-components.md#4710-deployment-model), **Runtime supervisor.**, **Environment.**) **[source]**. Under O4 the platform's variables gain `HOME=/tmp/home`, which a `HOME` pair in `env` replaces, and the supervisor creates the directory with mode `0700` as the slot UID when it uses the platform's value (PLR-15). Setup commands run with the same environment.

**The contract.** A runtime author relies on these statements, which the specification states in §6.4 and the runtime author guide repeats:

1. The runtime process starts when its session binds, after the session's workspace is materialized and its setup commands have run. No process of the runtime runs before then.
2. The working directory is `/workspace` when the process starts. The session's own working folder is `session_start`'s `cwd`, which lies under `/workspace`.
3. `/workspace` is the session's working tree. Everything in it is checkpointed, restored on resume and on a `from: latest` derive, and downloadable as the session's workspace. The path is the same on every pod and in every session.
4. `/session` is for state the runtime needs to continue the session and that the user's working tree should not show. Point the harness's state directory here through `env`, for example `CLAUDE_CONFIG_DIR=/session/claude`. It is checkpointed with the workspace and limited by `sessionSizeLimitBytes`.
5. `/tmp` is scratch space, and `HOME` is `/tmp/home` unless the Runtime's `env` sets it. Nothing in either survives the session. `/dev/shm` is private to the slot and limited by `shmSizeLimitBytes`.
6. `/run/lenny` holds the manifest and, when the session has one, the credential file, read-only. When `session_start` carries `credentialsPath`, read the credential file's path from it.
7. `/lenny/assets` holds the runtime's shared assets, read-only. `/lenny/git-stores` and `/lenny/bin` belong to the platform.
8. The image puts nothing under `/workspace`, `/session`, or `/lenny`, because mounts hide it. Content every session should start with goes in `workspaceDefaults`.
9. The names `.lenny-canary`, `.lenny-build`, `.lenny-prestage`, `.lenny-overlay-*`, and `.lenny-discard-*` at the top of `/workspace` belong to the platform. A runtime does not create them, and an entry under one of them is not checkpointed, downloaded, or exported.
10. A file offered to the user is offered by emitting a `file` part that names its path (O2).
11. Every other path is the image's own and is read-only.

## PL-7 What the layout gains

- **Absolute paths survive a derive.** A derived session restores the source's workspace at the same `/workspace`, so a Python virtual environment, `node_modules/.bin`, CMake and Bazel caches, `compile_commands.json`, and a git worktree's recorded location keep working **[inference]**. Under §6.4 each held the source's session identifier, and a derive gave the session a new one.
- **A constant working directory.** Every session of a runtime starts in `/workspace`, or in the same folder under it when a plan names one, on every pod.
- **Harness state keyed by working directory stays consistent.** A harness that names its state by working directory, as Claude Code names its project directory, finds the same key on a resume, a retry, a rebuild, and a derive **[inference]**.
- **No rename hazard.** The working tree is a mount point. SI-1's defence against a session renaming or replacing its session directory, and SIR-7's reopening of the session root on every adapter operation, have no subject left.
- **Simpler path translation.** The adapter maps fixed prefixes to the slot's broker roots, with no session identifier to parse or validate.
- **More identical prompts.** A harness that puts its working directory and environment into its system prompt produces the same text for every session of a runtime, so more requests share a cacheable prefix with the provider's prompt cache **[inference]**.

## PL-8 Removal of pre-launched runtimes

**A warm pod (D9).** A warm pod is a pod whose infrastructure is ready, and nothing else **[design]**. Its containers are running; each slot supervisor has answered, pinned its broker roots, and passed the start-up canary and Sweep; `lenny-assets` and `lenny-git-stores` are filled, with the stores' pristine trees; and each slot's warm-up checkouts are staged under `/workspace/.lenny-prestage` ([WM-15](workspace-materialization-design.md#wm-15-warm-up-checkout-and-reflink-rebuild)). No runtime process runs on it. The terms "pod-warm" and "SDK-warm" leave the specification, and "warm pod" keeps this one meaning.

**The launch at bind.** The adapter asks a slot's supervisor to launch the runtime once per session, after the session binds and after its seed restore, its materialization, and its setup commands have finished. The runtime's handshake follows ([`runtime-protocol-design.md`, "RP-1"](runtime-protocol-design.md#rp-1-handshake)), then `session_start`. This holds at the first bind of a slot and after every slot release: the release launches nothing, and it ends by staging the slot's warm-up checkouts for the next session ([SI-3](session-isolation-design.md#si-3-runtime-processes-slot-release-and-setup-commands); WM-15).

**What leaves.** [`runtime-protocol-design.md`](runtime-protocol-design.md#decisions) decision D6 removes the `preConnect` capability. This design removes the pod and pool parts that existed for it **[design]**:

- `capabilities.preConnect` and `sdkWarmBlockingPaths` on the Runtime, the §5.2 admission rule that admits `preConnect` only with one session per pod, and the clause of the derived `restartable` flag that names `preConnect`.
- The pod state `sdk_connecting`, its watchdog `sdkConnectTimeoutSeconds`, and the rows of the occupancy projection and the pod state machine that name it, including the coarse pod phase stored in the pod table.
- `ConfigureWorkspace` and `DemoteSDK` as separate paths, the error code `SDK_DEMOTION_NOT_SUPPORTED`, and the SDK-warm demotion contract for adapters.
- The demotion circuit breaker: `spec.sdkWarmDisabled`, `status.sdkWarmCircuitBreaker`, the PoolScalingController's trip and untrip, the admin route `PUT /v1/admin/pools/{name}/circuit-breaker`, and `lenny-ctl admin pools circuit-breaker`.
- The metrics `lenny_warmpool_sdk_demotions_total` and `lenny_warmpool_sdk_connect_timeout_total`, the alert `SDKConnectTimeout`, and the "pod-warm" qualifier of the startup latency SLO rows.
- The `preconnect-echo` test runtime and its pools.
- The refusals that existed because a pre-launched process could hold files open before its session, such as DR-11's refusal of a withheld store on a pool whose runtime pre-connects.

**What is lost, and why it is acceptable.** A harness's own start now falls inside the session's start, where a pre-launched process had already paid it. The owner judged runtime start times "relatively small" and asked for no validation of them. The pod-warm path was the default already, and a pool whose sessions carried a blocking path, such as Claude Code's `CLAUDE.md`, was demoted and paid the start anyway **[source]**.

**What is gained.** One start path for every session, with no demotion, no circuit breaker, and no pod state between ready and claimed. A runtime process never sees a workspace before it is complete, and no process can hold a store or a staged tree open before its session, so a withheld store and an unused warm-up checkout can be deleted for any pool.

**Size settings (O6, O7).** The pool's `sessionPolicy` sizes each slot's volumes with these settings, beside `workspaceSizeLimitBytes` **[design]**:

| Setting | Volume | Default | Notes |
| :-- | :-- | :-- | :-- |
| `workspaceSizeLimitBytes` | `slot-<n>-workspace` | 10 GiB (IC D3) | Existing. |
| `sessionSizeLimitBytes` | `slot-<n>-session` | 1Gi | Raised from today's 256 MiB cap for session files (D27). |
| `tmpSizeLimitBytes` | `slot-<n>-tmp` | 1Gi | Covers `HOME`'s package caches. |
| `shmSizeLimitBytes` | `slot-<n>-dshm` | 64Mi | Counted in the slot's memory: pool and resource-class validation refuses a configuration whose per-slot memory, less this size, falls below the platform's `runtimes.minSlotMemoryBytes` ([WM-14](workspace-materialization-design.md#wm-14-memory-sizing)). |
| `spoolSizeLimitBytes` | `lenny-spool`, one per pod | 16 GiB | WM's setting (D13). **Renames (D7).** These are straight renames, with no alias and no period in which both names are accepted **[design]**:

| Old name | New name | Meaning |
| :-- | :-- | :-- |
| `sessionPolicy.maxConcurrentSessions` | `sessionPolicy.maxConcurrentSessionsPerPod` | The number of sessions one pod serves at the same time, and the number of slot containers the pod renders. | `acknowledgeProcessLevelIsolation` | `sessionPolicy.acknowledgeSharedPod` | The deployer's acknowledgment, on the pool and never per session, that a pod serving several sessions at once still shares some resources between them. |

Revision 2 also renamed service mode's `maxConcurrent` to `maxConcurrentRequestsPerPod`. AR removed service mode, so neither name remains, and AR refuses a write that names `maxConcurrentRequestsPerPod`.

`recycle.acknowledgeBestEffortScrub` keeps its name. The old names appear in about 180 places across the specification, the designs, the documentation, the code, the charts, and the schemas; the specification's part goes through the proposal pipeline.

**`acknowledgeSharedPod`.** It is required only when `maxConcurrentSessionsPerPod` is above 1. Its use for `recycle.runtimeProcess: keep` leaves with `keep` itself (SI D4). A pool with `maxConcurrentSessionsPerPod` above 1 and without `acknowledgeSharedPod: true` is refused with `422 INVALID_POOL_CONFIGURATION`, and the error lists what the slots of such a pod still share **[design]**:

- the network namespace, with its side channels, ports, DNS cache, and timing; `CAP_NET_RAW` stays dropped;
- the IPC namespace: System V objects and POSIX message queues;
- the sandbox kernel under gVisor and Kata;
- the adapter and `netagent`; `netagent` scopes each slot's connections to that slot's session, and falls back to the union of the pod's sessions only on a pool whose runtime class does not answer slot attribution, as the pool's status records, where its sessions are also evaluated with no environment and `egress.allowedHosts` and `egressLockHosts` are refused; `sessionIsolationLevel.perSlotScopes` reports the fallback as `false` (D14);
- pod-wide eviction and pod-wide failure;
- contention for CPU, memory, disk, and network.

The same list replaces the text of `sessionIsolationLevel.residualStateWarning` for such a pod. Whether a session's pod is shared is reported by `sessionIsolationLevel.sharedPod`, and whether its slot has its own `netagent` scope by `sessionIsolationLevel.perSlotScopes`, both of which [`placement-design.md`, "PM-4"](placement-design.md#pm-4-placement-requirements) defines; this design adds no field of its own. A tenant whose security settings set `placement.allowSharedPod: false` never reaches such a pod ([`tenant-security-settings-design.md`](tenant-security-settings-design.md)).

## PL-10 Project quotas

**What a project quota gives.** XFS and ext4 keep a usage count and a limit for each project ID, a number every inode carries. On a filesystem mounted with `prjquota`, a write that would take a project past its hard limit fails at `write()` with `ENOSPC` on XFS or `EDQUOT` on ext4, with the bytes already written intact, and `statfs` called by an unprivileged process on a directory that carries the project's ID and the inherit flag reports the project's limit as the size and its usage as the used blocks. Bytes under a directory of mode `000` count. A project limit is independent of the kubelet's `sizeLimit`: with the limit below `sizeLimit`, the writes stopped at the limit and the kubelet evicted nothing. The AWS spike of 2026-11-14 measured each of these on XFS and on ext4, under runc with and without user namespaces, gVisor's default mount, and Kata virtio-fs ([its report, "Test 2: project quotas"](evidence/agent-pod-layout-design/attribution-and-quota-spike/RESULTS.md#test-2-project-quotas)) **[measured]**. A project quota slightly below a slot volume's `sizeLimit` therefore bounds the slot's own writes before the kubelet's count reaches the limit, and the adapter reads the volume's use from one `fstatfs` call that counts every byte, the bytes in a directory its owner cannot list included. Where it applies, it settles O9's residual risk.

**The owner's decision (D25).** On 2026-11-14 the owner answered "Adopt the automatic project-quota mode": a node agent detects project quotas on each node and assigns them to slot volumes, and the adapter detects a quota-bound volume by itself and uses it in place of a walk. Nothing needs configuring where a node offers project quotas, and every other node keeps the methods of "PL-5".

**Where quotas bound a volume.** A project quota is trusted as a bound only where the slot cannot take its own files out of the project, and only where the volume is a directory on the node's filesystem **[design]**:

| Runtime and mode | Volumes the agent assigns | Watch method for the volume |
| :-- | :-- | :-- |
| runc with user namespaces (`hostUsers: false`) | `slot-<n>-workspace`, `slot-<n>-session`, and `slot-<n>-tmp` | The quota, read with `fstatfs`. A slot's `FS_IOC_FSSETXATTR` on its own files fails with `EINVAL` under user namespaces **[measured]**. |
| runc without user namespaces (`userNamespaces: disabled`, [PM-1](placement-design.md#user-namespaces-on-the-standard-class)) | None | "PL-5"'s methods. The slot owns its files in the initial user namespace and can set their project ID to another value or clear the inherit flag with `FS_IOC_FSSETXATTR`, after which its bytes stop counting, on XFS and on ext4 **[measured]**. |
| gVisor (`sandboxed` and `gvisor-monitored`), default mount | `slot-<n>-tmp` | The quota. The ioctl is not supported inside the sandbox (`ENOTTY`), so the slot cannot change the project **[measured]**. |
| gVisor, pod-share mount | None: IC-8's annotation puts `slot-<n>-workspace` and `slot-<n>-session` on it | `statfs` of the sentry's volume ("PL-5", method 1), which counts every byte, those under a mode-`000` directory included **[measured]**. The volume is one `.gvisor.filestore.*` file on the node, which exists before the agent can act and keeps project 0, and the sentry's `statfs` reports an 8 EiB size whatever limit the file's project carries **[measured]**. |
| Kata virtio-fs (`kata.emptyDirMode: virtio-fs`) | `slot-<n>-workspace`, `slot-<n>-session`, and `slot-<n>-tmp` | The quota. The ioctl is not supported in the guest (`ENOTTY`) **[measured]**. |
| Kata block-plain (`kata.emptyDirMode: block-plain`) | None | The guest's `statfs` ("PL-5", method 1), which tracks the volume's usage exactly **[measured]**. A quota on the volume's `disk.img` stopped the VM when the guest reached it: the pod failed **[measured]**. |

**The node agent.** `lenny-quota-agent` is a DaemonSet in `lenny-node-agents`, a named node agent of [PM-5](placement-design.md#named-node-agents) that runs on every node of every agent class, with each agent class's taint and `lenny.dev/tenant` with `operator: Exists` among its tolerations, so it also runs on dedicated nodes **[design]**:

- **Container.** One container of the image `quotaAgent.image`, a digest-pinned static Go binary built without cgo and with no shell. It runs as UID 0 with every capability dropped except `CAP_SYS_ADMIN`, `privileged: false`, `allowPrivilegeEscalation: false`, the `Localhost` seccomp profile `lenny/quota-agent.json` of **Seccomp profile** below, and a read-only root filesystem. `CAP_SYS_ADMIN` under RuntimeDefault was enough to read and set project limits with `quotactl_fd` **[measured]**; the spike assigned project IDs from a privileged container and ran no custom profile, so the assignment under `CAP_SYS_ADMIN` alone and every call under the agent's own profile are owed to validation. The agent runs as UID 0 because the volume directories it changes are owned by root, so the ioctl needs no `CAP_FOWNER`.
- **Mount.** A `hostPath` of `<quotaAgent.kubeletRootDir>/pods`, `/var/lib/kubelet/pods` by default, with `HostToContainer` propagation, read-write because `FS_IOC_FSSETXATTR` refuses a read-only mount with `EROFS` **[inference]**. It needs no block device, no `/etc/projects` entry, and no other host path **[measured]**. The agent writes no file through the mount: it opens the slot volume directories of Lenny agent pods alone, with `openat2` under `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`, and calls `ioctl` and `quotactl_fd` on them.
- **API access.** The ServiceAccount `lenny-quota-agent` holds `get`, `list`, and `watch` on `pods` in each agent namespace, through a Role there, which it uses with a field selector on its own node, and `get` and `patch` on `nodes` through a ClusterRole. The ValidatingAdmissionPolicy `lenny-quota-agent-node-label` admits the agent's node writes only on the node named in its pod-bound token's `authentication.kubernetes.io/node-name` claim, and only when the write changes the label `lenny.dev/project-quota`, the annotation `lenny.dev/quota-agent-status` of **Status annotation** below, or both, and nothing else ([PM-6](placement-design.md#admission)). The token claim is owed to validation on the supported Kubernetes versions. The agent holds no other right.
- **No port (D29).** The agent serves no port and opens no listening socket: its seccomp profile lists no `bind`, `listen`, or `accept4` **[design]**. Its NetworkPolicy admits no ingress, and its egress goes to the API server alone. It reports its figures through its own node's status annotation, which `lenny-ops` reads (**Status annotation** below).
- **Resources.** `quotaAgent.resources`: a request of 10m CPU and 32 MiB, with a 64 MiB memory limit.

**Seccomp profile (D28).** The chart ships a seccomp profile for the agent, and the agent's container sets `seccompProfile` to `type: Localhost` with `localhostProfile: lenny/quota-agent.json` **[design]**. The profile fails every call it does not list with `EPERM`, and it lists only these:

- `execve`, which the container runtime calls after it installs the profile to start the agent's binary. Once the agent has entered its Landlock domain, below, the domain denies the execution of every file.
- The calls of the Go runtime: memory mapping, futexes, signals, timers, `epoll`, and thread creation through `clone` with no namespace flag in its flags argument. `clone3`, whose flags the filter cannot read, fails with `ENOSYS`.
- The filesystem calls of its work: `openat` and `openat2` for its own files and for directories beneath its mount, `getdents64`, `statx`, `newfstatat`, `fstatfs`, `read`, and `close`; `ioctl` with only `FS_IOC_FSGETXATTR` and `FS_IOC_FSSETXATTR` as the request; and `quotactl_fd` with only the project-quota commands `Q_XGETQSTATV`, `Q_XGETQUOTA`, `Q_XGETNEXTQUOTA`, and `Q_XSETQLIM`, so the agent cannot turn the filesystem's quotas off.
- The Landlock calls `landlock_create_ruleset`, `landlock_add_rule`, and `landlock_restrict_self`, and `prctl`.
- The calls of its API client over TCP: `socket` for `AF_INET` and `AF_INET6`, `connect`, `getsockopt`, `setsockopt`, `getsockname`, `getpeername`, `sendmsg`, `recvmsg`, `write`, and `read`. The profile lists no `bind`, `listen`, or `accept4`, so the agent can open no listening socket (D29).

Every other call fails, among them `mount`, `umount2`, `pivot_root`, `fsopen`, `fsmount`, `move_mount`, `open_tree`, `bpf`, `unshare`, `setns`, `ptrace`, `process_vm_readv`, `perf_event_open`, `keyctl`, `add_key`, `request_key`, `open_by_handle_at`, `init_module`, `finit_module`, `kexec_load`, `execveat`, and the path-based `quotactl`. `CAP_SYS_ADMIN` therefore reaches only what the listed calls reach. The kubelet reads a `Localhost` profile from the `seccomp` subdirectory of its root directory on the node, so the chart renders the profile into the ConfigMap `lenny-quota-agent-seccomp`, and the agent's pod runs an init container, `seccomp-install`, of the agent's image. It mounts the ConfigMap read-only and a `hostPath` of `<quotaAgent.kubeletRootDir>/seccomp/lenny` read-write, and no other host path; it writes the profile to `quota-agent.json` there, replacing an older copy by rename, and exits. It runs as UID 0 with every capability dropped, the RuntimeDefault profile, and a read-only root filesystem. When the file is missing or does not parse, the kubelet fails the agent's container at creation, so the agent never runs without its profile **[inference]**. A chart upgrade that changes the profile changes the ConfigMap's hash in the pod template, so the DaemonSet rolls and each new pod installs the new profile. `lenny-pod-security` refuses an agent pod whose agent container lacks this profile ([PM-6](placement-design.md#admission)). The owner confirmed the delivery through an init container, rather than through the Security Profiles Operator or the node image, on 2026-11-14 (D28).

**Landlock self-restriction (D28).** Before the agent calls the API server or opens anything beneath its mount, it restricts itself with Landlock **[design]**. It reads the kernel's Landlock ABI version with `landlock_create_ruleset` and the version flag, creates a ruleset that handles every filesystem access right that version defines, and adds these rules: `LANDLOCK_ACCESS_FS_READ_DIR` alone beneath its mount of the kubelet's `pods` directory, and `LANDLOCK_ACCESS_FS_READ_FILE` alone on its service-account token directory and on `/proc/self/mountinfo`. Every other access is denied. The ruleset handles no network access right, because the seccomp profile already refuses every call that opens a listening socket, and the API client needs `connect`. It then calls `landlock_restrict_self` on every thread of the process through Go's `syscall.AllThreadsSyscall`, because a Landlock domain binds the thread that enters it and the threads that thread later creates, and the Go runtime has started several threads by then. `allowPrivilegeEscalation: false` has already set `no_new_privs`, which the call requires. Beneath the mount the agent can then open a directory and list it, and call `FS_IOC_FSGETXATTR`, `FS_IOC_FSSETXATTR`, and `quotactl_fd` on the directory's descriptor, which Landlock does not mediate on a directory; it can open no file there for reading, writing, or execution, and can create, remove, rename, or link no entry **[inference]**. A process cannot leave a Landlock domain it has entered, so code that takes over the agent after start-up keeps these limits.

Landlock needs Linux 5.13 or later with Landlock among the kernel's active security modules, and the quota calls already need 5.14. When `landlock_create_ruleset` fails, with `ENOSYS` where the kernel lacks Landlock or `EOPNOTSUPP` where it is built in and not active, the agent acts on `quotaAgent.requireLandlock`:

- `true`, the default: it logs the reason, labels nothing, assigns nothing, and exits with an error, so its pod never becomes ready and `QuotaAgentUnavailable` fires. The node's pods keep "PL-5"'s methods. The owner confirmed this default on 2026-11-14 (D28).
- `false`: it logs a warning, sets `lenny_quota_agent_landlock` to 0, and runs without the restriction, under its seccomp profile alone.

**Detection.** At start and every `quotaAgent.recheckSeconds`, 300 s by default, the agent reads the superblock options of the filesystem that holds its mount from `/proc/self/mountinfo`, which must be `xfs` with `prjquota` or `pquota`, or `ext4` with `prjquota`, and reads the quota state with `quotactl_fd(Q_XGETQSTATV)`, which must report project accounting and enforcement on **[design]**. Both checks answered in the spike's agent, and the same quota calls from an unprivileged slot failed with `EPERM` **[measured]**. `quotactl_fd` needs Linux 5.14 or later. The agent labels its node `lenny.dev/project-quota=enforcing` when both checks pass and `lenny.dev/project-quota=unavailable` otherwise. The label is a report: no pod selects on it, and the adapter does not read it.

**Assignment.** The agent watches the pods of its node in the agent namespaces. For each Lenny agent pod whose runtime and mode the table above lists with volumes, once the kubelet has created the pod's volume directories under `pods/<uid>/volumes/kubernetes.io~empty-dir/`, it handles each listed volume once **[design]**:

1. It reads the directory's project ID and inherit flag with `FS_IOC_FSGETXATTR`. When the kubelet has assigned the directory a project, it keeps that ID. The kubelet's `LocalStorageCapacityIsolationFSQuotaMonitoring` feature gate assigns user-namespace pods IDs from 1048577 upward with the inherit flag and an effectively unlimited limit, and reads each volume's use from its own ID **[measured]**. The agent never moves such a directory to another project: moving one made the kubelet report 0 bytes for a volume that held 120 MiB **[measured]**, which would stop the kubelet's `sizeLimit` eviction from ever firing for it.
2. When the directory has no project, the agent assigns it a free Lenny project ID with the inherit flag through `FS_IOC_FSSETXATTR`. Lenny's IDs come from `quotaAgent.projectIds`, 1000000 to 1048575 by default, below the kubelet's range. An ID is free when no volume directory on the node carries it and the filesystem holds no usage and no limit for it, which the agent reads with `quotactl_fd(Q_XGETNEXTQUOTA)`.
3. It sets the project's hard block limit with `quotactl_fd(Q_XSETQLIM)` to the volume's `sizeLimit`, read from the pod's specification, less `quotaAgent.limitMarginPercent`, 2% by default, rounded down to 4 KiB. The kubelet left a Lenny limit on its own project in place for the 30 s the spike watched **[measured]**.

Entries created in a directory before its assignment keep their project and stay outside its count. The adapter's rule below accounts for them, so the agent assigns a volume whenever it reaches it.

**Deletion.** When a pod is deleted and the kubelet has removed its volume directories, the agent clears the hard limit of each Lenny project ID it assigned to them and returns the ID to the free range once the filesystem reports no usage for it **[design]**. It leaves a kubelet project alone, because the kubelet removes that quota when the pod is deleted **[measured]**. The agent keeps no state of its own: at start it rebuilds its assignments from the project IDs on the node's slot volume directories, and it clears every limit in its range whose directory no longer exists. A pod's volumes are not deleted while the pod runs.

**Status annotation (D29).** The agent writes its figures as the annotation `lenny.dev/quota-agent-status` on its own node, a JSON object of at most 1 KiB **[design]**:

```json
{ "detection": "enforcing", "landlock": "enforced", "volumesBound": 12, "assignmentErrors": 0, "writtenAt": "2026-11-15T09:30:00Z" }
```

- `detection` is the result of the last detection, `enforcing` or `unavailable`, which the agent also writes as the node's label.
- `landlock` is `enforced` while its Landlock restriction holds, and `absent` while it runs without one under `quotaAgent.requireLandlock: false`.
- `volumesBound` is the number of slot volumes on the node that carry a hard limit the agent set.
- `assignmentErrors` counts the assignments that failed since the agent started, and starts again at 0 when the agent restarts.
- `writtenAt` is the time of the write.

The agent writes the annotation in the same patch as the label, at start once its Landlock domain holds and after each detection, every `quotaAgent.recheckSeconds`, so `writtenAt` advances at least that often. An agent that refused to start for want of Landlock writes nothing. `lenny-quota-agent-node-label` admits the annotation beside the label and nothing else, and refuses a value over 1 KiB ([PM-6](placement-design.md#admission)). The figures are counts for the node and name no pod, volume, or tenant. `lenny-ops` reads them, exports them as metrics, and raises `QuotaAgentUnavailable` (**Monitoring** below).

**What the adapter does.** The adapter and the agent share no channel and no register. The adapter reads the kernel's figure itself **[design]**:

- **When it decides.** The adapter chooses each slot volume's method when the volume is empty: after the start-up Sweep (step 6 of the start-up order in "PL-5"), and after each slot release has passed its emptiness check. Every byte the next session or warm-up checkout writes is then created under the volume's root and inherits its project, so the project counts the whole volume. A volume that the agent reaches later keeps the method chosen for it until the next release, and the quota it gains in the meantime only adds a bound below `sizeLimit`. The owner confirmed this rule on 2026-11-14 (D25).
- **How it decides.** It calls `fstatfs` on the slot's broker-passed root descriptor of the volume, which the broker serves for `/workspace`, `/session`, and `/tmp` ([SI-5](session-isolation-design.md#si-5-the-supervisor-file-descriptor-broker)). The volume is quota-bound when the size `fstatfs` reports is below the size it reports on `/adapter/assets`, a volume on the same node filesystem that no Lenny project bounds, and the kubelet's own project limits exceed the node filesystem, so `statfs` still reports the whole filesystem there **[measured]**. On a pod of the `standard` member rendered without user namespaces the adapter never takes a volume as quota-bound, whatever `fstatfs` reports.
- **What it reads.** On a quota-bound volume the watch reads the used blocks from `fstatfs` at each `adapter.diskWatchIntervalSeconds` and keeps no running total, runs no walk, and runs no recalibration walk for that volume. It trips at `adapter.diskWatchThresholdPercent` of the volume's `sizeLimit`, as PLR-23 states. When a quota-bound volume's reported size rises to the node filesystem's, because its limit was cleared, the watch moves that volume to "PL-5"'s other methods at once with a recalibration walk.

**What the slot meets.** The watch fails the slot's session at the threshold, 90% of `sizeLimit` by default, as on every other volume. A writer faster than the watch's interval meets `ENOSPC` on XFS or `EDQUOT` on ext4 at the project's limit, at `write()`, and the pod is not evicted for that volume **[measured]**. The chart refuses a `quotaAgent.limitMarginPercent` whose limit, 100% less the margin, is at or below `adapter.diskWatchThresholdPercent`, so the watch trips before the limit at every allowed threshold. Under gVisor's default mount the project's usage ran ahead of the bytes written while files were still being extended, 63.9 MiB for 40 MiB, and matched them again at the limit **[measured]**, so the watch there trips early rather than late.

**Failure behaviour.** Every failure leaves the pod on "PL-5"'s methods, as before this section **[design]**:

- `quotaAgent.mode: off`, which renders no DaemonSet; no agent pod on the node, or one that is not ready; and a node labelled `unavailable`, whose filesystem lacks `prjquota` or enforcement, or whose kernel lacks `quotactl_fd`: no volume is assigned, `fstatfs` reports the node filesystem, and the watch uses "PL-5"'s methods.
- An assignment that fails: the agent counts it in the annotation's `assignmentErrors` and leaves the volume alone.
- An agent that stops while pods run: the kernel keeps every project and limit it set, so those volumes stay bound, and the restarted agent rebuilds its assignments. Limits of pods deleted meanwhile are cleared at its start.
- An agent that reaches a pod late: the volume keeps "PL-5"'s methods until its next release, under "When it decides" above.

**Chart values.**

| Value | Default | Meaning |
| :-- | :-- | :-- |
| `quotaAgent.mode` | `auto` | `auto` renders the DaemonSet, which assigns quotas on every node where it detects them; `off` renders nothing. |
| `quotaAgent.image` | The release's image | The agent's digest-pinned image. |
| `quotaAgent.kubeletRootDir` | `/var/lib/kubelet` | The kubelet's root directory; the agent mounts its `pods` subdirectory. |
| `quotaAgent.projectIds.first`, `quotaAgent.projectIds.last` | 1000000, 1048575 | Lenny's project ID range. The chart refuses a value at or above 1048576, the start of the kubelet's range, and a `first` above `last`. |
| `quotaAgent.limitMarginPercent` | 2 | The margin below `sizeLimit`, from 1 to 10. The chart refuses a value whose limit is at or below `adapter.diskWatchThresholdPercent`. |
| `quotaAgent.recheckSeconds` | 300 | How often the agent repeats its detection. |
| `quotaAgent.resources` | 10m CPU and 32 MiB requested, 64 MiB memory limit | The agent's resources. |
| `quotaAgent.requireLandlock` | `true` | `true` makes the agent refuse to start on a kernel without Landlock; `false` lets it run there without its Landlock restriction (D28). |

**Monitoring (D29).** `lenny-ops` reads the status annotation of every node of an agent class in its continuous check ([PM-6](placement-design.md#continuous-check-in-lenny-ops)), every `ops.placement.checkIntervalSeconds`, and exports these series, each with a `node` label: `lenny_quota_agent_node_enforcing` (1 when `detection` is `enforcing`), `lenny_quota_agent_landlock` (1 when `landlock` is `enforced`, 0 when it is `absent`), `lenny_quota_agent_volumes_bound`, `lenny_quota_agent_assignment_errors_total`, and `lenny_quota_agent_status_age_seconds`, the time since `writtenAt`. The agent itself exports nothing. The adapter exports `lenny_slot_disk_watch_volumes` with a `method` label of `quota`, `statfs`, `tracker`, or `walk`. `lenny-ops` raises the alert `QuotaAgentUnavailable`, at warning, while `quotaAgent.mode` is `auto` and a Ready node of an agent class has no status annotation or one whose `writtenAt` is older than three times `quotaAgent.recheckSeconds`, 15 minutes at the defaults, which includes a node whose agent refused to start for want of Landlock.

**Cost and exposure.** The agent is one small pod per agent node, whose node cost reaches no billing event, as for every DaemonSet ([`billing-resource-attribution-design.md`, "Scope"](billing-resource-attribution-design.md#scope)); a project quota changes no ephemeral-storage request, so it changes no bill. Its mount reaches every pod's volumes on its node, the projected service-account tokens and Secret volumes of other pods included. Its seccomp profile refuses `mount` and the other calls through which `CAP_SYS_ADMIN` reaches beyond its work, and its Landlock domain lets it open no file beneath the mount (D28). A compromise of the agent's process can therefore list directory names, read and change the project IDs and limits of its node's volumes, which can fail a volume's writes early, and patch its own node's label, and it reads no file content beneath the mount. It serves no port, and its status annotation holds counts for its node that any reader of `Node` objects can see. Where the agent runs without Landlock under `quotaAgent.requireLandlock: false`, a compromise of it reads every volume on its node. "Limits" states the exposure, and posture reports the pools whose volumes it bounds ([`security-oversight-design.md`, "Posture"](security-oversight-design.md#posture)).

**Posture.** `lenny-ops` computes each pool's `diskQuota` in its continuous placement check ([PM-6](placement-design.md#continuous-check-in-lenny-ops)): `notApplicable` when the pool's runtime and mode take no part under the table above, `none` when `quotaAgent.mode` is `off` or no node of the pool's class is labelled `enforcing`, `partial` when some of them are, and `enforced` when every node of the class is. It reports node coverage, which bounds every pod the agent reached in time, and does not report each pod's assignment, whose method `lenny_slot_disk_watch_volumes` reports.

## Worked example

A pool `team-agents` runs Claude Code with `sessionPolicy.maxConcurrentSessionsPerPod: 2` and `sessionPolicy.acknowledgeSharedPod: true` on runc nodes. Its Runtime sets `env: CLAUDE_CONFIG_DIR=/session/claude` and a default clone of `github.com/acme/monorepo` at `path: repo`, which a store on the pool's warm list serves.

1. The controller creates a pod with slot count 2, rendered with `hostUsers: false`, the placement fields of PM-5, and an ephemeral-storage request equal to the sum of its disk-backed `sizeLimit` values plus its class's own 1 GiB. `lenny-bin-stage` stages the supervisor, `lenny-materialize`, and `git`. `netagent` starts, and its startup probe passes after its slot-attribution check. `lenny-store-fill` fills the monorepo store and its pristine tree through `netagent` under its own UID and exits. Then `adapter`, `runtime-0`, `runtime-1`, and `keepalive` start.
2. The adapter checks `/proc/self/uid_map` and fills `/adapter/assets`. Each supervisor pins its broker roots, writes its canaries, and sends `ready`. The adapter pins each slot's roots, sees each canary through `/adapter/slots/<n>/`, runs the reflink probe, sends the start-up `sweep`, and finds each slot's volumes empty.
3. Each slot's helper stages a warm-up checkout of `repo` under `/workspace/.lenny-prestage`, cloning its files from the pristine tree by reflink, and refreshes its index. The adapter reports READY. No runtime process is running.
4. Alice's session binds to slot 0 at a newer monorepo commit. `lenny-materialize`, run by slot 0's supervisor as slot 0's UID, renames the staged tree to `/workspace/repo`, fetches the difference through `netagent`, checks out the newer commit incrementally, and writes the rest of her plan, including a Python virtual environment at `/workspace/.venv`. Her setup commands run. The supervisor then launches Claude Code in `/workspace`, which writes its transcript under `/session/claude/projects/-workspace/`, and keeps its npm cache under `/tmp/home`.
5. A checkpoint captures `/workspace` and `/session` in one snapshot through slot 0's broker, staging large files in `/adapter/spool/0/checkpoint/`.
6. Alice derives a new session `from: latest`. It binds to slot 1 of another pod. The restore writes the workspace into that slot's `/workspace` and the session state into its `/session`, and the helper removes the staged tree there, which the session does not need. `/workspace/.venv/bin/python` still names `/workspace/.venv`, so the environment works, and Claude Code finds its project directory under the same key.
7. Alice's agent runs `mv /workspace /w`, which fails with `EBUSY`. It emits a `file` part for `out/report.pdf`, which the adapter exports from `/workspace/out/report.pdf` under MD-18.

## Limits

- **Images cannot ship workspace content.** A file an image places under `/workspace`, `/session`, or `/lenny` is hidden on every pod.
- **Pod-wide eviction remains where no project quota applies.** A write burst that outruns the per-slot disk watch evicts every slot's session, and `/tmp` joins `/workspace` and `/session` among the volumes where that can happen. The watch measures each volume once per interval, so a writer that adds more than the 10% margin within one interval, plus the time of a pass, reaches the kubelet's limit first. On a volume that a project quota bounds, the writer meets `ENOSPC` or `EDQUOT` at the quota instead ("PL-10").
- **The watch costs broker work where it walks.** A walk pass goes through the slot's broker, about 2.6 s for a 200,000-entry workspace on Kata virtio-fs **[measured]**, and competes with the checkpoint's walk for the same supervisor. Where `statfs` or the tracker's running total applies, only the recalibration walk costs this.
- **The running total trusts the tracker between walks.** A change the tracker does not report leaves the total wrong until the next recalibration walk, 300 s by default, and a writer can pass the kubelet's limit in that window.
- **More reserved disk.** `/session` and `/tmp` on disk, the pod-wide spool of 16 GiB by default, and the pristine trees in the store volume raise each pod's ephemeral-storage request, which billing decision 10 bills.
- **Reserved names are skipped.** A session that creates an entry named like a reserved name at the top of `/workspace` loses it from its checkpoints, downloads, and exports.
- **Kata block-plain carries a group.** Every process on such a pod carries the volume GID, so files of mode `0640` and `0660` in the shared volumes are readable from every slot, and a broker restore drops setgid bits from directories **[measured]**.
- **A harness's start is in the session's start.** No runtime process is started before its session, so the first turn waits for the harness to start.
- **The run volume and `lenny-bin` carry no size limit.** The run volume is memory-backed and holds only the adapter's small files, and `lenny-bin` holds the release's fixed binaries, so neither counts in the ephemeral-storage request.
- **Bytes in a directory its owner cannot list.** A session can write files into a directory and then set the directory's mode to deny its owner read, such as `0300` or `0000`. The walk and the broker list a directory as the slot UID, so a walk misses those bytes, and a recalibration walk drops them from a running total, while the kubelet still counts them and evicts the whole pod. `statfs` counts them where a project quota bounds the volume and where the runtime reports the volume: under gVisor's pod-share mount and on Kata `block-plain` **[measured]**. The owner accepted the miss as a residual risk of shared pods (O9, D20), and project quotas settle it on runc with user namespaces, gVisor's `/tmp`, and Kata virtio-fs (D25). It remains on runc without user namespaces, on a node without project quotas or without a ready `lenny-quota-agent`, and on a volume the agent reaches during a session, until that slot's next release.
- **The quota agent reaches every volume on its node.** `lenny-quota-agent` runs as UID 0 with `CAP_SYS_ADMIN` and a read-write mount of the kubelet's `pods` directory, which holds every pod's volumes on the node, other pods' service-account tokens and Secret volumes included. It opens only slot volume directories and reads no file. Its seccomp profile and its Landlock domain leave a compromise of it able to list directory names and to read and change project IDs and limits on its node, and unable to read a file beneath the mount (D28). On a kernel without Landlock, where an operator sets `quotaAgent.requireLandlock: false`, a compromise of it reads every volume on its node ("PL-10").
- **Kata `block-plain` volumes run about 53 MiB above the guest's figure in the kubelet's count.** The guest's `statfs` leaves out the ext4 metadata the image holds **[measured]**. The watch adds `kata.blockPlainOverheadBytes`, 64 MiB by default, to cover it (O10, D26), and a gap larger than the allowance, which a larger node filesystem could produce, is owed to validation.

## Alternatives rejected

- **Keeping the embedded model for first-party runtimes.** It kept the agent inside the adapter's process with the adapter's credentials, a second blueprint with its own checkpoint path and broker transport, and a row in every design that touches the pod, for a latency gain no runtime in the tree needed.
- **Keeping pre-launched runtimes.** A pre-launched process saved one harness start per session, at the cost of a pod state, a demotion path, a circuit breaker, refusals on pools where it could hold files open, and a second meaning of "warm pod" (D9).
- **`/workspace/current/` as the working directory** (the D10 layout). A directory nested under the volume root is not a mount point, so the session could rename it, and it adds a level that every path translation and runtime has to carry. The owner replaced it the same day.
- **A session identifier in the working directory.** It breaks absolute paths on every derive, as "Problem" states, and separates nothing once each slot has its own volumes.
- **`/session` on tmpfs.** "PL-3" lists the memory charging, the out-of-memory risk, and the lost reflink path.
- **`HOME` under `/session`.** Package caches and tool state would be checkpointed with every snapshot and count against the session state limit.
- **`HOME=/tmp`.** Revision 1's recommendation. The owner chose `/tmp/home` with mode `0700`, which keeps dotfiles out of the scratch directory and gives tools that check their home's mode what they expect.
- **Path variables or manifest fields.** O1 gives the reasons.
- **Keeping `/artifacts` for future use.** Nothing reads it, and MD-18 already moves a runtime's files to the user.
- **Aliases for the renamed pool fields.** No deployment depends on the old names, and an alias would keep two names for one setting in the schema, the documentation, and every validator (D7).
- **`statfs` for the disk watch on every runtime.** It reports the whole node filesystem on runc **[measured]**, so it serves only where a project quota bounds the volume or the runtime reports the volume (O8, D25).
- **Moving a volume off the kubelet's project.** The kubelet reads a volume's use from its own project ID, and a volume moved to another project read 0 bytes while it held 120 MiB **[measured]**, which would disable the kubelet's eviction for it. The agent keeps the kubelet's ID and sets the limit on it (D25).
- **A privileged quota agent.** `CAP_SYS_ADMIN` alone read and set project limits under RuntimeDefault **[measured]**, and the owner asked for an agent that is not privileged (D25).
- **A quota on gVisor's pod-share filestore or on Kata `block-plain`'s `disk.img`.** The filestore file can be moved into a project, which then stops writes, but the sentry's `statfs` keeps reporting an 8 EiB size, so the slot never reads the limit, and the sentry's `statfs` already counts every byte. A quota on `disk.img` stopped the VM at the limit **[measured]** (D25).
- **Trusting a quota on runc without user namespaces.** A slot there takes its own files out of the project with `FS_IOC_FSSETXATTR`, and the kubelet still counts them, so the slot trades its own clean failure for a pod-wide eviction **[measured]** (D25).
- **The adapter reading the node label.** The label says what the node offers. It does not say whether the agent reached a given pod in time, and `fstatfs` on the volume says what bounds it.
- **The adapter as the store filler** (O5 (a)). It ran the pinned git on repositories an operator or a tenant admin named, at the UID that holds the pod's gateway credentials (D11).
- **A store-fill native sidecar for the pod's life.** The egress design's decision 61 (b) kept the container running so that it could delete withheld stores on request. The owner's feasibility conditions place it as an init container, and the adapter deletes through the group class of its read-write mount, so no container that parses repository data outlives the fill (D11).
- **Per-slot staging allowances.** No reliable largest upload is known ahead of time, so a per-slot allowance either wastes disk on every slot or refuses large uploads; one pod-wide spool with reserved capture budgets serves both (D13).
- **Skipping `lost+found` by name on Kata block-plain.** A slot can write into it through the volume GID, so a check that skips it would let a session leave data for the next one (D8).
