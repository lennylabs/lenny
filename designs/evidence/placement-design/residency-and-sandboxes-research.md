# Research: Kubernetes clusters across regions, and sandbox runtimes for AI agents

Date of research: 2026-11-15. Every claim carries a URL. Claims marked **[unverified]** come from a secondary source only, or from a search summary whose primary page could not be opened. Claims marked **[inference]** are this report's reasoning rather than a source's statement.

## Part 1: Kubernetes clusters that span regions

### 1.1 Managed offerings

Summary: of the hyperscalers, none runs one managed control plane with worker nodes in several of its own cloud regions. Each binds a cluster to one region and offers a multi-cluster product for multi-region work. Scaleway Kubernetes Kosmos is the one managed offering found that states multi-region nodes under one control plane. Several hosted-control-plane projects (k0smotron, Kamaji, Omni) let an operator attach remote nodes over a WAN.

### 1.2 Self-managed single cluster across regions

**etcd latency guidance.** The etcd defaults (100 ms heartbeat, 1000 ms election timeout) "should work well for installations on a local network." The heartbeat should be "around 0.5-1.5x the round-trip time", and "Election timeouts must be at least 10 times the round-trip time." The docs give 130 ms as a reasonable continental-US RTT and 350–400 ms for US–Japan. The election-timeout ceiling is 50 s, "which should only be used when deploying a globally-distributed etcd cluster." All members must use the same values ([etcd v3.6 tuning](https://etcd.io/docs/v3.6/tuning/)). Raft commits wait for a quorum, so every write pays the RTT to the nearest quorum member **[inference from Raft, consistent with [this summary](https://adhdecode-articles-1.pages.dev/articles/etcd/etcd-multi-region-cluster/)]**.

**Vendor thresholds.** Red Hat's OpenShift etcd guidance for clusters that span data centers sets an etcd peer RTT below 100 ms (combined network and disk), and for multi-region needs it says to "deploy one cluster per region or site" and manage them with ACM ([OpenShift etcd: clusters that span data centers](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/etcd/guidance-for-clusters-that-span-data-centers)) **[unverified: the page returned 403; text is from a search summary]**. An older Red Hat stretch-cluster test reported that stretched OpenShift clusters above 5 ms RTT failed health checks for persistent applications ([Red Hat blog](https://www.redhat.com/en/blog/metro-area-openshift-stretch-cluster-how-to-survive-an-outage-and-live-to-tell-about-it)) **[unverified: search summary]**. kMetal requires ≤10 ms between zones that hold etcd members ([kMetal](https://kmetal.clastix.io/docs/admin-guide/operations/stretched-clusters/)).

**Upstream Kubernetes position.** The multi-zone page describes a cluster spanning failure zones "typically where these zones fit within a logical grouping called a region", and recommends control-plane replicas across at least three zones. It does not discuss multi-region clusters ([Running in multiple zones](https://kubernetes.io/docs/setup/best-practices/multiple-zones/)).

**Kubelet to API server over a WAN.**
- The kubelet renews its node Lease every 10 s, retrying with backoff from 200 ms to 7 s; `.status` updates default to every 5 minutes ([Node status](https://kubernetes.io/docs/reference/node/node-status/)).
- If Ready stays Unknown past `node-monitor-grace-period`, the controller adds `node.kubernetes.io/unreachable`. The same upstream page states the default as both 40 s and 50 s ([Node status](https://kubernetes.io/docs/reference/node/node-status/)); AWS lists 40 s for EKS ([EKS hybrid pod failover](https://docs.aws.amazon.com/eks/latest/best-practices/hybrid-nodes-kubernetes-pod-failover.html)).
- Pods get a default `unreachable:NoExecute` toleration of 300 s, so eviction starts after roughly grace period plus 5 minutes. When 55% or more of a zone's nodes are unreachable (`unhealthy-zone-threshold`), evictions in that zone are cancelled; when every zone is down, the controller enters full-disruption mode and evicts nothing ([EKS hybrid pod failover](https://docs.aws.amazon.com/eks/latest/best-practices/hybrid-nodes-kubernetes-pod-failover.html)).
- During a partition, running pods keep running, but "you cannot perform mutating operations on your nodes or workloads until the connection is restored." A kubelet that restarts during a partition cannot start its pods because it cannot fetch them from the API server; only static pods restart ([same page](https://docs.aws.amazon.com/eks/latest/best-practices/hybrid-nodes-kubernetes-pod-failover.html)).
- Without `topology.kubernetes.io/zone` labels, all nodes form one implicit zone, which changes the eviction outcome ([same page](https://docs.aws.amazon.com/eks/latest/best-practices/hybrid-nodes-kubernetes-pod-failover.html)). A cross-region cluster has to label regions as zones (or the zone label must reflect real failure domains) for this logic to behave **[inference]**.
- API server to kubelet traffic (exec, logs, port-forward, webhooks to pod IPs) needs a reverse path. Hosted-control-plane projects use Konnectivity, where the node-side agent dials out ([Kamaji Konnectivity](https://kamaji.clastix.io/concepts/konnectivity/)). EKS Hybrid Nodes route the control plane to node and pod CIDRs through the VPC ([hybrid nodes networking](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-networking.html)).

**CNI options.**
- *Single cluster with an encrypted overlay.* Cilium WireGuard encrypts cross-node pod traffic; host-to-host traffic needs `encryption.nodeEncryption=true` ([Cilium WireGuard](https://docs.cilium.io/en/stable/security/network/encryption-wireguard/)). Kilo (Kosmos) and KubeSpan (Talos) are WireGuard meshes built for nodes in several networks ([Kosmos blog](https://blog.scaleway.com/best-practices-to-configure-a-multi-cloud-kubernetes-cluster/), [KubeSpan](https://docs.siderolabs.com/talos/v1.12/networking/kubespan)).
- *Cilium Cluster Mesh* connects separate clusters (one per region). Each cluster needs a unique name and ID; WireGuard-enabled clusters can be meshed, and clustermesh-apiserver distributes the WireGuard keys ([Cilium WireGuard](https://docs.cilium.io/en/stable/security/network/encryption-wireguard/)). Cluster Mesh keeps each region's control plane local, so it is the multi-cluster alternative to a stretched cluster **[inference]**.

**Storage topology.** Block volumes are zonal: an EBS volume attaches only to an instance in its AZ, and `WaitForFirstConsumer` binding creates the volume in the zone where the pod is scheduled ([AWS re:Post EBS mounts](https://repost.aws/knowledge-center/eks-troubleshoot-ebs-volume-mounts), [Portworx on volume node affinity](https://portworx.com/knowledge-hub/what-is-a-volume-node-affinity-conflict/)) **[unverified: secondary or search summary]**. A pod with a PV cannot move to another region; its data has to be copied at the application level **[inference]**. Object storage (Lenny's checkpoint target) is regional per bucket, so a cross-region pod that writes to a remote bucket pays cross-region transfer on every checkpoint **[inference]**.

**Cross-region egress cost.** AWS inter-region transfer is commonly $0.01–$0.02/GB from US, Canada, and Europe regions, and higher from some regions (one calculator lists up to $0.138/GB from São Paulo), billed to the sending side in each direction ([costgoat AWS data transfer](https://costgoat.com/pricing/aws-data-transfer), [Redress Compliance](https://redresscompliance.com/aws-inter-region-transfer-costs-multiregion)) **[unverified: third-party pricing summaries; the AWS price page was not read]**. GCP and Azure inter-region rates were not retrieved **[unverified]**. In a stretched cluster the recurring cross-region flows include etcd replication, kubelet lease and watch traffic, image pulls from a regional registry, webhook calls, metrics and logs, and any pod traffic across regions **[inference]**.

**Projects that target remote nodes under one control plane.**
- **KubeEdge** (CNCF graduated, 2024-10-15): CloudCore in the cloud, EdgeCore on nodes, a bidirectional message channel, and a node-local metadata cache so disconnected edges keep running pods and are not evicted ([CNCF announcement](https://www.cncf.io/announcements/2024/10/15/cloud-native-computing-foundation-announces-kubeedge-graduation/), [KubeCon 2019 slides](https://raw.githack.com/sbueringer/kubecon-slides/master/slides/2019-kubecon-na/KubeEdge%20%E2%80%93%20Kubernetes%20Native%20Edge%20Computing%20Framework%20-%20Jason%20Wu%20&%20Sean%20Wang,%20Futurewei%20-%202019KubeConNA-kubeedge-intro.pdf)). It replaces the kubelet with EdgeCore, so it is a different node agent **[inference from the architecture]**.
- **OpenYurt**: YurtHub runs on each node as a caching proxy between node components and kube-apiserver, giving node autonomy on unstable links ([OpenYurt mirror](https://sourceforge.net/mirror/openyurt/)). CNCF level is reported inconsistently **[unverified]**.
- **k3s**: no primary statement on WAN etcd was retrieved **[unverified]**.
- **Liqo** (Apache-2.0): peers separate clusters and represents a remote cluster as a virtual node; namespace offloading creates twin namespaces in remote clusters ([Liqo](https://github.com/liqotech/liqo)). It is multi-cluster.
- **Admiralty**: proxy pods on virtual-kubelet nodes in a source cluster, delegate pods in target clusters, and status fed back ([Admiralty package docs](https://pkg.go.dev/admiralty.io/multicluster-scheduler@v0.8.0), [scheduling concepts](https://github.com/admiraltyio/admiralty/blob/v0.15.0/docs/concepts/scheduling.md)). It is multi-cluster.
- **virtual-kubelet** is the library underneath Liqo and Admiralty ([virtual-kubelet](https://awesome.ecosyste.ms/projects/github.com%2Fvirtual-kubelet%2Fvirtual-kubelet)).

**Community consensus.** Practitioner and vendor sources agree that etcd should not span regions, that a stretched control plane suits metro distances only, and that multi-region deployments use one cluster per region with a fleet or federation layer ([discuss.kubernetes.io thread](https://discuss.kubernetes.io/t/k8s-deployment-best-practice-for-a-multi-region-application/7765), [ITNext wide cluster](https://itnext.io/3-reasons-to-choose-a-wide-cluster-over-multi-cluster-with-kubernetes-c923fecf4644), [ayedo](https://ayedo.de/en/posts/stretched-cluster-vs-multi-region-architekturentscheidungen-fur-maximale-resilienz/)). The workable single-cluster variant keeps etcd and the control plane in one region and puts only workers elsewhere (EKS Hybrid Nodes, Kosmos, Konnectivity-based hosted control planes, KubeEdge, OpenYurt). That variant accepts WAN latency on API calls, loss of mutation during partitions, and the eviction behaviour described above.

### 1.3 Residency in a cluster that spans regions

Everything stored through the Kubernetes API lives in etcd, which sits with the control plane. That includes pod specs (container args, env values, annotations, and labels), Secrets, ConfigMaps, Events (which carry free-text messages and object names), Leases, ServiceAccounts, and every custom resource ([Encrypting data at rest](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/)). Encryption at rest is off unless kube-apiserver runs with `--encryption-provider-config`, and it covers only the resources listed in the configuration; custom resources listed there are encrypted only for newly written objects on Kubernetes 1.26+ ([same page](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/)). Encryption does not move the data; the ciphertext still sits in the control-plane region, and a KMS provider adds a key location of its own **[inference]**.

Implications **[inference]**:
- A residency claim for a session must cover the control-plane region as well as the worker region, because any session-derived value written into a pod spec, annotation, label, Event message, CR status, or Secret is stored and backed up there.
- API server audit logs, controller logs, and managed-control-plane logging (CloudWatch, Cloud Logging) are emitted in the control-plane region.
- A claim such as "workspace bytes never leave region X" can hold with workers in X, if workspace data, checkpoints, and logs stay in regional stores in X. A claim such as "no data about the session leaves X" needs the control plane in X too, which means one cluster per residency region.
- AWS itself recommends Outposts local clusters (control plane on-premises) when residency mandates apply ([EKS on Outposts](https://docs.aws.amazon.com/eks/latest/userguide/eks-outposts.html)).

## Part 2: Sandbox runtimes for AI agent workloads

### 2.1 Per-technology findings

#### Firecracker
- **Type:** VMM (KVM microVM), Rust, Apache-2.0, developed at AWS with a published charter and maintainers file ([Firecracker repo](https://github.com/firecracker-microvm/firecracker)).
- **Isolation:** KVM guest with its own kernel, plus the jailer (cgroup, namespaces, privilege drop) and per-thread seccomp. Devices are virtio net, block, vsock, pmem, and entropy; virtio-PCI hotplug is a developer preview; the repo lists no GPU support. The repo now lists "Guests can run as Nitro Sandboxes" ([Firecracker repo](https://github.com/firecracker-microvm/firecracker)).
- **Kubernetes:** Kata supports Firecracker, but Kata with Firecracker has no virtio-fs, no device hotplug, no VFIO, and no CPU or memory hotplug ([Kata virtualization design](https://kata-containers.github.io/kata-containers/design/virtualization)) **[unverified: search summary]**. Kata 4.0's runtime-rs lists QEMU, Cloud Hypervisor, and Dragonball as its VMMs ([Kata 4.0 overview](https://katacontainers.io/blog/kata-containers-4-0-0-release-overview/)), so Firecracker remains a Go-runtime option **[inference]**. firecracker-containerd has no stable CRI path for Kubernetes ([DEV post](https://dev.to/alanpjohn/forking-openfaas-faasd-to-support-firecracker-containerd-1a5l)) **[unverified]**.
- **Adopters:** E2B (each sandbox a Firecracker microVM; userfaultfd lazy memory; pause stores memory and disk diffs in object storage; Apache-2.0 infra) ([E2B infra](https://github.com/e2b-dev/infra)); Vercel Sandbox ([Vercel security](https://vercel.com/docs/sandbox/concepts/security)); Fly.io Machines and Sprites ([Fly firecracker page](https://fly.io/learn/firecracker-vm/)). E2B claims ~150 ms start from a snapshot ([developersdigest](https://www.developersdigest.tech/agent-sandboxes/e2b)) **[unverified: vendor figure]**.

#### Cloud Hypervisor and Kata's VMM choices
- **Cloud Hypervisor:** Rust VMM. Supports snapshot/restore and live migration (compatibility guaranteed across the previous two major releases from v54), VFIO device hotplug, virtio-fs, and CPU and memory hotplug ([Cloud Hypervisor repo](https://github.com/cloud-hypervisor/cloud-hypervisor)). Licence and foundation were not shown on the page **[unverified]**.
- **Kata 4.0** (2026-07-22): runtime-rs is the default; Dragonball (Ant Group) is the built-in default VMM; supported VMMs are QEMU, Cloud Hypervisor, and Dragonball; NVIDIA GPU passthrough works with QEMU; the Go runtime is deprecated and may be removed no earlier than 5.0 (forecast Q1 2028) ([Kata 4.0 overview](https://katacontainers.io/blog/kata-containers-4-0-0-release-overview/)). Kata's hypervisor table marks GPU, TDX, and SEV-SNP as QEMU-only ([Kata hypervisors.md](https://github.com/kata-containers/kata-containers/blob/main/docs/hypervisors.md)). A Vercel explainer says Kata 4.1 added OpenVMM ([Vercel Kata explainer](https://vercel.com/i/kata-containers)) **[unverified]**. Kata is an OpenInfra project ([OpenInfra newsletter](https://openinfra.org/blog/openinfra-newsletter-july-2026)); its current foundation home was not confirmed **[unverified]**.
- **Adopters:** Northflank uses Kata with Cloud Hypervisor as its main path and gVisor where nested virtualisation is missing ([Northflank: microVM vs gVisor](https://northflank.com/blog/microvm-vs-gvisor)) **[vendor self-report]**. Google Agent Substrate offers Cloud Hypervisor as its microVM option ([GKE Agent Substrate](https://docs.cloud.google.com/kubernetes-engine/ai-ml/about-agent-substrate)).

#### libkrun, krun, and microsandbox
- **libkrun:** a library with an embedded VMM (KVM on Linux, HVF on macOS). Variants libkrun-sev and libkrun-tdx. Networking via TSI over vsock or virtio-net with passt or gvproxy. virtio-fs and virtio-gpu (venus, native context). Apache-2.0 ([libkrun](https://github.com/containers/libkrun)).
- **krun:** crun built with libkrun runs a container inside a microVM; used by Podman with `--runtime=krun` ([libkrun](https://github.com/containers/libkrun), [krun man page](https://www.mankier.com/1/krun)). No official CRI-O or Kubernetes documentation for krun as a RuntimeClass handler was found; crun-vm documents the CRI-O pattern ([crun-vm Kubernetes doc](https://gitea.cncfstack.com/containers/crun-vm/src/branch/cross-emulation/docs/3-kubernetes.md)) **[unverified for krun]**. krun isolates per container, so the containers of one pod would not share a VM **[inference]**.
- **microsandbox:** libkrun-based microVM runtime and SDK, embeddable with no daemon, runs OCI images, claims sub-100 ms boot (M1 Mac), Apache-2.0, self-described beta, no Kubernetes integration ([microsandbox](https://github.com/superradcompany/microsandbox)).

#### Edera
- **Type:** Xen-based hypervisor with a Rust control stack. Each pod runs in a "zone", a lightweight VM with its own kernel. It uses paravirtualization, so it does not need nested virtualization and runs on most cloud instance types. GPU drivers can run in separate driver zones. Kubernetes integration is through a RuntimeClass and a containerd shim ([Edera architecture](https://docs.edera.dev/technical-overview/architecture/overview/)).
- **Licence:** Edera Protect is commercial. Open components include OpenPaX (GPLv2) and the protos repository; a free one-node EderaON licence exists ([OpenPaX story](https://edera.dev/stories/edera-restores-security-benefits-for-linux-application-memory-safety-with-openpax), [protos](https://github.com/edera-dev/protos), [EderaON](https://on.edera.dev/what-is-ederaon/)). Third parties report the earlier krata project as GPL-2.0 and dormant since mid-2025 ([rywalker research](https://rywalker.com/research/edera)) **[unverified]**.
- **Startup:** "boot in milliseconds" without figures ([architecture](https://docs.edera.dev/technical-overview/architecture/overview/)). Research paper: [Goldilocks Isolation](https://arxiv.org/html/2501.04580v2).

#### AWS Nitro Sandboxes (new, 2026-11-09)
- Each sandboxed pod runs in its own lightweight VM on a Nitro Partition carved from a running instance. RuntimeClasses `isolated-sandbox` and `confidential-sandbox`; the confidential mode adds attestation and KMS release. Built into EKS Auto Mode; standard EKS needs a sandbox-enabled AMI; Kubernetes 1.36 or later. The post says the sandboxes pass Kubernetes conformance ([AWS Containers blog](https://aws.amazon.com/blogs/containers/aws-nitro-sandboxes-hardware-enforced-workload-isolation-on-amazon-eks/)). Startup about 1 s warm and 5–6 s cold is cited from AWS samples by a third party ([Qovery](https://www.qovery.com/blog/aws-nitro-sandboxes-eks-vs-daytona-e2b)) **[unverified]**. agent-sandbox v1.0.11 includes Nitro Sandbox examples ([agent-sandbox releases](https://github.com/kubernetes-sigs/agent-sandbox/releases)). GPU, checkpoint, and user-namespace behaviour are not stated in the retrieved content **[unverified]**.

#### Microsoft Hyperlight (CNCF Sandbox)
- Rust library VMM that runs guests with no kernel or OS inside micro-VMs (KVM, MSHV, WHP, HVF); guests are no_std Rust or C; hyperlight-wasm runs Wasm; pre-1.0; Apache-2.0 ([Hyperlight repo](https://github.com/hyperlight-dev/hyperlight)).
- **hyperlight-unikraft** (`hluk`, announced 2026-11-09) runs unmodified Linux binaries (Python, Node.js, .NET, Java, Go, and others) in a Unikraft unikernel inside a Hyperlight micro-VM. urunc runs these guests as OCI containers under containerd, so Kubernetes can use them via a RuntimeClass. agent-sandbox runs a sandbox's Python runtime in such a micro-VM without a RuntimeClass. Snapshot restore takes about 3 ms; Python hello-world measured 22 ms versus 17 ms native under nested virtualization ([CNCF blog](https://www.cncf.io/blog/2026/11/09/run-linux-applications-in-hypervisor-isolated-micro-vms-with-hyperlight/)).

#### Unikraft
- Unikraft Cloud describes each sandbox as a hardware-isolated microVM with its own kernel, an egress "shield" microVM that holds credentials, snapshot templates, scale-to-zero, and <10 ms cold start or restore ([Unikraft sandboxes](https://unikraft.com/docs/use-cases/sandboxes.md)) **[vendor claim]**. Release 12 added GPU support ([Unikraft blog](https://unikraft.com/blog/ai-sandboxes-at-scale)) **[unverified: title only]**. Adopter: Browser Use ([customer story](https://unikraft.com/customer-stories/browser-use-sandboxing)). Unikraft is a Linux Foundation project ([CNCF blog](https://www.cncf.io/blog/2026/11/09/run-linux-applications-in-hypervisor-isolated-micro-vms-with-hyperlight/)). Kubernetes integration of Unikraft Cloud itself was not documented on the page read **[unverified]**.

#### Sysbox
- Fork of runc. Every container gets a user namespace; procfs and sysfs are partly virtualized; selected syscalls are trapped; it runs systemd, Docker, and Kubernetes inside containers. Shares the host kernel. Install with the sysbox-deploy-k8s DaemonSet and select via RuntimeClass `sysbox-runc`. Apache-2.0. Docker acquired Nestybox in 2022; the project is "not officially supported by Docker" and support is best-effort ([Sysbox](https://github.com/nestybox/sysbox)). Daytona is reported to use Sysbox for rootless containers ([Northflank: Northflank vs Daytona](https://northflank.com/blog/northflank-vs-daytona)) **[unverified: competitor source]**.

#### Wasm sandboxes
- **runwasi:** containerd non-core sub-project; runs WASI workloads through containerd and the CRI plugin; wasmtime shim `io.containerd.wasmtime.v1`; Apache-2.0 ([runwasi](https://github.com/containerd/runwasi)).
- **SpinKube:** CNCF Sandbox since January 2025; Spin operator, containerd-shim-spin (built on runwasi), and runtime-class-manager; RuntimeClass handler `spin` ([Fermyon](https://www.fermyon.com/blog/introducing-spinkube), [techzine](https://www.techzine.eu/news/devops/117959/fermyon-technologies-introduces-spinkube-to-cncf-sandbox)).
- Wasm runs a single WASI module and offers no POSIX process model, so it cannot host a general coding agent that spawns shells and git **[inference]**.

#### OS-level sandboxes used by coding agents
- **Anthropic sandbox-runtime (`srt`):** macOS uses Seatbelt profiles via `sandbox-exec`; Linux uses bubblewrap (network namespace removed, traffic via host HTTP and SOCKS5 proxies over bind-mounted Unix sockets) and a seccomp filter that blocks Unix-socket creation; nested user namespaces blocked by default; deny-by-default network with domain allowlists; Windows alpha. "Beta Research Preview", Apache-2.0 ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)).
- **OpenAI Codex CLI:** Linux helper `codex-linux-sandbox` with a legacy Landlock pipeline and a vendored bubblewrap pipeline that applies `PR_SET_NO_NEW_PRIVS` and a seccomp network filter; macOS uses Seatbelt ([Codex linux-sandbox README mirror](https://forge.lthn.ai/core/core-agent-ide/blame/branch/dev/codex-rs/linux-sandbox/README.md), [Mintlify mirror](https://www.mintlify.com/openai/codex/architecture/sandboxing)) **[unverified: mirrors of the openai/codex repository; which pipeline is the current default is reported inconsistently]**.
- **NVIDIA OpenShell:** Apache-2.0 agent sandbox runtime using Landlock and seccomp per sandbox, with declarative YAML policy (network and inference policy hot-reloadable; process and filesystem policy fixed at creation); version 0.1.0 by October 2026 ([OpenShell docs](https://docs.nvidia.com/openshell/latest/about/overview.html), [NVIDIA playbook](https://build.nvidia.com/playbooks/openshell)).
- These run inside one kernel and restrict one process tree. They are defence in depth inside a pod rather than a pod isolation boundary **[inference]**.

#### Kubernetes agent-sandbox (kubernetes-sigs, SIG Apps)
- CRDs: `Sandbox` (core) plus `SandboxTemplate`, `SandboxClaim`, and `SandboxWarmPool` (extensions). API `agents.x-k8s.io/v1beta1`. Isolation is delegated to a RuntimeClass, named as gVisor or Kata. Apache-2.0 ([agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox)). Introduced on the Kubernetes blog on 2026-03-20 ([blog](https://kubernetes.io/blog/2026/03/20/running-agents-on-kubernetes-with-agent-sandbox)).
- Releases: weekly 1.0.x through v1.0.11 (12 Nov). Recent items: GKE Pod Snapshot primitives (snapshot, suspend, resume, restore) requiring gVisor (v1.0.8), Hyperlight micro-VM and GKE L4 GPU snapshot examples (v1.0.10), AWS Nitro Sandboxes examples (v1.0.11), a multi-cluster warm-pool planner (v1.0.6), and a note that default port-forward does not work with Kata or gVisor pods (v1.0.7) ([releases](https://github.com/kubernetes-sigs/agent-sandbox/releases)).
- **GKE Pod snapshots** capture process memory, rootfs, emptyDir, and tmpfs (not PVCs), require GKE Sandbox (gVisor), require matching CPU features and gVisor and GPU driver versions for `whole-pod` scope, and give each restored pod a new IP and hostname ([GKE Pod snapshots](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/pod-snapshots)).
- **Google Agent Substrate** (donated to CNCF Sandbox with gVisor, announced 2026-11-05): actors on pooled Worker pods; gVisor by default or Cloud Hypervisor microVMs; idle actors are snapshotted (RAM and files) to Cloud Storage and restored in under a second; open connections are dropped; no GPU passthrough to actors, and gVisor cannot snapshot live CUDA contexts in this product; GKE Standard 1.37+ ([Google open source blog](https://opensource.googleblog.com/2026/11/sandboxing-untrusted-ai-agents-at-scale.html), [GKE Agent Substrate](https://docs.cloud.google.com/kubernetes-engine/ai-ml/about-agent-substrate)).

#### gVisor recent changes
- **Governance:** Google is donating gVisor to the CNCF; Modal, Ant Group, and Tines committed maintainers ([Modal blog, 2026-11-11](https://modal.com/blog/modal-gvisor-maintainer), [Google open source blog](https://opensource.googleblog.com/2026/11/sandboxing-untrusted-ai-agents-at-scale.html)).
- **GPU (nvproxy):** compatible with NVIDIA's k8s-device-plugin (including CDI) and GKE's plugin; supported GPUs T4, A100, A10G, L4, and H100; strict driver-version matching; only `compute` and `utility` capabilities by default; no MIG. gVisor "is much less effective at mitigating vulnerabilities within the NVIDIA GPU drivers themselves" ([gVisor GPU guide](https://gvisor.dev/docs/user_guide/gpu)). A report of over-exposed GPUs under the NVIDIA DRA driver exists ([gVisor issue search summary](https://github.com/google/gvisor/issues/12144)) **[unverified]**.
- **Checkpoint/restore:** `runsc checkpoint` and `runsc restore`, with compression, zero-page exclusion, direct I/O, background (lazy) restore, application-triggered checkpoint through `/proc/gvisor/checkpoint`, and GPU checkpoint through `cuda-checkpoint` (not on arm64). Connected sockets get `ECONNRESET`; restore needs the source CPU features ([gVisor checkpoint/restore](https://gvisor.dev/docs/user_guide/checkpoint_restore/)). Modal restores about 670k gVisor containers from snapshots a day ([Modal blog](https://modal.com/blog/modal-gvisor-maintainer)).

### 2.2 Assessment for Lenny

Lenny context used here, from the designs **[source: `designs/session-isolation-design.md` revisions 13 and 16]**: Lenny supports runc, gVisor, and Kata. A pod holds several containers (adapter, `netagent`, and one container per slot) sharing a network namespace. Per-slot egress attribution reads the socket owner UID: `sock_diag` on runc, and `/proc/net/tcp` on gVisor and Kata. Project quotas bound slot volumes on runc with user namespaces, gVisor's `/tmp`, and Kata virtio-fs. runc pods run with `hostUsers: false`. Checkpoints capture workspace files, so they do not need memory snapshots.

A candidate therefore has to run a whole multi-container pod behind one boundary, expose per-UID socket ownership to `netagent`, present slot volumes that take project quotas or report through `statfs`, and run under a RuntimeClass **[inference from the designs]**.

Overall **[inference]**:
- No new technology clearly justifies a fourth isolation profile now. Every VM-class option (Kata VMMs, Edera, Nitro Sandboxes) gives the same guest-kernel boundary the Kata profile already names, so the profile set can stay runc, gVisor, and a VM profile. The VM profile can document which RuntimeClass backs it per environment: Kata with QEMU, Cloud Hypervisor, or Dragonball; Nitro Sandboxes on EKS; Edera where licensed.
- Each VM backend needs the same spike Lenny ran on 2026-11-14: `/proc/net/tcp` slot attribution, project quotas or `statfs` on slot volumes, and SO_PEERCRED behaviour.
- Kata's long-standing obstacle on public clouds is the need for bare metal or nested virtualization (Agent Substrate's microVM mode states the same requirement ([GKE Agent Substrate](https://docs.cloud.google.com/kubernetes-engine/ai-ml/about-agent-substrate))). Nitro Sandboxes (EKS) and Edera (Xen paravirtualization) are the two backends found that remove it.
- Memory snapshots are now common across providers (gVisor, Firecracker, Cloud Hypervisor, and Hyperlight). Lenny's per-slot model makes whole-pod memory snapshots awkward, because a pod with several slots holds several sessions. Restores also change the pod's IP, reset connections, and require matching CPU features and drivers.
