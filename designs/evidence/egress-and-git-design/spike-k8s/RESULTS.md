## Test 1: token isolation

### Manifests

Namespace `spike`, ServiceAccount `agent` with `automountServiceAccountToken: false`. Each test pod sets `automountServiceAccountToken: false` at pod level and has three containers from `alpine:3.22`:

- `netagent`: UID/GID 65530, env `NETAGENT_SECRET_ENV=s3cr3t-in-environ`, mounts the projected volume `egress-token` at `/var/run/secrets/lenny-egress` read-only, and logs the token file mtime, sha1 and payload every 10 s (used by Test 3).
- `runtime`: UID/GID 65533, `sleep infinity`, no volume mounts.
- `adapter`: UID/GID 65532, `sleep infinity`, no volume mounts.

All containers: `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`; pod `runAsNonRoot: true`.

```yaml
volumes:
- name: egress-token
  projected:
    sources:
    - serviceAccountToken: {audience: lenny-egress, expirationSeconds: 600, path: token}
```

Variants:

| Pod | shareProcessNamespace | runtime UID | pod fsGroup |
|:--|:--|:--|:--|
| iso-a | false | 65533 | none |
| iso-b | true | 65533 | none |
| iso-c (negative control) | true | 65530 (same as netagent) | none |
| iso-d | true | 65533 | 65530 |
| automount-on (control) | n/a | root | none, `serviceAccountName: default`, automount left on |

### Token file ownership and mode (as seen by netagent)

- iso-a (no fsGroup, containers with differing UIDs): `-rw-r--r-- 0 0 token` (root-owned, 0644). netagent can read it.
- iso-d (fsGroup 65530): `-rw-r----- 0 65530 token` (0640, group 65530), directories setgid. Note that fsGroup is added as a supplementary group to every container: runtime and adapter in iso-d ran with `groups=65533 65530` / `65532 65530`. They still had no mount of the volume.

### Probe from runtime and adapter (`t1-probe.sh`, output `t1-out.txt`)

| Pod / container | /var/run/secrets present | token found by `find /` | netagent PID visible | `/proc/<pid>/root/...token` | `/proc/<pid>/environ` | `/proc/<pid>/cmdline` | `/proc/<pid>/mountinfo` |
|:--|:--|:--|:--|:--|:--|:--|:--|
| iso-a runtime, adapter | no | no | no (own PID ns) | n/a | n/a | n/a | n/a |
| iso-b runtime, adapter | no | no | yes (PID 7) | `Permission denied` (also `ls /proc/7/root/`) | `Permission denied` | readable | readable (shows the tmpfs mount at `/run/secrets/lenny-egress`) |
| iso-c runtime (UID 65530) | no | no | yes | **readable** (`eyJhbGciOiJSUzI1NiIs...`) | **readable** (`NETAGENT_SECRET_ENV=s3cr3t-in-environ`) | readable | readable |
| iso-c adapter (UID 65532) | no | no | yes | `Permission denied` | `Permission denied` | readable | readable |
| iso-d runtime, adapter (with fsGroup) | no | no | yes | `Permission denied` | `Permission denied` | readable | readable |

`CapEff=0000000000000000` in every probed container. `/proc/<pid>/fd` was also denied for differing UIDs.

### automountServiceAccountToken

- `kubectl get pod iso-b -o jsonpath='{.spec.volumes[*].name}'` returns only `egress-token`; there is no `kube-api-access-*` volume. Only netagent has a volume mount.
- In netagent, `/var/run/secrets/` contains only `lenny-egress`; `/var/run/secrets/kubernetes.io` does not exist. In runtime and adapter `/var/run/secrets` does not exist.
- Control pod `automount-on` has volume `kube-api-access-5w7xz` with `/var/run/secrets/kubernetes.io/serviceaccount/{ca.crt,namespace,token}`.

### Verdict

PASS. With distinct UIDs, runtime and adapter cannot read the token or netagent's environ in either PID-namespace mode. The negative control shows that the protection in a shared PID namespace depends entirely on the UID difference (ptrace access check): a container sharing netagent's UID reads both the token and environ. Cmdline and mountinfo of netagent are world-readable in a shared PID namespace, so secrets must not be passed on the command line.

## Test 2: offline validation and pod-deletion latency

### Validator

`validator/main.go` (stdlib only, built `CGO_ENABLED=0 GOOS=linux GOARCH=arm64`, image `FROM scratch`), Deployment in `spike` with ServiceAccount `egress-decider`. RBAC (`t2-validator.yaml`): ClusterRole `get/list/watch pods`; `system:auth-delegator` binding only for the TokenReview comparison. No binding was needed for discovery: the default ClusterRoleBinding `system:service-account-issuer-discovery` already grants the discovery URLs to group `system:serviceaccounts`.

Behavior:

1. GET `https://kubernetes.default.svc/.well-known/openid-configuration` with its own SA token, then GET the advertised `jwks_uri` (`https://172.18.0.2:6443/openid/v1/jwks`; reachable from the pod with the SA CA, so the fallback path was not used).
2. Verify RS256 signature against the JWKS key by `kid`, `iss` equal to the discovery issuer, `aud` containing `lenny-egress`, `exp`/`nbf` with 5 s leeway, and require a `kubernetes.io.pod` claim.
3. Keep a pod map from a list + watch on `/api/v1/pods` (all namespaces); a token passes only if its pod UID is in the map with matching name and namespace. The map records `deletionTimestamp`; `?strict=1` rejects terminating pods.
4. `/probe` polls the validator check and a TokenReview (audience `lenny-egress`) every 100 ms for 90 s and logs transitions.

Startup log:

```
04:50:02.704 discovery: issuer=https://kubernetes.default.svc.cluster.local jwks_uri=https://172.18.0.2:6443/openid/v1/jwks
04:50:02.707 jwks: kid=-V17DYY8Dw1uZrW0WDXRNJTODJqC2KiR0UURiNzdjoY alg=RS256 use=sig
04:50:02.711 pods listed: 15 rv=910
```

### Claim and rejection checks (`t2-out1.txt`)

| Token | Validator | TokenReview (aud lenny-egress) |
|:--|:--|:--|
| iso-b projected token | ok, podState live | authenticated |
| default automount token (aud = issuer URL) | reject `aud [https://kubernetes.default.svc.cluster.local]` | `token audiences [...] is invalid for the target audiences ["lenny-egress"]` |
| `kubectl create token agent --audience lenny-egress` (not pod-bound) | reject `token not pod-bound` | authenticated |
| payload edited (pod name changed), original signature | reject `signature: crypto/rsa: verification error` | `error in cryptographic primitive` |
| iso-d token captured at start, checked after its exp | reject `expired` | `service account token has expired` |

Claims of a kubelet-issued token (iso-b):

```json
{"iss":"https://kubernetes.default.svc.cluster.local","sub":"system:serviceaccount:spike:agent","aud":["lenny-egress"],
 "exp":1793595444,"nbf":1793594844,"iat":1793594844,
 "kubernetes.io":{"namespace":"spike",
   "pod":{"name":"iso-b","uid":"4c8a3e5a-5b83-4043-8187-d46e81c1bb61"},
   "node":{"name":"spike-netagent-control-plane","uid":"28b786f4-..."},
   "serviceaccount":{"name":"agent","uid":"f78f12ae-..."}}}
```

The token also carries `jti`. The default token carries `kubernetes.io.warnafter`; the 600 s token does not.

Additional finding: `kubectl create token agent --audience lenny-egress --duration 10m --bound-object-kind Pod --bound-object-name iso-b --bound-object-uid <uid>` (run as cluster-admin) produced a token with the same claim keys (`aud, exp, iat, iss, jti, kubernetes.io{namespace,node,pod,serviceaccount}, nbf, sub`) and the validator accepted it. The validator cannot distinguish a kubelet-requested token from one minted by any principal with `create` on `serviceaccounts/token` for the agent ServiceAccount.

### Pod deletion latency (`t2-delete-validator.txt`, `t2-delete-host.txt`)

Victim pods: single netagent container with the projected token, `terminationGracePeriodSeconds: 30`. `victim-slow` runs `sh` as PID 1 without a TERM handler, so it ignores SIGTERM and is killed at the end of the grace period. `victim-fast` traps TERM and exits immediately. Host and node clocks agreed within about 40 ms. Delete was issued with `kubectl delete pod --wait=false`.

victim-slow:

```
host  04:50:51.126 DELETE issued
      04:50:51.187 WATCH MODIFIED deletionTimestamp=2026-11-02T04:51:21Z   (+61 ms)
      04:50:51.208 PROBE validator ok=true state=terminating
      04:51:21.842 WATCH DELETED                                          (+30.7 s)
      04:51:21.897 PROBE validator ok=false state=gone reason=pod uid not live   (+55 ms after DELETED)
      04:51:28.224 PROBE tokenreview authenticated=false [service account token has been invalidated]   (+6.4 s after DELETED)
```

victim-fast:

```
host  04:51:39.265 DELETE issued
      04:51:39.326 WATCH MODIFIED deletionTimestamp=2026-11-02T04:52:09Z   (+61 ms)
      04:51:39.364 PROBE validator ok=true state=terminating
      04:51:39.910 WATCH DELETED                                          (+645 ms)
      04:51:39.982 PROBE validator ok=false state=gone                     (+72 ms after DELETED)
      04:51:46.224 PROBE tokenreview authenticated=false [service account token has been invalidated]   (+6.3 s after DELETED)
```

Summary:

- Validator (watch-based) rejected within 55 to 72 ms of the DELETED event; the 100 ms poll interval bounds this measurement. A strict mode that rejects on `deletionTimestamp` would reject about 61 ms after the delete call.
- TokenReview kept authenticating the token for the whole terminating period and for about 6.3 to 6.4 s after the pod object was gone. The cause of the extra 6 s was not investigated; it is consistent with an authentication result cache in the API server, but this spike did not confirm that.
- The token remains valid by signature and exp throughout; only the pod-liveness check rejects it.

### Verdict

PASS. Caveats: token minting by any holder of `serviceaccounts/token create` on the agent SA produces accepted tokens; the validator relies on RBAC to prevent that. JWKS key rotation and watch reconnect/relist were not exercised.

## Test 3: rotation

Observed from the netagent logging loop in iso-a..iso-d (`t3-rotation.txt`):

| Pod | First token iat | Rewrite (file mtime) | Old token age at rewrite | New token exp - iat |
|:--|:--|:--|:--|:--|
| iso-b | 1793594844 | 1793595322 | 478 s | 600 |
| iso-d | 1793594844 | 1793595348 | 504 s | 600 |
| iso-a | 1793594882 | 1793595378 | 496 s | 600 |
| iso-c | 1793594844 | 1793595371 | 527 s | 600 |

- The kubelet rewrote every token file before expiry, between 478 s and 527 s (80% to 88% of the 600 s TTL). The rewrite is an atomic `..data` symlink swap to a new timestamped directory; the `token` symlink is unchanged. File mode and group were preserved after rotation (`t3-perms-after.txt`).
- Every token observed had `exp - iat = 600`; `--service-account-extend-token-expiration` (default on) did not extend it. The extension did apply to the default automount token (`expirationSeconds: 3607` requested): `exp - iat = 31536000` (one year), with `warnafter = iat + 3607`.
- The previous token remained valid after the rewrite: the iso-d first token was accepted by both the validator and TokenReview at 1793595429 (81 s after its replacement), and both rejected it as expired at 1793595510 (exp 1793595444).
- Only one rotation cycle was observed per pod.

Verdict: PASS.

## Test 4: native sidecar ordering (`t4-sidecar.yaml`)

netagent is an init container with `restartPolicy: Always`. It sleeps 5 s, writes `/shared/ca.crt` (tmp file + `mv`) into an `emptyDir` (medium Memory), and loops. `startupProbe: exec test -s /shared/ca.crt`, `periodSeconds: 1`, `failureThreshold: 60`. TERM handler: log, sleep 3, exit 1. runtime (UID 65533) mounts `/shared` read-only, logs the file content at start, tries `touch /shared/x`, TERM handler sleeps 2. adapter TERM handler sleeps 1. Timestamps use `/proc/uptime` (node-wide) because busybox `date` has no `%N`.

Startup:

```
04:53:21 up=1880525.26 netagent start
04:53:26 up=1880530.27 netagent wrote /shared/ca.crt
04:53:27 up=1880531.25 runtime start; ca.crt: -----BEGIN CERTIFICATE----- fake-ca 04:53:26 up=1880530.27
04:53:27 up=1880531.26 runtime write attempt: touch: /shared/x: Read-only file system
04:53:27 up=1880531.33 adapter start
```

runtime and adapter started 0.98 s after the file was written, which matches the 1 s probe period. Pod conditions: `Initialized` became True at 04:53:04 in the first run, the same second the main containers started.

Killing netagent (`kubectl exec sidecar -c netagent -- kill -TERM 1` at 04:53:38):

```
04:53:38 netagent got TERM ; 04:53:41 netagent exiting (exit 1)
04:53:42 netagent start (new instance, restartCount 1, startupProbe passed by 04:53:43)
04:53:47 netagent wrote /shared/ca.crt
```

After the restart: `netagent restarts=1 startedAt=04:53:42Z`; `runtime restarts=0 startedAt=04:53:27Z`; `adapter restarts=0 startedAt=04:53:27Z`. runtime and adapter were not restarted. Pod `Ready` was False in the 1 s polls at t+4 s and t+5 s (netagent terminated, then restarting); netagent was ready again at t+6 s, and pod `Ready` was True when checked at 04:54:05.

Caveat observed: the restarted netagent's startup probe passed before it rewrote the CA file, because the file from the previous instance persisted in the emptyDir. A file-existence startup probe does not prove the current instance is ready.

Termination (`kubectl delete pod sidecar` at 04:54:05, `kubectl logs -f` captured to `t4-term-*.log`):

```
04:54:05 up=1880569.36 runtime got TERM
04:54:06 up=1880569.43 adapter got TERM
04:54:07 up=1880570.44 adapter exiting
04:54:07 up=1880571.37 runtime exiting
04:54:08 up=1880571.93 netagent got TERM      (0.56 s after the last main container exited)
04:54:11 up=1880574.93 netagent exiting
```

Verdict: PASS.

## Test 6: NetworkPolicy

kind v0.31.0 with kindnetd `v20251212-v0.29.0-alpha-105-g20ccfc88` enforces NetworkPolicy: it installs `table inet kindnet-network-policies`, which sends packets of policy-selected pods (`set podips-v4 { 10.244.0.18 }`) to an nfqueue (`queue flags bypass to 101`) from a `postrouting` hook (and a `prerouting` hook for UDP 53). Calico was not installed.

Policy (`t6-netpol.yaml`):

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: agent-egress, namespace: spike}
spec:
  podSelector: {matchLabels: {role: agent}}
  policyTypes: [Egress]
  egress:
  - to:
    - podSelector: {matchLabels: {app: lenny-egress}}
    ports: [{protocol: TCP, port: 3128}]
  - to:
    - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: lenny-dns}}
      podSelector: {matchLabels: {app: proxied-dns}}
    ports: [{protocol: UDP, port: 53}, {protocol: TCP, port: 53}]
```

Probe from `proxied-client` (curl container), before and after the policy (`t6-out.txt`):

| Destination | Baseline | With policy |
|:--|:--|:--|
| `lenny-egress` Service ClusterIP:3128, CONNECT to example.com | 200 | 200 (0.09 s) |
| second CoreDNS ClusterIP (getent kubernetes.default) | resolves | resolves |
| default CoreDNS 10.96.0.10 | resolves | `connection timed out; no servers could be reached` (2 s) |
| validator Service ClusterIP 10.96.150.24:8080 | 200 | timeout (curl 28, 4 s) |
| validator pod IP 10.244.0.11:8080 | 200 | timeout |
| 1.1.1.1:443 | 301 | timeout |
| API server Service 10.96.0.1:443 | 200 | **200 (not blocked)** |
| node IP 172.18.0.2:10250 (kubelet) | 401 | **401 (not blocked)** |

Pod -> ClusterIP Service -> backend selected by podSelector works (policy is evaluated on the post-DNAT backend IP), and other pod, Service, DNS, and internet destinations are dropped.

Not blocked: destinations on the local node's own IP (the kubelet, and the API server, which in kind is a hostNetwork static pod on the same node, reached via 10.96.0.1 DNAT to 172.18.0.2:6443). This is consistent with the kindnet rules: they hook `postrouting`, which locally delivered packets do not traverse. Whether hostNetwork endpoints on a different node are blocked was not tested (single node). The nfqueue rule uses `flags bypass`, which accepts packets when no userspace program is attached to the queue.

Verdict: PARTIAL. The policy semantics under test behave as intended for pod, Service, DNS, and external destinations; kindnet does not block the local node IP or hostNetwork endpoints on the same node, including the API server.
