# Evidence for `pod-lifecycle-controller-design.md`

On 2026-11-15 the owner asked for a review of the upstream project `kubernetes-sigs/agent-sandbox` against Lenny's pod lifecycle: what upstream offers today, how Lenny's resource kinds compare with upstream's kinds of the same names, which upstream features are worth borrowing, and whether Lenny should depend on upstream. `agent-sandbox-review.md` is that review. It is a read-only study. Nothing ran against a cluster, and no upstream code was built or imported.

On 2026-11-16 an adversarial review read revision 2's statement that every `PodSet` carries a `lenny.dev/pool` label naming its pool. `pool-label-review.md` is that review. It is a read-only study of the tree, and nothing ran against a cluster.

| File | What it is |
| :-- | :-- |
| `agent-sandbox-review.md` | The review of 2026-11-15, read at Lenny commit `8702041e8` on branch `design/v1-cleanup` and upstream commit `454d3353` (the `v1.0.11` API types). Each upstream claim carries a URL, and claims that could not be confirmed against a primary source are marked unverified. Section 2 compares Lenny's `Sandbox`, `SandboxTemplate`, `SandboxWarmPool`, and `SandboxClaim` with upstream's field by field. Section 5 sets out the dependency options, and section 6 lists the gaps it found in Lenny's specification and code. Revision 1 of `pod-lifecycle-controller-design.md` rested on sections 2, 5, and 6. Revision 2 rests on it for the facts behind removing the specification's dependency text (sections 5 and 6) and keeps it as the record of that reasoning. Revision 2 takes no kind or field name from section 2, because the owner decided on 2026-11-15 that Lenny stops tracking upstream and names its kinds for itself. |
| `pool-label-review.md` | The review of 2026-11-16, read at Lenny commit `b622d716c` on branch `design/v1-cleanup`. It records three issues with the `lenny.dev/pool` label on `PodSet`: one label value serving both the pod-set scope and the pool scope during a rollout, with two PodDisruptionBudgets selecting one pod (medium); no guard on the label (low); and pool names the admin API accepts that are not valid label values (low). It lists what the review checked and ruled out, the owner's "ok" to all three fixes, and the points where revision 3 of the design differs from the review's wording. Revision 3's "PLC-2" **Pool and pod-set labels.**, "PLC-7", and PLCR-13 to PLCR-15 rest on it. |

While writing revision 1 of the design, the author fetched upstream's `api/v1beta1/sandbox_types.go` and `extensions/api/v1beta1/sandboxwarmpool_types.go` at tag `v1.0.11` from `raw.githubusercontent.com` to confirm three type facts: `Sandbox.status.podIPs` is a list of strings, `SandboxWarmPool.spec.sandboxTemplateRef` is an object with a `name` member, and the `Sandbox` condition types are `Ready`, `Suspended`, `PodScheduled`, and `Finished`. Revision 2 of the design withdraws the renames and the condition those facts informed, and its "Sources" records the files as read by revision 1.

Left out: the two downloaded upstream files, which are third-party source. The review has no logs or code.
