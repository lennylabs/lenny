# Proposal: Slot-aware checkpointing: carry slot_id on CheckpointStart and scope checkpointRoots() to the slot subtree

- **Status:** Implemented (2026-07-19). Spec applied and code landed on `proposal-b/c-22-slot-aware-checkpoint`; all reached tiers green (0/1/3/4/7a, independently verified under `-race`), 98.3% changed-line coverage, design-conformance review clean. Ready for `--no-ff` integration. Verified (2026-07-18) after 7 adversarial review rounds (9 findings fixed). Open decision resolved on sign-off: `CheckpointStart` carries `slot_id` only; `session_id` is not added (minimal-surface reading; the slot-assignment gate is the intended contract).
- **Date:** 2026-07-18.
- **Scope:** A proto, code, and spec change that makes a `sessionPolicy.maxConcurrentSessions > 1` pod checkpointable per slot, which the spec already mandates and the code cannot provide. It adds one field (`SlotId slot_id = 6`) to the streaming `CheckpointStart` message on `schemas/lenny-adapter.proto`, populates it gateway-side from `binding.SlotID`, and branches the adapter's `checkpointRoots()` onto the slot subtree. It touches `schemas/lenny-adapter.proto` (**C1**), `pkg/proto/adapter/v1` (regenerated), `pkg/gateway/checkpoint/checkpointer/checkpointer.go` (**C2**), `pkg/adapter/checkpoint.go` (**C3**), `pkg/adapter/oplock.go`, `pkg/adapter/lifecycle.go`, and `spec/04_system-components.md` §4.7 (**C4**), adapter and barrier-drain tests (**C5**), and the tier-3 checkpoint-stream contract test (`tests/tier3_contract/checkpoint_stream/checkpoint_stream_wire_test.go`). §5.2, §6.4, and §10.1 already specify per-slot checkpoints keyed on `(session_id, slot_id)`, so the capture-path correction is to the wire message and the adapter/gateway code. The op-lock rework in C4 changes the queue-depth contract that §4.7 authors for concurrent-session pods, so C4 also amends §4.7 to describe the per-slot pending set. It fixes the checkpoint-capture path that finding T-4.4.21 (`TEST-GAPS.md:691`) names, so a concurrent-session pod captures the correct slot subtree. The symmetric restore path (`ResumeRequest` carries no `slot_id` and `pkg/adapter/resume.go:180` extracts into the pod-global `checkpointRoots()`) is a companion change and stays out of scope, so this proposal unblocks but does not close T-4.4.21, whose suggested test asserts a per-slot round trip. It is independent of the eviction trigger.

This document stages the proposed proto, spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

`spec/05_runtime-registry-and-pool-model.md:542` (§5.2), `spec/06_warm-pod-model.md:373-395` (§6.4, with the checkpoint-export mandate at `:393`), and `spec/10_gateway-internals.md:141` (§10.1) all require per-slot checkpoints on a pool with `sessionPolicy.maxConcurrentSessions > 1`. Each slot owns `/workspace/slots/{slotId}/current/` and `/sessions/{slotId}/`, and each checkpoint is keyed on the `(session_id, slot_id)` pair, capturing only that slot's workspace and session state. `spec/05:542` states it directly: "Checkpoints are per-slot. Each slot's checkpoint includes only that slot's workspace state and conversation history." `spec/06:393` assigns the gateway the slot-qualified path: "Checkpoint export ([§4.4]) targets `/workspace/slots/{slotId}/current/` for the specific slot." The code cannot provide this.

### (A) The wire message carries no slot identity

The streaming `CheckpointStart` message (`schemas/lenny-adapter.proto:1101-1115`) carries `checkpoint_id`, `trigger`, `chunk_size_bytes`, `chunk_encoding`, and `deadline_ms`. It carries no `slot_id` and no `session_id`, so the gateway cannot tell the adapter which slot to checkpoint. The proto already carries `SlotId slot_id` on twelve other per-slot request messages (defined at `:585`, used at `:447`, `:682`, `:716`, `:838`, `:918`, `:949`, `:962`, `:986`, `:1005`, `:1020`, `:1032`, and `:1458`), so `CheckpointStart` is the one stream opener the per-slot field is missing from.

### (B) The adapter resolves only the pod-global bundle

`Server.checkpointRoots()` (`pkg/adapter/checkpoint.go:28-38`) returns the pod-global bundle `{WorkspacePrefix -> s.WorkspaceRoot}` plus optional `{SessionsPrefix -> s.SessionsRoot}`. It takes no slot argument and never resolves a slot subtree. Both callers inherit that bundle: `probeWorkspaceBytes` (`:44-54`) and the archive goroutine that passes `s.checkpointRoots()` to `workspace.ArchiveTree` (`:186`). On a concurrent-session pod the live workspace lives at `/workspace/slots/{slotId}/current/`, while `s.WorkspaceRoot` is the pod-global `/workspace/current` base tree, so `ArchiveTree` captures no slot's live workspace.

### (C) The handler performs no slot gate

The `Checkpoint` handler (`pkg/adapter/checkpoint.go:73-161`) gates only on `s.WorkspaceRoot == ""` (`:84`) and `s.CheckpointTransport == nil` (`:88`), plus the single pod-global op lock `s.ops.Begin(ctx, opCheckpoint)` (`:97`). It never resolves a slot, so it cannot reject a checkpoint for a slot with no bound session.

### (D) The gateway holds the slot identity but drops it

The gateway-side driver already reads the slot identity: `driveCheckpoint` sets `slotID := binding.SlotID` at `pkg/gateway/checkpoint/checkpointer/checkpointer.go:501`. It substitutes the manifest sentinel `partialmanifeststore.SlotDefault` ("default") when the binding is empty (`:502-503`) for the intent-row scoping, then omits the slot entirely from the `CheckpointStart` it builds at `:527-535`.

### (E) The result

A concurrent-session pod cannot be checkpointed at all, on any trigger (the periodic loop, the preStop barrier, or the future eviction trigger). This is finding T-4.4.21 (`TEST-GAPS.md:691`, "CheckpointRequest carries no slot_id and the adapter's checkpointRoots() is pod-global, so concurrent-session pods have no working checkpoint path", OPEN High). It is independent of the eviction trigger: the trigger selects when a checkpoint fires, and this proposal fixes what a checkpoint addresses.

## 2. Decisions

- **Classified `fix`.** §5.2, §6.4, and §10.1 already mandate per-slot checkpoints keyed on `(session_id, slot_id)`. The adapter and its wire message fail to provide a spec-mandated §4.4 durability capability for §5.2 concurrent mode. Adding `SlotId slot_id` to `CheckpointStart` follows the established per-slot field pattern the proto already carries on twelve other request messages, and a slot-branched `checkpointRoots()` follows the presence-keyed `useSlot` dispatch already used across the adapter (`session.go`, `staging.go`, `credentials.go`). No new RPC, stream, or protocol concept is introduced.
- **Add exactly one field: `SlotId slot_id = 6` on `CheckpointStart`.** Do not add a `session_id` field. The base single-session checkpoint path carries no session identity today and gates only on config plus the op lock. `slot_id` alone resolves the correct slot subtree, and the adapter validates that the named slot is assigned (has a bound session) as its gate. This is the minimal-surface reading of the pattern. A fuller `(session_id, slot_id)` binding is surfaced as an open decision.
- **The wire `slot_id` is the raw `binding.SlotID`, empty for a `maxConcurrentSessions: 1` pod.** It is the raw binding value rather than the gateway-side manifest sentinel `'default'` (`partialmanifeststore.SlotDefault`). The adapter's `useSlot` keys on non-empty presence (`slot.go:39-41`), and single-session runtimes never see a `slotId` (`spec/15:1459`). Sending `'default'` on the wire would route a single-session pod down the per-slot branch, which has no assigned slot state and would fail the assignment gate.
- **Pod-global behavior is preserved byte-for-byte when `slot_id` is absent.** A proto3 message field serializes to zero bytes when unset. `checkpointRootsForSlot("")` returns the existing `s.checkpointRoots()` slice unchanged, so the single-session `Checkpoint` stream is identical on the wire and on disk.
- **A slot-scoped `checkpointRoots()` swaps both roots to the slot subtree:** `WorkspacePrefix -> SlotPaths.Current` and `SessionsPrefix -> SlotPaths.Sessions`. The session tmpfs is itself slot-scoped at `/sessions/{slotId}` (`slotlayout.go:95-96`, `:145-146`). Scoping only the workspace root would bundle the wrong pod-global `/sessions` content into the slot's checkpoint.
- **The adapter op lock is extended to admit each distinct per-slot checkpoint and promote pending checkpoints in slot-ID order.** The shared op lock (`opLock`, one per pod `Server`, `server.go:300`) keeps a single queue slot and coalesces a second checkpoint into the queued one (`oplock.go:64-72`: `coalesce := kind == opCheckpoint && l.queuedKind == opCheckpoint`, with no slot comparison and a queue depth of one). Coalescing is correct for a whole-pod checkpoint, where the queued whole-pod checkpoint covers the coalesced request. Under per-slot semantics it drops slots: the gateway drain opens one `Checkpoint` stream per session concurrently (`barrier.go:200-204` and `:224-229`, one `Target` per lease from `wiring.go:122-134`), so on a concurrent pod with three or more occupied slots three or more streams reach `Begin` at once. One runs, one takes the single queue slot, and the rest coalesce into the queued slot and return `errOpCoalesced`, which `checkpoint.go:97-101` maps to `codes.Aborted`; the drain still acks the target (`barrier.go:242`) and the pod terminates with those slots never checkpointed. `Begin` therefore takes the slot identity: a re-fire for the same slot still coalesces because the pending checkpoint covers it, and a checkpoint for a distinct slot is admitted into an ordered pending set that `release` promotes in slot-ID order. Every assigned slot's upload runs, one at a time in slot-ID order, which matches `spec/05:542` ("The adapter processes one slot's checkpoint upload at a time, in slot-ID order"). The uploads are serialized, and they are not parallelized. C4 makes this change and stages the matching §4.7 spec amendment, whose queue-depth statement the rework supersedes for concurrent-session pods.
- **This addresses the capture half of T-4.4.21.** It makes a concurrent-session pod capture the correct slot subtree, which is the defect the finding's statement names. The symmetric restore path is a companion change (see non-goals), so this proposal unblocks but does not close T-4.4.21, whose suggested test asserts a per-slot round trip. It likewise unblocks but does not close T-4.4.14 (the gateway never drives the individual agent-pod eviction trigger) or T-4.6.4 (node-drain checkpoint-before-eviction); both require the eviction trigger wiring, which is a separate proposal.

## 3. How slot_id flows end to end

A checkpoint attempt begins at the gateway. `driveCheckpoint` (`checkpointer.go:500`) reads `binding.SlotID`, which is the raw slot identifier the registry binding holds (empty on a `maxConcurrentSessions: 1` pod). It keeps its existing `SlotDefault` substitution for the intent-row and single-flight scoping. Separately, it sets the wire `CheckpointStart.slot_id` from the raw binding value, so a single-session attempt sends no `slot_id` field and stays on the pod-global path.

The adapter's `Checkpoint` handler reads `start.GetSlotId().GetValue()` and resolves the roots once. When the value is empty, `checkpointRootsForSlot` returns the existing pod-global bundle and every downstream step is unchanged. When the value is non-empty, the handler looks up the slot state: if the slot has no registry entry or no bound session, it returns `codes.FailedPrecondition` before minting any grant. Otherwise it builds the slot-scoped roots (`SlotPaths.Current` under `WorkspacePrefix`, `SlotPaths.Sessions` under `SessionsPrefix`) and threads that slice through the size probe and the archive, so the probe measures and `ArchiveTree` captures the one slot's live subtree.

## 4. Proposed changes

### C1. `schemas/lenny-adapter.proto`: add `SlotId slot_id = 6` to `CheckpointStart`

**Target:** `schemas/lenny-adapter.proto` (`message CheckpointStart`, `:1101-1115`; `SlotId` defined at `:585`); `pkg/proto/adapter/v1` (regenerated via `make generate-proto`, `Makefile:91`).

**Rationale.** The gateway drives the `Checkpoint` stream, and a single pod-global runtime serves every slot multiplexed on `slotId` (`slot.go:14-16`, `spec/05:509`, `spec/15:1459`), so the adapter has no ambient per-connection slot identity. The slot must be named in the frame. `CheckpointStart` is the frame that opens the stream and already carries the other gateway-chosen parameters (`checkpoint_id`, `chunk_size_bytes`, `chunk_encoding`), so `slot_id` belongs alongside them rather than in a new message. This mirrors the `SlotId slot_id` field the proto already carries on twelve per-slot request messages. Adding the field requires no prose spec edit: `spec/05:542`, `spec/06:393`, and `spec/10:141` already describe per-slot checkpoints and the `(session_id, slot_id)` key, and the proto message is the authoritative wire surface being corrected. The one spec prose edit this proposal stages is in C4, where the op-lock rework changes §4.7's queue-depth contract.

**Change.** In `message CheckpointStart`, after `int64 deadline_ms = 5;`, add:

```protobuf
  // slot_id, when set, checkpoints this slot's per-slot workspace and
  // session subtree (/workspace/slots/{slotId}/current and
  // /sessions/{slotId}) instead of the pod-global roots. Empty when
  // maxConcurrentSessions: 1 (the pod-global base layout). spec: §5.2
  // (per-slot checkpoint granularity), §6.4 (per-slot layout).
  SlotId slot_id = 6;
```

Then run `make generate-proto` to regenerate `pkg/proto/adapter/v1`. The generated `CheckpointStart` gains `GetSlotId()` returning `*SlotId`.

Because adding a field to `CheckpointStart` is a wire-contract change, also extend the tier-3 contract pin in `tests/tier3_contract/checkpoint_stream/checkpoint_stream_wire_test.go:135-141` with `{name: "slot_id", number: 6}`. The `assertFields` helper iterates only its `want` slice and never asserts the total field count (`:92-104`, unlike `assertOneof` at `:77`), so also assert that `CheckpointStart` has exactly six fields and that `slot_id` is a `SlotId` message field, otherwise a coordinated proto-plus-regen renumber of the slot-routing field passes unpinned.

### C2. `pkg/gateway/checkpoint/checkpointer/checkpointer.go`: populate `slot_id` on the gateway-side `CheckpointStart`

**Target:** `pkg/gateway/checkpoint/checkpointer/checkpointer.go` (`driveCheckpoint`, `:500-540`; `slotID` resolved at `:501-503`; the `CheckpointStart` built at `:527-535`).

**Rationale.** Without the gateway sending `slot_id`, the new wire field is dead and concurrent-session pods still cannot be checkpointed. The driver already has `binding.SlotID` in scope (`:501`). It must send the raw `binding.SlotID` (empty for single-session), rather than the `partialmanifeststore.SlotDefault` sentinel it substitutes at `:502-503` for manifest scoping, because the adapter branches on non-empty `slot_id` presence and never sees `'default'`.

**Change.** Keep the existing manifest-side substitution for the intent-row and single-flight scoping (`slotID := binding.SlotID; if slotID == "" { slotID = partialmanifeststore.SlotDefault }` at `:501-504`). When constructing the `CheckpointStart` (`:529-535`), set the wire field from the raw binding value:

```go
Start: &adapterv1.CheckpointStart{
    CheckpointId:   checkpointID,
    Trigger:        trigger.Proto(),
    ChunkSizeBytes: c.chunkSize(),
    ChunkEncoding:  string(c.chunkEncoding()),
    DeadlineMs:     c.Deadline.Milliseconds(),
    SlotId:         slotIDField(binding.SlotID), // nil when empty
}
```

where `slotIDField` returns `nil` for `""` and `&adapterv1.SlotId{Value: id}` otherwise, so a single-session attempt serializes no `slot_id` and stays on the pod-global path. Do not pass the `'default'` sentinel here.

### C3. `pkg/adapter/checkpoint.go`: slot-scoped `checkpointRoots()` and a slot gate in the `Checkpoint` handler

**Target:** `pkg/adapter/checkpoint.go` (`checkpointRoots` `:28-38`, `probeWorkspaceBytes` `:44-54`, `Checkpoint` `:73-161`, `streamChunks` `:172-226`); `pkg/adapter/slot.go` (`slotStateLocked` `:95-98`, `useSlot` `:39-41`, reused rather than changed).

**Rationale.** The archive must target the slot's live subtree, and the handler must reject a checkpoint for an unassigned slot. Because the session tmpfs is slot-scoped, both the workspace root and the sessions root swap to the slot subtree. Threading a precomputed roots slice through the probe and the archive keeps the pod-global path (`slot_id` absent) returning exactly the current bundle.

**Change (resolver).** Add a resolver that branches on slot presence:

```go
func (s *Server) checkpointRootsForSlot(slotID string) ([]workspace.NamedRoot, error) {
	if !s.useSlot(slotID) {
		return s.checkpointRoots(), nil // base path unchanged
	}
	s.mu.Lock()
	st, ok := s.slotStateLocked(slotID)
	var paths slotlayout.SlotPaths
	var sess string
	if ok {
		paths, sess = st.paths, st.sessionID
	}
	s.mu.Unlock()
	if !ok || sess == "" {
		return nil, status.Errorf(codes.FailedPrecondition,
			"slot %s has no assigned session", slotID)
	}
	roots := []workspace.NamedRoot{
		{Prefix: workspace.WorkspacePrefix, Root: paths.Current},
	}
	if paths.Sessions != "" {
		roots = append(roots, workspace.NamedRoot{
			Prefix: workspace.SessionsPrefix, Root: paths.Sessions,
		})
	}
	return roots, nil
}
```

**Change (probe and archive take roots).** Change `probeWorkspaceBytes` to take `roots []workspace.NamedRoot` and iterate it rather than calling `s.checkpointRoots()`. Change `streamChunks` to take `roots` and pass it to `workspace.ArchiveTree` (`:186`) rather than calling `s.checkpointRoots()`.

**Change (gate in `Checkpoint`).** In `Checkpoint`, after `start := first.GetStart()` and the existing `WorkspaceRoot`/`CheckpointTransport` config checks (`:80-91`), resolve the roots once and gate:

```go
roots, err := s.checkpointRootsForSlot(start.GetSlotId().GetValue())
if err != nil {
	return err
}
```

Then call `s.probeWorkspaceBytes(roots)` (`:121`) and `s.streamChunks(ctx, stream, start, trigger, roots)` (`:152`). Pass the slot identity to the op lock: `s.ops.Begin(ctx, opCheckpoint, start.GetSlotId().GetValue())` (`:97`), which C4 extends to admit each distinct per-slot checkpoint and promote pending checkpoints in slot-ID order rather than coalescing distinct slots. Keep the `WorkspaceRoot == ""` config guard (`:84`), because `WorkspaceRoot` is still set on a concurrent pod.

### C4. `pkg/adapter/oplock.go`: admit each distinct per-slot checkpoint and promote in slot-ID order

**Target:** `pkg/adapter/oplock.go` (`opLock` `:42-50`, `Begin` `:57-100`, `release` `:104-117`, `errOpCoalesced`/`errOpBusy` `:26-35`); `pkg/adapter/checkpoint.go` (the `Begin` call `:97`); `pkg/adapter/lifecycle.go` (the Interrupt `Begin` call `:36`, the op lock's second production caller); `pkg/adapter/oplock_test.go` (the existing two-argument `Begin` call sites, updated to the three-argument signature, including `TestOpLockBusyWhenSlotFullDifferentKind` at `:125`, whose `errOpBusy` assertion the new pending-interrupt rule preserves); `spec/04_system-components.md` §4.7 "Checkpoint / Interrupt mutual exclusion" (the operation-lock framing at `:673` and the "Queue depth" bullet at `:677`).

**Rationale.** The op lock keeps a single queue slot and coalesces a second checkpoint into the queued one (`oplock.go:64-72`), which drops every distinct slot beyond the one running and the one queued. A whole-pod checkpoint covers a coalesced whole-pod request, so coalescing was correct before per-slot checkpoints existed. A per-slot checkpoint covers only its own slot, so coalescing a distinct slot loses that slot's checkpoint. The gateway drain fans a concurrent pod's sessions out into one `Checkpoint` stream each (`barrier.go:200-204`, `:224-229`, `wiring.go:122-134`) and acks each target even when its checkpoint errored (`barrier.go:233-242`), so a coalesced slot is a slot that terminates without a checkpoint. `spec/05:542` requires the adapter to process one slot's checkpoint upload at a time, in slot-ID order, so the serialization and the ordering belong in the adapter.

**Change.** `Begin` gains a `slotID string` parameter, which is a breaking Go signature change with no default argument, so every caller is updated in the same edit. `Begin` has two production callers. The `Checkpoint` handler passes `start.GetSlotId().GetValue()` (C3), which is the assigned slot on a concurrent pod and the empty whole-pod id on a single-session pod. The `Interrupt` handler (`lifecycle.go:36`) passes the empty whole-pod id `""`, so interrupts continue to serialize pod-wide as they do today. The existing two-argument `Begin` call sites in `pkg/adapter/oplock_test.go` are updated to the three-argument form, passing the empty slot id for the whole-pod cases.

At most one operation runs at a time, which is unchanged. The single queue slot becomes a pending set that holds either one pending interrupt or an ordered set of pending checkpoints keyed by `slotID`. The two never mix, because an interrupt is admitted only when the pending set is empty and a checkpoint is rejected while an interrupt is pending. When `Begin` finds an operation already running:

- If an interrupt is already pending, any incoming operation (checkpoint or interrupt) returns `errOpBusy`. A pending interrupt holds the whole-pod queue and never coexists with pending checkpoints. This resolves the case a bare admit/coalesce rule leaves ambiguous (a checkpoint arriving while only an interrupt is pending), preserves the depth-one whole-pod invariant, and keeps the existing `TestOpLockBusyWhenSlotFullDifferentKind` result, where a checkpoint arriving behind a queued interrupt is rejected with `errOpBusy`.
- Otherwise, a checkpoint whose `slotID` is already pending (including the empty whole-pod id) coalesces and returns `errOpCoalesced`, because the pending checkpoint for that slot covers the request.
- Otherwise, a checkpoint whose `slotID` is not pending is admitted into the ordered pending set and waits for promotion.
- An interrupt (`slotID` is the empty whole-pod id) returns `errOpBusy` whenever the pending set is non-empty (one or more pending checkpoints), preserving the current behavior that an interrupt never displaces a pending operation. When the pending set is empty the interrupt takes the queue as it does today.

`release` promotes a pending interrupt first when one is present; otherwise it promotes the pending checkpoint with the lowest `slotID`, so slots that wait concurrently run in slot-ID order. The whole-pod path (empty `slotID`, `maxConcurrentSessions: 1` pods) is unchanged: the pending set holds at most one entry, a second whole-pod checkpoint still coalesces into a pending whole-pod checkpoint, and a checkpoint or interrupt arriving behind a pending whole-pod interrupt is still rejected with `errOpBusy`.

**Spec edit (§4.7).** `spec/04_system-components.md` §4.7 "Checkpoint / Interrupt mutual exclusion" is the authoring source for the op lock (`oplock.go:29` cites "§4.7 queue depth is one"). Its queue-depth statement (`:677`, "At most one operation may be queued") and its "per-session operation lock" framing (`:673`) describe the pre-per-slot behavior and become inaccurate for a `maxConcurrentSessions > 1` pod, which now holds one pending checkpoint per distinct `slotId`. Amend §4.7 as follows. At `:673`, describe the lock as a pod-level lock that serializes `Checkpoint` and `Interrupt` across the pod's slots; on a `maxConcurrentSessions: 1` pod the pod-level lock and the per-session lock coincide. At the `:677` "Queue depth" bullet, retain the single-session rule (at most one queued; a second same-type checkpoint coalesces; an interrupt drops with `BUSY`) and add the concurrent-session rule: the lock admits one pending checkpoint per distinct `slotId` and promotes the pending checkpoints in slot-ID order ([§5.2](05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes)); a checkpoint whose `slotId` is already pending coalesces; and while an interrupt is pending it holds the whole-pod queue, so any further checkpoint or interrupt is dropped with a `BUSY` status.

### C5. `pkg/adapter` and `pkg/gateway/coordination/barrier`: tests for per-slot capture, unassigned-slot rejection, and concurrent-drain admission

**Target:** `pkg/adapter/checkpoint_stream_test.go` (the existing `CheckpointStart`-driven stream tests, e.g. `:233`, `:280`, `:329`, `:380`); `pkg/adapter/slot_test.go` (the `concurrentServer` and `slotStartReq` helpers and the exported `StartSession` RPC, reused for slot assignment); `pkg/adapter/oplock_test.go` (the `opLock` unit harness with `waitQueued`, `:12-28`, and the existing promotion, coalesce, and interrupt-busy cases at `TestOpLockSerializesAndPromotes` `:54`, `TestOpLockCoalescesSecondQueuedCheckpoint` `:108`, `TestOpLockRejectsSecondQueuedInterrupt` `:91`, and `TestOpLockBusyWhenSlotFullDifferentKind` `:125`); `pkg/gateway/coordination/barrier` (the drain-dispatch tests, for the concurrent-drain admission case).

**Rationale.** T-4.4.21's suggested test is a tier-4 per-slot checkpoint-and-restore round trip against a `maxConcurrentSessions > 1` pool. The restore half is a companion change (see non-goals), so C5 covers the capture and serialization behaviors this fix introduces that no existing test exercises: the slot subtree is archived, an unassigned slot is rejected, three or more concurrent per-slot checkpoints are all captured rather than coalesced, and the reworked `opLock` promotes pending checkpoints in slot-ID order while still coalescing a same-slot re-fire and rejecting an interrupt while any checkpoint is pending. The `opLock` behaviors are pinned directly on the lock in `oplock_test.go`, which observes promotion order deterministically through `waitQueued`; the capture behaviors are pinned end to end in the adapter checkpoint-stream test and the barrier drain-dispatch test.

**Change.** Add three adapter sub-cases, one barrier-drain case, and three `opLock` unit sub-cases.

1. **Per-slot capture round trip.** Assign a slot via `StartSession(ctx, slotStartReq(session, slot))` on a `concurrentServer`-style `Server`, seed `/workspace/slots/{slot}/current` and `/sessions/{slot}`, open `Checkpoint` with `CheckpointStart{SlotId: {Value: slot}}`, drive the grant/PUT/commit loop, and assert the tar carries the slot's `current/` files under `WorkspacePrefix` and the slot's session file under `SessionsPrefix`, and does not carry the pod-global `/workspace/current`.
2. **Unassigned-slot rejection.** A `CheckpointStart` naming an unassigned slot returns `codes.FailedPrecondition` before any grant is minted.
3. **Concurrent per-slot admission (C4).** Assign three or more slots with distinct `slotId`s on one `Server`, seed each slot's `current/` and session subtree with slot-distinct content, open three or more `Checkpoint` streams concurrently with the distinct `SlotId`s, drive each grant/PUT/commit loop, and assert every slot's checkpoint completes and its subtree is captured, so none returns `errOpCoalesced`/`codes.Aborted` and no slot is dropped. The non-happy path is the pre-fix op lock coalescing the third and later slots, which the depth-1 queue did before C4.
4. **Concurrent drain admits every slot (C4).** In `pkg/gateway/coordination/barrier`, drive a drain over a concurrent pod with three or more occupied slots (three or more `Target`s against the one adapter) and assert each slot's checkpoint is recorded before the pod is acked as drained, so the drain does not ack a slot whose checkpoint was coalesced away. The non-happy path is a target acked (`barrier.go:242`) with a coalesced checkpoint that never captured that slot.
5. **Op lock promotes in slot-ID order (C4).** On a reworked `opLock`, take the lock with one running checkpoint, then queue several distinct-slot checkpoints in non-ascending `slotID` order (each via `Begin(ctx, opCheckpoint, slotID)`, synchronizing entry with `waitQueued`), release, and assert the pending checkpoints are promoted in ascending `slotID` order. The non-happy path is an implementation that serializes the uploads in arbitrary order, which passes every completeness assertion while violating `spec/05:542`.
6. **Op lock coalesces a same-slot re-fire, admits a distinct slot (C4).** On a reworked `opLock` with one running checkpoint, a second `Begin(ctx, opCheckpoint, slotID)` for a `slotID` already pending returns `errOpCoalesced`, while a `Begin` for a distinct `slotID` is admitted into the pending set. This replaces `TestOpLockCoalescesSecondQueuedCheckpoint` (`:108`), whose single-queue-slot assumption C4 invalidates. The non-happy path is an implementation that admits every checkpoint unconditionally, double-uploading a slot and unbounding the pending set.

## 5. Non-goals

- **Building the §4.4 individual agent-pod eviction-checkpoint trigger.** No code path fires a checkpoint when an individual agent pod is evicted by a node drain, the kubelet Eviction API, a cluster upgrade, or a direct pod delete (proposal 0047's scope, tracked as T-4.4.14). The gateway preStop/barrier drain already stamps `checkpoint.TriggerEviction` on its own scale-down fan-out (`pkg/gateway/coordination/barrier/barrier.go:228`), so the missing driver is the one fired from an evicted agent pod. That is a separate proposal.
- **Slot-scoping the restore path.** `ResumeRequest` carries no `slot_id` (`schemas/lenny-adapter.proto:1218-1286`), the adapter `Resume` performs no slot resolution (`pkg/adapter/resume.go:25-47`), and `restoreChunks` extracts into the pod-global `s.checkpointRoots()` (`pkg/adapter/resume.go:180`). A per-slot checkpoint therefore restores into `/workspace/current` and `/sessions` rather than the replacement slot's `/workspace/slots/{slotId}/current` and `/sessions/{slotId}`. Making the restore side slot-aware is the symmetric companion to this proposal: it adds `SlotId slot_id` to `ResumeRequest`, branches `Resume` onto the slot subtree the way `StartSession` already does (`pkg/adapter/session.go:103`), and wires the gateway to pass the replacement `binding.SlotID` on Resume. It is out of scope here, and T-4.4.21's per-slot round trip closes only when both halves land.
- **The other eviction-trigger prerequisites:** coordinator resolution for pod-originated signals, the agent-pod grace-period budget, and the runtime-container preStop story.
- **Closing findings T-4.4.14 (the gateway never drives the individual agent-pod eviction trigger) and T-4.6.4 (node-drain checkpoint-before-eviction).** Slot-aware capture lets a concurrent pod be checkpointed correctly on the triggers that exist today, but it does not add the individual agent-pod eviction trigger, so it closes neither. Both close when that trigger ships. This proposal does not close T-4.4.21 either, because the per-slot round trip its suggested test asserts requires the companion restore change named in the non-goal above.
- **Adding a `SessionId session_id` field to `CheckpointStart`.** See open decisions.
- **Parallelizing per-slot checkpoint uploads.** `spec/05:542` requires the adapter to process one slot's checkpoint upload at a time, in slot-ID order, to avoid MinIO write amplification. C4 extends the shared op lock to admit each distinct slot's checkpoint and serialize the uploads in slot-ID order; it does not run the uploads concurrently. Replacing the shared op lock with independent per-slot locks that permit simultaneous uploads is out of scope.
- **Spec prose edits beyond §4.7.** `spec/05:542`, `spec/06:393`, and `spec/10:141` already specify per-slot checkpoints and the `(session_id, slot_id)` key, so the capture path needs no edit to them. The one spec prose edit this proposal stages is the §4.7 queue-depth amendment in C4, which the op-lock rework requires. No other spec section changes.

## 9. Open decisions for review

- **RESOLVED on sign-off (2026-07-19): `slot_id` only; `session_id` is not added.** The slot-assignment gate (the named slot has a bound session) is the intended contract. The rebind race the `(session_id, slot_id)` binding would guard is narrow and belongs with the restore-side companion change (see non-goals) rather than the capture path. Implement C1–C5 as staged.
- **Should `CheckpointStart` also carry `SessionId session_id`?** This proposal adds `slot_id` only. The base single-session checkpoint path carries no session identity, and `slot_id` alone resolves the correct subtree, so the slot-assignment gate (the named slot has a bound session) is sufficient to reject a checkpoint for an idle or nonexistent slot. A full `(session_id, slot_id)` binding, validated via the adapter's existing `checkSlotSession` (`slotsession.go`) as all twelve other per-slot RPCs do, would additionally let the adapter reject a checkpoint whose gateway-intended session no longer matches the slot's currently bound session, for example after an unexpected slot release and rebind between the gateway's decision and the stream open. This is a minimal-surface versus defense-in-depth tradeoff. The reviewer decides whether the slot-assignment gate is the intended contract or whether the session binding is required.
