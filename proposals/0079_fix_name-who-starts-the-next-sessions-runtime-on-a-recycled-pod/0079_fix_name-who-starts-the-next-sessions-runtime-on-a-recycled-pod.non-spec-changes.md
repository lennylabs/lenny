# Non-spec changes: Name who starts the next session's runtime on a recycled pod

## 4. Detailed design

### 4.1 The transport (CODE-1, CODE-4)

The design is the state table in the spec changes' design overview and D1 through D4. Proposal 0078 lands first; CODE-1 applies on top of its CODE-1 (the occupancy-zero branch without the listener close), CODE-2 (`CloseListener`), and CODE-3 (each connection's own subscriber set passed to `fanOut`). After this proposal only one connection exists per pod, so 0078's per-connection sets stay correct and inert. CODE-4 keeps 0078's `CloseListener` name and signature, so the cleanups 0078 §7.5 registers at every `SocketRuntimeProcess` construction site, 0078's TEST-4 and TEST-6, and 0078's `cmd/lenny-adapter` call compile unchanged. The 0078 cases that assert a second accept, or a closed-listener error from a `Start` after the pod-scope teardown, are disposed of in TEST-1.

### 4.2 The liveness sample (CODE-5)

`startPodScrub` samples `ServesNextSession` after `scrub.Run` returns and after `scrubOutcome` is computed, then passes it to `ReportPodScrub`. The sample must follow the scrub, because step 4 clears the `/tmp` and `/dev/shm` mounts the runtime container shares. On a false sample it logs at `Warn` with the pod identifier. The nil-`ScrubOps` withhold path is unchanged.

The interface is declared unexported in `pkg/adapter/podscrub.go`, at the consumer: `type nextSessionRuntime interface{ ServesNextSession() bool }`. `Server.runtimeServesNextSession` returns false when `s.Runtime` is nil or does not implement it. The `RuntimeProcess` interface is unchanged, so its test doubles compile unchanged and read as not live.

### 4.3 The `Decide` branches and their position (CODE-6)

Both branches sit after the uptime branch and before the host-schedulability branch. Each replaces a reuse, so it runs after every retirement that would retire the pod anyway: a pod at `maxSessionsPerPod` or `maxPodUptimeSeconds` keeps its counting limit reason, a `vm-restart` pod keeps `vm_restart_reprovision`, and the fail-policy and scrub-exhaustion branches keep their terminal and reason. The reason-stability argument `pkg/sandbox/podscrub/podscrub.go:379-388` makes for `VMRestart` is accepted as not transferring: a `maxSessionsPerPod: 1` pool without the acknowledgment retires with the counting `session_count_limit`, while an otherwise identical `maxSessionsPerPod: 5` pool retires with `process_reuse_unacknowledged`. The first pool reached a configured limit and has been counted that way since before this proposal, so moving it would change an existing pool's metrics.

`process_reuse_unacknowledged` precedes `runtime_not_live` because it is a configuration fact that holds at every boundary of the pool, which keeps one audit reason per pool. Both precede the host-schedulability branch, because a pod that cannot reuse its runtime cannot serve the next session on any node. `ScrubWarning: warned` carries the annotation onto the drain, matching `host_unschedulable`.

### 4.4 Tenant pin admission (CODE-8)

`AdmitTenantPin` reads the Pod once, before the claim is created, at each idle-acquisition site. It admits an unpinned pod, a pod pinned to the request's tenant, and a pod whose Pod object is absent (a NotFound read), and refuses a pod whose pin names any other value, including `unassigned`. An absent Pod carries no pin and no runtime process, so admitting it exposes nothing, and the claim path already tolerates a missing Pod (`pkg/gateway/podlifecycle/podclaim/claimer.go:150-155`); claim-path fixtures that seed an idle Sandbox without a Pod, such as `sandboxIn` in `claimer_test.go` and the tier-4 and tier-8 claim fixtures, keep binding. Any other read error is returned, and the claim fails closed rather than binding the pod. When it refuses a pod pinned to another tenant and the request carries `AllowCrossTenantReuse`, it stamps the drain request. The flag reaches the claim through `BindRequest` and `ResumeRequest` from the pool match the session server already resolves; the concurrent-slot path never carries it, because cross-tenant reuse is refused on concurrent pools.

On the Postgres fallback path the check runs inside `ClaimIdle`'s transaction, after the locked `SELECT` and before the `UPDATE`, because `ClaimIdle` commits the row as `claimed` under the requesting session and tenant before it returns (`pkg/agentpodstate/pgstore/pgstore.go:233-235`, committed at `:277`). A refused row is never updated, so it stays `idle` with its prior columns, and the transaction selects the next oldest idle row.

### 4.5 Pinned idle inventory (CODE-10)

The WarmPoolController planner counts every idle Sandbox toward the pool's warm target (`pkg/controller/warmpool/plan/plan.go:111-113`) and creates `target - warmCount` pods (`:130`), with no tenant awareness. After this proposal a recycled pod returns to idle pinned to its tenant for the pod's life, and the acquisition refuses it to every other tenant. Counted as general inventory, a pool whose warm pods have each served some tenant stops provisioning, and every other tenant's claim returns `ErrNoIdlePod`, while the pod retires only on its own tenant's `maxSessionsPerPod` or on an optional `maxPodUptimeSeconds`. §5.2 already states the rule the planner lacks: "inventory accounting counts pinned-idle pods as idle inventory available to that tenant alone". The planner therefore applies the SPEC-8(c) accounting and surfaces pinned idle pods in their own count. A pod is pinned when its `lenny.dev/tenant-id` label is present and names a tenant other than `unassigned`; a missing Pod reads as unpinned.

### 4.6 What does not change

Every production caller of `RuntimeProcess.Close`, `Interrupt`, and `Start` keeps its signature: `session.go` (`tearDownReclaimedSlot`, `StartSession`), `runtimegeneration.go` (`rollbackUnconfirmedStart`), `holdstate.go` (`terminateHeldSession`), `lifecycle.go` (the `Interrupt` RPC), `heartbeat.go` (`onHeartbeatHung`), `resume.go`, and `sdkwarm.go`. `InProcessRuntime`, `SDKWarmInProcessRuntime`, `MCPRuntime`, and `executor.SubprocessExecutor` keep their `Close` and `Interrupt` behaviour. The gateway does not refuse a recycling pool without the acknowledgment, does not warn at session creation, and changes no `sessionIsolationLevel` value (D12).

## 6. Observability surface

No new metric and no new alert. The change is observable through surfaces that already exist:

- The pod's retirement audit record carries `reason: process_reuse_unacknowledged` or `reason: runtime_not_live`. `lenny_gateway_pod_retirement_total` is unchanged, because §16.1 freezes its vocabulary to the three limit triggers.
- The adapter logs a false liveness sample at `Warn` with the pod identifier, and the gateway logs a tenant-change drain at `Info` with the pool, the pod, and `reason=kept_runtime_tenant_change`.
- `lenny_pod_session_reuse_count` p50 converges toward `recycle.maxSessionsPerPod` on an acknowledged pool and is 1 on a sequential pool without the acknowledgment.
- `docs/operator-guide/troubleshooting.md` names both reasons and their resolutions (DOC-4).

## 7. CRD and RBAC changes

No CRD field, label, or RBAC verb changes. The gateway already patches agent Pods for the tenant label and the drain-request annotation. The wire contract changes: `ReportPodScrubRequest` in `schemas/lenny-adapter.proto` gains `bool runtime_live = 4;`, documented as sampled after the scrub, with an absent field meaning not live, and `pkg/proto/adapter/v1` is regenerated.
