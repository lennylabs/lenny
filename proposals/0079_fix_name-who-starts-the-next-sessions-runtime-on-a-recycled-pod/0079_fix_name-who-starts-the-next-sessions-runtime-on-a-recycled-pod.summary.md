# Summary: Name who starts the next session's runtime on a recycled pod

## Summary

**Problem statement.** problem-statement.md §1 states the problem this proposal repairs.

**What changes.**

- The runtime process lives as long as the pod on every pool and in both deployment models. The sidecar runtime's `CH-MSGSOCK` connection is accepted at the pod's first session start and closed only by the pod-scope teardown `cmd/lenny-adapter` runs at process exit (D10). A later session on a recycled pod binds as a new slot on the live connection, which is the concurrent-pool model extended across occupancy zero. The embedded runtime's process is the adapter process, which already lives as long as the pod.
- `SocketRuntimeProcess.Close` and `Interrupt` stop tearing the transport down, and the active set that decided the teardown is deleted. The transport records a sticky ended state when the runtime closes its end, and `Start` and `Output` fail at once after it.
- The adapter reports on `ReportPodScrub`, in a new `runtime_live` field sampled after the whole-pod scrub, whether its runtime can serve the next session. `pkg/sandbox/podscrub.Decide` retires the pod with `runtime_not_live` when the report says it cannot or omits the field.
- `Decide` retires the pod with `process_reuse_unacknowledged` when the pool does not set `sessionPolicy.acknowledgeProcessLevelIsolation: true`. Both new reasons are non-counting and sit after the session-count and uptime retirements, and the gateway logs the reason of every `released` retire at `Info`.
- The gateway reads the tenant pin on every idle-pod acquisition, including the Postgres fallback claim, and refuses a pod pinned to another tenant. On an `allowCrossTenantReuse` pool it also drains that pod. The fallback claim stamps the pin and leaves the mirror row unchanged when it refuses a pod. The warm-pool planner keeps pinned idle pods out of the unpinned inventory that satisfies `minWarm` and drains those that do not fit under `maxWarm`, which is the interim rule (SPEC-8(c), D14).
- The §15.4.2 terminate frame is no longer sent at occupancy zero, and the pod-exit path sends it once. The runtime generation no longer resets when `runtimeLive` empties, so `soleSession` is empty on every session after a kept process's first.
- §4.6.1, §4.6.3, §4.7, §4.7.9, §4.7.10, §5.1, §5.2, §6.1, §6.2, §7.1, §11.4, §13.1, §15.4, §15.4.1, §15.4.2, §15.4.3, §16.1, §17.8.2, §28.5.3, §28.8, §29.2, §29.4, and §29.9 state the lifetime, the acknowledgment, the tenant rule, the new retire reasons, the scrub's reach, and the widened disclosure.

**Decisions.**

- The runtime process is kept across occupancy zero, by the human decision of 2026-09-30 (problem statement §1.7). No step reintroduces a close at occupancy zero or a runtime redial.
- The adapter rule is unconditional. The adapter reads no recycle, acknowledgment, or cross-tenant setting, because every pool that must not reuse a pod retires it through the gateway after occupancy zero.
- `vm-restart` pools are untouched. The `VMRestart` branch runs before every new branch, and the per-release `maxSessionsPerPod` drain and its `vm-restart` exclusion (`pkg/gateway/session/recycle/scrubreporter_seams.go:373`) are not edited.
- New `Decide` and `PodRecyclePolicy` fields are true to retire, so every existing literal keeps its disposition. The wire field is positive, so an absent `runtime_live` reads as not live.
- This proposal reverses part of proposal 0073's SCHEMA-1 ("`Runtime.Close` is unchanged by this deliverable, in signature and in behavior") for `SocketRuntimeProcess`. Proposal 0073 is not edited.
- Pinned idle inventory ships the interim rule, by the human decision of 2026-09-30 (option D, D14). SPEC-8(c) is its one home, and spec-changes §9.1, **Pinned idle bound and idle timeout**, states what the follow-up adds.
- Each new retire condition is stated once, in the §5.2 Pod retirement policy (D15). Every other staged specification site names the condition by its label, and TEST-16 fails on a restatement.

**Watch out for.**

- **The earlier attempt.** Commits 8cdd5d6d through ccaeb30d, reverted by 39e08bb4, oscillated between keeping and closing the runtime inside proposal 0073, against spec text that required closing. Their facets (drain-frame suppression, a generation reset failing open, runtime redial, a phantom sibling in the active set, a reader closing the wrong subscribers, and a parked accept goroutine) are closed here by deletion or by the sticky ended state. None returns while nothing tears the transport down per session, the terminate frame is not sent at occupancy zero, the generation does not reset, and nothing redials.
- **Ordering against proposal 0078.** 0078 keeps the listener and leaves `Close`'s occupancy-zero connection close in place, so landed alone it turns a recycled sidecar pod's failed second `Start` from immediate into a 30-second accept wait. Land 0078 immediately before this proposal. CODE-4 extends 0078's `CloseListener` and keeps its name and signature, so 0078's callers and test cleanups compile unchanged. 0078's TEST-1 and TEST-9 assert a second accept after the last `Close`, which the kept connection removes; TEST-1 disposes of them.
- **Runtimes written for one session per process.** The Go runtime SDK binds `OnCreate`, the manifest session, and the credential path once per process (`sdks/runtime/go/runtime/runtime.go:76-84`), and no frame tells a runtime that a session ended. On an acknowledged pool such a runtime receives a later session's frames under the first session's context. The same gap exists on concurrent pools today (open decision 3).
- **The Postgres fallback claim reads and writes no tenant pin** (`pkg/gateway/podlifecycle/podsession/fallbackclaim.go:91-133`, `pkg/agentpodstate/pgstore/pgstore.go:245-279`). CODE-8 closes it in the same step that keeps a runtime across tenants' reach.
- **Scrub reach does not follow from `shareProcessNamespace: false` alone.** `buildSidecar` mounts `workspace`, the credential volume, `tmp`, `sessions`, `artifacts`, `/dev/shm`, and `shared` into both containers (`pkg/controller/sandbox/podspec/podspec.go:536-557`), so the filesystem steps cross the boundary. Step 1b removes only the adapter UID's segments.
- **The tier-11 pinned phrases.** `tests/tier11_docs/vm_restart_reprovision_consistency_test.go:176-209` pins phrases in the §5.2 recycle-lifecycle sentence and the §6.2 projection sentence. SPEC-5 and SPEC-9 append to those sentences without rewording them.
- **The pinned-idle bound on admin-API pools** is zero only until demand is observed (D14); a finding that assumes it is always zero is wrong.
- **`cmd/lenny-adapter/main.go:86-88` states a "shared-uid pod layout".** The pod renders the adapter and runtime under distinct UIDs, and CODE-9 corrects the comment.

## Defects in the shipped tree that this proposal does not stage

- **The §16.1 `lenny_gateway_pod_retirement_total` row omits the gateway's non-counting retire reasons.** The row (`spec/16_observability.md:12`) lists the `reason` values `session_count_limit` and `scrub_failure_limit` and does not state that the gateway's other retire reasons go uncounted. The shipped gateway retires with three such reasons, `host_unschedulable`, `scrub_report_timeout`, and `vm_restart_reprovision` (`pkg/sandbox/podscrub/podscrub.go:197`, `:211`, and `:226`), for which `CountsOnGatewayRetirementTotal` reports false (`pkg/sandbox/podscrub/podscrub.go:244-251`, `:270-272`). The spec names only `vm_restart_reprovision` among the three, in §5.2 (`spec/05_runtime-registry-and-pool-model.md:504`). This proposal does not stage a fix. SPEC-7 declares its two new reasons, `process_reuse_unacknowledged` and `runtime_not_live`, non-counting and names them in §5.2, so the row stays accurate about the values the counter emits, and no staged change depends on editing the row (spec-changes.md, the §16.1 retirement-counter row non-goal).
- **The sidecar runtime reads the adapter manifest before the adapter writes it on a pod's first session.** The sidecar runtime container starts with the pod, and the Go runtime SDK reads the manifest as soon as its transport opens (`sdks/runtime/go/runtime/runtime.go:225` and `:237`). A missing file is logged and leaves the runtime with no manifest (`sdks/runtime/go/runtime/runtime.go:562-567`), and the SDK then degrades to the level the manifest supports and dials no platform MCP server or `CH-RUNTIMEOPS` (`sdks/runtime/go/runtime/runtime.go:310-322`). The adapter writes the manifest only when a session starts (`pkg/adapter/session.go:129`, `pkg/adapter/sdkwarm.go:238`, and `pkg/adapter/resume.go:138`). The spec states the reverse order in the sentences that describe the manifest as written before the runtime is spawned, such as the §4.7 adapter manifest (`spec/04_system-components.md:775`), and the §9.1 manifest-ordering non-goal in spec-changes.md lists every such site. This proposal does not stage a fix, because the defect affects the first session of every sidecar pod whether or not the pod is recycled, and the proposal keeps those sentences as they stand. SPEC-1's later-session sentence and the SPEC-12(a) relabel of §29.2 steps 26a through 28 assume that the first session's manifest read succeeds, so they hold in the tree only once the ordering is fixed.
- **Whole-pod scrub steps 3 and 5 never run, and no component re-runs the SDK pre-connect after a recycle.** The §5.2 scrub procedure requires step 3 to purge the previous session's injected environment variables and step 5 to truncate the adapter-local log buffers (`spec/05_runtime-registry-and-pool-model.md:484` and `:486`). `Server.scrubConfig` sets neither `ResetEnv` nor `TruncateLogs` in the `scrub.Config` it builds (`pkg/adapter/podscrub.go:120-129`, literal at `:123-128`), and the scrub records a step whose callback is nil as skipped (`pkg/adapter/scrub/scrub.go:157-165`, `:267`, and `:271`). §6.1 and §6.2 have the adapter re-establish SDK-warm state on the `claimed → sdk_connecting` re-warm edge after a preConnect pod's scrub report (`spec/06_warm-pod-model.md:74` and `:166`). The only production call to `Server.PreConnect` (`pkg/adapter/sdkwarm.go:152`) is the one at adapter startup in `cmd/runtimes/preconnect-echo/main.go:156`. This proposal does not stage a fix, because both gaps predate it and no staged deliverable depends on either step running or on the re-warm. SPEC-6's sentence that steps 3 and 5 act on the adapter's own environment and log buffers describes what the specified steps reach rather than what the tree runs, and SPEC-5(a), SPEC-4(c), and SPEC-9(f) narrow the pods that take the re-warm without relying on it. The §9.1 non-goal in spec-changes.md files both separately.
- **The embedded reference runtimes wire no whole-pod scrub operations, so an embedded recycling pod never reports its scrub.** Only `cmd/lenny-adapter/main.go:341` assigns `ScrubOps`. `cmd/runtimes/echo-embedded` and `cmd/runtimes/preconnect-echo` assign none, although both obtain a `PodScrubReporter` through `ConnectGateway` (`cmd/runtimes/echo-embedded/main.go:145`, `cmd/runtimes/preconnect-echo/main.go:121`, and `pkg/adapter/gatewaylink.go:69`). When `ScrubOps` is nil, `startPodScrub` returns before the scrub runs and withholds the `ReportPodScrub` (`pkg/adapter/podscrub.go:48-61`), so the gateway retires the pod through the missing-report timeout with `scrub_report_timeout`. This proposal does not stage a fix, because the gap predates it and no staged deliverable needs an embedded recycling pod to reach the report: TEST-7 exercises `InProcessRuntime.ServesNextSession` at unit level, TEST-11 and FIXTURE-1 run on `task-mode-echo-pool` with a sidecar runtime (`tests/testinfra/kind/install.sh:842-853`), and no fixture pool on an embedded runtime enables recycling (`tests/testinfra/kind/install.sh:773-787`). The staged `runtime_not_live` retire and `process_reuse_unacknowledged` gate are evaluated only when a report arrives, so they go unexercised on embedded pods, and open decision 2 concerns an embedded behaviour the reference runtimes cannot yet exhibit. The §5 embedded row and the §9.1 non-goal in spec-changes.md file it separately.
- **`Claimer.Claim` leaves its bound claim in place when the tenant stamp fails, and the registry `ClaimPod` implementations read no tenant pin.** After `CreateClaim` and `writeBoundStatus` succeed, `Claimer.Claim` returns the `stampPodTenant` error without deleting the `SandboxClaim` (`pkg/gateway/podlifecycle/podclaim/claimer.go:157-159`), whereas `reserveSlot` deletes a fresh claim on the same failure (`pkg/gateway/podlifecycle/podclaim/slotclaimer.go:723-733`). `CRDPodRegistry.ClaimPod` (`pkg/podregistry/crd.go:170-209`) claims an idle pod without reading its tenant pin, as do `PostgresPodRegistry.ClaimPod` (`pkg/podregistry/postgres.go:212-260`) and `AgentSandboxPodLifecycleManager.ClaimPod` (`pkg/podlifecycle/agentsandbox.go:166-212`). No non-test code calls any of the three: the gateway builds an `AgentSandboxPodLifecycleManager` (`cmd/lenny-gateway/reconciler_workers.go:92`) and calls only `GetPodStatus` on it (`cmd/lenny-gateway/worker_seams.go:55`). This proposal does not stage a fix, because neither defect lies on the recycle-boundary mechanism. CODE-8 places `AdmitTenantPin` on the three production acquisition paths, which are the idle scan, the concurrent-slot idle pass, and the Postgres fallback claim (CODE-8), so the staged §5.2 sentence that the gateway reads the pin on every idle-pod acquisition (SPEC-8(c)) holds without the `ClaimPod` implementations. CODE-8 models the fallback's stamp-failure cleanup on `reserveSlot` rather than on `Claim` (CODE-8), and no staged test exercises a stamp failure in `Claim`. A failed stamp returns an error, so no session runs on the pod through the leaked claim. The §9.1 non-goal in spec-changes.md files both separately.

- **The specification promises adapter signals, a `shutdown` frame, and exit-code observation that no production transport performs.** The sidecar adapter shares no process namespace with the runtime container, `SocketRuntimeProcess` holds a process handle only for the test-only `SpawnPath` child (`pkg/adapter/socketruntime.go:62-65`, `:302-315`), `pkg/adapter` writes no `CH-MSGSOCK` `shutdown` frame, and the only transport that reads a runtime's exit status and stderr is the developer-loop `SubprocessExecutor` (`pkg/gateway/session/executor/subprocess.go:309-333`). The runtime container carries no preStop hook, so at pod deletion the kubelet, rather than the adapter, sends it SIGTERM and then SIGKILL at `terminationGracePeriodSeconds`. The review log's blast-radius table lists the sentences that state otherwise, as classes P1 and P2 (spec-changes §9.1). This proposal does not stage a fix, because each sentence was false before it and it changes none of these facts.
