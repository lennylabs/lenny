# Summary: Name who starts the next session's runtime on a recycled pod

## Summary

**Problem statement.** A recycling pool with `recycle.maxSessionsPerPod > 1` never serves a second session on a sidecar pod. The specification states that the platform starts a fresh runtime process for each session. In the default sidecar deployment model the kubelet starts the runtime container once, no component starts it again, and the adapter ends the runtime at occupancy zero by closing its connection. The gateway still reuses the scrubbed pod, the next session's start waits out the accept bound and fails, and the gateway retries the session on another pod, so the pod is never reused and a pool sized by `mode_factor` is provisioned for a fraction of the pods it needs. The specification also names the adapter as the process that spawns the runtime in §4.7.9 step 7, and it states that the whole-pod scrub terminates the runtime's SDK process, which the scrub cannot reach. The proposal closes BUILD-GAPS F-5.2.33 part (b); proposal 0078 closes part (a).

**What changes.**

- The runtime process lives as long as the pod on every pool and in both deployment models. The sidecar runtime's `CH-MSGSOCK` connection is accepted at the pod's first session start and closed only by the pod-scope teardown, which `cmd/lenny-adapter` runs at process exit and the adapter runs when the coordinator hold times out (D10). A later session on a recycled pod binds as a new slot on the live connection, which is the concurrent-pool model extended across occupancy zero. The embedded runtime's process is the adapter process, which already lives as long as the pod.
- `SocketRuntimeProcess.Close` and `Interrupt` stop tearing the transport down, and the active set that decided the teardown is deleted. The transport records a sticky ended state when the runtime closes its end, and `Start` and `Output` fail at once after it.
- The adapter reports on `ReportPodScrub`, in a new `runtime_live` field sampled after the whole-pod scrub, whether its runtime can serve the next session. `pkg/sandbox/podscrub.Decide` retires the pod with `runtime_not_live` when the report says it cannot or omits the field.
- Pool admission refuses a recycling pool that keeps its runtime process across sessions without `sessionPolicy.acknowledgeProcessLevelIsolation: true`, on create, update, bootstrap seed, and dry-run (D5, CODE-11). The new `runtime_not_live` reason is non-counting and sits after the session-count and uptime retirements, and the gateway logs the reason of every `released` retire at `Info`.
- The gateway reads the tenant pin on every idle-pod acquisition, including the Postgres fallback claim, and refuses a pod pinned to another tenant. On an `allowCrossTenantReuse` pool it also drains that pod. On a pool whose configuration keeps no runtime process across sessions, which an admitted edit can produce, every acquisition, including the reserved-hold rebind, refuses a pod that has served a session (D16). The fallback claim stamps the pin and leaves the mirror row unchanged when it refuses a pod. The warm-pool planner keeps pinned idle pods out of the unpinned inventory that satisfies `minWarm` and drains those that do not fit under `maxWarm`, which is the interim rule (SPEC-8(c), D14).
- The adapter no longer sends the `CH-RUNTIMEOPS` `terminate` frame, whose only send was at occupancy zero, `drainViaLifecycle` is deleted, and §15.4.2 and §15.4.3 state that no drain coordination exists at pod exit (D8). The runtime generation no longer resets when `runtimeLive` empties, so `soleSession` is empty on every session after a kept process's first.
- §4.6.1, §4.6.3, §4.7, §4.7.9, §4.7.10, §5.1, §5.2, §6.1, §6.2, §7.1, §10.1.4, §11.4, §13.1, §15.4, §15.4.1, §15.4.2, §15.4.3, §16.1, §17.8.2, §28.3, §28.5.3, §28.8, §29.2, §29.4, and §29.9 state the lifetime, the acknowledgment, the tenant rule, the admission rule, the new retire reason, the scrub's reach, and the widened disclosure.

**Decisions.**

- The runtime process is kept across occupancy zero, by the human decision of 2026-09-30 (problem statement §1.7). No step reintroduces a close at occupancy zero or a runtime redial.
- The adapter rule is unconditional. The adapter reads no recycle, acknowledgment, or cross-tenant setting, because pool admission refuses a pool that would keep its runtime without the acknowledgment, and every other pool that must not reuse a pod retires it through the gateway after occupancy zero.
- `vm-restart` pools are untouched. The `VMRestart` branch runs before the new branch, and the per-release `maxSessionsPerPod` drain and its `vm-restart` exclusion (`pkg/gateway/session/recycle/scrubreporter_seams.go:373`) are not edited.
- The new `Decide` input `RuntimeNotLive` is true to retire, so every existing literal keeps its disposition. The wire field is positive, so an absent `runtime_live` reads as not live.
- This proposal reverses part of proposal 0073's SCHEMA-1 ("`Runtime.Close` is unchanged by this deliverable, in signature and in behavior") for `SocketRuntimeProcess`. Proposal 0073 is not edited.
- Pinned idle inventory ships the interim rule, by the human decision of 2026-09-30 (option D, D14). SPEC-8(c) is its one home, and spec-changes §9.1, **Pinned idle bound and idle timeout**, states what the follow-up adds.
- The new retire condition is stated once, in the §5.2 Pod retirement policy item "Runtime not live" (D15). Every other staged specification site names it by its label, and TEST-16 fails on a restatement.
- Pod-global surfaces fail closed on every session after a kept process's first, and proposal 0084 carries per-session attribution (spec-changes §12, decision 1).
- Pool admission refuses a recycling pool that would keep its runtime process across sessions without `sessionPolicy.acknowledgeProcessLevelIsolation: true`, and no recycle-boundary retire re-checks the rule (spec-changes §12, decision 2, Alternative B; D5, CODE-11).
- A follow-up proposal carries the runtime SDKs' multi-session change and the Go SDK's doc-comment correction, and checklist S19 waits for it. This proposal stages the `sessionId` keying statements in the specification and the runtime-author guide, and it edits no file under `sdks/` (spec-changes §12, decisions 3 and 7).
- Proposal 0078 lands first and unchanged (spec-changes §12, decision 4).
- No adapter path sends the `CH-RUNTIMEOPS` `terminate` frame, and the specification states that no drain coordination exists at pod exit (spec-changes §12, decision 5; D8). The pod-exit drain belongs to remediation-plan steps R16 and R17.
- An admitted edit that takes a pool outside the process-reuse rule ends reuse at the next acquisition, by the human decision of 2026-10-01 (spec-changes §12, decision 6; D16). Every acquisition, including the reserved-hold rebind and the Postgres fallback, refuses a pod that has served a session (D16), so `sessionIsolationLevel` never understates a kept process for the claim made at creation. SPEC-8(d) is the rule's one home.
- The CODE-7 `Info` log records a `released` retire's reason, SPEC-5(b) names "Runtime not live", and DOC-6 stays its own deliverable (spec-changes §12, decisions A, B, and C).

## Goals

- A recycled pod serves its pinned tenant's later sessions with the runtime process that served the first, until `recycle.maxSessionsPerPod` or another retire trigger ends the pod, in both deployment models.
- Pool admission accepts process reuse only on a pool that sets `sessionPolicy.acknowledgeProcessLevelIsolation: true`.
- A kept runtime process serves one tenant. Every idle-pod acquisition reads the tenant pin and refuses a pod pinned to another tenant, and the warm-pool planner keeps pinned idle pods out of the inventory that satisfies `minWarm`. After an admitted edit takes a pool outside the process-reuse rule, no acquisition places a session on a pod that has served one.
- A pod whose runtime cannot serve the next session retires at the recycle boundary with `runtime_not_live`, and a runtime that stops during the `reserved` hold fails the next start at once.
- The specification names who starts the runtime process, states its lifetime and what the whole-pod scrub reaches, and discloses to clients that a recycled session may run in a runtime process that served an earlier session of the same tenant.
- The proposal closes part (b) of BUILD-GAPS finding F-5.2.33.

## Non-goals

spec-changes.md §9.1 carries the detail and the evidence for each item.

- The platform does not re-create a runtime process inside a pod. A runtime that stops ends the pod's service through the `runtime_not_live` retire or the failed-start drain.
- The runtime SDKs' support for sequential sessions, and any end-of-session signal to the runtime, belong to a follow-up runtime-SDK proposal (spec-changes §12, decision 3).
- Per-session attribution of intra-pod MCP calls and direct-mode token usage on a runtime process that has served more than one session belongs to proposal 0084 (§12, decision 1).
- A drain signal to the runtime at pod exit belongs to remediation-plan steps R16 and R17 (spec-changes §9.1).
- A bound on pinned idle pods beyond `maxWarm` and an idle timeout for pinned pods belong to a follow-up proposal (D14).
- The pod-scoped listener teardown belongs to proposal 0078, which lands first.
- Per-slot cleanup and the per-release `maxSessionsPerPod` drain with its `vm-restart` exclusion are unchanged.
- The defects listed under **Defects in the shipped tree that this proposal does not stage**, including adapter exit at the coordinator hold timeout and a gateway consumer of `AdapterTerminating`, and the §6.2 `idle ──→ draining` trigger list, are filed separately.

Step identifiers refer to the implementation checklist.

1. **Sidecar `preConnect`.** Should §6.1 restrict `preConnect`, the SDK-warm pod mode, to the embedded deployment model? After SPEC-1 and SPEC-2 the adapter starts and restarts no process in a sidecar runtime container, so a sidecar pod has no mechanism that makes it SDK-warm. The only SDK-warm runtime in the tree is the embedded `SDKWarmInProcessRuntime`. The specification states no such restriction today, and the gap predates this proposal. The review log records no recommendation.
2. **Drains per acquisition on an `allowCrossTenantReuse` pool.** Should one acquisition drain at most one refused pinned pod? As SPEC-8(c) stages it, an acquisition stamps the drain request on every pinned pod its scan refuses to a different tenant, so when no admissible pod exists, one claim drains the pool's entire pinned idle inventory. The reviewer did not file it as a defect, because the replacements add unpinned capacity during exhaustion and the behaviour agrees with D6. The review log records no recommendation.
3. **The Postgres fallback's pin read inside the row lock.** Should the fallback claim keep calling `AdmitTenantPin` inside the `SELECT ... FOR UPDATE` transaction of `ClaimIdle`? ## Defects in the shipped tree that this proposal does not stage

- **The §16.1 `lenny_gateway_pod_retirement_total` row omits the gateway's non-counting retire reasons.** The row (`spec/16_observability.md:12`) lists the `reason` values `session_count_limit` and `scrub_failure_limit` and does not state that the gateway's other retire reasons go uncounted. The shipped gateway retires with three such reasons, `host_unschedulable`, `scrub_report_timeout`, and `vm_restart_reprovision` (`pkg/sandbox/podscrub/podscrub.go:197`, `:211`, and `:226`), for which `CountsOnGatewayRetirementTotal` reports false (`pkg/sandbox/podscrub/podscrub.go:244-251`, `:270-272`). The spec names only `vm_restart_reprovision` among the three, in §5.2 (`spec/05_runtime-registry-and-pool-model.md:504`). This proposal does not stage a fix. SPEC-7 declares its new reason, `runtime_not_live`, non-counting and names it in §5.2, so the row stays accurate about the values the counter emits, and no staged change depends on editing the row (spec-changes.md, the §16.1 retirement-counter row non-goal).
- **The sidecar runtime reads the adapter manifest before the adapter writes it on a pod's first session.** The sidecar runtime container starts with the pod, and the Go runtime SDK reads the manifest as soon as its transport opens (`sdks/runtime/go/runtime/runtime.go:225` and `:237`). A missing file is logged and leaves the runtime with no manifest (`sdks/runtime/go/runtime/runtime.go:562-567`), and the SDK then degrades to the level the manifest supports and dials no platform MCP server or `CH-RUNTIMEOPS` (`sdks/runtime/go/runtime/runtime.go:310-322`). The adapter writes the manifest only when a session starts (`pkg/adapter/session.go:129`, `pkg/adapter/sdkwarm.go:238`, and `pkg/adapter/resume.go:138`). The spec states the reverse order in the sentences that describe the manifest as written before the runtime is spawned, such as the §4.7 adapter manifest (`spec/04_system-components.md:775`), and the §9.1 manifest-ordering non-goal in spec-changes.md lists every such site. This proposal does not stage a fix, because the defect affects the first session of every sidecar pod whether or not the pod is recycled, and the proposal keeps those sentences as they stand. SPEC-1's later-session sentence and the SPEC-12(a) relabel of §29.2 steps 26a through 28 assume that the first session's manifest read succeeds, so they hold in the tree only once the ordering is fixed.
- **Whole-pod scrub steps 3 and 5 never run, and no component re-runs the SDK pre-connect after a recycle.** The §5.2 scrub procedure requires step 3 to purge the previous session's injected environment variables and step 5 to truncate the adapter-local log buffers (`spec/05_runtime-registry-and-pool-model.md:484` and `:486`). `Server.scrubConfig` sets neither `ResetEnv` nor `TruncateLogs` in the `scrub.Config` it builds (`pkg/adapter/podscrub.go:120-129`, literal at `:123-128`), and the scrub records a step whose callback is nil as skipped (`pkg/adapter/scrub/scrub.go:157-165`, `:267`, and `:271`). §6.1 and §6.2 have the adapter re-establish SDK-warm state on the `claimed → sdk_connecting` re-warm edge after a preConnect pod's scrub report (`spec/06_warm-pod-model.md:74` and `:166`). The only production call to `Server.PreConnect` (`pkg/adapter/sdkwarm.go:152`) is the one at adapter startup in `cmd/runtimes/preconnect-echo/main.go:156`. This proposal does not stage a fix, because both gaps predate it and no staged deliverable depends on either step running or on the re-warm. SPEC-6's sentence that steps 3 and 5 act on the adapter's own environment and log buffers describes what the specified steps reach rather than what the tree runs, and SPEC-9(f) narrows the pods that take the re-warm without relying on it. The §9.1 non-goal in spec-changes.md files both separately.
- **The embedded reference runtimes wire no whole-pod scrub operations, so an embedded recycling pod never reports its scrub.** Only `cmd/lenny-adapter/main.go:341` assigns `ScrubOps`. `cmd/runtimes/echo-embedded` and `cmd/runtimes/preconnect-echo` assign none, although both obtain a `PodScrubReporter` through `ConnectGateway` (`cmd/runtimes/echo-embedded/main.go:145`, `cmd/runtimes/preconnect-echo/main.go:121`, and `pkg/adapter/gatewaylink.go:69`). When `ScrubOps` is nil, `startPodScrub` returns before the scrub runs and withholds the `ReportPodScrub` (`pkg/adapter/podscrub.go:48-61`), so the gateway retires the pod through the missing-report timeout with `scrub_report_timeout`. This proposal does not stage a fix, because the gap predates it and no staged deliverable needs an embedded recycling pod to reach the report: TEST-7 exercises `InProcessRuntime.ServesNextSession` at unit level, TEST-11 and FIXTURE-1 run on `task-mode-echo-pool` with a sidecar runtime (`tests/testinfra/kind/install.sh:842-853`), and no fixture pool on an embedded runtime enables recycling (`tests/testinfra/kind/install.sh:773-787`). The staged `runtime_not_live` retire is evaluated only when a report arrives, so it goes unexercised on embedded pods. The admission rule (CODE-11) reads no report and applies to embedded pools as it does to sidecar pools. The §5 embedded row and the §9.1 non-goal in spec-changes.md file it separately.
- **`Claimer.Claim` leaves its bound claim in place when the tenant stamp fails, and the registry `ClaimPod` implementations read no tenant pin.** After `CreateClaim` and `writeBoundStatus` succeed, `Claimer.Claim` returns the `stampPodTenant` error without deleting the `SandboxClaim` (`pkg/gateway/podlifecycle/podclaim/claimer.go:157-159`), whereas `reserveSlot` deletes a fresh claim on the same failure (`pkg/gateway/podlifecycle/podclaim/slotclaimer.go:723-733`). `CRDPodRegistry.ClaimPod` (`pkg/podregistry/crd.go:170-209`) claims an idle pod without reading its tenant pin, as do `PostgresPodRegistry.ClaimPod` (`pkg/podregistry/postgres.go:212-260`) and `AgentSandboxPodLifecycleManager.ClaimPod` (`pkg/podlifecycle/agentsandbox.go:166-212`). No non-test code calls any of the three: the gateway builds an `AgentSandboxPodLifecycleManager` (`cmd/lenny-gateway/reconciler_workers.go:92`) and calls only `GetPodStatus` on it (`cmd/lenny-gateway/worker_seams.go:55`). This proposal does not stage a fix, because neither defect lies on the recycle-boundary mechanism. CODE-8 places `AdmitTenantPin` on the three production acquisition paths, which are the idle scan, the concurrent-slot idle pass, and the Postgres fallback claim (CODE-8), so the staged §5.2 sentence that the gateway reads the pin on every idle-pod acquisition (SPEC-8(c)) holds without the `ClaimPod` implementations. CODE-8 models the fallback's stamp-failure cleanup on `reserveSlot` rather than on `Claim` (CODE-8), and no staged test exercises a stamp failure in `Claim`. A failed stamp returns an error, so no session runs on the pod through the leaked claim. The §9.1 non-goal in spec-changes.md files both separately.

- **The specification promises adapter signals, a `shutdown` frame, and exit-code observation that no production transport performs.** The sidecar adapter shares no process namespace with the runtime container, `SocketRuntimeProcess` holds a process handle only for the test-only `SpawnPath` child (`pkg/adapter/socketruntime.go:62-65`, `:302-315`), `pkg/adapter` writes no `CH-MSGSOCK` `shutdown` frame, and the only transport that reads a runtime's exit status and stderr is the developer-loop `SubprocessExecutor` (`pkg/gateway/session/executor/subprocess.go:309-333`). The runtime container carries no preStop hook, so at pod deletion the kubelet, rather than the adapter, sends it SIGTERM and then SIGKILL at `terminationGracePeriodSeconds`. The review log's blast-radius table lists the sentences that state otherwise, as classes P1 and P2 (spec-changes §9.1). This proposal does not stage a fix, because each sentence was false before it and it changes none of these facts.

- **A coordinator hold timeout neither exits the adapter nor reaches a gateway consumer.** `onHoldTimeout` terminates the pod's sessions and returns without exiting (`pkg/adapter/holdstate.go:177-211`). No gateway code consumes `AdapterTerminating`: the only matches outside `pkg/adapter` are the `orphansession` package comment (`pkg/gateway/session/orphansession/orphansession.go:9`) and the generated gRPC comment (`pkg/proto/adapter/v1/lenny-adapter_grpc.pb.go:256`). The runtime container runs with `RestartPolicyNever` (`pkg/controller/sandbox/podspec/podspec.go:980`). The §10.1.4 orphan-session reconciler therefore never sees a `terminated` pod after a hold timeout (`orphansession.go:14-17`). This proposal does not stage a fix, because the gap predates it and the staged credential boundary does not depend on pod termination: CODE-4 ends the sidecar runtime's connection at the timeout, and the pod then retires through the `runtime_not_live` report, the failed-start drain, or the §4.6.1 orphan-claim drain (`pkg/controller/warmpool/gc.go:96-104`).
