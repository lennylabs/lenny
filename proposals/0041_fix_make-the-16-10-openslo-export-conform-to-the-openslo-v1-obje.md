# Proposal: Make the §16.10 OpenSLO export conform to the OpenSLO v1 object model with a self-contained, deployer-configurable AlertNotificationTarget: split each policy to one condition, emit a shared AlertNotificationTarget referenced by targetRef, and render alertPolicyRef object entries

- **Status:** Verified (2026-07-16). Converged after 3 adversarial review rounds (1 findings fixed); awaiting sign-off.
- **Date:** 2026-07-16.
- **Scope:** A spec-first reconciliation of the §16.10 OpenSLO export (`pkg/alerting/rules/openslo.go`, `RenderOpenSLO`) to the OpenSLO v1 object model it already advertises with `apiVersion: openslo/v1`. It lands a §16.10 spec edit that names `AlertNotificationTarget` as an emitted document kind and defines the deployer-configurable `monitoring.openslo.notificationTarget` surface, then implements the code, schema, and tests against it. The code splits each SLO's two-condition AlertPolicy into two single-condition AlertPolicy documents (`<name>-burnrate-fast`, `<name>-burnrate-slow`), emits one shared top-level `AlertNotificationTarget` document per fragment referenced from every AlertPolicy via `notificationTargets: [{targetRef: lenny-slo-notifications}]`, and renders each SLO `alertPolicies` entry as an `{alertPolicyRef: <name>}` object. It touches `spec/16_observability.md`, `pkg/alerting/rules/openslo.go`, `pkg/alerting/rules/openslo_test.go`, `tests/testdata/openslo/schema/openslo-v1.schema.json`, `tests/testdata/openslo/README.md`, `pkg/ctlcli/slo.go`, `cmd/gen-alerting-rules/main.go`, `charts/lenny/values.yaml`, `charts/lenny/templates/openslo-configmap.yaml`, `charts/lenny/tests/openslo-configmap_test.yaml`, `tests/spec-map.json`, the two code-generated artifacts (`charts/lenny/files/openslo.yaml`, `docs/alerting/openslo.yaml`), and un-skips the tier-0 conformance test (`tests/tier0_static/openslo_export_test.go`). It runs entirely at chart-generation and test time and carries no runtime or operator-hardware dependency. It supersedes proposal 0040 (git `898f3afd`), which converged on a code-only bare-`targetRef` design the reviewer directed to a self-contained, deployer-configurable form.

This document stages the proposed spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off, spec edit first.

## 1. Problem

The §16.10 OpenSLO export advertises OpenSLO v1 documents (`apiVersion: openslo/v1`, `pkg/alerting/rules/openslo.go:15`) but emits documents that violate the OpenSLO v1 object model in three ways, so a conformant tool (Sloth, Nobl9, OpenSLO Reliably) rejects them. The vendored authored schema (`tests/testdata/openslo/schema/openslo-v1.schema.json`) transcribes these constraints from the OpenSLO README and cross-checks them against the OpenSLO Go SDK `govy` validators (`tests/testdata/openslo/README.md:20-33`). The tier-0 conformance test `TestOpenSLOChartFragmentMatchesSpecification` (`tests/tier0_static/openslo_export_test.go`) validates the generated fragment `charts/lenny/files/openslo.yaml` against that schema and is `t.Skip`-ped (`:62-67`) pending this decision.

### (A) An AlertPolicy carries two conditions against the one-condition cap

Each SLO renders one AlertPolicy whose `spec.conditions` packs two inline AlertCondition entries: the fast/critical condition (`openslo.go:189-203`) and the slow/warning condition (`openslo.go:204-218`). OpenSLO v1 caps `spec.conditions` at exactly one entry (`openslo-v1.schema.json:186-187`, `minItems` 1 and `maxItems` 1), so a conformant validator rejects a two-condition AlertPolicy.

### (B) The AlertPolicy omits the required notificationTargets

`alertPolicySpec` (`openslo.go:87-91`) has no `notificationTargets` field and `RenderOpenSLO` never populates one. OpenSLO v1 requires `spec.notificationTargets` present and non-empty (`openslo-v1.schema.json:177`, required; `:190-194`, `minItems` 1), so a conformant validator rejects an AlertPolicy that omits it.

### (C) The SLO alertPolicies entries are bare strings against the required object entries

`sloSpec.AlertPolicies` is `[]string` (`openslo.go:72`), set to `[]string{policyName}` (`openslo.go:178`), so the SLO emits bare-string `alertPolicies` entries. `SLOAlertPolicyEntry` requires each entry to be an object that either references an AlertPolicy (`{alertPolicyRef}`) or inlines one (`openslo-v1.schema.json:79-90`). A bare string is neither branch, so a conformant validator rejects it.

### The reviewer-directed additions have no spec basis today

Proposal 0040 converged on a code-only design (fixes A and C plus a bare conventional `targetRef` with no spec edit) and is now superseded (git `898f3afd`; the 0040 file states so on line 3). During sign-off the reviewer directed the notification-target representation to a self-contained define-once form (one shared top-level `AlertNotificationTarget` document referenced by `targetRef`) and required the target to be deployer-configurable. Both additions have no spec basis today: §16.10 (`spec/16_observability.md:742-746`) names only `SLO`, `SLI`, and `AlertPolicy` as emitted document kinds (`:746`) and defines no notification-target configuration surface (only `monitoring.openslo.enabled`), and the vendored schema has no `AlertNotificationTargetDocument` def (only `SLIDocument` `:52`, `SLODocument` `:119`, `AlertPolicyDocument` `:198`; the existing `AlertNotificationTargetEntry` `:163` is the `notificationTargets` array-item rather than a top-level document). The change is therefore spec-first: land the §16.10 edit, then implement the code, schema, and tests, then un-skip the tier-0 test.

## 2. Decisions

- **Spec-first, per `spec-driven-development.md`.** The reviewer-directed additions (a self-contained `AlertNotificationTarget` document and a deployer-configurable target) each require a §16.10 edit before code: the spec must name `AlertNotificationTarget` among the emitted document kinds and define the `monitoring.openslo.notificationTarget` configuration surface. Fixes A (one condition per policy) and C (`alertPolicyRef` entries) are OpenSLO v1 object-model conformance that the `apiVersion: openslo/v1` advertisement already implies and the vendored schema already transcribes, so they ride along without new normative text; the §16.10 edit is scoped to the genuinely new surface.
- **Classified fix.** The dominant action reconciles an export to the object model it already claims and un-skips a test written to catch the gap. The change carries a bounded additive surface required by the reviewer's self-contained design (one new emitted document kind and one deployer-facing config key), defined normatively in §16.10 rather than smuggled in.
- **Preserve the §16.5 multi-window burn-rate by splitting rather than dropping a window** (carried forward from 0040 unchanged). Each SLO's fast/critical and slow/warning conditions render as two single-condition AlertPolicy documents, `<name>-burnrate-fast` (1h/14x critical) and `<name>-burnrate-slow` (6h/3x warning). The longest §16.5 name `session-creation-success-rate` (29 chars) yields `session-creation-success-rate-burnrate-fast` (43 chars), within the schema's 63-char lowercase-hyphen `metadata.name` limit (`openslo-v1.schema.json:9-13`).
- **Represent the notification target as Option B:** emit one shared top-level `AlertNotificationTarget` document per fragment (define-once) and reference it from every AlertPolicy via `notificationTargets: [{targetRef: lenny-slo-notifications}]`, so the ConfigMap is self-contained. This adds an `AlertNotificationTargetDocument` subschema to the vendored schema, an `AlertNotificationTarget` entry to the tier-0 test's kind-routing map, and the §16.10 document-kind naming edit.
- **The `AlertNotificationTarget`'s `metadata.name` and every `targetRef` are deployer-configurable via a default-literal replace, because a placeholder token cannot sit in the pattern-constrained name.** `metadata.name`, `targetRef`, and `alertPolicyRef` are pattern-constrained (`^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`, `maxLength` 63, `openslo-v1.schema.json:9-13`) and the tier-0 test validates the raw generated fragment with no substitution, so a `__OPENSLO_NOTIFICATION_TARGET_NAME__`-style token there would fail the name pattern. The renderer therefore emits the schema-valid default literal `lenny-slo-notifications` (the existing `openSLONotificationTargetName` constant) into `metadata.name` and every `targetRef`, so the raw fragment validates as-is and the tier-0 test needs no substitution machinery; the Helm template then replaces that literal with the deployer's configured name (a second `replace` beside the tier replace). The literal appears only as the shared target's `metadata.name` and the `targetRef` entries pointing at it, which must change together, so a global replace is correct. Per-deployment distinct names let deployments sharing one OpenSLO tool define separate targets.
- **Make the target type deployer-configurable through the existing tier-substitution pattern, and the name through the default-literal replace.** `RenderOpenSLO` gains a `notificationTarget` (type) parameter mirroring `tier`: the chart-fragment caller passes the placeholder constant `SLONotificationTargetPlaceholder` (`__OPENSLO_NOTIFICATION_TARGET__`), which the Helm template substitutes from `monitoring.openslo.notificationTarget.type` into the free-form `spec.target`; the docs and CLI callers (no Helm layer) pass a concrete default `OpenSLODefaultNotificationTarget` so their outputs are placeholder-free and schema-valid. The name is not threaded through `RenderOpenSLO` (it is the emitted `openSLONotificationTargetName` constant the Helm template replaces from `monitoring.openslo.notificationTarget.name`), so the renderer, its signature, and the Go unit tests are unchanged by the name-configurability.
- **Guard the configurable name in `values.schema.json`.** `charts/lenny/values.schema.json` types `monitoring` loosely as `{"type":"object"}` (`:176`), so the free-form target `type` needs no constraint. The `name`, however, renders into pattern-constrained `metadata.name`/`targetRef`, and the tier-0 test validates only the default fragment, so an invalid deployer-supplied name would produce an invalid `ConfigMap` at install that no test catches. Add a `monitoring.openslo.notificationTarget.name` sub-schema to `values.schema.json` constraining it to the OpenSLO name pattern (`^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`, `maxLength` 63) so an invalid name is rejected at install time. Both defaults are documented as operator-tunable in the `values.yaml` comment per `code-best-practices.md`.
- **Reuse the existing render, generation, and substitution surfaces.** The change splits one document, changes two field types, adds one shared document and one `notificationTargets` field, adds three package constants, and threads one new parameter. It adds no new RPC, no new generated file, and no new Helm template; the `openslo-configmap.yaml` template gains a second literal replace beside the tier replace.

## 3. The conformant document set

Per §16.5 SLO, the export renders the following documents, plus one shared notification target per fragment:

- One `SLI` document, unchanged.
- One `SLO` document whose `spec.alertPolicies` carries two `{alertPolicyRef: <name>}` objects, one referencing each burn-rate AlertPolicy.
- One `AlertPolicy` document named `<name>-burnrate-fast`, carrying exactly one condition (the fast-window 1h/14x critical condition) and `notificationTargets: [{targetRef: lenny-slo-notifications}]`.
- One `AlertPolicy` document named `<name>-burnrate-slow`, carrying exactly one condition (the slow-window 6h/3x warning condition) and the same single `notificationTargets` entry.
- One shared top-level `AlertNotificationTarget` document whose `metadata.name` is the deployer-configurable notification-target name (default `lenny-slo-notifications`), emitted once per fragment, whose `spec.target` carries the deployer-configurable type (default `webhook`). Every AlertPolicy's `targetRef` equals that name.

Each document validates against its per-kind subschema (`SLIDocument`, `SLODocument`, `AlertPolicyDocument`, and the new `AlertNotificationTargetDocument`), so the tier-0 conformance test passes once its kind-routing map gains the `AlertNotificationTarget` entry.

`monitoring.openslo.notificationTarget.type` / `OpenSLODefaultNotificationTarget`. Whether `monitoring.openslo.notificationTarget` should also configure the `AlertNotificationTarget`'s `spec.description`, or whether `description` stays a fixed literal.
