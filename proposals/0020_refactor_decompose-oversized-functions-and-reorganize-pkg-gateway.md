# Proposal: Behavior-preserving structural refactor: decompose 18 oversized functions and reorganize `pkg/gateway` for navigability

- **Status:** Applied to spec (2026-06-29). Verified (2026-06-29), converged after 2 adversarial review rounds (0 findings fixed) re-reviewing the post-convergence §4.1 subsystem-seam amendment, on top of the initial convergence (8 rounds, 6 findings fixed). The proposal has two workstreams.
- **Date:** 2026-06-29.
- **Scope:** This proposal covers two related, behavior-preserving structural refactors. **Part A** decomposes the 18 longest control-flow-heavy functions across `cmd/` and `pkg/` into smaller, single-responsibility helpers. **Part B** reorganizes `pkg/gateway` (538 of ~1,170 non-test library files in 172 flat sibling subpackages) into intermediate, spec-aligned groups, extracts one shared cross-cutting concern, and updates the non-Go references that name the moved paths. Both changes preserve behavior exactly and add no capability, so per `.claude/rules/spec-driven-development.md` they introduce no behavioral spec obligation. They do force mechanical spec path-reference edits, because spec prose names the moved `pkg/gateway` packages and pins them to spec sections; those path-string rewrites are staged in §3. Every existing `// spec:` citation and every existing test must still hold. All directory moves, package renames, and import-path rewrites in Part B are performed by committed, reproducible scripts rather than by hand (§2, §4 Part B).

This document stages the proposed code changes for the implementation step. It does not modify any code, spec, or doc file. Apply the changes in §4 after sign-off.

## 1. Problem

The tree has two structural problems, both behavior-preserving to fix and both surfaced by tooling in this repository. They are folded into one proposal because they share a discipline (mechanical, with no behavior change and only the mechanical spec path-reference edits in §3) and overlap in the gateway packages, so their landing order must be coordinated (§7).

### 1.1 Oversized functions (Part A)

The `lenny-test long-funcs` check (committed in `cmd/lenny-test/cmd_lint_funcs.go`) reports 561 functions whose body exceeds 50 lines under `pkg/`, `cmd/`, `sdks/`, and `migrations/`. Ranked by statement count, which separates control-flow-heavy bodies from large declarative literals, the 18 below are the densest. Each carries enough nested control flow that a reader cannot hold the whole function in view, and several interleave distinct concerns (request parsing, validation, authorization, persistence, and response rendering) in one body, which `.claude/rules/code-best-practices.md` names as the signal to extract a helper.

Length alone is a candidate signal rather than a verdict. The statement count is a secondary signal that correlates with control-flow density but does not by itself prove a function mixes abstraction levels. The decomposition boundaries named per function in §4 Part A are the proposed seams; each is confirmed by reading the function during implementation before the extraction lands.

### 1.2 The `pkg/gateway` concentration (Part B)

`pkg/gateway` holds 46% of the library in 172 flat sibling subpackages with zero files at its own root. The rest of the tree is comparatively well-organized (`pkg/ops` is split into 27 subdirs). A reader locating a concern scans 172 sibling directories with no intermediate structure. The themes are concentrated: 37 `*store` packages, 11 `session*`, 10 credential-related, 5 `quota*`, and smaller clusters. A second defect rides inside one package: `pkg/gateway/events` mixes the §25.3 gateway-side event buffer (gateway-internal) with the shared CloudEvents envelope and §16.6 event-type vocabulary that ~18 files in `pkg/ops`, `pkg/controller`, `pkg/upgrade`, and `pkg/alerting` consume.

### 1.3 What the adversarial review established about the gateway reorganization

A first-pass plan to lift the stores to `pkg/store`, `events` to `pkg/opsevents`, and `policy` to `pkg/policy` was tested by three independent reviewers and does not hold. Its conclusions constrain Part B:

- **The gateway is one §4 component.** §4.1 defines it as "internally partitioned into subsystem boundaries, not separate services, Go interfaces within a single binary" (`spec/04_system-components.md`). §11 (Policy and Controls) and §12 (Storage Architecture) are cross-cutting behavior chapters rather than spec components; the canonical layout the `code-best-practices` rule points to is the §4 component model. The fix is intermediate grouping inside `pkg/gateway`, which preserves the §4-component-to-package-tree correspondence the `// spec:` model relies on. The literal package paths that spec prose names move with the tree and are corrected as staged spec path-reference edits (§3).
- **`policy` is gateway-internal by spec.** §4.8 ("Gateway Policy Engine") states the engine is "physically embedded in edge gateway replicas (not a separate service). Can be split out later." The split is named and not yet taken, so `policy` stays in the gateway tree.
- **The §25.3 event buffer is gateway-side by spec.** §25.3 ("Gateway-Side Ops Endpoints") scopes the buffer to the gateway because it reads in-process state. The 18 external importers consume the shared event vocabulary rather than the buffer, so the correct move extracts the shared types and leaves the buffer in the gateway.
- **There is no `pkg/store` catch-all.** §4 defines no "Storage" component; it splits persistence into the Session Manager (§4.2), the Event/Checkpoint Store (§4.4), and the Artifact Store (§4.5), and most `*store` packages back other components. `code-best-practices.md` forbids a catch-all dumping package. `environmentstore` (§10.6) and `experiment*` (§10.7) are explicitly gateway-internal.
- **"Import paths only" is not the whole change.** Two stores anchor into gateway-core (`breakerstore`→`middleware/circuitbreaker`, `interceptorstore`→`interceptor`), so they group with their core dependencies rather than the persistence cluster. The `events` package clause is `events` (not `opsevents`) and collides conceptually with the existing `package events` at `pkg/ops/events` (imported there as `gwevents`). `tests/spec-map.json` (29 references) and `tests/change-graph.json` (2 references) name these paths, and spec prose under `spec/04`, `spec/11`, `spec/17`, `spec/18`, and `spec/25` names them too (§3). The `validate-maps` file-existence gate catches a skipped rewrite only for `tests/change-graph.json` glob keys; it does not existence-check `tests/spec-map.json` package or test references or spec prose, so those rewrites are guaranteed by the driver's deterministic replacement and a post-move audit rather than by the gate (§4 C4).
- **The churn is large and concurrent work is heavy.** The store grouping rewrites ~724 `.go` files; 100% of the last 200 commits touch `pkg/gateway`; unmerged branches (`docs/improvements`, `impl/0002-session-service`) each touch ~1,300 gateway files. This is the risk the script-driven execution in §2 mitigates and the maintainer has accepted to run now rather than defer.

## 2. Decisions

### Shared (both parts)

- **Behavior is preserved exactly.** No control-flow outcome, error code, log line, metric, or wire response changes. Part A extractions are mechanical block moves; Part B is package moves and import-path updates. Every existing `// spec:` citation moves with the code it annotates, and no citation is added or removed.
- **No behavioral spec changes; mechanical spec path edits only.** Neither part changes behavior, so neither creates a behavioral spec obligation. The moves do require mechanical path-reference rewrites in the spec prose that names the moved packages, staged in §3.
- **Decompose and relocate, do not rewrite.** Neither part re-expresses logic, changes data structures, or alters algorithms. A change tempting to fold in (a bug fix, a simplification) is filed separately so each diff stays reviewable as a pure move.

### Part A: function decomposition

- **Each helper lands in the concern's existing package or file.** Extracted helpers stay in the same file unless a sibling already owns the concern. No new package is created unless a concern has no home, called out per function.
- **Target: no target function over the threshold, with realistic exceptions named.** Each function drops below the 50-line `long-funcs` threshold where achievable. Where a sequence is irreducible (a registration table or a metric constructor), it splits into named per-group helpers each under the threshold and the top-level function becomes a short sequence of calls.
- **One function per change unit.** Each of the 18 is an independent change (R1–R18), landable and revertible on its own.

### Part B: gateway reorganization

- **Group inside `pkg/gateway`; do not relocate concerns out of it.** Grouping preserves the §4 component boundary. `policy` (§4.8), the §25.3 event buffer, `environmentstore` (§10.6), and `experiment*` (§10.7) stay in the gateway tree, grouped under their subsystem. `breakerstore` and `interceptorstore` group with the gateway-core they depend on rather than with the persistence cluster.
- **Preserve the §4.1 subsystem extraction seams.** §4.1 partitions the gateway into four subsystems (Stream Proxy, Upload Handler, MCP Fabric, and LLM Proxy) defined as Go interfaces, and the §4.1 "Extraction triggers" table plus §4.8 (the policy engine) record the design intent that any subsystem can later be extracted to a dedicated service or pod. §02 and §4.1 name the LLM Proxy extraction as the Tier 2-to-3 prerequisite. Because the seams are interfaces, the behavior-preserving moves do not touch them, and R1 reinforces them by extracting per-subsystem constructors. The C1 grouping keeps this property: each §4.1 subsystem's packages stay cohesive within a single group, the LLM Proxy and MCP Fabric get dedicated named groups (the LLM Proxy is the named first extraction target), the §4.8 policy group stays cohesive, and `sessionserver` (which realizes the Stream Proxy and Upload Handler behind their interfaces) is not split across groups. Critically, the delegation-orchestration packages group under MCP Fabric, because §4.1 assigns delegation to that subsystem, so the grouping does not split one subsystem across two groups, and no group entangles two subsystems. The result keeps a future per-pod extraction a directory-subtree move rather than a scattered cherry-pick.
- **All renames and moves are executed by committed, reproducible scripts.** No directory move, package rename, or import-path rewrite in Part B is performed by hand. The moves are data-driven from a manifest of `(old import path → new import path)` pairs consumed by a driver script under `scripts/refactor/` (or `hack/`). Per move the driver: (1) `git mv` the directory so rename detection preserves history; (2) replaces the fully-qualified import-path string (`github.com/lennylabs/lenny/<old>` → `…/<new>`) across all `*.go` files using a path-boundary-anchored match (the quote-delimited literal `"github.com/lennylabs/lenny/<old>"`, including the closing quote) rather than a bare substring, because many moved paths are strict prefixes of sibling paths (for example `pkg/gateway/mcp` is a prefix of `pkg/gateway/mcptools`, `pkg/gateway/mcpruntimes`, and `pkg/gateway/mcpschemagen`, `interceptor` of `interceptorstore`, `delegation` of `delegationbudget`, and `admin` of `admintoken`) and an unanchored replace would also match inside the longer sibling import and corrupt it; the anchored replace needs no identifier rewrites because package names are unchanged; in the same `*.go` pass it also rewrites runtime repo-relative path references to the moved package, because some tests read a moved package's source file at runtime by path rather than importing it (for example `tests/tier11_docs/playground_delegation_scope_test.go:53` calls `readRepoFile(t, root, "pkg", "gateway", "playground", "token.go")`, which a quote-delimited import-literal match never touches): the driver rewrites both the slash-joined bare string literal (`"pkg/gateway/<old>/…"`, boundary-anchored as above) and the split path-segment form (the consecutive quoted segments a `filepath.Join`/`os.ReadFile`/`readRepoFile` call passes, such as `"pkg", "gateway", "playground"`), inserting the new group segment so the runtime read resolves to the moved location; (3) replaces the same references in `tests/spec-map.json` and `tests/change-graph.json`, matching each entry on a path-token boundary (the exact string, or a trailing `/`, `/...`, or `"`) so the short-path replace does not collide with a longer sibling entry or a `/...` glob; (4) runs `gofmt -w` and `goimports -w` on the touched files to regroup imports; (5) gates on `go build ./...`, `go vet ./...`, and `lenny-test validate-maps`, aborting the move on any failure; and (6) regenerates the CodeGraph index. The manifest and the driver are committed so the transform is auditable and re-runnable.
- **Implement C3/C4 now rather than deferring, with script-based branch mitigation (maintainer decision).** The ROI review recommended deferring the mass move behind a pre-v1 freeze because a hand-edited rewrite would strand the gateway-heavy in-flight branches. Script-driven execution changes that calculus: a branch reconciles by merging the pre-move base and re-running the manifest driver, which reproduces the same deterministic transform instead of hand-resolving ~1,300 import conflicts. The residual coordination risk is recorded in §7; the decision is to proceed now using the scripted path.
- **Each move is a separate, verifiable step.** The manifest is partitioned so each group move (the store cluster, the session cluster, and so on) is applied, verified green, and committed before the next. A failed `go build` or `validate-maps` aborts and rolls back that one move.

## 3. Proposed spec changes

No behavioral change: the gateway stays one §4 component, the policy engine stays embedded per §4.8, and the §25.3 event buffer stays gateway-side. The moves are not spec-free, however. Spec prose names concrete `pkg/gateway` subpackage paths and pins them to spec sections, so the C2 extraction and the C3 regrouping make those literal path references stale. The references are corrected by mechanical, behavior-preserving path-string rewrites that mirror the same old→new mapping the code moves use. They are staged here and applied by `implement-proposal`, because the guard hook blocks ad-hoc spec writes and the C3 driver does not write under `spec/`. The complete set of spec prose references (confirmed by `grep -rn "pkg/gateway/" spec/`) is the following.

## 4. Proposed code changes

### Part A: function decomposition

Each entry names the target, its archetype, and the proposed extraction seams. The seams are the draft plan; the implementer confirms each by reading the function before extracting. Helper names are illustrative. These edits are manual and semantic; they are not script-driven (only Part B's mechanical moves are).

### Part B: `pkg/gateway` reorganization (script-driven)

#### C1. Author the group taxonomy and the move manifest

Define the intermediate group set for `pkg/gateway`. The four §4.1 subsystems (Stream Proxy, Upload Handler, MCP Fabric, and LLM Proxy) and the §4.8 policy engine are the primary group boundaries; each is kept cohesive in one group subtree so a future per-pod extraction stays a subtree move (§2 subsystem-seam decision). The MCP Fabric group holds the delegation-orchestration, virtual-child-MCP, and elicitation packages that §4.1 assigns to that subsystem, so delegation is not split into its own top-level group; the LLM Proxy group holds the credential-injecting reverse-proxy packages; and `sessionserver` (which realizes the Stream Proxy and Upload Handler) stays whole. The remaining packages group by §10 subsection or concern beneath those boundaries: stores, credentials, quota, pod lifecycle, and the operability endpoints. Map each group to its spec section. Record this as `pkg/gateway/ARCHITECTURE.md` (the navigational index) and, in the same step, as the machine-readable move manifest the C3 driver consumes (each `(old import path → new import path)` pair, with the exclusions from §1.3 encoded so `policy`, `environmentstore`, `experiment*`, `breakerstore`, and `interceptorstore` map to their correct group). C1 is the design artifact; C3 executes it. Cost: one doc plus one manifest, no import churn.

#### C2. Extract the shared event-type vocabulary

`pkg/gateway/events` mixes the §25.3 gateway-side buffer with the shared event vocabulary (the CloudEvents envelope, the `gateway`/`ops` `source` discriminator, and the §16.6 event-type catalog) that ~18 external files consume. Move the shared vocabulary to a neutral types package (candidate `pkg/events`), update the external importers and the gateway buffer to import it, and leave the §25.3 buffer in the gateway. This is a package split, so the symbol-selection (which identifiers move) is a manual design input captured in a manifest of files and symbols; the file moves, the new package clause, the buffer-package rename (if chosen, to resolve the dual-`package events` collision the mechanics review found, for example `eventbuffer`), and the import and qualifier updates are then performed by the script. Cost: roughly the events footprint plus its `spec-map.json`/`change-graph.json` references and the spec prose path references in §3 (`spec/04`, `spec/11`, `spec/18`, and `spec/25`).

#### C3. Group the gateway subpackages into intermediate directories

Run the C1 manifest through the driver script (§2), moving each subpackage under its group inside `pkg/gateway` with package names unchanged, so the change is limited to import paths and the path references that name them (the maps in §4 C4 and the spec prose in §3). This is the ~724-file import rewrite, executed as a sequence of per-group moves, each verified green and committed before the next. The exclusions from §1.3 are honored by the manifest: `policy` groups under policy/controls and stays in the gateway, `environmentstore`/`experiment*` group under gateway internals, and `breakerstore`/`interceptorstore` group with their gateway-core dependencies.

#### C4. Update the non-Go path references and regenerate derived indexes

This is performed by the same driver as part of C2 and C3 rather than as a follow-up: each move updates `tests/spec-map.json` and `tests/change-graph.json` with the path-boundary-anchored replacement from §2, re-runs `lenny-test validate-maps` as the tier-0 gate, and regenerates the CodeGraph index. The gate has a narrower reach than "the maps never drift": `validate-maps` existence-checks only `tests/change-graph.json` glob keys (`validateChangeGraphFileExistence` in `cmd/lenny-test/cmd_validate.go`), and `validateSpecMapPaths` checks only each section's `spec_file` pointer, so it does not existence-check `tests/spec-map.json` package or test references. A skipped or incomplete `spec-map.json` rewrite therefore passes `validate-maps`. Completeness of the `spec-map.json` edit is guaranteed instead by the driver's deterministic boundary-anchored replacement plus a post-move audit (an existence check for spec-map package paths could be added to `validate-maps` to make this a gate). The audit's abort condition is scoped to the boundary-anchored forms the driver rewrites, so the gate aborts only on a token the driver can fix. It greps `tests/spec-map.json`, `tests/change-graph.json`, and `*.go` sources including test files for a surviving pre-move path token in one of those forms: a quote-delimited import literal, the slash-joined bare string literal `"pkg/gateway/<old>/…"`, the split path-segment form a `filepath.Join`/`os.ReadFile`/`readRepoFile` call passes, or a JSON-map entry matched on its path-token boundary. A surviving token in one of those forms aborts the move. The abort condition matches the driver's rewrite granularity by design, because a path token the driver provably cannot reach must not block the move. A package path that appears in a plain Go comment or inside a larger informational string is bounded by a space or by `(`, `)`, `.`, or `;` rather than by a quote or a slash, so the driver never rewrites it, and the repository carries 347 such comment references (including the `// diagnosis:` comments `.claude/rules/test-coverage.md` mandates on every tier-2-and-up test, for example `tests/tier2_component/auditstore/auditstore_test.go:42` naming `pkg/gateway/auditstore`). Almost every moved store or subsystem package is named in at least one such comment, so an abort on those tokens would make every C3 group move unsatisfiable. The audit therefore surfaces comment and informational-string occurrences as a non-fatal warning that records the residual stale drift for an optional manual sweep, rather than aborting on them. The `*.go` abort reach still matters because a tier-11 source-reading test such as `tests/tier11_docs/playground_delegation_scope_test.go` reads a moved package's source at a runtime path (`pkg/gateway/playground/token.go`) through the split path-segment form, which the driver does rewrite; the per-move gate runs only tier-0 (`go build`, `go vet`, `validate-maps`) and never executes tier 11, and `validate-maps` existence-checks no `*.go` path string, so without the driver's runtime-path rewrite (§2) and this audit the broken read would land silently and fail later in tier 11. The informational `pkg/gateway/<old>` path strings in error and skip messages (for example in `tests/tier2_component/.../scaffolds_test.go` and `tests/tier4_integration/scaffolds_test.go`) carry a space before the token, so the driver cannot rewrite them and the audit warns rather than aborts; they do not break a build, and the warning records the stale drift for a manual sweep. A pre-existing set of stale `pkg/gateway/opsevents` references in `tests/spec-map.json` (the §16 umbrella and §16.6 entries name a removed `pkg/gateway/opsevents` directory that currently lives at `pkg/gateway/events`) demonstrates the gap and is cleaned up in this pass. These references point at the §16.6 operational-events catalog: `catalog.go` and its completeness tests `TestGatewayCatalogIsCompleteAgainstSpec166` and `TestOpsCatalogIsCompleteAgainstSpec166`. `catalog.go` is the §16.6 event-type vocabulary, imports only `strings`, and carries no gateway-internal dependency, so C2 relocates it together with `catalog_test.go` to the neutral `pkg/events` package, out of the gateway tree. The cleanup therefore resolves these stale references to `pkg/events` (the catalog's post-C2 location) rather than `pkg/gateway/events`, and it is sequenced after C2 so the destination exists. C2's boundary-anchored driver cannot reach these entries on its own: it is keyed on the real path `pkg/gateway/events` and never matches the stale `pkg/gateway/opsevents` token, so this C4 cleanup is the only mechanism that rewrites them. The spec prose path references (§3) are not touched by the driver, because the guard hook blocks ad-hoc spec writes; they land as the staged spec edits `implement-proposal` applies.

## 5. Non-goals

- **No behavior change (both parts).** Any bug found while reading or moving code is filed separately rather than folded in.
- **No behavioral spec change (both parts).** The spec's behavior, defaults, and contracts are unchanged; the only spec edits are the mechanical path-reference rewrites the moves force (§3).
- **No algorithmic rewrite or data-structure change (Part A).** Extractions move existing blocks; they add no abstraction beyond the helper boundary.
- **No reformatting outside the change.** Each diff is scoped; incidental reformatting of untouched code is reverted, except the import-grouping that `gofmt`/`goimports` applies to files the Part B moves already touch.
- **No expansion to the full 561 over-threshold functions (Part A).** The scope is bounded to the 18 in §1.1.
- **No relocation of concerns out of `pkg/gateway` (Part B).** `pkg/store`, `pkg/policy`, and `pkg/opsevents` as destinations are dropped; §4.8, §25.3, and the absence of a §4 "Storage" component make those lifts contradict the component model. Only the shared event vocabulary (C2) leaves the gateway, and it leaves because it is genuinely cross-cutting rather than gateway-internal.
- **No hand-edited moves (Part B).** Every directory move, package rename, and import-path rewrite goes through the committed driver and manifest; manual edits to import paths are out of scope.
- **The `long-funcs` check stays advisory.** This proposal does not promote it to a tier-0 gate.

## 6. Testing

Both parts are behavior-preserving and held to the existing tests passing rather than the new-code coverage target (`.claude/rules/test-coverage.md`).

### Part A

- **Tier 0.** `go build`, `go vet`, `golangci-lint`, `gofumpt`, and `goimports` on every touched package after each extraction.
- **Tier 1 and up.** Rerun the existing suite for the touched package and dependents, unchanged. The handler and orchestration targets (R5, R7, R9, R10, R12, R13, R14, R15, R16, R18) reach the tiers their packages already exercise (component, contract, integration, and security); rerun those rather than only tier 1.
- **Characterization tests where coverage is thin.** Before extracting a target whose existing tests do not pin its behavior, add a characterization test capturing the current input-to-output mapping, so the move is provably behavior-preserving. Each carries a `// spec:` annotation and, at tier 2 and up, a `// diagnosis:` comment.
- **Test files follow the source split, without rewriting behavior assertions.** When a target's decomposition creates new source files (for example R1, R2, R3, R6) or extracts a helper worth its own focused unit test, the existing `_test.go` file is split or moved to mirror the new file layout, and unit tests for the extracted helpers are added where they raise coverage. The existing behavior tests are not rewritten; they stay green as the safety net that proves the move preserved behavior. Test files are excluded from the `long-funcs` target set, so this split serves locality rather than the threshold.
- **Acceptance.** `lenny-test long-funcs` no longer reports the target (or only a sub-threshold dispatcher).

### Part B

- **Tier 0 per move.** The driver gates each move on `go build ./...`, `go vet ./...`, and `lenny-test validate-maps`, plus `go list ./...` to confirm zero import cycles. A move that fails any check is rolled back. The per-move gate does not run tier 11, so a tier-11 test that reads a moved package's source at a runtime path (such as `tests/tier11_docs/playground_delegation_scope_test.go`) compiles green even when its read path is stale; the driver's runtime-path rewrite (§2) and the post-move pre-move-token audit (§4 C4), which also aborts the move, cover that case.
- **Tier 1 and up for the affected packages and dependents.** C2's external importers span `pkg/ops`, `pkg/controller`, `pkg/upgrade`, and `pkg/alerting`; rerun the tiers those packages already exercise rather than only tier 1.
- **Acceptance.** The gateway root holds the intermediate group directories rather than 172 flat siblings; `go build ./...` and the reached tiers stay green; the CodeGraph index regenerates without dangling references; and `validate-maps` is green.

## 8. Resolved in adversarial review

Part B was reviewed by three independent adversarial lenses; their findings are folded into §1.3, §2, §4 Part B, and §5. Part A is not yet reviewed and its convergence runs when the scope is final.

- **Spec/architecture (partially refuted the original lift).** This lens established that the premise conflated the §11/§12 behavior chapters with the §4 component model; that §4.8 embeds the policy engine in the gateway with extraction explicitly deferred (drops the `pkg/policy` lift); that §25.3 scopes the event buffer to the gateway (redirects `events` from relocation to type extraction, C2); and that `pkg/store` is a forbidden catch-all with `environmentstore`/`experiment*` explicitly gateway-internal. These conclusions are folded into the "group inside the gateway" decision and the C3 exclusions.
- **Build/cycle mechanics (survives the hard tests, needs changes).** This lens confirmed zero import cycles and no destination collisions, but refuted "import-paths-only": `breakerstore`→`middleware/circuitbreaker` and `interceptorstore`→`interceptor` are not lower-layer leaves; the `events` package clause is `events` and collides with `pkg/ops/events`; `tests/spec-map.json` (29 refs) and `tests/change-graph.json` (2 refs) name the moved paths. The tier-0 `validate-maps` gate existence-checks only the change-graph glob keys, so a skipped `spec-map.json` rewrite passes the gate; the driver guarantees that edit by deterministic boundary-anchored replacement and a post-move audit (§4 C4). These findings are folded into the C3 exclusions, the C2 rename decision, and C4.
- **ROI/timing (recommended deferral; overridden with mitigation).** This lens quantified the churn (~724 files for the store move, ~1,144 for a full regroup), the commit pressure (100% of the last 200 commits touch `pkg/gateway`), and the branch-stranding risk (~1,300 gateway files per in-flight branch), and noted CodeGraph offsets the navigability benefit. The maintainer chose to proceed now; the script-driven execution (§2) is the accepted mitigation, since a branch reconciles by re-running the deterministic manifest driver rather than hand-resolving conflicts. The residual coordination risk is tracked in §7.

Point of reconciliation: the mechanics review found the move technically feasible while the spec and ROI reviews found the original lift inadvisable. Feasibility does not imply advisability; Part B keeps the inadvisable relocation out of scope (grouping inside the gateway instead) and uses the scripted path to make the feasible move safe to run now.
