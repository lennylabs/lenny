# Problem: Terminal pipeline completeness: seal and writer context

## Statement

The terminal pipeline covers the work between a session's terminal write and the end of its D7 terminal hook. On the P2a member paths it leaves workspace seals, audit rows, pod and slot releases, and post-commit work incomplete or wrong. This proposal is the first half of remediation plan P2 (P2a, seal and writer context). The member defects are F-7.1.21 to F-7.1.29, F-7.2.29, F-7.2.30, F-7.3.32, F-10.1.27, F-11.2.30, F-11.7.22 (the `session.force_terminated` half only), F-15.1.42, and F-15.1.44. BUILD-GAPS records each as OPEN on 2026-10-24. They correspond to terminal-transition rows TT-1 to TT-13, TT-28, TT-34, TT-36, and TT-87. Six of these members are High (F-7.1.21 to F-7.1.24, F-10.1.27, and F-11.2.30). The plan's figure of ten High findings counts the wider P2 group including TT-29.

Writer contexts are inconsistent across terminal writers, and none of them carries a stated bound. Since commit 3f943f56f (2026-10-13, the 0092 D7 hook implementation), the REST terminal write in `session_transitions.go` and the MCP terminal path run the hook on `context.WithoutCancel`. That detached context has no deadline: only the seal applies its own `sealMaxDuration` timeout, and the cascade, drain, signals, and release run without a budget. Other writers still pass a context that a caller or a process owns:

- `failFinalizing` runs the terminal write and `afterFailed` on the `/finalize` request context from three branches (F-7.1.25).
- Admin force-terminate runs `ForceTerminate`, its synchronous hook, and the `session.force_terminated` audit row on `req.Context()` (F-7.1.21 residual, F-11.7.22).
- The budget terminator runs the terminal write and the hook on a fire-and-forget goroutine with a 30 s `context.Background` deadline, which is shorter than the 300 s default seal window, and no durable owner retries it after a restart (F-11.2.30).
- Gateway shutdown applies `--shutdown-timeout` (default 5 s) to `httpSrv.Shutdown`, then closes the session server, and does not wait for open terminal hooks, claims, or D6 releases (F-10.1.27).

F-7.1.21 as recorded (the REST `recordSessionCompleted(r.Context(), ...)` call, re-confirmed at 319b80091 on 2026-10-12) is stale for the REST path. It is restated as the unbounded detached hook context plus the request-bound writers listed above.

The seal can report success for a workspace that was not sealed, or seal a workspace that changed afterwards. A concurrent unbind makes `Checkpointer.Seal` return nil (F-7.1.22). A Send after the hook reopens Attach (F-7.1.23). A binding left after a hard delete keeps exporting (F-7.1.24). A relabel store error returns the input row (F-7.1.26). A seal timeout on a concurrent-workspace slot releases only the slot (F-7.1.27). Retention GC can run before the funnel's retention roll (F-7.1.28). `isPermanentSealError` treats NotFound as transient, so the seal retries for the whole window (F-7.1.29). Post-resume partial-manifest cleanup can delete a terminal seal's intent row (F-7.3.32). A derive of a completed source during the seal window copies the pre-seal checkpoint (F-15.1.42). In addition, a terminal Update that applies but returns an error skips the post-commit tail (F-7.2.29). The terminate precondition admits `resume_pending` but rejects `resuming`, and `transitionTerminate` always writes `completed` even where §7.2 names `resume_pending → cancelled` (F-7.2.30). `persistDeriveFailure` performs its generation fence as a separate read outside the INSERT transaction, against §7.1 derive rule 2 (F-15.1.44).

The members fall into two groups, and the proposal adds spec text only for the first.

- Spec-silent rules. The D7 hook and funnel tail run on a context the platform owns, bounded by a stated budget, so that neither a writer's disconnect nor a short caller deadline bounds the seal or the release (F-7.1.21, F-7.1.25, F-11.2.30, and F-11.7.22). Gateway shutdown waits, within a stated bound, for open terminal hooks and D6 releases (F-10.1.27). An applied-but-errored terminal write has a stated resolution (F-7.2.29). The derive seal-window rule (F-15.1.42). The `resuming` edge for `POST /terminate` (the part of F-7.2.30 that §7.2 does not already state). Seal-exclusion conditions that existing text does not cover: unbind and eviction defer to an open seal, no Send reaches a sealing binding, a hard delete counts as a terminal signal, retention ordering, and intent-row ownership (F-7.1.23, F-7.1.24, F-7.1.28, and F-7.3.32, each checked against §7.1 and §12.8 before a rule is written).
- Code defects against existing text. F-7.1.22, F-7.1.26, F-7.1.27, and F-7.1.29 violate the §7.1 Seal-and-export invariant (export before release, terminate the pod anyway on seal failure, and a permanent export failure ends the window). The `resume_pending → cancelled` half of F-7.2.30 violates §7.2. F-15.1.44 violates §7.1 derive rule 2. These are fixed and tested under the current text, as F-15.1.43 was closed as a direct BUILD-GAPS fix.

A residual gap is recorded as a departure with a bounding fallback, per the plan's drafting rules, rather than as a new rule. Each member is re-confirmed against the current tree before drafting, and a member already fixed is dropped with the reason. F-7.1.29 is re-confirmed in particular: proposal 0094 removed `DELETE /v1/responses/{id}`, so its trigger is reframed (for example as a hard delete through `DELETE /v1/sessions/{id}` during the hook, which overlaps F-7.1.24) or dropped. Tests follow the plan's expansive test instruction.

Two items are out of scope. "One terminal-signal set for every writer" belongs to F-7.2.35 (TT-84), which the plan's seam places in P2b, so this proposal does not state it. F-10.1.33 (TT-29, off-holder terminal writes) and F-12.8.43 (a drained session bound on another replica keeps its pod after erasure) both depend on the inter-replica carrier proposal and are recorded as deferred. The plan includes TT-29 in P2a only "if 0092 records it as a departure", and 0092 and 0093 record the local write as an accepted departure until the forward lands on the carrier, so the deferral is stated as following from that condition.

## Who observes it

- API clients that derive from or retrieve the output of a completed, cancelled, or expired session. A seal that is cut, falsely reported as successful, or reopened by a late Send loses the final turn's workspace changes or exports a workspace that changed after the seal began. A derive during the seal window receives the pre-seal checkpoint. No sweeper re-seals a terminal session.
- Operators. A seal cut by a short caller context (the 30 s budget terminator against the 300 s window, or a cancelled `/finalize` request) records outcome `timeout`, which fires `WorkspaceSealStuck` and the seal-timeout metric although storage is healthy. A NotFound export error retries for the whole window and records a false seal failure.
- Auditors. The `session.force_terminated` audit row is lost when the admin request ends during the synchronous hook.
- Tenants that rely on budgets for cost control. A budget termination interrupted by a gateway restart is never retried, so a session that exhausted its budget can keep running.

## What breaks if nothing changes

- Final workspace output is lost on the paths above, against the §7.1 promise that session output is never lost to transient cleanup races.
- False `WorkspaceSealStuck` alerts and seal-timeout outcomes continue on every cut context.
- Every rolling deploy cuts open hooks after the 5 s shutdown timeout, so the seal, audit, and release losses occur at deploy frequency.
- Pod and slot capacity from an aborted release is held for up to about 15 minutes per incident, until the controller's orphaned-claim loop or the gateway leader's stale-slot release reclaims it after `claimOrphanTimeout`. This leakage is bounded rather than permanent.
- P2b (held messages, emission, and translators) and the P3 member TT-44 cannot proceed, because both depend on this proposal's writer-context rule.

## Prior art considered

- No other proposal stages this change. Proposals 0092 to 0099 are Implemented. 0092 hands the seal's writer-context question to P2 ("Owner: P2 (BUILD-GAPS F-7.1.22, TT-3)"), and 0094 states that "P2 owns the context the terminal pipeline runs on".
- Commit 3f943f56f (0092's D7 hook) detached the REST terminal write and the descendant cascade with `context.WithoutCancel`. It did not bound that context or reach the admin, finalize, and budget writers.
- Proposal 0094 landed the `tenant.suspended` half of F-11.7.22: `handleSuspendTenant` appends the audit row on a detached context before the drain. 0094 also removed `DELETE /v1/responses/{id}`, which was the trigger F-7.1.29 records.
- The admin drain and tenant suspend already use detached contexts, and `releaseAfterTerminal` already observes the server-lifetime context. These are site-level precedents for the single platform-owned hook context.
- The spec has no rule stating that the hook, seal, or release run on a platform-owned context, that shutdown waits for terminal hooks, or how a derive behaves during the seal window. Lookups over §7, §10, §11, and §15 found no such passage. §11.4 states a similar "client disconnect does not stop the effects" rule for user invalidation only.
- F-15.1.43 (TT-35), a sibling row from the same terminal-transition run, was closed as a direct BUILD-GAPS fix under existing spec text. That route applies to the members in the second group.
