# Proposal: Hold the single-shot Open Responses adapter pod for a per-runtime idle TTL: warm-path continuation reuse with 0059 rehydration as the cold-path floor

- **Status:** Verified (2026-07-25). Converged after 11 adversarial review rounds (20 findings fixed); awaiting sign-off.
- **Date:** 2026-07-25.
- **Scope:** A code-and-test build that adds an opt-in, per-runtime idle-TTL hold on the §15 single-shot compute model for `OpenResponsesAdapter` (`POST /v1/responses`). Under the model built by proposal 0057 (C-13) and extended by proposal 0059, a built-in OpenAI-dialect adapter request claims a fresh warm pod, dispatches one turn, and releases the pod plus its §4.9 credential lease within the same HTTP call, so a multi-turn Open Responses conversation re-pays the pod-claim cost and 0059's transcript rehydration on every message. This build adds a per-runtime `SessionPolicy.PodHoldIdleTtlSeconds` knob (zero-default, opt-in): after a completed Open Responses turn the pod is held in the replica-local registry with its idle clock stamped from that window, a continuation arriving within the window and routed to the same replica reuses the held pod (skipping the re-claim, the credential re-assignment, and the 0059 rehydration), and the held pod is released by the existing watchdog idle sweep when the window expires. 0059's `continuity.rehydrate` remains the correctness floor for every cold turn (first turn, TTL expiry, or a continuation routed to a different gateway replica), so the warm path keeps recording each turn's transcript bucket and `ContinuationParentID` lineage. The warm path is Open-Responses-only because the durable server-side conversation-affinity key (`previous_response_id` to `ContinuationParentID`) exists only for that adapter; Chat Completions is stateless and keeps its unconditional per-request release. `kind` is `new`: no existing spec clause obligates a pod hold, and §15 today mandates synchronous per-request release.

This document stages the proposed code and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

Under the §15 single-shot compute model (proposal 0057, landed), a built-in OpenAI-dialect adapter request claims a fresh warm pod, dispatches one turn, and releases the pod plus its §4.9 credential lease within the same HTTP call.

**1. The release is unconditional.** Both handlers defer the release on every exit path: `openai_chat.go:261` and `open_responses.go:304` both `defer releaseSingleShot(...)`, which calls `executor.ReleaseSession` through the shared helper (`openai_chat.go:484-491`). A multi-turn conversation therefore re-pays the entire pod-claim cost per message: the warm-pool draw, the §4.9 credential-lease assignment, the §6.3 workspace materialization, the runtime launch, and the teardown.

**2. Open Responses continuations re-pay 0059 rehydration on the fresh pod.** For a continuation, the create path also re-runs proposal 0059's transcript rehydration (`continuity.rehydrate` walking the `ContinuationParentID` chain, `open_responses.go:319-332`) onto the freshly-claimed pod on each turn, because the fresh pod starts with empty runtime memory.

**3. An OpenAI-style adapter sends no session-done signal.** The adapter is stateless and carries no explicit session-lifecycle frame, so the gateway cannot know when a conversation is finished and cannot hold a pod on an explicit client signal. Any hold must be inferred and time-bounded.

**4. The affinity key needed to route a continuation back to a held pod exists only for Open Responses.** A held pod is reachable by a later turn only through a durable server-side conversation-affinity key. Open Responses has one: `previous_response_id` resolves to `ContinuationParentID`. The single-shot claim path deliberately threads no lineage (`SingleShotSpec` carries no parent pointer, `singleshot.go:41-54`). Chat Completions is stateless with no server-side conversation id (`openai_chat.go:31-56`), so a held Chat pod could never be routed a continuation.

The current model mandates synchronous per-request release: the §15 built-in adapter single-shot compute-model paragraph states the pod and its §4.9 lease "are released synchronously, recording the completed or failed §6.2 terminal disposition, before the response returns" (`spec/15_external-api-surface.md:598-603`), and the continuation clause states the adapter "re-claims a fresh pod per request and does not retain a pod bind across calls." No existing spec clause obligates a pod hold. The `kind` is `new`: this proposal adds a capability neither the spec nor the code has today. It does not narrow the §15 proper-superset coverage clause (`spec/15_external-api-surface.md:581`) and does not change the OpenAI-dialect wire contract.

## 2. Decisions

- **`kind` is `new`.** The idle-TTL pod hold is a capability neither the spec nor the code has today; §15 currently mandates synchronous per-request release (`spec/15_external-api-surface.md:599-604`). The feature does not narrow the proper-superset coverage clause (`:581`) and does not change the OpenAI-dialect wire contract. A §15 spec edit (SPEC-1) is staged as a prerequisite deliverable that lands and is verified before CODE-1 through CODE-5, because the held Open Responses turn makes the live text that mandates synchronous per-request release false; a companion §5.2 edit (SPEC-2) adds the new `podHoldIdleTtlSeconds` key to the canonical `sessionPolicy` schema the new field belongs to, a companion §6.2 edit (SPEC-3) reconciles the idle-clock state machine so its "single idle bound" statement, its `running`-state `expired` trigger, and its concluding most-restrictive-resolution and `maxSessionAge`-default sentence stay accurate once the held single-shot pod-session's idle clock fires at `podHoldIdleTtlSeconds` rather than `maxClientIdleSeconds` and bypasses the most-restrictive resolution, and a companion §16 edit (SPEC-4) broadens the `max_idle_time` session-expiry series description so the observability inventory stays accurate once a held single-shot pod-session's idle-clock expiry stamps that reason and emits the `dev.lenny.session_expired` event under `podHoldIdleTtlSeconds`. Per `spec-driven-development.md` the spec change leads the code, so the internal-optimization-versus-spec-amendment question is resolved in favor of the amendment rather than deferred to a post-sign-off decision.
- **The idle TTL is configurable per runtime through a new `SessionPolicy.PodHoldIdleTtlSeconds int` field** (`runtimestore.go`), mirroring the `MaxClientIdleSeconds` pattern: a plain `int` with `json:",omitempty"` and a zero default. Zero means no hold, so the pod is released immediately, exactly today's single-shot behavior, and the feature is opt-in. A positive value holds the pod for that many idle seconds. This is a human sign-off mandate and is not re-litigated.
- **No Runtime CRD authoring surface is added.** `SessionPolicy` has no CRD mirror today (`RuntimeSpec` mirrors only `Limits`, `SetupPolicy`, and `DefaultPoolConfig`), and `MaxClientIdleSeconds`, the exact analog, reaches `runtimestore` only through the admin runtime-registration API. `PodHoldIdleTtlSeconds` follows that precedent: admin-API-only, with no `+kubebuilder` mirror. The mandate's "if a CRD authoring surface is required" condition resolves to not required.
- **The warm path is Open-Responses-only.** A held pod is reachable by a later turn only through the durable server-side conversation-affinity key `previous_response_id` to `ContinuationParentID`, which exists only for Open Responses. Chat Completions is stateless with no server-side conversation id (`SupportsSessionContinuity` is false), so a held Chat pod could never be routed a continuation, and `openai_chat.go:261` keeps its unconditional release. This matches 0059's scoping, which also holds Chat Completions out of continuation scope.
- **The hold decouples the pod-session row from the response rows.** The held pod-session is its own `StateRunning` `sessionstore` row, the id the single-shot binder registered the `BindResult` under (`create.go:356` persists its `PodAssignment`). That row owns the `podRegistry` `BindResult`, the cached `PodExecutor` Attach stream, the §4.9 credential lease, and the idle clock, and it is never a wire response id. Every response, including the first turn, is recorded under its own distinct `StateCompleted` response row with its own single-turn transcript bucket and `ContinuationParentID` link, so `GET /v1/responses/{id}` on any response row returns `"completed"`. The held pod-session row is internal and is never returned to a client, so a client never queries it and `mapStateToResponsesStatus` is never asked to render its `StateRunning` or `StateExpired` state on the wire. A warm continuation dispatches its new turn onto the held pod-session id (an `exec.Send` cache hit) while recording under its own new response row, so the 0059 chain stays complete. Under the zero-default (no hold) the base behavior is unchanged: a single row is created, the response id equals that row's id, and it is marked `StateCompleted` and released synchronously, exactly as today.
- **The hold-versus-release decision replaces the unconditional deferred release at `open_responses.go:304`.** When the resolved per-runtime `PodHoldIdleTtlSeconds` is positive and the response is a holdable Open Responses turn, the pod-session row stays in `StateRunning` with its held idle window stamped on the row (a new `sessionstore.Session` field the resolver reads, CODE-3), the deferred release is suppressed, and the `BindResult` and cached stream stay in place. Otherwise the pod releases exactly as today through `releaseSingleShot` to `executor.ReleaseSession`.
- **The hold recycles the watchdog idle-sweep machinery rather than a new coordinator, with an explicit non-holder-replica release fallback.** The held pod-session row is a `StateRunning` session, `StateRunning` is an idle-clock-running state, and the watchdog `sweepIdle` reaps any running session past its effective per-runtime idle cap, anchored on `LastAgentActivityAt` (`watchdog.go`). The sweep is store-backed and runs on every replica ungated by leader election, so any replica can flip the held row to `StateExpired`. When the replica that wins the flip is the holding replica, `TerminalHook.OnSessionTerminal` drains the pod through the local executor and the §6.2 recycle disposition is preserved. When the winning replica is not the holder, its per-replica registry misses the `BindResult`, so the terminal path releases the pod and revokes its §4.9 lease by name through `ReclaimClaimed(sess.PodAssignment, sess.ID)` (the same by-name reclaim `terminalReclaimPreRunning` uses for a claim without a local bind, extended to a held single-shot expired session), which retires the pod rather than recycling it. In a multi-replica gateway the non-holder case is the common one, so the sweep does not have a strictly-smaller strand window than an in-process timer; both fall back to a by-name reclaim off the holder. A new per-conversation in-process `time.AfterFunc` coordinator is still rejected because the watchdog sweep is the canonical owner of the idle-release concern and needs no new store or leader gate. The `recycle.HoldCoordinator` machinery is keyed per pod-claim at the reserved-hold recycle boundary and releases by deleting a reserved claim, so it is a different concern and is not reused.
- **0059 rehydration is the cold-path correctness floor and is not removed.** The cold path, a first turn, a TTL-expired conversation, or a continuation routed to a different gateway replica whose registry holds no binding, falls back to the 0057 claim-and-dispatch plus `continuity.rehydrate`. The warm path skips rehydration because the held runtime holds the conversation in its own memory, and it continues recording each turn's own transcript bucket (`continuity.record`) and setting `ContinuationParentID`, so a later cold turn walking the chain rehydrates a complete conversation and a mid-conversation path switch observes no discontinuity.
- **Same-tenant, same-conversation pod reuse across successive turns without an inter-turn scrub is permitted by the §13 isolation model.** The precedent is the REST interactive session: `handleMessages` (`sessionserver/messages.go:263`) issues many `executor.Send` calls onto one held, tenant-pinned pod with no inter-turn scrub; the scrub is a session-boundary (occupancy-zero) event rather than an inter-turn event. A held single-shot pod is tenant-pinned and never reused across tenants or across distinct conversations.
- **Cross-replica affinity is best-effort.** The affinity map and the registry are replica-local, so a continuation routed to a different replica finds no held binding and takes the cold path. A concurrent second request for the same conversation while the held pod is mid-turn also takes the cold path rather than serializing. A holding-replica crash is reclaimed by the same cross-replica watchdog idle sweep that reaps a held pod on a non-holder replica (CODE-3): a surviving replica lists the frozen `StateRunning` row, finds `LastAgentActivityAt` past `PodHoldIdleSeconds`, flips it to `StateExpired`, and runs the by-name `ReclaimClaimed` off the persisted `PodAssignment` (`create.go:356`), so a lost hold never strands the held pod. The reclaim is bounded by `PodHoldIdleSeconds`. The §4.6.1 orphan-GC is only a second-order backstop that engages after the idle sweep makes the row terminal, because orphan-GC's `bound`-claim predicate reclaims a claim only when its pod has no active session (`spec/04:497`) and a `StateRunning` held pod-session row counts as active (`GetActiveSlotsByPod` counts every non-terminal state, `pgstore.go:737-740`), so orphan-GC provably skips the claim while the hold is live.
- **Coordinate with proposal-B's C-22 (§4.6 warm-pool eviction) through the Integrator inbox,** because the hold reuses the shared warm-pool claim and release primitives and adds a new class of held-pod occupant the eviction machinery must account for. C-22's agent-pod eviction-checkpoint trigger (T-4.4.14 / T-4.6.4) is unbuilt (only prereqs 1 and 2 landed; the agent preStop only SIGTERMs the local adapter per `PROPOSAL-QUEUE.md:528`), so a held single-shot pod evicted mid-idle reduces to preStop-SIGTERM today. This is an accepted v1 gap, stated explicitly, mirroring the deferred T-JRN.13 (`MaxSuspendedPodHoldSeconds` sweep, also deferred pending C-22 coordination, `PROPOSAL-QUEUE.md:539-542`).

## 3. The warm and cold continuation request path after the change

`handleCreate` runs the following sequence. Steps 1, 2, 5, and 6 are the current 0057 and 0059 single-shot path; the affinity lookup in step 2 and the hold decision in step 7 are new.

1. Decode and validate the request body, resolve the tenant, and split the `model` into an environment scope and a runtime reference, exactly as today. Resolve the per-runtime `PodHoldIdleTtlSeconds` from the runtime reference.
2. Look up the conversation-affinity map keyed on the pair `(tenantID, req.PreviousResponseID)`, so an entry is reachable only by the tenant that created it. Each entry carries the held pod-session id, the entry's tenant id, an expiry (the hold-seed time plus the resolved `PodHoldIdleSeconds`), and an in-flight flag. On a warm hit whose entry is not expired, is not in-flight, and whose stored tenant id equals the request tenant, atomically take-and-mark the affinity entry as in-flight and route this turn onto the held pod-session id, skipping the claim and the rehydration; go to step 6. On a miss (no same-tenant affinity entry, an entry already in-flight, an expired entry, or an empty `previous_response_id`), take the cold path. Because the map key and the stored tenant id both carry the tenant, the map itself is the tenant-isolation gate for the warm path, and the executor is never asked for a tenant check. A `previous_response_id` presented by a different tenant never resolves to another tenant's held entry, so the warm path enforces the same tenant-scoped guarantee the cold-path `rehydrate` gives (`open_responses.go:321`, tenant-scoped resolution).
3. Cold path: claim a warm pod, launch the runtime, and register the binding through the single-shot binder, exactly as today. The returned `sessionID` names the pod-session row, not the wire response; the response is recorded under its own distinct response row (step 7).
4. Cold path: when `req.PreviousResponseID` is non-empty, resolve it fail-closed and rehydrate the prior conversation by walking the `ContinuationParentID` chain, exactly as 0059 does today. An unknown or cross-tenant id maps to a native `404` with no dispatch.
5. Normalize the new turn's input into `executor.Message` values, exactly as today.
6. Dispatch the turn onto the resolved pod-session id in one `exec.Send`. On the cold path the rehydrated prior conversation is prepended ahead of the new-turn messages. On the warm path the held runtime already holds the conversation, so only the new-turn messages are sent, and the held pod-session row's `LastAgentActivityAt` is stamped immediately before this dispatch so the in-flight turn's duration does not count against the idle window; the `sweepIdle` expiry closure re-checks the anchor under its transaction (CODE-3 point 5), so a sweep that listed the row before the stamp does not reap the re-stamped pod mid-turn. When the warm dispatch reports the held bind is gone (a concurrent TTL-expiry release raced the hit, surfaced as a not-bound error, a send failure, or a mid-dispatch receive error), evict the affinity entry and restart on the cold path rather than returning an error.
7. On success, create this turn's own `StateCompleted` response row (a distinct id from the pod-session id), set its `ContinuationParentID` from `req.PreviousResponseID` when non-empty, and record this turn's own transcript bucket on that response id, exactly as 0059 does. Then apply the hold decision: when the resolved `PodHoldIdleTtlSeconds` is positive and this is a holdable Open Responses turn, keep the pod-session row in `StateRunning` with its held idle window stamped on the row, stamp the pod-session row's `LastAgentActivityAt` so the idle clock is anchored at this turn, register the affinity map entry `(tenantID, this response id) -> pod-session id`, restore the taken entry from in-flight to held, and suppress the deferred release. Otherwise the base behavior holds: a single row is created, its id is the response id, it is marked `StateCompleted`, and the deferred release fires as the handler returns, exactly as today.

`GET /v1/responses/{id}` resolves a `StateCompleted` (or terminal `StateFailed`) response row and reads `previous_response_id` from `row.ContinuationParentID`, unchanged from 0059. The held pod-session row is internal and is never a wire response id, so `GET` never resolves it.

Each row names the observable outcome, the spec text that states it, and the reader-facing page that documents it. The reader-facing documentation of the hold behavior on `docs/api/open-responses.md` is a follow-on outside this proposal's staged edits, mirroring how 0057 and 0059 deferred their reader-facing pages.

## 5. Proposed changes

### SPEC-1. Amend the §15 single-shot compute-model paragraph to describe the opt-in per-runtime idle-TTL hold (prerequisite, lands and is verified before CODE-1 through CODE-5)

**Target:** `spec/15_external-api-surface.md` (the single-shot compute-model paragraph, the synchronous-release and continuation sentences at `:599-604`).

**Rationale:** The live text states the pod and its §4.9 lease "are released synchronously ... before the response returns" and that `OpenResponsesAdapter` continuation "re-claims a fresh pod per request and does not retain a pod bind across calls." CODE-5 suppresses the synchronous release on a held turn and CODE-3 keeps the pod-session `StateRunning` past the response return, so the implementation would contradict the spec. Per `spec-driven-development.md` the spec change leads the code: this edit lands and is verified in `spec/` before CODE-1 through CODE-5 are implemented.

**Change (staged spec text).** Amend the paragraph so it states that a completed `OpenResponsesAdapter` single-shot turn may, when the resolved per-runtime `PodHoldIdleTtlSeconds` is positive, retain its pod bind and §4.9 lease for that idle window instead of releasing synchronously; that within the window and on the same gateway replica a continuation reuses the held pod, skipping the re-claim, the credential re-assignment, and the transcript rehydration; that the watchdog idle sweep performs the release when the window expires (the §6.2 recycle disposition preserved when the holder performs the release, a by-name reclaim otherwise); and that the zero-default preserves the synchronous per-request release and the fresh-pod-per-request continuation this paragraph describes today. The cold path (first turn, TTL expiry, or a continuation on a different replica) keeps the fresh-claim-and-rehydrate behavior as the correctness floor. The edit does not narrow the `:581` proper-superset coverage clause and does not change the OpenAI-dialect wire contract.

### SPEC-2. Add `podHoldIdleTtlSeconds` to the §5.2 `sessionPolicy` schema (prerequisite, lands and is verified before CODE-1 through CODE-5)

**Target:** `spec/05_runtime-registry-and-pool-model.md` (the `sessionPolicy` YAML block at `:396-417` and the per-field prose at `:436`).

**Rationale:** `PodHoldIdleTtlSeconds` is a member of the §5.2 `sessionPolicy` block. It sits on `runtimestore.SessionPolicy` beside `MaxClientIdleSeconds`, is validated non-negative by the two §5.2-tied validators (`admin/runtimes.go:415-416` and `poolstore.go:557`, whose error message reads `sessionPolicy numeric fields must be >= 0 (§5.2)`), and is reachable through the admin runtime-registration API and a `Pool`'s `sessionPolicy`. The §5.2 YAML enumerates every other field of the block (`maxClientIdleSeconds: 7200` at `:413`, `maxQueueWaitSeconds: 30` at `:416`, with the `maxClientIdleSeconds` prose at `:436`) but not this one. Without this edit the validators and the CODE-1 tie reference a `sessionPolicy` key that the canonical §5.2 schema omits, leaving the non-negativity constraint without a §5.2 basis and a deployer reading §5.2 unable to find the key.

The `maxClientIdleSeconds` prose at `:436` also states "It is the single platform idle bound." That sentence becomes false once `podHoldIdleTtlSeconds` exists, because CODE-3 makes the held single-shot pod-session's `running`-state `expired` transition fire at `podHoldIdleTtlSeconds`, a distinct idle-seconds bound that may exceed `maxClientIdleSeconds`. This edit qualifies that sentence so `maxClientIdleSeconds` remains the idle bound for an ordinary live session while `podHoldIdleTtlSeconds` is named as the separate hold-retention idle bound that governs a held single-shot pod-session. The companion §6.2 reconciliation (SPEC-3) makes the matching correction to the §6.2 idle-clock state machine.

**Change (staged spec text).** Add `podHoldIdleTtlSeconds: 0` to the `sessionPolicy:` YAML block with a comment marking it opt-in and `OpenResponsesAdapter`-scoped, and add a per-field prose paragraph mirroring the `maxClientIdleSeconds` paragraph: state that a positive value holds the completed single-shot pod and its §4.9 lease for that many idle seconds so a continuation arriving within the window on the same gateway replica reuses it, that zero (the default) preserves the synchronous per-request release, and that a negative value is rejected at validation. State that it is a distinct hold-retention idle bound governing a held single-shot pod-session's idle clock and may exceed `maxClientIdleSeconds`, and that its state-machine behavior is specified in §6.2. Amend the existing `maxClientIdleSeconds` sentence at `:436` from "It is the single platform idle bound" to name it the idle bound for an ordinary live session and to cross-reference `podHoldIdleTtlSeconds` as the separate hold-retention idle bound for a held single-shot pod-session, so the two idle-seconds fields do not contradict each other. Cross-reference the §15 single-shot hold behavior. The edit changes no other existing field.

### SPEC-3. Reconcile the §6.2 idle-clock state machine to admit the held single-shot hold-retention bound (prerequisite, lands and is verified before CODE-1 through CODE-5)

**Target:** `spec/06_warm-pod-model.md` (the `maxClientIdleSeconds` clock-behavior paragraph at `:255`, the `running`-state row of the idle-clock pause table at `:267`, and the concluding most-restrictive-resolution sentence of the same subsection at `:276`).

Each affinity entry therefore carries an expiry (the hold-seed time plus the resolved `PodHoldIdleSeconds`), and a lookup treats an expired entry as a miss; a warm dispatch that finds the bind already gone (the `pod.go:136` not-bound error or a `pod.go:112` `stream.Send` failure) also evicts the entry and cold-paths, so a same-replica continuation after a TTL-expiry release rehydrates through the cold path rather than surfacing a 500. The warm path creates a fresh `StateCompleted` response row for `GET /v1/responses/{id}` and for transcript recording without claiming a pod, dispatches onto the held pod-session id, skips 0059 rehydration, and still records the turn and lineage so the cold-path floor stays correct.

The shared Attach stream must not be driven by two concurrent turns. `PodExecutor.Send` holds `e.mu` only to guard the streams map rather than the Send and Recv pair (`pod.go:79-160`), and `AttachStream` wraps a raw gRPC bidi client with no internal mutex, so two same-conversation continuations dispatching onto one held pod-session id would race the stream and interleave the protocol. An in-flight guard on the affinity entry serializes this: a warm hit atomically takes and marks the entry as in-flight under the map mutex before dispatch and restores it to held on completion, and a concurrent continuation that finds the entry in-flight misses and takes the cold path (a fresh `BindSingleShot` plus `continuity.rehydrate`), delivering the fallback Decision 10 promises.

## 6. Non-goals

- **Holding or reusing a pod for OpenAI Chat Completions.** It is stateless with no server-side conversation id, so no held pod could be routed a continuation; `openai_chat.go:261` keeps its unconditional per-request release.
- **Removing or replacing 0059's transcript rehydration.** `continuity.rehydrate` remains the correctness floor for every cold turn (first turn, TTL expiry, cross-replica continuation); the held pod is a performance fast path layered on top.
- **Adding a Runtime CRD authoring surface** (a `SessionPolicy` block on `RuntimeSpec`). `SessionPolicy` has no CRD mirror today and `MaxClientIdleSeconds` reaches `runtimestore` only through the admin API; `PodHoldIdleTtlSeconds` follows that precedent.
- **Any change to the OpenAI-dialect wire contract.** The hold is inferred and time-bounded, with no client-declared session lifecycle, no new request field, and no new endpoint.
- **A new per-conversation in-process hold coordinator.** The release is enforced through the existing watchdog idle sweep on the `StateRunning` held pod-session (CODE-3). The `recycle.HoldCoordinator` is keyed per pod-claim at the reserved-hold recycle boundary and is a different concern.
- **Changing the REST interactive session lifecycle** (`sessionserver`), which already holds its pod for the session's duration and is untouched.
- **Cross-replica coordinated affinity or a distributed held-pod registry.** Affinity is best-effort per replica; a continuation on a different replica cold-paths, and a holder crash is reclaimed by the cross-replica watchdog idle sweep (CODE-3), bounded by `PodHoldIdleSeconds`, with §4.6.1 orphan-GC as a second-order backstop after the idle sweep flips the row terminal.
- **Building the C-22 §4.6 agent-pod eviction-checkpoint trigger.** It is unbuilt and out of this cluster's scope; a held pod evicted mid-idle reduces to preStop-SIGTERM today (accepted v1 gap), coordinated with proposal-B through the Integrator inbox.
- **An inter-turn scrub between turns of one held conversation.** The §13 isolation model treats the session as the scrub boundary; same-tenant same-conversation reuse without an inter-turn scrub is already precedented by the REST message path.
- **Re-litigating whether the feature should be added at all.** A challenge round examined whether the feature should be added and recorded the case against it: the concern of a pod-held multi-turn conversation without a per-turn re-claim already has a canonical surface in the interactive session model (`POST /v1/sessions/start`, `sessionserver/messages.go:263`), which holds one pod across many turns; the performance premise that per-turn re-claim is a bottleneck is unmeasured; and 0057 made the opposite call by an explicit human-signed-off decision that "retaining an idle warm pod between calls contradicts claim-per-request and warm-pool economics" (`proposals/0057...:33`), which this feature reverses. The human sign-off mandate (Decision 2) fixed the per-runtime `PodHoldIdleTtlSeconds` field and directed the build regardless, so the feature proceeds and its necessity is not re-litigated. The §15 spec amendment that documents the hold is staged as the prerequisite SPEC-1 deliverable (Section 5), rather than deferred, because the implementation contradicts the live synchronous-release text and `spec-driven-development.md` requires the spec change to land first.

## 9. Resolved in adversarial review

Subsequent adversarial review rounds populate this section. The challenge-round revisions carried in the draft narrowed the proposal from its original form:

## 10. Open decisions for review

- **Resource accounting and reap-under-pressure.** A held pod occupies a drawn warm pod and its §4.9 credential lease for the whole idle window. The existing §11 concurrency caps (global, per-user, per-team, per-runtime), the hierarchical quota, and the credential-pool `MaxConcurrentSessions` cap gate new admissions rather than reap an already-held pod under contention. Two decisions belong to the human: (a) does the held pod's implicit session continue to count against the §11 caps for its idle window (recommended: yes, so the existing per-tenant, per-user, and per-runtime caps already bound how many a tenant can hold), and (b) does v1 add a reap-under-pressure policy that proactively releases held pods (for example least-recently-used) when warm-pool draws start returning `WARM_POOL_EXHAUSTED`, or does v1 rely on the `onPoolExhausted` reject-or-queue path plus TTL-driven release alone, accepting that held pods can delay fresh cold claims until their windows expire?
- **Admission gating on a warm continuation.** A warm continuation claims no new pod or credential lease and reuses an already-admitted pod, so the create-response-row-without-claim path could skip the full §15.2.1 admission chain. Confirm whether a lightweight active-session or admission-rate check still applies to a warm turn, or whether reuse of an already-admitted pod exempts it.
- **Deploy-wide ceiling on the per-runtime TTL.** The mandate fixes the per-runtime field and its zero default. Confirm whether a deploy-wide `--max-pod-hold-idle-ttl-seconds` flag capping what a runtime can declare is wanted, analogous to how the recycle hold is deploy-wide via `--claim-hold-ttl-seconds`, or whether the operator guardrail is declined for v1.
