# Non-spec changes — Pre-materialize large git repositories on a warm pod

## Design (implementation-facing)

The normative rules live in the staged spec text: §6.4 **Repository stores.** (SPEC-2), §4.7.1 `FetchGitPack` (SPEC-5), §14 **Cache-served `gitClone` sources.** rules 1 to 7 (SPEC-3), §6.4 **Private repository stores.** (SPEC-2 Edit (c)), the §4.9 **`hostPatterns`** rules and **`git-https` credentials.** (SPEC-8), and the §12.4 and §28.3 restore lineage rows (SPEC-10). The deliverables below cite those homes and add only what the implementor needs beyond them.

Component split:

- **Gateway** (CODE-3, CODE-5): a per-replica bare mirror per mirror key (§6.4 **Private repository stores.** rule 4), tree validation at materialization, eligibility routing in the binder, and the `FetchGitPack` handler.
- **Pool ownership** (CODE-8): `ownerTenantId` on pool records, its admission, and the resolution rule.
- **Controller and registry** (CODE-2): the `gitRepository` entry travels from the Runtime CRD to the adapter flag and into `runtimestore`, so the pod, the binder, and the `FetchGitPack` authorizer see the same url set.
- **Adapter** (CODE-4, CODE-5, CODE-6): the warm fill before READY, slot-repository construction, the capture copy, and restore completion.
- **Images** (CODE-1): the images of the binaries that run git carry a git binary (CODE-1 step 2).
- **Credential resolution** (CODE-7): the `git-https` provider and host-to-pool binding that every authenticated gateway git operation goes through.
- **Restore lineage** (CODE-9): the record that §14 **Cache-served `gitClone` sources.** rule 7 states.

One url-normalization function, `gitref.NormalizeURL` in `pkg/gateway/provisioning/gitref`, implements the §6.4 rule. The CODE-2 uniqueness check, the binder, the `FetchGitPack` authorizer, and the adapter all call it. The adapter imports it from that package, or the function moves to a leaf package both trees import; it is never reimplemented. `NormalizeURL` has no failure path, because CODE-3 step 6 calls it on a url the pod supplies, and that step's table decides a url that matches no entry.

Every adapter git invocation runs with `-c protocol.allow=never` and an environment with `GIT_TERMINAL_PROMPT=0` and no `HOME` config. The adapter runs only the git subcommands named in this file.

   // The first response is header; every later response is pack_chunk.

   // spec: §4.7.1 Role and Gateway RPC Contract (FetchGitPack)

2. **Authentication.** In `gwcontrol_server.go`, register a stream interceptor chain (`grpc.ChainStreamInterceptor`) carrying stream forms of `leasecontrol.RequireVerifiedPeerInterceptor` and `leasecontrol.RequireSATokenInterceptor`, built from the same arguments as the unary chain. 3. **Mirror** (`gitref.Mirror`). One bare repository per key (step 7 rule M1), created with `transfer.fsckObjects=true`, `fetch.fsckObjects=true`, `fetch.unpackLimit=1`, `gc.auto=0`, `maintenance.auto=false`, `pack.threads=1`, `pack.windowMemory=64m`, `pack.deltaCacheSize=64m`, `core.deltaBaseCacheLimit=32m`, `http.lowSpeedLimit=1024`, and `http.lowSpeedTime=60`. With these settings a fetch never starts a gc or leaves loose objects, and a stalled transfer fails. Each operation on a key (`Ensure`, `ResolveRef`, `ValidateTree`, `Pack`) holds that key's lock shared for its duration. Fetches for one key run one at a time, and identical concurrent fetches share one. A fetch adds objects beside running readers, so only rules M2 and M8 take the lock exclusively, and neither waits for it.
   - `Ensure(ctx, key, cred, sha)` (step 7 rule M1) fetches `sha` when absent with `git fetch -- <url> <sha>:refs/lenny/<sha>`, in `gitref.Clone`'s `authEnv` environment with the credential the caller passes (zero for a public key), so later fetches negotiate from the commits the mirror holds.

4. **ValidateTree** (`gitref.Mirror.ValidateTree(ctx, url, sha, pathPrefix, allow, limit)`, where `allow` is the source's `upload.RuntimeAllow`). Walks the whole tree with `git ls-tree -r -t -l --full-tree` for each entry's path, mode, and blob size, and lists its objects with `git rev-list --objects --no-walk <sha>` piped to `git cat-file --batch-check='%(objecttype) %(objectsize) %(rest)'` (`%(rest)` makes cat-file split off the path). ls-tree prints no commit or tree sizes and omits the root tree, so the bound's commit-object and tree-object terms come from the listing. It applies §14 rule 2 from both. It reads both listings as streams and keeps no per-entry state, because every clause of rule 2 is per entry or a running sum. `allow` carries the Runtime's `allowSymlinks`; do not copy `extractGitCloneSource`'s `AllowSymlinks: true`. Symlink targets go through `upload.ValidateSymlinkTarget` with the link path joined under `allow.WorkspaceRoot` and `pathPrefix`. A violation returns `*upload.ValidationError` with the matching `upload.Reason`. Add `upload.ReasonWorkspaceSizeLimit Reason = "workspace_size_limit"` for the bound's refusal, and the exported constant `checkpoint.DefaultWorkspaceSizeLimitBytes` (512Mi, the §4.4 default) in `pkg/checkpoint/checkpoint.go` for a zero `limit` (CODE-5 step 1).
   - Memoize the limit-independent results under step 7 rule M5: the path and symlink verdict and the materialization bound go in the verdict memo, and the listing's summed blob and tree-object bytes go in the tree-bytes memo. Compare the bound against `limit` on every call.
5. **Pack** (`gitref.Mirror.Pack(ctx, key, cred, want, have, w)`, with the key and credential of step 7 rule M1). Implements the §4.7.1 pack rule. Before it acquires its slot (step 7 rule M4), `Pack` `Ensure`s `want` and gives an unknown `have` one `Ensure`, dropping it when it is still absent. The delta's object bytes come from `git rev-list --objects <want> --not <have>` piped to `git cat-file --batch-check='%(objectsize)'`, compared with the `want` tree's summed blob and tree-object bytes (step 7 rule M5). The pack is produced with `git pack-objects --stdout` (never `--thin`) and streamed to `w`. A shallow pack is produced by piping step 4's object listing of `want` (`git rev-list --objects --no-walk <want>`) into `pack-objects`.

7. **Resource and admission model.** These rules are the one home of the mirror's keys, disk, concurrency, waiting, memory, process limits, and deadlines, for every git child the gateway starts. Every other site cites them by number.
   1. **M1 · Key.** A mirror key is the key §6.4 **Private repository stores.** rule 4 defines, carried as `gitref.MirrorKey{Owner, URL}`, with `Owner` empty for a public entry and set to the `OwnerTenantID` of the pool step 6 matched for a private one. The `url` parameter of `Ensure`, `ResolveRef`, `ValidateTree`, and `Pack` is a `MirrorKey`. `Ensure`, `ResolveRef`, and `Pack` also take a `gitref.Credential` after the `MirrorKey`, zero for a public key: the step 6 handler and the CODE-5 binder pass the credential they resolve under §6.4 rule 4, and `Pack` passes it to its own `Ensure` calls. Every lock, single-flight, memo entry, and recency record in steps 3 to 5 is per key. Each key has one bare repository at `<root>/m/<hex sha256 of Owner, a NUL byte, and URL>`. The gateway uses a key only after step 6's authorizer or §14 rule 1 has matched the request to a registered entry, so request input alone never creates a key. No per-tenant cap applies. Rule M2's deletion ignores the owner, so one tenant's fetches can delete another tenant's idle mirror, which costs that tenant a refetch.
   2. **M2 · Disk.** The root is the `git-mirror` volume (step 9). The budget is `gateway.gitMirror.maxBytes`, measured as the summed size of the regular files under `<root>`. The replica takes the measure before each fetch, before `Ensure` takes the requested key's lock, and every 5 seconds while a fetch or a clone runs. While the measure exceeds `maxBytes`, the replica deletes the least-recently-used key mirror whose lock it can take exclusively without waiting, taking the requested key's mirror last, and drops the deleted key's memo entries. When no mirror is left to delete and the measure still exceeds `maxBytes`, the fetch about to start and every running fetch and clone fail with `RESOURCE_EXHAUSTED`, and the replica logs the measure and `maxBytes` at WARN. The measure therefore exceeds `maxBytes` by at most what the running fetches and clones write in one 5-second interval. `<root>/tmp` holds the clone directories of `Mirror.CloneArchive`. A fetch that exits non-zero deletes the `tmp_*` files under its key's `objects/pack` and the `*.lock` files in its key's repository before it releases its slot, because a killed fetch leaves both behind. `buildPodLifecycle` in `cmd/lenny-gateway/pod_lifecycle.go` constructs the replica's one `gitref.Mirror` in its `--agent-namespace` block, shares it between the step 6 handler and the CODE-5 binder, and exits on a construction failure. The constructor deletes the root's contents before any mirror operation. A gateway without `--agent-namespace` constructs none and never reads the root, because it has no binder and rule P1 refuses every `FetchGitPack` before any mirror read.
   3. **M3 · Fetches.** Each mirror fetch holds one slot of a per-replica `subsystem.Limiter` sized by `gateway.gitMirror.maxConcurrentFetches` from before git starts until git exits, and each `Mirror.CloneArchive` holds one slot until it returns. Concurrent `Ensure` calls that step 3 merges into one fetch hold one slot between them. That fetch runs under a context that is cancelled when its last waiting caller returns. Step 3's `http.lowSpeed*` settings fail a stalled transfer, which releases its slot. `ResolveRef`'s `ls-remote` holds a rule M10 probe slot.
   4. **M4 · Packs and tree walks.** A second per-replica `subsystem.Limiter`, sized by `gateway.gitMirror.maxConcurrentPacks`, bounds pack production and tree walks. A `Pack` holds one slot from before its walk or `pack-objects` starts until its stream or its context ends. A `Pack` for a ref `want` takes a slot of the warm share, a third per-replica `subsystem.Limiter` sized W = max(1, `maxConcurrentPacks` − 2), immediately before its M4 slot and releases both together, so commit-SHA `Pack`s and walks never wait behind more than W warm fills. A `ValidateTree` memo miss holds one slot for its walk, and a walk inside a `Pack` uses that `Pack`'s slot. No caller holds a fetch slot while it holds a pack slot. The binder calls `ValidateTree` directly, through neither `UploadGate` nor `gatedExtract`. A walk therefore holds no Upload Handler slot, and its refusals never reach the upload breaker or `lenny_upload_extraction_aborted_total`. No mirror limiter has a breaker or is a `subsystem.Subsystem` or publishes a `subsystem`-labelled gauge.
   5. **M5 · Tree memo.** Step 4 memoizes into two maps per key. The verdict memo is keyed by `(sha, pathPrefix, allow.AllowSymlinks, allow.WorkspaceRoot)`. The tree-bytes memo is keyed by `sha`, and every walk fills it. Concurrent `ValidateTree` calls with one verdict key share one walk. The leader acquires the walk's M4 slot only after it becomes the leader, and the walk waits for that slot and runs under its own context, which, like rule M3's merged fetch, is cancelled when its last waiting caller returns, so a caller whose own context ends returns without ending the walk for the others. A `Pack` reads the tree-bytes memo when it holds the `sha`; otherwise it computes the sum in its own slot, and it never waits on another caller's walk. Entries are dropped only with their key's mirror or on restart, so the memo grows by one entry of a few hundred bytes per distinct validated `(sha, pathPrefix, allow)`. This growth is accepted.
   6. **M6 · Waiting.** A caller waits for an M3 or M4 slot within its own context (a shared walk waits under rule M5's context), with no queue-depth bound. When the context ends first, the caller holds no slot. The binder's context is the bound of §7.1 **Bind bounds.** A `FetchGitPack` handler's context is rule M11's, and the adapter's call can end it sooner: at the fill deadline (CODE-4 step 2.1) for a warm fill, at the bound of §7.1 **Bind bounds.** for §14 rule 3 packs and for restore completion at a first bind (CODE-6 step 3), and at the resume attempt's bound (§7.1 **Bind bounds.** rule 3) for restore completion on a resume. A resume attempt's bound is a cancellation with no gRPC deadline, so its calls end with `CANCELED` at the adapter. On a replica that starts with an empty mirror, the last of n warm fills against it completes within the fill deadline when ceil(K / `maxConcurrentFetches`) × t_fetch + ceil(n / W) × t_warm does not exceed that deadline. K is the number of keys the replica fetches at once, t_fetch and t_warm are INFRA-1 phase (g)'s times, and W is rule M4's warm share. The probes of n ref-want fills complete within `gitref.DefaultTimeout` when ceil(n / `maxConcurrentProbes`) × t_resolve does not exceed it, where t_resolve is INFRA-1 phase (g)'s time. A fill that misses the deadline takes its pod to `failed` (§6.4 **Repository stores.**).
   7. **M7 · Memory.** The gateway container's memory limit is at least B plus, for each admission limit in rule M10's table, that limit times the largest memory per holder among the rows it admits. B is the memory limit the deployment needs with no repository store (`512Mi` at the chart default). D is `gateway.gitMirror.maxProcessMemory`. S is INFRA-1 phase (g)'s largest summed peak, within one holder, of the processes the table does not count at D, plus the handler's 1 MiB chunk buffer. The upload path's in-process memory is outside this sum.
   8. **M8 · Tenant purge.** Every 30 seconds, the replica deletes the mirror of each private key whose `Owner` the `OwnerRegistered` function reports unregistered, per §6.4 **Private repository stores.** rule 4. It takes the key's lock exclusively without waiting and drops the key's memo entries as rule M2 does. A key whose lock is held, or whose registration read fails, is kept until a later pass, and a failed read is logged at WARN. `gitref.Mirror` gains the field `OwnerRegistered func(ctx context.Context, tenantID string) (bool, error)`, which `cmd/lenny-gateway` sets to `tenantRegistered` over its tenant store.
   9. **M9 · Git child runner.** Every git process the gateway starts goes through `gitref.runGit` in `pkg/gateway/provisioning/gitref/run.go`. `LsRemoteResolver.Resolve`, `Clone`, and every `Mirror` method call it, and no other gateway code starts git. `LsRemoteResolver` takes the probe limiter and D through `gitref.Options`, and `cmd/lenny-gateway` builds one resolver before `buildPodLifecycle` and passes it to `sessionsrv.go` and to the `gitref.Mirror`. The runner does the following.
      1. It starts `/bin/sh -c 'ulimit -d "$1" || exit 127; shift; exec "$@"' sh <KiB> <git> <args>`, where `<KiB>` is the row's ceiling in rule M10. Linux charges `RLIMIT_DATA` to private writable memory and leaves git's read-only pack mappings uncounted, so a process over the ceiling fails its own allocation and the gateway keeps running. Arguments pass as positional parameters and never enter the script text.
      2. It sets `Setpgid: true`, a `cmd.Cancel` that sends SIGKILL to the process group, and a `cmd.WaitDelay` of 5 seconds, as `pkg/adapter/workspace/setup.go` does, because `exec.CommandContext` signals only the direct child.
      3. It calls `syscall.Setpriority(syscall.PRIO_PROCESS, pid, 19)` after `Start` and logs a failure at WARN, so Go threads win the container's CPU share on a saturated node. A helper forked before that call stays at nice 0, which is harmless.
      4. It keeps the last 64 KiB of stderr, and of stdout unless the caller streams it. A non-zero exit returns that tail in its error, and the caller logs it at WARN.
      5. After `Wait` returns on a cancelled call, a goroutine calls `syscall.Wait4(-pgid, nil, 0, nil)` until `ECHILD`, because the gateway is PID 1 in its container and inherits the killed group's orphans.

## Edge cases and accepted failure modes

- **A `pod_id` naming another pod.** Served for a public entry when `podIdentityEnforced` is false, which §10.3 does not permit (CODE-3 step 6 rule I2). Every other GatewayControl RPC keeps the gap REC-1 files.
- **A pod that consumes its pack stream slowly.** It holds its rule M4 slot until CODE-3 step 7 rule M11's deadline at the latest. No per-pod limit applies, so one pod that opens many calls and stops reading can hold every slot for that long, and fills and binds on that replica wait.
- **A repository that outgrows `maxProcessMemory`.** The git process fails its allocation, the operation fails as a failed fetch or pack, and the replica keeps serving. Fills for that repository fail until the deployer raises the value.
- **A cold clone behind mirror fetches.** It waits for a fetch slot within the bound of §7.1 **Bind bounds.** (CODE-3 step 7 rules M3 and M6), and a replica fetching large repositories can fail it.
- **Git CPU in the autoscaler.** Git children count toward container CPU utilization, so a warm refill can scale the gateway out up to `maxReplicas`. This is accepted, because queue depth stays the primary signal.
- **Mirror loss on a gateway restart.** The mirror is an `emptyDir` cache. The next request refetches.
- **Many keys fetched on a cold replica.** Warm fills queue on the mirror limiters and can miss the fill deadline (CODE-3 step 7 rule M6).
- **A gateway replica without the source's commit.** `Ensure` fetches it by SHA. A remote that deleted the commit returns `NOT_FOUND`, and the materialization or restore fails.
- **Store staleness on recycling pools.** A store is never refreshed. A fresher store arrives with a replacement pod, bounded by the existing recycle limits.
