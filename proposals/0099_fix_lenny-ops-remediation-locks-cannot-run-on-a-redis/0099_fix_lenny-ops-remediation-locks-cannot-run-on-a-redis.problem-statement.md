# Problem: lenny-ops remediation locks are not atomic and cannot run on a Redis Cluster

## Statement

The lenny-ops Tier 2 remediation-lock store fails on a Redis Cluster today, and its acquire path breaks the §25.4 atomicity requirement on every Redis topology. The Helm chart passes `--redis-cluster-addrs` to lenny-ops when `redis.provider=cluster`. lenny-ops then builds a go-redis `ClusterClient` and hands that client to the Tier 2 lock store. The store uses three keys that hash to unrelated slots: `ops:lock:<scope>`, an `ops:lockidx:<id>` id index that no specification section documents, and `ops:lock-epoch:current`. The acquire and release Lua scripts take the scope key and the id-index key. `RemoveByID`, which the §25.4 split-brain reconciliation calls, runs the same release script. Extend and Steal write both keys through the `persist` transaction (`TxPipeline`). Every one of these operations spans two slots, so a Cluster rejects it with CROSSSLOT. Acquire also reads the epoch with a separate `GET`, and reads Redis `TIME` with a separate command, before its script runs. §25.4 "Storage Tiers" says the Tier 2 Lua script reads `ops:lock-epoch:current` atomically, derives `acquiredAt` and `expiresAt` from `redis.call('TIME')`, and writes with `PEXPIREAT`. The code does none of these inside the script and uses a relative `PEXPIRE`. This is BUILD-GAPS F-12.4.28 class B/C and remediation plan item P6.

§12.4 states no rule that tells a literal hash tag from a placeholder in a key pattern, and the specification uses braces for both. `t:{tenant_id}:`, `{root_session_id}:dlg:*`, and `lenny:pod:{pod_id}:*` are literal hash tags that the code writes with braces. `cb:{name}`, `sq:{tenant_id}`, `rl:{key}:{minute_epoch}`, `derive_lock:{source_session_id}`, `conn:oauth:state:{state}`, `pg:sess-tenant:{session_id}`, `lenny:events:{session_id}`, and §25.4's `ops:lock:{scope}` and `ops:escalations:{id}` are placeholders that the code writes without braces. The only related sentence is local to the §12.6 EventBus paragraph ("the `{tenant_id}` hash tag is still the first `{...}` match"). A rule that "the first braced segment of a key pattern is a literal hash tag" would misdescribe every placeholder pattern above, so the brace rule has to be worded so that it does not reclassify existing placeholders, or the notation change has to cover every key pattern the rule governs.

The fix has two parts that are staged and verified as separate deliverables. Part 1 names the lock key, the id-index key, and the epoch key under one shared hash tag in §25.4 (the Tier 2 paragraph, the Tier Transitions paragraph, and the Storage Routing row) and in the code. It moves the epoch read into the acquire script and reconciles the `TIME` and `PEXPIREAT` statements in §25.4 with the code, either by moving them into the script or by correcting the text. It confirms that acquire, release, `RemoveByID`, extend, and steal touch only the co-located keys, adds the §12.4 brace rule under the constraint above, and keeps the existing node-routed lock scan. Part 1 removes the `pkg/ops/coordination/redisstore` entry from the tier-0 Redis cluster safety exemption list, installs the cross-slot hook in the lock store's test constructors with a negative control, covers the operations and epoch transitions on the existing Redis Cluster test container, and updates the tier-11 key registry check. That check forbids `ops:lock:` and `ops:lockidx:` in §12.4, so any example the new §12.4 rule quotes must stay consistent with it.

Part 2 is the owner's 2026-10-21 decision that one Redis Cluster may serve every concern at Tier 3. §17.8.2 today places coordination on Sentinel and quota on Redis Cluster at Tier 3, and its Single-tenant Redis topology note prescribes separate Sentinel instances per concern. The relaxation rewrites the §17.8.2 Concern separation row and the single-tenant note. It deletes the per-tenant `redis.quotaStoreBackend` migration step and the sentence "The Coordination instance remains on Sentinel throughout" from the §12.4 pre-plan step 4, and it revises step 5 (Rollback), which also relies on the per-tenant flag. No code implements `quotaStoreBackend`. The relaxation holds under stated conditions: every store keeps each multi-key command inside one slot and routes `SCAN` to every primary, coordination correctness never depends on Redis durability, every Redis failure path is bounded and fails closed, and the lease TTL stays at least four renewal intervals. A per-concern endpoint remains an optional operator lever using the per-concern URLs the code already has. No per-concern Sentinel or Cluster wiring is added. The proposal verifies each condition against every Redis store and records any condition the code does not meet as a defect or a deliverable. Part 1 discharges the single-slot condition for the ops lock store.

## Who observes it

An operator or agent that acquires, extends, steals, or releases a remediation lock on an install with `redis.provider=cluster` while Postgres is unreachable. Tier 1 (Postgres) serves every acquisition while Postgres is healthy, so the defect stays hidden in normal operation and appears during a Postgres outage, which is when remediation is most likely. The coordination service maps the CROSSSLOT error to `ErrStoreUnavailable` and falls through to the in-memory tier (pkg/ops/coordination/service.go). The split-brain reconciler also observes it after recovery, because `RemoveByID` fails on a Cluster. The epoch read outside the script is observable on every topology only inside a narrow window at the Postgres-to-Tier-2 transition, where an `INCR` between the `GET` and the script stamps a lock with the previous epoch.

## What breaks if nothing changes

- On a Cluster install with the chart defaults (`ops.replicas: 1`, `ops.locks.memoryTier: single-replica-only`), a Postgres outage drops lock acquisition to replica-local in-memory locks. They remain exclusive because one replica runs, but they do not survive a lenny-ops restart, and the Tier 2 store reports itself as unavailable while Redis is healthy.
- On an HA Cluster install (two or more replicas), every acquisition returns `503 REMEDIATION_LOCK_NO_COORDINATION` for the length of the Postgres outage.
- The failure mode is loss of Tier 2 availability. It fails closed or degrades and does not produce two holders of one lock, because acquire cannot write any Redis lock on a Cluster.
- The specification stays inconsistent with a configuration the chart accepts: a `redis.provider=cluster` install already runs coordination on a Cluster, against the §17.8.2 placement of coordination on Sentinel.
- §12.4 keeps an ambiguous brace notation, so the next key pattern the specification writes can repeat the hash-tag-versus-placeholder confusion.

## Prior art considered

- Merge 4114b2c95 is the direct fix for F-12.4.28 classes A and A′ and F-12.4.29. It renamed tenant keys under `t:{tenant_id}:`, installed the cross-slot test hook in the gateway stores, and added node-routed `SCAN`. Its resolution note hands class B/C to P6 because the rename needs a §25.4 change. It does not solve this problem, and its test infrastructure (clustertest, the Redis Cluster container, the tier-4 smoke test) is available to this proposal.
- Proposal 0093 filed the cross-slot defect as REC-1 without staging a fix. Proposal 0032 routed the ops lock keys to §25.4 as their owning section and kept them out of the §12.4 registry.
- No other proposal or branch stages this change. The remediation plan lists P6 as not yet written.
- The §12.6 EventBus "first `{...}` match" sentence and §8.3 R-04 are precedent for hash-tag semantics. Neither is a general §12.4 rule.
- No spec passage already permits one Cluster for every concern at Tier 3.
- The chart's `redis.provider` renders exactly one connection block, so the relaxed single-endpoint topology already runs in code. The Part 2 spec change follows the code rather than adding wiring.

  - Holds narrowly: §12.4 has no brace rule, but §12.6 EventBus and §8.3 R-04 contain related local language. Verified; recorded.
