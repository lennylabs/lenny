# Non-spec changes: Session suspend, idle suspension, and resume driver

## Design (implementation-facing)

This proposal lands after proposal 0091. CODE-4 deletes the `ErrHeld` hold in `holdOrFailOnResumeError` that 0091 CODE-2 adds, and CODE-5 edits the `Sweep` loop that 0091 CODE-5 rewrites. Each edit is located by function and quoted text against the 0091 version of the code.

Each code deliverable states the invariants its code holds, the files it touches (its `Targets:` line), and the tests that pin each invariant. The SPEC item a deliverable cites is the normative statement of the behavior, and the deliverable does not restate it. Where the spec leaves a function-level choice open, the deliverable marks it **IMPLEMENTOR'S CHOICE** and states its bound. Rationale and history are in the review log entry `[restructure.non-spec-to-constraints]`.

The components:

- **Watchdog** (`pkg/gateway/runtime/watchdog`) lists rows and calls optional hooks that the session server implements: `ResumeDriver` (CODE-4), and `SuspendedPodReleaser`, `IdleSuspender`, and `BacklogResumer` (CODE-6). It gains `sweepSuspended` (CODE-6 item 2) and measures session age as active time (CODE-1).
- **Session server** (`pkg/gateway/sessionserver`) implements the hooks.
- **Binder** (`pkg/gateway/podlifecycle/podsession`) gains the post-claim callback (CODE-3) and `ReleaseUncommitted` (CODE-4 item 5.3).
- **Coordination Sweeper** (`pkg/gateway/coordination/coordination`) widens its adoption predicate and holds no lease for a podless `suspended` session (CODE-5).
- **Gateway leader** (`cmd/lenny-gateway/leader_sweeps.go`) runs the podless `suspended` backlog re-check (CODE-6 item 16).
- **Runtime adapter** (`pkg/adapter`) records each session's last activity, including a runtime's `busy` report, and seals a session against `message` delivery after an idle window without activity (CODE-6 items 4 and 18). The runtime SDKs (`sdks/runtime/{go,python,typescript}`) report `busy` (CODE-6 item 18.4).

**Design lease gate.** (D1) The resume driver, the suspension release, the idle suspension, the backlog resume of a row that names a pod, and every held-pod resume act only when the session's `REG-COORDLEASE` names this replica. They act on every session when no lease store or no pod binder is wired. A lease read that fails counts as "not the holder". Each caller states its outcome on a refusal. Pinned by the off-holder cases under the CODE-4 and CODE-6 tests.

**Design binding check.** (D2) When a pod binder is wired and this replica's pod registry holds no binding for the session, the suspension release, the idle suspension, and the backlog resume return before any lease read. Pinned by `TestBacklogAndReleaseSkipUnboundSessionWithoutLeaseRead_spec_7_2`.

**Per-session delivery lock.** (D3) `Server` gains `deliveryLocks`, a second instance of the per-session lock type in `slot_bind.go`, separate from `slotAccountLocks`. On one replica it makes each of the following one critical section against the delivery of held messages:

- the REST and MCP message paths, from the classification read through the hold or the send (taken honoring the request context);
- `completeResume`, `resumeHeldAndDrain`, and `handleStart`, from before their `running` write until `deliverBuffered` returns;
- the `lenny/delegate_task` held delivery.

Never take `slotAccountLocks` while holding the delivery lock, and never take the delivery lock while holding `slotAccountLocks`. The lock is not reentrant, so never call `ResumeSuspended` while holding it. `ReleaseSuspendedPod`, `SuspendIdle`, `enterResumePending`, and `BacklogRechecker.Pass` take no delivery lock. The lock orders nothing across replicas. Across replicas, the guarded row writes (D4) order the state changes, and the adapter's session seal (CODE-6 item 4 **Session seal.**) orders every delivery against an idle suspension. Cite `// spec: §7.2 (Message delivery routing — seven paths, path 6)`. Pinned by `TestHeldMessagesDeliveredBeforeNewMessage` and the tier-7a `TestHeldMessageRacingCommitDeliveredOnce`.

**Session-row read authority.** (D4) `Get`, `GetByID`, `List`, and `ListByRoot` read the §12.3 read pool, which lags the primary.

- A read-pool row may select work and serve a listing, a client-facing status, or a request's entry precondition check (`loadMessageTarget`, the MCP target lookup, `handleInterrupt`, `handleTransition`, `handleDelete`). It never decides a write. Every session-row write in this proposal re-evaluates, inside its `Update` mutator on the locked row, the state and every field its selection used: `UpdatedAt` for a window, `CoordinationGeneration`, `PodAssignment`, `SuspendedAt`, or `LastAgentActivityAt`. An active age past its cap needs only the state re-check. Work that writes no session row, such as a checkpoint or a `HeldLen` count, may act on the listed row.
- A one-shot decision that has no write of its own reads the primary through `sessionstore.ReadPrimary(ctx context.Context, st Store, timeout time.Duration, tenantID, id string) (Session, error)`, new in `sessionstore.go`. Such a decision is a route, a skip, a nil return, or the expected value of a compare-and-swap. `ReadPrimary` writes nothing: it advances no `UpdatedAt`, accrues no session age (CODE-1 item 3), and returns `ErrNotFound` and every other error unchanged. It runs under `context.WithTimeout(ctx, timeout)`, and a `timeout` at or below zero uses the exported `DefaultPrimaryReadTimeout` (5 s), so no call is unbounded. On expiry it returns an error that wraps `context.DeadlineExceeded`. Session-server sites call one helper, `s.readPrimary(ctx, tenantID, id)`, which passes the `primaryReadTimeout` field. That field is set from `Options.PrimaryReadTimeout` and defaulted beside `streamFailureReportTimeout` in `sessionserver.go`. Every `mcptools` read passes `deps.PrimaryReadTimeout`, which `cmd/lenny-gateway/mcpsurface.go` sets from the same flag: the MCP `lenny/send_message` classification read and its re-read after a seal refusal (CODE-6 item 7 **MCP**, in `mcptools_register.go`), and the `lenny/delegate_task` read. The flag is `--session-primary-read-timeout` / `LENNY_SESSION_PRIMARY_READ_TIMEOUT`, with default `sessionstore.DefaultPrimaryReadTimeout`. Its help states that the value is operator-tunable and bounds each primary read a one-shot decision makes, and startup exits with an error on a non-positive value. The 5 s default matches the bound the activity stamp already puts on its primary write (`sessionidle.go`, `persist`). An expired deadline is a primary error: on the message paths it takes the **Primary error** column of the **Message-path read failures.** table, and at every other site it takes the path that site's read error takes. No spec or docs page states the value, as for `--stream-failure-report-timeout`. Its sites are `holdMessage` (CODE-4 item 7), `handleResume` (CODE-4 item 8), `attemptResume` step 1 (CODE-4 item 3.1), the row `ReportSessionFailure` routes (`failure.go`), `ReportAttachStreamFailure` (CODE-4 item 16), `persistDeriveFailure` (CODE-4 item 17), the `ReleaseSuspendedPod` step 3 re-read (CODE-6 item 4), and the message-path reads in the table below.
- A mutator that decides not to write returns a package sentinel and never nil. The caller treats `errors.Is(err, <sentinel>)` as no change: it counts nothing, notifies nothing, runs no terminal hook, and continues. `Update` returns a zero `Session` with any error, so a caller that needs the row its guard read copies that row inside the mutator.

**IMPLEMENTOR'S CHOICE:** how `ReadPrimary` reaches the primary, for example an `Update` whose mutator copies the locked row and returns an unexported sentinel. Bound: it writes nothing and returns within its deadline. When the deadline expires during a primary partition, a row lock the read took stays on the primary until the primary ends the abandoned connection, as for any guarded write abandoned on the same path.

The watchdog's pre-running timeout sweep and `sweepAwaitingClientAction` keep their nil-returning mutators, and RECORDS-1 item 7(k) files them. Cite `// spec: §12.3 (Postgres HA Requirements)` on `ReadPrimary`. Pinned by `TestReadPrimaryWritesNothing_spec_12_3`, `TestReadPrimaryLeavesRowUnchanged_spec_12_3`, `TestReadPrimaryHonorsDeadline_spec_12_3`, `TestSessionPrimaryReadTimeoutFlag`, the tier-8 `TestPrimaryPartitionDeliversToRunningSession_spec_7_2`, and the `laggingGetStore` cases under the CODE-4 and CODE-6 tests.

**Message-path read failures.** (D5) Two invariants govern the reads on the REST and MCP message paths. (I1) A new message is never handed to the runtime ahead of a held entry that the delivering replica can read (SPEC-5i **Delivery of held messages.**). An entry that `Peek` or `PeekOldest` cannot read is outside I1. (I2) No session-row read on these paths refuses or stalls a message to a session whose entry row reads `running` during a §12.3 primary failover or partition, unless an idle suspension has sealed the session. The REST tenant-suspension and injection-support gates in `loadMessageTarget` read the primary and are outside I2. The entry row is the read-pool row that `loadMessageTarget` or the MCP target lookup read before the delivery lock. The classification read falls back to that row. A stale fallback row cannot end a turn, because the adapter of a session an idle suspension sealed refuses the delivery (CODE-6 item 4 **Session seal.**). No other read falls back to the read pool. The held branch is CODE-6 item 7's, run on the classification row with `State` set to `suspended`. Pinned by `TestMessagePathsClassifyPrimaryRow_spec_7_2`, `TestRefusedBatchRereadFailureTakesHeldBranch_spec_7_2`, `TestDelegateTaskDeliversHeldAfterTaskInput`, and the tier-8 `TestPrimaryFailoverDeliversToRunningSession_spec_7_2`, `TestPrimaryPartitionDeliversToRunningSession_spec_7_2`, `TestStaleRowDeliveryRefusedBySeal_spec_6_2`, and `TestHeldReadOutageDoesNotStallDelivery_spec_7_2`.

| Read | `ErrNotFound` | Primary error, read-pool row readable | Both unreadable |
|:--|:--|:--|:--|
| Classification read, under the delivery lock (`ReadPrimary`) | REST answers 404 `RESOURCE_NOT_FOUND` as `loadMessageTarget` does, and MCP answers `errSessionLookup`. Nothing is held or sent. | Classify the entry row, and log at WARN with the session ID. | Does not arise, because the entry read succeeded before the lock. |
| Re-read after a seal refusal (`executor.ErrSessionSealed`) on the `ActionDeliver` branch (`ReadPrimary`) | Held branch. | Held branch, with no read-pool fallback: a lagging row reads `running` and routes back to path 2. | Held branch. |
| `bufferAfterResumedSendFailure` re-read (`ReadPrimary`) | Held branch. | Held branch, with no read-pool fallback. The inbox is not a valid destination when the row cannot rule out a recovering state. | Held branch. |
| `SessionDelivery.DeliverHeld` | Reads no row. It delivers on the `running` row its caller passes. | Reads no row. | Reads no row. |
| `ResumeSuspended` | Reads no row. It branches on the row its caller passes, and every write it makes is guarded on the locked row. | Reads no row. | Reads no row. |
| delegate_task child read after the task input, under the delivery lock (`ReadPrimary`) | No delivery. | No delivery, with no read-pool fallback: the task-input turn can move the child out of `running`, and a lagging row cannot show it. | No delivery. |

The other reads on these paths state their own failure outcomes: `holdMessage`'s terminal re-read in CODE-4 item 7, `deliverBuffered`'s `Peek` and `PeekOldest` in CODE-4 item 6, and `HeldLen` at its callers in CODE-6 item 2, item 4 step 3a, and item 16.3.

## Staged code changes

### CODE-1 · Active-time session age in the store funnel

Targets: `migrations/0182_sessions_accumulated_session_age.up.sql` and `.down.sql` (the next number after 0181); `pkg/gateway/session/sessionstore/sessionstore.go`; `pkg/gateway/session/sessionstore/pgstore/pgstore.go`; `pkg/gateway/session/sessionstore/memstore/memstore.go`; `pkg/gateway/runtime/watchdog/watchdog.go`; `pkg/gateway/sessionserver/resume_held_pod.go`; `cmd/lenny-gateway/flags.go`; `pkg/gateway/runtime/runtimestore/runtimestore.go`; `pkg/api/v1/session/retry_policy.go`; `pkg/gateway/externalapi/openapi/openapi.json` and the generated `pkg/ops/mcp/generated_tools.go` and `pkg/gateway/mcpfabric/mcptools/generated_schemas.go`.

1. **Migration.** `ALTER TABLE sessions ADD COLUMN accumulated_session_age_seconds double precision NOT NULL DEFAULT 0 CHECK (accumulated_session_age_seconds >= 0)`. The down migration drops the column.
2. **Field and helpers** in `sessionstore.go`: the field `AccumulatedSessionAgeSeconds float64` on `Session`, and two exported helpers.
   - `AccrueSessionAge(prev session.State, prevUpdatedAt time.Time, row *Session, now time.Time)`: when `prev` is `starting`, `running`, or `input_required`, it adds `max(0, now - prevUpdatedAt)` in seconds to `row.AccumulatedSessionAgeSeconds`.
   - `ActiveAge(row Session, now time.Time) time.Duration`: the accumulated value, plus `now - row.UpdatedAt` when `row.State` is one of those counting states.
3. **The funnel.** In both stores' `Update`, after the mutator returns and before the `UpdatedAt` stamp, call `AccrueSessionAge(prev.State, prev.UpdatedAt, &row, now)` with the same `now` the stamp uses. Add the column to `Create`, to the `UPDATE` statement, to the select list, and to the scan in `pgstore.go`. `Store.Update` is the only writer of the sessions row; grep for any other `UPDATE sessions` statement and route it through the helper. A write that does not change the state still accrues, because the row stays in the counting state across it.
4. **Sweeps.** `sweepMaxAge` and `sweepExpiryWarning` compare `sessionstore.ActiveAge(row, now)` with `effectiveAgeCap` in place of `now.Sub(row.CreatedAt)`. Rewrite the doc comments of `sweepMaxAge`, `sweepExpiryWarning`, `DefaultMaxSessionAgeSeconds`, `Config.MaxSessionAgeSeconds`, the `resume_pending` and idle-clock comments, the `--max-session-age-seconds` help in `cmd/lenny-gateway/flags.go`, the `Limits` and `SessionPolicy` `MaxSessionAgeSeconds` comments in `runtimestore.go`, the `RetryPolicy.MaxSessionAgeSeconds` comment in `retry_policy.go`, and the `retryPolicy` and `sessionPolicy` `maxSessionAgeSeconds` descriptions in `openapi.json`, which describe age as wall-clock or total lifetime, as the SPEC-4a active-time cap; then run `make generate` and `go generate ./pkg/gateway/mcpfabric/mcptools/...` to regenerate `generated_tools.go` and `generated_schemas.go`. `sweepMaxAge`'s mutator returns a new package sentinel `errMaxAgeSuperseded` on a terminal row in place of nil, and the sweep runs no expiry side effect on that sentinel (Design **Session-row read authority.**). Cite `// spec: §6.2 (maxSessionAge timer behavior across states)`.
5. **Evaluation on entry to `running`.** The §6.2 paragraph after the pause table evaluates the timer on every transition into `running`. A paused session cannot gain age, so the only over-cap row that can reach `running` is one that left a counting state over the cap before a sweep saw it. CODE-4 item 1 covers the driver call, and this step covers the held-pod resume:
   - `resumeHeldPod` refuses, with an error the message path already treats as a failed resume, a row whose `ActiveAge` exceeds the effective cap.
   **IMPLEMENTOR'S CHOICE:** how `resumeHeldPod` obtains the effective cap. The constraint is that it returns the value `effectiveAgeCap` returns for the same row, from one shared resolver rather than a second copy of the min-wins logic.

### CODE-3 · Binder post-claim callback

Targets: `pkg/gateway/podlifecycle/podsession/resume.go`, `bindrequest.go`, `binder.go`, `claimconnect.go`, `bindclaim.go`, `bindprepare.go`, `bindlaunch.go`, and `slotbinder.go` (the slot-bind request, `connectSlot`); `pkg/gateway/sessionserver/pod_launch.go`, `slot_bind.go`, `resume_rebind.go`, and `checkpointResumeRequest`.

1. Add `OnClaimed func(context.Context) error` to `podsession.ResumeRequest`, `BindRequest`, and `SlotBindRequest`. A nil hook is a no-op, which covers create and start.
2. Split `connect` (`claimconnect.go`) into `claimPod`, which runs the claim and the fallback claim and returns the claimed sandbox name, and `handshake`, which runs `resolveSandbox`, `DialAdapter`, `NegotiateVersion`, and the `ClaimAccepted` record and closes any client it opened on its own failure. Invoke the hook once per binder call, after the claim and after the slot reservation where there is one, and before `handshake`:
   - `Binder.Resume`: `claimPod`, `reserveResumeSlot` on the claimed sandbox name, hook, `handshake`, `AssignCredentials` (CODE-4 item 20), `cl.Resume`. A `reserveResumeSlot` failure precedes the hook and releases nothing, as today.
   - `Binder.Claim`, and therefore `Binder.Bind`: `claimPod`, hook, `handshake`.
   - `Binder.BindSlot`: in `connectSlot`, after `SlotClaimer.ClaimSlot` and before `resolveSandbox`. `ClaimSlot` (create) reaches the same `connectSlot` with a nil hook.
3. **Release after the claim.** A hook error, and a resolve, dial, or handshake failure after `claimPod` or `SlotClaimer.ClaimSlot`, releases the claim, with or without a hook. No compensation RPC is sent, because no entry-touching RPC has run.
   - `Claim` and `Bind`: `podclaim.DeleteClaim` on the claimed sandbox, with no credential release. Today `connect` returns a handshake failure with the claim in place, so the create-time `Claim` leaks the pod until the orphan-claim GC. This item closes that leak on create too. The create handler rolls back no failed `Claim`, because `claimAtCreate` returns no `ClaimResult`, so the release runs once.
   - `Resume`: `releaseResumeSlot(leaked=false)`. Change `releaseResumeSlot` so that an empty slot ID (an exclusive pool) deletes the claim with `podclaim.DeleteClaim` instead of returning nil. Rewrite its doc comment, and the `failResume` sentence "On an exclusive pool the slot identifier is empty and no accounting runs", to match. This also changes `failResume`: a failed adapter `Resume` on an exclusive pool now deletes the claim after the compensating Shutdown, where today the claim is left to the orphan-claim GC. On a slot pool, the release frees the reservation alone, and `SlotClaimer.ReleaseSlot` deletes the claim only at occupancy zero. Do not call `failResume` for these failures. Failures from the credential assignment onward follow CODE-4 item 20.4.
   - `BindSlot`: on a hook error, `connectSlot` releases the reservation with `ReleaseSlotReservation(leaked=false)` and returns the hook error, never inside a `*SlotBindError`. `applySlotRetryPolicy` therefore neither releases it a second time nor retries it. A handshake failure after the hook keeps its `*SlotBindError`, which `applySlotRetryPolicy` releases and retries on a fresh slot.
   - `Bind` after the hook, in `Prepare` and `Launch`. Add `PrepareResult.MintedLeaseIDs []string`, which `Prepare` fills with the lease IDs its `assignCredentials` call returns on success; today `Prepare` discards them on success (`bindprepare.go:167`). `Bind` sets a new unexported `BindRequest` field `attemptScoped`, and it threads `PrepareResult.MintedLeaseIDs` into the `Launch` request. On an attempt-scoped request:
     - the `Prepare` reconnect failure calls `podclaim.DeleteClaim` in place of `ReclaimClaimed`;
     - the `Launch` reconnect failure calls `releaseAttemptCredentials` on those IDs and then `podclaim.DeleteClaim`;
     - the `Launch` reclaim closure calls `reclaimOnFailure` with `leaseAssigned` false, and first calls `releaseAttemptCredentials` on those IDs when the cause is not a slot-bind refusal.

     `ReclaimClaimed` and `failPhase` with `leaseAssigned` true call `ReleaseSession`, which revokes a lease another attempt minted for the session. The decomposed `/finalize` and `/start` path never sets `attemptScoped` and keeps its session-wide release. Where `Bind` serves a session whose only leases are the attempt's, the two releases are equal.
4. Return the hook error as the hook returned it. It is never wrapped in a `*SlotBindError` and never matches an exhaustion sentinel. The existing loops stop on it unchanged: `runWithQueue` re-enters only on `isExhaustion`, and `applySlotRetryPolicy` retries only a `*SlotBindError`. No sentinel is added. The driver tells a hook failure from a later failure through its own hook closure (CODE-4 item 3.6).
5. Thread the hook from `resumeOnPod` (new parameter `onClaimed`) into `checkpointResumeRequest`, and through `startOnPod` into both `bindReq` and `slotReq`, so a snapshotless rebuild on a pool with `maxConcurrentSessions > 1` reaches it through `bindConcurrentSlot`.
6. The coordination-lease acquire is not part of the hook. CODE-4 acquires the lease once, before `resumeOnPod`.
7. **Retry accounting at the claim boundary** (SPEC-1b **Retry accounting.**).
   - A failure before the hook writes nothing and spends no retry (CODE-4 item 3.5).
   - A hook error reports no failure; CODE-4 item 3.6 states its outcomes.
   - After a hook that wrote `resuming`, every failure is reported once as CODE-4 item 3.7 states; SPEC-1b **Retry accounting.** states which reports spend a retry.
   - On a slot pool, the `applySlotRetryPolicy` retries of one attempt run inside that attempt and spend no `retryCount`. The per-attempt flag of CODE-4 item 3.4 makes the second hook call a no-op. Only the attempt's final error reaches the driver.

6. **`deliverBuffered(ctx, row) error`** implements SPEC-5i **Delivery of held messages.** It is called on the coordinating replica with the delivery lock held. Invariants:
   - **Order.** It delivers one entry at a time, the earliest `EnqueuedAt` across the inbox head and the DLQ head, and the inbox head on a tie. DLQ score order is acceptance order because every DLQ enqueue scores `EnqueuedAt + DefaultDLQTTL`: `messages_inbox.go` and `mcptools_register.go` pass a zero TTL, and `MigrateInboxToDLQ` keeps the original `EnqueuedAt` (SPEC-5z item 7). A later per-row TTL must preserve this order, or else `PeekOldest` and `DLQ.CountAcceptedAfter` (CODE-6 item 2) must order by `EnqueuedAt`.
   - **Removal.** For each entry: `executor.Send`, then `recordDeliveredResponse`, then removal. A removal that finds nothing is not an error. These three run on the server-lifetime context whatever the caller's `ctx`. The loop reads `ctx` only before taking the next entry, and it returns `ctx.Err()` with the untaken entries in place.
   - **Failure.** A `Send`, audit-record, or removal error stops the loop and returns the error, leaving that entry at the head. A `Peek` or `PeekOldest` error is logged at WARN, stops the loop, and returns nil. An entry whose `Payload` does not decode as `MessagePayload` is logged at ERROR with the session ID and message ID and removed, and the loop continues. That is the only removal of an undelivered entry. The loop expires nothing, calls no `SweepExpired`, and writes nothing to the inbox or the DLQ.

   - **Encoding.** The inbox and the DLQ hold one encoding, `sessionserver.MessagePayload`. The MCP buffering block in `mcptools_register.go` marshals `MessagePayload{ID: messageID, Role: "user", Content: <the buffered content>}` in place of the bare `in.Message`. The projection to `executor.Message` is the one `parseMessageBatch` applies, extracted as a helper both call. `From` is set from the entry's `SenderSessionID` through `senderFrom`, which moves from `mcptools.go` to the executor package (§15.4).

## Edge cases and accepted failure modes

- **Hung pre-claim wait.** A claim that waits on an exhausted pool is bounded by the remaining window, after which the attempt context is cancelled and `sweepResumePending` moves the row to `awaiting_client_action`.
- **Driver goroutine at shutdown.** The server-lifetime context cancels an in-flight attempt. A cancelled attempt before the hook writes nothing. One after the hook leaves a `resuming` row for `sweepResuming` and its claimed pod for the claim-orphan GC, or a `running` row whose commit landed unacknowledged, with its pod, for the peer's adoption (SPEC-1b **Exits from `resuming`.**).
- **A resolution the expiry does not catch.** SPEC-5p2 states the outcomes. In code, the misses are an `ExpireRaisedBy` error (logged at WARN), the watchdog's `sweepResuming` write, a release whose lock wait the context ends, and every terminal writer outside `ReportSessionFailure` (CODE-6 item 19).
- **Message held by a non-coordinator replica during a delivery.** The delivery lock does not reach it. SPEC-5i **Delivery of held messages.** states when the entry is delivered. A message to a `running` target follows the §29.3 `running` row (RECORDS-1 item 7(f)).
- **Idle-suspended session with a delegation tree.** Children keep running. The parent's suspension releases only its own pod or slot.
- **Seal refused, unavailable, or not lifted.** SPEC-5f **Idle suspension.** states the outcome of a refusal, and SPEC-5ab **Session seal.** states who lifts the seal and how a seal that is not lifted ends. An `unsealSession` error is logged with the session ID.
- **`busy` unattributed, and sessions that cannot be idle-suspended.** SPEC-5ab **Session seal.** and SPEC-5f state the outcomes; CODE-6 items 4, 5, and 18 implement them.
- **Takeover racing the entry write.** A Sweeper whose `List` read a row in `resume_pending` can acquire the lease after the driver's entry write. Its `RecordHandoff` compare-and-swap at the listed generation misses, it releases the lease, and the incarnation continues (CODE-5 item 2b).
- **Terminal transition on another replica.** The attempt learns of it at its next write, so restoration RPCs run until then, bounded by the attempt deadline.
- **Watchdog anchor.** `sweepResuming` measures from `UpdatedAt`, which every write in the incarnation advances, including the asynchronous `AdvanceLastSeq`. The watchdog therefore fires `MaxResumingSeconds` after the last write in the incarnation, while §6.2 states a watchdog set on entry. This predates the proposal and is accepted.
- **Lease mirror lag.** A barrier sent within one Sweeper interval of a resume commit carries a stale generation (RECORDS-1 item 7(g)).
- **Held message whose `resume_pending` write does not follow.** SPEC-5i **Backlog resume.** states the outcome (CODE-6 items 4 step 3a, 7, and 16).
- **Message during a §12.3 primary failover.** D5 **Message-path read failures.** states the outcome for an entry row that reads `running`, and CODE-7 item 4 the outcome for one that reads `suspended`.
- **Snapshotless rebuild with long setup.** The 300 s watchdog and `claimOrphanTimeout` bound the rebuild below the setup cap a runtime may declare (RECORDS-1 item 7(m)).
- **Pod release on a replica that lost the lease.** The release returns the attempt's minted leases and the session's leases at or below its binding's stamp (CODE-4 item 24), so a peer restore's leases survive. SPEC-1f item 3 states the outcome.
- **Renewal racing a release by identifier.** `ReleaseUncommitted` and `failResume` release an attempt's leases by identifier (CODE-4 items 5.3 and 20.4). When a lease's renewal passes its post-check before that release, the replacement stays held by the session and keeps renewing, because the release names only the spent identifier. The replacement records the attempt's generation `G` (CODE-4 item 24), so the session's next pod release returns it, because that binding's stamp is at or above `G`, and the release lists the session's leases twice (CODE-4 item 23.1). Until then it counts against its pool. The case is reachable only when `leaseTTLSeconds` minus `renewBeforeBufferSeconds` is shorter than one attempt, which `maxResumingSeconds` (default 300 s) bounds, and the provider defaults (3600 s and 300 s) exclude it.
- **Concurrent-pool counter after an ambiguous commit.** `slotcounter.Counter.Release` decrements unconditionally. A `ReleaseUncommitted` after a commit that landed unacknowledged, followed by a release of the committed binding, therefore decrements twice. This requires a commit `Update` that applied and then errored, plus a state change before the repeat (CODE-4 item 5.3). The counter under-counts by one until post-recovery rehydration recounts the pod's live sessions. This is accepted.
- **Erasure racing a live session.** A message enqueued for one of the user's sessions after CODE-6 item 17 deletes the session's keys and before step 17 deletes the row stays in Redis. §12.8 already applies the same in-flight-session posture to every session-scoped store.
- **Cap full while held messages wait.** A podless `suspended` session with held messages stays `suspended` while a limit it counts toward is full, and the gateway leader retries it on each pass; its messages wait until the check admits the resume or the session expires (CODE-7 item 5).
