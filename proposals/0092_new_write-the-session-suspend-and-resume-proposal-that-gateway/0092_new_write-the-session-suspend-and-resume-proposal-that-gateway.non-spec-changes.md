# Non-spec changes: Session suspend, idle suspension, and resume driver

## Design (implementation-facing)

This proposal lands after proposal 0091. CODE-4 deletes the `ErrHeld` hold in `holdOrFailOnResumeError` that 0091 CODE-2 adds, CODE-5 edits the `Sweep` loop that 0091 CODE-5 rewrites, and CODE-6 reads the turn token that 0091 CODE-1 adds. Each of those edits is located below by function and quoted text, and each assumes the 0091 version of the code.

The components and the work each one does:

- **Watchdog** (`pkg/gateway/runtime/watchdog`). It runs on every replica every tick and already lists every state. It gains optional hooks beside `RetryAttemptNotifier`, each implemented by the session server: `ResumeDriver` (CODE-4), and `SuspendedPodReleaser`, `IdleSuspender`, and `BacklogResumer` (CODE-6). It gains one new sweep, `sweepSuspended` (CODE-6), and it measures session age as active time (CODE-1). Its `sweepResuming` exit gains the incarnation guard (CODE-4 item 15), and `sweepDLQExpiry` also lists `resuming` rows (CODE-6 item 12).
- **Session server** (`pkg/gateway/sessionserver`). It implements the hooks. The resume driver, the suspension release, the idle suspension, the backlog resume, and the held-pod resume (`resumeHeldAndDrain`, CODE-4 item 8) each act only on a session whose `REG-COORDLEASE` names this replica, or on every session when no lease store is wired (dev mode). A lease read that fails is treated as "not the holder". This is the Design lease gate. When it refuses this replica, a hook does nothing, and each held-pod resume site takes the outcome it states for a refusal.
- **Binder** (`pkg/gateway/podlifecycle/podsession`). It gains a post-claim callback (CODE-3), which is the only seam through which the driver writes `resuming`.
- **Coordination Sweeper** (`pkg/gateway/coordination/coordination`). Its adoption predicate widens (CODE-5).

**Per-session delivery lock.** CODE-4 adds `deliveryLocks sessionLocks` to `Server`, a second instance of the per-session lock type in `slot_bind.go`, separate from `slotAccountLocks`. On one replica it orders every classification, hold, and send of a message against the delivery of held messages (CODE-4 item 6). The REST and MCP message paths take it, honoring the request context, before they re-read the session row, classify that fresh row, and hold it through `holdMessage` (CODE-4 item 7), or through `resumeHeldAndDrain` and the `executor.Send` of the message. `completeResume` and `resumeHeldAndDrain` (CODE-4 item 8) hold it from before their `running` write until `deliverBuffered` returns. The lock is in-process and orders nothing served by another replica. A message another replica holds is delivered at the coordinating replica's next delivery point (CODE-4 item 6), and the row guards of `resumeHeldPod`, `enterResumePending`, and `ReleaseSuspendedPod` step 3 order the state writes against each other. `SuspendIdle`, `ReleaseSuspendedPod`, and `enterResumePending` do not take it. The executor's admission write orders a send against the `running → suspended` write on every replica (CODE-6 item 5). The lock is not reentrant: never call `ResumeSuspended` or take `slotAccountLocks` while holding it. Cite `// spec: §7.2 (Message delivery routing — seven paths, path 6)`.

## Staged code changes

### CODE-1 · Active-time session age in the store funnel

Targets: `migrations/0182_sessions_accumulated_session_age.up.sql` and `.down.sql` (the next number after 0181); `pkg/gateway/session/sessionstore/sessionstore.go`; `pkg/gateway/session/sessionstore/pgstore/pgstore.go`; `pkg/gateway/session/sessionstore/memstore/memstore.go`; `pkg/gateway/runtime/watchdog/watchdog.go`; `pkg/gateway/sessionserver/resume_held_pod.go`.

1. **Migration.** `ALTER TABLE sessions ADD COLUMN accumulated_session_age_seconds double precision NOT NULL DEFAULT 0 CHECK (accumulated_session_age_seconds >= 0)`. The down migration drops the column.
2. **Field and helpers** in `sessionstore.go`: the field `AccumulatedSessionAgeSeconds float64` on `Session`, and two exported helpers.
   - `AccrueSessionAge(prev session.State, prevUpdatedAt time.Time, row *Session, now time.Time)`: when `prev` is `starting`, `running`, or `input_required`, it adds `max(0, now - prevUpdatedAt)` in seconds to `row.AccumulatedSessionAgeSeconds`.
   - `ActiveAge(row Session, now time.Time) time.Duration`: the accumulated value, plus `now - row.UpdatedAt` when `row.State` is one of those counting states.
3. **The funnel.** In both stores' `Update`, after the mutator returns and before the `UpdatedAt` stamp, call `AccrueSessionAge(prev.State, prev.UpdatedAt, &row, now)` with the same `now` the stamp uses. Add the column to `Create`, to the `UPDATE` statement, to the select list, and to the scan in `pgstore.go`. `Store.Update` is the only writer of the sessions row; grep for any other `UPDATE sessions` statement and route it through the helper. A write that does not change the state still accrues, because the row stays in the counting state across it.
4. **Sweeps.** `sweepMaxAge` and `sweepExpiryWarning` compare `sessionstore.ActiveAge(row, now)` with `effectiveAgeCap` in place of `now.Sub(row.CreatedAt)`. Rewrite the doc comments of `sweepMaxAge`, `sweepExpiryWarning`, and the `resume_pending` and idle-clock comments that describe age as wall-clock time from `CreatedAt`. Cite `// spec: §6.2 (maxSessionAge timer behavior across states)`.
5. **Evaluation on entry to `running`.** The §6.2 paragraph after the pause table evaluates the timer on every transition into `running`. A paused session cannot gain age, so the only over-cap row that can reach `running` is one that left a counting state over the cap before a sweep saw it. Two checks cover it:
   - `sweepResumePending` does not call the CODE-4 driver for a row whose `ActiveAge` exceeds `effectiveAgeCap`. `sweepMaxAge` expires that row on the same or the next tick, because it applies to every non-terminal state.
   - `resumeHeldPod` refuses, with an error the message path already treats as a failed resume, a row whose `ActiveAge` exceeds the effective cap.
   **IMPLEMENTOR'S CHOICE:** how `resumeHeldPod` obtains the effective cap. The constraint is that it returns the value `effectiveAgeCap` returns for the same row, from one shared resolver rather than a second copy of the min-wins logic.

### CODE-3 · Binder post-claim callback

Targets: `pkg/gateway/podlifecycle/podsession/resume.go`, `bindrequest.go`, `binder.go`, and the slot-bind request and `Binder.BindSlot`; `pkg/gateway/sessionserver/pod_launch.go`, `slot_bind.go`, `resume_rebind.go`, and `checkpointResumeRequest`.

1. Add `OnClaimed func(context.Context) error` to `podsession.ResumeRequest`, `BindRequest`, and `SlotBindRequest`. A nil hook is a no-op, which covers create and start.
2. Invoke the hook after the claim, and after the slot reservation where there is one, and before the first entry-touching RPC on each path:
   - `Binder.Resume`: after `reserveResumeSlot`, before `cl.Resume`.
   - `Binder.Bind`: after the claim, before `Prepare`.
   - `Binder.BindSlot`: after `connectSlot`, before `materializeSlot`.
3. Release on a hook error, per path. No path issues a compensation RPC, because no entry-touching RPC has run.
   - `Bind`: `ReclaimClaimed(SandboxName, SessionID)`. No lease has been assigned yet.
   - `Resume`: `cl.Close`, `releaseResumeSlot(leaked=false)`, and `podclaim.DeleteClaim` on the claimed sandbox. Do not call `failResume`. `ReclaimClaimed` does not fit here, because its session-wide credential revoke has the wrong scope on a resume.
   - `BindSlot`: `cl.Close` and `ReleaseSlotReservation(leaked=false)`.
4. Return the hook error wrapped in the new sentinel `podsession.ErrOnClaimed`. `applySlotRetryPolicy` and `runWithQueue` treat an error that `errors.Is(err, podsession.ErrOnClaimed)` as non-retryable and stop.
5. Thread the hook from `resumeOnPod` (new parameter `onClaimed`) into `checkpointResumeRequest`, and through `startOnPod` into both `bindReq` and `slotReq`, so a snapshotless rebuild on a pool with `maxConcurrentSessions > 1` reaches it through `bindConcurrentSlot`.
6. The coordination-lease acquire is not part of the hook. CODE-4 acquires the lease once, before `resumeOnPod`.

### CODE-4 · Resume driver, store-only `POST /resume`, buffered delivery, tree-recovery routing

Targets: `pkg/gateway/runtime/watchdog/watchdog.go`; new `pkg/gateway/sessionserver/resume_driver.go`; `pkg/gateway/sessionserver/resume.go`, `resume_rebind.go`, `failure.go`, `stream_failure.go`, `podclaimerror.go`, `treerecovery.go`, `messages_delivery.go`, `messages_inbox.go`, `messaging.go`, `derive.go`, and `sessionserver.go`; `pkg/gateway/externalapi/errorclassify/errorclassify.go`; `pkg/api/v1/session/session.go`; `pkg/gateway/session/sessioninbox/coordinator.go`, `dlq.go`, and `sessioninbox.go`; `cmd/lenny-gateway/flags.go` and the wiring in `cmd/lenny-gateway`; `sdks/client/go/lenny/client.go`.

1. **Watchdog hook.** Add `ResumeDriver` beside `RetryAttemptNotifier`, with one method `DriveResume(ctx context.Context, row sessionstore.Session)`. In `sweepResumePending`, for a row still inside its window, call it when the wired `TerminalHook` implements `ResumeDriver`, subject to the CODE-1 item 5 age check. The expiry branch is unchanged.
2. **`DriveResume`** returns at once, writing nothing, when any of these holds: a lease store is wired and `leaseStore.Get` does not name this replica, or it returns an error; the session ID is in the per-replica in-flight set; or the session's next-attempt time is in the future. Otherwise it adds the session to the in-flight set and starts `attemptResume` on a goroutine whose context derives from the server-lifetime context, which `Server` cancels on shutdown. The goroutine removes the in-flight entry on exit. Cite `// spec: §7.3 (Resume driver)`.
3. **`attemptResume`**, in this order:
   1. Re-read the row and return unless it is `resume_pending`.
   2. Arm the attempt deadline with `time.AfterFunc` for the time left in the window (`UpdatedAt + maxResumeWindowSeconds - now`, resolved as `sweepResumePending` resolves it), cancelling the attempt context when it fires.
   3. Call `acquireCoordinationLease` once. `ErrHeld` or any other error ends the attempt with no write. The acquires inside `registerBinding` and in the checkpoint branch of `resumeOnPod` stay as idempotent self-renews.
   4. Call `resumeOnPod(ctx, row, onClaimed)`. The `onClaimed` hook is one store `Update` whose mutator returns `errResumeSuperseded` unless `r.State == resume_pending` and `r.CoordinationGeneration` equals the value item 3.1 read, and otherwise sets `State = resuming` and increments `CoordinationGeneration`. The attempt keeps the returned row's `CoordinationGeneration` as its incarnation generation `G`. A per-attempt flag makes a second invocation in the same attempt a no-op that returns nil, so a slot retry after a post-hook failure does not misfire. When the write succeeds, the hook resets the attempt deadline to `MaxResumingSeconds` from now. The deadline bounds how long the attempt holds its pod. Correctness does not depend on the attempt ending before `sweepResuming` acts, because every exit is conditioned on `G`. Cite `// spec: §7.3 (Resume driver)`.
   5. When the hook never ran, the failure is a pre-claim failure. Record the next-attempt time as `now + backoff + jitter`, where the jitter is uniform in `[0, backoff/2)`, and write nothing.
   6. When the hook returned `errResumeSuperseded`, stop. The binder has already released the claim.
   7. When the hook ran and a later step failed, report through `ReportSessionFailure`, which routes a `resuming` row to `applyFailureFromResuming`. The report carries `G` in a new field `FailureReport.ExpectedCoordinationGeneration`. When the report's source row is `resuming`, the store `Update` in `transitionToResumePending` and `transitionToAwaitingClientAction` also requires `r.CoordinationGeneration == rep.ExpectedCoordinationGeneration` and otherwise takes the existing `errReportConflict` no-op, so a report on an ended incarnation writes nothing and spends no retry. A report that leaves the field zero never matches, because every row's generation is at least 1. The only other reporter, the `CH-ATTACH` stream-failure path, already drops a report on a `resuming` row in `reportSupersededByPeer`, because every binding it can report on predates the entry increment. Delete the `bumpCoordinationGenerationOnSnapshotClose` call in `applyFailureFromResuming` (the `disp.From == session.StateResuming && disp.To != session.StateResuming` branch) and the F-7.1.14 paragraph of its doc comment. The next entry into `resuming` advances the generation, no published binding carries `G`, and the spec requires the bump only on a mid-resume terminal collapse, which `session_transitions.go` keeps. A setup-command failure that arrives as `FailedPrecondition` is reported as `setup_command_failed`, and every other post-claim error as `runtime_crash`. Increment `lenny_session_resume_attempts_total{outcome="failure"}`.
   8. On success, call `completeResume`.
4. **`resumeOnPod` publishes nothing.** Both branches return the `BindResult` and the adapter-reported mode without calling `registerBinding`, `podRegistry.Put`, `bumpRecoveryGeneration`, or `fenceResumedPod`. `completeResume` performs those steps after the commit. This keeps a lost commit from leaving a published binding or a `PodAssignment` behind.
5. **`completeResume`**, in this order:
   1. Take the per-session delivery lock.
   2. One store `Update` guarded on `State == resuming` and `CoordinationGeneration == G`: write `running` through `transitionResume`, increment `RecoveryGeneration`, set `PodAssignment` to the result's sandbox, and stamp `LastAgentActivityAt = now` (CODE-6 item 8). Both branches bump `recovery_generation`; the snapshotless branch did not before.
   3. When the guard fails, release the pod through the binder's post-RPC failure release, which runs the §7.1 pod-side reclaim and deletes the claim, then publish nothing, write nothing, release the lock, and stop. The attempt is the only gateway component that releases this pod. The WarmPoolController's orphan-claim GC reclaims it only when no session references it and its claim's binding-state transition is older than `claimOrphanTimeout` (SPEC-1b **Exits from `resuming`.**). A mid-resume terminal transition written on any replica does not release it, because the pod is unpublished and the attempt holds its connection and claim. **IMPLEMENTOR'S CHOICE:** whether the binder exports `failResume` or wraps it as a new `Binder` method. The constraint is that the release runs the pod-side reclaim on the connection the attempt holds before the claim is deleted.
   4. Stamp the `BindResult` with `G` through `stampBindingGeneration`, then publish the binding: `registerBinding` for the rebuild branch, `podRegistry.Put` for the checkpoint branch. Then call `fenceResumedPod`, which announces the row's current generation to the pod. Remove the stamps `resumeOnPod` applies today in `resume_rebind.go` (both branches), which use the row item 3.1 read and so carry the pre-entry generation. A binding stamped below `G` makes `reportSupersededByPeer` drop every later stream failure of the resumed session as superseded.
   5. Run the tail that `handleResume` runs today after its commit, moved here unchanged: the success counter, the `session.resumed` audit row, `emitStatusChange`, the partial-manifest cleanup, `classifyResumeWithAdapter`, `emitResumedEvent`, `emitChildrenReattached`, and `recoverDelegationTree`. Delete `clearInboxOnResume` from `messaging.go`. No resume clears an inbox: a podless resume migrated the inbox at `resume_pending`, and a held-pod resume runs on the replica that holds the inbox. §7.2 places `inbox_cleared` at lease takeover, which RECORDS-1 item 7(h) files. Keep `Coordinator.ClearInboxOnAcquire`.
   6. Call `deliverBuffered`, then release the lock.
6. **`deliverBuffered(ctx, row) error`**, called on the coordinating replica with the delivery lock held, implements §7.2 delivery path 6 **Delivery of held messages.**
   - Loop: read the inbox head with a new `Inbox.Peek` (`LINDEX 0` in `RedisInbox`, the slice head in `MemoryInbox`) and the DLQ head with a new `DLQ.PeekOldest(ctx, tenantID, sessionID)` (`ZRANGE key 0 0`, returning the decoded message and the raw member). Stop when both are empty.
   - Take the head with the earlier `EnqueuedAt`, and the inbox head on a tie. Send it with `executor.Send` and record it through the transcript and event-stream half of `recordDeliveredResponse`, split from the half that writes the HTTP response.
   - Then remove it, with a new `Inbox.Ack` (`LREM key 1 <member>` in `RedisInbox`, by `MessageID` in `MemoryInbox`) or a new `DLQ.Remove(ctx, tenantID, sessionID, member)` (`ZREM`). A removal that finds nothing is not an error, because another delivery already removed the entry.
   - A `Peek`, `Send`, or removal error stops the loop and returns the error, leaving every entry in place. The loop expires nothing, calls no `SweepExpired`, and never writes to the inbox or the DLQ.
   - DLQ score order is enqueue order, because every DLQ enqueue scores `EnqueuedAt + DefaultDLQTTL`: `messages_inbox.go` and `mcptools_register.go` pass a zero TTL, and `MigrateInboxToDLQ` keeps the original `EnqueuedAt`, as SPEC-5z item 7 states. A later per-row TTL, such as the pre-running row's `maxCreatedStateTimeoutSeconds`, must preserve this order or make `PeekOldest` and `DLQ.CountAcceptedAfter` (CODE-6 item 2.2) order by `EnqueuedAt`.
   - Callers: `completeResume` (item 5.6), `resumeHeldAndDrain` (item 8), and the REST and MCP message paths before every `executor.Send` of a new message on the `ActionDeliver` branch, which is §7.2 delivery path 2 (CODE-6 item 7). `resumeHeldAndDrain` returns the error as `errHeldDeliveryFailed` (item 8).
   - The §7.2 path-3 and path-5 return to `ready_for_input` is a further delivery point for inbox entries. The tree has no handler for the adapter's `ready_for_input` report (`messages_delivery.go` and `resume_held_pod.go` defer that signal), so this item adds no call site for it. The code that acts on the report for a `running` session calls `deliverBuffered` before any other delivery.
   - **IMPLEMENTOR'S CHOICE:** how a PostAgentOutput REJECT on a delivered held message is surfaced on the event stream. The constraint is that it writes no HTTP response and the entry is removed.
   - Cite `// spec: §7.2 (Message delivery routing — seven paths, path 6)`.
7. **`holdMessage(ctx, tenantID, sessionID string, msgs []sessioninbox.Message, ttl time.Duration)`** on `Server` is the one DLQ enqueue site of both message paths: `bufferIncomingMessages` calls it for `bufferTargetDLQ`, and the MCP path calls it through `SessionDelivery.HoldMessage` (CODE-6 item 7). It calls `EnqueueDLQ` for each message, then re-reads the row with `store.Get`.
   - When the re-read fails or returns a terminal row, it removes each member it enqueued with `DLQ.Remove` (item 6).
   - On a terminal row, it returns `terminal` when any removal found its member, and `queued` otherwise. The caller answers `terminal` with `TARGET_TERMINAL`, as `writeTargetTerminal` does.
   - On a re-read error, it returns the error, which the caller answers as an enqueue failure (`error`, `inbox_unavailable`).
   - On any other row, it returns `queued`, or `dropped` on eviction, and leaves the entries to §7.2 delivery path 6 **Delivery of held messages.**
   Cite `// spec: §7.2 (Message delivery routing — seven paths, path 6)`.
8. **Store-only `POST /resume`.** `EndpointResume` admits `StateAwaitingClientAction` and `StateSuspended`. `handleResume` becomes:
   - from `awaiting_client_action`, or from `suspended` with an empty `PodAssignment`: call `enterResumePending`, then answer `200` with the updated row;
   - from `suspended` with a non-empty `PodAssignment`, when the Design lease gate admits this replica: take the delivery lock, call `resumeHeldAndDrain`, and answer `200` with the row in `running`. `resumeHeldAndDrain(ctx, tenantID, id) error` is new in this item. Called with the delivery lock held, it calls `resumeHeldPod` and, on success, `deliverBuffered` (item 6). A `deliverBuffered` error comes after the `running` write, so `resumeHeldAndDrain` returns it wrapped in a new sentinel `errHeldDeliveryFailed`, which a caller tells apart from a `resumeHeldPod` error that leaves the row `suspended`. `handleResume` answers `200` with the row in `running` on `errHeldDeliveryFailed`, and `ResumeSuspended` (CODE-6 item 7) returns nil on it, because the failed entry stays at the head of its queue for the next delivery point (§7.2 delivery path 6 **Delivery of held messages.**). CODE-6 items 6 and 7 add its other callers and make it the only caller of `resumeHeldPod`.
   - from `suspended` with a non-empty `PodAssignment`, when the Design lease gate refuses this replica: write nothing and fail closed with `TARGET_NOT_READY`, HTTP 409, which is the §29.3 outcome for the held-pod `/resume` row with an unreachable coordinator, because no inter-replica carrier for the forward exists. `upload_to_session.go` already fails closed this way for a session it holds no binding for. Running `deliverBuffered` here would fail every `Send` in `streamFor` (`executor/pod.go`, "session %s is not bound to a pod"), and leave every held message in the DLQ of a `running` session.
   Delete the pre-claim `resuming` write, the `resumeOnPod` call, `holdOrFailOnResumeError` (including the 0091 `ErrHeld` hold and the `failSession` exit), and the `RESUME_FAILED` write. `incSessionResumeAttempt` moves to the driver.
9. **`enterResumePending`** in `failure.go`: a store `Update` guarded on the expected source state (and, for `suspended`, on an empty `PodAssignment`) that writes `resume_pending` without touching `RetryCount`, followed by `migrateInboxOnResumePending` and `emitStatusChange`. The guard failing returns the precondition error `handleResume` already writes. `POST /resume`, the CODE-6 message paths, and `ResumeSuspended` (CODE-6 item 7) call it.
10. **`RESUME_FAILED` removal.** Delete the code from `podclaimerror.go` and `errorclassify.go`. `openapi.json` does not name it.
11. **`ReattachNode`** in `treerecovery.go`: a node in `resume_pending` goes through `DriveResume`, which applies the in-flight set and the lease gate, and a node in `resuming` is skipped. A node in any other non-terminal state is left as it is, and `ReattachNode` returns nil. `ReattachNode` no longer calls `resumeOnPod` for any node, because after item 4 `resumeOnPod` publishes nothing and only `completeResume` publishes the binding, so a claim made outside the driver would leave a pod claimed with no published binding and a stale `PodAssignment`. A `running`, `input_required`, or held-pod `suspended` node whose coordinator died is re-adopted and re-fenced by the CODE-5 Sweeper, a node whose pod failed reaches `resume_pending` through its failure edge, and a podless `suspended` node is restored by its next message or resume (SPEC-5i). The `resumeOnPod` call and the unguarded `running` write are deleted. Rewrite the `sessionNodeReattacher` doc comment to state this routing.

13. **SDK.** Rewrite the `Resume` doc comment in `sdks/client/go/lenny/client.go`: the call returns the session in its new state, and the restore's outcome arrives on the event stream.

Otherwise the mutator returns a new package sentinel `errResumingSuperseded`. ## Edge cases and accepted failure modes

- **Hung pre-claim wait.** A claim that waits on an exhausted pool is bounded by the remaining window, after which the attempt context is cancelled and `sweepResumePending` moves the row to `awaiting_client_action`.
- **Driver goroutine at shutdown.** The server-lifetime context cancels an in-flight attempt. A cancelled attempt before the hook writes nothing. One after the hook leaves a `resuming` row for `sweepResuming` and the peer's adoption, and its claimed pod for the claim-orphan GC, which drains it once the claim's binding-state transition is older than `claimOrphanTimeout` (SPEC-1b **Exits from `resuming`.**).
- **Message held by a non-coordinator replica during a delivery.** The delivery lock does not reach it. An entry enqueued after the coordinating replica's last `deliverBuffered` stays in the DLQ of the `running` session. It is delivered before the next path-2 message the coordinating replica delivers, or after the idle suspension through the backlog resume. A message to a `running` target follows the §29.3 `running` row (RECORDS-1 item 7(f)).
- **Idle-suspended session with a delegation tree.** Children keep running. The parent's suspension releases only its own pod or slot.
- **Takeover racing the entry write.** A Sweeper whose `List` read a row in `resume_pending` can acquire the lease after the driver's entry write. Its `RecordHandoff` compare-and-swap at the listed generation misses, it releases the lease, and the incarnation continues (CODE-5 item 2b).
- **Terminal transition on another replica.** The attempt learns of it at its next write, so restoration RPCs run until then, bounded by the attempt deadline.
- **Watchdog anchor.** `sweepResuming` measures from `UpdatedAt`, which every write in the incarnation advances, including the asynchronous `AdvanceLastSeq`. The watchdog therefore fires `MaxResumingSeconds` after the last write in the incarnation, while §6.2 states a watchdog set on entry. This predates the proposal and is accepted.
- **Lease mirror lag.** After the entry increment, the `coordination_lease` mirror carries the pre-entry generation until the holder's next Sweeper renew, which is at most one Sweeper interval later. A preStop `CheckpointBarrier` sent in that interval carries the mirror's generation, so the replacement pod rejects it as generation-stale. The session is not quiesced, and no drain checkpoint is captured for it. The next coordinator re-adopts its pod without a restore. RECORDS-1 finding (h) records it.
