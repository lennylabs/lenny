DECISION: Returned no findings for the staged spec edits under the reliability lens — BECAUSE every recovery path traced (driver crash before and after the claim, watchdog-vs-attempt race on one replica, podless adoption without a fence, suspension release crash, budget-key re-arm) either serializes on the session row or falls to an existing reclaimer (§4.6.1 claim GC predicate 1, §6.2 `resuming` watchdog) — ALTERNATIVES: filing the narrow windows below as spec findings (their remedies are code, or they repeat refuted materiality cases).
FACT: A replacement pod is not named in `pod_assignment` during `resuming` in the current tree either: `bumpRecoveryGeneration` (the PodAssignment write) runs after `binder.Resume` returns. So CODE-4 moving it to the commit adds no new claim-GC exposure. EVIDENCE: pkg/gateway/sessionserver/resume_rebind.go:129; spec/04_system-components.md:517.
FACT: Same-replica attempt overlap is safe at row level. A watchdog `resuming → resume_pending` does not bump `coordination_generation`, but the `running` commit guard on `State == resuming` serializes a stale attempt against a fresh one, and the loser releases its pod. EVIDENCE: spec-changes.md SPEC-1b preamble; non-spec-changes.md CODE-4 item 5.2.
FACT: `resume_pending` rows keep the failed pod in `PodAssignment` by design (the failure reporters stamp it), so "no bound pod" in SPEC-2b has to be read as "binding released" per §28.5.1 CH-ATTACH, not as an empty column. EVIDENCE: pkg/gateway/sessionserver/failure.go:337-338; spec/28_communication-channels.md:261.
UNVERIFIED: The CODE-6 `SuspendIdle` turn check and guarded write do not take the per-session delivery lock. A message classified `running` just before the write can start a turn on a pod that the next tick checkpoints and releases. The tier-7a test claims it never loses the message, but no mechanism is staged. The non-spec loop should check whether message delivery stamps `LastAgentActivityAt` before it sends. EVIDENCE: non-spec-changes.md CODE-6 item 5; pkg/gateway/session/sessionidle/sessionidle.go:234.
UNVERIFIED: The podless message branch writes `resume_pending` and then enqueues to the DLQ (CODE-6 item 7). A driver that restores and drains before the enqueue strands the message in the DLQ of a `running` session. The window is tiny, so the non-spec loop should decide whether to enqueue first.
UNVERIFIED: The CODE-4 lease gate treats a lease read error as "not holder". During a Redis outage this stops every resume driver, while spec/12_storage-architecture.md:217 says leases fall back to Postgres. The non-spec loop owns this.
