# Summary: Session resume driver, recovering-state coordination lease, active-time session age, and idle suspension

## Summary

**Problem statement.** After proposal 0091 lands, every pod or `Attach` stream failure leaves a session in `resume_pending`, and nothing moves it on to `running`: the restore code exists, but no component triggers it, and a client's `POST /v1/sessions/{id}/resume` served by a replica other than the lease holder fails. A coordinator that dies in a recovering or held-pod suspended state leaves the session without an owner. Two retry budgets exist, and one recovered crash spends two units of the one that is read. Session age runs on wall-clock time where the spec requires active time. A suspended session never releases its pod, the idle flag is misnamed and misdocumented, and `lenny/resume_session` cannot resume a suspended session. The owner decided that an idle session is suspended and its pod released at once, that any message resumes a suspended session, and that a suspended session lives at most 7 days.

**What changes.**
- Session server and watchdog: a resume driver that is the only writer of `resume_pending → resuming`, an increment of `coordination_generation` on that write with every exit from `resuming` conditioned on the new value, a store-only `POST /resume` that also admits `suspended`, delivery of held messages, oldest first and before each path-2 delivery, by the coordinating replica after a restore and after a pre-running session's entry to `running`, and by the adopting replica after a takeover of a `running` session whose committing replica did not deliver, a commit classification that decides from the commit's error history and the locked row which replica owns the attempt's pod, a terminal transition in which every terminal write records the Terminated fact in the write itself and the writing replica runs one post-terminal hook that cancels a running resume attempt, seals the workspace, and releases the pod, the deletion of `RESUME_FAILED`, and a guarded `POST /start` commit (CODE-4, SPEC-1, SPEC-3).
- Binder: a post-claim callback, so `resuming` is written after the claim and before the first RPC to the pod (CODE-3), a release of the claim on every failure between the claim and the first entry-touching step, run on a context detached from the attempt's cancellation, with `Bind` releasing only the leases its attempt minted (CODE-3), credential assignment on the checkpoint resume, so a restored session holds new leases before its runtime starts, `ReleaseUncommitted`, which releases a lost commit's pod, slot, and only the credential leases that attempt minted, and, after a commit try that returned a store error, releases them only on a `RECLAIMED` reclaim reply (CODE-4 item 5.3), and a pod release that returns only its attempt's credential leases and the session's leases at or below its binding's generation stamp, a renewal loop that stops renewing a lease released on purpose without starting the Fallback Flow (CODE-4 items 20, 23, and 24, SPEC-1g, SPEC-1g3), and a crash mark on the binding that retires, at its release, a crashed pod that serves one session when the gateway classified the stream failure before the release (CODE-4 item 22a, SPEC-5b step 2).
- Coordination Sweeper: adoption of the states SPEC-2a lists, with the fence only when a pod is held, a peer-takeover check against the binding's own generation stamp, and a `RecordHandoff` compare-and-swap on the listed generation, and no renewal or adoption of a podless `suspended` session, whose mirror row it releases, a hook through which the session server delivers held messages after a takeover publish, and a hook that releases a binding this replica holds on a terminal row (CODE-5, CODE-4 items 26 and 27, SPEC-2, SPEC-5i).
- Retry accounting: `retryCount` is spent once per failure edge, `sessionPolicy.maxSessionRetries` is deleted, and the session `ValidTransitions` table gains the §7.2 edges it omits (CODE-2, SPEC-1).
- Session store and watchdog: active-time session age in `accumulated_session_age_seconds` (CODE-1, SPEC-4).
- Watchdog and session server: idle suspension, which requires both the gateway's idle clock and the adapter's activity window to find the session idle, the idle expiry kept for a session that cannot be idle-suspended, the suspension release, the 7-day suspended-session lifetime, resume on any message with every message to a `suspended` session that is not delivered synchronously held in its DLQ and resumed, as SPEC-5i §7.2 delivery path 6 states, the runtime adapter's session seal, which the adapter places only when the session had no activity for the idle window, the adapter activity that the CODE-6 item 18.1 inventory lists, including a runtime's `busy: true` on `heartbeat_ack` and each `CH-MCP-PLATFORM` or `CH-MCP-CONNECTOR` call in flight, with the adapter heartbeating each session from its `session_start` (SPEC-5ab, SPEC-5ac), a per-chunk stamp of the idle clock for a proxy-mode LLM stream (CODE-6 item 18.1, row G4), the renamed and corrected flags, a gateway-leader backlog re-check of podless `suspended` sessions, and a §12.8 erasure step for the session DLQ and durable inbox (CODE-6, SPEC-5).
- Session store and session server: the concurrent-session counts exclude `suspended` sessions, and every resume of a `suspended` session passes the creation-time cap check first, so a message or resume call at a full cap is refused with `429 QUOTA_EXCEEDED`, and the §16.5 session-availability SLI counts the same sessions (CODE-7, SPEC-6).
- Retry accounting on a restore: a lease assignment that the credential service refuses for a reason that recurs on every attempt is the non-retryable failure reason `credential_rejected` (CODE-4, SPEC-1).
- Interaction store and session server: a session's pending `lenny/request_elicitation` elicitations expire when it leaves its pod, including through a terminal transition (CODE-6 item 19, SPEC-5p2).
- Credential leases: one rule names the components that return a session's leases, and a lease that no releaser returns is returned at its expiry, an accepted departure recorded in Edge cases (non-spec Design D6 **Credential lease return.**, SPEC-1g, SPEC-1g3).
- Tests: the expansive lifecycle intents X1 to X5 run on a new test-only harness and invariant checker (non-spec Testing **Expansive lifecycle tests**), and one triage rule decides whether a step fixes or files each test failure it exposes (non-spec Testing **Failures the tests find.**).

**Decisions.**
1. The resume driver is the only code that writes `resume_pending → resuming`. It hooks `sweepResumePending` and runs on the lease holder, or on every replica in dev mode. Every route into recovery is a guarded store write into `resume_pending`, which reuses the §7.2 `awaiting_client_action → resume_pending` edge and the §29.6 step 3 write and needs no inter-replica forward.
2. `resuming` is written after the claim, through the binder's post-claim callback. A pre-claim failure writes nothing, so the `UpdatedAt`-anchored `maxResumeWindowSeconds` window keeps its meaning and the driver adds no state edge or field.
3. A post-claim failure goes through `ReportSessionFailure` and `applyFailureFromResuming`, which already implement the §6.2 `resuming` exits and never write `failed`. `holdOrFailOnResumeError` is deleted, which closes F-15.1.41 here.
4. `POST /v1/sessions/{id}/resume` admits `awaiting_client_action` and `suspended`. From `awaiting_client_action` and podless `suspended`, the call is a store write any replica serves. Held-pod `suspended` is resumed, and its held messages delivered, by the coordinating replica through `resumeHeldAndDrain`, the one implementation of the held-pod resume edge, and a call served by any other replica writes nothing and fails closed with `TARGET_NOT_READY` (CODE-4 item 8). `RESUME_FAILED` has no producer left and is deleted.
5. A lapsed lease is adopted for the states SPEC-2a lists, with the fence only when a pod is held. A session past `ready` holds the lease only while it has a bound pod or pending driver work, and in `awaiting_client_action`, where 0091's retention stands. A podless `suspended` session holds no lease and has no coordinator: the Sweeper neither renews nor adopts it and releases its `coordination_lease` mirror row, and the replica a request lands on serves every §29.3 route it admits (SPEC-2a, SPEC-2d, CODE-5 item 1). `resuming` is left to its watchdog, and a stale driver's attempt stops when its write finds its `resuming` incarnation ended (SPEC-1b **Exits from `resuming`.**).
6. `retryPolicy.maxRetries` is spent only on a failure edge into `resume_pending`, and `sessionPolicy.maxSessionRetries` is deleted. `sessionPolicy.maxSessionRetries` has no reader, and the second increment in `bumpRecoveryGeneration` would turn the default budget of 2 into one automatic recovery.
7. Active age uses the single column the spec names, accrued in `Store.Update` from the strictly advancing `UpdatedAt`. The §6.2 evaluation on entry to `running` stays normative. `sweepMaxAge` expires no `suspended` row (SPEC-5g) and re-checks the age on the locked row. Non-spec CODE-1 item 5 states the entry rule for an over-cap row, and Edge cases **Over-cap row entering `running`.** records its departure. The `resume_pending` and `awaiting_client_action` cases of F-6.2.28 stay with P3.
8. The suspension release reuses the §6.2 graceful release in the order checkpoint, clear binding, release, with the pool's normal session-end disposition and only the slot on a concurrent pod. Clearing the binding first means a crash leaves an orphan claim, never a row naming a released pod. The release returns the credential leases its own attempt minted and every lease of the session whose recorded `coordination_generation` is at or below the binding's stamp. A peer's restore records a higher generation, so a release on a replica that lost the lease never revokes the peer's leases. Every restore assigns new leases on the replacement pod before `Resume` (SPEC-1g, CODE-4 items 20 and 24).
9. `maxSuspendedPodHoldSeconds` governs interrupt suspensions only. An idle suspension, recorded with the suspension reason `Idle`, has a hold of zero: its `running → suspended` write also clears the pod from the row, and the same sequence releases the pod, so no `Idle` row names a pod.
10. Idle means a `running` session with no activity in either direction for `maxClientIdleSeconds` (default 900 s), where a runtime reporting busy counts as activity, as the owner decided on 2026-10-10. A runtime reports `busy: true` while it does any work for the session, as SPEC-5ac states (CODE-6 item 18.4). Activity is a SPEC-5e qualifying event on the gateway and is as SPEC-5ab **Session seal.** defines it on the adapter. A session is idle only when both find no activity in the window (Decision 16). The clock is not evaluated in `input_required`, where the runtime waits on the client, and is paused in `awaiting_client_action`.
11. Any message to a `suspended` session resumes it, and SPEC-5i §7.2 delivery path 6 states the custody rule. The DLQ sweep does not expire a `suspended` session's held messages. SPEC-5i **Held messages.** and **Backlog resume.** state what resumes a session whose message is held, and the terminal drain removes what remains (SPEC-5z).
12. A suspended session expires `gateway.maxSuspendedSessionSeconds` (default 604800 s) after its entry to `suspended`, reusing the `max_idle_time` expiry reason. The budget-key TTL default rises to 691200 s, must exceed that lifetime, and is re-armed on the transitions SPEC-5o names.
13. `ReattachNode` routes a `resume_pending` descendant through the driver and claims no pod itself for any node, so tree recovery and the driver cannot claim two pods for one session and no pod is claimed without a published binding. Tree recovery selects a node only by its row state `resume_pending`, never by its absence from the local pod registry, so a traversal that any node's commit starts drives or fails no node held on a peer. `ReattachNode` returns the driver's outcome for the node.
14. §7.3 step 3e states the snapshotless rebuild, `--max-idle-time-seconds` is renamed `--max-client-idle-seconds`, and the hold flag's help is corrected.
15. Each `resume_pending → resuming` write increments `coordination_generation`, so the state `resuming` and that value name one incarnation of the restore. The driver's commit, its failure report, and the `resuming` watchdog each take effect only on the incarnation they act on, and the attempt that claimed the replacement pod is the only gateway component that releases it. When the attempt stops without releasing it, the §4.6.1 orphan-claim GC drains it after `claimOrphanTimeout`. The post-exit generation bump in `applyFailureFromResuming` is deleted. SPEC-1b **Exits from `resuming`.** states the rule, and SPEC-1f states the increment in §10.1.1, how a replica that lost a podless session stops in §10.1.5, and the derive-failure fence wording in §7.1 and §16.1.
16. Idle suspension requires idleness on both the gateway's `maxClientIdleSeconds` clock and the runtime adapter's activity window, because the adapter observes the traffic that the adapter rows of the CODE-6 item 18.1 inventory list, which include `busy` reports and platform and connector calls in flight that no gateway stamp records, and every replica's delivery passes through it. The conjunction applies the owner's rule "lack of any activity, period" (Decision 30). A restore starts the adapter's window fresh, so nothing crosses a checkpoint. The adapter heartbeats each session from the write of its `session_start` until it writes the session's `session_end` or removes its registry entry, whether or not the gateway holds an `Attach` stream for it, so a session after a takeover, a restore, or a start with no message reports `busy` as any other does (OD-S8, decided 2026-10-10 and confirmed 2026-10-11 under the owner's standing delegation of 2026-10-09, "make them the same way I would and only raise stuff to me that only I can decide"). SPEC-5ab **Session seal.** states the case with no attributed `busy` (Decision 30). SPEC-5ab **Session seal.** states the adapter's rule, SPEC-5ac states the `busy` field, and SPEC-5f **Idle suspension.** states the conjunction and the sequence (CODE-6 items 4, 5, 7, and 18).

## Goals

- A session in `resume_pending` reaches `running` on a replacement pod with no client action, on whichever replica holds its lease.
- A session restored onto a replacement pod holds new credential leases on that pod before its runtime starts.
- A `POST /v1/sessions/{id}/resume` or `lenny/resume_session` call succeeds on any replica from `awaiting_client_action` and from a podless `suspended` session, and on the coordinating replica from a held-pod `suspended` session.
- A coordinator's death in a state SPEC-2a adopts leaves the session with a new owner.
- One recovered crash spends one retry, and a credential rejection that recurs on every attempt spends none under the default retry policy.
- Session age counts only active time.
- An idle session releases its pod or slot, or expires when it cannot be idle-suspended; a suspended session resumes on any message; and a suspended session expires after its lifetime.
- An elicitation pending when its session leaves its pod expires.
- A `suspended` session holds no concurrent-session cap slot, and a resume is refused when the check finds a cap the session counts toward at its limit.

## Non-goals

- A general §29.3 inter-replica forward carrier for non-message requests. The store-only resume route does not need it.
- Takeover of `starting` sessions after coordinator death, left to coordination work, and recycling an `expired` session's pod, left to the recycling follow-up.
- A Sweeper `Driver.Drive` seam hosting the resume, the hold release, and the idle suspension. The watchdog already lists each state, holds the hold and idle configuration, and runs every 5 s against the Sweeper's 15 s.
- Renewing the lease in podless `suspended`. The renewed population would grow with `gateway.maxSuspendedSessionSeconds` rather than with concurrent sessions, beyond the §12.4 lease-renewal row and its Postgres advisory-lock fallback.
- Releasing the lease with the binding. It reverses 0091's approved invariant and removes the claim mutex.
- A periodic backlog evaluation of podless `suspended` sessions on every replica, and an index on the held-pod `suspended` listing. The gateway leader's re-check reads only the podless partial index (CODE-6 item 16), and the other unindexed session listings are filed as RECORDS-1 item 7(l).
- Releasing the coordination lease in the suspension release. The lease lapses on its TTL once no Sweeper renews it, and the Sweeper releases the mirror row that the drain reads (CODE-5 item 1).
- Acquiring the lease at attempt time as the only adoption. It skips the `RecordHandoff` generation compare-and-swap that §10.1.2 requires on every acquisition.
- A synchronous `POST /resume` that claims a pod. It leaves two restore entry points and needs a forward or the off-holder `RESUME_FAILED`.
- A `202` response with idempotent replay in `resume_pending` and `resuming`. `200` with the row matches the existing endpoint, and a client that lost the response can read the state.
- Writing `resuming` at attempt start with a revert on a transient error, and anchoring the window on `ResumeEligibleUntil`, which is a §4.2 create-time field.
- A pool-exhaustion wait inside `resuming`. It moves the wait out from under `maxResumeWindowSeconds`.
- Splitting `Binder.Resume` into separate claim and restore calls. The callback gives the same ordering.
- A `resume_pending_since` column or any other new window anchor.
- An immediate `resume_pending → awaiting_client_action` on a non-retryable pre-claim error. A pre-claim error writes nothing, and the window ends it.
- Extra driver triggers from the failure funnel, from `POST /resume`, or from the podless message path, and an inline resume attempt in the message path. The 5 s tick covers every entry, and an inline attempt blocks the request.
- A lock around classify and send separate from the publish-after-commit order. CODE-4 takes the publish-after-commit order and one per-session delivery lock.
- Keeping `sessionPolicy.maxSessionRetries` as a per-pool cap or reconciling it through `min()`, and deleting `--retry-max-retries`, which is the deployer cap and default for `retryPolicy.maxRetries`.
- A second age column. Incremental accrual on the strictly advancing `UpdatedAt` is exact.
- Deleting `maxSuspendedPodHoldSeconds` and running the idle clock in pod-held `suspended`. The owner asked to enforce the existing release, and interrupt pause-and-decide keeps its held pod.
- Running the idle clock in `input_required` or `awaiting_client_action`, and idle detection from `LastAgentActivityAt` alone, which would suspend a runtime that works without producing traffic, because the gateway sees neither `busy` nor adapter-local frames.
- Taking the per-session delivery lock in `SuspendIdle` or in the suspension release. The lock is per replica and covers only the delivery points. The adapter's seal refuses a delivery from any replica, including one routed on a stale row during a §12.3 failover.
- A synchronous guarded `last_agent_activity_at` write before each `Send`. It costs one primary write per message and a §12.3 fail-open rule, and the adapter's seal already keeps every delivery off a released pod.
- Ending the seal on a `CoordinatorFence`. A later suspension attempt and `maxSessionAge` already bound a seal that outlives its attempt, so a fence rule adds adapter state and a test without changing what a client receives.
- Keeping the idle suspend write without a generation condition. An adopter that unseals after its own failed checkpoint and delivers a turn would have that turn's pod released by the stale coordinator's write.
- A helper that returns a session row together with the store it was read from. No branch consults the source, and the adapter's activity check reads no row.
- An adapter turn count (`message` raises, `response` lowers). Runtimes send several responses, unsolicited output, and background work, so a count does not show whether a runtime is working.
- An unaddressed `busy` on `heartbeat_ack`. On a concurrent pod one busy session would keep every co-tenant from idle suspension.
- Carrying the last-activity time across a checkpoint. The owner decided that the idle clock starts fresh after a restore.
- Releasing every suspension at once, including interrupt suspensions.
- New vocabulary: a new expiry or failure reason for the suspended lifetime, a new checkpoint trigger label (`pre_scale_down` is bound by §4.4 to the PoolScalingController release), a new release disposition, and a new suspension-reason column. `periodic`, `max_idle_time`, `DispositionCompleted`, and the existing `SuspendedReason` field are reused, with one new value `Idle`.
- A tenant-level override for `maxSuspendedSessionSeconds`.
- A new `resumeMode` value for a rebuild, or widening `conversation_only`. The misreported `full` mode is recorded as a defect.
- A new MCP-only route or REST endpoint for content-free resume.
- Resetting `retryCount` after a successful resume.
- A suspension release that keeps the session's credential leases. It would hold pool capacity for up to the suspended-session lifetime.
- A slot reservation that serializes cap admissions. Session creation has none, and the resume check reuses the creation check as it is.
- A cap check on a failure edge out of `suspended`. No caller exists to receive a refusal, and SPEC-6a **Resume admission.** states the exemption (OD-S9).
- A change to the active-delegated-children count, which still counts a `suspended` delegated child.
- Expiry of a §8.6 lease-extension elicitation. Its waiter is the gateway's lease-extension episode rather than a runtime call, and SPEC-5p2 covers only `lenny/request_elicitation`.
- A client event announcing an expired elicitation. The client learns of the expiry from the `404` on respond, and the restored runtime's new elicitation arrives as a new `elicitation_request`.
- Expiry when the `lenny/request_elicitation` call ends while the pod stays bound, which is unchanged from today.

## Defects in the shipped tree that this proposal does not stage

- **A snapshotless rebuild reports `resumeMode: full`.** `classifyResume` returns `full` for a resume with no checkpoint, which §7.2 defines as a full restore from a checkpoint. A new mode is out of scope; RECORDS-1 files it.
- **Off-holder `POST /resume` of a held-pod `suspended` session.** No inter-replica carrier for the §29.3 forward exists, so the serving replica writes nothing and fails closed with `TARGET_NOT_READY`, HTTP 409, as the §29.3 lead states for an unreachable coordinator (CODE-4 item 8). A message to such a session needs no forward, because the coordinating replica's backlog resume delivers it. RECORDS-1 files the missing forward.
- **Off-holder terminate and delete write the terminal state locally.** `handleDelete` and `handleTransition` (`session_transitions.go`) write the terminal state on whichever replica serves the request, while the §29.3 rows that SPEC-2d item 2 narrows require a forward to the coordinator. No inter-replica carrier for that forward exists, and §29.3 names none. This proposal records the local write as a departure. D6 releases the coordinating replica's binding within the D6 bound (T1.14), and the post-terminal hook runs on the writing replica. BUILD-GAPS F-10.1.33 (TT-29) tracks it, with fallback owner P2, which adds the off-holder text to the spec. RECORDS-1 item 6d annotates it and files nothing.
- **Unindexed session listings.** The coordination Sweeper, the checkpoint freshness reaper, and the watchdog's age and expiry-warning sweeps list every session row on every replica, and no `sessions` index keys `state`, so each per-state watchdog listing reads at best every non-terminal row of the tenant. RECORDS-1 item 7(l) files it.
- **A snapshotless rebuild is bounded below its setup cap.** The rebuild runs inside `resuming` under the 300 s watchdog, and the orphan-claim GC drains the unreferenced replacement claim after `claimOrphanTimeout`, so a rebuild whose setup approaches 300 s never reaches `running`. RECORDS-1 item 7(m) files it.
- **Credential fail-open on a failed lookup.** `resolveCredentialPools` returns no provider when the tenant read or the runtime resolution fails, so a session whose tenant has a credential policy starts or resumes with no credential on a transient error. RECORDS-1 item 7(n) files it.
- **Event replay buffer and relay disagree.** §10.4 places the event replay buffer that serves `attach_session` reattach on the coordinating replica, while §29.3 serves the events streaming form from `CH-EVENTRELAY` on any replica. RECORDS-1 item 7(o) files it.
- **Inbox fallback on an unreachable coordinator for `running` and `input_required`.** On the §29.3 off-holder `running` and `input_required` message rows (spec/29_communication-scenarios.md:565-566), an unreachable coordinator makes the serving replica buffer the message in its own session inbox, which the coordinating replica does not read under `durableInbox: false`, so no delivery rule reaches the message. The tree has no cross-replica forward, so the branch does not run in code (pkg/gateway/sessionserver/messages.go:148-151). This proposal changes the recovering and `suspended` states and leaves these two rows as they stand. RECORDS-1 item 7(f) files it.
- **A barrier sent just after a resume commit carries a stale generation.** The barrier target generation comes from the `coordination_lease` mirror (pkg/gateway/coordination/barrier/wiring.go:112), which only the Sweeper's `upsertMirror` writes (pkg/gateway/coordination/coordination/coordination.go:632-643), so the mirror lags the staged entry increment by up to one Sweeper interval. The replacement pod is fenced at the incremented generation and rejects the older barrier generation (pkg/adapter/coordination.go:280-283), while §10.1.8 step 1 states that a barrier carries the current `coordination_generation` (spec/10_gateway-internals.md:183). This proposal does not stage a fix because the rejection fails safe: §10.1.8 treats either barrier outcome as safe, and the drain still writes the eviction checkpoint without the ack. The staged generation increment on entry opens the window, so the gap is new with this proposal. RECORDS-1 item 7(g) files it under §10.1.8.
- **No duplicate suppression.** The §7.2 Explicit ACK row requires the adapter to keep a `delivered_message_ids` set and suppress a redelivered message (spec/07_session-lifecycle.md:305), and no code under `pkg/`, `cmd/`, or `sdks/` implements the set. `lenny_inbox_duplicate_suppressed_total` is registered (pkg/observability/metrics/catalog.go:123) and incremented nowhere. A held message that a crash or a lease handoff redelivers between its consumption and its removal therefore reaches the runtime twice. This proposal does not stage a fix because the set is an adapter feature in a different component, and the staged **Delivery of held messages.** text makes no single-delivery claim: it removes an entry only after the runtime consumes it, as the existing Explicit ACK row states. RECORDS-1 item 7(i) files it under §7.2.
- **No durable-inbox trimmer.** The §7.2 Per-message TTL row requires a trimmer that expires durable inbox entries while the session is in a recovering state and emits `message_expired` with reason `durable_inbox_ttl_expired` (spec/07_session-lifecycle.md:303), and no code implements it: `sessioninbox.ReasonDurableInboxTTLExpired` is declared (pkg/gateway/session/sessioninbox/events.go:30) and has no caller. A durable inbox entry therefore leaves the inbox only through delivery, the `maxInboxSize` overflow drop, or the terminal drain (pkg/gateway/session/sessioninbox/coordinator.go:196). This proposal does not stage a fix because the trimmer is a separate background mechanism that the suspend and resume contract does not depend on, and CODE-4 item 18 makes no claim that a trimmer runs. The staged removal of the `EXPIRE` on the durable inbox key (CODE-4 item 18) and the longer life of a `suspended` session lengthen how long an entry can stay, and an inbox whose best-effort terminal drain fails has no later cleanup until the trimmer exists. RECORDS-1 item 7(j) files it under §7.2.
- **No `inbox_cleared` at adoption.** No code emits the event the §7.2 crash-recovery row requires. RECORDS-1 files it.
- **No `BUDGET_KEYS_EXPIRED` detection.** Neither budget script checks the sentinel key, so an expired budget key reads as zero. It predates this proposal; RECORDS-1 files it.
- **No tenant cap for `maxSuspendedPodHoldSeconds`.** No tenant-configuration field carries it, so only the deploy-wide value applies. RECORDS-1 files it.
- **`resuming` returned to clients.** `toResponse` and `writePreconditionError` write the row's state verbatim, so `GET /v1/sessions/{id}` and a `409 INVALID_STATE_TRANSITION` `details.currentState` return `resuming`, which §15.1 states is never returned. It predates this proposal, and the resume driver makes the state routine. RECORDS-1 item 7(t) files it.
- **Terminal writers read `fromState` outside their mutator.** Terminal writers other than `handleTransition` and `handleDelete` take `fromState`, the pre-terminal state passed to terminal handling, from a row read before their `Update` mutator runs rather than from the locked row, for example `sweepMaxAge` (pkg/gateway/runtime/watchdog/watchdog.go:1113) and the delegation-tree orphan cleanup (pkg/gateway/mcpfabric/delegationtree/orphancleanup/orphancleanup.go:233). CODE-6 item 1 moves the read onto the locked row in the two REST handlers this proposal edits, and D7 does the same for every `hook` row of the D7 **Terminal writer inventory.** table. This proposal does not stage a fix for the rest because the defect predates it and belongs to the §7.2 step 4 work, and no staged deliverable relies on the remaining writers reading `fromState` under the lock: the resume driver commits only through an `Update` guarded on `resuming` and the generation it holds.
- **No session message queues in tenant deletion.** The §12.8 tenant-deletion Phase 4 eraser list erases no session DLQ or durable-inbox key. CODE-6 item 17 wires only the user-erasure step. RECORDS-1 item 7(p) files it.
- **No minimal-state resume.** The resume driver rebuilds a session that §4.4.5 resumes from its minimal state record. RECORDS-1 item 7(q) files it.
- **A partial-workspace restore fails.** `ExtractTree` returns an error on an end-truncated stream, and `Resume` aborts on that error, so a §10.1.7 **Reassembly on resume.** restore fails rather than resuming as `partial_workspace`. RECORDS-1 item 7(s) files it.
- **No takeover of `starting` sessions.** The finding 0091 filed is narrowed to `starting` and stays open.
- **An `expired` session's pod is not recycled on a recycling pool.** It belongs to the recycling follow-up, which RECORDS-1 item 9 hands it to.
- **Session-end order inside the release.** The terminal write precedes the seal, and `Binder.Release` sends `Shutdown` after the lease release and after the terminal signals, where §7.1 steps 20 to 22 and §29.4 steps 11, 12, and 15 place `Shutdown` before the terminal mark. RECORDS-1 item 7(u) files it and states why the hook keeps it.
- **Expired leases keep their pool slot.** The §4.9 expired-lease sweep deletes the record without returning the pool slot, so the lease-expiry fallback of D6 **Credential lease return.** frees no capacity. RECORDS-1 item 7(v) files it for P1.
- **A crashed slot left uncounted when the report commits no edge.** A `CH-ATTACH` stream-failure report that commits no failure edge runs no `accountFailedSlot` (pkg/gateway/sessionserver/failure.go:237, :440), as RECORDS-1 item 7(w) states; this proposal stages no fix and files it for P1.
- **A user revocation leaves a pre-running claim.** `terminateUserSessions` (pkg/gateway/externalapi/admin/users.go:443-470, cmd/lenny-gateway/user_revocation.go:118-123) leaves the claim of a pre-running row it cancels unreleased, as Edge cases **Pre-running claim at a `none` terminal write.** states; this proposal stages no reclaim, and RECORDS-1 item 7(x) files it for P1.
