# Proposal: Define at-least-once semantics for external side effects across an unplanned pod restore, document the `delegate_task` duplicate-spawn residual, and record the window-bounding external-effect checkpoint as a deferred follow-on

- **Status:** Applied to spec (2026-07-03). The S1 (§7.3, §4.4) and S5 (§8.10) spec edits are landed; the S5 handler-comment change to `pkg/gateway/mcpfabric/mcptools/mcptools_register.go` and the tests remain to be implemented in code. Signed off by the user for implementation; all three open decisions resolved (ship documentation only; §10.1 wording coordinated by the author; no `idempotencyKey` added to the pod-originated external-tool surfaces), none altering the staged S1/S5 edits. Converged after 5 adversarial review rounds (6 findings fixed).
- **Date:** 2026-07-02.
- **Scope:** Defines the platform guarantee for external, non-idempotent side effects when a session is restored on a fresh pod after an unplanned pod loss (the §7.3 `resume_pending → resuming → running` recovery path). Proposal 0026 removed the §10.1 coordinator-handoff resume-deduplication machinery as having no coherent gateway consumer and spun the genuine pod-restore exactly-once concern out to this proposal. An end-to-end trace (recorded in §1 below) shows the pod-restore path consults no completed-external-effect ledger and re-derives external effects from a possibly-stale checkpoint, so a `lenny/*` platform-tool action, a connector-tool call, or a `delegate_task` spawn performed after the last durable checkpoint can be re-issued on the fresh pod. The spec states an at-most-once tool-call guarantee only for the graceful-drain / handoff path and is silent on the pod-restore path. This proposal states the actual guarantee (**at-least-once** for external side effects across an unplanned pod restore) in §7.3, notes the corresponding limit on the §4.4 checkpoint-freshness SLO, documents the `delegate_task` duplicate-subtree residual in §8.10 as an unmitigated at-least-once residual on the recovery path (the §11.5 idempotency mechanism is client-facing and does not run on the intra-pod platform-tool path a restored parent re-issues `delegate_task` over), and updates the `delegate_task` handler comment to point at that residual. It **defers** the window-bounding external-effect-triggered checkpoint mechanism to a separate follow-on, recording in Non-goals both the mechanism and the resume-path change that were considered and dropped in adversarial review, with their reasons. It touches `spec/07_session-lifecycle.md`, `spec/04_system-components.md`, `spec/08_recursive-delegation.md`, `pkg/gateway/mcpfabric/mcptools/mcptools_register.go`, and the tests.

This document stages the proposed spec and code changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

On an unplanned pod loss (the retryable set at `spec/07_session-lifecycle.md:386` is `pod_evicted`, `node_lost`, and `runtime_crash`, each unconditionally retryable and routed to the recovery path when within the retry budget, `pkg/api/v1/session/retry_policy.go:297-303`, `pkg/gateway/sessionserver/failure.go:181-182`), the §7.3 recovery path brings the session up on a fresh warm pod and restores its runtime from the last durable checkpoint. Whether `pod_evicted`'s eviction checkpoint persisted affects which checkpoint the restore uses rather than whether the recovery path runs (§1.1). `resumeOnPod` (`pkg/gateway/sessionserver/start.go:3047`) resolves the pool, calls the pod binder's `Resume` with `CheckpointID = row.WorkspaceSnapshot.Ref` (`start.go:3095`), bumps `recovery_generation` (`start.go:3119`), and issues a coordinator fence (`start.go:3144`). It consults no completed-external-tool-call ledger and no deduplication marker. The adapter (`pkg/adapter/resume.go:32,:88`) loads that checkpoint, restores the `/sessions` native-SDK session file, and restarts the runtime, again with no idempotency consultation.

### 1.1 The pod-restore path re-derives external effects from a possibly-stale checkpoint

The eviction checkpoint and the §10.1 `CheckpointBarrier` are both graceful-termination mechanisms (`spec/04_system-components.md:235`; `spec/10_gateway-internals.md:163`). `resumeOnPod` restores from `row.WorkspaceSnapshot.Ref`, the freshest successful checkpoint recorded for the session regardless of the trigger that produced it (periodic, eviction, or pre-drain), overwritten last-writer-wins by the checkpointer (`spec/04_system-components.md:259`; `pkg/gateway/checkpoint/checkpointer/checkpointer.go:259-276`). The replay window therefore spans from that checkpoint to the moment of failure. `node_lost` and `runtime_crash` take no teardown checkpoint, so the restore falls back to the last periodic checkpoint, which is best-effort at a fixed interval (`periodicCheckpointIntervalSeconds` default 600s, `spec/04_system-components.md:257,:259`) and can be up to a full interval stale. `pod_evicted` is unconditionally retryable (`pkg/api/v1/session/retry_policy.go:299`) and records an eviction (preStop) checkpoint when the pod terminates gracefully: a successful eviction checkpoint becomes the freshest checkpoint and yields a near-current restore, and the restore falls back to the periodic checkpoint only when that eviction checkpoint could not be persisted.

A checkpoint bundles the native-SDK `/sessions` file (`spec/04_system-components.md:235`), and §7.3 restores that file and does a native-SDK resume (`spec/07_session-lifecycle.md:411-412`). The restored session therefore resumes its conversation as of the possibly-stale checkpoint. Any external, non-idempotent side effect the lost pod performed after that checkpoint is re-derivable from the restored conversation and can be re-issued, double-firing the external effect. The external-effect surfaces carry no idempotency key and no ledger on the intra-pod path: `CallPlatformTool` (`pkg/adapter/gatewaycontrol/platformtools.go:46`), `CallConnectorTool` (`pkg/adapter/gatewaycontrol/connectortools.go:69`), the gateway-side `DispatchTool` (which intentionally omits idempotency, `pkg/gateway/mcpfabric/mcp/mcp.go:460-462`), and the connector `Invoker.CallTool` (`pkg/gateway/connectors/connectorinvoke/invoker.go:106`). The only deduplication is the §11.5 client-supplied `idempotencyKey`, which requires a non-empty caller key read from request arguments (`pkg/gateway/mcpfabric/mcp/idempotency.go`) and is bypassed on the intra-pod path; `delegate_task`'s key is accepted and ignored by the handler (`pkg/gateway/mcpfabric/mcptools/mcptools_register.go:1899-1903`) and child creation carries no `(parent_session, call)` unique constraint.

### 1.2 The spec is silent on this path and invites over-extension of the §10.1 claim

The §10.1 resume-deduplication (`barrier.Coordinator.ResumeDedup`) is scoped to the coordinator handoff that re-adopts a still-running pod, has zero production callers, and is being removed by proposal 0026, which explicitly spins the pod-restore concern out to this proposal. The spec currently states an at-most-once tool-call guarantee only for the graceful drain / handoff path (`spec/10_gateway-internals.md:181`) and is silent on the pod-restore path. A reader can wrongly over-extend that guarantee to a path it does not cover. Proposal 0026 rewrites §10.1 steps 4-5 and removes the at-most-once tool-call claim entirely, so the reconciliation of that section belongs to 0026; this proposal defines the pod-restore guarantee the spec is missing and the residual it leaves.

## 2. Decisions

- **Automatic per-call exactly-once on the pod-restore path is not achievable and is not proposed.** The restored native-SDK session re-derives its continuation non-deterministically from a possibly-stale checkpoint (`spec/04_system-components.md:235`, `spec/07_session-lifecycle.md:411-412`). A re-issued external call has no stable identity that survives the restore: the runtime mints a fresh `tool_call_id`, and the arguments and ordering may differ, so there is no key to deduplicate on. This refutes the naive "add a completed-call ledger keyed on `(session, tool_call_id)` and skip duplicates" design, and it is why the §11.5 client-key mechanism cannot close the automatic case: a non-deterministic re-issue will not reproduce the same key.
- **The achievable platform guarantee is at-least-once for external side effects across an unplanned pod restore, and the spec is currently silent on it.** The silence is itself a defect because the §10.1 at-most-once claim (`spec/10_gateway-internals.md:181`) invites over-extension. Defining the guarantee, and its precise scope against the drain / handoff path, is the low-risk change and is what this proposal ships (S1).
- **The window-bounding external-effect-triggered checkpoint mechanism is deferred to a separate follow-on.** The mechanism considered was a checkpoint triggered on external-effect completion, collapsing the replay window from up to `periodicCheckpointIntervalSeconds` toward the single external call in flight at the instant of failure. Adversarial review found it does not reliably deliver that bound at the gateway boundary (§3) and that its efficacy also depends on wiring the spec does not currently support. It belongs in its own proposal that first resolves the transcript-recording observability gap. Non-goals records the dropped mechanism (S2) and the dropped resume-path change (S4) with their reasons.
- **Under the current periodic checkpoint the residual is any external effect performed since the last durable checkpoint, bounded by the §4.4 checkpoint-freshness SLO.** It stays at-least-once and is documented as such. The §11.5 idempotency mechanism does not mitigate the platform-tool or connector-tool residual: those intra-pod surfaces accept no §11.5 key (`pkg/gateway/mcpfabric/mcp/mcp.go:460-462`), and adding one is a deferred open decision. Where the external service exposes its own idempotency, a connector can bound the residual by passing an idempotency key to that external API from inside the connector.
- **`delegate_task` duplicate-spawn is the same class of residual; no automatic `(parent_session, call)` deduplication key is added,** because such a key has no stable definition under non-deterministic re-derivation (`mctools_register.go:1899-1903`; the delegation-service child id is random). The §8.10 tree recovery re-attaches children already recorded in the SessionStore (`children_reattached`) but does not recognize a freshly re-derived spawn as a duplicate, and reattachment does not inject the child's result into the restored runtime's session file. The duplicate-subtree residual across the whole replay window (a `delegate_task` in flight at the crash, or one that already completed and was recorded as a child but ran after the last durable checkpoint) is documented (S5) as unmitigated on the recovery path: the §11.5 `idempotencyKey` is client-facing and does not run on the intra-pod platform-tool path a restored parent re-issues `delegate_task` over (the hook is wired only on the client-facing edge `/mcp` surface, `cmd/lenny-gateway/httpsurface.go:686-694`; the intra-pod dispatch omits it, `pkg/gateway/mcpfabric/mcp/mcp.go:460-462`), so the duplicate subtree is not suppressed across a parent restore.
- **Ship documentation only; add no new tool-call transport, no new checkpoint trigger, and no code beyond a comment tweak.** The gateway is already the single execution boundary for every external effect, and the guarantee stands on the existing execution model without new surface.
- **Do not touch the §10.1 graceful-drain / coordinator-handoff path.** Proposal 0026 rewrites §10.1 steps 4-5, removes the `tool_call_idempotency_key` machinery and its at-most-once tool-call claim, and states that no gateway-side resume-deduplication is performed on handoff. This proposal adds nothing in §10.1 and defines only the distinct pod-restore guarantee. Coordinate wording so 0026's §10.1 cross-reference names this proposal's pod-restore **guarantee**, since this proposal ships the guarantee rather than a mechanism (see Open decisions).

## 3. Why exactly-once is unachievable here, and why the window-bounding mechanism is deferred

**No stable per-call identity survives the restore.** External tool results are recorded into the native-SDK `/sessions` file by the runtime, and the adapter observes only `tool_call` frames on the runtime's stdout (`pkg/adapter/coordination.go`); the gateway is not in the runtime's tool-processing loop (§4.7 observe-only model). When the session restores from a stale checkpoint, the runtime replays the conversation and re-derives its next actions. A re-derived external call is a new call with a new `tool_call_id`; it is not the same call the lost pod issued. There is no identity the gateway or the restore path could match against a prior completed call, so per-call exactly-once cannot be built on this path.

**The window-bounding checkpoint mechanism does not reliably close the gap at the gateway boundary.** The mechanism considered would fire a durable checkpoint when an external effect completes, so a restore never rewinds the runtime's conversation past a completed effect. The gateway learns that its `CallPlatformTool` / `CallConnectorTool` RPC returned (`pkg/adapter/gatewaycontrol/platformtools.go:46`, `connectortools.go:69`), but the runtime records the tool result into `/sessions`, and the gateway does not see that write. A checkpoint requested at the gateway execution boundary races the runtime's own persistence of that result into the transcript, so the checkpoint can capture the call-issued-but-result-absent state, and the "window collapses to the single in-flight call" claim is not something the mechanism can guarantee. Closing that gap requires first surfacing when the runtime has persisted a tool result to the transcript, which the platform does not observe today. The consistent variant of the checkpoint also quiesces a Full-level runtime per external effect (P95 near 2s per `spec/04_system-components.md:253`), imposing hot-path pause on the interactive path to shrink a window for the rare `node_lost` / `runtime_crash` cases where the guarantee is unchanged. For these reasons the mechanism is deferred to a separate proposal rather than shipped here.

## 4. Proposed changes

### S1. Define the pod-restore external-side-effect guarantee (at-least-once) in §7.3 and note the corresponding §4.4 SLO limit

**Target:** `spec/07_session-lifecycle.md`, §7.3 "Retry and Resume", immediately after the "Resume flow after pod failure" numbered list (after the line `4. If retries exhausted → state becomes` `awaiting_client_action`, near line 413), before the `**Client actions after retry exhaustion:**` heading. And `spec/04_system-components.md`, §4.4, the "Checkpoint freshness SLO" paragraph (near line 257), appended after the sentence ending `loses at most 10 minutes of workspace changes, not unbounded progress.`

**Anchor and change (§7.3):** Insert a new bolded subsection after the resume-flow numbered list.

```markdown
**External side effects across recovery.** An unplanned pod restore replays the session from its last durable checkpoint (steps 3e–3g above), which is the freshest successful checkpoint recorded for the session regardless of the trigger that produced it ([Section 4.4](04_system-components.md#44-event--checkpoint-store) checkpoint freshness SLO). The checkpoint bundles the native-SDK session file ([Section 4.4](04_system-components.md#44-event--checkpoint-store) checkpoint atomicity), and the restored runtime resumes its conversation as of that checkpoint. The replay window spans from that checkpoint to the moment of failure. `node_lost` and `runtime_crash` take no teardown checkpoint, so the restore falls back to the last periodic checkpoint, up to a full `periodicCheckpointIntervalSeconds` stale. `pod_evicted` records an eviction (preStop) checkpoint when the pod terminates gracefully: a successful eviction checkpoint becomes the freshest checkpoint and yields a near-current restore with a minimal window, and the restore falls back to the last periodic checkpoint only when that eviction checkpoint could not be persisted. Any external, non-idempotent side effect the lost pod performed within the replay window (a `lenny/*` platform-tool action, a connector-tool call, or a `lenny/delegate_task` spawn) is re-derivable from the restored conversation and can be re-issued on the fresh pod.

The platform therefore guarantees **at-least-once** semantics for external side effects across an unplanned pod restore: an external effect performed since the last durable checkpoint may be issued more than once. Exactly-once is not achievable on this path. The restored native-SDK session re-derives its continuation non-deterministically from the checkpoint, so a re-issued external call has no stable identity that survives the restore. The runtime mints a fresh `tool_call_id`, the arguments and ordering may differ, and there is no key on which the gateway could deduplicate. The platform provides no automatic deduplication on this path, and the [Section 11.5](11_policy-and-controls.md#115-idempotency) idempotency mechanism does not close it. That mechanism is client-facing: a client supplies the key on a REST call or a client-facing MCP call, and it collapses gateway-failover and client-retry duplicates. The re-derived calls a restored runtime issues travel the intra-pod platform-tool and connector-tool surfaces, which do not run the §11.5 hook, so the key does not deduplicate a recovery re-issue. Where an external service exposes its own idempotency, a connector can bound the residual by passing an idempotency key to that external API from inside the connector; the platform does not do this on the connector's behalf. Duplicate `delegate_task` subtrees are the same residual and are covered in [Section 8.10](08_recursive-delegation.md#810-delegation-tree-recovery).

This guarantee is specific to the unplanned pod-restore path (`resume_pending → resuming → running`, driven by the retryable failure set above). It does not apply to a graceful drain or coordinator handoff, where the coordinator re-adopts the still-running pod without a checkpoint restore and replays nothing ([Section 10.1](10_gateway-internals.md#101-horizontal-scaling)).
```

**Anchor and change (§4.4):** Append the following sentences to the "Checkpoint freshness SLO" paragraph, after `loses at most 10 minutes of workspace changes, not unbounded progress.`

```markdown
 This SLO bounds only recoverable workspace state. It does not bound external, irreversible side effects: an external tool action or `delegate_task` spawn performed after the last durable checkpoint is re-derivable when the session is restored on a fresh pod and can re-fire under the at-least-once guarantee defined in [§7.3](07_session-lifecycle.md#73-retry-and-resume) (External side effects across recovery).
```

**Rationale:** The spec guarantees at-most-once tool-call semantics only for the graceful drain / coordinator-handoff path (`spec/10_gateway-internals.md:181`, which proposal 0026 removes) and says nothing about the pod-restore path that `resumeOnPod` drives with a possibly-stale checkpoint (`start.go:3047,:3095`). §4.4's freshness SLO currently frames staleness as recoverable workspace loss alone (`spec/04_system-components.md:257`) and is silent on irreversible external effects re-firing. Stating the actual guarantee and its reason lets authors and operators reason about external effects correctly. The at-least-once and duplicate-suppression vocabulary already exists in §7.2 for inbox delivery (`spec/07_session-lifecycle.md:298`), so the guarantee reuses established spec language.

## 5. Non-goals

- **Automatic exactly-once for arbitrary non-idempotent external effects on the pod-restore path.** This is intractable under non-deterministic native-SDK re-derivation, since no stable per-call identity survives the restore (§3). The platform guarantees at-least-once.
- **The external-effect-triggered checkpoint mechanism that would bound the replay window (dropped alternative S2).** The mechanism would fire a durable checkpoint on external-effect completion to collapse the window toward the single in-flight call. It is dropped from this proposal because (a) the guarantee does not change, since the in-flight call still double-fires, so the defect (silent spec and over-extendable §10.1 claim) is resolved by S1 alone plus the existing §11.5 key; (b) its efficacy premise is not reliably achievable at the gateway boundary, since a checkpoint requested when the gateway's tool RPC returns races the runtime's own persistence of the result into `/sessions`, and the gateway has no signal that the transcript reflects the effect (§3); (c) the consistent variant quiesces a Full-level runtime per effect (P95 near 2s, `spec/04_system-components.md:253`), imposing frequent hot-path pause to shrink a window for rare failures; and (d) it adds a new checkpoint-trigger type and a new operator-tunable for a best-effort, marginal window reduction. If window reduction is later judged worth its cost, it belongs in a separate proposal that first resolves the transcript-recording observability gap.
- **Making `resumeOnPod` restore a separately-selected "freshest" checkpoint (dropped alternative S4).** This rests on a false premise. `row.WorkspaceSnapshot.Ref` is a single field overwritten last-writer-wins on every successful checkpoint by the checkpointer (`pkg/gateway/checkpoint/checkpointer/checkpointer.go`, `Checkpoint` at line 194), regardless of the trigger that produced it, so it already holds the freshest recorded checkpoint by construction; `resumeOnPod` reads exactly that field (`start.go:3095`) and the adapter loads whatever `CheckpointID` it is handed (`resume.go:88`). No resume-path or adapter change is required for the restore to pick up the freshest durable checkpoint. The only genuine deliverable, a regression test that the restore selects the freshest checkpoint, is folded into Testing. Inventing a parallel "max-by-timestamp among durable checkpoints" selection would duplicate the single ref the system already maintains and add surface for a problem the existing ref resolves.
- **The §10.1 graceful-drain / coordinator-handoff path and its `ResumeDedup` machinery.** Proposal 0026 governs that path. This proposal adds nothing there and does not modify the drain barrier or `ResumeDedup`.
- **Workspace-file exactly-once.** Local workspace effects are redoable and remain bounded by the periodic checkpoint freshness SLO (`spec/04_system-components.md:257`). This proposal targets external, irreversible side effects only.
- **Changing the periodic workspace checkpoint interval or the checkpoint freshness SLO.** The guarantee this proposal states is descriptive of the existing behavior; it changes no default.
- **A new gateway-to-pod tool-call dispatch transport or a per-call sequence number.** The gateway is not in the per-tool-call dispatch path (§4.7), and every external effect is already recorded at the gateway execution boundary the pod reaches pod → gateway.

- **tier-11 doc/spec consistency (spec-named guarantee, cross-reference resolution):** A consistency check asserts that §7.3 "External side effects across recovery" states the at-least-once guarantee and that its cross-references to §4.4, §8.10, §10.1, and §11.5 all resolve to real anchors; that the §4.4 freshness-SLO note and the §8.10 "Duplicate spawn across parent recovery" paragraph agree with §7.3 rather than contradicting it; and that the §7.3 scope sentence does not claim any guarantee on the drain / handoff path, staying consistent with proposal 0026's §10.1 rewrite (which states that no gateway-side resume-deduplication is performed on handoff). `// spec: 7.3 (external side effects across recovery), 4.4 (checkpoint freshness slo), 8.10 (duplicate spawn across parent recovery), 11.5 (idempotency)`.
- **tier-4 integration (boundary and spec-named-failure paths for the delegate_task residual):** With the gateway, Postgres, and the `idempotency_keys` table on the compose stack, a test drives a `delegate_task` re-issue across a simulated parent restore through the intra-pod platform-tool path (`GatewayControl.CallPlatformTool` → `DispatchTool`), the path a restored parent agent uses. It asserts that a second child subtree is created whether or not a §11.5 `idempotencyKey` is supplied, because the intra-pod dispatch does not run the §11.5 hook; this exercises the unmitigated at-least-once residual the spec now documents. A contrast case drives `delegate_task` through the client-facing edge `/mcp` surface with a §11.5 `idempotencyKey` and asserts the hook collapses a retry there: the same key with the same body replays the cached result, and the same key with a different request body returns `422 IDEMPOTENCY_KEY_REUSED`. This pins the mitigation to the client-facing edge and confirms the recovery path is unmitigated. `// spec: 8.10 (duplicate spawn across parent recovery), 11.5 (idempotency)`.
- **tier-2 component (recovery path, regression guard):** Against envtest, a test asserts that `resumeOnPod` restores from `row.WorkspaceSnapshot.Ref` (the freshest durable checkpoint, updated last-writer-wins by the checkpointer) and that the restore path consults no completed-external-effect ledger or deduplication marker, pinning the at-least-once guarantee to §7.3. The test seeds a session whose freshest checkpoint is a periodic checkpoint older than a recorded external effect and confirms the restore proceeds from that checkpoint without suppressing a re-derivable effect. `// diagnosis:` a failure means the restore path silently gained or lost a dedup consultation the guarantee depends on. `// spec: 7.3 (external side effects across recovery)`.
- **tier-0 build:** The `mctools_register.go` `IdempotencyKey` comment change compiles under `go build` / `go vet` with no behavior change; the comment references the new §8.10 subsection.
