# Proposal: Pod-status ownership decomposition and the WarmPoolController-driven task-mode disposition: WarmPoolController-sole-written `Sandbox.status`, gateway writes only `SandboxClaim`, occupancy as a claim-existence projection, and the between-task disposition relayed through a scrub-Result `ReportTaskCleanup` RPC and a claim-finalizer handshake

- **Status:** Verified (2026-06-10). Converged after 8 adversarial review rounds (17 findings fixed); awaiting sign-off.
- **Date:** 2026-06-10.
- **Scope:** Carries two changes in one proposal: (1) the pod-status ownership decomposition, and (2) the task-mode between-task disposition (F-5.2.30), staged as the scrub-Result relay plus claim-finalizer handshake described in Section 4.6. The decomposition removes the second writer of `Sandbox.status.phase`/`status.activeSlots`/`status.tenantId`. The gateway stops writing those fields and writes only `SandboxClaim` (including the net-new `SandboxClaim.status.phase` binding disposition and the net-new `SandboxClaim.status.cleanupReport` task-cleanup relay field) and the Postgres session store; the chart drops the `sandboxes` main-resource `patch` and `watch` verbs (converging the main-resource grant to the `get`/`list` the §4.6.3 gateway RBAC paragraph at `spec/04_system-components.md:588` grants) and narrows the `sandboxes/status` grant from `get`/`update`/`patch` to a scoped `get`/`patch` for the `Sandbox.status.conditions` writes the gateway still performs (open decision 2). The phase, slot-count, and tenant-pin writes leave the gateway entirely. The §5.2 application-layer tenant pin is re-pointed from `Sandbox.status.tenantId` onto the gateway-stamped agent-Pod `lenny.dev/tenant-id` label. Pod occupancy becomes a WarmPoolController level-triggered projection of `SandboxClaim` existence and disposition; a session-mode pod whose claim reaches `released`/`failed` reconciles through `draining → terminated` rather than back to `idle`, preserving the §6.2 one-session-only invariant, while a concurrent-workspace pod that loses its last slot recycles back to `idle` along the §6.2 line 164 edge. The between-task disposition of a task-mode pod is staged in this proposal: the projection writes the coarse occupancy phase `claimed` for a live task-mode claim, and the recycle-or-retire disposition on the between-task boundary (recycle to `idle` for a non-preConnect pod, recycle through `sdk_connecting` for a preConnect pod, or retire to `draining`/`failed` when a retirement limit is reached or `onCleanupFailure: fail` applies) is written by the WarmPoolController. The WarmPoolController obtains the scrub outcome it needs through the relay: the adapter reports each task's scrub `Result` to the gateway via a new `ReportTaskCleanup` RPC on the existing adapter→gateway `GatewayControl` service, the gateway writes it onto the per-task `SandboxClaim.status.cleanupReport` on the live `claim-<sessionID>` while leaving the claim binding phase at `bound`/`active`, and the WarmPoolController reads the report plus the pool `TaskPolicy` and runs the relocated `taskcleanup.Decide` to write the disposition on `Sandbox.status` under its own field manager. The claim binding lifecycle is per session: one `claim-<sessionID>` spans the pod's whole sequence of tasks, the disposition fires per task while the claim stays live, and the gateway sets the claim phase to `released`/`failed` and deletes the claim only at session termination (the client ends the session, or a between-task disposition retires the pod). A `lenny.dev/task-disposition` claim finalizer, added by the WarmPoolController and removed at session termination, guarantees the final task's report is consumed before the binding record is deleted. The per-pod counters move from gateway process memory onto `Sandbox.status.taskState` (`tasksCompleted`, `scrubFailureCount`, `lastTaskId`, `lastDisposition`, `lastScrubWarning`), WarmPoolController-written as a read-modify-write atomic with the disposition phase; this resolves the prior counter-store open decision to `Sandbox.status.taskState`, WPC-owned. The concurrent-workspace drains at §6.2 lines 165-167 also lose their gateway `Sandbox.status` writer: the uptime drains are written by the WarmPoolController from the pod `CreationTimestamp` against the pool's `maxPodUptimeSeconds`, and the unhealthy-threshold drain is written by the WarmPoolController reconciling a gateway-stamped `lenny.dev/drain-request` Pod annotation, so no concurrent pod is stranded once the gateway stops writing `Sandbox.status`. The Redis-unwired fallback concurrent-slot cap path is deleted, making the §5.2 Redis counter the single cap mechanism. The `Sandbox.status.conditions` writer and the deeper decomposition (removing the fine session/task-lifecycle phases from `Sandbox.status.phase` and relocating that authority to the §7.2/§8.8 Postgres session store) are recorded as reviewer-owned open decisions rather than staged, because they carry their own blast radius and are not required to remove the second writer. `maxTaskRetries` (pod crash mid-task) stays gateway-side and untouched: that is session recovery rather than a between-task disposition (§6.2 lines 185-192). Unblocks F-5.2.30.

This document stages the proposed spec, CRD, proto, and chart edits for both the decomposition and the task-mode disposition. It does not modify any spec file. The staged spec edits in Section 7 land only after sign-off. Code, chart, proto, and test changes are recorded for the implementer and land with the implementation work rather than with the spec apply.

## 1. Problem

Two authorities write `Sandbox.status` today, contradicting the §4.6.3 ownership table.

**The §4.6.3 ownership table assigns `Sandbox.status.*` solely to the WarmPoolController.** The table row reads `Sandbox | status.* | WarmPoolController | State machine transitions, health` (`spec/04_system-components.md:574`). The §4.6.3 gateway RBAC paragraph (`spec/04_system-components.md:588`) grants the gateway `get`/`patch` on `Pods`, `create`/`get`/`delete` on `SandboxClaim`, and `get`/`list` on `Sandbox`, with no access to the `sandboxes/status` subresource. §4.6.3 SSA rule 2 (`spec/04_system-components.md:582`) prohibits `Force: true`/force-conflicts in reconciliation code.

**The shipped gateway writes `Sandbox.status` anyway.** The gateway SSA-applies `Sandbox.status.phase` (and `status.activeSlots`, `status.tenantId`) under field manager `lenny-gateway` with `client.ForceOwnership` across the claim window: `ApplyGatewayPhase` (`pkg/gateway/podclaim/gatewaystatus.go:46-56`, called from `claimer.go:114` and the binder `setPhase` chain at `pkg/gateway/podsession/binder.go:739-748`), the slot-reservation write (`pkg/gateway/podclaim/slotclaimer.go:549-551`), the slot-release write (`slotclaimer.go:684-688`), and the suspend write (`binder.go:1537`). The drain/reclaim yield uses a non-Apply `Status().Update` to hand `status.phase` back to the WarmPoolController (`binder.go:780-801`, `slotclaimer.go:295-310`). The WarmPoolController is the second authority, writing `Sandbox.status.phase` via non-forcing SSA Apply under field manager `lenny-warm-pool-controller` (`pkg/controller/sandbox/controller.go:621`→`:686`; `pkg/controller/warmpool/pod_reconciler.go:469-474`).

**The chart over-grants `sandboxes/status` to make the gateway code work.** The shipped chart grants the gateway `get`/`update`/`patch` on `sandboxes/status` (`charts/lenny/templates/gateway-deployment.yaml:130-132`), a grant absent from the §4.6.3 paragraph at `:588` and present nowhere in `spec/`. Code comments cite a "§4.6.3 gateway carve-out" (`gatewaystatus.go:16-25`, `binder.go:730`) that the normative table does not contain.

**The fine session-lifecycle phases are the half the gateway force-writes.** The single 21-value `Sandbox.status.phase` state machine (`pkg/sandbox/state/state.go:74-95`; the §6.2 fenced block at `spec/06_warm-pod-model.md:82-177`) conflates warm-pool inventory (`warming`, `sdk_connecting`, `idle`, `draining`, `terminated`), session/task lifecycle (`receiving_uploads`, `finalizing_workspace`, `running_setup`, `starting_session`, `attached`, `task_cleanup`, `suspended`, `resuming`, `resume_pending`, `awaiting_client_action`, and the terminal `completed`/`failed`/`cancelled`/`expired`), and the session-to-pod binding (`claimed`, `slot_active`). The WarmPoolController never writes the fine session phases: its lifecycle planner sets only coarse phases (`Idle`, `Failed`, `Draining`, `Terminated`, `SDKConnecting`) because `SetupWithManager` registers only `For(&Sandbox{}).Owns(&Pod{})` (`pkg/controller/sandbox/controller.go:714-719`) and has no view of session or task progress.

**Finding context.** F-5.2.30 (`BUILD-GAPS.md:3689`, DEFERRED High) is the task-execution driver that runs the between-task reuse loop, calls `taskcleanup.Decide`, writes the §6.2 disposition pod phase (`spec/06_warm-pod-model.md:147-156`), writes the `scrub_warning` pod annotation, and emits the retirement counters. The shipped code keeps this in the gateway, and the per-pod counters live in gateway process memory today (`pkg/gateway/taskdriver/taskdriver.go:101-104`), against the §10.1 statelessness rule (`spec/10_gateway-internals.md:5`). The prior on-disk proposal (`proposals/0002_new_task-mode-gateway-driver-reporttaskcleanup-rpc-disposition-w.md`, Status "Verified (2026-06-09), awaiting sign-off") resolves F-5.2.30 by retro-documenting the gateway's `Sandbox.status` write window into §4.6.3 and keeping the disposition decision and counter writes in the gateway's claim-window carve-out. This proposal takes the opposite direction: it removes the second writer and relocates the disposition to the WarmPoolController, which already owns `Sandbox.status`. Because the scrub `Result` originates in the adapter (which has no Kubernetes client, §10.3) and the disposition is an inventory decision owned by the WarmPoolController (which reconciles the pool), the Result is relayed adapter → gateway → WarmPoolController through a new `ReportTaskCleanup` RPC and a new `SandboxClaim.status.cleanupReport` field. F-5.2.30 is in-scope and staged in this proposal; the design is Section 4.6.

## 2. Decisions

The following decisions constrain this design. The fine-phase relocation remains a reviewer-owned open decision in Section 11 rather than staged, because the second-writer removal does not require it. The task-mode disposition ownership is now decided here and staged (Section 4.6): the disposition moves from the gateway to the WarmPoolController.

- **The gateway stops writing `Sandbox.status.phase`, `status.activeSlots`, and `status.tenantId`.** `ApplyGatewayPhase` (the `claimed` write at `claimer.go:114`, taken by both session-mode and task-mode whole-pod claims through `Claimer.Claim` at `pkg/gateway/sessionserver/start.go:1186`), the slot-reservation and slot-release SSA phase writes, the suspend phase write, the session-mode drain/reclaim `Status().Update` (`binder.go:780-801`), the concurrent-mode uptime drain `Status().Update` (`slotclaimer.go:295-310`, `drainExpiredPod`), and the concurrent-mode whole-pod unhealthy drain `Status().Update` (`slotbinder.go:382-405`, `DrainSandbox`) are all removed. Removing `ApplyGatewayPhase` removes the task-mode `claimed` write as well as the session-mode one, so the WarmPoolController occupancy projection (Section 4.2) writes the task-mode `claimed` occupancy for a task-mode `Sandbox` holding a live claim. The gateway also stops writing the task-mode disposition pod phase (`pkg/gateway/taskdriver/taskdriver.go`): the §6.2 between-task boundary (`task_cleanup → idle`/`sdk_connecting`/`draining`/`failed`, `spec/06_warm-pod-model.md:147-156`) becomes a WarmPoolController-written outcome (Section 4.6). The gateway no longer holds the per-pod counters or calls `taskcleanup.Decide`.
- **The task-mode between-task disposition moves from the gateway to the WarmPoolController, relayed through `ReportTaskCleanup` and `SandboxClaim.status.cleanupReport`.** A task-mode session runs multiple sequential tasks on one pod under one `SandboxClaim` (`claim-<sessionID>`, created once at session start; the SDK receives a new `TaskID` under the same `SessionID` after each `task_ready` signal, `spec/15_external-api-surface.md:2568-2573`). The claim lifecycle is per session; the between-task disposition fires per task. The §5.2 scrub runs in-pod, adapter-internal and unchanged, producing a binary scrub `Result` (`succeeded` or `failed`, matching `pkg/adapter/scrub.Result`). The warn-versus-fail disposition is not a scrub outcome the adapter reports; the WarmPoolController derives it from a failed scrub plus the pool `onCleanupFailure` policy via `taskcleanup.Decide`. The disposition (recycle the pod to the pool versus retire it) is an inventory decision and therefore the WarmPoolController's, but the scrub `Result` originates in the adapter, which has no Kubernetes client (§10.3). It is relayed: the adapter reports the binary `Result` to the gateway via a new `ReportTaskCleanup` RPC on the existing adapter→gateway `GatewayControl` service (the `ExtendLease` Adapter→Gateway precedent in §4.7); the gateway writes the `Result` onto the live `claim-<sessionID>` as a per-task `SandboxClaim.status.cleanupReport {taskId, outcome}` field (the gateway already owns `SandboxClaim.status` per the §4.6.3 table) while leaving the claim binding phase at `bound`/`active`, writing nothing on `Sandbox.status`; the WarmPoolController, which already watches `SandboxClaim` for the occupancy projection, reads the report plus the pool `TaskPolicy` (`maxTasksPerPod`, `maxScrubFailures`, `maxPodUptimeSeconds`, `onCleanupFailure`, the runtime `preConnect` capability), the cumulative counters on `Sandbox.status.taskState`, pod uptime from the pod `CreationTimestamp`, and the `lenny.dev/host-schedulable` label, and runs `taskcleanup.Decide` (relocated from the gateway task path, a pure function with no Kubernetes client, `pkg/sandbox/taskcleanup/taskcleanup.go:18-23`) to write the disposition on `Sandbox.status` in one SSA Apply under its own field manager: the disposition phase (`idle` for a non-preConnect recycle, `sdk_connecting` for a preConnect re-warm, `draining` or `failed` for retirement), the incremented `taskState` counters, and the `scrub_warning` annotation on a warn outcome. On a recycle disposition the claim survives at `bound`/`active` so the session's next task reuses the same binding, and the gateway clears `cleanupReport` on the live claim when it re-dispatches that next task so the WarmPoolController occupancy projection reads `claimed` for the task's execution rather than holding the pod at the prior recycle phase (`cleanupReport` is written at task completion rather than at task dispatch, so the clear is the dispatch-time signal that the pod is busy again, Section 4.2); the gateway sets the claim phase to `released`/`failed` and deletes `claim-<sessionID>` only when the session terminates (the client ends the session, or the WarmPoolController retires the pod to `draining`/`failed` on a between-task disposition). The disposition is not a single coarse `claimed → idle` edge: §6.2 routes the between-task boundary through `task_cleanup → idle` for a non-preConnect pod (`spec/06_warm-pod-model.md:147`), through `task_cleanup → sdk_connecting → idle` for a preConnect pod so the returned idle pod is SDK-warm (`spec/06_warm-pod-model.md:154,183`), and through `task_cleanup → draining`/`failed` when a retirement limit is reached or `onCleanupFailure: fail` applies (`spec/06_warm-pod-model.md:149-151,156`). The shipped disposition function `taskcleanup.Decide` already encodes this branch (`pkg/sandbox/taskcleanup/taskcleanup.go:64-110,173-266`); the move relocates where it runs and who supplies its inputs, and leaves the function itself unchanged.
- **The per-pod counters move onto `Sandbox.status.taskState`, WarmPoolController-written.** `Sandbox.status` carries only `Phase`, `ActiveSlots`, `TenantID`, and `SessionID` today (`pkg/apis/lenny/v1alpha1/sandbox_types.go:100,107,114,123`), and the counters live in gateway process memory (`pkg/gateway/taskdriver/taskdriver.go:101-104`), against the §10.1 statelessness rule. `Sandbox.status.taskState` holds `tasksCompleted`, `scrubFailureCount`, `lastTaskId`, `lastDisposition`, and `lastScrubWarning`, WarmPoolController-written as a read-modify-write atomic with the disposition phase in the same SSA Apply. One actor reads and writes both the counters and the phase. The WarmPoolController mirrors `tasksCompleted`/`scrubFailureCount` into the net-new `agent_pod_state` `tasks_completed`/`scrub_failure_count` columns (the §12 mirror contract; Section 7.12 stages both the columns and the mirror sentence). This resolves the prior counter-store open decision to `Sandbox.status.taskState`, WPC-owned.
- **A `lenny.dev/task-disposition` finalizer guarantees the final task's report is consumed before the per-session claim is deleted.** The WarmPoolController adds the finalizer on first observing a task-mode claim and removes it at session termination, after the final task's report is consumed and the terminal disposition is written. The finalizer stays on the `claim-<sessionID>` across every between-task boundary, so the generic "claim gone → recycle to idle" occupancy projection never fires the wrong outcome for a task-mode pod, and at session end it holds the claim in `Terminating` with the report intact until the disposition runs. The per-task disposition itself runs off the per-task `cleanupReport` while the claim is `bound`/`active`, ahead of any deletion. The crash-recovery cases and the WPC-side `task_cleanup` watchdog are in Section 4.6.
- The §6.2 lines 165-167 concurrent-workspace drains the removed gateway writes performed are relocated to the WarmPoolController occupancy projection: the uptime drains (§6.2 lines 166-167) become a controller-derived transition from the pod `CreationTimestamp` against the pool's `maxPodUptimeSeconds`, and the unhealthy-threshold drain (§6.2 line 165) is written by the controller reconciling a gateway-stamped `lenny.dev/drain-request` Pod annotation (the gateway already holds `patch` on `Pods`). The gateway writes only `SandboxClaim` (including `SandboxClaim.status.phase` and `SandboxClaim.status.cleanupReport`), the `lenny.dev/drain-request` Pod annotation (using its existing Pod `patch`), the Postgres session store, and the agent-Pod labels it already mutates (it creates and deletes the binding claim, `pkg/gateway/podclaim/claimer.go:140-158`). `SandboxClaim.status` is the gateway-owned surface in the §4.6.3 table (`spec/04_system-components.md:590`), so this preserves the WarmPoolController-sole assignment of `Sandbox.status.phase` at `spec/04_system-components.md:574`. The gateway's `Sandbox.status.conditions` writes (`Terminated`/`Suspended`) are the subject of open decision 2 in Section 11 and are not removed by the staged change; the gateway keeps a scoped `get`/`patch` grant on `sandboxes/status` for those condition writes (the `update` verb is dropped because the writes use server-side apply), and the chart over-grant of `sandboxes/status` at `charts/lenny/templates/gateway-deployment.yaml:130-132` is narrowed from `get`/`update`/`patch` to that scoped `get`/`patch` rather than removed. This reverses the prior on-disk proposal's retro-documentation approach. The carve-out language in code comments (`gatewaystatus.go:16-25`, `binder.go:730`, `slotclaimer.go:37-44`) is deleted with the code.
- **`C1`, `C2`, and `C4` form a non-severable unit.** Removing the gateway writers (C1) leaves the fine session phases with no writer. Four spec locations still assert those phases live on `Sandbox.status.phase`: §6.2:305, §15:643, §4.6.3:591, and §4.6.1:384. C1 is therefore coherent only when it lands with the §6.2/§15 authority relocation (C2) and the admission-guard re-pointing (C4). Section 11 records the reviewer decision that gates the relocation; if the reviewer declines the relocation, the narrowed unit in Section 3 still removes the second writer (the fine phases become controller-or-unwritten values that no component force-writes).
- **Pod occupancy is a WarmPoolController level-triggered projection of `SandboxClaim` existence.** The WarmPoolController has no `SandboxClaim` watch today (`SetupWithManager` registers only `For(&Sandbox{}).Owns(&Pod{})`, `pkg/controller/sandbox/controller.go:714-719`; the only `SandboxClaim` references are `List`-only at `finalizer.go:60` and `warmpool/gc.go:151`), so adding the watch and the projection is net-new controller work. The coarse `lenny.dev/state` label is already a WarmPoolController-derived projection of `Sandbox.status.phase` via `state.CoarseState` (`pkg/controller/sandbox/controller.go:478-484`, `syncPodStateLabel` at `:496-516`); the change re-sources the occupancy phase from claim existence rather than from a gateway write.
- **The Redis-unwired fallback concurrent-slot cap path is deleted.** On the `Counter==nil` path the gateway's `Sandbox.status` SSA Apply doubles as the optimistic-lock cap check (`slotclaimer.go:546-557`: a conflict triggers undo-and-retry; the pre-read at `:514` reads `status.activeSlots`). Removing the gateway status write leaves nothing incrementing `status.activeSlots`, so that gate becomes vacuous. The §5.2 atomic Redis Lua `GET`-compare-`INCR` on `lenny:pod:{pod_id}:active_slots` (`spec/05_runtime-registry-and-pool-model.md:519`) is the single cap mechanism and is authoritative. The `Counter==nil` else-branch is removed and a nil `Counter` for a concurrent-mode claim is a configuration error. The code itself already disclaims the fallback as non-spec-aligned (`slotclaimer.go:220-223`, `cmd/lenny-gateway/main.go:2444-2447`).
- **The narrow cross-context seam is `SandboxClaim` existence.** The gateway creates and deletes the claim; the WarmPoolController reflects occupancy from it. No new client-facing protocol surface is added.
- **v1 ships one canonical implementation per concern with no tier-dependent branches and no migration shim.** No deployments exist in the wild. The gateway's `Sandbox.status` writers are deleted rather than gated behind a flag, and the dual `Counter`-wired/`Counter==nil` slot path is collapsed to the single Redis-counter path.

## 3. Design overview

The gateway's authority is reduced to `SandboxClaim` and the Postgres session store. It already creates the binding claim at `claimer.go:103` and deletes it on release, and it already owns the session and task state machine in Postgres (§7.2, §8.8). Removing the gateway's `Sandbox.status` writers leaves the WarmPoolController as the sole writer of that subresource, which is the assignment the §4.6.3 table already records.

The WarmPoolController gains a `SandboxClaim` watch and computes pod occupancy as a level-triggered reconciliation of claim existence, claim disposition, and concurrent-workspace lifecycle policy. A never-bound warm `Sandbox` with no referencing claim reads `idle`; a `Sandbox` referenced by one or more live claims reads the occupancy value (`claimed` for a session-mode or task-mode pod, `slot_active` for a concurrent-workspace pod). The projection is mode-aware (it reads `Sandbox.spec.executionMode`, enum `session;task;concurrent` at `pkg/apis/lenny/v1alpha1/sandbox_types.go:45`) to preserve the §6.2 one-session-only security invariant: a session-mode `Sandbox` whose referencing claim has reached the gateway-recorded terminal disposition (`SandboxClaim.status.phase` of `released` or `failed`) reconciles through its terminal phase to `draining` and then `terminated`, and is never returned to `idle`. A task-mode `Sandbox` reads `claimed` while a live claim references it. Its between-task disposition is computed by the WarmPoolController from the relayed scrub report rather than left to the occupancy projection alone (Section 4.6): the gateway writes each task's scrub `Result` onto the per-task `SandboxClaim.status.cleanupReport` on the live `claim-<sessionID>` while leaving the claim phase at `bound`/`active`, and the WarmPoolController reads that report plus the pool `TaskPolicy`, the `Sandbox.status.taskState` counters, the pod uptime, and the `lenny.dev/host-schedulable` label, runs `taskcleanup.Decide`, and writes the disposition on `Sandbox.status`. The claim binding lifecycle is per session (one `claim-<sessionID>` spans the pod's whole sequence of tasks); the disposition is per task, so a recycle disposition leaves the claim live for the next task and only a session-terminating disposition (the pod retired to `draining`/`failed`, or the client ending the session) sets the claim to `released`/`failed`. The gateway writes `cleanupReport` at task completion rather than at task dispatch, so it clears `cleanupReport` on the live claim when it re-dispatches the next task; the occupancy projection then reads `claimed` for the duration of that task's execution rather than holding the pod at the prior recycle phase (Section 4.2), and only the genuine idle-between-tasks window leaves the pod at the recycle phase. §6.2 routes the between-task boundary through `task_cleanup` to one of four dispositions: `idle` for a non-preConnect pod (`spec/06_warm-pod-model.md:147`), `sdk_connecting → idle` for a preConnect pod so the returned idle pod is SDK-warm (`spec/06_warm-pod-model.md:154`, preserving the §6.1/§6.2 invariant at `spec/06_warm-pod-model.md:183` that "every idle pod in a preConnect pool is SDK-warm"), `draining` when `maxTasksPerPod`, `maxScrubFailures`, or `maxPodUptimeSeconds` is reached (`spec/06_warm-pod-model.md:149-151`), and `failed` under `onCleanupFailure: fail` (`spec/06_warm-pod-model.md:156`). The disposition function `taskcleanup.Decide` selects among them from the scrub outcome, the cumulative scrub-failure count, the task count, the uptime, and the pool's `preConnect` capability (`pkg/sandbox/taskcleanup/taskcleanup.go:64-110,173-266`); the relay supplies the scrub outcome (the `cleanupReport`), the counters (`Sandbox.status.taskState`), and the `preConnect` capability (the pool `TaskPolicy`), so the WarmPoolController has every input the function needs. The disposition is not a coarse `claimed → idle` recycle that would bypass the spec's `maxTasksPerPod`, `maxScrubFailures`, and preConnect re-warm controls; it is the full `task_cleanup → {idle, sdk_connecting, draining, failed}` branch. A `lenny.dev/task-disposition` finalizer (Section 4.6) keeps the generic existence-driven occupancy path from firing the wrong outcome for the task-mode pod while the report is consumed. A concurrent-workspace `Sandbox` recycles: when its last slot's claim is deleted it returns from `slot_active` to `idle` along the §6.2 line 164 edge, and the controller drives the §6.2 lines 165-167 concurrent-workspace drains itself, from the pod uptime against the pool's `maxPodUptimeSeconds` (lines 166-167) and from a gateway-stamped `lenny.dev/drain-request` Pod annotation on the unhealthy-threshold trigger (line 165). The generic occupancy path emits `idle` for a `Sandbox` currently in a warm-inventory phase or a concurrent-workspace `slot_active` `Sandbox` with no live claim, and does not overwrite an in-flight `draining` or terminal phase; the task-mode disposition is report-driven through the `cleanupReport` branch rather than existence-driven. The coarse `lenny.dev/state` label projection (`syncPodStateLabel`) is unchanged in mechanism; its phase input now comes from the claim-existence projection rather than from a gateway write.

The gateway records the session-terminal disposition on its own surface. `SandboxClaim.status.phase` is the gateway-owned binding state (`spec/04_system-components.md:590`). The current §4.6.3 `released`/`failed` bullets (`spec/04_system-components.md:593-594`) describe a referenced `Sandbox` that has already transitioned to `idle` or `draining`/`terminated` at the moment `released`/`failed` is recorded, and a claim deleted shortly after entering `released` or right after the Postgres persist; this design reverses that ordering, so Section 7.6 restages both bullets. On session completion or failure the gateway sets `SandboxClaim.status.phase` to `released` or `failed` rather than writing `Sandbox.status`, the referenced `Sandbox.status.phase` is still at its session-terminal phase when the gateway records that disposition, and the claim survives until the WarmPoolController has driven the session-mode pod through `draining → terminated`. No production code writes `SandboxClaim.status.phase` today: the `SandboxClaim` phase type at `pkg/sandboxclaim/state/state.go:20` ("State is the SandboxClaim phase, written to `SandboxClaim.status.phase`") has zero production importers, and the only `SandboxClaim` writes in the gateway claim path are the CREATE/DELETE in `pkg/gateway/podclaim/claimer.go`, which set `spec` only. (`pkg/podregistry/crd.go` writes `Sandbox.status.phase`, a different subresource on a different CRD, and references `SandboxClaim` nowhere.) The gateway gains the `SandboxClaim.status.phase` writer as net-new work in the claim/release path.

## 4. Detailed design

### 4.1 Removing the gateway `Sandbox.status` writers

The gateway writers to remove are `ApplyGatewayPhase` and the phase-setting in `gatewayStatusPatch` (`pkg/gateway/podclaim/gatewaystatus.go`), the `claimer.go:114` phase write (the `SandboxClaim` CREATE at `claimer.go:103` is the claim mechanism and remains), the slot-reservation and slot-release SSA phase writes (`slotclaimer.go:549-551`, `:686-688`), the session-mode drain `Status().Update` (`binder.go:780-801` `b.drain`), the concurrent-mode uptime drain `Status().Update` (`slotclaimer.go:295-310` `drainExpiredPod`, the §6.2 lines 166-167 `slot_active → draining` and `idle → draining` over-uptime drain per its doc comment at `slotclaimer.go:286-294`), the concurrent-mode whole-pod unhealthy drain `Status().Update` (`pkg/gateway/podsession/slotbinder.go:382-405`, `DrainSandbox`, called from `pkg/gateway/sessionserver/start.go:1354` on the §6.2 line 165 / §5.2 `spec/05_runtime-registry-and-pool-model.md:531` whole-pod replacement trigger), the binder `setPhase` chain and `failPhase` Apply (`binder.go:739-748`, `:757`), the suspend Apply (`binder.go:1537`), and the fallback-claim phase Apply (`binder.go:1414-1417`). The session and task lifecycle these phases tracked is already maintained in the Postgres session store the gateway owns (§7.2, §8.8); §15 (`spec/15_external-api-surface.md:626`) already returns only session/task-model states from `GET /v1/sessions/{id}` and never the §6.2 pod phases.

Removing `drainExpiredPod` and `DrainSandbox` leaves the three concurrent-workspace drain transitions at §6.2 lines 165-167 with no writer. These triggers do not correspond to a single `SandboxClaim` reaching a terminal disposition: §6.2 line 165 fires on the gateway's rolling per-pod fail-or-leak count crossing `ceil(maxConcurrent/2)` while the pod typically still holds live slots; §6.2 line 166 fires on `maxPodUptimeSeconds` against the pod `CreationTimestamp` while slots are live; and §6.2 line 167 fires on `maxPodUptimeSeconds` against an idle pod with zero claims. Their writer is relocated to the WarmPoolController as part of the occupancy projection (Section 4.2), because the controller is the sole writer of `Sandbox.status.phase` and already reads the inputs both triggers need. The uptime drains (§6.2 lines 166-167) become a WarmPoolController-derived transition: the controller reads the pod `CreationTimestamp` (`pod_reconciler.go:383,433`) against the `ConcurrentWorkspacePolicy.MaxPodUptimeSeconds` the PoolScalingController already stamps on the pool (`pkg/controller/poolscaling/poolstoresource.go:83-85`) and emits `slot_active → draining` or `idle → draining`. The unhealthy drain (§6.2 line 165) keeps a gateway-owned signal because the fail-or-leak count is observed by the gateway: the gateway stamps a `lenny.dev/drain-request` annotation on the agent Pod when the rolling count crosses the threshold (the gateway already holds `patch` on `Pods` at `spec/04_system-components.md:588`, and the WarmPoolController already watches the backing Pod via `Owns(&Pod{})` at `controller.go:716`), and the WarmPoolController reconciles that annotation into `slot_active → draining`. This reuses the existing gateway Pod-patch grant and the existing controller Pod watch, adding no new RBAC surface or CRD field. The session-mode drain (`b.drain`) is the only drain whose disposition the gateway records on `SandboxClaim.status.phase`.

The session-terminal disposition that the removed session-mode drain (`b.drain`) recorded moves to `SandboxClaim.status.phase` (the gateway-owned binding surface, `spec/04_system-components.md:590`). On session completion, cancellation, or expiry the gateway sets `SandboxClaim.status.phase` to `released`, and on session failure it sets `failed`, per the §4.6.3 enumeration at `spec/04_system-components.md:593-595`. The WarmPoolController occupancy projection (Section 4.2) reads that terminal disposition and drives the session-mode pod through `draining → terminated` along the legal `state.ValidTransitions` edges (`pkg/sandbox/state/state.go:243-245,258-261`), preserving the §6.2 one-session-only invariant (`spec/06_warm-pod-model.md:24`) that a settled session-mode pod is terminated and replaced rather than recycled to `idle`. The claim survives until the WarmPoolController reaches `terminated`; only then does the gateway delete it. The concurrent-mode drains do not flow through this claim-disposition path: their writer is the WarmPoolController-derived uptime check and the gateway-stamped `lenny.dev/drain-request` Pod annotation described above, both of which the occupancy projection reconciles.

The chart edit narrows the `sandboxes/status` rule (`gateway-deployment.yaml:130-132`) from `get`/`update`/`patch` to `get`/`patch`, scoped to the `Sandbox.status.conditions` Terminated/Suspended writes the gateway still performs (open decision 2; `update` is dropped because the condition writes use server-side apply, which needs `get`/`patch`). On the `sandboxes` main resource (`gateway-deployment.yaml:122-129`) the chart drops both `patch` and `watch`, leaving `get`/`list`. The `watch` verb is dropped because the gateway holds no `Sandbox` informer or watch in code (no `Sandbox` Watch/Informer exists in `pkg/gateway`), and §4.6.3:588 grants the gateway only `get`/`list` on `Sandbox`; retaining `watch` would leave the chart over `spec/04_system-components.md:588` as-written. The gateway's §5.2 tenant pin is stamped on the agent Pod label `lenny.dev/tenant-id` (`stampPodTenant`, `slotclaimer.go:102-117`, backed by the existing gateway `patch` on `Pods` at `spec/04_system-components.md:588`); the redundant SSA label write on the `Sandbox` main resource (`slotclaimer.go:588-606`) is removed so the gateway needs no `patch` on `Sandbox`. The §4.6.3 gateway RBAC paragraph at `spec/04_system-components.md:588` grants the gateway `get`/`list` on `Sandbox` with mutations limited to Pod labels and `SandboxClaim`, so dropping the `sandboxes` `patch` and `watch` verbs converges the chart's `Sandbox` main-resource grants to that paragraph's `get`/`list` as-written. The RBAC additions are the gateway `sandboxclaims/status` subresource grant for the net-new binding-disposition write, staged in §4.6.3:588 in Section 7.1. The chart RBAC change and the code-writer change ship together: removing a grant while the code still issues the writes would return HTTP 403 from the running gateway, which is why the `sandboxes/status` grant is narrowed rather than removed while open decision 2 keeps the condition writes in the gateway.

### 4.2 Occupancy as a claim-existence projection

The WarmPoolController watches `SandboxClaim` and sets `Sandbox.status.phase` to the occupancy value as a level-triggered reconciliation of claim existence, claim disposition, and lifecycle policy. The projection branches on `Sandbox.spec.executionMode` (enum `session;task;concurrent`, `pkg/apis/lenny/v1alpha1/sandbox_types.go:45`). A never-bound warm `Sandbox` in a warm-inventory phase (`warming`, `sdk_connecting`, `idle`) referenced by no claim reads `idle`; a `Sandbox` referenced by one or more live claims (`SandboxClaim.status.phase` of `bound` or `active`) reads `claimed` (session mode or task mode, both of which take the whole-pod claim path through `Claimer.Claim` at `pkg/gateway/sessionserver/start.go:1186`) or `slot_active` (concurrent mode). The generic `claimed` write for a task-mode `Sandbox` is conditioned on the disposition state, so it does not re-promote a pod recycled into the idle-between-tasks window: a task-mode pod whose claim carries a present `cleanupReport` that has been consumed (the claim has a non-empty `SandboxClaim.status.cleanupReport.taskId` and `Sandbox.status.taskState.lastTaskId == SandboxClaim.status.cleanupReport.taskId`) holds the disposition-written phase (`idle` or `sdk_connecting`) rather than reading `claimed`, because the per-session claim remains `bound`/`active` while the pod awaits its next task. The `cleanupReport` is written by the gateway at task completion (on the adapter's `ReportTaskCleanup phase: result`, Section 4.6), not at task dispatch, so it cannot signal a freshly dispatched task on its own. The gateway therefore clears `SandboxClaim.status.cleanupReport` on the live claim when it re-dispatches the session's next task (a write on the gateway-owned `sandboxclaims/status` subresource it already uses for `cleanupReport`); with no consumed `cleanupReport` present, the generic `claimed` write fires for the duration of the dispatched task's execution. The generic `claimed` write therefore fires for a task-mode pod on the initial claim (no `cleanupReport` yet) and across each subsequent task's execution (the gateway has cleared the prior task's `cleanupReport` at re-dispatch, so the consumed-disposition condition is false until that task's own `phase: result` writes a new `cleanupReport` and its disposition runs); a pod recycled to `idle`/`sdk_connecting` by a consumed disposition is left at that phase only in the idle-between-tasks window, until the gateway re-dispatches the next task and clears the report.

A session-mode `Sandbox` whose referencing claim has reached a terminal disposition (`SandboxClaim.status.phase` of `released` or `failed`) is driven through its terminal phase to `draining` and then `terminated` along the `state.ValidTransitions` edges (`pkg/sandbox/state/state.go:243-245,258-261`: `{Claimed,Draining}`, `{Attached,Draining}`, `{Draining,Terminated}`, and the four session-terminal `{Completed,Draining}`/`{Failed,Draining}`/`{Cancelled,Draining}`/`{Expired,Draining}` edges), never back to `idle`; this is the §6.2 one-session-only invariant (`spec/06_warm-pod-model.md:24`), and the projection that follows it replaces the gateway's removed `b.drain` write (`binder.go:780-801`). The session-mode pod is never recycled to `idle`: no `{Attached,Idle}` edge exists in `state.ValidTransitions` (`pkg/sandbox/state/state.go:155-262`), the net-new `{Claimed,Idle}` edge that Section 7.9 stages is gated to `executionMode: task` by the projection (so it never fires for a session-mode pod), and the projection emits `idle` from a session-mode `claimed` value only for the warm-inventory and concurrent-recycle cases below, never for the session-mode terminal-disposition path.

A task-mode `Sandbox` reads `claimed` while a live claim references it. Its between-task disposition is computed by the WarmPoolController from the relayed scrub report rather than from claim existence alone; the full design and crash-recovery cases are in Section 4.6. §6.2 routes the between-task boundary through `task_cleanup` to exactly one of four dispositions: `idle` for a non-preConnect pod (`spec/06_warm-pod-model.md:147`), `sdk_connecting → idle` for a preConnect pod so the returned idle pod is SDK-warm (`spec/06_warm-pod-model.md:154`, preserving the invariant at `spec/06_warm-pod-model.md:183`), `draining` when `maxTasksPerPod`, `maxScrubFailures`, or `maxPodUptimeSeconds` is reached (`spec/06_warm-pod-model.md:149-151`), and `failed` under `onCleanupFailure: fail` (`spec/06_warm-pod-model.md:156`). The disposition function `taskcleanup.Decide` selects among them from the scrub outcome, the cumulative scrub-failure count, the task count, the uptime, and the pool's `preConnect` capability (`pkg/sandbox/taskcleanup/taskcleanup.go:64-110,173-266`; the test at `pkg/gateway/taskdriver/taskdriver_test.go:147-148` asserts the preConnect reuse phase is `sdk_connecting`). The generic occupancy projection cannot read those inputs from claim existence: its inputs are the `executionMode`, the claim set, the claims' `status.phase`, the pod `CreationTimestamp` against the pool uptime cap, and the `lenny.dev/drain-request` Pod annotation. The relay supplies the rest: the scrub outcome arrives on `SandboxClaim.status.cleanupReport`, the counters live on `Sandbox.status.taskState`, and the `preConnect` capability is on the pool `TaskPolicy` (all readable by the WarmPoolController, which reconciles the pool). A task-mode claim carrying an unconsumed `cleanupReport` (`taskState.lastTaskId != cleanupReport.taskId`) is therefore report-driven for that task (the WarmPoolController runs `Decide` and writes the disposition while the per-session claim stays `bound`/`active`); a session-mode or terminal-disposition claim drives the generic existence-driven occupancy path. The disposition writer moves the pod off `claimed` to the `Decide` target (`idle`, `sdk_connecting`, `draining`, or `failed`) directly, along the net-new task-mode-gated `{Claimed, Idle}`, `{Claimed, SDKConnecting}`, and `{Claimed, Failed}` edges that Section 7.9 stages in `state.ValidTransitions` (the `draining` retirement reuses the existing `{Claimed, Draining}` edge at `pkg/sandbox/state/state.go:243`); these three edges are gated to `executionMode: task` by the projection, mirroring the existing task-mode-only `{Cancelled, TaskCleanup}` edge, so a session-mode pod has no `claimed → idle` recycle. The `lenny.dev/task-disposition` finalizer (Section 4.6) stays on the per-session claim for the whole session and is removed only at session termination after the final report is consumed, so a claim deletion never lets the generic existence path fire a coarse `claimed → idle` recycle that would bypass the spec's `maxTasksPerPod` (`spec/05_runtime-registry-and-pool-model.md:451`), `maxScrubFailures` (`:453`), and `onCleanupFailure: fail` (`spec/06_warm-pod-model.md:156`) controls or hand a preConnect pod back to `idle` without the SDK re-warm.

A concurrent-workspace `Sandbox` recycles rather than terminates, because concurrent mode is not one-session-only. When a concurrent-mode `Sandbox` in `slot_active` has zero live referencing claims and is healthy, the projection reconciles it back to `idle` along the `{SlotActive,Idle}` edge (`state.go:232`, the §6.2 line 164 `slot_active → idle` recycle), replacing the gateway's removed slot-release recycle write (`slotclaimer.go:680-688`). The concurrent-workspace drains at §6.2 lines 165-167 are written by the projection from the relocated triggers in Section 4.1: a `slot_active` `Sandbox` carrying the gateway-stamped `lenny.dev/drain-request` annotation (§6.2 line 165 unhealthy threshold) or exceeding `ConcurrentWorkspacePolicy.MaxPodUptimeSeconds` against its pod `CreationTimestamp` (§6.2 line 166) reconciles to `draining` along `{SlotActive,Draining}` (`state.go:233`), and an idle concurrent-workspace `Sandbox` exceeding the uptime cap (§6.2 line 167) reconciles to `draining` along `{Idle,Draining}` (`state.go:242`); from `draining` the existing `{Draining,Terminated}` edge retires the pod once its slots have drained.

The generic existence-driven projection emits `idle` only for a `Sandbox` currently in a warm-inventory phase (`warming`, `sdk_connecting`, `idle`) or a concurrent-mode `slot_active` `Sandbox` with zero live claims, and it never overwrites an in-flight `draining` or terminal phase. It does not recycle a task-mode `claimed` `Sandbox` from claim existence, and it does not re-promote a recycled-to-`idle` or `sdk_connecting` task-mode `Sandbox` back to `claimed` while that claim's present `cleanupReport` is still consumed (a non-empty `cleanupReport.taskId` with `taskState.lastTaskId == cleanupReport.taskId`); the task-mode between-task disposition is the report-driven branch in Section 4.6, and the recycled pod holds its disposition-written phase through the idle-between-tasks window, until the gateway re-dispatches the next task and clears `cleanupReport`, at which point the generic `claimed` write fires for that task's execution. The watch is added at `controller.go:714-719` as `Watches(&SandboxClaim{}, ...)` with a handler that maps a claim to its referenced `Sandbox` via `.spec.sandboxRef`. The occupancy phase is computed in the `Sandbox` reconciler from the `executionMode`, the claim set, the claims' `status.phase`, the claim's `status.cleanupReport` (for the task-mode branch), the pod `CreationTimestamp` against the pool uptime cap, and the `lenny.dev/drain-request` Pod annotation; `syncPodStateLabel` (`:496-516`) keeps its role as the downstream label projection. The WarmPoolController RBAC paragraph at `spec/04_system-components.md:586` already grants `list`/`delete` on `SandboxClaim`; the projection adds `get`/`watch`/`update` so the controller can read individual claims, react to claim create, status, and delete events, and add and remove the `lenny.dev/task-disposition` finalizer (a metadata write on the claim, which needs `update`).

### 4.3 Admission guard re-pointing (bound to the fine-phase decision)

The `lenny-sandboxclaim-guard` CREATE single-claim check (deterministic `claim-<sessionID>` name plus existing-claim scan, `claimer.go:140-164`; `pkg/admission/sandboxclaim_guard/guard.go`) is authoritative and unchanged. The guard's PATCH/PUT stale-write check reads `Sandbox.status.phase` against `claimBoundPhases` (`guard.go:94-102`, `:259`), and the slot_active CREATE exemption reads it at `:230`. The webhook reads the phase generically via `referencedSandboxPhase` (`pkg/admission/webhook/sandboxclaim_guard.go:55-72`, `:110-122`), so no read site needs re-pointing.

The whole-pod candidate scan at `pkg/gateway/podclaim/claimer.go:92` reads `sb.Status.Phase != string(state.Idle)` to skip non-idle pods for session-mode and task-mode claims. Its predicate is unchanged: with the gateway no longer writing the `claimed` phase, the scan now reads the WarmPoolController-written occupancy projection (Section 4.2), which writes `claimed` for both a session-mode and a task-mode `Sandbox` holding a live claim, so a claimed pod of either mode still reads a non-`idle` phase and the scan skips it. The occupancy flip is now an async WarmPoolController reconcile rather than a synchronous gateway write, so the scan can briefly observe a pod as `idle` between the gateway's `SandboxClaim` CREATE and the controller's `claimed` write. The deterministic `claim-<sessionID>` CREATE and the existing-claim scan in the `lenny-sandboxclaim-guard` webhook (`guard.go:233-241`) remain the authoritative double-claim defense (`spec/04_system-components.md:384`): a second claim CREATE against an already-claimed pod is rejected at admission regardless of the occupancy phase the scan observed, so the async flip does not regress double-claim safety. The candidate scan is an availability optimization that selects a likely-idle pod; the CREATE guard is the correctness gate.

The guard's dependence on the fine phases is in the `claimBoundPhases` accept-set, which commits `2b203384` and `e0d19877` expanded to `{claimed, receiving_uploads, finalizing_workspace, running_setup, starting_session, attached, slot_active}` for F-6.2.7, because the §6.2 claim→setup→attached chain (`spec/06_warm-pod-model.md:84-93`) legitimately moves a claimed-and-bound pod through those phases. The guard test at `pkg/admission/sandboxclaim_guard/guard_test.go:216-239` asserts a PATCH/PUT against a `Sandbox` in any of that set is allowed.

The guard change follows mechanically from the fine-phase decision in Section 11 and is not an independent decision:

- If the reviewer accepts the fine-phase relocation, reduce `claimBoundPhases` to `{claimed, slot_active}`, update the matching test to the reduced set, and tighten the parenthetical example at `spec/04_system-components.md:591` to drop the `receiving_uploads`/`attached`/`running` examples that no longer name `Sandbox` phases. The narrative at `:384` already reads "not `claimed`" and needs no edit.
- If the reviewer declines the relocation, the accept-set stays as-is. Reducing `claimBoundPhases` without first removing the fine phases would regress F-6.2.7 by rejecting legitimate PATCH/PUT writes during the §6.2 setup chain and would break the existing guard test.

### 4.4 The concurrent-slot cap after the gateway write removal

The §5.2 atomic Redis Lua counter (`spec/05_runtime-registry-and-pool-model.md:519`) is the single cap mechanism for concurrent-mode pods, reinforced by `spec/06_warm-pod-model.md:197` ("the atomic Redis `INCR` gates assignment"). The spec describes no SSA-only or claim-counting cap path. The `Counter==nil` else-branch at `slotclaimer.go:510-518`, the SSA compare-and-swap conflict undo at `:553-557`, and the `Counter==nil` hard-error branch at `:562-565` are removed; a nil `Counter` for a concurrent-mode claim returns an explicit configuration error rather than silently falling back. Tests that exercised the SSA single-writer path wire a real or fake `Counter` (the rehydration unit tests already construct `slotcounter.New` against a Redis double, and `memstore` implements `GetActiveSlotsByPod` at `pkg/gateway/sessionstore/memstore/memstore.go:271-275`), so the test-only justification for the branch disappears.

The candidate-selection scan at `slotclaimer.go:374,377` reads `status.Phase == slot_active` and `status.ActiveSlots`. With the gateway no longer writing those fields, the scan is re-pointed onto the claim-existence projection (Section 4.2). This is required regardless of which cap remedy is chosen, because the scan reads a field the gateway stops writing. The scan's own uptime drain (`expiredByUptime` plus `drainExpiredPod` at `slotclaimer.go:387-394` and `:415-423`) is also removed: the WarmPoolController now writes the §6.2 lines 166-167 uptime drains, so an over-uptime pod already reads `draining` in the projection and the scan excludes it through the `slot_active` filter without issuing a drain itself.

The concurrent-mode application-layer tenant pin (§5.2 item 1, `spec/05_runtime-registry-and-pool-model.md:498`, and the task-mode form at `:391`) is enforced today by reading `sb.Status.TenantID` at `slotclaimer.go:382` (the candidate scan pre-filter) and `:480` (`reserveSlot`), and by writing it through the removed gateway status patches (`slotclaimer.go:549-551`, `:686-687`). With the gateway no longer writing `Sandbox.status.tenantId`, the authoritative pin surface is the `lenny.dev/tenant-id` label the gateway stamps on the agent Pod (`stampPodTenant`, `slotclaimer.go:102-117`), which the `lenny-tenant-label-immutability` webhook backstops (`spec/05_runtime-registry-and-pool-model.md:392`). The pin check moves into `reserveSlot`, which reads the candidate Pod's `lenny.dev/tenant-id` label via the gateway's existing `get` on `Pods` (`spec/04_system-components.md:588`) before reserving the slot and returns the existing `conflict` signal on a mismatch so the scan tries the next pod; the cheap `sb.Status.TenantID` pre-filter at `:382` is dropped because `Sandbox.status.tenantId` is no longer written. `ErrTenantMismatch` is derived from `reserveSlot` returning a tenant mismatch on every candidate rather than from the dropped pre-filter. This relocation keeps the §5.2 layer-1 pin intact after the gateway status write is removed and requires no `patch` on the `Sandbox` resource.

### 4.5 `Sandbox.status.activeSlots` after the cap change

With the Redis counter authoritative and the gateway no longer writing, `Sandbox.status.activeSlots` is no longer a gateway write. ### 4.6 The task-mode disposition: scrub-Result relay and claim-finalizer handshake (F-5.2.30)

**The seam: adapter → gateway → WarmPoolController.** A task-mode session runs multiple sequential tasks on one pod under one `SandboxClaim` (`claim-<sessionID>`, created once at session start; the SDK receives a new `TaskID` under the same `SessionID` after each `task_ready` signal, `spec/15_external-api-surface.md:2568-2573`, and the pod cycles between `idle` and `attached` for up to `maxTasksPerPod` tasks, `spec/05_runtime-registry-and-pool-model.md:415,451`). The claim lifecycle is per session; the between-task disposition fires per task. On each task's completion the adapter runs the §5.2 scrub in-pod (`pkg/adapter/scrub`, adapter-internal and unchanged), producing a binary scrub `Result` (`succeeded` or `failed`, matching `pkg/adapter/scrub.Result`). The warn-versus-fail disposition is derived downstream by the WarmPoolController from a failed scrub plus the pool `onCleanupFailure` policy rather than reported by the adapter. The disposition (recycle the pod to the pool versus retire it) is an inventory decision and therefore the WarmPoolController's, but the scrub `Result` originates in the adapter, which has no Kubernetes client (§10.3). It is relayed in three hops (the first hop carries two phases: a cleanup-start signal and the scrub result):

1. The adapter reports to the gateway via a new two-phase `ReportTaskCleanup` RPC on the existing adapter→gateway `GatewayControl` service (the `ExtendLease` Adapter→Gateway precedent in §4.7; `schemas/lenny-adapter.proto` service `GatewayControl`). The request carries the `sessionId`, the `taskId`, a `phase` (`started` or `result`), and the binary scrub `Result` (`succeeded` or `failed`, matching the adapter's `pkg/adapter/scrub.Result`) on the `result` phase; the response acks. The `sessionId` is how the gateway resolves the per-session binding claim `claim-<sessionID>` to patch: the claim is named deterministically per session (`claimName(sessionID) = "claim-" + sessionID`, `pkg/gateway/podclaim/claimer.go:160-163`) and `taskId` is distinct from `sessionId` in task mode (the SDK receives a new `TaskID` under the same `SessionID` after each task, `spec/15_external-api-surface.md:2568-2573`), so the adapter passes the `sessionId` explicitly, exactly as it does for `ExtendLease` (`pkg/adapter/gatewaycontrol/gatewaycontrol.go:204-206`). The adapter reports the binary scrub outcome only; the warn-versus-fail disposition is derived downstream by the WarmPoolController from a failed scrub plus the pool `onCleanupFailure` policy, because the adapter does not know that policy. The RPC is idempotent: a retry of either phase with the same `taskId` is safe.
2. The two phases land at different points in the cleanup. The `task_complete` / `task_complete_acknowledged` exchange runs over the intra-pod `@lenny-lifecycle` socket between the adapter and the runtime (§4.7); the adapter listens and the runtime connects as a client, and the gateway is not a party and observes no cleanup-start signal. The adapter is therefore the originator of the cleanup-start marker: immediately after the runtime returns `task_complete_acknowledged` and before the adapter runs `cleanupCommands` and the Lenny scrub, the adapter sends `ReportTaskCleanup` with `phase: started` carrying the task's `taskId`, and the gateway sets `SandboxClaim.status.cleanupStartedAt {taskId, at}` (a per-task structure on the gateway-owned `SandboxClaim.status` subresource) so the WarmPoolController can arm the `task_cleanup` watchdog from a signal the gateway actually receives and correlate it to the in-flight task. After the scrub completes the adapter sends `ReportTaskCleanup` with `phase: result`, carrying the binary scrub `Result`; the gateway writes the outcome onto the live `claim-<sessionID>` as a per-task `SandboxClaim.status.cleanupReport {taskId, outcome}` field (the gateway already owns `SandboxClaim.status` per the §4.6.3 table) and leaves the claim binding phase at `bound`/`active` so the claim survives for the session's next task. The gateway sets the claim phase to `released`/`failed` and deletes the claim only at session termination (Section 4.1); the per-task boundary leaves the claim live. The gateway writes nothing on `Sandbox.status`.
3. The WarmPoolController already watches `SandboxClaim` for the occupancy projection (Section 4.2); that reconcile is extended. For a task-mode claim carrying `cleanupReport`, the WarmPoolController reads the report plus the pool `TaskPolicy` (`maxTasksPerPod`, `maxScrubFailures`, `maxPodUptimeSeconds`, `onCleanupFailure`, and the runtime `preConnect` capability, all readable by the WarmPoolController, which reconciles the pool), the cumulative counters on `Sandbox.status.taskState`, the pod uptime from the pod `CreationTimestamp`, and the `lenny.dev/host-schedulable` label, which the WarmPoolController already maintains from its Node informer cache and now reads directly at disposition time rather than surfacing to the gateway (§6.2 line 181, restaged in Section 7.9 Anchor 3, and §4.6.1 line 481, restaged in Section 7.2, both re-attributing the label read and the `task_cleanup` precondition from the gateway to the WarmPoolController).
4. The WarmPoolController runs `taskcleanup.Decide` (a pure function with no Kubernetes client, `pkg/sandbox/taskcleanup/taskcleanup.go:18-23`; this relocates the decision from the gateway task path to the WarmPoolController and leaves the function unchanged) and writes the disposition on `Sandbox.status` in one SSA Apply under its own field manager: the disposition phase (`idle` for a non-preConnect recycle, `sdk_connecting` for a preConnect re-warm, `draining` or `failed` for retirement), the incremented `taskState` counters, and the `scrub_warning` annotation on a warn outcome. The phase is written directly from the projected `claimed` occupancy value along the net-new task-mode-gated `claimed → {idle, sdk_connecting, failed}` edges (and the existing `{Claimed, Draining}` edge for `draining`) that Section 7.9 stages in `state.ValidTransitions` and the §6.2 fenced diagram; the `Decide` branch over these targets matches the §6.2 `task_cleanup → {idle, sdk_connecting, draining, failed}` table at `spec/06_warm-pod-model.md:147-156` without the WarmPoolController writing the fine `task_cleanup` phase.

**Counters home (resolves the prior counter-store open decision).** `Sandbox.status.taskState` holds `tasksCompleted`, `scrubFailureCount`, `lastTaskId`, `lastDisposition`, and `lastScrubWarning`, WarmPoolController-written as a read-modify-write atomic with the disposition phase in the same SSA Apply. One actor reads and writes both the counters and the phase, which is why this is cleaner than a gateway-owned counter that a second actor would have to read. The WarmPoolController mirrors `tasksCompleted`/`scrubFailureCount` into the net-new `agent_pod_state` `tasks_completed`/`scrub_failure_count` columns (the §12 mirror contract; Section 7.12 stages both the columns and the mirror sentence). The prior counter-store open decision is resolved to `Sandbox.status.taskState`, WPC-owned.

**The per-task disposition loop and the claim-finalizer handshake.** The disposition runs once per task off the per-task `cleanupReport` while the per-session claim stays `bound`/`active`. A `lenny.dev/task-disposition` finalizer, added by the WarmPoolController on task-mode claims, guarantees the last task's report is consumed before the per-session binding record is deleted and keeps the generic "claim gone → recycle to idle" occupancy projection from firing the wrong outcome for a task-mode pod. The per-task happy path:

- The WarmPoolController adds the finalizer on first observing a task-mode claim. It stays on the claim for the whole session.
- The gateway writes the task's `cleanupReport {taskId, outcome}` on the live claim and leaves the claim phase at `bound`/`active`. It does not delete the claim.
- The WarmPoolController reconciles. The idempotency check: if `taskState.lastTaskId == report.taskId` the disposition for this task already ran, so it does nothing; otherwise it runs `Decide`, writes the disposition Apply (recycle `idle`/`sdk_connecting` or retire `draining`/`failed`), and records `taskState.lastTaskId = report.taskId`.
- On a recycle disposition the claim is unchanged and the pod holds the recycle phase (`idle` or `sdk_connecting`) through the idle-between-tasks window. When the gateway re-dispatches the session's next task it clears `cleanupReport` on the live claim before the next task runs, so the occupancy projection reads `claimed` for that task's execution (Section 4.2) rather than leaving the pod at the recycle phase while it is busy; the next task's `phase: result` then writes a fresh `cleanupReport` and the disposition runs again. On a retire disposition the pod is being terminated and the session is over; the gateway sets the claim phase to `released`/`failed` and the per-session deletion handshake below runs.

The per-session deletion handshake at session termination:

- The gateway sets the claim phase to `released`/`failed` and calls `Delete` (the client ended the session, or the WarmPoolController retired the pod on the last task's disposition).
- The finalizer holds the claim in `Terminating` until the WarmPoolController has consumed any pending final-task `cleanupReport` (the idempotency check above) and written the terminal disposition.
- The WarmPoolController removes the finalizer, and Kubernetes garbage-collects the claim.

**Crash recovery.** The handshake is durable across a crash of either actor:

- (a) **Gateway dies after the cleanup-start marker but before writing the report.** The gateway has received the adapter's `phase: started` and set `SandboxClaim.status.cleanupStartedAt {taskId, at}` for the in-flight task, which is not yet disposed (`cleanupStartedAt.taskId != taskState.lastTaskId`), so the WarmPoolController-side `task_cleanup` watchdog is armed at `cleanupStartedAt.at + taskCleanupTimeoutSeconds`; if no report for that task arrives by the deadline (`cleanupReport.taskId != cleanupStartedAt.taskId`) it fail-safe retires the pod to `draining`. The adapter may retry the idempotent `ReportTaskCleanup` result against a recovered gateway, which writes the report (`cleanupReport.taskId == cleanupStartedAt.taskId`) before the deadline and the disposition runs normally. A gateway that dies before receiving the `phase: started` signal has no `cleanupStartedAt` for the in-flight task on the claim, so the watchdog never arms; the pod is still serving the task at `bound`/`active` from the WarmPoolController's perspective, and that case is the session-recovery path (the claim's lease expiry and orphan-claim garbage collection) rather than the between-task watchdog.
- (b) **Gateway dies after writing a final-task report but before `Delete` at session termination.** The WarmPoolController's disposition trigger is "`cleanupReport` present" rather than "claim terminating", so it disposes off the report regardless of the claim's deletion state. If the disposition retires the pod, the claim is then reaped by the gateway's normal release or the 5-minute orphan-claim garbage collection.
- (c) **WarmPoolController dies after writing a task's disposition but before the next reconcile.** The post-restart list-and-sync sees `taskState.lastTaskId == report.taskId` and skips re-deciding that task, so the counters are not double-incremented; a subsequent task's report carries a new `taskId` and disposes normally.
- (d) **WarmPoolController dies before disposing or before removing the finalizer at session termination.** The finalizer holds the durable claim, and the restart reconcile processes the pending report and removes the finalizer.

The WarmPoolController's claim reconcile branches: a task-mode claim carrying an unconsumed `cleanupReport` (`taskState.lastTaskId != report.taskId`) is report-driven (run `Decide`); a session-mode or terminal-disposition claim drives the generic existence-driven occupancy path (Section 4.2).

**The `task_cleanup` watchdog.** The WarmPoolController needs an observable signal that a task-mode pod has entered cleanup before the `cleanupReport` arrives, so it can arm the watchdog without misfiring on a pod still legitimately running a long task. The claim alone does not carry that signal: between `task_complete_acknowledged` and the `ReportTaskCleanup` result the claim sits at `bound`/`active` with no `cleanupReport`, indistinguishable from a long-running task. The gateway cannot derive the signal from the `task_complete` exchange, which is an intra-pod adapter↔runtime exchange on the `@lenny-lifecycle` socket (§4.7) that the gateway does not observe. The adapter therefore originates the cleanup-start marker over the relay: immediately after the runtime returns `task_complete_acknowledged` and before the adapter runs `cleanupCommands` and the scrub, the adapter sends `ReportTaskCleanup` with `phase: started` carrying the task's `taskId`, and the gateway sets `SandboxClaim.status.cleanupStartedAt {taskId, at}` (a per-task structure on the gateway-owned `SandboxClaim.status` subresource, alongside `cleanupReport`). The signal is per task: each task's `phase: started` overwrites `cleanupStartedAt` with that task's `taskId` and start timestamp. The WarmPoolController arms the watchdog only for a cleanup task that has not yet been disposed (`cleanupStartedAt.taskId != Sandbox.status.taskState.lastTaskId`), at `cleanupStartedAt.at + taskCleanupTimeoutSeconds` (`taskCleanupTimeoutSeconds` is a net-new per-pool `taskPolicy` field, operator-tunable, staged in §5.2 and the CRD). The `cleanupStartedAt.taskId != lastTaskId` arming guard is necessary because the gateway clears `cleanupReport` when it re-dispatches the next task (Section 4.2): after a task's disposition the gateway clears that task's report, so the stale `cleanupStartedAt` left over from the disposed task would otherwise satisfy a bare `cleanupReport.taskId != cleanupStartedAt.taskId` test at the already-elapsed deadline and falsely retire a pod healthily running the next task. Gating the arm on `cleanupStartedAt.taskId != lastTaskId` disarms the watchdog for any task already disposed and arms it only once the adapter has reported `phase: started` for a new, not-yet-disposed task. The watchdog fires per task rather than per claim: at the deadline of an armed task, if no report for that in-flight task has arrived (`cleanupReport.taskId != cleanupStartedAt.taskId`), the watchdog fail-safe retires the pod to `draining` along the existing `{Claimed, Draining}` edge rather than leaving it stranded in `claimed`. This is the lost-report backstop for crash case (a) and for an adapter that never reports the result (a crashed or wedged runtime). Because the clock starts at `cleanupStartedAt.at` rather than at claim creation, a long-running task that has not yet entered cleanup never arms the watchdog and is never falsely retired.

**Out of scope for this seam.** `maxTaskRetries` (pod crash mid-task) is session recovery: the gateway claims a fresh pod and re-dispatches the task from the beginning (§6.2 lines 185-192). That path stays gateway-side and is untouched here, because it is a recovery decision the gateway already owns rather than a between-task inventory disposition.

## 5. Why §10.3 and the gateway statelessness rule stay intact

The occupancy write and the task-mode disposition write are performed by the WarmPoolController from `lenny-system` with its existing apiserver access and its existing `Sandbox.status` write grants, so no agent-pod apiserver path is opened and the §10.3 zero-RBAC posture is unchanged. The `ReportTaskCleanup` relay does not open an agent-pod apiserver path either: the adapter dials the gateway's `GatewayControl` gRPC server (the same mTLS adapter→gateway link as `ExtendLease`), and only the gateway and the WarmPoolController touch the apiserver. The gateway's `lenny.dev/drain-request` annotation write for the §6.2 line 165 unhealthy drain uses the gateway's existing `patch` on `Pods` from `lenny-system`, so it opens no new RBAC surface. Moving the per-pod task counters from gateway process memory onto `Sandbox.status.taskState` (Section 4.6) takes state off the gateway, which the §10.1 statelessness rule (`spec/10_gateway-internals.md:5`) requires. The `lenny.dev/drain-request` annotation is derived from the gateway's in-memory rolling fail-or-leak counter, which is the concurrent-mode counter rather than a task-mode counter and is left in place for the concurrent drain path.

Both fields are per task: the gateway overwrites `cleanupStartedAt` with the new `taskId` and start time at each task's cleanup start, then writes that task's `cleanupReport` from the adapter's `ReportTaskCleanup` RPC ([Section 4.7](#47-runtime-adapter)). The gateway clears `cleanupReport` on the live claim when it re-dispatches the session's next task, so the WarmPoolController occupancy projection reads `claimed` for the duration of that task's execution rather than holding the pod at the prior recycle phase ([Section 4.6.1](#461-warm-pool-controller-pod-lifecycle) pod occupancy projection). The gateway leaves `status.phase` at `bound`/`active` across the between-task boundary, because one `claim-<sessionID>` spans the whole task-mode session; the gateway sets `status.phase` to `released`/`failed` and deletes the claim only at session termination. The WarmPoolController reads `cleanupReport`, derives the warn-versus-fail disposition from the binary outcome plus the pool `onCleanupFailure` policy, and runs the between-task disposition ([Section 4.6.1](#461-warm-pool-controller-pod-lifecycle) pod occupancy projection, [Section 5.2](05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes), [Section 6.2](06_warm-pod-model.md#62-pod-state-machine)): it writes the disposition phase and the `Sandbox.status.taskState` counters on `Sandbox.status` for each task while the claim stays live. When `cleanupStartedAt` is set for a not-yet-disposed task (`cleanupStartedAt.taskId != Sandbox.status.taskState.lastTaskId`) and no report for that task has arrived by `cleanupStartedAt.at + taskCleanupTimeoutSeconds` (`cleanupReport.taskId != cleanupStartedAt.taskId`), the WarmPoolController fail-safe retires the pod to `draining`. The arming guard against `lastTaskId` keeps the stale `cleanupStartedAt` of an already-disposed task, whose `cleanupReport` the gateway cleared at the next re-dispatch, from firing the watchdog against a pod healthily running the next task. The finalizer is WarmPoolController-added when it first observes a task-mode claim and stays on the claim for the whole session; it is WarmPoolController-removed at session termination after the final task's report is consumed, so the per-session binding record is not garbage-collected before the last disposition runs, and it keeps the generic claim-existence occupancy projection from recycling a task-mode pod to `idle` ahead of the disposition. The disposition is idempotent against `Sandbox.status.taskState.lastTaskId`: a reconcile that observes `lastTaskId == cleanupReport.taskId` has already disposed that task and does nothing further for it.

```proto
// ReportTaskCleanup is the adapter's two-phase report of the §5.2
// between-task cleanup to the gateway, so the WarmPoolController can
// decide the pod's between-task disposition. The adapter has no
// Kubernetes client (spec §10.3), and the gateway does not observe the
// intra-pod task_complete / task_complete_acknowledged exchange on the
// @lenny-lifecycle socket, so the adapter is the only party that can
// signal cleanup-start to the gateway. The adapter sends phase=STARTED
// immediately after the runtime returns task_complete_acknowledged and
// before it runs cleanupCommands and the Lenny scrub, carrying the task's
// task_id; the gateway writes SandboxClaim.status.cleanupStartedAt
// {taskId, at}, the per-task cleanup-start signal the WarmPoolController
// uses to arm the task_cleanup watchdog and correlate the deadline to the
// in-flight task (it fires when cleanupReport.taskId is not equal to
// cleanupStartedAt.taskId at the deadline). The adapter
// sends phase=RESULT after the scrub completes, carrying the binary
// scrub Result; the gateway writes the per-task
// SandboxClaim.status.cleanupReport on the live claim-<sessionID> and
// leaves the claim binding phase at bound/active so the per-session
// claim survives the between-task boundary, and the WarmPoolController
// reads it and derives the warn-versus-fail disposition. The gateway
// sets the claim phase to released/failed and deletes the claim only at
// session termination. Idempotent: a retry of either phase with the
// same task_id is safe. spec: §4.7, §5.2, §6.2.
rpc ReportTaskCleanup(ReportTaskCleanupRequest) returns (ReportTaskCleanupResponse) {}

message ReportTaskCleanupRequest {
  // session_id identifies the task-mode session so the gateway can
  // resolve the per-session binding claim claim-<sessionID> to patch.
  // The SandboxClaim is named deterministically per session
  // (claimName(sessionID) = "claim-" + sessionID), and in task mode the
  // SDK receives a new TaskID under the same SessionID after each task
  // (spec §15.1), so task_id is distinct from session_id and the gateway
  // holds no taskId->session index. This mirrors the ExtendLease
  // precedent, whose request carries SessionId session_id = 1 and whose
  // handler resolves identity from it (pkg/gateway/leasecontrol:
  // sessionID := req.GetSessionId().GetValue()).
  SessionId session_id = 1;
  // task_id is the in-flight task's id, carried on BOTH phases. On
  // phase=STARTED the gateway records it in
  // SandboxClaim.status.cleanupStartedAt {taskId, at} so the
  // WarmPoolController can correlate the watchdog deadline to the task;
  // on phase=RESULT it keys SandboxClaim.status.cleanupReport {taskId,
  // outcome}.
  string task_id = 2;
  // phase distinguishes the cleanup-start signal from the scrub result.
  ReportTaskCleanupPhase phase = 3;
  // outcome is the binary §5.2 scrub Result reported by the adapter:
  // SUCCEEDED or FAILED, matching pkg/adapter/scrub.Result
  // (succeeded/failed). It is set only on phase=RESULT. The adapter
  // reports the scrub outcome only; the warn-versus-fail disposition is
  // derived downstream by the WarmPoolController from a FAILED scrub plus
  // the pool onCleanupFailure policy via taskcleanup.Decide. The adapter
  // does not know onCleanupFailure and cannot distinguish a recyclable
  // warning from a retiring failure, so the relay carries the binary
  // scrub result rather than a pre-decided three-valued disposition.
  ScrubOutcome outcome = 4;
}

enum ReportTaskCleanupPhase {
  REPORT_TASK_CLEANUP_PHASE_UNSPECIFIED = 0;
  // STARTED: the adapter has received task_complete_acknowledged and is
  // about to run cleanupCommands and the scrub.
  REPORT_TASK_CLEANUP_PHASE_STARTED = 1;
  // RESULT: the scrub has completed; outcome carries the binary Result.
  REPORT_TASK_CLEANUP_PHASE_RESULT = 2;
}

enum ScrubOutcome {
  SCRUB_OUTCOME_UNSPECIFIED = 0;
  SCRUB_OUTCOME_SUCCEEDED = 1;
  SCRUB_OUTCOME_FAILED = 2;
}

message ReportTaskCleanupResponse {}
```

## 8. Non-goals

- Adding a tier-dependent or dual-mode code path. v1 ships one implementation; the gateway's `Sandbox.status` writers are deleted rather than gated.
- Adding a migration shim, legacy flag, or backward-compatibility path for the removed gateway carve-out. No deployments exist in the wild.
- Introducing a `/v1/tasks` ingestion route. Task-mode work is ingested through the existing session path against an `executionMode: task` pool (`spec/05_runtime-registry-and-pool-model.md:475`; `pkg/gateway/sessionserver/start.go`).
- Adding a new client-facing protocol surface. The cross-context seams are `SandboxClaim` existence and `SandboxClaim.status.cleanupReport` (both on the existing `SandboxClaim` CRD) and the `ReportTaskCleanup` RPC on the existing adapter→gateway `GatewayControl` service. None is client-facing: clients submit task-mode work through the session API and never see the relay.
- Relaxing the §10.3 agent-pod zero-RBAC posture. No agent-pod apiserver path is opened; the WarmPoolController performs the `Sandbox.status` write from `lenny-system`.
- Capping concurrent slots from anything other than the §5.2 Redis counter. The respecified-fallback alternative (re-sourcing the fallback cap to an active-`SandboxClaim` count) was considered and rejected: the spec describes a single atomic-`INCR` cap, the `Counter==nil` branch is non-spec-aligned by its own code comments (`slotclaimer.go:220-223`, `cmd/lenny-gateway/main.go:2444-2447`), and adding a second cap path would reintroduce the dual-mode pattern the single-implementation rule excludes. The branch is deleted instead.
- Reducing the `Sandbox.status.phase` enum and relocating session/task-lifecycle authority to Postgres as part of this change. The second-writer removal does not require it; the relocation is a reviewer-owned open decision (Section 11) with its own blast radius.
- Touching `maxTaskRetries` (a pod crash mid-task). That path is session recovery, not a between-task disposition: the gateway claims a fresh pod and re-dispatches the task from the beginning (`spec/06_warm-pod-model.md:185-192`). It stays gateway-side and is untouched by the relay; only the between-task disposition (recycle versus retire) moves to the WarmPoolController.
- Adding a gateway→controller control transport for the disposition. The relay reuses the existing surfaces: the adapter→gateway `GatewayControl` gRPC link (the `ExtendLease` precedent) carries the scrub `Result` to the gateway, and `SandboxClaim.status.cleanupReport` plus the WarmPoolController's existing `SandboxClaim` watch carry it to the controller. The gateway and the controller still interact only through the Kubernetes API.
