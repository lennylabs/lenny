# Proposal: Relocate the §8.6 budget-exhaustion lease-extension trigger from the adapter into the gateway LLM Proxy, scope it to proxy mode, and reconcile the §8.6-vs-§4.9 responsibility contradiction (close F-8.6.6 / F-15.3.6)

- **Status:** Verified (2026-07-01). Converged after 5 adversarial review rounds (11 findings fixed); awaiting sign-off.
- **Date:** 2026-07-01.
- **Scope:** Reconciles the §8.6 budget-exhaustion lease-extension trigger, which the spec assigns to the adapter but which the adapter can never fire because the adapter is not in the LLM request path (§4.9/§13.2), by relocating the trigger into the gateway LLM Proxy, delivering the exhausting call's already-computed response transparently, and scoping the automatic extension to proxy mode. It reconciles the §11.2-line-44 "terminate immediately" collision so a proxy-mode session attempts the §8.6 extension before termination, wires the in-process trigger through an injected consumer-defined interface, deletes the dead adapter-side `LeaseExtender` seam and the orphaned `ExtendLease` gRPC surface, and adds the test coverage across the tiers the change reaches. It closes `F-8.6.6` (the trigger cannot be implemented as written) and `F-15.3.6` (the dead adapter-side seam). It touches `spec/08_recursive-delegation.md`, `spec/04_system-components.md`, `spec/09_mcp-integration.md`, `spec/11_policy-and-controls.md`, `spec/18_build-sequence.md`, `spec/19_resolved-decisions.md`, `schemas/lenny-adapter.proto`, the gateway proxy, session-budget, and lease-control packages under `pkg/gateway`, `cmd/lenny-gateway`, the adapter packages under `pkg/adapter`, `pkg/proto/adapter/v1`, and the tests.

This document stages the proposed spec, code, and test changes for the implementation step. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

§8.6 (`spec/08_recursive-delegation.md:627,629`) is normative that "when the LLM proxy rejects a call for budget exhaustion, the adapter automatically requests a lease extension from the gateway via the gRPC control channel ... the adapter retries the failed LLM call transparently — the runtime sees a slightly slow LLM response, not a failure," with the runtime "never aware it happened." This is the only trigger §8.6 defines, motivated by the chicken-and-egg problem that a runtime should not need LLM tokens to reason about asking for more tokens.

The trigger is unimplementable as written because the entity §8.6 designates, the adapter, is never in the LLM request path. In proxy mode the runtime SDK targets the gateway LLM Proxy directly (§4.9: `llm.baseUrl=proxyUrl` at `spec/04_system-components.md:809`; the standard SDK pointed at `proxyUrl` at `:1488-1489`; `proxyEndpoint=https://gateway-internal:8443/llm-proxy` at `:1534`; §13.2 egresses proxy-mode pods to the gateway `:8443` at `spec/13_security-model.md:78,118`), so the LLM request transits the gateway and bypasses the adapter sidecar. In direct mode the runtime egresses straight to the provider and "the gateway has no visibility into LLM API traffic" (`spec/04_system-components.md:1100,1646`; `spec/11_policy-and-controls.md:42`; §8.3 over-run bounded only by the next `ReportUsage` interval, `spec/08_recursive-delegation.md:435`), so no gateway-side per-call budget rejection is possible. The gateway budget-rejection path writes `BUDGET_EXHAUSTED` (403, POLICY, non-retryable) straight back to the pod at `pkg/gateway/llmproxy/llmproxy/handler.go:281-284` and requests no extension, so budget exhaustion surfaces to the runtime as a terminal error, defeating the transparency contract.

`F-8.6.6` (High) and `F-15.3.6` (Medium) are two views of one root cause. The adapter-side entry point `Server.HandleBudgetExhaustion` (`pkg/adapter/leaseextend.go:61-86`) has correct retry/propagate decision logic but zero production callers; its docstring records the seam (`leaseextend.go:55-60`); `Server.LeaseExtender` (`pkg/adapter/server.go:222`) is never assigned in production; `cmd/lenny-adapter/main.go` constructs no LLM-proxy client. The adapter↔gateway control channel (the gRPC `GatewayControl` service; the §4.7 lifecycle message set at `spec/04_system-components.md:705-731` is intra-pod adapter↔runtime) contains no gateway→adapter budget-exhaustion downcall by which the gateway could tell the adapter to request an extension; `terminate/reason:budget_exhausted` (`:725`) is a shutdown rather than a retry trigger. The gateway-side `ExtendLease` handler with its full §8.6 dispatch (`leasecontrol.ExtendLease` at `pkg/gateway/mcpfabric/delegationtree/leasecontrol/leasecontrol.go:776`; cool-off, the elicitation/auto approval gate with the per-minute rate-limit fallback, per-dimension `Grant` against `min(layered effective, parent-lease)` ceilings, the atomic in-flight re-check, and the `GRANTED`/`PARTIALLY_GRANTED`/`CEILING_REACHED`/`REJECTED` outcomes) is complete and ready to receive the call once the trigger's home is fixed. It runs in the same gateway process as the LLM proxy (`cmd/lenny-gateway/main.go:315` `buildLLMProxy`, `:322` `buildControlServer`, `:694` `RegisterGatewayControlServer`), so the proxy can call it in-process, but no in-process wire exists today.

This is a spec-first change: the §8.6-vs-§4.9 responsibility contradiction must be reconciled in `spec/` before non-dead code can land. `BUILD-GAPS.md:9837` already names the two candidate spec fixes: (a) relocate the trigger and transparent retry into the gateway LLM Proxy, or (b) redefine proxy-mode `proxyUrl` as a pod-local adapter forward-proxy that puts the adapter in the LLM path plus a gateway→adapter control-channel downcall.

## 2. Decisions

- **Take Option (a): relocate the §8.6 budget-exhaustion trigger and the transparent retry into the gateway LLM Proxy subsystem, and reduce the adapter's role for this trigger to nil.** Option (a) preserves the §4.9/§13.2 proxy-mode routing (runtime SDK to the gateway proxy over `:8443`) that is already implemented, tested, and network-policy-enforced. Option (b) would invert that routing to put a new LLM forward-proxy inside the adapter sidecar, add a new gateway→adapter control-channel downcall, re-open the §13.2 egress (the pod would egress to a pod-local adapter rather than the gateway), and duplicate lease validation the gateway proxy already performs (`handler.go:247-285`). Option (a) is the minimal-surface, routing-preserving reconciliation; Option (b) invents a parallel LLM path and a new protocol message for the same effect. The gateway proxy already holds the in-flight request context, the lease, and the session id, and co-runs with the complete `leasecontrol.ExtendLease` handler, so the trigger is realizable in-process with no new wire surface.
- **The trigger fires only in proxy mode; direct mode's budget-exhaustion posture is settlement-bounded over-run reconciled against the parent budget, with no in-path termination.** §8.6:629 currently names "the adapter" generically and promises a transparent gateway-mediated retry, but §4.9/§11.2/§8.3 already establish that in direct mode the gateway has no per-call LLM visibility and over-run is bounded only by the next `ReportUsage` settlement interval (`spec/04_system-components.md:1100,1646`; `spec/11_policy-and-controls.md:42`; the §8.3 over-run-semantics item at `spec/08_recursive-delegation.md:435`), so no per-call rejection point and therefore no transparent retry can exist for direct mode. The §8.6 trigger paragraph is scoped to proxy mode and states the direct-mode posture that §8.3:435 already defines: over-run is capped at settlement when `budget_return.lua` reconciles actual consumption against the granted slice, and the direct-mode session is not terminated in-path on budget breach. The proposal adds no direct-mode termination mechanism; the underlying rejection mechanism is already proxy-scoped at `spec/08_recursive-delegation.md:435`, and the amendment adds that scoping to the §8.6:629 trigger paragraph itself.
- **The path fails closed on every §8.6 error.** A failed, unreachable, or errored `ExtendLease` (transport error, no session, ceiling reached, user-rejected, or cool-off active) denies: the proxy writes `BUDGET_EXHAUSTED` and never silently grants tokens or bypasses the ceiling. This mirrors the existing adapter-side fail-closed posture (`leaseextend.go:62-63,79` return `PropagateBudgetExhausted` on a nil extender or a transport error) and the `code-best-practices` "fail closed on security-relevant paths" rule. The gateway `ExtendLease` handler already enforces the ceiling, tenant scoping, cool-off, and approval gate (`leasecontrol.go:776-861`).
- **The §11.2-line-44 terminate-immediately behavior is reconciled with the extension-then-retry contract.** Today `sessionbudget.Enforcer.Record` terminates the session the instant cumulative consumption reaches the budget (`pkg/gateway/session/sessionbudget/sessionbudget.go:108-124`, calling `TerminateSession(ReasonBudgetExhausted)`), and the next request is rejected pre-flight by `Enforcer.Allow` (`handler.go:281`, `sessionbudget.go:132-140`). A naive "call `ExtendLease` on the 403 and retry" collides with this because the session is torn down before any retry can happen. Under Option (a) the gateway must attempt the §8.6 extension at the exhaustion boundary, before terminating a proxy-mode session for budget exhaustion, and terminate only when the extension outcome is terminal (`CEILING_REACHED` or `REJECTED`). §11.2 line 44 and §8.6 line 629 are reconciled to sequence extension-then-terminate rather than terminate-immediately, for proxy-mode sessions whose lease is extendable. The spec change is the load-bearing prerequisite; the sessionbudget/enforcer change is core-product code.
- **F-15.3.6 is closed by deletion rather than by wiring.** Under Option (a) the adapter `LeaseExtender` seam has no production home and becomes dead code, which the no-dead-code and no-backward-compat project rules require removing. The proposal deletes `pkg/adapter/leaseextend.go` (the `LeaseExtender` interface, `HandleBudgetExhaustion`, `BudgetExhaustionDecision`, the `BudgetExhausted*` envelope helpers and message constants), the `Server.LeaseExtender` field (`server.go:217-222`), `gatewaycontrol.Client.ExtendLease` with its `Extension`/`ExtensionResult`/`ExtensionStatus` types (`pkg/adapter/gatewaycontrol/gatewaycontrol.go:104-239`), and `leaseextend_test.go`. The `gatewaycontrol` package survives (`Close`, the platform-tool, connector-tool, and scrub-report forwarding at `platformtools.go`/`connectortools.go`/`scrubreport.go` remain live via `ConnectGateway`'s `PlatformForwarder`/`ConnectorForwarder` wiring, `gatewaylink.go:58,63`). This is the smaller reconciliation than moving the seam to a new gateway package, because the gateway already owns the `ExtendLease` handler in-process.
- **Reuse the established consumer-defined-interface injection pattern for the proxy's in-process call to `leasecontrol` rather than dialing the gateway's own gRPC server.** The LLM proxy `Handler` already accepts injected seams (`BudgetGate`, `Usage`, `Credentials`, `Interceptors` at `handler.go:124-190`), and `cmd/lenny-gateway` injects `leasecontrol.Service` into its gRPC registration (`main.go:584-694`). Add a small consumer-side interface on the `Handler` (for example a `LeaseExtender` with an `ExtendForBudget` method) that `leasecontrol.Service` satisfies, and wire the concrete service into the proxy in `cmd/lenny-gateway/main.go` where both are already constructed. No new gRPC round-trip, no loopback hop, consistent with §4.9's "no sidecar, no loopback" proxy design (`spec/04_system-components.md:1484`).

### S1. Amend §8.6 (and its §4.9/§8.6 companion clauses) to relocate the budget-exhaustion trigger and transparent retry to the gateway LLM Proxy, and scope it to proxy mode

**Targets:**
- `spec/08_recursive-delegation.md`, the §8.6 "Lease Extension" trigger prose (`:627`, `:629`), the auto-mode must-not-retry sentence (`:712`), the elicitation-mode terminal-condition and infinite-retry rationale (`:725`), and the elicitation-mode "User rejects" requesting-subtree identifier that names the adapter's `ExtendLease` gRPC call (`:729`).
- `spec/04_system-components.md`, the §4.7 Runtime Adapter "Adapter → Gateway RPCs" table `ExtendLease` row (`:669`) and the §4.7 platform-MCP-server note that attributes lease extension to the "adapter↔gateway gRPC lifecycle" (`:697`).
- `spec/19_resolved-decisions.md`, the Resolved Decisions row 13 "Lease extension" (`:19`), which is a normative summary of §8.6 current behavior and still attributes the trigger and the must-not-retry obligation to the adapter over an "adapter↔gateway gRPC lifecycle".

**Rationale.** The §8.6:629 trigger paragraph names "the adapter" as the entity that requests the extension and transparently retries the failed LLM call, which is unimplementable because the adapter is never in the LLM request path (§4.9/§13.2). §8.6:627 further states lease extension is "part of the adapter↔gateway gRPC lifecycle" and "the runtime never calls it and is never aware it happened." Four further §8.6/§4.7 clauses assign the retry (or must-not-retry) obligation to the adapter, or name the adapter as the entity that issues the extension call: `:712` (auto mode "The adapter MUST NOT retry after `CEILING_REACHED`"), `:725` (elicitation mode "the adapter MUST treat this as a terminal condition ... The adapter MUST NOT retry extension requests after receiving `CEILING_REACHED`; doing so would create infinite retry loops (each request returns zero grant, each LLM call fails, adapter requests again)"), `:729` (the "User rejects" durability step identifying the requesting subtree as "the session whose adapter issued the `ExtendLease` gRPC call that triggered the elicitation"), and `:669` (the RPC-table row "Request a lease extension when the LLM proxy rejects a call for budget exhaustion ... The adapter MUST NOT retry on `CEILING_REACHED` or `REJECTED`"). §19:19 row 13 is a normative summary of §8.6 current behavior ("Triggered by the adapter when the LLM proxy rejects for budget exhaustion", "`CEILING_REACHED` (zero grant — adapter must not retry)") indexed to §8.6, so it must move in lockstep. The spec must name the gateway LLM Proxy as the trigger entity at every one of these locations and scope the automatic transparent retry to proxy mode, because direct mode has no gateway-side per-call rejection point. This is the load-bearing spec reconciliation; every code change depends on it and must land after it is applied and verified.

**§8.6:627 (the introductory sentences).** Rewrite the "adapter↔gateway gRPC lifecycle" framing that implies the adapter drives the extension, keeping the runtime-transparency guarantee. The reference to the `GatewayControl` service is conditional on the S6/Open-decision-1 outcome the same way the §4.7:669 row is: when S6 trims the `ExtendLease` gRPC method, drop the "the adapter↔gateway `GatewayControl` service also exposes" clause so no spec text names a removed RPC. The trimmed form is:

```markdown
### 8.6 Lease Extension

Lease extension is an internal gateway operation. The `ExtendLease` dispatch runs inside the gateway process, and the budget-exhaustion trigger is driven by the gateway LLM Proxy in-process rather than by the adapter. The runtime never calls lease extension and is never aware it happened.
```

If Open decision 1 retains the RPC, the middle sentence instead reads: "It uses the `ExtendLease` dispatch that the adapter↔gateway `GatewayControl` service also exposes, but the budget-exhaustion trigger is driven by the gateway LLM Proxy in-process rather than by the adapter."

**§8.6:629 (the Trigger paragraph).** Rewrite the subject from "the adapter" to the gateway LLM Proxy, and make the transparent path deliver the already-computed response of the call that exhausted the budget rather than re-issuing a second upstream call. The exhaustion is detected at settlement, after the upstream call has completed, been translated, and had its usage recorded, so the completed call already holds a valid, already-paid-for response; re-issuing it would make a second live upstream provider call and record its tokens a second time. The transparent path therefore writes the response the exhausting call already produced. Add the proxy-mode scoping and the direct-mode posture:

```markdown
**Trigger:** The gateway LLM Proxy detects budget exhaustion for a proxy-mode session when it settles the token usage of a completed upstream call and the session's cumulative consumption reaches its token budget. At that boundary the proxy automatically requests a lease extension for the session from the delegation lease-control service over the gateway's in-process control path (the §8.6 `ExtendLease` dispatch). This avoids the chicken-and-egg problem where a runtime would need LLM tokens to reason about requesting more tokens. On `GRANTED` or `PARTIALLY_GRANTED` the extension raises the session's budget and the session continues. For a non-streaming request the exhaustion is detected before the proxy has written the response, so the proxy delivers the already-computed response of the call whose settlement exhausted the budget and does not re-issue the upstream call; the runtime sees a slightly slow LLM response rather than a failure, and no second provider call or duplicate usage record is created. For a streaming request the response status and body are already committed to the runtime by the time usage is settled, so the raised budget applies to the session's next request, which the pre-flight budget gate then admits. On `CEILING_REACHED` (zero grant) the proxy MUST NOT re-request the extension; it terminates the session, and the next proxied request the session issues receives `BUDGET_EXHAUSTED` from the pre-flight budget gate as a terminal error. On `REJECTED` (user denied), or when the extension cannot be requested (no session, transport fault, or cool-off active), the proxy terminates the session and returns `BUDGET_EXHAUSTED` on the next request.

This automatic extension applies only in `deliveryMode: proxy`, where the gateway LLM Proxy settles the per-call usage. In `deliveryMode: direct` the gateway has no per-call LLM visibility (see [Section 4.9](04_system-components.md#49-credential-leasing-service) and [Section 11.2](11_policy-and-controls.md#112-budgets-and-quotas)); a direct-mode session's over-run is bounded only by the next `ReportUsage` settlement and is reconciled against the parent's delegation budget at settlement ([Section 8.3](08_recursive-delegation.md#83-delegation-policy-and-lease) over-run semantics), and it is not eligible for an automatic in-path extension.
```

**§8.6:712 (auto mode must-not-retry).** Replace the adapter subject in the single sentence "The adapter MUST NOT retry after `CEILING_REACHED`." with "The gateway LLM Proxy MUST NOT re-request the extension after `CEILING_REACHED`." The remainder of the auto-mode paragraph (the rate-limit and elicitation-fallback description) is unchanged.

### S2. Reconcile §11.2 (and the §8.3/§8.6 cross-references) so a proxy-mode session's budget exhaustion attempts the §8.6 extension before immediate termination

**Targets:**
- `spec/11_policy-and-controls.md`, the §11.2 "Budgets and Quotas" enforcement sentence ("if a session exceeds its token budget, the gateway terminates it immediately rather than waiting for session completion", `spec/11_policy-and-controls.md:44`).
- `spec/08_recursive-delegation.md`, the §8.6:629 trigger paragraph (cross-link only) and the §8.3 over-run-semantics item at `:435` (under `### 8.3 Delegation Policy and Lease`), whose proxy-mode clause "rejects LLM calls once the session's `maxTokenBudget` (leaf budget) is exhausted — this bounds over-run in proxy mode" must be amended so it no longer asserts unqualified rejection.

**Rationale.** §11.2 line 44 states the gateway "terminates it immediately rather than waiting for session completion" when a session exceeds its token budget. Taken literally with the S1 relocation, the session is torn down at the exhaustion boundary before the §8.6 extension-then-retry can fire, which is the collision the implemented `sessionbudget.Enforcer.Record` produces today (`sessionbudget.go:108-124`). The two spec statements are contradictory for proxy-mode sessions with an extendable lease. §11.2 must sequence extension-then-terminate: on exhaustion the gateway first attempts the §8.6 extension, and terminates only if the extension outcome is terminal. §8.3:435 carries the same collision from the other side: its over-run-semantics item states that in proxy mode the LLM reverse proxy "rejects LLM calls once the session's `maxTokenBudget` (leaf budget) is exhausted — this bounds over-run in proxy mode", which after the S1 relocation is no longer unqualified (on a grant the proxy raises the budget and the session continues). The proxy-mode clause of §8.3:435 must be amended in lockstep so §8.3, §8.6, and §11.2 state the same proxy-exhaustion predicate (attempt the extension, and terminate only on a terminal outcome), which the S7 tier-11 assertion requires.

**§11.2:44 (the enforcement sentence).** Qualify the "terminates it immediately" clause for proxy mode. Replace the sentence "The gateway enforces budget limits against Redis counters (fast path); if a session exceeds its token budget, the gateway terminates it immediately rather than waiting for session completion." with:

```markdown
The gateway enforces budget limits against Redis counters (fast path). If a `deliveryMode: proxy` session exhausts its token budget, the gateway first attempts a §8.6 lease extension for the session (see [Section 8.6](08_recursive-delegation.md#86-lease-extension), Trigger); it terminates the session only when the extension is terminal (`CEILING_REACHED` or `REJECTED`) or cannot be requested, and it terminates immediately, as before, when the lease is not extendable (extension is disabled or the ceiling is already reached). A `GRANTED` or `PARTIALLY_GRANTED` extension raises the session's budget and the session continues without termination. In `deliveryMode: direct` the gateway has no per-call LLM visibility, so a direct-mode session is not terminated in-path on budget breach; its over-run is bounded only by the next `ReportUsage` settlement interval and is reconciled against the parent's delegation budget at settlement (see [Section 8.3](08_recursive-delegation.md#83-delegation-policy-and-lease) over-run semantics), and it is not eligible for the in-path extension.
```

**§8.3:435 (the over-run-semantics item, proxy-mode clause).** Amend the proxy-mode sentence so it no longer asserts unqualified rejection at the budget boundary and instead states the extension-then-terminate sequence, keeping the over-run-bounding point. This bounds over-run in proxy mode.

Leave the rest of the §8.3 over-run item (the direct-mode `ReportUsage` clause and the settlement `budget_return.lua` reconciliation) unchanged; the §8.6:629 and §11.2:44 direct-mode statements already cite it as the standing authority. ## 4. Non-goals

- **No adapter-side LLM forward-proxy (Option (b)).** The proposal does not put the adapter in the proxy-mode LLM request path, does not redefine `proxyUrl` as a pod-local adapter endpoint, and does not add a gateway→adapter budget-exhaustion control-channel downcall. ## Open decisions for review

1. **Trim or retain the `GatewayControl.ExtendLease` gRPC RPC method and its proto messages (S6).** With the trigger relocated in-process (S3) and the adapter client deleted (S5), the RPC method has no remote caller; the gateway calls `leasecontrol.ExtendLease` in-process. The proposal stages the trim, because keeping the method for a possible future non-proxy or `type:mcp` trigger is a forward-compatibility affordance for a caller that does not exist, which the v1 no-shim principles reject. `leasecontrol.ExtendLease` stays a plain in-process method either way; only the gRPC exposure and the `ExtendLeaseRequest`/`ExtendLeaseResponse`/`FileExportLimitsDelta` proto messages are in question. Confirm the trim, or record a concrete future caller that justifies retaining the RPC surface.
2. **Elicitation-mode behavior on the LLM hot path.** The §8.6 default approval mode is elicitation (`spec/08_recursive-delegation.md:714`), which blocks on a user decision (the `leasecontrol` gate). Under Option (a) the proxy holds the runtime's SDK request open while it waits for that decision, so the "slightly slow LLM response" can be a wait bounded by the runtime SDK's own timeout. The proposal makes the wait honor `r.Context()` and fail closed on cancellation (S3). The open decision is whether blocking the proxied request on an elicitation is acceptable, or whether elicitation-mode extensions in proxy mode should be treated as non-transparent (return `BUDGET_EXHAUSTED` immediately and let the elicitation resolve out-of-band for the next request). This affects whether the S1 "transparent retry" wording is unqualified or carries an elicitation-mode caveat.
