## 1. Problem

§8.6 (`spec/08_recursive-delegation.md:627,629`) is normative that "when the LLM proxy rejects a call for budget exhaustion, the adapter automatically requests a lease extension from the gateway via the gRPC control channel ... the adapter retries the failed LLM call transparently — the runtime sees a slightly slow LLM response, not a failure," with the runtime "never aware it happened." This is the only trigger §8.6 defines, motivated by the chicken-and-egg problem that a runtime should not need LLM tokens to reason about asking for more tokens.

The trigger is unimplementable as written because the entity §8.6 designates, the adapter, is never in the LLM request path. In proxy mode the runtime SDK targets the gateway LLM Proxy directly (§4.9: `llm.baseUrl=proxyUrl` at `spec/04_system-components.md:809`; the standard SDK pointed at `proxyUrl` at `:1488-1489`; `proxyEndpoint=https://gateway-internal:8443/llm-proxy` at `:1534`; §13.2 egresses proxy-mode pods to the gateway `:8443` at `spec/13_security-model.md:78,118`), so the LLM request transits the gateway and bypasses the adapter sidecar. In direct mode the runtime egresses straight to the provider and "the gateway has no visibility into LLM API traffic" (`spec/04_system-components.md:1100,1646`; `spec/11_policy-and-controls.md:42`; §8.3 over-run bounded only by the next `ReportUsage` interval, `spec/08_recursive-delegation.md:435`), so no gateway-side per-call budget rejection is possible. The gateway budget-rejection path writes `BUDGET_EXHAUSTED` (403, POLICY, non-retryable) straight back to the pod at `pkg/gateway/llmproxy/llmproxy/handler.go:281-284` and requests no extension, so budget exhaustion surfaces to the runtime as a terminal error, defeating the transparency contract.

`F-8.6.6` (High) and `F-15.3.6` (Medium) are two views of one root cause. The adapter-side entry point `Server.HandleBudgetExhaustion` (`pkg/adapter/leaseextend.go:61-86`) has correct retry/propagate decision logic but zero production callers; its docstring records the seam (`leaseextend.go:55-60`); `Server.LeaseExtender` (`pkg/adapter/server.go:222`) is never assigned in production; `cmd/lenny-adapter/main.go` constructs no LLM-proxy client. The adapter↔gateway control channel (the gRPC `GatewayControl` service; the §4.7 lifecycle message set at `spec/04_system-components.md:705-731` is intra-pod adapter↔runtime) contains no gateway→adapter budget-exhaustion downcall by which the gateway could tell the adapter to request an extension; `terminate/reason:budget_exhausted` (`:725`) is a shutdown rather than a retry trigger. The gateway-side `ExtendLease` handler with its full §8.6 dispatch (`leasecontrol.ExtendLease` at `pkg/gateway/mcpfabric/delegationtree/leasecontrol/leasecontrol.go:776`; cool-off, the elicitation/auto approval gate with the per-minute rate-limit fallback, per-dimension `Grant` against `min(layered effective, parent-lease)` ceilings, the atomic in-flight re-check, and the `GRANTED`/`PARTIALLY_GRANTED`/`CEILING_REACHED`/`REJECTED` outcomes) is complete and ready to receive the call once the trigger's home is fixed. It runs in the same gateway process as the LLM proxy (`cmd/lenny-gateway/main.go:315` `buildLLMProxy`, `:322` `buildControlServer`, `:694` `RegisterGatewayControlServer`), so the proxy can call it in-process, but no in-process wire exists today.

This is a spec-first change: the §8.6-vs-§4.9 responsibility contradiction must be reconciled in `spec/` before non-dead code can land. `BUILD-GAPS.md:9837` already names the two candidate spec fixes: (a) relocate the trigger and transparent retry into the gateway LLM Proxy, or (b) redefine proxy-mode `proxyUrl` as a pod-local adapter forward-proxy that puts the adapter in the LLM path plus a gateway→adapter control-channel downcall.

## 2. Decisions

- **Take Option (a): relocate the §8.6 budget-exhaustion trigger and the transparent retry into the gateway LLM Proxy subsystem, and reduce the adapter's role for this trigger to nil.** Option (a) preserves the §4.9/§13.2 proxy-mode routing (runtime SDK to the gateway proxy over `:8443`) that is already implemented, tested, and network-policy-enforced. Option (b) would invert that routing to put a new LLM forward-proxy inside the adapter sidecar, add a new gateway→adapter control-channel downcall, re-open the §13.2 egress (the pod would egress to a pod-local adapter rather than the gateway), and duplicate lease validation the gateway proxy already performs (`handler.go:247-285`). Option (a) is the minimal-surface, routing-preserving reconciliation; Option (b) invents a parallel LLM path and a new protocol message for the same effect. The gateway proxy already holds the in-flight request context, the lease, and the session id, and co-runs with the complete `leasecontrol.ExtendLease` handler, so the trigger is realizable in-process with no new wire surface.
- **The trigger fires only in proxy mode; direct mode's budget-exhaustion posture is settlement-bounded over-run reconciled against the parent budget, with no in-path termination.** §8.6:629 currently names "the adapter" generically and promises a transparent gateway-mediated retry, but §4.9/§11.2/§8.3 already establish that in direct mode the gateway has no per-call LLM visibility and over-run is bounded only by the next `ReportUsage` settlement interval (`spec/04_system-components.md:1100,1646`; `spec/11_policy-and-controls.md:42`; the §8.3 over-run-semantics item at `spec/08_recursive-delegation.md:435`), so no per-call rejection point and therefore no transparent retry can exist for direct mode. The §8.6 trigger paragraph is scoped to proxy mode and states the direct-mode posture that §8.3:435 already defines: over-run is capped at settlement when `budget_return.lua` reconciles actual consumption against the granted slice, and the direct-mode session is not terminated in-path on budget breach. The proposal adds no direct-mode termination mechanism; the underlying rejection mechanism is already proxy-scoped at `spec/08_recursive-delegation.md:435`, and the amendment adds that scoping to the §8.6:629 trigger paragraph itself.
- **The path fails closed on every §8.6 error.** A failed, unreachable, or errored `ExtendLease` (transport error, no session, ceiling reached, user-rejected, or cool-off active) denies: the proxy writes `BUDGET_EXHAUSTED` and never silently grants tokens or bypasses the ceiling. This mirrors the existing adapter-side fail-closed posture (`leaseextend.go:62-63,79` return `PropagateBudgetExhausted` on a nil extender or a transport error) and the `code-best-practices` "fail closed on security-relevant paths" rule. The gateway `ExtendLease` handler already enforces the ceiling, tenant scoping, cool-off, and approval gate (`leasecontrol.go:776-861`).
- **The §11.2-line-44 terminate-immediately behavior is reconciled with the extension-then-retry contract.** Today `sessionbudget.Enforcer.Record` terminates the session the instant cumulative consumption reaches the budget (`pkg/gateway/session/sessionbudget/sessionbudget.go:108-124`, calling `TerminateSession(ReasonBudgetExhausted)`), and the next request is rejected pre-flight by `Enforcer.Allow` (`handler.go:281`, `sessionbudget.go:132-140`). A naive "call `ExtendLease` on the 403 and retry" collides with this because the session is torn down before any retry can happen. Under Option (a) the gateway must attempt the §8.6 extension at the exhaustion boundary, before terminating a proxy-mode session for budget exhaustion, and terminate only when the extension outcome is terminal (`CEILING_REACHED` or `REJECTED`). §11.2 line 44 and §8.6 line 629 are reconciled to sequence extension-then-terminate rather than terminate-immediately, for proxy-mode sessions whose lease is extendable. The spec change is the load-bearing prerequisite; the sessionbudget/enforcer change is core-product code.
- **F-15.3.6 is closed by deletion rather than by wiring.** Under Option (a) the adapter `LeaseExtender` seam has no production home and becomes dead code, which the no-dead-code and no-backward-compat project rules require removing. The proposal deletes `pkg/adapter/leaseextend.go` (the `LeaseExtender` interface, `HandleBudgetExhaustion`, `BudgetExhaustionDecision`, the `BudgetExhausted*` envelope helpers and message constants), the `Server.LeaseExtender` field (`server.go:217-222`), `gatewaycontrol.Client.ExtendLease` with its `Extension`/`ExtensionResult`/`ExtensionStatus` types (`pkg/adapter/gatewaycontrol/gatewaycontrol.go:104-239`), and `leaseextend_test.go`. The `gatewaycontrol` package survives (`Close`, the platform-tool, connector-tool, and scrub-report forwarding at `platformtools.go`/`connectortools.go`/`scrubreport.go` remain live via `ConnectGateway`'s `PlatformForwarder`/`ConnectorForwarder` wiring, `gatewaylink.go:58,63`). This is the smaller reconciliation than moving the seam to a new gateway package, because the gateway already owns the `ExtendLease` handler in-process.
- **Reuse the established consumer-defined-interface injection pattern for the proxy's in-process call to `leasecontrol` rather than dialing the gateway's own gRPC server.** The LLM proxy `Handler` already accepts injected seams (`BudgetGate`, `Usage`, `Credentials`, `Interceptors` at `handler.go:124-190`), and `cmd/lenny-gateway` injects `leasecontrol.Service` into its gRPC registration (`main.go:584-694`). Add a small consumer-side interface on the `Handler` (for example a `LeaseExtender` with an `ExtendForBudget` method) that `leasecontrol.Service` satisfies, and wire the concrete service into the proxy in `cmd/lenny-gateway/main.go` where both are already constructed. No new gRPC round-trip, no loopback hop, consistent with §4.9's "no sidecar, no loopback" proxy design (`spec/04_system-components.md:1484`).
- **Trim the `GatewayControl.ExtendLease` gRPC RPC method and its `ExtendLeaseRequest`/`ExtendLeaseResponse`/`FileExportLimitsDelta` proto messages (Open decision 1 resolved by sign-off: trim).** With the trigger relocated in-process (S3) and the adapter client deleted (S5), the RPC has no remote caller; `leasecontrol.ExtendLease` stays a plain in-process Go method. Retaining the gRPC surface for a hypothetical future non-proxy or `type: mcp` trigger is a forward-compatibility affordance for a caller that does not exist, which the v1 no-shim and no-dead-code rules reject; re-adding the RPC if a concrete caller ever appears is sanctioned by the "change interfaces freely and update every caller" rule. S6 removes the RPC method and the three messages, and the tier-3 `callback_reachability_test.go` mTLS round-trip re-targets a surviving `GatewayControl` RPC. Every "if Open decision 1 retains the RPC" alternative in S1 (the §8.6:627 middle-sentence variant, the §4.7:669 reworded-row form, and the §19:19 retain variant) is dropped; the trimmed form is the only staged form, so S1 deletes the §4.7:669 row rather than rewording it.
- **Bound the in-path extension wait by a short, operator-tunable deadline, with a still-pending elicitation falling through to a recover-on-next-request `BUDGET_EXHAUSTED` (Open decision 2 resolved by sign-off: option (iii), bounded wait).** The gateway LLM Proxy attempts the §8.6 extension at the exhaustion boundary and waits for the outcome up to `proxyExtensionWaitTimeout`, a new gateway config value with a flag override, default 5s, documented operator-tunable because §8.6 does not fix it (`code-best-practices` "a default not fixed by the spec must be overridable by a flag or config value"). The in-path wait alone is derived via `context.WithTimeout(r.Context(), proxyExtensionWaitTimeout)`, so a client disconnect or the runtime SDK's own timeout cancels the in-path wait. The elicitation dispatch itself runs on a separate context that is not derived from `r.Context()` or `proxyExtensionWaitTimeout`, so cancelling the in-path wait does not cancel the elicitation. `ExtendForBudget` starts (or joins) a per-tree extension episode that dispatches `leasecontrol.ExtendLease` on a session-scoped context bounded by the §8.6 elicitation lifecycle (the elicitor's own timeout, the `rejectionCoolOffSeconds` cool-off, and the interaction's expiry), on a single tracked goroutine keyed per tree so concurrent exhausting requests join the one in-flight episode rather than starting a second one, then blocks the caller on the episode's resolution signal up to the in-path deadline. The extension attempt returns a tri-state `Outcome`: `Granted` when the episode resolves `GRANTED`/`PARTIALLY_GRANTED` within the window; `Terminal` when it resolves `CEILING_REACHED`/`REJECTED` or the underlying `ExtendLease` errors or the parent `r.Context()` is itself cancelled (a client disconnect, distinguished from the in-path deadline by inspecting `r.Context().Err()`); and `Pending` when the in-path deadline elapses while the episode is still unresolved. On `Granted` the transparent path applies (a non-streaming request writes its already-computed response; a streaming request's raise applies to the next request). On `Terminal` the proxy terminates the session and returns `BUDGET_EXHAUSTED` (fail closed). On `Pending` the proxy does not terminate the session and does not cancel the still-running episode: the enforcer records a deny-next-request state decoupled from `TerminateSession`, so the pre-flight `BudgetGate.Allow` returns `BUDGET_EXHAUSTED` per request while the episode continues out-of-band. On `Pending` for a non-streaming request the response is not yet written, so the proxy returns `BUDGET_EXHAUSTED` for the current request; on `Pending` for a streaming request the 200 response is already committed, so the committed response stands and only the session's subsequent requests are denied by the pre-flight gate. A tree holds multiple proxy-mode sessions (the root plus its delegated children, each with its own enforcer counter, its own deny-next-request state, and its own `DelegationLease.MaxTokenBudget`), and the §8.6 line 719 batching lets several of them exhaust and join the one pending episode, so the episode tracks the set of sessions that joined it, each with its own requested dimensions. When the episode later resolves, its completion action (registered on the per-tree episode, invoked on the episode's own goroutine) runs the per-session `Grant` math and fans out to every joined session: for each session whose outcome is `GRANTED`/`PARTIALLY_GRANTED` it calls `RaiseBudget` with that session's granted delta, which raises that session's budget and clears that session's deny-next-request state so its next request is admitted by the pre-flight `BudgetGate.Allow`; for each session whose outcome is `CEILING_REACHED`/`REJECTED`/error it terminates that session (fail closed). No batched-and-detached session is left with a deny flag that nothing clears, because the fan-out reclaims every session that joined the episode. This bounds the in-path hold so a slow human decision never pins a live proxied request or a gateway connection, while preserving transparency for the fast (auto and quick-approval) cases. The extension-pending state does not leak a goroutine: the single per-tree episode goroutine is bounded by the §8.6 elicitation lifecycle (approval, rejection with `rejectionCoolOffSeconds` cool-off, or the elicitation's own expiry), and its terminal resolution runs the per-session fan-out exactly once and then exits. No extension-pending session is held indefinitely: the same elicitation lifecycle bounds the episode, and its terminal resolution either raises each joined session's budget or terminates that session. This qualifies §8.6's "transparent retry" wording: the retry is transparent for extensions that resolve within `proxyExtensionWaitTimeout`, and is a recover-on-next-request `BUDGET_EXHAUSTED` for elicitation approvals that take longer.

**§8.6:629 (the Trigger paragraph).** Rewrite the subject from "the adapter" to the gateway LLM Proxy, and make the transparent path deliver the already-computed response of the call that exhausted the budget rather than re-issuing a second upstream call. The exhaustion is detected at settlement, after the upstream call has completed, been translated, and had its usage recorded, so the completed call already holds a valid, already-paid-for response; re-issuing it would make a second live upstream provider call and record its tokens a second time. The transparent path therefore writes the response the exhausting call already produced. Add the proxy-mode scoping and the direct-mode posture:

```markdown
**Trigger:** The gateway LLM Proxy detects budget exhaustion for a proxy-mode session when it settles the token usage of a completed upstream call and the session's cumulative consumption reaches its token budget. At that boundary the proxy automatically requests a lease extension for the session from the delegation lease-control service over the gateway's in-process control path (the §8.6 `ExtendLease` dispatch) and waits for the outcome up to `proxyExtensionWaitTimeout` (an operator-tunable gateway deadline, default 5s). This avoids the chicken-and-egg problem where a runtime would need LLM tokens to reason about requesting more tokens. On `GRANTED` or `PARTIALLY_GRANTED` within the wait window the extension raises the session's budget and the session continues. For a non-streaming request the exhaustion is detected before the proxy has written the response, so the proxy delivers the already-computed response of the call whose settlement exhausted the budget and does not re-issue the upstream call; the runtime sees a slightly slow LLM response rather than a failure, and no second provider call or duplicate usage record is created. For a streaming request the response status and body are already committed to the runtime by the time usage is settled, so the raised budget applies to the session's next request, which the pre-flight budget gate then admits. In `auto` mode the extension resolves without a human, so it always resolves within the wait window. In `elicitation` mode the extension blocks on a user decision; when the user approves within the wait window the transparent path above applies. When the wait window elapses while an `elicitation`-mode extension is still pending, the proxy does not terminate the session and does not cancel the pending elicitation, which continues out-of-band bounded by its own lifecycle (approval, rejection cool-off, or expiry). For a non-streaming request the response is not yet written when the wait window elapses, so the proxy returns `BUDGET_EXHAUSTED` for the current request. For a streaming request the response status and body are already committed by the time usage is settled, so the committed 200 response stands and the current request cannot be denied; the proxy records the extension-pending state and denies the session's subsequent requests. In both cases the session stays in an extension-pending state that returns `BUDGET_EXHAUSTED` from the pre-flight budget gate on each subsequent request until the elicitation resolves: a `GRANTED` or `PARTIALLY_GRANTED` resolution raises the session's budget so the next request is admitted, and a `CEILING_REACHED` or `REJECTED` resolution terminates the session. On `CEILING_REACHED` (zero grant) the proxy MUST NOT re-request the extension; it terminates the session, and the next proxied request the session issues receives `BUDGET_EXHAUSTED` from the pre-flight budget gate as a terminal error. On `REJECTED` (user denied), or when the extension cannot be requested (no session, transport fault, or cool-off active), the proxy terminates the session and returns `BUDGET_EXHAUSTED` on the next request.

This automatic extension applies only in `deliveryMode: proxy`, where the gateway LLM Proxy settles the per-call usage. In `deliveryMode: direct` the gateway has no per-call LLM visibility (see [Section 4.9](04_system-components.md#49-credential-leasing-service) and [Section 11.2](11_policy-and-controls.md#112-budgets-and-quotas)); a direct-mode session's over-run is bounded only by the next `ReportUsage` settlement and is reconciled against the parent's delegation budget at settlement ([Section 8.3](08_recursive-delegation.md#83-delegation-policy-and-lease) over-run semantics), and it is not eligible for an automatic in-path extension.
```

Budget is enforced after the upstream call succeeds, in `recordUsage` at `handler.go:390` (non-streaming) and `:433` (streaming), which calls `proxyUsageRecorder.RecordUsage` (`cmd/lenny-gateway/llmproxy_usage.go:216`) and then `sessionbudget.Enforcer.Record`. `Record` fires `TerminateSession` the instant consumption reaches budget (`sessionbudget.go:118-123`), and the budget terminator force-transitions the session to `expired` and runs the terminal pipeline (pod release, audit, billing, SSE). By the time the `:281` rejection fires on the next request, the session is `expired` and its pod is being released. There is no in-flight LLM call to retry and no live session to raise a budget for.

The correct intervention is therefore to move the budget decision earlier, to the exhaustion boundary inside the record/terminate path, so the session is never torn down before the extension is attempted. §8.6:629 (as amended) delivers the already-computed response of the request whose settlement exhausted the budget, which is the call the proxy has just completed and whose usage pushed the session over budget. That call has already produced a valid, translated, already-charged response body (`handler.go:385`), and its usage has already been recorded exactly once (`handler.go:390`); re-issuing it from the top of `ServeHTTP` would make a second live upstream provider call (`handler.go:354`) and run the full `RecordUsage` pipeline a second time (`llmproxy_usage.go:195,204,209,216`), double-billing the provider and double-counting the tokens against §15.1 billing, §11.2 quota, §8.8 rollup, and the per-session budget. The transparent path therefore does not re-issue the call; it holds the exhaustion decision at the record boundary, applies the extension, and then writes the response the exhausting call already produced. This is a single trigger point that S3 and S4 share: the post-response record boundary, at which the exhaustion is first detected.

The transparent (non-terminal) path differs by request kind because streaming commits the response before exhaustion is detected. For a non-streaming request `recordUsage` runs at `handler.go:390`, before `w.WriteHeader(http.StatusOK)` at `:392` and `w.Write(respBody)` at `:393`, so the handler is still holding the already-computed `respBody`; on a `Granted` extension it writes that held `respBody` (a normal 200) rather than issuing a second call. For a streaming request `recordUsage` runs at `handler.go:433`, after `w.WriteHeader(http.StatusOK)` at `:426` and after `RelayStream` at `:432` has already flushed the entire SSE body to the pod (`sse.go:33` writes each line to the client, `:42` folds usage per line, so usage is complete only once the stream has been relayed). Once the status and body are committed a second `WriteHeader` and a second body are impossible, and the streamed call already delivered its complete output. On a streaming exhaustion the extension therefore raises the session budget for the runtime's next request (admitted by the pre-flight `BudgetGate.Allow` gate) without re-issuing the committed stream; a terminal extension outcome terminates the session.

Thread the request context through the record boundary so the extension attempt's in-path wait runs under `r.Context()`. Change `recordUsage` and the `UsageRecorder.RecordUsage` signature to accept a `context.Context` from `ServeHTTP`/`serveStream` (both already hold `r.Context()`), and add a `context.Context` parameter to `sessionbudget.Enforcer.Record` (S4) and to the S4 extension-attempt seam so the request context reaches `ExtendForBudget`. `ExtendForBudget` derives its in-path wait as `context.WithTimeout(r.Context(), proxyExtensionWaitTimeout)` and blocks the caller on the episode's resolution signal under that wait context, so a client disconnect, the runtime SDK's own timeout, or the `proxyExtensionWaitTimeout` deadline unblocks the in-path caller. Without threading `r.Context()`, the record path would run under `context.Background()` (`llmproxy_usage.go:194`), the in-path wait would be non-cancellable, and the fail-closed-on-disconnect guarantee below could not hold. The elicitation dispatch does not run under this wait context (see the episode paragraph below): `ExtendForBudget` must distinguish an in-path deadline (`Pending`, leave the episode running) from a genuine `r.Context()` cancellation (`Terminal`, fail closed) by inspecting `r.Context().Err()` rather than the derived wait context's error.

At the post-response record boundary the record path (S4) reports whether recording this usage exhausted the session and whether the lease is proxy-mode with a session id. When it exhausts and the lease is proxy-mode with a session id and a `LeaseExtender` is wired, the record path calls `ExtendForBudget` before the session's terminal side-effects fire (S4 gates the `TerminateSession` call on this attempt) and branches on the tri-state `Outcome`. On `Granted`, S4 raises the enforcer's per-session budget and clears the exhausted flag, and, so a later request's `Record` does not clobber the raise, the granted delta is propagated to the budget input the enforcer refreshes from (see the paragraph below and S4). On `Granted` for a non-streaming request the proxy writes the already-computed `respBody` it is holding (`handler.go:385`) as a normal 200; it does not re-issue the upstream call, so no second provider call is made and no duplicate usage is recorded. The exhausting call's own usage record, applied once at `handler.go:390`, now sits under the raised budget, so the session continues. On `Granted` for a streaming request the committed stream is not re-issued and the raised budget applies to the session's next request. On `Pending` (the in-path deadline elapsed with an `elicitation`-mode episode still unresolved), S4 records the deny-next-request state without firing `TerminateSession` and without cancelling the episode. On `Pending` for a non-streaming request the response is not yet written, so the current request returns `BUDGET_EXHAUSTED` (403, POLICY, non-retryable). On `Pending` for a streaming request the 200/SSE response is already committed (`handler.go:426,432`), so the committed response stands and the current request cannot be denied; the deny-next-request state means every subsequent request the session issues is rejected `BUDGET_EXHAUSTED` (403, POLICY, non-retryable) by the pre-flight `BudgetGate.Allow` gate. In both cases the still-running episode's per-session completion fan-out later calls `RaiseBudget` for this session on a grant (clearing this session's deny state so the pre-flight gate admits its next request) or terminates this session on a terminal outcome, and it does the same independently for every other session that joined the episode. On `Terminal` or error, the record path completes the termination and the pre-flight gate returns `BUDGET_EXHAUSTED` (403, POLICY, non-retryable) on the runtime's next request, preserving the current envelope.

The raised budget must survive the next `Record`. `Enforcer.Record` overwrites `c.budget = budget` on every call (`sessionbudget.go:104`), and `proxyUsageRecorder.RecordUsage` re-reads that budget argument each call from `sess.DelegationLease.MaxTokenBudget` (`llmproxy_usage.go:186`), which the §8.6 grant path does not update (it writes the leasecontrol `BudgetSource` via `ApplyGrant` at `leasecontrol.go:848` and the Redis tree counter via `GrantTokenBudget` at `:877`, never the session store, whose `DelegationLease` is written only at session creation, `delegation/service.go:1402`). If nothing propagates the grant, the session's next request settles its usage against the stale un-raised `MaxTokenBudget`, `Record` overwrites the raised `c.budget`, cumulative consumption still exceeds it, and the session is immediately re-terminated. The fix must make the effective per-session budget the enforcer reads reflect the granted extension delta: the S4 seam records the granted extension against the session so `RecordUsage` computes the budget as base `MaxTokenBudget` plus the accumulated granted delta before passing it to `Record` (or, equivalently, updates the session store's `MaxTokenBudget` in the same seam). The ordering guarantee is that the session's next request settlement sees the raised budget rather than the pre-extension `MaxTokenBudget`, so the session is not re-terminated. State this in S4.

Bound the extension so it is attempted at most once per distinct exhaustion event (a boolean on the request path guards against re-attempting the same exhaustion within one request), so a single exhaustion cannot loop. A later request that exhausts the granted-and-consumed raised budget is a new exhaustion event that attempts a new extension; it terminates the session only when that extension is terminal (`CEILING_REACHED` or `REJECTED`), because §8.6 permits a session to extend repeatedly up to the effective ceiling (`spec/08_recursive-delegation.md:645,712,726`; `maxExtendableBudget` default 500000, absolute ceiling 2000000 at `:676,678`), and each request against an already-reached ceiling returns a zero grant (`CEILING_REACHED`) from `leaseextension.Grant` (`leasecontrol.go:841`), which is the terminal condition that ends the loop. Termination is therefore gated solely on `CEILING_REACHED`/`REJECTED` (or an extension error or a genuine `r.Context()` cancellation), never on a count of prior grants and never on a `Pending` in-path deadline, so a session that legitimately needs more than one extension is not abandoned before the ceiling is reached.

Dispatch the extension as a per-tree extension episode rather than inline on the caller context, so the in-path wait and the elicitation lifecycle are decoupled. Today `leasecontrol.ExtendLease` runs the whole dispatch synchronously on its caller `ctx` (`leasecontrol.go:776`), the elicitation gate `s.gate(ctx, ...)` (`:823-829`) drives `requestConsent`/`await` (`elicitation.go:144,174`), and both block on `ctx.Done()` (`elicitation.go:176`), so cancelling the caller `ctx` cancels the elicitation (the elicitor returns `(false, ctx.Err())` at `lease_elicit.go:124-126` without resolving the still-pending interaction, and `requestConsent` tears the batch down at `elicitation.go:147-155`). Under option (iii) the elicitation must survive the in-path deadline, so the episode dispatches `ExtendLease` on a session-scoped context that is not derived from `r.Context()` or `proxyExtensionWaitTimeout` and is bounded instead by the §8.6 elicitation lifecycle (the elicitor's own `timeout`, the `rejectionCoolOffSeconds` cool-off, and the interaction expiry). The episode is keyed per tree, reusing the coordinator's existing per-tree serialization (`treeConsent.pending` at `elicitation.go:82,91`): a first exhausting request in a tree opens the episode on a single tracked goroutine, and concurrent exhausting requests join it rather than opening a second one, mirroring the existing §8.6 line 719 batching. A tree holds multiple proxy-mode sessions (the root plus its delegated children; `AddSession` maps many `sessionID`s to one `rootSessionID` at `membudget.go:345-350`), each with its own enforcer counter (`sessionbudget.go:54,99`), its own deny-next-request state, and its own per-session extension budget (`t.extensions[requestingSessionID]` at `membudget.go:578-586`), so a session B that exhausts and joins session A's pending episode needs its own reclaimer. The episode therefore tracks the set of sessions that joined it, and each joining session registers its own requested dimensions (`requestedDimensions` is per request; the `Grant` math at `leasecontrol.go:837-844` runs against each session's own `budget.Current` and `ApplyGrant` at `:848` is keyed per `sessionID`), so the shared per-tree elicitation consent resolves once while the grant math and terminal outcome are computed per session. The in-path caller blocks on the episode's resolution signal under `context.WithTimeout(r.Context(), proxyExtensionWaitTimeout)`; when that context fires it returns `Pending` (in-path deadline, if `r.Context().Err()` is nil) or `Terminal` (a genuine `r.Context()` cancellation, otherwise), leaving the episode running in the first case. For `auto` mode the episode resolves within the window (no human), so the transparent path applies and `ExtendForBudget` returns `Granted` or `Terminal`. For `elicitation` mode (the §8.6 default, which blocks on a user decision) the episode continues out-of-band past the in-path deadline: if it resolves `GRANTED`/`PARTIALLY_GRANTED` within the window `ExtendForBudget` returns `Granted`; if the window elapses first it returns `Pending`, the proxy does not terminate the session and does not cancel the episode, and S4 records the deny-next-request state decoupled from `TerminateSession` (S4). On `Pending` a non-streaming request whose response is not yet written returns `BUDGET_EXHAUSTED` for the current request, while a streaming request whose 200/SSE response is already committed (`handler.go:426,432`) leaves that response standing and the deny-next-request state rejects only the session's subsequent requests through the pre-flight `BudgetGate.Allow` gate. The episode carries a per-session completion action rather than a single per-episode callback, because a tree's sessions resolve independently (session A may resolve `GRANTED` while session B resolves `CEILING_REACHED`): when the episode later resolves on its own goroutine it runs the per-session `Grant` math once and fans out to every session that joined it, calling `RaiseBudget` with that session's granted delta on a `GRANTED`/`PARTIALLY_GRANTED` outcome (raising that session's budget and clearing that session's deny-next-request state so the pre-flight `BudgetGate.Allow` admits that session's next request) or terminating that session on its own `CEILING_REACHED`/`REJECTED`/error outcome (fail closed). The fan-out reclaims every joined session, so a session that joined the pending episode and had its deny flag set is never left denied with nothing to clear it. Because the episode keeps its per-tree slot alive until it resolves, a request that arrives after the in-path deadline joins the same episode rather than minting a second elicitation, and the per-session completion action (rather than any in-path wait) is what applies the deferred grant or termination for each joined session. The `proxyExtensionWaitTimeout` config value carries its `charts/lenny/values.yaml` entry, its `cmd/lenny-gateway/flags.go` flag with a `charts/lenny/templates/gateway-deployment.yaml` render, and its operator-tunable documentation in `docs/reference/configuration.md`. The extension-pending state does not leak a goroutine: the single per-tree episode goroutine is bounded by the §8.6 elicitation lifecycle (approval, rejection cool-off, or elicitation expiry), runs the per-session completion fan-out exactly once on its terminal resolution, and then exits; the in-path wait is separately bounded by `proxyExtensionWaitTimeout` and holds no goroutine of its own. No extension-pending session is held indefinitely: the same elicitation lifecycle bounds the episode, and the episode's terminal resolution either raises each joined session's budget or terminates that session, so a session that batched onto the episode and detached at the in-path deadline is reclaimed by the fan-out rather than left denied. The per-request `BUDGET_EXHAUSTED` is idempotent under repeated requests: each request re-reads the enforcer's deny-next-request state through `BudgetGate.Allow` and returns the same `BUDGET_EXHAUSTED` envelope without opening a new episode while one is pending. In `cmd/lenny-gateway`, thread the already-constructed `leasecontrol.Service` (`main.go:584`) into `buildLLMProxy`/`newLLMProxyServer` and assign it to `Handler.LeaseExtender`, alongside the existing `BudgetGate` wiring, and register the enforcer's `RaiseBudget`/terminate hooks as the episode's per-session completion fan-out so each joined session's deferred grant or termination is applied on its own outcome. Add a nil-guard so the local-development no-`leasecontrol` path preserves today's immediate-rejection behavior. Cite spec §8.6 (proxy trigger) and §11.2 on the new code.

**Rationale.** The §11.2-line-44 collision (Decision 4) lives in this package. `Record` couples the exhausted flag to termination at the consumed-over-budget boundary (`sessionbudget.go:108-124`): it sets `c.exhausted`, fires `onExceeded`, and calls `TerminateSession(ReasonBudgetExhausted)`, which force-expires the session and releases the pod. Under the S2 spec, a proxy-mode session's exhaustion must first attempt the §8.6 extension, and termination happens only on a terminal extension outcome. The extension attempt has three outcomes, so the seam cannot be a two-value boolean: a grant continues the session, a terminal outcome terminates it, and an `elicitation`-mode extension still pending at the in-path deadline must leave the session alive and denying per request (option (iii)). The current binary coupling of `c.exhausted` to `TerminateSession` cannot represent that third state: leaving `c.exhausted` clear admits the next unbudgeted request (bypassing the ceiling, contradicting fail-closed), while setting `c.exhausted` fires `TerminateSession` in the same branch and destroys the session that was supposed to recover on a later grant. The enforcer therefore needs a tri-state seam, a deny-next-request state that sets the deny flag (so `Allow` returns `BUDGET_EXHAUSTED`) decoupled from `TerminateSession`, a way to raise the budget and clear that deny flag when a grant lands (whether in-path or via the out-of-band episode callback), and a refreshed budget input that carries the granted delta so the next `Record` does not overwrite the raise, so the exhausting call's held response is delivered (S3) and subsequent `Allow` calls and settlements pass under the raised budget.

**Sketch.** Keep the terminate-vs-continue decision inside the package that owns the counter and lock (do not lift it out to the proxy). Gate the `TerminateSession` call in `Record` behind an injected synchronous extension-attempt seam that `Record` consults at the exhaustion boundary:

- Add a `context.Context` first parameter to `Enforcer.Record` (threaded from `ServeHTTP` through `RecordUsage`, S3) so the extension attempt fired from the record boundary honors the request context for the in-path wait. Add an optional seam whose return is the tri-state `Outcome` rather than a boolean, for example `extendOnExhaustion func(ctx context.Context, tenantID, sessionID string, budget, consumed int64) Outcome`, injected through `sessionbudget.New` (a nil seam preserves today's behavior). Because `RaiseBudget` and the terminate decision are per-session (`sessionbudget.go:54,99,139`) and the granted extension delta is applied per requesting session (`ApplyGrant` at `membudget.go:578-586`), the completion action must run each joined session's own `Grant` math and clear or terminate that session individually rather than resolving one session for the whole tree. ## 4. Non-goals

- **No adapter-side LLM forward-proxy (Option (b)).** The proposal does not put the adapter in the proxy-mode LLM request path, does not redefine `proxyUrl` as a pod-local adapter endpoint, and does not add a gateway→adapter budget-exhaustion control-channel downcall. - **No change to the §8.6 approval semantics.** Auto and elicitation modes, the per-minute auto rate-limit fallback, cool-off, the extension-denied subtree persistence, the per-dimension `Grant` math, and the `CEILING_REACHED`/`REJECTED` terminal outcomes are unchanged. - **No new non-token extension dimensions on the budget-exhaustion trigger.** The in-path trigger requests the token dimension only, as the adapter seam did; the full §8.6 extendable set stays available through the handler for other issuance paths.
- **No change to the semantic-cache, `PreLLMRequest`/`PostLLMResponse` interceptor, fallback-rotation, or translation paths in the proxy.** The trigger sits at the post-response budget-record boundary, after those stages.
- **No §17.2, §16.5 alert, or chart NetworkPolicy changes.** This trigger is entirely in-process within the existing gateway; it opens no new port, service, or egress and adds no new deployment surface.
