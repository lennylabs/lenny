# Proposal: Adopt a real per-tenant Postgres billing/audit sequence with a length-bounded safe-derived name, closing the §11.2 sequencing-authority divergence (F-11.2.10) and fixing the §10.2 DDL-identifier-length self-contradiction that makes the literal `billing_seq_{tenant_id}` name unsafe

- **Status:** Verified (2026-07-02). Converged after 9 adversarial review rounds (13 findings fixed); awaiting sign-off.
- **Date:** 2026-07-02.
- **Scope:** Reconciles the billing and audit sequencing authority to the real per-tenant Postgres sequence the spec mandates rather than the advisory-lock plus `MAX(sequence_number)+1` mechanism the live code implements, and resolves the §10.2 self-contradiction that pins `tenant_id` to a 128-character format while asserting the literal `billing_seq_{tenant_id}` identifier is safe in DDL. It amends §10.2 to require a length-bounded, collision-resistant safe-derived sequence name, corrects the §11.2.1 billing and §11.7 audit sequencing-authority text to that derived name with the monotonicity-across-deletes rationale made explicit, provisions the per-tenant sequence at tenant-creation time through the gateway's runtime-DDL path (the same technique the EventStore partition maintainer uses in code, without a spec anchor), from a shared helper both runtime tenant-creation paths call (`POST /v1/admin/tenants` and the `POST /v1/admin/bootstrap` seed path, so the Day-1 `default` tenant and every bootstrap-seeded tenant get a sequence), routed to the billing/audit shard where `billing_events` physically lives (`StoreRouter.BillingShard`) rather than the primary pool, through a CREATE-privileged role the implementer selects (Open decision 4), with a `USAGE` grant to `lenny_app`, switches billing `Append` and `InsertFromStream` to `nextval`, and reconciles the §12.8 cross-region monotonicity note (`:947`), the §18 build-sequence deliverable, the `docs/tutorials/multi-tenant-setup.md` example, and the `docs/api/admin.md` description to the derived name. It closes `F-11.2.10`. It touches `spec/10_gateway-internals.md`, `spec/11_policy-and-controls.md`, `spec/12_storage-architecture.md`, `spec/15_external-api-surface.md`, `spec/18_build-sequence.md`, `migrations/`, `pkg/gateway/externalapi/admin/tenants.go`, `pkg/gateway/externalapi/admin/bootstrap.go`, `pkg/gateway/billing/billingstore/pgstore/pgstore.go`, `pkg/gateway/audit/auditstore/`, a shared derived-name helper under `pkg/common`, `docs/tutorials/multi-tenant-setup.md`, `docs/api/admin.md`, `docs/reference/`, `BUILD-GAPS.md`, and the tests.

This document stages the proposed spec, code, and test changes for the implementation step. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

Spec §11.2.1 (`spec/11_policy-and-controls.md:150`) mandates that a billing event's `sequence_number` "is assigned by a **Postgres sequence** (`billing_seq_{tenant_id}`) — a dedicated per-tenant sequence object," assigned via `nextval('billing_seq_{tenant_id}')` inside the `EventStore` INSERT transaction, and states "this guarantees monotonicity across replicas." The §11.7 audit ledger bullet (`spec/11_policy-and-controls.md:365`) makes the identical claim for the audit log: the `sequence_number` is "a `bigint` allocated from a per-tenant Postgres sequence inside the same transaction that inserts the row." §15.1 (`spec/15_external-api-surface.md:814`) mandates `CREATE SEQUENCE IF NOT EXISTS billing_seq_{tenant_id} START WITH 1 INCREMENT BY 1 NO CYCLE` at tenant creation, the §12.8 Phase-4 teardown cell (`spec/12_storage-architecture.md:876`) mandates `DROP SEQUENCE IF EXISTS billing_seq_{tenant_id}` at teardown, and the §12.8 multi-region monotonicity note (`spec/12_storage-architecture.md:947`) and §18 (`spec/18_build-sequence.md:616`) name the same object.

The live code implements none of this. Billing `Append` (`pkg/gateway/billing/billingstore/pgstore/pgstore.go:84-94`) and `InsertFromStream` (`:377-387`) take `SELECT pg_advisory_xact_lock(hashtext($1))` keyed `"billing:"+tenantID`, read `SELECT COALESCE(MAX(sequence_number), 0) FROM billing_events WHERE tenant_id = $1`, then assign `SequenceNumber = tail + 1`. The audit ledger uses the identical mechanism (`pkg/gateway/audit/auditstore/lock.go` advisory lock keyed `"audit:"+tenantID`; `scanTail` reading `ORDER BY sequence_number DESC LIMIT 1`; `row.Seq = tail.Seq + 1`). No `CREATE SEQUENCE`, `nextval`, or `billing_seq` object exists anywhere in `migrations/`, `pkg/`, or `cmd/` (a repository-wide grep is clean), and the tenant-create path (`pkg/gateway/externalapi/admin/tenants.go`) issues no such DDL. `migrations/0001_initial_schema.up.sql:162` defines `sequence_number BIGINT NOT NULL` on `billing_events` under `PRIMARY KEY (tenant_id, sequence_number)` with no backing sequence, and `audit_log` (`:130`) does the same. Billing and audit are internally consistent with each other, and both diverge from their spec text. This is `F-11.2.10` (`BUILD-GAPS.md:16704`, High, OPEN).

The `MAX(sequence_number)+1` mechanism is not observably equivalent to the spec's sequence. The finding's deferral rests on the premise that `billing_events` is append-only with no `TRUNCATE` or partition-rotation path, so `MAX+1` never regresses. That premise is refuted by the code. `DeleteOlderThan` (`pgstore.go:544-569`, the §11.2.1 retention sweep, `DELETE FROM billing_events WHERE tenant_id = $1 AND created_at < $2` under `SET LOCAL lenny.erasure_mode = 'true'`) runs as a live gateway worker with a default 395-day window, and `DeleteByTenant` (`pgstore.go:509-534`) hard-deletes a tenant's rows at §12.8 Phase-4 teardown. The `lenny_erasure` role holds `GRANT DELETE ON billing_events` (migration 0093), and the immutability trigger permits `DELETE` under `lenny.erasure_mode`. When a tenant idle beyond the retention window has all of its rows swept, `COALESCE(MAX(sequence_number), 0) + 1` restarts at 1, a regression below the tenant's prior maximum that reuses sequence numbers and breaks the §11.2.1 gap-detection and replay contract that `GET /v1/metering/events?since_sequence={N}` depends on (`spec/11_policy-and-controls.md:150`). A real Postgres sequence retains its counter independent of table rows and does not regress. This is the correctness value the spec's "guarantees monotonicity across replicas" language carries and the current code lacks. The audit ledger has the same exposure via its own retention sweep (`PruneRetention` at `pkg/gateway/audit/auditstore/auditstore.go:549`).

The literal spec primitive is nonetheless unsafe as written because of a §10.2 self-contradiction (`spec/10_gateway-internals.md:210`). The same sentence pins `tenant_id` to `^[a-zA-Z0-9_-]{1,128}$` (enforced at `pkg/auth/auth.go:253`) and asserts this makes the value "safe for use in DDL identifiers (e.g., `billing_seq_{tenant_id}`)." The prefix `billing_seq_` is 12 characters. Postgres truncates identifiers to 63 bytes (`NAMEDATALEN-1`), so a 128-character `tenant_id` overruns the limit, and two tenants sharing a 51-character prefix collapse onto the same truncated sequence object, a cross-tenant sequence-corruption hazard. Adopting the literal name unchanged imports this hazard, so the fix must resolve it. The `lenny_app` role holds only `GRANT USAGE ON SCHEMA public` and `GRANT SELECT, INSERT ON audit_log, billing_events` (migration 0002), with no `CREATE ON SCHEMA`, so the DDL provisioning path must be chosen deliberately.

## 2. Decisions

- **Adopt the real Postgres sequence the spec mandates rather than weakening the spec to bless `MAX+1`.** The alternative direction, making advisory-lock plus `MAX+1` normative and dropping the `billing_seq`/`nextval` language, rests on a premise the evidence refutes: `billing_events` is deletion-bearing at runtime. The retention pruner (`pgstore.go:544`, a live gateway worker with a default 395-day window) and `DeleteByTenant` (`pgstore.go:509`) can empty a tenant's rows, after which `COALESCE(MAX, 0) + 1` restarts at 1, a monotonicity regression the real-sequence mandate specifically prevents. A `nextval` sequence retains its counter across those deletes. Blessing `MAX+1` would either leave a live correctness gap or require net-new machinery to persist a per-tenant counter across full-table deletes, which reinvents the Postgres sequence. Implementing the spec primitive is the smaller and more correct change.
- **Resolve the §10.2 DDL-identifier-length self-contradiction with a length-bounded safe-derived sequence name rather than the literal `billing_seq_{tenant_id}`.** The literal name overruns the 63-byte `NAMEDATALEN` limit for `tenant_id` values longer than 51 characters and collides across tenants sharing a 51-character prefix (`spec/10_gateway-internals.md:210` against `pkg/auth/auth.go:253`). Derive a fixed-length name, a per-ledger prefix (`billing_seq_` for the billing sequence, `audit_seq_` for the audit sequence) followed by a fixed-width lowercase hex digest of the raw `tenant_id` (a truncated SHA-256), so the identifier is deterministic per tenant and ledger, collision-resistant, and provably ≤ 63 bytes for every `tenant_id` the §10.2 format admits. The distinct prefixes keep the billing and audit ledgers on separate per-tenant sequence objects, so neither ledger's `nextval` consumes the other's numbers. This keeps the monotonicity guarantee intact, removes the hazard, and requires no §10.2 length cap that would narrow an enforced format.
- **Provision the per-tenant sequence at tenant-creation time through the gateway's existing runtime-DDL path, routed to the billing/audit shard where `billing_events` physically lives.** Tenants are created continuously at runtime through `POST /v1/admin/tenants` (`pkg/gateway/externalapi/admin/tenants.go:915`), which runs long after the one-time deploy migration. A migration runs once as a distinct forward-migration binary (`cmd/lenny-migrate/main.go`) and can provision sequences only for tenants that already exist when it runs, which is none on a fresh install (`spec/17_deployment-topology.md:430`: "After `helm install`, Postgres is empty — no runtimes, pools, tenants, or credentials exist"). Provisioning the sequence at migration time would therefore leave every runtime-created tenant without a sequence, so the first billing `Append` for that tenant would call `nextval` on a nonexistent relation and reject the billing write. The gateway already runs per-object DDL at runtime through a Postgres pool: the EventStore partition maintainer (`pkg/gateway/storage/partitionmaint/pgdriver.go:88`, wired in `cmd/lenny-gateway/workers.go:715`) executes `CREATE TABLE ... PARTITION OF` against `w.pgPool` on a leader-gated cadence, with identifiers validated against an allowlist regex before interpolation because DDL cannot bind identifiers. This is a code-only runtime-DDL precedent; no spec section describes runtime partition creation (§16.4 at `spec/16_observability.md:383` describes only the retention job that *drops* partitions past the window). The per-tenant sequence adopts the same runtime-DDL technique, but its placement is the billing/audit shard rather than the primary pool the partition maintainer uses: `billing_events` lives on the separate §12.3 R-03 instance (`LENNY_PG_BILLING_AUDIT_DSN`) when configured, and billing `Append` resolves its pool through `StoreRouter.BillingShard(tenantID)` (`pkg/gateway/billing/billingstore/pgstore/pgstore.go:56-57`, calling `r.billingAuditPool()` at `pkg/storerouter/storerouter.go:369-373,413-417`). A sequence created on the primary pool (where the partition maintainer, `session_logs`, and `stream_cursors` live) would not exist on that separate instance, so the `CREATE SEQUENCE` and the `setval` re-seed must run through `StoreRouter.BillingShard(tenantID)`, and the tenant-create handler must be given that billing-shard handle (the admin `Router` at `pkg/gateway/externalapi/admin/tenants.go:139` currently holds only a primary-pool `tenants` store). The tenant-create handler issues `CREATE SEQUENCE IF NOT EXISTS <derived-name> START WITH 1 INCREMENT BY 1 NO CYCLE` on that shard, using the S1 length-bounded safe-derived name (which the partition-DDL identifier allowlist and the S1 digest both make injection-safe), so the sequence exists before the first billing event as §15.1 requires. The `CREATE SEQUENCE` requires a role that holds `CREATE` on schema `public`, and the DDL-privilege question is not settled by the existing `lenny_app` grants. Spec §11.7 item 7 (`spec/11_policy-and-controls.md:384`, "Gateway replicas and all other services connect as `lenny_app`") and the billing pseudonymize comment (`pkg/gateway/billing/billingstore/pgstore/pgstore.go:410-425`, "the `lenny_app` pool used for normal writes is intentionally not authorized to rewrite the ledger ... The connection must additionally run as the `lenny_erasure` role") establish that `lenny_app` is the gateway pool's actual login role rather than a per-transaction role selection: `SET LOCAL app.current_tenant` (`pkg/gateway/storage/pgtenant/pgtenant.go:91`) sets a tenant-id GUC read by the RLS policies rather than switching the Postgres role, and no `SET ROLE` exists anywhere in `pkg/` or `cmd/`. `lenny_app` is created `NOLOGIN` with `GRANT USAGE ON SCHEMA public` and table-level DML only (`migrations/0002_rls_immutability_roles.up.sql:22,29,161`), with no `CREATE ON SCHEMA`, so a `CREATE SEQUENCE` issued through the `lenny_app` pool would raise `permission denied for schema public`. The §16.4 partition maintainer does not establish that `lenny_app` holds `CREATE`: migration 0149 grants only DML on the partition parents (`migrations/0149_eventstore_partitioned_logs.up.sql:71`) with no `CREATE` grant, so the maintainer's runtime `CREATE TABLE` either runs under a role other than `lenny_app` or is itself an unverified privilege assumption. Open decision 4 records the DDL-privilege resolution the implementer must choose; whichever it selects, the sequence is provisioned at tenant-create time through the shared helper both the `handleCreateTenant` and the bootstrap seed paths call, so it covers every runtime-created tenant, and the `USAGE ON SEQUENCE` grant `nextval` requires is applied to the sequences via `ALTER DEFAULT PRIVILEGES`. This keeps the §15.1 tenant-create-handler provisioning the spec already mandates and provisions the sequence for every tenant regardless of which endpoint creates it or when.
- **Apply the same sequence mechanism to both billing and audit, keeping the two ledgers internally consistent.** Both currently use the identical advisory-lock plus `tail+1` mechanism (billing `pgstore.go:84-94`; audit `auditstore.go`/`lock.go`) and both have the same retention-regression exposure (billing `DeleteOlderThan`; audit `PruneRetention` at `auditstore.go:549`). Reconciling only billing would leave audit diverging from §11.7:365 and split two structurally identical ledgers onto different mechanisms, against the single-canonical-implementation principle. The audit spec text names no literal identifier at §11.7:365, so audit adopts the same safe-derived naming scheme under its own `audit_seq_` prefix, a distinct per-tenant sequence object from billing's `billing_seq_` sequence, with no spec-name contradiction. The distinct prefixes matter because billing and audit route to the same physical billing/audit instance (`StoreRouter.BillingShard` and `StoreRouter.AuditShard` both resolve `billingAuditPool()` at `pkg/storerouter/storerouter.go:369-373`), so an identical name would place both ledgers on one shared sequence and interleave their numbers.
- **Preserve the advisory lock's other role, because for audit the lock serializes `prev_hash` chaining rather than sequence assignment.** §11.7:366 ("Concurrency control for `prev_hash`") requires the per-tenant advisory lock so two concurrent writers cannot fork the hash chain against the same tail row. Adopting `nextval` for the audit `sequence_number` does not remove that requirement: the lock stays, held across the tail-hash read and the INSERT. For billing there is no hash chain, so `nextval` alone provides monotonicity and the advisory lock is dropped from the billing write path. The proposal scopes which lock stays and which goes per ledger. Because the audit sequence must remain a dense within-chain ordinal that the chain verifier reads back, the audit conversion is scoped in S5 as an open decision rather than a committed `nextval` switch; see the audit-scope analysis in Section 3.
- **Reconcile the provisional renumber-at-flush path (`InsertFromStream`) to the sequence.** `pgstore.go:363-366` documents that the flusher re-derives the sequence under the per-tenant advisory lock exactly like `Append`, discarding the provisional `stream_seq`. Under the sequence model the flusher calls `nextval` at flush time instead of reading `MAX`, matching §11.2.1's "the flusher acquires the Postgres sequence value at flush time, not at buffer time" (`spec/11_policy-and-controls.md:150`). This aligns the code with a spec sentence the current `MAX+1` implementation only approximates.
- **Handle any existing-rows re-seed with `setval`.** A fresh `CREATE SEQUENCE` starts at 1, but `billing_events`/`audit_log` may already hold rows numbered via `MAX+1` from prior operation. On the `CREATE SEQUENCE IF NOT EXISTS` path in the tenant-create handler, when the sequence is newly created for a tenant whose rows predate it, the handler runs `setval()` to the current per-tenant `MAX(sequence_number)` so `nextval` does not collide with an existing `(tenant_id, sequence_number)` primary key. Because v1 has no deployments in the wild, this branch is effectively a no-op for a freshly-created tenant with no rows; the `setval` is specified so the mechanism is correct if any rows predate the sequence.

### S1. Amend §10.2 to require a length-bounded safe-derived sequence name and remove the false DDL-identifier-length safety claim

**Targets:**
- `spec/10_gateway-internals.md`: the §10.2 `tenant_id`-format sentence (`:210`) asserting `^[a-zA-Z0-9_-]{1,128}$` is "safe for use in DDL identifiers (e.g., `billing_seq_{tenant_id}`)."

**Rationale.** The current sentence is a load-bearing self-contradiction: the 128-character format overruns the 63-byte `NAMEDATALEN` limit, so the literal `billing_seq_{tenant_id}` name collides across tenants sharing a 51-character prefix (12-character prefix plus 51 surviving characters is 63 bytes). The format constraint prevents injection and path traversal but not length overflow. Every downstream section (§11.2.1, §15.1, §12.8, §18) that names `billing_seq_{tenant_id}` depends on this being safe.

**Sketch.** Narrow the safety claim to what the format guarantees (no injection, no path traversal) and state that per-tenant DDL identifiers derived from `tenant_id` **must** be length-bounded to ≤ 63 bytes via a deterministic collision-resistant digest, because Postgres truncates identifiers at `NAMEDATALEN-1` (63 bytes) and a 128-character `tenant_id` would otherwise collide across tenants sharing a 51-character prefix. Define the canonical derivation once here, with a per-ledger prefix (`billing_seq_` for billing and `audit_seq_` for audit) so the two ledgers derive distinct per-tenant sequence objects rather than colliding onto one, and reference it from §11.2.1, §15.1, §12.8 (both the teardown cell and the multi-region monotonicity note), and §18 (and from §11.7 for the audit prefix when the S5 Path A audit resolution is chosen) so all sites name the same derived identifier. Do not add a `tenant_id` length cap below 128, which would narrow the enforced §10.2 format for no benefit once the name is derived.

The current sentence at `:210` is:

```markdown
This format constraint ensures `tenant_id` values are safe for use in DDL identifiers (e.g., `billing_seq_{tenant_id}`), MinIO path prefixes, Redis key prefixes, and log fields without risk of injection or path traversal.
```

It becomes:

```markdown
This format constraint ensures `tenant_id` values are safe for use in MinIO path prefixes, Redis key prefixes, and log fields without risk of injection or path traversal. The format alone does not bound identifier length: a 128-character `tenant_id` exceeds the 63-byte Postgres identifier limit (`NAMEDATALEN-1`), and Postgres silently truncates any longer identifier, so two tenants sharing a 51-character prefix would collapse onto the same truncated object. A per-tenant Postgres DDL identifier derived from `tenant_id` (such as the per-tenant billing or audit sequence) **must** therefore be length-bounded and collision-resistant. The canonical derivation is a per-ledger literal prefix (`billing_seq_` for the billing sequence, `audit_seq_` for the audit sequence) followed by the lowercase hexadecimal encoding of a fixed-width prefix of `SHA-256(tenant_id)`, sized so the whole identifier is ≤ 63 bytes for every `tenant_id` the format admits. The two prefixes give the billing and audit ledgers distinct per-tenant sequence objects on the shared billing/audit instance, so each ledger's `sequence_number` advances independently and neither ledger consumes the other's sequence values. §11.2.1, §15.1, §12.8, and §18 refer to this derived identifier rather than the raw `billing_seq_{tenant_id}` string, and §11.7 refers to the `audit_seq_`-prefixed identifier when the S5 Path A audit resolution is chosen.
```

### S3. Provision the per-tenant sequence at tenant-creation time through the gateway runtime-DDL path with the derived name and a default `USAGE` grant to `lenny_app`, and reconcile §15.1 and §12.8

**Targets:**

GRANT USAGE ON SEQUENCES TO lenny_app` scoped to the schema so every subsequently-created sequence carries the grant, plus a `USAGE` grant covering any sequences that already exist at migration time. ## 4. Non-goals

- **No `tenant_id` length cap below 128 characters.** The §10.2 format is enforced at multiple boundaries (`pkg/auth/auth.go:253`, and the §17.6 and §27.2 ingestion points), and narrowing it to accommodate a naming choice the S1 derived name already resolves would be a backward-incompatible change.
- **No change to the runtime placement of the `CREATE SEQUENCE` beyond routing it to the billing/audit shard.** It runs from the tenant-create handler at runtime rather than at migration time, because a migration cannot provision sequences for tenants created after it runs, and it runs on the billing/audit shard (`StoreRouter.BillingShard`) where `billing_events` lives rather than the primary pool, so `nextval` resolves the sequence on the same instance in the separate-instance topology. The DDL-privilege the `CREATE SEQUENCE` requires (a role holding `CREATE` on schema `public`) is not settled by the existing `lenny_app` grants, which hold no `CREATE ON SCHEMA`; the choice between widening `lenny_app`'s grant and introducing a distinct CREATE-privileged connection is Open decision 4 and is not foreclosed here. `lenny_app` receives `USAGE ON SEQUENCE`, which `nextval` requires, independent of that resolution.
- **No DROP-SEQUENCE at teardown, and no `DROP SEQUENCE` inside `DeleteByTenant`.** `DeleteByTenant` runs as `lenny_erasure`, which holds no `DROP` privilege and cannot execute the statement. An orphaned unused sequence for a tombstoned tenant is inert, and the `tenants` row is retained as a tombstone.
- **No removal of the per-tenant advisory lock from the audit write path.** It serializes `prev_hash` chaining (§11.7:366), a concern orthogonal to sequence assignment. `nextval` replaces the lock only on the billing write path, where there is no hash chain.
- **No change to the client-facing gap-detection and replay API (`GET /v1/metering/events?since_sequence`).** The sequence adoption preserves the observable per-tenant monotonic contract that endpoint depends on and does not alter the wire surface.
- **No change to cross-region aggregation semantics beyond renaming the sequence object.** The §12.8 `(region, sequence_number)` composite ordering and per-region-per-tenant monotonicity are retained by construction.

## Open decisions for review

1. **The sequence-name derivation.** Which digest and encoding (truncated SHA-256 hex against base32) and how many bytes of digest to keep. Any collision-resistant fixed-width scheme that keeps `billing_seq_<digest>` and `audit_seq_<digest>` ≤ 63 bytes works; the reviewer confirms the exact derivation to canonicalize in §10.2 so the two ledgers derive distinct per-tenant names under their respective prefixes (billing and audit must never share one sequence object, because a shared `nextval` would interleave the two ledgers' numbers and break billing's dense per-tenant monotonicity and the audit chain's dense within-chain ordinal) and the digest width is fixed once.
2. **The audit sequencing resolution (S5 Path A against Path B).** Path A aligns audit to `nextval` with a chain-verifier reconciliation so a `nextval`-produced sequence does not misclassify a swept-empty or rolled-back chain, keeping billing and audit on one mechanism. Path B amends §11.7:365 to state the audit `sequence_number` is the per-tenant chain ordinal maintained under the `prev_hash` advisory lock, matching the code and removing the audit provisioning and derived-name machinery. Path B is the strictly smaller change; the reviewer picks one.
3. **The re-seed scope for existing rows.** On the `CREATE SEQUENCE IF NOT EXISTS` path in the tenant-create handler, a `setval` re-seeds a tenant whose `billing_events` rows predate the sequence to `MAX(sequence_number)`. Because v1 has no deployments in the wild, a freshly-created tenant has no rows and the branch is a no-op; the reviewer confirms whether the `setval` branch is worth retaining for the pre-existing-rows case or can be omitted.
4. **The DDL privilege for the runtime `CREATE SEQUENCE` (load-bearing).** The tenant-create handler issues `CREATE SEQUENCE`, which requires a role holding `CREATE` on schema `public` on the billing/audit instance where `billing_events` lives (the separate `LENNY_PG_BILLING_AUDIT_DSN` instance when configured, otherwise the primary). The gateway connects as `lenny_app` (`spec/11_policy-and-controls.md:384`), `SET LOCAL app.current_tenant` (`pkg/gateway/storage/pgtenant/pgtenant.go:91`) sets a tenant-id GUC read by RLS rather than a Postgres role, no `SET ROLE` exists in `pkg/` or `cmd/`, and `lenny_app` is created `NOLOGIN` with `USAGE ON SCHEMA public` and table-level DML only (`migrations/0002_rls_immutability_roles.up.sql:22,29,161`), with no `CREATE ON SCHEMA`. The code-only runtime partition-CREATE does not settle this: migration 0149 grants the partition parents only DML (`migrations/0149_eventstore_partitioned_logs.up.sql:71`), so the partition maintainer's runtime `CREATE TABLE` runs either under a role other than `lenny_app` or on an unverified privilege assumption. Without a resolution, the `CREATE SEQUENCE` raises `permission denied for schema public` and the first billing `Append` then fails on `nextval` of a nonexistent relation, breaking tenant creation and billing for every tenant. Three resolutions, in order of preference: (a) provision the `CREATE SEQUENCE` through a distinct CREATE-privileged login role and connection reserved for per-tenant DDL on the billing/audit instance, reconciling the §11.7 least-privilege model and the integrity-verifier surfaces so the DDL-capable role is auditable and never used for ledger writes (recommended, because it keeps `lenny_app` least-privilege and confines the CREATE grant to a role the pgaudit sink at §11.7 item 5 already captures); (b) grant `lenny_app` `CREATE ON SCHEMA public` and reconcile the §11.7 least-privilege model, §12.3, and `pkg/audit/integrity` to the widened grant; (c) abandon runtime `CREATE SEQUENCE` under any per-tenant DDL, in favor of a mechanism that needs no per-tenant DDL. The reviewer confirms the partition maintainer's actual DDL-privilege path before treating it as precedent, and selects the resolution.
