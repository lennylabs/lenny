## 1. Problem

Spec §11.2.1 (`spec/11_policy-and-controls.md:150`) mandates that a billing event's `sequence_number` "is assigned by a **Postgres sequence** (`billing_seq_{tenant_id}`) — a dedicated per-tenant sequence object," assigned via `nextval('billing_seq_{tenant_id}')` inside the `EventStore` INSERT transaction, and states "this guarantees monotonicity across replicas." The §11.7 audit ledger bullet (`spec/11_policy-and-controls.md:365`) makes the identical claim for the audit log: the `sequence_number` is "a `bigint` allocated from a per-tenant Postgres sequence inside the same transaction that inserts the row." §15.1 (`spec/15_external-api-surface.md:814`) mandates `CREATE SEQUENCE IF NOT EXISTS billing_seq_{tenant_id} START WITH 1 INCREMENT BY 1 NO CYCLE` at tenant creation, the §12.8 Phase-4 teardown cell (`spec/12_storage-architecture.md:876`) mandates `DROP SEQUENCE IF EXISTS billing_seq_{tenant_id}` at teardown, and the §12.8 multi-region monotonicity note (`spec/12_storage-architecture.md:947`) and §18 (`spec/18_build-sequence.md:616`) name the same object.

The live code implements none of this. Billing `Append` (`pkg/gateway/billing/billingstore/pgstore/pgstore.go:84-94`) and `InsertFromStream` (`:377-387`) take `SELECT pg_advisory_xact_lock(hashtext($1))` keyed `"billing:"+tenantID`, read `SELECT COALESCE(MAX(sequence_number), 0) FROM billing_events WHERE tenant_id = $1`, then assign `SequenceNumber = tail + 1`. The audit ledger uses the identical mechanism (`pkg/gateway/audit/auditstore/lock.go` advisory lock keyed `"audit:"+tenantID`; `scanTail` reading `ORDER BY sequence_number DESC LIMIT 1`; `row.Seq = tail.Seq + 1`). No `CREATE SEQUENCE`, `nextval`, or `billing_seq` object exists anywhere in `migrations/`, `pkg/`, or `cmd/` (a repository-wide grep is clean), and the tenant-create path (`pkg/gateway/externalapi/admin/tenants.go`) issues no such DDL. `migrations/0001_initial_schema.up.sql:162` defines `sequence_number BIGINT NOT NULL` on `billing_events` under `PRIMARY KEY (tenant_id, sequence_number)` with no backing sequence, and `audit_log` (`:130`) does the same. Billing and audit are internally consistent with each other, and both diverge from their spec text. This is `F-11.2.10` (`BUILD-GAPS.md:16704`, High, OPEN).

The `MAX(sequence_number)+1` mechanism is not observably equivalent to the spec's sequence. The finding's deferral rests on the premise that `billing_events` is append-only with no `TRUNCATE` or partition-rotation path, so `MAX+1` never regresses. That premise is refuted by the code. `DeleteOlderThan` (`pgstore.go:544-569`, the §11.2.1 retention sweep, `DELETE FROM billing_events WHERE tenant_id = $1 AND created_at < $2` under `SET LOCAL lenny.erasure_mode = 'true'`) runs as a live gateway worker with a default 395-day window, and `DeleteByTenant` (`pgstore.go:509-534`) hard-deletes a tenant's rows at §12.8 Phase-4 teardown. The `lenny_erasure` role holds `GRANT DELETE ON billing_events` (migration 0093), and the immutability trigger permits `DELETE` under `lenny.erasure_mode`. When a tenant idle beyond the retention window has all of its rows swept, `COALESCE(MAX(sequence_number), 0) + 1` restarts at 1, a regression below the tenant's prior maximum that reuses sequence numbers and breaks the §11.2.1 gap-detection and replay contract that `GET /v1/metering/events?since_sequence={N}` depends on (`spec/11_policy-and-controls.md:150`). A real Postgres sequence retains its counter independent of table rows and does not regress. This is the correctness value the spec's "guarantees monotonicity across replicas" language carries and the current code lacks. The audit ledger has the same exposure via its own retention sweep (`PruneRetention` at `pkg/gateway/audit/auditstore/auditstore.go:549`).

The literal spec primitive is nonetheless unsafe as written because of a §10.2 self-contradiction (`spec/10_gateway-internals.md:210`). The same sentence pins `tenant_id` to `^[a-zA-Z0-9_-]{1,128}$` (enforced at `pkg/auth/auth.go:253`) and asserts this makes the value "safe for use in DDL identifiers (e.g., `billing_seq_{tenant_id}`)." The prefix `billing_seq_` is 12 characters. Postgres truncates identifiers to 63 bytes (`NAMEDATALEN-1`), so a 128-character `tenant_id` overruns the limit, and two tenants sharing a 51-character prefix collapse onto the same truncated sequence object, a cross-tenant sequence-corruption hazard. Adopting the literal name unchanged imports this hazard, so the fix must resolve it. The `lenny_app` role holds only `GRANT USAGE ON SCHEMA public` and `GRANT SELECT, INSERT ON audit_log, billing_events` (migration 0002), with no `CREATE ON SCHEMA`, so the DDL provisioning path must be chosen deliberately.

## 2. Decisions

- **Adopt the real Postgres sequence the spec mandates rather than weakening the spec to bless `MAX+1`.** The alternative direction, making advisory-lock plus `MAX+1` normative and dropping the `billing_seq`/`nextval` language, rests on a premise the evidence refutes: `billing_events` is deletion-bearing at runtime. The retention pruner (`pgstore.go:544`, a live gateway worker with a default 395-day window) and `DeleteByTenant` (`pgstore.go:509`) can empty a tenant's rows, after which `COALESCE(MAX, 0) + 1` restarts at 1, a monotonicity regression the real-sequence mandate specifically prevents. A `nextval` sequence retains its counter across those deletes. Blessing `MAX+1` would either leave a live correctness gap or require net-new machinery to persist a per-tenant counter across full-table deletes, which reinvents the Postgres sequence. Implementing the spec primitive is the smaller and more correct change.
- **Resolve the §10.2 DDL-identifier-length self-contradiction with a length-bounded safe-derived sequence name rather than the literal `billing_seq_{tenant_id}`.** The literal name overruns the 63-byte `NAMEDATALEN` limit for `tenant_id` values longer than 51 characters and collides across tenants sharing a 51-character prefix (`spec/10_gateway-internals.md:210` against `pkg/auth/auth.go:253`). Derive a fixed-length name, a per-ledger prefix (`billing_seq_` for the billing sequence, `audit_seq_` for the audit sequence) followed by the lowercase hexadecimal encoding of the first 20 bytes (160 bits) of `SHA-256(tenant_id)`, a fixed 40-hex-character digest, so the identifier is deterministic per tenant and ledger, collision-resistant, and provably ≤ 63 bytes for every `tenant_id` the §10.2 format admits (`billing_seq_<40hex>` is 52 bytes and `audit_seq_<40hex>` is 50 bytes). The distinct prefixes keep the billing and audit ledgers on separate per-tenant sequence objects, so neither ledger's `nextval` consumes the other's numbers. This keeps the monotonicity guarantee intact, removes the hazard, and requires no §10.2 length cap that would narrow an enforced format.
- **Provision the per-tenant sequence at tenant-creation time through the gateway's existing runtime-DDL path, routed to the billing/audit shard where `billing_events` physically lives.** Tenants are created continuously at runtime through `POST /v1/admin/tenants` (`pkg/gateway/externalapi/admin/tenants.go:915`), which runs long after the one-time deploy migration. A migration runs once as a distinct forward-migration binary (`cmd/lenny-migrate/main.go`) and can provision sequences only for tenants that already exist when it runs, which is none on a fresh install (`spec/17_deployment-topology.md:430`: "After `helm install`, Postgres is empty — no runtimes, pools, tenants, or credentials exist"). Provisioning the sequence at migration time would therefore leave every runtime-created tenant without a sequence, so the first billing `Append` for that tenant would call `nextval` on a nonexistent relation and reject the billing write. The gateway already runs per-object DDL at runtime through a Postgres pool: the EventStore partition maintainer (`pkg/gateway/storage/partitionmaint/pgdriver.go:88`, wired in `cmd/lenny-gateway/workers.go:715`) executes `CREATE TABLE ... PARTITION OF` against `w.pgPool` on a leader-gated cadence, with identifiers validated against an allowlist regex before interpolation because DDL cannot bind identifiers. This is a code-only runtime-DDL precedent; no spec section describes runtime partition creation (§16.4 at `spec/16_observability.md:383` describes only the retention job that *drops* partitions past the window). The per-tenant sequence adopts the same runtime-DDL technique, but its placement is the billing/audit shard rather than the primary pool the partition maintainer uses: `billing_events` lives on the separate §12.3 R-03 instance (`LENNY_PG_BILLING_AUDIT_DSN`) when configured, and billing `Append` resolves its pool through `StoreRouter.BillingShard(tenantID)` (`pkg/gateway/billing/billingstore/pgstore/pgstore.go:56-57`, calling `r.billingAuditPool()` at `pkg/storerouter/storerouter.go:369-373,413-417`). A sequence created on the primary pool (where the partition maintainer, `session_logs`, and `stream_cursors` live) would not exist on that separate instance, so the `CREATE SEQUENCE` and the `setval` re-seed must run through `StoreRouter.BillingShard(tenantID)`, and the tenant-create handler must be given that billing-shard handle (the admin `Router` at `pkg/gateway/externalapi/admin/tenants.go:139` currently holds only a primary-pool `tenants` store). The tenant-create handler issues `CREATE SEQUENCE IF NOT EXISTS <derived-name> START WITH 1 INCREMENT BY 1 NO CYCLE` on that shard, using the S1 length-bounded safe-derived name (which the partition-DDL identifier allowlist and the S1 digest both make injection-safe), so the sequence exists before the first billing event as §15.1 requires. The `CREATE SEQUENCE` requires a role that holds `CREATE` on schema `public`, and the DDL-privilege question is not settled by the existing `lenny_app` grants. Spec §11.7 item 7 (`spec/11_policy-and-controls.md:384`, "Gateway replicas and all other services connect as `lenny_app`") and the billing pseudonymize comment (`pkg/gateway/billing/billingstore/pgstore/pgstore.go:410-425`, "the `lenny_app` pool used for normal writes is intentionally not authorized to rewrite the ledger ... The connection must additionally run as the `lenny_erasure` role") establish that `lenny_app` is the gateway pool's actual login role rather than a per-transaction role selection: `SET LOCAL app.current_tenant` (`pkg/gateway/storage/pgtenant/pgtenant.go:91`) sets a tenant-id GUC read by the RLS policies rather than switching the Postgres role, and no `SET ROLE` exists anywhere in `pkg/` or `cmd/`. `lenny_app` is created `NOLOGIN` with `GRANT USAGE ON SCHEMA public` and table-level DML only (`migrations/0002_rls_immutability_roles.up.sql:22,29,161`), with no `CREATE ON SCHEMA`, so a `CREATE SEQUENCE` issued through the `lenny_app` pool would raise `permission denied for schema public`. The §16.4 partition maintainer does not establish that `lenny_app` holds `CREATE`: migration 0149 grants only DML on the partition parents (`migrations/0149_eventstore_partitioned_logs.up.sql:71`) with no `CREATE` grant, so the maintainer's runtime `CREATE TABLE` either runs under a role other than `lenny_app` or is itself an unverified privilege assumption. The DDL-privilege resolution is option (a): the migration creates a distinct CREATE-privileged login role reserved for per-tenant DDL on the billing/audit instance, and `cmd/lenny-gateway` constructs a dedicated DDL pool that connects as that role (a pool separate from the `lenny_app` billing/audit pool), threaded into the admin `Router` so the provisioning helper opens the `CREATE SEQUENCE` on that connection. `lenny_app` stays least-privilege and never gains `CREATE ON SCHEMA`; it receives only `USAGE ON SEQUENCE`, which `nextval` requires, applied to future billing and audit sequences via `ALTER DEFAULT PRIVILEGES FOR ROLE <ddl_role>`. The sequence is provisioned at tenant-create time through the shared helper both the `handleCreateTenant` and the bootstrap seed paths call, so it covers every runtime-created tenant. This keeps the §15.1 tenant-create-handler provisioning the spec already mandates and provisions the sequence for every tenant regardless of which endpoint creates it or when. The `platform` pseudo-tenant audit chain is the one audit-write path with no `tenants` row and no tenant-creation path, so its fixed `audit_seq_<platform-40hex>` sequence is provisioned by the migration instead (a compile-time-constant name known at migration time), on every audit-bearing instance a platform-chain write can reach.
- **Apply the same sequence mechanism to both billing and audit, keeping the two ledgers internally consistent.** Both currently use the identical advisory-lock plus `tail+1` mechanism (billing `pgstore.go:84-94`; audit `auditstore.go`/`lock.go`) and both have the same retention-regression exposure (billing `DeleteOlderThan`; audit `PruneRetention` at `auditstore.go:549`). Reconciling only billing would leave audit diverging from §11.7:365 and split two structurally identical ledgers onto different mechanisms, against the single-canonical-implementation principle. The audit spec text names no literal identifier at §11.7:365, so audit adopts the same safe-derived naming scheme under its own `audit_seq_` prefix, a distinct per-tenant sequence object from billing's `billing_seq_` sequence, with no spec-name contradiction. The distinct prefixes matter because billing and audit route to the same physical billing/audit instance (`StoreRouter.BillingShard` and `StoreRouter.AuditShard` both resolve `billingAuditPool()` at `pkg/storerouter/storerouter.go:369-373`), so an identical name would place both ledgers on one shared sequence and interleave their numbers.
- **Preserve the advisory lock's other role, because for audit the lock serializes `prev_hash` chaining rather than sequence assignment.** §11.7:366 ("Concurrency control for `prev_hash`") requires the per-tenant advisory lock so two concurrent writers cannot fork the hash chain against the same tail row. Adopting `nextval` for the audit `sequence_number` does not remove that requirement: the lock stays, held across the tail-hash read and the INSERT. For billing there is no hash chain, so `nextval` alone provides monotonicity and the advisory lock is dropped from the billing write path. The proposal scopes which lock stays and which goes per ledger. The audit sequence is also a within-chain ordinal that two separate verifiers read back. The §25.9 query-API classifier (`pkg/audit/chain.go:437`) already tolerates a `nextval` gap as the advisory, non-alarming `gap_suspected` state and needs no change: `gap_suspected` is not alarming (`pkg/audit/audit.go:81-82`, `IsAlarming` is true only for `ChainBroken`), and the query API cross-references `ops_postgres_outage_log` to attribute a gap's cause. The integrity verifier that drives the `AuditChainGap` alert is a different function: `verifyChainWindow` (`pkg/audit/integrity/continuity.go:153`), invoked by the §12.3 startup continuity check (`cmd/lenny-gateway/main.go:1071,1077`) and the §11.7-item-2 periodic check (`pkg/audit/integrity/periodic.go:124-136`, `cmd/lenny-gateway/runserver.go:128`), which emit `lenny_audit_chain_integrity_total{state}` (the `state="broken"` counter drives `AuditChainGap` at `spec/16_observability.md:234` and `pkg/alerting/rules/rules.go:886`). `verifyChainWindow` classifies any `cur.Seq != prev.Seq+1` as `ChainBroken` and returns before it reaches the `prev_hash` link check (`continuity.go:160`), so under Path A a benign `nextval` rollback gap would increment `state="broken"`, fire `AuditChainGap`, and, with `audit.hardFailOnDrift` enabled, initiate a graceful gateway shutdown. S5 therefore reconciles `verifyChainWindow` so a sequence gap whose `prev_hash` link is intact is not `ChainBroken`, and only a sequence gap with a non-linking `prev_hash` (a committed-row tamper or removal) returns `ChainBroken`; the `prev_hash` linkage stays the authoritative tamper signal. An intact-link gap has two chain-indistinguishable causes: a benign transaction rollback that committed no row, and a crash that dropped an accepted buffered T2 batch after its `nextval` calls but before commit (genuine loss, the §12.3 accepted-data-loss tradeoff at `pkg/gateway/audit/auditstore/auditbatch/auditbatch.go:16-19`). The chain gap therefore cannot by itself signal buffered T2 loss, and it never was a reliable completeness signal for that loss under either mechanism: the pre-Path-A `MAX+1` ordinal re-densified after a dropped batch (the next flush re-read the committed tail), and the more common crash loses a buffer before its flush transaction ever calls `nextval`, so no sequence gap forms at all. Buffered T2 crash-window loss is the accepted, unsignaled data-loss tradeoff of the opt-in `audit.batchingEnabled` path, disabled by default and documented at §12.3:81-83 and §12.3:95, where completeness is preserved by the synchronous-by-default write path and the deployer who enables T2 batching accepts the documented data-loss risk. No chain-level alert covers this loss and none is introduced. S6 accordingly removes the false "no lost events" assurance from the §12.3:101 and §16.5:471 text, keeps neither attributing buffered T2 loss to `state="broken"`, and reconciles the single-source `pkg/alerting/rules/rules.go` catalog entry so `state="broken"` denotes only a committed-row tamper or removal (a non-linking `prev_hash`). A post-sweep chain restarting at a non-1 genesis is already accepted by `verifyChainWindow` (its genesis check keys on `rows[0].Seq == 1` at `continuity.go:144`, so a non-1 first row is not flagged) and by the query-API genesis branch (`chain.go:444-447`).
- **Reconcile the provisional renumber-at-flush path (`InsertFromStream`) to the sequence.** `pgstore.go:363-366` documents that the flusher re-derives the sequence under the per-tenant advisory lock exactly like `Append`, discarding the provisional `stream_seq`. Under the sequence model the flusher calls `nextval` at flush time instead of reading `MAX`, matching §11.2.1's "the flusher acquires the Postgres sequence value at flush time, not at buffer time" (`spec/11_policy-and-controls.md:150`). This aligns the code with a spec sentence the current `MAX+1` implementation only approximates.
- **Handle any existing-rows re-seed with `setval`.** A fresh `CREATE SEQUENCE` starts at 1, but `billing_events`/`audit_log` may already hold rows numbered via `MAX+1` from prior operation. On the `CREATE SEQUENCE IF NOT EXISTS` path in the tenant-create handler, when the sequence is newly created for a tenant whose rows predate it, the handler runs `setval()` to the current per-tenant `MAX(sequence_number)` so `nextval` does not collide with an existing `(tenant_id, sequence_number)` primary key. The re-seed runs on the CREATE-privileged DDL connection: that role owns the sequence it just created, so it holds the `UPDATE` privilege `setval` requires, and the migration grants it `SELECT` on `billing_events` and `audit_log` so it can read the per-tenant `MAX(sequence_number)` the re-seed targets (the `lenny_app` pool cannot run the re-seed, because `USAGE` on a sequence permits `nextval` but not `setval`). The `SELECT` grant alone is not sufficient, because `billing_events` and `audit_log` carry `ENABLE`/`FORCE ROW LEVEL SECURITY` with the hard-error tenant-isolation policy `tenant_id = current_setting('app.current_tenant', false)` (`migrations/0002_rls_immutability_roles.up.sql:146-150`, tightened to the hard-error form by `migrations/0051_rls_hard_error_form.up.sql:28,34-40`): the row-level policy still applies to the DDL role, which is not the table owner and holds no `BYPASSRLS`, and the `false` policy form raises `configuration_invalid` when `app.current_tenant` is unset. The re-seed therefore runs inside a tenant-scoped transaction on the DDL connection that first issues `SET LOCAL app.current_tenant = '<tenant_id>'` through the existing `pgtenant.InTx` helper (`pkg/gateway/storage/pgtenant/pgtenant.go:76,91`), so the policy admits the tenant's own rows and both the `MAX(sequence_number)` read and the `setval` succeed. The DDL role is not granted `BYPASSRLS`, which keeps it least-privilege and cross-tenant-isolated: the re-seed reads only the single tenant's rows it is provisioning. Because v1 has no deployments in the wild, this branch is effectively a no-op for a freshly-created tenant with no rows; the `setval` is specified so the mechanism is correct if any rows predate the sequence.

## 3. Proposed changes

Each change states its target and the exact text to insert or a precise change description. The convergence loop tightens every anchor against the current spec and code text.

### S1. Amend §10.2 to require a length-bounded safe-derived sequence name and remove the false DDL-identifier-length safety claim

**Targets:**
- `spec/10_gateway-internals.md`: the §10.2 `tenant_id`-format sentence (`:210`) asserting `^[a-zA-Z0-9_-]{1,128}$` is "safe for use in DDL identifiers (e.g., `billing_seq_{tenant_id}`)."

**Rationale.** The current sentence is a load-bearing self-contradiction: the 128-character format overruns the 63-byte `NAMEDATALEN` limit, so the literal `billing_seq_{tenant_id}` name collides across tenants sharing a 51-character prefix (12-character prefix plus 51 surviving characters is 63 bytes). The format constraint prevents injection and path traversal but not length overflow. Every downstream section (§11.2.1, §15.1, §12.8, §18) that names `billing_seq_{tenant_id}` depends on this being safe.

**Sketch.** Narrow the safety claim to what the format guarantees (no injection, no path traversal) and state that per-tenant DDL identifiers derived from `tenant_id` **must** be length-bounded to ≤ 63 bytes via a deterministic collision-resistant digest, because Postgres truncates identifiers at `NAMEDATALEN-1` (63 bytes) and a 128-character `tenant_id` would otherwise collide across tenants sharing a 51-character prefix. Define the canonical derivation once here, with a per-ledger prefix (`billing_seq_` for billing and `audit_seq_` for audit) so the two ledgers derive distinct per-tenant sequence objects rather than colliding onto one, and reference it from §11.2.1, §11.7 (the audit `audit_seq_` prefix, the committed Path A audit resolution), §15.1, §12.8 (both the teardown cell and the multi-region monotonicity note), and §18 so all sites name the same derived identifier. The digest is the lowercase hex encoding of the first 20 bytes (160 bits) of `SHA-256(tenant_id)`, a fixed 40-hex-character string, so `billing_seq_<40hex>` is 52 bytes and `audit_seq_<40hex>` is 50 bytes, both ≤ 63. Do not add a `tenant_id` length cap below 128, which would narrow the enforced §10.2 format for no benefit once the name is derived.

The current sentence at `:210` is:

```markdown
This format constraint ensures `tenant_id` values are safe for use in DDL identifiers (e.g., `billing_seq_{tenant_id}`), MinIO path prefixes, Redis key prefixes, and log fields without risk of injection or path traversal.
```

It becomes:

```markdown
This format constraint ensures `tenant_id` values are safe for use in MinIO path prefixes, Redis key prefixes, and log fields without risk of injection or path traversal. A per-tenant Postgres DDL identifier derived from `tenant_id` (such as the per-tenant billing or audit sequence) **must** therefore be length-bounded and collision-resistant. ```
```

## 4. Non-goals

- **No `tenant_id` length cap below 128 characters.** The §10.2 format is enforced at multiple boundaries (`pkg/auth/auth.go:253`, and the §17.6 and §27.2 ingestion points), and narrowing it to accommodate a naming choice the S1 derived name already resolves would be a backward-incompatible change.
- **No change to the runtime placement of the `CREATE SEQUENCE` beyond routing it to the billing/audit shard.** It runs from the tenant-create handler at runtime rather than at migration time, because a migration cannot provision sequences for tenants created after it runs, and it runs on the billing/audit shard (`StoreRouter.BillingShard` for `billing_events`, `StoreRouter.AuditShard` for `audit_log`, both resolving the billing/audit instance) rather than the primary pool, so `nextval` resolves the sequence on the same instance in the separate-instance topology. The DDL-privilege the `CREATE SEQUENCE` requires (a role holding `CREATE` on schema `public`) is not settled by the existing `lenny_app` grants, which hold no `CREATE ON SCHEMA`. The resolution is option (a): a distinct CREATE-privileged login role reserved for per-tenant DDL and a dedicated DDL pool built in `cmd/lenny-gateway`, threaded into the admin `Router`. `lenny_app` gains no `CREATE ON SCHEMA` and receives only `USAGE ON SEQUENCE`, which `nextval` requires.
- **The `platform` pseudo-tenant audit sequence is provisioned by the migration rather than by the runtime tenant-creation path.** The `platform` chain carries platform-admin audit events and is not a registered `tenants` row (`migrations/0001_initial_schema.up.sql:131-134`), so it never reaches `provisionTenantSequences`; the migration creates its fixed `audit_seq_<platform-40hex>` sequence (a compile-time-constant name known at migration time) on every audit-bearing instance a platform-chain audit write can reach. Billing needs no equivalent, because `billing_events` has a foreign key to `tenants` (`:160`) and only registered tenants ever hold billing rows, so there is no platform billing chain to provision.
- **No widening of `lenny_app`'s grant and no use of the DDL role for ledger writes.** The DDL role holds `CREATE` on schema `public` on the billing/audit instance and `SELECT` on `billing_events` and `audit_log` (which the `setval` re-seed reads for the per-tenant `MAX(sequence_number)`), and no `INSERT`/`UPDATE`/`DELETE` on either ledger table, so it provisions sequences and reads the ledger to re-seed but never writes or rewrites it; ledger writes stay confined to `lenny_app` (DML) and `lenny_erasure` (the erasure path).
- **No DROP-SEQUENCE at teardown, and no `DROP SEQUENCE` inside `DeleteByTenant`.** `DeleteByTenant` runs as `lenny_erasure`, which holds no `DROP` privilege and cannot execute the statement. An orphaned unused sequence for a tombstoned tenant is inert, and the `tenants` row is retained as a tombstone.
- **No removal of the per-tenant advisory lock from the audit write path.** It serializes `prev_hash` chaining (§11.7:366), a concern orthogonal to sequence assignment. `nextval` replaces the lock only on the billing write path, where there is no hash chain.
- **No change to the §25.9 query-API classifier or the `gap_suspected` enum semantics.** Path A leaves `pkg/audit/chain.go` unchanged and does not change what the `gap_suspected` verdict means. A `nextval` rollback gap surfaces there as the existing advisory, non-alarming `gap_suspected` classification (`:437`), distinguished from an outage gap by the `ops_postgres_outage_log` attribution the §25.9 query API already performs, and a post-sweep non-1 genesis is already accepted by the genesis branch (`:444-447`). The alert-driving integrity verifier is reconciled: `verifyChainWindow` (`pkg/audit/integrity/continuity.go:153`), which the §12.3 startup check and the §11.7-item-2 periodic check run to emit the `lenny_audit_chain_integrity_total{state="broken"}` counter that fires `AuditChainGap`, currently returns `ChainBroken` for any sequence gap before it checks the `prev_hash` link, so S5 reorders it to treat a sequence gap with an intact `prev_hash` link as benign and to break only on a sequence gap with a non-linking `prev_hash`. §11.7:369 and §16:234 keep their existing `gap_suspected` text unchanged, because neither names a Postgres outage as the sole cause of a gap. §25.9 (`:3666`, `:3668`, `:3669`), the §12.3 startup chain-continuity check spec text (`:101`), the §16.5 `AuditChainGap` alert catalog entry (`:471`) and its single-source `pkg/alerting/rules/rules.go:889` counterpart, and the `docs/runbooks/audit-chain-gap.md` runbook are reconciled in S6, because their current text presents a Postgres-unavailable window (or, at §12.3:101 and §16.5:471, a broken hash chain) as the cause of every detected gap, and Path A adds a benign non-outage source (a `nextval` rollback gap with no `ops_postgres_outage_log` window and an intact `prev_hash` chain) that the pre-Path-A dense ordinal never produced; the §25.9 reconciliation adds that non-outage case rather than changing the `gap_suspected` verdict, and the §12.3:101 and §16.5:471 reconciliations match the reconciled `verifyChainWindow` so an intact-`prev_hash`-link sequence gap is detected-but-not-broken and is not the `AuditChainGap` trigger, while the alert expression stays on `state="broken"`. The §12.3:101 and §16.5:471 text also stops reading an intact-link gap as proof of no loss, because a crash-dropped accepted buffered T2 batch leaves an intact-link gap chain-indistinguishable from a benign rollback; buffered T2 crash-window loss is the accepted, unsignaled data-loss tradeoff of the opt-in `audit.batchingEnabled` path (disabled by default, documented at §12.3:81-83 and §12.3:95), which no chain-level alert covers and for which none is introduced.
- **No change to the client-facing gap-detection and replay API (`GET /v1/metering/events?since_sequence`).** The sequence adoption preserves the observable per-tenant monotonic contract that endpoint depends on and does not alter the wire surface.

The resolutions are recorded here for traceability. **(1) Sequence-name derivation:** the canonical §10.2 derivation is a per-ledger literal prefix (`billing_seq_`, `audit_seq_`) followed by the lowercase hexadecimal encoding of the first 20 bytes (160 bits) of `SHA-256(tenant_id)` — a fixed 40-hex-character digest, so `billing_seq_<40hex>` (52 bytes) and `audit_seq_<40hex>` (50 bytes) are both ≤ 63 bytes for every admitted `tenant_id`, and the two prefixes keep the ledgers on distinct sequence objects. **(2) Audit sequencing: Path A.** Audit `sequence_number` is assigned by `nextval` on its own per-tenant `audit_seq_<40hex>` object (distinct from billing's), provisioned on the audit shard (`StoreRouter.AuditShard`) under the retained `prev_hash` advisory lock. S2's Path-A §11.7:365 wording is therefore the live edit, and S5 Path B is dropped. **(3) Re-seed: keep.** The tenant-create helper runs the `setval` re-seed to `MAX(sequence_number)` under `CREATE SEQUENCE IF NOT EXISTS`, an idempotent guard against a `(tenant_id, sequence_number)` PK collision for a tenant whose rows predate the sequence (a no-op in v1). The re-seed runs on the CREATE-privileged DDL connection, which owns the sequence (so it holds the `UPDATE` `setval` requires) and reads the ledger `MAX` through the DDL role's `SELECT` grant on `billing_events` and `audit_log`, inside a `SET LOCAL app.current_tenant = '<tenant_id>'` tenant-RLS context (via the existing `pgtenant.InTx` helper) that the `FORCE ROW LEVEL SECURITY` hard-error policy on both ledger tables requires; the DDL role is not granted `BYPASSRLS`, so the re-seed reads only the tenant it provisions. **(4) DDL privilege: option (a).** The runtime `CREATE SEQUENCE` runs through a distinct CREATE-privileged login role and connection reserved for per-tenant DDL on the billing/audit instance, keeping `lenny_app` least-privilege (`USAGE ON SEQUENCE` only, via `ALTER DEFAULT PRIVILEGES`); the DDL role is reconciled into the §11.7 least-privilege model and is captured by the §11.7 item-5 pgaudit sink, and is never used for ledger writes.

**Why Path A over Path B (verified 2026-07-02, correcting the S5 "dropped alternative" analysis).** Path B was reconsidered and rejected on evidence. The audit ledger is deletion-bearing exactly as billing is — `DeleteByTenant` runs `DELETE FROM audit_log WHERE tenant_id = $1` (`pkg/gateway/audit/auditstore/auditstore.go:488`) and `PruneRetention` hard-deletes rows past the window (`auditstore.go:573`) — so the `MAX+1` advisory-lock ordinal restarts at a lower value after a full sweep or a dormant-then-reactivated tenant, reusing `sequence_number` values just as billing does. The S5 "Analysis carried from the dropped alternative" claims this reuse is benign for audit because "audit has no `since_sequence` replay API … (that contract is billing-only)"; that premise is **false** and must be corrected in the re-converge. The audit `sequence_number` is load-bearing in three places that reuse would break: (1) the **SIEM delivery high-water mark** — the forwarder withholds any row whose `sequence_number` does not exceed the last acknowledged mark in `siem_delivery_state` (`auditstore.go:517-519`; `pkg/audit/siem/outbox.go:41`), which is precisely a `since_sequence` cursor, so a post-sweep restart at a low number silently withholds new audit events from compliance forwarding; (2) the **redaction-receipt binding** on `(tenant_id, sequence_number)` (`pkg/audit/integrity/redaction.go:56`), the "sole provenance token" for a lawful redaction, which reuse can mis-bind to the wrong row; and (3) the **external OCSF export** of `sequence_number` as `metadata.sequence` (`pkg/audit/ocsf/ocsf.go:413`), where reuse creates identity ambiguity in the compliance record. Path A (a real `nextval` audit sequence) keeps all three correct across deletes for the same reason it fixes billing, so the audit fix is warranted on its own merits and is not merely billing-symmetry. The re-converge must (a) correct the S5 false premise, (b) treat the SIEM high-water mark, the receipt `(tenant, seq)` binding, and the OCSF `metadata.sequence` export as consumers the audit-sequence change preserves, and (c) keep the `gap_suspected` enum semantics and the §25.9 query-API classifier unchanged, reconcile the alert-driving integrity verifier `verifyChainWindow` so a benign `nextval` rollback gap with an intact `prev_hash` link is not classified a broken chain (Pass 11: the `AuditChainGap` metric is emitted from `verifyChainWindow`, not `chain.go`, and `verifyChainWindow` breaks on a bare sequence gap before it checks the `prev_hash` link), and reconcile the two doc-and-spec surfaces that present a Postgres outage as the cause of every `gap_suspected` (§25.9:3668 and the audit-chain-gap runbook) so the benign `nextval` rollback gap is recorded as a non-outage source (Pass 10).

The original decision framings follow for reference.

1. **The sequence-name derivation.** Which digest and encoding (truncated SHA-256 hex against base32) and how many bytes of digest to keep. Any collision-resistant fixed-width scheme that keeps `billing_seq_<digest>` and `audit_seq_<digest>` ≤ 63 bytes works; the reviewer confirms the exact derivation to canonicalize in §10.2 so the two ledgers derive distinct per-tenant names under their respective prefixes (billing and audit must never share one sequence object, because a shared `nextval` would interleave the two ledgers' numbers and break billing's dense per-tenant monotonicity and the audit chain's dense within-chain ordinal) and the digest width is fixed once.
2. **The audit sequencing resolution (S5 Path A against Path B).** Path A aligns audit to `nextval` with a chain-verifier reconciliation so a `nextval`-produced sequence does not misclassify a swept-empty or rolled-back chain, keeping billing and audit on one mechanism. Path B amends §11.7:365 to state the audit `sequence_number` is the per-tenant chain ordinal maintained under the `prev_hash` advisory lock, matching the code and removing the audit provisioning and derived-name machinery. Path B is the strictly smaller change; the reviewer picks one.
3. **The re-seed scope for existing rows.** On the `CREATE SEQUENCE IF NOT EXISTS` path in the tenant-create handler, a `setval` re-seeds a tenant whose `billing_events` rows predate the sequence to `MAX(sequence_number)`. Because v1 has no deployments in the wild, a freshly-created tenant has no rows and the branch is a no-op; the reviewer confirms whether the `setval` branch is worth retaining for the pre-existing-rows case or can be omitted.
4. **The DDL privilege for the runtime `CREATE SEQUENCE` (load-bearing).** The tenant-create handler issues `CREATE SEQUENCE`, which requires a role holding `CREATE` on schema `public` on the billing/audit instance where `billing_events` lives (the separate `LENNY_PG_BILLING_AUDIT_DSN` instance when configured, otherwise the primary). The gateway connects as `lenny_app` (`spec/11_policy-and-controls.md:384`), `SET LOCAL app.current_tenant` (`pkg/gateway/storage/pgtenant/pgtenant.go:91`) sets a tenant-id GUC read by RLS rather than a Postgres role, no `SET ROLE` exists in `pkg/` or `cmd/`, and `lenny_app` is created `NOLOGIN` with `USAGE ON SCHEMA public` and table-level DML only (`migrations/0002_rls_immutability_roles.up.sql:22,29,161`), with no `CREATE ON SCHEMA`. The code-only runtime partition-CREATE does not settle this: migration 0149 grants the partition parents only DML (`migrations/0149_eventstore_partitioned_logs.up.sql:71`), so the partition maintainer's runtime `CREATE TABLE` runs either under a role other than `lenny_app` or on an unverified privilege assumption. Without a resolution, the `CREATE SEQUENCE` raises `permission denied for schema public` and the first billing `Append` then fails on `nextval` of a nonexistent relation, breaking tenant creation and billing for every tenant. Three resolutions, in order of preference: (a) provision the `CREATE SEQUENCE` through a distinct CREATE-privileged login role and connection reserved for per-tenant DDL on the billing/audit instance, reconciling the §11.7 least-privilege model and the integrity-verifier surfaces so the DDL-capable role is auditable and never used for ledger writes (recommended, because it keeps `lenny_app` least-privilege and confines the CREATE grant to a role the pgaudit sink at §11.7 item 5 already captures); (b) grant `lenny_app` `CREATE ON SCHEMA public` and reconcile the §11.7 least-privilege model, §12.3, and `pkg/audit/integrity` to the widened grant; (c) abandon runtime `CREATE SEQUENCE` under any per-tenant DDL, in favor of a mechanism that needs no per-tenant DDL. The reviewer confirms the partition maintainer's actual DDL-privilege path before treating it as precedent, and selects the resolution.
