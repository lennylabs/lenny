# Proposal: Concurrent-workspace per-slot execution: reconcile the adapter and reference runtimes to the canonical single-connection slotId-multiplexing model

- **Status:** Approved (2026-06-17). Converged after 5 adversarial review rounds (4 findings fixed); signed off by the human approver. Per-slot inbox routing is gateway-side `session → slot` resolution, and `SLOT_ID_REQUIRED` is an internal fail-closed invariant rather than a client-facing rejection. Slots are an internal mechanism: the client addresses by `session_id` and never supplies a `slotId`. Amended 2026-06-17: the implementation scope adds removal of the vestigial client-facing `MessagePayload.SlotID` field (§4.1.1, §5, §11) — a code-to-spec corollary of the converged design, not a design change.
- **Date:** 2026-06-16.
- **Scope:** Reconciles the adapter, the gateway's per-slot message routing, and a reference runtime to the spec's single-connection `slotId`-multiplexing model for `sessionPolicy.maxConcurrentSessions > 1` pools. The feature is fully specified and internally consistent; two adapter defects, an unimplemented gateway per-slot inbox routing and `SLOT_ID_REQUIRED` rejection (`spec/07:334`), and a missing runtime dispatch loop leave it non-functional in a deployed pod. The reconciliation is code-to-spec: it removes the `--concurrency-style` flag and the `ConcurrentWorkspace` adapter field, routes all slots over the single runtime connection keyed on `slotId` presence, adds the gateway's per-slot inbox routing and `SLOT_ID_REQUIRED` rejection on the coordinating replica, adds a `slotId` dispatch loop to a reference runtime, and adds functional coverage in the canonical test tiers. It stages no spec edit; the spec is already correct.

This document records a code-to-spec reconciliation. It stages no spec, CRD, or chart edit. The spec's single-connection `slotId`-multiplexing model is affirmed as written, and the implementation is brought into line with it. The proposal is a draft for review; the recorded decisions and the Section 7 implementation plan are applied during implementation after sign-off.

## 1. Problem

A session-mode pool with `sessionPolicy.maxConcurrentSessions > 1` multiplexes simultaneous sessions onto one pod, each in its own slot. The spec defines this end to end and the definition is internally consistent: one runtime process per pod, a `slotId` assigned per slot by the adapter, every binary-protocol frame carrying `slotId` when `maxConcurrentSessions > 1` over a single stdin channel, a runtime dispatch loop keyed on `slotId`, and per-slot `cwd`, workspace, and credentials derived from `slotId`. The model is stated verbatim across the spec:

- `spec/05_runtime-registry-and-pool-model.md:509`: "Message delivery uses `slotId` multiplexing over stdin: the adapter assigns a `slotId` per slot, creates the per-slot directory tree, and sets the slot's `cwd` to `/workspace/slots/{slotId}/current/`; the runtime implements a dispatch loop keyed on `slotId`; all binary protocol messages (inbound and outbound) carry `slotId` when `maxConcurrentSessions > 1`."
- `spec/15_external-api-surface.md:1459`: "Runtimes serving a pool with `maxConcurrentSessions > 1` implement a dispatch loop keyed on `slotId` ... This allows multiple independent concurrent session streams through a single stdin channel."
- `spec/06_warm-pod-model.md:384`: "The runtime MUST NOT assume a global `/workspace/current` path when `maxConcurrentSessions > 1`."
- `spec/07_session-lifecycle.md:334`: the `slotId` field in the `MessageEnvelope` determines which slot's inbox receives the message, and "Messages without a `slotId` for such a pod are rejected with `SLOT_ID_REQUIRED`."
- `spec/06_warm-pod-model.md:383` and the per-slot credential layout: per-slot directory trees at `/workspace/slots/{slotId}/`, `/sessions/{slotId}/`, and `/artifacts/{slotId}/`, with the per-slot credential file at `/run/lenny/slots/{slotId}/credentials.json` (`spec/05_runtime-registry-and-pool-model.md:511`).

The feature is non-functional in a deployed pod. The cause is a code-to-spec divergence rather than a missing spec mechanism.

**The gateway slot-bind path is correct; its per-slot message routing is not yet implemented.** A `maxConcurrentSessions > 1` session routes to the slot-bind path (`pkg/gateway/sessionserver/start.go:1252`), the adapter `StartSession` RPC is tagged with a `slotId` (`pkg/gateway/adapterclient/client.go:128-129`), and the `slotId` is reserved by the slot binder (`pkg/gateway/podsession/slotbinder.go`). The gateway already carries both the per-pod `sessionPolicy.maxConcurrentSessions` count (`pkg/gateway/sessionserver/sessionserver.go:2601`) and the envelope `slotId` (`pkg/gateway/sessionserver/messages.go:150`). The per-slot inbox routing that `spec/07:334` assigns to the coordinating gateway replica is not yet built: the `MessageEnvelope` accepts and forwards the `slotId` field but the gateway does not yet implement slot-aware routing (`pkg/gateway/sessionserver/messages.go:144-149`), the `pkg/gateway/sessioninbox` package has zero slot awareness, and the `SLOT_ID_REQUIRED` rejection appears nowhere in `pkg/` (`grep -rn SLOT_ID_REQUIRED pkg/` returns no match). Two downstream adapter implementation defects break the path (Defects 1 and 2), a third gap leaves no runtime able to serve a second slot (Gap 3), and a fourth gap leaves the spec-mandated per-slot routing and `SLOT_ID_REQUIRED` rejection unimplemented at the gateway (Gap 4).

**Defect 1: the adapter gates the per-slot path on a flag no production component passes.** The adapter takes its per-slot code path only when the `Server` field `ConcurrentWorkspace` is `true`: `useSlot` returns `s.ConcurrentWorkspace && slotID != ""` (`pkg/adapter/slot.go:62`). That field is set solely by the `cmd/lenny-adapter --concurrency-style=workspace` CLI flag (`cmd/lenny-adapter/main.go:119`, `:351-352`), which no controller, pod-spec builder, or Helm chart passes. The Sandbox pod-spec builder constructs the adapter args with a single static `--runtime-socket=@lenny-runtime` and never passes `--concurrency-style` (`pkg/controller/sandbox/podspec/podspec.go:519`); the chart passes nothing. So in every deployed pod `useSlot` is `false`: the first `slotId`-tagged `StartSession` falls through to the single-session base path and `claimSession` succeeds with the `slotId` ignored, and the second concurrent session is rejected with `codes.Unavailable` `"pod is not idle: session %s is already assigned"` (`pkg/adapter/session.go:103`, `:117`, `:331`). The pool serves one session per pod.

**Defect 2: even with the flag set, the adapter is structured as N runtime processes per pod.** Under `--concurrency-style=workspace` the adapter installs a per-slot `RuntimeFactory` (`cmd/lenny-adapter/main.go:357`) that dials a per-slot socket `@lenny-runtime-{slotId}` (`main.go:362`) or spawns a per-slot subprocess, each a `SocketRuntimeProcess` that "drives one session at a time" on its own `net.Listen` (`pkg/adapter/socketruntime.go:42-43`, `:69`) and carries no `slotId` on the wire. The field doc names this the "§6.4 N concurrent runtime processes per pod topology" (`pkg/adapter/server.go:83-91`). This contradicts the spec's one-runtime-process-per-pod single-connection model and is unimplementable in the §4.7 sidecar pod: the runtime container is given exactly one static `LENNY_ADAPTER_SOCKET=@lenny-runtime` environment variable at pod-spec build time (`pkg/controller/sandbox/podspec/podspec.go:159`, `:164`, `:538`), the adapter listens and the runtime dials (`pkg/runtimekit/transport.go:15-20`), and Kubernetes cannot inject dynamic per-slot socket names into a static container.

**Gap 3: no reference runtime implements a `slotId` dispatch loop.** An exhaustive grep for `slot`, `slotId`, and `slot_id` across `cmd/runtimes/` and `pkg/runtimekit/` returns zero matches. The shared `echocore` loop dispatches on the frame `type` field only (`pkg/runtimekit/echocore/echocore.go`), and `cmd/runtimes/echo-embedded/main.go:73-75` records the per-slot tree as unbuilt in v1. Even if the adapter activated, a pod could not serve a second slot because no runtime demultiplexes `slotId`.

**Gap 4: the gateway does not implement the per-slot inbox routing `spec/07:334` assigns it.** `spec/07:334` assigns the per-slot inbox routing to the coordinating gateway replica: each active slot maintains its own inbox and path evaluation runs per slot. Slots are an internal mechanism, so the gateway resolves the target slot from the session: a client or inter-session sender addresses a message by `session_id` and never supplies a `slotId`, the gateway maps the `session_id` to its bound slot (1:1 per `pkg/gateway/podclaim/slotclaimer.go:621`, `:168`), routes the message to that slot's inbox, and stamps the resolved `slotId` on the outbound adapter `MessageEnvelope`. The gateway accepts and forwards the `slotId` field but does not yet implement slot-aware routing (`pkg/gateway/sessionserver/messages.go:144-149`), the `pkg/gateway/sessioninbox` package has zero slot awareness, and `SLOT_ID_REQUIRED` appears nowhere in `pkg/`. The gateway already carries the session→slot binding, the per-pod `sessionPolicy.maxConcurrentSessions` count (`pkg/gateway/sessionserver/sessionserver.go:2601`), and the envelope `slotId` field (`pkg/gateway/sessionserver/messages.go:150`) it stamps. Without this routing, messages on a concurrent pod are not separated per slot: the inbox-buffering paths (`input_required`, runtime-busy, suspended) buffer in the gateway inbox without per-slot separation, and there is no internal `SLOT_ID_REQUIRED` fail-closed guard against per-slot dispatch reaching a `maxConcurrentSessions > 1` pod with no resolvable slot for the session.

The end-to-end path is unexercised: `tests/tier7b_load_kind/scaffolds_test.go:301-307` skips `TestConcurrentWorkspaceSlots` with the note that the gateway exposes no per-slot endpoint, so nothing tests the path.

**What is already in place.** The per-slot filesystem tree work landed: `pkg/adapter/slotlayout/` exists and `BUILD-GAPS.md` F-6.4.2 is marked CLOSED. The proto `SlotId` message and `slot_id` field are already threaded through `StartSession`, `PrepareWorkspace`, `FinalizeWorkspace`, `RunSetup`, `SendMessage`, and `ReportSessionScrub` (`schemas/lenny-adapter.proto:555`, `:417`, `:648`, `:686`, `:808`, `:886`, `:924`), and the binary-protocol `MessageEnvelope` already carries `slotId` (`spec/15_external-api-surface.md:1440-1452`). No new wire surface is needed. What remains is to route the adapter per slot over the single connection keyed on `slotId` presence, to add the gateway's per-slot inbox routing and `SLOT_ID_REQUIRED` rejection on the coordinating replica (`spec/07:334`), to add a `slotId` dispatch loop to a reference runtime, and to add functional coverage in the canonical test tiers.

Findings: **F-6.4.2** (`BUILD-GAPS.md:5305`, marked CLOSED with the landed N-process topology) is reopened by this reconciliation; implementing the single-connection model files a fresh Resolution note recording the landed design through the build-gaps flow (Section 6).

## 2. Decisions

The following were decided in review and constrain this design.

- The spec's single-connection `slotId`-multiplexing model is canonical and is affirmed as written. One runtime process per pod, a `slotId` assigned by the adapter, every binary-protocol frame carrying `slotId` when `maxConcurrentSessions > 1` over the single connection, and a runtime dispatch loop keyed on `slotId` are already specified at `spec/05:509`, `spec/15:1459`, `spec/06:384`, and `spec/07:334`. The N-runtime-processes-per-pod structure in `cmd/lenny-adapter` and `pkg/adapter` is the defect and is removed.
- This is a code-to-spec reconciliation (kind: fix) that stages no spec edit. The single-channel `slotId` transport is not a missing spec mechanism: `spec/15:1459` and `spec/05:509` already specify the single stdin channel, the adapter-assigned `slotId`, the runtime dispatch loop, slot assignment (`spec/05:509`), and per-slot teardown and release (`spec/05:537`). The sidecar mapping of that single stdin channel onto the single runtime connection is the established spec-wide model (`spec/04:869` "Same external contract either way"; `pkg/runtimekit/transport.go` carries the same JSONL frames over one socket), which `slotId` frames inherit.
- Per-slot routing in the adapter keys on `slotId` presence in the binary-protocol frame rather than on a mode flag or capability. The `--concurrency-style` mode-selector CLI flag (`cmd/lenny-adapter/main.go:119`) and the `ConcurrentWorkspace` boolean `Server` field (`pkg/adapter/server.go:74`) are removed; `useSlot` (`pkg/adapter/slot.go:62`) collapses to `slotID != ""`. This matches `spec/15:1459`: runtimes on `maxConcurrentSessions: 1` pods never see `slotId`, so a `slotId`-bearing frame is by definition a concurrent-pool frame. The adapter needs no per-pod concurrency count: a frame either carries a `slotId` (per-slot path) or does not (whole-pod base path), and `useSlot` reads that directly. No deployments exist in the wild, so the mode flag and boolean field are deleted with no migration shim.
- Per-slot inbox routing on the coordinating gateway replica resolves the target slot **from the session** rather than from a client-supplied field, because slots are an internal mechanism. A client or inter-session sender addresses a message by `session_id` (`POST /v1/sessions/{id}/messages`; `lenny/send_message` targeting a session id) and never supplies a `slotId`; `slotId` is adapter-assigned and lives only on the adapter↔runtime envelope (`spec/15:1459` "the adapter assigns a `slotId` per slot"), and in the gateway the slot is 1:1 with the session (`pkg/gateway/podclaim/slotclaimer.go:621` sets `SlotID: req.SessionID`; `:168` "one session occupies exactly one slot"). So `spec/07:334`'s per-slot inbox routing is realized as: the gateway maps the target `session_id` to its bound slot, routes the message to that slot's inbox, runs path evaluation (paths 1-7) per slot, and stamps the `slotId` on the **outbound** adapter `MessageEnvelope`. The gateway already holds the session→slot binding and the per-pod `sessionPolicy.maxConcurrentSessions` count (`pkg/gateway/sessionserver/sessionserver.go:2601`); the adapter gains no `MaxConcurrentSessions` field, no `--max-concurrent-sessions` flag, and no Sandbox-spec or CRD plumbing.
- `SLOT_ID_REQUIRED` is an internal fail-closed invariant rather than a client-facing rejection. A legitimate client or inter-session message never carries a `slotId`, so a gateway rule that rejected inbound messages lacking one would reject every message to a concurrent pod. It fires only if the gateway's own per-slot dispatch is reached for a `maxConcurrentSessions > 1` pod without a resolvable slot for the session (a routing bug): the gateway fails closed rather than misdelivering to another session's slot. `spec/07:334`'s wording ("Messages without a `slotId` for such a pod are rejected with `SLOT_ID_REQUIRED`") reads ambiguously as an inbound client field when taken in isolation; Section 6 records the decision that no clarifying spec edit to §7.2 is staged, because `spec/15:1711`'s adapter-injected classification of `slotId` makes the wording adequately read as the gateway-internal invariant.
- The `ConcurrentWorkspace` concept is not removed from the spec. The `--concurrency-style` mode-selector flag and its `ConcurrentWorkspace` adapter `Server` field are removed, and the adapter's `concurrentWorkspace` capability advertisement is removed with them. The advertisement is structurally coupled to the removed field: `advertisedCapabilities()` appends the token only when `s.ConcurrentWorkspace` is true (`pkg/adapter/server.go:403-404`), so deleting the field orphans both the advertisement and the `CapabilityConcurrentWorkspace` constant (`pkg/adapter/slot.go:55`), whose only referents are those two advertisement lines. No `pkg/gateway` code reads the token: the slot-bind path gates on `match.MaxConcurrentSessions > 1` (`pkg/gateway/sessionserver/start.go:1252`), and the slot binder never inspects the capability set, so the token is advertised today but never consumed. The token's enumeration in the proto doc comment (`schemas/lenny-adapter.proto:1386`) is a non-exhaustive list ("includes (but is not limited to)") and stays as documentation. `ConcurrentWorkspaceCredentialSharing` remains a current CRD condition (`spec/13_security-model.md:29`) and is left untouched.
- No new protocol surface. The proto `SlotId` message (`schemas/lenny-adapter.proto:555`) and the `slot_id` field are already carried on every relevant adapter RPC (`StartSession:886`, `PrepareWorkspace:648`/`:686`, `RunSetup:808`, `SendMessage:924`, `ReportSessionScrub:417`). The binary-protocol `MessageEnvelope` already carries `slotId` (`spec/15:1440-1452`). The reconciliation reuses these surfaces and introduces no new RPC, frame, field, or endpoint.
- Scope is the four confirmed gaps: route the adapter per slot over the single runtime connection and activate on `slotId` presence (`pkg/adapter`, `cmd/lenny-adapter`); add the gateway's per-slot inbox routing and `SLOT_ID_REQUIRED` rejection on the coordinating replica (`pkg/gateway/sessionserver`, `pkg/gateway/sessioninbox`, `spec/07:334`); add a `slotId` dispatch loop to a reference runtime (`cmd/runtimes`); add functional concurrent-slot coverage in the canonical test tiers (Section 5).
- This proposal is independent of proposal 0002. 0002 re-keyed the `concurrencyStyle`/execution-mode terminology onto `maxConcurrentSessions` and made comment-only edits to `cmd/lenny-adapter/main.go` and `cmd/runtimes/echo-embedded/main.go` (git log: "0002 cleanup: re-key stale task/concurrent-mode comments"); it changed neither the flag gating nor the missing dispatch loop.
- v1 ships one implementation per concern with no tier-dependent code paths. The adapter keeps a single `slotId`-keyed routing path that degenerates to the whole-pod session when no `slotId` is present (`spec/15:1459`), rather than two parallel single-session and per-slot paths gated by a flag.
- The `slotId` dispatch loop lands in a new dedicated concurrent-capable reference runtime, `cmd/runtimes/echo-concurrent`, rather than as an extension of the shared `pkg/runtimekit/echocore` loop. The shared `echocore` loop and the existing single-session runtimes (`echo`, `streaming-echo`, `echo-embedded`) are left unchanged, so per-slot multiplexing stays out of every single-session runtime's hot path. The new runtime reuses the shared `runtimekit` transport and `echocore`'s per-frame handling as composable primitives, adding the `slotId`-keyed demultiplexing as its own front loop. This resolves the Section 8 decision.

## 3. Design overview

The gateway already assigns and tags `slotId` on the slot-bind path. The reconciliation makes the adapter and a reference runtime honor it over the single runtime connection, and adds the per-slot inbox routing at the gateway, where `spec/07:334` assigns it. Slots are internal: a client or inter-session sender addresses a message by `session_id` and never supplies a `slotId`. On a `maxConcurrentSessions > 1` pod the gateway resolves the target `session_id` to its bound slot, routes the message to that slot's inbox, runs path evaluation (paths 1-7) per slot, and stamps the resolved `slotId` on the **outbound** adapter `MessageEnvelope`; the gateway already holds the session→slot binding (`pkg/gateway/podclaim/slotclaimer.go:621`) and the per-pod `sessionPolicy.maxConcurrentSessions` count (`pkg/gateway/sessionserver/sessionserver.go:2601`), and stamps the existing envelope `slotId` field (`pkg/gateway/sessionserver/messages.go:150`). `SLOT_ID_REQUIRED` is an internal fail-closed invariant that fires only when the gateway's own per-slot dispatch is reached for a `maxConcurrentSessions > 1` pod and the gateway cannot resolve a slot for the session (a routing bug), so the gateway fails closed rather than misdelivering to another session's slot. Per-slot routing in the adapter derives from the frame: a `slotId`-bearing frame takes the per-slot path, and a frame without a `slotId` keeps the whole-pod base path. The single runtime process serves all slots; outbound frames to the runtime carry `slotId`, and inbound frames from the runtime are demultiplexed by `slotId` to the originating slot's stream. Per-slot `cwd`, workspace, sessions, artifacts, and credentials continue to derive from `slotId` via the existing `slotlayout` package.

```
Gateway slot-bind path + per-slot inbox routing            (0) resolve session->slot;
  StartSession(slotId), SendMessage(slotId), ...               route to slot inbox;
  per-slot inbox on coordinating replica (spec/07:334)         stamp outbound slotId;
  resolve session->slot, stamp outbound slotId                 fail closed (SLOT_ID_REQUIRED)
        |                                                       only if no slot resolves
        v
Adapter: route per slotId over ONE runtime connection      (1) remove mode flag;
  useSlot(slotID) == (slotID != "")                            route on slotId presence;
  outbound frames -> runtime carry slotId                      no MaxConcurrentSessions
  inbound frames <- runtime demultiplexed by slotId            field in the adapter
        |
        |  single LENNY_ADAPTER_SOCKET connection (one runtime process per pod)
        v
Reference runtime: dispatch loop keyed on slotId           (2) add slotId loop;
  per-slot cwd = /workspace/slots/{slotId}/current/             per-slot cwd per spec/06:384
  per-slot state map; response echoes slotId
        |
        v
Functional coverage in canonical tiers                     (3) tier-4 flow assertion;
  two maxConcurrentSessions>1 sessions on one pod              re-key tier-12 load fixture
  in distinct slots with isolated workspaces                   (scenarios already exist)
```

No new RPC, frame, field, or endpoint is introduced. The single connection from `runtimekit.Open` (`pkg/runtimekit/transport.go`) is unchanged; the dispatch loop multiplexes `slotId` over it.

## 4. Detailed design

### 4.1 Adapter per-slot routing over the single runtime connection (C2)

This is the core code-to-spec reconciliation. `useSlot` currently gates on `s.ConcurrentWorkspace` (`slot.go:62`), set only by `--concurrency-style=workspace` (`main.go:351-352`), which no production component passes, so the per-slot path is dead in every deployed pod and a second concurrent session is rejected with `"pod is not idle"` (`session.go:331`). The per-slot `RuntimeFactory` (`main.go:357-368`) dials per-slot `@lenny-runtime-{slotId}` sockets (`main.go:362`), the N-processes-per-pod structure that contradicts the single-connection spec model and cannot be served in the §4.7 sidecar pod (one static `LENNY_ADAPTER_SOCKET=@lenny-runtime` per `pkg/controller/sandbox/podspec/podspec.go:538`).

The reconciliation:

- Remove the `--concurrency-style` mode-selector flag (`main.go:119`) and its activation block (`main.go:351-369`), including the per-slot `RuntimeFactory`. Preserve the per-slot root wiring that the block sets today: the `WorkspaceBase = filepath.Dir(*workspaceRoot)` and `ArtifactsRoot = *artifactsRoot` assignments (`main.go:353-354`) move out of the deleted block and become unconditional, set alongside the existing unconditional `SessionsRoot` (`main.go:258`) and `CredentialsDir` (`main.go:319`) assignments. `concurrentRoots()` reads `s.WorkspaceBase` and `s.ArtifactsRoot` (`slot.go:72`, `:74`), and `slotlayout.Resolve` gates per-slot path construction on each root being non-empty (`slotlayout.go:140`, `:148`); leaving these two assignments inside the removed block would empty both roots and leave the per-slot `/workspace/slots/{slotId}/current/` and `/artifacts/{slotId}/` trees unmaterialized (`spec/06:384`) in every deployed pod. Both roots derive from the always-defaulted `--workspace-root` (`/workspace/current`, `main.go:110`) and `--artifacts-root` (`/artifacts`, `main.go:116`) flags, so the unconditional assignments reproduce the production paths.
- Remove the `ConcurrentWorkspace` boolean `Server` field and the `RuntimeFactory` field (`server.go:74`, `:83-91`), the now-orphaned `concurrentWorkspace` advertisement in `advertisedCapabilities()` that the field gates (`server.go:403-404`), and the unused `CapabilityConcurrentWorkspace` constant (`slot.go:55`), whose only referents are those two advertisement lines. Removing the field without removing the advertisement would fail the tier-0 build (the advertisement references the deleted field) and leave the constant unused. No `pkg/gateway` code reads the token: the slot-bind path gates on `match.MaxConcurrentSessions > 1` (`pkg/gateway/sessionserver/start.go:1252`), so dropping the advertisement changes no routing behavior. The adapter gains no replacement concurrency field. The adapter does not need a per-pod concurrency count: per-slot routing keys on `slotId` presence alone, and the `SLOT_ID_REQUIRED` rejection that needs the per-pod count is enforced at the gateway (Section 4.1.1), where the count and the envelope `slotId` already live. Adding a `--max-concurrent-sessions` flag, an adapter `MaxConcurrentSessions` field, a Sandbox-spec field, and a WarmPoolController stamp would build a per-pod-count plumbing chain for a rejection the spec locates elsewhere; `sessionPolicy.maxConcurrentSessions` deliberately lives only in the gateway poolstore per the §4.6.3 ownership boundary (`pkg/controller/poolscaling/poolstoresource.go:105-106`) and is on no CRD the cluster controllers read, so neither the WarmPoolController nor the sandbox controller can obtain it to stamp.
- Reduce `useSlot` to `return slotID != ""` (`slot.go:62`) so a `slotId`-bearing frame takes the per-slot path and a frame without a `slotId` keeps the whole-pod base path. This matches `spec/15:1459`: a `slotId`-bearing frame is by definition a concurrent-pool frame. The per-slot routing decision keys only on `slotId` presence.
- Rework the per-slot machinery (`slotsession.go`, the `slotState` in `slot.go`) so a single runtime process, the existing single `Runtime` driven over the one `LENNY_ADAPTER_SOCKET` connection, serves all slots. Outbound frames to the runtime carry `slotId`; inbound frames from the runtime are demultiplexed by `slotId` to the originating slot's stream. Per-slot `cwd`, workspace, sessions, artifacts, and credentials continue to derive from `slotId` via the existing `slotlayout` package and the per-slot credential layout, fed by the now-unconditional `WorkspaceBase`, `ArtifactsRoot`, `SessionsRoot`, and `CredentialsDir` roots described above.
- Update `SocketRuntimeProcess` from "drives one session at a time" to multiplexing `slotId`-tagged frames over its single connection, or replace it with a multiplexing wrapper.

### 4.1.1 Gateway per-slot inbox routing (C4)

`spec/07:334` assigns per-slot inbox routing to the gateway's coordinating replica: "each active slot maintains its own independent inbox on the coordinating gateway replica ... Path evaluation (paths 1-7 above) is performed per slot." Slots are internal: a client or inter-session sender addresses a message by `session_id` (`POST /v1/sessions/{id}/messages`; `lenny/send_message` targeting a session id) and never supplies a `slotId`. `slotId` is adapter-assigned (`spec/15:1459`) and, in the gateway, is 1:1 with the session (`pkg/gateway/podclaim/slotclaimer.go:621` sets `SlotID: req.SessionID`; `:168` "one session occupies exactly one slot"). The gateway therefore resolves the slot **from the target session** rather than from an inbound envelope field. The adapter is a transport: its `SendMessage` RPC writes the envelope verbatim to the agent's stdin (`schemas/lenny-adapter.proto:925-926`), and per `spec/06:383-386` its per-slot duties are filesystem and `cwd` management and slot cleanup, never message-envelope routing. The inbox-buffering paths (path 3 `input_required`, path 5 runtime-busy, path 6 suspended) buffer in the gateway inbox and never reach the adapter, so per-slot routing must be a gateway concern.

The gateway routing is currently unimplemented: the `MessageEnvelope` accepts and forwards the `slotId` field but the gateway does not implement slot-aware routing (`pkg/gateway/sessionserver/messages.go:144-149`), and the `pkg/gateway/sessioninbox` package has zero slot awareness. The gateway already carries the session→slot binding and the per-pod `sessionPolicy.maxConcurrentSessions` count (`pkg/gateway/sessionserver/sessionserver.go:2601`).

The reconciliation:

- In the gateway message-routing path (`pkg/gateway/sessionserver` message handling and the `pkg/gateway/sessioninbox` inbox machinery), on a `maxConcurrentSessions > 1` pod resolve the target `session_id` to its bound slot, route the message to that slot's inbox, and run path evaluation (paths 1-7) per slot rather than per pod, so a message for one session's slot can be delivered while another slot is in `input_required`. A message to a single-session pod (`maxConcurrentSessions <= 1`) keeps the whole-pod routing unchanged.
- Stamp the resolved `slotId` on the **outbound** adapter `MessageEnvelope` (the existing `slotId` field) so the adapter's per-slot routing and the runtime's dispatch loop key on it. The client neither sees nor sets `slotId`.
- Remove the vestigial client-facing `slotId` from the inbound message body: delete the `MessagePayload.SlotID` field (`pkg/gateway/sessionserver/messages.go:150`, tagged `json:"slotId,omitempty"`) and its doc comment. `slotId` is adapter-injected (`spec/15:1711`) and internal; the client addresses a message by `session_id` (the path parameter on `POST /v1/sessions/{id}/messages`) and the gateway derives the slot from the session, so the request body must carry no client-settable `slotId`. The field is inert today (declared and deserialized but never read by the handler), so its removal makes a stray client-supplied `slotId` silently ignored rather than accepted onto the wire.
- Treat `SLOT_ID_REQUIRED` as an internal fail-closed invariant rather than a client-facing rejection. A legitimate client or inter-session message never carries a `slotId`, so there is no inbound "missing-`slotId`" message to reject; the slot is derived from the session. The invariant fires only if the per-slot dispatch is reached for a `maxConcurrentSessions > 1` pod and the gateway cannot resolve a slot for the session (a routing bug), failing closed rather than misdelivering to another session's slot.

The reconciled adapter keeps a single `slotId`-keyed routing path. A frame with no `slotId` degenerates to the whole-pod session, so the single-session pool behaves exactly as it does today.

### 4.2 Reference runtime `slotId` dispatch loop (C3)

Even with the adapter reconciled, a pod cannot serve a second slot because no reference runtime implements the `slotId` dispatch loop the spec mandates. `echocore` (`pkg/runtimekit/echocore/echocore.go`) dispatches on the frame `type` field only, and `cmd/runtimes/echo-embedded/main.go:73-75` records the per-slot tree as unbuilt in v1. `spec/05:509`, `spec/15:1459`, and `spec/06:384` require the runtime to run a dispatch loop keyed on `slotId` and to derive `cwd` per slot from `/workspace/slots/{slotId}/current/`, never assuming a global `/workspace/current` when `maxConcurrentSessions > 1`. A reference runtime must demonstrate this so the conformance and end-to-end paths have a working multiplexing runtime.

The reconciliation adds a new dedicated concurrent-capable reference runtime, `cmd/runtimes/echo-concurrent`, that implements the `slotId` dispatch loop. The shared `pkg/runtimekit/echocore` loop and the existing `echo`, `streaming-echo`, and `echo-embedded` runtimes stay single-session and are not modified. The new runtime reuses the shared `runtimekit` transport and `echocore`'s per-frame handling as primitives, adding the `slotId`-keyed front loop:

- Parse the optional `slotId` field on each inbound frame (`spec/15:1440-1452`) and maintain per-slot state keyed on `slotId`.
- When `slotId` is present, derive `cwd` as `/workspace/slots/{slotId}/current/` (`spec/06:384`), echo the response with the same `slotId`, and keep an independent per-slot sequence counter.
- When `slotId` is absent, retain the single-session whole-pod behavior (`spec/15:1459`: runtimes on `maxConcurrentSessions: 1` pods never see it), so `echo-concurrent` also serves a single-session pod correctly.
- Guard the per-slot state map with a mutex; a per-slot sequence counter replaces the single-session counter.

The single connection from `runtimekit.Open` (`pkg/runtimekit/transport.go`) is unchanged. It already returns one reader and one writer over the single `LENNY_ADAPTER_SOCKET` connection; the new runtime's front loop multiplexes `slotId` over it. Keeping the loop in a dedicated runtime leaves the shared `echocore` loop and the single-session runtimes untouched (the resolved Section 8 decision).

### 4.3 Why the single-connection model holds in the sidecar pod

The §4.7 sidecar pod gives the runtime container exactly one static `LENNY_ADAPTER_SOCKET=@lenny-runtime` environment variable at pod-spec build time (`pkg/controller/sandbox/podspec/podspec.go:159`, `:164`, `:538`). The adapter listens and the runtime dials over that one socket (`pkg/runtimekit/transport.go:15-20`). Kubernetes cannot inject dynamic per-slot socket names into a static container, so the removed per-slot `@lenny-runtime-{slotId}` factory could never have been served in a deployed pod. The deployed pod can carry only the single-connection multiplexing model, and that is the model the spec already specifies (`spec/15:1459`, `spec/04:869`).

## 6. Proposed spec changes

This proposal stages no spec edit. The single-connection `slotId`-multiplexing model is already specified end to end and is internally consistent (`spec/05:509`, `spec/15:1459`, `spec/06:384`, `spec/07:334`), so there is no spec defect, contradiction, or gap to correct. The reconciliation is entirely on the code side: the adapter and a reference runtime are brought into line with the spec, the gateway gains the per-slot inbox routing and the internal `SLOT_ID_REQUIRED` fail-closed invariant the spec already assigns it, and functional coverage is added in the canonical test tiers.

**Decision on the `spec/07:334` wording (deferred from Section 2).** No clarifying spec edit to §7.2 is staged.
