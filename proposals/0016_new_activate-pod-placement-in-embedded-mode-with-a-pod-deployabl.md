# Proposal: Activate pod placement in Embedded Mode with a pod-deployable echo runtime

- **Status:** Approved (2026-06-21); signed off by the project owner for implementation. Verified (2026-06-21); converged after 7 adversarial review rounds (6 findings fixed). Open decisions (§8) resolved at sign-off: (1) ship the pre-built echo-embedded tarball alongside the `lenny` binary and import it offline (C3 as written); (2) surface the runnable echo default in the `lenny up` output by augmenting the placeholder-pin warning; (3) keep `chat` as the user-facing named default while echo runs credential-free out of the box — the §26.7 user-facing default flip remains a separate proposal.
- **Date:** 2026-06-21.
- **Scope:** Activates the §4.7 pod-placement path in Embedded Mode (`lenny up`) for one credential-free runtime. The gateway-side placement path is already implemented and gated solely on a non-empty `--agent-namespace` flag (`cmd/lenny-gateway/main.go:755-756,2414,2587`), but the embedded stack never sets it (`pkg/embedded/stack/gateway.go:16-62,128`), so the embedded gateway always selects the in-process echo executor (`cmd/lenny-gateway/runtime_select.go:47`) and no Sandbox is ever placed (`BUILD-GAPS.md` F-17.4.12, DEFERRED). Activating placement needs a pullable image, which the §26 reference catalog does not have: every entry is placeholder-pinned and unpullable (`pkg/embedded/stack/catalog.go:97,142,197,211,218,229,236`). A pod-deployable, credential-free echo runtime image already exists in-tree (`cmd/runtimes/echo-embedded/main.go`, built by `Makefile:47`, pod-deployed in the Kind e2e infra at `tests/testinfra/kind/install.sh:100`). This proposal threads `AgentNamespace` through the embedded gateway spec, threads the agent namespace into the embedded controller so the PoolScalingController materializes the seeded pool into a SandboxWarmPool CRD, applies an echo Runtime CRD with `deploymentModel: embedded`, imports the echo-embedded image into the embedded containerd at bring-up through the existing `lenny image import` primitive, registers echo in the Embedded Mode catalog as a credential-free single-pod warm pool, and re-points the tier-4 smoke at the runnable echo runtime. It stages a §17.4, §26.7, and §26.1 spec edit (an appended passage on the "Reference runtimes pre-installed" paragraph, a reconciliation of the existing `warmCount: 0` cold-start sentence, and a reconciliation of the sites that present a placeholder-pinned reference-runtime session as the working zero-config flow: the §17.4 quickstart block, the §17.4 custom-runtime walkthrough step 4, the §26.7 use-case sentence, and the §26.1 day-one-utility purpose) plus the code and test changes for the implementation step. The OS/substrate decision stays confined to the substrate-provisioning layer (`pkg/embedded/stack`), preserving the §17.4 no-mode-dependent-business-logic-split invariant: the gateway executor selection stays the identical config-driven dispatch production uses.

This document stages the proposed spec change plus the code and test changes for the implementation step. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off. The spec edit (C1) lands first via implement-proposal; the code and test changes (C2–C5) implement against the committed spec.

## 1. Problem

§17.4 documents Embedded Mode (`lenny up`) as the primary path for deployers evaluating Lenny on a workstation, and "the recommended primary path for runtime authors" because "it exercises the real Kubernetes code path and the production gateway/controllers against the embedded stack" (`spec/17_deployment-topology.md:282`). Reaching a pod over the §4.7 boundary is the property that distinguishes Embedded Mode from the controller-simulator Source and Compose modes. Today Embedded Mode never reaches a pod.

### 1.1 The gateway-side placement path is complete but never activated

The gateway places each started session on a warm pod when `--agent-namespace` is set: the flag is documented at `cmd/lenny-gateway/main.go:755-756` ("the gateway places each started session on a warm pod via the §4.7 adapter instead of the in-process executor"), and the placer, cluster client, lease, and binder wiring plus the swap to `executor.NewPodExecutor` all live inside the single `if *agentNamespace != ""` block (`cmd/lenny-gateway/main.go:2414-2604`, swap at `:2587`). Without the flag, the gateway falls through to the default branch of `resolveExecutor` and selects the in-process echo executor (`cmd/lenny-gateway/runtime_select.go:47`, "in-process echo runtime (default)").

The embedded stack never sets the flag. `gatewayArgs()` emits `-addr`, `-dev-mode`, `-multi-tenant`, `-no-environment-policy allow-all`, `-redis-allow-insecure`, and conditionally `-bearer-trust-hmac-key-file` and `-grpc-addr` (`pkg/embedded/stack/gateway.go:128-160`). The `gatewaySpec` struct carries no agent-namespace field (`pkg/embedded/stack/gateway.go:16-62`), and no `AgentNamespace`, `--agent-namespace`, or `LENNY_AGENT_NAMESPACE` wiring exists anywhere under `pkg/embedded/`. So the embedded gateway always uses the in-process echo executor; no SandboxClaim or Sandbox is created, and the §4.7 placement, adapter, and mTLS pod path is inert in Embedded Mode (`BUILD-GAPS.md` F-17.4.12, DEFERRED).

### 1.2 Proposal 0013 cleared the cross-platform substrate blocker

Proposal 0013 (merged, commit `18ca14dd`) reworked `SupportedPlatform()` so the embedded k3s comes up cross-platform and wired the §4.7 cross-boundary dial host onto agent pods (`pkg/embedded/stack/stack.go:464,489` — `127.0.0.1` on Linux, `host.docker.internal` under the Docker VM). The §4.7 callback boundary is in place; placement is not activated over it.

### 1.3 The remaining blocker is a runnable image rather than the §4.7 boundary

Every §26 reference runtime in `pkg/embedded/stack/catalog.go` is pinned to an unpullable placeholder digest (`placeholderDigest = "@sha256:0000…0"` at `catalog.go:97`, applied at `catalog.go:142,197,211,218,229,236`; `hasPlaceholderDigest` at `catalog.go:256`). Flipping `--agent-namespace` on today would make every `lenny session new` mint a Sandbox whose image is an unpullable placeholder and fail with ImagePullBackOff.

The spec's only credential-free runtime, echo, is the §15.4.4 conformance exemplar embedded in the platform repo, classified separately from the §26 reference runtimes (`spec/26_reference-runtime-catalog.md:10`). The embedded catalog has no echo entry (a grep of `catalog.go` for `echo` returns nothing). A pod-deployable, credential-free echo runtime image already exists in-tree: `cmd/runtimes/echo-embedded/main.go` is a single container that links the §4.7 adapter and serves the adapter gRPC contract directly (the same §15.4.1 echocore loop as `cmd/runtimes/echo`, with no LLM credentials), built via the repo-root Dockerfile with `BINARY=runtimes/echo-embedded` (`Makefile:47`) and already pod-deployed under a resolved (pullable) digest in the Kind e2e infra (`tests/testinfra/kind/install.sh:100`).

### 1.4 Placement also needs a pool to claim from

The embedded bootstrap registers runtime records only and creates no warm pool (`pkg/embedded/stack/runtimes.go:28-32`). The gateway binder claims a pod from a named SandboxWarmPool and returns the `podclaim.ErrNoIdlePod` sentinel when none exists (returned from `binder.go` at `:1657`, `:1676`, `:1689`, `:1699`, and `:1724`; the sentinel is owned by `pkg/gateway/podclaim`), which the gateway maps to `503 WARM_POOL_EXHAUSTED` with reason `no_idle_pods` (`pkg/gateway/sessionserver/start.go:166-167`). So placement also needs an echo pool. The §5.2 pool taxonomy defines a hot pool (`minWarm > 0`) that the WarmPoolController pre-warms so the first claim finds an idle pod after the initial-fill window (`spec/05_runtime-registry-and-pool-model.md:608`). During that initial fill the pool carries the `PoolWarmingUp` condition (set only when `minWarm > 0`; `spec/05_runtime-registry-and-pool-model.md:618-624`) and the session-start path returns `503 RUNTIME_UNAVAILABLE` (`spec/05_runtime-registry-and-pool-model.md:626-653`, `pkg/gateway/sessionserver/start.go:133,279`) until the first pod becomes idle, then succeeds.

### 1.5 The remaining work is packaging and wiring

The §4.7 embedded deployment model is specified (`spec/04_system-components.md:868`, trade-off table `871-881`); the echo image conforms to it. The remaining work threads the agent namespace through the embedded gateway and controller, creates the agent namespace in the embedded k3s, applies the echo Runtime CRD with `deploymentModel: embedded`, imports the echo-embedded image into the embedded containerd at `lenny up` through the existing import path (`pkg/embedded/localcli/image.go`), registers echo as the credential-free runtime with a single-pod warm pool, and re-points the tier-4 smoke (`tests/tier4_integration/embedded_mode_smoke_test.go`) at the runnable echo runtime.

## 2. Decisions

- **Reuse the existing echo-embedded runtime rather than inventing a new image.** `cmd/runtimes/echo-embedded` is a credential-free, single-container §4.7 embedded-model adapter serving the same §15.4.1 echocore loop as `cmd/runtimes/echo` (`cmd/runtimes/echo-embedded/main.go:3-25`), built from the repo-root Dockerfile with `BINARY=runtimes/echo-embedded` (`Makefile:47`), and already pod-deployed under a resolved (pullable) digest in the Kind e2e infra (`tests/testinfra/kind/install.sh:100`). This proposal wires that image into Embedded Mode; it adds no new runtime binary or image.
- **Deliver the echo image offline by reusing the existing `lenny image import` primitive.** `pkg/embedded/localcli/image.go` loads an image into the embedded k3s containerd store with no registry pull, via a docker-save tarball on the `--file` path (`image.go:102-125`), substrate-aware for the Linux host-`ctr` and the Docker-backed `docker exec k3s ctr` paths (`image.go:308-353`). `catalog.go:95-96` already names `lenny image import` as the operator escape hatch for placeholder-pinned runtimes. The bring-up import reuses this code.
- **Resolve the echo image digest at import time and inject it at bring-up rather than as a `catalog.go` constant.** The echo-embedded image is delivered as a host-built tarball (the bullet above), so its content digest is only knowable when it is imported, not when the `lenny` binary is built; `catalog.go:88-96` already records that a runtime's digest is not known at `lenny` build time. The bring-up resolves the imported image's digest and injects the `@sha256:<resolved-digest>` reference into both the gateway runtime registry record (the bootstrap seed) and the applied Runtime CRD, mirroring the Kind infra's install-time `resolve_digest` substitution (`tests/testinfra/kind/install.sh:271,721`). This keeps the seeded digest, the CRD digest, and the digest of the image present in the embedded containerd identical, which the digest-pinned `IfNotPresent` pull policy requires.
- **Confine the activation decision to the substrate-provisioning layer.** The decision of whether to set `AgentNamespace` lives in `pkg/embedded/stack`, the same layer where proposal 0013 confined its OS branch and where the stack already gates `GRPCAddr` and the production controllers on `k3sEnabled` (`pkg/embedded/stack/stack.go:262,283`). The gateway executor selection (`resolveExecutor` → `NewEchoExecutor`, vs the `--agent-namespace` block → `NewPodExecutor` at `cmd/lenny-gateway/main.go:2587`) is the identical config-driven dispatch production uses, preserving the §17.4 no-mode-dependent-business-logic-split invariant (`spec/17_deployment-topology.md:168`).
- **Gate activation on the existing `k3sEnabled` substrate gate alone.** The pre-built echo tarball ships with the `lenny` binary and is imported at every bring-up where the substrate is up, so the runnable echo image is always present after import. `AgentNamespace` is therefore set whenever `k3sEnabled` is true, with no separate runtime precondition. When the cluster or Docker substrate is genuinely unavailable, `k3sEnabled` is false and the gateway keeps the in-process echo executor, mirroring the existing degraded path the stack already gates on `k3sEnabled`.
- **Keep the §26 reference runtimes placeholder-pinned and out of scope.** The framework and general-purpose reference runtimes (chat, langgraph, mastra, openai-assistants, and crewai) and the coding agents (claude-code, gemini-cli, codex, and cursor-cli) stay placeholder-pinned (`catalog.go:142,197,211,218,229,236`) and require their published images plus LLM provider credentials. Re-pinning them to runnable digests is a separate §26 distribution concern.
- **Add echo to the Embedded Mode catalog as a credential-free entry consistent with §15.4.4.** §26 classifies echo as "a conformance exemplar embedded in the platform repo", distinct from the §26 reference runtimes (`spec/26_reference-runtime-catalog.md:10`), so seeding echo from the platform binary is consistent. echo-embedded is Basic-level (`cmd/runtimes/echo-embedded/main.go:3`, `pkg/runtimekit/echocore/echocore.go:3`), so its catalog entry declares `integrationLevel: basic`, unlike the Full reference runtimes.
- **Seed echo as a single-pod warm pool.** A `warmCount: 0` pool cannot place a session in Embedded Mode: the poolstore-to-CRD mapping sets `SandboxWarmPool.spec.MaxWarm = WarmCount` (`pkg/controller/poolscaling/poolstoresource.go:66,96-97`), so `warmCount: 0` yields `minWarm = 0, maxWarm = 0` (the §5.2 disallowed/fully-empty case rather than the cold pool, which needs `maxWarm > 0`); the WarmPoolController planner targets `warmTarget(minWarm, maxWarm)`, which returns `minWarm` and therefore creates zero pods for a `minWarm = 0` pool (`pkg/controller/warmpool/plan/plan.go:104-130,149-160`); the embedded controller is wired with no DemandSource and no `--demand`/metrics flag (`cmd/lenny-controller/main.go:587-591`, `pkg/embedded/stack/controller.go:109-124`), so the §5.2 on-demand cold-start scaling never runs; and the gateway binder never creates a Sandbox (it claims an existing idle pod and otherwise returns `ErrNoIdlePod`). The echo pool is therefore seeded with `warmCount: 1`, which is the §5.2 hot-pool taxonomy (`minWarm > 0`; `spec/05_runtime-registry-and-pool-model.md:608`) and matches the working Kind precedent `echo-pool-embedded` (`tests/testinfra/kind/install.sh:604-609`, `warmCount: 1`). The WarmPoolController pre-warms one echo pod at initial fill; the start path returns `503 RUNTIME_UNAVAILABLE` during the `PoolWarmingUp` window (`spec/05_runtime-registry-and-pool-model.md:618-624,626-653`), then the first `session new` claims the idle pod. echo is not a §26 reference runtime (`spec/26_reference-runtime-catalog.md:10`), so the §17.4:172 `warmCount: 0` override never applied to it, and giving it a positive warm floor neither contradicts §17.4:172 nor needs `warmCount`-override spec text.
- **Extend the §17.4 "Reference runtimes pre-installed" paragraph for the auto-seed, reconcile the "invoke any of them" and cold-start claims, and reconcile every §17.4/§26 example that presents a placeholder-pinned reference-runtime session as the working zero-config flow.** §17.4 already covers echo-as-pod-runtime in the §17.6 Helm seed example and the §17.4 custom-runtime walkthrough. Several claims need spec text. First, `lenny up` automatically seeds a credential-free echo pod runtime and a single-pod warm pool at bring-up, rather than the operator importing one by hand per the existing `spec/17_deployment-topology.md:282-320` walkthrough. Second, once placement is active the existing paragraph's "the developer can invoke any of them without further configuration" and "pulled lazily on first session start" sentences no longer hold for a placeholder-pinned §26 record: the gateway routes every session through the §4.7 pod path, so a session against such a record fails with `503 SESSION_CREATION_FAILED` (no runnable image, no applied Runtime CRD instance, and no warm pool; `pkg/gateway/sessionserver/start.go:546,580,179-185` via the bare `podsession.ErrNoMatchingPool` at `pkg/gateway/podsession/resolve.go:245`) until a runnable digest is registered on the record, a Runtime CRD instance is applied for the runtime, and a warm pool exists for it. The §26 records are seeded only through `POST /v1/admin/bootstrap` (`pkg/embedded/stack/runtimes.go:48-52`), which creates a gateway registry record and no Runtime CRD instance; the Sandbox controller resolves the runtime from a Runtime CRD by name and fails with `get runtime <name>: ... not found` when none exists (`pkg/controller/sandbox/controller.go:378-379`), and the RuntimeReconciler mirrors Runtime CRDs into the registry rather than the reverse (`pkg/controller/runtime/controller.go:3-8`). Re-pinning the registry record or importing a local image with `lenny image import` supplies a pullable image but applies no CRD and creates no pool (`pkg/embedded/localcli/image.go:102-125`; the runtime's `defaultPoolConfig` is advisory pool-resolver metadata at `pkg/controller/runtime/controller.go:300-304`, not a pool factory), so none alone makes a §26 session start; the `lenny up` placeholder-pin warning already records the image half (`pkg/embedded/stack/runtimes.go:84-88`). Third, the existing `warmCount: 0` "(cold-start on first use)" sentence is inaccurate under active placement: the §26 records have no warm pool and the embedded controller wires no `DemandSource` (`cmd/lenny-controller/main.go:587-591`, `pkg/embedded/stack/controller.go:109-124`), so the §5.2 on-demand cold-start path never runs and a §26 session does not cold-start on first use. C1 removes or rewords the "(cold-start on first use)" parenthetical. Fourth, the same active-placement reconciliation must reach the §26 catalog sites that present a placeholder-pinned reference-runtime session as the working out-of-the-box flow, because under C1's own thesis every §26 record (including `chat` at `pkg/embedded/stack/catalog.go:197`) is placeholder-pinned and seeds no warm pool, so each presents an invocation that now returns `503 SESSION_CREATION_FAILED` rather than a session: (a) the §17.4 Embedded Mode quickstart code block, which runs `lenny session new --runtime=chat --attach "hello"  # Ready to use in < 60s` (`spec/17_deployment-topology.md:150`); (b) the §17.4 custom-runtime walkthrough step 4, which states "the pool warms a pod on next session start" with no Runtime-CRD-apply step and no pool-creation step in steps 1-5 (`spec/17_deployment-topology.md:308-318`); (c) the §26.7 `chat` use-case sentence, which presents `lenny session new --runtime=chat --attach "hello"` as "what `lenny up` uses as the zero-config default when no workspace is attached" (`spec/26_reference-runtime-catalog.md:360`); (d) the §26.1 day-one-utility purpose, which states for the whole §26 set that "an operator running `lenny up` has functioning agents to work with, not just `echo`" (`spec/26_reference-runtime-catalog.md:5`) and that "Each entry is a complete, working runtime that a deployer can install and use for real workloads without additional coding" (`spec/26_reference-runtime-catalog.md:3`); and (e) the §26.1 "Tenant access" paragraph, which states for `local` profile installations that "`lenny up` auto-grants access to the `default` tenant for every reference runtime it installs so the developer can invoke them without additional setup" (`spec/26_reference-runtime-catalog.md:30`, a separate paragraph from the lines-3/5 day-one-utility purpose). C1 points the quickstart block at the auto-seeded runnable echo runtime, adds a Runtime-CRD-apply step and a warm-pool-creation step to the walkthrough so its step-5 curl succeeds, narrows the §26.7 sentence so it states that `chat` is the user-facing default only once a runnable digest is registered, a Runtime CRD instance is applied, and a warm pool exists, narrows the §26.1 day-one-utility sentence so it scopes the functioning-§26-agents claim to a published or production install that carries real digests while echo is the credential-free runtime `lenny up` runs out of the box, and narrows the §26.1 "Tenant access" clause so the auto-grant supplies tenant access while a session against a placeholder-pinned §26 record still requires a runnable digest, an applied Runtime CRD instance, and a warm pool before it starts; each names echo as the auto-seeded credential-free runtime that runs out of the box. These reconciliations land in §17.4, §26.7, and §26.1; no new Embedded-Mode subsection and no line-264 reconciliation is needed. The user-facing question of whether to flip the surfaced default from `chat` to `echo` stays deferred to §8; C1 only stops the spec from presenting a `chat` session as a flow that starts in Embedded Mode when it does not.

## 3. Proposed changes

### C1. Spec change: `spec/17_deployment-topology.md` §17.4 bootstrap-seed clarification and `spec/26_reference-runtime-catalog.md` §26.1/§26.7 zero-config-default reconciliation

The primary edit anchors on the "Reference runtimes pre-installed" paragraph in §17.4, currently at line 172. C1 also reconciles the further sites that present a placeholder-pinned reference-runtime session as the working out-of-the-box flow (the §17.4 quickstart block, the §17.4 custom-runtime walkthrough step 4, the §26.7 use-case sentence, the §26.1 day-one-utility purpose, and the §26.1 "Tenant access" paragraph), detailed after the appended passage below. The current "Reference runtimes pre-installed" text reads:

```
**Reference runtimes pre-installed.** `lenny up` installs all reference runtimes from [Section 26](26_reference-runtime-catalog.md) as platform-global records and auto-grants access to the `default` tenant so the developer can invoke any of them without further configuration. Container images are pulled lazily on first session start for each runtime; subsequent sessions reuse the cached image. The warm pool defaults are overridden to `warmCount: 0` (cold-start on first use) to keep resource usage low on laptops.
```

Append a short passage to this paragraph stating the genuinely new bootstrap behavior and reconciling the existing "invoke any of them" sentence with pod placement. Once placement is active in Embedded Mode, the gateway routes every `lenny session new` through the §4.7 pod path, so a placeholder-pinned §26 runtime no longer starts a session: it has no runnable image, no applied Runtime CRD instance, and no warm pool, so `lenny session new` against it returns `503 SESSION_CREATION_FAILED` (the gateway resolves the pool by name from the agent namespace, finds none, and returns `podsession.ErrNoMatchingPool` mapped to the §7.1 fallback at `pkg/gateway/sessionserver/start.go:546,580,179-185`). Three things are missing for a §26 record at `lenny up`: a runnable image digest, a Runtime CRD instance, and a warm pool. Re-pinning the registry record to a runnable digest, or importing a local image with `lenny image import`, supplies a pullable image but applies no CRD and creates no pool; `lenny image import` loads an image into the embedded containerd and neither re-pins the registry record nor applies a CRD nor creates a pool (`pkg/embedded/localcli/image.go:102-125`), and the runtime's `defaultPoolConfig` is advisory metadata the pool resolver consults rather than a pool factory (`pkg/controller/runtime/controller.go:300-304`). The §26 records are seeded only through `POST /v1/admin/bootstrap` (`pkg/embedded/stack/runtimes.go:48-52`), which writes a gateway registry record and creates no Runtime CRD instance; the Sandbox controller resolves the runtime from a Runtime CRD by name and fails with `get runtime <name>: ... not found` when none exists (`pkg/controller/sandbox/controller.go:378-379`), and the RuntimeReconciler mirrors Runtime CRDs into the registry rather than projecting the registry back into CRDs (`pkg/controller/runtime/controller.go:3-8`), so even a runnable digest and a warm pool leave the warm pod creation failing until a Runtime CRD instance is applied. So a session against a placeholder-pinned §26 record starts only once a runnable digest is registered on the record, a Runtime CRD instance is applied for the runtime (carrying the deployment model the embedded substrate runs), and an explicit warm pool exists for the runtime. The seeded echo runtime is the credential-free runtime that arrives at `lenny up` with a runnable digest, an applied Runtime CRD, and a pool, so it runs end to end on a pod. The current paragraph's "the developer can invoke any of them without further configuration" and "pulled lazily on first session start" sentences are accurate for a registry that holds runnable digests with applied Runtime CRDs and warm pools; they must be reconciled to state that the placeholder-pinned §26 records register but do not start a session until a runnable digest, a Runtime CRD instance, and a warm pool exist for them. Appended passage:

```
The Section 26 records register through the gateway registry so the developer sees the catalog, but they ship with a placeholder image digest, apply no Runtime CRD instance, and seed no warm pool, so a session against one returns a session-creation failure rather than starting: the gateway routes every session through the pod path, finds no warm pool for the runtime, and fails the create. Starting a session against a Section 26 record requires three artifacts. First, register a runnable image digest on the record (re-register it with the published digest, or import a local image with `lenny image import` and re-register the record under that image). Second, apply a Runtime CRD instance for the runtime carrying the deployment model the embedded substrate runs, because the Sandbox controller resolves the runtime from a Runtime CRD by name and the bootstrap registry-only seed creates no such instance. Third, create a warm pool for the runtime. Importing an image alone supplies a pullable image but applies no CRD and creates no pool, and re-pinning the registry digest and creating a pool without applying a Runtime CRD leave the warm pod creation failing because the Sandbox controller cannot resolve a Runtime CRD that the registry-only seed never creates. In addition to those records, `lenny up` seeds the built-in echo runtime (the [Section 15.4.4](15_external-api-surface.md#1544-sample-echo-runtime) conformance exemplar, Basic-level) with a runnable image digest, an applied Runtime CRD carrying `deploymentModel: embedded`, and a single-pod warm pool, so a credential-free session runs on an in-cluster pod over the [Section 4.7](04_system-components.md#47-runtime-adapter) boundary; when the embedded cluster or Docker substrate is unavailable the gateway degrades to the in-process echo executor.
```

Reconcile the existing paragraph sentence "auto-grants access to the `default` tenant so the developer can invoke any of them without further configuration. Container images are pulled lazily on first session start for each runtime" so it no longer claims a placeholder-pinned record starts a session unattended; the applied edit makes the registration-versus-session-start distinction explicit.

Reconcile the existing `warmCount: 0` sentence rather than retaining it unchanged. The current sentence reads "The warm pool defaults are overridden to `warmCount: 0` (cold-start on first use) to keep resource usage low on laptops." Under active placement the §26 records have no warm pool at all, and the embedded controller wires no `DemandSource` (`cmd/lenny-controller/main.go:587-591`, `pkg/embedded/stack/controller.go:109-124`), so the §5.2 on-demand cold-start path never runs for them: a session against a §26 record fails to start until a warm pool exists, rather than cold-starting a pod on first use. The "(cold-start on first use)" parenthetical asserts a behavior the embedded stack does not provide and contradicts the appended passage, so it must be removed or reworded in the same edit. State that the §26 records are seeded with no warm pool to keep laptop resource usage low, and that a session against one does not start until a runnable digest, an applied Runtime CRD instance, and a warm pool exist. Do not leave the "(cold-start on first use)" clause intact.

In addition to the "Reference runtimes pre-installed" paragraph, reconcile the remaining sites that present a placeholder-pinned reference-runtime session as the working out-of-the-box flow, since under active placement each presents an invocation that now returns `503 SESSION_CREATION_FAILED`:

- **§17.4 Embedded Mode quickstart code block (`spec/17_deployment-topology.md:148-152`).** The block runs `lenny session new --runtime=chat --attach "hello"    # Ready to use in < 60s`. Repoint the `< 60s` example at the auto-seeded runnable runtime: replace `--runtime=chat` with `--runtime=echo`, so the example invokes the runtime that arrives at `lenny up` with a runnable digest, an applied Runtime CRD, and a warm pool. Keep the surrounding `lenny up` / `lenny down` lines unchanged.
- **§17.4 custom-runtime walkthrough step 4 (`spec/17_deployment-topology.md:308-318`).** Step 4 currently reads "The embedded gateway's CRD controller picks up the runtime automatically; the pool warms a pod on next session start," and steps 1-5 register the runtime through `lenny-ctl runtime register` but apply no Runtime CRD and create no warm pool. The `lenny-ctl runtime register --file runtime.yaml` of step 3 posts the definition to the gateway registry admin API (`POST /v1/admin/runtimes`; `pkg/ctlcli/runtime.go:315-317`, dispatched from `pkg/ctlcli/main.go:1067-1071`), so it creates a registry record and never applies a Runtime CRD instance.
