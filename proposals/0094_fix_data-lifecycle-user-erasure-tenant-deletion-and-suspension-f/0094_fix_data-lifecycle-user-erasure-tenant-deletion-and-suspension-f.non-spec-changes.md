Column rules:

- **Delegated child** is `Session.DelegationDepth > 0`. Only `delegation.Service.buildChildSession` writes a non-zero depth (the parent's depth plus one). `ParentSessionID` does not classify a row, because `handleDerive`, `persistDeriveFailure`, and `handleReplay` set it to the source session.
- **Gates.** `requireActiveUser` is the caller check and `requireSourceOwnerNotRestricted` is the source-owner check of the **Article 18 refusal table**, which states what each reads, refuses, and admits, and the order in which each meets the fence. Neither is a fence gate. Every other gate evaluates `CreationMarkers.Refusal` itself, over the tenant row and the owner's user row, so it answers the fence's code, in CODE-1 item 2's order, for the same marker state. A read error in a gate answers `500 INTERNAL_ERROR`, or the `INTERNAL_ERROR` tool error, and writes nothing.
- **Reservation.** `store.Reserve` runs the fence in its own transaction and records the session ID for its owner, and records nothing for an empty owner. A path takes one when it writes data keyed to the new session ID before the insert (C8, and C11 with `fileExport`). A path that reserved inserts through `store.CreateReserved`, which, for a row with an owner, deletes its reservation in the insert transaction and refuses when that reservation no longer exists; a row with no owner inserts as `Create` does. Only the erasure (`DeleteByUser`) of the owner, or the tenant's deletion (`DeleteByTenant`), removes another writer's reservation, so a write that outlives a completed erasure is refused and undone rather than inserted. `store.Create` also deletes a reservation whose ID and owner match the row. The erasure's session lister returns, with the user's session IDs, the IDs reserved for the user (CODE-7 item 8). A reservation is released only after the undo deleted what was written, and a non-refusal `Create` error deletes nothing and keeps the reservation, because such an error can follow a committed insert.
- **Undo** runs only on `errors.As(err, &ref)` for `*sessionstore.CreationRefusal`, after the branch's existing rollback and before the refusal is written.
- **Marker rows read in the commit transaction.** `FOR SHARE` conflicts with `FOR UPDATE`, which `tenantstore` and `userstore` `Update`, `SetErasureRestrictionTx`, and `ClearProcessingRestrictionTx` take, and with `FOR NO KEY UPDATE`, which any plain `UPDATE` takes, such as `userstore` and `tenantstore` `SoftDelete`. Summary D1 records why no weaker mode works. Every marker writer locks exactly one of the two rows, so the tenant-then-user order admits no lock cycle. The reservation's `DELETE` in `CreateReserved` conflicts with the `DELETE` of the same row by `DeleteByUser` or `DeleteByTenant`, so `CreateReserved` of a row with an owner either removes the reservation and commits the session row, or finds it gone and refuses. Each gate in the **Gates** column is an early-out of these reads.

Column rules:

- **Caller check** is `requireActiveUserForAction`, which `requireActiveUser` wraps for the create paths. It implements §11.4 for the requesting user and the caller refusal of §12.8 Article 18 item (3), and its doc comment cites both sections. It reads the user row through `userstore.Store.Get`, which reads the primary, and checks `IsActive` before `ProcessingRestricted`. It admits a request with no principal, an empty subject, or no registry row, and a read error answers `500 INTERNAL_ERROR`, or the `INTERNAL_ERROR` tool error on A8. On A8 it reads the principal from `authmw.FromContext`, as A7 does. The MCP tools record the resolution under the session's `row.UserID` and do not compare it with the principal, so a check on `row.UserID` would admit a restricted principal resolving another user's elicitation and refuse an active principal resolving a restricted user's.
- **Fence** is `CreationMarkers.Refusal`, whose code order is CODE-1 item 2's and Edit 1a's. Its gates and its commit transaction are the **Gates** and **Marker rows read in the commit transaction** cells of the **Creation-path table**.
- **Source-owner check** is `requireSourceOwnerNotRestricted` (CODE-2 item 9). It reads the source session owner's user row, refuses with `ERASURE_IN_PROGRESS` and details `userId` (the source owner) and `jobId` when `processing_restricted` is set, and admits an empty source owner and a missing row. It reads no other marker and is not the fence predicate (summary D3).
- **Serialization point.** A refusal derived from a lifecycle marker that guards residue, meaning data the marker's operation must drain, reach, or delete, is evaluated under a lock that conflicts with the marker writer, inside the transaction that commits the guarded effect. A handler pre-check is only an early-out. The refusals that guard residue are evaluated in the transactions the **Creation-path table** names. They are the fence, which keeps a session the drain has not listed out of the fenced scope, and the reservation-ended refusal, which keeps data written under a reserved ID from outliving the owner's erasure. The caller check and the source-owner check guard no residue, so each runs once, when the request is admitted. A session that a restricted caller creates belongs to the owner the fence reads, or to no user. A derive's copy is reserved for and inserted under its new owner, whose erasure and the tenant's deletion reach it, so a derive admitted before its source owner's flag commits leaves the outcome of a derive that completed before the erasure started (summary D32). An interaction resolution writes only rows of the user's session, which the drain and the user's erasers reach.
- **Scope of the caller refusal.** §12.8 Article 18 item (3) holds on every request path that `cmd/lenny-gateway` mounts. Rows A2 and A6 run no caller check. C6 and C7 run only when no single-shot binder or `SessionCreator` is injected. `cmd/lenny-gateway` injects both, so only in-process tests and harnesses reach C6 and C7, and they gain no gate (summary D3). On A6 the caller is a runtime rather than a user.

## Edge cases and accepted failure modes

1. **A long Phase 2 drain delays the tenant-deletion tick.** The tick budget bounds each drain (CODE-5 item 1), so a long drain delays other tenants' deletion by at most one budget per drain. The tier-4 and tier-8 runs log the drain time.
2. **Drained sessions are recorded as runtime failures.** The §24.11 transition writes `failed` with `FailureClassRuntime` and `FORCE_TERMINATED`, so failure metrics count lifecycle drains.
3. **The tenant-deletion job store stays in memory.** It is rebuilt from `TenantState` on restart, and a Phase 2 that had not completed resumes there.
4. **A reserved ID's data written after the erasers ran.** A derive copy or a delegated child's export that is still writing when the erasure of its owner runs its session-scoped erasers is refused at its insert, whether the erasure is still in progress (the fence) or has completed (`CreateReserved` finds no reservation), and deletes what it wrote. Only a gateway crash between the end of the erasers and the undo leaves data no eraser reaches, because the erasure already deleted the reservation. REC-1 item 11 files this residual.
5. **Reservations of creates that end without a row or an undo.** A copy failure (C9) or a crash keeps its reservation. The row is a few bytes, the owner's erasure or the tenant's deletion removes it, and no sweep is added.
