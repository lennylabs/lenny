# Proposal: Complete the §12.4 canonical Redis key-prefix table with the omitted tenant-embedded and platform-scoped prefix families (`rl:`, `sq:`, the tenant-leading `pg:*` playground family, and the platform-scoped `pg:sess-tenant` fan-in index), give the two spec-orphaned keys (`pg:user`, `pg:sess-tenant`) a documented home in §27, and reconcile the circuit-breaker pub/sub channel name divergence (`cb:events` vs `circuit_breaker_events`)

- **Status:** Verified (2026-07-02). Converged after 6 adversarial review rounds (9 findings fixed); awaiting sign-off.
- **Date:** 2026-07-02.
- **Scope:** A spec-documentation change with no behavioral code change. The §12.4 canonical key-prefix table (`spec/12_storage-architecture.md:177`) asserts it "lists all canonical key prefix patterns in use," but its rows omit several prefix families the gateway actively writes, and its exception-class summary names an explicit count of three exception classes that is now stale. This proposal adds the omitted gateway-datastore rows and scopes the table's intro claim to the tenant-isolation domain the table registers, so the claim no longer overreaches to component-owned Redis keys documented in their own sections (**S1**), rewrites the exception-class summary into two categories and corrects its enforcement clause to describe the mechanism the Redis Guard implements (**S2**), gives the two entirely spec-orphaned keys (`pg:user`, `pg:sess-tenant`) an owning-section home in §27 (**S3**), and reconciles the circuit-breaker change-propagation channel name so the spec and the code agree on a single literal value (**S4**). It touches `spec/12_storage-architecture.md`, `spec/27_web-playground.md`, and `spec/11_policy-and-controls.md`, plus lockstep doc-comment updates in `pkg/gateway/storage/rediskeys` (and its test) and `pkg/gateway/storage/slotcounter` that quote or count the §12.4 exception classes S2 rewrites, and in `pkg/gateway/session/sessionevents` (`redisrelay.go`, `events.go`, and `redisrelay_test.go`) plus the gateway wiring in `cmd/lenny-gateway/stores.go` that cite a non-existent §12.3.7 for the `lenny:events:` relay key S1 gives a §12.4 home. No store, proto, or wrapper behavior changes; the keys the gateway writes are correct and their tenant isolation holds, and the doc-comment edits are comment-accuracy changes that alter no code path. Two candidate changes are recorded in Non-goals: migrating `rl:`/`sq:` to a tenant-leading form (no isolation gain), and extending the `PlatformRedis` interface doc comment (a false-ownership edit that would diverge the spec copy from its Go source).

This document stages the proposed spec changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

The §12.4 canonical key-prefix table opens with the claim that it "lists all canonical key prefix patterns in use" (`spec/12_storage-architecture.md:177`), and its exception-class summary states there are exactly "three exception classes to the tenant-prefix rule" (`spec/12_storage-architecture.md:194`). Both statements are false against the code. A grep of §12.4 returns zero occurrences of `rl:`, `sq:`, or any `pg:*` family, and the summary's enumeration omits every key the gateway writes outside the listed patterns. Each omission is verified in code.

The "lists all ... in use" claim also reaches beyond the tenant-isolation datastore domain the table registers. Additional non-tenant-prefixed Redis keys exist across the platform: the gateway-emitted connector-OAuth state store `conn:oauth:state:{state}` (enumerated below and added as a §12.4 row), and component-owned keys documented in their own sections rather than in the gateway datastore registry. The Token Service token cache writes `lenny:token:{jti}` (`pkg/tokenservice/cache/cache.go:42`, wired in `cmd/lenny-token-service`), and the `lenny-ops` service writes `ops:lock:{scope}`, `ops:lockidx:`, `ops:lock-epoch:current`, and `ops:escalations:{id}` (`pkg/ops/coordination/redisstore/redisstore.go:38-40`, `pkg/ops/escalation/redisstore/redisstore.go:30`), all documented under §25.4 (`spec/25_agent-operability.md:1499-1500,:2189,:2375`). The routing cache prefix `lenny:route:` (`pkg/gateway/session/routingcache/routingcache.go:47`) is not wired into any binary (the package has no callers under `cmd/` or `pkg/`), so it emits no live keys. The gateway also emits further non-tenant-leading Redis prefixes, each accounted for below. The cross-replica session-event relay writes the Redis Streams key `lenny:events:{session_id}` (`pkg/gateway/session/sessionevents/redisrelay.go:29`, wired at `cmd/lenny-gateway/stores.go:1758-1759` on the CachePubSub concern); it is a canonical gateway datastore key and gains a §12.4 row (item 7 below). The `ops:events:stream` operability event stream is XADDed by the gateway (`pkg/gateway/eventbuffer/streamemitter.go:20`, wired at `cmd/lenny-gateway/auxstores.go:161-172`) but is platform-scoped and already owned by §25.5 (`spec/25_agent-operability.md:2586`), so it is dispositioned against its owning section rather than added as a §12.4 row. The pod-termination fan-out publishes on the pub/sub channel `lenny:session:terminate` (`pkg/gateway/podlifecycle/podterminate/propagator/propagator.go:46`, published at `cmd/lenny-gateway/user_revocation.go:92`), a gateway-internal replica-synchronization pathway whose mechanism §11.4 already documents (the full-revoke propagation note states the gateway "publishes the step-2 `Terminate` request ... on Redis pub/sub channels" so peer replicas apply it, `spec/11_policy-and-controls.md:263`); the literal channel name is not spelled in the spec, so it is dispositioned against its owning §11.4 section rather than added as a §12.4 row. Because a full platform-wide Redis-key audit spanning the Token Service and `lenny-ops` is outside this proposal's scope, S1 both adds the omitted gateway-datastore rows and scopes the line-177 intro claim to the domain the table registers rather than asserting exhaustive coverage of every Redis key in the system.

1. **`rl:{key}:{minute_epoch}`, the rate-limit window counter.** `pkg/gateway/policy/ratelimit/redisstore/redisstore.go:48` builds `windowKey := fmt.Sprintf("rl:%s:%d", key, now.Unix()/60)` and runs a single-key `INCR` Lua script on it (`:49`). `{key}` is caller-supplied and embeds the tenant for per-tenant limiters (`rt:{tenant}:{runtime}` at `pkg/gateway/sessionserver/admission_ratelimit.go:48`; `po:{tenant}:{pool}` at `:54`; `eval:s:{tenant}:{sid}` / `eval:t:{tenant}` at `pkg/gateway/sessionserver/eval.go:91,:96`; `msg:out:{tenant}:{sender}` / `msg:in:{tenant}:{target}` at `pkg/gateway/mcpfabric/mcptools/messaging.go:97,:105`; `connector-refresh:{tenant}:{id}` at `pkg/gateway/externalapi/admin/connector_refresh.go:88`). A deliberately platform-wide "global" limiter carries no tenant (`pkg/gateway/middleware/ratelimit/ratelimit.go:238`). The key is tenant-embedded but not tenant-leading, and the store issues single-key operations only, with no `SCAN`.

2. **`sq:{tenant_id}`, the storage-quota byte counter.** `pkg/gateway/quota/storagequota/redisstore/redisstore.go:22-24` defines `const keyPrefix = "sq:"` and `key(tenantID) = keyPrefix + tenantID`. The tenant id is the suffix. The store issues single-key `GET`/`INCRBY`/`SET`/`EVAL` for the §11.2 read-check-reserve only, with no `SCAN`.

3. **The tenant-leading playground `pg:*` family.** `pkg/gateway/mcpfabric/playground/sessionrecord.go` writes `t:{tenant_id}:pg:sess:{session_id}` (`:186`), `t:{tenant_id}:pg:revoked:{jti}` (`:192`), `t:{tenant_id}:pg:revocations` (`:222`), and `t:{tenant_id}:pg:user:{user_id}` (`:214`). The first three are documented in §27 (`spec/27_web-playground.md:88-89,:96`) but appear nowhere in the §12.4 table. `pg:user` is documented nowhere in the spec (a grep of `spec/` and `docs/` for `pg:user` returns zero matches), despite its code comment citing §11.4/§27.3.1/§27.6, which describe user invalidation without naming the key.

4. **`pg:sess-tenant:{session_id}`, the platform-scoped session-to-tenant fan-in index.** `pkg/gateway/mcpfabric/playground/sessionrecord.go:205` returns `"pg:sess-tenant:" + id` with no tenant prefix. It is documented nowhere in the spec (a grep for `sess-tenant` returns zero matches) and is the sole un-prefixed key in that file. The §27.3.1 line-81 citation in the surrounding code refers to the opaque cookie, not to this index.

5. **`derive_lock:{source_session_id}`, the derive concurrent-serialization lock.** `pkg/gateway/storage/derivelock/derivelock.go:257` sets `keyPrefix: "derive_lock:"` and `:280` builds `key := r.keyPrefix + sourceSessionID`, a single-key `SETNX` with a 30s TTL and an ownership-token-checked `DEL` release (`:287`, and the release Lua script). The key is session-scoped and carries no tenant component. It is documented in §7.1 (`spec/07_session-lifecycle.md:92`) and §18 (`spec/18_build-sequence.md:228`) but appears nowhere in the §12.4 table. The gateway resolves the source session under the calling tenant's scope before acquiring the lock, so a cross-tenant acquire is not reachable.

6. **`conn:oauth:state:{state}`, the connector-OAuth authorization-request state.** `pkg/connectoroauth/redis_state_store.go:50` defines `const redisStateKeyPrefix = "conn:oauth:state:"` and `:57` builds the key from the `state` string alone. It holds the §9.3 PKCE/anti-CSRF `state` context (Redis, 10-minute TTL) across gateway replicas and is consumed atomically by a single-key Lua swap-to-tombstone (`consumeStateScript`), so a replayed `state` returns `ErrStateConsumed`. The `state` value is a cryptographically unique HMAC nonce (`StateSigner.Mint`), so the key carries no tenant component by design; `Consume` receives only the `state` string. The store is gateway-emitted and wired at `cmd/lenny-gateway/credentialsurface.go:169` on the CachePubSub concern. It issues single-key operations with no `SCAN`, and it is documented nowhere in the §12.4 table today.

7. **`lenny:events:{session_id}`, the cross-replica session-event relay stream.** `pkg/gateway/session/sessionevents/redisrelay.go:29` returns `"lenny:events:" + sessionID`, the Redis Streams key the gateway's in-memory session-event Bus fans out to via `XADD` so a client reconnecting with `Last-Event-ID` to a different replica can replay the stream (`XRANGE` for history, `XREAD BLOCK` for live), satisfying the §15.2 event-stream resume contract. It is wired only when Redis is present (`cmd/lenny-gateway/stores.go:1758-1759`, CachePubSub concern); single-replica dev mode leaves the relay nil and keeps the Bus in-memory. The prefix scopes the stream to the gateway namespace, so the key is session-scoped and carries no tenant component. It is documented nowhere in the spec, and its code doc comments cite a non-existent §12.3.7 (`redisrelay.go:16,:25,:32,:43`, `events.go:13,:75,:170,:383`, `redisrelay_test.go:17`, and the gateway wiring that constructs and attaches the relay at `cmd/lenny-gateway/stores.go:1720,:1752`); §12.3 is "Postgres HA Requirements" and has no subsection 7. S1 adds a §12.4 row for it and retargets the dangling §12.3.7 code citations to §12.4 in lockstep.

8. **The circuit-breaker change-propagation channel name divergence.** `pkg/gateway/middleware/circuitbreaker/breakerstore/cachingstore/cachingstore.go:31` publishes on `const channel = "cb:events"`. The spec already documents this channel, twice, under a different literal name: `circuit_breaker_events` at `spec/11_policy-and-controls.md:301` and at `spec/12_storage-architecture.md:714`. The line-714 reference sits in the §12.6 "Interface Design" section, in the "Infrastructure pub/sub exclusion" paragraph, which documents circuit-breaker state propagation as a gateway-internal replica-synchronization pathway that bypasses EventBus. This is a spec/code name divergence for one channel rather than an undocumented key. Because that §12.6 paragraph records the channel as a platform-wide replica-sync pathway rather than a tenant-scoped datastore key, it needs no §12.4 key-prefix row; it needs a single agreed name.

The gap is documentation-only. Neither non-tenant-leading store (`rl:`, `sq:`) permits cross-tenant read or mutation: both issue single-key operations with no `SCAN` or wildcard (`pkg/gateway/quota/storagequota/redisstore/redisstore.go:63,:79,:87,:107`; `pkg/gateway/policy/ratelimit/redisstore/redisstore.go:49`), so tenant isolation holds and no code fix is warranted. §12.4 already establishes a documented-exception mechanism for non-tenant-leading keys (`spec/12_storage-architecture.md:189-195`), so the fix documents the families rather than migrating any key. Two families (`pg:user`, `pg:sess-tenant`) are orphaned from the spec entirely, so repairing the §12.4 table alone would leave them with no owning section that defines their semantics.

## 2. Decisions

- **The fix direction changes no store or wrapper behavior.** Both non-tenant-leading stores issue single-key operations with no `SCAN` or wildcard, so neither can read or mutate another tenant's counter. Tenant scoping is preserved: the tenant is embedded in `{key}` for `rl:` and is the suffix for `sq:`. The deviation from the literal tenant-leading rule is a naming choice rather than an isolation breach, so no code migration is warranted. The only code edit is a lockstep doc-comment update in `pkg/gateway/storage/rediskeys` that requotes the §12.4 sentence S2 rewrites (see S2); it changes no code path.
- **Document `rl:` and `sq:` as exceptions rather than migrating them to a tenant-leading form.** §12.4 already establishes an exception-class mechanism for non-tenant-leading keys (`spec/12_storage-architecture.md:189-195` names `lenny:pod:*`, `cb:{name}`, and `{root_session_id}:dlg:*`). `rl:`/`sq:` differ in kind from those three: the existing exceptions carry no tenant component at all (pod-, platform-, or tree-scoped), whereas `rl:`/`sq:` embed the tenant id but not as a leading segment. The summary is split into two categories to reflect this: genuinely non-tenant-scoped keys, and tenant-scoped-but-not-leading keys.
- **The §12.4 table is the canonical prefix registry; the owning section holds the semantics.** Per the documentation-content rule (introduce each concept once, in the page that owns it, and link elsewhere), the §12.4 rows for the `pg:*` families name the prefix, its scope class, and a terse role, then link to §27 and §11.4/§27.6 for full semantics. This matches the established table style, where the `evt:` row links to §12.6 and the `dlg:*` row links to §8.3 rather than restating their semantics inline.
- **`pg:user` and `pg:sess-tenant` get an owning-section home in §27 rather than a §12.4 registry row alone.** Both are documented nowhere in the spec today. A §12.4 row alone would leave their semantics undefined. Their semantics belong to §27: `pg:sess-tenant` is the §27.3.1 cookie-to-tenant fan-in index, and `pg:user` is the per-user playground session index the §11.4/§27.6 user-invalidation fan-out reads. Their descriptive rows are added to the §27 "Session record backing store" table alongside the sibling `pg:sess` and `pg:revoked` rows, and §12.4 links to them.
- **Combine the tenant-leading `pg:*` keys into one §12.4 registry row and keep `pg:sess-tenant` a separate row**, mirroring the existing combined `dlg:*` family row (`spec/12_storage-architecture.md:193`). The tenant-leading `pg:sess`/`pg:revoked`/`pg:revocations`/`pg:user` share the `t:{tenant_id}:` convention and one owning section; `pg:sess-tenant` is a distinct platform-scoped exception and reads clearer as its own row.
- **The circuit-breaker channel is already documented; the only defect is a name divergence, reconciled in the documentation-only direction.** The channel exists in the spec as `circuit_breaker_events` (`spec/11_policy-and-controls.md:301`, `spec/12_storage-architecture.md:714`) and in the code as `cb:events` (`cachingstore.go:31`). §12.4 registers literal wire values (the sibling `cb:{name}` row already uses the literal `cb:` form), so this proposal reconciles the two spec occurrences to the literal `cb:events` that the code publishes, giving §11.6, §12, and the code a single name. Because the §12.6 "Infrastructure pub/sub exclusion" paragraph already records this pub/sub channel as a gateway-internal replica-sync pathway rather than a §12.4 datastore key, no standalone §12.4 row is added for it; the reconciliation edits the two prose references and the S2 exception-class summary refers to `cb:events` under the shared `cb:` prefix already recognized by the Guard. The alternative reconciliation (rename the code constant to `circuit_breaker_events`) is a code change recorded as an open question.
- **The exception-class summary describes the passthrough mechanism the Redis Guard implements rather than a recognition it does not perform.** `rediskeys.ValidateKey` recognizes only `cb:`, `lenny:pod:`, `t:`, and `{root}:dlg:` (`pkg/gateway/storage/rediskeys/rediskeys.go:114-134`); `rl:`, `sq:`, and `pg:sess-tenant` fall through to `ErrNoPrefix`. They are not "recognized" by the wrapper. They are issued on unscoped or platform-scoped paths the Guard passes through unvalidated (`rediskeys.go:24-28`, "A command issued without a Scope is passed through unvalidated"). The summary states this accurately rather than asserting an enforcement the code does not perform. `cb:events` needs no addition to the enforcement clause: `ValidateKey` already admits it via `strings.HasPrefix(key, "cb:")` (`rediskeys.go:114`) and the existing clause already names the `cb:` prefix.
- **The change reaches tier 11 only (documentation and spec consistency).** No behavioral spec section changes and no code path changes, so no unit, component, or integration test is added. The existing `TestRedisTenantKeyIsolation` coverage (`spec/12_storage-architecture.md:195`) is not extended for `rl:`/`sq:`/`pg:sess-tenant`, because their isolation is structural (single-key operations with the tenant embedded in the key, or an opaque-id credential requirement) rather than enforced by a leading-prefix check; extending the prefix-isolation test model to them is recorded as a non-goal.

## 3. Two exception categories and the channel-name reconciliation

The §12.4 exception summary today groups its three exceptions under one heading: keys with no tenant component. The omitted families split that heading into two categories.

**Category A, non-tenant-scoped keys.** `lenny:pod:*` (pod-scoped), `cb:{name}` (platform-scoped), `pg:sess-tenant:{session_id}` (platform-scoped), `conn:oauth:state:{state}` (platform-scoped), `derive_lock:{source_session_id}` (session-scoped), `lenny:events:{session_id}` (session-scoped), and `{root_session_id}:dlg:*` (tree-scoped) carry no tenant component by design. Their isolation is established by the scope they use rather than by a tenant prefix: pod ids are cluster-globally unique, circuit breakers are platform-wide operational controls, the delegation-budget keys use an application-layer ownership check, the playground fan-in index resolves only for a caller already holding the opaque cookie credential, the connector-OAuth `state` key is a cryptographically unique HMAC nonce whose knowledge is itself the credential, the derive lock is acquired only after the gateway resolves the source session under the calling tenant's scope, and the `lenny:events:` relay stream names a single session's stream under a gateway-namespace prefix.

**Category B, tenant-scoped-but-not-leading keys.** `rl:{key}:{minute_epoch}` and `sq:{tenant_id}` embed the tenant id inside `{key}` (rate limit) or as the suffix (storage quota) rather than as a leading `t:{tenant_id}:` segment. Their isolation is structural: each store issues single-key operations only, so no cross-tenant read or mutation is possible, and no `SCAN` can enumerate another tenant's counter.

**Guard passthrough.** The Redis Guard validates a command's keys against the `Scope` carried in the command context and passes an unscoped command through unvalidated (`rediskeys.go:24-28`). `ValidateKey` admits `cb:`, `lenny:pod:`, `t:`, and `{root}:dlg:` prefixes and rejects everything else with `ErrNoPrefix` (`rediskeys.go:114-134`). The Category-B keys, `pg:sess-tenant`, `conn:oauth:state:`, `derive_lock:`, and `lenny:events:` are issued on unscoped or platform-scoped paths that the Guard passes through; they are not admitted by a `ValidateKey` prefix arm. The summary states this mechanism rather than claiming the wrapper recognizes them.

**Channel-name reconciliation.** The circuit-breaker change channel is a pub/sub pathway documented in the §12.6 "Infrastructure pub/sub exclusion" paragraph (`spec/12_storage-architecture.md:714`) as a gateway-internal replica-sync mechanism, so it never belonged in the §12.4 key-prefix table. The defect is that the spec names it `circuit_breaker_events` (`spec/11:301`, `spec/12:714`) while the code publishes on `cb:events` (`cachingstore.go:31`). S4 renames the two spec occurrences to the literal `cb:events` so all references agree, and adds no §12.4 row because the channel is not a key prefix.

## 4. Proposed changes

### S1. Add the omitted tenant-embedded, session-scoped, and platform-scoped prefix families to the §12.4 table

**Target:** `spec/12_storage-architecture.md`, §12.4 "Redis HA and Failure Modes", the table intro sentence (`spec/12_storage-architecture.md:177`) and the canonical key-prefix table body (rows currently at `spec/12_storage-architecture.md:181-193`).

**Anchor and change (intro):** The intro sentence asserts the table "lists all canonical key prefix patterns in use" (`spec/12_storage-architecture.md:177`), a platform-wide completeness claim that overreaches the tenant-isolation datastore domain the table registers (component-owned keys such as the Token Service `lenny:token:` cache and the `lenny-ops` `ops:*` keys are documented in §4.3 and §25.4 rather than here). Replace the completeness clause so it scopes to what the table registers:

```markdown
The following table registers the canonical tenant-scoped key prefix patterns and the documented exceptions to the tenant-prefix rule:
```

**Anchor and change (rows):** Insert the following rows into the table. Place the `rl:` and `sq:` rows after the `t:{tenant_id}:quota:tokens:{user_id}:{window}` row (`spec/12_storage-architecture.md:182`), so the quota-family rows sit together. Place the `derive_lock:` row, the `lenny:events:` row, the combined tenant-leading `pg:*` row, the `pg:sess-tenant` row, and the `conn:oauth:state:` row after the `{root_session_id}:dlg:*` delegation row (`spec/12_storage-architecture.md:193`), at the end of the table body, so the session-scoped, playground, and connector-OAuth exceptions follow the existing exception rows.
