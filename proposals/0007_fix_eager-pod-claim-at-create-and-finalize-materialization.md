# Proposal: Eager pod claim at create and finalize-time workspace materialization

- **Status:** Approved (2026-06-18). Verified and converged after 7 adversarial review rounds (11 findings fixed); awaiting implementation via implement-proposal. This is a code-to-spec reconciliation with a small set of staged spec edits; the bulk of the work is bringing the gateway session-creation path up to the lifecycle the spec already describes. It reverses the deferred-claim decision recorded in the F-7.1.6 resolution and closes F-7.1.17.
- **Date:** 2026-06-18.
- **Scope:** Reconciles the gateway's `POST /v1/sessions` → `/upload` → `/finalize` → `/start` decomposed lifecycle to the §7.1 / §15.1 claim-at-create model. The warm pod is claimed at `/create`, uploaded files are buffered in the Artifact Store during the upload window, `/finalize` streams the buffered content into the claimed pod, materializes `/workspace/current`, runs setup commands, and assigns the credential lease, blocking until the session is `ready`, and `/start` launches the runtime. The change is mostly code-to-spec; it stages modest spec edits to (a) resolve the §7.1-vs-§4.1 upload-staging inconsistency in favor of Artifact-Store buffering and (b) move credential-lease assignment from create to finalize.

This document stages the proposed spec edits. It does not modify any spec file or any code. The proposal is a draft for review; apply the changes in the "Proposed spec changes" section and implement the code during implementation after sign-off, without re-litigating the recorded decisions.

## 1. Problem

The spec's detailed session-lifecycle sections describe a single coherent model: the warm pod is claimed at session create, uploads land in the pod's staging area, and `/finalize` validates staging, materializes the workspace, and runs setup so the session reaches `ready` before `/start` launches the runtime. The implementation instead defers the entire pod-bind sequence (pod claim, workspace staging, materialization, setup commands, credential-lease assignment, and runtime launch) to `/start`. `/create` persists a row and mints an upload token but claims no pod, and `/finalize` is a gateway-only state transition that touches no pod. F-7.1.17 (`BUILD-GAPS.md:6095`, Low, DEFERRED) is the narrow symptom: `/finalize` does not validate staging or materialize the workspace. The root cause is the deferred-claim architecture that the F-7.1.6 resolution (`BUILD-GAPS.md:5735`, Medium, CLOSED) blessed at the code level without reconciling the spec.

**What the spec says (claim at create; finalize materializes).**

- §7.1 step 4 (`spec/07_session-lifecycle.md:19`): `Select pool, claim idle warm pod`, inside the "creation atomic unit (steps 2–8)" that runs at `CreateSession`.
- §7.1 steps 6–7 (`spec/07_session-lifecycle.md:21-25`): evaluate `CredentialPolicy`, assign the `CredentialLease`, and `AssignCredentials` to the pod, also inside the create atomic unit.
- §7.1 steps 11–13 (`spec/07_session-lifecycle.md:34-36`): `FinalizeWorkspace()` → `Validate staging, materialize to /workspace/current` → `Run setup commands`.
- §15.1 endpoint preconditions (`spec/15_external-api-surface.md:617`): `POST /finalize` … `Triggers workspace materialization and setup commands`. `POST /start` (`:618`) … `Starts the agent runtime`.
- §15.1 state definitions: `created` (`:630`) = "a warm pod has been claimed and credentials assigned (see §7.1 steps 4–6) … On expiry the gateway transitions the session to `expired`, releases the pod claim back to the pool, and revokes the credential lease"; `finalizing` (`:631`) = "Workspace materialization and setup commands in progress"; `ready` (`:632`) = "Setup complete, awaiting `start`".
- §15.1 `/terminate` notes (`spec/15_external-api-surface.md:620`): for `created`, "releases resources if any were allocated"; for `finalizing` and `ready`, "releases the pod". Both presuppose a pod is already held before `/start`.

**What the code does (defer everything to `/start`).**

- `createSession` (`pkg/gateway/sessionserver/sessionserver.go:2282`) runs the admission and quota gates, the workspace-plan validation, the row persist, and the upload-token mint. It claims no pod, runs no credential availability pre-check, and assigns no credential lease. The §7.1 step-3 credential availability pre-check is `resolveCredentialPools` (`pkg/gateway/sessionserver/start.go:1047`, calling `credrouter.PreClaim` at `start.go:1109`), invoked only from `startOnPod` (`start.go:1218`) at `/start`, so the security-relevant availability gate that step 3 places before the step-4 claim does not run at create today.
- `handleFinalize` / `transitionFinalize` (`pkg/gateway/sessionserver/sessionserver.go:3052`, `:3039`) bind the optional §14 WorkspacePlan to the row, validate that every `uploadRef` belongs to this session, close the upload window, and set the state directly to `ready`. No pod is involved; `transitionFinalize` is `row.State = session.StateReady`.
- `startOnPod` (`pkg/gateway/sessionserver/start.go:1213`) → `Binder.Bind` (`pkg/gateway/podsession/binder.go:625`) runs the whole §4.7 sequence at `/start`: `connect` claims the pod (`Claimer.Claim`), then `stageWorkspace` (PrepareWorkspace), `FinalizeWorkspace`, `RunSetup`, `assignCredentials`, and `StartSession`.
- The `created`-state TTL sweeper (`pkg/gateway/createdsweeper/createdsweeper.go`) drops abandoned `created` rows; it releases no pod because none is held, contradicting the §15.1 line 630 "releases the pod claim back to the pool" semantics.

**The spec also disagrees with itself about where uploads stage.** §4.1 line 105 (`spec/04_system-components.md:105`) defines the Upload Handler as doing "payload validation, **staging to the Artifact Store**, and archive extraction", and §7.4 line 451 (`spec/07_session-lifecycle.md:451`) states archive extraction "runs inside the gateway's Upload Handler subsystem … **never delegated to agent pods**". Both describe gateway-side, store-mediated staging, which the code implements: `runUpload` writes uploaded bytes to the blob store and returns a `lenny-blob://` reference (`pkg/gateway/sessionserver/upload.go:309`). But §7.1 step 10 (`spec/07_session-lifecycle.md:32`) says `Gateway → Pod: Stream files over mTLS into /workspace/staging`, and §7.4 lines 459/461 describe validation and promotion against `/workspace/staging` → `/workspace/current`, which §6.4 defines as pod volumes. The spec is internally inconsistent on the upload-staging target independent of the claim-timing question.

Findings: **F-7.1.17** (`BUILD-GAPS.md:6095`) is closed by making `/finalize` materialize. **F-7.1.6** (`BUILD-GAPS.md:5735`) is reopened: its resolution stated that "restructuring the gateway to claim at create-time … is explicitly out of scope"; this proposal overrides that decision. **F-7.1.20** (`BUILD-GAPS.md:6160`) is touched: the `created`-expiry sweeper must release the claimed pod rather than merely drop the row.

## 2. Decisions

The following were decided in review with the human approver and constrain this design.

- **The warm pod is claimed at `/create`, synchronously.** Pods are pre-warmed in the pool, so the claim reserves an idle pod rather than paying a cold start; doing it at create surfaces pool exhaustion immediately (fail-fast, before the client wastes an upload) and matches the §7.1 step-4 placement inside the create atomic unit. The session row persists the pod binding at create. This reverses the F-7.1.6 deferred-claim decision; the modest warm-pool capacity cost of holding a pod through the upload window is accepted because in the common case the client runs create → upload → finalize → start back-to-back, so the hold is the upload duration.
- **Uploads continue to buffer in the Artifact Store.** The gateway writes uploaded bytes to the blob store and extracts archives gateway-side (the implemented behavior, and what §4.1 / §7.4 line 451 mandate). `/finalize` streams the buffered content from the store into the claimed pod's `/workspace/staging`. Streaming directly into the pod as bytes arrive is rejected: it reintroduces an upload-before-pod-ready race and loses the gateway-side archive-extraction isolation. This resolves the §7.1-vs-§4.1 staging inconsistency in favor of store-mediated buffering.
- **`/finalize` is the preparation barrier.** It transitions `created → finalizing`, streams staging into the pod (PrepareWorkspace), materializes `/workspace/current` (FinalizeWorkspace), runs setup commands (RunSetup), and assigns the credential lease (AssignCredentials), then transitions `finalizing → ready`. It returns only once the session is fully prepared. A failure in any step fails the finalize and surfaces the corresponding error; the pod is reclaimed per the §6.2 pre-attached disposition.
- **The credential lease is assigned at `/finalize`.** Only the §7.1 step-3 credential *availability* pre-check runs at create; the actual `CredentialLease` is assigned in the finalize block. The pre-check is not implemented at create today: `resolveCredentialPools` (`pkg/gateway/sessionserver/start.go:1047`, calling `credrouter.PreClaim` at `start.go:1109`) runs only from `startOnPod` (`start.go:1218`) at `/start`. The implementation must move the pre-check (with the pod claim) into `createSession` ahead of the at-create claim, so that step 3 runs before the step-4 claim as the spec orders it. A lease held idle through a slow upload can reach rotation or TTL before the session starts, and deferring assignment trims the create-window waste to the pod alone. This is a deliberate, narrow deviation from the spec's literal step-6 ordering and is staged as a spec edit.
- **`/start` only launches the runtime.** It transitions `ready → starting`, invokes `StartSession` for a pod-warm pod or `ConfigureWorkspace` for an SDK-warm pod, and transitions to `running`. The heavy preparation is already done by `/finalize`, so `/start` is fast.
- **The `created`-expiry path releases the claimed pod (and the lease, if assigned).** The TTL sweeper extends to release the pod claim back to the pool and revoke any assigned lease, per §15.1 line 630, before retiring the row.
- **The claim is durable and handoff-safe.** The pod↔session binding is persisted at create and reconstructable by any gateway replica, so a coordinator handoff during the `create → finalize → start` window does not orphan the pod. The gateway reconnects to the claimed pod's adapter at each phase (finalize, start) rather than holding one live gRPC connection across the whole window.
- **v1 ships one implementation.** There is a single create → finalize → start path with no flag-gated deferred-claim alternative. The combined-convenience endpoint `POST /v1/sessions/start` (`handleCreateAndStart`, `pkg/gateway/sessionserver/start.go:317`) runs the same claim → prepare → launch sequence in one call.

## 3. Design overview

The decomposed lifecycle splits the §4.7 session-assignment sequence across the three client calls, instead of running it all at `/start`:

```
POST /v1/sessions  (create)        claim idle warm pod (sync);
  availability pre-check             persist pod<->session binding;
  claim pod (step 4)                 mint uploadToken; state = created
        |                            fail-fast on pool exhaustion
        v
POST /upload[-archive]  (n times)  buffer bytes to Artifact Store
  -> lenny-blob:// refs              (no pod I/O); state stays created
        |
        v
POST /finalize  (barrier)          state: created -> finalizing;
  reconnect to claimed pod           PrepareWorkspace (stream blobs in),
  stream + materialize + setup       FinalizeWorkspace (materialize current),
  + assign credential lease          RunSetup, AssignCredentials;
        |                            blocks until ready; state -> ready
        v
POST /start  (launch)              state: ready -> starting;
  StartSession (pod-warm) or         runtime launches; state -> running
  ConfigureWorkspace (SDK-warm)
```

`Binder.Bind`'s single monolithic sequence is decomposed into three reusable phases: a claim phase invoked from create, a prepare phase invoked from finalize, and a launch phase invoked from start. Each phase resolves the claimed pod's adapter address from the persisted binding and reconnects, so no phase depends on a connection held open by the phase before it.

## 4. Detailed design

### 4.1 Create: synchronous claim and durable binding

`createSession` keeps its current admission, quota, and plan-validation gates. It gains the §7.1 step-3 credential availability pre-check, which currently runs at `/start` inside `startOnPod` (`resolveCredentialPools`, `pkg/gateway/sessionserver/start.go:1047`/`:1218`). The implementation moves that pre-check call from `startOnPod` into `createSession` so that step 3 runs at create ahead of the step-4 claim, surfacing credential-pool exhaustion (`CREDENTIAL_POOL_EXHAUSTED`) before any pod is claimed or wasted. After the gates and the pre-check pass and before persisting the row, `createSession` claims an idle warm pod via the existing `podclaim.Claimer.Claim` path (the same call `Binder.connect` makes today, lifted to create). The claim outcome (the `SandboxClaim` reference and the resolved pool) is persisted on the session row alongside the existing fields, so the binding survives replica restart and coordinator handoff. Pool exhaustion at claim returns `503 SESSION_CREATION_FAILED` with `Retry-After` (the §7.1 atomicity envelope), so the client learns of exhaustion before uploading. The `sessionIsolationLevel` returned at create is now the actual claimed pod's profile rather than a pre-resolved estimate, tightening the F-7.1.6 / F-7.1.8 accuracy guarantee.

### 4.2 Upload: Artifact-Store buffering (unchanged)

`runUpload` and `handleUploadArchive` are unchanged: bytes are written to the blob store, archives are extracted gateway-side under the §7.4 ceilings, and a `lenny-blob://` reference is returned. No pod I/O occurs during the upload window even though a pod is now claimed; the pod sits reserved and idle.

### 4.3 Finalize: the preparation barrier

`handleFinalize` keeps its plan-binding and `uploadRef` validation, then runs the prepare phase against the claimed pod: transition `created → finalizing`, reconnect to the pod's adapter, `PrepareWorkspace` (stream the buffered blobs into `/workspace/staging`), `FinalizeWorkspace` (materialize to `/workspace/current`, including the post-promotion symlink re-validation §7.4 line 461 requires), `RunSetup`, and `AssignCredentials`. On success, transition `finalizing → ready`, consume the single-use upload token, and return. On any step failure, the finalize returns the corresponding error (workspace-validation, setup-command, or credential error), and the pod is reclaimed via the §6.2 pre-attached disposition (`failPhase`). For SDK-warm (`preConnect`) pods, the `DemoteSDK` blocking-path decision moves into this phase, because it depends on the materialized workspace plan.

### 4.4 Start: launch only

`handleStart` transitions `ready → starting`, reconnects to the prepared pod, and invokes `StartSession` (pod-warm) or `ConfigureWorkspace` (SDK-warm, pointing the pre-connected SDK at the finalized cwd), then transitions to `running`. No staging, materialization, setup, or credential work remains.

### 4.5 Created-expiry: release the pod

The `created`-state sweeper is extended to release the claimed pod back to the pool and revoke any assigned lease before retiring the row, matching §15.1 line 630. Because the lease is assigned at finalize (§2), an abandoned session that never finalized holds only a pod, and the sweep releases that pod.

### 4.6 Durable binding and coordinator handoff

The pod binding persisted at create is the single source of truth for which pod a `created`/`finalizing`/`ready` session owns. Any replica can reconnect from it, so a handoff mid-window does not strand the pod, and `/terminate` on a `created`/`finalizing`/`ready` session releases the pod per §15.1 line 620. This extends the §10.1 coordinator-handoff coverage from running sessions to pre-running sessions that hold a claimed pod.

### 4.7 Combined create-and-start

`handleCreateAndStart` (`POST /v1/sessions/start`) runs claim → prepare → launch in one call, reusing the three phases, so the convenience path and the decomposed path share one implementation.

## 5. Observability surface

The §6.3 startup-latency phases shift to their new boundaries without changing the histogram structure (`lenny_session_startup_phase_duration_seconds{phase, runtime_class}` is already labeled by phase):

- The `pod_claim` phase timing is recorded at `/create`.
- The `workspace_materialization`, `setup_commands`, and `credential_assignment` phase timings are recorded in the `/finalize` block.
- The runtime-launch timing is recorded at `/start`.

The `claim-to-ready` span (§6.3) now covers `create` (claim) through `finalize` (ready), which matches the spec's intent more closely than the current start-only span.

The §16.1 `lenny_session_creation_duration_seconds` histogram and the §16.5 session-creation-latency SLO change phase scope. The metric (`spec/16_observability.md:17`) is labeled by `phase` with the set `auth`, `policy`, `credential_precheck`, `pod_claim`, `postgres_persist`, `credential_assign`, `pod_assign`, scoped to "[§7.1] steps 1–8" of the `POST /v1/sessions` handler, and the SLO measurement (`spec/16_observability.md:620`) enumerates the same credential assignment and pod assignment within the `POST /v1/sessions` window. Because the credential lease assignment moves to `/finalize`, the create handler no longer runs a `credential_assign` phase, so the `credential_assign` label is removed from the create-handler set and the SLO measurement drops the credential-assignment enumeration; the `pod_assign` label is removed because the create handler's pod work is the claim recorded by `pod_claim`, and no separate pod-side assignment runs within the create window. The create-handler phase set becomes `auth`, `policy`, `credential_precheck`, `pod_claim`, and `postgres_persist`, and the metric and SLO scope re-anchors from "steps 1–8" to the create steps that remain (authenticate and authorize, credential availability pre-check, pod claim, and Postgres persist, through the `session_id` response). No new metric names are introduced.

## 6. CRD and RBAC changes

None. The change is confined to the gateway session-creation path, the `createdsweeper`, and the `podsession` binder decomposition. No CRD field, admission webhook, or RBAC grant changes.

## 9. Testing

The change reaches the gateway, the datastore, the pod-bind path, and cluster pod lifecycle, so it touches tiers 0, 1, 2, 4, 5, and 7a (per `test-coverage.md`):

- **Tier 1:** the claim/prepare/launch phase split in `podsession`; the `createSession` claim-and-persist path; the `createdsweeper` pod-release path; the finalize barrier state transitions and failure-to-error mapping.

- **Tier 4 (compose):** create → upload → finalize → start end-to-end with Artifact-Store buffering, asserting that finalize materializes `/workspace/current` and assigns the lease, and that `/start` only launches.
- **Tier 5 (Kind):** the full lifecycle against a warm pod, including pool exhaustion surfacing at `/create`, finalize-time materialization and setup, and pod release on `created`-expiry and on `/terminate` of a `finalizing`/`ready` session.
- **Tier 7a:** concurrent creates against a finite pool (fail-fast exhaustion at create) and coordinator handoff during the `create → finalize → start` window (the pod is not orphaned).

Every test carries its `// spec:` annotation (§7.1, §7.4, §15.1) and tier-2-and-up tests carry the `// diagnosis:` comment.
