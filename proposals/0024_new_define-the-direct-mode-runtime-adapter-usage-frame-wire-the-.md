- **Status:** Verified (2026-07-01). Converged after 5 adversarial review rounds (10 findings fixed); awaiting sign-off.
- **Date:** 2026-07-01.
- **Scope:** Defines the direct-mode runtime→adapter token source that two coupled OPEN findings block on, by adding optional token-count fields to the existing §4.7 `llm_request_completed` lifecycle frame, then wiring the adapter `UsageMeter` from that frame, a gateway-side direct-mode usage path over the session-scoped adapter client, and the §11.2 direct-mode integrity anomaly metric `lenny_gateway_token_usage_anomaly_total` with a §16.1.1-compliant label set, an alert, and a runbook. It reconciles the ReportUsage-direction inconsistency between the §11.2/§6.2 push-style prose and the canonical §4.7/proto/code gateway-pull direction, repairs every dangling §7.3 citation for the adapter pod-reported cumulative-usage re-report on reconnection (`spec/11_policy-and-controls.md:46,146,164` and `spec/12_storage-architecture.md:161`), and corrects the §11.2 `session_id` label that §16.1.1 forbids. It closes `F-15.3.7` (`ReportUsage` implemented but never polled in production) and `F-11.2.20` (`lenny_gateway_token_usage_anomaly_total` emitted nowhere). ## 1. Problem

Two coupled OPEN findings are blocked on a single missing spec surface.

`F-15.3.7` (`BUILD-GAPS.md:28001`) records that `ReportUsage` "is implemented but never polled in production." The adapter handler returns `codes.Unimplemented` unless `Server.Usage` (a `UsageMeter`) is set (`pkg/adapter/usage.go:48-51`), and `cmd/lenny-adapter/main.go` never sets it (`pkg/adapter/server.go:210` declares the field; nothing in production assigns it). The gateway-side pull wrappers `Client.ReportUsage` and `Client.ReportUsageForLease` (`pkg/gateway/runtime/adapterclient/client.go:671,697`) have no production caller, though the gateway holds a pollable client at `BindResult.Adapter` (`pkg/gateway/podlifecycle/podsession/binder.go:508`).

`F-11.2.20` (`BUILD-GAPS.md:16813`) records that `lenny_gateway_token_usage_anomaly_total`, the §11.2 direct-mode integrity control (`spec/11_policy-and-controls.md:42`), is emitted nowhere. It appears only as prose at §11.2:42, is absent from the §16.1 catalog and §16.5 alerts (`spec/16_observability.md` has no `token_usage_anomaly` entry), and is absent from the code catalog (`pkg/observability/metrics/catalog.go` registers only `lenny_delegation_tree_token_usage_total` at `:147` and `lenny_gateway_llm_upstream_egress_anomaly_total` at `:176`).

The single root blocker is that direct mode has no spec-grounded runtime→adapter token source. In direct mode the pod egresses to the provider directly and cannot reach the gateway LLM proxy on port 8443 (`spec/13_security-model.md:78,118,442`), so the runtime is the sole in-pod observer of provider token counts, and the gateway has no per-call visibility (`spec/08_recursive-delegation.md:435`). Neither runtime→adapter channel carries token counts. The §4.7 lifecycle frames `llm_request_started` and `llm_request_completed` carry only `{type, requestId, provider[, status]}` (`spec/04_system-components.md:730-731`; `schemas/lifecycle-events.schema.json:186-210`, with `additionalProperties: false`), and the §15.4.1 adapter↔binary stdout types are exactly `response`, `tool_call`, `heartbeat_ack`, `status`, and `set_tracing_context` (`spec/15_external-api-surface.md:1455-1463`). The §11.2:42 claim that "the runtime adapter extracts token counts from LLM provider responses" is therefore unsupported by the wire contract: a `UsageMeter` built today has no source, the adapter handler can only return `Unimplemented` for every shipped runtime, a gateway poller would call a dead handler, and the anomaly counter would be dead config.

The polling flow is spec-anticipated. §6.2:253 and §8.3:435 bound direct-mode over-run by "the next `ReportUsage` interval," and §11.2:46 describes the adapter retaining a cumulative usage total re-reported on reconnect. The fix defines the direct-mode runtime→adapter token frame in spec first, then wires the adapter meter, the gateway usage path, the anomaly detector, and the §16.1/§16.5 catalog entry.

Verification surfaced three spec inconsistencies the fix resolves rather than replicates.

1. **`ReportUsage` is a gateway-initiated pull.** It sits under the *Gateway → Adapter RPCs:* header at `spec/04_system-components.md:643` (the *Adapter → Gateway RPCs:* header is at `:665`); the proto defines it on `service Adapter` with the adapter as server (`schemas/lenny-adapter.proto:158`; `ReportUsageRequest` carries only `session_id`, and tokens live in `ReportUsageResponse`, `:1235-1243`); and the code is a gateway pull (`client.go:671`; `usage.go:40`). The §11.2:42 and §6.2:253 push-style prose contradict this direction.
2. **Four §11.2/§12 sentences cite §7.3 for a mechanism §7.3 does not define.** The pod-reported cumulative-usage re-report on reconnection is cited to [Section 7.3] at four sites: §11.2:46 (the crash-recovery MAX rule "cumulative usage total re-reported on reconnection"), §11.2:146 (in-memory buffer events "reconstructed from pod-reported token usage during session recovery"), §11.2:164 (`GATEWAY_CRASH_RECONSTRUCTION` reconciles "from pod-reported token totals"), and §12 storage-durability table `spec/12_storage-architecture.md:161` ("In-memory buffer events reconstructed from pod-reported token usage"). §7.3 (`spec/07_session-lifecycle.md:377-425`) defines only retry and resume; the phrases "re-reported on reconnection," "cumulative usage total," "pod-reported," and "reconstruct" appear nowhere in §7.3 or §4.7. All four are dangling citations for the same mechanism. The §7.3 citations at `spec/11_policy-and-controls.md:200-201` (max resume window, max awaiting client action) are correct and stay pointed at §7.3.
3. **§11.2:42 labels the metric by `session_id`.** §11.2:42 states the metric is "labeled by `session_id` and `tenant_id`," but §16.1.1 (`spec/16_observability.md:308`) forbids `session_id` as a Prometheus label as a CI-enforced rule, backed by the denylist at `pkg/observability/metrics/metrics.go:34` and `Validate` at `:75`.

## 2. Decisions

- **Add the token source as an optional field pair on the existing §4.7 lifecycle-channel `llm_request_completed` frame rather than inventing a new runtime→adapter frame.** The frame already fires once per completed direct-mode LLM call (`spec/04_system-components.md:731`; `schemas/lifecycle-events.schema.json:198-210`), carries `requestId` and `provider`, and the adapter already consumes it. Adding optional `inputTokens` and `outputTokens` integer fields reuses the frame the runtime already sends at the settlement point, with no new channel, socket, or message type. The §15.4.1 stdout channel is the wrong home: `llm_request_started` and `llm_request_completed` already model the direct-mode LLM-call lifecycle, while the §15.4.1 messages model agent content rather than provider-call accounting.
- **Keep `ReportUsage` a gateway-initiated pull (the canonical §4.7/proto/code direction) and reconcile the §11.2:42/§6.2:253 push-style prose to it.** The runtime hands token counts to the adapter over the enriched frame; the adapter accumulates a per-session cumulative total; the gateway pulls the incremental delta over `ReportUsage`. This preserves the implemented contract (`client.go:671`; `usage.go:40`; `proto:158`) and resolves the direction contradiction rather than inverting the code. §2 S2 constrains how far the direction reconciliation extends across the spec so it does not break the §6.2 idle-detection semantics or the §8.3 `FINAL_USAGE_REPORT` quiescence protocol that depend on the adapter-driven report timing.
- **Reach the pod's adapter over the session-scoped registry accessor rather than the transient `BindResult`.** `BindResult.Adapter` (`binder.go:508`) is owned and closed by the bind caller at session teardown (`binder.go:1836-1841`), so a lifetime usage loop keys off `podRegistry.Get(sessionID)` (`pkg/gateway/podlifecycle/podsession/registry.go:33`), which returns the session's `*BindResult` for as long as the session is bound, matching the existing session-scoped adapter callers. `ReportUsageForLease` already returns `ErrUsageReportProxyMode` for proxy leases (`client.go:697-701`), so the usage path filters delivery mode and never double-counts against the §4.9 proxy path.
- **Resolve the transport question before wiring: the adapter already pushes a terminal `FINAL_USAGE_REPORT` the gateway does not consume, and the spec model is push, so do not stand up a pull poller beside an unconsumed push channel carrying the same counts.** The adapter emits `FINAL_USAGE_REPORT` carrying input, output, and wall-clock over the lifecycle control stream (`pkg/adapter/controlchannel.go:215-224`), fed by the same `UsageMeter` this proposal wires (`pkg/adapter/session.go:293-305`), and the gateway does not yet consume that stream. §6.2:253 and §8.3:425 describe the adapter driving report timing. S4 resolves the transport choice as an explicit sub-decision at implementation, either reconciling §6.2/§8.3 to a gateway pull and justifying a single pull transport, or consuming the existing push channel, with a single usage transport as the outcome.
- **Route direct-mode usage into the same sinks the proxy recorder writes, extending the existing recorder rather than adding a parallel accounting path.** The proxy sink `proxyUsageRecorder` (`cmd/lenny-gateway/llmproxy_usage.go:35`) fans one input/output pair into the usage store, the session-usage accumulator, the quota counter, the fail-open accumulator, the mid-session budget enforcer, and the idle stamper, and its `RecordUsage` drops non-proxy leases at `:142`. S4 extends that recorder (or adds a direct-mode sibling that shares its fan-out) so direct-mode deltas reach the same sinks, including the mid-session budget enforcer, because §11.2:42 requires bounding direct-mode over-run.
- **Reconcile the §11.2:42 anomaly-metric label set to comply with §16.1.1: drop `session_id`, label the counter by `tenant_id` plus a bounded classification label.** `session_id` is CI-forbidden (`spec/16_observability.md:308`; `pkg/observability/metrics/metrics.go:34`). The detector evaluates per session (counting zero-token `ReportUsage` deltas per session), but the emitted counter increments a per-tenant series, matching `lenny_tokens_consumed_total` (`spec/16_observability.md:22`) and the delegation metrics that exclude `root_session_id` (`spec/16_observability.md:67`). Per-session attribution moves to structured logs, as §16.1.1 directs.
- **Operationalize the anomaly firing condition, which §11.2:42 under-specifies.** §11.2:42 pins the per-session zero-token window ("more than 3 `ReportUsage` calls within a session with zero tokens reported") but leaves the "implausibly small relative to LLM call frequency" branch with no numeric threshold, does not state whether the more-than-3 zero-token reports must be consecutive, and leaves "while LLM proxy activity is absent" undefined for direct mode. The fix defines the implausibly-small ratio threshold and the consecutiveness/window semantics as operator-tunable, flag-overridable, documented gateway config, and resolves "LLM proxy activity is absent" to the direct-mode predicate: the session's lease is direct-mode, so proxy activity is definitionally absent.
- **Register `lenny_gateway_token_usage_anomaly_total` in the §16.1 catalog and the `pkg/observability/metrics` code catalog, register a `TokenUsageAnomaly` alert in the single-source code catalog `pkg/alerting/rules/rules.go` (with its §16.5 spec-table mirror), mirror both into the hand-authored operator reference `docs/reference/metrics.md`, and add a runbook so tier-11 alert-to-runbook resolution passes.** The §16.5 alert catalog is single-sourced in Go: `Catalog()` in `pkg/alerting/rules/rules.go` is the source the gateway compiles into its in-process alert tracker and the Helm chart renders into a `PrometheusRule` CRD, with `charts/lenny/files/alerting-rules.yaml` and `docs/alerting/rules.yaml` regenerated by `make generate`. An alert added only to the §16.5 spec table never renders and fails the tier-11 checks that iterate `rules.Catalog()`. Git confirms the metric never existed in code; it lands together with its emitting detector and its code-catalog alert so it is not dead config.
- **Give §11.2:46 a wire path to the pod-reported cumulative total, then repair its dangling §7.3 citation.** §11.2:46 reconstructs direct-mode quota counters after a gateway crash as `MAX(postgres_checkpoint, pod-reported cumulative total)`, which requires a reconnected gateway replica to pull the pod's session-cumulative usage total. A delta-only `UsageMeter` cannot supply that total: its `ReportUsage` read returns only the delta since the crashed replica's last read, so a fresh replica would evaluate `MAX(stale_checkpoint, small_delta)` and silently under-count. Re-pointing the §7.3 citation to §4.7 alone does not close the gap, because §4.7's `ReportUsage` exposes no cumulative total until the meter and RPC carry one. The fix therefore adds the cumulative read to the `UsageMeter` and the `cumulative` flag to `ReportUsageRequest` (S3), defines the adapter cumulative-total-re-reported-on-reconnection behavior in §4.7 where `ReportUsage` lives, and re-points every §7.3 citation for the pod-reported cumulative-usage re-report (`spec/11_policy-and-controls.md:46,146,164` and `spec/12_storage-architecture.md:161`) from §7.3 (which defines only retry and resume, `spec/07_session-lifecycle.md:377-425`) to §4.7. Those sentences then cite a section that defines the mechanism, and the mechanism has a wire path to the value it needs.
- **Do not touch the proxy-mode path.** Proxy mode extracts authoritative counts at the §4.9 LLM proxy (`spec/11_policy-and-controls.md:41`), ignores `ReportUsage` for proxy sessions, and has no anomaly to detect. The change is direct-mode-scoped and adds no tier-dependent split beyond the delivery-mode filter the spec already draws.

### S1. Add optional `inputTokens`/`outputTokens` to the §4.7 `llm_request_completed` runtime→adapter frame and its JSON schema, defining the direct-mode token source

**Targets:**
- `spec/04_system-components.md`: the §4.7 lifecycle-channel message-schema table `llm_request_completed` row (`:731`) and the frame-roster prose (`:708-710`).
- `schemas/lifecycle-events.schema.json`: the `llm_request_completed` `$def` (`:198-210`, currently `additionalProperties: false` with `required=[type, requestId, provider, status]`).

**Rationale.** This is the spec surface both findings block on. No runtime→adapter frame carries token counts today (`schemas/lifecycle-events.schema.json:198-210`; `spec/15_external-api-surface.md:1455-1463`), so the adapter has no direct-mode token source. `llm_request_completed` is the frame the runtime already sends once per completed direct-mode LLM call, at the settlement point where counts are known, and the adapter already consumes it (`spec/04_system-components.md:731`). Enriching it is the minimal reuse. Every code change (S3 through S6) depends on this landing and being verified first.

**Sketch.** In the §4.7 `llm_request_completed` table row (`spec/04_system-components.md:731`) add two optional integer fields, `inputTokens` (prompt tokens extracted from the completed provider response) and `outputTokens` (completion tokens), with a Notes clause: the runtime SHOULD populate these in direct mode when it can extract them, and the adapter accumulates them into a per-session cumulative total internally and reports the incremental delta since the last read over the §4.7 `ReportUsage` RPC. Mark them optional so a runtime that cannot extract counts still sends a valid frame, in which case the adapter has no source for that session, which the S5 detector observes as a zero-token delta. In `schemas/lifecycle-events.schema.json:198-210` add `inputTokens` and `outputTokens` as `{"type": "integer", "minimum": 0}` properties on the `$def`, kept out of `required`; this is compatible with `additionalProperties: false` because they are now declared properties. Add a one-line note to the frame-roster prose at `:708-710` that `llm_request_completed` optionally carries the direct-mode token counts. Cite §11.2 direct-mode usage in the schema description.

The row text is:

```markdown
| `llm_request_completed`     | Runtime → Adapter  | `type`, `requestId` (string — matches the corresponding `llm_request_started`), `provider` (string), `status` (`"ok"` \| `"error"`), `inputTokens` (integer, optional), `outputTokens` (integer, optional)                               | Runtime's outbound LLM request has completed or errored. Adapter decrements the in-flight counter. When the counter reaches zero and a credential rotation is pending, the adapter proceeds to send `credentials_rotated`. In direct mode the runtime SHOULD populate `inputTokens` and `outputTokens` from the completed provider response when it can extract them; the adapter accumulates them into a per-session cumulative total internally and reports the incremental delta since the last read over the §4.7 `ReportUsage` RPC (see [Section 11.2](11_policy-and-controls.md#112-budgets-and-quotas)). A runtime that cannot extract counts omits both fields, and the session has no direct-mode token source. |
```

The `$def` becomes:

```json
    "llm_request_completed": {
      "title": "llm_request_completed",
      "description": "Runtime → adapter. The runtime's outbound LLM request has completed or errored. The adapter decrements the in-flight counter; when it reaches zero and a rotation is pending, the adapter sends credentials_rotated. In direct mode (§11.2) the runtime optionally carries the prompt and completion token counts extracted from the provider response, which the adapter accumulates into a per-session cumulative total internally and reports as the incremental delta since the last read over the §4.7 ReportUsage RPC.",
      "type": "object",
      "properties": {
        "type": { "const": "llm_request_completed" },
        "requestId": { "type": "string", "minLength": 1 },
        "provider": { "type": "string", "minLength": 1 },
        "status": { "enum": ["ok", "error"] },
        "inputTokens": { "type": "integer", "minimum": 0 },
        "outputTokens": { "type": "integer", "minimum": 0 }
      },
      "required": ["type", "requestId", "provider", "status"],
      "additionalProperties": false
    }
```

### S2. Reconcile the §11.2/§6.2 ReportUsage-direction prose to the gateway-pull model and repair the dangling §7.3 citation

**Targets:**
- `spec/11_policy-and-controls.md`: the §11.2 direct-mode bullet (`:42`) and every §7.3 citation for the pod-reported cumulative-usage re-report on reconnection: the crash-recovery MAX rule (`:46`), the in-memory-buffer reconstruction (`:146`), and the `GATEWAY_CRASH_RECONSTRUCTION` reconciliation (`:164`). The §7.3 citations for the resume-window parameters (`:200-201`) are correct and stay pointed at §7.3.
- `spec/12_storage-architecture.md`: the §12 storage-durability table row (`:161`) whose "In-memory buffer events reconstructed from pod-reported token usage" cites §7.3 for the same mechanism.
- `spec/06_warm-pod-model.md`: the §6.2 direct-mode idle bullet (`:253`, "Each `ReportUsage` gRPC call received from the adapter").
- `spec/08_recursive-delegation.md`: the §8.3 `FINAL_USAGE_REPORT` quiescence prose (`:425`) and the over-run item (`:435`), reconciled only if the reviewer expands scope per the challenge notes below.
- `spec/07_session-lifecycle.md`: §7.3 (`:377-425`), only if the reviewer homes the re-report mechanism here.

**Rationale.** `ReportUsage` is a gateway pull at every authoritative surface (`spec/04_system-components.md:643` header; `schemas/lenny-adapter.proto:158`; `client.go:671`; `usage.go:40`), while §11.2:42 and §6.2:253 describe an adapter push. Left unreconciled, the applied spec is internally inconsistent about who drives the call, and the enriched-frame flow reads as self-contradicting. Four citations to §7.3 are dangling: §11.2:46, §11.2:146, §11.2:164, and `spec/12_storage-architecture.md:161` all cite §7.3 for the pod-reported cumulative-usage re-report, but §7.3 (`spec/07_session-lifecycle.md:377-425`) defines no such mechanism. This change addresses two genuine defects, and its scope and resolution direction are constrained by the challenge notes so it does not leave the applied spec more inconsistent than it found it.

**Sketch.** Keep the §7.3-citation repair across all four dangling sites (§11.2:46, §11.2:146, §11.2:164, and `spec/12_storage-architecture.md:161`); it fixes real dangling references. For the direction inconsistency, do not rewrite §6.2:253 into a gateway-poll: that silently breaks the idle-detection semantics (§6.2:253 treats each `ReportUsage` as adapter-driven evidence of active work whose cadence the adapter owns) and strands the implemented `FINAL_USAGE_REPORT` quiescence protocol (`spec/08_recursive-delegation.md:423-425`; `spec/04_system-components.md:689`), which depends on the adapter flushing in-flight `ReportUsage` calls. Choose one coherent path: (i) expand scope to reconcile every adapter-push surface together, §11.2:42, §11.2:46, §6.2:253, §8.3:423, §8.3:425, §4.7:689, and §8.3:435, preserving the adapter-initiated conceptual model (the adapter drives report timing) and clarifying only that the gRPC transport is adapter-as-server; or (ii) narrow the direction fix to a single clarifying sentence at the §4.7/proto boundary and leave §6.2:253 and the §8.3 quiescence prose untouched. Either way, resolve the direction contradiction consistently across all six surfaces or not at all; do not reconcile two lines against the grain of four others.

**The four §7.3 citations and the cumulative-total wire path.** Re-point every dangling citation for the pod-reported cumulative-usage re-report and give the mechanism a wire path. The mechanism is cited to [Section 7.3](07_session-lifecycle.md#73-retry-and-resume) at four sites, none of which §7.3 defines: §11.2:46 ("each pod's runtime adapter retains a cumulative usage total that is re-reported on reconnection to a new gateway replica"), §11.2:146 (in-memory buffer events "reconstructed from pod-reported token usage during session recovery"), §11.2:164 (`GATEWAY_CRASH_RECONSTRUCTION` reconciles "from pod-reported token totals"), and `spec/12_storage-architecture.md:161` ("In-memory buffer events reconstructed from pod-reported token usage"). The `MAX(postgres_checkpoint, pod-reported cumulative total)` reconstruction the §11.2:46 sentence supports has no way to read the pod-reported cumulative total once the meter is delta-only. Re-point all four anchors to [Section 4.7](04_system-components.md#47-runtime-adapter), where `ReportUsage` and the adapter's cumulative accumulation are defined, and add to §4.7 the cumulative-total-re-reported-on-reconnection behavior backed by the S3 cumulative read and the `ReportUsageRequest.cumulative` flag. This is the load-bearing half of Open decision 1: without the cumulative read the re-point resolves the citations but leaves §11.2:46 asserting a recovery with no wire path to the value it needs. Under the Open-decision-1 alternative (keep the meter delta-only and revise the §11.2:46 reconstruction so it does not depend on a pod-reported cumulative total), all four citations stay pointed at §7.3 only if the re-report mechanism is instead defined in §7.3; do not re-point one citation in isolation, so the four sites and §11.2:46 continue to agree on where the mechanism lives.

**Challenge notes (applied verbatim).** S2 addresses two genuinely real defects, so it cannot be dropped, but its scope and its resolution direction are both wrong and would leave the applied spec more inconsistent than it found it.

REAL DEFECTS. (a) The dangling section-7.3 citation is confirmed. 11.2:46 cites 7.3 for the adapter cumulative-usage total re-reported on reconnection, but 7.3 (spec/07_session-lifecycle.md:377-425) defines only retry/resume, and the phrases re-reported-on-reconnection and cumulative-usage-total appear nowhere in 7.3 or 4.7. (b) A ReportUsage direction inconsistency is real: the proto puts ReportUsage on service Adapter (schemas/lenny-adapter.proto:158), so at the gRPC transport level the gateway is the caller (client.go:671-673), while spec prose describes it as adapter-initiated.

WRONG-1, UNDER-SCOPED. S2 targets only 11.2:42 and 6.2:253 and instructs do-not-restructure-the-surrounding-paragraphs. But the adapter-push framing is spec-wide and lives in surfaces S2 never touches: 8.3:423 (the ReportUsage gRPC call from the pod), 8.3:425 and 4.7:689 (after all in-flight ReportUsage calls have been flushed), and 8.3:1109 (over-run bounded by the next ReportUsage interval). Reconciling only two lines to gateway-pull while 8.3/4.7 retain the push framing leaves the applied spec internally inconsistent, the exact defect S2 claims to close.

WRONG-2, BREAKS A LOAD-BEARING BEHAVIOR. S2 declares gateway-pull canonical (from the proto being adapter-as-server) and rewrites 6.2:253 to each-ReportUsage-pull-the-gateway-issues. But 6.2:253 is a list of qualifying idle-clock-reset events, and it treats each ReportUsage as evidence of active work whose cadence is determined by the adapter reporting configuration (spec/06_warm-pod-model.md:253). If the gateway owns the poll cadence (S4 ticker), a gateway self-poll on a fixed timer resets the idle clock regardless of agent activity, so a hung direct-mode pod never idle-times-out. The push model is load-bearing for 6.2 idle detection and for the 8.3 FINAL_USAGE_REPORT quiescence protocol (in-flight ReportUsage calls flushed before FINAL_USAGE_REPORT), which is implemented in code (emitFinalUsage at pkg/adapter/session.go:293-297, EmitFinalUsageReport at pkg/adapter/controlchannel.go:212). sessionstore.go:324 likewise treats a direct-mode ReportUsage as an inbound activity signal.

CONCLUSION. The need is real (both the direction inconsistency and the dangling citation exist), but S2 as written is oversized-yet-under-scoped and picks a resolution that breaks implemented behavior, so it must be revised rather than kept or dropped.

### S3. Wire the adapter `UsageMeter` from the enriched frame and set it on the adapter server in production

**Targets:**
- `schemas/lenny-adapter.proto`: `ReportUsageRequest` (`:1235-1237`, currently carrying only `session_id`), adding a `cumulative` bool flag so a reconnected gateway replica can pull the session cumulative total for the §11.2 crash-recovery MAX rule.
- `pkg/adapter/usage.go`: the `UsageMeter` interface (`:28-34`) and the `ReportUsage` handler (`:40-61`).
- `pkg/adapter/session.go`: the `emitFinalUsage` consumer (`:293-305`), which already reads `s.Usage`.
- `pkg/adapter` (the lifecycle-channel handler that consumes `llm_request_completed`): fold token accumulation into it.
- `cmd/lenny-adapter/main.go`: the `adapter.New` construction and the field-assignment block, which never sets `adapterSrv.Usage`.

**Rationale.** The adapter `ReportUsage` handler returns `codes.Unimplemented` whenever `Server.Usage` is nil (`usage.go:48-51`), `Server.Usage` is set nowhere in production (`server.go:210`; only test stubs assign it), and `cmd/lenny-adapter/main.go` never sets it. With S1's frame carrying tokens, a production `UsageMeter` now has a spec-grounded source: the per-session accumulation of `llm_request_completed` token deltas.

## Open decisions for review

1. **The cumulative-total wire path the §11.2:46 crash-recovery MAX rule depends on, and where the re-report-on-reconnection contract lives.** §11.2:46 reconstructs direct-mode quota counters after a gateway crash as `MAX(postgres_checkpoint, pod-reported cumulative total)`, so a reconnected gateway replica must be able to pull the pod's session-cumulative usage total. The S3 meter reports the incremental delta over `ReportUsage`, which a fresh replica cannot use for the MAX rule, so the recovery needs a distinct cumulative accessor. The recommended resolution adds a cumulative read to the `UsageMeter` and a `cumulative` flag on `ReportUsageRequest` (S3), defines the cumulative-total-re-reported-on-reconnection behavior in §4.7 alongside `ReportUsage`, and re-points all four §7.3 citations for the pod-reported cumulative-usage re-report (`spec/11_policy-and-controls.md:46,146,164` and `spec/12_storage-architecture.md:161`) to §4.7. The alternative keeps `ReportUsage` delta-only and instead revises §11.2:46 so the recovery reconstruction no longer depends on a pod-reported cumulative total, reconciling the MAX-rule wording accordingly and homing the re-report mechanism in §7.3 so all four citations continue to resolve. The reviewer picks one; the recommended path is the first, because it preserves the §11.2:46 under-count protection that the direct-mode integrity control exists to provide. Re-pointing the citation alone, without one of these two, leaves §11.2:46 asserting a recovery with no wire path to the value it needs.
2. **The anomaly metric's second label.** A bounded `reason` (`zero_delta` or `implausibly_small`) in addition to `tenant_id`, or `tenant_id` alone. A `reason` label aids operator triage and is bounded (safe under §16.1.1) but adds a series dimension; the reviewer decides whether the extra cardinality is warranted.
3. **The default direct-mode `ReportUsage` poll interval and its minimum.** §6.2:253 and §8.3:435 tie the direct-mode over-run bound to "the `ReportUsage` interval" but the spec names no value today; the default trades over-run exposure against poll load. A value in the tens of seconds aligns with `quotaSyncIntervalSeconds` (30s) without being coupled to it; the reviewer should confirm the number and minimum.
4. **The transport for direct-mode usage (from the S4 challenge notes).** Reconcile §6.2/§8.3 to a gateway pull and run a single pull transport, or consume the already-implemented `FINAL_USAGE_REPORT` push channel; the outcome is a single usage transport rather than a pull poller beside an unconsumed push channel.
