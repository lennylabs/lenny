# Proposal: Implement §5.2 scrub step 7 (`vm-restart`) as a control-plane-brokered guest VM restart: reword the step-7 attribution off the in-guest adapter, drive the guest restart from the Lenny control plane, and re-verify the fresh guest before any cross-tenant reuse, so the agent-pod isolation posture (§13.1 host-sharing-forbidden, §10.3 zero-RBAC, §13.2 default-deny egress) is untouched

- **Status:** Verified (2026-07-02). Converged after 5 adversarial review rounds (7 findings fixed); awaiting sign-off.
- **Date:** 2026-07-02.
- **Scope:** A spec-first change that reattributes the §5.2 `vm-restart` scrub profile (step 7) from the in-guest adapter to the Lenny control plane, plus a gated code change that removes the unimplementable in-guest restart seam. **(S-1)** rewords §5.2 step 7 so the guest VM restart is effected by the control plane rather than the in-guest adapter and states the required outcome (a fresh guest with no residual state, re-verified clean before any cross-tenant reuse, fail-closed otherwise), keeping the `ReportPodScrub` outcome binary and committing to no concrete restart mechanism. **(S-2)** documents the §4.7 `ReportPodScrub` consequence for a `vm-restart` pool: a successful pre-restart report does not itself return the pod to reuse, and the missing-report timeout sentence gains a `vm-restart` restart-window exception in §4.7 where that timeout is defined. **(C-2)** removes the in-guest `scrub.VMRestarter` seam (`pkg/adapter/scrub/scrub.go:95-101,:175,:218-220,:236-237,:275-280`) so `scrub.Run` is uniform across profiles, and routes a binary pre-restart `SUCCEEDED` report to the control-plane restart on the pool's already-held `MicrovmScrubMode`; C-2 is **gated** behind proposal 0031 landing, reviewer acceptance of the control-plane direction, and the mechanism-feasibility open decision (which fixes the terminal-disambiguation and projection details). **(C-T)** spans tiers 1, 2, 7a, and 6 (NEEDS-OPERATOR). ## 1. Problem

§5.2 defines the `vm-restart` scrub profile (step 7): on a cross-tenant sequential-reuse microvm pool the guest VM is restarted after scrub steps 0-6, then step 6 is re-verified on the fresh guest (`spec/05_runtime-registry-and-pool-model.md:473-477`). The current spec attributes the restart to the in-guest actor: "The adapter requests a full guest VM restart via the Kata runtime's VM lifecycle API" (`spec/05:475`). That attribution is unimplementable under the isolation model and unwired in code, for two independent reasons.

### The survivor and driver problem

Under Kata the adapter is a sidecar inside the guest VM (`spec/04_system-components.md:876,:881`; the adapter is an in-pod sidecar container, and under Kata that container runs inside the guest). A full guest restart destroys the process that would drive it: one actor cannot both trigger the restart and survive to report success. Separately, an in-guest, zero-RBAC adapter cannot reach the host-side Kata VM lifecycle API. Host sharing is forbidden on every agent pod (`spec/13_security-model.md:16-23`, `POD_SPEC_HOST_SHARING_FORBIDDEN`), default-deny egress allows only the gateway port and DNS, and agent pods hold zero RBAC with no kube-apiserver path. Reaching a host Kata lifecycle socket would require a host carve-out on the agent pod that the security model rejects.

### The seam is unwired and fail-closes

The in-guest `scrub.VMRestarter` seam encodes exactly this broken single-process flow: `Run` calls `cfg.Restarter.RestartGuest(ctx)` then inline re-verifies (`pkg/adapter/scrub/scrub.go:275-280`), and `Run` returns `ErrNoRestarter` when `MicrovmRestart` is set with a nil `Restarter` (`scrub.go:218-220,:236-237`). The only `RestartGuest` implementer is a test fake; `pkg/adapter/scrub` has no production restart caller. Proposal 0031 (Approved) deliberately kept this seam and spun the concrete Kata restarter out as a NEEDS-OPERATOR follow-on, and proposal 0035 documents that a `vm-restart` pool stays fail-closed through the `ErrNoRestarter` withhold until that follow-on lands. This proposal is that follow-on. It resolves step 7 in the control-plane direction rather than by supplying an in-guest concrete `VMRestarter`, because the survivor and driver problem makes the in-guest actor the wrong owner.

### Resolution direction

The in-guest adapter reports the binary whole-pod scrub outcome after steps 0-6; the Lenny control plane performs the guest restart; the fresh guest's clean state is confirmed before the pod returns to cross-tenant reuse (how it is confirmed follows the §9 mechanism). Agent pods keep zero RBAC, the §13.2 default-deny egress and the §13.1 host-sharing-forbidden posture are untouched. The `ReportPodScrub` outcome stays binary (`POD_SCRUB_OUTCOME_SUCCEEDED`/`FAILED`/`UNSPECIFIED`, `schemas/lenny-adapter.proto:428-439`): the gateway already holds the pool's scrub profile at the recycle boundary (`resolve.go:106,:264` set `MicrovmScrubMode` from `sp.Recycle.ScrubProfile`), so it branches to the restart on a binary success report without a new wire value. The controller lifecycle carries no restart primitive (the `Action` enum is `{ActionNone, ActionCreatePod, ActionDeletePod, ActionSetPhase}`, `pkg/controller/sandbox/lifecycle/lifecycle.go:53-60`), so how the control plane effects the restart (an in-place guest restart via a privileged node executor, or a retire-and-reprovision through the existing WarmPoolController `ActionDeletePod`/`ActionCreatePod` lifecycle) is a NEEDS-OPERATOR feasibility question this proposal defers.

## 2. Decisions

- **The restart is control-plane-brokered.** The guest VM restart is performed by the Lenny control plane rather than the guest-resident adapter. Agent pods keep zero RBAC, the §13.2 default-deny egress and the §13.1 host-sharing-forbidden posture (`spec/13:16-23`) are untouched. This rejects both in-guest models: a host-mounted Kata control socket into the agent pod, and an agent pod calling a node broker, each of which needs an agent-pod §13.1 host-sharing carve-out. Preserving the carve-out-free agent-pod posture is the central invariant.
- **The step-6 re-verification runs on the fresh guest.** Because the restart destroys the adapter that ran steps 0-6, the re-verification runs on the fresh guest that boots after the restart, which `spec/05:475` already implies when it states step 6 is re-executed after the guest restarts. No control-plane component runs the in-guest filesystem verification. How the fresh guest's clean state reaches the control plane before reuse depends on the §9 mechanism: a same-pod post-restart `ReportPodScrub` from a fresh in-guest adapter under an in-place restart, or a fresh warm pod's normal warm-up under a retire-and-reprovision. The in-place same-pod re-verify carries additional durable-state and disambiguation requirements (see the §9 open decisions and C-2); this proposal does not decide between them.
- **The `ReportPodScrub` outcome stays binary.** The gateway routes a pre-restart `SUCCEEDED` report on a `vm-restart` pool to the control-plane restart by keying on the pool's already-known `MicrovmScrubMode` (`resolve.go:106,:264`), so the pre-restart routing needs no new wire value. Whether an in-place same-pod post-restart re-verify additionally requires a self-identifying signal (a scrub-attempt generation or a durable claim stamp), because an in-memory recycle-boundary phase alone cannot safely disambiguate a retried pre-restart report from a terminal post-restart report and does not survive the guest reboot across gateway replicas, is a mechanism-dependent question carried in the §9 open decisions rather than decided here. The binary `PodScrubOutcome` is not widened; any additional disambiguator, if the in-place mechanism is adopted, rides existing durable claim state rather than a third outcome enum value.
- **Remove the in-guest `VMRestarter` seam.** The in-guest step-7 machinery (the `VMRestarter` interface, `Config.MicrovmRestart`/`Restarter`, `ErrNoRestarter`, `StepGuestRestart`, and the step-7 block, `scrub.go:95-101,:175,:218-220,:236-237,:275-280`) is removed, because the restart no longer happens in-guest. `scrub.Run` becomes uniform (steps 0-6) across all profiles. No backward-compatibility shim (the platform is pre-deployment; `code-best-practices.md` forbids dual modes).
- **The gateway drives the restart through the control plane, reusing its recycle-boundary ownership.** On a binary `SUCCEEDED` pre-restart report for a `vm-restart` pool, the gateway (which owns the recycle boundary, the missing-report timeout, and the Pod annotation writes) invokes the control-plane restart and holds the pod out of cross-tenant reuse until the restart completes and re-verifies clean. The specific trigger surface (a gateway-to-executor RPC versus a gateway-stamped Pod annotation consumed by the WarmPoolController) and the way the completed-and-clean result reaches the gateway (a same-pod post-restart `ReportPodScrub` under an in-place restart, or the sizing reconciler's fresh replacement under a retire-and-reprovision) are carried as open decisions (§9).
- **A restart-timeout window replaces the generic missing-report timeout during the restart.** On the pre-restart success report the gateway cancels the `cleanupTimeoutSeconds`-based missing-report timer and arms a longer guest-restart window sized to the 3-8s reboot plus the fresh-guest re-verify. On expiry with no confirmed clean completion the pod is retired fail-closed, reusing the existing missing-report retire reason rather than minting a second one. This timeout is defined in §4.7 alongside the generic missing-report timeout, so the `vm-restart` exception is stated there (S-2).
- **Fail-closed is preserved and never weakened.** A failed or timed-out control-plane restart, or a failed re-verification, retires the pod (a re-verification reports `FAILED`, or the restart-timeout window expires with no confirmed clean completion). A pod is never cross-tenant-reused without a completed guest restart, matching the current posture where a `vm-restart` pool retires fail-closed.
- **The concrete restart mechanism is deferred.** No node-local privileged Lenny component exists today (no DaemonSet, no containerd-shim or Kata socket client in `pkg/` or `charts/`). Whether the control plane restarts the guest in place through a new privileged node executor, or retires the pod and provisions a fresh warm replacement through the existing WarmPoolController lifecycle (`lifecycle.go:55-59`, which already deletes and recreates pods), depends on the in-place-restart feasibility open decision (§9). A privileged node executor and its §13 threat model are not staged in this proposal; if a later decision adopts one, both are authored against the then-pinned host-access surface.
- **Proposal 0031 is a hard prerequisite; this is the step-7 follow-on it spun out.** 0031 lands the `RecycleScrub` sub-message, the `pkg/adapter/podscrub.go` driver, and the `scrub.Run`/`ReportPodScrub` production callers that C-2 extends. This proposal is the §5.2 step-7 `vm-restart` follow-on that 0031's Non-goals and 0035 reference, sequenced after 0031, resolving step 7 in the control-plane direction rather than by supplying an in-guest concrete `VMRestarter`.
- **The change is spec-first.** The §5.2:475 reattribution and the §4.7 note land and verify before the C-2 code, because the control-plane-brokered design contradicts the current in-guest wording (`spec-driven-development.md`). `kind` is `new` because the dominant change is a step-7 restart subsystem the implementation lacks, consistent with how 0031 and 0035 classify their step-7 and recycle work.

## 3. The two problems and the control-plane flow

**The survivor problem forces two actors.** The pre-restart actor (the in-guest adapter that runs steps 0-6) cannot be the post-restart reporter, because the restart destroys it. The control-plane restart sits between them: the gateway receives the pre-restart `SUCCEEDED` report and triggers the restart, and the fresh guest that boots afterward re-verifies step 6. Under an in-place same-pod re-verify the fresh in-guest adapter reports the terminal binary outcome, and the gateway must distinguish that terminal report from a retried pre-restart `SUCCEEDED` on the same pod. An in-memory recycle-boundary phase alone cannot do so safely: `ReportPodScrub` delivery is at-least-once (`spec/04:670`; a duplicate report is an expected, handled event, `recycleboundary.go:412`), so a pre-restart `SUCCEEDED` retried after the gateway flips to the restart-pending phase is indistinguishable from the terminal report and would reserve the pod with no completed guest restart; and the recycle-boundary phase is replica-local in-memory state (`recycleboundary.go:92-94`) that the reboot destroys, so the fresh adapter's report may land on a replica holding no phase for the pod. The in-place mechanism therefore requires a self-identifying terminal signal (a scrub-attempt generation, or a durable restart-started stamp on the gateway-owned `SandboxClaim.status` that any replica reads) rather than a replica-local phase; this is a §9 open decision. Under a retire-and-reprovision there is no second same-pod report to disambiguate: the pre-restart-clean pod is retired and the sizing reconciler provisions a fresh warm replacement.

**The driver problem forces the control plane.** A zero-RBAC agent pod with default-deny egress and host-sharing-forbidden (`spec/13:16-23`) cannot reach a host Kata lifecycle API. Only the control plane holds a path to the host-side guest lifecycle. The trigger stays off the Sandbox CRD (the gateway holds no Sandbox write grant), and no new `ActionRestartGuest` lifecycle primitive is introduced for the gateway-direct trigger path; the WarmPoolController-driven alternative that would add one is carried as an open decision (§9).

**The wire surface stays binary.** The gateway resolves the pool's scrub profile into `PoolMatch.MicrovmScrubMode` at bind (`resolve.go:264`) and already branches on it elsewhere (`sessionserver.go:2524`). With `scrub.Run` uniform across profiles (C-2), an in-guest `SUCCEEDED` on a `vm-restart` pool unambiguously means "steps 0-6 clean," and the gateway routes the pre-restart report to the restart from its own held profile. No adapter-side re-derivation of the profile and no `RESTART_PENDING` enum value is required for the pre-restart routing; the post-restart terminal disambiguation is the §9 mechanism-dependent question above.

## 4. Proposed changes

### S-1. Reword §5.2 step 7 to a control-plane-brokered restart with a fresh-guest re-verify

**Target:** `spec/05_runtime-registry-and-pool-model.md`, §5.2, the `vm-restart` step-7 paragraph (line 475).

**Anchor:** the numbered item beginning "7. **Guest VM restart:** The adapter requests a full guest VM restart via the Kata runtime's VM lifecycle API." Replace that item's body. Leave the profile-selection paragraph at `spec/05:477` (`standard`/`vm-restart`/`in-place`) and the "Scrub model" paragraph at `spec/05:451` unchanged.

```markdown
7. **Guest VM restart:** The guest VM restart is effected by the Lenny control
   plane rather than the in-guest adapter. A zero-RBAC agent pod with
   default-deny egress ([Section 13.2](13_security-model.md#132-network-isolation))
   and host-sharing forbidden
   ([Section 13.1](13_security-model.md#131-pod-security)) cannot reach the
   host-side Kata VM lifecycle API, and a full guest restart destroys the adapter
   process that would drive it, so the in-guest adapter neither performs nor
   requests the restart. The guest kernel is shut down and a fresh guest boots
   from the original VM image, eliminating all guest-kernel-level residual state
   (DNS cache, TCP `TIME_WAIT`, page cache, inotify registrations, kernel module
   state). The restart adds latency (typically 3-8 seconds, consistent with Kata
   cold-start times documented in
   [Section 6.2](06_warm-pod-model.md#62-pod-state-machine)). The fresh guest's
   clean state is confirmed before the pod returns to cross-tenant reuse. A
   restart that does not complete, a clean-state confirmation that does not
   pass, or a bounded control-plane restart window that expires with no
   confirmed clean result retires the pod; the pod is never returned to
   cross-tenant reuse without a completed guest restart and a confirmed clean
   state.
```

**Rationale:** `spec/05:475` attributes the restart to the in-guest adapter calling the Kata VM lifecycle API directly, which is incompatible with the zero-RBAC/host-sharing-forbidden agent-pod posture and with the survivor problem (the restart destroys the in-guest adapter). The reword removes the false attribution and states the control-plane-brokered flow and the required outcome (a fresh guest, re-verified clean, before any cross-tenant reuse; fail-closed otherwise), keeping the outcome binary. It deliberately states no concrete restart mechanism, because the in-place-restart feasibility is a NEEDS-OPERATOR open decision (§9): if the only available Kata primitive recreates the pod object, the restart is a retire-and-reprovision through the existing warm-pool lifecycle (`lifecycle.go:88-93`) rather than an in-place restart. To hold under either mechanism the text names no same-pod post-restart `ReportPodScrub`, no gateway recycle-boundary phase disambiguation, and no on-pod restart-hold projection, all of which are in-place-specific: the same-pod re-verify does not occur under a retire-and-reprovision (a fresh warm pod meets no recycle boundary and emits no `ReportPodScrub`; it is marked idle by its gRPC health check, `spec/04:882-883`), and its disambiguation and projection carry the durable-state requirements deferred to §9. The text does not assert workspace-mount preservation, which would be inaccurate on the cross-tenant path where scrub step 2 (`rm -rf $WORKSPACE_DIR`, `spec/05:465`) already wipes the workspace.

### S-2. Document the §4.7 `ReportPodScrub` consequence for a `vm-restart` pool

**Target:** `spec/04_system-components.md`, §4.7 (the `ReportPodScrub` row of the Adapter → Gateway RPC table, line 670). **Anchor and change (§4.7, line 670, success edge):** amend the row's "On success:" sentence so that on a `vm-restart` pool the pre-restart success does not advance the pod toward reuse. Insert after the "On success:" sentence and before the closing "A missing report is bounded by a gateway-side timeout" sentence:

```markdown
On a `vm-restart` pool ([Section 5.2](05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes)),
a successful pre-restart report does not advance the claim toward reuse: it
neither patches the claim to `reserved` on a non-preConnect pool nor begins the
SDK re-warm on a preConnect pool. The pod enters the control-plane guest-restart

```

**Anchor and change (§4.7, line 670, missing-report sentence):** amend the closing "A missing report is bounded by a gateway-side timeout (`cleanupTimeoutSeconds` plus a grace period), after which the pod is retired." sentence to add the `vm-restart` exception:

```markdown
On a `vm-restart` pool a successful pre-restart report cancels this
`cleanupTimeoutSeconds`-based timer and arms a longer control-plane
guest-restart window sized to the guest reboot plus the fresh-guest re-verify;
on expiry of that window with no confirmed clean completion the pod is retired
```

**Rationale:** §4.7 documents `ReportPodScrub` as a binary outcome (`spec/04:670`), and the `vm-restart` consequence needs a home there without widening the outcome. Both amendments target §4.7 because both the success edge (`On success: ... patches the claim directly to reserved`) and the missing-report timeout (`A missing report is bounded by a gateway-side timeout`) are defined in that one row; §4.6.1's single reference to the timeout delegates to §4.7 (`spec/04:392`), so §4.6.1 has no timeout description to amend. The success-edge amendment closes a fail-open: under the unamended projection a successful pre-restart report patches a non-preConnect pool's claim directly to `reserved` (`spec/04:670`) or begins a preConnect pool's SDK re-warm and arms `sdkConnectTimeoutSeconds` (`spec/04:393,:670`), returning the pod toward reuse before any guest restart runs, which contradicts the fail-closed invariant (§2). The projection for the guest-restart interval is mechanism-dependent and deferred with the §5.2 mechanism (§5): under a retire-and-reprovision the pre-restart-clean pod is retired and the sizing reconciler provisions a fresh replacement through the existing draining-to-terminated projection (no new §6.2 state); under an in-place same-pod restart the interval needs a non-reusable restart-hold projection (a §4.6.1:392-394 / §6.2:616-617 edit), which is staged with that mechanism. The gateway holds no Sandbox write grant, so the trigger is not a direct Sandbox write; the specific trigger surface (RPC versus annotation) is left to the §9 open decision, and the staged text commits only to control-plane coordination and the fail-closed timer behavior, which hold under either surface.

- Delete the `VMRestarter` interface, `Config.MicrovmRestart`/`Restarter`, the `ErrNoRestarter` guard, `StepGuestRestart`, and the `if cfg.MicrovmRestart { ... }` block from `scrub.Run`, so `Run` always executes steps 0-6. In the control-plane design the in-guest adapter never restarts, so the seam is dead code. `PodScrubOutcome` stays binary because the gateway routes the pre-restart report from the profile it already holds (`resolve.go:106,:264`); the terminal post-restart disambiguation rides durable gateway-owned claim state under an in-place restart, or does not arise under a retire-and-reprovision, so no third outcome enum value is needed. The change is gated because it depends on 0031's landed surfaces, on the reviewer accepting the redesign, and on the §9 mechanism (which fixes the terminal-disambiguation and projection details); absent adoption, the seam and the fail-closed posture stay.

## 5. Non-goals

- **No agent-pod node or host carve-out.** Agent pods (including `lenny-agents-kata`) keep zero RBAC, default-deny egress limited to the gateway port and DNS, and host-sharing-forbidden (`spec/13:16-23`). This proposal adds no hostPath mount, no host socket, and no egress allowance to any agent pod. Any host access lives solely in the control plane. This is the design's central invariant and the reason the control-plane direction is chosen over the two in-guest models.
- **No change to the `standard` or `in-place` scrub profiles.** `standard` runs steps 0-6 and reuses; `in-place` runs steps 0-6 inside the continuing guest with the `acknowledgeMicrovmResidualState` acknowledgment (`spec/05:477`). Only `vm-restart` gains the control-plane restart. Auto-degrading `vm-restart` to `in-place` when the restart is unavailable is rejected as a fail-open isolation regression; an unavailable restart fails closed (the pod retires).
- **No change to cross-tenant reuse semantics, tenant pinning, the T4 prohibition (`spec/05:445-449`), or the pool-controller validation that requires `vm-restart` or `in-place` on an `allowCrossTenantReuse` pool (`spec/05:477`).** The restart mechanism changes; the eligibility and isolation rules do not.
- **No concurrent-session (`maxConcurrentSessions > 1`) path.** Concurrent pools reject `allowCrossTenantReuse` (`poolstore.go:536-539`), so `vm-restart` never applies to them; that boundary is proposal 0035's concern. The control-plane restart is wired for the sequential-reuse microvm path only.
- **No `RESTART_PENDING` wire disposition (dropped alternative).** An earlier draft widened the binary `PodScrubOutcome` (`schemas/lenny-adapter.proto:428-439`) with a third `RESTART_PENDING` value so the in-guest adapter could signal "steps 0-6 clean, restart required." Dropped: the gateway already holds the pool's `MicrovmScrubMode` at the recycle boundary (`resolve.go:106,:264`), so it routes the pre-restart report to the restart from held pool config without a third outcome value. Disambiguating a terminal post-restart re-verify from a retried pre-restart report, if the in-place mechanism is adopted, rides a durable gateway-owned claim marker (§3, §9) rather than a third `PodScrubOutcome` enum value. The widening would have forced a §4.7/§5.2 binary-to-three-valued contract change and a tier-3 wire test to restate state the gateway already computes for the pre-restart routing, against the minimal-protocol-surface principle. The outcome stays binary; the gateway routes the pre-restart report on held state (see C-2).
- **No new §6.2 `restarting` pod state committed now (mechanism-dependent).** An earlier draft added a `restarting` sub-state of `recycling` to §6.2 unconditionally. Whether the guest-restart interval needs a new §6.2 projection depends on the §9 mechanism. Under a retire-and-reprovision the pre-restart-clean pod is retired and the existing draining-to-terminated projection provisions a fresh replacement (`lifecycle.go:88-93`), so no new §6.2 state is needed. Under an in-place same-pod restart the interval falls after the pre-restart `ReportPodScrub`, past the `recycling`/`claimed` scrub window that ends at that report (`spec/04:392,:616`), so it is not a longer opaque interval within that same projection and needs a non-reusable restart-hold projection (a §6.2:616-617 / §4.6.1:392-394 edit) staged with that mechanism. Either way, S-2's §4.7 success-edge amendment keeps a successfully-reported pre-restart scrub from advancing the pod to `reserved` or into the preConnect SDK re-warm. Extending the timeout's duration is an internal recycle-boundary concern stated in S-2's §4.7 note. A distinct `guest_restart_timeout` retire reason was dropped in favor of the existing missing-report retirement reason, absent an affirmative audit-trail justification.
- **No control-plane privileged node executor and no §13 threat model (deferred; dropped from this proposal's staged changes).** An earlier draft added a privileged node-executor DaemonSet in `lenny-system` (a wholly new package, binary, chart, and RBAC) plus a §13 threat model authorizing its host access. Dropped from the staged changes on two grounds. First, an existing surface may already cover the concern: the WarmPoolController lifecycle already retires a warm pod and provisions a fresh replacement through `ActionDeletePod`/`ActionCreatePod` (`lifecycle.go:55-59,:84-96`), and a fresh Kata pod is a fresh guest VM with zero guest-kernel residual state, which is exactly what §5.2 step 7 requires (`spec/05:475`). §5.2 mandates eliminating residual state, not preserving the pod object, node slot, or workspace mount; that preservation is an unconfirmed premise (§9 open decisions), and scrub step 2 already wipes the workspace (`spec/05:465`), so mount preservation buys nothing on the cross-tenant path. Second, the executor's host-access surface is itself a NEEDS-OPERATOR open decision, so a §13 threat model over it cannot be authored soundly now, and the control it would need to be authorized against is the §13.1 privileged/capabilities/hostPath pod-security baseline rather than the §13.1 four-flag host-sharing rule (`spec/13:16-23`, which covers only `shareProcessNamespace`/`hostPID`/`hostNetwork`/`hostIPC`). If a later decision (§9) adopts an in-place executor, the node component and its §13.1-targeted threat model are staged then, against the pinned host-access surface.
- **No WarmPoolController-driven trigger with an `ActionRestartGuest` primitive and a Sandbox CRD trigger field (dropped alternative; carried as an open decision).** An earlier draft staged, as an alternative to the gateway-direct trigger, a gateway-stamped `lenny.dev/guest-restart-request` Pod annotation consumed by the WarmPoolController, plus a new `ActionRestartGuest` planner primitive (`lifecycle.go:53-60` has no restart action today) and a new Sandbox trigger field with CRD regeneration. Dropped as staged surface: staging two mutually exclusive trigger implementations in one proposal is the parallel-surface duplication the single-canonical-implementation principle rejects. The WPC-driven path is carried as the considered alternative in the §9 trigger-path open decision; if the reviewer selects it, its concrete edits are authored against that direction at that point.

## 6. Testing

The change removes an in-guest seam and rewires a fail-closed recycle path, introduces recycle-boundary ordering and atomicity, and reaches a Kata-host behavior Kind cannot reproduce, so per `test-coverage.md` it reaches tier 1, tier 2, tier 7a, and tier 6 (NEEDS-OPERATOR). Each test pins a behavior this change introduces and asserts its non-happy path.

- **tier-1 unit (`scrub.Run` uniform across profiles, boundary):** In `pkg/adapter/scrub/scrub_test.go`, assert `scrub.Run` executes steps 0-6 and never a step 7 for every profile input, that the deleted `VMRestarter`/`MicrovmRestart`/`ErrNoRestarter` surface is gone, and that a `vm-restart` config runs the identical steps 0-6 as `standard`. The non-happy path is a scrub whose step-6 verify fails, which reports `FAILED`. `// spec: 5.2 (uniform scrub steps 0-6), 5.2:475 (restart no longer in-guest)`.
- **tier-1 unit (adapter driver reports the binary outcome uniformly, boundary):** In `pkg/adapter/podscrub_test.go`, assert the driver reports `POD_SCRUB_OUTCOME_SUCCEEDED` on a clean steps-0-6 result and `POD_SCRUB_OUTCOME_FAILED` on a failed result, with no profile-specific branch and no third outcome value. The non-happy path is the failed result on a `vm-restart` pool reporting `FAILED` rather than a restart-pending signal. `// spec: 5.2 (binary whole-pod scrub outcome)`.
- **tier-2 component (gateway branches a pre-restart `SUCCEEDED` report to the restart on a `vm-restart` pool, spec-named-failure):** In the gateway recycle-boundary consumer tests, assert a pre-restart `SUCCEEDED` `ReportPodScrub` for a `vm-restart` pool invokes the control-plane restart, cancels the missing-report timer, arms the guest-restart window, and does not advance the pod to `reserved` or into the preConnect SDK re-warm (the S-2 fail-open guard); a `SUCCEEDED` on a `standard` pool reserves directly with no restart; and a `FAILED` retires the pod. The non-happy path is the `FAILED` report and the pre-restart-success that must not reach reuse. The mechanism-resolved terminal disposition (reserve on a confirmed clean re-verify) and its disambiguation are tested with the §9 mechanism. `// diagnosis:` a failure means a `vm-restart` pod was reused without a completed guest restart. `// spec: 4.7 (ReportPodScrub binary outcome), 5.2:475 (control-plane restart)`.
- **tier-2 component (restart window replaces the missing-report timeout, spec-named-failure):** In the recycle-boundary tests, assert that on the pre-restart success the `cleanupTimeoutSeconds`-based timer is cancelled and the guest-restart window armed, and that window expiry with no confirmed clean completion retires the pod fail-closed using the existing missing-report retire reason. The non-happy path is the expired window retiring the pod. `// diagnosis:` a failure means a slow-but-successful restart was retired before its re-verify, or a lost restart left a pod stuck. `// spec: 4.7 (guest-restart window), 5.2:475 (fail-closed on restart failure)`.
- **tier-7a load and ordering (recycle boundary under `-race`, concurrent):** Run the tier-2 recycle-boundary cases under `-race`, and add a stress case asserting the control-plane restart is invoked exactly once per boundary and the terminal-event race between window expiry and a confirmed clean completion resolves to exactly one disposition (reserve or retire, never both). If the §9 mechanism is an in-place same-pod re-verify, add the stale-report race case: a duplicated or retried pre-restart `SUCCEEDED` arriving after the restart is triggered must not be consumed as the terminal re-verify (it must not reserve the pod). The non-happy path is the expiry-versus-completion race and the stale-pre-restart-report race. `// diagnosis:` a failure means the timer swap introduced a double-invoke or a lost-update race on the recycle boundary, or a retried pre-restart report reused a pod with no completed restart. `// spec: 5.2 (whole-pod scrub trigger atomicity)`.
- **tier-6 e2e (Kata-node guest restart, NEEDS-OPERATOR):** On an operator-provisioned Kata RuntimeClass, scaffold the control-plane restart path and assert the fail-closed posture end to end: a `vm-restart` pool at occupancy zero either completes a guest restart with a passing post-restart re-verify and reuses the pod, or retires fail-closed when the restart does not complete. The behavioral guest-restart battery is deferred with the concrete mechanism (§9); the scaffold and fail-closed assertions run now, and the tiers that run locally run regardless. The non-happy path is the incomplete restart retiring the pod. `// diagnosis:` a failure means a Kata guest was reused across tenants without a completed restart. `// spec: 5.2:475 (guest VM restart), 5.2:445-449 (cross-tenant reuse boundary)`.

## 8. Resolved in adversarial review

- **The `RESTART_PENDING` proto widening was dropped; the outcome stays binary.** An earlier draft added a third `PodScrubOutcome` enum value and a §4.7 binary-to-three-valued contract change so the in-guest adapter could signal "restart required." The gateway already holds `MicrovmScrubMode` at the recycle boundary (`resolve.go:106,:264`), so it routes the pre-restart report to the restart from held pool config with no wire value; the widening restated derivable routing state against the minimal-protocol-surface principle. The terminal post-restart disambiguation, if the in-place mechanism is adopted, rides a durable claim marker (§3, §9) rather than a third outcome enum. Dropped the enum value, the §4.7 contract change, the tier-3 wire test, and the representation open question; the gateway routes the pre-restart report in C-2.
- **The §6.2 `restarting` sub-state and the `guest_restart_timeout` reason were dropped as unconditional staged edits.** Whether the guest-restart interval needs a new §6.2 projection is mechanism-dependent (§5, §9): a retire-and-reprovision reuses the existing draining-to-terminated projection (`lifecycle.go:88-93`), while an in-place same-pod restart needs a non-reusable restart-hold projection (a §6.2:616-617 / §4.6.1:392-394 edit) staged with that mechanism, because the guest-restart interval falls after the pre-restart `ReportPodScrub` and past the `recycling`/`claimed` scrub window (`spec/04:392,:616`). The timer swap and fail-closed expiry fold into S-2's §4.7 note, where the missing-report timeout is defined (`spec/04:670`), reusing the existing missing-report retire reason. A distinct `guest_restart_timeout` reason was dropped absent an audit-trail justification.
- **The privileged node-executor DaemonSet and its §13 threat model were dropped from the staged changes.** The WarmPoolController lifecycle already retires and reprovisions pods (`lifecycle.go:55-59,:84-96`), and a fresh Kata pod is a fresh guest VM, which satisfies §5.2 step 7's residual-state elimination; the executor's host-access surface is a NEEDS-OPERATOR open decision, and the control it would be authorized against is the §13.1 privileged/capabilities/hostPath pod-security baseline rather than the §13.1 four-flag host-sharing rule. Both are deferred to the §9 mechanism decision rather than staged now.
- **The WarmPoolController-driven trigger (annotation plus `ActionRestartGuest` plus a Sandbox trigger field) was dropped as staged surface.** Staging it alongside the gateway-direct trigger stages two mutually exclusive implementations of one concern; it is carried as the considered alternative in the §9 trigger-path open decision.

It resolves step 7 in the control-plane direction rather than superseding a separate in-guest proposal; the two rejected in-guest models are recorded as considered-and-rejected alternatives in §2 and §5.

## 9. Open decisions for review

- **Trigger path.** Does the gateway call the control plane directly (reusing its recycle-boundary ownership and keeping the Sandbox CRD untouched), or does the restart flow through the WarmPoolController via a gateway-stamped `lenny.dev/guest-restart-request` Pod annotation plus a new `ActionRestartGuest` and a Sandbox trigger field (the drain-request precedent, `spec/04:398,:612`)? The gateway-direct path is smaller and adds no CRD surface; the WPC path aligns the restart with the existing pod-lifecycle owner but adds a lifecycle primitive, a CRD field, and CRD regeneration. C-2 and S-2 stage the gateway-direct path; the WPC path is the considered alternative.
- **In-place guest-restart feasibility (NEEDS-OPERATOR).** Confirm whether a Kata guest microvm can be restarted in place while preserving the pod object, the node slot, and the workspace mount. If the only available primitive recreates the pod object, the restart is a retire-and-reprovision through the existing WarmPoolController lifecycle (`lifecycle.go:55-59`), which needs no new privileged node component, and the recycle-versus-retire tradeoff changes. This is a tier-6 Kata-host behavior Kind cannot reproduce, and it gates whether the C-4-class node executor and its §13 threat model are ever staged.
- **In-place terminal disambiguation, projection, and durable claim state (conditional on in-place).** If an in-place same-pod re-verify is adopted, the mechanism carries edits this proposal does not stage: (a) a self-identifying terminal signal so any gateway replica distinguishes the fresh adapter's post-restart `ReportPodScrub` from a retried pre-restart report, because the recycle-boundary phase is replica-local in-memory state the reboot destroys (`recycleboundary.go:92-94`) and report delivery is at-least-once (`recycleboundary.go:412`); the candidate is a durable restart-attempt stamp on the gateway-owned `SandboxClaim.status` (a schemas/CRD field plus a §4.6.3 ownership entry, analogous to `rewarmStartedAt`); and (b) a non-reusable restart-hold projection for the guest-restart interval (a §6.2:616-617 / §4.6.1:392-394 edit), since that interval falls after the pre-restart report and past the `recycling`/`claimed` scrub window. A retire-and-reprovision needs neither, because there is no second same-pod report and the existing draining-to-terminated projection applies. These edits are authored with the mechanism once §9 resolves.
- **Node-executor mechanism (NEEDS-OPERATOR).** If an in-place restart is adopted, pin the concrete Kata VM lifecycle endpoint the executor drives (containerd-shim-v2 management socket, kata-runtime sandbox lifecycle, or a CRI sandbox recreate) and its host-access surface. This determines the node component's host mounts and the §13.1-targeted threat model, and is exercisable only on an operator-provisioned Kata RuntimeClass (tier 6).
- **Restart-timeout window value.** The fixed delay (or per-pool override) for the guest-restart window that replaces the missing-report timeout during the restart, sized to the 3-8s reboot plus the fresh-guest re-verify and reconnect, so a slow-but-successful restart is not retired before its confirmed clean completion arrives.
- **§13 threat-model acceptance (conditional).** If the in-place mechanism with a privileged node executor is adopted, confirm the reviewer accepts a single Lenny-operated privileged node workload as the one exception to the §13.1 pod-security baseline, with its residual risk (a compromised executor can restart or inspect guest VMs on its node) mitigated by a narrow RPC surface and a control-plane-only caller allowlist. If the retire-and-reprovision mechanism is adopted instead, no such exception is needed.
