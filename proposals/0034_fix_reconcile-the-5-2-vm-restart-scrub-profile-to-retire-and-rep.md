Converged after 13 adversarial review rounds (20 findings fixed); the §9 open decision is resolved by the reviewer (Branch A — confirm the foreclosure of the in-place option; commit retire-and-reprovision as the single canonical mechanism and delete the `VMRestarter` seam).
- **Date:** 2026-07-02.
- **Scope:** A spec-to-code reconciliation of the §5.2 `vm-restart` scrub profile plus the dead code that encodes its impossible flow. §5.2 step 7 mandates an in-guest adapter that "requests a full guest VM restart via the Kata runtime's VM lifecycle API" (`spec/05_runtime-registry-and-pool-model.md`, step 7), and the surrounding recycle passages frame the recycled `vm-restart` pod as reused in place. ## 1. Problem

§5.2 step 7 (the `vm-restart` scrub profile) mandates that "the adapter requests a full guest VM restart via the Kata runtime's VM lifecycle API. The guest kernel is shut down and a fresh guest boots from the original VM image" (`spec/05_runtime-registry-and-pool-model.md`, the Kata/microvm scrub variant, step 7). The surrounding passages frame the recycled `vm-restart` pod as reused in place: on a successful scrub "the pod is held for its tenant through the claim's `reserved` state and serves the next session" (`spec/05`, Recycle lifecycle), the adapter "keeps the pod process alive across the recycle boundary" (`spec/05` Lenny scrub procedure; `spec/04_system-components.md:663`), the reuse is amortized across `maxSessionsPerPod` (`spec/05`, Pod retirement policy), and a `preConnect` pool re-warms the SDK on the `claimed → sdk_connecting` edge before the claim enters `reserved` (`spec/05`, Recycle lifecycle; `spec/06_warm-pod-model.md:76,:149`). Both the in-guest attribution and the in-place-reuse framing are unimplementable.

The in-guest attribution violates the agent-pod isolation model. An agent pod holds zero RBAC with default-deny egress ([Section 13.2](spec/13)) and host-sharing forbidden ([Section 13.1](spec/13)), so an in-guest adapter cannot reach a host-side Kata VM lifecycle socket, and a full guest restart destroys the adapter process that would drive and report it (the survivor problem: the process issuing the restart is the process the restart kills). The repository's own superseded 0034 designs (git `4e3338d3`, a control-plane broker; git `a49bba30`, an in-guest `VMRestarter`) already reached this conclusion. Separately, no in-place guest-restart primitive that preserves the pod-sandbox across a guest reboot exists at any layer of the Kata/Firecracker/virtcontainers stack; the guest VM lifecycle is coupled 1:1 to the pod-sandbox lifecycle. Because a fresh guest necessarily means a fresh pod, pod-level in-place reuse across a guest restart is unachievable.

The achievable mechanism that satisfies step 7's required outcome (a fresh guest with zero guest-kernel residual state before any cross-tenant reuse, fail-closed otherwise) is retire-and-reprovision: retire the pod at the recycle boundary and let the gateway provision a fresh replacement pod, which is a fresh guest VM, from the warm pool. This mechanism carries no Kata dependency and runs on the `runc` RuntimeClass kind provides, so the finding is no longer operator-gated.

In code, the seam that encodes the impossible flow has no concrete implementer. `scrub.VMRestarter` (`pkg/adapter/scrub/scrub.go:99-101`), `Config.MicrovmRestart` and `Config.Restarter` (`:153-159`), `ErrNoRestarter` (`:218-220`, `:236-237`), `StepGuestRestart` (`:175`), and the step-7 block in `Run` (`:277-280`) exist only against a nil `Server.VMRestarter` field (`pkg/adapter/server.go:170-175`; the only `RestartGuest` implementers are test fakes). `scrubConfig` gates `MicrovmRestart=true` on `scrubProfile == "vm-restart"` alone (`pkg/adapter/podscrub.go:119-122`), and `startPodScrub` withholds `ReportPodScrub` on `ErrNoRestarter` (`:62-68`) so the gateway missing-report timeout retires the pod. That retire is emergent rather than deliberate: it runs through the coordinator's expire-missing-report path with reason `scrub_report_timeout`, which incurs the full `cleanupTimeoutSeconds+grace` window, audits as a scrub-report timeout rather than a vm-restart replacement, and is not counted on `lenny_pod_retirement_total` (`pkg/sandbox/podscrub/podscrub.go:201-208`). `podscrub.Decide` has no vm-restart branch and no scrub-profile input (`:254-358`), so a successful report on a vm-restart pool would reuse the pod (`:338-357`, `ReasonReuse`), a fail-open isolation regression the withhold exists to prevent.

This is the OPEN/DEFERRED finding **F-5.2.32** (`BUILD-GAPS.md:4062-4072`, filed by proposal 0031, tagged NEEDS-OPERATOR: Kata-enabled host RuntimeClass), rather than the CLOSED F-5.2.15 (`BUILD-GAPS.md:3885`). Reconciling §5.2 to retire-and-reprovision resolves F-5.2.32 and clears its NEEDS-OPERATOR gating, because the mechanism is fully kind-testable.

## 2. Decisions

- **Decide the mechanism: retire-and-reprovision.** §5.2 step 7's required outcome is a fresh guest with zero guest-kernel residual state before any cross-tenant reuse. The only achievable way to produce a fresh guest is a fresh pod, provisioned by the existing WarmPoolController lifecycle (delete-pod, then create-pod). This proposal commits to that mechanism as the single canonical implementation and forecloses the in-place option that the prior 0034 designs left deferred, on the strength of the multi-source impossibility research and the survivor/driver problem the repository already documents.
- **Do not rest on a mount-preservation premise.** §5.2 does not mandate preserving the pod object, node slot, containers, or workspace mounts across step 7; step 2 already wipes the workspace. The reconciliation targets the in-guest attribution (step 7) and the pod-level in-place-reuse framing (the `spec/05` Recycle-lifecycle, keep-pod-alive, and `maxSessionsPerPod` passages; `spec/04:663`; `spec/06:76,:149`), rather than a preservation guarantee the spec never made.
- **Make the cross-tenant retire an explicit, deliberate gateway disposition rather than an emergent missing-report timeout.** Removing the `VMRestarter` seam makes the adapter report a binary SUCCEEDED for a clean vm-restart scrub; without an explicit retire branch, `podscrub.Decide` would reuse the pod (fail-open). The gateway already holds the pool's scrub profile at the recycle boundary (it resolves the recycle policy from its own runtime store), so it branches to retire-and-reprovision on the profile it already knows. This retires immediately (no `cleanupTimeout+grace` wait) and audits deliberately, replacing the withhold-and-timeout stopgap.
- **Keep the `ReportPodScrub` outcome binary.** No `RESTART_PENDING` or third `PodScrubOutcome` value is added; the gateway routes on the profile it already holds. This honors the minimal-protocol-surface principle.
- **Add a distinct, non-counting `RetireReason` for the vm-restart reprovision.** The §16.1 `lenny_pod_retirement_total{reason}` vocabulary is frozen to the three limit triggers. A routine per-recycle-boundary reprovision is not a limit trigger, so the new reason does not count on the retirement counter (`CountsOnRetirementTotal` returns false), exactly like the existing `ReasonHostUnschedulable` and `ReasonScrubReportTimeout`. This needs no §16 spec change and does not widen the frozen label set; the reason is recorded in the audit trail only.
- **Reuse the existing draining → terminated pod-phase projection.** Retire-and-reprovision drives `NextPhase = Draining` through the disposition path the retirement-limit branches already use; the WarmPoolController provisions the fresh replacement. No new §6.2 pod state is introduced.
- **Remove the seam rather than leave it as dead code behind a nil field.** Because in-place restart is foreclosed, the seam has no future in-guest implementer; keeping it contradicts the reconciled spec and the single-canonical-implementation principle. No backward-compatibility shim is retained, because the platform is pre-deployment.
- **Spec-first.** The §5.2/§6.2 reconciliation lands and verifies before the code, because the retire-and-reprovision wording contradicts the current in-guest/in-place text. Classified `fix` because the dominant action reconciles existing spec text and core-product code and removes dead code, reusing the existing warm-pool retire/reprovision path rather than building a new subsystem.
- **Supersession.** This proposal supersedes both prior 0034 designs (git `4e3338d3`, control-plane broker; git `a49bba30`, in-guest `VMRestarter`), which were built on the premise that in-place restart is an open feasibility question. It resolves that question as foreclosed and collapses the six open decisions those drafts carried.

## 3. The mechanism: why in-place is foreclosed and what retire-and-reprovision provides

A microvm pod's guest VM lifecycle is coupled 1:1 to the pod-sandbox lifecycle across the Kata/Firecracker/virtcontainers stack. A fresh guest kernel therefore requires a fresh pod-sandbox, so there is no primitive that reboots the guest while preserving the pod object, its containers, and its mounts. The in-guest adapter cannot drive such a reboot in any case: it holds zero RBAC with default-deny egress and host-sharing forbidden, so it cannot reach the host-side Kata VM lifecycle socket, and a full guest restart would kill the process issuing and reporting the restart.

Retire-and-reprovision satisfies step 7's required outcome without any of those dependencies. On a `vm-restart` pool the pod runs the whole-pod scrub (steps 0-6), reports its binary outcome, and is then retired at the occupancy-zero recycle boundary; the gateway provisions a fresh replacement pod from the warm pool. A fresh microvm pod is a fresh guest VM, which structurally eliminates every guest-kernel-level residual state vector that the in-guest scrub cannot reach (guest DNS cache, TCP `TIME_WAIT`, page cache, inotify registrations, kernel module state). The property is fail-closed by construction: a pod is never returned to cross-tenant reuse without a fresh guest, and any scrub or reprovision failure retires the pod. The mechanism reuses the WarmPoolController delete-pod/create-pod lifecycle that the retirement-limit branches already drive, so it introduces no new pod-phase state and needs no host access.

## 4. Proposed changes

### S1. Reword §5.2 step 7 (vm-restart) from an in-guest Kata VM-lifecycle restart to retire-and-reprovision from the warm pool

**Target:** `spec/05_runtime-registry-and-pool-model.md`, §5.2, the Kata/microvm scrub variant introduction sentence (`spec/05:473`), the step-7 paragraph (`spec/05:475`), and the profile-selection paragraph that follows it (`spec/05:477`).

**Anchor and change:** First, reword the variant-introduction sentence so step 7 (the fresh-guest reprovision) applies to every `vm-restart` pool rather than only to cross-tenant-reuse pools. The current sentence scopes the variant to cross-tenant reuse: "When `isolationProfile: microvm` and `recycle.allowCrossTenantReuse: true`, the standard Lenny scrub (steps 1-6 above) is insufficient because the guest VM itself persists across sessions … For cross-tenant sequential reuse on microvm pods, the scrub procedure includes an additional step after step 6 (the `vm-restart` scrub profile):". Keep the guest-VM-persistence rationale (the standard scrub cannot reach guest-kernel residual state, which is why cross-tenant reuse on a microvm pod requires more than steps 1-6), but restate the mechanism so the additional step applies uniformly whenever `recycle.scrubProfile: vm-restart` is set, on same-tenant and cross-tenant pools alike (poolstore validation permits `vm-restart` on a same-tenant microvm pool; `pkg/gateway/runtime/poolstore/poolstore.go:580-585`). For example: "When `recycle.scrubProfile: vm-restart` is set (permitted on any `isolationProfile: microvm` pool), the standard Lenny scrub (steps 1-6 above) is insufficient because the guest VM itself persists across sessions … so the scrub procedure includes an additional step after step 6:". This matches the uniform `if in.VMRestart` branch in C3, which carries no cross-tenant conjunction.

Then replace the step-7 body:

```
7. **Guest VM restart:** The adapter requests a full guest VM restart via the Kata runtime's VM lifecycle API. The guest kernel is shut down and a fresh guest boots from the original VM image. This eliminates all guest-kernel-level residual state (DNS cache, TCP `TIME_WAIT`, page cache, inotify registrations, kernel module state). The restart adds latency (typically 3-8 seconds, consistent with Kata cold-start times documented in [Section 6.2](06_warm-pod-model.md#62-pod-state-machine)). The scrub verification (step 6) is re-executed after the guest restarts to confirm a clean state.
```

with a retire-and-reprovision statement (heading renamed from "Guest VM restart" to "Fresh-guest reprovision"):

```
7. **Fresh-guest reprovision:** On a `vm-restart` pool the pod is retired at the occupancy-zero recycle boundary after the whole-pod scrub (steps 0-6) reports, and the gateway provisions a fresh replacement pod from the warm pool. A fresh microvm pod is a fresh guest VM, which structurally eliminates all guest-kernel-level residual state (DNS cache, TCP `TIME_WAIT`, page cache, inotify registrations, kernel module state) that the in-guest scrub cannot reach. The in-guest adapter neither performs nor requests the restart: host sharing is forbidden ([Section 13.1](13_security-model.md)), egress is default-deny ([Section 13.2](13_security-model.md#132-network-isolation)), and a full guest restart would destroy the driving process. A pod is never returned to cross-tenant reuse without a fresh guest; any scrub or reprovision failure retires the pod (fail-closed). The reprovision cost is the warm-pod replacement latency, absorbed by warm-pool inventory rather than added to the recycle hot path.
```

In the profile-selection paragraph, change "`vm-restart` adds the guest restart in step 7" to "`vm-restart` retires the pod and reprovisions a fresh guest at the recycle boundary" (uniform phrasing, so the sentence does not re-scope the retire to cross-tenant reuse), and reframe the "guest restart latency cost" clause as the warm-pod reprovision cost. Leave the `in-place` clause (continuing-guest reuse with acknowledged residual state) unchanged.

**Rationale:** The current text attributes the guest restart to an in-guest adapter calling the Kata VM lifecycle API, which is unimplementable under the zero-RBAC/host-sharing-forbidden agent-pod model and destroyed by the restart it triggers. No in-place guest-restart primitive that preserves the pod-sandbox exists, so a fresh guest means a fresh pod. The reword states the achievable mechanism and step 7's required outcome without asserting the in-guest actor or any pod/mount preservation.

### S2. Reconcile the §5.2 reuse-in-place twins and pool-sizing formula so the vm-restart profile takes the retire path

**Target:** `spec/05_runtime-registry-and-pool-model.md`, §5.2: the Recycle-lifecycle successful-scrub reserved hold and the preConnect SDK re-warm clause of the same successful-scrub sentence, the "keeps the pod process alive" recycle-mechanism sentence, the cross-tenant reuse framing, the `onScrubFailure` interaction, the `maxSessionsPerPod` amortization in the Pod retirement policy, the `maxSessionsPerPod`-required paragraph, and the PoolScalingController `mode_factor` passages (the `session` mode-factor "Formula assumption: … converges toward the configured `recycle.maxSessionsPerPod`" and the "Once converged, `mode_factor` is bounded above by `recycle.maxSessionsPerPod`" caveat).

**Anchor and change:** Qualify each reuse-in-place passage so it scopes to the `standard` (same-tenant) and `in-place` (continuing-guest cross-tenant) profiles, and add the vm-restart carve-out:

1. On the Recycle-lifecycle successful-scrub sentence, which carries two success-path assertions ("the pod is held for its tenant through the claim's `reserved` state and serves the next session; on a preConnect pool the SDK re-warm runs after the scrub reports success and before the claim enters `reserved`, so every pod that reaches `reserved` or `idle` is SDK-warm"), scope both clauses to `standard` and `in-place` pools and add the `vm-restart` carve: a `vm-restart` pool instead retires the pod at the occupancy-zero boundary and the gateway provisions a fresh replacement (step 7 above), so a `vm-restart` preConnect pool projects `claimed → draining` after its scrub report rather than running the SDK re-warm leg or entering `reserved`. This mirrors the §6.2:82 occupancy-projection carve (S3 item 4), the §4.6.1:393 projection carve (S4 item 2), and the §4.6.3:616 `recycling`-enum carve (S4 item 6), which resolve the identical cross-passage contradiction at their sites. A sequential `vm-restart` pool can be preConnect (preConnect requires `maxConcurrentSessions: 1`, `poolstore.go:655`, and `vm-restart` carries no `maxConcurrentSessions` restriction of its own), so this clause genuinely covers `vm-restart` pools.
2. On the "keeps the pod process alive across the recycle boundary" mechanism sentence, note that the keep-alive-and-reuse path applies to `standard` and `in-place`; a `vm-restart` pod keeps the process alive only long enough to run and report the scrub, then retires.
3. On the `maxSessionsPerPod` amortization in the Pod retirement policy, state that `maxSessionsPerPod` remains a required, validated field but does not trigger the retire on any `vm-restart` pool: the C3 `if in.VMRestart` branch precedes the session-count retire branch in `Decide`, so every `vm-restart` pod retires at the occupancy-zero recycle boundary with the non-counting `vm_restart_reprovision` reason regardless of `maxSessionsPerPod`. This holds at the `maxSessionsPerPod: 1` boundary, where a sequential `vm-restart` pod's served-session count read back at the recycle boundary equals `maxSessionsPerPod` (1) when the whole-pod scrub reports: the session-count branch would fire there, but the preceding `vm-restart` branch retires first, so the retire reason and the `lenny_pod_retirement_total` increment do not diverge from a `maxSessionsPerPod >= 2` pool. The field still bounds pool sizing: on a concurrent `vm-restart` pool (`maxConcurrentSessions > 1`) it bounds the number of sessions the pod serves in its single occupancy cycle before the retire (feeding `mode_factor` per item 4).
4. On the PoolScalingController `mode_factor` passages, add: a sequential `vm-restart` pool (`maxConcurrentSessions: 1`) serves exactly one session per pod at the occupancy-zero recycle boundary and then retires, so its steady-state `mode_factor` is `1.0` (equivalently, the observed `lenny_pod_session_reuse_count` p50 is 1) rather than converging toward `recycle.maxSessionsPerPod`. A concurrent `vm-restart` pool (`maxConcurrentSessions > 1`) serves the sessions that overlap in its single occupancy cycle before the retire, so its `mode_factor` is above `1.0` and bounded above by `recycle.maxSessionsPerPod`; the PoolScalingController uses the observed `lenny_pod_session_reuse_count` p50 for it, consistent with the existing variable-workload guidance.
5. On the `maxSessionsPerPod`-required paragraph, note that the field remains required-but-inert for `vm-restart` pools, so the required-but-inert state is a deliberate, documented outcome rather than an unremarked contradiction (the proposal declines to change poolstore/admission validation; see Non-goals).
6. On the `onScrubFailure: warn` behavior paragraph (the `warn` bullet: "the pod is returned to the available pool with a `scrub_warning` annotation … the pod serves the next session" and the "preConnect interaction" clause routing the pod through the `claimed → sdk_connecting` re-warm edge before reaching `reserved`), add a `vm-restart` carve-out: on a `vm-restart` pool a `warn`-policy scrub outcome retires the pod at the occupancy-zero recycle boundary and the gateway provisions a fresh replacement, so the pod is not returned to the available pool, does not serve the next session, and does not traverse the `claimed → sdk_connecting` re-warm edge. The `scrub_warning` annotation and the cumulative `lenny_pod_scrub_failure_count` are still recorded on the retired pod's audit trail. This mirrors how the retire branch precedence in C3 places the `vm-restart` disposition ahead of the reuse and re-warm branches, so a `warn` outcome that has not exhausted `maxScrubFailures` still retires on a `vm-restart` pool.

**Rationale:** These passages assume a recycled pod is held for its tenant, serves the next session, and is amortized across sessions. That model holds for `standard` and `in-place` reuse but not for `vm-restart`, whose pod retires after each session under S1. Leaving them unqualified leaves the spec internally contradictory once step 7 becomes retire-and-reprovision. The `mode_factor` twins carry the identical `maxSessionsPerPod` amortization assumption; qualifying only the recycle-lifecycle sentences while leaving the sizing formula asserting convergence toward `maxSessionsPerPod` would leave §5.2 self-contradictory on the exact amortization axis this change reconciles.

## 5. Non-goals

- **Not changing the `standard` or `in-place` scrub profiles.** `standard` runs steps 0-6 and reuses same-tenant; `in-place` runs steps 0-6 in the continuing guest with the `acknowledgeMicrovmResidualState` acknowledgment and reuses the pod. Only `vm-restart` becomes retire-and-reprovision.
- **Not changing cross-tenant reuse eligibility, tenant pinning, the T4 dedicated-node prohibition, or the poolstore/admission validation** that requires `vm-restart` or `in-place` on an `allowCrossTenantReuse` pool (`poolstore.go:580-583`). The mechanism changes; the eligibility and isolation rules do not. `maxSessionsPerPod` remains a required field on `vm-restart` pools, inert but validated, rather than being relaxed.
- **Not building an in-place guest-restart primitive, a privileged node executor, a DaemonSet, or any Kata VM-lifecycle client.** No agent-pod §13.1 host-sharing, §13.2 egress, or §10.3 RBAC carve-out. Retire-and-reprovision reuses the existing WarmPoolController lifecycle and needs no host access. This foreclosure supersedes both prior 0034 designs (git `4e3338d3`, control-plane broker; git `a49bba30`, in-guest `VMRestarter`).
- **Not widening the binary `PodScrubOutcome`.** No `RESTART_PENDING` or third enum value; the gateway routes on the scrub profile it already holds at the recycle boundary.
- **Not adding a new §6.2 pod-phase state.** Retire-and-reprovision uses the existing draining → terminated projection and the warm-pool replacement path.
- **Not counting the vm-restart reprovision on `lenny_pod_retirement_total`.** The §16.1 reason vocabulary stays frozen to the three limit triggers; the new `ReasonVMRestartReprovision` is non-counting and audit-trail-only, like `ReasonHostUnschedulable` and `ReasonScrubReportTimeout`, so no §16 spec change is needed.
- **Not keeping the withhold-report-and-timeout retire as the shipped behavior.** It is replaced by the explicit gateway retire; the timeout path remains only as the generic backstop for a genuinely missing report on any profile.
- **Not reconciling the concurrent-session (`maxConcurrentSessions > 1`) recycle path (F-5.2.31).** A concurrent pool rejects `allowCrossTenantReuse` (`poolstore.go:536-539`), so no concurrent `vm-restart` pool reaches cross-tenant reuse. A same-tenant concurrent pool may still set `scrubProfile: vm-restart`, because `validateRecyclePolicy` imposes no `maxConcurrentSessions` restriction on `scrubProfile` (`poolstore.go:567-598`), and the uniform C3 `if in.VMRestart` branch retires it at the occupancy-zero boundary like any other `vm-restart` pool. On such a pool a pod serves the sessions that overlap in its single occupancy cycle before the retire (bounded above by `maxSessionsPerPod`), so its `mode_factor` exceeds `1.0`; the S2 `mode_factor` carve scopes the exactly-one-session and `mode_factor = 1.0` claim to sequential (`maxConcurrentSessions == 1`) vm-restart pools for this reason. This proposal does not otherwise reconcile the concurrent recycle path.
