# Problem: Per-state session deadlines and watchdog sweeps depart from the specification and leave a set of rules unstated

## Statement

The per-state session deadlines and the watchdog sweeps that enforce them depart from §6.2, §7.2, §10.1, and §11.3 in code, and the specification leaves a smaller set of rules unstated (plan item P3; BUILD-GAPS F-7.2.31, F-8.3.1, F-10.1.34, F-11.3.37 to F-11.3.43, and the resume_pending and awaiting_client_action cases of F-6.2.28). This statement is re-derived against the landed proposals 0092 and 0100. Proposal 0092 already closed the duplicate-hook half of F-10.1.34, the applied-check half of F-11.3.38, and the suspended case of F-6.2.28, and this proposal does not reopen them.

The following defects are code departing from rules the specification already states.

- Deadlines are anchored on `UpdatedAt` (F-11.3.41). The pre-running timeouts, the resume_pending window, the resuming budget, the awaiting_client_action deadline, the idle fallback anchor, the DLQ TTL, and the orphan-cleanup cascade window all measure from `UpdatedAt`, which every store `Update` rewrites, including writes that do not change state. §6.2 states each deadline as measured from entry to the state ("starts when the session enters `ready`", "measured from the session's entry to `suspended`"). `SuspendedAt` and `sweepSuspended`, added by 0092, are an existing state-entry stamp in code that the other states lack.
- No writer records `input_required` on the session row (F-11.3.39). §7.2 lists `running → input_required` when the runtime calls `lenny/request_input`, and the §6.2 idle-clock table marks `input_required` as not evaluated. The code tracks the wait only in a per-replica, in-memory registry, so the row stays `running` and `sweepIdle` idle-suspends it, or expires it with `expired:idle` when no suspender is wired or the row cannot be idle-suspended.
- `/start` runs `launchOnPod` and `registerBinding` while the row is still `ready`, and writes `running` only afterwards (F-11.3.37). The ready sweep guards only on the state and measures from `UpdatedAt`, so a launch still in progress when `maxReadyTimeoutSeconds` elapses fails with `READY_TIMEOUT`. §6.2 says the watchdog fires only when the client has not called `/start`.
- `sweepMaxAge` expires over-cap rows in `resume_pending`, `resuming`, and `awaiting_client_action`, because `maxAgeExpirable` excludes only `suspended` (F-6.2.28 remainder). §6.2 marks `maxSessionAge` as paused in all three states. Active age stops accruing there, so such a row is expired only when it left a counting state already over the cap.
- The orphan-session reconciler runs on every replica, although §10.1.4 states it runs on the "same leader-only pattern as orphan claim detection".
- Expiry writers stamp their reason only when `FailureReason` is empty (F-11.3.38 remainder). The failure funnel stamps a reason on entry to `resume_pending` and `awaiting_client_action`, and no code clears it, so a later idle, age, awaiting, or orphan-cleanup expiry keeps the stale crash reason.
- `sweepAwaitingClientAction`, `expireIdle`, and the pre-running sweep re-check only the state on the locked row and do not re-evaluate the deadline (F-11.3.40). `sweepMaxAge` and `sweepResumePending` re-check the deadline, and `sweepResuming` re-checks the coordination generation.
- Each sweep runs its terminal hook synchronously inside the serial `Tick` (F-11.3.42), and `Tick` returns on the first non-sentinel `List` or `Update` error, which skips the rest of that tenant and every later tenant (F-11.3.43). Orphan cleanup aborts its pass on the first error in the same way.

The following points are gaps in the specification and need a proposal.

- The data model defines no persisted state-entry timestamp, so the prose anchors in §6.2 have no column to read.
- §7.2 lists no edge, and no refusal, for specific terminal writes the code makes (F-7.2.31). `ForceTerminate` writes `failed` with `FORCE_TERMINATED` from any non-terminal state, and the budget terminator and orphan cleanup write `expired` from any non-terminal state. §7.2 lists no `→ failed` edge from `resume_pending`, `resuming`, or `awaiting_client_action`, and no `→ expired` edge from `resume_pending` or `resuming`. §7.2 does list other terminal edges from these states, including administrative-cancel edges to `cancelled`. §24.11 states that force-terminate moves a session "immediately to `failed`", which conflicts with §7.2.
- The specification assigns no replica to the watchdog's pre-running, idle, max-age, awaiting_client_action, and resume_pending sweeps, or to orphan cleanup (F-10.1.34 remainder). §10.1.1 states that every replica evaluates the `resuming` watchdog from the session row, so a blanket leader gate over every sweep would contradict §10.1.1 unless that section changes too.
- The specification does not state how a sweep re-checks a locked row, where it runs terminal hooks, or whether it continues past a per-row error.
- `perChildMaxAge` is persisted on a delegated child row in the `delegation_lease` JSONB column, but no sweep reads it (F-8.3.1). §8.2 defines it as "Max wall-clock seconds for the child", the code describes it as the budget "per descendant", and the specification does not say which session's stored value bounds which session or which sweep enforces it, although §6.2 and §7.2 name it as a `suspended → expired` trigger.

The fix for F-11.3.39 interacts with leader gating. A leader-gated watchdog cannot see a `lenny/request_input` wait held in another replica's in-memory registry, so the proposal has to persist the wait on the row (the missing `input_required` write) or sequence the item with plan item R20, the shared input-wait store.

## Who observes it

- A client or human answering a `lenny/request_input` question after more than `maxClientIdleSeconds` (default 900s) sees the session idle-suspended, or expired with `expired:idle` on a gateway with no suspender or for a session that cannot be idle-suspended.
- A webhook consumer and a delegating parent see the wrong reason for an expiry of a session that once entered `resume_pending` or `awaiting_client_action`. The stale `FailureReason` feeds `expiryReasonForState`, so `session.expired` reports the wrong `expiryReason`, and it feeds the `TaskErrorCode` and retryable classification in the parent's `child_failed` result, so a parent can retry a session that was reclaimed on purpose.
- A client whose `/start` launch outlasts the remaining ready window sees `READY_TIMEOUT` although it called `/start` in time.
- Operators see late expiry and late recovery-watchdog firing for every tenant when one row's `Update` or one tenant's `List` keeps failing, or when one terminal hook's seal runs long.
- A delegating parent sees a child outlive its `perChildMaxAge`, bounded only by `maxSessionAge` or, while suspended, by the suspended-session lifetime.

## What breaks if nothing changes

- Sessions waiting on a human are reclaimed contrary to §6.2.
- Terminal reasons reported to webhooks and parents are wrong after any recovery, and parents make retry decisions on the wrong code.
- One persistently failing row or tenant starves every later sweep for every tenant on every tick: the resume_pending caps, `maxSessionAge`, the awaiting deadlines, idle, the suspended lifetime, and the DLQ TTL. One slow seal delays the rest of the pass, and the ticker drops ticks while `Tick` runs.
- Writes that do not change state push per-state deadlines out, so a pod or slot is held past the bound §6.2 states.
- Every replica lists every tenant for every sweep and takes an in-process terminal claim on rows another replica writes. The row-locked guards in `pgstore.Update` prevent a double write and a double hook, so no session is expired twice.
- The narrow-window items have low practical impact. A locked-row re-check on state only can expire a row that left and re-entered the state between listing and update. `sweepMaxAge` expires a paused row that left a counting state already over its cap, which §6.2's evaluation on entry to `running` would have expired on resume anyway; the visible difference is that the session ends without a recovery attempt.

## Prior art considered

- Proposal 0092 (Implemented) made every terminal sweep's mutator return a sentinel for a row it does not apply to and run the hook only on a nil `Update`, stopped the terminal writers deciding "applied" from `FailureReason`, measured `maxSessionAge` as active age, and stopped `sweepMaxAge` expiring `suspended` rows. Its resolution notes hand leader gating, the unconditional reason stamp, and the resume_pending and awaiting_client_action cases to P3. Its `SuspendedAt` stamp and `sweepSuspended` locked-row re-check are a code precedent for a state-entry anchor.
- Proposal 0100 (Implemented, P2a) supplies the bounded terminal-hook context that moving hooks off the serial pass depends on. It does not move the hook and lists P3 as not drafted.
- No other proposal stages these changes. Proposals 0101 and 0104 are approved and do not cover them.
- The specification already holds a leader-only sweep pattern (§10.1.4 orphan-session reconciler), and the gateway already runs singleton sweeps under the §12.5 `lenny-gateway-leader` Lease in `startLeaderElectedSweeps`. Neither the watchdog nor orphan cleanup uses it.
- §7.2 already has administrative-cancel edges (`resume_pending → cancelled` for an operator or administrative cancel, `resuming → cancelled` for an operator cancel). Routing `ForceTerminate` onto those edges is one available answer to part of F-7.2.31.
- Plan item R20 (the shared input-wait store, not started) is the plan's route for the cross-replica wait that F-11.3.39 needs.

## Validated premises

- **Deadlines anchored on `UpdatedAt` (F-11.3.41): confirmed** by every lens that checked it (premise, evidence, scope, impact, alternatives). The alternatives and prior-art lenses refine the spec side: §6.2 states each entry anchor in prose, so the code departs from a defined rule, and the specification lacks only a persisted column.
- **Expiry stamps and post-checks depend on an empty `FailureReason` (F-11.3.38): half refuted.** The post-check half was closed by 0092 (premise, evidence, prior-art, scope, and alternatives lenses; BUILD-GAPS resolution note; each writer runs its hook on a nil `Update`). The stamp half is confirmed in `expireIdle`, `sweepAwaitingClientAction`, `sweepMaxAge`, and orphan cleanup. The impact lens established that the funnel stamps the reason and nothing clears it, so the stale reason reaches webhooks and parents.
- **Idle expiry fires during `lenny/request_input` (F-11.3.39): confirmed, re-classified.** The premise, evidence, prior-art, and alternatives lenses agree the specification already states the rule (§7.2 edge, §6.2 idle-clock table), so the cause is a missing state write rather than a spec gap. The premise lens adds that since 0092 the sweep idle-suspends when a suspender is wired, so "idle expiry" holds only without a suspender or for a non-suspendable row. The scope lens established the conflict with leader gating through the in-memory input-wait registry.
- **Ready timeout fails a timely `/start` (F-11.3.37): confirmed** (premise, evidence, alternatives). §6.2 already states the rule.
- **Terminal sweeps run unelected so two replicas claim one expiry (F-10.1.34): partly refuted.** All lenses that checked it agree the sweeps run unelected and that the "two replicas claim one expiry" consequence is refuted for the current tree: the sentinel and nil-`Update` discipline from 0092 and the row lock in `pgstore.Update` allow one write and one hook. The remaining cost is duplicated listing and an in-process terminal claim on each replica (impact lens).
- **The specification says nothing about which replica runs each sweep: refuted in part.** The evidence, prior-art, and alternatives lenses found §10.1.4 makes the orphan-session reconciler leader-only (a code-versus-spec defect, since the code runs it unelected) and §10.1.1 has every replica evaluate the `resuming` watchdog. The premise lens's exhaustive search found no passage assigning the other watchdog sweeps or orphan cleanup to a replica, which is the surviving gap.
- **Sweeps re-check only the state of a stale listing (F-11.3.40): partly stale.** The premise and impact lenses found `sweepMaxAge` and `sweepResumePending` re-check the deadline and `sweepResuming` the generation. The pre-running sweep, `sweepAwaitingClientAction`, and `expireIdle` re-check state only. The impact lens rates the window as narrow.
- **Terminal hooks inline in the serial pass (F-11.3.42) and abort on first per-row error (F-11.3.43): confirmed** (premise, evidence, impact). The impact lens rates F-11.3.43 as high blast radius. The scope lens notes the 0100 hook-context dependency is met.
- **`sweepMaxAge` expires paused resume_pending and awaiting_client_action rows (F-6.2.28 remainder): confirmed and widened.** The premise lens found `resuming` rows are expired too. The evidence and impact lenses established the defect is narrow, because active age stops accruing in paused states. The alternatives lens classifies it as a code-only fix.
- **ForceTerminate, orphan cleanup, and the budget terminator write on unlisted edges, and the spec names no edges for terminal writes from paused and recovering states (F-7.2.31): wording refuted, defect confirmed.** The premise, evidence, prior-art, and alternatives lenses found §7.2 lists many terminal edges from these states. The missing edges are `→ failed` from `resume_pending`, `resuming`, and `awaiting_client_action`, and `→ expired` from `resume_pending` and `resuming`. The premise lens found §24.11 conflicts with §7.2. The evidence lens's claim that `suspended → failed` with `FORCE_TERMINATED` is unlisted is narrower than stated: §7.2 lists `suspended → failed` for non-retryable failure and `BUDGET_KEYS_EXPIRED`, so the gap there is the cause rather than the edge. The scope lens argues this item is a state-machine decision that fits P2b or a separate proposal; it stays here unless the proposal states a reason to move it.
- **`perChildMaxAge` is stored nowhere (F-8.3.1): storage half refuted.** The premise and evidence lenses found it persisted in `delegation_lease` (migration 0099) by `storeLeaseFromSlice`, which this validation confirmed. The prior-art lens's claim that nothing stores it is refuted by that evidence. The enforcement half is confirmed: no sweep reads it. The open question is which session the stored value bounds and which sweep enforces it.
- **The specification gives no state-entry timestamp: confirmed as a data-model gap** (premise, evidence), with the refinement above that the anchors exist in prose.
- **Scope (scope lens):** deadline semantics and sweep mechanics interlock, because a locked-row deadline re-check needs the state-entry anchor, and they stay in one proposal. F-7.2.31 is separable. F-8.3.1 is small enough to stand as a direct fix if the proposal needs trimming.
- **Spec-change footprint (alternatives lens):** most items are code departing from clear specification text and need no staged spec edit: F-11.3.37, F-11.3.39, F-11.3.42, F-11.3.43, the F-6.2.28 remainder, the F-11.3.38 stamp, and the anchor substitution in F-11.3.41. The staged spec edits are the persisted state-entry column, the §7.2 edges or refusals and the §24.11 reconciliation, sweep replica ownership consistent with §10.1.1 and §10.1.4, the sweep re-check, hook, and error-continuation rules, and the `perChildMaxAge` binding and enforcer.
