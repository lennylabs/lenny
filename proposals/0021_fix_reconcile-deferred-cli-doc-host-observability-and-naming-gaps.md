### 1.1 CLI documentation reconciliations (`F-CTL-1`, `CTL-DOC-1`, `CTL-DOC-2`, `F-CTL-6`, `F-CTL-8`)

The §24 CLI reference has drifted from the implemented `lenny-ctl` surface.

- **F-CTL-1 (low/med, doc).** §24.9 documents `lenny-ctl admin users rotate-token` as mapping to `POST /v1/oauth/token` with an RFC 8693 token-exchange grant (`spec/24:119`), but the implemented route is the dedicated `POST /v1/admin/users/{user}/rotate-token` (`pkg/gateway/externalapi/admin/admin_token.go:74-106`). The route is cited to §17.6:472 in both the proposal's source and the code, but §17.6 line 472 is the unrelated `noEnvironmentPolicy: allow-all` "Option A" bootstrap text; the actual rotation procedure (the F-17.6.3 basis) is at `spec/17:507` (referenced again at `spec/17:669`). The §17.6:472 anchor is stale at 15 sites across 8 files (`admin_token.go:75,80`, `admintoken.go:46,91,231,319`, `routes.go:724`, `user_revocation.go:207`, `users.go:14,53,56`, and the three test files), every one citing line 472 as the rotation/no-grace-period procedure; all are retargeted to §17.6:507 in the same change. The exact-string grep `grep -rn "17.6 line 472"` matches only 13 of these; `admintoken.go:46` reads `clause, line 472` and `admintoken.go:91` wraps `§17.6` and `line 472` across two comment lines, so both are found by hand rather than by that pattern. **The dedicated route is the correct design:** it mints the new token via `adminToken.Rotate()` → `mint()`, which signs a JWT directly (`pkg/gateway/externalapi/admintoken/admintoken.go:312`), **patches the `lenny-admin-token` Kubernetes Secret server-side** (`admintoken.go:246`), and best-effort-revokes the superseded token (`admintoken.go:249` `revokePrevious`, but this revoke is non-durable, unaudited, and unretried; see the audit-coverage gap below), and it 404s any user except the managed admin so it cannot serve as a generic token mint (`admin_token.go:88-92`). The implementation does **not** use the token-exchange grant: `mint()` signs a fresh JWT and never invokes `/v1/oauth/token`. The superseded client-side model (the CLI calls `/v1/oauth/token` and the CLI patches the Secret) is documented across more sites than §24.9 alone: §17.6:507 ("the CLI updates the user record in Postgres and patches the `lenny-admin-token` Secret"), §13.3:551 ("admin rotation via `lenny-ctl` ... by direct caller invocation") and the §13.3 claim-mapping rows (`spec/13:558,560,576,581`), §15.1:881 (the `/v1/oauth/token` admin-rotation mapping `subject_token=<current>`), three operator-guide pages (`docs/operator-guide/lenny-ctl.md:265`, `installation.md:372`, `security.md:114`), and four further published doc pages outside the operator guide: `docs/api/admin.md` (the `/v1/oauth/token` caller table "Rotate admin tokens" row at :805, and :813, which describes the CLI as a wrapper around `/v1/oauth/token` that "additionally patches the `lenny-admin-token` Kubernetes Secret"; the page has dedicated `### POST /v1/admin/users/{userId}/invalidate` (:815) and `/erase` (:822) sections but no dedicated rotate-token section), `docs/client-guide/authentication.md` (the "Token Rotation and Exchange" section :95-138, including the worked "rotate an admin token" token-exchange example at :99-110 and the convenience-wrapper sentence at :138), `docs/tutorials/oauth-token-exchange.md` (the frontmatter `description` at :6 and the "Rotate the admin token" step at :20, which also names a non-existent `lenny-ctl auth rotate-admin-token` command), and `docs/tutorials/index.md:32` (the OAuth-token-exchange row describing `/v1/oauth/token` as the admin-rotation path). A further published page carries the same universal-minting claim that overstates the endpoint's coverage once the bootstrap admin token is a gateway-direct in-process mint: `docs/getting-started/architecture.md:192` states "every token issuance -- initial tokens, rotation, delegation child-token minting, scoped operator tokens -- flows through the canonical `POST /v1/oauth/token` endpoint", parallel to spec §4.3:193 and `docs/operator-guide/security.md:108,114`, so it is reconciled in the same change. The §15.1 REST endpoint table also omits the dedicated route entirely (it lists `/v1/admin/users/{userId}/invalidate` at :835 and `/erase` at :859, but no rotate-token row). **Two distinct rotation flows must be kept separate.** Flow (1) is the bootstrap `lenny-admin` Secret rotation: `lenny-ctl admin users rotate-token --user lenny-admin` -> the dedicated `POST /v1/admin/users/{user}/rotate-token` route -> `adminToken.Rotate()` -> `mint()`, which signs a JWT in process (`admintoken.go:312`) and patches the Secret; this flow never invokes `/v1/oauth/token`. Flow (2) is the general `/v1/oauth/token` self-rotation grant (the `isRotation` path, `pkg/tokenservice/tokenservice.go:769-784`): a caller presents its own current token as `subject_token` and requests a privilege-equivalent replacement, the prior token is revoked atomically inside the issue transaction (`RecordWithRotationAudit`), and the Token Service emits `token.exchanged{exchange_type:admin_rotation}` plus `token.revoked{rotation_replaced}`. Flow (2) remains implemented and is offered to platform-admin, tenant-admin, service-principal, and end-user self-rotation (`docs/api/admin.md:805-807`, `docs/client-guide/authentication.md:99-110`). The reconciliation therefore distinguishes the two flows rather than collapsing them: the §24.9/§17.6/§13.3:551 prose that describes the **bootstrap admin Secret rotation** as a CLI-driven `/v1/oauth/token` call is corrected to the dedicated gateway-direct in-process route (the CLI no longer calls `/v1/oauth/token` for the Secret rotation; the gateway mints in process and patches the Secret), but the general `/v1/oauth/token` self/service-principal rotation grant stays in §13.3:551/597, the §13.3:558/560/576/581 claim-mapping rows, §15.1:881, and the §16.7:672 classification, because the `isRotation` grant remains implemented. The §15.1 REST table gains the dedicated rotate-token row. How the route mints internally is not a doc question: the audit-coverage gap below shows the current bootstrap mint emits none of the spec's mandatory rotation audit rows and its revoke is non-durable, resolving the §6 F-CTL-1 decision toward keeping the in-process signer and closing the audit/durable-revoke gap at the issued-token-store layer (staged in C7).
- **F-CTL-1 audit-coverage gap (med, security).** The direct-sign mint (`admintoken.Rotate()` → `mint()`) emits **no audit events at all**: a tree search for any audit reference in `pkg/gateway/externalapi/admintoken/` returns zero. §13.3:587 makes rotation audit mandatory ("**Every** token exchange … emits a `token.exchanged` audit event"), and §16.7:672-673 require admin rotation to emit `token.exchanged` with `exchange_type: admin_rotation` and `token.revoked` with `revocation_reason: rotation_replaced`. The direct path emits neither. Its revoke is also non-durable: `revokePrevious` discards the error (`admintoken.go:351`, `_ = p.issued.Revoke(...)`); there is no retry or reconcile (the only caller, `Rotate()`, is request-scoped; `Provision()` preserves the existing Secret without re-revoking; no background sweep re-attempts a failed revoke); and the adapter pushes the revocation onto the volatile cache **even when the durable Postgres write fails** (`cmd/lenny-gateway/user_revocation.go:225-231`). Because the §12.2 rehydration reads `revoked_at IS NOT NULL` from Postgres (`issuedtokenstore.go:429-434`), a durable-write failure leaves the superseded token revoked only in memory, so it silently becomes valid again after any cache eviction or replica restart, contradicting the §17.6:507 "immediately invalidated (not a grace period)" guarantee, with no audit and no error surfaced. The canonical issued-token store the gateway already holds (`pkg/gateway/storage/issuedtokenstore`) provides the audit-and-record machinery: `RecordWithAudit` writes the new token and its `token.exchanged` audit row in one transaction (`issuedtokenstore.go:150`), and the store's atomic rotation method `RecordWithRotationAudit` adds the in-COMMIT prior-token `revoked_at` plus a post-COMMIT `token.revoked` (`issuedtokenstore.go:180-200`). The fix reuses these store surfaces from the `admintoken` adapter rather than re-implementing the audit/revocation machinery: it records the new token through `RecordWithAudit` with `exchange_type: admin_rotation`, patches the Secret, then durably revokes the prior token with `revocation_reason: rotation_replaced` once the patch succeeds (C7). The atomic single-transaction `RecordWithRotationAudit` is not used directly on this path because it revokes before the Secret is patched, which would strand the Secret on a dead token; the gateway must persist the Secret before revoking. Secondary gap, independent of the admin-rotation path: the Token Service's own `exchangeAuditPayload` (`tokenservice.go:782-792`) omits the §16.7:672-mandated `exchange_type` field on every `token.exchanged` row, so closing this gap also adds that field.

### 1.4 The `LenniOps*`→`Ops*` alert-name typo

## 2. Decisions

- **CLI doc reconciliations (1.1) follow the code.** The dedicated rotate-token route is kept and the §24.9/§17.6/§13.3/§15.1 docs are reconciled to it. **F-CTL-1's mint mechanism resolves to keeping the gateway's in-process signer and closing the audit/durable-revoke gap at the issued-token-store layer** (Section 6): `Rotate()` mints and records the new token through the canonical store's `RecordWithAudit` (emitting `token.exchanged{exchange_type:admin_rotation}`), patches the Secret, then durably revokes the prior token with `revocation_reason: rotation_replaced` (emitting `token.revoked`), preserving the persist-Secret-before-revoke ordering. Routing the mint through the HTTP `/v1/oauth/token` exchange is rejected: the gateway holds no in-process exchanger, the gateway egress NetworkPolicy does not admit the Token Service HTTP listener, the exchange grant cannot serve the §17.6 bootstrap first-token mint, and the rate-limit-bypass claim does not hold for that path. The audit/revoke fix reuses the issued-token store the gateway already holds rather than re-implementing rotation audit, so there is one canonical implementation. Two distinct rotation flows are kept separate (§1.1): the bootstrap `lenny-admin` Secret rotation is the gateway-direct in-process mint that moves off `/v1/oauth/token`, and the general `/v1/oauth/token` self/service-principal rotation grant (the `isRotation` path) stays on `/v1/oauth/token` and emitted by the Token Service. A single narrow normative §13.3:597 edit documents the gateway-mediated admin-credential rotation ordering (mint-record-persist-revoke) as distinct from the single-transaction token-exchange rotation; §13.3:551, §15.1:881, §4.3:193, and §16.7:672 are reconciled so the bootstrap admin Secret rotation reads as a gateway-direct in-process mint while the general rotation grant stays classified as a `/v1/oauth/token` token exchange emitted by the Token Service. §13.3:607 needs no edit, because the in-process bootstrap mint never reaches the rate-limited `/v1/oauth/token` exchange.
- **`LenniOps*`→`Ops*` uses the `Ops*` style** (`OpsLockSplitBrainDetected`, `OpsSelfHealthDegraded`), per the user's resolution. The rename regenerates the two `alerting-rules.yaml` artifacts via `make generate` rather than editing them by hand.
- **F-MCP-1 resolves to building the `openapi-to-mcp` generator, over a complete document so it also closes F-COV-3.** §25.12, §15.1, and §18 mandate the build-time generator (the `genmcpschemas` mechanism already used for §15.2); the hand-written `buildToolset()` violates the spec. The relax-the-mandate alternative is not taken.
- **SEC-BACKUP-1 and F-DR-1 resolve to implementing the spec-mandated behavior** (Section 6), not deferring: SEC-BACKUP-1 wires the config/CRD exporters, and F-DR-1 implements the three missing doctor remediations. The §25.6/§25.11 defer-via-spec-amendment alternatives are not taken; the F-DR-1 accuracy fixes (the `manual` comment and the tracking finding) land regardless.
- **F-COV-1 resolves to corrected Option 1** (Section 6): the OpenAPI document is a gateway build artifact (gateway-titled, generated from the gateway's Go types, CI-completeness-checked against the gateway mux, consumed at build time by the MCP generators), so reconcile §15.1:909/§25.12/§25.4 to name the gateway, make the gateway-hosted `/me` links absolute-to-gateway (the agent already holds `gatewayURL`), and add the missing `/v1/openapi.yaml`. ### C7. Close the admin-rotation audit and durable-revoke gap on the in-process mint path (F-CTL-1)

The audit-coverage gap is genuine: the gateway's admin-rotation mint emits no `token.exchanged` and its revoke emits no `token.revoked` and is non-durable (§1.1 audit-coverage gap). The mechanism that closes it keeps the gateway's **in-process signer** for both `Provision()` (the §17.6 bootstrap first-token mint) and `Rotate()`, because the Token Service exchange path cannot serve either. A token-exchange grant requires a `subject_token` the caller already holds (`tokenservice.go:420-424` rejects an empty `subject_token`, and `tokenservice.go:415-418` accepts only `grantTypeExchange`, `tokenservice.go:271`), and at bootstrap there is no prior admin token to present, so `Provision()` cannot mint via `/v1/oauth/token` (`admintoken.go:213`→`mint`→`p.signer.Sign`, `admintoken.go:312`). The earlier Option-C framing (route the mint through an internal `/v1/oauth/token` exchange) is rejected: the gateway holds no in-process exchanger and reaches `/v1/oauth/token` only by reverse-proxying over HTTP to the optionally-present Token Service Deployment (`cmd/lenny-gateway/flags.go:817` and `cmd/lenny-gateway/stores.go:511`), the gateway egress NetworkPolicy admits only the gRPC port to the Token Service and not its HTTP listener (`charts/lenny/templates/system-network-policies.yaml:534-539`, `pkg/embedded/manifests/manifests.yaml` gateway egress port `50052` only), and the exchange handler rate-limits every caller with no internal-caller bypass (`tokenservice.go:464`). Routing the bootstrap admin-credential rotation through that path would convert an in-process operation into a hard runtime dependency on an external service, contradict the §13.3:551 and §16.7:672 reconciliation of the bootstrap admin Secret rotation as a direct gateway-mediated in-process mint, and break the bootstrap path. (This is the bootstrap `lenny-admin` Secret rotation specifically; the general `/v1/oauth/token` self/service-principal rotation grant continues to flow through the Token Service exchange and is not affected by C7.)

The close-the-gap design reuses the canonical issued-token store the gateway already holds (`pkg/gateway/storage/issuedtokenstore`, the same store backing the admin adapter at `cmd/lenny-gateway/user_revocation.go:202-231`), so there is no second implementation of rotation audit or revocation:

- **Mint + record + exchange audit (no revoke yet).** `admintoken.Rotate()` signs the new token in process and records it through `Store.RecordWithAudit(tok, "token.exchanged", payload, at)` (`pkg/gateway/storage/issuedtokenstore/issuedtokenstore.go:150`), which INSERTs the issued-token row and writes the `token.exchanged` audit row in one transaction. Set the payload's `exchange_type: admin_rotation`. This step does **not** revoke the prior token, so the persist-Secret-before-revoke ordering is preserved.
- **Patch the Secret** with the new token.
- **Durable revoke + revoked audit, only on a successful patch.** Revoke the prior jti through the store with `revocation_reason: rotation_replaced` and emit the `token.revoked{revocation_reason:rotation_replaced}` audit row (mirroring the Token Service's post-COMMIT `emitRotationRevoked`, `tokenservice.go:947-959`; the standalone canonical revocation request emits `explicit_revoke`, `tokenservice.go:920-924`, so the rotation path needs a reason-parameterized revoke rather than the `explicit_revoke` request). Make this revoke durable: the error is surfaced and retried rather than discarded (`admintoken.go:351` discards it today), and the cross-replica cache push is gated on the durable Postgres write succeeding (`user_revocation.go:225-231` pushes to cache even on a durable-write failure today, which lets a §12.2 rehydration silently un-revoke the old token, `issuedtokenstore.go:429-434`).
- **Reclaim a named leaked predecessor on a crash between patch and revoke.** A process crash (or any hard failure) after the Secret patch succeeds but before the durable revoke commits would leave the prior `lenny-admin` token live with no reclaimer: `Rotate()` is request-scoped (its only caller is the request handler at `pkg/gateway/externalapi/admin/admin_token.go:93`, with no reconcile loop for admin tokens), and a later retry reads the now-patched Secret and revokes the new token's predecessor rather than the orphan. Without a reclaimer this contradicts the unedited §13.3:599 ("no grace period") and §13.3:601 ("Authoritative durability for revocation", under which every validation falls back to `issued_tokens.revoked_at`, which the crash leaves NULL, so the old credential validates indefinitely) and the §17.6:507 "immediately invalidated (not a grace period)" guarantee. A `Provision()`-time reclaimer does not close this window: `Provision()` is not called on a gateway start. Its sole production caller is `provisionAdminToken` (`pkg/gateway/externalapi/admin/admin_token.go:63`), reached only from the `POST /v1/admin/bootstrap` handler (`bootstrap.go:224`); gateway startup constructs and wires the provisioner but never calls `Provision()` (`cmd/lenny-gateway/adminrouter.go:842-857`). A start not followed by an operator bootstrap therefore never runs a `Provision()`-time reclaimer, and even on a re-run `Provision()` early-returns when the Secret already exists (`admintoken.go:208-212`), which is exactly the post-crash state, before any reclaim logic. Close the window instead with a continuously-running leader-gated periodic sweep registered in the existing gateway-singleton sweep set (`gatewayleader.NewGate` / `leaderGate.Add`, `cmd/lenny-gateway/workers.go:591-593,671-881`, which already runs the artifact-GC, audit-retention, and T4-probe sweeps under the `lenny-gateway-leader` Lease and falls back to `AlwaysLeader` off-cluster). **The sweep revokes a single named predecessor jti rather than every non-current token for the subject.** The whole-subject jti-excluding predicate (`sub = 'lenny-admin' AND revoked_at IS NULL AND jti <> $current`) is wrong on two counts. First, the bootstrap `lenny-admin` user is a platform-admin (`admintoken.go:277,309,323` set `Roles: []auth.Role{auth.RolePlatformAdmin}`), so the operator holding the bootstrap token is eligible for the flow-2 general `/v1/oauth/token` self-rotation grant the proposal explicitly preserves (§1.1); a flow-2 self-rotation mints a new live token for the same `lenny-admin`/`AdminTenant` subject via `RecordWithRotationAudit` (`tokenservice.go:710-715`) without patching the Secret, so its jti is not the Secret's jti, and the whole-subject predicate would revoke that legitimately self-rotated token within one sweep interval. Second, the staged ordering records the new token in Postgres (`mint()` calls `p.issued.Record` at `admintoken.go:320-323`) before patching the Secret (`p.secrets.Update` at `admintoken.go:246`), so between the record and the patch the new token has `revoked_at IS NULL` and `jti <> $current_secret_jti` (the Secret still holds the old jti); a sweep firing in that window matches the about-to-be-installed successor (the leader gate serializes only the sweep across replicas; `Rotate()` runs unguarded on whichever replica's request goroutine served `handleRotateToken`, `admin_token.go:93`), revokes it, and the rotation then patches the Secret to a jti Postgres already marks revoked, returning the operator a dead-on-arrival token and locking the operator out. This is the exact lockout the persist-Secret-before-revoke ordering exists to prevent. **Record both the current and the prior jti in the `lenny-admin-token` Secret** (add a `prevJtiKey` alongside `jtiKey`/`CreatedAtKey`, `admintoken.go:48-49`): `Rotate()` writes the predecessor's jti into `prevJtiKey` as part of the same Secret patch that installs the new jti, so the orphaned predecessor is durably named before the revoke step. The sweep then durably revokes, with `revocation_reason: rotation_replaced`, the single jti the Secret names in `prevJtiKey` when it is still `revoked_at IS NULL` (idempotent: a no-op once the in-handler revoke has already committed). A named-jti revoke (`Revoke(ctx, AdminTenant, prevJti, "rotation_replaced", now)`, the existing per-jti `Revoke` at `issuedtokenstore.go`) reaches only the orphaned predecessor: it never matches a flow-2 self-rotated token (which is never written into `prevJtiKey`, because flow 2 does not patch the Secret) and never matches the in-flight successor (which is the Secret's current jti, never its prior jti), so the jti-excluding whole-subject `RevokeBySubject` variant is not needed. **A single `prevJtiKey` slot is overwritable, so `Rotate()` must durably revoke the jti the slot currently names before it overwrites the slot, otherwise a second rotation that runs before the sweep fires permanently orphans the first crash's predecessor.** Without that step, trace two rotations straddling a crash: rotation A patches the Secret to `{jti:jti_B, prevJti:jti_A}` then crashes before its in-handler durable revoke of `jti_A` commits, leaving `jti_A` with `revoked_at IS NULL` and named in `prevJtiKey`; the operator (the HTTP call failed) retries; rotation B reads `{jti:jti_B, prevJti:jti_A}`, mints `jti_C`, and patches the Secret to `{jti:jti_C, prevJti:jti_B}`, a full-map replace (`k8ssecret.go:70` does `sec.Data = data`) that unconditionally overwrites `prevJtiKey` from `jti_A` to `jti_B`; rotation B's in-handler revoke targets the read-time current jti `jti_B` (`revokePrevious` reads `prev[jtiKey]`, `admintoken.go:344`), never `jti_A`; `jti_A` is then named nowhere and the sweep, which revokes only whatever `prevJtiKey` currently names, never reaches it, so with the ~10-year `DefaultTokenTTL` (`admintoken.go:55`) and §13.3:601 making Postgres the sole authoritative store, the orphaned admin credential validates indefinitely rather than to the sweep interval. Close this by ordering the predecessor's durable revoke ahead of the Secret patch that overwrites its name: `Rotate()` durably revokes the jti the live Secret's `prevJtiKey` already names (the prior crash's orphan, if any) and aborts the rotation before the patch when that revoke fails, so the slot keeps naming the unrevoked predecessor for the next attempt or the sweep, then mints, records, patches the Secret to `{current jti, prevJti:read-time current jti}`, and durably revokes the read-time current jti in-handler. The invariant the ordering preserves is that `prevJtiKey` is never overwritten while it names an unrevoked jti unless that jti is durably revoked in a committed write that precedes the overwrite, so every predecessor across any number of consecutive crash-then-retry rotations is durably revoked or durably named before its name is lost, and the post-patch sweep catches the last-named predecessor. This bounds the residual to the sweep interval (a flag-overridable cadence with a documented default, per the operator-tunability rule for non-spec defaults) rather than to the crash window or indefinitely, and keeps §13.3:601's authoritative-durability invariant true without weakening the no-grace-period guarantee in the spec and without revoking any legitimately-issued admin token.
  - **Serialize `Rotate()` so concurrent rotations cannot drop a successor jti through the non-atomic Secret read-modify-write.** The revoke-before-overwrite ordering above closes the **sequential** crash-then-retry leak, but it does not close a **concurrent** one, and the design admits concurrent rotations: `handleRotateToken` holds no lock (`admin_token.go:93`), and the leader gate serializes only the sweep across replicas, not the request-goroutine `Rotate()` calls. The Secret read-modify-write is non-atomic and carries no optimistic-concurrency guard: `Rotate()` reads `existing` (`admintoken.go:236`), derives `data` from that read, and `k8ssecret.Update` does a fresh `Get` only to refresh the ResourceVersion before a blind full-map replace `sec.Data = data` (`k8ssecret.go:65-75`, the overwrite at `:70`), with no `RetryOnConflict` and no advisory lock. Trace two **concurrent** rotations A and B from a clean Secret `{jti:J0, prevJti:empty}`: both Get `{jti:J0}` and both find `prevJtiKey` empty, so the revoke-before-overwrite step is a no-op for each; A mints J_A and B mints J_B; A patches to `{jti:J_A, prevJti:J0}`, then B patches to `{jti:J_B, prevJti:J0}` (B's read-time current was J0), a full-map replace that drops J_A from the Secret entirely; both in-handler revokes target the read-time current J0. Net: J0 is revoked, J_B is live and current, and J_A is live with `revoked_at IS NULL`, named **nowhere** in the Secret (a dropped successor, never a `prevJtiKey` predecessor), so the sweep (which revokes only `prevJtiKey`=J0, already revoked) never reaches it; with the ~10-year `DefaultTokenTTL` (`admintoken.go:55`) and §13.3:601 making Postgres the sole authoritative store, J_A validates indefinitely. This is the same indefinite-validation leak the sequential revoke-before-overwrite ordering was added to close, reappearing through the concurrent lost-update path, and it falsifies the §13.3:597 carve-out claim that the invariants hold for this path. Close it by **serializing `Rotate()` for the `lenny-admin` subject** so its read-modify-write commits without interleaving. The serialization primitive must span the **whole** `Rotate()` sequence, which is not a single Postgres transaction: it interleaves a Kubernetes Secret read-modify-write (a controller-runtime client call that cannot ride in a Postgres transaction) with several independent issued-token-store transactions, because every store method (`Record`, `RecordWithAudit`, `Revoke`) opens and commits its own `pgtenant.InTx` (`pkg/gateway/storage/pgtenant/pgtenant.go:76-100` begins and commits one transaction per call; `pkg/gateway/storage/issuedtokenstore/issuedtokenstore.go:113-114,150-152,290-294` each open their own `InTx`). A transaction-scoped `pg_advisory_xact_lock` releases automatically at the COMMIT of the single transaction that acquired it, so a lock taken inside any one store transaction is released before the next store/K8s step runs, and a concurrent `Rotate()` then interleaves during the mint+record, the Secret patch, or the final revoke — the exact window the lock is meant to close. The two `pg_advisory_xact_lock` idioms in the gateway (the per-session admission lock at `pkg/gateway/session/sessionstore/pgstore/pgstore.go:750`; the per-tenant audit lock at `pkg/gateway/audit/auditstore/lock.go:180`) hold the lock for a single transaction that does its entire read-modify-write inside that transaction, which is why the transaction-scoped form is correct there and insufficient here, and §13.3:605 likewise reads and revokes the actor jti inside the **same** advisory-locked transaction that issues the child. Bracket the whole sequence with a **session-scoped** advisory lock instead: acquire `pg_advisory_lock(hashtext("admintoken:"+subject))` on a single pinned, pooled connection before the read-existing step and release it with `pg_advisory_unlock` after the final revoke, with a deferred leak-safe unlock that runs on every error and panic path (the `pkg/gateway/storage/erasurejob/saltlockpg/saltlockpg.go:49-68` idiom, whose `WithSaltLock` acquires `pg_advisory_lock` on an acquired connection, runs the protected function "in between on its own connections", and releases on a `context.WithoutCancel` context so a cancelled `ctx` still frees the session-level lock). This needs a small `WithSubjectLock(ctx, subject, fn)` entry point — either a shared advisory-lock helper the `admintoken` adapter can call or a method on `issuedtokenstore` that holds a connection from the same pool — added to the C7 implementation and the §7 files-touched list, mirroring `saltlockpg` rather than inventing a new mechanism. Serialization is the architecturally best option for this path: it mirrors the discipline the spec already uses to guard the **other** rotation flow against concurrent rotation (§13.3 "Actor-token freshness under concurrent rotation", `spec/13:605`), it reuses the session-scoped advisory-lock idiom already present in the gateway (`saltlockpg`) rather than introducing the first `RetryOnConflict` on the Secret (option (a), which guards only the Secret write and not the cross-transaction record-then-revoke invariant, and must re-read the Secret and re-derive a fresh predecessor revoke on every conflict) or a new Postgres marker column and migration (option (c)), and it makes the whole read-modify-write atomic across the K8s patch and the separate store transactions so the revoke-before-overwrite ordering and the `prevJtiKey` invariant hold under concurrency exactly as they do sequentially. A second rotation now blocks until the first releases the lock, reads the first's installed Secret, durably revokes the predecessor the slot names, and proceeds, so no successor jti is ever dropped unnamed.

- **F-CTL-1 mint mechanism, RESOLVED: keep the in-process signer and close the audit/durable-revoke gap at the issued-token-store layer.** The dedicated rotate-token route is kept and the docs reconciled to it. The genuine defect is that the gateway's admin-rotation mint emits none of the §16.7 audit rows the spec mandates for rotation (§13.3:587, §16.7:672-673) and its revoke is non-durable, unaudited, and unretried (§1.1 audit-coverage gap, verified end to end). This reuses the issued-token store the gateway already holds, so there is one canonical rotation-audit implementation rather than a duplicate inside `admintoken`. Routing the mint through the internal `/v1/oauth/token` exchange (the earlier Option C) is rejected on architectural grounds: the gateway holds no in-process exchanger and reaches `/v1/oauth/token` only by reverse-proxying over HTTP to the optionally-present Token Service (`flags.go:817` and `stores.go:511`); the gateway egress NetworkPolicy admits only the Token Service gRPC port, not its HTTP listener (`system-network-policies.yaml:534-539`); the token-exchange grant cannot mint the bootstrap first token because it requires a `subject_token` the bootstrap caller does not yet hold (`tokenservice.go:415-424`); and the "internal calls bypass the rate limit" claim does not hold for the exchange path, which rate-limits every caller (`tokenservice.go:464`). Routing it through the exchange would also contradict the §13.3:551 and §16.7:672 reconciliation of the bootstrap admin Secret rotation as a direct gateway-mediated in-process mint. The single-transaction atomic mint+revoke (`RecordWithRotationAudit`) is rejected for this path because it revokes inside the mint transaction before the Secret is patched, so a patch failure would strand the Secret on a dead token and lock the operator out; the rotation must persist the Secret before revoking. Two distinct rotation flows are kept separate (§1.1): the bootstrap `lenny-admin` Secret rotation is this gateway-direct in-process mint, while the general `/v1/oauth/token` self/service-principal rotation grant (the `isRotation` path, `tokenservice.go:769-784`) stays on `/v1/oauth/token` and emitted by the Token Service. A single narrow normative §13.3:597 edit documents the gateway-mediated bootstrap admin-credential rotation ordering as distinct from the single-transaction token-exchange rotation, and states the leader-gated periodic reclaimer that durably revokes the single named predecessor jti the Secret records in `prevJtiKey` when a crash between the Secret patch and the durable revoke leaves it orphaned, the rule that `Rotate()` durably revokes the jti the live Secret's `prevJtiKey` already names before overwriting that slot (aborting before the patch when the revoke fails), and the rule that `Rotate()` runs its whole read-modify-write under a per-subject **session-scoped** Postgres advisory lock held across the K8s Secret patch and the separate store transactions so concurrent rotations cannot interleave, so a second rotation running before the sweep fires — whether a sequential crash-then-retry or a concurrent rotation — cannot strand a predecessor and §13.3:599/601 and §17.6:507 hold with the residual bounded to the sweep interval. The single `prevJtiKey` slot is overwritable (the Secret patch is a full-map replace, `k8ssecret.go:70`), so without the revoke-before-overwrite ordering a sequential crash-then-retry rotation that fires before the sweep would overwrite the orphaned predecessor's name and leave it revoked nowhere, and without the per-subject advisory lock two concurrent rotations would each blind-overwrite the Secret and drop the other's just-installed successor jti, named nowhere; either way the orphan validates indefinitely against the ~10-year `DefaultTokenTTL`. The revoke-before-overwrite ordering closes the sequential leak and the per-subject **session-scoped** advisory lock closes the concurrent one. The lock must span the whole `Rotate()` sequence, which is not a single Postgres transaction (it interleaves the K8s Secret read-modify-write with the `Record`/`RecordWithAudit`/`Revoke` store calls, each its own `pgtenant.InTx`, `pgtenant.go:76-100`), so a transaction-scoped `pg_advisory_xact_lock` (which releases at the COMMIT of the single transaction that took it) cannot serialize it; the gateway's `sessionstore/pgstore.go:750` and `auditstore/lock.go:180` idioms hold `pg_advisory_xact_lock` for a single transaction that does all its work inside that transaction, which is correct there but insufficient here. Serialization is the architecturally best guard for this path: it reuses the session-scoped advisory-lock idiom already present in the gateway (`saltlockpg`) rather than introducing the first `RetryOnConflict` on the Secret (which would guard only the Secret write and not the cross-transaction record-then-revoke invariant) or a new Postgres marker column and migration, and it mirrors the §13.3:605 advisory-locked concurrent-rotation discipline the spec already mandates for the other rotation flow.
