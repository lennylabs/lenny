# Proposal: Implement the concrete Kata guest-restart VMRestarter behind the §5.2 scrub step-7 seam, wiring the vm-restart scrub profile so a sequential-reuse microvm pool restarts its guest and reports success instead of fail-closing

- **Status:** Verified (2026-07-02). Converged after 4 adversarial review rounds (4 findings fixed); awaiting sign-off.
- **Date:** 2026-07-02.
- **Scope:** A change against the already-committed §5.2 step 7 and the `vm-restart` scrub profile whose C1 and C2 are implementation-only and whose C3 additionally requires a §13.2/§10.3 spec edit through the proposal pipeline (Open decision 1). It adds the concrete `VMRestarter` the existing scrub seam has never had (**C1**), activates it at adapter `Server` construction so proposal 0031's C-A2 driver reports a successful restart for reuse while withholding the report fail-closed on a failed or timed-out restart on a `vm-restart` pool (**C2**), wires the node-access and adapter identity that let a guest-resident adapter reach the Kata VM lifecycle API (**C3**, gated on Open decision 1), and adds the tier-1, tier-6, and driver-wiring tests (**C4**). It touches a new `pkg/adapter/kata/` package, the adapter `Server` construction site (`pkg/adapter/gatewaylink.go` / `cmd/lenny-adapter`), the chart node-access surface under `charts/`, and the tests. C1 and C2 stage **no** spec change: §5.2 step 7 and the `standard`/`vm-restart`/`in-place` profile enum are complete (`spec/05_runtime-registry-and-pool-model.md:473-477,:500`) and were confirmed against the spec. C3 is different. Every node-access model requires a §13.2/§10.3 spec edit before the charts can render it, because the spec forbids agent-pod node and host access categorically: the `default-deny-all` NetworkPolicy is rendered into every agent namespace including `lenny-agents-kata` and the base egress policy allows only the gRPC control channel on port 50051 and DNS (`spec/13_security-model.md:35,:78`), the `POD_SPEC_HOST_SHARING_FORBIDDEN` admission rule and the startup preflight forbid host sharing on every Lenny pod template (`spec/13_security-model.md:23`), and the agent-pod ServiceAccount has zero RBAC bindings with admission-time enforcement (`spec/10_gateway-internals.md:334,:336`). That spec impact is carried in Open decision 1 and must land through the proposal pipeline before C3's charts are staged, per spec-driven-development.md. Proposal 0031 (Approved 2026-07-02) is a hard prerequisite: it lands the `scrub.Run` production caller, the `RecycleScrub` sub-message, and the C-A2 adapter driver this change activates. The concrete transport (the Kata endpoint and protocol), the guest/host node-access model, and the adapter identity and sandbox-ID discovery are three genuine architecture and security decisions carried in Open decisions for review; implementation proceeds after the reviewer resolves them, and the tier-6 exercise requires an operator-provisioned Kata RuntimeClass (NEEDS-OPERATOR). Until the concrete client lands, a `vm-restart` pool at occupancy zero remains retired fail-closed by the gateway missing-report timeout, the current posture.

This document stages the proposed code and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

§5.2 fully defines the `vm-restart` scrub profile and step 7. On a cross-tenant sequential-reuse microvm pool (`isolationProfile: microvm`, `maxConcurrentSessions: 1`, `recycle.enabled: true`, `recycle.allowCrossTenantReuse: true`), after scrub steps 0-6 the adapter "requests a full guest VM restart via the Kata runtime's VM lifecycle API" and re-executes the step-6 verification once the fresh guest boots (`spec/05_runtime-registry-and-pool-model.md:473-477`). The profile is selected by `recycle.scrubProfile`, and the `microvm` isolation profile maps to the `kata` RuntimeClass (`spec/05_runtime-registry-and-pool-model.md:670`).

The code seam exists and fail-closes. `pkg/adapter/scrub/scrub.go` declares the `VMRestarter` interface with `RestartGuest(ctx)` (`:99-101`). `Run` records `cfg.Restarter.RestartGuest(ctx)` as the non-skipped `StepGuestRestart` step and re-runs the step-6 verification when `cfg.MicrovmRestart` is set (`:277-280`). A `var ErrNoRestarter` guard returns before step 0 when `MicrovmRestart` is set with a nil `Restarter` (`:220`, `:236-237`).

The only implementer in the tree is `fakeRestarter` in `pkg/adapter/scrub/scrub_test.go:327-335`. A tree-wide search for `RestartGuest` implementations returns only `scrub.go` (the interface) and `scrub_test.go`. No concrete Kata VM-lifecycle client exists. The remaining `kata` references are node-pool scheduling and isolation (`pkg/controller/sandbox/podspec/podspec.go:983-1015`, `applyKataNodeIsolation`), the `microvm → kata` RuntimeClass name (`pkg/sandbox/isolation/profile.go:95`), and the §17.2 privilege-escalation relaxation (`pkg/podsecurity/podsecurity.go:152-186`). None reaches a Kata VM lifecycle endpoint.

Consequently a `vm-restart` pool reaching occupancy zero cannot complete step 7. Proposal 0031's C-A2 adapter driver constructs `scrub.Config` with `MicrovmRestart: true` and a nil `Restarter` for a `vm-restart` pool, so `scrub.Run` returns `ErrNoRestarter`; the driver withholds the `ReportPodScrub` on that error, and the gateway missing-report timeout retires the pod (`pkg/gateway/session/recycle/recycleboundary.go`, keyed on `cleanupTimeoutSeconds` plus a grace period). Cross-tenant sequential reuse through `vm-restart` is therefore unavailable until a concrete restarter lands. The restarter-free `in-place` profile, which runs only steps 0-6 with `MicrovmRestart` false, remains available and provides cross-tenant sequential reuse without a guest restart (`spec/05_runtime-registry-and-pool-model.md:477`).

Failure semantics need a new fail-closed disposition for the runtime-restart-failure path, which does not exist today. A failed or timed-out `RestartGuest` is recorded as a non-skipped `StepGuestRestart` step that sets `Result = Failed` (`scrub.go:208-215`, `:282-284`), and `Run` returns `(Report{Result: Failed}, nil)` with a nil error (`scrub.go:277-285`). With the concrete restarter wired (C2), that nil-error `Failed` report is no longer the `ErrNoRestarter` case 0031's driver withholds on (the guard fires only when `Restarter == nil`, `scrub.go:236-237`); the driver instead calls `scrubOutcome` and emits `PodScrubFailed`. `podscrub.Decide` then runs under the default `warn` policy, where a single `ScrubFailed` below `maxScrubFailures` (default 3) falls through to `NextPhase: state.Reserved` or `state.SDKConnecting` with `Reason: ReasonReuse` rather than retiring (`podscrub.go:263-291`, `:338-357`), and `poolstore.validateRecyclePolicy` never forces `onScrubFailure: fail` for `allowCrossTenantReuse`/`vm-restart` pools (`poolstore.go:567-598`). On an `allowCrossTenantReuse` `vm-restart` pool the pin releases to `unassigned` (`spec/05_runtime-registry-and-pool-model.md:445`) and the pod is reused across tenants without a completed guest restart, up to `maxScrubFailures` times before retirement, leaking the guest-kernel residual state (DNS cache, TCP `TIME_WAIT`, page cache, inotify registrations) the profile exists to defeat. A failed or timed-out guest restart on a cross-tenant `vm-restart` pool must therefore be treated fail-closed exactly like the nil-restarter case: the adapter driver withholds `ReportPodScrub` so the gateway missing-report timeout retires the pod and never cross-tenant-reuses it without a completed restart. The disposition of a failed guest restart on a cross-tenant pool is arguably not settled by the spec and is carried as Open decision 4.

This is the residual of **F-5.2.15** (`BUILD-GAPS.md:3885`, "Kata/microvm scrub variant (step 7) is not implemented", DEFERRED / NEEDS-OPERATOR). Proposal 0031 closed F-5.2.15's session-mode wiring and filed the concrete Kata `VMRestarter` as a standalone implementation-only follow-on, NEEDS-OPERATOR (Kata RuntimeClass); this proposal implements that follow-on. The spec is silent on the concrete mechanism (the client library, the control socket, the node discovery, and the adapter identity and permission used to reach the Kata VM lifecycle API). That silence is genuine and is why the concrete transport (C1) and its activation (C2) are implementation-only rather than a spec gap. The node-access authorization surface C3 stages is a separate matter: the spec does not merely omit a path to the Kata endpoint, it forbids agent-pod node and host access categorically (`spec/13_security-model.md:23,:35,:78`, `spec/10_gateway-internals.md:334,:336`), so C3 requires a §13.2/§10.3 spec edit through the proposal pipeline (Open decision 1) rather than a pure chart edit.

## 2. Decisions

- **Implement behind the existing seam rather than a parallel one.** The concrete client implements the already-shipped `scrub.VMRestarter` interface (`scrub.go:99-101`) and is passed as `scrub.Config.Restarter` with `MicrovmRestart: true`. `scrub.Run` and `ErrNoRestarter` are unchanged, and the `StepGuestRestart` failure recording (an error yields `Result = Failed`, `scrub.go:282-284`) is reused. The disposition of that `Failed` result is not reused unchanged: the adapter driver (0031's `startPodScrub`) gains a fail-closed branch that withholds `ReportPodScrub` on a `Result == Failed` scrub for a cross-tenant `vm-restart` pool, so the gateway missing-report timeout retires the pod rather than the default `warn` policy cross-tenant-reusing it (see §1 and Open decision 4).
- **Activate the restarter at adapter `Server` construction rather than adding a new call site.** Proposal 0031's C-A2 driver already reads `cfg.Restarter = s.VMRestarter` (0031's C-A2 code, the `s.VMRestarter` field commented "nil until the Kata client lands"). Populating that field with `kata.NewRestarter(...)` at construction routes the concrete restarter through the existing driver with no edit to the `podscrub.go` branch logic.
- **Keep the fail-closed backstop.** The `podscrub.go` `ErrNoRestarter` withholding path and the `scrub.go:236-237` guard both stay. If the restarter is nil or fails to construct on a `vm-restart` pool, the driver still withholds `ReportPodScrub` and the gateway missing-report timeout retires the pod, rather than emitting a report that `podscrub.Decide` would fail-open into a cross-tenant reuse under the default `warn` policy. Removing either guard would weaken the fail-closed default the project mandates on isolation paths.
- **0031 is a hard prerequisite.** `pkg/adapter/podscrub.go` does not exist, `scrub.Run` has zero production callers, no production code constructs `scrub.Config` or sets `MicrovmRestart`, and the `RecycleScrub` proto sub-message that delivers `scrubProfile` and `pod_id` to the adapter is absent from `schemas/lenny-adapter.proto`. Proposal 0031 must be implemented before or alongside this change; there is no seam to plug into otherwise.
- **Scope to the sequential-reuse microvm path only.** §5.2 permits cross-tenant reuse (and therefore `vm-restart`) only when `maxConcurrentSessions: 1` with `recycle.enabled: true` and `microvm` isolation (`spec/05_runtime-registry-and-pool-model.md:447`, `:517`). The concurrent-session occupancy-zero boundary is a separate 0031 follow-on. The concrete restarter is constructed by the session-mode driver alone.
- **No spec change for C1 and C2; C3 requires one.** §5.2 step 7 and the `vm-restart` profile are complete and were confirmed against `spec/05_runtime-registry-and-pool-model.md:473-477`. C1 and C2 are implementation-only against the committed spec; the mechanism the spec abstracts as "the Kata runtime's VM lifecycle API" is filled in by code and by operator-provisioned Kata infrastructure. C3 is not implementation-only. The spec forbids agent-pod node and host access categorically (`spec/13_security-model.md:23,:35,:78`, `spec/10_gateway-internals.md:334,:336`), so every node-access model requires a §13.2/§10.3 spec edit (a scoped host-socket-mount admission exception for Model 1, or a `kata-vm-restart` egress allowance for Model 2) that must land through the proposal pipeline before the charts render it (Open decision 1).
- **Failure recording is answerable from existing code; the disposition of a failed restart is not.** A failed or timed-out `RestartGuest` returns a wrapped error that `Run` records as a non-skipped `StepGuestRestart` step (`scrub.go:278`), forcing `Result = Failed` (`scrub.go:282-284`). The restarter needs a bounded context and a wrapped error. It does introduce new disposition logic: `Run` returns that `Failed` report with a nil error, so on a cross-tenant `vm-restart` pool the driver must withhold `ReportPodScrub` to keep the pod fail-closed, because the default `warn` policy in `podscrub.Decide` would otherwise reuse it across tenants without the guest restart (see §1 and Open decision 4).
- **The transport, node-access model, and identity are open architecture decisions.** The Kata endpoint and protocol, the guest-resident-adapter node-access model, and the adapter identity with sandbox-ID discovery are not implementation details the spec abstracts over. They determine whether the microvm guest/host boundary is weakened. They are carried in Open decisions for review and are resolved before C1 and C3 are implemented.
- **Test reach.** The change reaches tier 1 (restarter unit behavior against a fake Kata endpoint: success, error, and timeout, plus a `scrub.Run` drive with `MicrovmRestart: true`), tier 1/2 (adapter driver wiring: a `vm-restart` pool with a non-nil restarter emits `ReportPodScrub` and reuses, a nil restarter withholds, and a non-nil restarter whose `RestartGuest` fails or times out withholds so the pod is retired fail-closed), tier 9 (the C3 node-access authorization and isolation posture of the resolved Open decision 1 model), tier 5 (for Model 1 only, the admission and securityContext relaxation that permits the host control-socket mount), and tier 6 (Kata-node e2e, operator-provisioned). Kind cannot reproduce a Kata guest restart, so tier 6 is implemented and its operator dependency stated while the locally runnable tiers run, per the test-coverage escape hatch. The tier-9 and tier-5 cases are gated on the resolved Open decision 1 model and stated with their operator dependency the same way. Tier 10 is excluded (see Testing).

## 3. Node access, the seam, and failure semantics

The concrete restarter's contract is narrow: implement `RestartGuest(ctx context.Context) error` against a bounded context, return a wrapped error on failure or timeout, and return nil only when a fresh guest has booted. `Run` records the outcome as `StepGuestRestart` and re-runs the step-6 verification (`scrub.go:277-280`). Two gaps in the surrounding orchestration remain and are carried as Open decisions. First, a `Failed` result does not by itself retire the pod: with the concrete restarter wired, `Run` returns a nil-error `Failed` report, and the default `warn` policy in `podscrub.Decide` cross-tenant-reuses the pod rather than retiring it, so the driver must withhold `ReportPodScrub` on a failed restart to fail-close (Open decision 4). Second, the inline re-verify and the success report at `scrub.go:277-280` run in the adapter process the guest restart destroys, so the success path cannot complete in that process (Open decision 5).

The open architecture is how a guest-resident adapter reaches a node-side Kata VM lifecycle endpoint that lives outside the guest. The adapter runs as a sidecar inside the Kata guest; the VM lifecycle API that restarts that guest is a node-side control plane. Three models reach it with different guest/host boundary costs, and the choice defines the C3 chart access and the C1 transport:

1. **Host-mounted Kata control socket exposed into the microvm agent pod.** The adapter calls the shim management socket directly. This is the smallest code path and the largest boundary cost: it exposes a node-side control socket into the guest, which weakens the guest/host isolation the microvm profile exists to provide.
2. **A Lenny node-local privileged broker (DaemonSet) the adapter calls.** The adapter calls a node-local Lenny component over a narrow RPC, and that component drives the Kata shim. This preserves the guest boundary at the cost of a new node component and a new RPC surface.
3. **A gateway or controller-brokered restart.** A control-plane component drives the restart. This conflicts with the spec's "the adapter requests a full guest VM restart" phrasing (`spec/05_runtime-registry-and-pool-model.md:475`).

The concrete restarter is one concern in its own package (C1), the node access and identity are the deployment wiring (C3), and both are gated on Open decision 1. The `scrub` package stays transport-free and off-Linux testable, matching how it isolates host operations behind `Ops` today.

A distinct gap is which process survives the restart to complete the success path. `scrub.Run` is a single synchronous call in the adapter process: it calls `cfg.Restarter.RestartGuest(ctx)` and then inline calls `rep.verify(ops, cfg)` (`scrub.go:277-280`), after which 0031's driver in the same process emits `ReportPodScrub`. A full guest VM restart shuts the guest kernel down and boots a fresh guest from the original VM image (`spec/05_runtime-registry-and-pool-model.md:475`), which destroys the guest-resident adapter process blocked in `RestartGuest`. That process cannot receive a nil "fresh guest booted" return, cannot run the inline re-verify, and cannot emit the success `ReportPodScrub`; the gateway observes the connection drop and the missing-report timeout retires the pod (`recycleboundary.go:24-31`), so the success path is unreachable in the in-guest process. Which process runs the post-restart re-verify and produces the success report is carried as Open decision 5. This gap blocks only the success path; the fail-closed retirement path (Open decision 4) is unaffected.

The guest restart adds latency (the spec cites 3-8 seconds, `spec/05_runtime-registry-and-pool-model.md:475`). Whether that latency needs a restart-specific timeout distinct from the gateway missing-report window is carried as Open decision 3, because a slow-but-successful restart must not be retired by the timeout before `ReportPodScrub` arrives.

## 4. Proposed changes

### C1. Add the concrete Kata `VMRestarter` implementing `scrub.VMRestarter`

**Target:** a new `pkg/adapter/kata/restarter.go`, implementing the `scrub.VMRestarter` seam (`pkg/adapter/scrub/scrub.go:95-101`).

**Precondition:** the transport (the concrete Kata endpoint and protocol), the node-access model (Open decision 1), the adapter identity and sandbox-ID discovery (Open decision 2), and the process-survival model for the post-restart re-verify and success report (Open decision 5) are resolved before this change is implemented. As drafted with those decisions open, C1 would add a thin wrapper plus a second empty consumer-side seam and leave the pool fail-closing; the concrete `RestartGuest` body is written once the transport is resolved rather than ahead of it.

**Change (once the decisions resolve):** add a `Restarter` type in `pkg/adapter/kata` whose `RestartGuest(ctx context.Context) error` drives the resolved Kata VM lifecycle endpoint for the pod's sandbox ID, honoring the passed context's deadline, and returns a wrapped error on failure or timeout:

**Rationale:** the seam has no concrete implementer; the only `RestartGuest` is `fakeRestarter` (`scrub_test.go:332`). A dedicated `pkg/adapter/kata` package keeps the Kata transport isolated behind the interface, matching how `pkg/adapter/scrub` isolates host operations behind `Ops`, and satisfies the one-concern-per-package rule. Placing it outside `scrub` keeps `scrub` transport-free and off-Linux testable. ### C2. Activate the restarter at adapter `Server` construction and fail-close a failed restart

**Target:** the adapter `Server` construction site that proposal 0031's C-A2 introduces (`pkg/adapter/gatewaylink.go` `ConnectGateway` / `cmd/lenny-adapter`), which already carries the `s.VMRestarter` field the C-A2 driver reads, and 0031's `startPodScrub` driver in `pkg/adapter/podscrub.go`, which gains a fail-closed withhold branch. The `scrub.go:236-237` guard and the existing `ErrNoRestarter` withholding path are kept unchanged.

**Change (a): assign the concrete restarter to the existing `Server` field at construction.**

```go
// s.VMRestarter was nil until the Kata client landed (see proposal 0031 C-A2);
// populate it so the C-A2 driver routes cfg.Restarter to the concrete restarter
// for a vm-restart pool. A nil VMRestarter still leaves the driver withholding
// ReportPodScrub on scrub.ErrNoRestarter, the fail-closed backstop.
s.VMRestarter = kata.NewRestarter(/* resolved endpoint, identity, discovery */)
```

The existing driver line `cfg.Restarter = s.VMRestarter` then routes the concrete restarter. This assignment may fold into C3, since C3 already touches the same construction and identity-access site, or remain a one-line assignment.

**Change (b): withhold `ReportPodScrub` when the guest restart fails on a cross-tenant `vm-restart` pool.** With a non-nil restarter, `scrub.Run` no longer returns `ErrNoRestarter` on a failed restart; it returns a `Result == Failed` report with a nil error (`scrub.go:277-285`), which the current `startPodScrub` reports as `PodScrubFailed` and the default `warn` policy cross-tenant-reuses. The driver gains a branch that withholds the report on a `Result == Failed` scrub for a `MicrovmRestart`/`vm-restart` pool, so the gateway missing-report timeout retires the pod:

```go
// A failed or timed-out guest restart on a vm-restart pool leaves the guest
// dirty. Reporting PodScrubFailed would let podscrub.Decide reuse the pod
// across tenants under the default warn policy without the completed restart,
// a fail-open cross-tenant-reuse regression. Withhold the report so the gateway
// missing-report timeout retires the pod, the same fail-closed posture the
// nil-restarter (ErrNoRestarter) case already holds. See Open decision 4.
if cfg.MicrovmRestart && rep.Result == scrub.Failed {
    slog.Warn("adapter: vm-restart guest restart failed; withholding report so the pod is retired", "pod", rc.GetPodId())
    return
}
```

**Do not** remove either fail-closed path. The `ErrNoRestarter` withholding (a nil restarter) and the new `Result == Failed` withholding (a failed restart) are both retained, symmetric with keeping the `scrub.go:236-237` guard: on a `vm-restart` pool the driver withholds `ReportPodScrub` and the missing-report timeout retires the pod, rather than emitting a report that `podscrub.Decide` under the default `warn` policy would fail-open into a cross-tenant reuse without the guest restart.

**Rationale:** the field assignment activates C1 through the injection point 0031 already built (`cfg.Restarter = s.VMRestarter`). The withhold branch is the smallest fail-closed fix for the runtime-restart-failure path and reuses 0031's existing withhold-on-`ErrNoRestarter` posture rather than inventing a new disposition: it lives in the adapter driver, so `scrub.Run` and `podscrub.Decide` stay unchanged, and it does not force `onScrubFailure: fail` on operator-configured `warn` pools. 0031's convergence record established that emitting any `ReportPodScrub` that resolves to `Failed` for a `vm-restart` pool is a fail-open cross-tenant-reuse regression, because `podscrub.Decide` under the default `warn` policy returns the pod to the pool without the guest VM restart (`pkg/sandbox/podscrub/podscrub.go`; `poolstore.go` does not force `onScrubFailure: fail`, `poolstore.go:567-598`). Whether the disposition of a failed guest restart on a cross-tenant pool belongs in the driver, in a `poolstore` policy floor, or in `podscrub.Decide` is arguably not settled by the spec and is carried as Open decision 4; the driver withhold is the option most consistent with 0031's fail-closed precedent.

### C3. Wire the node access and adapter identity that let the guest-resident adapter reach the Kata VM lifecycle API

**Target:** the adapter `Server` construction and gateway-connect site (`pkg/adapter/gatewaylink.go` / `cmd/lenny-adapter`) and the chart node-access surface under `charts/` (the microvm agent pod's access to the resolved Kata endpoint, the adapter ServiceAccount and permission, and sandbox-ID discovery).

**Precondition:** Open decision 1 (node-access model) and Open decision 2 (endpoint, protocol, identity, and sandbox-ID discovery) are resolved first. The concrete access surface follows the resolved model:

- Model 1 (host-mounted control socket) stages a `hostPath` or CSI mount of the Kata control socket into the microvm agent pod, plus the securityContext and admission changes that permit it. This weakens the guest/host boundary and is the reviewer's call to accept.
- Model 2 (node-local privileged broker) stages a DaemonSet, its RBAC, and a narrow adapter-to-broker RPC, and grants the adapter only the identity needed to call the broker.
- Model 3 (control-plane-brokered) stages no adapter-side node access and instead conflicts with the "the adapter requests" spec phrasing, and is recorded against Open decision 1.

**Spec impact.** C3 is not implementation-only against the committed spec, unlike C1 and C2. The spec forbids agent-pod node and host access categorically: the `default-deny-all` NetworkPolicy and the base egress policy that allows only the gRPC control channel on port 50051 and DNS are rendered into every agent namespace including `lenny-agents-kata` (`spec/13_security-model.md:35,:78`), the `POD_SPEC_HOST_SHARING_FORBIDDEN` admission rule and the startup preflight forbid host sharing on every Lenny pod template (`spec/13_security-model.md:23`), and the agent-pod ServiceAccount has zero RBAC bindings with admission-time enforcement in the `lenny-agents` and `lenny-agents-kata` namespaces (`spec/10_gateway-internals.md:334,:336`). Model 1's host control-socket mount plus its "admission changes that permit it" require a scoped host-socket-mount admission exception in §13.2 (and a matching §17.2 admission-inventory entry). Model 2's new adapter-to-broker egress requires a §13.2 egress-table allowance beyond port 50051 and DNS. Every viable model therefore requires a §13.2/§10.3 (and likely §17.2) spec edit before the charts can render it. Per spec-driven-development.md, that spec edit lands through the proposal pipeline and is verified before C3's charts are staged; it is carried as Open decision 1 rather than being staged here.

**Change:** once Open decision 1 resolves and its §13.2/§10.3 spec edit lands, stage the resolved model's chart access, the adapter ServiceAccount and permission to reach the endpoint, and the sandbox-ID discovery the `kata.NewRestarter` constructor consumes. The concrete manifests and identity are pinned once Open decisions 1 and 2 resolve.

**Rationale:** C1's `RestartGuest` cannot reach a node-side endpoint from inside the guest without an access path, and that path is the security-relevant surface of this change. Separating it from C1 keeps the transport code and the deployment access reviewable independently, and keeps the boundary cost explicit for the reviewer. C3 is the wiring that makes C2's field assignment reach a live endpoint.

### C4. Tests: unit restarter behavior, driver wiring, and Kata-node e2e

**Target:** a new `pkg/adapter/kata/restarter_test.go` (tier 1); `pkg/adapter/podscrub_test.go` (tier 1/2, driver wiring; the file proposal 0031 lands); a tier-9 isolation/security test and, for Model 1, a tier-5 admission test under the resolved Open decision 1 model (both gated on that decision and operator-provisioned); a tier-6 Kata-node e2e under `tests/tier6_e2e_cloud/` (operator-provisioned). See Testing for the specific cases. Tier 10 is excluded: the `vm-restart` scrub is not part of the runtime integration-level conformance battery `cmd/lenny-compliance` runs, and a guest restart requires a Kata node, which is tier 6.

**Rationale:** the change adds new production code (the concrete restarter, its activation, the fail-closed withhold branch, and the node access), so the test-coverage rule requires tests on every touched package. The non-happy paths (restart error and timeout mapping to a fail-closed retirement) matter because the failure mapping is the fail-closed behavior. C3 grants a zero-RBAC agent pod a new authorization and egress path to a node-side endpoint, which reaches tier 9 (authorization, isolation, egress) and, for Model 1, tier 5 (admission and securityContext), per `test-coverage.md`. - **Does not wire the concurrent-session (`maxConcurrentSessions > 1`) occupancy-zero boundary.** `vm-restart` applies only to the sequential-reuse path (`spec/05_runtime-registry-and-pool-model.md:517`); the concurrent boundary is a separate 0031 follow-on.

- **Does not remove or weaken the fail-closed withholding path.** The `ErrNoRestarter` withholding and the `scrub.go:236-237` guard are retained as the backstop for a nil or failed-to-construct restarter, and the withholding is extended to a failed or timed-out guest restart on a cross-tenant `vm-restart` pool (Open decision 4).
- **Does not add a tier-10 conformance fixture.** The runtime-adapter conformance battery does not cover the scrub or recycle surface; the concrete restart is tier 6.

## 8. Resolved in adversarial review

Adversarial review rounds populate this section as they run. The following scoping revisions are already baked into the staged changes:

- **C1 is sequenced after the Open decisions rather than landed as an implementation-only change while the transport is undecided.** As drafted with the transport, node-access model, and identity open, "add the concrete VMRestarter" would produce a thin wrapper plus a second empty consumer-side seam and leave the pool fail-closing. The three architecture and security decisions are carried in Open decisions for review, and C1's `RestartGuest` body is written against the resolved transport.
- **C2 populates the `s.VMRestarter` field and adds a fail-closed withhold branch for a failed restart.** It populates the existing `s.VMRestarter` field 0031's C-A2 introduced and keeps the `ErrNoRestarter` withholding path (a nil restarter) and the `scrub.go:236-237` guard. It adds a driver branch that withholds `ReportPodScrub` on a `Result == Failed` scrub for a `vm-restart` pool, because with the concrete restarter wired a failed restart is no longer the `ErrNoRestarter` case; without that branch the default `warn` policy in `podscrub.Decide` would cross-tenant-reuse the pod without a completed guest restart (Open decision 4).
- **C4 drops the tier-10 conformance element.** The `vm-restart` scrub is not part of the runtime integration-level conformance battery `cmd/lenny-compliance` runs; a fake-restarter fixture there would duplicate tier 1, and a guest restart requires a Kata node, which is tier 6. The Gateway-to-Adapter scrub wire contract has its canonical home in tier 3 (`tests/tier3_contract/gatewaycontrol_scrub/scrub_wire_test.go`, owned by proposal 0031).

## 9. Open decisions for review

- **Node-access architecture for the adapter to reach the Kata VM lifecycle API.** The adapter is a sidecar inside the Kata guest; a node-side VM lifecycle endpoint lives outside the guest. The options are (a) a host-mounted Kata control socket exposed into the microvm agent pod, which weakens the guest/host boundary the microvm profile exists to provide; (b) a Lenny node-local privileged broker (DaemonSet) the adapter calls, which drives the Kata shim and preserves the guest boundary at the cost of a new node component and RPC surface; and (c) a gateway or controller-brokered restart, which conflicts with the spec's "the adapter requests" phrasing (`spec/05_runtime-registry-and-pool-model.md:475`). This is a security and isolation decision for the reviewer, and it defines the C3 chart access. **Resolving it requires a §13.2/§10.3 spec change through the proposal pipeline before the C3 charts are staged, rather than a pure chart edit.** The spec forbids agent-pod node and host access categorically: the `default-deny-all` NetworkPolicy and the base egress policy that allows only the gRPC control channel on port 50051 and DNS cover every agent namespace including `lenny-agents-kata` (`spec/13_security-model.md:35,:78`), the `POD_SPEC_HOST_SHARING_FORBIDDEN` admission rule and the startup preflight forbid host sharing on every Lenny pod template (`spec/13_security-model.md:23`), and the agent-pod ServiceAccount has zero RBAC bindings with admission-time enforcement (`spec/10_gateway-internals.md:334,:336`). Model (a) requires a scoped host-socket-mount admission exception in §13.2 and a matching §17.2 admission-inventory entry; model (b) requires a new `kata-vm-restart` egress allowance in the §13.2 egress table beyond port 50051 and DNS. Whichever model the reviewer selects, its spec edit lands and is verified through the proposal pipeline before C3's charts render it.
- **The concrete Kata VM lifecycle endpoint and protocol, and the adapter identity model.** Pin the endpoint and protocol to the deployed Kata version (the containerd-shim-v2 management socket, the kata-runtime sandbox lifecycle, or a CRI sandbox recreate), and pin the adapter identity and permission (ServiceAccount, sandbox-ID discovery) used to reach it. The spec abstracts this as "the Kata runtime's VM lifecycle API" (`spec/05_runtime-registry-and-pool-model.md:475`) and names no concrete surface.
- **Restart-latency timeout.** The guest restart adds latency (the spec cites 3-8 seconds, `spec/05_runtime-registry-and-pool-model.md:475`). Decide whether a restart-specific timeout distinct from the gateway missing-report window (`cleanupTimeoutSeconds` plus grace, `pkg/gateway/session/recycle/recycleboundary.go`) is needed so a slow-but-successful restart is not retired by the timeout before `ReportPodScrub` arrives.
- **Disposition of a failed or timed-out guest restart on a cross-tenant `vm-restart` pool.** With the concrete restarter wired, `scrub.Run` returns a `Result == Failed` report with a nil error on a failed restart (`scrub.go:277-285`); the current driver reports `PodScrubFailed`, and under the default `warn` policy `podscrub.Decide` cross-tenant-reuses the pod up to `maxScrubFailures` (default 3) rather than retiring it (`podscrub.go:263-291`, `:338-357`), because `poolstore.validateRecyclePolicy` does not force `onScrubFailure: fail` for `allowCrossTenantReuse`/`vm-restart` pools (`poolstore.go:567-598`). The spec is arguably silent on this disposition: it defines the retirement path for a repeated scrub failure (`spec/05_runtime-registry-and-pool-model.md:481`) but does not state that a single failed guest restart on a cross-tenant pool must retire fail-closed. The options are (a) the adapter driver withholds `ReportPodScrub` on a `Result == Failed` scrub for a `vm-restart` pool so the gateway missing-report timeout retires the pod, reusing 0031's withhold-on-`ErrNoRestarter` posture (C2 change (b), the recommended path); (b) `poolstore` forces `onScrubFailure: fail` for `allowCrossTenantReuse`/`vm-restart` pools, which overrides an operator's `warn` choice; or (c) `podscrub.Decide` special-cases a failed guest restart to retire. C2 stages option (a) as the smallest change consistent with the existing fail-closed precedent; confirm the reviewer accepts it or selects (b) or (c).
- **Process survival for the post-restart re-verify and the success report.** `scrub.Run` runs the inline re-verify and 0031's driver emits the success `ReportPodScrub` in the guest-resident adapter process, which the full guest VM restart destroys (`spec/05_runtime-registry-and-pool-model.md:475`; `scrub.go:277-280`). The success path therefore cannot complete in that process, and the gateway missing-report timeout would retire even a successful restart (`recycleboundary.go:24-31`). Decide which process runs the post-restart step-6 re-verify and produces the success report: (a) a node-side survivor (the Model 2 broker or a controller) drives the restart and reports on the adapter's behalf; (b) a fresh in-guest adapter re-runs step-6 verification and reports after the reboot; or (c) the disposition treats a completed-restart-then-reconnect distinctly from a scrub failure. This decision interacts with Open decision 1 (Model 2's node-local broker is a natural survivor) and, if the success path moves off `scrub.Run`, revises the "No change to `scrub.Run`" Non-goal. It blocks only the success path; the fail-closed retirement path (Open decision 4) is unaffected.
