## 1. Problem

The §4.6.1 coordinator-direct eviction route is described in spec (`spec/04_system-components.md:489`, landed by prereq 2 / proposal 0052) but no code drives it, and the mechanism it needs to survive the default sidecar deployment model does not exist. Four facts define the build.

**1. No individual agent-pod eviction fires a checkpoint.** `checkpoint.TriggerEviction` is driven only on the gateway pod's own §10.1 preStop barrier fan-out (`pkg/gateway/coordination/barrier/barrier.go:228`, reached only from the gateway preStop handler), never on an individual agent-pod eviction. The agent-pod preStop `runPreStop` (`cmd/lenny-adapter/prestop.go`) SIGTERMs the local adapter and polls for its exit; the adapter SIGTERM handler (`cmd/lenny-adapter/main.go:411-425`) runs `ShutdownDemoteSDK`, `lifecycle.Close()`, and `srv.GracefulStop()` and emits no eviction signal to any gateway replica. The `Checkpoint` RPC is gateway-driven, so the pod cannot open it itself (`spec/04_system-components.md:489`). This is the C-22 eviction trigger, finding T-4.4.14.

**2. Runtime-container quiescence race in the default sidecar model.** In the default sidecar model the third-party `runtime` container carries no `Lifecycle`/preStop; only the adapter container carries the preStop drain hook. `RestartPolicy` is `Never` with no native-sidecar `InitContainer` ordering, so on kubelet termination the hookless runtime is SIGTERMed at `t=0` while the adapter's SIGTERM is deferred behind its preStop. The Full-level eviction checkpoint gates its archive on the live-runtime cooperative quiesce handshake `s.Lifecycle.RequestCheckpoint(...)` (`pkg/adapter/checkpoint.go:158-160`), which returns `codes.Internal "checkpoint quiesce handshake"` before `streamChunks`/`ArchiveTree` when the runtime's lifecycle connection has dropped. No pre-SIGTERM quiesce frame travels the kubelet path (`drainViaLifecycle`/`Terminate` fire only from the gateway `Shutdown` RPC handler; `SignalDeadlineApproaching` fires only from the `SignalDeadline` RPC), and `shareProcessNamespace` is prohibited (`spec/13_security-model.md` §13.1, `spec/04_system-components.md:243`). A SIGTERM-honoring runtime therefore exits before the eviction `checkpoint_request` reaches it, the handshake fails, and the current fail-closed at `checkpoint.go:158-160` drops the session to the minimal-state fallback (`resumeMode: conversation_only`, `workspaceLost: true`, `spec/04_system-components.md:264`), losing the live-workspace emptyDir.

The workspace is a separate pod-scoped `emptyDir` mounted `/workspace/` into both containers (`spec/04_system-components.md:865` deployment-model bullet; podspec renders it read-write into the adapter container). Kubernetes clears an `emptyDir` on pod removal rather than on a single container's exit, so after the runtime container exits under SIGTERM the still-alive adapter container retains full read access to `/workspace` through the grace window. The adapter already archives the checkpoint from its own on-disk mount (`workspace.ArchiveTree`, `pkg/adapter/checkpoint.go:201`), rather than by streaming from the runtime process. A runtime that has exited is no longer writing to the workspace and is therefore already quiesced; the cooperative handshake adds only tool-call consistency, which the spec already relaxes for eviction checkpoints and for the SIGSTOP eviction path (`spec/04_system-components.md:242-243`).

**3. The deferred 0052 coordinator decisions.** Proposal 0052's sign-off resolved coordinator-direct as the seam and deferred the within-window forced takeover and the forward-to-holder transport to this proposal.

**4. The §4.4 doc-nit.** `spec/04_system-components.md:264` and `:278` justify the eviction retry budget with `terminationGracePeriodSeconds (240s at Tier 1/2, 300s at Tier 3)`, and `spec/17_deployment-topology.md:971` labels that row `terminationGracePeriodSeconds (gateway pod)`. The eviction-checkpoint bullet at `:264` is titled "Eviction checkpoints (preStop hook)" and justifies its budget with "(a) the pod is terminating regardless — there is no agent to resume" and a resume-on-fresh-pod fallback (`resumeMode: conversation_only`, `workspaceLost: true`), so it documents the agent-pod eviction path this proposal builds, rather than the gateway-drain barrier path (`barrier.go:228`), during which the agent pod keeps running and its session continues after coordinator handoff. The agent pod's grace default is 120s (`spec/04_system-components.md:489`). Citing the gateway pod's 240/300s grace on the agent-pod eviction bullet is therefore the doc-nit: the bound there is the agent pod's 120s grace. The 30s MinIO plus 60s Postgres budgets (90s worst case) fit within 120s, so the numbers are not unsafe, but the grace attribution at `:264`/`:278` is wrong and SPEC-3 corrects it.

Prereqs 1 (0050, slot-aware checkpointing), 2 (0052, coordinator-direct route text at `spec/04_system-components.md:489`), and 3 (0056, admission grace floor) are landed and consumed unchanged. The earlier seed hint that `triggerForSource` at `checkpointer.go:366` must be reconciled is obsolete: `git grep triggerForSource|snapshotWithTrigger` returns zero hits under `pkg/` and `cmd/`. The switch was already collapsed and the trigger threads as a direct parameter through the checkpoint-snapshot core (`Checkpointer.CheckpointWithTrigger`, `pkg/gateway/checkpoint/checkpointer/checkpointer.go:375`), so the individual-eviction drive passes `TriggerEviction` directly, and finding T-4.4.20's code half is already resolved. The eviction drive reuses that binding-gated entry point on the coordinator's held binding; that reconciliation is described in §3 and CODE-3.

## 2. Decisions

- **Coordinator-direct is the built seam, per 0052's sign-off.** The adapter, on kubelet-driven pod termination, emits a new `AdapterEvicting` adapter-to-gateway control event on the per-pod control channel; the session's coordinator (the `coordinator_replica` recorded in the `coordination_lease` mirror, [§10.1](../spec/10_gateway-internals.md)) drives the eviction `Checkpoint` RPC with `TriggerEviction` under a read-side check that the driving replica still holds the session's coordination lease. Under proposal 0060 that coordinator holds both the session's coordination lease and its pod binding, and the lease-holder check is what makes a coordinator superseded during a handoff hand the drive on to the replica that now holds the lease rather than overwrite a newer checkpoint. The replica whose per-pod control stream receives `AdapterEvicting` is not guaranteed to be that coordinator (see decision below and §3), so the receiving replica drives locally when it holds the session's binding and otherwise identifies the coordinator through the `coordination_lease` mirror and forwards the drive to that coordinator's recorded dialable inter-replica address, over an internal gateway-to-gateway control-forward RPC on a dedicated gateway inter-replica gRPC port that a new §13.2 and `charts/` NetworkPolicy self-peer admits (the shipped default-deny otherwise blocks the forward). The drive reuses the binding-gated `Checkpointer.CheckpointWithTrigger` (`checkpointer.go` → `snapshot` → `Registry.Get`) against the binding the coordinator already holds, because under proposal 0060 the coordinator is by construction the replica holding the session's in-memory binding. No gateway-side agent-pod informer is built (that seam was surfaced-and-deferred by 0052 and would need dedup and RBAC across every replica).
- **The bind path seeds the `coordination_lease` mirror so a session is resolvable before it can be evicted.** The `coordination_lease` mirror row (`coordinator_replica`) is written only by the periodic coordination Sweeper (`coordination.go:150` `upsertMirror`, default 15s interval), never at session bind (the session-start `registerBinding` and the snapshot-resume rebind write only the in-memory `podRegistry` binding, `start.go:2668` and `:3595`). A session evicted within the first sweep interval after it binds therefore has no `coordinator_replica` row, so mirror-only routing would resolve no coordinator and drive no checkpoint on a reachable path (node drain or spot reclaim shortly after scheduling), which is the silent workspace loss C-22 prevents. The seed therefore folds into 0060's `acquireCoordinationLease`, the at-bind lease acquire that already runs at every path publishing a live binding (`registerBinding`, and hoisted ahead of the running-commit on the single-call `/start`, delegated-child, and checkpoint-restore paths). That helper today calls `leasestore.Acquire` alone and writes no mirror row; extending it to also `coordlease.Store.Upsert` the binding replica as the session's initial `coordinator_replica` at the session's `coordination_generation` (a fresh row baselines to 1, matching `coordfence.go`) makes every live-bound session resolvable before the adapter can emit `AdapterEvicting` for it, including a session resumed from a checkpoint onto a fresh warm pod. Folding it into the existing helper rather than adding a parallel seed seam keeps the lease acquire and the mirror seed from drifting, since under co-location they name the same replica. 0060's rollback counterpart `releaseCoordinationLease` retracts the seeded row as well as the lease, so a bind whose running-commit fails leaves no active mirror row naming a replica that holds neither the lease nor the binding. Because `coordinator_replica` is an opaque OTel `service.instance.id` (`coordlease.go:50`) and not a dialable address, the seed also records the coordinator's dialable inter-replica address (`POD_IP` plus `interReplicaGRPCPort`) in a new `coordinator_address` mirror column, and a by-session mirror read returns both, so a replica that must forward has a routable target rather than only an identity. The seed stays all-or-nothing with the acquire: it runs after `leasestore.Acquire` inside the same helper, and a `coordlease.Store.Upsert` failure releases the lease this call just acquired before returning the error, so every existing caller's assumption that an acquire error means nothing is held stays true and no bind strands a held coordination lease with no binding. Under co-location the seeded replica is the lease holder, so the first coordination sweep confirms the seeded row rather than correcting it; a later handoff moves the binding and the lease together and overwrites both fields with the new coordinator and its address. The mirror's recorded coordinator is the binding holder in steady state, and it is a lagging projection of that fact: the sweep refreshes it on a 15s interval, the sweep's dead-connection eviction releases the lease and drops the binding without touching the row (`coordination.go:332-338` continues past the sole mirror write at `:447`), and `upsertMirror` swallows a Postgres error without retry (`coordination.go:565-576`), so a row can name a replica that holds neither the lease nor the binding for at least one sweep interval. The routing predicate is therefore keyed on the binding rather than on the record alone: the receiving replica drives locally whenever it holds the session's in-memory binding, and forwards only when it holds no binding and a different replica is the recorded coordinator.
- **The gateway-side control-stream consumer does not exist yet and is built here.** The `LifecycleChannel` control stream is served only on the adapter side (`pkg/adapter/controlchannel.go:90`); `AdapterTerminating` and `FINAL_USAGE_REPORT` are emit-only (`controlchannel.go:34,39`), and no gateway production code opens the client bidi stream or reads `LifecycleChannelResponse`. The earlier framing that the transport "already carries `AdapterTerminating`" to a gateway consumer is corrected: the gateway consumer (client stream open, receive loop, reconnect, and session and slot routing) is new code this proposal builds.
- **A new §4.7 control event is warranted rather than overloading `AdapterTerminating`.** `AdapterTerminating` is a terminal notification (`spec/04_system-components.md:688`, reason `coordinator_lost`) that transitions the session immediately without waiting for the orphan reconciler; its semantics are wrong for "drive an eviction checkpoint, then terminate". `AdapterEvicting` requests a checkpoint drive and survives the minimal-surface test because no existing control event carries that request.
- **The eviction drive lives in the adapter SIGTERM handler rather than a new local RPC.** On the kubelet path the adapter-container preStop runs before the adapter's SIGTERM, so the SIGTERM handler is where the adapter is still fully serving and can emit the eviction event, keep the gRPC server accepting the coordinator's `Checkpoint` RPC (defer `GracefulStop`), await completion of the eviction checkpoint(s) for its live bound sessions under a deadline, then tear down. When the adapter has no live bound session, it emits nothing and exits as today. The adapter observes checkpoint completion locally because it serves the `Checkpoint` RPC, so no gateway-to-adapter completion-ack frame is added.
- **The runtime-container quiescence race is resolved by a best-effort eviction snapshot rather than by keeping the runtime alive.** When this pod is itself terminating (the adapter's own SIGTERM/eviction handler has engaged, tracked by an in-process `evicting` flag the handler sets before it emits `AdapterEvicting`) and the cooperative `checkpoint_request`/`checkpoint_ready` handshake cannot complete because the runtime lifecycle connection has already dropped, the adapter archives the still-mounted `/workspace` emptyDir directly and records it as an ordinary workspace checkpoint, rather than returning `codes.Internal` and aborting to the minimal-state fallback. The downgrade is gated on the adapter's own termination state rather than on the `TriggerEviction` trigger value, because `TriggerEviction` is shared with the §10.1 gateway-drain barrier path (`barrier.go:228`), during which the agent pod keeps running and its session continues after coordinator handoff. Gating on the trigger alone would let a transient lifecycle-connection drop during a barrier fan-out silently downgrade a still-running session's checkpoint to best-effort. The adapter that serves the `Checkpoint` RPC derives the trigger solely from `CheckpointStart` (`checkpoint.go:128`) and cannot otherwise tell the two paths apart, so the local `evicting` flag is the authoritative "this pod is terminating" signal. The restored snapshot resumes as `resumeMode: full` with `workspaceLost: false`, indistinguishable at the wire from a cooperatively-quiesced checkpoint. No new per-checkpoint or per-resume consistency field is added: the adapter-to-gateway `Checkpoint` stream (`CheckpointStart`/`CheckpointSummary`, `schemas/lenny-adapter.proto:1101,1187`) carries no `consistency` field, neither the `checkpoint_manifest` (`migrations/0178_checkpoint_manifest.up.sql:30`) nor the `session_checkpoints` record persists one, and the §7.2 `session.resumed` event (`spec/07_session-lifecycle.md:138`) enumerates `resumeMode` as `full`, `conversation_only`, `partial_workspace`, or `coordinator_handoff` with a boolean `workspaceLost` and no consistency field. Surfacing a distinct best-effort marker would require a new proto field, a migration, a §7.2/§15 event-schema field, and SDK plus `docs/client-guide/wire-format.md` mirroring, which the minimal-surface principle rejects because the spec's existing best-effort model already relaxes tool-call consistency without a per-resume marker (`spec/04_system-components.md:242-243`). The eviction path carries the tool-call-consistency caveat the spec already documents. This resolves the same failure the runtime-hold would (total workspace loss) at a single code site, with no init container, no shared binary copy, no unix-socket hold, and no third-party runtime image change. The rejected runtime-hold and its own rejected sub-alternatives are recorded in Non-goals.
- **The embedded deployment model is unchanged.** It runs a single first-party container that carries the preStop and links the adapter, with no separate hookless runtime, so the ordering race does not arise. The embedded model reaches the same SIGTERM handler and benefits from the same eviction drive; the best-effort snapshot fallback is a no-op there because the embedded runtime's lifecycle connection does not drop out from under the adapter.
- **The unreachable-coordinator and any cross-replica residual is accepted; no forced-takeover primitive is built.** Per 0052's Non-goals and sign-off, a still-live coordination lease cannot be acquired by a non-holder without a forced-acquisition primitive the leasestore holder invariant forbids (`pkg/.../leasestore.go` holder invariant; `ErrHeld`). A coordinator unreachable within the grace window is recovered only by the existing §10.1 TTL-driven handoff (default 4×15s, which may outlast the window), and that residual session drops to the §4.4 minimal-state fallback. This preserves the leasestore holder invariant and the `shareProcessNamespace` prohibition unchanged.
- **The eviction drive reuses the binding-gated `CheckpointWithTrigger` on the coordinator's own held binding, gated by a read-side coordination-lease-holder check rather than by a second `CoordinatorFence`.** The eviction drive and the §10.1 gateway-drain barrier drive both carry `TriggerEviction`, so the §16.1 `lenny_checkpoint_duration_seconds{trigger=eviction}` label and the §4.4 eviction retry budget apply on both. Under proposal 0060 the session's coordinator is the replica holding its binding, so `Checkpointer.CheckpointWithTrigger` (`checkpointer.go` → `snapshot` → `Registry.Get`) resolves on the replica that holds the binding. The drive therefore reuses that entry point unchanged and drives the same checkpoint-snapshot core with `TriggerEviction`. It does not call `coordfence.Fencer.Fence`: that primitive announces a generation to the pod through the `CoordinatorFence` RPC, and the adapter rejects any fence whose generation is not strictly greater than the one it already recorded (`pkg/adapter/coordination.go:100-107`, doc comment at `:70-77`). On every path where this coordinator already fenced the pod (the checkpoint-restore resume at `pkg/gateway/sessionserver/start.go:3950-3956`, the snapshot-resume rebind, and 0060's fence-first re-adopt) the pod's last fenced generation equals the session's current `coordination_generation`, so the announcement would return `FailedPrecondition`, the Fencer would find no generation advance, and it would relinquish: release the session's coordination lease and return `ErrRelinquished` without driving (`coordfence.go:164-180`, `:196-199`). That would drop the eviction checkpoint on exactly the sessions the drive exists for and would leave this replica holding the binding with no lease, the decoupling 0060 removes. The drive is instead gated by a read-side check that announces nothing: this replica drives only while the authoritative coordination lease for the session is held by this replica or by nobody (`leasestore.Store.Get` returns a `Lease` whose `Holder` is this replica's id, `pkg/gateway/storage/leasestore/leasestore.go:70-74,182`). The read has a third outcome the check must name: `Get` returns `ErrNotFound` when no lease exists for the session at all (`leasestore.go:43`, `:180-186`, `:195-198`). That outcome is authorization rather than denial, because no competing coordinator exists and no newer checkpoint can be in flight. It is reachable on two ordinary states: a deployment wired without Redis, where `acquireCoordinationLease` no-ops (`pkg/gateway/sessionserver/start.go:2891-2893`) because the lease store is assigned only inside the Redis branch of the composition root (`cmd/lenny-gateway/stores.go:1390,1453,1466`) and the §17.4 dev preset ships `redis.deploy: false` (`charts/lenny/presets/dev.yaml:83-85`), so no session ever holds a lease; and the window after a Redis restart or failover loses the coordination keys, during which every bound session reads `ErrNotFound` until the next sweep re-acquires (`pkg/gateway/coordination/coordination/coordination.go:355-361`). Denying there would drop the eviction checkpoint on exactly the store-failover window the gate must survive. The lease-absent outcome is made race-safe without a forced acquisition: the replica calls `leasestore.Store.Acquire(ctx, tenant, session, this replica, coordLeaseTTL)` for itself, drives when the acquire succeeds, forwards when it returns `ErrHeld`, and drives on any other `Acquire` error (`leasestore.go:134-137` returns the raw store error, distinct from the `ErrHeld` return at `:138-140`), because that error is the same unreachable coordination store the read-side transport-error branch fails open on, logged at warn level with tenant, session, and slot. `Acquire` is idempotent for the same holder and refuses a live foreign holder (`leasestore.go:125-146`), so the leasestore holder invariant is preserved. A nil lease store or an empty replica id is treated the same way, mirroring the no-op guard `acquireCoordinationLease` already applies to that posture. A transport error from the read authorizes the binding holder directly without the acquire, which would run against the same unreachable store (`leasestore.go:188-190`), because denying on an unreadable lease store would drop the eviction checkpoint for the duration of a coordination-store outage while the residual is at worst a checkpoint superseded by a concurrent holder's own archive. When the lease is held by a peer the replica archives no checkpoint and releases no lease, and it re-reads the mirror and forwards the eviction-drive request to the replica the record now names, which under co-location holds both the lease and the binding. The deny direction forwards rather than returning, because a replica can hold a stale in-memory binding for a session whose lease and re-adopted binding have moved: the sweep evicts a binding only on the dead-connection branch (`pkg/gateway/coordination/coordination/coordination.go:332-338`), and on a live connection whose lease a peer now holds the `Acquire` returns `ErrHeld` and the sweep continues with the binding still published (`:352-360`). A bare return on that state would drop the eviction checkpoint on a replica that could have routed it, which is the C-22 workspace loss, and the current holder has written no newer checkpoint for the deny to protect. Forwarding makes a coordinator superseded during a handoff neither overwrite a newer checkpoint nor drop the eviction checkpoint. When the re-read still names this replica, or the forward fails, the drop is logged at error level with tenant, session, and slot on the same observability path as the unreachable-coordinator residual. The check does not compare the mirror's `coordination_generation`. The mirror's generation is not a record of what the current coordinator observed: in one sweep iteration the row comes from the pre-bump `sessions.List` snapshot (`pkg/gateway/coordination/coordination/coordination.go:288-291`), `RecordHandoff` bumps the authoritative generation and returns the new value only to `readoptAndFence` (`:387-388`, `:480-497`), and the mirror write at the end of the same iteration stamps the pre-bump value (`:447`). A coordinator that just took the session over through a crash takeover therefore holds the lease and the binding, has fenced the pod at the new generation, and sees a mirror row one bump stale for a full sweep interval, so a generation conjunct would abort the legitimate current coordinator's drive on the post-crash-recovery window that correlates with node drains. The lease-holder test needs no such comparand: the session's coordination lease is single-holder, so a superseded coordinator fails it already, and the pod remains fenced at the generation its current coordinator announced. No binding-free drive entry point and no fresh-dial resolution are added; 0060 retires the barrier path's Conn-or-Dial (`pkg/gateway/coordination/barrier/wiring.go`) as production-dead, and re-deriving it here would reintroduce the decoupling 0060 removes. Reaching the coordinator at all is the forward's job (§3) rather than the driver's. The barrier orchestration (`barrier.go:228`, `dispatchOne`, the gateway preStop handler) is not modified. The shared trigger is why the best-effort downgrade (CODE-2) keys off the adapter's local `evicting` flag rather than the trigger value: the barrier path drives `TriggerEviction` against a running agent pod whose adapter has not engaged its SIGTERM handler, so that pod's `evicting` flag stays false and its checkpoint keeps failing closed on a dropped handshake.
- **T-4.4.20 is closed as already-resolved-in-code rather than re-reconciled.** The stale `triggerForSource`/`snapshotWithTrigger` comment no longer exists under `pkg/` or `cmd/` (verified by `git grep`, zero hits); the individual-eviction drive reaching the checkpoint-snapshot core with `TriggerEviction` is what a unit assertion pins, and the `TEST-GAPS.md` entry that still cites `checkpointer.go:339-352` is updated to reflect the collapsed direct-parameter mapping.

## 3. The coordinator-direct eviction route and the control-stream consumer

The route has three legs. The adapter emit and gateway consume legs are new, and the driver leg composes existing primitives.

- **Adapter emit leg (new).** On kubelet-driven termination, the adapter's SIGTERM handler enumerates its live bound sessions and emits one `AdapterEvicting` event per session (with `slot_id` on pods where `maxConcurrentSessions > 1`) on the per-pod control channel, then keeps serving until each emitted session's coordinator-driven `Checkpoint` RPC completes on this adapter or a deadline lapses.
- **Gateway consume leg (new).** The gateway opens the `LifecycleChannel` client bidi stream once per pod, runs a receive loop that decodes each `LifecycleChannelResponse.envelope_json` control event, and on `AdapterEvicting` routes to the driver for the named `session_id`/`slot_id`. This consumer is new: no gateway production code reads the control stream today. The adapter admits one stream per pod and rejects a second opener with `codes.FailedPrecondition` "lifecycle control channel already open for this pod" (`pkg/adapter/controlchannel.go:110-116`), so stream ownership is explicit: every replica holding a binding to the pod attempts the open, the replica that wins owns the stream for as long as it holds any binding to that pod, and a replica that loses treats the `FailedPrecondition` rejection as benign contention and retries on a bounded backoff so it takes the stream over when the owner releases it. This matters on the concurrent-slot pod the forward exists for, where the owning replica's own session can end first. On that pod the takeover needs no hold handling at all: `onCoordinatorChannelClosed` arms the §10.1 coordinator-loss hold only for the pod-global session id (`pkg/adapter/holdstate.go:91-97`, reading `currentSession`, `pkg/adapter/controlchannel.go:187-191`), and a concurrent-workspace pod records each session on its own slot (`st.sessionID`, `pkg/adapter/slotsession.go:44`) and leaves the pod-global id empty (`pkg/adapter/session.go:359-361`), so the close returns before `enterHoldState`. The hold does arm on a base pod (`maxConcurrentSessions == 1`), whose `claimSession` sets the pod-global id (`pkg/adapter/session.go:423`). There the re-open is still admitted, because `LifecycleChannel` is on the hold-state allowlist (`pkg/adapter/holdstate.go:54-60`) the stream interceptor applies (`:258-262`), and the hold exits when the coordinator's next `CoordinatorFence` lands (`exitHoldState`, `holdstate.go:131`), which 0060's fence-first re-adopt supplies.
- **Driver leg (composed from existing primitives).** The coordinator drives the adapter `Checkpoint` RPC with `TriggerEviction` through the binding-gated `Checkpointer.CheckpointWithTrigger` (`checkpointer.go` → `snapshot` → `Registry.Get`), gated by a read-side coordination-lease-holder check that announces nothing to the pod. The drive is not preceded by a `coordfence.Fencer.Fence` call: `Fence` issues the `CoordinatorFence` RPC, and the adapter rejects a generation that is not strictly greater than the one it already recorded (`pkg/adapter/coordination.go:100-107`), so on an already-fenced pod the Fencer would take its relinquish branch, release the session's coordination lease, and return `ErrRelinquished` without driving (`coordfence.go:164-180`, `:196-199`). The read-side check instead reads the session's authoritative coordination-lease holder (`leasestore.Store.Get`, `pkg/gateway/storage/leasestore/leasestore.go:182`) and drives while that holder is this replica. When the read returns `ErrNotFound` (`leasestore.go:43`, `:184-186`, `:195-198`), no replica coordinates the session, so the replica holding the binding is authorized to drive: it first calls `leasestore.Store.Acquire` for itself, drives on success, forwards on `ErrHeld`, and drives on any other `Acquire` error, because that error is the same unreachable coordination store the read-side transport-error branch fails open on (`leasestore.go:134-137`). That closes the no-Redis and lapsed-lease windows without force-acquiring a live lease. A transport error from the read (`leasestore.go:188-190`) authorizes the binding holder directly, without an acquire against the same unreachable store, so a coordination-store outage does not drop the eviction checkpoint. When a peer holds the lease it archives no checkpoint, releases no lease, and forwards the eviction-drive request to the replica the mirror now names (§3 routing paragraph below). It does not compare the mirror's `coordination_generation`, which the sweep writes from a pre-bump snapshot and which therefore reads one bump stale for a full sweep interval after a crash takeover (`pkg/gateway/coordination/coordination/coordination.go:288-291`, `:387-388`, `:447`). Under proposal 0060 the session's coordinator is by construction the replica holding its in-memory binding, so `Registry.Get` resolves on the replica that holds the binding, which is why the drive is routed to the binding holder (below) rather than to the mirror's record alone. The drive therefore reuses the checkpoint-snapshot core, the `TriggerEviction` trigger, and the live binding connection unchanged, which preserves the §16.1 `lenny_checkpoint_duration_seconds{trigger=eviction}` label and the §4.4 retry budget. No fresh-dial resolution is used: 0060 retires the barrier path's Conn-or-Dial (`pkg/gateway/coordination/barrier/wiring.go`) as production-dead, and re-deriving it here would reintroduce the decoupling 0060 removes.

Proposal 0060 co-locates the coordination lease with the pod binding: the lease is acquired at bind on the binding replica, and a crash takeover re-establishes the binding on the new holder through a fence-first re-adopt. The session's coordinator is therefore the replica that holds its in-memory binding, and `Registry.Get` resolves on the coordinator. That retires the lease-versus-binding decoupling an earlier round of this proposal was written against, and with it the fresh-dial driver leg.

It does not retire the forward. A pod carries one control stream, but a binding is per session: `podsession.Registry` is keyed by session id (`pkg/gateway/podlifecycle/podsession/registry.go`), and a slot claim is a shared-state operation against the `SandboxClaim` CR rather than a replica-local one, so on a pod running concurrent sessions (`maxConcurrentSessions > 1`) two slots can be bound, and therefore coordinated, on different replicas while a single replica consumes the pod's one control stream. An `AdapterEvicting` for a co-tenant session bound on another replica still arrives on a replica that does not coordinate it, and a bare local dispatch would return `ErrNoBinding` and silently drive no checkpoint, which is the workspace-loss failure C-22 exists to prevent. The second case an earlier round named, a rolling-update handoff that leaves the control stream on the old replica while the lease moves to a replica that never re-bound, does not survive 0060: the new holder re-adopts the still-running pod eagerly, so the binding and the coordinator move together.

The consumer therefore routes each `AdapterEvicting` to the replica that coordinates that session, which under 0060 is the replica holding its binding, rather than dispatching it locally without a binding check. The `coordination_lease` mirror is the routing record (`coordinator_replica` plus the new `coordinator_address` column, `pkg/gateway/coordination/coordlease/pgstore/pgstore.go`, which a handoff overwrites with the new holder and its address). `coordinator_replica` is an opaque OTel `service.instance.id` (`coordlease.go:50`) and not dialable on its own, so the mirror records the coordinator's dialable inter-replica address alongside it and a by-session read returns both. The column, the `CoordinatorAddress` field, its `Upsert` write, and the `GetBySession` read already landed on this branch (`migrations/0180_coordination_lease_address.up.sql:19`, `coordlease.go:52-57,83-91`, `pgstore/pgstore.go:47-55,99-118`). The mirror is written only by the periodic coordination Sweeper (`upsertMirror`, default 15s), never at bind, so a session evicted before its first sweep has no recorded coordinator. 0060 already acquires the coordination lease at bind through `acquireCoordinationLease` (`sessionserver/start.go`), called from `registerBinding` and hoisted ahead of the running-commit on the single-call `/start`, delegated-child, and checkpoint-restore paths, but that helper calls `leasestore.Acquire` alone and writes no mirror row. The seed therefore folds into it rather than adding a second bind-time seam: `acquireCoordinationLease` also upserts the mirror with this replica as `coordinator_replica` and its dialable inter-replica address as `coordinator_address`, which closes the pre-first-sweep window at every site 0060 already covers, including a session resumed from a checkpoint onto a fresh pod. The recorded coordinator is the binding holder in steady state, and the record is a lagging projection of that fact: the sweep refreshes it every 15s, the sweep's dead-connection eviction releases the lease and drops the binding without rewriting the row (`coordination.go:332-338`, which continues past the sole mirror write at `:447`), and `upsertMirror` logs and swallows a Postgres error without retry (`coordination.go:565-576`). Routing on the record alone would therefore send the drive to a replica that holds no binding, where `Registry.Get` misses (`podsession/registry.go:33`, keyed by session id) and `CheckpointWithTrigger` returns `ErrNoBinding` (`checkpointer.go:426`), while the replica that could have driven it immediately forwarded instead. The predicate is keyed on the binding: the receiving replica drives locally whenever it holds the session's in-memory binding, whatever the mirror records, and it drives through the binding-gated `CheckpointWithTrigger` under the read-side coordination-lease-holder check. When it holds no binding and a different replica is the recorded coordinator, it reads that coordinator's dialable inter-replica address from the mirror (the `coordinator_address` column, recorded because `coordinator_replica` is an opaque `service.instance.id` and not routable on its own) and forwards the eviction-drive request (tenant, session, and slot) to that coordinator address over an internal gateway-to-gateway control-forward RPC, and the coordinator drives it against the binding it already holds. The forwarded payload carries no pod dial address: under co-location the coordinator reaches the pod over its own held binding rather than dialing one the forwarder resolved for it. The forward travels a dedicated gateway inter-replica gRPC port that the shipped `lenny-system` default-deny NetworkPolicy blocks until a `lenny.dev/component: gateway` self-peer is added to `allow-gateway-egress` and `allow-gateway-ingress` and the matching §13.2 Gateway-row peer is staged (SPEC-4, CHART-1); without that self-peer the forward is silently default-denied and the reachable cross-replica cases drop no checkpoint. This reuses the §7.2/§10.1 coordinator-routing pattern of identifying the coordinator through the coordination lease and forwarding to it (`spec/07_session-lifecycle.md:330`, currently elided in the minimal gateway at `pkg/gateway/sessionserver/messages.go:240`). A forwarded drive that resolves no local binding on the recorded coordinator (the mirror named a replica whose binding has since moved or been evicted) returns a typed no-binding response to the forwarder rather than dropping silently: the forwarder re-reads the mirror once and re-forwards when the recorded coordinator has changed, and otherwise logs the drop at error level with the tenant, session, and slot, so the loss is observable on the same path as the unreachable-coordinator residual. The drive is gated by the read-side coordination-lease-holder check, so a replica whose binding is stale because the session's lease and re-adopted binding have moved archives no checkpoint and releases no lease, and instead re-reads the mirror and forwards the eviction-drive request to the replica the record now names, over the same forward path. That state persists rather than resolving itself: the sweep evicts a published binding only on the dead-connection branch (`coordination.go:332-338`), so a replica whose pod connection is still alive keeps its binding while `Acquire` returns `ErrHeld` and the sweep continues (`:352-360`), and a peer that took the session over publishes its own binding after the fence (`:442`). A bare deny on that state would drop the eviction checkpoint on the one replica that could still route it, while the current holder has archived no newer checkpoint for the deny to protect, so the deny direction forwards on the same terms as the no-binding direction and logs the drop at error level with tenant, session, and slot when the re-read still names this replica or the forward fails. When the coordinator is unreachable within the grace window, the residual falls to the §10.1 TTL-driven handoff (accepted, decision 3), and no forced acquisition of the still-held lease is attempted, so the leasestore holder invariant is preserved. This resolves the within-window transport decision 0052 deferred (§10, decision 2, resolved in Pass 4 and completed in Pass 5).

## 4. The best-effort eviction snapshot

The Full-level eviction checkpoint today fails closed at `pkg/adapter/checkpoint.go:158-160`: when `s.Lifecycle.RequestCheckpoint` errors because the runtime lifecycle connection has dropped, the RPC returns `codes.Internal` before any chunk is archived, and the session drops to the minimal-state fallback. On the kubelet eviction path this is the common case for a SIGTERM-honoring third-party runtime, because the runtime container exits at `t=0` before the eviction `checkpoint_request` reaches it.

The change makes a checkpoint taken while this pod is itself terminating tolerate the dropped handshake. When `RequestCheckpoint` fails because the lifecycle connection is closed or dropped, and the adapter's own SIGTERM/eviction handler has engaged (the in-process `evicting` flag CODE-1 sets before emitting `AdapterEvicting`), the adapter proceeds to `streamChunks` against the still-mounted `/workspace` emptyDir and records the resulting checkpoint as an ordinary workspace checkpoint, rather than returning `codes.Internal`. The workspace bytes are readable because the adapter container mounts `/workspace` read-write and defers its own SIGTERM behind its preStop, and the exited runtime is no longer writing. The spec already sanctions best-effort snapshots for runtimes without a lifecycle channel (`spec/04_system-components.md:242`) and already accepts mid-tool-call inconsistency on the SIGSTOP eviction path (`spec/04_system-components.md:243`), so the eviction path resuming from a best-effort snapshot is a consistency downgrade the spec's model already contemplates, and it is strictly better than the total workspace loss the current fail-closed produces. On resume the workspace is restored and the client observes `resumeMode: full` with `workspaceLost: false`. The eviction path's tool-call-consistency relaxation is not surfaced as a separate field on `session.resumed`, which matches how the spec handles Basic/Standard best-effort checkpoints: they are tagged by runtime level rather than by a per-resume marker, and no field on the adapter-to-gateway `Checkpoint` stream, the checkpoint records, or the `session.resumed` event carries one today.

Every checkpoint of a pod that is not itself terminating keeps the fail-closed handshake unchanged. A periodic or pre-scale-down checkpoint on a live session must not silently downgrade to best-effort, because the runtime is present to quiesce cooperatively. The §10.1 gateway-drain barrier checkpoint (`barrier.go:228`) also carries `TriggerEviction`, yet it runs against a still-running agent pod whose adapter has not engaged its SIGTERM handler, so its `evicting` flag is false and a transient lifecycle-connection drop during the barrier fan-out keeps returning `codes.Internal` rather than downgrading. The downgrade is scoped to a pod that is terminating regardless (its own `evicting` flag set), where there is no agent to resume in an inconsistent state.

### SPEC-2. Describe the best-effort eviction snapshot in §4.4 and the kubelet-path eviction drive in §4.6.1

**Target:** `spec/04_system-components.md` §4.4 (the Full-level cooperative-handshake bullet near `:241` and the eviction-checkpoint bullet near `:264`), and §4.6.1 "Disruption protection for agent pods" (`:489`).

**Rationale:** The eviction checkpoint requires either a live runtime to answer `checkpoint_request`/`checkpoint_ready` (`checkpoint.go:158-160`) or a fallback for when the runtime has already exited. In the default sidecar model the hookless runtime container is SIGTERMed at `t=0` on kubelet termination and no pre-SIGTERM quiesce frame reaches it. Keeping the third-party runtime alive through the eviction window (a preStop hold with an init-container binary copy and a unix-socket signal) is the largest surface for this failure; the workspace `emptyDir` survives the runtime's exit and is readable by the still-alive adapter container, so a best-effort snapshot resolves the same total-workspace-loss failure at a single code site without keeping the runtime alive. The spec must state that the eviction path takes a best-effort snapshot when the cooperative handshake cannot complete, and that the kubelet-path drive is coordinator-direct, without weakening the `shareProcessNamespace` prohibition (`:243`, §13.1). The §4.6.1 edit also amends the landed invariant clause: the current text (`:489`) asserts the coordinating replica drives "under its held lease" and that "no replica drives the eviction checkpoint until it holds that lease ... so no unfenced replica ever drives the checkpoint." The resolved coordinator-direct design (Pass 4/5) has the recorded coordinator drive fenced by `coordination_generation`, and in the pre-first-sweep window that recorded coordinator is the seeded binding replica, which holds no coordination lease. Leaving the invariant unchanged while adding a non-lease-holding coordinator drive would make §4.6.1 self-contradictory, so the invariant must be amended to authorize the individual-eviction drive by the recorded `coordinator_replica` and the `coordination_generation` fence, superseding the lease-hold requirement for this path.

**Change (staged spec text).** In the Full-level bullet near `:241`, after the cooperative-handshake sentence, add:

```markdown
When a checkpoint runs while **this agent pod is itself terminating** under the kubelet SIGTERM (the default sidecar model SIGTERMs the hookless runtime container at `t=0` while the adapter's own SIGTERM is deferred behind its preStop), and the cooperative `checkpoint_request`/`checkpoint_ready` handshake cannot complete because the runtime process has already terminated, the adapter captures a **best-effort** snapshot of the still-mounted `/workspace` `emptyDir` (readable by the adapter container, which defers its SIGTERM and retains the mount through the grace window) and records it as the session's workspace checkpoint, rather than aborting the checkpoint. The exited runtime is no longer writing to the workspace, so the snapshot is quiescent with respect to writes; it lacks only the tool-call-consistency guarantee the cooperative handshake provides, which eviction checkpoints already relax (see the SIGSTOP eviction path above). On resume the workspace is restored and the client observes `resumeMode: full` with `workspaceLost: false`; the eviction path's tool-call-consistency relaxation is inherent to eviction checkpoints and is not surfaced as a separate `session.resumed` field. This best-effort path applies only when the adapter's own pod is terminating; a checkpoint of a still-running pod keeps the cooperative handshake and fails closed on a dropped connection. This includes the gateway-drain barrier checkpoint, which also carries the `eviction` trigger but runs against a running agent pod whose session continues after coordinator handoff, and periodic and pre-scale-down checkpoints.
```

## 12. Revision for the co-located coordination model (2026-07-26)

Proposal 0060 co-locates the session-coordination lease with the pod binding, so the coordinator is by construction the replica holding the session's binding. This proposal was written against the decoupled model, and its spec edits had already been applied, so the revision below reconciles it. The eviction route, the decisions, and the three ratified sign-off decisions are otherwise unchanged.

**The driver leg is retired rather than adapted.** The staged drive resolved its adapter connection through the barrier path's Conn-or-Dial fresh-dial because the binding-gated `CheckpointWithTrigger` returned `ErrNoBinding` on a coordinator that held the lease but not the binding. Under 0060 that state does not exist, and 0060 deletes the Conn-or-Dial resolution outright as production-dead. The drive now reuses `CheckpointWithTrigger` unchanged on the replica holding the binding, and the binding-free checkpointer entry point this proposal staged is no longer added. Resuming the implementation against the pre-0060 text would not have compiled. Co-location also settles where the drive is authorized: the drive runs a read-side coordination-lease-holder check rather than calling `coordfence.Fencer.Fence`, because `Fence` announces a generation the adapter rejects unless it is strictly greater than the one already recorded, which on an already-fenced pod would relinquish the session's lease and drive no checkpoint. The check's deny direction forwards rather than returning: the merged sweep leaves a published binding in place whenever the pod connection is alive and the lease belongs to a peer (`coordination.go:332-338`, `:352-360`), so a replica can hold a stale binding for a session another replica coordinates, and a bare deny there would drop the eviction checkpoint on the one replica that could still route it. The check reads a third outcome as authorization rather than denial: when no lease is recorded for the session at all (a deployment wired without Redis, or the window after a Redis restart loses the coordination keys), the replica holding the binding acquires the lease for itself and drives, and forwards only when that acquire returns `ErrHeld`.

**The forward leg survives, on one case rather than two.** The staged forward rested on two cases. The rolling-update case, where a lease moves to a replica that never re-bound while the control stream stays on the old one, does not survive 0060's eager fence-first re-adopt: the binding and the coordinator move together. The concurrent-session case does survive and is sufficient on its own. `podsession.Registry` is keyed by session id and a slot claim is a shared-state operation against the `SandboxClaim` CR, so two slots on one `maxConcurrentSessions > 1` pod can be bound, and therefore coordinated, on different replicas while a single replica consumes the pod's one control stream. An `AdapterEvicting` for a co-tenant session still lands on a replica that does not coordinate it. The `coordinator_address` column, the by-session mirror read, the inter-replica port, the §13.2 peer (SPEC-4), the chart self-peer (CHART-1), and the generic coordinator-forward transport are therefore all retained.

**The forwarded payload loses the pod dial address.** It carried the agent pod's dial address so the coordinator could fresh-dial the adapter. The coordinator now reaches the pod over its own held binding, so the payload is tenant, session, and slot.

**The mirror seed folds into 0060's at-bind lease acquire.** The staged seed added a shared helper called from `registerBinding` and the snapshot-restore branch of `resumeOnPod`, which under 0060 would have missed the single-call `/start` and delegated-child paths that publish through `publishBinding` without calling `registerBinding` (`pkg/gateway/sessionserver/start.go:894`, `:1096`). 0060 runs `acquireCoordinationLease` at every one of those bind sites (`:858`, `:1042`, `:2825` inside `registerBinding`, and `:3941` on the checkpoint-restore resume), but that helper calls `leasestore.Acquire` alone and writes no mirror row, so the pre-first-sweep window it leaves remains open and the seed is still needed. It now extends that one helper rather than adding a second bind-time seam, which keeps the lease acquire and the mirror seed from naming different replicas. It also extends 0060's rollback counterpart `releaseCoordinationLease` to retract the seeded row, because the hoisted acquire runs ahead of the running-commit and a failed commit would otherwise leave an active mirror row with no lease and no binding behind it. The seed keeps the helper all-or-nothing: it runs after `leasestore.Acquire`, and an `Upsert` failure releases the lease the same call acquired before returning the error, so the callers' existing assumption that an acquire error means nothing is held stays true. The seed is skipped when no mirror store is wired, because the mirror is Postgres-backed and nil on a gateway wired without Postgres while the lease store is built from the Redis configuration alone, so a fail-closed seed there would abort every bind. Under co-location the first sweep confirms the seeded row rather than correcting it, and the row remains a lagging projection between sweeps, which is why the eviction route drives on the binding it finds locally rather than on the record alone.

**The applied spec text is corrected on three surfaces (SPEC-6).** The applied §4.6.1 paragraph asserts in two separate sentences that the drive is authorized by the fence rather than by lease ownership because the seeded binding replica "holds no coordination lease," which 0060 makes false; it carries a "when it does not already hold the session's binding" conditional that can no longer fire; and it justifies the forward partly by the retired lease-moved-without-rebinding case. The same falsified decoupling was applied to the §10.1 mirror description (`spec/10_gateway-internals.md:167`, "can name a non-lease-holding binding replica" and "may therefore return a seeded non-lease-holder") and to the authored migration-0164 comment ("holds no coordination lease yet", "not always the current lease holder"). Both §4.6.1 and the §4.7 `AdapterEvicting` row also name the driver by the mirror record in their lead sentences and state the forwarding predicate on the same record, which sends the replica holding the binding to forward to a replica that cannot drive whenever the mirror lags, so SPEC-6 re-keys the driver clause and the forwarding predicate on the binding across both surfaces and restates the authorization as the driving replica's held coordination lease. The second §4.6.1 authorization sentence is replaced whole rather than at its trailing clause, because its main clause states the record-and-generation authorization a second time. SPEC-6 stages all of those corrections; the §4.7 row's rationale clause that the control-stream consumer is not always the coordinator is kept, because 0060 does not falsify it. TEST-5 carries the tier-11 blast radius for the §4.6.1 correction.
