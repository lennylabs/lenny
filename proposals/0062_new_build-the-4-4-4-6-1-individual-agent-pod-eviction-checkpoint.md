## 1. Problem

The §4.6.1 coordinator-direct eviction route is described in spec (`spec/04_system-components.md:489`, landed by prereq 2 / proposal 0052) but no code drives it, and the mechanism it needs to survive the default sidecar deployment model does not exist. Four facts define the build.

**1. No individual agent-pod eviction fires a checkpoint.** `checkpoint.TriggerEviction` is driven only on the gateway pod's own §10.1 preStop barrier fan-out (`pkg/gateway/coordination/barrier/barrier.go:228`, reached only from the gateway preStop handler), never on an individual agent-pod eviction. The agent-pod preStop `runPreStop` (`cmd/lenny-adapter/prestop.go`) SIGTERMs the local adapter and polls for its exit; the adapter SIGTERM handler (`cmd/lenny-adapter/main.go:411-425`) runs `ShutdownDemoteSDK`, `lifecycle.Close()`, and `srv.GracefulStop()` and emits no eviction signal to any gateway replica. The `Checkpoint` RPC is gateway-driven, so the pod cannot open it itself (`spec/04_system-components.md:489`). This is the C-22 eviction trigger, finding T-4.4.14.

**2. Runtime-container quiescence race in the default sidecar model.** In the default sidecar model the third-party `runtime` container carries no `Lifecycle`/preStop; only the adapter container carries the preStop drain hook. `RestartPolicy` is `Never` with no native-sidecar `InitContainer` ordering, so on kubelet termination the hookless runtime is SIGTERMed at `t=0` while the adapter's SIGTERM is deferred behind its preStop. The Full-level eviction checkpoint gates its archive on the live-runtime cooperative quiesce handshake `s.Lifecycle.RequestCheckpoint(...)` (`pkg/adapter/checkpoint.go:158-160`), which returns `codes.Internal "checkpoint quiesce handshake"` before `streamChunks`/`ArchiveTree` when the runtime's lifecycle connection has dropped. No pre-SIGTERM quiesce frame travels the kubelet path (`drainViaLifecycle`/`Terminate` fire only from the gateway `Shutdown` RPC handler; `SignalDeadlineApproaching` fires only from the `SignalDeadline` RPC), and `shareProcessNamespace` is prohibited (`spec/13_security-model.md` §13.1, `spec/04_system-components.md:243`). A SIGTERM-honoring runtime therefore exits before the eviction `checkpoint_request` reaches it, the handshake fails, and the current fail-closed at `checkpoint.go:158-160` drops the session to the minimal-state fallback (`resumeMode: conversation_only`, `workspaceLost: true`, `spec/04_system-components.md:264`), losing the live-workspace emptyDir.

The workspace is a separate pod-scoped `emptyDir` mounted `/workspace/` into both containers (`spec/04_system-components.md:865` deployment-model bullet; podspec renders it read-write into the adapter container). Kubernetes clears an `emptyDir` on pod removal rather than on a single container's exit, so after the runtime container exits under SIGTERM the still-alive adapter container retains full read access to `/workspace` through the grace window. The adapter already archives the checkpoint from its own on-disk mount (`workspace.ArchiveTree`, `pkg/adapter/checkpoint.go:201`), rather than by streaming from the runtime process. A runtime that has exited is no longer writing to the workspace and is therefore already quiesced; the cooperative handshake adds only tool-call consistency, which the spec already relaxes for eviction checkpoints and for the SIGSTOP eviction path (`spec/04_system-components.md:242-243`).

**3. The deferred 0052 coordinator decisions.** Proposal 0052's sign-off resolved coordinator-direct as the seam and deferred the within-window forced takeover and the forward-to-holder transport to this proposal.

**4. The §4.4 doc-nit.** `spec/04_system-components.md:264` and `:278` justify the eviction retry budget with `terminationGracePeriodSeconds (240s at Tier 1/2, 300s at Tier 3)`, and `spec/17_deployment-topology.md:971` labels that row `terminationGracePeriodSeconds (gateway pod)`. The eviction-checkpoint bullet at `:264` is titled "Eviction checkpoints (preStop hook)" and justifies its budget with "(a) the pod is terminating regardless — there is no agent to resume" and a resume-on-fresh-pod fallback (`resumeMode: conversation_only`, `workspaceLost: true`), so it documents the agent-pod eviction path this proposal builds, rather than the gateway-drain barrier path (`barrier.go:228`), during which the agent pod keeps running and its session continues after coordinator handoff. The agent pod's grace default is 120s (`spec/04_system-components.md:489`). Citing the gateway pod's 240/300s grace on the agent-pod eviction bullet is therefore the doc-nit: the bound there is the agent pod's 120s grace. The 30s MinIO plus 60s Postgres budgets (90s worst case) fit within 120s, so the numbers are not unsafe, but the grace attribution at `:264`/`:278` is wrong and SPEC-3 corrects it.

Prereqs 1 (0050, slot-aware checkpointing), 2 (0052, coordinator-direct route text at `spec/04_system-components.md:489`), and 3 (0056, admission grace floor) are landed and consumed unchanged. The earlier seed hint that `triggerForSource` at `checkpointer.go:366` must be reconciled is obsolete: `git grep triggerForSource|snapshotWithTrigger` returns zero hits under `pkg/` and `cmd/`. The switch was already collapsed and the trigger threads as a direct parameter through the checkpoint-snapshot core (`Checkpointer.CheckpointWithTrigger`, `pkg/gateway/checkpoint/checkpointer/checkpointer.go:375`), so the individual-eviction drive passes `TriggerEviction` directly, and finding T-4.4.20's code half is already resolved. The eviction drive resolves the adapter connection through the barrier-path fresh-dial rather than the binding gate; that reconciliation is described in §3 and CODE-3.

## 2. Decisions

- **Coordinator-direct is the built seam, per 0052's sign-off.** The adapter, on kubelet-driven pod termination, emits a new `AdapterEvicting` adapter-to-gateway control event on the per-pod control channel; the session's coordinator (the `coordinator_replica` recorded in the `coordination_lease` mirror, [§10.1](../spec/10_gateway-internals.md)) drives the eviction `Checkpoint` RPC with `TriggerEviction`, fenced by the session's `coordination_generation` rather than authorized by lease ownership, because in the pre-first-sweep window the recorded coordinator is the seeded binding replica that holds no coordination lease yet. The replica whose per-pod control stream receives `AdapterEvicting` is not guaranteed to be that coordinator (see decision below and §3), so the receiving replica identifies the coordinator through the `coordination_lease` mirror and forwards the drive to the coordinator's recorded dialable inter-replica address when it is not the coordinator, over an internal gateway-to-gateway control-forward RPC on a dedicated gateway inter-replica gRPC port that a new §13.2 and `charts/` NetworkPolicy self-peer admits (the shipped default-deny otherwise blocks the forward). The drive resolves the adapter connection through the barrier path's Conn-or-Dial fresh-dial (`pkg/gateway/coordination/barrier/wiring.go`) rather than the binding-gated `Checkpointer.CheckpointWithTrigger` (`checkpointer.go:375` → `Registry.Get`, `:424`), so a coordinator that holds the lease but not the in-memory binding still drives. No gateway-side agent-pod informer is built (that seam was surfaced-and-deferred by 0052 and would need dedup and RBAC across every replica).
- **The bind path seeds the `coordination_lease` mirror so a session is resolvable before it can be evicted.** The `coordination_lease` mirror row (`coordinator_replica`) is written only by the periodic coordination Sweeper (`coordination.go:150` `upsertMirror`, default 15s interval), never at session bind (the session-start `registerBinding` and the snapshot-resume rebind write only the in-memory `podRegistry` binding, `start.go:2668` and `:3595`). A session evicted within the first sweep interval after it binds therefore has no `coordinator_replica` row, so mirror-only routing would resolve no coordinator and drive no checkpoint on a reachable path (node drain or spot reclaim shortly after scheduling), which is the silent workspace loss C-22 prevents. The seed therefore folds into 0060's `acquireCoordinationLease`, the at-bind lease acquire that already runs at every path publishing a live binding (`registerBinding`, and hoisted ahead of the running-commit on the single-call `/start`, delegated-child, and checkpoint-restore paths). That helper today calls `leasestore.Acquire` alone and writes no mirror row; extending it to also `coordlease.Store.Upsert` the binding replica as the session's initial `coordinator_replica` at the session's `coordination_generation` (a fresh row baselines to 1, matching `coordfence.go`) makes every live-bound session resolvable before the adapter can emit `AdapterEvicting` for it, including a session resumed from a checkpoint onto a fresh warm pod. Folding it into the existing helper rather than adding a parallel seed seam keeps the lease acquire and the mirror seed from drifting, since under co-location they name the same replica. Because `coordinator_replica` is an opaque OTel `service.instance.id` (`coordlease.go:50`) and not a dialable address, the seed also records the coordinator's dialable inter-replica address (`POD_IP` plus `interReplicaGRPCPort`) in a new `coordinator_address` mirror column, and a by-session mirror read returns both, so a replica that must forward has a routable target rather than only an identity. Under co-location the seeded replica is the lease holder, so the first coordination sweep confirms the seeded row rather than correcting it; a later handoff moves the binding and the lease together and overwrites both fields with the new coordinator and its address, so the mirror stays routable to the replica that actually holds the binding the drive runs on. The routing predicate is that the receiving replica drives locally when it is the recorded coordinator, or, as defense-in-depth for a missing record, when no coordinator is recorded and it holds the session's in-memory binding, and forwards only when a different replica is the recorded coordinator.
- **The gateway-side control-stream consumer does not exist yet and is built here.** The `LifecycleChannel` control stream is served only on the adapter side (`pkg/adapter/controlchannel.go:90`); `AdapterTerminating` and `FINAL_USAGE_REPORT` are emit-only (`controlchannel.go:34,39`), and no gateway production code opens the client bidi stream or reads `LifecycleChannelResponse`. The earlier framing that the transport "already carries `AdapterTerminating`" to a gateway consumer is corrected: the gateway consumer (client stream open, receive loop, reconnect, session and slot routing) is new code this proposal builds.
- **A new §4.7 control event is warranted rather than overloading `AdapterTerminating`.** `AdapterTerminating` is a terminal notification (`spec/04_system-components.md:688`, reason `coordinator_lost`) that transitions the session immediately without waiting for the orphan reconciler; its semantics are wrong for "drive an eviction checkpoint, then terminate". `AdapterEvicting` requests a checkpoint drive and survives the minimal-surface test because no existing control event carries that request.
- **The eviction drive lives in the adapter SIGTERM handler rather than a new local RPC.** On the kubelet path the adapter-container preStop runs before the adapter's SIGTERM, so the SIGTERM handler is where the adapter is still fully serving and can emit the eviction event, keep the gRPC server accepting the coordinator's `Checkpoint` RPC (defer `GracefulStop`), await completion of the eviction checkpoint(s) for its live bound sessions under a deadline, then tear down. When the adapter has no live bound session, it emits nothing and exits as today. The adapter observes checkpoint completion locally because it serves the `Checkpoint` RPC, so no gateway-to-adapter completion-ack frame is added.
- **The runtime-container quiescence race is resolved by a best-effort eviction snapshot rather than by keeping the runtime alive.** When this pod is itself terminating (the adapter's own SIGTERM/eviction handler has engaged, tracked by an in-process `evicting` flag the handler sets before it emits `AdapterEvicting`) and the cooperative `checkpoint_request`/`checkpoint_ready` handshake cannot complete because the runtime lifecycle connection has already dropped, the adapter archives the still-mounted `/workspace` emptyDir directly and records it as an ordinary workspace checkpoint, rather than returning `codes.Internal` and aborting to the minimal-state fallback. The downgrade is gated on the adapter's own termination state rather than on the `TriggerEviction` trigger value, because `TriggerEviction` is shared with the §10.1 gateway-drain barrier path (`barrier.go:228`), during which the agent pod keeps running and its session continues after coordinator handoff. Gating on the trigger alone would let a transient lifecycle-connection drop during a barrier fan-out silently downgrade a still-running session's checkpoint to best-effort. The adapter that serves the `Checkpoint` RPC derives the trigger solely from `CheckpointStart` (`checkpoint.go:128`) and cannot otherwise tell the two paths apart, so the local `evicting` flag is the authoritative "this pod is terminating" signal. The restored snapshot resumes as `resumeMode: full` with `workspaceLost: false`, indistinguishable at the wire from a cooperatively-quiesced checkpoint. No new per-checkpoint or per-resume consistency field is added: the adapter-to-gateway `Checkpoint` stream (`CheckpointStart`/`CheckpointSummary`, `schemas/lenny-adapter.proto:1101,1187`) carries no `consistency` field, neither the `checkpoint_manifest` (`migrations/0178_checkpoint_manifest.up.sql:30`) nor the `session_checkpoints` record persists one, and the §7.2 `session.resumed` event (`spec/07_session-lifecycle.md:138`) enumerates `resumeMode` as `full`, `conversation_only`, `partial_workspace`, or `coordinator_handoff` with a boolean `workspaceLost` and no consistency field. Surfacing a distinct best-effort marker would require a new proto field, a migration, a §7.2/§15 event-schema field, and SDK plus `docs/client-guide/wire-format.md` mirroring, which the minimal-surface principle rejects because the spec's existing best-effort model already relaxes tool-call consistency without a per-resume marker (`spec/04_system-components.md:242-243`). The eviction path carries the tool-call-consistency caveat the spec already documents. This resolves the same failure the runtime-hold would (total workspace loss) at a single code site, with no init container, no shared binary copy, no unix-socket hold, and no third-party runtime image change. The rejected runtime-hold and its own rejected sub-alternatives are recorded in Non-goals.
- **The embedded deployment model is unchanged.** It runs a single first-party container that carries the preStop and links the adapter, with no separate hookless runtime, so the ordering race does not arise. The embedded model reaches the same SIGTERM handler and benefits from the same eviction drive; the best-effort snapshot fallback is a no-op there because the embedded runtime's lifecycle connection does not drop out from under the adapter.
- **The unreachable-coordinator and any cross-replica residual is accepted; no forced-takeover primitive is built.** Per 0052's Non-goals and sign-off, a still-live coordination lease cannot be acquired by a non-holder without a forced-acquisition primitive the leasestore holder invariant forbids (`pkg/.../leasestore.go` holder invariant; `ErrHeld`). A coordinator unreachable within the grace window is recovered only by the existing §10.1 TTL-driven handoff (default 4×15s, which may outlast the window), and that residual session drops to the §4.4 minimal-state fallback. This preserves the leasestore holder invariant and the `shareProcessNamespace` prohibition unchanged.
- **The eviction drive reuses the binding-gated `CheckpointWithTrigger` and the `coordfence` generation fence, on the coordinator's own held binding.** The eviction drive and the §10.1 gateway-drain barrier drive both carry `TriggerEviction`, so the §16.1 `lenny_checkpoint_duration_seconds{trigger=eviction}` label and the §4.4 eviction retry budget apply on both. Under proposal 0060 the session's coordinator is the replica holding its binding, so `Checkpointer.CheckpointWithTrigger` (`checkpointer.go` → `snapshot` → `Registry.Get`) resolves once the drive runs on the coordinator, and the `ErrNoBinding` an earlier round of this proposal routed around cannot arise there. The drive therefore reuses that entry point unchanged, fences with `coordination_generation` through the existing `coordfence` primitive (`pkg/gateway/coordination/coordfence/coordfence.go`), and drives the same checkpoint-snapshot core with `TriggerEviction`. No binding-free drive entry point and no fresh-dial resolution are added; 0060 retires the barrier path's Conn-or-Dial (`pkg/gateway/coordination/barrier/wiring.go`) as production-dead, and re-deriving it here would reintroduce the decoupling 0060 removes. Reaching the coordinator at all is the forward's job (§3), not the driver's. The barrier orchestration (`barrier.go:228`, `dispatchOne`, the gateway preStop handler) is not modified. The shared trigger is why the best-effort downgrade (CODE-2) keys off the adapter's local `evicting` flag rather than the trigger value: the barrier path drives `TriggerEviction` against a running agent pod whose adapter has not engaged its SIGTERM handler, so that pod's `evicting` flag stays false and its checkpoint keeps failing closed on a dropped handshake.
- **T-4.4.20 is closed as already-resolved-in-code rather than re-reconciled.** The stale `triggerForSource`/`snapshotWithTrigger` comment no longer exists under `pkg/` or `cmd/` (verified by `git grep`, zero hits); the individual-eviction drive reaching the checkpoint-snapshot core with `TriggerEviction` is what a unit assertion pins, and the `TEST-GAPS.md` entry that still cites `checkpointer.go:339-352` is updated to reflect the collapsed direct-parameter mapping.

## 3. The coordinator-direct eviction route and the control-stream consumer

The route has three legs. The adapter emit and gateway consume legs are new, and the driver leg composes existing primitives.

- **Adapter emit leg (new).** On kubelet-driven termination, the adapter's SIGTERM handler enumerates its live bound sessions and emits one `AdapterEvicting` event per session (with `slot_id` on pods where `maxConcurrentSessions > 1`) on the per-pod control channel, then keeps serving until each emitted session's coordinator-driven `Checkpoint` RPC completes on this adapter or a deadline lapses.
- **Gateway consume leg (new).** The gateway opens the `LifecycleChannel` client bidi stream once per pod, runs a receive loop that decodes each `LifecycleChannelResponse.envelope_json` control event, and on `AdapterEvicting` routes to the driver for the named `session_id`/`slot_id`. This consumer is new: no gateway production code reads the control stream today.
- **Driver leg (composed from existing primitives).** The coordinator drives the adapter `Checkpoint` RPC with `TriggerEviction` through the binding-gated `Checkpointer.CheckpointWithTrigger` (`checkpointer.go` → `snapshot` → `Registry.Get`), fencing the drive with the session's `coordination_generation` through the existing `coordfence` primitive (`pkg/gateway/coordination/coordfence/coordfence.go`, which relinquishes without driving on a stale generation). Under proposal 0060 the session's coordinator is by construction the replica holding its in-memory binding, so `Registry.Get` resolves on the coordinator and the `ErrNoBinding` return that an earlier round of this proposal routed around cannot arise on this path. The drive therefore reuses the checkpoint-snapshot core, the `TriggerEviction` trigger, and the live binding connection unchanged, which preserves the §16.1 `lenny_checkpoint_duration_seconds{trigger=eviction}` label and the §4.4 retry budget. No fresh-dial resolution is used: 0060 retires the barrier path's Conn-or-Dial (`pkg/gateway/coordination/barrier/wiring.go`) as production-dead, and re-deriving it here would reintroduce the decoupling 0060 removes.

Proposal 0060 co-locates the coordination lease with the pod binding: the lease is acquired at bind on the binding replica, and a crash takeover re-establishes the binding on the new holder through a fence-first re-adopt. The session's coordinator is therefore the replica that holds its in-memory binding, and `Registry.Get` resolves on the coordinator. That retires the lease-versus-binding decoupling an earlier round of this proposal was written against, and with it the fresh-dial driver leg.

It does not retire the forward. A pod carries one control stream, but a binding is per session: `podsession.Registry` is keyed by session id (`pkg/gateway/podlifecycle/podsession/registry.go`), and a slot claim is a shared-state operation against the `SandboxClaim` CR rather than a replica-local one, so on a pod running concurrent sessions (`maxConcurrentSessions > 1`) two slots can be bound, and therefore coordinated, on different replicas while a single replica consumes the pod's one control stream. An `AdapterEvicting` for a co-tenant session bound on another replica still arrives on a replica that does not coordinate it, and a bare local dispatch would return `ErrNoBinding` and silently drive no checkpoint, which is the workspace-loss failure C-22 exists to prevent. The second case an earlier round named, a rolling-update handoff that leaves the control stream on the old replica while the lease moves to a replica that never re-bound, does not survive 0060: the new holder re-adopts the still-running pod eagerly, so the binding and the coordinator move together.

The consumer therefore routes each `AdapterEvicting` to the session's coordinator rather than driving locally. The `coordination_lease` mirror is the routing record (`coordinator_replica` plus the new `coordinator_address` column, `pkg/gateway/coordination/coordlease/pgstore/pgstore.go`, which a handoff overwrites with the new holder and its address). `coordinator_replica` is an opaque OTel `service.instance.id` (`coordlease.go:50`) and not dialable on its own, so the mirror records the coordinator's dialable inter-replica address alongside it and a by-session read (added to `coordlease.Store`/`pgstore`, which today expose only `ListHeldByReplica`, `Upsert`, and the delete paths) returns both. The mirror is written only by the periodic coordination Sweeper (`upsertMirror`, default 15s), never at bind, so a session evicted before its first sweep has no recorded coordinator. 0060 already acquires the coordination lease at bind through `acquireCoordinationLease` (`sessionserver/start.go`), called from `registerBinding` and hoisted ahead of the running-commit on the single-call `/start`, delegated-child, and checkpoint-restore paths, but that helper calls `leasestore.Acquire` alone and writes no mirror row. The seed therefore folds into it rather than adding a second bind-time seam: `acquireCoordinationLease` also upserts the mirror with this replica as `coordinator_replica` and its dialable inter-replica address as `coordinator_address`, which closes the pre-first-sweep window at every site 0060 already covers, including a session resumed from a checkpoint onto a fresh pod. The receiving replica drives locally when it is the recorded coordinator, or, as defense-in-depth for a missing record, when no coordinator is recorded and it holds the session's in-memory binding; it drives through the binding-gated `CheckpointWithTrigger`, fenced by `coordination_generation` (a fresh row baselines to generation 1, `coordfence.go`). When a different replica is the recorded coordinator, it reads that coordinator's dialable inter-replica address from the mirror (the `coordinator_address` column, recorded because `coordinator_replica` is an opaque `service.instance.id` and not routable on its own) and forwards the eviction-drive request (tenant, session, and slot) to that coordinator address over an internal gateway-to-gateway control-forward RPC, and the coordinator drives it against the binding it already holds. The forwarded payload carries no pod dial address: under co-location the coordinator reaches the pod over its own held binding rather than dialing one the forwarder resolved for it. The forward travels a dedicated gateway inter-replica gRPC port that the shipped `lenny-system` default-deny NetworkPolicy blocks until a `lenny.dev/component: gateway` self-peer is added to `allow-gateway-egress` and `allow-gateway-ingress` and the matching §13.2 Gateway-row peer is staged (SPEC-4, CHART-1); without that self-peer the forward is silently default-denied and the reachable cross-replica cases drop no checkpoint. This reuses the §7.2/§10.1 coordinator-routing pattern of identifying the coordinator through the coordination lease and forwarding to it (`spec/07_session-lifecycle.md:330`, currently elided in the minimal gateway at `pkg/gateway/sessionserver/messages.go:240`). The drive is fenced by `coordination_generation`, so a stale coordinator during a handoff window relinquishes rather than driving a checkpoint that could overwrite a newer one. When the coordinator is unreachable within the grace window, the residual falls to the §10.1 TTL-driven handoff (accepted, decision 3), and no forced acquisition of the still-held lease is attempted, so the leasestore holder invariant is preserved. This resolves the within-window transport decision 0052 deferred (§10, decision 2, resolved in Pass 4 and completed in Pass 5).

## 4. The best-effort eviction snapshot

The Full-level eviction checkpoint today fails closed at `pkg/adapter/checkpoint.go:158-160`: when `s.Lifecycle.RequestCheckpoint` errors because the runtime lifecycle connection has dropped, the RPC returns `codes.Internal` before any chunk is archived, and the session drops to the minimal-state fallback. On the kubelet eviction path this is the common case for a SIGTERM-honoring third-party runtime, because the runtime container exits at `t=0` before the eviction `checkpoint_request` reaches it.

The change makes a checkpoint taken while this pod is itself terminating tolerate the dropped handshake. When `RequestCheckpoint` fails because the lifecycle connection is closed or dropped, and the adapter's own SIGTERM/eviction handler has engaged (the in-process `evicting` flag CODE-1 sets before emitting `AdapterEvicting`), the adapter proceeds to `streamChunks` against the still-mounted `/workspace` emptyDir and records the resulting checkpoint as an ordinary workspace checkpoint, rather than returning `codes.Internal`. The workspace bytes are readable because the adapter container mounts `/workspace` read-write and defers its own SIGTERM behind its preStop, and the exited runtime is no longer writing. The spec already sanctions best-effort snapshots for runtimes without a lifecycle channel (`spec/04_system-components.md:242`) and already accepts mid-tool-call inconsistency on the SIGSTOP eviction path (`spec/04_system-components.md:243`), so the eviction path resuming from a best-effort snapshot is a consistency downgrade the spec's model already contemplates, and it is strictly better than the total workspace loss the current fail-closed produces. On resume the workspace is restored and the client observes `resumeMode: full` with `workspaceLost: false`. The eviction path's tool-call-consistency relaxation is not surfaced as a separate field on `session.resumed`, which matches how the spec handles Basic/Standard best-effort checkpoints: they are tagged by runtime level rather than by a per-resume marker, and no field on the adapter-to-gateway `Checkpoint` stream, the checkpoint records, or the `session.resumed` event carries one today.

Every checkpoint of a pod that is not itself terminating keeps the fail-closed handshake unchanged. A periodic or pre-scale-down checkpoint on a live session must not silently downgrade to best-effort, because the runtime is present to quiesce cooperatively. The §10.1 gateway-drain barrier checkpoint (`barrier.go:228`) also carries `TriggerEviction`, yet it runs against a still-running agent pod whose adapter has not engaged its SIGTERM handler, so its `evicting` flag is false and a transient lifecycle-connection drop during the barrier fan-out keeps returning `codes.Internal` rather than downgrading. The downgrade is scoped to a pod that is terminating regardless (its own `evicting` flag set), where there is no agent to resume in an inconsistent state.

## 7. Non-goals

- **Modifying the gateway-drain barrier orchestration** (`barrier.go:228` / `dispatchOne` / the gateway preStop handler). Its logic is unchanged. The eviction path reuses the `coordfence` generation fence and the binding-gated `CheckpointWithTrigger`, driving the shared checkpoint-snapshot core with `TriggerEviction`; it does not call or alter the barrier's own drive. It takes nothing from `barrier/wiring.go`, whose Conn-or-Dial resolution proposal 0060 deletes.
- **Re-solving prereq 1** (0050 slot-aware checkpointing: `slot_id` on `CheckpointStart`, slot-scoped checkpoint roots, and per-slot op-lock), **prereq 2** (0052 coordinator-direct route text at `spec/04_system-components.md:489`), or **prereq 3** (0056 admission grace-floor). All are landed and consumed unchanged.
- **Building the runtime-container quiescence hold** (a first-party preStop hold on the third-party runtime container, delivered by an init container that copies the adapter binary into a shared `emptyDir`, released over a unix socket the adapter closes on checkpoint completion). This was the original SPEC-2/CODE-2 mechanism. It is rejected in favor of the best-effort eviction snapshot (CODE-2), which resolves the same total-workspace-loss failure at a single code site because the workspace `emptyDir` survives the runtime's SIGTERM and is readable by the still-alive adapter container (`spec/04_system-components.md:865`); an exited runtime is already quiesced with respect to writes, and the cooperative handshake adds only tool-call consistency, which the spec already relaxes on the eviction and SIGSTOP paths (`:242-243`). The hold's own rejected sub-alternatives are recorded for completeness: a native preStop `sleep` action cannot bound an unknown checkpoint duration (workspace size varies up to `workspaceSizeLimitBytes`, so a mis-sized fixed sleep silently defeats the checkpoint and wastes teardown latency on empty scale-downs); a native-sidecar reorder (runtime as `RestartPolicy: Always` init container so it terminates last) inverts the container roles and forces the runtime to start before the adapter, risking the §6 warm-pod startup and preConnect dial ordering; a runtime-conformance "wait for terminate frame rather than exit on SIGTERM" contract pushes the burden onto third-party runtime authors and stays best-effort for a non-conformant image.
- **Enlarging the adapter-container preStop drain timeout** (the dropped CODE-4). The preStop cap is not a constant to enlarge: the podspec renders it as `terminationGrace(in) - preStopDrainMarginSeconds` (`pkg/controller/sandbox/podspec/podspec.go`), which is 110s at the 120s default and tracks the pod grace automatically, and the drain poll returns the moment the adapter exits (`cmd/lenny-adapter/prestop.go`) rather than waiting out the cap. The 90s worst-case eviction budget (30s MinIO + 60s Postgres, `spec/04_system-components.md:264,278`) already fits inside the 110s cap with headroom, so no constant needs adjusting. The one genuine obligation CODE-4 stated (a single shared eviction budget across the adapter wait and the preStop cap) is already owned by CODE-1's bounded wait; a "sizing reconciliation" change that edits nothing adds surface against the minimal-change principle. A single "confirm the rendered preStop cap covers the shared eviction budget" assertion folds into CODE-1's TEST-1 coverage.
- **Building a forced-acquisition / lease-steal primitive on the coordination lease**, or any within-grace-window takeover of a still-live lease. The leasestore holder invariant (`ErrHeld`) is preserved; the unreachable-coordinator residual is recovered by the §10.1 TTL-driven handoff and accepted as dropping to the minimal-state fallback.
- **Building a gateway-side agent-pod informer/watcher seam.** The coordinator-direct control-channel signal is the chosen seam (0052 sign-off); no pod watch, dedup, or per-replica ownership layer is added.
- **Building the §7.2 message-delivery semantics or the other cross-replica coordinator consumers.** This proposal builds only the generic coordinator-forward *transport* (coordinator resolution, the `coordinator_address`, the inter-replica port and NetworkPolicy self-peer, and the extensible forward RPC) with the eviction-drive as its first payload. The §7.2 *message* subsystem — the seven delivery paths, the in-memory/Redis durable inbox, the DLQ, resume-and-deliver, and delivery receipts (`spec/07_session-lifecycle.md:330`, its own §18 build-sequence slot at `spec/18_build-sequence.md:357`) — is out of scope. The other off-holder-broken coordinator consumers (`POST /v1/sessions/{id}/messages`, `interrupt`, and `upload-to-session`) are named as future users of this transport; fixing them is a later proposal that layers their payloads on it rather than this one.
- **Weakening the `shareProcessNamespace` prohibition** (`spec/13_security-model.md` §13.1, `spec/04_system-components.md:243`) or introducing cross-container process signaling. The best-effort snapshot reads the shared workspace `emptyDir`; it does not signal the runtime process.
- **Changing the embedded deployment model** (single first-party container). It carries no separate hookless runtime, so it needs no fallback change; it reaches the same SIGTERM handler and eviction drive.
- **Adding a new lifecycle-channel frame on the kubelet path.** The existing `RequestCheckpoint`/`checkpoint_request` handshake is attempted first; the best-effort snapshot is the fallback when it cannot complete. No new terminate/quiesce frame is driven from the kubelet path.
- **Re-justifying the §5.2/§10.1 admission termination-grace floor** (0056 owns it). SPEC-3 corrects the agent-pod grace attribution on the §4.4:264/:278 eviction-checkpoint budget and names the agent-pod bound in §4.6.1; it does not restate or change the admission floor. The §4.4:264/:278 correction is scoped to the grace figure on the agent-pod eviction bullet and does not touch the retry-budget totals or the fallback flow.

### Pass 1 (2026-07-22, automated)

- **The best-effort consistency tag and resume marker were removed because no surface carries, persists, or surfaces one.** The proposal made normative that the eviction snapshot is "tagged `consistency: best-effort`" and that resume restores the workspace "with a best-effort consistency marker instead of `workspaceLost: true`" (Decisions, §4, the §5 edge table, SPEC-2, CODE-2, TEST-1, and TEST-3), while §11 added no proto, migration, gateway-catalog, resume-event, or §7.2 edit to carry it. Verification confirmed the gap: `CheckpointStart`/`CheckpointSummary` carry no `consistency` field (`schemas/lenny-adapter.proto:1101,1187`), neither `checkpoint_manifest` (`migrations/0178_checkpoint_manifest.up.sql:30`) nor `session_checkpoints` has a `consistency` column, `pkg/checkpoint`'s `ConsistencyTag`/`ConsistencyBestEffort` have no production consumer, and the §7.2 `session.resumed` event (`spec/07_session-lifecycle.md:138`) enumerates `resumeMode` as `full`, `conversation_only`, `partial_workspace`, or `coordinator_handoff` with a boolean `workspaceLost` and no consistency field (mirrored at `docs/client-guide/wire-format.md:183`). A best-effort eviction snapshot that restores the workspace therefore resumes as `resumeMode: full` with `workspaceLost: false`, so the tag and marker language asserted a distinction no field defines. The finding's two options were adding the full plumbing (proto field, migration, gateway recording, a §7.2/§15 event field, and SDK plus client-doc mirroring) or dropping the marker language. The second option was taken: it is the choice consistent with the proposal's minimal-surface principle and with the spec's existing best-effort model, which tags Basic/Standard checkpoints by runtime level and relaxes tool-call consistency on the eviction and SIGSTOP paths without a per-resume marker (`spec/04_system-components.md:242-243`). The snapshot now persists as an ordinary workspace checkpoint that resumes as `resumeMode: full` with `workspaceLost: false`, the eviction path's tool-call-consistency relaxation is documented in §4.4 rather than surfaced per-checkpoint or per-resume, and the same predicate is propagated across the Decisions bullet, §4, the §5 edge-case row, the SPEC-2 staged text, CODE-2, TEST-1, and the TEST-3 tier-5 assertion. No new files are added to §11.
- **TEST-1.2 gained the missing eviction-path fail-closed deny cell.** The listing exercised the classifier on one axis only, varying the trigger (eviction vs periodic) while holding the error class at dropped-connection, so the cell CODE-2.2 explicitly names (`TriggerEviction` with a non-dropped-connection error, a live runtime present but refusing to quiesce) was untested. ### Pass 2 (2026-07-22, automated)

- **The best-effort downgrade was re-scoped off the `TriggerEviction` trigger value onto the adapter's own pod-termination state, because the trigger is shared with the gateway-drain barrier path.** CODE-2 originally scoped the downgrade to "the `TriggerEviction` path only" (§4, the §2 Decisions bullet, the §5 edge table, SPEC-2, CODE-2, and TEST-1.2), while §2 simultaneously stated that both the §10.1 gateway-drain barrier path and the new individual-eviction consumer call the same `Checkpointer.CheckpointWithTrigger(..., TriggerEviction)`. Verification confirmed the conflict: `barrier.go:228` drives `TriggerEviction` from the gateway-drain quiesce-and-hold fan-out (`barrier.go:215-221`), during which the agent pod keeps running and its session continues after coordinator handoff, and the adapter that serves the `Checkpoint` RPC derives the trigger solely from `CheckpointStart` (`checkpoint.go:128`), so it cannot tell the two paths apart from the trigger alone. The trigger-only predicate therefore also matched a barrier checkpoint whose lifecycle connection dropped transiently, which would have archived a mid-write best-effort snapshot for a still-running session and silently converted the existing fail-closed gate (`checkpoint.go:158-160`) into a downgrade on a path the safety rationale ("the pod is terminating regardless") does not cover. The finding's two options were gating on the absence of a linked quiesce-and-hold barrier (`!linked` at `checkpoint.go:123`) or threading an explicit "pod is terminating" signal. ## 12. Revision for the co-located coordination model (2026-07-26)

Proposal 0060 co-locates the session-coordination lease with the pod binding, so the coordinator is by construction the replica holding the session's binding. This proposal was written against the decoupled model, and its spec edits had already been applied, so the revision below reconciles it. The eviction route, the decisions, and the three ratified sign-off decisions are otherwise unchanged.

**The driver leg is retired, not adapted.** The staged drive resolved its adapter connection through the barrier path's Conn-or-Dial fresh-dial because the binding-gated `CheckpointWithTrigger` returned `ErrNoBinding` on a coordinator that held the lease but not the binding. Under 0060 that state does not exist, and 0060 deletes the Conn-or-Dial resolution outright as production-dead. The drive now reuses `CheckpointWithTrigger` unchanged, and the binding-free checkpointer entry point this proposal staged is no longer added. Resuming the implementation against the pre-0060 text would not have compiled.

**The forward leg survives, on one case rather than two.** The staged forward rested on two cases. The rolling-update case, where a lease moves to a replica that never re-bound while the control stream stays on the old one, does not survive 0060's eager fence-first re-adopt: the binding and the coordinator move together. The concurrent-session case does survive and is sufficient on its own. `podsession.Registry` is keyed by session id and a slot claim is a shared-state operation against the `SandboxClaim` CR, so two slots on one `maxConcurrentSessions > 1` pod can be bound, and therefore coordinated, on different replicas while a single replica consumes the pod's one control stream. An `AdapterEvicting` for a co-tenant session still lands on a replica that does not coordinate it. The `coordinator_address` column, the by-session mirror read, the inter-replica port, the §13.2 peer (SPEC-4), the chart self-peer (CHART-1), and the generic coordinator-forward transport are therefore all retained.

**The forwarded payload loses the pod dial address.** It carried the agent pod's dial address so the coordinator could fresh-dial the adapter. The coordinator now reaches the pod over its own held binding, so the payload is tenant, session, and slot.

**The mirror seed folds into 0060's at-bind lease acquire.** The staged seed added a shared helper called from `registerBinding` and the snapshot-restore branch of `resumeOnPod`. 0060 already runs `acquireCoordinationLease` at exactly those live-binding publish sites, but that helper calls `leasestore.Acquire` alone and writes no mirror row, so the pre-first-sweep window it leaves is real and the seed is still needed. It now extends that one helper rather than adding a second bind-time seam, which keeps the lease acquire and the mirror seed from naming different replicas. Under co-location the first sweep confirms the seeded row rather than correcting it.

**Three clauses of the applied spec text are corrected (SPEC-6).** The applied §4.6.1 text asserts the seeded binding replica "holds no coordination lease," which 0060 makes false; it carries a "when it does not already hold the session's binding" conditional that can no longer fire; and it justifies the forward partly by the retired lease-moved-without-rebinding case. SPEC-6 stages those corrections.

**Test reconciliation already landed on the branch.** Two mirror-address tests set up an unbound session and expected the sweep to acquire a lease for it. 0060's rescoped sweep renews what the replica binds and adopts only lapsed still-running-pod orphans, so they failed on the merge. They now bind the session they mirror, and the handoff case models the binding moving between replicas with the lease travelling with it.
