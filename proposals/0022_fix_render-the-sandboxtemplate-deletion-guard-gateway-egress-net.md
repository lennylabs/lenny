# Proposal: Render the sandboxtemplate-deletion-guard gateway-egress NetworkPolicy and reconcile the §13.2/§17.2 admission-plane spec (close F-13.2.24 / SEC-WEBHOOK-1)

- **Status:** Applied to spec (2026-07-02). Converged after 4 adversarial review rounds (5 findings fixed). Decision 1 resolved: the deletion-guard is a baseline implementation-only webhook (like `lenny-pod-security` / `lenny-tenant-label-immutability`), so it gains the §13.2 egress sub-rule and additive label but is not enumerated in the §17.2 numbered catalogue and carries no dedicated §16.5 alert. The webhook remains fail-closed (Decision 2 left as-is per the user).
- **Date:** 2026-07-01.
- **Scope:** Restores the gateway-probe egress the `lenny-sandboxtemplate-deletion-guard` fail-closed webhook needs, which the §13.2 `lenny-system` default-deny drops today, and reconciles the spec so the chart is permitted to render that egress. This is the dedicated proposal 0021 recorded in its Non-goals for the OPEN finding `F-13.2.24` (also carried as `SEC-WEBHOOK-1`). The fix lands a §13.2 admission-webhook egress sub-rule, a minimum §17.2 reconciliation forced by that sub-rule, a chart NetworkPolicy plus the additive webhook-name label, and the chart/e2e/isolation test coverage. It touches `spec/13_security-model.md`, `spec/17_deployment-topology.md`, `charts/lenny/templates/admission-policies/sandboxtemplate-deletion-guard-webhook.yaml`, and the chart and cluster tests. The confirmed impact is narrower than the BUILD-GAPS "no SandboxTemplate can be deleted" framing, and this proposal scopes the correction to the confirmed impact.

This document stages the proposed spec, chart, and test changes for the implementation step. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

The `lenny-sandboxtemplate-deletion-guard` is a fail-closed `ValidatingAdmissionWebhook` on `DELETE` of `sandboxtemplates` (`charts/lenny/templates/admission-policies/sandboxtemplate-deletion-guard-webhook.yaml:27-28`, `failurePolicy: Fail`, `timeoutSeconds: 5`). Its decider lists the `SandboxWarmPool`s whose `spec.templateRef` names the deleted template and probes the gateway `GET /internal/runtime-upgrade/active` endpoint for each pool's upgrade state (`pkg/admission/webhook/sandboxtemplate_deletion_guard.go:110-132`). The probe target is wired to the gateway internal port through the webhook workload include (`charts/lenny/templates/admission-policies/_webhook.tpl:76`, `--gateway-runtime-upgrade-active-url=http://lenny-gateway.<ns>.svc:<internalPort>/internal/runtime-upgrade/active`), and the gateway serves that endpoint at `cmd/lenny-gateway/httpsurface.go:528`.

Under the §13.2 `lenny-system` default-deny, the shared `allow-admission-webhooks` egress policy admits only kube-apiserver and kube-system CoreDNS egress for the admission-webhook pods (`charts/lenny/templates/system-network-policies.yaml:52-79`). The only webhook granted gateway egress is `lenny-drain-readiness`, through its dedicated `allow-drain-readiness-gateway-egress` NetworkPolicy narrowed to `lenny.dev/webhook-name: drain-readiness` (`charts/lenny/templates/admission-policies/drain-readiness-webhook.yaml:32-52`). The deletion-guard template renders no NetworkPolicy and passes no `egressLabel`, so its pods carry only `lenny.dev/component: admission-webhook` (`_webhook.tpl:52-56`) and its probe hop to the gateway is dropped, timing the fail-closed webhook out and failing the `DELETE` closed with a 503.

The chart cannot simply mirror drain-readiness. NET-068 (`spec/17_deployment-topology.md:56`) forbids adding a per-webhook egress label to any other webhook unless a future egress-narrowing need is documented in §13.2 alongside a corresponding sub-rule, and the deletion-guard is absent from the §13.2 admission-webhook row (`spec/13_security-model.md:221`) and the §17.2 catalogue and HA paragraph (`spec/17_deployment-topology.md:46-56`). This is a spec-first change: §13.2 adds the sub-rule and names the additive label, §17.2 acknowledges the deletion-guard as an admission-webhook Deployment carrying that label so the §13.2 cross-reference resolves, and only then may the chart render the egress policy.

### 1.1 Confirmed impact is narrower than BUILD-GAPS states

BUILD-GAPS records F-13.2.24 as "no SandboxTemplate can be deleted at all." That framing is refuted by the decider's per-pool probe condition. The guard hits the gateway only when a referencing `SandboxWarmPool` exists: a template with zero referencing pools, or a nameless collection delete, is `Allow`ed without any gateway hop (`sandboxtemplate_deletion_guard.go:104-109,132`). The automated pool-delete teardown never deletes the `SandboxTemplate`: `drainAndDeleteWarmPool` deletes only the `SandboxWarmPool` CRD and the caller retains the `SandboxTemplate` (`pkg/controller/poolscaling/controller.go:524-527,805`), so pool teardown is not blocked by the missing policy. The confirmed defect is confined to a `DELETE` that reaches the probe: an operator or tool deleting a `SandboxTemplate` (for example via `kubectl`) while at least one referencing `SandboxWarmPool` still exists, which then fails closed with a 503 under default network policies. The fix restores that path and closes the §13.2/§17.2 admission-plane reconciliation the additive-label render requires.

## 2. Decisions

- **Mirror the established drain-readiness pattern rather than invent a parallel mechanism.** Add a §13.2 admission-webhook egress sub-rule that grants gateway internal-port egress narrowed to `lenny.dev/component: admission-webhook` AND `lenny.dev/webhook-name: sandboxtemplate-deletion-guard` (the NET-068 additive label), and render `allow-deletion-guard-gateway-egress` as a copy of `allow-drain-readiness-gateway-egress`. This reuses the NET-068 additive-label affordance and the `_webhook.tpl` `egressLabel` parameter. No new label key, endpoint, or config value is introduced.
- **Reconcile §17.2 to the minimum the §13.2 edit forces, and keep the deletion-guard in the implementation-only set.** The §13.2 admission-webhook row and the §17.2 HA paragraph both count "the nine webhook Deployments enumerated in §17.2" and cross-reference that enumeration. Adding an egress sub-rule and a webhook-name additive label, and naming the deletion-guard as a labeled admission-webhook Deployment that already receives base egress, makes those counts, the "enumerated in §17.2" cross-reference, and the "purely in-process validators" clauses internally inconsistent unless both sections acknowledge the deletion-guard as an admission-webhook Deployment carrying the additive label with a documented gateway-egress sub-rule. The reconciliation is limited to that: a dedicated additive-label and HA sentence parallel to the drain-readiness sentence, the four count-free rewordings in §13.2 plus the count-free rewording in §17.2 per `doc-style.md`, and the "in-process validators" clauses reworded to exempt the two gateway-probing webhooks. The deletion-guard is deliberately kept out of the §17.2 line-56 `replicas: 2` enumeration governed by the SLO/1:1-alert clauses (mirroring `lenny-pod-security` and `lenny-tenant-label-immutability`, which §17.2 line-56 also omits) so §17.2 does not assert a per-webhook §16.5 alert the deletion-guard lacks (see the S2 design decision and Decision §2 below). The deletion-guard is not added to the §17.2 numbered admission-policies catalogue and is not moved out of `implementationOnlyValidatingWebhooks` (`pkg/preflight/webhooks.go:139-145`). The spec already carries a deliberate, machine-checked mechanism for admission webhooks that ship but are not in the numbered catalogue, and the deletion-guard already lives in that set with an `F-10.5.14` comment recording the divergence as intentional (`webhooks.go:127-131,143`). `lenny-pod-security` and `lenny-tenant-label-immutability` are likewise unconditional fail-closed baseline webhooks the spec keeps out of the numbered catalogue, so "unconditional and fail-closed" does not compel numbered-catalogue enumeration. Keeping the deletion-guard in the implementation-only set keeps `CatalogueCoverage` (`webhooks.go:165-194`) green with no preflight code change, so no `F-10.5.14` closure is coupled to this network fix.
- **No per-webhook `SandboxTemplateDeletionGuardUnavailable` alert is added.** The premise that every fail-closed webhook carries a 1:1 `Unavailable` alert does not hold: `lenny-pod-security` (`webhooks.go:39`, `failurePolicy: Fail` at `charts/lenny/templates/admission-policies/pod-security-webhook.yaml:30`) and `lenny-tenant-label-immutability` (`webhooks.go:35`, `failurePolicy: Fail` at `charts/lenny/templates/admission-policies/label-immutability-webhook.yaml:65`) are baseline, unconditionally-rendered, fail-closed webhooks with no dedicated per-webhook `*Unavailable` alert. `spec165WarningAlerts` (`pkg/alerting/rules/rules_test.go`) is a hand-curated allowlist, and the completeness tests enforce only that the code catalog and §16.5 agree with each other, not that every webhook has an alert. The alert is not needed to fix the confirmed defect (the network path plus the §13.2/§17.2 reconciliation resolve it), so no §16.5 row, no `pkg/alerting/rules/rules.go` rule, and no regenerated alerting artifacts are touched.
- **Scope the correction to the confirmed impact** (§1.1): a `DELETE` that reaches the gateway probe because a referencing `SandboxWarmPool` exists. The proposal does not repeat the every-deletion-blocked framing, and it does not change the automated pool-delete teardown, which retains the `SandboxTemplate` by design.
