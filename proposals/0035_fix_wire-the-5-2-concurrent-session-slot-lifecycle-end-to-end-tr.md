# Proposal: Wire the §5.2 concurrent-session slot lifecycle end to end: trigger the concurrent whole-pod scrub, emit ReportSessionScrub so maxSessionsPerPod is enforced, keep a leaked slot counted, retire a persistently-leaked pod, and consume the drain-request annotation (F-5.2.31; supersedes 0035 v1-v3)

- **Status:** Verified (2026-07-02). Converged after 9 adversarial review rounds (24 findings fixed); awaiting sign-off.
- **Date:** 2026-07-02.
- **Scope:** A spec-to-code reconciliation that wires the §5.2 concurrent-session (`maxConcurrentSessions > 1`) and per-session-release slot lifecycle at five verified points. Four are code defects against already-committed spec (§5.2 whole-pod scrub trigger, §4.7/§5.2 `ReportSessionScrub`, §6.2 leaked-slot occupancy accounting, §4.6.1/§4.6.3 drain-request consumer); one adds the §5.2/§6.2/§10.3 liveness edit that counts a leaked slot toward the unhealthy threshold from its persistent count rather than a rolling-window event that ages out and amends the §5.2 `maxSessionsPerPod` retirement so a concurrent non-`vm-restart` pool drains per session release decoupled from the whole-pod scrub. The change touches `spec/05_runtime-registry-and-pool-model.md`, `spec/06_warm-pod-model.md`, `spec/10_gateway-internals.md`, `spec/12_storage-architecture.md`, and `spec/16_observability.md` (**SPEC-D**), the adapter scrub-trigger and slot-release paths (`pkg/adapter`, **CODE-A**, **CODE-B**), the gateway recycle-boundary and slot-release code (`pkg/gateway/podlifecycle`, `pkg/gateway/mcpfabric/delegationtree/leasecontrol`, `pkg/gateway/session/recycle`, `pkg/gateway/runtime/slothealth`, **CODE-A**, **CODE-C**, **CODE-D**), the sandbox pod spec (`pkg/controller/sandbox/podspec`, **CODE-B**), the WarmPoolController pod reconciler (`pkg/controller/warmpool`, **CODE-E**), and new tests across tiers 1, 2, 3, 4, 7a, 9, 10, and 11. It closes **F-5.2.31** (`BUILD-GAPS.md:4050`) and supersedes the three prior 0035 versions (git `3186ca15`, `5b84b052`, `9c302a05`). The whole mechanism runs on the `runc` RuntimeClass kind provides and carries no Kata dependency.

This document stages the proposed spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

The §5.2 concurrent-session and per-session-release slot lifecycle is unwired at five verified points. Four are code that fails to implement committed spec; one adds a §5.2/§6.2/§10.3 edit that fixes the leaked-slot counting lifetime and amends the concurrent-pool `maxSessionsPerPod` retirement.

### (A) The concurrent whole-pod scrub trigger is missing

§5.2 requires a whole-pod scrub whenever occupancy reaches zero on a recycling pod, reported via `ReportPodScrub`, uniform across session modes. In concurrent mode a slot-qualified `Shutdown` early-returns to `shutdownSlot` (`pkg/adapter/session.go:226-228` → `pkg/adapter/slotsession.go:63-88`), which tears down one slot, returns `ExitedCleanly`, and never calls `startPodScrub` or reads `req.GetRecycle()`. The whole-pod scrub (`startPodScrub`, `pkg/adapter/podscrub.go`) has one production caller, the slot-less `Shutdown` path (`pkg/adapter/session.go:256-258`), gated by `checkSession` requiring `s.sessionID != ""` (`pkg/adapter/session.go:320-329`); concurrent `startSessionSlot` sets only the per-slot `st.sessionID` and never `s.sessionID` (`pkg/adapter/slotsession.go:45`), so the gate can never pass. Gateway-side `SlotClaimer.ReleaseSlot` patches the claim `bound → recycling` and arms the missing-report timeout (`pkg/gateway/podlifecycle/podclaim/slotclaimer.go:679-703`) expecting an adapter scrub that never runs, so a recycling concurrent pool at occupancy zero is retired by the timeout rather than scrubbed and reused. This is the availability gap F-5.2.31 records (`BUILD-GAPS.md:4058-4062`).

### (B) `recycle.maxSessionsPerPod` is inert

§5.2 (`spec/05_runtime-registry-and-pool-model.md:541`) and §4.7 require the adapter to report each per-slot cleanup outcome (`released` or `leaked`) via `ReportSessionScrub`, which increments `sessions_served`. No production adapter path emits it: `Client.ReportSessionScrub` (`pkg/adapter/gatewaycontrol/scrubreport.go:80`) has only test callers, and `slotsession.go`/`session.go` never emit it. The sole writer of `sessions_served` is `ScrubReporter.RecordSessionScrub` (`pkg/gateway/mcpfabric/delegationtree/leasecontrol/scrubreport_server.go:397-398` → `IncrementSessionsServed`), reachable only via the unemitted RPC, so the `maxSessionsPerPod` check in `podscrub.Decide` (`pkg/sandbox/podscrub/podscrub.go:358`) never fires. The same handler calls `drainLedger.RecordLeak` on a leaked outcome (`scrubreport_server.go:409`), so the entire gateway-side leak ledger is also unreached in production. This is inert in **both** session modes: the base (`maxConcurrentSessions == 1`) recycle `Shutdown` path runs `startPodScrub` on `req.GetRecycle()` and never emits `ReportSessionScrub` either, so `advanceScrubCounters` (`scrubreport_server.go`) reads back a `sessions_served` that no path advanced.

### (C) A leaked slot is wrongly un-counted

§6.2 (`spec/06_warm-pod-model.md:151`) requires a leaked slot to remain counted in the pod's Redis slot-counter occupancy so the gateway does not over-assign new slots into the leaked slot's unreleased resources. `SlotClaimer.ReleaseSlot` decrements the Redis counter unconditionally (`pkg/gateway/podlifecycle/podclaim/slotclaimer.go:669`), and `Binder.ReleaseSlot` discards the `ShutdownSlot` `exitedCleanly` result (`_, _ = result.Adapter.ShutdownSlot(...)`, `pkg/gateway/podlifecycle/podsession/slotbinder.go:498`), so a leaked slot is decremented. The Redis counter is the sole over-assignment gate (`pkg/gateway/storage/slotcounter/slotcounter.go:196-204`); `slotstate.Registry.ActiveCount`, which would keep a leaked slot counted, has zero production callers.

### (D) A persistently-leaked pod has two liveness gaps exposed by fixing C

Once a leaked slot stays counted (C), two occupancy-zero-gated retirements can never fire for a concurrent pool carrying a permanent leak:

- **Aging-out of the health count.** A leaked slot is physically permanent until pod termination (`spec/06:146`, `spec/05` slot-cleanup bullet), but `slothealth` records each leak as a timestamped `event` pruned by a rolling 5-minute window (`pkg/gateway/runtime/slothealth/slothealth.go:24-31`, `:88-113`, `pruneLocked` at `:148-170`). Permanent leaks arriving more than five minutes apart age out of the health count and never accumulate toward the `ceil(maxConcurrentSessions/2)` "fail or leak" threshold, so the existing `drainLedger` (`pkg/gateway/session/recycle/scrubreporter_seams.go:184-199`) never trips for slowly-accumulating permanent leaks. The threshold itself and its drain-request stamp are already wired; the defect is that leaks are counted with the wrong lifetime.
- **Occupancy-zero-gated limits never fire.** `maxSessionsPerPod` and `maxPodUptimeSeconds` are evaluated only inside `podscrub.Decide` (`pkg/sandbox/podscrub/podscrub.go:358,:369`), reached only via `RecordPodScrub` at the total-occupancy-zero recycle boundary. With C keeping a leaked slot counted, total occupancy never reaches zero on a pool holding a single sub-`ceil` permanent leak (`1 < ceil >= 2` on a `maxConcurrentSessions >= 3` pool), so a pool that keeps serving sessions past `maxSessionsPerPod`, or past `maxPodUptimeSeconds`, never retires. `RecordSessionScrub` advances `sessions_served` on every release (B) but never checks the limit.

### (E) The drain-request annotation is stamped but never read

§4.6.1/§4.6.3 require the unhealthy-threshold drain to derive from the gateway-stamped `lenny.dev/drain-request` annotation, WarmPoolController-written. The annotation (`pkg/apis/lenny/v1alpha1/annotations.go:39`) is stamped by `StampDrainRequest` (`pkg/gateway/podlifecycle/podclaim/slotclaimer.go:94-96`) and its doc comment (`annotations.go:27-38`) asserts a WarmPoolController consumer, but no controller reads it: the `PodReconciler` reads only `AnnotationCertNotAfter` (`pkg/controller/warmpool/pod_reconciler.go:411,:428`). An exhaustive non-test grep finds the annotation written and never read, so both drain-request writers (the existing `drainLedger` ceil-threshold stamp and the C/D leaked-slot paths) are unwired end to end.

## 2. Decisions

- **Spec-first for SPEC-D only.** A, B, C, and E are code that fails to implement committed spec (§5.2 whole-pod scrub trigger, §4.7/§5.2 `ReportSessionScrub`, §6.2 leaked-slot occupancy, §4.6.1/§4.6.3 drain-request consumer); they need no spec edit. SPEC-D carries the normative edits: the leaked-slot counting-lifetime change (§5.2:557, §6.2:151, §6.2:133, reconciled in §10.3:54), and the `maxSessionsPerPod` retirement amendment (§5.2:486, a new §6.2:135 concurrent-occupancy edge, reconciled in the §12:467/:480 schema prose and comment and the §16:12 retirement-counter row) that decouples a concurrent non-`vm-restart` pool's `maxSessionsPerPod` retirement from the whole-pod scrub, which CODE-D/D2 requires; the amendment excludes concurrent `vm-restart` pools so the existing `:486` `vm-restart` carve-out (retire at the occupancy-zero recycle boundary with `vm_restart_reprovision`) stays intact. The `maxPodUptimeSeconds` retirement mechanism is unchanged, a WarmPoolController-owned, `CreationTimestamp`-derived level-triggered drain whose code companion is CODE-E, but its §5.2/§6.2 text is reconciled: the **Uptime limit** bullet (§5.2:487) and the base occupancy-projection `idle → draining` uptime edge (§6.2:100) currently describe a gateway-driven, dispatch-gated check that contradicts §4.6.1:398 and the §6.2:135 concurrent-occupancy uptime edge and cannot reclaim an idle or placement-frozen over-uptime pod, so SPEC-D rewords `:487` and `:100` to the `CreationTimestamp`-derived WarmPoolController drain those sections already state. SPEC-D lands and verifies before its slothealth and per-release-retirement code companions.
- **Reuse the specified surfaces; add no new protocol.** A reuses the existing recycle-disposition `Shutdown` (`RecycleScrub` already carries `pod_id`) and `ReportPodScrub`; B reuses the existing `ReportSessionScrub` RPC and the `gatewaycontrol.Client` that already implements it; D and E reuse the existing `lenny.dev/drain-request` annotation, the existing `drainLedger`/`StampDrainRequest` path, and the existing `podscrub.Decide` disposition. No new RPC, proto field, endpoint, or CRD field is introduced.
- **The adapter emits `ReportSessionScrub`.** §5.2/§4.7 name the adapter as the reporter of the per-slot cleanup outcome, so the adapter emits the RPC rather than the gateway recording the outcome directly (a gateway-direct increment would contradict §4.7). The adapter obtains its pod identity from a Downward API `POD_NAME` env on the agent container and caches it on the `Server`, since `ShutdownSlot` carries no `pod_id` and the base recycle `Shutdown` carries `pod_id` only inside `RecycleScrub`.
- **Emit `ReportSessionScrub` in both session modes.** §5.2 states `recycle.maxSessionsPerPod` "applies as configured at every level" and "counts every session served," and `advanceScrubCounters` reads the count back rather than re-incrementing it. B therefore emits on the base recycle `Shutdown` path as well as the concurrent `shutdownSlot` path, so `maxSessionsPerPod` becomes functional in both modes. The prior draft's claim that base mode "already works" is corrected: base-mode `maxSessionsPerPod` is equally inert today.
- **Gate the Redis-counter decrement without relocating the release.** `Binder.ReleaseSlot` already calls `ShutdownSlot` synchronously before the decrement, and `ShutdownSlot` already returns `exitedCleanly`. C consumes the already-computed value and threads a `leaked` flag into `SlotClaimer.ReleaseSlot` to skip the decrement, so a leaked slot stays counted.
- **Count a leaked slot toward the ceil threshold from its persistent count.** A leaked slot persists until pod termination, so SPEC-D counts it against `ceil(maxConcurrentSessions/2)` from a persistent per-pod count (the `lenny_adapter_leaked_slots` gauge / Redis slot-counter occupancy that already keeps it counted) rather than as a rolling-window event that ages out. Failed slots keep their rolling-window semantics because a failure is transient. This preserves the existing "leaked_slots alone reaches ceil" clause and the deliberate sub-`ceil` tolerance in §5.2; it does not add a retire-on-first-leak trigger, and it does not reverse the §5.2 "a pod accumulating leaks is as degraded as one accumulating outright failures" rationale.
- **Close the occupancy-zero-gated retirement gap with a per-release `maxSessionsPerPod` check on concurrent pools.** Because C keeps a leaked slot counted, total occupancy never reaches zero on a concurrent pool holding a sub-`ceil` permanent leak, so the occupancy-zero-gated `maxSessionsPerPod` in `podscrub.Decide` never fires. A live-(non-leaked)-occupancy-zero evaluation does not close the gap: on a `maxConcurrentSessions >= 3` pool carrying one leaked slot the live slots keep cycling under sustained load, so a clean release drops the counter and an immediate re-claim raises it again, and the counter never rests at the leaked-slot floor. CODE-D/D2 therefore evaluates the served-session count on every session release in the `RecordSessionScrub` handler (where CODE-B already advances it via `IncrementSessionsServed`), decoupled from occupancy, gated on `maxConcurrentSessions > 1 && scrubProfile != vm-restart`. It separates the two concerns the single crossing conflates, and gives each its own predicate. The `lenny.dev/drain-request` stamp is level-triggered on `count >= maxSessionsPerPod` and re-issued idempotently on every qualifying release while the count stays at or above the bound, mirroring the existing `drainLedger.RecordLeak`, which re-calls the idempotent `StampDrainRequest` on every leak while its `>=` `tracker.Unhealthy` predicate holds (`scrubreporter_seams.go:184-196`). A merge-patch re-stamp is a no-op-cost idempotent PATCH, so a single lost or duplicated crossing report is recovered on the next release rather than abandoning the pod: `StampDrainRequest` tolerates only `NotFound` and returns any other error including a `409` conflict (`slotclaimer.go:94-107`), and `RecordSessionScrub` carries no dedup key and can error after committing the `IncrementSessionsServed` increment (`scrubreport_server.go:397-409`), so at-least-once redelivery can drop a stamp or double-increment the count. The `lenny_pod_retirement_total` increment is gated on the exact-equality crossing `count == maxSessionsPerPod`, true for exactly one release because the count is monotonic and advances by one per release, so the retirement counter records one increment per retirement matching the single-session path while the drain stamp stays retry-safe. Gating the stamp itself on exact equality would make the load-bearing drain one-shot with no re-evaluation, so a single failed PATCH would leak the pod indefinitely, which is strictly less reliable than the codebase's existing `drainLedger` re-stamp and is the exact failure D2 exists to prevent. A single-session pool takes no per-release stamp and retires through the occupancy-zero `podscrub.Decide` check with `ReasonSessionCountLimit`, matching the single-session clause of the `spec/05:486` amendment. A concurrent `vm-restart` pool also takes no per-release stamp: it retires at the occupancy-zero recycle boundary with the `vm_restart_reprovision` reason, which `podscrub.Decide` ranks above the session-count branch, so the per-release drain excludes it to preserve that precedence and the `:486` `vm-restart` carve-out. This guarantees a concurrent leaked pod drains within `maxSessionsPerPod` sessions regardless of live-slot overlap, resolving the retirement bound the live-occupancy-zero placement cannot guarantee. It reuses the existing `drainLedger`/`StampDrainRequest` path and adds no second drain-request stamper. This per-release retirement is the code companion to the `spec/05:486` amendment in SPEC-D. The `maxPodUptimeSeconds` retirement is not routed through this per-release check: a wall-clock bound advances while a pod is idle and `expiredByUptime` freezes placement once it is exceeded, so an over-uptime leaked pod with no live slot would never see another release; the uptime reclaimer is instead the level-triggered `CreationTimestamp`-derived WarmPoolController drain (CODE-E), matching the `spec/04:398` split between uptime drains and the drain-request annotation.
- **E implements the stated consumer contract.** §4.6.1/§4.6.3 already name the WarmPoolController as the drain-request reader and the sole writer of `Sandbox.status`, so the `PodReconciler` gains a `lenny.dev/drain-request` read and the draining transition alongside the way it already reads `AnnotationCertNotAfter`, driving `patchSandboxDraining` with `requireIdle=false` (the `reconcileCertIssuance` projection) because a drain-requested concurrent pod carrying a leaked slot is `claimed`/`active` rather than idle, so the idle-gated `reconcileCertExpiry` projection would skip it.
- **Supersede the three prior 0035 versions** (git `3186ca15`, `5b84b052`, `9c302a05`). This proposal is the single canonical wiring of the concurrent slot lifecycle and folds A-E into one coherent change set.
- **Classified `fix`.** The dominant action reconciles code to committed spec and wires already-specified surfaces end to end; the lone SPEC-D edit tightens the counting lifetime of an existing retirement policy rather than adding a new subsystem.

## 3. How the pieces fit at the occupancy-zero boundary

A concurrent recycling pod releases slots one at a time through `Binder.ReleaseSlot` → `SlotClaimer.ReleaseSlot`. Each release calls `ShutdownSlot` synchronously (which returns `exitedCleanly`) and emits `ReportSessionScrub` for the slot (B), advancing `sessions_served` and, on a leaked outcome, feeding the leak ledger. The Redis counter is decremented only when the slot released cleanly (C); a leaked slot stays counted.

When every slot released cleanly, the last release drives the Redis counter to zero, `SlotClaimer.ReleaseSlot` patches the claim to `recycling`, and the gateway sends the adapter a whole-pod recycle `Shutdown` carrying the last-released slot's `session_id` (so the adapter's non-empty `session_id` guard admits it) and the `RecycleScrub` disposition, so `startPodScrub` runs steps 0-6 and reports `ReportPodScrub` (A). `RecordPodScrub` reads back `sessions_served` and runs `podscrub.Decide`, which reuses the pod or retires it on a limit (`maxSessionsPerPod`, `maxPodUptimeSeconds`), replacing the missing-report timeout that retired every concurrent pool before.

When a slot leaked, the Redis counter never reaches zero, so the whole-pod scrub does not run. Three liveness paths then apply. If leaks accumulate to `ceil(maxConcurrentSessions/2)`, the existing `drainLedger` stamps `lenny.dev/drain-request` from the now-persistent leaked count (SPEC-D). If a single sub-`ceil` leak persists on a concurrent non-`vm-restart` pool while live slots keep cycling, the per-release `maxSessionsPerPod` check (CODE-D/D2, gated on `maxConcurrentSessions > 1 && scrubProfile != vm-restart`) stamps `lenny.dev/drain-request` on the level predicate `count >= maxSessionsPerPod` and increments the retirement counter exactly once, on the single crossing release where the post-increment served-session count equals `maxSessionsPerPod`, decoupled from occupancy zero, so the pod is guaranteed to drain within `maxSessionsPerPod` sessions even while live slots keep the counter above the leaked-slot floor. Because a leaked slot holds occupancy above zero, the remaining in-flight slots finish and release after the crossing; those later releases re-issue the idempotent drain-request stamp (so a lost or duplicated crossing stamp is recovered on a subsequent release rather than abandoning the pod) but do not re-increment the retirement counter, which the exact-equality gate holds to one per retirement. A concurrent `vm-restart` pool is excluded from the per-release drain and retires at the occupancy-zero recycle boundary with the `vm_restart_reprovision` reason instead. If the pod exceeds `maxPodUptimeSeconds` while a leaked slot has frozen placement and no live slot is in flight (so no further session release occurs), the level-triggered `CreationTimestamp`-derived WarmPoolController uptime drain (CODE-E) reclaims it regardless of session activity, matching `spec/04:398` and the concurrent-occupancy uptime edge `spec/06:135`. In the first two paths the WarmPoolController reads the `lenny.dev/drain-request` annotation and drives the draining transition; in the uptime path it drives the same transition from the pod `CreationTimestamp`. Each drains the pod's remaining slots gracefully and retires it (E), reclaiming the leaked resource at pod termination.

## 4. Proposed changes

### SPEC-D. Count a leaked slot toward the ceil threshold from its persistent count, reconcile the §10.3 restatement, and amend the maxSessionsPerPod retirement to drain per session release on a concurrent pool

**Target:** `spec/06_warm-pod-model.md`, §6.2 the **`leaked` slot semantics** paragraph (`spec/06:151`), the base occupancy-projection `idle → draining` uptime edge (`spec/06:100`), the concurrent-occupancy diagram edge (`spec/06:133`), and a new concurrent-occupancy diagram edge for the per-release `maxSessionsPerPod` drain added parallel to the existing `maxPodUptimeSeconds` edge (`spec/06:135`); `spec/05_runtime-registry-and-pool-model.md`, §5.2 the Slot-retry-policy **Whole-pod replacement trigger** bullet (`spec/05:557`), the **Session count limit** retirement bullet (`spec/05:486`), and the **Uptime limit** retirement bullet (`spec/05:487`); `spec/10_gateway-internals.md`, the §10.3 whole-pod-connection-loss restatement of the trigger (`spec/10:54`); `spec/12_storage-architecture.md`, the `agent_pod_state` schema prose paragraph (`spec/12:467`) and the `sessions_served` column comment (`spec/12:480`); `spec/16_observability.md`, the `lenny_pod_retirement_total` inventory row (`spec/16:12`). The **Uptime limit** bullet (`spec/05:487`) is amended to match §4.6.1 (`spec/04:398`): its current text says the gateway checks uptime before dispatching the next session, a dispatch-gated mechanism that cannot reclaim an idle or placement-frozen over-uptime pod, so it is reworded to state the `maxPodUptimeSeconds` retirement is a WarmPoolController-owned, `CreationTimestamp`-derived, level-triggered drain (the gateway's role is the `expiredByUptime` placement freeze, and the existing concurrent-occupancy uptime edge `spec/06:135` already states the WarmPoolController drain). Its code companion is the level-triggered WarmPoolController drain in CODE-E rather than a per-release check.

**Anchor and change (spec/06:151).** The paragraph currently reads:

```
**`leaked` slot semantics.** A slot in the `leaked` state remains counted in the pod's Redis slot-counter
occupancy (preventing the gateway from over-assigning new slots that would conflict with the leaked slot's
unreleased resources). A leaked slot counts toward the `ceil(maxConcurrentSessions/2)` unhealthy threshold
defined in [Section 5.2](...) (the "**fail or leak**" whole-pod replacement trigger): leaked slots are combined
with `failed` slots in the rolling 5-minute count, and if `failed_slots + leaked_slots >= ceil(maxConcurrentSessions/2)`
within that window, the pod immediately transitions to `draining`. If `leaked_slots` alone reaches
`ceil(maxConcurrentSessions/2)` (independent of any `failed` slots), the pod also transitions to `draining` for
the same reason.
```

Reword the counting clause so `failed` and `leaked` slots are counted with different lifetimes. Keep the two threshold clauses. For example:

```
A leaked slot counts toward the `ceil(maxConcurrentSessions/2)` unhealthy threshold defined in
[Section 5.2](...) (the "**fail or leak**" whole-pod replacement trigger). Because a `leaked` slot persists
until pod termination while a `failed` slot is transient, the two categories are counted with different
lifetimes: a `failed` slot is counted within a rolling 5-minute window, and a `leaked` slot is counted
persistently for as long as the slot remains leaked (the persistent count is the `lenny_adapter_leaked_slots`
gauge, equivalently the leaked portion of the pod's Redis slot-counter occupancy). The pod transitions to
`draining` when the rolling-window `failed_slots` plus the persistent `leaked_slots` reaches
`ceil(maxConcurrentSessions/2)`. If `leaked_slots` alone reaches `ceil(maxConcurrentSessions/2)` (independent
of any `failed` slots), the pod also transitions to `draining` for the same reason. Counting leaks persistently
rather than within the rolling window prevents a pod that accumulates permanent leaks slowly (more than five
minutes apart) from aging each leak out of the health count and never reaching the threshold.
```

```
  claimed ──→ draining              (ceil(maxConcurrentSessions/2) slots fail or leak within 5-min
                                     window — pod marked unhealthy)
```

Reword the parenthetical so the window applies to failures and the persistent count applies to leaks, for example:

```
  claimed ──→ draining              (ceil(maxConcurrentSessions/2) slots fail (5-min window) or

```

**Anchor and change (spec/06:135, add a concurrent-occupancy `maxSessionsPerPod` edge).** The concurrent-occupancy block carries a `maxPodUptimeSeconds` mid-occupancy drain edge but no `maxSessionsPerPod` edge, so the amended `:486` per-release retirement has no diagram representation. The `maxPodUptimeSeconds` edge currently reads:

```
  claimed ──→ draining              (recycle.maxPodUptimeSeconds exceeded — no new sessions accepted,
                                     existing sessions drain)
```

Leave the `maxPodUptimeSeconds` edge unchanged (it is the WarmPoolController-owned level-triggered drain, `spec/04:398`), and add a parallel edge for the per-release `maxSessionsPerPod` drain, for example:

  claimed ──→ draining              (served-session count reaches recycle.maxSessionsPerPod on a
                                     session release, scrubProfile is not vm-restart — drain
                                     requested, existing sessions drain; decoupled from the
                                     occupancy-zero whole-pod scrub)
```

The edge is scoped to a non-`vm-restart` concurrent pool: a `vm-restart` pool retires at the occupancy-zero recycle boundary with the `vm_restart_reprovision` reason and is unaffected by the per-release `maxSessionsPerPod` drain (the existing occupancy-zero **Recycle edges** block and the `vm-restart` precedence in `podscrub.Decide` cover it).

The new per-release edge is the primary `maxSessionsPerPod` trigger for a concurrent non-`vm-restart` pool.

  idle ──→ draining                 (recycle.maxPodUptimeSeconds exceeded while idle, checked before
                                     next assignment)

Reword the parenthetical to drop "checked before next assignment" and state the WarmPoolController-owned, `CreationTimestamp`-derived, level-triggered drain, matching the amended `:487`, `spec/04:398`, and the concurrent-occupancy uptime edge `:135`, for example:

**Anchor and change (spec/05:557).** The **Whole-pod replacement trigger** bullet currently reads:

```
- **Whole-pod replacement trigger:** When `ceil(maxConcurrentSessions / 2)` or more slots on the same pod
  **fail or leak** within a rolling 5-minute window, the gateway marks the pod as unhealthy, drains remaining
  slots gracefully, and requests a replacement pod from the warm pool. ... Both categories contribute to the
  threshold: slots that transition to `failed` ... and slots that transition to `leaked` ... Leaked slots count

On that same single crossing release, emit `IncRetirement(ReasonSessionCountLimit, pool, runtimeClass)` through the `RetirementMetricsSink` the recycle package already exposes (`scrubreporter_seams.go:757-761`, `:788-790`), so a concurrent-pool `session_count_limit` retirement increments `lenny_pod_retirement_total{reason="session_count_limit"}` exactly once, as the single-session recycle-disposition path does through `applyDisposition` (`scrubreport_server.go:519-520`, which emits once per disposition via `d.Reason.CountsOnRetirementTotal()`); without this the amended §5.2 would drain concurrent pools on a path that bypasses the sole `IncRetirement` caller and the counter would under-report them (the SPEC-D `spec/16:12` reword states this counting point). Reconcile the existing occupancy-zero `podscrub.Decide` check (`podscrub.go:358`) so the retirement is counted exactly once per pod even when the crossing release is also the pod's last clean slot: that release drives the Redis counter to zero and triggers CODE-A's occupancy-zero recycle `Shutdown` → `RecordPodScrub` → `podscrub.Decide` in the same cycle, where the `SessionsServed >= MaxSessionsPerPod` branch would otherwise emit a second `IncRetirement` through `applyDisposition`. `RecordPodScrub` resolves the pod's recycle policy through the `PodInspector` (`PodRecyclePolicy` already carries `VMRestart`/`scrubProfile` at `scrubreport_server.go:216` and `MaxSessionsPerPod` at `:212`); extend `PodRecyclePolicy` with `MaxConcurrentSessions`, which the inspector reads from the same pool `sessionPolicy` it already resolves, so `applyDisposition` suppresses the `session_count_limit` counter for a concurrent non-`vm-restart` pool (the per-release path owns that emission for that pool class) while the disposition still retires the pod as the state backstop. For a single-session pool and a concurrent `vm-restart` pool the occupancy-zero `applyDisposition` path stays the sole `session_count_limit` / `vm_restart_reprovision` counter emitter, selected by the same `maxConcurrentSessions > 1 && scrubProfile != vm-restart` predicate that gates the per-release stamp. The occupancy-zero `podscrub.go:358` check otherwise stays as the retirement path for a single-session pool and a redundant state backstop for a concurrent pool whose leaks all cleared, while the per-release check is the primary concurrent-pool trigger. This requires the `spec/05:486` amendment in SPEC-D, which decouples the concurrent-pool `maxSessionsPerPod` retirement from the whole-pod scrub.

**Rationale:** D1 is the slothealth code companion to SPEC-D: leaks are counted with the lifetime the spec now states, so the already-wired ceil-threshold drain fires for permanent leaks. D2 closes the residual gap that a single sub-`ceil` permanent leak leaves on a concurrent pool: the pool would otherwise keep serving sessions unboundedly past `maxSessionsPerPod` because total occupancy never reaches zero while live slots keep cycling. `maxSessionsPerPod` is required with no default when recycling is enabled (`spec/05:509`), so the per-release check is a guaranteed termination backstop for every concurrent recycling pool. A single-session pool retires through the occupancy-zero `podscrub.Decide` check with `ReasonSessionCountLimit`, and a concurrent `vm-restart` pool retires at the occupancy-zero recycle boundary with `vm_restart_reprovision` (above the session-count branch in `podscrub.Decide`), so the per-release stamp is gated on `maxConcurrentSessions > 1 && scrubProfile != vm-restart`. Both reuse the existing `drainLedger`/`StampDrainRequest` path and add no second annotation stamper; the retirement is enacted by the WarmPoolController in CODE-E, and the gateway-side `IncRetirement(ReasonSessionCountLimit)` at the stamp keeps `lenny_pod_retirement_total` accurate on the per-release path.

## 5. Non-goals

- **No new RPC, proto message, proto field, HTTP endpoint, or CRD field.** `RecycleScrub` already carries `pod_id`, `ReportSessionScrub` and `ReportPodScrub` already exist, and `lenny.dev/drain-request` already exists; the change wires existing surfaces. CODE-E adds one new pod annotation, `AnnotationMaxPodUptimeSeconds`, because no existing surface delivers `recycle.maxPodUptimeSeconds` (a gateway-poolstore knob absent from every CRD the controller reconciles) to the WarmPoolController; the annotation reuses the established gateway-stamps / controller-reads pattern of `AnnotationCertNotAfter` rather than introducing a new protocol or a CRD field, and `spec/04:398` already requires the controller to derive the uptime drain from `CreationTimestamp` against `recycle.maxPodUptimeSeconds`, so the cap must reach the controller by some surface.
- **No retire-on-first-leak trigger and no new §6.2 pod-phase state.** SPEC-D counts leaks persistently against the existing `ceil(maxConcurrentSessions/2)` threshold and preserves the deliberate sub-`ceil` tolerance; it does not retire a pod on its first leaked slot and does not reverse the §5.2 "leaked_slots alone reaches ceil" clause. The prior draft's retire-on-first-leak mechanism and the SPEC-D edit that would have superseded that clause are dropped.
- **No second drain-request stamper.** CODE-D reuses the existing `drainLedger`/`StampDrainRequest` path rather than adding a stamper in the slot-release code; the existing ceil-threshold drain and the CODE-D leaked-slot drain resolve to the same annotation.
- **No change to the base-mode reserve-hold, preConnect re-warm, or session-mode scrub paths beyond the `ReportSessionScrub` emission** that CODE-B adds to make `maxSessionsPerPod` functional in both modes.
- **No change to poolstore/admission validation of `maxSessionsPerPod`.** It stays required-when-recycle-enabled; B makes the already-required field functional rather than relaxing validation.
- **No vm-restart / cross-tenant-reuse scrub-profile work.** That is proposal 0034 (F-5.2.32) and stays out of scope. A concurrent pool rejects `allowCrossTenantReuse` (`poolstore.go:536-539`), so no concurrent pool reaches cross-tenant reuse. A concurrent `vm-restart` pool is a distinct, legal configuration (`scrubProfile` is independent of `allowCrossTenantReuse` and poolstore admits it, `poolstore.go:526-538,:585-586`), so the per-release `maxSessionsPerPod` drain (CODE-D/D2) and the SPEC-D `:486` amendment explicitly exclude it: a concurrent `vm-restart` pool retires at the occupancy-zero recycle boundary with the `vm_restart_reprovision` reason through `podscrub.Decide`, unchanged by this proposal.
- **No migration shim or dual mode.** The platform is pre-deployment, so the prior 0035 versions are superseded rather than kept compatible.

Decide whether to (a) emit `lenny_pod_retirement_total{reason="uptime_limit"}` from the controller for the level-triggered drain, or (b) accept that this residual-case uptime retirement is not counted and note the operator-visible gap in `spec/16`.
