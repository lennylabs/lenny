# Proposal: Wire the §5.2 per-slot `ReportSessionScrub` on every session release (session and concurrent modes) so `maxSessionsPerPod` fires, and gate the §6.2 Redis slot-counter decrement on the slot's synchronous cleanup outcome so a leaked slot stays counted (re-scope of 0035)

- **Status:** Verified (2026-07-02). Converged after 5 adversarial review rounds (7 findings fixed); awaiting sign-off. This re-scopes the superseded proposal 0035 (Verified, superseded `3186ca15`) with three product-owner decisions (D1/D2/D3) resolved.
- **Date:** 2026-07-02.
- **Scope:** A spec-to-code reconciliation of two verified code defects against spec text the code already owes and never satisfies. No spec edit is required (D3): §5.2, §6.2, and §4.7 already mandate both behaviors, so the code is the defect. **Defect 1:** the only production path that advances `sessions_served` (`ScrubReporter.RecordSessionScrub`, the `ReportSessionScrub` handler target) has no production caller, so the retirement predicate `SessionsServed >= MaxSessionsPerPod` never fires and `recycle.maxSessionsPerPod` is a platform-wide inert knob. **Defect 2:** `SlotClaimer.ReleaseSlot` decrements the Redis slot counter unconditionally at slot release, with no released/leaked distinction, so a leaked slot is wrongly un-counted, contradicting §6.2's requirement that a leaked slot "remains counted in the pod's Redis slot-counter occupancy." The change touches `pkg/adapter` (a new adapter-internal `SessionScrubReporter` seam, its emitters on both release paths, and its production wiring in `gatewaylink.go`), `pkg/gateway/podlifecycle/podsession/slotbinder.go`, `pkg/gateway/podlifecycle/podclaim/slotclaimer.go`, `schemas/lenny-adapter.proto` (a `pod_id` field on `ShutdownRequest` so the gateway delivers the pod identity the report echoes) with its regenerated mirror, and new tier-1/2/3/4/7a/9/10 tests. It reuses the already-wired `ReportSessionScrub` RPC and the existing per-pod slot-counter and recycle machinery. It adds one proto field (`ShutdownRequest.pod_id`), which reaches tier 3; the slot's leaked outcome for Defect 2 rides the existing `ShutdownResponse.ExitedCleanly` and adds no field there.

This document stages the proposed code and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

This re-scopes the superseded proposal 0035 (Verified, superseded `3186ca15`). It reconciles two verified code defects against spec text the code already owes.

### Defect 1: `recycle.maxSessionsPerPod` is an inert knob because no production path advances `sessions_served`

The only production path that advances `sessions_served` is `ScrubReporter.RecordSessionScrub`, the target of the `ReportSessionScrub` gRPC handler. `RecordSessionScrub` calls `counters.IncrementSessionsServed` (`pkg/gateway/mcpfabric/delegationtree/leasecontrol/scrubreport_server.go`, `RecordSessionScrub`); the RPC entry is `Service.ReportSessionScrub` at `scrubreport_server.go:75`, dispatching the outcome to `RecordSessionScrub`.

No production adapter sends `ReportSessionScrub`. The concurrent-slot teardown (`pkg/adapter/slotsession.go`, `shutdownSlot` → `releaseSlot`, lines 63-104) tears down the slot directory tree and deregisters the slot but never emits the report. The session-mode teardown (`pkg/adapter/session.go`, `Shutdown` → `releaseSession` at `session.go:248`, `:358`) never emits it either. Unlike the sibling whole-pod path (`pkg/adapter/podscrub.go`, which wires a `PodScrubReporter` emitter for `ReportPodScrub` and reports the outcome at `podscrub.go:77`), there is no `SessionScrubReporter` seam or emitter in `pkg/adapter` at all. The adapter's `ReportSessionScrub` client (`pkg/adapter/gatewaycontrol/scrubreport.go`, `Client.ReportSessionScrub` at `:80`) has zero production callers.

Consequently `sessions_served` stays 0. The retirement predicate `in.SessionsServed >= in.MaxSessionsPerPod` (`pkg/sandbox/podscrub/podscrub.go:295`) is evaluated only inside `podscrub.Decide`, whose sole caller is `RecordPodScrub`, the whole-pod `ReportPodScrub` handler (`scrubreport_server.go:435`). On a session-mode pool (`maxConcurrentSessions: 1`) with `recycle.enabled: true`, the occupancy-zero recycle boundary sends the adapter `ShutdownRecycle` (`binder.go:1891`), the adapter runs the whole-pod scrub and reports `ReportPodScrub`, and `podscrub.Decide` runs; the predicate still never fires there today because `sessions_served` is stuck at 0. On a concurrent pool (`maxConcurrentSessions > 1`) the occupancy-zero edge in `SlotClaimer.ReleaseSlot` only patches the claim to `recycling` and arms the missing-report timeout (`slotclaimer.go:689-701`); no code triggers a whole-pod scrub, so no `ReportPodScrub` arrives, the timeout retires the pod, and `podscrub.Decide` is never evaluated. So `recycle.maxSessionsPerPod` is inert on every pool today, and advancing `sessions_served` makes the predicate reachable only on the session-mode recycle path; making it govern concurrent-pool retirement additionally requires the concurrent whole-pod scrub trigger that the superseded 0035 staged as C-A1/C-A2, which this re-scope does not restore (see §5 and §9).

`spec/05_runtime-registry-and-pool-model.md` (the §5.2 "Scrub model" paragraph, line 451) mandates that the scrub is "uniform across session-mode configurations: a per-slot cleanup runs on every session release, reported by the adapter via `ReportSessionScrub`." `spec/04_system-components.md` (the §4.7 `ReportSessionScrub` Adapter → Gateway row, line 669) states that on that report "the gateway increments `sessionsServed` on the pod's `agent_pod_state` row, and `leaked` outcomes feed the unhealthy-threshold ledger."

### Defect 2: a leaked slot is wrongly un-counted, violating §6.2's leaked-slot occupancy rule

`spec/06_warm-pod-model.md:151` mandates that a slot in the `leaked` state "remains counted in the pod's Redis slot-counter occupancy (preventing the gateway from over-assigning new slots that would conflict with the leaked slot's unreleased resources)."

`SlotClaimer.ReleaseSlot` (`pkg/gateway/podlifecycle/podclaim/slotclaimer.go:655`) unconditionally decrements the Redis slot counter (`c.Counter.Release`, the clamped `DECR`) at slot release, with no released/leaked distinction. Over-assignment is gated exclusively by the Redis counter's atomic compare-and-increment (`pkg/gateway/storage/slotcounter/slotcounter.go`, the `reserveScript` at `:196`, reached via `SlotClaimer.Counter *slotcounter.Counter` on the slot-reservation path). `slotstate.Registry.ActiveCount` (`pkg/gateway/.../slotstate/registry.go:150`) has zero production callers and is not on the assignment path (the only other `ActiveCount` is an unrelated tenant-affinity request counter). So the current code decrements the very counter §6.2:151 says a leaked slot must remain counted in, and the superseded 0035's C-B2 ("keep the leaked slot in the `slotstate.Registry`") cannot fix it because the registry does not gate assignment.

The gateway already learns the cleanup outcome synchronously at the point it decrements. `Binder.ReleaseSlot` (`pkg/gateway/podlifecycle/podsession/slotbinder.go`) makes a synchronous `result.Adapter.ShutdownSlot(...)` RPC and only afterward calls `claimer.ReleaseSlot(...)`, in the same goroutine. Inside the adapter, `shutdownSlot` runs the runtime `Close` under a per-slot grace deadline and then `releaseSlot`/`removeSlotTree`, and returns `&adapterv1.ShutdownResponse{ExitedCleanly: closeErr == nil}` synchronously (`slotsession.go:63-88`). So by the time the decrement runs, cleanup has already finished and its outcome is available. The bug is that `Binder.ReleaseSlot` discards that outcome (`_, _ = result.Adapter.ShutdownSlot(ctx, ...)`) and then decrements unconditionally.

The spec's concurrent state machine couples the decrement to the per-slot cleanup outcome at teardown time: "a session completes or fails — per-slot cleanup runs, Redis-counter occupancy decremented" (`spec/06_warm-pod-model.md`, the concurrent-occupancy edge list), with `released` = "slot workspace removed, processes killed, slotId released" and `leaked` = "cleanup timeout exceeded." §6.2:151 then requires a leaked slot to stay counted. `ReportSessionScrub` is the adapter's report of the outcome for accounting (`sessionsServed` plus the unhealthy-threshold drain ledger, `spec/04:669`); no spec text attaches the Redis slot-counter decrement to that RPC.

### Superseded proposal

This re-scopes the superseded 0035, whose C-B2 registry mechanism cannot gate assignment. The two decisions that follow (D1 folds the session-mode caller into the scope; D2 gates the existing synchronous decrement on the cleanup outcome) supersede that draft.

## 2. Decisions

- **D1: emit `ReportSessionScrub` on every session release in both modes.** `spec/05:451` says the per-slot cleanup runs on every session release uniformly across session-mode configurations, including `maxConcurrentSessions: 1`. The re-scope adds a session-mode emitter (the `pkg/adapter/session.go` release path) alongside the concurrent-slot emitter (`pkg/adapter/slotsession.go`) so `sessions_served` advances on every pool. The handler already ignores `slot_id` when empty (`scrubreport_server.go:91-93`; the RPC requires only a non-empty `pod_id` and `session_id`), so the session-mode caller reuses the existing RPC with an empty `slot_id` rather than adding a new surface. This is the fix for Defect 1: `RecordSessionScrub` increments `sessions_served`, so `maxSessionsPerPod` fires on the session-mode recycle boundary that drives `ReportPodScrub`. That boundary sends `ShutdownRecycle` (`binder.go:1891`), whose already-carried `RecycleScrub.pod_id` supplies the pod identity the session-scrub emitter echoes into the report, so the report is accepted and `sessions_served` advances there. On concurrent pools the emitter advances `sessions_served` and feeds the leaked-slot drain ledger as `spec/05:451,:541` require, but concurrent-pool retirement on the predicate additionally needs the whole-pod scrub trigger this re-scope leaves out (§5, §9).
- **D2: gate the Redis slot-counter decrement on the slot's synchronous cleanup outcome, kept synchronous and in place.** The released/leaked outcome is already returned synchronously by `ShutdownSlot` at the exact point where the decrement currently happens. `Binder.ReleaseSlot` consumes the discarded `ShutdownSlot` result and passes a `leaked` flag to `SlotClaimer.ReleaseSlot`; on a leaked outcome the claimer skips `Counter.Release` so the slot stays counted per §6.2:151, and on a released outcome it runs the current synchronous decrement and the occupancy-zero disposition unchanged and in place. This resolves Defect 2 without moving the decrement onto the asynchronous `ReportSessionScrub` handler.
- **The occupancy-zero recycle trigger stays synchronous and in place.** Because the decrement is not relocated, the whole-pod recycle trigger and claim-delete derived from its return value (`slotclaimer.go`: `remaining > 0`; `WriteRecyclingStatus`; `DeleteClaim`; `RecycleBoundary.OnRecycling`) are unchanged. They run exactly as today on the released path and do not run on the leaked path (a leaked slot stays counted, so `remaining` cannot reach zero on that release).
- **The reservation-rollback decrement is unchanged.** `Binder.ReleaseSlotReservation` (`slotbinder.go`, `recycle=false`) rolls back a §5.2 reservation that never became a running session; it has no adapter connection and no cleanup outcome to consult, so it always releases (equivalently, it passes `leaked=false`). Only the session-teardown decrement gains the leaked gate.
- **Fail closed on a missing or errored cleanup outcome.** An errored or unclean `ShutdownSlot` (including adapter death during the RPC) reads as leaked, so the slot stays counted (`spec/13` fail-closed posture: on doubt, over-count rather than over-assign). No new missing-report timeout is required, because the decrement never leaves the synchronous teardown path.
- **D3: no spec edit.** The change is a pure implementation reconciliation. `spec/05:451`, `spec/06:151`, and `spec/04:669` already mandate the behavior; no `spec/` edit is staged, and the proposal cites those sections in code rather than restating them in spec text.
- **Minimal protocol surface.** Reuse the fully wired `ReportSessionScrub` RPC (proto, adapter `Client` at `gatewaycontrol/scrubreport.go:80`, gateway handler at `scrubreport_server.go:75`, and the counter store) rather than adding a new RPC. C1 adds one field, a top-level `pod_id` on `ShutdownRequest`, because the adapter holds no pod identity of its own (`schemas/lenny-adapter.proto:1266`) and the gateway handler rejects an empty `pod_id` fail-closed (`scrubreport_server.go:80-81`); the gateway must deliver the pod identity the report echoes. This extends the established `RecycleScrub.pod_id` echo pattern (`schemas/lenny-adapter.proto:1266-1272`) to every teardown rather than inventing a parallel identity source such as a downward-API `POD_NAME` env, which would risk delivering the pod's `metadata.name` where the gateway keys `agent_pod_state` on the `SandboxName`. The `ShutdownRequest.pod_id` field is a wire-contract change and reaches tier 3. C2 surfaces the slot's leaked outcome through the existing `ShutdownResponse.ExitedCleanly` field rather than a new field, so it adds no wire surface of its own. Whether `ExitedCleanly` (runtime `Close` only) is too coarse to represent leaked, and a dedicated `ShutdownResponse.leaked` field is warranted, is left as an open decision (§9).
- **Classified `fix`.** The dominant action reconciles core-product code to existing spec text and reuses the existing per-pod slot-counter and recycle machinery (`SlotClaimer`, `Counter`, `RecycleBoundary`) rather than building a new subsystem.

## 3. The mechanism: why the synchronous conditional decrement, and why not the asynchronous relocation

The superseded 0035 and an earlier draft of this re-scope proposed to hold the Redis decrement off the synchronous teardown path and move it onto the gateway's `ReportSessionScrub` handler, applied only on a released outcome, with a new per-slot missing-report timeout to bound a report that never arrives. That relocation is spec-mismatched and oversized, and it rests on a false premise.

The premise is that the released/leaked outcome is only knowable via the asynchronous `ReportSessionScrub` RPC. It is not. `Binder.ReleaseSlot` calls `ShutdownSlot` and only afterward calls `SlotClaimer.ReleaseSlot` (the decrement), in the same goroutine. `ShutdownSlot` returns synchronously, and the adapter runs the actual cleanup (runtime `Close` under a grace deadline, then `removeSlotTree`) inside `shutdownSlot` before it returns (`slotsession.go:63-104`). The leaked determination is available at `ShutdownSlot`'s return; the current code discards it.

The spec does not assign the decrement to `ReportSessionScrub`. `spec/04:669` enumerates the handler's gateway effects narrowly (increment `sessionsServed`; feed the leaked unhealthy-threshold ledger) and says nothing about the Redis decrement. `spec/05:451` only says the cleanup is "reported by the adapter via `ReportSessionScrub`," and `spec/06:151` only requires a leaked slot to stay counted. Relocating the decrement onto that RPC would drag a counter, recycle-disposition, and kube-write responsibility onto a handler the spec keeps narrow, and it would sever the decrement from the synchronous teardown, creating a stranding/liveness hazard that a per-slot timeout would then have to patch.

The synchronous conditional decrement needs none of that. Keep the decrement where it is and make it conditional on the leaked outcome `ShutdownSlot` already returns: on released, decrement and run the occupancy-zero disposition exactly as today; on leaked, skip the decrement so the slot stays counted, which is precisely the §6.2:151 over-assignment gate. An errored or unclean `ShutdownSlot` (adapter death included) reads as leaked and the slot stays counted, fail-closed, with no timeout. `ReportSessionScrub` keeps its narrow `spec/04:669` role (advance `sessions_served`, feed the leaked ledger) and continues to ignore `slotID`.

The two defects are independent. Defect 1 (C1) rides `ReportSessionScrub` because `spec/04:669` legitimately assigns `sessions_served` accounting to that RPC. Defect 2 (C2) rides the synchronous slot-teardown path because that is where the spec couples the decrement to the cleanup outcome. Neither borrows the other's mechanism.

## 4. Proposed changes

### C1. Emit `ReportSessionScrub(released|leaked)` on every session release in both session and concurrent modes

**Target:** `pkg/adapter/server.go` (a new adapter-internal `SessionScrubReporter` seam and `Server` field, mirroring the existing `PodScrubReporter`); `pkg/adapter/gatewaylink.go` (`ConnectGateway`, `:69`: bind the dialed `gwClient` to the new field, `s.SessionScrubReporter = gwClient`, immediately alongside the existing `s.PodScrubReporter = gwClient`, so the field is non-nil in every production binary (`cmd/lenny-adapter/main.go:305`)); `pkg/adapter/slotsession.go` (`shutdownSlot` lines 63-88 and `releaseSlot` lines 90-104: the concurrent-slot teardown); `pkg/adapter/session.go` (`Shutdown` around line 248 and `releaseSession` at `:358`: the session-mode teardown); `pkg/adapter/slot.go` (`removeSlotTree`, whose error signals a non-clean slot cleanup). The pod identity the report carries is delivered by the gateway on the teardown RPC: `schemas/lenny-adapter.proto` gains a top-level `pod_id` field on `ShutdownRequest` (regenerating `pkg/proto/adapter/v1`), the gateway populates it with the pod's `SandboxName` on the plain `Shutdown` (session-mode retire), `ShutdownSlot` (concurrent-slot), and `Terminate` (§11.4 full_revoke eviction) calls (`pkg/gateway/runtime/adapterclient/client.go` `shutdown`/`ShutdownSlot`/`Terminate`, reached from `pkg/gateway/podlifecycle/podsession/slotbinder.go` `ReleaseSlot`, `binder.go` `shutdownAdapter`, and `cmd/lenny-gateway/user_revocation.go` `terminateLocal` (`:129`), all of which already hold the pod's `SandboxName` (`BindResult.SandboxName`, `binder.go:487`)). `Client.Terminate` (`client.go:805`) is a distinct teardown helper that does not route through the `shutdown` helper and today sets no top-level `pod_id`, so it gains the same caller-supplied `pod_id` argument. The session-mode occupancy-zero recycle boundary sends `ShutdownRecycle` (`binder.go:1891`), which does not route through the plain `Shutdown` helper and already carries the pod identity in the nested `RecycleScrub.pod_id`; it needs no gateway change. The adapter's session-scrub emitter therefore sources the pod identity from `req.GetRecycle().GetPodId()` on the recycle branch (mirroring how `ReportPodScrub` sources it at `podscrub.go:77`) and falls back to the top-level `req.GetPodId()` on the plain-`Shutdown` and `ShutdownSlot` branches, then echoes the resolved identity into the report. The emitter reuses the fully wired `Client.ReportSessionScrub` (`pkg/adapter/gatewaycontrol/scrubreport.go:80`).

**Change:** Add an adapter-internal `SessionScrubReporter` interface mirroring `PodScrubReporter`, a `Server.SessionScrubReporter` field, and the production wiring `s.SessionScrubReporter = gwClient` in `ConnectGateway` (`gatewaylink.go:69`), the sole site that binds a gateway-control reporter to the dialed client. Without that line the field stays nil in every real adapter, the emitter's nil fallback fires, no report is sent, and Defect 1 is not fixed. On every session release, derive the outcome from the cleanup result the adapter already computes (a failed `removeSlotTree` or a non-clean runtime `Close` is `leaked`, otherwise `released`) and emit `ReportSessionScrub(ctx, podID, sessionID, slotID, outcome)` guarded by a nil check with a `slog.Warn` fallback matching the `PodScrubReporter` pattern (`podscrub.go:70-74`).

In the concurrent-slot path (`slotsession.go`), capture the `removeSlotTree` result in `releaseSlot` (today discarded at `slotsession.go:102`, `_ = removeSlotTree(st)`), map it and the runtime-close outcome to the `SessionScrubOutcome`, and emit with `slot_id` set (the pod runs `maxConcurrentSessions > 1`). In the session-mode path (`session.go`), after `releaseSession()` on the session-release branch, emit with an **empty** `slot_id` (the handler ignores it, `scrubreport_server.go:91-93`). The whole-pod `startPodScrub` call on the recycle branch (`session.go:257`) is unchanged; the per-slot session-scrub report is a distinct, additional emission. Determine `podID` from the recycle sub-message when present (`req.GetRecycle().GetPodId()`, the pod identity `ShutdownRecycle` already carries on the session-mode recycle boundary, mirroring `podscrub.go:77`), falling back to the top-level `ShutdownRequest.pod_id` the gateway supplies on the plain `Shutdown`, `ShutdownSlot`, and `Terminate` teardown RPCs, and echo the resolved identity in the report. The §11.4 full_revoke eviction path reaches the same session-mode emitter, because `Server.Shutdown` calls `releaseSession()` before the `req.GetRecycle()` check (`session.go:248`, `:256`) and the emitter fires after it; the `Terminate` helper carries no recycle sub-message, so the emitter resolves the identity from the top-level field the gateway now sets from `bind.SandboxName`. The adapter holds no pod identity of its own (`schemas/lenny-adapter.proto:1266`), so the gateway must deliver it, and the recycle boundary delivers it through the existing `RecycleScrub.pod_id` rather than the new top-level field. The gateway handler rejects an empty `pod_id` fail-closed (`scrubreport_server.go:80-81`), so the delivery is required for the report to be accepted at all; sourcing it from the recycle sub-message on the `ShutdownRecycle` boundary is what keeps the session-mode recycle report, the sole Defect-1 fix path, from being rejected.

**Rationale:** `spec/05:451` mandates a per-slot cleanup reported via `ReportSessionScrub` on every session release, uniform across session-mode configurations, and `spec/05:541` requires the concurrent-slot path to report each slot cleanup (`released` or `leaked`) via the same RPC. Today neither the concurrent-slot path nor the session-mode path reports it, so `sessions_served` never advances and the whole-pod `RecordPodScrub` handler that reads it never retires a pod on the session-count predicate (Defect 1). D1 folds in the session-mode caller so `maxConcurrentSessions: 1` recycling pools advance `sessions_served`, which is the input `podscrub.Decide` reads on the session-mode `ReportPodScrub` recycle boundary, so `maxSessionsPerPod` fires there. The concurrent-slot emitter also advances `sessions_served` and feeds the leaked-slot drain ledger (`spec/04:669`), both of which `spec/05:451,:541` require on every slot release; it does not by itself retire the concurrent pool, because a concurrent pool reaches `podscrub.Decide` only through a whole-pod `ReportPodScrub` that no code triggers today (see §5 and §9). The `released|leaked` determination comes from the cleanup outcome the adapter already computes.

### C2. Gate the Redis slot-counter decrement on the slot's synchronous cleanup outcome so a leaked slot stays counted

**Target:** `pkg/adapter/slotsession.go` (`shutdownSlot` lines 63-88: surface the slot's leaked outcome on the synchronous `ShutdownResponse`); `pkg/gateway/podlifecycle/podsession/slotbinder.go` (`Binder.ReleaseSlot`: stop discarding the `ShutdownSlot` response and derive the leaked flag; `Binder.ReleaseSlotReservation`: unchanged); `pkg/gateway/podlifecycle/podclaim/slotclaimer.go` (`SlotClaimer.ReleaseSlot` at `:655`: add a `leaked bool` parameter and skip `Counter.Release` when leaked). On the recommended path the leaked outcome rides the existing `ShutdownResponse.ExitedCleanly`; see §9 for the dedicated-field alternative that would touch `schemas/lenny-adapter.proto`.

**Change:**

1. **Adapter surfaces the leaked outcome synchronously.** `shutdownSlot` already returns `&adapterv1.ShutdownResponse{ExitedCleanly: closeErr == nil}` (`slotsession.go:88`), where `closeErr` is the runtime `Close` result. Fold the discarded `removeSlotTree` result (today dropped at `slotsession.go:102`) into that outcome so `ExitedCleanly` is `false` when the runtime `Close` or the slot-tree removal did not complete cleanly. `ExitedCleanly == false` is the leaked signal the gateway consumes, matching `spec/06`'s `leaked` = "cleanup timeout exceeded / slot not reclaimed."
2. **`Binder.ReleaseSlot` consumes the outcome.** Stop discarding the `ShutdownSlot` result (`slotbinder.go:498`, `_, _ = result.Adapter.ShutdownSlot(...)`); read both returns, `exitedCleanly, err := result.Adapter.ShutdownSlot(...)`, and derive `leaked := err != nil || !exitedCleanly`. The transport-error branch is distinct from a clean-return unclean outcome: on `err != nil` the adapter died mid-RPC and the client returns `false` for `exitedCleanly` (`adapterclient/client.go` `shutdown`, `return false, err`), so folding `err != nil` into the derivation reads adapter death as leaked and never un-counts a slot whose teardown result is unknown. Pass `leaked` to the claimer.
3. **`SlotClaimer.ReleaseSlot` gains a `leaked` gate.** Add a `leaked bool` parameter. When `leaked`, skip `Counter.Release` so the slot stays counted per §6.2:151, and return without touching the occupancy-zero disposition. When not leaked, run exactly the current synchronous decrement, `remaining > 0` check, and `WriteRecyclingStatus` / `RecycleBoundary.OnRecycling` / `DeleteClaim` logic, unchanged and in place.
4. **`Binder.ReleaseSlotReservation` is unchanged.** It calls `claimer.ReleaseSlot(ctx, sandboxName, slotID, false)` for a `recycle=false` rollback; it passes `leaked=false` (a reservation that never ran a session has nothing to leak), so its decrement always runs, as today.

Illustrative `SlotClaimer.ReleaseSlot` gate at the top of the function:

```go
func (c *SlotClaimer) ReleaseSlot(ctx context.Context, sandboxName, sessionID string, recycle, leaked bool) error {
	if c.Counter == nil {
		return errors.New("podclaim: slot counter is required for concurrent-session slot release")
	}
	if leaked {
		// spec: §6.2 (a leaked slot remains counted in the pod's Redis
		// slot-counter occupancy, preventing the gateway from over-assigning
		// new slots that would conflict with the leaked slot's unreleased
		// resources). Skip the decrement; the slot stays counted until pod
		// termination. The occupancy-zero recycle disposition below cannot be
		// reached on this release because the counter is not decremented.
		return nil
	}
	// released: the existing synchronous decrement and occupancy-zero
	// disposition run unchanged.
	remaining, err := c.Counter.Release(ctx, sandboxName)
	// ... unchanged remaining>0 / recycle / DeleteClaim logic ...
}
```

**Rationale:** Over-assignment is gated exclusively by the Redis counter (`pkg/gateway/storage/slotcounter/slotcounter.go` `reserveScript`), and §6.2:151 requires a leaked slot to stay counted, so the decrement must be applied only on a released outcome and withheld on leaked (Defect 2). The released/leaked outcome is already returned synchronously by `ShutdownSlot` at the point of the decrement, so the fix keeps the decrement synchronous and in place and conditions it on that outcome. This resolves §6.2:151 entirely without relocating the decrement to the asynchronous `ReportSessionScrub` handler, without splitting `SlotClaimer.ReleaseSlot`, and without a new missing-report timeout. Adapter death during `ShutdownSlot` naturally reads as leaked, so the slot stays counted (fail closed).

### C3. Tests across the tiers the change reaches

## 5. Non-goals

- **No `spec/` edit (D3).** `spec/05:451`, `spec/06:151`, and `spec/04:669` already mandate the behavior; the change reconciles code to the committed spec and cites those sections in code.
- **Do not place the leaked slot in `slotstate.Registry`.** The superseded 0035 C-B2 mechanism is abandoned because `Registry.ActiveCount` (`registry.go:150`) has zero production callers and is not on the assignment path. Keeping the slot counted means leaving the Redis counter incremented, which is the sole over-assignment gate (`pkg/gateway/storage/slotcounter/slotcounter.go` `reserveScript`).
- **Do not relocate the Redis slot-counter decrement onto the asynchronous `ReportSessionScrub` handler.** The earlier async design rested on a false premise (the leaked outcome is already returned synchronously by `ShutdownSlot`) and manufactured a stranding/liveness gap. The decrement stays synchronous and in place, conditioned on the `ShutdownSlot` outcome. `RecordSessionScrub` keeps its narrow `spec/04:669` role and continues to ignore `slotID`.
- **Do not add a per-slot missing-report timeout.** That timeout existed only to bound the async liveness gap the relocation created. The synchronous conditional decrement guarantees release (or a fail-closed leaked hold) on the teardown path, so no new timeout is needed. The pre-existing whole-pod `ReportPodScrub` missing-report timeout (`RecycleBoundary.OnRecycling`) is unaffected and still governs the recycle occupancy-zero edge.
- **Do not add a new RPC or frame, and keep the proto delta to the one field the pod-identity delivery requires.** `ReportSessionScrub` is reused end to end, and the Defect-2 leaked outcome rides the existing `ShutdownResponse.ExitedCleanly` with no new field. C1 adds exactly one field, a top-level `pod_id` on `ShutdownRequest`, because the report is rejected fail-closed without a pod identity the adapter cannot supply itself; it extends the existing `RecycleScrub.pod_id` echo pattern rather than adding an RPC or a parallel identity source. A dedicated `ShutdownResponse.leaked` proto field for the Defect-2 outcome is an open decision (§9) rather than part of the recommended path.
- **Do not change `Binder.ReleaseSlotReservation`.** The reservation-rollback decrement stays exactly as is (`recycle=false`, `leaked=false`).
- **Do not change poolstore/admission validation** of `maxConcurrentSessions`, `recycle.enabled`, or `recycle.maxSessionsPerPod`.
- **Do not alter the whole-pod `ReportPodScrub` path** (`pkg/adapter/podscrub.go`, `RecordPodScrub`) beyond the fact that it now reads a correctly advanced `sessions_served`; its disposition logic in `podscrub.Decide` is unchanged except for the retirement predicate now being reachable on the session-mode recycle boundary that already drives `ReportPodScrub`.
- **Do not add the concurrent-pool whole-pod scrub trigger.** A concurrent pool (`maxConcurrentSessions > 1`) reaches `podscrub.Decide` only through a whole-pod `ReportPodScrub`, and no code triggers a whole-pod scrub at the concurrent occupancy-zero edge today (`slotclaimer.go:689-701` only patches the claim to `recycling` and arms the missing-report timeout). Wiring that trigger is the superseded 0035's C-A1/C-A2 and is out of this re-scope, whose §2 keeps the occupancy-zero recycle trigger synchronous and in place. C1 therefore advances `sessions_served` and feeds the leaked-slot drain ledger on concurrent pools as `spec/05:451,:541` require, but concurrent-pool `maxSessionsPerPod` retirement is deferred to the follow-up in §9.

## 9. Open decisions for review

- **Dedicated `ShutdownResponse.leaked` field versus reusing `ExitedCleanly`.** The recommended path folds the `removeSlotTree` outcome into the existing `ShutdownResponse.ExitedCleanly` (runtime `Close` today), so `ExitedCleanly == false` is the leaked signal and no proto field is added. Recommendation: reuse `ExitedCleanly`, since `spec/06` defines `leaked` as a cleanup-timeout/non-completion outcome that a false `ExitedCleanly` already represents.
- **Concurrent-pool `maxSessionsPerPod` retirement requires a whole-pod scrub trigger this re-scope does not restore.** `spec/05:451` mandates the whole-pod scrub uniformly across session-mode configurations whenever occupancy reaches zero on a recycling pool, and `spec/05:456` mandates that the gateway trigger it by sending the recycle disposition. For session-mode pools the gateway already sends it (`ShutdownRecycle`, `binder.go:1891`), so C1's advanced `sessions_served` makes `maxSessionsPerPod` fire there. For concurrent pools the gateway sends no such trigger at the occupancy-zero edge (`slotclaimer.go:689-701`), so `podscrub.Decide` never runs and `maxSessionsPerPod` cannot retire a concurrent pool even with `sessions_served` advancing. Restoring the concurrent whole-pod scrub trigger (the superseded 0035's C-A1/C-A2, firing on the last confirmed-`released` slot under D2) closes the concurrent half of Defect 1 but reintroduces the occupancy-zero coupling this re-scope deliberately shed. Decide whether to fold that trigger into this proposal or to track it as a separate follow-up; the product-owner intent recorded for D1 (make `maxSessionsPerPod` functional in both modes) is met for session mode by this proposal and requires the trigger for concurrent mode.
- **Whether a `leaked` outcome should advance `sessions_served` toward `maxSessionsPerPod`.** The current `RecordSessionScrub` increments `sessions_served` before the `leaked` branch, so a leaked release still counts a served session. C1 preserves that (a session ran even if its slot leaked). Confirm this is the intended retirement-accounting semantics, or whether a leaked session should not count toward `maxSessionsPerPod`.
