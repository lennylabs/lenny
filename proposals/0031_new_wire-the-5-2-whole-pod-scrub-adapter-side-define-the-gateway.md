# Proposal: Wire the §5.2 whole-pod scrub adapter-side by defining the gateway→adapter recycle-scrub trigger and scrub-config delivery, running `scrub.Run` and `ReportPodScrub` in production, and splitting the concrete Kata guest-restart client out as an operator-gated follow-on

- **Status:** Applied to spec (2026-07-03). Converged after 5 adversarial review rounds (7 findings fixed); all three §9 open decisions resolved by the reviewer in favor of the recommended options (extend the existing `Shutdown` RPC; deliver the scrub config on the recycle-trigger `Shutdown`; spin the concrete Kata `VMRestarter` out to a separate NEEDS-OPERATOR finding).
- **Date:** 2026-07-02.
- **Scope:** Wires the §5.2 whole-pod scrub on the adapter side and defines the gateway→adapter mechanism that triggers it and delivers its configuration. The §5.2 scrub orchestration and the gateway consumer side of the report already exist and are complete; the residual is that `scrub.Run` (`pkg/adapter/scrub/scrub.go:232`) and the adapter emitter `Client.ReportPodScrub` (`pkg/adapter/gatewaycontrol/scrubreport.go:103`) have zero production callers, and no Gateway→Adapter RPC carries the scrub configuration or a recycle disposition, so a recycle-eligible pod reaching occupancy zero is retired fail-closed by the gateway-side missing-report timeout rather than reused. This proposal closes the spec gap that left the code dead: it defines the recycle-scrub trigger on the existing `Shutdown` RPC and the scrub-config delivery in `spec/04_system-components.md` §4.7 and `spec/05_runtime-registry-and-pool-model.md` §5.2 (change **S-A1**), extends the `ShutdownRequest` proto with a recycle sub-message (**C-A1**), adds the adapter-side scrub driver that runs `scrub.Run` asynchronously and reports via `ReportPodScrub` (**C-A2**), and threads the pool's scrub configuration onto the gateway's recycle-path `Shutdown` (**C-A3**). It touches `spec/04_system-components.md`, `spec/05_runtime-registry-and-pool-model.md`, `schemas/lenny-adapter.proto`, `pkg/adapter/session.go`, `pkg/adapter/gatewaylink.go` (retain the GatewayControl client as a `ReportPodScrub` emitter on the adapter `Server`), a new `pkg/adapter/podscrub.go`, `pkg/gateway/podlifecycle/podsession/resolve.go` (fold `cleanupCommands`/`cleanupTimeoutSeconds` into `PoolMatch`), the session-mode `pkg/gateway/sessionserver` bind-request builder (`exclusiveBindRequest`), `pkg/gateway/podlifecycle/podsession/binder.go`, `pkg/gateway/runtime/adapterclient/client.go`, and the tests. The concrete Kata `VMRestarter` for scrub step 7 is **not** part of this proposal; it is recorded in Non-goals as a separate implementation-only finding against the already-complete §5.2 step 7, marked NEEDS-OPERATOR (Kata RuntimeClass). The adapter trigger is wired here for the session-mode (`maxConcurrentSessions: 1`) occupancy-zero boundary only; the concurrent-session (`maxConcurrentSessions > 1`) occupancy-zero boundary reaches the same whole-pod scrub through the separate `ReleaseSlot` path and is likewise recorded in Non-goals as an implementation-only follow-on.

This document stages the proposed spec and code changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

Finding F-5.2.15's "step 7 not implemented" framing is stale. The §5.2 scrub orchestration exists and is complete: `scrub.Run` (`pkg/adapter/scrub/scrub.go:232`) runs steps 0-6 and step 7 (`cfg.Restarter.RestartGuest` at `:278`, gated on `cfg.MicrovmRestart` at `:277`) behind the `VMRestarter` seam (`:99-101`), with a fail-closed `ErrNoRestarter` guard (`:220`, `:236-237`). The `scrubProfile` enum (`standard` / `vm-restart` / `in-place`) is wired from the CRD through admission, the store, and the gateway's pool selection (`pkg/gateway/podlifecycle/podsession/resolve.go:264`; `pkg/gateway/sessionserver/sessionserver.go:2489,:2506`). The gateway consumer side of the report is fully built and wired: the `leasecontrol` `ReportPodScrub` handler (`pkg/gateway/mcpfabric/delegationtree/leasecontrol/scrubreport_server.go:113`), the pure disposition table (`pkg/sandbox/podscrub/podscrub.go:254-358`), and the recycle-boundary missing-report timeout (`pkg/gateway/session/recycle/recycleboundary.go:307-408`, wired at `cmd/lenny-gateway/main.go:699-744` and `cmd/lenny-gateway/stores.go:1621`).

The residual is that the whole-pod scrub is entirely unwired on the adapter side, and the gateway→adapter trigger for it is unspecified.

1. **`scrub.Run` has zero production callers.** Nothing outside `pkg/adapter/scrub` imports or invokes it; the package is exercised only by its own tests. The scrub orchestration is dead code.
2. **The adapter emitter `Client.ReportPodScrub` (`pkg/adapter/gatewaycontrol/scrubreport.go:103`) has no production caller.** The gateway handler that consumes the report is live, but nothing in the adapter ever sends one.
3. **The recycle-path `Shutdown` carries no recycle indicator and no scrub config.** `Release` patches the claim `bound → recycling`, arms the missing-report timeout, and calls `shutdownAdapter` (`pkg/gateway/podlifecycle/podsession/binder.go:1799-1819`), whose comment claims the `Shutdown` "is the occupancy-zero signal that runs the whole-pod scrub." But `shutdownAdapter` (`:1836-1841`) calls `Adapter.Shutdown` with only a session id, then `Close()`. The adapter's `Shutdown` handler (`pkg/adapter/session.go:218-250`) closes the session runtime and releases the session, and never runs `scrub.Run` or `ReportPodScrub`.
4. **No scrub config reaches the adapter.** `schemas/lenny-adapter.proto` carries no `cleanupCommands`, `scrubProfile`, or recycle field in any Gateway→Adapter message (`ShutdownRequest` at `:1318-1328`), and the §4.7 Gateway → Adapter RPC table (`spec/04_system-components.md:643-663`) documents the single proto `Shutdown` RPC (`schemas/lenny-adapter.proto:163`) only as the `Terminate` row (`spec/04:663`) and names no recycle disposition or scrub trigger.
5. **No concrete `VMRestarter` exists.** The only implementer is `fakeRestarter` in `scrub_test.go`; step 7 requires the Kata runtime's VM lifecycle API (`spec/05_runtime-registry-and-pool-model.md:475`), exercisable only on a Kata-enabled host RuntimeClass (the `microvm → kata` mapping at `spec/05:670`), a tier-6 behavior Kind cannot reproduce.

Because pod reuse is gated on a `ReportPodScrub` disposition and no adapter ever sends one, a recycle-eligible pod reaching occupancy zero sits in `recycling` and is retired fail-closed by the missing-report timeout (`recycleboundary.go:397-407`). Between-session isolation is preserved (the pod is terminated and replaced, the stronger default posture); the gap is availability and efficiency (the pod-reuse optimization never delivers) rather than an isolation breach. The §5.2 obligation is genuine (the whole-pod scrub reported via `ReportPodScrub`; step 7 `vm-restart`), but the mechanism that triggers the adapter and delivers the scrub config is a spec gap, which is why the code was left dead.

The dead code has two occupancy-zero entry points. The exclusive session-mode boundary runs through `Binder.Release` (`binder.go:1799-1828`), and the concurrent-session boundary (`sessionPolicy.maxConcurrentSessions > 1` with `recycle.enabled: true`, a valid pool configuration that only rejects `allowCrossTenantReuse`, `poolstore.go:536-539`) runs through `Binder.ReleaseSlot` → `SlotClaimer.ReleaseSlot` (`slotbinder.go:494-514`, `slotclaimer.go:679-704`) when the last slot drains cleanly. Both patch the claim to `recycling` and arm the same missing-report timeout, and both currently retire the pod because no adapter reports. This proposal's code wires the adapter trigger for the session-mode (`maxConcurrentSessions: 1`) boundary through `Binder.Release`; the concurrent-session boundary is a distinct release path (`ReleaseSlot` sends only a per-slot `ShutdownSlot`, and the adapter `Shutdown` handler early-returns on any slot-qualified request at `session.go:226-227` before the recycle branch runs) and is filed as a separate implementation-only follow-on finding (see Non-goals). The §5.2 whole-pod scrub contract (S-A1) covers both boundaries; only the session-mode code path is wired here.

## 2. Decisions

- **The spec gap is the root cause of the dead code.** §5.2 says the whole-pod scrub "runs" and is reported via `ReportPodScrub` (`spec/05:453,:457`), and §4.7 lists `ReportPodScrub` as an Adapter → Gateway RPC (`spec/04:671`). No Gateway → Adapter RPC in the §4.7 table (`spec/04:643-663`) triggers the scrub, and no adapter proto message carries `cleanupCommands` or `scrubProfile` (`schemas/lenny-adapter.proto` has none). Nothing told an implementer what to wire. Closing that gap (S-A1) is the core spec edit.
- **Reuse the existing proto `Shutdown` RPC (the row the §4.7 table lists as `Terminate`) as the recycle-scrub trigger rather than adding a new RPC.** The wire contract has exactly one RPC in this family, `rpc Shutdown` (`schemas/lenny-adapter.proto:163`); the §4.7 Gateway → Adapter table denotes it as the `Terminate` row (`spec/04:663`), and `binder.go:1813-1818` already documents that the recycle-path `Shutdown` "is the occupancy-zero signal that runs the whole-pod scrub." Extend `ShutdownRequest` with a recycle disposition plus the pod identity and scrub parameters (`podId`, `cleanupCommands`, `cleanupTimeoutSeconds`, `scrubProfile`) and branch the adapter handler on it, matching the existing code intent and the minimal-new-protocol-surface principle. S-A1 extends the existing `Terminate` row rather than inserting a second row, and reconciles the spec name (`Terminate`) with the proto name (`Shutdown`). The dedicated-RPC alternative is recorded as an open decision.
- **On a recycle `Shutdown` the adapter runs the scrub asynchronously and reports via `ReportPodScrub` on its separate GatewayControl link.** The gateway design already assumes an async report bounded by the missing-report timeout (`spec/05:457`; `recycleboundary.go` `OnRecycling`), and `shutdownAdapter` closes the gateway→adapter connection immediately after `Shutdown` returns (`binder.go:1836-1841`). The adapter (pod) process stays alive across the recycle boundary; only the ending session's runtime is closed. The GatewayControl channel the adapter reports over is already dialed (`pkg/adapter/gatewaylink.go:54`), but the dialed `*gatewaycontrol.Client` is currently retained only as the platform and connector forwarders (`gatewaylink.go` `PlatformForwarder`/`ConnectorForwarder`); C-A2 also retains it on the `Server` as a `ReportPodScrub` emitter so the driver can send the report.
- **The adapter learns the pod identity from the recycle-trigger `Shutdown`, not from any held state.** `ReportPodScrubRequest.pod_id` is required (`schemas/lenny-adapter.proto:452`) and is the `agent_pod_state` row key (the Sandbox name) the gateway keys the missing-report timeout on (`binder.go:1811` `OnRecycling(result.SandboxName)`; `recycleboundary.go:342` `OnScrubReported` cancels by the same key). The adapter has no pod-identity source today (the `Server` struct carries no pod name and `StartSessionRequest` no sandbox id), so the recycle `RecycleScrub` message carries `pod_id` (== the gateway's `SandboxName` timer key), which the adapter echoes back in `ReportPodScrub` so the report matches the armed timer.
- **The gateway consumer side is already built and wired; this proposal does not touch it.** The `leasecontrol` `ReportPodScrub` handler (`scrubreport_server.go:113`), `podscrub.Decide` (`podscrub.go:254-358`), the recycle-boundary missing-report timeout (`recycleboundary.go`), and their production wiring (`cmd/lenny-gateway/main.go:699-744`, `stores.go:1621`) already consume the report and drive recycle-versus-retire. The residual is exclusively the adapter-side producer and the trigger that reaches it.
- **The concrete Kata `VMRestarter` (step 7) is not shipped in this proposal.** Step 7 is already fully specified (`spec/05:473-477`) and requires the Kata runtime's VM lifecycle API (`spec/05:475`) on a `microvm → kata` RuntimeClass (`spec/05:670`), a tier-6 behavior Kind cannot reproduce. This proposal's spec edit (S-A1) does not touch step 7, so the Kata client stages zero spec change and is a pure code implementation against an already-complete spec. Coupling it to this change would tie a CI-testable spec-gap fix to an operator-hardware dependency that cannot run to green in the same landing. The adapter driver (C-A2) passes a `nil` restarter for non-`vm-restart` profiles, which the fail-closed `ErrNoRestarter` guard permits. For a `vm-restart` profile with no concrete restarter the driver withholds the `ReportPodScrub` entirely (recognizing `scrub.ErrNoRestarter`), so the gateway missing-report timeout retires the pod. That reproduces the exact fail-closed posture that holds today, where no adapter reports and the timeout retires. Emitting a report instead would let `podscrub.Decide` reuse the pod under the default `warn` policy (`podscrub.go:264-358`), which on an `allowCrossTenantReuse` pool would reuse it across tenants without the guest VM restart the `vm-restart` profile exists to perform (a fail-open isolation regression). The concrete Kata `VMRestarter` is filed as a separate implementation-only finding, NEEDS-OPERATOR (Kata RuntimeClass); see Non-goals.
- **The per-slot cleanup report (`ReportSessionScrub`) adapter-side wiring is out of scope.** Its emitter (`scrubreport.go:80`) and gateway handler (`scrubreport_server.go:75`) exist but the adapter has no production caller. It is a distinct concern (`maxConcurrentSessions > 1` per-slot release, rather than the occupancy-zero whole-pod boundary) and belongs to its own finding. This proposal scopes to the whole-pod scrub only and records the per-slot gap as a non-goal.
- **The concurrent-session (`maxConcurrentSessions > 1`) occupancy-zero whole-pod scrub trigger is wired in a follow-on finding, not here.** A recycling pool with `maxConcurrentSessions > 1` is a valid configuration (`poolstore.go:536-539` rejects only `allowCrossTenantReuse` on it), and its last-slot-drain edge reaches the same §5.2 whole-pod scrub. That edge runs through a different release path: `Binder.ReleaseSlot` sends only a per-slot `ShutdownSlot` and closes the connection (`slotbinder.go:494-514`), and `SlotClaimer.ReleaseSlot` patches the claim to `recycling` and arms the missing-report timeout on occupancy zero (`slotclaimer.go:679-704`) without triggering the adapter scrub. The adapter `Shutdown` handler also early-returns on any slot-qualified request (`session.go:226-227`) before the recycle branch C-A2 adds. Wiring the concurrent boundary requires threading the last-slot/occupancy-zero signal from `SlotClaimer.ReleaseSlot` back to `Binder.ReleaseSlot` so it sends a whole-pod recycle `Shutdown` carrying `podId` plus the scrub parameters before closing the adapter, with the adapter running the scrub outside the early-returning slot branch. That is a self-contained change with its own tier-2/tier-4 tests. This proposal wires the session-mode (`Binder.Release`) boundary and files the concurrent boundary as a separate implementation-only follow-on finding against the §5.2 whole-pod scrub contract S-A1 already covers. C-A3 therefore populates the scrub-config fields only on the session-mode bind result; the concurrent `slotBindRequest` does not carry them, because no code delivers them until the follow-on lands.

## 3. Trigger, config delivery, and async report

**Trigger.** The gateway already reaches the adapter's `Shutdown` handler on the recycle path (`binder.go:1818`), and the handler already tears the ending session's runtime down and releases the session (`session.go:244-248`). The `Shutdown` handler is therefore the point where the occupancy-zero whole-pod scrub belongs. This proposal adds a `recycle` disposition to `ShutdownRequest`. When it is present, the handler tears the session runtime down as before, then runs the whole-pod scrub; when it is absent (the terminate path), the handler behaves exactly as it does today.

**Config delivery.** The scrub parameters and the pod identity are delivered on the recycle-trigger `Shutdown` itself rather than held on the adapter across the session. The adapter holds no recycle state and does not need to. The gateway captures the parameters at session start, at the same instant it captures the `Recycle` flag, and carries them on the session-mode `BindResult` (`podRegistry.Put` at `start.go:2196`), then reads them back on release (`registry.Remove` at `executor/pod.go:313`, feeding `Release` with no pool re-resolution) and delivers them to the adapter on the recycle `Shutdown`. The concurrent-session bind result does not carry the scrub-config fields; the concurrent occupancy-zero trigger is a follow-on (see Non-goals). The scrub therefore runs against the pool configuration as it stood at session start; a pool whose `cleanupCommands` or `scrubProfile` changes mid-session is not re-resolved at the recycle boundary, matching how the `Recycle` flag itself is captured once at bind time. The gateway resolves the pool's `scrubProfile` into `PoolMatch.MicrovmScrubMode` (`resolve.go:264`, consumed by `scrubPolicyForPool` at `sessionserver.go:2506`), but `cleanupCommands` and `cleanupTimeoutSeconds` are not on `PoolMatch`; they live on the resolved `runtimestore.SessionPolicy` (`runtimestore.go:1040,:1043`). C-A3 folds `cleanupCommands` and `cleanupTimeoutSeconds` into `PoolMatch` from the `SessionPolicy` mirror (the way `AllowCrossTenantReuse` is already folded) and threads them plus `scrubProfile` and the pod's `SandboxName` (as `pod_id`) onto the recycle-path `Shutdown`. No cleanup shell mode is threaded: the pool configuration carries no cleanup shell field (`RecyclePolicy` and `SessionPolicy` have none; only `SetupCommandPolicy.Shell` exists, and it governs setup commands), so the scrub runs cleanup commands in the default argv mode (`scrub.Config.ShellMode` false).

**Async report.** The scrub runs asynchronously on the adapter. `Shutdown` returns to the gateway as soon as the session runtime is closed; the gateway then closes the gateway→adapter connection (`binder.go:1841`), which the async scrub does not depend on because it reports over the separate GatewayControl link (`gatewaylink.go:54`). The gateway bounds the report with the missing-report timeout it arms before sending `Shutdown` (`binder.go:1810-1811`): a scrub that never reports within `cleanupTimeoutSeconds` plus a grace retires the pod. A synchronous scrub inside the `Shutdown` response is rejected because it would hold the gateway on the scrub duration and couple the report to the connection the gateway closes immediately after `Shutdown` returns.

## 4. Proposed changes

### S-A1. Define the recycle-scrub trigger and scrub-config delivery in §4.7 and §5.2

**Target:** `spec/04_system-components.md`, §4.7 "Runtime adapter", the Gateway → Adapter RPC table (near line 663). And `spec/05_runtime-registry-and-pool-model.md`, §5.2, the "Lenny scrub procedure" paragraph (near line 457).

**Anchor and change (§4.7):** Extend the existing `Terminate` row of the Gateway → Adapter RPC table (`spec/04:663`), which already denotes the single proto `rpc Shutdown` (`schemas/lenny-adapter.proto:163`). The table has no separate `Shutdown` row and there is no `rpc Terminate`, so the recycle disposition extends this one row rather than adding a second row that would map a second name to the same proto RPC. Rewrite the row to name the recycle disposition and reconcile the spec name (`Terminate`) with the proto name (`Shutdown`); the existing `adapterclient` mapping comment (`pkg/gateway/runtime/adapterclient/client.go:806-809`) stays accurate because the spec name remains `Terminate`.

```markdown
| `Terminate` (proto `Shutdown`) | Graceful end-of-session shutdown of the pod's runtime. On the default disposition the adapter closes the session runtime and the pod is replaced. On the **recycle disposition** (occupancy zero on a recycling pod, [Section 5.2](05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes)) the request also carries the pod identity (`podId`) and the whole-pod scrub parameters (`cleanupCommands`, `cleanupTimeoutSeconds`, `scrubProfile`); the adapter closes the ending session's runtime, keeps the pod process alive across the recycle boundary, runs the §5.2 whole-pod scrub asynchronously, and reports its binary outcome for `podId` on the GatewayControl link via `ReportPodScrub`. The gateway does not block the response on the scrub; a missing report is bounded by the gateway-side timeout (`cleanupTimeoutSeconds` plus a grace period). |
```

**Anchor and change (§5.2):** Append the trigger and delivery mechanism to the end of the "Lenny scrub procedure" paragraph, after the sentence ending `a missing report is bounded by a gateway-side timeout (` `cleanupTimeoutSeconds` `plus a grace period), after which the pod is retired.` (`spec/05:457`).

```markdown
 The gateway triggers the whole-pod scrub by sending the adapter the `Terminate` RPC ([Section 4.7](04_system-components.md#47-runtime-adapter), the proto `Shutdown`) carrying the **recycle disposition**, the pod identity (`podId`), and the pool's scrub parameters (`cleanupCommands`, `cleanupTimeoutSeconds`, and `scrubProfile`). The gateway sends this request after it has patched the claim to `recycling` and armed the missing-report timeout, keyed on `podId`. On the recycle disposition the adapter closes only the ending session's runtime, keeps the pod process alive across the recycle boundary, runs the scrub asynchronously, and reports the outcome for `podId` via `ReportPodScrub` on its GatewayControl link. The gateway does not block the response on the scrub. The gateway captures the scrub parameters when the session binds, at the same instant it captures the pool's recycle setting, and delivers them on this request; the adapter holds no recycle state of its own.
```

**Rationale:** §5.2 states that the whole-pod scrub "runs" and is reported via `ReportPodScrub` (`spec/05:453,:457`) but names no mechanism by which the gateway triggers the adapter or delivers the scrub configuration, and the §4.7 Gateway → Adapter table (`spec/04:643-663`) documents the single proto `Shutdown` RPC only as the `Terminate` row (`spec/04:663`) with no recycle disposition and no message carrying the scrub parameters. That silence is why `scrub.Run` and the adapter `ReportPodScrub` emitter were left with no production caller. Extending the `Terminate` row with the recycle disposition, the pod identity, and the parameters it carries gives the adapter side a defined contract to implement and matches the existing recycle-path code intent (`binder.go:1813-1818`), without adding a second table row for the one proto RPC. The spec text states the contract for every occupancy-zero recycle boundary, matching §5.2's existing statement that the whole-pod scrub "runs whenever occupancy reaches zero on a recycling pod" (`spec/05:451`), which spans both session-mode and concurrent pools. This proposal's code (C-A2, C-A3) wires the trigger for the session-mode boundary; the concurrent-session boundary is a filed implementation-only follow-on against the same contract, the same way step 7's Kata restarter is deferred against an already-complete spec.

### C-A1. Extend `ShutdownRequest` with a recycle scrub sub-message

**Target:** `schemas/lenny-adapter.proto`, `message ShutdownRequest` (lines 1318-1328).

**Anchor and change:** Add a `RecycleScrub` sub-message and a `recycle` field to `ShutdownRequest`, after the existing `slot_id` field.

```proto
message ShutdownRequest {
  SessionId session_id = 1;
  string reason = 2;
  int32 deadline_ms = 3;
  // slot_id, when set, tears down just this §6.4 per-slot session (its
  // runtime, credential timers, and per-slot directory tree) while
  // sibling slots on the pod keep running. Empty when
  // `maxConcurrentSessions: 1` (the whole-pod shutdown). spec: §6.4 lines
  // 401-405.
  SlotId slot_id = 4;

  // recycle, when set, marks this as the occupancy-zero recycle-boundary
  // shutdown (§5.2): the adapter closes the ending session's runtime, keeps
  // the pod process alive, runs the §5.2 whole-pod scrub with the carried
  // parameters, and reports the binary outcome asynchronously via
  // ReportPodScrub. Absent on the terminate path (the pod is replaced).
  // spec: §5.2 recycle lifecycle; §4.7 Shutdown recycle disposition.
  RecycleScrub recycle = 5;
}

// RecycleScrub carries the pod identity and the §5.2 whole-pod scrub
// parameters the adapter needs to run the scrub at the recycle boundary and
// report its outcome. The gateway resolves these from the pod's SandboxName
// and the pool's sessionPolicy.recycle block.
message RecycleScrub {
  // pod_id is the agent_pod_state row key (the Sandbox name) the gateway
  // resolves the recycling claim from and keys the missing-report timeout on.
  // The adapter, which holds no pod identity of its own, echoes it back in
  // ReportPodScrub so the report matches the timer the gateway armed before
  // sending this request. spec: §4.7 ReportPodScrub pod_id (proto line 452).
  string pod_id = 1;
  // cleanup_commands are the deployer-defined cleanupCommands run after the
  // credential purge (step 0) and before scrub steps 1-6. Empty runs no
  // cleanup commands. spec: §5.2 line 415.
  repeated string cleanup_commands = 2;
  // cleanup_timeout_seconds is the aggregate cap on cleanup_commands; the
  // gateway-side missing-report timeout is this value plus a grace period.
  int32 cleanup_timeout_seconds = 3;
  // scrub_profile is one of "standard", "vm-restart", or "in-place" and
  // selects the §5.2 scrub variant. "vm-restart" adds step 7 (guest VM
  // restart); with no concrete VMRestarter the adapter withholds the report
  // (fail-closed) so the missing-report timeout retires the pod. spec: §5.2
  // lines 473-477. There is no cleanup shell field: the pool configuration
  // carries none, so cleanup commands run in the default argv mode.
  string scrub_profile = 4;
}
```

**Rationale:** The recycle disposition and the scrub parameters need a wire representation on the existing `Shutdown` RPC so the gateway can deliver them and the adapter can branch on them. A sub-message keeps `ShutdownRequest`'s terminate path (`recycle` unset) byte-identical to today and isolates the scrub parameters in one place. The derived `*.pb.go` is regenerated from this definition; it is not hand-edited (see `code-best-practices.md` escape hatches).

### C-A2. Add the adapter-side scrub driver and branch `Shutdown` on the recycle disposition

**Target:** `pkg/adapter/session.go`, `Server.Shutdown` (lines 218-250), a new `pkg/adapter/podscrub.go`, and `pkg/adapter/gatewaylink.go` / `pkg/adapter/server.go` to retain the dialed `*gatewaycontrol.Client` on the `Server` as a `PodScrubReporter` (a small consumer-side interface with the one `ReportPodScrub` method) so the driver can send the report. The `Server` gains no pod-identity field; the pod id arrives on the `RecycleScrub` message.

**Anchor and change (`session.go`):** In `Server.Shutdown`, after the session runtime is closed and the session released (`:246-248`), branch on `req.GetRecycle()`. On the recycle disposition, hand off to the new driver, which runs the scrub asynchronously and reports via `ReportPodScrub`; on the terminate path (recycle unset), return as today.

```go
	closeCtx, cancel := contextWithGraceDeadline(ctx, time.Duration(req.GetDeadlineMs())*time.Millisecond)
	closeErr := s.Runtime.Close(closeCtx, sessionID)
	cancel()
	s.releaseSession()
	// spec: §5.2 recycle lifecycle; §4.7 Shutdown recycle disposition. On the
	// occupancy-zero recycle boundary the pod process stays alive: after the
	// ending session's runtime is closed, run the whole-pod scrub and report
	// its binary outcome asynchronously via ReportPodScrub. The Shutdown
	// response does not wait for the scrub; the gateway bounds it with the
	// missing-report timeout it armed before sending this Shutdown.
	if rc := req.GetRecycle(); rc != nil {
		s.startPodScrub(rc)
	}
	return &adapterv1.ShutdownResponse{ExitedCleanly: closeErr == nil}, nil
```

**Anchor and change (new `pkg/adapter/podscrub.go`):** Add a small driver that builds `scrub.Config` from the `RecycleScrub` message, runs `scrub.Run` on a background context, and reports the binary outcome for the message's `pod_id` via the GatewayControl `ReportPodScrub` emitter retained on the `Server`. It selects a `nil` `VMRestarter` for `standard` and `in-place` profiles. For a `vm-restart` profile with no concrete restarter it withholds the report entirely (recognizing `scrub.ErrNoRestarter`), so the gateway missing-report timeout retires the pod rather than reusing it under the default `warn` policy.

```go
// startPodScrub runs the §5.2 whole-pod scrub for the recycle boundary and
// reports its binary outcome via ReportPodScrub. It runs on a background
// context because the Shutdown response has already returned and the
// gateway→adapter connection is closed immediately after; the scrub reports
// over the separate GatewayControl link. The gateway bounds the report with
// its missing-report timeout, so a scrub that hangs or crashes here retires
// the pod rather than leaving it stuck in `recycling`.
//
// spec: §5.2 whole-pod scrub; §4.7 ReportPodScrub.
func (s *Server) startPodScrub(rc *adapterv1.RecycleScrub) {
	go func() {
		ctx := context.Background() // the RPC context is gone; the gateway timeout bounds this.
		cfg := s.scrubConfig(rc)
		rep, err := scrub.Run(ctx, s.ScrubOps, cfg)
		if errors.Is(err, scrub.ErrNoRestarter) {
			// A vm-restart pool with no concrete VMRestarter cannot perform the
			// step-7 guest VM restart. Reporting any outcome would let the
			// gateway reuse the pod: under the default `warn` policy podscrub.Decide
			// returns the pod to the pool on a failed scrub, and on an
			// allowCrossTenantReuse pool that reuses it across tenants without the
			// VM restart the profile exists to perform. Withhold the report so the
			// gateway missing-report timeout retires the pod — the identical
			// fail-closed posture that holds today, until the Kata client lands.
			slog.Warn("adapter: vm-restart scrub without a concrete restarter; withholding report so the pod is retired", "pod", rc.GetPodId())
			return
		}
		outcome, detail := scrubOutcome(rep, err)
		if reportErr := s.PodScrubReporter.ReportPodScrub(ctx, rc.GetPodId(), outcome, detail); reportErr != nil {
			// The gateway missing-report timeout is the backstop; log and move on.
			slog.Error("adapter: ReportPodScrub failed", "pod", rc.GetPodId(), "err", reportErr)
		}
	}()
}

// scrubConfig maps the recycle-trigger parameters onto scrub.Config. It leaves
// Restarter nil for the standard and in-place profiles (which never reach
// step 7) and only wires a concrete VMRestarter for vm-restart. A vm-restart
// profile with no concrete restarter leaves MicrovmRestart set with a nil
// Restarter, so scrub.Run returns ErrNoRestarter and the driver withholds the
// report (fail-closed). ShellMode is left at its false default because the pool
// configuration carries no cleanup shell field. spec: §5.2 lines 473-477;
// scrub.ErrNoRestarter.
func (s *Server) scrubConfig(rc *adapterv1.RecycleScrub) scrub.Config {
	cfg := scrub.Config{
		CredentialFile: s.CredentialFile,
		WorkspaceDir:   s.WorkspaceDir,
		// cleanupCommands, cleanupTimeoutSeconds, and the standard step
		// callbacks are populated from rc and the adapter's own ops.
	}
	if rc.GetScrubProfile() == "vm-restart" {
		cfg.MicrovmRestart = true
		cfg.Restarter = s.VMRestarter // nil until the Kata client lands (see Non-goals).
	}
	return cfg
}

// scrubOutcome converts a completed scrub Report (or a step failure) into the
// ReportPodScrub outcome and an audit detail string. The ErrNoRestarter start
// error is intercepted by startPodScrub before this is called and never
// produces a report.
func scrubOutcome(rep *scrub.Report, err error) (gatewaycontrol.PodScrubOutcome, string) {
	if err != nil {
		return gatewaycontrol.PodScrubFailed, err.Error()
	}
	if rep.Result == scrub.Failed {
		return gatewaycontrol.PodScrubFailed, rep.FailureDetail()
	}
	return gatewaycontrol.PodScrubSucceeded, ""
}
```

**Rationale:** This is the missing production caller for both `scrub.Run` (`scrub.go:232`) and `Client.ReportPodScrub` (`scrubreport.go:103`). The driver runs on a background context because the `Shutdown` RPC context is gone by the time the scrub runs and the gateway→adapter connection is closed right after `Shutdown` returns (`binder.go:1841`); the report travels the independent GatewayControl link (`gatewaylink.go:54`). The `ErrNoRestarter` interception keeps `vm-restart` pools without a concrete restarter fail-closed: the driver withholds the report, so the gateway missing-report timeout retires the pod rather than `podscrub.Decide` reusing it under the default `warn` policy. `standard` and `in-place` pods scrub and reuse without the concrete Kata client. The pod id is read from `rc.GetPodId()` (the gateway's `SandboxName`, echoed back so the report matches the armed timer); the report travels through `s.PodScrubReporter`, the dialed `*gatewaycontrol.Client` retained on the `Server` in `ConnectGateway`. Field and helper names (`ScrubOps`, `VMRestarter`, `PodScrubReporter`, `FailureDetail`) align to the existing `scrub` and `gatewaycontrol` surfaces at implementation time; the driver is a thin adapter over them rather than new scrub logic.

### C-A3. Populate the recycle disposition and scrub config on the recycle-path `Shutdown`

**Target:** `pkg/gateway/podlifecycle/podsession/resolve.go` (`PoolMatch` gains `CleanupCommands` and `CleanupTimeoutSeconds`, folded from the `runtimestore.SessionPolicy` mirror the way `AllowCrossTenantReuse` already is; `MicrovmScrubMode` already carries `scrubProfile`), the session-mode `pkg/gateway/sessionserver` bind-request builder (`exclusiveBindRequest`, `start.go:1881-1903`, which builds the `BindRequest` from `match`), `pkg/gateway/podlifecycle/podsession/binder.go` (`BindResult` carries the scrub config from the resolved pool, populated on the session-mode bind path; `shutdownAdapter`, lines 1836-1841, gains a `recycle bool` parameter; the two `Release` call sites at `binder.go:1818` and `:1823` pass the effective recycle decision), and `pkg/gateway/runtime/adapterclient/client.go` (`ShutdownRecycle` variant that carries the recycle sub-message). The concurrent `slotBindRequest` builder and `slotbinder.go` are not modified: the concurrent occupancy-zero trigger is a follow-on finding (see Non-goals), so populating the scrub-config fields on the concurrent bind result would leave them undelivered.

**Anchor and change:** Fold the pool's `cleanupCommands` and `cleanupTimeoutSeconds` from the `SessionPolicy` mirror into `PoolMatch` in `resolve.go` (they are not on `PoolMatch` today; only `MicrovmScrubMode` is), and populate them plus the `SandboxName` onto the session-mode `BindResult` in the `exclusiveBindRequest` builder alongside the existing `Recycle` flag and `scrubProfile` (`SandboxName` is already on `BindResult`, used at `slotbinder.go:514` and `binder.go:1800`). The parameter is required because `BindResult.Recycle` is the pool-level `sessionPolicy.recycle.enabled` flag (outcome-independent, `binder.go:495-505`); a failed or crashed session on a recycle-enabled pool short-circuits the recycle branch and falls through to the retire path with `result.Recycle` still true (`binder.go:1799`, `:1822-1823`).
```go
// shutdownAdapter shuts the pod's runtime down through the adapter and closes
// the connection. recycle carries the effective per-release recycle decision
// (Release's `result.Recycle && disposition != dispositionFailed`), passed
// true only from the recycle branch and false from the retire path; it is not
// re-derived from result.Recycle here, because result.Recycle is the
// pool-level recycle.enabled flag and a failed/crashed session on a recycling
// pool takes the retire path with that flag still set. On the recycle path it
// sends the §4.7 recycle disposition plus the pool's whole-pod scrub
// parameters, which is the occupancy-zero signal that triggers the §5.2 scrub
// the adapter reports via ReportPodScrub. On the retire path it sends a plain
// Shutdown that tears the session's processes down before the pod drains. A
// nil Adapter is a no-op.
func (b *Binder) shutdownAdapter(ctx context.Context, result *BindResult, recycle bool) {
	if result.Adapter == nil {
		return
	}
	if recycle {
		_, _ = result.Adapter.ShutdownRecycle(ctx, result.SessionID, adapterclient.RecycleScrub{
			PodID:                 result.SandboxName,
			CleanupCommands:       result.CleanupCommands,
			CleanupTimeoutSeconds: result.CleanupTimeoutSeconds,
			ScrubProfile:          result.ScrubProfile,
		})
	} else {
		_, _ = result.Adapter.Shutdown(ctx, result.SessionID)
	}
	result.Adapter.Close()
}
```

The two call sites pass the decision explicitly: the recycle branch calls `b.shutdownAdapter(ctx, result, true)` at `binder.go:1818`, and the retire path calls `b.shutdownAdapter(ctx, result, false)` at `binder.go:1823`.

**Rationale:** The gateway resolves the pool's `scrubProfile` into `PoolMatch.MicrovmScrubMode` (`resolve.go:264`, consumed by `scrubPolicyForPool` at `sessionserver.go:2506`) but not the pool's `cleanupCommands` and `cleanupTimeoutSeconds`, which live on the resolved `runtimestore.SessionPolicy` (`runtimestore.go:1040,:1043`) and are not on `PoolMatch`. C-A3 folds those two fields into `PoolMatch` from the `SessionPolicy` mirror, carries them and the `SandboxName` onto the session-mode `BindResult` through the `exclusiveBindRequest` builder, and delivers them on the recycle-trigger `Shutdown`, where `shutdownAdapter` currently calls `Adapter.Shutdown` with a session id alone (`binder.go:1840`). The `recycle` parameter makes `shutdownAdapter` match `Release`'s recycle predicate (`result.Recycle && disposition != dispositionFailed`, `binder.go:1799`) so a failed or crashed session on a recycling pool retires its pod with a plain `Shutdown` rather than triggering the scrub-and-reuse path; keying on `result.Recycle` alone would fire the recycle disposition on the retire path because that flag is the outcome-independent pool config value. C-A3 preserves the existing ordering (patch claim `recycling`, arm the missing-report timeout keyed on `SandboxName`, then send the recycle `Shutdown`, `binder.go:1800-1818`). The retire path is unchanged apart from passing `recycle: false`. The consumer side and the timeout are not modified.

## 5. Non-goals

- **The concrete Kata `VMRestarter` for scrub step 7 (split out as a separate implementation-only finding).** Step 7 is already fully specified (`spec/05:473-477`), so it stages no spec change and is a pure code implementation against an already-complete spec. It requires the Kata runtime's VM lifecycle API (`spec/05:475`) on a `microvm → kata` RuntimeClass (`spec/05:670`), a tier-6 behavior Kind cannot reproduce, and there is no existing Kata VM-lifecycle client to reuse (the only `kata` references in the tree are node-pool scheduling and isolation labels, `pkg/controller/sandbox/podspec/podspec.go:990-1050`, `pkg/sandbox/isolation/profile.go:95`, and the only `VMRestarter` implementer is `fakeRestarter` in `scrub_test.go`). Coupling it here would tie a CI-testable spec-gap fix to operator hardware that cannot run to green in the same landing, and its absence causes no isolation regression: for a `vm-restart` pool that reaches step 7 without a concrete restarter, `scrub.Run` returns `ErrNoRestarter` and the driver withholds the `ReportPodScrub` entirely, so the gateway missing-report timeout retires the pod, which is the current fail-closed default. It is filed as a standalone BUILD-GAPS finding against §5.2 step 7, NEEDS-OPERATOR (Kata RuntimeClass), to be built when a Kata host is available. C-A2 keeps a `vm-restart` profile with a nil restarter fail-closed by withholding the report on `scrub.ErrNoRestarter` rather than emitting a `PodScrubFailed` the default `warn` policy would treat as a reuse.
- **The per-slot cleanup report (`ReportSessionScrub`) adapter-side wiring.** Its emitter (`scrubreport.go:80`) and gateway handler (`scrubreport_server.go:75`) exist, but the adapter has no production caller. This is a distinct `maxConcurrentSessions > 1` per-slot-release concern rather than the occupancy-zero whole-pod boundary, and belongs to its own finding.
- **The concurrent-session (`maxConcurrentSessions > 1`) occupancy-zero whole-pod scrub trigger (split out as a separate implementation-only finding).** A recycling pool with `maxConcurrentSessions > 1` is a valid configuration; the pool controller rejects only `recycle.allowCrossTenantReuse` on it (`poolstore.go:536-539`), and its last-slot-drain edge reaches the same §5.2 whole-pod scrub that S-A1 specifies. Wiring it requires threading the last-slot/occupancy-zero signal from `SlotClaimer.ReleaseSlot` back to `Binder.ReleaseSlot` so it sends a whole-pod recycle `Shutdown` carrying `podId` and the scrub parameters before closing the adapter, with the adapter running the scrub outside the early-returning slot branch, plus its own tier-2 and tier-4 tests for a concurrent recycling pool reusing on success and retiring on a withheld report. It is filed as a standalone implementation-only BUILD-GAPS finding against the §5.2 whole-pod scrub contract S-A1 defines, to keep this proposal's landing to the session-mode path. Until it lands, a concurrent recycling pod at occupancy zero is retired fail-closed by the missing-report timeout, the same posture that holds today; there is no isolation regression.
- **The gateway consumer side of `ReportPodScrub`.** The `leasecontrol` handler (`scrubreport_server.go:113`), `podscrub.Decide` (`podscrub.go:254-358`), the recycle-boundary missing-report timeout (`recycleboundary.go`), and their wiring (`cmd/lenny-gateway/main.go:699-744`, `stores.go:1621`) are already built and are not modified.
- **The §6.2 recycle disposition table and the preConnect re-warm edge**, which are already implemented and consume the report unchanged.
- **Changing the missing-report timeout, the fail-closed retirement behavior, or the checkpoint/isolation model.** Between-session isolation is already preserved by fail-closed retirement; this proposal restores the pod-reuse optimization without weakening that backstop.
- **Any cross-tenant microvm reuse semantics beyond invoking step 7.** Tenant pinning, the T4 prohibition, and the `allowCrossTenantReuse` gate (`spec/05:445-449`) are unchanged.
- **A synchronous scrub inside the `Shutdown` response.** The scrub is asynchronous and bounded by the existing gateway-side missing-report timeout.
