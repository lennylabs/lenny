# Summary: Sidecar runtime processes have no platform supervisor

## Summary

**Problem statement.** On a sidecar pod the kubelet starts the runtime image's entrypoint once, and nothing the platform controls launches, observes, or ends the runtime process. That leaves the first session without a manifest (F-4.7.26), specification promises about signals, deadlines, and exit codes that nothing keeps (F-4.7.27), no sidecar SDK-warm (F-6.1.28), a scrub that cannot reach the runtime container (F-5.2.37, F-5.2.39 step 3), `cleanupCommands` exposed to agent-planted symlinks (F-5.2.36), a hung runtime that passes the scrub (F-5.2.46), and keeping the process as the only reuse path on non-microVM recycling pools. The owner directed a platform supervisor as the first process of the runtime container on every sidecar pod (plan §10.3). This is part 1. Part 2, cross-tenant reuse on `in-place` pools, moved to proposal 0096.

**What changes.**

- `Runtime.spec.command` is required on every `type: agent` sidecar Runtime, on the Runtime CRD, from which the RuntimeReconciler mirrors a derived `restartable` flag into the runtime registry. An optional `Runtime.spec.env` list of name and value pairs, also on the Runtime CRD, gives the runtime process the variables its image `ENV` no longer supplies (§5.1; the Runtime CRD, the RuntimeReconciler, and the runtime registry).
- A pool field `sessionPolicy.recycle.runtimeProcess: keep | restart` selects the runtime-process lifetime of the pods a reusing recycling pool creates, which each pod carries from its creation as a `keep` pod or a `restart` pod (D-PODLIFETIME). Gateway pool admission requires it where 0079's keep rule applies, refuses `restart` on a runtime that is not `restartable`, and exempts `restart` on a sequential pool from `acknowledgeProcessLevelIsolation` (§5.2; `poolstore`, the tenant-pin and acquisition predicates, the SandboxTemplate mirror).
- A runtime supervisor, a static C binary from its own digest-pinned image `lenny-supervisor`, is staged by an init container into a volume mounted read-only into the runtime container, and runs as the runtime container's first process on every sidecar pod of a `type: agent` runtime (§4.7.10 **Runtime supervisor.**, §4.7.11 item 8, §13.1; `supervisor/`, `pkg/controller/sandbox/podspec`, the chart, and CI).
- A new intra-pod channel, `CH-SUPERVISE`, carries launch, end, liveness, the supervisor's self-test report, and exit reports as JSON Lines, with a generation number and request ID on every message and mutual peer-UID authentication. The adapter gates READY on it (§28.3, §28.5.3, §28.6, §28.8; `pkg/adapter`).
- The runtime process is launched after the manifest exists, ended on `DemoteSDK` and, on a `restart` pod, in each whole-pod scrub, before and again after `cleanupCommands`, and proven gone by two consecutive clean passes. After each of those boundary ends on a `restart` pod the supervisor's forked worker sweeps the agent UID's IPC objects and files (§4.7.10 **Runtime supervisor.** **Sweep.**, §4.7.9, §5.2, §6.1; `pkg/adapter`, `pkg/adapter/scrub`).
- On every pod that runs the supervisor the deployer's `cleanupCommands` run at the agent UID in the runtime container, in a worker the supervisor forks, and on a `restart` pod the boundary ends every process again after them (§5.2; `supervisor/`, `pkg/adapter/scrub`).
- The `CH-MSGSOCK` and `CH-RUNTIMEOPS` listeners are closed and rebound between an attested end and the next launch, and the adapter's own scrub file operations resolve beneath their root with no symlink traversal (§4.7.10, §5.2; `pkg/adapter`).
- The specification's `shutdown` deadline, SIGTERM and SIGKILL, and exit-code statements become true on sidecar pods through `CH-SUPERVISE`, or are corrected where they cannot be (§28.5.3, §28.8, §15.4).

**Decisions.**

- **D-SCOPE.** Part 1 only, on every sidecar pod of a `type: agent` runtime: session-mode and service-mode, `preConnect` or not, `keep` or `restart`. Embedded runtimes have no runtime container and are unchanged. A `type: mcp` runtime gets no supervisor and no `command`, because the specification defines no launch for it and its runtime-side path is Phase 12b (§18.29). This departs from the problem statement's recorded owner decision that every sidecar pod runs the supervisor, and the owner approved the departure on 2026-10-22. `type: mcp` runtimes stay unsupervised and without `command` until the proposal that defines their launch, which the `type: mcp` supervision follow-up in gateway-runtime-comms-remediation.md §10.2 records. Part 2 is proposal 0096.
- **D-MOTIVATION.** Kind `new`. It is a capability the owner directed, and it also closes the BUILD-GAPS findings the plan's Phase 2 entry assigns to it.
- **D-COMMAND.** `command` is required on a `type: agent` sidecar Runtime and forbidden on every other Runtime (§5.1 **`command`**). It is settable only on the Runtime CRD, as `requireSoPeercred` is. Plan §10.3 says both that `command` stays CRD-only (the admission-predicate decision) and that the admin registration API gains it (the later supervisor-scope decision); the proposal follows the CRD-only decision, which departs from the problem statement's recorded owner decision. The owner approved the departure on 2026-10-22: `command` and `env` are settable only on the Runtime CRD. An admin-only record has no pod path, the pod builder reads the live CRD, and `lenny up` seeds the embedded `echo` and the §26 records through the admin path, so a payload field would have no consumer and would break those seeds. Admission reads only the registry's `restartable` (D-RESTARTABLE).
- **D-LIFETIME.** `recycle.runtimeProcess` is required, with no default, on every reusing recycling pool (SPEC-5(b)), sequential or concurrent, and rejected on every other pool. A `keep` pod and a `restart` pod are pods whose lifetime, fixed at creation from the pool's `recycle.runtimeProcess` and carried by the pod label (D-PODLIFETIME), is `keep` or `restart`; SPEC-5(b) defines both terms, and every staged lifetime statement uses them. A `keep` pod has 0079's lifetime unchanged. A `restart` pod launches a new runtime process for the first session after each occupancy-zero boundary at which it is reused, and on a concurrent pool sessions that start while a process is live join it. Retirement at `maxSessionsPerPod` or `maxPodUptimeSeconds` is the same on both kinds of pod. The pool field is read only at pod creation, by pool admission, and by the acknowledgment requirement.
- **D-RESTARTABLE.** The RuntimeReconciler mirrors only `restartable`, as §5.1 **`command`** defines it, decided 2026-10-22 under the owner's delegation: `command` and `env` stay on the Runtime CRD, which the pod builder reads, so registry copies of them would have no reader. Gateway pool admission refuses `restart` when the flag is false, so the deployer gets a synchronous error, as plan §10.3 records.
- **D-ACK.** A sequential pool under `recycle.runtimeProcess: restart` does not require `acknowledgeProcessLevelIsolation`. `acknowledgeBestEffortScrub`, which every recycling pool already requires, covers the remaining shared state. A concurrent pool requires the acknowledgment under both values, because its sessions share a process while they overlap. `KeepsRuntimeAcrossSessions` therefore splits: the acknowledgment predicate becomes "concurrent, or recycling under `keep`", and the same-tenant reuse predicate that `AdmitTenantPin` and the reserved-hold rebind read becomes "the pool reuses pods", so same-tenant reuse and the reserved hold do not depend on the field. The tenant pin is the same on a `keep` pod and a `restart` pod. A pod's lifetime is fixed when the pod is created (D-PODLIFETIME).
- **D-RESTARTGATE.** Approved by the owner on 2026-10-22. Until proposal 0084 lands, gateway pool admission refuses `recycle.runtimeProcess: restart` on every pool. The refusal is a code-only gate in CODE-5 with no specification text, so SPEC-5 states only the end-state admission rule. The reason is the intra-pod MCP nonce rule: an intra-pod MCP server validates the nonce bound at its start, and a later manifest write does not re-arm it (§29.2 step 26a, the §4.7.6 `mcpNonce` row, and §15.4.3 **Authentication**), so a process launched after the first on a `restart` pod has no specified way to authenticate its platform MCP calls until 0084 rebinds the intra-pod MCP servers per runtime generation. The gate returns `400 VALIDATION_ERROR` (§15.1), as the other recycle-policy rejections do, and its code comments state the interim reason and that the gate is removed when 0084 lands. The remediation plan records the gate beside the 0084 entry. Cases that need an admitted `restart` pool above tier 1 are written now and skipped through `tests/registers/skip-reasons.yaml` until 0084 lands.
- **D-PODLIFETIME.** Decided 2026-10-22 under the owner's delegation, replacing the re-baseline's delivery of the lifetime on the `Shutdown` recycle disposition, which needed a proto field in the S-2 proto window. The pod builder renders the pool's `recycle.runtimeProcess` into the adapter flag `--runtime-process` and the pod label `lenny.dev/runtime-process` when it creates the pod (`keep` on every pod where the pool's value is not `restart`). That fixed value makes the pod a `keep` pod or a `restart` pod (SPEC-5(b)). The adapter reads its lifetime from the flag and holds no other recycle state. An admitted edit of the field applies to pods created after it. A `keep` pod that has served an earlier session is acquired again only while the resolved configuration requires `acknowledgeProcessLevelIsolation`. Otherwise every acquisition refuses the pod and requests its drain, as 0079's fail-closed edit rule does. A `restart` pod stays one after an edit of the field to `keep`, which gives more separation than the pool asks for. The disposition alternative was rejected for two reasons beyond the proto field. A pod whose last boundary disposition was `keep` and that sits `reserved` or `idle` would serve one more session in the kept process after an edit of the field to `restart` that removed the acknowledgment. A pod that started as a `keep` pod became Ready with any failed property only logged (D-PROPERTIES), and would then end its runtime process at boundaries without the property gate.
- **D-BINARY.** The supervisor is a single-threaded freestanding C program, built static with no `PT_INTERP`, no dynamic section, no libc, and no NSS, in its own digest-pinned image `lenny-supervisor` that carries only the binary. A Go supervisor is excluded because the Go runtime installs its own signal handlers, loses `si_pid`, and dies on default-action signals (plan §10.3, gVisor spike). The image is a chart value and a controller flag, is signed and in the cosign policy, and a CI check rejects a binary with an interpreter, a dynamic section, or a `dlopen` or NSS reference. The draft's adapter subcommand is withdrawn.
- **D-STAGE.** An init container `lenny-supervisor-stage` runs the supervisor image's own `stage` mode to copy the binary into an `emptyDir` volume. It runs at a dedicated UID that is neither the agent nor the adapter UID, because §13.1 **Container identity.** reserves both for the regular containers `runtime` and `adapter`. The runtime container mounts the volume read-only, and no container other than `lenny-supervisor-stage` mounts it read-write.
- **D-ENV.** The supervisor calls `clearenv()` before anything else and launches each runtime process with an explicit environment the pod builder renders into its arguments: a fixed `PATH`, the Runtime's `env` (D-RUNTIMEENV), and the platform's runtime variables (the socket names and the manifest path). Nothing secret is rendered, because `/proc/1/cmdline` is readable at the agent UID. It opens no file in the runtime image's root filesystem: only `/proc` and platform volumes, through `openat` with `O_NOFOLLOW`. Each launch therefore starts from the same environment, which makes the runtime half of scrub step 3 true (F-5.2.39).
- **D-RUNTIMEENV.** Decided 2026-10-22 under the owner's delegation, replacing the re-baseline's "no `Runtime.spec.env` field". `Runtime.spec.env` is an optional list of name and value pairs, **Inherited** in the derived-runtime merge, because the supervisor ignores the image's `ENTRYPOINT`, `CMD`, and `ENV` and calls `clearenv()` first, so a runtime whose image set a variable such as a virtual-environment `PATH` would otherwise lose it with no replacement. The values are visible at the agent UID, so the field carries no `envFrom` and no reference to a Secret or ConfigMap, and secrets reach the runtime through the credential file. No per-pool override is added. SPEC-1 §5.1 **`env`** is the home of the field's rules, and SPEC-2 **Environment.** of the order in which the supervisor applies it.
- **D-SIGNALS.** Redesigned 2026-10-22 (third redesign). The supervisor handles every catchable signal, takes no action that depends on a signal's sender, and takes none on the kubelet's stop signal, so the `si_pid`/`si_code` stop-request filter of the earlier staging is withdrawn. After round 21 the filter had no action left to select, and plan §10.3's rule that the supervisor acts on a shutdown signal only when `si_pid == 0` holds because it acts on none. SPEC-2 **Signals.** is the home of each signal source's action and outcome.
- **D-CHANNEL.** `CH-SUPERVISE`, JSON Lines on the abstract socket `@lenny-supervise`, adapter flag `--supervise-socket`, and no proto field. Every message carries the runtime generation and a request ID, so the adapter can reject a reply or an exit report that belongs to no outstanding request or to an earlier process. No author-controlled bytes cross the channel; the only deployer-defined bytes are the `cleanupCommands` argv lists and the step-0 cleanup metadata (D-CLEANUP). The SPEC-7 §28.5.3 card is the home of the messages, their members, and the strict decoding.
- **D-AUTH.** The adapter listens and accepts once, through `peerCheckedListener` with the agent-UID check, and closes the listener. The supervisor dials, checks with `SO_PEERCRED` that the peer is the adapter UID, and exits when its connection closes. In nonce-only mode neither check is available, and ordering identifies both ends: the supervisor is the runtime container's first process, it launches nothing before `launch`, and §13.1 gives the agent and adapter UIDs to one container each.
- **D-READY.** The adapter waits for the supervisor's connection and its `ready` after its `SO_PEERCRED` self-test and before `srv.Serve`, so a pod whose supervisor never connects, or never sends `ready`, never becomes `idle`. On timeout the adapter exits non-zero.
- **D-LAUNCH.** The adapter asks for a launch only after the manifest the process reads exists and every listener the runtime dials is bound, which closes F-4.7.26 for every sidecar pod. A `scrub_warning` does not block a launch, because under `onScrubFailure: warn` the pod serves the next session as a `keep` pod does, and a failed end or sweep already retires it. SPEC-2 **Launch.** is the home of the launch points and the warm-up READY gate.
- **D-END.** The supervisor ends a runtime process by ending every other process in the runtime container and attests the end only after two consecutive clean passes, because the end has to hold against a runtime that does not cooperate (plan §10.6). On a recycle boundary the end has no SIGTERM grace, because the session is already sealed. SPEC-2 **End.** is the home, including the end's use for `DemoteSDK` and the `shutdown` deadline; CODE-2 adds the `pids.current` read.
- **D-SWEEP.** On a `restart` pod a worker the supervisor forks sweeps the agent UID's IPC objects and files after each boundary end. The sweep's volume list is the runtime container's writable mounts in `pkg/controller/sandbox/podspec/sidecar.go`, and the worker matches System V objects on `cuid` as well as `uid`, because an owner can move `uid` with `IPC_SET`. SPEC-2 **Sweep.** is the home of what the sweep removes, and SPEC-5 **Supervised scrub sequence.** of the outcome of each sweep result (F-5.2.36 and F-5.2.37, cleanup halves).
- **D-CLEANUP.** Decided 2026-10-22 under the owner's delegation, closing the re-baseline's open decision 1 with its option (b). On every pod that runs the supervisor, `keep` pods and `restart` pods alike, the deployer's `cleanupCommands` run at the agent UID in the runtime container, in a worker the supervisor forks, and on a `restart` pod a second end and sweep follow them even when they fail or run past the `cleanupTimeoutSeconds` deadline. Commands at the agent UID gain nothing from a symbolic link the agent planted (F-5.2.36), the runtime image carries the deployer's tools that the shell-less distroless adapter image lacks, and failed or timed-out commands are the ones most likely to leave processes behind. SPEC-2 **Cleanup.** is the home of how the worker runs the commands, the SPEC-7 card of what `cleanup` carries, SPEC-5(c) of the scrub order, and SPEC-5 **Supervised scrub sequence.** of each step's outcome. The embedded model has no supervisor and keeps running `cleanupCommands` in the adapter's container.
- **D-PATHS.** The adapter's own scrub file operations (`RemoveAll`, `ClearContents`, `PathState`, and log truncation) resolve with `openat2` and `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS` (F-5.2.36).
- **D-STALE.** Between an attested `end` and the next `launch`, the adapter closes and rebinds the `CH-MSGSOCK` listener and, when bound, the `CH-RUNTIMEOPS` listener, which discards every backlogged connection the ended process left. The manifest nonce already rotates at each session start (`writeSessionManifest`), and the runtime-first nonce line of the 0090 handshake rejects a stale connection that survives a rebind. The draft's argument that `CH-RUNTIMEOPS` rejects a stale peer because the adapter writes first is withdrawn: since 0090 the runtime writes first. The intra-pod MCP listeners belong to proposal 0084 (security review finding 4). 0087 does not render `--runtime-ops-socket`. R17 renders it and inherits the rebind.
- **D-TRANSPORT.** On a `keep` pod and a `restart` pod alike the adapter builds one 0079 `SocketRuntimeProcess` per launched process with the exported constructor and calls its `CloseListener` after an attested end, so 0079's sticky `ended` and no-redial rules hold per composed object. On a `keep` pod that is one per pod unless `DemoteSDK` ends the process.
- **D-COHORT.** Each launch increments the adapter's runtime generation, and the session cohort that `soleSession` reads resets at each new generation. On a `keep` pod one launch serves the pod's life unless `DemoteSDK` ends it, which is 0079's rule.
- **D-CRASH.** A runtime process that exits, other than by an `end`, while it holds a session fails each session it holds with `runtime_crash`, which proposal 0091's funnel takes to `resume_pending` (§7.3), and the pod retires on every pool (plan §10.3); on a concurrent pool every slot fails together, because the slots share the process. The adapter does not relaunch, because relaunch after a crash is deferred (Non-goals). SPEC-2 **Crash.** and **Liveness.** are the home, and the release row of SPEC-5 **Supervised scrub sequence.** decides an exit around the release of a `restart` pod's last session.
- **D-HUNG.** A heartbeat escalation on a `keep` pod marks the runtime as not live for the next boundary report, so a hung runtime no longer passes the occupancy-zero scrub (F-5.2.46). On a `restart` pod the boundary's `end` replaces the process. The supervisor liveness ping detects a frozen or dead supervisor and is a separate mechanism.
- **D-PING.** The adapter sends `ping` at a fixed interval while no other request is outstanding, and a missed `pong` deadline marks the runtime as not live (security review finding 10). The interval and deadline are adapter flags.
- **D-SDKWARM.** The pod builder fixes at pod creation, in the adapter flag `--warm-up-launch`, whether the pod launches its `preConnect` process at warm-up, and sets the flag when the pool's SDK-warm circuit breaker is closed at that moment. The WarmPoolController already reads `spec.sdkWarmDisabled` per Sandbox when it chooses the `sdk_connecting` route (`resolveSDKWarm` and `sdkWarmActive` in `pkg/controller/sandbox/sdkwarm.go`), and a fixed flag closes the round-3 gap in which the READY gate waited on a warm-up launch that the breaker suppressed. SPEC-2 **SDK-warm.** is the home of the sidecar SDK-warm lifecycle, including `ConfigureWorkspace`, `DemoteSDK`, and the re-warm edge. This closes F-6.1.28. R23 keeps the gateway `DemoteSDK` fallback.
- **D-SERVICE.** A service-mode runtime is launched at warm-up and kept for the pod's life. Its exit, or any other **Liveness.** condition, makes the adapter exit non-zero, because the pod has no boundary report; the failed pod is replaced.
- **D-PODEXIT.** At pod termination the supervisor forwards no stop signal to the runtime, and the adapter ends the runtime with `end` during its drain. The runtime is no longer its container's PID 1, so a forwarded SIGTERM would kill a runtime that has no SIGTERM handler, as the SDK runtimes have none, and fail each session it holds with `runtime_crash` while the adapter's preStop eviction checkpoint (§4.6.1) still needs the runtime. The kubelet row of SPEC-2 **Signals.** is the home of the pod-exit order.
- **D-SHUTDOWN.** The `CH-MSGSOCK` `shutdown` frame's contract becomes true on sidecar pods through `exited` and `end`, as SPEC-8 states in the `CH-MSGSOCK` card's **Timing.** bullet. Whether and when the adapter writes `shutdown` at pod drain stays with R16 and the adapter shutdown proposal. `RUNTIME_CRASH` is built from the exit status alone, because no runtime output crosses `CH-SUPERVISE`, and the "and stderr" wording is corrected (F-4.7.27).
- **D-PROPERTIES.** Decided 2026-10-22 (second redesign) under the owner's delegation. The supervisor reports its startup self-test in `ready` and gates nothing, and the adapter applies the gate on a `restart` pod, because the adapter knows the pod's lifetime from `--runtime-process` and its log is the only place a supervisor diagnostic reaches (D-LOGS). The re-baseline's `--require-properties` supervisor flag is withdrawn. SPEC-4 item 8 **Property self-test.** is the home of the tested properties, the pods each one gates, and `lenny-ctl preflight supervisor`. Sender identification stays in the self-test and the gating set because the owner recorded it (plan §10.3), although after the third redesign it protects no mechanism (D-SIGNALS); whether to retire it is the non-blocking open decision below.
- **D-LOGS.** The supervisor writes nothing to the runtime container's stdout or stderr, which the runtime inherits and can forge. Its diagnostics reach the adapter as enumerated codes, and the adapter logs them.
- **D-SURFACE.** No proto file changes. `CH-SUPERVISE` has no proto artifact, and the lifetime and the warm-up launch reach the adapter by flag (D-PODLIFETIME, D-SDKWARM). Migrations add the registry column `restartable` and the pool field's storage. Gateway behavior changes only in pool admission, the split predicates, and the acquisition read of the pod's lifetime label. The OpenAPI pool schema changes.
- **D-SPEC-HOMES.** The mechanism has one home, a new §4.7.10 **Runtime supervisor.** paragraph, whose **SDK-warm.** bullet is the home of the sidecar SDK-warm lifecycle, whose **Sweep.** bullet is the home of what the runtime sweep removes, and whose **Signals.** table is the home of the supervisor's action for each signal source. The outcome of each step of the scrub on a supervised pod, and of the launch that follows it on a `restart` pod, has one home, the §5.2 **Supervised scrub sequence.** table. The trust basis has one home, §4.7.11 item 8. The lifetime field has one home in §5.2. The `CH-SUPERVISE` contract has one home, its §28.5.3 card.
- **D-PART2.** Cross-tenant reuse, the tenant-pin reset, and `recycle.allowCrossTenantReuse` moved to proposal 0096.
- **D-PREREQS.** The proposal follows the plan's Phase 2 ordering (problem statement, **Prerequisites**). Its spec steps land after 0090's (landed) and before 0084's. Pool admission refuses `restart` until 0084 lands (D-RESTARTGATE), so `restart` pods serve sessions only after 0084. Its podspec edits serialize with R17's under rule S-4.
- **D-FIXTURE.** The cluster tiers run against a test-only Standard-level probe runtime (FIXTURE-1), because tier 5 has to observe a per-process identity, the manifest a process read at start, and an MCP call from a relaunched process.

**Watch out for.**

- Every `type: agent` sidecar Kind fixture Runtime CRD gains `command`, and every one whose image relied on its `ENV` gains the matching `env` pairs (D-ENV, D-RUNTIMEENV). Test-coverage preflight check 1 applies to the new supervisor image and the adapter's new flags.
- `tests/tier11_docs/runtime_process_lifetime_doc_reconciliation_test.go` bans phrases such as "starts a fresh runtime process for each session" and "Adapter spawns runtime binary" across `spec/` and `docs/`. New wording says "launch" and names the supervisor. Its `**Runtime not live:**` one-home check stays.
- `KeepsRuntime` is computed in `sessionserver/pool_policy_mirror.go` and read at `podclaim/claimer.go`, `podclaim/slotclaimer.go`, `podclaim/tenantpin.go`, `podsession/resolve.go`, `podsession/resume.go`, `podsession/bindrequest.go`, `podsession/bindclaim.go`, `podsession/claimconnect.go`, `sessionserver/bind_request.go`, and `sessionserver/resume_rebind.go`. The D-ACK split touches each.
- `createPod` passes no execution mode today. D-LAUNCH and the pod builder need it.
- `scrub.DefaultOps` execs `sh` and `ipcrm`, which the distroless adapter image lacks.
- A System V segment's owner can move `shm_perm.uid` with `IPC_SET`. Match on `cuid`.
- No test outside a container may call `kill(-1)`.

## Goals

- Every `type: agent` sidecar runtime process is launched by the platform after the manifest exists, with a platform-controlled environment.
- A deployer can choose a fresh runtime process at each reused occupancy-zero boundary on any isolation profile, once proposal 0084 lands (D-RESTARTGATE).
- On `restart` pods the runtime end and sweep reach the runtime container and remove agent-owned processes, IPC objects, and files before and after `cleanupCommands` run, and step 3 resets the runtime's environment at each launch. Steps 1 and 1b keep running in the adapter container on every pod.
- Sidecar `preConnect` pools serve sessions.
- The specification's signal, deadline, and exit-code statements about the sidecar runtime are true.

## Non-goals

- Cross-tenant reuse and `recycle.allowCrossTenantReuse` (proposal 0096).
- Relaunching after a crash, and starting the next runtime process before its session arrives on a session-mode pod without `preConnect`. Both stay deferred (plan §10.2, **Not yet scheduled**).
- Per-generation rebind and nonce of the intra-pod MCP listeners (proposal 0084).
- The adapter shutdown budget, the eviction signal, and whether the adapter writes `shutdown` at pod drain (the adapter shutdown and eviction proposal, then R16).
- Rendering `--runtime-ops-socket` (R17).
- A self-test of PID-namespace init signal immunity that gates admission.
- Kubernetes-native restart, image volumes, ephemeral containers, `pods/exec`, the Kata guest-agent API, or a CRI DaemonSet. Each is ruled out at the 1.27 floor or because it does not end a predecessor that does not cooperate (plan §10.6).

## Open decisions for human to make

- **Retire the sender-identification property (non-blocking).** The owner kept sender identification (`si_pid` and `si_code`) among the self-test properties that gate a `restart` pod (plan §10.3, trust model of 2026-10-02). After the third redesign no action of the supervisor depends on a signal's sender: SPEC-2 **Signals.** gives no catchable signal an action that varies with its sender, and the stop-request filter that used the property is withdrawn (D-SIGNALS). The property therefore gates `restart` pods without protecting any mechanism. Question: retire it from the self-test, the gating set, `lenny-ctl preflight supervisor`, and SPEC-4 item 8, or keep it? Recommendation: retire it, because a gate that protects nothing refuses `restart` on a runtime class where the property fails for no gain, and its test is the most runtime-class-sensitive part of the self-test. Alternative: keep it as a guard for a future signal action, at the cost of a gate with no current job. The staging keeps it, as the owner recorded, and states plainly that it gates nothing on its own account, so the proposal can land either way; retiring it later edits SPEC-4 item 8, SPEC-13, CODE-2, CODE-3, CODE-6, and TEST-1. Confidence: medium.

## Defects in the shipped tree that this proposal does not stage

- Scrub step 5 is not wired (`podscrub.go` `scrubConfig` sets no `TruncateLogs`). F-5.2.39 assigns it to the recycling follow-up proposal.
- §6.1 **Circuit-breaker for SDK-warm pools.** says that pods created while the breaker is open warm in pod-warm mode only, but in the embedded model `cmd/runtimes/preconnect-echo` calls `PreConnect` at startup whatever the breaker says, and the gateway chooses `ConfigureWorkspace` from the runtime's `capabilities.preConnect` rather than the pod's state (`pkg/gateway/podlifecycle/podsession/bindlaunch.go`). D-SDKWARM makes sidecar pods honor the breaker and does not change the embedded runtime. File it for the SDK-warm follow-up (R23).
- The step-0 cleanup metadata is not wired: `podscrub.go` `scrubConfig` sets neither `PrevProvider` nor `PrevLeaseID`, so `LENNY_PREV_CREDENTIAL_PROVIDER` and `LENNY_PREV_LEASE_ID` reach `cleanupCommands` empty. D-CLEANUP carries whatever values the adapter holds and does not populate them. File it for the recycling follow-up proposal.
