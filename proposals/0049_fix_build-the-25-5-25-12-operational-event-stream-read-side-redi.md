# Proposal: Build the §25.5 operational event-stream read side: Redis source, gateway-buffer fan-out fallback, and delivery-time plus read-time tenant filtering

- **Status:** Applied to spec (2026-07-19). Converged after 3 adversarial review rounds on re-review (2 findings fixed: the CODE-5 events⇄eventsubscription import cycle and the SPEC-4 deliveries `limit` max), following the initial 5-round read-side convergence (8 findings fixed). All three §9 decisions resolved at sign-off: platform-scoped events reach only platform-admin read callers (CODE-4); the `ListDeliveries` keyset cursor is built (CODE-5) with a §25.5 deliveries-pagination amendment (SPEC-4); and the §25.12 MCP-native subscription (T-25.12.6) plus the unified `EventStreamService` aggregator (T-25.5.6) are deferred to follow-on clusters recorded in the Integrator inbox.
- **Date:** 2026-07-19.
- **Scope:** A code-and-test build of the §25.5 operational event-stream read side hosted by `lenny-ops`, with one small §25.5 spec amendment. It adds a Redis `ops:events:stream` source to `pkg/ops/events.Service` (`XRANGE` for polling and Last-Event-ID resume, `XREAD BLOCK 0` for the live SSE tail), replaces the label-only Redis-down degradation with a cross-process fan-out to the gateway event buffer over the `lenny-gateway-pods` headless Service deduped by `eventKey`, adds delivery-time tenant filtering to the webhook path, threads a resolved caller into the SSE and polling handlers so both apply the same tenant filter, and builds the `ListDeliveries` keyset cursor end to end (a §25.5 prose amendment documenting `?cursor=`/`?limit=` on the deliveries endpoint plus the store and handler support; the illustrative `EventStreamService` interface at `spec/25_agent-operability.md:2590` already declares the cursor). Every read-source behavior other than the deliveries-pagination prose is already fully specified in §25.5, so the only spec edit is the deliveries-pagination amendment. It closes T-25.5.1, T-25.5.5, T-25.5.7, T-25.5.15, T-25.5.20, and T-25.3.5. The unified `EventStreamService` production aggregator (the single-implementor half of T-25.5.6) and the §25.12 MCP-native subscription (T-25.12.6) are out of scope and deferred to follow-on clusters recorded in the Integrator inbox; the reasons are in Non-goals and Open decisions.

This document stages the proposed code and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

The §25.5 operational event-stream read side hosted by `lenny-ops` (`pkg/ops/events.Service`) serves entirely from an in-memory `eventbuffer.EventBuffer` and never consumes the Redis `ops:events:stream` nor fetches gateway-originated events cross-process. The `Service` struct holds `buffer *eventbuffer.EventBuffer` plus a `health SourceHealth`; it holds no Redis client and no gateway fan-out client (`pkg/ops/events/service.go:71-83`). The package doc records the Redis source and the degradation matrix as outstanding (`F-25.5.1` / `F-25.5.14`, `service.go:20-26`). Three spec-mandated read-side behaviors therefore have no data source.

**1. Read source (T-25.5.1, T-25.5.7, T-25.3.5).** The spec requires the SSE handler to read Redis via `XREAD BLOCK 0` in a goroutine with per-connection `XRANGE` resume from `Last-Event-ID` (`spec/25_agent-operability.md:2685`), and polling to serve from the same Redis stream (`GET /v1/admin/events`, `spec/25_agent-operability.md:2693-2705`). Each SSE connection gets an independent read cursor against the raw stream with no consumer group (`spec/25_agent-operability.md:2687`). The webhook worker's `RedisEventSource` reads only via `XRangeN` / `XRevRangeN` from a single per-process cursor (`pkg/ops/opsservice/rediseventsource.go:29-32`); it has no `XREAD BLOCK` tail and is wired to the webhook worker alone rather than to `events.Service`. Cross-source cursor translation returns `gapDetected` plus `oldestAvailableCursor` when a cursor's `eventKey` has been evicted (`spec/25_agent-operability.md:2679`); `events.Service` encodes the source kind into every cursor today (`pkg/ops/events/cursor.go`) but has no Redis stream to translate against.

**2. Gateway-buffer fallback (T-25.5.20).** When Redis is unreachable and the gateway is up, the spec requires SSE and polling to fetch gateway-originated events from the gateway event buffer (`GET /v1/admin/events/buffer`, defined in §25.3; the SSE fallback at `spec/25_agent-operability.md:2689` and the degradation statement at `2776`), fanned over the `lenny-gateway-pods` headless Service and deduped by `eventKey`. Today `streamState()` computes an `actualSource: gateway-buffer` label and a degradation envelope over the same local buffer with no cross-process fetch (`pkg/ops/events/degradation.go:73-111`), so the Redis-to-gateway-buffer fallback is label-only. The existing `pkg/ops/gateway.Client.FanOutGet` already discovers gateway pods over the headless Service and is exercised against `/v1/admin/events/buffer` in its own test, so the fan-out primitive exists but is not wired into the read path.

**3. Delivery-time and read-time tenant filtering (T-25.5.5, T-25.5.15).** The spec requires event delivery to filter each event against the subscription's `tenantFilter`, with platform-scoped (no-label) events matched only by `tenantFilter: "*"` subscriptions, and SSE and polling applying the same filter (`spec/25_agent-operability.md:2771-2772`). Today webhook matching is type-only (`pkg/ops/opsservice/webhookloop.go:52-62`), the stored `TenantFilter` is dropped in the subscription-cache refresh mapping (`pkg/ops/opsservice/subscriptioncache.go:200-205`), and `lennytenantid` exists only as an untyped CloudEvents extension. The read handlers `HandlePoll` / `HandleStream` take `(w, r)` with no caller identity (`pkg/ops/events/service.go:336,465`), so no per-caller tenant filter is applied even though the ops schema now admits `tenant-admin` on both endpoints. T-25.5.15 records the resulting spec-versus-RBAC contradiction on the read path (`TEST-GAPS.md:9482`) as the read-side twin of the delivery-time gap T-25.5.5 (`TEST-GAPS.md:9427`).

The findings that record these gaps all point at the same unbuilt read source. T-25.5.1 (`TEST-GAPS.md:9410`, High) names the Redis source and the degradation matrix; T-25.3.5 (`TEST-GAPS.md:9153`, Medium) and T-25.5.20 (`TEST-GAPS.md:9502`, Medium) name the cross-process fan-out; T-25.5.7 (`TEST-GAPS.md:9443`, Medium) names the evicted-Redis-stream gap recovery; T-25.5.5 (`TEST-GAPS.md:9427`, High) and T-25.5.15 (`TEST-GAPS.md:9482`, Medium) name the tenant filter. Each carries a needs-human note asking whether the read source should be built once through the proposal pipeline, which is what this proposal does.

## 2. Decisions

- **The read source lives in `events.Service` rather than the webhook worker's `RedisEventSource`.** `RedisEventSource` is a single per-process shared cursor for webhook fan-out; the SSE side needs a per-connection independent cursor with no consumer group (`spec/25_agent-operability.md:2687`). A distinct low-level Redis stream reader owned by `events.Service` exposes an `XRANGE` read for polling and SSE backlog resume and an `XREAD BLOCK 0` tail for the live SSE stream. It reuses the already-imported go-redis client and adds no dependency.
- **The in-memory buffer stays as the canonical source of `lenny-ops`-originated events, and Redis becomes the primary source of the merged cross-replica view.** During a dual Redis and gateway outage the local buffer is the only observable source for `lenny-ops`-originated events, while gateway-originated events return `503` (`spec/25_agent-operability.md:2782`). The buffer is reclassified from the sole source to the local-origin source; it is not removed.
- **The Redis-down fallback is a cross-process fetch.** `events.Service` fans `GET /v1/admin/events/buffer` over the `lenny-gateway-pods` headless Service using the existing `pkg/ops/gateway.Client.FanOutGet`, merges the per-replica pages, and dedups by `eventKey` (`spec/25_agent-operability.md:759` in §25.3, cross-referenced by the dual-source dedup statement at `2784`). `SourceHealth` drives the actual data-path source selection rather than only the degradation label.
- **Cross-source cursor translation is by `eventKey` scan with `gapDetected` and `oldestAvailableCursor` on a miss.** The opaque cursor already encodes `source_kind` (`redis` / `buffer` / `mixed`) through `pkg/ops/events/cursor.go`. A mid-connection SSE source switch tracks the last delivered `eventKey` and locates the continuation point in the new source, emitting a `:gap` comment when no event has a greater-or-equal `eventKey`. This reuses the existing cursor and gap machinery rather than a parallel cursor.
- **Delivery-time tenant filtering adds a tenant dimension to the delivery path, sourced from the `lennytenantid` CloudEvents extension.** `WebhookEvent` gains a `TenantID` parsed from `Extensions[lennytenantid]`; `WebhookSubscription` gains a `TenantFilter` copied in `subscriptioncache.refresh` (which currently drops it); `webhookloop.matches` gates on tenant as well as type, where a no-label platform-scoped event matches only `tenantFilter: "*"`. This reuses the stored `TenantFilter` column rather than a second tenant model.
- **The read handlers thread an explicit caller, resolved in `opsserver`.** The resolution mirrors the shipped `subscriptionCaller(r)` (`pkg/ops/opsserver/event_subscriptions.go:53-72`). A tenant-admin sees only events labeled with its tenant; platform-scoped no-label events are delivered only to a platform-admin caller (`spec/25_agent-operability.md:2772`). Delivery-time tenant filtering on the read path is a silent drop rather than a `403`: `SUBSCRIPTION_TENANT_FORBIDDEN` is a create-only error (`spec/25_agent-operability.md:2771`) and is absent from the §25.5 read-endpoint error table.
- **The caller threads through the concrete handlers rather than the `EventStreamService` interface.** The interface at `pkg/ops/events/interface.go:26-35` is an illustrative documentation surface with no production implementor, and it already diverges from the shipped concrete types on method names and return types. Reconciling the caller alone would leave it self-inconsistent. The caller is resolved at the `opsserver` HTTP boundary and passed into `events.Service`; where the read path needs identity, it flows on the request-scoped `context.Context`. The interface and its reflection test stay valid and unchanged.
- **The read-source behaviors need no spec change and are a pure build.** `XREAD BLOCK`, the gateway-buffer fan-out fallback, cross-source cursor translation, and the dual-down `503` are already fully specified (`spec/25_agent-operability.md:2685` for `XREAD BLOCK`, `2689` for the SSE fallback, `2679` for cursor translation, and `2782` for the dual-down `503`). The tenant-filter rule is already normative prose (`spec/25_agent-operability.md:2771-2772`), so threading a caller and enforcing that predicate is code.
- **Platform-scoped events reach only a platform-admin caller (settled).** The spec's "if the caller has permission for platform-scoped events (typically `platform-admin` only)" (`spec/25_agent-operability.md:2772`) is pinned to platform-admin-only: a tenant-admin read caller sees only events labeled with its own tenant, and no-label platform-scoped events are dropped for it. This fails closed on a tenant-isolation boundary and matches the §13 posture. The `Caller` model already exposes `PlatformAdmin`, so the predicate is enforceable against the unchanged spec (no named tenant-admin platform-event capability is introduced).
- **`ListDeliveries` gains a real keyset cursor, and §25.5 documents deliveries pagination (settled).** The illustrative `EventStreamService` interface already declares `ListDeliveries(ctx, subID, cursor string, limit int)` (`spec/25_agent-operability.md:2590`), but the deliveries endpoint row (`spec/25_agent-operability.md:2575`) documents no pagination params and the shipped store is limit-only (`pkg/ops/eventsubscription/pgstore/pgstore.go:169-199`). Rather than reconcile the interface down to limit-only, this proposal builds the cursor: a keyset over the delivery primary key `id` (`cursorKind: "pk"`, `ORDER BY id DESC`), the canonical §25.2 pagination envelope assembled at the `opsserver` handler boundary, and a §25.5 prose amendment (SPEC-4) documenting `?cursor=`/`?limit=` on `GET /v1/admin/event-subscriptions/{id}/deliveries`, mirroring the pagination the sibling `GET /v1/admin/events` endpoint already carries. This makes the shipped endpoint match the already-cursored interface rather than leaving a standing contradiction.

## 3. The read-source data path after the change

`events.Service` selects its data source from `SourceHealth`:

- **Redis up.** The primary source is the Redis `ops:events:stream`. Polling reads a page via `XRANGE` from the cursor's stream position; SSE resumes the backlog via `XRANGE` from `Last-Event-ID`, then tails live via `XREAD BLOCK 0` on a per-connection cursor with no consumer group. Each poll and SSE frame carries the full CloudEvents envelope. The cursor's `cursorKind` reports `redis`.
- **Redis down, gateway up (case 1).** The primary source is the gateway event buffer. Polling and the SSE fallback serve pages fetched by `FanOutGet('/v1/admin/events/buffer')` across the `lenny-gateway-pods` replicas, merged and deduped by `eventKey`. The response carries the `EVENT_STREAM_DEGRADED` envelope (`actualSource: gateway-buffer`). On SSE the handler polls the fan-out every 2 seconds while the connection stays open, and switches back to `XREAD` transparently when `SourceHealth` reports Redis recovered, emitting a `:degradation {"level":"healthy"}` comment. Across the switch the handler tracks the last delivered `eventKey` and emits a `:gap` comment when the new source has no greater-or-equal `eventKey`.
- **Redis down, gateway down (case 4).** Polling returns `503 EVENT_STREAM_UNAVAILABLE` for gateway-originated events. SSE keeps serving `lenny-ops`-originated events from the local ring buffer with the `:degradation {"actualSource":"lenny-ops-local-buffer","unavailableFields":["gateway-events"]}` comment. The per-replica local-buffer serving behavior is preserved. When Redis recovers, `lenny-ops` flushes the events it buffered locally during the outage to the Redis `ops:events:stream` on a best-effort basis, with `eventKey` deduplication preventing duplicate consumer-side delivery (`spec/25_agent-operability.md:2784`). The flush is a property of the replica and fires whether or not an SSE connection is open across recovery, so a consumer that connects only after Redis is back still observes the buffered events. This recovery flush does not exist in the current code and is built by CODE-2 through a replica-level edge detector, scoped to Redis recovery. On gateway-only recovery the buffered `lenny-ops` events remain the per-replica limitation, because the gateway event buffer exposes no ingest path `lenny-ops` could write to (see CODE-2 step 5).

`streamState()` continues to compute the degradation envelope, and its `actualSource` now selects the actual data path rather than only labeling a response served from the local buffer.

## 4. Proposed changes

### CODE-1. Add the Redis `ops:events:stream` source to `events.Service`

**Target:** `pkg/ops/events/service.go` (`:71-83` Service struct, `:336-432` `HandlePoll` / `pollPage`, `:465-532` `HandleStream`); new `pkg/ops/events/redissource.go`; `pkg/ops/events/cursor.go` (source-kind cursor).

**Rationale:** The spec requires the SSE read side to consume Redis via `XREAD BLOCK 0` with per-connection `XRANGE` resume (`spec/25_agent-operability.md:2685`) and polling to serve from the Redis stream (`GET /v1/admin/events`, `spec/25_agent-operability.md:2693-2705`). `events.Service` holds no Redis client (`pkg/ops/events/service.go:71-83`). The per-connection independent cursor (`spec/25_agent-operability.md:2687`) rules out reusing the webhook worker's shared-cursor `RedisEventSource`.

**Change (staged description).**

1. Add a `redisSource` type in the new file, wrapping the go-redis client already constructed in `cmd/lenny-ops`. It exposes `ReadRange(ctx, sinceID, count)` via `XRANGE` for polling and SSE backlog resume from `Last-Event-ID`, and `Tail(ctx, lastID, out chan)` via `XREAD BLOCK 0` for the live SSE tail. Each SSE connection gets its own cursor; no consumer group is created.
2. Decode the single event field of each stream entry back into a `BufferedEvent`, matching the XADD encoding written by `pkg/gateway/eventbuffer`'s stream emitter, so the polling envelope and SSE frame are identical to the buffer-served path.
3. Add `redis *redisSource` to the `Service` struct and select it as the primary source when `SourceHealth.RedisAvailable()`.
4. In `HandlePoll` / `pollPage` and `HandleStream`, resolve the incoming cursor's `source_kind`: a `redis` cursor reads Redis by stream ID; a `buffer` cursor is translated by scanning for the matching `eventKey`, returning `gapDetected` plus `oldestAvailableCursor` on a miss. Keep the local buffer as the `lenny-ops`-origin source.

Reuse the go-redis client already imported; add no dependency. Run `gofumpt` and `goimports`. Carry a `// spec: 25.5` tie on the source logic and a `// diagnosis:` comment on every tier-2-and-up test.

### CODE-2. Wire the Redis-down fallback and the mid-connection source switch

**Target:** `pkg/ops/events/service.go` (Service struct plus poll and stream data path); `pkg/ops/events/degradation.go` (`:73-111` `streamState`, `:118-122` dual-down `503`); `pkg/ops/gateway/client.go` (`FanOutGet`, present) and `pkg/ops/gateway/discovery.go`; `cmd/lenny-ops/events_wiring.go` (`opsstream.New` construction at `:49` inside `buildEventStreamAndWebhooks`; a post-construction setter on `events.Service` invoked from `buildGatewayLink` after `:167` injects the gateway fan-out client `w.gwClient`, which is still nil at the `:49` construction site; the live `sourceHealthProbe` is already constructed and wired here at `:44-48` and run at `:172-173`); `cmd/lenny-ops/sourcehealth.go` (`:50-69` `run`, extended with the replica-level down-to-up edge detector that invokes the recovery flush).

**Rationale:** `streamState()` attaches an `actualSource` label over the same local buffer with no cross-process fetch (`pkg/ops/events/degradation.go:73-111`), so the transparent Redis-to-gateway-buffer fallback is label-only (T-25.5.20, `TEST-GAPS.md:9502`). The spec requires a fan-out to the gateway buffer deduped by `eventKey` (`spec/25_agent-operability.md:2689` for the SSE fallback and `759` in §25.3 for the cross-replica `eventKey` dedup), and `pkg/ops/gateway.Client.FanOutGet` already discovers gateway pods over the `lenny-gateway-pods` headless Service.

**Change (staged description).**

1. Inject the gateway fan-out client (`pkg/ops/gateway.Client`) into `events.Service` through a post-construction setter. At the `opsstream.New` construction site (`cmd/lenny-ops/events_wiring.go:49`, inside `buildEventStreamAndWebhooks`) `w.gwClient` is still nil: it is assigned only at `:167` inside `buildGatewayLink`, which `wiring.go` calls at `:56` after `buildEventStreamAndWebhooks` at `:54`. Call the setter from `buildGatewayLink` immediately after the `:167` assignment, mirroring how the source-health probe receives `w.gwClient` as a `run` argument at `:172-173` inside the same function.
2. When `SourceHealth` reports Redis down and gateway up (case 1), serve poll and SSE-fallback pages from `FanOutGet('/v1/admin/events/buffer')`, merging the per-replica pages by `eventKey` (drop duplicates, secondary content-hash check) and honoring the same filter. Keep the case-1 `EVENT_STREAM_DEGRADED` envelope on the response.
3. On SSE, poll the fan-out every 2 seconds while the connection stays open; when `SourceHealth` flips back, switch to `XREAD` and emit `:degradation {"level":"healthy"}`. Track the last delivered `eventKey` across the switch; on a miss in the new source emit the `:gap` comment (reuse the existing gap-write path).
4. Keep the dual-down (case 4) path: poll returns `503 EVENT_STREAM_UNAVAILABLE` (`pkg/ops/events/degradation.go:118-122`), and SSE keeps serving `lenny-ops`-origin buffer events with the `actualSource: lenny-ops-local-buffer` / `unavailableFields: [gateway-events]` degradation comment.
5. Build the best-effort recovery flush (`spec/25_agent-operability.md:2784`), which does not exist in the current code, scoped to Redis recovery. A replica-level edge detector, independent of any open read connection, drives the flush: extend the `sourceHealthProbe.run` refresh loop (`cmd/lenny-ops/sourcehealth.go:50-69`, a background ticker bounded by `w.ctx`) to remember the previous Redis reachability and, on a down-to-up edge, invoke a flush callback on `events.Service` exactly once. On that edge, re-emit the `lenny-ops`-originated events buffered in the per-replica local ring during the outage to the Redis `ops:events:stream` (the sole shared destination `lenny-ops` can write, via the existing `redisFanOutEmitter` path at `cmd/lenny-ops/events_wiring.go:52`). Host the flush in this replica-level loop rather than the per-connection SSE source switch of step 3, so the flush fires on recovery even when no SSE connection is open across the transition. A poll is a single stateless request, and an SSE connection that opens after recovery begins already in the healthy state, so neither read handler observes a down-to-up edge. The `sourceHealthProbe` stores only `redisUp` / `gatewayUp` `atomic.Bool` values and fires no transition callback today (`cmd/lenny-ops/sourcehealth.go:21-40`), so the edge detector is new work. Dedup by `eventKey` so a consumer that already saw an event does not receive it twice. The flush is best-effort: a re-emit failure is logged and does not block serving. The spec's line-2784 mention of flushing to the gateway buffer on gateway-only recovery is not built here. The gateway event buffer is exposed to `lenny-ops` only as the read-only `GET /v1/admin/events/buffer` endpoint (`pkg/gateway/externalapi/admin/routes.go:190`, query-only per `pkg/gateway/externalapi/admin/eventbuffer.go:16-21`) with no ingest route, so `lenny-ops` cannot push into another process's in-memory ring, and building such a write path would require a new gateway ingest endpoint and would change the §25.3 gateway emission path this proposal lists as a non-goal. On gateway-only recovery (Redis still down) the buffered `lenny-ops` events remain the documented per-replica limitation until Redis recovers. Raising the gateway-buffer flush as a real mechanism is a §25.3 spec gap for a separate proposal through the pipeline.
6. Consume the live `SourceHealth` signal `streamState()` already exposes rather than replacing a static probe: the live `sourceHealthProbe` already exists (`cmd/lenny-ops/sourcehealth.go:21-69`), is set on the `Service` via `streamOpts.SourceHealth` at `cmd/lenny-ops/events_wiring.go:46-47`, is run against Redis (`PING`) and the gateway (version `GET`) by the background loop at `events_wiring.go:172-173`, and already feeds `streamState()` (`pkg/ops/events/degradation.go:77-78`). The remaining work is making `HandlePoll` / `HandleStream` select the data source (Redis stream, gateway-buffer fan-out, or local buffer) from that signal, because the read path currently serves the local ring buffer regardless of the `actualSource` `streamState()` computes. The recovery flush of step 5 consumes the same probe through the separate replica-level edge detector rather than through these per-request handlers, because neither handler observes a down-to-up edge on its own.

Carry `// spec: 25.5` ties. Put a timeout on every outbound fan-out call.

### CODE-3. Add delivery-time tenant filtering to the webhook path

**Target:** `pkg/ops/opsservice/webhookloop.go` (`:21-62` `WebhookEvent`, `WebhookSubscription`, `matches`; `:225-238` `Tick` delivery loop); `pkg/ops/opsservice/subscriptioncache.go` (`:200-205` refresh mapping); `pkg/ops/opsservice/rediseventsource.go` (populate `WebhookEvent.TenantID`).

**Rationale:** The spec requires event delivery to filter each event against the subscription's `tenantFilter`, with no-label events matched only by `tenantFilter: "*"` (`spec/25_agent-operability.md:2771`). Today matching is type-only (`pkg/ops/opsservice/webhookloop.go:52-62`), the stored `TenantFilter` is dropped in the cache refresh (`pkg/ops/opsservice/subscriptioncache.go:200-205`), and `lennytenantid` is only an untyped extension. This is the delivery-side half of T-25.5.5.

**Change (staged description).**

1. Add `TenantID string` to `WebhookEvent`, parsed from the CloudEvents `Extensions["lennytenantid"]` when `RedisEventSource` decodes each entry. An empty value denotes a platform-scoped event.
2. Add `TenantFilter string` to `WebhookSubscription` and copy `r.TenantFilter` in `SubscriptionCache.refresh` alongside `ID`, `CallbackURL`, `Types`, and `Generation`.
3. Extend `WebhookSubscription.matches` to gate on tenant as well as type: an empty event `TenantID` (platform-scoped) matches only `TenantFilter == "*"`; a labeled event matches when `TenantFilter == "*"` or `TenantFilter == event.TenantID`.
4. Apply the tenant predicate in the `Tick` delivery loop next to `matches(ev.Type)`.

Carry `// spec: 25.5` ties.

### CODE-4. Thread the caller into the read handlers and enforce the tenant filter on SSE and polling

**Target:** `pkg/ops/events/service.go` (`:336` `HandlePoll`, `:465` `HandleStream`, `:273` `parseFilter`); `pkg/ops/opsserver/eventstream.go` (`:13-14` route registration); `pkg/ops/opsserver/event_subscriptions.go` (`:53-72` `subscriptionCaller`, reused).

**Rationale:** `HandlePoll` / `HandleStream` take `(w, r)` and resolve no caller (`pkg/ops/events/service.go:336,465`), so no tenant filter is applied despite the schema admitting `tenant-admin`. The spec requires SSE and polling to apply the same tenant filter as delivery (`spec/25_agent-operability.md:2772`). This is the read-side half of T-25.5.5 and the resolution of the T-25.5.15 read-path contradiction. The caller-driven filter is already normative prose, so no spec edit is needed to license it.

**Change (staged description).**

1. Resolve the caller at the `opsserver` route boundary with the existing `subscriptionCaller(r)` (`pkg/ops/opsserver/event_subscriptions.go:53-72`) at `eventstream.go` registration, and pass a resolved tenant scope (`Subject`, `TenantID`, `PlatformAdmin`) into the read path. Where the path needs the identity to flow through `events.Service`, carry it on the request-scoped `context.Context` so the pinned handler and interface signatures stay valid.
2. In the read path, intersect the served events with the caller's tenant: a platform-admin sees all events; a tenant-admin sees only events whose `lennytenantid` equals its tenant, and no-label platform-scoped events are dropped for a tenant-admin (`spec/25_agent-operability.md:2772`).
3. Apply the same predicate to the SSE backlog replay, the live delivery, and the poll page. Add it as a post-query authorization filter rather than a field on the caller-supplied URL `EventFilter`.
4. The read-path tenant filter is a silent drop. `SUBSCRIPTION_TENANT_FORBIDDEN` stays a create-only error and is not returned by the read endpoints.

Carry `// spec: 25.5` ties.

### SPEC-4. Document deliveries-endpoint pagination in §25.5

**Target:** `spec/25_agent-operability.md`, the event-subscription endpoints table and the prose immediately after it (the table row for `GET /v1/admin/event-subscriptions/{id}/deliveries` at `:2575`).

**Rationale:** The illustrative `EventStreamService` interface already declares `ListDeliveries(ctx, subID, cursor string, limit int)` (`spec/25_agent-operability.md:2590`), but the endpoints table documents no pagination params for the deliveries endpoint and the shipped store is limit-only (`pkg/ops/eventsubscription/pgstore/pgstore.go:169-199`), so the endpoint contract and the interface disagree. ## 5. Non-goals

Only the single-implementor question of T-25.5.6 is deferred; its `ListDeliveries` cursor half is built here by CODE-5 and SPEC-4. ## 9. Decisions settled on review (2026-07-19)

The three open decisions this proposal raised were settled on human review before sign-off. They are recorded here and reflected in Sections 2, 4, and 5.

### Platform-scoped event delivery predicate — settled: platform-admin-only

A tenant-scoped read caller sees only events labeled with its own tenant; no-label platform-scoped events are delivered only to a platform-admin caller. This is the conservative reading of `spec/25_agent-operability.md:2772` ("typically `platform-admin` only"), fails closed on a tenant-isolation boundary, and is enforced against the unchanged spec through the `Caller.PlatformAdmin` flag (CODE-4). No named tenant-admin platform-event capability is introduced.

### `ListDeliveries` cursor — settled: build the keyset cursor and amend the spec

The cursor is built end to end (CODE-5) and §25.5 is amended to document deliveries pagination (SPEC-4), rather than reconciling the interface down to limit-only. This makes the shipped endpoint match the already-cursored §25.5 interface declaration (`spec/25_agent-operability.md:2590`) instead of leaving a standing contradiction.

### §25.12 MCP-native subscription — settled: defer to a follow-on cluster

The §25.12 MCP-native subscription is taken as a separate focused change-proposal in *new* mode that stages a §25.12 spec amendment ratifying the transport (MCP Streamable HTTP versus a dedicated SSE endpoint versus a long-lived POST), the `notifications/subscribe` param structure, and the `notifications/message` payload envelope before the management-server restructure. It is sequenced after this proposal lands the read source it consumes. The deferral is recorded in the Integrator inbox (finding T-25.12.6) for a new cluster.
