### [spec.1.fix-design-G1.1]
DECISION: SPEC-1 rule 5 defines acting as every covered request that does not only retrieve the session's state or content, and names derive and replay as acts. BECAUSE a complement cannot go stale as routes are added, and derive and replay retrieve the source but must stay acts (summary decision on derived-session ownership). ALTERNATIVES: a closed list of acts, the current text, which omits upload, finalize, start, extend-retention, and memory write and delete; a closed list of reads, which drifts the same way; classification by HTTP method, which MCP tools do not have; the reviewer's complement plus an "including ..." list, which restates the list.
DECISION: SPEC-1 rule 4 drops "in its tenant" ("reads another user's session when ..."). It does not add a cross-tenant clause. BECAUSE tenant resolution fixes which tenant a request reads, and the "Access other tenants' data" row governs cross-tenant access, so rule 4 decides only the owner dimension. A cross-tenant clause would push an implementor toward a row.TenantID check in SessionAccessible, which duplicates resolveTenant and RLS. ALTERNATIVES: the reviewer's "or in any tenant when its role grants 'Access other tenants' data'" (adds text and a second tenant mechanism).
FACT: the only cross-tenant session read in code is handleList's platform-admin `?tenant=` override. Every {id} route reads with resolveTenant, which returns the principal's tenant first. SessionAccessible therefore never sees a row from a foreign tenant on an {id} route. EVIDENCE: pkg/gateway/sessionserver/session_read.go:49-55; pkg/gateway/sessionserver/request_identity.go:56-72

The REST route and the MCP tool share one gate, so SPEC-1 rule 6 has to exempt both. EVIDENCE: pkg/gateway/mcpfabric/mcptools/client_tools.go:113; pkg/gateway/sessionserver/route_table.go:90; pkg/gateway/sessionserver/session_subresources.go:131-137
