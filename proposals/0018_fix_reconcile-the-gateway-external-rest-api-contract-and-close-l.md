## 1. Problem

The gateway external REST API carries 26 findings from a converged adversarial review. They divide by where the fix lands: a set that reconciles the contract surfaces (the §15.1 catalog, the served `openapi.json`, the §16.7 audit catalog, the §7.3 retry policy, and the docs) and a set that closes localized implementation gaps in `pkg/gateway` against a correct spec.

### 1.1 Contract gaps

- **W1 (revised, medium): the served `openapi.json` is incomplete.** `pkg/gateway/openapi/openapi.json` carries roughly 73 admin path templates while `pkg/gateway/admin/*.go` registers about 113, so roughly 40 mux-registered admin templates are absent from the document. Every named example (`/v1/admin/preflight`, `/v1/admin/operations`, `/v1/admin/platform/config`, `/v1/admin/ca-rotation/*`, `tenants/{id}/force-delete`, `tenants/{id}/credential-rekey`, `pools/{name}/upgrade/*`, `audit-events/summary`) has a grep-count of zero in the document. The guard `TestDocumentMatchesEndpoints` (`pkg/gateway/openapi/openapi_test.go:97-181`) iterates a hardcoded `expected[]` allowlist for presence and never enumerates the live mux, so the §15.1:923 requirement that every RBAC admin endpoint appear in the document (from which the `/mcp/management` tool inventory is generated) is under-covered. The absent admin operations get no generated MCP tool, no scope entry, and no SDK surface.
- **W2 (revised, medium): five error codes are absent from the §15.1 catalog.** `SESSION_CREATION_FAILED` (`pkg/gateway/sessionserver/start.go:209`), `STARTING_FAILED` (`start.go:698`), `KMS_SIGNING_UNAVAILABLE` (`pkg/auth/jwt/breakersigner.go:13`), `CONFIRMATION_REQUIRED` (`pkg/gateway/admin/migrations.go:80`), and `SLOT_ID_REQUIRED` (`pkg/gateway/executor/pod.go:28`) are emitted or named but absent as rows from the §15.1 error-code catalog table (header at `spec/15_external-api-surface.md:974`, rows ending before line 1101) and from the `pkg/gateway/errorclassify/errorclassify.go` table, so their `(category, retryable)` survives only on the unknown-code fallback or hardcoded per-call-site values rather than being catalog-governed.
- **J1 (revised, low): `GET /v1/sessions/{id}/events` has no §15.1 endpoint row.** The SSE stream is served (`pkg/gateway/sessionserver/events.go:59`, route at `sessionserver.go:1873`) and present in `openapi.json` (lines 904-915), but it has no dedicated §15.1 REST endpoint row. It appears only in the line-660 attach-precondition table. The `eventSortField` constant comment (`events.go:22-23`) cites `§15.1 line 1228` as listing this endpoint, where line 1228 actually lists `GET /v1/metering/events`.
- **F-CS6 (revised, low): a setup-command failure returns a retryable code.** A deterministic setup-script failure returns the retryable `503 SESSION_CREATION_FAILED`/`STARTING_FAILED` fallback with `Retry-After: 5` and `details.reason=setup_command_failed` (`start.go:118-130`), while §7.3 (`spec/07_session-lifecycle.md:387-389`) lists `setup_command_failed` under `retryPolicy.nonRetryableFailures`. The wire `retryable: true` tells a client to retry a deterministic failure that will fail identically.
- **F-EL3 (revised, spec enhancement, low): the URL-mode elicitation drop is not audited.** A `DOMAIN_NOT_ALLOWLISTED` URL-mode elicitation drop (`pkg/gateway/mcptools/elicitation.go:165-203`) emits the `lenny_elicitation_dropped_total{reason="domain_not_allowlisted"}` metric and a tool error but writes no §16.7 audit row, because the §16.7 catalog defines no `elicitation.url_mode_domain_rejected` event. The code conforms to spec; §9.2 mandates only the drop, the metric, and the tool error.
- **Nits and journey notes.** W4 (the split retry-hint convention: admin errors carry `suggestedRetryAfter`, session errors carry only `Retry-After`), W5 (snake-case `{user_id}` versus camelCase `{credId}`/`{tenantId}` among the documented sub-resource params), W6 (`POST /v1/sessions/start` in the `{id}` slot; `DELETE /v1/sessions/{id}` returning 200+body versus `DELETE .../memory/{memoryId}` returning 204; the legal-hold singular `POST` versus plural `GET` at `pkg/gateway/admin/tenants.go:752,756`; `TARGET_NOT_READY` as `TRANSIENT` at 409, `errorclassify.go:438`), and the journey notes J2, J5, J6, J8 are graded by the review as nits, by-design, or documented tradeoffs.

### 1.2 Implementation gaps (spec correct, fixable now)

- **F-IA1 (upheld, HIGH): tool-approval await is replica-local.** The tool-approval await blocks on a process-local channel, timeout, and `ctx.Done` (`pkg/gateway/sessionserver/toolapproval.go:112-126`) with no store-poll fallback, while the sibling elicitation await already polls the Postgres-backed shared interaction store (`pkg/gateway/mcptools/mcptools.go:2152-2169`). On the supported multi-replica topology, an approve POSTed to a non-coordinator replica updates the shared store but never wakes the blocked tool call until `approval_timeout`.
- **F-CS1 (upheld, medium): archive-limit violations are mis-coded.** `UPLOAD_ARCHIVE_LIMIT_EXCEEDED` is registered 413/PERMANENT (`errorclassify.go:360`) but emitted by no handler. An over-limit or decompression-bomb archive raises `*upload.ValidationError` from `archive.Extract`, which propagates through `Binder.Prepare` to `writePodClaimError` (`start.go:78-187`), whose switch has no `*upload.ValidationError` case, so it falls to the retryable `503 SESSION_CREATION_FAILED` default and conforming clients retry indefinitely.
- **F-MS4 (revised, medium): inbox-unavailable has two wire contracts.** Inbox-unavailable returns `HTTP 503 INBOX_UNAVAILABLE` on REST (`pkg/gateway/sessionserver/messages.go:465,480`) but a `200` with `status:"error", reason:"inbox_unavailable"` receipt on MCP `send_message` (`mcptools.go:996`), violating the §15.2.1 parity contract. §15.4 (`spec/15_external-api-surface.md:1723,1735,1743`) mandates a `delivery_receipt` for every `send_message` and defines `inbox_unavailable` strictly as a receipt `status`/`reason`. `INBOX_UNAVAILABLE` is in neither the §15.1 catalog nor `openapi.json`, so the REST 503 envelope is the non-conforming side.
- **F-MS6 (revised, medium): the injection gate fails open on a transient store error from either backing store.** The gate rejects only when `ResolveForTenant` returns `err==nil && !InjectionSupported()` (`messages.go:280`), and `ResolveForTenant` reads two stores: the runtime registry (`runtimestore.Resolve`) and the per-tenant capability override store (`overrides.Get`). The two stores fail open through different mechanisms. On the registry path, `runtimestore`'s `pgstore.Get` maps `pgx.ErrNoRows` to `ErrNotFound` but returns any other (transient) error raw, which `runtimestore.Resolve` propagates unchanged (`merge.go:18-19`); `ResolveForTenant` then returns that registry error, so the gate's `err==nil` guard short-circuits and admits injection. On the override path, which is the security-relevant F-5.1.20 surface (a tenant narrowing `injection.supported` to false on this runtime), the failure is worse: `runtimecapoverride`'s `pgstore.Get` maps `pgx.ErrNoRows` to not-found and returns any other (transient) error raw (`runtimecapoverride/pgstore/pgstore.go:45-58`), but `ResolveForTenant` then deliberately swallows that error and returns `(un-overlaid base runtime, nil)` (`runtimecapoverride.go:125-128`, comment at `:110-114`). The gate sees `err==nil` and evaluates `!InjectionSupported()` against the base runtime, which reports injection supported, so a transient override-store error skips the `INJECTION_REJECTED` block and admits injection against §5.1's fail-closed posture for the exact tenant-narrowing case the gate exists to enforce.
- **W3 (revised, low): session and admin classify the same code differently.** The session `writeError` uses code-only `errorclassify.Classify` (unknown code maps to `TRANSIENT`, retryable; `sessionserver.go:3362`) while admin uses the status-aware `ClassifyStatus` (`tenants.go:2183`). For an unmapped non-5xx code the two surfaces disagree.
- **F-CS2 (upheld, medium): `pool` is accepted, echoed, and ignored for scheduling.** The create-body `pool` field is accepted and echoed (`row.Pool = req.Pool`, `pkg/gateway/sessionserver/envelope.go:70`) but `ResolvePool` (`pkg/gateway/podsession/resolve.go:192`) takes no pool parameter and every call site passes only `RuntimeRef` and `IsolationProfile`, so the client-supplied pool is dropped from scheduling with no signal. §7.1 (`spec/07_session-lifecycle.md:6,18,19`) and §14.1 (`spec/14_workspace-plan-schema.md:311`) document `pool` as a scheduling selector.
- **F-MS5 (upheld, medium): inbound message content is a bare string on both REST and MCP.** `MessagePayload.Content` is a bare `string` (`messages.go:125`) and the MCP `lenny/send_message` tool declares its `message` argument as a bare string in both its served `InputSchema` (`mcptools.go:857`) and its parsing struct (`mcptools.go:869`), where §15.4 `MessageEnvelope.input` is `OutputPart[]` (`spec/15_external-api-surface.md:1688`), so multipart, image, or file-reference input is unrepresentable on either surface. §15.4 binds `MessageEnvelope` across "the stdin binary protocol, platform MCP server tools, and all external APIs" (`spec/15_external-api-surface.md:1672`), so the two surfaces are parallel representations of one contract.
- **F-CS5 (revised, medium, contract+impl): `WorkspacePlan` is validated by hand-rolled Go.** `WorkspacePlan` is validated by `workspaceplan.Parse` (`start.go:763-766`) rather than against the published JSON Schema §15.1 prescribes. Three of the six canonical example fixtures (`invalid-setuid`, `invalid-unknown-field`, `unknown-source-type`) reach the parser only through inline JSON literals rather than the shared `schemas/examples/` fixture files, so a fixture file could drift from the parser's inline copy uncaught.
- **F-CS4 (revised, nit): `metadata` keys are not emptiness-checked** (`sessionserver.go:2450`). The keys round-trip and no spec requires non-empty keys; this is a hardening nit.

### 1.3 Subsystem-gated deferrals

Four high-confidence findings are confirmed deferrals on subsystems v1 does not build, classified as deferred sub-parts of the closed F-7.2.4/F-7.2.5 inbox and DLQ machinery. F-MS3 (the `RedisInbox` exposes only `Enqueue`/`Drain`/`Len`/`Expire` with no `LREM`/ACK, so a `queued` receipt never redelivers to a running runtime; gated on the unbuilt §4.7 `ready_for_input` model), F-EL1 (the dispatcher leaves `forwardedContentFor` nil, so the §9.2 forward-hop digest comparison never runs; tracked F-9.2.1, DEFERRED/NEEDS-OPERATOR), and F-MS1/F-MS2 (`delivery: immediate` validated then ignored; mid-tool-call delivery versus queued; both gated on the unbuilt §4.7/§9.2 models). This proposal reconciles their tracking status and the contract surfaces they touch in §7. It stages no redelivery or ACK loop, no forward-hop wire mechanism, no atomic resume-and-deliver, and no readiness model.

## 2. Decisions

- **Honor the review's where-the-fix-lands split.** Contract findings (W1, W2, J1, F-CS6, F-EL3, and the W4/W5/W6/J2/J5/J6/J8 nits) stage spec, `openapi.json`, and doc edits. Implementation findings (F-IA1, F-CS1, F-MS4, F-MS6, W3, F-CS2, F-MS5, F-CS5, F-CS4) stage `pkg/gateway` code and test changes. `tmp/gateway-rest-api-review.md` is the scope source of truth.
- **Build no deferred subsystem.** F-MS3, F-EL1, F-MS1, and F-MS2 are gated on the unbuilt §4.7 `ready_for_input` model and the §9.2 per-hop re-emission wire. This proposal reconciles their tracking status and the contract surfaces they touch; it stages no redelivery or ACK loop, no forward-hop wire mechanism, no atomic resume-and-deliver, and no readiness model.
- **Treat F-EL3 as a spec enhancement.** §9.2 mandates only the drop, the metric, and the tool error for a URL-mode `DOMAIN_NOT_ALLOWLISTED` block, and the audit event was deliberately uncataloged. Adding a §16.7 `elicitation.url_mode_domain_rejected` audit event plus a localized audit write at the existing drop point (`elicitation.go:165-203`) is a catalog edit plus a localized code change rather than a subsystem build.
- **Align F-MS4 by changing the REST side to the MCP receipt form.** §15.4 mandates that every `send_message` returns a `delivery_receipt` and defines `inbox_unavailable` strictly as a receipt `status:"error"`/`reason` value. `INBOX_UNAVAILABLE` is absent from both the §15.1 catalog and `openapi.json`, so the REST 503 envelope is the non-conforming side and the MCP receipt is the spec-conformant form.
- **Fix F-IA1 by reusing the sibling store-poll pattern.** The elicitation await already polls the Postgres-backed shared interaction store, which is cross-replica through `interactionpg` while the `toolapproval.Registry` is per-process. The tool-approval await gets the same store-poll fallback rather than a new coordinator-pinning mechanism.
- **Add the W2 codes to the catalog and the classifier.** Add `SESSION_CREATION_FAILED`, `STARTING_FAILED`, `RESUME_FAILED`, `KMS_SIGNING_UNAVAILABLE`, and `CONFIRMATION_REQUIRED` as both §15.1 catalog rows and `errorclassify` entries with their correct `(category, retryable)` pairs. `RESUME_FAILED` is emitted on the `/resume` transient fallback (`start.go:2556`) and is in the same uncataloged state as `SESSION_CREATION_FAILED` and `STARTING_FAILED`, so it joins the batch rather than being named as an established code the catalog never defines. Add a dedicated non-retryable `SETUP_COMMAND_FAILED` code (F-CS6) that the `setupFail` case in `writePodClaimError` emits for a deterministic setup-command exit, so the wire envelope stops contradicting §7.3's `nonRetryableFailures` classification. The emission is scoped two ways. First, it fires only when the wrapped cause is the adapter's `FailedPrecondition` non-zero-exit (or hard-timeout) failure; every other cause (the complement of `codes.FailedPrecondition`, including a crashed pod surfaced as `Unavailable` or `DeadlineExceeded`, a wrapped or non-status cause that reports as `codes.Unknown`, and `Internal`, `Aborted`, or `ResourceExhausted`) keeps the existing retryable 503 plus `Retry-After` fallback, because that failure is recoverable on a fresh session and §6.2 retries it with a fresh pod. The same `codes.FailedPrecondition`-versus-complement boundary governs both the wire-envelope retryability and the `/resume` row-state demotion (C1), so the two decisions stay aligned and a recoverable session is never demoted to terminal `failed` under a retryable envelope. Second, because the shared `setupFail` case is invoked from the decomposed `POST /v1/sessions/{id}/finalize` path, the combined `POST /v1/sessions/start` path, the concurrent-pool `POST /v1/sessions/{id}/start` path, and the `POST /v1/sessions/{id}/resume` path, the §15.1 catalog row and the §7.2 and §6.2 prose name every one of those endpoints as a surface for the code rather than `/finalize` alone. Defer `SLOT_ID_REQUIRED` until the `pod.go:17` "internal, never client-facing" versus `spec/07:333` "client-rejected" contradiction is resolved (S1 and Open decisions). Extend the catalog table and the `errorclassify` map rather than inventing a parallel taxonomy.
- **Switch the session `writeError` to the status-aware `ClassifyStatus`.** W3 routes the session surface through the same `ClassifyStatus` the admin path uses, so both surfaces agree on an unmapped code and the `(TRANSIENT, retryable)` fallback no longer mis-marks an unmapped non-5xx code as retryable. This is the single canonical classification choice.
- **Replace the `openapi.json` allowlist guard with a mux-enumerating completeness test.** W1 rewrites the presence guard to enumerate the live serve mux and assert that every registered admin template appears in the document, and completes `openapi.json` with the absent admin templates, so the §15.1:923 generation requirement is enforceable rather than under-covered by a hardcoded allowlist.
- **Treat the W4/W5/W6 and J2/J5/J6/J8 items as small reconciliations and design notes.** These are nits or documented tradeoffs in the review. The substantive residuals (the canonical `Retry-After` header convention, a `/resume`-versus-`/messages` cross-reference for a suspended session, and a 300s-TTL staged-create note) are spec or doc cross-references, recorded in Non-goals rather than staged as behavior changes.
- **Respect project principles.** v1 ships one implementation per concern with no dual modes or compatibility shims. Every staged change extends an existing surface (the §15.1 catalog, `errorclassify`, `openapi.json`, the §16.7 audit catalog, `writePodClaimError`'s switch, the injection gate, the `workspaceplan` validator). No new RPC, frame, or endpoint is introduced beyond the one already-served `/events` row and the one new §16.7 audit event the contract requires.
