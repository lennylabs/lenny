# Proposal: Wire the full §5.2 concurrent-session (`maxConcurrentSessions > 1`) and per-session-release slot lifecycle: the concurrent occupancy-zero whole-pod scrub trigger, per-session-release `ReportSessionScrub` so `recycle.maxSessionsPerPod` fires platform-wide, and the leaked-slot Redis-counter gate, superseding both prior 0035 versions

- **Status:** Verified (2026-07-02). Converged after 4 adversarial review rounds (8 findings fixed); awaiting sign-off.
- **Date:** 2026-07-04.
- **Scope:** A code-to-spec reconciliation of three §5.2/§6.2/§4.7 slot-lifecycle behaviors the committed spec mandates but which have no production path. §5.2 mandates that the whole-pod scrub "runs whenever occupancy reaches zero on a recycling pod ... reported via `ReportPodScrub`" uniformly across session-mode configurations, and that a per-slot cleanup "runs on every session release, reported by the adapter via `ReportSessionScrub`" (`spec/05_runtime-registry-and-pool-model.md`, the "Scrub model" paragraph). §4.7 states the gateway "increments `sessionsServed` on the pod's `agent_pod_state` row" on that `ReportSessionScrub` (`spec/04_system-components.md`, the `ReportSessionScrub` RPC row). §6.2 states a `leaked` slot "remains counted in the pod's Redis slot-counter occupancy (preventing the gateway from over-assigning new slots)" (`spec/06_warm-pod-model.md`, "`leaked` slot semantics"). Gap A: the concurrent occupancy-zero whole-pod scrub trigger is unwired, so a recycling concurrent pool at occupancy zero is retired by the missing-report timeout instead of scrubbed and reused. Gap B: no production adapter emits `ReportSessionScrub`, so `sessions_served` stays `0` and `recycle.maxSessionsPerPod` never fires in either mode. Gap C: `SlotClaimer.ReleaseSlot` decrements the Redis slot counter unconditionally, so a leaked slot is un-counted and the pod can be over-assigned. This proposal wires all three end to end and supersedes both prior 0035 versions (git `3186ca15`, original full scope; git `5b84b052`, narrow re-scope). It touches `pkg/gateway/podlifecycle/podclaim`, `pkg/gateway/podlifecycle/podsession`, `pkg/gateway/session/executor`, `pkg/gateway/sessionserver`, `pkg/gateway/runtime/adapterclient`, `pkg/adapter`, `schemas/lenny-adapter.proto` with its regenerated mirror, and new tier-1/2/3/4/7a/9/10 tests. No spec edit: the committed spec already mandates all three behaviors, and the code is the defect.

This document stages the proposed code and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

Three §5.2/§6.2/§4.7 behaviors the committed spec mandates have no production path today. All three are code defects with no spec basis to change.

**(A) The concurrent whole-pod scrub trigger is unwired.** §5.2 mandates that the whole-pod scrub run uniformly across session-mode configurations "whenever occupancy reaches zero on a recycling pod ... reported via `ReportPodScrub`" (`spec/05_runtime-registry-and-pool-model.md`, the "Scrub model" paragraph), gateway-triggered via the recycle disposition. On the concurrent boundary, `Binder.ReleaseSlot` sends only `ShutdownSlot` and closes the adapter connection (`pkg/gateway/podlifecycle/podsession/slotbinder.go:494-515`) before `SlotClaimer.ReleaseSlot` even computes occupancy (the `Counter.Release` decrement at `pkg/gateway/podlifecycle/podclaim/slotclaimer.go:669`), and `SlotClaimer.ReleaseSlot` at the occupancy-zero edge only patches the claim `bound → recycling` (`WriteRecyclingStatus`) and arms the missing-report timeout (`RecycleBoundary.OnRecycling`, `slotclaimer.go:689-701`) with no adapter handle to trigger a scrub. The sole `ShutdownRecycle` production caller is the session-mode `Binder.Release` path (`pkg/gateway/podlifecycle/podsession/binder.go:1891`). The comment at `slotclaimer.go:684` asserts "The adapter runs the whole-pod scrub on occupancy zero," but nothing sends the trigger, and the adapter's slot-qualified `Shutdown` early-returns via `shutdownSlot` (`pkg/adapter/session.go:226-227`) before any whole-pod logic (`startPodScrub`, `pkg/adapter/session.go:257`, runs only on the non-slot path). A recycling concurrent pool at occupancy zero is therefore retired fail-closed by the missing-report timeout instead of scrubbed and reused. This is the OPEN finding **F-5.2.31** (`BUILD-GAPS.md:4050-4068`).

**(B) `recycle.maxSessionsPerPod` is inert platform-wide.** The only writer of `sessions_served` is the gateway-side `ScrubReporter.RecordSessionScrub` (the `ReportSessionScrub` handler, `pkg/gateway/mcpfabric/delegationtree/leasecontrol/scrubreport_server.go:389`), and no production adapter emits `ReportSessionScrub`: the exported adapter-side emitter `gatewaycontrol.Client.ReportSessionScrub` (`pkg/adapter/gatewaycontrol/scrubreport.go:80`, package `gatewaycontrol` under `pkg/adapter`) has zero production callers, and neither concurrent teardown (`pkg/adapter/slotsession.go` `shutdownSlot → releaseSlot`) nor session-mode teardown (`pkg/adapter/session.go` `Shutdown → releaseSession`) sends it. So `sessions_served` stays `0` and the predicate `in.MaxSessionsPerPod > 0 && in.SessionsServed >= in.MaxSessionsPerPod` (`pkg/sandbox/podscrub/podscrub.go:295`) never fires, in both session and concurrent modes. §5.2 mandates the per-slot cleanup "on every session release, reported by the adapter via `ReportSessionScrub`" (`spec/05`, "Scrub model"); §4.7 states the gateway increments `sessionsServed` on that report (`spec/04`, the `ReportSessionScrub` RPC row).

**(C) A leaked slot is wrongly un-counted.** §6.2 mandates that a leaked slot "remains counted in the pod's Redis slot-counter occupancy (preventing the gateway from over-assigning new slots that would conflict with the leaked slot's unreleased resources)" (`spec/06_warm-pod-model.md`, "`leaked` slot semantics"). `SlotClaimer.ReleaseSlot` unconditionally decrements the counter (`Counter.Release`, `slotclaimer.go:669`) with no released/leaked distinction, and over-assignment is gated exclusively by that counter's atomic compare-and-increment (the Lua `reserveScript` in `pkg/gateway/storage/slotcounter/slotcounter.go:196`, the type `SlotClaimer.Counter *slotcounter.Counter` at `pkg/gateway/podlifecycle/podclaim/slotclaimer.go:232` binds); `slotstate.Registry.ActiveCount` (`pkg/sandbox/slotstate/registry.go:150`) has zero production callers and is off the assignment path. The slot's cleanup outcome is already available synchronously: `shutdownSlot` returns `ShutdownResponse{ExitedCleanly: closeErr == nil}` (`pkg/adapter/slotsession.go:88`) from the `ShutdownSlot` RPC that `Binder.ReleaseSlot` issues before calling `claimer.ReleaseSlot` in the same goroutine, but the result is discarded (`_, _ =`, `slotbinder.go:498`).

This proposal supersedes both prior 0035 versions (git `3186ca15`, original full scope; git `5b84b052`, narrow re-scope) and closes all three gaps end to end.

## 2. Decisions

- **Supersede both prior 0035 versions.** The original (`3186ca15`) wired gaps A and B but proposed the abandoned `slotstate.Registry` mechanism for the leaked-slot occupancy (its C-B2). The narrow re-scope (`5b84b052`) fixed gap B (session mode) and gap C with the synchronous decrement gate but explicitly deferred gap A (its §9 leaves the concurrent whole-pod scrub trigger out, so concurrent-pool `maxSessionsPerPod` stays unreachable). This full-scope proposal takes gap A from the original, gap B from the re-scope (extended so concurrent `maxSessionsPerPod` now fires because A supplies the missing whole-pod `ReportPodScrub`), and gap C from the re-scope's synchronous decrement gate.
- **No spec edit.** The "Scrub model" paragraph and recycle-lifecycle passages of §5.2, the "`leaked` slot semantics" paragraph of §6.2, and the `ReportSessionScrub` RPC row of §4.7 already mandate all three behaviors; the code is the defect. Classified `fix` (code-to-spec reconciliation reusing the existing `SlotClaimer`/`Counter`/`RecycleBoundary`/`ReportSessionScrub`/`ShutdownRecycle` machinery), consistent with the re-scope's classification and the `0035_fix_` filename.
- **Gap A composes with gap C via a two-phase concurrent last-slot teardown, because the leaked outcome must be known before the recycle decision.** Phase 1: `ShutdownSlot` tears the last slot down (emits its per-slot `ReportSessionScrub`, gap B) and returns the leaked signal (`ExitedCleanly`, gap C). Gate the decrement on it. Phase 2: only on a clean occupancy-zero recycle does the gateway send the whole-pod scrub trigger (a recycle-disposition `Shutdown` carrying `RecycleScrub`) so the adapter runs `startPodScrub` and reports `ReportPodScrub`. A leaked last slot stays counted (occupancy never reaches zero) and does not recycle, which is fail-closed and correct: a pod holding unreleased leaked resources must not be returned to cross-tenant reuse.
- **Reject the combined single-RPC variant** (a recycle-carrying `ShutdownSlot` that tears the slot and runs the scrub in one call, the original C-A2). It forces triggering the whole-pod scrub before the leaked outcome is known, so a leaked last slot would wrongly trigger scrub-and-reuse. The two-phase design avoids that circularity.
- **Gap C uses the synchronous decrement gate** (`leaked := err != nil || !exitedCleanly`; skip `Counter.Release` when leaked), rather than the `slotstate.Registry` approach the original 0035 C-B2 proposed. The registry is not on the assignment path (`Registry.ActiveCount` has zero production callers), so keeping a slot in the registry cannot prevent over-assignment; the Redis counter is the sole gate.
- **Do not touch the `lenny_adapter_leaked_slots` gauge wiring.** It is already driven in production by the slot-bind-failure retry path (`pkg/gateway/sessionserver/start.go:2159-2161`, `MarkLeaked → SlotLeakGauge → SetAdapterLeakedSlots` at `cmd/lenny-gateway/sessionsrv.go:310`). The original 0035 C-B2 rested on a refuted premise that this wiring is absent; this proposal does not drive the gauge from `RecordSessionScrub` and does not disturb the existing gauge path.
- **Minimal protocol surface.** Reuse `ShutdownRecycle`, `ShutdownSlot`, `ReportSessionScrub`, and the existing `RecycleScrub` sub-message. Add exactly one wire field, a top-level `ShutdownRequest.pod_id`, because the `ReportSessionScrub` handler rejects an empty `pod_id` fail-closed (`scrubreport_server.go:80-81`) and the adapter holds no pod identity of its own; this delivers the pod identity on the plain `Shutdown`, `ShutdownSlot`, and `Terminate` teardowns that do not carry `RecycleScrub`. Reuse `ShutdownResponse.exited_cleanly` for the leaked signal (no new response field). Deliver the per-slot cleanup budget on the existing `ShutdownRequest.deadline_ms` field (see C6) rather than a new `StartSessionRequest` field.
- **A failed or crashed last slot retires the pod rather than triggering scrub-and-reuse** (`spec/05`, "A session that ends in failure or a crash always retires its pod"). Thread the slot's terminal disposition from `PodExecutor.Release` (`pkg/gateway/session/executor/pod.go:305,:318`, which currently calls `binder.ReleaseSlot` with no disposition) through `Binder.ReleaseSlot` into `SlotClaimer.ReleaseSlot`, mirroring the session-mode `result.Recycle && disposition != dispositionFailed` predicate.

## 3. The mechanism: the two-phase concurrent last-slot teardown

The three gaps interlock on the last-slot drain, so the wiring order matters. Today `Binder.ReleaseSlot` sends `ShutdownSlot`, discards its result, closes the adapter connection, and only then calls `SlotClaimer.ReleaseSlot`, which computes occupancy and arms the missing-report timeout with no adapter handle left to trigger a scrub. The reorder makes the concurrent path structurally match session-mode `Binder.Release`.

Phase 1 (per-slot teardown) sends `ShutdownSlot`. The adapter tears down only this slot's runtime and per-slot tree, emits the per-slot `ReportSessionScrub` for the slot (`released` or `leaked`, gap B), and returns `ShutdownResponse.exited_cleanly` (gap C). The gateway derives `leaked := err != nil || !exitedCleanly` and passes it to `SlotClaimer.ReleaseSlot`, which skips the Redis decrement for a leaked slot so the slot stays counted (§6.2), and otherwise decrements and computes occupancy. `SlotClaimer.ReleaseSlot` returns a structured outcome: siblings remain, the pod is recycling, or the pod is retired.

Phase 2 (whole-pod scrub trigger) runs only on the recycling outcome: the gateway sends the recycle-disposition `Shutdown` carrying `RecycleScrub` (the existing `ShutdownRecycle` path) with an empty `slot_id`, so the adapter runs `startPodScrub` through the new concurrent whole-pod branch (C2) that bypasses the `checkSession` gate a slot-less concurrent recycle would otherwise fail, and reports `ReportPodScrub`. A clean report advances the pod through the existing recycle disposition; the now-correctly-advanced `sessions_served` (gap B) makes `podscrub.Decide` fire `maxSessionsPerPod` in concurrent mode as it already can in session mode. Only after Phase 2 does the gateway close the adapter connection.

A leaked last slot never reaches occupancy zero (its count is withheld), so it takes neither the recycle nor the retire branch and the pod is not returned to reuse; a failed last slot retires the pod. Both are fail-closed by construction: a pod holding unreleased leaked resources or a crashed slot is never returned to cross-tenant reuse.

## 4. Proposed changes

### C1. Thread the last-slot occupancy-zero disposition out of `SlotClaimer.ReleaseSlot` and reorder `Binder.ReleaseSlot`

**Target:** `pkg/gateway/podlifecycle/podclaim/slotclaimer.go`, `pkg/gateway/podlifecycle/podsession/slotbinder.go`, `pkg/gateway/session/executor/pod.go`, `pkg/gateway/sessionserver/start.go`.

**Anchor and change:** `Binder.ReleaseSlot` (`slotbinder.go:494-515`) today sends `ShutdownSlot` and closes the adapter connection before `SlotClaimer.ReleaseSlot` computes occupancy (the decrement at `slotclaimer.go:669`), so the whole-pod scrub can never be triggered. `SlotClaimer.ReleaseSlot` returns a bare `error` and holds no adapter handle. The reorder makes the concurrent path structurally match session-mode `Binder.Release`: tear the slot down, learn occupancy, then on a clean occupancy-zero recycle trigger the scrub.

Change `SlotClaimer.ReleaseSlot(ctx, sandboxName, sessionID string, recycle bool) error` to `ReleaseSlot(ctx, sandboxName, sessionID string, recycle, failed, leaked bool) (SlotReleaseOutcome, error)`, where `SlotReleaseOutcome` is an enum `{SlotSiblingsRemain, SlotRecycling, SlotRetired}`. The `leaked` parameter is C5's gate: when set, skip `Counter.Release`, return `SlotSiblingsRemain`, and compute no occupancy-zero disposition (the leaked slot keeps the pod counted, §6.2). On a released slot, run the current `DECR`:

- `remaining > 0` → `SlotSiblingsRemain` (sibling slots remain; the per-pod claim stays, unchanged from `slotclaimer.go:675`).
- `remaining == 0 && recycle && !failed` → `WriteRecyclingStatus` + `RecycleBoundary.OnRecycling` (unchanged from `slotclaimer.go:689-701`) → `SlotRecycling`.
- `remaining == 0 && (!recycle || failed)` → `DeleteClaim` → `SlotRetired` (a failed last slot retires; `spec/05`, "A session that ends in failure or a crash always retires its pod").

Delete the stale comment at `slotclaimer.go:684` that claims the adapter self-detects occupancy zero ("The adapter runs the whole-pod scrub on occupancy zero"): nothing sends that trigger today, and C2 makes it an explicit gateway send.

In `Binder.ReleaseSlot`: release credentials, send `ShutdownSlot` (Phase 1, whose return C3 and C5 read), call `claimer.ReleaseSlot` to get the outcome, then on `SlotRecycling` send the Phase-2 whole-pod scrub trigger (C2), then `Adapter.Close()`; move the `Close` to the end of the function so the adapter connection survives the Phase-2 trigger.

Thread the terminal disposition: `PodExecutor.Release` (`pkg/gateway/session/executor/pod.go:318`) passes `string(disposition)` into `ReleaseSlot`; the rollback path passes the failed disposition it already carries. `Binder.ReleaseSlotReservation` passes `failed=true, leaked=false` and ignores the outcome (rollback never recycles).

**Rationale:** `SlotClaimer.ReleaseSlot` is the sole place occupancy is computed; returning a structured outcome rather than a bare error lets `Binder.ReleaseSlot` decide whether to trigger the whole-pod scrub. Gating the decrement on `leaked` (C5) and returning the disposition composes gaps A and C without a second round trip, and honors §5.2's "runs whenever occupancy reaches zero on a recycling pod" and §6.2's leaked-slot occupancy rule in one path.

### C2. Send the concurrent whole-pod scrub trigger on the recycling outcome and run `startPodScrub` outside the slot branch

**Target:** `pkg/gateway/podlifecycle/podsession/slotbinder.go`, `pkg/gateway/podlifecycle/podsession/binder.go`, `pkg/adapter/session.go`.

**Anchor and change:** On the `SlotRecycling` outcome from C1, `Binder.ReleaseSlot` sends a recycle-disposition `Shutdown` carrying `RecycleScrub` (the existing `ShutdownRecycle` production path, whose sole caller is the session-mode `Binder.Release` at `binder.go:1891`) before `Adapter.Close()`. Reuse the `RecycleScrub` sub-message with the scrub parameters C6 populates onto the concurrent `BindResult`; source `pod_id` from `BindResult.SandboxName` as the session-mode path does. The armed missing-report timeout that `SlotClaimer.ReleaseSlot` set on `SlotRecycling` (`RecycleBoundary.OnRecycling`) is cancelled by the adapter's `ReportPodScrub`, the same correlation the session-mode boundary uses.

On the adapter side, the Phase-2 trigger carries no `slot_id` (the slot is already gone) and does carry `recycle` (`RecycleScrub`). It cannot take the existing non-slot recycle branch, because that branch runs `checkSession(sessionID)` (`pkg/adapter/session.go:229`) before it reaches `startPodScrub` (`session.go:256-257`), and `checkSession` returns `FailedPrecondition "pod has no assigned session"` whenever `s.sessionID == ""` (`session.go:323-324`). In concurrent (`maxConcurrentSessions > 1`) mode `s.sessionID` is never set: a slot-qualified `StartSession` returns via `startSessionSlot` (`session.go:103-107`) before `claimSession`, so the sole non-SDK setter of `s.sessionID` (`session.go:342`) never runs, and concurrent slot starts set only the per-slot `st.sessionID` (`slotsession.go:45`). A Phase-2 recycle `Shutdown` with an empty `slot_id` therefore fails `useSlot("")` (`slot.go:39-41`, returns false) and then fails the `checkSession` gate, returning before `startPodScrub` runs. The whole-pod scrub never runs, `ReportPodScrub` never fires, and the recycling concurrent pod is retired by the armed missing-report timeout, which is the exact fail-closed retirement gap A closes.

Add an explicit adapter `Shutdown`-handler branch for a slot-less recycle `Shutdown` on a concurrent pod with no pod-global session: when `req.GetRecycle() != nil`, `slot_id` is empty, and `s.sessionID == ""`, dispatch `startPodScrub(rc)` directly, ahead of and bypassing `checkSession`, `emitFinalUsage`, `drainViaLifecycle`, `Runtime.Close`, and `releaseSession` (all already performed per-slot in Phase 1 at `slotsession.go`), and emit no second `ReportSessionScrub` (the per-slot report already fired in Phase 1). Placing the scrub on the last-slot session that Phase 1 already tore down and Runtime-closed would run a second `Runtime.Close`, a second drain, and a second `releaseSession`, double-counting `sessions_served`, so a concurrent-specific whole-pod entry point is required. A recycle-carrying `ShutdownSlot` is rejected in §2 because it forces triggering the scrub before the slot's leaked outcome is known, so the concurrent whole-pod trigger stays a separate slot-less recycle `Shutdown` handled by this new branch.

**Rationale:** The whole-pod scrub is the §5.2 "runs whenever occupancy reaches zero on a recycling pod, reported via `ReportPodScrub`" behavior. Phase 2 is a separate RPC from Phase 1 so the leaked outcome (gap C) is known before the recycle decision; a combined recycle-carrying `ShutdownSlot` would force triggering the scrub before the slot's leaked outcome is known and would wrongly scrub-and-reuse a pod with a leaked last slot (see §2, rejected variant).

**Anchor and change:** The only writer of `sessions_served` is the gateway-side `RecordSessionScrub` (`scrubreport_server.go:389`), and no production adapter emits `ReportSessionScrub` (the exported adapter-side `Client.ReportSessionScrub` at `pkg/adapter/gatewaycontrol/scrubreport.go:80` has zero production callers). §5.2 mandates the per-slot cleanup reported via `ReportSessionScrub` on every session release, uniform across session-mode configurations; §4.7's `ReportSessionScrub` row makes that report the `sessionsServed` increment.

### C4. Add the top-level `ShutdownRequest.pod_id` wire field

**Target:** `schemas/lenny-adapter.proto` (the `ShutdownRequest` message `:1239-1257`), `pkg/proto/adapter/v1/lenny-adapter.pb.go` (regenerated; do not hand-edit), `pkg/gateway/runtime/adapterclient/client.go` (the shutdown helper `:778-789` and the `Shutdown` `:767`, `ShutdownSlot` `:774`, and `Terminate` `:805` signatures and call sites), `pkg/gateway/podlifecycle/podsession/binder.go` (the sole `Client.Shutdown` caller `shutdownAdapter` `:1898`), `pkg/gateway/podlifecycle/podsession/slotbinder.go` (the sole `Client.ShutdownSlot` caller `Binder.ReleaseSlot` `:498`), `cmd/lenny-gateway/user_revocation.go` (the sole `Client.Terminate` caller `:129`), `pkg/adapter/session.go` (the `Shutdown` handler that reads it).

Add `string pod_id = 6;` to `ShutdownRequest` with a comment stating that it carries the `agent_pod_state` row key on the plain-shutdown, slot-shutdown, and terminate teardowns that do not carry `RecycleScrub`, and that on the recycle path `RecycleScrub.pod_id` remains the source. Update every production caller to pass the gateway-side sandbox name:

- `Client.Shutdown`: the sole production caller is `Binder.shutdownAdapter` (`pkg/gateway/podlifecycle/podsession/binder.go:1898`, `_, _ = result.Adapter.Shutdown(ctx, result.SessionID)`), which passes `result.SandboxName`. - `Client.ShutdownSlot`: the sole production caller is `Binder.ReleaseSlot` (`slotbinder.go:498`, already reordered by C1/C5), which passes `result.SandboxName`.

**Rationale:** This is the single wire field the change adds, and it is unavoidable: the `ReportSessionScrub` handler fails closed on an empty `pod_id` and the adapter holds no pod identity of its own on the non-recycle teardowns. Reusing the existing `RecycleScrub.pod_id` on the recycle path and adding a top-level field only for the paths that lack it keeps the protocol surface minimal.

### C5. Gate the Redis slot-counter decrement on the synchronous cleanup outcome

**Target:** `pkg/gateway/podlifecycle/podsession/slotbinder.go`, `pkg/gateway/podlifecycle/podclaim/slotclaimer.go`.

**Anchor and change:** `SlotClaimer.ReleaseSlot` unconditionally decrements the counter (`Counter.Release`, `slotclaimer.go:669`) with no released/leaked distinction, and over-assignment is gated exclusively by that counter's atomic compare-and-increment (the Lua `reserveScript` in `pkg/gateway/storage/slotcounter/slotcounter.go:196`). §6.2 mandates that a leaked slot stay counted so the gateway does not over-assign.

In `Binder.ReleaseSlot`, read the `ShutdownSlot` return (today discarded, `slotbinder.go:498`) and derive `leaked := err != nil || !resp.GetExitedCleanly()`. Pass `leaked` into `SlotClaimer.ReleaseSlot` (C1). In `SlotClaimer.ReleaseSlot`, when `leaked` is true, skip `Counter.Release` entirely and return `SlotSiblingsRemain` with no occupancy-zero disposition, so the leaked slot's count is withheld and the pod never reaches occupancy zero on the strength of a leaked slot. An errored or unclean `ShutdownSlot` reads as leaked (fail-closed): the decrement stays synchronous and in place, and no per-slot missing-report timeout is added.

**Rationale:** The leaked outcome is returned synchronously by `ShutdownSlot` (`ShutdownResponse.exited_cleanly`, `slotsession.go:88`), so the decrement gate needs no asynchronous relocation onto the `ReportSessionScrub` handler and no timeout backstop. The Redis counter is the sole over-assignment gate, so withholding its decrement is the only mechanism that keeps a leaked slot counted; the `slotstate.Registry` the original 0035 C-B2 proposed is off the assignment path.

### C6. Populate the scrub-config fields on the concurrent `BindResult` and deliver the per-slot cleanup budget on `ShutdownRequest.deadline_ms`

**Target:** `pkg/gateway/podlifecycle/podsession/resolve.go`, `pkg/gateway/sessionserver/start.go`, `pkg/gateway/podlifecycle/podsession/slotbinder.go`, `pkg/gateway/podlifecycle/podsession/binder.go`, `pkg/gateway/runtime/adapterclient/client.go`, `pkg/adapter/slotsession.go`, `pkg/adapter/session.go`.

**Anchor and change (Part 1 — populate the concurrent `BindResult` scrub fields):** Gap A's Phase-2 recycle trigger (C2) needs `cleanupCommands`, `cleanupTimeoutSeconds`, and `scrubProfile` on the concurrent `BindResult`. These struct fields already exist on `BindResult` (`binder.go:526-528`) and are populated only on the exclusive path; the concurrent `BindSlot` result (`slotbinder.go:308-330`) sets only `MaxConcurrentSessions` and `Recycle`, leaving the scrub fields empty. `resolve.go` already folds `CleanupCommands`/`CleanupTimeoutSeconds`/`ScrubProfile` onto `PoolMatch` (`resolve.go:118-119,:284,:339-340`), so the concurrent `slotBindRequest` builder in `start.go` copies them onto the `SlotBindRequest`, and `BindSlot` (`slotbinder.go`) sets them on the concurrent `BindResult` it constructs. This is a one-hop copy with no new surface.

**Anchor and change (Part 2 — deliver the per-slot cleanup budget on the existing `deadline_ms`):** The §5.2 per-slot cleanup timeout is `max(cleanupTimeoutSeconds / maxConcurrentSessions, 5)` seconds, "minimum 5s enforced at runtime by the adapter" (`spec/05`, the "Slot cleanup" bullet). Do not add new proto fields for this. The existing `ShutdownRequest.deadline_ms` (`schemas/lenny-adapter.proto:1242`, field 3) already flows to the slot teardown: the adapter dispatches a slot-qualified `Shutdown` to `shutdownSlot(ctx, sessionID, slotID, req.GetDeadlineMs())` (`session.go:227`) and `slotsession.go:82` bounds `Runtime.Close` with `contextWithGraceDeadline(ctx, deadlineMs)`. The gateway shutdown helper (`adapterclient/client.go:778-789`, reached by both `Shutdown` and `ShutdownSlot`) leaves `DeadlineMs` unset (`0`), so the adapter falls to its internal default; setting it on the slot path is free.

Both inputs to the §5.2 formula are already gateway-side at the `ShutdownSlot` call: `BindResult.MaxConcurrentSessions` is populated for routing (`slotbinder.go:319`, `binder.go:496`) and `BindResult.CleanupTimeoutSeconds` is supplied by Part 1. The adapter clamps the slot-path `deadlineMs` to a 5s minimum and uses it to bound both `Runtime.Close` (already wired) and `removeSlotTree` (the C3/C5 slot-tree teardown whose result feeds `ExitedCleanly`). CRD validation already guarantees `cleanupTimeoutSeconds >= maxConcurrentSessions * 5` (`spec/05`, the "CRD validation rule" bullet), so the delivered quotient is always `>= 5` for valid pools and the clamp is defense-in-depth, exactly as the spec frames "enforced at runtime by the adapter."

This drops the earlier draft's `StartSessionRequest` proto fields (`max_concurrent_sessions`, `cleanup_timeout_seconds`), the adapter `Server` pod-global cache, and the adapter-side division, cutting one tier-3 wire obligation while satisfying the §5.2 per-slot cleanup budget identically. No `schemas/lenny-adapter.proto` or `pkg/proto/adapter/v1/lenny-adapter.pb.go` change beyond C4's `pod_id` field is needed for C6.

**Rationale:** The concurrent `BindResult` genuinely needs the scrub fields for the Phase-2 recycle trigger, and `resolve.go` already carries them onto `PoolMatch`, so Part 1 is a minimal copy. Part 2 reuses the existing `deadline_ms` slot-teardown channel already wired end to end, so the per-slot cleanup budget is a gateway-computed quantity delivered on an existing field, and the only adapter-side obligation the spec names — the 5s floor — is a small local clamp with zero new proto fields.
