# Proposal: Build the §15 single-shot pod-binding model so the built-in OpenAI-dialect adapters claim, dispatch, and release a warm pod within one HTTP call

- **Status:** Applied to spec (2026-07-22). Open decision 1 (Open Responses continuity) resolved as option (b): `SupportsSessionContinuity` stays `true`; lineage persistence and conversation rehydration are filed as a bounded follow-on proposal. Open decision 2 (pool-exhaustion envelope) resolved as `503` with `Retry-After`, matching the platform-wide §7.1 taxonomy. Converged after 6 adversarial review rounds (11 findings fixed).
- **Date:** 2026-07-22.
- **Scope:** A code-and-test build that makes the two built-in OpenAI-dialect adapters (`OpenAICompletionsAdapter` at `/v1/chat/completions`, `OpenResponsesAdapter` at `/v1/responses`) functional against a `PodExecutor`-backed gateway, plus one small §15 spec amendment that documents the single-shot pod-binding compute model the spec's unconditional "Always available" declaration implies but never states. Both handlers today mint a session row and call `executor.Executor.Send` without ever running the sessionserver claim-launch-registerBinding sequence, so every request against the standard chart's `--agent-namespace` (`PodExecutor`) wiring returns `500 server_error` with `podexec: session ... is not bound to a pod`. The build routes each adapter request through the shared §15.2.1 session-creation service so the admission gates run, a warm pod is claimed and launched, and the binding is registered, then dispatches the turn over `exec.Send`, then releases the pod and its §4.9 lease synchronously within the same HTTP call on success, dispatch failure, and timeout. It un-blocks T-STD.4 (`TEST-GAPS.md:11846`): the two tier-5 conformance tests `TestOpenAIChatCompletionsConformsToPublishedSchemaOnDeployedGateway` and `TestOpenAIResponsesConformsToPublishedSchemaOnDeployedGateway` skip on this exact defect today (`tests/tier5_e2e_kind/openai_conformance_test.go:54-57`). The single §15 amendment is the only spec edit.

This document stages the proposed spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

Spec §15 declares the two built-in OpenAI-dialect adapters "Always available": `OpenAICompletionsAdapter` at `/v1/chat/completions` and `OpenResponsesAdapter` at `/v1/responses` (`spec/15_external-api-surface.md:566-567`, inventory table at `573-583`). On any standard Helm deployment both are non-functional.

**1. The default wiring selects `PodExecutor`.** The chart sets `agentNamespaces` by default (`charts/lenny/values.yaml:18-20`), which renders `--agent-namespace` (`charts/lenny/templates/gateway-deployment.yaml:611-613`) and selects `PodExecutor` as the single session executor (`cmd/lenny-gateway/stores.go:2106`, `exec = executor.NewPodExecutor(podRegistry, podBinder)`).

**2. Both handlers dispatch without claiming a pod.** `handleCreateCompletion` (`pkg/gateway/environment/translator/openai_chat.go:176-263`) mints a `sessionstore.Session` row with `store.Create` (`:219`) and dispatches a full Lenny runtime turn over `exec.Send` (`:235`). `handleCreate` on the Open Responses adapter does the same (`pkg/gateway/environment/translator/open_responses.go:209-287`, `store.Create` at `:251`, `exec.Send` at `:263`). Neither runs the sessionserver claim-launch-registerBinding sequence that every REST and MCP session runs. `exec.Send` is the same interactive-session dispatch interface (`pkg/gateway/sessionserver/messages.go:538`), rather than the separate §4.9 llmproxy outbound credential-injection path.

**3. `PodExecutor.Send` fails closed on the never-registered session.** `PodExecutor.Send` routes through `streamFor` (`pkg/gateway/session/executor/pod.go:79-83`), which calls `registry.Get` on the session id (`pod.go:134`) and, on a miss, returns `podexec: session %s is not bound to a pod` (`pod.go:135-136`). The handlers wrap that into `500 server_error` with `executor failure: %v` (`openai_chat.go:236-240`, `open_responses.go:264-267`), so every real request returns `500`. The `podsession.Registry` is populated only by `registerBinding` inside `sessionserver.Server` (`podRegistry.Put` at `start.go:2501`, reached from `start.go:788` in the create-and-start path and `start.go:3428` in the `/start` path), none of which the translators reach.

**4. Release leaks a claimed pod on the dispatch-failure path.** Today `exec.Close` runs only after `Send` succeeds (`openai_chat.go:250`, `open_responses.go:275`). The `Send`-error path returns early (`openai_chat.go:236-240`) with no release. If the handlers claimed a pod, a dispatch failure would leak the claim and its credential lease.

**5. The spec defines no single-shot pod-binding model for a built-in adapter.** §15's inventory carries no clause on how an adapter request that dispatches a runtime turn acquires, uses, and releases compute. §7.1's atomicity model (`spec/07_session-lifecycle.md:23`) is written for the REST and MCP session-lifecycle endpoints the adapters do not call. This is the confirmed spec gap.

This blocks T-STD.4 (`TEST-GAPS.md:11846`, High). The finding's needs-human note (2026-07-06) states the same diagnosis: "on any standard Helm deployment the spec's 'Always available' built-in OpenAI-dialect adapters are non-functional today," names it "a design question, not a small patch," and asks whether the fix goes through the change-proposal pipeline and "what is the intended pod-binding model for these two adapters when the gateway runs a PodExecutor: claim-per-request against the existing warm pool, a dedicated always-warm pool for translator traffic, or something else?" This proposal answers that question and builds the model. The two tier-5 conformance tests skip on this defect (`tests/tier5_e2e_kind/openai_conformance_test.go:54-57`, call sites at `:134` and `:196`).

## 2. Decisions

- **Claim-per-request against the shared warm pool, reusing the shared §15.2.1 create-and-start service rather than a parallel path.** A built-in adapter request that dispatches a runtime turn runs an implicit single-shot session: it claims a warm pod from the shared §5 pool, dispatches the turn, and releases the pod within one HTTP call. No dedicated translator pool is introduced. This answers the T-STD.4 design question in favor of claim-per-request against the existing pool.
- **The reuse surface is the create-and-start composition rather than the create-only `CreateSessionService`.** `sessionserver.Server` already exports `CreateSessionService` (`service.go:145`), the shared service layer §15.2.1 rule 1 mandates, which runs the admission gates and claims a pod. It drives the two-step `handleCreate` (`service.go:161`), which persists the row and claims the pod but does not register the binding into `podRegistry` or launch the runtime: `registerBinding`/`podRegistry.Put` run in the create-and-start path (`start.go:788`, `:2501`) and are deferred to `/finalize` and `/start` in the two-step lifecycle (`finalize.go:345`). A session created through `CreateSessionService` alone therefore still fails `exec.Send` with `is not bound to a pod`. The single-shot adapter needs a pod-bound, runtime-started, registry-registered session, which is what the create-and-start handler `handleCreateAndStart` (`start.go:423`) produces: it runs `createAndStartGates` (`start.go:453`, the §15.2.1 admission gates) then `mintClaimStartPersist` (`start.go:687`), which composes `claimAtCreate` (credential pre-check plus warm-pod claim, `start.go:725`), `startOnPod` (prepare plus launch, `start.go:751`), and `registerBinding` (`start.go:788`), with `rollbackClaim` (`start.go:760`) and `rollbackBinding` (`start.go:778`) on every failure edge. This proposal adds a `CreateAndStartService` wrapper mirroring the existing `CreateSessionService` pattern so the adapter reuses that composition through one canonical, gate-running service entry point.
- **The single-shot session runs through the full §15.2.1 admission stack, which this proposal completes on the create-and-start path.** Today `createAndStartGates` (`start.go:453`) runs only the active-user, tenant-state, tenant-classification, session-quota, and policy-chain gates. The concurrency and admission-rate gates (§11.1) and the environment-admission gate (§10.6) run only on the two-step create path (`requireConcurrencyLimits` at `create.go:104`, `requireAdmissionRateLimit` at `create.go:117`, `requireEnvironmentAdmission` at `create.go:134`), after the request body is decoded. Routing the external OpenAI-dialect surface through the create-and-start path as it stands would fail open on those three gates, and the environment-admission gate is load-bearing here because the adapter resolves an environment scope from the `model` (`splitEnvModel`, `openai_chat.go:202`) and sets `req.Environment`. This proposal therefore adds `requireConcurrencyLimits`, `requireAdmissionRateLimit`, and `requireEnvironmentAdmission` to the create-and-start path, run after the request is decoded (they read the resolved runtime, pool, and environment), before `mintClaimStartPersist` claims the pod, with the concurrency and admission-rate gates placed before the policy chain as the two-step create path places them (§11.1: an over-limit create reserves no rate or token budget). `POST /v1/sessions/start` and the adapter then run the §11.1 concurrency and admission-rate gates and the §10.6 environment-admission gate that the two-step create path runs, so OpenAI-dialect traffic no longer fails open on them. This closes the three gates the finding named; any remaining divergence between the two gate functions (for example the dual-store, tenant-state, and tenant-classification gates that sit on only one path today) is a separate pre-existing question outside this proposal. A bespoke claim-only method that jumped straight to `claimAtCreate` would bypass the whole stack and fail open on an external surface, so it is rejected (see "Resolved in adversarial review").
- **Guaranteed synchronous release within the same HTTP call on success, dispatch failure, and timeout, recording the §6.2 disposition.** Release moves from a post-`Send` call to a `defer` that fires on every handler exit. The release routes through `executor.ReleaseSession(ctx, h.exec, sessionID, disp)` (`executor.go:180`), the single disposition-recording entry point: for a pod-backed executor it calls `PodExecutor.Release` (`pod.go:305`), which removes the registry binding and calls `binder.Release` for an exclusive session-mode bind or `binder.ReleaseSlot` for a concurrent-slot bind (`pod.go:313-325`), recording the §6.2 terminal disposition on the backing Sandbox before draining the pod. The handler passes `DispositionCompleted` (`executor.go:144`) on a successful turn and `DispositionFailed` (`executor.go:147`) on a dispatch error or request timeout, so the recorded §6.2 phase matches the outcome. A bare `PodExecutor.Close` is not used because it routes to `Release(ctx, id, "")` with an empty disposition and explicitly does not record the §6.2 terminal phase (`pod.go:293-296`). The release runs on a context detached from the request context (`context.WithoutCancel(r.Context())` bounded by a fresh release timeout) so the pod-drain and lease-release apiserver calls survive a request-context timeout or client disconnect, which is the exact failure the deferred release exists to reclaim; `Binder.Release` performs a `Client.Get` then a `DeleteClaim` (`binder.go:1870,1142`) that would return `context.Canceled` immediately on an already-cancelled request context.
- **The translator package defines the claim capability as a small consumer interface, injected at the gateway wiring boundary.** `pkg/gateway/sessionserver` already imports `pkg/gateway/environment/translator` (`runtimes.go:13`), so the translator cannot import sessionserver without a cycle. The capability is a small interface defined at the consumer (translator), satisfied by a thin wiring adapter in `cmd/lenny-gateway` that maps the adapter's fields into a `sessionserver.CreateSessionRequest` and calls `CreateAndStartService`. `cmd/lenny-gateway` imports both packages, so it is the one place the binding can be made. This is the idiomatic consumer-interface pattern and is required by the cycle constraint.
- **One canonical adapter dispatch path, gated by dependency injection rather than a runtime branch.** The handler always calls the injected binder. In the `PodExecutor` wiring the binder is the sessionserver-backed adapter, which claims, launches, and registers; the release then drains the pod. In the in-memory `EchoExecutor` wiring (`podBinder == nil`) the same create-and-start composition no-ops the claim (`mintClaimStartPersist` guards the claim on `s.podBinder != nil`, `start.go:724`), persists the row, and returns the id, so the existing echo round-trip the tier-3 in-process suites rely on is preserved on the same code path. Handlers constructed without a binder (the pure in-process translator unit tests) fall back to a default no-op binder that persists a minimal row through the handler's own store, matching today's inline behavior.
- **Open Responses continuation re-claims per request; the pod bind is not retained across HTTP calls.** Retaining an idle warm pod between calls contradicts claim-per-request and warm-pool economics. The single-shot path does not persist `previous_response_id` as the session-row `ParentSessionID`: the reuse surface (`CreateAndStartRequest`, `start.go:383`) carries no parent field, and `buildCreateAndStartRow` never assigns `ParentSessionID` (`start.go:592-609`). Threading it in would also collide with the §8.2/§8.6 delegated-child semantics, because `registerLeaseTree` suppresses the credential-lease-tree root registration when `row.ParentSessionID != ""` (`sessionserver.go:831`), so an adapter-supplied lineage on an ephemeral single-shot session would be mistaken for a delegated child and its lease root would not be registered. The `previous_response_id` lineage pointer is therefore not carried through the single-shot create-and-start path, and `GET /v1/responses/{id}` echoes an empty `previous_response_id` (`open_responses.go:367`). Persisting the lineage without the delegated-child side effects is folded into the Open Responses continuity follow-on (see Open decisions). Release stays synchronous within one call for both adapters despite the `SupportsSessionContinuity` asymmetry (`open_responses.go:30` true, `openai_chat.go:39` false).
- **Pool exhaustion and credential-availability misses map to the sessionserver's own classification, which distinguishes two codes.** `mintClaimStartPersist` returns the typed pool, slot, and credential errors that `writePodClaimError` (`start.go:64`) classifies. A warm-pod or concurrent-slot claim exhaustion wraps `errCreateClaimExhausted` and maps to `503 SESSION_CREATION_FAILED` with a `Retry-After` header (`start.go:167-179`). A credential-availability pre-check miss (`credrouter.ErrNoCredentialAvailable`) maps to `503 CREDENTIAL_POOL_EXHAUSTED` (category POLICY) with no `Retry-After` header (`start.go:155-158`, `writeCredentialPoolExhausted` at `start.go:294-298`), matching §4.9 and the §7.1 pre-claim rule (`spec/07_session-lifecycle.md:8-12`). `CreateAndStartService` surfaces both as a typed `ServiceError` carrying the HTTP status, code, retryability, and (for the `SESSION_CREATION_FAILED` case) the `Retry-After` seconds captured from the recorder header, and the adapter re-emits the same code and header in its native error envelope. The adapter fails closed rather than emitting a generic `server_error`.
- **`kind` is `fix`, not `new`.** The capability is already promised by the spec's unconditional "Always available" declaration. Correcting non-functional code to honor that promise is a reconciliation, and the single §15 amendment documents the pod-binding model the declaration implies but never states.

## 3. The single-shot request path after the change

Both adapter handlers run the same sequence, which replaces the current `store.Create` then `exec.Send` then post-success `exec.Close`:

1. Decode and validate the request body, resolve the tenant (`resolveTenant`, `openai_chat.go:395`), and split the `model` into an environment scope and a runtime reference (`splitEnvModel`, `openai_chat.go:202`), exactly as today.
2. Call the injected single-shot binder with the resolved tenant, user, runtime reference, and environment. The binder maps these into a `sessionserver.CreateSessionRequest` and calls `CreateAndStartService`, which runs the full §15.2.1 admission stack (including the concurrency, admission-rate, and environment-admission gates this proposal adds to the create-and-start path), claims a warm pod, launches the runtime, and registers the binding into the shared `podRegistry` the `PodExecutor` reads. It returns the created session id, or a typed error.
3. On a binder error, map it into the native envelope: a `503 SESSION_CREATION_FAILED` warm-pod or slot claim exhaustion becomes a `503` with `Retry-After`; a `503 CREDENTIAL_POOL_EXHAUSTED` pre-check miss becomes a `503` with no `Retry-After`; an admission-gate rejection (quota, concurrency, admission-rate, policy, and environment) becomes the gate's native status and code; any other failure becomes `500 server_error`. No pod was dispatched.
4. Arrange the release: on every subsequent exit path the handler calls `executor.ReleaseSession(context.WithoutCancel(r.Context()), h.exec, sessionID, disp)` on a detached context bounded by a fresh release timeout, with `disp` = `DispositionCompleted` on a successful turn and `DispositionFailed` on a dispatch error or timeout. Against `PodExecutor` it removes the binding and drains the pod through `binder.Release`/`binder.ReleaseSlot`, recording the §6.2 terminal disposition. The detached context ensures the drain and lease release survive a request-context timeout or client disconnect. Against `EchoExecutor` the release falls back to `Close` and is a no-op (`ErrUnsupported`, already tolerated at `openai_chat.go:250`).
5. Dispatch the turn: translate the messages and call `exec.Send(ctx, sessionID, msgs)`. On a `Send` error, return `500 server_error`; the deferred release drains the claimed pod, so no pod or lease leaks.
6. On success, mark the session completed (`store.Update`, unchanged) and write the OpenAI or Open Responses response body. The deferred release fires as the handler returns, so the pod and its §4.9 lease are released before or as the response is flushed.

Against the `EchoExecutor` wiring (`podBinder == nil`), step 2's create-and-start composition no-ops the claim and just persists the row, step 4's release is a no-op, and step 5 dispatches against the in-memory echo executor, so the in-process behavior the tier-3 suites pin is unchanged.

## 4. Edge cases and accepted failure modes

Each row names the observable outcome and the spec text that states it. The single-shot pod-binding sentence SPEC-1 stages is the spec basis for the release-and-rollback rows; the reader-facing documentation of the model on `docs/api/openai-completions.md` and the Open Responses reference page is a follow-on outside this proposal's staged edits.

(`spec/07_session-lifecycle.md:23`) |

## 5. Proposed changes

### SPEC-1. Document the built-in-adapter single-shot pod-binding compute model in §15

**Target:** `spec/15_external-api-surface.md`, the built-in adapter section immediately after the inventory table (after `spec/15_external-api-surface.md:583`, the `type: mcp` dedicated-endpoints paragraph), reusing the existing "implicit session record ... for audit and billing" framing that paragraph already uses.

**Rationale:** §15 declares the OpenAI-dialect adapters "Always available" (`spec/15_external-api-surface.md:566-567`) but carries no clause on how a built-in adapter request that dispatches a runtime turn acquires, uses, and releases compute, and §7.1's atomicity model (`spec/07_session-lifecycle.md:23`) is scoped to the REST and MCP session-lifecycle endpoints the adapters do not call. This is the confirmed spec gap and the only spec edit.

**Change (staged spec text).** Insert the following paragraph immediately after the `type: mcp` dedicated-endpoints paragraph (`spec/15_external-api-surface.md:583`):

```markdown
**Built-in adapter single-shot compute model.** A built-in adapter request
that dispatches a Lenny runtime turn (`OpenAICompletionsAdapter`,
`OpenResponsesAdapter`) runs an implicit single-shot session that claims a
warm pod, dispatches the turn, and releases the pod within one HTTP call.
The implicit session runs through the same [Section 15.2.1](#1521-restmcp-consistency-contract)
shared session-creation service as `POST /v1/sessions/start`, so the active-user,
quota, concurrency, admission-rate, policy-chain, and environment-admission gates
apply identically. The claim follows the [Section 7.1](07_session-lifecycle.md#71-normal-flow)
step-3 credential-availability pre-check and step-4 warm-pod claim atomicity,
and both roll back with no leaked pod or credential lease. A warm-pod or slot
claim, prepare, or launch failure returns a retryable `503 SESSION_CREATION_FAILED`
with a `Retry-After` header, and a credential-availability pre-check miss returns
`503 CREDENTIAL_POOL_EXHAUSTED` (POLICY) with no pod claimed and no `Retry-After`
header, each mapped into the adapter's native error envelope. On success,
completion, dispatch failure, or request timeout, the pod and its
[Section 4.9](04_system-components.md#49-credential-leasing-service) lease are
released synchronously, recording the completed or failed
[Section 6.2](06_warm-pod-model.md#62-pod-state-machine) terminal disposition,
before the response returns. `OpenResponsesAdapter` continuation
(`previous_response_id`) re-claims a fresh pod per request and does not retain a
pod bind across calls.
An implicit session record is created per request for audit and billing.
```

### CODE-1. Add a `CreateAndStartService` wrapper on `sessionserver.Server` and the translator consumer interface

**Target:** `pkg/gateway/sessionserver/service.go` (new exported method mirroring `CreateSessionService` at `:145`, plus a `RetryAfterSeconds` field on `ServiceError` at `:23`); `pkg/gateway/sessionserver/start.go` (add the three missing admission gates to the create-and-start path); new `pkg/gateway/environment/translator/singleshot.go` (consumer interface and its request/error types).

**Rationale:** The dispatch-ready create-and-start composition (`handleCreateAndStart` at `start.go:423`, running `createAndStartGates` plus `mintClaimStartPersist`) already claims, launches, and registers the binding, but has no service-layer wrapper the way `handleCreate` has `CreateSessionService`. `CreateSessionService` (create-only) claims but does not register the binding (Decision 2), so it cannot be reused directly. The create-and-start gate set is also incomplete relative to the two-step create path (Decision 3): it omits the §11.1 concurrency and admission-rate gates and the §10.6 environment-admission gate, which the external adapter surface must run to avoid failing open. The translator cannot import sessionserver (cycle via `runtimes.go:13`), so the dependency is inverted through a consumer interface.

**Change (staged description).**

1. Add `CreateAndStartService(ctx context.Context, tenantID string, req CreateSessionRequest) (CreateSessionResponse, *ServiceError)` to `sessionserver.Server`, mirroring the `CreateSessionService` recorder pattern (`service.go:145-195`): marshal `req`, build a synthetic `POST /v1/sessions/start` request against an in-process `httptest` recorder with the tenant stamped on `X-Lenny-Tenant-ID`, call `s.handleCreateAndStart(rec, httpReq)`, and decode the recorder into a `CreateSessionResponse` on `201`/`200` or a typed `ServiceError` from the error envelope otherwise. Do not mirror `CreateSessionService` exactly on the error path: `CreateSessionService` reads only `rec.Body`, but the `Retry-After` value lives only on the recorder response header (`start.go:176,210`), so `CreateAndStartService` must additionally read `rec.Header().Get("Retry-After")` and populate a new `RetryAfterSeconds int` field on `ServiceError` (added at `service.go:23`), leaving it zero when the header is absent (for example the `CREDENTIAL_POOL_EXHAUSTED` case, which sets no header). Reusing the canonical handler against a recorder keeps the two surfaces from drifting in gate order or error codes, the same rationale `CreateSessionService` documents (`service.go:134-142`). Carry a `// spec: §15.2.1 rule 1; §7.1 create-and-start atomicity` tie.
2. Complete the create-and-start admission stack (Decision 3): add `requireConcurrencyLimits`, `requireAdmissionRateLimit`, and `requireEnvironmentAdmission` (defined in `quota.go:169`, `admission_ratelimit.go:27`, and `runtimes.go:467`, called today only from `handleCreate` at `create.go:104,117,134`) to the create-and-start path. Because these three gates read the decoded `RuntimeRef`, `IsolationProfile`, `Pool`, and `Environment`, run them after `buildCreateAndStartRow` decodes the request and in the same relative order as `handleCreate` (concurrency and admission-rate before the policy chain, environment-admission after), before `mintClaimStartPersist` claims the pod. Preserving the §11.1 concurrency-and-rate-before-policy ordering requires the policy chain to run after the decode on this path as well, so `createAndStartGates` is restructured to run after the request is decoded rather than before it. This closes the fail-open on these three gates for `POST /v1/sessions/start` as well as for the adapter. Carry a `// spec: §11.1 (concurrency, admission-rate); §10.6 (environment-admission); §15.2.1 rule 1` tie.
3. In the new `pkg/gateway/environment/translator/singleshot.go`, define the consumer interface and its plain-Go request and error types, with no dependency on `sessionserver`:

   ```go
   // SingleShotBinder runs the shared §15.2.1 create-and-start service for
   // one built-in-adapter request: it applies the admission gates, claims a
   // warm pod, launches the runtime, and registers the pod binding, returning
   // the created session id. A pool or credential exhaustion, or an
   // admission-gate rejection, is returned as a *SingleShotError carrying the
   // HTTP status, error code, and Retry-After the adapter surfaces in its
   // native envelope. spec: §15 built-in adapter single-shot compute model.
   type SingleShotBinder interface {
       BindSingleShot(ctx context.Context, spec SingleShotSpec) (sessionID string, err error)
   }

   // SingleShotSpec carries the adapter-resolved fields the binder maps into
   // a sessionserver create-and-start request. It carries no lineage pointer:
   // the create-and-start reuse surface has no parent field and setting the
   // row's ParentSessionID would collide with the §8.2/§8.6 delegated-child
   // lease semantics (see Decision on Open Responses continuation), so
   ```

## 6. Non-goals

- **Conversation rehydration or turn replay for Open Responses `previous_response_id`.** Replaying prior turns onto a freshly-claimed pod is a separate concern from the pod-binding defect and is not built here. The single-shot create-and-start path also does not persist the `previous_response_id` lineage as the row's `ParentSessionID` (setting it would trigger the §8.2/§8.6 delegated-child lease semantics at `sessionserver.go:831`); persisting the lineage without those side effects is folded into the same continuity follow-on (see Open decisions).
- **A dedicated always-warm translator pool.** The claim reuses the shared §5 warm pool and its primitives (`podsession.Binder`, the credential pre-claim in `claimAtCreate`); a second pool is not introduced. This is the explicit answer to the T-STD.4 design question in favor of claim-per-request against the existing pool.
- **Retaining a pod bind across Open Responses continuation calls.** The bind is claim-per-request and released within one HTTP call.
- **Changing the MCP adapter or the `type: mcp` dedicated-endpoint path.** MCP sessions already claim a pod through the sessionserver create path, confirmed by T-STD.4 (the MCP tier-5 conformance tests pass end to end); this proposal touches only the two OpenAI-dialect translators.
- **The separate §4.9 llmproxy outbound credential-injection path.** That is a distinct subsystem (`llmproxy/translator.go`) and is not the `executor.Send` dispatch path these adapters use.
- **A bespoke claim-only method on `sessionserver.Server`.** Jumping straight to `claimAtCreate` would bypass the §15.2.1 admission gates `handleCreateAndStart` runs before the claim and fail open on an external surface. The adapter reuses the gate-running create-and-start service instead (see "Resolved in adversarial review").
- **Any backward-compatibility shim or dual mode.** The platform is pre-deployment; the adapter constructors and the sessionserver service surface change in place with every caller updated.

## 9. Resolved in adversarial review

Subsequent adversarial review rounds populate this section. The challenge-round revisions carried in the draft narrowed the proposal from its original form:

- **The bespoke claim-only method was dropped in favor of the shared gate-running create-and-start service.** The original CODE-1 added a new method on `sessionserver.Server` that wired `claimAtCreate` → `startOnPod` → `registerBinding` directly. Those are the internals of the create path, and calling them directly bypasses the §15.2.1 admission-gate stack that `handleCreateAndStart` runs before the claim (`createAndStartGates`, `start.go:453`: the active-user, tenant-state, tenant-classification, session-quota, and policy-chain gates, plus the concurrency, admission-rate, and environment-admission gates this proposal adds to the path per Decision 3). For an external, unauthenticated-capable surface that would be a §15.2.1-rule-1 drift and a fail-open regression. The proposal now routes the adapter through a `CreateAndStartService` wrapper over the canonical `handleCreateAndStart`, so the gates run exactly once through the shared service layer.
- **The reuse surface was corrected from create-only `CreateSessionService` to the create-and-start composition.** The challenge directed reuse of the existing `CreateSessionService` (`service.go:145`) on the premise that it registers the binding into `podRegistry`. On inspection, `CreateSessionService` drives the two-step `handleCreate`, which claims the pod but defers `registerBinding`/`podRegistry.Put` (`start.go:788,2501`) and the runtime launch to `/finalize` and `/start` (`finalize.go:345`), so a session created through it alone still fails `exec.Send` with `is not bound to a pod`. The dispatch-ready surface is `handleCreateAndStart` (`start.go:423`), which runs the gates, claims, launches, and registers in one call. The proposal adds a `CreateAndStartService` wrapper mirroring the `CreateSessionService` pattern rather than reusing the create-only wrapper.
- **The test scope was narrowed to the tier-5 un-skip plus a focused tier-2 component test.** The original TEST plan enumerated separate new tier-8 chaos and tier-9 security suites. Those would re-exercise the reused sessionserver claim, rollback, binder, and credential primitives, which this proposal reuses unchanged and which already carry tier-9 credential, lease, and isolation coverage in the session-lifecycle path, and the two adapters already have end-to-end tier-4 cross-tenant coverage. The scope is the tier-5 conformance un-skip and the tier-2 component tests covering the bind-dispatch-release lifecycle, the release-on-failure and timeout exits, the two-code exhaustion mapping, and the admission-gate denial.

## 10. Open decisions for review

- **Open Responses continuity substance and lineage persistence.** With the pod-binding fix a `previous_response_id` continuation re-claims a fresh pod but still does not replay the parent's turns, and the single-shot create-and-start path does not persist the lineage as the row's `ParentSessionID` (threading it would trip the §8.2/§8.6 delegated-child lease semantics at `sessionserver.go:831`, so `GET /v1/responses/{id}` echoes an empty `previous_response_id`). `SupportsSessionContinuity: true` (`open_responses.go:30`) is therefore declared true but substantively empty. Options: (a) rehydrate the conversation onto the freshly-claimed pod and persist the lineage through a parent field that does not trigger the delegated-child lease suppression; (b) leave `SupportsSessionContinuity` true and file both lineage persistence and rehydration as a bounded follow-on; or (c) reconcile the capability to false until both exist. Recommended: (b), scoping this proposal to the pod-binding defect that blocks all requests.
- **Pool-exhaustion error surface in the OpenAI envelope.** Is `503` with `Retry-After` (mirroring the §7.1 `SESSION_CREATION_FAILED` taxonomy) the right mapping, or is the OpenAI-idiomatic `429 rate_limit_exceeded` preferred for OpenAI-client compatibility? Recommended: `503` with `Retry-After` to match the platform-wide §7.1 taxonomy, with the code named in SPEC-1.
