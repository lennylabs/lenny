# Proposal: Complete §7.2 path 6 across a real cluster — the §6.2 pod-release sweep, the §4.7 adapter `ready_for_input` signal and 30s delivery timeout, §10.1 `ForwardMessage` cross-replica forwarding, and MCP `send_message` delivery-field threading

- **Status:** Verified (2026-07-23). Converged after 4 adversarial review rounds (5 findings fixed); awaiting sign-off.
- **Date:** 2026-07-23.
- **Scope:** A bundled follow-up to proposal 0055, which built the §7.2 path-6 pod-held atomic resume-and-deliver on the coordinating replica for the in-process echo executor. Four pieces remain to make path 6 correct across a real, horizontally-scaled cluster, and this proposal stages all four. **Piece 1 (§6.2 pod-release sweep):** a `sweepSuspended` pass in the watchdog checkpoints the workspace, releases a held pod after `maxSuspendedPodHoldSeconds`, clears the pod binding, keeps the session `suspended` (podless), and produces the two declared-but-producerless counters, plus the podless-versus-pod-held branch in `Classify`/`resumeHeldPod`. **Piece 2 (§4.7 `ready_for_input` + 30s timeout + real-pod in-place resume):** a wire form for the runtime-readiness signal and a bounded consumption receipt, then the readiness-gated real-pod resume-and-deliver in the executor. **Piece 3 (§10.1 `ForwardMessage`):** a gateway-internal gRPC service so a non-coordinator replica forwards a `delivery: "immediate"` message to the session's coordinator, falling back to `queued` when the coordinator is unreachable, including the coordination-identity-to-endpoint resolution the forward needs. **Piece 4 (MCP delivery-field threading):** a `delivery` enum on the `lenny/send_message` tool input schema and the shared resume-and-deliver service entry point both REST and MCP invoke. Pieces 2 and 3 require spec edits (§15.4.1 plus the adapter JSONL schema; §10.1 plus a new gateway-internal proto service and the §13.2/`charts/` NetworkPolicy peer that admits the gateway-to-gateway flow). Pieces 1 and 4 require no spec edit (§6.2 and §15.4.1/§15.2.1 are complete for them). This closes T-JRN.13, T-JRN.14, T-JRN.15, and T-JRN.16 (`TEST-GAPS.md`), and the tier-5 real-pod half of T-JRN.1.

This document stages the proposed spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off. The staged spec edits land through the proposal pipeline before the code that depends on them.

## 1. Problem

Proposal 0055 built the §7.2 path-6 pod-held atomic resume-and-deliver on the coordinating replica for the in-process echo executor. The router gained `ActionResumeAndDeliver` (`pkg/gateway/session/messagerouting/messagerouting.go`, returned for a `suspended` target carrying `delivery: "immediate"`); the REST handler runs the coordinator-side resume-and-deliver on that action (`pkg/gateway/sessionserver/messages.go`); and `resumeHeldPod` (`pkg/gateway/sessionserver/start.go`) performs a single `store.Update` guarded on `session.StateSuspended`. Its own doc comment defers two pieces: the pod-held/podless distinction (to the §6.2 sweep) and the real-pod adapter-resume signal (to §4.7).

Four pieces remain to make path 6 correct across a real, horizontally-scaled cluster.

### 1.1 Piece 1: the §6.2 pod-release sweep is unbuilt (T-JRN.13, Medium, OPEN, `TEST-GAPS.md:11956`)

No `sweepSuspended` pass exists in the watchdog. The two counters `lenny_session_pod_released_during_suspension_total` and `lenny_session_suspension_checkpoint_failed_total` are declared (`pkg/observability/metrics/catalog.go:292-293`) with no producer. `MaxSuspendedPodHoldSeconds` is defined and defaulted to 900 (`pkg/gateway/runtime/watchdog/watchdog.go:199-204,251-252`, default at `:134-141`) but is consumed by no sweep. §6.2 fully specifies the behavior (`spec/06_warm-pod-model.md:215-219,280`): on the timer firing, checkpoint the workspace; on checkpoint success release the pod back to the pool, clear the session's pod binding, emit `session.pod_released_during_suspension`, and keep the session in `suspended` (podless) with no state change; on checkpoint failure emit `session.suspension_checkpoint_failed` and retry on the next 60s evaluation interval. The watchdog ticker runs at `DefaultTickInterval` (5s, `watchdog.go:166-168`), not 60s, so the checkpoint-failure retry must be gated to 60s independently of the 5s tick rather than re-attempted on every tick.

The sweep must also be scoped to the coordinating replica. The watchdog runs on every gateway replica: it is started unconditionally (`go w.wd.Run(...)`, `cmd/lenny-gateway/workers.go:101`) and is not under the §12.5 leader election, which gates only the gateway-singleton background sweeps (`cmd/lenny-gateway/flags.go:1024`). The `List` the sweep runs selects every session for a tenant filtered by state alone, with no coordinator filter (`pkg/gateway/runtime/watchdog/watchdog.go:611`). The checkpoint the sweep must run first is coordinator-only: the checkpointer resolves the session's pod through its in-memory `Registry` and returns `ErrNoBinding` when this replica does not coordinate the session (`pkg/gateway/checkpoint/checkpointer/checkpointer.go:33,371,424-426`), and §7.2 requires the pod-side resume operations to run on the session's coordinating gateway replica (`spec/07_session-lifecycle.md:330`). Treating any checkpoint non-success as the §6.2 checkpoint-failure branch would make every non-coordinating replica emit a spurious `session.suspension_checkpoint_failed` event and increment the failure counter for every past-cap suspended session once per 60s, and would re-attempt the coordinator-only checkpoint from the other replicas, amplifying load on the MinIO checkpoint store the 60s gate exists to protect. The existing terminal-sweep pattern is safe across replicas only because `PodExecutor.Release` no-ops on a `Registry` miss (`pkg/gateway/session/executor/pod.go:313-315`); the new checkpoint step has no such graceful non-coordinator no-op, so the sweep must skip a row it does not coordinate rather than count it as a checkpoint failure. `sweepSuspended` therefore acts only on rows this replica coordinates (it holds the session's in-memory pod binding), and distinguishes `ErrNoBinding` from a genuine checkpoint failure. No spec edit is needed for Piece 1.

Because no sweep releases a suspended pod today, every `suspended` row is pod-held in the currently reachable state set, which is why 0055 gated `resumeHeldPod` and the router on `session.StateSuspended` alone. Once the sweep can produce a podless-suspended row, `Classify`/`resumeHeldPod` must distinguish the pod-held row from the podless row and route the podless case to `resume_pending`/`queued` per §7.2 line 328 (`spec/07_session-lifecycle.md:328`) and §6.2:280.

### 1.2 Piece 2: the §4.7 `ready_for_input` signal has no wire form (T-JRN.14, Medium, OPEN, `TEST-GAPS.md:11964`)

The routing semantics are fully specified. §7.2 path 2 (`spec/07_session-lifecycle.md:320`) requires `delivered` only after confirmed stdin consumption within the configurable delivery timeout (default 30 seconds), falling through to `queued` on timeout. The `ready_for_input` normative definition (`spec/07_session-lifecycle.md:322`) requires the adapter to emit it only when all tool calls have settled and the runtime is reading stdin. The pod-held branch of path 6 (`spec/07_session-lifecycle.md:327`) delivers once the runtime reports `ready_for_input`. §15.4.1 (`spec/15_external-api-surface.md:1726`) commits the same 30s-timeout fall-through to `queued`.

The wire contract does not exist. `grep -rn ready_for_input schemas/` returns nothing. `ready_for_input` and the stdin-consumption confirmation are §15.4.1 stdin/stdout channel concepts. (The "Surface readiness status to gateway" line at `spec/04_system-components.md:326` is a §4.6.1 Warm Pool Controller responsibility about surfacing pod warm-readiness through the CRD status subresource. It is unrelated to the runtime `ready_for_input` stdin signal, so it is not the missing wire contract and needs no edit.) The §15.4.1 delivery-semantics text already commits `delivered` "once the runtime confirms stdin consumption within the delivery timeout" and `queued` delivery "when the runtime next enters `ready_for_input`" (`spec/15_external-api-surface.md:1726-1727`), yet the outbound (agent→adapter, stdout) message table lists only `response`, `tool_call`, `heartbeat_ack`, `status`, and `set_tracing_context` (`spec/15_external-api-surface.md:1456-1464`), and the JSONL frame union has no `ready_for_input` or consumption-ack frame (`schemas/lenny-adapter-jsonl.schema.json:10-18`). `SendMessageResponse` is empty (`schemas/lenny-adapter.proto:955`), but the unary `Adapter.SendMessage` RPC is not on the executor's delivery path: `Client.SendMessage` (`pkg/gateway/runtime/adapterclient/client.go:404-412`) has no non-test caller, and its adapter handler is fire-and-forget (`pkg/adapter/session.go:175-204`). `PodExecutor.Send` delivers exclusively over the bidirectional Attach stream (`pkg/gateway/session/executor/pod.go:79-84`), whose `AttachResponse` frames carry opaque `bytes envelope_json` validated against `schemas/lenny-adapter-jsonl.schema.json` (`schemas/lenny-adapter.proto:971-975`). It blocks in `readAttachResponse` until a `response` envelope returns (`pkg/gateway/session/executor/pod.go:172-199`), so it couples the receipt to the entire runtime turn and has no bounded timeout, and cannot produce the spec's `delivered`-on-consumption-within-30s receipt. The `LifecycleChannel` RPC is a separate adapter↔runtime lifecycle surface validated by `schemas/lifecycle-events.schema.json`, whose fourteen-event union (`schemas/lifecycle-events.schema.json:6-21`) the proto :224 doc comment samples with `checkpoint_ready`, `interrupt_acknowledged`, `credentials_acknowledged`, and `deadline_approaching`; `PodExecutor` holds no handle to it (`pkg/gateway/session/executor/pod.go:49`). Readiness therefore rides the §15.4.1 Attach frames the executor already reads.

The committed spec is internally inconsistent about which actor produces the signals. §7.2 path 2 attributes them to the adapter ("the adapter acknowledges the write", `spec/07_session-lifecycle.md:320`; "The adapter MUST emit `ready_for_input`", `:322`), while the path-6 pod-held branch says "the runtime reports `ready_for_input`" (`:327`). The adapter owns the agent's stdin pipe and mediates `tool_call`/`tool_result` correlation, so it already holds the inputs to compute both `ready_for_input` (conditions a and b at `:322`) and a per-message `delivered` receipt from the runtime's next post-delivery stdout frame. The spec edit must reconcile the actor before it adds any frame, rather than re-home the adapter's signals as runtime-emitted stdout frames alongside contradictory prose. A spec edit is required.

### 1.3 Piece 3: §10.1 defines no `ForwardMessage` RPC (T-JRN.15, Medium, OPEN, `TEST-GAPS.md:11972`)

The routing behavior is committed. §7.2 path 6 (`spec/07_session-lifecycle.md:330`) requires a non-coordinator replica to forward a `delivery: "immediate"` message to the session's coordinator over the internal gRPC `ForwardMessage` RPC, falling back to `queued` when the coordinator is unreachable, and points to §10.1. §18.19 (`spec/18_build-sequence.md:357`) lists `ForwardMessage` as a build item.

§10.1 defines no such RPC, and no gateway-to-gateway gRPC service exists. `ForwardMessage` appears only as prose and code comments. The by-session coordinator lookup the forward needs already exists: `leasestore.Store.Get(ctx, tenantID, sessionID)` returns `Lease.Holder` (`pkg/gateway/storage/leasestore/leasestore.go:73-74,182-206`), the coordinating replica's coordination id. That id is not a routable endpoint: `Holder` is whatever is passed to `Acquire` as the replica id, which is `resolveReplicaID()` = the `LENNY_REPLICA_ID` override or `hostname-<random hex>` (`cmd/lenny-gateway/main.go:1014-1018`). The same value is stamped as the OTel `service.instance.id`, an observability label rather than a network locator, and its random suffix breaks any pod-name-to-Endpoints join. There is no existing surface that maps this id to a gateway endpoint. A spec edit to §10.1 plus a new internal proto service is required, and the edit must define how a lease `Holder` resolves to a routable gateway endpoint.

### 1.4 Piece 4: MCP `lenny/send_message` cannot express `delivery: "immediate"` (T-JRN.16, Low, OPEN, `TEST-GAPS.md:11980`)

`mcptools_register.go:356` hard-codes `immediate=false` in its `Classify` call, and `sendMessageInputSchema` (`pkg/gateway/mcpfabric/mcptools/mcptools.go`) declares no `delivery` field, so an inter-session `delivery: "immediate"` message can never select `ActionResumeAndDeliver` (`messagerouting.go`, returned for suspended+immediate) and never reaches path 6. The REST handler already threads the real bool and handles `ActionResumeAndDeliver` (`pkg/gateway/sessionserver/messages.go`). §15.2.1 rule 1 (`spec/15_external-api-surface.md:1389`) requires REST and MCP operations that perform the same action to be semantically identical and to share a common service layer so the business logic is implemented exactly once. The current divergence — an `immediate` message behaves differently on the two surfaces — is a parity defect the spec forbids. The `delivery` enum and `INVALID_DELIVERY_VALUE` are already specified for the wire envelope (`spec/15_external-api-surface.md:1726`); only the MCP tool input schema is not separately pinned, and §15.2.1 rule 1 already covers the parity requirement, so at most a one-line clarification is needed.

## 2. Decisions

- **Bundle all four pieces in one proposal.** Two spec edits are staged: Piece 2 (§15.4.1 plus `schemas/lenny-adapter-jsonl.schema.json` for the `ready_for_input` and `message_consumed` outbound frames and the 30s-timeout fall-through to `queued`) and Piece 3 (§10.1 plus a new gateway-internal proto service defining `ForwardMessage` and the coordination-identity-to-endpoint resolution, plus the §13.2 NetworkPolicy row and `charts/` templates that admit the gateway-to-gateway flow). Pieces 1 and 4 need no spec edit.
- **The C-22 coordination surface is the checkpoint-capture mechanism rather than a pod-release drain.** `Binder.Release` (`pkg/gateway/podlifecycle/podsession/binder.go`) performs credential release, adapter shutdown, and drain but no checkpoint. C-22 (T-4.4.14, `TEST-GAPS.md:639`) is the §4.4/§4.6 eviction-checkpoint trigger, and proposal 0050 built only the capture side (`slot_id` on `CheckpointStart`). Piece 1's sweep checkpoints before releasing, using the C-22 capture entry point when it has landed, or driving `checkpoint.TriggerEviction`/the periodic checkpointer directly and flagging the entry point to the integrator when it has not. Piece 1 builds its own no-terminal-disposition release on `Binder.Release`. There is no shared drain primitive with C-22 to duplicate.
- **Piece 3 reuses the existing by-session coordinator lookup and adds the endpoint-resolution surface the lookup lacks.** `leasestore.Store.Get` returns `Lease.Holder`, an opaque coordination id, so the by-session lookup is reused but is not itself the discovery surface. Piece 3's §10.1 edit defines how a `Holder` resolves to a routable gateway endpoint (either a stable, routable per-replica coordination identity, or a §10.1 peer directory keyed by `Holder`), and Piece 3's code implements whichever the spec edit lands. The `coordlease` mirror package and its `ListHeldByReplica` are not the discovery surface.
- **Piece 1's release primitive is a new variant no current caller exercises.** It releases the pod (`Binder.Release`) and clears `PodAssignment`/`PoolRef` while keeping the session in `suspended` (podless), without a terminal disposition and without tearing down the session row. The only current `Binder.Release`/`PodExecutor.Release` callers drain to a terminal disposition and end the session.
- **The watchdog reaches the release primitive through an optional hook on the already-injected `TerminalHook` rather than a new struct field or constructor signature.** The watchdog already discovers optional side-effect hooks by type-asserting its injected `TerminalHook` (`AwaitingClientActionEntryNotifier`, `RetryAttemptNotifier`, `SessionExpiryNotifier`, `ExpiryWarningNotifier` at `pkg/gateway/runtime/watchdog/watchdog.go:329-387`), and `AwaitingClientActionEntryNotifier` already proves that pattern covers a non-terminal transition. Piece 1 defines a `SuspendedPodReleaser` optional hook discovered the same way, so no new struct field, no `WithX` builder, and no `New(...)` signature change is added. The `WithTerminalHook(sessionSrv)` wiring already supplies the concrete object, and that server already performs executor release in its completion path.
- **`sweepSuspended` acts only on rows the running replica coordinates.** The watchdog runs on every replica (`cmd/lenny-gateway/workers.go:101`, outside the §12.5 leader election at `cmd/lenny-gateway/flags.go:1024`) and lists every suspended row for a tenant with no coordinator filter (`watchdog.go:611`), but the checkpoint the sweep runs first resolves the pod through the coordinator-only in-memory `Registry` and returns `ErrNoBinding` off the coordinating replica (`checkpointer.go:33,371,424-426`). §7.2 requires the pod-side operations on the coordinating replica (`spec/07:330`). The sweep gates on the local pod binding and treats `ErrNoBinding` as a skip rather than a §6.2 checkpoint failure, so only the coordinating replica emits `session.suspension_checkpoint_failed`, increments the failure counter, and re-attempts against MinIO. This mirrors the existing cross-replica-safe terminal sweep, whose `PodExecutor.Release` no-ops on a `Registry` miss (`pod.go:313-315`). The alternative of routing the checkpoint-and-release to the coordinator (the way Piece 3 routes delivery) is rejected as a larger surface: the coordinating replica already holds the binding the checkpoint needs, so skipping the non-coordinated rows is the minimal change and reuses the established watchdog-runs-everywhere pattern.
- **The podless resume path reuses existing machinery.** A podless-suspended row routes a `delivery: "immediate"` message to `resume_pending` with a `queued` receipt, then the existing `resume_pending → resuming → running` sweeps and the `resumeOnPod` fresh-pod-claim plus checkpoint-restore take over. `resumeHeldPod` and the router gain a pod-held (non-empty binding) versus podless (released) predicate. The new Classify/`resumeHeldPod` work is branch selection rather than new resume logic.
- **Piece 1 corrects the existing `MaxSuspendedPodHoldSeconds` doc, rather than adding a parallel config field.** The field already exists (`watchdog.go:134-141,199-204`) and `spec/11:239` links `maxSuspendedPodHoldSeconds` to §6.2, but its code doc comment misattributes it to "§11.3 line 233". The sweep uses this field as the deploy-wide ceiling and resolves the effective per-session cap as `min(deployment_value, tenant_value)` through an `effectiveMaxSuspendedPodHold` resolver, mirroring the idle and resume-window resolvers, per §6.2 (`spec/06:216`, "The most restrictive wins"). The doc comment is corrected to the §6.2 semantics (the session stays `suspended`, podless; it does not transition to `expired`).
- **Piece 2 reconciles the readiness/consumption actor before adding any wire form, and adds only the frame the reconciliation lands.** The committed spec attributes both signals to the adapter ("the adapter acknowledges the write" at `spec/07_session-lifecycle.md:320`; "The adapter MUST emit `ready_for_input`" at `:322`), while `:327` says "the runtime reports `ready_for_input`". P2-SPEC-1 reconciles that inconsistency as a prerequisite. If the committed adapter-emitted model stands, readiness is covered as an adapter→gateway signal on the existing surface and no agent→adapter stdout JSONL frame is added, which keeps a Basic-level runtime (stdin/stdout only, no lifecycle channel) conformant. If the model is intentionally changed to runtime-emitted, the re-attribution of `:320`/`:322` is the staged edit rather than a silent stdout-frame addition alongside contradictory prose. When a stdout frame is the reconciled home, it is a `$def` on the §15.4.1 Attach frame union the executor already reads (`readAttachResponse`, `pkg/gateway/session/executor/pod.go:172-199`), validated by `schemas/lenny-adapter-jsonl.schema.json` (`schemas/lenny-adapter.proto:971-975`), with no proto message change. The already-committed delivered-within-30s / fall-through-to-queued rule (`spec/15:1726`, `spec/07:320,324`) is not restated in a new paragraph. A `message_consumed` by-id frame is added only if the per-message `delivered` receipt provably cannot be derived from signals the adapter already sees, since the adapter owns the stdin pipe and can observe the runtime's next post-delivery stdout frame on `AttachResponse`. The held-pod resume is a `ready_for_input`-gated stdin write over the existing Attach stream; no new adapter resume RPC is staged, and the existing adapter `Resume` RPC (replacement-pod checkpoint-restore) is not conflated with in-place resume.
- **Piece 4 threads the delivery field and routes both surfaces through one shared resume-and-deliver service entry point.** `resumeHeldPod` is an unexported method on `sessionserver.Server`; the MCP tools run through a `deps` struct whose only delivery surface is `deps.Executor.Send`, so MCP cannot call it and must not duplicate the resume branch. Both REST and MCP invoke a single shared resume-and-deliver service entry point, per §15.2.1 rule 1's requirement that the logic be implemented exactly once.
- **Build sequence.** Land the two spec edits first, then the two spec-complete pieces (1 and 4), then the two spec-gap pieces (2 and 3), so the distributed-correctness work builds on committed wire contracts. Piece 1 is gated on the integrator landing C-14 (0055) first and coordinating with C-22's checkpoint surface.

## 3. Piece 1: the §6.2 pod-release-during-suspension sweep

The watchdog runs a per-tenant sweep loop that already carries `sweepResumePending` and `sweepResuming` passes over the session store, each of which lists by state, compares a budget against `now.Sub(UpdatedAt)`, and applies a state mutator inside `store.Update`. Piece 1 adds a `sweepSuspended` pass modeled on that structure.

The effective hold cap is `min(deployment_value, tenant_value)` per §6.2 (`spec/06_warm-pod-model.md:216`, "The most restrictive wins") and §11.3's config table (`spec/11:239`, "deploy + tenant, most restrictive wins"). `w.cfg.MaxSuspendedPodHoldSeconds` is the deploy-wide platform ceiling only, so the sweep resolves the effective cap per session through a resolver, mirroring `sweepIdle`'s `idleResolver.EffectiveMaxIdleSeconds` and `sweepResumePending`'s `effectiveMaxResumeWindow`. Unlike `sweepResumePending`/`sweepResuming`, whose `store.Update` transitions the row out of the swept state, the suspended-hold predicate is anchored on `SuspendedAt` (`pkg/gateway/session/sessionstore/sessionstore.go:68`), stamped once on suspend-entry, rather than on `UpdatedAt`. `UpdatedAt` strictly advances on every successful `store.Update` (`pkg/gateway/session/sessionstore/pgstore/pgstore.go:396-398`, "clamped to the prior value + 1µs"), and because a checkpoint-failure retry writes a no-state-change `store.Update` that leaves the row `suspended`, reading `UpdatedAt` would reset the primary predicate to ~0 on every failure and defer re-selection by a whole hold window. `SuspendedAt` is not moved by those later Updates, so the row stays selectable each tick and the secondary 60s gate governs the retry cadence.

The sweep is scoped to the coordinating replica. The watchdog runs on every replica and lists every suspended row for a tenant with no coordinator filter (`watchdog.go:611`), but the checkpoint step is coordinator-only: the checkpointer resolves the pod through its in-memory `Registry` and returns `ErrNoBinding` on a replica that does not coordinate the session, before any MinIO upload (`checkpointer.go:424-426`, the `Registry.Get` miss short-circuits ahead of `driveCheckpoint`). The sweep treats `ErrNoBinding` as a skip: a row this replica does not coordinate produces no event, no counter increment, no MinIO work, and no retry stamp, so only the coordinating replica performs the checkpoint-and-release per §7.2 (`spec/07_session-lifecycle.md:330`). Because `ErrNoBinding` is returned from the `Registry` miss alone, the skip needs no new watchdog dependency; a replica that does hold the binding proceeds to the release. For each `suspended` row whose `now.Sub(SuspendedAt) >= effectiveMaxSuspendedPodHold(row, w.cfg.MaxSuspendedPodHoldSeconds)` and that still holds a pod (non-empty `PodAssignment`/`PoolRef`), the sweep runs the following, where step 1's checkpoint determines coordination and skips a non-coordinated row via `ErrNoBinding`:

1. Checkpoints the workspace through the C-22 checkpoint-capture entry point (or `checkpoint.TriggerEviction`/the periodic checkpointer directly when C-22 has not landed, flagged to the integrator). A returned `ErrNoBinding` means this replica does not coordinate the session, so the row is skipped without a failure event, counter increment, or retry stamp rather than entering the checkpoint-failure branch below.
2. On checkpoint success, calls the release primitive (the `SuspendedPodReleaser` hook), which first claims release exclusivity in a single `store.Update` mutator that re-checks `row.State == StateSuspended`, captures the pod binding, clears `PodAssignment` and `PoolRef`, and sets a release-in-progress/podless marker, all while leaving the state unchanged. Only when that guarded transition commits does the primitive call `Binder.Release` (or `ReleaseSlot` for slotted pools) on the captured binding with a non-terminal disposition to return the pod to the pool. Claiming the row before the irreversible release closes the double-release race with a concurrent terminal path. The sweep increments `lenny_session_pod_released_during_suspension_total` and emits `session.pod_released_during_suspension`.
3. On a genuine checkpoint failure (a checkpoint error other than `ErrNoBinding`, on the coordinating replica), increments `lenny_session_suspension_checkpoint_failed_total`, emits `session.suspension_checkpoint_failed`, does not release, and stamps a per-row last-suspension-checkpoint-attempt timestamp into a dedicated field the primary `SuspendedAt` predicate does not read, through a no-state-change `store.Update`. The retry is gated on that dedicated field: the row is re-selected for a retry only once `now.Sub(that timestamp) >= 60s`, so the retry fires on the §6.2 60s evaluation interval rather than on every 5s tick. Because the primary predicate reads `SuspendedAt` and not the `UpdatedAt` the failure Update advances, the row stays past its hold cap and the 60s gate alone governs the retry cadence.

The release is fail-closed: the guarded `store.Update` runs before `Binder.Release`, so if the row is no longer `suspended` when the mutator runs (a concurrent cancel, expiry, or cascade), the mutator claims nothing, the primitive does not call `Binder.Release`, and the row is left in its terminal state whose own completion path owns the pod drain. The pod is never released twice, because exactly one of the sweep's guarded claim and the terminal path's claim wins.

Once the sweep can produce a podless-suspended row, that row is reachable by the router. `Classify` and `resumeHeldPod` gain a pod-held-versus-podless predicate: a pod-held row (non-empty binding) keeps `ActionResumeAndDeliver`/`delivered`; a podless row (released) selects a `resume_pending` routing with a `queued` receipt, feeding the existing `resume_pending → resuming → running` machinery, where `resumeOnPod` does the fresh-pod claim and checkpoint restore. The branch keys on an explicit released marker set by the release primitive rather than on raw `PodAssignment` emptiness, because the `--dev-mode` gateway builds no pod binder and its suspended rows carry an empty `PodAssignment` while still holding the in-process executor.

## 4. Piece 2: the §4.7 `ready_for_input` signal, the 30s timeout, and real-pod in-place resume

### 4.1 Wire form

P2-SPEC-1 reconciles the readiness/consumption actor as a prerequisite before staging any frame. §15.4.1 already commits the readiness gate and the stdin-consumption confirmation (`spec/15_external-api-surface.md:1726-1727`), but §7.2 attributes the signals to the adapter (`spec/07_session-lifecycle.md:320,322`) while line 327 says the runtime, and that must be settled first.

If the committed adapter-emitted model stands, readiness is an adapter→gateway signal on the existing surface and no agent→adapter stdout JSONL frame is added; the executor observes readiness on the Attach stream it already reads (`readAttachResponse`, `pkg/gateway/session/executor/pod.go:172-199`). A Basic-level runtime speaks only stdin/stdout and opens no lifecycle channel, so requiring it to emit a stdout readiness frame would make it non-conformant, which is why readiness stays adapter-derived under this branch. If the model is intentionally changed to runtime-emitted, the re-attribution of `spec/07:320,322` is the staged edit, and only then does a `ready_for_input` outbound `$def` enter the §15.4.1 frame union (`schemas/lenny-adapter-jsonl.schema.json:10-18`, validated against the opaque `envelope_json` `AttachResponse` already carries at `schemas/lenny-adapter.proto:971-975`, so no proto message change).

A per-message `message_consumed` frame is added only if the `delivered`-on-consumption receipt provably cannot be derived from signals the adapter already sees: the adapter owns the stdin pipe and observes the runtime's next post-delivery stdout frame on `AttachResponse`, so it can produce the receipt without a new by-id runtime-emitted frame and without touching every runtime SDK. The unary `Adapter.SendMessage` RPC and its `SendMessageResponse` are off the executor's delivery path in any case (`Client.SendMessage` has no non-test caller, `pkg/gateway/runtime/adapterclient/client.go:404-412`), so the receipt is not placed there. Under either branch the net new wire surface is at most a single readiness signal rather than two frames plus an SDK-wide emission requirement, and the already-committed delivered-within-30s / fall-through-to-queued rule (`spec/15:1726`, `spec/07:320,324`) is not restated in a new §15.4.1 paragraph.

### 4.2 Executor and real-pod resume

`PodExecutor.Send` blocks in `readAttachResponse` until a `response` envelope returns and has no bounded timeout, so it cannot emit a prompt `delivered` receipt on stdin consumption within 30 seconds: a runtime whose turn exceeds 30 seconds would still have consumed the message, yet a naive `Send`-with-deadline would wrongly report `queued`. The new consumption-receipt surface decouples the consumption ack from the whole turn, so the executor can return `delivered` on confirmed consumption within the timeout and fall through to `queued` on timeout.

The Executor interface gains a readiness-gated delivery with a timeout parameter. The real held-pod resume is a `ready_for_input`-gated stdin write over the existing Attach stream, and how the executor observes readiness and consumption follows which frames the P2-SPEC-1 reconciliation lands. Under the runtime-emitted branch the executor observes the `ready_for_input` frame on the Attach stream, writes the message, then reads the `message_consumed` frame that confirms stdin consumption. Under the committed adapter-emitted branch no such stdout frame exists (`readAttachResponse` drops any non-`response` envelope, `pkg/gateway/session/executor/pod.go:194-197`); the adapter derives readiness and the per-message consumption receipt and surfaces both to the gateway over the existing adapter→gateway surface, and the executor gates delivery on that signal instead of on a new stdout frame. Both branches return `delivered` on confirmed consumption within the timeout and `queued` on timeout. No new adapter resume RPC is staged. The existing adapter `Resume` RPC (`pkg/gateway/runtime/adapterclient/client.go:674`) is the replacement-pod checkpoint-restore counterpart of `StartSession` and is not used for in-place resume. If an interrupted-but-held runtime does not naturally reach `ready_for_input`, that is closed in the §15.4.1 spec edit rather than by inventing a resume-handshake RPC in code.

`resumeHeldPod` (`pkg/gateway/sessionserver/start.go`), which today only writes state for the echo executor, drives the real-pod in-place resume-and-deliver against a still-held pod. For the always-ready in-process executor the readiness gate is a construction no-op.

## 5. Piece 3: the §10.1 `ForwardMessage` RPC and coordinator discovery

A non-coordinator replica cannot forward a `delivery: "immediate"` message today; the handler assumes it is the coordinator. Piece 3 adds a gateway-internal gRPC service with a `ForwardMessage` RPC: the request carries the tenant id, session id, the message batch, the caller's authenticated identity and tenant, and the coordination generation; the response carries the delivery receipt (`delivered` or `queued`) or a typed unreachable error the caller maps to the `queued` fallback so the message is not silently dropped. The service uses the §10.3 mTLS PKI and interacts with generation fencing so a stale forward is rejected.

This is the first gateway-replica-to-gateway-replica direct network flow in the platform. Existing cross-replica coordination goes through Redis and Postgres leases and the Redis event bus, and the `lenny-system` namespace runs default-deny (`charts/lenny/templates/system-network-policies.yaml:14`). The §13.2 Gateway row admits no gateway peer on either side, and the rendered `allow-gateway-egress` policy carries `to` peers only for adapter, token-service, pgbouncer, redis, minio, kube-api, and dns, with no gateway-component `to` peer (`charts/lenny/templates/system-network-policies.yaml:536-620`). mTLS is an application-layer control and does not open an L3/L4 hole, so without a NetworkPolicy peer the default-deny drops every `ForwardMessage` dial before the TLS handshake and the synchronous `delivered` path is unreachable in a horizontally-scaled cluster. Piece 3 therefore also stages the §13.2 Gateway-row entry and the `charts/` gateway-to-gateway peer clauses that admit the flow on the new port.

The forward's coordinator lookup reuses `leasestore.Store.Get`, which returns `Lease.Holder`. Because `Holder` is an opaque coordination id rather than a routable endpoint, the §10.1 edit defines the resolution from `Holder` to a gateway endpoint. Two options are open (see §10): redefine the §10.1 coordination identity to a stable, routable per-replica endpoint so `Holder` is directly dialable, or add a §10.1 peer directory keyed by `Holder` that maps it to a gateway endpoint. Piece 3's code implements whichever the spec edit lands; the resolution is a genuinely new surface rather than a code-only one-liner over the existing lookup.

## 6. Piece 4: MCP `send_message` delivery-field threading

`sendMessageInputSchema` gains a closed `delivery` enum property (`queued`|`immediate`) validated with the existing `INVALID_DELIVERY_VALUE` semantics. `mcptools_register.go` reads the field and passes the real bool to `Classify`, replacing the literal `false`. Both REST and MCP route the `ActionResumeAndDeliver` outcome through one shared resume-and-deliver service entry point, so the resume-and-deliver logic is single-sourced per §15.2.1 rule 1. The MCP path selects `delivered` versus `queued` from the outcome rather than a hard-coded status, failing closed to `queued` exactly as REST does.

It first claims release exclusivity in a single `store.Update` mutator that re-checks `row.State == session.StateSuspended`, captures the pod binding into a local, clears `PodAssignment` and `PoolRef`, sets an explicit podless/released marker, and leaves the state unchanged. Only if that guarded claim commits does it then call `Binder.Release` (or `ReleaseSlot` for slotted pools) on the captured binding with a non-terminal disposition to return the pod to the warm pool. Ordering the guarded claim before the irreversible release is what makes it fail-closed: if the row is no longer suspended when the mutator runs (a concurrent cancel, expiry, or cascade whose terminal completion path itself drains the pod per §6.2), the claim fails, no release is issued, and the terminal path is the sole releaser. The primitive does not emit the `session.pod_released_during_suspension` structured event; the sweep (P1-C2) is the single writer of that event and emits it once, after the `SuspendedPodReleaser` hook returns success, alongside the `lenny_session_pod_released_during_suspension_total` increment. §6.2 defines exactly one event per successful release (`spec/06:219`), so colocating the event with the metric in the sweep prevents a double emission. Do not duplicate the checkpoint drain; the sweep checkpoints first. `// spec: 6.2`.
