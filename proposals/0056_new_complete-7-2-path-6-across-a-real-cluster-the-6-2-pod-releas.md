# Proposal: Complete §7.2 path 6 across a real cluster: the §6.2 pod-release sweep, the §4.7 adapter `ready_for_input` signal and 30s delivery timeout, async shared-inbox `immediate` delivery (retiring the §10.1 `ForwardMessage` design), MCP `send_message` delivery-field threading, and the durable session inbox as the default for correct message delivery behind a load balancer

- **Status:** Verified (2026-07-24). Converged after 5 adversarial review rounds (6 findings fixed); awaiting sign-off.
- **Date:** 2026-07-23.
- **Scope:** A bundled follow-up to proposal 0055, which built the §7.2 path-6 pod-held atomic resume-and-deliver on the coordinating replica for the in-process echo executor. Five pieces remain to make path 6 correct across a real, horizontally-scaled cluster, and this proposal stages all five. **Piece 1 (§6.2 pod-release sweep):** a `sweepSuspended` pass in the watchdog checkpoints the workspace, releases a held pod after `maxSuspendedPodHoldSeconds`, clears the pod binding, keeps the session `suspended` (podless), and produces the two declared-but-producerless counters, plus the podless-versus-pod-held branch in `Classify`/`resumeHeldPod`. **Piece 2 (§4.7 `ready_for_input` + 30s timeout + real-pod in-place resume):** a wire form for the runtime-readiness signal and a bounded consumption receipt, then the readiness-gated real-pod resume-and-deliver in the executor. **Piece 3 (async shared-inbox `immediate` delivery):** redefine `delivery: "immediate"` so any replica durably enqueues the message to the shared session inbox with immediate priority and the session's coordinating replica delivers it as soon as possible, interrupting a busy runtime (§7.2 path 4) or resuming a suspended session (§7.2 path 6) rather than waiting for the next natural `ready_for_input`. This retires the §10.1 `ForwardMessage` gateway-to-gateway RPC design entirely: the durable session inbox (`RedisInbox`, selected by the existing `messaging.durableInbox: true` deployment flag) is Redis-backed shared state that crosses replicas, so no replica-to-replica networking is introduced. The synchronous receipt is `queued` (durably buffered under the durable inbox, never dropped); the delivery outcome carries the existing `queued` observability rather than a new positive per-message consumption event (§5). **Piece 4 (MCP delivery-field threading):** a `delivery` enum on the `lenny/send_message` tool input schema and the shared resume-and-deliver service entry point both REST and MCP invoke. **Piece 5 (durable inbox as the default):** flip `messaging.durableInbox` to default `true` so message delivery is correct out of the box behind any load balancer, emit a startup warning when it is disabled, and document in §7.2, §10.1, and the operator guide that the in-memory-inbox opt-out requires a single replica or sticky load-balancer routing. This closes the gap between §10.1's any-replica correctness rule and the coordinator-local message path, and makes Piece 3's cross-replica `immediate` delivery correct in the default configuration. Pieces 2, 3, and 5 require spec edits (Piece 2: §15.4.1 plus the adapter JSONL schema; Piece 3: §7.2 and §15.4.1, redefining `immediate` as async shared-inbox delivery and retiring the §10.1 `ForwardMessage` forwarding requirement; Piece 5: §7.2 and §10.1, flipping the default and stating the load-balancer requirement for the opt-out). Pieces 1 and 4 require no spec edit (§6.2 and §15.2.1 are complete for them). This closes T-JRN.13, T-JRN.14, T-JRN.15, and T-JRN.16 (`TEST-GAPS.md`), and the tier-5 real-pod half of T-JRN.1.

This document stages the proposed spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off. The staged spec edits land through the proposal pipeline before the code that depends on them.

## 1. Problem

Proposal 0055 built the §7.2 path-6 pod-held atomic resume-and-deliver on the coordinating replica for the in-process echo executor. The router gained `ActionResumeAndDeliver` (`pkg/gateway/session/messagerouting/messagerouting.go`, returned for a `suspended` target carrying `delivery: "immediate"`); the REST handler runs the coordinator-side resume-and-deliver on that action (`pkg/gateway/sessionserver/messages.go`); and `resumeHeldPod` (`pkg/gateway/sessionserver/start.go`) performs a single `store.Update` guarded on `session.StateSuspended`. Its own doc comment defers two pieces: the pod-held/podless distinction (to the §6.2 sweep) and the real-pod adapter-resume signal (to §4.7).

0055 built `immediate` as a synchronous request-scoped operation on the coordinating replica: the handler resumes-and-delivers in the request and returns a synchronous `delivered` receipt, and the tier-4 test `TestInteractiveIterationInterruptThenResumeAndDeliver` asserts that synchronous outcome. Piece 3 redefines `immediate` as an asynchronous shared-inbox operation (any replica enqueues; the coordinator delivers as soon as possible), so this proposal reconciles 0055: the synchronous receipt becomes `queued` (the message is durably buffered), the delivery outcome carries the existing `queued` observability rather than a positive per-message consumption event (§5), and the `resumeHeldPod` resume-and-deliver mechanism is retained but is triggered by the coordinator's inbox drain rather than the synchronous handler. The 0055 tier-4 test is updated to the async contract.

Five pieces remain to make path 6 correct across a real, horizontally-scaled cluster.

### 1.1 Piece 1: the §6.2 pod-release sweep is unbuilt (T-JRN.13, Medium, OPEN, `TEST-GAPS.md:11956`)

No `sweepSuspended` pass exists in the watchdog. The two counters `lenny_session_pod_released_during_suspension_total` and `lenny_session_suspension_checkpoint_failed_total` are declared (`pkg/observability/metrics/catalog.go:292-293`) with no producer. `MaxSuspendedPodHoldSeconds` is defined and defaulted to 900 (`pkg/gateway/runtime/watchdog/watchdog.go:199-204,251-252`, default at `:134-141`) but is consumed by no sweep. §6.2 fully specifies the behavior (`spec/06_warm-pod-model.md:215-219,280`): on the timer firing, checkpoint the workspace; on checkpoint success release the pod back to the pool, clear the session's pod binding, emit `session.pod_released_during_suspension`, and keep the session in `suspended` (podless) with no state change; on checkpoint failure emit `session.suspension_checkpoint_failed` and retry on the next 60s evaluation interval. The watchdog ticker runs at `DefaultTickInterval` (5s, `watchdog.go:166-168`), not 60s, so the checkpoint-failure retry must be gated to 60s independently of the 5s tick rather than re-attempted on every tick.

The sweep must also be scoped to the coordinating replica. The watchdog runs on every gateway replica: it is started unconditionally (`go w.wd.Run(...)`, `cmd/lenny-gateway/workers.go:101`) and is not under the §12.5 leader election, which gates only the gateway-singleton background sweeps (`cmd/lenny-gateway/flags.go:1024`). The `List` the sweep runs selects every session for a tenant filtered by state alone, with no coordinator filter (`pkg/gateway/runtime/watchdog/watchdog.go:611`). The checkpoint the sweep must run first is coordinator-only: the checkpointer resolves the session's pod through its in-memory `Registry` and returns `ErrNoBinding` when this replica does not coordinate the session (`pkg/gateway/checkpoint/checkpointer/checkpointer.go:33,371,424-426`), and §7.2 requires the pod-side resume operations to run on the session's coordinating gateway replica (`spec/07_session-lifecycle.md:330`). Treating any checkpoint non-success as the §6.2 checkpoint-failure branch would make every non-coordinating replica emit a spurious `session.suspension_checkpoint_failed` event and increment the failure counter for every past-cap suspended session once per 60s, and would re-attempt the coordinator-only checkpoint from the other replicas, amplifying load on the MinIO checkpoint store the 60s gate exists to protect. The existing terminal-sweep pattern is safe across replicas only because `PodExecutor.Release` no-ops on a `Registry` miss (`pkg/gateway/session/executor/pod.go:313-315`); the new checkpoint step has no such graceful non-coordinator no-op, so the sweep must skip a row it does not coordinate rather than count it as a checkpoint failure. `sweepSuspended` therefore acts only on rows this replica coordinates (it holds the session's in-memory pod binding), and distinguishes `ErrNoBinding` from a genuine checkpoint failure. No spec edit is needed for Piece 1.

Because no sweep releases a suspended pod today, every `suspended` row is pod-held in the currently reachable state set, which is why 0055 gated `resumeHeldPod` and the router on `session.StateSuspended` alone. Once the sweep can produce a podless-suspended row, `Classify`/`resumeHeldPod` must distinguish the pod-held row from the podless row and route the podless case to `resume_pending`/`queued` per §7.2 line 328 (`spec/07_session-lifecycle.md:328`) and §6.2:280.

### 1.2 Piece 2: the §4.7 `ready_for_input` signal has no wire form (T-JRN.14, Medium, OPEN, `TEST-GAPS.md:11964`)

The routing semantics are fully specified. §7.2 path 2 (`spec/07_session-lifecycle.md:320`) requires `delivered` only after confirmed stdin consumption within the configurable delivery timeout (default 30 seconds), falling through to `queued` on timeout. The `ready_for_input` normative definition (`spec/07_session-lifecycle.md:322`) requires the adapter to emit it only when all tool calls have settled and the runtime is reading stdin. The pod-held branch of path 6 (`spec/07_session-lifecycle.md:327`) delivers once the runtime reports `ready_for_input`. §15.4.1 (`spec/15_external-api-surface.md:1726`) commits the same 30s-timeout fall-through to `queued`.

The wire contract does not exist. `grep -rn ready_for_input schemas/` returns nothing. `ready_for_input` and the stdin-consumption confirmation are §15.4.1 stdin/stdout channel concepts. (The "Surface readiness status to gateway" line at `spec/04_system-components.md:326` is a §4.6.1 Warm Pool Controller responsibility about surfacing pod warm-readiness through the CRD status subresource. It is unrelated to the runtime `ready_for_input` stdin signal, so it is not the missing wire contract and needs no edit.) The §15.4.1 delivery-semantics text already commits `delivered` "once the runtime confirms stdin consumption within the delivery timeout" and `queued` delivery "when the runtime next enters `ready_for_input`" (`spec/15_external-api-surface.md:1726-1727`), yet the outbound (agent→adapter, stdout) message table lists only `response`, `tool_call`, `heartbeat_ack`, `status`, and `set_tracing_context` (`spec/15_external-api-surface.md:1456-1464`), and the JSONL frame union has no `ready_for_input` or consumption-ack frame (`schemas/lenny-adapter-jsonl.schema.json:10-18`). `SendMessageResponse` is empty (`schemas/lenny-adapter.proto:955`), but the unary `Adapter.SendMessage` RPC is not on the executor's delivery path: `Client.SendMessage` (`pkg/gateway/runtime/adapterclient/client.go:404-412`) has no non-test caller, and its adapter handler is fire-and-forget (`pkg/adapter/session.go:175-204`). `PodExecutor.Send` delivers exclusively over the bidirectional Attach stream (`pkg/gateway/session/executor/pod.go:79-84`), whose `AttachResponse` frames carry opaque `bytes envelope_json` validated against `schemas/lenny-adapter-jsonl.schema.json` (`schemas/lenny-adapter.proto:971-975`). It blocks in `readAttachResponse` until a `response` envelope returns (`pkg/gateway/session/executor/pod.go:172-199`), so it couples the receipt to the entire runtime turn and has no bounded timeout, and cannot produce the spec's `delivered`-on-consumption-within-30s receipt. The `LifecycleChannel` RPC is a separate adapter↔runtime lifecycle surface validated by `schemas/lifecycle-events.schema.json`, whose fourteen-event union (`schemas/lifecycle-events.schema.json:6-21`) the proto :224 doc comment samples with `checkpoint_ready`, `interrupt_acknowledged`, `credentials_acknowledged`, and `deadline_approaching`; `PodExecutor` holds no handle to it (`pkg/gateway/session/executor/pod.go:49`). Readiness therefore rides the §15.4.1 Attach frames the executor already reads.

The committed spec is internally inconsistent about which actor produces the signals. §7.2 path 2 attributes them to the adapter ("the adapter acknowledges the write", `spec/07_session-lifecycle.md:320`; "The adapter MUST emit `ready_for_input`", `:322`), while the path-6 pod-held branch says "the runtime reports `ready_for_input`" (`:327`). The adapter owns the agent's stdin pipe and mediates `tool_call`/`tool_result` correlation, so it already holds the inputs to compute both `ready_for_input` (conditions a and b at `:322`) and a per-message `delivered` receipt from the runtime's next post-delivery stdout frame. The spec edit must reconcile the actor before it adds any frame, rather than re-home the adapter's signals as runtime-emitted stdout frames alongside contradictory prose. A spec edit is required.

### 1.3 Piece 3: `immediate` is specified as synchronous cross-replica forwarding (T-JRN.15, Medium, OPEN, `TEST-GAPS.md:11972`)

The committed spec makes `immediate` a synchronous, request-scoped operation. §7.2 path 6 (`spec/07_session-lifecycle.md:330`) requires a non-coordinator replica to forward a `delivery: "immediate"` message to the session's coordinator over an internal gRPC `ForwardMessage` RPC, so the receiving replica can return a synchronous `delivered` receipt, falling back to `queued` only when the coordinator is unreachable. That synchronous forwarding requirement is why §7.2:330 points to a §10.1 `ForwardMessage` RPC, which §10.1 does not define and no gateway-to-gateway gRPC service implements; §18.19 (`spec/18_build-sequence.md:357`) lists it as a build item.

Building `ForwardMessage` would introduce the first gateway-replica-to-gateway-replica direct network flow in the platform: a new internal gRPC service, mTLS between replicas over the §10.3 PKI, a §13.2/`charts/` NetworkPolicy hole in the `lenny-system` default-deny, and a coordinator-endpoint resolution surface the opaque lease `Holder` (`resolveReplicaID()` = `LENNY_REPLICA_ID` or `hostname-<random hex>`, an OTel `service.instance.id` rather than a routable locator) does not provide. That surface exists to preserve one property: a synchronous `delivered` receipt on the request that landed on the wrong replica.

The synchronous receipt is not essential to what `immediate` is for. The mechanically distinguishing behavior of `immediate` versus `queued` is that the runtime is reached without waiting for the next natural `ready_for_input`: a busy runtime is interrupted mid-turn (§7.2 path 4), and a suspended session is resumed (§7.2 path 6), rather than the message waiting in the inbox for the runtime's next pause. That interrupt is a coordinator-local action (the coordinator holds the pod connection and the `Interrupt` RPC, `schemas/lenny-adapter.proto:110`). The cross-replica part (getting the message from the receiving replica to the coordinator) does not need a synchronous RPC when the deployment runs the durable session inbox: `RedisInbox` (`pkg/gateway/session/sessioninbox/sessioninbox.go:189`, selected only when `messaging.durableInbox: true`, `cmd/lenny-gateway/stores.go:2266-2269`) is a Redis-backed FIFO list any replica can write to, so the receiving replica enqueues and the coordinating replica drains the same shared list. Under the default in-memory inbox (`MemoryInbox`, `messaging.durableInbox: false`) the session inbox is a per-coordinator in-memory map (`sessioninbox.go:110-120`) that does not cross replicas, and the implemented gateway already elides all cross-replica coordinator routing (`pkg/gateway/sessionserver/messages.go:240-243`); `ForwardMessage`, the spec's cross-replica mechanism, was never built, so multi-replica message routing under the memory inbox is already absent. This proposal therefore makes cross-replica `immediate` delivery correct under the durable inbox and states the memory-inbox limitation, redefining `immediate` as durable shared-inbox delivery with immediate priority and a coordinator-driven interrupt, retiring the `ForwardMessage` design rather than reintroducing a gateway-to-gateway RPC. A spec edit to §7.2 and §15.4.1 is required to redefine `immediate` and remove the `ForwardMessage` forwarding requirement; no §10.1 RPC, gateway-internal gRPC service, or §13.2/`charts/` NetworkPolicy change is introduced.

### 1.4 Piece 4: MCP `lenny/send_message` cannot express `delivery: "immediate"` (T-JRN.16, Low, OPEN, `TEST-GAPS.md:11980`)

`mcptools_register.go:356` hard-codes `immediate=false` in its `Classify` call, and `sendMessageInputSchema` (`pkg/gateway/mcpfabric/mcptools/mcptools.go`) declares no `delivery` field, so an inter-session `delivery: "immediate"` message can never select `ActionResumeAndDeliver` (`messagerouting.go`, returned for suspended+immediate) and never reaches path 6. The REST handler already threads the real bool and handles `ActionResumeAndDeliver` (`pkg/gateway/sessionserver/messages.go`). §15.2.1 rule 1 (`spec/15_external-api-surface.md:1389`) requires REST and MCP operations that perform the same action to be semantically identical and to share a common service layer so the business logic is implemented exactly once. The current divergence (an `immediate` message behaves differently on the two surfaces) is a parity defect the spec forbids. The `delivery` enum and `INVALID_DELIVERY_VALUE` are already specified for the wire envelope (`spec/15_external-api-surface.md:1726`); only the MCP tool input schema is not separately pinned, and §15.2.1 rule 1 already covers the parity requirement, so at most a one-line clarification is needed.

### 1.5 Piece 5: the default in-memory inbox breaks message delivery behind a non-sticky load balancer

§10.1's correctness rule (`spec/10_gateway-internals.md:22`) states that "Sticky routing is an optimization. A client can reconnect to any replica and resume." That any-replica rule holds for the stream and reconnect path: a client resumes an SSE or attach stream from any replica through the Postgres session store and event replay (`isCoordinatorHandoffReattach`, `pkg/gateway/sessionserver/events.go:245`). It does not hold for the message-delivery path under the default in-memory inbox. The session inbox in the default mode (`messaging.durableInbox: false`, `cmd/lenny-gateway/flags.go:848`) is a per-coordinator in-memory map (`MemoryInbox`, `pkg/gateway/session/sessioninbox/sessioninbox.go:110-120`), and the implemented gateway elides all cross-replica coordinator routing (`pkg/gateway/sessionserver/messages.go:240-243`). So a message that a non-sticky load balancer routes to a replica other than the session's coordinator has no path to the coordinator, and this holds for a `queued` message as much as an `immediate` one. The spec states the any-replica rule for streams but never states the load-balancer requirement that the message-delivery path carries, so a deployer who reads §10.1, runs a round-robin load balancer, and keeps the default inbox has messages that intermittently fail to reach the session.

Piece 5 closes this by making the durable inbox the default, so message delivery is any-replica-correct out of the box and consistent with §10.1:22, and by warning and documenting the requirement for the in-memory-inbox opt-out. This is also the configuration Piece 3 relies on for cross-replica `immediate` delivery, so flipping the default makes Piece 3 correct in the shipped default rather than only under an opt-in flag. The durable inbox is already implemented (`RedisInbox`) and its selection is gated on Redis being present (`cmd/lenny-gateway/stores.go:2266`), and Redis is already a required gateway dependency (coordination lease, routing cache, event bus), so defaulting it on introduces no new dependency and no new code path, only a different backing store for the same enqueue-and-drain logic.

## 2. Decisions

- **Bundle all five pieces in one proposal.** Three spec edits are staged: Piece 2 (§15.4.1 plus `schemas/lenny-adapter-jsonl.schema.json` for the `ready_for_input` and `message_consumed` outbound frames and the 30s-timeout fall-through to `queued`), Piece 3 (§7.2 and §15.4.1, redefining `immediate` as async shared-inbox delivery with a coordinator-driven interrupt and retiring the §10.1 `ForwardMessage` forwarding requirement), and Piece 5 (§7.2 and §10.1, flipping the durable-inbox default and stating the load-balancer requirement for the in-memory opt-out). Pieces 1 and 4 need no spec edit.
- **The C-22 coordination surface is the checkpoint-capture mechanism rather than a pod-release drain.** `Binder.Release` (`pkg/gateway/podlifecycle/podsession/binder.go`) performs credential release, adapter shutdown, and drain but no checkpoint. C-22 (T-4.4.14, `TEST-GAPS.md:639`) is the §4.4/§4.6 eviction-checkpoint trigger, and proposal 0050 built only the capture side (`slot_id` on `CheckpointStart`). Piece 1's sweep checkpoints before releasing, using the C-22 capture entry point when it has landed, or driving `checkpoint.TriggerEviction`/the periodic checkpointer directly and flagging the entry point to the integrator when it has not. Piece 1 builds its own no-terminal-disposition release on `Binder.Release`. There is no shared drain primitive with C-22 to duplicate.
- **Piece 3 redefines `immediate` as async shared-inbox delivery with a coordinator-driven interrupt, retiring `ForwardMessage`.** Any replica that receives a `delivery: "immediate"` message writes it to the shared `RedisInbox` (`pkg/gateway/session/sessioninbox/sessioninbox.go:189`) flagged immediate-priority and returns a synchronous `queued` receipt (durably buffered under the durable inbox); the delivery outcome carries the existing `queued` observability rather than a positive per-message consumption event (§5). The session's coordinating replica, which owns the pod connection, processes an immediate-flagged message as soon as possible rather than at the next natural `ready_for_input`: it interrupts a busy runtime through the existing adapter `Interrupt` RPC (`schemas/lenny-adapter.proto:110`, the §7.2 path-4 mechanism) or resumes a suspended session (§7.2 path 6, reusing `resumeHeldPod` and Piece 1's podless branch). A notification on the existing cross-replica event bus (`pkg/gateway/storage/eventbus`) wakes the coordinator so delivery is prompt; a missed wake is recovered by the coordinator-side fallback below, so no synchronous coordinator reachability and no gateway-to-gateway RPC are needed. This retires the §10.1 `ForwardMessage` RPC, the new gateway-internal proto service, the §13.2/`charts/` NetworkPolicy peer, and the coordinator-endpoint-resolution surface, because the durable shared inbox carries the cross-replica part. The rejected alternative (build `ForwardMessage`) preserves a synchronous `delivered` receipt at the cost of the platform's first gateway-to-gateway network flow, mTLS peer, and NetworkPolicy hole; no `immediate` use case requires blocking the caller until consumption rather than returning a synchronous `queued` receipt and letting the client observe the outcome on the existing session event stream (§5).
- **Piece 3's cross-replica property requires the durable inbox, which Piece 5 makes the default.** The shared state the redesign relies on is the durable `RedisInbox`, selected by `messaging.durableInbox` (`cmd/lenny-gateway/stores.go:2266-2269`). Piece 5 flips that flag to default `true`, so cross-replica `immediate` delivery is correct in the shipped default configuration. Under the in-memory-inbox opt-out (`messaging.durableInbox: false`, `MemoryInbox`, `sessioninbox.go:110-120`) the session inbox is a per-coordinator in-memory map, so an `immediate` message that lands on a non-coordinating replica cannot reach the coordinator through the inbox. This is not a new drop: the implemented gateway already elides all cross-replica coordinator routing (`pkg/gateway/sessionserver/messages.go:240-243`) and `ForwardMessage` was never built, so multi-replica message routing under the memory inbox is already absent, for a `queued` message as much as an `immediate` one. Under the opt-out the operator is warned at startup (Piece 5) and must run a single replica or configure sticky load-balancer routing. `messaging.durableInbox` is an existing §7.2 deployment flag rather than a new mode or a tier-dependent code path: the same enqueue-and-drain code runs in both, and only the backing store differs.

- **Piece 5 defaults the durable inbox on and warns when it is disabled.** `messaging.durableInbox` flips from default `false` to default `true` (`cmd/lenny-gateway/flags.go:848`; the Helm values and the gateway-deployment flag render), so message delivery is any-replica-correct out of the box, consistent with §10.1:22's any-replica rule. The default only takes effect when Redis is present (the inbox selection is inside `if redisClient != nil`, `cmd/lenny-gateway/stores.go:2266`), so a dev or single-binary deployment without Redis is unaffected, and Redis is already a required gateway dependency, so no new dependency is introduced. When the operator sets `messaging.durableInbox: false`, the gateway emits a single startup `WARN` through `log/slog`: message delivery is coordinator-local under the in-memory inbox, so undelivered messages are lost on coordinator crash and a message a non-sticky load balancer routes to a non-coordinating replica cannot reach the session; the operator should enable the durable inbox or run a single replica or sticky load-balancer routing. The warning is emitted once at startup, never per message. The spec §7.2 mode labels and mode-selection guidance flip to name the durable inbox as the default and the in-memory inbox as the opt-out, and §10.1:22 is reconciled so the any-replica rule covers stream reconnection while message delivery additionally requires the durable inbox (default) or sticky routing.
- **A coordinator-side fallback sweep recovers a missed event-bus wake for a running or a suspended session.** The event bus is at-most-once and drops on a Redis pub/sub hiccup (`pkg/gateway/storage/eventbus/cloudevents.go:14`), so the wake is best-effort. No periodic drain delivers a buffered immediate message to a coordinated session today: the only `Inbox.Drain` callers are the `resume_pending` inbox-to-DLQ migration and the terminal drain (`pkg/gateway/session/sessioninbox/coordinator.go:121,201`), and `pkg/gateway/sessionserver/messages.go:606-608` is a comment ("its inbox drains on the next `ready_for_input`") rather than a running-session drain loop, so a running session has no inbox-drain-on-`ready_for_input` mechanism either. Piece 3 therefore folds an immediate-flag check into the coordinating replica's watchdog sweeps (P3-CODE): the coordinating replica's running-session sweep (`sweepIdle` lists `StateRunning`, `pkg/gateway/runtime/watchdog/watchdog.go:980,1007`) drives interrupt-and-deliver, and `sweepSuspended` drives resume-and-deliver. The sweep scans the rows it coordinates for an immediate-flagged inbox message and delivers it, bounding the missed-wake latency to the watchdog tick interval and never dropping the message. The fallback reads the shared durable inbox, so it holds under the same durable-inbox precondition.
- **`immediate`'s receipt becomes asynchronous, reconciling 0055.** 0055 returned a synchronous `delivered` receipt for a coordinator-side `immediate` message. Under the shared-inbox model the synchronous receipt is `queued` (durably buffered) and the delivery outcome carries the existing `queued` observability rather than a positive per-message consumption event (§5). The `resumeHeldPod` resume-and-deliver mechanism is retained but is triggered by the coordinator's inbox drain rather than the synchronous handler, and the 0055 tier-4 test `TestInteractiveIterationInterruptThenResumeAndDeliver` is updated to assert the async contract (`queued` synchronously, then the resume drives the `state_change` from `suspended` to `running` observable on the session event stream, confirmed by a follow-up state check showing the session `running`).
- **Piece 1's release primitive is a new variant no current caller exercises.** It releases the pod (`Binder.Release`) and clears `PodAssignment`/`PoolRef` while keeping the session in `suspended` (podless), without a terminal disposition and without tearing down the session row. The only current `Binder.Release`/`PodExecutor.Release` callers drain to a terminal disposition and end the session.
- **The watchdog reaches the release primitive through an optional hook on the already-injected `TerminalHook` rather than a new struct field or constructor signature.** The watchdog already discovers optional side-effect hooks by type-asserting its injected `TerminalHook` (`AwaitingClientActionEntryNotifier`, `RetryAttemptNotifier`, `SessionExpiryNotifier`, `ExpiryWarningNotifier` at `pkg/gateway/runtime/watchdog/watchdog.go:329-387`), and `AwaitingClientActionEntryNotifier` already proves that pattern covers a non-terminal transition. Piece 1 defines a `SuspendedPodReleaser` optional hook discovered the same way, so no new struct field, no `WithX` builder, and no `New(...)` signature change is added. The `WithTerminalHook(sessionSrv)` wiring already supplies the concrete object, and that server already performs executor release in its completion path.
- **`sweepSuspended` acts only on rows the running replica coordinates.** The watchdog runs on every replica (`cmd/lenny-gateway/workers.go:101`, outside the §12.5 leader election at `cmd/lenny-gateway/flags.go:1024`) and lists every suspended row for a tenant with no coordinator filter (`watchdog.go:611`), but the checkpoint the sweep runs first resolves the pod through the coordinator-only in-memory `Registry` and returns `ErrNoBinding` off the coordinating replica (`checkpointer.go:33,371,424-426`). §7.2 requires the pod-side operations on the coordinating replica (`spec/07:330`). The sweep gates on the local pod binding and treats `ErrNoBinding` as a skip rather than a §6.2 checkpoint failure, so only the coordinating replica emits `session.suspension_checkpoint_failed`, increments the failure counter, and re-attempts against MinIO. This mirrors the existing cross-replica-safe terminal sweep, whose `PodExecutor.Release` no-ops on a `Registry` miss (`pod.go:313-315`). The alternative of routing the checkpoint-and-release to the coordinator (the way Piece 3 routes delivery) is rejected as a larger surface: the coordinating replica already holds the binding the checkpoint needs, so skipping the non-coordinated rows is the minimal change and reuses the established watchdog-runs-everywhere pattern.
- **The podless resume path reuses existing machinery.** A podless-suspended row routes a `delivery: "immediate"` message to `resume_pending` with a `queued` receipt, then the existing `resume_pending → resuming → running` sweeps and the `resumeOnPod` fresh-pod-claim plus checkpoint-restore take over. `resumeHeldPod` and the router gain a pod-held (non-empty binding) versus podless (released) predicate. The new Classify/`resumeHeldPod` work is branch selection rather than new resume logic.
- **Piece 1 corrects the existing `MaxSuspendedPodHoldSeconds` doc, rather than adding a parallel config field.** The field already exists (`watchdog.go:134-141,199-204`) and `spec/11:239` links `maxSuspendedPodHoldSeconds` to §6.2, but its code doc comment misattributes it to "§11.3 line 233". The sweep uses this field as the deploy-wide ceiling and resolves the effective per-session cap as `min(deployment_value, tenant_value)` through an `effectiveMaxSuspendedPodHold` resolver, mirroring the idle and resume-window resolvers, per §6.2 (`spec/06:216`, "The most restrictive wins"). The doc comment is corrected to the §6.2 semantics (the session stays `suspended`, podless; it does not transition to `expired`).
- **Piece 2 reconciles the readiness/consumption actor before adding any wire form, and adds only the frame the reconciliation lands.** The committed spec attributes both signals to the adapter ("the adapter acknowledges the write" at `spec/07_session-lifecycle.md:320`; "The adapter MUST emit `ready_for_input`" at `:322`), while `:327` says "the runtime reports `ready_for_input`". P2-SPEC-1 reconciles that inconsistency as a prerequisite. If the committed adapter-emitted model stands, readiness is covered as an adapter→gateway signal on the existing surface and no agent→adapter stdout JSONL frame is added, which keeps a Basic-level runtime (stdin/stdout only, no lifecycle channel) conformant. If the model is intentionally changed to runtime-emitted, the re-attribution of `:320`/`:322` is the staged edit rather than a silent stdout-frame addition alongside contradictory prose. When a stdout frame is the reconciled home, it is a `$def` on the §15.4.1 Attach frame union the executor already reads (`readAttachResponse`, `pkg/gateway/session/executor/pod.go:172-199`), validated by `schemas/lenny-adapter-jsonl.schema.json` (`schemas/lenny-adapter.proto:971-975`), with no proto message change. The already-committed delivered-within-30s / fall-through-to-queued rule (`spec/15:1726`, `spec/07:320,324`) is not restated in a new paragraph. A `message_consumed` by-id frame is added only if the per-message `delivered` receipt provably cannot be derived from signals the adapter already sees, since the adapter owns the stdin pipe and can observe the runtime's next post-delivery stdout frame on `AttachResponse`. The held-pod resume is a `ready_for_input`-gated stdin write over the existing Attach stream; no new adapter resume RPC is staged, and the existing adapter `Resume` RPC (replacement-pod checkpoint-restore) is not conflated with in-place resume.
- **Piece 4 threads the delivery field and routes both surfaces through one shared resume-and-deliver service entry point.** `resumeHeldPod` is an unexported method on `sessionserver.Server`; the MCP tools run through a `deps` struct whose only delivery surface is `deps.Executor.Send`, so MCP cannot call it and must not duplicate the resume branch. Both REST and MCP invoke a single shared resume-and-deliver service entry point, per §15.2.1 rule 1's requirement that the logic be implemented exactly once.
- **Build sequence.** Land the two spec edits first, then the two spec-complete pieces (1 and 4), then the two spec-gap pieces (2 and 3), so the distributed-correctness work builds on committed wire contracts. Piece 1 is gated on the integrator landing C-14 (0055) first and coordinating with C-22's checkpoint surface.

## 3. Piece 1: the §6.2 pod-release-during-suspension sweep

The watchdog runs a per-tenant sweep loop that already carries `sweepResumePending` and `sweepResuming` passes over the session store, each of which lists by state, compares a budget against `now.Sub(UpdatedAt)`, and applies a state mutator inside `store.Update`. Piece 1 adds a `sweepSuspended` pass modeled on that structure.

The effective hold cap is `min(deployment_value, tenant_value)` per §6.2 (`spec/06_warm-pod-model.md:216`, "The most restrictive wins") and §11.3's config table (`spec/11:239`, "deploy + tenant, most restrictive wins"). `w.cfg.MaxSuspendedPodHoldSeconds` is the deploy-wide platform ceiling only, so the sweep resolves the effective cap per session through a resolver, mirroring `sweepIdle`'s `idleResolver.EffectiveMaxIdleSeconds` and `sweepResumePending`'s `effectiveMaxResumeWindow`. Unlike `sweepResumePending`/`sweepResuming`, whose `store.Update` transitions the row out of the swept state, the suspended-hold predicate is anchored on `SuspendedAt` (`pkg/gateway/session/sessionstore/sessionstore.go:68`), stamped once on suspend-entry, rather than on `UpdatedAt`. `UpdatedAt` strictly advances on every successful `store.Update` (`pkg/gateway/session/sessionstore/pgstore/pgstore.go:396-398`, "clamped to the prior value + 1µs"), and because a checkpoint-failure retry writes a no-state-change `store.Update` that leaves the row `suspended`, reading `UpdatedAt` would reset the primary predicate to ~0 on every failure and defer re-selection by a whole hold window. `SuspendedAt` is not moved by those later Updates, so the row stays selectable each tick and the secondary 60s gate governs the retry cadence.

The sweep is scoped to the coordinating replica. The watchdog runs on every replica and lists every suspended row for a tenant with no coordinator filter (`watchdog.go:611`), but the checkpoint step is coordinator-only: the checkpointer resolves the pod through its in-memory `Registry` and returns `ErrNoBinding` on a replica that does not coordinate the session, before any MinIO upload (`checkpointer.go:424-426`, the `Registry.Get` miss short-circuits ahead of `driveCheckpoint`). The sweep treats `ErrNoBinding` as a skip: a row this replica does not coordinate produces no event, no counter increment, no MinIO work, and no retry stamp, so only the coordinating replica performs the checkpoint-and-release per §7.2 (`spec/07_session-lifecycle.md:330`). Because `ErrNoBinding` is returned from the `Registry` miss alone, the skip needs no new watchdog dependency; a replica that does hold the binding proceeds to the release. For each `suspended` row whose `now.Sub(SuspendedAt) >= effectiveMaxSuspendedPodHold(row, w.cfg.MaxSuspendedPodHoldSeconds)` and that still holds a pod (non-empty `PodAssignment`/`PoolRef`), the sweep runs the following, where step 1's checkpoint determines coordination and skips a non-coordinated row via `ErrNoBinding`:

1. Checkpoints the workspace through the C-22 checkpoint-capture entry point (or `checkpoint.TriggerEviction`/the periodic checkpointer directly when C-22 has not landed, flagged to the integrator). A returned `ErrNoBinding` means this replica does not coordinate the session, so the row is skipped without a failure event, counter increment, or retry stamp rather than entering the checkpoint-failure branch below.
2. On checkpoint success, calls the release primitive (the `SuspendedPodReleaser` hook), which first claims release exclusivity in a single `store.Update` mutator that re-checks `row.State == StateSuspended`, captures the pod binding, clears `PodAssignment` and `PoolRef`, and sets a release-in-progress/podless marker, all while leaving the state unchanged. Only when that guarded transition commits does the primitive call `Binder.Release` (or `ReleaseSlot` for slotted pools) on the captured binding with a non-terminal disposition to return the pod to the pool. Claiming the row before the irreversible release closes the double-release race with a concurrent terminal path. The sweep increments `lenny_session_pod_released_during_suspension_total` and emits `session.pod_released_during_suspension`.
3. On a genuine checkpoint failure (a checkpoint error other than `ErrNoBinding`, on the coordinating replica), increments `lenny_session_suspension_checkpoint_failed_total`, emits `session.suspension_checkpoint_failed`, does not release, and stamps a per-row last-suspension-checkpoint-attempt timestamp into a dedicated field the primary `SuspendedAt` predicate does not read, through a no-state-change `store.Update`. The retry is gated on that dedicated field: the row is re-selected for a retry only once `now.Sub(that timestamp) >= 60s`, so the retry fires on the §6.2 60s evaluation interval rather than on every 5s tick. Because the primary predicate reads `SuspendedAt` and not the `UpdatedAt` the failure Update advances, the row stays past its hold cap and the 60s gate alone governs the retry cadence.

The release is fail-closed: the guarded `store.Update` runs before `Binder.Release`, so if the row is no longer `suspended` when the mutator runs (a concurrent cancel, expiry, or cascade), the mutator claims nothing, the primitive does not call `Binder.Release`, and the row is left in its terminal state whose own completion path owns the pod drain. The pod is never released twice, because exactly one of the sweep's guarded claim and the terminal path's claim wins.

Once the sweep can produce a podless-suspended row, the coordinator's inbox drain must distinguish it. Under Piece 3's async model, an immediate message to a suspended session is enqueued with a `queued` receipt on any replica; the coordinating replica's drain then branches on a pod-held-versus-podless predicate: a pod-held row (non-empty binding) runs `resumeHeldPod` resume-and-deliver in place, and a podless row (released) transitions to `resume_pending`, feeding the existing `resume_pending → resuming → running` machinery, where `resumeOnPod` does the fresh-pod claim and checkpoint restore. The branch keys on an explicit released marker set by the release primitive rather than on raw `PodAssignment` emptiness, because the `--dev-mode` gateway builds no pod binder and its suspended rows carry an empty `PodAssignment` while still holding the in-process executor.

## 4. Piece 2: the §4.7 `ready_for_input` signal, the 30s timeout, and real-pod in-place resume

### 4.1 Wire form

P2-SPEC-1 reconciles the readiness/consumption actor as a prerequisite before staging any frame. §15.4.1 already commits the readiness gate and the stdin-consumption confirmation (`spec/15_external-api-surface.md:1726-1727`), but §7.2 attributes the signals to the adapter (`spec/07_session-lifecycle.md:320,322`) while line 327 says the runtime, and that must be settled first.

If the committed adapter-emitted model stands, readiness is an adapter→gateway signal on the existing surface and no agent→adapter stdout JSONL frame is added; the executor observes readiness on the Attach stream it already reads (`readAttachResponse`, `pkg/gateway/session/executor/pod.go:172-199`). A Basic-level runtime speaks only stdin/stdout and opens no lifecycle channel, so requiring it to emit a stdout readiness frame would make it non-conformant, which is why readiness stays adapter-derived under this branch. If the model is intentionally changed to runtime-emitted, the re-attribution of `spec/07:320,322` is the staged edit, and only then does a `ready_for_input` outbound `$def` enter the §15.4.1 frame union (`schemas/lenny-adapter-jsonl.schema.json:10-18`, validated against the opaque `envelope_json` `AttachResponse` already carries at `schemas/lenny-adapter.proto:971-975`, so no proto message change).

A per-message `message_consumed` frame is added only if the `delivered`-on-consumption receipt provably cannot be derived from signals the adapter already sees: the adapter owns the stdin pipe and observes the runtime's next post-delivery stdout frame on `AttachResponse`, so it can produce the receipt without a new by-id runtime-emitted frame and without touching every runtime SDK. The unary `Adapter.SendMessage` RPC and its `SendMessageResponse` are off the executor's delivery path in any case (`Client.SendMessage` has no non-test caller, `pkg/gateway/runtime/adapterclient/client.go:404-412`), so the receipt is not placed there. Under either branch the net new wire surface is at most a single readiness signal rather than two frames plus an SDK-wide emission requirement, and the already-committed delivered-within-30s / fall-through-to-queued rule (`spec/15:1726`, `spec/07:320,324`) is not restated in a new §15.4.1 paragraph.

### 4.2 Executor and real-pod resume

`PodExecutor.Send` blocks in `readAttachResponse` until a `response` envelope returns and has no bounded timeout, so it cannot emit a prompt `delivered` receipt on stdin consumption within 30 seconds: a runtime whose turn exceeds 30 seconds would still have consumed the message, yet a naive `Send`-with-deadline would wrongly report `queued`. The new consumption-receipt surface decouples the consumption ack from the whole turn, so the executor can return `delivered` on confirmed consumption within the timeout and fall through to `queued` on timeout.

The Executor interface gains a readiness-gated delivery with a timeout parameter. The real held-pod resume is a `ready_for_input`-gated stdin write over the existing Attach stream, and how the executor observes readiness and consumption follows which frames the P2-SPEC-1 reconciliation lands. Under the runtime-emitted branch the executor observes the `ready_for_input` frame on the Attach stream, writes the message, then reads the `message_consumed` frame that confirms stdin consumption. Under the committed adapter-emitted branch no such stdout frame exists (`readAttachResponse` drops any non-`response` envelope, `pkg/gateway/session/executor/pod.go:194-197`); the adapter derives readiness and the per-message consumption receipt and surfaces both to the gateway over the existing adapter→gateway surface, and the executor gates delivery on that signal instead of on a new stdout frame. Both branches return `delivered` on confirmed consumption within the timeout and `queued` on timeout. No new adapter resume RPC is staged. The existing adapter `Resume` RPC (`pkg/gateway/runtime/adapterclient/client.go:674`) is the replacement-pod checkpoint-restore counterpart of `StartSession` and is not used for in-place resume. If an interrupted-but-held runtime does not naturally reach `ready_for_input`, that is closed in the §15.4.1 spec edit rather than by inventing a resume-handshake RPC in code.

`resumeHeldPod` (`pkg/gateway/sessionserver/start.go`), which today only writes state for the echo executor, drives the real-pod in-place resume-and-deliver against a still-held pod. For the always-ready in-process executor the readiness gate is a construction no-op.

## 5. Piece 3: async shared-inbox `immediate` delivery

Piece 3 redefines `delivery: "immediate"` so that no gateway-to-gateway networking is needed, and stages the §7.2/§15.4.1 spec edit that redefines it.

**Enqueue on any replica.** Any replica that receives a `delivery: "immediate"` message writes it to the session's shared inbox (`RedisInbox`, `pkg/gateway/session/sessioninbox/sessioninbox.go:189`) flagged immediate-priority, exactly as a `queued` message is buffered, and returns a synchronous `queued` receipt. Under the durable inbox (`messaging.durableInbox: true`) the inbox is Redis-backed shared state, so this crosses replicas with no replica-to-replica call and the message is durable and never silently dropped. Under the default in-memory inbox (`MemoryInbox`) the inbox is per-coordinator and does not cross replicas, which is why a horizontally-scaled deployment that requires cross-replica `immediate` delivery runs the durable inbox (§2). The message carries the caller's authenticated identity and tenant into the inbox record so the coordinator delivers under the right tenant.

**Deliver on the coordinator.** The session's coordinating replica (the lease `Holder`, which owns the pod connection) processes an immediate-flagged message as soon as possible rather than waiting for the next natural `ready_for_input`. No periodic drain delivers a buffered immediate message today (`pkg/gateway/sessionserver/messages.go:606-608` is a comment rather than a drain loop), so for both a running and a suspended session the immediate-flag path is driven by the event-bus wake and the coordinator-side fallback sweep (below). Three cases: (a) the runtime is idle at `ready_for_input`, so the coordinator delivers immediately; (b) the runtime is busy mid-turn (running with a tool call in flight), so the coordinator issues the existing adapter `Interrupt` (`schemas/lenny-adapter.proto:110`, `InterruptRequest`/`InterruptResponse` at `:1046`/`:1057`; the gateway waits for `interrupt_acknowledged` for a Full-level runtime, or proceeds after the in-flight stdin write for a Basic/Standard-level runtime, matching §7.2 path 4) and delivers as the runtime yields; (c) the session is `suspended`, so the immediate-flagged message triggers the coordinator's path-6 resume-and-deliver, reusing 0055's `resumeHeldPod` (pod-held) and Piece 1's podless-to-`resume_pending` branch. FIFO ordering within the inbox is preserved; immediate priority governs how promptly the coordinator drains rather than reordering ahead of already-buffered messages.

**Prompt cross-replica wake.** When an immediate message is enqueued for a session the receiving replica does not coordinate, the receiving replica publishes a notification on the existing cross-replica event bus (`pkg/gateway/storage/eventbus`) so the coordinator wakes and drains promptly, and so a suspended session's coordinator is woken to run resume-and-deliver. The event bus is keyed by tenant and topic (`Publish(ctx, tenantID, topic, event)`, `pkg/gateway/storage/eventbus/eventbus.go:172`) with a fixed topic set (`session_lifecycle`, `cloudevents.go:55-63`); the wake rides `TopicSessionLifecycle` carrying the target session as the event `Subject` (`session/{id}`), and each subscribed replica filters by that subject to recognize a session it coordinates. The bus is at-most-once and drops on a Redis pub/sub hiccup (`cloudevents.go:14`), so the wake is best-effort. A missed wake is recovered without loss by the coordinator-side fallback sweep (P3-CODE, folded into the coordinating replica's watchdog sweeps): its running-session sweep scans the running rows it coordinates for an immediate-flagged inbox message and drives interrupt-and-deliver, and `sweepSuspended` scans the suspended rows it coordinates and drives resume-and-deliver, bounding the latency to the watchdog tick interval. No synchronous coordinator reachability is required, which is the property that removes the need for a `ForwardMessage` RPC.

**Delivery outcome under the async model.** The synchronous receipt is `queued` and carries the existing `queued` delivery semantics: the message is durably buffered and delivered in FIFO order, and the sender is notified only on non-delivery, through the existing `message_expired` event on its session event stream (`spec/07:349`, `spec/15:1767`). No new positive per-message delivery or consumption event is added, and the closed `SessionEventKind` enum (`spec/15:315-323`) stays unchanged: it carries `state_change`, `output`, `elicitation`, `tool_use`, `error`, and `terminated` and no delivery/consumption kind, and extending it would require a `SessionEvent` schema version bump plus adapter-capability updates (`spec/15:544`) that the async model does not need. A client observes the effect of an `immediate` delivery through the session's existing event stream, namely the `state_change` from `suspended` to `running` when a suspended session is resumed (`spec/15:548`) and the runtime's subsequent `output`, exactly as it observes any other `queued` message. This is the receipt-semantics change from 0055's synchronous `delivered`: the async model drops the positive per-message confirmation and keeps the standard `queued` observability, reconciled in §1 and §2.

`ForwardMessage`, the gateway-internal gRPC service, the §13.2 Gateway-row NetworkPolicy peer, the `charts/` gateway-to-gateway clauses, the mTLS peer, and the `Holder`-to-endpoint resolution are all retired: none is built, because the durable shared inbox and the existing event bus carry the cross-replica part with no new network flow.

### 5.1 Piece 5: the durable inbox is the default, with a load-balancer warning for the in-memory opt-out

Piece 3's cross-replica correctness, and message delivery generally, hold only when the receiving replica can reach the session's coordinator. Under the in-memory inbox that requires the request to land on the coordinator, which a non-sticky load balancer does not guarantee. Piece 5 removes that footgun from the default configuration.

**Flip the default.** `messaging.durableInbox` flips from default `false` to default `true` (`cmd/lenny-gateway/flags.go:848`, the Helm values, and the gateway-deployment flag render), so the shipped default is the shared `RedisInbox` and message delivery is any-replica-correct. The flag is unchanged in shape; only its default and the label of which mode is "default" versus "opt-out" change. The durable inbox activates only when Redis is present (`cmd/lenny-gateway/stores.go:2266`), so a dev or single-binary deployment without Redis continues to run the in-memory inbox with no behavior change, and because Redis is already required for the coordination lease, routing cache, and event bus, defaulting the durable inbox on adds no new dependency.

**Warn when disabled.** When `messaging.durableInbox: false` is set, the gateway emits a single startup `WARN` in the in-memory-inbox branch (`stores.go`, the `else { NewMemoryInbox }` arm): message delivery is coordinator-local, so a message a non-sticky load balancer routes to a non-coordinating replica cannot reach the session and undelivered messages are lost on coordinator crash; the operator should enable `messaging.durableInbox` or run a single replica or sticky load-balancer routing. The warning is a startup log, emitted once, never per message. No metric is added, so no §16 inventory or `docs/reference/metrics.md` companion is required.

**Reconcile §10.1's correctness rule.** The §10.1:22 any-replica rule is clarified: it covers stream reconnection, where a client resumes an SSE or attach stream from any replica through the Postgres session store and event replay. Message delivery to a session additionally requires the request reach the session's coordinator, which the durable inbox satisfies (the default; shared Redis state any replica appends to and the coordinator drains) or, under the in-memory-inbox opt-out, sticky load-balancer routing satisfies. Sticky routing therefore stays an optimization for streams and becomes a requirement for message delivery under the in-memory inbox.

## 6. Piece 4: MCP `send_message` delivery-field threading

`sendMessageInputSchema` gains a closed `delivery` enum property (`queued`|`immediate`) validated with the existing `INVALID_DELIVERY_VALUE` semantics. `mcptools_register.go` reads the field and passes the real bool to `Classify`, replacing the literal `false`. Both REST and MCP route an `immediate` message through one shared enqueue-and-deliver service entry point (Piece 3's immediate-priority enqueue with the coordinator drain), so the logic is single-sourced per §15.2.1 rule 1. Under the async model both surfaces return a synchronous `queued` receipt on enqueue with the existing `queued` observability (§5), so the MCP path returns the same receipt as REST rather than a hard-coded status.
