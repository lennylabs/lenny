# Review log: Runtime SDKs assume one session per process

## Standing context

### Settled

- Owner decisions (gateway-runtime-comms-remediation.md section 10.3): one runtime lifetime contract; `session_start` and `session_end` ride CH-MSGSOCK rather than CH-RUNTIMEOPS; no runtime capability declaration for sequential sessions; no backward-compatibility shims. Do not reopen.
- Owner answers of 2026-10-03: Part B (SPEC-8, CODE-7, the nonce handshake) stays here; `session_start` omits `taskId` and the workspace path because both derive from `sessionId`; per-session platform and connector MCP connections, and the "MCP tools stop working for a later session" symptom, belong to proposal 0084; this proposal's spec steps land before 0087's and 0084's. Do not reopen.
- The first-session manifest-ordering defect (BUILD-GAPS F-4.7.26) belongs to draft proposal 0087's supervisor. Stage no fix here; state the dependency only.
- "Stream" in the §28.5.3 card means one session's logical stream multiplexed over the pod's one connection. The carrier is "the connection or loop" (sidecar connection, embedded runtime loop). Never write "stream" for the carrier (spec.1.fix-G1).

### Traps

- A `*spec-changes.md` glob also matches `*non-spec-changes.md`. Name the file in full when reading, grepping, or editing either one.
- Heartbeat escalation ends only that session's stream (pkg/adapter/heartbeat.go, attach.go hbHung case) and never closes the pod connection (§4.7.10 "No session's teardown, interrupt, or heartbeat escalation ... closes that connection"). §15.4.3 says a missed ack "ends the session"; keep the frame-writes table consistent with both.
