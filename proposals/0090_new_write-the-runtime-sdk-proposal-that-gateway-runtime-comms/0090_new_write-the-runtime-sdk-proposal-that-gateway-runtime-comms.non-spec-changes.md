# Non-spec changes: Runtime SDKs assume one session per process

## Design (implementation-facing)

The adapter gains a frame-writing helper pair over the existing `RuntimeProcess.WriteEnvelope` and an open sequence that every start runs, so it writes the SPEC-3 frames on the paths the SPEC-3 **Session frame writes.** table states, through one path, and the `RuntimeProcess` interface does not change (CODE-1). The developer-loop executor writes a minimal `session_start` for a child it spawns itself (CODE-2). The session-scoped `CH-RUNTIMEOPS` senders gain a session argument and `terminate` is deleted on the adapter side (CODE-3). The three SDKs keep per-session state keyed by `sessionId` and invoke the handler per session (CODE-4, CODE-5). The compliance harness plays the adapter's new side of the contract (CODE-6). Once the SDKs read the frame, the adapter stops writing the per-session manifest fields (CODE-8). Once every in-tree runtime that opens `CH-RUNTIMEOPS` writes `session_started`, the adapter waits for it in the open sequence and writes the session-scoped `CH-RUNTIMEOPS` frames only after it (CODE-9). Part B adds the connection handshake on both runtime listeners and the SDK client half (CODE-7).

Each deliverable updates, in the same commit, the existing tests its change breaks. TEST-1 holds the new cross-component tests. The wire rules are stated once in the spec text staged by SPEC-3 (`session_start` rules 1 to 3, `session_end` rules 1 to 3, `session_started` rules 1 to 5, **Session frame writes.**, **Session errors.**), SPEC-4, and SPEC-8; the deliverables below cite them.

## Staged code changes

### CODE-1 · Adapter session frames: the open sequence and the end write at every row of the SPEC-3 matrix

Targets: `pkg/adapter/sessionframes.go` (new), `pkg/adapter/session.go` (`StartSession`, `tearDownReclaimedSlot`), `pkg/adapter/resume.go` (`Resume`), `pkg/adapter/sdkwarm.go` (`ConfigureWorkspace`, `DemoteSDK`), `pkg/adapter/attach.go` (the protocol-frame filter), `pkg/adapter/manifest.go` (`ManifestLLM`, `manifestLLMFromPayload`), `pkg/adapter/server.go` (the per-`Server` `startId` counter on `Server`). `pkg/adapter/holdstate.go`, `pkg/adapter/runtimegeneration.go`, `pkg/adapter/lifecycle.go`, and `pkg/adapter/heartbeat.go` do not change, because their rows write no frame. Each item below implements one or more rows of SPEC-3 **Session frame writes.**

1. `sessionframes.go` defines:
   - `sessionStartFrame`, with JSON members `type`, `sessionId`, `startId`, `credentialsPath` (`omitempty`), `experimentContext`, `tracingContext`, and `llm`. The last three are written as `null` when the session has none. The members reuse `manifestExperimentContext`, `s.sessionCredentialsPath`, and `s.manifestLLM`, after deleting `ManifestLLM.BaseURL` and its assignment in `manifestLLMFromPayload` (the proxy URL stays in the credential file only, §4.7.11 item 4). `writeSessionStart` sets `credentialsPath` only when the session's registry entry, read under `s.mu`, records `assigned`, and omits it otherwise.
   - `sessionEndFrame`, with JSON members `type` and `sessionId`.
   - `(s *Server) writeSessionStart(sessionID, startID string, in manifestInputs) error` and `(s *Server) writeSessionEnd(sessionID string)`. Both write through `s.Runtime.WriteEnvelope(sessionID, …)`. `writeSessionEnd` logs a failed write with `slog.Debug("session_end_write_failed", "slot_id", …, "error", …)` and returns nothing. Both write nothing when `s.RuntimeKind == RuntimeKindMCP`.
   - `(s *Server) openRuntimeSession(ctx context.Context, sessionID string, claim slotClaim, in manifestInputs, guardHeld bool) (confirmed bool, err error)`, the open sequence:
     a. Unless `guardHeld`, acquire the slot's per-slot guard with `lockSlotGuard(ctx, sessionID)` and release it on return. When `lockSlotGuard` reports `false` (the acquisition outlived `ctx`), return an error and write nothing.
     b. Under `s.mu`, compare `s.slots[sessionID]` with `claim.entry` by pointer identity, as `reclaimSlotIfOwnedLocked` does. This is the first rule-8 confirmation (§4.7.1 rule 8, as SPEC-3 Edit 13 states it). On a mismatch return `(false, nil)` with no frame.
     c. Mint `startID` from a per-`Server` atomic counter formatted as a decimal string, then `writeSessionStart`. On error return the error.
     d. `noteRuntimeStarted(sessionID, claim.attempt)`. On true return `(true, nil)`. Its token comparison is the rule-8 entry-identity confirmation at this point: step b established identity under the slot serialization, and until the sequence ends another entry for the identifier cannot be created, because the reclaim hold of any removal lasts until then (§5.2). The entry can only have been removed, which the token comparison detects. Every caller of `noteRuntimeStarted` is replaced by this call, so `runtimegeneration.go` does not change.
     e. Otherwise call `writeSessionEnd(sessionID)` and return `(false, nil)` without re-reading the registry. State in the function's comment why no re-read is needed, citing §28.5.3 (CH-MSGSOCK, Session frame writes) and §5.2 (slot-identifier reclaim hold).
2. Start rows.
   - `StartSession`: after `Runtime.Start` succeeds, call `openRuntimeSession(ctx, sessionID, claim, in, false)` with the `manifestInputs` already passed to `writeSessionManifest`.
     - On an error, call `s.Runtime.Close`, then `releaseClaimedSlot`, and answer `codes.Internal` categorized TRANSIENT.
     - On `!confirmed`, take the existing `rollbackUnconfirmedStart` arm unchanged.
   - `Resume`: the same call with `guardHeld` true, because `Resume` holds the guard from ahead of its claim.
     - On an error, call `s.Runtime.Close`, then `releaseSessionSlotUnderGuard(sessionID, true)`, and answer `codes.Internal`.
     - On `!confirmed`, take the existing `rollbackUnconfirmedStart` arm unchanged.
   - `ConfigureWorkspace`, fresh arm only: after `sw.ConfigureWorkspace` succeeds, call `openRuntimeSession(…, false)` with the `manifestInputs` the RPC already assembles.
     - On an error, call `releaseClaimedSlot` and answer `codes.Internal`. The gateway's `DemoteSDK` fallback then finds no session `running` and writes nothing.
     - On `!confirmed`, take the existing `refuseUnconfirmedSDKWarmStart` arm unchanged. Its `session_end`, when one is owed, was already written at step e and precedes `DemoteSDK`.
     - The idempotent repeat calls nothing and writes nothing.
3. End rows.
   - `tearDownReclaimedSlot`: inside `if r.started`, call `writeSessionEnd(sessionID)` before `Runtime.Close` when `r.live` is true. `r.live` is already read in the deregistration's critical section, and the write precedes the release of the reclaim hold.
   - `DemoteSDK` handler: resolve `sessionID := s.anyRegisteredSession()`. When it is non-empty:
     - acquire `lockSlotGuard(ctx, sessionID)`. When it reports `false`, because the acquisition outlived the request's deadline, log `slot_guard_not_acquired`, write no `session_end`, call no `sw.DemoteSDK`, leave `sdkConnected` and the registry entry unchanged, and answer `codes.DeadlineExceeded` (the `DemoteSDK` deadline row of SPEC-3 **Session frame writes.**). This handler does not proceed without the guard as `releaseSessionSlot` does. Each caller then takes its existing `DemoteSDK`-failure branch, which the same row states;
     - read `running := s.runtimeHoldsLocked(sessionID)` under `s.mu`;
     - call `writeSessionEnd(sessionID)` when `running`;
     - then call `sw.DemoteSDK`, keeping its current `codes.Internal` answer on error, clear `sdkConnected`, and call `noteRuntimeClosed(sessionID)` and `releaseSessionSlotUnderGuard(sessionID, true)`.
     When it is empty, keep the current `sw.DemoteSDK`, `sdkConnected`, and `cancelPodMCPIfRuntimeIdle` path. The SIGTERM-time `ShutdownDemoteSDK` reaches this handler and writes what the `DemoteSDK` rows state.
   - The hold-timeout termination, `Interrupt`, heartbeat escalation, and process exit write nothing and are not edited.
4. `attach.go`: the protocol-frame filter that consumes `heartbeat_ack` also consumes `session_started` and relays it to no stream (SPEC-3 **Outbound: `session_started`** rule 5). The SDKs write the frame from CODE-4 and CODE-5 on, before CODE-9 adds the wait, so the filter lands here and reaches no client in between. A tier-1 case beside `TestAttachRelaysAProtocolLevelFrame_spec_28_5_3` in `pkg/adapter/attach_test.go`, with `HeartbeatInterval` unset, asserts that a `session_started` reaches no Attach stream and that the `response` written after it reaches its session's stream.
5. Cite `// spec: §28.5.3 (CH-MSGSOCK, Session frame writes); §4.7.1 (role and gateway RPC contract), rule 8; §5.2 (slot-identifier reclaim hold)` on `openRuntimeSession`, and `// spec: §28.5.3 (CH-MSGSOCK, Session frame writes)` at each call site.

Existing adapter tests whose fake `RuntimeProcess` asserts the exact sequence of frames it received gain the frames their row states.

### CODE-4 · Go runtime SDK serves sessions keyed by `sessionId`

Targets: `sdks/runtime/go/runtime/runtime.go`, `types.go`, `context.go`, `mcp.go`, `lifecycle.go`, `options.go`, `sdks/runtime/go/example/{echo,delegate,lifecycle}`, and `cmd/lenny-ctl/runtimescaffold/templates/{go-minimal,go-coding,go-chat}.main.go.tmpl`.

1. Frame loop. The loop reads every inbound frame and never blocks on one session's work. It routes `session_start`, `message`, `tool_result`, and `session_end` to the addressed session's state through a routing table keyed by `sessionId`; it handles `heartbeat` and `shutdown` itself. Each session has its own goroutine and its own queue. **IMPLEMENTOR'S CHOICE:** the queue implementation. A full queue may block delivery only to its own session, never the loop.
2. Session state. `session_start` creates a `sessionState` holding a context derived from the process context and its cancel function, the parsed frame, the `CredentialBundle` loaded from the frame's `credentialsPath` (none when the member is absent), a create error, and a sequence counter. The SDK then invokes `OnCreate` with a `CreateRequest` whose `SessionID` and `TaskID` are the frame's `sessionId` and whose `ExperimentContext`, `TracingContext`, and `LLM` come from the frame. Once `OnCreate` returns, the session's goroutine writes `{"type":"session_started","sessionId":…,"startId":…}`, echoing the `startId` of the `session_start` it answers, on stdout, with `error` (`code` `RUNTIME_ERROR` and the failure text) when the credential-file read or `OnCreate` failed (SPEC-3 **Outbound: `session_started`** and **Session errors.**). The state is in the routing table and in the lifecycle router before the frame is written, so a `CH-RUNTIMEOPS` event the adapter sends after it reads the frame finds the session. A duplicate `session_start` is otherwise ignored and is answered with `session_started` again, carrying `error` when the held session's create failed (SPEC-3 **Inbound: `session_start`** rule 3).
3. Messages. `Message.SessionID` and `Message.TaskID` come from the inbound frame's `sessionId`, and `Message.Sequence` is the session's counter. A message for a session with no state, or whose create failed, is answered as SPEC-3 **Session errors.** states, with `error.code` `RUNTIME_ERROR`, and is not dispatched. The process keeps running.
4. `session_end`. The frame loop removes the session from its routing table when it reads `session_end` and hands the state to the session's goroutine, which cancels the session context, discards queued messages without dispatching them, cancels the session's pending `tool_call` waiters, waits for the in-flight handler to return, and calls `OnTerminate(ctx, sessionID, TerminationReason{Reason: "session_end"})`. A `session_start` for that `sessionId` read afterwards creates a new state whose `OnCreate` runs after the removed state's `OnTerminate` returns, and its messages queue meanwhile. When the frame loop reads `session_end` it marks the removed state ended under the stdout writer's lock, and every `response` and `tool_call` written for that state, including the in-flight handler's answer and a leaked goroutine's `tool_call`, checks the mark under that lock and is logged and dropped once it is set (SPEC-3 **Inbound: `session_end`** rule 2); a dropped `tool_call` returns an error to its caller at once. `Lifecycle.Send` applies no per-session filter, because SPEC-3 **Inbound: `session_end`** rule 2 admits a late `llm_request_completed`. A `session_end` for an unknown session is ignored.
5. EOF and `shutdown` close every live session's queue. Each session dispatches its queued messages, its in-flight handler returns, and the SDK then calls `OnTerminate(ctx, sessionID, reason)` with the reason `Run` passes today (the `shutdown` frame's reason, or `stdin_closed` on EOF). Sessions drain concurrently, and `Run` returns after every session goroutine has returned, including one item 4 removed from the routing table. Only `session_end` discards queued messages.
6. MCP. The platform and connector MCP connections stay process-scoped: `startChannels` dials them once per process with `CH-RUNTIMEOPS` and keeps its current hard-error and degrade behavior. A failed credential-file read sets that session's create error and does not end the process.
7. Handler signature. `Handler.OnTerminate` becomes `OnTerminate(ctx context.Context, sessionID string, reason TerminationReason) error`. The `Handler` doc comment follows SPEC-5 Edit 1; the comment that a recycled session gets a fresh `OnCreate` after the runtime exits is removed. The `types.go` comments on `CreateRequest` and `Message` follow SPEC-5.
8. Credentials. Delete `resolvedCredentialsPath`'s fallbacks to the manifest's `credentialsPath` and to `WithCredentialsPath`, and delete the `WithCredentialsPath` option. The `session_start` `credentialsPath` is the only source. `CredentialBundle` decodes the credential file in the layout item 4 of §4.7.11 states, a `Providers` list whose entries carry `LeaseID`, `Provider`, `ExpiresAt`, `DeliveryMode`, and `MaterializedConfig` (the entry's object, left undecoded), in place of the flat `Mode`, `APIKey`, `APIKeyEnv`, and `BaseURL` fields. `credentials_rotated` reloads the bundle of the session its `sessionId` names.
9. Lifecycle routing (the SDK half of SPEC-4). `OnCheckpoint`, `OnInterrupt`, and `OnCredentialsRotated` callbacks gain a leading `sessionID string` parameter, and `LifecycleEvent` gains `SessionID`. A `CH-RUNTIMEOPS` event naming a session the SDK does not hold, or one whose create failed, is logged and dropped without a reply, as SPEC-4 Edit 2 states. The SDK keeps no queue of early events and adds no `Run` option for them.
10. `AdapterManifest` drops `SessionID`, `TaskID`, `CredentialsPath`, and `TracingContext`. `withSessionContext` takes the `sessionState`, which carries the session's context and credentials and the process-scoped `Tools` and `Lifecycle`.
11. The echo example reports the session's `SessionID` and experiment variant in its reply text, so TEST-1's tier-10 cases can observe the context. The delegate and lifecycle examples and the Go scaffold templates adopt the new `OnTerminate` and lifecycle callback signatures, and the go-chat template's header comment names `session_start` as the source of `credentialsPath`.
12. In the same commit, retarget the Go cases of `tests/tier10_conformance/credential_path_resolution_conformance_test.go` to drive `session_start` (`…FromTheManifest` becomes `…FromSessionStart`), including the rotation case, which writes `credentials_rotated` after it reads the session's `session_started`, and `TestGoRuntimeSDKStartsWithNoCredentialFileAtTheManifestPath_spec_4_7`, which sends a `session_start` without `credentialsPath`. The Go cases write their credential files with a providers-layout `writeCredentialBundle` and assert `Providers[0].Provider`; the Python and TypeScript cases keep the flat writer under another name until CODE-5 item 8. Update `runtime_test.go`, `lifecycle_test.go`, and `mcp_test.go` for the new behavior, and have every existing test that reads the Go SDK's stdout frame by frame, in `tests/tier3_contract/sdks/runtime_sdk_test.go` and `tests/tier10_conformance/credential_path_resolution_conformance_test.go`, expect or skip the `session_started` the SDK now writes.

### CODE-6 · Compliance harness, reference runtimes, and deletion of the runtime-side `terminate` handlers

Targets: `cmd/lenny-compliance/{main,standard,full}.go` and their tests (`full_test.go`, `standard_test.go`, `deadline_test.go`, `sessionlifetime_test.go` (new)), `cmd/runtimes/echo-concurrent/{dispatch,main_test}.go`, `cmd/runtimes/streaming-echo/main.go`, `sdks/runtime/go/runtime/lifecycle.go`, `sdks/runtime/python/lenny_runtime/lifecycle.py`, `sdks/runtime/typescript/src/lifecycle.ts`, `cmd/lenny-ctl/runtimescaffold/{probe,probe_test}.go`, `tests/tier3_contract/sdks/runtime_sdk_test.go`.

1. The `session_started` read. The battery's `session_start` prefix and the interim order this item replaces are in CODE-3 item 4. This item replaces that order with the precondition SPEC-6 Edit 4 states, and it is the read's one specification.
   - Helper. `full.go` gains `readSessionStarted(out *bufio.Scanner, sessionID, startID string, wait time.Duration) error`. It reads the runtime's stdout until a `session_started` that carries the `sessionId` and `startId` of CODE-3 item 4's prefix, and skips every other frame. It returns an error when that frame carries `error`, when stdout ends first, or when `wait` elapses first; the expiry error wraps a sentinel, `errSessionStartedWaitExpired`. Every Full check that writes a session-scoped `CH-RUNTIMEOPS` frame calls the helper after `handshake` returns and after it writes the prefix, and writes that frame only after the helper returns nil. `checkRuntimeOpsHandshake` reads item 8's acknowledgement through the same helper. A check whose helper returns an error returns that error at once, so no later read shares the stdout scanner with the helper's pending read.
   - Bound. `full.go` declares `sessionStartedWait = 10 * time.Second`. CODE-9 item 2 keeps the adapter's default below the 10 s `ConfigureWorkspace` timeout, so a 10 s wait is no shorter than any default S18 can choose, and a runtime the adapter accepts passes; S16 needs no knowledge of S18's value. Each Full check today runs its runtime under a fixed 10 s process context, inside which `waitConn` and each read take up to 3 s, so a 10 s wait cannot fit there: the runtime would be killed and the read would end at EOF before the wait elapsed. Each Full check's process context is therefore the wait plus the former 10 s, which keeps the existing budget for the connection, the handshake, and the check's own exchange behind a full wait. A bound stated relative to the check's deadline is rejected, because it shrinks by whatever the connection and the handshake consume and cannot guarantee a wait as long as the adapter's default. `runFullBattery` passes `sessionStartedWait` to the Full checks as a value, such as a field of a receiver whose methods are the checks, rather than through a package variable, so `full_test.go` drives them with a short wait. The wait is a constant rather than a flag, because its value follows from CODE-9 item 2's cap and a shorter value would reject runtimes the adapter accepts.
   - Expiry. A check whose helper returns an error returns it, and `recordCheck` records `Pass=false` with the error in `Detail`. `Check` has no failure-category field, and this item adds none.
   - Test. `full_test.go` runs item 8's stub that never writes `session_started`, made to answer every session-scoped `CH-RUNTIMEOPS` frame and every `message` and to keep stdout open past the wait, through each check that sends such a frame with a short wait. It asserts that each check returns an error matching `errSessionStartedWaitExpired` under `errors.Is`, and that `recordCheck` records `Pass=false` for it. A check that skips the read passes against this stub, and a check that fails at EOF returns a different error, so the test fails both.

Add the `session_lifetime` check that SPEC-6 **session lifetime** states, replacing the code-only `sequential_messages_handled` check in `main.go` and as the Basic key of `checkLevel` in `cmd/lenny-ctl/runtimescaffold/probe.go`, which skips a name it does not map, updating `probe_test.go`. A waiting start subscribes with `s.Runtime.Output(waitCtx, sessionID)` before step c, so an acknowledgement written at once is not missed, and after step c reads that subscription until a `session_started` that carries the start's `startId`; a non-waiting start opens no subscription. When the wait ends without the frame, or the frame carries `error`, the sequence logs `session_start_unacknowledged` with the slot id and the error code, moves the gate to failed (item 1), and only then calls `writeSessionEnd(sessionID)`, takes no record, and returns `errSessionStartUnacknowledged`, a typed error, so each caller takes the error arm CODE-1 item 2 gives it (SPEC-3 **Session frame writes.**, the acknowledgement-failure row). **IMPLEMENTOR'S CHOICE:** the flag's default. 3. The `CH-RUNTIMEOPS` gate. `(s *Server) awaitSessionStarted(ctx context.Context, st *slotState) error` reads the acknowledgement gate (item 1) of the entry its caller passes and never looks the session up again, because a successor attempt's entry under the same key carries a new gate:
   - When the gate is not awaiting or read, it returns nil without consulting `ctx`, so a caller whose context has already ended, such as the deferred `CompleteCheckpoint` on a checkpoint's abort path, still writes its frame.
   - When the gate is failed or released, it returns an error.
   - When the gate is not started or pending, it waits for the gate's next transition or the end of `ctx`, then reads the state again. Only this wait observes `ctx`; when `ctx` ends first, it returns an error.
   Each caller of the session-scoped senders that CODE-3 item 2 names calls it before the sender:
   - `Checkpoint` calls it before `s.ops.Begin`, and again on the same entry after `Begin` returns and before `RequestCheckpoint` by a call that does not wait, where a gate that is not started or pending is an error.
   - `Interrupt` does the same on its clean `CH-RUNTIMEOPS` branch, whose condition it evaluates before `s.ops.Begin`, with the second call before `interruptViaLifecycle`.
   - `FinalizeWorkspace` calls it, and then `SignalFilesUpdated`, after it releases the slot guard, and holds no per-slot guard at the call.
   - `RotateCredentials` holds neither the pod-level op lock nor a per-slot guard at the call.
   - `SignalDeadline` holds neither the pod-level op lock nor a per-slot guard at the call.

   **IMPLEMENTOR'S CHOICE:** how each caller resolves the entry it passes. Constraint: each request resolves its `slotState` once and passes that pointer to every `awaitSessionStarted` call it makes, the deferred `CompleteCheckpoint` included; it never re-resolves the entry by session id; and it makes no waiting call under `s.ops` or a per-slot guard, because a wait under `s.ops` blocks every co-tenant's checkpoint and interrupt, and a wait under the guard blocks `Shutdown`, `DemoteSDK`, and `Resume` from releasing the gate.

   On an error the caller writes no frame and takes the branch it takes today when the runtime does not answer: the checkpoint timeout, `INTERRUPT_TIMEOUT`, the 60-second rotation fallback, or no delivery for `deadline_approaching` and `files_updated` (SPEC-4 Edit 2). Every waiter's `ctx` carries a deadline, so no gate that is never reset or released holds a waiter past it: the rotation path passes its acknowledgement-bounded `ackCtx`; the checkpoint path bounds `stream.Context()` by `CheckpointStart.deadlineMs` for the wait, because the tree's checkpoint handler has no `deadlineMs` context of its own; the interrupt path bounds its request context by the request's `deadlineMs`, as `interruptViaLifecycle` bounds `ictx`; `SignalDeadline` passes its request context bounded by the frame's `remainingMs`; `FinalizeWorkspace` passes its request context bounded by `SessionStartAckTimeout`; and a caller whose bound above is zero bounds its context by `SessionStartAckTimeout`.

## Edge cases and accepted failure modes

- A `session_end` write that fails on a live connection is logged and dropped. The partial-write hazard on the shared connection predates this proposal and applies to every frame.
- For a refused SDK-warm start that wrote `session_start`, the adapter writes `session_end` before `DemoteSDK`, because `DemoteSDK` does not end the runtime process (SPEC-3 **Session frame writes.**).
- Under the developer loop no credential file is provisioned, so the SDK loads no credential bundle for the session.
- A runtime that never writes `session_started` starts no session whose start waits under SPEC-3 **Outbound: `session_started`** rule 3 once CODE-9 lands; the Full **CH-RUNTIMEOPS opening** check (CODE-6 item 8) reports it before deployment.
- A runtime process that crashes takes every session's context with it; the pod is retired and a resume on a fresh pod re-delivers the context in a new `session_start`.
