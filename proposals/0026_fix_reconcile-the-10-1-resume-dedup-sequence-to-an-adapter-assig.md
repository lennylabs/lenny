# Proposal: Reconcile the §10.1 resume-dedup sequence to a checkpoint-persisted tool-call ordinal, drop the gateway-dispatch assumption §4.7/§4.9 contradict, add the `last_tool_call_sequence` wire field, and wire `ResumeDedup` into the coordinator-handoff resume path (F-10.1.19 residual)

- **Status:** Verified (2026-07-02). Converged after 3 adversarial review rounds (1 findings fixed); awaiting sign-off.
- **Date:** 2026-07-02.
- **Scope:** Reconciles the resume-deduplication half of the §10.1 CheckpointBarrier protocol (steps 4 and 5) to an execution model §4.7 and §4.9 actually provide. The current §10.1 text assumes the gateway dispatches each tool call and stamps a session-stable `tool_call_sequence_number`, then compares that numeric sequence against a string `last_tool_call_id`. §4.7 makes the runtime adapter observe-only, and §4.9 puts the runtime in the per-LLM/per-tool-call path, so no gateway→pod per-tool-call dispatch transport exists to carry a gateway-assigned sequence, and the numeric-versus-string comparison crosses a type boundary. This proposal redefines §10.1 steps 4 and 5 to a checkpoint-persisted, adapter-assigned tool-call ordinal defined at the adapter's verified observation surface, states precisely which tool calls that ordinal covers and scopes the dedup guarantee to that set, corrects the §16 counter description to the numeric-versus-numeric comparison, adds `last_tool_call_sequence` to the `CheckpointBarrierResponse` proto (which today carries no sequence field), threads that value through the gateway `adapterclient` result and `PodDispatcher.Send` onto `barrier.Ack.LastToolCallSequence` so the already-built persistence into `session_checkpoint_meta` receives a real value, and wires `barrier.Coordinator.ResumeDedup` into the coordinator-handoff resume path once §10.1 defines a consumer that path can honor. It resolves the resume-dedup residual of `F-10.1.19`. It touches `spec/10_gateway-internals.md`, `spec/04_system-components.md`, `spec/16_observability.md`, `schemas/lenny-adapter.proto`, `pkg/proto/adapter/v1/` (regenerated), `pkg/adapter/coordination.go`, `pkg/adapter/attach.go`, `pkg/gateway/runtime/adapterclient/client.go`, `pkg/gateway/coordination/barrier/wiring.go`, `pkg/gateway/sessionserver/`, `cmd/lenny-gateway/httpsurface.go`, `BUILD-GAPS.md`, and the tests.

This document stages the proposed spec, code, and test changes for the implementation step. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

The dispatch and drain half of the §10.1 CheckpointBarrier protocol is wired into the live gateway. `cmd/lenny-gateway/httpsurface.go:579-624` builds `barrier.MirrorTargetLister`, `barrier.PodDispatcher`, and `barrier.New`, and hooks `barrier.Coordinator.Dispatch` into `prestop.Hook.Barrier` bounded by `checkpointBarrierAckTimeoutSeconds` (`F-11.3.15` CLOSED). The `F-10.1.19` finding's `cmd/lenny-gateway/main.go:1740-1784` location and its "no `barrier.` caller in `cmd/lenny-gateway`" evidence are stale: proposal 0020 relocated the block into `httpsurface.go` (merge `31c65673`), where the barrier construction is at `httpsurface.go:579-624` and the residual `nil` `ManifestReader` argument is at `:608`.

The genuinely-open residual is the resume-dedup half (§10.1 steps 4 and 5). `barrier.New` passes `nil` for the `ManifestReader` (`httpsurface.go:608`); `barrier.Coordinator.ResumeDedup` (`pkg/gateway/coordination/barrier/barrier.go:285`) has zero production callers (a grep finds only `barrier_test.go:222,242,264,284,296`); `pkg/gateway/sessionserver` does not import the barrier package, so `ResumeDedup` is structurally unreachable from the resume re-bind path (`resumeOnPod` at `pkg/gateway/sessionserver/start.go:3047`, which fences via `fenceResumedPod` → `s.fencer.Fence` at `:3140,:3144` but never dedups); and `PodDispatcher.Send` (`pkg/gateway/coordination/barrier/wiring.go:59-62`) never sets `Ack.LastToolCallSequence`, so `barrier.Ack.LastToolCallSequence` (`barrier.go:82`) is the `int64` zero value on every live-adapter dispatch and `ResumeDedup`'s comparison has no real sequence to compare.

The residual is spec-blocked by a §10.1 versus §4.7/§4.9 execution-model contradiction. §10.1 step 4 (`spec/10_gateway-internals.md:178`) assumes a gateway-dispatch model: "Each tool call dispatch carries a `tool_call_idempotency_key` — a `(session_id, coordination_generation, tool_call_sequence_number)` tuple ... the new coordinator compares the pod's `last_tool_call_id` against its own last-dispatched `tool_call_sequence_number` before re-dispatching," and step 5 (`:179`) skips "Any tool call with `tool_call_sequence_number <= last_tool_call_id`," a numeric-versus-string comparison that also crosses a type boundary. §4.7 (Runtime Adapter, `spec/04_system-components.md:637`) makes the adapter observe-only: it records a runtime-generated `last_tool_call_id` string it reads from the runtime's stdout (`SetLastToolCallID` at `pkg/adapter/coordination.go:55`, called from `pkg/adapter/attach.go:134` and `:180`; `extractToolCallID` at `pkg/adapter/toolcall.go:31` returns the opaque JSONL `id`). §4.9 (Credential Leasing Service, `spec/04_system-components.md:1104`) puts the runtime in the per-LLM and per-tool-call path (direct mode reaches the provider with the leased credential; proxy mode calls the reverse proxy, `spec/04_system-components.md:1100`). The adapter RPC surface (`schemas/lenny-adapter.proto`: `StartSession`, `SendMessage`, `Attach`, `Checkpoint`, `CheckpointBarrier`, `CoordinatorFence`, and the others) has no gateway→pod per-tool-call dispatch RPC onto which the gateway could stamp a sequence, and the `CheckpointBarrierResponse` proto message (`schemas/lenny-adapter.proto:1181`; the §4.7 `CheckpointBarrierAck` at `spec/04_system-components.md:687`) carries only `barrier_id`, `last_tool_call_id`, `checkpoint_ref`, and `quiesced_ms`, with no `last_tool_call_sequence` field. The gateway is never in the per-tool-call dispatch path, so the producer §10.1 assumes cannot exist.

The `session_checkpoint_meta` store (migration 0148, `last_tool_call_sequence BIGINT DEFAULT 0`), `ResumeDedup` and its unit tests, and the `lenny_coordinator_resume_deduplicated_total` emitter are all built and correct. The gateway-side comparison surface is already the numeric one this proposal adopts: `barrier.Ack.LastToolCallSequence` is `int64` (`barrier.go:82`), `ResumeDedup` takes `ownLastDispatchedSequence int64` (`barrier.go:285`), and `Dispatch` already persists `ack.LastToolCallSequence` into the record (`barrier.go:219`). Only the producer of a real, comparable, session-stable sequence is missing, and it cannot be built until the spec settles who assigns the sequence and how a resuming coordinator consumes it. This is the resume-dedup residual of `F-10.1.19` (`BUILD-GAPS.md:12868`, DEFERRED pending a spec change).

## 2. Decisions

- **Redefine §10.1 steps 4 and 5 to a checkpoint-persisted tool-call sequence rather than a gateway-stamped one.** The alternative direction, inventing a gateway→pod per-tool-call dispatch transport with gateway-assigned stamping, reverses the settled §4.7/§4.9 execution model in which the runtime owns its LLM and tool calls and the adapter observes stdout, and it is the same missing gateway↔adapter task-control transport prior findings already deferred. The checkpoint-persisted direction keeps the runtime-driven model, keeps the adapter as the party that sees the tool-call stream, and reuses the durable-counter-survives-handoff pattern the platform already runs for `SessionEvent.SeqNum` (`spec/07_session-lifecycle.md:399`, `sessions.last_seq`: advanced atomically, survives handoff, restart, and resume, primed from Postgres at handoff step 0).
- **Define the sequence at the adapter's verified observation surface, and scope the dedup guarantee to what that surface covers.** The adapter's `SetLastToolCallID` advance-sites (`pkg/adapter/attach.go:134,:180`) fire only on frames on the runtime's stdin/stdout `tool_call` channel. At Standard and Full integration levels the runtime calls MCP tools over its MCP client connection to the adapter's local servers rather than over the stdin `tool_call` channel (`spec/15_external-api-surface.md:1877`: "The stdin `tool_call`/`tool_result` channel is used for adapter-local tools only"), and those MCP calls flow through separate paths (`pkg/adapter/mcpruntime.go` `client.CallTool`, `pkg/adapter/connectortoolprovider.go` `Call`) that do not touch `SetLastToolCallID`. The spec text must define the ordinal at the adapter's actual observation surface (the stdin/stdout adapter-local `tool_call` channel) and state precisely which tool calls the ordinal covers, then scope the dedup guarantee to that set. The spec must not assert dense coverage of every tool invocation while the adapter-local subset is all the current adapter observes. Whether a single adapter mediation point can serialize both the stdin/stdout channel and the MCP-local-server channel into one total order is Open decision 1: the implementer either establishes such a point with a code cite and then widens the stated coverage, or narrows the spec's guarantee to the adapter-local channel and documents that MCP-tool-call dedup is out of scope for this ordinal.
- **Assign the sequence adapter-side as a per-adapter-process ordinal on the observed tool-call stream, persist it in the checkpoint metadata alongside `last_tool_call_id`, and echo the last-completed ordinal on `CheckpointBarrierAck`.** The comparison in §10.1 step 5 becomes numeric-versus-numeric (last-completed ordinal against the resuming coordinator's own view), removing the string-versus-`int` type mismatch. The ordinal extends the `coordinationState` that today holds only `lastToolCallID` (`pkg/adapter/coordination.go:39`). The adapter resets `lastToolCallID` only on a coordination-generation gap (`pkg/adapter/coordination.go`, the §10.1 line 36 reset at `:119-131`, taken when a `CoordinatorFence` skips one or more generations; a contiguous +1 fence does not reset it), so the ordinal advances across contiguous coordination-generation handoffs on a surviving pod and restarts at 0 only on a gap or in a fresh adapter process. Because a fresh pod runs a fresh process, its ordinal begins at 0 and the persisted prior-generation value is read on resume rather than continued in place. The cross-generation comparability of this per-adapter-process ordinal is Open decision 2, and it is the primary coordinator-handoff resume path rather than an edge case. A cross-replica coordinator handoff advances `coordination_generation`: `Sweeper.RecordHandoff` (`pkg/gateway/coordination/coordination/coordination.go:170` `row.CoordinationGeneration++`) bumps it on every observed cross-replica lease handoff (`:144-146`), and this sweeper runs in production (constructed at `cmd/lenny-gateway/stores.go:1085`, started at `cmd/lenny-gateway/workers.go:1223`), matching spec §4.2 line 156 ("`coordination_generation` is incremented on coordinator handoff across gateway replicas"). The other two increment sites are `bumpCoordinationGenerationOnSnapshotClose` (`pkg/gateway/sessionserver/start.go:3363` `row.CoordinationGeneration++`) on snapshot-close and the same function called from a terminal collapse out of `resuming` (`failure.go:223`). The successful resume re-bind itself bumps only `recovery_generation`: `resumeOnPod` (`pkg/gateway/sessionserver/start.go:3047`) calls `bumpRecoveryGeneration` (`:3396` `row.RecoveryGeneration++; row.RetryCount++`) and re-fences the fresh pod at the current `coordination_generation` through `fenceResumedPod` (`:3140`), reading whatever value `RecordHandoff` already advanced. Because the handoff that triggers the resume already bumped the generation, the fresh adapter is fenced into the new higher generation as its first fence (never a gap, `coordination.go:22-24`), so its ordinal begins at 0 as a new process while the persisted `last_tool_call_sequence` was written under the prior generation. The spec text must state exactly what the resuming coordinator compares in this cross-generation case, because it is the normal path: either it defines a comparison that reads the prior generation's persisted ordinal, or, if no coherent cross-generation comparison exists once the generation always advances on handoff, the resume-dedup sub-item closes as "no gateway consumer exists" (S4 outcome (a)) rather than being wired against an uncomparable ordinal.
- **Add `last_tool_call_sequence` to the wire and thread it through the already-built persistence and gateway logic on one canonical path.** The adapter assigns and echoes the ordinal; `adapterclient.CheckpointBarrierResult` reads it; `PodDispatcher.Send` maps it onto `Ack.LastToolCallSequence`; `Dispatch` persists it into `session_checkpoint_meta` (the column exists, migration 0148); `ResumeDedup` reads it from Postgres. Every added field extends an existing message, store, or code path. No parallel surface is introduced.
- **Land the Postgres-primary dedup source in this proposal and defer the MinIO `barrier_meta` fallback.** The `session_checkpoint_meta` write is the authoritative v1 dedup source, and the code already tolerates a `nil` `ManifestReader`: `ResumeDedup`'s fallback branch returns cleanly when `c.manifest == nil` (`pkg/gateway/coordination/barrier/barrier.go:296-297`). The MinIO fallback for the Postgres-absent-at-SIGKILL case requires two surfaces that do not exist: the adapter does not write `barrier_meta` into a checkpoint manifest (`flushBarrierCheckpoint` at `pkg/adapter/coordination.go:225-230` explicitly disclaims it), and there is no blob-store list/read surface to discover the session's latest checkpoint manifest. Leaving `barrier.New`'s manifest argument `nil` (`httpsurface.go:608`, unchanged) keeps this proposal to the Postgres-primary path and carves the manifest layer as its own follow-on finding rather than smuggling a new adapter-write path and a blob List surface into a wiring step.
- **Wire `ResumeDedup` into the existing coordinator-handoff resume path only after §10.1 defines a consumer that path can honor.** The gateway has no tool-call re-dispatch path and no coordinator-side last-dispatched-sequence view. `resumeOnPod` (`pkg/gateway/sessionserver/start.go:3047`) fences the resumed pod and re-delivers user messages through the inbox dequeue; on resume the pod's runtime autonomously continues its own agentic loop from the checkpointed workspace, which is the runtime-driven model this proposal affirms. The consumer question is folded into S1: S1 defines, in spec text, what "skip an already-completed tool call on resume" concretely means in that model, and the resume wiring targets whatever real seam S1 identifies with a real `ownLastDispatchedSequence` from that seam's own bookkeeping. If S1 concludes the resuming coordinator has no tool-call dispatch to gate, `ResumeDedup` and its counter are dead surface and the resume-dedup sub-item closes as "no gateway consumer exists" rather than being wired against a re-dispatch that does not exist.

## 3. The execution-model constraint the redefinition must respect

The redefinition rests on three facts about the runtime-driven model that the spec text must not contradict.

**The gateway is never in the per-tool-call dispatch path.** §4.9 puts the runtime in the per-LLM and per-tool-call path: in direct mode the runtime reaches the provider with its leased credential, and in proxy mode it calls the reverse proxy (`spec/04_system-components.md:1100`). The adapter RPC surface (`schemas/lenny-adapter.proto`) defines lifecycle and control RPCs (`StartSession`, `SendMessage`, `Attach`, `CheckpointBarrier`, `CoordinatorFence`, and the rest) with no gateway→pod per-tool-call dispatch RPC. There is no gateway-issued tool-call dispatch onto which the gateway could stamp a session-stable sequence, so §10.1 step 4's gateway-stamped `tool_call_sequence_number` cannot be produced.

**The adapter observes only the stdin/stdout adapter-local `tool_call` channel today.** Both `SetLastToolCallID` call sites fire on frames on the runtime's stdin/stdout `tool_call` relay (`pkg/adapter/attach.go:134,:180`). Per `spec/15_external-api-surface.md:1877`, at Standard and Full levels the runtime calls MCP tools over the MCP client connection to the adapter's local servers rather than over the stdin `tool_call` channel. The MCP platform and connector tool calls flow through separate adapter paths (`pkg/adapter/mcpruntime.go` `client.CallTool`, `pkg/adapter/connectortoolprovider.go` `Call`) that never touch `SetLastToolCallID`, so the existing `last_tool_call_id` string already does not cover the MCP path. The spec must define the ordinal at the surface the adapter verifiably observes and scope the dedup guarantee accordingly (Open decision 1).

**A per-adapter-process ordinal must be comparable across the handoff it protects, and that handoff always crosses a generation boundary.** Resume claims a fresh pod with a fresh adapter process (`resumeOnPod` at `pkg/gateway/sessionserver/start.go:3047`). The coordinator handoff that triggers the coordinator-handoff resume advances `coordination_generation`: `Sweeper.RecordHandoff` (`pkg/gateway/coordination/coordination/coordination.go:170` `row.CoordinationGeneration++`) bumps it on every observed cross-replica lease handoff (`:144-146`), and the sweeper runs in production (`cmd/lenny-gateway/stores.go:1085`, `cmd/lenny-gateway/workers.go:1223`). Spec §4.2 line 156 names exactly this trigger: "`coordination_generation` is incremented on coordinator handoff across gateway replicas." The other two increment sites are `bumpCoordinationGenerationOnSnapshotClose` (`start.go:3363`) on snapshot-close and the same function called from a terminal collapse out of `resuming` (`failure.go:223`). The successful resume re-bind itself bumps only `recovery_generation`: `resumeOnPod` calls `bumpRecoveryGeneration` (`:3396` `row.RecoveryGeneration++; row.RetryCount++`) and re-fences the fresh pod at the current `coordination_generation` through `fenceResumedPod` (`:3140`), which reads the generation `RecordHandoff` already advanced. `ResumeDedup` (`barrier.go:285`) compares the prior pod's persisted `last_tool_call_sequence` against the resuming coordinator's view. The normal coordinator-handoff resume therefore crosses a generation boundary: the fresh adapter is fenced into the new higher generation as its first fence, which is never a gap (`coordination.go:22-24`), so the gap-reset branch is not even taken and the fresh adapter's ordinal simply begins at 0 as a new process, while the persisted `last_tool_call_sequence` was written under the prior generation. The spec text must state exactly what the resuming coordinator compares in this cross-generation case, because it is the primary path rather than an edge case: either it reads the prior generation's persisted ordinal, or, if no coherent cross-generation comparison exists once the generation always advances on handoff, the resume-dedup sub-item closes as "no gateway consumer exists" (S4 outcome (a)) rather than being wired against an ordinal in a different generation on a different pod with no relationship to the persisted value (Open decision 2). The two prior findings that reached the same conclusion (`BUILD-GAPS.md:12868`, that dedup needs a gateway-assigned session-stable sequence because the adapter's per-pod count resets on resume) are recorded so the redefinition addresses them head-on rather than re-deriving them.

## Open decisions for review

1. **Scope of the adapter's sequence view at Standard and Full levels (load-bearing for S1's spec text).** The adapter observes adapter-local `tool_call` frames on stdin/stdout directly (`pkg/adapter/attach.go:134,:180`), but MCP tool calls (`lenny/delegate_task`, connectors) at Standard and Full levels go over the MCP client connection to the adapter's local servers (`spec/15_external-api-surface.md:1877`; separate paths at `pkg/adapter/mcpruntime.go` `client.CallTool` and `pkg/adapter/connectortoolprovider.go` `Call`, neither touching `SetLastToolCallID`). The implementer either establishes, with a code cite, a single adapter mediation point that serializes both channels into one total order before the spec claims dense coverage, or narrows the spec's stated guarantee to the adapter-local channel and documents that MCP-tool-call dedup is out of scope for the adapter-assigned ordinal. S1's final spec wording depends on this resolution.
2. **The cross-generation comparison the resuming coordinator performs, which is the primary coordinator-handoff resume path (load-bearing for S1's spec text).** The coordinator-handoff resume always crosses a generation boundary, so the cross-generation comparison is the normal case rather than an edge case. The cross-replica coordinator handoff that triggers the resume advances `coordination_generation` via `Sweeper.RecordHandoff` (`pkg/gateway/coordination/coordination/coordination.go:170` `row.CoordinationGeneration++`, on every observed cross-replica lease handoff at `:144-146`, sweeper wired at `cmd/lenny-gateway/stores.go:1085` and `cmd/lenny-gateway/workers.go:1223`), matching spec §4.2 line 156 ("`coordination_generation` is incremented on coordinator handoff across gateway replicas"). The successful resume re-bind step itself bumps only `recovery_generation`: `resumeOnPod` (`pkg/gateway/sessionserver/start.go:3047`) calls `bumpRecoveryGeneration` (`:3396`) and re-fences the fresh pod at the current `coordination_generation` through `fenceResumedPod` (`:3140`), reading the value the handoff already advanced. The other two increment sites are `bumpCoordinationGenerationOnSnapshotClose` (`start.go:3363`) on snapshot-close and the same function called from a terminal collapse out of `resuming` (`failure.go:223`). The fresh adapter is fenced into the new higher generation as its first fence, which is never a gap (`coordination.go:22-24`), so the gap-reset branch is not taken and the fresh adapter's ordinal begins at 0 as a new process, while the persisted `last_tool_call_sequence` was written under the prior generation. `ResumeDedup` (`barrier.go:285`) compares the persisted `last_tool_call_sequence` against the resuming coordinator's view. S1's spec text must therefore state, for this cross-generation case, exactly what the resuming coordinator compares and against which generation's persisted ordinal: either it reads the prior generation's persisted ordinal so a per-adapter-process counter is comparable at the `ResumeDedup` seam, or, if no coherent cross-generation comparison exists once the generation always advances on handoff, the resume-dedup sub-item closes as "no gateway consumer exists" (S4 outcome (a)) rather than being wired against a fresh-adapter ordinal starting at 0 with no relationship to the persisted prior-generation value.
3. **The checkpoint-manifest `barrier_meta` fallback layer.** The blob store is write-once with no list surface, and the barrier flush records no discoverable per-checkpoint manifest carrying `barrier_meta` (`pkg/adapter/coordination.go:225-230`; `BUILD-GAPS.md:12868`). This proposal lands the Postgres `session_checkpoint_meta` primary write and leaves the `ManifestReader` `nil` (`httpsurface.go:608`), which `ResumeDedup` tolerates (`barrier.go:296-297`). The reviewer confirms deferring the MinIO fallback (an adapter `barrier_meta` manifest write plus a blob-store list and read surface) to a separate follow-on finding rather than broadening this proposal's scope.
4. **Whether `last_tool_call_id` (the string) is retained on the ack and in `session_checkpoint_meta` once the numeric sequence is authoritative for dedup, or kept only for trace and observability.** Keeping both is the low-risk default. The reviewer may prefer to drop the string from the dedup contract to avoid two overlapping identifiers.
