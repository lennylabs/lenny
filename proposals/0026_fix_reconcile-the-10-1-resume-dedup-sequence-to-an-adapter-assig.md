## 1. Problem

§10.1 steps 4 and 5 (`spec/10_gateway-internals.md`, the "CheckpointBarrier protocol" resume-deduplication text near lines 178-179) specify a resume-deduplication mechanism built on a `tool_call_idempotency_key = (session_id, coordination_generation, tool_call_sequence_number)`: on a coordinator handoff the new coordinator is to read the persisted `last_tool_call_id`, then skip "any tool call with `tool_call_sequence_number <= last_tool_call_id`" before re-sending tool-call RPCs. The text compares a numeric `tool_call_sequence_number` against a string `last_tool_call_id`, a type boundary that is the surface symptom of a deeper problem: the mechanism presupposes an execution model the platform does not implement.

### 1.1 Verified coupling (the rationale for closing rather than building)

A code-level trace establishes four facts that make the specified mechanism unbuildable and its consumer inert:

1. **The gateway is not in the per-tool-call dispatch path.** The runtime initiates every tool call (§4.7). Execution splits three ways: the adapter runs built-in file tools (`pkg/adapter/toolcall.go`, `localtools.Dispatch`), the runtime runs its other internal tools, and Lenny MCP tools (`lenny/*`, connectors) are executed by the gateway MCP fabric but reached **pod → gateway** (the pod's MCP client calls the adapter's intra-pod MCP server, which forwards to the gateway over `gatewaycontrol`), never gateway → pod. There is no gateway→pod tool-call dispatch transport, and no `tool_call_sequence_number` is assigned anywhere in non-test code. The adapter records only a best-effort **string** `last_tool_call_id` observed on the runtime's stdout (`SetLastToolCallID` at `pkg/adapter/attach.go:134,:180`), and that observe path does not even cover the MCP-fabric tools.
2. **A coordinator handoff re-adopts the still-running pod; it does not restore from a checkpoint.** On a cross-replica handoff the sweep does `RecordHandoff` (bump `coordination_generation`) plus `upsertMirror` and nothing else (`pkg/gateway/coordination/coordination/coordination.go:144-150,168-176`); there is no `resumeOnPod` call. The pod keeps running: "the handoff re-attaches the live pod, so the workspace is intact (workspaceLost: false)" (`pkg/gateway/sessionserver/start.go:3225`). The pod re-executes nothing.
3. **`ResumeDedup` guards a replay that cannot occur.** `barrier.Coordinator.ResumeDedup` (`pkg/gateway/coordination/barrier/barrier.go:285`, documented "for a coordinator handoff" at `:270`) exists to stop the new coordinator from re-sending tool-call RPCs the pod already completed. But no gateway→pod tool-call RPC stream exists (fact 1) and the pod is not restored (fact 2), so there is nothing to re-send and nothing to skip.
4. **The consumer and its inputs are dead.** `ResumeDedup` has zero production callers (only `barrier_test.go` references it). The `CheckpointBarrierResponse` proto carries only `last_tool_call_id` (string), no `last_tool_call_sequence`, so `barrier.Ack.LastToolCallSequence` and the persisted `sessioncheckpointmeta` sequence are always 0. The gateway wiring passes `nil` for the `ManifestReader` (`cmd/lenny-gateway/httpsurface.go:608`), disabling the spec's designated primary durable source. The `lenny_coordinator_resume_deduplicated_total` counter is registered with Prometheus but never incremented, because its only increment site sits inside the dead `ResumeDedup` (`pkg/gateway/coordination/barrier/barrier.go:325`).

The genuine external-side-effect double-execution risk lives elsewhere: a pod **restored from a checkpoint** (the `resumeOnPod` / `recovery_generation` path, driven by pod loss) can re-issue a tool call whose **external** side effect already happened (an MCP/connector action, a `delegate_task`). `ResumeDedup` does not guard that path, and the adapter-observed stdout marker does not cover those tools. That risk is the subject of proposal 0027, which defines the pod-restore guarantee as at-least-once for external side effects (exactly-once is not achievable on this path).

## 2. Decisions

- **Close the resume-dedup residual as "no coherent gateway consumer exists," rather than building the mechanism.** Wiring an adapter-assigned sequence + `ResumeDedup` would be dead plumbing: a consumer for a dispatch stream that does not exist, guarding a replay that cannot occur (§1.1). Building it violates the no-dead-code principle.
- **Reconcile the incoherent §10.1 steps 4-5 spec text by removing the gateway-dispatch machinery.** Remove the `tool_call_idempotency_key` tuple, the gateway-assigned `tool_call_sequence_number`, and the numeric-versus-string comparison, and replace them with a statement of the actual coupling: a coordinator handoff re-adopts the still-running pod without a restore, the gateway is not in the per-tool-call dispatch path, so no gateway-side resume-deduplication is required or possible; the genuine pod-restore path provides at-least-once semantics for external side effects per proposal 0027 (exactly-once is not achievable on this path).
- **Remove the dead code the mechanism would have fed.** Delete `barrier.Coordinator.ResumeDedup`, `DedupDecision`, and the `AddResumeDeduplicated` metric method it calls (declared on the `barrier.Metrics` interface, with the concrete helper and the `resumeDeduplicated` `CounterVec` registration living in `gatewaymetrics`), the `LastToolCallSequence` field on `barrier.Ack` and `sessioncheckpointmeta.Record` (always 0, no producer) together with its `last_tool_call_sequence` persistence in pgstore and migration 0148, and the `ManifestReader` parameter/plumbing that is passed `nil`. **Also remove the `last_tool_call_id` metadata entirely (Open decision 1, resolved by sign-off: remove).** With `ResumeDedup` gone `last_tool_call_id` has no consumer, so per the no-dead-code principle it is deleted rather than retained for a possible future 0027 use. The verified reader set is removed in full: the `LastToolCallID` field on `barrier.Ack` (barrier.go:81) and the two gateway populators that feed it (the returned `Ack` literal at `wiring.go:60`, and the `CheckpointBarrierResult.LastToolCallID` field and its `resp.GetLastToolCallId()` assignment at `adapterclient/client.go:487,:514`); the `dispatchOne` assignment at `barrier.go:218` (the `LastToolCallSequence` assignment removed with the always-zero field is the sibling line at :219) and the persisted `LastToolCallID` on `sessioncheckpointmeta.Record` (sessioncheckpointmeta.go:55) with its `session_checkpoint_meta` column, the pgstore `last_tool_call_id` INSERT/ON CONFLICT/SELECT/Scan bindings, and the migration-0148 column; the proto `CheckpointBarrierResponse.last_tool_call_id` field (`schemas/lenny-adapter.proto:1181`, regenerated via `make generate-proto`); the adapter-side observation and emit chain that populate it (the `lastToolCallID` field and its `SetLastToolCallID`/`LastToolCallID` accessors, the `CheckpointBarrier` read and the `EmitCheckpointBarrierAck` emit in `pkg/adapter/coordination.go`, the `controlEvent.LastToolCallID` field at `pkg/adapter/controlchannel.go:68`, and the stdout `tool_call` tracking at `pkg/adapter/attach.go:134,:180`); and the spec and doc surfaces that document it as a recorded or reported value (§10.1 steps 2-3, the §4 `CheckpointBarrierAck` message row at `spec/04_system-components.md:687`, and `docs/reference/adapter-contract.md`). The `CoordinatorFence` generation-gap reset (`coordination.go:126`) is removed with the chain: its only effect is to zero the value the ack surfaces (the field has no other reader; the getter at `coordination.go:66` is test-only), and its own comment ties it to a `deduplication replay`, so once the ack drops `last_tool_call_id` the reset has no purpose independent of the deleted dedup path. The §16.3 `session.tool_call` span attribute at `attach.go:179` (`tool.call_id`) is independent of the ack and stays. The CheckpointBarrier **dispatch/flush** half is otherwise kept: it still flushes the workspace checkpoint (`barrier_id`, `checkpoint_ref`, and `workspace_recovery_fraction` and their consumers are retained), and the doc comments (the `barrier` package doc, the `Dispatch`/`dispatchOne` comments, the `sessioncheckpointmeta` package doc, and the parallel adapter/lease/migration comments) are reconciled to drop the removed resume-dedup consumer. It flushes a checkpoint on graceful drain and is independently useful. If proposal 0027 needs a last-completed-tool-call marker it introduces its own.
- **Remove the registered-but-never-incremented `lenny_coordinator_resume_deduplicated_total` counter** from §16.1, the typed `pkg/observability/metrics` catalog (`catalog.go` plus the `spec161Metrics` list in `catalog_test.go`), and the `gatewaymetrics` registration, since its only increment site is the dead `ResumeDedup`.
- **Spin the genuine pod-restore external-side-effect concern out to proposal 0027.** That concern lives on the `resumeOnPod` / `recovery_generation` path and covers the external-side-effect tools (MCP/connector/`delegate_task`), a different transition and a different signal than the coordinator-handoff `ResumeDedup`. Proposal 0027 defines the guarantee on that path as at-least-once (exactly-once is not achievable on this path) and defers any window-bounding mechanism.
