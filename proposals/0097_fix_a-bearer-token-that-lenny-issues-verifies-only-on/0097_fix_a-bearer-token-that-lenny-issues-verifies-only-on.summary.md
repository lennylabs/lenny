# Summary: Lenny-issued bearer tokens verify only on the process that signed them

## Summary

**Problem statement.** Every gateway replica and every Token Service replica draws its own random HS256 key at startup and holds it in plaintext, and each verifier trusts only its own key. In a default multi-replica install, gateway-minted bearers fail on peer replicas, `POST /v1/oauth/token` bearers verify on no gateway, Token Service replicas reject each other's tokens, and every token stops verifying when its signer restarts. `lenny-ops` requires in production an HMAC key that no component signs with. The code also departs from the §10.2 rule that the signing key never exists in gateway memory. The spec is silent on the algorithm, key identity, verifier key distribution, signing topology, and rotation state, and it contradicts itself on which component mints, on per-interaction token refresh, and on where signing sits relative to the advisory lock. The owner has settled remote asymmetric KMS signing, a fixed token lifetime, a 15-minute default for every token whose holder can refresh it, `lenny-ops` acceptance of unrevoked Lenny-issued tokens during a Postgres outage, and `lenny-ops` production readiness that passes when either Postgres or the Kubernetes API is reachable.

**What changes.**
- §10.2, §4.3, §17.4, §18, §25.4, and §25.15: one ES256 key named by the `platform:jwt-signing` alias, signed remotely on AWS, GCP, or Azure and derived from the master key on `local`. A key set loaded once at startup by the gateway, the Token Service, and `lenny-ops`, and a three-rollout rotation, with `lenny-ops` holding a revocation set for Lenny-issued tokens that stays in force through a Postgres outage (SPEC-1, SPEC-2, SPEC-6, SPEC-9, SPEC-11, CODE-6).
- §10.2, §13.3, and §27: a fixed token lifetime and the renamed `auth.capabilityTokenTtlSeconds` knob, which sets the default lifetime of playground bearers and of `POST /v1/oauth/token` JWTs requested without `expires_in` (SPEC-3, CODE-8, CHART-1).
- §10.2, §15, §16, and §17.8: throttling as backpressure, a sign-rate metric, a near-quota alert, and sign-rate sizing (SPEC-4, SPEC-5, SPEC-8, CODE-3, CODE-7, CODE-11, CHART-5).
- §13.3 and §8.2: signing before the write-before-issue transaction, with an in-lock revocation re-read of the subject and actor, and the Token Service's refusal of a playground caller token (SPEC-7, CODE-5, CODE-9).
- `pkg/kms`, `pkg/auth/jwt`, and the three binaries: the KMS `Sign` and `PublicKey` seam, the remote signer and `KeySet`, the wiring, and deletion of the HMAC signer, `RotatingVerifier`, and the published JWKS endpoint (CODE-1, CODE-2, CODE-4, CODE-5, CODE-6, CODE-10, CODE-12).
- §25.4 "Probes", `pkg/ops/opsserver`, and the `lenny-ops` chart: production readiness uses the permissive `/healthz`, which passes when Postgres or the Kubernetes API is reachable, and `/healthz?strict=true` remains a diagnostic check that no probe uses (SPEC-11, CODE-13).
- Chart, docs, records, and cross-process tests: the local master key Secret, `lenny-ops` KMS wiring, gateway and `lenny-ops` KMS egress, the runbook rewrite, and the every-replica tier-4 probe (CHART-2, CHART-4, SPEC-10, DOCS-1, DOCS-2, REC-1, TEST-1).

**Decisions.**
- D1. The design has the fewest moving parts that resolve the defect: one ES256 key shared by the gateway and the Token Service, identity through the existing alias map, a thumbprint `kid`, a static key set, Helm-held rotation state, and the production code path in dev. Every addition below answers a failure mode this design creates or a requirement it leaves unmet.
- D2. ES256 is the only algorithm in every environment, and verifiers accept only `alg: ES256`. All three cloud providers offer it natively, so no algorithm knob is added.
- D3. The providers are AWS KMS, GCP Cloud KMS, and Azure Key Vault, matching `kms.provider`, with `local` for dev. Vault Transit is removed because no adapter exists.
- D4. `kms.Provider` gains `Sign` and `PublicKey` and the `ErrThrottled` sentinel. Only six types implement it, so the compiler forces every adapter to sign and resolution stays on `providerflags.Resolve`.
- D5. Key identity uses two reserved aliases in the existing map: `platform:jwt-signing` and the optional verify-only `platform:jwt-verify`. No new flags or values carry key identity. This departs from the problem statement's scope line "A key-identity configuration surface: flags and Helm values", because the existing `kms.aliases` map already carries a per-alias provider key reference.
- D6. On a cloud provider a `platform:jwt-*` alias must name an immutable key version, and startup rejects a repointable reference. The `kid` is computed once from the startup fetch, so a repointed reference would make every new token fail everywhere.
- D7. `kid` is the RFC 7638 thumbprint. A KMS reference string would give one key two `kid`s and leak resource names into tokens.
- D8. The key set is loaded once at startup and never refreshed. An unknown `kid` makes no KMS call, and a process that cannot load its set exits. Running processes therefore verify through a KMS outage. This departs from the problem statement's scope line asking for "a refresh rule": a version-pinned public key is immutable, so the startup-loaded static set replaces the refresh rule, and SPEC-2 states that no refresh occurs.
- D9. The gateway and the Token Service both sign with the one key. §4.3 item 3 lists what the Token Service mints, and §10.2 "Signing topology" lists what the gateway mints in process. The gateway and Token Service ServiceAccounts hold `Sign` and `GetPublicKey`, and `lenny-ops` holds `GetPublicKey` only.
- D10. Rotation is three Helm rollouts, and step 2 re-mints the bootstrap admin credential with the existing `rotate-token` route. The admin token's 10-year lifetime would otherwise lock the operator out at step 3. `RotatingVerifier`'s timed overlap window is deleted, because it started at pod start and conflicts with config-held state.
- D11. The step-3 wait is the `lenny-gateway` per-dialect cap, which SPEC-7 now states numerically in §13.3 so the rotation rule rests on spec text.
- D12. Dev uses the local provider's master-key-derived ES256 key, and a mapped `platform:jwt-*` reference is the derivation input so rotation works under `local`. Under `kms.provider=local`, every process mounts one shared master key Secret (CHART-2 item 1). No new gate is added, because local signing runs the production path and the existing production refusal of `local` applies. `--bearer-trust-hmac-key-file` stays as the dev embedded-OIDC trust hook and is refused under `lenny-ops --production`.
- D13. `playground.bearerTtlSeconds` becomes `auth.capabilityTokenTtlSeconds`, named for owner decision 3's capability token lifetime. Per owner decision 5 (2026-10-23), it is the one operator-tunable default lifetime of every Lenny-issued JWT whose holder can obtain a fresh one before `exp` by requesting it: the bearers `POST /v1/playground/token` mints, and the JWTs `POST /v1/oauth/token` issues when the request carries no `expires_in`, which covers user bearers from the rotation grant and scope narrowing and operability-scope tokens. The Token Service's hard-coded 1-hour default for an absent `expires_in` is replaced by the same value (CODE-8). SPEC-3 Edit 1 states the default and the bounds once. A token whose holder has no refresh path keeps its cap: the session-creation `session_capability` token, which pods present and which is the delegation `actor_token`, keeps its per-dialect cap, and delegated children take no default `requested_exp` in the §13.3 `exp` formula. A 900 s session-creation token would fail pod→gateway calls and delegation 15 minutes into a session, and the gateway-to-pod renewal path that would fix that is a follow-up proposal.
- D14. Signing stays outside the advisory lock, because a 5–30 ms remote sign held under it would serialize a tenant's mints. The in-lock re-read covers the subject and the actor. It implements the existing §13.3 and §8.2 actor freshness rule and the §13.3 no-grace-period rule, and it stops two concurrent rotations of one subject from both committing. `subject_token_revoked` is a new `invalid_grant` reason.
- D15. Throttling returns the existing 503 `KMS_SIGNING_UNAVAILABLE` with `Retry-After` and never trips the breaker, so no new error code is added. No client-side sign rate limit is added, which departs from the problem statement's scope line "There is also a per-replica sign rate limit": the provider throttle already enforces the quota fleet-wide with the same 503, while a static per-replica split of the quota refuses demand the quota could serve, because the Token Service does not autoscale. One new counter, `lenny_jwt_sign_requests_total`, is added. The errors counter keeps its name, takes the code's `reason` label, and stops counting throttled requests, so the existing alert expression stays correct. Its spec text now matches the code's `rate(…[30s]) > 1`.
- D16. `kms.signQuotaPerSecond` has no default and is required on cloud providers, because provider quotas vary by account and region and a shipped default would be wrong for most installs. SPEC-8 Edit 2 states the sign-rate formula and carries no worked Tier figures. Under owner decision 5 the refreshing-holder term counts API clients as well as playground bearers, and no §16.5 tier parameter fixes that population, so any figure would rest on an assumed holder count. The formula has no credential-lease term, because a credential-lease token is an opaque `TokenStore` handle and signs nothing (`credential.MintLease` in `pkg/credential/lease_mint.go`; the Token Service `AssignCredentials` and `RotateCredentials` paths in `pkg/tokenservice/grpc.go` hold no signer).
- D17. The published `/.well-known/jwks.json`, `--jwks-publish`, and the `jwksAdvertisesAsymmetric` notice are deleted. No spec section defines the endpoint and no in-platform verifier reads it.
- D18. `platform.jwt_signing_key_rotated` is dropped from §18. No §16.7 entry defines it, and a configuration rollout has no Lenny-side transition to emit from.
- D19. The gateway and `lenny-ops` reach KMS through a `kms.endpointCIDR` peer whenever `kms.provider` is not `local`, and the chart refuses `0.0.0.0/0` and `::/0` on a cloud provider. The gateway has no unconditional external-HTTPS rule to reach a public endpoint through, and an unrestricted peer would cancel the NET-057 excepts. A public KMS endpoint spans provider ranges that no single CIDR covers, so a cloud deployment uses the subnet of the provider's private KMS endpoint.
- D20. Capacity text goes in §17.8 only. The `issued_tokens` write-rate gap in the §12.3 table predates this change, so this proposal leaves it unstaged. This departs from the problem statement's scope line asking for capacity guidance in "§17.8 and §12.2" with "the token-issuance rows in the Postgres write budget".
- D21. There is one spec pass and one implementation pass, and every adapter gains signing before any binary switches. No interim production posture or claim-register row is needed.
- D22. Per owner decision 4 (2026-10-23), `lenny-ops` keeps an in-memory revocation set for Lenny-issued tokens (option B). SPEC-11 Edit 2 states the rules and CODE-6 item 6 implements them. No revocation can commit while Postgres is down, so a set loaded before an outage misses only revocations that committed before it and had not arrived. Those are enforced at the first successful read after Postgres returns, or never if the token expires first. The window is bounded by the outage rather than by a lifetime cap, because `lenny-ops` accepts every audience: `lenny-ctl` presents its gateway bearer to `lenny-ops`. This departs from the 1-hour bound in the problem statement's owner decision 4, which assumed that only `lenny-ops`-audience tokens reach `lenny-ops`. A `lenny-ops` that starts during the outage refuses Lenny-issued tokens until a read succeeds. A read that fails while Postgres still accepts writes, such as a permissions or routing fault, leaves the set behind until a read succeeds, and the error log of each failed read records it. Both residual risks are accepted. The spec states the 30-second re-read for `lenny-ops` because §13.3 states no periodic read, and without it a Redis outage would leave the set unrefreshed. Rejected: option A, refusing all Lenny-issued tokens while Postgres is down, which disables the §25.15 loop in the outage it exists for; and option C, accepting only `lenny-ops`-audience tokens with revocation deferred, which leaves revocation unchecked.
- D23. OD1 is settled as option (a) by the owner's delegate (2026-10-24). `lenny-ops` reuses the gateway's `authmw` unchanged and emits the gateway's existing revoked-token response, `401 TOKEN_REVOKED`. SPEC-11 Edit 2 rule 3 refers to the response a gateway replica returns for a revoked token and names no code, because the §15 error catalog defines no revoked-token code in either spelling, every §15 code is upper snake case, and §13.3's lowercase `token_revoked` reads as an informal mention. The CODE-6 rule-3 case and TEST-1 items 2 and 6 assert parity with the gateway's response. Rejected: option (b), changing `authmw` to emit `token_revoked`, which is a client-visible change on every gateway route and widens CODE-6 into the gateway. A follow-up reconciles §15 and §13.3 with the code (Defects). Rules 4 and 7 take the same form and name the gateway response each reproduces by the section that states it. §15 has no `token_validation_unavailable` row, and the rule-7 response carries the `details.reason` that §27.3.1 states.
- D24. Per owner decision 6 (2026-10-24), OD2 is settled as option (b). `lenny-ops` production readiness passes when either Postgres or the Kubernetes API is reachable, as §25.4 "Startup and Readiness" already states. SPEC-11 Edit 6 moves the §25.4 "Probes" readiness probe to the permissive `/healthz` and keeps `/healthz?strict=true` as a diagnostic check that no probe uses. CODE-13 makes the permissive `/healthz` handler implement the either-dependency rule, which it does not today, and renders `/healthz` as the production readiness probe. A Postgres outage fails every replica at once, so strict readiness empties the Service and makes the §25 degraded-mode design unreachable in production. That design covers owner decision 4, the Tier 2 and Tier 3 remediation locks, the Redis escalation fallback, and the §25.15 rows. Accepted cost: a single replica whose Postgres connection broke while its peers are healthy stays in rotation and serves degraded responses with `degradation.warnings`. Because liveness and startup share the permissive `/healthz`, a pod that reaches neither dependency now fails liveness, as §25.4 already states. Rejected: option (a), deferring the probe fix to a follow-up proposal, which leaves owner decision 4 effective only in non-production renders.
- D25. `lenny-ops` refuses one class of Lenny-issued token, the playground bearer, whose revocation a gateway replica checks in the §27.3.1 playground revocation key rather than in `issued_tokens` (SPEC-11 Edit 2 rule 7). Rule 7 keys on the `origin` claim that the gateway's own playground check keys on, so `lenny-ops` makes no store read for it, and no flow sends a playground bearer to `lenny-ops`, because the §27.7 CSP `connect-src` names only the playground origin and the gateway. Every other class that §10.2 "Signing topology" lists goes through rules 1 to 5. A platform-admin impersonation bearer carries no claim that distinguishes it from a user bearer and has no revocation record in any store (Defects), so `lenny-ops` honors it until `exp`, as every gateway replica does. Rule 4 takes precedence over rules 3 and 7 so that a token presented before the first successful read has one response. Rejected: a new impersonation claim with a refusal on `lenny-ops`, which changes the gateway mint and the §10.2 claims to refuse a token every gateway replica accepts; wiring `authmw` `PlaygroundRevocations` against Redis on `lenny-ops`, which adds a hot-path Redis read and a Redis fail-closed path for a token no flow sends there; and accepting only tokens with an unrevoked `issued_tokens` row, which needs a per-request store read.
- D26. OD3 is settled as option (c) by the owner's delegate (2026-10-24). This proposal leaves §17.4 "Dev mode guard rails" item 3 universal, as SPEC-9 Edit 2 stages it, and keeps `lenny-ops` on `--production`, as CODE-6 items 2 and 4 stage. The mismatch predates this proposal. The rule already states the required behaviour, so the follow-up is a direct code fix that lands after this proposal's implementation, rather than a widening of CODE-6. Option (a) was rejected for this proposal because it adds a flag, a chart change, and tests that no review lens examined. Option (b) was rejected because it weakens a security rule to match a defect.
- D27. The Token Service refuses a playground bearer as the caller token (SPEC-7 Edit 7, CODE-5 item 4). CODE-5's key set is the first Token Service verifier that accepts gateway-minted tokens, and a child minted from a playground bearer carries no `origin` claim, so §27.3.1 logout revocation does not name it and the §27.6 caps do not bind it. The playground refreshes through `POST /v1/playground/token`, so no flow presents a playground caller. The `subject_token` and `actor_token` are not checked, because §8.2 makes the playground bearer the `subject_token` of a delegation from a playground session. Accepted residual: a holder of another user's playground bearer and of a non-playground token in the same tenant can exchange that bearer as the `subject_token`, before or after logout, for a child that lives until the bearer's `exp`. The spec does not state whether the §27.3.1 revocation check applies to a body-borne `subject_token`, and a later proposal owns that question. Rejected: a `pg:revoked` read on the Token Service, which adds a Redis fail-closed path and does not stop a bearer exchanged before logout; and refusing a playground `subject_token`, which rejects the §8.2 delegation.

**Watch out for.**
- SPEC-1, SPEC-4, SPEC-6, and SPEC-9 contradict each other unless they land in one pass (spec-changes **Design**).
- Each implementation step must compile on its own. CODE-10 lands before CODE-4, and CODE-12 deletes the old types only after CODE-4, CODE-5, and CODE-6 (non-spec **Design**).
- The local key derivation must not use `ecdsa.GenerateKey` with the HKDF reader (CODE-1 item 3).
- After CODE-4 and CODE-5 a cloud install fatals unless `platform:jwt-signing` maps to an immutable key-version reference. The old `platform:token-service-signing` alias is no longer read.
- Only one `PublicKey` fetch per process: build the signer from the key set (non-spec **One key-set construction**).
- `tokenservice.NewServer`'s signer-as-verifier fallback must go, or the Token Service rejects every token (CODE-5 item 2).
- `lenny-ops` has no `--dev-mode`, and its production signal is `--production` (CODE-6 items 2 and 5).
- A `0.0.0.0/0` KMS egress peer on the gateway or `lenny-ops`, copied from `allow-token-service`, weakens the SSRF boundary (CHART-4).
- The rotation tests now expect a retried rotation to fail (CODE-9 item 3), and the tier-4 rotation test depends on CODE-1 item 3.
- Proposal 0095's files are not edited when its tier-4 narrowing is removed (TEST-1 item 3).
- `lenny-ops` must not wire the gateway's `RevocationFreshness` gate with `Cache.Stale`, which is option A (CODE-6 item 6).
- `lenny-ops` must not back `authmw.Options.PlaygroundRevocations` with Redis (CODE-6 item 6, D25).
- A chart-deployed `lenny-ops` that cannot reach Postgres refuses every Lenny-issued token for the life of the process. It reaches Postgres only through the CODE-6 item 6 chart change, and the self-managed answer-file renders give it no Postgres path (Defects).
- `cmd/lenny-gateway/user_revocation.go` and its test fake change with the CODE-9 store signature, or `cmd/lenny-gateway` stops compiling (CODE-9 item 4).
- After CODE-13 the permissive `/healthz` fails when neither Postgres nor the Kubernetes API is reachable, so the tier-4 Postgres-outage case needs a Kubernetes API for `lenny-ops` (TEST-1 item 2). The CODE-13 chart comment rewrite changes the dev-preset render, so the embedded manifests are regenerated in the same step (CODE-13 item 4).

## Goals

- A Lenny-issued token verifies on every gateway replica, every Token Service replica, and `lenny-ops`, and survives a restart of its signer.
- On a cloud provider, no private signing key exists in any Lenny process.
- The spec states the algorithm, key identity, key distribution, signing topology, rotation procedure, dev posture, and token lifetime, and its contradictions on these points are resolved.
- A KMS quota burst degrades mints with retryable 503s rather than tripping the breaker fleet-wide, and the spec sizes the sign rate and the quota.
- A subject or actor whose `issued_tokens` row is revoked cannot produce a token, including through a concurrent rotation.
- A production `lenny-ops` replica stays Ready during a Postgres outage while the Kubernetes API is reachable, so the §25.15 degraded mode and owner decision 4 hold in production.

## Non-goals

- Persisting the sealed HS256 key and reloading it through `KMSSignerFromSealed` (F-10.2.22's suggestion). Owner decision 1 rejects it, because every verifier would hold forging power and the key would sit in memory.
- A per-replica KMS-signed intermediate key, as a default or as a documented mitigation. Owner decision 1 rejects it as a default, and the non-tripping throttle path plus quota sizing remove the capacity motive.
- Separate gateway and Token Service signing keys that each verifier trusts. Every verifier would trust both, so the split adds an alias pair, a rotation, and an IAM binding with no containment, and the gateway already mints impersonation bearers and the 10-year admin token.
- Routing every gateway mint through the Token Service over a new internal RPC. `tokensv1` has no mint RPC. The change would add protocol surface and a hop on the playground and admin paths, contradict the §13.3 and §17.6 gateway-direct admin rotation, and leave key distribution unsolved.
- A JWKS endpoint served by the gateway or the Token Service as the verifier distribution channel. It needs a refresh rule, an unknown-`kid` fetch path, publisher trust, and startup ordering between components, and `GetPublicKey` over immutable key versions needs none of them.
- Keeping `/.well-known/jwks.json` as an output, always on, default on, or opt-in. No spec section defines it and no in-platform verifier reads it; a later proposal can add it together with a consumer.
- Public keys distributed in a Helm-rendered ConfigMap with `activateAt` scheduling, a 30 s re-read, and post-sign self-verification. It adds an operator copy step, a key-drift failure, clock-driven key selection, and propagation-lag rules. Fail-closed startup during a KMS outage is the accepted cost of the simpler design.
- Automatic leader-gated re-keying of the bootstrap admin token when the signing `kid` changes. The manual `rotate-token` step in rotation step 2 resolves the lockout with no new trigger.
- An exactly-once `platform.jwt_signing_key_rotated` audit emission, or emission through an extended §16.7 deployment-config event. No §16.7 entry defines the event, and rotation is a configuration rollout.
- A Postgres `signing_keys` table driven by a leader, or the runbook's `tokenService.signingKeySealed` and `signingKid` values. Helm values already hold which key signs and which verifies, and the table would add a migration, a coordinator, and a boot dependency on Postgres.
- Keeping `RotatingVerifier`'s in-process 24 h overlap timer. It starts at pod start, which is the wrong clock, and conflicts with config-held rotation state.
- Discovering rotation state from the KMS or relying on provider-native automatic rotation. AWS asymmetric keys have no version namespace, and AWS and GCP do not auto-rotate asymmetric keys, so behavior would differ per provider.
- A periodic or on-miss public-key refresh. Pinned versions are immutable, and an on-miss fetch would let an attacker-chosen `kid` drive KMS calls.
- `kid` as the KMS key reference string or as an operator-configured value (D7).
- New dedicated key-identity flags and values. The existing alias map already carries per-alias provider key references.
- A separate `kms.SigningKeys` or `kms.Signer` interface. `Provider` has six implementations, so extending it keeps one resolution path and one set of fakes.
- A HashiCorp Vault Transit adapter. No adapter, chart option, or validated need exists, and the §12.5 and §12.8 Vault mentions are outside this change.
- An HS256 dev signer for Lenny-issued tokens, or a third dev shared-key mechanism. The local provider's ES256 key from the existing `--kms-master-key-file` runs the production code path.
- Retiring `--bearer-trust-hmac-key-file` by having the CLI mint dev bearers from the local signing key. That widens the change into §17.4 and the embedded dev IdP stand-in, which is a different issuer.
- Requiring `LENNY_DEV_MODE` for local signing in addition to the production refusal of `local`. Local signing is no longer a bypass, and an extra gate would break non-dev-mode tier-4 stacks.
- Keeping `playground.bearerTtlSeconds` beside the new lifetime value. Two values for one token class would need a precedence rule.
- Applying the 900 s default to the bootstrap admin credential, to the session-creation `session_capability` token, or to delegated children. The admin credential is retired by rotation, and the session and delegation tokens have no refresh path (D13).
- A gateway-to-pod renewal path for the session-creation `session_capability` token. It is recorded as a follow-up under "Defects in the shipped tree that this proposal does not stage".
- Refusing every Lenny-issued token on `lenny-ops` while Postgres is down (owner decision 4 option A), or accepting only `lenny-ops`-audience tokens with revocation deferred (option C) (D22).
- Refusing impersonation bearers on `lenny-ops`, or making an impersonation bearer revocable (D25).
- Letting the self-rotation grant extend `exp` past `subject_token.exp`. It would allow an unbounded refresh chain without upstream re-authentication.
- Dropping the capacity strand. The validated scope names throttling backpressure, a sign-rate metric, a near-quota alert, and capacity text. D15 covers the scope's per-replica limit.
- Deleting the §13.3 re-read clause instead of implementing it. The `exp` clamp bounds expiry only, and §13.3 and §8.2 already require a revocation re-read.
- Holding the remote sign inside the advisory lock to match the current §13.3 wording (D14).
- Renaming `lenny_gateway_kms_signing_errors_total` now that the Token Service also emits it. The rename only causes churn, and the `job` label identifies the process.
- A new error code for throttling. `KMS_SIGNING_UNAVAILABLE` is already 503 `TRANSIENT` and retryable.
- Splitting the implementation into a local-only part 1 and a cloud part 2 (D21).
- Readiness-gated retry instead of fatal exit when the key set cannot load. Fatal exit matches the existing startup posture, and a crashlooping pod is equally fail-closed.
- RS256 or EdDSA. RS256 roughly quadruples signature size, and EdDSA is not available for KMS signing on every listed provider.
- A per-request verified-token cache to offset ES256 verification cost. The problem does not exhibit the cost, and §17.8 records it as a sizing note.
- Implementing the session-creation `session_capability` mint and delegation child-token signing. They are out of scope per the problem, and §10.2 "Signing topology" states which signer each will use.
- Adding an `issued_tokens` row to the §12.3 write-IOPS table (D20).
- Deferring the `lenny-ops` production readiness fix to a follow-up proposal (owner decision 6 option (a), D24).
- Changing `authmw` to emit `token_revoked` (OD1 option (b), D23).

## Open decisions for human to make

None. OD1, OD2, and OD3 are settled (D23, D24, D26).

## Defects in the shipped tree that this proposal does not stage

- `lenny-ops` admits its dev bearer-trust hook and the `X-Lenny-Tenant-ID`, `X-Lenny-User-ID`, and `X-Lenny-Roles` dev headers whenever `--production` is false (`cmd/lenny-ops/main.go`), and the chart defaults `ops.production` to false, while §17.4 "Dev mode guard rails" item 3 makes `LENNY_DEV_MODE` the single gate for every dev-mode security relaxation. An install that leaves `ops.production` unset therefore accepts the dev identity headers on `lenny-ops`. The specification already states the rule, so a direct code fix binds those relaxations to `LENNY_DEV_MODE` after this proposal lands (D26).
- Session creation (`POST /v1/sessions`) mints no `session_capability` token, although §10.2 says the session-creation path does; `pkg/gateway/sessionserver` has no signer. It is out of scope per the problem statement, and SPEC-1 names the gateway signer it will use. The 24 h `lenny-gateway` per-dialect cap that SPEC-7 Edit 2 states is wired only in the Token Service (`cmd/lenny-token-service/server.go`), so the follow-up that adds the gateway in-process mint also applies that cap to it.
- No path renews a session-creation `session_capability` token for the pod that holds it, so that token keeps its per-dialect cap instead of the 15-minute default (D13, owner decision 5). A follow-up proposal owns the gateway-to-pod renewal path, together with the session-creation mint above.
- Delegation child tokens are claim records that are never signed and never written to `issued_tokens`, and the gateway's `childtoken.Minter` checks the actor against the revocation cache under its own lock rather than through the Token Service. It is out of scope per the problem statement, and SPEC-1 names the Token Service as the signer.
- The §7.1 `uploadToken` key ring is also seeded per process (`cmd/lenny-gateway/token_signing.go`). It is a separate finding with a different key and consumer.
- No upstream-IdP JWKS verifier exists in production (T-10.2.1). It is a separate verifier path.
- The spec names production mode `LENNY_ENV=production`, while `providerflags` refuses `local` on `--environment=prod` (`LENNY_ENV=prod`). The drift predates this change and spans every production gate.
- The §12.3 write-IOPS table has no `issued_tokens` row for token issuance. It is a pre-existing sizing gap (D20).
- F-10.2.23 and F-10.2.24 (tenancy-mode behavior) are out of scope per the problem statement.
- `cmd/lenny-token-service` never sets `tokenservice.Options.RevocationPropagator`, so a committed rotation publishes no `token.revoked` event and records `propagation_mode: postgres_only`, although §13.3 "Token rotation and revocation" says the revocation propagates on the EventBus. Gateway replicas and `lenny-ops` learn of it only at their next 30-second read.
- The §15 error catalog has no row for a revoked token, and §13.3 "Token rotation and revocation" spells the code `token_revoked` in lower case, while `authmw` refuses a revoked `jti` with `401 TOKEN_REVOKED` (`pkg/gateway/middleware/auth/auth.go`). `lenny-ops` emits the same response (D23). §15 likewise has no row for `token_validation_unavailable`, which §13.3 "Authoritative durability for revocation" and `authmw` spell identically. A follow-up proposal adds the §15 rows and reconciles the §13.3 spelling with the code.
- Ending a platform-admin impersonation session revokes nothing. `impersonation.Service.End` stamps the ticket ended in a replica-local `MemStore` that no verifier reads, the bearer has no `issued_tokens` row, and it carries no claim that distinguishes it from a user bearer. Every gateway replica and `lenny-ops` therefore honor it until `exp`, at most the 1-hour impersonation maximum, and §11.4 user invalidation does not revoke it either (D25).
- No verifier enforces `aud` by default. The admin credential and impersonation bearers carry the `--bearer-expected-audiences` value, which is empty by default.
- Under an enforcing CNI, the self-managed answer-file renders give no Lenny client a Postgres path. PgBouncer listens on `pgbouncer.port` (default 6432), while `allow-pgbouncer` and every client egress peer admit 5432. The chart's `pgbouncer.ini` names no database, and no answer file sets `pgbouncer.databaseURLSecret`. `postgres.dsn` names `lenny-postgres-rw`, which no client egress policy reaches unless `postgres.gatewayEgressCIDR` is set. `lenny-ops` shares the gateway's path (CODE-6 item 6), so in those renders SPEC-11 Edit 2 rule 4 refuses every Lenny-issued token on it. A direct chart fix owns the path.
- `lenny-ops` sets no `authmw` `PlatformRoles` resolver (`cmd/lenny-ops/main.go` `buildAuthConfig`), so it authorizes on the token's `roles` claim, while the gateway lets a §10.2 platform-managed role row replace that claim (`cmd/lenny-gateway/httpsurface.go`, `userstorePlatformRoles`). A user whom a tenant-admin downgraded keeps the claimed role on `lenny-ops` until the token's `exp`. The gap predates this change, which widens only the set of token classes `lenny-ops` accepts, and a separate finding owns it.
- The §25.4 "Probes" YAML sets no `timeoutSeconds`, which implies kubelet's 1 s default against the 2 s probe timeout of §25.6. After CODE-13 the chart renders `timeoutSeconds: 3` on all three `lenny-ops` probes. The YAML is illustrative and its liveness values already differ from the chart, so adding `timeoutSeconds: 3` to it is a separate spec finding.
