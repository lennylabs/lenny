# Review log: Lenny-issued bearer tokens verify only on the process that signed them

## Standing context

### Settled

- Owner decision 1 (2026-10-23): production signing is remote asymmetric KMS signing, and every verifier verifies locally against public keys selected by `kid`. Rejected: one shared HS256 key sealed by the KMS, and a per-replica KMS-signed intermediate key as a default.
- Owner decision 2 (2026-10-23): Lenny-issued tokens have a fixed lifetime, the gateway never re-mints per interaction, and holders refresh by pulling.
- Owner decision 3 (2026-10-23): the default capability token lifetime is 15 minutes, operator-tunable within the bounds SPEC-3 Edit 1 states (`120 ≤ ttl ≤ 3600`).
- Owner decision 4 (2026-10-23): option B. Home: SPEC-11 Edit 2 (**Revocation set** rules 1 to 6); implementation: CODE-6 item 6; reasons, residual risks, and rejected options: summary D22.
- Owner decision 5 (2026-10-23): the 15-minute default governs every Lenny-issued token whose holder can refresh it by pulling: playground bearers and `POST /v1/oauth/token` tokens requested without `expires_in` (user bearers from rotation and scope narrowing, and operability-scope tokens). An explicit `expires_in` is honoured within the per-dialect caps. The session-creation `session_capability` token and the delegation `actor_token` path keep their caps. The gateway-to-pod renewal path is a follow-up proposal. Home: SPEC-3 Edit 1; implementation: CODE-8 items 3 to 5; summary D13.
- OD1 (owner's delegate, 2026-10-24): option (a). `lenny-ops` reuses the gateway's `authmw` unchanged and emits the gateway's existing revoked-token response, `401 TOKEN_REVOKED`. SPEC-11 Edit 2 rule 3 refers to the response a gateway replica returns for a revoked token and names no code, because §15 defines no revoked-token code and §13.3's lowercase `token_revoked` is an informal mention. The §15 row and the §13.3 spelling are a follow-up recorded under the summary's Defects. Home: SPEC-11 Edit 2 rule 3; tests: the CODE-6 rule-3 case and TEST-1 items 2 and 6; summary D23.
- Owner decision 6 (owner, 2026-10-24), answering OD2 with option (b): `lenny-ops` production readiness passes when either Postgres or the Kubernetes API is reachable. Home: SPEC-11 Edit 6 (§25.4 "Probes"); implementation: CODE-13 (the permissive `/healthz` handler, the harness wait, and the production readiness probe); tests: CODE-13's tier-1 and Helm cases and the readiness assertions in TEST-1 item 2; summary D24. Accepted cost: a replica whose own Postgres connection broke while its peers are healthy stays in rotation with `degradation.warnings`. Rejected: deferring the probe fix to a follow-up.
- Step (1a) passes a token with no `issued_tokens` row and rejects only on `revoked_at`. The round-1 fail-closed missing-row rule is withdrawn ([spec.2.fix-G1.1] and [spec.2.fix-design-G1.1] CORRECTS entries), because playground and impersonation bearers have no row and are the delegation `subject_token`, so the rule rejected every delegation from those sessions.
- The client-side per-replica KMS sign rate limit is deleted (round 4, [spec.4.fix-G2.1], summary D15). A static split of a fleet quota across replicas refuses demand the quota could serve, because the Token Service does not autoscale, and the provider throttle already returns the same retryable 503 fleet-wide without tripping the breaker. This departs from the problem statement's scope line "There is also a per-replica sign rate limit" as an explicit decision.
- Scope departures recorded as decisions in the summary: the per-replica limit (D15), the §12.2 rows (D20), key-identity flags and values replaced by the reserved aliases `platform:jwt-signing` and `platform:jwt-verify` (D5), and the verifier refresh rule replaced by a startup-loaded static key set (D8).
- The §25.15 closing paragraph ("the core operational loop ... continues to function") stays true under owner decision 4 for a `lenny-ops` that loaded its revocation set before the outage, so it needs no edit. This closes the round-4 OPEN on that paragraph.
- SPEC-11 Edit 5 (the `/v1/admin/me` Degradation qualification) is retired, because under owner decision 4 the unqualified sentence holds for every caller `lenny-ops` authenticates; the cold-start refusal lives in SPEC-11 Edit 2.
- The §25.4 GatewayClient holds the projected ServiceAccount token (`pkg/ops/gateway/token.go` `FileTokenLoader`; `ops-deployment.yaml` `expirationSeconds: 3600`), and no `lenny-ops` code requests a `POST /v1/oauth/token` token. `security.oidc.minTokenTTLSeconds` therefore never meets a token that `auth.capabilityTokenTtlSeconds` governs, and the 120 s floor has no conflict. SPEC-8's GatewayClient refresh-lead example is withdrawn. The spec-versus-chart default (300 s versus 600 s) predates 0097.
