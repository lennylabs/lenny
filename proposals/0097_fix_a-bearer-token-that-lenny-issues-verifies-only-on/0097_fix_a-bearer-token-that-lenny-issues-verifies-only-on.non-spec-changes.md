# Non-spec changes: Lenny-issued bearer tokens verify only on the process that signed them

## Design (implementation-facing)

The work follows one dependency chain. The KMS seam gains signing (CODE-1). The `pkg/auth/jwt` package gains a remote ES256 signer and a static key set (CODE-2), and the breaker learns throttling (CODE-3). The published JWKS endpoint and the rotation observer go (CODE-10). The three binaries are then wired to one signer construction and one key set (CODE-4, CODE-5, CODE-6), after which the per-process HMAC signer and `RotatingVerifier` are deleted (CODE-12). The outcome mapping (CODE-7), the lifetime knob (CODE-8), the revocation re-read (CODE-9), and the alert catalog (CODE-11) are independent of that chain beyond their stated dependencies. Each deliverable compiles on its own: a deliverable that changes an exported signature updates every caller in the same commit, and a type is deleted only in the deliverable that removes its last caller. CODE-13 moves `lenny-ops` production readiness to the either-dependency check of owner decision 6 and depends only on the SPEC-11 spec pass. The chart (CHART-1 to CHART-5), docs (DOCS-1, DOCS-2), records (REC-1), and the cross-process tests (TEST-1) follow.

**Ordering constraint.** Every adapter (local, aws, gcp, azure, the testinfra stub, and the tenantkms test fake) implements `Sign` and `PublicKey` in CODE-1, before any binary switches to remote signing in CODE-4 and CODE-5. No intermediate commit leaves a production provider without a signer.

**One key-set construction.** `jwt.LoadKeySet` (CODE-2) is the only code that calls `PublicKey` on the `platform:jwt-*` aliases, and the signer is built from the key set's signing entry. The gateway, the Token Service, and `lenny-ops` each call it once at startup. A second `PublicKey` fetch in a signer constructor is a defect, because the signer's `kid` and the verifier's `kid` must come from one fetch.

## Staged code changes

### CODE-1 · KMS seam: `Sign`, `PublicKey`, `ErrThrottled`, and signing-reference validation in every adapter

Targets: `pkg/kms/kms.go`, `pkg/kms/local.go`, `pkg/kms/aws/aws.go`, `pkg/kms/gcp/gcp.go`, `pkg/kms/azure/azure.go`, `pkg/kms/providerflags/providerflags.go`, `tests/testinfra/stubs/kms/provider.go`, and the fake Provider in `pkg/tenantkms/probemanager_test.go`.

1. Extend `kms.Provider` with:

   ```go
   // Sign returns the ES256 signature of a 32-byte SHA-256 digest under the
   // key the alias names, as the 64-byte JWS r||s encoding (RFC 7518 §3.4).
   Sign(ctx context.Context, alias string, digest []byte) ([]byte, error)
   // PublicKey returns the P-256 public key of the key the alias names.
   PublicKey(ctx context.Context, alias string) (*ecdsa.PublicKey, error)
   ```

   Add the sentinel `kms.ErrThrottled`. Every adapter wraps its provider's throttling error with it: AWS `ThrottlingException` and `LimitExceededException`, GCP `codes.ResourceExhausted`, and Azure HTTP 429. `Sign` rejects a digest whose length is not 32 bytes. `PublicKey` returns an error when the key is not an ECDSA P-256 key.
2. Each cloud adapter extends its narrow `keyClient` interface with the SDK's sign and get-public-key calls. AWS and GCP return ASN.1 DER signatures, which the adapter converts to the 64-byte r||s form, left-padding each half to 32 bytes. Azure returns r||s already. Every call passes its `ctx` to the SDK call, and `Sign` disables the SDK's retry for its own call (AWS per-call `RetryMaxAttempts = 1`, Azure `policy.WithRetryOptions` with `MaxRetries: -1`, GCP `gax.WithRetry` returning a nil `Retryer`), so a throttle returns `kms.ErrThrottled` from one provider request instead of surfacing as expiry of the CODE-3 `SigningCallTimeout`.
3. Local provider: derive the ES256 private key deterministically from the seed and a signing reference. The reference is the value `--kms-alias` maps the `platform:jwt-*` alias to, and for an unmapped alias it is the alias name. The `providerflags` local branch passes the `platform:jwt-*` entries of `AliasToKey` to the local provider; it ignores the map today.

   **IMPLEMENTOR'S CHOICE:** the scalar derivation — it is deterministic for a given (seed, reference) pair, uses an HKDF-SHA256 salt domain-separated from `kekMaterial`'s `alias\x00version` salt, yields distinct keys for distinct references, and builds the key from the derived scalar (for example with rejection sampling below the P-256 order). Do not pass the HKDF stream to `ecdsa.GenerateKey`: its output is not deterministic for a fixed reader by design, so two processes with one seed would derive different keys.
4. `providerflags`: when the provider is not `local`, reject at startup a `platform:jwt-signing` or `platform:jwt-verify` alias whose reference is repointable, per SPEC-1 **Production**. Update the `--kms-alias` help example to `platform:jwt-signing=<immutable P-256 key ref>`.
5. Rewrite the `kms.Provider` doc comment to describe both operation families: KEK wrap and unwrap for the envelope helper and the other wrap callers, and asymmetric `Sign` and `PublicKey` for the JWT signer. Remove the "sole caller" wording.
6. The testinfra stub gains `Sign` and `PublicKey` over an in-memory P-256 key per alias, plus fault injection for a hard error and for `kms.ErrThrottled`.

### CODE-2 · `pkg/auth/jwt`: context on `Sign`, remote ES256 signer, and the static key set

Targets: `pkg/auth/jwt/jwt.go`, `pkg/auth/jwt/kmssigner.go`, new `pkg/auth/jwt/keyset.go`, `pkg/auth/jwt/jwks.go`, `pkg/auth/jwt/breakersigner.go`, and every caller of `Signer.Sign`.

1. `jwt.Signer` becomes `Sign(ctx context.Context, c Claims) (string, error)`. The same commit updates every implementation (`BreakerSigner` and the existing HMAC-backed `KMSSigner`, which CODE-12 deletes) and every mint site, each of which passes its request context.
2. Add the remote ES256 signer to `kmssigner.go` as a new type beside the existing `KMSSigner`. It builds the JOSE header `{"alg":"ES256","typ":"JWT","kid":<thumbprint>}`, hashes the signing input with SHA-256, calls `Provider.Sign` on `platform:jwt-signing`, and base64url-encodes the r||s result. Its constructor takes the signing entry from the key set and fetches nothing. It implements no `Verifier`.
3. New `keyset.go`: `LoadKeySet(ctx, provider, aliasToKey map[string]string) (*KeySet, error)` calls `PublicKey` for `platform:jwt-signing` and, when `aliasToKey` has a `platform:jwt-verify` entry, for `platform:jwt-verify`, and returns any error. It indexes each key by its RFC 7638 thumbprint and exposes the signing entry. `KeySet.Verify` implements SPEC-2 and the `alg` rule of SPEC-1: it rejects any `alg` other than `ES256`, returns `VerifyError` reasons `missing_kid` and `unknown_kid` with no provider call, and then checks the ECDSA signature and the existing claim checks. `KeySet` is the only verifier of Lenny-issued tokens.
4. `jwks.go`: add the EC JWK form and the RFC 7638 thumbprint function to the existing JWK type.
5. `HMACSigner` keeps `Sign(c Claims)` without a context as a concrete method for `pkg/embedded/devauth` and tests, and keeps `Verify` for the dev-only embedded HMAC trust member. It no longer satisfies `jwt.Signer`, so no production wiring can pass it where a signer is expected.
6. Test sites that pass a `*jwt.HMACSigner` where a `jwt.Signer` is expected change in this commit, because item 5 stops them compiling. The sites that set `tokenservice.Options.Signer` are in `pkg/tokenservice` (`audit_test.go`, `drift_test.go`, `exchange_type_test.go`, `request_validation_test.go`, `revocation_propagation_metric_test.go`, `revocation_test.go`, `rotation_test.go`, and `unavailable_test.go`), `tests/tier3_contract/oauth_token/oauth_token_test.go`, `tests/tier3_contract/oauth_token/oauth_token_record_test.go`, and `tests/tier9_security/token_revocation_propagation_alert_test.go`. The sites that set `playground.Options.Signer` are in `pkg/gateway/mcpfabric/playground` (`playground_test.go`, `cookie_opaque_test.go`, `idle_sweep_test.go`, `sessionrecord_test.go`, `token_currentexp_test.go`, and `user_invalidation_test.go`), `tests/tier3_contract/playground/playground_test.go`, and `tests/tier9_security/tenant_deletion_isolation_test.go`. Each passes a test-local adapter whose `Sign(ctx, c)` calls the concrete `HMACSigner.Sign(c)`. A site that also sets a `Verifier` keeps the `HMACSigner` there. The adapter is not a `jwt.Verifier`, so a site that sets no `Verifier` and relies on the signer-as-verifier fallback of `tokenservice.NewServer` or `playground.New` sets `Verifier` to the same `HMACSigner`; without it the handler is left with no verifier. The `Signer` interfaces of `pkg/gateway/externalapi/admintoken` and `pkg/gateway/credentials/impersonation` take the context in this commit too, because the gateway passes its `BreakerSigner` to both and item 1 updates their mint sites. The sites that pass an `HMACSigner` to `admintoken.New` therefore take the same adapter: `pkg/gateway/externalapi/admintoken/admintoken_test.go` and `tests/tier2_component/stores/admintoken_rotation_test.go`. The test-local `jwt.Signer` fakes, `stubSigner` in `pkg/auth/jwt/breakersigner_test.go` and `breakerStubSigner` in `pkg/tokenservice/kms_unavailable_test.go`, and the impersonation fakes, `fakeSigner` in `pkg/gateway/credentials/impersonation/service_test.go` and `stubImpSigner` in `pkg/gateway/externalapi/admin/impersonation_test.go`, gain the context parameter under item 1. Sites that use an `HMACSigner` only as a `Verifier` and call its concrete `Sign(c)`, such as `tests/tier3_contract/ops_endpoints/helpers_test.go` and `tests/tier3_contract/rest_auth/auth_test.go`, compile unchanged and are not edited.

   **IMPLEMENTOR'S CHOICE:** one adapter per test package or one shared test helper. The bound is that the adapter lives in a `_test.go` file or under `tests/testinfra/`, so no package under `pkg/` or `cmd/` can import a type that makes an `HMACSigner` a `jwt.Signer`, and the test files of every tier build tag (`contract` and `security` among them) compile at this step's commit.

### CODE-3 · Breaker backpressure: throttling, `Retry-After`, and the outcome hook

Target: `pkg/auth/jwt/breakersigner.go`.

1. `BreakerSigner.Sign` runs the inner call under `context.WithTimeout(ctx, SigningCallTimeout)`, a new 5-second constant with a `CallTimeout` override field beside `Cooldown`, and classifies the result:
   - A success calls `recordSuccess`. Outcome `ok`.
   - `kms.ErrThrottled`: outcome `throttled`.
   - Any other error while the caller's `ctx` is done: outcome `error`. Test `ctx.Err()` on the caller's context rather than the error's type, because expiry of `SigningCallTimeout` is also `context.DeadlineExceeded`.
   - Any other error, including expiry of `SigningCallTimeout` while the caller's `ctx` is live, calls `recordFailure` and `OnSigningFailure`. Outcome `error`.

   A throttled or caller-done result neither counts toward the trip nor clears the failure run. In half-open state it clears `probeInFlight` and leaves the breaker half-open, so the next call is admitted as the probe. Otherwise the slot stays held and the breaker refuses every mint until restart.
2. Every error `Sign` returns is a `*SigningError{RetryAfter time.Duration}`, which wraps the inner error when there is one. `RetryAfter` is the SPEC-4 `Retry-After` duration. Callers detect a signing error with `errors.As`. `RetryAfterSeconds() int` returns `RetryAfter` rounded up to whole seconds with a floor of 1, and every CODE-7 writer sets the header from it. A breaker-open refusal wraps the existing `ErrSigningUnavailable` sentinel, so existing `errors.Is` checks keep holding.
3. Extend `BreakerObserver` with `OnOutcome(outcome string)`, called once per `Sign` with one of `ok`, `throttled`, `circuit_open`, or `error` (SPEC-5 **JWT sign requests** row). `OnSigningFailure` fires only where item 1 calls `recordFailure` and `OnRejected` only for `circuit_open`, so `lenny_gateway_kms_signing_errors_total` stops counting throttled requests. `pkg/auth/jwt` gains no metrics dependency.

### CODE-9 · In-transaction source-token revocation re-read

## Edge cases and accepted failure modes

- **Local provider without a master key file.** A process started without `--kms-master-key-file` derives from a random seed, and its tokens verify only on itself. This is the developer's single-process case. The chart (CHART-2) and the harness (TEST-1) always pass a file.
- **`lenny-ops` reaches neither Postgres nor the Kubernetes API.** After CODE-13 the permissive `/healthz` returns 503, so liveness restarts the pod, as §25.4 "Probes" states. Today's handler keeps such a pod alive. A pod that reaches either dependency stays live and Ready.
- **Upgrade of a cloud-provider install.** The chart refuses to render until `kms.signQuotaPerSecond` is set and `kms.endpointCIDR` names the private KMS endpoint subnet (SPEC-10 Edit 1, CHART-4). The shipped `0.0.0.0/0` default fails, so the upgrade of the Token Service and every other component waits on those two values.
- **Playground bearer exchanged as a `subject_token`.** A holder of a playground bearer and of a non-playground caller token in the same tenant can exchange the bearer as the `subject_token` of `POST /v1/oauth/token`, before or after logout, for a child that lives until the bearer's `exp` (D27). The Token Service refuses the bearer only as the caller token (CODE-5 item 4). DOCS-2 states the residual on the web playground page.
- **Embedded gateway restart under `kms.provider=local`.** The master key Secret survives a gateway pod restart (CHART-2), so the signing key does too, while the embedded in-memory `issued_tokens` rows and revocation cache do not (§17.4). A gateway-minted token revoked before the restart verifies again after it until its `exp`. Before this change each gateway process signed with a random key, so a restart invalidated every gateway-minted token. The case is accepted, because Embedded Mode is development-only and its CLI presents the dev bearer rather than a key-set token. `lenny down --purge` clears the Secret.
- **A concurrent rotation whose loser had already signed.** The loser's signed token is discarded (CODE-9). One wasted KMS `Sign` call is the cost.
