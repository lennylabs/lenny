The external-protocol Task surface (the MCP/A2A primitive, the `lenny/delegate_task`, `lenny/get_task_tree`, and `lenny/send_message` tool names, the §8.8 protocol-mapping table, and the MCP-output strings in `MCPProtocolState`) is kept. ## 1. Problem

Proposal 0002 (applied 2026-06-12) collapsed the session/task execution model to a single session unit and explicitly deferred a "Phase 2" lexical sweep of internal `task` names in Go identifiers, file paths, and proto field names to a separate cleanup proposal (`proposals/0002_fix_session-service-execution-model-pod-occupancy-claim.md:33`, `:130`, `:1337`, `:2156`). That separate proposal does not exist. The `proposals/` directory holds only 0001 (auditor), 0002 (the deferring proposal), 0003 (nonce-only mode), and 0004 (concurrent-slot); 0003's "Phase 2" references are the build-sequence deliverable numbering (`spec/18:117`) rather than this sweep. The deferred work is unstaged.

**Phase 1's structural collapse landed.** `executionMode` is the `session`/`service` enum (`pkg/apis/lenny/v1alpha1/runtime_types.go:39`, `sandbox_types.go:47`, `sandboxtemplate_types.go:117`), `pkg/gateway/taskdriver` was removed, the between-task lifecycle frames are gone, and migration 0167 renamed the `task_policy` columns to `session_policy` on both registries and replaced the `execution_mode` CHECK with `('session','service')`. The rename surface that remains is cross-cutting: roughly 51 Go files reference `TaskRecord`/`TaskResult`/`taskcleanup`/`taskusage`/`TaskID`/`taskId`, with exported-identifier counts `TaskID` 134, `TaskResult` 77, `TaskRecord` 36, `TaskSpec` 34, `TaskHandle` 24, `TaskUsage` 14, `TaskReuseQuantile` 9, plus the proto `task_id` fields (`schemas/lenny-adapter.proto:876` field 8, `:1069` field 6), the §8.8 `TaskRecord`/`TaskResult` durable schema, the SDK types, and the manifest `taskId` field (`spec/04:768`, `:798`).

**The premise that 0002 contains a self-contradiction is refuted.** The single §6.51 directive that produced the §8.8 line "carry the external-protocol vocabulary" (`spec/08:831`) is the same directive that says "the lexical renames of `TaskRecord`, `TaskResult`, and `taskId` are deferred to Phase 2" (`proposals/0002...:1337`). The §8.8 sentence is a Phase-1 rationale for keeping the spelling during Phase 1, with the rename deferred, rather than a permanent freeze. The two statements are mutually consistent: keep the spelling in Phase 1, sweep it in Phase 2. The work this proposal does is to apply the owner's governing three-way classification rule, which is external to the spec text (it appears nowhere in `spec/` or any committed doc), to each surface and to perform the deferred renames.

**The owner's three-way classification rule.** Names an external standard defines (the MCP/A2A Task primitive that clients interact with at the boundary) cannot be renamed. Lenny's own APIs, proto, and schemas (defined independently of any standard) are renamed where applicable. Purely-internal identifiers and packages are renamed. The rule turns on the origin of the name rather than on ownership of the transport. The genuine standard boundary is the `ExternalProtocolAdapter` translation layer (`pkg/gateway/mcp/mcp.go`, the `/mcp` surface) and the MCP-output mapping in `pkg/task/state/state.go:88` (`MCPProtocolState`'s output strings). `pkg/session/state/state.go:138` already performs the identical Lenny-to-MCP-surface mapping with no "Task" vocabulary, which establishes that the term is a Lenny-side identifier choice rather than a standard obligation.

**Rename candidates.** The Lenny-defined candidates include the §8.8 durable schema (which is renamed at the prose level only; see below) and the `lenny-adapter.proto` `task_id` (Lenny's own gateway-to-adapter transport, unrelated to MCP/A2A). The internal candidates include `pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, `pkg/gateway/taskusage`, the `TaskReuseQuantile` Go method (which now reads the already-renamed `lenny_pod_session_reuse_count` metric), and stale Phase-1 comments (`taskusage.go:14` "the task/concurrent execution modes"; `openapi.json:880` "delegation task tree").

**Two scope corrections versus the original problem statement, both confirmed by direct evidence.**

1. `migrations/` is not a rename target. Migration 0167 already renamed `task_policy` to `session_policy` on the live schema (`migrations/0167_...up.sql:97`, `:99`) and replaced the `execution_mode` constraint. The residual `task` references in 0001/0022/0085 are frozen append-only historical SQL and comments that must not be edited.
2. The `lenny_task_*` metric family was already renamed by Phase 1 and is out of scope (`proposals/0002...:2202`). `TaskReuseQuantile` is a Go method name rather than a metric name.

**Genuinely-contested boundary cases.** The proposal records adjudications for the proto `task_id` (whose own comment classifies "Task" as the external-protocol name) and for the §8.8 schema field naming, and it resolves the `taskId`/`sessionId` coexistence question (`spec/08:813-814` carry both as distinct fields though production sets both from the same session-derived value).

Findings: this proposal stages the Phase-2 sweep that 0002 deferred at `proposals/0002...:33`, `:130`, and `:1337`. Implementation runs through the existing build-gaps flow.

## 2. Decisions

The following were decided in review and constrain this design.

- **The premise of a 0002 self-contradiction is rejected.** The §8.8 sentence "carry the external-protocol vocabulary" (`spec/08:831`) and the Phase-2 deferral (`proposals/0002...:130`, `:1337`) are mutually consistent statements within the same §6.51 directive: keep the spelling in Phase 1, sweep it in Phase 2. This proposal performs the deferred sweep; it does not resolve a contradiction that does not exist.
- **The owner's three-way classification rule is the design axis and is external to the spec.** Standard-defined names (the MCP/A2A Task primitive clients interact with) are kept; Lenny-defined APIs, proto, and schemas are renamed where applicable; purely-internal identifiers and packages are renamed. The rule turns on the origin of the name rather than on ownership of the transport.
- **The genuine standard boundary is the `ExternalProtocolAdapter` translation layer** (`pkg/gateway/mcp/mcp.go`) and the MCP-output side of `pkg/task/state.MCPProtocolState`. These keep the "Task"/MCP vocabulary. `pkg/session/state/state.go:138` already maps session states to the MCP surface with no "Task" term, which establishes that the MCP-mapping role does not require the standard term.
- **The `lenny/delegate_task`, `lenny/get_task_tree`, and `lenny/send_message` tool names are kept.** They are Lenny-namespaced tool strings that surface the client's external-protocol Task concept (an MCP/A2A Task), they are part of the wire and tool contract callers depend on, and renaming them would break the standard-aligned client surface for no internal benefit. Keeping them means the "task tree" delegation vocabulary (§8.5, §8.9, `lenny/get_task_tree`) and the openapi "delegation task tree" summary string (`openapi.json:880`) stay as the standard-aligned surface.
- **`migrations/` is not in scope.** Migration 0167 already renamed the live `task_policy` columns to `session_policy` and replaced the `execution_mode` CHECK with `('session','service')`; migration files are append-only history and the residual `task` text in 0001/0022/0085 is frozen historical SQL and comments that must not be edited.
- **The `lenny_task_*` metric family is out of scope; Phase 1 already renamed it** (`lenny_pod_session_reuse_count` etc., `proposals/0002...:43`, `:2202`). `TaskReuseQuantile` is an internal Go method name reading the already-renamed metric and is in scope as an internal rename.
- **Generated artifacts are never hand-edited.** `lenny-adapter.pb.go`, `zz_generated.deepcopy.go`, and the CRD manifests under `charts/lenny/crds` and `pkg/embedded/crds` regenerate from the proto and the `+kubebuilder`-marked API types via `make generate` / `make generate-proto`; the rename edits the proto and Go sources and regenerates.
- **`taskId` and `sessionId` carry the same value in production** (every `TaskID` assignment derives from a session id: `taskrecord.go:36-37`, `tree.go:175`, `mcptools.go:3941/4201/4371`, `usage.go:641/855`), but §8.8 retains both as distinct fields. The schema description keeps the two-field structure to avoid a value collision and to keep the record forward-compatible, rather than merging them.
- **v1 ships one implementation per concern with no compatibility shims.** No deployments exist in the wild, so renamed Go identifiers, package paths, and the affected SDK types are changed in place with all callers updated and no deprecated aliases, dual names, or migration shims.

## 3. Design overview

The sweep classifies each `task`-named surface under the owner's three-way rule and applies the rename the classification dictates, with no behavior change. The external-protocol Task surface stays: the MCP/A2A primitive, the `lenny/delegate_task`/`lenny/get_task_tree`/`lenny/send_message` tool names, the §8.8 protocol-mapping table, the MCP-output strings in `MCPProtocolState`, and the `/mcp` adapter. The Lenny-defined and purely-internal surfaces are renamed: the internal Go packages and types (`pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, `pkg/gateway/taskusage`), the `TaskReuseQuantile` method, and the stale Phase-1 comments. The §8.8 durable-schema spec edit is narrowed to a single sentence that records the settled post-Phase-1 classification and removes the deferral cruft, while keeping the `TaskRecord`/`TaskResult`/`taskId` spellings so the section stays consistent with its cross-references in §7, §10, §12, and §15.

```
Classification (owner's three-way rule, external to the spec)
  origin of the NAME decides keep vs. rename
        |
        +-- KEPT (standard-defined / standard-aligned)
        |     MCP/A2A Task primitive; lenny/delegate_task,
        |     get_task_tree, send_message; §8.8 protocol-mapping table;
        |     MCPProtocolState output strings; /mcp adapter
        |
        +-- RENAMED (Lenny-defined)
        |     §8.8 durable-schema deferral prose (C1, sentence rewrite,
        |       schema spellings kept for cross-reference consistency)
        |
        +-- RENAMED (purely internal)
              pkg/task, pkg/task/state, pkg/sandbox/taskcleanup,
              pkg/gateway/taskusage (C3); TaskReuseQuantile (C4);
              stale Phase-1 comments (C3/C4); tests/spec-map.json §8.8 (C6)
```

The renames are mechanical and carry all callers in place. No control flow, wire semantics, or persisted value changes; `taskId` and `sessionId` continue to hold the same session-derived value.

## 4. Detailed design

### 4.1 §8.8 durable-schema classification (C1)

The §8.8 text currently reads "The `TaskRecord` and `TaskResult` schemas and the `taskId` field carry the external-protocol vocabulary for the session's execution" (`spec/08:831`), which is the Phase-1 rationale for deferring the rename. The minimal correct change rewrites that one sentence to state the settled post-Phase-1 classification: `TaskRecord`, `TaskResult`, and `taskId` are the external-protocol-facing names Lenny keeps, the durable record is the protocol surface of a session, and adapters map at the boundary. The schema names are kept.

The schema names are kept because they are cross-referenced as durable record types across §7 (`spec/07:111`, `:429`), §10 (`spec/10:395`), §12 (`spec/12:786`, `:810`), and §15 (`spec/15:1500`, the `blobStore.taskRecordTtlSeconds` config knob at `spec/15:1569`, `:2451`, `:2476`). Renaming the §8.8 schema while leaving every cross-reference would name the same durable type two ways, which the throughline and internal-consistency rules make a defect. The committed spec already classifies these names as external-protocol vocabulary at `spec/08:831` and the proto comment at `schemas/lenny-adapter.proto:871-872` ("`Task` is the external protocol name for the session"), and §15:1479 frames `TaskResult` as "Lenny's internal content model" that the adapter translates at the boundary. Keeping the spelling and rewriting only the deferral sentence makes §8.8 agree with §15:1479 and the proto comment, removes the deferral cruft, and touches one section with no cross-reference fan-out.

The staged edit is in Section 6.

### 4.2 Internal Go package and type renames (C3)

`pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, and `pkg/gateway/taskusage` are purely-internal identifiers and package paths with no external-standard origin. The spec references none of these Go package paths (a grep of `spec/` for `pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, `pkg/gateway/taskusage` returns nothing), so package names are pure implementation governed by `code-best-practices.md` rather than by §8.8. The exported Go types are already Lenny-own names qualified by the package: `record.go:115` `type Record struct`, `record.go:130` `type Result struct`, plus `Message`, `Usage`, and `TreeUsage`. Only the package name `task` and the JSON wire tags (`record.go:117` `json:"taskId"`) carry the word "task", and the JSON tags are wire format this proposal does not change.

The package names are stale after the session/task collapse: `pkg/sandbox/taskcleanup/taskcleanup.go:3` documents the package as "the §6.2 recycle disposition branching for a recycling session-mode pod" with no task semantics, and `pkg/gateway/taskusage/taskusage.go:14` carries the dead comment "the dedicated timers land with the task/concurrent execution modes" for modes 0002 removed. `code-best-practices.md` requires packages "named for the concern or the spec component it implements", so these renames are legitimate code hygiene.

The reconciliation, decoupled from C1's schema-name decision:

- Rename `pkg/sandbox/taskcleanup` to its current concern under `code-best-practices.md` alone: `pkg/sandbox/recyclecleanup` (or `podscrub`) per its §6.2 whole-pod recycle role. Update its importers (`pkg/adapter/scrub`, `pkg/gateway/recycle`, `pkg/gateway/leasecontrol`).
- Rename `pkg/gateway/taskusage` to a `TaskResult`-rollup name that deconflicts with the existing `pkg/gateway/sessionusage`. Update all its non-test importers: `pkg/gateway/mcptools` (`mcptools.go:79`, the `TaskUsage *taskusage.Builder` field at `:442`, and the `resolveChild`/`collectChildResults` signatures at `:3994`/`:4104` on the delegation result-collection path), `pkg/gateway/sessionserver` (`sessionserver.go:71`), and `cmd/lenny-gateway` (`main.go:289`, the `taskusage.New(...)` wiring at `:3528`). Rewrite the package doc comment (`taskusage.go:1-22`), which contains the stale "task/concurrent execution modes" clause at line 14, as part of this package rename.
- Leave the Go type names `task.Record` / `task.Result` and all JSON wire tags (`taskId`, etc.) unchanged, since they are already Lenny-own and the wire format is out of scope. The `pkg/task` package rename, if kept, names the package without requiring §8.8 to change.
- Resolve the `pkg/task/state` question explicitly. `pkg/session/state/state.go:138` `MCPProtocolState` already performs the full §8.8 Lenny-session-to-MCP projection across every state with metadata annotations. `pkg/task/state/state.go:88` `MCPProtocolState` is a strict subset whose terminal outputs are byte-identical (both map `Completed`→`completed`, `Failed`→`failed`, `Cancelled`→`canceled`, `Expired`→`failed`, `InputRequired`→`input_required`), and `usage.go:957-972` `mcpStateForSession` routes terminal states through `taskstate` and the rest through `sessionstate`, producing the same strings either way. State whether `pkg/task/state` folds into `pkg/session/state` (the one-implementation-per-concern outcome) or stays a distinct package; do not blind-rename a package that may be dead by duplication. This proposal scopes behavior change out, so the merge-versus-rename choice is recorded as an open decision in Section 8. Whichever way the decision goes, `tests/change-graph.json` carries the glob key `pkg/task/state` (`tests/change-graph.json:312`) with its `pkg/task/state/...` unit value (`:313`), and the tier-0 `validate-maps` file-existence check (`cmd/lenny-test/cmd_validate.go:278-313`, wired into the static tier at `cmd/lenny-test/cmd_run.go:733` and listed at `tests/groups.yaml:93`) fails when a glob key points at a missing path. The renamed path is not exempt under `tests/change-graph-pending.txt`, whose exemption is scoped to forward references that do not yet exist on disk rather than to renames. The rename or fold must therefore move that key (and its unit value) to the renamed package path, or fold it into the existing `pkg/session/state` entry (`:309-310`), so tier 0 stays green.
- The file count is roughly 51 Go files that reference these identifiers (across `pkg/`, `cmd/`, and `sdks/`), correcting the broader Phase-2 figure of 70 that spans every change. `TaskReuseQuantile` is handled by C4 and is not in C3's target list.

The MCP-output side of `pkg/task/state.MCPProtocolState` keeps the MCP output vocabulary at the standard boundary even as the package and `State` type rename.

### 4.3 The `TaskReuseQuantile` method and stale comments (C4)

`TaskReuseQuantile` (`pkg/gateway/gatewaymetrics/gatewaymetrics.go:3187`) is an internal Go method whose underlying metric was already renamed to `lenny_pod_session_reuse_count` by Phase 1; the method name lags the metric, which is session vocabulary everywhere (`spec/05:570`, `spec/16:126`, `pkg/observability/metrics/catalog.go:200`, `pkg/gateway/gatewaymetrics/gatewaymetrics.go:2612`). The consumer-side interface is already named `PoolSessionReuseMedian` (`pkg/controller/poolscaling/controller.go:291`). `TaskReuseQuantile` is not the only lagging identifier. None of the three carries an external-protocol classification: each reads or writes the session-vocabulary metric and none has a production caller (a grep of `pkg/`, `cmd/`, and `sdks/` for `ObserveTaskReuseCount` and `.TaskReuseQuantile(` outside `gatewaymetrics.go` and its test returns nothing). The full `TaskReuse` identifier family lags the metric and is in scope for C4.

The reconciliation renames the full `TaskReuse` identifier family across two files. In `pkg/gateway/gatewaymetrics/gatewaymetrics.go`: rename the method `TaskReuseQuantile` to `SessionReuseQuantile` (the function at `:3187` plus the doc-comment mentions at `:3181` and `:3260`), the method `ObserveTaskReuseCount` to `ObserveSessionReuseCount` (the function at `:3174` plus the doc-comment mention at `:3170`), and the struct field `taskReuseCount` to `sessionReuseCount` (the declaration at `:775`, the comment at `:770`, the local variable and struct-init assignment at `:2611` and `:3066`, the registration list at `:2787`, and the field read at `:3178`). The two surplus targets from the original draft are reassigned. ## 7. Non-goals
