# Proposal: Phase 2 task-vocabulary sweep: rename internal "task" identifiers, remove the dead gateway↔adapter `task_id` gRPC field, and keep the external-protocol Task surface

- **Status:** Verified (2026-06-17). Converged after 3 adversarial review rounds (3 findings fixed); awaiting sign-off. An end-to-end trace confirmed the gateway↔adapter proto `task_id` field carries no information, so it is removed from the gRPC, and the accompanying spec and documentation edits are staged.
- **Date:** 2026-06-17.
- **Scope:** Performs the "Phase 2" lexical sweep of internal `task` names that proposal 0002 deferred when it collapsed the session/task execution model to a single session unit, and removes the dead gateway↔adapter gRPC `task_id` field. The structural Phase 1 collapse landed (`executionMode` is the `session`/`service` enum, `pkg/gateway/taskdriver` was removed, migration 0167 renamed the `task_policy` columns to `session_policy`). The residual rename surface spans Go packages and identifiers (`pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, `pkg/gateway/taskusage`, `TaskReuseQuantile`), stale Phase-1 comments, the §8.8 durable-schema deferral language, and the `tests/spec-map.json` §8.8 entry. The sweep applies the owner's three-way classification rule: names an external standard defines (the MCP/A2A Task primitive clients interact with at the boundary) are kept; Lenny-defined APIs, proto, and schemas are renamed where applicable; purely-internal identifiers and packages are renamed. The external-protocol Task surface (the MCP/A2A primitive, the `lenny/delegate_task`, `lenny/get_task_tree`, and `lenny/send_message` tool names, the §8.8 protocol-mapping table, the MCP-output strings in `MCPProtocolState`, and the manifest/SDK `taskId` identifier) is kept. Separately, the dead gateway↔adapter gRPC `task_id` field (`StartSessionRequest` field 8 and `ResumeRequest` field 6) is removed: an end-to-end trace confirmed the gateway never populates it and the adapter already derives the manifest `taskId` from the session id, so the field carries no information. This proposal stages spec edits to §8.8 and to the manifest `taskId` descriptions, the proto field removal, the documentation edits, and the code-side renames the implementer applies after sign-off.

This document stages spec and documentation edits as fenced markdown blocks under Section 6 and records the code-side renames and the proto field removal that follow. It does not apply any spec edit itself; the `implement-proposal` skill lands the staged §8.8 and manifest-description edits in `spec/`, the documentation edits in `docs/`, and verifies them, then implements the code renames, the proto field removal, and updates `tests/spec-map.json`. ## 1. Problem

Proposal 0002 (applied 2026-06-12) collapsed the session/task execution model to a single session unit and explicitly deferred a "Phase 2" lexical sweep of internal `task` names in Go identifiers, file paths, and proto field names to a separate cleanup proposal (`proposals/0002_fix_session-service-execution-model-pod-occupancy-claim.md:33`, `:130`, `:1337`, `:2156`). That separate proposal does not exist. The `proposals/` directory holds only 0001 (auditor), 0002 (the deferring proposal), 0003 (nonce-only mode), and 0004 (concurrent-slot); 0003's "Phase 2" references are the build-sequence deliverable numbering (`spec/18:117`) rather than this sweep. The deferred work is unstaged.

**Phase 1's structural collapse landed.** `executionMode` is the `session`/`service` enum (`pkg/apis/lenny/v1alpha1/runtime_types.go:39`, `sandbox_types.go:47`, `sandboxtemplate_types.go:117`), `pkg/gateway/taskdriver` was removed, the between-task lifecycle frames are gone, and migration 0167 renamed the `task_policy` columns to `session_policy` on both registries and replaced the `execution_mode` CHECK with `('session','service')`. The rename surface that remains is cross-cutting: roughly 51 Go files reference `TaskRecord`/`TaskResult`/`taskcleanup`/`taskusage`/`TaskID`/`taskId`, with exported-identifier counts `TaskID` 134, `TaskResult` 77, `TaskRecord` 36, `TaskSpec` 34, `TaskHandle` 24, `TaskUsage` 14, `TaskReuseQuantile` 9, plus the proto `task_id` fields (`schemas/lenny-adapter.proto:876` field 8, `:1069` field 6), the §8.8 `TaskRecord`/`TaskResult` durable schema, the SDK types, and the manifest `taskId` field (`spec/04:768`, `:798`).

**The premise that 0002 contains a self-contradiction is refuted.** The single §6.51 directive that produced the §8.8 line "carry the external-protocol vocabulary" (`spec/08:831`) is the same directive that says "the lexical renames of `TaskRecord`, `TaskResult`, and `taskId` are deferred to Phase 2" (`proposals/0002...:1337`). The §8.8 sentence is a Phase-1 rationale for keeping the spelling during Phase 1, with the rename deferred, rather than a permanent freeze. The two statements are mutually consistent: keep the spelling in Phase 1, sweep it in Phase 2. The work this proposal does is to apply the owner's governing three-way classification rule, which is external to the spec text (it appears nowhere in `spec/` or any committed doc), to each surface and to perform the deferred renames.

**The owner's three-way classification rule.** Names an external standard defines (the MCP/A2A Task primitive that clients interact with at the boundary) cannot be renamed. Lenny's own APIs, proto, and schemas (defined independently of any standard) are renamed where applicable. Purely-internal identifiers and packages are renamed. The rule turns on the origin of the name rather than on ownership of the transport. The genuine standard boundary is the `ExternalProtocolAdapter` translation layer (`pkg/gateway/mcp/mcp.go`, the `/mcp` surface) and the MCP-output mapping in `pkg/task/state/state.go:88` (`MCPProtocolState`'s output strings). `pkg/session/state/state.go:138` already performs the identical Lenny-to-MCP-surface mapping with no "Task" vocabulary, which establishes that the term is a Lenny-side identifier choice rather than a standard obligation.

**Rename candidates.** The internal candidates include `pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, `pkg/gateway/taskusage`, the `TaskReuseQuantile` Go method (which now reads the already-renamed `lenny_pod_session_reuse_count` metric), and stale Phase-1 comments (`taskusage.go:14` "the task/concurrent execution modes"; `openapi.json:880` "delegation task tree").

**Removal candidate: the gateway↔adapter gRPC `task_id` field.** The `lenny-adapter.proto` `task_id` (Lenny's own gateway-to-adapter transport, unrelated to MCP/A2A) is the one Lenny-defined `task` surface this proposal removes rather than renames or keeps. Section 4.4 records the end-to-end trace that justifies the removal.

**Resolved boundary case: the proto `task_id` is removed.** An end-to-end trace (Section 4.4) established that the gateway↔adapter gRPC `task_id` carries no information: no gateway code path populates it, the adapter already defaults the manifest `taskId` to the session id, checkpoint keys use `(tenant_id, session_id, slot_id)` rather than `taskId`, and a delegated child's `task_id` equals the child's own session id rather than the tree-root identity. The field is removed from the proto. The §8.8 schema field naming and the manifest/SDK `taskId` are kept as the external Task surface, and the `taskId`/`sessionId` coexistence question is resolved by the v1 "task record == session row" invariant (`spec/08:813-814` carry both as distinct fields though production sets both from the same session-derived value).

**Two scope corrections versus the original problem statement, both confirmed by direct evidence.**

1. `migrations/` is not a rename target. Migration 0167 already renamed `task_policy` to `session_policy` on the live schema (`migrations/0167_...up.sql:97`, `:99`) and replaced the `execution_mode` constraint. The residual `task` references in 0001/0022/0085 are frozen append-only historical SQL and comments that must not be edited.
2. The `lenny_task_*` metric family was already renamed by Phase 1 and is out of scope (`proposals/0002...:2202`). `TaskReuseQuantile` is a Go method name rather than a metric name.

Findings: this proposal stages the Phase-2 sweep that 0002 deferred at `proposals/0002...:33`, `:130`, and `:1337`. Implementation runs through the existing build-gaps flow.

## 2. Decisions

The following were decided in review and constrain this design.

- **The premise of a 0002 self-contradiction is rejected.** The §8.8 sentence "carry the external-protocol vocabulary" (`spec/08:831`) and the Phase-2 deferral (`proposals/0002...:130`, `:1337`) are mutually consistent statements within the same §6.51 directive: keep the spelling in Phase 1, sweep it in Phase 2. This proposal performs the deferred sweep; it does not resolve a contradiction that does not exist.
- **The owner's three-way classification rule is the design axis and is external to the spec.** Standard-defined names (the MCP/A2A Task primitive clients interact with) are kept; Lenny-defined APIs, proto, and schemas are renamed where applicable; purely-internal identifiers and packages are renamed. The rule turns on the origin of the name rather than on ownership of the transport.
- **The genuine standard boundary is the `ExternalProtocolAdapter` translation layer** (`pkg/gateway/mcp/mcp.go`) and the MCP-output projection that maps Lenny states to the MCP surface. The kept MCP-output strings are the protocol vocabulary at that boundary. `pkg/session/state/state.go:138` `MCPProtocolState` already maps session states to the MCP surface with no "Task" term and is the surviving projection after `pkg/task/state` is folded into it (Section 4.2), which establishes that the MCP-mapping role does not require the standard term.
- **The `lenny/delegate_task`, `lenny/get_task_tree`, and `lenny/send_message` tool names are kept.** They are Lenny-namespaced tool strings that surface the client's external-protocol Task concept (an MCP/A2A Task), they are part of the wire and tool contract callers depend on, and renaming them would break the standard-aligned client surface for no internal benefit. Keeping them means the "task tree" delegation vocabulary (§8.5, §8.9, `lenny/get_task_tree`) and the openapi "delegation task tree" summary string (`openapi.json:880`) stay as the standard-aligned surface.
- **The gateway↔adapter gRPC `task_id` field is removed.** An end-to-end trace (Section 4.4) confirmed the field serves no purpose: the three production callers that build `StartSessionParams`/`ResumeParams` never set it (`pkg/gateway/podsession/binder.go:740-747`, `:1219-1231`, `slotbinder.go:162-171`), so the adapter always takes its empty→session-id default (`pkg/adapter/manifest.go:253-256`); it is never set to the tree-root identity (`RootSessionID` never flows into the manifest path); and checkpoint keys use `(tenant_id, session_id, slot_id)` rather than `taskId`. The proto `StartSessionRequest.task_id` (field 8) and `ResumeRequest.task_id` (field 6) are removed and their field numbers reserved. The manifest `taskId` external surface is kept and is now unconditionally the session id.
- **The manifest `taskId` field is kept.** The manifest `taskId` is the external-protocol Task identifier the runtime and SDKs read (`CreateRequest.TaskID`, `Message.TaskID`); it is the standard-aligned external surface, classified keep, and is now derived adapter-side from the session id. Removing it is out of scope (Section 7).
- **`migrations/` is not in scope.** Migration 0167 already renamed the live `task_policy` columns to `session_policy` and replaced the `execution_mode` CHECK with `('session','service')`; migration files are append-only history and the residual `task` text in 0001/0022/0085 is frozen historical SQL and comments that must not be edited.
- **The `lenny_task_*` metric family is out of scope; Phase 1 already renamed it** (`lenny_pod_session_reuse_count` etc., `proposals/0002...:43`, `:2202`). `TaskReuseQuantile` is an internal Go method name reading the already-renamed metric and is in scope as an internal rename.
- **Generated artifacts are never hand-edited.** `lenny-adapter.pb.go`, `zz_generated.deepcopy.go`, and the CRD manifests under `charts/lenny/crds` and `pkg/embedded/crds` regenerate from the proto and the `+kubebuilder`-marked API types via `make generate` / `make generate-proto`; the rename and the proto field removal edit the proto and Go sources and regenerate.
- **`taskId` and `sessionId` carry the same value in production** (every `TaskID` assignment derives from a session id: `taskrecord.go:36-37`, `tree.go:175`, `mcptools.go:3941/4201/4371`, `usage.go:641/855`), but §8.8 retains both as distinct fields. The schema description keeps the two-field structure to avoid a value collision and to keep the record forward-compatible, rather than merging them.
- **v1 ships one implementation per concern with no compatibility shims.** No deployments exist in the wild, so renamed Go identifiers, package paths, the affected SDK types, and the removed proto field are changed in place with all callers updated and no deprecated aliases, dual names, or migration shims.

## 3. Design overview

The sweep classifies each `task`-named surface under the owner's three-way rule and applies the rename or removal the classification dictates, with no behavior change. The external-protocol Task surface stays: the MCP/A2A primitive, the `lenny/delegate_task`/`lenny/get_task_tree`/`lenny/send_message` tool names, the §8.8 protocol-mapping table, the MCP-output strings in `MCPProtocolState`, the manifest/SDK `taskId`, and the `/mcp` adapter. The Lenny-defined and purely-internal surfaces are renamed: the internal Go packages and types (`pkg/task`, `pkg/sandbox/taskcleanup`, `pkg/gateway/taskusage`), the `TaskReuseQuantile` method, and the stale Phase-1 comments. The purely-internal `pkg/task/state` is folded into the existing `pkg/session/state` (one implementation per concern) rather than renamed, with its two MCP-routing consumers rewritten. The one Lenny-defined surface that is removed rather than renamed is the dead gateway↔adapter gRPC `task_id` field. The §8.8 durable-schema spec edit is narrowed to a single sentence that records the settled post-Phase-1 classification and removes the deferral cruft, while keeping the `TaskRecord`/`TaskResult`/`taskId` spellings so the section stays consistent with its cross-references in §7, §10, §12, and §15.

```
Classification (owner's three-way rule, external to the spec)
  origin of the NAME decides keep vs. rename vs. remove
        |
        +-- KEPT (standard-defined / standard-aligned)
        |     MCP/A2A Task primitive; lenny/delegate_task,
        |     get_task_tree, send_message; §8.8 protocol-mapping table;
        |     MCPProtocolState output strings; /mcp adapter;
        |     manifest/SDK taskId (now derived from sessionId)
        |
        +-- REMOVED (Lenny-defined, dead)
        |     gateway->adapter gRPC task_id (C2): StartSessionRequest
        |       field 8, ResumeRequest field 6 -- never populated,
        |       carries no information (Section 4.4)
        |
        +-- RENAMED (Lenny-defined)
        |     §8.8 durable-schema deferral prose (C1, sentence rewrite,
        |       schema spellings kept for cross-reference consistency)
        |
        +-- RENAMED (purely internal)
        |     pkg/task, pkg/sandbox/taskcleanup,
        |     pkg/gateway/taskusage (C3); TaskReuseQuantile (C4);
        |     stale Phase-1 comments (C3/C4); tests/spec-map.json §8.8 (C6)
        |
        +-- FOLDED (purely internal, one impl per concern)
              pkg/task/state -> existing pkg/session/state (C3);
              both MCP-routing consumers (usage.go, mcptools.go) rewritten
```

The renames are mechanical and carry all callers in place. The removal deletes a field no caller populates. No control flow, wire semantics, or persisted value changes; `taskId` and `sessionId` continue to hold the same session-derived value, and the manifest `taskId` keeps the value it already had.

## 4. Detailed design

### 4.1 §8.8 durable-schema classification (C1)

The §8.8 text currently reads "The `TaskRecord` and `TaskResult` schemas and the `taskId` field carry the external-protocol vocabulary for the session's execution" (`spec/08:831`), which is the Phase-1 rationale for deferring the rename. The minimal correct change rewrites that one sentence to state the settled post-Phase-1 classification: `TaskRecord`, `TaskResult`, and `taskId` are the external-protocol-facing names Lenny keeps, the durable record is the protocol surface of a session, and adapters map at the boundary. The schema names are kept.

The schema names are kept because they are cross-referenced as durable record types across §7 (`spec/07:111`, `:429`), §10 (`spec/10:395`), §12 (`spec/12:786`, `:810`), and §15 (`spec/15:1500`, the `blobStore.taskRecordTtlSeconds` config knob at `spec/15:1569`, `:2451`, `:2476`). Renaming the §8.8 schema while leaving every cross-reference would name the same durable type two ways, which the throughline and internal-consistency rules make a defect. The committed spec already classifies these names as external-protocol vocabulary at `spec/08:831`, and §15:1479 frames `TaskResult` as "Lenny's internal content model" that the adapter translates at the boundary. Keeping the spelling and rewriting only the deferral sentence makes §8.8 agree with §15:1479, removes the deferral cruft, and touches one section with no cross-reference fan-out. (The proto comment at `schemas/lenny-adapter.proto:871-872` previously restated the same classification, but it is removed with the `task_id` field under C2; the §15:1479 framing and the cross-references carry the argument without it.)

The staged edit is in Section 6.

### 4.2 Internal Go package and type renames (C3)

`pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, and `pkg/gateway/taskusage` are purely-internal identifiers and package paths with no external-standard origin. The spec references none of these Go package paths (a grep of `spec/` for `pkg/task`, `pkg/task/state`, `pkg/sandbox/taskcleanup`, `pkg/gateway/taskusage` returns nothing), so package names are pure implementation governed by `code-best-practices.md` rather than by §8.8. The exported Go types are already Lenny-own names qualified by the package: `record.go:115` `type Record struct`, `record.go:130` `type Result struct`, plus `Message`, `Usage`, and `TreeUsage`. Only the package name `task` and the JSON wire tags (`record.go:117` `json:"taskId"`) carry the word "task", and the JSON tags are wire format this proposal does not change.

The package names are stale after the session/task collapse: `pkg/sandbox/taskcleanup/taskcleanup.go:3` documents the package as "the §6.2 recycle disposition branching for a recycling session-mode pod" with no task semantics, and `pkg/gateway/taskusage/taskusage.go:14` carries the dead comment "the dedicated timers land with the task/concurrent execution modes" for modes 0002 removed. `code-best-practices.md` requires packages "named for the concern or the spec component it implements", so these renames are legitimate code hygiene.

The reconciliation, decoupled from C1's schema-name decision:

- Rename `pkg/sandbox/taskcleanup` to `pkg/sandbox/podscrub` (resolved 2026-06-17), per its §6.2 whole-pod recycle role under `code-best-practices.md`. Update its importers (`pkg/adapter/scrub`, `pkg/gateway/recycle`, `pkg/gateway/leasecontrol`).
- Rename `pkg/gateway/taskusage` to `pkg/gateway/resultrollup` (resolved 2026-06-17), the `TaskResult`-rollup builder, which deconflicts with the existing `pkg/gateway/sessionusage`. Update all its non-test importers: `pkg/gateway/mcptools` (`mcptools.go:79`, the `TaskUsage *taskusage.Builder` field at `:442`, and the `resolveChild`/`collectChildResults` signatures at `:3994`/`:4104` on the delegation result-collection path), `pkg/gateway/sessionserver` (`sessionserver.go:71`), and `cmd/lenny-gateway` (`main.go:289`, the `taskusage.New(...)` wiring at `:3528`). Rewrite the package doc comment (`taskusage.go:1-22`), which contains the stale "task/concurrent execution modes" clause at line 14, as part of this package rename.
- Rename the `pkg/task` package to `pkg/sessionrecord` (resolved 2026-06-17). The Go type names `Record` / `Result` (and `Message`, `Usage`, `TreeUsage`) and all JSON wire tags (`taskId`, etc.) are unchanged, since the types are already Lenny-own and the wire format is out of scope; the package path is internal, so renaming it does not require §8.8 to change.
- Fold `pkg/task/state` into the existing `pkg/session/state` (resolved 2026-06-17, the one-implementation-per-concern outcome). `pkg/session/state/state.go:138` `MCPProtocolState` already performs the full §8.8 Lenny-session-to-MCP projection across every state with metadata annotations. The five states the two consumers route through `pkg/task/state.MCPProtocolState` (`pkg/task/state/state.go:88`) produce byte-identical MCP strings under `pkg/session/state.MCPProtocolState` (both map `Completed`→`completed`, `Failed`→`failed`, `Cancelled`→`canceled`, `Expired`→`failed`, `InputRequired`→`input_required`), so the MCP-output projection is preserved. The §8.8 task-level state set (`Submitted`, the 7-element `All()`, `ValidTransitions()` including `{Submitted, Running}`, `IsValid`, and the task-specific `InvalidTransitionError`) is removed with the package; §8.8 defines the canonical task machine as the §7.2 session machine (`spec/08:831`), so `pkg/session/state` is the surviving canonical implementation and its existing `_spec_8_8_871` tests pin the §8.8 surface (covered under Finding 3 in the spec-map re-key below). `pkg/task/state` has two production consumers, each with its own MCP-routing split that the fold must rewrite. `pkg/gateway/sessionserver/usage.go:27` imports `taskstate` and routes the terminal and `input_required` states through it in `mcpStateForSession` (`usage.go:957-972`). `pkg/gateway/mcptools/mcptools.go:88` also imports `taskstate` and calls `taskstate.MCPProtocolState` five times (`InputRequired`/`Completed`/`Failed`/`Cancelled`/`Expired`) in `nodeProtocolState` (`mcptools.go:108-122`), which feeds its own `mcpStateForSession` (`mcptools.go:97-100`) and the live callers at `mcptools.go:3941`, `:4043`, `:4199`, and `:4376`. The two signatures differ: `pkg/task/state.MCPProtocolState` returns a single `string` while `pkg/session/state.MCPProtocolState` returns `(string, map[string]any)`, so a mechanical import swap does not compile. The fold removes `pkg/task/state` and both `mcpStateForSession`/`nodeProtocolState` splits, rewriting each to route every state through `pkg/session/state.MCPProtocolState` and discard the metadata value in the single-value `mcpStateForSession` path. The stale comment at `pkg/gateway/sessionserver/tree.go:11-12` ("The §8.8 TaskRecord state machine in pkg/task/state") names the deleted package and is reframed to the surviving `pkg/session/state`. `tests/change-graph.json` carries the glob key `pkg/task/state` (`tests/change-graph.json:312`) with its `pkg/task/state/...` unit value (`:313`), and the tier-0 `validate-maps` file-existence check (`cmd/lenny-test/cmd_validate.go:278-313`, wired into the static tier at `cmd/lenny-test/cmd_run.go:733` and listed at `tests/groups.yaml:93`) fails when a glob key points at a missing path. The renamed paths are not exempt under `tests/change-graph-pending.txt`, whose exemption is scoped to forward references that do not yet exist on disk rather than to renames. The fold therefore folds that key (and its unit value) into the existing `pkg/session/state` entry (`:309-310`), so tier 0 stays green.
- The file count is roughly 51 Go files that reference these identifiers (across `pkg/`, `cmd/`, and `sdks/`), correcting the broader Phase-2 figure of 70 that spans every change. `TaskReuseQuantile` is handled by C4 and is not in C3's target list.

The MCP-output vocabulary for the terminal and `input_required` states is preserved in `pkg/session/state.MCPProtocolState` (the surviving superset) after `pkg/task/state` is folded away. That function performs the §8.8 Lenny-session-to-MCP projection across every state at the standard boundary, so removing `pkg/task/state.MCPProtocolState` loses no MCP output string.

### 4.4 Remove the dead gateway↔adapter gRPC `task_id` field (C2)

An end-to-end trace of the gRPC `task_id` established that it carries no information not already available to the adapter as the session id, so it is removed from the proto rather than renamed or kept. The evidence:

- **The gateway never populates it.** The wire field is set in exactly two places, both copying a struct field: `pkg/gateway/adapterclient/client.go:122` (`TaskId: p.TaskID`, StartSession) and `:633` (`TaskId: p.TaskID`, Resume).
