# Proposal: Make CREDENTIAL_REVOKED reachable under the shared lease store and complete the §4.9 user-credential deny-list startup rebuild

- **Status:** Applied to spec (2026-07-17). Converged after 9 adversarial review rounds (15 findings fixed). The code change is not yet implemented. Land as a coordinated pair with proposal 0036 (both touch `credrenewal` / `cmd/lenny-gateway/revocation.go`).
- **Date:** 2026-07-16.
- **Scope:** A spec-to-code reconciliation that makes the §4.9 `CREDENTIAL_REVOKED` deny-list contract reachable in the multi-replica shared-Postgres topology and completes the §4.9 startup rebuild union across both credential stores. Two coupled code defects are fixed: revocation deletes the lease before the deny-list check can run (`CREDENTIAL_REVOKED` is unreachable under the shared lease store), and the startup rebuild seeds only the pool term of the two-store union on a stale premise (a restarted replica rebuilds a pool-only deny list). The change deletes two `leases.Remove` calls across the two credential-revocation paths whose backing credential is durably marked `status = 'revoked'` (**CODE-A**, `pkg/gateway/credentials/usercreds/usercreds.go`, `cmd/lenny-gateway/credential_revocation.go`); the §11.4 full_revoke path (`cmd/lenny-gateway/user_revocation.go`) is excluded because it marks no credential revoked, so the startup rebuild could not re-deny a retained lease there. The change adds a `RevokedCredentials` listing query to `TokenStore` on Memory and pgstore mirroring the pool store (**CODE-B**, `pkg/gateway/credentials/credentialstore`), seeds the user-credential term in the §4.9 rebuild union (**CODE-C**, `cmd/lenny-gateway/workers.go`), and retargets the spec-named `TestUserCredentialRevocationDenyListProxy` to the shared-store topology and adds the restart-rebuild path plus store-query unit tests (**TEST-E**). This revision expands scope to bound retention properly rather than perpetuate the shipped over-approximation: **CODE-D** applies the §4.9 lease-existence filter at the rebuild site so a deny-list entry is seeded only for a revoked credential that still has an active lease (both pool and user keys), bounding the per-replica deny list and the startup rebuild that otherwise grow monotonically with cumulative revocations; **CODE-E** adds a plain `expires_at` column to `credential_leases` (migration `0175`), a `DeleteExpired` lease-store method, and an error-returning `LeasesByCredentialCount` existence query; **CODE-F** adds a `DenyList.Remove` method and a periodic gateway sweep worker that deletes expired lease rows and drops each credential's deny entry only when the store definitively reports no remaining lease for it (failing closed on a store error), implementing the `spec/04:1671` promise that entries "expire when the credential's natural lease TTL lapses"; **SPEC-E** rewords the `active_leases_terminated` audit count (leases-affected: terminated in direct mode, denied in place in proxy mode); **SPEC-F** reconciles the §4.9 rebuild bullets (`:1694`/`:1695`) to "active lease" now that the filter is implemented; and **SPEC-G** reconciles the `CredentialCompromised` gauge and alert semantics (`spec/16`) and their runbook and metrics-reference mirrors to the retain-and-deny model, so a revoked credential whose retained lease is correctly on the deny list is not counted as a compromise. The change therefore edits the spec (SPEC-E/SPEC-F/SPEC-G), adds one schema migration, two new lease-store methods (`DeleteExpired` and `LeasesByCredentialCount`) plus the `expires_at` projection on `Put`, a background worker, and a regeneration of the rendered alert catalog, on top of the deny-list-reachability fix.

This document stages the proposed code and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

Spec §4.9 mandates that a proxy request presenting a lease whose backing credential was revoked is rejected with `CREDENTIAL_REVOKED` (category `SECURITY`) before any upstream call, via a source-aware deny list (`spec/04_system-components.md:1672`, `:1690`), and that a restarted replica rebuilds a complete deny list from a union across both credential stores (`spec/04:1692-1697`, exercised by the spec-named `TestUserCredentialRevocationDenyListProxy` at `:1699`). Two coupled code defects make this contract unreachable in the multi-replica shared-Postgres topology that is v1's canonical production deployment.

### (A) `CREDENTIAL_REVOKED` is unreachable under the shared lease store

The LLM proxy resolves the lease before it consults the deny list. A `GetByToken` miss returns `LEASE_TOKEN_INVALID` (401) and returns early (`pkg/gateway/llmproxy/llmproxy/handler.go:319-323`), and only a resolved lease reaches `DenyList.Revoked(lease.CredentialKey())`, whose `RejectRevoked` result yields `CREDENTIAL_REVOKED` (403) at `handler.go:326-347`. Three revocation paths write the deny-list entry and then delete the lease. Two of them revoke a specific credential and durably mark it `status = 'revoked'` in a credential store, so a retained lease against that credential is re-deniable from the store on a restarted replica:

- `Materializer.RevokeUser` (`pkg/gateway/credentials/usercreds/usercreds.go:259-263`), reached from `POST /v1/credentials/{credentialRef}/revoke`, which marks the token-store credential revoked via `store.Revoke` before propagating (`credentialserver.go:313`, `:323`), and
- pool-credential revocation (`cmd/lenny-gateway/credential_revocation.go:59-62`), whose admin endpoint marks the pool credential revoked in the `CredentialPoolStore` (`credential_revocation.go:13-14`).

The third path, the §11.4 full_revoke lease revoker (`cmd/lenny-gateway/user_revocation.go:186-187`), revokes the user rather than a credential. It writes an in-memory deny-list entry keyed on `lease.CredentialKey()` and cancels the user's sessions, but no code on the full_revoke fan-out marks any credential `status = 'revoked'` (`users_invalidate.go:145-197`). A retained lease on that path is therefore not re-deniable from either store on restart, so CODE-A leaves the full_revoke path deleting its lease. The reasoning is developed in §2 and recorded as a non-goal in §5.

When the LLM-proxy lease store is the shared Postgres backend (`stores.go` substitutes `credleasestore/pgstore` when a `pgPool` is configured), `Store.Remove` is a global `DELETE FROM credential_leases WHERE lease_id = $1` (`pkg/gateway/credentials/credleasestore/pgstore/pgstore.go:190-193`) and `GetByToken` resolves against the same shared table (`pgstore.go:172-177`). A post-revocation proxy request therefore resolves no lease on every replica and returns `LEASE_TOKEN_INVALID` rather than `CREDENTIAL_REVOKED`; the deny-list entry is never consulted because lease resolution already failed. This contradicts the deny-list design in which an entry shadows a still-resolvable lease until its natural TTL lapses (`spec/04:1671`, `:1687-1688`).

The spec-named `TestUserCredentialRevocationDenyListProxy` passes today only because the existing tier-4 test uses two independent in-memory lease stores (`leasesOrigin`, `leasesPeer`) so the modeled peer retains the lease (`tests/tier4_integration/credential_denylist_proxy_test.go:94`, `:126-130`). That separation collapses under a shared store: the single `DELETE` removes the row every replica reads.

### (B) The user-credential startup rebuild is vacuous

The §4.9 rebuild worker seeds only the pool term. It calls `w.credentialPools.RevokedCredentials`, builds `{Source: SourcePool, ...}` keys, and `Reset(keys)`; it emits no `{source: user, tenantId, credentialRef}` entries, and its comment declares the user term vacuous because "no user-backed lease is minted at session creation yet" (`cmd/lenny-gateway/workers.go:1421-1453`, comment at `:1430-1432`). Proposal 0007 moved lease minting to `/finalize`, so user-backed leases are in fact minted (`pkg/gateway/credentials/usercreds/usercreds.go:190-209`), which makes the comment stale.

`TokenStore` (`credentialstore.Store`) exposes no revoked-credential listing query analogous to `credentialpoolstore.RevokedCredentials` on either Memory or pgstore (`credentialstore.go:92-148`). A replica restarted immediately after a user-credential revocation therefore rebuilds a pool-only deny list. Once defect A is fixed so the lease survives revocation, that replica resolves the retained lease, misses the absent user deny-list entry (`DenyList.Revoked` returns false), and accepts the revoked user credential on the upstream path until the lease TTL lapses. This is a fail-open `SECURITY` regression on restart.

### The shared root gap

Both defects share one root gap: revocation deletes the lease so the deny-list check never runs, and the rebuild has no store query to enumerate revoked user credentials. Defect A is latent as long as B is unfixed (a deleted lease also cannot be accepted), and B is latent as long as A is unfixed (a deleted lease is never resolved on restart either). Fixing one without the other either leaves `CREDENTIAL_REVOKED` unreachable or opens the restart fail-open, so the two are fixed together.

### (C) Retaining leases exposes an unbounded, unswept deny list and stale audit wording

Fixing defect A means revocation retains the lease instead of removing it, which surfaces two pre-existing gaps that CODE-A would otherwise make worse:

- **The startup deny-list rebuild is unbounded.** `RevokedCredentials` (pool, `credentialpoolstore.go:576-602`, and the new user query) returns every revoked credential with no lease-existence bound, and `DenyList` is a plain `map[CredentialKey]struct{}` with no TTL or prune (`denylist.go:26-83`). Because a revoked credential's `status = 'revoked'` row persists for audit, the authoritative startup `Reset` re-seeds an entry for every ever-revoked credential on every replica start, so the per-replica deny list and the rebuild query grow monotonically with the deployment's cumulative revocations. The `spec/04:1694`/`:1695` "active lease" clause names the bound, but neither the shipped pool query nor a naive user query implements it, and `spec/04:1671` promises entries "expire when the credential's natural lease TTL lapses" — an expiry the code does not perform.
- **No expired-lease garbage collector exists.** The `credential_leases` table has no sweep for any lease; a retained revoked lease now lingers (denied) up to its full TTL, following the same lifecycle as an already-expired lease that also never gets collected.
- **The `active_leases_terminated` count is now inaccurate for proxy mode.** With CODE-A denying proxy-mode leases in place rather than removing them, the audit field and endpoint count (`spec/04:1674`/`:1675`/`:1375`/`:1764`/`:1766`) counts leases that were denied rather than terminated.
- **The `CredentialCompromised` gauge and alert now false-positive on every successful proxy-mode revocation.** The `lenny_credential_revoked_with_active_leases` / `lenny_user_credential_revoked_with_active_leases` gauges count revoked credentials that "still have one or more active leases outstanding against them," with a documented steady-state of zero, and any non-zero value sustained for more than 30s fires the `CredentialCompromised` critical alert (`spec/16:60`/`:61`, `:422`). Under CODE-A a correctly-propagated proxy-mode revocation deliberately retains an active lease (`ExpiresAt` in the future, denied on the deny list) for up to its full TTL, which is the exact condition CODE-D seeds a deny entry on. The gauge as specified would therefore go non-zero for the retained lease's TTL on every normal revocation and fire a critical alert that is meant to signal a propagation failure, contradicting the alert-clear promises at `spec/04:1701` step 4, `spec/11:501`, and the runbook trigger text (`docs/runbooks/emergency-credential-revocation.md:26`). The gauge is defined in the catalog and drives the alert (`pkg/observability/metrics/catalog.go:147-148`, `pkg/alerting/rules/rules.go:400-405`) but is not yet emitted by any code, so this is a spec-and-doc self-contradiction rather than a live false page today; SPEC-E's reword of the parallel "terminated" audit wording leaves this parallel surface unreconciled.

The rebuild and sweep entries are inert (a revoked credential with no live lease is never resolved and cannot be re-leased), so the growth gap is a resource and documentation-fidelity gap rather than a security one, but retaining leases makes it visible enough to close here: CODE-D bounds the rebuild, CODE-E/CODE-F implement the sweep and deny-entry expiry, and SPEC-E/SPEC-F/SPEC-G reconcile the spec, the audit wording, and the compromise gauge and alert.

## 2. Decisions

- **Retain the revoked lease; reject via the deny list (CODE-A).** Revocation stops deleting the lease from the lease store and relies on the source-aware deny list to reject it. Scoping `CREDENTIAL_REVOKED` to a single-binary or in-memory topology is rejected: the multi-replica shared-Postgres store is v1's canonical production topology, §4.9's contract is unconditional, and the project ships one canonical implementation per concern with no tier-dependent code paths. Retention is what the deny-list design already assumes: an entry "expire[s] when the credential's natural lease TTL lapses" (`spec/04:1671`, `:1687-1688`) presupposes the lease remains resolvable through revocation. With the lease retained, the proxy's `GetByToken` hits on every replica (shared-store or per-replica), reaches `DenyList.Revoked`, and returns `CREDENTIAL_REVOKED` (`handler.go:326-347`). No spec edit is needed: step 3's "terminate it immediately via in-process signal or Redis pub/sub" (`spec/04:1671`) describes deny-list propagation, so the `leases.Remove` calls are the deviation from the spec rather than the spec being wrong.
- **Retention is scoped to the two credential-revocation paths and excludes the §11.4 full_revoke lease revoker (CODE-A scope).** CODE-A retains the lease on the two paths whose backing credential is durably marked `status = 'revoked'`: `Materializer.RevokeUser`, reached from `POST /v1/credentials/{credentialRef}/revoke` (which calls `store.Revoke` at `credentialserver.go:313` before propagating at `:323`), and `poolCredentialRevoker.RevokePoolCredentials`, whose admin endpoint marks the pool credential revoked in the `CredentialPoolStore` (`credential_revocation.go:13-14`). A retained lease on either path is re-denied on a restarted replica because CODE-C's rebuild enumerates the revoked credential from its store. The §11.4 full_revoke lease revoker (`user_revocation.go:183-190`) is excluded: it revokes the user, writes an in-memory deny-list entry keyed on `lease.CredentialKey()`, and cancels the user's sessions, but no code on the full_revoke fan-out marks any credential `status = 'revoked'` (`users_invalidate.go:145-197`, which drives pod termination, lease revocation, token revocation, and playground revocation without a `credentialstore.Revoke` call). Retaining a full_revoke lease would therefore open a restart fail-open: a replica restarted after a full_revoke resolves the retained lease from the shared Postgres store, the rebuild finds the credential still `active` in both stores and adds no deny-list entry, and the proxy has no session-tombstone gate, so the request reaches upstream. Deleting the lease on the full_revoke path keeps that path fail-closed on the shared store: the global `DELETE` removes the row every replica reads, so a post-revocation request resolves no lease and is rejected `LEASE_TOKEN_INVALID` on every replica and across restarts. `LEASE_TOKEN_INVALID` is a fail-closed rejection; the §4.9 `CREDENTIAL_REVOKED` contract governs credential revocation, and the §11.4 full_revoke path is a user-level revocation that does not require the `CREDENTIAL_REVOKED` category. Marking full_revoke credentials revoked so their leases become re-deniable is a larger change that would also have to durably revoke the pool credentials held by the user's pool-backed sessions without revoking them for other users, so it is out of scope; the minimal fail-closed choice is to leave the full_revoke path removing its lease.
- **The retained lease is never treated as live by any other path.** The deny check precedes budget and session accounting: the proxy returns `CREDENTIAL_REVOKED` at `handler.go:339-347` before the `BudgetGate` at `handler.go:353`, so session accounting never runs for a denied request. Renewal cannot resurrect the retained lease: the credential-lease revocation propagator already drops the renewal worker's tracked leases bound to the revoked credential on `Revoke` (`cmd/lenny-gateway/revocation.go:79-86`, `:152-155`; `pkg/gateway/credentials/credrenewal/credrenewal.go:170-174`, `:196-198`, feeding exhaust then fault rotation), and even absent that, a renewal re-resolves the backing credential, which is now revoked and is treated as not-found by the resolution path (`credentialstore.go:107-109`), so `Renew` fails, `ExpiresAt` is never extended, and the worker exhausts. The retained revoked lease follows the identical lifecycle as any already-expired lease, resolvable but rejected, until the existing session-teardown path removes it (`credassign` `ReleaseSession` calls `Release` over `LeasesBySession`, `pkg/gateway/credentials/credassign/client.go:340-347`), the bounded sweep (CODE-F) removes it once past `ExpiresAt`, or it lapses at its natural `ExpiresAt` and is rejected thereafter as `LEASE_EXPIRED`. Retaining revoked leases makes the pre-existing absence of an expired-lease garbage collector more visible, so this revision adds one (CODE-E/CODE-F) rather than leave it out of scope.
- **Add a revoked-listing query to `TokenStore` and wire it into the rebuild union (CODE-B, CODE-C).** Add `RevokedCredentials(ctx)` to `credentialstore.Store`, implemented on Memory and pgstore, mirroring `credentialpoolstore.RevokedCredentials` (`credentialpoolstore.go:274-283`, `:576-600`; `pgstore.go:301-340`). It returns every `(tenantId, credentialRef)` where `status = 'revoked'`, scanned across all tenants. The `workers.go` rebuild appends `{Source: SourceUser, TenantID, CredentialRef}` keys to the pool keys and `Reset`s the union, replacing the stale pool-only seed and its comment. The store query stays store-scoped (the `credentialstore` holds no lease index); the lease-existence bound is applied at the rebuild site by CODE-D, which has `w.llmLeases` in hand.
- **Bound the rebuild to credentials with an active lease (CODE-D); reconcile both §4.9 rebuild bullets (SPEC-F).** The §4.9 rebuild bullets (`spec/04:1694`/`:1695`) say `WHERE status = 'revoked' AND EXISTS an active lease`, but the shipped pool query and a naive user query both ignore that clause and return every revoked credential. Because `DenyList` has no TTL or prune (`denylist.go`, a plain `map[CredentialKey]struct{}`) and `RevokedCredentials` is unbounded, the startup `Reset` re-seeds an entry for every ever-revoked credential on every replica start, so the per-replica deny list and the rebuild query grow monotonically with the deployment's cumulative revocations. The entries are inert (a revoked credential with no live lease is never resolved, and cannot be re-leased), but their count is unbounded, which is exactly what the "active lease" clause exists to prevent. CODE-D applies the filter at the rebuild site for both pool and user keys, seeding a deny entry only when `w.llmLeases.LeasesByCredentialCount(ctx, key, now)` reports at least one active lease (`expires_at` in the future, or a NULL pre-backfill `expires_at`). The rebuild is a fail-closed `SECURITY` decision (the authoritative one-shot `Reset` is the only way a fresh replica learns of a revocation it missed on pub/sub), so CODE-D uses the error-returning `LeasesByCredentialCount` rather than the error-swallowing `LeasesByCredential` and, on any non-nil store error, retains the candidate key in the `Reset` set instead of dropping it, so a transient Postgres or KMS fault at boot over-approximates the deny list rather than opening a durable fail-open. The same fail-closed rule governs the two revoked-credential listing queries (`RevokedCredentials` on the pool store and the token store) that feed the union, extending the fail-closed decision beyond the per-key `LeasesByCredentialCount` filter: on a non-nil error from either listing query the rebuild does not commit a `Reset` at all, because a `Reset` built after a failed listing query omits that store's revoked set, and under CODE-A that leaves a retained active revoked lease resolvable with an empty (pool-query error) or pool-only (user-query error) deny list for the replica's whole lifetime, a durable `CREDENTIAL_REVOKED` fail-open strictly worse than the shipped lease-deletion behavior. Instead the rebuild runs in a background goroutine, so `startBackgroundWorkers` returns and `runServers` brings up the `/healthz` liveness and `/readyz` readiness listeners rather than blocking on a synchronous retry that would leave the pod serving neither and liveness-kill it into a crashloop during an extended boot-time outage. The goroutine retries both listing queries with bounded backoff until both return without error and commits the authoritative `Reset` only on the complete filtered union. Until that `Reset` commits it holds the replica out of the §10.4 `/readyz` ready set: it sets a rebuild-committed flag on `gatewayWiring` when the `Reset` lands, `readinessVerdict` (`readiness.go:52`) gains a rebuild-pending precedence input that returns 503 while the flag is unset, and the `/readyz` handler (`httpsurface.go:653`) threads the flag in beside the existing draining, clock-drift, dual-store, and hard-dependency inputs. A transient boot-time Postgres fault that recovers before request time therefore cannot leave the replica serving proxy traffic with a dropped store's revoked set, and one that outlasts a liveness probe does not crashloop the pod because `/healthz` stays live throughout. This is the listing-query analogue of the per-key fail-closed filter, and the pool store's shipped log-and-skip error path (which commits no `Reset` and leaves the list empty) is replaced by the same retry-and-gate handling. SPEC-F reconciles both bullets to "active lease" so spec and code now agree (resolving the parallel-bullet asymmetry the prior draft avoided by leaving both unreconciled).
- **Bounded expired-lease sweep and deny-entry expiry (CODE-E/CODE-F), implementing `spec/04:1671`.** The spec says deny-list entries "expire when the credential's natural lease TTL lapses," but no such expiry exists and no lease-TTL GC exists for any lease. The lease body is a single envelope-encrypted blob with no plain `expires_at` column, so CODE-E adds that column (migration `0175`, populated on `Put` from `lease.ExpiresAt`; a one-time backfill decrypts pre-migration rows) and a `DeleteExpired(ctx, cutoff)` method returning the count of rows removed. CODE-F adds `DenyList.Remove(key)` and `DenyList.Keys()` and a periodic gateway sweep worker (modeled on the idempotency-key GC at `workers.go:1455`) that deletes lease rows past `ExpiresAt` and then reconciles each replica's own deny list against the store, removing a credential's deny entry only when `LeasesByCredentialCount(ctx, key, now)` returns a count of zero with no error. The sweep fails closed on a store error: `LeasesByCredentialCount` (CODE-E) is a plain-column `SELECT count(*)` that returns an error on a query failure, so a transient Postgres or KMS fault leaves the deny entry in place for that tick rather than removing it, unlike the error-swallowing `LeasesByCredential` (which returns nil indistinguishably on a query error, an `rows.Err()`, or an all-rows-fail-to-decrypt result). `LeasesByCredentialCount` takes an `activeAsOf` cutoff and counts only leases whose `expires_at` is in the future or NULL (a pre-backfill row of unknown expiry, counted so the guard fails closed), so the same error-returning query serves both the CODE-F sweep and the CODE-D rebuild filter, which both pass `now`. Because each expired row is deleted by exactly one replica under the shared store, the deny-entry removal is driven by each replica's own `Keys()` rather than by the deleted rows, so every replica's in-memory list is bounded within its lifetime rather than only the list on the replica that won each delete race. This bounds both the `credential_leases` table and the in-memory deny list within a replica's lifetime, and makes the `:1671` promise real.
- **Re-document the revocation `active_leases_terminated` count (SPEC-E).** With proxy-mode leases denied in place rather than removed, the count means leases-affected (terminated in direct mode, denied in place in proxy mode). SPEC-E rewords the field's description at `spec/04:1674`/`:1675`/`:1764`/`:1766`/`:1375`, at the parallel spec/11 §11.2.1 rows (`:75`, `:128`) that carry the same "terminated" wording, and at the `spec/24:92` `revoke-credential` command description ("terminates all active leases") that carries the same phrasing for the same admin command; the field is not renamed, so the wire and audit contract are unchanged.
- **Reconcile both §4.9 rebuild bullets together (SPEC-F), now that the filter is implemented.** The prior draft left `:1694` and `:1695` unreconciled to avoid an asymmetry between two parallel union terms while the code over-approximated. CODE-D implements the "active lease" clause for both pool and user keys at the rebuild site, so SPEC-F now reconciles both bullets together (tightening `:1694`'s "active-or-recent lease" and `:1695`'s "active lease" to the single implemented meaning: a lease not past `ExpiresAt`), keeping the two bullets parallel and matching the code. This is the "reconcile both" option the prior draft's Open decision 1 named.
- **Reconcile the `CredentialCompromised` gauge and alert to the retain-and-deny model (SPEC-G).** CODE-A makes a revoked credential with a retained, denied active lease the normal successful outcome, but the `lenny_credential_revoked_with_active_leases` / `lenny_user_credential_revoked_with_active_leases` gauges count any such credential as a compromise with steady-state zero, firing the `CredentialCompromised` critical alert (`spec/16:60`/`:61`, `:422`). SPEC-G redefines both gauges and the alert to count only a genuine propagation gap: a revoked credential with an active lease that is not shadowed by a deny-list entry, so a lease correctly on the deny list is not a compromise and steady-state stays zero under CODE-A. SPEC-G rewords the §11.8 security-signals table's `CredentialCompromised` row at `spec/11:493` (whose signal text is "revoked credential still has active leases") and the alert-clear sentence at `spec/11:501` (whose text is "The `CredentialCompromised` alert clears once all active leases are terminated.") to the deny-list-shadowing condition ("clears once every active lease against the credential is on the deny list (or terminated in direct mode)"), so the two `CredentialCompromised` descriptions in the same spec file agree, and reconciles the parenthetical gloss on `spec/04:1701` step 4 (whose text reads "confirm the `CredentialCompromised` alert clears within 60s (indicating revocation propagation succeeded)") so "revocation propagation succeeded" is defined as every active lease reaching a deny-list entry, keeping the "within 60s" verification bound intact. SPEC-G also updates the doc mirrors `docs/runbooks/emergency-credential-revocation.md`, `docs/runbooks/credential-revocation.md`, and `docs/reference/metrics.md`. The gauge is spec-defined but not yet emitted by any code (`catalog.go:147-148` catalogs it, `rules.go:400-405` alerts on it, no emitter sets it), so SPEC-G is a spec-and-doc reconciliation with no metric-emission code added. `pkg/alerting/rules/rules.go` is the single authoring source for the alert (its `CredentialCompromised` `Summary` and `Description` at `:400-405` are literal strings that SPEC-G hand-edits to the deny-list-shadowing condition), and `make generate` re-renders those strings into three `DO NOT EDIT` generated artifacts, none hand-edited: the chart fragment `charts/lenny/files/alerting-rules.yaml:99-107`, the deployer rule reference `docs/alerting/rules.yaml:102-110`, and the embedded `pkg/embedded/manifests/manifests.yaml:1586`. `make generate` runs `gen-alerting-rules` first, which regenerates the chart fragment and the docs reference from the catalog (`Makefile:79-80`, `cmd/gen-alerting-rules/main.go:46`, `:62`), then runs `helm template`, which regenerates `manifests.yaml` from the chart (`Makefile:85-88`), so `manifests.yaml` is downstream of the chart fragment rather than rendered from `rules.go` directly. The `gen-alerting-rules -check` cross-check (`tests/tier2_component/observability/catalog_crosscheck_test.go:354`) and the tier-11 three-render doc test (`tests/tier11_docs/audit_gdpr_erasure_reconciliation_test.go:285-291`) both fail if any of the three renders is left stale, so all three are regenerated in the same `make generate` run. Renaming or removing the gauge is rejected: the gauge and alert are the spec-named signal for a real revocation-propagation failure, which still exists under CODE-A (a revoked credential whose active lease never reached the deny list), so the signal is retargeted to that condition rather than dropped.
- **Classified a `fix`-plus-`new` hybrid with spec edits.** The deny-list reachability (CODE-A/B/C) is the `fix` half: behavior already normative under §4.9 that the code failed to implement. The rebuild filter (CODE-D), the `expires_at` column and `DeleteExpired` (CODE-E), and the sweep with deny-entry expiry (CODE-F) are the `new` half: they implement §4.9 bounds (`:1671`, `:1694`/`:1695`) the code never honored, and they add a schema migration, two lease-store methods (`DeleteExpired` and `LeasesByCredentialCount`), a `DenyList.Remove` method, and a background worker. SPEC-E/SPEC-F/SPEC-G edit the spec and regenerate the rendered alert catalog. No new RPC, endpoint, proto field, or CRD field is introduced.
- **Cite durable spec anchors only.** New and reworded comments carry `// spec: §4.9` rather than a coverage-tracker finding id; no finding id appears in spec text, code, test names, comments, or commit messages.

## 3. How the pieces fit at revocation and restart

A revocation writes the source-aware deny-list entry (`{source: user, tenantId, credentialRef}` for a user credential, `{source: pool, poolId, credentialId}` for a pool credential) and, with CODE-A applied, leaves the backing lease in the store. On the next proxy request, any replica resolves the retained lease through `GetByToken` (a hit on the shared Postgres table or on a per-replica store), reaches `DenyList.Revoked(lease.CredentialKey())`, and returns `CREDENTIAL_REVOKED` before the `BudgetGate` and any upstream call. The retained lease is denied on every request until session teardown removes it or it lapses at its natural `ExpiresAt`.

A replica that restarts after a revocation runs the §4.9 startup rebuild (`workers.go`). With CODE-B and CODE-C applied, the rebuild `Reset`s the union of the pool store's revoked `(poolId, credentialId)` rows and the token store's revoked `(tenantId, credentialRef)` rows, so the fresh replica denies a revoked user credential it resolves from the shared lease store rather than failing open. The `Reset` is authoritative and runs once at startup on an empty list, so deny-list entries stay bounded across restarts regardless of how many leases the shared table retains.

### CODE-F. Add `DenyList.Remove` and a bounded expired-lease sweep worker

**Target:** `pkg/gateway/credentials/denylist/denylist.go` (`Remove` and `Keys`); `cmd/lenny-gateway/workers.go` (a new sweep worker beside the §11.5 idempotency GC at `:1455`); a `--credential-lease-gc-interval-seconds` flag (default `3600`).

**Change.** Add two methods to `DenyList`: `Remove(key credential.CredentialKey)` (deletes the key under the write lock, the inverse of `Revoke`) and `Keys() []credential.CredentialKey` (returns a snapshot of the current entries under the read lock). Add a periodic worker that, every interval, runs two steps: (1) call `w.llmLeases.DeleteExpired(ctx, now)` to remove lease rows past `ExpiresAt` from the store, bounding the `credential_leases` table; (2) reconcile this replica's in-memory deny list against the store by iterating `w.credDeny.Keys()` and, for each key, calling `w.llmLeases.LeasesByCredentialCount(ctx, key, now)`, then calling `w.credDeny.Remove(key)` only when that returns a count of zero with a nil error (the store definitively holds no active lease for the credential, so no request can resolve to an unexpired lease and the entry is inert). On any store error or a positive count, keep the deny entry for this tick and retry next interval. Emit `lenny_gateway_credential_leases_swept_total` with the `DeleteExpired` row count and log both counts. The worker runs on every replica so every replica's in-memory list is bounded within its lifetime.

The reconcile step must fail closed on a store error, because removing a live deny entry is a `CREDENTIAL_REVOKED` bypass on a fail-closed `SECURITY` control. `LeasesByCredentialCount` is used rather than `LeasesByCredential` precisely so the sweep can tell a genuine zero from an unanswerable query: `LeasesByCredential` returns nil on a Postgres query error, on `rows.Err()`, and when every matching row fails to decrypt under a KMS outage (`pgstore.go:254-256`, `:271-273`, `:293-296`), so a sweep driven by it would, during a failover or KMS blip, see every deny key look lease-free and call `Remove` on all of them even though the active revoked lease rows still exist (`DeleteExpired` removes only rows past `ExpiresAt`, so an active revoked lease is never deleted). Once removed, a deny entry is only re-added by a fresh pub/sub `Revoke` (which never refires for an already-revoked credential) or the authoritative startup `Reset`, so it would stay gone until the replica restarts, and when the store recovers the proxy would resolve the still-retained active revoked lease and accept it upstream. That is a durable fail-open strictly worse than the shipped `DenyList`, which has no removal path and survives a store failover untouched. The count-with-error query keeps the removal fail-closed: it reports zero only when no active plain-column row matches (an unexpired or unknown-expiry row still counts) and returns the error otherwise.

The deny-entry removal is driven by the replica's own deny list rather than by the keys `DeleteExpired` deleted, because under the shared-Postgres store each expired row is deleted by exactly one replica: `DELETE ... RETURNING` yields a row only to the statement that removed it, so a removal set derived from `DeleteExpired`'s result would shrink only the one replica that won each row's delete race and would leave every other replica's entry in place until restart. That is precisely defect (C)'s unbounded-growth condition. Iterating each replica's own `Keys()` and re-checking `LeasesByCredentialCount` against the shared store bounds every replica's list regardless of which one deleted the row. Leader-electing the whole sweep is rejected: the §11.5 idempotency GC this worker is modeled on runs on every replica with no leader gate (`workers.go:1459` guards only on `pgPool != nil`), v1 adds no leader-election machinery for a per-replica cache, and a leader gate would leave every non-leader replica's list growing until restart.

**Rationale:** This realizes the `spec/04:1671` promise that deny-list entries "expire when the credential's natural lease TTL lapses" and bounds both the `credential_leases` table and every replica's in-memory deny list within its lifetime. Removing the deny entry only when the store definitively reports no lease for the credential is safe: while any lease for a revoked credential still resolves, `LeasesByCredentialCount` returns a positive count and the entry stays so the proxy keeps rejecting it; once the store holds no lease for it and answers without error, no request can resolve to it and the entry is inert, so removing it cannot let a revoked credential through (a revoked credential cannot be re-leased). The removal is gated on a zero count with a nil error, so a transient store or KMS fault that cannot enumerate the leases keeps the entry rather than dropping it, keeping the sweep fail-closed on the security path. The per-replica reconcile is the writer that shrinks each replica's in-memory deny list within its lifetime, complementing the authoritative startup `Reset`.

## 5. Non-goals

- **The store-scoped `RevokedCredentials` queries stay unfiltered; the lease-existence bound is applied at the rebuild site (CODE-D).** The pool and user `RevokedCredentials` store methods keep returning every revoked credential (they hold no lease index); the "active lease" filter is applied once, in `workers.go`, against `w.llmLeases`. This keeps the store queries simple and avoids a cross-store join inside a store method.
- **The sweep removes expired lease rows; it does not add a soft-delete or tombstone.** CODE-E adds a plain `expires_at` projection column and CODE-F hard-deletes past-`ExpiresAt` rows. No soft-delete flag, tombstone row, or lease-state machine is introduced.
- **No change to direct-mode revocation behavior.** The `RotateCredentials` push (`directModeRevocationRotator`) is unchanged; only proxy-mode deny-list reachability is fixed. Direct mode still reads the retained leases via `LeasesByCredential`.
- **No new RPC, endpoint, proto field, or CRD field.** The change adds one plain projection column, two lease-store methods (`DeleteExpired` and `LeasesByCredentialCount`), a `DenyList.Remove`, a background worker, and three spec-text reconciliations (SPEC-E/SPEC-F/SPEC-G) with a regeneration of the rendered alert catalog.
- **No change to the §11.4 full_revoke lease revoker.** `userLeaseRevoker.RevokeUserLeases` (`user_revocation.go:183-190`) continues to remove its leases. The full_revoke fan-out marks no credential `status = 'revoked'` (`users_invalidate.go:145-197`), so a retained lease there is not re-deniable from either store on restart; deleting the lease keeps the full_revoke path fail-closed on the shared store (a post-revocation request resolves no lease and is rejected `LEASE_TOKEN_INVALID` on every replica and across restarts). Making full_revoke credentials re-deniable would require durably revoking both the user credential and the pool credentials held by the user's pool-backed sessions, which is a larger change out of scope here.
- **No termination of a revoked user's sessions.** Session lifecycle is unchanged; the retained lease is denied on every request and cleaned up at the session's existing teardown.
