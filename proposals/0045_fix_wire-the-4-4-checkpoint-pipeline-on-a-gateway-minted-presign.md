# Proposal: Wire the §4.4 checkpoint pipeline on a gateway-minted presigned capability: one chunked upload path, a gateway-minted checkpoint_id and intent row, a §13 pod-to-object-store capability grant, and the §6.2 recycle unblock (successor to 0046)

- **Status:** Applied to spec (2026-07-17); the initial apply's two missed edits (§07 derive-copy chunk-set semantics, §04 `chunk_object_key_prefix` rename) are now landed and spec/ is aligned with the staged edits. Verified (2026-07-14), converged after 13 adversarial review rounds (81 findings fixed); all four §9 open decisions resolved and recorded in §2 (Q1 cloud egress via operator CIDR allow-list, Q2 Embedded Mode wires a signing backend, Q3 `terminated_during_resume` removed as unsatisfiable, Q4 `checkpointGrantWindow` default 4 with per-pool override).
- **Date:** 2026-07-14.
- **Scope:** A spec-and-code change that builds the §4.4 produce → store → restore pipeline that no production binary contains today, and resolves the spec's own contradiction about who holds the object-store socket. The upload stays in the agent pod, as `spec/10_gateway-internals.md:131`, `spec/12_storage-architecture.md:294`, `spec/04_system-components.md:249`, and `spec/11_policy-and-controls.md:35` already state, and the pod is given a gateway-minted presigned capability rather than a credential. The change touches `spec/04_system-components.md`, `spec/07_session-lifecycle.md`, `spec/10_gateway-internals.md`, `spec/11_policy-and-controls.md`, `spec/12_storage-architecture.md`, `spec/13_security-model.md`, `spec/15_external-api-surface.md`, `spec/16_observability.md`, `spec/17_deployment-topology.md` (**S1**–**S6**), the docs mirrors of the §13.1 control table and the seal-alert surfaces in `docs/`, `schemas/lenny-adapter.proto` (**P1**), `pkg/blobstore`, `pkg/adapter`, `cmd/lenny-adapter`, `pkg/gateway/checkpoint`, `pkg/gateway/sessionserver`, `pkg/gateway/podlifecycle/prestop`, `pkg/gateway/coordination/barrier`, `pkg/gateway/storage/legalholdreconciler`, `cmd/lenny-gateway`, `pkg/preflight`, `pkg/alerting/rules`, `migrations/` (**C1**–**C6**), `charts/lenny`, `cmd/lenny-controller`, `pkg/controller/sandbox` (**C7**), and new tests across tiers 1, 2, 3, 4, 5, 7, 9, and 11 (**T1**). ## 1. Problem

`spec/04_system-components.md` §4.4 states that a session survives the loss of its pod. The produce → store → restore pipeline that would implement it is absent in every production binary, and the spec contradicts itself about who holds the object-store socket.

### (A) The spec puts the upload in the pod

`spec/10_gateway-internals.md:131` has the gateway "instruct the adapter to begin issuing single-part `PutObject` calls under `partial_object_key_prefix`". `spec/10:139` has the adapter upload the tar stream in fixed-size chunks. `spec/12_storage-architecture.md:294` has the adapter retry against MinIO with exponential backoff. `spec/04:249` has the adapter delete partially uploaded objects. `spec/11_policy-and-controls.md:35` names "the adapter [supplying] the tar size from the workspace-size probe before upload begins" as the checkpoint quota input. `spec/10:167` sizes Tier 3 around "a MinIO I/O burst of up to 400 simultaneous uploads" from coordinated pods during drain, and the §17.8.2 throughput budget is written against that burst.

### (B) §13 gives the pod neither route nor credential

`spec/13_security-model.md:12` forbids standing credentials. `spec/13:13` pins file delivery to "Gateway-mediated only". `allow-pod-egress-base` (`spec/13:84-113`, rendered at `charts/lenny/templates/agent-network-policies.yaml:69`) permits gateway TCP 50051 and DNS. The MinIO ingress row (`spec/13:220`, rendered at `charts/lenny/templates/system-network-policies.yaml:476`) admits only gateway, `lenny-ops`, and `lenny-backup` pods. No presigned-URL mechanism appears anywhere in `spec/`, and `grep -c -i checkpoint spec/13_security-model.md` is zero.

The five supplemental agent-egress policies do not on their own establish a route: `allow-pod-egress-llm-proxy` targets the gateway on a second port, `allow-pod-egress-otlp` and `allow-pod-egress-kube-dns` are off by default (`charts/lenny/values.yaml:1065`, `:356`), `allow-pod-egress-provider-direct` renders zero rules under `egressCIDRs.providers: []` (`values.yaml:304`), and `allow-pod-egress-internet` `except`s the cluster pod and service CIDRs (`agent-network-policies.yaml:237-238`) so it cannot reach an in-cluster object store. They do establish the *pattern* the amendment follows: `allow-pod-egress-otlp` (NET-046, `spec/13:147-176`) is a config-gated supplemental agent-egress policy to an in-cluster `lenny-system` component, paired with a conditional ingress row on that component (`spec/13:223`), over TLS, with a deployer-supplied CA bundle projected into agent pods.

### (C) The pipeline is unbuilt at every layer, independently of (B)

`pkg/adapter/server.go:216` (`Checkpoints CheckpointSink`) and `:259` (`Restorer CheckpointSource`) are nil after `adapter.New` (`server.go:398-404`), and `cmd/lenny-adapter/main.go:258` assigns neither. `pkg/adapter/checkpoint.go:161-168` and `pkg/adapter/resume.go:44-47` return `codes.Unimplemented` in production. `pkg/adapter/coordination.go:198-201` behaves differently: `flushBarrierCheckpoint` short-circuits on the same nil field and returns an empty `checkpoint_ref`, so the `CheckpointBarrier` RPC acks successfully with no checkpoint behind it rather than failing with `Unimplemented`. No non-test type implements either interface.

`schemas/lenny-adapter.proto:1021-1029` carries only `session_id` and `deadline_ms` and returns an adapter-minted `checkpoint_id`, so there is no wire slot for a key prefix, chunk parameters, an upload capability, or a chunk ack.

`partialmanifeststore.Put` has no production caller; the wiring comment at `cmd/lenny-gateway/stores.go:993-997` records that "the writer is dormant until the §10.1 partial-upload pipeline is wired". The gateway never mints a `checkpoint_id` and never writes an intent row. `migrations/0062_session_partial_checkpoint_manifest.up.sql:26-62` carries seven columns and its own header (`:15-23`) records that the §10.1 column set is "deliberately omitted", so the `spec/10:130` INSERT and the `spec/10:131` conditional counter `UPDATE` are both unwritable. `pkg/blobstore` is linked only into `cmd/lenny-gateway`.

### (D) Blast radius beyond checkpointing

Because `Checkpoint` returns `Unimplemented` on every bound pod, `Checkpointer.Seal` (`checkpointer.go:211-216`, which no-ops only on `ErrNoBinding`) fails, `sealWorkspace` (`pkg/gateway/sessionserver/seal.go:74-115`) exhausts its 300s window, `failWorkspaceSeal` (`seal.go:145-181`) marks the session `failed` with `workspace_seal_timeout`, and `pkg/gateway/podlifecycle/podsession/binder.go:1829` skips the recycle branch for a failed disposition. Every session that ran on a bound pod is relabelled failed, its terminal state and audit trail are corrupted, up to 300s is added to each teardown, and §6.2 occupancy-zero recycling is unreachable on session-mode recycling pools. The concurrent-slot path at `pkg/gateway/podlifecycle/podclaim/slotclaimer.go:782` is not gated on disposition, and recycling is opt-in per `spec/06_warm-pod-model.md:24`, so the claim is scoped to session-mode recycling pools rather than universal.

### (E) Three defects travel with the same pipeline

The first is the manifest schema gap in (C). The second is the `checkpoint_id` minting site: `spec/10:130` requires the gateway to mint it at intent-row INSERT, while `schemas/lenny-adapter.proto:1027` returns it from the adapter and `checkpointer.go:260` stores that value; the accurate defect is a missing capability rather than an inversion, because `spec/10:130` scopes gateway minting to the chunked path, which is unbuilt. The third is `triggerForSource` (`checkpointer.go:337-352`), which returns `TriggerPeriodic` on every arm and whose doc comment defers to a `snapshotWithTrigger` function that exists nowhere in the repository, so `checkpoint.TriggerEviction` is selected by no code path.

## 2. Decisions

- **The adapter keeps the object-store socket.** The spec's capacity model was written around pod-side upload (`spec/10:167`'s 400-pod drain burst, §17.8.2's MinIO throughput budget, `spec/11:35`'s adapter-supplied probe size), and routing the bytes through the gateway relocates a data plane the deployment topology was sized around. Proposal 0046 (gateway-mediated relay) is withdrawn and is not revived. No checkpoint payload byte crosses the gateway.
- **Authority stays at the gateway.** The gateway alone mints `checkpoint_id`, writes the manifest rows, reserves and reconciles quota, chooses the T4 SSE-KMS key, validates the tenant prefix, and issues every `DeleteObject`. The pod receives a capability (a presigned, single-key, single-method, short-expiry URL) rather than a credential. `spec/13:12`'s "no standing credentials" survives verbatim.
- **The capability is bound by signature rather than by convention.** The gateway signs the SSE-KMS headers into the presigned URL, so a pod cannot downgrade encryption: minio-go v7.1.0 `PresignHeader` (`api-presigned.go:104`) threads extra headers into `req.Header` (`api.go:905-909`) and `PreSignV4` (`pkg/signer/request-signature-v4.go:210`, `:223`, `:230`) folds them into `X-Amz-SignedHeaders` and the canonical request, ignoring only `Accept-Encoding`, `Authorization`, and `User-Agent` (`:61-65`). The gateway already builds `encrypt.NewSSEKMS` at `pkg/blobstore/miniostore/miniostore.go:309-318`, and the AWS arm's SSE fields (`pkg/blobstore/s3/s3.go:242-243`) ride `PresignClient.PresignPutObject`. `Content-Length` is signed the same way.
- **The chunked-object model becomes the single upload path for every trigger, and `partial` becomes a column rather than a separate pipeline.** The adapter streams an unbuffered tar (`pkg/adapter/checkpoint.go:326-380`) whose length is unknown at signing time; an S3-compatible PUT requires a `Content-Length` on the wire; and this proposal elects to sign that length so the object store rejects a body that does not match it. Fixed 16 MiB chunks give every PUT an exact, signable length and collapse full-restore and partial-reassembly into the one concatenate-then-decompress pipeline `spec/10:155` already specifies. A checkpoint whose terminal summary arrives with every declared byte confirmed finalises `partial = false`; one cut short finalises `partial = true`.
- **The quota cap is a gateway observation rather than a server-enforcement assumption.** The gateway reserves from the workspace-size probe, clamps every adapter-declared chunk length to the `chunk_size_bytes` it chose itself, refuses to sign a grant whose `Content-Length` would carry the attempt past its reservation plus remaining tenant headroom, and confirms each chunk with `StatObject`. No quantity a compromised pod reports can widen what a capability carries. A confirmed size larger than the size signed into the grant aborts the attempt and reconciles the excess into the counter. The signed `Content-Length` is defence in depth on top of that confirmation. A provider that does not enforce the signed length degrades the bound from zero to the outstanding-grant window (`grantWindow × partialChunkSizeBytes`) rather than to unbounded.
- **Confirmation does not gate the next grant.** `spec/10:131` makes the chunk counter fire-and-forget with respect to `PutObject` latency, and a confirm-then-grant serialisation would put a stream round trip, a `StatObject`, and a Postgres commit in front of every 16 MiB chunk on a replica coordinating up to 400 concurrent uploads (`spec/10:167`). The gateway mints a bounded window of grants ahead (`checkpointGrantWindow`, default 4) and reserves headroom against the sum of outstanding signed `Content-Length`s. Confirmation and the monotonic counter `UPDATE` run asynchronously and must complete before finalisation and before quota reconciliation.
- **Write-once, catalog rows, and quota reconciliation move to explicit post-hoc gateway steps.** They live inside `blobstore.Store.Put` today (the §4.5 `StatObject` precheck at `pkg/blobstore/miniostore/miniostore.go:278-284`; the `artifact_store` row at `pkg/blobstore/cataloging/cataloging.go:143`) and a presigned PUT bypasses `Put`. The gateway confirms each acked chunk with the existing `Store.Stat`, which is also the "bytes actually written" `spec/11:36` requires, and inserts the catalog row from the confirmed size. Chunk keys are unique per `checkpoint_id` UUID, so write-once holds by construction and the confirm step is its check.
- **One existing RPC becomes streaming and no new RPC is added.** `Checkpoint` becomes bidirectional-streaming on the existing Adapter service (`schemas/lenny-adapter.proto:103`), where the gateway is already the client over the one channel `spec/13:84-113` permits. An adapter-to-gateway upload RPC on `GatewayControl` is rejected: it inverts the driver `spec/10:130` requires and adds a second control path for one concern. `Resume` stays unary and carries one presigned single-key `GET` capability per chunk, whose expiry covers the resume window.
- **Restore is a presigned `GET`, symmetric with the upload.** There is no gateway-to-adapter byte channel on the resume path today: `Resume` is unary (`schemas/lenny-adapter.proto:120`), `ResumeRequest` carries identifiers only (`:1048-1100`), and the adapter's only byte source for a checkpoint is the in-pod pull `CheckpointSource.LoadCheckpoint` (`pkg/adapter/resume.go:20-23`, `:88`) that C2 deletes. Making the gateway stream N chunk bodies would require either a new server-streaming RPC or a re-use of `PrepareWorkspace`, both of which add a gateway-side data plane that this proposal exists to avoid, and would put a 512 MiB workspace (`spec/04:255`) through gRPC framing. The gateway therefore mints one `GET` capability per chunk against the same `Presigner` boundary, and the adapter fetches, concatenates, and extracts. `spec/13:13`'s "File delivery: gateway-mediated only" row is amended rather than claimed as preserved: the gateway remains the sole authority that resolves, validates, and signs the keys, and the pod holds no object-store credential, no `LIST`, and no `DELETE`. A `GET` capability names one key the pod's own session authored, so it grants no read the pod did not already have.
- **`CheckpointBarrier` becomes quiesce-and-hold, and the ack is the completion signal.** The adapter cannot self-initiate an upload under this model (it holds no `checkpoint_id`, no intent row, and no grants), so the barrier RPC narrows to quiescence and the gateway drives the same `Checkpoint` stream against the held-quiescent pod inside the BarrierAck deadline. The barrier dispatcher opens that stream concurrently with the in-flight `CheckpointBarrier` RPC, because a gateway that waits for the ack and an adapter that waits for the stream would deadlock (C3). The adapter returns `CheckpointBarrierAck` only after the gateway's `Checkpoint` stream terminates, so `checkpoint_ref` echoes the gateway-minted `checkpoint_id` the adapter received in `Start`, and `quiesced_ms` is time-to-quiescence measured inside that window. Keeping the ack as the completion signal is what preserves `spec/10:124`'s BarrierAck floor rule (the deadline must cover the longest tier cap because the upload happens inside the ack window), `spec/10:167`'s single wall-clock deadline, and `spec/10:169-172`'s BarrierAck-timeout partial-capture path, all of which are written against an ack that follows the upload.
- **§13 is amended as an extension of the NET-046 pattern.** Agent pods get one new config-gated supplemental egress policy to the object store and MinIO gets one paired conditional ingress clause, over TLS, with the CA bundle projected into agent pods. The policy takes a NET id and joins the `lenny-preflight` selector audit.
- **Every `DeleteObject` stays gateway-side.** The pod is granted single-key `PUT` capabilities on the upload path and single-key `GET` capabilities on the restore path, and no delete or multipart capability on either, so `spec/04:249`'s adapter-side `AbortMultipartUpload`/`DeleteObject` text is corrected to the gateway-side prefix sweep the same spec already assigns to the coordinator at `spec/10:157`. No multipart upload is ever opened.
- **`slot_id` is written by the gateway from the registry binding** (`checkpointer.go:286` already reads `binding.SlotID` for the retention catalog). Slot-scoped adapter checkpoint roots and the slot-aware `CheckpointRequest` stay with proposal 0047.
- **A non-signing object-store provider cannot serve pod-based checkpointing.** `pkg/blobstore/fsstore.go` and `MemoryStore` have no signing primitive, so the gateway fails closed at startup when pod-based sandboxes are configured against a resolved store that cannot mint capabilities, rather than growing a second, relayed data path for them.
- **Cloud-managed profiles upload pod-side through an operator-supplied egress allow-list (resolves the Q1 review question).** A `provider = s3 | gcs | azure` profile has an external object-store endpoint. Its `allow-pod-egress-objectstore` cloud-managed arm renders an `ipBlock` peer on TCP 443 from a required, operator-supplied `objectStorage.egressCIDRs` allow-list, or a PrivateLink or VPC-endpoint address, and there is no ingress-side clause. A self-managed MinIO profile instead uses the paired pod-selector ingress rule on the MinIO component (`spec/13:220`). An empty `objectStorage.egressCIDRs` under a non-`minio` provider renders no policy and fails preflight. This is the S1 drafting mechanism, and v1 accepts the operator-supplied CIDR list rather than deferring the cloud-managed profiles.
- **Embedded Mode wires a signing store so the adapter code path is byte-identical (resolves the Q2 review question).** Embedded Mode selects a signing backend, either an embedded MinIO or a `Presigner` implementation over the embedded store, so the adapter runs the one HTTP `PUT` against a signed URL that every other mode runs. Embedded Mode is not checkpoint-free. §4.4 therefore stays deployment-mode-independent, which `spec/17:217` requires; declaring Embedded Mode checkpoint-free would make §4.4 mode-dependent, which v1 forbids. The Embedded Mode store resolution must yield a `Presigner`-capable store, so the C1 startup assertion passes for it (the bare in-memory `MemoryStore` reached by a misconfigured empty `minio.endpoint` still fails closed, because it exposes no signing primitive).
- **The grant window defaults to 4 and a pool may override it (resolves the Q4 review question).** `checkpointGrantWindow` sets both the pipelining depth and the worst-case unreconciled overage against a provider that ignores the signed `Content-Length` (`checkpointGrantWindow × partialChunkSizeBytes`). Its deployment-wide default is 4. A pool config value overrides the deployment-wide default, so an operator sets the pipelining-versus-overage trade-off per pool; the checkpoint driver reads the pool's override at attempt time and falls back to the deployment-wide default when the pool sets none. `checkpointCapabilityTTLSeconds` (default 30) is the paired capability TTL and stays deployment-wide.
- **`manifest_reason = 'terminated_during_resume'` is removed (resolves the Q3 review question).** The value is unsatisfiable. The mid-resume terminal collapse (`resuming → cancelled` / `resuming → completed`) writes no manifest row: `bumpCoordinationGenerationOnSnapshotClose` (`pkg/gateway/sessionserver/start.go:3397`) bumps `coordination_generation` and writes the terminal session state alone, and the resume path is read-then-delete (`resumeOnPod` restores the workspace from the checkpoint, then `CleanupAfterResume` soft-deletes the row on success, `start.go:2786`). The aborted replay commits no chunks and writes no row that could carry the reason. The enum becomes the closed set `in_progress`, `complete`, `timeout`, `stream_truncated`, `superseded`, `quota_exceeded`. The durable record of an intentional mid-resume collapse is the terminal session state plus the `coordination_generation` bump written in the same transaction. S2 removes the value from the §10.1 enum (`spec/10:141`) and the §16.1 label domain (`spec/16:195`), and two further S2 change blocks remove its cross-references at `spec/07:214` and `spec/04:157`.
- **Classified `fix`.** The dominant action builds the pipeline the committed spec already describes and reconciles the spec passages that contradict it. The one new normative surface is the capability model in §13.2 and its rendered policy pair.

## 3. How the pieces fit at the chunk boundary

A checkpoint attempt begins at the gateway. `Checkpointer.snapshot` mints a `checkpoint_id` UUID, opens the bidirectional `Checkpoint` stream against the bound pod, and sends `Start{checkpoint_id, trigger, chunk_size_bytes, chunk_encoding}`. The adapter runs the §4.4 line 255 workspace-size probe and replies `Probe{bytes}`. The gateway reserves `bytes` against the tenant's storage quota (`spec/11:35`), inserts the manifest row with `partial = true`, `manifest_reason = 'in_progress'`, `chunk_count = 0`, `workspace_bytes_uploaded = 0`, and the `chunk_object_key_prefix` derived from `checkpoint_id`, soft-deleting every prior active (`partial = TRUE AND deleted_at IS NULL`) manifest row for `(tenant_id, session_id, slot_id)` at or below the incoming `coordination_generation` in the same transaction, and only then sends the first grants. The supersede predicate is at-or-below rather than strictly-below because `coordination_generation` does not advance between two checkpoints of the same session on the same coordinator, so a retained aborted attempt sits at the same generation as the next one and would otherwise collide with the partial-active unique index.

The adapter archives `/workspace/current` into the same `io.Pipe` it uses today, buffers exactly one `chunk_size_bytes` block at a time, and sends `ChunkReady{index, length}` for each. The gateway rejects any declared `length` outside `(0, chunk_size_bytes]`, the value it chose itself and sent in `Start`, and aborts the attempt with `stream_truncated` before it signs anything or touches the quota counter. It then signs a PUT capability for `chunk-{index}.{enc}` at that exact `Content-Length`, with the tenant's SSE-KMS headers bound into the signature, and returns `Grant{index, url, expires_at}`. Up to `checkpointGrantWindow` grants are outstanding at once; reserved headroom covers the sum of their signed lengths. The adapter PUTs the block against the URL, retries within the §4.4 lines 261-264 budget, and acks. The gateway confirms the object with `Stat`, inserts the `artifact_store` catalog row from the confirmed size, and issues the monotonic conditional `UPDATE` from `spec/10:131`. Confirmation runs off the upload's critical path and never gates the next grant.

The adapter closes with `Summary{total_bytes, chunk_count}`. When every declared byte is confirmed, the gateway finalises the row with `partial = false` and `manifest_reason = 'complete'`, reconciles the reservation against the confirmed total (`Adjust(confirmed_total − reserved)`), writes the retention-catalog entry, and sets the session's `WorkspaceSnapshot.Ref` to the object path of the checkpoint's chunk prefix, whose last path segment is the gateway-minted `checkpoint_id`. When the attempt ends early (deadline fire, stream truncation, adapter crash, supersession, or a quota refusal at signing time), the gateway finalises `partial = true` with a `manifest_reason`. A **deadline-fire** finalisation (`manifest_reason = 'timeout'`) is the recovery aid `spec/04:235` describes: its row and chunks are retained for the resume path and reclaimed only by the resume-time cleanup or the §12.5 backstop. Every terminal arm releases the reservation the attempt is not going to keep: on abort, `Adjust(−(reserved − confirmed_bytes))` after finalisation, so an aborted checkpoint charges the tenant only for the chunks it actually confirmed. When an attempt aborts on one of the **other** arms (stream truncation, adapter crash, supersession, quota refusal), no resume will consume it, so the gateway sweeps the prefix by `ListObjectsV2` under `chunk_object_key_prefix`: for every object the list returns it runs the guarded cataloging soft-delete (which releases a confirmed chunk's bytes from the quota counter and no-ops for an uncounted straggler that an outstanding grant wrote to the prefix after the last counter read), then issues the per-key `DeleteObject` call, and soft-deletes the manifest row only after a final prefix list returns empty. The list is the discovery step, not the confirmed-chunk set, so a chunk that a still-outstanding presigned grant lands after the gateway observed the truncation is deleted rather than orphaned under a soft-deleted manifest row the `deleted_at IS NULL` backstop no longer selects.

Resume selects the highest-`coordination_generation` active manifest row for `(session_id, slot_id)`, which is the session's completed checkpoint unless a newer drain attempt left a `partial = true` row at or above it, and validates it against the session's `WorkspaceSnapshot.Ref`. It lists the chunk set under `chunk_object_key_prefix`, checks contiguity, mints one presigned `GET` capability per chunk index in `[0, chunk_count)`, and passes them on the unary `Resume` call. The adapter fetches the chunks in index order, concatenates them into the single byte stream `spec/10:155` already specifies, and extracts. The gateway then cleans up only when the row it restored from was `partial = true`: a completed checkpoint survives its own resume and is reclaimed by the §12.5 retention and rotation path, which C3 wires to release each rotated-out checkpoint's chunk rows and objects (the current `recordRetention` discards the rows `Rotate` returns for exactly that purpose). Seal runs the same `Checkpoint` stream, so `Seal` stops returning `Unimplemented`, `sealWorkspace` stops burning 300s, the session reaches `completed` rather than `failed`, and the `binder.go:1829` recycle branch is reachable for the first time.

## 4. Proposed changes

### S1. §13: the presigned checkpoint capability, the agent-to-object-store egress policy, and the MinIO ingress clause

**Target:** `spec/13_security-model.md` §13.1 (the control table, `:5-14`, including the **Credentials** row `:12` and the **File delivery** row `:13`); §13.2 (the base-policy prose sentence `:78`; the supplemental-policy block after `allow-pod-egress-otlp`, `:145-178`; the NET-003 label-immutability note `:184`; the NET-047/NET-050 selector-audit note `:209`; the MinIO component row `:220`; the NET-002 note `:444`); §13.3 (credential flow); `spec/17_deployment-topology.md` §17.6 "Checks performed" (the new preflight row, S6); `docs/getting-started/architecture.md:523-524` and `:534`; `docs/operator-guide/security.md:270-271` (the two verbatim mirrors of the §13.1 table and the "Pods CANNOT … Access MinIO, Postgres, or Redis directly" row); `docs/getting-started/concepts.md:423-427` (the "Gateway-mediated file delivery" concept section, which states the same invariant in prose, "no direct object store access from pods").

**Rationale.** The §13 tables never wrote a checkpoint row, so the upload path the rest of the spec assumes has no route and no credential. Keeping the upload pod-side requires §13 to say so explicitly. The amendment follows the NET-046 pattern (`spec/13:147-176` plus the conditional component-table row at `spec/13:223`): a config-gated supplemental agent-egress policy to an in-cluster `lenny-system` component, paired with a conditional ingress row on that component, over TLS, with a deployer-supplied CA bundle projected into agent pods.

**Change (§13.1 table).** Amend the **Credentials** row (`:12`) to name the capability class explicitly, amend the **File delivery** row (`:13`) so it stops asserting a gateway byte path for checkpoint objects, and add a **Checkpoint transfer** row:

```
| Credentials     | No standing credentials; projected SA token + short-lived credential lease only (see [Section 4.9](04_system-components.md#49-credential-leasing-service)). Object-store access is granted as a gateway-minted presigned capability (single key, single method, exact `Content-Length` on a `PUT`, short expiry) and never as an object-store credential. |
| File delivery   | Gateway-mediated for all session inputs and outputs. Checkpoint chunk objects are the one exception: their bytes travel between the agent pod and object storage against gateway-minted presigned capabilities (see **Checkpoint transfer**). The gateway remains the sole authority that resolves the key, validates the tenant prefix, and signs. No shared storage mounts. |
| Checkpoint transfer | The agent pod `PUT`s checkpoint chunks to, and on resume `GET`s them from, object storage against gateway-minted presigned URLs (NET-0xx). The pod holds no object-store credential, receives no `LIST`, `DELETE`, or multipart capability, and can address no key outside the `checkpoint_id` prefix the gateway signed for its own session. A `PUT` capability cannot be used for a `GET` and a `GET` capability cannot be used for a `PUT`: the HTTP method is inside the signature. |
```

The `docs/getting-started/architecture.md` and `docs/operator-guide/security.md` mirrors of this table carry the same amendment, and the "Pods CANNOT … Access MinIO, Postgres, or Redis directly" row (`docs/getting-started/architecture.md:534`) is narrowed to Postgres and Redis, with the object-store row moved to the "Pods CAN" column as "`PUT` and `GET` their own checkpoint chunks against a gateway-minted presigned capability".
