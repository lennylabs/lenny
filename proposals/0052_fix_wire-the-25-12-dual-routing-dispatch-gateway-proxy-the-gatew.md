# Proposal: Wire the §25.12 dual-routing dispatch: gateway-proxy the gateway-owned tools with forwarded identity, bridge the RFC 9068 JWT scope claim into the MCP-boundary gate, and fix the stale operability-vs-admin capability filter

- **Status:** Verified (2026-07-22). Converged after 6 adversarial review rounds (6 findings fixed); awaiting sign-off.
- **Date:** 2026-07-22.
- **Scope:** A spec-first fix that completes the §25.12 `/mcp/management` `tools/call` dispatch surface. It stages one §25.12 spec clarification (`spec/25_agent-operability.md`, the Capability Negotiation table region at `:4585`), four code changes (`pkg/ops/opsserver/mcp.go`, `pkg/ops/gateway/client.go`, a new `pkg/ops/opsserver` bridge middleware, and `pkg/ops/mcp/{registry.go,server.go}`), the wiring through `pkg/ops/opsserver` and `cmd/lenny-ops`, and the tests across tiers 1, 4, and 9. The registry already holds the full 222-tool inventory (164 `admin.*` gateway-owned plus 58 `lenny_*` ops-owned, `pkg/ops/mcp/generated_tools.go`) and `tools/list` already intersects the caller scope claim (`pkg/ops/mcp/server.go:188-189`), but the dispatch side is half-built: no ops-vs-gateway routing predicate and no gateway proxy, no bridge from the authenticated JWT scope claim to the MCP-boundary gate, no identity-forwarding transport, and a stale capability classifier that returns an empty list for `scope: "admin"`. This proposal settles the dispatch on the existing drift-guarded `opsserver.RouteSchemas()` ownership predicate for transport routing and on the tool's scope-claim domain prefix for capability classification. It closes T-25.12.2, T-25.12.3, T-25.12.7, T-25.12.22, and T-STD.8.

This document stages the proposed spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off, spec edit first.

## 1. Problem

The §25.12 `ManagementMCPAdapter` `tools/call` surface is half-built. `tools/list` works end to end: the registry holds 222 generated tools (164 `admin.*` platform-management tools plus 58 `lenny_*` operability tools, `pkg/ops/mcp/generated_tools.go`), and `handleToolsList` already passes the caller scope claim into `FilterForList` (`pkg/ops/mcp/server.go:188-189`). Four dispatch-side gaps remain, all verified at branch HEAD.

**1. No ops-vs-gateway routing predicate and no gateway proxy.** `opsInvoker` is `type opsInvoker struct { server *Server }` (`pkg/ops/opsserver/mcp.go:30`) with no gateway-client field and no proxy branch. `Invoke` (`pkg/ops/opsserver/mcp.go:55-126`) unconditionally replays every tool via `httptest` against `i.server.mcpReplay` (`:102`), which is the local post-auth chain `requireAdminRole(scopeEnforce(mux))` (`pkg/ops/opsserver/auth.go:60,71`). The ~162 gateway-owned `admin.*` tools (every `admin.*` except `admin.me` and `admin.me_authorized_tools`, which are ops-owned per `pkg/ops/opsserver/schema.go:178-179`) have no dispatch target and 404 against the lenny-ops mux. The illustrative `ManagementMCPAdapter` in the spec (`spec/25_agent-operability.md`, Architecture, `opsRouter` + `gateway` fields) declares fields that do not exist on the actual invoker; the spec mandates transparent dual routing ("Tool invocations are routed transparently to either `lenny-ops` handlers ... or Gateway admin API via `GatewayClient`").

**2. The RFC 9068 JWT scope claim never reaches the MCP-boundary gate.** `mcp.WithScopes` (`pkg/ops/mcp/server.go:368`), documented as the bridge the admin-API middleware calls after validating a Bearer JWT, has zero callers in the tree (grep confirms only its own definition). `authmw.Principal.Scopes`, parsed off the JWT, is enforced only at the REST-replay gate (`pkg/ops/opsserver/scope_enforce.go:117`). The MCP-boundary gate at `pkg/ops/mcp/server.go:251` reads `requestScopes`, which sees a scope claim only via the `X-Lenny-Scope` dev header (`:384`). So the spec-named check ("A caller whose scope doesn't match receives `403 SCOPE_FORBIDDEN` from the MCP adapter before any REST call is issued") is unreachable for a JWT caller (T-STD.8, `TEST-GAPS.md:11886`).

**3. No identity-forwarding transport for the gateway proxy.** `GatewayClient` (`pkg/ops/gateway/client.go`) authenticates with a single service-account OIDC bearer (`:194-227`) with no per-call identity override, and wraps every response `>= 400` into `*HTTPError` (`:269`) with no raw `(status, body)` passthrough for verbatim re-emission of a gateway RBAC denial. §25.12 requires forwarding the caller identity as the `Authorization` header on gateway calls ("The authenticated identity from the MCP session → `Authorization` header on gateway calls") so the gateway's own OIDC/RBAC re-authorizes as the actual caller, and requires that a `tenant-admin` calling a `platform-admin` tool receives the gateway's own `403`.

**4. The capability classification is stale and incomplete.** `FilterForList` (`pkg/ops/mcp/registry.go:76-101`) returns an empty list for `caps.Scope == "admin"` (`:89-91`) with the now-wrong comment "until the admin-API tools are generated"; there is no `caps.Scope == "operability"` positive branch; `Capabilities` (`:52-63`) models only `ReadOnly`/`NonDestructive`/`Scope` with no `TenantScoped`; `capabilitiesFromParams` (`pkg/ops/mcp/server.go:404`) does not parse `tenantScoped`. The §25.12 capability table enumerates operability and admin as domain lists (`spec/25_agent-operability.md:4585-4586`) that do not cover the ~30 generated `admin.*` domains (`pool`, `user`, `tenant`, `rbac`, `connector`, `environment`, and others; census over `pkg/ops/mcp/generated_tools.go`), so `FilterForList` has no mechanical rule for those tools (T-25.12.7, `TEST-GAPS.md:10084`).

The single existing de-facto ops-vs-gateway predicate is `opsserver.RouteSchemas()` membership (`pkg/ops/opsserver/schema.go`, drift-guarded by `TestRouteSchemasMatchLiveMux`): the 60 non-empty `MCPTool` names it enumerates (58 `lenny_*` plus `admin.me` and `admin.me_authorized_tools`) are the ops-owned tools; the remaining 162 `admin.*` tools are gateway-owned. This proposal settles transport routing on that predicate and classifies capability filtering by the tool's scope-claim domain prefix, closing T-25.12.2 (`TEST-GAPS.md:10054`), T-25.12.3 (`:10062`), T-25.12.7 (`:10084`), T-25.12.22 (`:10154`), and T-STD.8 (`:11886`).

## 2. Decisions

- **Adopt `opsserver.RouteSchemas()` membership as the single ops-vs-gateway transport-routing predicate (CODE-1).** A tool whose `Name` is one of the 60 non-empty `MCPTool` values in `RouteSchemas()` is ops-owned (local replay); every other tool in the 222-tool inventory is gateway-owned (gateway proxy). This predicate already exists and is drift-guarded bidirectionally by `TestRouteSchemasMatchLiveMux`, so it needs no generator or OpenAPI change. The rejected alternative is a new `x-lenny-owner` OpenAPI extension plus generator emit and a second drift guard, which adds protocol surface for information `RouteSchemas()` already carries (recorded in Non-goals).

- **Classify operability-vs-admin capability filtering by the tool's scope-claim domain prefix against an explicit operability-domain set, decoupled from the transport-routing predicate (SPEC-1, CODE-4).** The operability-vs-admin axis is a semantic category that is orthogonal to transport ownership: the spec's own operability row (`spec/25_agent-operability.md:4585`) lists `health` and `audit` as operability domains, yet both are gateway-owned (audit has zero `RouteSchemas` entries and the aggregate `lenny_health_*` tools are absent from `schema.go`). Classifying by `RouteSchemas` ownership would push `health`, `audit`, and `recommendations` into `admin`, contradicting the operability row. Every generated tool already carries a `tools:{domain}:{action}` scope claim (`pkg/ops/opsserver/schema.go:183`), so the mechanical rule tests that domain prefix against a closed operability-domain set that the spec clarification pins.

- **Inject the ops-owned tool-name set from `opsserver` into `pkg/ops/mcp` rather than recompute it there (WIRE-1).** `pkg/ops/mcp` cannot import `pkg/ops/opsserver` (`opsserver` imports `mcp`; the reverse is a cycle), and `RouteSchemas()` lives in `opsserver`. `opsserver` builds the ops-owned name set once from `RouteSchemas()` and passes it to `opsInvoker` (for CODE-1 routing) and into `mcp.NewServer` (available for the registry). Duplicating the ops list inside `mcp` is rejected because it would drift from the drift-guarded `RouteSchemas()` source.

- **Forward the caller identity to the gateway with a single additive raw-passthrough method on the §25.4 `GatewayClient` (CODE-2).** The new method sets no service-account bearer, forwards the headers the invoker assembled (the caller `Authorization` bearer, or the dev-mode identity headers, plus the §25.12 correlation headers), and returns the gateway status and body verbatim without wrapping `>= 400` into `*HTTPError`. The existing SA-bearer `Get`/`PostJSON`/`PutJSON`/`FanOut*` methods are untouched so the drift/health/config fan-out role is unchanged. A separate proxy component is rejected because it would duplicate the client's transport, TLS-handshake metrics, and timeout handling (recorded in Non-goals).

- **Bridge the authenticated `Principal.Scopes` onto the MCP request context via the already-exported `mcp.WithScopes` at the ops MCP boundary (CODE-3, the core T-STD.8 fix).** A small middleware wrapping the mounted `mcp.Server` reads `authmw.FromContext`, calls `mcp.WithScopes(ctx, principal.Scopes)`, and captures the caller identity headers for the proxy. The bridge attaches a context scope set only when the JWT scope claim is present (`p.Scopes.Present()`). The `AllowDevHeaders` dev-header posture attaches a `Principal` with a zero `Scopes` set (`pkg/gateway/middleware/auth/auth.go:561-568` never sets `Scopes`), so guarding on `Present()` leaves the context scope set unset and `requestScopes` (`pkg/ops/mcp/server.go:385-388`) falls back to `X-Lenny-Scope` exactly as today. An absent JWT scope claim (`Present() == false`) applies no narrowing per the §25.1 absent-claim semantics.

- **Re-emit gateway 4xx RBAC denials verbatim with no error-envelope work.** The invoker maps the raw `(status, body)` into `ToolResult{Status, Body}`, and `toolCallResult` (`pkg/ops/mcp/server.go:325-329`) already sets `isError = Status >= 400` and carries the body as the content text. A transport failure (gateway unreachable) maps to `ToolResult{Unavailable: true}` → `-32000 ENDPOINT_UNAVAILABLE`, keeping the tool in `tools/list`. Reconciling the error-envelope taxonomy is C-32's scope (recorded in Non-goals).

- **Derive `tenantScoped` from the existing `Tool.RequiredRole` (CODE-4).** `tenantScoped == RequiredRole != "platform-admin"` (the underlying endpoint admits `tenant-admin`), so it needs no new generated field; only the `Capabilities` model and `capabilitiesFromParams` parsing are extended.

## 3. The dispatch path after the change

An MCP `tools/call` arrives on the `/mcp/management` mount, which sits behind `withOpsAuth` in `opsserver` (so `authmw.Wrap` has attached the `Principal` to the context). The CODE-3 bridge middleware reads the `Principal`, enriches the context with `mcp.WithScopes(ctx, p.Scopes)` when the JWT scope claim is present (`p.Scopes.Present()`) so the MCP-boundary gate at `pkg/ops/mcp/server.go:251` sees the RFC 9068 scope claim, and stashes the caller identity headers (the raw `Authorization` bearer, or the dev-mode identity headers the gateway auth layer consumes, `X-Lenny-Tenant-ID`, `X-Lenny-Roles`, and `X-Lenny-Groups`, under `AllowDevHeaders`) on an opsserver-internal context key.

`handleToolsCall` runs the pre-dispatch scope check (`server.go:251`); a scope mismatch now returns `403 SCOPE_FORBIDDEN` before any REST or gateway call, because the JWT claim is on the context. On pass, it calls `opsInvoker.Invoke`. The invoker branches on `i.opsOwned[tool.Name]`: an ops-owned tool keeps the existing local `httptest` replay against `i.server.mcpReplay`; a gateway-owned tool calls `invokeGateway`, which assembles the forward headers (caller `Authorization` or dev identity, plus `Content-Type` and the §25.12 `X-Lenny-Operation-ID`/`X-Lenny-Agent-Name` correlation headers), calls `GatewayClient.ProxyAdminCall`, and maps the raw `(status, body)` into `ToolResult`. A gateway `403` reaches the agent verbatim as an `isError` tool result; a transport failure maps to `-32000` and the tool stays listed.

For `tools/list`, `FilterForList` classifies each tool's scope-claim domain prefix against the operability-domain set: `scope: "operability"` keeps only operability-domain tools, `scope: "admin"` keeps only admin-domain tools, `tenantScoped` keeps only tools whose `RequiredRole` admits `tenant-admin`, and the existing `ReadOnly`/`NonDestructive` branches and the `callerScopes.Matches` intersection are unchanged.

## 4. Proposed changes

### SPEC-1. Pin the §25.12 operability-vs-admin capability classification to the tool's scope-claim domain prefix

**Target:** `spec/25_agent-operability.md` §25.12 Capability Negotiation table region (`:4585-4586`), the `scope: "operability"` and `scope: "admin"` filter rows.

**Rationale:** The `scope: "operability"` row (`:4585`) is a closed parenthetical of domains and the `scope: "admin"` row (`:4586`) names only "tenant/pool/credential/runtime/quota lifecycle", but the generated inventory carries ~30 `admin.*` domains (`user`, `rbac`, `connector`, `environment`, and others) that fall in neither list, and the served OpenAPI supplies no per-tool operability-vs-admin marker. Without a mechanical rule, `FilterForList` cannot classify those tools. The natural marker is the `tools:{domain}:{action}` scope claim every generated tool already carries; the rule tests that domain prefix against an explicit operability-domain set. This set is seeded from the existing operability row plus `recommendations` (named as operability at the routing exceptions and the `lenny-ctl` target table) and `logs` (named as an ops target at the `lenny-ctl` table), and it explicitly assigns every currently-unlisted generated domain. Classifying by domain prefix keeps `health`, `audit`, and `recommendations` on the operability side (matching the operability row and the routing tables) and preserves consistency between the two capability rows. It decouples this semantic axis from the ops-vs-gateway transport-routing predicate, which remains correct for CODE-1.

**Anchor:** Replace the `scope: "operability"` and `scope: "admin"` filter-effect cells. The `readOnly`, `nonDestructive`, and `tenantScoped` rows and the surrounding table are unchanged.

**Change (staged text).** Replace the `scope: "operability"` row:

```
| `{"access": ["admin-api"], "scope": "operability"}` | Only operability tools (health, diagnostics, runbooks, events, audit, drift, backup/restore, upgrade, locks, escalations, caller identity, operations inventory). |
```

and the `scope: "admin"` row:

```
| `{"access": ["admin-api"], "scope": "admin"}` | Only platform-management tools (tenant/pool/credential/runtime/quota lifecycle). |
```

with:

```
| `{"access": ["admin-api"], "scope": "operability"}` | Only operability tools, classified by the tool's `x-lenny-scope` domain prefix (`tools:{domain}:{action}`). The operability domains are `health`, `diagnostics`, `runbooks`, `events`, `audit`, `drift`, `backup`, `restore`, `upgrade`, `locks`, `escalation`, `logs`, `me` (caller identity), `operations` (operations inventory), `recommendations`, and the introspection and control domains `config`, `schema`, `sessions`, `tree`, `platform`, and `preflight`. A tool whose domain is in this set is an operability tool regardless of whether it is served by lenny-ops or proxied to the gateway admin API. |
| `{"access": ["admin-api"], "scope": "admin"}` | Only platform-management tools, classified as every tool whose `x-lenny-scope` domain prefix is not in the operability-domain set above (for example `tenant`, `pool`, `credential_pool`, `runtime`, `quota`, `user`, `rbac`, `connector`, `environment`, `delegation_policy`, and the other platform-lifecycle domains). The operability and admin sets partition the full tool inventory. |
```

**Preserved unchanged:** the `readOnly`, `nonDestructive`, and `tenantScoped` rows, the "Multiple filters can be combined" note, and the Security Model section. The operability-vs-admin axis is now defined for every generated tool, and it is independent of the ops-vs-gateway transport-routing split.

### CODE-1. Add the ops-vs-gateway routing branch and gateway-proxy dispatch to opsInvoker

**Target:** `pkg/ops/opsserver/mcp.go` (`opsInvoker` struct `:30-32`, `Invoke` `:55-126`).

**Rationale:** `opsInvoker` replays every tool locally (`:102`), so the 162 gateway-owned `admin.*` tools 404 against the lenny-ops mux with nowhere to dispatch. The struct carries no gateway client and no ops-owned set. §25.12 mandates transparent dual routing.

**Change (staged description).** Extend `opsInvoker` with an ops-owned name set `opsOwned map[string]bool` (built by `opsserver` from the non-empty `MCPTool` values in `RouteSchemas()`, 60 entries) and a gateway proxy dependency `gateway *gateway.Client`. In `Invoke`, branch on `i.opsOwned[tool.Name]`:

- **In-set (ops-owned):** keep the existing local-replay path unchanged (`httptest` against `i.server.mcpReplay`, the §25.2 dry-run probe at `:110-119`).
- **Not-in-set (gateway-owned):** call a new `invokeGateway(ctx, tool, args)`. It reuses `buildToolRequest` to form path/query/body, assembles the forward headers (the caller `Authorization` bearer or the dev-mode identity headers read from the context carrier CODE-3 sets, plus `Content-Type`, `X-Lenny-Caller`, and the §25.12 `X-Lenny-Operation-ID` / `X-Lenny-Agent-Name` correlation headers from `correlation.From(ctx)`, exactly as the local replay does at `:94-100`), calls the CODE-2 `ProxyAdminCall` raw method, and maps the raw `(status, body)` into `ToolResult{Status, Body}` with the same §25.2 dry-run probe the local path applies. A transport error from the proxy sets `ToolResult{Unavailable: true}` so `handleToolsCall` returns `-32000` and the tool stays in `tools/list`.

A nil `i.gateway` (dev / no-gateway posture) makes every gateway-owned tool report `ENDPOINT_UNAVAILABLE`, consistent with the local-only dev deployment.

### CODE-2. Add an identity-forwarding raw-passthrough method to the §25.4 GatewayClient

**Target:** `pkg/ops/gateway/client.go` (new `ProxyAdminCall` method alongside `do` `:194` and `doRaw` `:397`).

**Rationale:** The client presents a single service-account bearer (`:217-227`) with no per-call identity override and wraps every response `>= 400` into `*HTTPError` (`:269`), so it can neither forward the caller identity nor re-emit a gateway RBAC denial verbatim. §25.12 requires the caller identity on the gateway `Authorization` header and requires the underlying `403` to reach the agent.

**Change (staged description).** Add:

```go
// ProxyAdminCall executes one §25.12 gateway-proxied admin-API call on
// behalf of an MCP caller. It forwards the supplied headers verbatim (the
// caller's Authorization bearer or dev-mode identity headers, the §25.12
// correlation headers, and Content-Type) and sets NO service-account
// bearer, so the gateway's own OIDC/RBAC re-authorizes as the real caller.
// It returns the gateway's status and body for any completed HTTP response
// including 4xx/5xx, without wrapping into *HTTPError, so a gateway RBAC
// denial re-emits verbatim to the agent. Only a transport-level failure
// (the request never completed) returns a non-nil err.
//
// spec: §25.12 (Headers and Correlation; Security Model layer 3)
func (c *Client) ProxyAdminCall(ctx context.Context, method, path string, body []byte, headers http.Header) (status int, respBody []byte, err error)
```

The method builds the request against `c.baseURL + path` with the given body, copies `headers` verbatim onto the request, sets no SA bearer, executes via `c.http`, records the §25.4 TLS handshake via `c.recordHandshake`, reads the full body, and returns `(resp.StatusCode, body, nil)`. Leave `Get`/`PostJSON`/`PutJSON`/`FanOutGet`/`FanOutGetRaw` and the SA-token `do`/`doRaw` path untouched.

### CODE-3. Bridge Principal.Scopes into the MCP-boundary scope gate and capture caller identity for the proxy

**Target:** a new `pkg/ops/opsserver/mcp_bridge.go`; the `/mcp/management` mount in `pkg/ops/opsserver/opsserver.go` (`:437-439`).

**Rationale:** `mcp.WithScopes` (`pkg/ops/mcp/server.go:368`) has zero production callers, so a Bearer-JWT caller's RFC 9068 scopes never reach the MCP-boundary gate at `pkg/ops/mcp/server.go:251` (T-STD.8). The gateway proxy also needs the caller's `Authorization` bearer, which the `Invoker` interface does not carry (`Invoke` takes `ctx` only, `pkg/ops/mcp/server.go:73`).

**Change (staged description).** Add a middleware that wraps the mounted `mcp.Server`:

1. On each request, read `authmw.FromContext(r.Context())`. When a `Principal` is present and its scope claim is present (`p.Scopes.Present()`), enrich the context with `mcp.WithScopes(ctx, p.Scopes)` so `requestScopes` (`pkg/ops/mcp/server.go:384`) sees the JWT claim at the MCP-boundary gate. When the `Principal` carries a zero `Scopes` set (the `AllowDevHeaders` dev-header posture attaches a `Principal` without scopes, `pkg/gateway/middleware/auth/auth.go:561-568`), do not attach a context scope set, so `requestScopes` falls through to the `X-Lenny-Scope` header fallback (`pkg/ops/mcp/server.go:385-388`) instead of short-circuiting on an empty set whose `Present()` is false (`pkg/common/scopes/scopes.go:226`).
2. Store the caller identity for forwarding on an opsserver-internal context key: the raw `Authorization` header when present, else the dev-mode identity headers the gateway auth layer consumes (`X-Lenny-Tenant-ID`, `X-Lenny-Roles`, and `X-Lenny-Groups`) when `AllowDevHeaders` is set. The gateway auth middleware enters its dev-header path only when `X-Lenny-Tenant-ID` is present and reads roles from `X-Lenny-Roles` (plural) under `AllowDevRoles` (`pkg/gateway/middleware/auth/auth.go:358-359,565-568`); it does not consume `X-Lenny-Scope` for role enforcement and its dev path leaves `Principal.Scopes` zero, so forwarding `X-Lenny-Scope` would not affect the gateway's RBAC decision. The singular `X-Lenny-Role` is a lenny-ops REST-handler convention (`pkg/ops/opsserver/locks.go:89`, `event_subscriptions.go:64`) that the gateway auth layer never reads.
3. Serve `s.mcp` with the enriched context.

At `opsserver.go:437-439`, wrap `s.mcp` in this middleware before `Handle`. The bridge sits inside `withOpsAuth` (the `/mcp/management` mount is on `s.mux`, reached after `authmw.Wrap` attaches the `Principal`), so the `Principal` and its parsed `Scopes` are already on the context. Because the bridge attaches a context scope set only when `p.Scopes.Present()`, `requestScopes` retains its `X-Lenny-Scope` header fallback both in the no-`AuthConfig` dev path and in the `AllowDevHeaders` posture, where the attached `Principal` carries a zero `Scopes` set. An absent JWT claim (`Present() == false`) applies no narrowing per §25.1.

### CODE-4. Fix FilterForList classification, model tenantScoped, and classify by scope-claim domain

**Target:** `pkg/ops/mcp/registry.go` (`Capabilities` `:52-63`, `FilterForList` `:76-101`); `pkg/ops/mcp/server.go` (`capabilitiesFromParams` `:404-433`).

**Rationale:** `FilterForList` returns an empty list for `scope: "admin"` (`:89-91`) with a stale comment, has no operability positive branch, and models no `tenantScoped`; `capabilitiesFromParams` does not parse `tenantScoped` (T-25.12.7). The classification is by the tool's scope-claim domain prefix against the SPEC-1 operability-domain set rather than by transport ownership.

**Change (staged description).**

1. Add `TenantScoped bool` to `Capabilities` and parse it in `capabilitiesFromParams` from both `capabilities` and `clientInfo.capabilities`.
2. Add an operability-domain set to the registry (a package-level `map[string]bool` seeded from the SPEC-1 enumeration) and a small `domainOf(scope string) string` helper that extracts the `{domain}` from a `tools:{domain}:{action}` scope claim (`t.Scope`).
3. In `FilterForList`, replace the `if caps.Scope == "admin" { continue }` block with:
   - `if caps.Scope == "operability" && !operabilityDomains[domainOf(t.Scope)] { continue }` (operability lists only operability-domain tools).
   - `if caps.Scope == "admin" && operabilityDomains[domainOf(t.Scope)] { continue }` (admin lists only non-operability-domain tools).
   - `if caps.TenantScoped && t.RequiredRole == "platform-admin" { continue }` (`tenantScoped` keeps only tenant-admin-accessible tools).
4. Keep the `ReadOnly` and `NonDestructive` branches and the already-wired `callerScopes.Matches(t.Scope)` intersection (`:95`). Update the stale `:86-88` comment.

Each check is an independent guard, so combined filters (for example `scope: "operability"` + `readOnly: true`) fall out naturally.

### WIRE-1. Thread the gateway proxy client and the ops-owned set through opsserver and cmd/lenny-ops

**Target:** `pkg/ops/opsserver/opsserver.go` (`Options`; `s.mcp` construction at `:437`); `cmd/lenny-ops` (`opsserver` `Options` assembly; reuse `buildGatewayClient` in `cmd/lenny-ops/gatewayclient.go:50`).

**Rationale:** `opsInvoker`'s gateway branch (CODE-1) needs a `*gateway.Client`, and the routing predicate needs the ops-owned set. `opsserver.Server` holds no gateway client today; `cmd/lenny-ops` already builds one via `buildGatewayClient` for `configservice`/`driftservice`/events (`gatewayclient.go:50`, `events_wiring.go:149`).

**Change (staged description).** Add a gateway-proxy client field to `opsserver.Options` (a `*gateway.Client`, nil in dev). In the constructor, build `opsOwned` once from `RouteSchemas()` (collect the non-empty `MCPTool` names), pass both `opsOwned` and the `Options` gateway client into the `opsInvoker` construction so the invoker carries them, and mount `s.mcp` behind the CODE-3 bridge. In `cmd/lenny-ops`, reuse `buildGatewayClient` to populate the new `Options` field, mirroring the existing `configservice`/`driftservice` wiring. A nil gateway client leaves the gateway branch reporting `ENDPOINT_UNAVAILABLE`.
