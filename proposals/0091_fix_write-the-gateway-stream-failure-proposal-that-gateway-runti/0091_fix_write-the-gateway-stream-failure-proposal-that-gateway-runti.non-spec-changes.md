# Non-spec changes: Gateway does not survive or react to Attach stream failure

## Design (implementation-facing)

The pod executor holds one `Attach` stream per session on a session-scoped context. One reader goroutine per stream consumes every frame. A one-slot turn token serializes turns on the stream, so the runtime's reply to an abandoned turn is consumed by the reader and never delivered to the next turn. The reader also observes every end of the stream, including an end while no message is outstanding. It evicts the stream from the cache and, for the ends SPEC-2b names as stream failures, calls a handler that the gateway injects. The handler reports `runtime_crash` through `Server.ReportSessionFailure`. The release that retires the pod runs in one place, `applyFailureFromActive`, so every reporter gets it.

The parts land in this order, and a later part depends on each earlier one:

1. CODE-1 (the held stream, the reader, and the turn token) lands before any reporter is wired. Without it, every second message on a session would end the stream and would be reported as a failure.
2. CODE-2 (the release funnel) lands before CODE-3 wires the detector, so no commit reports a failure that nothing releases.
3. CODE-3 wires the detector.

CODE-5 depends on CODE-1, whose cancel-based `EvictStream` ends the evicted stream on the adapter side.

The change adds no RPC, error code, details key, or session state, and it changes no response envelope. It adds one `BindResult` field, `CoordinationGeneration` (CODE-3 item 7).

## Binding and coordination-lease ownership

This section states the rule for a session's pod binding (its `podRegistry` entry and its cached `Attach` stream) and its §10.1 coordination lease on every edge that 0091 adds or changes. CODE-2 items 4, 7, and 8 point here.

**Invariant.** 0091 adds no `REG-COORDLEASE` write. The coordinating replica keeps the lease across the failure edge to `resume_pending` or `awaiting_client_action`. The Sweeper's self-held renew term (`priorHolder == s.replicaID` in `Sweep`) keeps renewing it there without a binding, which §29.6 **Preconditions.** and the §7.2 durable-inbox rows assume of the coordinating replica in those states. A resume bind on the holder renews the lease through the idempotent `leasestore.Acquire`. A resume bind on any other replica meets `leasestore.ErrHeld` while the holder renews the lease, and CODE-2 item 8 holds the row. RECORDS-1 item 10 files the lease lifecycle in the recovering states. No edge below releases a binding that a later bind of the same session published, except inside the windows the residuals state. A terminal session's binding is released by `recordSessionCompleted`. Its lease lapses at its TTL, because the Sweeper's terminal-row branch never renews it.

**Accepted residuals.**

1. **Registry read before removal.** The funnel's identity check, the dead-channel eviction, the peer-takeover eviction, and the CODE-3 item 3.3 eviction each read the registry and later remove by session ID. For the CODE-3 item 3.3 eviction, a same-replica binding published between its pointer check and `Remove` is removed and its stream evicted, with no release. A same-replica `POST /resume` loses its binding only if it runs CODE-2 item 7, claims and binds a pod, and publishes the binding between that read and the removal. After the funnel's removal, the resumed row is `running` with no binding while this replica still holds the lease. The Sweeper therefore renews the lease through its self-held term and does not re-adopt the pod. On a pool with `maxConcurrentSessions: 1`, once the released pod reaches `terminated`, the orphan session reconciler fails the session within one 60 s interval. A released slot binding leaves its pod and the pod's sibling slots live, because `ReleaseSlot` drains only that slot, so the session stays `running` with no binding and a lease this replica renews until the session watchdog ends it.
2. **Fence relinquish after the publish.** `resumeOnPod` publishes the binding before `fenceResumedPod`. A relinquish returns `coordfence.ErrRelinquished` with the binding published and the lease already released by the Fencer, and `isTransientPodClaimError` holds the row in `awaiting_client_action`. The Sweeper acquires the lease again on its next pass because the session is bound. The pod stays claimed until the next `POST /resume` releases it at CODE-2 item 7 or a terminal transition releases it.
3. **`coordinator_hold` over a recovered channel.** An `UNAVAILABLE` end with `coordinator_hold` keeps the binding, as the `UNAVAILABLE` row states, and the lease. The summary **Defects** entry **A coordinating replica cannot end a hold over a recovered channel.** states the outcome, and RECORDS-1 files it.
4. **Concurrent `POST /resume` calls.** `handleResume` checks the precondition on the row it read and then writes `resuming` unconditionally, so two concurrent `POST /resume` calls on one session are both admitted. On one replica, the second call's CODE-2 item 7 can release the binding the first call published. Across replicas, the second call meets `ErrHeld` and answers `RESUME_FAILED`. Its CODE-2 item 8 hold writes `awaiting_client_action` only over a `resuming` row, so it keeps a `running` commit that the first call wrote after the second call's `resuming` write. A `running` commit that lands before the second call's `resuming` write is replaced by that unconditional write, and the hold then writes `awaiting_client_action` over it, which leaves the row in `awaiting_client_action` while the first call's replica holds the binding and the lease. When the first call has not committed by the time the hold runs, the hold writes over the first call's `resuming`, the first call's commit then writes `running`, and a third `POST /resume` admitted between those writes repeats the race. Today `failSession` writes `failed` in each case. The race predates 0091.

## Staged code changes

### CODE-1 · Session-scoped `Attach` stream with one reader, a turn token, cancel-based eviction, and eviction on end

Targets: `pkg/gateway/session/executor/pod.go` (`PodExecutor.streams`, `streamFor`, `Send`, `EvictStream`, `readAttachResponse`, `maybeGateToolCall`); `pkg/gateway/session/executor/podstream.go` (new file in the existing package); `pkg/gateway/runtime/adapterclient/client.go` (`Attach` doc comment only).

Spec ties: §28.5.1 `CH-ATTACH` **Timing.** (as SPEC-2a states it), §28.5.3 `CH-MSGSOCK` **Timing.**, §7.2 tool-use approval.

1. **`attachConn`.** Add the unexported type `attachConn` in `podstream.go`. It holds the `*adapterclient.AttachStream`, the stream's context and its `cancel`, the session's `tenantID`, `sessionID`, and `sandboxName` (read from the binding at open), a `sendMu sync.Mutex`, a `closedByGateway` flag (`atomic.Bool`), the turn token (a channel of capacity 1), the registered turn (guarded by a small mutex), a `ready` channel closed when the open completes, the open error, and a `done` channel that the reader closes when it exits. `PodExecutor.streams` becomes `map[string]*attachConn`.
2. **Single writer.** Every write to the stream goes through `conn.send(b []byte) error`, which holds `sendMu` around `AttachStream.Send`. Both the `Send` path and the reader's approval relay use it. gRPC `SendMsg` is not safe for concurrent calls, so no other code calls `AttachStream.Send` directly.
3. **Open.** On a cache miss, `streamFor` reads the binding and caches a new conn under `e.mu`, with its context `context.WithCancel(context.WithoutCancel(ctx))`, and releases `e.mu`. A goroutine opens the stream on that context, starts the reader on success, removes the entry if the open fails and the entry is still this conn, and closes the conn's `ready` channel. Every `Send` on the session waits on `ready` or its own `ctx.Done()` before step 4.1, and returns the open error when one is recorded. The empty-session-identifier guard stays first.
4. **Turn.** For each message, `Send`:
   1. Acquires the turn token, selecting on the token, `ctx.Done()`, and `conn.done`.
   2. Registers the turn with a result channel of capacity 1.
   3. Writes the envelope through `conn.send`.
   4. Waits on the result channel, `ctx.Done()`, and `conn.done`.

   On `ctx.Done()`, `Send` returns the context error, wrapped, and leaves the turn registered and the token held. Only the reader completes a turn. It does so when it consumes a `response` frame, or when the stream ends. Completing a turn clears the registration and returns the token. On `conn.done`, `Send` returns a wrapped stream-ended error. The tenant for the approval gate comes from the conn rather than a fresh registry read.
5. **Reader.** The reader loops on `Recv` and handles each frame in this order:
   1. When an approval gate is wired, the reader gates a `tool_call` frame carrying `approvalRequired: true` on the conn's context with the conn's `tenantID`, whether or not a turn is registered, and relays the verdict through `conn.send`. A gate error fails closed: the reader logs it and relays a deny `tool_result` with `isError: true` and the reason `approval_error`, as for a timeout. When the conn's context is already done, because `EvictStream` cancelled it, the reader relays nothing. An evicted conn's replica may no longer coordinate the session (CODE-5). A relay write error is dropped, and the reader's next `Recv` returns the stream's end for `endConn` to classify.
   2. A `response` frame completes the registered turn by writing to its result channel. A `response` that arrives while no turn is registered is discarded.
   3. Every other frame is discarded, as `readAttachResponse` skips such frames today.

   The reader blocks only in `Recv`, in the approval gate, and in `conn.send`. It never waits on a consumer, so the adapter's per-subscriber intake never fills.
6. **End.** When `Recv` returns an error or `io.EOF`, the reader runs `endConn`:
   1. If `closedByGateway` is set, `endConn` closes `done` and returns.
   2. Otherwise it takes `e.mu` and deletes the cache entry only if the cached pointer is this conn.
   3. It runs the classification CODE-3 adds.
   4. It cancels the conn's context and closes `done`. A `Send` waiting on the conn therefore returns only after a reported failure has released the binding.

   Lock order: `e.mu` before any conn mutex. The reader holds no conn mutex while it takes `e.mu`.
7. **`EvictStream`.** Under `e.mu`, set `closedByGateway`, call the stored cancel, and delete the entry. Do not call `CloseSend`. `Release` and the coordination Sweeper's `EvictBinding` keep calling `EvictStream` unchanged.
8. **Removal.** Delete `readAttachResponse`. Change `maybeGateToolCall` to take the conn in place of the stream, so it writes through `conn.send` and gates on the conn's context.
9. **`adapterclient.Attach` doc comment.** State that the executor holds the stream on a session-scoped context and cancels it on eviction.
10. **Implementor verification.** Before CODE-3 wires the handler, confirm that no gateway-initiated operation other than `EvictStream` or `Release` ends a session's `Attach` stream with a status CODE-3 reports. If an operation does, its caller calls `EvictStream` before it issues the operation. An `Interrupt` on the embedded runtime ends its stream with `io.EOF` and needs no `EvictStream`; the next delivery's report is the summary defect **Embedded `Interrupt` ends the session's runtime loop**.

## Edge cases and accepted failure modes

- **Abandoned turn that never answers.** The token stays held until the stream ends or the session's binding is released. Later `Send` calls on the session wait on the token and return their own context errors. The watchdog or a heartbeat escalation bounds the wait.
- **Approval pending after the client disconnects.** The gate runs on the session-scoped context, so the approval stays resolvable. `toolApprovalTimeout` bounds it when set. At its default of 0, the wait lasts until the approval is resolved or the session's binding is released. While the reader waits in the gate, it reads no frames.
- **Failed report.** The stream has already been evicted, so the next message re-Attaches and re-escalates within the heartbeat interval plus the ack timeout (30 s + 10 s by default). The watchdog bounds an idle session.
- **Single-shot translator sessions.** These report through the same path. The `resume_pending` row they leave holds no resources, because the release runs on the failure edge.
- **Clean runtime exit.** An `io.EOF` end evicts without a report. Until the next message delivery reports the exited runtime under SPEC-2b, the session watchdog bounds an idle session.
- **Stale coordinator between a peer's adoption and its own next sweep.** Its stream and any approval gate stay live until CODE-5 evicts them. A stream failure inside the window is not reported, because CODE-3 item 3.3 finds the advanced generation and evicts the binding without a drain. A peer takeover that lands between the item 3.3 row read and the report's commit is not caught, because the compare-and-swap of CODE-2 item 2 checks the state only. A sweep that fails with an error other than `ErrHeld` extends the window, and a replica that lost the lease before any sweep renewed it, or that renews a stale Redis lease after a Redis outage, keeps its binding. A session released and rebound on the same replica between two sweeps keeps its old entry, so a `coordination_generation` bump between those sweeps, such as the one a failed `POST /resume` makes, followed by a stale-holder `ErrHeld` evicts the current coordinator. The per-frame `CH-ATTACH` generation check, filed by RECORDS-1, would close it.
- **Stale binding generation without a peer.** Three paths leave this replica coordinating under a binding whose stamp is below the row's generation. A peer's takeover can bump the generation and then fail to re-adopt and release the lease, after which this replica's sweep re-acquires it. `handleResume`'s failure exit bumps the generation while the row is still `resuming`, before the hold writes `awaiting_client_action`. The §8.10 tree-recovery reattach stamps the generation of a stale row, because `sessionNodeReattacher.ReattachNode` passes `resumeOnPod` a row listed at the start of `RecoverTree`. A stream failure on any of these bindings is evicted under CODE-3 item 3.3 without a drain. The pod stays claimed until the session reaches a terminal state, which the session watchdog bounds, or a later resume moves `pod_assignment`. The orphan-claim GC then drains it after its orphan timeout.
