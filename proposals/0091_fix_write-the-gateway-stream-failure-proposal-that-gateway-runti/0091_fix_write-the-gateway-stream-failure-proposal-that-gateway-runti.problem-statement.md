# Problem: Gateway does not survive or react to Attach stream failure

## Statement

This proposal is the gateway stream-failure proposal that gateway-runtime-comms-remediation.md section 10.2 schedules after proposal 0090. It closes BUILD-GAPS F-7.3.28 (Critical) and F-7.3.27 (High), both in the §7.3 section of BUILD-GAPS.md. The remediation plan lists it as a release prerequisite. The proposal has two dependent steps. Step 1 is a code-only fix that needs no spec change and lands first. Step 2 depends on step 1 and stages spec reconciliation.

**Step 1: F-7.3.28, the cached stream dies with its first request.** `PodExecutor.streamFor` (pkg/gateway/session/executor/pod.go) opens the cached Attach stream with the context of the first `Send` and caches it. `adapterclient.Attach` passes that context to the gRPC bidi stream and documents that cancelling it closes the stream. The REST paths pass `r.Context()`, and MCP `send_message` and `delegate_task` pass the tools/call request context. The stream therefore ends when the first request returns. Nothing evicts the dead stream, so every later message on a pod-backed multi-turn session fails until the session is released. REST answers 500 `EXECUTOR_FAILURE`, MCP `send_message` returns an error, and a `delegate_task` follow-up fails. The single-shot OpenAI Chat and Open Responses translators bind one session per request and release it on every exit, so F-7.3.28 does not affect them. They are in scope only for abandon-on-disconnect and error classification.

The step-1 design must settle these points:

- **Stream lifetime.** One candidate opens the cached stream on a session-scoped context (`context.WithCancel(context.WithoutCancel(ctx))`), stores the cancel, and cancels it in `EvictStream` and `Release`. The scratchpad verification sketches this fix. A second candidate opens one Attach per `Send` on the request context and caches nothing. The spec places no limit on concurrent CH-ATTACH streams from one holding replica, and the adapter subscribes each Attach to the runtime output fan-out afresh. That candidate loses heartbeat coverage between turns and drops runtime frames emitted between turns, and §29 describes CH-ATTACH as the session's pod control stream, open in the running states. The proposal names both candidates and records the choice and the reason.
- **Request abandonment.** With a detached stream, `Send` no longer observes the request context, so a client disconnect mid-turn no longer abandons the wait. `Send` must honor the request context while waiting without ending the stream, for example through a per-stream reader that delivers frames over a channel.
- **Turn correlation.** `readAttachResponse` returns the first `response` frame it reads and never checks it against the message envelope ID. Once `Send` can abandon a wait without ending the stream, the abandoned turn's late response stays on the stream, and the next `Send` would take it as its own reply. The design must correlate replies to messages or drain stale frames.
- **Error classification.** A typed stream-ended error separates a cancel the gateway caused (`EvictStream`, `Release`, or a request abandon) from an adapter or runtime failure. Today `EvictStream` only calls `CloseSend`, and the adapter keeps streaming after a half-close. Once the stored cancel exists, eviction and release end the stream with `codes.Canceled`, and without classification those cancels would be reported as failures.
- **Eviction on error.** A stream that ends with an error is evicted from the cache.

Step 1 must land before step 2. With failure reporting in place and the stream still bound to the first request, every second message would be reported as a failure and would move the session to `resume_pending`. Step 1 has no spec dependency and can land as a direct code change ahead of the rest of this proposal if the human approver prefers.

**Step 2: F-7.3.27, the gateway does not react to a failed stream.** When an Attach stream ends with an error, including the adapter's heartbeat-escalation `DeadlineExceeded`, the gateway does nothing. `ReportSessionFailure` (pkg/gateway/sessionserver/failure.go) and its §7.3 classifier, built under the closed F-7.3.4, have no production caller. `transitionToResumePending` and `transitionToAwaitingClientAction` write the row without releasing the old binding. The resume rebind calls `podRegistry.Put` over any existing entry without `Shutdown` or `EvictStream`. Because `streamFor` consults its stream cache before the registry, a session that resumes on the same replica would keep the stale cached stream. The session keeps its slot, runtime context, workspace, and claim until a terminate or the watchdog fires (`maxSessionAgeSeconds`, default 7200 s). On a `maxConcurrentSessions: 1` recycling pool, the watchdog's `expired` disposition takes the recycle branch and reuses a pod whose runtime hung, which conflicts with §6.2 "Pod crash during an active session". Under proposal 0090, no `session_end` is written until that release.

The step-2 design must settle these points:

- **Detection on the stream.** The adapter's heartbeat monitor runs only while an Attach stream is open and is bound to that stream's context. With a detached stream from step 1, heartbeats run between turns, so a heartbeat escalation or an adapter error can end the stream while no `Send` is in flight. Calling `ReportSessionFailure` from the message paths alone, as the BUILD-GAPS resolution suggests, misses those failures. The per-stream reader (or an equivalent stream watcher) must observe the stream end and own failure reporting. Message paths still surface the error to the caller.
- **Release on the failure edges.** The old binding is released with the retire (`failed`) disposition on the `resume_pending` and `awaiting_client_action` edges, and any prior binding is released before a resume rebinds. A stream failure is always observed on the replica that holds CH-ATTACH, so the release can run locally at the moment of failure.
- **Concurrent pools.** The concurrent-pool release path (`Binder.ReleaseSlot`) takes no disposition. It can recycle at occupancy zero and has no way to retire a pod for a failed slot. Retiring a concurrent pod needs new plumbing or relies on the §5.2 whole-pod replacement trigger.
- **Coexistence with proposal 0060.** The coordination Sweeper evicts the binding and the cached stream and releases the lease for re-adoption only when the held gRPC channel itself reports not alive. A stream-level error on a live channel, such as the heartbeat `DeadlineExceeded`, falls outside that path and is the case this step handles. The two paths must not confuse each other, and `EvictStream` is the shared seam.
- **Call sites and pool variants.** The test matrix covers REST direct and resume-and-deliver, MCP `send_message`, `delegate_task` follow-ups, and the translators, on session and task pods and on concurrent and recycling pools.

**Spec reconciliation staged by step 2.** The spec does not agree with itself on the stream-failure outcome, so this proposal needs more spec work than the two decisions the remediation plan names.

- (a) **Exhaustion outcome and classification.** The §28.8 CH-ATTACH failure row and §7.3 "Resume flow after pod failure" step 4 send exhausted retries to `awaiting_client_action`. The §7.2 transition table has no `running → awaiting_client_action` edge and lists `running → failed` for "runtime crash, unrecoverable error, retries exhausted". §6.2 "Retry exhaustion" also says `failed`. §7.3 lists `runtime_crash` as retryable while §7.2 maps a running-state runtime crash to `failed`, and §15.4.3 says a missed heartbeat ack "ends the session". The code follows §7.3 and §28.8 (`legalReportTransition` admits `running → awaiting_client_action`). The proposal reconciles these statements and decides whether a heartbeat-escalation stream end is classified as `runtime_crash`.
- (b) **Hung runtime on a concurrent pod.** §5.2 says slots fail independently, and §4.7.10 keeps one runtime process for the pod's life, so a hung runtime affects every slot. Implemented proposal 0079 already recorded the intended behavior as an accepted edge case: the session fails, a `maxConcurrentSessions: 1` pool retires the pod, and a concurrent pool counts the failed slot toward the §5.2 whole-pod replacement trigger (`ceil(maxConcurrentSessions / 2)` failed or leaked slots) and reuses the pod with the hung runtime until the trigger fires. The proposal adopts that decision or reverses it explicitly, citing 0079 and the §5.2 Slot retry policy. If the question widens into a general runtime-lifetime reconciliation, it moves to its own spec proposal and 0091 adopts an interim rule.

**Deferred and out of scope.** Each item below is named so reviewers do not reopen it.

- Same-pod Attach redial. The §28.8 CH-ATTACH row states that the spec is silent on it. The adapter keeps no hung marker and enforces no single-consumer lock, so a redial against a hung runtime would be admitted and would start a fresh heartbeat monitor, and an unbounded redial policy could loop. The proposal either states no redial or bounds it.
- Automatic replacement-pod re-dispatch. The §28.8 row and §6.2 say the session is re-attached on a replacement pod, but no gateway code drives `resume_pending` forward. The watchdog moves it to `awaiting_client_action` when `maxResumeWindowSeconds` elapses. Without re-dispatch, a session that this proposal moves to `resume_pending` waits out that window or a client resume. The proposal states this behavior and names the owner of the remaining gap. Re-dispatch is in scope only if it is needed to send `Shutdown`.
- Cross-replica release. A release on a replica that does not hold the in-memory binding is a no-op. This defect affects every watchdog and terminate release and is not specific to stream failure. It is filed as a separate finding.

**Scope (owner decision, 2026-10-06).** This proposal does not change `REG-COORDLEASE` ownership. On a stream-failure edge the coordinating replica releases the session's pod binding and keeps the coordination lease, which it continues to renew in `resume_pending` and `awaiting_client_action`, as §29.3, §29.6, §7.2, and §7.3 already state and as the shipped Sweeper already does. A `POST /v1/sessions/{id}/resume` whose bind meets that lease answers the retryable `RESUME_FAILED` and holds the row in `awaiting_client_action`, rather than demoting it to `failed`. When and by whom the lease is acquired, adopted, or released in the recovering states, and the §29.3 off-holder forward for the resume route, belong to a separate proposal; RECORDS-1 files them.

## Who observes it

- Every multi-turn client of a pod-backed session observes F-7.3.28 on the production deployment path, because `PodExecutor` is the executor whenever the gateway runs against an agent namespace. The echo and subprocess executors are developer-loop alternatives.
- REST clients receive HTTP 500 `EXECUTOR_FAILURE` on the second and later direct deliveries. On the running path the message is buffered to the inbox and the session stays `running`.
- MCP `send_message` callers and `delegate_task` callers that send a follow-up receive errors on every message after the first.
- Operators observe F-7.3.27 once F-7.3.28 is fixed. A session whose runtime hangs holds its slot, workspace, and claim for up to `maxSessionAgeSeconds` (default 7200 s), and a recycling pool can return a pod with a hung runtime to service.
- Existing tests miss F-7.3.28 because they use contexts that are never cancelled (`context.Background`, or `httptest.NewRequest` served through `ServeHTTP`), and the tier-5 and tier-6 scenarios send one message per session. A fix needs tier-4 and tier-5 tests that send two or more messages per session.

## What breaks if nothing changes

- Every pod-backed session fails on its second message. This blocks multi-turn conversation, `send_message`, and delegation follow-ups on any real deployment.
- Fixing F-7.3.28 alone makes F-7.3.27 the main way a session fails. A hung runtime is never classified, the session never reaches `resume_pending`, `awaiting_client_action`, or `failed`, its resources stay held until the watchdog, and `session_end` is not written until that late release.
- On a `maxConcurrentSessions: 1` recycling pool, the late release recycles a pod whose runtime hung, which the §6.2 drain rule forbids.
- Adding failure reporting without the step-1 fix would move every multi-turn session to `resume_pending` on its second message.

## Findings this unblocks

- BUILD-GAPS F-7.3.28 and F-7.3.27.
- The "the session fails" behavior that proposal 0079 recorded for a missed heartbeat, which depends on the F-7.3.27 wiring.

## Prior art considered

- No proposal under proposals/ stages this change. Implemented proposal 0090 lists the stream-failure fix as a non-goal and a dependency on a separate proposal. The remediation plan schedules this proposal as an unwritten item after 0090.
- No commit has changed the Attach-open context in pkg/gateway/session/executor/pod.go. The `context.WithoutCancel` uses in the tree cover release and cleanup only (the translators and the slot binder).
- Proposal 0060 (implemented) added `EvictStream` and the coordination Sweeper's dead-connection path. It covers a gRPC channel that reports not alive, and it evicts, releases the lease, and leaves the session for re-adoption. It does not cover a stream-level error on a live channel, and it neither sends `Shutdown`, releases the slot, nor calls `ReportSessionFailure`. This proposal reuses `EvictStream` and must coexist with that path.
- F-7.3.4 (closed) built `ReportSessionFailure` with the §7.3 classifier and noted that its detector is tracked separately. No finding tracked that detector until F-7.3.27, and proposal 0081 recorded the same missing caller. The classification and transition machinery exists, so step 2 is mostly wiring callers.
- Proposal 0079 (implemented) recorded the missed-heartbeat edge case in its spec changes: the session fails, a `maxConcurrentSessions: 1` pool retires the pod, and a concurrent pool counts the failed slot toward the §5.2 whole-pod replacement trigger. Decision (b) starts from that recorded decision.
- The orphan-session reconciler (reason `orphan_pod_terminated`) covers a terminated pod only. It does not cover a hung runtime on a live pod.
- No other open BUILD-GAPS or TEST-GAPS finding overlaps F-7.3.27 or F-7.3.28.

## Validated premises

Six lenses validated the original statement independently. The evidence and impact lenses returned "stands". The premise, prior-art, scope, and alternatives lenses returned "revise". The consolidated verdict is that the problem is viable and the statement above is revised.

- **P1: the cached stream is opened on the first request's context and dies with it.** Confirmed by the premise, evidence, prior-art, impact, and alternatives lenses. The fix depends on this premise. `PodExecutor` is the only production Attach consumer.
- **P2: every multi-turn caller passes a request-scoped context.** Confirmed for REST direct delivery, resume-and-deliver, MCP `send_message`, and `delegate_task`. Refuted for the translators (premise lens): OpenAI Chat and Open Responses bind a single-shot session per request and release it on every exit, so F-7.3.28 does not affect them. They stay in scope only for abandon-on-disconnect and error classification.
- **P3: a dead or errored stream is never evicted.** Confirmed (premise, evidence, and alternatives lenses). `EvictStream` runs only from `Release` and the coordination dead-connection seam.
- **P4: `ReportSessionFailure` has no production caller, and the failure transitions release nothing.** Confirmed (premise, evidence, prior-art, and alternatives lenses). The premise lens added that a same-replica resume keeps serving the stale cached stream because `streamFor` consults the cache before the registry.
- **P5: the adapter's heartbeat escalation ends the stream with `DeadlineExceeded`.** Confirmed (premise and evidence lenses), enabled by default at 30 s and 10 s. The evidence lens noted the status is returned in attach.go, with heartbeat.go holding the escalation helper. The premise lens added that the adapter keeps no hung marker or consumer lock, so an unbounded same-pod redial could loop.
- **Implicit premise: failure detection can live on the `Send` or message path.** Refuted (premise lens). After step 1, heartbeats run between turns and a stream can end while no `Send` is in flight. The BUILD-GAPS suggestion to call `ReportSessionFailure` from the message paths alone would miss those failures. Detection belongs to the per-stream reader or watcher. The fix depends on this premise, and the statement now assigns failure reporting to the stream reader.
- **P6: the spec already requires the fix with no spec change except two named decisions.** Refuted (premise lens; verified in §7.2, §7.3, §6.2, §15.4.3, and §28.8). The spec disagrees on whether exhausted retries and a running-state runtime crash go to `awaiting_client_action` or `failed`. The fix depends on this premise, and decision (a) now includes reconciling these statements. The no-spec-change claim survives for step 1 (scope and alternatives lenses).
- **P7: recycling release and cross-replica release behave as stated.** Confirmed (premise and evidence lenses): only `failed` retires a recycling pod, and a release on a non-holding replica returns nil. The premise lens added that `ReleaseSlot` carries no disposition and cannot retire a concurrent pod. The scope lens showed cross-replica release is a general release-path defect that affects every watchdog and terminate release; it is cut from this proposal and filed separately.
- **P8: decision (b) is open.** Partly refuted (prior-art lens; verified in the 0079 spec changes and the §5.2 Slot retry policy). Implemented proposal 0079 already recorded the outcome as an accepted edge case. This premise determines how decision (b) is staged, and the proposal adopts or explicitly reverses 0079. The scope lens recommends moving any wider runtime-lifetime reconciliation to its own proposal.
- **P9: the spec is silent on same-pod redial.** Confirmed (premise, evidence, and prior-art lenses). The row is in §28.8 Failure and degradation matrix; the original §28.6 citation was wrong (evidence lens). Redial is deferred with a stated policy.
- **P10: nothing writes `session_end` on a stream error.** Confirmed (premise lens). `Shutdown` writes it through `writeSessionEnd`, so `session_end` waits for the eventual release.
- **P11: classification must separate gateway-caused cancels from failures.** Confirmed (premise and scope lenses). Today `CloseSend` does not end the adapter-side stream. A stored cancel turns eviction and release into stream-ending events that read as `codes.Canceled`.
- **P12: F-7.3.28 and F-7.3.27 belong in one proposal.** Revised (scope and alternatives lenses). F-7.3.28 is a prerequisite with no spec dependency and must land first. The scope lens keeps both in one proposal as ordered steps; the alternatives lens prefers landing F-7.3.28 directly outside the proposal. The statement keeps the ordered steps and records direct landing as an option for the approver.
- **P13: the detached-context sketch is the fix.** Revised (alternatives lens). One Attach per `Send` on the request context is a smaller alternative the spec admits. The detached design also brings a turn-correlation hazard that the original statement did not name (verified: the reply's envelope ID is never checked). The proposal names both candidates and records the choice.
- **P14: the defect is reachable and observed.** Confirmed (impact lens). `PodExecutor` is wired on the production path, every second message fails, and existing tests miss it because their contexts are never cancelled.
- **P15: replacement-pod re-dispatch is out of scope.** Confirmed with an added obligation (scope lens). No gateway code drives `resume_pending` forward except the watchdog timeout, so the proposal states the resulting wait-out behavior and names an owner for the gap.
- **Section citations.** The evidence lens found two drifted citations: the CH-ATTACH failure row is in §28.8 rather than §28.6, and the 10-second ack timing is in §15.4.3 rather than §15.4.1. Both are corrected above.
