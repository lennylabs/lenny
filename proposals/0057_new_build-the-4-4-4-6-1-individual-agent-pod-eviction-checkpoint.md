# Proposal: Build the §4.4/§4.6.1 individual agent-pod eviction-checkpoint trigger with a best-effort eviction-snapshot fallback (C-22 culminating change, folding prereq 4)

- **Status:** Verified (2026-07-22). Converged after 5 adversarial review rounds (5 findings fixed); awaiting sign-off.
- **Date:** 2026-07-22.
- **Scope:** A code change that builds the §4.6.1 coordinator-direct eviction-checkpoint route for an individual agent pod (the C-22 culminating change, finding T-4.4.14), plus the coupled spec edits it requires. The adapter, on kubelet-driven pod termination, emits a new `AdapterEvicting` adapter-to-gateway control event; the gateway's session-coordination-lease holder drives the existing `Checkpointer.CheckpointWithTrigger(..., TriggerEviction)` under its held lease. To survive the default sidecar model, where the third-party runtime container is SIGTERMed at `t=0` with no preStop while the adapter's SIGTERM is deferred behind its own preStop, the eviction path takes a best-effort workspace snapshot from the still-mounted `/workspace` emptyDir rather than aborting to the minimal-state fallback when the cooperative quiesce handshake cannot complete. The change stages spec edits in §4.4, §4.6.1, and the §4.7 control-event table, code in `cmd/lenny-adapter`, `pkg/adapter`, and `pkg/gateway`, and tests across tiers 1, 3, 4, 5, 7a, and 8. It reuses the §4.4 eviction retry budget and the §16.1 `lenny_checkpoint_duration_seconds{trigger=eviction}` label through the existing `CheckpointWithTrigger` driver rather than duplicating any checkpoint-driver code. It builds no forced-takeover primitive on the coordination lease and no gateway-side agent-pod informer.

This document stages the proposed spec, code, and test changes. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off.

## 1. Problem

The §4.6.1 coordinator-direct eviction route is described in spec (`spec/04_system-components.md:489`, landed by prereq 2 / proposal 0052) but no code drives it, and the mechanism it needs to survive the default sidecar deployment model does not exist. Four facts define the build.

**1. No individual agent-pod eviction fires a checkpoint.** `checkpoint.TriggerEviction` is driven only on the gateway pod's own §10.1 preStop barrier fan-out (`pkg/gateway/coordination/barrier/barrier.go:228`, reached only from the gateway preStop handler), never on an individual agent-pod eviction. The agent-pod preStop `runPreStop` (`cmd/lenny-adapter/prestop.go`) SIGTERMs the local adapter and polls for its exit; the adapter SIGTERM handler (`cmd/lenny-adapter/main.go:411-425`) runs `ShutdownDemoteSDK`, `lifecycle.Close()`, and `srv.GracefulStop()` and emits no eviction signal to any gateway replica. The `Checkpoint` RPC is gateway-driven, so the pod cannot open it itself (`spec/04_system-components.md:489`). This is the C-22 eviction trigger, finding T-4.4.14.

**2. Runtime-container quiescence race in the default sidecar model.** In the default sidecar model the third-party `runtime` container carries no `Lifecycle`/preStop; only the adapter container carries the preStop drain hook. `RestartPolicy` is `Never` with no native-sidecar `InitContainer` ordering, so on kubelet termination the hookless runtime is SIGTERMed at `t=0` while the adapter's SIGTERM is deferred behind its preStop. The Full-level eviction checkpoint gates its archive on the live-runtime cooperative quiesce handshake `s.Lifecycle.RequestCheckpoint(...)` (`pkg/adapter/checkpoint.go:158-160`), which returns `codes.Internal "checkpoint quiesce handshake"` before `streamChunks`/`ArchiveTree` when the runtime's lifecycle connection has dropped. No pre-SIGTERM quiesce frame travels the kubelet path (`drainViaLifecycle`/`Terminate` fire only from the gateway `Shutdown` RPC handler; `SignalDeadlineApproaching` fires only from the `SignalDeadline` RPC), and `shareProcessNamespace` is prohibited (`spec/13_security-model.md` §13.1, `spec/04_system-components.md:243`). A SIGTERM-honoring runtime therefore exits before the eviction `checkpoint_request` reaches it, the handshake fails, and the current fail-closed at `checkpoint.go:158-160` drops the session to the minimal-state fallback (`resumeMode: conversation_only`, `workspaceLost: true`, `spec/04_system-components.md:264`), losing the live-workspace emptyDir.

The workspace is a separate pod-scoped `emptyDir` mounted `/workspace/` into both containers (`spec/04_system-components.md:865` deployment-model bullet; podspec renders it read-write into the adapter container). Kubernetes clears an `emptyDir` only on pod removal, not on a single container's exit, so after the runtime container exits under SIGTERM the still-alive adapter container retains full read access to `/workspace` through the grace window. The adapter already archives the checkpoint from its own on-disk mount (`workspace.ArchiveTree`, `pkg/adapter/checkpoint.go:201`), rather than by streaming from the runtime process. A runtime that has exited is no longer writing to the workspace and is therefore already quiesced; the cooperative handshake adds only tool-call consistency, which the spec already relaxes for eviction checkpoints and for the SIGSTOP eviction path (`spec/04_system-components.md:242-243`).

**3. The deferred 0052 coordinator decisions.** Proposal 0052's sign-off resolved coordinator-direct as the seam and deferred the within-window forced takeover and the forward-to-holder transport to this proposal.

**4. The §4.4 doc-nit.** `spec/04_system-components.md:264` and `:278` justify the eviction retry budget with `terminationGracePeriodSeconds (240s at Tier 1/2, 300s at Tier 3)`, and `spec/17_deployment-topology.md:971` labels that row `terminationGracePeriodSeconds (gateway pod)`. The eviction-checkpoint bullet at `:264` is titled "Eviction checkpoints (preStop hook)" and justifies its budget with "(a) the pod is terminating regardless — there is no agent to resume" and a resume-on-fresh-pod fallback (`resumeMode: conversation_only`, `workspaceLost: true`), so it documents the agent-pod eviction path this proposal builds, rather than the gateway-drain barrier path (`barrier.go:228`), during which the agent pod keeps running and its session continues after coordinator handoff. The agent pod's grace default is 120s (`spec/04_system-components.md:489`). Citing the gateway pod's 240/300s grace on the agent-pod eviction bullet is therefore the doc-nit: the bound there is the agent pod's 120s grace. The 30s MinIO plus 60s Postgres budgets (90s worst case) fit within 120s, so the numbers are not unsafe, but the grace attribution at `:264`/`:278` is wrong and SPEC-3 corrects it.

Prereqs 1 (0050, slot-aware checkpointing), 2 (0052, coordinator-direct route text at `spec/04_system-components.md:489`), and 3 (0056, admission grace floor) are landed and consumed unchanged. The earlier seed hint that `triggerForSource` at `checkpointer.go:366` must be reconciled is obsolete: `git grep triggerForSource|snapshotWithTrigger` returns zero hits under `pkg/` and `cmd/`. The switch was already collapsed and the trigger threads as a direct parameter through `Checkpointer.CheckpointWithTrigger` (`pkg/gateway/checkpoint/checkpointer/checkpointer.go:375`), so the individual-eviction path need only call it with `TriggerEviction`, and finding T-4.4.20's code half is already resolved.

## 2. Decisions

- **Coordinator-direct is the built seam, per 0052's sign-off.** The adapter, on kubelet-driven pod termination, emits a new `AdapterEvicting` adapter-to-gateway control event on the per-pod control channel; the session-coordination-lease holder ([§10.1](../spec/10_gateway-internals.md)) drives the existing `Checkpointer.CheckpointWithTrigger(tenantID, sessionID, TriggerEviction)` (`checkpointer.go:375`) under its held lease. No gateway-side agent-pod informer is built (that seam was surfaced-and-deferred by 0052 and would need dedup and RBAC across every replica).
- **The gateway-side control-stream consumer does not exist yet and is built here.** The `LifecycleChannel` control stream is served only on the adapter side (`pkg/adapter/controlchannel.go:90`); `AdapterTerminating` and `FINAL_USAGE_REPORT` are emit-only (`controlchannel.go:34,39`), and no gateway production code opens the client bidi stream or reads `LifecycleChannelResponse`. The earlier framing that the transport "already carries `AdapterTerminating`" to a gateway consumer is corrected: the gateway consumer (client stream open, receive loop, reconnect, session and slot routing) is new code this proposal builds.
- **A new §4.7 control event is warranted rather than overloading `AdapterTerminating`.** `AdapterTerminating` is a terminal notification (`spec/04_system-components.md:688`, reason `coordinator_lost`) that transitions the session immediately without waiting for the orphan reconciler; its semantics are wrong for "drive an eviction checkpoint, then terminate". `AdapterEvicting` requests a checkpoint drive and survives the minimal-surface test because no existing control event carries that request.
- **The eviction drive lives in the adapter SIGTERM handler rather than a new local RPC.** On the kubelet path the adapter-container preStop runs before the adapter's SIGTERM, so the SIGTERM handler is where the adapter is still fully serving and can emit the eviction event, keep the gRPC server accepting the coordinator's `Checkpoint` RPC (defer `GracefulStop`), await completion of the eviction checkpoint(s) for its live bound sessions under a deadline, then tear down. When the adapter has no live bound session, it emits nothing and exits as today. The adapter observes checkpoint completion locally because it serves the `Checkpoint` RPC, so no gateway-to-adapter completion-ack frame is added.
- **The runtime-container quiescence race is resolved by a best-effort eviction snapshot rather than by keeping the runtime alive.** When this pod is itself terminating (the adapter's own SIGTERM/eviction handler has engaged, tracked by an in-process `evicting` flag the handler sets before it emits `AdapterEvicting`) and the cooperative `checkpoint_request`/`checkpoint_ready` handshake cannot complete because the runtime lifecycle connection has already dropped, the adapter archives the still-mounted `/workspace` emptyDir directly and records it as an ordinary workspace checkpoint, rather than returning `codes.Internal` and aborting to the minimal-state fallback. The downgrade is gated on the adapter's own termination state rather than on the `TriggerEviction` trigger value, because `TriggerEviction` is shared with the §10.1 gateway-drain barrier path (`barrier.go:228`), during which the agent pod keeps running and its session continues after coordinator handoff. Gating on the trigger alone would let a transient lifecycle-connection drop during a barrier fan-out silently downgrade a still-running session's checkpoint to best-effort. The adapter that serves the `Checkpoint` RPC derives the trigger solely from `CheckpointStart` (`checkpoint.go:128`) and cannot otherwise tell the two paths apart, so the local `evicting` flag is the authoritative "this pod is terminating" signal. The restored snapshot resumes as `resumeMode: full` with `workspaceLost: false`, indistinguishable at the wire from a cooperatively-quiesced checkpoint. No new per-checkpoint or per-resume consistency field is added: the adapter-to-gateway `Checkpoint` stream (`CheckpointStart`/`CheckpointSummary`, `schemas/lenny-adapter.proto:1101,1187`) carries no `consistency` field, neither the `checkpoint_manifest` (`migrations/0178_checkpoint_manifest.up.sql:30`) nor the `session_checkpoints` record persists one, and the §7.2 `session.resumed` event (`spec/07_session-lifecycle.md:138`) enumerates `resumeMode` as `full`, `conversation_only`, `partial_workspace`, or `coordinator_handoff` with a boolean `workspaceLost` and no consistency field. Surfacing a distinct best-effort marker would require a new proto field, a migration, a §7.2/§15 event-schema field, and SDK plus `docs/client-guide/wire-format.md` mirroring, which the minimal-surface principle rejects because the spec's existing best-effort model already relaxes tool-call consistency without a per-resume marker (`spec/04_system-components.md:242-243`). The eviction path carries the tool-call-consistency caveat the spec already documents. This resolves the same failure the runtime-hold would (total workspace loss) at a single code site, with no init container, no shared binary copy, no unix-socket hold, and no third-party runtime image change. The rejected runtime-hold and its own rejected sub-alternatives are recorded in Non-goals.
- **The embedded deployment model is unchanged.** It runs a single first-party container that carries the preStop and links the adapter, with no separate hookless runtime, so the ordering race does not arise. The embedded model reaches the same SIGTERM handler and benefits from the same eviction drive; the best-effort snapshot fallback is a no-op there because the embedded runtime's lifecycle connection does not drop out from under the adapter.
- **The unreachable-coordinator and any cross-replica residual is accepted; no forced-takeover primitive is built.** Per 0052's Non-goals and sign-off, a still-live coordination lease cannot be acquired by a non-holder without a forced-acquisition primitive the leasestore holder invariant forbids (`pkg/.../leasestore.go` holder invariant; `ErrHeld`). A coordinator unreachable within the grace window is recovered only by the existing §10.1 TTL-driven handoff (default 4×15s, which may outlast the window), and that residual session drops to the §4.4 minimal-state fallback. This preserves the leasestore holder invariant and the `shareProcessNamespace` prohibition unchanged.
- **The gateway-drain barrier path is reused as the driver rather than duplicated or modified.** Both the barrier path (`barrier.go:228`) and the new individual-eviction consumer call the same `Checkpointer.CheckpointWithTrigger(..., TriggerEviction)`, so the §16.1 `lenny_checkpoint_duration_seconds{trigger=eviction}` label and the §4.4 eviction retry budget apply on this path with no new checkpoint-driver code. The shared trigger is why the best-effort downgrade (CODE-2) keys off the adapter's local `evicting` flag rather than the trigger value: the barrier path drives `TriggerEviction` against a running agent pod whose adapter has not engaged its SIGTERM handler, so that pod's `evicting` flag stays false and its checkpoint keeps failing closed on a dropped handshake.
- **T-4.4.20 is closed as already-resolved-in-code rather than re-reconciled.** The stale `triggerForSource`/`snapshotWithTrigger` comment no longer exists under `pkg/` or `cmd/` (verified by `git grep`, zero hits); the individual-eviction path reaching `CheckpointWithTrigger` with `TriggerEviction` is what a unit assertion pins, and the `TEST-GAPS.md` entry that still cites `checkpointer.go:339-352` is updated to reflect the collapsed direct-parameter mapping.

## 3. The coordinator-direct eviction route and the control-stream consumer

The route has three legs, and only the driver leg already exists in code.

- **Adapter emit leg (new).** On kubelet-driven termination, the adapter's SIGTERM handler enumerates its live bound sessions and emits one `AdapterEvicting` event per session (with `slot_id` on pods where `maxConcurrentSessions > 1`) on the per-pod control channel, then keeps serving until each emitted session's coordinator-driven `Checkpoint` RPC completes on this adapter or a deadline lapses.
- **Gateway consume leg (new).** The gateway opens the `LifecycleChannel` client bidi stream once per pod, runs a receive loop that decodes each `LifecycleChannelResponse.envelope_json` control event, and on `AdapterEvicting` routes to the driver for the named `session_id`/`slot_id`. This consumer is new: no gateway production code reads the control stream today.
- **Driver leg (reused).** `Checkpointer.CheckpointWithTrigger(ctx, tenantID, sessionID, TriggerEviction)` (`checkpointer.go:375`) drives the checkpoint under the held lease. It drives only when the local `Registry` holds the session binding (`checkpointer.go:424`), returning `ErrNoBinding` otherwise.

The routing invariant this design depends on is that the replica whose control-stream consumer receives `AdapterEvicting` is the session-coordination-lease holder for that session, so `CheckpointWithTrigger` finds the binding rather than returning `ErrNoBinding`. That invariant is unverified in the current code because no control-stream client exists. The implementation must either prove that the control-channel-holding replica is always the binding holder, or add forwarding to the holder, before dispatching to the driver. A non-holder that receives `AdapterEvicting` and returns `ErrNoBinding` would silently drive no checkpoint, which is the workspace-loss failure C-22 exists to prevent. This is raised as an open decision (§10) and is the within-window transport decision 0052 deferred to this proposal.

## 4. The best-effort eviction snapshot

The Full-level eviction checkpoint today fails closed at `pkg/adapter/checkpoint.go:158-160`: when `s.Lifecycle.RequestCheckpoint` errors because the runtime lifecycle connection has dropped, the RPC returns `codes.Internal` before any chunk is archived, and the session drops to the minimal-state fallback. On the kubelet eviction path this is the common case for a SIGTERM-honoring third-party runtime, because the runtime container exits at `t=0` before the eviction `checkpoint_request` reaches it.

The change makes a checkpoint taken while this pod is itself terminating tolerate the dropped handshake. When `RequestCheckpoint` fails because the lifecycle connection is closed or dropped, and the adapter's own SIGTERM/eviction handler has engaged (the in-process `evicting` flag CODE-1 sets before emitting `AdapterEvicting`), the adapter proceeds to `streamChunks` against the still-mounted `/workspace` emptyDir and records the resulting checkpoint as an ordinary workspace checkpoint, rather than returning `codes.Internal`. The workspace bytes are readable because the adapter container mounts `/workspace` read-write and defers its own SIGTERM behind its preStop, and the exited runtime is no longer writing. The spec already sanctions best-effort snapshots for runtimes without a lifecycle channel (`spec/04_system-components.md:242`) and already accepts mid-tool-call inconsistency on the SIGSTOP eviction path (`spec/04_system-components.md:243`), so the eviction path resuming from a best-effort snapshot is a consistency downgrade the spec's model already contemplates, and it is strictly better than the total workspace loss the current fail-closed produces. On resume the workspace is restored and the client observes `resumeMode: full` with `workspaceLost: false`. The eviction path's tool-call-consistency relaxation is not surfaced as a separate field on `session.resumed`, which matches how the spec handles Basic/Standard best-effort checkpoints: they are tagged by runtime level rather than by a per-resume marker, and no field on the adapter-to-gateway `Checkpoint` stream, the checkpoint records, or the `session.resumed` event carries one today.

Every checkpoint of a pod that is not itself terminating keeps the fail-closed handshake unchanged. A periodic or pre-scale-down checkpoint on a live session must not silently downgrade to best-effort, because the runtime is present to quiesce cooperatively. The §10.1 gateway-drain barrier checkpoint (`barrier.go:228`) also carries `TriggerEviction`, yet it runs against a still-running agent pod whose adapter has not engaged its SIGTERM handler, so its `evicting` flag is false and a transient lifecycle-connection drop during the barrier fan-out keeps returning `codes.Internal` rather than downgrading. The downgrade is scoped to a pod that is terminating regardless (its own `evicting` flag set), where there is no agent to resume in an inconsistent state.

## 6. Proposed changes

### SPEC-1. Add the `AdapterEvicting` adapter-to-gateway control event to §4.7

**Target:** `spec/04_system-components.md`, the "Adapter → Gateway events" table (`:679-689`) and the surrounding control-event prose.

**Rationale:** The landed §4.6.1 route (`:489`) says the preStop signals its coordinating replica "over the same channel that carries `AdapterTerminating`", but `AdapterTerminating` (`:688`) is a terminal notification that transitions the session immediately without a checkpoint. The adapter-to-gateway control-event enum (`pkg/adapter/controlchannel.go:18-45`) carries `RATE_LIMITED`, `AUTH_EXPIRED`, `PROVIDER_UNAVAILABLE`, `LEASE_REJECTED`, `AdapterTerminating`, `FINAL_USAGE_REPORT`, and `CheckpointBarrierAck`, and no eviction or checkpoint-request event. A new event is the minimal surface that carries "drive an eviction checkpoint, then terminate" without corrupting `AdapterTerminating`'s terminal semantics.

**Change (staged spec text).** Add a table row after the `AdapterTerminating` row (`:688`):

```markdown
| `AdapterEvicting`      | Adapter's request that its coordinating replica drive an eviction checkpoint before pod termination (kubelet-driven node drain, Eviction API, cluster upgrade, or direct delete). Fields: `session_id`, `slot_id` (present only on pods with `maxConcurrentSessions > 1`). The coordinating replica (the session-coordination-lease holder, [§10.1](10_gateway-internals.md#101-horizontal-scaling)) drives the existing `Checkpoint` RPC with the `TriggerEviction` trigger under its held lease. This event is advisory-then-terminal: after the driven checkpoint settles or the deadline lapses, the pod terminates regardless. Distinct from `AdapterTerminating`, which transitions the session terminal without a checkpoint. See [Section 4.6.1](#461-warm-pool-controller-pod-lifecycle). |
```

Add one sentence to the control-event prose introducing the event, cross-referencing §4.6.1 and §4.4, and stating that the adapter keeps serving the coordinator's `Checkpoint` RPC until the driven checkpoint settles or the deadline lapses.

### SPEC-2. Describe the best-effort eviction snapshot in §4.4 and the kubelet-path eviction drive in §4.6.1

**Target:** `spec/04_system-components.md` §4.4 (the Full-level cooperative-handshake bullet near `:241` and the eviction-checkpoint bullet near `:264`), and §4.6.1 "Disruption protection for agent pods" (`:489`).

**Rationale:** The eviction checkpoint requires either a live runtime to answer `checkpoint_request`/`checkpoint_ready` (`checkpoint.go:158-160`) or a fallback for when the runtime has already exited. In the default sidecar model the hookless runtime container is SIGTERMed at `t=0` on kubelet termination and no pre-SIGTERM quiesce frame reaches it. Keeping the third-party runtime alive through the eviction window (a preStop hold with an init-container binary copy and a unix-socket signal) is the largest surface for this failure; the workspace `emptyDir` survives the runtime's exit and is readable by the still-alive adapter container, so a best-effort snapshot resolves the same total-workspace-loss failure at a single code site without keeping the runtime alive. The spec must state that the eviction path takes a best-effort snapshot when the cooperative handshake cannot complete, and that the kubelet-path drive is coordinator-direct, without weakening the `shareProcessNamespace` prohibition (`:243`, §13.1).

**Change (staged spec text).** In the Full-level bullet near `:241`, after the cooperative-handshake sentence, add:

```markdown
When a checkpoint runs while **this agent pod is itself terminating** under the kubelet SIGTERM (the default sidecar model SIGTERMs the hookless runtime container at `t=0` while the adapter's own SIGTERM is deferred behind its preStop), and the cooperative `checkpoint_request`/`checkpoint_ready` handshake cannot complete because the runtime process has already terminated, the adapter captures a **best-effort** snapshot of the still-mounted `/workspace` `emptyDir` (readable by the adapter container, which defers its SIGTERM and retains the mount through the grace window) and records it as the session's workspace checkpoint, rather than aborting the checkpoint. The exited runtime is no longer writing to the workspace, so the snapshot is quiescent with respect to writes; it lacks only the tool-call-consistency guarantee the cooperative handshake provides, which eviction checkpoints already relax (see the SIGSTOP eviction path above). On resume the workspace is restored and the client observes `resumeMode: full` with `workspaceLost: false`; the eviction path's tool-call-consistency relaxation is inherent to eviction checkpoints and is not surfaced as a separate `session.resumed` field. This best-effort path applies only when the adapter's own pod is terminating; a checkpoint of a still-running pod keeps the cooperative handshake and fails closed on a dropped connection. This includes the gateway-drain barrier checkpoint, which also carries the `eviction` trigger but runs against a running agent pod whose session continues after coordinator handoff, and periodic and pre-scale-down checkpoints.
```

In the eviction-checkpoint bullet near `:264`, adjust the fallback description so the minimal-state fallback (`resumeMode: conversation_only`, `workspaceLost: true`) is reached only when the workspace snapshot itself cannot be persisted, rather than when the cooperative handshake could not complete. State that when a best-effort snapshot was taken on a terminating pod (the handshake was skipped because the runtime had already exited), the resume path restores the workspace from that snapshot and the session resumes as `resumeMode: full` with `workspaceLost: false`, without a separate consistency marker on `session.resumed`.

In §4.6.1 (`:489`), state that the individual agent-pod eviction drive is coordinator-direct: the adapter emits `AdapterEvicting` on the per-pod control channel, and the session-coordination-lease holder drives the `Checkpoint` RPC with `TriggerEviction` under its held lease. Keep the existing unreachable-coordinator TTL-handoff sentence unchanged.

### SPEC-3. Correct the agent-pod grace attribution on the §4.4 eviction-checkpoint budget and name the agent-pod bound in §4.6.1

**Target:** `spec/04_system-components.md` §4.4 eviction-checkpoint bullet (`:264`) and Postgres-fallback-retry paragraph (`:278`), plus §4.6.1 "Disruption protection for agent pods" (`:489`, folded into the SPEC-2 edit at the same anchor).

**Rationale:** The eviction-checkpoint bullet at §4.4:264 is titled "Eviction checkpoints (preStop hook)" and justifies its retry budget with "(a) the pod is terminating regardless — there is no agent to resume" and a resume-on-a-fresh-pod fallback (`resumeMode: conversation_only`, `workspaceLost: true`). A path where the pod is terminating with no agent to resume is the agent-pod eviction path, which is exactly the path C-22 builds. It is not the §10.1 gateway-drain barrier path (`barrier.go:228`), during which the draining gateway replica terminates while the agent pod keeps running and its session continues after coordinator handoff. The grace citation at §4.4:264/:278 therefore names the wrong pod: it cites the gateway pod's `terminationGracePeriodSeconds` (240s at Tier 1/2, 300s at Tier 3; labeled `terminationGracePeriodSeconds (gateway pod)` at `spec/17_deployment-topology.md:971`) on a bullet that describes the agent-pod eviction, whose grace default is 120s (`spec/04_system-components.md:489`). The correct fix is a substitution rather than an additive clause: correct the attribution at §4.4:264/:278 to the agent pod's 120s grace, cross-reference §17.8's gateway-pod row only for the distinct gateway-drain barrier path, and add the matching bound to §4.6.1. Verification confirmed the gap: `CheckpointStart`/`CheckpointSummary` carry no `consistency` field (`schemas/lenny-adapter.proto:1101,1187`), neither `checkpoint_manifest` (`migrations/0178_checkpoint_manifest.up.sql:30`) nor `session_checkpoints` has a `consistency` column, `pkg/checkpoint`'s `ConsistencyTag`/`ConsistencyBestEffort` have no production consumer, and the §7.2 `session.resumed` event (`spec/07_session-lifecycle.md:138`) enumerates `resumeMode` as `full`, `conversation_only`, `partial_workspace`, or `coordinator_handoff` with a boolean `workspaceLost` and no consistency field (mirrored at `docs/client-guide/wire-format.md:183`). A best-effort eviction snapshot that restores the workspace therefore resumes as `resumeMode: full` with `workspaceLost: false`, so the tag and marker language asserted a distinction no field defines. The finding's two options were adding the full plumbing (proto field, migration, gateway recording, a §7.2/§15 event field, and SDK plus client-doc mirroring) or dropping the marker language. The second option was taken: it is the choice consistent with the proposal's minimal-surface principle and with the spec's existing best-effort model, which tags Basic/Standard checkpoints by runtime level and relaxes tool-call consistency on the eviction and SIGSTOP paths without a per-resume marker (`spec/04_system-components.md:242-243`). The snapshot now persists as an ordinary workspace checkpoint that resumes as `resumeMode: full` with `workspaceLost: false`, the eviction path's tool-call-consistency relaxation is documented in §4.4 rather than surfaced per-checkpoint or per-resume, and the same predicate is propagated across the Decisions bullet, §4, the §5 edge-case row, the SPEC-2 staged text, CODE-2, TEST-1, and the TEST-3 tier-5 assertion. No new files are added to §11.
- **TEST-1.2 gained the missing eviction-path fail-closed deny cell.** The listing exercised the classifier on one axis only, varying the trigger (eviction vs periodic) while holding the error class at dropped-connection, so the cell CODE-2.2 explicitly names (`TriggerEviction` with a non-dropped-connection error, a live runtime present but refusing to quiesce) was untested. If the classifier were miswired to treat every eviction-trigger `RequestCheckpoint` error as a dropped connection, a live runtime refusing to quiesce would silently produce a mid-tool-call best-effort snapshot with no test catching it. TEST-1.2 now asserts both deny cells: the periodic dropped-connection cell and the eviction non-dropped-connection cell, the latter still returning `codes.Internal` and archiving no snapshot, pinning that the eviction branch downgrades only on a dropped connection.

### Pass 2 (2026-07-22, automated)

- **The best-effort downgrade was re-scoped off the `TriggerEviction` trigger value onto the adapter's own pod-termination state, because the trigger is shared with the gateway-drain barrier path.** CODE-2 originally scoped the downgrade to "the `TriggerEviction` path only" (§4, the §2 Decisions bullet, the §5 edge table, SPEC-2, CODE-2, TEST-1.2), while §2 simultaneously stated that both the §10.1 gateway-drain barrier path and the new individual-eviction consumer call the same `Checkpointer.CheckpointWithTrigger(..., TriggerEviction)`. Verification confirmed the conflict: `barrier.go:228` drives `TriggerEviction` from the gateway-drain quiesce-and-hold fan-out (`barrier.go:215-221`), during which the agent pod keeps running and its session continues after coordinator handoff, and the adapter that serves the `Checkpoint` RPC derives the trigger solely from `CheckpointStart` (`checkpoint.go:128`), so it cannot tell the two paths apart from the trigger alone. The trigger-only predicate therefore also matched a barrier checkpoint whose lifecycle connection dropped transiently, which would have archived a mid-write best-effort snapshot for a still-running session and silently converted the existing fail-closed gate (`checkpoint.go:158-160`) into a downgrade on a path the safety rationale ("the pod is terminating regardless") does not cover. The finding's two options were gating on the absence of a linked quiesce-and-hold barrier (`!linked` at `checkpoint.go:123`) or threading an explicit "pod is terminating" signal. The second option was taken in the form that adds no wire surface: the adapter `Server` carries an in-process `evicting` flag its SIGTERM handler sets (CODE-1) before it emits `AdapterEvicting`, and CODE-2 gates the downgrade on that flag rather than on the trigger. This is more robust than `!linked` (which races the barrier `open()`/`link()` ordering and would still misfire if `link` lost the race) and adds no new proto field, migration, or trigger value, so it preserves the reuse of `TriggerEviction` for the §16.1 label and the §4.4 retry budget while the barrier path (whose pod's `evicting` flag stays false) keeps failing closed. The same predicate is propagated across the §2 Decisions bullets, §4, the §5 edge table (a new gateway-drain deny row), the SPEC-2 staged text, CODE-1, CODE-2, TEST-1.2 (a new deny cell asserting a dropped-connection barrier checkpoint still returns `codes.Internal`), and the §11 files-touched list.
- **A tier-7a stress test (TEST-4) was added for the concurrent multi-session eviction completion-wait.** CODE-1's completion-wait is genuinely concurrent shared state: the `Checkpoint` RPC is served on gRPC's goroutines (`main.go:428`) while the extracted SIGTERM-handler goroutine (`main.go:411`) waits and aggregates per-slot completion across every bound session, then races that aggregate against a single deadline. Per `.claude/rules/test-coverage.md:38` that is a tier-7a surface, and `code-best-practices.md` requires such code to be `-race` clean and exercised under stress. The only listed test was the single-session tier-1 TEST-1.3, and the tier-5 node drain (TEST-3.2) drives a single session, so the multi-slot aggregate wait (the reason `slot_id` exists) and the concurrency of the completion set were untested at any tier. TEST-4 adds the multi-session aggregate wait, the partial-completion boundary where one slot settles and another does not before the shared deadline, and a `-race` run under `lenny-test stress`, carrying `// spec: 4.6.1, 4.7`. The summary tier list and the §11 files-touched list are updated to name tier 7a.

## 10. Open decisions for review

- **Ratify the best-effort eviction snapshot over the runtime-container quiescence hold.** The proposal takes a best-effort snapshot of the surviving `/workspace` `emptyDir` when the cooperative handshake cannot complete on the eviction path, accepting a tool-call-consistency downgrade the spec already accepts on the eviction and SIGSTOP paths (`spec/04_system-components.md:242-243`), rather than keeping the third-party runtime alive through the eviction window. Confirm the downgrade is acceptable. If a Full-level session must never resume from a non-quiesced snapshot even on a terminating eviction path, the runtime-container hold (original SPEC-2/CODE-2: init container, shared binary copy, unix-socket preStop hold) is the alternative, and the proposal would need to record why best-effort-on-eviction is unacceptable given the spec's existing best-effort and SIGSTOP-eviction allowances.
- **Confirm the coordinator-holds-the-stream invariant, or ratify forwarding to the holder.** `CheckpointWithTrigger` drives only when the receiving replica holds the session binding (`checkpointer.go:424`, else `ErrNoBinding`). The gateway control-stream consumer CODE-3 builds must either prove the control-channel-holding replica is always the session-coordination-lease holder, or forward the `AdapterEvicting` request to the holder over the existing gateway-to-gateway path. This is the within-window transport decision 0052 deferred. A non-holder that silently returns `ErrNoBinding` would drive no checkpoint, so the invariant must be established before dispatch.
- **Confirm accepting the unreachable-coordinator and cross-replica residual.** A coordinator unreachable within the grace window is recovered only by the §10.1 TTL-driven handoff (default 4×15s, which may outlast the window), and that residual session drops to the §4.4 minimal-state fallback. No forced-takeover primitive is built, consistent with 0052's sign-off. If within-grace-window recovery is wanted instead, it requires a forced-acquisition primitive that changes the leasestore holder invariant and must be staged as its own spec change.
