# Proposal: Route the binder adapter dial across the host/Docker boundary so Embedded Mode places sessions on macOS and Windows

- **Status:** Draft for review.
- **Date:** 2026-06-22.
- **Scope:** Closes the host-to-pod dial gap that proposal 0016 leaves open on the Docker-backed substrate (macOS and Windows). Proposal 0016 (approved 2026-06-21) activates the §4.7 pod-placement path in Embedded Mode by threading `--agent-namespace` into the host-process gateway and seeding a credential-free echo runtime, but it keeps the gateway as a host child process. The gateway binder dials each agent pod directly at its in-cluster pod IP on adapter port 50051 (`pkg/gateway/podsession/binder.go:1069` builds `net.JoinHostPort(sb.Status.PodIP, b.AdapterPort)` and `:1077` wraps the failing handshake as `podsession: negotiate version with %s`). On the Linux child-process launcher the gateway and pods share the host network, so the host reaches the pod CIDR. On the Docker-backed launcher the pod CIDR lives inside the Docker VM (`--flannel-backend host-gw` with no `--cluster-cidr`; `pkg/embedded/k3s/dockerk3s.go:229`, `pkg/embedded/k3s/childk3s_unix.go:186`), and the launcher publishes only the k3s API port to the host (`pkg/embedded/k3s/dockerk3s.go:205`), so the host has no route to pod IPs. A `host.docker.internal` mapping exists only for the reverse pod-to-host callback (`pkg/embedded/k3s/dockerk3s.go:206`, `:132`); no host-to-pod mechanism exists. With 0016 applied the binder dial to `10.42.x.y:50051` is dropped and `lenny session new --runtime echo` fails after a connect timeout. This proposal adds a host-to-pod route for the binder adapter dial on the Docker-backed launcher, reusing the proposal-0013 host/Docker bridge, so the dial reaches the in-cluster adapter. It leaves the rest of Embedded Mode (the host-process gateway and controllers, the echo seed, and the §17.4/§26 spec reconciliations) to proposal 0016, which already stages those edits. This proposal stages no spec edit; it documents the §17.4 behavior the scoped code change preserves and stages the code and test changes for the implementation step.

This document stages the proposed code and test changes for the implementation step. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off. The change builds on the spec proposal 0016 stages (§17.4 and §26 reconciliation); it adds no spec edit of its own and is implemented against the committed spec and the merged proposal 0016.

## 1. Problem

§17.4 documents Embedded Mode (`lenny up`) as the primary path for deployers evaluating Lenny on a workstation and "the recommended primary path for runtime authors" because "it exercises the real Kubernetes code path and the production gateway/controllers against the embedded stack" (`spec/17_deployment-topology.md:282`). Reaching a pod over the §4.7 boundary is the property that distinguishes Embedded Mode from the controller-simulator Source and Compose modes. Proposal 0016 activates that path. It does not place a session on the Docker-backed substrate that macOS and Windows use.

### 1.1 The gateway runs as a host process and dials pod IPs directly

The embedded stack starts the production gateway as an `os/exec` host child process (`pkg/embedded/stack/stack.go:265` calls `startGateway(s.gwSpec)`; `pkg/embedded/stack/gateway.go` launches the sibling `lenny-gateway` binary) and binds it to loopback on the host. With proposal 0016 applied, the stack passes `-agent-namespace`, so the gateway selects the §4.7 pod executor and the binder places each started session on a warm pod.

The binder reaches the pod by dialing the pod's in-cluster IP directly. `pkg/gateway/podsession/binder.go:1069` builds `addr := net.JoinHostPort(sb.Status.PodIP, strconv.Itoa(b.AdapterPort))`, dials it with `b.DialAdapter(addr)`, and wraps a failing handshake at `:1077` as `podsession: negotiate version with %s`. The adapter port is the §13.2 adapter gRPC listener, `adapterPort int32 = 50051` (`pkg/controller/sandbox/podspec/podspec.go:96-97`). `sb.Status.PodIP` is an address on the flannel pod CIDR (`10.42.0.0/16`).

### 1.2 On the Docker substrate the host has no route to the pod CIDR

The Docker-backed launcher runs k3s inside the Docker Desktop Linux VM. Its server args set `--flannel-backend host-gw` with no `--cluster-cidr` (`pkg/embedded/k3s/dockerk3s.go:229`), matching the Linux child-process launcher (`pkg/embedded/k3s/childk3s_unix.go:186`), so the pod CIDR `10.42.0.0/16` lives inside the VM. The launcher's `runArgs` publishes one port to the host, the k3s API server port (`-p 127.0.0.1:<APIPort>:<APIPort>`; `pkg/embedded/k3s/dockerk3s.go:205`), and adds one host mapping, `--add-host` for `host.docker.internal` (`pkg/embedded/k3s/dockerk3s.go:206`). The host therefore reaches the in-VM API server through the published port, and it has no route to any pod IP on the in-VM pod CIDR. A connection from the host process to `10.42.x.y:50051` is not deliverable, so the binder's `DialAdapter` connect blocks until its dial deadline and the session-start path fails.

### 1.3 The existing host/Docker bridge is one-directional

Proposal 0013 (merged, commit `18ca14dd`) wired the §4.7 cross-boundary dial host onto agent pods so the in-cluster adapter reaches the host gateway's §8.6/§9.1 GatewayControl listener: `GatewayHost()` returns `host.docker.internal` on the Docker-backed launcher (`pkg/embedded/k3s/dockerk3s.go:132`), and `runArgs` maps that alias to the host gateway IP with `--add-host` (`pkg/embedded/k3s/dockerk3s.go:206`). `gatewayGRPCAddr(sup.GatewayHost(), defaultGatewayGRPCPort)` (`pkg/embedded/stack/stack.go:464`) stamps that address onto each pod. This bridge carries the pod-to-host callback only. The reverse host-to-pod direction the binder needs has no counterpart: the host can reach the in-VM gateway-control endpoint a pod calls back to, but it cannot reach the in-VM pod IP the binder dials.

### 1.4 Proposal 0016 closes placement but leaves the Docker substrate dial open

Proposal 0016 threads `--agent-namespace` into the host-process gateway, threads the agent namespace into the controller so the PoolScalingController materializes the seeded echo pool, applies an echo Runtime CRD with `deploymentModel: embedded`, imports the echo-embedded image, seeds a single-pod warm pool, and stages the §17.4 and §26 spec reconciliations. After 0016 the WarmPoolController pre-warms one echo pod and the gateway binder claims it. On the Linux launcher the binder's pod-IP dial succeeds because the gateway and pods share the host network. On the Docker-backed launcher the same dial is dropped (§1.2), so the placement 0016 activates does not complete a session on macOS or Windows. The tier-4 embedded smoke (`tests/tier4_integration/embedded_mode_smoke_test.go`) runs `lenny session new` end to end; on the Docker substrate it fails at the binder dial with a connect timeout to `10.42.x.y:50051`.

### 1.5 The remaining work is a host-to-pod route for one dial on one launcher

The §4.7 adapter contract, the binder, the placement path, and the pod-to-host callback are all in place. The remaining work adds the reverse route the binder dial needs on the Docker-backed launcher alone: a host-reachable path to the in-VM adapter endpoint of the claimed pod, computed in the same substrate-provisioning layer where proposal 0013 confined its OS branch and where the gateway's dial host is already computed (`pkg/embedded/stack/stack.go:464,489`). The Linux launcher needs no change; the host already reaches the pod CIDR there.

## 2. Decisions

- **Scope this proposal to the verified Docker-substrate host-to-pod gap; let proposal 0016 land the rest.** Proposal 0016 is approved and converged after 7 adversarial rounds, and it stages the host-process placement activation, the echo seed, and the §17.4/§26 spec reconciliations. The verified root cause that 0016 does not close is narrow: the host-process gateway binder cannot route to a pod IP on the Docker substrate (§1.2). This proposal adds that one route and changes nothing else 0016 covers. The in-cluster re-architecture explored in the draft is recorded in Non-goals with its reasons, since it does not close this gap minimally.
- **Route the binder adapter dial through the host/Docker boundary the launcher already bridges.** Proposal 0013 establishes that `host.docker.internal` (mapped by the Docker launcher's `--add-host`) bridges the host/VM boundary for the pod-to-host callback. The host-to-pod direction reuses the same boundary: the host reaches the in-VM adapter endpoint through a host-reachable route the launcher provisions, rather than dialing the in-VM pod IP directly. The decision of which mechanism the launcher provisions (a per-claim port forward into the VM, a published adapter port, or a pod-CIDR route through the VM) is left as an open decision in §8, since each reuses an existing Docker primitive and the trade-off is between connection setup latency and a long-lived forwarder.
- **Confine the route decision to the substrate-provisioning layer.** The host-to-pod route lives in `pkg/embedded/stack` and the Docker launcher under `pkg/embedded/k3s`, the same layer where proposal 0013 confined its OS branch and where the gateway's dial host is computed (`pkg/embedded/stack/stack.go:464`). The gateway binder's dial target is computed from the address the stack supplies; the §4.7 adapter contract and the binder's placement logic stay substrate-agnostic, preserving the §17.4 no-mode-dependent-business-logic-split invariant (`spec/17_deployment-topology.md:168`).
- **Change only the Docker-backed launcher.** On the Linux child-process launcher the gateway and pods share the host network, so the binder's pod-IP dial already reaches the pod and no route is added. The host-to-pod route is gated on the Docker-backed substrate, mirroring how proposal 0013 returns `host.docker.internal` from the Docker launcher's `GatewayHost()` and `127.0.0.1` from the Linux launcher.
- **Stage no spec edit.** Proposal 0016 already stages the §17.4 and §26 reconciliations that the activated pod path requires. This proposal preserves the §17.4 behavior 0016 documents (a credential-free echo session runs on an in-cluster pod over the §4.7 boundary) and adds the route that makes it true on the Docker substrate. The §17.4 same-platform-code-path invariant and the §17.4 local-fidelity disclosure are unchanged, so this proposal adds no spec edit of its own.
- **Do not re-architect the control plane into the cluster to close this gap.** Relocating the gateway and controllers into the embedded k3s as chart-deployed pods would also put the gateway on the flannel pod network and remove the host-to-pod requirement, but it is a far larger change (an in-binary Helm-render-and-apply surface with no existing render path, a Helm SDK dependency, a dev store pod, a gateway Service type change, and the removal of the host-process model) and it exceeds the minimal fix for the verified root cause. The re-architecture is recorded in Non-goals; if it is judged worthwhile on independent grounds it should be a separate forward-looking proposal that resolves the chart-render mechanism and the bring-up-time target before staging any §17.4 edit, rather than blocking pod-placement activation on a control-plane relocation.

## 3. Proposed changes

### C1. Code change: provision a host-reachable route to the claimed pod's adapter on the Docker-backed launcher

Targets: `pkg/embedded/k3s/dockerk3s.go` (the Docker launcher, alongside `GatewayHost()` at `:132` and `runArgs()` at `:197-211`) and `pkg/embedded/stack/stack.go` (the substrate-provisioning layer that computes the gateway dial address at `:464,489`).

Rationale: with proposal 0016 applied the gateway binder dials each claimed pod at `net.JoinHostPort(sb.Status.PodIP, b.AdapterPort)` (`pkg/gateway/podsession/binder.go:1069`). On the Linux launcher the gateway and pods share the host network and the dial reaches the pod. On the Docker-backed launcher the pod CIDR lives inside the Docker VM and the launcher publishes only the API port (§1.2), so the dial is dropped. The route the binder needs is the reverse of the §4.7 callback bridge proposal 0013 already provisions: the host must reach the in-VM adapter endpoint, just as the in-VM adapter already reaches the host gateway through `host.docker.internal`.

Staged change:

- Add a host-to-pod route on the Docker-backed launcher that makes the claimed pod's `50051` adapter endpoint reachable from the host process. The mechanism is the §8 open decision; the launcher exposes the route through a method on the launcher interface (for example, a host-reachable adapter address the launcher returns for a given pod IP, or a launcher hook the binder's dial path consults), so the stack and the binder dial that address rather than the raw in-VM pod IP. The Linux launcher returns the pod IP unchanged, since the host already reaches it.
- Thread the launcher-provided route into the gateway's binder dial target in the same substrate-provisioning layer that computes `gatewayGRPCDialAddr` (`pkg/embedded/stack/stack.go:464`). The binder's `DialAdapter` consumes the address the stack supplies, keeping the substrate branch out of the §4.7 placement logic. Confirm whether the binder dial target is configurable from the embedded stack today or whether a small seam is added so the stack can rewrite the host-to-pod dial address on the Docker substrate; if a seam is added, it is a single injection point in the same layer as the existing gateway-dial-address computation rather than a branch in the binder.
- Gate the route on the Docker-backed substrate only. The Linux child-process launcher adds nothing, mirroring the existing `GatewayHost()` split (`pkg/embedded/k3s/dockerk3s.go:132` returns `host.docker.internal`; the Linux supervisor returns `127.0.0.1` at `pkg/embedded/k3s/childk3s_unix.go:77`).
- Honor the `EMBEDDED_MODE_LOCAL_ONLY` constraint (`spec/17_deployment-topology.md:184`): any host-side port the launcher publishes for the route binds to loopback, matching the existing API-port publish `-p 127.0.0.1:<APIPort>:<APIPort>` (`pkg/embedded/k3s/dockerk3s.go:205`).
- Cite `// spec: §4.7 (the gateway↔adapter dial), §13.2 (adapter on TCP 50051), §17.4 (per-OS substrate)` on the launcher route and the stack wiring.

### C2. Test change: assert the host-to-pod route closes the Docker-substrate binder dial

Targets: `pkg/embedded/k3s/dockerk3s_test.go` (the Docker launcher unit tests), `pkg/embedded/stack/stack_test.go` (the substrate-provisioning wiring tests), and `tests/tier4_integration/embedded_mode_smoke_test.go` (the embedded smoke proposal 0016 re-points at echo).

Rationale: the gap is verified by the tier-4 smoke failing at the binder dial on the Docker substrate (§1.4). The fix is verified by the smoke completing a `session new --runtime echo` end to end on that substrate, and by unit tests that pin the launcher route and the stack wiring on both launchers.

Staged change:

- **Tier 1 (unit).** The Docker launcher exposes a host-reachable route for a given pod IP, binds any host-side port to loopback, and the Linux launcher returns the pod IP unchanged. The stack computes the binder dial target from the launcher route on the Docker substrate and from the pod IP on the Linux substrate. Carry a `// spec: §4.7, §13.2, §17.4` annotation.
- **Tier 4 (integration smoke).** With proposal 0016's echo seed in place, `make test-smoke-embedded` runs `lenny up` → `lenny session new --runtime echo` → `lenny down` to completion on the Docker-backed substrate, placing a session on an in-cluster pod over the §4.7 boundary through the new host-to-pod route, and tolerating the §5.2 `503 RUNTIME_UNAVAILABLE` initial-fill window proposal 0016 documents (`spec/05_runtime-registry-and-pool-model.md:618-624`). Where a macOS or Windows host with Docker Desktop is unavailable in CI, the Docker-backed leg is deferred per the test-coverage tier-5/6 escape hatch: the test skips and states the dependency. Carry a `// diagnosis:` comment stating that a failure at the binder dial means the host-to-pod route did not reach the in-VM adapter.

## 4. Non-goals

- **No re-architecture of Embedded Mode into an in-cluster chart deployment to close this gap.** The draft explored relocating the gateway, controllers, agent pods, and dev stores into the embedded single-node k3s as pods deployed from the production chart `charts/lenny`, with the `lenny` binary embedding the chart, rendering it with a dev values profile, and applying it. That model also removes the host-to-pod requirement because the in-cluster gateway sits on the flannel pod network, but it exceeds the minimal fix for the verified root cause and it rests on surface the repository does not have. `go.mod` carries no Helm SDK; only the CRD yamls are `go:embed`'d (`pkg/embedded/crds`), not the chart; and the chart's templates use Helm directives (`{{ .Values }}`, `{{ include }}`, `{{ .Release.Namespace }}`) that the existing `crdinstall.go` CRD-install path does not render. `crdinstall` unmarshals plain non-templated CRD manifests into typed `CustomResourceDefinition` structs; it sidesteps Helm rendering rather than performing it, so it is not an existing chart-render surface. In-binary chart rendering is a new dependency (a vendored Helm SDK, pre-rendered manifests, or a vendored helm binary), and the full-chart pod bring-up is slower than host-process bring-up, so the §17.4 ready-in-under-60s target (`spec/17_deployment-topology.md:150`) would need reconciling before any §17.4 edit. Both questions are unresolved. If the in-cluster model is judged worthwhile on independent grounds, it belongs in a separate forward-looking proposal that resolves the chart-render mechanism and the bring-up target before staging a §17.4 edit, rather than blocking pod-placement activation on a control-plane relocation.
- **No dev Postgres pod or store-pod chart profile.** The draft proposed adding a `postgres:16` pod, a chart values profile enabling the chart Redis and MinIO deploy paths, and a NodePort gateway Service. The chart's gateway template leaves `LENNY_POSTGRES_DSN`, `LENNY_REDIS_URL`, and `LENNY_MINIO_*` unset under `global.devMode` so a stock render falls back to the in-process in-memory development backends (`charts/lenny/templates/gateway-deployment.yaml`; `charts/lenny/values.yaml` devMode notes), which is the §17.4 "same Go storage interface as production" model (`spec/17_deployment-topology.md:161-166`). A dev store pod is unnecessary, contradicts the §17.4 "no Postgres operator" non-requirement (`spec/17_deployment-topology.md:152`), and the chart's only Postgres template is a CloudNativePG `Cluster` CR requiring the operator. The chart Redis and MinIO deploy paths require HA topologies and mandatory TLS, so they are not a free toggle for a laptop profile. None of this is needed to close the host-to-pod dial gap.
- **No removal of the host-process embedded model.** The draft removed `startGateway`, `startController`, the host TLS proxy, the host PostgreSQL binary, the `miniredis` store, and the host-process bring-up, replacing `lenny status`/`lenny logs` with pod queries. This proposal keeps the host-process model that proposal 0016 builds on and adds one route; it removes nothing.
- **No supersession of proposal 0016.** The draft framed 0016 as a "host-process pod-placement effort" to be superseded. Proposal 0016 activates in-cluster pod placement and is approved and signed off. This proposal builds on 0016: it depends on 0016's `--agent-namespace` threading, echo seed, and §17.4/§26 spec reconciliations, and adds only the Docker-substrate route 0016 leaves open. 0016 lands first; this proposal's code is implemented against it.
- **No §26 reference-runtime reconciliation or re-pinning.** Proposal 0016 stages the §26.1 and §26.7 reconciliations and keeps the reference runtimes placeholder-pinned and credential-gated. This proposal touches neither §26 nor the reference-runtime catalog.
- **No change to the §4.7 adapter contract, the gateway-adapter gRPC API, the binder's placement logic, or executor selection** (`cmd/lenny-gateway/runtime_select.go`). The binder dials the address the substrate layer supplies; the contract and the placement logic stay identical to production.
- **No change to the §4.7 pod-to-host callback wiring.** Proposal 0013 already stamps `host.docker.internal:<port>` onto agent pods for the callback (`pkg/embedded/stack/stack.go:464,489`). This proposal adds the reverse host-to-pod route and leaves the callback wiring unchanged.
- **No change to proposal 0013.** The cross-platform k3s substrate carries forward unchanged as the precondition; this proposal reuses its host/Docker bridge.
- **No change to Source Mode or Compose Mode** (`spec/17_deployment-topology.md:193-264`); their in-process echo is unchanged.
- **No new client-facing protocol, RPC, frame, field, or endpoint.** The change adds a host-to-pod route inside the substrate-provisioning layer and reuses the existing §4.7 adapter dial.

## 7. Resolved in adversarial review

Adversarial review rounds populate this section. The challenge revisions already folded into the draft above:

- **Scoped the proposal to the verified Docker-substrate host-to-pod gap and dropped the in-cluster re-architecture.** The draft re-architected Embedded Mode to deploy the full production stack in-cluster from the chart (the §17.4 rewrite, a dev Postgres chart profile, an embed/render/apply path, and the removal of the host-process model). That direction rests on surface the repository lacks (no Helm SDK in `go.mod`, no embedded chart, an `IfNotPresent` CRD-install path that does not render Helm templates) and duplicates the approved, signed-off proposal 0016 that closes the same finding F-17.4.12 by threading `--agent-namespace` and seeding echo. The verified root cause is narrow: the host-process gateway binder cannot route to a pod IP on the Docker substrate. The proposal is reduced to adding that one host-to-pod route, reusing the proposal-0013 host/Docker bridge, and 0016 lands the rest. The re-architecture is recorded in Non-goals with its reasons and the unresolved chart-render and bring-up-time questions it would have to settle.
- **Corrected the "existing surface already renders chart manifests" premise.** The draft claimed `crdinstall.go` already applies chart-derived manifests without helm. The CRD-install path unmarshals plain non-templated CRD yamls into typed structs and uses no Helm directives; the chart's templates all use `{{ .Values }}` / `{{ include }}` / `{{ .Release.Namespace }}`. The CRD path sidesteps rendering rather than performing it, so it is not an existing chart-render surface. The corrected proposal adds no chart-render path at all.
- **Dropped the dev Postgres pod and store-pod chart profile.** The chart's gateway template leaves the store DSN/URL/endpoint unset under `global.devMode` and falls back to the in-process in-memory development backends, which is the §17.4 "same Go storage interface as production" model. A dev store pod is unnecessary, contradicts the §17.4 "no Postgres operator" non-requirement, and the chart's deploy paths for Postgres/Redis/MinIO require an operator or HA topologies. The store-pod profile is recorded in Non-goals.
- **Dropped the supersession of proposal 0016.** 0016 activates in-cluster pod placement and is approved and signed off; it is not a host-process placement effort to be superseded. This proposal depends on 0016 and adds only the Docker-substrate route 0016 leaves open.

## 8. Open decisions for review

- **Host-to-pod route mechanism on the Docker-backed launcher.** Three mechanisms reach the in-VM adapter endpoint from the host process, each reusing an existing Docker primitive: (a) a per-claim `docker exec`/port-forward into the VM that publishes the claimed pod's `50051` to a loopback host port for the life of the binding; (b) a published adapter port the launcher maps through `runArgs` when a pod is claimed; or (c) a pod-CIDR route through the Docker VM so the host reaches `10.42.0.0/16` directly. Option (c) is the closest to the Linux behavior but depends on Docker Desktop VM routing the launcher does not control; options (a) and (b) are self-contained but add a per-claim host-side forwarder the stack must set up and tear down. Confirm which the launcher provisions and how its lifecycle ties to the binding lifecycle.
- **Binder dial-target seam.** Confirm whether the embedded stack can already rewrite the binder's dial host-to-pod target, or whether a single injection point is added in the substrate-provisioning layer (alongside the existing `gatewayGRPCDialAddr` computation) so the stack supplies the host-reachable adapter address on the Docker substrate without branching the §4.7 placement logic in the binder.
- **Sequencing against proposal 0016.** This proposal's code is implemented against proposal 0016 (the `--agent-namespace` threading, the echo seed, and the §17.4/§26 spec reconciliations). Confirm that 0016 lands first via implement-proposal and that this proposal's tier-4 smoke runs against the 0016 echo seed, so the Docker-substrate route is the only remaining gap the smoke exercises.
