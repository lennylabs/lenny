# Proposal: Re-architect §17.4 Embedded Mode to run the gateway and controllers in-cluster from the chart

- **Status:** Applied to spec (2026-06-24). Approved and signed off by the project owner for implementation. Verified (2026-06-24). Converged after a re-review against the merged proposal 0016 (5 rounds, 5 findings fixed), on top of the initial convergence (7 rounds, 24 findings fixed).
- **Date:** 2026-06-23.
- **Scope:** Closes the Docker-substrate host-to-pod placement gap (macOS and Windows) at its root by running the production gateway and controllers as in-cluster pods in the embedded k3s, rendered from the production chart `charts/lenny` with a dev profile, rather than as host child processes. With the gateway on the pod network, the §4.7 adapter dial reaches agent pods directly on every platform, so the host/Docker boundary the binder cannot cross today (`pkg/gateway/podsession/binder.go:1069` dials `sb.Status.PodIP:50051`, unreachable from the host on the Docker-backed launcher) disappears rather than being tunnelled. The production cluster binaries (`lenny-gateway`, `lenny-controller`, and the rest) run unmodified from their production images; all embedded-specific logic stays in the `lenny` CLI (`pkg/embedded`) and a chart dev profile. The control plane places sessions for any runtime over the §4.7 boundary exactly as production does; the credential-free echo runtime ([§15.4.4](15_external-api-surface.md)) is the seeded zero-config default and the smoke fixture, while the mode supports any runtime. This proposal stages §17.4 spec edits (the control-plane topology, the store-durability and gateway-address rows, and the bring-up-time expectation) plus the code and test changes for the implementation step. It builds on the approved proposal 0016 (the echo seed and the §17.4/§26 placement reconciliations) and supersedes 0016's host-process gateway/controller threading with the in-cluster deployment.

This document stages the proposed spec change plus the code and test changes for the implementation step. It does not modify any spec, code, or doc file. Apply the changes in the "Proposed changes" section after sign-off. The spec edits land first via implement-proposal; the code and test changes implement against the committed spec and the merged proposal 0016.

## 1. Problem

### 1.1 The §4.7 pod path is the property that defines Embedded Mode, and it is the recommended path for runtime authors

§17.4 documents Embedded Mode (`lenny up`) as the primary local-development path and "the recommended primary path for runtime authors" because "it exercises the real Kubernetes code path and the production gateway/controllers against the embedded stack, so a runtime that passes Embedded Mode registration is the closest local approximation to how it will behave in a real cluster" (`spec/17_deployment-topology.md:282`). Embedded Mode is for any runtime: the §17.4 custom-runtime walkthrough builds an arbitrary image, imports it with `lenny image import`, registers a Runtime, and runs a session (`spec/17_deployment-topology.md:284-341`). Reaching a pod over the §4.7 boundary is the property that distinguishes Embedded Mode from the controller-simulator Source and Compose modes. The echo runtime is the credential-free zero-config default and the conformance/smoke fixture; the mode covers any runtime.

### 1.2 The gateway runs as a host process and cannot reach pod IPs on the Docker substrate

The embedded stack starts the production gateway and controller as `os/exec` host child processes (`pkg/embedded/stack/stack.go` `Up()` sequence: self-signed TLS, embedded Postgres with migrations, miniredis, dev OIDC, k3s substrate with CRD install, `startGateway`, the TLS-terminating reverse proxy, then `startController`; `startGateway` at `pkg/embedded/stack/gateway.go:76-84` launches the sibling `lenny-gateway` binary). With proposal 0016 applied, the host gateway selects the §4.7 pod executor and the binder places each session on a warm pod by dialing the pod's in-cluster IP: `pkg/gateway/podsession/binder.go:1069` builds `net.JoinHostPort(sb.Status.PodIP, b.AdapterPort)` and dials it.

On the Linux child-process launcher the gateway and pods share the host network, so the host reaches the pod CIDR. On the Docker-backed launcher (macOS and Windows) k3s runs inside the Docker VM with `--flannel-backend host-gw` and no `--cluster-cidr` (`pkg/embedded/k3s/dockerk3s.go:229`), so the pod CIDR `10.42.0.0/16` lives inside the VM, and the launcher publishes only the k3s API port to the host (`-p 127.0.0.1:<APIPort>:<APIPort>`; `pkg/embedded/k3s/dockerk3s.go:205`). The host has no route to any pod IP, so the binder dial to `10.42.x.y:50051` is dropped and `lenny session new` fails after a connect timeout. The gateway being a host process outside the pod network is the root cause.

### 1.3 The spec is neutral on where the control plane runs

§17.4 places the per-OS substrate provisioning "below the gateway, controllers, CRDs, and storage interfaces, which stay identical across operating systems" (`spec/17_deployment-topology.md:168`), and it asserts "the production gateway, controllers, CRDs, and storage interfaces" and "no mode-dependent code splits in business logic." It does not state that the gateway and controllers run as host processes; that is an implementation choice of the current embedded stack. Running them as in-cluster pods is consistent with the §17.4 architecture description and strengthens the "same platform code path as production" property: the placement that fails on the Docker substrate is performed by the production gateway and controller running the way they run in a real cluster.

### 1.4 The remaining work is a topology change confined to the embedded layer and the chart

The §4.7 adapter contract, the binder, the placement path, the chart that deploys the production gateway and controllers, and the echo seed (proposal 0016) are all in place. The remaining work renders the chart's gateway and controllers (plus the default echo seed) into the embedded k3s as pods, exposes the gateway to the `lenny` CLI through a loopback-published port, and removes the host-process model. The production cluster binaries are unchanged; the embedded decision stays in `pkg/embedded` and a chart dev profile, preserving the §17.4 no-business-logic-split invariant.

## 2. Decisions

- **Run the gateway and controllers as in-cluster pods rendered from the production chart.** The embedded k3s deploys the production gateway and controller Deployments, Services, and RBAC from `charts/lenny` under a dev profile, so the gateway sits on the flannel pod network and dials each agent pod's `sb.Status.PodIP:50051` directly on every platform. This removes the host-to-pod gap at its root rather than tunnelling around it, and it places sessions for any runtime exactly as production does. The production gateway and controller binaries run unmodified from their production images; no embedded-only code is added to any cluster-component binary.
- **Keep all embedded-specific logic in the `lenny` CLI and a chart dev profile; keep one `lenny` binary.** The render, apply, image import, substrate provisioning, port publishing, and status/logs reconciliation live in `pkg/embedded`, compiled into the single `lenny` binary, preserving the §17.4 "single statically-linked binary" property (`spec/17_deployment-topology.md:154`). The dev profile is a values file plus a small number of chart additions; it does not change the chart's production defaults. A separate `lenny-embedded` binary is recorded in Non-goals as a later packaging option.
- **Pre-render the dev profile at build time and embed the manifests; do not vendor a Helm SDK.** The embedded dev profile is fixed (namespace, NodePort, tag-based image references, `spiffeTrustDomain`, the disabled admission/mTLS stack), so the chart is rendered to plain manifests at build time with `helm template <dev-profile>` in `make generate`, and the output is `go:embed`'d the way the embedded CRDs already are (`pkg/embedded/crds/crds.go` `//go:embed *.yaml`). At bring-up the manifests are applied through a dynamic client with a RESTMapper, the apply machinery already present in-repo (`dynamic.NewForConfig` at `cmd/lenny-ops/main.go:520`; server-side apply via `client.RawPatch(types.ApplyPatchType, …)` at `pkg/controller/sandbox/controller.go:636,660`). This avoids a large new runtime dependency and removes runtime render cost. A CI sync check re-renders the chart and diffs against the embedded manifests so they cannot drift, the same obligation the embedded CRDs already carry. The chart's Helm hooks must be excluded from the embedded manifest set, because `helm template` emits hook-annotated resources into its output by default and the `helm.sh/hook` annotations are meaningful only to Helm's install/upgrade engine, so a plain dynamic server-side apply would create them as ordinary objects (the bootstrap Job duplicating or racing the embedded `/v1/admin/bootstrap` call, the preflight Job probing the disabled admission plane and the absent backends, and the post-upgrade CRD-validate, deployment-config-sync, MinIO-lifecycle, and Redis-cluster hook Jobs). The `make generate` render therefore runs `helm template --no-hooks` so no `helm.sh/hook`-annotated resource enters `pkg/embedded/manifests/` in the first place. The embedded stack performs bootstrap through the existing gateway `/v1/admin/bootstrap` path (proposal 0016) and needs no migration against the in-memory stores, so excluding those hook Jobs removes no required step.
- **Use the chart's dev in-memory stores; deploy no store pods and require no operator.** Under the dev profile the gateway and controller start with no Postgres DSN and no Redis URL, so they use the in-process in-memory backends (store selection keys on a non-empty Postgres DSN, independent of `--dev-mode`; `cmd/lenny-gateway/main.go:1379`, with every Postgres-only surface gated on `pgPool != nil`). A single-replica gateway and controller run correctly on the in-memory path for single-node, low-concurrency workloads; the durability and concurrent-mode surfaces are absent by design, which matches the embedded posture. The §4.6.2 pool-materialization channel is the one controller surface that the no-Postgres profile breaks rather than merely leaves absent: the PoolScalingController that projects a poolstore pool row into its `SandboxTemplate`/`SandboxWarmPool` CRD pair is registered only when `poolScalingPools != nil && len(agentNamespaces) > 0` (`cmd/lenny-controller/main.go:575`), and `poolScalingPools` is constructed only inside `if postgresDSN != ""` (`cmd/lenny-controller/main.go:383,398`). Without Postgres the PoolScalingController never registers, so the gateway `/v1/admin/bootstrap` pool seed (which writes only a poolstore row through the §5.2 Store CRUD; `pkg/gateway/admin/bootstrap_resources.go:85`) is never materialized into the `SandboxWarmPool` CRD that the gateway's `ResolvePool` lists (`pkg/gateway/podsession/resolve.go:193`), and `lenny session new --runtime echo` would find no pool and fail. The embedded applier therefore applies the echo `SandboxTemplate` and `SandboxWarmPool` CRD pair (`minWarm = maxWarm = 1`) directly through the dynamic-apply path (C2), so the unconditionally-registered WarmPoolController (`warmpool.Reconciler` at `cmd/lenny-controller/main.go:436-457`, not Postgres-gated) pre-warms the echo pod. No CloudNativePG operator, Redis Sentinel, or MinIO is deployed (`postgres.deploy`, `redis.deploy`, and `minio.deploy` stay false; their chart paths require an operator or HA topologies with mandatory TLS). The cost is that in-memory state is ephemeral and lost on pod restart or `lenny down`, which the §17.4 store table records.
- **Render the `runc` RuntimeClass in the dev profile so the echo pool can warm.** The WarmPoolController validates that the RuntimeClass the pool's isolation profile maps to exists in the cluster before it sizes the pool, and a missing RuntimeClass marks the pool `Degraded=True` and sets `decision.Create = 0`, suppressing pod creation (`pkg/controller/warmpool/controller.go:287-288`; the checker is wired unconditionally at `cmd/lenny-controller/main.go:444`, independent of `--dev-mode`). The echo pool carries the `standard` isolation profile (proposal 0016, `:127`), which resolves to the RuntimeClass object name `runc` (`pkg/sandbox/isolation/runtimeclass.go:26-27`), and the Sandbox reconciler then stamps `runtimeClassName: runc` onto the pod (`pkg/controller/sandbox/podspec/podspec.go:453,829`), which the API server rejects when no such RuntimeClass object exists. A default k3s/containerd cluster has no RuntimeClass object named `runc` (containerd's default low-level handler being runc does not create one), and the chart renders the `runc` RuntimeClass only when `runtimeClasses.create=true` and the `standard` profile is `enabled` (both default false; `charts/lenny/values.yaml:1958-1959,1991-1993`; `charts/lenny/templates/runtimeclasses.yaml:13`). The dev profile therefore sets `runtimeClasses.create=true` with the `standard` profile `enabled: true` (name `runc`, handler `runc`) so the embedded manifests render the `runc` RuntimeClass, mirroring the Kind reference path that installs the same object out-of-band for exactly this reason (`tests/testinfra/kind/agent-workload.yaml:30-38`). Rendering it through the chart's existing `runtimeClasses` surface reuses the production render path rather than applying a parallel standalone object.
- **Disable the admission-webhook and mTLS stack in the dev profile, and add the chart toggle that makes that possible.** The chart unconditionally registers a set of fail-closed (`failurePolicy: Fail`) validating webhooks scoped to agent namespaces (the `pod-security`, `sandboxclaim-guard`, `direct-mode-isolation`, `ephemeral-container-cred-guard`, `pool-config-validator`, `sandboxtemplate-deletion-guard`, and `label-immutability` admission policies, the last rendering two `ValidatingWebhookConfiguration`s), each served by a cert-manager-issued certificate with a CA-injected bundle, with no enable toggle and no devMode gate. Without cert-manager those webhook pods never become Ready, the CA bundle is never injected, and Pod CREATE in the agent namespace is rejected, so no agent pod schedules. §17.4 requires Embedded Mode to need "no cert-manager" (`spec/17_deployment-topology.md:154`), so the dev profile must run without it. This proposal adds a chart values gate (`admissionWebhooks.enabled`, default true) that the dev profile sets false, and sets `mtls.enabled=false` and `certmanager.enabled=false`. Disabling the admission stack also serves the runtime-author audience: the chart's `requireDigest` and cosign-signature admission policy would otherwise reject a runtime author's locally-imported, tag-based, unsigned `my-agent:dev` image. The §17.4 local-fidelity disclosure already states that NetworkPolicy enforcement and the isolation profiles are not exercised locally (`spec/17_deployment-topology.md:170`); the disabled admission/mTLS stack is the same class of disclosed local-fidelity gap, and it introduces no business-logic split.
- **Expose the gateway to the `lenny` CLI through a loopback-only TLS-terminating host-side forwarder in front of the NodePort, carrying the `EMBEDDED_MODE_LOCAL_ONLY` check.** The chart's gateway Service is `ClusterIP`. The dev profile pins the gateway to a `NodePort`. A `NodePort` binds `0.0.0.0` on the node by default, so the node port alone does not satisfy the spec's fail-closed `EMBEDDED_MODE_LOCAL_ONLY` constraint (`spec/17_deployment-topology.md:186`). The in-cluster gateway serves its REST and `/playground` API over plaintext HTTP, the same listener it serves in production where an ingress terminates TLS in front of it (`cmd/lenny-gateway/main.go:6443-6447` builds the `http.Server` with no `TLSConfig`, started by `httpSrv.ListenAndServe()` at `:8059`; the `--tls-terminated-upstream` flag at `main.go:370-371` acknowledges that posture). Embedded Mode has no ingress, so the host-side forwarder retains the TLS-terminating reverse-proxy role the current proxy holds (`pkg/embedded/stack/tlsproxy.go:16-20,69`: `ServeTLS` with the self-signed leaf) and presents `https://127.0.0.1:8443` to the CLI while forwarding plaintext HTTP to the gateway node port. The forwarder carries the `isLoopbackHost` fail-closed check the proxy holds (`pkg/embedded/stack/tlsproxy.go:39-42`). The `127.0.0.1:8080` HTTP leg is a plain TCP relay to the same node port. On the Docker-backed launcher the launcher publishes the in-VM node port to host loopback (`-p 127.0.0.1:<nodePort>:<nodePort>`) and the forwarder targets that published port; on the Linux launcher the forwarder targets the node port on the substrate. The CLI's existing gateway-URL resolution (`pkg/embedded/localcli/session.go` precedence `--api-url`, `LENNY_API_URL`, then the recorded address) points at the forwarder's `127.0.0.1:8443` host port. The CLI-to-gateway crossing is one stable endpoint, unlike the per-session dynamic pod IPs the gateway now dials natively in-cluster.
- **Use the k3s built-in CoreDNS; do not deploy the chart's dedicated CoreDNS.** The chart requires a dedicated CoreDNS with a pinned `coredns.clusterIP` once an agent namespace exists (`charts/lenny/templates/coredns-service.yaml:17` aborts the render otherwise). The dev profile disables the chart CoreDNS and relies on the k3s built-in CoreDNS for in-cluster name resolution, since the agent egress split-horizon DNS policy the dedicated CoreDNS enforces is part of the network-isolation surface §17.4:170 already discloses is not exercised locally.
- **Remove the host-process control plane.** The in-cluster deployment supersedes the host gateway and controller processes, the embedded Postgres binary, the miniredis store, and the host dev OIDC provider. The TLS-terminating reverse proxy is retained in re-pointed form: it stops fronting a host gateway process and instead presents `https://127.0.0.1:8443` in front of the gateway node port (the in-cluster gateway serves plaintext HTTP, the same listener as in production where an ingress terminates TLS; `cmd/lenny-gateway/main.go:6443-6447,8059`), and its `EMBEDDED_MODE_LOCAL_ONLY` fail-closed loopback check is retained. `lenny up` provisions the substrate, imports the platform and echo images, applies the embedded manifests, starts the forwarder, and waits for readiness; the host-process bring-up legs are deleted. Dev authentication keeps the embedded-OIDC bearer model the CLI already uses and trusts that bearer at the in-cluster gateway through the chart's `--bearer-trust-hmac-key-file` hook, per the dev-authentication decision below, so removing the standalone host OIDC provider does not break the CLI's authenticated path.
- **Trust the embedded dev bearer at the in-cluster gateway through the chart's `--bearer-trust-hmac-key-file` hook.** The CLI authenticates by minting a bearer from a persisted HMAC key and sending it as `Authorization: Bearer` (`pkg/embedded/localcli/session.go:209,246-256`; `lenny token print` reads the same key, `pkg/embedded/localcli/token.go:74`). The in-cluster gateway in `--dev-mode` trusts only the in-process Token Service rotating verifier and rejects any other bearer with `401 TOKEN_INVALID` with no fall-through to the dev headers (`cmd/lenny-gateway/main.go:2217`; `pkg/gateway/middleware/auth/auth.go:391-397`); the `--dev-mode` shortcuts are the `X-Lenny-Roles`/`User-ID`/`Tenant-ID` headers (`cmd/lenny-gateway/main.go:6342`), which the bearer-based CLI never sends. The gateway already carries the exact hook for this: `--bearer-trust-hmac-key-file` adds the embedded key as a second verifier wrapped in an audience check pinned to `dev.local` (`cmd/lenny-gateway/main.go:2218,2244,9762-9766`, F-17.4.16), but the chart's dev-mode branch passes only `--dev-mode` and `--redis-allow-insecure` (`charts/lenny/templates/gateway-deployment.yaml:565-578`) and never sets it. The dev profile therefore keeps an in-process dev token signer whose persisted HMAC key `lenny up` writes (the role the embedded OIDC provider's key holds today) and mounts that key into the gateway pod, wiring `--bearer-trust-hmac-key-file` at it through a dev-profile chart value (C1/C3). This reuses the existing dev-bearer hook rather than redefining the CLI auth transport, so the CLI's minted bearer verifies and the `dev.local` foreign-audience rejection control (the basis for the §17.4 audience-rejection sentence S8 reconciles) is retained at the in-cluster gateway. `lenny token print` and `lenny session new` mint against the same persisted key with no change to their flow.
- **Persist the substrate and the imported image store across `lenny down`/`up`, with a version-aware reconcile.** `lenny down` stops the k3s container by default and removes it only on `--purge`, so the k3s image pull, the component image imports, the CRD install, and the manifest apply become one-time first-run costs and a warm `lenny up` restarts in roughly 20-35s. To avoid running stale images after a `lenny` upgrade, `lenny up` compares the CLI version against the deployed image tag and re-imports and re-applies on a mismatch, and falls back to a fresh provision when the persisted substrate is unhealthy.
- **Tune the dev profile for fast, single-node bring-up.** The dev profile sets single replicas, the gateway `PodDisruptionBudget` disabled, and small resource requests so pods schedule immediately on the single node. These settings live only in the dev values file and do not touch the chart's production defaults, which constrains the profile to the knobs the chart already exposes. Three resilience surfaces the chart wires unconditionally have no values-file off-switch and are left at their chart defaults, where each is inert at a single replica rather than removed: the controller pod anti-affinity (the `controller.antiAffinity` knob exposes only `preferred`/`required` with no off setting, so the profile keeps the advisory `preferred` term, which never blocks scheduling with no peer pod), the mandatory `lenny-ops` `PodDisruptionBudget` (rendered unconditionally with no disable knob, its `minAvailable` never blocks at one replica), and the gateway and controller readiness/liveness probe `initialDelaySeconds` (hardcoded in the templates with no values knob, affecting only first-Ready timing rather than scheduling). Adding chart-template off-switches for these is a chart change outside this values-file-only step; the dev profile documents each in its comments and the tier-0 render tests pin the achievable posture (`TestDevProfilePDBPosture`, `TestDevProfileControllerAntiAffinityInert`). Ship the platform images the dev render deploys or stamps (gateway, controller, the mandatory `lenny-ops` Deployment, which the chart hard-fails on any attempt to disable, `charts/lenny/templates/ops-deployment.yaml:6-8,31`, and the `lenny-adapter` image the controller stamps onto every sidecar-model agent pod) and the default echo image as one deduplicated `docker save` tarball imported in a single `ctr images import`, reusing the substrate-aware import path (`pkg/embedded/localcli/image.go`); user runtimes are imported on demand through the same path. The `lenny-adapter` image is bundled and `controller.adapterImage` is set in the dev profile (C1) because the §17.4 walkthrough runtime defaults to the sidecar deployment model, which requires the adapter container; without it `podspec.Build` rejects the sidecar pod (`pkg/controller/sandbox/podspec/podspec.go:478-479`) and the pool cannot warm. The echo seed itself is the embedded deployment model (a single container linking the adapter as a library, `cmd/runtimes/echo-embedded/main.go:15-17`), so the echo smoke path needs no adapter image, but the runtime-agnostic walkthrough does. The token-service Deployment is gated off in the dev profile (C3), so its image is not bundled. `make images` builds `lenny-gateway`, `lenny-controller`, `lenny-adapter`, and the rest but not `lenny-ops` today (`Makefile:37`), so the image set adds `lenny-ops` so the mandatory Deployment reaches Ready rather than landing in ImagePullBackOff; `lenny-adapter` is already built by `make images` and needs only to be added to the import bundle.
- **Decouple "stack ready" from "pool warm."** `lenny up` returns when the gateway answers, and the seeded echo pool warms in the background. The first `lenny session new` against a still-warming pool returns the §5.2 `PoolWarmingUp` `503 RUNTIME_UNAVAILABLE` that proposal 0016 already documents and the smoke already tolerates (`spec/05_runtime-registry-and-pool-model.md:618-624`). `lenny status` distinguishes "gateway up" from "pool ready" so the readiness is honest.
- **Keep the design runtime-agnostic; echo is the default seed and the smoke fixture.** The in-cluster control plane places sessions for any runtime over the §4.7 boundary, including the §26 reference runtimes (with operator-supplied digests and credentials) and arbitrary custom runtimes through the §17.4 walkthrough. The walkthrough's `lenny-ctl runtime register` writes only a runtime-registry record through the admin API (`POST /v1/admin/runtimes`; `pkg/ctlcli/runtime.go:317`), which creates no `Runtime` CRD; the Sandbox controller resolves the runtime from a `Runtime` CRD by name (`pkg/controller/sandbox/controller.go:377-379`), and the no-Postgres dev profile registers no PoolScalingController to project a poolstore pool row into a `SandboxWarmPool` CRD (§2 store decision, §8), so a runtime registered through the walkthrough alone has no `Runtime` CRD and no pool and `ResolvePool` returns `ErrNoMatchingPool` (`pkg/gateway/podsession/resolve.go:245`), the identical failure the echo seed works around with a direct CRD apply. To carry the runtime-agnostic deliverable rather than fix it for echo alone, C2 adds a `lenny` CLI verb that applies a runtime's `Runtime`, `SandboxTemplate`, and `SandboxWarmPool` CRD set to the embedded kubeconfig through the same dynamic-apply path the echo seed uses, so the Sandbox controller resolves the runtime by name, and S5 stages the matching walkthrough step. A custom runtime then materializes its pool the same way the echo seed does, so the WarmPoolController reconciles it to a warm pod. The disabled admission stack makes the runtime-author walkthrough frictionless for locally-imported dev images. Substrate persistence keeps a runtime author's imported image and registration across `down`/`up`.
- **Build on proposal 0016 and supersede its host-process threading.** Proposal 0016 is approved and signed off; it activates pod placement, seeds the credential-free echo runtime (the Runtime CRD with `deploymentModel: embedded`, the single-pod warm pool, and the image import), and stages the §17.4/§26 placement reconciliations. This proposal reuses 0016's echo seed and its §17.4/§26 reconciliations and re-architects the host-process control plane 0016 activates into in-cluster pods, so 0016's host gateway/controller `--agent-namespace` threading is set instead through the chart's `agentNamespaces` values. The proposal is implemented against the merged 0016.

### S2. Reconcile the dev-backend rows for in-process ephemeral stores

In the "Embedded components" dev-backend table, reconcile the Postgres row (`spec/17_deployment-topology.md:161`), Redis row (`:162`), KMS row (`:163`), and Object-storage row (`:165`), and the `mode=embedded` driver-selection sentence in the following paragraph (`:168`). Under the in-cluster gateway the development backends are the in-process in-memory stores inside the gateway pod, and their state is ephemeral and lost on pod restart or `lenny down`. Remove the `~/.lenny/postgres/` persistence claim from the Postgres row. ## 7. Non-goals

- **No runtime Helm SDK dependency.** The dev profile is fixed, so it is pre-rendered at build time and embedded, with a CI sync check, rather than rendered in-process. Vendoring `helm.sh/helm/v3` (a large dependency, absent from `go.mod`) is avoided.
- **No full production admission/mTLS/cert-manager stack in Embedded Mode.** The fail-closed validating webhooks, the CRD-conversion webhook, the shared cert-manager `Issuer`, every webhook `Certificate`, the mTLS material, the token-service (through the new `tokenService.enabled=false` gate, C3), and the dedicated CoreDNS are disabled in the dev profile, so the rendered dev manifests carry no `cert-manager.io/v1` object. Running them would require provisioning webhook serving certificates without cert-manager (a CA, the serving Secrets, and caBundle injection), contradict the §17.4 "no cert-manager" requirement, push bring-up to minutes, and, through the `requireDigest`/cosign admission policy, reject runtime authors' locally-imported unsigned dev images. The disabled stack is the same class of disclosed local-fidelity gap as the NetworkPolicy and isolation-profile degradation §17.4:170 already records.
