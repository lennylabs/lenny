# Non-spec changes: Release ownership for pods, slots, per-pod claims, and credential leases at and after a terminal write

## Design (implementation-facing)

The slot release becomes idempotent per session at the one primitive every slot reservation and release passes through (CODE-1, implementing SPEC-1a). Because a duplicate release is then a no-op, the design adds no arbitration between releasers. It routes every pre-running release through one slot-aware `Binder.ReclaimClaimed` (CODE-2), deletes the side releasers that delete a shared claim by name (CODE-3, CODE-4), orders the post-terminal hook against a superseded binding and against the failure funnel (CODE-5, CODE-6), and routes full_revoke through the existing releasers (CODE-7). Every consumer that reads slot occupancy from the session rows uses the one **Slot-holder predicate** stated with the **Slot-set outage recovery case table**, which CODE-1 item 9 makes true. The recovery of the slot sets after a Redis outage is that table's (CODE-1 item 8). What each release path does when one of its steps fails is the **Release-path failure-outcome table** below. A slot member that its release left behind, because the release failed or never ran, is released by the leader-run **Stale-slot reaper** (CODE-9) once the session's row has been terminal for longer than `claimOrphanTimeout`. Releases that no replica can perform are accepted departures, each with one row in the **Accepted-departure register** below.

The change adds no RPC, proto field, column, table, session state, or error code. Its loops are the slot-set recovery probe of CODE-1 item 8, which follows the storage-quota `RecoveryReconciler`, and the stale-slot reaper of CODE-9, which runs on the gateway leader. It changes the value type stored under `lenny:pod:{pod_id}:active_slots`, spells the pod identifier in every per-pod key as a Redis hash tag (CODE-1 item 7), clears `pod_assignment` on the failure funnel's two non-terminal edges (CODE-1 item 9), and changes the signatures of `slotcounter.Counter.Reserve`, `slotcounter.Counter.Release`, `slotcounter.SlotSource.GetActiveSlotsByPod`, `sessionstore.Store.GetActiveSlotsByPod`, and `podclaim.SlotClaimer.ReleaseSlot`, and it adds `ListPodsWithActiveSlots` to `slotcounter.SlotSource` and `sessionstore.Store`. CODE-9 adds `ListStaleTerminalSessions` to `sessionstore.Store`, adds `Counter.Members` and `Counter.Reap`, and makes the adapter's `absent` answer report an unclean exit for an identifier under the §5.2 reclaim hold (SPEC-1k). Every caller is updated in the same step.

**Resource-to-owner table after this proposal.** Each cell names the one component that releases the resource on that path. A second release from any other path is a no-op, apart from the duplicate release after a Redis restart or a recovery rebuild (**Accepted-departure register** row A13): a keyed slot release that finds no member (CODE-1), a claim delete that finds no claim, or a lease release for a session that holds no lease.

**Invariants.** Each is stated here once.

1. No release path writes the claim's `failed` or `released` binding state. Only the recycle boundary writes them (SPEC-2d).
2. A withdrawal that holds no occupancy (D8) has no claim effect.
3. No row states the pod's resulting phase. The §4.6.1 **Occupancy projection** decides it from the claim the row leaves.

**Paths outside the table.** These write or delete the claim and are not releases of an occupancy: the hold-expiry delete and the acquisition path that ends a hold (§4.6.3 already names both), the recycle boundary's `reserved`, `released`, and `failed` writes and its missing-report retire, `DrainSandbox` (it stamps an annotation and writes no claim), and the WarmPoolController's deletes at pod termination and orphan GC. The **Stale-slot reaper** removes a member and writes no claim, because it never empties a set. `CRDPodRegistry.ReleasePod` (`pkg/podregistry`) and `AgentSandboxPodLifecycleManager.ReleasePod` (`pkg/podlifecycle`) delete a claim by name and have no production caller.

**Races the table does not close.** Each predates this proposal, except where the item says otherwise, and each is an accepted departure with a row in the **Accepted-departure register** (rows A16 to A19):

- The release that empties the set (D2, D4, D6, D7) deletes the claim or patches it while a peer's reservation on the same pod is in flight. A sibling reservation writes no claim, so no precondition sees it.
- `SlotClaimer.ClaimSlot` Pass 1 skips only a missing claim and the terminal binding states, so it can reserve a slot on a claim in `recycling`, whose set the last release emptied (register row A17).
- `terminalReclaimPreRunning` decides pre-`running` from the row's `fromState` and the local registry. `/start` registers the binding before `commitStart`, so a row can still read `ready` while its slot is `running` on another replica, and CODE-7's `ReclaimRevokedPreRunning` reads a peer's binding the same way (full_revoke row R3; register row A18).
- Row D9's by-name deletes run on a pool with `maxConcurrentSessions` above 1 through `Binder.Resume`, which calls `claimPod` on every pool kind. `SlotClaimer.ClaimSlot` Pass 1 joins any found claim whose phase is not terminal and whose `spec.tenantId` matches, including the empty-phase claim `claimIdle` has just created, so a same-tenant sibling can reserve onto the claim before the delete (register row A19).

### full_revoke release table

This table is the proposal's full statement of how full_revoke releases what it releases: the order of its steps, the effect of each step on each session it cancels, and the response field each outcome increments. CODE-7, the summary, and the P5b impact row cite it and do not restate it. The session set, its listing, and the deny-list granularity belong to P5b (summary Decision 18); the table takes the set that `terminateUserSessions` lists today. The cells state the tree after CODE-1, CODE-2, CODE-5, and CODE-7, and every cell was checked against `cmd/lenny-gateway/user_revocation.go`, `pkg/gateway/externalapi/admin/users.go`, `pkg/gateway/externalapi/admin/users_invalidate.go`, and `pkg/gateway/sessionserver/terminal_binding.go` at 29c764c55, whose code is unchanged from 85c9ab19a.

**Order.** full_revoke runs these steps in this order. SPEC-3a states the order in the spec: step 1 states the return-then-deny order and its precedence over the cancel writes, and step 4 states the reclaim's precedence over the handling replica's releases. This list is the single non-spec statement of the order and implements SPEC-3a; no other non-spec site restates it.

1. `terminateUserSessions` lists the user's sessions (`List` with the `UserID` filter) and collects the identifiers of the non-terminal rows.
2. `RevokeUserLeases` enumerates the leases those sessions hold (`LeasesBySession`), calls the credential assigner's `Release` on every lease, and then writes one deny-list entry (`lease.CredentialKey()`) per lease. Every `Release` precedes the first deny-list write, because the deny list's in-process revoke hook `directModeRevocationRotator.onRevoke` rotates every direct-delivery lease it still finds on the credential and would push a fresh key to a revoked session; a per-lease interleaving lets one lease's entry find a later lease on the same pool credential. The step precedes the first cancel write, because once a row is terminal the coordination Sweeper's D6 release and the resume tail can release its binding, which returns its leases and removes their records, and a lease the enumeration no longer finds receives no deny-list entry.
3. For each listed row in turn: open the session's terminal claim on the handling replica (`BeginTerminal`), then the guarded cancel write (the pre-revoke state read on the locked row, `cancelled`, and `MarkTerminated`), then `AfterRevokeWrite` (`CancelResumeAttempt`, then the inbox and DLQ drain). A write that does not apply or returns an error ends its claim at once. No post-terminal hook runs. While a claim is open, `startRelease` refuses, so neither the handling replica's coordination Sweeper (`sweepTerminal`, every 15 seconds by default) nor its resume tail can release the cancelled session's binding before step 4(a).
4. `runFullRevokeFanOut`: (a) `ReclaimRevokedPreRunning` for each cancelled session whose pre-revoke state is `created`, `finalizing`, or `ready`, and then the end of every claim step 3 opened; (b) `TerminateUserSessions`, which runs `terminateLocal` and then publishes the request to peers, each of which runs `terminateLocal` over its own registry; (c) the token and playground steps, unchanged. The handler then dismisses the user's pending elicitations, unchanged. Step (a) precedes step (b), and the step-3 claims keep the handling replica's own releases out of the same window, because `terminalReclaimPreRunning` skips a session bound on this replica only while the registry still holds the binding; after a release removed it, a reclaim would delete by name a claim the release had just patched to `recycling` (row D3b). The claims end before step (b), so step (b)'s `startRelease` is not refused by them. The handler also ends every claim on each return path; the end function is idempotent. A process exit drops the claims with the bindings they fence.

**Release outcomes.** `terminateLocal` calls `ReleaseRevokedBinding` for each registry entry of a cancelled session and maps its result into the response: `(true, nil)`, returned when the executor release returned nil, counts one in `podsTerminated`; `(false, nil)`, returned for a non-terminal row, a refused `startRelease` (a D6 or resume-tail release of the session is running, or a terminal writer's claim is open on this replica, which leaves the binding to D6), no binding, a stale binding it evicts, or a binding `releaseReportedBinding` finds replaced, counts nothing; `(false, err)`, returned for a `ReadPrimary` error, a lock-wait error on the bounded call context, or an executor release error, adds the session to `podTerminationFailures`. An executor error leaves no binding to retry, because `PodExecutor.Release` unbinds before the binder runs. `leasesRevoked` is the number of leases step 2 enumerated, a lease whose `Release` failed included. A peer's release and the pre-running reclaim count nothing, and a reclaim error is only logged.

The columns are:

- **Lease record** and **Pool slot**: "step 2" means `Release` removed the record and returned the pool slot. With the in-process assigner the slot is returned to the handling replica's per-replica count, so a lease a peer minted (rows R3, R6, and R7) leaves the minter's count high and the handler's low, the per-replica accounting departure N4 owns. Both assigners remove the record, the Token Service client even when its `RevokeCredentials` call fails, in which case the Token Service's pool count stays until lease expiry (N4).
- **Deny-list entry**: "step 2" means one entry per enumerated lease, published to peers.
- **onRevoke**: the hook runs only with the in-process assigner, on the handling replica and on each peer that applies the published entry. A peer finds none of the session's leases when the replicas share the Postgres lease store; with in-memory lease stores a peer still finds a lease it minted (P5b). Beyond the rows below, it marks each deny-listed pool credential unselectable and rotates every other session's direct-delivery lease on it (C3, owned by P5b).
- **Binding release**: what releases the session's pod binding or its pre-running claim.
- **Claim and slot**: the disposition table row the release takes.
- **Response field**: what the session adds to the response, with n the number of its leases step 2 enumerated.

### Slot-set outage recovery case table

This table is the proposal's single statement of how the slot sets recover when a Redis outage ends: what starts the recovery rebuild of CODE-1 item 8, which replicas run it, what the outage ledger records, and what happens to each kind of member. Every other site that describes the recovery rebuild, the outage ledger, or their residue cites this section. A change to outage recovery starts at its row or at the **Outage ledger and add-only rebuild.** paragraph, re-derives it from the functions it names, and then edits CODE-1 item 8, the register rows it cites, and the tests. Failure-outcome table row F1 states what a release does when the rebuild fails, and the **Accepted-departure register** states each residue's bound.

**Slot-holder predicate.** A session holds a slot on pod P exactly when its row is non-terminal and its `pod_assignment` names P. This paragraph is the predicate's only statement, and every consumer cites it: the rehydration seed (`GetActiveSlotsByPod`, SPEC-1b's "the pod's non-terminal sessions"), the §12.4 fallback gate (`ReserveSlotUnderLock`), the orphan GC's `PodHasActiveSession`, and the rebuild's `ListPodsWithActiveSlots`. Each path that releases a slot keeps it true:

- The failure funnel's `resume_pending` and `awaiting_client_action` edges clear `pod_assignment` in the edge write, before the release (CODE-1 item 9), as the suspension release clears it before its release (`clearSuspendedPod`) and the idle suspension clears it in its own write (`writeIdleSuspension`). One other writer moves a bound row into a recovery state: `MarkBudgetUnrecoverable` (`delegationbudget/adapters.go`) moves a tree root from any non-terminal state to `awaiting_client_action` and releases nothing, so the row keeps naming the pod it still holds, and `enterResumePending` carries that row to `resume_pending`. Every other writer of `resume_pending`, `resuming`, or `awaiting_client_action` starts from a row already cleared and keeps the value, and only the resume commit names a pod again, in the write that moves the row to `running`.
- The resume binder's compensation (`failResume`, `releaseResumeSlot`) and `ReleaseUncommitted` release the attempt's pod, which no row names before the commit lands. `releaseEarlierBinding` clears `pod_assignment` under `slotAccountLocks` before it releases the binding of a `resume_pending` row (CODE-1 item 9), which covers the row `MarkBudgetUnrecoverable` left naming its pod; on a row the funnel cleared the clear changes nothing.
- `BindReservedSlot`'s release after a failed `/start` leaves the row `ready` and naming the pod, so the row stays a slot holder. The `/start` retry binds on that pod without a new reservation (summary **Defects in the shipped tree that this proposal does not stage**), and the session's terminal release is keyed and removes any member a rehydration added for it (disposition table rows D2 and D4).
- The terminal releases (the post-terminal hook, D6, and full_revoke) follow a terminal write, and the predicate excludes terminal rows.
- `persistPodAssignment` (`sessionserver/bind_registration.go`) skips a row in a recovery state (CODE-1 item 9), so a binding publish that races the funnel's edge write cannot name the pod again.

**Outage ledger and add-only rebuild.** This paragraph is the only statement of what the outage ledger records and of what the recovery rebuild changes in a slot set. CODE-1 item 8 states the code that builds it, and every other site cites this paragraph or a row below.

- The ledger is per `Counter`, guarded by `outageMu`, and holds entries of two kinds, each of which adds a member at the rebuild: an admission (pod, session), recorded when `fallbackReserve` admits; and a leaked mark (pod, session), recorded whenever a leaked `Counter.Release` fails, whatever the error: Redis unreachable for its script, its rehydration, or the rebuild it runs first, a Postgres error or `ErrRehydrationStalled` in its rehydration, or its context deadline, whether or not the outage clock is set. The mark is add-only, so recording it on every failure is safe. It counts the leak of a session that holds no member, such as a session the fallback admitted, and it keeps the leak counted when a later clean release of the same session removes the session's member. A clean release that fails records nothing. Recording an entry that is already present records it again without adding a second entry. Admissions are bounded by one fallback window, because the gate fails closed after `slotCounterPostgresFallbackMaxSeconds`, and leaked marks by the leaked releases during the outage.
- `fallbackReserve`, an unreachable probe tick, and any `Counter.Release` that fails because Redis is unreachable stamp the outage clock under `outageMu` when it is zero; no other failure stamps it. While the clock is set or the ledger holds an entry, `Reserve` and `Release` run the rebuild before their script, and a reachable probe tick runs it.
- The rebuild reads the ledger and, only while the clock is set, lists the pods the **Slot-holder predicate** names (`ListPodsWithActiveSlots`). For each pod the ledger or the listing names, one script adds the ledger's admissions and leaked marks for that pod and, when the listing names the pod, deletes the pod's `rehydrated` flag. Each listed pod's next reservation or release then rebuilds the set through the §5.2 blocking rehydration, whose seed adds the rows' identifiers and removes no member.
- The rebuild removes no member. Every member a set holds when Redis returns stays, including a `leaked:<sessionId>` member, a create's or a resume's reservation made before its row names the pod, and another replica's re-reservation of a session. A member whose release failed during the outage also stays, whether the session's row is terminal or non-terminal and whether the replica whose release failed still runs or exited before Redis returned. Each such member fails closed: it holds one slot until a later release of its session removes it or, when none does, until the **Stale-slot reaper** releases it once the session's row has been terminal for longer than `claimOrphanTimeout` (register row A27). The member a rebuild adds for a fallback-admitted session whose release ran on another replica before that rebuild stays counted with the same bound (register row A31).
- The rebuild runs no occupancy-zero disposition, because it removes no member.
- An entry is removed once the script for its pod succeeds, unless it was recorded again after the rebuild read the ledger, in which case it stays for the next rebuild. Only a successful rebuild that leaves the ledger empty clears the clock. Rebuilds run single-flight per `Counter`. With no `SlotSource` wired, the rebuild lists no pods and runs the script for the ledger's pods only, deleting no flag.

Each row states one case under the staged design: the rehydration adds the rows' identifiers and removes no member (SPEC-1b), and the recovery rebuild is add-only, as **Outage ledger and add-only rebuild.** states (summary Decision 21). The rebuild keeps every member a set holds when Redis returns, so a member kind has a row only when its outcome differs from that rule: the rebuild adds it, or it stays counted under a register bound. Row numbers are identifiers that the register and the tests cite, and a removed row's number is not reused, so O12 to O14 are unassigned. ### Stale-slot reaper

This section is the only statement of which slot members the stale-slot reaper releases, how it releases them, and how it orders against the other releases of the same member. CODE-9 states the code that builds it, failure-outcome table row F21 states what it does when a step fails, and register row A32 bounds what it keeps. The owner added the reaper on 2026-10-19 (summary Decision 23). A change to the reaper starts here.

- **Eligible member.** A plain session member S of pod P's slot set whose session row is in a terminal state and whose `terminated_at` is older than `claimOrphanTimeout` (the gateway's `--slot-reaper-terminal-age`, default 5 minutes, the default of the controller's `--claim-orphan-timeout`). `sessionstore.MarkTerminated` stamps `terminated_at` in the first terminal write and keeps it on a relabel, so no later write moves it. A terminal session makes no further transition, and its identifier is never reserved again, so S names no live or future slot. A `leaked:` member is never eligible (§6.2 **`leaked` slot semantics.**), and neither is a member whose row is missing, non-terminal, or terminal with no `terminated_at`, which covers a create's reservation made before its row exists.
- **Discovery.** Each pass lists the pods `ListPodsWithActiveSlots` names (CODE-1 item 8), reads each listed pod's members with one `SMEMBERS` on its active-slots key, and resolves the plain members with `ListStaleTerminalSessions`, one cross-tenant primary-key read per batch of identifiers. A pod that no non-terminal row names is not listed. Its members hold no live session's capacity, and the orphan GC drains the pod (**GC** backstop).
- **Release.** For each eligible S on P, the reaper resolves P's Sandbox and dials its adapter at the pod address, as `connectSlot` does, and sends the unconditional `Shutdown` for S. That call tears S's slot down when the adapter still holds an entry for S, and answers `absent` when it holds none. Only when the call returns no error and reports a clean exit does the reaper run `reapScript` on P's keys, which removes S only while P's `rehydrated` flag is set and the set holds another member. The reaper therefore never empties a set, runs no occupancy-zero disposition, and writes no claim. A member it does not remove stays and is retried on the next pass (row F21).
- **The adapter answer it relies on.** An `absent` answer reports an unclean exit while S's identifier is under the §5.2 slot-identifier reclaim hold (SPEC-1k), which holds while another release's cleanup of S is in flight and, after a cleanup that did not complete, for the pod's life. Without that answer, after a teardown that did not complete, a leaked release that failed, and a leaked mark lost with its exited replica, the reaper would free a slot whose runtime may still run.
- **Order against other releases.** The reaper shares no lock with the release paths. The keyed removal serializes them: a late release of S and the reaper each remove S at most once, a `releaseScript` that finds no member returns `removed` false and runs no disposition, and a `reapScript` that finds no member changes nothing. A late leaked release adds `leaked:S` whether or not it removed S (SPEC-1a), so a leak reported after the reaper's removal stays counted. A late release whose `Shutdown` is still tearing S down holds S's reclaim hold, so the reaper's `Shutdown` reports an unclean exit and the reaper keeps S. A recovery rebuild that adds S again from its ledger (row O15) leaves S for the next pass. Two leaders during a Lease failover run the same idempotent steps.
- **Rate.** A pass starts `--slot-reaper-interval` (default 60 seconds) after the previous pass ends. Releases are limited by a token bucket at `--slot-reaper-rate` (default 50 per second), with at most that many in flight, so the about 12,000 members a 60-second outage leaves at Tier 3 clear in about 4 minutes. A pod with no eligible member is not dialed. At Tier 3 sizing (up to about 2,500 concurrent pods) discovery adds about 42 `SMEMBERS` reads per second at the default interval, and releases add at most 50 scripts and 50 `Shutdown` calls per second, against the ~6,500 Redis writes per second §12.4 sizes for Tier 3.
- **Recovery time.** A member whose release failed is released about `claimOrphanTimeout` after its session ended, plus up to one pass interval, plus its place in the drain at the rate limit.

Cancelling the server's lifetime context during that wait instead makes no `terminalReclaimPreRunning` or executor call. Both cases hold the lock before they cancel, because `sessionLocks.Lock` picks at random when its context is done and the lock is free. With the writer's context cancelled before step 5 on a concurrent pool, the release removes the member, adds `leaked:<sessionId>`, and writes no claim (**Release-path failure-outcome table** row F6, register row A5).

## Edge cases and accepted failure modes

The SPEC-owned cases are in the spec-changes file. This section holds the **Accepted-departure register** and the code-level cases.

### Accepted-departure register

This register is the proposal's only rule site for accepted departures. Each row states one departure's bound, the site that describes its mechanism, its BUILD-GAPS record (REC-1 items 3 and 5), its reader-page site (DOCS-1), and the test that pins it. Every other site that names a departure describes the mechanism and cites a row here. A change to a departure starts at its row, then the sites its row names.

The bounds use these backstops:

- **GC**: the chart-installed claim-orphan GC drains the pod and deletes a `bound` or `recycling` claim once its last binding-state transition is older than `claimOrphanTimeout` and no non-terminal session row names the pod, within one GC sweep interval after that (defaults 5 minutes and 60 seconds).
- **Counted**: the slot's member stays in the set, which fails closed. A plain session member is released by the **Stale-slot reaper** once its session's row has been terminal for longer than `claimOrphanTimeout`, within one pass interval plus the drain at the reaper's rate limit after that (defaults 5 minutes, 60 seconds, and 50 members per second). A member the reaper keeps (register row A32), and a `leaked:` member, stays until the GC drains the pod or until a Redis restart loses the set and a rehydration rebuilds it from the session rows; on a pod with continuous sibling traffic that is the pod's lifetime. A recovery rebuild after a Redis outage removes no member (**Slot-set outage recovery case table**).
- **Lease expiry**: the lease-store expiry sweep removes the lease row and expires its deny-list entry at the lease's expiry. With the in-process assigner, the per-replica credential-assignment count returns only at a process restart until N4 lands.

### Code-level cases

- **Releases no replica performs.** These releases have no replica that runs them, and each is a register row:
  - a process exit between the terminal commit and the release (A1);
  - the F-10.1.21 residue (A2);
  - a `failFinalizing` write that commits and reports a store error on any exit other than the plan-parse exit (A3);
  - a slot release that still fails when the bounded retry ends, or at a `reserveSlot` rollback's single attempt (A4);
  - a release whose caller's context ends while it runs (A5);
  - the claim `claimPod` created when `reserveResumeSlot` fails (A6, summary Decision 11) or when `StampPodTenant` fails in `Claimer.claimIdle` (A7);
  - a lease release that is lost (A8);
  - a full_revoke cancel write that commits and reports a store error on a pre-running row with no binding (A25).
- **A disposition failure after the member is removed.** The recycle patch or the claim delete fails after the release removed the last member, or a slot release's script ran and its reply was lost (a transparent client re-send, or a repeat by `releaseSlotRetrying`). No path repeats the disposition, because a repeat finds no member (**Release-path failure-outcome table** rows F1 and F2; A9).
- **A superseded coordinator's terminal write loses the seal.** After CODE-5, a terminal write by a replica whose binding is stale does not seal through that binding, and the adopter's D6 release runs no seal, so §7.1 **Seal-and-export invariant:** is not met for that case. This is the same loss an off-holder terminal write already has under the F-10.1.33 departure, which this case joins (A10).
- **A reservation made during a Redis outage.** The §12.4 Postgres fallback admits without adding a member, and how the session is counted afterwards is **Slot-set outage recovery case table** rows O1, O5, O15, and O16, with the register rows those rows cite.
- **A CREATE loser's withdrawal after the winner's last release.** The winner's session releases while the loser's member is still counted, so that release leaves the set nonempty and runs no disposition. The loser's withdrawal (row D8) then removes the last member through the raw `Counter.Release`, which runs no disposition either, and the winner's claim stays `bound` on a pod with an empty set (A20).
- **F-7.3.34(b).** A rebuild-branch bind failure is on an exclusive pod, and the drain retires the pod, so the code is not changed.
- **An exclusive recycling pod rebound before a writer's by-name delete.** A peer's D6 recycles a `/start` binding of a pre-running session and a successor rebinds the pod before the writer's hook deletes the claim by name. Closing it needs session identity on the claim, which this proposal does not add (A21).
