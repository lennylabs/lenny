# Non-spec changes: Release ownership for pods, slots, per-pod claims, and credential leases at and after a terminal write

## Design (implementation-facing)

The slot release becomes idempotent per session at the one primitive every slot reservation and release passes through (CODE-1, implementing SPEC-1a). Because a duplicate release is then a no-op, the design adds no arbitration between releasers. It routes every pre-running release through one slot-aware `Binder.ReclaimClaimed` (CODE-2), deletes the side releasers that delete a shared claim by name (CODE-3, CODE-4), orders the post-terminal hook against a superseded binding and against the failure funnel (CODE-5, CODE-6), and routes full_revoke through the existing releasers (CODE-7). Releases that no replica can perform are recorded as departures with a bound (**Edge cases and accepted failure modes** below).

The change adds no RPC, proto field, column, table, session state, background loop, or error code. It changes the value type stored under `lenny:pod:{pod_id}:active_slots` and the signatures of `slotcounter.Counter.Reserve`, `slotcounter.Counter.Release`, `slotcounter.SlotSource.GetActiveSlotsByPod`, `sessionstore.Store.GetActiveSlotsByPod`, and `podclaim.SlotClaimer.ReleaseSlot`. Every caller is updated in the same step.

**Resource-to-owner table after this proposal.** Each cell names the one component that releases the resource on that path. A second release from any other path is a no-op, apart from the Redis-restart departures in the spec-changes **Edge cases and accepted failure modes**: a keyed slot release that finds no member (CODE-1), a claim delete that finds no claim, or a lease release for a session that holds no lease.

**Invariants.** Each is stated here once.

1. No release path writes the claim's `failed` or `released` binding state. Only the recycle boundary writes them (SPEC-2d).
2. A withdrawal that holds no occupancy (D8) has no claim effect.
3. No row states the pod's resulting phase. The §4.6.1 **Occupancy projection** decides it from the claim the row leaves.

**Paths outside the table.** These write or delete the claim and are not releases of an occupancy: the hold-expiry delete and the acquisition path that ends a hold (§4.6.3 already names both), the recycle boundary's `reserved`, `released`, and `failed` writes and its missing-report retire, `DrainSandbox` (it stamps an annotation and writes no claim), and the WarmPoolController's deletes at pod termination and orphan GC. `CRDPodRegistry.ReleasePod` (`pkg/podregistry`) and `AgentSandboxPodLifecycleManager.ReleasePod` (`pkg/podlifecycle`) delete a claim by name and have no production caller.

**Races the table does not close.** Each predates this proposal, except where the item says otherwise, and is filed by REC-1 item 6:

- The release that empties the set (D2, D4, D6, D7) deletes the claim or patches it while a peer's reservation on the same pod is in flight. A sibling reservation writes no claim, so no precondition sees it.
- `SlotClaimer.ClaimSlot` Pass 1 skips only a missing claim and the terminal binding states, so it reserves a slot on a claim in `recycling`, whose set the last release emptied. The new session's slot then shares the pod with the running whole-pod scrub. After CODE-1 item 4, a D7 rollback of that join also deletes the `recycling` claim, where today's rollback deletes no joined claim; the delete retires the pod mid-scrub, which fails closed. The recycling follow-up owns it.
- `terminalReclaimPreRunning` decides pre-`running` from the row's `fromState` and the local registry. `/start` registers the binding before `commitStart`, so a row can still read `ready` while its slot is `running` on another replica. A terminal write on a replica without the binding then runs D1 or D2 on a `running` slot: on a recycling `mcs 1` pool the claim is deleted where D3b would patch it, and on `mcs >1` the member is removed under a running runtime, after which the binding replica's D5 release removes nothing. CODE-7's `ReclaimRevokedPreRunning` has the same exposure. The F-10.1.21 owner (R16 with S17) owns it.
- Row D9's by-name deletes run on a pool with `maxConcurrentSessions` above 1 through `Binder.Resume`, which calls `claimPod` on every pool kind. `SlotClaimer.ClaimSlot` Pass 1 joins any found claim whose phase is not terminal and whose `spec.tenantId` matches, including the empty-phase claim `claimIdle` has just created, so a same-tenant sibling can reserve onto the claim before the delete. The delete then drains the pod under the sibling, whose session takes the pod-failure path. The delete fails closed for isolation. A delete that is safe against the join needs the slot set on the resume path, which summary **Non-goals** declines for N2. REC-1 item 6 files it as an accepted departure.

### full_revoke release table

This table is the proposal's full statement of how full_revoke releases what it releases: the order of its steps, the effect of each step on each session it cancels, and the response field each outcome increments. CODE-7, the summary, and the P5b impact row cite it and do not restate it. The session set, its listing, and the deny-list granularity belong to P5b (summary Decision 18); the table takes the set that `terminateUserSessions` lists today. The cells state the tree after CODE-1, CODE-2, CODE-5, and CODE-7, and every cell was checked against `cmd/lenny-gateway/user_revocation.go`, `pkg/gateway/externalapi/admin/users.go`, `pkg/gateway/externalapi/admin/users_invalidate.go`, and `pkg/gateway/sessionserver/terminal_binding.go` at 29c764c55, whose code is unchanged from 85c9ab19a.

**Order.** full_revoke runs these steps in this order. SPEC-3a step 1 states the return-then-deny order and its precedence over the cancel writes, and SPEC-3a step 4 states the reclaim's precedence over the handling replica's releases. This list is the only full statement of the order, and no other proposal site restates it.

1. `terminateUserSessions` lists the user's sessions (`List` with the `UserID` filter) and collects the identifiers of the non-terminal rows.
2. `RevokeUserLeases` enumerates the leases those sessions hold (`LeasesBySession`), calls the credential assigner's `Release` on every lease, and then writes one deny-list entry (`lease.CredentialKey()`) per lease. Every `Release` precedes the first deny-list write, because the deny list's in-process revoke hook `directModeRevocationRotator.onRevoke` rotates every direct-delivery lease it still finds on the credential and would push a fresh key to a revoked session; a per-lease interleaving lets one lease's entry find a later lease on the same pool credential. The step precedes the first cancel write, because once a row is terminal the coordination Sweeper's D6 release and the resume tail can release its binding, which returns its leases and removes their records, and a lease the enumeration no longer finds receives no deny-list entry.
3. For each listed row in turn, the guarded cancel write (the pre-revoke state read on the locked row, `cancelled`, and `MarkTerminated`), then `AfterRevokeWrite` (`CancelResumeAttempt`, then the inbox and DLQ drain). No post-terminal hook runs, and no terminal claim is opened.
4. `runFullRevokeFanOut`: (a) `ReclaimRevokedPreRunning` for each cancelled session whose pre-revoke state is `created`, `finalizing`, or `ready`; (b) `TerminateUserSessions`, which runs `terminateLocal` and then publishes the request to peers, each of which runs `terminateLocal` over its own registry; (c) the token and playground steps, unchanged. The handler then dismisses the user's pending elicitations, unchanged. Step (a) precedes step (b), because `terminalReclaimPreRunning` skips a session bound on this replica only while the registry still holds the binding; after (b) removed it, a reclaim would delete by name a claim the binding release had just patched to `recycling` (row D3b).

**Release outcomes.** `terminateLocal` calls `ReleaseRevokedBinding` for each registry entry of a cancelled session and maps its result into the response: `(true, nil)`, returned when the executor release returned nil, counts one in `podsTerminated`; `(false, nil)`, returned for a non-terminal row, a refused `startRelease` (a D6 or resume-tail release of the session is running, or a terminal writer's claim is open on this replica, which leaves the binding to D6), no binding, a stale binding it evicts, or a binding `releaseReportedBinding` finds replaced, counts nothing; `(false, err)`, returned for a `ReadPrimary` error, a lock-wait error on the bounded call context, or an executor release error, adds the session to `podTerminationFailures`. An executor error leaves no binding to retry, because `PodExecutor.Release` unbinds before the binder runs. `leasesRevoked` is the number of leases step 2 enumerated, a lease whose `Release` failed included. A peer's release and the pre-running reclaim count nothing, and a reclaim error is only logged.

The columns are:

- **Lease record** and **Pool slot**: "step 2" means `Release` removed the record and returned the pool slot. With the in-process assigner the slot is returned to the handling replica's per-replica count, so a lease a peer minted (rows R3, R6, and R7) leaves the minter's count high and the handler's low, the per-replica accounting departure N4 owns. Both assigners remove the record, the Token Service client even when its `RevokeCredentials` call fails, in which case the Token Service's pool count stays until lease expiry (N4).
- **Deny-list entry**: "step 2" means one entry per enumerated lease, published to peers.
- **onRevoke**: the hook runs only with the in-process assigner, on the handling replica and on each peer that applies the published entry. A peer finds none of the session's leases when the replicas share the Postgres lease store; with in-memory lease stores a peer still finds a lease it minted (P5b). Beyond the rows below, it marks each deny-listed pool credential unselectable and rotates every other session's direct-delivery lease on it (C3, owned by P5b).
- **Binding release**: what releases the session's pod binding or its pre-running claim.
- **Claim and slot**: the disposition table row the release takes.
- **Response field**: what the session adds to the response, with n the number of its leases step 2 enumerated.

## Edge cases and accepted failure modes

The SPEC-owned cases are in the spec-changes file. These are the departures and code-level cases.

- **Releases no replica performs (departures).** Each is bounded as follows. An exclusive claim is reclaimed by the claim-orphan GC within `claimOrphanTimeout` plus one sweep interval (defaults 5 minutes and 60 seconds); the GC runs in a chart install since F-4.6.30 closed. A concurrent slot stays counted, which fails closed, until the GC drains a pod that no non-terminal row names or until a Redis reseed; on a pod with continuous sibling traffic that can be the pod's lifetime. A lease row is removed by the expiry sweep, which also expires its deny entry, but the per-replica credential-assignment count is returned only by a process restart until the credential-accounting fix (N4) lands. The cases are:
  - a process exit between the terminal commit and the release (F-4.6.29);
  - the F-10.1.21 residue: the dead-connection eviction, coordinator loss, a failed readopt, and `ReleaseSuspendedPod` stopping between clearing `pod_assignment` and the release;
  - a `failFinalizing` write that commits and reports a store error on any exit other than the plan-parse exit (no hook runs, and the watchdog no longer lists the row);
  - a slot release that still fails when the bounded retry ends (CODE-1 item 5);
  - the exclusive claim of a full_revoke release whose adapter `Shutdown` does not return within `userTerminateRPCTimeout`, which leaves the claim delete on an expired context after the binding is removed (CODE-7 item 5);
  - the claim `claimPod` created when `reserveResumeSlot` fails (N2, row D13, summary Decision 11) or when `StampPodTenant` fails in `Claimer.claimIdle` (row D10);
  - a lease release that is lost.
- **A disposition failure after the member is removed.** The recycle patch or the claim delete fails after the release removed the last member. The release is not repeated (CODE-1 item 5). The claim is left for the claim-orphan GC, or for the recycle missing-report timeout once the claim is `recycling`. This is unchanged from today. A slot release whose script ran and whose reply was lost (a transparent client re-send, or a repeat by `releaseSlotRetrying`) also skips the disposition, because the repeat finds no member, and leaves the claim as a release that removed nothing leaves it.
- **A superseded coordinator's terminal write loses the seal.** After CODE-5, a terminal write by a replica whose binding is stale does not seal through that binding, and the adopter's D6 release runs no seal, so §7.1 **Seal-and-export invariant:** is not met for that case. This is the same loss an off-holder terminal write already has under the F-10.1.33 departure (owner P2), which this case joins.
- **A reservation made during a Redis outage.** The §12.4 Postgres fallback admits without adding a member. After a Redis restart, the rehydration or the session's own release seeds its member (SPEC-1a). When Redis kept its data through the outage, the session's release finds no member and changes nothing. No reseed runs after an outage in which Redis kept its data, so that session stays uncounted, and when it outlives its siblings, the last sibling's release empties the set and runs the occupancy-zero disposition under it.
- **F-7.3.34(b).** A rebuild-branch bind failure is on an exclusive pod, and the drain retires the pod, so the code is not changed.
- **An exclusive recycling pod rebound before a writer's by-name delete.** A peer's D6 recycles a `/start` binding of a pre-running session and a successor rebinds the pod before the writer's hook deletes the claim by name. The case predates this proposal, is narrow, and recovers through the successor's own failure path. Closing it needs session identity on the claim, which this proposal does not add.
