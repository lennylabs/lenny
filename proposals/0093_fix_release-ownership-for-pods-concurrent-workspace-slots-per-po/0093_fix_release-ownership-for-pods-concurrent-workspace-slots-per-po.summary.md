# Summary: Release ownership for pods, slots, per-pod claims, and credential leases at and after a terminal write

## Summary

**Problem statement.** Several gateway paths release a pod, the per-pod SandboxClaim `claim-<podName>`, a concurrent-workspace slot, or a credential lease at or after a session's terminal write, and no terminal path has a single owner for those releases. Some releases hit the wrong target. On a concurrent-workspace pool, a DELETE, a terminate, or a watchdog timeout of a session that has not started deletes the shared per-pod claim, and the WarmPoolController then drains the pod and ends every live sibling session. The finalize failure exits and the created sweeper delete the same claim by name, a superseded coordinator releases a pod a peer adopted, and full_revoke sends an unfenced `Shutdown` that a later release repeats. Other releases never happen: a pre-running slot reservation has no slot-aware releaser, a failed slot release is not retried, full_revoke removes lease records without returning pool slots, and a process exit between the terminal commit and the release leaks the claim, the slot, and the leases. Making the pre-running release slot-aware over today's decrement-only slot counter double-decrements on paths the tree already has, and an under-count that reaches zero deletes the shared claim under live siblings. The spec also lists no gateway session-end claim delete in its SandboxClaim writer sets.

**What changes.**
- Slot occupancy register: `REG-SLOTCOUNT` becomes a per-pod set keyed by session, with an idempotent keyed release and an occupancy-zero disposition gated on the removing release (SPEC-1, CODE-1). The per-pod keys carry the pod identifier as a Redis hash tag, the failure funnel clears `pod_assignment` so one slot-holder predicate holds for every reader of the session rows, and the slot sets recover after a Redis outage as the non-spec **Slot-set outage recovery case table** states (CODE-1).
- Pre-running releases: one slot-aware `Binder.ReclaimClaimed`; the finalize exits and the deleted created sweeper stop deleting a claim by name; the SandboxClaim writer set in §4.6.3 names the delete by a release that ends the occupancy without reuse, and the sites that contradict it point at it (SPEC-2, CODE-2, CODE-3, CODE-4). The non-spec **SandboxClaim end-of-occupancy disposition table** states the claim and slot effect of every gateway release path.
- Post-terminal hook: a stale-binding step before the seal, and the slot-accounting lock on the release step (CODE-5, CODE-6).
- full_revoke: leases return to their pools at the deny-list step, and each cancelled session is released through the pre-running reclaim or the D6 release body, as the non-spec **full_revoke release table** states; §11.4 states the release and drops the `USER_REVOKED` reason (SPEC-3, CODE-7).
- Release failures: the non-spec **Release-path failure-outcome table** states what every release path does when one of its steps fails.
- Reader pages, code comments, and generated descriptions that state a retired end-of-occupancy outcome (DOCS-1, CODE-8).
- Tests across tiers 1, 2, 3, 4, 5, 7a, 8, 9, and 11 (TEST-1 and the per-deliverable tests), and the BUILD-GAPS records (REC-1).

**Decisions.**
1. The design is the minimal one: one idempotent slot-release primitive, a slot-aware `ReclaimClaimed`, deletion of the side releasers, a hook stale-binding step, a hook release lock, full_revoke through the existing releasers, and departures for releases no replica can perform. It adds no RPC, proto field, column, table, session state, or error code, and its one loop is the slot-set recovery probe of Decision 21.
2. `REG-SLOTCOUNT` keeps its key and register identifier and changes its value to a Redis set. A parallel `released_slots` key was rejected because it is lost on a Redis restart, after which a duplicate release under-counts toward a false zero, and because it grows by one member per session with no TTL.
3. The occupancy-zero disposition runs only when the release removed the session's member and left the set empty, so a duplicate release while Redis keeps the set, and a release of a member rehydration already dropped, never patch or delete a claim.
4. The pool-kind discriminator is `row.ScrubPolicy == "best-effort-per-slot"`, which is frozen at create and set under the same condition that selects `ClaimSlot`; a live pool lookup was rejected because `maxConcurrentSessions` can change after create.
5. The exclusive pre-running branch stays a by-name delete with no precondition, because that delete drains the pod, apart from the pre-projection departure (non-spec **Accepted-departure register** row A15), and `commitStart` refuses after a terminal write.
6. F-10.1.28 and F-11.4.11 are closed on the gateway side with D6's generation predicate. The pod-side `Shutdown` generation fence stays with R16 under its existing UNWIRED claim-register row, because pulling it in requires restaging `Binder.Release` and taking C2.
7. Missed releases get no durable pending-release record and no reconciler; each is a departure with a bound in the non-spec **Accepted-departure register**.
8. full_revoke returns each lease at §11.4 step 1 through the credential assigner's `Release`, because removing the lease record rejects the token on every replica through the lease store, whatever happens to the deny-list publish or the binding replica, and `Release` returns the pool slot that a bare record removal strands. The order of the step and the response accounting are the non-spec **full_revoke release table**'s.
9. §11.4 step 2 drops `USER_REVOKED`, because the adapter never reads `ShutdownRequest.reason` and threading it through the release path would change four signatures for a value nothing observes.
10. F-5.2.49 is fixed by a bounded detached retry of counter failures only, which is safe because the keyed release is idempotent.
11. N2 gets no code change, because a sibling can reserve onto the freshly created claim before the failed resume reservation, so a by-name delete is unsafe.
12. F-7.3.34(b) gets no code change, because the rebuild-branch drain retires the exclusive pod.
13. `revokeFinalizeLease` and its call sites stay unchanged. F-4.9.35 closes as resolved by 0092's D7, because `finalizing` exits only to the finalize handler's own ready write or to a terminal state.
14. The hook's release step waits on `slotAccountLocks` instead of the funnel deferring to an open terminal claim, because a deferral drops the failure from the §5.2 replacement trigger and leaks the binding when the terminal write loses.
15. The hook's stale-binding step evicts the binding without a binder call for every `fromState` from `running` onward, the list CODE-5 item 2 gives. A stale binding with a resume-family `fromState` exists only on a replica that lost a running-state takeover, and the adopter's failure funnel released that pod when it wrote `resume_pending` or `awaiting_client_action`, under the slot-accounting lock and before any `resuming` write, so a release there repeats the adopter's.
16. The per-pod keys carry the pod identifier as a Redis hash tag (`lenny:pod:{<pod>}:active_slots`, `:rehydrated`, and `:rehydrating`), which the §12.4 spelling `lenny:pod:{pod_id}:*` already reads as, so every multi-key script and `Counter.Reset`'s `DEL` stay in one Redis Cluster slot (CODE-1 item 7). The owner decided it on 2026-10-18, because the chart ships a Redis Cluster provider and §12.4 requires Redis Cluster at Tier 3, while the untagged keys fail those calls with `CROSSSLOT`. No key migration runs: the renamed keys start absent and rehydrate from the session rows, and the old keys are never read again. The rename also retires the stale string-key cleanup that the set's value type would otherwise need on standing test clusters.
17. Existing spec text does not suffice. A slot-aware reclaim over the decrement-only counter double-decrements after a failed `/start` followed by DELETE and after a hook reclaim followed by a peer's D6 release, and an under-count that reaches zero deletes the shared claim under live siblings. §5.2 specifies the counter's script, so the idempotent keyed release is a spec change.
18. Scope boundaries: P5b owns the full_revoke deny-list granularity (C3), the full_revoke session set and listing, and the remaining halves of F-11.4.10, because the owner split P5 on 2026-10-16 (0094 decision D20): 0094 covers the lifecycle fence, the session drain, the durable erasure job, and the removal of the `DELETE /v1/responses/{id}` route, and changes no full_revoke code. P3 owns the retention of the `failed` rows the watchdog now leaves and the created-expiry state mismatch; R16 owns S16, S17, and the generation checks on operational RPCs; F-7.1.30 owns the session-end order. The edits to `cmd/lenny-gateway/user_revocation.go` and the full_revoke handler land before P5b's.
19. full_revoke holds each listed session's terminal claim (the existing `terminalClaims` record, through `BeginTerminal`) from before its cancel write until the pre-running reclaim has run, so the handling replica's own Sweeper cannot release a pre-running binding first and leave the reclaim to delete a `recycling` claim by name. The record is per replica and a process exit drops it with the bindings it fences, so it adds no state that cannot be lost.
20. `Binder.Release` makes its claim writes on `detachedReleaseContext`, so a caller context that ends during the best-effort `Shutdown` no longer leaves an unbound claim to the GC.
21. When a Redis outage ends, the gateway rebuilds the slot sets through the §5.2 blocking rehydration before fast-path enforcement resumes, as §12.4 requires and SPEC-1d keeps. The owner decided on 2026-10-18 that the gateway runs this rebuild, that the rehydration merges (SPEC-1b: it adds the rows' identifiers and keeps every member already present), and that the rebuild replays from each replica's outage ledger the releases that failed during the outage. The non-spec **Slot-set outage recovery case table** states each case, CODE-1 item 8 states what to build, and register rows A26 to A28 state the residue. Register row A27's cases were accepted by the owner on 2026-10-18. A replacing rebuild was rejected because it drops `leaked:` members and in-flight reservations once per observing replica; a rebuild on the admitted session's next slot call, because that call is the session's own release; a rebuild at gateway start, because it runs on every rollout and cannot see the admissions of the process that exited; and a Postgres check before each occupancy-zero disposition, because it adds a store read to the emptying release and still lets the pod admit over its cap.
22. A session holds a slot on pod P exactly when its row is non-terminal and names P. The predicate is stated once, as the non-spec **Slot-holder predicate**, and every reader of the session rows cites it. The owner decided on 2026-10-18 that the failure funnel clears `pod_assignment` in its `resume_pending` and `awaiting_client_action` edge writes (CODE-1 item 9), as the suspension release already clears it, because the funnel released the slot while the row kept naming the pod, so the rehydration seed, the fallback gate, the rebuild's replay filter, and the orphan GC counted a session that held no slot. No reader needs the failed pod's name, because a resume claims a fresh pod. Narrowing the seed and the queries to slot-holding states was rejected, because the same query feeds the fallback gate and the GC, and a second predicate would need its own cases.

**Watch out for.**
- The non-spec **Release-path failure-outcome table** is the only rule site for what a release path does when one of its steps fails. A change to a failure outcome starts at its row, then the register row and the tests that cite it; no other site restates an outcome.
- The non-spec **SandboxClaim end-of-occupancy disposition table** is the only statement of which release deletes, patches, or leaves the claim. A change to that disposition starts at the table, then SPEC-2c, then the pointer sites. A universal that covers every acquisition undo is wrong for the CREATE loser, whose withdrawal must leave the winner's claim intact (row D8).
- The leaked arm of the release script adds the `leaked:` member whether or not `SREM` removed one. Gating it on the removal looks tidier and loses the leak after a clean pre-running reclaim, which fails open.
- `SlotClaimer.ReleaseSlot` must gate the disposition on `removed`. A gate on `remaining == 0` alone re-runs the disposition when a duplicate release finds the set already empty.
- A disposition error after the member is removed must not be retried (failure-outcome table row F2).
- The non-spec **Accepted-departure register** is the only rule site for accepted departures: each departure's bound, BUILD-GAPS record, doc site, and pinning test. A new or changed departure starts at its row; REC-1, DOCS-1, and TEST-1 follow it, and no other site restates a bound.
- The non-spec **Slot-set outage recovery case table** is the only rule site for how the slot sets recover when a Redis outage ends. A change starts at its row, then CODE-1 item 8, the register rows, and the tests. A rehydration that replaces the set looks simpler and drops `leaked:` members and in-flight reservations at every outage end.
- Register row A27 lists exactly the cases the owner accepted on 2026-10-18. Do not add a case to A27, or widen a case, without asking the owner; a new residue gets its own register row and an owner decision.
- The non-spec **Slot-holder predicate** is the only statement of which sessions hold a slot. A new path that releases a slot while the row stays non-terminal must clear `pod_assignment` in or before its release, or the rehydration adds the session again. A path that names a pod on a row (`persistPodAssignment`, the resume commit) must not name it on a recovery-state row.
- The non-spec **full_revoke release table** is the only full statement of full_revoke's order and response accounting. A change to either starts at that table, then SPEC-3.
- The unconditional `revokeFinalizeLease` in `finalizePrepareFailed` looks redundant after CODE-3 and is the only lease return when `failFinalizing` commits and reports a store error.
- Holding `slotAccountLocks` across the seal looks safer and blocks the failure funnel for up to the seal window.

## Goals

- No terminal write of a session that has not started deletes the claim of a live sibling on a concurrent-workspace pool.
- Every slot reservation is returned once, however many paths release it, and every leaked slot stays counted, apart from the rehydration departures in the non-spec **Accepted-departure register**.
- Each resource on each terminal path has one releaser, as the non-spec resource-to-owner table states.
- The spec states the slot set and its keyed release, the gateway's claim delete by a release that ends the occupancy without reuse, and the full_revoke release.
- Every release no replica can perform is recorded as a departure with its bound, record, doc site, and pinning test in the non-spec **Accepted-departure register**.
- The tests cover every writer, path, and state the change touches, with randomized interleavings, fault injection, and invariant checks.

## Non-goals

- **A §7.3 rule naming the only paths that return a session's leases.** Existing text already makes both code defects defects (§6.1, §7.3 **Credential leases on the replacement pod.**, §11.4 step 6), and an exclusive list would forbid the terminal-handling lease release that §7.2 and §6.2 require and the assignment-failure and renewal removals in the tree.
- **A §10.1.1 statement of when a pre-running start acquires `REG-COORDLEASE` (S17).** No release in this design depends on it, a correct statement also has to cover the delegated-child `created` acquisition and the Sweeper renewal of a bound `ready` row and co-edit three §29 rows, and R16 already edits the same §10.1.1 bullet for S16. It goes to R16 with S16, or is filed as a standalone spec gap.
- **A parallel `released_slots` key in front of the counter.** It is lost on a Redis restart and grows without bound; Decision 2 replaces it.
- **A sorted set scored by reservation time, rebuilt when full, with a grace tunable.** A rebuild from rows drops in-flight create and resume reservations unless a timing grace covers them, which is a new tunable and a fail-open risk.
- **Rehydration as the slot backstop for missed releases**, by clearing the `rehydrated` flag or by a periodic reseed. A rehydration removes no member, so it cannot return a slot a release missed. The one rebuild the design runs is §12.4's after a Redis outage (Decision 21).
- **A durable pending-release record** (a column, a table, or a Sweeper adoption of terminal rows). Each adds a migration, a writer at every terminal write, and a completer, while the GC, a counted slot, and lease expiry already bound the cases.
- **The pod-side `Shutdown` generation fence.** It needs `Binder.Release` restaged so `Shutdown` runs before the claim and lease effects, and it is registered UNWIRED with deferral R16.
- **Restaging `Binder.Release` and the lease-before-`Shutdown` half of C2.** C2 is conditional on a restage, which this design does not do, and F-7.1.30 keeps the session-end order.
- **Hoisting `REG-COORDLEASE` to `/start` entry and gating the hook's release on it.** With a keyed release a duplicate is harmless, and the hoist adds a release on every failure exit and a stuck-lease trap on a `ready` row.
- **Keeping the reservation on a failed `/start` and clearing `pod_assignment` when the slot leaks.** It arbitrates ownership that the keyed release makes unnecessary and changes `/start` retry semantics.
- **A UID or `resourceVersion` precondition, or a Postgres owner check, on the exclusive claim delete.** The pre-running exclusive delete drains the pod, apart from the pre-projection departure (register row A15), a sibling reservation does not write the claim, and an owner check breaks the bind-failure callers whose row still names the pod.
- **Session identity on the SandboxClaim.** The concurrent claim is shared, and §4.6.3 keeps the session binding on the Postgres row.
- **Exclusive pools on the slot set with a cap of 1.** It adds a Redis dependency and the §12.4 fallback to every exclusive claim and release.
- **Resolving the pool kind by a live lookup or `ResolvePool`.** Decision 4.
- **A pre-running `Shutdown` before the concurrent slot release.** A pre-running concurrent session holds no pod-side workspace unless a `/start` is in flight, and that start is released by D6.
- **Resuming through `SlotClaimer.ClaimSlot` to fix N2, or deleting N2's claim when the reservation fails.** The first changes resume placement onto sibling-occupied pods; the second is unsafe (Decision 11).
- **A `ShutdownReclaim` before the rebuild-branch drain.** Decision 12.
- **Threading `USER_REVOKED` through the release path.** Decision 9.
- **A new §7.1 **Session release.** paragraph, a §4.7.1 gate, and a §10.1.5 item.** §7.2, §7.3, and D6 already state the two release forms, and the fence clauses belong to R16.
- **Keeping the created sweeper with a state predicate.** Two writers for one deadline is the defect, and the watchdog's guarded write and the hook own the deadline.
- **Keeping the finalize store-error reclaim on the ready-write exit, with or without a re-read.** When the ready write's outcome is unknown, the reclaim can end a committed `ready` session's pod.
- **A per-session tombstone key with a TTL.** The TTL bounds idempotency while the duplicate window has no fixed bound, and the key blocks a legitimate re-reservation.
- **Forwarding a release to the binding replica over pub/sub.** 0092's Sweeper already hands every bound terminal row to the holder, and a forward is not durable.
- **Moving every claim delete to the controller GC.** It adds up to `claimOrphanTimeout` to every session end and breaks the gateway-coordinated recycle disposition.
- **Reassigning F-10.1.28, F-11.4.11, and the full_revoke halves to R16 or P5b.** The validated scope keeps the mechanism of release in P1.
- **S16** (the coordination lease and mirror row at a terminal write). R16 owns it.
- **The members the problem statement moved out**: the credential-accounting findings (N4, F-4.9.32, F-4.9.34, F-4.9.37), F-4.9.33, F-10.1.30, F-10.1.32, F-5.2.50, and the deny-list and session-set halves of F-11.4.10 with C3.

## Defects in the shipped tree that this proposal does not stage

- **A retried `/start` materializes an uncounted slot.** `BindReservedSlot` releases the reservation on a failed `/start` while the row stays `ready` with its pod, so a retry binds without a reservation. The fix changes `/start` retry semantics, which is outside release ownership. REC-1 files it.
- **`Counter.Reset` has no production caller**, so the §10.1.4 whole-pod reset does not run. It belongs with the whole-pod connection-loss reaction. REC-1 files it.
- **Token Service pool counts are per replica (N4).** A release that reaches the wrong replica, or a Token Service restart, drifts the counts. The credential-accounting proposal owns it.
- **Created-state expiry ends `failed` with `CREATED_TIMEOUT`, while §15.1 names `expired` and §7.2 has no timeout edge out of `created`.** The mismatch predates the created sweeper's deletion and belongs to P3. REC-1 files it.
- **§10.1.1 says a `created` or `ready` session holds no coordination lease**, while `/start` acquires the lease on a `ready` row, delegated-child materialization acquires it on a `created` row, and three §29 rows say no acquisition point is stated (S17). It goes to R16 or a standalone spec proposal.
- **full_revoke deny-lists a pool credential without the user** (the deny-list half of F-11.4.10, C3). P5b owns it. After CODE-7, step 1 also returns each such lease to its pool through `Release` while the same step deny-lists the pool credential. With the in-process assigner the deny list's revoke hook marks that credential unselectable for every user; with the Token Service, which wires no hook, the pool can hand the returned slot to a new lease on a credential every replica rejects. P5b's granularity change settles both.
- **`Claimer.claimIdle` leaves a `bound` claim when `StampPodTenant` fails (disposition table row D10).** The non-spec **Accepted-departure register** row A7 records it, with its bound and record.
- **A full_revoke cancel write that commits and reports a store error leaves the row outside the fan-out (register row A25).** `pgtenant.InTx` returns `pgtenant: commit: %w` when `Commit` fails (pkg/gateway/storage/pgtenant/pgtenant.go:99), `terminateUserSessions` then returns before it adds the row to the IDs it returns (pkg/gateway/externalapi/admin/users.go:491), and a repeated full_revoke skips the row because it is now terminal (users.go:474). Under CODE-7 the row stays `cancelled` outside the set **Order** step 3 returns, so a pre-running row with no binding on any replica has no releaser. The proposal stages no fix because the row's leases are already returned and deny-listed at **Order** step 2 and the orphan GC bounds the residue, as it does for the commit-then-error departures A3 and A24. A re-read after the error runs on the failing store and cannot tell this cancel from another writer's, and a duplicate by-name reclaim of a row another writer cancelled can delete a successor's exclusive claim (register row A21). The non-spec **Accepted-departure register** row A25 records it, with its bound and record.
- **Other gateway and ops Redis stores issue multi-key commands across hash slots.** On the chart's Redis Cluster provider these fail with `CROSSSLOT`, or with go-redis's client-side `ErrCrossSlot` for a transaction: the lenny-ops coordination lock scripts and transaction over `ops:lock:<scope>` and `ops:lockidx:<id>` (`pkg/ops/coordination/redisstore/redisstore.go`); the semantic cache's entry-and-index transaction, `MGET`, and batch `DEL` (`pkg/gateway/llmproxy/semanticcache/redisstore/redisstore.go`); the playground session record's transactions over the session, fan-in, user, and revocation keys (`pkg/gateway/mcpfabric/playground/sessionrecord.go`); the circuit-breaker `MGET` (`pkg/gateway/middleware/circuitbreaker/breakerstore/redisstore/redisstore.go`); the quota store's sliding-window `MGET` and batch `DEL` (`pkg/gateway/quota/quotastore/quotastore.go`); and the batch `DEL` in `pkg/gateway/storage/leasestore/leasestore.go` and `pkg/gateway/experiment/experimentsticky/experimentsticky.go`. The `t:{tenant_id}:` keys are written without braces, so §12.4's statement that the prefix hashes a tenant's keys to one slot does not hold in the code. These stores are outside release ownership, and CODE-1 item 7 fixes only the slot counter. REC-1 files it.
- **A full_revoke cancel write that commits and returns a store error skips `AfterRevokeWrite`** (`terminateUserSessions` returns before it, `pkg/gateway/externalapi/admin/users.go`), so `CancelResumeAttempt` and the inbox and DLQ drain do not run for that row. No other path drains a terminal session's inbox and DLQ: the inbox and the DLQ keys carry no TTL, the watchdog's DLQ sweep lists only recovery states, and the other `drainMessagingOnTerminal` callers run only on a later message or a suspension release. The release residue of the same row is register row A25. The messaging residue predates this proposal and belongs to P5b, which owns the full_revoke session handling. REC-1 files it.
- **The usage rollup derives `podMinutes` from the row's current `pod_assignment`** (`resultrollup.usageFrom`), so a session that ends without naming a pod reports zero pod minutes. A podless suspension already ends that way, and after CODE-1 item 9 a session that ends from a recovery state does too. §8.8 defines no `podMinutes` rule beyond its examples. REC-1 files it.
- **Races the disposition table does not close**, listed in the non-spec disposition table's **Races the table does not close** and recorded in the **Accepted-departure register**.
