Lenny is at an **early, pre-release stage**. There is no tagged release, and no binaries, container images, Helm chart, Homebrew formula, or SDK packages are published; the platform is built from source. The [technical specification](https://github.com/lennylabs/lenny/tree/main/spec) drives implementation under a spec- and test-driven workflow. The documentation throughout this site describes the **target surface**: the platform as it stands once the plan below is complete.

This page first states the plan toward the first release, milestone by milestone, with the share of each milestone's work that has landed. It then lists the work planned after the first release. Last, it tracks which platform surfaces are wired up today, so readers can tell which parts of the docs describe running code and which parts describe work ahead.

## Planned after v1

The work below is planned for after the first release and is outside the v1 program. The data models and interfaces of the first release leave room for each item, so adding it does not change their schemas.

- **A2A protocol support.** The gateway serves the Agent-to-Agent (A2A) protocol: an A2A task creates a Lenny session, each runtime's published interface generates its A2A agent card, A2A callers receive push notifications as the session progresses, and external A2A agents are callable through delegation.
- **A2A inside the agent pod.** A runtime that opts in serves its own A2A endpoints inside the pod, and the gateway proxies all A2A traffic to and from it.
- **Agent Protocol support.** A further client protocol adapter serves the task and step endpoints of the Agent Protocol (AP).
- **Further conversational patterns.** Threaded messages, multiple participants, non-linear context retrieval, broadcast, and external agent participation. The message envelope already carries the `id`, `from`, `inReplyTo`, and `threadId` fields these patterns use.
- **Environment management UI.** A web UI browses environments, edits their membership, and previews which runtimes and connectors a selector matches. It is a thin client of the admin API, whose dry-run preview ships in the first release.
- **Finer environment controls.** Richer controls for delegation across environments, runtime-level exceptions at a finer granularity, and delegation boundaries scoped to an experiment.
- **Multi-cluster federation.** Sessions and connectors span several clusters. Session IDs are globally unique, and the storage interfaces assume no single-cluster topology.
- **Web portal.** A web portal consumes the admin API as a thin client, in the same way `lenny-ctl` does.
- **SSH Git URLs for workspace sources.** A `gitClone` workspace source accepts SSH URLs, authenticated with an SSH key mounted into the pod in place of the HTTPS credential lease. In the first release, `gitClone` accepts HTTPS URLs only.
- **External execution hosts.** An agent that runs outside Lenny, such as a wrapper on a developer's machine working on an existing checkout, uses Lenny for runtime discovery, policy, and delegation into sandboxed children. The plan adds a public runtime execution manifest (`GET /v1/runtimes/{name}`), an external session mode (`executionMode: external`) in which a caller heartbeat replaces the pod, and an event ingest endpoint (`POST /v1/sessions/{id}/events`) that feeds the same transcript and audit pipeline as pod-backed sessions.
- **Community runtime registry.** Runtime authors publish versioned adapter packages to a registry, and operators discover and install them from it. The [contributor guide](contributing.html#community-runtime-registry) describes how runtime adapters are distributed until then.

| Surface | Status | Notes |

## How this page is maintained

- The plan section is generated from the programs under [`changes/programs/`](https://github.com/lennylabs/lenny/tree/main/changes/programs) and the status of each step by `python3 scripts/changes/changes.py status-page`. Edit the program and regenerate the section, rather than editing it by hand; a static check fails when the section no longer matches the programs and the steps.
- The plan changes whenever the program does. Milestones and their order shift as implementation surfaces new constraints, so treat the plan as a plan rather than a commitment.
- The list under "Planned after v1" is written by hand. An item leaves it when a program takes it up.
- The surface tables are written by hand. Updates land with the work that changes a surface's status, rather than in a separate pass. Update the "Last updated" date under "Platform surfaces today" with each change.
- When a surface reaches "Shipped," link to the specific documentation page that describes the shipped behavior.
