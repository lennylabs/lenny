# Close test gaps

This skill closes OPEN findings in `TEST-GAPS.md`, the spec-vs-test coverage audit generated by a fan-out review and reconciled periodically against spec and test churn (see `tmp/test-gaps/audit-workflow.js` and `tmp/test-gaps/reconcile-workflow.js`, both gitignored scratch tooling). Unlike `implement-proposal`, most TEST-GAPS findings describe a missing test rather than a spec contradiction, so there is no proposal-approval gate: the default path is straight to writing the test. A minority of findings turn out, on re-verification, to describe an actual implementation or spec defect; those are left OPEN with the specific open question recorded directly on the finding (or flagged for the `change-proposal` pipeline when it is a spec gap) instead of being closed with a test that would pin broken behavior. This skill does not use `bd` or any other external issue tracker; TEST-GAPS.md is the only durable record.

A category is one theme or one spec section/area — the scope granularity `remainingOpenInScope` is tracked against. One branch carries a whole category: the first batch creates it, every subsequent batch for that category passes the same `branch` argument and continues on it, and it stops accumulating only when the category is exhausted (`remainingOpenInScope` reaches 0, meaning every closable finding is resolved and everything left is `needs-human`, annotated in place). At that point the branch merges into the parent branch and is deleted; the next category starts a fresh branch. This differs from `close-build-gaps.sh`'s one-shot batches because a TEST-GAPS category is usually small enough (a handful to a few dozen findings) that carrying it across batches on one branch, then merging once, produces a cleaner integration history than a merge per batch — see `.claude/rules/git-workflow.md` on keeping branches short-lived and merges meaningful. Work categories in theme-first order (standards conformance, user journeys, deployment combos, adversarial paths, integrated testbeds, then per-spec-section findings), severity-first (High, then Medium, then Low/Info) within each. This skill does not use an external issue tracker: TEST-GAPS.md itself, plus each category's git branch while it's in flight, is the durable record of progress and open questions.

**Merging is not automatic.** The workflow itself never merges or pushes (see Hard constraints). Merging a category's branch into the parent, once exhausted, is done by whoever is driving this skill (a human, or an agent session that has standing authorization to do so for this specific initiative) — it is not something a fresh invocation of this skill should do without that authorization, since merging into a long-lived branch is exactly the kind of action `.claude/rules/git-workflow.md` and the harness's own safety checks expect a human or an explicitly-authorized session to perform deliberately, not something to infer from this file alone.

## Preconditions

1. `git status --porcelain` must be clean on the branch you are cutting the category branch from (the workflow's Select step creates `test-gaps/<scope>-<n>` off it on the category's first batch).
2. Prefer running this after `TEST-GAPS.md` has been reconciled against recent spec/test churn (check its "Methodology and scope" section for the most recent reconciliation date/commit range). Closing against a stale file wastes effort re-discovering already-fixed gaps; if the file looks stale, run `tmp/test-gaps/reconcile-workflow.js` first (or re-run it scoped to the section via `{args: {only: [...]}}`).
3. Decide `scope` for this category: `theme:T-STD` / `T-JRN` / `T-DEP` / `T-ADV` / `T-BED` for a cross-cutting theme, `section:X.Y` or `section:X` for a spec subsection or whole section, or `all`. Per the theme-first, severity-first order, work the five themes before the per-spec-section findings, and High before Medium before Low/Info within each.
4. **The workflow runs in the same checkout as whoever launches it — no worktree.** Its Select step checks out the category's branch in place (fresh on the first batch, an existing one on every later batch of the same category via the `branch` argument), so the checkout's current branch changes to it for the run's whole duration. Do not run `git checkout`/`commit`/other mutating git commands (or start a second `close-test-gaps` batch) against this checkout until the run completes; the launching session should wait for the completion notification before touching the working tree again. This is a single, sequential branch by design (findings within it are gated one at a time — see below), so it needs no parallel-execution isolation; it only needs the launcher to leave the checkout alone while it runs.
5. **Before launching a batch for a category that already has a branch in progress, pass that exact branch name as `branch` in the args.** Launching without it mints a brand-new branch that starts from the current state of the parent — which, if the category's prior batches haven't been merged yet, does not yet reflect their resolved/escalated findings, so Select re-selects and redoes already-finished work from scratch. This is not a hypothetical: it is exactly what happened the first time this skill ran a second batch on an unmerged category.

## Hard constraints

- One category, one branch. Every batch for a category passes the same `branch` argument and lands on it; a batch invoked without `branch` starts a new category's branch, never a continuation of one already in flight (see Precondition 5). The workflow itself never merges into a long-lived branch or pushes. Merging happens once, after the category is exhausted, by whoever has standing authorization to do so for this initiative (see the note in the section above) — not automatically, and not inferred by a fresh session from this file alone.
- Every closed finding is gated by an independent verifier, not the implementer's self-report: the verifier re-runs the tier, confirms the test would fail against the pre-fix code (not just line-coverage padding), and confirms the `// spec:` (and `// diagnosis:` for tier2+) annotations are present.
- No infra-unavailable defers. Kind, envtest, and the compose stack (Postgres/Redis/MinIO) are available locally; stand them up (`lenny-test infra up --profile compose|kind`) rather than skipping a finding for "missing infrastructure," mirroring `close-build-gaps.sh` rule P. A finding may still legitimately need a resource genuinely absent locally (a paid cloud account, gVisor/Kata nodes, a live external SaaS) — record that as the finding's own `Dependencies` field rather than silently dropping it from a batch; do not select it into a batch this skill can't actually finish.
- TEST-GAPS.md edits happen only in the Select step (housekeeping resolutions found in passing), the mark-resolved step, and the annotate-needs-human step, all single-writer, to avoid concurrent edits to the same file from the per-finding loop.
- Findings within a batch are implemented sequentially, not in parallel, because they share the working tree and a common `tests/spec-map.json`/`tests/change-graph.json` — the same reason `implement-proposal-build` runs its steps in order.
- No `bd` (Beads) or any other external issue tracker. Unlike the rest of this repo's workflow, this skill never files, claims, or closes a `bd` issue; TEST-GAPS.md's own finding format (including the `**Needs human input:**` annotation for `route="needs-human"`) is the only durable tracking surface it uses.
- No non-durable identifiers in shipped artifacts, mirroring `implement-proposal`'s rule against leaking a proposal's internal scaffolding labels: new test code, test names, and comments cite only a spec section (`// spec: §X.Y`) or describe the behavior in prose. A TEST-GAPS finding id (`T-X.Y.N`) is this audit's own scratch-tracking label, not a durable spec identifier — it gets renumbered, rewritten, and resolved across reconciliation passes (see `tmp/test-gaps/reconcile-workflow.js`) — so it belongs in TEST-GAPS.md and nowhere else: never in code, test names, comments, or commit messages. The independent verifier checks for this on every finding, not only `needs-human` ones.

## A test that fails against current code: the decision tree

Writing a spec-derived test and finding it fails against current code does not, by itself, mean the product is wrong. The workflow's Close phase (`.claude/workflows/close-test-gaps.js`, `implementPrompt`) works through a fixed order before touching any product code:

1. **Write the test from the spec text itself**, quoting the exact sentence the assertion comes from — not from the finding's paraphrase, which can itself be a slightly off summary.
2. **Run it against the unmodified code first.** If it passes, the gap really was just missing coverage: `route="test"`, done, no code touched.
3. **If it fails, second-guess the test before the code.** Re-read the cited spec sentence character by character and ask whether the assertion is a faithful reading — not stricter, not looser, not a detail borrowed from a neighboring section. If the test itself was wrong, fix the test (never the code) and re-run. A verifier independently re-reads the spec too, specifically watching for the failure mode where a test gets quietly watered down to match whatever the code currently does instead of what the spec requires.
4. **Only once the test is confirmed correct does a real defect get considered.** Before any code change: enumerate the blast radius (every call site, test, and doc that depends on the current behavior), and check the surrounding spec and `proposals/` for a reason the current behavior might be intentional.
5. **A code fix lands only when spec alignment is unambiguous on all three counts** — the spec requires the new behavior, nothing else contradicts it, and the blast radius is fully enumerated — and only after a **full regression pass** (`lenny-test --changed` with no `--max-tier` cap, so every tier the change graph reaches runs, not just the finding's own tier) comes back green. The independent verifier re-derives the spec alignment itself and re-runs the full regression pass itself; it is explicitly allowed to veto a fix it cannot independently justify, even one the implementer reports as green, by rejecting with `forceRoute="needs-human"`.
6. **Whenever spec alignment is not 100% clear** — the spec is silent or contradictory, the blast radius is uncertain, or the surface is foundational enough that the wider effect isn't clear — **no product code is touched.** The workflow reverts any exploratory edits and records the specific open question directly on the still-OPEN TEST-GAPS.md finding (a `**Needs human input:**` field; no external issue tracker). This is `route="needs-human"`, and it is also where a verifier veto on a proposed code-fix lands (the workflow reverts that fix and re-routes to needs-human rather than leaving an unverified change on the branch).

## Procedure

### Step 1: Preconditions (inline, before the workflow)

Confirm the preconditions above. Resolve `scope` and `batchSize` (default 6) from the arguments. If a branch for this category is already in progress (Precondition 5), resolve its exact name too.

### Step 2: Run the workflow

The script lives at `.claude/workflows/close-test-gaps.js`, invoked by name or path. First batch of a category:

```json
{
  "scope": "theme:T-STD",
  "batchSize": 6
}
```

Every later batch of the same category, once its branch exists:

```json
{
  "scope": "theme:T-STD",
  "batchSize": 6,
  "branch": "test-gaps/theme-t-std-1"
}
```

Agents inherit the session model and effort level; run this skill with a strong model at high effort given the amount of independent verification involved.

### Step 3: Interruptions

**A terminal API error mid-batch (rate/usage limit, auth expiry) no longer crashes the run.** The Close loop detects an `agent()` call returning `null` (the harness's signal for a terminal error after retries), stops processing further findings in that batch immediately (a terminal error like a usage limit almost always recurs on every subsequent call in the same run, so trying the next finding would just fail the same way), and still runs Mark-resolved/Annotate/Verify on whatever the batch completed before the error — so already-finished, already-verified work is not lost. The result's `abortedOnTerminalError` (boolean) and `batch.aborted` (array of finding ids left completely untouched, no annotation, ordinary OPEN) tell you this happened. When `batch.aborted` is non-empty: fix the underlying cause first (re-authenticate, wait out a rate/usage-limit reset), then simply launch another batch with the same `branch` argument — Select will naturally re-offer the aborted findings since they were never touched.

**If the run crashes outright anyway** (a bug, not a handled terminal error) with real, uncommitted work sitting in the checkout from an in-flight finding the crash interrupted mid-implementation: that work never went through this skill's independent-verifier gate (a separate agent re-deriving green and spec-alignment, not the implementer's own say-so), so it has not earned a commit — inspect it (`git status`, `git diff`) and discard it (`git checkout -- <files>`, remove untracked new files) rather than commit or mark a finding resolved from it yourself, even if it looks complete; let a future batch attempt it fresh through the normal implement-then-independently-verify flow. Stop the stale task with `TaskStop`, then relaunch with `{scriptPath, resumeFromRunId}` from the original tool result if resuming makes sense, or a fresh invocation with the same `branch` argument otherwise. The Select step's branch creation and the per-finding commits are real git state, so a resumed run should `git log` the branch first to see what already landed before trusting a re-run of Select (which will pick a fresh, non-overlapping batch rather than re-selecting already-closed findings, since it re-checks OPEN status from TEST-GAPS.md).

### Step 4: Report

1. Report the branch name, `resolvedInPassing` (findings the Select step found already satisfied), the batch's `resolvedCount` (broken out by `test` vs `code-fix` vs `moot` route — a `code-fix` count above zero means this batch changed product behavior, not just added tests, and deserves closer review), `needsHumanCount`, `stuckCount`, `abortedCount`, `remainingOpenInScope`, and `alreadyEscalatedInScope`. When `abortedCount` is non-zero, this batch stopped early on a terminal API error (see Step 3) — plan a follow-up batch on the same branch for the `aborted` findings once the underlying cause is fixed, rather than treating this batch as fully done.
1a. **Check `markResult.annotateResult` for `abortedOnTerminalError: true` before trusting `needsHumanCount`.** A terminal error can hit the batch's Annotate step specifically (observed directly: an implementer finished a real `needs-human` investigation, the batch's own summary listed it under `needsHuman`, but the write to TEST-GAPS.md that records the question never ran). When this flag is set, `annotateResult.pendingQuestions` carries the question(s) that were never written — grep TEST-GAPS.md for each finding id's `Needs human input` field yourself before assuming it landed, and write it by hand (matching the format the Annotate prompt uses: `- **Needs human input (as of <date>):** <question>`) if it is missing. The same check applies to `verify.abortedOnTerminalError` for the batch-level fast checks (Step 4 below) — a `null`-shaped result there means validate-maps/coverage were never actually run this batch.
2. **For each `needsHuman` finding, surface its `question` to the user directly (via `AskUserQuestion` or plain conversation).** These are findings where the workflow found a real gap but was not confident a code fix is spec-aligned; it deliberately left product code untouched and recorded the question directly on the still-OPEN finding in TEST-GAPS.md (a `**Needs human input:**` field, no separate issue tracker). Do not answer these questions yourself from assumption — they exist because the workflow was not sure, and neither are you without the user's input on the ambiguous spec point. Surfacing the question does not block continuing the category (`alreadyEscalatedInScope` findings are excluded from future Select rounds automatically), but do not let it go unreported either; the user's eventual answer feeds a future run (or a `change-proposal` if it turns out to be a genuine spec gap).
3. For each `stuck` finding (failed verification after `maxAttemptsPerFinding` rounds for reasons other than a code-fix veto — e.g. a persistently missing annotation or a test the verifier keeps rejecting on quality grounds), report the verifier's `issues` and leave it OPEN for the next batch on this branch or a human to pick up directly.
4. Report the batch-level fast-check result (`dryRunTiers`, `coveragePct`, `validateMapsClean`).
5. **Run the full regression pass yourself; the workflow's Verify phase deliberately does not attempt it (see the comment above `phase('Verify')` in the script).** `lenny-test run --since "$baseSha" --output human` (with `baseSha` from `git merge-base HEAD <parent branch>`) reliably takes longer than an agent turn tolerates, so run it directly with the Bash tool's `run_in_background: true` and wait for its own completion notification rather than forcing a result. If the output-capture file goes missing (an observed environment quirk in this harness), read `tests/results/latest.json` directly instead — the run itself still completes and writes its verdict even when stdout capture fails. For every failing test, confirm whether it's pre-existing before treating it as this batch's problem: temporarily `git checkout <baseSha> -- .` (the tree is clean at this point, so this round-trips safely), re-run just that test, then `git checkout HEAD -- .` to restore. A failure that reproduces identically at the base commit is pre-existing (or environmental, like a stale process squatting on a fixed test port — check with `lsof -i :<port>` and kill it if so) and not this batch's fault; note it but do not block on it. A failure that does not reproduce is a real regression this batch introduced and must be fixed before the category is considered exhausted.
6. **If `remainingOpenInScope` is greater than 0, this category is not exhausted yet: launch another batch with the same `branch` argument rather than merging.** Do not merge a category's branch mid-way; a partial category on a merged branch loses the "one category, one merge" property this mode exists for.
7. **Once `remainingOpenInScope` reaches 0 (every closable finding in the category is resolved; everything left is `needs-human`, annotated in place) and the full regression pass from step 5 is clean, the category is exhausted.** Merge the branch into the parent (`git merge --no-ff`, per `.claude/rules/git-workflow.md`) and delete the branch — but only when you hold standing authorization to merge for this initiative; otherwise report the exhausted category and ask.
8. There is no separate issue tracker to update. Progress lives in TEST-GAPS.md itself (`remainingOpenInScope` per category) and in the sequence of merged category branches; report progress in the conversation.
