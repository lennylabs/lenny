| D1 | Operator rollouts of a new version of one runtime are designed here, separately from [`0141-runtime-routing`](../0141-runtime-routing/change.md), which adds no routes across tenants. |
| D2 | No caller can choose a revision. Every session receives the revision the traffic selects. |
| D3 | `automatic` is the default rollout policy. A change that must reach the next session uses `immediate`, either as the runtime's policy, as `?rollout=immediate` on a write, or as an operator's promote. "RV-1" states the policies (formerly O1). |
| D4 | Every revision is kept until a platform-level retention period passes, 365 days by default, and is then deleted only when no traffic or live session references it (formerly O3). |
| D5 | Derived runtimes have no revisions of their own and follow their base's revisions (formerly O4). A derived runtime's overrides merge over the selected base revision, so the base's traffic alone decides which binary a session runs. |
| D6 | The default rollout key is `user`, with the root session ID for an anonymous session (formerly O5). |
| D7 | A resume whose revision has been retired runs on the revision with the highest weight, and the change is recorded on the session and in an audit event (formerly O6). |

Settled by the owner on 2026-11-09, in the owner's words "Go with this":

| ID | Decision |
| :-- | :-- |
| D9 | Which fields are versioned (formerly O2). The classification of "Field classes" under "RV-1" stands, and `runtimeOptionsSchema` is versioned and gateway-read. The `Runtime` resource carries the schema inline, the built-in reference runtimes' schemas ship as files, no component fetches a schema URL, a write compiles the schema and refuses one that does not compile, and the revision stores the schema by digest ("RV-7"). A session's options are validated at the post-chain point against the chosen revision's schema, and a derived runtime's own schema is a second, separate check. Validation against every revision in the traffic was rejected, because renaming an option would then refuse every client as soon as the new revision entered the traffic. Versioned fields split into pod-affecting and gateway-read fields, and revisions with the same pod hash share a pod set, so a rollout that changes only gateway-read fields warms nothing ("RV-1", "RV-3", and "RV-4"). Discovery shows the revision a caller would be assigned ("Discovery" under "RV-2"). The options reach the runtime in `session_start`, the delegation `TaskSpec` and a derive can carry them, an interceptor cannot change them ([`0141-runtime-routing`, "RT-2 The interceptor contract"](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract)), and a resume onto a revision whose schema refuses them fails with a recorded reason ("RV-6"). |

Settled by the owner on 2026-11-09, after an adversarial review of revision 6's "Field classes". D10 was accepted before the others. The owner settled D11 to D19 in the words "go with your recommendations", and the removal of the tenant's `preConnect` override in D15 in the words "I agree we shouldn't have a tenant override for preConnect". D18 follows the coordinator's correction of the review's finding, whose premise about the tree was false:

| ID | Decision |
| :-- | :-- |
| D10 | Pod-affecting and gateway-read fields (review finding F3). A field is pod-affecting when it shapes the pod, its template, or its warm state before bind, and data the gateway delivers per session at bind is gateway-read. `sdkWarmBlockingPaths` and `minPlatformVersion` become gateway-read. `restartable` leaves the field list, because `Spec.Restartable()` computes it. `requireSoPeercred`, `deploymentModel`, `workspaceTier`, and `capabilities.preConnect` stay pod-affecting ("Field classes"). On 2026-11-12, D20, D21, and D22 removed `deploymentModel`, `capabilities.preConnect`, `sdkWarmBlockingPaths`, and `workspaceTier` from the runtime, so the pod-affecting fields are those of "Field classes". |
| D11 | Isolation floor (G1). A runtime's `isolationProfile` is a live floor and is not versioned. Pool admission and the WarmPoolController refuse a pool below it, pool creation and a session that names no profile are raised to it, and a write that raises it is refused while a weaker pool references the runtime ("Isolation floor"). |
| D12 | Agent card (G2). `agentInterface` is versioned and gateway-read. Discovery publishes it per caller, and the gateway generates the agent card on read from the selected revision's `agentInterface` and caches it by revision. §5.1's card generated at write time and `regenerate-cards` are retired ("Discovery" under "RV-2"). Superseded in part on 2026-11-14 by [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), which moves every client protocol adapter out of Lenny: the card generation on read and its cache leave with `pkg/gateway/runtime/agentcard`, and the A2A adapter builds the card from the `agentInterface` that discovery publishes per caller. `agentInterface` stays versioned and gateway-read, and the retirement of the write-time card and `regenerate-cards` stands. |
| D13 | Pod-set key (G3). A pod set's key hashes the base revision's pod-affecting fields with the derived runtime's and the pool's pod-affecting contributions. A change to those contributions creates a pod set without creating a revision ("RV-3"). |
| D14 | Checkpoint exclusions (G4). `checkpointExcludes` is gateway-read, and the gateway delivers each session's list at bind: the base revision's list with a tenant's entries appended ("Field classes", and IC-8 of [`0131-incremental-checkpoint`](../0131-incremental-checkpoint/change.md#runtime-fields-and-revisions)). |
| D15 | `preConnect` (F4 and G5). A tenant cannot override `capabilities.preConnect`. The gateway's bind branch and the recycle re-warm read it from the revision of the pod's pod set. A tenant turns SDK-warm off with a blocking path such as `*` on a shared pool, and with the pool setting `sdkWarm: disabled` on an owned pool ("Per-tenant capability override"). Superseded on 2026-11-12 by D21, which removes `preConnect`, SDK-warm, and the `sdkWarm` pool setting. |
| D16 | Blocking paths (G6). The per-tenant override of `sdkWarmBlockingPaths` is append-only, and the demotions that a tenant's appended patterns force are counted apart from a shared pool's SDK-warm circuit breaker rate. A platform-owned derived runtime may still replace the list ("Per-tenant capability override" and "RV-5"). Superseded on 2026-11-12 by D21, which removes `sdkWarmBlockingPaths` and the circuit breaker. |
| D17 | Interaction and injection (G7). The per-tenant capability override may only narrow `capabilities.interaction` and `capabilities.injection`, and a widening is refused, because these fields describe the binary ("Per-tenant capability override"). |
| D18 | Derived runtimes and `capabilities` (G8, as corrected). A derived runtime may set no `capabilities` field, as §5.1 "Example B" states, and §5.1's merge table gains the Prohibited rows it lacks for `capabilities.preConnect` and `capabilities.midSessionUpload` ("RV-5"). |
| D19 | Resume across revisions (G9). A resume that moves revision under D7 keeps the session's stored plan, and §7.3 step 3e's snapshotless rebuild runs that plan's setup commands under the new binary. The base `workspaceDefaults` stays gateway-read, and a tenant-derived runtime's warm entries reach the pods through the pod-set key of D13 ("RV-6" and "Field classes"). |
