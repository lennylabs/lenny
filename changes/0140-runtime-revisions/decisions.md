# Decisions: 0140 Runtime revisions

## Open decisions

The questions below are open. Each names what it blocks and the other changes it names.

- **O7. Whether a runtime's `description` is live or versioned.** Revision 6 kept `description` live beside `publishedMetadata`, while the owner's wording of D9 named descriptions among the gateway-read fields, and "Validation owed" in `steps.md` recorded the question as open for the owner without an entry here. Options: (a) live, beside `publishedMetadata`, as "Field classes" under "RV-1" states; (b) versioned and gateway-read. Recommendation: (a), because `description` is admin-facing text that describes no part of the binary, and `agentInterface`, which describes the binary's skills, is already versioned under D12. Blocks: 0140.S1 tasks 1 and 2, the field classes in §5.1 and the hash. (raised by the M3 readiness review, 2026-11-19; sources: the status assessment of the review, the "Validation owed" row on `description`)
- **O8. How revision data reaches the controllers, and which component drives a rollout.** Revisions, traffic, and rollout state live in Postgres, while the AgentPod controller reads only the `Runtime` resource (`pkg/controller/agentpod/controller.go`), and `runtime_types.go` states that `env` is not mirrored into the registry. "RV-3" has the pod builder read the revision a `PodSet` names with no transport, and no section names the component that watches the pod sets' warm counts, moves weights, fires `warmTimeoutSeconds`, and advances the phases of "RV-4" with several gateway replicas. Options: (a) the PoolScalingController, which already reads the Postgres pool store (`pkg/controller/poolscaling/poolstoresource.go`), renders the revision's pod-affecting values and each pod set's warm target into its `PodSet`, and the AgentPod controller reads only the `PodSet`, so `env` sits in a `PodSet` spec; (b) the AgentPod controller reads `runtime_revisions` from Postgres; (c) revisions are mirrored as custom resources. Under each option a job on the gateway's leader gate (`pkg/gateway/replica/gatewayleader`) drives the phase machine from `PodSet` status, and the `chaos` tier adds a leader change during `Expanding` and during `Contracting`. Recommendation: (a), with the rollout loop as a leader-gate job, because it keeps one Postgres reader on the controller side and makes the `PodSet` the full record of what its pods run. Blocks: 0140.S1 tasks 2, 3, and 5. Relates to O9. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F2)
- **O9. Which controller creates and deletes `PodSet` objects.** "RV-3", the §4.6.1 row, and the `component` test row have the warm pool controller keep, create, and delete pod sets per pod-set key. [`0137-pod-lifecycle-controller`](../0137-pod-lifecycle-controller/change.md) gives every `PodSet` spec write to the PoolScalingController ("PLC-2" **The merge.**: "The PoolScalingController owns all of `spec` and writes it in one apply per reconcile"), and the chart grants the WarmPoolController only `get`, `list`, and `watch` on `podsets` (`charts/lenny/templates/controller-rbac.yaml`). The PoolScalingController does not observe the deletion conditions of "RV-3", which are that no session uses the pod set and that no quarantined `AgentPod` remains (RVR-10). Options: (a) the PoolScalingController creates and deletes `PodSet` objects and learns that a pod set holds no session and no quarantined `AgentPod` from the WarmPoolController, through a `PodSet` status condition, the fail-closed `PodSet` deletion guard, or a WarmPoolController finalizer; (b) the WarmPoolController creates and deletes them, which needs an RBAC grant, an exception in `lenny-pool-config-validator`, and a rewrite of 0137's ownership text. Recommendation: (a), because the PoolScalingController already owns `spec` and the collision check of PLCR-17. Blocks: 0140.S1 task 3 and 0137.S2. Names 0137, which records the same question as its O5. (raised by the M3 readiness review, 2026-11-19; sources: pod-structure-C3)
- **O10. How 0140.S1's pod-set part and 0137.S2 land, and which step owns the claim-scope code.** 0137.S2 depends on 0140.S1 for `spec.podHash` and `spec.podSetKey` and allows "0137.S2 and RV-3 land together or RV-3 first", while "RV-3", "RV-2" **Claim.**, and RVR-16 state the same `<pool>.<key16>` names, `lenny.dev/pod-set` label, selectors, and claim scope that PLCR-13, PLCR-17, and PLCR-18 state. An edge from 0140.S1 to 0137.S2 would close a cycle. Landing RV-3 first creates several `PodSet` objects per pool while the claim still selects by pool, so a session can bind to another revision's pod (RVR-16). Options: (a) 0137.S2 and task 3 of 0140.S1 land on one branch, and both steps say so; (b) 0140.S1 (part) depends on 0137.S2, which then adds `podHash` and `podSetKey` itself so that no cycle forms, and "RV-3" points to "PLC-2" rather than restating it; (c) 0140.S1 implements the names, labels, selectors, and claim scope, and 0137.S2 narrows to what this change does not state and lands after it. Recommendation: (a), because it keeps one owner for each test without moving fields between changes. Blocks: 0140.S1 task 3 and 0137.S2. Names 0137, which records the same question as its O6. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F9, pod-structure-C4)
- **O11. Which path prevails when the `Runtime` resource and the admin API write one runtime.** Both paths create revisions. An admin `PUT` that changes a versioned field of a runtime a `Runtime` resource also declares is reverted by the reconciler's next resync, which computes a hash that differs from the latest revision, and a resync during a rollout is refused with `409 ROLLOUT_IN_PROGRESS` with nowhere to surface but the resource status. The tree shows the same conflict for the schema in F-5.1.34. Options: (a) a runtime is owned by the path that created it, and the other path's writes to it are refused; (b) the resource wins, and the admin API refuses versioned-field writes on a runtime a resource manages; (c) the last writer wins, and the reconciler reports a `409` as a status condition and does not retry until the resource changes. Under each option the `component` and `integration` tiers test the rule. Recommendation: (a), because it is the only rule under which neither path silently reverts the other. Blocks: 0140.S1 task 2. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F3)
- **O12. Which revision a rollback restores when more than two revisions hold weight or drain.** A canary of revision 7 over revision 6 followed by an `immediate` write of revision 8 leaves revisions 6 and 7 both draining, while **Rollback.** under "RV-4" and the phase table speak of "the old revision". Options: (a) an `immediate` write or a promote ends the rollout in progress and starts a new one whose old revision is the revision with the highest weight before the write, the other earlier revisions drain under the ended rollout, and a rollback restores that old revision; (b) rollback is unavailable after an `immediate` write ends a rollout, until the new rollout completes. Under either option a `unit` test covers it. Recommendation: (a), because it keeps rollback available for the urgent case. Blocks: 0140.S1 task 5. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F4)
- **O13. What a `tenant-admin` may read of a platform runtime's revisions.** Today `env` lives only on the `Runtime` resource behind Kubernetes RBAC. Under "Record" the revision row stores it in Postgres for the retention period, `GET /v1/admin/runtimes/{name}` returns the latest revision's versioned fields behind `requireTenantResourceAdmin` (`pkg/gateway/api/admin/routes.go`), [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md) DR-1 keeps reads open to a `tenant-admin` ("Reads stay."), and the read authorization of `GET .../revisions` is unstated, so a value the operator removed stays readable by every granted tenant's admin. Options: (a) `GET .../revisions` is open to `platform-admin` alone, and `env` and `command` are omitted from `GET /v1/admin/runtimes/{name}` for a `tenant-admin`, with `security` tier tests; (b) reads stay open, and the operator guide states the exposure. Recommendation: (a). The write half, a `tenant-admin` creating a revision of a platform runtime before DR-1 lands, is settled by 0140.S1's edge to 0147.S1 and needs no decision. Blocks: 0140.S1 task 2 and the §15.1 row. Names 0147, which records the same question as its decision 51. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F6, runtime-contract-C11)
- **O14. Which object a capability handshake report is kept for.** [`0139-runtime-protocol`](../0139-runtime-protocol/change.md) treats a pod set as one per revision or pod hash and records reports and refusals "on the pod set" ("RP-1", "RP-2"). This change keeps one `PodSet` per pool and pod-set key, keeps earlier keys of a pod hash claimable, and gives owned pools their own `PodSet` objects, so the report key, the claim-time check, and the scope of a refusal are undefined. Options: (a) key reports by `PodSet` object, and the claim-time check reads the report of every `PodSet` in the claim set; (b) key them by pod hash across pools, so a refusal crosses pool and tenant boundaries and a tenant's owned pool could stop platform pools. Recommendation: (a). Blocks: 0140.S1 task 3 and the report store of 0139.S1. Names 0139. (raised by the M3 readiness review, 2026-11-19; sources: runtime-contract-C2)
- **O15. Which capability keys the per-tenant override may narrow.** D17 (2026-11-09) limits narrowing to `capabilities.interaction` and `capabilities.injection`, before the capability catalog of RP-2 (D23, 2026-11-12) added keys such as `conversationInput`, `childSessions`, `clientTools`, and `checkpoint`. 0139's example narrows `conversationInput` per tenant, which also clears `clientTools`, and 0147's DR-8 follows D17. Whether a tenant can narrow `childSessions`, `clientTools`, `conversationInput`, `checkpoint`, or `midSessionUpload` is undefined, and the override's write validator needs a closed list. Two other changes rely on narrowings outside D17's list. AMR-18 of [`0120-anthropic-messages-api`](../0120-anthropic-messages-api/change.md) lets the override clear `conversationInput` and narrow `conversationParameters` to a subset. O7 of [`0122-client-tools`](../0122-client-tools/decisions.md), which the owner settled on 2026-11-09 as D17 was settled, lets it clear `clientTools.supported` and `clientTools.customTools` and append to `clientTools.reservedNames`, a member that RP-2 does not class as a capability. Options: (a) keep D17's list, and 0139 restates its example as `injection.supported: false` clearing `multi_turn` and `steer`, which withdraws 0122's O7 and 0120's AMR-18; (b) extend narrowing to every boolean capability, with edits to D17, RVR-15, and DR-8; (c) a closed list that adds to D17's keys the narrowings the other changes name, which are `conversationInput` cleared, `conversationParameters` narrowed to a subset, `clientTools.supported` and `clientTools.customTools` cleared, and `clientTools.reservedNames` appended, with edits to D17, RVR-15, and DR-8, and with "Per-tenant capability override" stating how an append to a member outside the capability catalog is stored. Recommendation: (c), because it gives the write validator a closed list and keeps 0122's settled O7 and the controls 0120 and 0122 build on. The first pass of the review recommended (a) before the requests of 0120 and 0122 reached this change. Blocks: 0140.S3 and 0139's example. Names 0120, 0122, 0139, and 0147, which record the same question as 0122's O19, 0139's O19, and 0147's decision 50. (raised by the M3 readiness review, 2026-11-19; sources: runtime-contract-C7; recommendation revised in the second pass, requested by changes 0120, 0122, 0139, and 0147)
- **O16. Whether the rollout key's bucket changes between rollouts.** Selection hashes `HMAC-SHA256(key = "revision/" + runtime name, message = rollout key)`, so a user's bucket is the same for every rollout of a runtime, and under `rollout.key: user` the same users are the canary of every rollout. Options: (a) the HMAC key also carries a value per rollout, such as the new revision's number, so each rollout picks a different canary population while a key stays on one revision within one traffic version; (b) the key stays per runtime. Recommendation: (a). The shared bucketing function of RT-4 in [`0141-runtime-routing`](../0141-runtime-routing/change.md) carries whichever key this change passes, and discovery's per-caller revision uses the same key. Blocks: 0140.S1 task 3. Names 0141. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F15)
- **O17. A `rollout` object on a derived runtime, and a change to `rollout.policy` during a rollout.** A derived runtime has no revisions (D5), and "Rollout settings" does not say what its `rollout` object does; nor does it say what a policy change does to a rollout in progress. Options for a derived runtime: (a) a write that sets `rollout` on a derived runtime is refused with `400 VALIDATION_ERROR` naming the field; (b) the field is accepted and has no effect. Options for a policy change: (c) the new policy applies from the next rollout; (d) it applies to the rollout in progress, so a change from `automatic` to `manual` holds the current weights. Recommendation: (a) and (c), because a stored value with no effect misleads the operator, and a rollout keeps the rules it started under. Blocks: 0140.S1 tasks 4 and 5. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F16)
- **O18. Whether the public runtime index reports `runtimeRevision`.** "Discovery" under "RV-2" has each entry report `runtimeRevision`, and the unauthenticated public index `GET /v1/public-runtimes` of R8 in [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md) is one of the routes it covers, so an anonymous caller sees rollout activity. Options: (a) the public index omits `runtimeRevision`; (b) it reports it as authenticated discovery does. Recommendation: (a), because an anonymous caller is always shown the highest-weight revision, and the number tells it nothing it needs. Blocks: 0140.S1 task 3 and the §15.1 row. Names 0138. (raised by the M3 readiness review, 2026-11-19; sources: 0140-F24)
- **O19. Whether a pool's size settings are pod-affecting contributions of the pool under "RV-3".** [`0118-agent-pod-layout`](../0118-agent-pod-layout/decisions.md) "PL-5" renders each volume's `sizeLimit`, the pod's ephemeral-storage request, and the spool's size from the pool's size settings, and the gateway refuses an upload larger than the pool's staging space with `staging_limit`. "Pod-set key" under "RV-3" keys a pod set on the revision's pod hash and the pool's pod-affecting contributions and does not list the size settings, so a write to them either builds new pods inside the same pod set or creates a new one, and the staging check does not say which pod's spool it reads while pods of two sizes coexist. Options: (a) the size settings are pod-affecting contributions of the pool, so a write creates a new pod-set key without creating a revision, and the staging check reads the staging space of the pod set the session claims from; (b) a write applies to pods created after it within the same pod set, and the staging check reads the smallest staging space among the pool's pods. Recommendation: (a), because the pods of one pod set then share one specification and the check reads the pod that serves the session. Blocks: 0140.S1 task 3 and the §5.2 and §4.6.2 row. Names 0118 and 0137. (raised by the M3 readiness review, 2026-11-19; requested by change 0118; mirrors O16 of 0118)
- **O20. Whether the per-tenant override record carries `allowDelegation: false`.** [`0126-delegation-availability`](../0126-delegation-availability/change.md) "DA-1" adds `allowDelegation: false` to the tenant runtime entry, which is the per-tenant capability override record, and reads it at each delegation call and each list, while "Per-tenant capability override" under "RV-1" narrows only capability keys and applies over the chosen revision at the post-chain point. `allowDelegation` itself is a live runtime field ("Field classes"). Options: (a) the existing override record carries `allowDelegation: false` and refuses `true`, and "Per-tenant capability override" states that the record's capability keys apply over the chosen revision at session creation while `allowDelegation` is read at each call and each list; (b) a sibling record with the same key carries the field, and the capability override stays limited to capability keys. Recommendation: (a), because one record per tenant and runtime keeps one admin route, and the read time differs by field rather than by record. Blocks: 0140.S3 and 0126.S1. Names 0126. (raised by the M3 readiness review, 2026-11-19; requested by change 0126; mirrors O11 of 0126)
- **O21. Which session states the rollout drain covers, and whether `maxSessionAge` bounds it.** [`0146-session-lifecycle`](../0146-session-lifecycle/decisions.md) "SL-6" pauses `maxSessionAge` in `dormant`, so a session that alternates between `idle` and `dormant` can outlive `maxSessionAge` in wall-clock time. "Rollout settings" defaults `rollout.drainTimeoutSeconds` to the runtime's `maxSessionAge`, the worked example states that no session outlives `maxSessionAge`, "Options the new revision refuses" under "RV-4" counts only suspended sessions, and `Draining` ends "the remaining ones" at the timeout without stating in which state an `idle` or `dormant` session ends. Options: (a) `Draining`, the D7 move of "RV-6", and the options report name the states `idle`, `dormant`, `suspended`, and `blocked`, `drainTimeoutSeconds` stops relying on `maxSessionAge` as a wall-clock bound, and this change states whether the drain ends a waiting session, and in which state, or moves it to the new revision at its next resume; (b) `maxSessionAge` keeps running in `dormant`, which changes "SL-6" and "SL-10" of 0146, and this change keeps its text. Recommendation: (a), because `dormant` replaces the idle suspension, whose `maxSessionAge` pauses today, and the drain is the mechanism that reads the bound. Blocks: 0140.S1 task 5 and the §10.5 row. Names 0146. (raised by the M3 readiness review, 2026-11-19; requested by change 0146; mirrors SL-Q5 of 0146)

| D9 | Which fields are versioned (formerly O2). The classification of "Field classes" under "RV-1" stands, and `runtimeOptionsSchema` is versioned and gateway-read. The `Runtime` resource carries the schema inline, the built-in reference runtimes' schemas ship as files, no component fetches a schema URL, a write compiles the schema and refuses one that does not compile, and the revision stores the schema by digest ("RV-7"). A session's options are validated at the post-chain point against the chosen revision's schema, and a derived runtime's own schema is a second, separate check. Validation against every revision in the traffic was rejected, because renaming an option would then refuse every client as soon as the new revision entered the traffic. Versioned fields split into pod-affecting and gateway-read fields, and revisions with the same pod hash share a pod set, so a rollout that changes only gateway-read fields warms nothing ("RV-1", "RV-3", and "RV-4"). Discovery shows the revision a caller would be assigned ("Discovery" under "RV-2"). The options reach the runtime in `session_start`, the delegation `TaskSpec` and a derive can carry them, an interceptor cannot change them ([`0141-runtime-routing`, "RT-2 The interceptor contract"](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract)), and a resume onto a revision whose schema refuses them fails with a recorded reason ("RV-6"). |
