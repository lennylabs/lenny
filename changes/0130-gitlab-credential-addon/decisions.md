# Decisions: 0130 GitLab credential add-on

## Open decisions

Decisions 1 and 2 moved here from "Decisions" in the M3 readiness review of 2026-11-19, because no owner answer is recorded for either: the status line that `review-history.md` keeps from 2026-11-16 states that both "carry recommendations for owner review". Each keeps its number, and its recommendation, cost, and alternatives are restated as options in the format of the entries below, with no change of content (sources: 0130-F2).

1. **GitLab merge request authoring** (formerly [`0152-user-git-identity` decision 26](../0152-user-git-identity/decisions.md#decisions)). Options: (a) option E of "Options" on 19.2 and later, per-session fine-grained tokens, with S13 selecting the parent, and option D below 19.2, on a VCS pool with `prAuthoring: bot`, and if S13 finds no programmatic path; (b) option D for everyone, which gives up user attribution, half of the request; (c) option B, which breaks `glab`; (d) option F, which three texts refuse and which is withdrawn. Under every option a VCS pool's `prAuthoring` never selects option A, and authorization ships regardless. Recommendation: (a), settled after S13 runs, with the S13 row that applies (open decision 3). Cost: GL-2 waits on S13, and depending on it the Token Service holds `api` parents, or users take a manual step; each session mints and revokes a token, and S13 decides whether each one notifies the user; older instances keep the bot author; a tenant can still build option A itself under the generic mechanism. Blocks: 0130.S2, and 0130.S1 when S13 lands on row 1, because that row changes the link's scopes and every user relinks.
2. **Quick actions** (formerly [`0152-user-git-identity` decision 31](../0152-user-git-identity/decisions.md#decisions)). Options: (a) `gitlab-deny`'s `bodyPatterns` refuse lines naming commands that reach review or merge state, whatever the context, and a tenant's rules can tighten them; (b) the prototype's refusal of every `/word` line, which rejects `/usr/bin/env` **[captured]**; (c) no check, relying on the token, which S13 has not shown to bind quick actions. Recommendation: (a), with S17 passing before 0130.S3 lands. Cost: it is a deny list that fails open on a new command, and a literal `/merge` line in a code block is refused. Blocks: 0130.S3, and 0130.S2 through its dependency on 0130.S3.
3. **The parent rows S13 can select, and the scopes a `gitlab` link provider admits.** Row 2 of the table under GL-2 "Recommendation" needs a tenant opt-in that no change defines (no setting, scope, guardrail, or posture row), and row 3 needs a fine-grained token registered as a link's parent, which [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) does not define (its parent token is the access token and refresh token a link holds), with no route, store column, token trust record treatment, expiry handling up to 365 days, or rotation. `scopes` on a `gitlab` link provider has a default and no list of admitted values, so a tenant admin can set `api` or `sudo` under GL-1 alone, and the refusal of an instance administrator is stated only inside row 2. Options: (a) keep all four rows and define the opt-in and the registered parent now, with a request to 0151; (b) run S13, keep only the row that applies, and refuse at write any `scopes` value beyond `read_api`, `read_user`, and the scope S13 settles, with `provider_is_admin` refusing a link for an instance administrator whenever the link holds a write-capable scope; (c) drop rows 2 and 3, leaving option E only with a low-scope OAuth parent and option D otherwise. Recommendation: (b). Blocks: 0130.S1 (the admitted `scopes` values) and 0130.S2. Names [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md), which would define a registered parent under (a) or under (b) on row 3, and [`0152-user-git-identity`](../0152-user-git-identity/change.md), whose "Token Service compromise" residual refers to the tenant opt-in. (raised by the M3 readiness review, 2026-11-19; sources: 0130-F4)
4. **`followsEntryState` on `gitlab-fine-grained`.** The template narrows each mint to the session's projects in state `granted`, but does not set `followsEntryState`, so it does not follow a later change of an entry's state and stays outside the `mint-scoped` class, and [`0142-security-oversight` decision 25](../0142-security-oversight/decisions.md#decisions) refuses it on a repository rule's API host. [`0152-user-git-identity`](../0152-user-git-identity/change.md) waits on GL-2 for the answer. Options: (a) set `followsEntryState: true` once S13 shows that `project_ids` narrowing holds, revoking and minting again on an entry change as [`0129-github-credential-addon`](../0129-github-credential-addon/change.md) does, so the token is `mint-scoped` and admitted on a repository rule's API host; (b) leave it unset and state the refusal on a repository rule's API host as a v1 limit of GitLab. Recommendation: (a), conditional on S13. Blocks: 0130.S2, and whether user-authored merge requests work on a GitLab host with an SO-5b repository rule. Names 0152, which keeps or drops its interim refusal in the same words, and 0142. (raised by the M3 readiness review, 2026-11-19; sources: 0130-F6, credentials-git-C10)
5. **`pushIdentity` on GitLab.** [`0152-user-git-identity` decision 10](../0152-user-git-identity/decisions.md#decisions) defaults `pushIdentity` to `user` through a git child, and a human session with no git child cannot push. GitLab has no git child: its pushes use the project token until S13, which is the App-identity case that decision 10 admits only under `pushIdentity: app` with UG-4, and on GitLab UG-4 needs external status checks on a paid tier (S12). [`0152-user-git-identity` decision 47](../0152-user-git-identity/decisions.md#decisions), which asks how App-identity pushes are bounded, is open. Options: (1) on GitLab, `pushIdentity` must be `app` until GL-2 delivers a per-session git token, with decision 47 option (b), a per-user branch namespace; (2) admit `pushIdentity: user` on GitLab with the meaning "project token until S13", and state the residual; (3) refuse `prAuthoring: user` on GitLab until S13 passes. Recommendation: (1). Blocks: 0130.S2. Names [`0152-user-git-identity`](../0152-user-git-identity/change.md), whose UG-3 states the same value and whose decision 47 is settled together with this one. The matching decision in that change is [`0152-user-git-identity` decision 57](../0152-user-git-identity/decisions.md#open-decisions), which asks the same question with the same options, and the two are settled as one. (raised by the M3 readiness review, 2026-11-19; sources: 0130-F7, credentials-git-C2)
6. **Overridable fields of `gitlab-fine-grained`.** GL-2 says `Approve` and `Merge` are "never in the default set", which implies an override that the change does not define, and [`0151-user-credential-delivery`, "Narrowing templates"](../0151-user-credential-delivery/change.md#narrowing-templates) requires the add-on that ships a template to name its overridable fields and state what an override widens. Options: (a) `permissions` is overridable, audited, and reported in posture, as [`0129-github-credential-addon` decision 5](../0129-github-credential-addon/decisions.md#decisions) settles for `github-scoped`, and a widening to `Approve` or `Merge` leaves approval and merge to the preset alone; (b) `permissions` is overridable, and a write that adds `Approve` or `Merge` is refused, so the host keeps refusing both; (c) the template has no overridable field. Recommendation: (b), because it keeps the host's refusal of approval and merge that UR-4 relies on and leaves other additions to the tenant. Blocks: 0130.S2 and the "Configuration by scope" row for the override. (raised by the M3 readiness review, 2026-11-19; sources: 0130-F3)
7. **REST equivalents of `/target_branch` and `/run_pipeline`.** The text family refuses `/target_branch` and `/run_pipeline`, while the `target_branch` field of `PUT projects/*/merge_requests/*`, which `glab mr update --target-branch` sends and the token's `Update` admits, and the pipeline creation routes are not refused. `target_branch` cannot go into `denyBodyKeys`, because `glab mr create` sends it on every create. Options: (a) drop the two names from the pattern and state that the token's permissions and the project's own settings govern retargeting and pipelines; (b) keep the names and refuse the equivalents: `target_branch` on the update route alone, which needs a route-scoped body key refusal in the preset format of [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md), and the pipeline creation routes, with the route names confirmed by S17; (c) keep the pattern as it is and state the gap as a residual. Recommendation: (b) when 0151's format can scope a body key to a route, otherwise (c). Blocks: 0130.S3. (raised by the M3 readiness review, 2026-11-19; sources: 0130-F14)
8. **The Policy family under a Maintainer-role project token.** Under option D the project token's role is the tenant's choice, and with a Maintainer role the project's settings, approval settings, members, hooks, and CI variables are writable through routes `gitlab-deny` does not name, while the Policy family names only `projects/*/protected_branches/**` writes. Options: (a) add those routes to the Policy family, with the route names confirmed by S17; (b) require a Developer-role project token under option D, which [`0127-egress-and-git`](../0127-egress-and-git/change.md) enforces when it mints; (c) both. Recommendation: (c), because the role bounds the token at the host and the routes bound a token whose role a tenant raises. Blocks: 0130.S3. Names 0127 under (b) and (c). (raised by the M3 readiness review, 2026-11-19; sources: 0130-F17)
