# Decisions: 0173 Credentials in stored idempotency responses

## Open decisions

None.

## Decisions

1. **Credentials in stored idempotency responses.** Settled by the owner on 2026-11-20, question DV-6 of the M3 readiness decision page, option (a), recorded as decision D14 of [0150](../../0150-tenant-security-settings/decisions.md#decisions) (open decision O21 there). A response that carries a credential is not stored with it: a critical operation that returns one stores the response with the token removed and mints a fresh token on replay, or calls `idempotencymw.DoNotStore`, and §12.9 classifies idempotency records. D14 placed the work in the step named when the proposed upload-token change was created. That change was never created, so this change carries the work, and 0173.S1 is the step D14 names. The options not taken were (b), encrypting the stored response body under the tenant key, and (c), classifying the records as Secret and relying on volume encryption.
2. **Which token a replay mints (IK-1).** A replay mints the token again under the key that signed the original, so the minted token equals the original while that key is in the ring, the token's digest stays the one on the session row that `FinalizeWorkspace` marks consumed, and the replayed body equals the original. This is the reading of "mints a fresh token" in decision 1. Owner's answer to IK-1 on the M3 readiness decision page, 2026-11-25, option (a), given after the owner was told that the §11.5 idempotent replay stays, and that change 0144 removes session replay (`POST /v1/sessions/{id}/replay`), a different feature. The option not chosen was (b), minting a new token under the active key on every replay and writing its digest and expiry to the session row. The general review of 0173.S1 (finding 2) raised it.
3. **Client values with the token's form (IK-2).** The redaction keeps working on the bytes of the response, so it reaches a token wherever a response carries it, and a value a client sent that the response echoes, and that has the form of an upload token or of a redaction reference, is stored with a mark no key reproduces and replays differently from the original response. Owner's answer to IK-2 on the M3 readiness decision page, 2026-11-25, option (a), given with the same context as decision 2. The option not chosen was (b), redacting only the `uploadToken` fields of the responses that create a session, by their JSON position. The security review of 0173.S1 (finding 3) raised it.
