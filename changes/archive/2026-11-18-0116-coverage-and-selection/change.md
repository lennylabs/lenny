# Coverage and test selection from annotations

Status: `Implemented`, revision 4, 2026-11-18. Programs: [v1](../../programs/v1.md), milestone M1.

## Problem

Three hand-kept files record what the tests cover and which tests a change runs, and the registers and self-tests around them hold the files in step with the tree:

- `tests/spec-map.json` maps 231 numbered sections to 5,686 test references, with 102 exempted sections in `tests/spec-map-exceptions.yaml` and 19 tolerated dangling references in `tests/spec-map-pending.txt`.
- `tests/change-graph.json` maps 343 path prefixes to the tests each tier runs, with 90 not-yet-existing paths in `tests/change-graph-pending.txt`, 368 grandfathered directories in `tests/registers/change-graph-coverage.yaml`, and 82 residual entries in `tests/registers/residual-change-graph-coverage.yaml`.
- `tests/claim-map.json` records the implementation status of 102 statements of §28, generated by `scripts/seed-claim-register.py` and held by 16 tier-0 tests.

The files are expensive to keep. Of the 2,717 commits since 2026-09-01, 409 touched at least one of these eight files, and `tests/spec-map.json` alone was touched by 363, against 586 commits that touched `pkg/` or `cmd/`. Every package move rewrites path keys in two maps, which caused most of the friction when the migration spike moved a package ([0115's spike evidence](../2026-11-16-0115-spec-structure/evidence/spike-migration/FINDINGS-code.md), "Retire `spec-map.json`"). Nine tier-0 files with 48 tests exist only to check the maps against themselves ([test infrastructure review](../2026-11-17-0154-merge-gate/evidence/test-infrastructure-review.md), "Question 1", category F).

The files also disagree with what the tree states. The `// spec:` annotations already name the section each test verifies: 10,690 of the 18,213 top-level test functions carry one in their doc comment. For the sections the spec map keys, it lists 3,093 test functions whose annotations cite the same section, omits 11,671 that annotations cite, and lists 939 whose annotations cite a different section or none. The change graph selects tests by hand-written prefixes, while the Go import graph already knows which tests build a changed package: for the 479 packages under `pkg/`, a change reaches a component test package through imports for 361 packages, and the change graph selects the component tier for 90 of them.

The specification restructure of [0115](../2026-11-16-0115-spec-structure/change.md) makes the section-keyed map obsolete. Each area change replaces numbered sections with successor stubs and introduces requirement identifiers such as `POOL-R5`, so a map keyed by section number goes stale area by area, and 0115 defers its gate "every added or modified requirement has a citing test" to this change.

## Scope

- **In scope.**
  - An index of every `// spec:` annotation in the tree, built on 0115's annotation parser, and a coverage view derived from it on demand: requirement or section to tests and deciding code, with no committed coverage file.
  - The coverage gate that 0115 plans: every requirement a branch adds or modifies has a test that cites it, or an issue that records why it has none (decision O1).
  - `--changed` selection derived from the Go import graph (`go list -deps -test`) for Go sources, from annotations for specification edits, and from a short hand-kept list for inputs outside Go packages.
  - The tier bound of a selection taken from the merge, area, and release gates of [0154](../2026-11-17-0154-merge-gate/change.md), with `--max-tier` removed.
  - The claim register of §28.4 replaced by issues under `issues/`, and §28 edited to say so (decision O2).
  - The retirement of `tests/spec-map.json`, `tests/spec-map-exceptions.yaml`, `tests/spec-map-pending.txt`, `tests/change-graph.json`, `tests/change-graph-pending.txt`, `tests/claim-map.json`, the two change-graph registers, `scripts/seed-claim-register.py`, the tier-0 self-tests of the maps, and the `validate-maps` checks that read them, each with the replacement named in "CS-9 Retirements and replacements".
  - 0115's annotation lint extended to refuse identifiers in test names, as it already refuses section numbers.
- **Out of scope.**
  - Re-annotating existing code and renaming the 8,234 test functions whose names carry a section number. Each area change does both for its packages before its milestone exits, as `spec-annotations.md` states.
  - Renaming the tier directories and splitting the static tier ([0155](../2026-11-17-0155-test-tiers-by-name/change.md)).
  - The gate command, its container, and the definitions of the merge, area, and release gates (0154).
  - The 14 registers of the channel-naming and line-citation migration, which retire with that migration (0155).
  - Deleting the tier-11 tests that compare specification prose (0155 and each area change), except where this change edits one because it reads a retired file.

## High-level design

The annotations are the record. Every test that verifies a requirement already names it in its doc comment, and code that makes a decision names the requirement it carries out. This change reads those annotations into an index each time a tool needs one, and every view that the maps provided becomes a query over that index.

Coverage is the first query. For an identifier, the coverage view lists the tests that cite it directly. For a numbered section, it lists the tests that cite the section or one of its subsections. When an area has migrated, a section citation also reaches the identifiers that the section's successor stub lists, and the view shows those as indirect. The coverage gate reads the same index: a branch that adds or modifies a requirement passes when a test cites the requirement, or when an issue records that no test does yet.

Selection is the second query, built from three sources. For a changed Go file, or a file a Go package embeds or keeps under `testdata/`, the import graph names every test package that builds the owning package, directly or through other packages. For a changed specification page, the hunks name identifiers or numbered sections, and the index names the tests that cite them and the code whose behavior they define. For the few inputs outside Go packages, such as the chart, the compose stack, and the runtime supervisor's C sources, a short hand-kept list names the tests that read them. The gate that runs the selection bounds it: the merge gate runs what the selection reaches in its tiers, and the area and release gates run their own tiers.

The claim register records which §28 statements the tree does not yet carry out. Those rows become issues, filed under the code of the page that will own each statement, and §28.4 says that the issues hold that record. The rows that record a mechanism as wired retire, because the deciding code's annotation states the same fact.

With the index in place, the maps, their pending lists, their registers, and the tests that checked them against each other have nothing left to hold, and they are deleted.

## Detailed design

### CS-1 Annotation index

The index moves into `scripts/specshift/annotation` as `Index`, built by one walk over the tracked Go files of the shared read domain (`scope.ReadDomain`), which already leaves out `testdata/`, the change records, the proposals, and generated files. For each annotation it records the path, the line, the declaration that carries it (from `survey`'s declaration finder, which moves with it), the site kind (test function, other code, or package doc comment), the identifiers its items cite (`Identifiers`), and the section numbers its items cite (`IsSectionCitation`, with the number parsed). The test functions with no annotation are recorded too, so the coverage view can count them.

`survey`'s `findSites` becomes a query over the index, so `where`, `digest`, the coverage view, the coverage gate, and selection share one reading. `lookupSpecSections` in `cmd/lenny-test/gotest_json.go` is replaced by a lookup in the same index, and verdict files report identifiers and sections as the annotation states them.

A test is identified by its package directory and function name. Its tier is the tier of its package directory, read from the one table in `cmd/lenny-test/tiers.go` that 0155.S1 edits when the directories take their names; a test outside the tier directories is a unit test.

### CS-2 Coverage view during the transition

`lenny-test coverage --spec [<identifier | code | §N.M>...] [--area <code>] [--json]` prints the coverage view from the index, the registry, the successor stubs, and the issues. With no argument it prints every page and numbered file.

- **Identifiers.** For each requirement, operation, and definition block in the registry: the tests that cite it directly, grouped by tier; the deciding code that cites it; the open and planned issues whose `requirements` list names it; and the tests that reach it through a section citation of a section whose successor stub lists it, marked indirect.
- **Numbered sections.** For each numbered heading that is not yet a successor stub: the tests that cite the section or one of its subsections. The 102 exceptions of `tests/spec-map-exceptions.yaml` have no successor, so the view lists a heading with no citing test as uncovered and the reader judges it.
- **Unresolved citations.** Section numbers that name no heading (46 today) and identifiers the registry does not carry are listed with their sites. The section numbers are defects of the area that owns the code, and each area change fixes its own when it re-annotates.
- **Unannotated tests.** A count of test functions with no annotation, per tier and per package.

Nothing is committed. The view is a few seconds of computation over the tree, and `where` (0115.S8) shows the same rows for one identifier.

### CS-3 Coverage gate

`TestEveryChangedRequirementHasACitingTest` in `tests/static` compares the registry of the branch head with the registry at the branch's merge base with `main`, using `survey`'s snapshot comparison. For each requirement the branch adds, or whose text it modifies, the gate passes when one of these holds, and fails naming the requirement otherwise:

- a test function's annotation cites the requirement directly;
- an open or planned issue under `issues/<CODE>/` names the requirement in its `requirements` list, when decision O1 settles on option (b).

A moved requirement whose text is unchanged is neither added nor modified. A retired requirement needs no test, and a test that still cites it fails the annotation lint of 0115.S5 because the identifier no longer resolves. The gate skips with a reason when the branch has no merge base with `main`, as the annotation lint does. Until an area lands, the registry holds no requirements and the gate passes vacuously.

Numbered sections are outside the gate. A numbered section edited before its area migrates is a paragraph inside a heading that other tests already cite, and a per-section rule would pass on any one of them. The coverage view reports such sections, and each area change's diff adds its requirements, so the gate checks the whole area when it lands.

`.claude/rules/spec-annotations.md` names the gate in its "Gate" section, replacing the sentence that defers it to this change.

### CS-4 Selection from the import graph

`loadPkgGraph` runs `go list -e -deps -test -tags <every tier tag> -json ./...` once and keeps, for each in-module package, its directory, its imports, its test imports, its external test imports, and its embedded files. The tags are the union of the build tags the tier directories declare, read from the tier table, so a tagged tier package is in the graph.

For each changed path:

1. The owning package is found as today (`packageForPath`), extended with the embed lists, so a file a package embeds from a subdirectory selects that package.
2. The owning package and every package whose build, including test builds, depends on it directly or transitively are selected: the reverse closure over imports, plus the packages whose test imports reach the closure. This is the "changed packages and their dependents" of 0154's merge gate. `--rdeps-depth` stays as an operator flag to narrow the walk in the inner loop, and its default becomes the full closure.
3. A selected package runs whole. The integration and chaos tiers are one Go package each, so an import that reaches either selects the whole tier; decision O3 settles how those tiers narrow.

`go.mod`, `go.sum`, and `go.work` keep their module-wide treatment. A changed Go file that does not load (a syntax error in the diff) keeps its owning package through the directory walk, because `go list -e` reports the package with its error.

### CS-5 Selection from specification edits

For a changed file under `spec/`, the selector reads the diff hunks against the base:

- **A page of the new tree.** Each hunk inside a requirement, operation, or definition block selects the identifier through the registry's anchors. The selection adds the test functions that cite the identifier directly or indirectly, and the packages whose code cites it are treated as changed under CS-4, so a changed default reaches the code that reads it and that code's dependents. A hunk outside any identifier, such as an introduction or a gloss, selects the unit tests of the packages whose `doc.go` names the page code.
- **A numbered file.** Each hunk selects the numbered heading that encloses it. The selection adds the test functions that cite the heading or a subsection of it. A hunk that turns a section into a successor stub selects the tests that cite the identifiers the stub lists.
- **Test functions run by name.** A selection from a specification edit runs functions with `-run '^(TestA|TestB)$'` in their packages. When CS-4 selects the same package whole, the whole package runs.

The registry's own regeneration, a catalog regeneration, and an index regeneration are edits to generated files; the gates that compare generated files with a fresh run hold them, and they select nothing further.

### CS-6 Non-Go inputs

`tests/non-go-inputs.yaml` holds the inputs no Go package owns. Each row names path patterns, the test packages or tiers that read them, and a reason:

```yaml
# SPDX-License-Identifier: MIT
kind: non-go-inputs
version: 1
inputs:
  - paths: ["charts/lenny/**"]
    runs: [tests/component/pgbouncerchart, e2e_kind]
    reason: The PgBouncer component test renders the chart, and the Kind tier deploys it.
  - paths: ["compose/**", "docker-compose.yml", "Dockerfile"]
    runs: [integration]
    reason: The integration tier runs on the compose stack these files define.
```

The first version holds a row each for the chart, the compose stack and its images, the runtime supervisor (`supervisor/**` and `Dockerfile.supervisor`), the Kind install scripts under `tests/testinfra/kind/`, `docs/**`, and `spec/**` (the documentation tier, in addition to CS-5). The exact package names come from the build, which reads each tier package for the paths it opens. The tests named in each row are the tests that read the input, rather than the tests of the code it configures. A row names a tier when every package of that tier reads the input, so a new test of that tier needs no new row.

A changed path that no package owns and no row matches selects nothing beyond the static tier, and the selection notes name it, as the unmapped note does today. The static tier runs whole on every invocation, so the chart lint, the schema checks, the migration numbering, and the shell lints keep running for any change. Paths under `changes/`, `proposals/`, `issues/`, and the root records select nothing further.

`lenny-test validate` checks the file: it parses, every pattern matches at least one tracked file, every package target exists, and every tier target is a tier name. The check fails on a dead row, so the list stays short.

### CS-7 Tier bounds

0155 moves the ordering that `--max-tier` expresses to the gates of 0154. This change carries that out in the harness:

- `--max-tier` is removed from `lenny-test run`, `tests/groups.yaml`, and the reusable workflow.
- `--tier` accepts a comma-separated list of tier names.
- `--gate <merge | area | release>` caps a selection at the tiers of that gate, as 0154.S2 defines them. `lenny-test gate merge` is `run --changed --gate merge` with the merge gate's verdict file.
- Without `--tier` or `--gate`, `run --changed` runs every tier the selection reaches that runs without infrastructure: static, unit, component, and contract. A tier that needs the compose stack or a cluster runs only when a gate or `--tier` names it, so a developer's inner loop does not start infrastructure by surprise.
- `pr-fast` becomes `changed` with `tiers: [static, unit, component]`, and `pr` becomes `gate: merge`. The reusable workflow's `max_tier` input becomes `gate`.
- `.claude/rules/test-coverage.md` and the `build` skill instruct `lenny-test run --changed` and `lenny-test gate merge` in place of `--changed --max-tier <tier>`.

### CS-8 Claim register into issues

The claim register exists because §28.4 requires it. This change rewrites §28.4 and files its open rows as issues, as decision O2 settles.

- **Rows that are not `WIRED`.** Each of the 41 rows becomes an issue of kind `build-gap`, filed under the page code that 0115's map assigns to the row's anchor: the card's page for a contract-card anchor (`CHGWPOD`, `CHPODGW`, `CHREPLICA`, `CHEGRESS`, `CHCTRL`, or `CHSTORE`; for the intra-pod card, `RTPMSG`, `RTPOPS`, `RTPTOOL`, or `CHINTRA` by the channel the row names), `CHAN` for the exclusivity model, the register sections, and the wire-contract register, and `NAMING` for the naming table. The issue body quotes the row's claim, surface, and note under Evidence, and names the remediation step of the deferral under Suggested resolution. Each row is triaged against the member changes of the v1 program first: a row whose mechanism a member change removes or redesigns is filed directly under `closed/` as `obsolete`, with `closed-by` naming that change, as `issues/README.md` states for the gap records.
- **`WIRED` rows.** The 61 rows retire with the file. Each names the production surface that reaches a mechanism, which is a statement about the tree that the deciding code's annotation and `where` already give.
- **§28.4** keeps its number and takes the heading "Implementation status", with the anchor move recorded in the anchor-redirect map. Its text states that a mechanism this section specifies and the tree does not carry out, or carries out with no production caller, is recorded as an issue under the code of the page that owns the mechanism's contract, and that the issue names the step that closes it. The §28 lead, N4 of §28.1 ("carries a claim-register row with status `ABSENT`"), the §28.5 lead, and §29.1 refer to that record instead of the register. `.claude/rules/channel-naming.md` (step 4 of "How to apply when naming", and its restatement of N4) follows.
- **Gates.** The 16 claim-register tests and `scripts/seed-claim-register.py` retire. The reachability rule they enforced for adapter client methods (`TestAdapterClientReachabilityRequiresAProductionCaller`) was a means of keeping `WIRED` rows honest, and it retires with them. The annotation lint resolves issue identifiers through `issues/<CODE>/`, so a `// spec: CHGWPOD-R4 (partial: CHGWPOD-I2)` annotation on the code that carries a statement in part resolves once the area lands.

### CS-10 Test names

0115.S5's lint refuses a section number in the name of a new or changed test function. This change adds an identifier in the name, such as `TestPOOL_R5Holds` or `TestPoolR5`: a requirement or issue identifier, with its hyphen written as an underscore or dropped, inside a test function or subtest name on a changed line. The rule already says that a test name carries no identifier, so the edit to `spec-annotations.md` is to its "Gate" list.

The 8,234 existing names that carry a section number are renamed by the area that owns each package, as part of re-annotating it, and the entries that key a renamed test by name in `tests/registers/skip-reasons.yaml`, `tests/registers/residual-skip-reasons.yaml`, and `tests/flake-budget.yaml` follow each rename. This change adds that to the area exit of the v1 program, beside the area's count of old `§` citations reaching zero.

## Worked example

Area `pools` has migrated. A branch changes `pkg/controller/warmpool/reconcile.go` and modifies the text of `CLAIM-R4` on `spec/capabilities/pools/pod-claims.md`.

1. **Selection.** The owning package of the Go file is `pkg/controller/warmpool`. The import graph adds every package that builds it: `cmd/lenny-controller`, the component test packages under `tests/component/` that import the controller, and the integration package. The hunk in `pod-claims.md` falls inside `CLAIM-R4`; the index names three test functions that cite it, in `pkg/gateway/podlifecycle/podsession` and in a contract package, and one deciding function in `pkg/gateway/podlifecycle/podclaim`, whose package is then treated as changed. No non-Go input changed.
2. **Bound.** `lenny-test run --changed` runs static, unit (the selected packages), component, and contract. `lenny-test gate merge` also runs the integration package, which the merge gate's tiers include.
3. **Coverage gate.** `CLAIM-R4` is modified, and three tests cite it directly, so the gate passes. Had the branch added `CLAIM-R9` with no citing test, the gate would fail naming it, unless an open issue under `issues/CLAIM/` listed `CLAIM-R9` (decision O1, option (b)).
4. **Coverage view.** `lenny-test coverage --spec CLAIM-R4` lists the three tests by tier, the deciding function, and any tests that still cite `§4.6.1` and reach `CLAIM-R4` through the stub, marked indirect.

## Limits, and alternatives rejected

- **Selection is sound for imports and approximate elsewhere.** A test that exercises a package through a running binary, the wire, or a file reaches it through no import. The measurement above counts such cases for 6 to 34 packages per tier against the change graph. The gates cover them: the merge gate runs the integration package whenever any import reaches it, which is 292 of 479 `pkg/` packages, and the area and release gates run their tiers whole. A test that reads a non-Go input needs a row in the non-Go list, and the build skill's instruction to run the tiers a step reaches stays.
- **Coverage is as good as the annotations.** 41% of test functions carry no annotation, most of them unit tests under `pkg/`. The coverage view counts them and the gate applies only to requirements a branch adds or modifies. Each area change re-annotates its packages.
- **Section citations name no heading in 234 cases.** The coverage view lists them; each area fixes its own.
- **Other changes' edits to the retired files.** 0125, 0132, 0137, and 0141 list edits to the spec map or the change graph. A change that lands after the retirement step drops those edits; one that lands before applies them, and the retirement deletes the result. 0155's "Tests" names `lenny-test validate-maps`, which this change renames to `validate`; whichever lands second uses the name the tree has.
- **Rejected: generate the maps from annotations and keep them committed.** A committed generated map is regenerated by every change that touches a test, which keeps most of the commit churn measured above, and the generator's freshness gate replaces the self-tests with one more gate.
- **Rejected: keep one hop of importers as the default.** One hop leaves out dependents that 0154's merge gate names, and it is the reason the current selector carries `go vet ./...` as its safety net. The full closure selects a median of 12 tested packages per changed package.
- **Rejected: keep `--max-tier` with an order over named tiers.** 0155 settled that ordering moves to the gates, and a bound by gate states what has to pass for a merge.
- **Rejected: carry the claim register into the new tree as a definition-block kind.** A register of what the tree does restates the code, and the open half is what issues already record.

## Tests

All tests are tier 0, or the tests of `cmd/lenny-test` and `scripts/specshift`. They test contributor tooling, so they carry no `// spec:` annotation and say so in a comment. The §28.4 edit adds no test: the issues it points to are records, and the annotation lint already resolves issue identifiers.

- **Index.** Fixtures with annotations on test functions, code, and package doc comments; continuation lines; section and identifier items in one annotation; generated files and `testdata/` left out; unannotated tests counted.
- **Coverage view.** Direct and indirect coverage through a successor stub; a numbered heading covered through a subsection; an unresolved section number and an unresolved identifier listed with their sites; the JSON output.
- **Coverage gate.** With a fixture registry at a base and a head: an added requirement with a citing test passes; one with none fails naming it; one named by an open issue passes or fails as O1 settles; a modified requirement is checked and a moved one is not; a retired requirement needs nothing; no merge base skips with a reason.
- **Import-graph selection.** On a fixture module: a changed leaf selects its transitive dependents including test-only importers; a tagged tier package is in the graph; an embedded file and a `testdata/` fixture select their owner; a file that does not compile keeps its owner; `go.mod` is module-wide; `--rdeps-depth` narrows the walk.
- **Specification-edit selection.** A hunk inside a requirement selects its citing tests and treats its citing code's package as changed; a hunk outside identifiers selects the packages whose `doc.go` names the page; a numbered-file hunk selects the tests of the enclosing heading and its subsections; a stub hunk selects the tests of the stub's identifiers.
- **Non-Go list.** Parsing; a dead pattern, a missing package, and an unknown tier each fail `validate`; an unmatched path is reported and selects only the static tier.
- **Tier bounds.** `--gate` caps a selection; `--tier` takes a list; `run --changed` without a bound leaves out the infrastructure tiers; `--max-tier` is rejected as an unknown flag.
- **Test-name check.** Identifiers in function and subtest names on changed lines are refused in their spellings; a name with a version number is accepted.
- **Equivalence before retirement.** Before the maps are deleted, a one-time comparison records, for each spec-map key with tests, whether the coverage view covers it, and for the last 50 merges into `main`, the tests the change graph selected and the tests the new selector selects. The step digest records both, and "Validation owed" in `steps.md` names what waits on them.
- **The tier-0 suite** passes after the retirements, with the residual gate and the gate-integrity list updated for the removed classes and gates.
