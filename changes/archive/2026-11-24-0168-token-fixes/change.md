# Token rule fixes from the property tests

Status: `Implemented`, revision 5, 2026-11-24.

## Problem

Change 0165 (a formal model of the token rules, [`changes/0165-token-rules-model/`](../2026-11-23-0165-token-rules-model/change.md)) checks the token rules of §13.3 (Credential Flow), the playground mint invariants of §10.2, and step 5 of the full revoke in §11.4 with an Alloy model and with generated property tests against the Token Service (step 0165.S2, in `tests/component/tokenproperties`). Change 0167 (token rule fixes from the formal model) fixed the model's first findings. The property tests of 0165.S2 and the reviews of 0167.S1 and 0165.S2 found further defects, which the owner settled on 2026-11-23 on the M3 readiness decision page for this change to fix:

- **F1, TOKX-I22.** A recursive-revocation request whose caller is an impersonation bearer that the `subject_token`'s lineage started refuses itself. The request ends the impersonation sessions the lineage started, revoking its own caller, and the cascade then reads the caller as revoked and answers `401 invalid_client`, so the `subject_token` stays live. An administrator who impersonates a user of the administrator's own tenant with a bearer B, and revokes B with the impersonation bearer as caller, hits it.
- **TOKX-I20.** The subtree read that checks the caller and the impersonation update run in two transactions, so a revocation of the caller that commits between them does not stop the impersonation step from ending sessions.
- **F2, TOKX-I19.** A full revoke of a user seeds its lineage walk with the user's own rows only. A child that another user minted with an unrecorded token of the user as `actor_token` names the user in `act_sub` and in its `act` claim and stays live.
- **FM-16.** The Token Service reads no user invalidation level. After a full revoke, a token of the user that has no `issued_tokens` row, such as an upstream OIDC ID token the identity provider still issues, authenticates mints and recursive-revocation requests on `/v1/oauth/token`, and a `tenant-admin` or `platform-admin` role resolved for it still passes the revocation request's role check.
- **TOKX-I17.** Every recursive-revocation request served by a durable store runs the impersonator-link update under the `__all__` sentinel and writes one `cross_tenant_read` event, for any caller the request accepts, whether or not a token of the subtree started an impersonation. §4.2 and §12.3 name it as the one exception to their rule that only `platform-admin` paths set `__all__`. Change 0167 kept the exception (its decision 12) until this change removes it.

Change 0169 (a concurrency model of the token rules, [`changes/archive/2026-11-23-0169-token-concurrency-model/`](../2026-11-23-0169-token-concurrency-model/change.md)) checked the locking design of revision 3 of this change with a TLA+ model before its code lane, and found these orderings, which the owner settled on 2026-11-23 (FM-26 to FM-29, and the bound of TOKX-I10 in chat) for this change to fix:

- **R5, an undetected wait.** Two recursive-revocation requests in acme and globex whose callers are impersonation bearers started from tokens of each other's subtrees wait on each other with no end. Each outer transaction holds the share lock on its caller and waits in the application for a nested transaction that waits for the other request's caller row, so Postgres sees two lock waits and no cycle.
- **R1 and R2, TOKX-I13.** A rotation, a narrowing, a child mint, or a playground mint from a token of a revocation's subtree that commits while the cascade's statement runs stays live, and a full revoke has the same window for a mint from one of the user's tokens or their descendants. TF-4's user-row read closes the full revoke's window only for a mint on `/v1/oauth/token` that presents a token carrying the user's `sub`.
- **R6, a bearer row without a start record.** When the first transaction of rule 1 (c) fails at `COMMIT` after its nested transaction committed the bearer row, the bearer row stays live without a start record, and the impersonation step does not reach it.
- **G3, the unlocked caller check.** `checkCaller` reads the impersonation caller's bearer without a lock, so an impersonation whose caller check precedes a cascade's commit and whose record commits after it is linked to a revoked bearer and stays live.
- **TOKX-I10.** The cascade has no bound on the depth of a chain or on its duration, and with the advisory lock of TOKX-I13's fix it blocks the tenant's issuances for as long as it runs.

The issues [TOKX-I10](../../../issues/closed/TOKX/TOKX-I10-revocation-cascade-has-no-depth-or-time-bound.md), [TOKX-I13](../../../issues/closed/TOKX/TOKX-I13-derivation-committed-during-a-cascade-escapes-it.md), [TOKX-I17](../../../issues/closed/TOKX/TOKX-I17-every-revocation-request-runs-a-cross-tenant-step.md), [TOKX-I19](../../../issues/closed/TOKX/TOKX-I19-full-revoke-misses-delegations-made-with-a-token-without-a-row.md), [TOKX-I20](../../../issues/closed/TOKX/TOKX-I20-caller-revoked-between-the-subtree-read-and-the-impersonation-step.md), and [TOKX-I22](../../../issues/closed/TOKX/TOKX-I22-revocation-refuses-a-caller-its-own-impersonation-step-revoked.md) are under `issues/TOKX/`. No issue tracks FM-16, R5, R6, or G3, and the step files none, because this change is their fix.

- The routes that revoke an administrator's bearer without following the impersonator link (a self-rotation, an operator revocation of its `jti`, the bootstrap admin-credential rotation, and a full revoke of the administrator by a caller without `platform-admin`). Change 0167 decision 13 keeps them as they are.
- The refusal of decision 4 on the credential-lease mint of §4.9 and on the playground mint of §10.2. Decision 4 names the token endpoint, and the playground mint already refuses an invalidated user through the §27.6 revocation primitive that a full revoke runs. - TOKX-I21, the missing test that refuses a playground bearer as an impersonation caller.

## High-level design

The change corrects the recursive-revocation request, the full revoke, and the token endpoint.

The impersonation step moves into one transaction in the request's tenant that holds the share lock on the caller's row for its whole length. That transaction reads the subtree and the start records of the subtree's tokens. It revokes the impersonation rows of the request's own tenant, and, for each other target tenant, switches to that tenant's context with `SET LOCAL app.current_tenant`, revokes that tenant's matching rows, and switches back, all before it commits. Every wait between two such requests is then a row-lock wait that the Postgres deadlock detector sees, and the step retries a transaction the detector aborts. No statement of the step sets `__all__`, so the step needs no `platform-admin` caller and writes no `cross_tenant_read` event, and a subtree that started no impersonation switches to no other tenant. The `jti` values the step revokes in the request's tenant go to the cascade, which accepts a caller among them and refuses every other revoked caller as before.

The cascade and the full revoke's walk take the tenant's audit advisory lock before they read the subtree, which every issuance already takes, so an issuance from a token of the subtree either commits before the walk reads and is revoked with it, or runs after the walk commits and finds its source revoked. Because the lock blocks the tenant's issuances while a cascade runs, the cascade and the walk run under a 5-second statement timeout, and an exchange whose parent is 32 links deep is refused. The impersonation start reads its caller's bearer row under a share lock, so an impersonation started from a token of the subtree either commits before the cascade revokes that token or is refused.

The full revoke of a user also starts its walk from the child rows that name the user as delegating identity in `act_sub`. The token endpoint reads the user row of each token a request presents, under a share lock in the transaction that issues or revokes, and refuses a token whose user is invalidated.

## Detailed design

### TF-1 A caller that the request's impersonation step revoked (decision 1)

The impersonation step returns the `jti` values it revoked in the request's own tenant, from the `RETURNING` set of its update. `LineageRevocation` gains a field, such as `StepRevokedCallers`, that carries them, and `checkCallerLive` accepts a revoked caller row whose `jti` is in that set. It refuses every other revoked caller with `ErrCallerRevoked` as now. The acceptance reads the set rather than `revoked_reason` or `revoked_at`, so a caller that another request revoked stays refused. §13.3 **Recursive-revocation request authorization.** states the acceptance, and items 3 and 4 of **Token rule properties.** hold as the branch of 0165.S2 states them. The property tests drop the generator's exclusion (`callerEndedByLink` in `generated_test.go`) and the skip of the F1 subtest.

### TF-2 The caller's share lock across the impersonation step (decisions 2 and 8)

The step runs in one transaction in the request's tenant (the outer transaction). It reads the caller's row `FOR SHARE` and refuses a revoked caller, reads the caller's user row as TF-4 states, reads the root's subtree, and reads the start records whose bearer `jti` is in the subtree. It then revokes the active impersonation rows of the request's own tenant whose impersonator link names the request's tenant and a `jti` of the subtree. For each other target tenant the start records name, it sets that tenant's context with `SET LOCAL app.current_tenant`, revokes the matching active impersonation rows, and sets the request's tenant again with `SET LOCAL app.current_tenant` before the next statement. Every update runs in the outer transaction, which commits once, after the last one (decision 8).

The caller can be one of the rows the step revokes (F1). The outer transaction holds the share lock on the caller's row and updates that row itself, which Postgres permits within one transaction. A revocation of the caller token that commits before the outer transaction's share read refuses the request before any session ends, and one that starts later waits until the outer transaction commits, which closes TOKX-I20.

Two requests whose callers are impersonation bearers started from tokens of each other's subtrees (R5 of change 0169) each hold the share lock on their own caller and wait for the row lock on the other's. Both waits are row-lock waits of one transaction each, so the deadlock detector finds the cycle and aborts one transaction with `40P01`. The step retries a transaction aborted with `40P01`, as `RevokeLineage` retries the cascade, up to the same number of attempts (`cascadeDeadlockAttempts`, 3). The retry reads its caller revoked by the other request and refuses with `401 invalid_client`, and the other request revokes its root.

A failure of the outer transaction, including a `40P01` on the last attempt, rolls back every update of the step in every tenant and returns `500 token_exchange_failed`, as a failure of the step does now, and a retry of the request runs the step again. `writeImpersonationStepError` keeps its mapping.

### TF-3 Full revoke from the user's delegations (decision 3)

`RevokeBySubject` seeds its walk with the rows of the tenant whose `sub` is the user, and with the rows whose `act_sub` is the user and whose `parent_jti` is set. The second term selects child rows only, because an impersonation row has `parent_jti` null and rule 6 of **Platform-admin impersonation.** governs it. Migration 0202 adds the partial index `(tenant_id, act_sub) WHERE act_sub IS NOT NULL AND parent_jti IS NOT NULL` so the seed reads an index. §11.4 step 5 and §12.2 state the seed and the index, and `RevokeBySubject` drops its partial citation on TOKX-I19. The property tests drop the skip of the F2 subtest.

### TF-4 Invalidated users on the token endpoint (decisions 4 and 7)

Step (1a) of **Write-before-issue ordering.** also reads, under a share lock, the user row of the `tenant_id` and `sub` of the `subject_token`, of the `actor_token` when one is present, and of the caller token, in the same transaction, and refuses a token whose user row records a hard disable or a full revoke (decision 7). A user without a user row carries no level, as rule 1 (c) of **Platform-admin impersonation.** states. The read reuses `checkUserNotInvalidated`, which rule 1 (c) already uses, and `SourceToken` carries each source's `sub` so `recheckSources` can read it. A subject or actor refusal answers `400 invalid_grant` with the reason `subject_user_invalidated` or `actor_user_invalidated`, and a caller refusal answers `401 invalid_client` with the reason `caller_user_invalidated`, under the rejected-exchange audit discipline. A recursive-revocation request reads the caller's user row in the outer transaction of TF-2 and in the cascade's transaction, beside the caller's `issued_tokens` row, and refuses with `401 invalid_client`. A request whose caller is the full revoke's own target therefore fails after the full revoke commits its level.

The share lock conflicts with the `UPDATE` that writes the invalidation level, which the full revoke commits before step 1 of §11.4. A mint therefore either observes the level or commits before it. Step 5 then revokes, with TF-3, every token such a mint issued that carries the user's `sub`, names the user in `act_sub`, or descends from a token of the user. §11.4 states the refusal under the full-revoke level, and §13.3 states it in step (1a), in **Recursive-revocation request authorization.**, and in items 4 and 8 of **Token rule properties.** The property tests' model of the Token Service refuses the same tokens, so the checks of items 4 and 8 follow the rule.

### TF-5 Start records and a revocation without `__all__` (decisions 5, 6, and 10)

Rule 1 (c) of **Platform-admin impersonation.** also writes, in its first transaction in the administrator's tenant and before the second transaction opens, a start record naming the caller bearer's `jti`, the target tenant, the impersonation bearer's `jti`, and the bearer's `exp`. A caller bearer without a `jti` writes no start record, as it writes no impersonator link. Under decision 6 the record is a row of a tenant-scoped table that migration 0201 adds, with `tenant_id` leading its primary key under R-01, a row-level security policy and the tenant guard trigger as every tenant-scoped table has, and an index on `(tenant_id, impersonator_jti)`. The expired-row GC deletes a row whose `exp` has passed, and tenant deletion deletes the tenant's rows. A `DELETE`, a full revoke, or the expiry of the session leaves its start record until the GC removes it, and the step then matches no active impersonation row in that target tenant.

Rule 7 states the step of TF-2: it reads the start records in the request's tenant and sets a target tenant's context only for a tenant those records name. It drops the `__all__` context, the `cross_tenant_read` event, and the statement that the step needs no `platform-admin` caller. §4.2 and the pairing rule of R-02 in §12.3 drop the exception that names the step, so only `platform-admin` paths set `__all__`. §4.2's statement that the gateway sets the caller's own `tenant_id` gains the two places that run statements under a target tenant's context: the second transaction of rule 1 (c), a nested transaction that commits before the first, and the step's updates of rule 7, which run in the request's own transaction under `SET LOCAL app.current_tenant` (decision 8). Each is confined to rows that a record in the caller's own tenant names. `RevokeImpersonationsByImpersonator` loses its `-- platform-admin-cross-tenant-allowed` annotation, `pkg/tokenservice` drops the `CrossTenantReads` dependency and `errNoCrossTenantReads`, and §12.2 lists the table of decision 6. The `DELETE` lookup, the `GET` listing, and the rule 6 revocation keep `__all__` and their events, because their callers hold `platform-admin`.

Rule 1 (c) states that a failure of the first transaction after the second one committed leaves a bearer row that no client holds, because the call returns no bearer, that the impersonation step does not reach, because no start record names it, and that the `GET /v1/admin/impersonation` listing shows until its `exp`, a `DELETE`, or rule 6 ends it (decision 10).

### TF-6 The cascade and the full revoke under the per-tenant lock (decision 9)

`revokeLineageOnce` and `RevokeBySubject` take the per-tenant audit advisory lock of the request's tenant as the first statement of their transaction, before the statement that reads the subtree, under the acquisition timeout of §11.7 (`audit.lock.acquireTimeoutMs`). Every issuance of the Token Service takes the same lock before its step (1a) re-read: a rotation, a narrowing, a child mint, a credential-lease issuance, and a playground mint. An issuance from a token of the subtree therefore either commits before the cascade takes the lock, so its row is in the cascade's snapshot and is revoked with the subtree, or takes the lock after the cascade commits, so step (1a) reads its source revoked and refuses it. The full revoke orders the same way against a mint from one of the user's tokens or a descendant, whatever `sub` the mint presents, which closes the windows that TF-4's user-row read leaves (R2). Each attempt of `RevokeLineage` takes the lock again. A cascade or a walk that cannot acquire the lock within the timeout revokes nothing and fails as TF-8 states for the statement timeout.

The impersonation step of TF-2 takes no advisory lock, and the impersonation start takes none in the administrator's tenant, so TF-7 orders an impersonation against the cascade. §13.3 states the ordering under **Lineage of derived tokens.** and in rule 7, and §11.4 step 5 states it for the full revoke. This closes TOKX-I13.

### TF-7 The impersonation caller's bearer under a share lock (decision 11)

The first transaction of rule 1 (c) reads the caller bearer's `issued_tokens` row under a share lock, in place of the unlocked read of `checkCaller`, and refuses the call as `checkCaller` does when step (1a) would reject the row as a `subject_token`. The share lock conflicts with the cascade's update of that row, so an impersonation started from a token of the subtree either commits its start record before the cascade's update reaches the caller bearer, or waits for the cascade to commit and then reads the bearer revoked and is refused. Rule 7's window, in which an impersonation started from a token of the subtree after the step reads the start records escapes the request, therefore ends when the cascade commits, and rule 7 states it so. A caller bearer without an `issued_tokens` row has no row to lock, and its impersonations keep the window rule 7 states.

### TF-8 A depth cap and a statement timeout (decision 12)

Migration 0203 adds `depth integer NOT NULL DEFAULT 0` to `issued_tokens`. The write-before-issue transaction records, for a token whose row records a `parent_jti`, the parent row's `depth` plus one, reading the parent row in step (1a), and 1 when the parent has no row. A row without a parent, such as an impersonation row or a token the gateway mints outside an exchange, records 0. The playground mint records its depth the same way.

An exchange on `/v1/oauth/token` whose parent token is already at the cap is refused in step (1a) with `400 invalid_grant` and a reason that the specification lane names, and no row is inserted. The parent is the token the issued row records in `parent_jti`: the `subject_token` for every exchange except `a2a_delegation` child minting, whose parent is the `actor_token`. The cap is an operator-tunable setting, with default 32. The playground mint is not refused, so a playground bearer minted from a token at the cap sits one link deeper. A playground bearer is never the subject or the actor of an exchange that mints a token, so the chain ends there.

`revokeLineageOnce` and the walk of `RevokeBySubject` run under `SET LOCAL statement_timeout` set to an operator-tunable setting, with default 5 seconds, which matches the default lock acquisition timeout of §11.7. A cascade that reaches the timeout rolls back, revokes nothing, and answers `503` with `retryable: true`; `RevokeLineage` does not retry it. The impersonation step committed before the cascade, so the sessions it ended stay ended, as they do when the cascade fails for any other reason. A full revoke whose walk reaches the timeout revokes no token in step 5 and reports the token effect as partial-failure detail, as §11.4 reports any failed effect. §13.3 and §11.4 state both settings, their defaults, and the outcomes, and §12.2 lists the column.

## Worked example

bob in acme holds a bearer B with the `platform-admin` role. He starts an impersonation of himself in acme, bearer I1, and of carol in globex, bearer I2. Rule 1 (c) writes two start records in acme naming B, one with target acme and one with target globex, then the two impersonation rows. bob then sends a recursive-revocation request with I1 as caller and B as `subject_token`.

The outer transaction in acme reads I1's row under a share lock (live), reads bob's user row (no invalidation), reads B's subtree, and finds the two start records. It revokes I1 in acme, sets globex's context, revokes I2, and sets acme's context again. The outer transaction commits, and no statement sets `__all__`. The cascade takes acme's advisory lock, reads I1 as revoked, finds it in the set the step returned, and revokes B and its descendants. The request answers `200`.

dave, a `tenant-admin` of acme, later revokes a token T of alice whose subtree started no impersonation. The step finds no start record and sets no other tenant's context. frank, who holds a leaked copy of T, sends a self-rotation of T while dave's cascade holds acme's lock. The rotation waits for the lock, and after the cascade commits, its step (1a) reads T revoked and refuses it. alice also lent an unrecorded token A to erin, who minted a child C with her own token as `subject_token` and A as `actor_token` and caller, so C's row names alice in `act_sub`. dave then fully revokes alice. Step 5 seeds its walk with C and revokes it. alice's identity provider still issues her an ID token U, which has no row. A mint or a revocation request with U as caller answers `401 invalid_client` with the reason `caller_user_invalidated`.

## Limits, and alternatives rejected

- **No way back from the refusal.** Decision 4 refuses an invalidated user's tokens on the token endpoint for as long as the user row records the level. Nothing lifts a hard disable or a full revoke today ([AUTHN-I1](../../../issues/AUTHN/AUTHN-I1-no-way-to-lift-a-user-invalidation.md)), so the refusal holds until AUTHN-I1 is settled, as the gateway's session-creation refusal already does.
- **Gateway paths outside the token endpoint.** The refusal covers `/v1/oauth/token`. A gateway path that reads no user row, unlike the session-creation and interaction gate of `activeUserRefusal`, still accepts a token of an invalidated user that has no `issued_tokens` row, and this change adds no such read.
- **Escape window.** An impersonation whose start record commits after the step reads the start records and before the cascade commits escapes the request (rule 7). TF-7 ends that window at the cascade's commit for a caller bearer with an `issued_tokens` row; a caller bearer without one keeps the window. Rule 1 (c) commits the start record with its first transaction, after the bearer's row, and returns the bearer only after that commit.
- **A bearer row without a start record.** A failure of the first transaction of rule 1 (c) after the second one committed leaves a bearer row that no client holds, that the impersonation step does not reach, and that the listing shows until it ends (decision 10). The row grants nothing, because the call returns no bearer. Committing the start record first in a transaction of its own, or ending the row with `EndImpersonation` on the failure, were the options not chosen.
- **Issuances wait for a cascade.** While a cascade or a full revoke's walk holds the tenant's advisory lock, every issuance and audit write of the tenant waits, for at most the 5-second statement timeout of TF-8 by default. An issuance whose wait reaches the acquisition timeout of §11.7 follows the retry of §11.7 and answers `503 audit_unavailable` when its retries fail.
- **The depth cap bounds depth only.** The cap bounds the length of a chain and not the number of a token's descendants, so a wide subtree is bounded only by the statement timeout. The impersonation step's read of the subtree in TF-2 runs under no statement timeout.
- **Other bounds of TOKX-I10.** A statement timeout alone, and a depth cap alone, were the options not chosen (decision 12).
- **The wait of R5.** Nested transactions with a `lock_timeout` on each, and nested transactions with the wait stated in rule 7, were the options not chosen (decision 8). With the first, both requests can time out together and meet in the same wait on retry; with the second, they wait until their clients give up.
- **Statements under another tenant's context for a caller without `platform-admin`.** The step writes in another tenant on behalf of a caller of the request's tenant. It does so under that tenant's own context, only for rows a record in the caller's tenant names and that match the impersonator-link and impersonation-row predicates, which is the alternative that change 0167 decision 12 left for this change. Keeping `__all__` for the step and running it only when a start record exists would have cut the volume of `cross_tenant_read` events and kept the exception in §4.2 and §12.3.
- **Accepting a caller by its revocation reason or time.** TF-1 accepts only the `jti` values that the same request's step revoked. Accepting any caller revoked with `cascade_from_parent`, or revoked after the request started, would accept a caller that another request revoked (0165 decision 15).
- **One transaction for the step and the cascade.** Running the cascade inside the outer transaction would let the caller check pass at its start without the set of TF-1. 0165 decision 15 names the set, and the step stays apart from the cascade so that a failed step revokes nothing in the request's tenant and leaves the caller live for a retry, as rule 7 states.
