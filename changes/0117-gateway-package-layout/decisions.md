# Decisions: 0117 Gateway package layout

## Decisions

Settled by the owner on 2026-11-17 ("go with all your recommendations, except ..."); the questions as framed are in `review-history.md`.

1. **Domain packages.** All 124 domain packages leave `pkg/gateway`.
2. **Directory level.** Concern directories under `pkg/`, extending the existing ones.
3. **REST handlers.** Each part registers its own routes with the API front through the registration interface in `pkg/gateway/seam`.
4. **`sessionserver`.** The seam, plumbing, and domain files move out, and the rest, about 19,400 lines, stays as one session core package.
5. **Packages a member change removes.** They stay in place, listed in the layout gate's register with the change that removes it. In the owner's words: "keep in place but remember to move at the end if for whatever reason they weren't deleted (fully or partially)". Step 0117.S13 runs before v1 closes and moves into the layout whatever a removal left, whole packages or parts, so the register is empty when v1 closes.
6. **Package names.** Directories change, and each move step settles the names of the packages it moves: a package keeps its name where the name fits its component page or concern, and is renamed in the same step where it does not, so that every package is named appropriately when v1 closes. In the owner's words: "let's make sure packages are named appropriately at the end of v1 (done at each step and not at the end)". No rename is deferred to a final pass.
7. **`cmd/lenny-gateway`.** Each move step also moves the wiring of the part it moves into that part's package: its constructor, the flags only it reads, and its route registration under decision 3. Shared startup (stores, telemetry, and shutdown order) stays in `cmd/lenny-gateway`, which thins with every step and ends v1 as a composition root. Step 0117.S1 first adds two guard tests: one that fixes the set of flag names, defaults, and help text, and one that fixes the startup and shutdown order; every later step keeps both green. Settled by the owner on 2026-11-17 ("I'm ok with 0117's decision 7"), after an elaboration that recommended this option over moving only import paths, consistent with decisions 5 and 6.
8. **Seam operations that member changes remove, reshape, or add.** (a): the seam interface page states today's operations, as "SP-2" says. Each member change that removes, reshapes, or adds a mechanism behind a seam operation edits `spec/interfaces/gateway-seams.md` and `pkg/gateway/seam` in the step that changes the mechanism, and that step names the operations it edits. The affected changes are 0118, 0122, 0126, 0133, 0135, 0138, 0139, 0141, 0142, 0145, 0146, 0151, and 0153. Settled by the owner on 2026-11-17, choosing the recommendation.
9. **Crossings at the wiring level.** (a): a static check of `cmd/lenny-gateway` refuses a value of one part passed where another part expects an interface, unless the interface is declared in `pkg/gateway/seam`. Today's crossings are listed in a register that only shrinks, and each move step routes its crossings through the seam interface and deletes their rows. Settled by the owner on 2026-11-17, choosing the recommendation.
10. **Credential and admission packages.** (a): the layout gate confines `credentialstore`, `credleasestore`, the authentication middleware, `quota`, `policy`, and the tenant store to the session core, the metering proxy, the API front (the authentication middleware only), and `cmd/lenny-gateway`, with today's other importers listed in the register. The owner added no package to the list. Settled by the owner on 2026-11-17, choosing the recommendation. Decision 11 widens what the API front may import, and decision 13 extends the list.
11. **The API front's admin handlers.** The API front may import the admin stores, quota, the interceptor stores, and the rate limiter, which its admin handlers read, as well as the authentication middleware. This amends the allowed parts of decision 10: the API front is a replica-level part that is not extracted, and decision 10's reason concerns extracting a seam. "Policy" includes `pkg/gateway/policy/ratelimit`, which this decision allows to the API front. The packages decision 13 adds that the admin handlers import are allowed to the API front for the same reason. Settled by the owner on 2026-11-18, choosing the recommendation.

41. **How the session core serves the seams' calls until 0117.S11.** The session server is the core's side of the operations each split seam calls, and the composition root hands that side to the seam through the seam interfaces. 0117.S5 gives the upload handler `sessionserver.UploadSeam`, and 0117.S6 gives the stream proxy `sessionserver.StreamSeam`. Both serve `GWSEAM-LookupSession`, `GWSEAM-AuthorizeSession`, and `GWSEAM-RequestTenant`, so once both branches land the package holds two copies of those three methods and of the function that turns a stored session into a seam session record. (a) One adapter type per seam, holding only the operations that seam calls, with the shared operations' bodies in unexported methods of `Server` that each adapter calls, so the duplicate bodies collapse when the second of 0117.S5 and 0117.S6 merges. (b) One adapter type, such as `sessionserver.Seam`, that serves every operation the core serves to any seam, handed to each seam through the interfaces it holds. (c) Keep both types as they are until 0117.S11 moves the core and settles its side of the seam there. Recommendation: (a), built on 0117.S6: `StreamSeam` serves the seam interfaces the stream proxy takes, `seam.Sessions` (whose `GWSEAM-AuthorizeSession` it serves although the stream proxy does not call it today), `seam.StreamFrames`, and `seam.RequestIdentity`, and the shared bodies are already `Server` methods (`lookupSeamSession`, `authorizeSeamSession`, `requestSeamTenant`, and `seamSessionOf`). A seam's adapter then states which core operations that seam reaches, as the per-caller interfaces of 0117.S3 and 0117.S5 do. When 0117.S5 and 0117.S6 have both merged, `UploadSeam` points its three methods at those `Server` methods and its `seamSession` is deleted, because neither branch can name the other's code.

   Settled on option (a), the recommendation the branch built.

42. **Whether the session event bus enforces the tenant on every subscription.** The bus binds a session to the tenant of the first publish that names one on the serving replica and refuses a later subscription by another non-empty tenant. It does not refuse an empty tenant, a session whose events so far were published without a tenant (the platform tools seam's `agent_output`, elicitation, and input-expiry events, the lease elicitation, and the eviction bridge's `session.lost`), or a reader on a replica that never published for the session, whose backlog comes from the cross-replica relay, whose entries carry no tenant. Every route that reaches the bus today checks the tenant first (the session read check and the session lookup on the event and log streams, and `Authorize` on the platform tools seam's attach stream), so this is defense in depth rather than a path a client can take, and `main` behaves the same. (a) Keep this step behavior-preserving, state in `GWSEAM-Subscribe` what the bus enforces, and file the tightening as an issue under GWSTREAM for the step or change that owns the event stream. (b) Tighten now: the untenanted publishers pass the session's tenant, `Subscribe` refuses an empty tenant from a seam, and the relay entries carry the tenant that `History` checks. Recommendation: (a), built on 0117.S6 with the summary of `GWSEAM-Subscribe` corrected; the issue is filed when the owner chooses (a). 0117's steps are refactors that pass the same tests before and after, and (b) changes what three publishers send and what the relay stores, which 0138.S1's reshaping of `GWSEAM-Publish` also touches. Raised by the security review of 0117.S6.

   Settled on option (a), the recommendation the branch built.

43. **Whether the session authorization operation checks the principal's tenant.** `GWSEAM-AuthorizeSession` reads the session in the tenant its caller passes and grants access when the session's owner is the principal's subject, without comparing that tenant with the principal's. A seam that passed a tenant other than the request's would let a principal of one tenant reach another tenant's session owned by the same subject string. No caller does this today: the upload handler passes the request's tenant, and the stream proxy does not call the operation. (a) The core refuses, as a missing session, a principal bound to a tenant other than the one passed, before it reads the session. (b) The operation takes no tenant and reads it from the principal in the context, as the page's convention that an operation trusts the identity its caller's context carries suggests, which changes the operation's signature on 0117.S5 and 0117.S6. (c) Leave it to each caller. Recommendation: (a), built on 0117.S6 in the shared `authorizeSeamSession`, so the upload handler takes it when 0117.S5 merges and points `UploadSeam` at it (decision 41). It fails closed and changes no signature; (b) remains open to 0117.S8, when the API front holds the request identity. Raised by the security review of 0117.S6.

   Settled on option (a), the recommendation the branch built.
