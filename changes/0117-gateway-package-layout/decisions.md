# Decisions: 0117 Gateway package layout

## Open decisions

21. **The metrics a seam emits.** The wiring check counts the gateway's metric set (`replica/gatewaymetrics`) handed to a seam's metrics interface as a crossing, because a seam may not import a replica-level part. The seam interface page said each part emits its metrics through a metrics interface it declares, which the gateway's metric set satisfies. The register carried five such rows into the metering proxy at 0117.S4, and the stream proxy, the upload handler, and the platform tools seam meet the same question at 0117.S5 to 0117.S7.
    - (a) A seam registers its own metric collectors on the gateway's metric registry, which the composition root hands it as a `prometheus.Registerer`, a dependency type that is not a crossing target under decision 17. The upload handler's byte and queue metrics, the playground, the health service, the event bus, and the T4 KMS probe already register their own collectors this way.
    - (b) Each seam's metrics interfaces are declared in `pkg/gateway/seam` beside the operations, and the gateway's metric set still satisfies them.
    - (c) The wiring check leaves out a value of the gateway's metric set.

    Recommendation: (a). It follows the pattern the tree already uses, an extracted seam takes its collectors with it, and the check keeps its reach. Option (b) puts interfaces in the seam package that are not operations of the seam interface, and option (c) weakens the check. The branch of 0117.S4 builds (a): the seam page's "Crossings without an operation" says a seam registers its own collectors, and `llmproxy.PromMetrics` holds the metering proxy's active-connection, translation, credential rotation, fallback exhaustion, and session budget collectors with their names, labels, and buckets unchanged. The credential rotation and fallback exhaustion counters were built in the gateway's metric set but never registered, so `lenny_credential_rotation_total` and `lenny_gateway_credential_fallback_exhausted_total` were absent from `/metrics`; the metering proxy's set registers them. Choosing (b) or (c) moves the collectors back into `gatewaymetrics` and reverts the page edit. Raised by the build of 0117.S4 on 2026-11-18.

23. **Confined jobs on the replica's leader gate.** The leader gate (`replica/gatewayleader`) runs the gateway-singleton sweeps while the replica holds the leader lease. The composition root handed it the T4 KMS probe of `pkg/tenantkms`, which GW-R2 confines, as a job, which the wiring register carried as two confined-value rows at 0117.S4. The admin-token reclaimer, handed to the gate the same way, is registered at 0117.S8 under decision 16.
    - (a) The session core builds and holds the confined jobs in a set of its own (`pkg/gateway/core/leaderjobs`): the composition root hands the core the job's inputs, the core constructs the job, and the leader gate runs the set as one job, so the gate holds a session core value, which a replica-level part may hold.
    - (b) The leader gate reports each leadership term to the composition root, which starts the confined jobs itself. This adds a goroutine to the startup order that the order guard of decision 7 pins.
    - (c) GW-R2 lets the leader gate's job slot take a confined job, because the gate runs the job and reads nothing from it.

    Recommendation: (a). It keeps GW-R2 and both guards of decision 7 unchanged, and 0117.S8 builds the admin-token reclaimer in the same set. The set itself is a generic list of jobs, and the wiring check does not follow values into the slice it holds (`gatewaywiring/doc.go`), so the rule holds because the job is constructed inside the session core: `Set.AddT4KMSProbe` builds the T4 KMS probe and its metrics from the inputs the composition root passes, the key lifecycle and the tenant source among them, and registers the job. A job a later step adds to the set is held to the same form, which review checks. The branch of 0117.S4 builds (a): the gate runs the set as the job `core-leader-jobs`, and the startup log line counts every sweep. Choosing (b) or (c) removes `core/leaderjobs` and hands the probe back to the gate. Raised by the build of 0117.S4 on 2026-11-18, and reworded after the review of 0117.S4 found that the first build constructed the probe in the composition root and placed only the finished job in the set.

24. **Route registration for the parts of 0117.S4.** Decision 3 has each part register its routes with the API front through the route registration interface of `pkg/gateway/seam`, which no part implements until 0117.S8. The playground serves its routes on the client listener as path prefixes that dispatch by method inside the handler, and the drain and ops endpoints serve on the internal port, which the interface's listeners (client, pod proxy, and forward) do not name.
    - (a) The composition root keeps mounting these routes on today's muxes until 0117.S8 implements the interface, and 0117.S8 adds an internal listener to the interface and moves the registrations into the parts.
    - (b) The playground registers its routes now, one route per method and path, through an adapter over today's mux, and the internal routes wait for 0117.S8.

    Recommendation: (a). Option (b) changes how the client mux answers a method the playground does not serve, which the move steps leave unchanged, and the adapter would be written again at 0117.S8. The branch of 0117.S4 builds (a) by leaving the mounts in `cmd/lenny-gateway`. Raised by the build of 0117.S4 on 2026-11-18.

25. **Where the gateway's audit appender is declared.** The composition root typed its audit appender as `policy.AuditAppender`, an interface of the confined policy package, and built the in-memory appender with `policy.NewChainSetAppender`, so every gateway part it handed the appender to received a confined value. At 0117.S4 that was the forced-drain audit endpoint (`drain/drainreadiness`); the wiring register also carried the same value into the platform tools seam (`mcptools.Deps.VCSLeaseAuditor`, at 0117.S7) and the API front's circuit breaker reporter (`circuitbreaker.NewAuditReporter`, at 0117.S8). The appender writes the audit chain, which GW-R2 does not confine; it sat in the policy package beside the interceptor audit sink. Open decision 32 on the branch of 0117.S5 meets the same value in the upload handler's audit sink.
    - (a) Move the interface and the in-memory chain set appender to the audit concern, `pkg/audit`, as `audit.Appender` and `audit.ChainSetAppender`, so the appender is no confined value and every part that writes an audit event may hold it.
    - (b) Keep them in the policy package, and route each part's audit write through an operation of the seam interface that the session core serves, as 0117.S5's option (a) does with `GWSEAM-AuditUpload`.

    Recommendation: (a). The audit chain is a domain concern, the durable appender (`auditstore`) is already a domain package, and the move changes no audit behavior: the append stays synchronous and a zero time still takes the appender's clock. It removes the three rows, at 0117.S4, 0117.S7, and 0117.S8, that the type alone produced. Option (b) adds an operation per writer for a value that holds no credential or admission rule. The branch of 0117.S4 builds (a). If the owner chooses (a), 0117.S5's open decision 32 loses the reason its option (a) gives, and its option (b) is then built; choosing (b) here restores the policy package's types and the three rows. Raised by the review of 0117.S4 on 2026-11-18.

## Decisions

Settled by the owner on 2026-11-17 ("go with all your recommendations, except ..."); the questions as framed are in `review-history.md`.

1. **Domain packages.** All 124 domain packages leave `pkg/gateway`.
2. **Directory level.** Concern directories under `pkg/`, extending the existing ones.
3. **REST handlers.** Each part registers its own routes with the API front through the registration interface in `pkg/gateway/seam`.
4. **`sessionserver`.** The seam, plumbing, and domain files move out, and the rest, about 19,400 lines, stays as one session core package.
5. **Packages a member change removes.** They stay in place, listed in the layout gate's register with the change that removes it. In the owner's words: "keep in place but remember to move at the end if for whatever reason they weren't deleted (fully or partially)". Step 0117.S13 runs before v1 closes and moves into the layout whatever a removal left, whole packages or parts, so the register is empty when v1 closes.
6. **Package names.** Directories change, and each move step settles the names of the packages it moves: a package keeps its name where the name fits its component page or concern, and is renamed in the same step where it does not, so that every package is named appropriately when v1 closes. In the owner's words: "let's make sure packages are named appropriately at the end of v1 (done at each step and not at the end)". No rename is deferred to a final pass.
7. **`cmd/lenny-gateway`.** Each move step also moves the wiring of the part it moves into that part's package: its constructor, the flags only it reads, and its route registration under decision 3. Shared startup (stores, telemetry, and shutdown order) stays in `cmd/lenny-gateway`, which thins with every step and ends v1 as a composition root. Step 0117.S1 first adds two guard tests: one that fixes the set of flag names, defaults, and help text, and one that fixes the startup and shutdown order; every later step keeps both green. Settled by the owner on 2026-11-17 ("I'm ok with 0117's decision 7"), after an elaboration that recommended this option over moving only import paths, consistent with decisions 5 and 6.
8. **Seam operations that member changes remove, reshape, or add.** (a): the seam interface page states today's operations, as "SP-2" says. Each member change that removes, reshapes, or adds a mechanism behind a seam operation edits `spec/interfaces/gateway-seams.md` and `pkg/gateway/seam` in the step that changes the mechanism, and that step names the operations it edits. The affected changes are 0118, 0122, 0126, 0133, 0135, 0138, 0139, 0141, 0142, 0145, 0146, 0151, and 0153. Settled by the owner on 2026-11-17, choosing the recommendation.
9. **Crossings at the wiring level.** (a): a static check of `cmd/lenny-gateway` refuses a value of one part passed where another part expects an interface, unless the interface is declared in `pkg/gateway/seam`. Today's crossings are listed in a register that only shrinks, and each move step routes its crossings through the seam interface and deletes their rows. Settled by the owner on 2026-11-17, choosing the recommendation.
10. **Credential and admission packages.** (a): the layout gate confines `credentialstore`, `credleasestore`, the authentication middleware, `quota`, `policy`, and the tenant store to the session core, the metering proxy, the API front (the authentication middleware only), and `cmd/lenny-gateway`, with today's other importers listed in the register. The owner added no package to the list. Settled by the owner on 2026-11-17, choosing the recommendation. Decision 11 widens what the API front may import, and decision 13 extends the list.
11. **The API front's admin handlers.** The API front may import the admin stores, quota, the interceptor stores, and the rate limiter, which its admin handlers read, as well as the authentication middleware. This amends the allowed parts of decision 10: the API front is a replica-level part that is not extracted, and decision 10's reason concerns extracting a seam. "Policy" includes `pkg/gateway/policy/ratelimit`, which this decision allows to the API front. The packages decision 13 adds that the admin handlers import are allowed to the API front for the same reason. Settled by the owner on 2026-11-18, choosing the recommendation.
12. **The wiring check's scope.** The check counts a crossing only where the import rules would refuse the receiving part importing the value's part, and GW-R1's wiring sentence says so. An adapter type that `cmd/lenny-gateway` declares is attributed to the parts whose values its fields hold, and a function literal to the parts whose functions or methods it calls or whose values it captures. 20. **How the metering proxy's budget expiry reaches the session core.** When a session exhausts its token budget, the budget enforcer of the metering proxy calls a terminator that `cmd/lenny-gateway` declares. The terminator writes the session's expired state through the session store and then runs the session core's terminal pipeline (`Server.BeginTerminal` and `Server.OnSessionTerminal`). The wiring register carried this as four crossings at 0117.S3. The seam interface page of 0117.S1 listed the metering proxy among the callers of `GWSEAM-BeginTerminal` and `GWSEAM-OnSessionTerminal`, which pass the session as the seam's session record, a subset of the stored row that the terminal pipeline reads.
    - (a) Add an operation served by the session core to the metering proxy, `GWSEAM-ExpireSession`, which writes the expired state with the caller's failure reason and runs the terminal pipeline. The terminator stays on the core's side of the seam, and the enforcer reaches it only through the operation.
    - (b) Move the terminator into the metering proxy. It writes the expired state through the session store, a domain package any part may import, and calls `GWSEAM-BeginTerminal` and `GWSEAM-OnSessionTerminal`. The session core implements both and re-reads the stored row from the session record the seam passes.

    Recommendation: (a). It changes no behavior: the terminal pipeline runs on the row the write returned, as today, with no second read and no new failure path. It also keeps the session's state writes in the session core, so an extracted metering proxy holds no write access to the session store. The branch of 0117.S3 builds (a): the specification edit adds `GWSEAM-ExpireSession` and removes the metering proxy from the callers of the terminal pipeline operations. Choosing (b) reverts that edit, moves the terminator into `pkg/gateway/meteringproxy/sessionbudget`, and adds the core's implementation of `seam.Terminals`. Either way, open decision 5 of 0133 settles whether 0133.S3 keeps the expiry when it replaces the enforcer. Raised by the build of 0117.S3 on 2026-11-18.

   Settled on option (a), the recommendation the branch built.

22. **The web playground's token packages.** The playground mints the playground bearer itself: it signs and verifies JWTs through `pkg/auth/jwt`, reads the issued-token store, and checks that a tenant exists through the tenant store. GW-R2 confines all three and allowed none of them to the playground, so the layout register carried two import rows and the wiring register eight confined-value rows at 0117.S4.
    - (a) GW-R2 lets the web playground import the JWT package, the issued-token store, and the tenant store, the packages its token mint reads, as decision 11 lets the API front import the packages its admin handlers read.
    - (b) Route the mint through operations of the seam interface served by the session core: sign, verify, read an issued-token row, and look up a tenant, with claim values that `pkg/gateway/seam` declares, because the seam package may not import the JWT package.
    - (c) Move the playground's token routes into the API front, which GW-R2 already allows those packages, and leave the playground the UI and its session records.

    Recommendation: (a). The playground is a replica-level part that is not extracted, which is decision 11's reason for the API front, and the packages are the ones the API front may already import. Option (b) adds four operations that exist only to keep a token issuer away from its signing package, and option (c) splits the playground's component page across two parts. The branch of 0117.S4 builds (a) in GW-R2, `confined.go` (a `Playground` mark on the JWT package, the issued-token store, and the tenant store at both their paths), the layout gate's tests, `pkg/gateway/ARCHITECTURE.md`, and `code-best-practices.md`. Choosing (b) or (c) reverts those edits and restores the ten rows until the step that builds the choice. Whichever option the owner chooses meets 0149 next: its browser login (TS-6 and TS-7) moves the playground's login onto the identity-source registry's resolver and its mint under `/t/{tenantId}/playground/`, so the packages that resolver reads either join this allowance or reach the playground through the option chosen here. Raised by the build of 0117.S4 on 2026-11-18.
