52. **How the session core receives the stored session that a platform tool read or wrote.** The session core's logic behind the operations the platform tools seam calls (the terminal pipeline after a cancel, the orphan sweep, and the deadlock writer, held delivery, resume, forwarding, the retry budget, experiment routing for a child not yet created, and starting a tree node) reads fields of the stored session row that the seam's session record does not carry, such as the retry policy, the isolation profile, the resume windows, and the pod assignment. Today those calls pass the full row.
    - (a) The session record carries the row the caller read or wrote in `seam.Session.Stored`, typed `any` because `seam` may not import the session store until 0117.S12 moves it out of `pkg/gateway`. The core uses it when present and its identifier and tenant are the record's, and returns the row its logic produced in the same field of the record it returns, which the seam reads back, so the field carries rows in both directions. For a record that carries no row, the terminal pipeline re-reads the row from the primary, and the other operations run on the row the record's fields describe.
    - (b) The core always re-reads the row by tenant and identifier, from the primary for the terminal pipeline: one more read per call, a new failure path (on which the terminal pipeline runs on the record's fields so the pod is still released, and a tree node is not started so its level timeout fails it), and no row at all for an uncreated child under experiment routing.
    - (c) The record carries every field the core reads.
    - (d) The core performs the platform tools seam's state writes itself through new operations, as `GWSEAM-ExpireSession` does for the metering proxy.

    Recommendation: (a). It changes no behavior: the core runs on the row the write returned, as today, with no second read and no new failure path. Option (c) copies most of the stored row into the seam package, and (d) moves the cancel and sweep writes out of the seam that owns them. The branch of 0117.S7 builds (a), with (b)'s re-read as the terminal pipeline's fallback for a record without a row (`sessionserver.ToolsSeam`'s `terminalRow`, `rowOf`, and `recordRow`, and `platformtools/seamrow`), and the seam page's "Values" convention says a record may carry the stored row in both directions. Since the review of 0117.S7, the core and `seamrow` ignore a carried row whose identifier or tenant differs from the record's. 0117.S12 types the field once the session store is a domain package outside `pkg/gateway`. Choosing (b) deletes the field and keeps the re-read; choosing (c) or (d) is built where the choice names. Raised by the build of 0117.S7 on 2026-11-18.

## Decisions

Settled by the owner on 2026-11-17 ("go with all your recommendations, except ..."); the questions as framed are in `review-history.md`.

1. **Domain packages.** All 124 domain packages leave `pkg/gateway`.
2. **Directory level.** Concern directories under `pkg/`, extending the existing ones.
3. **REST handlers.** Each part registers its own routes with the API front through the registration interface in `pkg/gateway/seam`.
4. **`sessionserver`.** The seam, plumbing, and domain files move out, and the rest, about 19,400 lines, stays as one session core package.
5. **Packages a member change removes.** They stay in place, listed in the layout gate's register with the change that removes it. In the owner's words: "keep in place but remember to move at the end if for whatever reason they weren't deleted (fully or partially)". Step 0117.S13 runs before v1 closes and moves into the layout whatever a removal left, whole packages or parts, so the register is empty when v1 closes.
6. **Package names.** Directories change, and each move step settles the names of the packages it moves: a package keeps its name where the name fits its component page or concern, and is renamed in the same step where it does not, so that every package is named appropriately when v1 closes. In the owner's words: "let's make sure packages are named appropriately at the end of v1 (done at each step and not at the end)". No rename is deferred to a final pass.
7. **`cmd/lenny-gateway`.** Each move step also moves the wiring of the part it moves into that part's package: its constructor, the flags only it reads, and its route registration under decision 3. Shared startup (stores, telemetry, and shutdown order) stays in `cmd/lenny-gateway`, which thins with every step and ends v1 as a composition root. Step 0117.S1 first adds two guard tests: one that fixes the set of flag names, defaults, and help text, and one that fixes the startup and shutdown order; every later step keeps both green. Settled by the owner on 2026-11-17 ("I'm ok with 0117's decision 7"), after an elaboration that recommended this option over moving only import paths, consistent with decisions 5 and 6.
