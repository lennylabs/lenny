## Problem

A pool with `sessionPolicy.maxConcurrentSessionsPerPod` above 1 runs several sessions on one pod, and those sessions can belong to different users of one tenant. Today they share one runtime container, one UID, one process namespace, `/tmp`, and a group that reads every slot's credential file. The deployer accepts this through the concurrent-session acknowledgment of [§5.2](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes), "Deployer acknowledgment (concurrent sessions)", which PL renames `acknowledgeSharedPod` **[source]**.

That sharing blocks features the other designs need:

- A process in one session can act for another session on the same pod. A per-session token does not help, because every process in the container runs as the same UID and can read where the token is kept.
- `netagent`, the egress container of [`0127-egress-and-git`](../0127-egress-and-git/change.md), cannot tell which slot sent a request, because every slot runs under one UID. Such pods get per-pool policy today, and [`0152-user-git-identity`](../0152-user-git-identity/change.md) and [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) refuse or weaken user features on them **[source]**. The egress design's decisions 52 and 60 attribute and scope each connection by its slot's UID once this design gives each slot its own ("SI-10").
- Slot cleanup kills the slot's process group, and a process that calls `setsid` escapes it **[measured]**.

Giving each session its own UID raises a second problem: the adapter, which runs under its own UID and holds no capability, has to read every file a session can write for checkpoints, and write files that the session owns for restores. Files created with mode `0600`, such as those from `mkstemp` or an editor's atomic save, are unreadable to the adapter under any scheme that relies on permission bits **[measured]**.

The owner asked for "the proper solution, potentially using kubernetes user namespaces", then for a spike that answers the open questions, explains how shared pre-materialized resources such as a git repository work, and shows how a pod's CPU and memory budget is shared across containers, including "can a container use a non-proportional % of pod resources during transient tasks?".

## Scope

In scope:

- One slot container per slot, each under its own UID, on every agent pod, whatever its `maxConcurrentSessionsPerPod` ("SI-1"). PL owns the blueprint, the paths, and the volumes.
- The adapter's identification of each slot by per-slot socket names and the peer UID of each connection ("SI-2").
- A fresh runtime process for every session, launched at bind; the slot release; and the supervisor's worker, which runs setup and cleanup ("SI-3").
- Per-slot liveness and dead slots ("SI-4").
- The supervisor's file-descriptor broker, and the rules of the whole `CH-SUPERVISE` connection ("SI-5").
- The isolation rules of checkpoint, restore, export, and cleanup through the broker ("SI-6").
- Per-slot credentials and manifests ("SI-7").
- Shared repository stores across slot containers ("SI-8").
- CPU and memory across slot containers ("SI-9").
- What slots still share, and the acknowledgment that remains ("SI-10").
- User namespaces on runc pools, and Landlock ("SI-11").

Non-goals:

- The pod blueprint, the runtime-visible paths, the volumes with their media and size limits, the reserved `/lenny` root, and the field renames. [PL](../0118-agent-pod-layout/change.md) owns them.
- What is written into a workspace and by whom: the `lenny-materialize` helper, its plan and result, the git steps, the warm checkouts, archive extraction, and fetch grants. [WM](../0153-workspace-materialization/change.md) owns them.
- Node classes, node tenancy, the node prerequisites of user namespaces, and the separation of profiles on nodes. [PM](../0136-placement/change.md) owns them.
- The checkpoint itself: the walk, the index, the change rules, the clone fallback, the spool, staggering across slots, and restore. [IC](../0131-incremental-checkpoint/change.md) owns them, and SI states only the broker rules they rest on (D3, D9).
- The protocol between the adapter and the runtime. [RP](../0139-runtime-protocol/change.md) owns it.
- Runtimes other than agent runtimes. [`0119-agent-runtimes-only`](../0119-agent-runtimes-only/change.md) removed `type: mcp` runtimes and service mode, so every pod this design covers is an agent pod whose sessions bind to slots.
- A separate network namespace or IPC namespace per slot. Kubernetes gives one of each per pod.
- Isolation between users who distrust each other. One session per pod remains the boundary for that ("SI-10").

## Terms

| Term | Meaning |
| :-- | :-- |
| Slot | One of the places on a pod where a session runs. A pod has a slot count, equal to the pool's `maxConcurrentSessionsPerPod` when the pod is created and recorded on the pod ("SI-4"). |
| Slot container | The runtime container that serves one slot. It is named `runtime-<n>` for slot index `n`, runs the runtime supervisor as its first process, and runs under the slot UID ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)). |
| Slot UID and slot GID | The UID and GID a slot container runs under. Each slot of a pod has its own pair, and every pod uses the same in-pod pair for the same slot index. Under user namespaces each pod maps them to host UIDs of its own ("SI-11"). |
| Slot volumes | The volumes of one slot that PL lists: the workspace volume at `/workspace`, the session volume at `/session`, the scratch volume at `/tmp`, the shared-memory volume at `/dev/shm`, and the run volume at `/run/lenny`. Each is mounted only into its own slot container, and the workspace, session, and run volumes also into the adapter ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). |
| Brokered volume | A slot volume that the slot's broker serves as a root: the workspace volume, as the root `workspace`, and the session volume, as the root `session`. The scratch volume is served as a third root, `tmp`, for the per-slot disk watch alone ("SI-5"). |
| Mount boundary | The rule that a volume is reachable only from the containers that mount it. |
| Run | A `setup` or `cleanup` request that the supervisor is executing. At most one run is outstanding in a slot ("SI-3"). |
| Refusal | A reply whose error is `malformed_request`, `gen_mismatch`, or `worker_busy`. It means the supervisor did not execute the request ("SI-5"). |
| Cancel pipe | A pipe whose read end the adapter passes at index 2 of every `setup` and which only the supervisor keeps. The adapter cancels the run by closing the write end ("SI-3"). |
| Log pipes | Two pipes whose write ends a setup program receives as its standard output and standard error, and whose read ends the adapter holds ("SI-3"). |
| File-descriptor broker | The supervisor's handling of the `fs` request on `CH-SUPERVISE`: it opens, creates, stats, or watches entries of its slot's brokered volumes as the slot UID, confined beneath a pinned root, and passes descriptors to the adapter over `SCM_RIGHTS` ("SI-5"). |
| Broker root | A directory descriptor the supervisor opens on each brokered volume when it starts, before any session binds to the slot, beneath which it resolves every request for the pod's life. |
| Pin | The device and mount ID that the adapter records from each broker root before the pod reports READY, and against which it checks every descriptor and every stat result ("SI-5"). |
| `statat` | The broker operation that returns the identity of up to 253 entries as integers, with no descriptor ("SI-5"). |
| Parallel stat walk | IC's walk that lists each directory through a broker-passed directory descriptor with the adapter's own `getdents`, stats its entries in parallel relative to that descriptor, and falls back to the broker per directory on `EACCES`. IC owns the walk, and "SI-5" states its broker rules. |
| Request deadline `D(n)` | The time the adapter allows an `fs` request of `n` paths: 1 s plus 4 ms for each path ("SI-5"). |
| Metadata-only entry | An entry the slot owner itself cannot open without changing its mode, such as a file with mode `0000` or a directory with mode `0300`. A checkpoint records its type, mode, and times and no content (O2). |
| Peer UID | The UID that `SO_PEERCRED` reports for the process at the other end of a Unix socket. |
| End | The runtime supervisor's operation that sends SIGTERM and then SIGKILL to every other process in its container through `kill(-1, …)`, and attests the end after two passes find none ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model), **Runtime supervisor.**; `supervisor/procs.c`) **[source]**. |
| Sweep | The runtime supervisor's operation that removes the slot UID's IPC objects and files in its container's writable volumes ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model), **Runtime supervisor.**; `supervisor/sweep.c`) **[source]**. "SI-3" states the coverage and the fixes this design requires. |
| Launch at bind | The rule that a slot's runtime process starts only after its session's workspace is materialized and its setup commands have run (D15, "SI-3"). |
| Slot release | The sequence at the end of each session in a slot: End, Sweep, the pool's cleanup commands, End again, a second Sweep, the adapter's removal of what remains, an emptiness check, and the staging of the warm checkouts. It launches nothing ("SI-3"). |
| Start-up canary | The file `.lenny-canary` that each supervisor writes on each brokered volume, and that the adapter must see through its own mount before it reports READY ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). |
| Dead slot | A slot whose container has ended, whose supervisor link failed, whose broker missed a deadline, or whose slot release failed, including a release that left a brokered volume not empty. It serves no session for the rest of the pod's life, counts in the pod's occupancy, and is recorded in the pod state mirror's `dead_slots` column. It replaces the specification's `leaked` slot (D38, "SI-4"). |
| Pod-wide scrub | What remains of the specification's whole-pod scrub once every slot release has run: the cleanup of pod-wide state outside any slot when a recycling pod's occupancy reaches zero, and its report through `ReportPodScrub` (D39, "SI-3"). |
| Scrub profile | The pool's `recycle.scrubProfile`: `standard`, which runs the pod-wide scrub and holds the pod for its tenant, or `vm-restart`, on a `microvm` pool, which runs it and retires the pod for a fresh one (D39, "SI-3"). |
| Shared pod | A pod with a slot count above 1, which a pool runs only with `acknowledgeSharedPod` ("SI-10"). |
| Dedicated volume GID | The GID that a Kata `block-plain` pool sets as `fsGroup` and that nothing else uses ("SI-1"). |
| Never-launched pod | A pod to which no session has bound, so no runtime process, setup command, or session materialization has run in it, and the only code that has run in its slot containers is the platform's: the supervisor and `lenny-materialize` on warm-up checkouts ("SI-2"). IC's platform chunk sets accept contributions only from such a pod ([`0131-incremental-checkpoint`, "Platform chunk sets"](../0131-incremental-checkpoint/change.md#platform-chunk-sets)). |
| Pod-level resources | The Kubernetes `spec.resources` field on a pod, which sets one CPU and memory budget for all its containers. It is beta and on by default since Kubernetes 1.34 **[external]**. |

## High-level design

Every agent pod gets one runtime container per slot, and a pod with one slot has one such container. Each slot container runs its own copy of the runtime supervisor under a UID and GID that belong to that slot. PL lays out the pod: the containers, the paths a runtime sees, and the volumes.

Each slot's volumes are mounted whole into that one slot container, and its workspace, session, and run volumes into the adapter as well. A slot cannot see another slot's files, because they are not mounted in its container, and it cannot see another slot's processes, because each container has its own process namespace.

The adapter does not read a slot's files through permission bits. It asks that slot's supervisor to open, create, or stat them. The supervisor runs as the slot's UID, so it can open every file the session itself can open, including files created with mode `0600`. It resolves every path beneath a root it opened before any session bound to the slot, refuses links out of it, and passes descriptors to the adapter over the socket. The adapter checks each descriptor before it uses it, and does all the checkpoint work itself.

The supervisor also runs programs for the adapter: setup commands, the pool's cleanup commands, and the materialization helper. It runs one such program at a time, and while one runs it keeps answering file requests, pings, and `end`. The adapter cancels a program by closing a pipe.

Each slot has its own socket names. The adapter listens on a name per slot, and every connection is checked in both directions. A process in one slot cannot act for another slot's session, which makes platform tools safe on pods that serve several sessions.

Every session gets a fresh runtime process, launched when the session binds, after its workspace is written and its setup commands have run. When a session ends, the supervisor ends every process in the slot container and sweeps the slot's files, the pool's cleanup commands run, the adapter checks that the slot is empty, and the warm checkouts for the next session are staged. No runtime process waits in a free slot.

A slot whose container dies, or whose supervisor stops answering, stays dead for the pod's life, and the pod keeps serving sessions on its other slots until enough slots have died to replace it.

CPU can burst: a slot uses idle CPU up to the pod's limit. Memory is split into hard per-slot limits.

What stays shared is the network namespace, the IPC namespace, the adapter and `netagent`, the node's disk, and the kernel. `netagent` serves every slot, and scopes each slot's connections to that slot's session. On runc pools user namespaces are on by default, so each pod's UIDs map to a host range of its own.

```
 agent pod (Pod Security Standards Restricted)
 +----------------------------------------------------------------------------------+
 | adapter (adapter UID)                       netagent (native sidecar)            |
 |   listens: @lenny-runtime-<n> (runtime and tool connections),                    |
 |            @lenny-supervise-<n>, for each slot n                                 |
 |   reaches slot files only through slot n's broker (SCM_RIGHTS)                   |
 |                                                                                  |
 | runtime-0 (slot 0 UID)              runtime-1 (slot 1 UID)            ...        |
 |   PID 1: supervisor                   PID 1: supervisor                          |
 |     broker (fs), one run at a time      broker (fs), one run at a time           |
 |   runtime process, launched at bind   runtime process, launched at bind          |
 |   slot 0's volumes only               slot 1's volumes only                      |
 +----------------------------------------------------------------------------------+
   shared: network namespace, IPC namespace, adapter, netagent, node disk, kernel
   runc pods: hostUsers: false, so the pod's UIDs map to a host range of its own
```

**O12. Whether the Sweep runs again after the cleanup commands. Settled 2026-11-13: (a)** (D23).

The release runs End, Sweep, the pool's cleanup commands, and End ("SI-3"). The second End kills what the cleanup commands left running, but nothing removes the files they leave in `/tmp` or `/dev/shm`, which the adapter does not mount and the emptiness check does not cover. Cleanup commands run as the slot UID, so such a file reaches the next session in the slot, which can belong to another user.

- (a) A second Sweep after the second End: End, Sweep, cleanup, End, Sweep. The second Sweep finds only what the cleanup commands left.
- (b) Keep the order, and state that cleanup commands write nothing outside the brokered volumes, whose emptiness check catches what they leave there.
- (c) Run the cleanup commands first: End, cleanup, End, Sweep.

**Recommendation: (a).** It costs one walk of nearly empty volumes and keeps the first Sweep ahead of the cleanup commands. (c) would let session-planted files, such as a shell profile under `HOME=/tmp/home`, reach the cleanup commands, which the first Sweep prevents today. (b) leaves the rule to each deployer. "SI-3" states the release with the second Sweep.

**O13. How the per-slot disk watch measures a volume's use. Settled 2026-11-13 through PL's O8** (D24).

The adapter fails a slot's session at `adapter.diskWatchThresholdPercent` of a disk-backed slot volume's `sizeLimit`, 90% by default, before the kubelet evicts the pod ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). On runc, `statfs` on an `emptyDir` reports the whole node filesystem **[measured]**, so the watch cannot use it. PL makes `/tmp` disk-backed and inside the watch, and the adapter does not mount `/tmp`.

- (a) The adapter sums allocated blocks over a parallel stat walk of each brokered volume at a fixed interval, a chart value of 30 s by default, and reuses the sum of a checkpoint walk that ran within the interval. `/tmp` becomes a third broker root, `tmp`, which serves `open` of a directory and `statat` only, for this walk.
- (b) A supervisor request that walks a volume as the slot UID and answers one integer.
- (c) The kubelet's per-volume figure, read by a controller from the node's statistics and forwarded to the adapter.

**Recommendation: (a).** It reuses the parallel stat walk and its checks, and it keeps every walk in the adapter (D3). A walk of a Chromium-sized tree costs 0.3 s under runc and up to 7 s on Kata `virtio-fs` at the measured rates **[inference]**, which a 30 s interval bounds. (b) adds a tree walk to the supervisor beyond the Sweep. (c) gives the adapter a figure only as fresh as the kubelet's own measurement, which is the figure the watch has to beat. Under every option a writer faster than the interval reaches the kubelet's limit first, as PL's "Limits" states.

The owner settled the question on PL's O8 instead, in a revised form that keeps (a)'s walk where nothing cheaper works: the adapter reads `statfs` on a broker-passed root descriptor where the runtime reports the volume, keeps a running total from the change tracker's events where the tracker runs, with a periodic recalibration walk, and walks every 10 s only elsewhere ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). The `tmp` root of (a) is adopted ("SI-5").

## Current state

### Specification

- **Pod security.** Every agent-pod container drops all capabilities, runs non-root, and states its own `runAsUser` and `runAsGroup`. The adapter UID is reserved for the container named `adapter` and the agent UID for the container named `runtime` ([§13.1](../../spec/13_security-model.md#131-pod-security), **Container identity.**) **[source]**. `shareProcessNamespace`, `hostPID`, `hostNetwork`, and `hostIPC` are forbidden on every agent pod **[source]**.
- **Cross-UID delivery.** The pod sets `fsGroup` and `supplementalGroups` to the `lenny-cred-readers` GID, and the adapter writes the credential file `0440` for the runtime to read through that group ("Cross-UID file delivery without `CAP_CHOWN` (fsGroup-based)") **[source]**. On a pod with several slots, "any slot's agent code can read every other slot's credential file" ("Per-slot credential-read scope") **[source]**. `lenny-ephemeral-container-cred-guard` refuses an ephemeral container whose `runAsUser` is the adapter or agent UID, or whose groups include the `lenny-cred-readers` GID, or that omits its identity fields ("`lenny-cred-readers` membership boundary") **[source]**.
- **Connection checks.** The adapter accepts `CH-MSGSOCK` only from the agent UID by `SO_PEERCRED`, with a manifest nonce as a second check; `requireSoPeercred: false` accepts a nonce-only mode ([§4.7.11](../../spec/04_system-components.md#4711-adapter-agent-security-boundary) item 1) **[source]**. `CH-SUPERVISE` admits one connection for the pod's life, guarded by `restartPolicy: Never`, "the adapter's closing of its listener after the first connection it accepts before READY", and the supervisor's exit when that connection closes ([§28.5.3](../../spec/28_communication-channels.md#2853-intra-pod), `CH-SUPERVISE` **Exclusivity.**; [§28.6](../../spec/28_communication-channels.md#286-exclusivity-and-concurrency-model), **One connection per pod.**) **[source]**. No `CH-SUPERVISE` message carries a byte a runtime process or a cleanup command wrote, and the adapter "has at most one request outstanding" **[source]**.
- **Process model.** One runtime process serves every session on the pod over one `CH-MSGSOCK` connection, "multiplexed by `sessionId`" ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model), **Runtime process lifetime.**) **[source]**. Between an attested End and the next launch "the adapter closes and rebinds its `CH-MSGSOCK` listener", and a failed rebind is a cause under **Liveness.** **[source]**.
- **Runtime-process lifetime.** A pod is `keep` or `restart`, fixed from `recycle.runtimeProcess` and recorded in the label `lenny.dev/runtime-process`. On a `keep` pod the runtime process serves later sessions, behind the acknowledgment for a runtime process kept across sessions ([§5.2](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes)) **[source]**.
- **Supervisor.** End sends SIGTERM and then SIGKILL "to every other process in the runtime container" and attests the end after "two consecutive passes find no other process". Sweep runs on a `restart` pod and removes the agent UID's IPC objects and files in the container's writable volumes, except the workspace's `slots/` directory. The supervisor ignores the kubelet's stop signal and keeps serving until the adapter's `end` ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model), **Runtime supervisor.**, **Signals.**) **[source]**.
- **Liveness.** "The adapter holds one not-live state for the pod", set by a reply error, a link failure, a runtime exit, and other causes, and "nothing clears it, because the pod retires" ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model), **Liveness.**) **[source]**.
- **Slots.** Slot cleanup "kills any processes owned by the slot's process group"; a failed slot is marked `failed` under **Failure isolation:**; a pod is replaced when half of its slots, rounded up, are unhealthy; the gateway reserves slots in the Redis set `lenny:pod:{pod_id}:active_slots` against the pool's concurrent-session count ([§5.2](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes)); a slot whose cleanup is not acknowledged clean enters the `leaked` sub-state, stays in occupancy as a `leaked:<sessionId>` member of that set for the pod's life, and is counted by `lenny_adapter_leaked_slots` ([§6.2](../../spec/06_warm-pod-model.md#62-pod-state-machine), **`leaked` slot semantics.**). After a Redis restart, rehydration rebuilds the set from the rows of the sessions holding the pod alone, so a `leaked` member is lost and the pod looks as if it had a free slot (**Post-recovery rehydration atomicity.**) **[source]**.
- **Recycling.** On a pool with one session per pod, a session that ends in failure or a crash retires the pod, and a release ends the occupancy without reuse "when the session failed or crashed" ([§4.6.3](../../spec/04_system-components.md#463-crd-field-ownership-and-write-boundaries), the `SandboxClaim` row; [§5.2](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes), **Pod retirement policy (recycling pools).**). The retirement condition **Runtime not live:** retires a pod whose `ReportPodScrub` states that its runtime cannot serve the next session, with the reason `runtime_not_live`. `recycle.scrubProfile` takes `standard`, `vm-restart`, or `in-place`, `in-place` requires `acknowledgeMicrovmResidualState`, and `onScrubFailure` and `maxScrubFailures` govern the whole-pod scrub (**Kata/microvm scrub variant.**, **`onScrubFailure` behaviors:**) **[source]**.
- **Setup commands.** They run in the session's working directory ([§7.5](../../spec/07_session-lifecycle.md#75-setup-commands)) **[source]**.
- **Profiles.** [§5.3](../../spec/05_runtime-registry-and-pool-model.md#53-isolation-profiles) labels runc "Development/testing only" **[source]**.
- **Minimum Kubernetes.** The installer's preflight checks a server version of 1.27 or later ([§17.6](../../spec/17_deployment-topology.md#176-packaging-and-installation), "Checks performed") **[source]**.

### What today's adapter can reach in the runtime's files

The adapter and the runtime share the `lenny-cred-readers` GID through `fsGroup`. The adapter reads a file the runtime created through its group or other bits, which the runtime's umask decides, and it holds no capability, so it cannot read a file the runtime created with mode `0600` **[inference from the modes and the capability posture]**. Spike 2 measured the same loss under per-slot UIDs: `0600` files, the contents of `0700` directories, and a `0644` file replaced by an atomic save through Python's `tempfile`, which leaves it `0600` **[measured]**. A restore today writes adapter-owned files, so the session's ownership, hard links, and exact modes are lost **[measured]**.

## SI-1 Pod layout

**The blueprint.** [PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint) lists the containers of an agent pod with slot count `N`: an init container that stages the platform binaries, `netagent`, the `lenny-store-fill` init container, `adapter`, the slot containers `runtime-0` to `runtime-<N-1>`, each running the supervisor as PID 1 under its slot UID, and `keepalive`. [PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout) states the paths a runtime sees, and [PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction) states the volumes. This section states the isolation properties that the layout gives.

**Processes.** `shareProcessNamespace` stays false, so each slot container has its own process namespace and a slot sees only its own processes **[measured]**.

**The mount boundary.** Each slot's volumes are mounted into its own slot container and, for the workspace, session, and run volumes, into the adapter, and into no other container. No mount uses `subPath` (PLR-10). Spike 1 found that a `subPath` layout fails silently under gVisor with the pod-share annotation: the adapter and the slot got disjoint views, so the adapter would have checkpointed none of the slot's files and reported no error **[measured]**. Spike 2 ran whole-volume mounts under runc, gVisor, and gVisor with the pod-share annotation, and every byte of every file the adapter could read came back **[measured]**.

**The working tree is a mount point.** `/workspace` is the workspace volume's root, so a slot cannot rename or remove it: spike 2 measured `EACCES` and `EBUSY` **[measured]**. Revision 3's defence against a slot renaming its session directory, and its rule that the adapter reopen a session root from the volume root on every operation, have no subject left. The volume root's mode is `0777` under runc and gVisor's default mount and `1777` under gVisor's pod-share annotation **[measured]**, and "SI-3" covers the `1777` case at release.

**UIDs.** Slot `n` runs as `slotUidBase + n` with GID `slotGidBase + n`. The bases are chart values chosen so that the range meets none of the UIDs of `adapter`, `netagent`, `keepalive`, `lenny-bin-stage`, and `lenny-store-fill`, nor the store GID (SIR-39), and every pod uses the same in-pod values. Under user namespaces each pod maps them to a host range of its own ("SI-11"). The slot count is recorded in `spec.slotCount` of the pod's `AgentPod` when the pod is created ("SI-4").

**Security context.** Every container keeps today's posture: non-root, every capability dropped, no privilege escalation, and the RuntimeDefault seccomp profile. The pod sets no pod-level `supplementalGroups`, and no `fsGroup` except on Kata `block-plain` (SIR-31). No slot's access relies on group permissions. The one use of a group is the adapter's deletion of withheld stores on the store volume ("SI-8"). Every pod the spikes ran passed Pod Security Standards Restricted admission **[measured]**.

**Kata `block-plain` (D16).** Under Kata with `emptydir_mode = "block-plain"`, each disk-backed `emptyDir` is an ext4 file system on its own virtual disk in the guest, and without `fsGroup` its root comes up `root:root` with mode `0755`, which the slot UID cannot write **[measured]**. A Kata `block-plain` pool therefore sets `fsGroup` to the dedicated volume GID, a chart value outside the slot GIDs that differs from the adapter's GID. The AWS run used 29000 **[measured]**. With it, disk roots come up `root:<GID>` with mode `2775`, `lost+found` comes up `2770`, and memory-backed roots come up `3777` **[measured]**. Its effects:

- **Every process carries the GID.** The supervisor, the runtime process, every other process of each slot, and the adapter carry it as a supplementary group **[measured]**.
- **Slots stay apart.** No path in one slot reaches another slot's volumes. A slot reaches another slot's object through the GID only when that slot's owner assigns the object to the GID with `chown` or `IPC_SET` in a namespace both share, which the owner can grant without `fsGroup` by mode `0666` **[measured]**. No object a slot creates with default settings lands in the GID in a shared namespace **[measured]**.
- **Shared read-only volumes.** Every slot reads files of mode `0640` and `0660` in the pod-wide read-only volumes through the GID **[measured]**. PL stages those volumes with files `0444`, so this affects only a file a deployer stages group-only **[inference]**.
- **The adapter's own mount.** The adapter can read and write group-accessible slot files through its own mount **[measured]**. It must not rely on that: SIR-8 sends every access through the broker.
- **Restore drops setgid on directories.** The broker's `mkdir` inherits the setgid bit from its parent, and its `chmod` refuses mode bits outside `01777`, so a restored directory loses the bit. A file the runtime creates there afterwards carries the slot's own GID **[measured]**. Nothing reads files through the group, so the loss is cosmetic **[inference]**.
- **`lost+found`.** Through the GID a slot can write into, remove, or replace its volume's `lost+found` **[measured]**. The emptiness check requires it to be empty (SIR-34).
- **Fewer broker fallbacks.** A slot's `0750` directory inherits the GID, so the adapter lists and searches it, which halved the parallel stat walk's fallback in the permission test **[measured]**.

PL's PLR-10 carries this exception, and `lenny-pod-security` admits it on Kata `block-plain` pods only.

**Minimum versions.** The deployment-wide Kubernetes floor of [§17.6](../../spec/17_deployment-topology.md#176-packaging-and-installation) stays at 1.27, and a cluster that runs standard-class pools needs 1.33 on the API server and every standard-class node ([PM-1](../0136-placement/change.md#user-namespaces-on-the-standard-class)). The supervisor needs a kernel of 5.9 or later for `close_range`, `openat2`, and `STATX_MNT_ID` ("SI-5"). gVisor `release-20261109.0` is verified, and the earliest gVisor release that serves the protocol is unknown **[measured]**.

## SI-2 Slot identity and socket names

**Names.** Each slot `n` gets `@lenny-runtime-<n>` for `CH-MSGSOCK` and `@lenny-supervise-<n>` for `CH-SUPERVISE`. The supervisor already takes its socket name as `--socket`, so slot `n`'s container renders `--socket @lenny-supervise-<n> --adapter-uid <adapter UID>`, and the runtime reads its name from `LENNY_ADAPTER_SOCKET`, as today (`podspec/supervisor.go`, `podspec/msgsock.go`) **[source]**. The adapter binds every slot's names when it starts. `CH-RUNTIMEOPS` and its pod-wide name `@lenny-runtime-ops` leave, because RP O7, settled as (a), carries its frames on the runtime connection.

**Connections on a slot's `CH-MSGSOCK` endpoint.** A slot's endpoint accepts one runtime connection and the tool connections of the slot's MCP bridges, which declare `"role": "tools"` in their `hello` (RP O3, settled as (b)). The adapter binds every connection of either role to the slot by the name it arrived on and its peer UID, and the session it acts for is the slot's session. The tool multiplexer of revision 3 and its socket in `/tmp` leave.

**Checks in both directions (SIR-4).**

| Connection | Server checks | Client checks |
| :-- | :-- | :-- |
| `CH-SUPERVISE` of slot `n` | The adapter accepts on `@lenny-supervise-<n>` only slot `n`'s UID. | The supervisor accepts the server only as the adapter UID, through its existing `--adapter-uid` check. |
| `CH-MSGSOCK` of slot `n`, runtime or tool connection | The adapter accepts on `@lenny-runtime-<n>` only slot `n`'s UID, and takes every frame's session from slot `n` (AR O5 (b): no frame other than `session_start` carries `sessionId`). | The runtime SDK and the bridge accept the server only as the adapter UID, which the slot's manifest names. |

The spikes measured that a process in slot 1 is seen as slot 1's UID whatever it claims, and that it cannot change its UID, under runc, gVisor, Kata, and kind with user namespaces **[measured]**. `SO_PEERCRED` reports a peer's process ID as 0 across process namespaces **[measured]**, so the design uses only the UID.

**How squatting is closed.** Abstract names are visible to and bindable by every container in the pod's network namespace **[measured]**. The design closes each window:

- **Before the first bind.** A slot container runs only its supervisor until the adapter asks it to run something, because the supervisor "launches nothing otherwise" ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model), **Runtime supervisor.**) **[source]**. Before READY it runs only the platform's own helper, for the warm checkouts. No code a runtime author or a session supplies runs in the pod before the adapter has bound every name and accepted every supervisor, so the adapter needs no start ordering (D5).
- **`CH-SUPERVISE` after READY.** The adapter closes each slot's supervise listener after its first connection, as today. A supervisor dials only once and exits when its connection ends, so a squatter on a free supervise name receives no connection.
- **`CH-MSGSOCK` between End and the next launch.** Under SIR-5 the adapter keeps each slot's listener bound for the pod's life, and after an attested End it accepts and closes every connection queued on it, of either role, before the next launch. End's passes have ended every process of the old session, so nothing of it can queue a connection afterwards. The purpose of today's rebind, that "no connection the ended process opened or left pending reaches the next process", holds, and the name is never free.
- **Another container.** `netagent`, `keepalive`, and any deployer container run under other UIDs, so every client check refuses them. `lenny-bin-stage` and `lenny-store-fill` are init containers that exit before the adapter starts, so neither can hold a name, and each runs under a UID of its own (SIR-39).

**Setup commands before the launch.** Setup commands run as the slot UID before the runtime launches at bind ("SI-3"). The adapter drains the listener again immediately before `launch`, and a process a setup command left running can still connect in the launched process's place. It acts only for its own session, whose code it already is, and "Limits" records it.

**Never-launched pods (SIR-38).** Until a session first binds to a slot, the only processes that have run in its container are the supervisor and `lenny-materialize` runs on warm-up checkouts, whose input is the pod's stores and whose output is the slot's own volumes. A bind runs the session's materialization and setup commands before its `launch`, so the guarantee ends at the slot's first bind, which precedes its first launch. The guarantee holds per slot, and for the pod only while it holds for every slot: once one slot has served a session, another slot's later contribution could carry content shaped by session code through the pod's shared namespaces. IC's platform chunk sets rely on it, so a pod contributes only before any session binds to it, which in practice means before READY, and the adapter records the first bind on the pod.

**Nonce-only mode.** Where `requireSoPeercred: false` accepts a nonce-only mode, no peer UID is checked. A supervisor dials only its own name, from its rendered argument, before any untrusted code runs, so the name it connects on maps it to its slot. Each slot's manifest on its run volume carries that slot's `connectionNonce`, which no other slot mounts, and every connection of either role presents it. The broker's descriptors arrive on the supervisor's own connection, so they need no further mapping.

**Tools on pods with several slots.** The adapter knows which session every frame acts for, so platform tools are allowed on every pod from proposal SI-A on, and RP O10 is retired. Lenny has no other tool server: a slot reaches an operator's MCP services through `netagent` and egress, attributed to the slot as any other connection (CR-3 of [`0124-connector-removal`](../0124-connector-removal/change.md#cr-3-external-services)).

## SI-3 Runtime processes, slot release, and setup commands

**One session per runtime process, launched at bind (D4, D15).** Each slot container's supervisor launches one runtime process for each session, when the session binds, and never before. A pod reports READY with no runtime process running. At bind, in order:

1. The adapter restores the session's seed through the broker when it has one ([IC-5](../0131-incremental-checkpoint/change.md#ic-5-restore-derive-download-and-seal)).
2. Helper runs write the session's workspace, adopting a staged warm checkout where one matches ([WM-7](../0153-workspace-materialization/change.md#wm-7-ordering-and-collisions), [WM-10](../0153-workspace-materialization/change.md#wm-10-git)).
3. The setup commands run, one `setup` request each.
4. The adapter drains the slot's `CH-MSGSOCK` listener and sends `launch`. The runtime's handshake and the check of the session's effective capabilities run before `session_start` ([RP-1](../0139-runtime-protocol/change.md#rp-1-handshake), RP O2 as settled).

A failure before `session_start` that is not a cause of "SI-4", a handshake refusal included, ends the bind and runs the slot release as after any session, and the slot stays live (RP-1). On a pod with one slot the failure decides nothing about the pod, which follows the pool's disposition for a release (D36, "Recycling after the release").

**Slot release (SIR-13, SIR-35).** At the end of each session in a slot:

1. The adapter waits until the session's seal checkpoint and its exports have ended ([IC-5](../0131-incremental-checkpoint/change.md#ic-5-restore-derive-download-and-seal), "Seal"), and the supervisor serves the broker until then.
2. The adapter sends `end`. End kills every other process in the slot container, the session's escaped processes included, and stops an outstanding run first.
3. The adapter sends `sweep`, and the supervisor's Sweep removes the slot UID's IPC objects and its files in every writable slot volume.
4. The adapter sends `cleanup` with the pool's cleanup commands.
5. The adapter sends `end` again, which kills what the cleanup commands left running. A `launch` after a cleanup run requires an attested End, and is refused with `launch_not_permitted` until then **[measured]**.
6. The adapter sends `sweep` again, and the second Sweep removes what the cleanup commands left in any writable slot volume, `/tmp` and `/dev/shm` included, which the emptiness check does not cover (O12, D23).
7. The adapter removes what remains in each brokered volume through its own mount, which on a `1777` root under gVisor's pod-share annotation are the entries the adapter owns **[measured]**, and runs the emptiness check (SIR-34). A brokered volume that is not empty makes the slot dead (SIR-15). Once the check passes, the slot accepts a session.
8. The adapter drains the slot's `CH-MSGSOCK` listener (SIR-5).
9. The adapter stages the slot's warm checkouts through a `prestage` helper run. A bind that arrives before or during the run cancels it, runs `discard` on what it staged, and materializes the plan without staged trees, so staging never delays a bind ([WM-15](../0153-workspace-materialization/change.md#wm-15-warm-up-checkout-and-reflink-rebuild)).

A step of steps 2 to 7 that answers an error or misses its bound fails the release, and a failed release makes the slot dead ("SI-4") whatever the pool's `onScrubFailure` says (D39). That includes a `cleanup` run answered with `cleanup_failed` or `cleanup_timeout`, because the pool's cleanup commands run in the release.

**A quarantined pod.** A pod under forensic quarantine gets no slot release: its slots keep their processes and files until the quarantine's recorded release, after which the pod terminates ([`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md), FE-1).

The asynchronous worker's spike ran the supervisor's part of this order without the second Sweep, `end`, `sweep`, `cleanup`, `end`, and then a `launch`, on runc and gVisor **[measured]**. The second `sweep` after an attested End is the same request on a nearly empty slot **[inference]**. Spike 2 ran the Sweep and the adapter's removal on runc, gVisor, and gVisor with the pod-share annotation, and the volume was empty in each **[measured]**. The AWS run on Kata `block-plain` ran End, Sweep, cleanup, the adapter's removal, and the emptiness check over ordinary and hostile sessions, and every volume came out empty once the Sweep was fixed **[measured]**.

**The emptiness check (SIR-34).** The adapter lists each brokered volume's root through its own mount. The check passes when the root holds nothing, or only a directory named `lost+found` that is itself empty. On Kata `block-plain` the adapter lists `lost+found` through the dedicated volume GID **[measured]**. A check that skipped `lost+found` by name would skip a directory the slot can write, and ownership by root does not show that it is empty **[measured]**. A slot that removed `lost+found` leaves a volume without one for the pod's life, which ext4 tolerates **[inference]**.

**The Sweep (SIR-33).** The AWS run found three defects in the tree's Sweep, each of which fails a release **[measured]**:

- **Coverage.** The tree's Sweep skips `slots/` under `/workspace`, so under revision 3's layout it never swept the slot's workspace volume **[measured from the source]**. The Sweep covers every writable slot volume of [PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout), `/workspace`, `/session`, `/tmp`, and `/dev/shm`, with no skipped child, plus the slot UID's POSIX message queues and System V objects.
- **Directories that deny their owner.** The tree's Sweep fails with `sweep_failed` on a slot-owned directory of mode `0500`, `0300`, or `0000`, the adapter cannot remove it either, and the slot fails, under runc with or without `fsGroup` **[measured]**. A tool that leaves read-only directories, such as Go's module cache with its `0555` directories, triggers it **[inference]**. Before it opens a slot-owned directory, the Sweep adds owner read, write, and search to its mode with `fchmodat` as the owner. The AWS run's patch, which set `0700`, removed the failure **[measured]**.
- **The entry bound.** The tree's Sweep stops at 200,000 entries per volume, so the release of an LLVM-sized session, 208,088 entries, failed with `sweep_bound` on runc and Kata `block-plain` **[measured]**. The bound becomes per volume the larger of 200,000 and the volume's `sizeLimit` divided by 4 KiB, which the controller renders as a supervisor argument per volume: 2,621,440 entries for a 10 GiB workspace. The Sweep's time backstop of 4 minutes still bounds the walk, and a release at that scale is owed validation.

The Sweep never changes the mode of a volume root, which belongs to `root`, and it cleans `/tmp`. Spike 1 required both **[measured]**. The supervisor recreates `HOME` under `/tmp` as PL states.

**What this retires.**

- **`recycle.runtimeProcess` and `keep`.** Every slot behaves as today's `restart` pod at every release. The field, the label `lenny.dev/runtime-process`, and the acknowledgment for a runtime process kept across sessions leave.
- **Process-group cleanup.** **Slot cleanup:**'s "kills any processes owned by the slot's process group" is replaced by End.
- **The whole-pod scrub.** The per-slot release does, at every release, what the supervised scrub sequence does for the pod at its recycle boundary. What remains for the occupancy-zero boundary is the pod-wide scrub: the pod-wide state outside any slot and the report through `ReportPodScrub` ("Recycling after the release").
- **"Runtime not live".** No runtime process outlives its session (D4, D15), so `ReportPodScrub` states nothing about a runtime's readiness, and the retirement condition that read it leaves with its reason `runtime_not_live` (D37).
- **The `leaked` slot.** A slot whose release fails is dead ("SI-4"), so the `leaked` sub-state leaves (D38).
- **`in-place` and `acknowledgeMicrovmResidualState`.** The scrub profiles are `standard` and `vm-restart` (D39).
- **A runtime process waiting in a free slot.** Pre-launched runtime processes are removed (D15). A slot's runtime starts only at bind, in the working directory and with the credentials of its session.

**Recycling after the release (D36, D37, D39).** The slot release runs at the end of every session on every pool. What follows it depends on the pool **[design]**:

- **A pod with one slot (D36, SIR-40).** A failure before `session_start` that is not a cause of a dead slot leaves the pod to the pool's disposition for a release: a pool that does not recycle ends the occupancy, and a recycling pool runs the pod-wide scrub and holds the pod for its tenant. A failure or a crash after `session_start` ends the occupancy without reuse, so the gateway deletes the claim and the pod drains, as [§4.6.3](../../spec/04_system-components.md#463-crd-field-ownership-and-write-boundaries) states today. A dead slot retires the pod ("SI-4"). The binding is published only after the pod accepts the session's start, so a failure before `session_start` has no published binding. §4.6.3's clause for a release with no published binding therefore applies only to a release that never reached the pod, such as one after a gateway crash before publishing, and it does not apply to a failure before `session_start` whose slot release completed and passed its emptiness check (D36).
- **The pod-wide scrub.** When a recycling pod's occupancy reaches zero, the adapter cleans the pod-wide state that no slot release reaches and reports the outcome through `ReportPodScrub`. The report states that outcome alone (D37).
- **Scrub profiles (D39, SIR-43).** `recycle.scrubProfile` takes `standard`, the default, which runs the pod-wide scrub and on success holds the pod for its pinned tenant, or `vm-restart`, allowed on a `microvm` pool, which runs the pod-wide scrub and then retires the pod so that the gateway provisions a fresh guest. `in-place` and `acknowledgeMicrovmResidualState` leave. `in-place` existed because `standard` was refused on a pool with `allowCrossTenantReuse`, which [`0136-placement`, "Removals"](../0136-placement/change.md#removals) removes, and with the tenant pin on every pool, `in-place` on a microVM pool was `standard` with an acknowledgment. Under `standard` on a `microvm` pool the guest kernel continues across the pinned tenant's sessions, and its DNS resolver cache, TCP `TIME_WAIT` state, buffer and page cache priming, and inotify and fanotify registrations persist across them. The documentation states that list, and `vm-restart` is the profile that clears it.
- **Scrub failures (D39, SIR-43).** `onScrubFailure` and `maxScrubFailures` govern the pod-wide scrub alone. A failed slot release makes the slot dead under every `onScrubFailure` value and never takes the `warn` path.
- **Retirement (D37, SIR-41).** A recycling pod retires at the session count limit, the uptime limit, the scrub failure limit, and under **Runtime refused**: after a handshake refusal that [RP-1](../0139-runtime-protocol/change.md#rp-1-handshake) classes as not retryable and that stops the pod's binds, which is every such reason except `capability_missing` and `role_refused`, the pod accepts no further binds on any pool, and once its occupancy reaches zero it retires with the non-counting reason `runtime_refused` ahead of the reserved hold. The adapter exits with the refusal as its termination reason, and the WarmPoolController backs off creating pods for the pod set, as RP-1 states. The "Runtime not live" condition and its reason `runtime_not_live` leave. A runtime that cannot serve is otherwise found through its slot: a runtime exit or a link failure makes the slot dead, and dead slots count toward the whole-pod replacement trigger ("SI-4").

**User git identity (UGI decision 14).** Its refusal of recycled pods rests on the reasons it states **[source]**. One, a `keep` process that carries planted state into the next session, no longer exists under D4. The other, residue from Alice's repositories reaching Bob, rests on the scrub's coverage. Under this design each release ends every process of the slot UID, sweeps every file and IPC object that UID owns in the slot's volumes, removes what remains, and checks that the brokered volumes are empty, and the second Sweep removes what the cleanup commands left (O12), so what can survive is state outside the slot's volumes, `netagent`'s caches, which the egress design keys on binding generation and session and flushes on each binding change **[source]**, and kernel state. The refusal of pods with several slots rests separately on what one pod's slots still share ([SI-10](#si-10-what-stays-shared)): per-slot attribution and per-slot scopes in `netagent` (O9; egress decisions 52 and 60) remove the shared egress identity, while the network and IPC namespaces, the adapter, the kernel, and pod-wide eviction stay shared. The owner settled UGI's decision 52 and UCD's decision 41 together on 2026-11-13 (D29): user git identity, user credential bindings, and `lockEgressToHosts` are allowed on a pool whose status records per-slot attribution, and refused on a fallback pool and on a recycled or used pod.

### The supervisor's worker (D6, D14)

**Runs.** A `setup` or a `cleanup` request is a run, and at most one run is outstanding in a slot (SIR-23). While a run is outstanding, the supervisor serves `fs`, `ping`, and `end`, and answers `launch`, `sweep`, `setup`, and `cleanup` with `worker_busy`, and the forensic `freeze` too while the run is a `setup`. To freeze a slot that has a `setup` run outstanding, the adapter cancels the run by closing its cancel pipe, waits for `setupdone`, and then sends `freeze` ([`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md)). A `cleanup` run has no cancel pipe and runs under the cleanup deadline: a `freeze` or an `end` that arrives while it is outstanding makes the supervisor kill the cleanup worker's process group, answer the run with `cleaned` carrying `cleanup_failed`, and then act on the `freeze` or the `end`. It serves requests in the order they arrive and writes each reply whole, and it writes a run's reply between two of them **[measured]**. An `end` stops an outstanding run first: the run's reply carries `setup_cancelled` and precedes `ended` when the run's status reached the supervisor, and follows within 5 s otherwise **[measured]**. A `setup` leaves the launch permission as it was, so a fresh slot runs helper runs and setup commands before its first launch; a `cleanup` clears it until the next End **[measured]**.

**The `setup` request.** The adapter sends one `setup` per setup command or helper run **[design]**:

```
{"type":"setup","gen":<gen>,"id":<id>,
 "argv":["/lenny/bin/lenny-materialize","materialize"],
 "cwd":"<raw bytes, relative to /workspace>","env":"empty",
 "timeoutMs":<ms>,"fsizeBytes":<bytes or 0>,"nfds":<K>}
```

| Member | Meaning |
| :-- | :-- |
| `argv` | The program and its arguments. `argv[0]` is an absolute path, or a name without a slash that the fixed `PATH` resolves. A relative `argv[0]` containing a slash is refused with `malformed_request`, because it would resolve against the workspace (SIR-30). |
| `cwd` | The working directory, relative to the workspace root and resolved beneath it with `RESOLVE_BENEATH`, `RESOLVE_NO_XDEV`, `RESOLVE_NO_SYMLINKS`, and `RESOLVE_NO_MAGICLINKS`. A `cwd` that resolves to no directory beneath the root fails with `setup_failed`, `reason` `cwd`, and the errno. |
| `env` | `launch`, the launch environment, for a setup command, or `empty` for a helper run. It names a choice and carries no value. |
| `timeoutMs` | The run's deadline. |
| `fsizeBytes` | The `RLIMIT_FSIZE` the program runs under, or 0 for none. WM sets it on helper runs only. |
| `nfds` | The number of descriptors attached to the line, from 3 to 253. |

**Descriptors (SIR-25, SIR-26).** The adapter attaches the `nfds` descriptors with `SCM_RIGHTS` to the line's first byte. The supervisor places them as follows:

| Passed index | Descriptor in the program | Contents |
| :-- | :-- | :-- |
| None | 0 | `/dev/null` |
| 0 | 1 | The write end of the standard output log pipe |
| 1 | 2 | The write end of the standard error log pipe |
| 2 | None | The read end of the cancel pipe, which only the supervisor keeps |
| `i` from 3 | `i` | The run's own descriptors. A helper run has its plan at 3, its result pipe at 4, and its end of the content socket at 5 ([WM-3](../0153-workspace-materialization/change.md#wm-3-the-protocol)). |

A setup command therefore takes `nfds` 3, and a helper run takes `nfds` 6. Content descriptors never cross `CH-SUPERVISE`: they reach the helper on the content socket, `CH-MATCONTENT`, one per source ([WM-4](../0153-workspace-materialization/change.md#wm-4-the-plan-the-adapter-builds)).

**Cancellation.** The adapter cancels a run only by closing its write end of the cancel pipe. The supervisor polls the read end asking for no event, so the hang-up that the close produces wakes it, and a byte written to the pipe cancels nothing **[measured]**. The supervisor then kills the program's process group and answers `setup_cancelled`. The supervisor closes the read end when the run ends.

**The program.** The supervisor forks the program as the run's child. Before it executes `argv`, the child closes `CH-SUPERVISE`, changes to `cwd`, places the descriptors and closes every other one with `close_range`, sets `RLIMIT_FSIZE` when `fsizeBytes` is set, sets `RLIMIT_CORE` to 0 for both limits, sets `no_new_privs`, marks itself non-dumpable, and starts a new session (SIR-27) **[measured]**. The non-dumpable mark survives `execve` only for a file the slot cannot read, which is why WM stages the helper and the pinned git with mode `0111`: a same-UID process then got `EPERM` from `pidfd_getfd` and `EACCES` reading its descriptors, while a readable setup program stayed dumpable **[measured]**.

**Process groups.** When the program exits, the supervisor kills its process group while the program's zombie still holds the group's ID, so a setup command cannot leave background jobs. Only a process that called `setsid` escapes, and it survives until the next End **[measured]**. Today a setup command's background job outlives it, so this is a change of behaviour for setup commands.

**Deadlines.** The supervisor enforces `timeoutMs` itself from PID 1: at the deadline it kills the program's process group, and it waits up to 5 s more for the status. A status that does not arrive is a failure. A `cleanup` worker enforces the cleanup deadline itself, and the supervisor's backstop kills it at `timeoutMs` plus 5 s, then waits up to 5 s more **[measured]**. The adapter's bound for a run's reply is the run's deadline plus the supervisor's stop wait plus a margin, and a reply missing past it is a link failure.

**The reply.** `{"type":"setupdone","gen":<gen>,"id":<id>,"exit":<status>}`, or `"signal":<number>` when a signal ended the program, carried only when the program's status reached the supervisor, with an optional `error` and, for a request error, `reason` and `errno`. The reply carries integers and enumerated codes only **[measured]**.

| Error | When |
| :-- | :-- |
| `setup_failed` | The program exited non-zero or by a signal, or did not start. When the request caused it, `reason` is `cwd` or `exec` with the errno. |
| `setup_timeout` | The `timeoutMs` deadline passed. |
| `setup_cancelled` | The adapter closed the cancel pipe, or an `end` stopped the run. |
| `setup_spawn_failed` | A step of the supervisor's own failed before the program's `execve`. |
| `worker_busy`, `malformed_request`, `gen_mismatch` | A refusal ("SI-5"). |

**`cleanup`.** A `cleanup` carries the pool's cleanup commands, as today, and runs them in a forked worker with the launch environment, from the workspace root, under the cleanup deadline. Its reply is `cleaned`, with `cleanup_failed` or `cleanup_timeout` on failure.

**What the protocol changes for the adapter.** A setup command's output arrives on the log pipes, which the adapter drains to their end, and no `CH-SUPERVISE` message carries a byte a command wrote. A long setup command or helper run no longer holds back the broker: the spike walked 100,100 entries in 502 broker requests in 200 ms while a setup ran, against 216 ms idle **[measured]**. Whether a checkpoint or an export waits for a helper run is a rule of WM and IC, which the protocol leaves to them.

**Container restart.** The local spike restarted a slot container through container restart rules: 1.5 s, then 14.9 s and 29.0 s under backoff, and the workspace, `/tmp`, `/dev/shm`, and System V segments survived **[measured]**. This design does not restart containers.

## SI-4 Slot liveness and the slot count

**Per-slot not-live state.** **Liveness.** today holds one not-live state for the pod **[source]**. Under this design the adapter holds one per slot. Each cause **Liveness.** lists that concerns a supervisor or a runtime process sets the not-live state of the slot it concerns, and a cause that concerns the adapter itself sets the pod's state as today.

**Causes of a dead slot (SIR-15).**

- The slot container ended. The pod's `restartPolicy` is `Never`, so a slot container that exits stays exited for the pod's life. It ends when its supervisor ends, for example by an out-of-memory kill: the kubelet sets `memory.oom.group` to 1 on the container's cgroup, so the kill takes every process in the container, the supervisor included **[measured]**.
- `CH-SUPERVISE` failed: the connection closed, including when the supervisor exited after a write made no progress for 10 s (SIR-28), or a line the supervisor could not attribute to any request made it exit.
- A request missed its deadline: an `fs` request its `D(n)` ("SI-5"), a run its bound ("SI-3"), and every other request its bound under [§28.5.3](../../spec/28_communication-channels.md#2853-intra-pod), **Timing.**
- The adapter refused a reply under "SI-5".
- A slot release failed ("SI-3"): a step answered an error or missed its bound, including a `cleanup` run answered with `cleanup_failed` or `cleanup_timeout` and a Sweep answered with `sweep_failed` or `sweep_bound`, or the release left a brokered volume not empty. This holds under every `onScrubFailure` value (D39).
- The supervisor's self-test failed a gating property ([§4.7.11](../../spec/04_system-components.md#4711-adapter-agent-security-boundary) item 8). The gating properties are the supervisor's non-dumpable state and End's reach to a double-forked process **[measured]**.

A handshake refusal is not a cause: it ends the bind and releases the slot ("SI-3"). A refusal RP-1 classes as not retryable stops the pod accepting binds, and the pod exits once idle ([RP-1](../0139-runtime-protocol/change.md#rp-1-handshake)), which "Recycling after the release" states as the retirement condition **Runtime refused** with the reason `runtime_refused` (D37).

**What follows.** The adapter reports the slot dead on `CH-ADAPTEREVENTS`, and a session that holds the slot fails with `runtime_crash` and follows [§7.3](../../spec/07_session-lifecycle.md#73-retry-and-resume). The gateway records the slot's index in the pod's `agent_pod_state.dead_slots` and then adds a member `dead:<n>` to the pod's slot set, so the dead slot counts in occupancy for the pod's life and toward the whole-pod replacement trigger of half the slot count, rounded up, and the gauge `lenny_adapter_dead_slots` counts it per pod. A pod with one slot retires, as today (D36). Before READY, a failed slot fails the pod, as does a missing canary or a failed `uid_map` check ("SI-11").

**One state (D38).** The dead slot replaces the specification's `leaked` slot. A cleanup that would have entered the `leaked` sub-state makes its slot dead: `ReportSessionScrub` reports `dead` in place of `leaked`, the gateway adds `dead:<n>` in place of `leaked:<sessionId>`, the `leaked` sub-state, its row, and its column of the §5.2 scrub model table leave, and `lenny_adapter_leaked_slots` becomes `lenny_adapter_dead_slots`.

**Dead slots across a Redis restart (SIR-42).** Rehydration reads the pod's `agent_pod_state.dead_slots` together with the session rows of `SessionStore.GetActiveSlotsByPod`, adds a `dead:<n>` member for each recorded index beside the session members, and only then sets the pod's `rehydrated` flag, so a pod with dead slots never looks as if it had free slots. The Postgres fallback that gates a pod's capacity during a Redis outage counts the recorded dead slots with the session rows. The gateway writes the index before it adds the member, so every `dead:<n>` member the set holds is recorded, and nothing clears an index, because a dead slot stays dead for the pod's life. `dead_slots` is gateway-written, as `sessions_served` and `scrub_failure_count` are, and the WarmPoolController's mirror writes leave it unchanged. The adapter binds a session only to a live slot, so a write that fails before the member is added refuses that bind at the pod rather than admitting it to a dead slot **[design]**.

**Signals to PID 1 under gVisor.** Under runc, a slot process cannot stop or kill its supervisor, because the kernel ignores SIGSTOP and SIGKILL sent to a PID namespace's init from inside the namespace: a ping answered in 0.1 ms after a slot process sent SIGSTOP **[measured]**. Under gVisor, PID 1 is not immune: SIGSTOP from a slot process held the supervisor for 2.7 s until the test resumed it, and SIGKILL killed it **[measured]**. The adapter's liveness deadlines are the only backstop there: a stopped supervisor misses its ping and request deadlines, and a killed one ends the container, and either makes the slot dead. The slot's own session caused it, so it costs that session and the slot. The self-test reports the immunity properties and does not gate on them.

**Pings during a run.** The supervisor answers `ping` during a run, so the adapter pings every slot on its normal schedule whatever runs there **[measured]**.

A deployer who wants an out-of-memory kill to take only the largest process can set the kubelet's `singleProcessOOMKill` **[inference]**.

**Slot identifiers.** The gateway mints the `slotId` at claim, as today. The adapter binds the session to the lowest slot index whose slot is live and free, records `slotId` to index in its slot registry, and reports the index on `CH-ADAPTEREVENTS` for observability.

**The slot count (SIR-16).** The controller records the pod's slot count in `AgentPod.spec.slotCount` when it creates the pod, equal to the slot containers it rendered, and never changes it. The reservation script of **Slot assignment atomicity** compares occupancy against that recorded count in place of the pool's current `maxConcurrentSessionsPerPod` **[source]**. A pool whose `maxConcurrentSessionsPerPod` changes gets new pods with the new count, and existing pods keep theirs until they retire.

## SI-5 The supervisor file-descriptor broker

**Why a broker (D9).** The slot UID owns a session's files, and the adapter runs under another UID with no capability. Pod Security Standards Restricted allows adding only `NET_BIND_SERVICE`, Baseline's added capabilities include `DAC_OVERRIDE` and `FOWNER` but not `DAC_READ_SEARCH`, capabilities added to a non-root container are not effective, and user namespaces relax only `runAsNonRoot` and `runAsUser` **[measured]** **[external]**. The process that can open every file the session can open is a process running as the slot UID, and the supervisor already is one. The broker lets the adapter use that process's access without moving any checkpoint logic into it: the supervisor opens, creates, stats, and watches entries, and returns descriptors and integers.

**Roots.** The supervisor serves the brokered volumes as the roots `workspace` and `session`, and the scratch volume as the root `tmp`, rendered as `--fs-root workspace=/workspace --fs-root session=/session --fs-root tmp=/tmp` ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). The `tmp` root serves the per-slot disk watch alone (D24): on it the supervisor answers `open` of a directory and `statat`, and refuses every other operation with `EPERM` in that path's `errs` entry, so the adapter can measure `/tmp` and can neither read a file there nor create one **[design]**. The adapter calls `fstatfs` on a root descriptor where PL's disk watch reads a volume's use from `statfs`.

**The request.** On `CH-SUPERVISE` the adapter sends **[design]**:

```
{"type":"fs","gen":<gen>,"id":<id>,"root":"workspace","op":"open","paths":["<raw bytes>", ...],"targets":[...],"nums":[...]}
```

- `root` names one of the slot's broker roots.
- `paths` holds up to 253 paths, relative to the root, each as a JSON string of raw bytes. The supervisor's parser keeps bytes of `0x80` and above as they are, so any file name passes. Go's `json.Marshal` replaces invalid UTF-8, so the adapter uses its own encoder for these strings **[measured]**.
- `targets` carries the second path of `symlink` and `link`, and `nums` the integer arguments of `mkfile`, `mkdir`, `mkfifo`, `utimens`, and `chmod`.

**The operations (SIR-20).** Every operation resolves beneath the root with `RESOLVE_BENEATH | RESOLVE_NO_XDEV | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`, and the supervisor runs every request under a umask of 0 so the modes it creates are exact **[measured]**:

| Op | What the supervisor does | Returns | Used by |
| :-- | :-- | :-- | :-- |
| `open` | `O_RDONLY \| O_NOFOLLOW \| O_NONBLOCK \| O_NOCTTY`, falling back to `O_PATH` on `ELOOP`, `ENXIO`, or `EACCES`. | A descriptor per path. | IC's walk, for directories it lists and files it reads or clones; exports; the parallel stat walk's fallback for a subdirectory; WM's working-directory check. |
| `openpath` | `O_PATH`, for an entry whose type is neither a regular file nor a directory, so a FIFO is never opened. | A descriptor per path. | IC's walk. |
| `statat` | `statx` with `AT_SYMLINK_NOFOLLOW` of each path's final component, relative to its parent opened beneath the root and reused for consecutive paths in one directory. A final component on another mount than its parent is refused with `EXDEV`. | Per path, eleven integers: device major and minor, inode, mode, link count, size, allocated blocks, and modification and change times in seconds and nanoseconds. No descriptor. | The parallel stat walk's fallback; IC's identity checks. |
| `mkfile` | `O_WRONLY \| O_CREAT \| O_EXCL` with the requested mode. | A writable descriptor per path. | Restore; IC's tracker barrier file and reflink probe file. |
| `mkdir`, `mkfifo`, `symlink`, `link` | Creates the entry as the slot UID. | None. | Restore. |
| `utimens` | Sets times with `AT_SYMLINK_NOFOLLOW` from `sec, nsec, sec, nsec`. | None. | Restore. |
| `chmod` | Changes a directory's mode, through an `O_DIRECTORY` descriptor. | None. | Restore. |
| `inotify` | Creates the slot's `inotify` descriptor once. | The shared descriptor. | IC's tracker. |
| `watch` | Pins the directory with `O_PATH`, then adds a watch on `/proc/self/fd/N` with the tracker's mask plus `IN_ONLYDIR`. | Watch descriptors, as integers. | IC's tracker. |

The set is closed. The supervisor walks no tree, reads no file content, computes nothing about a checkpoint, and copies nothing. `statat` joins the set under IC's decision D16, which the owner settled on the AWS numbers, and it serves the parallel stat walk's fallback (D17).

**The reply.** `{"type":"fsdone","gen":<gen>,"id":<id>,"errs":[...]}`, with `"wds":[...]` for `watch` and `"st":[...]` for `statat`. `errs` holds one errno per path, 0 for success, and the descriptors follow over `SCM_RIGHTS` in path order, one per zero for the ops that return descriptors. The reply carries integers only, so the rule that no runtime bytes cross `CH-SUPERVISE` holds **[measured]**. A reply line is at most 96 KiB.

**The supervisor's validation.** It refuses with `malformed_request` a request whose op is outside the set, whose arrays exceed their per-op lengths (253, which is `SCM_MAX_FD`), whose line exceeds 64 KiB, whose final path component is empty, `.`, or `..`, whose mode has a bit outside `01777`, which takes in the set-user-ID and set-group-ID bits (SIR-30), or whose `watch` comes before `inotify` **[measured]**. `openat2` confines the paths.

**The pinned root (SIR-22).** Each supervisor opens its broker roots when it starts, before any session binds to the slot, while no untrusted code has run in the container, and resolves every request beneath those descriptors for the pod's life. At bind, before the launch, the session's helper runs parse session-supplied content as the slot UID (`lenny-materialize`'s `materialize` and `restore-complete`), and its setup commands are session code ("SI-3"), so the adapter treats every broker reply as untrusted from the first run of the supervisor's worker for the first session bound to the slot, normally the helper's `materialize` or `restore-complete`, or from that session's launch when no run precedes it, as [IC S6](../0131-incremental-checkpoint/change.md#security-properties) states. The restore at bind precedes that run, so this point leaves it unaffected. Before READY the adapter asks for each root through the broker and records its device and mount ID from `statx` as the pin. The adapter pins identity from these broker-opened roots and never from its own mount: spike 3 measured that a descriptor the broker returns carries the slot's mount ID (374) where the adapter's own mount has 322, and that under gVisor's default mount the device differs as well (`0:96` against `0:55`) **[measured]**. On Kata `virtio-fs` the adapter's own mount reported device `0:49` and mount ID 156 against the pin's `0:57` and 186 **[measured]**.

**The adapter's checks against a hostile peer (SIR-21).** The supervisor runs on the untrusted side of the boundary ([§4.7.11](../../spec/04_system-components.md#4711-adapter-agent-security-boundary) item 8), so the adapter checks every reply:

- each descriptor's device and mount ID from `statx` against the pin, except that an `openpath` descriptor of a FIFO whose device differs under gVisor's default mount is not used and the FIFO is recorded from its listing as metadata-only ("SI-6");
- the expected type for the op, and the access mode;
- for `open` of a regular file, an `O_PATH` descriptor is accepted only as a metadata-only entry and is never read as content, which reconciles the check with `open`'s fallback to `O_PATH` for a file of mode `0000`;
- a size bound on each regular file;
- for `mkfile`, `O_WRONLY`, size 0, and one link;
- that the number of descriptors equals the number of zero errnos for the op, and that `MSG_CTRUNC` is clear;
- the reply's `id`, no unknown members, and the line bound;
- for `statat`, eleven integers per path, and a device equal to the pin's;
- a deadline per request ("Batches and deadlines"), after which the slot is dead ("SI-4").

Spike 3 sent 25 hostile replies on each runtime, and the adapter refused 24: a FIFO, `/dev/zero`, a `/tmp` file, a file on another volume with the same device (caught by the mount ID), a memfd, a 1 TiB sparse file, a directory, a socket, and write-only, read-write, and `O_PATH` descriptors; on restore, an existing file, a FIFO, a `/tmp` file, and a read-only descriptor; and on the protocol, extra and missing descriptors, 1,012 flooded descriptors, a wrong `id`, unknown members, a line over 1 MiB, a partial line, and a stall past a 2 s timeout **[measured]**. It accepted a descriptor to a different file in the same workspace, which harms only that session, because the slot could write those bytes itself **[measured]**.

**The parallel stat walk's broker rules (D17).** IC owns the walk ([IC-1](../0131-incremental-checkpoint/change.md#ic-1-capture-in-passes)). These rules are what makes the adapter's own lookups safe:

- The adapter opens each directory it walks through broker `open`, or relative to a broker-passed or already checked directory descriptor with `openat2` and `RESOLVE_BENEATH | RESOLVE_NO_XDEV | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`. Every directory descriptor gets the descriptor checks above and an inode match against its `statx`.
- It lists a directory with its own `getdents` on the descriptor, and stats only single names that `getdents` returned, never `.`, `..`, an empty name, or a name containing `/` or NUL.
- Every `statx` is relative to the directory descriptor, with `AT_SYMLINK_NOFOLLOW` and `STATX_MNT_ID`, and its device and mount ID must equal the pin. A result without a mount ID is refused. A descriptor in the slot's mount view gives the slot's device and mount ID: on Kata `virtio-fs`, `statx` relative to a broker-passed descriptor returned the pin's `0:57` and 186 **[measured]**.
- It reads a symbolic link's target with `readlinkat` on the parent descriptor, and follows no link.
- On `EACCES` from a `statx` in a directory, the rest of that directory goes to broker `statat`, and on `EACCES` from an `openat2`, the subdirectory is opened through broker `open`. The fallback is per directory and fires on `EACCES` only (SIR-36).

The AWS run measured 0 missed changes and 0 identity differences against the slot's own view on runc, Kata `block-plain`, Kata `virtio-fs`, gVisor's default mount, and gVisor's pod-share mount, over 208,084 to 1,000,002 entries per tree **[measured]**. A walk with no fallback sent one broker request, and its worst broker round trip was 0.1 to 0.5 ms **[measured]**.

**Batches and deadlines.** An `fs` request carries at most 253 paths, the most descriptors one `SCM_RIGHTS` message passes, and at most 56 KiB of line, which leaves room under the supervisor's 64 KiB line bound (SIR-36). Each request has the deadline `D(n)` = 1 s + 4 ms × `n` for `n` paths, so a full batch has about 2 s. The deadline scales with the batch and never with the directory: a huge directory spans many requests, and the adapter pages `getdents` on its own descriptor, so the supervisor holds no per-directory state. The supervisor serves requests in order, so a request's deadline counts from the reply to the request ahead of it on the connection, or from its write when none is ahead. The parallel stat walk keeps at most 2 fallback requests outstanding per slot: 16 threads that queued their fallback batches on the single-threaded supervisor produced worst round trips of 146 to 370 ms on Kata `virtio-fs` **[measured]**, which every other user of that slot's broker would wait behind. Spike 3 measured a walk with open and read over 10,000 files of 4 KiB at 4.9 µs per file through the broker in batches of 253 on runc, against 3.8 µs directly and 39.0 µs in batches of 1 **[measured]**.

**Descriptors the kernel refuses (SIR-29).** `sendmsg` with descriptors fails with `ETOOMANYREFS` when the sending UID already holds more descriptors in flight than its `RLIMIT_NOFILE`, and the count is per UID across the kernel. When the kernel refuses a reply's descriptors, or another failure prevents the first byte from carrying them, nothing was sent, so the supervisor sends the reply again without descriptors, with that errno for each path that had one, and keeps serving. It first removes every entry a refused `mkfile` created, so a retry does not meet `EEXIST`. The spike measured both halves: during the refusal the reply carried errno 109 and no descriptor and a ping still answered in 0.1 ms, and a retry afterwards succeeded with the refused entry gone **[measured]**. "SI-11" states the cross-pod case and its fix.

### Rules for the whole `CH-SUPERVISE` connection

- **Refusals (SIR-24).** `malformed_request`, `gen_mismatch`, and `worker_busy` are refusals. A refusal keeps the request's own reply type, such as `{"type":"cleaned",…,"error":"worker_busy"}`, means the supervisor did not execute the request, and never carries `exit` or `signal`. A request whose type, `gen`, and `id` the supervisor can read but whose members are not valid gets `malformed_request`. A line the supervisor cannot attribute to any request makes it exit, which is a link failure **[measured]**.
- **Descriptors (SIR-25).** The supervisor reads with `recvmsg` and `MSG_CMSG_CLOEXEC`. On a stream socket one read can return earlier lines together with the bytes that carry descriptors, and the kernel ends that read after them, so the supervisor binds each batch of descriptors to the line that contains the last byte of the read that delivered it. It accepts descriptors only with a `setup` line, and exactly `nfds` of them; descriptors with any other line, a count that differs, more than 253, or `MSG_CTRUNC` are closed and answered with `malformed_request` **[measured]**. The adapter sends descriptors only with a `setup`, on the line's first byte, in a `sendmsg` that carries exactly that line or its start.
- **Writes (SIR-28).** Every supervisor write goes through a polled send with a no-progress bound of 10 s, after which the supervisor exits. A reader that stopped closed the connection 10.04 s later in the spike **[measured]**. The bound does not use `SO_SNDTIMEO`, which gVisor does not enforce on Unix stream sockets: a write blocked for more than 5 s there with a 1 s timeout set, where runc gave up after 1.02 s **[measured]**. The adapter therefore reads `CH-SUPERVISE` continuously, whatever else it is doing.
- **Pipelining.** The adapter may have several requests outstanding on one connection, which the supervisor answers in order, interleaved with a run's reply. In the spike, 200,000 `fs` replies came back in order with one `setupdone` among them, with up to 64 requests in flight and no reply carrying the wrong descriptor count **[measured]**.
- **Versions (SIR-37).** The adapter and the supervisor ship together in one Lenny release, so `CH-SUPERVISE` carries no version. The supervisor needs a kernel of 5.9 or later in the slot's view: `close_range` arrived in 5.9, `openat2` in 5.6, and `STATX_MNT_ID` in 5.8 **[external]**. Under gVisor the sentry provides them, and `release-20261109.0` is the release verified **[measured]**.

**The supervisor's size.** The tree's supervisor has 3,585 lines **[source]**. The broker prototype added about 470 lines, and the materialization prototype added 179 lines over it. The asynchronous worker adds 376 lines of code net, not counting blank and comment lines, over the prototype that merges both, for 4,915 lines in all **[measured]**. The owner accepted the broker's cost (D9) and approved the asynchronous worker after its security review (D14).

## SI-6 Checkpoint, restore, export, and cleanup

IC owns each of these. This section states what isolation requires of them.

**Reads.** The adapter's checkpoint reaches a slot's files only through the broker and the parallel stat walk's rules ("SI-5"). Spike 3 measured that `getdents` on passed descriptors of `0700` and `0500` directories works, and so do reads of `0600`, `0400`, and `mkstemp` files, under runc, gVisor's default mount, and gVisor's pod-share mount, where the adapter's own mount returns `EACCES` for each **[measured]**.

**Identity.** `fstat` on a passed descriptor matches `lstat` on device, inode, size, mode, and change and modification times to the nanosecond, and IC's recheck of a file written during capture works through it **[measured]**. The adapter compares identities only within the slot's mount view, the broker's, because under gVisor's default mount the device differs between the adapter's view and the slot's **[measured]**.

**Metadata-only entries (O2).** An entry the owner cannot open, such as a `0000` file or a `0300` directory, comes back from `open` as an `O_PATH` descriptor, and the adapter records it in the checkpoint's metadata record ([§4.4](../../spec/04_system-components.md#44-event--checkpoint-store), **Checkpoint Atomicity:**) as `metadata_only`, with a session warning event and the metric `lenny_checkpoint_metadata_only_paths_total` ([§16.1](../../spec/16_observability.md#161-metrics)) **[design]**. A FIFO under gVisor's default mount is the one other metadata-only case: its `O_PATH` descriptor reports a device other than the broker root's, so the device check of SIR-21 refuses it, and the adapter records the FIFO from its directory listing as `metadata_only` and a restore recreates it with `mkfifo` ([IC-1](../0131-incremental-checkpoint/change.md#ic-1-capture-in-passes), "Reading the slot's files") **[measured]**. The AWS re-validation of 2026-11-12 found such FIFOs left out of the snapshot without an error before this rule. Any other entry that fails the device check is refused. Sockets are recorded and not restored. Extended attributes are not captured: `fgetxattr` on a passed descriptor of a `0600` file returns `EACCES` **[measured]**, and the checkpoint format carries none.

**Clones into the spool.** The spool is on `lenny-spool`, which only the adapter mounts and whose size the pool's `spoolSizeLimitBytes` sets. The adapter reserves each slot's `checkpointCaptureBudgetBytes` in it and lets the slots share the rest as upload staging ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction); [WM-4](../0153-workspace-materialization/change.md#wm-4-the-plan-the-adapter-builds)), so one slot's staging cannot take another slot's capture room. The adapter clones a large changed file from the broker's descriptor into the spool with `FICLONE`, which Linux allows across mounts of one file system from 5.18 **[external]**. Spike 3 measured 12 of 12 clones from broker descriptors, and a 64 MiB clone that used no spool bytes **[measured]**. Under gVisor `FICLONE` returns `EOPNOTSUPP` **[measured]**, and IC states the fallback and the spool's accounting.

**The change tracker.** The supervisor creates the slot's `inotify` descriptor and passes it, the adapter asks the broker to add watches, and the adapter reads events from the shared descriptor. Spike 3 measured 212 dirty paths on runc and 211 on gVisor's default mount, where an adapter-side tracker sees no events **[measured]**. The tracker's barrier file is created through the broker. gVisor's `inotify` queue has no bound and never reports an overflow **[measured]**, so IC caps the events the adapter reads in one swap. `max_user_watches` and `max_user_instances` count against the UID that holds the instance, which is the slot UID; without user namespaces that UID is the same on every pod of the node, and under user namespaces it is per pod ("SI-11").

**Restore (D9).** The adapter asks the broker to create each entry as the slot UID with its recorded mode, and writes file content through the returned descriptors. Directories are created `0700`, then times are set deepest first, then each directory's recorded mode is set **[measured]**. Spike 3 restored owner, mode (including `0000`, `0400`, `0500`, and `0300`), nanosecond modification time, hard links, sparse extents, FIFOs, and symbolic links exactly, in 0 differences over 23 entries, against 22 of 23 entries wrong on today's restore path; the slot can change the mode and times of every restored entry **[measured]**. On Kata `block-plain` with the dedicated volume GID, LLVM and Chromium broker restores lost only the setgid bit on directories ("SI-1") **[measured]**.

**Materialization.** Every write of a plan source runs in `lenny-materialize` as the slot UID through `setup` ([`0153-workspace-materialization`](../0153-workspace-materialization/change.md)), so every entry a session finds in its workspace is owned by the slot UID. The broker creates entries only for restores.

**Export.** A file part's path is a path in the slot container, which the adapter maps to a broker root and opens through the broker ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout); [IC-3](../0131-incremental-checkpoint/change.md#ic-3-checkpoint-stream)).

**Cleanup.** "SI-3" states the release.

## SI-7 Credentials, manifests, and other shared files

**Credentials.** Where a session has a credential file, the adapter writes it into the slot's run volume, which only the adapter and that slot mount, with mode `0444` set explicitly. The mount boundary protects the file, and the broker is not involved, because the slot only reads it and the adapter owns it. `lenny-cred-readers`, the pod-level `fsGroup`, and the `POD_SPEC_CRED_FSGROUP_MISSING` rejection leave, and §13.1's statement that "any slot's agent code can read every other slot's credential file" stops being true. [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/change.md) removes direct LLM delivery mode, the file's LLM use, so the file exists only if a VCS path still uses it, which that design leaves to validation. PL names the path.

**`netagent` credentials.** A session's `delivery: file` credentials sit on the slot's own credentials volume, `slot-<n>-netcred`, a memory-backed volume that `netagent` mounts read-write and writes, that slot container `n` mounts read-only at `/run/netagent/credentials`, and that no other slot mounts ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). Every other value that belongs to one session sits on the same volume: the session's binding list, `/run/netagent/credentials/bindings.json`, which names each of the session's bindings with its hosts; the `netrc` file; the session's git configuration include file, which the pod-wide git configuration names by a path under `/run/netagent/credentials`; one commit identity file per VCS pool of the session, which the include file selects per repository with git's `includeIf "hasconfig:remote.*.url:<pattern>"`, as the owner confirmed on 2026-11-13 and the egress design states; the files and variable values of a federated binding; and the session's coordination generation. The pod-wide files, the network descriptor `/run/netagent/network.json` and the git configuration `/run/netagent/gitconfig` among them, name only paths under `/run/netagent/credentials`, which are the same in every slot because each slot mounts its own volume there. `NETRC` names `/run/netagent/credentials/netrc` on every pod, a file that is empty when the session has no Basic binding, and the `inject` placeholder is the profile's constant `lenny-injected`, so no launch variable carries a session's value and no slot reads the binding names, hosts, or settings of another slot's session ([`0127-egress-and-git`, "Injected configuration"](../0127-egress-and-git/change.md#injected-configuration)). The mount boundary keeps one slot's credential files and binding list from every other slot, as it does for the run volume. `netagent` scopes the slot's connections to its own session (egress decision 60), so the file a slot reads and the scope its connections get belong to the same session.

**Manifest.** Each slot has its own manifest on its run volume, written the same way, with its own `connectionNonce` and the adapter UID the SDK checks ("SI-2").

**Webhook rules.** The `lenny-pod-security` webhook's rules extend to the slot containers: slot `n`'s volumes may be mounted only by `adapter` and `runtime-<n>`, its credentials volume `slot-<n>-netcred` read-write only by `netagent`, its writer, read-only only by `runtime-<n>`, and by no other container, `lenny-spool` only by `adapter`, `lenny-git-stores` read-write only by `lenny-store-fill` and `adapter`, no volume mount sets `subPath`, each slot UID is reserved for its own container, the store GID is the `runAsGroup` of `adapter` and `lenny-store-fill` alone and is refused as the `runAsGroup` or `runAsUser` of every other container and in `supplementalGroups` (D28), and `fsGroup` is admitted only on a Kata `block-plain` pod and only as the dedicated volume GID. `lenny-ephemeral-container-cred-guard` refuses an ephemeral container that runs as a slot UID, the adapter UID, or the `lenny-store-fill` UID, carries the dedicated volume GID or the store GID, or mounts any slot volume, any credentials volume, `lenny-spool`, or `lenny-git-stores`, in place of its `lenny-cred-readers` condition.

**Modes of the pod-wide volumes.** Without `fsGroup`, a reader in a slot container reads through the other class of each file's mode. [PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction) states the owner and modes of every volume, and the egress design states `netagent`'s.

## SI-8 Shared repository stores

**Stores.** The `lenny-store-fill` init container fills the repository stores and their pristine trees on the pod-wide store volume before any regular container starts, under a UID of its own, with no credential, through `netagent`, which attributes its UID as the platform fill (D26). It writes with a dedicated store GID as the group, which is the primary group of both `lenny-store-fill` and the adapter, and a umask of `0002`, so directories come out `0775` and object files `0444`, and after each fill an explicit mode pass over the store and its pristine tree sets directories to `0775`, regular files to `0444`, and executable files to `0555` and clears every setuid and setgid bit, so nothing in the volume grants write to the other class (D28; [PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout); [WM-15](../0153-workspace-materialization/change.md#wm-15-warm-up-checkout-and-reflink-rebuild)). Every agent-pod container runs with `allowPrivilegeEscalation: false`, so a set-ID bit has no effect in any case **[source]**. Every slot reads the stores through the other class. No slot container holds the store GID. Sharing the adapter's primary group with the fill exposes nothing else of the adapter's, because the fill mounts no adapter volume other than the store volume, its other mounts are `lenny-bin` and `/run/netagent` read-only, and it is an init container that has exited before the adapter starts ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). The adapter mounts the volume read-write only to delete a withheld store and its pristine tree, which it does through the group class, and it reads no repository data, the pristine trees included. The deletion follows no symbolic link: the adapter opens each directory with `openat2` and `RESOLVE_NO_SYMLINKS | RESOLVE_BENEATH | RESOLVE_NO_XDEV` relative to a directory descriptor beneath the volume root, and removes each entry with `unlinkat` relative to its parent's descriptor, so a link in a store cannot point the deletion outside it. On a Kata `block-plain` pod, whose volume root carries the setgid bit and the dedicated volume GID, `lenny-store-fill` regroups each store's directory to the store GID and clears its setgid bit before it writes into it, so the deletion works the same way (PL-3). PL's "Validation owed" carries the hostile-repository stress test suite of D28. Every slot container mounts it read-only at `/lenny/git-stores`, the same path in every slot ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)), so the absolute path a slot repository's `objects/info/alternates` names resolves in every slot **[measured]**. Writes fail with `EROFS` **[measured]**. Every git step on a slot repository runs as the slot UID in the helper ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)), so only slot containers resolve the path.

**How a session uses a store.** The slot repository borrows objects through alternates, which is what `git clone --shared` sets up. The local spike of 2026-11-11 measured, on a 301 MiB pack with a 9.9 MB working tree of 2,001 files:

| Per-session method, as the slot UID | Time | Disk per session |
| :-- | :-- | :-- |
| `clone --shared` (alternates) | 56 to 60 ms | 9.9 MB, with a `.git` of 340 KB |
| `clone --reference` | About 60 ms | 9.9 MB |
| `clone --shared --no-checkout` | Under 10 ms | 168 KB |
| `clone --shared --sparse`, one package | About 20 ms | 920 KB |

**Image volumes.** A Kubernetes image volume was admitted under Pod Security Standards Restricted, and `clone --shared` from it took 0.06 s **[measured]**. This design records it and does not adopt it.

**Withheld stores (O10).** A failed read check on a store whose repository the session's plan does not name refuses the session on a shared pod, as today. A staged warm checkout from a store withheld for the session is removed before the session starts ([`0153-workspace-materialization`](../0153-workspace-materialization/change.md)).

## SI-9 CPU and memory

**What the local spike measured** on Kubernetes 1.35.0 with cgroup v2 **[measured]**:

- **CPU with no per-container limit.** A slot with a 250m request used 6.00 cores with no throttling while the others idled, and two busy slots split the node evenly.
- **CPU under a pod-level limit.** With a pod limit of 2 CPU and no container limits, every container's `cpu.max` was the pod's, a slot reached 2.01 cores alone, and two busy slots split 1.00 and 0.99.
- **Per-container memory limits.** A slot that exceeded its 128Mi limit was killed as a whole container, and the other slots ran on.
- **Memory under a pod-level limit.** A slot held 404 MiB of a 512Mi pod limit alone. When a second slot grew, the pod-level out-of-memory kill took the largest container, and under fast growth also the second slot about 3 ms later, in 2 of 2 runs.
- **Overcommitted per-slot limits.** With a 512Mi pod limit and 256Mi slot limits, a third slot's growth made the pod-level kill take a slot that had not caused the pressure.
- **In-place resize.** A pod-level resize and a per-container resize applied with no restart. In-place resize of pod-level resources needs an alpha feature gate **[external]**.

**Rule.** Under O4 (a) and O5 (a), a resource class states the pod's total, as billing decision 7 settles today **[source]**:

- the pod's `spec.resources` takes the class's CPU limit, so CPU bursts across slots;
- `adapter` and `netagent` take their chart values;
- each slot container takes a CPU request of the remaining CPU divided by the slot count, with no CPU limit;
- each slot container takes a memory request and limit of the remaining memory divided by the slot count, which must be at least the platform's floor on slot memory ([WM O1](../0153-workspace-materialization/change.md#open-decisions)).

A container that sets a limit and no request gets a request equal to its limit, and the API refused a pod where that made the requests exceed the pod's until every request was set **[measured]**, so the renderer sets every request.

**Memory-backed volumes.** A slot's `/dev/shm` counts against its own memory limit, at the pool's per-slot size ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). `/session` and `/tmp` are disk-backed under PL, so revision 3's session-file cap in the adapter's memory leaves.

**Contention between slots.** Concurrent checkpoints and restores of several slots slow each other: the AWS re-validation measured two concurrent LLVM restores at 241 to 283 s against 47 to 132 s alone **[measured]**. IC staggers checkpoints so that at most one slot of a pod checkpoints at a time ([IC decision D20](../0131-incremental-checkpoint/change.md#decisions)).

**Detection.** The API server drops a field whose feature gate is off without an error **[external]**, so reading the pod back proves only the API server's gate. The design detects enforcement where it takes effect **[design]**:

- The renderer gives the adapter a CPU request and no CPU limit when it renders pod-level resources.
- At start-up the adapter reads its own cgroup's `cpu.max`. Under enforced pod-level resources a container without its own limit carries the pod's limit, as the spike measured **[measured]**, and otherwise it reads `max`.
- The adapter reports the result on `CH-ADAPTEREVENTS`. When pod-level resources are not enforced, the controller records that on the pool and renders later pods with each slot's CPU limit equal to its request.

## SI-10 What stays shared

The local spike measured what separate containers do not isolate **[measured]**:

- **Network.** A slot reached another slot's listener on `127.0.0.1`. Abstract socket names are listed in `/proc/net/unix` for every container, a slot connected to another slot's abstract socket, and a slot can bind a name another container has not bound. "SI-2" closes each case that touches a platform socket.
- **IPC.** The IPC namespace is per pod, so System V objects and POSIX message queues are shared: a slot listed another slot's System V segments. A `0600` object stayed private. PL gives each slot its own `/dev/shm`, so POSIX shared memory objects are private to the slot ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). The Sweep removes a slot's objects at each release.
- **Disk.** Every `emptyDir` lives on the node's disk, and the kubelet evicts the whole pod when one `emptyDir` exceeds its size limit **[measured]** **[external]**. The adapter's per-slot disk watch fails the offending slot's session first, measuring each volume as PL's O8 settles ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction); D24). Where the node's filesystem has project quotas, a quota slightly below `sizeLimit` bounds each slot volume of runc pods with user namespaces and Kata virtio-fs pods, and `/tmp` under gVisor, so a slot's write past it fails with `ENOSPC` or `EDQUOT` and evicts nothing, and the watch reads the volume with one `fstatfs` call that counts every byte **[measured]** ([PL-10](../0118-agent-pod-layout/change.md#pl-10-project-quotas); D32). On runc without user namespaces a slot can take its own files out of a project, so no quota is trusted there **[measured]**.
- **Kernel.** Under gVisor and Kata every container of the pod shares the pod's sandbox kernel. Under runc every container shares the node's kernel with every pod on the node, which PM's node classes and node tenancy bound ("SI-11").
- **The adapter and `netagent`.** One adapter and one `netagent` serve every slot. `netagent` attributes each connection to its slot (O9; egress decision 52) and scopes it to that slot's session: its readable and writable sets, its environment, its host lists, and its credential bindings (D25; egress decision 60). On each CONNECT it opens for an attributed connection, `netagent` names the session in the header `x-lenny-session`, which it strips from agent input, and the decision service accepts the header only for a session the pod's binding lists and keys its cached decisions on that session, so one slot's allow never serves another slot. Whether attribution answers is a property of the pool's runtime class: `netagent` reports at start whether its readers answered, and the controller records the result in the pool's status. On a pool whose runtime class does not answer, the pod falls back to the union of its sessions' readable and writable sets, applies no per-session credential binding, evaluates its sessions with no environment, and refuses `egress.allowedHosts` and `egressLockHosts`, and `sessionIsolationLevel.perSlotScopes` reports the fallback as `false` ([PM-4](../0136-placement/change.md#what-sessionisolationlevel-reports)). A `netagent` whose reader stops answering on a running pod refuses the connection rather than falling back ([`0127-egress-and-git`, "Slot attribution and fetch grants"](../0127-egress-and-git/change.md#slot-attribution-and-fetch-grants)). User credential bindings, `lockEgressToHosts`, and user git identity are allowed on a pool whose status records per-slot attribution and refused on a fallback pool and on a recycled or used pod (D29). The spike D29 asked for measured on 2026-11-14 that runc pools attribute through `sock_diag` and gVisor and Kata pools through `/proc/net/tcp`, so no measured runtime class is a fallback pool, and `netagent` accepts an answer only for an established socket of a UID it was configured with ("Validation record"). A slot under gVisor or Kata can create a nested user namespace, which runc's RuntimeDefault seccomp profile refuses, and both readers still report the slot's UID **[measured]**; an isolation argument that assumes a slot cannot create a user namespace holds on runc alone. `netagent` marks a connection whose socket owner is the adapter's or `netagent`'s own UID as platform and allows it only to platform destinations, the gateway, object storage, and the git mirror; a slot cannot obtain the marker, because the attribution reads the kernel-reported socket owner and `netagent` strips the header from agent input (D30).
- **Failure and resources.** An eviction or a node failure ends every slot's session, and slots contend for CPU, memory bandwidth, disk, and network.

**The acknowledgment that remains (D20, D21).** A pool runs with `maxConcurrentSessionsPerPod` above 1 only with `acknowledgeSharedPod: true` in its `sessionPolicy`, which the deployer sets on the pool and never per session. A pool whose value is 1 needs no acknowledgment. Its use for `recycle.runtimeProcess: keep` leaves together with `keep` (D4). The validation error states what slots still share **[design]**:

> `sessionPolicy.acknowledgeSharedPod` must be true when `maxConcurrentSessionsPerPod` is above 1. Each session on a shared pod runs in its own slot container under its own UID, and the sessions still share the pod's network namespace (localhost ports, abstract sockets, the DNS cache, and timing side channels; `CAP_NET_RAW` stays dropped), the pod's IPC namespace (System V objects and POSIX message queues), the sandbox kernel under gVisor and Kata, the adapter and `netagent` (which scopes each slot's connections to that slot's session, and falls back to the union of the pod's sessions only on a pool whose runtime class does not answer slot attribution, as the pool's status records), pod-wide eviction and failure, and contention for CPU, memory bandwidth, disk, and network.

**What a client sees.** The session's `sessionIsolationLevel` reports `sharedPod`, `userNamespaces`, and `perSlotScopes` as [PM-4](../0136-placement/change.md#what-sessionisolationlevel-reports) defines them, and its `residualStateWarning` text names the same shared properties as the validation error. A tenant that sets `placement.allowSharedPod: false` keeps its sessions off shared pods, and `placement.allowReusedPod: false` off pods that have served a session ([TSS-6](../0150-tenant-security-settings/change.md#tss-6-placement-settings)).

## SI-11 User namespaces and Landlock

**User namespaces on runc pools (D18, SIR-32).** Every runc pod runs with `hostUsers: false` by default, so the kubelet gives each pod a host UID range of its own, and every UID in the pod, the slot UIDs included, maps to an unprivileged host UID in that range. Slots inside a pod keep distinct UIDs inside the pod's range. An operator may disable user namespaces on the standard class, which renders the pods without them and logs a loud warning, as [PM-1](../0136-placement/change.md#user-namespaces-on-the-standard-class) states with its preflight warning, alert, audit record, and `sessionIsolationLevel.userNamespaces`. There is no intermediate mode. gVisor refuses `hostUsers: false` with "RuntimeClass handler "runsc" does not support user namespaces" **[measured]** and does not need it, because the sentry accounts per sandbox. Kata does not need it, because each pod has its own guest kernel, and its support is unverified. PM states the node prerequisites: Kubernetes 1.33 or later, containerd 2.0 or later with runc 1.2 or later, a kernel with idmapped mounts for every volume type the pod mounts, and on Bottlerocket a raised `user.max_user_namespaces`.

**What it fixes.** Per-UID kernel accounting is node-wide: descriptors in flight over `SCM_RIGHTS`, `inotify` instances and watches, pipe pages, and process counts are counted per host UID. Every pod uses the same in-pod slot UIDs, so without user namespaces a process at slot 0's UID in any pod on a runc node shares slot 0's accounting in every other pod on that node. The asynchronous worker's spike measured the consequence: a pod on the same runc node, running at the slot UID and holding 1,048,685 descriptors in flight against an `RLIMIT_NOFILE` of 1,048,576, made the victim slot's broker replies fail with `ETOOMANYREFS` for about 20 s, after which they recovered once the attacker released them **[measured]**. A session on any runc pod of a node could thereby deny descriptor passing to every slot with the same index on that node, which fails their checkpoints. Under user namespaces each pod's slot UIDs map to distinct host UIDs, so the accounting is per pod. Under gVisor the attacker held 53,886,976 descriptors in flight with no limit and the victim was unaffected **[measured]**. An escape from a runc container also lands as an unmapped, unprivileged host UID.

**The mitigation in the supervisor.** The supervisor's handling of `ETOOMANYREFS` ("SI-5") stays as defence in depth and for the case inside a pod, where a slot can exhaust only its own UID's count: during such an attack by the slot itself the reply carried the errno, a ping answered in 0.1 ms, and the broker served normally afterwards **[measured]**. A pod whose operator disabled user namespaces keeps the cross-pod exposure, and the warning names it.

**The `uid_map` check.** The API server drops `hostUsers` without an error where the feature is off: the egress design measured it on Kubernetes 1.31.4 **[measured]**. Before READY, on a pod the controller rendered with user namespaces, the adapter reads `/proc/self/uid_map`, and when the map is the host's identity map, `0 0 4294967295`, it reports the pod failed with the reason `user_namespace_missing` and does not report READY. Through kind's kubelet with user namespaces the map read `0 3145662464 65536` **[measured]**. The check keeps an enabled setting from degrading silently.

**What user namespaces do not give.** They do not give the adapter access to a slot's files: a capability that reads past permissions, `DAC_READ_SEARCH`, needs the Privileged standard, and root with it in the host user namespace reached `open_by_handle_at` past the RuntimeDefault seccomp profile, which is the primitive of the "shocker" container escape **[measured]**. In kind, `SO_PEERCRED` reported the in-pod UIDs and Pod Security Standards Restricted admission passed under user namespaces **[measured]**. On EKS AL2023 with kernel 6.18, idmapped mounts on XFS and tmpfs worked, and with kernel 6.1 idmapped tmpfs failed with `EINVAL` **[measured]**.

**runc as a profile (D19).** runc shares the host kernel and gives no protection against kernel exploits. Its blast radius is bounded by the node class, which by default keeps gVisor pods, Kata pods, and Lenny system components off runc nodes, and by user namespaces, which land an escape as an unmapped host UID ([PM-1](../0136-placement/change.md#pm-1-node-classes-and-presets)). runc pods on one node share that node's kernel across the tenants scheduled there, unless the operator dedicates nodes per tenant ([`0136-placement`, "PM-2 Node tenancy"](../0136-placement/change.md#pm-2-node-tenancy)). The choice of profile is the operator's, and `allowStandardIsolation` stays as its explicit opt-in.

**Landlock (O7).** Landlock restricts a process's file access, and from ABI 6 its connections to abstract sockets and its signals, with no privilege beyond `no_new_privs`, which Lenny sets **[external]**. The spikes measured ABI 6 on kernel 6.12, ABI 7 on kernel 6.18 on EKS AL2023 and Bottlerocket, ABI 2 on kernel 6.1, which has file rules and no socket or signal scoping, and `ENOSYS` under gVisor **[measured]**. A ruleset confined a slot to its workspace and refused `connect` to the adapter's socket with `EPERM` **[measured]**, so scoping would also change how a runtime connects. The design defers it.

## Worked example

A pool `team-agents` runs Claude Code with `maxConcurrentSessionsPerPod: 2` and `acknowledgeSharedPod: true` on runc nodes of the standard class, with user namespaces on. Its runtime carries a public warm-list entry for `github.com/acme/monorepo`.

1. The controller creates a pod with slot count 2 and `hostUsers: false`. `netagent` starts, and `lenny-store-fill` fills the monorepo store and its pristine tree through it under its own UID and exits. `adapter`, `runtime-0` under in-pod UID 20000, and `runtime-1` under in-pod UID 20001 start. Each supervisor opens its broker roots, writes its canaries, dials its own `@lenny-supervise-<n>`, and checks that the adapter answers as the adapter UID; the adapter checks the supervisor's UID.
2. The adapter reads `uid_map` and finds a range of the pod's own. It asks each broker for its roots and pins their device and mount ID, sees each canary through its own mount, and reads its own `cpu.max` to confirm pod-level resources. After the pre-READY Sweep it stages a warm checkout of the monorepo in each slot through a helper run, and reports READY. No runtime process runs.
3. Alice's session binds to slot 0. A helper run adopts the staged checkout into `/workspace/repo`, the session's setup commands run as UID 20000, one `setup` each, and `npm ci` takes 90 s. During it the adapter's pings and broker requests to slot 0 are answered as usual. The adapter then drains `@lenny-runtime-0`, sends `launch`, and the runtime's handshake and capability check pass before `session_start`.
4. Bob's session binds to slot 1 the same way.
5. Alice's agent calls `start_child_session` through its bridge's tool connection on `@lenny-runtime-0`. The adapter attributes the call to Alice's session. A frame on slot 0's connections acts for Alice's session whatever it carries: a `sessionId` member naming Bob's session is an unknown member, which the adapter ignores (AR O5 (b)).
6. Alice's agent runs `mv /workspace /w`, which fails with `EBUSY`. It plants `/workspace/peek` as a symbolic link to `/adapter/slots/1/run`, and an editor saves a file through `mkstemp`, leaving it `0600`. At the next checkpoint the parallel stat walk records `peek` as a link with its target text and follows nothing, and the adapter reads the `0600` file through a broker descriptor. No path in slot 0 reaches a volume of slot 1.
7. Bob's session ends. After its seal, slot 1's supervisor runs End and the Sweep, which gives a `0555` module directory owner write before descending into it. The cleanup commands run, End runs again, a second Sweep removes a file a cleanup command left in `/tmp`, the adapter finds both brokered volumes empty, drains `@lenny-runtime-1`, and stages a warm checkout for the next session. Alice's session is untouched.

## Limits

- **The network and IPC namespaces stay shared.** A slot can reach another slot's localhost listeners and abstract sockets, and see its System V objects and POSIX message queues ("SI-10").
- **One slot can evict the pod by disk where no project quota applies.** The disk watch fails the slot first, and an eviction it misses ends every slot's session ("SI-10", D24). A volume that a project quota bounds stops the slot's writes at the quota instead (D32).
- **Bytes the disk watch cannot list.** A session can write files into a directory and then set the directory's mode to deny its owner read, such as `0300` or `0000`. Neither the walk nor the broker can list such a directory, so a walk misses its bytes, while the kubelet still counts them and evicts the whole pod. `statfs` counts them where a project quota bounds the volume, under gVisor's pod-share mount, and on Kata `block-plain` **[measured]**. The owner accepted the miss as a residual risk of shared pods (PL's O9 settled as (a), D31), and the project quotas of D32 settle it on runc with user namespaces, gVisor, and Kata. It remains on runc without user namespaces, on a node without project quotas or without a ready quota agent, and on a volume the agent reaches during a session, until that slot's next release.
- **Setup commands precede the launch.** A process a setup command leaves running can connect to the slot's endpoint in the launched runtime's place, for its own session ("SI-2").
- **gVisor.** A slot process can stop or kill its own supervisor, which costs the slot ("SI-4"). The names of the supervisor's descriptors in `/proc/1/fd` are listable by slot processes **[measured]**, which shows descriptor types and the broker roots' paths and no content. gVisor has no limit on descriptors in flight **[measured]**, so a slot can hold sentry memory with them. No reflink clones exist, so the spool takes real copies, and sparse files are reported as one data extent **[measured]**.
- **A same-UID tracer on runc.** A slot process that traces the setup program can hold back its status, so the run ends at its deadline plus 5 s **[inference]**. It harms only its own session.
- **Metadata-only entries.** A checkpoint keeps no content of an entry the owner cannot open, and restores no socket (O2).
- **No extended attributes.** Checkpoints carry none.
- **No memory borrowing between slots.** Under O4 (a) an idle slot's memory is unused.
- **A dead slot stays dead.** Each out-of-memory kill of a slot container, and each failed slot release, a cleanup command that fails or times out included, costs the pod that slot until the pod is replaced ("SI-4", D39).
- **Guest-kernel state under `standard` on `microvm` pools.** The guest's DNS resolver cache, TCP `TIME_WAIT` state, buffer and page cache priming, and inotify and fanotify registrations persist across the pinned tenant's sessions. `vm-restart` clears them at the cost of a fresh pod at every occupancy-zero boundary (D39).
- **Broker fallback.** A tree the adapter cannot search costs about what a broker `statat` walk costs, and a flat directory of 1,000,000 entries does not fit the 10 s pause budget on gVisor's default mount or Kata `virtio-fs` without the tracker **[measured]**.
- **Kata `block-plain`.** The dedicated volume GID lets every slot read group-readable files of the pod-wide volumes, and restores drop setgid on directories ("SI-1").
- **Withheld stores.** A session whose read check fails on a store its plan does not name is refused on a shared pod (O10).

## Alternatives rejected

- **A per-session token in one shared container.** Every process in the container runs as one UID, which can read a token wherever it is kept.
- **One shared runtime process that switches UIDs for each session's harness.** It needs `CAP_SETUID` in a process that runs runtime-author code, Pod Security Standards Restricted forbids the capability, and every frame would still cross one connection.
- **A root supervisor in a user namespace that switches UIDs.** `CAP_SETUID` stays forbidden under Pod Security Standards Restricted with `hostUsers: false`, so the pod falls to Baseline.
- **Pod-level `fsGroup` or `supplementalGroups` for per-slot groups.** They apply to every container, so every slot joins every group **[measured]**. The Kata `block-plain` exception uses one dedicated GID for volume roots only.
- **Default ACLs per slot volume.** Revision 1's mechanism. A `chmod 600` or `setfacl -b` still locks the adapter out **[measured]**, and it depends on ACL support in each file system.
- **A umask of 0 with widened restore modes.** Revision 2's mechanism (D7). It still loses `0600` files, the contents of `0700` directories, atomic saves, hard-link identity, ownership, and exact modes **[measured]**.
- **subPath mounts.** Under gVisor with the pod-share annotation the adapter and the slot get disjoint views, and the adapter checkpoints nothing without an error **[measured]**.
- **A broker container per slot, in Go.** Its tracker on gVisor's default mount saw 1 event of 211, and it costs about 10 MB of resident memory per slot on runc and about 63 MB on gVisor **[measured]**.
- **Capabilities for the adapter.** Pod Security Standards Restricted rejects them, Baseline lacks `DAC_READ_SEARCH`, added capabilities are not effective for a non-root container, Kubernetes has no ambient-capability field, and `DAC_READ_SEARCH` as root reached the `open_by_handle_at` escape primitive **[measured]**.
- **Copy-out by the supervisor.** It would move the walk, the index, the change rules, and the clone fallback into C, against D3.
- **Rewriting modes.** A pass that adds group read changes modes visibly, and `ssh` refuses a group-readable key; `LD_PRELOAD` misses static binaries; seccomp notification has no Kubernetes API and a time-of-check race; and Kubernetes has no per-container idmapped mounts **[measured]**.
- **A synchronous worker.** The materialization study recommended it. On AWS a detached checkout over the store's alternates took 19.2 s, and a broker request sent 0.1 s after it waited 19.1 s; a capture-copy repack of LLVM outlived the 120 s broker deadline, and the slot was declared dead **[measured]**.
- **Supervisor broker workers.** Several forked broker processes, each on its own socket pair, gave worse worst-case latencies than one supervisor at 8 and 16 threads in the local walk spike **[measured]**, and the parallel stat walk removes the broker from the steady-state walk.
- **Broker `statat` as the whole walk.** It costs 1.6 to 4 times the parallel stat walk per entry, and its worst requests reached 76 ms on Kata `virtio-fs` **[measured]**.
- **Per-pod slot UIDs allocated by the controller.** The cross-pod accounting could also be split by UIDs unique across the cluster and recorded on the `AgentPod`. The owner chose user namespaces, which split the accounting with no allocator and also land an escape as an unmapped host UID (D18).
- **A `preferred` user namespace mode.** The owner chose on by default with an explicit disable, and the `uid_map` check (D18).
- **Skipping `lost+found` by name in the emptiness check.** On Kata `block-plain` the slot can write into it through the volume GID **[measured]**.
- **Checkpoint and cleanup as the slot UID through the supervisor.** The owner flagged it (D3).
- **A native-sidecar adapter.** Per-slot names, two-way checks, and SIR-5 close squatting with the adapter as a regular container (D5).
- **Container restart as cleanup.** It is slow under backoff and leaves files and IPC objects **[measured]**.
- **bubblewrap or nsjail inside the slot.** Both need to create user namespaces, which the RuntimeDefault seccomp profile refuses without `CAP_SYS_ADMIN` **[measured]**.

### Spike 1: compatibility with the incremental checkpoint design

Every mechanism of the incremental checkpoint design worked through the per-slot layout under runc and gVisor: the identity comparison, the rule for files written during capture, `FICLONE` into the spool, export clones, the change tracker on runc, confined reads, restore with revision 2's mode rule, and cleanup **[measured]**. A change set was captured in 8.7 ms with 1.6 MiB of new disk on XFS through `FICLONE`, against about 60 ms and 101.6 MiB through the copy fallback **[measured]**. Every planted symbolic link was refused, where a naive open would have read the other slot's secret and the adapter's environment **[measured]**. The verdict was "compatible with the changes listed". Its findings:

- Under gVisor, the IC-8 pod-share annotation on a volume a slot mounts through subPath gives the adapter and the slot disjoint views, so the adapter would checkpoint none of the slot's files and report no error. D8 is the fix.
- The kubelet created subPath directories as `root` with mode `0777`, so the slot could rename its session directory. D8 makes this moot.
- Slot roots should be opened with `RESOLVE_BENEATH | RESOLVE_NO_XDEV | RESOLVE_NO_SYMLINKS`, everything below them with `RESOLVE_BENEATH | RESOLVE_NO_XDEV`, and final components with `O_NOFOLLOW`.
- Warm stores must be at the same absolute path wherever git resolves alternates.
- Restore as the adapter with widened modes left the slot with `EPERM` on `chmod` and on `utimensat` with explicit times. D9 retires that rule.
- The Sweep must not depend on changing the mode of a volume root, and must clean `/tmp`; the adapter must check that the tree is empty before reusing a slot, and fail the slot otherwise.
- `mkstemp` files are `0600` and unreadable to the adapter under any non-privileged scheme. D9 addresses this.
- An `EACCES` from `inotify_add_watch` should count as one unreadable path rather than degrade the whole tracker. D9's supervisor-held tracker supersedes this.
- The spool cap must be accounted per file by logical size or allocated blocks, never by `statfs`, because the kubelet counts reflink clones at full size against `emptyDir.sizeLimit`.
- Index identity is per mount view: under gVisor the device differs between containers, which costs a full re-read and causes no error.
- After `git clone --shared` from a warm store, the index must be refreshed more than 1 s after checkout, or 2,342 duplicate loose objects, about 28 MB, are written into the slot.
