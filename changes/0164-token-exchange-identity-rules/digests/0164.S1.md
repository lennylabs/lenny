## Defaults applied

Revision 3:

- **Rotation lineage inheritance.** Decision 7 says a rotation records no parent. The token a rotation issues takes the replaced row's own `parent_jti` and `act_sub` instead of null, so the decision holds for a root token, and a narrowed, other-caller, or child token keeps the parent decision 7 preserves. O3 lets the owner revisit it.
- **Administrator roles.** The administrator roles are `tenant-admin` and `platform-admin`. They are read as the gateway reads them: a platform-managed assignment in the users table replaces the token's `roles` claim, and the claim holds without one. A failed lookup refuses the request with `503 token_store_unavailable` during a Postgres outage and `500 token_exchange_failed` otherwise. The token's own user is accepted without a lookup.
- **Refusal codes.** A caller that is neither the owner nor an administrator receives `403 unauthorized_client`, the RFC 6749 code for a client not authorized for the grant, with the status of the existing cross-tenant refusal. A revoked caller token receives `401 invalid_client`, as a playground caller does. A child mint whose actor is not the caller's receives `400 invalid_grant` with reason `actor_token_not_caller`.
- **Revoked-caller check placement.** The caller row is read `FOR SHARE` inside the revoking transaction through a new store method, `RevokeCascadeByCaller`, rather than in a separate read before it. A caller with no row, such as an upstream OIDC ID token, passes.
- **Deadlock retry.** `RevokeCascadeByCaller` runs at most three transactions when Postgres aborts one as a deadlock victim.
- **Child-mint rule scope.** The child-mint rule compares `sub` only, as decision 8 states; `caller_type` is not compared, because an agent session minting a child for its human user carries a different `caller_type`.
- **Same-tenant administrators.** The tenant check runs before the role check, so a `platform-admin` revokes only within its own tenant, as decision 9's "administrator role for the tenant" reads.

Revision 2:

- **One step.** The lineage of decision 3 is one function and one sentence of §13.3, so the change plans one step rather than two.
- **Non-canonical requested values.** A requested value that is not canonical is refused even when the subject carries it literally, and an explicit request from a subject whose scope does not parse is refused, as decision 1's "every value parses" reads. A request without scope from such a subject still receives the subject's scope (the 0163 default). - **Different-caller refusal.** The error is `400 invalid_scope` with reason `scope_not_narrowed`, because the remedy is a narrower `scope`. A `caller_type` that only one of the two tokens carries is not compared, because an IdP caller token carries none.

- **Impersonation scope source.** The handler passes `principal.Scopes.Raw`, the parsed claim text, and the row records the claim split on whitespace.
- **Audit fields.** `requested_scope` is the request's `scope` as split, absent when the request named none; `granted_scope` is absent on every rejected row, including the step (1a) refusal.
