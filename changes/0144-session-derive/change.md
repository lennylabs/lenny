# Session derive

Status: `Draft`, revision 29, 2026-11-27. Programs: [v1](../programs/v1.md).

## Problem

[§15.1 REST API](../../spec/15_external-api-surface.md#151-rest-api) defines two routes that start a session from an earlier one. `POST /v1/sessions/{id}/derive` copies a snapshot, and `POST /v1/sessions/{id}/replay` copies the same snapshot and also claims to replay the prompts.

- **Replay starts from the end.** §15.1 populates the workspace from "the source session's sealed final workspace snapshot". A prompt that says "create `feature.py`" would run where `feature.py` exists.
- **Replay delivers no prompts.** Under replay's default `replayMode: prompt_history`, §15.1 says the source session's prompt history, read from its transcript, "is replayed verbatim as the initial message sequence", and the code copies the transcript and never reads it back on a start path (F-15.1.77).
- **`replayMode: workspace_derive` duplicates derive.** §15.1 states that this replay mode equals a derive onto another runtime, with no prompts delivered. Derive already takes an optional `runtimeRef` in the code, which the specification does not state (F-15.1.76).
- **Neither route has a defined way to start from the beginning**, which is what a regression test needs.

Identifiers of the form F-n.n.n, such as F-15.1.77, are findings filed in `BUILD-GAPS.md` at the repository root. The statements in this design about the tree were checked by reading the code and the specification.

## Scope

This design covers the single derive route that replaces both routes, what each of its modes starts from, what the new session takes from its source, and the read that returns client messages. It applies to every session on every runtime. It removes `POST /v1/sessions/{id}/replay`.

Comparing two runs stays out of scope, and a derive records no evaluation identifier. A session's calls to external systems repeat if a client re-sends the messages that caused them.

## Terms

| Term | Meaning |
| :-- | :-- |
| Derive | `POST /v1/sessions/{id}/derive`, which creates a new session from an earlier one. Under this design it is the only route of its kind. |
| Source session | The session a derive starts from. The new session is the derived session. |
| Mode | A derive's `from` field. `from: latest` starts from the source's latest snapshot, and `from: start` starts from the source's stored plan with no snapshot. "What each mode starts from" states both. |
| Exact start | The owner's aim that a derived session begin in the state its source was in: at the source's beginning under `from: start`, or at its latest snapshot under `from: latest`. "What an exact start does not cover" lists what can differ. |
| Target runtime | The runtime the derived session runs on. The request names it in `runtimeRef`, by default the source's runtime, and a `PreRoute` interceptor can change it before the post-chain point, so the target is the runtime the chain leaves. "Another runtime" in this document means a target other than the source's runtime. |
| Stored plan | The workspace plan a session row holds once the plan binds, with `resolvedCommitSha`, the commit each `gitClone` source resolved to. Under this design a derive copies its source's stored plan. |
| `origin` | A field this design adds to each stored setup command: `operator`, `tenant`, `client`, or `derive`. It decides which policy checks the command, and it decides no folder, because the command's stored `cwd` holds its folder. "Checks", **Setup commands.**, states how a derive reads it. |
| `additionalSetupCommands` | Setup commands a client adds to a derive, which run after the source's, in the plan's working directory unless a command sets its own `cwd`. See "Additional setup commands". |
| Content stop | A change that ends a tenant-derived runtime's content after a compromise: a grant flag set false, or a forbid in the tenant's security record. See "Stops". |
| Content stop check | The function under "Stops" that refuses a derive, at create and at finalize, when a runtime in `planOriginRuntimes` no longer resolves, is retired, or carries a changed stop counter. It is unrelated to the review rounds that "Review history" calls stop checks. |
| `planOriginRuntimes` | The tenant-derived runtimes whose defaults a plan holds, each with the two stop counters read when the plan was composed. See "Stops". |
| `content_stop_epochs` | The tenant-keyed table that holds the stop counters. See "Stops". |
| Client messages | The messages a client sent to a session, as the transcript records them. "Reading client messages" adds a read that returns them. |
| Held message | A message the gateway holds in a session's inbox or dead-letter queue until the session can take it ([§7.2](../../spec/07_session-lifecycle.md#72-interactive-session-model)), such as one a parent session sends to its child with the platform operation `session.send` of [`0166-delegation-primitives`, "DP-1"](../0166-delegation-primitives/change.md#dp-1-session-grant), which replaces `lenny/send_message` and carries `from.kind: agent` ([`0135-message-delivery`, "MD-9"](../0135-message-delivery/change.md#md-9-inter-session-messages-system-messages-and-delegation)). Sessions message each other only along the delegation tree. |
| Transcript | A session's message record, the `session_messages` table, which the `transcriptstore` package writes and reads. |
| Lineage | `derivedFromSessionId` on the derived session's row, which names its source session. |
| `derivedFrom` | A field this design adds to the derived session's row, holding the mode, `latest` or `start`, that created it. It is unrelated to `derivedFromSessionId`, which names the source. "What it refuses" reads it for `start_was_snapshot`. |
| `snapshotIsOwn` | A field this design adds to the session row, which the checkpointer sets once the session's own checkpoint has written its snapshot. Until then a derived session's snapshot is the one its derive copied, so a resume repeats the first bind, and a later derive of it passes on what its parent had. |
| Labels | Parts of the design carry the label SD-n. |

### Terms from other designs and the platform

This design builds on mechanisms other designs and the specification define. The table gives each one the meaning this document relies on.

| Term | Meaning |
| :-- | :-- |
| Workspace plan | The `WorkspacePlan` of [§14 Workspace Plan Schema](../../spec/14_workspace-plan-schema.md#14-workspace-plan-schema). Its `sources` are files, uploads, and `gitClone` clones of git repositories, each written at a workspace-relative `path`, and it lists `setupCommands`. |
| `env` and `runtimeOptions` | Session fields of the create request, stored on the session row beside the plan. `env` holds environment variables injected into the agent session, and the `env` blocklist is a deployer-configured list of variable names and patterns that a create refuses ([§14](../../spec/14_workspace-plan-schema.md#14-workspace-plan-schema)). `env` is unrelated to an environment, below. `runtimeOptions` holds runtime-specific options, validated at the post-chain point against the chosen revision's `runtimeOptionsSchema` ([`0140-runtime-revisions`, "RV-7 Session options"](../0140-runtime-revisions/change.md#rv-7-session-options)). |
| Session states | A session moves through `created`, `finalizing`, `ready`, and `starting`, and while live it is `running` with a turn open or `idle` between turns, and can also be `dormant`, `suspended`, `blocked`, `resume_pending`, `resuming`, or `awaiting_client_action` ([`0146-session-lifecycle`, "SL-1"](../0146-session-lifecycle/change.md#sl-1-states), which removes the `input_required` sub-state). `completed`, `failed`, `cancelled`, and `expired` are terminal. A live source is one in a non-terminal state. Today `session.Validate` refuses a derive of a source in `created`, `finalizing`, or `ready`. Under this design `from: latest` needs a resolvable snapshot, and `from: start` needs only a bound plan. |
| Plan binding | The step that fixes a session's plan and stores it on the session row ([§14.1](../../spec/14_workspace-plan-schema.md#141-workspaceplan-schema-versioning) **Plan binding.**). Today a plan binds at create or at finalize. |
| Composition | The gateway merging the target runtime's `workspaceDefaults`, which are its default files, default clones, and setup commands, into the plan when the plan binds ([§14.1](../../spec/14_workspace-plan-schema.md#141-workspaceplan-schema-versioning) **Runtime workspace defaults.**). |
| Finalize | `POST /v1/sessions/{id}/finalize`, which ends a session's `created` state. It binds a plan if none is bound, materializes the workspace, and runs the setup commands. |
| Claim and bind | A claim reserves a warm pod for a session, and bind attaches the session to that pod and builds its workspace. A session's first bind is the first time this happens. A resume binds again. The exclusive bind path (`exclusiveBindRequest`) binds a session to a whole pod, and the slot bind path (`slotBindRequest`) binds it to one slot of a pod that serves several sessions at once. |
| Credential binding | An object of the [egress design](../0127-egress-and-git/change.md) that gives sessions a secret for named hosts. A binding with `delivery: inject` has `netagent` attach the secret to requests, so the agent never holds it. A named binding is one with `scope: onRequest`, which attaches only to a session whose plan names it. |
| User link | A Lenny user's stored authorization at a provider, such as their GitHub account, which [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) defines. On a VCS pool with `userAuthorization: required`, Lenny checks through the link that the user can reach each repository. |
| Read checks | The checks at bind that a session may read each repository it can reach: the repository allowlist, the session's environment, and, on a VCS pool with `userAuthorization: required`, the user's own access through their link. |
| Provisional binding | The state of a pod during a resume rebuild, before the session returns to `running`, in which the pod receives only read tokens and the secrets of bindings with `delivery: inject`. |
| Readable set | The repositories a session may read, recorded as entries with a state, beside its writable entries ([`0127-egress-and-git`](../0127-egress-and-git/change.md)). |
| Materialization | Writing the plan's sources into the slot's workspace. The adapter stages the uploads, and the materialization helper writes every source as the slot UID ([`0153-workspace-materialization`](../0153-workspace-materialization/change.md)). |
| Materialization helper, `materialize`, and `restore-complete` | `lenny-materialize`, the static binary that the slot's supervisor executes as the slot UID for every write of a plan source and every git step on a slot repository. Its `materialize` subcommand writes a plan's sources into an empty workspace, and its `restore-complete` subcommand reconnects each repository of a restored workspace to the pod's repository store, fetching the repository's base commit through `netagent` when the pod's store lacks it ([WM-2 and WM-13](../0153-workspace-materialization/change.md#wm-13-resume-and-derive)). |
| Slot and slot UID | A place on a pod where one session runs, with its own container and its own UID, under which the runtime, setup commands, and the materialization helper run ([`0145-session-isolation`, "SI-1"](../0145-session-isolation/change.md#si-1-pod-layout)). |
| File-descriptor broker | The slot supervisor's service through which the adapter opens and creates the slot's files as the slot UID. A restore writes a snapshot into the slot through it ([SI-5](../0145-session-isolation/change.md#si-5-the-supervisor-file-descriptor-broker)). |
| Snapshot and checkpoint | A workspace snapshot is an archive of a session's whole workspace. A checkpoint writes one while the session runs, and a session that ends seals a final one ([§4.5](../../spec/04_system-components.md#45-artifact-store) **Workspace lineage:**). [§7.1](../../spec/07_session-lifecycle.md#71-normal-flow) **Derive copy semantics:** copies the source's snapshot to a derived session today. A rebuild is a resume with no snapshot, which builds the workspace from the plan. |
| Upload | A file a client sends before its session starts. The plan names it by `uploadRef`, and an upload and finalize accept the upload secret whose digest the client sent as `uploadTokenDigest` on create or derive (decision 6 of change [0182](../0182-client-chosen-upload-secret/decisions.md)). An upload expires 7 days after it is made, under `UploadDefaultTTL`. |
| Setup command and `setupCommandPolicy` | A setup command is a command the plan lists, which runs in the pod at finalize ([§7.5 Setup Commands](../../spec/07_session-lifecycle.md#75-setup-commands)). The runtime's `setupCommandPolicy` admits each one through its mode, such as `allowlist`, its `shell` setting, and `maxCommands`. §7.5 **Command policy:** exempts the defaults an operator wrote on the runtime. |
| Runtime and runtime row | A runtime is a registered agent definition, with its image, its process, its `workspaceDefaults`, and its `setupCommandPolicy`. Every runtime is an agent runtime whose sessions each bind to a slot of a claimed pod, and no runtime carries a type or an execution mode ([`0119-agent-runtimes-only`](../0119-agent-runtimes-only/change.md), decisions O1 and O2). The runtime row is the gateway's record of a runtime in `runtime_definitions`. Its `registered` field records whether the `Runtime` resource is admitted, which the RuntimeReconciler mirrors onto the row ([DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records)). |
| Pool and isolation profile | A pool keeps warm pods of one runtime. A pool's `sessionIsolationLevel.isolationProfile` is `standard`, `sandboxed`, or `microvm`, in increasing strength. §15.1's isolation monotonicity rule refuses a target weaker than the source unless the request sets `allowIsolationDowngrade`. |
| Pods that serve several sessions | A target that reuses pods is a pool whose pods serve more than one session, one after another under recycling, or at once in several slots when `sessionPolicy.maxConcurrentSessionsPerPod` is above 1. On a pod with several slots, `netagent`, the egress proxy in each agent pod, attributes each connection to its slot and applies that slot's session's own environment, readable and writable sets, and credential bindings, under decision 60 (a) of the egress design, settled by the owner on 2026-11-13 ([`0127-egress-and-git`, "Slot attribution and fetch grants"](../0127-egress-and-git/change.md#slot-attribution-and-fetch-grants)). A pod with no per-session policy is a pod with several slots where that attribution is unavailable. It keeps the union scope over its sessions and applies only the tenant's unscoped egress objects, those that name no environment, to every session it serves ([`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md)). |
| Adapter | The Lenny process in each agent pod that talks to the gateway, stages uploads, restores snapshots through the slot's broker, and asks the slot's supervisor to run the materialization helper and the setup commands. It runs at its own UID and holds the pod's service account token. |
| Runtime supervisor | The first process of every slot container. It launches the runtime's process when the adapter asks, and it runs setup commands and the materialization helper as the slot UID ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model) **Runtime supervisor.**, [SI-3](../0145-session-isolation/change.md#si-3-runtime-processes-slot-release-and-setup-commands)). Every runtime's pods have one, because every pod follows the blueprint of [PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint): the embedded deployment model is removed ([PL-2](../0118-agent-pod-layout/change.md#pl-2-removal-of-the-embedded-deployment-model)), and every runtime is an agent runtime whose sessions run in slot containers ([`0119-agent-runtimes-only`, "AR-5"](../0119-agent-runtimes-only/change.md#ar-5-what-simplifies-in-the-other-designs)). |
| Tenant-derived runtime and platform runtime | A tenant-derived runtime is one a `tenant-admin` derives from a platform runtime, its base, and it can add default files, setup commands, and default clones ([`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md)). A platform runtime is one the platform operator registers. |
| Derivation grant and grant entry | A platform admin's grant that lets a tenant derive runtimes. It holds one entry per base, with the flags `allowWorkspaceFiles`, `allowSetupCommands`, `allowGitClones`, `allowGitCloneWrites`, and `allowAssets` ([`0147-tenant-derived-runtimes`, "Who turns it on"](../0147-tenant-derived-runtimes/change.md#who-turns-it-on)). |
| Tenant view | The runtime store's read for one tenant, which resolves a runtime name to a platform runtime the tenant is granted or to one of the tenant's own ([DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records)). A retired runtime is one the base lifecycle of [DR-6](../0147-tenant-derived-runtimes/change.md#dr-6-base-changes) has retired, which is unrelated to a retired revision under [`0140-runtime-revisions`](../0140-runtime-revisions/change.md), and an `incompatible` one is one whose live base or grant entry no longer admits its settings. |
| Default clone, warm store, `coveredStores`, and `withheldStores` | A default clone is a `gitClone` source a runtime's `workspaceDefaults` adds to every session's plan, an operator's runtime or a tenant-derived runtime ([DR-9](../0147-tenant-derived-runtimes/change.md#dr-9-default-git-clones)). A warm store is a copy of a repository's objects that a pod fetches before any session claims it, for an entry on its pool's warm list, which is always a `gitRepository` entry of a runtime's `sharedAssets`: an operator's public entry on a Runtime, or a `gitRepository` asset of a tenant-derived runtime ([`0147-tenant-derived-runtimes`, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores), **Warm list.**). An entry that sets `prestage: true` also stages a checkout in each idle slot, which the session's first `gitClone` source of that repository adopts. A store serves any `gitClone` source in the plan whose URL matches it. When a session resumes onto a pod whose store differs, the helper's `restore-complete` fetches the clone's base commit through `netagent`. `coveredStores` lists on a claim the stores the session's read checks cover, together with the stores of the pool's public platform entries. `withheldStores` lists the stores of entries whose checks failed, which the adapter deletes before the session starts (**Withheld stores.** in the same section). |
| Tenant security record and forbid | The record in which a `security-admin` sets a tenant's guardrails ([SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)). `derivedRuntimes.forbid` names the derived-runtime features the tenant may not use, and `verbatimClientFiles: forbid` forbids the `verbatimClientFiles` gate of the [egress design](../0127-egress-and-git/change.md). The record is stored as versions, and a change that weakens a guardrail waits as a pending version until a delay passes. |
| `verbatimClientFiles` | The egress design's per-tenant gate, a grant a platform admin gives, on the tenant's client config files, which are tool configuration files such as an `.npmrc`, and on the file templates a tenant's pool overlay adds to the client proxy profile. `netagent`, the Lenny container the egress design adds to an agent pod, writes both into the pod verbatim. |
| Environment | A named scope inside a tenant with its own hosts, routes, and denies, which a session records ([`0149-tenant-scoping-identity`, "TS-3: Session environment context and cross-environment sharing"](../0149-tenant-scoping-identity/change.md#ts-3-session-environment-context-and-cross-environment-sharing)). `egressLockHosts` is a lock that limits a session and its descendants to named hosts, `crossed_from_environment` records that a delegated child crossed from another environment, and the delegation limit bounds the depth of a session's delegation tree. |
| Delegation | A session that holds a session grant can start child sessions through the platform operations of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-1-session-grant), and they form a delegation tree under a root session. A child's exports and inherited inputs come from its parent. |
| Admission gates and interceptors | The checks a create runs before it claims a pod, such as rate limits, `PLATFORM_DEGRADED`, and tenant classification. `PostAuth`, `PreRoute`, and `PostRoute` are interceptor phases at which deployer-supplied interceptors can reject or rewrite a request ([§4.8](../../spec/04_system-components.md#48-gateway-policy-engine)). |
| `PreRoute` chain, creation kind, and last modifier | The `PreRoute` chain is the single run of every `PreRoute` interceptor, in priority order, on every session creation path, including the built-in route interceptor that applies runtime routes ([`0141-runtime-routing`, "RT-2 The interceptor contract"](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract)). Its payload's `kind` field is `create`, `delegate`, or `derive`, and an interceptor's `MODIFY` may change the payload's `requested_runtime`, `requested_pool`, and `routing`. The last modifier is the interceptor whose `MODIFY` last changed a field, which a refusal after the chain names in `details.interceptor_ref`. |
| Runtime route | A tenant's admin resource that sends the sessions requesting one runtime to target runtimes by weight, chosen by a stable hash of a routing key such as the user ID ([`0141-runtime-routing`, "RT-4 Runtime routes"](../0141-runtime-routing/change.md#rt-4-runtime-routes)). |
| Routing labels | The `routing` map on a session, which `PreRoute` interceptors write and the session record then keeps, and which the runtime, billing events, and usage reports read ([`0141-runtime-routing`, "RT-3 Routing labels"](../0141-runtime-routing/change.md#rt-3-routing-labels)). |
| Runtime revision and traffic | A revision is an immutable, numbered version of the runtime fields that define what runs in its pods, such as the image and the `command`. A runtime's traffic is its active revisions and their weights, and the gateway places each new session on one revision by a hash of its rollout key over that traffic ([`0140-runtime-revisions`, "RV-2 Selection"](../0140-runtime-revisions/change.md#rv-2-selection)). No request can name a revision. |
| Post-chain point | The step of session creation that follows the `PreRoute` chain and revision selection and precedes the pod claim. | Placement checks | The post-chain checks that [`0136-placement`](../0136-placement/change.md) adds for every creation kind: the final pool's placement offering is a default offering or one granted to the session's tenant ([PM-3](../0136-placement/change.md#pm-3-placement-offerings-and-per-pool-nodeplacement)), the final pool and the chosen revision's pod set meet the session's effective placement requirements, the union of its tenant's, its environment's, and the operator's placement settings for the tenant ([PM-4](../0136-placement/change.md#pm-4-placement-requirements)), and the final pool's region equals the session's `dataResidencyRegion` ([PM-7](../0136-placement/change.md#pm-7-region-placement)). |
| Account link check | The check at the post-chain point of every creation path, derive included, that refuses a session whose plan needs an account link the user has not made, such as a `userCredential` binding on a link provider or an add-on's repository check. | Pack reference | How [`0131-incremental-checkpoint`, "IC-5: Restore, derive, download, and seal"](../0131-incremental-checkpoint/change.md#ic-5-restore-derive-download-and-seal) stores a derive's starting snapshot: a snapshot row that references the source snapshot's manifest and packs, the stored blocks of workspace content, and copies no object. ## High-level design

A Lenny session runs an agent in a pod against a workspace that a plan describes: files, git clones, and setup commands. A client sometimes wants a new session that starts from an earlier one, for example to run the same work on another runtime as a regression test, or to continue from a session's latest state. The API has two routes for this today, derive and replay. Both start the new session from the earlier session's final workspace, neither can start from the beginning, and replay's promise to repeat the earlier prompts is not implemented.

This design keeps one route, derive, with two starting points. `from: latest` starts from the earlier session's last saved workspace. `from: start` starts from the workspace the earlier session began with, rebuilt from its stored plan at the same git commits. The new session copies the earlier session's plan rather than composing a new one from the target runtime's defaults, and it passes the admission and security checks a new session passes. A derive is routed and placed on a runtime revision as a create is, so a runtime route or an interceptor can move it, and it runs on the revision its runtime's traffic gives it rather than on its source's revision. Lenny does not repeat the prompts itself: a read returns the messages the client sent to the earlier session, and the client decides whether to send them again. The main limit is that a derive reproduces the workspace alone. The image, what setup commands download, and the answers of external systems and models can differ, and a client that re-sends messages repeats the pushes and external calls those messages caused.

The rest of this section states each part in the design's terms, which "Terms" above defines. All of it is one proposal, SD-1.

**Request and modes (SD-1, "Request" and "What each mode starts from").** `POST /v1/sessions/{id}/derive` takes `from`, an optional target runtime, pool, and isolation profile, `additionalSetupCommands`, `runtimeOptions`, `delegationLease.maxDepth`, which can only lower the carried delegation depth, and the new session's own `labels`, `budget`, and `budgetRefs` (decision 14), and the replay route goes. At create the gateway copies the source's stored plan and `env` to the new row, so nothing composes, and it copies the source's `runtimeOptions` unless the request carries its own, which replace them. Under `from: latest` the adapter restores the source's snapshot through the slot's broker, and the materialization helper runs `restore-complete`, so no plan source is fetched or written. Under `from: start` the helper runs `materialize` from the copied plan at each `resolvedCommitSha`, with the plan's uploads copied to the new session. Setup commands run again in both modes, as the slot UID. A derive copies no call to a client's tool, because under [`0122-client-tools`](../0122-client-tools/change.md) a call is open only inside a running turn of the source. A derived session starts with no children, and when its source has children, its first delivery carries a system message saying that they did not carry over (decision 11 of 0166).

**Additional setup commands and writes (SD-1, "Additional setup commands" and "Writes").** A client can append setup commands, such as one that creates a branch for the run, under the target's `setupCommandPolicy`. A later derive does not copy them. Repository writes, meaning pushes and pull requests, stay on, and each writable entry is checked again at bind, so an entry that no longer passes reads as read-only. The derive response lists such an entry in `readOnlyDefaultClones` when a default clone added it, and in `readOnlyRepositories` otherwise.

**Reading client messages (SD-1).** `GET /v1/sessions/{id}/messages?from=client` returns the client's messages in order, each with the `toolResults` it carried. The transcript gains a sender and a delivery state on each row, in columns that [`0135-message-delivery`](../0135-message-delivery/change.md#md-3-inbox-states-and-custody) adds, and the REST send path records the client's messages. Under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), every protocol adapter sends through that path.

**Refusals and checks (SD-1, "What it refuses" and "Checks").** A derive runs the `PreRoute` chain with `kind: derive`, and then the checks a new session with the copied plan would meet, on the new session's user and environment and on the runtime, revision, and pool the chain and revision selection chose. The placement checks of the placement design run there too, on the derive's final pool. A refused check stops the derive before any pod claim or copy. One storage reservation covers the whole derive. Each stored setup command carries an `origin`, so an operator's command keeps its policy exemption only where the target's operator wrote the same command. Each also carries the `cwd` that composition wrote, so a derive does not move a command to another folder.

**Stops and the final runtime (SD-1, "Stops" and "Final runtime row").** A plan records the tenant-derived runtimes whose content it holds, with counters that rise at each content stop. A derive is refused once a stop follows the plan, through any chain of derives. A derive compares no execution modes and checks no runtime supervisor, because every runtime is an agent runtime whose slot containers run the supervisor. The final runtime's row must be `registered`, which [DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records) checks at the post-chain point for every creation kind.

```
 Client ──POST /derive {from}──> Gateway: PreRoute chain (kind: derive), revision selection,
                                   │ post-chain checks, content stop check, storage reservation
                                   │ copies the stored plan, env, and runtimeOptions,
                                   │ unless the request replaces the options
                                   │ from: latest: also the snapshot
                                   │ from: start:  also the plan's uploads
                                   ▼
                          Derived session on the target runtime
 Client ──GET /messages?from=client──> source's client messages
 Client ──(re-sends them, if it chooses)──> derived session
```

## Requirements

- R1. A derive names its starting point: `latest` or `start`.
- R2. A derive composes nothing from the target runtime. The target contributes its image, its process, and its pods.
- R3. A check that would refuse a new session with this plan refuses the derive, before a pod is claimed.
- R4. A derive does not bring back content that a stop has ended.
- R5. A client can read a session's client messages in order, and it decides what to do with them.
- R6. A client can add setup commands to run after the source plan's.
- R7. A derived session starts with no children and no open call to a client's tool, and when its source had children, its runtime is told in its first delivery that they did not carry over (decision 11 of [`0166-delegation-primitives`](../0166-delegation-primitives/decisions.md#decisions)).

## Security properties

- SD-P1. The new session takes the source's owner, as [§10.2](../../spec/10_gateway-internals.md#102-authentication) **Session ownership.** states, and its credentials, meaning the credential bindings it receives and its effective LLM upstream list, which the post-chain point fixes for every session under [`0133-llm-upstreams-and-cost-budgets`, "LU-2 Assignment and resolution"](../0133-llm-upstreams-and-cost-budgets/change.md#lu-1-the-llm-gateway-as-an-egress-destination), are evaluated afresh rather than inherited. It takes the source's plan and `env`, its `runtimeOptions` unless the request replaces them, and what [`0149-tenant-scoping-identity`, "TS-3: Session environment context and cross-environment sharing"](../0149-tenant-scoping-identity/change.md#ts-3-session-environment-context-and-cross-environment-sharing) states a derive takes: its environment, `egressLockHosts`, `crossed_from_environment`, and its delegation limit.
- SD-P2. Every check runs against the plan on the new session's user and environment, and on the final runtime, its chosen revision, and the final pool that the post-chain point sees.
- SD-P3. A plan carrying content from a tenant-derived runtime is refused after any later content stop on that runtime's grant entry or its tenant's security record, through any chain of derives, whether or not the content is still on the runtime.
- SD-P4 is withdrawn. It refused a derive onto a target with no runtime supervisor, because on such a pod a file the source's agent kept, such as a `requirements.txt`, would reach an operator's setup command, such as `pip install -r requirements.txt`, at the adapter's UID with the pod's service account token. Every runtime's pods now run the supervisor in every slot container, and setup commands and the materialization helper run as the slot UID through it ([SI D6](../0145-session-isolation/decisions.md#decisions), [WM-1](../0153-workspace-materialization/change.md#wm-1-what-moves-and-what-stays)), so a kept file reaches only the identity the session's own agent already holds. The case SD-P4 still covered, a runtime row left stale when [DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records)'s mirror refuses a `Runtime` resource, is the post-chain check of DR-4 that the final runtime row is `registered`, which applies to every create, derive, and delegated child (decision O8 of [`0119-agent-runtimes-only`](../0119-agent-runtimes-only/decisions.md#decisions), settled by the owner on 2026-11-13, and decision 8 below).

## Detailed design

### SD-1: One route

#### Request

```json
{
  "from": "latest",
  "runtimeRef": "<runtime-name (optional)>",
  "targetPool": "<pool-name (optional)>",
  "targetIsolationProfile": "<profile (optional)>",
  "allowStale": false,
  "additionalSetupCommands": [{ "cmd": "git -C src checkout -b ab/run-17" }],
  "runtimeOptions": { "model": "<model (optional)>" },
  "delegationLease": { "maxDepth": "<integer, at most the carried value (optional)>" },
  "labels": { "project": "checkout" },
  "budget": { "limits": { "models": { "meters": ["externalCost"], "amount": 40.00 } } },
  "budgetRefs": ["principal/ci-weekly"],
  "allowIsolationDowngrade": false,
  "ticketId": "<ticket (with allowIsolationDowngrade)>"
}
```

`allowStale: true` admits a live source, and the derive then uses the source's most recent successful checkpoint, which can lag the live workspace by up to the checkpoint interval. `ticketId` is an optional free-text justification that the gateway copies into the `derive.isolation_downgrade` audit event. `allowIsolationDowngrade` needs the `platform-admin` role, and no component checks the ticket. A request that names `deferConnectors`, which left with connectors, is refused with `400 VALIDATION_ERROR` naming the field, under D7 of [`0124-connector-removal`](../0124-connector-removal/decisions.md#owner-decisions).

`runtimeOptions` sets the derived session's options. When the request omits the field, the derived session copies the source session's stored options. When the request carries an object, it replaces the source's options. When the request carries `null`, the derived session has no options, and the gateway validates that absence as it validates any absence, as an empty object, so a schema's `required` refuses it. The size cap and the JSON parse run at request validation, and the schema validation runs at the post-chain point against the chosen revision, as **Options.** under "Checks" states. A client whose suspended session cannot resume because the new revision's schema refuses its stored options recovers through a derive `from: latest` that replaces them ([`0140-runtime-revisions`, "RV-6 Sessions over time"](../0140-runtime-revisions/change.md#rv-6-sessions-over-time)).

`labels`, `budget`, and `budgetRefs` are the derived session's own, as on any root's creation (decision 14). The label rules of [`0149-tenant-scoping-identity`, "Label rules (TS-10)"](../0149-tenant-scoping-identity/change.md#label-rules-ts-10) check `labels` against the deriving owner and the derived session's environment, and refuse a governed value the owner may not set or a missing required key with `403 LABEL_NOT_PERMITTED`. `budget` and `budgetRefs` resolve under [`0170-budgets`, "BG-2" and "BG-3"](../0170-budgets/change.md#bg-2-session-budgets) with the session budget defaults and ceilings of the derived session's runtime, environment, tenant, and platform. Nothing of the source's labels, session budget, or budget set is copied, so a client that wants the derived session under the source's budgets names them again, and a budget that selects on a governed label binds the derived session only when its owner may set that label.

`delegationLease.maxDepth` can only lower the delegation depth the derived session carries. A derived session is a new root at depth 0, and it stores the source's `maxDepth` minus the source's depth, with a floor of 0, under TS-3 of [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md#ts-3-session-environment-context-and-cross-environment-sharing). A request that sets `0` derives a session that cannot delegate, which answers `DELEGATION_DISABLED` with `disabledBy: session`. The owner settled the field under decision O5 of [`0126-delegation-availability`](../0126-delegation-availability/decisions.md), and that change's "Derive (O5)" under DA-2 owns its rules.

`from` defaults to `latest`. `runtimeRef` defaults to the source's runtime. The isolation monotonicity rule stays as §15.1 states it, applied to the final pool after the `PreRoute` chain. When the chain left the runtime and pool as the request and **Pool and profile.** set them, a final pool weaker than the source's refuses with §15.1's `422 ISOLATION_MONOTONICITY_VIOLATED` unless the request sets `allowIsolationDowngrade`. When the chain changed the runtime or pool, the isolation check refuses with `422 ROUTE_ISOLATION_UNAVAILABLE` and names the last modifier in `details.interceptor_ref`, as the post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point) states for every creation kind. A derive compares no execution modes, because no runtime carries one, and `INCOMPATIBLE_RUNTIME` leaves the error catalog (decision O2 of [`0119-agent-runtimes-only`](../0119-agent-runtimes-only/decisions.md#decisions), settled by the owner on 2026-11-13). "Routing and revision" under "Checks" states how the chain and revision selection treat a derive. A `from: start` of a source in any state needs `session.Validate`'s rule for the derive endpoint changed, because it refuses `created`, `finalizing`, and `ready` today, ahead of knowing the mode. The replay route, its `replayMode` field, and the `prompt_history` mode are removed. The platform has no deployments, so nothing needs a compatibility path.

#### What each mode starts from

At create, the gateway copies the source's stored plan to the new row, with `env`, and with `runtimeOptions` as "Request" states, so the plan binds at create and composition never runs. Every bind stores a plan, the canonical empty plan where nothing was composed, so an absent plan means the session never bound, in any state. That is new on the paths that store nothing today: `composeRuntimeDefaults` on a create-and-start (`POST /v1/sessions/start`, which creates and starts a session in one call), and `composeChildWorkspaceDefaults` for a delegated child whose runtime has no defaults, which leaves the child's plan unchanged. Composition is skipped outright when the row's `derivedFrom` field is set.

A source whose effective `checkpointPolicy` is `none` has none ([IC-8](../0131-incremental-checkpoint/change.md#ic-8-checkpoint-policy-interval-and-change-tracker)). A source whose effective `checkpointPolicy` is `sealOnly` has one only after its seal at session end, because it writes no checkpoint while it runs, and an idle one stays on its pod until its idle timeout ends it ([SL-6](../0146-session-lifecycle/change.md#sl-6-idle-pods-and-dormancy)), so a derive `from: latest` of it while it is live is refused with `no_snapshot`. | A bound plan, in any state |
| **Uploads** | Dropped from the plan copy, because the snapshot holds their files, and `bindprepare.go` would otherwise fetch each one and fail once it has expired | Copied to the new session, with `uploadRef` rewritten, each a write declared by its size to the limits on the storage meters in the new session's budget set under 0170 "BG-6". An unreadable upload refuses. How long a copy lives is open decision 12. |
| **A resume before the first checkpoint** | Repeats the first bind, because `snapshotIsOwn` is still false | Takes the rebuild path, which reads the plan |

In both modes the plan stays on the row, because the new session's read checks, its readable set of repositories, the read tokens of the provisional binding, the base-commit fetch of `restore-complete`, and a later derive all read it. Setup commands run at finalize in both modes, as the slot UID through the slot's supervisor, followed by `additionalSetupCommands`. [WM-13](../0153-workspace-materialization/change.md#wm-13-resume-and-derive) lists the helper run of each path. A new pod lacks anything installed outside the workspace, so `from: latest` runs them too, over the restored tree. That can change the exact state, because `npm ci` resets `node_modules`, and a command that is unsafe to repeat can fail.

The source's agent can have deleted or replaced the plan's working directory. On a `from: latest` derive, a working directory that fails the start check of [DR-12](../0147-tenant-derived-runtimes/change.md#dr-12-repository-folders-and-the-working-directory) starts the runtime in `/workspace` and records the session event `workspace.working_directory_fallback`, with the folder the plan named and the reason the check failed, and the derive proceeds. A `from: start` derive materializes the plan's folders, so a working directory that fails the check there fails the start with `SESSION_CREATION_FAILED` and the reason `working_directory_invalid`, as for any create. 0147.S13 lands the check, the fallback, and the event, and tests them.

A client cannot add sources. A `finalize` whose body carries a plan answers `400 VALIDATION_ERROR` with `details.reason = "plan_already_set"`, as it does for any row with a bound plan. Derive requires `uploadTokenDigest`, as create does, and its response carries no `uploadToken` (decision 6 of change [0182](../0182-client-chosen-upload-secret/decisions.md)); `handleFinalize` verifies the client's upload secret first, and §14.1 leaves an upload no plan names unmaterialized, so the upload routes need no change. `claimDerivedRow` passes `Plan{}` today, which `slotBindRequest` consumes, so it passes the row's plan instead. Today `handleDerive` takes the row's lineage, `ParentWorkspaceRef`, and part of its response from the copied snapshot, `WorkspaceSnapshot`. A `from: start` derive copies no snapshot, so `handleDerive` records the lineage as `derivedFromSessionId` instead, and it does so in both modes.

A derived session inherits no inbox entry of its source, so a message held for the source stays with the source. It copies no output file of its source either: a `from: latest` derive references the source snapshot's packs alone, its platform packs included, and the derived session's allowed set under [IC-4](../0131-incremental-checkpoint/change.md#reference-closure) leaves out the packs that only the source's output files reference, so the derived session can neither reference nor download them.

A derive copies no call to a client's tool. Under the blocking interface that decisions 23 and 24 of [`0166-delegation-primitives`](../0166-delegation-primitives/decisions.md#decisions) assign to [`0122-client-tools`](../0122-client-tools/change.md), a call stays open inside the turn that made it, for at most `clientToolHoldSeconds`, and a session that waits between turns holds no pending set. A derive starts a new session, so no call of the source is open in it, and a result that the source's client later sends answers the source alone. The copy of a pending set on a `from: latest` derive, the `422 CLIENT_TOOLS_UNSUPPORTED` refusal of a revision that could not take the copied calls, and `abandonPendingToolCalls` on the derived session's first request retire with it (0166 "DP-7"). A derived session reads its client's tool definitions from each message, as any session does under 0122.

A derive copies no child of its source. The derived session is a new root, so it starts with no children and no child event, and the source's children stay with the source. When the source has a non-terminal child at the derive, the gateway writes a system message to the derived session's inbox, which its first delivery carries: `from.kind: system`, stating that the source session had children and that they did not carry over to this session, with no text a child wrote. It takes the `append` intent of [MD-1](../0135-message-delivery/change.md#md-1-delivery-intents) of `0135-message-delivery`, so it opens no turn of its own and reaches the runtime with the first message the client sends, ahead of it. A runtime whose restored state under `from: latest` names children it started reads from the message that those children are not its own, and starts new ones if it needs them (decision 11 of 0166). The message is written under both modes.

The plan copy keeps the client's `writeDefaultClones` and drops the source's gateway-written `readOnlyDefaultClones`, which described the source's bind. The derive's bind computes `readOnlyDefaultClones` again for the new session under "Writes", so the stored plan, the derive response, and `GET /v1/sessions/{id}` list the same entries ([DR-9](../0147-tenant-derived-runtimes/change.md#write-scope)).

A chain needs little handling. Each derive copies its source's plan, apart from additional commands, so a session with no checkpoint of its own, whose `snapshotIsOwn` is false, passes on what its parent had. A `from: start` of a session that itself came from `from: latest` is refused, because that session's start was a snapshot its own checkpoints have since replaced.

#### Additional setup commands

`additionalSetupCommands` appends client commands to the new row's plan, after the source's. They have the origin `derive`, they count toward `maxCommands`, and they pass the target's `setupCommandPolicy`, and the `shell` setting of the target's `setupCommandPolicy` applies to them as to every command of the run. The plan copy of a later derive omits them, so a chain does not accumulate commands, a `from: latest` of the run does not repeat `checkout -b` on a tree that already has the branch, and a `from: start` of the run starts where the first session started. A resume or a rebuild of the same session reads them as any plan command. The usual use is to give a run its own branch before the client sends anything. They reach nothing a client's plan could not state.

A command can set `cwd`, under the checks of [DR-12](../0147-tenant-derived-runtimes/change.md#dr-12-repository-folders-and-the-working-directory). A command that sets none runs in the plan's working directory, as a client's command does, and the gateway writes that folder on the command as its `cwd` when it appends the command to the plan.

A command sets where the session starts, and it bounds nothing. An agent told to push `fix-login` can still push that branch from `ab/run-17`, within what the session's writable entries allow. A hard limit is `allowedRefPatterns` on the entry, and decision 3 under "Decisions" in `decisions.md` records that option. Every entry a restore or the helper creates is owned by the slot UID, the UID the runtime and the setup commands run as ([WM-13](../0153-workspace-materialization/change.md#wm-13-resume-and-derive)), so git in the session does not refuse a repository as owned by another user.

#### Writes

Writes stay on. The plan's `writableRepositories` and write scopes, which are `gitClone` sources whose `auth.leaseScope` is `vcs.<provider>.write`, copy to the new row, and each is read again at bind against the VCS pool's repository allowlist, the VCS pool's `allowWrite`, and, on a VCS pool with `userAuthorization: required`, the check of the user's own access. An entry that no longer passes reads as read-only rather than refusing the derive, because the derive request named no repository. An entry that a default clone added also follows the read-only rule under [`0147-tenant-derived-runtimes`, "Write scope"](../0147-tenant-derived-runtimes/change.md#write-scope), which covers a target that reuses pods and a VCS pool that has since set `prAuthoring: user`. Whether that re-check also applies the grant flag `allowGitCloneWrites` and the forbids `writableDefaultClones` and `alwaysWritableClones` as they stand at the derive, or whether those stops raise the counters of "Stops", is open decision 9.

The derive response lists each entry that reads as read-only, in one of two fields. An entry that a default clone added goes in `readOnlyDefaultClones`, with the clone's `path` and a reason and without the repository's name, as "Write scope" states for a new session, because the client never named that repository. Every other entry goes in `readOnlyRepositories`.

A client that re-sends a session's messages can therefore repeat its pushes and pull requests on the repository itself. That is the owner's stated choice, and `additionalSetupCommands` is how a run avoids a shared branch. Tool calls to other systems repeat in the same way.

#### Reading client messages

`GET /v1/sessions/{id}/messages?from=client` returns the session's client messages in order, under the route's existing access rule. A filter on the existing route avoids a new one.

- `transcriptstore.Entry` gains a sender, with an explicit `client` value, so a message another session's agent sends, which under [MD-9](../0135-message-delivery/change.md#md-9-inter-session-messages-system-messages-and-delegation) is a parent's or a child's message with `from.kind: agent`, is not returned, a writer that omits it is not read as the client, and `deriveMessageFrom` reads it. The `session_messages` sender and delivery-state columns and their migration are added by 0135.S1 under [MD-3](../0135-message-delivery/change.md#md-3-inbox-states-and-custody) **Records**. This design writes `client` on the REST send path and reads the columns.
- The inbound rows are appended before the message is passed to `Deliver`, which replaces the executor's `Send` under [MD-6](../0135-message-delivery/change.md#md-6-executor-lock-and-waiting), with a delivery state, so a failed turn's message is on the record, and `toMessageNode`, which reports every row as `delivered` today, reads that state. Today `recordDeliveredResponse` appends them after `Send`. `deliverHeldEntry` appends a held message once across its retries.
- The REST send path, `POST /v1/sessions/{id}/messages` and the first message of `POST /v1/sessions/start`, is the only client send path. Under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), the Model Context Protocol (MCP) send paths leave Lenny with the MCP API, and the MCP adapter and every other protocol adapter send on the REST path, so a session driven through an adapter has messages to read. Revision 19 required the MCP send paths to append client rows as well.
- The delivery state a row records takes the states of [MD-3](../0135-message-delivery/change.md#md-3-inbox-states-and-custody), and the row also records the message's intent.
- The read skips activity rows, which carry the role `activity` and no client message, as MDR-16 of that design requires.

The read returns each message's text and the `toolResults` it carried, so a client that re-runs a session can see what it answered ([`0122-client-tools`, "CT-7"](../0122-client-tools/change.md#ct-7-continuation), **Re-running a session**). Today `projectMessage` sends text alone, and 0122.S1 adds the results. The transcript's retention, [§12.8](../../spec/12_storage-architecture.md#128-compliance-interfaces) erasure, the Confidential class of [§12.9](../../spec/12_storage-architecture.md#129-data-classification), which transcripts carry on every tenant ([TSS-8](../0150-tenant-security-settings/change.md#tss-8-data-classes)), and legal holds apply with no new rule, and the read returns nothing once the retention sweep has removed the rows. `POST /v1/sessions/{id}/extend-retention` lengthens that window. A client SDK or CLI helper can re-send them in a loop, and the design requires none.

This closes F-15.1.77 by removing §15.1's statement. A client that re-sends messages is an ordinary client, so delivery, duplicates, and interrupts behave as they do for any session.

#### What it refuses

The gateway answers `422 DERIVE_SOURCE_UNAVAILABLE` with `details.reason`, before any claim, apart from `no_snapshot`, which keeps today's `400 VALIDATION_ERROR` under §7.1. The reasons that read the target runtime or pool are decided at the post-chain point, and when the `PreRoute` chain changed the runtime or pool, the refusal names the last modifier in `details.interceptor_ref`:

| Reason | Cause |
| :-- | :-- |
| `no_snapshot` | `from: latest`, and the source has no resolvable snapshot. |
| `checkpointing_disabled` | `from: latest`, and the source's effective `checkpointPolicy` is `none`, so it never had a snapshot. [IC-8](../0131-incremental-checkpoint/change.md#ic-8-checkpoint-policy-interval-and-change-tracker) adds this reason, and a `from: start` of the same source still rebuilds from the plan. |
| `not_bound` | `from: start`, and the source has no plan, so it never bound, whatever its state. |
| `upload_unavailable` | `from: start`, and the plan names an upload that cannot be read, because its TTL passed or the retention sweep removed it. |
| `start_was_snapshot` | `from: start`, and the source itself came from `from: latest`. |
| `delegated_source` | `from: start`, and the source has a delegation parent, because its exports and inherited inputs came from that parent, and a derive is a new root. |
| `source_runtime_stopped` | "Stops" below applies. |

No reason reads the target's execution mode or its runtime supervisor. A final runtime whose row is not `registered` is refused at the post-chain point as an unknown runtime, with `404 RESOURCE_NOT_FOUND`, by the check of [DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records) that every creation kind meets ("Final runtime row").

A commit the host no longer serves is not known before the fetch, because a pinned commit skips `ls-refs`, git's request that lists a repository's refs. It fails at materialization with `SESSION_CREATION_FAILED`, after the claim, under `from: start`, and under `from: latest` when `restore-complete` needs to fetch it.

#### Checks

The plan passed its checks when the source bound it, and those checks can have changed. At the post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point), after the `PreRoute` chain and revision selection and before the claim, the gateway runs the checks a client's plan gets, on the final runtime and pool and the chosen revision. No single function does that today: `resolveSubmittedPlan` takes raw JSON, `Parse` refuses `resolvedCommitSha`, `validatePlanUploadRefs` needs a session, and `enforceSetupCommandPolicy` and the default-clone run of [DR-9](../0147-tenant-derived-runtimes/change.md#dr-9-default-git-clones) are separate steps. SD-1 extracts one function over a parsed plan, which every bind path calls. It covers the auth bindings, under which each `gitClone` source with an `auth` block maps its host to exactly one of the tenant's VCS pools whose provider matches its `leaseScope`, the named credential bindings, `egress.allowedHosts`, and `gitClone` sources under the environment, the rule for pods with no per-session policy, the repository check of [UG-2](../0152-user-git-identity/change.md) on the user's link on a VCS pool with `userAuthorization: required`, and `verbatimClientFiles`.

**Admission.** A derive passes the admission steps a create passes, judged against the derive's target runtime and pool, apart from the steps the list below leaves out. Each step that reads the runtime, its revision, or the pool runs at the post-chain point on what the chain and revision selection chose. On a session row, `Pool` is the pool name the client gave at create, and `PoolRef` is the pool the gateway resolved and scheduled the session on.

- **Pool and profile.** `handleDerive` passes `targetPool` as the create's `pool`, or the source's client-named `Pool` when the derive stays on the source's runtime and profile, and otherwise none, so the gates and the claim resolve a pool as a create does. It passes the derive's resolved target as the create's `isolationProfile`, so a weaker `targetPool` cannot pass the downgrade check, and a refusal's `details.field` names the derive's field. The `source.PoolRef` fallback goes, because the row defaults to it while `claimAtCreate` resolves `Pool`, so checks could judge a pool the claim does not use, and it names no pool of another runtime.
- **Gates.** It calls `createAdmissionGates` with the target, which gains `requireTenantClassification`, and it drops its own two early policy calls, which would otherwise run `PostAuth` twice.
- **Row build.** SD-1 extracts the row assembly, `validateRequestEnvelope`, `applyPlaygroundCaps`, `requirePoolNotDraining`, and the `PreRoute` and `PostRoute` chains from `validateAndBuildCreateRow` into one function that a create and a derive both call. It leaves out `composeRuntimeDefaults` and `enforceSetupCommandPolicy`, which sit in that same region today, because a derive runs neither and the second would check exempt commands. A deployer's interceptor that rejects a runtime therefore also rejects a `runtimeRef` naming it, and a playground caller's derive meets §27.6's caps, which `applyPlaygroundCaps` reads from the caller's principal. The drain gate runs once, on the final pool, at the post-chain point.
- **Rate limit.** The tenant view resolves the name first, ahead of `requireAdmissionRateLimit`'s `ResolvePool`, so a name from another tenant creates no rate-limit entry.

This closes F-15.1.78.

**Routing and revision.** A derive runs the single `PreRoute` chain of [RT-2](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract) with `kind: derive`, as decision [D11](../0141-runtime-routing/decisions.md#decisions) of the routing design settles, and the route interceptor treats it as any creation. The payload starts as follows:

- `requested_runtime` is `runtimeRef`, or the source session's resolved runtime when the request omits it. A derive that omits `runtimeRef` therefore asks for the runtime its source ran, and a route keyed on the runtime the source first asked for does not move it. A route keyed on the source's resolved runtime moves it, as it moves any creation that asks for that runtime.
- `requested_pool` is the pool that **Pool and profile.** above passes.
- `routing` is the source session's routing labels ([RT-3](../0141-runtime-routing/change.md#rt-3-routing-labels)), and the chain may change any key.
- `environment` is the source's environment, which the derive copies under SD-P1.
- `labels` is the derive request's `labels`, checked by the label rules before the chain as at a root's creation, and `budget_refs` and `session_budget` are the request's `budgetRefs` and `budget`, which the chain may add to and lower under [RT-2](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract) (decision 14).
- `input` is empty.

An interceptor's `MODIFY` may change the runtime, the pool, and the routing labels, so a runtime route can place a derive on another target. Revision selection ([RV-2](../0140-runtime-revisions/change.md#rv-2-selection)) then picks a revision of the final runtime by its traffic and the derive's rollout key, as for a create, and a derive does not inherit its source's revision ([RV-6](../0140-runtime-revisions/change.md#rv-6-sessions-over-time)). The gateway then runs every target check of this section, the content stop check of "Stops", and the `registered` check of "Final runtime row" at the post-chain point, on the final runtime and pool and the chosen revision. A check that reads a versioned field, such as the `workspaceDefaults` that the relabel under **Setup commands.** compares, reads the chosen revision. A failed check refuses the derive with its own code and names the last modifier when the chain changed the runtime or pool. The gateway never falls back to the requested runtime.

**Account links.** The account link check of [UC-2](../0151-user-credential-delivery/change.md#flow) runs at the post-chain point, on the derived session's user and on the final runtime and pool, as for every creation path. Each missing link joins the combined missing-links response, `403 LINKS_REQUIRED`, under `details.userLinks`, as the post-chain table of [RT-2](../0141-runtime-routing/change.md#post-chain-point) states. The response carries no `details.connectors`, and no runtime capability exempts a derive from the check ([CR-1](../0124-connector-removal/change.md#cr-1-removal)).

**Placement.** The placement checks run at the post-chain point on the derive's final pool and the chosen revision's pod set, as the placement design's row of the post-chain table states ([`0141-runtime-routing`, "Post-chain point"](../0141-runtime-routing/change.md#post-chain-point)). The offering grant of [PM-3](../0136-placement/change.md#pm-3-placement-offerings-and-per-pool-nodeplacement) refuses a pool whose offering is neither a default nor granted to the tenant with `403 PLACEMENT_OFFERING_NOT_GRANTED`. A derived session is a new root, so its effective placement requirements are its own tenant's, its environment's, which is the environment it copies from its source under SD-P1, and the operator's placement settings for the tenant ([`0150-tenant-security-settings`, "TSS-6"](../0150-tenant-security-settings/change.md#tss-6-placement-settings)), and a pool that fails one refuses with `422 PLACEMENT_REQUIREMENT_UNMET` ([PM-4](../0136-placement/change.md#pm-4-placement-requirements)). The residency check of [PM-7](../0136-placement/change.md#pm-7-region-placement) refuses a pool whose region differs from the session's `dataResidencyRegion` with `403 REGION_CONSTRAINT_VIOLATED`. Each refusal names the last modifier when the chain changed the pool, and none falls back to another pool.

**Options.** The derived session's options, the request's or the source's, are validated at the post-chain point against the chosen revision's `runtimeOptionsSchema`, and on a derived runtime with its own schema against that schema as well, as separate validations under [RV-7](../0140-runtime-revisions/change.md#rv-7-session-options). A derive onto the source's runtime validates the copied options against its chosen revision, which can differ from the source's. A refusal answers `400 RUNTIME_OPTIONS_INVALID` with `details.runtimeRevision`, and names the runtime and the last modifier when the chain moved the derive. No interceptor can change the options, because the `PreRoute` payload carries them as immutable ([RT-2](../0141-runtime-routing/change.md#preroute-payload)).

**Order.** Every gate, the `PreRoute` chain, revision selection, the plan checks, the placement checks, the `registered` check of "Final runtime row", and the content stop check of "Stops" run ahead of `reserveDerivedSession` and any copy, so a refusal there has nothing to undo. The `derive.isolation_downgrade` audit follows them, so those refusals record no downgrade. `cataloging.Copy` charges nothing today, and `DeleteBySession` releases live rows' bytes, so undoing a copy would lower the tenant's storage counter. A `from: latest` derive copies no object: it writes a snapshot row that references the source snapshot's manifest and packs, its platform packs included, under [IC-5](../0131-incremental-checkpoint/change.md#ic-5-restore-derive-download-and-seal), and the tenant was already charged for each of its own packs when its checkpoint confirmed it ([`0131-incremental-checkpoint`, "Quota"](../0131-incremental-checkpoint/change.md#quota)), so a `from: latest` derive reserves nothing. A `from: start` derive copies the plan's uploads, so one check of the upload objects' total size against the new session's storage limits covers them, ahead of the first copy, as 0170 "BG-6" checks a declared write. A refusal there answers `429 BUDGET_EXHAUSTED` with nothing copied. Later failures in the reference row, the upload copies, the claim, the refusal at the insert of an upload digest that another live session of the user records (`digest_in_use`, US-2 of change 0182), or the fence go through `undoDerivedWrites`, which deletes the reference row of a `from: latest` derive and releases what a `from: start` derive reserved for its uploads. The fence is the coordinator-handoff check of [§10.1](../../spec/10_gateway-internals.md#101-horizontal-scaling) on the insert, which skips the write when the source's `coordination_generation` has advanced since admission, as it does after a coordinator handoff. `undoDerivedWrites` releases what the `Reserve` took and what `DeleteBySession` did not. `DeleteBySession` returns an object count today, so it gains the bytes it freed. `undoDerivedWrites` runs only on a failure inside the process, and what restores the storage counter when a replica ends between the `Reserve` and the insert is open decision 13.

**Setup commands.** §7.5 exempts operator-written defaults from `setupCommandPolicy`, and the stored plan does not say which commands those are. Each stored command therefore gains an `origin`: `operator`, `tenant`, `client`, or `derive`. `runtimestore.ComposeWorkspaceDefaults`, which the create path calls through `composeRuntimeDefaults` and the delegation path calls through `composeChildWorkspaceDefaults` (`pkg/gateway/platformtools/delegation`), writes `operator` on an operator-written default and `tenant` on a tenant-written one. The plan parse writes `client` on each command a client's plan states and refuses a client-supplied `origin`, and the derive handler writes `derive` on each `additionalSetupCommands` entry. On a derive that stays on the source's runtime and whose chosen revision equals the source's recorded `runtimeRevision`, an `operator` command stays exempt. On a derive onto another runtime, or onto the source's runtime at a different revision, in either mode, it keeps that origin only when its text is among the operator-written defaults of the target's chosen revision, and otherwise the plan copy relabels it `client`, so the target's effective policy checks it. Under either mode the tree can hold content a client or an agent chose, a plan file under `from: start` or an edited script under `from: latest`, so `npm ci` from another runtime's defaults would otherwise run client-chosen code past a policy the target's operator set. The relabel stays on the copy, so a later derive on that runtime cannot regain the exemption. The relabel changes which policy checks a command, and it leaves the command's folder unchanged. When a session's plan is composed, the gateway resolves each command's folder under [DR-12](../0147-tenant-derived-runtimes/change.md#dr-12-repository-folders-and-the-working-directory) and writes it on the stored command as an explicit `cwd`, a derive copies each command with its `cwd`, and `origin` decides no folder. For example, the platform runtime `web-dev`, which tenant `acme` uses, names `workingDirectory: app`, so its operator's default `npm ci` is stored with `cwd: app` and runs in `/workspace/app`. When bob derives a session of `web-dev` onto `web-test`, whose operator-written defaults lack `npm ci`, the copy relabels the command `client`, `web-test`'s policy checks it, and it still runs in `/workspace/app`. A `tenant` command is also refused on a target whose `setupCommandPolicy` is not mode `allowlist` with `shell: false`, as [DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records) requires, because an inert string would otherwise run under a shell. Under `shell: false` a command runs through `exec` as an argument list, so pipes, substitutions, and redirects in it are inert text ([§7.5](../../spec/07_session-lifecycle.md#75-setup-commands)), and DR-4 admits tenant-written commands only on such a base. The source's original commands are the only ones that run, plus any the request adds, and the check decides whether the target admits them.

**Warm stores on the target.** A target's pods can hold warm stores for repositories the plan does not name, from a tenant-derived runtime's `gitRepository` asset whose repository the stored plan omits, under [`0147-tenant-derived-runtimes`, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores), and the agent can read them. Ahead of `reserveDerivedSession` and any copy, the gateway runs the read checks on each tenant entry of the target pool's warm list for the chosen revision that the plan does not name, because the warm list is kept per pool and revision ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)), as that design's ["Binding"](../0147-tenant-derived-runtimes/change.md#binding) states for a derive. `coveredStores` includes each entry whose checks pass. The new session's plan does not name such an entry's repository, so a failed check withholds its store through `withheldStores` and the derive proceeds, and `GET /v1/sessions/{id}` lists the entry in `withheldWarmEntries` without its URL, as **Withheld stores.** in that section states.

#### Stops

A stored plan can hold content a tenant has since stopped, and a grant flag set false or a forbid is "the stop after a compromise". A derive is a new session, so it is refused. Reading the source's runtime alone would not hold, because a derive onto a platform runtime before a forbid leaves a row whose runtime is that platform runtime. A plan therefore carries `planOriginRuntimes`, the tenant-derived runtimes whose defaults it holds. A derive copies its source's set at create, and it adds nothing, because it composes nothing. A session that composes adds its runtime at bind, in the update that binds the plan, and a delegated child copies its parent's at bind, because a child's exports came from that parent.

A runtime's current state would not hold either. If a `security-admin` sets a forbid or an operator sets a grant entry's `allowGitClones` to false after the tenant has removed the clone, the runtime looks clean, and a derive of a session from before the incident would rerun the pinned commit. Two counters therefore record stops, in a tenant-keyed `content_stop_epochs` table, outside the grant's and the security record's bodies, because a `PUT` replaces each of those documents and [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture) stores the record as versions, so a pending weakening written before a forbid would otherwise regress a counter kept inside it. An absent row reads as 0. Each is incremented in the stop's own transaction: the grant entry's, keyed by base, when `allowWorkspaceFiles`, `allowSetupCommands`, or `allowGitClones` is set false, and the security record's, in the transaction that activates a version adding `all`, `setupCommands`, `workspaceFiles`, `gitClones`, or `floatingCloneRefs`, which forbids default clones at a branch or tag rather than a full commit, to `derivedRuntimes.forbid`, or setting `verbatimClientFiles: forbid`. Each `planOriginRuntimes` entry stores both values, from the same read of the tenant view that composition used.

Each write lands with the step that adds the mechanism it rides on. 0144.S1 adds the `content_stop_epochs` table, `planOriginRuntimes`, its copy on a derive and on a delegated child, and the content stop check. [DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records) (0147.S4) adds the grant flags, the tenant view, and tenant defaults, so it raises the grant counter in the transaction that sets a flag false and appends a tenant-derived runtime to `planOriginRuntimes` when a plan composes its defaults. [DR-6](../0147-tenant-derived-runtimes/change.md#dr-6-base-changes) (0147.S10) adds the retirement that the check reads. The forbid values come from [DR-7](../0147-tenant-derived-runtimes/change.md#dr-7-security-oversight-and-records) (0147.S11) and the versioned record from [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture) (0142.S2), and whichever of those two steps lands second raises the security counter in the transaction that activates a version adding a content forbid. Before each of those steps lands, the mechanism it adds does not exist, so the check has no stop to miss.

The grant flag `allowAssets` raises no counter. A tenant-derived runtime's `inline` and `artifact` assets render under `/lenny/assets` on that runtime's own pool, and neither the stored plan nor the snapshot holds them, so a derive carries none. Its `gitRepository` assets are warm stores, which **Warm stores on the target.** covers.

The content stop check is one function, which `handleDerive` calls at create and finalize calls again, because a row created before a stop can finalize after it. For each entry, the tenant view must resolve that runtime now, it must not be retired, and both stored values must equal the current ones. A deleted runtime refuses, and names stay consumed, so one cannot be recreated to pass. A runtime that is `incompatible` for another reason, such as a `Registered=False` condition, does not refuse. A plan from before a stop stays refused after the stop is lifted, because a counter only rises. The owner can still read such a workspace through `GET /v1/sessions/{id}/workspace`.

A platform-owned source runtime has no such rule, because starting the session of a platform runtime that [DR-6](../0147-tenant-derived-runtimes/change.md#dr-6-base-changes) has retired on a successor runtime is a regression test.

#### Final runtime row

A derive meets no supervisor check and no execution-mode check. Every runtime is an agent runtime, and every runtime's pods follow the blueprint of [PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint), whose slot containers each run the runtime supervisor, so setup commands and the materialization helper run as the slot UID through it on every target ([SI D6](../0145-session-isolation/decisions.md#decisions)). A file the source's agent left in the tree therefore reaches only the identity the session's own agent already holds, on the source's runtime and on any other. Setup at the slot UID also closes the exposure that F-7.5.17 records for setup at the adapter's UID. Decision O8 of [`0119-agent-runtimes-only`](../0119-agent-runtimes-only/decisions.md#decisions), settled by the owner on 2026-11-13, withdrew SD-P4 and its refusal reason `target_unsupervised` on that ground.

One concern of SD-P4 stays, as a check that every creation kind meets. [DR-4](../0147-tenant-derived-runtimes/change.md#dr-4-tenant-runtime-records)'s mirror, which copies the `Runtime` resource's fields into the runtime row, leaves the row stale when it refuses a resource, so a target whose row is not `registered` could run on fields its resource no longer holds. At the post-chain point, after the `PreRoute` chain and revision selection, the gateway requires the final runtime's row to be `registered`, for every create, derive, and delegated child, and for a platform-derived runtime also the base's row, and refuses one that is not as an unknown runtime: `404 RESOURCE_NOT_FOUND` on a create or a derive, and `TARGET_NOT_IN_SCOPE` for a delegated child. DR-4 owns the check under **Registered rows**, and the post-chain table of [`0141-runtime-routing`, "Post-chain point"](../0141-runtime-routing/change.md#post-chain-point) lists it. A derive meets it on the final runtime, whether `runtimeRef` named that runtime or a route or an interceptor moved the derive there, and the refusal names the last modifier when the chain changed the runtime.

A derive that stays on the source's runtime and lands on a different revision gets no special treatment from this check. It is still treated as a runtime change for the `operator` setup command exemption under **Setup commands.**, as decision 1 records.

## What an exact start does not cover

`from: start` matches what the plan states, and `from: latest` matches what the snapshot holds. These differ, and the documentation says so:

- **The image.** A target runtime's image is the variable under test. On the source's own runtime, the derive's revision comes from the runtime's traffic and can differ from the source's revision.
- **What setup commands fetch.** `npm install` resolves against the registry on the day it runs.
- **External answers.** Tool calls and model responses are not recorded inputs.
- **Egress and credentials.** These are the tenant's and the pool's settings on the day of the derive.
- **A target that expects its own defaults.** Nothing composes, so a target relying on a default clone or a setup command it added runs without it.
- **`from: latest`'s moment.** A snapshot records its own moment, and on a live source that is the last checkpoint. The runtime's private session state under `/session`, such as a harness's transcripts, is checkpointed in the same snapshot as the workspace and is restored with it, as a resume restores it ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). Under `from: start` the derived session's `/session` starts empty.
- **Messages the read lacks.** A lost append, and attachments.

## Costs

- A client that wants a re-run writes the loop, or uses a helper, and it stays attached for the run.
- A client that re-sends messages repeats pushes and external calls on real systems.
- An additional command is not repeated by a later derive, so a package it installed outside the workspace is missing under `from: latest` of that run.
- A derive cannot add files, so a client that needs them uses an additional command. Today's derive can add them at finalize.
- A tenant's later change to a runtime reaches no derived session, including a security fix to a default file on a platform runtime that a tenant did not stop.
- A derive cannot name a revision ([`0140-runtime-revisions`](../0140-runtime-revisions/change.md), D2). A regression test against a new revision of the same runtime runs once the rollout gives the derive's rollout key that revision, and a test against a fixed version names a runtime registered for it.
- A derive that names a runtime a route matches can run on another of the route's targets. A client that needs a specific runtime names one that no route matches.
- A source that used uploads cannot be derived `from: start` once they are gone, 7 days after each upload, or sooner when the tenant's `retention.sessionArtifactHours` setting is shorter ([TSS-5](../0150-tenant-security-settings/change.md#tss-5-deadlines-and-retention)).
- A content stop refuses every earlier plan under that grant entry or tenant, on any runtime and whether or not that runtime held the stopped content, and it stays refused after the stop is lifted.
