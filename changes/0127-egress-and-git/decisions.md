# Decisions: 0127 Egress and git access for agent pods

## Open decisions

The M3 readiness review of 2026-11-19 raised these questions. Each continues the numbering of "Decisions" below and moves there with the owner's answer.

Options:

(raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F1, 0127-p3-F5)

70. **The commit key a slot repository records.** This design keeps 0111's `lenny.storeCommit` beside `lenny.gitStoreUrl` ("Terms from other designs and the platform", Proposal 0111), while WM-10 of [`0153-workspace-materialization`](../0153-workspace-materialization/change.md) records `lenny.gitStoreUrl` and `lenny.baseCommit`, and [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md) uses the same pair. WM-10's `restore-complete` "fetches `lenny.baseCommit` when the pod's store differs", which needs the capturing pod's store commit. The two member changes disagree, so the conflict is raised on both. Options:
    - (a) one key, `lenny.baseCommit`, as WM-10 states, and this design drops `lenny.storeCommit`;
    - (b) both keys: `lenny.baseCommit` for the commit the session checked out, and `lenny.storeCommit` for the store's commit at materialization, which `restore-complete` compares with the pod's store, and WM-10 records and reads both.

    Recommendation: (b), because restore completion has to tell whether the restoring pod's store is the one the repository borrowed from, and the URL alone does not identify a store generation. It blocks 0127.S5, 0153.S4, and 0153.S6. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F1 (skeptic's correction, item 4), 0127-p1 cross-change candidate 1)

71. **Whether 0127.S2 is split.** 0127.S2 carries `netagent`, `lenny-egress`, `lenny-egress-authz` with two APIs, `pkg/binding` with informers in three components, the pod credential API listener, the §7.3 provisional binding, the DNS resolver, the removal of `provider-direct`, and the evidence producers, and steps of 0124, 0128, 0133, 0142, 0143, 0148, 0149, 0151, and 0152 wait on it. `changes/README.md` makes a step one branch that is built, reviewed, and merged. Options:
    - (a) split it along its seams, for example `pkg/binding` with the Kubernetes issuer verifier and the binding feed; `lenny-egress-authz`; `lenny-egress` with its chart rules; `netagent` with slot attribution; the pod credential API listener and the Token Service's mint path; and the `proxied` profile with the DNS resolver and the removal of `provider-direct`, moving each dependent edge of another change to the part it needs;
    - (b) keep one step and build it as several commits on one branch.

    Recommendation: (a). It lets other changes start on the part they need, and each part can be reviewed and gated on its own. The edges of other changes move in their own folders. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F10)

72. **Which destinations a platform-marked CONNECT reaches through `lenny-egress`.** Decision 64 admits a marked CONNECT to the gateway, the deployment's object storage, and the git mirror. The gateway and the mirror are cluster services, and `lenny-egress` refuses cluster ranges by its address filter and its NetworkPolicy with no exemption. Options:
    - (a) a marked CONNECT is admitted only to the deployment's object storage on a public address, the gateway and the mirror are reached directly under the pod's NetworkPolicy, and a marked CONNECT that names either is refused with an `egress.decision` record;
    - (b) `lenny-egress` gains pinned routes and NetworkPolicy rows to the gateway and the mirror.

    Recommendation: (a). Option (b) gives the central proxy a path to in-cluster services that the design otherwise denies it. It blocks 0127.S2. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F4)

73. **Where the removal of the gateway clone path lands.** 0127.S3 removes the gateway clone path and closes F-14.1.37, and the pod-side clone lands in 0153.S4, which depends on 0127.S3, so between the two merges `main` cannot materialize a `gitClone` source. Options:
    - (a) the clone-path removal and the closure of F-14.1.37 become a part of 0127.S3 that lands with 0153.S4, written with `(part)` on both sides;
    - (b) 0127.S3 lands whole first, and `main` has no `gitClone` materialization until 0153.S4 lands.

    Recommendation: (a). 0127.S1 already takes care to land without breaking `gitClone`. It blocks 0127.S3, 0153.S4, and the `closes` entry for F-14.1.37. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F3)

74. **The pool's attribution status across a `netagent` image change, and its carrier.** The controller clears the status whenever the pool's runtime class or the `netagent` image changes, and a cleared status counts as union scope, so every upgrade refuses sessions that name an `onRequest` or `poolAttach` binding, a `userCredential` binding, or an identity assertion until a new pod reports, while existing pods still attribute. `netagent` also has no connection to the controller for its start report. Options for the status:
    - (a) key the status on the pool, the runtime class, and the `netagent` image, and keep the previous result until a pod of the new key reports; a new pod whose `netagent` finds no reader on a pool whose status records attribution fails its readiness, as today, so no session lands on a pod whose scope differs;
    - (b) keep the rule as written, with the refusals during each upgrade.

    Options for the carrier: (i) a pod condition that the controller reads; (ii) a report on `netagent`'s pod binding API subscription, which the decision service records for the controller. Recommendation: (a) with (ii), because the readiness rule already guards a new pod, and `netagent` holds no Kubernetes API credential while it already reports to the decision service. It blocks the attribution status in 0127.S2. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F6)

75. **The stores for state shared across replicas.** The design names no store for: the per-pod and per-tenant rates, which Envoy spreads across the decision service's replicas, so a counter per replica enforces a multiple of the limit and the chart's check against Envoy's limits is wrong by the replica count; the per-tenant concurrency count, which each replica receives in part from the access log stream; the Token Service's mint cache, "shared across its replicas" with "one mint at a time per key"; the mirror's fill record and fill ID; and the history of slot assignments that `pkg/binding` reads to attribute a late record to a session for [`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md). The pending-revocation record is defined by [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) UC-2. Options:
    - (a) Redis for the rate and concurrency counters, the mint cache, and the per-key mint lock, and Postgres through the pooler for the fill record and the slot assignment history, with each component failing closed when its store is unavailable;
    - (b) enforcement per replica with each budget divided by the replica count and no shared store for rates, a mint cache per replica, and Postgres through the pooler for the durable records.

    Recommendation: (a). P7 rests on these quotas, and a cache per replica multiplies mints by the replica count, which the design states it avoids. Each item needs its key or table and its §13.2.4 row in the step that builds it. It blocks 0127.S1 (the mint cache), 0127.S2 (quotas and the slot history), and 0127.S5 (the fill record). (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F7, 0127-p1-F13)

76. **The read credential of the gateway's ref resolver on `mint-coarse` and `stored` providers.** The gateway obtains its read credential on the Token Service's gateway listener with the gateway cause assertion as the cause, and on a `mint-scoped` provider it gets a read token for the one repository ("Credentials", **The gateway runs no git.**). On a `mint-coarse` provider a GitLab project access token is "minted per session and revoked at session end", and no session row exists when the resolver runs on the create path. Options:
    - (a) mint a token for the resolution alone and revoke it at once through the pending-revocation record, and use the stored read token on a `stored` provider;
    - (b) mint the session's token at resolution and hand it to the session at bind, revoking it if the create fails;
    - (c) resolve repositories of `mint-coarse` and `stored` providers without a credential, so a private one fails with `auth_failed`.

    Recommendation: (a), because no session row exists to own the token and the resolution needs read access alone. It blocks the ref resolver in 0127.S3. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F8)

77. **When the specification identifiers are assigned.** Every step has a `specification` lane, and the change names numbered sections only. The "Requirements" section holds the owner's direction as prose with no requirement identifiers, no step names the page codes it writes, the links and channels I1 to I8, the binding push, the access log stream, and the evidence ingest have no canonical `LNK-` or `CH-` identifiers under the naming law, and most of the alerts, metrics, and refusal codes the design describes have no name. Options:
    - (a) assign them in `change.md` before the change moves to `Decided`: identified requirements, a page code on each step, a naming table for the links and channels, and the catalog names of the alerts, metrics, and codes;
    - (b) let each step's specification lane assign them, with the first step that builds a channel choosing its name.

    Recommendation: (a). Other changes cite these channels and requirements, and a name chosen at build time binds every later change to the first builder's choice. It blocks the specification lane of 0127.S2 and every later step. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F12, 0127-p1-F21, 0127-p3-F7)

78. **Whether a binding written during a session reaches that session's running processes.** A tenant admin can add an `always` binding, a VCS pool, or a git route while sessions run, and `netagent` re-renders the git configuration and re-issues the trust anchor when a binding adds a host, while a runtime process that loaded the name-constrained anchor before the write refuses the new host. Options:
    - (a) additions apply to running sessions, the anchor is re-issued, tools that re-read the bundle on each invocation (git and curl) see the new host, and the documentation names the limit for long-lived in-process clients;
    - (b) additions apply only to sessions created after the write, while removals and suspensions apply at once in both options.

    In both options, a second `always` binding with `delivery: inject` on a host that another `always` binding with `delivery: inject` holds is refused at write, apart from the O5 exception, so one tenant-admin write cannot make every later session fail at bind. Recommendation: (b). It keeps the rule that a process serves one binding set and removes the stale-anchor case, and removals still take effect at once. It blocks the binding rules of 0127.S4 and the anchor re-issue of 0127.S3, and it needs `integration` tests for a mid-session `always` binding, a new VCS pool on a running session, and the write-time refusal. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p2-F4)

79. **The serving path of the Token Service's public issuer routes.** The federation, identity, and exchange issuers serve discovery documents and key sets unauthenticated under `/oidc/`, `/identity/`, and `/exchange/` on the gateway ingress, reserved for the Token Service, and providers must reach them. Today the Token Service admits only gateway pods on its mTLS port, and no listener, port, or `lenny-system` ingress row is stated here, in [`0124-connector-removal`](../0124-connector-removal/change.md) "Key publication.", or in [`0143-service-account-credentials`](../0143-service-account-credentials/change.md) SA-3. Options:
    - (a) a dedicated read-only HTTP listener on the Token Service that serves only the discovery documents and key sets, with its own connection budget, a `lenny-system` ingress row from the ingress controller on that port alone, and no route to the mint path or the pod credential API;
    - (b) the gateway serves the documents from key material that the Token Service publishes.

    Recommendation: (a). It keeps signing keys and key-set assembly in one component and adds one narrow NetworkPolicy row. It blocks `federation` in 0127.S4, and the same answer applies to 0124 and 0143, which their agents record. [`0124-connector-removal`](../0124-connector-removal/change.md) CR-2 **Serving the public routes.** now states option (a) for `/identity/`, with documents built when a key or tenant changes and a per-source cap, and asks that `/oidc/` take the same listener, which this decision settles. A `security` test checks that the listener answers nothing but the issuer routes. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p2-F7)

80. **Details the design leaves unstated.** Each is small, and each needs one answer:
    - The provisional binding's store and a coordinator handoff during a resume. Recommendation: a row keyed on session and pod, fenced on the coordination generation, and a new coordinator's resume attempt replaces it under its own generation.
    - The setting that disables the peer-address check where kube-proxy translates pod sources. Recommendation: an explicit Helm value that preflight requires when it detects source translation, never an automatic disable, with the residual stated.
    - A platform registration of a private destination whose address no rendered `ipBlock` row of the `lenny-egress` policy covers. Recommendation: refuse the registration at write.
    - An upstream record's CA on a tenant-owned pool behind a tenant-registered intercepting upstream. Recommendation: the record's CA counts for the hosts routed through that upstream, for `netagent`'s upstream validation.
    - How the ref resolver tells an SSRF refusal on the server-name-check route, which arrives as 200 followed by EOF, from a transient failure. Recommendation: the resolver maps it to `GIT_CLONE_REF_RESOLVE_TRANSIENT`, and the `egress.decision` record names the refusal so an operator can tell them apart.

    They block the steps that build each item: 0127.S2, 0127.S6, and 0127.S3. (raised by the M3 readiness review, 2026-11-19; sources: 0127-p1-F18, 0127-p1-F19, 0127-p1-F25, 0127-p2-L7, 0127-p3-F14)

81. **What a pod with a non-empty warm list does on a pool that runs no `netagent`.** [`0118-agent-pod-layout`](../0118-agent-pod-layout/change.md) renders `netagent` where this design renders it and `lenny-store-fill` when the pod's warm list is not empty, and `lenny-store-fill` fills every store through `netagent` (PLR-21). This design has pools with `egressProfile: internet` that run no `netagent`, and a public `gitRepository` entry of a Runtime's `sharedAssets` goes onto the warm list of every pool of that runtime ([`0147-tenant-derived-runtimes`, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores)). No change states what such a pod does. Options:
    - (a) pool admission refuses a pool whose warm list is not empty when the pool runs no `netagent`;
    - (b) the controller renders `netagent` on every pod whose warm list is not empty;
    - (c) the pod renders no `lenny-store-fill` and skips the warm list.

    Recommendation: (a). It states the combination as a configuration error at write time, keeps this design's choice of which pools run `netagent`, and leaves no pod that silently lacks its stores. It blocks the warm-list carrier of 0127.S5 on pools that run no `netagent`, and 0118.S4 and 0153.S9 on the other side. (raised by the M3 readiness review, 2026-11-19; requested by change 0118; mirrors 0118 O14)

82. **Whether a later `allowed` verdict restores an entry marked `userAccess: userRefused`.** The user verdict `userAccess` is a field of a readable or writable entry separate from SO-5b's `state` ("Reserved for other designs", the writable set entry row), so an approval or an expiry never rewrites a refusal. What a later sweep verdict of `allowed` does to an entry marked `userRefused` in a running session is undefined, and the mint checks and `netagent` read the field. Options:
    - (a) the next `allowed` verdict clears `userRefused` and pushes a binding change, so the repository returns to the session;
    - (b) `userRefused` stays for the rest of the session, and only a new session regains the repository.

    Recommendation: (a), as [`0152-user-git-identity`](../0152-user-git-identity/decisions.md) recommends and [`0142-security-oversight`](../0142-security-oversight/change.md) requested, because under (b) a transient misclassification costs the session the repository for good. It blocks the transition rule of the writable set entry row in 0127.S2 and the sweep's transitions in 0152.S2. (raised by the M3 readiness review, 2026-11-19; requested by change 0142; mirrors 0152 decision 54)

83. **Who triggers an emergency rotation of the federation key and the identity key.** **Identity issuer and key sets.** under "Delivery modes" states that "An emergency rotation through the admin API drops the previous key from both at once" and defines no route, permission, or caller, and the federation issuer states no emergency rotation. A rotation of the federation key refuses every federation exchange of the tenant at providers that cached the earlier key set for up to `tokenService.federationIssuer.prePublishSeconds`, so whoever can call it can deny the tenant's provider access for about a day. [`0143-service-account-credentials`](../0143-service-account-credentials/decisions.md) raises the same question for the exchange key as its O10, and asks that this design align with its answer. Options:
    - (a) one route per issuer, such as `POST /v1/admin/tenants/{id}/federation-issuer/rotate` and `POST /v1/admin/tenants/{id}/identity-issuer/rotate`, held by the tenant's `security-admin` and by a `platform-admin` with a justification mirrored to the tenant's chain under SO-4a, audited with the reason `emergency`, with a `security` test of its authorization;
    - (b) the same routes held by a `platform-admin` alone, mirrored under SO-4a;
    - (c) the same routes held by the tenant's `tenant-admin`.

    Recommendation: (a), the answer 0143 recommends for its O10, so that the three issuers of the Token Service share one rule. It blocks the emergency rotation of the federation key in 0127.S4 and of the identity key. (raised by the M3 readiness review, 2026-11-19; requested by change 0143; mirrors 0143 O10)

Raised on 2026-11-24 by decision 22 of [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/decisions.md#decisions).

84. **The scope of a binding that a `platform-admin` writes.** "Credential bindings" **Platform and pool bindings.** lets one operator LLM gateway serve every tenant through an attribution binding that a `platform-admin` writes. **Recommendation: (c)**, because platform scope serves a gateway for every tenant with one record, and pool scope keeps a pool's traffic on its own gateway, such as one in a region. Options:
    - (a) Platform scope alone.
    - (b) Pool scope alone.
    - (c) Both, with a pool binding taking the place of a platform binding on the same host for that pool's sessions.

   Blocks: "Credential bindings", 0127.S4, and 0133.S1.
85. **How an exhausted budget stops a session's model calls.** **Binding suspension.** stops attaching the attribution assertion, so the gateway refuses the next call. **Recommendation: (a)**, because it needs no change in the gateway beyond verifying the assertion, and it takes effect at the next request. Options:
    - (a) Suspend the session's attribution bindings through the pod binding API, with the Token Service refusing to mint.
    - (b) The gateway looks up the session's state at Lenny by session identifier and caches the answer.
    - (c) The Token Service refuses to mint alone, so a suspension takes effect when the cached assertion expires.

   Blocks: **Binding suspension.**, 0127.S4, and 0170.S6.

## Decisions

Recorded owner decisions:

- The scope rule (2026-11-02): this document holds egress and git. A proposal here carries other work only as a hook when adding it later would be rework, and everything else goes in its own design document. Proposals interleave across documents, with dependencies cross-referenced from the documents and no shared queue file.
- Proposal 0 stays in this design (withdrawn on 2026-11-13 by decision 62). F-25.6.9 and F-25.4.40 move to [`0142-security-oversight`](../0142-security-oversight/change.md).
- The evidence streams belong in this design, with room for later agent activity streams. The tenant outbound connector has its own design document, with its hooks here.
- Level 1 replacement is included (2026-11-02). The owner reversed the deferral, and the documentation must state its limits and why it is not the recommended approach.
- Decisions 1 to 11, 13 to 30, and 32 are adopted as recommended (2026-11-02), along with the four corrections listed under revision 15 in "Review record". Server TLS on I2 (the proxy hop), I5 (the git endpoint), and I7 (the pod binding API) is adopted (2026-11-02), after a spike the owner asked for. R14 stays outside this design. Decisions 33 to 38 are adopted as recommended (2026-11-02), with 6 hours as the default for decision 36 and the note under "Transport security" that R14 may merge the two PKIs. Decision 31 is adopted as recommended (2026-11-02), with the anti-affinity, the `hostUsers` value, and the ID rule below. Decisions 39 to 42 are adopted as recommended (2026-11-02), with the changes the twenty-first review round forced, stated at each.
- A local endpoint is adopted, and it runs in the separate `netagent` container. Decision 44 removed the second, loopback git endpoint.
- The decision service runs separately from the gateway.
- Pull requests and host APIs go through standard HTTP on the egress route, with no platform tool. An in-pod API token is acceptable as a tenant opt-in.
- Policy for concurrent-slot pods is per pool and tenant. Decision 60 replaced this on 2026-11-13 with per-slot scopes, and the per-pool-and-tenant policy remains the fallback where slot attribution does not answer.
- Envoy is the default proxy. The owner made this conditional on hands-on testing, and the third validation round passed it with the configuration changes listed under "Central egress proxy".
- Stored-token push sits behind a gate plus a per-pool tenant opt-in, with the risks stated under "Credentials". Revision 6 made the gate a per-tenant platform grant (decision 19), which supersedes the deployment-wide gate this decision first recorded.
- Tenant admins can register upstream proxies and git endpoints on public addresses, following the connector precedent. Private-address services stay under platform registration. (The precedent was §9.3's MCP connector definitions, which [`0124-connector-removal`](../0124-connector-removal/change.md) removes under the owner's decision of 2026-11-15. The decision stands without it.)
- `gitAccess` on pools with `egressProfile: restricted` is adopted, so pools with `egressProfile: restricted` keep warm stores without general egress.

Decisions raised in revision 3:

1. **Remove `provider-direct` now.** Recommendation: adopt. Revision 77 drops the pairing of `deliveryMode: direct` with `proxied` that this decision first carried, because LU-4 removes direct delivery mode (see "Consolidating `provider-direct`").
2. **Remove the gateway clone path.** Recommendation: adopt. The gateway runs no git, clones run in the pod through `netagent`, and F-14.1.37 closes by deletion (see "Credentials", **The gateway runs no git.**).
3. **Remove category-keyed defaults from §26.2.** Recommendation: adopt (see "Runtime categories in §26.2").
4. **`inject` as the default credential delivery, including TLS termination for bound hosts.** Recommendation: adopt, with `file` as the gated opt-in. Round 3 validated both transports with mitmproxy standing in for `netagent`.
5. **Egress groups for corporate gateway identity.** Recommendation: adopt, because no surveyed gateway documents header identity on an undecrypted CONNECT.
6. **Tenant pool overlays with `tenantOverride` defaulting to `narrow`.** Recommendation: adopt (see "Tenant pool overlays").
7. **SSH remotes through `sshForms` data with a git `ERR` fallback.** Recommendation: adopt, with no per-provider code in `netagent`.
8. **SDK scope.** Recommendation: one read-only network accessor per SDK (endpoints, launch variables, bindings, and `file` values read on each call), and nothing else. Every mechanism keeps working for runtimes without an SDK.
9. **Cloud and platform credentials.** Recommendation: adopt `federation` as the generic mechanism, with the Token Service as OIDC issuer and provider templates as data, and adopt `metadata` as a provider plugin for tenants that cannot configure federation trust, with AWS shipped first. Both sit behind the `agentReadableDelivery` grant with `file`.
10. **No tool-specific templates shipped by Lenny.** Recommendation: adopt. Lenny ships the convention variables, the git config, the CA bundle, the descriptor, and the generic credential directory with a `netrc` projection. Tool files (Maven `settings.xml`, `gh` `hosts.yml`) come from the runtime image or a deployer template.
11. **Constant placeholder.** Recommendation: adopt `lenny-injected` as a constant fixed at pod creation, because `netagent` overwrites the header whatever the placeholder holds.

Decisions raised by the revision 4 review:

12. **Level 1 replacement.** The review recommended deferring it. The owner decided to include it, with its limits and the reasons it is not recommended stated in the documentation (see "Level 1 replacement").
13. **Private destinations pinned by the decision, with no filter exemptions.** Recommendation: adopt. It closes the cross-tenant path through tenant-controlled DNS, and it removes the need for SSRF exemptions.
14. **Per-tenant federation issuers.** Recommendation: adopt, because AWS and Azure trust conditions cannot express a tenant claim, and a per-tenant issuer scopes trust by construction.
15. **Egress groups as additional `lenny-egress` Deployments with pod pinning.** Recommendation: adopt, in place of a second proxy tier.
16. **Ref resolution stays in the gateway, through a Go `ls-refs` client.** Recommendation: adopt. It keeps the §14 contract synchronous and trusts no SHA from the pod.

Decisions raised by the revision 5 review:

17. **Binding feed as a gateway push plus bounded re-reads, with a provisional binding on resume.** Recommendation: adopt. Postgres notifications are unavailable through the §12 pooler, and the provisional binding is the smaller change to §7.3.
18. **Egress-group grants as Helm values with chart-rendered ingress policies.** Recommendation: adopt, so no Lenny component writes NetworkPolicies.
19. **One gate per risk class, granted per tenant.** Recommendation: adopt, in place of one deployment-wide gate.
20. **A tunnel lifetime menu rendered by the chart.** Recommendation: adopt, so pools choose a cap without xDS.

Decisions raised by the revision 6 review:

21. **`netagent` requests credentials from the Token Service directly (I8, the pod credential API), and the Token Service consults the decision service for scope.** Recommendation: adopt, because relaying the pod's token through the decision service made that service a bearer-token relay.
22. **The controller stamps the owner tenant on tenant-owned pool pods at creation.** Recommendation: adopt, with the matching label-webhook rule.
23. **One shared repository-path canonicalizer** for the resolver, session create, and `netagent`. Recommendation: adopt.

Decisions raised by the revision 7 review:

24. **Two independent gates for every mint, with the Token Service authoritative for binding definitions and the decision service for policy and liveness.** Recommendation: adopt, with one shared `pkg/binding` package.
25. **I8 (the pod credential API) on an isolated, rate-limited TLS listener of the Token Service.** Recommendation: adopt, so pod load cannot reach the gateway's lease path.
26. **`ownerTenantId` set only at pool creation and immutable afterwards.** Recommendation: adopt.
