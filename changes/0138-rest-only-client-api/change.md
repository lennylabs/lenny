## Problem

"Terms", after "Scope", defines the vocabulary this document uses.

[§15 External API Surface](../../spec/15_external-api-surface.md#15-external-api-surface) exposes several client-facing APIs through the `ExternalAdapterRegistry`, a set of adapters compiled into the gateway and routed by path prefix **[source]**. Its paragraph **REST vs MCP split (operator vs session).** makes MCP at `/mcp` the recommended path for session flows and REST the path "for callers that cannot implement MCP". Its **Built-in adapter inventory:** lists MCP, OpenAI Chat Completions, and Open Responses for v1, and A2A and Agent Protocol for later ([§21 Planned / Post-V1](../../spec/21_planned-post-v1.md#21-planned--post-v1)). The designs under `designs/` add an Anthropic Messages adapter ([`0120-anthropic-messages-api`](../0120-anthropic-messages-api/change.md)), a dual-era MCP endpoint with the MCP Tasks extension ([`0134-mcp-protocol-upgrade`](../0134-mcp-protocol-upgrade/change.md)), client-defined tools on every surface ([`0122-client-tools`](../0122-client-tools/change.md)), provider-surface delivery rules ([MD-8](../0135-message-delivery/change.md#md-8-provider-surfaces)), and protocol state mappings ([SL-11](../0146-session-lifecycle/change.md#sl-11-external-mappings)).

Each protocol puts its wire format, version policy, identifiers, and state inside the gateway **[source]**:

- MCP: per-version serializers, a Redis record per handshake-era `Mcp-Session-Id`, header and `Origin` validation, a version window with a deprecation header and a metric, the per-kind wire projection of §15.2, and the Tasks mapping that replaces the MCP column of [§8.8](../../spec/08_recursive-delegation.md#88-taskrecord-and-taskresult-schema) ("MP-1" to "MP-4", "MP-8").
- Open Responses and Anthropic Messages: response records on the session row, keyed conversation digests and request records in two tables, warm-turn forwarding between replicas, `x-api-key` handling in the auth middleware, and provider error envelopes in the gateway (§15 **Open Responses conversation sessions.**, "AM-2", "AM-5", "AM-8").
- A2A: an outbound push channel that signs with `X-Lenny-Signature`, agent cards generated at write time, and an aggregated `/.well-known/agent.json` (§21.1).
- All of them: the adapter interface and its outbound dispatcher, a runtime registration endpoint with a validation gate, the translation fidelity matrix, the protocol columns of the §28.5.3 type registry, and contract tests that run every built-in adapter ([§15.2.1 REST/MCP Consistency Contract](../../spec/15_external-api-surface.md#1521-restmcp-consistency-contract)).

Every revision of an external protocol therefore changes the gateway. MCP published `2025-06-18`, `2025-11-25`, and `2026-07-28` within about thirteen months. A2A 1.0 renamed the card path and every operation that §21.1 names. Anthropic added the API version `2026-10-21` **[external]**. The spike of 2026-11-13 found that every client-facing MCP and A2A feature Lenny uses maps onto REST once REST gains a few additions, and that MCP `2026-07-28` removed the connection state that made an MCP server inside the gateway attractive. The owner decided on 2026-11-13 that Lenny keeps only its REST API, with its server-sent event stream, as the client-facing API, and that every client protocol adapter moves into a separate first-party repository maintained by the Lenny project ("Decisions" in `decisions.md`).

This design states what REST gains, how an adapter works in front of REST, how one is deployed and versioned, how adapters are tested, how Lenny's own clients move to REST, what leaves Lenny, and what changes in the designs that specify adapters.

## Scope

**Removed from Lenny:**

- The `ExternalAdapterRegistry`, the `ExternalProtocolAdapter` interface, `BaseAdapter`, `OutboundChannel` and its back-pressure policy, `OutboundCapabilitySet`, `AdapterCapabilities` and the `adapterCapabilities` member of discovery, the dispatch-filter rule, the three tiers of pluggability, `POST /v1/admin/external-adapters` with its validation gate, and `lenny-ctl admin external-adapters` ("RO-11").
- Every client protocol endpoint the gateway serves: MCP at `/mcp`, `/mcp/environments/{name}`, and the WebSocket `/mcp/v1/ws`; OpenAI Chat Completions at `/v1/chat/completions`; Open Responses at `/v1/responses` and `/v1/responses/{id}`; Anthropic Messages at `/v1/messages`; the models list at `/v1/models`; and the planned A2A and Agent Protocol endpoints ("RO-11").
- The state those endpoints keep: the handshake-era session record, the response records on the session row, the conversation digests and request records, and the push subscriptions of §21.1 ("RO-11").
- The protocol text of the specification: §15.2, §15.2.1, the protocol columns of §8.8, of the translation fidelity matrix, and of the §28.5.3 type registry, §21.1, §21.3, and the protocol rules of the designs that specify adapters ("RO-11", "Instructions for reviewers of other designs").

**Added to Lenny:**

- REST additions R1 to R17 and R19 to R25 ("RO-2"), of which R10 and R11 are deferred under O9. R18 is withdrawn under O3. R20 to R25 give a client the session primitives of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md) and of the changes that own their mechanisms, and each cites the change that defines its semantics.
- An operator-written adapter registry and the authorization rules that let an adapter forward its caller's bearer under MCP's token rule: a resource identifier per adapter, narrowing of each forwarded request to that adapter's registered operations, request capabilities, and role ceiling, minting refusals, and a dedicated adapter listener with mutual TLS ("RO-4").
- A download origin that serves the signed download URLs of R13.
- An adapter conformance kit published from Lenny's repository, which replaces the §15.2.1 contract tests ("RO-6").
- Optional dependencies on the adapter subcharts in the `lenny` chart, with the MCP adapter enabled by default ("RO-5").

**Changed in Lenny:**

- The session commands of `lenny session`, the client SDKs, and the web playground speak REST and the event stream ("RO-7").
- The specification's statement of the client surface, discovery, idempotency, authentication, and the event stream ("RO-1", "Specification changes").

**Added outside Lenny's tree, maintained by the Lenny project:** one repository per adapter, for MCP, A2A, OpenAI Chat Completions, Open Responses, and Anthropic Messages, each with its own specification, image, and Helm chart ("RO-5", "RO-8" to "RO-10").

## High-level design

Lenny's gateway serves one client API: REST under `/v1` and the session event stream. Every other client protocol is served by an adapter, a separate program that the Lenny project maintains in its own repository and ships as an image and a Helm chart. An adapter calls the client API as any client does. It holds no Lenny credential and forwards the bearer its own client sent, so Lenny authenticates, authorizes, scopes, meters, and audits the request as it would a direct REST request, narrowed to what the adapter is registered for. It keeps no durable state: every identifier it hands out encodes the Lenny identifiers behind it or resolves through a REST lookup, so any replica serves any request.

REST gains what the adapters need and today's REST lacks: the event sequence number at the moment of a send, message and turn resources, a list of pending input, idempotent sends, webhook subscriptions, a public runtime index, signed download URLs, conversation history on a send, a conditional send for warm continuations, a client reference for conversation lookup, a per-session elicitation policy, and a turn interrupt. REST also gains the client's side of the session primitives of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md): the `append` intent, routes with which the root's client transfers or releases a descendant, the events and the answer route of client tool calls, events for a session that leaves its parent, the hand-off with its successor, and a read of a session's history. Each is a protocol-neutral REST feature that a direct client can use as well ("RO-2").

MCP requires a server to accept only tokens issued for it and forbids it to pass any other token on. The operator therefore registers each adapter in the adapter registry, and the gateway computes the adapter's resource identifiers, such as `https://lenny.acme.com/mcp`, serves their metadata, and accepts a token issued for one of them only on a request that the adapter forwards and that names that adapter. Such a request is narrowed: it may call only the operations and use only the request capabilities the registration lists, under a role ceiling, and it can never mint another token. A first-party adapter reaches the gateway on a dedicated listener with mutual TLS, so its certificate names the registration. Ingress routes the protocol paths to the adapters and `/v1` to the gateway. The `lenny` chart deploys the MCP adapter this way by default, and the other adapters when an operator enables them ("RO-4", "RO-5").

The §15.2.1 contract tests become an adapter conformance kit that Lenny publishes. Each adapter repository runs it against a deployed Lenny, and Lenny's release runs every first-party adapter's suite before its chart pins that adapter's version ("RO-6"). Lenny's own CLI, SDKs, and playground use REST and the event stream, so Lenny's own clients exercise the contract that third parties use ("RO-7").

Inside the adapters, MCP and A2A tasks represent one message each: a send creates a task whose identifier names the session and the message, and the task completes at the end of the turn that consumed the message (D4). Cancelling a task retracts its message while it is pending and interrupts its turn once the turn runs (O4). A2A push notifications travel through webhook subscriptions to the A2A adapter's push relay, which posts each event to the A2A client with the client's own credentials. The provider adapters run each request as one turn in an ordinary session, which stays `idle` with its pod after the turn and becomes `dormant` after its idle timeout. A later request continues the session warm with a conditional send, waking it when it is `dormant`, or runs cold in a new session with the conversation as history. Open Responses finds the session through the response ID, and Chat Completions and Anthropic Messages through a conversation fingerprint stored as a client reference. The turn resource replaces the Open Responses response records, and client references replace the Anthropic conversation digest tables ("RO-8" to "RO-10").

## Requirements

| # | Requirement |
| :-- | :-- |
| ROR-1 | Lenny's gateway serves one client API: REST under `/v1` and the session event stream. It serves no route on a protocol path ("RO-1"). |
| ROR-2 | Every client-facing feature that a first-party adapter serves is reachable through the client API with the caller's own bearer. No adapter holds a Lenny credential, a role, or a route that Lenny grants to it alone. An adapter's client certificate on the adapter listener identifies its registration, which only narrows the authority of the bearer it forwards and never grants authority ("RO-4"). |
| ROR-3 | An adapter keeps no durable state and no response cache shared across bearers. Any replica serves any request, and the loss of a replica loses only its open connections. |
| ROR-4 | The client API accepts a token whose audiences are all adapter resource identifiers only on a request narrowed to one of them, and limits that request to the intersection of the caller's authority with the registration's operations, request capabilities, and role ceiling. An adapter forwards only bearers presented on its own paths, and no narrowed request or adapter-audience token mints another token (O1, S1). |
| ROR-5 | Authentication, ownership, quota, admission, rate limits, audit, and billing apply to a request that an adapter makes exactly as to a direct REST request. |
| ROR-6 | Every protocol identifier that an adapter issues encodes Lenny identifiers or resolves through a REST lookup made with the caller's bearer, so a guessed identifier reveals nothing under session ownership rule 7. |
| ROR-7 | The `lenny session` commands, the client SDKs, and the web playground use only the client API. |
| ROR-8 | Each first-party adapter version that the umbrella chart pins has passed the adapter conformance kit against that Lenny release. |
| ROR-9 | The umbrella chart enables the MCP adapter by default and every other adapter only on request, and enabling or disabling an adapter changes no behaviour of the client API. |
| ROR-10 | Lenny's specification states no client protocol's wire format, version policy, or state mapping. |
| ROR-11 | A session created through an adapter is an ordinary session: REST reads, derive, approvals, retention, and erasure apply to it. |
| ROR-12 | Every REST addition is protocol-neutral: its contract names no client protocol, and a direct REST client can use it. |
| ROR-13 | No client bearer reaches a pod, a webhook target, webhook subscriber data, a session label, an LLM upstream, or a log, in Lenny or in a first-party adapter. |
| ROR-14 | A conversation that an MCP or A2A adapter serves continues on the successor when its session ends with a hand-off, and no message the client sends after the hand-off is lost (R24). |

## Detailed design

### RO-1 The client contract

**One client API [design].** The gateway serves REST under `/v1`, the event stream `GET /v1/sessions/{id}/events`, the OpenAPI documents, the RFC 9728 metadata of R9, the playground's assets and token routes, and nothing else on the client listener. The adapter listener of "RO-4" serves the same REST routes and event stream to attested adapters, and the download origin serves R13's downloads alone. §15's introduction states this in place of **REST vs MCP split (operator vs session).**: sessions and administration both use REST, and protocol adapters are separate projects that call REST.

**Protocol paths [design].** The client API defines no route on these paths, so ingress can route them to adapters: `/mcp` and `/t/{tenantId}/mcp` with their sub-paths, `/a2a` with its sub-paths, `/.well-known/agent-card.json`, `/v1/chat/completions`, `/v1/responses`, `/v1/messages` with its sub-paths, `/v1/models`, and `/v1/files`. A request to one of them that reaches the gateway, because no adapter is enabled for it, answers `404 RESOURCE_NOT_FOUND`. The specification lists the paths so that a later REST route never collides with one; the list is a reservation and names no protocol behaviour.

**Event stream [design].** The rules that §15.2 states for the MCP attach stream move to the event stream route of §15.1: the SSE `id` carries `SeqNum`, `Last-Event-ID` resumes, `gap_detected` precedes the oldest retained event when the cursor has been evicted, the coordinator-handoff synthesis precedes any `gap_detected`, and a `:keepalive` comment is written after 20 seconds without an event. The bounded-error back-pressure policy that §7.2 states for SSE readers applies to every reader, an adapter's included. The `SessionEvent` kind registry stays as the stream's contract, with the kinds the designs add (`message_state`, `turn_start`, `turn_end`, `usage`, `activity`, and, under R22 to R24, `tool_call`, `tool_call_withdrawn`, `child_transferred`, `child_released`, `left`, and `handoff`), and loses the dispatch-filter rule, because no in-gateway adapter receives events. A stream closes when its bearer's `exp` passes and when the bearer's `jti` is revoked, after a final stream-control frame `stream_closed` that carries `reason` (`token_expired` or `token_revoked`) and the last `SeqNum` written; the reader reopens the stream with a current bearer and `Last-Event-ID` (S1, O13).

**Discovery [design].** `GET /v1/runtimes` keeps `AuthorizedRuntime` without `adapterCapabilities` (and without `mcpEndpoint`, which AR-1 removed). R8 adds a public index and a single-runtime read. `?adapter=` leaves.

**Shared error taxonomy [design].** §15.2.1 rule 3 moves to §15.1 **Error response envelope.**, because other sections cite it for every REST error.

**R1. Sequence number at send [design].** The receipt of `POST /v1/sessions/{id}/messages` carries `seq`, the session's `last_seq` after the message's `message_state` event was written, and `POST /v1/sessions/start` carries the same for its first message. `GET /v1/sessions/{id}` carries `lastSeq`. A client that sends and then opens the stream with `Last-Event-ID: <seq>` sees every event from the send on, with no race and no replay of the whole buffer. The counter exists as `sessions.last_seq` (§10.4) **[source]**.

**R2. Message resource [design].** `GET /v1/sessions/{id}/messages/{messageId}` returns `messageId`, `state` (the states of the message delivery design, `retracted` and `consumed_unrecorded` among them), `intent`, `fromKind`, `turn` (the turn that consumed it, once consumed), `clientRef` (R17), `createdAt`, and `reason` for a message that ended without consumption. The fields are those the `message_state` event already carries (MD-7) **[source]**. Session ownership applies; a message of a session the caller may not read, or a message ID unknown on the session, answers `404 RESOURCE_NOT_FOUND`.

**R3. Turn resource [design].** `GET /v1/sessions/{id}/turns/{turn}` and `GET /v1/sessions/{id}/turns` (paginated, filterable by `causedBy` sender kind) return for each turn: `turn`, `status` (`running`, `completed`, `failed`, `interrupted`, `runtime_exit`, or `cut` with its cause, as SL-3 records), `causedBy` with the sender kind, `consumed` with each consumed message and the output position at which it was consumed, `output` (the turn's output parts from the transcript, in order), `endOfTurn` (the end-of-turn `message`'s own parts), `clientToolCalls`, each call of the turn to a client tool with its `callId`, its group, and its outcome (`open`, `answered`, or `withdrawn` with its reason) under R22, `usage` (the totals of `turn_end`, by source), `error`, `startedAt`, `endedAt`, and `firstSeq` and `lastSeq` on the event stream. A client cuts a response at the consumption of its own message, as MD-8 requires of the provider surfaces, by taking the output from that message's position. The turn's data exists in the `turn_end` payload (MD-20) and the transcript **[source]**; R3 exposes it durably, where the replay buffer holds only recent events.

**R4. Pending input [design].** `GET /v1/sessions/{id}/elicitations?state=pending` and `GET /v1/sessions/{id}/approvals?state=pending` list a session's open elicitations and its pending tool-use and harness approvals. Each entry carries its identifier, `turn`, `mode` (form or URL), `message`, `requestedSchema` or `url`, provenance (the asking session and hop, or, for a link prompt the gateway raises, `initiator_type: platform`, `purpose: account_link`, and the link provider), and `createdAt`. An elicitation from an operator service reaches R4 as its runtime's question under B6 of [`0135-message-delivery`](../0135-message-delivery/decisions.md#decisions). A link prompt ([`0151-user-credential-delivery`, "UC-8: Link prompts"](../0151-user-credential-delivery/change.md#uc-8-link-prompts)) is one per user and link provider, so the same entry appears in the list of each root session it is shown on, and a response or a dismissal from any of them resolves it on all. Pending elicitations are already durable, because a coordinator handoff re-synthesizes them from Postgres (§10.4) **[source]**. The respond, dismiss, approve, and deny routes are unchanged.

**R5. Idempotent sends [design].** `POST /v1/sessions/{id}/messages` accepts `Idempotency-Key` under §11.5's rules. Every key of §11.5 is scoped by the tenant, the subject, the effective audience (none for a request that is not narrowed), the token's `azp` or `client_id`, the method, the route template, the path parameters, and the key, in place of `(tenant_id, key)`. Two users of one tenant who send the same A2A `messageId` therefore do not collide, and a key that one adapter or route used never replays a response for another. A retry with the same key within §11.5's 24-hour window returns the original receipt, `seq` included. Each first-party adapter prefixes the keys it derives with its registration name, such as `a2a:` before an A2A `messageId`, and a provider adapter's key is a digest of the request, so an identical retry within the window returns the original receipt. The operation check of "RO-4" runs before the replay, so a narrowed request never receives a stored response for an operation outside its registration. The MCP tool argument `idempotencyKey` leaves §11.5 with the MCP API.

**R6. Webhook subscriptions [design].**

- Routes: `POST /v1/sessions/{id}/webhooks`, `GET /v1/sessions/{id}/webhooks`, `GET /v1/sessions/{id}/webhooks/{webhookId}`, and `DELETE /v1/sessions/{id}/webhooks/{webhookId}`, owner-only under session ownership. §10.2's authorization matrix, whose row "Configure callback URLs / webhooks" denies the `user` role today **[source]**, gains a row that lets a session's owner create, list, and delete subscriptions on that session. Creating a subscription uses the `webhook` request capability of "RO-4".
- Body: `url`; `eventKinds` from the kind registry; optional `coalesceMs` for `activity` and `output` (at least 1,000 ms for `activity`, as MD-21 coalesces it for webhooks); `secret`, write-only, stored as `callbackSecret` is; optional `subscriberData`, an opaque string of at most 4 KiB that Lenny stores encrypted and echoes in every delivery; and optional `expiresAt`.
- Limits: `webhooks.maxPerSession`, default 8, operator-tunable; a request above it answers `409 WEBHOOK_LIMIT_EXCEEDED`.
- Delivery: one CloudEvents envelope per event, carrying the `SessionEvent`, its `SeqNum`, the tenant, session, and subscription identifiers, and `subscriberData`, signed with the `X-Lenny-Signature` scheme of [§14](../../spec/14_workspace-plan-schema.md), "Webhook Delivery Model", retried on its schedule, delivered in `SeqNum` order per subscription, and listed after exhaustion at `GET /v1/sessions/{id}/webhook-events` with the subscription's identifier.
- Delivery state: each subscription stores its delivery cursor, the last `SeqNum` that its target acknowledged or that was listed after exhaustion, in Postgres with the subscription. One gateway replica at a time delivers a subscription's events, under a lease on the subscription, and a replica that takes the lease after a replica loss or a coordinator handoff resumes from the cursor through the event relay's history, so no event is skipped and no two replicas deliver one subscription at once. Delivery is at least once: the CloudEvents `id` is derived from the tenant, session, subscription, and `SeqNum`, so a target discards a redelivery by its `id`.
- Targets: the SSRF rules of `callbackUrl` apply. A target is an HTTPS URL; the gateway resolves the host once per delivery, checks the address against the SSRF rules, connects to that address, and follows no redirect. `webhooks.internalTargets`, an operator list of exact in-cluster URL prefixes, admits a private address for URLs under those prefixes alone, so the A2A push relay can be a target; the chart writes the relay's URL prefix when the A2A adapter is enabled, and the gateway's NetworkPolicy admits egress to the relay's pods by pod selector. A narrowed request whose token is `adapter-only` may name only a URL under its registration's `webhookTargets` ("RO-4").
- Lifetime: a subscription ends at its `expiresAt`, at `DELETE`, or when the session's retention ends, and the session's erasure removes it. A subscription created by a narrowed request has a lifetime of at most `webhooks.maxRestrictedLifetimeSeconds` (O13). Each subscription records the creating token's `azp` and the effective audience. Delivery stops while the session's owner is disabled. The owner lists and deletes subscriptions by the client that created them with `?clientId=`.
- Under O2 (b), `callbackUrl` and `callbackSecret` on creation create one subscription for `terminated`, under the same target, capability, and lifetime rules.

**Gateway egress [design].** The gateway's outbound HTTPS to hosts outside the cluster passes one NetworkPolicy in `lenny-system`, `allow-gateway-egress-external`, which takes the purposes of `allow-gateway-egress-llm-upstream` (§13.2.5) that remain once [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/change.md) removes the LLM proxy (decision D5). Webhook delivery is its main purpose, so this change states it. Its purposes:

- webhook and `callbackUrl` delivery (R6);
- the platform's OIDC issuer at `auth.oidc.issuerUrl` (§10.2);
- the issuers of customer identity sources of [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md);
- external interceptors that run outside the cluster (§4.8).

It admits TCP 443 to the `0.0.0.0/0` and `::/0` peers with the excepts of NET-057 and NET-062: the cluster pod and service CIDRs, `egressCIDRs.excludePrivate`, the link-local ranges, and the IMDS addresses. When the deployer sets the strict list `egressCIDRs.gatewayExternal`, it admits those CIDRs alone, with `identity.issuerCIDRs` merged into the list. The chart renders it when `webhooks.enabled` (default `true`), `identity.customerSources.enabled`, or `gateway.externalEgress.enabled` (default `true`) is true. `gateway.externalEgress.enabled` covers the platform's issuer and interceptors outside the cluster, and a deployer whose issuer and interceptors run in the cluster sets it to `false`. With all three false, the gateway has no external egress. With `webhooks.enabled: false`, R6's routes and `callbackUrl` are refused with `422 WEBHOOKS_DISABLED`, category `POLICY`. The gateway's own checks of each connection stay: the SSRF rules of webhook targets, of issuers, and of interceptor endpoints. In-cluster interceptors keep `allow-gateway-egress-interceptor-<namespace>` (NET-039), and the A2A push relay keeps its pod-selector rule. Agent pods are unaffected, because their egress is `0127-egress-and-git`'s.

**R7. Stable operations (O6 (b)) [design].** Every client route carries a unique `operationId` and a one-line summary. §15.5 states that an `operationId` is renamed or removed only in a major version of the client API, and Lenny publishes its OpenAPI document as a release artifact. Every operation already carries a unique `operationId` **[source]**. The document also carries the tags that "RO-4" reads: `x-lenny-adapter-eligible` on each operation an adapter may call, `x-lenny-scope` on each eligible operation, and `x-lenny-capability` on each request field that grants a capability.

**R8. Runtime index [design].** `GET /v1/public-runtimes` lists, without authentication, the runtimes that carry a `public` `publishedMetadata` entry, with their names and the keys of their public entries; it pages as every list does and answers the same for every caller. `GET /v1/runtimes/{name}` returns one `AuthorizedRuntime` to a caller who may use it, and `404 RESOURCE_NOT_FOUND` otherwise. `GET /v1/runtimes` and the single read include the aliases that RT-4's "Discovery" shows the caller, each marked as an alias, so a models list needs no second source.

**R9. Adapter resource identifiers (O1 (a)) [design].**

- Configuration: the adapter registry of "RO-4". The gateway computes each registration's identifiers: for a path prefix `p` on the gateway's origin, `https://<host><p>` and, when the registration sets `perTenant`, `https://<host>/t/{tenantId}<p>`; for an external origin, its `publicBaseUrl` and, with `perTenant`, `<publicBaseUrl>/t/{tenantId}`. An identifier takes its canonical form: lowercase scheme and host, no default port, no trailing slash, no query, and no fragment. The chart writes the MCP adapter's registration with `/mcp` when the adapter is enabled.
- Audiences: the deployment identity source accepts every computed identifier and each registration's `audienceAliases` in `aud`, beside `auth.oidc.clientId`. A customer identity source accepts the per-tenant identifiers of its own tenant that its `audiences` list. The gateway refuses a tenant's write of `audiences` or `pin_audience` that names a deployment-wide identifier or another tenant's identifier, and on every path the tenant the request resolves to must equal the tenant of the per-tenant identifier the token carries. The client API accepts a token with an adapter audience only under the rules of "RO-4", and refuses every other audience with `401 TOKEN_INVALID` and its challenge.
- Metadata: the gateway serves the RFC 9728 document of each identifier at its path-inserted well-known URL, `/.well-known/oauth-protected-resource<p>` and `/.well-known/oauth-protected-resource/t/{tenantId}<p>`, naming the identifier as `resource`, the issuers TS-7 names as `authorization_servers`, and the registration's `scopesSupported` as `scopes_supported`. The gateway builds each URL from the registration's configured base rather than from the request's `Host` header. Ingress routes `/.well-known/oauth-protected-resource` to the gateway on the gateway's origin and on each registered external origin.
- Challenge: the adapter answers an unauthenticated or refused request with `WWW-Authenticate: Bearer resource_metadata="<that URL>"`, copying `error` and `scope` from the client API's challenge to the forwarded call. The adapter builds the URL from its configured `publicBaseUrl` and its own path, and validates a `/t/{tenantId}` segment against Lenny's tenant identifier grammar first.

**R10 and R11 [design].** Deferred under O9, with the spike's contracts. These use cases would warrant them:

- R10, a per-principal stream of state changes across the caller's sessions, serves an MCP client that subscribes to `notifications/tasks` for many tasks at once, an A2A `ListTasks` across contexts, and a dashboard that follows every session of a user. Without it the adapter polls R2 and R3 at one REST call per task or per session. R10 is warranted when that polling load is measured to matter on a deployment, or when a client needs task changes faster than its polling interval.
- R11, a creation that commits the session and holds it until the missing links exist, serves an A2A client that expects an `auth-required` task at creation, and any client that wants one creation call to survive a link flow. Without it a creation that lacks links answers with the link URLs, and the client retries the creation. R11 is warranted when an adapter's protocol cannot express that retry, or when a creation is costly to repeat, as one with a large inline workspace is.

**R12. Input policy [design].** Session creation takes `inputPolicy`, `ask` by default or `decline`. Under `decline`, an agent elicitation is answered `decline` at once, including a question a runtime forwards from an operator service, a link prompt the gateway raises stays pending in R4's list until it expires or the link callback resolves it, and DA-7 omits the tools whose offer depends on a client that can answer. The field replaces the surface checks that AM-6 and DA-7 make against an in-gateway adapter's `SupportsElicitation`.

**R13. Signed download URLs (O9) [design].** `POST /v1/sessions/{id}/download-urls` takes a list of artifact paths and blob references of the session and returns, for each, a URL on the download origin, `https://<downloads.host>/d/<token>`, valid for `downloads.urlTtlSeconds` (O13). Session ownership applies, and a narrowed request may call the operation only when its registration lists it ("RO-4"). The token is encrypted and authenticated with a key derived per purpose by HKDF from the gateway's download key, carries a `kid` for rotation, and binds the tenant, the session, the path or reference, an HMAC of the subject, and the expiry. The download origin serves `GET /d/<token>` and `HEAD /d/<token>` and nothing else: it sets no cookie, reads no `Authorization` header, answers with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, and `Cache-Control: no-store`, and refuses a token whose session has ended its retention or whose owner is disabled. The download origin is a host separate from the gateway's origin, so a downloaded file never runs script with the gateway's or an adapter's origin. Ingress routes `downloads.host` to the gateway's download handler alone.

**R14. Client protocol attribution [design].** A request may carry `Lenny-Client-Protocol: <protocol>/<version>`, such as `mcp/2026-07-28`. The gateway records the value, truncated to 64 characters and limited to `[a-z0-9./-]`, in the audit record and as a bounded metric label `client_protocol` on request and session-creation metrics, with values outside an operator list (`observability.clientProtocols`, default the first-party protocols) recorded as `other`. It never reads the value for a decision. It replaces `AdapterCapabilities.Protocol` in audit and metrics.

**R15. Conversation input on REST [design].** The body of `POST /v1/sessions/{id}/messages`, and the first message of `POST /v1/sessions/start`, accept `conversation` in AM-4's form: `entries` with roles and the new input marked, `instructions`, `parameters`, and CT-1's `clientTools` and `toolChoice`, which sit inside `conversation` on REST. R15 is the member's only source. A client-written member follows AM-4's rules in [`0120-anthropic-messages-api`](../0120-anthropic-messages-api/change.md#am-4-conversation-input): its entry schema, under which an `assistant` entry carries `clientToolCalls` and a `user` entry carries `toolResults` in CT-1's form; "Validation", which the gateway applies before it accepts the message; and "Custody and redelivery", under which the gateway stores the member with the message, erases it with the message, and delivers it again on redelivery. The gateway delivers the member on the runtime's envelope when the chosen revision declares `capabilities.conversationInput`, and renders it as AM-4's transcript otherwise. `parameters` follow AM-3's enforced-parameter rules against `capabilities.conversationParameters`. The history is the client's assertion, delivered with `from.kind: client`, so it grants nothing a client could not send as text.

**R16. Conditional send [design].** The send body accepts `continues`, the identifier of a message of the same session. Lenny accepts the send only while all of these hold, checked and written in one conditional write:

1. The named message is the newest message the session's client sent.
2. The turn that consumed it ended `completed`.
3. The session's state still contains that turn: no restore since the turn ended used a checkpoint taken before the turn ended (O12). The move to `dormant` checkpoints after the turn, so a `dormant` session meets the condition, and a recovery from pod failure to an older checkpoint does not.
4. The session waits for its client: it is `idle` or `dormant`, or `running` with an open turn that no client message caused.

Otherwise the send answers `412 MESSAGE_PRECONDITION_FAILED` with `details.failed` naming the first condition that failed, and writes nothing. R5's idempotency replay runs before these conditions, so a retry of an accepted conditional send with the same `Idempotency-Key` returns the original receipt rather than failing condition 1 on its own message. A terminal session, such as one that a `one_shot` runtime completed, fails condition 4. Of two concurrent sends that name the same message, exactly one is accepted. An accepted send to a `dormant` session takes the resume path of [SL-5](../0146-session-lifecycle/change.md#sl-5-messages-to-a-waiting-or-paused-session): the session is restored under resume admission, and the message opens a turn once the restore lands. These are the conditions of §15 **Open Responses conversation sessions.** and AM-5 restated over messages, with the pod condition replaced by the waiting states; the owner, runtime, and environment conditions are already met, because only the session's owner may send to it and a session keeps its runtime and environment.

**R17. Client reference [design].** The send body accepts `clientRef`, an opaque string of at most 256 characters, stored with the message for the session's retention and erased with it. `GET /v1/client-refs/{clientRef}` returns the newest message of the caller's tenant and subject that carries the reference, with its session, message identifier, state, and turn, or `404 RESOURCE_NOT_FOUND`. A reference is never matched across tenants or subjects.

**R18 [design].** Withdrawn under O3. A provider adapter creates ordinary sessions, and no creation option closes a session after its turn ("RO-10").

**R19. Turn interrupt (O4, O11) [design].** `POST /v1/sessions/{id}/turns/{turn}/interrupt` stops the named turn while it is open:

- When the session's effective capabilities include `interrupt`, the gateway sends `interrupt_request` as [SL-3](../0146-session-lifecycle/change.md#sl-3-suspension-and-the-open-turn) does for a suspension. The runtime stops at a safe point and closes the turn with its end-of-turn `message`, and the turn ends `interrupted` on R3 and on `turn_end`. The session stays `idle` with its pod, and no suspension takes place.
- When the effective capabilities lack `interrupt`, the route answers `409 INTERRUPT_UNSUPPORTED`, category `POLICY`, not retryable, and writes nothing. The turn keeps running.
- When the runtime does not acknowledge within the `interrupt_request` deadline, the route answers `504 INTERRUPT_TIMEOUT`, category `TRANSIENT`, and writes no session state, as the `Interrupt` RPC's timeout writes none ([SL-3](../0146-session-lifecycle/change.md#sl-3-suspension-and-the-open-turn)). The turn keeps running, and a late stop by the runtime still ends it `interrupted` on `turn_end`.
- Lenny suspends no session on R19's behalf. A caller that receives either code and must stop the turn calls `POST /v1/sessions/{id}/suspend`, which stops the turn on every runtime under [SL-4](../0146-session-lifecycle/change.md#sl-4-tree-suspension): it seals the session, checkpoints the workspace, releases the pod, and pauses the session's descendants, and the client's next message resumes the session under SL-5 (O11).
- The route answers `202` with the turn resource once the runtime acknowledges, and the outcome arrives as `turn_end`. A turn that has already ended answers `200` with the turn resource and changes nothing, so a repeated call is safe. A turn number the session has not reached answers `404 RESOURCE_NOT_FOUND`.
- Session ownership applies: the owner, or the root's client for a child, may interrupt. The precondition is `running` with the named turn open; a session in another state answers `200` as for an ended turn when the turn has ended, and `409 INVALID_STATE_TRANSITION` otherwise.
- Every message the turn consumed is reported with the turn's status, so each MCP or A2A task whose message the turn consumed ends `cancelled`.

A runtime with `interrupt` keeps its pod, and its session stays `idle`. `lenny session interrupt` calls the route and, on either code, reports it and names `lenny session suspend`; the playground's Stop button calls the route and falls back to the suspend route on either code ("RO-7").

**R20. The `append` intent (decision 38 of 0166) [design].** The `intent` member of `POST /v1/sessions/{id}/messages` takes `append`. [MD-1 and MD-14](../0135-message-delivery/change.md#md-14-future-use-cases-and-the-extension-rule) of `0135-message-delivery` define the intent for every sender, and DPR-15 of 0166 binds it: the message starts no turn, waits in the session's inbox for its next turn, and is steered into an open turn when the session's runtime declares `steer`. Whether a runtime declares the intent, and the refusal of an intent it does not declare, follow MD-1. R1's `seq`, R5's `Idempotency-Key`, and R17's `clientRef` apply to an `append` send as to any send, and R2 reports the message `pending` until a turn consumes it. A parent's `session.send` with the `append` intent is the same send under 0166 "DP-8".

**R21. Transfer and release by the root's client (decisions 32, 33, and 46 of 0166) [design].** `POST /v1/sessions/{id}/transfer` and `POST /v1/sessions/{id}/release` let the root's client take over a descendant of its root, as a parent does with `session.transfer` and `session.release`. "Leaving the parent" in "DP-2" of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-2-parent-link) defines what each leave does and what it carries, and DPR-16 governs both routes:

- Caller: the owner of the root of the named session's tree, under session ownership. A principal that carries a session claim, which the gateway gives a runtime's platform tool calls, is refused by the predicate of SLR-22 of [`0146-session-lifecycle`](../0146-session-lifecycle/change.md#sl-4-tree-suspension) even when its subject owns the root, so a runtime cannot move a session out of its parent through this route. A session the caller may not read answers `404 RESOURCE_NOT_FOUND` under rule 7, and a root, which has no parent, answers `409 INVALID_STATE_TRANSITION`.
- Body: `transfer` takes none. `release` takes `handoff`, `false` by default; `handoff: true` ends the root of the tree with the released session as its successor under R24 and 0146's hand-off.
- Checks: the gateway checks the call against the root's grant, its `leave` and `leaveMaxDepth`, and the security record, read at the call, and refuses a leave they do not allow with the refusal 0166 states for it. A release of a session in another environment than its parent also meets that environment's admission check under TS-3 (decision 41 of 0166).
- Answer: `200` with the session resource after the leave. A session that already left in the mode the route names answers `200` with its resource and changes nothing, and R5's `Idempotency-Key` applies.
- Events: the root's event stream receives R23's event for the mode, and the former parent receives the `left` child event.
- Adapters: neither operation carries `x-lenny-adapter-eligible` under "RO-4", so a narrowed request cannot call it.

**R22. Client tool calls (decisions 23, 24, and 48 of 0166) [design].** [`0122-client-tools`](../0122-client-tools/change.md#ct-5-open-calls) owns the blocking interface for tools a client offers. When a runtime calls such a tool, the call stays open until the client answers it or the gateway withdraws it, at the latest when the session's hold passes, and a result for a withdrawn call reaches the runtime as `toolResults` on the next message from the call's client. "CT-5 Open calls" of 0122 states the semantics of each member below, and R22 lists them as the client API carries them:

- Session creation. `POST /v1/sessions` and `POST /v1/sessions/start` take `clientToolTurns`, `own` by default or `all`, which decides whether the client's tools are callable only in turns its own messages started (decision 48), and `clientToolHoldSeconds`, 300 by default, at most the tenant's ceiling (decision 24).
- `tool_call` event. The gateway writes one `tool_call` event to the session's event stream for each call that passes CT-4's validation, as CT-5 of 0122 states, so calls are delivered, held, and answered independently. The event carries the call's external `callId`, `name`, and `arguments` or custom input, `group` when the runtime labelled the call with one, `holdUntil`, and `turn`, the turn's provenance: `startedBy`, the `from` of the message that started the turn, and `contentFrom`, the ids of the other sessions whose content the runtime received in the turn before the call. The client runs, confirms, or refuses each call by its own policy from that provenance.
- `tool_call_withdrawn` event. The gateway writes it when it withdraws open calls, naming their external ids and the reason that CT-5 states: `hold_expired`, `cancelled`, `interrupted`, `pod_lost`, or `closed`.
- `openToolCalls` on `GET /v1/sessions/{id}` lists the session's open calls with their external ids, names, arguments or input, groups, and hold deadlines, so a reader that reconnects, and an adapter that keeps no state, finds the calls it has not answered.
- `POST /v1/sessions/{id}/tool-calls/{callId}/result` answers a call, with `content` as `MessagePart` entries and `isError`. It returns `answered` for an open call and `late` for a withdrawn one, whose result becomes a late result (DPR-13 of 0166). A repeated answer returns the first answer's outcome, and R5's `Idempotency-Key` applies. A call the session does not have answers `404 CLIENT_TOOL_CALL_NOT_FOUND`, and an answer from anyone other than the session's client answers `403 CLIENT_TOOL_RESULTS_FORBIDDEN`, as CT-5 states. A send with no input parts is accepted only while late results wait for its sender.
- `CLIENT_CHANGED`. §15.1's catalog gains the code, category `PERMANENT`, `retryable: false`. It is the code with which an open call to a parent's tool ends when the session leaves its parent ("DP-2" of 0166): the runtime's `tool_result` carries it, and the call's withdrawal names it.
- Adapters: `openToolCalls` and the answer route carry `x-lenny-adapter-eligible` under "RO-4", because every provider adapter and the MCP adapter answer calls through them ("RO-8", "RO-10").

A parent answers its child's calls with `tools.result` of 0166, which binds the answer route for a parent under "DP-8".

**R23. Events for a session that leaves its parent (decision 33 of 0166) [design].**

- `child_transferred` and `child_released` are written to the root's event stream when a session of its tree leaves its parent, with `sessionId`, `formerParentSessionId`, `actor` (`parent`, or `client` for R21), and, on `child_released`, `handoff`. A question of the session that was pending at its former parent moves to the root's client under 0166 "DP-2" and appears in R4's list with the asking session.
- `left` is the child event that MD-22 of 0135 writes to the former parent's inbox as its last event from the session, naming the mode. A client of the former parent reads it as it reads any child event of MD-22.
- Each is a kind of the registry, so an R6 subscription names it in `eventKinds`.

**R24. Hand-off (decision 21 of 0166) [design].** A root that releases a descendant with `handoff: true`, through `session.release` or through R21, ends under 0146's hand-off with the released session as its successor. R24 states what a client sees:

- `GET /v1/sessions/{id}` and the session list carry `successorSessionId` on a session that ended by a hand-off, and on no other session.
- A send to such a session, R16's conditional send included, answers `409 SESSION_HANDED_OFF` and writes nothing. The code has category `PERMANENT`, `retryable: false`, and `details.successorSessionId`. R5's replay runs first, so a retry of a send that the session accepted before the hand-off returns its original receipt.
- The session's event stream ends with a `handoff` event that carries `successorSessionId` and `successorSeq`, the successor's `last_seq` when the hand-off committed, and the stream then closes. A reader continues on the successor's stream with `Last-Event-ID: <successorSeq>` and sees every event of the successor from the hand-off on.
- An R6 subscription names `handoff` in `eventKinds`. A subscription stays on the session that ended, and a subscriber that follows the conversation creates one on the successor.
- The successor keeps its root's `labels` (decision 44 of 0166), so a lookup by label finds both sessions, and the one without `successorSessionId` is the live one.

**`budget_notice` (decisions 45 and 77 of 0170) [design].** The gateway writes `budget_notice` to the root session's event stream when a charge carries a limit of the tree's session budget or a cap past a threshold, naming the session that holds the limit, with the limit's key, the threshold, the unit, the consumption, and the amount, as [`0170-budgets`, "BG-6"](../0170-budgets/change.md#bg-6-enforcement) **Notices** states. It is a kind of the registry, so an R6 subscription names it in `eventKinds`, and the runtime receives none.

**R25. History read (decision 34 of 0166) [design].** `GET /v1/sessions/{id}/transcript` takes `after`, a `SeqNum`, and `limit`, and returns in order the stored history of the events a client attached to the session receives, which are the events a watch under [MD-25](../0135-message-delivery/change.md#md-25-watching-a-childs-stream) carries, each with its `SeqNum`, and with each streamed part as its completed part. The page carries the cursor of the next page. Session ownership applies, so the owner and the root's client for a descendant read it. `GET /v1/sessions/{id}/messages` stays the list of the messages sent to and from the session with their delivery states. `session.messages` of 0166 is the parent's binding of this read: a parent receives the same history under MD-25's checks, and, for a child in another environment, only what TS-3 "Model" lists (DPR-19 of 0166).

### RO-3 The adapter model

**Unprivileged [design].** An adapter holds no Lenny credential, service account binding, role, or network policy exception toward Lenny's stores. Its client certificate on the adapter listener names its registration, which narrows what a forwarded bearer may do and grants nothing ("RO-4"). Every REST call carries the bearer its client sent, unchanged. A request without a bearer is answered with the protocol's own `401` and R9's challenge, without a REST call.

**No durable state [design].** An adapter has no database, no cache whose loss changes behaviour, and no response cache shared across bearers; Lenny answers a narrowed request with `Cache-Control: no-store` and `Vary: Authorization, Lenny-Resource` ("RO-4"). Every identifier it issues encodes the Lenny identifiers it maps to or resolves through REST:

| Protocol identifier | Encoding | Lookup |
| :-- | :-- | :-- |
| MCP `2025-11-25` `Mcp-Session-Id` (O5) | Signed token: version, client capabilities, subject digest, expiry | Verified with the adapter's key |
| MCP JSON-RPC ID of a server-sent `elicitation/create` | `elic:<sessionId>:<elicitationId>` | The respond route |
| MCP SSE event ID (`2025-11-25`) | `<sessionId>:<seq>` | The event stream with `Last-Event-ID: <seq>` |
| MCP task ID and A2A task ID | `<sessionId>.<messageId>` | R2, then R3 and R4 |
| A2A `contextId` | The session ID, or a client value stored as a session label | `GET /v1/sessions/{id}` or `GET /v1/sessions?labels=` |
| A2A push config ID | The webhook subscription ID | R6 |
| Open Responses response ID and Anthropic `request-id` | `<sessionId>.<messageId>` | R2 and R3 |
| Chat Completions and Anthropic conversation continuation | The conversation fingerprint, a keyed digest of the normalized conversation, stored as `clientRef` | R17 |

**Configuration [design].** An adapter may hold one symmetric key in a Kubernetes Secret, shared by its replicas. It derives a separate key per purpose from it with HKDF: the signed identifiers, the push relay's subscription secrets and sealed subscriber data, and a provider adapter's conversation fingerprint. Each signed identifier is encrypted, carries a `kid` so that a rotation keeps the previous key for verification until the identifiers it signed expire, and binds the resource it names with its tenant, an HMAC of the subject, and an expiry. Losing or rotating the key invalidates outstanding identifiers of those kinds and changes no Lenny state; a rotated fingerprint key sends each provider conversation's next request cold once.

**Any replica [design].** No adapter needs session affinity. A replica that dies drops its open streams, and the client reopens them on another replica, which resumes from the client's cursor where the protocol has one. Tasks requests carry `Mcp-Name` for routing **[external]**, which the adapter does not need.

**Errors, limits, and retries [design].** The REST envelope's `code`, `category`, `retryable`, and HTTP status are enough to map every error to each protocol; each adapter's specification holds its table. `Retry-After` and `429` or `503` pass through. Lenny's limits key on tenant, user, session, and adapter, so the users behind one adapter keep separate limits. A per-client-IP limit reads the client address from `X-Forwarded-For`, which the gateway trusts only from ingress and from attested adapters whose registration sets `trustForwardedFor` ("RO-4").

**Shared client [design].** Each first-party adapter is written in Go on the Go client SDK, so the SDK's REST and stream handling serve every adapter and are exercised by them.

**Hand-off [design].** When a session an adapter serves ends with a successor under R24, the MCP and A2A adapters move the conversation to the successor (ROR-14). A send that answers `409 SESSION_HANDED_OFF` is sent again to `details.successorSessionId` with the same `Idempotency-Key`, and every protocol identifier the adapter issues afterwards names the successor. A stream that reads a `handoff` event continues on the successor's event stream from `successorSeq`. A lookup that finds a session with `successorSessionId` follows it. A successor can hand off in turn, so the adapter follows the chain until it reaches a session without a successor, within its bound on the REST calls one protocol request makes. A hand-off never forms a cycle, because the session that hands off ends. "RO-8" and "RO-9" state what each adapter's client sees.

**Cost [inference].** Every event crosses one more process and is encoded twice, and an attached client holds two connections, one to the adapter and one from the adapter to the gateway. The gateway's connection budget for stream readers counts the adapter's streams as it counts a direct client's.

### RO-4 Authorization of adapter requests

MCP requires a server to accept only tokens issued for it as the audience and forbids it to "accept or transit any other tokens" **[external]**. An adapter that forwards its client's bearer to the client API transits that token, so the rule holds only when the client API accepts the token as issued for that adapter and lets it do only what that adapter needs. The rules below apply to every adapter, first-party or third-party, as one capability of the platform (O1).

**Findings behind the rules [source].** Revision 1 had the client API accept any of the deployment's protected resource identifiers. Two security reviews of 2026-11-14 found that rule false as written. The client API's audience check is a union, so an adapter would transit tokens issued for other resources: a token for the REST audience, a playground bearer, or another adapter's token. A token issued for an adapter carried the caller's whole REST authority, token exchange included. The second review found that no enforcement point carried an `operationId`, because the authentication middleware runs before routing, several routers serve the client API, and some public routes verify their own tokens. It also found that an operation is coarser than the capabilities its request fields grant, and that a role such as `platform-admin` passed through an adapter unchanged. The owner accepted every fix of both reviews (S1), and the paragraphs below state the combined rule set.

**Adapter registry [design].** The operator writes `auth.adapters[]` in the Helm values. Each adapter subchart contributes a default registration that the operator's values override, and the gateway reads the rendered ConfigMap at start and on change. No API writes the registry, and no tenant setting reaches it. Each replica publishes a digest of the registry it loaded as a metric, and an alert fires while replicas disagree. A registration has these fields:

| Field | Meaning |
| :-- | :-- |
| `name` | The registration's name, used in audit records, metrics, and idempotency key prefixes. |
| `protocol` | The protocol the adapter serves, such as `mcp`, recorded beside R14's header in audit. |
| `paths` | Path prefixes on the gateway's origin, such as `/mcp`. |
| `publicBaseUrl` | An external origin the adapter serves, such as `https://a2a.acme.com`, in place of `paths`. |
| `perTenant` | Whether the adapter also serves each prefix under `/t/{tenantId}` for login routing. |
| `audienceRule` | `resource`, under which a token passes through the adapter only when its `aud` contains the adapter's identifier or alias, or `resourceOrRest`, under which a `rest` token also passes and is narrowed the same way. The chart refuses `resourceOrRest` for `protocol: mcp`, because MCP's token rule forbids it. |
| `audienceAliases` | Client IDs that an identity provider without RFC 8707 support writes into `aud` in place of the identifier. The chart refuses the REST or playground client ID and an alias that another registration lists. |
| `operations` | The `operationId`s the adapter may call. |
| `capabilities` | The request-capability classes the adapter may use. |
| `scopesSupported` | The `tools:` scope values the adapter's metadata publishes. |
| `roleCeiling` | The highest role honoured on the adapter's requests, `user` by default. |
| `crossUserReads` | Whether the adapter may read other users' sessions that the caller's role permits, `false` by default. |
| `binding` | `attested` or `header`, the way a forwarded request names the registration (O13). |
| `peer` | The identity in the adapter's client certificate, a SPIFFE ID or a DNS SAN, required under `attested`. |
| `trustForwardedFor` | Whether the gateway reads `X-Forwarded-For` from this peer. |
| `senderConstrained` | Reserved for a later release (**Sender-constrained tokens.** below). The chart accepts it only with `peer`. |
| `webhookTargets` | Exact URL prefixes that a narrowed request with an `adapter-only` token may name as a webhook target. |
| `allowedOrigins` | The browser origins the adapter accepts. |
| `maxStreamsPerSubject` | The cap on open event streams per subject through this adapter (O13). |

**Eligibility and capability tags [design].** Lenny's OpenAPI document marks each operation that an adapter may call with `x-lenny-adapter-eligible: true`, and an unmarked operation is ineligible. Each eligible operation carries `x-lenny-scope`, from which a registration's `scopesSupported` is checked. Each request field that grants a capability carries `x-lenny-capability` with one class: `webhook` (`callbackUrl` and webhook subscriptions), `credential-use` (a plan's `onRequest` `userCredential` binding entries, as `0151-user-credential-delivery` UC-3 **Requests through a protocol adapter.** states; a `poolAttach` binding is outside the class and attaches through any adapter, because the operator configured its VCS pool to act as the user and the request is authenticated as that user, so no post-chain check reads it), `vcs-write` (git clone write leases), `delegation` (`delegationLease`), `exec-setup` (`setupCommands`, `env`, and `runtimeOptions`), `isolation-select` (`pool` and `isolationProfile`), or `workspace-content` (inline files and uploads). Tool-use, harness, and write approvals are separate operations, so a registration lists each kind it answers. A registration that names an ineligible operation fails at chart render and at gateway load. Token exchange at `/v1/oauth/token`, both playground mints, the impersonation mint, the identity-source routes, `/v1/admin/*`, SCIM, credential and user-link management, and tenant usage and metering reports are never eligible. Every other operation outside the adapters' needs, such as derive, replay, evaluation, and retention extension, stays ineligible until a proposal marks it. Each first-party adapter's subchart generates its registration's `operations` and `capabilities` from the adapter's tool or method catalogue at build time.

**Audience classification [design].** After the signature and issuer checks, the verifier classifies each token by its `aud` alone, as `rest`, `adapter-only`, or `mixed` ("Terms"). Audiences match exactly, in the canonical form of R9, with no prefix match. A per-tenant identifier admits a token only on a request whose resolved tenant equals the identifier's tenant, and a bare identifier is accepted only from the deployment identity source.

**Narrowing [design].** A forwarded request names one adapter resource, its effective audience:

- Under `binding: attested`, the adapter sends the request to the adapter listener with its client certificate, and the registration whose `peer` matches the certificate gives the effective audience. A `Lenny-Resource` header that names another resource answers `400 VALIDATION_ERROR`. An `adapter-only` token of an attested registration that arrives on the public listener answers `401 TOKEN_INVALID`.
- Under `binding: header`, the adapter sends `Lenny-Resource: <canonical identifier>`, and that identifier is the effective audience.
- A request with more than one `Lenny-Resource` header answers `400 VALIDATION_ERROR`.
- The token's `aud` must contain the effective audience or one of its aliases, and under `audienceRule: resourceOrRest` may instead be a `rest` token. Otherwise the request answers `401 TOKEN_INVALID` with that resource's challenge.
- An `adapter-only` token on a request that names no adapter resource answers `401 TOKEN_INVALID`.

Narrowing only removes authority. A `rest` or `mixed` token on a narrowed request takes the adapter's authority, and no header or certificate adds authority to any token.

**Evaluation [design].** The authority of a narrowed request is the intersection of the caller's roles, the token's `tools:` scopes where the identity provider issues them, and the registration's `operations`, `capabilities`, and `roleCeiling`. Each request is evaluated against its own registration, and no request receives the union of several registrations' sets. Under the default ceiling `user`, a narrowed request reaches the caller's own sessions alone, a cross-tenant filter is refused, and other users' sessions are readable only under `crossUserReads`. `platform-admin` is never honoured through an adapter, at any ceiling. An operation outside the set, or a request field of a class outside the set, answers `403 OPERATION_NOT_PERMITTED_FOR_RESOURCE`.

**Enforcement [design].** Every route is registered through one helper that binds its `operationId` at registration, and the leaf handler enforces the narrowed authority, so every router and every public route that verifies its own token applies the same check. A route registered without an `operationId` is denied to every narrowed request. Before routing, the authentication middleware applies a coarse prefix gate to narrowed requests and `adapter-only` tokens, refusing `/v1/admin/`, `/v1/oauth/`, `/v1/playground/`, and `/playground/`. The operation and capability check runs before the ownership lookup, body validation, and idempotency replay. A narrowed request is normalized strictly: `HEAD` maps to the operation of `GET`; `OPTIONS`, `CONNECT`, and `TRACE` are refused; a trailing slash is refused; `/t/{tenantId}` is stripped once; a non-canonical path answers `400 VALIDATION_ERROR` with no redirect; a path parameter that is `.` or `..`, or contains `/`, after unescaping is refused; and a version prefix other than `/v1` is denied. Ingress strips method-override headers from every request.

**Minting refusals [design].** Token exchange at `/v1/oauth/token`, under every grant and with an `adapter-only` token as `subject_token` or `actor_token`, refuses an `adapter-only` token and every narrowed request. So do `POST /v1/playground/token`, the playground's cookie exchange, and the impersonation mint, each with `403 OPERATION_NOT_PERMITTED_FOR_RESOURCE`. `lenny-ops` refuses an `adapter-only` token on every route with `401 TOKEN_INVALID`. The Token Service reads no adapter identifier from the registry, so it never mints a `lenny-gateway` token from an adapter's token. A narrowed request forwarded between gateway replicas over `CH-HOLDERFORWARD` carries its effective audience, and the coordinating replica trusts that value only from a peer that presents a gateway replica certificate.

**Refusal code [design].** §15.1's catalog gains `OPERATION_NOT_PERMITTED_FOR_RESOURCE`: HTTP `403`, category `POLICY`, `retryable: false`, with `details.resource` naming the effective audience and `details.operation` or `details.capability` naming what was refused. The response carries no `insufficient_scope` challenge, because a broader scope does not lift a registration's limit.

**Streams [design].** An event stream closes at its bearer's `exp` and at the revocation of its `jti`, after the final `stream_closed` frame of "RO-1", and the adapter resumes with the client's refreshed bearer and `Last-Event-ID`.

**Webhooks [design].** R6 states the rules: creating a subscription, `callbackUrl` included, uses the `webhook` capability; an `adapter-only` token names only a target under its registration's `webhookTargets`; a subscription that a narrowed request creates lives at most `webhooks.maxRestrictedLifetimeSeconds`; each subscription records `azp` and the effective audience; delivery stops while the owner is disabled; and the owner lists and deletes subscriptions by the client that created them. `webhooks.internalTargets` holds exact URL prefixes, and the gateway's NetworkPolicy admits egress to the push relay by pod selector.

**Idempotency [design].** R5 states the key scope: tenant, subject, effective audience, `azp`, method, route template, path parameters, and key.

**Rate limits and stream caps [design].** The adapter is a rate-limit dimension: Lenny's limits count per registration and per subject and registration, beside tenant, user, and session. `maxStreamsPerSubject` caps the open event streams of one subject through one adapter, and a stream above the cap answers `429`. Before signature verification the gateway refuses a bearer longer than 16 KiB, one whose `exp` has passed, and one whose `iss` names no configured issuer, so a flood of forged tokens costs no signature check. A per-client-IP limit reads the client address as **The adapter hop.** states. Each adapter bounds the REST calls one protocol request makes, and its specification states the bound.

**Caching [design].** Lenny answers every narrowed request with `Cache-Control: no-store` and `Vary: Authorization, Lenny-Resource`, and an adapter keeps no response cache across bearers (ROR-3).

**Audit [design].** The audit record of a narrowed request carries the matched `aud`, the effective audience, the token's `azp` or `client_id`, its `jti`, the attested registration when the request arrived on the adapter listener, and R14's declared protocol. Refusals with `OPERATION_NOT_PERMITTED_FOR_RESOURCE` are audited with sampling, and a metric counts every one by registration and operation.

**The adapter hop [design].** The gateway serves a dedicated adapter listener that requires a client certificate. cert-manager issues each adapter's certificate from the cluster CA of [§10.3 mTLS PKI](../../spec/10_gateway-internals.md#103-mtls-pki), with the identity the registration's `peer` names. A NetworkPolicy admits each adapter's pods to the adapter listener and admits nothing else to it. Ingress strips every `Lenny-*` and `X-Forwarded-*` header a client sends before it adds its own. The gateway trusts `X-Forwarded-For` only from ingress and from attested adapters whose registration sets `trustForwardedFor`, and the audit record names the attested registration.

**External origins [design].** An adapter registered with `publicBaseUrl`, such as `https://a2a.acme.com`, has its own resource identifiers on that origin, and the gateway serves their RFC 9728 documents through the origin's ingress route. Its registration's operations, capabilities, and role ceiling apply as on the gateway's origin. Revision 1 let an adapter on another host forward any token whose audience the client API accepts; that rule leaves, because such a token carries REST authority. An operator who deploys a third party's adapter registers it on an external origin, so that the adapter's responses never share an origin with the client API or the playground.

**Identity providers without RFC 8707 [design].** Where an identity provider does not write the requested `resource` into `aud`, the operator configures a resource in the provider that maps to the adapter's identifier. Only when the provider offers no such mapping does the registration list a client ID dedicated to that adapter in `audienceAliases`. Lenny's documentation of the identity provider contract states that refresh tokens issued to public clients rotate, because an adapter never sees a refresh token and a leaked one outlives the access tokens an adapter forwards.

**Sender-constrained tokens [design].** A DPoP token (RFC 9449) or a certificate-bound token (RFC 8705) cannot pass through an adapter, because its proof binds to the client's connection to the adapter and the gateway cannot verify it. The gateway refuses a token that carries a `cnf` claim on a narrowed request with `401 TOKEN_INVALID`. The registry reserves `senderConstrained` for a later release that verifies the proof at the edge and carries the result over the attested hop.

**Same-origin browser rules [design].** An adapter on the gateway's origin shares that origin with the client API and the playground in a browser. An adapter therefore serves no HTML; answers every download and proxied response with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, and `Content-Security-Policy: sandbox`; validates `Origin` against `allowedOrigins` and `Host` against its configured base; sends no credentialed CORS response; and exposes `WWW-Authenticate` to scripts. R13's URLs are served on the download origin.

**Adapter obligations [design].** Each adapter meets these rules, and the conformance kit checks each first-party adapter against them ("RO-6"):

- It never logs or persists an `Authorization` header, an `x-api-key`, a cookie, or a protocol session identifier, holds a bearer only for the life of the request that carried it, and never puts one in a URL.
- It builds each REST request from scratch and forwards only the bearer, `Lenny-Resource`, `Lenny-Client-Protocol`, `Idempotency-Key`, `Last-Event-ID`, and the body it composed.
- It retries a mutation only with an `Idempotency-Key`.
- It validates every identifier it places in a path against Lenny's identifier grammar, escapes it with `url.PathEscape`, and follows no redirect from Lenny.
- It builds metadata and challenge URLs from its configured `publicBaseUrl`.
- In the compose stack it binds loopback, and the development playground's mint is unreachable through it.

**Why the MCP rule holds [inference].** The token's audience is the adapter's identifier, which the client named in its `resource` parameter. The gateway accepts the token only on a request narrowed to that identifier and limits the request to the adapter's registered operations, capabilities, and role ceiling, so the client API serves as one interface of the adapter's resource. The tokens the reviews found an adapter could transit fail at the gateway: a REST-audience token and a playground bearer lack the effective audience under `audienceRule: resource`, and another adapter's token lacks it as well. No narrowed request or adapter token mints a token for any other service, so the confused-deputy case of MCP's security guidance does not arise.

**Login routing [design].** TS-7's per-tenant resource URLs become `https://<host>/t/{tenantId}/mcp`, served by the MCP adapter, which forwards to `/t/{tenantId}/v1/...` on the adapter listener. The client API's `403 TENANT_PATH_MISMATCH` and per-tenant metadata apply unchanged.

**Provider credentials [design].** The Anthropic adapter accepts a Lenny bearer in `Authorization: Bearer` or `x-api-key`, forwards it as `Authorization: Bearer`, refuses a value starting with `sk-ant-` without echoing it, as AM-2 states, and refuses a request whose `Authorization` and `x-api-key` differ. The gateway's auth middleware reads `Authorization` alone.

### RO-5 Packaging, versioning, and deployment

**Repositories [design].** The Lenny project creates one public repository per first-party adapter under the project's organization, beside the client SDK repositories that §15.6 names: `lenny-adapter-mcp`, `lenny-adapter-a2a`, `lenny-adapter-openai-chat`, `lenny-adapter-open-responses`, and `lenny-adapter-anthropic-messages`. Each holds its specification, its designs (O8), its code, its tests, its image build, and its Helm chart, and publishes a container image and a chart per release. The adapters carry Lenny's licence and governance.

**Specification per repository [design].** Each adapter's specification states its protocol versions with the URL and check date of each, as MP-8 requires; its mapping from the protocol onto the client API; its identifiers; its error table; and its limits. MP-8's rule that a version claim without a URL and a date is a defect applies there.

**Versions (O7 (a)) [design].** Each adapter has its own semantic version. Each release names the oldest Lenny release whose client API it requires, and refuses to start against an older one: at start the adapter reads `info.version` from `GET /openapi.json` and exits with a message naming both versions. The umbrella chart pins, per Lenny release, the adapter chart versions that passed the conformance kit against it. An adapter adopts a protocol revision in its own release; the MCP adapter applies MP-8's window, counted in its own releases.

**Subcharts [design].** `charts/lenny/Chart.yaml` lists each adapter chart as a dependency with `condition: adapters.<name>.enabled`; Helm enables or disables a subchart by such a condition in the top parent's values **[external]**. The defaults are `adapters.mcp.enabled: true` and `false` for `a2a`, `openaiChat`, `openResponses`, and `anthropicMessages`. Each subchart renders a Deployment, a Service, a PodDisruptionBudget, a cert-manager `Certificate` for the adapter's client certificate, its default registration for `auth.adapters[]`, a NetworkPolicy that admits ingress from the ingress controller and egress to the gateway's adapter listener alone, and, where the adapter holds a key, a Secret reference. The A2A subchart's push relay also has egress to port 443 on the internet, excluding the cluster's CIDRs and the cloud metadata addresses. Each adapter runs with the restricted Pod Security Standard and no service account token.

**Routing [design].** The umbrella chart's ingress templates, and its Gateway API routes where the operator uses them, add one path route per enabled adapter on the gateway's host, and the gateway's own route catches the rest:

| Adapter | Paths |
| :-- | :-- |
| MCP | `/mcp`, `/t/{tenantId}/mcp`, and their sub-paths |
| A2A | `/a2a` and its sub-paths, `/.well-known/agent-card.json`, and the push relay's in-cluster Service |
| OpenAI Chat Completions | `/v1/chat/completions` |
| Open Responses | `/v1/responses` and its sub-paths |
| Anthropic Messages | `/v1/messages` and its sub-paths, `/v1/files` |
| One enabled provider adapter | `/v1/models` and its sub-paths |
| Token Service | `/oidc/`, `/identity/`, and `/exchange/` with their sub-paths, the per-tenant issuers' discovery and key set routes, which the Token Service serves rather than the client listener ([`0143-service-account-credentials`, SA-3](../0143-service-account-credentials/change.md#sa-3-the-issuerexchange-source), **Discovery and key set routes.**) |
| Gateway | Everything else on the gateway's host, `/.well-known/oauth-protected-resource` on each registered external origin, and every path on `downloads.host` |

Every provider adapter serves `GET /v1/models` in both the OpenAI and the Anthropic format, chosen by `anthropic-version` or `?adapter=` as AM-9 states, from R8. The chart routes the path to the first enabled provider adapter in the order Anthropic Messages, Open Responses, Chat Completions, so no ingress needs a header match. The adapter routes disable request and response buffering, as the stream routes of the gateway already do.

**External origins [design].** An adapter registered with `publicBaseUrl` gets its own ingress host instead of a path route, and that host also routes `/.well-known/oauth-protected-resource` to the gateway ("RO-4").

**Third-party adapters [design].** A third party builds an adapter the same way and deploys it with its own chart. The operator registers it in `auth.adapters[]`, preferably on an external origin, and Lenny accepts its clients' tokens only under that registration ("RO-4"). Lenny runs no conformance gate on a third party's adapter; the conformance kit is how a third party shows conformance.

### RO-6 Conformance

**What replaces §15.2.1 [design].** Rule 1 holds by construction, because one API exists. Rules 2 and 4 become R7. Rule 3 moves to §15.1. Rule 5 and `RegisterAdapterUnderTest` become the adapter conformance kit, and the production gate of `POST /v1/admin/external-adapters/{name}/validate` leaves with the endpoint.

**The kit [design].** Lenny's repository publishes `lenny-adapter-conformance`, a Go package and a binary versioned with Lenny. It drives a deployed Lenny (the compose stack or Kind) through an adapter under test, using a driver interface that each adapter implements: "perform this operation through your protocol", such as create a session, send a message, answer an input request, cancel, or resume a dropped stream. It checks each outcome through REST, so the expected result is stated once, against Lenny's state:

- Lifecycle: create, send, suspend, resume, close, and cancel reach the session states SL-1 states; every externally visible state sequence of §15.2.1's matrix is driven.
- Errors: every class of §15.2.1's matrix, the session-creation rejection family included, keeps its `code`, `category`, and `retryable` in the adapter's protocol mapping, which the adapter declares in a table the kit reads.
- Ownership: a second user's request for the first user's identifiers is answered as not found, and no adapter identifier reveals a session's existence.
- Idempotency: a protocol retry produces one message (R5).
- Streams: a stream dropped after an event resumes from the client's cursor on another replica with no loss, an evicted cursor yields one gap signal, and a coordinator handoff yields the synthesized frames before any gap.
- Statelessness: every step alternates between two adapter replicas, and killing a replica mid-stream loses only that stream.
- Credentials: every REST call the gateway receives from the adapter carries the client's bearer, and the audit record names the client's subject and the R14 value.
- Authorization: a token for the REST audience, a playground bearer, and another adapter's token are each refused through the adapter, and the challenge names the adapter's metadata URL. An operation outside the registration, a request field of a capability class outside it, a request above the role ceiling, and another user's session each answer as "RO-4" states, with `OPERATION_NOT_PERMITTED_FOR_RESOURCE` where it applies. The adapter's token is refused at token exchange, at both playground mints, and at `lenny-ops`. A stream through the adapter closes at the token's `exp` and resumes with a refreshed bearer.
- Adapter obligations: the kit's request recorder finds no bearer, `x-api-key`, or cookie in the adapter's logs or in any URL it requests; every REST request carries only the headers "RO-4" lists; a mutation retried after a dropped response carries an `Idempotency-Key`; an identifier with `/`, `..`, or percent-encoding is escaped or refused; a redirect from a stub of Lenny is not followed; and a download or proxied response carries the attachment, `nosniff`, and sandbox headers.
- Pagination: a multi-page listing through the adapter yields the same set as REST.

A strict mode of the kit fails a run on any of these negative cases, and every first-party adapter runs it.

Each adapter repository adds its protocol's own conformance tests, such as MCP schema validation of both eras or the official Anthropic SDKs against the adapter, as MP and AM state them.

**Where it runs [design].** Each adapter repository runs the kit in CI against Lenny's latest release and against Lenny's main branch. Lenny's release pipeline runs the kit for every first-party adapter version it intends to pin, in the `e2e_kind` tier, and a failure blocks the release or the pin.

### RO-7 Lenny's own clients

**Client SDKs [design].** The Go, Python, and TypeScript client SDKs drop their MCP clients (`mcp.go`, `mcp.py`, `mcp.ts`). They wrap REST and the event stream: a send returns the receipt with R1's `seq`, a stream opens at that cursor, a dropped stream reconnects with `Last-Event-ID` and surfaces `gap_detected`, and helpers read R2, R3, and R4. §15.6 lists the Python SDK, which §18.19 already names **[source]**, and states that the SDKs are generated from the OpenAPI document with hand-written streaming.

**`lenny session` [design].** Every session command maps to REST:

| Command | Mapping |
| :-- | :-- |
| `lenny session new --runtime <name> [--attach] [--workspace <dir>] [--file <path>]...` | `POST /v1/sessions/start`, or with a workspace `POST /v1/sessions`, uploads, `/finalize`, and `/start`; with `--attach`, the event stream from the receipt's `seq` |
| `lenny session attach <sessionId>` | The event stream, resuming with `Last-Event-ID` |
| `lenny session send <sessionId> <message>` | `POST /v1/sessions/{id}/messages`; attached, the stream from the receipt's `seq` |
| `lenny session interrupt <sessionId>` | `POST /v1/sessions/{id}/turns/{turn}/interrupt` for the session's open turn (R19) |
| `lenny session suspend <sessionId>` | `POST /v1/sessions/{id}/suspend` (SL-4) |
| `lenny session close <sessionId>` | `POST /v1/sessions/{id}/close` (SL-7) |
| `lenny session cancel <sessionId>` | `DELETE /v1/sessions/{id}` |
| Answers to prompts while attached | The elicitation respond and dismiss routes, and the approve and deny routes |

`lenny-ctl install`'s smoke test creates a session and reads its turn through REST.

**Web playground [design].** The chat pane sends with `POST /v1/sessions/{id}/messages` and reads the event stream with `fetch` and a streaming body, carrying the bearer in `Authorization`, because `EventSource` cannot set the header; this is MP-9's approach applied to the REST stream. Stop calls R19 for the open turn and falls back to the suspend route on `INTERRUPT_UNSUPPORTED` or `INTERRUPT_TIMEOUT`, Suspend and Cancel call the REST routes, prompts use the elicitation and approval routes, and a browser close sends `DELETE` with `keepalive: true`. The raw-frame inspector shows SSE frames. The "Copy as client SDK snippet" button emits REST SDK code that compiles against the current SDKs. `POST /v1/playground/token` mints the same bearer it mints today, and §27 calls it a client API bearer. The WebSocket `/mcp/v1/ws`, its `Sec-WebSocket-Protocol` carrier, close code `4401`, and `lenny_playground_ws_connect_total` leave, as MP-9 already removes them.

### RO-8 The MCP adapter

The MCP adapter carries MP-1 to MP-4, MP-8's window, and the client half of MP-7 as its own specification, with these changes for a stateless program in front of REST **[design]**.

**Transport and eras.** It serves `2026-07-28` statelessly and `2025-11-25` through `initialize` with O5's signed identifier, validates `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, and `Origin`, implements `server/discover`, and refuses other versions as MP-1 states.

**Tools.** Its catalogue maps MCP tools onto `operationId`s (O6 (b)), with the names MD-23 sets: `create_session`, `create_and_start_session`, `upload_files`, `finalize_workspace`, `start_session`, `attach_session`, `send_message`, `suspend_session`, `get_session_status`, `get_task_tree`, `get_session_logs`, `get_token_usage`, `list_artifacts`, `download_artifact`, `close_session`, `cancel_session`, `resume_session`, `list_sessions`, `list_runtimes`, `respond_to_elicitation`, and `dismiss_elicitation`, with the retraction tool that MD-7 generates from the retraction route. Uploads arrive as base64 and leave as multipart REST uploads under REST's limits. Client tool members are tool arguments generated from the REST definitions, as CT-6's MCP row states.

**Streams.** `attach_session` streams the event stream, translated into MP-2's and MD-21's projections, with `<sessionId>:<seq>` as the SSE `id` on `2025-11-25`. A stateless-era client resumes by calling `attach_session` with `resumeFromSeq`.

**Tasks (D4).** A `send_message`, or a `create_and_start_session` or `create_session` that delivers a first message, returns a task whose `taskId` is `<sessionId>.<messageId>`, after the message's receipt, so a `tasks/get` for it resolves at once, as the extension requires **[external]**. A create call that delivers no message returns no task. `tasks/get` reads R2, R3, and R4:

| Message, turn, and session | Task status |
| :-- | :-- |
| The message is pending or held, or its turn runs with no pending input of that turn | `working` |
| The turn runs and holds an elicitation or approval of that turn (R4), or an open client tool call of that turn (R22) | `input_required`, with `inputRequests` keyed by elicitation ID or tool call ID |
| The session is `suspended` or `blocked` while the message is pending or its turn is open | `working`, with `lenny/paused: true` under `_meta` |
| The session is `resume_pending` or `resuming` | `working`, with `lenny/resuming: true` under `_meta` |
| The turn ended `completed` | `completed`, with the output from the message's consumption position as content and the turn resource in `structuredContent` |
| The turn ended `failed` or `runtime_exit` | `failed`, with Lenny's error envelope |
| The turn ended `interrupted`, or `cut` by a suspension | `cancelled` (O4) |
| The turn ended `cut` for another cause, such as the idle clock | `failed` with the cause |
| The message was retracted | `cancelled` |
| The message ended without consumption (`target_terminated`, expiry) | `failed` |

`tasks/update` answers an input request through the respond, approve, or deny route, and an open client tool call through R22's answer route. `tasks/cancel` follows O4: it retracts the task's message while the message is pending ([MD-11](../0135-message-delivery/change.md#md-11-retraction)); once the message's turn runs, or when the retraction finds the message already consumed, it calls R19 for that turn, and on `INTERRUPT_UNSUPPORTED` or `INTERRUPT_TIMEOUT` it calls `POST /v1/sessions/{id}/suspend` as its fallback (O11); and it reports the task `cancelled`. A task that is already terminal keeps its status. `notifications/tasks` through `subscriptions/listen` is served by polling R2 and R3 for the tasks the client names, until R10 exists (O9). An `idle`, `dormant`, or `awaiting_client_action` session has no open task, as MP-4 at revision 5 and SL L32 state.

**Elicitation and links.** MP-3's forms are produced from R4 and the event stream: `elicitation/create` on `2025-11-25`, input requests on `2026-07-28`, and, for `403 LINKS_REQUIRED` at creation, `URLElicitationRequiredError` or an input-required result, after which the client's retry calls REST again and the link check runs again.

**Progress and resources.** `notifications/progress` carries the newest top-level activity's `summary` when the attach request has a `progressToken` (MD-21). `resource_link` names an R13 URL on the download origin, so a client fetches it without the bearer. `resources/read` serves the same file by proxying the REST download with the caller's bearer, under the response headers of "RO-4".

**Discovery.** `list_runtimes` maps to `GET /v1/runtimes`.

**Hand-off.** A `send_message` to a session that answers `409 SESSION_HANDED_OFF` is sent to the successor under "RO-3" **Hand-off**, and the task it returns is `<successorId>.<messageId>`, with `lenny/successorSessionId` under `_meta`, so the client names the successor in its later calls. `attach_session` continues on the successor's stream after a `handoff` event and sends a notification naming the successor. `tasks/get` for a task of the ended session reads the session's own records, so a task the hand-off left open ends as its turn ended.

### RO-9 The A2A adapter

The A2A adapter serves A2A `1.0` in the HTTP+JSON, JSON-RPC, and gRPC bindings, and its specification replaces §21.1 **[design]**.

**Cards.** It serves one agent card per runtime, at a per-runtime base URL under `/a2a/runtimes/{name}`, composed from the runtime's `agentInterface`, its own URLs, and the deployment's security schemes; `/.well-known/agent-card.json` serves the card of the runtime the operator names in `a2a.defaultRuntime`, or `404` without one. It reads public runtimes from R8 and extended cards with the caller's bearer. Lenny no longer generates an `agent-card` metadata entry, because a card generated at write time cannot name the adapter's URL or the identity provider **[source]**; `agentInterface` stays as runtime metadata.

**Tasks (D4).** `SendMessage` and `SendStreamingMessage` create a session for a new context or send to the context's session, with R5's key from the A2A `messageId`; the task is `<sessionId>.<messageId>`. The states map as the MCP adapter's do: `submitted` while pending, `working`, `input-required` for pending input of the task's turn, `completed` or `failed` at the turn's end, `canceled` for a task cancelled under O4, through R19 with the MCP adapter's fallback to the suspend route (O11), and `rejected` for a refusal at creation. Under O10 the A2A adapter's specification states and the adapter implements `input-required`: a pending elicitation of the task's turn appears with its schema in a data part, and the client's reply goes to R4's respond route. `CancelTask` follows O4 as the MCP adapter's `tasks/cancel` does. A message with `taskId` that answers an `input-required` task answers its pending input; any other message is a new message and a new task. `SubscribeToTask` sends the current task and streams from R1's `lastSeq`. A message to a context whose session ended by a hand-off goes to the successor under "RO-3" **Hand-off**: a `contextId` that is the session ID resolves through `successorSessionId`, and one stored as the label `a2a-context` resolves to the session of that label without a successor, because the successor keeps its root's labels. The `contextId` the client holds stays valid, and the adapter creates the context's push subscriptions on the successor when it first follows it. A missing link at creation answers with a `Message` carrying the link URLs, because R11 is deferred (O9). File parts carry R13 URLs.

**Push through webhook subscriptions.** `CreateTaskPushNotificationConfig` creates an R6 subscription on the task's session whose target is the adapter's push relay, whose kinds are those the task's updates need (`message_state`, `turn_end`, `output`, `activity` coalesced to one per second, and `terminated`), and whose `subscriberData` holds the client's push config: the URL, the token, the `AuthenticationInfo`, the config ID, and the task ID. The relay draws a nonce per subscription, sets the subscription's `secret` to HKDF(adapter key, "relay" ‖ nonce), and seals the push config with an AEAD under its relay key, with the tenant, the session, and the nonce as associated data; the nonce travels in clear beside the sealed config (O13). The relay's URL lies under the A2A registration's `webhookTargets`, and the subscription's lifetime is capped by `webhooks.maxRestrictedLifetimeSeconds` (R6). On each delivery the relay derives the secret from the nonce and verifies Lenny's signature, opens the subscriber data only when the delivery's tenant and session match its associated data, drops events of other tasks, translates the event into an A2A `StreamResponse`, posts it to the client's URL with `Authorization: <scheme> <credentials>`, and returns the client's status to Lenny within the delivery timeout, so Lenny's retries and its undelivered-event log cover the whole path. The relay validates the client URL against SSRF as A2A asks before it registers the subscription and again before each post: the URL is HTTPS, the relay resolves the host once per post and connects to the checked address, and it follows no redirect. `Get`, `List`, and `Delete` map to R6's routes. Lenny stores no A2A body format and no third-party credential in clear text.

**Context.** A client-chosen `contextId` is stored as the session label `a2a-context`, found through `GET /v1/sessions?labels=`. `ListTasks` within a context lists the session's client messages; across contexts it lists the labelled sessions first (O9).

### RO-10 The provider adapters

The provider adapters carry the protocol parts of AM, CT-6, MD-8, and §15's single-shot and conversation-session rules as their own specifications. Each request is one turn, and each adapter creates sessions with `inputPolicy: decline` (R12), so an agent elicitation is answered `decline` at once (R12) **[design]**.

**Common rules.**

- `model` names a runtime, an alias, or `environments/{name}/{model}`, which becomes the creation's `environment`.
- A request is served by sending its new input with `conversation` (R15), its client tools (CT-1), and `Idempotency-Key`, then reading the event stream from R1's `seq` until `turn_end` for the turn that consumed the message, or until a `tool_call` event of that turn, and cutting the output at the message's consumption position (MD-8). A turn no client request caused never appears in a response (MD O3).
- Client tool calls follow the provider mapping of 0122's blocking interface (decision 23 of 0166). The calls of the request's turn end the response as the provider's tool use, with the calls of one labelled group in one response and an unlabelled call in a response of its own, as CT-5 of 0122 states, while the turn stays open. The caller's next request carries the results: the adapter finds the session as for a follow-up, posts each result through R22's answer route, and reads the stream on from the `tool_call` event, so the next response continues the same turn. When the calls are no longer open, because their hold passed or the session was recovered, the request runs cold, with the calls and their results in the new session's history under CT-7. A caller that never returns lets the calls' hold pass. A provider adapter sets `clientToolTurns: own` on each session it creates, as CT-5 of 0122 states (decision 48 of 0166).
- A dropped client connection does not end the turn, because the turn runs in Lenny and the send has returned; the adapter's retry handling below reattaches.
- `usage` comes from R3, with the summed `input_tokens` of AM O12.
- `GET /v1/models` answers from R8 in both formats ("RO-5").
- The response headers carry `lenny-session-id` and `lenny-runtime-revision` from the REST responses.

**Sessions (O3).** A provider adapter creates ordinary sessions and keeps no record of which session it may continue; the session's state and the lookups below decide it.

- After its turn a session is `idle` with its pod, and after its idle timeout it becomes `dormant`, which checkpoints the workspace and releases the pod (SL-6). A later message wakes a `dormant` session through resume admission and a restore (SL-5). A `dormant` session expires after `maxSuspendedSessionSeconds`, seven days by default.
- An adapter may shorten a session's idle timeout with `timeouts.maxIdleSeconds` on creation, from its setting `sessions.idleTimeoutSeconds`, unset by default. The most-restrictive timeout resolution lets the value only shorten the pool's `sessionPolicy.maxClientIdleSeconds`. An operator who wants provider conversations to keep their pods longer lengthens the pool's idle timeout.
- A `one_shot` runtime's end-of-turn frame completes its session under the completion rule of MD-22, so the next request of that conversation fails R16 and runs cold.
- A session whose effective `checkpointPolicy` is `sealOnly` or `none` expires at its idle timeout instead of becoming `dormant` (SL L30), so a follow-up after that runs cold.
- Each adapter routes a follow-up to its session: Open Responses by `previous_response_id`, and Chat Completions and Anthropic Messages by conversation fingerprint. The send carries `continues` (R16), and a `412` sends the request cold.

**Conversation fingerprint.** Chat Completions and Anthropic Messages carry the whole conversation on every request. The adapter computes a keyed digest, AM-5's digest with the adapter's fingerprint key, over the normalized request: the model, `system` or the system messages, `tools`, `tool_choice`, the `lenny` object without labels, `metadata.user_id` for Anthropic, and the messages. Tenant and owner are not in the digest, because R17 scopes the lookup to the caller's tenant and subject.

- On every send, `clientRef` is the fingerprint of the whole request's messages.
- Join: before sending, the adapter looks up the request's own fingerprint. A message found with a running turn is a retry of a running request, and the adapter streams that turn without sending; this is AM-5's in-flight join, and it holds from the moment the first request's message is written.
- Warm: for a request whose last assistant message is at index `k`, the adapter looks up the fingerprint of `messages[0..k-1]`, which is the previous request's reference, reads the turn that consumed the found message, and checks that the client's `messages[k]` equals the assistant message the adapter returned for that turn, after AM-5's normalization. When they match, it sends the new input to that session with `continues` (R16), waking the session when it is `dormant`; a `412` or a mismatch is a cold turn.
- Cold: a new session with the history in `conversation.entries` and the final input as new input.

**OpenAI Chat Completions.** Requests continue and start sessions under the fingerprint rules above. A response that carries client tool calls ends at their `tool_call` event, and the next request carries their results under the common rule for client tool calls above, which replaces the turn-ending exchange of CT T4.

**Open Responses: the turn resource replaces the response records.** A response ID is `<sessionId>.<messageId>` of the message the request sent, and `GET /v1/responses/{id}`, an OpenAI extension the Open Responses specification lacks, reads R2 and R3. The session row keeps no `Responses` records and no `ContinuationParentID`:

- A request without `previous_response_id` creates a session and labels it `responses-continued-from` with nothing.
- A request with `previous_response_id` `S.m` sends to `S` with `continues: m` (R16), waking `S` when it is `dormant`. An accepted send is a warm turn. A `412` is the cold path: the adapter reads the conversation context, which is `S`'s transcript up to the end of `m`'s turn (R3's `lastSeq`), preceded by the context of the response named in `S`'s `responses-continued-from` label, back to the first session of the conversation, stopping at a session already visited or one the caller cannot read, and creates a new session labelled with `S.m`, with that context as history.
- An identical retry of a running continuation joins the running turn: the adapter's `Idempotency-Key` is a digest of the request, and R5 returns the original receipt (CT O5).
- The history entry order of CT-7 "Order of history entries" is the adapter's to keep when it builds the cold context.

**Anthropic Messages: client references replace the digest tables.** Requests continue and start sessions under the fingerprint rules above.

- A cold session carries `metadata.user_id` as the label `anthropic-user-id`.
- `request-id` is `<sessionId>.<messageId>`, so support finds the session and turn behind it through R2, which replaces the `messages_requests` table.
- The tables `conversation_turns` and `messages_requests`, `anthropicMessages.digestKey` as a gateway secret, and the forward of `anthropic-version` between replicas leave Lenny: the references live on messages and are erased with them, the key is the adapter's, and the REST send forwards internally under §29.3.

### RO-12 What simplifies

- **One creation path for clients.** Every client-created session enters through `POST /v1/sessions` or `POST /v1/sessions/start`; the MCP creators and `BindSingleShot` leave TS-3's list of root creators, F-13.3.26's impersonation rule has one surface, and the link check of CA-4 has one placement.
- **No session state per protocol.** The session row loses the response records; the gateway loses the handshake record, the digest tables, and the request records. Erasure under §12.8 names no protocol table.
- **No outbound dispatcher.** The gateway writes events to the replay buffer and the event relay; readers pull them. Webhook deliveries are the only push.
- **One stream contract.** The resume, gap, handoff, and keepalive rules are stated once, for the event stream.
- **One test surface in Lenny.** The REST contract tests pin the client API; protocol tests live with their adapters.

- **Elicitation surfaces.** AM-6's and DA-7's checks of an adapter's `SupportsElicitation` become R12's `inputPolicy` on the session.
- **The playground.** It drops the WebSocket and the MCP bearer wording and uses the same calls as the SDKs.

## Limits

- **One more hop.** Every adapter request and event crosses an extra process and is re-encoded, and an attached client holds two connections. No measurement exists ("Validation owed" in `steps.md`).
- **Registered adapters only.** An adapter forwards bearers only under a registration in `auth.adapters[]`, on the gateway's origin or on an external origin the operator routes. An adapter that the operator has not registered cannot forward bearers, and Lenny offers no token exchange for it.
- **Narrowed authority.** A client that reaches Lenny through an adapter can do only what the adapter's registration lists, under the `user` role ceiling by default. An administrator works through REST, the CLI, or `lenny-ops`.
- **Sender-constrained tokens.** A DPoP or certificate-bound token cannot pass through an adapter, and the gateway refuses one on a narrowed request.
- **Stream lifetime.** An event stream ends at its bearer's expiry, so a long-attached client reconnects with a refreshed bearer at each expiry.
- **Handshake-era identifiers.** Under O5 (a) a `2025-11-25` `Mcp-Session-Id` cannot be revoked before it expires, and `DELETE` answers `405`.
- **Push relay.** A2A push adds a hop and needs the gateway to reach the relay, which R6's `webhooks.internalTargets` admits. A push config ends with its subscription at `webhooks.maxRestrictedLifetimeSeconds`, and the client then polls the task or creates the config again.
- **Creation-time authorization in A2A.** Without R11, a missing link at creation produces a `Message` and a retry where A2A would expect an `auth-required` task.
- **Cross-session listing.** Without R10, A2A `ListTasks` across contexts and MCP task notifications cost one REST call per session or per task.
- **Dormant provider sessions.** Each provider conversation leaves a session that becomes `dormant` after its idle timeout and keeps its checkpoint until it expires after `maxSuspendedSessionSeconds`, and a follow-up to it pays a restore before its turn.
- **Cold Open Responses walks.** The adapter reads ancestor transcripts through REST, one paginated read per session in the conversation.
- **Edited history runs cold.** A Chat Completions or Anthropic request whose earlier messages differ from what the adapter returned runs cold, as AM's "Limits" states, and a rotated fingerprint key sends each conversation's next request cold once.
- **A task cancel may suspend.** On a runtime without `interrupt`, or one that does not acknowledge in time, an adapter's cancel of a running task falls back to the suspend route, which suspends the session and pauses its descendants, and the next message resumes the session after a restore.
- **Protocol drift is the adapter's.** A protocol revision that needs a REST change waits for a Lenny release that carries the addition.
- **A hand-off changes the session behind a conversation.** An MCP client that names the ended session in a later call reaches the successor through the adapter, and a direct REST client follows `successorSessionId` itself. A webhook subscription stays on the session that ended (R24).

## Alternatives rejected

- **Keep MCP built in (the spike's option (a)).** It avoids the extra hop on the main interactive path, the deployment condition on the resource identifier, and the unrevocable handshake identifier. It keeps the dual-era serializers, the version window, the Tasks mapping, and their releases inside the gateway, and it saves none of the REST additions, because A2A needs them. The owner chose (b) (D1).
- **Direct webhook delivery to A2A clients.** Lenny would post A2A bodies with client-supplied `Authorization` headers, which puts A2A's body format in Lenny and stores third-party credentials there.
- **MCP metadata in Lenny's OpenAPI document.** O6 (a).
- **A digest written after the turn for Anthropic continuation.** The spike's alternative to R17 at send time: the adapter would write the reference onto the turn after it ends, which needs a write route and leaves the in-flight join to a separate mechanism. A reference written with the message serves both the join and the warm lookup.
- **Response IDs from turn ordinals.** A turn ordinal is not known when the response is created, because another session's message can open a turn first (MD O3); a message ID is known at the receipt.
- **An in-cluster adapter registry in Lenny.** It would keep the registration endpoint and a routing table in the gateway for programs the gateway no longer calls. Ingress and the umbrella chart route the paths.
- **One repository for the provider adapters.** The owner chose one repository per adapter (D3). A shared Go library is the Go client SDK.
- **A union audience check (revision 1's RO-4).** The client API accepted any of the deployment's resource identifiers, so an adapter transited tokens issued for other resources and its own tokens carried full REST authority (S1).
- **One operation set per adapter, enforced in the middleware.** The first review's operation sets, checked before routing, missed routers and self-verifying public routes and ignored request-field capabilities; the second review replaced them with leaf enforcement, capability classes, and per-registration evaluation (S1).
- **A close-after-turn option (revision 1's R18) and a rule that kept some provider sessions on their pods.** Lenny would have had to decide per revision which sessions to keep. Ordinary sessions with an idle timeout that an adapter may shorten serve the same purpose (O3).
- **Lenny suspending a session on R19's behalf (revision 2's O11 (a)).** The owner kept Lenny's behaviour unchanged: R19 refuses a runtime without `interrupt` and an unacknowledged interrupt, and the adapter falls back to the suspend route (O11).
- **A suspension for every task cancel (revision 1's O4 (b)).** A runtime that declares `interrupt` stops its turn and keeps its pod, so a suspension is needed only as the fallback (O4).
