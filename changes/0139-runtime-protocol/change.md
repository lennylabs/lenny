## Problem

> **Revision 10.** [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors under the owner's decision of 2026-11-15 ("Yes, let's drop connectors."). A statement in this section about connectors, `connector:<id>`, the connector client, connector links, `deferredToolDiscovery`, `tool_progress`, or `toolProgress` that the edits of revision 10 did not rewrite is withdrawn and kept as the record. The platform statements stand.

"Terms", after "Scope", defines the vocabulary this document uses.

A runtime talks to the adapter in its pod over several conversations today, and each has its own transport, authentication, and versioning **[source]**:

- `CH-MSGSOCK` carries the JSON Lines frames every runtime speaks. It has no protocol version and no handshake beyond the connection's nonce line ([§28.5.3](../../spec/28_communication-channels.md#2853-intra-pod), [§4.7.11](../../spec/04_system-components.md#4711-adapter-agent-security-boundary) item 1).
- `CH-RUNTIMEOPS` is a second socket for checkpoint, interrupt, and credential signals. It opens with `lifecycle_capabilities`, in which the adapter offers a `protocolVersion` string, and the runtime answers with `lifecycle_support`, which carries capabilities and no version (§28.5.3).
- `CH-MCP-PLATFORM` and `CH-MCP-CONNECTOR` are MCP servers the adapter runs on abstract Unix sockets, one for Lenny's platform tools and one per connector. A runtime authenticates to each by adding a `_lennyNonce` member to MCP `initialize` ([§15.4.3](../../spec/15_external-api-surface.md#1543-runtime-integration-levels)), and the adapter negotiates MCP versions on each.

This arrangement costs the platform and runtime authors in these ways:

- The adapter carries an MCP server, its version negotiation (MCP `2025-03-26` and `2024-11-05` today, and the `2026-07-28` changes that [`0134-mcp-protocol-upgrade`](../0134-mcp-protocol-upgrade/change.md#mp-5-intra-pod-servers) MP-5 plans), a Lenny-private nonce inside an MCP message, and one socket per connector.
- The harnesses Lenny wraps cannot reach those sockets. Claude Code documents stdio, HTTP, Server-Sent Events, and WebSocket MCP transports, and Codex documents stdio and HTTP, and neither states Unix socket support **[external]**. Connector authorization's "CA-9" therefore adds a stdio bridge to every pod.
- Nothing tells a runtime that its tool list changed. [`0126-delegation-availability`](../0126-delegation-availability/change.md#da-5-running-sessions) chose live reads with no notification (DA O4) because no carrier existed.
- What a runtime can do is stated as an integration level, Basic, Standard, or Full (§15.4.3). A level bundles unrelated abilities: a runtime that pauses for checkpoints must also accept credential rotation signals on the same socket to be "Full", and every runtime that uses a platform tool is "Standard" whatever else it does. The declared level is compared with a level observed through the MCP handshake and the `CH-RUNTIMEOPS` handshake ([§5.1](../../spec/05_runtime-registry-and-pool-model.md#51-runtime)), and nothing reports which protocol version a runtime speaks.

This design states one framed protocol between the adapter and the runtime, a handshake every runtime performs, capabilities in place of integration levels, per-session availability with change notices, and a reference MCP bridge that the runtime SDKs ship.

## Scope

**Added:**

- A handshake on every runtime connection: the runtime's `hello` with the protocol versions it speaks, its capabilities, and its name and SDK, and the adapter's `welcome` or refusal ("RP-1", D2).
- The capability catalog, its dependency rules, and a check at session bind of the session's capabilities against what the runtime offered ("RP-2", D3, O2).
- Tool calls as `tool_call` frames with a `server` member, which takes `platform` and `client`, tool listing by `list_tools` and `tool_list` frames, and cancellation by `tool_cancel` ("RP-3", D1). The `client` tool server, a call's `group` for calls made at one model step, and the `internal` attribute of a platform tool list entry carry the session primitives of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md) and the blocking interface for client tools of [`0122-client-tools`](../0122-client-tools/change.md) ("RP-3", revision 15).
- `lineage` and `tags` on `session_start`, and the capability `childEvents` ("RP-2", "RP-4", revision 15).
- The rule that a tool call has no duration a runtime may assume ("RP-3", D11). Revision 9 also added a `tool_progress` frame under a `toolProgress` capability, which revision 10 withdraws because [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors, its only producer.
- Tool connections: connections a reference bridge opens to its slot's `CH-MSGSOCK` endpoint to carry tool frames alone (O3).
- Per-session availability on `session_start` and the `availability_changed` frame, with the `client` tool server ("RP-4", D4).
- The reference MCP bridge, specified in a section of its own and shipped by the runtime SDKs, which serves the reference extension of 0166 in place of gateway-hosted delegation tools ("RP-5", D1).
- A version for the adapter-to-runtime protocol and its support window ("RP-7").
- Conformance tests per capability ("RP-8", D3).

**Changed:**

- The adapter manifest moves to `version: 2`. It loses the platform server, the connector servers, and the adapter-local tool list, and `mcpNonce` becomes `connectionNonce`. Each slot has its own manifest under session isolation ("RP-6").
- The adapter's activity window counts `tool_call` frames in flight in place of MCP calls ([§4.7.1](../../spec/04_system-components.md#471-role-and-gateway-rpc-contract) **Session seal.**, "RP-6").
- The Runtime definition declares capabilities, and the gateway and the adapter check them against what the runtime offered ("RP-2", O2).
- The tool list of a session reaches its runtime with a change notice, which reopens DA O4 ("RP-4").
- A frame's session is the session of the slot whose connection carries it, so no frame other than `session_start` carries `sessionId`, and `session_start` and `session_started` carry no `startId` ("RP-3", D9).

**Removed:**

- The integration levels Basic, Standard, and Full, `integrationLevel` on the Runtime definition, the observed-level probe, and `RUNTIME_LEVEL_UNDERPERFORMS` ("RP-2").
- The adapter's platform MCP server, the channel `CH-MCP-PLATFORM`, and the nonce inside MCP `initialize` ("RP-3", "RP-6"). [`0124-connector-removal`](../0124-connector-removal/change.md) removes the connector servers and `CH-MCP-CONNECTOR`.
- `lifecycle_capabilities` and `lifecycle_support`, which the handshake replaces ("RP-1").
- The adapter-local tools `read_file`, `write_file`, `list_dir`, and `delete_file`, and custom adapter-local tools (D5).
- The rules for several sessions on one connection: interleaving and demultiplexing by `sessionId`, `startId`, and the refusal of platform and connector tools on pods with several slots ("RP-3", O10, D9).
- The `preConnect` capability and every path that launches a runtime process before its session (D6). Every runtime process launches at bind, after materialization and setup, and `session_start` follows its handshake ("RP-1"). [0118.S2](../0118-agent-pod-layout/steps.md#steps) removes `capabilities.preConnect` and `sdkWarmBlockingPaths` and lands the refusal of a write that names either, and this change lands its catalog without `preConnect`.

**Out of scope:**

- The adapter's conversation with the runtime supervisor on `CH-SUPERVISE`, which [`0145-session-isolation`](../0145-session-isolation/change.md) owns: `launch`, `end`, `sweep`, `cleanup`, `setup`, and the file-descriptor broker's `fs` and `fsdone`. This design covers the adapter and the runtime process on `CH-MSGSOCK` and nothing the supervisor carries.
- The gateway's own `/mcp` endpoint and its MCP versions, which [`0134-mcp-protocol-upgrade`](../0134-mcp-protocol-upgrade/change.md) covers.
- The platform tool-forwarding RPCs between the adapter and the gateway on `LNK-GWCONTROL` (`ListPlatformTools` and `CallPlatformTool` in `schemas/lenny-adapter.proto`) **[source]**. The adapter calls them from frames as it calls them from MCP today. The connector RPCs beside them, `ListSessionConnectors`, `ListConnectorTools`, and `CallConnectorTool`, leave under "CR-1" of [`0124-connector-removal`](../0124-connector-removal/change.md).

## Terms

| Term | Meaning |
| :-- | :-- |
| Slot and slot container | One of the places on a pod where a session runs, and the runtime container `runtime-<n>` that serves it under its own UID, which [`0145-session-isolation`](../0145-session-isolation/change.md) "SI-1" defines. Every agent pod has one slot container per slot, a pod with one slot included. |
| Runtime process | The process the slot's runtime supervisor launches from the runtime's `command` when a session binds to the slot, after materialization and setup. It holds its slot's runtime connection and serves that one session over its life ("Process model"). |
| Bind | The step at which a claimed session takes a slot of a pod: at a creation, a resume, or a restore. The adapter materializes the workspace, runs setup, launches the runtime process, completes its handshake, and writes `session_start` ("RP-1"). |
| Harness | An agent program a runtime process wraps, such as Claude Code or Codex, which reaches tools as an MCP client. |
| Framed protocol | The JSON Lines frames between the adapter and a slot on `CH-MSGSOCK`, each a JSON object with a `type` member on one line. |
| Runtime connection | The `CH-MSGSOCK` connection the runtime process opens to its slot's endpoint, `@lenny-runtime-<n>` on an agent pod, or the runtime process's stdin and stdout in the developer loop and the conformance harness (O5). It carries every frame of the protocol. |
| Tool connection | A `CH-MSGSOCK` connection a stdio bridge opens to its slot's endpoint, which carries tool frames alone (O3). |
| Handshake | The exchange that opens every connection: the nonce line on a socket, then the client's `hello` and the adapter's `welcome` or refusal ("RP-1"). |
| Protocol version | An integer that names a version of the framed protocol. A new version is issued only for a change that breaks an existing frame ("RP-7"). |
| Capability | A behaviour the runtime declares because the platform must know of it before it acts: either the platform sends the runtime something the runtime must handle in a particular way, or the gateway makes a decision before a pod exists ("RP-2"). |
| Capability dependency | A rule that a capability requires another, such as `clientTools.supported` requiring `conversationInput` ("RP-2"). |
| Declared capabilities | The capabilities a runtime revision states in its `capabilities` object ("RP-2"). |
| Offered capabilities | The capabilities a runtime's `hello` lists ("RP-1"). |
| Effective capabilities | A session's declared capabilities after the per-tenant override narrows them ("RP-2"). |
| Tool progress | Withdrawn in revision 10, because [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors, its only producer. It was a `tool_progress` frame the adapter wrote for a pending connector call to a session whose effective capabilities included `toolProgress` (D11). |
| Tool server | A named set of tools a session may call: `platform`, Lenny's platform tools, and, since revision 15, `client`, the tools the session's client offers under the blocking interface of [`0122-client-tools`](../0122-client-tools/change.md) ("RP-3"). Revisions 1 to 9 also named `connector:<id>` for each connector, which [`0124-connector-removal`](../0124-connector-removal/change.md) removes. |
| Internal operation | A platform tool whose `tool_list` entry carries `internal: true`. The reference MCP bridge never lists it to a harness, and code such as the reference extension calls it with `tool_call` frames ("RP-3", RPR-24). The platform operations of 0166, such as `session.create`, are internal. |
| Call group | The calls a runtime makes at one model step, which a `tool_call` to the `client` server marks with `group` and its size, so a client receives them together ("RP-3"). |
| Lineage and tags | Two members of `session_start`. `lineage` is the list of runtimes from the root of the session's tree to the session, which the gateway records. `tags` is the map of strings a parent set on the session at `session.create` for its own bookkeeping, which billing, budgets, and routing never read ("RP-4", decision 44 of 0166). |
| Availability | What a session may use at a moment: its tool servers and the operations that travel on frames, such as creating sessions as its children and asking questions ("RP-4"). |
| Reference MCP bridge | The MCP server the runtime SDKs ship. It serves each tool server to a harness, turns MCP requests into frames, and serves the session tools of the reference extension in its `platform` server ("RP-5"). |
| Reference extension | The session tool set and the `sessions` library over the platform operations of 0166, shipped with the runtime SDKs and the reference MCP bridge, which a runtime author may use, replace, or omit ([`0166-delegation-primitives`, "DP-5"](../0166-delegation-primitives/change.md#dp-5-reference-extension)). |

## High-level design

**Process model.** Under [`0145-session-isolation`](../0145-session-isolation/change.md), every agent pod has one slot container per slot, `runtime-<n>`, each under its own UID, a pod with one slot included ("SI-1", D1) **[source]**. Each slot container's first process is a runtime supervisor. When a session binds to the slot, the adapter materializes the workspace and runs setup through the supervisor, and then the supervisor launches one runtime process from the runtime's `command`, with `/workspace` as its working directory ("SI-3", WM-3, "PL-3") **[source]**. No runtime process runs in a slot that holds no session (D6). That process dials its slot's `CH-MSGSOCK` endpoint, `@lenny-runtime-<n>`, and the adapter binds the connection to slot `n` by the name it arrived on and by the peer UID that `SO_PEERCRED` reports (SIR-3) **[source]**. The handshake follows, and then `session_start` ("RP-1"). At the slot release the supervisor ends every process in the slot container, the slot is swept, and no process is launched until the next session binds, so each runtime process serves one session over its life (D4, "SI-3") **[source]**. The runtime process may start other processes, such as a harness CLI, MCP bridges, and the tools a model runs. The runtime process speaks the full protocol, and a bridge it starts speaks the tool frames alone. The supervisor's own conversation with the adapter, `CH-SUPERVISE`, is session isolation's subject and outside this design. Every runtime is an agent runtime in this model, because AR removed `type: mcp` runtimes and service mode. The runtime SDKs are optional throughout: the frames are the contract, and the SDKs implement them.

A runtime process opens its connection to the adapter and introduces itself. It names the protocol versions it speaks, the capabilities it has, and its own name and SDK. The adapter picks a version both sides speak, checks that the capabilities are consistent and that the runtime offered every capability the session's runtime revision promised, and reports what the runtime offered to the gateway. Only then does it write `session_start`. Because the runtime process launches for its session, a refused handshake ends that session's bind, and the gateway remembers the refusal for the pod set so later sessions do not meet it. Every runtime performs the handshake, the simplest included.

A capability is something the platform needs to know about before it acts. Whether a runtime pauses for a checkpoint, stops when asked, or takes a second message changes what the platform does, so each is a capability. Operations a runtime starts itself, such as calling a tool, reporting activity, or asking a question, need no declaration, because using them is the declaration. Some capabilities depend on others: a runtime that accepts client tools must accept structured history.

Tools travel as frames. A runtime that calls a platform tool writes a `tool_call` frame naming the tool server, `platform`, and the adapter forwards it to the gateway as it forwards MCP calls today. A runtime that calls a tool its client offers names the server `client`, and the call stays open until the client answers it, under the blocking interface of [`0122-client-tools`](../0122-client-tools/change.md). The adapter knows the session from the slot whose connection carried the frame, so the frame names no session, and tools work on every pod, pods with several slots included. Only `session_start` carries the session's identifier, as data for the runtime. The adapter runs no MCP server.

Harnesses such as Claude Code reach tools through MCP. The runtime SDKs ship a reference MCP bridge: an MCP server inside the runtime process for a harness that supports one, or a small stdio program the harness launches. A stdio bridge opens its own tool connection to its slot's endpoint, so it needs nothing from the runtime process beyond being started. The bridge serves one MCP server per tool server, `platform` and `client`, because [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors. The platform operations with which a session creates and manages other sessions are marked `internal` and never listed to a harness: in their place the bridge's `platform` server lists the session tools of the reference extension of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-5-reference-extension), which call those operations. A harness reaches an operator's own MCP service over HTTP through `netagent`, outside the frames.

When a session starts, `session_start` tells the runtime what the session may use, its tool servers and whether it may create children or ask questions, and where it sits: its `lineage` from the root of its tree and the `tags` its parent set. When that changes, an `availability_changed` frame says so, and the bridge tells the harness to list its tools again. The gateway still checks every call when it arrives, so a runtime that ignores the notice meets the same refusal it meets today.

```
 slot container runtime-<n> (slot UID)                         adapter                      gateway
   supervisor (PID 1) ───────── CH-SUPERVISE @lenny-supervise-<n> ──> (session isolation)
   runtime process ─── runtime connection ─┐
        └─ harness (Claude Code)            ├─ @lenny-runtime-<n> ──> slot n = its session ──LNK-GWCONTROL──> tool dispatch
              └─ stdio bridge ── tool conn ─┘   hello / welcome          runtime_handshake ──> pod row, bind check
                                                session_start {availability, capabilities}
                                                tool_call {server, name} ──> forward ───────> live checks
                                            <── tool_result, availability_changed <── UpdateAvailability (CH-ATTACH)
```

The rest of this document states each part in the design's terms.

## Detailed design

### RP-1 Handshake

**Order.** Every connection opens with the same sequence **[design]**:

1. On a socket, the client checks that the server runs as the adapter UID, which its slot's manifest names ("SI-2"), and writes the runtime connection handshake of §4.7.11 item 1: the nonce line from its slot's manifest, and in nonce-only mode the challenge and its answer. The adapter has already bound the connection to its slot by the name it arrived on and the peer UID (SIR-3). Over stdin and stdout this step is absent.
2. The client writes `hello` as its first frame.
3. The adapter writes `welcome`, or an `error` frame with `code: "handshake_refused"` and a `reason`, and closes the connection.

The client writes `hello` within a bound the adapter sets, 10 seconds by default (`adapter.runtimeHelloTimeoutSeconds`). A first frame of any other type is refused with `no_hello`. The adapter writes no frame other than the handshake's before `welcome` (RPR-1).

**`hello` from a runtime process:**

```json
{
  "type": "hello",
  "role": "runtime",
  "protocolVersions": [1],
  "capabilities": {
    "interaction": "multi_turn",
    "injection": { "supported": true, "modes": ["queue", "steer", "interrupt"] },
    "interrupt": true,
    "checkpoint": true,
    "childSessions": true,
    "conversationInput": true,
    "clientTools": { "supported": true, "customTools": true }
  },
  "runtime": { "name": "claude-code-wrapper", "version": "2.4.0" },
  "sdk": { "name": "runtime-sdk-go", "version": "1.6.0" }
}
```

`role` is `runtime` for the runtime process, and its default. A slot has one runtime connection, and the adapter refuses a second `runtime` hello on a slot whose runtime connection is open. `protocolVersions` lists every version the client speaks. `capabilities` takes the schema of the Runtime definition's `capabilities` object, restricted to the catalog of "RP-2", and a missing member means the capability is absent. `runtime` is required, and `sdk` is absent for a runtime written without an SDK.

**`hello` from a bridge.** Under O3 (b) a stdio bridge writes `{"type":"hello","role":"tools","protocolVersions":[1],"sdk":{...}}`. A tool connection offers no capabilities, because capabilities describe the runtime process. The adapter accepts tool connections only on a slot whose runtime connection has completed its handshake, up to a bound per slot (`adapter.maxToolConnectionsPerSlot`, 32 by default), and binds each to the slot as it binds the runtime connection.

**`welcome`:**

```json
{
  "type": "welcome",
  "protocolVersion": 1,
  "capabilities": { "...": "the offered capabilities the adapter accepted" },
  "adapter": { "version": "1.9.0" },
  "limits": { "maxLineBytes": 52428800 }
}
```

`protocolVersion` is the highest version both sides speak. On a runtime connection, `capabilities` repeats the offered capabilities, and which of them a session uses arrives on its `session_start` as its effective capabilities ("RP-4"). `limits` carries the adapter's limits that a client respects, starting with the line limit of "MD-24".

**Refusal.** The adapter refuses with one of these reasons, in the `error` frame's `reason` member and on the report below:

| `reason` | Cause | Retryable |
| :-- | :-- | :-- |
| `no_hello` | No frame within the bound, or a first frame that is not `hello`. | Yes. A slow start can cause it. |
| `malformed_hello` | A `hello` that is not valid JSON or lacks `protocolVersions`, or a runtime `hello` that lacks `runtime`. | No. |
| `unsupported_version` | No version in `protocolVersions` that the adapter supports. | No. |
| `capability_dependency` | An offered capability whose dependency the `hello` lacks. The frame names each one. | No. |
| `capability_missing` | A runtime `hello` that lacks a capability in the effective capabilities of the session the process was launched for ("RP-2"). The frame names each one. | No, for the session and its capabilities. Another session whose effective capabilities the offer covers can bind to the pod set. |
| `role_refused` | A second `runtime` hello on a slot, or a `tools` hello beyond the bound or before the runtime connection's handshake. | No, for the connection. The slot is unaffected. |

**After a refusal.** A runtime process exits with a non-zero status on an `error` frame with `handshake_refused`, and does not dial again; a bridge reports the refusal to its harness and exits. The re-dial rule of §4.7.11 item 1 still applies to a connection the adapter closes before the client's first frame.

**Where a refusal lands.** Every runtime process launches when a session binds to its slot, after materialization and setup, and the adapter writes that session's `session_start` only after the handshake has passed (D6, RPR-20). A runtime handshake therefore runs inside a session's creation, resume, or restore, and a refusal ends that bind **[design]**:

- **The slot.** The runtime process exits on the refusal. The adapter answers the bind with the refusal, reports it ("Report", below), and releases the slot as after any session ("SI-3"). The slot stays in service.
- **The session.** A creation fails with `RUNTIME_HANDSHAKE_REFUSED`, whose `details.reason` names the refusal reason, or with `RUNTIME_CAPABILITY_MISSING` for `capability_missing`. A refusal that is not retryable at a resume or a restore ends its retries under [§7.3](../../spec/07_session-lifecycle.md#73-retry-and-resume) and ends the session `failed`, as "SL-2" of [`0146-session-lifecycle`](../0146-session-lifecycle/change.md#sl-2-transitions) states for every failure that is not retryable (D10, which settles O13 and that design's SL-Q2 together). A retryable refusal (`no_hello`) is retried on another pod under the pre-attached failure retry of [§6.2](../../spec/06_warm-pod-model.md#62-pod-state-machine) for a creation, and under §7.3's retries for a resume or a restore. §6.2 limits that retry to the creation of `POST /v1/sessions/start` and makes one attempt for `POST /v1/sessions/{id}/finalize` and for delegated-child materialization, which are binds under D6; O16 in `decisions.md` asks the owner what a `no_hello` refusal does on those two paths.
- **The pod set.** Every pod of a pod set runs the same image, and an image does not change within a pod set (RV-3), so a reason that is not retryable recurs on each of its pods. The gateway records the refusal on the pod set and claims none of its pods for a later session; for `capability_missing` it stops claiming them only for sessions whose effective capabilities the recorded offer does not cover ("RP-2"). For the other reasons that are not retryable, the adapter stops accepting binds, and once none of its slots holds a session it exits with the refusal as its termination reason (how a dead slot, which counts in the pod's occupancy for the pod's life, counts toward that boundary follows the answer to O14 of [`0145-session-isolation`](../0145-session-isolation/decisions.md)), and the pod retires with the reason `runtime_refused` that [`0145-session-isolation`](../0145-session-isolation/change.md) states under **Runtime refused** (its D37 and SIR-41). The WarmPoolController, which writes `PodSet` `status` conditions under [§4.6.3](../../spec/04_system-components.md#463-crd-field-ownership-and-write-boundaries), sets the `RuntimeHandshakeRefused` condition on the `PodSet` of the pod that exited, from that termination reason, and backs off creating pods for that `PodSet`, so an image that cannot speak to the adapter does not churn pods. A new revision with a fixed image builds a new pod set, which starts with no recorded refusal. The owner has not settled whether one session's handshake may decide claims for a whole pod set (O14), or which object keys the recorded refusal and offer and where they are stored (O15); this bullet and "Report" stand as written until both are settled.

The time of the handshake counts toward the session's start. The owner asked for no validation of runtime start-up times, because they are small (2026-11-12).

**Report.** The adapter reports each runtime handshake on `CH-ADAPTEREVENTS` as a `runtime_handshake` event with the slot index, the result, the reason of a refusal, the chosen version, the offered capabilities, and `runtime` and `sdk`. The gateway stores the last report of each pod set, with its offered capabilities or its refusal, where the claim-time check of "RP-2" reads it, and counts `lenny_runtime_handshake_total{result, reason, version, role}`. The report replaces `GetObservedIntegrationLevel`. Tool connections are counted on the same metric with `role: tools` and are not stored. The gateway has no consumer of `CH-ADAPTEREVENTS` today (issue CHPODGW-I3). [0145.S1](../0145-session-isolation/steps.md#steps), on which 0139.S1 depends, needs that consumer first for its dead-slot reports, so 0139.S1 adds the `runtime_handshake` event to the consumer that 0145.S1 lands.

**What it replaces.** `lifecycle_capabilities` and `lifecycle_support` leave together with `CH-RUNTIMEOPS` (O7 (a)). §4.7.9 steps 8 and 9 become the handshake, which runs at bind. The manifest's `version` stays the version of the manifest's own schema, and the protocol version lives only in the handshake.

### RP-2 Capabilities and their dependencies

**What a capability is.** A behaviour is a capability when the platform must know of it before it acts: the platform sends the runtime something the runtime must handle in a particular way, or the gateway decides something before a pod exists **[design]**. A frame the runtime starts needs no capability, because the runtime's use of it is the declaration: `message_part`, `activity`, `consumed`, `request`, `tool_call`, `list_tools`, `tool_cancel`, `retract`, and `watch_child_session`. `set_tracing_context` leaves, because "DP-6" of 0166 replaces the tracing context with tags. A frame the platform sends that a runtime may ignore needs none either, because "MD-24" has a runtime ignore an adapter-to-runtime frame it does not know: `deadline_approaching`, `files_updated`, `availability_changed`, and `error`.

**Catalog.** The capabilities, what a runtime that declares one does, what the platform does for a runtime that does not, and the dependency of each:

**Changes from today's capabilities.**

- **`preConnect` leaves.** §5.1 lists it today, for a runtime that pre-connects its harness at warm-up and can be demoted ([§6.1](../../spec/06_warm-pod-model.md#61-what-a-pre-warmed-pod-looks-like)) **[source]**. Every runtime process now launches at bind, after materialization and setup (D6), so no runtime starts before its session and none is demoted. `sdkWarmBlockingPaths`, the demotion path, and its circuit breaker leave with it. [0118.S2](../0118-agent-pod-layout/steps.md#steps) removes the capability and `sdkWarmBlockingPaths` and lands the refusal of a write that names either, and 0139.S1 depends on it.
- **`deadline_signal` leaves the catalog.** Today `lifecycle_support` lists it, and §15.4.6 tests it when declared. `deadline_approaching` is a one-way warning that needs no answer, so under "MD-24" a runtime that does not know it ignores it, and the platform does nothing differently for a runtime that does. The adapter sends it to every session it applies to.
- **A runtime without `checkpoint` gets best-effort snapshots.** §15.4.3 gives a Basic runtime "No checkpoint support" and a Standard runtime a best-effort snapshot. Without levels, every runtime that does not declare `checkpoint` gets the best-effort snapshot that Standard gets today, so a runtime that was Basic gains snapshots it did not have, with the "Minor workspace inconsistencies possible on resume" that §15.4.3 states for them.
- **Credential rotation leaves the catalog.** [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/change.md) ("LU-4") removes LLM credential leases, direct delivery mode, and the rotation of credentials into running pods, with `credentials_rotated`, `credentials_acknowledged`, `hotRotation`, and §4.7.8. The platform then sends a runtime nothing about rotation, so no `credentialRotation` capability exists. Revision 5 listed it; it is not carried forward.
- **`childEvents` joins the catalog.** [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-4-events-from-children) keeps an extension written against it working when a later change adds a child event kind that needs the parent to act, or a way for a child to join a parent other than `session.create`, such as an actor outside the pod attaching a child (decision 2 of 0166). The gateway delivers such a kind, and attaches a child by such a path, only to a runtime that lists it in `childEvents`, a list capability that the **Coverage.** rule compares element by element. 0166 defines no value, so the list has no defined value in v1, and `childSessions` stays the boolean of "MD-22".
- **The usage frames stay undeclared.** `llm_request_started` and `llm_request_completed` are runtime-started frames, so using them is the declaration. They remain the runtime's own report of a model call it sends outside the gateway's LLM proxy, which no budget reads ("LU-10"), and no capability obliges a runtime to write them.

**Dependency rules.** The gateway refuses a Runtime registration, a revision, or a derived runtime whose declared capabilities break a dependency, with `422 INVALID_RUNTIME` naming the capability and its missing dependency (RPR-4). The adapter refuses a `hello` that breaks one ("RP-1"). The per-tenant override narrows capabilities, and a narrowing that removes a dependency removes what depends on it: clearing `conversationInput` for a tenant also clears `clientTools.supported` and `clientTools.customTools` for that tenant's sessions **[design]**. [`0140-runtime-revisions`](../0140-runtime-revisions/decisions.md) D17 and [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md) DR-8 let the override narrow only `interaction` and `injection`, which this example exceeds; O19 in `decisions.md` asks the owner which keys the override may narrow, and the example stands until it is settled.

**Coverage.** Both checks below ask whether an offer covers a set of capabilities, and coverage is defined per value type **[design]**: a boolean capability is covered when the offer sets it `true`; a list, such as `injection.modes` or `conversationParameters`, is covered when the offer contains every element of the list it is compared with; `interaction` is covered when the offer's value is the same or is `multi_turn`, because a runtime that takes further messages also serves a session that ends at its first turn; and an object, such as `injection` or `clientTools`, is covered member by member under these rules. A capability absent from the offer covers nothing.

**Declared, offered, and effective (O2 (d)).** A session uses its effective capabilities (RPR-5). The adapter accepts any offered set that passes the dependency rules and reports it ("RP-1"). Two checks compare a session's effective capabilities with what the runtime offers **[design]**:

- **At the claim, in the gateway.** When the pod set of the chosen revision has a recorded report, the gateway compares the session's effective capabilities with the report's offer before it claims a pod, at a creation, a resume, or a restore. A session the offer does not cover is refused with `RUNTIME_CAPABILITY_MISSING` naming each missing capability, and no pod is claimed. A pod set with no report yet is claimed, and the adapter's check decides. Under [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) "RV-2" **Claim.** and "RV-3", the claim set of a revision can hold several `PodSet` objects; which of them the check reads, and which object keys the report, is O15 in `decisions.md`. 0140's D23 and its "RV-2" **Capability checks (D23).** state these two checks since the M3 readiness review of 2026-11-19; O20 asks the owner to confirm them.
- **At launch, in the adapter.** The bind carries the session's effective capabilities to the adapter (`StartSessionRequest`). After the runtime process it launched for the session writes `hello`, the adapter compares the offer with them, and refuses the handshake with `capability_missing` when one is absent ("RP-1"), so no `session_start` reaches a runtime that cannot honour it.

Every pod of a pod set runs the same image, so the gateway does not try another pod of the set after `capability_missing`: a creation fails with `RUNTIME_CAPABILITY_MISSING`, and a resume or a restore ends its retries under [§7.3](../../spec/07_session-lifecycle.md#73-retry-and-resume) and ends the session `failed` (D10). At the first report from a pod set, the gateway also checks every active revision that uses the pod set, records a mismatch on the revision in the runtime registry, shows it in the admin API's revision view, and counts `lenny_runtime_capability_mismatch_total{runtime, runtime_revision}`, with the revision label named as [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) names it on the session metrics, so an operator sees the drift before a later session meets it. An offered capability no revision of the pod set declares is recorded as `runtime.capabilities.underdeclared` in the audit stream.

**What leaves.** `integrationLevel`, its default, its ordering, and its validation leave §5.1, the CRD, the admin API, the database column, and the derived-runtime field table. `RUNTIME_LEVEL_UNDERPERFORMS` and `runtime.integrationLevel.underdeclared` leave, and `RUNTIME_CAPABILITY_MISSING` and `runtime.capabilities.underdeclared` replace them. The §26.1 catalog's `Level` column becomes a capabilities column. §15.4.3 becomes "Runtime Capabilities", with the catalog above in place of the comparison matrix and the Basic-level limitation list. Every sentence of the specification and the documentation that names a level is restated in capabilities (RPR-6). A runtime write that still names `integrationLevel` is refused with `400 VALIDATION_ERROR` naming the field, as [0118.S2](../0118-agent-pod-layout/steps.md#steps) already refuses a `capabilities` object that still names `preConnect`, under the owner's rule of 2026-11-13 for removed fields in every design ([`0119-agent-runtimes-only`, "AR-4"](../0119-agent-runtimes-only/change.md#ar-4-admission-of-removed-fields), AR D6).

### RP-3 Tool calls on frames

**`tool_call` names its server.** A `tool_call` gains `server`, which names the tool server **[design]**:

```json
{
  "type": "tool_call",
  "id": "tc_7",
  "server": "platform",
  "name": "session.create",
  "arguments": { "target": "reviewer", "task": [{ "type": "text", "inline": "Review the diff." }], "tags": { "role": "reviewer" } }
}
```

`server` takes `platform` or `client`. D5 retires the adapter-local tools and [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors (revision 10), and revision 15 adds `client` under decision 23 of [`0166-delegation-primitives`](../0166-delegation-primitives/decisions.md). The member stays so that a later tool server does not change the frame, and a frame naming another value is answered with `tool_result` carrying `error.code: "UNKNOWN_SERVER"`. The adapter forwards `platform` with `CallPlatformTool` on `LNK-GWCONTROL`, naming the session of the slot whose connection carried the frame. The gateway's checks are unchanged: TS-3's allow-list, the session grant of "DP-1" of 0166, which 0126 decides with its live checks of "DA-2" and "DA-3", and tool approval (RPR-9). Today a runtime can set `approvalRequired: true` on a `tool_call` to have the call held for the user's approval (`schemas/lenny-adapter-jsonl.schema.json`), and `CallPlatformToolRequest` has no member that carries the flag; whether the flag survives the move to `CallPlatformTool` is O18 in `decisions.md`. The `session.create` argument that names the runtime is `target`, as "DP-1" of 0166 states. Revisions 1 to 9 also took `connector:<id>`, forwarded with `CallConnectorTool` and checked against §9.3; that path is withdrawn with connectors. The platform tools are the operations of "DP-1" of 0166 under the namespaces `session.*`, `events.*`, `questions.*`, `files.*`, `tools.*`, and `runtimes.*` (decision 16 of 0166), and the tools that address the session's own client, such as `send_update` and `ask_question`, which keep the names of "MD-23" without the `lenny/` prefix. The session tools that "MD-23" named, such as `start_child_session`, leave the gateway for the reference extension ("RP-5"). A runtime process launches only for a bound session (RPR-20), so a slot's connections always act for that session; a tool frame that arrives after the session has ended and before the release's End closes the connection is answered with `TOOL_SERVER_UNAVAILABLE`.

**The `client` server.** A runtime calls a tool its session's client offers with `server: "client"`, under the blocking interface of [`0122-client-tools`](../0122-client-tools/change.md), which decision 23 of 0166 makes one interface for every client, a REST client, a provider adapter, and a parent included **[design]**. The adapter forwards the call to the gateway on `LNK-GWCONTROL` as it forwards a `platform` call, naming the slot's session and the server. The call stays open until the client answers it, and the adapter then writes `tool_result` with the client's `content` and `isError`, or until the gateway withdraws it, when the adapter writes `tool_result` with `isError: true` and `error.code: "CLIENT_TOOL_CALL_WITHDRAWN"` with the reason, or `CLIENT_CHANGED` when the session left its parent ("DP-2" of 0166). A call that fails 0122's validation is answered with `error.code: "CLIENT_TOOL_CALL_INVALID"` with the reason. "CT-1" and "CT-5" of 0122 state these answers. A result that arrives after the withdrawal reaches the runtime as `toolResults` on the session's next message, as 0122 states. A runtime that runs its own model loop and receives its client's tool definitions on the message, as CT-1 states, calls them the same way.

```json
{ "type": "tool_call", "id": "tc_9", "server": "client", "name": "read_calendar",
  "arguments": { "day": "2026-11-24" }, "group": { "id": "g_3", "size": 2 } }
```

**Call groups.** A runtime that makes several calls to the `client` server at one model step marks each with the same `group`, whose `id` the runtime chooses and whose `size` is the number of calls in the step, so the gateway delivers the step's calls to the client together and a provider adapter returns them in one response, as 0122 states. A call without `group` is a group of one. The adapter ignores `group` on a `platform` call.

**The session of a frame (RPR-18).** Revision 2 required `sessionId` on every tool frame, because one connection could carry several sessions. Under session isolation every `CH-MSGSOCK` connection is bound to one slot (SIR-3), the slot holds at most one session at a time, and its runtime process serves at most one session over its life (D4) **[source]**. The adapter therefore knows the session of every frame from the connection that carries it, and under AR's O5 (b) no frame other than `session_start` carries `sessionId` (D9). Each frame of the protocol stands as follows:

- **`session_start`** keeps `sessionId` as data the runtime reads, and the adapter never acts on it (RPR-21). A runtime uses it to correlate its logs with the platform's for support, to keep one identity across restarts of its process, to build idempotency keys for actions it takes outside the session, and to detect that its session was derived, because a derived session carries a new identifier over a restored workspace (AR D5). No runtime-visible path carries it. The frame's `cwd` is the constant `/workspace`, or the folder under it that DR-12's `workingDirectory` names, and its `credentialsPath` is the constant `/run/lenny/credentials.json`, present only when a credential file exists ("PL-3"). The LLM upstreams design removes direct delivery mode, the file's LLM use, so the file exists only if a VCS path still uses it, which that design leaves to validation. It carries no `startId`.
- **Every other session-scoped frame**, the tool frames included, carries no `sessionId`, and `session_started` carries no `startId`. A runtime that still writes either member is unaffected: under the leniency rules of "MD-24" an unknown member of a known frame is ignored with no report, and only an unknown frame type produces a `runtime_warning` **[source]**. The frame acts for the slot's session whatever the member says.
- **Tool connections** carry no `sessionId` in any frame, and each scopes its own frame `id`s.
- **Process-scoped frames**, such as `hello`, `welcome`, `heartbeat`, and `llm_request_started`, carry none, as today.

**What retires.** The interleaving of several sessions' frames on one connection, the runtime's dispatch loop keyed on `sessionId` that the `CH-MSGSOCK` card's **Exclusivity.** bullet requires "on every pod", the "multiplexed by `sessionId`" sentence of §4.7.10 **Runtime process lifetime.**, the "MD-24" rule that a frame may omit `sessionId` only while its connection serves one session, the `CH-MCP-PLATFORM` card's refusal of calls from a process holding several sessions, revision 2's per-frame `sessionId` requirement and its multiplexer stamping, and `startId` on `session_start` and `session_started` with the rule that drops a `session_started` whose `startId` is not that of the open sequence. Session isolation's own proposals retire the process-model sentences; this design and AR retire the frame rules ("Specification changes"). No rule for several sessions on one connection remains, because AR removed service mode, the last place that kept one (D9).

**`tool_result`.** The frame is unchanged apart from an optional `error` member, `{ "code": "<CODE>", "message": "<string>" }`, beside `isError: true`. Its codes take the gateway's spelling: `DELEGATION_DISABLED` and the other codes each tool already answers, `TOOL_NOT_FOUND`, `UNKNOWN_SERVER`, `TOOL_SERVER_UNAVAILABLE`, `CANCELLED`, `RESULT_TOO_LARGE`, and, for a `client` call, `CLIENT_TOOL_CALL_WITHDRAWN`, `CLIENT_TOOL_CALL_INVALID`, and `CLIENT_CHANGED`.

**Large results.** A platform result reaches the adapter as one `bytes` member of a gRPC response, bounded by grpc-go's 4 MiB default receive limit, which the tree does not raise **[source]**. The gateway dereferences any `lenny-blob://` reference in a result and inlines its content before it answers the adapter, as §15.2 states for external MCP clients, because such a reference resolves only through the client-facing `GET /v1/blobs/{ref}` route and a runtime has no path to it (RPR-17). A result larger than the bound after that is answered with `RESULT_TOO_LARGE`. The gateway fetches each referenced blob before it checks the size, and a child event that `events.wait` returns can carry a part of up to 50 MB staged with a `lenny-blob://` reference, as [`0135-message-delivery`](../0135-message-delivery/change.md) stages parts from 64 KB to 50 MB and delivers a child's end-of-turn event once under its MDR-37, which the bound refuses with no other path for the runtime to read it; O17 in `decisions.md` asks the owner how an over-bound part reaches a runtime and whether a refused result consumes the child event. An operation that moves files, such as `files.import`, moves them through the checkpoint restore path that "MD-26" states, which session isolation runs through the broker ("SI-6"), and the result names them.

**Listing.** A client lists a server's tools with a request and answer pair:

```json
{ "type": "list_tools", "id": "lt_1", "server": "platform" }
{ "type": "tool_list", "id": "lt_1", "server": "platform",
  "tools": [{ "name": "ask_question", "description": "...", "inputSchema": { "type": "object" } },
            { "name": "session.create", "internal": true, "description": "...", "inputSchema": { "type": "object" } }] }
```

The adapter answers `platform` from `ListPlatformTools`, which computes the session's list as "DA-4" states. An entry with `internal: true` names an operation for code to call: each platform operation of "DP-1" of 0166 carries it, and a tool that a model calls directly, such as `ask_question`, does not. The reference MCP bridge never lists an internal entry to a harness (RPR-24), and the adapter forwards a call of one as any other call, so the gateway decides it (RPR-9). A reader that does not know the member ignores it under "MD-24" and sees the operation as an ordinary tool. The adapter answers `client` with the definitions of the tools the session's client offers for the open turn, which 0122 states, and an empty list when the client offers none. A listing that fails answers `tool_list` with `error` and no `tools`. Revisions 1 to 9 also answered a connector from `ListConnectorTools`, and a runtime that declared `deferredToolDiscovery` kept a failed listing ("CA-8"); both are withdrawn with connectors.

**Cancellation.** A client that abandons a call writes `{ "type": "tool_cancel", "id": "tc_7" }` on the connection that carried the call. The adapter cancels the forwarded call, stops counting it as activity (RPR-12), and answers it with `tool_result` carrying `error.code: "CANCELLED"`. The reference bridge writes `tool_cancel` when its harness sends MCP `notifications/cancelled` **[external]**. Without the frame, an `events.wait` call that a harness abandoned would count as activity until the gateway answered it. A `tool_cancel` for a `client` call is answered with `CANCELLED` as well, and the gateway withdraws the call from the client with the reason `cancelled` ("CT-5" of 0122). When a tool connection closes, the adapter cancels the calls still in flight on it.

**Progress (D11), withdrawn.** [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors, the only producer of `tool_progress`, so revision 10 withdraws the frame, the `toolProgress` capability, `gateway.toolProgressMinIntervalMs`, and the server-streaming form of `CallConnectorTool`. The paragraph below is kept as the record of revision 9. While a call is pending, the adapter writes `tool_progress` frames for it on the connection that carried the `tool_call`, and only for a session whose effective capabilities include `toolProgress` **[design]**:

```json
{ "type": "tool_progress", "id": "tc_7", "progress": 40, "total": 100, "message": "Indexed 40 of 100 files" }
```

`id` names the pending `tool_call`. `progress` is a number that rises with each frame for the call, and `total` and `message` are optional. The frame reports that the call is still working with what its tool server reported. It is not a result, it changes nothing about the call, and the adapter never writes it after the call's `tool_result`. A frame that crosses the runtime's `tool_cancel` names an id the runtime no longer holds, and the runtime ignores it. The gateway produces the frames for connector calls: for a session whose effective capabilities include `toolProgress`, the connector client sends a progress token with the connector's `tools/call` and reads the MCP `notifications/progress` that the connector sends for that call ([`0134-mcp-protocol-upgrade`, "MP-6"](../0134-mcp-protocol-upgrade/change.md#mp-6-outbound-clients)). `CallConnectorTool` becomes a server-streaming RPC whose stream carries zero or more progress messages and ends with the result, and the adapter writes one `tool_progress` frame for each progress message. The gateway drops a notification whose `progress` does not exceed the call's previous one, and forwards at most one per call in each `gateway.toolProgressMinIntervalMs`, 1000 ms by default, keeping the newest. A platform tool sends no progress. A progress frame adds no activity of its own, because the call already counts as activity until its result or its cancel (RPR-12).

**Duration (D11).** A tool call has no duration a runtime may assume. The time a call takes is its tool server's. Revision 9 added that progress frames show a call still runs; with `tool_progress` withdrawn in revision 10, a runtime learns of a call only from its result. A runtime or a harness that stops waiting for a call writes `tool_cancel`, which the adapter answers with `CANCELLED` and which ends the call's count as activity (RPR-23). A harness timeout that abandons a call without the frame leaves the call counted as activity until its result arrives.

**Order (RPR-16).** Frames on one connection reach the adapter in the order the client wrote them. Frames on a slot's tool connections and on its runtime connection reach it in the order they arrive, as `CH-MCP-PLATFORM` calls and stdout frames do today. The guarantees that matter rest on causality: a harness waits for a tool's result before it acts on it, so it cannot end the turn before a call it made returns, and "MD-22"'s H1 rule places a `send_update` after every runtime-connection frame the adapter has read before it answers the call, so the update reaches the gateway before the turn's end-of-turn `message`. The order of a tool's events against text the harness printed immediately before the call is the order of arrival.

**`EG-3` first.** `cmd/git-credential-lenny` dials the platform MCP socket and calls `lenny/vcs_token` **[source]**. "EG-3" removes both. Proposal RP-B, which removes the socket, lands after "EG-3".

**What leaves.** The adapter's platform MCP server and its socket; the manifest's `platformMcpServer`; the MCP nonce of §15.4.3 with its "Nonce wire format", "Strict MCP client libraries", "Deprecated location", and "Migration path — v2 out-of-band handshake" notes; the "only one session" refusal of the `CH-MCP-PLATFORM` card and its code in `pkg/adapter/platformtoolprovider.go`, which no call meets from 0145.S1 on because each runtime process then holds one session (O10), and which 0139.S2 removes; the adapter-local tools and their custom extensions (D5); and the channel `CH-MCP-PLATFORM`, which O11 (a) retires. [`0124-connector-removal`](../0124-connector-removal/change.md) 0124.S1 removes everything connector-specific: the adapter's connector MCP servers and sockets (`pkg/adapter/connectormcp.go` and `connectortoolprovider.go`), the manifest's `connectorServers`, and the channel `CH-MCP-CONNECTOR` with its register row and successor pointer, whichever of 0124.S1 and 0139.S2 lands first. The `UNKNOWN_SERVER` rule above is this change's, and 0139.S2 lands it.

### RP-4 Availability

**On `session_start`.** Each `session_start` carries `availability`, `capabilities`, `lineage`, and `tags` **[design]**:

```json
"availability": {
  "delegation": true,
  "questions": true,
  "toolServers": [
    { "server": "platform" },
    { "server": "client" }
  ]
},
"lineage": ["claude-code", "reviewer"],
"tags": { "role": "reviewer", "traceId": "4bf92f35" }
```

- `delegation` is whether the session holds a session grant under "DP-1" of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-1-session-grant), which 0126 decides from its availability levels and the session's room (decision 39 of 0166), for a runtime revision that declares `childSessions` (DA E1). A revision without `childSessions` always reads `false`. The reference extension lists `start_session` and `discover_agents` from it ("DP-5" of 0166), and the gateway refuses `session.create` from a session without a grant with `403 DELEGATION_DISABLED` ("DP-1" of 0166).
- `questions` is the `ask_question` rule of "DA-4": the session's `inputPolicy` is `ask` (R12 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md#ro-2-rest-additions)), and the elicitation suppression of [§9.2](../../spec/09_mcp-integration.md#92-elicitation-chain) does not suppress every elicitation of the session. The session's `inputPolicy` is fixed for the session, so a change of the pool's `elicitationDepthPolicy` or allow list is what changes it. A `request` with `kind: "question"` follows it.
- `toolServers` lists every tool server the session may call: `platform` always, and `client` for every session whose effective capabilities include `clientTools.supported`, whose list is empty until the session's client offers tools, so a harness configured at launch has the server before the first tool arrives. 0122 lists `client` only once the client offers tools, and O24 in `decisions.md` asks the owner which rule stands. [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors. Revisions 1 to 9 listed each connector with its link state ("CA-4", "CA-6"), and a connector that needed a link only for a runtime that declared `deferredToolDiscovery`. A harness reaches an operator's MCP service over HTTP through `netagent`, and the runtime's own configuration names it ("CR-3" of the removal design). A runtime whose harness waits on such a service reports `busy: true` on its heartbeats under the rule for runtime authors of [`0146-session-lifecycle`, "SL-6"](../0146-session-lifecycle/change.md#sl-6-idle-pods-and-dormancy), because Lenny does not count egress traffic as session activity.

- `lineage` is the list of runtime names from the root of the session's tree to the session itself, which the gateway records when it creates the session, a list of one for a root ("DP-1" of 0166). A session that left its parent keeps its lineage, and `session.self` of 0166 states how the leave is recorded on it. An extension that avoids cycles reads it, as "DP-6" of 0166 states for the cycle detection that leaves the gateway.
- `tags` is the map of strings that the session's parent set on `session.create`, at most 16 keys of 64 bytes and values of 256 bytes, and is empty for a root (decision 44 of 0166). A parent passes a role or a trace identifier in it, which replaces `tracingContext` ("DP-6" of 0166). Billing, budgets, and routing never read it.

`capabilities` is the session's effective capabilities ("RP-2"). Neither `lineage` nor `tags` grants anything, and no frame a runtime writes changes them (RPR-25). An extension on a tool connection, which receives no `session_start`, reads both with `session.self` of 0166. A restore, a resume, and a wake from `dormant` each write a new `session_start` to a fresh runtime process, so the runtime receives current availability whenever its session comes back (RPR-10). After a restored parent's resends, its runtime receives the system message of SL-12 that lists each child's state and tags and names each pending question by its id, in place of the `children_reattached` event (decision 47 of 0166).

**Changes.** When a session's availability changes, the adapter writes to the slot's runtime connection and to each of its tool connections:

```json
{ "type": "availability_changed",
  "availability": { "...": "the full new availability" },
  "changedServers": ["platform"] }
```

The frame carries the full new availability, so a client never applies a difference, and `changedServers` names each tool server whose tool list may have changed. A bridge acts on the servers it serves.

**How the gateway sends it.** The gateway calls a new unary RPC on `CH-ATTACH`, `UpdateAvailability`, beside `SealSession` and `UnsealSession`. An `Attach` stream exists only from a session's first message delivery (§28.5.1), and a notice can be due before then or while no delivery is under way, so a request variant on the stream would need the gateway to open a stream for it. A unary call needs no stream, and the gateway waits for its return before it writes the turn's first message, so the adapter writes `availability_changed` ahead of that message on the runtime connection. `UpdateAvailability` carries the `coordination_generation` stamp, and the pod rejects a stale one, as the `CH-ATTACH` card's **Preconditions.** require of every gateway-to-pod RPC ([§28.5.1](../../spec/28_communication-channels.md#2851-gateway-to-pod)). Where the coordinating replica keeps what it last sent, what a new coordinator does after a handoff, what the adapter does with a call that arrives before `session_start`, and what the gateway does when the call fails before the turn's first message are O22 in `decisions.md`.

**When the gateway sends it (O6 (e)).** The coordinating replica recomputes `delegation` and `questions` when it opens a turn with a message and when it records a turn the runtime opened ("MD-4"), compares them with what it last sent, and calls `UpdateAvailability` with `changedServers: ["platform"]` when either differs (RPR-11). Every `session_start` carries a fresh computation of the whole availability.

**When the client's tools change.** The client's tool list changes only with an event the gateway already handles: a message that declares a different set of tools, a parent's `session.create` or `session.send` with `tools`, and a leave, which withdraws a parent's tools ("DP-2" of 0166). On each such event the gateway calls `UpdateAvailability` with `changedServers: ["client"]` before it writes the message that carries the new set, and at once for a leave, as O6 (e) has connector state notify through its own events rather than a per-turn recomputation. The `client` entry of `toolServers` is unchanged by these notices, so only the list the bridge serves changes.

**Enforcement stays at the call.** Availability is advice to the runtime. The gateway checks each call as it arrives (RPR-9), so a runtime that ignores `availability_changed`, and a harness that keeps an old list, meet the refusals "DA-3" and "DA-4" state today.

**DA O4.** This design replaces "DA-5"'s **No notification.** paragraph: the reads at each call and each list stay, as "DA-5" **Adding a notification later.** foresaw, and the notice prompts the runtime to list again sooner. The other grounds of DA O4 stand: the list is computed live, the adapter keeps no copy of it, and no admin write path enumerates sessions.

**A harness's fixed configuration.** A harness such as Claude Code reads its MCP configuration at launch. A tool server that first appears mid-session cannot join a running harness, so the runtime configures every tool server in `toolServers` at launch, and a server whose list changes reaches the harness through `notifications/tools/list_changed` ("RP-5"). A tool server that first appears in a running session's availability reaches the harness at the session's next `session_start` ("Limits").

### RP-5 Reference MCP bridge

**What it is.** The reference bridge is an MCP server for each tool server of a session, which a harness reaches as an ordinary MCP server **[design]**. It ships with the runtime SDKs in Go, Python, and TypeScript, and as a static release binary, in these forms:

- **In process.** The SDK serves the MCP servers inside the runtime process, for a harness the runtime drives as a library with in-process MCP servers, and writes their frames on the runtime connection. The Claude Agent SDK offers such servers **[unverified]**.
- **Stdio.** `lenny-mcp-bridge --server <server>` is a static binary that a harness launches as a stdio MCP server. Under O3 (b) it reads its slot's manifest for the nonce and the adapter UID, dials the endpoint named by `LENNY_ADAPTER_SOCKET`, performs the `tools` handshake of "RP-1", and carries its server's frames on that tool connection. It needs no argument naming a session, because the adapter binds the connection to the slot, and no token, because the slot's endpoint admits only the slot's UID (SIR-3).

**Session tools.** The bridge does not host the gateway's delegation tools, which leave the gateway (decision 1 of 0166). Its `platform` server lists the platform tools that are not internal, such as `send_update` and `ask_question`, and, beside them, the session tools of the reference extension of "DP-5" of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-5-reference-extension), such as `start_session`, `send_message`, and `await_sessions`, which it serves over the SDK's `sessions` library. The library calls the internal operations with `tool_call` frames on the bridge's tool connection, and 0166 states when the bridge lists each session tool. The bridge's option `--session-tools` takes `reference`, the default, or `none`, which lists no session tool, so a runtime author who ships another tool set adds that MCP server to the harness configuration. The option `--session-defaults` names a file of default `session.create` arguments for each target, which the model cannot override. 0166 states both options in full.

**MCP mapping.** The bridge maps one MCP server to one tool server (RPR-13). The tool servers are `platform` and `client`, because [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors, whose tools the rule kept apart. The `client` server lists the tools the session's client offers, so a harness sees them as typed tools, and refreshes its list on `availability_changed` naming `client` ("RP-4"):

| MCP | Frame |
| :-- | :-- |
| `initialize` | Answered by the bridge. It declares `tools: { "listChanged": true }`. |
| `tools/list` | `list_tools`, answered from `tool_list` without its internal entries (RPR-24), and on `platform` with the session tools of the reference extension added. A listing error becomes the MCP error the harness tolerates ("CA-9"'s spike). |
| `tools/call` | `tool_call` on the request's server, answered from `tool_result`; a call of a session tool runs the extension's handler, which calls the operations of 0166. `TOOL_NOT_FOUND` becomes `-32602`, as "DA-4" asks of the adapter today. |
| `notifications/cancelled` | `tool_cancel`. |
| `availability_changed` naming the server | `notifications/tools/list_changed`, or under MCP `2026-07-28` the equivalent on a `subscriptions/listen` stream **[external]**. |

Revision 9's row mapping `tool_progress` to MCP `notifications/progress` is withdrawn with the frame in revision 10, so the bridge sends no progress notification to its harness.

**Groups from the bridge.** MCP carries no model step on a `tools/call`. The in-process bridge drives its harness as a library and receives each model step's tool calls together, so it marks the `client` calls of one step with one `group` and its size ("RP-3"). A stdio bridge sees each `tools/call` alone and sends each `client` call without a group ("Limits"). 0122 states that the reference bridge groups a harness's calls, and O24 in `decisions.md` asks the owner which rule stands. The bridge answers every `tools/list` with the cache hints `ttlMs: 0` and `cacheScope: "private"` that "DA-5" states for `2026-07-28`. It serves the MCP versions that MP O1 sets for every surface Lenny serves, which "MP-5" states for the bridge, because the adapter serves no MCP.

**Specification.** The framed protocol is normative in the `CH-MSGSOCK` card of §28.5.3. The bridge has its own section under §15.7, "Reference MCP Bridge", which states the mapping, the tool handshake, the environment it reads, and its conformance cases, so a runtime author can write a compatible bridge in another language (RPR-14).

**CLI configuration.** Each runtime's wrapper writes its harness's MCP configuration before launch, from the session's `toolServers`: one stdio server entry per tool server, each running `lenny-mcp-bridge` with that server's name, and on the `platform` entry the session-tool options the runtime author chose.

### RP-6 What the adapter enforces

The adapter-to-runtime boundary stays untrusted (§4.7.11), and session isolation draws it around each slot container **[design]**. The adapter enforces:

- **Who connects.** The slot binding of session isolation on every socket connection: the endpoint's name, the peer UID, and in nonce-only mode the slot's own nonce ("SI-2", SIR-3). The nonce line and challenge of §4.7.11 item 1, and the handshake on every connection. The nonce authenticates only `CH-MSGSOCK`, because `CH-RUNTIMEOPS` leaves (O7 (a)), so the manifest field becomes `connectionNonce`. The nonce key and the challenge helpers that `pkg/adapter/intrapodauth.go` uses stay, moved out of `pkg/adapter/mcp`.
- **Which session a frame acts for.** The session of the connection's slot (RPR-18). A `sessionId` member on a frame other than `session_start` is ignored.
- **Which frames a connection carries.** A tool connection carries tool frames alone (RPR-19).
- **Which tools a pod reaches.** Platform tools on every pod (O10, RPR-8).
- **Which frames the platform sends.** A platform-initiated frame that needs a capability goes only to a session whose effective capabilities include it.
- **Sizes.** The line limit and the refusal of an overlong line alone ("MD-24"), and the bound on tool connections per slot.
- **Activity and the seal.** Each `tool_call` read on any connection of the slot and not yet answered or cancelled counts as activity (RPR-12), and the seal answers "not sealed" while one is in flight, as it does for MCP calls today. "SL-3"'s L24 refuses the slot's new tool calls on every connection and answers the ones in flight with `CANCELLED`.

The gateway keeps every decision about what a call may do. What leaves the adapter is the MCP server, its per-connection nonce, and its pod-wide binding at the first session's start.

**Security.** Each slot container is one trust domain that serves one session at a time. Every process in it runs as the slot UID, can read the slot's manifest, and can open a connection to the slot's endpoint, as a process there can dial the MCP sockets today ("CA-9", **Security.**), and every such connection acts for the slot's session and no other. A process in another slot runs under another UID and cannot reach this slot's endpoint, manifest, or `/tmp` ("SI-2", "SI-7") **[source]**. Nothing about a call is trusted because it came through the bridge.

**Manifest `version: 2`.** Each slot's manifest keeps `version`, `agentInterface`, `minPlatformVersion`, and `observability`, and `mcpNonce` becomes `connectionNonce`, which session isolation gives each slot its own of ("SI-7"). The manifest also names the adapter UID the client checks ("SI-2"). `platformMcpServer`, `connectorServers`, `adapterLocalTools`, `runtimeOps` (O7 (a)), and `runtimeMcpServers`, which AR removes with `type: mcp`, leave, and the §4.7.6 "Level reading requirements" leave. A runtime rejects a manifest version above the one it understands, as §4.7.6 states, so the SDKs and `pkg/runtimekit/handshake.go` move to version 2 with this change.

**The version 2 field set and where each change lands.** This paragraph is the one statement of manifest `version: 2` for the program. Each slot's manifest at version 2 holds `version`, `agentInterface`, `minPlatformVersion`, `observability`, `connectionNonce`, the adapter UID, and the per-session fields, which hold `runtimeRevision` ([`0140-runtime-revisions`](../0140-runtime-revisions/change.md)) and `routing` in place of `experimentContext` ([`0141-runtime-routing`](../0141-runtime-routing/change.md)). It holds no `platformMcpServer`, `connectorServers`, `adapterLocalTools`, `runtimeOps`, `runtimeMcpServers`, or `runtimeOptions`, which moves to `session_start` under 0140. The changes land in this order **[design]**:

- Before 0139.S1, under version 1: [0119.S1](../0119-agent-runtimes-only/steps.md#steps) removes `runtimeMcpServers`, [0124.S1](../0124-connector-removal/steps.md#steps) removes `connectorServers`, and [0145.S1](../0145-session-isolation/steps.md#steps) writes one manifest per slot with its own `connectionNonce` in place of `mcpNonce` ("SI-7"), each with the matching SDK and `pkg/runtimekit` change.
- 0139.S1 raises `version` to 2, removes `runtimeOps` (O7 (a)), and moves the SDKs and `pkg/runtimekit/handshake.go` to version 2 in the same step.
- 0139.S2 removes `platformMcpServer` and `adapterLocalTools`, and [0140.S1](../0140-runtime-revisions/steps.md#steps) and [0141.S2](../0141-runtime-routing/steps.md#steps) make their changes, under version 2. Under the program's rule against transition modes, none of them raises the version again.

### RP-7 Versioning

Under O1 (a) **[design]**:

- The framed protocol has an integer version, starting at 1 with this design and message delivery revision 14.
- A new version is issued only for a change that breaks an existing frame: a removed or renamed member or frame, a changed meaning, or a changed default. An added optional member, an added frame type, an added capability, and an added value of an enum member keep the version, because "MD-24" has both sides ignore a member or a frame they do not know and handle an unknown value as `other` (D12).
- The adapter supports the current version and the previous one. The version rule for the MCP versions Lenny's own surfaces serve is MPR-8 of [`0134-mcp-protocol-upgrade`](../0134-mcp-protocol-upgrade/change.md#mp-8-version-rule-in-the-specification), on the page that its O10 settles; the gateway's `/mcp` and its version window under [§15.5](../../spec/15_external-api-surface.md#155-api-versioning-and-stability) item 2 move to the MCP adapter project. A version leaves the adapter no earlier than 6 months after its successor ships, and `lenny_runtime_handshake_total{version}` shows which versions pods still speak before one leaves.
- A pod set whose image speaks only a retired version fails its first bind with `unsupported_version`, the gateway claims none of its pods afterwards, and its `PodSet` carries `RuntimeHandshakeRefused` ("RP-1"). A session kept on such a revision under RV-6 finds no pod to restore onto, and its resume fails as a resume against a pool with no ready pod does under §7.3, until its revision is retired and RV-6 moves it to a newer one, or until its client ends it.
- Each SDK release states the protocol versions it speaks, and an SDK's own version is independent of the protocol's. `lenny.runtime.protocol_version` in §15.7 is replaced by this rule.
- §15.5 gains an item for the adapter-to-runtime protocol beside item 3, which keeps the gateway-to-adapter `INIT` negotiation.

### RP-8 Conformance by capability

**Selection.** `lenny runtime validate` reads the runtime's declared capabilities from `runtime.yaml`, runs the core cases, and runs the cases of each declared capability (RPR-15). It also performs the handshake and reports a declared capability the runtime does not offer as missing, and an offered capability it does not declare as under-declared. This replaces the observed-level probe of §5.1's first `integrationLevel` user **[design]**.

**Core cases.** Every runtime passes these: the handshake with each refusal reason and the exit on `handshake_refused`, `session_start` and `session_started` (O9), `message` in both directions with the "MD-24" defaults and without `sessionId`, `heartbeat` with `busy`, `shutdown`, an unknown adapter-to-runtime frame ignored, `availability_changed` ignored or handled, and the unknown values of D12: a `child_session_event` whose `event` the runtime does not know, an `ended` event whose `state` it does not know, a `tool_result` with a content block of an unknown `type` and an unknown `error.code`, and a `retract_result` with an unknown result, each handled as `other` with no error frame from the runtime and no stop in its reading, and a `session_start` with `lineage` and `tags` read without error.

**Capability cases.** Each capability of "RP-2" has its cases: `interrupt` acknowledges within the deadline and stops the turn ("SL-3"), `checkpoint` quiesces, `steer` reads messages during a turn and reports consumption, `childSessions` renders a child event's sender, `childEvents` receives a child event kind it lists and none it does not, with a kind the conformance harness injects, as the DPR-12 tests of 0166 state, and the others as their designs state. The "connector MCP server reachability" case of §15.4.6 leaves with connectors, and the core cases call `list_tools` and `tool_call` on the `platform` tool server.

**Bridge cases.** The reference bridge has cases of its own in its section: each row of the mapping table, an internal entry never listed, the session tools listed under `--session-tools reference` and absent under `none`, the `client` server's list refreshed on `availability_changed`, the `tools` handshake and its refusal, two bridges of one slot with overlapping frame `id`s, the cancel path and the cancellation of a closed connection's calls, and a stock harness listing again on `list_changed`. A bridge written by a runtime author runs the same cases.

## Worked example

Alice and Bob, of tenant `acme`, start `claude-code` sessions on a pool with `sessionPolicy.maxConcurrentSessionsPerPod: 2`.

1. The controller creates a pod with slot containers `runtime-0` and `runtime-1` ("SI-1"). Each slot's supervisor starts and waits. No runtime process runs, and the pod reports READY once its infrastructure is ready.
2. Alice's session claims the pod. The pod set has no recorded report yet, so the gateway's claim-time check passes, and the adapter binds the session to slot 0 with her effective capabilities. The adapter materializes slot 0's workspace and runs setup through the supervisor (WM-3), and the supervisor then launches the Claude Code wrapper, built on `runtime-sdk-go`, in `/workspace`.
3. The wrapper checks that `@lenny-runtime-0` is served by the adapter UID, writes the nonce line from slot 0's manifest, and writes `hello` with `role: runtime`, protocol version 1, and `interaction: multi_turn`, `injection` with `steer` and `interrupt`, `interrupt`, `checkpoint`, `childSessions`, `conversationInput`, and `clientTools`. The dependency rules hold, and the offer covers Alice's effective capabilities. The adapter writes `welcome`, reports `runtime_handshake`, and the gateway records the report for the pod set and finds that the pod set's active revision declares nothing the runtime did not offer.
4. `session_start` for Alice carries `cwd: "/workspace"`, no `credentialsPath`, because her session has no credential file, `availability` with `delegation: true`, `questions: true`, and the servers `platform` and `client`, her effective capabilities, `lineage: ["claude-code"]`, because her session is a root, and empty `tags`. Bob's session binds to slot 1 the same way, and the gateway's check reads the pod set's recorded report before the claim.
5. Alice's wrapper writes Claude Code's MCP configuration with one `lenny-mcp-bridge` entry for each of the `platform` and `client` servers and launches Claude Code. Each bridge opens a tool connection to `@lenny-runtime-0` and writes `hello` with `role: tools`. Claude Code calls `tools/list` on the `platform` server, the bridge writes `list_tools`, and the adapter answers from `ListPlatformTools` for Alice's session. The bridge drops the internal entries, such as `session.create`, and adds the reference extension's session tools, `start_session` among them.
6. The model calls `start_session`. The extension's handler in the bridge writes a `tool_call` for `session.create` on its tool connection, the adapter forwards it for Alice's session, the gateway checks her session grant and creates a child, and the `tool_result` returns the child's id, which the handler returns to the model. The child's `session_start` carries `lineage: ["claude-code", "reviewer"]` and the tags the handler set. A frame from slot 1's connections can act only for Bob's session.
7. An administrator disables delegation for Alice's environment. When Alice's next message opens a turn, the coordinating replica computes `delegation: false` and calls `UpdateAvailability`, and the adapter writes `availability_changed` with `changedServers: ["platform"]` to slot 0's runtime connection and tool connections before the turn's message.
8. The platform bridge sends `notifications/tools/list_changed`. Claude Code lists again, and `start_session` is gone from the list, while the session tools that manage Alice's child stay ("DP-5" of 0166). Had the model called `start_session` from an old list, the gateway would have answered the extension's `session.create` with `DELEGATION_DISABLED`.
9. Bob's session ends. Slot 1's release ends every process in `runtime-1`, the bridges and their connections included, sweeps the slot, and launches nothing. The next session that binds to slot 1 launches a fresh wrapper, which performs a new handshake before its `session_start` ("SI-3").

## Limits

- **A harness that does not list again keeps a stale list.** The notice prompts a harness, and one that ignores `list_changed` keeps its list until it lists again. The gateway's refusals cover a stale entry, and a tool that became available stays hidden from such a harness until its next launch.
- **A change during a long turn reaches the runtime at the next turn.** Under O6 (e), a change of `delegation` or `questions` while a turn runs is announced at the next turn, and a runtime can make a model call before it reads the notice.
- **A tool server that first appears mid-session waits for the next `session_start`.** A harness reads its MCP configuration at launch, so such a server reaches the runtime at the next restore, resume, or wake, unless the runtime restarts its harness.
- **An operator service's tool list is outside Lenny.** A harness reaches an operator's MCP service over HTTP through `netagent`, and changes to that service's tools reach the harness on its own MCP session with the service ("CR-3" of [`0124-connector-removal`](../0124-connector-removal/change.md)).
- **Order across connections is order of arrival.** Under O3 (b) a tool's events and text the harness printed immediately before the call reach the adapter in the order they arrive ("RP-3").
- **No adapter-local tools.** Under D5 a runtime uses its own filesystem, and a runtime that offers file tools to its model writes them against that filesystem.
- **No tool call reports progress.** A platform tool call, `events.wait` included, and a `client` call write nothing until their `tool_result`, so a runtime meets a call that runs long with no frame until its result (D11).
- **A stdio bridge sends no call groups.** MCP carries no model step, so a stdio bridge sends each `client` call alone, and a provider adapter returns each such call in a response of its own. The in-process bridge and a runtime that runs its own model loop group the calls of a step ("RP-3", "RP-5").
- **A bridge that does not know `internal` lists the operations.** A bridge written before revision 15 ignores the member under "MD-24" and lists the platform operations of 0166 to its harness. The gateway checks each call as it arrives (RPR-9), so such a listing grants nothing.
- **Capabilities stay coarse where today's are.** `interrupt` covers both the suspension signal and the `interrupt` delivery intent's stop, because both use `interrupt_request`.

## Alternatives rejected

> **Revision 10.** [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors under the owner's decision of 2026-11-15 ("Yes, let's drop connectors."). A statement in this section about connectors, `connector:<id>`, the connector client, connector links, `deferredToolDiscovery`, `tool_progress`, or `toolProgress` that the edits of revision 10 did not rewrite is withdrawn and kept as the record. The platform statements stand.

- **Keeping the MCP servers in the adapter.** Today's model keeps an MCP server, its versions, and a Lenny-private nonce in the adapter, a socket per connector, and a bridge for every stdio harness. The owner proposed the move (D1).
- **One aggregated MCP server for every tool server.** The `CH-MCP-CONNECTOR` card's reasons hold for the bridge as they do for the adapter: tool names and resource URIs collide, and capability negotiation is per server.
- **An optional handshake for the simplest runtimes.** The owner asked for a handshake on every runtime (D2), and a version on only some connections leaves the adapter guessing for the rest.
- **Capability negotiation inside MCP `initialize`.** A runtime that uses no MCP would have no handshake, and the adapter no longer speaks MCP.
- **Keeping integration levels as named bundles of capabilities.** The owner asked for a spectrum (D3), and a bundle hides which behaviour the platform depends on.
- **Retiring channels through naming-table rows.** Revision 1 proposed it. A naming-table row records a changed spelling, and a removed channel has none (O11).
- **A per-session token on the tool multiplexer.** Revision 2's mechanism. Under session isolation every process in the slot container runs as the slot UID and serves one session, so the token separates nothing the slot binding does not already separate.
- **`sessionId` on every tool frame.** Revision 2's rule. Under session isolation the connection names the session, and a member that can only repeat it, or contradict it, adds a refusal path and no information.
- **`sessionId` as an optional member checked against the slot's session.** Revisions 3 and 4 kept it, accepted when it named the slot's session and refused otherwise, so that one schema served service mode as well. AR removed service mode, and the owner chose AR's O5 (b), which leaves the member on `session_start` alone (D9).

### What the documentation states

The owner asked on 2026-11-13 that every design's documentation list every setting, default, limit, failure mode, and runtime-facing rule it introduces. The pages above carry these, with no specification section numbers:

- **The handshake.** `docs/reference/adapter-contract.md` and `docs/runtime-author-guide/lifecycle.md` state the order (the server-UID check, the nonce line, `hello`, then `welcome` or a refusal); that `hello` is the first frame; its members; the `hello` bound, `adapter.runtimeHelloTimeoutSeconds`, 10 s by default; the refusal reasons `no_hello`, `malformed_hello`, `unsupported_version`, `capability_dependency`, `capability_missing`, and `role_refused`, each with its retryability; that a runtime exits non-zero on `handshake_refused` and does not dial again; and that the handshake runs at bind, after materialization and setup, and before `session_start`.
- **Where a refusal lands.** `docs/client-guide/error-handling.md`, `docs/reference/error-catalog.md`, and `docs/operator-guide/troubleshooting.md` state that a refused handshake fails a creation with `RUNTIME_HANDSHAKE_REFUSED` or `RUNTIME_CAPABILITY_MISSING`, ends the session `failed` when the refusal meets a resume or a restore, releases the slot, which stays in service, and, for a reason that is not retryable, stops claims of the pod set, sets the `RuntimeHandshakeRefused` condition on the `PodSet` of the pod that exited, and backs off pod creation until a revision with a fixed image builds a new pod set.
- **Capabilities.** `docs/runtime-author-guide/integration-levels.md`, renamed for capabilities, states the catalog of "RP-2" with `childEvents`, its dependency on `childSessions`, and that it has no defined value in v1, what the platform does for a runtime without each capability, the dependency rules with the `422 INVALID_RUNTIME` refusal, the narrowing of dependents by the per-tenant override, the check before the claim against the pod set's recorded offer, and the adapter's check at launch.
- **Frames and sessions.** `docs/reference/adapter-contract.md` states that a frame's session is its connection's slot's session; that no frame other than `session_start` carries `sessionId`; that `session_start`'s `sessionId` is the runtime's to read for log correlation, identity across process restarts, idempotency keys, and derived-session detection, and the adapter never acts on it; that `session_start` and `session_started` carry no `startId`; that every runtime answers each `session_start` with `session_started`; that an unknown member is ignored with no warning while an unknown frame type is reported once per type per session as `runtime_warning`; and that an unknown value of a known enum member is handled as `other` and is never an error, on both sides, with the values that select what the adapter does as the exception that "MD-24" states (D12). It states `lineage` and `tags` on `session_start`, what each holds, that neither grants anything, that `tags` replaces `tracingContext`, and that an extension on a tool connection reads both with `session.self`.
- **Tools.** `docs/runtime-author-guide/platform-tools.md` states `tool_call` with `server`, whose values are `platform` and `client`, and `UNKNOWN_SERVER` for any other value; a `client` call that stays open until the client answers or withdraws it, with a pointer to the client tools page that 0122 writes; `group` with its `id` and `size`; `list_tools`, `tool_list` with the `internal` attribute and which tools carry it, `tool_cancel`, the `tool_result` error codes with `CLIENT_TOOL_CALL_WITHDRAWN`, `CLIENT_TOOL_CALL_INVALID`, and `CLIENT_CHANGED`, the 4 MiB bound on a result with `RESULT_TOO_LARGE`, tool connections with `role: tools`, their bound of 32 per slot, and what a tool connection may carry; that no tool call reports progress; and that a tool call has no duration a runtime may assume, so a runtime stops waiting for a call only with `tool_cancel` (D11).
- **Availability.** `docs/runtime-author-guide/platform-tools.md` states `availability` on `session_start`, that its `toolServers` lists `platform` and, for a runtime that declares `clientTools.supported`, `client`, `availability_changed` with `changedServers` and the events that notify a change of the `client` list, when a change reaches the runtime, and that the gateway checks every call whatever the runtime was last told.
- **The reference bridge.** `docs/runtime-author-guide/runtime-sdk.md` states the in-process and stdio bridges, one MCP server per tool server with the `platform` and `client` servers, the mapping to frames, the hiding of internal entries, call groups from the in-process bridge and their absence from a stdio bridge, the `list_changed` notice, and that the session tools of the reference extension, with `--session-tools` and `--session-defaults`, replace the gateway-hosted delegation tools, which the same page states in full under 0166.
- **Versioning.** `docs/runtime-author-guide/runtime-sdk.md` and `docs/reference/adapter-contract.md` state the integer protocol version, that a new version is issued only for a change that breaks a frame, that the adapter supports the current version and the previous one, and that a version leaves no earlier than 6 months after its successor ships.
- **Monitoring.** `docs/reference/metrics.md` states `lenny_runtime_handshake_total{result, reason, version, role}` and `lenny_runtime_capability_mismatch_total{runtime, runtime_revision}`, and the audit event `runtime.capabilities.underdeclared`. `docs/operator-guide/observability.md`, `docs/runbooks/checkpoint-stale.md`, and `docs/alerting/openslo.yaml` restate `lenny_checkpoint_duration_seconds` and `CheckpointDurationHigh` without the `level` label.
- **Settings.** `docs/operator-guide/configuration.md` states `adapter.runtimeHelloTimeoutSeconds`, 10 s by default, and `adapter.maxToolConnectionsPerSlot`, 32 by default.
- **Commands.** `docs/operator-guide/lenny-ctl.md` states `lenny runtime init` scaffolding capabilities and `lenny runtime validate` selecting conformance cases by capability ("RP-8"), and `docs/index.md` names capabilities in place of levels.

## Instructions for reviewers of other designs

- [`0145-session-isolation`](../0145-session-isolation/change.md): this design asks for these changes, each as a request:
  - **SI-2 and SIR-3.** A slot's `CH-MSGSOCK` endpoint accepts several connections: one runtime connection and, under RP O3 (b), tool connections from the slot's bridges, each bound to the slot by name and peer UID. The drain of SIR-5 after End closes every queued connection of either role.
  - **SI-2, the tool multiplexer row, "Tool multiplexer" in Terms, and the link to RP-5.** Under RP O3 (b) the multiplexer and its `/tmp` socket leave. The section the link names is now "RP-5 Reference MCP bridge".
  - **`CH-RUNTIMEOPS`.** It leaves under RP O7 (a), settled on 2026-11-12, so SI needs no per-slot endpoint for it, and today's pod-wide `@lenny-runtime-ops` goes.
  - **The adapter-local tools.** The owner retired them on 2026-11-12 (RP D5), so the broker needs no operation for them, and no SI text needs to provide for adapter file access on a runtime's behalf.
  - **SI-3.** The runtime process launches at bind, after materialization and setup, and its handshake and the capability check against the session's effective capabilities run before `session_start` (RP D6, RPR-20). A handshake refusal ends the bind and releases the slot as after any session; it does not make the slot dead. The release launches no runtime process.
  - **SI-4.** Drop any cause of a dead slot that rests on a handshake at warm-up or at a relaunch after release, because neither exists. A refusal that is not retryable stops the pod accepting binds, and the pod exits once idle ("RP-1").
  - **"Labels from other designs".** RP O10 is retired as SI-2 foresaw, and RPR-8 now allows the tools on every pod.
  - **SIR-3 and SI-2's check table.** Under AR's O5 (b) (D9), no frame other than `session_start` carries `sessionId`, so the refusal of a frame that names a session the slot does not hold leaves: the adapter takes every frame's session from the slot and ignores the member silently where a runtime still writes it. The worked example's refused frame and the tier 1 test change with it.
- [`0146-session-lifecycle`](../0146-session-lifecycle/change.md#sl-3-suspension-and-the-open-turn): restate L15, "SL-3", "Limits", the worked example, the tests, and the Terms row for integration levels in capability terms. "A runtime below Full level" becomes "a runtime whose session's effective capabilities lack `interrupt`", and "a Full-level runtime" becomes "a runtime that declares `interrupt`". Under O7 (a), `interrupt_request` travels on `CH-MSGSOCK`. The qualifying-activity list counts `tool_call` in flight on any connection of the slot, and L24's cancellation answers in-flight tool calls on every connection of the slot with `CANCELLED`.
- [`0135-message-delivery`](../0135-message-delivery/change.md#md-24-runtime-frames-and-leniency): "MD-24" states that the handshake is the one exchange every runtime must perform, that a first frame other than `hello` is refused, and that the leniency rules do not soften it. Its frame table points to this design's §28.5.3 row for the handshake frames, `session_start`, `session_started`, and the tool frames, which that row lists in full. "MD-23"'s session tools leave the gateway for the reference extension of 0166, and the platform operations take 0166's names. `set_tracing_context` and `tracingContext` leave, because tags replace them ("DP-6" of 0166). Its rule for omitting `sessionId` reduces to RPR-18 and RPR-21: no frame other than `session_start` carries `sessionId`, which `session_start` keeps as data the adapter never acts on, and a member a runtime still writes on another frame is ignored silently as an unknown member. The leniency rules lose their example of a frame that names a session the connection does not serve. `startId` leaves under AR's D2, which settles C1 as (c). "`interrupt_request` stays on `CH-RUNTIMEOPS`" follows O7. "MD-2" and MDR-9 replace "Full" with the `interrupt` capability. "Runtime-reported usage needs Full level" becomes a statement about the usage frames, which need no capability. The conformance rows of §15.4.6 are restated by capability.
