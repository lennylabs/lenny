- **O12. The in-gateway translators and MCP tools between the first step that changes what they call and 0138.S6.** 0122.S1 changes the executor's `Message` and the handling of `tool_call` frames, which the OpenAI translators reach through `Executor.Send` (`pkg/gateway/environment/translator/openai_chat.go`), and 0138.S6 removes the translators and the client MCP tools last.   - (a) The surfaces that leave may stop working from the first step that changes what they call. Each earlier step deletes or stubs the surface code it would otherwise port, and 0138.S6 removes the rest. 0122.S1 then neither maps client tools on the translators nor keeps them compiling against the old executor types.
  - (b) Earlier steps keep the surfaces working and port them. 0122.S1 then keeps the translators compiling and refusing `tools` against the new executor types.
  - (c) A new early step of 0138 removes the surfaces ahead of 0135.S1, which leaves MCP clients without a path until 0138.S5.

  - (raised by the M3 readiness review, 2026-11-19; sources: client-api-sessions-C12)
- **O13. Cold continuation of a client tool round trip over REST, and O4.** Under 0138 every provider adapter reaches Lenny through REST. A cold turn of a tool round trip creates a new session whose history carries the earlier calls and results, and whose new input carries the results of the final round ([`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), R15 and "RO-10"). The answer route answers calls of the session it names, so a new session has no call that the final round's results could answer. O4 refuses client tools on a REST session whose revision is `one_shot` or refuses injection, on the premise that such a session could never receive its results. Under the blocking call a result reaches the runtime inside the turn, and only a late result needs a further message. The question is raised on 0138 and on [`0120-anthropic-messages-api`](../0120-anthropic-messages-api/change.md) (its O22) as well. Revision 13 restated it for the blocking interface.
  - (a) Add a REST cold form and withdraw O4. On a new session, the first message whose `conversation.entries` end with an assistant entry that carries `clientToolCalls` may carry the matching results in its marked user entry, and the gateway writes the envelope's `toolResults` from them, with the external ids passed to the runtime as opaque strings, as "CT-1" states for cold turns. A `one_shot` session, or one that refuses injection, accepts client tools, and a late result for it returns `late` with no message to carry it, which the documentation states.
  - (b) Add the same REST cold form and keep O4 for `one_shot` runtimes and for revisions that refuse injection.
  - (c) Add no REST cold path. 0138 "RO-10" then states that a provider adapter cannot continue a tool round trip cold.
  - Recommendation: (a). 0138 sends a request cold on every failed conditional send, after an expiry, after a recovery to an older checkpoint, and after an edited history, so the cold branch is common. Under the blocking call a `one_shot` runtime receives every answer that arrives within the hold, so O4's premise holds only for late results, and 0166's decision 23 asks that client tools serve every runtime. The marked entry is the one form, so the REST body carries cold results in one place.
  - Blocks: 0122.S1, 0138.S1, and 0138.S5.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F2, client-api-sessions-C1; restated by revision 13)
- **O14. An answer after the runtime cancels a call.** Revision 12 asked how a runtime's retraction of a pending call under MD-11 of [`0135-message-delivery`](../0135-message-delivery/change.md) behaves on a session a provider adapter drives, because the gateway cannot tell an adapter's session from another REST session. The blocking interface has no pending set, and a runtime that stops waiting writes RP-3's `tool_cancel`, which withdraws the call with the reason `cancelled` for every client alike ("CT-5"). The part of the question that remains is what happens to an answer that arrives after the cancel. 0135 records the original question as its O21 and 0138 as its O22, so the owner's answer is recorded in all three changes. Revision 13 restated it.
  - (a) The answer returns `late`, and the result reaches the runtime in `toolResults` on the client's next message, as for every other withdrawal (DPR-13 of 0166). A runtime that cancelled the call ignores the result or shows it to its model.
  - (b) The answer returns `withdrawn`, and the gateway drops the result, because the runtime chose to stop waiting.
  - Recommendation: (a). It gives every withdrawal one behavior, follows DPR-13 of 0166, under which a result that arrives after the call is gone reaches the runtime, and keeps a side effect the client already caused visible to the model.
  - Blocks: the cancellation paragraph of "CT-5" and the client-call rows of 0135's MD-11.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F10, client-api-sessions-C4; restated by revision 13)
- **O16. The tool set a call's validation reads.** "CT-3" keeps compiled schemas only for the turn, and "CT-4" checks calls against the turn's `clientTools`. Under [`0135-message-delivery`](../0135-message-delivery/change.md) a turn can consume several client messages (MD-5), a client message can wait on the queue or the resume path and be delivered later by another replica, and a coordinator handoff hands an open turn to a replica that did not receive the client request (MD-3). Under the blocking call a turn stays open while its calls wait, so a client message steered into the turn can arrive between two calls, and under the turn rule `all` a turn another sender started carries the tools of the client's most recent message. Revision 13 restated the question.
  - (a) A call's tool set is that of the newest client message the turn consumed before the call, or, for a turn another sender started under `all`, of the client's most recent message. Each accepted client message stores its `clientTools` and `toolChoice` with its inbox entry, bounded by `clientTools.maxSchemaBytes`. An adopting replica rebuilds the tool set from the turn's `delivered` entries, and a call whose tool set cannot be read is answered with a retryable error that `lenny_client_tool_call_invalid_total` does not count.
  - (b) As (a), with the union of the tool sets of every client message the turn consumed.
  - (c) The tool set of the message that opened the turn alone. The tools of a steered client message are ignored, and the steered sentence of "CT-1" is withdrawn.
  - Recommendation: (a). It matches the steered case of "CT-1" and gives the runtime one list to present at each point of the turn.
  - Blocks: 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F6; restated by revision 13)
- **O17. What a turn does after a violation, and what a `MODIFY` may change.** Under the blocking call the gateway answers each call of a violating group with an error `tool_result` naming the reason, so the runtime's model history holds a result for every call. T6 then fails the turn. "CT-8" does not state whether a `MODIFY` may remove, add, rename, or re-identify a call, and a turn that fails after a `MODIFY` counts against the runtime's revision. Revision 13 restated the question, whose earlier options turned on a runtime that ended its turn holding calls with no results.
  - (a) The error results are the whole response: the turn continues, the model sees the reason, the violation counts on the metric and in the audit, and T6's failure of the turn is narrowed to that.
  - (b) The error results and a failed turn, as T6 states.
  - For a `MODIFY`: it may change `arguments` and `input` alone, a change to `id`, `name`, or the number of calls is a violation with a reason of its own, and a violation after a `MODIFY` carries that reason so the rollout metric separates it from the runtime's defects.
  - Recommendation: (a), with the `MODIFY` limit. It follows the leniency rule of MD-24, under which a conversation does not stop because one frame was refused, and the blocking call lets the model correct its own call. It narrows T6, which the owner settled, so the owner decides it.
  - Blocks: 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F7; restated by revision 13)
- **O18. Calls after a restore from an older checkpoint, and the scope of `duplicate_id`.** A pod loss withdraws the open calls, and a late result reaches the restored runtime in `toolResults` (DPR-13 of 0166). A runtime restored from a checkpoint taken before the turn that made the call holds neither the client message that started the turn nor the call. A restored runtime that numbers its calls from restored state can reuse an id. Revision 12 also asked whether a stale derive copies a pending set, which lapses because a derive copies no open call. 0144 records the original question as its open decision 10. Revision 13 restated it.
  - (a) The gateway delivers the late result whatever the checkpoint holds, and a runtime that does not know the id treats the result as context or drops it, under the runtime obligation of "CT-7". `duplicate_id` covers the session's open calls and the late results that wait for delivery.
  - (b) At a restore from a checkpoint older than the call, the gateway drops the call's late result and emits `tool_call_withdrawn` with a restore reason, as MD-3 of 0135 marks messages `consumed_unrecorded`. `duplicate_id` covers the same set as in (a).
  - Recommendation: (a). It follows DPR-13 of 0166, under which no result the client sends is lost, and it keeps the gateway from reading a checkpoint's contents to decide a delivery.
  - Blocks: 0122.S1, and decision 10 of 0144.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F8, client-api-sessions-C7; restated by revision 13)
- **O19. The per-tenant override for client tools.** O7 lets a tenant clear `clientTools.supported` and `clientTools.customTools` and append to `clientTools.reservedNames`, and "CT-8" relies on it for a tenant that must not use client tools. D17 of [`0140-runtime-revisions`](../0140-runtime-revisions/decisions.md), settled on 2026-11-09 like O7, states that the override "may only narrow `capabilities.interaction` and `capabilities.injection`", and 0140's "Per-tenant capability override" lists those two alone. [`0139-runtime-protocol`](../0139-runtime-protocol/change.md) "RP-2" classes `clientTools.reservedNames` as a member that is not a capability. Neither decision names the other, and the question is raised on 0140 as well.
  - (a) 0140 takes O7: the override gains the two narrowings and the append, and 0140 states how an append to a member outside the capability catalog is stored.
  - (b) O7 is withdrawn, and a tenant disables client tools only by clearing `conversationInput`, which 0140 then lists. "CT-8" **Approvals** changes to match.
  - (c) O7 is withdrawn, and a tenant cannot disable client tools.
  - Recommendation: (a). It keeps the control that "CT-8" names, and it is a narrowing of the kind D17 allows.
  - Blocks: the override rule of 0122.S1, and 0140.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F12)
- **O20. Boundary outcomes and names that the design leaves unstated.** Each item has its own recommendation. Revision 13 dropped the items on `abandonPendingToolCalls` and on the bound of the serialized pending set, whose subjects no longer exist, and restated the others.
  - The REST status and code of each limit of "CT-3", which "CT-3" states as "`413` or `400` as the surface pairs them". Recommendation: `400 CLIENT_TOOL_DEFINITION_INVALID` naming the limit for each limit, with `413 MESSAGEPART_TOO_LARGE` kept for result parts.
  - The point of the capability check for a message with tools to an existing session, and for the first message after a two-step create, both of which arrive after the pod is claimed. Recommendation: at message admission, against the session's effective capabilities, before the message is written.
  - A REST client message with `clientTools` addressed to a child session, whose client is its parent. Recommendation: refuse it with `422 CLIENT_TOOLS_UNSUPPORTED` naming the child, so tools are never dropped with a success status as F-15.1.82 records.
  - Names: the audit events for a delivered group, an answer, a withdrawal, a late result's delivery, and a violation (recommendation: `client_tool_call.requested`, `client_tool_call.answered`, `client_tool_call.withdrawn`, `client_tool_call.late`, and `client_tool_call.invalid`); the gateway flags for the limits (recommendation: `--client-tools-max-tools`, `--client-tools-max-schema-bytes`, `--client-tools-max-open-calls`, and `--client-tools-max-arguments-bytes`); and the answer of the approve and deny routes of MD-19 for the external id of a call to a REST client's tool (recommendation: `404`, because no approval exists for such a call, while a call to a parent's tool held by `approvals.parentTools` is resolved through 0142's routes).
  - A bound on the serialized open calls and late results of a session, which `maxOpenCalls` times `maxArgumentsBytes` puts at 8 MiB in the session store, in the session read, and in `tool_call` events. Recommendation: a further limit, `clientTools.maxOpenBytes`, refused as `limit_exceeded`.
  - The retention of a result part staged as a `lenny-blob://` reference, which a late result or a cold history reads after the 1-hour default expiry of a live-delivery blob that 0135 reports **[unverified]**. Recommendation: a staged result part is kept for the session's retention, as the transcript's other staged parts are.
  - Blocks: the text and tests of these items in 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F19, 0122-F20, 0122-F21, 0122-F22, 0122-F23; restated by revision 13)
- **O21. The edge of 0122.S1 on 0146.S1 if 0146.S1 is split.** 0122.S1 depends on 0146.S1 for the states `idle` and `dormant`, qualifying activity, and the close rule (SL-1, SL-6, and SL-7). SL-Q10 of [`0146-session-lifecycle`](../0146-session-lifecycle/decisions.md) asks whether 0146.S1 is split into states, the store migration, and the caps (SL-1 and SL-10); suspension and tree suspension (SL-3 to SL-5); idle and dormancy (SL-6); and close and cascade (SL-7 and SL-9). This entry follows the owner's answer to SL-Q10 and adds no choice of its own.
  - (a) If SL-Q10 takes (a), 0122.S1 depends on the split steps that carry SL-1, SL-6, and SL-7 in place of 0146.S1, and the step text of 0122.S1 names them.
  - (b) If SL-Q10 takes (b), the edge on 0146.S1 stays as it is.
  - Recommendation: follow SL-Q10, whose recommendation is (a). 0122.S1 does not read suspension or tree suspension, so it does not wait on that step.
  - Blocks: the `depends-on` entry of 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; requested by change 0146; mirrors SL-Q10 of 0146)

## Decisions

Settled by the owner on 2026-11-09. T1 to T8 came with revision 1, and the owner revised T5 and added T9 with revision 2:

| ID | Decision | Where |
| :-- | :-- | :-- |
| T1 | The mechanism is turn-ending. The runtime's end-of-turn `message` carries `clientToolCalls`, as the `response` frame did before the message delivery design's MD-24 replaced it. The next client request reaches the runtime as a `message` with a `toolResults` member. The tools arrive in `conversation.clientTools` and `conversation.toolChoice` on every turn. | CT-1 |
| T2 | The v1 surfaces are Chat Completions, Responses, REST, and the Messages API. MCP gets client tools only as Lenny-specific tool arguments. | CT-6 |
| T3 | Lenny is not prescriptive. `capabilities.clientTools` is the runtime author's declaration, and Lenny refuses client tools only on runtimes that do not declare it. Lenny's own reference runtimes do not declare it in v1. | CT-2 |
| T4 | On Chat Completions, each tool round trip continues cold with the history. Superseded on 2026-11-14 by the conversation fingerprint rule of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md#ro-10-the-provider-adapters): a round trip continues warm on the session the fingerprint finds, under that design's conditional send (R16), and continues cold with the history otherwise. | CT-6, CT-7 |
| T5 | A client message without the pending results is refused, apart from the REST exception of T9. For a runtime that does not declare the `steer` delivery intent of [`0135-message-delivery`](../0135-message-delivery/change.md), inter-session messages and other inbox deliveries wait until the results arrive, and are delivered right after them. For a steer-declaring runtime, inbox deliveries are not held while calls are pending, and the runtime places them after the results. The cold-history builder places a message that arrived while calls were pending after their results, so each call and its result stay adjacent. | CT-5, CT-7 |
| T6 | The gateway passes `tool_choice` and the parallel limit to the runtime. It validates the runtime's response: declared tool names, arguments against `input_schema`, `tool_choice`, and the parallel limit. A violation fails the turn with a do-not-retry error and a per-revision metric. The gateway does not repair the response. The owner confirmed with revision 2 that the JSON arguments of a function tool are still validated against its input schema. | CT-4 |
| T7 | Client tools are not delegated. | CT-9 |
| T8 | This is a standalone design, landing after the Messages design's AM-A and alongside the F-15.1.82 fix. | "Steps" in `steps.md` |
| T9 | On REST, a client message without the pending results is refused unless the request sets `abandonPendingToolCalls: true`, which turns the pending calls into "cancelled by client" error results. MCP clients reach `abandonPendingToolCalls` as a generated argument in the MCP adapter. Chat Completions, Responses, and the Messages API always refuse such a message. | CT-5 |

The owner's decisions of 2026-11-09 on [`0120-anthropic-messages-api`](../0120-anthropic-messages-api/change.md) also bind this design: that surface has no open turns, the conversation input carries ordered entries with the new input marked (its O3), warm continuation uses an HMAC-SHA256 conversation digest with an in-flight join that reattaches a retry to the running turn (its O2 and M1), and every failure after dispatch carries `x-should-retry: false`.

Settled by the owner on 2026-11-09 with revision 2, from the open decisions of revision 1. O1, O2, and O4 to O7 take revision 1's recommendation. O8 and O9 take the owner's own answers:

| ID | Question | Decision | Where |
| :-- | :-- | :-- | :-- |
| O1 | The form of the capability. | An object, `capabilities.clientTools.supported` with `reservedNames`, that requires `capabilities.conversationInput: true`. The cold path delivers earlier calls and results as structured history, which transcript rendering cannot express, so the dependency on conversation input is structural. `reservedNames` lets a runtime protect the names of its own model-visible tools, which the gateway cannot discover. O9 adds `customTools`. | CT-2 |
| O2 | Whether a runtime may declare that it accepts results only warm. | No field. A declaring runtime accepts results cold from history, and for calls it no longer holds in memory, or answers with an end-of-turn `message` carrying `error`. A harness wrapper that parks a call in memory can declare the capability and fail a cold continuation with an error. A `warmOnly` field is revisited when a harness wrapper asks for it. | CT-7 |
| O4 | REST sessions whose revision cannot accept a further message (`capabilities.interaction: one_shot`, or `capabilities.injection.supported: false`). | Client tools on such a session are refused at creation with `422 CLIENT_TOOLS_UNSUPPORTED`, naming the missing capability. On REST a session has no cold path with history, so a session that cannot take a second message can never receive its results. Chat Completions, Responses, and the Messages API are unaffected, because their cold path delivers results in a new session. | CT-2, CT-6 |
| O5 | A retried Responses continuation that carries results. | The Messages API's in-flight join extends to Responses continuations: a continuation of response `R` whose input equals the input of the running continuation of `R` reattaches to that turn. The SDKs retry a dropped connection twice by default **[external]**, and a results request is the most frequent request in a tool loop. Chat Completions stays cold under T4. REST need no join, because a second results message finds no pending calls and is refused. | CT-7 |
| O6 | How a deployer's output interceptors see call arguments. | The `PostAgentOutput` payload gains an optional `clientToolCalls` member beside the output parts, so an existing output filter covers arguments and custom tool input with no change to its registration. | CT-8 |
| O7 | The per-tenant capability override for client tools. | A tenant may clear `clientTools.supported`, may clear `clientTools.customTools`, and may append to `clientTools.reservedNames`. A widening is refused. This is the narrowing form RV-1 gives `capabilities.interaction` and `capabilities.injection`. Clearing `customTools` follows from O9 under the same narrowing rule. | CT-2 |
| O8 | A re-run of a session that used client tools. | Server-side replay no longer exists under [`0144-session-derive`](../0144-session-derive/change.md). A client that re-runs a session re-sends its messages itself and executes its own tools. A derive from a session with pending client calls copies them, and the derived session's first client request must carry the results. Revision 3 narrows the copy to `from: latest` (T10) and lets that request abandon the calls instead (T12). | CT-7 |
| O9 | OpenAI `allowed_tools` and `custom` tools. | `allowed_tools` is accepted as a restriction in `toolChoice`, `allowedNames`, which the T6 check enforces. `custom` tools are accepted for runtimes that declare `clientTools.customTools`. For a custom tool call the gateway checks the name, that the input is a string, `tool_choice`, and the parallel limit, and never checks the grammar. Grammar conformance is the runtime's responsibility, and the client verifies it. | CT-1, CT-2, CT-3, CT-4, CT-6 |
