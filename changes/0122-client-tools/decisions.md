- **O13. Cold continuation of a client tool round trip over REST, and O4.** Under 0138 every provider adapter reaches Lenny through REST. A cold turn of a tool round trip creates a new session whose history carries the earlier calls and results, and whose new input carries the results of the final round ([`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), R15 and "RO-10"). This design states that REST has no cold path with history ("CT-6", REST row), refuses `toolResults` on a session with no pending calls (rule 5 of "CT-5"), and under O4 refuses client tools on a REST session whose revision is `one_shot` or refuses injection, on the premise that only the provider surfaces had a cold path. The question is raised on 0138 and on [`0120-anthropic-messages-api`](../0120-anthropic-messages-api/change.md) (its O22) as well.
  - (a) Add a REST cold form and withdraw O4. On a session with no pending set, the first message whose `conversation.entries` end with an assistant entry that carries `clientToolCalls` may carry the matching results in its marked user entry, and the gateway writes the envelope's `toolResults` from them. Rule 5 gains that exception, the ids of such a turn pass to the runtime as opaque strings, as "CT-1" states for cold turns, and "CT-1" states the form of an external id on REST so that an adapter can derive its own identifiers without keeping a record.
  - (b) Add the same REST cold form and keep O4 for `one_shot` runtimes and for revisions that refuse injection.
  - (c) Add no REST cold path. 0138 "RO-10" then states that a provider adapter cannot continue a tool round trip cold.
  - Recommendation: (a). 0138 sends a request cold on every failed conditional send, after an expiry, after a recovery to an older checkpoint, and after an edited history, so the cold branch is common, and under O4 a `one_shot` runtime with client tools would be refused on every request behind every adapter, which contradicts "Cold sessions" in "CT-5". The marked entry is the one form, so the REST body carries results in one place.
  - Blocks: 0122.S1, 0138.S1, and 0138.S5.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F2, client-api-sessions-C1)
- **O14. Retraction on a session that a provider adapter drives.** "CT-5" ("Retraction") and MD-11 of [`0135-message-delivery`](../0135-message-delivery/change.md) answer a retraction with `retracted` on a REST session and with `too_late` on a provider surface. Under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md) a provider adapter creates ordinary REST sessions, the gateway never reads the protocol header for a decision (R14), and R18 is withdrawn, so the gateway cannot tell the two apart. The question is raised on 0135 as its O21 and on 0138 as its O22, so the owner's answer is recorded in all three changes.
  - (a) One Lenny behavior, the REST row. A retracted call leaves the pending set and fires a `tool_use` event with phase `retracted`, and an adapter drops the client's results for a retracted call, using the event or the remaining ids in the `409 CLIENT_TOOL_CALLS_RETRACTED` details. The provider rows leave "CT-5", "CT-6", "Limits", and MD-11 for the adapters, and the same reading applies to `abandonPendingToolCalls`, which an adapter may then use.
  - (b) A session-creation field that an adapter sets, under which a retraction answers `too_late`. It brings back part of R18 and needs a capability tag under "RO-4".
  - Recommendation: (a).
  - Blocks: the retraction rows of "CT-5", which land with 0135.S2, and 0135.S2.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F10, client-api-sessions-C4)
- **O15. Custody of a results message.** Rule 1 of "CT-5" clears the pending set and writes the envelope in two writes. A gateway failure after the clear and before the inbox accepts the message loses the results, the client's retry answers `409`, and the runtime holds calls that no message answers. A results message can also be held (`pending`) on the resume path or behind a refused resume admission, and a client can retract its own `pending` message with `DELETE /v1/sessions/{id}/messages/{messageId}` under MD-7 of [`0135-message-delivery`](../0135-message-delivery/change.md).
  - (a) The gateway writes the inbox entry first, and the clear is idempotent on redelivery of that message id.
  - (b) The pending set records the id of the accepted results message. A second results message is refused while the id is recorded, and the set is cleared when that message becomes `consumed`.
  - For a held results message: (i) its client cannot retract it, and the `DELETE` answers `409`; or (ii) a retraction restores the pending set.
  - Recommendation: (b) with (i). Under (b) the pending set always names the message that answers it, and under (i) the runtime never holds calls that no message answers. The `load_local` and `chaos` tests gain the failure and the retraction cases.
  - Blocks: 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F5)
- **O16. The tool set a turn's validation reads.** "CT-3" keeps compiled schemas only for the turn, and "CT-4" checks calls against "the turn's `clientTools`". Under [`0135-message-delivery`](../0135-message-delivery/change.md) a turn can consume several client messages (MD-5), a client message can wait on the queue or the resume path and be delivered later by another replica, and a coordinator handoff hands an open turn to a replica that did not receive the client request (MD-3). CTR-1 limits calls to the tools of "the request that started the turn", while "CT-1" lets a steered client request add its own tools. The term "Inbox delivery" excludes the client's own messages and includes held messages from the session inbox, and a client's own queued message that is held when a turn ends with calls falls under both.
  - (a) The turn's tool set is that of the newest client message the turn consumed. Each accepted client message stores its `clientTools` and `toolChoice` with its inbox entry, bounded by `clientTools.maxSchemaBytes`. An adopting replica rebuilds the tool set from the turn's `delivered` entries, and a turn whose tool set cannot be read fails with a retryable error that `lenny_client_tool_call_invalid_total` does not count. CTR-1 names the newest consumed client message. A client's own held message is not an inbox delivery: it waits behind pending calls and is delivered after the results turn as a turn of its own, with its own tools.
  - (b) As (a), with the union of the tool sets of every client message the turn consumed.
  - (c) The tool set of the message that opened the turn alone. The tools of a steered client message are ignored, and the steered sentence of "CT-1" is withdrawn.
  - Recommendation: (a). It matches the steered case of "CT-1" and gives the runtime one list to present at each point of the turn.
  - Blocks: 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F6)
- **O17. What a runtime receives when the gateway refuses its calls, and what a `MODIFY` may change.** After a "CT-4" violation or a `PostAgentOutput` rejection, the runtime has ended its turn with calls in its model history, the gateway records no pending set, and the next client message carries no results. A model API that requires each call to be followed by its result then refuses the runtime's next model request. "CT-8" does not state whether a `MODIFY` may remove, add, rename, or re-identify a call, and a turn that fails after a `MODIFY` counts against the runtime's revision.
  - (a) The gateway answers the refused end-of-turn `message` with the `error` frame of MD-24 of [`0135-message-delivery`](../0135-message-delivery/change.md), naming the code, the reason, and the call ids, and the runtime discards the calls or answers them itself before its next turn.
  - (b) The session ends `failed`.
  - (c) The gateway synthesizes error results for the refused calls on the next client message.
  - For a `MODIFY`: it may change `arguments` and `input` alone, a change to `id`, `name`, or the number of calls is a violation with a reason of its own, and a failure after a `MODIFY` carries that reason so the rollout metric separates it from the runtime's defects.
  - Recommendation: (a), with the `MODIFY` limit. It follows the leniency rule of MD-24, under which a conversation does not stop because one frame was refused.
  - Blocks: 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F7)
- **O18. Pending calls after a restore from an older checkpoint, a stale derive, and the scope of `duplicate_id`.** A REST session restored from a checkpoint taken before the turn that issued its pending calls keeps the set, and its runtime holds neither the client message that caused the turn nor the calls. A `from: latest` derive with `allowStale: true` of [`0144-session-derive`](../0144-session-derive/change.md) can copy a pending set onto a snapshot older than that turn. The `duplicate_id` rule of "CT-4" needs every call id the session ever used, which no store keeps, and a restored runtime that numbers its calls from restored state reuses an id. The question is also recorded on 0144 as its open decision 10, so the owner's answer is recorded in both changes, and it narrows the derive copy that client-api-sessions-C7 asks 0144 to take.
  - (a) At a restore from a checkpoint older than the turn that issued the pending set, the gateway clears the set and emits a `tool_use` event with a restore reason, as MD-3 of [`0135-message-delivery`](../0135-message-delivery/change.md) marks messages `consumed_unrecorded`. A derive copies the pending set only when its snapshot is at or after that turn. `duplicate_id` covers the `message` and the current pending set.
  - (b) The set stays, and the runtime fails the turn with `error`. `duplicate_id` keeps the session scope, with a bounded store of issued ids that a restore resets.
  - (c) The gateway delivers the missing turn as history.
  - Recommendation: (a).
  - Blocks: 0122.S1 and 0144.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F8, client-api-sessions-C7)
- **O19. The per-tenant override for client tools.** O7 lets a tenant clear `clientTools.supported` and `clientTools.customTools` and append to `clientTools.reservedNames`, and "CT-8" relies on it for a tenant that must not use client tools. D17 of [`0140-runtime-revisions`](../0140-runtime-revisions/decisions.md), settled on 2026-11-09 like O7, states that the override "may only narrow `capabilities.interaction` and `capabilities.injection`", and 0140's "Per-tenant capability override" lists those two alone. [`0139-runtime-protocol`](../0139-runtime-protocol/change.md) "RP-2" classes `clientTools.reservedNames` as a member that is not a capability. Neither decision names the other, and the question is raised on 0140 as well.
  - (a) 0140 takes O7: the override gains the two narrowings and the append, and 0140 states how an append to a member outside the capability catalog is stored.
  - (b) O7 is withdrawn, and a tenant disables client tools only by clearing `conversationInput`, which 0140 then lists. "CT-8" **Approvals** changes to match.
  - (c) O7 is withdrawn, and a tenant cannot disable client tools.
  - Recommendation: (a). It keeps the control that "CT-8" names, and it is a narrowing of the kind D17 allows.
  - Blocks: the override rule of 0122.S1, and 0140.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F12)
- **O20. Boundary outcomes and names that the design leaves unstated.** Each item has its own recommendation.
  - `abandonPendingToolCalls: true` on a session with no pending calls, including after a retraction removed the last call. Recommendation: the gateway ignores the field and delivers the message as an ordinary client message, because the client cannot tell a retraction race from its own request.
  - The REST status and code of each limit of "CT-3", which "CT-3" states as "`413` or `400` as the surface pairs them". Recommendation: `400 CLIENT_TOOL_DEFINITION_INVALID` naming the limit for each of the four limits, with `413 MESSAGEPART_TOO_LARGE` kept for result parts.
  - The point of the capability check for a message with tools to an existing session, and for the first message after a two-step create, both of which arrive after the pod is claimed. Recommendation: at message admission, against the session's effective capabilities, before the message is written.
  - A client message with `clientTools` addressed to a child session, which "CT-9" never offers tools. Recommendation: refuse it with `422 CLIENT_TOOLS_UNSUPPORTED` naming the child, so tools are never dropped with a success status as F-15.1.82 records.
  - Names: the audit events for a requested call, a completed call, an abandoned set, and a violation (recommendation: `client_tool_call.requested`, `client_tool_call.completed`, `client_tool_call.abandoned`, and `client_tool_call.invalid`, beside MD-11's `client_tool_call.retracted`); the gateway flags for the four limits (recommendation: `--client-tools-max-tools`, `--client-tools-max-schema-bytes`, `--client-tools-max-pending-calls`, and `--client-tools-max-arguments-bytes`); and the id that a `tool_use` event with `target: "client"` carries, with the answer of the approve and deny routes of MD-19 for it (recommendation: the external id, and `404` from those routes, because no approval exists for a client tool call).
  - A bound on the serialized pending set, which `maxPendingCalls` times `maxArgumentsBytes` puts at 8 MiB on the session row, in the session read, in `tool_use` events, and in each derive copy. Recommendation: a fifth limit, `clientTools.maxPendingBytes`, refused as `limit_exceeded`.
  - The retention of a result part staged as a `lenny-blob://` reference, which a cold history reads after the 1-hour default expiry of a live-delivery blob that 0135 reports **[unverified]**. Recommendation: a staged result part is kept for the session's retention, as the transcript's other staged parts are.
  - Blocks: the text and tests of these items in 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; sources: 0122-F19, 0122-F20, 0122-F21, 0122-F22, 0122-F23)
- **O21. The edge of 0122.S1 on 0146.S1 if 0146.S1 is split.** 0122.S1 depends on 0146.S1 for the states `idle` and `dormant` and the close rule (SL-1, SL-6, and SL-7). SL-Q10 of [`0146-session-lifecycle`](../0146-session-lifecycle/decisions.md) asks whether 0146.S1 is split into states, the store migration, and the caps (SL-1 and SL-10); suspension and tree suspension (SL-3 to SL-5); idle and dormancy (SL-6); and close and cascade (SL-7 and SL-9). This entry follows the owner's answer to SL-Q10 and adds no choice of its own.
  - (a) If SL-Q10 takes (a), 0122.S1 depends on the split steps that carry SL-1, SL-6, and SL-7 in place of 0146.S1, and the step text of 0122.S1 names them.
  - (b) If SL-Q10 takes (b), the edge on 0146.S1 stays as it is.
  - Recommendation: follow SL-Q10, whose recommendation is (a). 0122.S1 does not read suspension or tree suspension, so it does not wait on that step.
  - Blocks: the `depends-on` entry of 0122.S1.
  - (raised by the M3 readiness review, 2026-11-19; requested by change 0146; mirrors SL-Q10 of 0146)

- **O22. The stream form of a custom tool call on Chat Completions.** O10 refuses a Chat Completions request with `stream: true` that declares a custom tool until OpenAI documents a stream form. Desk validation VAL-010 found that OpenAI's OpenAPI description (version 2.3.0) and `openai-python` v3.57.0 still type a streamed tool-call delta as `function` alone, and that `openai-node` v7.62.0, since a commit of 2026-08-12, types `delta.tool_calls[]` with `type: "custom"` and a `custom` member holding `name` and `input` **[external]**. This part of the change is adapter work under O8 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md).
  - (a) Keep the refusal until OpenAI's API reference or OpenAPI description documents the form. Record `openai-node`'s type as the signal to watch, and record what the live API emits in the provider SDK probe P6 of the M3 readiness validation plan.
  - (b) Treat `openai-node`'s type as the documented form, lift the refusal, and emit that form.
  - Recommendation: (a). The API reference and the Python SDK still type the delta as `function` alone, and O10 waits for OpenAI's documentation rather than for one SDK's type.
  - Blocks: the Chat Completions rows of "CT-6" in the adapter that O8 of `0138-rest-only-client-api` names.
  - (raised by the desk validation of the M3 readiness review, 2026-11-19; sources: VAL-010)
- **O23. OpenAI custom tools on the Open Responses adapter, and the `allowed_tools` modes that T15 does not map.** The Open Responses specification of 2026-04-24 defines no custom tool type, since its tools are function tools only, and its extension rule requires an implementor-slug prefix on a non-standard item or event type. This design emits unprefixed `custom_tool_call` items and `response.custom_tool_call_input.*` events, which OpenAI SDK clients parse and which do not follow that rule. Open Responses also lets `allowed_tools` omit `mode` or set it to `none`, while T15 maps only `auto` and `required`. Desk validation VAL-012 found both, and its checker confirmed them **[external]**.
  - (a) Accept OpenAI custom tools on the Open Responses adapter in OpenAI's unprefixed form, documented as a non-portable extension, as `0138-rest-only-client-api` keeps `GET /v1/responses/{id}` as an extension.
  - (b) Refuse custom tools on the Open Responses adapter with `400`, and serve them on Chat Completions and OpenAI Responses only.
  - (c) Use slug-prefixed names, which follow the extension rule and which no OpenAI SDK client parses.
  - Under every option, T15 maps an absent `mode` to `auto` and `none` to `toolChoice` `none`. T15 is settled, so the mapping needs the owner's confirmation.
  - Recommendation: (a), with the T15 mapping of an absent `mode` and of `none` confirmed. OpenAI SDK clients parse the unprefixed form, and a slug-prefixed form reaches no client.
  - Blocks: the Open Responses rows of "CT-6" in the adapter that O8 of `0138-rest-only-client-api` names.
  - (raised by the desk validation of the M3 readiness review, 2026-11-19; sources: VAL-012)

## Decisions

Settled by the owner on 2026-11-09. T1 to T8 came with revision 1, and the owner revised T5 and added T9 with revision 2:

| ID | Decision | Where |
| :-- | :-- | :-- |
| T1 | The mechanism is turn-ending. The runtime's end-of-turn `message` carries `clientToolCalls`, as the `response` frame did before the message delivery design's MD-24 replaced it. The next client request reaches the runtime as a `message` with a `toolResults` member. The tools arrive in `conversation.clientTools` and `conversation.toolChoice` on every turn. | CT-1 |
| T2 | The v1 surfaces are Chat Completions, Responses, REST, and the Messages API. MCP gets client tools only as Lenny-specific tool arguments. | CT-6 |
| T3 | Lenny is not prescriptive. `capabilities.clientTools` is the runtime author's declaration, and Lenny refuses client tools only on runtimes that do not declare it. Lenny's own reference runtimes do not declare it in v1. | CT-2 |
| T4 | On Chat Completions, each tool round trip continues cold with the history. Superseded on 2026-11-14 by the conversation fingerprint rule of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md#ro-10-the-provider-adapters): a round trip continues warm on the session the fingerprint finds, under that design's conditional send (R16), and continues cold with the history otherwise. | CT-6, CT-7 |
| T5 | A client message without the pending results is refused, apart from the REST exception of T9. For a runtime that does not declare the `steer` delivery intent of [`0135-message-delivery`](../0135-message-delivery/change.md), inter-session messages and other inbox deliveries wait until the results arrive, and are delivered right after them. For a steer-declaring runtime, inbox deliveries are not held while calls are pending, and the runtime places them after the results. The cold-history builder places a message that arrived while calls were pending after their results, so each call and its result stay adjacent. | CT-5, CT-7 |
| T6 | The gateway passes `tool_choice` and the parallel limit to the runtime. It validates the runtime's response: declared tool names, arguments against `input_schema`, `tool_choice`, and the parallel limit. A violation fails the turn with a do-not-retry error and a per-revision metric. The gateway does not repair the response. The owner confirmed with revision 2 that the JSON arguments of a function tool are still validated against its input schema. | CT-4 |
| T7 | Client tools are not delegated. | CT-9 |
| T8 | This is a standalone design, landing after the Messages design's AM-A and alongside the F-15.1.82 fix. | "Steps" in `steps.md` |
| T9 | On REST, a client message without the pending results is refused unless the request sets `abandonPendingToolCalls: true`, which turns the pending calls into "cancelled by client" error results. MCP clients reach `abandonPendingToolCalls` as a generated argument in the MCP adapter. Chat Completions, Responses, and the Messages API always refuse such a message. | CT-5 |

The owner's decisions of 2026-11-09 on [`0120-anthropic-messages-api`](../0120-anthropic-messages-api/change.md) also bind this design: that surface has no open turns, the conversation input carries ordered entries with the new input marked (its O3), warm continuation uses an HMAC-SHA256 conversation digest with an in-flight join that reattaches a retry to the running turn (its O2 and M1), and every failure after dispatch carries `x-should-retry: false`.

Settled by the owner on 2026-11-09 with revision 2, from the open decisions of revision 1. O1, O2, and O4 to O7 take revision 1's recommendation. O8 and O9 take the owner's own answers:

| ID | Question | Decision | Where |
| :-- | :-- | :-- | :-- |
| O1 | The form of the capability. | An object, `capabilities.clientTools.supported` with `reservedNames`, that requires `capabilities.conversationInput: true`. The cold path delivers earlier calls and results as structured history, which transcript rendering cannot express, so the dependency on conversation input is structural. `reservedNames` lets a runtime protect the names of its own model-visible tools, which the gateway cannot discover. O9 adds `customTools`. | CT-2 |
| O2 | Whether a runtime may declare that it accepts results only warm. | No field. A declaring runtime accepts results cold from history, and for calls it no longer holds in memory, or answers with an end-of-turn `message` carrying `error`. A harness wrapper that parks a call in memory can declare the capability and fail a cold continuation with an error. A `warmOnly` field is revisited when a harness wrapper asks for it. | CT-7 |
| O4 | REST sessions whose revision cannot accept a further message (`capabilities.interaction: one_shot`, or `capabilities.injection.supported: false`). | Client tools on such a session are refused at creation with `422 CLIENT_TOOLS_UNSUPPORTED`, naming the missing capability. On REST a session has no cold path with history, so a session that cannot take a second message can never receive its results. Chat Completions, Responses, and the Messages API are unaffected, because their cold path delivers results in a new session. | CT-2, CT-6 |
| O5 | A retried Responses continuation that carries results. | The Messages API's in-flight join extends to Responses continuations: a continuation of response `R` whose input equals the input of the running continuation of `R` reattaches to that turn. The SDKs retry a dropped connection twice by default **[external]**, and a results request is the most frequent request in a tool loop. Chat Completions stays cold under T4. REST need no join, because a second results message finds no pending calls and is refused. | CT-7 |
| O6 | How a deployer's output interceptors see call arguments. | The `PostAgentOutput` payload gains an optional `clientToolCalls` member beside the output parts, so an existing output filter covers arguments and custom tool input with no change to its registration. | CT-8 |
| O7 | The per-tenant capability override for client tools. | A tenant may clear `clientTools.supported`, may clear `clientTools.customTools`, and may append to `clientTools.reservedNames`. A widening is refused. This is the narrowing form RV-1 gives `capabilities.interaction` and `capabilities.injection`. Clearing `customTools` follows from O9 under the same narrowing rule. | CT-2 |
| O8 | A re-run of a session that used client tools. | Server-side replay no longer exists under [`0144-session-derive`](../0144-session-derive/change.md). A client that re-runs a session re-sends its messages itself and executes its own tools. A derive from a session with pending client calls copies them, and the derived session's first client request must carry the results.
