## Problem

"Terms", after "Scope", defines the vocabulary this document uses.

A person who works with a coding agent often types a correction while the agent is busy: "use the staging database instead", or "skip the tests for now". Most agent harnesses accept such a message at any time and fold it into the agent's work at its next model step, after the tool calls it is running finish **[external]**. Claude Code, the Claude Agent SDK, Codex, Cursor, and the Vercel AI SDK behave this way by default. They also offer a mode that holds the message until the agent's turn ends, and a mode that stops the agent and sends the message next.

Lenny offers only the queue and interrupt modes, and the tree offers neither in the form the specification states **[source]**:

- The specification buffers every message that arrives while a tool call is in flight, and the only mid-turn delivery it defines interrupts the runtime ([§7.2](../../spec/07_session-lifecycle.md#72-interactive-session-model), "Message delivery routing", paths 4 and 5).
- The gateway executor pairs each message with one `response` through a turn token, discards a `response` that no message caused, and holds the session's delivery lock for the whole turn. A message sent mid-turn waits for the running turn to end before anything answers it, and a parent session's `lenny/send_message` call blocks until the child's turn ends.
- `capabilities.injection.modes` appears in runtime declarations, and no section says what a mode means.

The wire protocol between the adapter and the runtime does not cause any of this: the `CH-MSGSOCK` card already requires a runtime to handle a `message` that arrives before a pending `tool_result`. The alternation comes from the gateway's delivery policy, its executor, and the runtime SDKs.

The owner asked for a general machinery that covers today's cases and later ones. This design gives every message a delivery intent, lets each runtime declare the intents it accepts, gives every message an explicit state from acceptance to consumption, and keeps the gateway's custody of a message until the runtime reports that it consumed it. The non-interrupting mode the harnesses default to becomes the intent `steer`, which a runtime declares when it can take a message at any time.

A person who watches a coding agent also expects to see what it does while a turn runs: the tool it runs, the plan it follows, the text it writes, and the questions its harness asks before it runs a command. Every harness surveyed on 2026-11-10 streams these **[external]**. Lenny's path from the runtime to the client carries none of them in a form a client can use **[source]**. The gateway's executor drops every runtime frame other than `response` and an approval-gated `tool_call`, the `status` frame included. An output part cannot grow while it streams. `lenny/output` reaches the gateway on a different link from the stdout frames and skips the `PostAgentOutput` interceptors and the transcript. A harness's permission request for a tool that Lenny does not route has no way to reach the client. "MD-15" to "MD-21" add these reports.

## Scope

**Added:**

- Delivery intents `steer`, `queue`, and `interrupt` on every message, with a rule for adding intents ("MD-1" and "MD-14").
- The definition of `capabilities.injection.modes` as the intents a runtime accepts, and `capabilities.injection.defaultMode` ("MD-2").
- Inbox states, custody until consumption, at-least-once delivery up to consumption, deduplication by message id, and the `consumed_unrecorded` state that reports a message consumed after the checkpoint a session resumes from ("MD-3").
- Turn accounting on `CH-MSGSOCK`: end-of-turn `message` lists the message ids it consumed, a `consumed` frame reports consumption during a turn, and an end-of-turn `message` that no message caused is accepted ("MD-4").
- Retraction: a runtime may retract a message it generated, by id, and receives `retracted`, `too_late`, or `unknown` ("MD-11"). A client may retract a message it sent through `DELETE /v1/sessions/{id}/messages/{messageId}` and the generated MCP tool ("MD-7", O5).
- A drain call in the runtime SDKs that returns the messages queued for a session between model steps ("MD-12").
- The session events `message_state` and `turn_end`, and per-message delivery receipts on REST ("MD-7").
- Rules for sessions created on a provider surface. Client tools are offered only in turns a client request caused, and a turn that no client request caused never appears in a provider-surface response ("MD-8", O3).
- Activity: the `activity` frame and SessionEvent kind, with an open `kind`, the operations `start`, `update`, `patch`, `append`, and `end`, turn and session lifetimes, recording that the runtime asks for under a rate cap, a size cap, and the current state of open activities on attach ("MD-15", A2, A3, A7, and A10).
- Streaming output: the stdout `message_part` frame as the only output path, with `append`, `end`, and `reset` on a streaming part ("MD-16", A5 and A6).
- Reasoning as a `reasoning_trace` part with `signature`, `encrypted`, and `redacted`, or as a `thinking` activity, as the runtime chooses ("MD-17", A1).
- File parts that name a workspace path, which the adapter uploads to the artifact store ("MD-18", A11).
- The `request` frame with `kind: "approval"` and its `reply`, which bring a harness's own permission requests into the tool-use approval path, with a policy for unattended sessions, and the same frames with `kind: "question"` for a harness's own questions ("MD-19", A4, B7, B8, and B-O6).
- A child session that behaves as a top-level session whose client is its parent, child events pushed to the parent's inbox, mid-turn messages from every session to its client through `send_update` and the `message` frame, completion by `complete: true`, `capabilities.childSessions`, and `humanRequired` on elicitations ("MD-22", B1 to B6).
- Tool names without the `lenny/` prefix, and the renames of "MD-23", which name the session in every tool that acts on a child (B10, B11).
- One `message` frame in both directions with optional members and defaults, the delivery rules of a `message`, and the leniency rules under which a frame that is slightly off never stops a conversation ("MD-24", B-O6, B12).
- A parent's runtime that watches a child's event stream ("MD-25", B13).
- Files from a child to its parent, imported on demand into the parent's workspace over the checkpoint restore path ("MD-26", B14).
- The session events `turn_start`, `usage`, and `activity`, and `status` and `usage` on `turn_end` ("MD-20", A8).
- The projection of each report on REST, MCP, A2A, the provider surfaces, and AG-UI, under the rule that every report translates to AG-UI without loss ("MD-21", G3).

**Changed:**

- The [§7.2](../../spec/07_session-lifecycle.md#72-interactive-session-model) delivery paths are rewritten as named paths keyed on the turn state and the intent ("MD-5"). The `ready_for_input` term leaves the specification (O1).
- The envelope's `delivery` member takes intents in place of `immediate` and `queued` ("MD-1").
- The executor's turn token and the turn-long delivery lock are replaced by a writer, a frame reader, and a turn waiter ("MD-6").
- `POST /v1/sessions/{id}/messages` and the agent-facing `message_child_session` return receipts at once, with consumption and output reported as session events ("MD-7").
- The client-tools hold rule applies only to runtimes that do not declare `steer`, and the cold-history builder gains an ordering rule ("MD-10").
- An inbox delivery to a session a provider adapter created is delivered on arrival under the ordinary intent rules, in place of waiting for the next client turn ("MD-8", O3).
- The reference runtime declarations of [§26](../../spec/26_reference-runtime-catalog.md#26-reference-runtime-catalog) ("MD-13").
- A `message` frame writes into the transcript only the parts it carries with content, and names an already-written part by its `id` or delivers everything written since the previous `message` (the delivery rules of "MD-24", B12).
- The executor's frame reader routes every runtime frame and no longer blocks while a tool call awaits approval ("MD-6", "MD-19").
- §13's exception to gateway-mediated file delivery for checkpoint packs extends to the packs of output files, under the checkpoint capability model ("MD-18").

**Removed:**

- The executor's turn token (`attachConn.token`) and the rule that discards an end-of-turn `message` with no registered turn.
- The synchronous `output` member of the REST message response.
- The delivery timeout of 30 seconds that §7.2 measures against a consumption acknowledgement no frame carries.
- `lenny/output`, whose output reaches the gateway on its own link ("MD-16", A6).
- `lenny/request_input`, the `input_required` sub-state, `maxRequestInputWaitSeconds`, and the reply path for them ("MD-22", B5).
- The `siblings` messaging scope ("MD-9", B9).
- The platform tool `lenny/set_tracing_context`, whose frame stays, and the `lenny/` prefix of every platform tool ("MD-23", B10).

**Out of scope:**

- Steering by a provider-surface client. A Chat Completions, Responses, or Messages API client cannot correct its own running turn, because each request is one turn, as the provider APIs define it ("MD-8").
- Scheduled delivery, priority ordering, context-only messages, and the other future cases of "MD-14". The machinery accommodates them, and none ships in v1.
- Retraction of output and session events. Output already streamed cannot be recalled, and output the gateway has not yet sent to a client is ignored for now ("MD-11", "Blast radius"). A runtime's `reset` of a part that is still streaming is not a retraction, and "MD-16" states it.
- Activity on the provider surfaces, and Messages API event types for it, which a later version may add behind a request header ("MD-21", A9).
- Relay of a delegated child session's activity into its parent's event stream ("MD-15", A7). A child's messages and ends reach the parent as child events ("MD-22"), and the parent's runtime may watch the child's stream ("MD-25").
- Frames for the parent-side operations `start_child_session`, `message_child_session`, `await_child_sessions`, and `close_child_session`, which are tools only in v1 and can gain frames later (B8).
- The session state machine, tree suspension, the close rule, and the cascade when a parent ends, which [`0146-session-lifecycle`](../0146-session-lifecycle/change.md) states.
- An AG-UI endpoint. v1 states the projection and builds no adapter ("MD-21", G3).
- Multi-thread sessions, which the owner left out of v1 under G2. `threadId` keeps its v1 meaning.
- The fix of each tree defect as a separate change. The owner decided that the defects under "Defects found while verifying" are fixed later under a holistic plan.

## Terms

| Term | Meaning |
| :-- | :-- |
| Message | One `MessageEnvelope` of type `message` that a sender addresses to a session: a client message, an inter-session message, or a system message. |
| Delivery intent (intent) | The value of a message's `delivery` member, which states when the message reaches the runtime relative to the runtime's current turn: `steer`, `queue`, or `interrupt`. |
| `steer` | Deliver the message now, without interrupting. The runtime reads it at its next model step, after the tool calls it is running finish, and places it after their results. Without a running turn, the message starts one. |
| `queue` | Hold the message until the runtime's current turn ends, then deliver it as the start of a new turn. |
| `interrupt` | Stop the runtime's current work at a safe point, then deliver the message as the start of a new turn. |
| Default intent | The intent a message takes when its sender names none: the runtime's `defaultMode`, which is `steer` when the runtime declares `steer` and `queue` otherwise. |
| Turn | The runtime's work from the delivery of a message to an idle runtime, or from output the runtime starts on its own, until its next end-of-turn `message`, which replaces the specification's `response` frame ("MD-24"). |
| Open turn | A turn whose end-of-turn `message` has not arrived. The gateway tracks it per session from the frames it writes and reads ("MD-4"). |
| Unsolicited response | An end-of-turn `message` that closes a turn the runtime started on its own, for example after background work or a child's result. |
| Causing message | The message whose delivery opened a turn. A turn the runtime starts on its own has no causing message. |
| Client request | A message from the session's client on any client surface: REST, MCP, Chat Completions, Responses, or the Messages API. A turn whose causing message is a client request is caused by that request. A turn caused by another session's message, a system message, or an external message is not caused by a client request. |
| Consumption | The runtime's acceptance of a delivered message into its own handling: the message entered its model history, or the runtime acted on it without a model call. The runtime reports it by message id. |
| Inbox | The gateway's per-session store of messages it has accepted and not yet released: the session inbox of §7.2, extended to hold delivered messages until consumption ("MD-3"). |
| Inbox state | One of `pending`, `delivered`, `consumed`, `consumed_unrecorded`, `retracted`, `expired`, `dropped`, and `superseded`, defined in "MD-3". |
| Retraction | A sender's request that the gateway never deliver a message it sent. It succeeds only while the message is `pending`, and for a client tool call only while the call is pending on a REST session ("MD-11"). |
| Retraction result | The answer to one retracted id: `retracted`, `too_late` (the recipient already received it, or the surface cannot withdraw it), or `unknown` (the id names nothing this sender may retract). |
| Custody | The gateway's obligation to keep a message and redeliver it until the runtime reports its consumption (O4). |
| Drain call | The runtime SDK call that returns the messages queued in the runtime process for a session while a handler runs ("MD-12"). |
| Provider surfaces | The Chat Completions, Responses, and Messages API surfaces, whose clients follow a provider's API. |
| Activity | A runtime's report of what it is doing, keyed by an `id` the runtime chooses, which the gateway shows to clients and keeps out of model history ("MD-15"). |
| Activity kind | The open string `kind` of an activity. "MD-15" lists the conventional kinds, and a custom kind takes the `x-<vendor>/` prefix. |
| Open activity | An activity that has started and has not ended. |
| Recorded activity | An activity started with `record: true`, whose final state the gateway writes to the transcript when it ends ("MD-15"). |
| Streaming part | An output part emitted with `status: "streaming"`, which later `message_part` frames grow by its `id` until it ends or is reset ("MD-16"). |
| File part | A `file` output part that names a workspace path, which the adapter uploads to the artifact store before the gateway releases the part ("MD-18"). |
| Output file | The stored copy of a file part's file: an `output_files` row with the file's chunk list, and the packs that hold its chunks ("MD-18"). |
| Export | The copy of one file part's file to the artifact store over the `ExportOutputFile` stream, from the gateway's `ExportStart` to `ExportReady` or a failure ("MD-18"). |
| `exportTimeoutSeconds` | The pool setting, 900 seconds by default, counted from an export's `ExportStart`, after which an export that has not reached `ExportReady` fails. The same span, counted from a part's first frame, bounds a part's wait for the export cap ("MD-18", "Clocks"). |
| Export cap and export queue | A session runs at most `files.maxConcurrentExports` exports at once, 2 by default. A file part over that cap waits in the session's export queue, which holds at most `files.maxQueuedExports` parts, 8 by default ("MD-18", "Copy"). |
| `output_file_exports` | The gateway's durable record of each file part, a Postgres table keyed by session and part, with the export's state, its clocks, its quota reservation, the coordination generation that drives it and guards every change to the row, and its failure notice until the runtime acknowledges it ("MD-18", "Export record"). |
| Unopened part | A file part that the adapter relays with the member `unopened: true` because it already holds its cap of open export descriptors for the session. The gateway refuses exactly the parts that carry the marker, with `too_many_exports` ("MD-18", "Freeze"). |
| `ExportAbort` | The message with which the gateway ends a failing export on the `ExportOutputFile` stream, with the failure reason, in place of the `Checkpoint` stream's `CheckpointAbort` ("MD-18", "Refusals"). |
| Seal window ceiling | The chart value `gateway.workspaceSealMaxDurationCeilingSeconds`, 600 seconds by default, which the gateway reads as `--workspace-seal-max-duration-ceiling-seconds`. No pool and no runtime may set a seal window above it, and the chart computes the default claim orphan timeout from it ("MD-18", "Seal window"). |
| `suspend_hold_expired` | The failure reason of a file part whose export a suspension ends: a part that still waits for the export cap when the pod hold of a `suspended` or `blocked` session ends, and every export of a session whose suspension releases the pod at once ("MD-18", "Export lifecycle"). |
| Pack nonce | The random 128-bit value the adapter writes into the footer of every pack it builds, for checkpoints and exports alike, so no two packs share a pack ID ("MD-18", "Copy"). |
| `Repr-Digest` | The HTTP header of RFC 9530 that carries a digest of the full representation a response selects, whatever its content coding and range. `GET /v1/blobs/{ref}` sends the output file's whole-file SHA-256 in it ("MD-18", "Download"). |
| `output_failed` | The frame the adapter writes to the runtime, and the session event the gateway emits, when a file part fails, with the reason, so the runtime can emit the file again. The gateway keeps each notice until the runtime acknowledges it with `output_failed_ack`, and sends it again after a resume ("MD-18", "Failure notice"). |
| `CH-OUTPUTFILE` | The channel this design adds for the `ExportOutputFile` stream on the gateway's gRPC link to the adapter ("MD-18", "Channel"). |
| Harness approval | A permission request that a harness raises for a tool it runs itself, which the runtime forwards with a `request` frame of `kind: "approval"` ("MD-19"). |
| Client of a session | Whoever sends the session its messages and reads its output: a REST, MCP, or provider-surface client for a top-level session, and the parent session for a child ("MD-22", B1). |
| Child event | A message the gateway writes into a parent's inbox on a child's behalf: a mid-turn message, an end of turn, the end of the session, retries exhausted, or a direct suspension or resume. The gateway delivers each once, as a message in the parent's inbox or as the result of `await_child_sessions` ("MD-22"). |
| Mid-turn message | A message a session sends its client during a turn, through `send_update` or a `message` frame with `endOfTurn: false`, without ending the turn ("MD-22", B4). |
| End-of-turn `message` | The `message` frame that ends a turn, which replaces the specification's `response` frame. A `message` frame ends the turn unless it sets `endOfTurn: false`, and with `complete: true` it also completes the session ("MD-24"). |
| `capabilities.childSessions` | The Runtime capability that states that the runtime shows its model the sender of each child event, so it can start and steer children ("MD-22", B3). |
| `humanRequired` | The elicitation member that sends an elicitation past every parent to the human-facing edge of the tree ("MD-22", B6). |
| Request and reply frames | The `request` frame a runtime writes to ask the gateway for a decision, with `kind` and an optional `requestId`, and the one `reply` frame the adapter writes back ("MD-19"). |
| `message_part` | The frame that writes a part of the message being composed into the transcript and onto the event stream, whole or as a stream of operations. It replaces the specification's `output` frame ("MD-16", "MD-24"). |
| Delivery rules | The rules that decide which parts a `message` delivers to its recipient ("MD-24", B12). |
| Leniency rules | The rules under which the adapter and the gateway ignore, default, or drop a frame that is slightly off and keep the session running ("MD-24", B-O6). |
| Watch | A parent runtime's subscription to a child's event stream through `watch_child_session` ("MD-25"). |
| Import | The copy of a child's output file into its parent's workspace ("MD-26"). |
| Waiting and paused states | `idle` and `dormant`, in which a session has no open turn and waits for its client, and `suspended` and `blocked`, in which the root's client paused it or an ancestor. [`0146-session-lifecycle`](../0146-session-lifecycle/change.md) defines them. |
| AG-UI | The Agent-User Interaction Protocol, an open event protocol between agent backends and user interfaces that CopilotKit maintains. Version 1.0 was published on 2026-09-17 **[external]**. |
| MD-n, MDR-n, MDF-n, and MD-A onward | The parts of this design under "Detailed design" carry MD-n, its requirements under "Requirements" carry MDR-n, and the defects under "Defects found while verifying" carry MDF-n. MD-A, MD-B, and the later letters name the steps of `steps.md` that land the design, and each step lists the parts it lands. `decisions.md` gives each owner decision an ID, such as S-n, O-n, A-n, or B-n. |

## High-level design

Every message a session receives says when it should reach the runtime. A message marked `steer` goes to the runtime at once, and the runtime reads it at its next model step without stopping what it is doing. A message marked `queue` waits until the runtime finishes its current turn. A message marked `interrupt` stops the runtime's work and goes next. Most clients name no intent: the message takes the runtime's preference, which is `steer` for a runtime that declares it. A client that wants another behaviour sets one field on that message.

The gateway keeps each message from the moment it accepts it until the runtime reports that it consumed it, and records the message's state along the way. A send call answers as soon as the message is written to the runtime or held, and the client follows consumption and output on the session's event stream. Because the runtime reports which messages each reply consumed, the gateway no longer assumes one reply per message: one turn can consume several messages, and a runtime can reply without any new message.

The rest of this section states each part in the design's terms, which "Terms" above defines.

**Intents (MD-1).** The envelope's `delivery` member carries `steer`, `queue`, or `interrupt`. Absent means the default intent. The values mirror the Claude Agent SDK's `priority` values `next`, `later`, and `now`.

**Declaration (MD-2).** `capabilities.injection.modes` lists the intents a runtime accepts, and must include `queue`. `steer` needs no other capability, and `interrupt` requires the runtime to declare the `interrupt` capability of [RP-2](../0139-runtime-protocol/change.md#rp-2-capabilities-and-their-dependencies). `defaultMode` names the runtime's preference. An explicit intent the runtime does not declare is refused.

**States and custody (MD-3).** A message is `pending` while the gateway holds it, `delivered` once written to the runtime, and `consumed` once the runtime reports it. It may also end `retracted`, `expired`, or `dropped`, and `superseded` is reserved for a later intent. Custody ends when the runtime reports consumption (O4). The gateway redelivers a `delivered` message after a pod loss, and the adapter and the SDK drop a message id they have already consumed. A message consumed after the checkpoint a session resumes from is not redelivered: it becomes `consumed_unrecorded`, and its sender decides whether to send it again.

**Turn accounting (MD-4).** end-of-turn `message` gains `consumed`, a list of message ids. A new `consumed` frame reports consumption during a turn (O2). An end-of-turn `message` with no message to attribute is an unsolicited response and is recorded. The gateway tracks an open turn from the frames it writes and reads, which replaces `ready_for_input` (O1).

**Delivery paths (MD-5).** §7.2's numbered paths become named paths: the dead-letter path, the resume path, the direct path, the steer path, the interrupt path, and the queue path.

**Executor (MD-6).** A writer delivers an envelope and returns. A reader routes every frame. A turn waiter lets a caller that needs a turn's output wait for the turn that consumed its message. The delivery lock covers the routing decision and the write, and never a turn.

**REST (MD-7).** A send returns one receipt per message at once. `message_state` and `turn_end` events report consumption and turn ends.

**Provider surfaces (MD-8).** A request remains one turn. The adapter waits for the turn that consumed its message. An inbox delivery to a provider-adapter session between client requests is delivered on arrival under the ordinary intent rules. A turn that no client request caused carries no client tools, and its output never appears in a provider-surface response (O3).

**Inter-session messages, system messages, and delegation (MD-9).** `message_child_session` carries an intent and returns at once. A parent can redirect a running child with `steer`. Sessions message each other only along the tree, and the `siblings` scope leaves. Child events pass the parent's content policy and interceptors, `messagingRateLimit` bounds a loop between a parent and a child, and a message between environments passes the rules of both.

**Client tools (MD-10).** A `steer` runtime receives inbox deliveries while client calls are pending and places them after the results. A turn that an inbox delivery causes carries no client tools (O3). The cold-history builder never places an entry between calls and their results.

**Retraction (MD-11).** A runtime writes a `retract` frame naming ids it generated and receives a `retract_result` frame with `retracted`, `too_late`, or `unknown` for each. A pending client tool call on REST is cancelled and the client receives a retraction event. A returned call on a provider surface cannot be withdrawn, so the answer there is `too_late`. A message the runtime sent to another session is retracted while it is `pending` in the recipient's inbox and is `too_late` once delivered. Output and session events are not retracted in v1.

**SDKs (MD-12).** The drain call returns messages queued behind the running handler. The SDK reports consumption, drops duplicate ids, and can write an unsolicited response.

**Reference runtimes (MD-13).** `claude-code`, `codex`, and `chat` declare `steer`. The others declare `queue` and `interrupt` until their harnesses' steering is verified.

**Extension (MD-14).** A new intent states its gateway behaviour per turn state, its runtime obligation, and its states, and is declared when the runtime has to act on it.

During a turn the runtime also reports what it is doing. Activity frames show tools, plans, steps, and other progress, and the gateway keeps the current state of every open activity, so a client that connects mid-turn sees it. Output streams as the model writes it. Reasoning is content or activity, as the runtime chooses. A file the agent produces is copied to the artifact store and offered to the client as a download. A harness's own permission requests reach the client through the approval flow that Lenny's tools use. Every report translates to AG-UI without loss.

**Activity (MD-15).** An `activity` frame starts, updates, patches, appends to, or ends an activity by `id`. `kind` is open, and conventions name the common kinds. The gateway keeps open activities and sends them on attach, records an activity in the transcript only when the runtime asks, caps recorded activity per minute, and closes a turn's open activities when the turn ends. The adapter caps a frame at 1 MiB and merges rapid updates.

**Output (MD-16).** The stdout `message_part` frame is the only output path. A streaming part grows by `append`, ends by `end`, and is discarded by `reset`. `lenny/output` is removed.

**Reasoning (MD-17).** A `reasoning_trace` part carries the provider's signature or encrypted value and enters the transcript. A `thinking` activity shows reasoning without recording it.

**Files (MD-18).** A `file` part names a workspace path. The adapter freezes the file with a reflink clone where the filesystem allows one, splits it into the content-addressed chunks of the incremental checkpoint design, skips chunks the session's checkpoints already hold, and uploads the rest in packs of at most 32 MiB against grants the gateway signs, sharing the session's checkpoint grant window. The gateway replaces the path with a `lenny-blob://` reference and renders downloads from the packs. The limit is 5 GiB, a runtime can lower it, and the file has the session's retention. An export has its own deadline and outlives its turn, at session end it finishes in the time the seal checkpoint leaves in the seal window, and a file part that fails reaches the runtime as `output_failed`, which the gateway keeps until the runtime acknowledges it, so the runtime can emit the file again.

**Harness approvals (MD-19).** A `request` frame with `kind: "approval"` sends a harness's permission request through the `tool_use` approval path to the person watching the root, and a declared policy answers for unattended sessions. A harness's own question travels as a `request` with `kind: "question"`.

**Turn and usage events (MD-20).** `turn_start` and `usage` events are added, and `turn_end` carries a status and usage. Usage comes from the gateway's metering and from the runtime's report, each labelled with its source.

**Surfaces (MD-21).** Each report has a projection on REST, MCP, and A2A, provider surfaces carry output and reasoning only, and every report has a lossless AG-UI projection, through a `CUSTOM` event where AG-UI has none.

A child session behaves as a top-level session whose client is its parent. The parent starts, steers, and closes children with tools, and the child's messages and ends arrive in the parent's inbox as Claude Code delivers a sub-agent's notices. Frames carry everything the harness itself triggers, and tools carry only what the model decides.

**Parents and children (MD-22).** A child's mid-turn messages, its ends of turn, and its end reach the parent as child events, once each, after the parent's content policy. Every session can message its client during a turn with `send_update`. Asking is replying, and `complete: true` completes a session. An elicitation with `humanRequired` skips the parents, and an approval always goes to the person watching the root. [`0146-session-lifecycle`](../0146-session-lifecycle/change.md) states the states a parent and its children pass through.

**Names (MD-23).** No platform tool carries the `lenny/` prefix, and every tool that acts on a child names the session: `start_child_session`, `message_child_session`, `await_child_sessions`, `close_child_session`, `list_child_sessions`, and `import_child_session_file`. `send_update`, `ask_question`, and `discover_agents` complete the agent-facing set.

**Frames and leniency (MD-24).** A minimal runtime reads `message` and writes `message`. Every other frame and every other member is optional, with a default that keeps the conversation moving, and a frame that is slightly off is dropped alone and reported. A `message` delivers the parts it names, or everything written since the previous `message`.

**Watching a child (MD-25).** A parent's runtime may watch a child's event stream, as a client attaches to a session, and decide what its model sees.

**Files from a child (MD-26).** A child event carries a reference to each file the child delivers, and the parent imports it into its workspace on demand, over the checkpoint restore path, so a large file never passes through stdout or the gateway.

## Requirements

| ID | Requirement |
| :-- | :-- |
| MDR-1 | Every message the gateway accepts has exactly one inbox state at a time, records its sender's `from.kind` and its intent, and changes state only along the transitions of "MD-3". |
| MDR-2 | A message reaches a runtime only with an intent the session's revision, after the per-tenant override, declares. An explicit intent the revision does not declare is refused before the message is held. |
| MDR-3 | The gateway keeps custody of every message until the runtime reports its consumption, or until the message ends `retracted`, `expired`, or `dropped`. ### Specification

**Envelope [source].** §15.4.1 "`MessageEnvelope` — Unified Message Format" defines `delivery` as an optional closed enum "controlling interrupt behaviour": `"immediate"` ("Interrupt the running agent and deliver now"), `"queued"` ("Buffer for next natural pause"), and absent, which equals `"queued"`. Unknown values are refused with `400 INVALID_DELIVERY_VALUE`. `from.kind` is a closed enum of `client`, `agent`, `system`, and `external`, and the adapter overwrites any runtime-supplied `from`. Sender-supplied ids must be unique within the tenant, and the gateway keeps a deduplication window of seen ids (`messaging.deduplicationWindowSeconds`, 3600 seconds by default). The section's closing paragraph calls the envelope future-proof for "all future conversational patterns without schema changes".

**Receipts [source].** §15.4.1 "`delivery_receipt` acknowledgement schema" gives `status` the values `delivered` ("runtime consumed"), `queued`, `dropped`, `expired`, `rate_limited`, and `error`. `message_expired` reaches the sender session's event stream with the reasons `dlq_ttl_expired`, `durable_inbox_ttl_expired`, and `target_terminated`.

**Wire contract [source].** The `CH-MSGSOCK` card of §28.5.3 lists the runtime-to-adapter frames `session_started`, `response`, `tool_call`, `heartbeat_ack`, `status`, and `set_tracing_context`. Under **Inbound: `tool_result`**, "Delivery semantics" states: "Other inbound messages (`heartbeat`, additional `message` content) may arrive before the `tool_result` — the agent must handle interleaved delivery." **Outbound: `response`** carries `output` and an optional `error`, and nothing in the card pairs one `response` with one `message`. **Outbound: `heartbeat_ack`** requires `busy: true` while the runtime handles a message, runs a tool call, does background work outside a turn, or waits on children.

**Capabilities [source].** §5.1 "Runtime" shows `injection: {supported: true, modes: [immediate, queued]}` in its YAML and defines only `supported`: "`capabilities.injection` declares whether the runtime supports mid-session message delivery." `multi_turn` requires `injection.supported: true`. No section defines `modes`. The CRD comment on `InjectionCapabilityCRD.Modes` (`pkg/apis/lenny/v1alpha1/runtime_types.go`) reads "`immediate` interrupts a suspended session to deliver, `queued` buffers the message for the next runtime turn", which matches neither §15.4.1 nor §7.2.

**Delivery paths [source].** §7.2 "Message delivery routing — seven paths" evaluates paths in order:

- Path 1 resolves an outstanding `lenny/request_input` by `inReplyTo`.
- Path 2 writes the message when the runtime is available, meaning its adapter reports `ready_for_input`. The receipt is `delivered` "only after confirmed stdin consumption" within a delivery timeout of 30 seconds, and otherwise the message falls through to the inbox. The "`ready_for_input` — normative definition for concurrent tool execution" requires that no tool call is in flight and that the runtime is reading stdin, and routes "a message arriving while any tool call is in flight" to path 5.
- Path 3 buffers while the session is `input_required`, even under `delivery: "immediate"`.
- Path 4 is the only mid-turn delivery: under `delivery: "immediate"` with a tool call in flight, the gateway calls the adapter's `Interrupt`, the adapter writes `interrupt_request` on `CH-RUNTIMEOPS`, and the message follows the acknowledgement at Full level or follows at once at Basic and Standard.
- Path 5 buffers in the session inbox while the runtime is busy and delivers in FIFO order at the next `ready_for_input`.
- Path 6 resumes a `suspended` session, with **Delivery of held messages.**, which delivers every held message of the inbox and the DLQ before each path-2 message, one at a time and oldest first, and removes an entry only after the runtime consumed it.
- Path 7 sends a message for a terminal or recovering session to the dead-letter handling.

The durable inbox's "Explicit ACK" row removes an entry after delivery and requires the adapter to keep a `delivered_message_ids` set of the last 1000 ids in checkpoint state, suppressing redelivered duplicates and counting them on `lenny_inbox_duplicate_suppressed_total`.

**Unstated signals [source].** §29.3 "Interactive message send" step 8 records that "the specification does not state which channel and which message carry the adapter's report that the runtime is `ready_for_input` and its acknowledgement that the runtime consumed the written message".

**SDKs [source].** §15.7 "Runtime Author SDKs" defines `Handler.OnMessage(ctx, Message) (Reply, error)` and busy holds for work after a handler returns, including "the rest of a turn whose Reply is streaming and not final".

**Reference runtimes [source].** §26.2 declares `multi_turn` with `modes: [immediate, queued]` for the coding-agent runtimes, §26.7 `chat` and §26.10 `openai-assistants` declare `[immediate]`, and §26.8, §26.9, and §26.11 declare `[immediate, queued]`. Every reference runtime is Full level (§26.1). §26.3 "Bootstrap behavior" pipes each message to `claude` and states nothing about a message that arrives while `claude` works.

## Detailed design

### MD-1 Delivery intents

**Values [design].** `delivery` on the `MessageEnvelope` takes `steer`, `queue`, or `interrupt`, or is absent. `immediate` and `queued` leave the enum, because Lenny has no deployments to keep. An unknown value is refused with `400 INVALID_DELIVERY_VALUE`, whose message lists the defined values.

| Intent | Meaning | Claude Agent SDK `priority` | Codex | Cursor |
| :-- | :-- | :-- | :-- | :-- |
| `steer` | Deliver now and do not interrupt. The runtime reads the message at its next model step and places it after the results of the tool calls it is running. Without an open turn, the message starts one. | `next`, the default | `turn/steer` | `delivery: "steer"` |
| `queue` | Hold until the open turn ends, then deliver as the start of the next turn. | `later` | Tab-queued input | Tab-queued follow-up |
| `interrupt` | Stop the open turn at a safe point, then deliver as the start of the next turn. | `now` without background work | `turn/interrupt`, then `turn/start` | Second Enter |

Claude Code's `now` first moves background-capable work to the background and lets Claude read the message in the same turn. Lenny's `interrupt` does not, because the gateway cannot move a runtime's work. A runtime that can do so is a future intent ("MD-14").

**Default [design, S2].** A message without `delivery` takes the default intent of the session's revision: its `injection.defaultMode` when set, `steer` when the revision declares it, and `queue` otherwise. The gateway writes the resolved intent into the envelope it delivers and the inbox entry it records, so a runtime and a reader of the transcript see the intent that applied.

**Override [design, S2].** A sender sets `delivery` on one message to override the default. REST takes it per message in the batch, the client-facing MCP `send_message` and the agent-facing `message_child_session` take it in the message, and the `lenny session send` command gains `--delivery`. Provider surfaces take no override ("MD-8").

**Unsupported intents [design].** A message whose explicit intent the revision does not declare is refused before it is held: `422 DELIVERY_MODE_UNSUPPORTED` on REST, with the declared intents in `details`, and a receipt with `status: "error"` and `reason: "delivery_mode_unsupported"` on `message_child_session`. A refusal is explicit, because degrading `steer` to `queue` would delay a correction a person expects the agent to read now, and degrading `interrupt` to `steer` would let work the sender meant to stop continue.

**Direction [design, B9].** `interrupt` comes only from a session's client: a REST client, or the parent through `message_child_session`. A child event and every other message a session sends its client take the recipient's default intent and never `interrupt` (MDR-38).

**Ordering [design].** Messages of one intent reach the runtime in the order the gateway accepted them. A `steer` message overtakes `queue` messages that are still `pending`, as the harnesses' steered messages overtake their queued ones.

### MD-2 Runtime declaration

```yaml
capabilities:
  interaction: multi_turn
  injection:
    supported: true
    modes: [steer, queue, interrupt]
    defaultMode: steer
```

**[design, S10]**

- `modes` lists the intents the runtime accepts. When `supported` is true, `modes` must contain `queue`, because every injecting runtime takes a message at the start of a turn. Registration refuses an unknown value, a list without `queue`, and a non-empty list with `supported: false`.
- `steer` declares the obligations of MDR-5: the runtime reads `message` frames at any time, during a turn, while platform and approval-held tool calls run, while its harness waits on an operator service through egress, and while client calls are pending, and it places each message in its model history only at a point the model API accepts. It reports consumption with `consumed` frames and `message.consumed` ("MD-4"). `steer` is available at every integration level, because it uses `CH-MSGSOCK` alone.
- `interrupt` declares that the runtime handles `interrupt_request` on `CH-MSGSOCK`, ends its open turn with an end-of-turn `message` once it acknowledges, and keeps the interrupted work's tool calls paired with results, for example by recording an error result for a call it abandons. Registration refuses `interrupt` on a runtime whose `integrationLevel` is below `full`, and the existing check of the observed level at the first session applies.
- `defaultMode` is optional and must be one of `modes`. A runtime that declares `steer` but prefers `queue` sets it, as Gemini CLI queues by default although it can steer.
- The fields are versioned and gateway-read under RV-1, so the session's revision decides. The per-tenant capability override may keep a subset of `modes` that still contains `queue`, as RV-1 states for `injection.modes`, and may set `defaultMode` to one of the remaining intents. When an override removes the revision's `defaultMode`, the default falls back to the rule of "MD-1".
- The CRD comment on `InjectionCapabilityCRD.Modes` states the meaning above.

### MD-3 Inbox states and custody

**States [design, G1].**

| State | Meaning | Receipt status |
| :-- | :-- | :-- |
| `pending` | Accepted and held by the gateway: in the session inbox or the DLQ, waiting for the turn state its intent requires, for a resume, or for a session to start. | `queued` |
| `delivered` | Written to the session's `CH-ATTACH` stream for the runtime, and not yet reported consumed. | `delivered` |
| `consumed` | Reported consumed by the runtime in a `consumed` frame or an end-of-turn `message`. Custody ends, and the entry leaves the inbox (O4). | Reported by event |
| `consumed_unrecorded` | Reported consumed, after which the session resumed from a checkpoint taken before the consumption, so the restored runtime does not hold the message. It is not redelivered (O4). | Reported by event |
| `expired` | Its TTL elapsed while the session was in a recovering state, or the session ended before consumption. | `expired`, or the `message_expired` event |
| `dropped` | Evicted by inbox or DLQ overflow. | `dropped` |
| `retracted` | Retracted by its sender while `pending` ("MD-11"). It is never delivered. | Reported by event |
| `superseded` | Reserved for a later intent that replaces a `pending` message ("MD-14"). No v1 path produces it. | Reported by event |

Transitions: `pending` to `delivered`, `retracted`, `expired`, or `dropped`; `delivered` to `consumed` or `expired`, and back to `pending` when a redelivery is due; `consumed` to `consumed_unrecorded` on a resume from a checkpoint taken before the consumption. `consumed_unrecorded` is final, and `consumed` is final unless such a resume occurs. A `delivered` message is never `retracted` or `dropped`, because the runtime already holds it, and a redelivery returns it to `pending` only inside the gateway's redelivery step, where no retraction can intervene: the step holds the session's delivery lock.

**Records [design, MDR-1].** Each inbox entry carries the message id, the sender's `from.kind` and `from.id`, the resolved intent, the state, the acceptance time, and the time of each transition. The transcript row of the message, which SD-1 "Reading client messages" gives a sender and a delivery state, carries the same state and intent, so `GET /v1/sessions/{id}/messages` reports them. The transcript row keeps the state after the inbox entry is released, and for a consumed message it also records the consumption's position in the session's sequence of consumption reports, which the gateway assigns in the order the session's stream relays them.

**Custody [design, S4, O4].** Delivery no longer removes an inbox entry. The entry moves to `delivered` and stays until the runtime reports consumption. When the gateway records the consumption, custody ends and the entry leaves the inbox, whether or not a checkpoint has recorded the consumption. In the durable inbox, `pending` entries stay in the Redis list, and an entry moves at delivery into a per-session Redis hash keyed by message id, which the coordinating replica reads on lease acquisition, and leaves the hash at consumption. The in-memory inbox keeps the same states in memory, and its documented loss window on a coordinator crash is unchanged.

**Redelivery [design].** The gateway redelivers every `delivered` entry, and never a consumed message (O4), oldest first and ahead of `pending` entries:

- after a resume onto a new pod (§7.3), at the session's first commit to `idle` after the restore: the restore's own commit, or, for a restore that landed in a paused state, the resume's commit to `idle` (lifecycle design, "SL-2");
- after a coordinator handoff with the durable inbox, at the new coordinator's adoption of the session, once it holds the lease. The runtime process is the same one, so the adapter suppresses ids it has already written to that process.

**Consumption after a checkpoint [design, O4].** A runtime restored from a checkpoint lacks every message it consumed after that checkpoint, and the gateway does not resend those messages, because a consumed message can have caused side effects that the checkpoint does not undo, for example a push. When a session resumes from a checkpoint, the coordinating replica reads the checkpoint's consumed set through the IC-4 catalog and takes the newest id in it that the gateway recorded as consumed. Every message whose consumption the gateway recorded after that id moves to `consumed_unrecorded`, oldest first. When no id in the set qualifies, every message the session consumed moves. Each move emits `message_state` with `state: "consumed_unrecorded"` and `reason: "checkpoint_restore"` on the session's event stream, and, for a message from another session, on the sending session's event stream as well, as `message_expired` reaches a sender today. A client or a parent that reads the event decides whether to send the content again, as a new message with a new id. A parent's runtime also receives the move as a notice in its inbox ("MD-22", **Outcomes**).

**Deduplication [design].** Because only `delivered` entries are redelivered, deduplication covers the following cases. After a coordinator handoff, the runtime process is the same one and may already hold a redelivered entry. After a resume, the restored runtime may hold an entry whose consumption report the pod loss cut off, when the checkpoint was taken after the runtime consumed it. The adapter keeps, per session, the ids it has written to the current runtime process for the first case, and for the second the ids the runtime reported consumed, bounded to the last 1000, kept in report order, and carried in the checkpoint. The consumed set replaces the `delivered_message_ids` set of the durable inbox's "Explicit ACK" row, and it no longer filters consumed messages, which are never redelivered. On a redelivery the adapter drops an id in either set and counts it on `lenny_inbox_duplicate_suppressed_total`, and for an id from the consumed set it relays a `consumed` frame, so the entry leaves custody. The runtime SDKs keep the ids each session consumed and drop a repeated id ("MD-12"), which covers a runtime whose own persisted history records a consumption that neither the gateway nor the checkpoint's set records. Within the gateway's deduplication window, a sender that sends again a message with the same sender-supplied id and the same content receives the original receipt and no second message, so a sender that lost a receipt can retry. Another sender's reuse of the id, or a reuse with other content, is refused as today.

**Expiry [design].** A `pending` entry keeps today's TTL rules, except as the lifecycle design states in "SL-5": an entry held for a `dormant`, `suspended`, or `blocked` session takes no TTL and expires when the session ends, and a child event takes no TTL while its parent lives, because the child cannot send it again (MDR-51). A `delivered` entry has no TTL while the session lives, because the runtime holds it. When the session ends, its `pending` and `delivered` entries become `expired` with `reason: "target_terminated"`, and the sender is notified as §15.4.1 states today.

### MD-4 Turn accounting

**`message.consumed` [design, S5].** The end-of-turn `message` frame gains `consumed`, an array of message ids that the runtime consumed in the turn the frame closes and has not reported in a `consumed` frame:

```json
{
  "type": "message",
  "parts": [{ "type": "text", "inline": "Switched to the staging database and reran the migration." }],
  "consumed": ["msg_01J9A", "msg_01J9B"]
}
```

**`consumed` frame [design, O2].** A runtime that declares `steer` writes `{"type": "consumed", "ids": ["msg_01J9B"]}` when it consumes messages during a turn. The adapter relays it on `CH-ATTACH` as it relays end-of-turn `message`, and `consumed` joins the session-scoped frame types the adapter routes to their session, which is the session of the connection's slot (`sessionScopedFrameTypes` in `pkg/adapter/attach.go`). A runtime that does not declare `steer` need not write it. The frame is a `CH-MSGSOCK` message, so no channel is added and the §28.3 registers are unchanged.

**Attribution without `consumed` [design, MDR-8, B-O6].** An end-of-turn `message` without `consumed` consumes every message of the session that is `delivered` when the frame arrives, and each becomes `consumed`. A runtime that handles one message per turn has one such message, so a runtime that declares no capability writes nothing new, and a `steer` runtime that omits the member reports the messages it was given. A mid-turn `message` without `consumed` consumes nothing. The end-of-turn `message` that closes a turn a suspension stopped consumes only the ids it lists, and every other `delivered` message of the session returns to `pending`, so the resume delivers it again (B19, MDR-55). Revision 9 attributed a frame without the member to the oldest `delivered` message, and a `steer` runtime's frame without it to none.

**Unsolicited responses [design, S5].** An end-of-turn `message` that finds no `delivered` message to attribute, and carries no `consumed` ids, closes a turn the runtime started on its own. The gateway records its output in the transcript, emits its `output` events and a `turn_end` event with `unsolicited: true`, and counts it on `lenny_unsolicited_response_total{runtime, runtime_revision}`. A child's unsolicited response counts against the child's outgoing `messagingRateLimit` ("MD-9"). An id in `consumed` that names no `delivered` message of the session is logged as a protocol error and ignored.

**Open turn [design, O1].** The gateway's session state records whether a turn is open:

- A turn opens when the gateway writes a message while no turn is open, and when the runtime emits output, a `tool_call`, or a `consumed` frame while no turn is open. A `retract` frame ("MD-11") opens no turn, because it produces no work for the session, and an `activity` frame opens none ("MD-15"). A `message_part` frame is output and opens a turn ("MD-16"). A frame from a session in a paused state opens no turn and changes no session state (lifecycle design, "SL-3").
- A turn closes on the runtime's end-of-turn `message` and on the end of the runtime process. The gateway also cuts an open turn at a suspension, at the idle clock, at a close, and at a pod loss (lifecycle design, "SL-3", "SL-6", and "SL-7").

The open turn replaces `ready_for_input` as the condition a `queue` message waits for. A runtime that writes no end-of-turn `message` keeps its turn open, as it keeps a turn open today, and the idle clock of the lifecycle design's "SL-6" bounds the turn: when no qualifying activity arrives for `maxClientIdleSeconds`, the turn is cut and the session becomes `dormant`. The turn ordinal increments at each opening, and `turn_end` events carry it.

**Errors [design].** An end-of-turn `message` with `error` closes the turn as a failed turn, and the messages it lists in `consumed` are `consumed`. A message the failed turn did not consume stays `delivered`, and the runtime may consume it later. The gateway reads `error`, which the executor ignores today (client-tools design, "Defects found while verifying").

### MD-5 Delivery paths

§7.2 "Message delivery routing" is rewritten as named paths, evaluated in order, where the first match wins **[design]**. Names in place of numbers let a later path join the list without renumbering its neighbours, as the specification's naming law asks of channel identifiers.

| Path | Condition | Action | Receipt |
| :-- | :-- | :-- | :-- |
| Dead-letter path | The session is terminal, pre-running, `resume_pending`, or `resuming`, or it is in `awaiting_client_action` and the message comes from neither the session's client nor the root's client. | As old path 7 and the dead-letter table state. | As today |
| Resume path | The session is `dormant`, `suspended`, or `blocked`, or it is in `awaiting_client_action` and the message comes from the session's client or the root's client. | For a `dormant` session, hold the message and wake the session through the resume admission check and a restore, then apply the rows below to the restored runtime. For a `suspended` or `blocked` session, hold the message, and resume the session only when the message comes from the root's client, under the table of the lifecycle design's "SL-5". For a session in `awaiting_client_action`, hold the message and resume the session through a restore, as a resume by its client does. When the admission check refuses, the message stays `pending` in the DLQ. | `delivered` on synchronous delivery, otherwise `queued`, and `queued` with `reason: "resume_refused"` and the refused scope when admission refuses |
| Direct path | No turn is open, or the message is a results message. | Write now. | `delivered` |
| Steer path | A turn is open and the intent is `steer`. | Write now. | `delivered` |
| Interrupt path | A turn is open and the intent is `interrupt`. | Hold the message, call the adapter's `Interrupt`, and write the message when the interrupted turn's closing `message` arrives. When `interrupt_acknowledged` does not arrive within the `interrupt_request` deadline, the message continues as `queue`, and the adapter writes no session state (MDR-54). | `queued` |
| Queue path | A turn is open and the intent is `queue`. | Hold until the turn's closing `message`. | `queued` |

The session stays `running` on the interrupt path. Suspension is a separate operation: `POST /v1/sessions/{id}/suspend`, which replaces `POST /v1/sessions/{id}/interrupt`, pauses the session and its subtree under [`0146-session-lifecycle`](../0146-session-lifecycle/change.md) ("SL-4"). The direct, steer, interrupt, and queue paths cover the `idle` and `running` states of that design.

**Delivery of held messages [design].** At each turn end, after each commit to `running` or `idle`, and after each adoption of a `running` or `idle` session (MDR-56), the coordinating replica writes the held entries whose intent now permits a write, oldest first by acceptance time across the inbox and the DLQ. For a runtime that does not declare `steer`, it writes one entry and waits for the next turn end before the next, so each held message is its own turn as today. For a `steer` runtime it writes every eligible entry, and the runtime may consume them in one turn. Held deliveries no longer precede every direct-path write: a held entry that is eligible is written before the new message at the same delivery point, which keeps acceptance order.

**Client tools [design, S6].** For a session with pending client calls, the client-message rules of [CT-5](../0122-client-tools/change.md#ct-5-pending-calls-and-the-hold-rule) run before the paths. For a runtime that does not declare `steer`, inbox deliveries are held as CT-5 and the client-tools design's O3 state. For a `steer` runtime they take the paths above ("MD-10").

**Successor pointers [design].** Each numbered path keeps a pointer in §7.2 to its named successor: path 2 to the direct path, path 5 to the queue path, path 4 to the interrupt path, path 6 to the resume path, and path 7 to the dead-letter path. Path 1 and path 3 leave with `lenny/request_input` and the `input_required` sub-state, and their pointers name "MD-22" (B5). The proposal retargets the specification's citations of path numbers, in §7.3, §10.1.2, §11.1, §15, §15.4.1, and §29.3 among others, to the names.

**Removed rules [design, O1].** The `ready_for_input` definition, the delivery timeout of 30 seconds and its fall-through to the inbox, and the `input_required` overlap rule between old paths 3 and 5 leave §7.2. §29.3 step 8 is rewritten: the adapter relays `consumed` and end-of-turn `message`, and the gateway derives the open turn from them.

### MD-6 Executor, lock, and waiting

**Writer [design, S9].** `PodExecutor` gains `Deliver(ctx, sessionID, []Envelope) ([]WriteResult, error)`, which writes each envelope on the session's `CH-ATTACH` stream and returns once the writes succeed or the stream fails. It takes no turn token, and a write is allowed while a turn is open. `attachConn.token`, `acquireTurn`, and the turn registration leave `podstream.go`.

**Reader [design].** The stream's reader routes every frame: `consumed` and end-of-turn `message` update inbox states and the open-turn state through one session-scoped recorder, end-of-turn `message` and `message_part` frames go to the transcript and the event stream under "MD-16", `activity` frames go to "MD-15", and an unsolicited response is recorded under "MD-4". Nothing is discarded for want of a waiter. An approval-required `tool_call` and a `request` frame wait off the reader's goroutine, so the reader keeps reading during an approval (MDR-22, MDF-8).

**Turn waiter [design].** `AwaitConsumingTurn(ctx, sessionID, messageID) (TurnResult, error)` returns the end-of-turn `message` of the turn that consumed the message, or the failed turn's error. The provider-surface adapters and replay use it. A waiter that stops waiting leaves nothing registered on the stream, because the reader's routing does not depend on waiters.

**Delivery lock [design, MDR-4].** `deliveryLocks` covers classification, the inbox write, and the `Deliver` call, and is released before any wait for a turn. The lock still serializes held-message delivery against the message paths on one replica, which is the purpose `sessionserver.go` states for it.

**Classification [design].** `messagerouting.Classify` takes the session row, the open-turn state, the resolved intent, the revision's declared intents, and whether the message is a results message, and returns a named path. Its comment that a synchronous executor is ready by construction leaves with the turn token.

### MD-7 REST

<a id="md-7-rest-and-mcp"></a>

> **Adapter-facing parts.** The REST route, the receipts, the events, and the client retraction route still govern Lenny. The client-facing MCP `send_message` tool and the MCP retraction tool generated from the route move to the MCP adapter under O8 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), stay here unchanged until that adapter's repository takes them, and stage no edit to Lenny's specification.

**Send [design, S3].** `POST /v1/sessions/{id}/messages` answers with `deliveryReceipts`, one per message in the batch, in the order sent, and no `output` member. `delivered` now means that the gateway wrote the message for the runtime. The receipt answers once the message is written or held, without waiting for consumption or output, and carries `seq`, the session's event sequence number after the message's `message_state` event, under R1 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), so a client that opens the event stream from that number misses no event of the send. The client-facing MCP `send_message` tool and the agent-facing `message_child_session` return the same receipt. The §15.4.1 description of `delivered` changes from "runtime consumed" to "written for the runtime; consumption is reported by the `message_state` event".

**Events [design].** The `SessionEvent` registry of §15 gains these kinds:

| Kind | Payload | Fires when |
| :-- | :-- | :-- |
| `message_state` | `{ "messageId", "state", "intent", "fromKind", "fromId"?, "turn"?, "reason"? }` | A message of the session changes state, including to `retracted` and to `consumed_unrecorded`. A move to `consumed_unrecorded` also reaches the sending session's stream for a message from another session ("MD-3"). The payload carries no content. |
| `turn_end` | `{ "turn", "consumed": [ids], "unsolicited": bool, "error"? }` | An end-of-turn `message` closes a turn. |

"MD-15" adds `activity`, and "MD-20" adds `turn_start` and `usage` and extends `turn_end`. The registry is closed, so the additions take the `SessionEvent` schema revision the registry requires. The session's `output` events carry the turn's output as they do today. Adapters that do not list the kinds in `SupportedEventKinds` do not receive them, under the registry's dispatch-filter rule.

**Client retraction [design, O5].** Under O5, a client retracts its own `pending` message: `DELETE /v1/sessions/{id}/messages/{messageId}` runs the retraction of "MD-11" for a message the caller sent to the session and answers `200` with `{ "messageId", "result" }`, where `result` is `retracted`, `too_late`, or `unknown`. A message the caller did not send answers `unknown`, under MDR-11. The MCP tool is generated from the route under §15.2.1 rule 4.

**Clients [design].** The Go client SDK, the `lenny session send` command, and the web playground read output from the event stream. `lenny session send` without an attached stream prints the receipt and exits, as §24 states today.

### MD-8 Provider surfaces

> **Moves to the provider adapters.** Under O8 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), the surface rules of this section and requirement MDR-14 govern the OpenAI Chat Completions, Open Responses, and Anthropic Messages adapters and no longer govern Lenny. They stay here unchanged until each adapter's repository takes them, and stage no edit to Lenny's specification. The consumption attribution the adapters read, the `consumed` list of "MD-4" and the cut point at a message's consumption, stays in Lenny, and R2 and R3 of that design expose it.

A Chat Completions, Responses, or Messages API request is one turn, because its client follows the provider's API, where a request is a turn **[design]**:

- The adapter writes the request's message through the paths of "MD-5" with no intent the request can set. A cold turn reaches a new session through the direct path. A warm turn reaches a session whose newest client turn has completed, under the conditional send, R16 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), so the only turn that can be open is one that no request on this surface caused, such as a turn another session's message caused. With no open turn, the message takes the direct path on an `idle` session and the resume path on a `dormant` one, which R16 accepts when no restore to a checkpoint older than that turn has happened (its O12). With such a turn open, it takes the steer path on a runtime that declares `steer` and the queue path, which waits for the turn's closing `message`, on any other runtime (O3).
- The adapter waits with `AwaitConsumingTurn` for the turn that consumed the request's message, and returns that turn's output from the point the runtime consumed the message. A turn the message opened returns all its output. For a message steered into a running turn, the response carries the output that follows the `consumed` frame listing the message, or, when only the turn's closing `message` lists it, that end-of-turn `message`'s own output. A `steer` runtime may consume inbox deliveries in the same turn, and their ids appear in the turn's `consumed` list. Only the client's message decides which turn answers the request.
- A second request during a running turn that a request on the same surface caused behaves as it does today: on Responses it runs cold, on the Messages API an identical retry joins the running turn through AM-5's in-flight join and any other request runs cold, and on Chat Completions, whose adapter finds a conversation's session by its fingerprint under the simplified O3 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), a request whose history lacks the running turn's reply matches no session and runs cold.
- A Chat Completions session is an ordinary session, as every provider-adapter session is: it stays open after its turn, and its `pending` entries wait as they do on any session. A `one_shot` runtime ends its own session at its end-of-turn frame ("MD-22"), and its `pending` entries then expire with `target_terminated`.
- The Responses cold walk of a conversation's transcript includes consumed inbox deliveries as entries carrying their `from` object, with the output of the turns they caused, so a cold runtime reads what the warm runtime read. The Messages API and Chat Completions take their history from the client, and the gateway adds nothing to it.

**Delivery on arrival [design, O3].** A message from another session to a session created on a provider surface is delivered on arrival under the ordinary intent rules of "MD-1" and "MD-5", and the provider surfaces add no handling of their own. On a provider-adapter session between client requests no turn is open, so the message takes the direct path and opens a turn. No delivery waits for the client's next request. These rules keep such a turn away from the provider-surface client:

1. **Client tools only in turns a client request caused.** A turn caused by another session's message, a system message, or an external message carries no `conversation.clientTools` and no `conversation.toolChoice`, and an end-of-turn `message` of such a turn that carries `clientToolCalls` fails the check of [CT-4](../0122-client-tools/change.md#ct-4-response-validation) with `no_tools_declared`. A client request steered into such a turn carries its own `conversation.clientTools` in its envelope, so the runtime may call those tools from the point it consumes the request, and the turn's closing `message` returns the calls to that request's client.
2. **No such turn in a provider-surface response.** A turn that no client request caused never appears in a provider-surface response. Its output goes to the transcript and to the session's REST event stream. It writes no response record and no conversation digest and takes no response ordinal, so the warm conditions of the client's next request are unaffected. The client's next response is the output of the turn its own message caused, under the `consumed` attribution of "MD-4" and the cut point stated above.

Tool-use approvals in such a turn work through the approvals API as on any session. Elicitation stays refused on those surfaces, as AM-6 states for the Messages API, whatever caused the turn, and a runtime asks its provider-surface client by replying ("MD-22").

**Scenarios [design, O3].** A message reaches a session created on a provider surface other than through the client's own requests in these cases:

- Asynchronous delegation, the main case. A runtime served on the Messages API or Responses starts a child, replies to its client, and after that reply the child sends a mid-turn message, ends a turn, completes, or fails. Each reaches the parent as a child event ("MD-22"), and the parent runtime takes it in a turn of its own. The client sees that turn on the session's REST event stream, and in a provider response only when the runtime refers to it in a later turn the client caused.
- The same session used from REST, through the session id the response headers carry. A REST client message causes a turn whose output reaches the REST event stream and no provider-surface response.

### MD-9 Inter-session messages, system messages, and delegation

**Inter-session messages [design, B1].** A session sends messages to other sessions only along the delegation tree. A parent sends to a child with `message_child_session`. A session sends to its client, which for a child is its parent, with `send_update` or a mid-turn `message` frame, and ends its turn with an end-of-turn `message` ("MD-22"). `message_child_session` carries `delivery` in its message and resolves the target's default intent when absent. The cross-tenant check, the messaging scope, the rate limits, and the `PreMessageDelivery` interceptor run before the intent check, as §7.2 orders them today. The call returns its receipt once the message is written or held, so a sender never waits for the target's turn. A parent learns the outcome of its own messages as a client does ("MD-22", **Outcomes**).

**Messaging scope [design, B9].** The `siblings` value of `messagingScope` leaves §7.2, and `direct`, a parent and its direct children, is the only scope. A child that needs a sibling's result asks its parent by ending a turn, and the parent relays it with `message_child_session`. `interrupt` travels only from a session's client to the session: from a REST client, or from a parent through `message_child_session`.

**Sender [design].** `message_child_session` takes its sender only from the calling session, which the adapter's binding of the platform server names, and it accepts no `fromSessionId`. The client-facing MCP `send_message` of §15.2 keeps its own rules. Today one handler serves both, and it takes `fromSessionId` as the sender whenever the caller's principal carries no session claim, after it checks that the caller owns that session (`callerSessionID` and the `send_message` handler in `pkg/gateway/mcpfabric/mcptools`) **[source]**. Within one owner, the caller chooses the sender. The agent-facing tool does not inherit that member. The root's client of the lifecycle design is the authenticated principal that owns the root, so a `fromSessionId` never makes a caller the root's client and never lifts a suspension (lifecycle design, SLR-22).

**Policies on child events [design, M6].** A child event is a message into the parent, so it passes the parent's `contentPolicy` and its `PreMessageDelivery` interceptors, as a `message_child_session` from the parent passes the child's. A compromised child therefore reaches its parent's running turn only through the checks every other message meets. `send_update` and a mid-turn `message` count against the child's outgoing `messagingRateLimit`, as `message_child_session` counts against the parent's. A child can also open turns on its own, because output opens a turn ("MD-4"), so an end-of-turn child event whose turn consumed neither a message from the parent nor a system message of the gateway counts against the same limit, and one over the limit is refused as a `send_update` over it is (R10-H1). No rate limit refuses an end-of-turn child event whose turn consumed a message from the parent or a system message of the gateway, such as the lifecycle design's resume notice, an `awaiting_client_action` event, or an `ended` event: such a turn answers one of the parent's own sends, which the parent's limit bounds, or a notice the gateway sent, a session produces one `ended` event, and a refusal would leave the parent without the child's answer (MDR-43). The `turn_lost` and `idle_timeout` reports of the lifecycle design come from the gateway and count against no limit. When an interceptor rejects such an event, the gateway delivers in its place a notice that names the child, the event, and the rejection, so the parent still learns that the turn or the session ended.

**Loop bound [design, B-O4].** Two models can keep each other busy: a child's end-of-turn event opens a turn in its idle parent, and the parent's reply opens a turn in the child. Every round of such a loop needs one `message_child_session` from the parent or one turn the child opens on its own, and every loop runs along one edge of the tree, because siblings no longer message each other. `message_child_session` falls under the parent's `messagingRateLimit`, whose `maxPerMinute` is 30 by default and whose `maxPerSession` caps the session's life ([§8.3](../../spec/08_recursive-delegation.md#83-delegation-policy-and-lease)), and an end-of-turn event of a turn the child opened on its own falls under the child's ("Policies on child events"), so a loop slows to those rates and stops at the lifetime caps at every level of the tree. No further mechanism is added. When a session reaches `maxPerSession`, the gateway emits `messaging_limit_reached` on the root's event stream, naming the session and the limit, so the person watching the root sees why the tree stopped.

**Across environments [design, B-O5].** A parent in environment E and a child that crossed into environment T through a sharing path of [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md#ts-3-session-environment-context-and-cross-environment-sharing) TS-3 message each other. A message passes the sending environment's `contentPolicy` and `PreMessageDelivery` interceptors, then the receiving environment's. The rules that bind the whole tree apply on every edge whatever environment either end is in: the delegation lease, the budgets, `maxDelegationPolicy`, and `messagingRateLimit`, so crossing an environment never loosens a rule that applies to the session as a whole. Steering crosses the boundary, because `TaskResult` already crosses it.

**Delegation [design].** A parent can redirect a running child with `steer`, for example "stop exploring the cache layer and fix the failing test", without closing it and losing its work. A parent that wants the child to stop first sends `interrupt`, when the child's runtime declares it. The `task` of `start_child_session` is the child's first message and starts its first turn, so no intent applies to it. The child's mid-turn messages, its ends of turn, and its end reach the parent as child events under "MD-22". A child event to a parent created on a provider surface is delivered on arrival, and the turn it causes follows the rules of "MD-8" (O3). The subtree deadlock detector of §8.8 leaves, because no state waits on another session ([`0146-session-lifecycle`](../0146-session-lifecycle/change.md), "SL-8").

**System messages [design].** A message the gateway itself originates carries `from.kind: system` and takes the target's default intent unless the mechanism that sends it names one. v1 defines the notice of a failed outcome of a parent's own message ("MD-22"), the notice that replaces a rejected child event, and the resume notice of the lifecycle design's "SL-3". Child events carry `from.kind: agent` with the child's session id. "MD-14" lists further candidates.

**External senders [design].** Until revision 22, a message routed through a connector carried `from.kind: external` and followed the same rules as an inter-session message. [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors, so no Lenny path produces `from.kind: external` today. The value stays defined for a participant outside Lenny ("MD-14"), with the inter-session rules, and a reader treats it as any `from.kind`.

**Sender kind [design].** The adapter writes `from` as today, and the inbox entry and the transcript row record it (MDR-1), so a runtime that weighs a client's correction above an agent's suggestion can tell them apart. A child event carries the child's session id in `from.id` ("MD-22").

### MD-10 Client tools

The client-tools design's revision 2 already scopes its hold rule to runtimes that do not declare `steer` ("Steer-declaring runtimes" under CT-5) and adds the history rule ("Order of history entries" under CT-7). This part states the delivery machinery's side of both.

**Inbox deliveries while calls are pending [design, S6].** For a runtime that declares `steer`, an inbox delivery to a session with pending client calls takes the paths of "MD-5". The session has no open turn after the turn that returned the calls, so the message is written at once and opens a turn. That turn carries no `conversation.clientTools`, because no client request caused it (O3, rule 1 of "MD-8"). The runtime holds the message, places it after the results when they arrive, and reports its consumption then, or acts on it without a model call. CTR-4 of the client-tools design narrows to runtimes that do not declare `steer`, for which T5's hold and that design's O3 stand. CTR-5 holds unchanged, because the calls themselves stay session data and the held message is in the gateway's custody until consumed ("MD-3").

**Client messages [design, S7].** A client message without the pending results is refused on every surface. On REST a message that sets `abandonPendingToolCalls: true` is a results message whose results are the "cancelled by client" error results, with the client's text as `input`. A results message takes the direct path whatever the open-turn state, because a `steer` runtime may be holding an inbox delivery behind the pending calls.

**Retraction [design, S8].** A runtime that no longer wants some or all of its pending calls retracts them by their runtime ids with the `retract` frame of "MD-11". On REST the calls are cancelled and the client receives a retraction event. On provider surfaces the answer is `too_late`, the client still sends results, and the runtime ignores them.

**Cold-history ordering [design, S6, MDR-7].** The cold-history builder, which the client-tools design's CT-7 and AM-4 use, places each entry by the turn and the position at which the runtime consumed it, from `consumed` frames and `message.consumed`. An entry consumed while client calls were pending moves to after the entry that carries their results, as CT-7 "Order of history entries" requires, and entries that move keep their relative order. An entry reported only on an end-of-turn `message` is placed after the output that turn streamed before the end-of-turn `message`, and before the end-of-turn `message`'s own output. The builder never places an entry between an assistant entry that carries calls and the entry that carries their results.

### MD-11 Retraction

The owner settled S8 on 2026-11-09: a runtime may retract any message it generated. Retraction is one operation in the delivery machinery, keyed by id, and it changes only what no recipient has received **[design, S8, MDR-10]**.

#### Request and result

A runtime writes a `retract` frame on `CH-MSGSOCK`, inside or outside a turn:

```json
{ "type": "retract", "retractId": "rt_1", "ids": ["tc_7", "msg_01J9X"] }
```

The adapter relays it on `CH-ATTACH` to the stream of the session it names, as a session-scoped frame ("Blast radius"). The gateway answers with a `retract_result` frame, which the adapter writes to the runtime as it writes every envelope the gateway sends:

```json
{
  "type": "retract_result",
  "retractId": "rt_1",
  "results": [
    { "id": "tc_7", "result": "too_late" },
    { "id": "msg_01J9X", "result": "retracted" }
  ]
}
```

- `results` holds one entry per requested id, in request order, with `result` set to `retracted`, `too_late`, or `unknown`.
- `retracted`: the item will never reach its recipient. A repeated retraction of an id already retracted answers `retracted`, so a runtime may retry after a lost answer.
- `too_late`: the recipient already received the item, the item reached a final state another way, or the surface cannot withdraw it. Nothing changes.
- `unknown`: the id names nothing this session may retract (MDR-11).
- The frames add no channel, so the §28.3 registers and the naming law are unaffected. A runtime that never writes `retract` never receives `retract_result`.

#### What a runtime may retract

| Item | Id the runtime names | `retracted` when | `too_late` when | Effect of `retracted` |
| :-- | :-- | :-- | :-- | :-- |
| A pending client tool call on a REST session | The call's runtime `id` from `clientToolCalls` | The call is still in the session's pending set. | A results message cleared the set first. | The gateway removes the call from the pending set with the conditional write [CT-5](../0122-client-tools/change.md#ct-5-pending-calls-and-the-hold-rule) uses for results, and emits a `tool_use` event with `target: "client"` and phase `retracted`. The next results message answers exactly the calls that remain, and one that names a retracted call is refused with `409 CLIENT_TOOL_CALLS_RETRACTED`. When no call remains, the session has no pending calls. |
| A client tool call on a provider surface (Messages, Chat Completions, or Responses) | The call's runtime `id` | Never. | Always. | None. A returned call cannot be withdrawn on these surfaces: the pending set stays, the client sends results as the provider's API requires, and the runtime ignores them. |
| A message the runtime sent to a child through `message_child_session`, or a mid-turn message it sent to its parent through `send_update` or the `message` frame | The `messageId` of the receipt, or the id the runtime supplied | The message is `pending` in the recipient's inbox or DLQ. | The message is in any other state: `delivered`, `consumed`, `expired`, or `dropped`. | The entry moves to `retracted` and leaves the store, it is never delivered, and the recipient's event stream receives `message_state` with `retracted` and no content. |
| Output and session events | None, because output parts and events carry no id | Never in v1. | Not applicable. | Ignored for now ("Blast radius"). Output already streamed to a client cannot be recalled. A part still streaming can be discarded with `reset` ("MD-16"), which is not a retraction. |
| Anything else: a child's `task` from `start_child_session`, a mid-turn message to a top-level client, which an event already carried, a `tool_call`, another sender's message, or an id the gateway does not know | Any | Never. | Never. | `unknown`. A runtime stops a child with `close_child_session`. |

A retracted `interrupt` message is never delivered, and an interrupt the gateway already requested for it proceeds, because the runtime may already be stopping.

#### Ordering

A message retraction runs on the recipient's coordinating replica under the recipient's delivery lock, which the message paths and the delivery of held messages also take ("MD-6"), so a retraction and a write of the same entry never interleave: the one that takes the lock first wins. The gateway routes a retraction to the recipient as it routes the `message_child_session` call that sent the message, including the forwarding to a coordinating replica on another gateway replica. A client-call retraction and a results message race on the session row's conditional write, and exactly one of them takes effect.

#### Audit and interceptors

Each retraction that changes state writes the audit event `message.retracted`, or `client_tool_call.retracted` for a call, naming the retracting session and principal, the item's id and kind, the recipient session, the surface, and the result (MDR-12). The counter `lenny_retraction_total{kind, result}` counts every result, including `too_late` and `unknown`, so an operator can see a runtime that retracts often or names ids it does not own. Audit records carry no message content.

No interceptor phase runs on a retraction. A retraction removes content from a recipient's path and adds none, and the retracted content already passed `PreMessageDelivery` for a message, or `PostAgentOutput` for a call's arguments, when it was sent. A deployer who needs to observe retractions reads the audit event.

#### Blast radius

The owner asked for retraction of messages other than client calls if its blast radius is small. It is small for messages, because "MD-3" already gives every inbox entry a state and a lock-held transition, and a runtime's message to another session lives in one place:

| Component | Change | Size |
| :-- | :-- | :-- |
| Inbox store (`sessioninbox`, in memory, on the Redis list, and in the DLQ sorted set) | The `retracted` state and one transition from `pending`. Removing a `pending` entry uses the removal the store already performs at delivery and expiry. | Small |
| Outbound queue | None. Lenny has no outbound queue: a runtime's `message_child_session` lands in the recipient's inbox or DLQ, so a retraction has one place to look. | None |
| Routing to the recipient | The retraction reuses the send path's classification read and its forwarding to the coordinating replica. | Small |
| Session row (client tools) | Removal of ids from the pending set by the conditional write CT-5 defines. | Small |
| Executor | The reader routes `retract` to a retraction handler, and the writer sends `retract_result`. | Small |
| Adapter | `retract` joins `sessionScopedFrameTypes` in `pkg/adapter/attach.go`, so the demultiplexer relays it to its own session's stream alone. Without the entry, a frame type outside the set passes through to every Attach stream on the pod as a protocol-level frame. `attachRecvLoop` writes `retract_result` as it writes every envelope the gateway sends. | Small |
| Runtime SDKs | A `Retract` call ("MD-12"). | Small |
| Audit, events, and metrics | The audit events `message.retracted` and `client_tool_call.retracted`, the `retracted` value on `message_state` and `tool_use`, and `lenny_retraction_total`. | Small |

Output and session events are not small, so they are ignored for now. Output parts and events carry no id a runtime could name. An `output` event fans out at once to every outbound channel of the session, enters the event store's replay sequence, and enters the transcript, and the provider adapters fold it into response records. Recalling one part would need ids on parts, a tombstone in the replay sequence, and a rule for channels that already received it. "MD-14" lists it as a future case.

### MD-12 Runtime SDKs

**Drain call [design].** The Go, Python, and TypeScript SDKs add a call on the handler's context, `DrainMessages(ctx) []Message` in Go, `drain_messages()` in Python, and `drainMessages()` in TypeScript. It returns, in arrival order, the messages that reached the runtime for the session while the handler runs, and removes them from the session's queue. A model loop calls it between model steps, after the step's tool results are in hand, and appends what it returns after those results. The SDK treats every returned message as consumed, writes a `consumed` frame for their ids, and keeps them out of a later `OnMessage`.

**Consumption reporting [design].** The SDK writes `consumed` on the end-of-turn `message` it writes for an `OnMessage` call, listing that call's message and any drained message not yet reported. A handler that declares `steer` and never calls the drain call degrades to queue-until-turn-end inside the SDK: the queued messages wait for the next `OnMessage`, and the runtime is still correct.

**Deduplication [design].** The SDK keeps the ids each session consumed, bounded to the last 1000, and drops a message whose id is among them. A runtime that persists its own history keeps the set with it, so a restored runtime drops the redeliveries "MD-3" sends.

**Unsolicited responses [design].** The SDK adds `Respond(ctx, sessionID, Reply)`, which writes an end-of-turn `message` outside an `OnMessage` call, for a runtime that finishes background work and wants to report it.

**Retraction [design, S8].** The SDK adds `Retract(ctx, sessionID, ids) ([]RetractResult, error)` in Go, and `retract()` in Python and TypeScript. It writes a `retract` frame with a fresh `retractId`, waits for the matching `retract_result` under the caller's context, and returns one result per id. A context that ends first returns an error, and a retry is safe because retraction is idempotent.

**Messages, requests, and children [design, B-O6, H1].** `Respond` writes a `message` frame and takes `endOfTurn`, `complete`, and `parts`, and `Update` writes a mid-turn `message`. `Request(ctx, sessionID, Request) (Reply, error)` in Go, and `request()` in Python and TypeScript, write a `request` frame and wait for its `reply`, for approvals, questions, and imports. `WatchChild` and `ImportChildFile` wrap "MD-25" and "MD-26". The SDKs flush stdout before any platform tool call, so a `send_update` the adapter converts lands after the frames the runtime wrote first ("MD-22").

**Busy reporting [design].** A handler that holds a drained message across a wait for client results takes a busy hold only while it works. Holding a message is not work, so the session idles and suspends as §15.7 states.

**Activity, output, files, and approvals [design].** The SDKs add `ReportActivity(ctx, Activity)` in Go, `report_activity()` in Python, and `reportActivity()` in TypeScript, which write `activity` frames, with helpers for each operation and an `End` that sets the final status. `Output` writes the `message_part` frame, with a streaming writer that emits `append`, `end`, and `reset`. A file helper emits a `file` part by workspace path with a fresh part `id`. The SDKs report the `output_failed` frame of "MD-18" to the runtime through `OnOutputFailed(ctx, OutputFailure)` in Go, `on_output_failed()` in Python, and `onOutputFailed()` in TypeScript, with the part `id` and the reason, so a runtime can emit the file again. When the handler returns, the SDK writes `output_failed_ack` with the part `id`, and it drops a later notice for a part `id` it has already acknowledged, because the gateway sends an unacknowledged notice again after a resume. `RequestApproval` and `RequestElicitation` write a `request` frame of `kind` `approval` and `question` and return the matching `reply`, through the `Request` call below. `SendUpdate` writes a mid-turn `message` frame, and `Complete` writes the end-of-turn frame with `complete: true` ("MD-22"). The client SDKs keep events as `{type, data}` strings, so the new kinds reach applications with no client SDK release, and typed helpers for the conventional kinds are optional.

### MD-14 Future use cases and the extension rule

**Cases the machinery covers [design].** None ships in v1.

| Case | How it fits |
| :-- | :-- |
| Scheduled delivery | A `deliverAt` member keeps a message `pending` until a time. The gateway alone acts on it, so no runtime declares it. |
| Priority ordering | A `priority` member orders `pending` entries of one intent. Gateway-only. |
| Context-only messages | An intent `append` delivers a message the runtime adds to its history without starting a turn, as the Claude Agent SDK's `shouldQuery: false` does. Declared, because the runtime acts on it. |
| Background, then steer | An intent that asks the runtime to move its running work to the background and read the message in the same turn, as Claude Code's `now` does with a human origin. Declared. |
| Further system notices | `system` messages from the gateway, such as a budget warning or a deadline, delivered with the target's default intent, as Claude Code folds task notifications into a turn. A child's completion and failure ship in v1 as child events ("MD-22"). |
| Consumption notices to senders | A `message_state` event on the sending session's stream for every state change, beyond the move to `consumed_unrecorded` that v1 already reports there and the failed outcomes a parent receives ("MD-22"), and a notice when a target goes idle, as Claude Code's `notify_when_idle` does. |
| Replacement | An intent that supersedes the sender's earlier `pending` message with a new one. It uses the `superseded` state. |
| Retraction of output | Ids on output parts and events, a tombstone in the event replay sequence, and a rule for channels that already received a part, so a runtime can recall output the gateway has not yet sent to a client. S8 leaves it for later ("MD-11"). |
| External participants | Messages with `from.kind: external` from a participant outside Lenny, steered into a running session. Revision 21 named connectors as their path; [`0124-connector-removal`](../0124-connector-removal/change.md) removes connectors, and a future path states its own sender rules. |

**Extension rule [design, G1].** An addition to the machinery satisfies all of these:

1. A behaviour that applies whatever the intent, such as a delivery time or an order, is its own envelope member. A behaviour that changes when the runtime receives a message relative to its turn is an intent.
2. An intent states the gateway's action for each turn state of "MD-5" and the receipt it gives.
3. An intent the runtime must act on is declared in `injection.modes`, and the gateway sends it only to a declaring revision. A gateway-only intent is never declared and is listed in the §15.4.1 enum alone.
4. An intent states the runtime's obligation, including where the message goes in model history and how its consumption is reported.
5. An intent uses the states of "MD-3", and adds a state only when no existing state expresses its outcome. A new state states its transitions and its receipt.
6. The enum stays closed: an unknown intent is refused with `400 INVALID_DELIVERY_VALUE`, and registration refuses an unknown declared intent.
7. A new intent comes with a conformance case in §15.4.6 and a mapping row on each surface that exposes it.

### MD-15 Activity

The owner settled A2, A3, A7, and A10 on 2026-11-10 and kept the activity `kind` open-ended under conventions. Activity is the runtime's own report of what it is doing. The gateway shows it to clients, keeps the current state of every open activity, and keeps it out of model history **[design]**.

#### Frame

```json
{
  "type": "activity",
  "op": "start",
  "id": "act_7",
  "kind": "tool",
  "lifetime": "turn",
  "record": true,
  "parentId": "act_2",
  "agent": "explorer",
  "summary": "Running npm test",
  "detail": { "toolKind": "execute", "command": "npm test", "output": "" }
}
```

| Field | Set on | Meaning |
| :-- | :-- | :-- |
| `id` | Every frame | The runtime's identifier for the activity, unique within the session. |
| `op` | Every frame | `start`, `update`, `patch`, `append`, or `end`. |
| `kind` | `start` | An open string. "Conventional kinds" lists the kinds clients can rely on, and a custom kind takes the `x-<vendor>/` prefix that custom `MessagePart` types use. The gateway checks no `detail` schema for any kind. |
| `lifetime` | `start` | `turn`, the default, or `session`. A `turn` activity ends with its turn. A `session` activity, such as a plan, spans turns. |
| `record` | `start` | `true` asks the gateway to write the activity's final state to the transcript when it ends ("Recording"). The default is `false`. |
| `parentId` | `start` | The id of an enclosing activity, for nesting, such as a tool run inside a step or a subagent. |
| `agent` | `start` | The name of the harness-internal subagent that produced the activity. |
| `status` | `start`, `update`, `end` | `active`, the default on `start`, then `completed`, `failed`, or `cancelled` on `end`. |
| `summary` | `start`, `update`, `end` | A one-line text for display. |
| `detail` | `start`, `update`, `end` | Any JSON value, a string included. |
| `patch` | `patch` | An RFC 6902 JSON Patch applied to `detail` when `detail` is an object or an array. |
| `path` and `text` | `append` | `text` is appended to the string at the RFC 6901 JSON Pointer `path` inside `detail`. An empty `path` names `detail` itself when `detail` is a string. |

`kind`, `lifetime`, `record`, `parentId`, and `agent` are fixed at `start`. A frame that changes one is dropped with the reason `immutable_field`.

#### Operations

| `op` | Effect |
| :-- | :-- |
| `start` | Creates the activity. An `id` the session already used is dropped with the reason `duplicate_id`. |
| `update` | Replaces `summary`, `detail`, and `status` with the values the frame carries. A member the frame omits keeps its value. |
| `patch` | Applies `patch` to `detail`. The gateway applies the patch to its own copy before it forwards the frame, and a patch that fails to apply is dropped with the reason `patch_failed` and reaches no client (A3). |
| `append` | Appends `text` to the string at `path`. A `path` that names no string is dropped with the reason `invalid_target`. JSON Patch has no string append, so `append` covers growing text such as a command's output. |
| `end` | Sets the final `status`, and optionally a final `summary` and `detail`, and closes the activity. A frame for an ended `id` is dropped with the reason `ended_id`. |

A frame for an `id` the session never started is dropped with the reason `unknown_id`. Every drop is counted on `lenny_activity_dropped_total{runtime, runtime_revision, reason}`, and the gateway emits an `activity` event with `op: "lost"`, the `id`, and the reason, so a client knows its copy of that activity missed a change.

#### Conventional kinds

The kinds below are conventions that runtime authors and clients share. A runtime may send any kind.

| Kind | Meaning | Conventional `detail` members |
| :-- | :-- | :-- |
| `tool` | A tool the harness runs itself, such as its shell or file editor. A tool call that Lenny routes is reported by the `tool_use` event and never as activity. | `toolKind` (the Agent Client Protocol values `read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, and `other`), `title`, `toolUseId` (the harness's call id), `input`, `output` (a string, grown by `append`), `changes` (`[{path, change: add \| modify \| delete, diff?}]`), and `locations` (`[{path, line?}]`). |
| `plan` | The agent's plan or todo list. One per session, with `lifetime: session`, replaced by `update` or changed by `patch`. A plan proposed for the user's approval is an elicitation ("MD-19"). | `entries` (`[{id?, content, status: pending \| in_progress \| completed, priority?}]`). |
| `step` | A named phase of the agent's work. | `name`. |
| `thinking` | Reasoning shown as status ("MD-17"). | `text` (grown by `append`), `durationMs`, and `estimatedTokens`. |
| `subagent` | A subagent the harness runs inside its own process, such as a Claude Code task. Activities the subagent produces name it in `agent` and its activity in `parentId`. | `name` and `description`. |
| `compaction` | The harness compacting its context. | `tokensBefore` and `tokensAfter`. |
| `context` | The fill of the model's context window. | `usedTokens` and `windowTokens`. |
| `diff` | The workspace changes of a turn. | `files` (`[{path, additions, deletions}]`). |
| `hook` | A harness hook run. | `event`, `name`, and `output`. |
| `retry` | A model or tool call the harness retries. | `attempt`, `reason`, and `delayMs`. |
| `notice` | A message for the user that is not conversation content. | `severity` (`info`, `warning`, or `error`), `title`, and `description`. |
| `waiting` | The harness waits on something outside Lenny. | `on`. |
| `mode` | The harness changed its mode, such as a plan mode. | `mode`. |
| `model` | The harness changed its model. | `model`. |

#### Turn and close rules

- Activity never opens or closes a turn ("MD-4"). The gateway stamps each activity event with `turn`, the ordinal of the open turn, when a turn is open.
- When a turn closes, every open activity of that turn with `lifetime: turn` ends `cancelled` with `reason: "turn_ended"`. When the runtime process ends, every open activity ends `cancelled` with `reason: "runtime_exit"`. When the session ends, every open `session` activity ends `cancelled` with `reason: "session_ended"`. A client spinner therefore always stops.
- Activity counts as qualifying activity for the idle clock of the lifecycle design's "SL-6", as §6.2 counts `agent_output` and `tool_use`.

#### Current state and attach (A2)

The gateway keeps the current state of every open activity of a session in a Redis hash keyed by activity id, on the session's data shard, so any gateway replica that coordinates the session holds it. The hash is bounded by `activity.maxOpen` (default 256) and `activity.snapshotMaxBytes` (default 8 MiB) per session. A `start` past either bound is dropped with the reason `open_limit`.

On every attach and every resume, after the replayed events, the gateway sends one `activity` event with `op: "snapshot"` that lists every open activity, with a fresh `SeqNum` as the synthesized frames of §10.4 "Coordinator-handoff reattach" take. Activity events are volatile events under §10.4 "volatile vs. reconstructible events": a resume whose range lost only activity events receives the snapshot and no `gap_detected` for them. When the replay ring must evict, it evicts first an activity event whose `id` has a later event in the ring, so activity does not push other events out of the ring.

#### Recording (A2)

Activity stays out of the transcript unless the runtime starts it with `record: true`. When a recorded activity ends, the gateway writes one transcript row with the role `activity` that carries the activity's `kind`, `summary`, `detail`, final `status`, `agent`, `parentId`, `turn`, and its start and end times, at the position of its `start`. Intermediate updates are not recorded.

`activity.recordPerMinute` (default 60, operator-configurable) caps the recorded rows per session per minute. A recorded activity that ends over the cap is still shown live, and the gateway writes one marker row for the minute that states how many activities it did not record, and counts them on `lenny_activity_unrecorded_total`.

Recorded rows never reach a model: the cold-history builders of CT-7 and AM-4, conversation input, and SD-1's `GET /v1/sessions/{id}/messages?from=client` skip them. `GET /v1/sessions/{id}/transcript` returns them. Transcript retention, [§12.8](../../spec/12_storage-architecture.md#128-compliance-interfaces) erasure, and legal holds apply to them as to every transcript row.

#### Adapter rules

- **Size (A10).** The adapter parses each `activity` frame and drops one larger than `activity.maxFrameBytes` (default 1 MiB, operator-configurable) with the reason `oversize`. The session continues. Activity has no blob references: content larger than the cap is a file part ("MD-18") that an activity names by path.
- **Coalescing.** The adapter holds the newest `update` per `id` for at most `activity.minIntervalMs` (default 250 ms) and concatenates consecutive `append` frames to the same `id` and `path`. It never holds `start`, `patch`, or `end`, and before it relays any other session-scoped frame of the session it relays every held frame in the order of their newest writes. Coalescing therefore skips intermediate states and never reorders an activity against output, `tool_call`, `consumed`, or end-of-turn `message`.
- **Routing.** `activity` and `output` join `sessionScopedFrameTypes` in `pkg/adapter/attach.go`, so the demultiplexer relays them to their own session's stream alone.

#### Gateway rules

- **Interceptors.** A new interceptor phase, `PostAgentActivity`, receives each activity frame as JSON before the gateway applies and forwards it. `MODIFY` may change `summary`, `detail`, `patch`, and `text`, and may not change `id`, `kind`, `op`, `parentId`, or `status`. `REJECT` drops the frame, writes the audit record other phases write, and never fails the turn. A rejected `end` still closes the activity, with its `summary` and `detail` removed, so the close rule holds. The phase follows the failure policy each interceptor declares, as the other phases do. `PostAgentOutput` does not fit, because its payload is `MessagePart[]`.
- **Trust.** Activity is the runtime's claim about itself. No audit record, policy decision, budget, or approval reads it.
- **Opt-out.** A subscriber passes `activity: "none"` on `attach_session` and on `GET /v1/sessions/{id}/events` to receive no activity events. The default delivers them.

#### Child sessions (A7)

A delegated child session's activity stays on the child's stream. The parent's `tool_use` event for `start_child_session` carries `childSessionId`, and a client that wants the child's detail attaches to the child. A subagent that a harness runs inside its own process is a `subagent` activity of the session, because Lenny learns of it only from the harness. A parent's runtime may watch a child's stream, activity included ("MD-25").

### MD-16 Output streaming

The owner settled A5 and A6 on 2026-11-10 **[design]**.

**One path (A6).** A runtime emits output on the stdout `message_part` frame, whatever capabilities it declares. `lenny/output` leaves the platform tool set, and the runtime SDKs' `Output` call writes the frame. A `message` frame writes into the transcript only the parts it carries with content, and refers to a part already written on a `message_part` frame by its `id`, under the delivery rules of "MD-24". Every output therefore reaches the gateway on the session's `CH-MSGSOCK` frames, in write order, and passes the same interceptor and transcript rules.

```json
{ "type": "message_part", "parts": [{ "id": "p1", "type": "text", "status": "streaming", "inline": "Found" }] }
{ "type": "message_part", "parts": [{ "op": "append", "id": "p1", "inline": " the failing test." }] }
{ "type": "message_part", "parts": [{ "op": "end", "id": "p1" }] }
```

**Part operations (A5).**

| Entry | Effect |
| :-- | :-- |
| A `MessagePart` without `op` | A whole part with `status: "complete"`, the default, or the start of a streaming part with `status: "streaming"`, which then needs an `id`. |
| `{op: "append", id, inline}` | Appends `inline` to a streaming part of type `text` or `reasoning_trace`. |
| `{op: "end", id, status?}` | Ends a streaming part with `status` `complete`, the default, or `failed`. |
| `{op: "reset", id}` | Discards a streaming part, for example when the harness retries a model call halfway through. Clients remove what they rendered of it, and neither the transcript nor `PostAgentOutput` ever receives it. |

A streaming part still open when its turn closes ends `failed`, except a file part whose export is in progress or that waits for the export cap, which ends by the export's own outcome or at one of the deadlines of "MD-18", "Clocks" ("MD-18", "Export lifecycle"). A `reset` is not a retraction under "MD-11": it applies only to a part that has not completed, and the part never reaches the transcript.

**Turn.** A `message_part` frame opens a turn when none is open, as output opens one under "MD-4".

**Interceptors (A5).** `PostAgentOutput` runs once on each completed part, before the part reaches the transcript. On a session whose interceptor chain includes a `PostAgentOutput` interceptor, the gateway holds a streaming part's deltas and releases the completed, intercepted part as one event, so the policy sees every byte before any client does and streaming is lost on that session. A session with no such interceptor receives the deltas as they arrive.

**Transcript.** The transcript records each completed part once, at the position of its first frame, which is the position the cold-history builder of "MD-10" reads.

**Events.** The `output` SessionEvent carries the frame's entries, so a client applies `append`, `end`, and `reset` as the runtime wrote them. The `outputDeltas` adapter capability leaves under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md): an adapter reads the same entries from the REST event stream and coalesces the part operations itself when its protocol needs whole parts.

### MD-17 Reasoning

The owner settled A1 on 2026-11-10: "I think it could be either, depending on what the runtime implements." The runtime chooses where its reasoning goes, declares nothing, and Lenny does not convert one form into the other **[design]**.

- **As content.** The runtime emits a `reasoning_trace` output part, the registry type of §28.5.3 that AM-6 maps to a Messages API `thinking` block. The part gains `signature` (an opaque string the provider issued), `encrypted` (an opaque provider value), and `redacted` (`true` when the provider withheld the text, in which case `inline` is absent and `encrypted` carries the provider's data). The part streams under "MD-16", passes `PostAgentOutput`, and enters the transcript, cold history, and derive history. A `MODIFY` may not change `signature` or `encrypted`, and a `MODIFY` that changes the `inline` of a part carrying `signature` removes the signature, because the provider refuses an altered block.
- **As activity.** The runtime emits a `thinking` activity whose `detail.text` carries the reasoning. It stays out of the transcript unless recorded, and it never reaches a model or a provider surface.

A runtime has to emit reasoning as content when a Messages API client must send thinking blocks back with their signatures, or when the reasoning must survive in the transcript and in cold history.

### MD-18 Files

The owner settled A11 on 2026-11-10: the file goes "straight to storage", the size limit is a "5 GiB default. Runtimes can lower it", and the file has the "same retention as the session". Under A12, also of 2026-11-10, an output file is copied with the chunks, packs, and grants of [`0131-incremental-checkpoint`](../0131-incremental-checkpoint/change.md). A file the agent produces for the user is copied into the artifact store and offered as a download. Its bytes never travel on stdout, on `CH-ATTACH`, or through the gateway **[design]**.

**The only route to the user (PL O2).** A file reaches the user as an output file only when the runtime emits a `file` part that names it. The platform defines no output directory: §26.2's `/workspace/output/` convention, under which agents "MUST write intended outputs here", and §26.3's statement that files under it "are sealed as session artifacts" are removed, and §24.18's scaffold stops generating the convention, under decision O2 of [`0118-agent-pod-layout`](../0118-agent-pod-layout/decisions.md#open-decisions), which the owner accepted on 2026-11-12. Nothing implemented either rule **[source]**. A runtime may keep its own folder for outputs, and it emits a part for each file in it that it offers. The whole workspace stays downloadable through `GET /v1/sessions/{id}/workspace`, which is a download of the workspace rather than an output file.

**Part.** A `file` part may name a workspace path in place of `inline` or `ref`:

```json
{ "type": "file", "id": "p9", "path": "out/report.parquet", "name": "report.parquet", "mimeType": "application/vnd.apache.parquet" }
```

`path` is relative to `/workspace`, the session's workspace, and is mutually exclusive with `inline` and `ref`. A part that names a path requires an `id`. Part ids are unique per session: the gateway refuses a file part whose `id` the session already used, and the part ends `failed` with the reason `duplicate_part_id`. Small files can still be sent inline under §28.5.3's rules.

**Freeze.** When the adapter reads the part from stdout, it opens the file without following any path a runtime can swap. It translates `path` to a path beneath the slot's `workspace` broker root and opens it through the slot's file-descriptor broker, whose `openat2` resolution with `RESOLVE_BENEATH | RESOLVE_NO_XDEV | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` fails for a path that leaves the root, for a path with a symlink in any component, and for a magic link under `/proc` ([IC-3](../0131-incremental-checkpoint/change.md#ic-3-checkpoint-stream), [SI-5](../0145-session-isolation/change.md#si-5-the-supervisor-file-descriptor-broker)). The broker opens the file as the slot UID and passes the descriptor, which the adapter checks against the pinned device and mount of the broker root. It runs the regular-file check and records the file's identity with `fstat` on the passed descriptor, and it clones, copies, or reads from that descriptor, so the file it checked is the file it copies. A failed open or check ends the part `failed` with the reason `file_not_found`, `outside_workspace`, `symlink_in_path`, or `not_regular_file`. A path through a symlink is refused even when the symlink's target lies inside the workspace, because the adapter cannot tell a safe symlink from one the runtime will swap. The adapter freezes a part when it reads it, whether the part's export starts at once or waits for the export cap ("Copy"), so it holds at most `files.maxQueuedExports` plus `files.maxConcurrentExports` open export descriptors per session, 10 at the defaults. The gateway passes both caps to the adapter with the session's other settings at bind. The adapter's count of open export descriptors is authoritative. The adapter does not open a file part beyond that count and relays it with the member `unopened: true`, an unopened part, and the gateway refuses exactly the parts that carry the marker, with `too_many_exports`, without a count of its own. The adapter sets or removes the member on every file part it relays, so a value the runtime writes has no effect. The adapter closes a part's descriptor and removes its clone or copy when the part's export ends, whatever its outcome, and when it receives `output_failed` for the part, whether or not the gateway ever opened an `ExportOutputFile` stream for it, so a part that fails while it waits for the export cap, for example with `queue_timeout`, frees its place. The adapter then freezes the file's content:

- When the reflink probe of [IC-1](../0131-incremental-checkpoint/change.md#capture) found reflink mode for the slot's workspace volume and the file is at least `reflinkMinBytes` (1 MiB), the adapter clones it with `FICLONE` from the passed descriptor into `/adapter/spool/<n>/export/{adapter_id}` on the spool volume, where `<n>` is the session's slot and `adapter_id` is an id the adapter mints for the export. The clone's name never carries the runtime's part id, so no part id can name a path. A clone shares the file's disk blocks and takes about 1 ms for 2 GiB on the measured nodes, so later writes by the runtime do not reach the copy. When the probe found copy mode, as under gVisor, the adapter copies the file the same way with `copy_file_range` and counts the copy at its full size, under IC's decision D18 of 2026-11-12, which spares the runtime a `file_changed` failure for a file it rewrites during the read: on AWS a copy of 256 MiB took 0.056 s on gVisor's pod-share mount. Export clones and copies count against the spool cap of [IC-7](../0131-incremental-checkpoint/change.md#ic-7-size-limits-and-drain-budgets) and may use at most `exportSpoolFraction` of it, a constant of 0.5, so that a checkpoint's capture pass always has at least half of the spool. The clones and copies of parts waiting for the export cap count against that share as well as those of running exports. A file larger than the remaining export share, 256 MiB at the default `checkpointCaptureBudgetBytes` of 512 MiB, is neither cloned nor copied: the adapter reads it in place with the identity check of the next item (A21). The adapter removes the clone or copy when the export ends, whatever its outcome.
- Otherwise, on a slot volume in read mode or for a file over the remaining export share, the adapter reads the file in place through the passed descriptor and compares the file's identity, the device, inode, size, `mtime` and `ctime` in nanoseconds, and mode of IC's "Change detection", recorded with `fstat` when it opened the file, with `fstat` after the read. A part that waits for the export cap is read when its export starts, so a change in that wait also ends it `failed`. On a difference it ends the part `failed` with the reason `file_changed`, so the runtime can emit it again. It also applies IC's racy rule: when the file's `mtime` falls within `racyWindow` (2 s) before the read would start, an unchanged identity does not prove the content unchanged, so the adapter starts the read only once `racyWindow` has passed since that `mtime`. The check cannot see a write that changes no identity field, such as a write through a memory mapping that the kernel has not yet written back, and the whole-file SHA-256 that `ExportReady` carries is computed from the bytes read, so such a write can reach the stored copy ("Limits"). `FICLONE` works under runc on XFS with `reflink=1` and on Btrfs, and returns `EOPNOTSUPP` under gVisor and Kata on the measured nodes **[source]**. Under gVisor `copy_file_range` works, so gVisor pools copy, and Kata `block-plain` volumes are separate file systems inside the guest, which the probe finds in read mode, so those pools take this path.

**Copy.** The gateway records the part when it reads it from the session's stream ("Export record"), and when the part's export starts it opens an `ExportOutputFile` stream to the adapter on the channel `CH-OUTPUTFILE` ("Channel"). The stream follows the gateway-driven grant and confirm structure of the `Checkpoint` stream ([IC-3](../0131-incremental-checkpoint/change.md#ic-3-checkpoint-stream)) and reuses its pack messages. A session runs at most `files.maxConcurrentExports` exports at once, 2 by default, because the exports of a session share one grant window and gain no upload bandwidth from running in parallel, while each running export holds a quota reservation and a share of the spool. A file part over that cap waits in the session's export queue, which holds at most `files.maxQueuedExports` parts, 8 by default. The adapter's descriptor cap bounds the queue: the gateway refuses with the reason `too_many_exports` exactly the unopened parts of "Freeze", so a runtime cannot hold an unbounded number of open files and clones in the adapter, and the gateway's queue and the adapter's open descriptors cannot disagree. A waiting part stays `streaming`, and the waiting parts start oldest first as the session's exports end.

**Clocks.** Two deadlines bound a file part, and the gateway records the instant each one counts from in the part's `output_file_exports` row ("Export record"). `first_frame_at` is the instant the gateway read the part's first frame from the session's stream, and a part still waiting for the export cap `exportTimeoutSeconds` after it fails with `queue_timeout`. `started_at` is the instant the gateway sent `ExportStart`, and an export that has not reached `ExportReady` `exportTimeoutSeconds` after it fails with `export_timeout`. A part therefore ends within twice `exportTimeoutSeconds` of its first frame. The export's own deadline starts at `ExportStart` rather than at the first frame, so a part that waited for the cap still gets the whole deadline for its copy.

1. `ExportStart` names the session, the part, the path, the effective limit, and `pack_target_bytes`, and the gateway sets the part's row to `exporting` with `started_at`. The effective limit is the smaller of the operator's `files.maxBytes` (default 5 GiB) and the revision's `capabilities.output.maxFileBytes`.
2. The adapter answers `ExportProbe` with the file's size and `estimated_new_bytes`, the bytes of chunks its dedup set does not hold. The gateway refuses a file over the limit with the reason `too_large`, and reserves `estimated_new_bytes` against the tenant's storage quota with §11.2's atomic reservation, as a checkpoint reserves its estimate ([IC-4](../0131-incremental-checkpoint/change.md#quota)), recording it as `reserved_bytes` on the part's row, or refuses with `quota_exceeded`. The pod's estimate does not bound what the export can write: the gateway applies §11.2's signing-time headroom check to each grant of the export, and refuses to sign a grant whose length would carry the export's granted total past its reservation plus the tenant's remaining headroom, so an adapter that reports zero new bytes still cannot exceed the quota.
3. The adapter splits the frozen file into chunks with the content-defined chunking of [IC-2](../0131-incremental-checkpoint/change.md#ic-2-storage-format): a minimum of 256 KiB, an average of 1 MiB, and a maximum of 4 MiB, each named by the SHA-256 of its bytes and compressed with zstd unless compression saves less than 3%. It skips every chunk its dedup set holds, and it checks each chunk against the dedup set when it packs the chunk, so a chunk that a checkpoint confirmed while the export ran, the seal's included, is referenced rather than uploaded. The dedup set is the one a checkpoint uses: chunks of the session's retained snapshots, of the snapshot it started from, of its unreferenced packs under lease, and of its earlier output files ("Retention"). A chunk enters the dedup set only after the gateway has confirmed its pack with `PackCommitted`, so a checkpoint never references a chunk of an export whose pack upload is still in flight, and the reverse. `Resume` and `CheckpointStart` carry the session's output-file chunk lists and its leased packs, so the dedup set of a new pod includes them. A file that a checkpoint already captured therefore uploads only the chunks that changed since that checkpoint.
4. The adapter packs the new chunks into packs with a 16 MiB target and the 32 MiB `packMaxBytes` bound, writes a random 128-bit nonce into each pack's footer, as it does for a checkpoint's packs ([IC-2](../0131-incremental-checkpoint/change.md#packs)), and declares each with `PackReady` (`pack_id`, `length`, and `content_md5`). The nonce makes every pack the adapter builds distinct, so no two packs share a pack ID (A18). The gateway first checks the declared length: a length of zero ends the export with the reason `pack_empty`, and a length over `packMaxBytes` with `pack_too_large`, and nothing is signed. It then resolves the pack ID against the session's own object key, `(tenant_id, owner_session_id, pack_id)`:
   - When the catalog holds that key and the pack is in the session's allowed set, the gateway answers "already stored", with the message `PackStored`, and the adapter skips that upload and references the pack. This is the resend of a pack the adapter built, after a `PackCommitted` that the stream lost, because the adapter resends the pack with the same nonce.
   - When the catalog holds that key in any other state, a soft-deleted row included, the gateway signs nothing and ends the export with the reason `pack_key_held`, as S1 states. A soft-deleted row keeps its key until the tombstone sweep removes it, so the key stays held for that time.
   - When the catalog holds no row for that key, the gateway checks the packs in the session's allowed set that another session owns, which are the packs of a derived session's starting snapshot. A match is answered `PackStored`, and the session's reference names that pack's owner. These keys are consulted for the "already stored" answer only and never lead to a grant.
   - Any other pack is answered `PackGrant`, a single-key `PUT` grant for `/{tenant_id}/checkpoints/{session_id}/packs/{pack_id}` that signs `Content-Length`, `Content-MD5`, and the server-side encryption headers of [§13.2.3](../../spec/13_security-model.md#1323-checkpoint-capability-model).

   The answers reveal nothing outside the session's own keys and its allowed set, which the session may already read.
5. The adapter uploads each pack and sends `PackCommitted`. The gateway checks the object's length with `StatObject` and records the pack as a checkpoint records one, in state `unreferenced` with a lease, and adds its bytes to `confirmed_bytes` on the part's row in the same transaction. Its charge draws down the export's reservation and does not add to it.
6. The adapter sends `ExportReady` with the file's chunk list, each chunk's offset and length in the file and its pack ID, the referenced pack IDs, and the SHA-256 of the whole file. The gateway treats this metadata as untrusted. It checks that the chunk offsets are contiguous from 0, that each chunk's length is at most the 4 MiB maximum chunk and matches the length the pack's footer lists for that chunk, and that the lengths sum to the size from `ExportProbe`, which is within the effective limit. These checks catch a missing or overlapping chunk. It runs the reference closure check of [IC-4](../0131-incremental-checkpoint/change.md#reference-closure). A closure failure answers `ReferenceRefused` with the offending pack IDs, and the adapter evicts their chunks from its dedup set, uploads the chunks again in new packs, and sends `ExportReady` again. The gateway then writes the `output_files` row, which records for each chunk its pack ID and its offset within the pack and records the whole-file SHA-256, its `output_file_packs` references, and the state `ready` on the part's row in one transaction. It releases the rest of the reservation by the guarded update of "Export record", sets `ref` to the file's `lenny-blob://` URI and `sha256` to the whole-file SHA-256, releases the part to `PostAgentOutput` as complete, and closes the stream.

A failed stream leaves the confirmed packs under lease. A retry of the export reuses their chunks, because the retry's dedup set holds the chunks of the session's confirmed packs under lease, as a failed checkpoint attempt's chunks are reused (R3 of that design). The adapter never rebuilds a pack to reuse it: the chunks a retry has to upload again go into new packs, with new nonces, new pack IDs, and new grants. The part ends `failed` with the reason the stream carried.

**Refusals.** The gateway ends a failing export with `ExportAbort`, which carries the reason, in place of the `CheckpointAbort` of the `Checkpoint` stream. The reasons it sends on the stream are `too_large`, `quota_exceeded`, `pack_empty`, `pack_too_large`, `pack_key_held`, `export_timeout`, `seal_timeout`, and `pod_evicted`. The adapter answers `ExportAbort` by removing the clone and closing the stream, and the part ends `failed` with the same reason. A `PostAgentOutput` `REJECT` and the scanner's hash mismatch of "Turn close and interceptors" come after step 6 has closed the stream, so they reach the adapter only as the `output_failed` frame, with the reasons `rejected` and `digest_mismatch`.

**Export record.** The gateway records each file part in `output_file_exports` when it reads the part from the session's stream. The table is keyed by `(session_id, part_id)` and holds `tenant_id`, `state` (`queued`, `exporting`, `ready`, or `failed`), `first_frame_at`, `started_at`, `reserved_bytes`, `confirmed_bytes`, `reservation_released_at`, `coordination_generation`, the generation of the coordinator that drives the export, `failure_reason`, and `notice_acked_at`. The reservation follows §11.2 as a checkpoint's does. Step 2 takes it with the atomic Redis increment and records `reserved_bytes`. Every party that ends the export, the success and failure arms, a new coordinator, and the §12.5 backstop for a row of a terminal session, releases it with one guarded `UPDATE ... SET reservation_released_at = now() WHERE session_id = $1 AND part_id = $2 AND coordination_generation = $3 AND reservation_released_at IS NULL`, and applies the counter decrement, `reserved_bytes − confirmed_bytes`, only when that update changed the row (**Reservation release is exactly-once and guarded.**). The generation guard applies to every release and every state transition of the row: each update carries `AND coordination_generation = $gen`, where `$gen` is the writing coordinator's own generation, or for the backstop the generation it read from the row, so a coordinator that a handoff replaced changes no row and releases no reservation (MDR-34). `Rehydrate` adds `reserved_bytes − confirmed_bytes` over the rows whose `reservation_released_at` is null, so a rebuilt counter still holds every outstanding export reservation (**The relative decrement is rebuild-safe.**). A new coordinator reads the session's rows after the pod acknowledges its fence. It takes over each unreleased reservation by writing its own generation to the row with an update guarded by `coordination_generation < $gen`, without reserving again, reopens `ExportOutputFile` for each `exporting` row, keeps each `queued` row waiting, and applies `exportTimeoutSeconds` from `started_at` and from `first_frame_at` as "Clocks" states. A stream that the adapter cancels when it acknowledges the new coordinator's fence is not a failure for the previous coordinator: that coordinator stops the stream without releasing the reservation, changing the row, or sending `output_failed`, and the new coordinator carries the export on. A row lives as long as the session's other records.

**Turn close and interceptors.** A file part whose export is in progress is exempt from the rule of "MD-16" that a streaming part open at turn close ends `failed`, and a part that waits for the export cap counts as exporting for that exemption. It ends by the export's own outcome, or at a deadline of "Clocks". On a session whose interceptor chain has no `PostAgentOutput` interceptor, clients see the part until step 6 with `status: "streaming"` and its `name`, `mimeType`, and `sizeBytes`. On a session whose chain has one, clients receive nothing about the part, neither a placeholder nor its name or size, until the interceptor answers, so MDR-21 holds. Later frames are not held behind the export, and the part keeps the position of its first frame. A `REJECT` from `PostAgentOutput`, which may read the file through `ref` to scan it, withholds the part with the reason `rejected` and deletes the `output_files` row, after `EnsureCopied` when a hold covers the session ("Retention"), and pack reclamation removes any pack that nothing else references. When the scanner reads the whole file through `ref`, the gateway hashes the bytes it serves and compares the result with the whole-file SHA-256 that `ExportReady` carried. On a mismatch it refuses the part at the `PostAgentOutput` stage as a `REJECT`, with the reason `digest_mismatch`, and the deletion that follows a `REJECT` runs. This is the only place the gateway compares the whole-file hash, because it is the only read of the whole file that precedes release (A20).

**Deadlines.** `exportTimeoutSeconds` is a pool setting, 900 seconds by default, counted from `ExportStart` ("Clocks"). At the default 5 GiB limit it allows an average of about 5.7 MiB/s from `ExportStart` to `ExportReady`, which is about a fifth of the slowest whole-workspace rate the checkpoint benchmarks measured, 5.9 GiB in 208 s on 2 CPUs under gVisor, and it bounds how long a failed export can hold a quota reservation and a spool clone. When it passes, the gateway fails the part with the reason `export_timeout`, releases the export's unused reservation, and sends `ExportAbort`, and the adapter removes the clone. A confirmed pack is kept under its pack lease, `packLeaseSeconds`, a gateway setting of 1800 seconds by default ([IC-4](../0131-incremental-checkpoint/change.md#catalog)). Pool admission refuses a pool unless `packLeaseSeconds` is at least twice the larger of `checkpointAttemptTimeoutSeconds` and `exportTimeoutSeconds`, so a retry that runs a whole deadline after a timed-out attempt or export still finds the packs that attempt confirmed. The lease is extended each time an `ExportReady`, a `SnapshotReady`, or an "already stored" answer references the pack, so a pack a retry is about to reference does not expire under it.

**Seal window (A19, A23).** `maxWorkspaceSealDurationSeconds` is the pool setting of §7.1, and under A19 it is also a runtime field, versioned and gateway-read under RV-1. A session's effective value is its seal window, resolved in this order: the value in the session's revision, then the value on its pool, then the gateway flag `--workspace-seal-max-duration-seconds` (300 seconds by default), each at most the seal window ceiling. The pool value is a field of the pool record that the admin pool API writes, checked by `validatePoolForStore` in `pkg/gateway/externalapi/admin/pools.go` and by the bootstrap pool validation in `bootstrap.go`, and it is mirrored wherever the gateway reads the pool record. A tenant-derived runtime's owned pool copies it from its template pool under "Template copy" of [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md), because it is not a pool setting a tenant may write; the tenant sets the runtime field instead. The chart value `gateway.workspaceSealMaxDurationCeilingSeconds`, the seal window ceiling, bounds both: pool admission refuses a pool, and a runtime write refuses a runtime, whose value exceeds it. The chart renders the ceiling as the gateway flag `--workspace-seal-max-duration-ceiling-seconds` (`LENNY_WORKSPACE_SEAL_MAX_DURATION_CEILING_SECONDS`), because the gateway runs both pool admission and runtime writes, and the gateway refuses at startup a `--workspace-seal-max-duration-seconds` above it. A runtime write also refuses a value that is not greater than `delegation.usageQuiescenceTimeoutSeconds`, the rule §8.3 **Return on completion** states for a pool's value, because the runtime's value replaces the pool's in the terminal pipeline that rule protects. A tenant-derived runtime may set the field within the same bounds. The ceiling defaults to 600 seconds, twice the default seal window, so a runtime whose workspace or exports need more time can double the seal's retry window, and at 600 seconds the computed claim orphan timeout below stays at today's 900 seconds. A session's terminal pipeline budget is its own seal window plus the release allowance of 30 s, and the bound a deployment check reads is the ceiling plus the allowance, 630 seconds at the defaults. The readers of the window follow from that split. The seal's retry window, the terminal context of the pipeline, and the post-terminal window of §7.1 **Post-terminal window:** rule 1, which the session store caps, take the session's own budget. The `CH-ATTACH` stream-failure report, whose bound the gateway sets before it reads the session, and the shutdown wait of §10.1 **Terminal pipelines at process exit.**, which covers sessions with different windows, take the ceiling plus the allowance. `sessionserver.TerminalPipelineBudgetFor` keeps its signature, and its callers pass the window that applies.

**Post-terminal deadline (A22).** §7.1 **Post-terminal window:** rule 1 caps a session's post-terminal window at its own terminal pipeline budget, and a session's budget depends on its seal window, so one store-wide cap cannot be exact. The gateway's terminal write, which sets `terminated_at`, also sets `post_terminal_until` on the session row to `terminated_at` plus the session's terminal pipeline budget, computed from the session's effective seal window, which the gateway reads from the session's revision and pool. §7.1 **Gateway-owned terminal writes:** makes the gateway the only writer of a terminal state, so every terminal row carries the column. `InPostTerminalWindow` and `HoldsPod` (`pkg/gateway/session/sessionstore/terminal_mark.go`), the Postgres store's slot queries, and the retention collector (`pkg/gateway/storage/retentiongc`) compare the time against `post_terminal_until` in place of `terminated_at` plus a cap, so the store option `WithPostTerminalCap` and the collector option `PostTerminalCap` are removed. A terminal row that names a pod and records no release and no `post_terminal_until` counts as holding its pod, because a window held too long only delays the pod's reuse, while a window ended too early frees a pod whose seal or export may still read its workspace. The window still ends at once when the gateway records the release, as rule 1 states. The platform has no deployments, so no existing row needs a value.

**Pool admission and the `claimOrphanTimeout` bound (A23).** §5.2 **Slot assignment atomicity** says that pool admission refuses a pool whose configuration does not meet the `claimOrphanTimeout` bound, and no window that bound reads is a pool field in the tree (F-5.2.57). Under this design the bound reads the seal window ceiling: pool admission refuses a pool whose `maxWorkspaceSealDurationSeconds` exceeds the ceiling, and the gateway's startup check, or the chart's computed default, makes `claimOrphanTimeout` and the stale-slot terminal age exceed the ceiling plus the release allowance by at least one second. Every admitted pool therefore meets the bound. The other windows the bound guards, the launch window of `maxFinalizingTimeoutSeconds` and the `resuming` watchdog, stay gateway flags that the startup check already reads. The §5.2 sentence is rewritten to state that pool admission refuses a pool whose seal window exceeds the ceiling, which is how a pool meets the bound, in place of a pool-admission check with no input. Proposal MD-D lands this rewrite and the pool field and closes F-5.2.57.

The windows that §5.2 **Slot assignment atomicity** guards are the launch, which `maxFinalizingTimeoutSeconds` bounds (600 s by default), a restore in `resuming`, which the `resuming` watchdog bounds (300 s), and the terminal pipeline, whose bound the chart takes as the ceiling plus 30 s. When the operator does not set `controller.claimOrphanTimeoutSeconds`, the chart renders into the controller's `--claim-orphan-timeout` and the gateway's `--slot-reaper-terminal-age` the larger of 900 seconds and one second more than the largest of those windows, rounded up to a whole minute. At the default ceiling that is 631 seconds rounded to 660, so the default stays 900 seconds, and a ceiling of 900 seconds gives 960 seconds. The chart computes from the defaults of the finalizing and `resuming` deadlines, which it does not render, so the gateway's startup check `validateSlotReaperFlags` still verifies the terminal age it runs with, an explicitly set value included, against the deadlines in effect and the ceiling plus the release allowance, and the chart still fails to render an explicit value below that floor.

**Export lifecycle (A15, A19).** An export, or a part that waits for the export cap, ends in these cases besides its own outcome:

- **Seal (A19).** At session end the seal checkpoint runs first. On a pod with several slots it waits in the pod's checkpoint queue while another slot's attempt runs, and that wait counts against the seal window ([IC-1](../0131-incremental-checkpoint/change.md#staggering-across-slots), "Staggering across slots"; IC-5, "Seal"). It and the session's exports share one window, the session's seal window, counted from the start of the seal, which keeps its meaning as the retry window for object-store failures of the seal export. The gateway signs no export grant while the seal checkpoint runs, so the checkpoint has the whole grant window, as on a drain. The seal checkpoint captures the workspace, which holds every exported file, and the seal and the exports share one dedup set, so the seal uploads an exported file's chunks once, and an export that continues after it references the chunks the seal confirmed at step 3 and finishes its bookkeeping. Exports still running, and parts still waiting for the export cap, when the seal checkpoint ends finish in the time the seal leaves in the window, and waiting parts start as running exports end. Under an effective `checkpointPolicy` of `none`, which takes no seal snapshot, the exports get the whole window. When the window ends, each part still exporting or waiting fails with `seal_timeout`. The terminal pipeline budget stays the seal window plus the release allowance of 30 s, as §7.1 states it, because the exports end inside the seal window. These cases upload an exported file's bytes apart from the seal:
  - A file that the runtime changed or deleted after it emitted the part is exported from its clone. The clone's chunks are not in the seal snapshot, which captured the file's later content or no file, so they upload separately.
  - An export pack whose grant is outstanding when the seal starts is not yet confirmed, so its chunks are outside the dedup set and the seal may upload them again. The gateway signs no export grant while the seal checkpoint runs, so at most one grant window of packs, 128 MiB at the default window, is uploaded twice.
  - Under an effective `checkpointPolicy` of `none`, no seal snapshot stores any chunk, so each export uploads every chunk its dedup set does not hold.
- **Drain.** On a preStop drain of the agent pod, the eviction checkpoint runs first, within `evictionCheckpointCapSeconds`, and the eviction checkpoints of a pod's slots run one after another in the pod's checkpoint queue, which the agent-pod grace floor and the gateway's waits size by the slot count (IC-7, "Drain caps"), and the gateway signs no export grant while it runs, so the checkpoint has the whole grant window. Exports then continue only with the budget the checkpoint leaves in the drain's checkpoint stage. An `ExportOutputFile` stream never uses the stream-drain stage of §10.1.7: an export still running when the checkpoint stage ends fails with `pod_evicted`, and so does each part still waiting for the export cap at that point. A gateway replica's own preStop drain does not wait for its export streams, which the session's next coordinator reopens.
- **Idle clock.** An export in progress, and a part that waits for the export cap, count as qualifying activity for the idle clock of the lifecycle design's "SL-6", as activity does under "MD-15", so a session does not become `dormant` while one of its files is being copied.
- **Suspension.** A suspension through `POST /v1/sessions/{id}/suspend` that holds the pod does not end the session's exports. The session moves to `suspended` or `blocked` under the lifecycle design's "SL-4", and the exports continue on the held pod under their own deadlines, because an export is the adapter's work rather than the runtime's. When the hold of `maxSuspendedPodHoldSeconds` ends, each part still waiting for the export cap fails with `suspend_hold_expired`, and the gateway starts no further export. It releases the pod only after the exports already started end. Each of them started before the hold ended and fails at `exportTimeoutSeconds` from its `ExportStart`, so the release comes at most `exportTimeoutSeconds` after the hold ends, 900 seconds at the default. A suspension that releases the pod at once, because the runtime does not declare `interrupt` or did not acknowledge it ("SL-3"), ends every export of the session with `suspend_hold_expired`, waiting and running alike, so the release is not delayed. A failure while the session is paused reaches the runtime after the resume ("Failure notice").
- **Coordinator handoff.** When the pod acknowledges the new coordinator's fence, the adapter cancels the session's open `Checkpoint` and `ExportOutputFile` streams of the previous generation ("Grant window"). The cancellation is not a failure for the previous coordinator, which stops each such stream without releasing its reservation, changing its row, or sending `output_failed`, and its own updates no longer match the row's generation ("Export record"). The new coordinator then takes over the session's `output_file_exports` rows ("Export record") and reopens `ExportOutputFile` for each part that is still exporting. The adapter reuses its clone and its confirmed packs, and the export continues from step 2 without a second reservation. When the clone is gone, the part fails with `clone_lost`.
- **Pod loss.** The part fails with `pod_lost`, and the gateway releases the export's unused reservation.

Every terminal outcome settles the reservation exactly once by the guarded update of "Export record": success settles it at step 6, and a failure, a timeout, a `REJECT`, and a pod loss release what the confirmed packs did not draw down.

**Failure notice (A15).** When a file part fails, the gateway sets the part's row to `failed` with `failure_reason`, emits the session event `output_failed`, and sends the frame `output_failed` on `CH-ATTACH`, which the adapter writes to the runtime as it writes every envelope the gateway sends:

```json
{ "type": "output_failed", "id": "p9", "reason": "file_changed" }
```

The runtime acknowledges the notice with the frame `output_failed_ack`, which the runtime SDKs write after `OnOutputFailed` returns ("MD-12"), and the adapter relays it to the gateway as a session-scoped frame:

```json
{ "type": "output_failed_ack", "id": "p9" }
```

The gateway records the acknowledgement as `notice_acked_at` on the part's row. A notice without an acknowledgement stays on the row, and the gateway sends the frame again after each resume of the session and after a coordinator handoff, until the runtime acknowledges it or the session reaches a terminal state, so a failure that a pod loss or a suspension cut off reaches the restored runtime. A runtime receives no frame after the session's terminal transition, so a part that fails at the seal reaches clients through the event alone.

| Kind | Payload | Fires when |
| :-- | :-- | :-- |
| `output_failed` | `{ "partId", "partType": "file", "reason", "turn"? }` | A file part ends `failed`. The part's own `output` entry also ends `failed` with the same reason. |

The reasons are `duplicate_part_id`, `too_many_exports`, `file_not_found`, `outside_workspace`, `symlink_in_path`, `not_regular_file`, `file_changed`, `too_large`, `quota_exceeded`, `pack_empty`, `pack_too_large`, `pack_key_held`, `queue_timeout`, `export_timeout`, `seal_timeout`, `pod_evicted`, `suspend_hold_expired`, `clone_lost`, `pod_lost`, `rejected`, `digest_mismatch`, and the reason a failed stream carried. A runtime that receives the frame can emit the file again as a new part with a new `id`. On a session with a `PostAgentOutput` interceptor, the event reaches clients only for a part the interceptor has already answered, because clients have received nothing about an earlier one.

**Channel.** `ExportOutputFile` is a new conversation on `LNK-POD-GRPC`, the gateway's gRPC link to the adapter, so it takes its own channel under the specification's naming law: `CH-OUTPUTFILE`, a mnemonic for the output-file copy, which shares no stem with `CH-CHECKPOINT` or any other channel on the gateway-to-pod boundary and uses neither reserved word. Its register row in §28.3 names `LNK-POD-GRPC`, the `gateway-to-pod` boundary, the state plane, the gateway as dialler, authority on both sides, gRPC, and the vocabulary "Output-file copy to object storage". Its contract card states generation fencing as the other fenced gateway-to-pod channels do: the pod rejects a stream that carries a generation other than the one it holds for the session, cancels the session's open stream of the previous generation when it acknowledges a new coordinator's fence, and the new coordinator completes the handoff protocol before it reopens one. An export takes no pod-wide operation lock, so the `CH-OBJSTORE` row in §28.5.5 and §28's statement that the operation lock bounds the transfer `CH-OBJSTORE` carries change to name the export transfer as one the lock does not bound. A claim-register row with status `ABSENT` records the channel until the code lands.

**Grant window (A12, A13, A14, A17).** The gateway counts the outstanding pack grants of a session across its `Checkpoint` and `ExportOutputFile` streams against one window, the pool's effective `checkpointGrantWindow`: the per-pool override `PodSet.checkpointGrantWindow` when set, at most 8, and otherwise the gateway's default of 4. The gateway refuses at startup a `--checkpoint-grant-window` (`LENNY_CHECKPOINT_GRANT_WINDOW`) above 8, as admission refuses a pool override above 8, so the default window cannot exceed the bound either. The counter lives on the session's coordinating replica. On a coordinator handoff, the new coordinator cannot see which grants the previous one signed, and the pod accepts the previous coordinator's RPCs until it acknowledges the new coordinator's fence (§10.1.2, step 2). The new coordinator therefore counts the session's whole window as outstanding until the grant TTL, `checkpointCapabilityTTLSeconds` (30 s), has passed since the pod acknowledged the fence. When the adapter acknowledges the fence, it cancels the session's open `Checkpoint` and `ExportOutputFile` streams of the previous generation, so the previous coordinator signs no grant after the acknowledgement, and every grant it signed before expires within that count. A compromised pod can therefore write at most the pool's effective window times `packMaxBytes` of chosen bytes at once, 128 MiB by default and at most 256 MiB, which is the bound of S5. Today's bound is `checkpointGrantWindow × partialChunkSizeBytes`, 4 × 16 MiB, so the pack format doubles it by default. The bound limits a burst of chosen bytes in the session's own prefix, which the tenant's quota pays for and garbage collection reclaims. An export slows the pre-copy and upload passes of a concurrent checkpoint of the same session, which share the window. During a checkpoint's capture pass the adapter pauses export reading, hashing, and compression, so an export does not compete with the capture for disk and CPU while a runtime that declares `checkpoint` is quiesced, and uploads of packs the export already built continue. The export takes no quiesce and no pod-wide operation lock.

**Size (A11b).** The default of 5 GiB is a policy limit. No single upload approaches the object store's 5 GiB limit for one `PUT`, because every pack is at most 32 MiB. The tenant's quota and the pool's `workspaceSizeLimitBytes`, which already bounds the file inside the workspace, also apply. `capabilities.output.maxFileBytes` is versioned and gateway-read under RV-1, and it can only lower the operator's limit.

**Download.** The gateway renders an output file from its chunk list and packs with its own object-store credentials, as [IC-5](../0131-incremental-checkpoint/change.md#download) renders the workspace download, and verifies the SHA-256 of each chunk as a restore does (S4). `GET /v1/blobs/{ref}` serves it with the file's `mimeType` and accepts a `Range` header, which the row's chunk offsets and pack offsets resolve to the byte ranges of the packs that hold the range, so an interrupted download resumes. S4's check of every chunk it serves is the storage-integrity guarantee: a corrupt or substituted pack fails the read of the chunk it holds (A20). The whole-file SHA-256 that `ExportReady` carried is metadata. The gateway publishes it as `sha256` on the released file part and in a `Repr-Digest` header (RFC 9530) on every response of `GET /v1/blobs/{ref}`, as `Repr-Digest: sha-256=:<base64 digest>:`, so a client can verify its download end to end. `Repr-Digest` describes the full representation whatever its content coding and range, so a `206` response to a `Range` request carries the same value and a client that assembled ranges can still verify the file. `Content-Digest` describes the bytes of each response's content, which for a `206` response is the range alone, so it does not fit. The gateway itself compares the hash only on the scanner's read of "Turn close and interceptors". The whole-file hash cannot detect a compromised pod, which writes both the chunk list and the hash, and the `ExportReady` checks catch missing or overlapping chunks. An adapter that orders chunks wrongly is caught by the tier 1 and tier 10 tests. `GET /v1/sessions/{id}/artifacts` lists the file. "MD-21" states the other surfaces.

**Retention (A11c, A16).** The `lenny-blob://` URI of an output file takes the session's retention as its `ttl`, in place of the 1-hour live-delivery default of §28.5.3. The `output_files` row lives for the session's retention, and its `output_file_packs` references keep its packs alive: pack reclamation ([IC-6](../0131-incremental-checkpoint/change.md#ic-6-retention-garbage-collection-erasure-and-legal-hold)) counts them beside `checkpoint_snapshot_packs`, so a pack that a rotated snapshot shared with an output file stays. Erasure under §12.8 deletes the file's row, and a legal hold on the session keeps it. Under A16, a security hold whose `include` lists `artifacts` covers output files under FE-3, and it copies an output file's packs and its `output_files` row to escrow, as IC-6 copies a held snapshot's packs. The §12.8 legal-hold escrow handles a pack-backed item, a snapshot or an output file, the same way: it copies every pack the item references and the item's row. Every path that deletes an `output_files` row, the deletion after a `REJECT` included, calls `EnsureCopied` first, and the refusal for `digest_mismatch` takes the `REJECT` path.

**Security model.** §13's "File delivery" row names checkpoint chunk objects as the exception to gateway-mediated delivery. The packs of output files are checkpoint packs under the same capability model: keys under the session's own pack prefix, the `PUT` method alone, a signed `Content-Length` and `Content-MD5` of at most `packMaxBytes`, a short expiry, and no `LIST`, `DELETE`, or multipart capability (R5 of that design). The pod holds no object-store credential, and naming a chunk hash grants no read (R6).

**Performance.** The incremental checkpoint design's benchmarks bear on exports **[source]**:

- Reading dominates on sandboxed and microvm pools. A 4 KiB file costs 5 to 13 µs to read under runc and on a Kata block volume, and 46 to 129 µs under gVisor and on Kata's shared file system. A large file is read sequentially, and its export time is then set by the hashing and compression CPU and the upload bandwidth, which those benchmarks did not measure for a single large file ("Validation owed" in `steps.md`).
- The adapter's CPUs matter. With 2 CPUs in place of 4, the first checkpoint of a 5.9 GiB checkout under gVisor took 208 s against 139 s.
- Deployer levers that speed exports as they speed checkpoints: gVisor's pod-share mount hint, which made restore 3.2 times faster, Kata's `virtio_fs_cache = "metadata"`, and a Kata block volume, which measured close to runc.
- Deduplication removes most of the cost of exporting a file that a checkpoint already captured, and a retry after a failure uploads only the chunks that no confirmed pack holds.

**Isolation profiles.** The export works on `standard`, `sandboxed` (gVisor), and `microvm` (Kata) pools, because it uses the reads, the egress policy, and the pack grants that checkpoints use under every isolation profile ([§13.2](../../spec/13_security-model.md#132-network-isolation), NET-071). The reflink clone is limited to runc on a filesystem that supports it, and the copy to pools whose reflink probe finds copy mode, such as gVisor. The freeze opens the file through the slot's file-descriptor broker, whose `openat2` resolution runs in the slot container and was measured under runc and gVisor in the session isolation spikes and under Kata in the AWS runs of 2026-11-12 ([`0145-session-isolation`, "Validation record"](../0145-session-isolation/steps.md#validation-record)).

### MD-19 Harness approvals

The owner settled A4 on 2026-11-10, revision 9 moved its transport onto frames under B7 and B8, and revision 10 merges the frames into one request frame and one reply frame under B-O6. Coding harnesses ask permission before running their own tools, for example Claude Code's `can_use_tool`, Codex's `item/*/requestApproval`, and the Agent Client Protocol's `session/request_permission` **[external]**. Each of these asks the program that hosts the harness and never the model. Lenny's tool-use approval path (SO-5a) covers only tools that Lenny routes **[source]**, so today an adapter has to approve a harness's tools automatically or leave the harness waiting **[design]**.

**Request and reply frames [design, B8, B-O6].** A runtime asks the gateway for a decision with a `request` frame on stdout and receives exactly one `reply` frame on stdin. `kind` names what it asks: `approval`, `question`, or `import_file` ("MD-26"). Both frames carry the session id and a `requestId`. The `requestId` is optional: when a runtime omits it, the adapter assigns one, and the replies to such requests arrive in the order the requests were written. The adapter relays the request on `CH-ATTACH` as a session-scoped frame and writes the reply as it writes every envelope the gateway sends. The runtime waits for the reply off its own frame reader, so it keeps reading messages while it waits. A request whose session ends, or whose pod is lost, receives no reply, and a restored runtime raises it again. A request that waits for its reply counts as activity for the session's idle clock until the reply arrives or the request expires (lifecycle design, "SL-6"). A later request kind reuses the pattern.

**Approval [design, B7].** The runtime writes a request for a harness's permission request:

```json
{ "type": "request", "kind": "approval", "requestId": "ap_3", "toolUseId": "toolu_01A", "tool": "Bash", "input": { "command": "rm -rf build/" }, "title": "Delete the build directory", "reason": "Clean rebuild requested" }
```

The adapter writes back `{ "type": "reply", "requestId": "ap_3", "decision": "approved" | "denied" | "withdrawn", "updatedInput"?, "message"?, "source": "client" | "policy" }`. `updatedInput` carries a client's edit of the input, which the harness applies, as Claude Code's `updatedInput` and AG-UI's `editedArgs` do **[external]**. The frames use `CH-MSGSOCK` alone, so every runtime forwards approvals, and no runtime declaration and no platform tool is involved.

**Who answers (B7, B15).** An approval always goes to a person watching the root of the session's tree, on a child session as on a top-level one, or to the declared unattended policy. A parent session never answers a child's approval and never sees a way to. Approvals reach only people because a pod holds no client credential: a pod authenticates to the gateway with its projected service-account token and never holds a client bearer or a `session_capability` token ([§10.2](../../spec/10_gateway-internals.md#102-authentication)) **[source]**. A Lenny credential that a user or a deployer places in a pod acts as its owner, approvals included, as every other use of that credential does.

**Path (H5).** The gateway emits a `tool_use` event with `target: "harness"` and phase `requested`, approval required, which takes the projection approval-required `tool_use` events take today: MCP `elicitation/create`, and the REST routes `POST /v1/sessions/{id}/tool-use/{toolCallId}/approve` and `.../deny`. For a child, the gateway emits the event on the child's stream and on the root's stream, with `originSessionId` naming the child, and the root's client answers it on the root's routes or on the child's. MCP `elicitation/create` reaches the root's client. The approve route accepts `updatedInput`. The gateway answers when a decision arrives or the approval timeout of SO-5a passes. When a suspension stops the turn first, the gateway withdraws the approval (B21): it emits `tool_use` with the phase `withdrawn`, a later decision on the approve or deny route answers `404 RESOURCE_NOT_FOUND`, and while the pod is held the runtime receives a `reply` with `decision: "withdrawn"`, or, for an approval-gated `tool_call` the gateway holds, an error result that names the withdrawal, as a denial does. The lifecycle design's resume notice names each withdrawn approval ("SL-3").

**Unattended sessions.** The root's session create request takes `harnessApprovals: { "allowTools": [...], "unattended": "deny" | "allow" }`, with a default on the runtime revision. A child takes the root's `harnessApprovals`: no parent sets a child's, so no agent widens the approvals of another (H5). A tool in `allowTools` is approved at once without asking. When no client answers within the approval timeout, the gateway answers with `unattended`, which defaults to `deny`. A withdrawn approval takes no timeout answer and no `unattended` answer (B21). A tenant's policy may narrow both members. Each decision writes the approval audit record SO-5a writes, with `source` and the originating session.

**Boundary.** The harness runs the tool inside the pod, so Lenny relays the decision and cannot enforce it. The sandbox and the egress policy remain the security boundary, and the approval is a user-facing gate.

**Reader.** The approval waits off the session's frame reader, so frames keep flowing while a harness or a Lenny tool waits for approval (MDF-8).

**Harness questions [design, B6].** A harness's structured question to the user, such as Claude Code's AskUserQuestion, and a plan proposed for approval, such as Codex plan mode or Claude Code's ExitPlanMode, are elicitations. The runtime writes a `request` with `kind: "question"`, the message, the requested schema or URL, and `humanRequired`, and receives a `reply` with the answer. The elicitation then follows the §9.2 chain as one from `ask_question` does ("MD-22", **Questions and approvals**). A question pending when a suspension stops the turn is withdrawn, and its `request` receives a `reply` with `outcome: "withdrawn"` while the pod is held (B20).

### MD-21 Surfaces and AG-UI

### MD-22 Parents and children

The owner settled B1 to B6 and B9 on 2026-11-10, and B-O1 to B-O5, B11 to B14, and the fixes of the adversarial review of revision 9 on 2026-11-11 **[design]**. [`0146-session-lifecycle`](../0146-session-lifecycle/change.md) states the states a top-level session and a child share, `running`, `idle`, `dormant`, `suspended`, and `blocked`, with tree suspension, the close rule, `onParentEnd`, and the recovery of child events. This part states the messages between a parent and its children.

**One session model (B1).** A child session behaves as a top-level session in every way, and its parent is its client for messages. A runtime cannot tell whether a person, a program, or a parent session is its client, so one runtime serves at any depth with no change, and a parent can pass a child's question up to its own client on the same path. The delegation lease constrains a child, through its budget, depth, deadline, tool list, and delegation targets. Approvals and human-required elicitations skip the parent ("Questions and approvals").

| A client with a top-level session | A parent with a child |
| :-- | :-- |
| Creates the session with a first message. | `start_child_session` with a `task`. |
| Sends a message with `steer`, `queue`, or `interrupt`. | `message_child_session` with the same intents. |
| Retracts a `pending` message. | The `retract` frame, as for any message the runtime sent ("MD-11"). |
| Reads the outcome of its messages. | A notice for each failed outcome ("Outcomes"). |
| Receives mid-turn messages, ends of turn, and the end of the session. | Child events in its inbox, or the result of `await_child_sessions` ("Child events"). |
| Attaches to the session's event stream. | Its runtime watches the child's event stream ("MD-25"). |
| Downloads the session's files. | Imports the child's files into its workspace ("MD-26"). |
| Suspends and resumes the session. | Neither in v1. Only the root's client suspends and resumes (lifecycle design, "SL-4"). |
| Closes the session, or cancels it. | `close_child_session`, under the close rule (lifecycle design, "SL-7"). |
| Answers an elicitation. | Answers an elicitation that is not human-required, through the §9.2 chain. |

**Messages to the client (B4, B-O6).** Every session can send its client a message in the middle of a turn. The model calls `send_update`, or the runtime writes a `message` frame with `endOfTurn: false`:

```json
{ "type": "message", "id": "m_7", "endOfTurn": false, "parts": [{ "type": "text", "inline": "The schema check passed. Running the migration next." }] }
```

A `message` frame without `endOfTurn` ends the turn, and one with `complete: true` also completes the session ("MD-24"). A mid-turn `message` opens a turn when none is open, as output does ("MD-4"). What a `message` delivers passes `PostAgentOutput` and enters the transcript as output does ("MD-16"), as one entry that carries the message's `id`, and a top-level client receives it on the `output` event with `messageId`. The delivery rules of "MD-24" decide what a `message` delivers, so a child that streamed its answer on `message_part` frames still delivers it. A message to a client never interrupts the client (MDR-38).

**`send_update` ordering (H1).** `send_update` reaches the adapter's platform tool server as a `tool_call` frame, on the runtime connection or on a tool connection of the slot ([RP-3](../0139-runtime-protocol/change.md#rp-3-tool-calls-on-frames)), which is a different path from the runtime's `message` frames. The adapter converts each call into a mid-turn `message` frame on the session's relay, placed after every stdout frame it has read for the session, before it answers the call, and the runtime SDKs flush stdout before they call a platform tool. The update therefore reaches the gateway ahead of the turn's end-of-turn `message`, as a frame written to stdout would (MDR-42).

On a provider surface, a mid-turn message is part of the turn's output, in the order the runtime wrote it. On the Messages API its parts are content blocks of the turn's assistant message, and on Chat Completions and Responses they are content of the turn's response, streamed with the provider's own deltas. The provider APIs have no marker for it, and the surfaces add none.

**Child events (B2).** The gateway turns each of these into a message in the parent's inbox, with `from: { "kind": "agent", "id": <child session id> }` and an `event` member:

| `event` | Source | Content |
| :-- | :-- | :-- |
| `message` | A mid-turn `message` of the child. | What the message delivers ("MD-24"). |
| `end_of_turn` | An end-of-turn `message` of the child that does not complete it, or the gateway's report that a pod loss or the idle clock cut the child's turn. | What the message delivers, and `error` when the turn failed. The gateway writes the event with `error: "turn_lost"` and no parts when a pod loss cut the turn and the restored child was told to continue, and with `error: "idle_timeout"` when the idle clock cut it (lifecycle design, "SL-3" and "SL-6"). The end-of-turn `message` that closes a turn a suspension stopped produces no event. |
| `ended` | The child reached a terminal state that its parent did not cause with `close_child_session`. | `state`, one of `completed`, `failed`, `cancelled`, and `expired`, and the child's `TaskResult`. A completing `message` produces this event alone, with what the message delivers as `TaskResult.output` (M9, MDR-45). It replaces §8.10's `child_failed`. |
| `awaiting_client_action` | The child's retries are exhausted (lifecycle design, "SL-8"). | `recoverable: true` and the failure. The parent closes the child, or resumes it with `message_child_session`. |
| `suspended` and `resumed` | The root's client suspended the child directly, or resumed it (lifecycle design, "SL-4"). | The time of the change. |

A child event takes the parent's default intent, and never `interrupt`. It follows the paths of "MD-5": it is written after the current tool result when the parent's runtime declares `steer` and a turn is open (MDR-5), it waits for the turn's end on any other runtime, and it opens a new turn when the parent is waiting. Each child event is delivered once: as the result of a pending `await_child_sessions` call that covers that child, and otherwise as an inbox message (MDR-37). A child event passes the parent's content policy and interceptors ("MD-9", **Policies on child events**), and the lifecycle design holds it while the parent is paused ("SL-5"). Activity and streamed parts are not child events: the parent's runtime may watch them ("MD-25"), and the root's client sees the tree.

**`await_child_sessions` (B-O1, H3, B16).** The call covers the children it names, or, without a list of names, every non-terminal child of the caller and every child with an unconsumed event, and takes a mode:

- When the call is made, the gateway moves into its result every end-of-turn, `ended`, `awaiting_client_action`, and `suspended` event of a covered child that waits in the parent's inbox unconsumed, oldest first, and those events count as delivered.
- A covered child that is terminal counts as answered, with its state and its `TaskResult` from `session_tree_archive`, whether or not it ever produced an event, a child the parent closed itself included.
- A covered child that is waiting or paused, and has no unconsumed event, counts as answered: its result entry carries the child's state and no content, and the call does not wait for it.
- Otherwise the call waits for each covered child's next end-of-turn, `ended`, `awaiting_client_action`, or `suspended` event. When the root's client suspends a covered child directly while the call waits, the child's `suspended` event answers the call for that child with the state `suspended`. When a covered child ends for any reason while the call waits, whether it completes, is closed or cancelled, fails, or expires, the call returns for it at once with its final state, because the gateway writes the child's terminal entry from the session-tree record whether or not the child replied (B16, MDR-50). A mid-turn `message` event is not a result and reaches the inbox.
- `any` returns at the first covered child with an entry, and `all` once every covered child has one. `settled` stays a synonym of `all`, and it no longer waits for every covered child to reach a terminal state, as §8.8 "TaskResult" defines it today **[source]**.
- An event a pending call returns is not also delivered to the inbox.

Without the third rule, a parent that awaits a waiting child would wait for an event the child sends only after the parent's next message. Without the second and fourth rules, a call would wait for a child that ended without an event, such as one the parent closed itself or one whose event a restore lost, until the parent's own limits ended its turn.

**Rendering (B3).** The runtime renders `from` for its model, so the model can tell its children apart and name one in `message_child_session`, as Claude Code's harness tags each sub-agent notice with the sub-agent's id **[unverified]**. A runtime that renders it declares `capabilities.childSessions: true`, a versioned, gateway-read capability under RV-1. A revision that does not declare it cannot delegate and is offered no delegation tool, under "DA-2" and "DA-4" of [`0126-delegation-availability`](../0126-delegation-availability/change.md#da-4-tool-list) revision 7.

**Asking is replying (B5).** A session that needs an answer ends its turn with its question and stays open, and its client's next message is the answer. `inReplyTo` may correlate it. A top-level client, a parent, and an A2A client see the same thing: a turn that ended with a question, after which the session is `idle`. `lenny/request_input`, the `input_required` sub-state it causes, `maxRequestInputWaitSeconds`, path 1 and path 3 of §7.2, and the subtree deadlock detector leave the specification (lifecycle design, "SL-8"). A question from a harness's own ask tool keeps the elicitation path ("MD-19"). An end-of-turn frame carries no status that marks a question, because no client reads one: the text tells a person or a model what the turn asked.

**Completion (B5, M9).** Today no frame completes a session. §7.2 lists `running → completed (agent finishes)` with no signal, §5.1's `one_shot` ends the task after its single `response`, and the tree moves a session to `completed` only on a terminate (`transitionTerminate` in `pkg/gateway/sessionserver/session_transitions.go`) and in the OpenAI translators after their single turn (`openai_chat.go` and `open_responses.go` in `pkg/gateway/environment/translator`) **[source]**. An end-of-turn `message` with `complete: true` completes the session when the turn closes, and what it delivers is the session's result. The completing frame produces the `ended` child event alone, with no `end_of_turn` event before it, so a parent pays one turn for a child's last answer. A `one_shot` runtime's end-of-turn frame completes the session without the member, as §5.1 states today, and that completion is the rule by which a provider adapter's `one_shot` conversation runs cold on its next request, whose conditional send fails on the terminal session (R16 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md)). Otherwise a session stays open after a turn, `idle` and later `dormant`, until it completes, its client closes or cancels it, or a limit ends it, and the close rule decides the state a close records (lifecycle design, "SL-7").

**Outcomes [design].** A parent receives a notice in its inbox for each failed outcome of its own message, `expired`, `dropped`, or `consumed_unrecorded`, with `from.kind: system`, the message id, and the reason, as a client reads the same outcomes from `message_state`. A `delivered` or `consumed` outcome sends no notice, and the parent's event stream carries it.

**Waking a parent [design].** A child event to a `dormant` parent takes the resume path of "MD-5": it wakes the parent and claims a pod, under the resume admission check (`AdmitResume` in `pkg/gateway/sessionserver/quota.go`) **[source]**. When admission refuses, the event stays `pending` in the parent's DLQ until a later resume and does not expire while the parent lives (MDR-51). The receipt of the frame or call that caused it is `queued` with `reason: "resume_refused"`. A child event to a `suspended` or `blocked` parent is held and wakes nothing (lifecycle design, "SL-5").

**Questions and approvals.**

- **Elicitations (B6, H5).** The §9.2 chain is unchanged: an elicitation from `ask_question` or from a `request` with `kind: "question"` goes to the session's client one hop at a time, and a parent may answer it or pass it on. An elicitation with `humanRequired: true` skips the parent hops: the gateway sends it to the root's client, emits it on the root's event stream with `originSessionId` naming the asking session, no parent can answer or clear the flag, and no per-hop forwarding timeout applies. A URL-mode elicitation, such as a sign-in or a credential prompt, is always human-required. §9.2's deep elicitation suppression, `elicitationDepthPolicy`, its depth-based restrictions, and `maxElicitationWait` apply to a human-required elicitation as to any other, so a child cannot flood the person past its parents (M6). A parent sees that its child waits on an elicitation through `list_child_sessions`. The content integrity rules of §9.2 apply as today. A question pending when a suspension stops the asking session's turn is withdrawn under §9.2 item 6, a later answer is refused with `404 ELICITATION_NOT_FOUND`, and the resume notice names it so the runtime may ask again (B20, lifecycle design "SL-3").
- **Approvals (B7).** A harness approval always goes to a person watching the root, on the root's stream ("MD-19"). An approval pending when a suspension stops the asking session's turn is withdrawn, as a question is (B21, lifecycle design "SL-3").

**Recovery.** After a parent's restore, the gateway resends each `ended` child event the parent consumed after its checkpoint, from `session_tree_archive`, and each `end_of_turn` child event, from the child's transcript, each with its original message id, so the deduplication of "MD-3" drops a resend that the restored runtime already holds (R10-M11). Mid-turn `message` events take the `consumed_unrecorded` notice of "MD-3" (lifecycle design, "SL-12").

### MD-24 Runtime frames and leniency

The owner settled B-O6 and B12 on 2026-11-11 **[design]**. The owner asked to "simplify as much as possibe and use optional parameters where possible", without dropping a capability, so that "conversations shouldn't get stuck just because the runtime did something slightly off".

**Frames.** A minimal runtime reads `message` and writes `message`. Every other frame is optional for it.

| Direction | Frame | Purpose | Optional members and their defaults |
| :-- | :-- | :-- | :-- |
| Runtime to adapter | `message` | Speaks to the session's client. | `endOfTurn`, default `true`. `complete`, default `false`, which implies the end of the turn. `parts`, default under the delivery rules below. `consumed`, default every `delivered` message of the session on an end-of-turn frame and none on a mid-turn frame ("MD-4"). `id`, `inReplyTo`, and `error`. |
| Runtime to adapter | `message_part` | Writes a part of the message being composed into the transcript and onto the event stream, whole or as `append`, `end`, and `reset` operations ("MD-16"). It replaces `output`. | The whole frame. |
| Runtime to adapter | `activity` | Reports what the runtime does ("MD-15"). | The whole frame. |
| Runtime to adapter | `consumed` | Reports consumption during a turn ("MD-4"). | The whole frame, for a runtime that does not declare `steer`. |
| Runtime to adapter | `request` | Asks for a decision, with `kind` `approval`, `question`, or `import_file` ("MD-19", "MD-26"). | `requestId`. |
| Runtime to adapter | `retract`, `output_failed_ack`, `set_tracing_context`, and `watch_child_session` | As "MD-11", "MD-18", §28.5.3, and "MD-25" state. | The whole frame. |
| Adapter to runtime | `message` | A message from the session's client, a child event, or a system message, in the `MessageEnvelope` of §15.4.1. | None. |
| Adapter to runtime | `reply` | Answers a `request`. | None. |
| Adapter to runtime | `retract_result`, `output_failed`, `child_session_event`, and `error` | As "MD-11", "MD-18", "MD-25", and the leniency rules below state. | None. |

`interrupt_request`, `checkpoint_request`, and the other operational frames of today's `CH-RUNTIMEOPS` travel on `CH-MSGSOCK` under RP O7 (a), and [`0139-runtime-protocol`](../0139-runtime-protocol/change.md#rp-1-handshake) states them with its handshake. The handshake is the one exchange every runtime must perform: a first frame other than `hello` is refused, and the leniency rules below do not soften it. The required member is `type` on every frame.

**The session of a frame (RPR-18, AR O5).** Every connection of a slot serves the slot's one session, and a runtime process serves one session over its life ([`0145-session-isolation`](../0145-session-isolation/decisions.md#decisions) D4). The adapter therefore takes a frame's session from the connection that carries it, as RPR-18 of [`0139-runtime-protocol`](../0139-runtime-protocol/change.md#rp-3-tool-calls-on-frames) states, and no frame carries `sessionId` except `session_start`. `session_start` keeps `sessionId` as data the runtime reads, for log and support correlation, for its identity across process restarts, for idempotency keys of actions outside Lenny, and for detecting a derived session, and the adapter never acts on it. A runtime that still writes `sessionId` on another frame is unaffected: the member is unknown and is ignored silently under the leniency rules below. `startId` leaves `session_start` and `session_started`: the adapter writes one `session_start` per runtime process, accepts the first `session_started` after it, and drops any later one with a `runtime_warning`, as [`0119-agent-runtimes-only`, "AR-3"](../0119-agent-runtimes-only/change.md#ar-3-runtime-protocol-frames) states. The owner settled both on 2026-11-13 (C1, and AR O5 (b)).

**One name in each direction.** `message` names the frame in both directions, because a runtime receives messages and sends them. The JSONL schema `schemas/lenny-adapter-jsonl.schema.json` splits into a runtime-to-adapter union and an adapter-to-runtime union, each discriminated on `type`. stdin and stdout are separate streams, so no reader meets both unions on one stream.

**What a `message` delivers (B12).** These rules decide which parts a `message` hands its recipient:

1. A `message` whose `parts` carry content delivers those parts, and each enters the transcript, as the end-of-turn frame's `output` does today.
2. An entry of `parts` that carries only an `id` names a part the session already wrote on a `message_part` frame, and delivers it without writing it twice. An `id` that names no part of the session is ignored with a `runtime_warning`.
3. A `message` with no `parts` delivers every part the session wrote since its previous `message`, without `reasoning_trace` parts (MDR-47).

Rule 3 lets the simplest streaming runtime work unchanged. Rules 1 and 2 let a runtime send its parent only its final answer, as a Claude Code sub-agent returns only its last message **[unverified]**. The adapter's conversion of `send_update` writes a `message` with explicit parts, so a mid-turn update delivers only its own text, and a later `message` with no parts delivers what was written after the update. A client attached on REST sees the streamed parts on the `output` event either way, and the `message` marks the delivery point. What a `message` delivers is what a parent's child event, `TaskResult.output`, and an A2A message carry. A provider-surface response carries the turn's output as "MD-8" states.

**Leniency (B-O6, MDR-46).** The adapter and the gateway keep a conversation moving when a runtime writes something slightly off:

- An unknown member of a known frame is ignored silently, with no event. An unknown frame type is ignored, and the gateway emits a `runtime_warning` event on the session's stream with the frame type, at most once per type per session.
- A missing optional member takes the default of the table above.
- A malformed frame, one that is not valid JSON or lacks a required member, is answered with an `error` frame to the runtime that names the problem and the frame's `type` when it has one. Only that frame is dropped, the session continues, and the gateway emits `runtime_warning`.
- A line longer than the adapter's line limit is refused alone: the adapter discards the line up to its newline, writes an `error` frame with `line_too_long`, and keeps reading the connection, so the session continues (MDF-10).
- The adapter and the gateway refuse a frame only to keep isolation or another session safe: a frame whose `childSessionId` names a session that is not a direct child of the frame's session, a file part whose path leaves the workspace, or a request the session's lease forbids. Such a refusal answers with an `error` frame or the operation's own refusal, and counts on `lenny_runtime_frame_refused_total{reason}`.
- A runtime ignores an adapter-to-runtime frame of a type it does not know, such as `error`, `reply`, `child_session_event`, or `output_failed` for a runtime that uses none of them, and keeps reading. A runtime that wrote every stdin line to its model as a message would otherwise answer an `error` frame. The runtime SDKs ignore such frames, and the conformance suite of §15.4.6 has a case for it (MDR-53).
- An unknown value of a known enum member is handled as `other` and is never an error, in both directions (MDR-57). The owner settled this on 2026-11-15 ("2.2: ok"). A runtime that reads a child event whose `event` it does not know, an `ended` event whose `state` it does not know, a `tool_result` content block whose `type` it does not know, an `error.code` it does not know on a `tool_result` or an `error` frame, or a `retract_result` value it does not know, handles the value as the member's generic case: it shows a child event by its sender and its parts, keeps a content block it cannot render as opaque content, and treats an unknown code as a failure described by the frame's `message`. It never answers such a frame with an error and never stops reading. The adapter and the gateway apply the same rule to a runtime's frame where a member's value describes rather than selects what they do, such as an activity's `toolKind` or a `notice`'s `severity`: the value is carried as `other`, and the frame is not refused. A value that selects what the adapter does, such as a `request`'s `kind` or a `message_part`'s operation, names an action the adapter cannot take, so that frame is malformed and the rule above answers it with an `error` frame while the session continues. The runtime SDKs expose an unknown value as `other` with the value it carried beside it, so a runtime can log it, and the conformance suite of §15.4.6 has cases for it ("RP-8" of [`0139-runtime-protocol`](../0139-runtime-protocol/change.md#rp-8-conformance-by-capability)). An added value of an enum member therefore keeps the protocol version, as "RP-7" of that design states.

### MD-25 Watching a child's stream

The owner settled B13 on 2026-11-11 **[design]**. The owner asked "could we stream everything to the parent and let it decide how to handle? ... it would create more parity between parent sessions and root clients". Claude Code's harness receives a sub-agent's whole stream, which is how it shows the sub-agent's progress, and its model sees only the result **[unverified]**, so the parity is between the root's client and the parent's runtime.

**Frames.** The parent's runtime writes `{ "type": "watch_child_session", "childSessionId": <child>, "fromSeq": <n> }`, with `fromSeq` optional, to start watching a child, and the same frame with `"stop": true` to stop. The adapter then writes each event of the child's stream to the runtime as `{ "type": "child_session_event", "childSessionId": <child>, "seq": <n>, "event": <SessionEvent> }`, in the child's order.

**What the runtime receives.** The events a client attached to the child receives: `output` with streamed parts, `activity`, `turn_start`, `turn_end`, `usage`, `tool_use`, and `message_state`, after the child's `PostAgentOutput` and `PostAgentActivity` interceptors, with the activity snapshot on attach that "MD-15" gives a client. Before the adapter writes a watched `output` event, the gateway runs the parent's `contentPolicy` and `PreMessageDelivery` interceptors on its completed parts, as on a child event's, and when the parent's policy names an interceptor it holds a streaming part's deltas until the part completes, as MDR-21 holds them for a client. A part the interceptors reject reaches the parent's runtime as a notice that names the rejection. A watch across environments therefore meets the receiving environment's rules, as a child event does ("MD-9", MDR-52). A watched event is not a child event: it opens no turn, takes no inbox state, and reaches no model unless the runtime passes it on. Child events still arrive as messages, and `await_child_sessions` still returns them.

**Scope.** A runtime watches only its own direct children (MDR-48). A `watch_child_session` for any other session is answered with an `error` frame that reveals nothing about it. A watch ends when the child ends or the parent's process ends. A restored parent watches again from its last `seq`, and when the child's replay buffer no longer holds that sequence, the adapter writes `gap_detected` in a `child_session_event` and continues, as §7.2 does for a client.

**Cost.** Each watched child's deltas cross the parent's pod connection, which is why the watch is opt-in per child.

**No tool.** The harness, which hosts the model, decides what its model sees, so the operation is a frame (B8).

### MD-26 Files from a child

The owner settled B14 on 2026-11-11 **[design]**: "we need to make sure child sessions can send back files to parents, including large files". §8.8's `TaskResult.output.artifactRefs` names a child's stored files, and nothing puts one into the parent's workspace today **[source]**. A child's file part is copied to the artifact store under "MD-18", up to 5 GiB by default, and its bytes never travel through stdout or the gateway. The parent's pod holds no credential that reads the store.

**Reference.** A child event that delivers a file part carries it as a reference: the part's `id`, `name`, `mimeType`, size, `sha256`, and the child's session id. The part's `ref` stays inside the gateway. A file part still exporting when the event is written carries `status: "streaming"`, and the parent can import it once the part is released.

**Import.** The model calls `import_child_session_file` with the child's session id, the part's `id`, and a destination path relative to the parent's workspace, or the harness writes a `request` with `kind: "import_file"` and the same members. The gateway checks that the child is a direct child of the caller, that the part is a released output file of the child, and the import limits. It then drives an `ImportFile` stream to the parent's adapter, which follows the restore of [IC-5](../0131-incremental-checkpoint/change.md#ic-5-restore-derive-download-and-seal): the gateway signs short-lived `GET` grants for the file's packs, and the adapter downloads them and verifies every chunk under S4.

**Write.** The adapter writes nothing into the parent's workspace itself. It stages the verified file in the parent slot's staging area on the spool volume, `/adapter/spool/<n>/staging/`, and runs the materialization helper's `overlay` as the parent's slot UID, under the files-only rule of [WM O4](../0153-workspace-materialization/decisions.md#open-decisions) that the owner settled on 2026-11-12, with the shared staging space of WM O9 settled on 2026-11-13 ([WM-12](../0153-workspace-materialization/change.md#wm-12-mid-session-uploads-and-child-file-imports)):

- At the start of the run the adapter gives the helper one end of a socketpair. It sends the staged file's read-only descriptor over the socket, the helper writes the file at the destination, and the adapter then deletes the staging file. The adapter never reads what the helper writes on the socket. An import carries one file, so the run applies one source.
- The helper resolves the destination beneath `/workspace` without following a link or crossing a mount, and refuses an existing file at the destination with `target_exists` unless the call sets `overwrite: true`. It assembles the file in its overlay directory and moves it into place with one rename, so the runtime never sees a partly written file.
- The staged file takes the staging space the pod's slots share on the spool volume, the part of the adapter's usable half of `spoolSizeLimitBytes` left after each slot's spool cap ([WM-4](../0153-workspace-materialization/change.md#wm-4-the-plan-the-adapter-builds), WM O9). The gateway refuses an import larger than the parent pool's staging space with `IMPORT_LIMIT_EXCEEDED` and `details.reason: "staging_limit"` before it signs a grant, and an import that fits waits for free space. An import whose wait reaches the helper run's deadline fails with `IMPORT_LIMIT_EXCEEDED` and `details.reason: "staging_timeout"`, as [WM-4](../0153-workspace-materialization/change.md#wm-4-the-plan-the-adapter-builds) states for every content source. At the defaults the staging space holds a file of the 5 GiB default `files.maxBytes` on a pod of up to six slots. A file waits on the spool only from its verification until the helper has applied it. There is no streaming path.

The call returns, or the `reply` arrives, after the helper run ends with a valid result, with the file's path, size, and `sha256`. Those values come from the adapter's own verification of the chunks rather than from the helper's result, so they are platform-verified. A helper run that fails, times out, or is cancelled fails the import, and the adapter removes the overlay directory with the helper's `discard`. The bytes never pass through the gateway.

**Limits.** `fileImportLimits` on the delegation lease, with `maxTotalSize` and `maxFiles` per child, mirrors `fileExportLimits` of §8.7, and the parent's workspace size limit applies. An import over a limit is refused with `IMPORT_LIMIT_EXCEEDED` before any grant is signed, and the helper's running total of the workspace's bytes enforces the workspace limit again during the write.

**Content.** A child's files are untrusted input to the parent: a child can return an instruction file that the parent's harness would read. When the parent lease's effective `contentPolicy.scanExportedFiles` is `true`, the gateway invokes `contentPolicy.interceptorRef` at the `PreExportMaterialization` phase once per imported file before it signs a grant, as §8.7 does for a file a parent exports to its child.

**Channel.** The `ImportFile` stream runs on a new gateway-to-adapter channel, `CH-FILEIMPORT`, with a register row, a contract card, and the generation fencing of `CH-OUTPUTFILE`. Its pack downloads travel on `CH-OBJSTORE` under presigned grants, as a restore's do.

**When.** A parent imports while the child lives and after it ends, within the child's retention, which "MD-18" gives its output files.

## Worked example

Alice, of tenant `acme`, runs the `claude-code` runtime through REST. Its revision declares `modes: [steer, queue, interrupt]`.

1. Alice sends "Run the migration against the dev database." No turn is open, so the message `msg_A` takes the direct path, its receipt is `delivered`, and a turn opens. Claude Code starts running shell commands.
2. Alice sends "Use the staging database instead." with no `delivery`. The default is `steer`, a turn is open, and the steer path writes `msg_B` at once. The receipt is `delivered`. Claude Code reads it when the running command finishes, and the adapter writes `consumed` with `msg_B`. Alice's event stream shows `message_state` `consumed` for `msg_B`.
3. Alice sends "Afterwards, write a summary." with `delivery: "queue"`. The queue path holds `msg_C`, and the receipt is `queued`.
4. A child session that the agent started sends "Schema check passed." with `send_update`. It reaches the parent's inbox as a child event under the parent's default intent, `steer`, so the gateway writes it into the running turn, and the child's call returns `delivered` at once.
5. The agent had earlier sent its other child, which is restoring onto a new pod after a pod loss, "Also run the slow integration suite." as `msg_D`, held `pending` in that child's DLQ. Having switched databases, the agent writes `retract` with `msg_D`. The entry is still `pending`, so it becomes `retracted`, the agent receives `retracted`, and the audit log records `message.retracted`. A second id in the same frame names a message the first child already consumed, and its result is `too_late`.
6. The runtime ends the turn with an end-of-turn `message` whose `consumed` lists `msg_A` and the child's message. Alice receives `turn_end` with turn 1 and those ids. The turn end makes `msg_C` eligible, the gateway writes it, and turn 2 starts.
7. The pod is lost during turn 2 after the runtime consumed `msg_C`, and before a checkpoint recorded it. The session resumes from the checkpoint taken after turn 1, whose consumed set ends with the child's message. The gateway recorded the consumption of `msg_C` after that message, so under O4 `msg_C` is not redelivered and moves to `consumed_unrecorded`. Alice's event stream shows `message_state` with `consumed_unrecorded` for `msg_C`, and she sends "Afterwards, write a summary." again as a new message, which the restored runtime takes as a new turn.

A second example covers a provider surface under O3. Bob, of tenant `acme`, uses the Anthropic SDK against a runtime whose revision declares `steer`, `conversationInput`, and `clientTools`.

1. Bob sends a request with a client tool `open_ticket` and "Investigate the failing build." The runtime delegates a child to bisect the failure and replies "I started a bisect." The gateway returns the reply, stores the digest, and holds the session.
2. The child ends its work with an end-of-turn frame that carries `complete: true` and "The regression is in commit 4f2a.", which reaches the parent as an `ended` child event with `state: "completed"`. No turn is open, so the message takes the direct path and opens a turn. Its envelope carries no `conversation.clientTools`. The runtime writes a summary of the finding, which reaches the transcript and the session's REST event stream. No Messages response carries it, and the turn writes no response record and no digest.
3. Bob sends his next request while that turn runs. Its history up to the last assistant message matches the stored digest, so it is a warm turn, and its message takes the steer path with its `conversation.clientTools`. The runtime writes `consumed` for the message, answers, and ends the turn with a call to `open_ticket`. Bob's response carries the output that followed the `consumed` frame and a `tool_use` block, with `stop_reason: "tool_use"`.

A third example covers what Alice sees during a turn. Her session runs `claude-code`, whose adapter uses `stream-json`, and her deployment configures no `PostAgentOutput` interceptor.

1. Alice sends "Fix the flaky test and export the failure report." The gateway emits `turn_start` with turn 3.
2. Claude Code writes its todo list. The adapter writes `activity` `start` for `plan_1` with `kind: plan`, `lifetime: session`, and three entries, and Alice's client draws the list.
3. Claude Code runs `npm test`. The adapter writes `activity` `start` for `act_9` with `kind: tool` and `record: true`, then `append` frames that grow `detail.output`, which it merges every 250 ms. The command needs approval, so the adapter writes a `request` frame with `kind: "approval"` and Alice approves it on the REST approve route. Frames keep flowing while she decides.
4. Alice's laptop sleeps and her client reconnects. It receives the replayed events and one `activity` snapshot with `plan_1` and `act_9`, so it redraws both.
5. The test ends. The adapter writes `end` for `act_9` with `status: completed`, the gateway writes its final state to the transcript, and a `patch` marks the plan's first entry completed.
6. Claude Code writes its explanation, which streams as `message_part` `append` entries to part `p4` and ends with `end`. The transcript records `p4` once, after `PostAgentOutput`.
7. Claude Code writes a 200 MB failure report to `out/failures.parquet` and emits a `file` part with that path. Alice's pool runs runc on XFS, and the file fits the export share of the spool, so the adapter clones the file into its spool at once. Alice's client shows the part as `streaming` with its name and size while the adapter chunks the clone, skips the chunks the last checkpoint already stored, and uploads about 12 packs of 16 MiB, four at a time. The turn could end first, and the part would still finish, because an export outlives its turn. The gateway confirms each pack, checks the references, sets `ref`, and releases the part, and Alice downloads the file with `GET /v1/blobs/{ref}`.
8. The runtime writes its end-of-turn `message`. The gateway emits `usage` events with `source: gateway` for each proxied model call during the turn, and `turn_end` with `status: completed` and the turn's usage. `plan_1` stays open, because its lifetime is the session.

## Limits

- **A suspension that releases the pod ends the exports.** A suspension of a runtime that does not declare `interrupt`, or one the runtime does not acknowledge, fails every export of the session with `suspend_hold_expired`, and the runtime emits the files again after the resume ("MD-18").
- **Runtime cooperation.** `steer` works only as well as the runtime's placement of messages. The gateway cannot check that a runtime places a message after tool results, and the conformance cases of §15.4.6 test it against recorded model requests.
- **In-memory inbox.** Custody survives a coordinator crash only with the durable inbox. With `messaging.durableInbox: false`, the documented loss window of §7.2 applies to `pending` and `delivered` entries alike.
- **Duplicates after a restore.** Consumed messages are never redelivered, so a duplicate arises only from a redelivered `delivered` entry that the restored runtime already holds: one it consumed before the checkpoint and had not yet reported. A runtime that does not persist its consumed ids with its history can read such a message twice. The SDK's set covers a runtime whose history the SDK holds, and the adapter's checkpointed set covers a consumption the runtime reported before the checkpoint, up to its bound of 1000 ids.
- **Consumption after the last checkpoint is not replayed.** Under O4, a runtime restored from a checkpoint lacks the messages it consumed after that checkpoint, and the gateway reports them `consumed_unrecorded` in place of resending them. A sender that does not read the event loses the message's effect on the runtime's history.
- **Late consumption reports.** A runtime that declares `queue` alone reports consumption only on end-of-turn `message`, so its messages stay `delivered` for the whole turn.
- **Interrupts come from clients.** Only a session's client, a REST client or its parent, can interrupt it, so a child cannot stop its parent's turn (B9).
- **Parents pay a turn per child event.** Each child event can start a turn in a waiting parent, which costs model tokens. A loop between a parent and a child is bounded by the parent's `messagingRateLimit` and the budgets, and the root's stream reports a session that reaches its lifetime cap (B-O4).
- **Children stay open after a turn.** A child that never completes waits for its parent's next message until the parent closes it, `onParentEnd` closes it, or a limit ends it. It releases its pod once it is `dormant` ([`0146-session-lifecycle`](../0146-session-lifecycle/change.md), "SL-6").
- **Siblings do not message each other.** A child that needs a sibling's result goes through its parent, which spends a turn on the relay (B9).
- **Provider surfaces do not steer.** A user of a Chat Completions, Responses, or Messages client cannot correct a running turn, because those APIs have no request for it.
- **Other turns are outside provider responses.** Under O3, the output of a turn that no client request caused reaches the transcript and the REST event stream, and no provider-surface response. A client that reads only its provider responses learns of such a turn only when the runtime refers to it in a later turn the client caused. A cold continuation on the Messages API takes its history from the client, so it lacks such a turn.
- **A client request can wait for another turn.** Under O3, on a runtime that does not declare `steer`, a client request that arrives during a turn another session's message caused waits for that turn's closing `message`, and a non-streaming client's timeout bounds the wait.
- **Retraction is not recall.** A retraction succeeds only before delivery. A message a recipient received, a client tool call a provider-surface client holds, and output already streamed stay where they are, and the runtime receives `too_late`. A REST client that already started a retracted call's tool learns of the retraction only from the event, and the tool's side effects stand.
- **Output is not retracted.** Under S8, retraction of output and session events is ignored for now ("MD-11", "Blast radius").
- **Activity is the runtime's claim.** The gateway cannot check that an activity describes what the runtime does, so nothing that decides policy, audit, or billing reads it.
- **A pod loss loses unended activity.** Open activities end `cancelled` with `runtime_exit`, and the restored runtime starts its own.
- **Interceptors cost streaming.** A session with a `PostAgentOutput` interceptor receives each part once, completed (A5).
- **Harness approvals are not enforced.** The harness runs the tool, and Lenny relays the decision ("MD-19"). The approval frames travel on `CH-MSGSOCK`, so a runtime at every integration level forwards approvals.
- **Runtime-reported usage depends on the runtime.** `llm_request_completed` travels on `CH-MSGSOCK` and needs no capability, so a runtime that calls a provider outside the LLM proxy and writes no such frame reports no usage for that call (LU-10).
- **Files changed during an export without a clone.** On a pool without reflink clones, which includes every sandboxed and microvm pool, a file the runtime changes while the adapter reads it ends the part `failed` with `file_changed`, and the runtime has to emit it again ("MD-18"). The check sees only changes to the file's identity. A write through a memory mapping that the kernel has not yet written back changes no identity field, so the stored copy can hold a mix of old and new bytes, and its whole-file SHA-256 matches that copy (MDR-29).
- **Symlinks in an exported path.** The adapter refuses a path with a symlink in any component, including one whose target lies inside the workspace, so a runtime exports the file by its real path ("MD-18", "Freeze").
- **Exports share the checkpoint grant window.** A large export slows the pre-copy and upload passes of a concurrent checkpoint of the same session, which keeps the S5 bound (A12). During a checkpoint's capture pass the export's reading, hashing, and compression wait (A17).
- **Large files are not cloned or copied.** On a pool in reflink or copy mode, a file larger than the remaining export share of the spool, 256 MiB at the default `checkpointCaptureBudgetBytes` of 512 MiB, is read in place with the identity check and is neither cloned nor copied, and the clones and copies of parts waiting for the export cap also count against the share. Such a file ends `file_changed` when the runtime changes it during the read, as on a pool without clones (A21).
- **Exports have a deadline.** An export that does not reach `ExportReady` within `exportTimeoutSeconds` of its `ExportStart` fails, a part that waits for the export cap fails after `exportTimeoutSeconds` from its first frame, a session runs at most `files.maxConcurrentExports` exports at once, and its queue holds at most `files.maxQueuedExports` parts, so a large file on a slow pool has to be split or exported from a pool with a longer deadline.
- **Exports end with the seal window.** At session end an export gets the time the seal checkpoint leaves in the session's seal window, 300 seconds by default and at most the ceiling of 600, and the whole window under `checkpointPolicy: none`. An export still running when the window ends fails with `seal_timeout`, so a runtime that emits a large file shortly before the session ends can lose it. A runtime that needs more time sets a longer `maxWorkspaceSealDurationSeconds` within the ceiling (A19).
- **Some exported bytes upload apart from the seal.** The seal uploads an exported file's chunks once, with three exceptions. A file that the runtime changed or deleted after it emitted the part is exported from its clone, whose chunks the seal snapshot does not hold. An export pack whose grant is outstanding when the seal starts is not yet confirmed, so the seal may upload its chunks again, at most one grant window of packs. Under `checkpointPolicy: none`, no seal snapshot stores any chunk (A19).
- **The whole-file hash is not a defence.** The gateway compares the whole-file SHA-256 only on a `PostAgentOutput` scanner's read. A compromised pod writes both the chunk list and the hash, so the hash detects no tampering by the pod, and S4's per-chunk check is the storage-integrity guarantee (A20).
- **Failure notices need an acknowledgement.** A runtime that does not use the SDKs and never writes `output_failed_ack` receives each notice again after every resume until the session ends.
- **The grant window grows with the pack format.** S5's bound rises from 4 × 16 MiB today to 4 × 32 MiB by default, and to 8 × 32 MiB on a pool that sets the largest override (A13, A14).
- **Requests need a reader.** A runtime that writes a `request` and stops reading stdin until the `reply` arrives receives nothing else meanwhile. The SDKs wait off the frame reader, and a runtime written without them has to do the same ("MD-19").
- **Leniency hides mistakes.** An ignored member or frame type surfaces only as a `runtime_warning` event, so a runtime author reads the session's stream to find it ("MD-24").
- **Watching costs bandwidth.** Each watched child's deltas cross the parent's pod connection ("MD-25").
- **Imports are copies.** An imported file is a copy in the parent's workspace that counts against its size limit and its checkpoints, and a child's later change to the file does not reach it ("MD-26").
- **A rejected child event loses its content.** When the parent's interceptor rejects an end-of-turn or terminal child event, the parent receives a notice in its place, and the child's answer stays in the child's transcript ("MD-9").

## Alternatives rejected

- **A steer special case.** A boolean `steer` beside `immediate` and `queued` would leave queueing, interruption, and later intents as separate rules. The owner directed a general per-message model.
- **Steer by default for every runtime.** A runtime that does not read its input mid-turn would receive messages its SDK queues, which matches `queue` while reporting `delivered`, and a runtime that reads one message per turn would gain nothing.
- **Delivering mid-turn to every runtime between tool calls.** The adapter cannot observe tool calls inside a runtime's own process, and §29.3 records that no frame carries the signal.
- **One `response` per `message`, with steered messages folded into the next `response`.** A runtime that consumes several messages in one turn would owe several `response` frames, and output with no causing message would still be discarded.
- **A send call that waits for the consuming turn.** A REST caller would wait for a turn that may run many minutes, and an agent's `message_child` would block its own model loop. The event stream carries the outcome.
- **Holding inbox deliveries to a provider-surface session until the next client turn.** Revision 1 recommended it, so that a delivery would join work a client is waiting for. A message to an idle provider-surface session then waited for the client's next request or its TTL, and every provider surface needed a hold of its own. Delivery on arrival with the two rules of "MD-8" keeps the turn away from the client with no surface-specific hold (O3).
- **Custody until a checkpoint records the consumption.** Revision 1 recommended it, so that a restored runtime would receive again a message it consumed after its checkpoint. The redelivery can repeat side effects that the checkpoint does not undo, and a runtime that never checkpoints would keep every consumed message in the inbox until the session ends. The `consumed_unrecorded` report leaves the choice to resend with the sender (O4).
- **Gateway-side ordering of steered messages into model history.** The gateway does not see the runtime's model requests, and only the runtime knows where its model steps fall.
- **Activity as a flag on `output`.** Every consumer of `output` would have to check the flag: the transcript, cold history, the provider adapters, `TaskRecord`, and `PostAgentOutput`. A consumer that missed it would put display state into a model's history.
- **A closed list of activity kinds.** The owner asked for an open `kind` governed by conventions, so a runtime can report what its harness reports without a Lenny release.
- **Transient activity with no current state.** A client that attaches mid-turn would see nothing until the next update, and the short replay buffers would lose the rest.
- **Every activity update in the transcript.** A test run can produce thousands of updates, which would push other events out of the replay buffers and grow the transcript. The runtime chooses what to record, and only final states are recorded (A2).
- **Blob references for large activity.** The owner decided that activity frames are not stored as files (A10). A large result is a file part.
- **Files through stdout.** A stdout line is limited to 50 MiB, base64 grows binary content by a third, and a large file would hold every later frame of the runtime behind it (A11).
- **Files through the gateway.** Streaming the bytes through the gateway would let an interceptor scan them in flight, at the cost of gateway bandwidth for every file. The owner chose the direct upload (A11a), and an interceptor reads the stored object through `ref`.
- **One `PUT` per file.** Revision 3 proposed it. A grant of up to 5 GiB breaks the incremental checkpoint design's S5 bound of `checkpointGrantWindow × packMaxBytes`, a file over 5 GiB would need the multipart capability R5 withholds, a failed upload would start again from nothing, and content a checkpoint already stored would be uploaded again (A12).
- **A grant window of its own for exports.** It would keep exports from slowing checkpoint uploads and double the bytes a compromised pod can write at once (A12).
- **Removing the per-pool grant window override.** It would make S5's bound one constant, at the cost of a setting the tree already carries on `PodSet`. A maximum of 8 keeps the bound stated (A13).
- **Path checks by resolved path, as `ExportPaths` does.** A check on a resolved path followed by a read by path leaves a window in which the runtime can swap a component for a symlink. Opening beneath a directory descriptor and reading the descriptor that was checked closes it ("MD-18", "Freeze").
- **Pack IDs from content alone.** Revision 5 named a pack by the SHA-256 of bytes that the adapter's input determined, so a pack the adapter rebuilt had the ID of the pack it rebuilt, and S1 had to either refuse a rebuilt pack whose key the catalog held or answer it from rows outside the allowed set. The pack nonce makes every pack distinct, so a rebuilt file gets new pack IDs and new grants, and the "already stored" answer is left for a resend (A18).
- **Narrowing S1 and reviving soft-deleted pack rows.** A rebuilt pack whose row was soft-deleted would be revived and leased again in place of a new upload. A soft-deleted row keeps its key for `gc.tombstoneRetentionSeconds` while the object delete or the §12.5 backstop sweep is still pending, so the object behind a revived row can be deleted after the fact, and a snapshot or an output file would reference a missing pack (A18).
- **Waiting for exports up to `exportTimeoutSeconds` at the seal.** Revision 5 did so. The wait could reach 900 seconds past the seal window, which §7.1's terminal pipeline budget did not cover, and neither an operator nor a runtime could shorten it. Exports now end inside the seal window (A19).
- **A separate export wait after the seal checkpoint.** Revision 6 first gave exports still running after the seal checkpoint their own wait, the runtime field `files.sealExportWaitSeconds`, 120 seconds by default under a ceiling of 900 seconds, as A19 first recorded. An exported file lies in the workspace, which the seal checkpoint captures whole, and the seal and the exports share one dedup set, so the seal stores the file's chunks and an export that continues after it only finishes its bookkeeping. A wait beyond the seal window would therefore cover no transfer the seal does not already make, while it raised the terminal pipeline budget to 1230 seconds at the defaults and the claim orphan timeout to 1260 seconds. The owner replaced it on 2026-11-10 (A19).
- **Verifying the whole-file SHA-256 on the first full read.** Revision 5 did so, with a `checksum_mismatch` failure that deleted the file. S4's per-chunk check already detects corrupt or substituted storage, a compromised pod writes the hash it is checked against, and the check added a deletion path for held material. Publishing the hash lets a client verify end to end (A20).
- **A parent that reads children only through tools.** The owner first considered it, because a harness cannot tell a child's message from its client's. Claude Code pushes a sub-agent's messages and ends into the parent's conversation with the sub-agent's id, and the model routes by that id, so the runtime only renders `from` (B2, B3).
- **An upward `send_message`.** A child messaged its parent as a peer, while a top-level session has no such call toward its client. `send_update` gives every session the same call toward its client (B1, B4).
- **A status on the end-of-turn frame that marks a question, or a model-facing tool that marks a turn as waiting for input.** No client reads the difference between a question and an answer from anything but the text, and A2A, the OpenAI APIs, and the Messages API end both kinds of turn the same way. The owner's rule kept only what a client and a top-level agent use (B5).
- **Elicitations sent to the person past every parent.** It removes the per-hop forwarding, and it loses a parent's ability to answer. The owner kept the §9.2 chain and added `humanRequired` (B6).
- **A parent that approves a child's harness approval, or sets the child's approval policy.** An agent would approve another agent's risky action, possibly steered by text the child produced. The owner chose the person at the edge (B7).
- **A tool for harness approvals.** Every harness's approval mechanism asks the program that hosts it, so a tool made the host relay a request it already held and put an unusable tool in the model's list (B8).
- **Keeping the `lenny/` prefix.** The MCP tool-name rule and the Anthropic API exclude `/`, so every harness rewrites the name (B10).
- **An AG-UI endpoint in v1.** AG-UI is run-based and re-sends state on each run, while Lenny is session-based, and it would be a fourth client surface (G3).
- **Separate `response` and `update` frames.** Revision 9's review recommended a new frame for each purpose. The owner preferred one frame with optional members, so a runtime author learns one frame and a forgotten member takes a default (B-O6).
- **`endOfTurn` defaulting to `false`.** A runtime that forgot the member would leave its client waiting for a turn that never ends. With the default `true`, a forgotten member ends the turn early, and a later `message` is recorded as unsolicited under "MD-4" (B-O6).
- **Naming the streaming frame `progress`.** Its parts are the session's answer and enter the transcript, while `activity` carries progress (B-O6).
- **A hop count as the loop guard.** It needs reply links along the loop, and an end-of-turn child event carries none. `messagingRateLimit` already bounds every loop, because each round needs a `message_child_session` (B-O4).
- **A per-pair turn cap with `dropped` past it.** A dropped end-of-turn or terminal child event strands the conversation, and the existing rate limit bounds the loop (B-O4).
- **A stream that replaces child events.** Every runtime would decide which events wake its model, and `await_child_sessions` would become a harness feature. The watch of "MD-25" adds the stream, and child events stay the messages a model receives (B13).
- **Refusing the approve routes to principals with a session claim.** No pod holds a client credential, and a credential placed in a pod by its owner carries no session claim, so the check would refuse nothing (B15).
- **Files from a child copied into the parent at once.** A large file that the parent never reads would cost its transfer and its workspace space. An import on demand copies only what the parent asks for (B14).
- **Files from a child through stdout or the gateway.** The reasons of A11 apply in the other direction (B14).
- **Session lifecycle alternatives.** The `cancel` flag on the close tool, two close tools, the pod as a property of every state, and the other alternatives of the lifecycle are recorded in [`0146-session-lifecycle`](../0146-session-lifecycle/change.md).

- The durable inbox's "Explicit ACK" row requires the adapter to keep a `delivered_message_ids` set in checkpoint state. No code in `pkg/adapter` keeps one, and `lenny_inbox_duplicate_suppressed_total` has a catalog entry and no producer. "MD-3" replaces the set with the consumed set.
