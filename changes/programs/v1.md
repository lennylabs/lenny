# Program v1

This program carries Lenny to v1: every change that came from `designs/` implemented, every open finding in `BUILD-GAPS.md` and `TEST-GAPS.md` closed, and the specification restructured to state the result. The front matter is the plan; this text explains it.

## Order

- **M0** puts the records and the helpers in place, so every later change uses them.
- **M1** first makes `main` green and puts every merge behind one gate in one Linux environment (0154), so later failures are seen when they happen. It lands the specification structure (0115) and the tooling it needs. Coverage derived from annotations and test selection derived from the import graph (0116) replace the maps and registers keyed by path or section number, which caused most of the friction in the migration spike. Once 0115 merges and before any area starts, the test tiers take their names and the static tier splits (0155), so every later change writes the new names. The pod lifecycle controller's kind renames and the `PodSet` merge (0137.S5) run once, tree-wide, before any area migrates, because they touch 463 Go files.
- **M2** settles the gateway's package layout (0117) before areas move code, and pilots the persona journey tier (0157), in which an agent follows the documentation as an operator, a tenant admin, or a user and the harness checks the result.
- **M3 onward** migrates one area per milestone. Each area change writes the area's pages and discharges the specification lane of every change touching the area. It re-annotates the area's packages with identifiers and renames their test and subtest names that carry a section number, with the entries that key those tests by name in `tests/registers/skip-reasons.yaml`, `tests/registers/residual-skip-reasons.yaml`, and `tests/flake-budget.yaml` (0116). It moves the area's integration tests out of the single integration package into a Go package of their own, so the merge gate's selection runs only the affected parts rather than the whole package (0116, decision 6). The code steps stay with their changes. Each area also retires its tests that compare specification prose, adds conformance suites for its stores (0156), and runs its persona journeys. Areas run in parallel once M1 has landed.

The test infrastructure review behind 0154 to 0157 is in [0154's evidence](../archive/2026-11-17-0154-merge-gate/evidence/test-infrastructure-review.md).

## Reading the program

The changes of this program describe one refactor that lands in pieces, and an agent working on any part of it reads them together:

- **The target state** is the current specification as every member change modifies it, whatever each change's status. A question about how Lenny behaves is answered from the target state, naming the change that states it. A question about what the tree does today is answered from the tree.
- **"Current state" sections** of member changes describe the tree before the program, and they go stale as other members land. The tree is the authority on what exists now.
- **Members that disagree.** When two member changes state different things, neither wins silently: the agent records the conflict as an open decision on both changes and raises it with the owner.
- **No transition modes.** Code written for a member change implements the target state. It keeps no dual mode, fallback, or flag for behavior a member change removes, because Lenny has no deployments to keep compatible.
- **Retired records and sections.** 0115.S9 removed `BUILD-PLAN.md`, `BUILD-PROGRESS.md`, and `ROADMAP.md` and turned §18, §21, and §23 into successor stubs. An edit a member change states for one of them applies to its successor instead: the plans to this program, its board, and `docs/about/status.md`, the post-v1 items of §21 to "Planned after v1" on that page, and §23 to `docs/about/comparisons.md`. An edit with no successor is moot.
  - **Spec-map and change-graph edits.** 0116.S6 retired `tests/spec-map.json`, `tests/change-graph.json`, their exception and pending lists, and the change-graph registers. An edit in a member change that adds a spec-map entry is read as the `// spec:` annotation the test carries, an edit that adds a change-graph key is read as a row in `tests/non-go-inputs.yaml` when the input is one no Go package owns and is otherwise moot, and a driver step that rewrites either map is moot. 0117, 0125, 0132, 0137, and 0141 carry such edits.
  - **Claim-register edits.** 0116.S5 retired the claim register `tests/claim-map.json` and filed its open rows as issues under `issues/`. An edit in a member change that adds a claim-register row is read as filing an issue under the code of the page that owns the mechanism, and an edit that retires rows is read as closing the matching issues. 0128, 0131, 0135, 0139, and 0148 carry such edits.
- **Outside the program.** The open proposals under `proposals/` and any change not listed in `members` are not part of the target state until the owner adds them.

## Decisions

The owner settled these questions on the M3 readiness decision page. Each entry names the page's question, and the finding of the M3 readiness review where one exists. The front matter and "Order" apply decisions 1, 6, 7, 9, and 10 when the M3 step list is written, and until then they read as revised by these decisions.

1. **Who writes the specification pages of an area.** Settled by the owner on 2026-11-19, question S-1 (program-C1), option (a). The first step of each area change writes the area's pages at the target state and files a planned issue for each requirement whose member step has not landed. The member steps for that area then carry code, tests, and documentation only. The edits that apply this to the member steps (an edge on the area step, a specification lane discharged by that step, and the planned issues in `closes`) land with the M3 step list. The options not taken were (b), in which member steps keep editing the numbered sections and the area change later migrates what landed, and (c), in which a member step edits the numbered section or the page depending on whether it lands before or after its area.
2. **The playground mint's empty scope.** Settled by the owner on 2026-11-19, question S-2, option (a): the mint refuses an unparseable subject scope with `401` and a disjoint intersection with `403`. Change [0162](../0162-playground-mint-scope-refusal/decisions.md) records the answer as its decision 1 and built it in 0162.S1, which has landed. The program owes nothing further for this question.
3. **The steps that the fix agents added or split.** Settled by the owner on 2026-11-19, question S-3, option (a): the splits stay, and the owner may veto each one. They are 0134.S5, 0136.S7, 0136.S8, 0140.S2, 0140.S3, 0141.S3, 0141.S4, 0146.S3, 0147.S13, 0149.S10, 0149.S11, and 0150.S4, and they merged with `records/m3-readiness`. No veto is recorded. The option not taken was (b), reverting every split and raising each as an open decision.
4. **Lint findings in the merge gate.** Settled by the owner on 2026-11-19, question S-4, option (b): a golangci-lint finding on a line the branch changes fails the static tier, and the findings that predate the check stay a warning until they reach zero. The merge of `fix/gate-follow-ups` built it, and GATE-I1 tracks the remaining findings. The options not taken were (a), keeping the check as a warning with an issue, and (c), burning down the existing findings before M3 and making every finding fail.
5. **How the owner settles the design questions.** Settled by the owner on 2026-11-19, question S-5, option (c), in the owner's words: "I'll answer everything, but tier C can wait until its step is built". No question on the decision page takes its recommendation without the owner's answer. A tier C question stays open until the owner answers it, which can be when its step is built. The options not taken were (a), in which tiers B and C take the recommendation unless the owner changes one, and (b), in which tier C takes the recommendation.
6. **The M3+ milestones and their exit.** Settled by the owner on 2026-11-19, question PG-C2 (program-C2), option (a), with the owner's note "Elaborate. Show me what this means in practice". Each M3+ milestone lists its steps in the front matter, as M1 and M2 do, in the dependency order that the readiness review proposed. Its exit reads: the area change's steps and the member steps listed in the milestone have landed, and every requirement of the area's pages whose step sits in a later milestone has a planned issue. `current` moves to M3 once its steps are listed. The M3 step list carries the front matter edits and the elaboration the owner asked for. The options not taken were (b), whole-change exits with the areas ordered by the depth of their dependency closure, and (c), parallel page work with a single exit at Close.
7. **Placeholder pages outside the capability folders.** Settled by the owner on 2026-11-19, question PG-C3 (program-C3), option (a). Each placeholder page that carries no area, under `components/`, `interfaces/`, `cross-cutting/`, or `overview/`, is assigned to the milestone of the area whose steps change it, the program records the assignment, and the change that removes the numbered files joins Close. The owner added: "At the same time, we need to allow for steps to create new pages if needed. There's no guarantee that the existing placeholders are sufficient". A step may therefore create a specification page that no placeholder provides, and the program records the milestone of each new page in the same way. The option not taken was (b), one milestone for the shared pages after the areas.
8. **The removed-field error format, and the status of the member changes.** Settled by the owner on 2026-11-19, question PG-C5 (program-C5), option (a): a refusal of a removed field names the field in `details.fields[].field`, the array that §15.1 defines for every validation error. The answer is recorded as open decision 1 of [0119](../0119-agent-runtimes-only/decisions.md), O16 of [0124](../0124-connector-removal/decisions.md), open decision 1 of [0132](../0132-llm-response-cache-removal/decisions.md), and open decision 3 of [0133](../0133-llm-upstreams-and-cost-budgets/decisions.md), and the owner confirmed it on 2026-11-20 as question PR-A1. The owner added: "Open questions that aren't the shared error-format question need to be answered by me". The other open decisions of 0133, and of every member change, wait for the owner's answers. A settled entry leaves "Open decisions", and a change with no open decision and no started step becomes `Decided`. The option not taken was (b), keeping `details.field` and changing §15.1 for this refusal.
9. **The exit criterion for findings from the gap records.** Settled by the owner on 2026-11-19, question PG-C10 (program-C10), option (a), with the owner's note "Elaborate". An area's findings from `BUILD-GAPS.md` and `TEST-GAPS.md` are filed as issues, and each is closed or planned in a named step, with the high-severity issues blocking the area's exit. The `triage` and `issue` helpers that `changes/README.md` lists are built before M3 starts. The M3 step list carries the edit of the exit and the elaboration the owner asked for. The options not taken were (b), keeping "closed" and adding per-area fix steps after triage, and (c), closing the build findings per area and leaving the test findings to one step for the program.
10. **The exit criterion for old section citations.** Settled by the owner on 2026-11-19, question PG-C11 (program-C11), option (a). The measure for an area is the citations, in any package, of the numbered sections that the area has turned into full successor stubs, and a gate fails on a citation of a full stub. The per-package ratchet of `tests/registers/spec-section-citations.yaml` stays as the rule that counts do not grow. The option not taken was (b), zero citations for each package whose `doc.go` names only the area's pages, with the shared packages left to Close.
11. **Pod sets after a change to a tenant's assets.** Settled by the owner on 2026-11-19, question PG-C14 (program-C14), option (a): a change to a tenant-derived runtime's `inline` or `artifact` assets retires the earlier pod sets from the claim. [0137](../0137-pod-lifecycle-controller/decisions.md) records it as its open decision O8, [0147](../0147-tenant-derived-runtimes/decisions.md) as its decision 45, and [0140](../0140-runtime-revisions/decisions.md) as its open decision O22. The option not taken was (b), keeping the earlier pod sets claimable as for stores.
12. **The `openai-assistants` reference runtime.** Settled by the owner on 2026-11-20, question DV-1, option (a): a small change removes it, with its mentions in the specification (§26.10, §5, §14, and §15), its entry in `pkg/embedded/stack/catalog.go`, the embedded manifests, the chart values and the chart's reference-runtimes test, and the documentation.
