# Program v1

This program carries Lenny to v1: every change that came from `designs/` implemented, every open finding in `BUILD-GAPS.md` and `TEST-GAPS.md` closed, and the specification restructured to state the result. The front matter is the plan; this text explains it.

## Order

- **M0** puts the records and the helpers in place, so every later change uses them.
- **M1** first makes `main` green and puts every merge behind one gate in one Linux environment (0154), so later failures are seen when they happen. It lands the specification structure (0115) and the tooling it needs. Coverage derived from annotations and test selection derived from the import graph (0116) replace the maps and registers keyed by path or section number, which caused most of the friction in the migration spike. Once 0115 merges and before any area starts, the test tiers take their names and the static tier splits (0155), so every later change writes the new names. The pod lifecycle controller's kind renames and the `PodSet` merge (0137.S5) run once, tree-wide, before any area migrates, because they touch 463 Go files.
- **M2** settles the gateway's package layout (0117) before areas move code, and pilots the persona journey tier (0157), in which an agent follows the documentation as an operator, a tenant admin, or a user and the harness checks the result.
- **M3 onward** migrates one area per milestone. Each area change writes the area's pages and discharges the specification lane of every change touching the area. It re-annotates the area's packages with identifiers and renames their test and subtest names that carry a section number, with the entries that key those tests by name in `tests/registers/skip-reasons.yaml`, `tests/registers/residual-skip-reasons.yaml`, and `tests/flake-budget.yaml` (0116). It moves the area's integration tests out of the single integration package into a Go package of their own, so the merge gate's selection runs only the affected parts rather than the whole package (0116, decision 6). The code steps stay with their changes. Each area also retires its tests that compare specification prose, adds conformance suites for its stores (0156), and runs its persona journeys. Areas run in parallel once M1 has landed.

The test infrastructure review behind 0154 to 0157 is in [0154's evidence](../archive/2026-11-17-0154-merge-gate/evidence/test-infrastructure-review.md).

## Reading the program

The changes of this program describe one refactor that lands in pieces, and an agent working on any part of it reads them together:

- **The target state** is the current specification as every member change modifies it, whatever each change's status. A question about how Lenny behaves is answered from the target state, naming the change that states it. A question about what the tree does today is answered from the tree.
- **"Current state" sections** of member changes describe the tree before the program, and they go stale as other members land. The tree is the authority on what exists now.
- **Members that disagree.** When two member changes state different things, neither wins silently: the agent records the conflict as an open decision on both changes and raises it with the owner.
- **No transition modes.** Code written for a member change implements the target state. It keeps no dual mode, fallback, or flag for behavior a member change removes, because Lenny has no deployments to keep compatible.
- **Retired records and sections.** 0115.S9 removed `BUILD-PLAN.md`, `BUILD-PROGRESS.md`, and `ROADMAP.md` and turned §18, §21, and §23 into successor stubs. An edit a member change states for one of them applies to its successor instead: the plans to this program, its board, and `docs/about/status.md`, the post-v1 items of §21 to "Planned after v1" on that page, and §23 to `docs/about/comparisons.md`. An edit with no successor is moot.
  - **Claim-register edits.** 0116.S5 retired the claim register `tests/claim-map.json` and filed its open rows as issues under `issues/`. An edit in a member change that adds a claim-register row is read as filing an issue under the code of the page that owns the mechanism, and an edit that retires rows is read as closing the matching issues. 0128, 0131, 0135, 0139, and 0148 carry such edits.
- **Outside the program.** The open proposals under `proposals/` and any change not listed in `members` are not part of the target state until the owner adds them.
