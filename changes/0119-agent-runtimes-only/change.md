## Problem

"Terms", after "Scope", defines the vocabulary this document uses.

The specification defines a runtime by its type and, for an agent runtime, by its execution mode ([§5.1 Runtime](../../spec/05_runtime-registry-and-pool-model.md#51-runtime), [§5.2 Pool Configuration and Execution Modes](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes)) **[source]**:

- A `type: agent` runtime runs sessions, with a workspace, delegation, elicitation, and multi-turn dialog.
- A `type: mcp` runtime hosts an MCP server that knows nothing about Lenny. Lenny manages its pod lifecycle, isolation, credentials, workspace, pool, egress, and audit, and the gateway exposes it at `/mcp/runtimes/{name}`.
- An agent runtime in `executionMode: session` binds each session to a claimed pod. An agent runtime in `executionMode: service` is a replicated service: one runtime process serves many requests, with no claim, no workspace, no checkpoint, and no per-session lifecycle, and the gateway routes each message to a tenant-pinned replica.

The changes of the v1 program have rebuilt the session-mode agent pod: one slot container per slot under its own UID, a runtime supervisor that launches a fresh runtime process per session at bind, a file-descriptor broker, a fixed runtime-visible layout, a handshake on every runtime connection, and per-slot egress scopes. The `type: mcp` and service-mode cases do not fit that model, and before the cross-design review of 2026-11-13 applied this design, every design that touches the pod, the protocol, egress, or admission carried a separate rule for them **[source]**:

- The pod layout renders a service-mode pod with no `/workspace` or `/session` and a launch at pod start, and a `type: mcp` pod as a pod with one slot whose adapter speaks MCP to the runtime ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)).
- The runtime protocol keeps `sessionId` multiplexing and refuses tool calls on a service-mode pod, because one process serves several requests there ([RP-3](../0139-runtime-protocol/change.md#rp-3-tool-calls-on-frames)). The message delivery design keeps `startId` open as decision C1 because service mode might need it ([`0135-message-delivery`, "Decisions"](../0135-message-delivery/decisions.md#decisions)).
- The egress design plans a whole proposal, its proposal 0, for a durable service-mode tenant pin, a service-mode listener in the adapter, and new network policy rows, to close two High findings: F-5.2.65, in which service-mode tenant pins have no arbiter across gateway replicas, and F-5.2.66, in which the service-mode request path is not wired at all ([`0127-egress-and-git`, "Relationship to proposal 0111 and open findings"](../0127-egress-and-git/change.md#relationship-to-proposal-0111-and-open-findings)). It also leaves the trust anchor unconstrained on service-mode and `type: mcp` pods.
- Tenant scoping evaluates a service-mode pod with no environment and refuses sessions whose environment has anything of its own ([`0149-tenant-scoping-identity`, "Effective policy"](../0149-tenant-scoping-identity/change.md#effective-policy)). The user git identity and user credential delivery designs refuse service-mode pods.
- Session derive and tenant-derived runtimes refuse a target without a runtime supervisor (SD-P4 and the export refusal of DR-8), a case that now reduces to a `type: mcp` target or a stale runtime row.

Neither mode is in use. The `/mcp/runtimes/{name}` endpoint is wired with a nil dispatcher in the gateway, so every call answers `RUNTIME_UNAVAILABLE` ([`0134-mcp-protocol-upgrade`, "Current state"](../0134-mcp-protocol-upgrade/change.md#current-state)) **[source]**. The service-mode slot gate in `pkg/adapter/statelessslot` has no production caller (F-5.2.66) **[source]**. No reference runtime is `type: mcp`, and the specification's catalog already directs MCP servers away from runtimes ([§26.1 Catalog Overview](../../spec/26_reference-runtime-catalog.md#261-catalog-overview)) **[source]**. Lenny has no deployments.

The owner decided on 2026-11-13 to remove both modes. After this change Lenny runs `type: agent` runtimes in session mode and nothing else. This design states what leaves, what simplifies in the other designs, how the removed fields are refused, and what users of the removed modes do instead.

## Scope

**Removed:**

- The `type: mcp` runtime: the enum value, the dedicated endpoint `/mcp/runtimes/{name}` and its implicit sessions, the adapter's MCP client to a runtime, `mcpEndpoint` in discovery, `mcpRuntimeFilters` on environments, the `type: mcp` delegation refusal, the reference `type: mcp` runtime, and every `type: mcp` exception in admission, pod rendering, idle handling, derive, delegation, and billing ("AR-1").
- Service mode: `executionMode: service`, `maxConcurrentRequestsPerPod`, claimless tenant-affinity routing, the `/v1/stateless/{pool}` route the tree serves, the service-mode tenant pin of the egress design's proposal 0, the service-mode pod layout, the service-mode scaling formula and its metrics, `conversationContinuity`, and every service-mode exception in the other designs ("AR-2").
- `startId` on `session_start` and `session_started`, `sessionId` on every frame other than `session_start`, and the remaining rules for several sessions on one runtime connection ("AR-3", O5).
- The `type` and `executionMode` fields themselves, under O1 and O2 ("AR-4").

**Changed:**

- Writes that name a removed field are refused by name ("AR-4", O3).
- A derive no longer compares execution modes, and the refusals that existed only for targets without a supervisor leave. A check at the post-chain point that the final runtime row is `registered` takes their place for every create, derive, and delegated child ("AR-5", O8).
- `sessionIsolationLevel` loses `executionMode` and `conversationContinuity` (O4).
- Headings that name the removed concepts are renamed through the anchor-redirect map (O7).

**What stays: MCP as a protocol.** Two different things in Lenny carry the name MCP, and only one of them leaves:

| MCP as a client-facing and tool protocol (stays) | MCP-server runtimes (removed) |
| :-- | :-- |
| The gateway serves MCP to clients: the MCP API of [§15.2 MCP API](../../spec/15_external-api-surface.md#152-mcp-api), MCP Tasks, and the protocol versions [`0134-mcp-protocol-upgrade`](../0134-mcp-protocol-upgrade/change.md) upgrades. | A runtime whose process is an MCP server, registered with `type: mcp`. |
| Lenny's platform tools, which an agent runtime calls through `tool_call` frames or through the reference MCP bridge ([RP-3](../0139-runtime-protocol/change.md#rp-3-tool-calls-on-frames), [RP-5](../0139-runtime-protocol/change.md#rp-5-reference-mcp-bridge)). | The gateway's dedicated endpoint `/mcp/runtimes/{name}`, which proxies a client's MCP calls to that process. |
| MCP servers that an operator runs as operator services, which a harness in the pod reaches as an MCP client through egress ([`0124-connector-removal`, "CR-3 External services"](../0124-connector-removal/change.md#cr-3-external-services)). **Non-goals:**

- Pods with several slots. `sessionPolicy.maxConcurrentSessionsPerPod` above 1 stays, with `acknowledgeSharedPod`, as [PL-9](../0118-agent-pod-layout/change.md#pl-9-pool-settings-and-renames) states. The rules that serve concurrent session-mode pods stay unless this design names them.
- A replacement for either mode (O6).
- Editing any design other than this one. "Instructions for reviewers of other designs" states each design's change.

## High-level design

Lenny runs one kind of runtime. A runtime is an agent program that runs sessions on an agent pod, and every session binds to a slot of a claimed pod, where the runtime supervisor launches a fresh runtime process after materialization and setup. Every runtime therefore has a supervisor, a workspace, a session volume, slots, checkpoints, and a per-session lifecycle, and every pod follows the layout of [PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint).

The `type` and `executionMode` fields carry one value each after the removal, so they leave the `Runtime` resource, the pool and pod resources, the admin API, the runtime and session rows, discovery, and `sessionIsolationLevel` (O1, O2). A write that still names one is refused with an error that names the field (O3). The pool field `maxConcurrent` leaves with service mode; 0118 had planned to rename it `maxConcurrentRequestsPerPod`, and the rename never reached the tree.

The runtime protocol has one frame contract. A runtime process serves one session, so `startId` leaves `session_start` and `session_started`, and no rule for several sessions on one connection remains. No frame carries `sessionId` except `session_start`, which keeps it as data the runtime reads: to correlate its logs with the platform's, to keep one identity across restarts of its process, to build idempotency keys for actions outside the session, and to detect that its session was derived. The adapter never acts on it. A runtime that still writes `sessionId` on another frame is unaffected, because the adapter ignores an unknown member silently (O5).

Routing has one path: create, claim, and bind. Tenant-affinity routing, the `/v1/stateless/{pool}` route, the service-mode tenant pin, the service-mode listener, and the service-mode scaling formula leave. Egress has no pod without a session binding apart from warm and pinned idle pods, so every runtime process runs under a name-constrained trust anchor, and the egress design's proposal 0 is withdrawn rather than built.

Every refusal that existed for these modes leaves: the service-mode tool refusal, SD-P4's `target_unsupervised`, DR-8's export refusal on an unsupervised target, the `type: mcp` delegation refusal `target_not_an_agent`, the `allowDelegation`, `integrationLevel`, and `agentInterface` refusals on `type: mcp`, the service-mode refusals of the user git identity and user credential designs, and the service-mode clauses of tenant scoping, placement, and tenant security settings. One general check replaces SD-P4's fail-closed property: at the post-chain point of every create, derive, and delegated child, the final runtime's row must be `registered`, and the tenant-derived runtimes design owns the check (O8).

A user who hosted an MCP server as a runtime runs it as an operator service that agent runtimes reach through egress, or has an agent runtime launch it. A user who ran a stateless agent as a service runs it in session mode, where a pool with several slots per pod gives density, or runs it outside Lenny as an operator service when it needs no agent session ("AR-6").

## Requirements

| # | Requirement |
| :-- | :-- |
| ARR-1 | The `Runtime` resource, the admin API, the runtime row, and discovery carry no runtime type. Every runtime is an agent runtime (O1). |
| ARR-2 | No resource, row, response, or interface carries an execution mode. Every session binds to a slot of a claimed pod (O2). |
| ARR-3 | A write to the admin API, the bootstrap seed, or `lenny-ctl runtime validate` that names a removed field (a runtime's `type` or `executionMode`, a pool's `executionMode` or `maxConcurrent`, or an environment's `mcpRuntimeFilters`) is refused with `400 VALIDATION_ERROR` naming the field (O3, D6). A member named `type` elsewhere in the same document, such as `agentInterface.inputModes[].type` or `sharedAssets[].type`, is accepted. |
| ARR-4 | The gateway serves no `/mcp/runtimes/{name}` route and no `/v1/stateless/{pool}` route. A request to either answers `404`, the answer the gateway's router gives a path it does not mount. |
| ARR-5 | `session_start` and `session_started` carry no `startId`. The adapter writes one `session_start` per runtime process and reads one `session_started` in answer (D2). |
| ARR-6 | No rule for several sessions on one runtime connection remains. A session-scoped frame's session is its connection's slot's session (RPR-18). No frame other than `session_start` carries `sessionId`, the adapter ignores the member silently on any other frame, and it never acts on the `sessionId` of `session_start` (O5, D5). |
| ARR-7 | Platform tools reach every runtime process. No pod refuses them for its execution mode. 0119.S2 removes the refusal; the tool calls on frames of [`0139-runtime-protocol`](../0139-runtime-protocol/steps.md#steps) (0139.S2) deliver the per-slot path, and that step tests it. |
| ARR-8 | `netagent` issues the name-constrained trust anchor on every agent pod. [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions) took this requirement as its decision 62, and 0127.S2, which adds `netagent`, delivers and tests it. |
| ARR-9 | Every runtime's sessions can be idle-suspended and become dormant, subject only to their checkpoint policy. 0119.S1 removes the idle exemption by runtime type; the dormant state arrives with [`0146-session-lifecycle`](../0146-session-lifecycle/steps.md#steps) (0146.S1), which delivers and tests the dormancy half. |
| ARR-10 | A derive does not compare execution modes, and no derive or delegation is refused for a target's lack of a runtime supervisor. The final runtime row of every create, derive, and delegated child is `registered` (O8). The second sentence is DR-4's check: [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/steps.md#steps) (0147.S4) delivers and tests it, and no step of this change builds it. |
| ARR-11 | `sessionIsolationLevel` carries neither `executionMode` nor `conversationContinuity`, and `podReuse` and `residualStateWarning` are true only for recycling pools and pools with `maxConcurrentSessionsPerPod` above 1 (O4). |
| ARR-12 | Pool scaling uses the session-mode formula for every pool, with `mode_factor` from recycling and slots alone and one `safety_factor` per tier. |

What becomes of the member once the runtime row carries no type is open decision 2 in `decisions.md`; 0119.S4 waits on it.

### AR-2 Service mode

**What leaves.** `executionMode` (O2) and its `service` value, with:

- `maxConcurrent` on the pool, the `PodSet`, the pool store, and the admin API, and the `max_concurrent` column. 0118's PL-9 had planned to rename the field `maxConcurrentRequestsPerPod`; 0119.S2 lands before that rename, so the name never ships;
- the service-mode slot, the service-mode session contract, and the claimless path through create, start, claim, and launch;
- tenant-affinity routing, the gateway's in-memory tenant-to-pod map, its EndpointSlice watch, the `/v1/stateless/{pool}` route, and the packages `tenantaffinity`, `statelessproxy`, `statelessrouting`, and `statelessslot`;
- the egress design's proposal 0: the durable service-mode tenant pin, the label arbitration, the UID-keyed router, the snapshot age limit, the service-mode listener in the adapter with its pod-UID check, the agent ingress and gateway egress rows, the §28 register entry, the §12.8 retirement of service-mode pods before their pin records, the §12.9 classification of pin records, and the §25.11 rebuild of pin records from pod labels;
- the service-mode scaling formula, its demand signal, and the metrics `lenny_service_requests_total` and `lenny_service_concurrent_active`; the experiment metrics' `session_type` label loses its meaning and leaves;
- the service-mode case of the admission webhook's termination-grace floor;

- `INCOMPATIBLE_RUNTIME` and the derive's mode equality;
- the service-mode pod of PL-1, the launch at pod start, and the service-mode `AgentPod` column of §4.7.10;
- the service-mode tool refusal (RP O10, RPR-8) and the service-mode `sessionId` rule (RP-3, MD-24);
- every service-mode refusal and clause listed under "Designs", and the service-mode half of build phase 12c.

**What stays.** Pods with several slots, `maxConcurrentSessionsPerPod`, `acknowledgeSharedPod`, recycling, tenant pinning of session-mode pods and its label webhook, and the claim queue. The gateway subsystems' `maxConcurrent` settings are unrelated and stay.

### AR-3 Runtime protocol frames

**`startId` leaves (D2).** Under [SI D4](../0145-session-isolation/decisions.md#decisions) a runtime process receives one `session_start` in its life, so `startId` tells apart nothing on a session-mode pod, and service mode was the one case that might have needed it **[source]**. The adapter writes `session_start` without `startId`, the runtime answers `session_started` without it, and §28.5.3's rule that the adapter drops a `session_started` whose `startId` is not that of the open sequence becomes a rule that the adapter accepts the first `session_started` after the `session_start` it wrote and drops any later one with a `runtime_warning`. A `session_started` that arrives before the adapter wrote `session_start` is dropped with the same warning, and the gateway emits that warning at most once per session, as "MD-24" bounds the warning for an unknown frame type. A runtime that still sends `startId` is handled under the leniency rules of "MD-24": the member is an unknown member of a known frame and is ignored with no report **[design]**. `schemas/lenny-adapter-jsonl.schema.json` stops requiring it, and its examples drop it.

**No multiplexing remains.** The "Remaining multi-session rules" of RP-3 lose both of their entries, so the section leaves. The runtime SDKs' tables that route frames by `sessionId` and answer duplicate starts leave, because a process serves one session.

**`sessionId` only on `session_start` (O5 (b), D5).** No frame other than `session_start` carries `sessionId`. The JSONL schema drops the member from every other frame, the SDKs stop writing it, and the frame examples of the specification and the message delivery design drop it. A runtime that still writes it on another frame is unaffected, because the adapter ignores an unknown member silently; the adapter takes the frame's session from its connection's slot (RPR-18). `session_start` keeps `sessionId` as data the runtime reads: the identifier it logs under so that support can correlate its logs with the platform's, an identity that survives a restart of its process, the key it builds idempotency keys from for actions outside the session, and the value that tells it its session was derived, because a derived session has a new identifier over a restored workspace. The adapter never acts on it **[design]**.

**Tools on every pod.** RPR-8 becomes "Platform tool calls reach the gateway from every runtime process", and RP-4's `toolServers` lists `platform` for every session, which is its only value since CR-1 of [`0124-connector-removal`](../0124-connector-removal/change.md#cr-1-removal) removed connector tool servers.

### AR-4 Admission of removed fields

**Refusal (O3).** The admin API's runtime, pool, and environment writes, creates and updates alike, the bootstrap seed, and `lenny-ctl runtime validate` refuse a document that names a removed field (a runtime's `type` or `executionMode`, a pool's `executionMode` or `maxConcurrent`, or an environment's `mcpRuntimeFilters`) with `400 VALIDATION_ERROR`, whose `details.field` names the member and whose message reads, for example, "`type` was removed: Lenny runs agent runtimes in session mode only" **[design]**. The refusal holds whatever value the member carries, `agent` and `session` included, so a document is either current or refused. The CRDs drop the fields from their structural schemas; whether `kubectl apply` refuses an unknown field under its default field validation is owed ("Validation owed" in `steps.md`). What a `Runtime` or `PodSet` resource that names a removed field becomes when it reaches the API server through a client that does not ask for strict field validation is open decision 4 in `decisions.md`.

**Stored data.** Lenny has no deployments, so no stored resource or row carries a `type: mcp` runtime or a service-mode pool **[source]**. A new migration drops `runtime_definitions.type` with its CHECK constraint, `runtime_definitions.execution_mode` with its CHECK constraint, `runtime_definitions.restartable` (migration `0189_runtime_restartable`), `pools.max_concurrent`, `pools.execution_mode` (migration `0033_sandbox_warm_pools`, on the table that `0198_pools_rename` renamed), `sessions.execution_mode`, `sessions.conversation_continuity` (migration `0168_session_conditions_conversation_continuity`), and the pod-registry and agent-pod-state `execution_mode` columns. Applied migrations are not edited, because the migration tests read the chain as written **[inference]**. The backup export stops writing the columns.

**Phase 3 gate.** The migration drops columns, so it begins with the preflight block that [§10.5](../../spec/10_gateway-internals.md#105-upgrade-and-rollback-strategy), **Phase 3 enforcement gate (required):**, requires, as migrations `0167` and `0180` do. The block aborts the migration when a `runtime_definitions` row has `type <> 'agent'` or `execution_mode <> 'session'`, or a `pools` row has `execution_mode = 'service'` or `max_concurrent > 0`, so a development or test database that holds a `type: mcp` runtime or a service-mode pool fails the migration instead of keeping the row with its distinguishing column gone. The down file restores each dropped column with its earlier type, default, and CHECK constraint; it restores no values, and a restored `restartable` column holds its default until the RuntimeReconciler writes the row again.

**Why a refusal rather than silence.** A silent drop would register an MCP server image as an agent runtime, and the error would surface at the first bind as a handshake failure that names no field (O3).

**One rule in every design (D6).** The owner made O3's refusal the rule for every field a design removes. A write that names a removed field is refused with `400 VALIDATION_ERROR`, whose `details.field` names the member, whatever its value. The LLM response cache removal design applies it to `cachePolicy` and `cacheScope` (its O3), and the LLM upstreams design's LU-4 applies it to `deliveryMode`, `credentialPolicy`, `supportedProviders`, `credentialCapabilities`, and the other fields it removes. Each design lists its own removed fields, and the admin validator holds one list of removed fields keyed by resource and JSON path, so each refusal is one entry in the same check **[design]**. A list of bare names would refuse valid writes, because `type` is a live member elsewhere in a runtime document (`agentInterface.inputModes[].type`, `sharedAssets[].type`) and on other admin resources, and `maxConcurrent` names unrelated gateway subsystem settings. Whether strict decoding of every admin write and seed replaces the list, with the list kept only for the "was removed" message, is open decision 3 in `decisions.md`.

**Which step refuses which field.** D6 makes the refusal part of each removal, so the step that removes a field lands its refusal: 0119.S1 refuses an environment's `mcpRuntimeFilters`, 0119.S2 refuses a pool's `maxConcurrent`, and 0119.S4 refuses a runtime's `type` and `executionMode` and a pool's `executionMode`. A pool write that names `maxConcurrent` is therefore never ignored between 0119.S2 and 0119.S4.

### AR-5 What simplifies in the other designs

- **One pod layout.** Every pod is the session-mode pod of PL-1: the adapter, `netagent`, and one slot container per slot with the supervisor and the runtime. PL D6 is moot, because every runtime container is a slot container. PLR-2's `command` on every runtime holds without its `type: mcp` clause.
- **Every runtime has a supervisor, a workspace, and slots.** SD-P4's supervisor refusal and DR-8's export refusal have no target left, so both leave, and `target_unsupervised` leaves the derive refusal reasons. The stale-row concern they carried moves to a general check (O8). DR's grant condition that the base is `type: agent` and `executionMode: session`, and DR decision 10 on service-mode bases, leave.
- **One frame contract.** "AR-3".
- **One routing path.** Every session is created, routed through the `PreRoute` chain, claimed, and bound. A derive compares no execution modes.
- **No trust-anchor exception.** `netagent` issues the name-constrained anchor on every agent pod, because no runtime process runs before its session's binding. The rule that the TLS interception bundle is per deployment or pool stays, because warm-up work still runs before any tenant.
- **No service-mode egress pod model.** The "Pod models" table of the egress design loses its service-mode row. The pods bound to a tenant without a session are then pinned idle pods and warm pods of tenant-owned pools.
- **No E = ∅ rule for service mode.** Tenant scoping's "Pods with no per-session policy" keeps only concurrent pods, and only where the per-slot attribution of EG decision 60, settled as (a) on 2026-11-13, is unavailable.
- **One stale-row check.** SD-P4 and DR-8's export refusal leave, and DR-4 checks at the post-chain point that the final runtime row of every create, derive, and delegated child is `registered`, and that a platform-derived runtime's base row is too, under its "Registered rows" paragraph (O8).
- **Fewer refusals.** The service-mode rows of the user git identity, user credential delivery, placement, and tenant security settings designs leave. The account-link check of [UC-3](../0151-user-credential-delivery/change.md#uc-3-the-usercredential-binding) applies to every session.
- **Every session can become dormant.** SL-6's exceptions leave; the checkpoint policy alone decides.
- **One scaling formula and one `safety_factor` per tier.**
- **`restartable` leaves.** `Spec.Restartable()` returns true for a runtime with `command`, `executionMode: session`, and no `preConnect` **[source]**. PLR-2 requires `command` on every runtime, PL-8 removes `preConnect`, and this design removes `executionMode`, so the flag is always true, and its reader, `recycle.runtimeProcess: restart`, left with SI D4 **[source]**. The flag, its mirror into the runtime registry, and `runtime_restartable.go` leave. In the tree the flag is neither constant nor unread until those changes land: `Restartable()` still reads `command` and `preConnect`, and `pkg/controller/agentpod/supervision.go`, `pkg/runtime/poolstore` (`ValidateRuntimeProcessRestartable`), and `pkg/gateway/api/admin/pools.go` read it. 0119.S4 therefore removes the flag only after 0118.S1 (`command` required), 0118.S2 (`preConnect` removed), and 0145.S3 (the retirement of `keep` with its reader) have landed.

### AR-6 What users of the removed modes do instead

- **An MCP server reachable over the network.** Run it as an operator service. The harness of an agent runtime reaches it as an MCP client through the pod's egress, the runtime's own configuration names its URL, and a credential binding on its host attaches the credential ([`0124-connector-removal`, "CR-3 External services"](../0124-connector-removal/change.md#cr-3-external-services)). Lenny keeps no record of the service, and the service owns its tool rules, approvals, and per-call audit. [§9.3](../../spec/09_mcp-integration.md#93-connector-definition-and-oauthoidc) is a successor pointer to that design's CR-1, and the catalog sentence of [§26.1](../../spec/26_reference-runtime-catalog.md#261-catalog-overview) states this path ("Specification changes").
- **An MCP server on a customer's private network.** An agent runtime reaches it over the pod's egress through the tenant outbound connector, on an outbound connector route ([`0148-tenant-outbound-connector`, "Scope"](../0148-tenant-outbound-connector/change.md#scope); [`0124-connector-removal`, "CR-3 External services"](../0124-connector-removal/change.md#cr-3-external-services)).
- **An MCP server that needs Lenny's isolation, workspace, and credentials.** Package it with an agent runtime that launches it as a stdio MCP server inside the slot, as harnesses such as Claude Code launch configured servers. It then runs under the slot UID with the session's workspace, egress, and credentials **[inference]**.
- **A stateless agent served as a replicated service.** Run it in session mode. A pool with `maxConcurrentSessionsPerPod` above 1 and `acknowledgeSharedPod` serves several sessions per pod, and recycling reuses pods across sessions. Each session gets its own process, workspace, and egress scope, which service mode did not give. An agent that needs no session at all runs outside Lenny as an operator service, which agent runtimes reach through egress (CR-3).

## Limits

- **Session cost for stateless work.** Each request that service mode served from a running process now costs a claim, a bind, materialization, and a process launch. The owner noted on 2026-11-12 that runtime start-up times are small and need no validation **[source]**.
- **No hosted MCP servers.** Lenny no longer runs an unmodified MCP server in a pod it manages (O6).
- **Client-visible removals.** `mcpEndpoint`, `executionMode`, and `conversationContinuity` leave public responses and the client SDKs. No client depends on them **[source]**.

## Alternatives rejected

- **Keep `type: mcp` and remove service mode alone.** `type: mcp` keeps the second pod rendering, the adapter's MCP client, the dedicated endpoint, the `ToolAnnotations` path at registration, the discovery fields, the delegation refusal, and the idle and safety-factor exceptions, for a mode whose endpoint has never served a call in production **[source]**.
- **Keep service mode as session mode with zero-cost binds.** It would need the claimless routing and the tenant pin that the egress design's proposal 0 builds, which is what this design removes.
- **Keep the fields with one value.** O1 (b) and O2 (b).

### What the documentation states

The owner asked on 2026-11-13 that every design's documentation list every setting, default, limit, failure mode, and runtime-facing rule it introduces. Published pages cite no specification section numbers.

- **Runtime kinds.** `docs/getting-started/concepts.md`, `docs/runtime-author-guide/index.md`, and `docs/about/why-lenny.md` state that Lenny runs agent runtimes, each session on a slot of a claimed pod, and that MCP stays as the client-facing protocol, the tool protocol of the reference bridge, and the protocol a harness speaks to operator services through egress.
- **Alternatives for the removed modes.** `docs/runtime-author-guide/index.md` and `docs/operator-guide/configuration.md` state the paths of "AR-6": an MCP server reachable over the network runs as an operator service that a runtime's harness reaches through egress, with the page on reaching operator services that [`0124-connector-removal`](../0124-connector-removal/change.md#changes-to-lennys-documentation) adds; one on a private network is reached through the tenant outbound connector from an agent runtime; one that needs Lenny's isolation runs as a stdio server launched by an agent runtime inside its slot; a stateless agent runs in session mode, with `maxConcurrentSessionsPerPod` above 1 and `acknowledgeSharedPod` for density.
- **Refusal of removed fields.** `docs/reference/configuration.md`, `docs/reference/error-catalog.md`, `docs/api/admin.md`, and `docs/runtime-author-guide/publishing.md` state that a runtime, pool, or environment write, a bootstrap seed, or `lenny-ctl runtime validate` that names a removed field (a runtime's `type` or `executionMode`, a pool's `executionMode` or `maxConcurrent`, or an environment's `mcpRuntimeFilters`) is refused with `400 VALIDATION_ERROR` whose `details.field` names the member, whatever its value, `agent` and `session` included.
- **Removed routes.** `docs/api/rest.md` and `docs/api/mcp.md` state that `/mcp/runtimes/{name}` and `/v1/stateless/{pool}` do not exist, and drop `mcpEndpoint` from `GET /v1/runtimes`, `list_runtimes`, and `lenny/discover_agents`.
- **Client-visible fields.** `docs/client-guide/session-lifecycle.md` and `docs/api/rest.md` drop `executionMode` and `conversationContinuity` from `sessionIsolationLevel`, and drop `INCOMPATIBLE_RUNTIME` from the derive's refusals.
- **The stale-row refusal.** `docs/api/rest.md` and `docs/runtime-author-guide/delegation.md` state that a create, a derive, or a delegated child whose final runtime row is not `registered`, or whose platform-derived runtime's base row is not, is answered as an unknown runtime: `404 RESOURCE_NOT_FOUND`, or `TARGET_NOT_IN_SCOPE` for a delegated child, as DR-4's "Registered rows" states; and that a resume is not refused (O8).
- **Runtime-facing frame rules.** `docs/reference/adapter-contract.md` and `docs/runtime-author-guide/lifecycle.md` state that `session_start` and `session_started` carry no `startId`; that the adapter accepts the first `session_started` after its `session_start` and drops a later one with a `runtime_warning`; that no frame other than `session_start` carries `sessionId`; that `session_start`'s `sessionId` is the runtime's to read, for log correlation, identity across process restarts, idempotency keys, and derived-session detection, and the adapter never acts on it; and that a runtime that still writes `startId` or `sessionId` where it no longer belongs is unaffected, because an unknown member is ignored with no warning while an unknown frame type produces a `runtime_warning`.
- **Isolation and idle behaviour.** `docs/reference/state-machines.md`, `docs/reference/cloudevents-catalog.md`, and `docs/client-guide/webhooks.md` state that every session can be idle-suspended and become dormant under its checkpoint policy, and `docs/operator-guide/namespace-and-isolation.md` and `docs/operator-guide/multi-tenancy.md` drop tenant-affinity routing and state that `netagent` issues a name-constrained trust anchor on every agent pod.
- **Scaling.** `docs/operator-guide/configuration.md`, `docs/operator-guide/scaling.md`, and the capacity pages state one `safety_factor` per tier and one scaling formula.
- **Metrics.** `docs/reference/metrics.md` drops the `session_type` label and the metrics `lenny_service_requests_total` and `lenny_service_concurrent_active`.
- **Other pages that name the removed modes.** `docs/about/comparisons.md` (the successor of §23) restates its runtime-type rows; `docs/operator-guide/security-principles.md`, `docs/runtime-author-guide/platform-tools.md`, `docs/operator-guide/web-playground.md`, and the tutorials `build-a-runtime.md`, `deploy-to-cluster.md`, `evaluation-scoring.md`, `recursive-delegation.md`, and `session-derive-replay.md` drop their `type: mcp`, service-mode, `executionMode`, and `startId` mentions.
- **Readers.** Client: `docs/api/rest.md`, `docs/api/mcp.md`, `docs/client-guide/session-lifecycle.md`, and `docs/client-guide/webhooks.md`. Operator: `docs/operator-guide/`, `docs/api/admin.md`, `docs/reference/configuration.md`, `docs/reference/metrics.md`, and `docs/reference/error-catalog.md`. Every reader: `docs/getting-started/concepts.md`, `docs/about/`, `docs/reference/state-machines.md`, and `docs/reference/cloudevents-catalog.md`.
- **Changelog.** A removal note in the root `CHANGELOG.md` names each removed field, route, frame member, metric (`lenny_service_requests_total` and `lenny_service_concurrent_active`), error (`target_not_an_agent`, `INCOMPATIBLE_RUNTIME`, and `target_unsupervised`), and the renamed headings of O7.
