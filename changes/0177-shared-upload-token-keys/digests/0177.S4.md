## Defaults applied

- **The empty-digest rule, settled from the tree.** Every path that issues a token records its digest (`mintUploadToken` in `create.go` and `mintClaimStartPersist` in `create_and_start.go`); the rows that record none are those of delegated child sessions and single-shot sessions, which are issued no token. A row with no recorded digest therefore refuses every token with `401 UPLOAD_TOKEN_INVALID`, and §7.1 states it. A missing row still returns nil to the caller's own lookup, as before (UPLOAD-I12).
- The digest check runs before the consumed check, so a forged token for a consumed session is `401 UPLOAD_TOKEN_INVALID` and the issued token `410 UPLOAD_TOKEN_CONSUMED`.
- Create-and-start records `upload_token_consumed_at` equal to the row's `created_at`, in the row's insert (`pgstore` gains the column in its insert list); no migration.
- `Insert` keeps the earlier of the stored and the new value for both `retire_after` and `delete_after`; decision 11 names `delete_after`, and keeping `retire_after` too is what stops a rewrite from reviving the replaced key.
- A ring whose newest key carries a retirement instant (its successor's row was deleted) writes that slot again one publish lead ahead on its next refresh and signs nothing until the key activates; `Open` in that state writes the slot and starts without a signing key rather than refusing to start. The all-rows-deleted path keeps the backdated first key (UPLOAD-I13).
- The route is `POST /v1/admin/upload-token-keys/rotate`, following the collection-and-action form of `/v1/admin/erasure-jobs/{jobId}/retry` and the noun of `/v1/admin/audit-receipt-keys`; `platform-admin` only (`requireAdmin`); OpenAPI scope `tools:platform:write`, category `security`, MCP tool `admin.rotate_upload_token_keys` classified as a mutation; no `dryRun`; registered only when a ring is wired.

- **Decision 13, defaults.** The refusal reuses the catalog code `INVALID_STATE_TRANSITION` (`409`, `PERMANENT`, not retryable) with `details.keyId` and `details.activeFrom` (RFC 3339) of the pending key, and writes no `Retry-After`. The kind of rotation is recorded in a new column, `platform_signing_keys.forced` (`BOOLEAN NOT NULL DEFAULT false`, migration 0207), which `Store.Insert` writes and `Store.List` reads, and which `MemoryStore` carries in `Record.Forced`. A call whose reload succeeds and that is refused still installs the reloaded snapshot. A refusal is a `*signingkeys.ForcedRotationPendingError` matching `signingkeys.ErrForcedRotationPending`. The incident procedure waits one publish lead (`sleep 120` at the default) between its two calls.
- **The UPLOAD-I15 wording.** §7.1 states that a replica never signs with a key after the retirement instant it has loaded for that key, and that a replica that has not loaded it signs until its last reload is as old as the stale bound, at most the stale bound minus the publish lead after the retirement instant (3 minutes at the defaults), the bound `StaleMintBounded` checks.
