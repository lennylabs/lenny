## Defaults applied

- The receipt signing alias is `platform:audit-signing`, with the optional `platform:audit-verify` for the previous key, as for the JWT keys (O4 option (a)). No `kms.Provider` lookup of a public key by key identifier was added, which departs from SK-6's "a lookup of a public key by key identifier".
- The key identifier a receipt records is the reference the alias maps to in `--kms-alias`; when the local provider leaves the alias unmapped, it is the alias name.
- The gateway loads the receipt keys at startup and does not start without them, as for the JWT key set, so a cloud deployment must map `platform:audit-signing`.
- `GET /v1/admin/audit-receipt-keys` answers `{"keys":[{"keyId","alg":"ES256","jwk":{...}}]}`, sorted by key identifier, under the audit reader gate (tenant-admin, scope `tools:audit:read`); with no key set wired it answers an empty list.
- The periodic receipt scan checks the signature and the row binding; the `original_hash` match stays with the chain verifier.
- The upload-token KEK alias is `platform:upload-token-signing`, as SK-2 names it; on a cloud provider it must be mapped, and the gateway does not start without it.
- Gateway flags `--signing-key-refresh-interval` (default 30 s), `--signing-key-publish-lead` (default 2 minutes), and `--upload-token-key-rotation-interval` (default 24 hours); the chart sets none of them. §7.1 now states the first two defaults.
- The stale bound and the verification time of a replaced key are both `uploadtoken.DefaultOverlapWindow` (5 minutes), with no flag (O5 option (a), UPLOAD-I3).
- Rotation is due when the newest key has been active for the rotation interval, and the next key activates one publish lead after the write; the rotation slot is the previous key's slot plus one.
- The first key is written active at once, backdated by the publish lead.
- A gateway without Postgres, or with the local KMS provider and no master key file, keeps its upload-token keys in memory, because no other process could unwrap them; §7.1 states it.
- The consumed check reads the session row after the token verifies, through a new read by primary key in the session core: the upload path's existing row read is in the upload handler, and `GWSEAM-VerifyUploadToken` gained the request's tenant to read it. A row the store does not hold carries no mark, so the caller's own lookup reports the missing session; any other read failure answers `500 INTERNAL_ERROR`.
- The finalize ready write records the consumed mark whether or not the row carries a token digest, and a store write never clears a set mark (`COALESCE` in the Postgres store, a floor in the memory store).
- A failed mint because the ring refuses to sign is reported as a TRANSIENT error on the creation span and answers `503 SESSION_CREATION_FAILED` with the existing reason `upload_token_issuance_failed`.
- The per-process `uploadtoken.Rotator` and the consumed-tracker sweep are removed; `uploadtoken.MemoryTracker` stays for tests.
- The migration is 0205, after change 0176's 0204.
