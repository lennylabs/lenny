# Decisions: 0177 Shared signing keys for upload tokens and redaction receipts

## Open decisions

- **O4. Which receipt signing keys a chain verifier trusts after more than one rotation (raised while building 0177.S1, 2026-11-26).** SK-6 has the verifier read the public key for the identifier a receipt records, and leaves open which identifiers it may read. Reading any identifier the receipt names would let a database writer insert a receipt signed by a KMS key in an account or project the writer controls, so the verifier needs a trusted set. Receipts are kept for `audit.gdprRetentionDays` (default 2555 days), so the set has to outlive several rotations. Options:
  - (a) The keys that `platform:audit-signing` and an optional `platform:audit-verify` name, as §10.2 does for the JWT signing key. A receipt signed two rotations ago no longer verifies and reads `broken`, unless the operator keeps mapping the old key under `platform:audit-verify`. No new setting.
  - (b) Option (a) plus a gateway setting listing the KMS key identifiers of retired receipt keys, each read through a new `kms.Provider` lookup of a public key by key identifier (the lookup SK-6 names). Every receipt verifies for as long as its key stays in the KMS and in the list.
  - (c) Any identifier naming another version of the key `platform:audit-signing` names (GCP and Azure key versions). AWS asymmetric keys have no versions, so a rotation on AWS would still need (a) or (b).

  Recommendation: (b), because receipts outlive more than one rotation and (b) keeps the trusted set explicit. The branch builds (a), which needs no new setting, and records it in the digest's "Defaults applied"; (b) adds the setting and the lookup on top of it.
- **O5. The stale bound and the verification time against the token lifetime (raised by the review of 0177.S1, 2026-11-26).** Decision 4 stops minting once a replica's last reload is older than the overlap window (5 minutes), and a replaced key verifies for the same overlap window after the next key becomes active. A replica whose last reload was at t0 keeps signing with the old key until t0 + 5 minutes when a peer publishes the next key just after t0; the peers delete the old key at t0 + 2 minutes (the publish lead) + 5 minutes, and the tokens the stale replica minted are valid until t0 + 10 minutes, so for about three minutes the peers refuse tokens that have not expired with `401 UPLOAD_TOKEN_INVALID`. The same holds on healthy replicas when the token lifetime (`maxCreatedStateTimeoutSeconds`) is set above the overlap window. Options:
  - (a) Keep decision 4 as built: the stale bound and the verification time are both the overlap window, and the refusal window above is accepted.
  - (b) Lengthen the verification time of a replaced key to the overlap window plus the stale bound (10 minutes at the defaults), so every token a replica can mint verifies on its peers until it expires, and refuse to start when the token lifetime exceeds the overlap window.
  - (c) Shorten the stale bound to the overlap window minus the publish lead (3 minutes at the defaults), with a startup check that the publish lead is shorter than the overlap window.

  Recommendation: (b), because it keeps decision 4's bound and closes the window by keeping a retired key a few minutes longer, which costs nothing a token holder can use after expiry. The branch builds (a).
- **O6. Whether a chain verifier checks a redacted row's content against the receipt's `new_hash` (raised by the review of 0177.S1, 2026-11-26).** The verifiers accept a redacted row whose receipt signature verifies and whose `original_hash` matches, and do not compare the row's current content hash with the signed `new_hash`. A writer with the `lenny_erasure` grant on the payload columns, or a database administrator, can rewrite an already-redacted row again to any payload that keeps the redaction marker, and the row still reads `redacted_gdpr`. §12.8 step 14 says `new_hash` is recorded for provenance and is not consulted for link continuity. Options:
  - (a) The chain verifier and the periodic receipt scan also require the row's recomputed content hash to equal the receipt's `new_hash`, and §12.8 states it.
  - (b) Keep the receipt check as built, and record that a second rewrite of a redacted row is outside what the receipt detects.

  Recommendation: (a). The branch builds (b), and issue AUDIT-I5 tracks the gap.

## Decisions

1. **A change for a shared key ring and a shared consumed-token tracker (IK-4).** The per-replica upload-token key ring and consumed tracker are replaced by shared ones, through a change whose design the owner reviews before it is settled, with the choice between Redis, Postgres, or both. The change lands before the milestones that run several gateway replicas. Owner's answer to IK-4 on the M3 readiness decision page, 2026-11-25, option (a), with the words "but I would like to see the design first (Redis, Postgres, or both)". The question arose from the review of change [0173](../archive/2026-11-25-0173-idempotency-stored-credentials/change.md), whose replay rebuilds a token only on a replica whose ring holds the signing key.
2. **The redaction receipt signer is fixed in this change, reusing its mechanism where possible (AUDIT-I2).** The dead-letter redaction receipt signer, whose key is generated per process and discarded ([AUDIT-I2](../../issues/AUDIT/AUDIT-I2-redaction-receipt-signing-key-per-process.md)), is fixed together with the per-replica upload-token keys ([UPLOAD-I1](../../issues/UPLOAD/UPLOAD-I1-upload-token-keys-and-consumed-state-per-replica.md)), and ideally reuses the same mechanism. Owner's direction in chat, 2026-11-25, with the words "Solve the `deadletterredaction` issue along with the other one, and ideally reuse the mechanism." Whether the receipt signer reuses the shared store or signs in the KMS as §12.8 states was open decision O3, which decision 5 settles.
3. **The store for the signing keys and the consumed state (O1).** Postgres only. The upload-token signing keys sit in the platform table `platform_signing_keys`, keyed by purpose (SK-2), each envelope-encrypted under its purpose's KMS alias, `platform:upload-token-signing` for upload tokens, and the consumed state is the column `sessions.upload_token_consumed_at`, set in the `finalizing` → `ready` write of `FinalizeWorkspace` (SK-3). The options not chosen were (b), Redis only, with the keys in Redis under the same alias and the consumed state as a `SET NX` of the digest with a TTL, and (c), both, with the keys in Postgres and the consumed state in Redis. Owner's answer to UK-1 (open decision O1) on the M3 readiness decision page, 2026-11-26, option (a).
4. **The behavior when the ring cannot be refreshed (O2).** A replica that cannot refresh its key ring for longer than the upload-token overlap window stops minting upload tokens, so session creation on that replica answers `503`, while it keeps verifying with the loaded ring (SK-4). The option not chosen was (b), minting with the last loaded active key for as long as the process runs and relying on peers that hold the same ring. Owner's answer to UK-2 (open decision O2) on the M3 readiness decision page, 2026-11-26, option (a).
5. **The key that signs redaction receipts (O3).** Redaction receipts are signed inside the KMS with an ES256 key under a platform audit signing alias, through `kms.Provider.Sign` as the §10.2 JWT signer does, and `signature_kms_key_id` records the KMS key and its version (SK-6). The shared store holds no receipt purpose, so it serves upload tokens only, and the fix for the receipt signer ([AUDIT-I2](../../issues/AUDIT/AUDIT-I2-redaction-receipt-signing-key-per-process.md), [AUDIT-I3](../../issues/AUDIT/AUDIT-I3-chain-verifier-accepts-unverified-receipt-signatures.md), and [AUDIT-I4](../../issues/AUDIT/AUDIT-I4-receipt-signing-key-reference-is-undefined.md)) uses the KMS signing path rather than the shared store. This settles decision 2's preference for reusing the mechanism: the receipt signer reuses the KMS signing path of the §10.2 JWT signer rather than the shared store. §12.8 keeps its text, with the §11.7 parenthetical replaced by the alias's name. The options not chosen were (b), the shared store with an HMAC key under a `redaction-receipt` purpose, which removes the public key and the external verification §12.8 states, and (c), the shared store with an ES256 key pair under a `redaction-receipt` purpose, whose private key is wrapped under the KEK and used in gateway memory. Owner's answer to UK-3 (open decision O3) on the M3 readiness decision page, 2026-11-26, option (a).
6. **Coverage waiver for 0177.S1.** The floor of 80% is waived for the changed lines the unit tier cannot reach: the Postgres store code that only the component tier runs, 133 lines in `pkg/signingkeys/pgstore/pgstore.go`, `pkg/audit/auditstore/redaction.go`, `pkg/session/sessionstore/pgstore/pgstore.go`, and `pkg/audit/auditstore/auditstore.go`; the gateway wiring that the integration tests run through the gateway binary, 35 lines under `cmd/lenny-gateway/`; and the test infrastructure in `tests/testinfra/receiptkeys/receiptkeys.go`, 22 lines. The measured coverage was 70.8% (629 of 888 lines) on gate run `d1be08fc25ecbd51726d62eb`, and 90.1% (629 of 698 lines) without those lines. Issue GATE-I14 records that the coverage check measures the unit tier alone. Owner's answer to UK-W in chat, 2026-11-26, option (a), with the words "UK-W: waived".
