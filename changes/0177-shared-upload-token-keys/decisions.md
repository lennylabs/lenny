# Decisions: 0177 Shared signing keys for upload tokens and redaction receipts

## Open decisions

- **O8. A cap on the expiry an upload token carries, and retiring a key early (UPLOAD-I6, raised by the security review of 0177.S2, 2026-11-26).** The verifier refuses a token only once the clock passes the expiry the token itself carries ([UPLOAD-I6](../../issues/UPLOAD/UPLOAD-I6-verifier-accepts-any-expiry-the-token-carries.md)), so a holder of a leaked signing key mints tokens for any session that verify on every replica until the key's row is deleted, up to a rotation interval plus the verification time, and no documented way retires a suspected key early. Options:
  - (a) §7.1 requires the verifier to refuse a token whose expiry lies further ahead than the token lifetime plus a clock-skew allowance, and the documentation, or a `lenny-ctl` command, states how to retire a key early by deleting its row and writing the next key.
  - (b) The expiry cap alone, with no early retirement.
  - (c) No change, with the limit documented.

  Recommendation: (a), so a forged token gains nothing beyond the key's own verification time and an operator can respond to a suspected leak.

## Decisions

1. **A change for a shared key ring and a shared consumed-token tracker (IK-4).** The per-replica upload-token key ring and consumed tracker are replaced by shared ones, through a change whose design the owner reviews before it is settled, with the choice between Redis, Postgres, or both. The change lands before the milestones that run several gateway replicas. Owner's answer to IK-4 on the M3 readiness decision page, 2026-11-25, option (a), with the words "but I would like to see the design first (Redis, Postgres, or both)". The question arose from the review of change [0173](../archive/2026-11-25-0173-idempotency-stored-credentials/change.md), whose replay rebuilds a token only on a replica whose ring holds the signing key.
2. **The redaction receipt signer is fixed in this change, reusing its mechanism where possible (AUDIT-I2).** The dead-letter redaction receipt signer, whose key is generated per process and discarded ([AUDIT-I2](../../issues/closed/AUDIT/AUDIT-I2-redaction-receipt-signing-key-per-process.md)), is fixed together with the per-replica upload-token keys ([UPLOAD-I1](../../issues/closed/UPLOAD/UPLOAD-I1-upload-token-keys-and-consumed-state-per-replica.md)), and ideally reuses the same mechanism. Owner's direction in chat, 2026-11-25, with the words "Solve the `deadletterredaction` issue along with the other one, and ideally reuse the mechanism." Whether the receipt signer reuses the shared store or signs in the KMS as §12.8 states was open decision O3, which decision 5 settles.
3. **The store for the signing keys and the consumed state (O1).** Postgres only. The upload-token signing keys sit in the platform table `platform_signing_keys`, keyed by purpose (SK-2), each envelope-encrypted under its purpose's KMS alias, `platform:upload-token-signing` for upload tokens, and the consumed state is the column `sessions.upload_token_consumed_at`, set in the `finalizing` → `ready` write of `FinalizeWorkspace` (SK-3). The options not chosen were (b), Redis only, with the keys in Redis under the same alias and the consumed state as a `SET NX` of the digest with a TTL, and (c), both, with the keys in Postgres and the consumed state in Redis. Owner's answer to UK-1 (open decision O1) on the M3 readiness decision page, 2026-11-26, option (a).
4. **The behavior when the ring cannot be refreshed (O2).** A replica that cannot refresh its key ring for longer than the upload-token overlap window stops minting upload tokens, so session creation on that replica answers `503`, while it keeps verifying with the loaded ring (SK-4). The option not chosen was (b), minting with the last loaded active key for as long as the process runs and relying on peers that hold the same ring. Owner's answer to UK-2 (open decision O2) on the M3 readiness decision page, 2026-11-26, option (a).
5. **The key that signs redaction receipts (O3).** Redaction receipts are signed inside the KMS with an ES256 key under a platform audit signing alias, through `kms.Provider.Sign` as the §10.2 JWT signer does, and `signature_kms_key_id` records the KMS key and its version (SK-6). The shared store holds no receipt purpose, so it serves upload tokens only, and the fix for the receipt signer ([AUDIT-I2](../../issues/closed/AUDIT/AUDIT-I2-redaction-receipt-signing-key-per-process.md), [AUDIT-I3](../../issues/closed/AUDIT/AUDIT-I3-chain-verifier-accepts-unverified-receipt-signatures.md), and [AUDIT-I4](../../issues/closed/AUDIT/AUDIT-I4-receipt-signing-key-reference-is-undefined.md)) uses the KMS signing path rather than the shared store. This settles decision 2's preference for reusing the mechanism: the receipt signer reuses the KMS signing path of the §10.2 JWT signer rather than the shared store. §12.8 keeps its text, with the §11.7 parenthetical replaced by the alias's name. The options not chosen were (b), the shared store with an HMAC key under a `redaction-receipt` purpose, which removes the public key and the external verification §12.8 states, and (c), the shared store with an ES256 key pair under a `redaction-receipt` purpose, whose private key is wrapped under the KEK and used in gateway memory. Owner's answer to UK-3 (open decision O3) on the M3 readiness decision page, 2026-11-26, option (a).
6. **Coverage waiver for 0177.S1.** The floor of 80% is waived for the changed lines the unit tier cannot reach: the Postgres store code that only the component tier runs, 133 lines in `pkg/signingkeys/pgstore/pgstore.go`, `pkg/audit/auditstore/redaction.go`, `pkg/session/sessionstore/pgstore/pgstore.go`, and `pkg/audit/auditstore/auditstore.go`; the gateway wiring that the integration tests run through the gateway binary, 35 lines under `cmd/lenny-gateway/`; and the test infrastructure in `tests/testinfra/receiptkeys/receiptkeys.go`, 22 lines. The measured coverage was 70.8% (629 of 888 lines) on gate run `d1be08fc25ecbd51726d62eb`, and 90.1% (629 of 698 lines) without those lines. Issue GATE-I14 records that the coverage check measures the unit tier alone. Owner's answer to UK-W in chat, 2026-11-26, option (a), with the words "UK-W: waived".
7. **The verification time of a replaced upload-token key (O5).** Option (b), with the time derived from the configured values. A replaced key verifies on every replica for the stale bound plus the longer of the overlap window and the upload-token lifetime (`maxCreatedStateTimeoutSeconds`), 10 minutes at the defaults, so every token a replica can mint, including one minted by a replica whose last reload is as old as the stale bound, verifies on every replica until it expires. Because the time follows the token lifetime, the startup refusal of a token lifetime longer than the overlap window, which option (b) named, is not needed and is not built. The overlap window, and with it the stale bound, is the constant `uploadtoken.DefaultOverlapWindow` today ([UPLOAD-I3](../../issues/UPLOAD/UPLOAD-I3-upload-token-overlap-window-has-no-setting.md)); a setting added for it changes the verification time with it. Owner's answer to UK-5 in chat, 2026-11-26, option (b), with the words "(b) but make sure the 10 min are adjusted if the other times are configured differently (I don't know if they are configurable)". The options not chosen were (a), keeping the overlap window as both the stale bound and the verification time and accepting that peers refuse unexpired tokens for about three minutes, and (c), shortening the stale bound to the overlap window minus the publish lead. The owner confirmed the derivation, without the startup refusal, in chat on 2026-11-26, with the words "UK-5: ok".
8. **A chain verifier checks a redacted row against the receipt's `new_hash` (O6).** Option (a). The chain verifier and the periodic receipt scan require the recomputed content hash of a redacted row to equal the `new_hash` its receipt signs, and §12.8 step 14 states it in place of the sentence that `new_hash` is recorded for provenance and not consulted for link continuity. Step 0177.S2 confirms whether a row can be redacted more than once, such as a row that names two subjects erased at different times; if it can, the later redaction writes a receipt whose `original_hash` is the earlier receipt's `new_hash`, so a legitimate second redaction still verifies. Owner's answer to UK-6 in chat, 2026-11-26, option (a), with the words "go with your recommendation". The option not chosen was (b), keeping the receipt check as built and recording that a second rewrite of a redacted row is outside what the receipt detects ([AUDIT-I5](../../issues/closed/AUDIT/AUDIT-I5-receipt-check-ignores-the-signed-new-hash.md)).
9. **The receipt keys a chain verifier trusts (O4).** Option (b). The chain verifier and the periodic receipt scan trust the keys that `platform:audit-signing` and the optional `platform:audit-verify` name, and the KMS key identifiers of retired receipt keys that a gateway setting lists, each read through a `kms.Provider` lookup of a public key by key identifier. A receipt verifies for as long as its key stays in the KMS and in the list, and the documentation tells an operator to keep a retired receipt key in the KMS, and in the list, for `audit.gdprRetentionDays`. A receipt whose key is outside that set reads `broken`, so a database writer cannot add a receipt signed with a key it controls. Owner's answer to UK-4 in chat, 2026-11-26, option (b), after the owner asked whether to build both (b) and (c). The options not chosen were (a), the two aliases alone, under which a receipt signed two rotations earlier reads `broken`, and (c), trusting any version of the key `platform:audit-signing` names, which needs each KMS adapter to recognize the versions of a key, helps only on GCP and Azure, and gives each provider a different trust rule.
10. **The fix for AUDIT-I6 is a step of this change (O7).** A new step 0177.S3 fixes the append path of `pkg/audit/auditstore` so that a row appended after a redacted tail row links to the tail's `original_hash`, read from its receipt, with a component test that redacts a tenant's newest row and verifies the chain ([AUDIT-I6](../../issues/AUDIT/AUDIT-I6-row-appended-after-a-redacted-tail-links-to-its-post-redaction-hash.md)). Owner's answer to UK-7 (open decision O7) in chat, 2026-11-26, option (a), with the words "UK-7: ok". The options not chosen were (b), a separate change, and (c), folding the fix into 0177.S2, which had merged.
