# Decisions: 0177 Shared signing keys for upload tokens and redaction receipts

## Open decisions

- **O1. The store for the signing keys and the consumed state.** "Detailed design", SK-1, compares the options.
  - (a) Postgres only. The keys sit in a platform table keyed by purpose (SK-2), each envelope-encrypted under its purpose's KMS alias, such as `platform:upload-token-signing`, and the consumed state is a column of the session row, set in the `finalizing` → `ready` write.
  - (b) Redis only. The keys sit in Redis, envelope-encrypted under the same alias, and the consumed state is a `SET NX` of the digest with a TTL.
  - (c) Both. The keys sit in Postgres as in (a), and the consumed state sits in Redis as in (b).
  - Recommendation: (a). The upload and finalize paths already depend on Postgres for the session row, so (a) adds no store and no failure mode to them, and the consumed check can ride on a row read the paths already make. Postgres keeps the keys across a restart, which (b) does not, and a lost key ring under (b) leaves every session in `created` unable to finalize, because §7.1 does not reissue a token. (b) and (c) add a Redis round trip per upload and a refusal of uploads during a Redis outage while Postgres is up, and they need a memory fallback for the development mode that runs without Redis.
  - The receipt signer of decision 2 bears on O1 only under O3 (b) or (c). A receipt key has to verify receipts for `audit.gdprRetentionDays` (default 2555 days), and Redis is not a system of record, so under those options the receipt keys sit in Postgres whatever O1 settles. Option (b) of O1 would then split the signing-key store across Redis for upload tokens and Postgres for receipts, which is a further reason for (a). Under O3 (a) the receipt key sits in the KMS, and O1 concerns the upload-token state alone.
- **O2. The behavior when the ring cannot be refreshed.** Under SK-4, a replica that has not refreshed its ring for longer than the overlap window stops minting tokens, so session creation on that replica answers `503`, while verification continues with the loaded ring.
  - (a) Stop minting after the overlap window without a refresh, as SK-4 states.
  - (b) Keep minting with the last loaded active key for as long as the process runs, and rely on peers that have the same ring.
  - Recommendation: (a). After the overlap window a peer may have rotated to a key this replica has not loaded and retired the key this replica signs with, so a token from this replica may not verify elsewhere. (a) fails closed, and the window is long enough that a short Postgres outage does not reach it.
- **O3. The key that signs redaction receipts.** §12.8 step 14 states that a receipt is "Signed by the platform's KMS-held audit signing key", that "External verifiers fetch the public key from the admin API", and that `signature_kms_key_id` keeps prior receipts verifiable after a rotation. An HMAC key from the shared store of SK-2 gives every replica the same key and keeps old receipts verifiable, and it has no public key and is not held by the KMS. Decision 2 asks to reuse the shared mechanism where possible, so the choice is between following §12.8 as written and reusing the store. "Detailed design", SK-6, describes each option.
  - (a) KMS signing. Each receipt is signed inside the KMS with an ES256 key under a platform audit signing alias, through `kms.Provider.Sign` as the §10.2 JWT signer does, and `signature_kms_key_id` records the KMS key and version. The shared store holds no receipt purpose. §12.8 keeps its text, with the §11.7 parenthetical replaced by the alias's name.
  - (b) The shared store with an HMAC key under the `redaction-receipt` purpose, kept for `audit.gdprRetentionDays` after retirement. §12.8 drops the public key and external verification: only the platform's chain verifier checks a receipt.
  - (c) The shared store with an ES256 key pair under the `redaction-receipt` purpose: the private key wrapped under the KEK and used in gateway memory, the public key kept for `audit.gdprRetentionDays` after retirement and served by the admin API. §12.8 changes "KMS-held" to a key wrapped under a KMS key.
  - Recommendation: (a). A receipt is the provenance token that tells an authorized redaction from tampering for seven years by default, and (a) is the option under which a compromised gateway process cannot take a key that forges receipts later, because the private key never leaves the KMS. It needs no stored secret and no retention policy for one, it reuses the existing KMS signing path of the §10.2 JWT signer, and its cost, one KMS call per redacted row inside an asynchronous erasure job, is small. It does not reuse the shared store of this change, which departs from decision 2's preference; (c) is the option that reuses the store and keeps external verification, at the cost of a long-lived private key in gateway memory. (b) removes a property §12.8 states and is not recommended. Under every option the §11.7 parenthetical is corrected, because §11.7 defines no genesis-nonce signing and no code signs the nonce.

## Decisions

1. **A change for a shared key ring and a shared consumed-token tracker (IK-4).** The per-replica upload-token key ring and consumed tracker are replaced by shared ones, through a change whose design the owner reviews before it is settled, with the choice between Redis, Postgres, or both. The change lands before the milestones that run several gateway replicas. Owner's answer to IK-4 on the M3 readiness decision page, 2026-11-25, option (a), with the words "but I would like to see the design first (Redis, Postgres, or both)". The question arose from the review of change [0173](../archive/2026-11-25-0173-idempotency-stored-credentials/change.md), whose replay rebuilds a token only on a replica whose ring holds the signing key.
2. **The redaction receipt signer is fixed in this change, reusing its mechanism where possible (AUDIT-I2).** The dead-letter redaction receipt signer, whose key is generated per process and discarded ([AUDIT-I2](../../issues/AUDIT/AUDIT-I2-redaction-receipt-signing-key-per-process.md)), is fixed together with the per-replica upload-token keys ([UPLOAD-I1](../../issues/UPLOAD/UPLOAD-I1-upload-token-keys-and-consumed-state-per-replica.md)), and ideally reuses the same mechanism. Owner's direction in chat, 2026-11-25, with the words "Solve the `deadletterredaction` issue along with the other one, and ideally reuse the mechanism." Whether the receipt signer reuses the shared store or signs in the KMS as §12.8 states is open decision O3.
