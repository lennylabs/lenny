# Decisions: 0180 A formal model of the audit chain and redaction receipts

## Open decisions

Each decision below comes from a counterexample of the model that step 0180.S1 checked against the specification and the code ("Model results" in `change.md`). The fix of each lands in another change, as "Specification and non-specification changes" in `change.md` states.

None.

## Decisions

1. **The modelling tool, and the model kept for reruns (O1).** TLA+ with the TLC model checker, reusing the runner and the pinned `tla2tools.jar` of change 0169. The model is stored under `tests/formal/auditchain/` with its module, one configuration file per scenario, a `run.sh` that runs every configuration, and a `README.md` that states what the model covers, the properties in plain words, how to run it, and its results, as `tests/formal/tokenconcurrency/` does, so that a later change that edits a rule the model describes updates the model and reruns it. The `formal/` entry of `tests/README.md` names the model. Owner's answer in chat, 2026-11-26, with the words "go ahead with 1-4" to the recommendation of TLA+, and "Store the TLA+ models so that we can update and re-run them later if we have to make changes". The options not chosen were Alloy, as change 0165 used, and a model-based property test in Go.
2. **Program membership (O2).** The change stays outside the v1 program, as change 0172 does, and "Formal verifications owed before M3" in [the v1 program](../programs/v1.md) tracks it as FV-3. Owner's answer in chat, 2026-11-26, with the words "go ahead with 1-4" to that recommendation. The option not chosen was membership in milestone M3.
3. **The verifiers after a retention sweep (O4, AUDIT-I10, AUDIT-I11).** Option (a). The verifiers check links only from the oldest row the general retention window still holds. A `gdpr.*` row older than the cutoff that the sweep keeps is checked alone, its content and its receipt, as the remnant of a deleted tenant is, and the first row checked carries the sentinel only when it is the first value of the tenant's sequence. The window check no longer reports a break after a sweep, and the query verifier no longer reads the oldest remaining row as broken. Step 0180.S2 builds it. The options not chosen were (b), a chain or table of its own for the `gdpr.*` rows, and (c), a record of each hole written by the sweep. Owner's answer to AM-2 in chat, 2026-11-27: "AM-2 to AM-5: go with your recommendations."
4. **One read of rows and receipts (O5, AUDIT-I12).** Option (a). `Store.Rows`, `Store.Verify`, and `auditReceipts` read the rows and the receipts in one `REPEATABLE READ` transaction, or in one statement that joins them, as the receipt scan does, so a redaction that commits during an audit query no longer reads as a broken row. Step 0180.S2 builds it. The option not chosen was (b), one retry of a query that reports a row `broken`. Owner's answer to AM-3 in chat, 2026-11-27, as for decision 3.
5. **A receipt key rotation in two rollouts (O6, AUDIT-I13).** Option (a). §12.8 and the security guide state two rollouts: first map `platform:audit-verify` to the new key and list the key it named before in `audit.retiredReceiptKeyIds`; then swap the two mappings. The model's `rotation_verifyfirst` configuration holds under this order. Step 0180.S2 edits the text. The options not chosen were (b), one rollout with the alert it raises documented, and (c), refreshing the trusted receipt keys from the KMS while the gateway runs. Owner's answer to AM-4 in chat, 2026-11-27, as for decision 3.
6. **The application role decides the dead-letter state (O7, AUDIT-I14).** Option (a). §11.7 and §12.8 state that the application role, which runs the translator, decides which rows are dead-lettered, so a compromised application role can expose a row that names an erased user to the redaction, and that the SIEM copy keeps the original. Step 0180.S2 edits the text. The options not chosen were (b), the translator's state machine held by the trigger, and (c), a redaction only when a dead-letter record exists outside `audit_log`. Owner's answer to AM-5 in chat, 2026-11-27, as for decision 3.
7. **A stored hash of each row (O3, AUDIT-I9, AUDIT-I8).** Option (b). `audit_log` gains a column that holds each row's own hash, written at `INSERT` and outside every role's `UPDATE` grant, the erasure role's included. The window check, the query verifier, the receipt scan, and the external verification of §12.8 compare each row's recomputed hash with the stored one, and accept a difference only when a verifying receipt explains it: the receipt's `original_hash` equals the stored hash and the row carries the redaction marker. An unmarked rewrite of the newest row by the erasure role then reads as broken, and a kept `gdpr.*` row that a retention sweep isolated (decision 3) has its content checked against its stored hash. The append path links a new row to the tail's stored hash, so it no longer reads the tail's receipt, and the `lenny_audit_immutability` trigger refuses an `INSERT` whose `prev_hash` differs from the tail's stored hash, the check §11.7 item 3 states (AUDIT-I8). Step 0180.S3 builds it, with the model under `tests/formal/auditchain/` extended by a configuration that checks the stored hash; how the column is filled for rows written before the migration is settled in the step's design. The options not chosen were (a), a trigger that admits only a marked rewrite of a dead-lettered row, which the owner may still add on top, and (c), stating the rewrite as a limit of the erasure role. Owner's answer to AM-1 in chat, 2026-11-28, "Am-1: (b)", after asking on 2026-11-27 "why not (b) if it also addresses the other problem? It feels (b) is a more elegant/generic solution".
