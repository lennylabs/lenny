## Problem

"Terms", after "Scope", defines the vocabulary this document uses. The rest of the design uses the kind names the owner settled in D6, and "Terms" gives the name each kind carries today.

The specification says Lenny is built on the upstream project `kubernetes-sigs/agent-sandbox` ([§4.6.1 Warm Pool Controller (Pod Lifecycle)](../../spec/04_system-components.md#461-warm-pool-controller-pod-lifecycle), **Implementation:**), and the code has no dependency on it **[source]**. `go.mod` does not list `sigs.k8s.io/agent-sandbox`. Lenny defines its own resource kinds `Sandbox`, `SandboxTemplate`, `SandboxWarmPool`, and `SandboxClaim`, with a further kind `Runtime`, under `lenny.dev/v1alpha1` in `pkg/apis/lenny/v1alpha1`, ships them in `charts/lenny/crds/`, and runs its own controllers in `pkg/controller/sandbox`, `pkg/controller/warmpool`, and `pkg/controller/poolscaling` **[source]**. The tree is in the state the specification's fallback plan describes.

The specification's dependency text therefore binds nothing that exists **[source]**:

- **Implementation:** credits upstream with community maintenance, "Pod Snapshots on GKE", and a claim model designed by SIG Apps. Upstream's snapshot feature is part of its Python client, and its controllers contain no snapshot logic **[external]**.
- **Dependency pinning and upgrade policy:** pins a tagged release and calls upstream "a v0.x project". Upstream is at `v1.0.11` with a `v1beta1` API **[external]**.
- **Go/no-go criteria for the agent-sandbox dependency:** and **Fallback plan if agent-sandbox is abandoned or diverges:** gate Phase 2 on an assessment of upstream and estimate "2-3 engineering-weeks" for a replacement that is already built.
- §3, §17.1, §17.6, §18.2, §18.6, §18.9, §18.40, §19, and §23 repeat the dependency.

The kind names come from upstream and match neither Lenny's vocabulary nor Lenny's meaning ("Vocabulary" under "Current state"). The specification, the REST API, `lenny-ctl`, the labels, and the metrics say "pool", "agent pod", and "pod claim", and Lenny already uses "sandbox" for a different idea: the isolation sandbox of §5.3 and the `sandboxed` isolation profile. The pool is split into a `SandboxTemplate` and a `SandboxWarmPool` that one controller always writes, names, and deletes together. Lenny's `SandboxClaim` is a lock the gateway takes on a pod it has already chosen, which upstream's claim of the same name is not.

The review also found places where the specification and the code disagree ("Current state"), and the Go types that implement the specification's pod lifecycle interfaces are named `AgentSandbox*`, which describes the `lenny.dev` types as upstream types **[source]**.

The code treats the `lenny.dev/pool` label value and the warm pool object's name as one value, and selects by the label both for work scoped to one warm pool object and for work scoped to the whole pool **[source]**. Under RV-3 a pool has several pod sets during a rollout, under names that differ from the pool's name, so one label cannot serve both scopes, and a claim that lists the pool's pods by the pool label alone can bind a session to a pod of a revision it did not choose. Nothing guards the label, although during a rollout it is the only record of which pool a pod set belongs to, and the admin API accepts pool names that Kubernetes cannot carry as a label value ("Pool label" under "Current state"). The registration paths accept runtime names that Kubernetes cannot carry in the `lenny.dev/runtime` pod label or as the name of a `Runtime` resource, so a runtime is stored and its pools never warm ("Runtime names" under "Current state").

## Scope

**Changed:**

- The specification describes Lenny's own controllers in §4.6.1, §3, §17.1, §17.6, §18.2, §18.6, §18.9, §18.40, §19, and §23, with no reference to upstream ("PLC-1").
- The kinds take Lenny's names: `AgentPod`, `PodSet`, `PodClaim`, and `Runtime`. `PodSet` replaces the `SandboxTemplate` and `SandboxWarmPool` pair. The fields that reference a kind take the new kind's name, and every identifier derived from a retired kind name follows ("PLC-2", D6).
- Each selector is scoped to one pod set, to the pod sets of one pod hash, or to the whole pool by a stated rule, `lenny.dev/pool` and `lenny.dev/pod-set` are required and immutable on every `PodSet` and every agent pod, and each pod set has its own PodDisruptionBudget ("PLC-2" **Pool and pod-set labels.**, D10, D12).
- The gateway's claim and its Postgres fallback take a pod only from the pool's pod sets for the chosen revision's pod hash ("PLC-2" **Pool and pod-set labels.**, D12).
- Every `PodSet` is named `<pool>.<key16>`, and `AgentPod.spec.podSetRef` and the owner reference are the authoritative record of a pod's pod set ("PLC-2" **Pod-set names.**, D12).
- The admin API and the bootstrap seed refuse a pool name that is not a valid Kubernetes label value ("PLC-7", D10).
- The admin API, the bootstrap seed, the RuntimeReconciler, and the tenant-derived runtime create refuse a runtime name outside the same pattern, and the embedded stack's `lenny runtime apply` names its pool after the runtime ("PLC-7", D11).
- The specification and the documentation describe each kind in Lenny's terms ("PLC-3").
- The spec and code mismatches the review found are corrected ("PLC-4").
- The `AgentSandbox*` Go types become `CRD*` types, and the §17.1 row names them ("PLC-5").

**Removed:**

- The specification's dependency text: "built on", the pinned release, the v0.x upgrade policy, the go/no-go criteria, the fallback plan, the Phase 2 dependency assessment, the upstream-contribution cadence, the "default implementation wraps `kubernetes-sigs/agent-sandbox`" statements, §23's upstream row, and the upstream license criterion (D3, D4).
- Every tracking statement, including revision 1's reconsideration trigger, and every requirement, documentation item, or test that follows upstream (D4).
- The reserved `SnapshotPod` and `RestoreFromSnapshot` extension points of §4.6.1 (D4, the former O2).

**Out of scope:**

- Adopting upstream as a dependency in any form. "Alternatives rejected" records the review's option (b).
- GKE Pod Snapshots, the multi-cluster warm-pool planner, refill pacing, and the other upstream features section 4 of the review lists.
- The content of resource classes. [`0121-billing-resource-attribution`, "Resource classes in configuration"](../0121-billing-resource-attribution/change.md#resource-classes-in-configuration) (BR-1) owns it, and PLC-4 records how it settles the review's resource class finding.
- Applying the new names to other designs. "Instructions for other designs" lists every site for the pass that applies them, which runs now that the owner has confirmed the names (D6).
- Architecture Decision Records under `docs/adr/`. [`0125-decision-records`](../0125-decision-records/change.md) removes them (D9), and this design changes none of their files.

## High-level design

Lenny runs its own controllers for its own resource kinds, and the specification says so without naming any other project. The specification loses its dependency text and every statement that follows upstream, so no section, document, chart value, code comment, or test names upstream (D4, "PLC-1"). No historical sentence about the origin of the resource model stays (D7).

The kinds take the names Lenny already uses for the objects they record (D6, "PLC-2"):

- An `AgentPod` records one agent pod. The specification calls the object an agent pod, and Lenny's first kind for it was `AgentPod`.
- A `PodSet` records one pod set of a pool. It holds the pool settings that today sit on the `SandboxTemplate` and the warm targets and counts that today sit on the `SandboxWarmPool`. The two objects are one record in two halves: the PoolScalingController writes both specs in one reconcile, names both after the pool, and points the warm pool at the template of the same name, and [RV-3](../0140-runtime-revisions/change.md#rv-3-pods) creates and deletes them as a pair per pod set. A pool has one `PodSet` outside a rollout.
- A `PodClaim` records the gateway's claim on one agent pod. The specification calls the act a pod claim in §6.3, the interface method is `ClaimPod`, and the metrics are `lenny_pod_claim_*`.
- `Runtime` keeps its name.

A field that references another kind takes that kind's name: `AgentPod.spec.podSetRef` and `PodClaim.spec.agentPodRef`. The template reference disappears with the merge. `AgentPod.status.podIP` keeps its name, because the gateway dials one address per pod, and `AgentPod.spec.slotCount` takes SI-4's term. Nothing is deployed, so no kind, resource, or field keeps its old name in any form. A manifest naming a retired kind is refused by the API server, which names the kind, and no external writer exists for a retired field.

The specification describes each kind in Lenny's terms ("PLC-3"), corrects its own errors about the kinds ("PLC-4"), and names the Go types behind the pod lifecycle interfaces for what they act on ("PLC-5"). The `AgentPod` gains no condition mirrored from the pod (D8), and §4.6.1 loses the snapshot extension points (D4).

Each `PodSet` is named `<pool>.<key16>`, where `key16` is the first 16 hexadecimal characters of its pod-set key, inside and outside a rollout ("PLC-2" **Pod-set names.**, D12). Two labels record membership ("PLC-2" **Pool and pod-set labels.**, D10, D12). The pool label names the pool on each `PodSet` and on each of its pods, and everything that acts on the whole pool selects by it: recycle's lookup of the pool's policy, topology spread, and the operator's `kubectl` commands. The pod-set label holds `key16` on each `PodSet` and each of its pods, and everything that acts on particular pod sets selects by it together with the pool label: the gateway's claim, which covers the pod sets of the chosen revision's pod hash, its Postgres fallback, and the pod set's PodDisruptionBudget, of which there is one per `PodSet`. The WarmPoolController's reconcile of one `PodSet` lists its `AgentPod` objects by owner reference or `spec.podSetRef`, which are the authoritative record, and the labels are copies a webhook checks against `spec.podSetRef` at create. Both labels are required and immutable, and a pool name must be a valid label value, so the admin API refuses any other name ("PLC-7").

A runtime name follows the same rule (D11). The WarmPoolController copies it into the `lenny.dev/runtime` label on each agent pod, a declaratively registered runtime's `Runtime` resource carries it as its object name, and a tenant-derived runtime's owned pool takes it as the pool name. Every path that registers a runtime refuses a name outside the pattern before it writes anything ("PLC-7").

A custom resource's name is a DNS subdomain: at most 253 characters of lower-case letters, digits, `-`, and `.`, beginning and ending with a letter or a digit. `k8s.io/apiextensions-apiserver` v0.31.4 checks it with `NameIsDNSSubdomain` in `pkg/registry/customresource/validator.go` **[external]**. What happens today to a runtime name the pattern of PLCR-15 refuses, read from the code and not run **[inference]**:

- **64 to 128 characters, otherwise valid.** Every registration path accepts it, a `Runtime` resource included, because 128 is within 253. A pool on the runtime is accepted, because pool admission reads the runtime and does not check its name's form. The first pod create fails, because the API server refuses a `lenny.dev/runtime` value longer than 63 characters, so the pool is stored and never warms. F-5.1.31 in `BUILD-GAPS.md` and DF-10 of [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md#names) record this case.
- **Holding `_`, or ending in `-` or `_`.** The admin API and the bootstrap seed store it. The API server refuses a `Runtime` resource of that name, so the runtime exists only as a registry row, and a pool on it is accepted. In today's tree `createPod` reads the `Runtime` resource before it builds the pod, so no pod is created. Under [RV-3](../0140-runtime-revisions/change.md#rv-3-pods) the pod builder reads the revision instead, and the pod create then fails at the label for a name ending in `-` or `_`, which a label value refuses. A name holding `_` between letters is a valid label value, and it still cannot be an owned pool's name, which a tenant-derived runtime gives its pool.
- **59 to 63 characters, through `lenny runtime apply`.** The verb's pool name is 64 to 68 characters, so the first `Sandbox` create fails at `lenny.dev/pool`.
- **More than 128 characters.** Every registration path refuses it.

A runtime registered only through the admin API has no `Runtime` resource, so in today's tree `createPod` fails for it whatever its name, and the embedded verb exists to apply that resource **[source]**. RV-3 removes this dependency, which is why the label case above governs once the designs are implemented.

**The merge.** A `PodSet` holds what the template and the warm pool of one pod set hold today, under the same field names **[design]**:

- `spec` carries the pool settings of today's template, as the other designs leave them ("PLC-4" **Fields after the designs.**), together with `minWarm`, `maxWarm`, `scalePolicy`, and DR-10's `reservedPods`. The PoolScalingController owns all of `spec` and writes it in one apply per reconcile.
- `status` carries `warmCount`, `readyCount`, `scalingMode`, `bootstrapHoursOfData`, one `observedGeneration`, and one `conditions` list that holds the conditions the template carries today (`PoolWarmingUp`, `PoolDrained`, `SecurityDegradedMode`, `Degraded`, and PM-6's `PlacementRefused` and `PlacementUnschedulable`). The WarmPoolController owns `status` except `scalingMode` and `bootstrapHoursOfData`, which stay the PoolScalingController's carve-out under its own field manager, as today on the warm pool. PL-8 removes `sdkWarmCircuitBreaker` and `sdkWarmDisabled`.
- The `PodSet` is the controller owner of each of its `AgentPod` objects, as the warm pool is today, and `AgentPod.spec.podSetRef` names it.
- RV-3's pair per pool and pod-set key becomes one `PodSet` per pool and pod-set key, named and labelled as **Pod-set names.** below states. The PoolScalingController sets `lenny.dev/pool` to the pool name when it creates a `PodSet`, and the WarmPoolController copies the `PodSet`'s `lenny.dev/pool` and `lenny.dev/pod-set` values onto each `AgentPod` and its pod. Each selector selects by the scope **Pool and pod-set labels.** below gives it. RV-3's deletion rule and its quarantine retention apply to the one object. Outside a rollout a pool has one `PodSet`.
- `lenny-pool-config-validator` reviews `PodSet` writes, and the deletion guard that today refuses a template deletion refuses a `PodSet` deletion under the same conditions.

The merge removes the template reference and its required-field check, the window in which one half of a pair is written and the other is not, and the ordering of creation and deletion between the halves. An operator reads a pool's settings and its warm counts with one `kubectl get podsets`. A warm-target change now bumps the `metadata.generation` of the object that carries the pool settings. The WarmPoolController already reconciles on a change to either object, so it reconciles no more often **[inference]**.

**Pod-set names.** One rule names every `PodSet`, inside and outside a rollout (D12) **[design]**:

- **Key.** RV-3's pod-set key is the SHA-256 digest of the pod hash and the derived runtime's and the pool's contributions, written as 64 lower-case hexadecimal characters in `PodSet.spec.podSetKey` ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)). `key16` is its first 16 characters.
- **Name.** A `PodSet` is named `<pool>.<key16>`, such as `web.1a2b3c4d5e6f7a8b`. A pool name holds no `.` under "PLC-7", so no `PodSet` name equals a pool name, and the text before the first `.` is always the pool. The name is a DNS subdomain of at most 80 characters: a pool name of at most 63, the `.`, and 16 hexadecimal characters. A pool outside a rollout has one `PodSet` under the same rule, so the `PodSet` that remains after a rollout is named for the key it was built for.
- **Label value.** `lenny.dev/pod-set` holds `key16`, 16 characters, on the `PodSet`, on each of its `AgentPod` objects, and on each pod. It is the one label RV-3's "labelled with the key" refers to. Two pools on one revision with no contributions of their own compute the same key, so `lenny.dev/pod-set` identifies a pod set only together with `lenny.dev/pool`, and every selector that names it also names the pool.
- **Uniqueness.** RV-3 keeps one `PodSet` per pool and distinct pod-set key, so `{pool, key}` is unique by construction. Two distinct keys of one pool share `key16` with probability below n²/2⁶⁵ for n keys, about 3 × 10⁻¹⁴ for 1,000 keys over a pool's life. Before it applies a `PodSet`, the PoolScalingController reads `spec.podSetKey` on any `PodSet` that already holds the computed name and refuses to overwrite one whose key differs: it sets the condition `Degraded` with the reason `PodSetKeyCollision` on the existing `PodSet` and writes nothing for the new key.
- **Derived names.** The PDB is `<podSet>-warm`, at most 85 characters. An `AgentPod`, and so its pod, keeps the generated name `<pool>-<random>`: the WarmPoolController sets `generateName` to the `PodSet`'s `lenny.dev/pool` value and `-`, as `createSandbox` in `pkg/controller/warmpool/controller.go` sets it to the warm pool object's name today **[source]**. The API server keeps at most 58 characters of the base and adds 5 random ones **[external]**, so the name holds at most 63 and carries no `.`. The claim stays `claim-<podName>`.

**Pool and pod-set labels.** Two labels record membership, and each selector uses the one that matches its scope (D10, D12) **[design]**:

- **Values.** The PoolScalingController sets `lenny.dev/pool` to the pool name and `lenny.dev/pod-set` to `key16` when it creates a `PodSet`. The WarmPoolController copies both values onto each `AgentPod` it creates and onto the pod.
- **Authority.** `AgentPod.spec.podSetRef` and the `AgentPod`'s controller owner reference are the authoritative record of its `PodSet`. Both labels are copies, which a selector can name where an object reference cannot be used, such as in a PodDisruptionBudget, a pod list, or `kubectl -l`.
- **One pod set.** The WarmPoolController's reconcile of a `PodSet` lists its `AgentPod` objects by the controller owner reference or by a field index on `spec.podSetRef`, and plans from that list alone. The pinned idle listing of `tenantLabelledPods` in `pinned.go` lists pods, which carry no `podSetRef`, by `{lenny.dev/pool, lenny.dev/pod-set}`. Mirror recovery takes each `AgentPod`'s pool from its `lenny.dev/pool` and its pod set from `spec.podSetRef`, and reads the `PodSet` of that name for the execution settings where it still exists, so it still converges after the `PodSet` is deleted. The PodDisruptionBudget follows the next bullet.
- **PodDisruptionBudget.** There is one per `PodSet`, named `<podSet>-warm`, owned by the `PodSet`, and selecting `{lenny.dev/pool: <pool>, lenny.dev/pod-set: <key16>, lenny.dev/state: idle}`, with an integer `minAvailable` of the `PodSet`'s `minWarm - 1` and none when that `minWarm` is below 2, as §4.6.1 **Disruption protection for agent pods:** states per template today. Each agent pod carries one `lenny.dev/pod-set` value, so no two PDBs select it.
- **The claim.** The gateway claims from the pod sets of the chosen revision ([RV-2](../0140-runtime-revisions/change.md#rv-2-selection) **Claim.**). `ClaimRequest` carries the pool and the revision's pod hash. The claimer lists the pool's `PodSet` objects by `lenny.dev/pool`, keeps those whose `spec.podHash` is the revision's pod hash, which includes an earlier pod set of the same pod hash that "Changing the list" under [DR-11](../0147-tenant-derived-runtimes/change.md#warm-stores) keeps claimable, and lists `AgentPod` objects by `lenny.dev/pool=<pool>, lenny.dev/pod-set in (<key16>, ...)`. `Claim` in `claimer.go`, its reserved-hold rebind, which runs on the same list, and `ClaimSlot` in `slotclaimer.go` use that list. The claim-time refusals of "Changing the list", at `AdmitTenantPin`, apply per pod as today. An empty list takes the existing path for a pool with no idle pod. The claimer never lists by `lenny.dev/pool` alone, so a session never binds to a pod of another pod hash. A retried or resumed session claims the same way with its recorded revision's pod hash ([RV-6](../0140-runtime-revisions/change.md#rv-6-sessions-over-time)).
- **The Postgres fallback.** Each `agent_pod_state` row records its pod set in a new column `pod_set`, the `PodSet` name, beside the pool. `agentpodstate.Store.Sync` converges the rows of one `PodSet`, `ClaimIdle` takes the pool and the claim's `PodSet` names and selects only their rows, and `MirrorLagSeconds` reads the lag of those rows, so `fallbackClaim` in `pkg/gateway/podlifecycle/podsession/fallbackclaim.go` claims within the same pod sets as the Kubernetes-API path.
- **The whole pool.** Recycle's lookups of the pool record's recycle policy, cleanup timeout, and concurrency, in `scrubreporter_seams.go` and `recycleboundary.go`, read `lenny.dev/pool` from the pod, because those settings belong to the pool record, and recycle returns a pod to idle inventory in its own pod set. Topology spread, the pool diagnosis of §25.6 behind `lenny-ctl diagnose pool` where it reads pods from Kubernetes, the runbooks, and an operator's `kubectl get podsets -l lenny.dev/pool=<pool>` also select by `lenny.dev/pool`. The orphaned-claims metric's `pool` label reads the `AgentPod`'s `lenny.dev/pool`, and, where the `AgentPod` lacks it, the owning `PodSet`'s `lenny.dev/pool`. It never falls back to `spec.podSetRef`, which names a pod set. The stateless endpoint lister of `cmd/lenny-gateway/statelessrouting_wiring.go` serves service mode, which [AR-2](../0119-agent-runtimes-only/change.md#ar-2-service-mode) removes with the `/v1/stateless/{pool}` route, so it has no scope here.
- **Required and immutable.** `lenny-pool-config-validator` refuses a `PodSet` `CREATE` without `lenny.dev/pool` or with a value that is not a valid label value, or whose name is not `<lenny.dev/pool>.<lenny.dev/pod-set>` with a `lenny.dev/pod-set` equal to the first 16 characters of `spec.podSetKey`, and an `UPDATE` that changes or removes either label. `lenny.dev/pool` and `lenny.dev/pod-set` join the labels that `lenny-label-immutability` holds strictly immutable on agent pods, and the webhook applies the same rule to both on `AgentPod` updates. `AgentPod.spec.podSetRef` is immutable through the CRD rule `self == oldSelf`.
- **Equal at create.** `lenny-label-immutability` also reviews `AgentPod` `CREATE` and refuses an `AgentPod` whose `lenny.dev/pool` is not the text of `spec.podSetRef` before its first `.`, or whose `lenny.dev/pod-set` is not the text after it. The `PodSet` name carries both values, so the check reads no other object. The pod copies the `AgentPod`'s labels at its create, and both labels are immutable on both objects after that, so every carrier keeps the value `spec.podSetRef` fixes.

The rule follows from what goes wrong with either single value during a rollout, when a pool has two `PodSet` objects. If the pods carried the `PodSet` name in `lenny.dev/pool`, recycle and the operator's commands, which select by the pool name, would not find the new revision's pods. If they carried the pool name alone and each `PodSet`'s reconcile and the claimer selected by it, each reconcile would count the other pod set's pods as its own and warm too few, two PDBs would select the same idle pods, and a session that chose one revision would bind to a pod of another. The eviction API refuses to evict a pod that more than one PDB selects **[external]**, so node drains would stall for the length of the rollout.

The PDB is per `PodSet` rather than per pool because the warm target is per pod set: RV-3 splits the pool's target across its pod sets by the summed weight of each pod set's active revisions, with a floor of one pod, so each `PodSet` carries its own `minWarm`, and the WarmPoolController reconciles one `PodSet` at a time. A PDB per `PodSet` takes `minAvailable` from the `minWarm` its own reconcile reads. A PDB per pool would need a writer that sums `minWarm` across pod sets and an owner that outlives any one of them. Outside a rollout the two rules give the same budget. During a rollout each pod set admits its own eviction at steady state, so a drain can take one idle pod from each pod set at once.

The pool label is immutable because the claimer, recycle, and the operator's commands select by it, and they trust it. A `PodSet` or pod relabelled to another pool would make pods built with the first pool's isolation profile, egress profile, and runtime claimable by the second pool's sessions. The tenant check at claim limits this on a tenant-owned pool and not on a shared one.

The pod-set label is immutable as well (D12). The gateway's Role in `charts/lenny/templates/gateway-deployment.yaml` grants `get`, `list`, `watch`, and `patch` on pods and no `delete` **[source]**, so a principal holding it can change a pod's labels and cannot remove the pod. A pod whose `lenny.dev/pod-set` changes or disappears leaves its PDB and the claim's selector, and `tenantLabelledPods` no longer finds it, so a tenant-pinned pod counts as general warm inventory. Nothing restores the label: the WarmPoolController copies an `AgentPod`'s labels onto its pod once, through `podLabels` in `pkg/controller/sandbox/podspec/base_pod.go`, and afterwards re-syncs only `lenny.dev/state` and `lenny.dev/host-schedulable` **[source]**.

**No alias and no migration.** Nothing is deployed, so no retired kind, resource, field, or identifier keeps its name in any form, and no conversion or data migration runs (the owner's no-backward-compatibility rule) **[design]**:

- A manifest naming a retired kind is refused by the API server, because no CRD serves the kind. `kubectl apply` reports `no matches for kind "SandboxTemplate" in version "lenny.dev/v1alpha1"`, and a request to the retired resource path, such as `/apis/lenny.dev/v1alpha1/namespaces/<ns>/sandboxtemplates`, answers `404 NotFound`. ### PLC-3 Resource kinds

§4.6.1's kind table describes each kind by what it records and who writes it, and the glossary and the architecture page state the same **[design]**. No row compares a kind with another project.

**`AgentPod`.**

- One object per agent pod. The pod takes the `AgentPod`'s name, and `status.podName` records it.
- It holds no pod template. The controller renders the pod from the `PodSet`, the referenced `Runtime` or, for an owned pool, the base named by `podRuntimeRef` (DR-2), and the pool's resolved placement (PM-5).
- `spec.slotCount` records the slot containers the pod was rendered with ("PLC-4").
- `status.phase` is the occupancy projection of the pod's claim ([§6.2](../../spec/06_warm-pod-model.md#62-pod-state-machine)), and `status.podIP` is the address the gateway dials.
- The `PodSet` owns the `AgentPod` for its whole life, and the pod serves many sessions in turn. A pod retires through its pool's recycle limits and uptime limit, and a failed pod is retired and replaced through its pod set. A session suspension checkpoints the slot's files and releases the slot ([`0146-session-lifecycle`](../0146-session-lifecycle/change.md)), and the pod stays.

**`PodSet`.**

- One object per pod set of a pool ("PLC-2" **The merge.**). It names the runtime and carries the pool settings that the WarmPoolController, the pod builder, and `lenny-pool-config-validator` read, and the warm targets.
- It holds no `PodSpec` and no volume claim templates. Per-session inputs travel over the adapter protocol, and the pool's pods carry labels that select the NetworkPolicies the chart creates per egress profile.
- The PoolScalingController writes its spec from the pool record ([§4.6.3](../../spec/04_system-components.md#463-crd-field-ownership-and-write-boundaries)), and neither a user nor an operator writes it directly.
- It is sized by `minWarm` and `maxWarm`, which the PoolScalingController computes from demand, schedules, and bootstrap data ([§4.6.2](../../spec/04_system-components.md#462-poolscalingcontroller-pool-configuration)), split across the pool's pod sets by RV-3. It has no `replicas` and no `/scale` subresource, so an HPA or KEDA cannot size it.
- A claimed pod stays a member. After its sessions end, the pod is scrubbed, held for its pinned tenant through the reserved hold, and returned to idle inventory. `status.warmCount` and `status.readyCount` leave out pinned idle pods, which only their tenant can claim.
- A runtime revision with a new pod hash gets a `PodSet` of its own ([`0140-runtime-revisions`](../0140-runtime-revisions/change.md)).

**`PodClaim`.**

- It is a lock the gateway takes on a pod it has already chosen, named `claim-<podName>` and naming the pod in `spec.agentPodRef`.
- No controller fulfils it. Creation either succeeds or fails with `AlreadyExists`, and `lenny-podclaim-guard` refuses a second claim on a pod.
- It does not own its `AgentPod`, carries no owner reference, and is deleted explicitly at hold expiry, at a release that ends the occupancy, by orphan collection, or when the pod terminates.
- It lasts one occupancy episode, which spans every session on the pod and the reserved hold after them.

**`Runtime`.** The row points to §5.1.

### PLC-7 Pool and runtime names

**Pool names.** A pool name is a valid Kubernetes label value and a valid object name, because the controllers copy it into the `lenny.dev/pool` label and name the pool's `PodSet` objects and PDBs from it (D10) **[design]**:

- The admin API's `POST /v1/admin/pools`, its dry-run preview, and the bootstrap seed refuse a pool name that does not match `^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$`: 1 to 63 characters, lower-case letters, digits, and `-`, beginning and ending with a letter or a digit. All three call `poolstore.ValidateName`, so the pattern changes in that one function.
- The refusals are the ones each path returns for a bad pool name today, with a message that states the pattern: `400 VALIDATION_ERROR` with `details.field` set to `name` from the admin API, and an entry error with the code `SEED_VALIDATION` from the bootstrap seed. Nothing is written.
- `_` and `.` are left out, although a label value admits them. An object name of most kinds is a DNS subdomain, which admits no `_`, so a name holding `_` fails as the `PodSet` name **[external]**. Leaving out `.` as well makes every pool name a DNS label, the narrowest Kubernetes name form, so it fits any object Lenny names after a pool.
- The rule sits beside the reservation of `--` in [DR "Names"](../0147-tenant-derived-runtimes/change.md#names), which stays a separate check with its own refusal. A tenant-derived runtime's owned pool takes the runtime's name, which DR "Names" caps at 63 characters, so owned pools already meet the length rule.
- A pool is never renamed, because `UpdatePoolRequest` has no name field, so the rule applies at create alone. Nothing is deployed, so no stored pool needs a migration (the owner's no-backward-compatibility rule).

**Runtime names.** A runtime name follows the pool-name rule, because the WarmPoolController copies it into the `lenny.dev/runtime` label on each agent pod, a declaratively registered runtime's `Runtime` resource carries it as its object name, and a tenant-derived runtime's owned pool takes it as the pool name ([DR "Names"](../0147-tenant-derived-runtimes/change.md#names)) (D11) **[design]**:

- `runtimestore.ValidateName` uses the pattern of PLCR-15, and every path that registers a runtime calls it: `POST /v1/admin/runtimes` and its dry-run preview, which `lenny-ctl runtime register` reaches; the bootstrap seed's runtime entries, which `lenny-ctl bootstrap` reaches; the RuntimeReconciler's `mirror`; the tenant-derived runtime create `POST /v1/admin/derived-runtimes` ([DR "API"](../0147-tenant-derived-runtimes/change.md#api)); and the stores' `Create`. A platform-derived runtime registers through `POST /v1/admin/runtimes` and meets the same check.
- The refusals are the ones each path returns for a bad runtime name or field today, with a message that states the pattern, and nothing is written: `400 VALIDATION_ERROR` with `details.field` set to `name` from `POST /v1/admin/runtimes`; an entry error with the code `SEED_VALIDATION` from the bootstrap seed; `Registered=False` with the reason `InvalidRuntime` from the RuntimeReconciler, which mirrors no row; and `422 INVALID_DERIVED_RUNTIME` with `details.field` set to `name` from the tenant-derived runtime create, which is how [DR "API"](../0147-tenant-derived-runtimes/change.md#api) answers a field refusal.
- No path renames a runtime. `UpdateRuntimeRequest` has no name field, `PUT /v1/admin/runtimes/{name}` takes the name from the path, and [DR "API"](../0147-tenant-derived-runtimes/change.md#api) makes `name` immutable on `PUT /v1/admin/derived-runtimes/{name}`, so the rule applies at create alone. The capability override routes under `/v1/admin/tenants/{id}/runtime-capability-overrides/{runtime}` call `ValidateName` on the path, so a name outside the pattern answers `400 VALIDATION_ERROR` naming `runtime` there, and no stored runtime carries such a name.
- The pattern is the pool pattern rather than the label value syntax. A `Runtime` resource is a custom resource, whose name the API server checks as a DNS subdomain, which admits no `_` **[external]**. A tenant-derived runtime's name is its owned pool's name, so it has to pass the pool rule. Leaving out `.`, which both a label value and a DNS subdomain admit, keeps one pattern for runtime and pool names, so any runtime name can serve as a pool name.
- The reservation of `--` in [DR "Names"](../0147-tenant-derived-runtimes/change.md#names) stays a separate check with its own refusal. A tenant-derived name `<namePrefix>--<suffix>` matches the pattern when its suffix holds lower-case letters, digits, and `-` and ends with a letter or a digit, because the prefix grammar of DR "Names" is already within the pattern. DR "Names" caps the whole name at 63 characters, and the pattern enforces the same length on every runtime name.
- `lenny runtime apply` in the embedded stack names the pool it applies after the runtime, with no suffix. Today it names the pool `<runtime>-pool`, which adds 5 characters, so a runtime name of 59 to 63 characters gives a pool name of 64 to 68, which `lenny.dev/pool` cannot carry. The runtime name already keeps the verb's pools distinct, and an owned pool takes its runtime's name in the same way. The embedded echo pool, `echo-pool-embedded`, is named separately and does not change. Keeping the suffix would require runtime names of at most 58 characters, a limit no other path needs. Once the kinds merge, the verb's `PodSet` is `<runtime>.<key16>` under "PLC-2" **Pod-set names.**, and `lenny.dev/pool` carries the runtime name alone, so the arithmetic holds.
- Nothing is deployed, so no stored runtime needs a migration (the owner's no-backward-compatibility rule).

The refusals replace today's failure modes, in which the admin API stores a pool whose name the controllers cannot use, or a runtime whose pods the API server refuses, and the pool never warms ("Pool label" and "Runtime names" under "Current state").

## Limits

- Lenny maintains its controllers alone.
- The renames touch the specification, the code, the chart, the RBAC, the webhooks, the metrics, the alerts, the runbooks, the documentation, and the other designs. "Instructions for other designs" lists the design sites, and PLCR-11's check finds any site the rename misses outside the records.
- An operator who knows the REST API meets "pool" there and "pod set" in `kubectl`. Outside a rollout the two correspond one to one, and the `lenny.dev/pool` label on each `PodSet` names its pool.
- A development cluster installed from an earlier build keeps the retired CRDs and their objects until it is reinstalled. Nothing deletes them.

## Alternatives rejected

- **Adopt upstream `v1beta1` (the review's option (b)).** Upstream's `Sandbox` controller would own the pod create and observe loop. Lenny would keep its own claim, recycle, hold, phase projection, scaling, and tenant pinning, because upstream's claim picks the sandbox and never returns it. It would move Lenny from Go 1.25, `k8s.io/api` v0.31, and `controller-runtime` v0.19 to Go 1.26, v0.37, and v0.25, share one cluster-wide CRD version and controller with any other upstream user, and follow weekly releases whose patch releases carry action-required changes **[external]**. The owner chose (a) (D1) and stopped tracking upstream (D4).
- **Keep upstream's kind names (revision 1, D2).** The names do not describe Lenny's objects, collide with the isolation sense of "sandbox", and rest on upstream alignment, which the owner dropped (D4).
- **Rename fields toward upstream's names (revision 1).** `status.podIPs` as a list and `spec.sandboxTemplateRef.name` as an object followed upstream. Lenny dials one address per pod, and the merge removes the template reference.
- **Name the merged kind `Pool` (O3 (b)).** It matches the admin API and the `lenny.dev/pool` label, so an operator who knows the REST API meets the same word in `kubectl`. During a rollout a pool has one object per pod set, so `kubectl get pools` would list more objects than the admin API has pools, under names that differ from the pool's name, and `Pool` would describe the object wrongly for as long as the rollout runs.
- **Use Lenny's names from before upstream (O3 (c)).** `AgentPool` repeats the problem of (b), and on AKS the REST API calls a managed cluster's pools of nodes agent pools **[external]**, which an operator there reads first. `AgentPodClaim` is longer than `PodClaim` and adds nothing, because the claim is on a pod.
- **Keep two pool kinds under Lenny names.** The PoolScalingController writes, names, and deletes the two halves together, and a separate warm-target object helps only an external autoscaler that the `/scale`-less design rules out. `PodTemplate`, the obvious name for the template half, is a core Kubernetes kind.
- **Mirror the pod's `PodScheduled` condition on the `AgentPod`.** "PLC-2" **Conditions.** gives the reason.
- **Keep a reconsideration trigger or a tracking checklist.** The owner stopped tracking upstream (D4).
- **Keep one historical sentence about upstream (O4 (b)).** No Lenny name or field comes from upstream after D6, so the sentence explains nothing a reader of the specification meets, and the history stays in this design, its evidence, and the git history (D7).
- **Carry the `PodSet` name in `lenny.dev/pool` on the pods.** Recycle and the operator's commands select by the pool name and would not find a new revision's pods during a rollout ("PLC-2" **Pool and pod-set labels.**).
- **Claim from every pod set of the pool.** A session that chose one revision would bind to an idle pod of another revision whenever one came first, against RV-2's split by weight ("PLC-2" **Pool and pod-set labels.**, D12).
- **Name a `PodSet` `<pool>-<suffix>` and label pods with the `PodSet` name.** A pool name of 63 characters plus any suffix exceeds the 63-character label value limit, and a name such as `web-1a2b3c4d` can be another pool's name ("PLC-2" **Pod-set names.**).
- **Label pods with the full pod-set key.** A SHA-256 digest in hexadecimal is 64 characters, one more than a label value holds.
- **Name the `PodSet` after the pool outside a rollout.** The `PodSet` that remains after a rollout would carry another key's name, or the controller would rename it, which Kubernetes does not support for an object.
- **Leave `lenny.dev/pod-set` mutable.** The gateway can patch pod labels and cannot delete pods, and nothing restores a changed label, so a pod would leave its PDB and its pinned listing ("PLC-2" **Pool and pod-set labels.**).
- **One PodDisruptionBudget per pool.** The warm target is per pod set under RV-3, and a pool budget would need a writer that sums `minWarm` across pod sets and an owner that outlives each of them ("PLC-2" **Pool and pod-set labels.**).
- **A `spec.pool` field on the `PodSet` in place of the label.** A field cannot be selected on by `kubectl -l` or by a label selector, so the claimer, topology spread, and the operator's commands would still need the label, and the field would carry the same value twice.
- **Accept `_` in pool names and refuse only what a label value refuses.** A name holding `_` is a valid label value and an invalid object name, so the pool would still be stored and never warm ("PLC-7").
- **Refuse only what the `lenny.dev/runtime` label refuses in runtime names.** A runtime name holding `_` could not name a `Runtime` resource or a tenant-derived runtime's owned pool ("PLC-7" **Runtime names.**).
- **Keep the `-pool` suffix of `lenny runtime apply` and limit runtime names to 58 characters.** The limit would bind every registration path for the sake of one development verb, and DR "Names" already allows 63 ("PLC-7" **Runtime names.**).

**Settings, defaults, limits, and failure modes.** This design adds no setting or default. It adds one limit, the name pattern of PLCR-15 and PLCR-16 for pools and runtimes, which `docs/api/admin.md` and the runtime configuration reference state. Its failure modes are the refusal of a pool or runtime name outside the pattern by the admin API, the bootstrap seed, the RuntimeReconciler's `Registered=False` condition, and the tenant-derived runtime create, the API server's refusal of a manifest naming a retired kind, which `docs/operator-guide/troubleshooting.md` lists, the webhooks' refusal of a write that changes `lenny.dev/pool` or `lenny.dev/pod-set`, or of an `AgentPod` whose labels differ from its `spec.podSetRef`, which the namespace and isolation page lists, the `Degraded` condition with the reason `PodSetKeyCollision` on a `PodSet`, which `docs/operator-guide/scaling.md` lists, and preflight's report of a missing CRD on a cluster installed from an earlier build, whose message the upgrade documentation quotes. An operator reads a pool's settings and warm counts with `kubectl get podsets`, its pods with `kubectl get agentpods`, and their claims with `kubectl get podclaims`.

**Runtime authors.** The adapter protocol, the pod layout, and every runtime-visible path are unaffected. The one runtime author document that names a kind, `docs/runtime-author-guide/lifecycle.md`, takes the new name. A runtime author meets the runtime-name pattern of PLCR-16 when registering a runtime, and `docs/runtime-author-guide/runtime-configuration.md` states it.
