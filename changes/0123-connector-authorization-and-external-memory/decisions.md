# Decisions: 0123 Connector authorization and external memory

## Open decisions

Raised on 2026-11-19 by the M3 readiness review.

1. **O1. What step 0123.S1 builds, and when it lands.** CA-0's start page logs the user in through the "Browser login" of [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md), whose shared resolver lands in 0149.S6 (`depends-on: [0149.S2, 0149.S4]`), and 0123.S1 has no `depends-on` and says it lands first. The tree's only browser OIDC login is the playground's (`pkg/gateway/playground/oidc.go`), which reads the tenant from a raw claim that 0149 removes. 0124.S1 depends on 0123.S1 and deletes the §9.3 handlers that 0123.S1 converts, and F-9.3.18, rated High, exists only on those handlers. D14 ("The shared OAuth flow lands first") was settled while connectors were staying, and D6 of [`0124-connector-removal`](../0124-connector-removal/decisions.md) kept CA-0 on 2026-11-15 without settling this order. Options: (a) add 0149.S6 to the `depends-on` of 0123.S1 and keep the conversion of the §9.3 handlers, which delays F-9.3.18, 0124.S1, and through 0124.S1 also 0123.S2, behind 0149.S2, 0149.S4, and 0149.S6; (b) build the start page on today's deployment OIDC login and let 0149.S6 replace it later, which reads the tenant from a raw claim that 0149 identifies as a defect on broker tokens; (c) drop the conversion: 0124.S1 closes F-9.3.18 by deleting the handlers, loses its edge to 0123.S1, and renames `pkg/connectoroauth`, and 0123.S1 lands the shared flow on the account-link routes with or before 0151.S2, with `depends-on: [0149.S6]`. Recommendation: (c), because it closes F-9.3.18 soonest, removes work that the next step deletes, and follows the program's "No transition modes" rule. Under (c), 0123.S1 moves `closes: [F-9.3.18]` to 0124.S1, the CA-0 banner and its "Code exchange and token storage" row lose the §9.3 clause, CA-0's requirements land on the account-link routes of §15.1 in the same step as their code, and 0151's F-9.3.18 bullet under "Defects found while verifying" and its 0151.S2 text name 0124.S1 as the step that closes the defect. Under (a) or (b), CA-0 needs a "Specification changes" row for the hardened §9.3 flow, a live requirement that only the subject who requested a link can complete it (CP-2 today, withdrawn with the threat model), and a documentation row for the converted routes. In every option the owner also names the shared package that replaces `pkg/connectoroauth` and its Redis state key that replaces `conn:oauth:state:{state}`, for example `pkg/oauthlink` with `oauth:link:state:{state}`, and 0123, 0124, and 0151 use that name. Under (a) or (b), 0123.S1 renames the package and the key. Under (c), 0124.S1 renames them. Blocks: 0123.S1, 0124.S1, 0123.S2 through its edge to 0124.S1, and 0151.S2. The other change is `0124-connector-removal`, which records the same question as its open decision O21. (raised by the M3 readiness review, 2026-11-19; sources: 0123-F1, 0123-F3, connectors-llm-billing-C4, connectors-llm-billing-C5; mirrors 0124 O21, requested by change 0124)

2. **O2. The link start page in a deployment with no OIDC browser login.** CA-0's defense against the account-link attack is the login and subject check on the start page. `playground.authMode` takes `oidc`, `apiKey`, or `dev` (§27.3), and neither 0123, 0149, nor 0151 states what the start page does under `apiKey` or under `global.devMode=true`. If the step skips the login there, a link URL sent to another user completes under the sender's subject, which is F-9.3.18 again in that mode. Options: (a) account linking requires an OIDC identity source, and the link routes answer a typed refusal without one; (b) the start page accepts a pasted bearer in `apiKey` mode and compares its subject with the flow's; (c) dev mode skips the login and binds the flow to the synthetic dev user. Recommendation: (a) for `apiKey` mode, and (c) for dev mode only, because dev mode has one synthetic principal and no second subject to confuse. The answer goes into "CA-0" with a security-tier case for each mode. Blocks: 0123.S1 and 0151.S2. (raised by the M3 readiness review, 2026-11-19; sources: 0123-F2)

3. **O3. Whether memory removal waits for the egress pattern, and which step writes `externalDataNotErased` and `docs/tutorials/agent-memory.md`.** 0123.S2 depends on 0124.S1 so that the egress pattern exists when memory goes, but 0124.S1 only removes connectors. The identity assertion lands in 0124.S2 (`depends-on: [0127.S2, 0127.S4, 0127.S10, 0151.S3]`), the documentation of external services in 0124.S4, `netagent` in 0127.S2, `userCredential` links in 0151.S3, and outbound connector routes in 0148.S1 and 0148.S2. The receipt field reads bindings and links that do not exist when 0124.S1 lands, and the documentation gate fails a tutorial that names a setting the catalogs lack. 0124's "Changes to Lenny's documentation" also names `docs/tutorials/agent-memory.md`, and neither change names the step that writes it. Options: (a) keep one step and add 0124.S2, 0124.S4, 0127.S4, and 0151.S3 to its `depends-on`; (b) split: 0123.S2 removes built-in memory with no dependency on 0124, and a new 0123.S3 lands `externalDataNotErased` and the tutorial with `depends-on: [0124.S2, 0151.S3]`, adding 0148.S2 only if the tutorial shows the private-network case, and 0124 names that step as the tutorial's writer. Recommendation: (b), because the removal adds no behavior and can land early, and the receipt field needs bindings and links that exist only after those steps. Blocks: 0123.S2. The other change is `0124-connector-removal`, which records the same question as its open decision O22. `0148-tenant-outbound-connector` names the split and the edge to 0148.S2 as this change's decision. (raised by the M3 readiness review, 2026-11-19; sources: 0123-F5, connectors-llm-billing-C6; mirrors 0124 O22, requested by changes 0124 and 0148)

4. **O4. Whether migrations 0032 and 0044 stay.** CA-10 keeps both migrations as history and also says the `vector` extension requirement goes. Migration 0044 runs `ALTER TABLE agent_memory ADD COLUMN embedding vector(256)`, so every database that runs the chain from the start needs pgvector or the embedded stack's `vector` shim while the migration stays. Options: (a) keep both migrations and add a drop migration; pgvector stays a prerequisite of the migration chain, and the documentation says so; (b) remove the `agent_memory` content from 0032, 0044, and the later migrations that name the table, including the reserved preflight tenant of 0096, and drop the pgvector image from `tests/testinfra/containers/postgres.go` and `compose/default.yml`, the `VECTOR` entry from `deploy/terraform/cloud/azure/managed-services.tf`, and the embedded shim. Recommendation: (b), because no database has applied the chain outside test environments and (a) keeps an install prerequisite for a feature that no longer exists. The owner rules, because (b) departs from the current text "Migrations 0032 and 0044 stay as history" and rewrites applied migrations. Blocks: 0123.S2. (raised by the M3 readiness review, 2026-11-19; sources: 0123-F7)

5. **O5. The lifetime of a link URL that a prompt shows for longer than 10 minutes.** CA-0's flow identifier lives 10 minutes. A link prompt under UC-8 of [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) stays pending for `maxElicitationWait`, 600 seconds by default and set per pool, so a pool that raises `maxElicitationWait` shows a prompt whose URL has expired. Options: (a) the link URL names a link request, and the start page mints the one-time flow identifier, with its 10-minute lifetime, when the user opens it; (b) the flow identifier's lifetime follows the prompt's; (c) keep 10 minutes and refresh the prompt's URL when it expires. Recommendation: (a), because the one-time identifier keeps its 10-minute window and the URL in a prompt or in a combined missing-links response stays usable, while the start page's login and subject check still binds the flow to the requesting subject. Blocks: 0123.S1 and UC-8 in 0151. (raised by the M3 readiness review, 2026-11-19; sources: 0123-F4)

6. **O6. Which bindings `externalDataNotErased` names for a user, and whether it names the provider account.** "External memory pattern" now states the field's format, its empty case, the read before the link delete, and the tenant case. Two questions remain. First, a binding deleted before the erasure carried the user's identity and is absent from a receipt that reads current bindings, which is the case the field exists to prevent. Second, the receipt names hosts and the user, and a memory service that keys data on a `userCredential` link's provider account cannot find it once the link is deleted. Options for the bindings: (a) the tenant's `identityAssertion` bindings current at the erasure and the user's `userCredential` links the erasure deletes, with the operator guide stating that a deleted binding is not named; (b) the Token Service records each host to which it delivered an assertion or a link token for the user, at mint time, and the receipt names that set, which the erasure then deletes. Options for the provider account: (c) the receipt names the hosts alone, with the Lenny user it already names; (d) the receipt also names the provider account of each deleted link. Recommendation: (b), because the receipt then never omits a host that held the user's identity, at the cost of a per-user host record that the Token Service writes when it mints and that the erasure deletes; and (c), because the receipt is kept in the audit trail after the erasure, and a provider account there would keep a personal identifier of the erased user. Blocks: the step that lands `externalDataNotErased` under O3, and lines in 0124 CR-2 and 0151 that state which hosts the erasure job reports. (raised by the M3 readiness review, 2026-11-19; sources: 0123-F6, connectors-llm-billing-C6)

## Decisions

> **Partly superseded in revision 17, 2026-11-15, under [`0124-connector-removal`](../0124-connector-removal/change.md).** The owner decided on 2026-11-15 to remove connectors: "Yes, let's drop connectors." The decisions "Remove built-in memory" and "The shared OAuth flow lands first" stay. Every other row concerns connectors, and the table keeps it as the record.

These are settled by the owner, and the rationale stays here so a later reader does not reopen them by accident. The rows were numbered D1 to D14 on 2026-11-19 in their existing order. They carry no dates: each was settled before the design moved into `changes/`, and `review-history.md` names the revision that recorded each where it is known.

| ID | Decision | Text or effect |
| :-- | :-- | :-- |
| D1 | Remove built-in memory | The owner asked for "Dropping memory store in Lenny + replacing with this generic mechanism". |
| D2 | No stored tool catalog | The owner rejected registering tools and arguments apart from the MCP server: "that creates a shadow config that will be out of sync". `tools/list` always asks the server. |
| D3 | The authorization failure reaches the runtime | "Shouldn't the auth error be propagated to the runtime so it knows it needs to authenticate?" The failure is translated at the gateway boundary, because the runtime's server is the adapter's local server. See "CA-5". |
| D4 | A link check runs regardless of runtime | The owner: "the Coder-style check makes sense no matter what". Coder, a cloud development environment product, requires a user to link each external account that a workspace template names before it creates or updates the workspace, unless the template marks that account optional. The owner's phrase refers to a check of that kind. |
| D5 | The trigger is a connector property | The owner replaced a pool-level "required" flag with "requiring auth to list tools". This design detects that property live, for the owner's own reason that a stored flag can drift. |
| D6 | The runtime declares tolerance | "The runtime should indicate whether they can gracefully handle failed `tools/list`". See "CA-8". |
| D7 | A parent retries after a link | No push notification. The refusal carries `details.retryAfterSeconds`. See "CA-7". |
| D8 | Impersonation and linked connectors | "Accept and document the risk." No check is added for this design's sake. See "Limits". |
| D9 | Connector tokens stay keyed by environment | The reason is separation: a token granted in one project context is not the token another context draws. Policy controls access under either key, with or without the environment, so policy is not the reason. |
| D10 | The capability snapshot stays | "Keep the snapshot and don't change anything else." A deployer who wants enforcement downstream uses OAuth scopes. See "CA-8". |
| D11 | An explicit resume checks links first | The check runs before an explicit resume of a released pod starts its new process, so a user who links gets the connector on that resume. See "CA-6". |
| D12 | The bridge reaches every runtime | The platform delivers it to every sidecar `type: agent` pod, using the runtime supervisor's delivery pattern. See "CA-9". Superseded on 2026-11-12 by [`0139-runtime-protocol`](../0139-runtime-protocol/decisions.md#decisions) D7, which settled RP O4 (a): the bridge ships with the runtime SDKs and as a release binary, and the platform delivers no copy. |
| D13 | The bridge keeps its own init container | The owner chose this over sharing `lenny-supervisor-stage`, accepting about one second per pod and leaving the supervisor untouched. See "CA-9". Superseded on 2026-11-12 with the decision above: no init container delivers the bridge. |
| D14 | The shared OAuth flow lands first | It is its own proposal, "CA-0", ahead of this design's other proposals and of [UC-2](../0151-user-credential-delivery/change.md#uc-2-the-oauth2link-source-and-account-linking) in [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md). "Instructions for reviewers of other designs" carries the changes this requires elsewhere. |
