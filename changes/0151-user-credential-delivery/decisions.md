# Decisions: 0151 User credential delivery

## Open decisions

The M3 readiness review of 2026-11-19 raised the questions below, which continue the numbering of decisions 1 to 44.

- **45. How link state events reach every gateway replica, and how a lost event is recovered.** UC-8 sends a link state event on `WatchLinkStates`, a server-streaming call that each gateway replica opens to the Token Service, and decision 42 records it as settled under D12 of `0124-connector-removal`. The Token Service runs as a Deployment of two or more replicas with no affinity (§4.3), so a stream lands on one replica, and the replica that refuses a refresh emits the event to the gateway replicas whose streams sit on it alone. An event written while no stream is attached, during a restart of either side, is lost, because the call has no cursor and the gateway runs no reconciliation, so a link prompt is silently missing and UCR-10 fails with no error or metric. Which gateway replica writes the prompt on the stream of a root session that another replica coordinates is also unstated. Options: (a) keep `WatchLinkStates` and `user_link_prompts`, and add both a fan-out, in which every Token Service replica delivers each event to every subscriber (for example through a Redis channel) or each gateway replica opens one stream per Token Service endpoint through a headless Service, and a reconciliation, in which the gateway, on each connect and reconnect, lists the links in `user_act_required` for users with non-terminal sessions holding a binding on those providers and inserts prompts conditionally; (b) replace the event stream with a durable outbox row in the Token Service's store that the gateway polls; (c) accept lost prompts as a residual, stated under "Residual risks" and against UCR-10. Recommendation: (a), because it keeps the settled call and table and closes the loss. Whichever option is chosen, "Tests" gains a Tier 4 case with two Token Service replicas and a Tier 8 case for a Token Service replica restart. Blocks: 0151.S8. (raised by the M3 readiness review, 2026-11-19; sources: 0151-F2, 0151-F9)
- **46. The `/v1/credentials` wire names.** §4.9 names the body field `credential` and the identifier `credential_ref`, the code uses `secret` and `ref` (F-4.9.47), and this design's admin route body uses `secret` while its path parameter and audit records use `credentialRef`. `0133-llm-upstreams-and-cost-budgets` records F-4.9.47 as shared with this change and leaves the names to UC-1, and neither change settles them. Options: (a) the code's names, `secret` in the body and `ref` as the identifier, with §4.9 and §15.1 edited to match and `credentialRef` kept as the name of the same identifier in paths and audit records; (b) §4.9's names, `credential` and `credential_ref`, with the code and this design's admin route body changed to match. Recommendation: (a), because the design's new admin route already uses `secret` and no deployment in the wild depends on either spelling. Blocks: 0151.S1 and the closure of F-4.9.47. (raised by the M3 readiness review, 2026-11-19; sources: 0151-F5)
- **47. Which pods count as used on a pool with several slots.** Decision 41 is settled, but it records that the used-pod reading on a pool with several slots "is a choice of revision 31 that awaits the owner's confirmation", and no later record confirms it. `0152-user-git-identity` decision 52 records the same reading as settled, and `0124-connector-removal` relies on it and raises it as its O17. 0152 now raises the question as its open decision 58, and 0124 O17 and 0152 decision 58 follow the answer here. Options: (a) confirm the reading: a pod any of whose slots has served a session and been released counts as used, so a `userCredential` binding, an `identityAssertion` binding, and a repository under a VCS pool with `userAuthorization: required` are refused there, and a marked pod is never given another slot; (b) count only a slot that has served a session as used, and admit a new session on an unused slot of the same pod. Recommendation: (a), because the ground of decision 41 is the pod-wide components (`netagent`, the adapter, and the sandbox kernel), which a slot release does not clean, and the owner withdrew O10 of the removal design on that ground ("refusal on both (I changed my mind)"). Blocks: 0151.S3 and 0151.S5, and through decision 44 the matching rules of 0124.S2 and 0152.S2. (raised by the M3 readiness review, 2026-11-19; sources: 0151-F8, credentials-git-C3; mirrors 0124 O17 and 0152 decision 58)
- **48. Options: (a) confirm decisions 25 (where `registered` rows live), 27 (the add-on model), 28 (where the link flow lives), and 40 (reads in allow-list mode) as recommended; (b) reopen any of them, naming which. Recommendation: (a), because each is reflected consistently in `change.md` and states its cost. Blocks: 0151.S1 (decision 25), 0151.S2 and 0151.S7 (decisions 27 and 28), and 0151.S4 (decision 40). (raised by the M3 readiness review, 2026-11-19; sources: the review's status assessment, OD-B)
- **49. Which step of `0123-connector-authorization-and-external-memory` writes `externalDataNotErased` and the external memory tutorial.** 0123.S2 adds the §12.8 receipt field `externalDataNotErased`, computed from `userCredential` links (0151.S3) and `identityAssertion` bindings (0124.S2), and documents them, but it depends on 0124.S1 alone. Options: (a) split 0123.S2 into the removal of built-in memory (CA-10) with no dependency on 0124, and a second step for `externalDataNotErased` and `docs/tutorials/agent-memory.md` that depends on 0124.S2 and 0151.S3, and on 0148.S2 if the tutorial shows the private case, with this change and 0124 each stating which hosts the erasure job reports; (b) keep one step and add 0124.S2, 0151.S3, and 0148.S2 to its `depends-on`, which delays the memory removal. Recommendation: (a). The answer is the owner's for 0123 and 0124, which record the same question (0124 as its O22). This change then states, in UC-2's "Lifecycle and revocation at the provider", which type hosts of a user's links and rows the erasure receipt names. Which hosts those are, including whether the link erasure returns the hosts of the links it deletes or the Token Service records each host at mint, is O6 of 0123 and O25 of 0124, and 0123 asks this change to state the hosts its link erasure returns once that is settled (0123-F6). Blocks: no step of this change; 0123.S2. (raised by the M3 readiness review, 2026-11-19; sources: connectors-llm-billing-C6, and 0123-F6 requested by change 0123; mirrors 0123 O3 and O6, and 0124 O22 and O25)
- **50. Recommendation: (c), as 0123 recommends, because it closes F-9.3.18 soonest and removes work the next step deletes. Under (c), the F-9.3.18 bullet under "Defects found while verifying" and the 0151.S2 text name 0124.S1 as the step that closes the defect, and 0151.S2 keeps its edges on 0123.S1 and 0149.S6. Under (a) or (b), the text stays. In every option the owner also names the shared package that replaces `pkg/connectoroauth`, which decision 29 leaves as "renamed when CR-A lands". Blocks: 0151.S2. (raised by the M3 readiness review, 2026-11-19; requested by change 0123; mirrors 0123 O1 and 0124 O21)
- **51. How the link URL in a link prompt stays usable for the prompt's lifetime.** UC-8's prompt carries UC-2's `linkUrl` for a CA-0 flow, whose one-time flow identifier lives 10 minutes, and the prompt stays pending for `maxElicitationWait`, 600 seconds by default and set per pool, so a pool that raises `maxElicitationWait` shows a URL that has expired. Options, as 0123 O5 states them: (a) the link URL names a link request, and the start page mints the one-time flow identifier, with its 10-minute lifetime, when the user opens it; (b) the flow identifier's lifetime follows the prompt's; (c) keep 10 minutes and refresh the prompt's URL when it expires. Recommendation: (a), as 0123 recommends, because the one-time identifier keeps its 10-minute window, the URL in a prompt or in the combined missing-links response stays usable, and the start page's login and subject check still binds the flow to the requesting subject. Under (a), UC-2's "Flow", step 2, and UC-8's **URL.** state that `linkUrl` names a link request. Blocks: 0151.S8, and the `linkUrl` of 0151.S2. (raised by the M3 readiness review, 2026-11-19; requested by change 0123; mirrors 0123 O5)
