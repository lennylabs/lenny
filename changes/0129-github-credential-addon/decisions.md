# Decisions: 0129 GitHub credential add-on

## Open decisions

The M3 readiness review of 2026-11-19 moved decisions 2, 3, 4, 6, and 7 here from "Decisions", because none of them has an owner answer, and raised decision 9. Each entry keeps its number.

- **2. Sessions across owners** (formerly [`0152-user-git-identity` decision 23](../0152-user-git-identity/decisions.md#decisions)). Open. A child token has one `target`, the account that owns its repositories. What happens to a session whose writable entries in state `granted` span two owners? Options: (a) refuse the second owner on the binding with `USER_TOKEN_MULTI_OWNER`, at the cost that a session cannot author pull requests in two organizations and cannot push to a fork under another account that it declares writable through `writableRepositories` of [`0127-egress-and-git`](../0127-egress-and-git/change.md#credentials); (b) one child per target, with `netagent` selecting by request path, which adds path parsing to the attach step; (c) one API child for the base owner and one git child per owner, with `netagent` selecting the git child by the repository it already reads from the smart HTTP path, which keeps fork pushes working with no path parsing on the API. Under (a) or (b) the decision also settles which owner counts as the first, since the entries are a set and two replicas can mint at once, whether the refusal happens at session creation or at the first mint, the HTTP status and response format of `USER_TOKEN_MULTI_OWNER`, and what a grant in the middle of a session that adds an owner does. Recommendation: the change recommended (a). The M3 readiness review recommends (c), and, for any refusal that remains, a refusal at session creation that lists the owners and a refusal of a mid-session grant that adds an owner. It blocks 0129.S2 and the `USER_TOKEN_MULTI_OWNER` entry of the error catalog. The other change is [`0127-egress-and-git`](../0127-egress-and-git/decisions.md), which owns `writableRepositories`. (extended by the M3 readiness review, 2026-11-19; sources: 0129-F1, 0129-F4)
- **3. Read-only repositories on the child** (formerly [`0152-user-git-identity` decision 24](../0152-user-git-identity/decisions.md#decisions)). Open. Does the API child cover the repositories a session declares read-only? Options: (a) they are absent, per [`0142-security-oversight` decision 25](../0142-security-oversight/decisions.md#decisions)'s reasoning, at the cost that `gh pr view` on a read-only declared repository gets 404 from GitHub; (b) a second read-only child selected by path, at the cost that decision names. Recommendation: (a). It blocks 0129.S2. (moved to "Open decisions" by the M3 readiness review, 2026-11-19; sources: 0129-F1)
- **4. Review comments** (formerly [`0152-user-git-identity` decision 34](../0152-user-git-identity/decisions.md#decisions)). Open. Does `github-deny` refuse `addPullRequestReview` for every event? Options: (a) yes, so `gh pr review --comment` stays refused by default, an agent loses inline review comments, and `gh pr comment` is the substitute; a tenant can drop the name and accept approval with it, since rules no longer read the event; (b) the preset reads `event: COMMENT`, which needs an input check of the kind D1 removed. Recommendation: (a). It blocks 0129.S3. (moved to "Open decisions" by the M3 readiness review, 2026-11-19; sources: 0129-F1)
- **6. The user's email addresses** (formerly [`0152-user-git-identity` decision 46](../0152-user-git-identity/decisions.md#decisions)). Open. S6, in the VCS layer's revision 25, found on an App holding the email addresses permission that a child does not narrow that account permission, so an agent can read its user's private addresses through the API child. Options: (a) add `GET /user/emails` and `GET /user/public_emails` to `github-deny`, which a tenant can drop, at the cost that a tool or script that reads the user's addresses through the API fails inside a session, and with the preset's version raised from 8; (b) leave them, which lets an agent read its user's private addresses; (c) drop the App's email permission, which also breaks link providers with `identityBinding: verifiedEmail`, since that reads `GET /user/emails` with the parent. Recommendation: (a). It blocks 0129.S3. (moved to "Open decisions" by the M3 readiness review, 2026-11-19; sources: 0129-F1)
- **7. A per-person limit on child mints** (formerly [`0152-user-git-identity` decision 48](../0152-user-git-identity/decisions.md#decisions)). Open, found in the review of the VCS layer's revision 25. GitHub's 2,000 token requests per hour apply per App, so they are shared by every user of the tenant. When settling decision 1 the owner said limits should be left to GitHub "unless GH's limit is global for all users combined, in which case I agree we need a limit". Options: (a) a per-person hourly limit on mints, set by Helm and narrowed per tenant, under which a person past the limit gets a retryable `USER_TOKEN_RATE_LIMITED`, and which must sit well above normal use, since each session takes one or two mints; (b) no limit, which lets one injected session exhaust the tenant's App for an hour. Recommendation: (a), settled against the result of spike S2b in `steps.md`, which measures which GitHub budget a scoped mint and a refresh consume, because S2 left the scope of the 2,000 per hour unverified. It blocks 0129.S2, "Configuration by scope", and "Documentation". (S2b added by the M3 readiness review, 2026-11-19; sources: 0129-F1, 0129-F5)
- **9. A guardrail on widened template permissions.** Open. [Decision 5](#decisions) settled that `narrowing.permissions` on `github-scoped` is template data a `tenant-admin` can widen. It did not settle who may widen it. Widened to `contents: write` or `actions: write`, merges and content writes rest on `github-deny` alone, and the only controls are an audit event and a posture row. [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) gives `security-admin` the `requestRules.requiredPresets` guardrail for the preset, and no guardrail bounds the template's permissions. Options: (a) a maximum permission set on the tenant security record, a guardrail row of SO-2 in [`0142-security-oversight`](../0142-security-oversight/change.md) that refuses a template write above it; (b) no guardrail, with the audit event and the posture row as today. Recommendation: (a). It blocks the template write of 0129.S2 and the matching SO-2 row of 0142. The other change is [`0142-security-oversight`](../0142-security-oversight/decisions.md), which owns the guardrails. (raised by the M3 readiness review, 2026-11-19; sources: 0129-F14)
