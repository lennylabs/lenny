# Decisions: 0165 A formal model of the token rules

## Open decisions

Each open decision answers a counterexample under "Counterexamples" in `change.md`, which states the scenario and confirms it against the text, and each names its recommendation. A decision that changes a rule lands in a change of its own, or in a revision of 0164 while it is open, and the model's predicate changes with it. CX-1 and CX-12 need no decision: 0164.S1 closes CX-1, and 0164 decision 8 settled CX-12.

1. **CX-2 Whether a rotation records the token it replaces (0164 O3).** The model answers the two questions of O3 for three lineages: 0164.S1 as built leaves a leaked token's holder able to keep a successor it rotated before the owner revoked the leaked token, and option (a) of O3 closes that and lets a holder of a live token of the owner's identity revoke the owner's successor through the replaced token. No lineage closes both, because the Token Service cannot tell the owner from the holder when each presents a live token of the owner's identity. Options: (a) restore the rotation edge, as option (a) of O3, and state in the operator security guide that a leak of more than one token of a user is answered with a full revoke of the user, which ends a holder's other live tokens; (b) keep the build, record the replaced `jti` where the cascade does not walk it, and state that a leaked token that may have been rotated is answered with a full revoke, as option (b) of O3; (c) keep the build as it is. Recommendation: (a). Continued access by a holder of a leaked token is worse than a denial of service the owner ends by signing in again, and under (a) the denial of service needs a second live token of the owner's identity, which a full revoke ends.
2. **CX-3 A playground bearer outlives the revocation of its subject (`P3_derived_playground`).** Options: (a) record the playground bearer in `issued_tokens` with the subject's `jti` as `parent_jti` in the `apiKey` mode, so the cascade revokes it and every replica refuses it through the revocation cache; (b) state in §13.3 and §27.3 that revoking a subject leaves its playground bearers live until their `exp`, which `auth.capabilityTokenTtlSeconds` bounds, and that logout or a full revoke ends them; (c) have the revocation request also write the playground revocation marker for bearers the playground session records name. Recommendation: (a), because it reuses the lineage and closes G2 (the revocation request then finds a row for a playground subject).
3. **CX-4 An impersonation bearer outlives and escapes the caller's token (`P3_derived_impersonation`, `P9_impersonation_bounded_by_caller`).** Options: (a) clamp the bearer's `exp` to the caller token's `exp` as well as to `durationSeconds`, and state that revoking the caller's token does not end the session, which `DELETE`, a full revoke of the platform-admin, or an operator revocation of the bearer does; (b) also record the caller's `jti` on the impersonation row in a column the impersonation predicate does not read, and have the cascade walk it; (c) keep the rule and state both behaviours. Recommendation: (a), because it is one comparison and keeps the impersonation row predicate of rule 2.
4. **CX-5 An upstream ID token cannot be named as a revocation root (`P3_every_lineage_root_revocable`, G3).** A token derived from an ID token records the ID token's `jti` as its parent, and the revocation request refuses the ID token because it has no row. Options: (a) accept a root without a row: walk `parent_jti` from the presented `jti` and insert a revoked row for it, so the Token Service also refuses it as a subject or actor afterwards; (b) state that an ID token is not a revocation root and that its derived tokens are revoked one by one or by a full revoke; (c) record a row for every ID token the Token Service accepts as a subject. Recommendation: (a).
5. **CX-6 A child is broader than its actor (`P1_no_broader_than_lineage_parent`).** Rule (a) bounds a child by its subject only, so a child minted from an unrestricted subject with a narrow actor token is unrestricted while its lineage parent is narrow. No user gains reach, because the caller holds the subject. Options: (a) require the actor's scope to grant every issued value too, so a child is no broader than either token; (b) keep the rule and state that the actor names the delegator and bounds lifetime and lineage, and the subject bounds reach. Recommendation: (a), because a delegation that exceeds its delegator is the reading most callers will assume.
6. **CX-7 Strictly narrower by values admits a copy at equal reach (`P5_other_identity_strictly_narrower`, `P5_child_other_identity_strictly_narrower`).** A request that lists every action of a domain does not grant the domain wildcard, so it counts as strictly narrower while admitting the same tools. Options: (a) define strictly narrower on reach: the requested values admit a strict subset of the tools the subject's scope admits under the tool catalog, so a domain wildcard counts as every action its domain's tools declare; (b) keep the value comparison and state that a wildcard is broader because it admits tools added later; (c) refuse a request that names every action of a domain the subject holds by wildcard. Recommendation: (b), because no user gains reach (`P5_no_identity_escalation` holds) and the rule cannot be stronger than bearer possession, as "Limits" states; (a) needs the catalog at the Token Service.
7. **CX-8 A child's depth can fall below its subject's (`P7_depth_not_below_subject`).** The child's depth is the actor's plus one, whatever the subject's, while rule (b) says an exchange rejects a decrement. Options: (a) state in rule (b) that the comparison is with the actor for a child mint and with the subject otherwise; (b) set a child's depth to the larger of the two depths plus one. Recommendation: (a), because the actor is the delegator whose depth the child extends, and the caller holds the subject anyway.
8. **CX-9 A delegated token loses its `act` claim on a narrowing or a rotation (`P7_delegated_token_names_actor`).** An exchange without `actor_token` issues no `act`, so a narrowed copy of an `a2a_delegation` child keeps depth 1 and `typ` `a2a_delegation` but no longer names its delegator. Options: (a) copy the subject's `act` claim onto every exchange without `actor_token`; (b) refuse an exchange without `actor_token` whose subject carries `act`. Recommendation: (a), a one-row change to the claim table of §13.3.
9. **CX-10 A revoked caller token authenticates a mint (`P8_revoked_caller_cannot_mint`, G4).** Options: (a) read the caller token's `issued_tokens` row in step (1a) of every mint and refuse a revoked caller with `401 invalid_client`, as decision 9 of 0164 does for the revocation request; (b) state that a mint does not check the caller's revocation, because the caller's identity only decides whether the request must narrow. Recommendation: (a), because it makes "a revoked token authorizes nothing" a single rule.
10. **CX-11 A full revoke misses the delegations the user made for another identity (`P10_full_revoke_reaches_delegations`).** Step 5 of §11.4 revokes the user's issued tokens by `sub` and does not cascade, so a child the user minted as actor for another user's subject (carrying the other `sub`, `act` naming the revoked user, and a revoked parent) stays live. Options: (a) have step 5 revoke the lineage descendants of every token it revokes; (b) have step 5 also revoke the rows whose `act_sub` is the user, which rule 6 of **Platform-admin impersonation.** already does for impersonation rows; (c) keep step 5. Recommendation: (a), because it reuses the cascade and also reaches narrowed copies other callers derived from the user's tokens.
11. **CX-13 Whether any token of the user may send the revocation request (0164 O4).** The model confirms the premise of option (a) of O4: a revocation request revokes only tokens whose bytes the presenting user holds and their lineage descendants, in every variant. It also shows that a token whose scope admits nothing revokes the user's unrestricted token, and that under option (a) of CX-2 a narrow token plus a token the owner rotated away from revoke the owner's current token. Option (b) of O4 would stop that and would also stop the owner's own cleanup of a revoked leaked root, because no live token is that root or its ancestor. Options: (a) keep decision 9 of 0164 as written; (b) accept the user's own caller only when its token is the subject token or one of its ancestors; (c) accept the user's own caller only when its token carries no `scope` claim or `tools:*`. Recommendation: (a), as 0164 recommends; option (c) is the variant to choose if the denial of service of CX-2 under its option (a) matters, because an agent's narrowed token then cannot revoke.

## Decisions

1. **Whether to build a formal model of the token rules (owner's request of 2026-11-20).** Three review passes over changes 0162, 0163, and 0164 found about ten design gaps in token exchange, narrowing, revocation, and impersonation (TOKX-I2 to TOKX-I11, and open decisions O1 and O2 of 0164). The owner asked on 2026-11-20 for a formal model that makes the design of those rules sound, and agreed the plan of two steps: 0165.S1 states the properties in plain words and checks them with an Alloy model, and 0165.S2 checks the same properties against the Token Service with generated property tests in Go. A TLA+ model of the concurrent orderings is held as a candidate until the owner has seen the Alloy results. The change is outside program v1, in the manner of 0161 to 0164.
