# Tenant scoping and identity

Status: `Draft`, revision 47, 2026-11-24. Programs: [v1](../programs/v1.md).

## Problem

A company runs Lenny as a multi-tenant SaaS. One of its customers has several teams and wants each team to have its own egress and git configuration, with single sign-on (SSO) and user lifecycle coming from the customer's own directory.

The following gaps stand in the way:

- In [`0127-egress-and-git`](../0127-egress-and-git/change.md), egress policy, VCS credential pools, and credential bindings are tenant-wide. Any client in a tenant can name any binding with `scope: onRequest` or any allowlisted repository, and any agent in a tenant can fetch any allowlisted repository at run time. The environments of [§10.6](../../spec/10_gateway-internals.md#106-environment-resource-and-rbac-model) select runtimes only. They also selected connectors until [`0124-connector-removal`](../0124-connector-removal/change.md#cr-1-removal) removed connectors.
- Lenny trusts one OpenID Connect (OIDC) issuer per deployment and has no SCIM (System for Cross-domain Identity Management), the protocol through which a customer's directory provisions and deprovisions users. A SaaS operator therefore needs an identity broker for per-customer SSO, which the specification neither says nor bounds with a contract, and a customer cannot bring its own issuer.

## Scope

This design covers environment scoping of the objects in [`0127-egress-and-git`](../0127-egress-and-git/change.md), the identity model (a broker by default, or a customer's issuer per tenant), a SCIM server, and the user lifecycle path into Lenny. Migrating a tenant between issuers is out of scope. It treats those egress objects as fixed inputs. [`0142-security-oversight`](../0142-security-oversight/change.md) owns security roles.

## Terms

| Term | Meaning |
| :-- | :-- |
| E | The environment a session runs in. A session whose create named no environment has none, which this document writes as E = ∅. See "A session's environment". |
| Explicit path and transparent path | An explicit path is a session create that names an environment: `/v1/environments/{name}/sessions` or the `environment` body field. A protocol adapter's environment-scoped form, such as the MCP adapter's `/mcp/environments/{name}` or a provider adapter's model name `environments/{name}/{model}`, reaches the client API as the `environment` body field ("RO-10" of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md#ro-10-the-provider-adapters)). The transparent path is a create that names none, such as `POST /v1/sessions`, on which §10.6's transparent filtering applies: the caller sees the union of the runtimes selected by every environment in which its groups hold a role, and runtimes no such environment selects are hidden. |
| Scoped object | A VCS credential pool, credential binding, user credential type, or link provider whose `environments` list names the environments whose sessions can use it. An object with no list is tenant-wide. |
| `environmentPolicies[E]` | The section of the tenant egress policy that holds environment E's own always-allowed, session-requestable, and denied hosts, and its egress and git routes. |
| `visible`, `always(E)`, `requestable(E)`, `denied(E)`, and `routes(E)` | The sets that combine tenant-wide entries with E's own objects, hosts, and routes. "Effective policy" under TS-1 defines them. |
| Pod with no per-session policy | A pod with several slots on a pool whose runtime class does not answer slot attribution, which the controller records in the pool's status. Its `netagent` keeps the union over the pod's sessions, so its egress policy cannot differ by session, and it evaluates every session with E = ∅ ([`0127-egress-and-git`, "Slot attribution and fetch grants"](../0127-egress-and-git/change.md#slot-attribution-and-fetch-grants), **Per-slot scopes (decision 60)**). A one-session pod, and a pod with several slots on a pool that answers slot attribution, apply each session's own policy to its slot. |
| Sharing path | A pair of `dangerouslyShare` entries, outbound in one environment and inbound in another, through which a delegated child of a session in the first runs in the second. A path works only while the tenant setting `dangerouslyAllowCrossEnvironmentSharing` is on. See "Cross-environment sharing (decision 14)". |
| Delegation gate and environment caveat | The check the gateway runs on each `session.create` (formerly `start_child_session`, today `lenny/delegate_task`), and for `runtimes.list`, to decide whether the session may reach the target runtime. Today `runtimeAuthorizedForCaller` and `crossEnvReachable` decide it from the caller's environment memberships. Under TS-3 it reads the session's E and the live sharing declarations, and under [`0166-delegation-primitives`, "DP-1"](../0166-delegation-primitives/change.md#dp-1-session-grant) it is the environment caveat of the session grant, checked at the post-chain point of RT-2. |
| Crossing, target T, and crossing mark | A crossing is a `session.create` over a sharing path. T is the target environment, and the crossing child runs under T's policy. The crossing mark is the child's `crossed_from_environment` column, which holds the caller's environment and stops a second crossing. |
| Identity source | Where a tenant's users authenticate: the deployment source or a customer source. |
| Deployment issuer and deployment source | The OIDC issuer at the Helm value `auth.oidc.issuerUrl`, which every tenant uses by default. It can be the operator's identity broker. On it, the tenant comes from a token claim. |
| Identity broker | An identity service an operator runs or buys, which federates each customer's own identity provider (IdP) behind one issuer and states the customer's tenant in a claim. "Broker contract" states what Lenny requires of it. |
| Customer source | A row in `tenant_identity_sources` naming a customer's own OIDC issuer, pinned to one tenant. See "Identity source record (TS-6)". |
| Shared issuer | An issuer that serves many customers, such as Google's, so the issuer alone cannot select a tenant. A platform admin lists it in `identity.sharedIssuers`, and each of its rows pins an audience, an organization claim, or both. "Issuer pin and proof" defines the term exactly. |
| Pin (issuer pin), domain pin, and domain-pinned row | A pin is what ties a customer source to one tenant: the exact issuer, and on a shared issuer also the pinned audience or claim value. A domain pin is a pin whose claim value is a DNS domain (`pin_claim_is_domain`), such as Google's `hd`, and a domain-pinned row is a source row that holds one. The word also names unrelated mechanisms: the tenant pin, which is the pod label that "Claim, bind, and tenant pin" under "Terms from other designs and the platform" defines, and the credential-pinned host rule (`credentialPinned`) of the egress design. |
| Canonical subject | A customer source's user key, `~<source_id>~<value of subject_claim>`. A deployment source's `sub` keeps its form. See "Several IdPs in one tenant, and namespacing". |
| Lenny subject and subject namespaces | The subject half of the user key `(tenant_id, subject)`. A person's Lenny subject is its canonical subject, a service caller's is `~svc~` followed by its canonical subject, and an `agent` caller's is `~agt~` followed by it, so the three caller types never share a subject ([`0143-service-account-credentials`, "SA-6 Subject namespaces"](../0143-service-account-credentials/change.md#sa-6-subject-namespaces)). See "Several IdPs in one tenant, and namespacing". |
| Verifier registry and snapshot | The registry is the member of `pkg/auth/jwt` that selects a token's source by its `iss`, verifies the token, and resolves its tenant and subject. The snapshot is the in-memory copy of active sources it reads. See "Verifier registry". |
| Activation rule, proofs, and activation preflight | The activation rule governs how a source becomes `active` or changes. The proofs are the checks recorded on the row before activation: discovery, sign-in, domain, and attestation. The activation preflight is the read before activation that refuses or lists principals left on old subjects. See "Activation rule" and "Issuer pin and proof". |
| Configuration preflight | The `lenny-preflight` Job, which runs before an install or upgrade and fails it on a misconfigured deployment ([§17.6](../../spec/17_deployment-topology.md#176-packaging-and-installation)). Unlike the chart's own validation, it can read stored rows, so it can refuse an `identity.sharedIssuers` entry that conflicts with a source row. |
| `deploymentIssuerAllowed` | A flag on the tenant record that states whether the tenant accepts the deployment issuer. Activating a customer source sets it false. |
| Operator tenant | The one tenant, named by the Helm value `auth.platformAdminTenant`, whose rows can hold `platform-admin`. It is a tenant that exists and holds user rows, so it is a different tenant from the platform tenant, whose ID `platform` [§10.2](../../spec/10_gateway-internals.md#102-authentication) reserves. The chart refuses `auth.platformAdminTenant: platform` (decision 27). |
| Directory | A customer's record of its users and groups, such as Entra ID or Okta, which provisions and deprovisions users through SCIM or through a sync worker. |
| Sync worker | A process that receives a directory's changes through a broker or vendor endpoint and calls Lenny's `invalidate` and `reinstate` routes, authenticating per tenant under a role that holds `manage_user_lifecycle`, such as `identity-sync`. |
| Directory row | A row in `directory_users`, written through SCIM. `externalId` is the directory's own identifier for the user, which the directory sends in SCIM. `match_claim` is the source field naming the token claim whose value must equal it. On the deployment source the row binds to a subject when a token's `match_claim` value first equals its `externalId`. See "SCIM server (TS-8)". |
| Hold | An invalidation entry on a user row for one caller class (`admin`, `sync`, or `scim:<source_id>`), with its invalidation level. A user is active only when no hold remains. See "User lifecycle (TS-4)". Two other holds are unrelated to users. An issuer-level hold stops fetches from a shared issuer whose address resolves into an excluded range, and a deployment-level hold pauses the lapse count of every domain-pinned row while many TXT records go missing at once. "Issuer pin and proof" and "Failure behaviour (identity)" state both. |
| `manage_user_lifecycle` | A permission TS-4 adds that covers the `invalidate` and `reinstate` calls alone, so a sync worker or a custom role such as `identity-sync` can deprovision users without assigning roles. |
| Hook | Work that a proposal of the egress design carries for this design, because adding it later would force rework of a stored record format, a wire contract, or a shipped enforcement point. The egress design lists its hooks under "Reserved for other designs". |
| Labels | Parts of the design carry the label TS-n, and requirements carry the label TSR-n. |

### Terms from other designs and the platform

This design builds on mechanisms other designs and the specification define. The table gives each one the meaning this document relies on.

| Term | Meaning |
| :-- | :-- |
| Tenant | Lenny's unit of isolation between customers. Tenants are separated by tenant pinning of pods, row-level security in Postgres, and separate keys. |
| Environment | A resource inside a tenant ([§10.6](../../spec/10_gateway-internals.md#106-environment-resource-and-rbac-model)) that names members, each a subject or an `oidc-group` with a role of `viewer`, `creator`, `operator`, or `admin`, and a `runtimeSelector` that chooses the runtimes its members reach. Its `connectorSelector` left with connectors under CR-1 of [`0124-connector-removal`](../0124-connector-removal/change.md#cr-1-removal), and an environment write that names it is refused with `400 VALIDATION_ERROR`. |
| `noEnvironmentPolicy` | A tenant setting, with a deployment default, that decides what a user with no environment membership reaches: no runtime under `noEnvironmentPolicy: deny-all`, or every runtime of the tenant under `noEnvironmentPolicy: allow-all`. |
| Runtime and pool | A runtime is a registered agent image and its configuration. A pool is a set of pods for a runtime, kept warm for sessions. |
| Concurrent-session pool, slot, and slot attribution | A pool with `sessionPolicy.maxConcurrentSessionsPerPod` above 1 runs several sessions on one pod, and each session's share of the pod is a slot with its own container and UID. Slot attribution is `netagent`'s mapping of a connection to the slot whose UID owns it, which under the egress design's decision 60, settled on 2026-11-13, applies each session's own environment, sets, and bindings to its slot. Whether a pool's runtime class answers it is recorded in the pool's status. |
| Recycling pool and pool recycle scrub | A pool with `recycle.enabled: true` returns a pod to the pool after a session, and the pool recycle scrub of [§5.2](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes) cleans it between sessions. State the scrub does not reach survives into the next session. |
| Derived runtime, owned pool, and `oneSessionPerPod` | Under [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md), a `tenant-admin` holding a grant derives a runtime from a base runtime and gives it a pool the tenant owns. `oneSessionPerPod: true` makes that pool's pods one-session pods. |
| Derive | Starting a new root session from an existing session's state, under [`0144-session-derive`](../0144-session-derive/change.md), which also absorbed the former replay route. |
| Delegation, delegation lease, and session grant | A session can start child sessions through the `lenny/delegate_task` tool, which [`0135-message-delivery`](../0135-message-delivery/change.md#md-23-tool-and-frame-names) renames `start_child_session`, and they form a delegation tree under a root session. Children of the same parent are siblings. A delegation lease records what a child receives from its parent, including `maxDepth`, the depth limit, and `maxChildrenTotal`, a cap on children ([§8.2](../../spec/08_recursive-delegation.md#82-delegation-mechanism)). Under [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-1-session-grant), the session grant replaces the lease: a gateway-side record of the security caveats, such as the remaining depth, the isolation floor, the policy cap, the environment, the credential bindings and egress hosts a child may receive, and the content caveat, and of the resource caveats, such as the child count and the carved budget. A session creates a child with the platform operation `session.create`, and manages it with `session.send`, `events.wait`, `session.list`, `session.transfer`, `session.release`, `files.import`, and the other operations of 0166 "DP-1", each acting only on the caller's own children. The reference tools a model calls, such as `start_session`, `list_sessions`, and `discover_agents`, run in the reference MCP bridge and reach the gateway as these operations. |
| Delegation presets, `DelegationPolicy`, and budget slice | Under [§8.3](../../spec/08_recursive-delegation.md#83-delegation-policy-and-lease), a delegation preset is a named lease template a deployer defines in `delegationPresets`, with values such as `maxDepth` and `maxChildrenTotal`. A `DelegationPolicy` is a named resource whose tag rules state which runtimes and pools a session may delegate to, and `delegationPolicyRef` is a field that names one. Under 0166 "DP-1", the policy cap of a grant is the intersection of every policy the platform, the tenant, the environment, the runtime, and the client name, and a delegation preset becomes an operator-defined default lease. A budget slice (`lease_slice`) is the share of the parent's budget a parent allocates to a child, which Redis Lua scripts reserve atomically. |
| Delegation inheritance | What every child takes from its parent's grant, whatever environment it runs in: the security caveats of 0166 "DP-1" other than the credential bindings and egress hosts, which within one environment are subsets of the parent's and across environments come from the target's policy (0166 decision 41). Isolation monotonicity requires the child's pool isolation to be at least as restrictive as the parent's. The content caveat holds `contentPolicy`, which limits the size of a task's input and exported files and names any content interceptor, and the export and import limits. A child's value of each can only narrow. `treeVisibility`, which limited how much of the task tree `lenny/get_task_tree` showed, leaves under 0166 "DP-6", and `session.list` returns the caller's own descendants with each one's runtime. |
| Environment delegation inputs | An environment's `defaultDelegationPolicy` and `delegationCeilings`, which 0166 "DP-1" reads as root grant inputs at every `session.create` of a session in the environment. TS-3 states them under "An environment's delegation inputs". |
| Session plan fields | Fields of a session's workspace plan ([§14](../../spec/14_workspace-plan-schema.md)) and egress request: `gitClone` names a repository and ref to clone into the workspace, `writableRepositories` names repositories the session pushes to without cloning, and `egress.allowedHosts` lists the hosts the session asks for. A runtime's `sharedAssets` are files placed read-only in every pod before it is ready, and a `gitRepository` shared asset is one filled from a repository, which the egress design's warm fill serves. |
| Warm list | The one list per pool of repository stores that the pool's pods fill before they report ready, under one rule set, which [`0147-tenant-derived-runtimes`, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores) defines. Every entry is a `gitRepository` entry of a runtime's `sharedAssets`: a Runtime's public entries, and on a tenant-owned pool the `gitRepository` assets of the tenant-derived runtime, which a tenant admin or a platform admin writes through the derived-runtimes route. |
| `PreRoute` chain and creation kind | An interceptor is a hook the gateway calls at a named phase of request handling ([§4.8](../../spec/04_system-components.md#48-gateway-policy-engine)). The `PreRoute` chain is the ordered set of interceptors the gateway calls before it settles a session's runtime, and each may answer with a `MODIFY` that changes the requested runtime, the pool, and the routing labels. Under [RT-2](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract) of [`0141-runtime-routing`](../0141-runtime-routing/change.md), every session creation path runs one chain, and the payload's `kind` field names the creation kind: `create`, `delegate` for a delegated child, or `derive`. For `kind: delegate`, the payload's `environment` field is the parent's E. |
| Runtime route and routing labels | A runtime route is a tenant-scoped admin resource that sends the sessions asking for one runtime to weighted target runtimes and pools, applied by a built-in `PreRoute` interceptor, the route interceptor ([RT-4](../0141-runtime-routing/change.md#rt-4-runtime-routes)). It replaces the experiment routing that §10.7 describes today. Routing labels are the `routing` map on a session that `PreRoute` interceptors write and the runtime reads to tag its traces ([RT-3](../0141-runtime-routing/change.md#rt-3-routing-labels)). A delegated child starts with its parent's routing labels. |
| Runtime revision | An immutable numbered version of a runtime's pod-defining fields, under [`0140-runtime-revisions`](../0140-runtime-revisions/change.md). The gateway selects a revision of the final runtime after the `PreRoute` chain. |
| Post-chain point, final row, and last modifier | The post-chain point is the single step of session creation that follows the `PreRoute` chain and revision selection and precedes the pod claim. Every check that depends on the runtime, the revision, or the pool runs there, on the final row: the runtime and pool the chain left, the chosen revision, and the session's environment ([`0141-runtime-routing`, "Post-chain point"](../0141-runtime-routing/change.md#post-chain-point)). The last modifier is the interceptor whose `MODIFY` last changed the payload, and a refusal at the post-chain point names it in `details.interceptor_ref`. |
| Intra-pod tool surface | The `platform` tool server a runtime reaches inside its pod through `tool_call` frames under [`0139-runtime-protocol`, RP-3](../0139-runtime-protocol/change.md#rp-3-tool-calls-on-frames), on every pod, whose calls `toolbridge.Bridge` (`pkg/gateway/platformtools/toolbridge`) forwards to the gateway. It replaces today's platform MCP server (`@lenny-platform-mcp`). Tool names follow [`0135-message-delivery`, "MD-23"](../0135-message-delivery/change.md#md-23-tool-and-frame-names). |
| Token Service | The Lenny service that stores user and provider credentials, mints short-lived tokens from them, and answers the pod credential API ([§4.3](../../spec/04_system-components.md#43-token-service)). It also serves the token exchange at `/v1/oauth/token`. |
| `netagent` | A container in every agent pod that uses the local egress endpoint, which acts as the pod's egress proxy. It runs under its own UID, holds the pod's service account tokens for egress, terminates TLS for the hosts it must inspect, attaches credentials, runs the git path, and applies request rules. |
| `lenny-egress` | The central egress proxy, built on Envoy, through which agent traffic leaves the cluster. |
| Decision service | `lenny-egress-authz`, which decides whether each connection is allowed, from the session's effective policy, and returns the route to use. It runs one of the mint checks. |
| Mint checks | The two independent checks on every mint that [`0127-egress-and-git`, "Egress decision service"](../0127-egress-and-git/change.md#egress-decision-service-lenny-egress-authz) defines under **Credential requests**: the Token Service's own check of the pod, its bindings, and its writable set, and the scope decision it asks of the decision service. A mint happens only when both agree. |
| Git mirror | `lenny-git-mirror`, which serves git fetches from per-tenant stores, fills those stores through the Token Service, and accepts prefetch requests. A warm fill populates a store before any session exists. |
| `pkg/binding` | The package the Token Service, the decision service, and the mirror use to resolve a pod to its session, user, tenant, and bindings. |
| Pod credential API | The gRPC API on which `netagent`, and the git mirror, ask the Token Service for a binding's token or secret. A response carries the binding's hosts and how to attach the credential. [`0127-egress-and-git`, "Interfaces"](../0127-egress-and-git/change.md#interfaces) defines it as I8. |
| Egress decision API | The API on which a proxy, the git endpoint, or the Token Service asks `lenny-egress-authz` whether a connection is allowed. [`0127-egress-and-git`, "Interfaces"](../0127-egress-and-git/change.md#interfaces) defines it as I3. |
| Pod binding API | The gRPC API on which `netagent` receives its pod's bindings, covered host set, and base destinations from `lenny-egress-authz`. [`0127-egress-and-git`, "Interfaces"](../0127-egress-and-git/change.md#interfaces) defines it as I7. |
| Credential binding | An egress-design object that gives sessions a secret for named hosts. Its `delivery` field selects `inject`, under which `netagent` attaches the secret and the runtime holds a placeholder, `file`, under which the runtime reads the secret from a file, or `federation` or `metadata`, which deliver cloud credentials. |
| Binding `scope` | When a binding attaches to a session: `always`, to every session of the tenant; `onRequest`, to a session whose plan names it; or `poolAttach`, to a session on a pool whose add-on attaches it. |
| VCS credential pool | An egress-design object that names repository prefixes, a provider credential such as a GitHub App, and an allowlist of repositories. Under [`0152-user-git-identity`](../0152-user-git-identity/change.md), `userAuthorization: required` makes each repository need the user's own access at the provider, and under `userAuthorization: off` the pool's own token serves any caller. |
| User credential type, link provider, and link | Objects of [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md). A type names a kind of per-user token and its source: `registered`, which a tenant backend or the user writes, or `oauth2Link`, which the user links at a link provider through a browser flow. A link is one user's stored authorization under one link provider. |
| `userCredential` binding | A credential binding whose `secret` names a user credential type, so each session receives its own user's token. |
| Token trust record | The record of everything that decides where a stored user token can go. A change to it makes the token unusable until the user acts again. |
| Tenant egress policy | The tenant's lists of always-allowed hosts, which every session reaches, session-requestable hosts, which a session plan can add, and denied hosts, with its egress and git routes. |
| Route | A tenant setting that sends traffic for matching hosts to a target: `direct`, a tenant's upstream proxy, a registered private endpoint, or an outbound connector. Egress routes carry API traffic, and git routes carry git traffic. |
| Effective policy | The hosts and bindings a session may use, which the decision service computes from pool, tenant, and session settings within the pool's egress ceiling. [`0127-egress-and-git`, "Effective policy"](../0127-egress-and-git/change.md#effective-policy) gives the formulas this design extends. |
| Egress ceiling and host set | A pool's egress ceiling is the largest set of hosts any pod of the pool can reach through the proxy, whichever tenant or session it serves. A host set is a named list of host patterns, such as `npm`, `pypi`, or `stripe-api`, which ceilings and policies reference. |

| Tenant pool overlay | A tenant's narrowing or extension of a pool's egress and git settings, within limits the platform admin sets on the pool. |
| Upstream and egress group | An upstream is a deployer's or tenant's proxy that `lenny-egress` chains to. An egress group is an additional `lenny-egress` Deployment, assigned to one tenant, whose traffic leaves the cluster from a dedicated address. |
| Covered host | A git host that a VCS pool or a git route of the tenant names, or an alias host of that provider. `netagent` terminates TLS for it and runs the git path. |

| `egress.allowedHosts`, `lockEgressToHosts`, and `egressLockHosts` | `egress.allowedHosts` is a session plan's list of hosts. `lockEgressToHosts`, a binding option of [UC-5](../0151-user-credential-delivery/change.md#uc-5-delivery-file), limits the session that holds the binding to that binding's hosts and the base destinations, which are the platform's own destinations every agent pod reaches, such as the gateway and the object store. | Evidence streams and `credential.mint` | Append-only records that [`0127-egress-and-git`, "Evidence streams"](../0127-egress-and-git/change.md#evidence-streams) defines. `credential.mint` records each token release or mint. |

A security principal is a row in `tenant_security_principals` that grants one. The tenant setting `securityRoleSource` states whether a token claim can carry such a role: never under `securityRoleSource: managed`, and through the roles claim under `securityRoleSource: oidc`. |
| Guardrail, posture, and the weakening delay | A guardrail is a setting a `security-admin` writes in the tenant security record ([SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)) that limits what a tenant admin can configure. | `lifecycleSubjects` | A list in the [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture) tenant security record naming the callers, such as `scim:<source_id>`, that may invalidate and reinstate a security principal. |
| Platform roles and permissions | Lenny's roles under [§10.2](../../spec/10_gateway-internals.md#102-authentication): `platform-admin` spans every tenant, `tenant-admin` administers one tenant, and `user` creates sessions. ## High-level design

A company that runs Lenny for many customers gives each customer its own tenant. Inside one customer, teams often need different network and repository access, and the customer wants its own single sign-on and its own employee directory to decide who can use Lenny. This design adds both. A tenant admin can divide a tenant into environments, each with its own repositories, credentials, allowed and denied hosts, and network routes. The gateway, the egress decision service, the Token Service, and the git mirror each check the session's environment, so an agent running inside a session cannot reach another environment's resources at run time. A tenant can also trust its customer's own identity provider for sign-in, with Lenny checking that one customer's provider cannot speak for another tenant or grant platform authority, and the customer's directory can remove a departing employee's access, including running sessions.

The main limit is that an environment is a policy boundary inside one tenant rather than an isolation boundary. Environments in a tenant share pods, stores, quotas, and egress addresses, so a team that needs isolation uses a tenant of its own. On the identity side, the operator remains inside every tenant's trust through impersonation and through activating sources, and much of the identity design rests on provider behaviour that has not been tested.

The rest of this section states each part in the design's terms, which "Terms" above defines.

**Environment scoping (TS-1).** VCS credential pools, credential bindings, user credential types, and link providers gain an `environments` list, and the tenant egress policy gains `environmentPolicies[E]` with host lists and routes per environment. A session in E sees tenant-wide objects and those that list E, and a tenant deny applies in every environment. The gateway checks a session's plan at create, and the decision service, the Token Service, and the git mirror each check again at run time from their own reads of the session row. A pod with no per-session policy cannot apply an environment's entries, so a session whose environment has anything of its own is refused on such a pod.

**Session environment context and cross-environment sharing (TS-3).** A session's environment is fixed at create, and a derived session and a delegated child take it. TS-3 moves the delegation gate from the caller's groups to the session's stored environment, as the environment caveat of the session grant of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-1-session-grant), makes the calling session the only parent a runtime can act as, limits the intra-pod tool surface to §9.1's platform tool table and 0166's platform operations, which omit the tools that create a root session, and lets a client disable delegation with `maxDepth: 0`. An environment's `defaultDelegationPolicy` and `delegationCeilings` apply at every `session.create`. It adds opt-in sharing paths, through which a delegated child runs in another environment under that environment's policy and cannot cross again, and it states for every operation of 0166 what crosses: files under both environments' content caveats, a parent's read of a crossed child limited to its messages and results, no parent tools, and a release that meets the target's admission check.

**Identity model and platform boundary (TS-2).** The deployment issuer, which can be an operator's identity broker, stays the default identity source. TS-2 states the broker contract, builds a token's claims from an allowlist, removes `platform-admin` from every IdP token, and confines `platform-admin` rows to one operator tenant.

**Identity sources and the verifier registry (TS-6).** A tenant can instead hold a customer source: the customer's own OIDC issuer pinned to that tenant, or its organization on a listed shared issuer. A `platform-admin` activates a source once its proofs pass, and at a tenant with a `security-admin` the activation also takes [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s delay and a reachable `security-admin`'s approval. The verifier registry selects the source by the token's `iss`, verifies the token, and takes the tenant from the source record. Subjects and groups carry a source prefix, so two issuers cannot collide.

**Login routing (TS-7).** Per-tenant URLs and metadata documents tell MCP clients and the playground which issuers a tenant accepts.

**User lifecycle (TS-4), SCIM server (TS-8), and directory groups (TS-9).** A directory reaches Lenny through Lenny's SCIM server or through a sync worker, and both end in one invalidation path. TS-4 lets invalidation reach a user known only through an IdP, refuses an invalidated user at authentication, keeps one hold per caller class, and adds `reinstate`. TS-8 serves SCIM, and TS-9 lets a source take groups from SCIM in place of token claims.

TS-5, delegated environment administration, is deferred under decision 7.

```
 Bearer token ──> gateway or Token Service
                    │ verifier registry: unverified iss selects a verifier (unknown iss: refused, no fetch)
                    ├─ deployment issuer: tenant from auth.tenantIdClaim, refused if the tenant disallows it
                    └─ customer source:   tenant from the source record (and pin), canonical subject ~<source_id>~<subject>
                    ▼
                  claim allowlist, role boundary, active-source and invalidation checks ──> principal
                    ▼
 Session create ──> environment E fixed on the session row
                    ▼
 decision service, Token Service, git mirror: each reads E and the object, and serves only visible(objects, E)
```


## Requirements

- TSR-1. A tenant admin can give an environment its own VCS credential pools, credential bindings, host lists, and routes.
- TSR-2. An object with no environment scope keeps the meaning [`0127-egress-and-git`](../0127-egress-and-git/change.md) gives it.
- TSR-3. Scoping holds at run time, against an agent acting inside a session, as well as at session create.
- TSR-4. A narrowing that Lenny cannot enforce on a given pod is refused rather than ignored.
- TSR-5. The specification states the identity model: the deployment issuer by default, a customer issuer per tenant, and what stays with an operator.
- TSR-6. A customer's directory can end a departing user's access to Lenny, including running sessions, within a bound the directory and the operator control, through SCIM or a sync worker.
- TSR-7. No customer-controlled input, including a customer's issuer, can produce authority over another tenant or any platform-wide authority. On a listed shared issuer, this rests on the platform admin's assertion under "Issuer pin and proof".
- TSR-8. One deployment holds tenants on the deployment issuer and tenants on customer issuers at once, and a single-company deployment is unaffected.

## Security properties

- TP1. A session in environment E can use a scoped object only when the object lists E. For credentials, the Token Service and `lenny-egress-authz` each hold this independently, from their own reads of the session row and the object. The mirror's own fills hold it through the pool and the cause each request names, which the Token Service checks itself from a pod's binding, a gateway cause assertion, or a prefetch record, as "Filling the mirror" under "Enforcement points" states.
- TP2. The gateway sets a session's environment at create and it never changes. A root session's environment is checked against the caller's membership. A delegated child takes its parent's, or under a declared sharing path the target's. Nothing in a pod can set it. A runtime cannot create a root session, because the intra-pod tool surface omits those tools.
- TP3. A pod with no per-session policy applies unscoped objects alone, for every session it serves. Omitting an environment never widens access: a caller cannot leave an environment's denies or routes behind by using the transparent path.
- TP4. A caller receives the same refusal for an object scoped to another environment and for an object that does not exist, so environment object names do not leak across environments.
- TP5. A role claim from an IdP cannot confer `platform-admin`. A `platform-admin` row can exist only in one configured operator tenant, so a subject in any other tenant cannot hold the role. Whichever issuer authenticates the operator tenant can assert a staff subject, so that issuer holds platform authority: with the deployment issuer in that position, a broker compromise reaches every tenant.
- TP6. Environment scoping is a policy boundary inside a tenant. It carries none of the pod pinning or row-level isolation that the tenant boundary has from §12 and from [P4](../0127-egress-and-git/change.md#security-properties), the egress design's property that keeps one tenant's data and credentials away from another tenant's pods. "Residual risks" states what follows.
- TP7. A delegated child runs in its parent's environment unless a sharing path applies, so a chain of delegations reaches nothing its root's environment does not offer. Under a sharing path, the child runs under the target environment's policy, the caller's denies and routes do not follow it, it and its descendants cannot cross again, it receives none of its parent's tools, and a release of it meets the target's admission check. A runtime can act on no session other than its own children through the platform operations.
- TP8. A customer source's tenant comes from the record its verified token selects: by issuer alone on an ordinary issuer, and on an issuer in `identity.sharedIssuers` by the issuer with a verified audience or a claim the platform admin named as provider-set. It never comes from `auth.tenantIdClaim` or a claim a source chooses. The deployment issuer cannot speak for a tenant configured for customer sources.
- TP9. An unverified `iss` selects a verifier and nothing else, an unknown one causes no fetch from that issuer, and pin values are read only after the signature verifies.
- TP10. A customer source's subjects and groups are namespaced, so two issuers in a deployment or a tenant cannot collide.
- TP11. Every browser login goes through the same resolver as a bearer, an authorization code goes only to the source whose callback received it, and the row its token selects must be that source.
- TP12. A subject whose source is not active is refused on every verifier path, including with a Lenny-issued token.

## Detailed design

### TS-1: Environment scoping

#### A session's environment

TS-1 relies on [TS-3](#ts-3-session-environment-context-and-cross-environment-sharing), which makes `sessions.environment` dependable. A session has a value E when its create named an environment through `/v1/environments/{name}/sessions` or the `environment` body field, which a protocol adapter's environment-scoped form becomes. Both already run the explicit admission check (membership, at least `creator`, and the runtime selector). A transparent-path session has no E, and the formulas below write that as E = ∅.

A new session with E = ∅ (a root create, a derive, or a delegated child) is refused with `422 ENVIRONMENT_REQUIRED` when any environment in the tenant whose selector admits the runtime has `denied` or route entries. The check reads the tenant's environments and takes no input from the caller's groups, so a token with no `groups` claim, under either `noEnvironmentPolicy` value, cannot shed an environment's policy. A resume is exempt, so a deny added later does not strand a running session. A caller who belongs to no such environment has no path to that runtime, including an administrator who is not a member, and a `tenant-admin` resolves that by adding the member or by giving the environment its own runtime, or by narrowing the selector so that the environment no longer admits the runtime. On a pool with no per-session policy, an added member still meets the rule under **Pods with no per-session policy**, in "Effective policy" below. See decision 3.

The `PreRoute` chain can change a session's runtime and pool after admission. Under [RT-2](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract), every creation path runs one chain, and any `PreRoute` interceptor, including the route interceptor that applies runtime routes, may change the runtime and the pool on every path. The gateway then selects a revision of the final runtime and runs every check that depends on the runtime, the revision, or the pool once, at the post-chain point ([`0141-runtime-routing`, "Post-chain point"](../0141-runtime-routing/change.md#post-chain-point)). The runtime-dependent checks in this section are post-chain checks on the final row: the selector for E, `ENVIRONMENT_REQUIRED`, the rule for pods with no per-session policy, the refusal of `lockEgressToHosts` on a pool with `egressProfile: internet`, which [UC-5](../0151-user-credential-delivery/change.md#uc-5-delivery-file) owns, the refusal in [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) of a `userCredential` binding on a pod that can serve another session, and the environment's `placementRequirements`, which join the session's effective placement requirements that [PM-4](../0136-placement/change.md#pm-4-placement-requirements) checks on the final pool, refusing with `422 PLACEMENT_REQUIREMENT_UNMET` and `details.source: environment`. They run for every creation kind, whether or not an interceptor changed the runtime. For `kind: delegate`, the `environment` field of the `PreRoute` payload is the parent's E, and the post-chain point settles the child's own environment: the parent's E when its selector admits the final runtime, or T when a live sharing path applies, as "Cross-environment sharing" under TS-3 states. A miss on the tenant view of [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md), the read interface through which every session path resolves the runtimes a tenant can see, is a post-chain check of that design, and it refuses on any name. A derive naming a `targetPool`, the derive request's optional field that names the pool for the derived session, meets the same checks, because a child under `lockEgressToHosts` moved to a pool with `egressProfile: internet` would otherwise bypass the lock through its raw sockets. A check that fails refuses the create, the derive, or the delegation with its own code. When the chain changed the runtime or the pool, the refusal names the last modifier, and the gateway never falls back to the requested runtime, as RT-2 states. A pool that is not known until the pod claim, rather than at the post-chain point, is checked at claim, before bind.

Until the interceptor contract proposal of [`0141-runtime-routing`, "Steps"](../0141-runtime-routing/steps.md#steps) lands, today's tree runs no post-chain point. TS-1 then runs these checks after the last `PreRoute` segment and the experiment rewrite (`routeExperiment` and `preRouteAfterExperiment` in `create.go` and `create_and_start.go`, and `ApplyExperimentRouting` in `buildChildSession`), and that proposal moves them to the post-chain point.

#### What is scoped

Scoping applies to objects the platform evaluates per session.

| Object | Scoped | Reason |
| :-- | :-- | :-- |
| VCS credential pool | Yes, through `environments` | Selected per repository at mint time |
| Credential binding | Yes, through `environments` | Resolved per session on the pod credential API |
| User credential type and link provider | Yes, through `environments` | Resolved per session on the pod credential API, under [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md). The binding that names one is scoped as above, and a session needs both visible. |
| A user's token (a `registered` row or a link) | The `registered` row has an `environment` column, and §4.3's empty value means no environment. A link has none, and it is keyed on the link provider's name. | The Token Service takes the session's E, then the no-environment row. A link records a fact about a person on a provider, so a member of two environments links once. |
| `requestRules` and presets | No | They are part of a binding, which is scoped. An environment that needs other rules has its own binding on that host, and the one-binding-per-host rule applies per session. |
| Always-allowed, session-requestable, and denied hosts | Yes, through `environmentPolicies` | Read per decision |
| Egress routes and git routes | Yes, through `environmentPolicies` | Read per decision. A route can name an outbound connector once [OC-2](../0148-tenant-outbound-connector/steps.md#steps) (the outbound connector's hosts and policy, whose validator admits the `outboundConnector` route target) lands, with no further change. A token trust record covers every such route on its host, across every environment, as [`0151-user-credential-delivery`, "Token trust record"](../0151-user-credential-delivery/change.md#token-trust-record) states under **Route value**, so one environment's scoped route, a move between environments, or a reorder on a token's host makes that token unusable for all environments, and an asserted route, the expected route that a call carrying a user token names on its CONNECT and that the decision service compares with its own choice, uses `routes(E)` for the session's E. The covered host set reads every git route and VCS pool of the tenant, unfiltered by environment, so a session in E2 on a host only E1 names gets a refused push rather than an opaque tunnel, in which `netagent` would pass the connection through without terminating TLS, as [`0127-egress-and-git`, "Git on covered hosts"](../0127-egress-and-git/change.md#git-on-covered-hosts-netagent) states. |
| Tenant warm-up additions | No | They apply before any session exists. |
| Tenant pool overlay | No | It applies at pod creation or per pool and tenant. |
| Egress group and CA trust bundle | No | Each is fixed at pod creation or dialled by tenant. |
| Client config files, such as `.npmrc` and `pip.conf` | No | `netagent` writes them at tenant binding. See decision 4. |
| Per-class gates | No | They remain platform grants per tenant. |
| Tenant-registered upstreams and git endpoints, and outbound connectors and outbound hosts | No | The registration is tenant-wide, and a scoped route selects it. Decision 4 leaves outbound connectors and outbound hosts out of the scoped objects, so TS-1 has no dependency on [OC-2](../0148-tenant-outbound-connector/steps.md#steps). |

#### API

The objects gain these fields through the admin API resources that the egress design's proposals [EG-1](../0127-egress-and-git/steps.md#steps) (git prerequisites), [EG-4](../0127-egress-and-git/steps.md#steps) (credential delivery), and [EG-9](../0127-egress-and-git/steps.md#steps) (egress policy objects) define:

```yaml
vcsCredentialPool:
  name: web-github
  repositoryPrefixes: ["github.com/acme-web/"]
  environments: [web]            # absent: tenant-wide

credentialBinding:
  name: payments-stripe
  scope: onRequest
  hosts: [api.stripe.com]
  environments: [payments]

tenantEgressPolicy:
  alwaysAllowed: [npm, pypi]
  sessionRequestable: [huggingface.co]
  denied: [pastebin.com]
  environmentPolicies:
    payments:
      alwaysAllowed: [stripe-api]
      sessionRequestable: []
      denied: [huggingface.co]
      egressRoutes: [{ hosts: ["*.stripe.com"], upstream: acme-pci-swg }]
      gitRoutes: []
```

The rules for these fields are:

- `environments` is either absent or a non-empty list. An empty list is refused with `422 VALIDATION_ERROR`, because it has no clear reading.
- Every name must be an existing environment in the tenant, or the write fails with `422 ENVIRONMENT_NOT_FOUND`. An `environmentPolicies` key follows the same rule.
- A deployment with no environment registry wired refuses these fields with `422 ENVIRONMENTS_NOT_AVAILABLE`, since §10.6 admission runs open in that posture.
- `DELETE /v1/admin/environments/{name}` fails with `409 RESOURCE_HAS_DEPENDENTS` while any object or policy key names the environment. A recreated environment therefore inherits nothing.
- A tenant warm-up addition, a `gitRepository` warm fill, or a warm-list entry of either declarer, whether or not it sets `prestage: true`, cannot name a repository whose only covering pool is scoped, because a pod with no session has no E (decision 28). The write is refused unless the repository lies under no VCS pool prefix, or credential selection at E = ∅ resolves it to a VCS pool with no `environments` list whose allowlist names it, which is the predicate the fill evaluates. A write of a `gitRepository` asset on a tenant-derived runtime answers `422 INVALID_DERIVED_RUNTIME`, whether a tenant admin or a platform admin sends it.
- A VCS pool write that makes a warm-list entry fail that predicate, such as one that adds `environments` to the covering pool or deletes or narrows a tenant-wide pool that covered it, passes with a `Warning` naming each runtime and entry it affects. The PoolScalingController applies the same predicate at each render, so the entry leaves the rendered list and is reported as suspended with the reason `environmentScoped`. The drain of [`0147-tenant-derived-runtimes`, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores) then reaches idle pods holding the store, `coveredStores` refuses such pods at the next claim, and the entry returns once the pool is unscoped again.
- The two rules above read the `environments` field that TS-1 adds to a VCS pool. The write check and the render suspension belong to the step that owns each declarer's warm-list entries: [0147.S8](../0147-tenant-derived-runtimes/steps.md#steps) for tenant entries and [0127.S5](../0127-egress-and-git/steps.md#steps) for platform-declared entries. Whichever of 0149.S1 and the owning step lands second adds the environment case.
- Two pools can hold the same repository prefix only when their `environments` lists are disjoint, and neither may be tenant-wide. Selection takes the longest prefix among the pools visible to E, so exactly one pool answers for any repository and environment. This lets two environments use separate GitHub Apps on one organization.
- A credential binding's `hosts` must lie within the allow set of each environment the binding lists, that is `always(E) ∪ requestable(E)` for each E, or within the tenant's set for a tenant-wide binding. TS-1 extends the "each host must lie within the tenant's effective allow set" validator of [EG-4](../0127-egress-and-git/steps.md#steps) in this way, or the `payments-stripe` example above would fail.
- The mirror prefetch resource is a tenant admin's alone. Every prefetch record carries a pool: when a request omits the pool and exactly one pool covers the repository, the API stores that pool, and when several pools cover it, the API refuses a request that omits the pool.
- A shadow policy's candidate carries its own `environmentPolicies`, and each decision evaluates the candidate with the session's E. `environments` lists sit on objects and stay outside the candidate.
- A write that adds `denied` or route entries to an environment answers with a `Warning` header and a count when live sessions in it run on pods with no per-session policy, because those sessions cannot adopt the entries.
- A write that adds an environment's first `denied` or route entry answers with a `Warning` header listing the runtimes its selector admits, because transparent creates on those runtimes will now answer `ENVIRONMENT_REQUIRED`. A tenant admin learns this before those clients break. A selector or runtime label change that extends such an environment to new runtimes answers with the same `Warning`.

The effective-policy read gains an optional `environment` parameter and lists `environment` among the layers that decided each host. `GET /v1/egress/decisions` and the evidence export gain an `environment` filter. Both wait for [EG-8](../0127-egress-and-git/steps.md#steps), the egress design's tenant visibility proposal.

#### Data model

- VCS pool and binding rows gain a nullable `environments` text array. NULL means tenant-wide.
- The tenant egress policy document gains `environmentPolicies`, keyed by environment name.
- Neither is a foreign key, following the reasoning in migration 0059. The write check and the delete guard hold the reference, and one lock on the environment's row orders them. Every write that adds a reference to an environment (an `environments` entry on a pool, a binding, a user credential type, or a link provider, an `environmentPolicies` key, or a `dangerouslyShare` entry) reads the named environment's row with `SELECT ... FOR SHARE` in the same transaction as the write, and so does the session create, derive, or delegation that records E, in the transaction that writes the session row. `DELETE /v1/admin/environments/{name}` takes `SELECT ... FOR UPDATE` on that row before it checks for references and for active sessions. A reference write or a session that commits first makes the delete find it and answer `409 RESOURCE_HAS_DEPENDENTS`, and a delete that commits first makes the reference write or the create find no environment and answer `422 ENVIRONMENT_NOT_FOUND`, so no name outlives its environment and a recreated environment inherits nothing. VCS pool writes that set `repositoryPrefixes` or `environments` take a transaction-scoped advisory lock keyed on the tenant, so the disjointness check under "API" sees every committed pool.
- The environment record gains `placementRequirements`, which holds the requirements of [PM-4](../0136-placement/change.md#pm-4-placement-requirements) that an environment may set: `requireNodeSeparation`, `nodeTenancy: dedicated`, `allowSharedPod: false`, and `allowReusedPod: false`. They add to the tenant's requirements and cannot remove one. An empty or absent value adds nothing. Adding a requirement applies at once. Removing one, or moving one to a weaker value, is a relaxation under the rules of the tenant security settings: the write needs a `justification`, the relaxation is recorded in the tenant's audit chain, and it takes effect after the tenant security record's weakening delay, during which the tenant's `security-admin` or a `platform-admin` can cancel it ([PM-4](../0136-placement/change.md#pm-4-placement-requirements), decision 29). `dataResidencyRegion` stays where it is today.
- The environment record holds no data-classification override. The stricter-only environment override of `workspaceTier` leaves with the setting, under decision O6 (a) of [`0150-tenant-security-settings`](../0150-tenant-security-settings/decisions.md#open-decisions), and environments inherit the tenant's security settings.
- The existing `sessions.environment` column holds E.
- All tables are tenant-scoped under the existing row-level security policy.

#### Effective policy

Define the following, where E = ∅ selects no environment entries:

- `visible(objects, E)` is the objects with no `environments` list, plus those whose list contains E.
- `always(E)` is tenant always-allowed ∪ `environmentPolicies[E].alwaysAllowed`.
- `requestable(E)` is tenant session-requestable ∪ `environmentPolicies[E].sessionRequestable`.
- `denied(E)` is tenant denied ∪ `environmentPolicies[E].denied`.
- `routes(E)` is `environmentPolicies[E]` routes in order, followed by tenant routes in order.

The formulas from [`0127-egress-and-git`, "Effective policy"](../0127-egress-and-git/change.md#effective-policy) become:

| Case | Formula | Change |
| :-- | :-- | :-- |
| Unbound pod | `ceiling ∩ (pool warm-up policy ∪ warm-list hosts)` | The warm list's hosts, from the egress design's decision 45. No environment entry applies. |
| Tenant-bound pod without a session | `ceiling ∩ (always(∅) ∪ tenant warm-up additions ∪ warm-list hosts) − denied(∅)` | Environment entries do not apply. The warm list's hosts join, from the egress design's decision 45. |
| Pod with one session | `ceiling ∩ session allowed − denied(E)` | `session allowed` is the plan's list, or `always(E)` when the plan sets none. Each list entry must lie within `always(E) ∪ requestable(E)`. A session under a lock, through `lockEgressToHosts` on its own binding or `egressLockHosts` inherited from an ancestor, is further limited to the lock's hosts and the base destinations, as the egress design's one-session formula states. |
| Pool with `egressProfile: restricted` and `gitAccess` | `gitAccess hosts ∩ git hosts(E) − denied(E)` | `git hosts(E)` takes the hosts of `visible(VCS pools, E)`, the LFS host sets of those pools' providers, the explicit git routes in `routes(E)`, and the hosts of the pool's warm list, whose entries all pass the predicate under "API" at E = ∅. A session carrying `egress.allowedHosts`, its own or inherited, intersects this set with that list, and a lock through `lockEgressToHosts` or `egressLockHosts` limits it as it limits the one-session formula. |
| Pod with several slots on a pool that answers slot attribution | Per slot, the one-session formula or the `restricted` row with that slot's session's E and inputs | `netagent` applies each connection's slot's session ([`0127-egress-and-git`, "Slot attribution and fetch grants"](../0127-egress-and-git/change.md#slot-attribution-and-fetch-grants), **Per-slot scopes (decision 60)**), so each slot behaves as a one-session pod for its policy. |
| Pod with no per-session policy | `ceiling ∩ always(∅) − denied(∅)` | Environment entries do not apply, because `netagent` keeps the union over the pod's sessions. See **Pods with no per-session policy.** |
| Delegated child in the parent's environment, on a one-session pod or a pod with `egressProfile: restricted` | The one-session formula, or the `restricted` row, with the parent's E, and the parent's `egress.allowedHosts` and named bindings as its inputs | The rule in [`0127-egress-and-git`](../0127-egress-and-git/change.md). |
| Delegated child under a sharing path to T, on a one-session pod or a pod with `egressProfile: restricted` | The one-session formula, or the `restricted` row, with E = T, and `session allowed` = `always(T)` | No input comes from the parent, and no term comes from the caller's environment. `denied(T)` includes the tenant's list. |

Consequent rules:

- **Bound.** The pool ceiling bounds every environment entry. A tenant deny applies in every environment, so an environment cannot re-allow a host the tenant denies.
- **Repositories.** Readable repositories are the session's `gitClone` sources, the allowlists of `visible(VCS pools, E)`, and the public platform entries of the pool's warm list. Before a session binds, a pod's readable repositories are the pool's warm list plus the repositories of the warm-up policy that applies to it, with no environment entry applying, and every entry on the list passes the predicate under "API" at E = ∅. Writable repositories must lie within `visible(VCS pools, E)` at bind and at each mint.
- **Bindings.** A session attaches bindings with `scope: always` from `visible(bindings, E)`, and it can name bindings with `scope: onRequest` from the same set.
- **User credentials.** A `userCredential` binding needs its type visible too, as `visible(types, E)`. It takes `scope: onRequest`, or `scope: poolAttach` under [`0152-user-git-identity`, "The attach rule"](../0152-user-git-identity/change.md#the-attach-rule), whose trigger is a declared writable repository under such a pool in `visible(VCS pools, E)`. The credential-pinned host rule (`credentialPinned`) of a VCS pool with `userAuthorization: required`, under which `netagent` terminates TLS for the pool's hosts and refuses a request when the host has no binding, is outside `visible`, because it reads every VCS pool of the tenant. The pod refusal in [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) covers E = ∅ on a pod with no per-session policy, because such a pod refuses the binding outright. Under the owner's settlement of 2026-11-13 of that design's decision 41 and [`0152-user-git-identity`](../0152-user-git-identity/decisions.md#decisions) decision 52, user credential bindings, `lockEgressToHosts`, and a user git identity are allowed on a pool whose status records slot attribution, and refused on a pool whose status records the union fallback and on a recycled or used pod (decision 31). Which runtime classes answer slot attribution is measured by a spike that the egress design owes ("Validation owed" in `steps.md`).
- **Pods with several slots.** Where the pool's runtime class answers slot attribution, every rule above applies per slot with that slot's session's E, at the decision service, the Token Service, and the mirror, and the rules below do not apply. A pod with several slots therefore needs no environment refusal of its own when its pool answers, with one exception for shared warm stores. A session on a concurrent pool whose runtime class answers slot attribution is refused with `422 ENVIRONMENT_POLICY_NOT_ENFORCEABLE`, naming the entry, when its environment denies the host of an entry on the pool's warm list, because the warm store is shared by every slot of the pod and cannot be withheld from one slot ([`0147-tenant-derived-runtimes`, "Warm stores", **Withheld stores.**](../0147-tenant-derived-runtimes/change.md#warm-stores), its decision 41, settled 2026-11-13). The cause is the one the code names elsewhere: a pod that cannot apply the session's environment to a resource its other sessions share (decision 30).
- **Pods with no per-session policy.** A pod with several slots whose pool's status records that slot attribution is unavailable evaluates with E = ∅ for every session on the pod, including at the Token Service and in the readable and writable sets. [`0127-egress-and-git`, "Git on covered hosts"](../0127-egress-and-git/change.md#git-on-covered-hosts-netagent) makes those sets the union over the pod's sessions there, because `netagent` cannot attribute a request to a slot, so a scoped repository on such a pod would be open to every slot. The post-chain point reads the pool's status. The rules follow from this:
  - A plan that names an object visible to E alone (for example a repository whose only covering pool is scoped) is refused with `422 ENVIRONMENT_POLICY_NOT_ENFORCEABLE`.
  - A session whose E has non-empty `denied`, `egressRoutes`, or `gitRoutes` is refused with the same code (TSR-4). The check runs at create, derive, resume, and delegated child placement, on the final runtime and pool.
  - A session whose E has anything of its own that adds access is refused with the same code: an `alwaysAllowed` or `sessionRequestable` entry, or a VCS pool, binding, type, or link provider that lists E. A runtime is not guaranteed to work without access its environment provides (decision 15). The check runs at the same points except a resume, where it runs at session create alone, because a session that began without an entry keeps working without it, and an entry added later does not strand it.
  - A session or delegated child carrying `egress.allowedHosts` or `egressLockHosts`, its own or inherited, is refused with the same code (TSR-4), because the pod cannot apply either to one slot. An injected agent could otherwise delegate to such a pod, losing its parent's lock, and send a token delivered under `delivery: file` to any tenant always-allowed host. Check 2 under "Cross-environment sharing" refuses a locked crossing for the same reason. This check runs at every point above, including a resume.
  - Otherwise E has nothing of its own, and the session proceeds with unscoped objects. A refused caller can still use the transparent path when no environment admitting the runtime has a deny or route. That session has E = ∅ and widens nothing, and it runs without the environment's access. The owner left this allowed, in the words "leave allowed" (decision 15).
  - An environment that needs such a runtime uses a derived runtime and its owned pool under `oneSessionPerPod: true`, under a platform grant, whose pods are one-session pods with E's full policy. That route does not work today, because no derived runtime runs a session and §15.1 reserves creating a runtime or a pool to a `platform-admin`. The owner chose [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md) as the design that lets a `tenant-admin` holding a grant do this. A pool on a runtime class that answers slot attribution is the other route, and it keeps several slots per pod.
  - The `Warning` under "API" above also covers a write that gives an environment its first entry or scoped object, listing the runtimes on pools with no per-session policy that its selector admits.

#### Enforcement points

The session create check alone is insufficient. An agent can run `git fetch` at any time against any repository on the tenant's allowlist, and bindings with `scope: always` attach with no plan entry, so most of the enforcement happens after create.

| Point | Component | Check |
| :-- | :-- | :-- |
| Session create, derive, resume, and delegation | Gateway | Named bindings, `gitClone` sources, `writableRepositories`, and `egress.allowedHosts` lie within the sets above for E, and the refusal rules for transparent creates and for pods with no per-session policy apply. The runtime- and pool-dependent rules run at the post-chain point on the final row, as "A session's environment" states. |
| Ref resolution: the gateway's git `ls-refs` request, which resolves a `gitClone` ref to a commit at plan bind | Gateway through the egress decision API | Resolution runs after the post-chain point on every creation path, so the final pool and E are settled, and before the pod claim where the plan arrives with the create request. At finalize, the pod was claimed at create under the eager claim of proposal 0007, so a bad ref fails the finalize on a claimed pod, and the gateway takes E from the session row. The request carries a gateway cause assertion, a JWT of type `lenny-cause+jwt` with the audience `lenny-cause` that names the tenant, E, the session ID, the upstream, and the pool. The decision service verifies the assertion and reads E from it, and one assertion serves the direct path through `lenny-egress` and the mirror path, where "Filling the mirror" below reads it. No new header reaches a level 2 proxy. |
| CONNECT | `lenny-egress-authz` | The formula for the pod's case, with E from `pkg/binding`. |
| Mint or secret on the pod credential API | Token Service, then the egress decision API | Each component reads E and the object, and both must agree (TP1). Nothing is minted on refusal. |
| Serving from the mirror | Mirror through the egress decision API | The resolver selects the pool for the repository and E, and readable repositories for E are checked on every request. A store's identity in [`0127-egress-and-git`](../0127-egress-and-git/change.md) includes the credential, so same-prefix pools in different environments use different stores. |
| Filling the mirror | Mirror to the Token Service on the pod credential API | The request names the pool and one cause: the UID of the pod whose fetch caused the fill, which covers a warm pod's fill and a pod's fetch miss; the gateway cause assertion that the gateway's `ls-refs` at plan bind carries and the mirror forwards; or a prefetch record. The Token Service reads the pod's binding through its own `pkg/binding` instance, verifies the assertion's signature, its type `lenny-cause+jwt`, and its audience `lenny-cause`, or reads the prefetch record itself. No other Lenny verifier accepts that type, so no other Lenny-issued JWT passes as an assertion and an assertion passes as nothing else. It refuses a cause that is not live or that belongs to a tenant other than the request's, and a cause from another tenant also writes an audit event and raises an alert, because a healthy mirror never sends one. For a pod cause, E follows this design's rules: a warm pod has E = ∅; on a pod with several slots whose pool answers slot attribution, `netagent` names the session whose slot it attributed the fetch to, the mirror forwards that session with the pod cause, and the Token Service accepts it only when the pod's binding holds that session, so E is that session's environment; and a pod with no per-session policy has E = ∅. For an assertion, E is the value it carries. For both, the Token Service accepts only the pool that VCS pool selection picks for the upstream and E, the longest matching prefix among `visible(VCS pools, E)`, through the selection function the gateway also uses. For a prefetch cause, the pool must be the one the record names. The cause is checked at the fill's first mint, which returns a fill ID that the Token Service binds to the mirror's identity, the tenant, the upstream, and the pool. Later mints that present the fill ID need no new check for the fill's lifetime, `tokenService.mirrorFillLifetimeSeconds` with a default of 3600, so a fetch can outlive its pod. A fill ID presented with any other value or after that lifetime is refused. A prefetch record is live from its write until its fill completes or fails, and a change to the named pool's `environments` or prefixes, or its deletion, voids a pending record. [`0127-egress-and-git`, "Git mirror (`lenny-git-mirror`)"](../0127-egress-and-git/change.md#git-mirror-lenny-git-mirror) states these rules under **Fill causes**. Warm fills reach unscoped pools alone, so the write and render rules under "API" keep a warm-list entry whose repository only a scoped pool covers off every warm list. |
| Git path and binding hosts | `netagent` | No new logic. It enforces what the pod binding API and the pod credential API return, and it flushes credentials at session end and on each binding change, so a sequentially reused pod does not carry a credential across sessions. |

`netagent` needs no environment concept. The cache key [`0127-egress-and-git`](../0127-egress-and-git/change.md) uses for bindings with `scope: always` (the tenant pin) stays safe because the flush at session end precedes the next session.

#### Failure behaviour

| Condition | Result |
| :-- | :-- |
| An object outside E is named at create | `422` with the same code and message as an unknown object (TP4) |
| Environment store or policy read fails at create | `500 INTERNAL_ERROR`, as admission does today, and no session is created |
| `pkg/binding` cannot read the session row | Fails closed, with the existing retryable error for a binding that is not yet visible |
| A tenant admin removes E from a pool or binding during a session | The object's version bumps, the gateway pushes a binding change, `netagent` flushes, and the next request on the pod credential API is refused. The session continues without it. |
| A tenant admin removes a host from `requestable(E)` during a session | Applies to new sessions, as the tenant list does in [`0127-egress-and-git`](../0127-egress-and-git/change.md). Adding the host to `denied(E)` closes it at the next decision. |
| A member leaves the environment during a session | The session keeps E, because membership is a check at create. See "Residual risks". |
| A delegation target with neither the parent's selector nor a live two-sided sharing path | `TARGET_NOT_IN_SCOPE` |
| A child reached by crossing, or its descendant, tries to cross | `TARGET_NOT_IN_SCOPE`, with the audit reason `second_crossing` |
| A resume meets a deny added to E after the session began on a pod with no per-session policy | `ENVIRONMENT_POLICY_NOT_ENFORCEABLE`, and the session stays suspended until its owner ends it or the tenant admin changes the policy. |
| A session on a concurrent pod with slot attribution whose environment denies the host of a warm-list entry | `422 ENVIRONMENT_POLICY_NOT_ENFORCEABLE` naming the entry, because the shared store cannot be withheld from one slot (decision 30). |
| An environment vanishes under a live session through a store-level race | `visible` finds no entries for E, which narrows the session to unscoped objects. The row lock under "Data model" keeps a delete from committing while a session in E is being recorded, so a recreated environment does not reach an orphaned session. |

A `tenant-admin` remains able to scope any object to any environment and add itself as a member, which matches §10.2's statement of tenant authority.

#### Why not separate tenants

A customer can give each team its own tenant today. That yields tenant pinning, row-level isolation, and separate keys, which environments do not provide. It also means no shared policy, no shared admin, no combined billing rollup, and no delegation between environments, since Lenny has no grouping above a tenant. Teams needing an isolation boundary should be tenants, and teams needing separate configuration under one administration should be environments. The documentation states this choice.

It does not hold overall, because enforcement is at run time in components [EG-2](../0127-egress-and-git/steps.md#steps) (the pod network agent and proxied egress) ships, evidence records are written from day one, and [EG-1](../0127-egress-and-git/steps.md#steps) (git prerequisites) fixes the prefix rule. ### TS-3: Session environment context and cross-environment sharing

TS-1 cannot rest on the current propagation. TS-3 lands first and depends on nothing in [`0127-egress-and-git`](../0127-egress-and-git/change.md), apart from the evidence field step the dependency table names.

Under [`0166-delegation-primitives`](../0166-delegation-primitives/change.md), a session creates a child with the platform operation `session.create` under its session grant, and manages it with the other operations of its "DP-1". TS-3 owns crossing between environments for every one of those operations (0166 decision 41), and states below what each operation does when its parent and its child are in different environments. 0166 owns the grant, its caveats, and the resolution of each caveat, which TS-3 cites (0166 decision 40).

- **Derive.** The new session takes the source's environment, and the explicit admission check runs against it. A caller who has left the environment gets `403`.
- **Delegated child's environment.** The child takes the parent's E, set on the row `buildChildSession` writes, when `runtimeSelector` of the parent's E admits the final runtime that the child's `PreRoute` chain leaves at the post-chain point. Otherwise it needs a sharing path under "Cross-environment sharing", and with none it answers `TARGET_NOT_IN_SCOPE`.
- **The environment caveat reads the session.** A call from inside a pod authenticates as a principal with no groups (`WithSessionPrincipal` builds it), and today's delegation gate, `runtimeAuthorizedForCaller` and `crossEnvReachable`, resolves environments from that principal. A session whose owner belongs through a group therefore has no environments in the delegation gate. Under `noEnvironmentPolicy: deny-all` its delegations answer `TARGET_NOT_IN_SCOPE`, including within its own environment, and under `noEnvironmentPolicy: allow-all` every runtime is admitted, regardless of selectors. Tests set `Groups` on the principal directly, which hides this. TS-3 replaces the delegation gate with the environment caveat of the session grant (0166 "DP-1"), which holds the session's E and any sharing path, and checks a `session.create` of a session with E against the session's E and the live declarations, with no reference to the principal or to the owner's membership. A session with E = ∅ keeps the existing check, adds `ENVIRONMENT_REQUIRED`, and cannot cross. That existing check is the one F-10.6.16 records, so what the check reads for a session with E = ∅ is open as decision 32 in `decisions.md`.
- **The parent is the calling session.** Today's delegation tools take the parent session from their arguments, and the gateway accepts any session with the same owner: `lenny/delegate_task` reads `parentSessionId` and `lenny/await_children` reads `sessionId`, and `lookupCallerSession` admits any session of the same owner. A runtime can therefore name another session as parent and escape its limit, its environment, and its crossing mark, or read another session's child results. When the principal carries `SessionID`, as `WithSessionPrincipal` sets it, TS-3 makes that session the caller of every platform operation of 0166 "DP-1": `session.create` takes no parent argument, and each operation that names a session acts only on a direct child of the caller, apart from `files.import`, which names a session that delivered the caller a file part, and `session.self`, which names none. An operation whose `sessionId` names a session that is not the caller's child answers `404 RESOURCE_NOT_FOUND`, under the existence-hiding rule of §10.2 **Session ownership.** rule 7, so a runtime learns nothing about a session it cannot act on. `PARENT_SESSION_MISMATCH`, which revisions before 44 gave for a parent argument that differed from the calling session, leaves, because no operation of 0166 takes a parent argument. A client at the gateway edge acts on a session through its own REST routes under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), and the rules read that session's row. F-10.2.29 is separate: it is the finding that the gateway serves a call a pod's runtime adapter forwards under whatever session ID the adapter presents, so a compromised adapter can present another session's ID, and this rule does not stop that. TS-3 does not depend on F-10.2.29, and its `security` tier tests cover a runtime's tool calls and no forged adapter call.
- **The intra-pod tool surface.** `toolbridge.Bridge` forwards any registered tool, so a runtime can call `lenny/create_session` or `lenny/create_and_start_session` and start a new root with no limit, another environment, and no crossing mark. TS-3 allow-lists the Bridge's list and call to §9.1's **Platform MCP Server Tools** table, which omits those tools, together with the platform operations of 0166 "DP-1", and any other name answers `ErrPlatformToolNotFound`. Under [`0139-runtime-protocol`](../0139-runtime-protocol/change.md), the intra-pod tool surface is the `platform` tool server reached by `tool_call`, and the allow-list applies to it unchanged, on every pod. The gateway-hosted delegation tools of [`0135-message-delivery`, "MD-23"](../0135-message-delivery/change.md#md-23-tool-and-frame-names) leave under 0166, whose operations take their place on the allow-list, and the reference tools such as `start_session` run in the reference MCP bridge and never reach the gateway. The gateway edge is unchanged. A later proposal for F-10.2.32, the finding that the MCP and adapter session surfaces skip §10.2's permission matrix, must not reopen this by exempting in-pod principals.
- **Fail closed.** The environment caveat refuses on every read error, where `runtimeAuthorizedForCaller` returns true on a `Runtimes.Get` error today. [DR-8](../0147-tenant-derived-runtimes/change.md#dr-8-interactions) in [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md), which covers that design's interactions with delegation and environments, depends on this check. `runtimes.list` answers from the session's E and its live sharing paths, in place of the principal's groups, and it omits sharing paths from a session under a lock, its own or inherited (`egressLockHosts`).
- **Effects on existing features.** Billing rollup, retention tier, the environment's delegation inputs, and §4.3 credential scope read the same field, so a child and a derived session follow the session's environment in each. The `environment` claim of an identity assertion that `netagent` attaches for an operator service reads it too ([`0124-connector-removal`, "CR-2 Identity assertion"](../0124-connector-removal/change.md#cr-2-identity-assertion)).

#### Client delegation limits (decision 26)

The owner settled this on 2026-11-03, in the words "yes, add it with maxDepth: 0". `delegationLease.maxDepth: 0` at session creation means this session cannot delegate. #### Cross-environment sharing (decision 14)

The owner settled decision 14 on 2026-11-03: keep cross-environment delegation, under option B with guardrails, in the words "go with B with these guardrails". Option B is opt-in sharing under which a crossing child runs under the target environment's policy unchanged, as "Model" below states. TS-3 carries it, because it needs TS-3's session-based environment check and child propagation, which also close F-10.6.15 and F-10.6.16. Under decision 41 of 0166, TS-3 owns crossing for every operation of 0166 "DP-1".

**Model.** A crossing child runs under the target environment's policy, unchanged: the target's allow list, denies, routes, bindings, pools, and repositories. A shared runtime has the same egress and credentials for every caller. Nothing in those sets is intersected with the caller's, so the rule of 0166 DPR-3 that a child's credential bindings and egress hosts are subsets of its parent's applies within one environment only (0166 decision 41). Across environments, the `credentialBindings` and `egressHosts` arguments of `session.create` can only narrow what T's policy gives. A child still takes from its parent's grant every security caveat other than the bindings and hosts: its remaining depth through its stored `maxDepth`, the isolation floor, the policy cap, `onParentEnd`, `offerTools`, `leave`, `leaveMaxDepth`, and the content caveat (0166 "DP-1"). T narrows each where it has an input: the child's policy cap also intersects T's `defaultDelegationPolicy`, its numeric caveats are lowered to T's `delegationCeilings`, and its content caveat is narrowed by T's level. The child's principal is its parent's (0166 "DP-2").

What moves across is the `task` and the `files` of `session.create`, the messages of `session.send` downward and the child events upward under [`0135-message-delivery`](../0135-message-delivery/change.md#md-22-parents-and-children), which removes the `siblings` scope, file parts in either direction with their import through `files.import` and a parent's `materialize` push, the child's runtime, state, and tags in `session.list` and `session.get`, and the parent's routing labels, with which the child's `routing` map starts under [RT-3](../0141-runtime-routing/change.md#rt-3-routing-labels), as for any delegated child ([`0141-runtime-routing` decision D14](../0141-runtime-routing/decisions.md#decisions)). Its results return to the caller. A crossing child takes T's `placementRequirements` together with its parent's effective placement requirements, because [PM-4](../0136-placement/change.md#pm-4-placement-requirements) adds a delegated child's parent's requirements to its own, so a child never runs on weaker placement than its parent or than its target environment requires.

- **Messages.** A message between the parent in E and the child in T passes the sending environment's content caveat and `PreMessageDelivery` interceptors and then the receiving environment's. The rules that bind the whole tree, the grant's caveats, the carved budget, `maxDelegationPolicy`, and `messagingRateLimit`, apply on every edge whatever environment either end is in, as [`0135-message-delivery`](../0135-message-delivery/change.md) states under its settled B-O5.
- **Files.** A file that moves between the parent and a crossed child passes the sender's content caveat on export and the receiver's on import, under 0166 decision 45. A `files` export on `session.create`, a `materialize` push on `session.send`, and a `files.import` across environments therefore apply both content caveats, each with the environment level of its own session, and the cooldown of [`0142-security-oversight`, "Tightening and weakening"](../0142-security-oversight/change.md#tightening-and-weakening) covers each.
- **What a parent reads of a crossed child.** A parent's watch of a crossed child, and its `session.messages`, carry only what this model lists as moving across: the messages the child sends its parent, its child events, and its results. They leave out the child's activity and its tool calls with their results, and they keep the child's usage totals, which are cost figures rather than data from T (0166 decision 34). This list is TS-3's, and the filter that applies it to the watch and to the read is MD-25's of [`0135-message-delivery`](../0135-message-delivery/change.md#md-22-parents-and-children). No filter keeps a compromised child from encoding what it read in a message, and the sharing decision bounds what the child can read.
- **Parent tools.** A parent's tools never reach a child in another environment (0166 decision 41). The post-chain point refuses a `session.create` that crosses and carries `tools` or `offerTools: allow`, and the gateway refuses a `session.send` to a crossed child that carries `tools`, each with `403 TARGET_NOT_IN_SCOPE` and `details.reason: "parentTools"`. A child whose environment changes in no other way keeps none of its parent's tools.
- **Leaving the parent.** A crossed child that leaves its parent under 0166 "DP-2" keeps its environment T and its crossing mark. `session.release` makes it a root of the same principal in T, and `session.transfer` makes the root's client its client, which reads the child's whole stream. Both run the explicit admission check for T, as for a derive: the principal must hold at least `creator` in T, and T's `runtimeSelector` must admit the child's runtime. Otherwise the leave answers `403` and the child stays with its parent (decision 43). A leave of a crossed child also requires the conditions that "The check" below states for a session with a crossing mark, so a forbidden setting or a removed declaration refuses it with `TARGET_NOT_IN_SCOPE`.

**Opt-ins.** Sharing is off for each tenant by default, and it needs both of these:

```yaml
tenant:
  dangerouslyAllowCrossEnvironmentSharing: false   # default

environment:                     # web
  dangerouslyShare:
    outbound:
      - targetEnvironment: platform
        runtimes: { matchLabels: { shared: "true" } }
environment:                     # platform
  dangerouslyShare:
    inbound:
      - sourceEnvironment: web
        runtimes: { matchLabels: { shared: "true" } }
```

`dangerouslyShare` replaces `crossEnvironmentDelegation`, in the same two-sided form. `runtimes` must be a non-empty selector on both sides, because `Selector.Matches` with no clauses admits every runtime. `ENVIRONMENT_NOT_FOUND` and `RESOURCE_HAS_DEPENDENTS` cover these names, so a recreated environment inherits no path. With the tenant setting off or forbidden (see guardrail 5), a write that adds an entry answers `422 CROSS_ENVIRONMENT_SHARING_DISABLED`, and a removal always succeeds. Existing declarations stay stored and have no effect, and they apply again if the setting returns, which posture lists. A `tenant-admin` writes both sides, so the two-sided form records each environment's intent and does not separate two people. No name in the tree conflicts with these.

**The check.** On each `session.create` whose final runtime the parent's selector does not admit, the environment caveat requires all of these, reading them live as §10.6 **Cross-environment check evaluation semantics** states:

1. The session holds a grant that permits a child. A session under `maxDepth: 0` holds none and can never cross, whatever the environments declare, and it gets `DELEGATION_DISABLED` first.
2. The session is not under a lock, its own or one inherited from an ancestor, because that lock limits every descendant to its hosts and a crossing child runs under T's list. A child records the lock as `egressLockHosts`, with the inherited inputs the delegated child rule stores on its session row, and each descendant and derived session copies it, so a session holding no binding is still under it. [UC-5](../0151-user-credential-delivery/change.md#uc-5-delivery-file), the user credential design's `delivery: file` proposal, owns the field. Otherwise this answers `TARGET_NOT_IN_SCOPE`.
3. The tenant setting is on and not suspended (see guardrail 5).
4. The parent's E is not ∅, and its `crossed_from_environment` is null.
5. An outbound entry in E's list names a target T and its `runtimes` admit the runtime. The first such entry in list order that also passes the next two checks selects T, so the source environment controls the order.
6. T's `runtimeSelector` admits the runtime.
7. An inbound entry in T's list names E, and its `runtimes` admit the runtime.
8. The child's inherited `labels` satisfy T's label rules and carry each key T requires, under "Label rules (TS-10)". A child that fails this check is refused with `403 LABEL_NOT_PERMITTED` (decision 46).

For a session with a crossing mark, every `session.create`, including one inside T, and the `session.release` of such a session, also require that the tenant setting is on and not suspended, that the marked environment's outbound list still names T, and that T's inbound list still names the marked environment. Otherwise each answers `TARGET_NOT_IN_SCOPE`, so a forbid or a removed declaration stops a crossed subtree from creating children or leaving the tree. Sessions already running continue.

`CrossEnvironmentReachable` returns a boolean today, and the child needs T, so it must return T. Its wildcard match on `*` goes. The gateway first evaluates the check on the requested runtime when `session.create` arrives. The evaluation that selects T and sets the child's E runs at the post-chain point of [RT-2](../0141-runtime-routing/change.md#rt-2-the-interceptor-contract), on the final runtime the child's `PreRoute` chain leaves, for every `session.create` whether or not an interceptor changed the runtime, beside the other checks of 0166 "DP-1" that run there. A final row that leaves the path, changes T, or changes whether the hop crosses refuses the `session.create`, because the first evaluation ran on the earlier answer. An in-flight child is not revoked when a declaration or the setting changes.

**Guardrails.**

1. **Tenant denies.** The tenant's `denied` list applies in every environment, because `denied(T)` includes it. `environmentPolicies[E].denied` of the caller does not apply to the child.
2. **User authorization.** The child keeps its parent's user (0166 "DP-2"), so a mint on a VCS pool in T with `userAuthorization: required` checks Alice's own access to that repository, and TS-4's invalidation levels stop it. This covers repository reads and writes on VCS pools with `userAuthorization: required`. It does not cover a pool with `userAuthorization: off`, where the App's token reaches T's allowlist for any caller, a stored API key under `delivery: inject`, a tenant-wide or scoped binding with no user, a binding with `delivery: federation` or `delivery: metadata`, a host on T's allow list, an operator service the child reaches through T's egress, or the LLM upstreams that T's environment lists. A `userCredential` binding crosses only when `session.create` names it in `credentialBindings` and T can see the binding and its type, and `caller_type` is copied as [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) states.
3. **No second crossing.** A child's grant carries its parent's `maxDepth` across a crossing, so the target's policy does not widen it. The child's row records `crossed_from_environment`, a new nullable column holding the caller's E. A session with a value cannot cross, which closes transitive chains. A same-environment descendant stays in T, copies the value, inherits its parent's inputs under the ordinary rule, and can create children on runtimes T's selector admits. It cannot cross either. A derived session and a released session copy the value and meet the explicit admission check for T.
4. **Named environments only.** `sourceEnvironment: "*"` and any wildcard source or target are refused at write with `422 VALIDATION_ERROR`. The sharing side names who it trusts. This differs from §10.6's example, which shows `sourceEnvironment: "*"`. `runtimes` keeps its label selector.
5. **Security oversight.** A `security-admin` can forbid the tenant setting through the guardrail `crossEnvironmentSharing: forbid` in the tenant security record of [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture). A forbid refuses additions and suspends existing paths, so the setting reads as off at the crossing check, and the operations SO-2's enforcement table names for it are refused. Turning the setting on, and adding a `dangerouslyShare` entry, each take [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s weakening delay at a tenant with a security record, and posture reports the setting and each declared path. A label edit on a runtime or a change to T's selector can add a runtime to a path at once, with no delay, which "Residual risks" states.
6. **Records.** `delegation.spawned` of 0166 DPR-11, which carries `cross_environment` today as the delegation audit event, gains `caller_environment` and `target_environment`, and `delegation.left` of a crossed child names both. §11.7 events, `credential.mint`, and evidence for the child carry `environment`, which is T, and `crossedFromEnvironment`, which is the caller's. Billing and retention follow T, through the same field they read today.

**Accepted risk.** The owner accepted these statements:

- On a declared path, an injected caller can hand data to a target runtime, which can send it anywhere the target allows, skipping the caller's denies and proxy.
- A non-member's agent can drive the target's credentials and receive results, on any pool with no user check.

The first statement includes anything the caller's agent can read, such as a token delivered under `delivery: file` with no `lockEgressToHosts`. A session under that lock cannot cross.

**Interactions.**

| Surface | Behaviour under this model |
| :-- | :-- |

A fill's cause is the child's pod, whose E follows TS-1's rules, or the gateway cause assertion for the child, which carries E = T. The child can read T's stores on pools with `userAuthorization: off`. |

### Identity model (TS-2, TS-4, and TS-6 to TS-9)

#### Owner's decision

The owner decided decision 8 on 2026-11-03, reversing revision 12's recommendation, in these words: "I think we need to support per-tenant OIDC and serve SCIM. In that model, a deployer can use a broker by default but change to a customer's SSO when needed". The evidence for the need remains vendor documentation with no first-hand complaint found, so the decision rests on the owner's judgment of the product rather than on that evidence.

The model is:

- **A tenant has one or more identity sources.** The default is the deployment source, the issuer at `auth.oidc.issuerUrl`, which can be the operator's broker. It needs no record until the tenant uses SCIM, and the tenant comes from the tenant claim, under "Broker contract".
- **A tenant can instead be configured with a customer source**, the customer's own OIDC issuer, pinned to that tenant, or on a listed shared issuer its organization on that issuer, under "Activation rule". The source is a configuration choice. Lenny has no mechanism for moving a tenant from one to the other, and the owner removed migration from this design.
- **Lenny serves SCIM 2.0**, for a tenant on either kind of source.
- **Both kinds coexist.** One deployment holds tenants on the deployment source and tenants on customer sources at once.
- **A single-company deployment is unaffected.** With the Helm value `auth.multiTenant: false`, which runs the deployment as a single tenant, or no customer source, the registry holds only the deployment issuer, subjects keep their form, and a write of a source is refused.

This table records what each side costs. Column B is now designed below, and column A stays the default.

| Concern | A: broker | B: per-tenant OIDC and SCIM in Lenny |
| :-- | :-- | :-- |
| Lenny code for SSO | The protected resource metadata route and the `WWW-Authenticate` challenge, and the boundary changes in this section | The same route, plus the source record, the verifier registry, per-issuer JWKS caches on the gateway and the Token Service, and per-source claim mapping |
| URLs from tenants | No issuer URLs. `identityProvider.introspectionEndpoint` is already a tenant-supplied URL the gateway calls, and TS-4 adds its missing address check. | Each issuer and `jwks_uri` is also a URL the gateway and the Token Service fetch |
| Issuer ownership | Broker concern | Lenny must establish that a tenant controls what it registers |
| Protocols | Whatever the broker federates, including SAML | OIDC alone. A SAML-only customer stays on the deployment source behind a broker. |
| Login routing | One authorization endpoint named in one metadata document. The broker does home-realm discovery, choosing the customer IdP a user signs in at, for example from the email domain. | Per-tenant URLs and metadata |
| SCIM | Lenny's server, or a broker or vendor endpoint with a sync worker | Lenny's server |
| Group storage | None required. Groups can stay in tokens. | New tables when a source takes groups from SCIM |
| Subject stability | The broker issues `sub`, so a customer changing IdPs behind it keeps its users. | `sub` belongs to each issuer, and Lenny provides no migration (see "Residual risks") |
| Several IdPs in one tenant | Broker concern | Lenny namespaces `sub` and groups |
| Tenant boundary | One claim from one issuer. A broker fault or mapping error crosses tenants. | The issuer selects the tenant, or on a listed shared issuer the issuer with a provider-set audience or claim, so a customer's IdP administrator cannot assert another tenant |
| Outage | A broker outage stops logins for every tenant on it. | A customer IdP outage affects that tenant alone, or every tenant on a shared issuer |
| Operator's work | Run or buy a broker | Run Lenny's new surface, and handle customer IdP support |

No effort estimate was measured. Column B is a new subsystem, and it does not remove the need for a customer-facing portal.

#### What comparable systems do

- Keycloak's organizations link customer IdPs to an organization inside one realm, so one issuer serves all customers. Its token claim is an object keyed by organization alias. Keycloak's SCIM is per realm, and its documentation says organization groups cannot have members managed through SCIM ([project documentation](https://www.keycloak.org/docs/latest/server_admin/index.html)). A vendor extension adds [per-organization SCIM as experimental](https://phasetwo.io/blog/orgs-scim-experimental/) (vendor source).
- Auth0 organizations put `org_id` in tokens, and its documentation calls validating that identifier the preferred method ([vendor documentation](https://auth0.com/docs/organizations/using-tokens)). Its [device flow does not natively carry organizations](https://support.auth0.com/center/s/article/missing-org-id-in-auth0-device-authentication-flow) (vendor source), which matters to a CLI login.
- WorkOS sells Directory Sync, which [hides SCIM behind an API and delivers changes through webhooks or an events API](https://workos.com/docs/directory-sync) (vendor documentation).
- Products sold directly to enterprises expose SSO and SCIM themselves: [Devin](https://docs.devin.ai/enterprise/security-access/sso/guide.md) and [Cursor](https://cursor.com/docs/account/teams/scim) (vendor documentation). Those pages do not say whether a broker sits behind them. Devin's page states that without SCIM, groups sync only at login, and that the vendor's team configures the connection.
- [Coder](https://coder.com/docs/admin/users/idp-sync.md) syncs groups, roles, and organizations from claims per organization, and it overwrites membership at login (vendor documentation).
- Microsoft states that [`sub` is pairwise per application, `oid` is immutable across applications, and `email` must never be used for authorization](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference) (provider documentation). Three design choices below follow from those statements: a per-source subject claim, per-issuer `iss` values such as Entra's tenant-specific URI, and no automatic match on email.

#### Identity source record (TS-6)

`tenant_identity_sources` is a tenant-scoped table under the existing row-level security policy.

| Column | Meaning |
| :-- | :-- |
| `tenant_id`, `name` | The primary key. `name` is short and tenant-chosen, it cannot contain `~`, and `deployment` is reserved. |
| `source_id` | A random short identifier, fixed at creation, used in canonical subjects, groups, callbacks, and SCIM credentials. It is never `svc` or `agt`, which the subject namespaces reserve. |
| `issuer` | The exact issuer string. A partial unique index over rows in any state but `draft` holds the pin, so a draft claims nothing and a retired row still holds its exact pin values. Only a `draft` or `retired` row can be deleted, which for a `retired` row releases the index, and `source_id` is never reused. |
| `pin_audience`, `pin_claim`, `pin_claim_value`, `pin_claim_is_domain`, `pin_client_claim`, `pin_authorization_params`, `pin_domain_unconfirmed_since` | Empty on an ordinary issuer. On an issuer `identity.sharedIssuers` lists, they hold the values its entry requires, under "Issuer pin and proof". They are stored here so that a later list edit cannot change what the row enforces. |
| `require_directory_row` | Refuses a subject with no directory row, under "Issuer pin and proof". A change is a change on the source. |
| `authorization_endpoint`, `token_endpoint` | Captured from discovery at proof, checked under "SSRF and NetworkPolicy", and used for every login. A change is a change on the source. |
| `audiences` | The values accepted in `aud`, never empty. When a token has several audiences and an `azp`, `azp` must be in this list or equal `client_id`. |
| `client_id`, `clientSecret` | The login client. PKCE with no secret is the default, as `buildPlaygroundOIDC` does today. `clientSecret` is optional and write-only, as below. |
| `subject_claim` | The claim holding the user identifier, `sub` by default. An Entra source can name `oid`. "Issuer pin and proof" lists what a row refuses here. |
| `roles_claim`, `role_map` | The claim read for roles, and a map from its values to tenant-scoped role names. An unmapped value grants nothing. |
| `groups_claim`, `group_source` | The claim read for groups, and `token` or `scim`. |
| `service_claim` | An optional claim with the values that mark a token as `caller_type: service` or `agent`, as §25.1's agent callers need. Every other token from this source has `caller_type: human`. |
| `match_claim`, `scim_deactivate_mode` | The claim a directory's `externalId` must equal, fixed to `subject_claim` on a customer source, and what a SCIM deactivation does, under "SCIM server". |
| `email_domains` | Verified domains used for login routing. None is required. |
| `state` | `draft`, `pending_effective`, `active`, `suspended`, or `retired`. A `suspended` row records its reason, which is `address`, `domain_lapse`, `pin_required`, or `issuer_conflict`. `pending_effective` applies only to first activation, and such a row refuses writes. A `retired` or `suspended` row refuses writes too, and a reactivation that changes a field states the changes as a `pending_version` and follows the activation rule. A `retired` row returns to `active` with the same `source_id` under **Reactivating**, so a customer can recover its own issuer, and a `suspended` row returns as "Failure behaviour (identity)" states. |
| `pending_version` | A proposed change to an active source or a deployment settings row (described below the table), or to a reactivating row, under the activation rule. The row stays on its live values until the version takes effect. A pending `clientSecret` waits in its own sealed row keyed on tenant, `source_id`, and version, and the approval digest (the `approved_digest` row) covers a keyed hash of its value. A pending `deploymentIssuerAllowed` waits on the tenant record beside the flag, in the same form. |
| `tokens_not_before` | Set at retirement and carried in the snapshot. Step 7 under "Verifier registry" refuses any token, IdP or Lenny-issued, whose `iat` is earlier. |
| `proof`, `approved_digest` | The results of the checks under "Issuer pin and proof", with who ran them and when. The preview, which the sign-in proof under "Issuer pin and proof" produces, holds the canonical subject, and no name. Any draft edit clears `proof`. Approval records a digest of the first activation's row or of the pending version, which must still match at effect. |
| `activated_by`, `justification`, `ticket_id`, `effective_at` | The activation record. `ticket_id` is optional, for an operator whose process uses tickets. |

**Deployment settings.** A tenant on the deployment source that uses SCIM has one row with `source_id: deployment`, the reserved name, and no `issuer`. It holds `match_claim`, `scim_deactivate_mode`, `group_source`, and its credentials, it has the same states, and it is not a registry entry. A change to it follows the activation rule, and the proofs do not apply, because it names no issuer.

**Client secret.** The same mechanism applies as for a link provider's client secret in [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md). The Token Service stores the submitted value envelope-encrypted under the tenant's Token-Service-only key, in a row keyed on tenant and `source_id`, sealed with a digest of `tenant_id`, `source_id`, `issuer`, `token_endpoint`, and `client_id`. No route returns it, and no field names a Secret, so a tenant cannot point at another tenant's. The Token Service alone reads it, and a source with a secret has its code exchange done by the Token Service over mTLS, which sends the value only when the digest matches and returns the token response to the gateway. A change to any sealed field leaves the secret unusable until a write re-supplies it.

A tenant holds at most a small number of sources, a Helm value that defaults to 5, so the registry and its caches stay bounded. A write creating a row that names an issuer on `identity.deniedIssuers`, a Helm list that ships with known shared issuers, is refused unless `identity.sharedIssuers` lists it, and a write naming the deployment issuer is always refused. Writes go through a new admin resource, `/v1/admin/tenants/{id}/identity-sources`, with `If-Match`, and through the single write path for tenant opt-ins that the egress design's proposal [EG-9](../0127-egress-and-git/steps.md#steps) (egress policy objects) adds, once it lands. §10.6's `identityProvider` keeps its introspection settings and gains no issuer.

**Activation rule.** A source can be drafted by a `tenant-admin`, a `security-admin`, or a `platform-admin`. Activation is the power to decide who every user in a tenant is, so it follows a stricter rule (decision 17):

- A `platform-admin` activates a source, with a justification, once the proofs pass. A `tenant-admin` cannot, because a stolen tenant admin credential could otherwise plant a lasting backdoor.
- At a tenant with a `security-admin` row in any state, activation and a change to `deploymentIssuerAllowed` take the weakening delay of [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture). Any reachable `security-admin` must also approve and can cancel. Invalidating the security team therefore does not remove the delay. This extends [`0142-security-oversight` decision 23](../0142-security-oversight/decisions.md#decisions)'s rule for `identityProvider.*`, since an operator able to repoint an issuer silently could regain what the pin removes.
- A deployment can set `identity.allowTenantActivation: true`, default `false`, under which a tenant's `security-admin` activates alone, with the proofs passing and the same delay, and no operator action. A tenant with no `security-admin` always goes through the operator.
- Every change on an active source or a deployment settings row, including `roles_claim`, `groups_claim`, `group_source`, `client_id`, `clientSecret`, endpoints, an added `email_domains` or `audiences` entry, `match_claim`, and `scim_deactivate_mode`, creates a `pending_version` under the same rule. Further widening writes are refused while one exists. A stated narrowing applies at once: removing an audience other than the last, a `role_map` entry, or an email domain. A narrowing, a suspension, or a retirement cancels the pending version, and its proposer can submit it again.
- Before activation, a preflight reads the proof's preview. At a tenant with a `security-admin` row in any state, it refuses unless a `security-admin` row exists on a canonical subject of the new source, so oversight survives activation, and it lists what stays on old subjects: principals, `lifecycleSubjects`, role rows, and owners of running sessions. On a reactivation it also lists role rows, custom roles, and SCIM credentials written by that source's subjects. The preflight refuses or lists, and it migrates nothing.
- **Retiring.** A `security-admin` retires a source at once. A `platform-admin`'s retirement at a tenant with an active `security-admin` takes [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s delay and can be cancelled, because immediate retirement would lock out the principals who could cancel what follows. At a tenant with none, it applies at once with a justification. An attacker asserting a principal's subject through a compromised issuer could cancel a delayed retirement, so the incident path is invalidation first and retirement second: an invalidated principal does not count as active here, and this path is reversible. Retirement sets `tokens_not_before`, and TS-8 adds the step that revokes the source's SCIM credentials. It ends playground records from the source. Its subjects are refused under "Verifier registry".
- **`invalidateSubjects`.** This optional mode needs a second `security-admin` or [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s delay, because it cannot be undone, and that confirmation comes before the retirement it accompanies, since a sole source's retirement refuses the second principal too. It runs §11.4's `full_revoke` for each of the source's subjects, as a job that reports partial failure, placing an `admin` hold on each. Reactivation clears none of those holds. An admin clears them per subject, or in bulk by naming the job.
- **Stranded rows.** A security principal row on a subject whose source is not active counts as active for approval and for the **Platform admin limit** of [SO-1](../0142-security-oversight/change.md#so-1-security-roles), under which a platform admin assigns `security-admin` only when the tenant has no active one, so a retirement cannot remove the approver by locking it out.
- **Reactivating.** Every return to `active` takes the locked overlap check under "Issuer pin and proof", and a domain-pinned row takes the conditions under "A lapsed domain". Returning the same `source_id` needs a new sign-in proof and a justification recording the customer's request, and it drops cached keys. The row returns on its stored values, and any changed field waits as a `pending_version` under the activation rule. When a reachable principal exists, such as on a second source, it also needs that principal's approval and the delay. A proof does not show that a compromised key was rotated, because such a key can choose its own `iat`, so the customer rotates it first. A different issuer follows the activation rule.
- **A customer that has permanently lost its issuer.** Its principals cannot authenticate, and they count as active, so no customer approval exists. The operator removes those rows under [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s delay, which nobody can cancel, and assigns a new `security-admin` against the customer's recorded request. The customer's protection in this case is the operator's process and the mirrored audit record.
- `issuer`, the pin fields, and `subject_claim` cannot change on a row, because canonical subjects include `source_id` and a changed issuer's `sub` values could collide with the old ones and inherit their records. A different issuer is a new row with a new `source_id`.

**Pointing an existing tenant at a different issuer.** The write is allowed, under the activation rule and its preflight above, with no further check. Refusing it would need a definition of a tenant that already has users, and an exception for tenants that want this. "Residual risks" states the consequence.

**Which issuer a tenant accepts.** The tenant record holds `deploymentIssuerAllowed`, true by default. Activating a customer source sets it false, and retiring that source leaves it false, so retiring a compromised source does not reopen the tenant to the broker. Every move of a customer source to `active` sets it false. Setting it back to true follows the activation rule, and it is refused while a customer source is `active` or `pending_effective`. Any such move, and a pending reactivation, cancels a pending change to true, and the change is checked again at effect. A tenant therefore accepts either the deployment issuer or its customer sources, and never both.

#### Verifier registry

`pkg/auth/jwt` gains a registry member that `composeBearerVerifier` and `buildCallerVerifier` join behind the Lenny key set, so the gateway and the Token Service run one implementation:

1. It refuses a token over 16 KiB, decodes the payload with no verification, and reads `iss`, capped at 512 bytes.
2. It looks `iss` up in an in-memory snapshot of active sources, by exact match. The deployment issuer is the entry that keeps today's path. A shared issuer's entry holds one verifier and its pinned rows, and its `issuerAliases`, the other spellings of its issuer that "Issuer pin and proof" describes, lead to the same entry.
3. An unknown `iss` is refused with `401 TOKEN_INVALID`, with no fetch of that issuer and no store read. The reason `unknown_issuer` appears in logs and counters and never in a response, because a caller could otherwise test which IdPs are customers. The gateway's `serveServiceIdentity`, which admits §25.4's service accounts, still submits a `TokenReview` for a token claiming its audience, which is an existing path and is not an issuer fetch.
4. The entry's own verifier checks the signature, `iss`, `aud`, `exp`, and `nbf`. The unverified `iss` selected a verifier and nothing else, so a token claiming a victim's issuer but signed elsewhere fails against the victim's keys. On a shared issuer, the verifier checks the signature, `iss` against `issuer` and `issuerAliases`, `exp`, and `nbf` here, and `aud` follows in step 5.
5. On a shared issuer, the verified `aud` and pin claim select the row. The claim is read by exact key and must be one non-empty string of at most 256 bytes. A row matches when `pin_audience` and `pin_claim_value`, where non-empty, each equal the token's value, read under `pin_claim`, and an empty field places no condition. Exactly one row must match. The selected row's `audiences` and `azp` rule then apply on every pin form, so a token Acme's user obtained for another application is refused. No match and more than one match are each `401 TOKEN_INVALID`, with the reason in logs and counters alone, so a caller cannot test which organizations are customers. For a customer source, the tenant is the record's tenant, and any tenant claim in the token is ignored. For the deployment issuer, the tenant comes from `auth.tenantIdClaim`, and the request is refused with `401 TENANT_ISSUER_MISMATCH` when that tenant's `deploymentIssuerAllowed` is false. This second check is what keeps a broker out of a pinned tenant.
6. The claim allowlist, `normalizeUserBearer`, and the role boundary apply, and the canonical subject is computed.
7. The check first strips one `~svc~` or `~agt~` caller-type namespace from the subject, under "Caller-type namespaces." below, and reads the source from the remainder. A subject whose source is not active is refused with `401 TOKEN_INVALID`, by the remainder's `~<source_id>~` prefix against the snapshot, and so is a token whose `iat` precedes the source's `tokens_not_before`, or that has no `iat` when that value is set. A remainder with no `~` prefix is a deployment subject, a bare subject, whether or not a namespace preceded it, and a bare subject is refused at a tenant whose `deploymentIssuerAllowed` is false. A service or agent token of a retired source therefore meets that source's `tokens_not_before`, and a deployment service token meets the bare-subject refusal. [`0143-service-account-credentials`](../0143-service-account-credentials/change.md) SA-6, which 0143.S1 implements, adds the namespaces, and 0143.S1, which depends on 0149.S6, adds the stripping with them. A subject with no directory row is refused here too on a source with `require_directory_row`. This check sits in the auth middleware, in `lenny-ops`, on `/v1/oauth/token` for the caller, subject, and actor tokens, in the browser resolver, in `/v1/playground/token` in both playground mint modes, and in the impersonation mint, so it covers Lenny-issued tokens too. `mintOIDC` has no token to read, so it compares the playground record's issue time with `tokens_not_before`. `mintAPIKey` calls the verifier directly and `completeMint` stamps a new `iat` today, so without this check a mint during retirement would produce a token that survives reactivation. The bootstrap `lenny-admin` credential and §25.4 service identities are exempt, as the recovery path.

The snapshot is rebuilt from Postgres on a version change announced through Redis and on a poll every `identity.registry.pollSeconds`, and it survives a store outage with its last value. Past `identity.registry.maxSnapshotAgeSeconds`, `IdentityRegistrySnapshotStale` fires. It reads a dedicated view exposing `tenant_id`, `source_id`, `issuer`, the pin fields, `audiences`, `client_id`, `require_directory_row`, `state`, `tokens_not_before`, `deploymentIssuerAllowed`, and the mapping fields to a dedicated role, because a pre-authentication read across tenants cannot use §12's `__all__` path, the `app.current_tenant = '__all__'` setting through which a platform-admin path reads across tenants under row-level security. `lenny-ops` keeps its single issuer, and a customer source's user reaches it only through a Lenny-issued token. TS-2 closes F-13.3.27: `/v1/oauth/token` refuses a playground-origin `subject_token`, the token being exchanged, because `mintToken` drops `origin` and `lenny-ops` would otherwise accept the result. It reverses `TestPlaygroundOriginSubjectTokenAccepted_spec_13_3` and the `authenticateCaller` comment that pin today's behaviour. Tenant administration uses the gateway's admin API. Reasons are counted without the `iss` value, because it is attacker-chosen.

#### Keys and caches

Each source has its own `OIDCVerifier` on each gateway and Token Service replica, built lazily on the first token for that issuer. A shared issuer has one verifier for all its rows, so key refresh, maximum staleness, and the refetch limit apply per issuer. A tenant's reactivation there fetches keys first and swaps them on success, so it does not interrupt other tenants. `OIDCVerifier.key` holds its mutex across a fetch, so one slow IdP can pile up waiting requests. TS-6 therefore refreshes in the background with no lock held. `MinRefetchInterval` already limits fetches for an unknown `kid`, per issuer. A refresh re-reads discovery, because `jwksURI` is otherwise cached until restart.

These verifiers accept keys that a tenant's issuer chooses, and verification runs before the rate limit in `httpsurface.go`. TS-2 therefore bounds RSA at 4096 bits, a Helm value, and requires `e` of 65537, because `publicKey` enforces only a minimum today. The cost of an oversized key has not been measured.

A refresh failure keeps the previous keys, as `refreshLocked` does today. A replica that restarts during an IdP outage has none, so that source's tokens fail on that replica until the IdP returns. For a customer source this design adds a maximum staleness, a Helm value that defaults to 24 hours, past which that source's tokens are refused with `503` and its alert fires, because an IdP that rotated out a compromised key while unreachable would otherwise stay trusted indefinitely. The deployment issuer keeps today's behaviour. Decision 22 covers the value.

#### Claim allowlist and mapping

TS-2 changes the IdP boundary for every issuer. Today an IdP-verified token keeps `caller_type`, `act`, `authorized_tools`, and `scope`, and `normalizeUserBearer` clears only `typ`, `session_id`, `delegation_depth`, and `origin`. The boundary instead builds claims from an allowlist, each read by exact key, because Go's struct decoding also matches other cases: `iss`, `aud`, `azp`, `exp`, `nbf`, `iat`, `jti`, `sub` or `subject_claim`, `scope`, the roles claim, and the groups claim, plus the tenant claim on the deployment issuer. `match_claim`, `service_claim`, `nonce`, `email`, and the provider identity claim that a link provider with `identityBinding: claim` names under [UC-2](../0151-user-credential-delivery/change.md#uc-2-the-oauth2link-source-and-account-linking) ([`0151-user-credential-delivery`, "Identity binding"](../0151-user-credential-delivery/change.md#identity-binding)), are read by exact key and returned only to the purpose that needs them. Everything else is dropped. An absent or empty subject claim refuses the token.

`scope` is filtered to values with the `tools:` prefix, as §25.1's deployer policies at the IdP need. A token with no such value has an absent scope, and a malformed `tools:` value stays `TOKEN_INVALID`, as does a value with any case of `tool` as its prefix that fails to parse, such as `tool:pool:read` or `TOOLS:pool:*`, because reading it as absent would widen the token. Dropped values are counted. No mapping is needed, because scope only narrows, so it is safe from any issuer, and `openid profile` no longer refuses the token. `caller_type` comes only from `service_claim`, or `auth.serviceClaim` on the deployment issuer, which can set `service` or `agent`, and every other token reads `human`. The `security-*` values in the roles claim pass the boundary to the role resolver of [`0142-security-oversight`](../0142-security-oversight/change.md), which removes them under `securityRoleSource: managed` and reads them under `securityRoleSource: oidc`, so `role_map` is not involved.

The tenant has no mapping on a customer source, because the record supplies it. `role_map` is explicit because customer IdPs emit a `roles` claim for their own purposes, as Entra's token reference shows, and today's code would read it as Lenny roles. The mapping can name tenant-scoped built-in roles and custom roles, and a write naming a platform role or a `security-*` role is refused. A platform role is a built-in role whose authority spans tenants: `platform-admin`, and `platform-forensics` of [`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md) FE-0. `groups_claim` must yield an array of strings. Past Entra's overage limit [the claim is absent](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference) (provider documentation), which reads as no groups and refuses the environment, so a tenant with users in many groups uses `group_source: scim`.

#### Issuer pin and proof

An issuer pins to one tenant through the partial unique index, checked at activation, unless `identity.sharedIssuers` lists it, and the deployment issuer can never be registered as a customer source (decision 18). A conflict returns a generic refusal, so the answer does not say whether another tenant holds the issuer. `email_domains` are unique in the same way. The harm being prevented is specific. A tenant pointing at an issuer it runs gains nothing outside itself, because the tenant comes from the record. A tenant claiming another customer's issuer can squat it, so the customer that owns it cannot register, and with a claimed email domain it can route that customer's users to its own tenant's login.

These proofs run in order, and each is recorded on the row:

1. **Discovery.** `issuer` in the document must be identical to the URL used, as [OpenID Connect Discovery requires](https://openid.net/specs/openid-connect-discovery-1_0.html), and `jwks_uri` must be `https`. This proves the URL serves a consistent issuer, and no more.
2. **Sign-in.** A named customer administrator completes an authorization code login with PKCE and a nonce against the issuer, through the client the record names. The login starts from the drafting admin's session, or from a one-time token that names the expected source, is short-lived, and is single use. It uses the callback and resolver under "Browser login" and creates no session or bearer. The result previews the mapped subject, roles, and groups. This proves a client is registered at that issuer and the mapping works. It is weak on ownership alone, since some IdPs let an ordinary user register an application.
3. **Domain.** For each entry in `email_domains`, a DNS TXT record at `_lenny-challenge.<domain>` holds a value bound to the tenant and source. This proves control of a domain and is what permits routing by it. It does not bind a domain to a hosted issuer, because no record at `login.microsoftonline.com` is the customer's to write. The record is re-read daily, and a lapsed domain stops routing and affects no token, except on a row with a domain pin, under "A lapsed domain".
4. **Attestation.** The platform admin's justification records the customer's request for this issuer, and the operator keeps whatever further record its own process requires. Under `identity.allowTenantActivation`, the `security-admin`'s approval stands in its place.

**Shared issuers (decision 18).** Some providers use one issuer for many customers, so the issuer alone cannot select a tenant. Google's ID tokens carry `https://accounts.google.com` for every customer and name the organization in `hd` ([provider documentation](https://developers.google.com/identity/openid-connect/openid-connect)), and an Auth0 tenant using organizations names one in `org_id`. An issuer unique to a customer, such as an Okta org URL or Entra's tenant-specific URI, keeps the one-tenant rule above.

`identity.sharedIssuers` is a Helm list that a platform admin writes. Each entry names `issuer` and `pinBy`, which is `audience`, `claim`, or `audienceAndClaim`. An entry using a claim names `claim`, and sets `claimIsDomain: true` when the value is a DNS domain. An entry can also name `issuerAliases`, `authorizationParams`, `subjectClaims`, and `clientClaim`, which the items below describe.

```yaml
identity:
  sharedIssuers:
    - issuer: https://accounts.google.com
      issuerAliases: [accounts.google.com]
      pinBy: claim
      claim: hd
      claimIsDomain: true
      authorizationParams:
        hd: "{pin_claim_value}"
```

A **shared-issuer row** is a row with a `pin_audience` or `pin_claim_value`, whatever the list says now, and a **shared issuer** is one that is listed or that has such a row. Registry step 5, the client claim rule, the issuer-level hold (the stop on a shared issuer's fetches under "Failure behaviour (identity)"), and the lapse check follow that definition.

- **Issuer spellings.** `issuerAliases` lists other exact strings the provider's tokens carry in `iss`. Google's documentation names `https://accounts.google.com` and `accounts.google.com`. Each is an exact match, with no normalization or pattern. Only the Helm entry holds aliases, and a tenant cannot add one. `issuer` is what discovery and every fetch use, so an alias is never fetched and needs no address check. A row's `issuer` must be the entry's `issuer`, and a draft naming an alias is refused. The chart refuses an alias that equals the deployment issuer or another entry's `issuer` or alias.
- **What the entry asserts.** The platform admin asserts what Lenny cannot check: no customer's administrator can set that claim to a value another customer uses, and the provider issues a token with a pinned audience only to the registered client. A false assertion restores the tenant-claim risk. The chart refuses the deployment issuer, and refuses `auth.tenantIdClaim`'s value, `tenant_id`, `sub`, `email`, `preferred_username`, `name`, `given_name`, `family_name`, `nickname`, `org_name`, `groups`, and `roles` as a `claim`, and it warns on an issuer and claim pair outside a shipped list of known pairs. The claim must be a top-level string, so Keycloak's organization claim, an object, needs a mapper on an attribute users cannot edit. An entry overrides `identity.deniedIssuers` for its issuer. The configuration preflight refuses an alias equal to a row's `issuer`. If one arrives anyway, because the chart cannot see rows, a row whose `issuer` equals `auth.oidc.issuerUrl` or another entry's alias becomes `suspended` with reason `issuer_conflict` and raises its alert, and the snapshot excludes it. The shipped denied list names Entra's personal-account tenant issuer, because many customers' personal accounts share it.
- **`pinBy: audience`.** Lenny then checks no organization, so whoever can obtain that audience from the provider is a user of the tenant. The chart refuses this form on `https://accounts.google.com`, because any Google Cloud service account [can request an ID token with any audience](https://docs.cloud.google.com/docs/authentication/token-types) (provider documentation), whatever the client's login settings, and a client ID is visible in a login redirect. The chart warns on every other such entry, and posture reports each source's pin form. Such a row accepts only tokens whose `aud` is its `client_id`, so a provider's API access token, which carries an API identifier, does not work as a bearer on it.
- **The client claim.** On a shared-issuer row, the claim the entry names in `clientClaim`, `azp` by default, must equal `client_id` or a value in `audiences` when it is present, whatever the number of audiences. Google sets `azp` to the service account's ID on those tokens, so one minted with a victim's client ID as `aud` is refused. A user's token can omit it, so absence is allowed. Providers name the client differently, as Okta's `cid` and Entra v1's `appid` show, and a token that names it nowhere passes this check.
- **The subject claim.** A new owner of a domain can recreate `admin@acme.com`, so an email address as a subject would hand over that person's roles, sessions, and links. Every row refuses `email`, `preferred_username`, `upn`, `name`, `given_name`, `family_name`, and `nickname` as `subject_claim`. A shared-issuer row takes `sub` or a value in the entry's `subjectClaims`, which the platform admin asserts is immutable and never reassigned.
- **Authorization parameters.** `authorizationParams` adds parameters to the login request, each a literal or `{pin_claim_value}`, such as `hd` on Google or `organization` on Auth0. Google's token types page says `hd` appears [only when the client specified the `hd` parameter](https://docs.cloud.google.com/docs/authentication/token-types), while its OpenID Connect page reads absence as an account outside a hosted domain, so the lead case, a Google Workspace customer pinned by `hd`, depends on this. These parameters are hints to the provider, and the verified token alone decides. An MCP client makes its own authorization request and may not send them, which the **Unproven** item under "Residual risks" lists.
- **The row.** A draft on a listed issuer states its audience and claim value, and the row copies `pin_claim`, `pin_claim_is_domain`, `pin_client_claim`, and `pin_authorization_params` from the entry, so a tenant cannot choose them. `pinBy` is the minimum a new row must hold. When `pinBy` includes the audience, `audiences` holds one value, equal to `client_id`, and that value is `pin_audience`. A customer with two Lenny tenants on one provider organization uses `audienceAndClaim`, with a client per tenant.
- **Fixed values.** The pin fields cannot change on a row, and neither can `audiences` and `client_id` on a row pinned by audience. A different value is a new row with a new `source_id`, because another organization's subjects could otherwise collide with the old ones and inherit their records. The one exception is a `pending_version` taking a row from `claim` to `audienceAndClaim`, so that a customer can add a second tenant. Every subject on such a row already came from that organization, so `source_id` stays.
- **Later list edits.** The pin is enforced from the row, so removing an entry leaves a row's pin, its login parameters, and its TXT re-read in place. Removing an entry therefore closes the list to new rows and leaves existing rows working, apart from tokens carrying an alias: an entry's aliases leave with it, so those tokens stop resolving, which can stop logins on a provider that returns the alias. An issuer that has been listed, with its aliases, goes on a stored marker that outlasts the entry, and a `helm rollback` does not clear it. A platform admin clears a marker through the admin API with a justification.
- **A row with no pin on a listed issuer.** Such a row would accept every customer's tokens from that issuer, so it has no path to a pin, which matches the owner's removal of migration. The configuration preflight refuses an entry for an issuer a row with no pin holds, so the operator retires that row first, and the tenant then activates a new pinned source, whose subjects are new users. If such a row meets an entry or a marker anyway, the snapshot excludes it at once, and in one transaction the row becomes `suspended` with reason `pin_required`, `tokens_not_before` is set, its SCIM credentials are revoked, and its playground records end. No list edit clears that state, and its one exit is retirement. A retired row with no pin cannot return while the entry or marker stands, and activation of a row with no pin is refused on such an issuer.
- **Index and activation.** The partial unique index covers `issuer`, `pin_audience`, `pin_claim`, and `pin_claim_value`, with an empty value treated as a value. A row's empty field places no condition on a token, so two rows overlap unless a field non-empty on both differs, and two claim values differ only when both rows name the same claim. The index does not see this. Every entry to `pending_effective` and every move to `active`, whether first activation, reactivation, a return from `suspended`, or a `pending_version` adding a pin field, therefore takes a per-issuer lock and refuses a row that overlaps another row in `pending_effective`, `active`, or `suspended`. A retired row holds only its exact values, so another tenant can activate an overlapping row with a platform admin's justification, and the retired row's return is then refused. A row with no pin overlaps every row on its issuer. The check reads through a dedicated function outside tenant context, as the snapshot's view does, and it answers only conflict or no conflict.
- **Proof.** The sign-in proof's verified token must carry the audience and claim value being claimed, or the proof fails, so a tenant cannot claim an organization without a login from it. The comparison is against the draft on a first activation, the stored pin on a reactivation or a return, and the pending value on a `pending_version`, and proofs 2, 3, and 4 apply to each. Proof 3 is read again when the change takes effect, so a domain that lapses during the delay stops it. Under `claimIsDomain`, proof 3 also covers the pin value, because any one employee could otherwise pass the sign-in proof and hold their company's value from a trial tenant. For the same reason, on any shared-issuer row proof 4 names the pin value and records that the organization's administrator asked for it, and `identity.allowTenantActivation` does not apply to a shared-issuer row with no domain proof, so such a row always takes an operator's activation.
- **A lapsed domain.** Google's `hd` stays the same when a domain changes hands, so a later owner of a defunct company's domain can [obtain tokens with the old value](https://trufflesecurity.com/blog/millions-at-risk-due-to-google-s-oauth-flaw) (vendor source). On a row with `pin_claim_is_domain`, a TXT record found missing at the daily re-read raises an alert, and after `identity.domainPinLapseDays`, default 7, the source becomes `suspended` and `tokens_not_before` is set. Lookups that keep failing raise the same alert and suspend after `identity.domainPinLookupFailureDays`, default 30, so a new owner cannot avoid the check by answering with errors. A sweep that finds at least 5 records and more than a tenth of the deployment's active domain pins missing at once raises a deployment-level hold and alert, and counts toward no row's bound, because that pattern is an operator's resolver fault. While the deployment-level hold stands, no domain-pinned row's lapse count advances. The hold ends at the next sweep below that threshold. A lapse is a sign that the proof may no longer stand, so every return of a domain-pinned row to `active`, whatever state it returns from, needs a new TXT check, a justification, and a sign-in by a subject that held a role row or security principal on that source before `pin_domain_unconfirmed_since`. That column stores the time of the first read that failed to confirm the record, whether missing or failed, ignoring reads during a hold, and a confirming read clears it. A row can move from `suspended` to `retired`, and retiring it does not relax this. A new owner's accounts have a different stable identifier and cannot pass. A tenant with no such subject uses a new source.
- **`require_directory_row`.** A source with SCIM can set this, `false` by default, to refuse a subject with no directory row, under registry step 7, with the read cached and failing closed. A resold domain's new accounts then get nothing, and neither does a user the customer has not provisioned.

No mechanical proof binds a customer to a hosted issuer, so the pin rests on proofs 2 and 3 together with proof 4. A disputed issuer is resolved by a `platform-admin` retiring the wrong row and deleting it, with an audit event, which releases the index. At a tenant with a `security-admin` row in any state, the delete takes [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s delay. If the tenant's own `security-admin` cancels the retirement, the operator invalidates that principal first, which applies at once, and then retires. "Residual risks" states this.

#### SSRF and NetworkPolicy

Every customer issuer, `jwks_uri`, `authorization_endpoint`, and `token_endpoint` passes one checker, shared with TS-4's `introspectionEndpoint` check. The deployment issuer is exempt, because an operator can run a broker in the cluster:

- The URL must be `https`, on port 443 unless the record's port is on a Helm allowlist, with no userinfo or fragment, and with no query except on `authorization_endpoint`, where some IdPs publish one.
- Each resolved address is refused when it falls in the §13.2.5 excluded ranges, in `127.0.0.0/8`, `::1/128`, `0.0.0.0/8`, or `100.64.0.0/10`, which that list omits and which NetworkPolicy does not cover for loopback, or in the cluster's own node and load-balancer addresses. An IPv4-mapped IPv6 address is normalized first.
- The dialer repeats that check on the address it connects to, so a name that re-resolves between check and dial is refused.
- Redirects are refused on every call the checker governs, including the token request, whose client follows them today. The transport ignores proxy environment variables. Responses are capped in size, and the key count is bounded.

The consequences in the chart are these:

- **Gateway.** Today `allow-gateway-egress-llm-upstream`, the NetworkPolicy that lets the gateway reach external LLM providers, is the gateway's only external HTTPS path, and it excludes private ranges (§13.2.4). Under decision 22 of [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/decisions.md#decisions) the gateway reaches no LLM provider, so that rule leaves, and the chart renders `allow-gateway-egress-issuers` in its place whenever `identity.customerSources.enabled` is true: HTTPS to the `0.0.0.0/0` peer with the private-range excepts, or to `identity.issuerCIDRs` alone when a strict deployer sets it. NetworkPolicy cannot match names, so a strict deployer maintains addresses per customer.
- **Token Service.** `allow-token-service`, the Token Service's NetworkPolicy, renders `kms.endpointCIDR` on TCP 443 unconditionally, which is open with no excepts under the local provider's default and closed to issuers once a cloud KMS narrows it. An except is an entry in a NetworkPolicy rule's `except` list, here the private ranges and the instance metadata address that an external HTTPS rule excludes. "Defects found while verifying" records this, and the Token Service should use `lenny.kmsEgressRule`, as the gateway does. That chart helper renders the KMS rule only for a cloud KMS, and it refuses an unrestricted CIDR. Without that change, the excepts of the rule below are void under the local provider, because NetworkPolicy allows are additive: the unrestricted port 443 rule already admits the addresses another rule excepts. Only the dialer's check would then hold. [`0127-egress-and-git`, "Credentials"](../0127-egress-and-git/change.md#credentials) adds a direct rule for provider APIs with the gateway's exclusions, and this design uses the same rule, which also widens the egress of the component that holds every provider credential. TS-6 renders the rule when [EG-1](../0127-egress-and-git/steps.md#steps), the egress design's git prerequisites, has not.
- **Private-address IdPs.** An issuer on a private address is refused in the first version. The issuer, `jwks_uri`, `authorization_endpoint`, and `token_endpoint` must all pass the checker, so publishing metadata alone is not enough, and that customer stays behind a broker that can reach its IdP or exposes those endpoints (decision 21).

#### Browser login (TS-6)

A browser login is part of the same boundary as the registry. The playground, the sign-in proof, and the link start page under [`0151-user-credential-delivery`, "Flow"](../0151-user-credential-delivery/change.md#flow) all use this path, and this design lands it in TS-6 because customers register these URIs at their IdPs and a later change forces them to register again.

1. **One resolver.** The registry exposes one function that takes a source and an ID token and returns the tenant and canonical subject, applying registry step 5, the allowlist, the role boundary, `deploymentIssuerAllowed`, the active-source check, and `require_directory_row`. On a shared issuer it refuses unless the row the token selects is the callback's source, and the proof purpose compares the token against the values "Proof" names instead. `extractSubject`'s read of raw claims goes away, so a bare playground login with `tenant_id: acme` on a broker token gets `TENANT_ISSUER_MISMATCH`. The proof purpose is exempt from the active-source check, since it runs on a row that is not yet active, on a draft, a return, or a pending version, and it creates no session.
2. **One redirect URI per source.** Each source has `/auth/callback/{source_id}`, and the deployment source has `/auth/callback/deployment`. `state` names the purpose, so one URI serves every use.
3. **Refusal before any token request.** The state cookie is scoped to that callback's path, with a short lifetime as today. The callback refuses when the cookie is absent, when `state` does not match, or when the state's source differs from the path's source, and none of these sends the authorization code or the PKCE code verifier anywhere. A hostile source that bounces a browser to another IdP therefore delivers the code to the other source's callback, where no state cookie exists.
4. **RFC 9207.** When the response carries `iss`, it must equal the source's issuer or one of its entry's `issuerAliases`. It is not required, because IdPs differ.
5. **Exchange, then resolve.** The authorization code and the PKCE code verifier go only to the source's recorded `token_endpoint`, directly or through the Token Service when the source has a secret. The ID token and nonce then go through the resolver.
6. **Cookies.** The state cookie is scoped per source, as above. The playground session cookie is scoped per tenant in TS-7, by path under `/t/{tenantId}/playground/`, with the mint moved under that prefix, because a browser does not send a cookie scoped to `/playground/` to `/v1/playground/token`. A silent login at a hostile source, one the IdP completes with no user interaction because the browser already has a session there, then cannot replace a session on another tenant.

How each provider behaves on these flows is untested, including silent single sign-on and RFC 9207 support. Which spelling of Google's issuer a given flow returns is also untested, and `issuerAliases` admits both.

#### Login routing (TS-7)

Only the deployment source can use the bare URLs, because nothing else identifies a tenant before a token exists.

| Client | How the tenant is known | Behaviour |
| :-- | :-- | :-- |
| MCP client | A per-tenant resource URL, `/t/{tenantId}/mcp` and `/t/{tenantId}/mcp/environments/{name}` | A 401 names the metadata at `/.well-known/oauth-protected-resource/t/{tenantId}/mcp`, which lists that tenant's active issuers in `authorization_servers`. Bare `/mcp` names the deployment issuer alone. |
| REST client | The same prefix, or none, since the bearer identifies the tenant | A token from a customer source also works on the bare path. Under `/t/{tenantId}`, a token that resolves to another tenant gets `403 TENANT_PATH_MISMATCH`. |
| Playground | `/t/{tenantId}/playground`, or an email domain typed on the shared page when the source has verified domains | Login follows "Browser login". A tenant with several sources gets a chooser. |
| `lenny-ctl` | `--token` or `LENNY_API_TOKEN`, as today. It has no login command. | Unchanged. A customer's administrator supplies a bearer from its own tooling. |
| Link start page ([`0151-user-credential-delivery`, "Flow"](../0151-user-credential-delivery/change.md#flow)) | The flow's tenant | Logs in through that tenant's source and "Browser login", in place of `auth.oidc.issuerUrl` alone. |

RFC 9728 metadata names the deployment issuer for the deployment resource, and per-tenant documents name only that tenant's issuers (decision 20). One shared document listing all issuers would disclose every customer, and [the MCP specification leaves selection to the client](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). The per-tenant document is public, so it discloses a tenant identifier and its IdP host to anyone who guesses the identifier, as the [egress design](../0127-egress-and-git/change.md)'s `/oidc/<tenant-id>` path already does for its identifier. The specification also says a client without dynamic client registration, the OAuth mechanism through which a client registers itself at an authorization server, needs a client ID by hand, so a customer IdP lacking that feature needs one configured in each MCP client. The audience check that MCP requires of `/mcp` applies to each per-tenant resource URL as "Discovery" states. How MCP clients behave against these documents is unproven.

#### Several IdPs in one tenant, and namespacing

A customer source's user key is the canonical subject `~<source_id>~<value of subject_claim>`. `subjectPattern` in `userstore` (`pkg/tenancy/userstore`) already admits `~` and limits a subject to 256 printable characters, and a longer result is refused at the boundary. A deployment source's `sub` keeps its form, so a single-company deployment and every tenant that never moves are unchanged. Once customer sources are enabled, a deployment token whose `sub` begins with `~` is refused, and a deployment group beginning with `~` is dropped, so no presented value can collide. `(tenant_id, subject)` stays the user key throughout.

Groups follow the same form, `~<source_id>~<group>`, because `oidc-group` is a bare string match and two IdPs could both assert `security-engineers`. TS-6 fixes this form, since environment members store it. Under `group_source: scim`, `<group>` is `displayName`, which SCIM holds unique per source. A rename changes the string, so its members stop matching, which fails closed, and posture lists the environment members with no group. An environment member names that string, and the admin API accepts it verbatim. A deployment source's groups keep their form. Two subjects from two sources in one tenant are two users, and Lenny has no account linking between them.

The `~<source_id>~` prefix in `user_id` names which issuer vouched, so §11.7 events and evidence need no new field for attribution. A deployment subject carries no prefix, which names the deployment issuer.

**Caller-type namespaces.** Under [`0143-service-account-credentials`, "SA-6 Subject namespaces"](../0143-service-account-credentials/change.md#sa-6-subject-namespaces), the user key also names the caller type. A token whose `caller_type` is `service` takes the Lenny subject `~svc~<canonical subject>`, one whose `caller_type` is `agent` takes `~agt~<canonical subject>`, and a person keeps the canonical subject, so a person and a service account whose canonical subjects are equal hold two users. The one resolver of "Verifier registry" and the deployment issuer's path form the Lenny subject after the claim allowlist sets `caller_type`, and they refuse a token whose `caller_type` is `human` and whose canonical subject begins with `~svc~` or `~agt~` with `401 SUBJECT_RESERVED` and an `auth_failure` event naming the reason, on the gateway, on `lenny-ops`, and on the Token Service. A customer source's canonical subject begins with `~<source_id>~`, and no `source_id` is `svc` or `agt`, so the refusal reaches only a deployment `sub` beginning with `~`, which this section already refuses once customer sources are enabled. Every Lenny-issued token carries a `user_id` and a `caller_type` that agree, and a verifier refuses one that does not. The writes that first name a subject check its prefix: the SCIM server of TS-8 provisions persons and refuses a reserved prefix with `400`, the TS-4 lifecycle calls and role assignment through `/v1/admin/users` take the Lenny subject in any namespace, and `lifecycleSubjects` and a VCS pool's `serviceIdentities` take only `~svc~` subjects. That rule and the `scim:<source_id>` entry the SCIM deprovisioning table under TS-8 requires in `lifecycleSubjects` disagree, and decision 33 in `decisions.md` holds the question open. Ownership, derive, invalidation, erasure, and role rows key on the Lenny subject, so none of them joins a person with a service account. `userstore`'s 256-character limit applies to the prefixed subject. No deployment runs outside development, so no stored subject is migrated, and a person whose deployment `sub` begins with a reserved prefix is refused until the issuer emits another `sub` for that person.

#### Role boundary

§10.2 **Role assignment:** allows an OIDC claim to carry any built-in role. In code, an IdP-verified token's `roles` reach `Principal.Roles` unchanged, and `platform-admin` then spans all tenants. TS-2 closes this for every issuer, and TS-6 extends it. The boundary applies to every platform role, `platform-admin` and the `platform-forensics` role of [`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md) FE-0 alike, and to any later built-in role whose authority spans tenants, so the bullets below that name `platform-admin` hold for each such role:

- The IdP boundary, beside `normalizeUserBearer`, removes every platform role from an IdP-verified token's roles on the gateway and on the Token Service. The request continues with the remaining roles. Each removal emits an `auth.platform_role_dropped` audit event and a counter with an alert.
- A customer source goes further, because only values `role_map` names become roles, and that map cannot name a platform role. A customer's IdP therefore has no way to express one.
- `platform-admin` comes from a platform-managed role row, a Lenny-issued token, or a §25.4 service identity. `/v1/admin/users` already allows a `platform-admin` to grant that role, and §15.1 must list that surface, which it omits today.
- **Operators' staff.** `auth.platformAdminTenant` names one operator tenant, and rows of a platform role exist only there, on every write path: `POST` and `PUT /v1/admin/users`, and the bootstrap seed, with `tenant_user_roles.go` already refusing the role. The role resolver ignores such a row elsewhere, and chart validation requires `gateway.adminToken.tenant` to match. `auth.platformAdminTenant` defaults to the value of `gateway.adminToken.tenant`, which is `default` in `values.yaml`, so an install that sets neither has `default` as its operator tenant. A single-tenant install (`auth.multiTenant: false`) has one tenant, which is the operator tenant. The chart refuses `auth.platformAdminTenant: platform` at render time, with a message stating that [§10.2](../../spec/10_gateway-internals.md#102-authentication) **`tenant_id` format validation.** reserves the tenant ID `platform` for the platform tenant, under which the platform audit chain is written (decision 27). The admin API and the bootstrap seed already refuse to create a tenant with that ID, so the refusal stops an install whose operator tenant could never exist. Staff log in through whichever issuer authenticates that tenant. The broker contract requires that tenant's IdP link to be operator-only.
- **What this does and does not stop.** A customer's IdP can never reach platform authority, on either kind of source. The issuer of the operator tenant can, by asserting a staff `sub`. With the default, a broker compromise reaches platform authority and therefore every tenant, including pinned ones through impersonation. The operator tenant can hold a customer source naming the operator's own IdP, which takes the broker out of that path (decision 24). On a deployment with more than one tenant, preflight and the operator tenant's posture read warn while that tenant's `deploymentIssuerAllowed` is true.
- The specification and the code agree on claim names (decision 10).

**How the tenant-claim risk changes.** For a tenant on the deployment source, the risk is as it was: a broker fault or compromise can issue a token for that tenant. For a tenant on a customer source, the tenant comes from the pin and the check in registry step 5 refuses the deployment issuer, so the broker cannot reach it, and the customer's IdP can reach only its own tenant. A broker and a pinned issuer therefore coexist without either speaking for the other's tenants at the token boundary. On a listed shared issuer, a customer's administrator still reaches only its own tenant while the entry's assertion holds, and a fault at the provider reaches every tenant on that issuer. This does not remove the operator from the pinned tenant's trust. A `platform-admin` retains impersonation and can repoint a source, both audited, and the second takes the delay at a tenant with a `security-admin` row in any state.

**An issuer's power over its principals.** An issuer controls every principal it authenticates. It can assert the subject of a `tenant-admin` or a security principal, and it chooses the `iat` value read by [SP1](../0142-security-oversight/change.md#security-properties), the security oversight property under which a security principal row grants its role only on a bearer issued after the row took effect, and the row then grants the role, whatever `securityRoleSource` says. `securityRoleSource: managed` stops a role claim, and it does not separate a principal from its issuer. On a tenant on the deployment source, an operator's broker can therefore assert a `security-approver`'s `sub` and approve the operator's own request. Posture reports each principal's issuer. A tenant that needs separation from its operator moves to a customer source, and decision 25 leaves a second factor out of the first version.

#### Broker contract

These go into §10.2 as requirements on the issuer named by `auth.oidc.issuerUrl`, and they are the contract for the default source.

| Claim | What Lenny does | Requirement on the broker |
| :-- | :-- | :-- |
| `iss`, `aud`, `exp`, `nbf` | Verified against `auth.oidc.issuerUrl`, and `aud` against `auth.oidc.clientId` or a computed adapter identifier ("Discovery") | One issuer for all tenants on this source, and the client API's audience or an adapter identifier as each client requests |
| Tenant claim (`auth.tenantIdClaim`) | Read as a string. Refused when absent, malformed, unregistered, or naming a tenant that does not allow this issuer. | Set from the broker's organization record. Never derived from a user attribute or a claim a customer can write. A nested claim needs a mapper to a string. |
| `sub` | The user key within a tenant, and session owner | Stable, never reassigned, unique within a tenant across all of that customer's IdPs, and not beginning with `~` |
| `roles` | An array of role names | Tenant-scoped roles only. A customer's own mapping must not reach it unfiltered. |
| `groups` | An array matched exactly against `oidc-group` members | Stable names, namespaced when a tenant has several IdPs. A complete list or none: Entra [limits a JWT to 200 groups](https://docs.azure.cn/en-us/entra/identity/users/directory-service-limits-restrictions) (provider documentation), and past that a broker must resolve the set itself. An absent claim reads as no groups, so the failure is a refused environment. |

The broker must also keep token lifetimes short enough for the operator's offboarding bound, and keep the operator tenant's IdP link operator-only. It delivers lifecycle events through a sync worker, or the customer's directory calls Lenny's SCIM directly.

#### Discovery

§10.2 calls the gateway an MCP-standard protected resource server. Under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), Lenny serves a REST client API alone, and the MCP endpoint at `/mcp` and `/t/{tenantId}/mcp` is served by the MCP adapter on the gateway's origin, as one interface of a protected resource whose other interface is the client API. [The MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), at the `2026-07-28` version that [`0134-mcp-protocol-upgrade`, "MP-1 Gateway versions and negotiation"](../0134-mcp-protocol-upgrade/change.md#mp-1-gateway-versions-and-negotiation) adopts, requires such a server to serve RFC 9728 metadata, to answer an invalid token with HTTP 401 and a `WWW-Authenticate` challenge that names the metadata's location, and to accept only tokens issued for it as the audience. No route, handler, or specification text in the tree serves the metadata or the challenge, so a client learns the issuer out of band. TS-2 adds `/.well-known/oauth-protected-resource`, naming `auth.oidc.issuerUrl`, and the client API's challenge header. TS-7 adds the per-tenant documents.

**Adapter identifiers.** The gateway computes the deployment's protected resource identifiers from the operator's adapter registry, which [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md) defines with its fields, its narrowing, and its refusals (["RO-4"](../0138-rest-only-client-api/change.md#ro-4-authorization-of-adapter-requests) and [R9](../0138-rest-only-client-api/change.md#ro-2-rest-additions)). Each registered adapter path `p` gives the identifier `https://<host><p>` and, under login routing, `https://<host>/t/{tenantId}<p>`. The gateway serves the RFC 9728 document of each identifier at its path-inserted well-known URL, naming the issuers that "Login routing (TS-7)" names for the bare and the per-tenant form, and the adapter writes the challenge that names that document. The client API accepts an adapter identifier as an audience only on a narrowed request under ["RO-4"](../0138-rest-only-client-api/change.md#ro-4-authorization-of-adapter-requests), and the gateway refuses a tenant's write of `audiences` or `pin_audience` that names a deployment-wide identifier or another tenant's identifier, as [R9](../0138-rest-only-client-api/change.md#ro-2-rest-additions) states. This design keeps no list of adapters of its own.

**Audience check.** The verifier registry holds one audience rule for the client API, whichever interface a token reaches it through. A token from the deployment source must carry in `aud` either `auth.oidc.clientId`, the client API's own audience, or one of the computed adapter identifiers (registry step 4 and the broker contract). A token from a customer source must carry a value in the source's `audiences`, with the `azp` rule (registry steps 4 and 5), and a customer that uses an adapter lists the adapter's per-tenant identifier there. A token issued for any other audience is refused with `401 TOKEN_INVALID` and the challenge header. A token whose audience is an adapter identifier carries the authority that the adapter registry of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md) gives that adapter, and that design states which tenant a per-tenant identifier admits. This replaces the rule of revision 37, which required `auth.oidc.clientId` in `aud` on `/mcp`: an MCP client names the MCP adapter's identifier in its RFC 8707 `resource` parameter, so its token carries that identifier as its audience. Whether a token that an MCP client obtains through its own login carries that audience at each IdP is unproven, as **Unproven.** under "Residual risks" states.

#### SCIM server (TS-8)

The server implements RFC 7643 and RFC 7644 at `/scim/v2/{tenantId}/{sourceName}`, on the gateway's ingress behind its own middleware rather than the OIDC chain. A tenant on the deployment source uses the source name `deployment`.

| Surface | First version |
| :-- | :-- |
| Discovery | `ServiceProviderConfig`, `ResourceTypes`, and `Schemas`, stating what is absent |
| Users | `GET` by `id`, list with pagination, `POST`, `PUT`, `PATCH`, and `DELETE`. Core user schema. Extension fields are dropped and not stored. `externalId` cannot change after provisioning. |
| Groups | The same methods, with `PATCH` add and remove on `members`, and `excludedAttributes=members`. `displayName` is unique per source. |
| Filters | `eq` on `userName`, `externalId`, `id`, and `displayName`. Any other filter answers `400 invalidFilter`. |
| `PATCH` | Both the `path: active` form and the pathless `value` form. Vendor blogs report that [identity providers differ on this](https://ssojet.com/blog/okta-scim-provisioning-saas-vendors) (vendor source), and Okta's own documentation was not retrieved. |
| Absent | Bulk, sort, ETags, `/Me`, and password changes |

These follow what [Microsoft's tutorial](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups) lists for its service (provider documentation): queries by `userName` and `externalId`, groups by `displayName`, `excludedAttributes=members`, and a soft-deleted user still returned with `active=false`.

**Credentials.** A credential is a random 256-bit bearer, bound to one tenant and one source, stored only as a keyed hash, shown once, and rotated with an overlap. A `platform-admin`, a `tenant-admin`, or a `security-admin` mints one, because the directory is the customer's. A custom role that holds `manage_user_lifecycle`, such as `identity-sync`, does not, so a sync worker cannot mint a credential, as "Who can do what (identity)" states. It authenticates only on `/scim/v2/{tenantId}/{sourceName}`, where its `active` and `DELETE` writes reach the invalidation and reinstatement code of TS-4 for its own class and its other writes reach the directory tables. No admin API route accepts it, including `invalidate` and `reinstate`. Its audit subject is `scim:<source_id>`. Disallowing the deployment issuer disables a `deployment` credential.

**Quotas.** Per source, Helm values cap credentials, users, groups, and memberships per user. Requests are rate limited per tenant, and failed authentication per source address, since an invalid bearer has no credential to count against. The body limit is 1 MiB, invalidations are coalesced, and the group cache is bounded per tenant.

**Matching a directory user to a token.** SCIM carries no OIDC subject, so a source names `match_claim`, a claim the source declares immutable and verified, whose value must equal the directory's `externalId`. A declaration is a change on the source, under the activation rule. `userName` and `preferred_username` never bind, because a user may be able to edit them and Microsoft warns that they change.

- On a customer source, `match_claim` is `subject_claim`, so the canonical subject is computed at provisioning. `externalId` is unique per source. An Entra source maps `objectId` to `externalId` and sets `subject_claim: oid`, since Microsoft's default user mapping uses `mailNickname` and `sub` is pairwise.
- On the deployment source, a broker issues its own `sub`, so the directory row stays unbound until a token's `match_claim` equals `externalId`, and it then binds once. Every IdP token from a deployment source with a settings row is checked against the directory, with the read cached, whether or not a user row exists. A match on an inactive row refuses the login and places a hold on that subject under the `lifecycleSubjects` rule, so a security principal is protected as it is on a direct write. A deployment `externalId` beginning with `~` is refused.
- `active: false` on an unbound row has no subject to hold. The SCIM response reports it, and an alert fires. "Residual risks" states what this leaves running.
- Posture reports provisioned rows that never matched a login, and logins with no directory row, because a wrong mapping otherwise deactivates a subject nobody uses while the intended user stays active.

**Deprovisioning into TS-4.**

| SCIM operation | Effect |
| :-- | :-- |
| `active: false` | A hold of this source's class at `scim_deactivate_mode`, `full_revoke` by default (decision 11), through the same code as `POST .../invalidate`, at server time |
| `DELETE /Users/{id}` | The same hold, and the directory row goes. The user row stays held. It is not an erasure, which keeps §12.8's job path. |
| `active: true` | Clears this source's hold alone. Any other class's hold stays, and the response reports `active: false`. |
| Any write on a subject with a completed erasure job | `409` |
| A lifecycle write on a security principal | Refused per user with `403` unless `scim:<source_id>` is in the `lifecycleSubjects` list of the [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture) tenant security record, and posture reports it. Which entries that list accepts is open as decision 33. A group write is not a lifecycle write. |
| Provisioning a user | A `users` row with no role and `RoleAssigned` false, written by its own path, because `handleCreateUser` sets it and would blank the user's token roles. No session, role, or environment follows from it. Decision 13's rule on login rows is unchanged. |

A store failure answers `503` with `Retry-After`. Microsoft's service [retries and eventually quarantines a failing job](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/how-provisioning-works) (provider documentation), so a user stays active during an outage, which "Residual risks" states.

**Conformance.** The test corpus is a set of recorded and hand-written request sequences per directory, because no live directory is available to the suite. Passing it shows agreement with the corpus and no more, and each directory's own validator is a manual step per release. No directory has been tried.

#### Directory groups (TS-9)

`directory_users` holds `tenant_id`, `source_id`, the SCIM `id`, `external_id`, `user_name`, `active`, and the bound subject, if any. `directory_groups` holds the SCIM `id`, `external_id`, and `display_name`, and `directory_group_members` joins them. All are tenant-scoped under row-level security.

`group_source` on the source selects where a user's groups come from, and the two never merge (decision 19):

- **`token`**, the default, keeps today's behaviour.
- **`scim`** makes the auth middleware replace `Principal.Groups` from `directory_group_members`, at the same point introspection replaces them today, for IdP tokens and Lenny-issued tokens alike. SCIM provisions persons alone, so what a `service` or `agent` caller of such a source receives is open as decision 37 in `decisions.md`.

A tenant with a customer source refuses `introspectionEnabled` on every source kind, because a tenant-set endpoint would receive every bearer presented for the tenant. Activation refuses while it is on. A deployment-source tenant is left to [`0142-security-oversight` decision 23](../0142-security-oversight/decisions.md#decisions).

`envaccess` (`pkg/tenancy/envaccess`), the environment membership resolver, keeps its `Caller` input, so `Membership` and `AuthorizedRuntimes` are unchanged, and the new reader sits ahead of it. The read is cached for 30 seconds, a SCIM write invalidates it through Redis, and a store failure answers `503`, as `GROUP_INTROSPECTION_UNAVAILABLE` does. `GET /v1/admin/environments/{name}/access-report`, which §15.1 describes as a resolved member list with group expansion, can read these tables for a source with `group_source: scim` and can do no such expansion for a source with `group_source: token`.

**Erasure and classification.** §12.9 adds directory users, groups, and memberships to the Confidential class beside user identifiers, source records to the Confidential class, and SCIM credential hashes and the stored client secret to the Secret class. `DeleteByUser` removes the directory row, the memberships, and any proof preview naming that subject, and `DeleteByTenant` removes all of them. An unbound directory row has no subject to find, so an erasure job addresses it by SCIM `id`. §12.8's tombstone refuses re-provisioning an erased subject, with the `409` above. Group display names can carry personal or organizational data, so they are Confidential as well.

#### When SCIM and token claims disagree

| Disagreement | Which wins | Reason |
| :-- | :-- | :-- |
| A valid token, and SCIM has deactivated the user | SCIM | TS-4's refusal at authentication reads the row on every bearer, so a token's remaining lifetime grants nothing at `full_revoke`. |
| A stale `groups` claim, with `group_source: scim` | SCIM | The claim is ignored. |
| A `groups` claim, with `group_source: token`, and SCIM holds different groups | The token | The source said so. Posture reports a tenant whose SCIM groups are stored and unused, because this is the likely misconfiguration. |
| SCIM says active, and the IdP refuses login | The IdP | No token exists, so nothing reaches Lenny. |
| SCIM says `active: true`, and an administrator holds the user | The administrator | SCIM clears only its own hold. |
| A role in a token and a platform-managed row | The row | §10.2's precedence. SCIM carries no roles in the first version. |

For the TS-1 rules:

- Explicit environment admission and the TS-3 transparent `creator` check use the groups the table above resolves.
- `ENVIRONMENT_REQUIRED` reads the tenant's environments and no groups, so neither source can change its answer.
- A running session keeps E, and `visible`, the delegation gate, and `ENVIRONMENT_POLICY_NOT_ENFORCEABLE` read E alone, so a SCIM group removal does not reach a running session. Only a lifecycle event does, under TS-4's levels.
- A Lenny-issued token carries groups copied at exchange under TS-3, and under `group_source: scim` they are replaced at each request, so they cannot outlive a removal. Under `group_source: token`, they last until that token's expiry.

#### User lifecycle (TS-4)

A directory reaches Lenny either directly through the SCIM server or through a broker or vendor endpoint and a sync worker that calls the routes below. Both end in the same invalidation code. Today that code fails in these ways:

- `POST /v1/admin/users/{userId}/invalidate` answers `404` when the user has no row. Rows come only from the admin API, so a user who only ever logged in through an IdP cannot be invalidated, and that user's sessions keep running.
- `requireActiveUserForAction` admits a user with no row, so an absent row also means no gate on a fresh token.
- `hard_disable` and `full_revoke` set `DeletedAt`, and no endpoint clears it, so a returning employee cannot be reinstated. Entra [reactivates users that move from soft-deleted to active](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/how-provisioning-works) (provider documentation).
- Invalidation needs `manage_users`, which also assigns roles. A worker holding it has more authority than deprovisioning requires.
- Invalidation does not stop an administrator. `serveBearer` never reads `IsActive`, `PlatformRoles.ResolveRoles` ignores `Disabled` and `DeletedAt`, and the only callers of `user.IsActive` guard session creation, interaction resolution, and elicitation. An invalidated `tenant-admin` holding a live IdP token keeps the admin API.

TS-4 makes these changes:

- **Upsert on invalidate.** Invalidating an unknown subject creates its row in the invalidated state and runs the §11.4 steps, which list sessions by owner and do not depend on the row having existed.
- **Refusal at authentication.** The row lookup the middleware already performs for `PlatformRoles` also reads the invalidation state, so this adds no read. A `full_revoke` row refuses every bearer with `403 USER_INVALIDATED`, the status §15.1's **Error code catalog** and the §12.8 creation fence already give the code, on the gateway, on `lenny-ops`, and for a caller credential at `/v1/oauth/token`, so the code has one status and a client does not retry it as a request to re-authenticate. On the gateway this adds no read. The Token Service has no user store today, so it gains a read of the user row through the Postgres connection pooler. A `soft_disable` or `hard_disable` row keeps the §11.4 session behaviour and reduces the principal's roles to `user`, so no disabled user holds admin authority. The reduction runs after every role resolver, so it also removes the `security-*` roles that the resolver of [`0142-security-oversight`, SO-1](../0142-security-oversight/change.md#so-1-security-roles) adds from `tenant_security_principals`, and a principal with any hold does not count as active for an approval or a cancellation.
- **Holds per caller class.** The user row gains a `holds` column, one entry per class: `admin`, `sync`, and `scim:<source_id>`, each with its mode and stored time. The effective mode is the highest remaining, and a user is active only when no entry with a mode remains. `reinstate` leaves its class's entry in place as a tombstone with mode `none` and the stored time, so a retried older invalidation of that class still compares against it and answers `applied: false`. `holds` is the single source of the invalidation level: `Disabled` and the invalidation use of `DeletedAt` are derived from it, `DeletedAt` otherwise marks a row removed through `DELETE` alone, and `IsActive`, `PlatformRoles`, and the §12.8 creation fence's user marker read the effective mode. Every write of a hold takes the exclusive lock on the user row that §12.8 **Lifecycle fence and drain** requires of a marker write, so a create racing a hold sees either the hold or no hold. A caller holding `manage_users` or `security-admin` is `admin`, and any other caller with `manage_user_lifecycle` is `sync`. `invalidate` writes its caller's class, and `reinstate` clears only that class, so a directory or a stolen worker credential cannot erase an incident hold. An `admin` caller can name other classes to clear. This is a stored format, and it lands in TS-4 because TS-8 reads it.
- **Deleted rows and store errors.** A `DELETE`d row is refused as a `full_revoke` row is, because `SoftDelete` sets `DeletedAt` and leaves `RoleAssigned` and `Roles` in place, so a deleted administrator keeps its role today. A store error fails closed on the gateway and the Token Service. `lenny-ops` deliberately authorizes on the token's roles when the lookup fails (`claimOnLookupError`, §25.4), and this design leaves that as written, so a Postgres outage suspends the refusal on `lenny-ops` alone. A §25.4 service identity is unaffected, which keeps a recovery path. Whether a `DELETE`d subject can ever return, and through which route, is open as decision 35 in `decisions.md`.
- **Impersonation bearers.** `soft_disable` and `hard_disable` run the §13.3 **Platform-admin impersonation** rule 6 cascade, which revokes the impersonation bearers the user started and runs on `full_revoke` alone today, so a disabled user's bearers do not outlive its authority. A caller without `platform-admin` gets the existing skipped report.
- **Reinstate.** `POST /v1/admin/users/{userId}/reinstate` clears a hold and restores nothing else. It refuses a user under an §12.8 erasure, it does not revive a row removed through `DELETE`, and it refuses a caller reinstating itself with `403`. It is the only way back: `PUT /v1/admin/users/{userId}` refuses `disabled: false` on an invalidated row, where it would otherwise skip the self-reinstatement and ordering rules, and the bootstrap seed's force update refuses to reverse a disable. Upserts for unknown subjects are capped per tenant and per caller class: the `sync` class and each `scim:<source_id>` class count the rows their upserts created that still exist, against `identity.userUpsertLimitPerClass`, and a call past the cap answers `429 QUOTA_EXCEEDED` with `details.quota: userUpserts` and creates no row. The `admin` class is not capped, so a stolen sync or SCIM credential cannot use up the allowance that an incident response needs. The alert `UserUpsertCapNear` fires when a class reaches 80% of the cap. A self-reinstatement answers `403 FORBIDDEN` with `details.reason: self_reinstatement`.
- **Ordering.** Both calls accept `observedAt`, and the hold stores min(`observedAt`, server time). A future stamp, whether malicious or from a fast worker clock, therefore cannot make a later call stale, and an emergency call at server time always applies. An absent value takes the server's time. A call whose value is older than its class's stored time answers `200` with `applied: false`, so a retried event cannot reverse a later one, and on a tie an invalidation wins. Both calls are idempotent.
- **Permission.** A new `manage_user_lifecycle` permission covers these calls alone. `tenant-admin` holds it, and a custom role can hold it alone, such as `identity-sync`. A worker authenticates per tenant, through the client credentials path of §10.2, with that role, and `service_claim` or `auth.serviceClaim` marks it as a service. A SCIM credential reaches the same invalidation and reinstatement code for its own class only through SCIM `active` and `DELETE` writes on `/scim/v2/{tenantId}/{sourceName}`, and it authenticates on no other route, including `POST /v1/admin/users/{userId}/invalidate` and `/reinstate`.
- **`identityProvider` hardening.** `GET rbac-config` stops returning `introspectionClientSecret`. The write validator and the client refuse an `introspectionEndpoint` that resolves to the §13.2.5 excluded ranges, through the shared checker. The handler checks only for HTTPS and a host today, and the client uses a default dialer, while the gateway posts bearers to that URL.

**User credentials and links.** A session's `caller_type` now sits on its row, and a delegated child copies its parent's value. A read of that row releases only the token of the principal it names, from a row whose principal type equals that `caller_type`: a person's token to her sessions, a service account's token to that service account's sessions under [`0143-service-account-credentials`, "SA-1 Principal-owned credentials"](../0143-service-account-credentials/change.md#sa-1-principal-owned-credentials), and nothing to an `agent` caller. The invalidation levels below apply to a service account's subject as to a person's, and stop its principal-owned releases. Each of `soft_disable`, `hard_disable`, and `full_revoke` stops a user's `userCredential` releases, through `pkg/binding`'s invalidation level, and it revokes `oauth2Link` tokens at the provider, under [`0151-user-credential-delivery`, "Lifecycle and revocation at the provider"](../0151-user-credential-delivery/change.md#lifecycle-and-revocation-at-the-provider). A `registered` token stays valid at its provider, because Lenny cannot revoke it, and the tenant is told. Reinstate restores neither. A subject with an invalidation level or a GDPR Article 18 restriction, which §12.8 sets on a user under erasure, cannot be written to through `PUT /v1/admin/users/{userId}/credentials/{type}`. `identityBinding: claim` adds a provider identity claim to the broker contract or to a customer source's mapping. An issuer that cannot supply it uses `identityBinding: directory`, under which a sync worker or an admin writes each user's expected provider account, and that write sits under `manage_user_lifecycle`, so the sync worker can hold it. A SCIM credential does not hold that write in the first version.

When a worker or a directory cannot reach Lenny, the event waits with it, and a user stays active until delivery succeeds. A partial failure reported in the invalidate response is retried, as the idempotent call allows. For a caller without `platform-admin`, §11.4 step 5 reports the impersonation cascade as skipped, which is correct for a customer user, and the operator invalidates its own staff with a `platform-admin` caller.

Offboarding latency is the directory's delivery time, plus the sync worker's on that path. Microsoft documents incremental cycles [at intervals defined per application](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/how-provisioning-works) (provider documentation), with no general figure on that page. Until delivery, a user can create sessions while a token is valid. Lenny-issued tokens default to 900 seconds and are capped at 24 hours for `lenny-gateway` (§13.3 **`exp` granularity and parent-expiry handling.**), and a running session does not depend on its creator's token, so only invalidation ends it.

#### What stays with an operator's portal

Lenny supplies admin APIs and no customer-facing identity UI, which §10.2 lists as a future goal. These remain the operator's: the page where a customer enters issuer details, instructions for registering an application at each IdP and for publishing the DNS record, sign-up and contract records behind the request, SAML bridging through a broker, support for a customer's IdP misconfiguration, and any directory connection other than SCIM.

### Label rules (TS-10)

The owner settled this as decision 45 on 2026-11-23, from the review of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md) and [`0170-budgets`](../0170-budgets/change.md) **[design]**. A session's `labels` are set by the root's client at the root's creation and inherited unchanged by every descendant ([`0166-delegation-primitives`, "DP-2"](../0166-delegation-primitives/change.md#dp-2-parent-link), decision 44). Label rules decide who may set a label key and value, so a label can stand for a team, a project, or a cost center that a budget of 0170, a usage report, or a deployer's cost matching reads.

**Free and governed keys.** A key that no rule names is free: any client may set it to any value or omit it, as today. A key that a rule names is governed: a session may carry it only when a rule allows the key and the value for the session's owner. A session creation that sets a governed key with a value no rule allows for its owner, or omits a key that a rule requires, is refused with `403 LABEL_NOT_PERMITTED`, whose details name the key and no rule.

**Where rules live.**

- A tenant's rules apply to every session of the tenant. A `tenant-admin` reads and writes them with `GET` and `PUT /v1/admin/label-rules`, under `If-Match`.
- An environment may add rules, written on the environment resource as `labelRules` by whoever administers the environment (TS-1, and TS-5 when it lands). A session in the environment must satisfy the tenant's rules and the environment's. An environment's rules may govern a free key of the tenant or narrow a governed one, and they never widen what the tenant's rules allow.
- A `platform-admin` reserves key prefixes in `labels.reservedPrefixes` (default `[lenny.dev/]`). No client may set a key under a reserved prefix, and no tenant rule may govern one.

**What a rule says.** A rule names `key`, an exact key or a pattern with `*`, and any of these:

| Field | Meaning |
| :-- | :-- |
| `values` | The values the key may take, each exact or with `*`. Without `allow` or `valueFrom`, any owner may set any of them, so the rule validates the value alone. |
| `allow` | Who may set the key: `principals`, `groups` (the owner's directory groups at creation, TS-9), `principalKinds` (`user` or `serviceAccount`), and `environments`. An entry may carry its own `values`, so one rule gives each team its own values. |
| `valueFrom` | The value must come from the owner's identity: `group`, with `match`, `value`, and an optional `source`; `principal`, the owner's subject; or `environment`, the session's environment. A rule with `valueFrom` admits any owner whose identity yields the value. `match` is an RE2 regular expression of at most 256 characters that must match the whole group name as Lenny stores it, `~<source_id>~<group>` for a customer source under "Several IdPs in one tenant, and namespacing", so a group of another source or a group that merely contains the pattern yields nothing. `source` limits the match to the groups of one identity source. `value` takes capture groups in the `${1}` form alone. The admin API refuses a `match` that does not compile or exceeds the length, and a `value` in another form, with `400 VALIDATION_ERROR`, and a session whose `match` yields an empty value or one that fails the syntax of a label value is refused with `403 LABEL_NOT_PERMITTED`. |
| `required` | The key must be set, optionally only in the listed `environments`. |

```yaml
labelRules:
  - key: team
    valueFrom: { group: { source: corp, match: "~corp~team-(.+)", value: "${1}" } }   # group team-payments of source corp sets team: payments
  - key: costCenter
    values: ["CC-100", "CC-2*"]
    required: true
    environments: [prod]
  - key: pipeline
    allow: { principalKinds: [serviceAccount] }
  - key: project
    allow:
      - { values: ["checkout"], groups: [checkout-eng] }
      - { values: ["search"], groups: [search-eng, search-contractors] }
```

**When rules apply.** The gateway checks the rules once, at a root's creation, against the owner, the owner's groups, and the environment the session gets, before the `PreRoute` chain. A child inherits its root's labels and is not checked again in its parent's environment. A child that crosses into another environment under TS-3 has its inherited labels checked against that environment's rules, and must carry each key that environment requires, at the crossing check of "Cross-environment sharing", and a violation refuses the crossing with `403 LABEL_NOT_PERMITTED` (decision 46). A derive under [`0144-session-derive`](../0144-session-derive/change.md) is a new root whose request carries its own labels, which the rules check as at any root's creation (0144 decision 14). A change to a rule applies to sessions created afterwards, and a running session keeps its labels.

**Limits and audit.** A tenant holds at most `labels.maxRulesPerTenant` (default 200) rules, an environment at most the same, and a rule at most `labels.maxValuesPerRule` (default 100) values. A write past a limit is refused with `429 QUOTA_EXCEEDED` naming it. Each refusal of a session writes `label.refused` with the key, the owner, and the environment, and each write of a tenant's or an environment's rules writes `label_rules.updated` with the actor and the rules changed.

**Readers.** A budget of 0170 that selects on a governed key binds the sessions the rules admit to the label, and the budget admin API answers a budget that selects on a key that is free in a tenant or in an environment the budget can match with a `Warning` ([`0170-budgets`, "BG-3"](../0170-budgets/change.md#bg-3-matching), its decision 49). A write of a tenant's or an environment's rules that frees a key some budget selects on, so that the key is no longer governed wherever that budget can match, is accepted and answers with a `Warning` naming those budgets (decision 46). The usage reports of §15.1 filter on labels as today.

## Scenarios

**Two environments in one customer.** Tenant `acme` has environments `web` and `payments`, with members from the groups `acme-web` and `acme-payments`. Pool `web-github` covers `github.com/acme-web/` for `web`, and pool `pay-github` covers `github.com/acme-pay/` for `payments`. The tenant allows `npm`. `payments` adds `stripe-api` and denies `huggingface.co`.

- Alice, in `web`, creates a session through `/v1/environments/web/sessions` that clones `acme-web/site`, and it succeeds.
- A plan from Alice naming `acme-pay/ledger` is rejected with the same answer as a repository outside every pool.
- An agent in Alice's session runs `git fetch https://github.com/acme-pay/ledger`. The scope check refuses it, nothing is minted, and `git` gets 403.
- Bob, in `payments`, reaches `api.stripe.com`, and Alice's session gets 403 for the same host.

**A session on the transparent path.** Alice calls `POST /v1/sessions` with no environment, on a tenant whose `web` runtime she can see, and `web` has no denied or route entries. The session has E = ∅ and reaches `npm`. A plan naming `web-github` fails. The error message tells a caller to use an environment path for environment objects, without naming any object. Bob makes the same call for a runtime `payments` selects, and it fails with `ENVIRONMENT_REQUIRED`, whether or not his token carries groups, so he cannot shed the deny on `huggingface.co` by omitting the environment.

**Two environments and one GitHub organization.** Pools `web-app` and `pay-app` both cover `github.com/acme/`, with separate GitHub Apps and allowlists, for `web` and `payments` respectively. A third, tenant-wide pool with that prefix is refused at write. GitHub enforces each App's own repository selection, so the environments' tokens differ.

**An environment's cloud role.** Binding `payments-aws` has `delivery: federation`, and it lists `payments`. The subject `lenny:acme:payments-aws` is stable. Acme's AWS trust policy names that subject, so only a session able to obtain this binding reaches the role. A session in `web` gets no token from the pod credential API.

**A shared pod on a recycling pool.** Pool `coding` has `recycle.enabled: true`. Alice's `web` session ends, `netagent` flushes its credentials, and Bob's `payments` session claims the pod. Bob's binding set and policy are correct, and any file state the pool recycle scrub does not reach survives from Alice's session.

**A concurrent pool.** Pool `chat` serves concurrent sessions on a runtime class whose `netagent` cannot attribute connections to slots, so its status records slot attribution as unavailable. Bob's create in `payments` fails with `ENVIRONMENT_POLICY_NOT_ENFORCEABLE`, because the pool cannot apply `payments`' deny or its route to `acme-pci-swg` per session. His retry through `POST /v1/sessions` fails with `ENVIRONMENT_REQUIRED`. Alice's create in `web` fails with `ENVIRONMENT_POLICY_NOT_ENFORCEABLE`, because `web` has a pool that lists it, so no slot on the pod can reach `acme-web/site` through the union. Carol's create in `support`, which has no entries and no object listing it, proceeds with unscoped objects. To run this runtime for `web`, a `tenant-admin` holding a grant gives `web` a derived runtime with a one-session owned pool, once [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md) lands, or the operator runs `chat` on a runtime class that answers slot attribution, on which each slot applies its own session's environment and all three creates proceed.

**A delegated child.** Alice's `web` session creates a child with `session.create` on a runtime that `web` selects, and the child has E = `web` with her session's inputs, as does each further hop. A target `web` neither selects nor shares answers `TARGET_NOT_IN_SCOPE`, whether Alice's group gives her membership or not. A `payments` child placed on `chat` is refused like a create.

**A shared review runtime.** Tenant `acme` turns on `dangerouslyAllowCrossEnvironmentSharing`. `web` declares `shared-review` outbound to `platform`, and `platform` declares it inbound from `web`. Alice, who is not a member of `platform`, has a `web` session create a child on it with `session.create`. The child has E = `platform`, `crossed_from_environment: web`, and `platform`'s hosts, routes, and bindings, and it bills to `platform`. The parent's tools do not reach it, a file it sends its parent passes `platform`'s content caveat on export and `web`'s on import, and the parent's watch of it shows its messages and results but not its tool calls. It reads a `platform` repository on a pool with `userAuthorization: off`, and a VCS pool with `userAuthorization: required` refuses it unless Alice has access. Its results return to her session, and it can send what `web` handed it to any host `platform` allows, including one `web` denies. When it calls `session.create` for `other-tool`, which `platform` shares with `tools`, the crossing check answers `TARGET_NOT_IN_SCOPE`. When the parent releases it with `session.release`, the release answers `403`, because Alice is not a member of `platform`. `credential.mint` and the audit event name both `web` and `platform`.

**A runtime route.** A `tenant-admin` writes a runtime route that sends 10 percent of the sessions asking for a runtime to a target runtime on pool `chat`. Bob's create in `payments` passes admission against the runtime he asked for, and the route interceptor moves it to the target. The post-chain check on the final row refuses it with `ENVIRONMENT_POLICY_NOT_ENFORCEABLE`, naming the route interceptor as the last modifier, since `chat` cannot apply `payments`' deny. A target runtime that `web`'s selector does not admit is refused in the same way for Alice, and an external `PreRoute` interceptor that makes the same change meets the same refusal.

**Onboarding a customer on the broker.** The operator creates tenant `globex`, a broker organization whose claim maps to `globex`, and a link to Globex's IdP. Alice, a Globex administrator, logs in. The broker issues `roles: [tenant-admin]` under a mapping the operator set. Alice creates environments with Globex's group names.

**A tenant on its own issuer, beside a tenant on the broker.** The operator creates tenant `acme` with a customer source for Acme's Entra tenant, with `subject_claim: oid`, `role_map` sending Acme's `lenny-admins` value to `tenant-admin`, and `group_source: scim`. The sign-in proof previews Alice's subject as `~k3f9~<oid>`, and the operator activates the source with a justification. Alice's MCP client uses `/t/acme/mcp`, whose metadata names Acme's issuer alone. `globex`, in the same deployment, stays on the broker and is unchanged.

- A broker token with `tenant_id: acme` gets `401 TENANT_ISSUER_MISMATCH`.
- A token from Acme's issuer carrying `tenant_id: globex` resolves to `acme`, because the claim is ignored.
- A token with an unknown `iss` is refused with no fetch.

**A customer's IdP asserts a platform role.** A token from Acme's issuer carries `roles: [platform-admin]`. `role_map` has no such entry, so it grants nothing, and the boundary records the drop. A `platform-admin` trying to grant Alice the role by row is refused, because `acme` is not the operator tenant.

**A stale claim against SCIM.** Bob's Entra group changes, and Acme's directory removes him from `payments-engineers` through SCIM. His token still carries that group. Under `group_source: scim`, his next `/v1/environments/payments/sessions` call gets `403`, because the claim is ignored. His running `payments` session continues. `ENVIRONMENT_REQUIRED` answers as it did before, since it reads no groups. If Acme's directory then deactivates him, his next request gets `403 USER_INVALIDATED`, whatever his token says, and his sessions end under `full_revoke`.

**A squatted issuer.** A trial tenant drafts a source naming Globex's Entra URI. The draft holds no index, so Globex can still register. The trial tenant fails the sign-in proof, since it holds no client there. Were it to pass, it would still need the operator's attestation, or under `identity.allowTenantActivation` its own `security-admin`'s approval, so that option carries the larger squatting risk. A `platform-admin` then retires the wrong row and deletes it to release the index. If the squatter's `security-admin` cancels the retirement, the operator invalidates that principal first.

**A customer on Google Workspace.** The operator lists `https://accounts.google.com` with `pinBy: claim`, `claim: hd`, and `claimIsDomain: true`. Acme's admin drafts a source with `pin_claim_value: acme.com`, and Globex's admin does the same with `globex.com`. Each passes the sign-in proof and the TXT check on its own domain, and both rows activate on one issuer. Alice's token carries `hd: acme.com` and Acme's client as its audience, so it resolves to `acme`. A personal Google account has no `hd` and is refused. A token Alice obtained for another application has `hd: acme.com` and that application's audience, and it is refused too. A service account token naming Acme's client as its audience has no `hd` and a foreign `azp`, so it is refused twice over. A Globex employee who drafts `acme.com` fails the proof, and one who signs in at Acme's callback gets a token selecting Globex's row, which the resolver refuses.

**A mix-up attempt.** Tenant `initech` runs a hostile source on its own IdP, and its admin sends Bob, an operator staff member, a proof link. Bob's browser reaches that source's authorization endpoint, which redirects to the broker with the deployment `client_id` and redirect URI. The broker returns a code to `/auth/callback/deployment`. The state cookie is scoped to the hostile source's callback path, so it is absent there, and Lenny refuses with no token request. The code never reaches `initech`. How a given broker handles that redirect is untested.

**A compromised source is retired.** Acme's IdP is compromised, and the attacker asserts `tenant-admin`, mints a SCIM credential, and opens a playground session. A `security-admin` requests `invalidateSubjects: true`, a second one confirms it, and the first retires the source. Tokens from that issuer stop, Lenny-issued tokens of its subjects are refused, the credential and the playground record are revoked, and a job ends those subjects' sessions and revokes their links. Broker tokens stay refused, because `deploymentIssuerAllowed` stays false. After Acme rotates its key, the source returns to `active` with the same `source_id` on a new proof and a justification, and tokens issued before retirement stay refused through `tokens_not_before`. The activation preflight lists role rows and credentials the attacker's subjects wrote, and an admin clears the job's holds so Acme's users return.

**An incident hold and the directory.** An admin invalidates Carol during an incident, placing an `admin` hold. Acme's directory then sends `active: false`, then `active: true`. The `scim` hold comes and goes, the `admin` hold stays, and SCIM reports `active: false`. A sync worker's `reinstate` behaves the same way.

**Activation with a security team.** Globex, on the broker, has a `security-admin` on a bare subject. A request to activate its own IdP stops at the activation preflight, which lists that principal as stranded. The `security-admin` assigns a new principal on the preview's canonical subject, which takes [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)'s delay, and approves. The activation preflight then passes, and the old row stays behind, unreachable, as "Residual risks" states.

**A departure.** Bob leaves Globex. He has logged in but has no user row. Globex's directory deactivates him, the broker receives the SCIM change, and the sync worker calls `invalidate` with `mode: full_revoke`, as `identity-sync` in tenant `globex`. Lenny creates the row, ends his sessions, and revokes his issued tokens. A later retry is idempotent. If Bob returns, the worker calls `reinstate`. A tenant whose directory calls Lenny's SCIM directly gets the same result with no worker.

**An invalidated administrator.** Carol, a `tenant-admin` at Globex, is invalidated with `full_revoke` while holding a valid IdP token. Her next admin call gets `403 USER_INVALIDATED`. She cannot call `reinstate`, and a stale `observedAt` from any caller cannot reverse a newer invalidation. Another `tenant-admin` can reinstate her.

**A mapping error.** A broker change lets Acme's mapping reach `roles`, and a token arrives with `roles: [platform-admin]`. The gateway removes the role, the caller acts with no platform authority, and the alert fires. A separate error placing `tenant_id: globex` on Acme's token is not caught, which "Residual risks" states.

## Residual risks

- **Environment scoping shares pods.** On a recycling pool, state the pool recycle scrub does not reach survives into another environment's session within the tenant, as it does between users today. An environment needing separation uses a pool with `recycle.enabled: false`, or a separate tenant (decision 5).
- **Shared tenant resources.** The mirror's store for a pool used by several environments, the Token Service token cache, egress group, and the quotas of [P7](../0127-egress-and-git/change.md#security-properties), the egress property that bounds each pod's and each tenant's egress load, are shared across environments. One environment can consume the tenant's quota (decision 6). One environment's egress address is the same as another's, so a customer firewall rule admits both.
- **Tenant-wide objects stay tenant-wide.** An environment cannot opt out of a tenant-wide binding or host. It can deny a host. The tenant admin must scope a binding to remove it from an environment. Scoping a pool also leaves a repository reachable through any wider tenant-wide pool whose allowlist names it, so the write response warns when a scoped pool's repository appears on such an allowlist.
- **A person's token across environments.** A link has no environment, so a member of two environments has one token. Under `oauth2Link` with no narrowing template, the link provider data that derives a narrower per-session token from the stored one, a session in either environment holds that token's full reach, whichever environment's repositories it was meant for.
- **Policy added after a session began.** A deny or a route added to an environment reaches its one-session pods at the next decision. A transparent session created before the entry existed keeps E = ∅, and a session already running on a pod with no per-session policy keeps running until its next resume, as the write's `Warning` reports.
- **Cross-environment sharing.** On a declared path, an injected caller can hand data to a target runtime, which can send it anywhere the target allows, skipping the caller's denies and proxy. That data includes anything the agent can read, such as a token delivered under `delivery: file` with no `lockEgressToHosts`. A non-member's agent can drive the target's credentials and receive results, on any pool with no user check. The owner accepted both under decision 14. A `tenant-admin` writes both sides of a path, so its two sides do not separate duties.
- **Label edits on a sharing path.** A label edit through `PUT /v1/admin/derived-runtimes/{name}`, a `platform-admin`'s edit through `PUT /v1/admin/runtimes/{name}`, which [DR-1](../0147-tenant-derived-runtimes/change.md#dr-1-to-dr-3-prerequisites), a prerequisite proposal in [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md), closes to a `tenant-admin`, or a change to T's selector, adds a runtime to a declared path at once, with no delay. Posture lists paths and reports after the fact.
- **Forged adapter calls.** The rule that a platform operation acts only on the calling session's children trusts the session the adapter presents, so a compromised adapter can still name another session until F-10.2.29 closes.
- **Per-parent child cap.** A positive `maxChildrenTotal` caps each parent's children and does not bound a tree.
- **Shared runtimes run with the caller's objects.** This applies to a runtime several selectors admit, with no sharing path. A runtime that several environments select runs under each session's own E, so that environment's scoped credentials and repositories reach the shared runtime's code. A tenant admin decides this when writing the selector, and no inbound consent exists on the side that owns the runtime.
- **Members of several environments.** A caller in both `web` and `payments` can create in `web` and avoid `payments`' deny. A deny binds an environment's sessions and does not bind a person. Under `noEnvironmentPolicy: allow-all`, a token with no groups can likewise run E = ∅ on a runtime that no environment with denied or route entries selects.
- **Invalidation during a Postgres outage.** `lenny-ops` falls back to token roles, as above.
- **Mirror assertions.** The Token Service verifies the cause a mirror fill names. A compromised mirror can still name any live pod cause in a tenant whose route names the mirror, and it can replay a gateway cause assertion within its 60-second expiry for the same upstream and pool. This is the same limit as its tenant assertion, the `x-lenny-tenant` header with which the mirror names a store's tenant on its upstream fetches.
- **Membership at create.** A user removed from a group keeps running sessions, and those sessions keep E's objects, until the session ends or the user is invalidated. Removal from an environment alone has no session effect.
- **Exfiltration between environments.** A session in `web` with a host open can send data anywhere that host accepts. Scoping limits credentials and destinations. It does not stop a user who belongs to two environments from moving data between sessions.
- **Changing a tenant's issuer.** Each issuer has its own subjects. If an operator points an existing tenant at a different issuer, Lenny treats the new subjects as new users, and data keyed on the old ones (sessions, user rows, links, and registered tokens) does not carry over. Lenny provides no migration. That includes security principal rows and `lifecycleSubjects` on old subjects, which the activation preflight lists, and a new subject cannot re-link a provider account an old one holds, because `user_links` is unique on `provider_user_id`.
- **Broker correctness.** For a tenant on the deployment source, the tenant boundary rests on one claim from one issuer. A broker fault or a compromised broker can issue a token for any such tenant, and a second claim from the same issuer adds nothing. A broker that authenticates the operator tenant can also assert a staff subject, which reaches platform authority and, through impersonation, every tenant, including pinned ones (TP5).
- **An issuer's principals.** An issuer controls every principal it authenticates, including a `security-approver`, whatever `securityRoleSource` says. On a tenant on the broker, an operator can therefore act as that approver through its broker. Posture reports the dependency, and decision 25 leaves a second factor out.
- **A customer's IdP.** A compromised or misconfigured customer IdP can assert any subject, mapped role, or token group in its own tenant, including `tenant-admin` through `role_map`. Under `securityRoleSource: managed`, `security-*` claims stay ignored, but it can assert a principal's subject, as above. It cannot reach another tenant or a platform role, subject to "Shared issuers" below for a listed issuer.
- **Hosted issuers.** No mechanical proof binds a customer to an issuer on a shared host, so a pin rests on the sign-in proof, the domain proof, and the operator's attestation. The first activation holds the index until a `platform-admin` resolves a dispute, and `identity.allowTenantActivation` removes the operator's check from that path. The denied list is known shared issuers and cannot be complete.
- **Shared issuers.** Tenants on one listed issuer share its key set and its availability, and a fault or compromise at the provider reaches all of them. A platform admin's wrong entry, naming a claim a customer can write, lets that customer's administrator assert another tenant's value, and Lenny cannot detect this. `pinBy: audience` leaves the decision to the provider, and the `azp` rule stops only what a provider marks. On a non-domain claim, one member of an organization who gets past the operator's checks can hold its value until a dispute is resolved, and until then that organization's members resolve into the wrong tenant. If an entry proves wrong, removing it does not stop existing rows, and the response is to retire those rows, under the delay where it applies, or to turn off `identity.customerSources.enabled`. These follow from decision 18, and a tenant that cannot accept them uses an issuer of its own.
- **Resold domains.** A later owner of a domain pin's value holds tokens with that value, and those subjects are new users of the old tenant for up to `identity.domainPinLapseDays` after the TXT record goes. They have no role row on a provider with no role claim, such as Google as far as the documentation shows, and on a provider with an admin-set role claim and a `role_map` a later owner's administrator can assert a mapped role. Under `noEnvironmentPolicy: allow-all` they still reach the tenant's runtimes and tenant-wide objects. `require_directory_row` stops this. An owner who republishes the old TXT value, which is public, removes the time limit. A [2024 flaw](https://www.techrepublic.com/article/google-workspace-vulnerability-accounts-exposed/) let unverified Workspace accounts sign in to third parties (secondary source), and whether those tokens carried `hd` is unconfirmed. If they did, a token could select a pinned row with no control of the domain. Google [disputes the report's severity](https://www.securityweek.com/google-oauth-flaw-leads-to-account-takeover-when-domain-ownership-changes/amp/) because `sub` differs for the new accounts, and that difference is what keeps them off the old subjects (secondary source).
- **An unlisted shared issuer.** The denied list and `identity.sharedIssuers` cannot be complete. A row with no pin on a shared issuer that neither list names would accept every customer of that provider, and the sign-in proof does not reveal this. Proof 4 and the operator's review carry it.
- **Operator reach into a pinned tenant.** A `platform-admin` keeps impersonation and can activate a source. At a tenant with no `security-admin` row in any state, nothing delays that, and [SO-4](../0142-security-oversight/change.md#so-4-operator-access-transparency), the security oversight design's operator access transparency, is what makes it visible. Where the delay applies, a stolen `platform-admin` can first invalidate the principals who could cancel and write its own justifications, so the delay, the SIEM event, and any outage are what remain to warn the customer.
- **Unchanged reactivation.** With no reachable principal, a stolen `platform-admin` with a login at a compromised issuer can undo a `security-admin`'s emergency retirement at once, by returning the row unchanged. This has no delay, because retirement has to stay reversible during an incident. `tokens_not_before` still refuses older tokens.
- **Cached keys.** An IdP rotating out a compromised key while unreachable stays trusted up to the maximum staleness.
- **A stolen `tenant-admin`.** It can mint a SCIM credential, which posture lists, and it can write role rows and custom roles. On a deployment-source tenant with no security principal, it can also set `introspectionEndpoint` and capture bearers, which [`0142-security-oversight` decision 23](../0142-security-oversight/decisions.md#decisions) governs.
- **A stolen SCIM credential.** It can deactivate any unprotected user in its tenant, within its quotas, and under `group_source: scim` it can change group membership, and so environment membership. It cannot authenticate as anyone, assign a role, or clear another class's hold.
- **Egress for issuers.** The gateway's external rule and the Token Service's are wide, and each customer issuer depends on them. A strict deployer maintains addresses per customer.
- **Published metadata.** A per-tenant metadata document discloses a tenant identifier and its IdP host, and the typed-email page discloses which domains are customers.
- **Declared claims.** `match_claim` is immutable and verified because the source says so. Lenny cannot check that, and a wrong declaration brings back takeover through a directory row.
- **Ongoing proof.** Discovery and domains are re-read, and the sign-in proof and attestation run once.
- **Broker availability.** A broker outage stops new logins and token refresh for all tenants on it. Verification continues on cached keys, and running sessions continue. A customer IdP's outage does the same for its tenant alone, and a shared issuer's outage for all its tenants.
- **Running sessions on unbound rows.** A user on the deployment source whose directory row never bound has no subject to hold, so `active: false` leaves that user's running sessions up until the next IdP token matches. A Lenny-issued bearer carries no `match_claim` either, so it also waits for that. The SCIM response and an alert report the case, and TSR-6 holds only in part here.
- **Lost issuer.** A customer that has permanently lost its issuer cannot approve or cancel its own recovery, and the operator acts under a delay nobody can cancel.
- **Stale snapshots.** A replica with a stale snapshot can mint a Lenny token after retirement with an `iat` that passes `tokens_not_before`, and it survives a later reactivation until it expires.
- **Rotated keys.** `tokens_not_before` cannot stop a compromised key that was not rotated, because such a key chooses its own `iat`.
- **Stale group data.** Under `group_source: token` with no introspection, group changes wait for a new token. With introspection, a failure of the tenant's endpoint fails its requests closed with `503`. Under `group_source: scim`, changes wait for the directory's delivery and the 30-second cache, and a store failure answers `503`.
- **Lifecycle delivery.** Lenny cannot detect a lost event. The directory or the operator's worker owns retry, and a user stays active during an outage of either side.
- **Unproven.** Nothing in the identity design has run. Open questions include whether Google's tokens carry `hd` with and without the request parameter, which spelling of its issuer each flow returns, whether an MCP client's own login yields a token that selects a pinned row, how MCP clients behave against per-tenant metadata and audiences, whether Entra's, Okta's, and other directories' SCIM traffic matches the corpus, the 24-hour staleness value, provider behaviour on the browser login path including silent single sign-on, the CPU cost of oversized keys, the dial-time address check under production resolvers, group read latency on the auth path, and memory for per-issuer verifiers across many tenants and replicas.
- **Secret in `rbac-config`.** See "Defects found while verifying".

A missing TXT record suspends past its bound, lookups that keep failing suspend past theirs, a mass miss holds instead, every return of a domain pin needs a subject already holding a role row, including from `retired`, and the TXT check repeats at effect. `subject_claim: email` and a tenant-chosen `pin_claim` are refused. A shared issuer's excluded address holds the issuer, changes no row, cancels no pending version, and clears itself. `require_directory_row` refuses a subject with no directory row.
- Directory tables under row-level security, with one tenant's credential unable to read or write another's rows.

### `contract`

- The admin API representation of each scoped object and of `environmentPolicies`.
- The refusal for an out-of-scope object and for an unknown object are byte-identical apart from the request's own name (TP4).
- The `reinstate` and `invalidate` request and response formats, including `applied`.
- `DELEGATION_DISABLED` on REST envelopes, and `delegationLease` echoing an explicit 0.
- The evidence envelope carries `environment` on each producer's stream.
- The `identity-sources` resource, the `/t/{tenantId}` paths, and RFC 9728 documents with `WWW-Authenticate`.
- SCIM requests and responses against RFC 7643 and RFC 7644 as far as the surface goes, including the error schema, and against the recorded directory corpus.

### `integration`

- A session create through each explicit path sets E, and through the transparent path leaves it empty.
- An environment write that adds a requirement applies at once, and one that removes or weakens a requirement without a `justification` is refused, while one with a `justification` takes effect only after the weakening delay and is cancelled by the tenant's `security-admin` (decision 29).
- An environment's `placementRequirements` refuse a session in that environment whose final pool fails one, with `PLACEMENT_REQUIREMENT_UNMET` and `details.source: environment`, while a session in another environment of the same tenant on that pool passes. A write cannot remove a requirement of the tenant through the environment. A crossing child into T on a pool that meets its parent's requirements and fails T's is refused, and so is one on a pool that meets T's and fails its parent's.
- Derive and delegation propagate E, and billing rollup and retention follow. A crossing child bills and retains under T, and its records name both environments. Same-environment descendants copy `crossed_from_environment` and cannot cross.
- A session under `maxDepth: 0` holds no grant and gets `DELEGATION_DISABLED` from a runtime's direct `session.create` call through the intra-pod `platform` tool server, its `availability.delegation` is `false`, and `runtimes.list` is refused. `POST /v1/sessions/start` applies the field, and every root creator writes a value. An in-pod caller whose `session.send`, `events.wait`, `session.list`, or other operation names a session that is not its child gets `PARENT_SESSION_MISMATCH`, and an operation outside §9.1's table and 0166's list gets `ErrPlatformToolNotFound`. While `lenny/create_and_start_session` and `BindSingleShot` remain, until 0138.S6, a session each creates stores the resolved value and delegates up to it. A session with an absent value delegates up to the resolved limit, and that limit stays stored when the Helm value later changes.
- A child cannot widen its parent's value through `session.create`. A derive stores the source's value minus its depth, and a resume keeps its row. A session that recovers after a pod failure keeps the same stored value. A non-empty `delegationPolicyRef` is accepted, echoed, and changes nothing, and §27.4's playground payload still creates a session.
- A session under `maxDepth: 0` cannot cross with both sides declared.
- A declaration or setting change applies to the next `session.create` and revokes no in-flight child. A `PreRoute` change that moves the child's final runtime off the path refuses the `session.create`, and a crossing child's routing labels start as its parent's. A `userCredential` binding crosses only when `session.create` names it and T can see it. A crossing child's `credentialBindings` and `egressHosts` are T's, narrowed by the arguments, and its policy cap, numeric caveats, and content caveat are its parent's narrowed by T's `defaultDelegationPolicy`, `delegationCeilings`, and environment level.
- An environment's `defaultDelegationPolicy` refuses a `session.create` of a session in it whose target the policy does not admit, at the post-chain point, and a change to the policy applies to the next `session.create`. `delegationCeilings` lower the resolved numeric caveats of a root in the environment.
- Across environments: a `session.create` that crosses and carries `tools` or `offerTools: allow`, and a `session.send` to a crossed child that carries `tools`, are refused with `TARGET_NOT_IN_SCOPE`. A `files` export, a `materialize` push, and a `files.import` between a parent and a crossed child each apply the sender's content caveat on export and the receiver's on import. A parent's watch of a crossed child and its `session.messages` carry the child's messages, child events, and results, and no activity or tool call. A `session.release` of a crossed child by a parent whose principal is not a `creator` in T, or for a runtime T's selector no longer admits, answers `403` and leaves the child with its parent, and one under a forbidden setting or a removed declaration answers `TARGET_NOT_IN_SCOPE`. A released crossed child keeps its mark. A VCS pool in T with `userAuthorization: required` checks the parent's user, and a pool with `userAuthorization: off` does not. A crossing child reaches an operator service only on a host of T's allow list, with T's credential bindings, and an `identityAssertion` attached for it names T as its environment. §8.3's `inherit` check runs on a crossing.
- The forbid of [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture) refuses the write and suspends the paths, turning the setting on waits out the delay, and posture lists the paths.
- A `viewer`, and a member whose environments do not select the runtime, are refused on the transparent create.
- The existing `cross_environment_delegation_test` moves to the opt-ins, with an in-pod caller whose principal has no groups.
- Edit propagation: removing E from a binding refuses the next request on the pod credential API, and adding a host to `denied(E)` refuses the next decision within the policy version rule, under which every policy write increments a version in the decision cache key, so an edit applies at the next decision rather than when the cache entry expires.
- Invalidating a subject with no row creates the row and ends sessions. After `full_revoke`, a fresh IdP token is refused on every path, including the admin API and `/v1/oauth/token`. After `soft_disable` or `hard_disable`, the same token keeps session reads and loses admin authority. Reinstate restores access. A user under erasure cannot be reinstated, and a caller cannot reinstate itself.
- An in-pod delegation with no groups on the principal follows the session's E under both `noEnvironmentPolicy` values. A chain of delegations keeps E's denies and routes at every hop, and the decision service, the Token Service, and the mirror agree two hops down.
- `PUT disabled:false` is refused on an invalidated row. A `DELETE`d administrator's token is refused. `soft_disable` and `hard_disable` by a `platform-admin` revoke the user's impersonation bearers. A token from `/v1/oauth/token` carries the subject's groups and enters an environment by `oidc-group`.
- A mirror fill names a pool and one cause: a pod UID, a gateway cause assertion, or a prefetch record. The Token Service refuses a cause that is not live, a cause from another tenant, and a pool other than the one selection picks from `visible(VCS pools, E)` for the cause's E. A cause from another tenant also writes an audit event and raises the alert. A warm pod and a pod with no per-session policy select at E = ∅, a fill from a pod with several slots whose pool answers slot attribution selects at the E of the session `netagent` attributed the fetch to and is refused when the pod's binding does not hold that session, an assertion selects at the E it carries, and a prefetch cause takes the record's pool. A fill accepted at its first mint keeps minting on its fill ID after its pod is gone until the fill lifetime ends, and a fill ID presented with another mirror identity, tenant, upstream, or pool, or after the lifetime, is refused. A change to the `environments` list or prefixes of a pending prefetch record's pool voids the record. A prefetch request that omits the pool stores the one covering pool and is refused when several pools cover the repository.
- Ref resolution on each creation path, including derive and delegate, runs after the post-chain point, so an assertion names the final pool and the settled E, and a bad ref in a plan sent with the create request claims no pod. At finalize, the assertion carries E from the session row. The decision service reads E from the assertion on the direct path.
- `introspectionEndpoint` resolving to an excluded range is refused at write and at call.
- The metadata route names the issuer, and a 401 carries the challenge header. A per-tenant document names only that tenant's active issuers. A token whose `aud` names another audience is refused by the client API with the challenge header, whether it arrives on REST or through the MCP adapter at `/mcp` or `/t/{tenantId}/mcp`, and a token whose `aud` names a computed adapter identifier is accepted.
- A fake OIDC issuer per tenant: login, verification, mapping, and rotation with a new `kid`, on the gateway and on the Token Service at `/v1/oauth/token`.
- A proof login runs on a draft through the resolver. A `platform-admin`'s retirement at a tenant with a `security-admin` waits out the delay and can be cancelled, and a `security-admin`'s applies at once. `invalidateSubjects` needs a second `security-admin` or the delay, and its holds survive reactivation until cleared. A stranded row counts as active for approval. Reactivation needs a new proof and a justification, and drops cached keys. `tokens_not_before` refuses older IdP and Lenny-issued tokens, and tokens with no `iat`, on the gateway, on `/v1/oauth/token` for each token, and on `lenny-ops`. A retired issuer stays held until its row is deleted.
- A `retired` or `suspended` row refuses writes, and a reactivation that changes a field waits as a `pending_version` under the activation rule, while an unchanged return does not. A suspension cancels a pending version.
- A first activation's row refuses writes, a draft edit clears `proof`, and a digest that no longer matches stops the change at effect. A change on an active source or settings row leaves the row `active` on live values during the delay, further widening is refused, and a narrowing or retirement cancels the pending version. Activation and a `deploymentIssuerAllowed` change wait out the delay after every `security-admin` is invalidated. Only a `draft` or `retired` row can be deleted, and a `retired` row's deletion takes the delay where one applies. `introspectionEnabled` is refused at a tenant with a customer source. A playground-origin `subject_token` is refused.
- A deployment token matching an inactive directory row is refused whether or not a user row exists, a login hold on a security principal follows `lifecycleSubjects`, and `active: false` on an unbound row reports in the SCIM response and fires the alert.
- A callback refuses with no token request when its state cookie is absent, when `state` does not match, when the state's source differs from the path's, or when RFC 9207 `iss` differs. A bare playground login and the link start page go through the resolver and answer `TENANT_ISSUER_MISMATCH` for a broker token naming a pinned tenant. `/t/{tenantId}` refuses a token of another tenant.
- A proof login needs the drafting admin's session or a live one-time token, creates no session, and a token cannot be used twice. Retirement refuses Lenny-issued tokens of its subjects, revokes SCIM credentials and playground records, and `invalidateSubjects` reports partial failure. Reactivation keeps `source_id`.
- A secret is returned by no route, is sent only by the Token Service, and is unusable after a sealed field changes.
- A SCIM deactivate reaches each `scim_deactivate_mode`, `active: true` clears only SCIM's own hold, re-provisioning an erased subject is refused, a security principal needs `lifecycleSubjects`, `externalId` cannot change, quotas apply, and a provisioned row leaves token roles in effect.
- Under `group_source: scim`, a stale claim does not admit, a removal takes effect within the cache bound, a store failure answers `503`, and `introspectionEnabled` is refused.
- `match_claim` binds once on the deployment source, a matching login on an inactive row is refused, a deployment `externalId` beginning with `~` is refused, and a `deployment` credential stops when the tenant disallows the deployment issuer.
- Erasure removes directory rows and memberships, and tenant deletion removes sources, credentials, and directory rows.
- `GET rbac-config` does not return the introspection secret.
- A `sync` class past `identity.userUpsertLimitPerClass` gets `429 QUOTA_EXCEEDED` with `details.quota: userUpserts` and creates no row, an `admin` caller's invalidate of an unknown subject still succeeds at that point, and `UserUpsertCapNear` fires at 80% of the cap.
- `reinstate` on a row removed through `DELETE` is refused, and the creation fence refuses a session create for a user held by a SCIM class, on every creation path.
- A full-revoked user's bearer gets `403 USER_INVALIDATED` on the gateway, `lenny-ops`, and `/v1/oauth/token`.
- A SCIM credential rotated with an overlap authenticates under the old and the new value until the overlap ends and under the new value alone after it, and failed SCIM authentication is rate limited per source address.

### `e2e_kind`

- Two environments in one tenant run the first scenario in full: clone, push, a refused fetch, a bound host, and a refused host, through `netagent`, `lenny-egress`, the decision service, and the Token Service.
- A sequentially reused pod carries no credential across a change of environment.
- A runtime on Kind under `maxDepth: 0` calls `session.create` directly and is refused, with no child pod claimed, and a pod failure in a tree recovers no wider value.
- A crossing child on Kind reaches T's hosts, is refused a tenant-denied host, and reaches a host the caller's environment denies, which pins the accepted behaviour.
- A concurrent pool whose status records slot attribution as unavailable refuses a session in an environment with anything of its own and a plan naming a scoped repository, and it admits an environment with nothing of its own. A session or delegated child carrying `egress.allowedHosts` or `egressLockHosts`, inherited included, is refused. A slot on an admitted pod cannot reach a scoped repository through the union.
- A create, derive, and delegated child each meet the same refusal on that pool, a resume meets it for a deny, a route, or a lock, and a resume proceeds with only a later additive entry.
- A concurrent pool whose runtime class answers slot attribution admits sessions of two environments in two slots of one pod, each slot reaches its own environment's hosts and scoped repositories and is refused the other's, and a session carrying `egressLockHosts` is limited to its lock in its own slot.
- Tenants on the deployment issuer and on a fake customer issuer run at once in one deployment, each refusing the other's tokens, under the chart's NetworkPolicy with an enforcing CNI, on the gateway and on the Token Service.
- A single-company install with no source behaves as before, and subjects keep their form.

### `e2e_cloud`

### `load_local`, and `load_kind` for the cases across replicas

- Concurrent writes to an object's `environments` and to session creates produce a consistent decision for each session.
- A write that adds `environments: [web]` to a binding, a VCS pool, or a `dangerouslyShare` entry, run concurrently with `DELETE /v1/admin/environments/web`, leaves either the reference and the environment or neither, and a later environment named `web` inherits no reference.
- A session create in `web` run concurrently with the delete of `web` leaves either the session with the environment, which makes the delete answer `RESOURCE_HAS_DEPENDENTS`, or no session.
- Two VCS pool writes with the same prefix and overlapping `environments` run concurrently, and one of them is refused, so exactly one pool answers for any repository and environment.
- Repeated identical `invalidate` calls during a `reinstate` converge on the state of the newest stored time.
- The resolver adds no measurable decision latency beyond the existing cached policy read, measured against a stated threshold in the proposal.
- A flood of tokens with unknown `iss` values causes no fetch of those issuers and stays within a stated CPU bound, and refresh holds no lock during a fetch. Tokens for one slow issuer do not delay another's on a shared replica.
- Many sources across replicas, for verifier memory and the group read on the auth path, against stated thresholds. A SCIM burst stays within its rate limit, with one tenant's burst not affecting another.

### `chaos`

- Postgres loss during a decision or a mint fails closed. During the loss, the gateway refuses every bearer on the role lookup, and `lenny-ops` authorizes on token roles as §25.4 states.
- The issuer's JWKS endpoint goes down during a run, cached keys continue to verify, an unknown `kid` is refused, and past maximum staleness that source alone is refused, or every row on a shared issuer with none changing state.
- A Postgres outage leaves the registry on its last snapshot, a SCIM write answers `503`, and the group read of a source with `group_source: scim` answers `503`.
- A partial `full_revoke` reports its failures, and a retry completes it.
- The Token Service's read of the user row fails during an exchange, and the exchange is refused.
- Retried older invalidations interleaved with a reinstate across replicas leave the user active, because the cleared class keeps its stored time.

### `security`

- A client outside a rule's `allow` or `valueFrom` cannot create a session that carries a governed key or value, a session missing a required key is refused, no client sets a key under a reserved prefix, an environment's rules never admit what the tenant's rules refuse, a derive cannot carry a label the current rules refuse, a child cannot cross into an environment whose rules refuse its inherited labels or that requires a key it lacks, and a principal of a second identity source that asserts the same group name as the first, or a group that contains the pattern, does not obtain the label a `valueFrom` rule derives for the first source.
- The Token Service and the decision service refuse as a cause any Lenny-issued JWT that is not of type `lenny-cause+jwt` with the audience `lenny-cause`, and every other Lenny verifier refuses a gateway cause assertion.
- A token from the configured issuer with `roles: [platform-admin]` cannot reach any platform-only endpoint on the gateway, and cannot exchange into that authority at `/v1/oauth/token`. A tenant IdP token carrying `platform-forensics` reaches no forensic route, a `role_map` naming it is refused, and a `platform-forensics` row outside the operator tenant is refused at write and ignored by the resolver.
- A member of an environment with denied entries cannot reach a denied host through the transparent path, derive, delegation, or a runtime route or `PreRoute` interceptor that moves the session to another runtime or pool.
- With no sharing path, a descendant at any depth cannot obtain an object scoped outside its root's environment, or reach a host that environment denies. With one, a child and its descendants cannot obtain the caller's scoped objects or cross a second time, no pod input can set `crossed_from_environment`, and the tenant's denies hold.
- A hostile source cannot obtain another source's code through a redirect at its authorization endpoint, tested with a fake broker, and a silent login there cannot replace another tenant's session cookie.
- A hostile discovery document naming an in-cluster, loopback, or redirecting endpoint is refused for each endpoint.
- A tenant cannot name another tenant's secret, because no field names one.
- A broker token cannot reach a pinned tenant through the bare playground login.
- An invalidated `tenant-admin` with a valid IdP token cannot reach the admin API, reinstate itself, or poison ordering with a future `observedAt`, and a token with no groups cannot shed an environment's deny under `noEnvironmentPolicy: allow-all`.
- A compromised runtime cannot delegate under `maxDepth: 0` or shed its limit, environment, or mark by any tool call: naming another session's child in an operation, creating a root session, calling any tool outside the §9.1 table and 0166's operations, offering its tools to a crossed child, or releasing a crossed child into an environment its principal cannot enter. A forged adapter call is out of scope until F-10.2.29 closes, and a test records that gap.
- A session cannot change its environment through any request field, and a body `environment` on a path naming another is overridden.
- An agent in E cannot obtain a credential scoped elsewhere through the pod credential API, a direct call to the Token Service with its own token, the mirror, or `netagent`'s git path.
- A compromised-decision test: a stubbed decision service that allows a scoped object does not produce a mint, since the Token Service's own read refuses it.
- A token with an absent, malformed, or unregistered tenant claim keeps the §10.2 refusals, and a nested tenant claim is refused.
- A customer issuer cannot reach another tenant through any claim, a platform role through any claim or row outside the operator tenant, or a `security-*` role under `securityRoleSource: managed`. A broker token cannot reach a tenant whose `deploymentIssuerAllowed` is false, including after its customer source retires. A token carrying an alias verifies and resolves as one carrying `issuer` does, a near-match of either is refused, and a draft naming an alias is refused. On a shared issuer, these are refused with one indistinguishable answer: a token with another row's pin value and this row's audience, an audience array matching two rows, an absent claim, a claim that is an array or an object, a claim differing only in case, an unsigned token naming a pin value, a token with a matching single audience and a foreign client claim, and any token for a row with no pin on a listed or marked issuer. Both playground mint modes and the impersonation mint refuse a subject of a retired or suspended source, a playground record older than `tokens_not_before` mints nothing, and one with no directory row under `require_directory_row`. The chart refuses `pinBy: audience` on Google's issuer and each refused claim name. A browser login at one source whose token selects another row is refused in both directions, on the playground and the link start page. A sign-in proof whose token differs from the draft's pin fails, and so does a `claimIsDomain` draft with no TXT record.
- A tenant admin cannot activate or widen a source, and at a tenant with a `security-admin`, a platform admin's activation waits out the delay and can be cancelled.
- A new issuer's `sub` equal to an old one's reaches no old row, because the `source_id` differs.
- A Lenny-issued service or agent token whose subject carries a retired source's `~<source_id>~` after its `~svc~` or `~agt~` namespace is refused on every path registry step 7 covers, and so is a deployment `~svc~` subject at a tenant whose `deploymentIssuerAllowed` is false.
- Issuer URLs that resolve to excluded ranges, redirect, or rebind are refused, with the gateway and the Token Service both tested.
- A SCIM credential reaches only its own tenant and source, and every admin API route refuses it, including `POST /v1/admin/users/{userId}/invalidate` and `/reinstate`. Its value appears in no log.
- A role holding `manage_user_lifecycle` alone can call `invalidate` and `reinstate` in its own tenant, and nothing else.
- A `security-admin` or `security-approver` placed under `soft_disable` or `hard_disable`, by an administrator or by a SCIM deactivation, holds no `security-*` role on its live bearer, cannot cancel a weakening or approve an activation or operator access, and does not count as active for approval.
