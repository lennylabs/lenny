# Decisions: 0131 Incremental checkpoints

## Owner's direction

On 2026-11-05 the owner wrote: "we definitely need to improve checkpointing with a re-design." The owner supplied pointers from another conversation, which "Starting points" evaluates.

On the same day the owner accepted the recommended `checkpointPolicy` values (IC-8, [decision D8](#decisions)), in the words "your recommendation makes sense", and added: "I think a runtime/pool should be able to override the default checkpoint interval if possible."

The owner then asked for measurements on AWS, run independently of the project's test infrastructure, with repositories fetched from the internet, and scoped to "how long it takes to checkpoint and transfer". For the follow-up runs the owner wrote: "Depending on the results, and if needed to find a good solution, try different combinations. If 4 helps, then it should be documented for deployers. Make sure to measure performance impacts of 5." Item 4 is the gVisor KVM platform, and item 5 is the inotify change tracker. The owner added: "Once we're done with the tests and decisions, make sure the design doc includes changes/updates to Lenny's docs, with maybe a new section for checkpointing, with actual benchmarks and all the levers operators and tenants can use to reduce the impact when needed (including things like disabling checkpointing or changing the frequency, running on runc in a dedicated pool (tenant pool), etc.)"

Asked whether the default pause budget should be 5 s or 10 s, the owner chose "10 s default" ([decision D7](#decisions)). The same day the owner asked for the Kubernetes checks in "Benchmarks": "Test --file-access-mounts=exclusive with ConfigMaps etc. Test emptydir_mode = "block-plain"'s interaction with the kubelet's emptyDir size limit."

Asked whether the platform has a way to stop a runtime that does not quiesce, such as the cgroup freezer, which suspends every process in a container's control group, the owner answered: "no, I don't want the forcing mechanism, thanks". Quiescence therefore stays cooperative. A quiescing runtime pauses itself on `checkpoint_request`, and every other runtime is captured on the best-effort path while it runs.

On 2026-11-08 the owner accepted, in the word "ok", the recommended placement of the settings this design names with defaults ([decision D14](#decisions)). The pack format and capture settings are constants that the specification states, `checkpointConcurrency` is a gateway setting from the chart, and `restoreConcurrency` is an adapter setting that the controller passes from the chart to every agent pod.

On 2026-11-09 the owner settled that the embedded `SIGSTOP` checkpoint path of §4.4.3 is removed, and that this design states the removal ([decision D15](#decisions), IC-9). [`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md) had proposed to amend that path for quarantined pods, and it drops the amendment.

On 2026-11-12, after three spikes that checked this design against [`0145-session-isolation`](../0145-session-isolation/change.md), the owner settled that design's decisions D8 and D9. Under SI decision D8 each slot container mounts its whole workspace volume with no `subPath`, a separate volume that only the adapter mounts holds the spool and the export staging, and the warm clones are mounted read-only at the same absolute path in the adapter and in every slot. Under SI decision D9 the adapter reaches every slot file through the runtime supervisor's file-descriptor broker, the `fs` request on `CH-SUPERVISE`, the owner accepted about 470 added lines in the C supervisor, and all checkpoint logic stays in the adapter. The owner asked that this design and the other designs that handle session files be updated, and that the checkpoint design then get a full validation with performance measurements like the AWS benchmarks of 2026-11-05 and 2026-11-06. Revision 13 applies the update, and "Benchmarks", "Validation owed" in `steps.md` states the validation.

The validation ran on AWS on 2026-11-12, and a second run the same day measured Kata `block-plain` with a dedicated `fsGroup` and the parallel stat walk ("Re-validation through the broker"). On those numbers the owner settled the open decisions of revision 13 the same day: "D16: adopt `statat`", "D17: keep the tracker off on 9p under auto", "D18: copy-mode freeze for files within the export share", and "The tracker can be enabled on Kata virtio-fs" ([decisions D16 to D18](#decisions)). The owner directed three fixes without a decision: FIFOs on gVisor's default mount are recorded as metadata-only, the spool's `sizeLimit` sits above the adapter's cap and any single clone is bounded by the slot's remaining share, falling back to reading in place, and the 4 GiB constant-write clone that took 11 s against 2 to 2.5 s before is recorded as an investigation owed.

The owner then asked for a faster broker walk, "with a specific concern about directories holding very large numbers of files and about timeouts", and settled it as option (b): the adapter stats in parallel relative to broker-passed directory descriptors, falls back to the broker's `statat` only on `EACCES`, and the supervisor forks no broker workers ([decision D19](#decisions)). The owner also decided to "stagger checkpoints across slots: at most one slot checkpointing at a time per pod, the others queued", as a decision of this design, with a measurement later ([decision D20](#decisions)).

On 2026-11-13 the owner asked for cross-session deduplication as an optimization, possibly as an opt-in per tenant. A study found that sharing chunks between sessions lets a session probe what other sessions hold, through the pod's network byte counters on every isolation profile, checkpoint timing, or the quota. The owner chose a hybrid: only files the platform staged, from warm repository stores and from a runtime's shared assets, are deduplicated, with one set per source and no key by commit ([decision D1](#decisions), IC-4, "Platform chunk sets").

The same day the owner settled the remaining recommendations of this design after each was explained. The owner answered "D2 ok", "D4 ok", and "D5 ok". For D3 the owner accepted the 10 GiB default of `workspaceSizeLimitBytes` and, after asking what the change to `ephemeral-storage` involves, accepted that the controller renders each disk-backed volume's `sizeLimit` and an `ephemeral-storage` request equal to their sum, and that the ResourceQuota defaults of [§17.8.2](../../spec/17_deployment-topology.md#1782-capacity-tier-reference) and the tiered drain caps of [§10.1.7](../../spec/10_gateway-internals.md#1017-prestop-hook-drain) are recomputed. For D6 the owner asked whether a runtime can override the maintenance settings and accepted that it can, at the cost of its own session's next checkpoint. For D9 the owner chose that the pool's value wins, clamped to the deployer's bounds. For D10 the owner confirmed the tracker as designed, with `auto` as the default. For D11 the owner asked to "be a bit conservative" and accepted the slowest observed rates with a margin of 1.5: the adapter pauses only if 1.5 times the estimate fits the budget. For D13 the owner answered "yes" and added: "we must document all the relevant details of this design (and all others)". The owner also accepted the defaults this design chose in revision 14, which are the spool's headroom factor of 2, 2 fallback requests, 16 walker threads, a stagger that covers the whole attempt, and restores that are not queued. The owner required a test on pods with several runtimes before the design is final ("Validation owed" in `steps.md`, item 16).

The same pass applies owner decisions that other designs own. The embedded deployment model is removed, with the in-process broker of revision 13 ([PL-2](../0118-agent-pod-layout/change.md#pl-2-removal-of-the-embedded-deployment-model)). The runtime sees `/workspace` and a disk-backed `/session` on every pod ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). Every git step on a slot repository, the capture copy and restore completion included, runs as the slot UID in the materialization helper ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)), and the supervisor's worker runs asynchronously, so a helper run no longer blocks the broker. Runtimes declare capabilities in place of integration levels ([`0139-runtime-protocol`](../0139-runtime-protocol/decisions.md#decisions), D3). Pre-launched runtimes are removed, so every runtime launches at bind and a slot release launches nothing. runc pools require user namespaces ([PM-1](../0136-placement/change.md#pm-1-node-classes-and-presets)).

Revision 16 applies the owner's decisions of 2026-11-13 that other designs own. The spool volume is sized by one pod-wide `spoolSizeLimitBytes`, of which the adapter uses half and reserves each slot's spool cap ([`0153-workspace-materialization`](../0153-workspace-materialization/decisions.md#open-decisions), O9 as revised). The `lenny-store-fill` init container fills the warm repository stores and their pristine trees, so the adapter runs no git ([`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), decision 61). An idle session whose checkpoint policy is `sealOnly` or `none` stays idle on its pod and ends at the idle timeout ([`0146-session-lifecycle`, "SL-6"](../0146-session-lifecycle/change.md#sl-6-idle-pods-and-dormancy)). `type: mcp` runtimes and service mode are removed ([`0119-agent-runtimes-only`](../0119-agent-runtimes-only/change.md)), so every pod this design checkpoints is an agent pod with slots.
