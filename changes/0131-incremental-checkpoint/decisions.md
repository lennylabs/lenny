# Decisions: 0131 Incremental checkpoints

## Owner's direction

On 2026-11-05 the owner wrote: "we definitely need to improve checkpointing with a re-design." The owner supplied pointers from another conversation, which "Starting points" evaluates.

On the same day the owner accepted the recommended `checkpointPolicy` values (IC-8, [decision D8](#decisions)), in the words "your recommendation makes sense", and added: "I think a runtime/pool should be able to override the default checkpoint interval if possible."

The owner then asked for measurements on AWS, run independently of the project's test infrastructure, with repositories fetched from the internet, and scoped to "how long it takes to checkpoint and transfer". For the follow-up runs the owner wrote: "Depending on the results, and if needed to find a good solution, try different combinations. If 4 helps, then it should be documented for deployers. Make sure to measure performance impacts of 5." Item 4 is the gVisor KVM platform, and item 5 is the inotify change tracker. The owner added: "Once we're done with the tests and decisions, make sure the design doc includes changes/updates to Lenny's docs, with maybe a new section for checkpointing, with actual benchmarks and all the levers operators and tenants can use to reduce the impact when needed (including things like disabling checkpointing or changing the frequency, running on runc in a dedicated pool (tenant pool), etc.)"

Asked whether the default pause budget should be 5 s or 10 s, the owner chose "10 s default" ([decision D7](#decisions)). The same day the owner asked for the Kubernetes checks in "Benchmarks": "Test --file-access-mounts=exclusive with ConfigMaps etc. Test emptydir_mode = "block-plain"'s interaction with the kubelet's emptyDir size limit."

Asked whether the platform has a way to stop a runtime that does not quiesce, such as the cgroup freezer, which suspends every process in a container's control group, the owner answered: "no, I don't want the forcing mechanism, thanks". Quiescence therefore stays cooperative. A quiescing runtime pauses itself on `checkpoint_request`, and every other runtime is captured on the best-effort path while it runs.

On 2026-11-08 the owner accepted, in the word "ok", the recommended placement of the settings this design names with defaults ([decision D14](#decisions)). The pack format and capture settings are constants that the specification states, `checkpointConcurrency` is a gateway setting from the chart, and `restoreConcurrency` is an adapter setting that the controller passes from the chart to every agent pod.

On 2026-11-09 the owner settled that the embedded `SIGSTOP` checkpoint path of §4.4.3 is removed, and that this design states the removal ([decision D15](#decisions), IC-9). [`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md) had proposed to amend that path for quarantined pods, and it drops the amendment.

On 2026-11-12, after three spikes that checked this design against [`0145-session-isolation`](../0145-session-isolation/change.md), the owner settled that design's decisions D8 and D9. Under SI decision D8 each slot container mounts its whole workspace volume with no `subPath`, a separate volume that only the adapter mounts holds the spool and the export staging, and the warm clones are mounted read-only at the same absolute path in the adapter and in every slot. Under SI decision D9 the adapter reaches every slot file through the runtime supervisor's file-descriptor broker, the `fs` request on `CH-SUPERVISE`, the owner accepted about 470 added lines in the C supervisor, and all checkpoint logic stays in the adapter. The owner asked that this design and the other designs that handle session files be updated, and that the checkpoint design then get a full validation with performance measurements like the AWS benchmarks of 2026-11-05 and 2026-11-06. Revision 13 applies the update, and "Benchmarks", "Validation owed" in `change.md` states the validation.

The validation ran on AWS on 2026-11-12, and a second run the same day measured Kata `block-plain` with a dedicated `fsGroup` and the parallel stat walk ("Re-validation through the broker"). On those numbers the owner settled the open decisions of revision 13 the same day: "D16: adopt `statat`", "D17: keep the tracker off on 9p under auto", "D18: copy-mode freeze for files within the export share", and "The tracker can be enabled on Kata virtio-fs" ([decisions D16 to D18](#decisions)). The owner directed three fixes without a decision: FIFOs on gVisor's default mount are recorded as metadata-only, the spool's `sizeLimit` sits above the adapter's cap and any single clone is bounded by the slot's remaining share, falling back to reading in place, and the 4 GiB constant-write clone that took 11 s against 2 to 2.5 s before is recorded as an investigation owed.

The owner then asked for a faster broker walk, "with a specific concern about directories holding very large numbers of files and about timeouts", and settled it as option (b): the adapter stats in parallel relative to broker-passed directory descriptors, falls back to the broker's `statat` only on `EACCES`, and the supervisor forks no broker workers ([decision D19](#decisions)). The owner also decided to "stagger checkpoints across slots: at most one slot checkpointing at a time per pod, the others queued", as a decision of this design, with a measurement later ([decision D20](#decisions)).

On 2026-11-13 the owner asked for cross-session deduplication as an optimization, possibly as an opt-in per tenant. A study found that sharing chunks between sessions lets a session probe what other sessions hold, through the pod's network byte counters on every isolation profile, checkpoint timing, or the quota. The owner chose a hybrid: only files the platform staged, from warm repository stores and from a runtime's shared assets, are deduplicated, with one set per source and no key by commit ([decision D1](#decisions), IC-4, "Platform chunk sets").

The same day the owner settled the remaining recommendations of this design after each was explained. The owner answered "D2 ok", "D4 ok", and "D5 ok". For D3 the owner accepted the 10 GiB default of `workspaceSizeLimitBytes` and, after asking what the change to `ephemeral-storage` involves, accepted that the controller renders each disk-backed volume's `sizeLimit` and an `ephemeral-storage` request equal to their sum, and that the ResourceQuota defaults of [§17.8.2](../../spec/17_deployment-topology.md#1782-capacity-tier-reference) and the tiered drain caps of [§10.1.7](../../spec/10_gateway-internals.md#1017-prestop-hook-drain) are recomputed. For D6 the owner asked whether a runtime can override the maintenance settings and accepted that it can, at the cost of its own session's next checkpoint. For D9 the owner chose that the pool's value wins, clamped to the deployer's bounds. For D10 the owner confirmed the tracker as designed, with `auto` as the default. For D11 the owner asked to "be a bit conservative" and accepted the slowest observed rates with a margin of 1.5: the adapter pauses only if 1.5 times the estimate fits the budget. For D13 the owner answered "yes" and added: "we must document all the relevant details of this design (and all others)". The owner also accepted the defaults this design chose in revision 14, which are the spool's headroom factor of 2, 2 fallback requests, 16 walker threads, a stagger that covers the whole attempt, and restores that are not queued. The owner required a test on pods with several runtimes before the design is final ("Validation owed" in `change.md`, item 16).

The same pass applies owner decisions that other designs own. The embedded deployment model is removed, with the in-process broker of revision 13 ([PL-2](../0118-agent-pod-layout/change.md#pl-2-removal-of-the-embedded-deployment-model)). The runtime sees `/workspace` and a disk-backed `/session` on every pod ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)). Every git step on a slot repository, the capture copy and restore completion included, runs as the slot UID in the materialization helper ([WM-10](../0153-workspace-materialization/change.md#wm-10-git)), and the supervisor's worker runs asynchronously, so a helper run no longer blocks the broker. Runtimes declare capabilities in place of integration levels ([`0139-runtime-protocol`](../0139-runtime-protocol/decisions.md#decisions), D3). Pre-launched runtimes are removed, so every runtime launches at bind and a slot release launches nothing. runc pools require user namespaces ([PM-1](../0136-placement/change.md#pm-1-node-classes-and-presets)).

Revision 16 applies the owner's decisions of 2026-11-13 that other designs own. The spool volume is sized by one pod-wide `spoolSizeLimitBytes`, of which the adapter uses half and reserves each slot's spool cap ([`0153-workspace-materialization`](../0153-workspace-materialization/decisions.md#open-decisions), O9 as revised). The `lenny-store-fill` init container fills the warm repository stores and their pristine trees, so the adapter runs no git ([`0127-egress-and-git`](../0127-egress-and-git/decisions.md#decisions), decision 61). An idle session whose checkpoint policy is `sealOnly` or `none` stays idle on its pod and ends at the idle timeout ([`0146-session-lifecycle`, "SL-6"](../0146-session-lifecycle/change.md#sl-6-idle-pods-and-dormancy)). `type: mcp` runtimes and service mode are removed ([`0119-agent-runtimes-only`](../0119-agent-runtimes-only/change.md)), so every pod this design checkpoints is an agent pod with slots.

## Open decisions

The M3 readiness review of 2026-11-19 raised D24 to D35, and its second pass raised D36 to D39 as the counterparts of decisions that other changes of the program hold. Each continues the numbering of "Decisions" and moves there with the owner's answer.

1. **D24. The trust source for seeding the file index at adoption, and the trust point for a contribution's reads.** IC-4, **Adoption.**, seeds the file index of a session's adopted files from the contribution recorded for the staged commit, which another pod may have written, and pre-copy then keeps the seeded chunk list without reading the file. A contribution whose chunk list does not match this pod's bytes, whether written by a pod compromised before its first bind or produced by a byte difference between checkouts, makes every snapshot of the session record the contribution's content for those paths, and S4 cannot detect it because each chunk matches its own ID; S8 and "Residual risks" claim the worst outcome is a failed restore. Step 1 of **Who adds chunks.** and S6 also trust the broker's replies during the contribution because no session code has run, while `prestage` has already run the pinned git as the slot UID over warm-list repositories, tenant repositories included, and a process that escapes a `prestage` run can survive into the next session (pod-structure-C2, which `0145-session-isolation` and `0153-workspace-materialization` record). Options: (a) seed only from the pod's own read and chunking of its staged tree, outside the pause, with one read per re-staged tree on a reused pod or seeding only at a never-launched pod's first staging, and move the trust point to the first worker run in the slot, `prestage` included, so that the contribution's reads take S6's descriptor checks; (b) drop seeding, so the first pre-copy reads every adopted file outside the pause while dedup still avoids the upload, and move the trust point as in (a); (c) keep the current rules and state the residual in S8. Recommendation: (a), because it removes the cross-tenant integrity path and keeps most of the first pre-copy saving, and the slot-level question of whether each slot's tree is read or the pod-local identity is accepted is settled with it. It blocks 0131.S4 and the S6 text that 0131.S1 builds against, and it needs the matching statements in SIR-22 of `0145-session-isolation` and WM-15 of `0153-workspace-materialization`. The matching decisions are O24 of `0145-session-isolation` and O11 of `0153-workspace-materialization`, and S6's trust point follows the answer they share. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p1-F1, checkpoint-workspace-C11, pod-structure-C2)
2. **D25. How the pack lease relates to the interval at which a failed attempt is retried.** An `unreferenced` pack keeps its lease for `packLeaseSeconds` (1800 s) from confirmation, pool admission ties that lease only to `checkpointAttemptTimeoutSeconds` and `exportTimeoutSeconds`, and a failed periodic attempt is retried at the session's next interval, which the deployer's bound allows up to 3600 s (`schedule.go` in `pkg/gateway/core/checkpoint/checkpointer`). A timed-out attempt sends no `SnapshotReady`, so with an effective interval above about 1500 s its confirmed packs expire before the next attempt, and a first checkpoint that needs several attempts never completes, against R3 and IC-7, **Attempt deadline.** Options: (a) `CheckpointStart` and `Resume` extend the lease of each leased pack they list, which alone does not help once the packs have expired before the next attempt; (b) a failed or timed-out attempt is retried after a backoff of about one `checkpointAttemptTimeoutSeconds`, independent of the interval, which the existing admission rule already covers; (c) pool admission requires `packLeaseSeconds` of at least the largest effective interval plus the attempt timeout; (d) (a) combined with (b) or (c). Recommendation: (d) with (b), because the retry then always falls inside the lease the admission rule guarantees, and the extension keeps a long first checkpoint's packs alive across many retries. It blocks 0131.S4 (lease), 0131.S7 (attempt deadline), and 0131.S8 (interval). (raised by the M3 readiness review, 2026-11-19; sources: 0131-p1-F2, downgraded to Medium by the skeptic)
3. **D26. The order of the pod-wide checkpoint queue for seals, eviction checkpoints, CheckpointBarrier attempts, and the disk watch's checkpoint.** IC-1, "Staggering across slots", starts queued attempts in arrival order, and a running attempt holds the queue for up to `checkpointAttemptTimeoutSeconds`, 300 s by default. A seal's wait counts against its seal window, 300 s by default, and a seal that outlasts the window relabels the session `failed` with `workspace_seal_timeout`, so on a multi-slot pod the session's final changes can be lost. The agent-pod grace floor counts one capped checkpoint per slot and no periodic attempt already running when the preStop hook starts. The disk watch's best-effort checkpoint, which `0146-session-lifecycle` (SL-2) and `0118-agent-pod-layout` (PLR-23) add, would wait in the same queue while the slot's runtime keeps writing toward the kubelet's eviction of the whole pod; `0118-agent-pod-layout` records that part as its O12. Decision D20 settled serialization, and arrival order was the writer's default rather than the owner's words. Options: (a) seal, eviction, CheckpointBarrier, and disk-watch checkpoints go to the front of the queue, and a seal, a drain, or a disk-watch trip cancels a running periodic attempt of another slot, whose confirmed packs the next attempt reuses (this depends on D25); (b) priority without cancellation, with the grace floor and the seal window each counting one `checkpointAttemptTimeoutSeconds`, which at the defaults also needs a larger seal window or a shorter attempt timeout; (c) keep arrival order. In each option a new attempt for a slot that already has one running or queued joins it. Recommendation: (a), because it is the only option that keeps the seal and the eviction checkpoint inside their budgets at the defaults. It blocks 0131.S1, 0131.S5, and 0131.S7, and the disk-watch step of `0118-agent-pod-layout`. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p1-F3, checkpoint-workspace-C5)
4. **D27. Which step owns the capture copy and restore completion wiring, given that 0131.S1 and 0153.S4 each need the other.** IC-1, **Capture copy.**, runs the helper's `capture-copy` before every pre-copy, and IC-5 runs `restore-complete` after a restore; [0153.S4](../0153-workspace-materialization/steps.md#steps) builds both subcommands and depends on 0131.S1. An edge from 0131.S1 or 0131.S5 to 0153.S4 would close a cycle, and the `integration` test that runs `capture-copy` before pre-copy has no step that can pass it. This is a disagreement between this change and `0153-workspace-materialization`, which records it too. Options: (a) a new or reshaped step of `0153-workspace-materialization`, ahead of 0131.S1, builds `capture-copy` and `restore-complete`, and 0131.S1 and 0131.S5 depend on it; (b) 0153.S4 lands the adapter's calls to both subcommands itself, owns the `integration` test, and drops 0131.S1 from its depends-on, with 0131.S1 leaving the hook; (c) 0131.S1 and 0131.S5 carry `0153.S4 (part)` edges scoped to the calls, which leaves a cycle through a part edge. Recommendation: (a), which the consistency review recommends, because it orders the helper before both of its callers without a part-edge cycle. It blocks 0131.S1 and 0131.S5. (raised by the M3 readiness review, 2026-11-19; sources: checkpoint-workspace-C2, 0131-p1-F5, 0131-p2-F3)
5. **D28. The order of 0131's steps against 0139.S1, the prerequisites of the platform chunk sets, and 0128.S4, which 0135.S4's edges to every 0131 step make cyclic.** [0135.S4](../0135-message-delivery/steps.md#steps) depends on 0131.S1 to 0131.S7 as whole edges. Through it, three edges this change needs would close cycles: 0131.S1 on [0139.S1](../0139-runtime-protocol/steps.md#steps) (the `checkpoint` capability and the quiesce frames on `CH-MSGSOCK`; 0139.S1 depends on 0135.S5, which depends on 0135.S4), 0131.S4 on 0147.S8, 0140.S1, and 0153.S8 (the warm stores, the pod set keys, and the warm-up checkout that the platform chunk sets read), and 0131.S6 on [0128.S4](../0128-forensics-evidence-preservation/steps.md#steps) (`EnsureCopied` and the escrow prefix; 0128.S4 waits in part on 0135.S4). This involves `0135-message-delivery`, `0139-runtime-protocol`, `0147-tenant-derived-runtimes`, `0140-runtime-revisions`, `0153-workspace-materialization`, and `0128-forensics-evidence-preservation`. Options: (a) 0135.S4 narrows its edges to the 0131 steps whose code its export path calls, as `(part)` entries that name the export path, which removes all three whole-edge cycles; (b) this change splits the platform chunk sets of IC-4 and IC-6 into a new step that depends on 0147.S8, 0150.S2, 0140.S1, and 0153.S8, 0131.S1 lands its handshake on the runtime connection of the tree and 0139.S1 moves the frames as its O7 (a) states, and 0131.S6 keeps the 0128.S4 order as a sentence; (c) keep every one of these orders as a sentence. Recommendation: (a), because 0135.S4's whole edges are the common link of the three cycles, and (b) can follow for the platform chunk sets if the owner wants them to land separately. It blocks 0131.S1, 0131.S4, and 0131.S6. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p1-F5, 0131-p2-F3, checkpoint-workspace-C7)
6. **D29. Suspended and blocked sessions under `checkpointPolicy: sealOnly` or `none` keep their pod while the concurrency caps do not count them.** IC-8's policy table keeps a suspended session's pod under `sealOnly` and `none` and does not take the release after `maxSuspendedPodHoldSeconds`. `0146-session-lifecycle` excludes `suspended` and `blocked` from the caps (SL-10) and releases the pod at `maxSuspendedPodHoldSeconds` with no exception for these policies. Read together, a client can suspend sessions and start more, and each suspended session holds a warm pod's slot for up to `maxSuspendedSessionSeconds`, 7 days, without counting against a cap. This is a disagreement between this change and `0146-session-lifecycle`, which records it too. Options: (a) a paused session that holds its pod counts against the caps under every policy; (b) under `sealOnly` and `none` a suspension that lasts `maxSuspendedPodHoldSeconds` ends the session as `expired` after its seal; (c) keep the pod and add a per-tenant cap on paused sessions that hold a pod. Recommendation: (a), because it keeps the policy's promise to the runtime author and closes the hoarding path with the cap that already exists. Whichever option is taken, IC-8's table and 0146's timer row state the same outcome. It blocks 0131.S8. (raised by the M3 readiness review, 2026-11-19; sources: checkpoint-workspace-C1)
7. **D30. How a session under `sealOnly` or `none` resumes after it loses its pod.** IC-8's table says a pod failure or an eviction resumes the session with `resumeMode: conversation_only` and `workspaceLost: true` from the §4.4.5 minimal state record. That record is written only when an eviction checkpoint fails, which these policies never take, and a `node_lost` or `runtime_crash` writes none, so §7.3 step 3e, SL-6 of `0146-session-lifecycle`, WM-13 of `0153-workspace-materialization`, and D19 of `0140-runtime-revisions` send such a session through the snapshotless rebuild, which reruns setup commands and carries no conversation state. This is a disagreement with those changes. `0146-session-lifecycle` records it as SL-Q8 and `0153-workspace-materialization` as O18. `0140-runtime-revisions` records no counterpart, because its RV-6 sends a session that has neither a checkpoint nor a minimal state record through the snapshotless rebuild, which holds under either option, so the answer changes this change and 0146. Options: (a) under `sealOnly` and `none` the preStop path and the pod-failure path write the minimal state record without a checkpoint, so IC-8's statement holds and SL-6 names the case; (b) IC-8 adopts the snapshotless rebuild for these policies and drops `conversation_only` from its table and its documentation. Recommendation: (a), because it keeps the conversation that a runtime author who chose `sealOnly` expects to survive. It blocks 0131.S8. (raised by the M3 readiness review, 2026-11-19; sources: checkpoint-workspace-C4)
8. **D31. Which step builds the generation fence on `Checkpoint` and `Resume`.** S5 bounds a compromised pod's chosen bytes across a coordinator handoff on the assumption that the pod refuses the previous coordinator's RPCs once it acknowledges the new fence. In the tree the adapter's `Checkpoint` and `Resume` handlers do not compare `coordination_generation` (issues CHGWPOD-I7 and CHGWPOD-I13, both open with no planned step), so a stale replica can open a new `Checkpoint` stream and sign grants after the fence, and the bound does not hold. The reviewers differed on whether the assignment needs the owner. Options: (a) 0131.S3 closes CHGWPOD-I7 and 0131.S5 closes CHGWPOD-I13, with a `contract` case that a `Checkpoint` stream older than the acknowledged fence receives no grant and a `chaos` case for `Resume`; (b) a step of another change that owns the gateway-to-pod fence closes both, as 0133.S2 does for CHGWPOD-I9, I12, and I15, and 0131.S3 and 0131.S5 depend on it. Recommendation: (a), because 0131.S3 rewrites the `Checkpoint` stream and 0131.S5 the restore that `Resume` drives. It blocks 0131.S3 and 0131.S5. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p2-F4, 0131-p1-F6)
9. **D32. How the adapter's memory and the spool hold one file index per slot.** "Costs" puts the index at about 128 bytes per file and states that the adapter's memory limit has to leave room for one index per slot, while the re-validation measured 1.0 to 1.3 GiB of adapter memory with Chromium's index and 2.0 GiB after a package install. `0121-billing-resource-attribution` gives the adapter a fixed chart value, `adapterResources`, and `0118-agent-pod-layout` costs the adapter at about 50 MB. At 128 bytes per file, a 10 GiB workspace of 3,000,000 small files needs a 384 MiB index on the spool, inside a 512 MiB cap of which export clones may take 256 MiB. No change says what happens when an index does not fit, and an adapter killed for memory ends every slot's session. Options: (a) the controller adds a per-slot index allowance to the adapter's memory request, derived from `workspaceSizeLimitBytes` or a new pool setting, and the resource-class mapping of `0121-billing-resource-attribution` accounts for it; (b) the index lives on the spool with bounded resident memory and a cap on indexed entries per slot, and an attempt over the cap takes a stated outcome, such as a walk without an index or a refusal with a metric. Recommendation: (b) with an explicit entry cap, plus a request to `0121-billing-resource-attribution` to document `adapterResources` sizing per slot. It blocks 0131.S1 and 0131.S7. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p2-F6)
10. **D33. Which step builds the agent pod's eviction checkpoint trigger.** IC-7 replaces the tiered drain caps with `evictionCheckpointCapSeconds` per slot for the agent pod's eviction checkpoint, and the `e2e_kind` and `chaos` tests assert it. In the tree an agent pod's preStop hook does not signal its coordinating replica, so an evicted pod's sessions get no eviction checkpoint, and no member step builds the signal or the checkpoint it drives (issues CHGWPOD-I2, CHPODGW-I1, and CHPODGW-I2). The reviewers differed on whether the assignment needs the owner. Options: (a) 0131.S7 closes the three issues and IC-7 states that the agent pod signals its coordinating replica on `CH-ADAPTEREVENTS` before the per-slot caps apply; (b) a new step of this change, on which 0131.S7 depends, closes them; (c) a step of another change closes them and 0131.S7 depends on it. Recommendation: (a), because this change is the only member that changes this path. It blocks 0131.S7. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p2-F5, 0131-p1-F6)
11. **D34. The format of `checkpointExcludes` entries.** Decision D5 adopts a runtime-declared list of regenerable directories such as `node_modules/`, with a tenant's entries appended on a derived runtime, and IC-8 delivers the list to the adapter. No change states whether an entry is a path relative to a tree root or a directory-name pattern that matches at any depth, which tree it applies to, the limits on entry count and length, or how a tenant-written entry is validated, and the list crosses a trust boundary into the adapter. A root-relative path does not cover a nested `node_modules/`, which is the common case. Options: (a) each entry is a directory path relative to the root of `/workspace`, with no `..`, no absolute path, and no wildcard, matched at that path only; (b) each entry is either a single directory name, which matches a directory of that name at any depth in `/workspace`, or a relative directory path as in (a), with no wildcard; (c) as (b), applied to `/session` as well. In each option the write is refused with `400 VALIDATION_ERROR` when an entry breaks the syntax or the list exceeds bounds the specification states, such as 64 entries of at most 256 bytes. Recommendation: (b), because the regenerable directories the decision names nest, and a name match needs no wildcard engine in the adapter. It blocks 0131.S1 and 0131.S8. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p1-F7)
12. **D35. A bound on the entry count and path bytes of a manifest that the gateway renders as a download.** IC-5, "Download", bounds a manifest by the sum of its workspace entry sizes, `workspaceSizeLimitBytes`, and by nothing else. A compromised pod's manifest of many empty entries or long paths costs gateway CPU and memory on every download of its own session; the reviewer marked the impact unverified and limited to the tenant's own requests. Options: (a) the gateway also refuses a manifest whose entry count or total path bytes exceed bounds the specification states; (b) the gateway renders the download as a stream with bounded memory and accepts the CPU cost as the tenant's own; (c) no change. Recommendation: (a), with bounds derived from the largest workspace the measurements covered. It blocks 0131.S5. (raised by the M3 readiness review, 2026-11-19; sources: 0131-p1-F21)
13. **D36. What the slot's runtime does while the disk watch's trip takes its best-effort checkpoint, and how that checkpoint starts and queues.** IC-1, "Staggering across slots", and IC-8's `full` row list the disk watch's checkpoint as a trigger with the `trigger` value `disk_watch`, and every checkpoint starts from the gateway's `CheckpointStart` and waits in the pod-wide queue under the attempt deadline, 300 s by default. PLR-23 of `0118-agent-pod-layout` and "SL-2" of `0146-session-lifecycle` have the adapter take that checkpoint before it ends the slot's session, and "SL-2" defers the checkpoint's start and deadline to IC-1 and IC-8, which do not yet state them or what the runtime does while the checkpoint runs. On a pod with several slots, and on a volume that no project quota bounds, a session can write past the threshold while its checkpoint waits, and the kubelet then evicts the pod and ends every slot's session. Options: (a) the adapter ends the slot's runtime processes with the release's first End, the gateway then starts the best-effort checkpoint of the quiesced volumes as a `disk_watch` trigger that skips the queue and runs under a short time cap, and the session ends `failed`; (b) as (a), with the slot frozen in place of ending its runtime processes; (c) the checkpoint keeps its order and queues like any other trigger with a short deadline, and is abandoned when use passes a second threshold; (d) accept the eviction risk and state it in 0118's "Limits". Recommendation: (a), because a runtime that has ended cannot write past the threshold and an End is already the release's first step. Under (a) or (b), the disk-watch part of D26 falls away, and D26 orders seals, eviction checkpoints, and CheckpointBarrier attempts only. IC-1 and IC-8 then state the trigger's start, its cap, and its exemption, and 0118 and 0146 state the order by reference to them. It blocks 0131.S1 and 0131.S8, and the step that lands the disk watch. The matching decision is O12 of `0118-agent-pod-layout`. (raised by the M3 readiness review, 2026-11-19; requested by change 0118, and by change 0146 for its "SL-2"; sources: 0118-F5, checkpoint-workspace-C5)
14. **D37. The usable size of a slot volume, against which this change's size checks compare.** PLR-23 of `0118-agent-pod-layout` trips the disk watch at `adapter.diskWatchThresholdPercent` of a volume's `sizeLimit`, 90% by default, and a project quota stops writes at `sizeLimit` less 2% ("PL-10"). This change's size probe refuses an attempt only when a tree exceeds `workspaceSizeLimitBytes` or `sessionSizeLimitBytes` (IC-3, `CheckpointProbe`), and a restore admits a manifest up to the same limits (IC-5), so a tree between the threshold and the limit passes this change's checks while the disk watch ends its session, or a restore fails with `ENOSPC` on a volume that a project quota bounds. Options: (a) the usable size of a slot volume is `adapter.diskWatchThresholdPercent` of its `sizeLimit`, every size check of this change and of `0153-workspace-materialization` compares against it, and a trip with no session bound discards the staged trees and keeps the slot; (b) the checks stay at `sizeLimit`, and a trip with no session bound fails the slot. Recommendation: (a), because a check that admits what the watch then fails gives the deployer a limit that does not hold. It blocks 0131.S5 and 0131.S7, and the step that lands the disk watch. The matching decision is O13 of `0118-agent-pod-layout`. (raised by the M3 readiness review, 2026-11-19; requested by change 0118; sources: 0118-F6)
15. **D38. How the platform tenant exists in Postgres so that the `artifact_store` rows of platform-owned packs can name it.** IC-4, "Quota", records each confirmed pack of a platform-owned chunk set under the platform tenant, `platform`, and stores the packs under `/platform/chunk-sets/{source_id}/packs/{pack_id}`. The tree has no `tenants` row and no billing sequence for `platform`, and `artifact_store` and `billing_events` both reference `tenants(id)`. Options: (a) a reserved `tenants` row and a billing sequence created by migration, excluded from tenant lists, authentication, quota, erasure, and tenant deletion, with the storage reconciliation listing the `/platform/` prefix; (b) a separate operator-cost table and stream outside `artifact_store` and `billing_events`. Recommendation: (a), because it keeps one ledger and one reader. Under (a), 0131.S4 names the migration that provisions the platform tenant and states that the reconciliation lists `/platform/`. It blocks 0131.S4. The matching decision is decision 25 of `0121-billing-resource-attribution`, which `0140-runtime-revisions` also reads. (raised by the M3 readiness review, 2026-11-19; requested by change 0121; sources: 0121-F3)
16. **D39. Which change builds the output-file export stream and its tables.** IC-3 and IC-4 define `ExportOutputFile`, its messages, `CH-OUTPUTFILE`, `output_files`, `output_file_packs`, and `output_file_exports`, and "MD-18" of `0135-message-delivery` defines them too, and neither step list says which step builds them. 0131.S3 would build the stream before 0135 has a file part to drive it, and 0135.S4 depends on 0131.S3 and 0131.S4. Options: (a) this change's steps build the shared pack messages, the catalog, and reclamation, and 0135.S4, or its export part, builds `ExportOutputFile`, `CH-OUTPUTFILE`, and the three output-file tables, with IC-3 and IC-4 marking those parts as landing with it; (b) 0131.S3 and 0131.S4 build them, and 0135.S4 builds only the part handling and the adapter's freeze. Recommendation: (a), because the export stream serves file parts, which 0135 defines, and the shared pack machinery stays with this change. The answer also bears on D28, because under (a) 0135.S4's edges to this change's steps narrow to the shared machinery. It blocks 0131.S3 and 0131.S4. The matching decision is O10 of `0135-message-delivery`. (raised by the M3 readiness review, 2026-11-19; requested by change 0135; sources: 0135-p1-F11)
