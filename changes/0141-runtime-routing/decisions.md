# Decisions: 0141 Runtime routing

## Open decisions

The M3 readiness review of 2026-11-19 raised D19 to D24. Each entry states the question, the options, a recommendation, and what it blocks.

| ID | Question | Recommendation |
| :-- | :-- | :-- |
| D19 | Which runtime do the playground's `playground.allowedRuntimes` boundary, the §27.6 playground caps, and the §14 envelope (`limits.maxSessionAge`) judge once a route or an interceptor moves a session? Today `createAdmissionGates` runs `requirePlaygroundRuntimeVisible` on the requested name, which its comment calls an authorization boundary (F-27.4.1), and the create path validates the envelope and applies the caps before the chain (F-4.8.26, open). A `tenant-admin` route from a name the playground allows to a runtime it does not allow moves a playground session past the operator's list. (a) Judge all three on the final runtime at the post-chain point. (b) Judge playground visibility on the requested name before the chain, as today, and on the final runtime at the post-chain point, and judge the caps and the envelope on the final runtime. (c) Keep all three on the requested name before the chain, which leaves F-4.8.26 open and the route bypass in place. | (b). The playground picker shows names, so the name a caller asks for must be visible to it, and the runtime that runs must be allowed. Under (a) or (b), the post-chain table gains a row for the three checks, and 0141.S1 closes F-4.8.26 in part, with [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) RV-7 closing its `runtimeOptions` part. Blocks: the list of checks 0141.S1 moves to the post-chain point, and its `closes` field. (raised by the M3 readiness review, 2026-11-19; sources: 0141-F4) |
| D20 | How do the gateway replicas read the route store, and what does the route interceptor do when the store cannot be read? The design states that deleting a route "stops routing at once" and tests that "the route store's cache stays consistent during weight updates", but defines no read path, no invalidation across replicas, and no bound, so two replicas can place the same `key: user` user on different targets during an update, against RTR-4. Built-in interceptors have no stated `failPolicy`. Options for a read failure: (a) fail closed and refuse the create with `503`; (b) fail open and create on the requested runtime with no route labels; (c) serve the last routes the replica read, up to a stated bound, and then (a). The read path is a per-create read or a cache with an invalidation channel across replicas and a staleness bound, and "at once" becomes that bound. | (c), with a cache that each route write invalidates on every replica and a staleness bound stated in "RT-4". Routes are small, and a fail-open placement on the requested runtime breaks a split without a signal. Blocks: the route interceptor and `routestore` in 0141.S2, the `load_local` cache test, and the `chaos` case for a store outage. (raised by the M3 readiness review, 2026-11-19; sources: 0141-F9) |
| D21 | What happens to a session of a tenant that a registration does not list, when a `DelegationPolicy` that applies to it names that scoped interceptor in `contentPolicy.interceptorRef`? "RT-6" says the policy "applies it only to sessions of the listed tenants", which built as a skip lets delegations of unlisted tenants pass `PreDelegation` and `PreExportMaterialization` with no content scan. Today `RunPolicyScoped` fails closed when the referenced interceptor is absent (`pkg/policy/interceptor/interceptor.go`). (a) Fail closed, as for an unregistered reference. (b) Skip the interceptor and emit an audit event. (c) Refuse at write time every policy that can apply to a session of an unlisted tenant, and fail closed at run time for any that remains. | (c). It keeps today's fail-closed rule for a content scanner the gateway cannot apply and stops such a policy at the point where an admin can fix it. Blocks: "RT-6" **Policy references.**, 0141.S4, and its `security` tests. (raised by the M3 readiness review, 2026-11-19; sources: 0141-F12) |
| D22 | How does route admission judge an alias name against the tenant view of [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md)? "RT-4" refuses an alias that names a runtime outside the tenant view, which needs to know that another tenant's `--` name or an unshared platform runtime exists. 0147's DP2 and DP3 forbid that read across tenants and require one answer for an absent name and another tenant's name, so the rule would give a `tenant-admin` an oracle for other tenants' runtime names, and 0147 DR-8 states no alias rule. The conflict is recorded on 0147 as well, as its open decision 49 ([`0147-tenant-derived-runtimes`, "Decisions"](../0147-tenant-derived-runtimes/decisions.md)). (a) Admission reads only the tenant view; an alias name containing `--` must carry the writer's own `namePrefix`; any other name that is absent or unreachable gets the same answer, either accepted as an alias or refused with one code for both cases. (b) Refuse every alias whose name contains `--`, and accept other names absent from the tenant view. (c) Keep the rule of "RT-4" and accept the oracle, which contradicts DP3. | (a). It keeps admission inside the tenant view and gives one answer for both cases, as DP3 requires. Blocks: "RT-4" **Aliases.**, route admission in 0141.S2, and the alias rule of 0147 DR-8. (raised by the M3 readiness review, 2026-11-19; sources: runtime-contract-C9) |
| D23 | How is 0141.S2 split? It holds the removal across the gateway, the admin API, the PoolScalingController, the adapter, the proto, the Go, Python, and TypeScript runtime SDKs, the alerts, the migrations, erasure, and the documentation, and also the route resource, aliases, discovery, and routing labels. The route interceptor and the `ExperimentRouter` both sit at priority 300, so a step that adds routes while the router remains needs a rule for the two. (a) Keep 0141.S2 as one step. (b) Split by layer: 0141.S2 lands routes, routing labels, aliases, and discovery together with the removal of the `ExperimentRouter` and the experiment and eval surfaces of the gateway and the admin API and the migration, so the route interceptor replaces the router in one branch; a new step removes the experiment code from the PoolScalingController, the adapter, the proto, and the runtime SDKs, and replaces `experimentContext` with `routing` there. (c) Land routes in 0141.S2 beside the `ExperimentRouter`, with a stated order for the two built-ins at priority 300, and remove the router in a later step. | (b). It keeps one built-in at priority 300 at every point and moves the layers that share no code with routes to their own branch. Under (b), the `pkg/gateway/experiment/` packages still leave in 0141.S2, so the edges other changes draw to 0141.S2, such as the bucketing function 0140.S1 uses, the aliases 0138.S1 lists, and the package removals 0117.S13 waits on, keep their target. Blocks: the step layout of 0141.S2 and the edges other changes draw to it. (raised by the M3 readiness review, 2026-11-19; sources: 0141-F8) |

## Decisions

Settled by the owner on 2026-11-08:

| ID | Decision |
| :-- | :-- |
| D1 | Eval storage is removed. |
| D2 | Every feature specific to experimentation is removed, and Lenny keeps no experiment object. |
| D3 | Routes are built in, implemented as a `PreRoute` interceptor against the contract external interceptors follow, and can be turned off and replaced. |
| D4 | Interceptor registration stays with `platform-admin`. Tenant-written interceptors are out of scope. |
| D5 | Interceptors run in the cluster. A deployer reaches a remote service through an in-cluster interceptor or relay of their own. |
| D6 | Interceptor calls do not pass through `lenny-egress`. |
| D7 | An interceptor registration may be scoped to a list of tenants. |
| D8 | Routes match on the requested runtime alone. A deployer who wants rules on session labels writes an interceptor (formerly O1). |
| D9 | A delegated child starts with its parent's routing labels, and the child's chain may change any key (formerly O2). |
| D10 | A `tenant-admin` writes routes for their own tenant, and a `platform-admin` writes routes for any tenant (formerly O3). |
| D11 | `evalRef` is retired. A derive runs the `PreRoute` chain with `kind: derive`, the route interceptor treats it like any creation, and derive's own checks run after the chain (formerly O4). |
| D12 | This design adds no route that applies across tenants. Operator rollouts of a new version of one runtime belong to [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) (formerly O5). |
| D13 | The interceptor changes listed in "RT-2" and "RT-6" beyond the `PreRoute` payload are part of this design: session context on every phase, the payload audit, the last modifier, the scope check on `interceptorRef`, and routing reuse on retry and resume. |

| D17 | A route's requested name may name no runtime, which makes the route an alias, and the models list shows a tenant's aliases. Since 2026-11-14 Lenny's discovery routes carry the aliases and the provider adapters build their models lists from them (R8 of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md)). The per-runtime admission limits move after the chain, so neither an alias nor a route moves a session past them ("RT-4", **Aliases.**, "Before the chain", and "Discovery"). |
