## Open decisions

The owner settled O1 to O7 on 2026-11-12 by accepting each recommendation, with refinements to O4 and O7 (D5), and O8 on 2026-11-13 in a revised form (D12). Egress decision 61 superseded O5 on 2026-11-13 (D11). The owner settled O9 on 2026-11-13 as (a) (D20), and the spike it asked for led to D25 on 2026-11-14. O10, which that spike raised, was settled on 2026-11-14 as (a) (D26). Each settled decision keeps its options and reasoning as the record of the choice.

**O1. How the runtime learns its paths. Settled.**

- (a) Fixed constants that the specification states, with the supervisor starting each runtime process in `/workspace`.
- (b) Environment variables, such as `LENNY_WORKSPACE_DIR` and `LENNY_SESSION_DIR`, set at launch.
- (c) Manifest fields in `/run/lenny/adapter-manifest.json`.
- (d) Constants, plus environment variables that repeat them for discoverability.

**Settled 2026-11-12: (a).** Variables and manifest fields exist so that a value can differ between pods, and these values never differ. A runtime author sets harness variables in the Runtime's `env`, such as `CLAUDE_CONFIG_DIR=/session/claude`, and `env` holds literal values with no expansion ([§5.1](../../spec/05_runtime-registry-and-pool-model.md#51-runtime), **`env`**) **[source]**, so a constant is the only value it can use there. Variables in (b) and (d) invite code that reads them, which then cannot be tested against a second value, and they add a source that can disagree with the mount table. `session_start` keeps `sessionId` as data, `credentialsPath` keeps its field with the constant value `/run/lenny/credentials.json` so that its presence still says whether a credential file exists, and DR-12's `cwd` keeps naming the session's working folder under `/workspace`.

**O2. The rule for files a runtime offers to the user. Settled.**

[§26.2](../../spec/26_reference-runtime-catalog.md#262-shared-patterns-for-coding-agent-runtimes) states that `/workspace/output/` "is provided for agents to write artifacts that should survive session teardown and be recoverable via `GET /v1/sessions/{id}/artifacts`" and that "Agents MUST write intended outputs here", and §26.3 says files under it "are sealed as session artifacts" **[source]**. Nothing in the tree implements either, the directory was a sibling of `/workspace/slots/` that no mount provided, and `GET /v1/sessions/{id}/artifacts` lists catalog rows and reads nothing from the pod ([`0135-message-delivery`, "Current state"](../0135-message-delivery/change.md#tree)) **[source]**. MD-18 exports a file when the runtime emits a `file` part that names its workspace path **[source]**.

- (a) One rule: a file reaches the user as an output file only when the runtime emits a `file` part naming it. The platform defines no output directory. A runtime may keep its own `output/` folder, and it emits a part for each file in it. The whole workspace stays downloadable through `GET /v1/sessions/{id}/workspace`.
- (b) Keep `/workspace/output/` as a platform directory, and have the adapter export every file in it as an output file at session end.
- (c) Both.

**Settled 2026-11-12: (a).** MD-18 already covers every path in the workspace, with its size limit, export cap, freeze, and failure notice, and it lets a runtime offer a file mid-session. Under (b) the seal would export files the runtime never announced, outside MD-18's per-part accounting, and a directory under `/workspace` would be a platform convention nested in a tree that D2 says the platform leaves empty. The reference runtimes adopt (a) in their wrappers.

**O3. The medium of `/tmp`. Settled.**

- (a) Memory-backed, as today, with a `sizeLimit` of 256Mi. The kubelet sizes a memory-backed `emptyDir` to its `sizeLimit`, so a write past it fails with `ENOSPC` rather than evicting the pod **[inference]**. Its pages count against the slot container's hard memory limit (SI O4 (a)).
- (b) Disk-backed with its own `sizeLimit`, inside the per-slot disk watch.

**Settled 2026-11-12: (b).** `HOME` points into `/tmp` under O4, and `HOME` collects package caches for npm, pip, Go modules, and Cargo, which can exceed 256Mi. Under (a) those caches consume the slot's memory, and an out-of-memory kill makes the slot dead for the pod's life ([SI-4](../0145-session-isolation/change.md#si-4-slot-liveness-and-the-slot-count)). Under (b) an overflow is caught by the same disk watch that already guards `/workspace` and `/session`. The cost of (b) is that a write burst that outruns the watch evicts the whole pod, which the watch already risks for `/workspace`, and that scratch data reaches the node disk, which node-level disk encryption covers as it covers `/workspace` ([§6.4](../../spec/06_warm-pod-model.md#64-pod-filesystem-layout), **Data-at-rest protection:**).

**O4. `HOME`. Settled.**

The supervisor starts each launch from an empty environment with a fixed `PATH`, the Runtime's `env`, and the platform's variables, so `HOME` is unset today, and the root filesystem is read-only **[source]**. A tool that writes under `~` therefore fails or writes into a read-only image path.

- (a) The supervisor sets `HOME=/tmp` as a platform variable, and a `HOME` pair in the Runtime's `env` replaces it, as an `env` `PATH` pair replaces the fixed `PATH`.
- (b) `HOME` stays unset, and each runtime sets it in `env`.
- (c) A separate `/home` volume.

**Settled 2026-11-12: (a), with `HOME=/tmp/home`.** The owner's refinement: "HOME=/tmp/home, created by the supervisor, owned by the slot UID, and mode 0700. The runtime `env` can override it. Harness state goes to /session." A home directory of its own, rather than `/tmp` itself, keeps dotfiles and caches out of the scratch directory that other tools list and clean, and mode `0700` matches what tools such as `ssh` require of a home. It gives every tool a writable home that the slot release sweeps and no checkpoint carries, which is where package caches belong. (b) leaves each runtime author to find the same answer. (c) adds a path outside D2's list.

**O5. Who fills the repository stores. Settled.**

[SI-1](../0145-session-isolation/change.md#si-1-pod-layout) lists "the warm-clone fill, the init step that fills `lenny-warm-clones` before any regular container starts, as spike 2 ran it" **[source]**. DR-11 has the adapter fill each store before the pod reports ready, through `netagent`, and has the adapter delete a withheld store before anything runs for a session ([`0147-tenant-derived-runtimes`, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores)) **[source]**.

- (a) The adapter fills the stores, as DR-11 states, on `lenny-git-stores` mounted read-write at `/adapter/git-stores`, running the pinned git from `lenny-bin` mounted read-only at `/adapter/bin`.
- (b) An init container fills the stores under its own UID, as SI-1 states.

**Settled 2026-11-12: (a).** Under (b) the stores' files and directories belong to the init container's UID, which no running container holds, so the adapter cannot delete a withheld store, and §13.1 reserves the adapter UID for the container named `adapter` ([§13.1](../../spec/13_security-model.md#131-pod-security), **Container identity.**) **[source]**. A bare store records no absolute path, so it serves alternates at `/lenny/git-stores` in the slots although the adapter wrote it at `/adapter/git-stores` **[inference]**. SI O11 forbids the adapter git work on slot repositories, and the fill works on stores, which no slot can write.

**Superseded 2026-11-13 by D11.** The egress design's decision 61 found that the fill parses untrusted git input at the adapter UID, against the materialization design's rule that no platform-privileged process parses untrusted content, and the owner chose a separate `lenny-store-fill` container. The reason (b) was rejected, that no running container could delete a withheld store, is answered by the adapter's read-write mount, which it uses only to delete: `lenny-store-fill` writes with a dedicated store GID as its group and group-writable directories, and the adapter, whose primary group is the same GID, can unlink what the fill wrote ("PL-3", D17).

**O6. Where the new size limits are set. Settled.**

- (a) Pool settings beside `workspaceSizeLimitBytes`: `sessionSizeLimitBytes`, 256Mi by default, and `tmpSizeLimitBytes`, 1Gi by default under O3 (b).
- (b) Chart values for every pool.

**Settled 2026-11-12: (a).** `workspaceSizeLimitBytes` is a pool setting today ([§4.4.4](../../spec/04_system-components.md#444-checkpoint-slos-and-scheduling), **Hard workspace size limit.**) **[source]**, and a harness's transcript size and a toolchain's cache size vary with the runtime that the pool serves. The 256Mi default keeps today's cap for session files ([§6.4](../../spec/06_warm-pod-model.md#64-pod-filesystem-layout)). O7's `shmSizeLimitBytes` joins them, and "PL-9" lists the three settings.

**O7. `/dev/shm` per slot. Settled.**

- (b) One volume for the pod, mounted into every slot container.

**Settled 2026-11-12: (a), with a pool setting for its size.** The owner added "a pool setting for the per-slot /dev/shm size (for example `shmSizeLimitBytes`, default 64Mi), counted in slot memory." **O8. How the per-slot disk watch measures a volume. Settled 2026-11-13 in a revised form (D12).**

On runc, `statfs` on an `emptyDir` reports the whole node filesystem **[measured]**, so the watch cannot read a volume's use from the filesystem. The kubelet counts a volume by walking it, and it counts a reflink clone at its full size **[measured]**. The adapter's own mount cannot descend into a slot-owned directory of mode `0700`, and it does not mount `/tmp` at all.

- (a) A walk through the slot's broker: the adapter walks each watched volume as the checkpoint walks a workspace, listing directories and statting entries in parallel through broker-passed directory descriptors, with the broker's `statat` as the fallback on `EACCES` ([IC-1](../0131-incremental-checkpoint/change.md#ic-1-capture-in-passes), "The walk"). It counts each inode once, at the larger of its logical size rounded up to 4,096 bytes and its allocated blocks, so its figure is never below the kubelet's. The broker gains a `tmp` root for this walk alone.
- (b) Project quotas where the node filesystem has them: the kubelet then assigns each `emptyDir` a project and reads its use from the quota, and the adapter would read the same figure.
- (c) (a) on every pod, and (b) in its place where a node offers project quotas the adapter can read.

**Recommendation of revision 2: (a) for the first release, with (c) as a refinement once validated.** (a) works on every runtime and every node filesystem with machinery the checkpoint already has, and it counts reflink clones as the kubelet does. Its cost is a walk per interval: the pstat walk measured 0.5 µs per entry on runc, 1.0 µs on Kata block-plain, 3.1 µs on gVisor's pod-share mount, 9.8 µs on gVisor's default mount, and 12.7 µs on Kata virtio-fs **[measured]**, so a 200,000-entry workspace costs about 0.1 s on runc and about 2.6 s on Kata virtio-fs per pass. A writer faster than the interval can still pass the kubelet's limit between two passes, which "Limits" states. Whether a pod can read its own project quota without a privilege the adapter does not hold is unverified.

The owner asked whether free space can be read without walking. The answer, by runtime: `statfs` reports the volume under gVisor's pod-share mount **[measured]**, and should under Kata `block-plain`, where each volume is its own ext4 device in the guest **[inference]**; elsewhere `statfs` reports the node filesystem, but the change tracker already reports every path that changes, so a running total can follow the writes between walks. The revised option:

- (d) `statfs` where it reports the volume; a running total kept from the change tracker's events where the tracker runs, with a periodic recalibration walk; a walk every 10 s only where neither applies; and project quotas as a later refinement.

**Settled 2026-11-13: (d)** (D12). It reacts to a write within the tracker's event latency where the tracker runs, and costs one `statfs` call where the runtime reports the volume, so the full walk's cost falls only on the volumes neither covers. `statfs` on Kata `block-plain` is owed to validation, and the watch walks there until it is measured. "PL-5" states the mechanism.

**Measured 2026-11-14.** On Kata `block-plain` the guest's `statfs` tracks each volume's usage exactly, bytes under a mode-`000` directory included, and reports the node filesystem's size rather than a limit **[measured]**, so method 1 of "PL-5" applies there for usage. O10 states the gap between that figure and the kubelet's. Project quotas, the later refinement of (d), are adopted under D25 ("PL-10").

**O9. How the disk watch treats a directory whose owner cannot list it. Settled 2026-11-13: (a) (D20).**

A session can write files into a directory and then set the directory's mode to deny its owner read, such as `0300` or `0000`. The walk lists a directory with `getdents` on a descriptor that the broker opens as the slot UID, and the broker's `statat` stats named entries only, so neither can enumerate such a directory **[inference]**. The watch's figure then misses the bytes beneath it, and a recalibration walk drops them from a running total, while the kubelet counts them and evicts the whole pod when the volume passes its `sizeLimit` **[inference]**. `statfs`, where the runtime reports the volume, counts them. A checkpoint records such a directory as `metadata_only` ([SI-6](../0145-session-isolation/change.md#si-6-checkpoint-restore-export-and-cleanup)), and the Sweep restores owner access before it descends at release.

- (a) Accept the miss as a residual risk of shared pods, stated in "Limits" here and in session isolation: one slot can evict the pod by this route. The mitigations are `statfs` where the runtime reports the volume, project quotas once validated, and on Kata `block-plain` the per-volume block device, whose size bounds the volume's writes **[inference]**. "Validation owed" in `steps.md` measures the miss on each runtime.
- (b) Give the walk the Sweep's remedy: a new broker operation adds owner read and search to such a directory during the session, and the walk then lists it. It changes a live session's modes, which a runtime can observe, and adds an operation to the broker's closed set.
- (c) Fail the session when a walk meets a directory its owner cannot list on a volume the watch walks. It closes the route at the cost of failing a session that uses such a mode for another reason.

**Recommendation: (a).** The route harms only pods with several slots, which the deployer already acknowledges as sharing pod-wide eviction (`acknowledgeSharedPod`), and it needs a session that hides bytes on purpose. (b) widens the broker for a case the kubelet already bounds, and (c) fails sessions for a mode choice.

**Settled 2026-11-13: (a)** (D20). The miss is a stated residual risk of shared pods ("Limits"). The owner asked for a spike on how project quotas would be used where a node offers them, detected automatically, which "Validation owed" in `steps.md` lists. The threshold is the chart value `adapter.diskWatchThresholdPercent`, 90 by default (D23).

**Spike and correction, 2026-11-14.** The spike measured that Kata `block-plain` backs each volume with a sparse `disk.img` sized to the node filesystem, 64 GB on its node, rather than to `sizeLimit` **[measured]**. The device's size therefore does not bound the volume's writes, and the guest's `statfs` reports the node filesystem's size, so it reports no limit, which corrects the inference of (a) above. The guest's `statfs` does count the bytes under a directory its owner cannot list **[measured]**, so the mitigation on Kata `block-plain` is that `statfs`, as on gVisor's pod-share mount. The owner adopted automatic project quotas (D25, "PL-10"), which count those bytes on runc with user namespaces, gVisor's default mount, and Kata virtio-fs. The residual risk remains on runc without user namespaces, on a node without project quotas or without a ready agent, and on a volume the agent reaches during a session, until that slot's next release.

**O10. The gap between the guest's figure and the kubelet's on Kata `block-plain`. Settled 2026-11-14: (a) (D26).**

The kubelet counts a Kata `block-plain` volume by the allocated blocks of its `disk.img`, which ran about 53 MiB above the guest's `statfs` figure at every step the spike measured: 117 MiB against 64 MiB, 167 MiB against 114 MiB, and 103 MiB against 50 MiB **[measured]**. The difference fits the ext4 metadata the guest writes into the image, which the guest's `statfs` leaves out **[inference]**. The watch's figure there therefore runs about 53 MiB below the kubelet's. At the defaults that is within the 10% margin of the 10 GiB workspace volume and the 1 GiB `/tmp`, and larger than the 25.6 MiB margin of the 256 MiB session volume, so a session volume can pass its `sizeLimit` in the kubelet's count before the watch trips.

- (a) The watch adds a fixed allowance on Kata `block-plain` pods, the chart value `kata.blockPlainOverheadBytes`, 64 MiB by default, to the guest's figure before it compares it with the threshold.
- (b) The controller adds the same allowance to the `sizeLimit` it renders for each disk-backed volume of a Kata `block-plain` pod, and to the pod's ephemeral-storage request, so the session keeps its full size.
- (c) State the gap as a limit of Kata `block-plain` and change nothing.

**Recommendation: (a).** It keeps the rendered limits and the bill unchanged and closes the gap with one constant, at the cost of 64 MiB of each `block-plain` volume. (b) raises every `block-plain` pod's request. Whether the overhead depends on the node filesystem's size, which sets the image's size, is owed to validation, and the allowance follows it.

**Settled 2026-11-14: (a).** The owner answered "ok" (D26). The watch adds `kata.blockPlainOverheadBytes`, 64 MiB by default, to the guest's figure on every disk-backed volume of a Kata `block-plain` pod before it compares the figure with the threshold, as "PL-5" states. The same day the session volume's default became 1 GiB (D27), whose 10% margin of 102.4 MiB also exceeds the measured gap, so at the defaults no volume depends on the allowance; the allowance still covers a pool that sets a smaller volume, and a volume whose kubelet overhead grows with the node filesystem.
