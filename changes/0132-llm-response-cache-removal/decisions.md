# Decisions: 0132 LLM response cache removal

## Open decisions

1. **Error detail format for a removed field.** D6 of [`0119-agent-runtimes-only`](../0119-agent-runtimes-only/decisions.md#decisions) refuses a write that names a removed field with `400 VALIDATION_ERROR` whose `details.field` names it, and 0132's O3 and tests and 0133's D9 repeat that wording. §15.1's `VALIDATION_ERROR` example and `docs/reference/error-catalog.md` put the field in `details.fields[].field` instead. Options: (a) state the refusal as `details.fields[].field` in 0119's D6, 0132's O3 and tier 1 and tier 3 tests, and 0133's D9, matching §15.1; (b) keep `details.field` and change §15.1's format for this refusal. Recommendation: (a), because every other validation error already uses the array. Raised on 2026-11-16 by the review of 0132.
   - Extended by the M3 readiness review, 2026-11-19. [`0124-connector-removal`](../0124-connector-removal/change.md) states the same refusal ("Removed fields (D7)": "refuse, with `400 VALIDATION_ERROR` whose `details.field` names the member") and records the question as its open decision O16, so the owner's answer is recorded in 0119, 0124, 0132, and 0133 together. The bootstrap seed cannot answer as O3 states: it reports a refused entry as a per-entry error with the code `SEED_VALIDATION` in its section result, answers `207 Multi-Status` when any entry fails, and its `BootstrapError` carries `index`, `id`, `code`, and `message` and no field list (`pkg/gateway/api/admin/bootstrap.go`). The answer therefore also states how the seed reports a pool entry that names `cachePolicy` or `cacheScope`. Options for the seed: (a) a per-entry error with the existing `SEED_VALIDATION` code and a message naming the field; (b) a per-entry error with the code `VALIDATION_ERROR` and a field list added to `BootstrapError` in the format the first question settles; (c) the whole seed refused with `400 VALIDATION_ERROR`. Recommendation: (b), settled with the first question, so that the seed and the admin API name the field in the same way and the seed keeps applying its other entries. The admin `POST` and `PUT` pool endpoints keep `400 VALIDATION_ERROR` under every option. Blocks: the refusal of "RC-2" in 0132.S1, the §15.1 statement, the tier 1 and tier 3 tests, and the documentation of the refusal. (raised by the M3 readiness review, 2026-11-19; sources: 0132-F1, connectors-llm-billing-C9, program-C5)
2. **The `cached` source of the lease assignment metric.** §16.1 lists `primary`, `fallback`, and `cached` as the `source` values of `lenny_credential_lease_assignments_total` and does not define `cached`. The doc comment of `IncCredentialLeaseAssignment` in `pkg/gateway/replica/gatewaymetrics/gatewaymetrics.go` names the semantic cache as the source of `cached` and states that v1 always records `primary`. A cache hit skipped credential resolution, so no code path issues a lease with that source. Credential pools keep leases for VCS credentials under [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/change.md), so the label outlives both changes unless one of them removes it. Options: (a) 0132.S1 removes `cached` from the §16.1 `source` values and the doc comment, because its only stated source is the semantic cache; (b) the value stays, and the owner of §16.1 defines it, with an issue filed under that page; (c) 0133.S2 removes or defines it with the lease rework. Recommendation: (a), because the tree names no other source and the value is never emitted. Blocks: the §16.1 edit of 0132.S1 and RCR-2's statement that no metric refers to the cache. (raised by the M3 readiness review, 2026-11-19; sources: 0132-L4)

## Decisions

Settled by the owner on 2026-11-09:

| ID | Decision |
| :-- | :-- |
| D1 | Lenny's own LLM response cache is removed. In the owner's words: "Remove caching LLM response currently provided by Lenny." |
| D2 | Provider prompt caching passes through. The owner answered "ok" to the recommendation of revision 2's O1, which the adversarial review labelled C1, and the rule reads: Lenny never strips or rewrites `cache_control`. Provider cache isolation follows the LLM upstream's provider account or workspace, and [`0133-llm-upstreams-and-cost-budgets`](../0133-llm-upstreams-and-cost-budgets/change.md) defines upstreams, the posture report of tenants that share an upstream, and the warning when a shared upstream is granted to a `hipaa` or `fedramp` tenant. A regulated tenant gets its own upstream. Strict isolation between users within a tenant is not a Lenny feature: the proxy forwards identity attributes, such as tenant, user, and session, to the upstream, so an operator-run LLM gateway behind Lenny can choose a provider workspace or key per user, and the upstreams design specifies the attributes. The residual risk within a shared upstream stays documented: `cache_read_input_tokens` and latency let users detect each other's prompt prefixes ("RC-5"). The rejected options were stripping `cache_control` in the translators and a pool setting that allows or strips it. Stripping raises cost and latency for every runtime that uses the cache, and it would be incomplete, because OpenAI and Azure OpenAI cache automatically with no request field **[external]**. |
