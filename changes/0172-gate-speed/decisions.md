# Decisions: 0172 Merge gate wall time

## Open decisions

1. **Narrowing the selection and recording it in the verdict (GS-1).** The gate already runs the `--changed` selection against its base, and `--all` is its full mode, so the question is whether to narrow what a specification edit reaches and to record each tier's selection in the verdict. Options: (a) add the row target form that runs a package's own tests without walking its dependents, move the `spec/**` row's `pkg/observability/tracing` and `pkg/api/openapi` to it along with any other row whose package reads its input only in tests, and add `gate.selection` to the verdict; for the diff of run `10acfc52`, the unit selection falls from 145 patterns to about 63, the component selection from 26 to 15, and the contract selection from 45 to 27, and the integration tier still runs whole when reached until M3 splits it; (b) add `gate.selection` to the verdict only and keep the rows as they are; (c) neither. Recommendation: (a), because CS-6 of change 0116 names the tests that read an input rather than the code they configure, and the dependent walk of those two packages accounts for 123 of the 145 unit patterns. Blocks: 0172.S1.
2. **Full runs on `main` (GS-2).** The v1 merge policy names no full run, so a dependency the selection misses goes unchecked until a run happens to reach it. Options: (a) a full run (`lenny-test gate --all`) before a milestone is reported complete and once a week on a day a merge landed, with selected runs for every other batch; (b) a full run before a milestone is reported complete only; (c) a full run as the first gate run of each day on which a merge landed, with selected runs for later batches that day. Recommendation: (a), because a weekly full run bounds how long a missed dependency or an environment drift stays unseen at about 22 minutes a week. Blocks: 0172.S1 (the policy text).
3. **Running the tiers concurrently (GS-3).** Options: (a) adopt GS-3 with the layout and bound that open decision 5 settles, and make the layout the default after the validation runs in `steps.md`; (b) adopt GS-3 behind an option that is off by default, and decide the default after the validation runs; (c) keep the tiers serial. Recommendation: (a), because the validation runs already gate the default and the option stays available to turn it off. Blocks: 0172.S2.
4. **Dropping the coverage profile from the gate's unit run (GS-4).** No part of the gate or the static tier reads `tests/results/cover.out`. `lenny-test coverage --go` and `--diff` read it, and so does the `unit` job of `.github/workflows/pr.yml`, which runs `lenny-test --tier unit` rather than the gate. Options: (a) drop `-coverprofile` and `-covermode=atomic` from the gate's unit run only, keep `-race`, and keep the profile in `run --changed` and `--tier unit`; (b) keep the coverage flags in the gate and write the profile where `lenny-test coverage` reads it, so a gate run on `main` also yields a coverage report; (c) keep the gate as it is. Recommendation: (a), because the 80% floor is checked on a branch's own `run --changed` profile and no reader of the gate's profile exists. Blocks: 0172.S3.
5. **The concurrency bound (GS-3).** Estimates are lower bounds from the per-tier durations in `change.md`, with no slowdown from sharing the machine. Options: (a) "Unit alone": [static, contract] beside [component, integration], then unit, then the documentation gates, with each tier's default `go test -p`, about 16 minutes; (b) "Two lanes": [static, unit, contract] beside [component, integration], then the documentation gates, with `go test -p` at half the container's CPUs for each tier while lanes overlap, about 12 minutes before contention; (c) "Two lanes" with the default `go test -p` for every tier, about 12 minutes before contention and the highest risk of a container-start timeout. In each option the layout and the `-p` values are gate options, so a host with more memory, or Docker Desktop with more than 8 GB, changes them without a code edit. Recommendation: (a), because the unit tier uses every CPU under `-race` and starts the envtest control planes, and keeping it away from the containers in the 8 GB VM avoids the load failure seen on 2026-11-23; (b) is the next step if the validation runs show headroom. Blocks: 0172.S2.
6. **Program membership.** Options: (a) not a member of the v1 program, as changes 0168 and 0171 are not, with GS-2 still amending v1 decision 13, which leaves these proposals to a change of their own; (b) a member of the v1 program with its steps in the current milestone (M1), whose exit criterion names the merge gate; (c) a member of the v1 program with its steps in no milestone. Recommendation: (a), because its steps advance no milestone's exit criterion and the plan section of `docs/about/status.md` stays as it is. Blocks: none.
