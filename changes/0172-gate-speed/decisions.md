# Decisions: 0172 Merge gate wall time

## Open decisions

- **GS-20. The default layout after the static-first validation run.** Decision 15 makes the static-first layout the default after a clean validation run, and "Validation owed" in `steps.md` names a container-start timeout or a VM memory peak within 10% of its limit as what returns the layout to the owner. The run, gate run `40f5968e0e96924efb1c59a3` (`lenny-test gate --all --layout static-first` on `7ad88bee1`, 2026-11-25), had neither: no container-start timeout, and a VM memory peak of 5,022 MiB of 13,960 MiB (36%). Its tiers took 34.9 minutes. It failed one test, `TestPythonClientStreamingReconnect` in `tests/contract/sdks` ("expected the SDK to reconnect after the forced disconnect, saw 1 connection(s)"), while the contract tier ran beside the component lane; a rerun of the package on the same commit with no other job passed, and five more runs of the test passed. The host slept for about 17 minutes during the run's static phase. Whether a load failure of another kind leaves the run clean is not settled, so 0172.S6 keeps the serial default.
  - (a) Make static-first the default now, and treat the reconnect failure as a load failure that the gate runs on `main` watch, as decision 7 states for container-start timeouts.
  - (b) Keep the serial default and run one more static-first validation run.
  - (c) Make static-first the default with the contract tier moved out of the container lane's phase, such as beside the unit tier, and validate that layout.
  - Recommendation: (a). The run met both stated criteria, the failure did not reproduce, and the same overlap of the contract tier with the container lane passed in gate run `d47d33b8ed80054999c769e1`.
- **GS-15. The static tier's working files and caches in the same run.** The merge-gate review of 0172.S6 (security reviewer, High) found that the snapshot of decision 14 fixes the tree, `HEAD`, and the refs the static tier reads, while the static tier still writes its working files under the fixture root that the gate user owns: the secret scan's tree and `report.json` (`runSecretScanAt`, `os.MkdirTemp("", "lenny-secretscan-")`), the lint's patch and whole-tree report (`lint_changed.go`, `os.CreateTemp("", "lenny-lint-*.patch")`), and the test binaries `go test` links under `GOTMPDIR`. The static tier also builds from the module cache and the build cache, which the gate user can write in the same run (TESTING.md "Merge gate" item 9 records the later-run case). A process of the gate user can rewrite those files between their write and their read: a test in a lane beside the static tier in the `unit-alone` layout, and in every layout the branch's own `scripts/*.sh`, which the static tier runs alongside the secret scan and the lint. The `static-first` layout of decision 15 removes the concurrent tests; the branch's scripts remain, as in issue GATE-I7.
  - (a) Run the static tier's checks under a second user, with a private `TMPDIR`, `GOTMPDIR`, and build cache, so no test and no branch script can write what they read.
  - (b) Run the secret scan and the two golangci-lint runs in the container script before the gate starts, as the fill runs now, and lock their outputs as the snapshot is locked; the branch's scripts still run as the gate user.
  - (c) Accept the window as a limit, recorded beside GT-11 and GT-16 in TESTING.md, and make `static-first` the default so that no test runs beside the static tier.
  - Recommendation: (c) now, because during the v1 program only the owner's branches run the gate and decision 15 already moves the tests out of the static tier's phase, with (a) filed as an issue for when contributors arrive.
- **GS-16. The snapshot's object store.** The snapshot borrows the worktree's objects through git's alternates file (`createStaticSnapshot`), and git does not check an object's content against its name when it reads it; the security reviewer reproduced a substituted loose object that `git cat-file --batch`, `git reset --hard`, and `git diff` returned without error. In a main checkout, such as the clone the gate on `main` runs in, the object store lies in the writable worktree mount, so a process of the gate user can change what the secret scan, the lint's register read at the merge base, and `buf breaking` read, in the same run or for a later run. A linked worktree's object store is mounted read-only.
  - (a) Fill the snapshot's own object store with `git fetch` from the worktree, which re-hashes every object it receives, and lock it with the snapshot; the cost is a fetch of the history on every run.
  - (b) Keep the alternates, and make the verdict `UNVERIFIED` when the git common directory lies inside the writable worktree mount.
  - (c) Keep the alternates and record the limit, as the build now does in TESTING.md and the code comments.
  - Recommendation: (c) during the v1 program, for the reason of GS-15, with (a) measured and filed as an issue.
- **GS-17. The writers of the snapshot that remain.** A gate that runs as root holds `CAP_SYS_ADMIN` and can remount the snapshot writable, and a process with the host Docker socket can reach it; the writability check runs before the tiers. The owner accepted the same writers for the golangci-lint cache (GT-16). The build records both in TESTING.md.
  - (a) Extend the acceptance of GT-16 to the snapshot.
  - (b) Make a gate that runs as root in a concurrent layout `UNVERIFIED`.
  - Recommendation: (a).
- **GS-18. A merge check with no recorded `--cover` gate run.** Decision 18 has `lenny-test coverage --diff` refuse a profile whose hash does not match the latest restricted gate verdict for the same commit. 0172.S8 measures the profile with a note when no gate run with `--cover` on `HEAD` is recorded, so the profiles of `lenny-test run --changed`, `lenny-test --tier unit`, and the `unit` job of `.github/workflows/pr.yml` keep working; it refuses a profile that a gate run on another commit recorded. The merge check of decision 8 then passes on a profile that no gate run on the head wrote, for example after a `gate --tier ...` run without `--cover`, or a history line the gate failed to append (`writeGateVerdict` treats that failure as a warning).
  - (a) Add `coverage --diff --require-gate`, which refuses when no such run is recorded, and use it in the check before a merge in `.claude/rules/git-workflow.md`, `.claude/rules/test-coverage.md`, and the build skill.
  - (b) Keep the note, as built.
  - Recommendation: (a).
- **GS-19. A profile from a gate run that did not pass.** 0172.S8 accepts the profile of the latest `--cover` gate run on `HEAD` whatever its verdict, and refuses one from a run on a dirty tree. Decision 8 requires the gate run to pass separately, and the run the merge records may not be the latest one.
  - (a) Refuse a profile whose gate run's verdict is not `PASS`.
  - (b) Accept it, as built, and leave the verdict to the merge record.
  - Recommendation: (a), because the merge check reads the two results as one.

## Decisions

1. **Narrowing the selection and recording it in the verdict (GS-1).** The `spec/**` row of `tests/non-go-inputs.yaml` moves `pkg/observability/tracing` and `pkg/api/openapi` to a new row target form that runs a package's own tests without walking its dependents, together with any other row whose package reads its input only in tests, and the verdict records each tier's selection as `gate.selection`. The options not chosen were (b), recording `gate.selection` only, and (c), neither. Owner's answer to GS-1 on the M3 readiness decision page, 2026-11-23, option (a).
2. **Full runs on `main` (GS-2).** A full run (`lenny-test gate --all`) runs on `main` before a milestone is reported complete and once a week on a day a merge landed, and selected runs cover every other batch. This amends v1 program decision 13, and 0172.S1 writes it into the v1 merge policy. The options not chosen were (b), before a milestone only, and (c), the first run of each day on which a merge landed. Owner's answer to GS-2 on the M3 readiness decision page, 2026-11-23, option (a).
3. **Running the tiers concurrently (GS-3).** The gate runs its tiers concurrently, with the layout and bound of decision 5, and the layout becomes the default once the validation runs in `steps.md` pass. The options not chosen were (b), an option that is off by default, and (c), serial tiers. Owner's answer to GS-3 on the M3 readiness decision page, 2026-11-23, option (a).
4. **Dropping the coverage profile from the gate's unit run (GS-4).** The gate's unit run drops `-coverprofile` and `-covermode=atomic` and keeps `-race`; `run --changed` and `--tier unit` keep the profile. The options not chosen were (b), keeping the flags and writing the profile where `lenny-test coverage` reads it, and (c), keeping the gate as it is. Owner's answer to GS-4 on the M3 readiness decision page, 2026-11-23, option (a).
5. **The concurrency bound (GS-5).** "Unit alone": static and contract run beside component and integration, then unit, then the documentation gates, with each tier's default `go test -p`, about 16 minutes before contention. The layout and the `-p` values are gate options. The options not chosen were (b), "two lanes" with `-p` at half the container's CPUs while lanes overlap, and (c), "two lanes" with the default `-p`. Owner's answer to GS-5 on the M3 readiness decision page, 2026-11-23, option (a).
6. **Program membership (GS-6).** 0172 is not a member of the v1 program. The options not chosen were (b), a member with its steps in M1, and (c), a member with its steps in no milestone. Owner's answer to GS-6 on the M3 readiness decision page, 2026-11-23, option (a).
7. **One validation run for the concurrent layout, then watching the gate on `main`.** 0172.S2 validates the layout with one `lenny-test gate --all` run instead of three, and makes the layout the default when that run is clean. The gate runs on `main` that follow record the same signals, and when a container-start timeout appears in two of the first few runs with the new layout, the gate on `main` goes back to serial tiers through the serial option and the bound returns to the owner. The owner raised the Docker Desktop VM's memory on 2026-11-24, from 8 GB to about 13.6 GiB, before this decision. Owner's answer in chat, 2026-11-24, to the question of whether one run is enough; the option not chosen was the three runs of revision 2.
8. **The check before a code branch merges.** A branch that touches a path outside the records and documentation merges when, on its committed head with `main` merged in, `lenny-test gate --tier static,unit,component,contract --cover` passes, `lenny-test coverage --diff main --threshold 0.80` passes on that run's profile, the tests the branch adds or changes in a tier the gate does not run (such as security or load_local) pass in a targeted run that the digest or the merge commit message names, and the secret scan passes. The specification gates for a diff of `spec/` and the docs tier for a diff of `docs/` stay. The integration tier and the general documentation gates run in the gate on `main` after the merge. The gate's selection is the diff selection of `lenny-test run --since main`, so the restricted run runs the tests of those tiers that the branch reaches and no others. Until 0172.S4 lands, a code branch runs `lenny-test gate` on its head with `main` merged in, which selects every merge-gate tier the diff reaches. This replaces `lenny-test run --changed` on the committed head, which reads the working-tree diff and on a clean head selects the static tier alone, so the branches merged under it (0165.S2, 0169, and 0168.S1) were checked before merging by the static tier and covered by the gate on `main` after merging. Owner's answer in chat, 2026-11-24. The options not chosen were keeping the static tier before the merge with the gate on `main` right after each code merge, and the full gate before every code merge as the lasting rule.
9. **A tier option and a coverage option on the gate (0172.S4).** `lenny-test gate --tier <tiers>` restricts the gate's selection to the named tiers of the merge gate, and `--cover` writes the unit run's coverage profile to `tests/results/cover.out`. The gate on `main` uses neither, so decision 4 holds for it. The verdict records the tiers the run was restricted to and whether it wrote a profile. Owner's answer in chat, 2026-11-24.
10. **`lenny-test run` in the gate container (0172.S5).** `lenny-test run --container` runs the `run` selection inside the gate image with the gate's container setup (the Docker socket, the user, and the caches), so `run --since main` on a developer host runs the unit, component, and contract tiers in the environment the gate uses. The `go vet` failure on macOS hosts, which reads a file that builds only on Linux, is fixed in the repository. The cgo link failure of `-race` builds on macOS 27.2 hosts is a mismatch between the Go toolchain and the SDK outside the repository, and the container option is the path around it. Owner's answer in chat, 2026-11-24, that `run --since main` should work rather than only the gate.
11. **Build order and deferred testing.** The steps are built one after another on stacked branches, in the order S1, S3, S2, S4, S5, and testing that loads the machine waits until S5 is written. One round then runs on the stacked head: the coverage timing of 0172.S3, the single validation run of 0172.S2 (`lenny-test gate --all`), which is also the check before merging of decision 8's interim rule, the comparison of the old and new selection for 0172.S1, and the checks of 0172.S4 and 0172.S5. Each step's diff is reviewed with the `review` skill, the steps merge in order, and one gate runs on `main` after them. Owner's answer in chat, 2026-11-24, to speed the change up.
12. **Review of the selection files before a merge (GS-8).** `tests/non-go-inputs.yaml`, `tests/groups.yaml`, and `tests/groups.subsets.yaml` join the paths of "Review changes to the merge gate" in `.claude/rules/git-workflow.md`, amending change 0158 decision 6, and 0172.S4 writes them into the rule. The options not chosen were (b), a check in `lenny-test validate` that fails a `tests` target whose files outside its tests name a path the row matches, (c), both, and (d), neither. Owner's answer to GS-8 on the M3 readiness decision page, 2026-11-24, option (a).
13. **Full runs outside the cadence (GS-9).** The cadence of decision 2 stays as written: the milestone run and one run a week are full runs, and every other run is a selected run. The options not chosen were (b), the cadence as a minimum, and (c), (b) with a full run for a batch that changes `go.mod`, `go.sum`, `go.work`, `vendor/`, or `tests/gate/Dockerfile`. Owner's answer to GS-9 on the M3 readiness decision page, 2026-11-24, option (a), with the note: "This is just during the development of the v1 program, so it's temporary. Right now I have no collaborators."
14. **The static tier reads a snapshot (GS-10).** The static tier reads a snapshot that the tests cannot write: the gate resolves `HEAD` once, passes the commit to the secret scan and the git reads, and runs the checks that read the working tree on an export of that commit that the gate user cannot write. Step 0172.S6 builds it after the stack of 0172.S1 to 0172.S5 merges, and until then the tiers keep running in parallel. The options not chosen were (a), a phase of its own for the static tier, and (c), accepting the window. Owner's answer to GS-10 on the M3 readiness decision page, 2026-11-24, option (b), with the note: "Until built, continue running in parallel."
15. **The default layout after the validation run (GS-11).** The serial layout stays the default. 0172.S6 adds a layout that runs the static tier in a phase of its own ahead of the lanes of decision 5, and validates it with one `lenny-test gate --all` run under "Validation owed" in `steps.md`; a clean run makes that layout the default, as decision 7 states for the runs that follow. The options not chosen were (b), the unit-alone layout as the default with the two timeouts of gate run `d47d33b8ed80054999c769e1` treated as load failures, and (c), the unit-alone layout with `--go-test-p component=2,integration=2` and one more validation run. Owner's answer to GS-11 on the M3 readiness decision page, 2026-11-24, option (a).
16. **`tests/docs` in a full run (GS-12).** The unit tier of a `--all` run leaves out `tests/docs`, whose tests belong to the docs tier, so the full runs of decision 2 do not fail on the 102 gap-record reconciliation tests and subtests there that fail on `main`. Those tests are recorded in issue GATE-I9 to be fixed or retired. 0172.S7 builds the exclusion. The options not chosen were (a), fixing or retiring the tests before the first full run with `tests/docs` kept in the unit tier, and (c), quarantining them under the flake budget. Owner's answer to GS-12 on the M3 readiness decision page, 2026-11-24, option (b).
17. **Two rows of `tests/non-go-inputs.yaml` (GS-13).** 0172.S7 adds the missing targets to two rows: the row of `.github/workflows/release.yml` runs `tests/security`, whose `scaffolds_test.go` reads that file, and the runbooks row names the chaos, security, and load_kind tiers, which run the image that copies `docs/runbooks`. The option not chosen was (b), an issue fixed at M3 sequencing. Owner's answer to GS-13 on the M3 readiness decision page, 2026-11-24, option (a).
18. **The coverage profile and the container messages (GS-14).** The gate's verdict records a hash of the coverage profile that `--cover` writes, and `lenny-test coverage --diff` refuses a profile whose hash does not match the latest restricted gate verdict for the same commit. The image-build messages name the command that runs them, `lenny-test gate` or `lenny-test run --container`. 0172.S8 builds both. The options not chosen were (b), the hash alone, and (c), an issue for later. Owner's answer to GS-14 on the M3 readiness decision page, 2026-11-24, option (a).
