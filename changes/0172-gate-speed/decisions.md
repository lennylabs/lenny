7. **One validation run for the concurrent layout, then watching the gate on `main`.** 0172.S2 validates the layout with one `lenny-test gate --all` run instead of three, and makes the layout the default when that run is clean. The gate runs on `main` that follow record the same signals, and when a container-start timeout appears in two of the first few runs with the new layout, the gate on `main` goes back to serial tiers through the serial option and the bound returns to the owner. Owner's answer in chat, 2026-11-24, to the question of whether one run is enough; the option not chosen was the three runs of revision 2.
8. **The check before a code branch merges.** A branch that touches a path outside the records and documentation merges when, on its committed head with `main` merged in, `lenny-test gate --tier static,unit,component,contract --cover` passes, `lenny-test coverage --diff main --threshold 0.80` passes on that run's profile, the tests the branch adds or changes in a tier the gate does not run (such as security or load_local) pass in a targeted run that the digest or the merge commit message names, and the secret scan passes. The specification gates for a diff of `spec/` and the docs tier for a diff of `docs/` stay. The integration tier and the general documentation gates run in the gate on `main` after the merge. The gate's selection is the diff selection of `lenny-test run --since main`, so the restricted run runs the tests of those tiers that the branch reaches and no others. Until 0172.S4 lands, a code branch runs `lenny-test gate` on its head with `main` merged in, which selects every merge-gate tier the diff reaches. This replaces `lenny-test run --changed` on the committed head, which reads the working-tree diff and on a clean head selects the static tier alone, so the branches merged under it (0165.S2, 0169, and 0168.S1) were checked before merging by the static tier and covered by the gate on `main` after merging. Owner's answer in chat, 2026-11-24. The options not chosen were keeping the static tier before the merge with the gate on `main` right after each code merge, and the full gate before every code merge as the lasting rule.
9. **A tier option and a coverage option on the gate (0172.S4).** `lenny-test gate --tier <tiers>` restricts the gate's selection to the named tiers of the merge gate, and `--cover` writes the unit run's coverage profile to `tests/results/cover.out`. 10. **`lenny-test run` in the gate container (0172.S5).** `lenny-test run --container` runs the `run` selection inside the gate image with the gate's container setup (the Docker socket, the user, and the caches), so `run --since main` on a developer host runs the unit, component, and contract tiers in the environment the gate uses. The cgo link failure of `-race` builds on macOS 27.2 hosts is a mismatch between the Go toolchain and the SDK outside the repository, and the container option is the path around it. Owner's answer in chat, 2026-11-24, that `run --since main` should work rather than only the gate.

26. **A narrower check before a merge (owner's direction after the timing of 0171.S2 and 0172.S10).** Three changes land together as one step, 0172.S11. (1) `lenny-test gate --rerun-failed` reruns only the tests that failed in the latest gate run on the same commit, a few times, and when they pass it records a `PASS` verdict that names the original run and reuses its coverage profile, so `coverage --diff --require-gate` accepts it; a flaky failure then costs the rerun of one test rather than of the whole gate. (2) The gate before a merge, `--tier static,unit,component,contract`, selects the changed packages and the packages that import them directly, rather than every package that reaches them through other packages; the gate on `main` keeps the full reverse-dependency walk, and the full runs of decision 2 stay, so a break that only a package further away sees is caught on `main` after the merge. (3) A change to a generated file (the chart's alert rules and the embedded manifests regenerated from `pkg/alerting/rules`, and the registers under `tests/registers/` whose counts a run writes back) selects the check that regenerates or reads that file, rather than every package its row of `tests/non-go-inputs.yaml` lists. The evidence is the first gate run of branch `change/0171.S2-0172.S10` (run `e16818ce8507b5fcd52e7008`, 2026-11-25): of 137 selected packages, 28 imported or were the changed code, about 82 reached it only through `pkg/storage/pubsub` or another package, and about 27 came from rows of regenerated files; the run failed on a flaky test the branch did not touch, and its rerun took 826 s where the failing test passed five times in 6 s. Owner's direction in chat, 2026-11-25: "yes, all three as one 0172 step (insert as the next step)".
27. **The gate on `main` runs in GitHub Actions during the v1 program.** A workflow runs `lenny-test gate` on each push to `main`, in the gate container on a GitHub-hosted runner, against the base that "The gate on `main`" in `.claude/rules/git-workflow.md` names: the commit of the latest passing run of that workflow on `main`. Its scheduled weekly run, and the run before a milestone is reported complete, are full runs (`--all`), as decision 2 states. Runs of the workflow queue in one concurrency group without cancelling, so pushes that land while a run is in progress are covered together by the next run. The workflow's run identifier and result take the place of the local run in merge commit messages and digests, and a branch merges only when the latest finished run of the workflow on `main` passed, or its failure has been fixed or reverted. The local gate on `main` continues until the workflow's first passing run on `main`. The repository is public, so GitHub-hosted runners carry no minute charge. The workflow joins the paths of "Review changes to the merge gate". Owner's direction in chat, 2026-11-25: "can we rely on Github's CI to run the full gate after each merge to main? That would free up resources on this machine. If you agree, add it to 0172.S11".
