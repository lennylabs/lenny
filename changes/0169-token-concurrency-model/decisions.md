# Decisions: 0169 A concurrency model of the token rules

## Open decisions

3. **PlusCal or plain TLA+.** The request processes are sequential programs whose statements run inside transactions, and Postgres underneath them is a set of rules about snapshots, locks, and aborts.
   - (a) Write the request processes in PlusCal, with one label per statement or lock step, and describe Postgres as TLA+ operators and macros in the same module. The translator ships in `tla2tools.jar` (`pcal.trans`), so the runner needs no other tool. Each label is one atomic step, so a reviewer checks the atomicity of the model against the Go code by reading the labels beside the statements, and adding the `TF` variant edits the process bodies where 0168 changes the code. The translation is committed in the module between the translator's markers, and the runner checks that it is current.
   - (b) Write the whole model in plain TLA+ as one next-state relation. It gives full control over each action and can merge steps the processes do not need to split, which keeps the state space smaller, at the cost of a model that reads as a state machine rather than as the code's statement order, which makes a review against the Go code slower.
   - Recommendation: (a). The model's value depends on its steps matching the code's statements, and PlusCal states that order directly. Where a step needs plain TLA+, such as the deadlock detector or the bus, it is a TLA+ action outside the processes.
4. **Which TLC release to pin.** The tlaplus GitHub releases, checked on 2026-11-23, list `v1.7.4` (2024-08-05) as the latest release and `v1.8.0` (2026-11-19) as a pre-release; "CM-5 Running TLC" in `change.md` gives the size and checksums of each jar.
   - (a) `v1.7.4`. Its release notes publish a SHA-1 for `tla2tools.jar`, which the downloaded jar matches, and the SHA-256 the runner pins is computed from that download. Its release notes name one fix, tlaplus issue 971, an unsound liveness check when TLC runs with several workers, which matters for the liveness properties of C4 and C5.
   - (b) `v1.8.0`. GitHub publishes a SHA-256 digest for its jar, which the downloaded jar matches. It is marked as a pre-release and was published four days before this change was framed, and its release notes link the milestone of `v1.7.1` as its changelog.
   - Recommendation: (a). The model's results have to be reproducible by the change that reruns it, and a pre-release published four days ago has had little use. `v1.8.0` can replace it in a later revision once it is a release, with every configuration rerun.
5. **Bounds and configurations.** TLC's run time grows with the number of processes, tokens, and tenants, and the free configuration grows fastest.
   - (a) Directed configurations at 2 tenants, 2 users per tenant, 2 replicas, up to 3 request processes, up to 6 tokens, 1 abort per behavior, and the 3 cascade attempts the code makes; one configuration per ordering of "Scope" in `change.md`, naming the operations that race. One free configuration at 2 request processes and 5 tokens, in which each process chooses any operation. A configuration that does not finish within 12 hours on the owner's laptop is stopped and recorded, as 0165 recorded its unfinished large-scope checks.
   - (b) Free configurations only, at 2 request processes. Every interleaving of two operations of any kind is covered, but no three-way race, such as a cascade, a rotation, and a child mint from the rotated token, is.
   - (c) Directed configurations at 3 tenants as well, for orderings of nested transactions across more than two target tenants.
   - Recommendation: (a). Each ordering in scope names the operations that race, so a directed configuration reaches it at the smallest state space, and the free configuration catches pairs the list does not name. Two tenants are enough for the cycle C8 describes; a third tenant is added for C8 only if the two-tenant run finds no cycle and the owner asks for more.
6. **Whether a tier of `lenny-test` runs the model.**
   - (a) No tier runs it. It is a design check run by hand with `tests/formal/tokenconcurrency/run.sh`, and the change that edits a rule the model describes reruns it, as 0165's model is run (0165's `change.md`, "Tests").
   - (b) The static tier runs the PlusCal translation and the parser (SANY) only, so a model that no longer parses fails the merge gate, without running TLC.
   - (c) The release gate runs the directed configurations.
   - Recommendation: (a). It follows 0165. The gate image (`tests/gate/Dockerfile`) carries no JDK, and running TLC from it would add one or a nested container to the merge gate; the model changes only when a rule it describes changes, and the change that edits that rule reruns it.
7. **Whether the model checks the resolution TOKX-I13 suggests.** TOKX-I13 suggests that the cascade and `RevokeBySubject` take the per-tenant audit advisory lock before the statement that reads their snapshot, and leaves the decision to the owner with the bound of [TOKX-I10](../../issues/TOKX/TOKX-I10-revocation-cascade-has-no-depth-or-time-bound.md). 0168 leaves TOKX-I13 out.
   - (a) Step 0169.S2 adds the variant `I13Lock`, which is `TF` with that lock, and checks C1, C7, C8, and C5 under it, so the owner sees whether the lock closes the window and whether it adds a wait cycle with 0168's nested transactions.
   - (b) The model checks `Main` and `TF` only.
   - Recommendation: (a). The variant is one lock step in two processes, and the owner has to decide TOKX-I13 with evidence about how the lock composes with 0168's design.
8. **Whether steps 0169.S1 and 0169.S2 share a branch.**
   - (a) One branch for both steps, with one digest, reporting the results of `Main` and `TF` together. The Postgres description, the replicas, and the processes are written once, `TF` edits the processes where 0168 changes the code, and the results of `Main` are the baseline for reading those of `TF`: a property that fails under both is inherited from `main`, and one that fails only under `TF` is a defect of 0168's design.
   - (b) Separate branches, with 0169.S1 merged first. The results of `Main` reach the owner before `TF` is written.
   - Recommendation: (a). 0168.S1's code lane waits on the results of `TF`, which need the model of `Main` first, and a separate merge of 0169.S1 adds a gate run without bringing those results earlier.
9. **Whether the change states the concurrent properties in §13.3.** **Token rule properties.** states its properties for operations that complete one at a time.
   - (a) No specification text. The properties stay in `change.md` and in the model's README, and each change that fixes a counterexample states in §13.3 the ordering it settles.
   - (b) A specification lane on 0169.S2's branch adds a paragraph to §13.3 after **Token rule properties.** stating the properties C1 to C10 the model confirms, with the accepted windows.
   - Recommendation: (a). 0168's specification lane edits **Token rule properties.** and the paragraphs around it now, so a lane of this change on the same paragraphs would conflict with it, and which properties hold is not known until the model runs. The owner can choose (b) when the results are in.

## Decisions

1. **Build the TLA+ model now, as its own change (owner, 2026-11-23).** The owner decided on 2026-11-23 to build the TLA+ model of the concurrent orderings of the token rules now, as this change. This amends decision 14 of change 0165 (a formal model of the token rules), under which the model stayed a candidate until step 0165.S2 was done.
2. **The model checks 0168's locking design before its code lane (owner, 2026-11-23).** The owner decided on 2026-11-23 that the model checks the locking design of change 0168 (token rule fixes from the property tests), as its decisions 1, 2, 5, and 6 and its sections TF-1 to TF-5 state it, before the code lane of 0168.S1 is written. The specification lane of 0168.S1 may proceed in parallel. The counterexamples the model finds in that design are reported to the owner before the code lane starts.
