## Defaults applied

- **Error codes.** The unparseable refusal is `401 UNAUTHORIZED` with `details.reason: "subject_scope_invalid"`, following the playground's other 401 refusals, which carry `details.reason`. The disjoint refusal is `403 SCOPE_FORBIDDEN`, the §15.1 catalog code for a refusal caused by the `scope` claim alone, with `details.activeScope` set to the subject's claim and `details.requiredScope` set to `playground_allowed_scope` as a space-separated list, any one value of which admits the mint. No new error code was added. `FORBIDDEN` and `TOKEN_INVALID` (which the catalog does not list) were the alternatives.
- **Audit identifiers.** The refusals emit `playground.bearer_mint_rejected` with the invariant identifiers `subject_scope_invalid` and `scope_intersection_empty`, which the §10.2 edit names. The `apiKey` subject now carries the pasted token's `jti` so the event names it.
- **Absent subject scope.** A subject with no `scope` claim, or an empty or whitespace-only one, keeps minting `playground_allowed_scope`, as the code did before the branch. Decision 1 covers the unparseable and the disjoint cases, and the old §10.2 row described an empty subject scope as yielding an empty intersection, which contradicted §25.1's absent-claim semantics and the code. The §10.2 edit states the absent-claim result explicitly. Refusing an absent claim would refuse every identity provider that omits `scope` from its ID tokens.
- **Order.** The scope check runs in `completeMint` before the signer check, after the `typ`, tenant, and step (1a) checks in `apiKey` mode and after the invalidation check in `oidc` mode, so a refused subject receives the refusal whatever the signer's state.
- **Silent refresh.** No separate check was added. The refresh calls `POST /v1/playground/token`, which runs the same check on every mint.
- **`oidc` callback and UI.** The login callback still establishes a session for an ID token with an unparseable `scope`, and the mint refuses it. The UI was left unchanged: `mintBearer` redirects to login only on a 401 without a reason or with `playground_session_expired`, so both refusals surface as errors with no login loop.
- **Documentation.** `docs/reference/error-catalog.md` gained a `SCOPE_FORBIDDEN` row, which it lacked before the branch.
