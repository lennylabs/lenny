## Problem

"Terms", after "Scope", defines the vocabulary this document uses.

The owner asked for this: "If that's not the case today already, the ability for a runtime/pool to delegate should be configurable with a platform/tenant default. If disabled, then delegateTask shouldn't be a tool offered to the runtime. Not sure if the same should apply to other platform tools (I don't think so, but worth double-checking)." The owner later added a thought for this design: "we should probably allow sessions to disable delegation."

It is not the case today. No setting at the platform, tenant, runtime, or pool level makes delegation unavailable, and every session is offered `lenny/delegate_task` **[source]**:

- The Runtime fields that concern delegation, `delegationPolicyRef` and `allowSelfRecursion`, decide which targets a session may reach and whether a runtime may repeat in its own lineage. Neither turns delegation off. Pools carry no delegation field, and the tenant record carries none.
- A `DelegationPolicy` with no allow rule permits no target. The gateway applies the policy's rules to `lenny/discover_agents` and to connector authorization, and it does not apply them to `lenny/delegate_task`, so such a policy empties discovery and leaves delegation open ("Current state", F-8.3.14).
- The platform MCP server inside the pod lists every tool the gateway's `/mcp` endpoint registers, for every session, whatever its configuration (F-9.1.13).

One part of the request already has a settled answer. [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md#client-delegation-limits-decision-26) settled, as its decision 26, that a client creating a session with `delegationLease.maxDepth: 0` disables delegation for that session, that the gateway refuses `lenny/delegate_task` with `403 DELEGATION_DISABLED`, and that the intra-pod tool list omits the tool for that session. Its proposal TS-3 carries the work. This design builds the levels above the session on the same refusal and the same list filtering, and it settles the questions decision 26 leaves open for the session level.

The owner's request names pools. The owner decided on 2026-11-09 that the pool level is dropped, because a derived runtime can turn delegation off for the sessions that need it (D2).

[`0166-delegation-primitives`](../0166-delegation-primitives/change.md) replaces built-in delegation with primitives in the core: a session grant, held by the gateway, with which a session creates sessions as its children through the platform operations of its "DP-1", and a reference extension in the runtime SDKs and the reference MCP bridge that offers a model the session tools ("DP-5"). Under its decision 39, settled by the owner on 2026-11-23, this change keeps its availability levels, their order, the checks, the refusal, and the `availability` notice, cut down to deciding whether a session holds a grant. 0166 owns the grant, its caveats, the resolution of every caveat, and the operations, and the extension owns the list of session tools.

## Scope

**Added:**

- A delegation availability setting at the platform, tenant, and runtime levels, with a platform default, a tenant default, a narrow-only tenant entry for one runtime, and a resolution rule that combines them with the session level ("DA-1" and "DA-2").
- A tenant hard switch as the guardrail `"delegation": "forbid"` in the tenant security record of [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture), written by a `security-admin` (D5).
- The rule that decides whether a session holds the session grant of [`0166-delegation-primitives`, "DP-1"](../0166-delegation-primitives/change.md#dp-1-session-grant): a session receives a grant at creation only when it may delegate, and each call that needs the grant reads availability again ("DA-2", 0166 decision 39).
- A call-time refusal of the platform operations of 0166 "DP-1" that names the level that disabled delegation, with the operations a session that has children keeps (DAR-6, "DA-3").
- A per-session platform tool list that omits each tool whose call the session's settings guarantee to be refused or to have no effect, such as `ask_question` on a session created with `inputPolicy: decline` ("DA-4", O7).
- The runtime capability `capabilities.childSessions: true` as a condition of delegation, because a runtime that cannot show its model which child a message came from cannot manage children ("DA-2", E1, and "MD-22" of [`0135-message-delivery`](../0135-message-delivery/change.md#md-22-parents-and-children)).
- Live reads of the settings at each call of an operation that needs the grant and at each platform tool list, with no copy of the list in the adapter, and the `delegation` and `questions` members of the session's availability, which the runtime protocol design sends to the runtime and from which the reference MCP bridge lists the session tools ("DA-5", O4, 0166 "DP-5").
- A per-hop rule for a parent that wants its child unable to delegate: an explicit `maxChildrenTotal: 0` in the `limits` of `session.create` (D4, "DA-6").
- Audit events that distinguish a change which widens availability from one which narrows it ("DA-1").
- The tenant delegation settings route, which carries the tenant default of this change and the tenant `policyRef` and `ceilings` that 0166 "DP-1" reads as root grant inputs (0166 decision 26, O10).

**Changed:**

- §8.5's statement that the delegation tools are "available on the platform MCP server for every delegation-capable pod" leaves with the gateway-hosted tools, which 0166 replaces with the platform operations and the reference extension. The refusal of "DA-3" applies to the operations.
- An explicit `maxChildrenTotal: 0` in the limits a parent gives a child means that the child starts no child, and lease extension never raises it ("DA-6").
- `Bridge.ListPlatformTools`, which ignores the session ID today, filters the list for the calling session ("DA-4").

**Removed:**

- `capabilities.harnessApprovalRequests` and its list rule, which revision 4 added, because harness approvals travel on frames (E3).
- `approvalMode` as an argument of today's delegation tool, with `ErrDelegationDenied`, the `DELEGATION_DENIED` code, and `ERROR_CODE_DELEGATION_DENIED` in the adapter proto, whose number is reserved (D4, "DA-6"). 0166 "DP-6" drops the lease field of §8.4 as well.
- The list rules of revisions 1 to 13 for the tools that start and manage children. The reference extension of 0166 "DP-5" lists those tools from the session's `availability.delegation` and its children, and the gateway marks each platform operation as one the reference MCP bridge never lists ("DA-4", 0166 decision 39).

**Out of scope:**

- A pool level. The owner dropped it (D2).
- Per-tool switches for the other platform tools. "DA-7" reviews each tool and finds an existing control for each, and O7 records the owner's answer.
- The notice to a running runtime when its availability changes. [`0139-runtime-protocol`, "RP-4"](../0139-runtime-protocol/change.md#rp-4-availability) owns the `availability_changed` frame and when the gateway sends it (O4 as reopened). This design supplies the values the notice carries for delegation and questions ("DA-5").
- The session grant, its caveats, the root grant inputs other than availability, the resolution of every caveat, the platform operations, and the reference extension with its tool list. [`0166-delegation-primitives`](../0166-delegation-primitives/change.md) owns them ("DP-1" and "DP-5").
- Which targets a session may reach. The policy cap of the grant decides that, and 0166 checks it at the post-chain point of [`0141-runtime-routing`](../0141-runtime-routing/change.md#post-chain-point), which also closes F-8.3.14 ("DP-6" of 0166). O12 records which change closes the finding.
- Publishing a runtime's delegation availability in discovery (`GET /v1/runtimes`).
- Root-session creation through the gateway's public API from inside a pod. "Limits" states it.

## Terms

| Term | Meaning |
| :-- | :-- |
| Delegation availability | Whether a session's configuration allows it to hold a session grant and start children. The platform, the tenant, the tenant security record, the session's environment, a tenant runtime entry, and the runtime decide it ("DA-1"). |
| `allowDelegation` | The availability field on a Runtime, on an environment, and on a tenant runtime entry. On a Runtime it is `true`, `false`, or unset. On an environment and on a tenant runtime entry it is `false` or unset. |
| Tenant runtime entry | A tenant's per-runtime record of §5.1 "Capabilities are customizable per tenant", stored at `/v1/admin/tenants/{id}/runtime-capability-overrides/{runtime}` **[source]**. This design adds `allowDelegation: false` to it, which narrows one runtime for one tenant (D1). |
| Default | A level's value that applies when the runtime says nothing: `allowByDefault` at the platform and the tenant. A more specific level can override a default in either direction. |
| Forbid | A switch that makes delegation unavailable whatever the more specific levels say: `gateway.delegation.forbid` at the platform, and the delegation guardrail at the tenant. |
| Delegation guardrail | The entry `"delegation": "forbid"` in the tenant security record of [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture), written by a `security-admin`, or by a `platform-admin` with a justification, under SO-2's tightening and weakening rules (D5). |
| Room | Whether the session's grant allows one more child: its remaining depth is above 0, which is a stored `maxDepth` greater than the session's own depth, and its `maxChildrenTotal` is not an explicit 0. A root under `maxDepth: 0` has no room, and neither has a child whose parent passed an explicit `maxChildrenTotal: 0` in the `limits` of `session.create`. TS-3 defines the stored `maxDepth`, and 0166 "DP-1" resolves it. |
| May delegate | Delegation availability and room together, with the runtime capability of E1. A session that may delegate at creation receives a session grant, and a call that needs the grant passes this gate only while the session may delegate ("DA-2"). |
| Operations that need the grant | The platform operations of 0166 "DP-1" other than `session.self`, and other than `files.import` of a file part delivered to the caller, which every session holds. A session with no grant, or one that may no longer delegate, is refused each of them, apart from the operations that DAR-6 keeps for a session that has children ("DA-3"). |
| Operations kept for children | The operations of 0166 "DP-1" to which DAR-6 maps "the tools that manage them": `events.wait`, `events.peek`, `session.get`, `session.list`, `session.close`, `session.send`, `session.interrupt`, `session.messages`, `session.set_limits` for a cut, `questions.answer`, `questions.forward`, and `tools.result`. `session.transfer` and `session.release` are not among them. |
| Platform tool list | The `tool_list` frame the adapter answers to a `list_tools` frame with `server: "platform"`, for the session of the slot whose connection carried it, and the `tools/list` result the reference MCP bridge builds from it for a harness. The gateway computes it at each list ("DA-4" and "DA-5"). Each operation of 0166 "DP-1" carries the attribute of [`0139-runtime-protocol`, "RP-3"](../0139-runtime-protocol/change.md#rp-3-tool-calls-on-frames) that marks a platform tool the bridge never lists to a harness. |
| Inapplicable tool | A platform tool whose call the session's current settings guarantee to be refused or to have no effect, such as `ask_question` on a session created with `inputPolicy: decline`. "DA-4" lists each one, and the platform tool list leaves it out so that its description costs the agent no context (O7). |
| Stale list | A tool list that a runtime keeps from a list made before a setting changed, whether the platform tool list or the list of session tools the reference MCP bridge builds from `availability.delegation`. The runtime holds it until it lists again, which the `availability_changed` notice prompts ("DA-5"). |
| `capabilities.childSessions` | The Runtime capability of "MD-22" of [`0135-message-delivery`](../0135-message-delivery/change.md#md-22-parents-and-children), stating that the runtime shows its model the sender of each child event, so the model can tell its children apart. It is `true` or unset, versioned and gateway-read. A revision that does not declare it cannot delegate (E1). |
| Operation and tool names | This design uses the platform operations of [`0166-delegation-primitives`, "DP-1"](../0166-delegation-primitives/change.md#dp-1-session-grant) and the reference tools of its "DP-5", which replace the names of "MD-23" of [`0135-message-delivery`](../0135-message-delivery/change.md#md-23-tool-and-frame-names) (0166 decision 16): `session.create` (reference tool `start_session`) for the specification's `lenny/delegate_task`, `session.send` (`send_message`) for the agent-facing `lenny/send_message`, `events.wait` (`await_sessions`) for `lenny/await_children`, `session.close` (`close_session`) for `lenny/cancel_child`, `session.list` (`list_sessions`) for `lenny/get_task_tree`, `files.import` (`import_file`) for MD-26's import, and `runtimes.list` (`discover_agents`) for `lenny/discover_agents`. `ask_question` keeps its name for `lenny/request_elicitation`, and `send_update` keeps its name. "Problem", "Current state", "Alternatives rejected", "Decisions" in `decisions.md`, and the records keep the names they were written with (E2, E5). |
| `disabledBy` | The field of the `DELEGATION_DISABLED` refusal that names the level that made delegation unavailable ("DA-3"). |
| Widening and narrowing | A write that makes delegation available where it was unavailable widens availability, and a write that does the reverse narrows it. Each writes its own audit event ("DA-1"). |
| Labels | Parts of the design carry the label DA-n, and requirements carry the label DAR-n. |

## High-level design

Delegation stays a platform primitive, built on the session grant of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md#dp-1-session-grant), and an operator can turn it off where it does not belong. The platform sets a default and can forbid delegation outright. A tenant can replace the platform default for its own sessions and can turn delegation off for one runtime in the tenant. A tenant's security team can forbid delegation for the whole tenant through its security record, and lifting that forbid waits out the record's weakening delay. A runtime can state that its sessions delegate or do not, which overrides both defaults, and a derived runtime can turn delegation off for the sessions it serves, which covers workers that run beside an orchestrator of the same base runtime. A client creating a session can turn it off for that session and its tree, as decision 26 already settled, and a parent can turn it off for one child. The forbids, a tenant runtime entry, a base runtime's `false`, and the session's and parent's choices can only take delegation away.

The gateway resolves at each session's creation whether the session may delegate, and gives a session a grant only when it may (0166 decision 39). On every call of a platform operation that needs the grant, the gateway resolves again, from the session's row and the live settings, and refuses with `403 DELEGATION_DISABLED` when the session may not delegate. The refusal names the level responsible. A session that has children keeps the operations that manage them. The session's `availability.delegation` carries the same answer to its runtime, and the reference MCP bridge offers the model `start_session` only while it is `true` (0166 "DP-5"). The platform tool list leaves out each tool whose call the session's settings guarantee to fail or to have no effect, such as `ask_question` on a session whose client declines input. A tool left out of a list costs the agent no context tokens and cannot be chosen. When a setting changes what a running session may do, the session's runtime receives an `availability_changed` notice at its next turn and lists again. A runtime that ignores the notice keeps its list until it lists again, and the refusal covers a stale entry.

The rest of this section states each part in the design's terms, which "Terms" above defines.

**Levels (DA-1).** `gateway.delegation.allowByDefault` and `gateway.delegation.forbid` in Helm, `delegation.allowByDefault` on the tenant, the delegation guardrail in the tenant security record, `allowDelegation: false` on an environment, `allowDelegation: false` on a tenant runtime entry, and `allowDelegation` on the Runtime with a restrict-only rule for derived runtimes.

**Resolution (DA-2).** A forbid wins, then a tenant runtime entry, then the runtime's value, then the tenant default, then the platform default. The session's room applies on top. A session receives a grant at creation only when it may delegate then, and the settings are live: the gateway reads them again at each call that needs the grant.

**Refusal (DA-3).** `403 DELEGATION_DISABLED`, which TS-3 introduces, gains `details.disabledBy`. The gateway checks at the top of each operation that needs the grant and again where the session core creates a child.

**Tool list (DA-4).** The gateway answers `ListPlatformTools` for the calling session. Every operation of 0166 "DP-1" carries the attribute by which the reference MCP bridge never lists it to a harness, and the bridge lists the session tools from `availability.delegation` and the session's children under 0166 "DP-5". The gateway omits `ask_question` on a session created with `inputPolicy: decline` and where §9.2 suppresses every elicitation of the session. A runtime revision that does not declare `capabilities.childSessions` may not delegate.

**Running sessions (DA-5).** Each operation that needs the grant reads the current settings at each call, and `ListPlatformTools` computes the list from the current settings at each list. The adapter keeps no copy. The `delegation` and `questions` members of the session's availability come from the same resolution, and the gateway sends `availability_changed` with `changedServers: ["platform"]` when either changes, under "RP-4".

**Per-hop narrowing (DA-6).** A parent that passes an explicit `maxChildrenTotal: 0` in the `limits` of `session.create` creates a child with no room, so the child cannot delegate.

**Other tools (DA-7).** Each other platform tool already has a control of its own, so no per-tool switch is added (O7). The list rules of "DA-4" read those controls.

```
 session.create from session S (pod, through the platform tool server)
        │
        ▼
 S is the calling session (TS-3); S holds a grant (0166 DP-1)
        │ no grant ──> 403 DELEGATION_DISABLED, details.disabledBy
        ▼
 Availability of S, read live from S's tenant, security record, and runtime:
   capability ─ platform forbid ─ guardrail ─ tenant runtime entry ─ runtime value ─ tenant default ─ platform default
        │ unavailable ──> 403 DELEGATION_DISABLED, details.disabledBy
        ▼
 Room on S's grant (stored maxDepth under TS-3, explicit maxChildrenTotal 0)
        │ no room ──> 403 DELEGATION_DISABLED (disabledBy: session) or DELEGATION_DEPTH_EXCEEDED
        ▼
 0166's caveats: PreRoute chain (kind: delegate), post-chain point (policy cap, isolation floor,
 remaining depth, binding and egress subsets, environment), carved budget
```

"Limits" states what the change costs: a runtime keeps a stale list until its next turn, or longer if it ignores the notice, a list change costs the runtime a provider prompt-cache write, a platform Helm change reaches running processes only after a gateway restart, a session created while delegation was unavailable holds no grant after a level widens (O18), and a pod that can reach the gateway's public API with a client credential can still create a root session.

## Current state

**No availability setting [source].** §5.1 gives the Runtime `delegationPolicyRef` and `allowSelfRecursion` (`pkg/apis/lenny/v1alpha1/runtime_types.go`, `runtimestore.Runtime`). §5.2 gives pools no delegation field. The tenant record carries no delegation field, although it carries `messaging.scope` (§7.2) and `leaseExtension` (§8.6). The Helm values that concern delegation are `gateway.cycleDetection.mode`, `gateway.allowSelfRecursion`, and `gateway.delegation.defaultMaxDepth` (§8.3), and the last is not rendered by the chart (F-8.3.12).

**A per-tenant runtime record exists [source].** §5.1 states "Capabilities are customizable per tenant", and the admin API serves `GET`, `PUT`, and `DELETE /v1/admin/tenants/{id}/runtime-capability-overrides/{runtime}` (`pkg/gateway/externalapi/admin/runtime_capability_overrides.go`), whose body holds capability axes such as `interaction` and `sdkWarmBlockingPaths`. RV-1 makes the record a narrowing ("Per-tenant capability override"). It carries no delegation field.

**`maxDepth` cannot be 0 today [source].** §8.2 **Effective `maxDepth` resolution** requires every effective lease to carry a positive integer, and every layer of its chain can only produce one. A client's `delegationLease` at creation is validated, stored, and echoed with no effect (F-8.2.34). TS-3 wires it and admits 0 as decision 26.

**A zero `maxChildrenTotal` in a lease slice means no limit [source].** §8.2's `LeaseSlice` table describes `maxChildrenTotal` as "Max children the child may spawn". The `lenny/delegate_task` input schema carries `leaseSlice.maxChildrenTotal` as an integer, `lease.ValidateChildSlice` checks a child's value only when both the parent's and the child's are greater than 0, and the stored `sessionstore.DelegationLease` documents that "A zero field means 'no limit set at this scope'". A parent that passes 0 today grants its child unlimited children. The session-creation request is different: `sessionstore.DelegationLeaseRequest` holds `maxDepth` and `maxChildrenTotal` as pointers so an explicit zero is distinguishable. §8.6 lists `maxChildrenTotal` among the extendable fields.

**`DelegationPolicy` rules are not applied to `lenny/delegate_task` [source].** `DelegationPolicy.Evaluate` has these production callers: `filterByEffectiveDelegationPolicy` for `lenny/discover_agents` (`pkg/gateway/mcpfabric/mcptools/mcptools.go`), `connectorauthz` for connector calls, and the pool isolation audit. The `lenny/delegate_task` handler (`mcptools_register.go`) checks environment scope through `runtimeAuthorizedForCaller` and `crossEnvReachable`, and `Service.detectCycle` (`pkg/gateway/mcpfabric/delegation/service.go`) reads the *target* runtime's `delegationPolicyRef` for the self-recursion layer and the content policy. No step evaluates the calling session's policy rules against the target. A policy that allows nothing therefore hides every target from discovery and blocks no delegation. The audit note 8.3-H1 in `BUILD-GAPS.md` records the missing call with no checkbox or F-id, and revision 2 files it as F-8.3.14.

**`approvalMode: deny` refuses the caller's own call [source].** §8.4 defines `deny` as "Delegation not permitted" on the lease, and §8.4 states that the `approval` value "is accepted at policy registration time". `lenny/delegate_task` accepts `approvalMode` as an argument, and `validateDelegation` returns `ErrDelegationDenied` (`DELEGATION_DENIED`) when the caller passes `deny`, before it reads the parent. Nothing stores the value on the child's lease, and nothing sets it on a root, so a runtime can only refuse itself (F-8.4.1's resolution). Revision 2 files this as F-8.4.4.

**`DELEGATION_DENIED` lives only in code and in the adapter proto [source].** No specification section and no page under `docs/` names it. The code names it in `errorclassify` (`"DELEGATION_DENIED": {CategoryPolicy, false}`), in the handler of `mcptools_register.go`, in comments of `delegation/service.go`, and in `delegate_approvalmode_test.go`. `schemas/lenny-adapter.proto` declares `ERROR_CODE_DELEGATION_DENIED = 20`, and the generated `pkg/proto/adapter/v1/lenny-adapter.pb.go` carries it.

**How the tool list is built [source].**

- The adapter starts the platform MCP server once per pod (`startPlatformMCP`, `pkg/adapter/platformmcp.go`). Each `tools/list` goes to `platformToolProvider.List`, which resolves the calling session through `callingSession` and forwards `ListPlatformTools` with that session's ID over `GatewayControl` (`pkg/adapter/platformtoolprovider.go`). The adapter keeps no copy: `toolList` in `pkg/adapter/mcp/server.go` calls the provider on every `tools/list`, so each list reaches the gateway.
- The gateway's `Bridge.ListPlatformTools` (`pkg/gateway/gatewaycontrol/platformtools/platformtools.go`) ignores the session ID and returns `Catalog()` of the gateway's `/mcp` server. Its comment states that "the catalog is uniform across type:agent sessions".
- That catalog holds every tool `mcptools.Register` installs: the tools of §9.1's table, `lenny/vcs_token`, and the client-facing tools such as `lenny/create_session`, `lenny/create_and_start_session`, `lenny/list_sessions`, and `lenny/upload_files`. A runtime can call `lenny/create_session` from its pod and start a new root session outside its delegation lease. TS-3 found this and allow-lists the bridge to §9.1's table. `BUILD-GAPS.md` already records it as F-9.1.13, so revision 2 files no new finding for it.
- `lenny/delegate_task` is never refused for being disabled, because nothing disables it.

**The server cannot announce a change [source].** `initializeResponse` in `pkg/adapter/mcp/server.go` declares `"tools": {}` with no `listChanged`, and the serve loop only answers requests. No list-change notification exists in the tree: no Go file under `pkg/`, `cmd/`, or `sdks/` and no proto under `schemas/` names `listChanged` or `list_changed`. The server speaks MCP `2025-03-26`. The runtime protocol design removes the server and moves the platform tools to tool frames ("RP-3"). CA-8 found the same for connector servers and proposes the adapter changes and a gateway-to-adapter RPC, `NotifyConnectorToolsChanged`, for a runtime that declares `deferredToolDiscovery`.

**A process can outlive a session [source].** The platform MCP server is pod-wide, and `callingSession` resolves the caller per request to the single session the pod's shared runtime process holds. §28.5.3 states that a later session's manifest write does not re-arm the server. TS-3 notes that a runtime process that listed before a change can hold the earlier list.

**What MCP requires [external].** Under `2025-11-25`, a server declares its capabilities in the `initialize` result, and a server that declares `tools.listChanged` "SHOULD" send `notifications/tools/list_changed` when its tools change, after which the client lists again. Under `2026-07-28`, no `initialize` handshake exists for a modern client: a server "MUST implement `server/discover`", whose result carries `capabilities`, and the server sends the notification on a `subscriptions/listen` stream the client opened with `toolsListChanged: true`. | Session | `delegationLease.maxDepth` at creation, and an explicit `maxChildrenTotal: 0` in the `limits` of the parent's `session.create` | Client, and the parent session | Under "Session level" in DA-2 and under DA-6. |

**Tenant delegation settings.** The route `PUT /v1/admin/tenants/{id}/delegation` also carries the tenant's `policyRef`, a `DelegationPolicy` applied to every session in the tenant, `sessionBudget`, the tenant's level of `gateway.delegation.sessionBudget` (0166 decision 52), and `ceilings`, a maximum for each numeric resource caveat other than the carved budget, whose ceilings are the session budget settings of [`0170-budgets`, "BG-2"](../0170-budgets/change.md#bg-2-session-budgets), which [`0166-delegation-primitives`, "DP-1"](../0166-delegation-primitives/change.md#dp-1-session-grant) reads as root grant inputs (0166 decision 26). This change owns the route, its storage, its `If-Match`, and its audit, and 0166 owns how `policyRef` and `ceilings` enter the resolution of each caveat. `allowByDefault` decides availability, and `policyRef` and `ceilings` never do: a policy that admits no runtime leaves a session that may delegate with no target it can reach, as "Alternatives rejected" states. The form of the route is open decision O10, and 0166's tenant delegation settings wait on it.

**Environment.** `allowDelegation: false` on an environment makes delegation unavailable for every session whose environment it is, whatever the runtime, the tenant runtime entry, or the tenant default say (0166 decision 50). It accepts only `false`, and a write of `true` is refused as a widening, as the tenant runtime entry's is, because an environment narrows its tenant and never widens it. Clearing the field removes the narrowing. It is everyday policy of the tenant's administrators: setting and clearing it each apply in the write's transaction, with no delay, as the tenant default does (0166 decision 51). A security team that needs a forbid that a `tenant-admin` cannot lift uses the delegation guardrail, which is tenant-wide like every member of the security record. A session's environment is the one TS-3 records on its row, so a child that crossed into another environment under a sharing path reads the target environment's value.

**Ceilings are not switches.** A numeric ceiling never decides availability. 0166 "DP-1" refuses a ceiling of 0 for `maxDepth`, `maxChildrenTotal`, or `maxParallelChildren` at the platform, the tenant, the environment, or the runtime, and its error names these levels (0166 decision 50).

**Derived runtimes.** `allowDelegation` merges restrict-only, as `allowSelfRecursion` does under §5.1. A derived runtime may set `false` on any base. It may set `true` only when the base's value is not `false`, and the write answers `422 INVALID_DERIVED_RUNTIME` with `details.field: "allowDelegation"` otherwise. The status and `details.field` are those [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md#fields) states for a derived-runtime refusal. The tree answers that refusal with `400` and no `details` today (`pkg/gateway/api/admin/runtimes.go`), so 0126.S1 answers with the status and details the derived-runtime refusal carries in the tree when it lands, and the step that moves that refusal to `422` moves this case with it. The merged value is `false` when either value is `false`, `true` when either is `true` and neither is `false`, and unset otherwise. A base that later changes to `false` makes the merged value `false` at the next resolve, which DR-6 already lists as a narrowing that "applies at the next resolve". A derived runtime's `true` over an unset base lets a tenant override its own tenant default for that runtime, and it cannot lift a forbid.

**Workers beside orchestrators.** An operator who runs one base runtime as an orchestrator that delegates and as workers that must not delegate registers a derived runtime for the workers with `allowDelegation: false`, with its own pool at the isolation profile and size the workers need. A tenant does the same with a tenant-derived runtime and its owned pool. The client or the orchestrator names the worker runtime as the target, so the setting sits on the name the caller selects, and a `PreRoute` interceptor that moves a session to another pool of the same runtime does not change its availability. This is the case revision 2 served with a pool-level `false`, which the owner dropped (D2).

**Owned pools.** Pools carry no delegation field, so the template copy of DR-5 copies none, and an owned pool has no delegation rule of its own.

**Tenant runtime entry.** A tenant runtime entry with `allowDelegation: false` applies to the sessions of that tenant whose runtime is the named runtime or a derived runtime whose base it is, merged restrict-only as above. It accepts only `false`: a write of `true` is refused as a widening, as RV-1's "Per-tenant capability override" refuses a widening of `capabilities.interaction`, because a tenant widens a runtime only through a tenant-derived runtime. Clearing the field removes the narrowing. The entry is the tenant's way to turn delegation off for one platform runtime whose `allowDelegation: true` overrides the tenant default (D1).

**Writes and audit [design].** Each field is part of an existing admin write, so the existing audit rows for runtime, tenant, tenant runtime entry, and security record changes record it. On top of them, a write at the tenant default, an environment, the tenant runtime entry, or the runtime level that changes the resolved availability of any running or future session writes one of these events, carrying the level, the old and new values, and the actor: `delegation.availability_narrowed` when it makes delegation unavailable where it was available, and `delegation.availability_widened` when it does the reverse. A SIEM rule can then alert on widening alone.

**The guardrail's transitions [design].** The delegation guardrail follows SO-2's rules for every forbid in the record. Setting it is a tightening: it applies in the write's transaction and emits `security.config_tightened`, and each session's next call and next list read it. Removing it is a weakening: it needs a `justification`, creates a pending version, emits `security.config_weakening_requested` at once, and takes effect only at `effectiveAt`, after the tenant's `weakeningDelaySeconds`, when the applier emits `security.config_weakened` and the next call and list of each session read the new version. A `security-admin` can cancel the pending removal. A `tenant-admin` cannot write the record, so a tenant's own administrators cannot lift the guardrail, and a stolen administrator credential cannot lift it inside the delay without the security team seeing the request (D5, DAR-9). What the guardrail refuses at each operation, and what happens to a call in flight when it is set, is 0142's enforcement row for `delegation` ([SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture)).

**Switches for an incident.** `gateway.delegation.forbid` takes effect only when the gateway restarts with the new value, so it is a deployment posture and not a switch for an incident. During an incident an operator uses a live level: a `platform-admin` sets `allowDelegation: false` on the runtime involved, which reaches every tenant's sessions of that runtime at their next call, and a tenant's `security-admin` sets the delegation guardrail, which applies in the write's transaction. A `tenant-admin` can also set the tenant default to `false`, set `allowDelegation: false` on an environment, or write a tenant runtime entry. Each change is enforced at the next call of every running session it reaches, reaches the session's runtime as `availability_changed` at the session's next turn, and reaches its list when the runtime lists again ("DA-5").

### DA-2 Resolution

**Runtime capability (E1).** Before the levels below, a session whose runtime revision does not declare `capabilities.childSessions: true` may not delegate, and the refusal names `disabledBy: capability`. The capability states what the binary can do, so no level lifts it, and it is versioned with the revision.

For a session S with tenant T and runtime R (merged with its base when R is derived), read live at each call:

| Order | Condition | Result | `disabledBy` |
| :-- | :-- | :-- | :-- |
| 1 | `gateway.delegation.forbid: true` | Unavailable | `platform` |
| 2 | T's active security record carries `"delegation": "forbid"` | Unavailable | `securityGuardrail` |
| 3 | S's environment carries `allowDelegation: false` | Unavailable | `environment` |
| 4 | T's tenant runtime entry for R, or for R's base, carries `allowDelegation: false` | Unavailable | `tenantRuntime` |
| 5 | R's merged `allowDelegation` is set | That value | `runtime` when `false` |
| 6 | T's `delegation.allowByDefault` is set | That value | `tenantDefault` when `false` |
| 7 | Otherwise | `gateway.delegation.allowByDefault` | `platformDefault` when `false` |

S may delegate when it is available and has room. S has room when its stored `maxDepth` is greater than its own depth and its grant's `maxChildrenTotal` is not an explicit 0. A session without room gets one of these refusals:

- `DELEGATION_DISABLED` with `disabledBy: session` when its stored `maxDepth` is 0, which a client sets at creation with `delegationLease.maxDepth: 0` and a parent sets for a child with `maxDepth: 0` in `session.create`, or its grant's `maxChildrenTotal` is an explicit 0, which a client sets with `delegationLease.maxChildrenTotal: 0` and a parent through the `limits` of `session.create` (DA-6). TS-3 no longer stores a `maxChildrenTotal` of 0 as `maxDepth: 0` (0149 decision 44). Either value states that the session is not to delegate.
- `DELEGATION_DEPTH_EXCEEDED`, as today, when its stored `maxDepth` is positive and not greater than its depth, because its tree can delegate and it has reached the limit.

The rule and "DA-6" therefore give one refusal for a child that a parent created unable to delegate: `DELEGATION_DISABLED` with `disabledBy: session`. Revision 2 stored the child's depth as its `maxDepth` for this case, which this rule would have answered with `DELEGATION_DEPTH_EXCEEDED`, and the review found the disagreement.

**Examples.** Platform default `true` with no forbid:

| Tenant default | Tenant runtime entry | Runtime | Effective | Reason |
| :-- | :-- | :-- | :-- | :-- |
| Unset | Unset | Unset | Available | Platform default |
| `false` | Unset | Unset | Unavailable, `tenantDefault` | The tenant default replaces the platform default |
| `false` | Unset | `true` | Available | The runtime is more specific than the tenant default |
| Unset | `false` | `true` | Unavailable, `tenantRuntime` | The tenant narrows one runtime |
| `true`, with the guardrail set | Unset | `true` | Unavailable, `securityGuardrail` | A forbid wins over every value below it |

**Whether a session holds a grant (0166 decision 39).** The session grant of [`0166-delegation-primitives`, "DP-1"](../0166-delegation-primitives/change.md#dp-1-session-grant) exists only for a session that may delegate when it is created. The gateway resolves "may delegate" for a root at its creation, and for a child from the child's own row once the child's `PreRoute` chain has settled its final runtime at the post-chain point. A session that may delegate then receives a grant, whose caveats 0166 resolves. A session that may not delegate then receives none, keeps none for its life, and is refused every operation that needs the grant with the `disabledBy` of the level that decided it. A session that holds a grant is checked again at each call that needs it, so a level that narrows reaches it at its next call, and a level that widens again restores its use of the grant it holds. A level that widens after a session's creation does not give that session a grant. The owner accepted this difference from O4's live reads in both directions as O18 on 2026-11-23. A session with no depth left, a root created with `maxDepth: 0`, a child whose parent passed `maxDepth: 0`, or a session at its tree's depth limit, also receives no grant (0166 decision 50), so its `availability.delegation` is `false` and the reference bridge does not list `start_session`, and an operation that needs the grant gets the refusal of the room rule above.

**Live reads.** The gateway reads the settings at each call of an operation that needs the grant and at each `ListPlatformTools` call, and the adapter keeps no copy of the list (O4, "DA-5"). The tenant, security record, tenant runtime entry, runtime, and base runtime rows are read from their stores at each call, each list, and each turn opening that computes the availability of "DA-5". The gateway keeps no cache of them, so a write served by one replica governs the next read on every replica. The platform values are process flags. A change reaches a running session at its next call.

**Failed reads.** A read that fails leaves the gateway unable to resolve availability, and the gateway fails closed, as `.claude/rules/code-best-practices.md` requires on a security-relevant path. An operation that needs the grant is refused with a retryable error of category `TRANSIENT`, never with `DELEGATION_DISABLED`, so a runtime does not read a store failure as a setting. A session whose availability cannot be resolved at its creation receives no grant, and its creation proceeds, because a session that cannot delegate is still a session. The availability computation sends `false` for a member it cannot compute, and the platform tool list treats a pool row that cannot be read as suppressing every elicitation, so it omits `ask_question`. The operations DAR-6 keeps for a session that has children are not refused for a failed read of the levels, because they do not depend on availability. This matches §8.3's rule that a delegation policy "is re-evaluated on each `delegate_task` call", which 0166 restates for `session.create`, and it keeps §8.3's rule that a change "does not affect active child sessions": a child already running continues (DAR-6).

**Delegated children.** A child's own availability is resolved from the child's row, whose runtime is the one its `PreRoute` chain (`kind: delegate`) settled at the post-chain point. The post-chain point refuses no child for availability: availability is a property of the session as a delegator, and a runtime with delegation unavailable can still be a target, which the grant's policy cap decides under 0166. A child whose runtime makes delegation unavailable is created with no grant, and it still holds `session.self` and `files.import` of a file part delivered to it (0166 "DP-1"). The parent's availability is read from the parent's row before the chain runs.

**Session level.** The session level reuses decision 26 and adds no field:

- **Create.** A client sets `delegationLease.maxDepth: 0` on `POST /v1/sessions` and `POST /v1/sessions/start`, as TS-3 wires them. `create_and_start_session` is no longer a root creator in Lenny under TS-3, because the MCP and provider adapters of [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md) create sessions through the REST routes. `delegationLease.maxChildrenTotal: 0` leaves the session no room while it holds, as a resource value under DA-6, and TS-3 no longer stores it as `maxDepth: 0` (0149 decision 44). `delegationLease.maxDelegationPolicy` narrows the policy cap under 0166 "DP-1" and does not decide availability.
- **Narrowing only.** A session's `maxDepth` resolves under 0166 "DP-1" "Resolution", which TS-3 cites, so a client lowers it and never raises it above a ceiling. A session can turn delegation off and can never turn it on where any level makes it unavailable. A session that sets a positive `maxDepth` on a runtime with delegation unavailable gets `disabledBy` from that level.
- **Children.** A child's grant carries its parent's `maxDepth`, so a root at 0 has no children, and a parent with room can narrow one child with an explicit `maxChildrenTotal: 0` in the `limits` of `session.create` (DA-6). The availability levels are not inherited: each child resolves its own runtime, and its tree's stored `maxDepth` still bounds it.
- **Mid-session (D3).** No request changes a session's stored `maxDepth` or `maxChildrenTotal` to disable delegation, and §8.6 already makes `maxDepth` not extendable. An operator who must stop a running session's delegation uses a level above the session, which takes effect at the next call.
- **Derive (O5).** TS-3 stores the source's `maxDepth` minus the source's depth, with a floor of 0. This design adds `delegationLease.maxDepth` to the derive request, which can only lower that value, so a client can derive a session that cannot delegate. A source at its tree's depth limit yields a stored `maxDepth` of 0, so the derived session answers `DELEGATION_DISABLED` with `disabledBy: session`, as a root created with `maxDepth: 0` does. The derived session resolves availability from its own runtime, which [`0144-session-derive`](../0144-session-derive/change.md#sd-1-one-route) lets differ from the source's.
- **Resume and recovery (O5).** A resume keeps the row and the grant, so it keeps the stored value, and the levels are read live after it. Each session recovers under [`0146-session-lifecycle`](../0146-session-lifecycle/change.md) with its own row and grant (0166 decision 15), and its next call reads the levels live.

### DA-3 Refusal

The gateway refuses an operation that needs the grant with `403 DELEGATION_DISABLED`, which TS-3 introduces with category `POLICY` and `retryable: false`. This design adds `details.disabledBy`, one of `capability`, `platform`, `securityGuardrail`, `environment`, `tenantRuntime`, `runtime`, `tenantDefault`, `platformDefault`, and `session`, and `details.effectiveSettings` with the values each level held, as §8.2's cycle refusal reports `blockedBy` and `effectiveSettings`. What `details.effectiveSettings` holds, and whether the pod receives it, is O14. A `capability` value names the runtime revision that does not declare `capabilities.childSessions` (E1, review finding M2). A `runtime` value names the runtime and states whether the `false` came from its base, an `environment` value names the environment, a `tenantRuntime` value names the runtime the entry names, and a `securityGuardrail` value names the active security record version.

**Which operations.** The refusal applies to every platform operation of 0166 "DP-1" that needs the grant, with these exceptions, as 0166 states:

- A session that has children keeps the operations of DAR-6: `events.wait`, `events.peek`, `session.get`, `session.list`, `session.close`, `session.send`, `session.interrupt`, `session.messages`, `session.set_limits` for a cut, `questions.answer`, `questions.forward`, and `tools.result`. A child counts when it is a session row whose parent link names the session, in any state.
- Every session holds `session.self`, and `files.import` of a file part delivered to it, whatever its grant.

`session.create`, `session.transfer`, `session.release`, `runtimes.list`, and a `session.set_limits` that raises a limit are refused while the session may not delegate, whether or not it has children. The refusals of `leave` and `leaveMaxDepth` on a transfer or a release are 0166's.

The check runs at each of these points, as TS-3 places its own:

- At the top of each operation's handler, after TS-3 fixes the caller as the calling session, and for `session.create` before the target resolution, the `PreRoute` chain, the export, and any pod claim. This covers a call from the pod (DAR-1). Until 0166.S1 replaces the gateway-hosted delegation tool with `session.create`, the check runs at the top of that tool's handler in the same place. A call from a client at the gateway `/mcp` endpoint leaves with the MCP API under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md). The REST routes of 0138 by which the root's client transfers or releases a descendant are governed by the root's grant, which 0166 "DP-2" states.
- Where the session core creates a child, before the parent lookup's later checks, for any caller that bypasses the handler.

The gateway counts refusals in `lenny_delegation_disabled_refusals_total{disabled_by}`. A runtime that calls `session.create` from a stale list appears there, which tells an operator that the runtime has not listed since the change. Each refusal also writes the delegation rejection audit that §8.2 states for a refused delegation, with `DELEGATION_DISABLED` and `disabledBy`.

`Bridge.ListPlatformTools` uses the session ID it already receives. At each list it reads the session's row and the current settings, and after TS-3's allow-list it removes the inapplicable tools by this table (DAR-10). The third column states the answer a call receives when the runtime calls the tool anyway, for example from a stale list. That answer is the enforcement, and the list keeps the tool's description out of the agent's context (S2).

| Tool | Listed when | Answer to a call the list omits |
| :-- | :-- | :-- |
| The operations of 0166 "DP-1" | Always, each with the attribute of "RP-3" that marks a platform tool the reference MCP bridge never lists to a harness. | The refusal of "DA-3" for an operation the session may not call. |
| `ask_question` | The session's `inputPolicy` is `ask` (R12), and §9.2 does not suppress every elicitation of the session. §9.2 suppresses every elicitation when the session is delegated and its pool's `elicitationDepthPolicy` is `block_all`, and when the session's depth is at or beyond the pool's suppression depth (3 by default, N under `suppress_at_depth: N`, none under `allow_all`) and the pool's allow list names no elicitation type. | The immediate `decline` of R12 under `inputPolicy: decline`, or `SUPPRESSED` under §9.2. |

| Every other tool on the allow-list | Always, as "DA-7" states. | The tool's own answer. |

**The session tools.** Revisions 1 to 13 listed `start_child_session` and `discover_agents` by "may delegate" and the tools that manage children by whether the session had a child. Under 0166 decision 39 those rules leave the gateway. The reference MCP bridge lists `start_session` and `discover_agents` when `availability.delegation` is `true`, and the tools that manage children while `session.list` names a child, under [`0166-delegation-primitives`, "DP-5"](../0166-delegation-primitives/change.md#dp-5-reference-extension). Another extension decides its own list from the same members. `availability.delegation` is "may delegate" of "DA-2", which this change supplies ("DA-5").

**`session.create` arguments and result.** `session.create` names the child's runtime in `target`, as 0166 "DP-1" states and as O13 of [`0124-connector-removal`](../0124-connector-removal/decisions.md#owner-decisions) settled for the tool it replaces. Its result carries no `origin` member. Lenny keeps no external-agent concept, so no target, discovery entry, or child listing marks a runtime as one that talks to an external agent, and a runtime that talks to one does so itself through egress (CR-3).

**What changes the list.** The platform tool list of a running session changes when its pool's `elicitationDepthPolicy` or allow list changes. The session's depth and its `inputPolicy` are fixed for the session. A delegated child carries the default `inputPolicy` of R12, `ask`, because no client request creates it. The list keeps a fixed tool order, as `2026-07-28` recommends. A change of "may delegate" changes `availability.delegation`, and with it the bridge's list of session tools.

`Bridge.CallPlatformTool` does not check the list. A call to a tool the session's list omits reaches the handler, which answers with the refusal of "DA-3" for an operation and the existing answers for the others. A call to a name outside TS-3's allow-list answers `ErrPlatformToolNotFound`, which the adapter writes as a `tool_result` with `error.code: "TOOL_NOT_FOUND"` ("RP-3"). The reference MCP bridge maps `TOOL_NOT_FOUND` to JSON-RPC `-32602`, the MCP error for an unknown tool **[external]**, as "RP-5" states. Today `callTool` in `pkg/adapter/mcp/server.go` reports any forwarded failure as `-32603` **[source]** (F-15.4.8); the runtime protocol design removes that server, which closes the finding once the bridge's mapping lands.

Lenny keeps no client-facing tool catalogue. Revision 10 kept one catalogue at the gateway `/mcp` endpoint for every client, because a connection names no session until a call does. Under [`0138-rest-only-client-api`](../0138-rest-only-client-api/change.md), that catalogue leaves with the MCP API, and the MCP adapter builds its own from Lenny's OpenAPI document (R7). The platform tool list of this section is the only list Lenny computes.

**Runtimes whose harness is an MCP client.** A runtime whose harness is an MCP client connected to several servers, such as Claude Code with the bridge's platform server and servers of its own, among them an operator's MCP services that it reaches through egress (CR-3), sees a change to the platform list or to the session tools when it lists that server again, which the bridge prompts with `notifications/tools/list_changed` on an `availability_changed` that names `platform`, and a client that prefixes tool names by server, as Claude Code did in the CA-9 spike, keeps the prefix on the platform tools.

### DA-5 Running sessions

The owner chose option (D) on 2026-11-10 (O4), reopened O4 on 2026-11-11 (RP D4), and settled the notice on 2026-11-12 (RP O6 (e) and O8 (b)) **[design]**. 0166 decision 39 gives a session a grant at creation only when it may delegate then, which O18 settles.

**Reads at each call and each list.** Each operation that needs the grant reads the current settings at each call ("DA-2" and "DA-3"). `ListPlatformTools` computes the list for the calling session from the current settings at each list ("DA-4"). The adapter forwards each `list_tools` frame to the gateway and keeps no copy of the list ("RP-3").

**Notice (replaces revision 9's "No notification").** The session's availability carries `delegation`, whether the session may start a child now, and `questions`, whether it may ask a question. The gateway computes `delegation` as `true` when the session holds a grant and may delegate under "DA-2", and `questions` with the `ask_question` rule of "DA-4", and writes both on every `session_start`. The coordinating replica recomputes them when it opens a turn with a message and when it records a turn the runtime opened, and calls `UpdateAvailability` with `changedServers: ["platform"]` when either differs from what it last sent; the adapter writes `availability_changed` to the slot's runtime connection and tool connections ahead of the turn's first message ("RP-4"). A change to a pool's `elicitationDepthPolicy` or allow list reaches `questions` the same way.

**Stale lists.** A session that listed before a change keeps its list until its runtime lists again. The notice shortens that window to the session's next turn for a runtime that honours it. The reference bridge answers the platform server's list with `ttlMs: 0` and `cacheScope: "private"` ("RP-5"), so a harness that honours the hints treats the list as stale at once and never shares it across sessions. Each list the harness makes reaches the gateway.

**Blast radius.** Option (D) changes the handlers of the operations that need the grant and `Bridge.ListPlatformTools` in the gateway, and supplies the resolver to the availability computation of "RP-4" and to the grant creation of 0166 "DP-1". The tool frames, `UpdateAvailability`, the `availability_changed` frame, and the bridge's `-32602` mapping and cache hints belong to the runtime protocol design. Revision 3's option (A) needed a per-session list in the adapter, a fan-out from every admin write path and from the SO-2 applier, and a rate flag ("Alternatives rejected"); the notice of "RP-4" needs none of them, because it is recomputed per turn.

**MCP versions.** The reference bridge serves `2025-11-25` and `2026-07-28` (MP-5). Each bridge serves one slot, whose runtime process serves one session, so the list varies only over time as settings and children change, which `2026-07-28` permits **[external]**.

### DA-6 Per-hop narrowing

**Two switches (D4, O19) [design].** A parent that passes an explicit `maxChildrenTotal: 0` in the `limits` of `session.create` creates the child with no room for children now. The 0 is a resource value: the child's grant records it as an explicit 0, the child cannot delegate while it holds, its `availability.delegation` is `false`, its refusal names `disabledBy: session` under the rule of DA-2, and the parent that set it may raise it later with `session.set_limits` (O19). A parent that wants the child never to delegate passes `maxDepth: 0` in `session.create`, which gives the child a remaining depth of 0. Depth is a security caveat of [`0166-delegation-primitives`, "DP-1"](../0166-delegation-primitives/change.md#dp-1-session-grant), so no hop, extension, or `session.set_limits` raises it, and the refusal names `disabledBy: session` in the same way. A grandchild cannot exist, so no inheritance rule is needed below it. The field means "Max children the child may spawn" in §8.2, and 0166 keeps it as a resource caveat of the grant, so 0 reads as its plain meaning. Until 0166.S1 lands, the parent passes the same value as `lease_slice.maxChildrenTotal: 0` on the gateway-hosted delegation tool.

**Explicit zero.** The `limits` argument distinguishes an explicit 0 from an absent field, as `DelegationLeaseRequest` already does on session creation, and the child's grant distinguishes them as well. An absent field keeps its meaning, no limit set at this hop beyond what the parent's grant has left. `lease.ValidateChildSlice`, or its successor under 0166, admits an explicit 0 against any parent, because it narrows. This changes the meaning of an explicit 0, which today means no limit (S4).

**Extension.** §8.6 lists `maxChildrenTotal` as extendable, and 0166 "DP-3" keeps lease extension for the resource caveats. An extension never raises a `maxChildrenTotal` that is an explicit 0, because the 0 records the parent's decision, which an exhausted budget does not. The parent that set the 0 may raise it with `session.set_limits`, which is that parent's own later decision (O19).

**Removal of the argument.** Today's delegation tool stops accepting `approvalMode`. `ErrDelegationDenied` and the `DELEGATION_DENIED` code go from `validateDelegation`, the handler of `mcptools_register.go`, `errorclassify`, `delegate_approvalmode_test.go`, and the `ErrDelegationDenied` case of `pkg/gateway/platformtools/delegation/service_test.go`, because no caller refuses itself any longer. The handler also stops validating the argument with `lease.ValidateApprovalMode` and stops passing it as `Request.ApprovalMode`. The delegation rejection audit, which records the declared `approvalMode` under F-8.4.3, records the parent lease's `approvalMode` in its place, `policy` when the lease sets none, until 0166.S4 drops the lease field under its "DP-6". `schemas/lenny-adapter.proto` drops `ERROR_CODE_DELEGATION_DENIED = 20` and declares `reserved 20;` and `reserved "ERROR_CODE_DELEGATION_DENIED";` in the `ErrorCode` enum, so neither the number nor the name is reused, and the generated code is regenerated. No specification section changes for the code, because none names it. `session.create` of 0166 takes no `approvalMode` argument. The removal closes the self-refusal half of F-8.4.4. The other half, that no path stores `deny` on a lease, is O12's.

## Limits

- **A runtime keeps a stale list until its next turn, or until it lists again.** The `availability_changed` notice reaches the runtime at the session's next turn ("RP-4"), so a change during a turn is not announced until the turn ends. A runtime that ignores the notice keeps its list until it lists again. A runtime that listed before delegation became unavailable is still offered `start_session` by the reference MCP bridge in that window, and its call is refused, which the refusal counter of "DA-3" shows. A runtime that listed before delegation became available again is not offered the tool until it lists again.
- **No process carries a list into a new session.** Under [`0145-session-isolation`](../0145-session-isolation/decisions.md#decisions) decision D4, a runtime process serves at most one session over its life, and since the owner removed pre-launched runtimes on 2026-11-12, every runtime process launches at bind, after its session's workspace is built. A list a runtime holds was therefore made for its own session.
- **A list change costs a prompt-cache write.** A runtime that lists again sends its model a changed set of tool definitions. Providers cache a prompt prefix in the order tools, system, and messages, and a change to the tools invalidates the cached prefix after it **[external]**, so the runtime's next model call after a change pays the provider's cache-write price for its whole prompt. A change at a tenant or runtime level reaches every running session of that tenant or runtime, so it costs one such write per session that lists again. The fixed tool order of "DA-4" keeps a list that did not change from costing one.
- **The model may not be told of the change.** A runtime that ignores the notice gives its model no sign of the change. A model that planned to delegate learns of the change from the refusal text.
- **A Helm forbid is not a switch for an incident.** `gateway.delegation.forbid` and `gateway.delegation.allowByDefault` take effect when the gateway restarts with them, so a process meets them at its next call after the restart, receives them in its availability at its next turn, and sees them in its list when it lists again. During a rolling restart, replicas hold different values of the two flags, so a session's calls, lists, and availability can resolve against either value until the rollout completes. "Switches for an incident" under DA-1 names the live levels.
- **Lifting the guardrail waits out the delay.** A tenant that set the delegation guardrail during an incident regains delegation only after the SO-2 weakening delay, which is the protection D5 asks for.
- **A disabled level does not stop a running child.** A child created before the change runs to completion, and its own next call reads the new value.
- **A level that widens reaches only new sessions.** A session created while delegation was unavailable holds no grant, so a level that widens later gives it none, and only sessions created afterwards delegate. A session that holds a grant and lost delegation to a narrowing regains it when the level widens again. The owner accepted the difference from O4's live reads in both directions as O18.
- **The public API is a path around the setting.** DAR-8 closes the pod's path to root-session creation through the platform tool server. A pod whose egress reaches the gateway's public API and which holds a client credential, such as a user's bearer passed into the workspace, can call `POST /v1/sessions` and start a root session outside its grant and outside this setting. The egress policy of the pod and the handling of client credentials govern that path, and this design adds no check to it. The platform operations of [`0166-delegation-primitives`](../0166-delegation-primitives/change.md) give an orchestrator a way to create children without a client credential in the workspace, so a deployer has no need to place one there.
- **An explicit zero changes meaning.** A runtime written against the current code, which treats `leaseSlice.maxChildrenTotal: 0` as no limit, now creates a child that cannot delegate, and so does an extension that passes an explicit 0 in the `limits` of `session.create`.

## Alternatives rejected

- **Express "disabled" as a `DelegationPolicy` that allows nothing.** The policy decides targets, it has no default at the tenant or the platform, the gateway does not apply its rules to `start_child_session` today, and "allows nothing" can only be known by evaluating every runtime's labels, so the tool list could not follow it.
- **Use `maxDepth: 0` in the Runtime's default lease or in a preset.** §8.2's item 3 and item 2 would carry it, and TS-3's minimum would make it restrict-only. Neither layer exists in code, a minimum gives no default that a lower level can override, and it ties availability to the depth budget, so a refusal could not name the level.
- **Make the levels restrict-only (O1 option A).** A platform or tenant default of `false` could never be overridden, so it would be a forbid under another name.
- **Notify the runtime of each change (revision 3's O4 option A).** Revision 3 recommended live reads with a best-effort notification. The platform MCP server declared `tools.listChanged` in the `2025-11-25` `initialize` result and in the `2026-07-28` `server/discover` result, and implemented `subscriptions/listen` for `2026-07-28` clients. The adapter kept one list per session and cleared it on a notification RPC from the gateway, which generalized CA-8's `NotifyConnectorToolsChanged` (withdrawn since with connectors, CR-1), and on a new session's bind. Each admin write and each activation of a security record version that changed a value the resolution reads made the gateway enumerate the running sessions it reached and send the RPC for each through the session's coordinating replica, rate limited by `--delegation-list-change-rate` and counted in `lenny_platform_tools_list_changed_total{outcome}`. The owner asked for the smallest blast radius, and option (D) has it: the adapter caches nothing today, `ListPlatformTools` already receives the session ID, and no notification exists in the tree, so (D) changes two gateway functions where (A) added an adapter cache, an RPC, a fan-out from every write path, a flag, a counter, and two protocol features. The refusal enforces the setting under both options, and most harnesses list once per connection, so the notification would shorten the stale window only for a runtime that honours it. The notification can be added later without changing (D) (O4). The runtime protocol design later added it in another form, recomputed at each turn with no fan-out ("DA-5", O4 as reopened).
- **Snapshot availability at creation (O4 option B).** The gateway would resolve each session's availability at creation, store it on the session row, and read the stored value at each call and list. It changes the session store and every creation path, including delegation, derive, and the provider surfaces, as well as the two gateway functions that (D) changes, so it is larger than (D). It also loses the incident switch: a runtime turned off during an incident would keep delegating for the life of its sessions.
- **Live for a change that disables, snapshot for one that enables (O4 option C).** It needs the stored snapshot of (B) beside the live read of (D), for no gain the owner asked for.
- **A pool level.** Revision 2 proposed `allowDelegation: false` on a pool. A `PreRoute` interceptor or a runtime route can move a session to another pool of the same runtime, so a pool setting would make availability depend on a placement the client and the runtime author do not see, and the pool level added an owned-pool copy rule and a resolution step. A derived runtime with `allowDelegation: false` serves the same case on the name the caller selects. The owner dropped the pool level (D2).
- **`approvalMode: deny` as the per-hop switch.** Revision 2 recommended giving `deny` that meaning. `approvalMode` is a policy-level enum whose `approval` value is reserved, and a field of the lease slice that already counts children carries the meaning directly. The owner chose `lease_slice.maxChildrenTotal: 0` (D4).
- **A tenant forbid on the tenant record.** Revision 2 put `delegation.forbid` and `forbidSetBy` on the tenant record, written by a `tenant-admin` or a `platform-admin`. A forbid that the tenant's own administrators can clear protects no one from a stolen administrator credential, and the security record already gives every forbid a single writer, a weakening delay, and SIEM events. The owner moved the hard switch there (D5).
- **Keep a uniform tool list and rely on the refusal.** The owner asked that the tool not be offered. Every listed tool's description costs context tokens on every model call, and an agent offered a tool it cannot use can choose it and waste a turn on the refusal (S2).
- **Omit the platform tool server, the one entry of the session's `toolServers`, when delegation is unavailable.** The other platform tools would go with it.
- **A per-runtime allow-list of platform tools.** Every tool already has a control of its own (DA-7), a list of names would duplicate those controls without their semantics, and an omitted core tool such as `ask_question` would break a session that needs it. The list rules of "DA-4" read the existing controls, so an operator sets nothing new (O7).
- **An environment level written as a ceiling of 0.** A ceiling is fixed when a grant is created, leaves the tool listed, and gives a limit error, so a ceiling of 0 would be a second off switch that reaches no running session. The environment level of DA-1 is a live availability level instead (0166 decision 50). Revisions 1 to 14 rejected any environment level for want of a use case, which the owner named on 2026-11-23.
- **An environment-scoped guardrail in the security record.** The security record holds tenant-wide constraints, and the environment level is everyday policy with no delay (0166 decision 51).
