# Decisions: 0176 Erasure waits for the terminal pipeline

## Open decisions

- **O2. A billing append after the budget reaches the failover tiers.** Raised by the review of 0176.S1, 2026-11-25. A terminal pipeline that runs past its budget, such as a seal that runs to its maximum followed by a slow release, still calls `billing.Append` for the `session.completed` event on its expired context (`afterTerminalRelease`, `pkg/gateway/core/session/sessionserver/usage.go`). The primary insert fails on the expired context, the Redis stream publish fails on the same context, and `failover.Pipeline.Append` (`pkg/billing/billingstore/failover/failover.go`) then stages the event in the replica's in-memory buffer, which takes no context. A flusher inserts it into `billing_events` with the raw `user_id` later. The erasure gate's budget arm has already released the job by then, and `PurgeStagedByUser` purges only the erasure replica's buffer (F-12.8.53). The branch qualifies the §7.1 statement and the `TerminalPipelinePending` comment to name this exception; it does not change the behavior. Change.md "Scope" excludes failover-tier events, but this case needs no primary outage: every budget overrun produces it.

  Option (a) Skip the `session.completed` append when the pipeline's context has ended, and count the drop on a metric. §11.2.1 states that a billing event is never dropped, so this needs a §11.2.1 exception.

  Option (b) Have `failover.Pipeline.Append` return the caller's context error without staging when the caller's context has ended, so only a primary failure on a live context reaches the failover tiers. Every caller of `Append` on an ended context then loses the event, which also needs a §11.2.1 exception.

  Option (c) Keep the behavior, as the qualified §7.1 text states, and leave the exposure to F-12.8.53.

  Option (e), proposed by the owner in chat on 2026-11-26 in reply to EW-2b, with the words "if it doesn't carry much information and it's not used, could we not store the user id with it at all? Just the session id". The `session.completed` event carries no user: `user_id` is written empty, which the column allows (`NOT NULL DEFAULT ''`), and the event keeps the tenant, the session id, the environment, the experiment and variant, and the labels. A consumer that needs the user joins on `session_id` with the session's `session.created` event, whose `user_id` the erasure pseudonymizes. A late append then carries nothing the erasure rewrites, because the pseudonymize path updates `billing_events.user_id` alone (`UPDATE billing_events SET user_id = $3 WHERE tenant_id = $1 AND user_id = $2` in `pkg/billing/billingstore/pgstore/pgstore.go`), so the event is neither dropped nor left with a raw identifier, and §11.2.1 needs no exception to "never dropped". §11.2.1's `user_id` row states that `session.completed` leaves it empty, and the billing documentation states the join. A consumer that filters the billing stream by user no longer receives `session.completed` without the join. The review of EW-2 found that no Lenny code, alert, budget, or invoice total reads the event.

  Recommendation, revised on 2026-11-26: (e). It closes the leak for every overrun, keeps the end marker in the billing stream during incidents, and needs no exception to §11.2.1. The earlier recommendation follows.

  Recommendation: (a), scoped to the terminal pipeline, because it closes the case where the erasure has already moved on, and the event it drops belongs to a session whose terminal accounting has already run past its budget. A follow-up change carries the §11.2.1 exception.

## Decisions

1. **The erasure job waits for the whole terminal pipeline (ER-1).** The gateway marks the session row when the last step of the session's terminal pipeline finishes, after `afterTerminalRelease` in `recordSessionCompleted`, and every terminal session, with or without a pod, is pending until the mark is set or the terminal pipeline budget has elapsed. User erasure (`store_deleting`) and tenant deletion, which uses the same predicate, both wait on it. Owner's answer to ER-1 on the M3 readiness decision page, 2026-11-25, option (a). The options not chosen were (b), moving the billing, quota-checkpoint, and session-log steps before the pod release and extending the wait to sessions without a pod, and (c), option (a) together with re-pseudonymizing when the verification finds a row and refusing billing writes for a user whose processing is restricted.
2. **The erasure wait also keeps the post-terminal window (O1).** User erasure and tenant deletion wait while a drained session is pipeline-pending or in its post-terminal window, so the lost `CH-BINDRELEASE` case keeps the guarantee that `TestLostBindReleaseFanOutHoldsErasureUntilReleaseOrWindowCap_spec_28_5_7` pins; both arms end within one terminal pipeline budget. 0176.S1 built it. The option not chosen was (b), the pipeline mark alone. Owner's answer to EW-1 on the M3 readiness decision page, 2026-11-26, option (a).
3. **A margin on the budget arm (O3).** An operator-tunable margin, default 30 seconds, is added to the budget that the erasure gate and the tenant-deletion terminator read, and to nothing else, to cover clock skew between replicas and a commit that lands just after the deadline. A budget raised during a rollout stays the operator's responsibility, which the configuration page states. 0176.S2 builds it. The options not chosen were (b), a per-row pipeline deadline plus a margin, and (c), no margin with the clock assumption stated in §7.1. Owner's answer to EW-3 on the M3 readiness decision page, 2026-11-26, option (a).
4. **Writers that run the post-terminal hook alone (O4).** §7.1 "Terminal pipeline context:" names which terminal writers run the session-log close, the final quota checkpoint, and the `session.completed` billing event, and which run the terminal write and the pipeline mark alone; whether every writer should run the full pipeline is issue SEND-I1. 0176.S2 edits §7.1. The option not chosen was (b), routing every writer through the full pipeline in this change. Owner's answer to EW-4 on the M3 readiness decision page, 2026-11-26, option (a).
5. **Coverage waiver for 0176.S1.** The floor of 80% is waived for the 20 changed lines of `pkg/session/sessionstore/pgstore/pgstore.go`, which the unit tier cannot reach without Postgres and which the step's component, integration, and security tests exercise, and for the 3 changed lines of `cmd/lenny-gateway/sessionsrv.go` that pass two flag values through `terminalPipelineFlags`. The measured coverage was 70.9% (56 of 79 lines) on gate runs `cc7d4399f9e28c53f221834b` and `d0b76fb7f7a807c81cf6267a`. Issue GATE-I14 records that the coverage check measures the unit tier alone. Owner's answer to EW-W on the M3 readiness decision page, 2026-11-26, option (a).
