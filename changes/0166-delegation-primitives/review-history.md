# Review history: 0166 Delegation as session primitives

- 2026-11-22, revision 1. Created at the owner's request, after the owner asked whether Lenny should provide delegation or the mechanisms with which a deployer builds it outside Lenny or as an extension. The revision frames the problem with evidence from §8, the delegation packages, and the v1 member changes, proposes the primitives and the reference extension, maps each setting, and lists O1 to O9 for the owner. No review has run.
- 2026-11-22, revision 2. Owner request: examples of orchestration and how an operator or author sets each one up. Added "Worked examples" with five examples (the reference tool set, a programmatic fan-out, an operator's own tool set with roles, cycle avoidance, retry, and tracing, untrusted code in a stronger sandbox with an incident switch, and a workflow engine outside the pods). To give the examples concrete names, DP-1 now lists the platform operations under O3 option (a) and marks them internal, and DP-5 states the extension's library and tool set and the bridge's `--child-tools` option.
- 2026-11-22, revision 3. Owner decision and review. The owner chose O1 option (a) ("i like this design (option a)"), recorded as decision 1, and asked that tenant administrators be able to configure delegation policies. Three reviewers looked for valid user scenarios the design could not handle, one each for runtime authors and orchestration patterns, for operators, tenants, and governance, and for lifecycle, failure, and scale. Their findings were checked against the change and the related changes before this revision acted on them.
  - Regressions from built-in delegation, fixed: a child's question had no hop to its parent once the virtual child interface left (the `question` event, `child.answer`, and `child.forward`, held across recovery); `runtimeOptions`, which 0140 adds to the delegation `TaskSpec`, was missing from `child.create`; `child.list` could not list descendants for MD-23's depth option; SO-5a's rules and the delegation guardrail named `start_child_session`, which no longer reaches the gateway (DP-7 retargets them to `child.create`); §8.6 lease extension had no disposition and DPR-2 forbade it (the caveats split into security and resource caveats); `onParentEnd` was a free argument of `child.create` (it is a security caveat, and a force-terminate and the new tree terminate close a tree at once); the grant's creation and each child's creation had no audit content (DPR-11).
  - Tenant administration, added: the root grant inputs of DP-1, with a tenant delegation policy and ceilings, an environment's `defaultDelegationPolicy` applied at child creation and `delegationCeilings`, presets kept as operator-defined default leases, and a statement of the §10.2 RBAC under which a `tenant-admin` writes its tenant's policies. Example 5 shows a tenant administrator setting them up.
  - Flexibility, added: idempotency keys, child labels delivered in `session_start` beside a gateway-recorded `lineage` (which also replace trace identifiers in the prompt), `child.set_limits`, the parallelism count by state, `maxEntries` and the return of a cancelled wait's events, a child's inheritance of the parent's session `labels` for cost attribution, narrowing of named bindings and egress hosts on `child.create`, and the bridge's `--child-defaults` and listing of management tools while children exist.
  - Text errors, fixed: Example 2 dropped `idle` children and stalled on parallelism, and lost its state on a restore (rewritten over child labels and idempotency keys); Example 4 claimed the child received no binding although 0127 passes named bindings, and used `disabledBy: "guardrail"` for 0126's `securityGuardrail`; DP-4 moved the wait modes to the extension while DP-1 kept them (they stay in the primitive); DP-5 hid the management tools from a parent with children; `messagingRateLimit` applied to every operation (it counts `child.message` alone).
  - Raised as open decisions: O10 approval by target or budget, O11 handoff, O12 sibling messaging, O13 files to a running child, O14 fork, O15 a non-blocking event read, and O16 a dormant child's age and a derived session's notice. O4 gains the cross-tree budget of a team or project.
