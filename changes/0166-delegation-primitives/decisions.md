# Decisions: 0166 Delegation as session primitives

## Open decisions

- **O33. Who may set `maxDepth: 0`.** TS-3 of 0149 lets only a client supply 0, and keeps every default and ceiling of the platform, the tenant, the environment, and the runtime at 1 or more, so turning delegation off for a whole tenant or environment is left to the availability levels of 0126. The owner questioned the rule on 2026-11-23: "Agent choice 2: ok except I don't get why `maxDepth: 0` can only be set by the client for its session. A tenant, for example, should be able to disable delegation across the board." A tenant already turns delegation off everywhere through 0126's tenant default `allowByDefault: false`, its tenant runtime entries, or 0142's guardrail, each read live; no level turns it off for one environment, where an environment policy that admits no runtime refuses each child as a target that is not allowed. Options: (a) availability stays the only switch and gains an environment level, `allowDelegation: false` on an environment, written by `tenant-admin` and read live, and a ceiling of 0 anywhere is refused with an error that points to the switch; (b) a tenant or environment ceiling of `maxDepth: 0` is accepted and means delegation is unavailable at that level, read live unlike every other ceiling and reported in `disabledBy`. Recommendation: (a). It keeps one off switch with one refusal and one live read, and it adds the missing environment level. Blocks: 0166.S1 (part).




## Decisions

1. **Where delegation lives (O1).** The owner chose option (a) on 2026-11-22: "i like this design (option a)". The core keeps the session grant, the parent link, the carved budget, and child event delivery, and the child-session tools move to the runtime SDKs and the reference MCP bridge. Option (b), built-in delegation with the settings of "DP-6" dropped, and option (c), the program as written, are not taken.
2. **No token form of the grant in v1, with room to add external attachment later (O2).** The owner chose option (a) on 2026-11-23: "I agree we don't need a token for this yet. However, I think we need to think about what this would do to the internal communication protocol and tools. If an exteral actor could attach a child to a session eventually, the parent would need to be notified and that (plus anything adjacent the parent might need) could change the internal tooling and protocol. I'd want to make sure such a change is backward compatible as much as possible." The grant is reached only through the platform tool server, and the `a2a_delegation` child minting of §13.3 retires. DPR-12 and "Later additions" in "DP-4" state the rules that let a later change add a child that the parent did not create, and the event that announces it, without breaking an extension written against this change.
3. **Platform operations (O3).** The owner chose option (a) on 2026-11-23: "(a)". The extension reaches the primitives through the operations "DP-1" lists, restricted to the caller's children, with no tool descriptions.
4. **File export stays in the core (O5).** The owner chose option (a) on 2026-11-23: "(a)". The gateway keeps materializing a parent's exported files in the child's workspace with `scanExportedFiles` and its limits, and `PreDelegation` folds into the `PreRoute` chain for `kind: delegate`.
5. **Cycle detection and policy snapshotting leave (O6).** The owner chose option (a) on 2026-11-23: "(a)". The self-recursion gate, `gateway.cycleDetection.mode`, and `snapshotPolicyAtLease` leave, and the policy cap is read live at each `session.create`.
6. **The availability levels of 0126 become root grant inputs (O8).** The owner chose option (a) on 2026-11-23: "(a)". The forbids are read live at each `session.create`, and the refusal keeps `disabledBy`.
7. **This change joins the v1 program (O9).** The owner chose option (a) on 2026-11-23: "(a)". The affected changes have no started step, so the redesign replaces design text before any of it is built.
8. **Approval by target and budget (O10).** The owner chose option (a) on 2026-11-23: "(a)". A `DelegationPolicy` rule gains `approval` (`none`, `owner`, or `security`) and an optional `approvalAboveCreditBudget`. It adds a part to 0166.S1.
9. **A parent can release a child (O11).** The owner chose option (a) on 2026-11-23: "(a) but I want to think about how the release works from the user's point of view." `session.release(sessionId)` makes the child a root owned by the same principal, which keeps its security caveats, takes its carved budget as its own, and leaves the parent's cascade. O17 holds the question of how the user meets the released session. It adds a part to 0166.S1.
10. **A non-blocking event read named `events.peek` (O15).** The owner chose option (a) on 2026-11-23: "(a). Should this be called "peak"?" The operation is `events.peek(afterSeq)`, after the owner's name for it: it returns the parent's child events since a sequence number without consuming them from the inbox and without counting as activity under SL-6. It adds a part to 0166.S3.
11. **A derived session is told that the children did not carry over (O16 (ii)).** The owner chose option (a) for part (ii) on 2026-11-23: "ok". A session derived under 0144 from a parent with children receives a system message saying so in its first delivery. It adds a part to 0166.S3.
12. **A child's budget is carved from budget objects (O4).** The owner chose option (a) on 2026-11-23: "Go with your recommendation. Draft the change now". The carve of "DP-3" is a reservation from the budget objects that apply to the parent, and the child's share is a budget object of the child's session funded by it. The budgeting change [`0170-budgets`](../0170-budgets/change.md) defines budget objects, credits and infrastructure resources as units, money through an operator's rate card, and resets, and 0166.S2 waits on its step that adds budget objects.
13. **A child's age is a deadline, with the parent's choice of notice (O16 (i)).** The owner chose on 2026-11-23: "keep but holding the notice should be determined by confid or arguments. A parent may want to notified at once if a child expires (that should be the default IMO). Ok to letting session.set_limits extend a child's age." `perChildMaxAge` runs in every non-terminal state, `dormant` included. `session.create` takes `expiryNotice`, `immediate` by default, which delivers an expiry's `ended` event at once and wakes a `dormant` parent, or `on_wake`, which holds it until the parent's next wake; a runtime's or an operator's default lease sets the default for a grant. `session.set_limits` raises a live child's age within the caller's own grant.
14. **No fork in v1 (O14).** The owner decided on 2026-11-23: "don't include this in v1". `session.create` with `from: "self"` over 0144's snapshot restore stays the candidate design for after v1.
15. **No ordering across a tree in recovery, with recovery rules (O7).** The owner chose option (a) with the fixes of the review on 2026-11-23: "Ok on the fixes." "DP-4" states the recovery rules, and "DP-7" names the parts of 0135, 0146, and §9.2 they change. The owner asked not to edit the other changes until 0166's design settles.
16. **Generic tool and operation names (owner's request).** The owner asked on 2026-11-23: "Also, tool names should be generic. Make sure we're not overusing "child."" The operations are `session.*`, `events.*`, `questions.*`, `files.*`, and `runtimes.*`, the reference tools are `start_session`, `send_message`, `await_sessions`, and the others of "DP-5", the bridge options are `--session-tools` and `--session-defaults`, and the SDK module is `sessions`. Words that name the relation stay where the relation is meant, such as "child event" and `perChildMaxAge`.
17. **Progress updates open no turn, and child events have classes (O18).** The owner chose option (a) on 2026-11-23: "ok (this ties into my previous answer about child expirations, which is a type of event). We probably need to differentiate between two types of updates: updates from the session itself and Lenny lifecycle updates (which maybe come through different channels already?)". "DP-4" sorts child events into the classes `update`, `result`, `question`, and `status`, marks a `status` event as written by the gateway with `from.kind: system`, and lets a parent choose with `wake` which classes open a turn in it or wake it. The default set is every class except `update`. `wake` replaces the `expiryNotice` argument of decision 13, whose default and choice it keeps: an expiry is a `status` event.
18. **Files travel by reference in any message, and a parent may push them (O13).** The owner chose option (a) on 2026-11-23: "ok, go with your recommendation". A file part in a message one session sends another names a file in the sender's workspace, exported under MD-18, and the recipient imports it on demand with `files.import`, under MD-26 extended to every direction and its limits and scanning. A parent may set `materialize: true` on a file part of `session.send` to place the file in its child's workspace through WM-12, gated on the child runtime's `midSessionUpload`. No `session.upload` operation is added.
19. **A message that starts no turn, for every sender (O19).** The owner chose option (a) on 2026-11-23: "ok but the client surface should match. Is 'note' the best name? I like it, but I wonder if there's something else that conveys the fact that the session isn't woken up". A REST client, a parent through `session.send`, and a peer can send a message that waits for the recipient's next turn instead of starting one, and is steered into an open turn on a runtime that declares `steer`. It amends MD-1 of 0135, which waits until the owner turns to the other changes. O21 settles the name.
20. **Peer messaging over directed edges (O12).** The owner chose option (a) on 2026-11-23: "ok". "DP-8" ("Between connected peers") and the operations `session.connect` and `session.disconnect` of "DP-1" state it. Each peer message counts against its sender's `messagingRateLimit` and the edge's cap, a peer has no control operation, `peerMessaging` lets a tenant forbid edges, and a group chat is the parent acting as its manager, as the owner agreed earlier that day.
21. **A released child is announced, and a root can hand off (O17).** The owner chose option (b) on 2026-11-23: "go with your recommendation". The root's event stream and webhooks receive `child_released`, and a root that releases a child with `handoff: true` ends with `successorSessionId`, which clients and adapters follow. A swap of session IDs is rejected.
22. **The message that starts no turn is `wake: false` (O21).** The owner chose option (a) on 2026-11-23: "i like `wake: false` as a flag". It is a member on any message beside its intent, refused with `interrupt`.
23. **One blocking interface for tools a client offers, parents included (O20).** The owner chose option (a) on 2026-11-23: "(a), as long as this doesn't break support for "a runtime that runs its own model loop, and the provider APIs (Chat Completions, Responses, Anthropic Messages), whose protocol works exactly that way"". "Tools a client offers" in "DP-8" states the interface, and DPR-13 the owner's condition. A runtime that runs its own model loop receives the definitions on the message as before, calls a tool with a blocking `tool_call`, and receives a late result as `toolResults` on its next message. A provider adapter returns a group of parallel calls in one provider response and posts the results from the caller's next request, and a cold continuation delivers them through 0122 CT-7's history rules. Parent tools are off by default behind the switch that section lists. The amendments to 0122 wait until the owner turns to the other changes.
24. **A blocking tool call is held for a bounded time (review R6).** The owner agreed on 2026-11-23: "ok". A call to a client tool stays open for up to `clientToolHoldSeconds`, 300 by default with a tenant ceiling, and is then withdrawn with `tool_call_withdrawn`, so the session can go `dormant`. A result that arrives later reaches the runtime as `toolResults` on its next message under DPR-13.
25. **The `wake` set is `wakeOn`, and names events as well as classes (review R8).** The owner agreed on 2026-11-23: "ok". `session.create` takes `wakeOn`, a list of event classes or event kinds, so a parent can sleep through expiries alone. `wake: false` on a message keeps its name (decision 22).
26. **The tenant delegation route depends on 0126's O10 (review R9).** The owner agreed on 2026-11-23: "ok". "DP-1" states the dependency, and the route settles when the owner turns to 0126.
27. **Edges stay within one environment (review R4).** The owner agreed on 2026-11-23: "ok. Is the environment the only boundary we should worry about?" If edges remain under O25, `session.connect` refuses an edge between children in different environments, and ends existing edges when `crossEnvironmentSharing` is forbidden. O26 holds the other boundaries.
28. **A parent tool's call is a child-written event with a digest in the audit (review R5).** The owner agreed with the general direction on 2026-11-23: "ok in general". A `tool_call` event carries `from.kind: agent` and passes the parent's `contentPolicy` and `PreMessageDelivery`, and `delegation.tool_called` records a digest of the arguments. O26 holds the remaining two points.
29. **T16 and CT-9 of 0122 stay (O23).** The owner chose option (a) on 2026-11-23: "client tools aren't automatically passed down to children, right? As long as that's the case I'm ok with the recommendation". A child never receives its parent's client tools (0122 T7 and CT-9), a parent's own tools are the only tools it offers a child, and a call to a client tool in a turn that another session opened is refused with `no_tools_declared` unless the client marks the tool `allowInOtherTurns: true`. A parent's code therefore cannot relay a child's request to the user's client tools in a turn the child's event opened.
30. **The parent brokers every message between its children (O25).** The owner chose option (a) on 2026-11-23: "ok". `session.connect`, `session.disconnect`, peer edges, and the `peerMessaging` caveat leave, MD-9 of 0135 stays as written, and the SDK library gains a relay that forwards a child's events to another child by rules the parent's code sets. This replaces decision 20, and decision 27 lapses with the edges. Edges remain a possible later addition under DPR-12.
31. **A fenced child stays fenced, and approval rules can name parent tools (O26).** The owner chose option (a) on 2026-11-23: "ok". A child created with fewer credential bindings, fewer egress hosts, or a stronger isolation profile than its parent gets no parent tools unless its `session.create` sets `offerTools: allow` within the grant, and 0142's SO-5a rules can match parent tools by name, or all of them with `approvals.parentTools: all`.
32. **Two ways to leave a parent (O22).** The owner chose on 2026-11-23: "I think we should support both modes" and then "ok" to the proposal. `session.reattach` keeps the session in its tree, counted in `maxTreeSize`, inside the root's cascade and `terminate-tree`, with the root's client as its client. `session.release` makes it a root of the same principal outside the tree, with its security caveats, resource caveats from the root grant inputs, its unused carve as its session budget, and the tenant's session quotas, and it alone takes `handoff: true`. The security caveats `leave` (`none`, `reattach`, or `release`) and `leaveMaxDepth` govern both, resolved from the root grant inputs with platform defaults `reattach` and 1 and narrowed by `session.create`. Neither works while the session has no grant or the guardrail forbids delegation. O27 holds what a leave carries.
33. **What a leave carries (O27).** The owner chose on 2026-11-23: "O27.i: drop" and "O27.ii: ok". The rules O27 proposed hold: the parent receives a `left` event as its last event from the session; pending questions to the parent move to the root's client; open calls to the parent's tools return `CLIENT_CHANGED`; the parent's pending messages are dropped with a `dropped` notice to the parent; the user's client tools arrive only on the user's own messages; the session leaves the parent's relays and group chats, and the parent's watch ends; file parts sent before the leave stay importable by the parent; the session keeps its labels, its lineage with `leftFrom`, and its children; its carve moves to the root under `session.reattach` and becomes its session budget under `session.release`; `wakeOn` and `questions: forward` lapse; and the root's stream receives `child_reattached` or `child_released`. The root's client can also reattach or release a descendant through a REST route, under the same `leave` caveats.
34. **One view of a child, and what crosses an environment (O24).** The owner chose option (b) on 2026-11-23: "ok, go with your recommendation". `session.messages` returns the stored history of the events a watch under MD-25 carries, under the watch's checks, and for a child in another environment both the read and the watch carry only what TS-3's "Model" lists, leaving out activity and tool calls with their results. The change to MD-25 waits until the owner turns to 0135. No filter keeps a compromised child from encoding what it read in a message; the sharing decision of TS-3 bounds what a child can read.
35. **Concerns return to the changes that own them (overlap item 1).** The owner agreed on 2026-11-23: "ok". 0166 keeps the grant and its caveats, the root grant inputs and the resolution of every caveat, the parent link, the tree terminate, the leave modes, the platform operations, `wakeOn` and `events.peek`, what is specific to parent tools, and the reference extension with the SDK library. The blocking client-tool interface goes to 0122, child events with their classes, `from`, the wait, and questions as events to 0135 MD-22, the recovery rules to 0146 SL-12, the message that starts no turn to 0135 MD-1 and MD-14, hand-off and successors to 0146 with routes, events, webhooks, and error codes in 0138, the carve's mechanics to 0170, where delegation checks run to 0141, crossing between environments to 0149 TS-3, approval holds and each guardrail's refused operations to 0142, the client-tool audit to 0122 CT-8, and the watch's crossing filter to 0135 MD-25. 0166 cites each owner and states its delta, and "DP-7" lists what each change takes on when the owner turns to it.
36. **Approval of a child lives in 0142 alone (overlap item 2).** The owner agreed on 2026-11-23: "ok". SO-5a gains a condition on the target runtime and one above a credit amount, held at `session.create` and at a `session.set_limits` raise. The `approval` and `approvalAboveCreditBudget` fields of a `DelegationPolicy` rule leave. This replaces decision 8.
37. **Security-tier delegation switches are security record fields (overlap item 3).** The owner agreed on 2026-11-23: "ok". The tenant floor of `leave` and `leaveMaxDepth`, `offerTools`, and the forbid of parent tools are fields of 0142's security record under its single writer and weakening rule. Numeric resource ceilings stay with `tenant-admin`.
38. **The message that starts no turn is 0135's `append` intent (overlap item 4).** The owner agreed on 2026-11-23: "ok". MD-14 already names `append`, which delivers a message without starting a turn, and its extension rule makes a timing behaviour an intent. `wake: false` leaves, and this replaces decision 22's form while keeping decision 19's behaviour.
39. **0126 keeps availability (overlap item 5).** The owner agreed on 2026-11-23: "ok". 0126 keeps its levels, their order, its checks, and the `availability` notice, cut down to deciding whether a session holds a grant, and 0166 cites it. 0126 is not cancelled.
40. **0166 owns the resolution of every caveat (overlap item 6).** The owner agreed on 2026-11-23: "ok". A runtime contributes a default and, separately, a ceiling, and TS-3 cites 0166's resolution.
41. **TS-3 owns crossing for every operation (overlap item 8).** The owner agreed on 2026-11-23: "ok". A release of a crossed child meets the target environment's admission check, parent tools are refused across environments, and DPR-3's subset rule applies within one environment.
42. **No argument digest in the audit (overlap item 11).** The owner agreed on 2026-11-23: "ok". A parent tool's call reuses 0122 CT-8's audit fields, which omit arguments so erasure under §12.8 removes them. This replaces the digest of decision 28.
43. **0170 joins the v1 program (overlap item 13).** The owner agreed on 2026-11-23: "ok". The edit to the program lands with 0170.
44. **Two maps: `labels` and `tags` (O28).** The owner chose option (b) on 2026-11-23: "ok". `labels` are set by the root's client and inherited unchanged by every descendant, and no parent writes them. `tags`, which replace child labels, are the parent's bookkeeping, which the child receives and which billing, budgets, and routing never read. Routing labels stay under RT-3.
45. **Every session carries a content caveat (O29).** The owner chose option (a) on 2026-11-23: "ok". `contentPolicy` and the export and import limits are resolved for every session from the platform, the tenant, the environment, and the runtime, the strictest value winning, narrowed for a child and never widened, and every transfer applies the sender's caveat on export and the receiver's on import. 0142's cooldown after a weakened scan covers every transfer path.
46. **The mode that stays in the tree is `session.transfer` (O32).** The owner chose on 2026-11-23: "use 'transferred'". The operation is `session.transfer`, the event `child_transferred`, and the reference tool `transfer_session`. This replaces the name `session.reattach` of decision 32.
47. **`children_reattached` becomes a system message to the runtime (O31).** The owner chose option (a) on 2026-11-23: "ok". After the recovery rules' resends, the restored parent's runtime receives a system message listing each child's state, tags, and pending question by id. A client reads the tree through `GET /v1/sessions/{id}/tree` after `session.resumed`, and the SSE event leaves §7.2.
48. **T16 becomes a client's choice with provenance (O30).** The owner chose option (b) on 2026-11-23: "ok, go with (b)". A client declares for the session whether its tools are callable only in turns its own messages started, the default, or in every turn, a provider adapter always declares the first, and every `tool_call` event carries what started the turn and which sessions' content entered it, so the client runs, confirms, or refuses the call by its own policy. 0122 owns the rule. `allowInOtherTurns` leaves.
49. **How every numeric caveat resolves, with the gaps filled (resolution review).** The owner accepted on 2026-11-23: "Agent choice 2: ok except I don't get why `maxDepth: 0` can only be set by the client for its session." Decision 40 stands. A caveat the client leaves unset takes the first default set among the runtime's, the environment's, the tenant's, and the platform's, which 0170 "BG-2" also reads for a session budget. A client may name a delegation preset, whose values become its request and are lowered to every ceiling. Lowering a ceiling applies to new grants, and an existing grant keeps its values, while forbids and policies are read live (decision 5). Decision 26 of 0149 is revised accordingly: its sentences "A client can only narrow, resolution becomes a minimum" and "`maxChildrenTotal: 0` is stored as `maxDepth: 0`" no longer hold, and 0149's decision 44 drops the mapping. Who may set `maxDepth: 0` is open as O33. "DP-1" ("Resolution") states the rule once.
