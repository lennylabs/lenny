## Problem

Feedback on Lenny, which this document calls the feedback proposal, asked for user-scoped repository access and pull request authoring, similar to what Coder offers. These gaps stand behind it.

- **Authorization.** At session bind, [the egress design](../0127-egress-and-git/change.md) checks a repository against the tenant's allowlist and the VCS pool's `allowWrite` ([`0127-egress-and-git`, "Credentials"](../0127-egress-and-git/change.md#credentials), **Write scope**). It does not ask whether the requesting user can access the repository. Any user in a tenant reaches any allowlisted repository through the App.
- **Authorship.** A pull request created with an App token has the App as its author. GitHub then sees no relationship between the requesting user and the pull request, so that user can approve the agent's work, which defeats two-person review.

These are separate features with different risk. Authorization keeps the user's token inside the Token Service. Pull request authoring lets an agent act with a token derived from a user's authority. This document therefore separates them, and either one's proposal can be rejected without affecting the other's dependencies, except that UG-3 needs UG-2's link and check.

Pull request authoring is not a special case in the pod any more. It is a `userCredential` binding of [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md), the generic mechanism that gives a session its own user's token, with an `oauth2Link` source, a narrowing template, and a preset, all held as data. "Terms" below defines each of these.

## Scope

This design is the VCS layer of the user credential mechanism in [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md). It covers the rules every VCS link kind follows (UG-1), repository authorization on VCS hosts (UG-2), pull request authoring as a configuration of the generic binding (UG-3), and an approval check for tenants that refuse user tokens (UG-4). [`0129-github-credential-addon`](../0129-github-credential-addon/change.md) implements it for GitHub and GitHub Enterprise Server (GHES), and [`0130-gitlab-credential-addon`](../0130-gitlab-credential-addon/change.md) implements it for GitLab, where user-authored merge requests, formerly UG-5, are [GL-2](../0130-gitlab-credential-addon/change.md#gl-2-user-authored-merge-requests).

Out of scope: tenant-wide session content reads, in which someone other than a session's user reads its content across a tenant, the repository visibility rule, which decides which repositories a user can see, and the defaults of the egress design's exfiltration controls, [EG-12](../0127-egress-and-git/change.md#steps). [`0127-egress-and-git`](../0127-egress-and-git/change.md) owns egress and git, and this document lists what it asked of that design under "Changes requested of 0127-egress-and-git" near the end. [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) owns the `userCredential` binding, the `registered` and `oauth2Link` sources, the link flow and stored links, `file` delivery, request rules, the preset format, and the add-on model. [`0142-security-oversight`](../0142-security-oversight/change.md) owns repository rules and guardrails, [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md) owns user lifecycle and environments, [`0148-tenant-outbound-connector`](../0148-tenant-outbound-connector/change.md) owns private hosts, and [`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md) owns preservation.

Generic, ["Presets"](../0151-user-credential-delivery/change.md#presets). |

| Release and pod release | A release is the Token Service handing a binding's token to `netagent`, or to the mirror, on the pod credential API. ### Terms from other designs and the platform

This design builds on mechanisms other designs and the specification define. The table gives each one the meaning this document relies on.

| Term | Meaning |
| :-- | :-- |
| Gateway replica | One instance of Lenny's API gateway. One replica coordinates each session under a lease. |
| Token Service | The Lenny service that stores user and provider credentials, mints short-lived tokens from them, and answers the pod credential API ([§4.3](../../spec/04_system-components.md#43-token-service)). |
| `netagent` | A container that the egress design adds to every agent pod that uses the local egress endpoint, where it acts as the pod's egress proxy. It holds the pod's service account tokens for egress, terminates TLS for the hosts it must inspect, attaches credentials, runs the git path, and applies request rules. |
| `lenny-egress` | The central egress proxy, built on Envoy, through which agent traffic leaves the cluster. |
| Decision service | `lenny-egress-authz`, which decides whether each connection is allowed, from the session's effective policy, and returns the route to use. |
| Mint checks | The independent checks on every mint and release of a token, which [`0127-egress-and-git`, "Terms"](../0127-egress-and-git/change.md#terms) defines: the Token Service's own check of the pod, its bindings, and its writable set, and the scope decision the Token Service asks of the decision service. ## High-level design

Lenny agents reach git repositories today through a credential the tenant owns, such as a GitHub App, so any user of a tenant can have an agent read any repository the tenant allows, and every pull request an agent opens is authored by the App. A user can therefore reach a repository through Lenny that the provider would not open to her. Because the provider cannot tell who asked for the agent's pull request, that person can also approve her own agent's work, which defeats two-person review.

This design adds repository authorization and pull request authoring for git hosts, and a tenant turns each one on separately. With repository authorization, each user links her own provider account once in a browser, and Lenny asks the provider, before her session starts and every few minutes while it runs, whether she can still reach each repository the session declares. With pull request authoring, Lenny derives a short-lived token from her linked account, limited to the session's repositories, and `netagent`, a proxy in the agent's pod, adds it to the agent's requests, so the provider records her as the author while the agent never sees the token, and default rules refuse approving and merging. Tenants that refuse user tokens in pods can instead run an approval check that fails a pull request approved only by the people whose sessions pushed to it. The main limit is that two-person review on work the agent pushed depends on the repository's own rule about the most recent push. This document is the VCS layer of the generic [user credential mechanism](../0151-user-credential-delivery/change.md), and separate add-ons implement it for GitHub and GitLab.

The rest of this section states each part in the design's terms, which "Terms" above defines.

The design is split into the proposals UG-1 to UG-4 here and the add-ons' GH-n and GL-n proposals. It rests on [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md), which owns links, the link flow, the binding, request rules, and the add-on model. This layer is an add-on to that design, and the GitHub and GitLab add-ons build on this layer. UG-2 and UG-3 build on UG-1's link kinds, UG-3 also needs UG-2's check, and UG-4 needs a link alone.

**VCS link kinds (UG-1).** A VCS kind is a link provider kind that a VCS add-on registers. Its block names a host that a VCS pool covers, it fixes the endpoints, the API hosts, and `attach`, and it must name a shipped narrowing template when its delivery ceiling is `inject` or `file`. A provider account belongs to one Lenny user across every link provider of a VCS kind on that host.

**Repository authorization (UG-2).** A VCS pool that sets `userAuthorization: required` names a link provider in `userAuthorization.linkProvider`. For each repository a session declares under that pool, the Token Service asks the provider, with the user's parent token, whether the user holds the declared access level. The check runs at session bind, at resume, and before every token mint, and a gateway job repeats it for running sessions every 300 seconds. A `refused` or `unavailable` verdict refuses the session or the mint, and no path falls back to an App token. A refusal during a session marks the repository's entry `userRefused` and pushes a binding change that flushes `netagent`'s cached tokens, so an honest pod loses access within 6 minutes: the 300-second interval, jitter, and the time to flush, which "Revocation" totals. Under such a pool, a session's readable set holds only the repositories it declared. Pod models that could carry one user's state into another session are refused, and service identities listed on the pool give automated sessions a path with no user.

**Pull request authoring (UG-3).** Under pull request authoring, the agent's pull requests are made with a token derived from the requesting user's own link, so the provider records that user as their author. A VCS pool that sets `prAuthoring: user` attaches a `userCredential` binding, through the attach extension point, to each human session that declares a writable repository under it. The binding uses the `oauth2Link` source with `delivery: inject`, and it replaces the tenant's App binding on the API host for that session. The kind's shipped template derives a per-session token limited to the session's writable repositories whose entry `state` is `granted`, and the kind's default preset refuses the operations that approve or merge. The pool's `pushIdentity` decides whose token carries git pushes. This layer's host policy decides which other tokens may sit on a covered host: a stored secret is refused, and a binding with `delivery: file` is admitted only where every VCS pool covering the host sets `allowRuntimeHeldCredentials`.

**Independent approval check (UG-4).** An optional status check from the tenant's App fails a pull request when every approver is its opener or a user whose session pushed to it. It serves tenants that refuse user tokens in pods, and it is required on a VCS pool that sets `prAuthoring: user` with `pushIdentity: app`.

**Add-ons.** The GitHub add-on supplies the `github` and `github-enterprise` kinds, the repository check against the GitHub API, the `github-scoped` template with its per-session child tokens, pushes as the user, and the `github-deny` preset. The GitLab add-on supplies the `gitlab` kind, its repository check, the `gitlab-deny` preset, and user-authored merge requests from per-session fine-grained tokens once spike [S13](../0130-gitlab-credential-addon/change.md#validation-owed) confirms them.

```
 Browser ──(link flow)──────> Gateway ──(code exchange, checks)──> Token Service ──> provider OAuth and API
 Client ──(create session)──> Gateway                                    ▲          (through lenny-egress)
                                                                         │ pod credential API: derived token, request rules
 Pod: gh, glab, git ──(placeholder token)──> netagent ───────────────────┘
                                                │ token attached, request rules applied
                                                └──> lenny-egress ──> provider API and git
```

Two limits frame the result. Two-person review on pushed work holds where the repository requires approval of the most recent push, and UG-4 extends it to every pusher where a tenant runs it. A compromised `netagent` holds the session's child tokens and can approve and merge with them, as "Residual risks" states.

## Personas and requirements

Alice is a developer at `acme` and Bob is her reviewer. Carol is `acme`'s tenant admin and Dave is its `security-admin`. Tenant `globex` runs on GitHub with its own App. Tenant `initech` runs self-managed GitLab, and Erin is a developer there.

- UR-1. Alice links her account once per link provider, and she sees the prompt before her session starts rather than a failure in the middle of it. This applies to repositories under a VCS pool with `userAuthorization: required`, which every VCS pool with `prAuthoring: user` also sets.
- UR-2. A session reaches a repository under a VCS pool with `userAuthorization: required` only when the requesting user can reach it at the access level the session declared.
- UR-3. When Alice loses access, her session stops reading and writing that repository within a stated bound.
- UR-4. Alice's pull request has Alice as its author, and Alice cannot supply the approval it needs. On GitHub, when the repository requires approval of the most recent push, her approval does not count while a push her agent made is the most recent one, because her agent pushes as her ([S3](../0129-github-credential-addon/change.md#validation-owed)). GitHub's rule reads the latest push alone, so once someone else pushes after her, her approval counts again for a pull request that holds her agent's commits, as it would after a push she made by hand. Without that repository rule, GitHub lets a pusher approve. UG-4 counts every pusher and closes both gaps where a tenant runs it ("Residual risks").
- UR-5. An agent running any `gh` or `glab` command works with the tool unmodified and with a placeholder as its token, **within the token's permissions**, except what the preset refuses, which a tenant can change. The host refuses what the token does not permit: under the child token's default permissions, `pull_requests: write` and `contents: read`, that includes `gh issue create` and `gh run`, and likely `gh issue view` and `gh pr checks` ([S15](../0129-github-credential-addon/change.md#validation-owed)). The narrowing template's `permissions` is data a tenant can widen. **This is met on a stub under git path T, and live hosts are owed:** `gh` and `glab` worked on every command listed under "Git remotes and client tools" **[measured]**. `gh` needs git in the image even with `-R`, and `gh release upload` needs a binding on `uploads.github.com`. A new `gh` release needs no change here, because a new operation passes by default.
- UR-6. With the preset on, no agent can approve or merge through an operation the preset names, with a credential Lenny attaches under a binding with `delivery: inject`. **This is a deny list, and the owner accepted that a new operation with that power passes until the preset is updated.** A tenant can clear the preset unless a `security-admin` requires it. It does not hold for a token the runtime holds under a binding with `delivery: file`, or against text a repository's own automation reads as a command, which "Comment-triggered actions" treats.
- UR-7. Automated sessions keep working under a named service identity, and a person cannot use that path to skip the check.
- UR-8. A tenant can refuse user tokens in pods and still get a two-person review check.

## Threat model

### Security properties

- UP-1. A refresh token never leaves the Token Service, and it goes only where its token trust record says. On a link provider of a VCS kind, a parent access token never leaves either, because such a link provider whose `delivery` ceiling is `inject` or `file` must name a platform-shipped narrowing template. On a link provider with `kind: oauth2` and no template, `netagent` receives the parent access token under the record's `delivery` ceiling, as [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) states, and a replica can obtain it under `leakScan` on a binding with `delivery: file`. The mirror never holds a parent token. The Token Service API and the `user_links` store hold this.
- UP-2. Under a platform-shipped narrowing template, a child token is limited at the host to the session's writable repositories whose entry `state` is `granted` and to the template's `permissions`, by default `pull_requests: write` and `contents: read`. The git child, which exists on a VCS pool with `pushIdentity: user`, is limited to `contents: write` alone. The host enforces this, which [S15](../0129-github-credential-addon/change.md#validation-owed) measured live for the repository limit and the merge refusal. The write path requires a shipped template on every link provider of a VCS kind whose `delivery` ceiling is `inject` or `file`.
- UP-3. Under a binding with `delivery: inject`, `netagent` attaches a user-derived token only to the binding's hosts and only to a request the binding's request rules admit, with `requestRules.default: allow` and the preset as this configuration's default. A credential whose required handling `netagent` does not implement is refused. `netagent` holds this, and the Token Service sets the rules and the requirement. Under `delivery: file` none of this applies.
- UP-4. A session with a requesting user never receives an App token for a repository under a VCS pool with `userAuthorization: required` unless a fresh verdict, one no older than the 60-second verdict cache (`verdictCacheSeconds`), says the user holds that access. The Token Service holds this before its cache lookup, and `lenny-egress-authz` holds it independently from the recorded entry state.
- UP-5. A user-derived token never reaches a pod that can serve a later session or that has served one, and reaches a pod that serves several sessions at once only when its pool's attribution status records per-slot attribution (decision 52). The binding validator, the session gateway check, and the Token Service each hold this.
- UP-6. A session with no link, or a failed or unavailable check, never falls through to an App token on such a pool.
- UP-7. An impersonation bearer cannot cause a linked token to be used. The gateway's session input check holds this, over the session's delegation tree, under [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md).
- UP-8. One tenant's link, check result, or token never reaches another tenant. Link rows sit under row-level security, and every cache key carries the tenant.
- UP-9. A link's provider account is one the tenant's identity source ties to the Lenny user, unless the tenant records that it does not. The link flow and the sweep hold this.
- UP-10. No token held under this design's links leaves the Token Service except through the pod credential API, under the binding's `delivery` and the link provider's `delivery` ceiling, or to a session's coordinating gateway replica under `leakScan`, and a compromised replica can acquire any such session's lease, as [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) states. No gateway path receives one, because Lenny calls no external service for a session once §9.3 connectors are removed ([`0124-connector-removal`, "CR-1 Removal"](../0124-connector-removal/change.md#cr-1-removal)).

## UG-1: VCS link kinds

[UC-2](../0151-user-credential-delivery/change.md#uc-2-the-oauth2link-source-and-account-linking) of [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) owns the link flow, the stored links, identity binding, refresh, and revocation at the provider, for every kind. This proposal states what every VCS kind adds, and the GitHub and GitLab add-ons implement it.

- **Host.** A VCS kind's block names `host`, the canonical host, which one of the tenant's VCS pools covers. Several link providers of a VCS kind can share a host, such as one whose App has `metadata: read` for the check and one whose App authors pull requests.
- **Fixed endpoints.** The kind fixes the endpoint paths from the host, so a tenant supplies no OAuth URL, and it fixes `apiHosts` and `attach` from the host's flavour under "Request rules on VCS hosts".
- **Templates.** A VCS kind takes shipped templates alone, with the tenant override limited to the fields each template names, and a link provider of a VCS kind whose delivery ceiling is `inject` or `file` must name one.
- **One account per host.** Across the link providers of a VCS kind on one host, a `provider_user_id` belongs to one Lenny user. A link that names an account another user holds through any such link provider on that host is refused, so [`0151-user-credential-delivery` decision 31](../0151-user-credential-delivery/change.md#decisions) holds whichever link provider's App was used, and one person can link the same account through several link providers. That decision refuses two Lenny users on one provider account within a tenant. Removing or revoking a person's link on a host covers each of their links there.
- **Ceilings.** The link provider that a VCS pool with `userAuthorization: required` names for its check needs a delivery ceiling of `none` or above. The link provider behind the binding that a VCS pool with `prAuthoring: user` attaches needs `inject` or above.
- **`oauth2` on VCS hosts.** A link provider with `kind: oauth2` whose endpoint sits on a host a VCS pool covers, or on a VCS kind's API host, is refused, so that kind cannot stand in for a VCS kind, and a VCS pool added later suspends such a provider. This is part of this layer's host policy.
- **Identity.** A VCS kind supports every `identityBinding` value, and a link provider write must set one. **Connectors** under "User tokens on a VCS host" records how decision 3 treated §9.3 connectors on these hosts before [`0124-connector-removal`](../0124-connector-removal/change.md) removed them.

### User tokens on a VCS host

Revision 3 said a host has one store of user tokens per tenant and refused VCS providers on `/v1/credentials`, the §4.9 route on which a user registers her own credential for the LLM reverse proxy. The owner's generic mechanism must not be tied to or excluded from GitHub, so this is reworked.

## UG-2: Repository authorization

### The requirement sits on the VCS pool

`userAuthorization` on a VCS credential pool takes `off` (the default) or `required`. "Pool" in the feedback proposal is ambiguous, and the VCS pool is the correct object: it is a tenant object, it names the repository prefixes, [TS-1](../0149-tenant-scoping-identity/change.md#ts-1-environment-scoping) environment scoping can scope it, and a shared warm pool is platform-global. A tenant's `security-admin` can force the value through a new `userAuthorization.require` guardrail in the tenant security record of [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture), which sets `suspendedBy` on non-compliant pools.

This work belongs in the Token Service and the pod credential API. `usercreds` is the §4.9 LLM reverse proxy path, and the feedback proposal's change there would alter nothing the design's git path reads, so `pkg/gateway/credentials/usercreds/usercreds.go` is left as written.

### Declared repositories

Under [the egress design](../0127-egress-and-git/change.md), a session's readable set includes the tenant's whole allowlist, so an agent can fetch an undeclared allowlisted repository at run time. For repositories under a VCS pool with `userAuthorization: required`, the readable set holds only what the session declared: its `gitClone` sources, a new `readableRepositories` plan field, its `writableRepositories`, and each tenant entry on its pool's warm list whose store it holds after passing that entry's check, as ["Mirror, warm fills, and the 6-hour promise"](#mirror-warm-fills-and-the-6-hour-promise) states. A default clone, on an operator's runtime or a tenant-derived runtime, is a `gitClone` source once composed, so it is declared, and the check runs on the session's user. There a runtime's writer named the repository, so a refusal omits its name ([DR-9](../0147-tenant-derived-runtimes/change.md#dr-9-default-git-clones) of [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md)). `netagent` refuses others with 403 and the decision identifier. Decision 22 records the cost and the on-demand alternative.

Public repositories under no VCS pool with `userAuthorization: required` are unaffected, because nothing is authorized about them.

### The check

The Token Service makes one call with the parent token per repository and level. It compares the provider's numeric identifier with the one the VCS pool stores, because GitHub serves a renamed repository under its old name and the egress design keys on the identifier.

Each VCS add-on states the read and write calls of its kind, and which fields report inherited and shared access.

Classification, which every caller uses:

- `allowed`: the provider answered and the level holds.
- `refused`: 404, 403 without a rate-limit header or a header the kind classifies, or a level below the declared one.
- `unavailable`: 5xx, 429, a 403 with a rate-limit header, a timeout, a CONNECT failure, an outbound connector being offline, or a refresh lease not obtained, which is the 30-second row lease one gateway replica holds while it refreshes a link's parent token.
- A 401 attempts refresh once and then counts as `refused` with the reason `user_act_required`.
- A kind can classify a provider's own header, as the GitHub kind does for single sign-on with the reason `sso_required`.

A provider `refused` is `USER_REPOSITORY_ACCESS_DENIED`, naming the repository Alice declared. It reveals nothing she did not name.

When the plan binds at create, the check runs at the post-chain point of [RT-2](../0141-runtime-routing/change.md#post-chain-point), on the final runtime and pool and before the pod claim, because a `PreRoute` interceptor or a runtime route can change the runtime, and with it the default clones a plan declares. The cache key keeps its form, because under this rule a cached App token is reused only by a session that has already passed. The check's result has its own cache, keyed on tenant, `link_ref`, repository identifier, and level, for 60 seconds, which is the "short-lived cache" the feedback proposal asked for.

### Revocation

Mid-session revocation needs a writer and a route. The route exists: `netagent` flushes on every binding change on the pod binding API, and a binding push makes each decision service replica re-read the session row. This design adds the writer and closes the paths that skip it.

**Entry state.** Writable entries are already records with a `state`. Readable entries become records too (see "Changes requested of 0127-egress-and-git" near the end). A new state, `userRefused`, on a writable entry denies both writes and reads of that repository, in both mint checks and in `netagent`, and an unknown state on a readable entry denies access, as the hook row in [`0127-egress-and-git`, "Reserved for other designs"](../0127-egress-and-git/change.md#reserved-for-other-designs) states. Each entry records `verifiedAt`, the time of its last `allowed`. A value per session would let one repository's success mask another's `unavailable`.

**Sweep.** §4.3 has the gateway calling the Token Service, and the Token Service has no route to gateway replicas, so a gateway background job does this, as orphan cleanup does. Every `recheckIntervalSeconds` (300 by default, with up to 10% jitter) it calls the Token Service for each distinct link and repository among bound sessions, bypassing the verdict cache. A `refused` writes `userRefused` on the matching entries in the row's transaction and pushes a binding change. `allowed` updates that entry's `verifiedAt`, and every update for a session is one write to its row. Deduplication makes the provider load per link and repository rather than per session, and conditional requests lower it further.

**What a binding change does.** Every `lenny-egress-authz` replica re-reads the row and drops the pod's decisions. `netagent` flushes cached tokens and closes that session's tunnels at once. The next pod credential API call is refused, and the mirror's next egress decision API call is refused.

**`cacheUntil`.** The pod credential API response gains this field, the earlier of the credential's expiry and a value the Token Service chooses. `netagent` re-asks at that time. For a repository under a VCS pool with `userAuthorization: required`, the Token Service sets 300 seconds, on App tokens as well as child tokens, so a lost subscription cannot extend use past that. This generalizes the 15-minute lifetime stored secrets have.

| Compromised `netagent` holding a child token | Until Lenny revokes it at the host or it expires. On a verdict of `refused`, the Token Service calls `DELETE /applications/{client_id}/token` on the session's child tokens, which [S5](../0129-github-credential-addon/change.md#validation-owed) showed leaves the parent and other children valid **[measured]**. | **[design]** |
| Git operations in flight | A running push or fetch ends when its tunnel closes | **[design]** |

The stated figure for an honest pod is **6 minutes**. A tenant can lower `recheckIntervalSeconds` to 60 at a cost in provider calls. Webhooks would shorten this and are excluded from the first version, because Lenny has no provider webhook ingress and a repository-level `member` event would need one on every organization; UG-4 builds that ingress, and a later change can feed the sweep from it.

Once an entry is refused, `onAccessLost` on the VCS pool decides what happens to the session. The default, `deny`, keeps the session running without that repository and tells the client with a `repository_access_lost` event. `terminate` ends it. Content already in the workspace stays where it is under `deny`. See decision 13.

### Mirror, warm fills, and the 6-hour promise

- **Mirror reads.** The mirror authorizes each request through the egress decision API. For a repository under a VCS pool with `userAuthorization: required`, that check names the repository and reads the entry's state, so a store-served fetch with no mint still stops.
- **Warm fills.** A warm fill has no user, so the mirror's warm fill keeps its App path. Its contents enter a pod an agent reads. Every pre-filled store on a pod comes from its pool's warm list, as [`0147-tenant-derived-runtimes`, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores) states under **Warm list.** A `gitRepository` entry on a Runtime is public only, so a private store comes only from a tenant-owned pool's warm list: a `gitRepository` asset of the tenant-derived runtime, which a tenant admin writes, or a `platform-admin` through the same route. On every path that claims a pod, the gateway runs this design's repository authorization check on each tenant entry of the pool's warm list, whether or not the plan names the repository, as that design's ["Binding"](../0147-tenant-derived-runtimes/change.md#binding) and **Who reaches a store.** state. At create, a user lacking access to a repository a `gitClone` source of the plan names is refused, because the session needs its files, and a refusal on a default clone omits the repository's name. On a pool that runs one session per pod, a user lacking access to an entry whose repository the plan does not name has that store withheld: the adapter deletes it before the session starts, the session proceeds, and `withheldWarmEntries` reports the entry without its URL, as **Withheld stores.** states. On a pod with several slots, a failed check on any entry refuses the session, because a store cannot be withheld from one slot. A tenant entry under a VCS pool with `userAuthorization: required` is refused at write on a pool that reuses pods, and the render leaves a platform entry under such a VCS pool off a pool with concurrent sessions, so no per-user check runs where a store cannot be withheld, as that design's **Withheld stores.** states. A resume, retry, rebuild, or derive runs the check on every tenant entry of the warm list of the next pod's pool that the stored plan does not name, because an entry added after the session bound can put a store the plan does not declare on that pod. The plan does not name such an entry's repository, so a failure withholds its store and the session proceeds, except on a pod with several slots, where it refuses. A default clone's `write` value adds a writable entry at bind, and a user who can read and not write gets a read-only session on that entry, as [DR-9](../0147-tenant-derived-runtimes/change.md#dr-9-default-git-clones)'s "Write scope" states. A repository the client names keeps this design's refusal. A default clone's `write: always`, under which every session on the runtime can push to the clone with no statement from the client, is refused for a repository under a VCS pool with `prAuthoring: user`. The trigger of "The attach rule" under UG-3, a writable repository the session declares, therefore always comes from the client.
- **Outage rule.** The mirror's "Upstream outage" row in [`0127-egress-and-git`, "Git mirror"](../0127-egress-and-git/change.md#git-mirror-lenny-git-mirror), and its 6-hour confirmation, conflict with fail-closed authorization. The rule is:
  - A new session, a resume, and a mint need a current `allowed` from the provider. `unavailable` refuses them, with a retryable error. Writes need the host anyway.
  - A running session's reads of a repository continue from the mirror's store while that entry's `verifiedAt` is within `verdictMaxAgeSeconds` (900 by default, and a ceiling of 3600). Past that, both mint checks refuse reads of that repository until a sweep succeeds, and other repositories are unaffected.
  - The 6-hour fallback therefore never applies to a repository under a VCS pool with `userAuthorization: required`. It keeps its meaning under every other VCS pool. A tenant that values outage reads above per-user limits leaves the pool's `userAuthorization` at `off`.
  - A stalled sweep, whatever its cause, has the same effect after 900 s, which is the direction of the egress security property [P6](../0127-egress-and-git/change.md#security-properties), that a failure of any egress component blocks traffic. `UserAuthorizationSweepStalled` alerts well before that.

### Pod models

UP-5 refuses a `userCredential` binding, with `422 USER_CREDENTIAL_UNSUPPORTED_POD` as [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) states for every type, and the repositories of a VCS pool with `userAuthorization: required`, with `422 USER_AUTHORIZATION_UNSUPPORTED_POD`, on these pods. The binding validator refuses a definition that can only reach such pods. The generic design's `retireOnRelease` keeps a later pool edit from making the pod eligible to serve another session, and the pod credential API refuses a release without it. It applies to these repositories too, and [UC-3](../0151-user-credential-delivery/change.md#uc-3-the-usercredential-binding) builds it.

| Pod | Why |
| :-- | :-- |

Under decision 60 of [`0127-egress-and-git`](../0127-egress-and-git/change.md#decisions), settled on 2026-11-13, `netagent` attributes each loopback connection to its slot by the connecting socket's owner UID and gives each slot its own session's readable and writable sets, environment, and credential bindings, so Alice's token no longer serves Bob's slot where attribution holds. The `sessionPolicy.maxConcurrentSessionsPerPod > 1` refusal lifts on a pool whose attribution status records per-slot attribution, because the egress design's decision 60 gives each slot its own scopes, and it stays on a fallback pool, where the union fallback applies. The `recycle.enabled` and served-pod refusals remain on the restated ground. Which runtime classes answer attribution is measured by a spike the owner asked for (V5). The `scope: always` refusal does not depend on the slot model. Those settings apply to the whole tenant and neither replace nor relax the refusals here, which apply to the repositories and bindings of this design.

Warm pods remain allowed. No runtime process runs on a pod before bind: every runtime process starts at bind, after materialization and setup. A warm pod's stores and warm checkouts come from its pool's warm list, which the repository check covers ("Mirror, warm fills, and the 6-hour promise"). The materialization helper runs every git step on a slot repository as the slot UID with the pinned `/lenny/bin/git` and holds no token, and its fetches reach the host through `netagent` under a fetch grant the adapter registers ([`0153-workspace-materialization`](../0153-workspace-materialization/change.md)). The adapter runs no git on slot repositories. Materialization therefore opens no path around the check at bind. The refusals cost concurrent and recycled pools their efficiency for these tenants, which decision 14 records.

### Identity cases

The requesting user is read from the session row by both mint checks, through `pkg/binding`, and never from a token or a pod. A running session does not depend on its creator's bearer.

- **Impersonation.** A bearer whose `issued_tokens` row is an impersonation row already cannot create, derive (start a session from another session's workspace snapshot or stored plan), or create-and-start. For a session with a repository under a VCS pool with `userAuthorization: required`, or holding a `userCredential` binding, [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md)'s session input check refuses it at `executor.Executor.Send`, `sessioninbox.Inbox.Enqueue`, and the non-message session routes, with `403 FORBIDDEN` and the reason `impersonation_user_credential`. A test covers every mounted mux. An operator can read the session and cannot drive it into using Alice's token. [SO-4a](../0142-security-oversight/change.md#so-4a-mirror-to-the-tenant-chain)'s `impersonated_by` claim is the same signal once it exists.
- **Delegated children.** A child carries its parent's user on its row, so the same link and check apply to its own declared set for App tokens. It receives the pool's `userCredential` binding only when the delegation lease names it, and `poolAttach` does not bypass that, under [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md). A child with no lease entry has no API token, and no App binding stands in for it, so its identity does not change silently. Its pod must pass the same pod model test. `credential.mint` records its `sessionId`, and the session row gives its `root_session_id`.
- **Detached orphans.** An orphan "carries the originating user's identity" ([§8.10](../../spec/08_recursive-delegation.md#810-delegation-tree-recovery)), keeps being swept, and ends at `cascadeTimeoutSeconds`, 3600 by default. It keeps authorization and keeps what it was granted, because `detach` is what the client asked for, and §11.4's listing by owner reaches it. Decision 18 records this.
- **Disabled users.** Each mint check reads the user's invalidation level and `processing_restricted` through `pkg/binding`. Any of `soft_disable`, `hard_disable`, or `full_revoke` refuses every user-derived mint and every App mint for a repository under a VCS pool with `userAuthorization: required`, including the running sessions §11.4 otherwise leaves up on the lesser levels. A store error fails closed, as [TS-4](../0149-tenant-scoping-identity/change.md#user-lifecycle-ts-4) does.
- **Cross-environment.** Under [`0149-tenant-scoping-identity` decision 14](../0149-tenant-scoping-identity/change.md#cross-environment-sharing-decision-14), a child in its parent's environment needs no new rule, and a child reached through a sharing path runs in the target environment, written T here, so `visible(bindings, T)` and `visible(VCS pools, T)` apply. It keeps its parent's user, so a VCS pool in T with `userAuthorization: required` checks that user. A user-sourced binding crosses only when the delegation lease names it. The link itself has no environment, so no team needs its own link.
- **Environment-less pods.** Under [`0149-tenant-scoping-identity` decision 15](../0149-tenant-scoping-identity/change.md#decisions), a pod with several slots evaluates with no environment where `netagent` cannot attribute a connection to its slot, the fallback of the egress design's decision 60, and a session is refused there when its environment has anything of its own. Where attribution holds, each slot evaluates its own session's environment. The refused pod models above refuse pods with several slots for the repositories and bindings of this design in the first case, and admit them in the second on a pod that has served no session (decision 52).

### Service identities

An automated session has no person to check. A VCS pool with `userAuthorization: required` lists service identities in its `serviceIdentities` field, each with a `subject`, its own repository allowlist, and its own `allowWrite`. A session uses that path only when all of these hold:

- The caller's `caller_type` is `service`, which [§13.3](../../spec/13_security-model.md#133-credential-flow) makes impossible to elevate on exchange, and which the session row now records, so both mint checks read it through `pkg/binding`.
- The bearer's Lenny subject is listed on the pool. A service caller's Lenny subject is `~svc~` followed by its canonical subject under [`0143-service-account-credentials`, "SA-6 Subject namespaces"](../0143-service-account-credentials/change.md#sa-6-subject-namespaces), each entry's `subject` must begin with `~svc~`, and a pool write naming any other subject is refused with `422 VALIDATION_ERROR`, so no person's subject can be listed.
- The session is a root session under that subject. A human's delegated child stays under the human, and its row copies the human's `caller_type`.

Who may hold one: a system principal authenticating through the client credentials path of §10.2, whose credential no person handles as a routine. A `tenant-admin` writes the list through the single write path for tenant opt-ins, which the egress design's proposal [EG-9](../0127-egress-and-git/change.md#steps) (egress policy objects) adds, each write emits an audit event, and a `security-admin` can restrict or forbid the list through a new `userAuthorization.serviceIdentities` guardrail. A person cannot move onto this path by presenting a token with a chosen `caller_type`, because the subject must be listed. Lenny cannot detect a person holding a listed client secret, which "Residual risks" states.

A listed service session takes the App binding on that host, under "The attach rule", so its pull requests have the App as author. A service account can own rows of a `userCredential` type under [`0143-service-account-credentials`](../0143-service-account-credentials/change.md), and "Other tokens on these hosts" refuses such a type on the API host of a VCS pool with `userAuthorization: required` whatever its source, so a listed service session keeps the App path and the UG-2 check. Any other root session whose `caller_type` is not `human` is refused for repositories under a VCS pool with `userAuthorization: required`, with no check to run. The flavour's preset applies to that binding too, because `pull_requests: write` on an App token can approve any human's pull request.

### Attribution

`credential.mint` carries "a session identifier and no user identifier", and §12.8 treats it accordingly: `DeleteByUser` deletes nothing from it. This design keeps that.

- `credential.mint` gains `tokenSource` and `linkRef`. `tokenSource` is one of `app`, `userRegistered`, `userOauth2`, `userChild`, and `userCheck`, as [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) defines. It carries no login, email, or `user_id`.
- `linkRef` is a pseudonym in the same class as the session identifier. Its join lives in `user_links`, which erasure deletes, so a stored record stops resolving to a person, and the erasure statement in [`0127-egress-and-git`, "Evidence streams"](../0127-egress-and-git/change.md#evidence-streams) stays true once it says so. The class statement needs that one sentence when UG-2 lands.
- The token hash field stays. For a child token, the hash also joins to the provider's audit log, which GitHub describes as listing the user with "`programmatic_access_type`" of "GitHub App user-to-server token" **[documented]**. That join lies with the customer's provider log rather than a Lenny store.
- The provider login appears only in `user_links` and in §11.7 audit events, whose treatment §12.8 already defines through step 13 and step 14.
- A tenant's security team asks "who" by joining `sessionId` to the session row while it exists.
- A request rule refusal goes to `egress.local` with the decision identifier and the operation name, with no variables or body. Repeated refusals on one session raise a `user_credential_rule_refusals` alert, because an agent trying to approve is a prompt injection signal. These records are `self_reported`, as the stream's table says.

## UG-3: Pull request authoring

### The binding

Revision 3 had a third `secret` kind, `userLink`, with a filter a tenant could not clear. **`userLink` is now the `oauth2Link` source of a `userCredential` binding**, and setting `prAuthoring: user` on a VCS pool writes this record:

```yaml
userCredentialTypes:
  - {name: github-user, source: oauth2Link, linkProvider: github-acme}
---
secret: { kind: userCredential, type: github-user }
hosts: [api.github.com]
delivery: inject
scope: poolAttach
# no attach: the kind fixes it, in the token trust record
# no preset key: resolved on the pod credential API from the flavour of the pool's provider and host
```

- A VCS pool's `prAuthoring: user` requires `userAuthorization: required` on the same pool, and an `oauth2Link` type whose named link provider is on the pool's host with a `delivery` ceiling of `inject` or above. That link provider can differ from the one `userAuthorization.linkProvider` names for the check. A write without them is refused, so the check and the missing-link refusal always hold on such a pool. Decision 44 records the cost. A write of `userAuthorization: required` whose `userAuthorization.linkProvider` is absent or names no VCS-kind provider on the pool's host is refused too.
- `hosts` is the API host from the kind's request layout: `api.github.com` on GitHub, `api.<name>.ghe.com` on `ghe.com`, and the host itself on GHES and GitLab. On GHES, the same hostname serves git and the web, and a smart HTTP path there takes [the egress design](../0127-egress-and-git/change.md)'s git path rather than this binding.
- The link provider names its kind's shipped template, which on GitHub is `github-scoped`, whose `permissions` is `pull_requests: write` and `contents: read` by default. That is data a tenant can widen, which the owner settled under [`0129-github-credential-addon` decision 5](../0129-github-credential-addon/change.md#decisions).
- The preset resolves on the pod credential API from the flavour of the VCS pool's provider and host, and a tenant can change it. A `security-admin` can require it through `requestRules.requiredPresets`. See [`0151-user-credential-delivery`, "Who can change a preset"](../0151-user-credential-delivery/change.md#who-can-change-a-preset).
- `netagent` holds no provider code for this. The add-on's code runs in the Token Service.

### The attach rule

This is the one place the attach is defined, and the [egress design](../0127-egress-and-git/change.md)'s `scope`, [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md), and [`0149-tenant-scoping-identity`](../0149-tenant-scoping-identity/change.md) point here.

- **The trigger.** A human root session that declares at least one writable repository under a VCS pool with `prAuthoring: user` receives that pool's binding, with `scope: poolAttach`, without naming it. The binding's own `required: true` field makes a missing link refuse the session with `403 LINKS_REQUIRED`, which lists the link under `details.userLinks`. A session declaring only read-only repositories there does not attach.
- **It replaces a same-host App binding, on that host alone, for that session.** A tenant-wide App binding on `api.github.com` can exist beside it, because service sessions need one. It keeps its other hosts, such as `uploads.github.com`. Replacement holds whatever the user binding's state, so a user binding with `suspendedBy` set restores no App binding (UP-6). It also holds when the session's other entries sit under a VCS pool with `prAuthoring: off` on that host. A session naming a second binding with `delivery: inject` on that host explicitly is refused at bind under the one-binding rule.
- **A listed service session** takes the App binding on that host, and never the pool's. Any other caller whose `caller_type` is not `human` is refused on such a pool.
- **A delegated child** receives the pool's binding only when the lease names it, as "Identity cases" states.

### Other tokens on these hosts

Under [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md), a tenant can also define a type of its own on these hosts, and rules evaluate that type's hosts. Such a type does not bypass the UG-2 check on App tokens, and it does sit beside it. **What follows is by host, for every session of the tenant.** On the API host of a VCS pool with `userAuthorization: required`, the only permitted bindings with `delivery: inject` are an App-sourced binding, which the check governs, and the pool's link. A stored secret has no check, so it is refused at write, setting `userAuthorization: required` on a VCS pool suspends one that exists, and `userAuthorization.require` makes that hold whatever a tenant admin writes. **The owner also adopted this rule: a binding with `delivery: file` whose type hosts include a covered host is refused unless every VCS pool covering that host sets `allowRuntimeHeldCredentials`, whatever the pool's `userAuthorization` value,** because on a VCS pool with `userAuthorization: off` the push would otherwise silently act as the App. A VCS pool added later without `allowRuntimeHeldCredentials`, or that setting cleared later, suspends the binding, and a running session that named it gets a 401 on git rather than the App. On a host covered by a git route alone, the binding is admitted, the held token is dropped on the git path, and a push is refused. A platform warm-up asset covers its host only until bind, except on a pool whose `egressProfile` is `restricted` with `gitAccess`, so it does not bring this rule to a tenant with no pool there. A plan naming a suspended binding with `delivery: file` is rejected at create with `422 USER_CREDENTIAL_BINDING_SUSPENDED`. This layer's host policy states these, and `allowRuntimeHeldCredentials` builds on [UC-5](../0151-user-credential-delivery/change.md#uc-5-delivery-file) of [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md).

| On the hosts of a VCS pool with `userAuthorization: required` | Result |
| :-- | :-- |
| A stored secret binding, under either delivery | Refused at write. |
| Any other `userCredential` type with `delivery: inject` on the API host, whatever its source: `registered`, a link provider with `kind: oauth2`, `clientCredentials`, or `issuerExchange`, and whatever principal owns its rows | Refused at write. |
| A binding with `delivery: file` whose type hosts include these hosts, where some VCS pool covering them lacks `allowRuntimeHeldCredentials` | Refused at write. |
| That binding, where every VCS pool covering the host sets `allowRuntimeHeldCredentials: true`, this pool's `prAuthoring` is not `user`, and the session has no App binding on the API host | **UP-4 still holds for App tokens: no App token without a verdict. UP-9, UR-2 for what the agent's token reaches, UR-4, and UR-6 do not hold for that session,** since its token leaves every Lenny control. Posture reports the pool, and the session is marked `agentHeldCredential`, the generic design's mark for a session that holds a token under `delivery: file`. **Other sessions on the pool are unchanged:** the runtime-held attach, under which `netagent` attaches the value the runtime holds to its git requests ("Git and hosts" below), applies to a session naming that binding, whatever its release or suspension state, and with no current value the host answers 401. The pin exception, under which such a session is excepted from the pool's pin on that host ("Other hosts", **Pinned hosts**), needs a release, and suspension ends it. Without `allowRuntimeHeldCredentials`, a held token is dropped for git and the mint is used **[measured]**. With it, `netagent` attaches the current value it holds on every git request and no mint is used to `netagent` for that host, under "Git and hosts", and with no current value the host answers 401 **[measured]**. |
| That binding on a VCS pool with `prAuthoring: user`, or beside an App binding on the API host | Refused at bind by the one-binding rule. |
| A binding with `delivery: file` on a type whose source is this pool's link provider | Refused unless `allowRuntimeHeldCredentials` applies as above and the link provider's `delivery` ceiling is `file`. |

A tenant that needs `userAuthorization: required` to mean what it says leaves `allowRuntimeHeldCredentials` off and takes the `userAuthorization.forbidRuntimeHeld` guardrail of [SO-2](../0142-security-oversight/change.md#so-2-tenant-security-record-and-posture). Under that guardrail every VCS pool's `allowRuntimeHeldCredentials` reads as `false`, so a `userCredential` binding with `delivery: file` whose type hosts include those pools' hosts is suspended, and a plan naming it is refused at create with `422 USER_CREDENTIAL_BINDING_SUSPENDED`.

A `registered` type can lie, by declaring an innocent host and holding a GitHub token. That passes the checks above, and the enforcing control is the pin on the host the token works on, which waits on the egress design's exfiltration controls, [EG-12](../0127-egress-and-git/change.md#steps).

**A smuggled token.** A client can also place a token through an `inlineFile` workspace plan source, whose content the client supplies, through the plan's `env` variables under a name the deployer's blocklist of denied variable names does not match, or in a message **[source]**, and input checks cannot recognize one. For repositories under a VCS pool with `userAuthorization: required`, this bypasses the check on any unpinned host, and revision 3 pinned nothing. **The rule, which the owner settled under decision 40: when any VCS pool with `userAuthorization: required` covers a host, that host and the kind's API hosts are `credentialPinned` for every session of the tenant, once [EG-12](../0127-egress-and-git/change.md#steps) has landed.** A token reaching that host reaches the pool's repositories whichever pool the session is on, so the pin source reads every VCS pool of the tenant, unfiltered by environment and whether or not a guardrail has suspended it. A pool with `egressProfile: internet` gives its sessions raw sockets that bypass `netagent`, so they stay outside the pin, and posture reports that too. Until [EG-12](../0127-egress-and-git/change.md#steps) lands, under `pinHosts: false`, or on a pool with `egressProfile: internet`, this is a stated residual. Under git path T, a held token on a covered host is dropped for git and the mint is used **[measured]**, so the residual there is the API host. Decision 40 records the costs.

### Other hosts

- **Stored token on a covered git host.** [The egress design](../0127-egress-and-git/change.md) refuses a stored token binding, under either delivery, on a git host a VCS pool covers, because the token would reach that host's REST write routes with no path enforcement. A `registered` type under `delivery: inject` is a stored token, so the refusal applies, evaluated on type hosts. The one exception is a `userCredential` binding under `delivery: file` when `allowRuntimeHeldCredentials` applies.
- **A type a link uses.** A binding with `delivery: file` is refused on a type whose link provider a VCS pool's `prAuthoring: user` binding or its UG-2 check uses, unless `allowRuntimeHeldCredentials` applies and the record's delivery ceiling is `file`.
- **Pinned hosts.** `credentialPinned` strips other credentials, so a token under `delivery: file` sent to a pinned host breaks: `netagent` removes it. A binding with `delivery: file` whose type hosts include a pinned host is refused at write, and a pin added later suspends that binding, naming the pin, rather than leaving one that silently fails. A session that `allowRuntimeHeldCredentials` applies to is excepted from the pin of a VCS pool with `userAuthorization: required`, on that host alone, once it has received a release, and suspension ends the exception.
- **A host with a binding under `delivery: inject` and no VCS pool.** `netagent` classifies smart HTTP on every terminated host, so git to it carries no credential, the secret stays off the git request, and a push is refused **[measured]**. The host of a binding with `delivery: file` is not terminated for that reason, so with no VCS pool or route it stays opaque.
- **A host with a binding under `delivery: inject`.** `netagent` overwrites the `attach` header, and its credential list strips others, so a runtime token sent there is replaced. The one-binding rule refuses this at bind.
- **Hosts of a VCS pool with `userAuthorization: required`.** See "Other tokens on these hosts".

### Request rules on VCS hosts

[`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md) defines request rules, presets, and who can change them. This section states what they mean here.

**The model.** Each VCS add-on ships its presets as data, with paths per API flavour and request forms: `github-deny` in [`0129-github-credential-addon`](../0129-github-credential-addon/change.md#preset-body) and `gitlab-deny` in [`0130-gitlab-credential-addon`](../0130-gitlab-credential-addon/change.md#preset-body). The flavour of the VCS pool's provider and host selects the preset when the pod credential API answers. A binding that adds rules keeps the preset, and only the binding field `preset: none` clears it. The `github-deny` body is the extended preset, which the owner settled under [`0129-github-credential-addon` decision 8](../0129-github-credential-addon/change.md#decisions). Under `requestRules.default: allow`, the default, a request matching no rule passes, so a new `gh` release keeps working, and `gh pr comment`, `edit`, `ready`, `close`, `reopen`, and `edit --base` all pass the rules by default. A binding a tenant puts in allow-list mode, which [`0151-user-credential-delivery`, "Allow-list mode"](../0151-user-credential-delivery/change.md#allow-list-mode) states, refuses a write no allow rule admits, and the preset still applies on top. What the preset refuses stays refused unless a tenant changes it.

**Selecting the flavour.** The flavour derives from a VCS pool's provider and host, with no stored field, and the pod credential API reads it. Each VCS add-on registers the request layout for its kinds: the flavour, the API host, `apiBase`, `restPrefix`, the GraphQL paths, the uploads path, and `attach`. [`0129-github-credential-addon`, "Request layout"](../0129-github-credential-addon/change.md#request-layout) and [`0130-gitlab-credential-addon`, "Request layout"](../0130-gitlab-credential-addon/change.md#request-layout) list them.

A tenant admin has no field to set, so she cannot satisfy the `requestRules.requiredPresets` guardrail with rules that match nothing. Resolution reads every VCS pool of the tenant, unfiltered by environment and whether or not a guardrail has suspended it, and a write refuses two VCS pools on one host whose flavours differ. `/api/graphql` is a listed path for both GHES and GitLab. On a host no pool covers, each preset therefore carries the other's denied mutation names. REST there fails closed on the prefix: a path under `/graphql*` or `/api/*` that is not the resolved flavour's own GraphQL, uploads, or REST prefix is refused **[measured]**, with 13 of the 36 names tried. A link provider's `kind` must agree with the host's flavour at write.

**On by default, resolved on the pod credential API.** A binding whose `requestRules` has no `preset` key, whatever its source, on the API host of a VCS pool, from the add-on's request layout, resolves on the pod credential API to that flavour's preset. It covers an App-sourced binding, a project token, and a `registered` type, because an App token with `pull_requests: write` can also approve. `preset: none` clears it explicitly. On a host no VCS pool covers, no preset applies unless the binding names one, and then its family, `github-deny` or `gitlab-deny`, and the host give the flavour: `github-deny` is `github` on `api.github.com` and `api.<name>.ghe.com`, and `github-enterprise` elsewhere, and `gitlab-deny` is `gitlab`. No field can select another. Resolution on the pod credential API means a VCS pool added later takes effect at the next `cacheUntil`.

**What remains unbound.** Targets (which pull request or object an operation acts on), reads (`repository`, `node`, and `search` read whatever the token reads), free text, and git, which sits under the [egress design](../0127-egress-and-git/change.md)'s rules, this design's ["Push identity"](#push-identity), and the push option refusal.

### Keeping presets current

An unlisted operation passes under `requestRules.default: allow`, so a new `gh` release breaks nothing. The risk moves to the server side and to presets.

- A CI job diffs GitHub's public GraphQL schema and REST OpenAPI description, and GitLab's quick action page and fine-grained tables, on a schedule. A new name in the review, merge, queue, content, ref, deployment, or policy families raises a preset change for review. The preset names REST twins and policy mutations that exist today, which the accepted loss of UR-6, a new operation passing until the preset names it, does not cover. The rate is about one a year on GitHub, in one reading **[source]**.
- Rules reach `netagent` resolved on the pod credential API, so a preset update reaches a pod at its next `cacheUntil` with no image change.
- The window in which a new mutation with that power passes is the schedule, the review, and `cacheUntil`. "Residual risks" states it.

### Comment-triggered actions

An input something else treats as a command carries Alice's identity. Each add-on states its provider's automation: [`0129-github-credential-addon`](../0129-github-credential-addon/change.md#comment-triggered-actions-on-github) covers comment bots and label triggers on GitHub, and [`0130-gitlab-credential-addon`](../0130-gitlab-credential-addon/change.md#quick-actions) covers GitLab's quick actions, commands such as `/merge` that GitLab runs from a comment or description. The body of `createPullRequest` and `updatePullRequest` carries the same risk as a comment, so refusing comments never closed this path, and revision 3's capture showed that it cost `gh pr comment` **[captured]**.

**Under the preset model.** Revision 3's required `repositoryAutomation` statement is retired, along with its label-key logic, because those were allowlist input checks. A tenant with such automation adds rules:

- `graphql.denyMutations: [addComment, addLabelsToLabelable, ...]` refuses an operation outright.
- `bodyPatterns` with the bot's grammar refuses per line on comments, PR bodies, and titles, including every string and block string literal in a GraphQL document, such as `createNote(input: {body: "ok\n/merge"})`, a variable default, or a directive argument **[measured]**. A pattern is a deny list over free text, which the capture found weak: refusing every `/word` line also refused `/usr/bin/env` **[captured]**. It is offered because the tenant's list targets a grammar it controls.
- The stronger control sits with the bot: a comment made through a GitHub App user token carries a non-null `performed_via_github_app` in the REST schema **[documented]**, and the UI shows the App's badge, so a bot or workflow can refuse commands from it. The tenant page recommends that first, and whether bots see that field in webhook payloads is [S15](../0129-github-credential-addon/change.md#validation-owed).

The owner settled decision 35: `repositoryAutomation` is retired, and the setup flow and posture prompt a tenant about bots.

**CI (continuous integration).** A pushed branch triggers the repository's existing workflows. GitHub's page says secrets are withheld "when a workflow is triggered from a forked repository" **[documented]**, and it describes no such withholding for a branch in the same repository, which is where an agent pushes. The default token omits `workflows: write`, so an agent cannot edit a workflow file, and a workflow still runs the branch's build scripts. Whether an App token's push triggers these is not stated on that page ([S15](../0129-github-credential-addon/change.md#validation-owed)). GitLab behaves the same way for unprotected variables, and it has no permission like `workflows: write`, so an agent can also push a `.gitlab-ci.yml`, as the egress design states. A tenant limits this with required reviewers on environments and protected variables, and the repository setting that lets Actions approve pull requests stays off. This exists under the egress design's App-token pushes today, and "Residual risks" states it.

### Git push options

`git push -o` reaches GitLab inside `git-receive-pack`, past everything else here. Under option D of [`0130-gitlab-credential-addon`](../0130-gitlab-credential-addon/change.md#options), git uses the project token and `netagent` reads only ref commands, so `git push -o merge_request.create -o merge_request.auto_merge -o merge_request.target=main` requests a bot-authored merge request with auto-merge, and Erin can approve a bot's merge request. `merge_request.description` also carries text past `netagent`'s ref checks. GitLab's page lists these along with `ci.skip`, `ci.no_pipeline`, `ci.variable`, `ci.input`, `integrations.skip_ci`, `secret_push_protection.skip_all`, and `security_policy.bypass_reason` **[documented]**.

The rule, on every covered host: **`netagent` refuses a `git-receive-pack` request that uses the `push-options` capability, and strips that capability from the ref advertisement, so git reports the failure before sending a pack.** The VCS pool's `allowedPushOptions` list can admit a specific option, and it is empty by default. An agent using `-o ci.skip` is refused. The capture did not examine `git push`, and the worked `gh pr create` and `glab mr create` flows need no push option. Because a push option's section sits between the ref commands and the pack, `netagent` needs bounded parsing past the commands it reads today, and that is a requested change on the egress design's pod git path, [EG-3](../0127-egress-and-git/change.md#steps). **[design]**

### Push identity

A VCS pool with `prAuthoring: user` sets `pushIdentity`, which decides whose token carries a human session's git pushes. Under `user`, a push carries a token the kind's add-on derives from the requesting user's link, so the provider records the user as the pusher. Under `app`, pushes keep repository-limited App tokens, and a pool write with `prAuthoring: user` and `pushIdentity: app` is refused unless the tenant runs UG-4, which reasons about sessions rather than pushers. A listed service session has no user and keeps the App write token (UR-7). Lenny writes no branch rules for user pushes, by decision 10, so the session pushes wherever its user can push on the session's writable repositories, and the repository's own branch protection and rulesets apply to the agent as they apply to the user. A tenant can still set `allowedRefPatterns` on a VCS pool under the egress design, and none is written by default.

`user` is the default on GitHub, and [`0129-github-credential-addon`, "Pushes as the user"](../0129-github-credential-addon/change.md#pushes-as-the-user), states how the GitHub add-on implements it and what GitHub's most-recent-push rule then gives. On GitLab, pushes use the project token until spike [S13](../0130-gitlab-credential-addon/change.md#validation-owed) shows a per-session token can push, and decision 47 asks how to bound App-identity pushes.

### Commit authorship

[The egress design](../0127-egress-and-git/change.md#push-limits-and-commit-identity) lets a VCS pool set the author and committer. On a VCS pool with `prAuthoring: user`, the gateway sets the author to the linked user: on GitHub `<id>+<login>@users.noreply.github.com` and on GitLab the link's verified primary email, read at link with `read_user`. The committer stays the pool's agent identity, and a `Lenny-Session` trailer is added by the commit template in the git configuration Lenny renders for the session. This serves GitLab's "Prevent approvals by users who add commits", which excludes "the Git author and Git committer" **[documented]**, and it makes commit history truthful about who requested the work. The egress design renders these fields into one identity file per VCS pool on the slot's credentials volume, and the session's git configuration file, which the pod-wide configuration includes, selects that file per repository under `includeIf "hasconfig:remote.*.url:<pattern>"` ([`0127-egress-and-git`, "Git configuration"](../0127-egress-and-git/change.md#git-configuration), [decision 65 of `0127-egress-and-git`](../0127-egress-and-git/change.md#decisions), settled on 2026-11-13). A repository under a VCS pool with `prAuthoring: user` therefore takes the linked user as author, a repository under another VCS pool of the same session takes that pool's identity, and no slot reads another session's author. The template fills the commit message editor, so a commit made with `git commit -m` or `-F` carries no `Lenny-Session` trailer.

These fields are text the agent can change with `git -c`, and `netagent` does not read pack contents, so they are advisory on GitHub and a soft signal on GitLab ([S12](../0130-gitlab-credential-addon/change.md#validation-owed) tests how GitLab matches them). Signing is out of scope, because the agent holds no user key.

### Delivery

The binding that a VCS pool's `prAuthoring: user` attaches uses `delivery: inject`, and its link provider's `delivery` ceiling is `inject` or `file`. A runtime that needs its token as a file uses `delivery: file` under [`0151-user-credential-delivery`](../0151-user-credential-delivery/change.md), behind the `userCredentialDelivery` grant and a binding opt-in. Revision 3 dropped `delivery: file` from the first version here. The owner's direction now is that the mechanism exists, generically, because Lenny "can't possibly handle all injection scenarios". Decision 16 records the change. `gh` and `glab` accept a placeholder **[measured]** (rounds 3 and 10) **[captured]**, so this configuration does not need it.

A token in a file readable by the agent UID can leave the pod through any allowed host and stay valid for up to 8 hours, a child token's lifetime from its creation ([S1](../0129-github-credential-addon/change.md#validation-owed)), and unlike a JSON Web Token (JWT) under the egress design's `federation` delivery, which gives a runtime a short-lived identity token that it exchanges at a cloud provider for that provider's credentials, it has no trust condition binding it to an address.

**Why Coder's delivery does not fit as a default.** Coder exposes the token inside the workspace through `GIT_ASKPASS` and `coder external-auth access-token` **[documented]**. For a person at a workspace, the person is the principal, and handing them a token they could get anyway removes nothing. An autonomous agent reads untrusted content, so any process it starts can run that command and send the result to any allowed host, after which no rule applies and no later revocation reaches it. Lenny keeps Coder's linking experience and defaults to a different delivery: the placeholder stays in the pod and the token stays in `netagent`, and `gh` runs with `GH_TOKEN=lenny-injected` as the egress design validated.

### Repository rules

[`0142-security-oversight` decision 25](../0142-security-oversight/change.md#decisions) and [SP11](../0142-security-oversight/change.md#security-properties), the property that a repository marked for approval receives no write token until its approval exists, apply as written:

- A child token from a platform-shipped template with `followsEntryState`, a template flag under which each mint names only the session's writable repositories whose entry `state` is `granted`, which is `github-scoped` today, is a binding mint from a provider in the egress design's `mint-scoped` class, so it names only entries in state `granted`, and a repository rule added during a session moves the entry and flushes the cache by binding change.
- A GitLab project token or any non-`mint-scoped` binding on a repository rule's API host is refused or suspended under [`0142-security-oversight`](../0142-security-oversight/change.md#so-5b-repository-write-approvals)'s `approvals.repositoryWrites` setting. `gitlab-fine-grained`, the narrowing template the GitLab add-on ships, is narrower than those, and it does not set `followsEntryState` until [GL-2](../0130-gitlab-credential-addon/change.md#gl-2-user-authored-merge-requests) is settled, so it is treated as non-`mint-scoped` for now. PR authoring on GitLab is therefore absent on a host with a repository rule, which that decision's cost already names.
- Pushes follow the repository write approvals of [SO-5b](../0142-security-oversight/change.md#so-5b-repository-write-approvals) unchanged, and the git child, like the API child, names only entries in state `granted`.
- A child minted before a repository rule moved its entry is revoked and reminted for the new set, which [S5](../0129-github-credential-addon/change.md#validation-owed) makes safe. Until the revocation lands it stays valid at the host, and [SP11](../0142-security-oversight/change.md#security-properties)'s residual covers this.

## UG-4: Independent approval check

A required status check from the App fails when the only approver is the session's requesting user. This is offered on any VCS pool, for tenants that refuse user tokens in pods or that want every pusher excluded rather than the latest alone, and it is required for a VCS pool with `prAuthoring: user` and `pushIdentity: app`, where GitHub sees the App as the pusher. It needs no token in a pod.

**How it works.** Lenny's App reports a status `lenny/independent-approval` on each pull request head:

- A webhook receiver listens for `pull_request` and `pull_request_review` events and verifies the signature. It needs `statuses: write` or `checks: write`.
- For a pull request's commits, it collects the sessions that pushed them from `git.operation`, which records refs and new SHAs, and maps each session to a user and then to a provider identity through `user_links`. The opener comes from the pull request's author when that is a person. When the App authored it, GitHub does not say which token made the request, so the check uses the pushers alone. Earlier revisions read the opener from the head branch's namespace, which decision 10 removed.
- It passes when at least one approver's provider identifier is outside that set, and it fails otherwise. A commit it cannot attribute counts as having no person, which leaves the approver free.

It catches the case the native rule misses, including Alice's agent pushing to Bob's pull request, because it reasons about sessions rather than pushers.

**Limits.**

- A pull request still shows the App as author.
- "No user token" is true at run time, and the check needs a proven mapping from Lenny user to provider identity. A link runs with the link provider's `delivery` ceiling at `identifier`, which keeps the numeric identifier and login and discards the token, so an attacker cannot claim someone else's identity. A tenant that refuses even that gets a mapping it must supply itself, which then rests on the tenant's own directory.
- The tenant configures the check as required on each protected branch. Lenny can verify that with a read and report it in posture, and it cannot force it.
- It adds a public webhook ingress to the gateway and App permissions, and a Lenny outage leaves the status pending, which blocks merges. That is fail-closed, at the cost of a merge outage.
- `git.operation` from `netagent` is `self_reported`, so a compromised `netagent` can omit a record.
- It needs `git.operation` retention at least as long as a pull request stays open.
- An App-authored pull request whose opener pushed nothing to it does not count the opener. An agent that opens a pull request for commits only another user's session pushed leaves its own user free to approve.

On GitLab, external status checks are the corresponding feature, on the tiers GitLab offers it, and the same logic applies. [S12](../0130-gitlab-credential-addon/change.md#validation-owed) confirms tier and behaviour.

### A GitHub token beside `userAuthorization: required`

VCS pool `github.com/acme/` sets `userAuthorization: required` and `prAuthoring: off`. Carol adds type `gh-pat`, with `source: registered` and `hosts: [github.com, api.github.com]`, and a binding with `delivery: file`. Declaring `hosts: [docs.acme.com]` passes that check, since a `registered` type can lie, and the agent then holds the token anyway. The enforcing control on that path is the pin on `github.com`, which strips it. She sets `allowRuntimeHeldCredentials: true` on the pool instead, and posture reports that this design's UP-9, UR-2, UR-4, and UR-6 no longer hold for sessions naming this binding. Alice's agent runs `git push` with the token:

- Without `allowRuntimeHeldCredentials`, the mint replaces it on a covered host **[measured]**, under "Git and hosts".
- With `allowRuntimeHeldCredentials`, `netagent` attaches the current value it holds on every git request and keeps path enforcement and `git.operation`, with no mint for that host **[measured]**.
- App mints stay checked. A session that does not name the binding keeps the pin, and the mint replaces any token it sends.

## Residual risks

- **Concurrent sessions on an attributing pod.** Under decision 52, a pool with several slots whose attribution status records per-slot attribution admits these repositories and bindings, so a session whose agent compromises `netagent`, the adapter, or the sandbox kernel reaches the tokens of the sessions running beside it on the pod. The operator's `placement.allowSharedPod: false` keeps a tenant's sessions off such pods, and a pool with `maxConcurrentSessionsPerPod: 1` has no neighbouring session.
- **Token Service compromise.** It holds parent tokens, and refresh tokens, for every linked user. It already holds every App's private key and every stored secret. On GitHub a parent is limited by its link provider's App, which a read-only App narrows to nothing, and on GitLab with `read_api` a parent cannot write. Under [GL-2](../0130-gitlab-credential-addon/change.md#gl-2-user-authored-merge-requests), if [S13](../0130-gitlab-credential-addon/change.md#validation-owed) requires it, it holds `api` parents, which widens what its compromise exposes and is why that case needs a tenant opt-in.
- **The revocation window.** A revoked user keeps git access through an honest pod for up to 6 minutes, and for up to 15 minutes of reads during a host outage.
- **Workspace content.** What a session has cloned stays in the workspace, and in its checkpoints and artifacts, after access is lost. A VCS pool's `onAccessLost: terminate` ends the session and leaves stored artifacts under the owner's existing access.
- **Allowed mutations on other people's work.** On a session repository, Alice's agent can change the title, body, base, or state of Bob's pull request, close it, comment on it, and request reviewers, because rules do not see authorship or input keys and the host allows it. These are attributed, and most are reversible. A base change can move an approved pull request onto another branch ([S16](../0129-github-credential-addon/change.md#validation-owed)).
- **New operations.** Under `requestRules.default: allow`, a new GitHub or GitLab operation with approval or merge power passes until the preset names it. The owner accepted this. About one a year needs only `pull_requests: write` on GitHub, in one reading **[source]**.
- **Pushes with the user's rights.** On a VCS pool with `pushIdentity: user`, an agent pushes wherever its user can on the session's writable repositories, including a protected branch the user is allowed to bypass. Lenny writes no branch rules, by the owner's decision 10, and the repository's own protection is the control.
- **Two-person review depends on the repository.** UR-4 holds for pushed work only where the repository requires approval of the most recent push, and only while the agent's push is the latest. Without that rule, or after Bob or anyone else pushes again, Alice's agent's commits can sit in Bob's pull request and Alice's approval counts, as it would after a push she made by hand. UG-4 closes this where a tenant runs it, and on a VCS pool with `pushIdentity: app` it is required.
- **App-identity pushes have no branch bound.** On a VCS pool with `pushIdentity: app` on GitHub, and on GitLab, where git stays on the project token until [S13](../0130-gitlab-credential-addon/change.md#validation-owed), an agent pushes as the App with the App's rights rather than its user's. It can push to another user's merge request branch, which the per-user branch namespace of earlier revisions prevented, and to any branch the App may push to, including protected branches where the App is a bypass actor or a Maintainer-role project token can push where its user cannot. Decision 47 asks how to bound this.
- **`delivery: file` tokens on these hosts.** Where every VCS pool covering a host sets `allowRuntimeHeldCredentials: true`, a session holding a binding with `delivery: file` for that host has a token that leaves every control here. A `registered` type can also lie about its hosts, which the pin addresses on the host the token works on.
- **Uncovered hosts.** Under git path T, a token the agent holds reaches an uncovered git host in an opaque tunnel, and a push is not refused, as [the egress design](../0127-egress-and-git/change.md) states.
- **A smuggled token** reaches an unpinned host through an opaque tunnel, until [EG-12](../0127-egress-and-git/change.md#steps) lands, on a VCS pool with `pinHosts: false`, or on a pool with `egressProfile: internet`.
- **PR content.** An agent's pull request body or comment can carry anything, including text aimed at a human reviewer or at a reviewer's agent.
- **Preset-only limits.** Against a Developer-level GitLab project token, `gitlab-deny` is all that stops approval and merge, and its route families are unmeasured beyond approve, unapprove, merge, rebase, `reset_approvals`, and `cancel_merge_when_pipeline_succeeds`. Against a GitHub child, nothing at the host distinguishes creating a pull request from approving one.
- **Service identities.** A person holding a listed client secret can start App-authored work and then approve it. Lenny cannot distinguish that person from the system. The audit trail shows the subject, and UG-4 cannot name a person who is absent from the session.
- **Comment-driven and other automation.** A comment, PR body, label, or other allowed event acts with Alice's standing on any bot that reads it. If a tenant adds no rule, or its `bodyPatterns` miss a grammar, or its bot acts on an event no rule gates, a single injected agent can approve or merge through such a bot wherever it trusts her. Request rules cannot close this, and only the tenant's rules and the bot's own check of `performed_via_github_app` bear on it.
- **CI on pushed branches.** An agent's branch runs the repository's existing workflows or pipelines with the secrets they get for a same-repository branch, and its build scripts are agent-written. This allows secret exfiltration and anything those secrets can do, including a workflow token permitted to approve. It exists wherever pods can push, under App tokens too.
- **Operator services on other hosts.** An operator service, such as an MCP server, on a host outside the provider's host set that holds its own credential to the same repositories is undetectable here. A runtime reaches it through egress, where the tenant's egress policy decides whether its host is allowed and `egress.tunnel` records the connection ([`0124-connector-removal`, "CR-3 External services"](../0124-connector-removal/change.md#cr-3-external-services)). The residual of §9.3 connectors on link hosts, which decision 3 stated, left with connectors.
- **A second account as approver.** Identity binding covers the linked account. A person with a second account in the organization can approve from it unless the organization's sign-on rules prevent that.
- **Provider and client behaviour.** The presets and checks depend on behaviour listed under "Validation owed". A new `gh` or `glab` release passes rather than breaks, which is the reverse of revision 3's failure mode.
- **Identifier-only linking under UG-4** proves an identity at one time. An account later transferred at the provider is not noticed.
