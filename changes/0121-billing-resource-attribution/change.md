## Problem

[§11.2.1](../../spec/11_policy-and-controls.md#1121-billing-event-stream) describes its billing event stream as suitable for invoice-grade billing, and an operator cannot price a tenant's usage from it today.

- No billing event carries pod time. §11.2.1 lists `pod_minutes` and does not say which event carries it, and the gateway sets it on no event it emits.
- A pod's cost depends on its CPU, memory, and storage, and no event states them. The operator also redefines a resource class at any time, so a class name alone does not state what a pod held.
- The code holds the class values. [§5.2](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes) names `small`, `medium`, and `large` and gives no quantities, the controller carries built-in quantities, and the `PodSet` CRD (the Kubernetes custom resource the controller creates a pool's pods from) refuses any other class name.
- A tenant's owned pool, which [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md) adds under [DR-5](../0147-tenant-derived-runtimes/change.md#dr-5-owned-pools) (owned pools), keeps pods that serve no session: warm pods, pods in the reserved hold between one tenant's sessions, and the capacity-reservation pods that DR-10 marks `spec.reserved`, and a shared pool keeps pinned idle pods that only one tenant can claim (§5.2 **Pinned idle inventory.**). Both appear only in a per-pool metric with no tenant.
- Stored bytes have a quota ([§11.2](../../spec/11_policy-and-controls.md#112-budgets-and-quotas)) and no billing event, and legal-hold escrow copies ([§12.8](../../spec/12_storage-architecture.md#128-compliance-interfaces) Phase 3.5) have neither. The `artifact_store` ledger, a Postgres table with one row per stored artifact, holds every size and lifetime the bill needs, and nothing compares it with the object store, which holds bytes the ledger does not count.

## Scope

This design covers resource classes as deployment configuration, the resource fields on session pod usage, a periodic `pool.idle_usage` event for owned pools and for pinned idle pods on shared pools, a periodic `storage.usage` event computed from the `artifact_store` ledger and from the legal-hold escrow records, a daily reconciliation of that ledger against the object store, and a per-tenant metric that estimates Postgres-held data.

The following are outside it:

- Prices, currencies, invoices, and rating. Lenny records quantities, and the operator's billing system prices them.
- Token metering, which §11.2 already covers.
- Activity evidence bytes, which [`0128-forensics-evidence-preservation`, "Volume and cost"](../0128-forensics-evidence-preservation/change.md#volume-and-cost) meters as `evidence.usage`.
- Extended resources such as GPUs in a class. A class here holds CPU, memory, and ephemeral storage.
- Node-level costs that no pod requests, such as DaemonSets, among them the named node agents `lenny-activity-collector` and `lenny-quota-agent` of [`0136-placement`, "PM-5"](../0136-placement/change.md#named-node-agents), the kubelet reserve, and idle node capacity on shared nodes. Dedicated nodes are the exception: BR-7 reports their capacity under the tenant they are dedicated to. A project quota that `lenny-quota-agent` sets on a slot volume ([PL-10](../0118-agent-pod-layout/change.md#pl-10-project-quotas)) changes no ephemeral-storage request, so it changes no bill.
- The size limits of the agent pod's volumes, which [PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction) owns, with the workspace default of [IC decision D3](../0131-incremental-checkpoint/change.md#decisions) and the spool size of [WM O9](../0153-workspace-materialization/change.md#open-decisions). The pod builder is the controller code in `pkg/controller/agentpod/podspec` that builds each agent pod's specification. This design reads the limits the builder applies: the memory-backed ones in the class check under "Checks at load", and the disk-backed ones in the ephemeral storage request under "Ephemeral storage".
- The checkpoint storage format, its reference closure, and its quota, which [IC-4](../0131-incremental-checkpoint/change.md#ic-4-catalog-reference-closure-and-quota) owns. This design bills the packs that format stores, including the platform chunk sets, under "Checkpoint packs and platform chunk sets".

Relationship to other designs:

- [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md) supplies `ownerTenantId` on the pool row ([DR-5](../0147-tenant-derived-runtimes/change.md#dr-5-owned-pools)), the `spec.reserved` mark ([DR-10](../0147-tenant-derived-runtimes/change.md#dr-10-capacity-reservation)), and the warm store storage request, `warmCloneBytes`, under DR-11, which [DR-9's "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores) carries. On an owned pool that request is the template's value plus the grant entry's `maxWarmCloneBytes`, and on a platform pool a `platform-admin` sets it on the pool row for the operator's entries. `pool.idle_usage` depends on DR-5, and [its "Not verified" bullet](../0147-tenant-derived-runtimes/change.md#not-verified) on idle billing now points here. Its DR-10 section ["Reporting"](../0147-tenant-derived-runtimes/change.md#reporting) attributes a tenant's reserved idle cost through `pool.idle_usage` and points here, because `lenny_warmpool_idle_pod_minutes` carries no tenant.
- [`0141-runtime-routing`](../0141-runtime-routing/change.md) removes the experiment fields from billing events and adds the session's routing labels ([RT-3](../0141-runtime-routing/change.md#rt-3-routing-labels)), and [`0140-runtime-revisions`](../0140-runtime-revisions/change.md) adds the session's runtime revision ([RV-2](../0140-runtime-revisions/change.md#rv-2-selection)). `session.pod_usage` carries both in its common envelope, and `pool.idle_usage` reports each revision's pod set separately ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)).
- [`0128-forensics-evidence-preservation` decision 16](../0128-forensics-evidence-preservation/change.md#decisions) makes the operator pay for quarantined pods and held bytes. `pool.idle_usage` leaves out quarantined pods, and `storage.usage` leaves out the security-hold copies that design writes under the `security-hold/` prefix of the escrow bucket. `storage.usage` bills the §12.8 legal-hold escrow copies under the `legal-hold-escrow/` prefix, which are a separate mechanism with separate records (decision 14).
- [`0127-egress-and-git`, "Git mirror (`lenny-git-mirror`)"](../0127-egress-and-git/change.md#git-mirror-lenny-git-mirror) places `lenny-git-mirror`, the shared git cache that serves git fetches from per-tenant stores, on persistent volumes in `lenny-system`, the platform's namespace, or in its own `lenny-mirror` namespace when the deployer places it there. Those volumes are outside the artifact ledger in either namespace.

## Terms

| Term | Meaning |
| :-- | :-- |
| Resource class | A named set of CPU and memory requests and limits, with optional ephemeral storage, that a pool names in its `resourceClass` field and that sets the resources of the pool's pods. Under this design the chart's `resourceClasses` map holds every class, and a class states the whole pod's resources (decision 7). See "Resource classes in configuration". |
| Effective value | A pod's total request or limit for one resource, computed as Kubernetes computes it for scheduling and quota. See "Effective values". |
| Usage interval | `billing.usageIntervalSeconds`, a Helm value, default 3600. Every periodic event divides time into windows of this length, aligned to UTC. |
| Periodic events | `session.pod_usage`, `pool.idle_usage`, and `storage.usage`, the billing events this design adds. Each reports one window for one subject. |
| Pod-binding window | An interval during which one session is bound to one pod, closed at the binding's release or at the next usage interval boundary. Each `session.pod_usage` event reports one. |
| Subject | What one periodic event reports on: a session on one pod, one revision's pod set of a pool and the tenant it is attributed to, or a tenant's store and artifact type. |
| `usage_window_key` | The idempotency key of a periodic event, a hash of its type, tenant, subject, window start, and resource values. See "Writing periodic events". |
| Emitter | The leader-elected gateway task that turns closed windows into billing events. It records progress only after it reads an event back from Postgres. See "Emitter progress". |
| Idle pod minutes | Pod minutes on pods that serve no session: pods warming, idle, in the reserved hold, or draining. `pool.idle_usage` reports them. |
| Accrual | The WarmPoolController's persisted running total of idle pod minutes per pool, runtime revision, tenant, window, and set of resource values, held in the `pool_usage_accrual` table. See "Accrual". |
| Slot and concurrent pod | A slot is one place for a session on an agent pod, served by its own slot container ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)). A pod whose pool sets `sessionPolicy.maxConcurrentSessionsPerPod` above 1 is a concurrent pod, and it serves that many sessions at once, one per slot. |
| Slot memory floor | `runtimes.minSlotMemoryBytes`, a Helm value, default 1Gi until validation on managed nodes replaces it: the smallest memory limit a slot container may have ([WM O1](../0153-workspace-materialization/change.md#open-decisions), settled 2026-11-12). Pool and class validation refuses a class whose per-slot memory falls below it. A `platform-admin` may lower it, which logs a warning, and a pool owner may not go below it. |
| Dedicated node capacity | The node minutes and allocatable CPU and memory of nodes labelled `lenny.dev/tenant=<tenantId>`, which carry one tenant's agent pods alone ([PM-2](../0136-placement/change.md#pm-2-node-tenancy)). BR-7 reports them as `node.dedicated_usage` (decision 17). |
| Platform tenant | The tenant ID `platform` that §10.2 reserves. A periodic event attributed to it bills no customer, so the operator sees the cost in the same stream. `owned_rollout` idle minutes (decision 16) and the platform-owned packs of "Checkpoint packs and platform chunk sets" are attributed to it. |
| Artifact ledger | The `artifact_store` table in Postgres, with one row per stored artifact recording its tenant, type, size, legal hold mark, and lifetime. `storage.usage` with `store: artifact` is computed from it. |
| Store | The `store` field of `storage.usage`: `artifact` for the artifact ledger, or `escrow` for the legal-hold escrow records. |
| Watermark | For `storage.usage`, the end of the last window whose event the emitter has read back from Postgres, kept per tenant, store, and artifact type. The tombstone sweep keeps a deleted ledger row until the watermark passes it. |
| Reconciliation | The daily gateway task that compares the artifact ledger with the object store, reports each difference as a metric, and lowers a bill that counted bytes the store does not hold. See "Daily reconciliation". |
| Snapshot time | The moment a reconciliation run's view of the object store reflects: the start of its listing, or the generation time of an inventory report. |
| Reserved ephemeral storage | A pod's effective ephemeral storage request, which the scheduler reserves on the node and which this design bills as pod disk (decision 10). It is unrelated to the reserved hold and to reserved pods, which "Terms from other designs and the platform" defines. |
| BR-n | This design's proposals, listed under "Proposals". |
| DF-n | The defects this document found in today's tree, listed under "Defects found while verifying". [`0147-tenant-derived-runtimes`](../0147-tenant-derived-runtimes/change.md#defects-found-while-verifying) numbers its own defects DF-n as well, and a DF-n in this document names a row of this document's table alone. |
| F-n.n.n | A finding filed in `BUILD-GAPS.md` at the repository root. Each DF-n names the F-id it is filed under. |
| Decision N | An owner decision listed under "Decisions" in this document, unless the sentence names another design. |
| Read | In "Current state" and "Defects found while verifying", evidence that comes from reading the code, with nothing run. |
| Test tier | A stage of the repository's test suite, from Tier 0, static checks, upward, which `.claude/rules/test-coverage.md` defines. "Tests" lists the tiers this design reaches. Kind, named in Tier 5, runs a Kubernetes cluster in containers on one machine. |

### Terms from other designs and the platform

This design builds on mechanisms other designs and the specification define. The table gives each one the meaning this document relies on.

| Term | Meaning |
| :-- | :-- |
| Gateway | Lenny's API gateway, which serves the external API, binds sessions to pods, and writes billing events. It runs as several replicas, and one replica at a time runs the leader-elected tasks. |
| Runtime | A record in Lenny's runtime registry that names an agent image or a base runtime, its isolation profile, and its allowed resource classes ([§5.1](../../spec/05_runtime-registry-and-pool-model.md#51-runtime)). A pool runs one runtime. A Kubernetes RuntimeClass is a different object. |
| Routing labels | The `routing` map on a session, which `PreRoute` interceptors write while the gateway chooses the session's runtime and which the session record then keeps unchanged ([`0141-runtime-routing`, "RT-3 Routing labels"](../0141-runtime-routing/change.md#rt-3-routing-labels)). A `PreRoute` interceptor is a hook the gateway calls before it selects a session's runtime, and the built-in runtime routes are one. Billing events carry the map in place of `experiment_id` and `variant_id`, which that design removes with the experimentation subsystem. |
| Runtime revision and pod set | A runtime revision is an immutable, numbered version of the runtime fields that define what runs in its pods. The gateway chooses a revision for each new session and records it as `runtimeRevision` ([`0140-runtime-revisions`, "RV-2 Selection"](../0140-runtime-revisions/change.md#rv-2-selection)). A pod set is the warm pods of one pool built from one revision, and during a rollout a pool keeps a pod set per active revision ([`0140-runtime-revisions`, "RV-3 Pods"](../0140-runtime-revisions/change.md#rv-3-pods)). A session keeps its revision for its life, apart from a resume after its revision is retired ([`0140-runtime-revisions`, "RV-6 Sessions over time"](../0140-runtime-revisions/change.md#rv-6-sessions-over-time)). |
| Pool and pool row | A set of pre-warmed agent pods for one runtime and one configuration. The gateway stores each pool as a row in Postgres, and the PoolScalingController renders the row into Kubernetes resources ([§5.2](../../spec/05_runtime-registry-and-pool-model.md#52-pool-configuration-and-execution-modes)). |
| Shared pool | A pool with no owning tenant, whose pods serve the sessions of every tenant it admits. |
| Owned pool and `ownerTenantId` | The pool that [DR-5](../0147-tenant-derived-runtimes/change.md#dr-5-owned-pools) creates for each tenant-derived runtime, which is a runtime a tenant admin derives from one the platform offers. An owned pool serves its owning tenant alone, and the pool row's `ownerTenantId` names that tenant. |
| WarmPoolController and PoolScalingController | Controllers in `lenny-controller`. The WarmPoolController creates a pool's pods, tracks their phase, and integrates idle pods into the metric `lenny_warmpool_idle_pod_minutes` ([§4.6.1](../../spec/04_system-components.md#461-warm-pool-controller-pod-lifecycle)). The PoolScalingController renders each pool row into the pool's `PodSet` resources and sets their warm counts. |
| `PodSet` and `AgentPod` | Kubernetes custom resources, defined by CustomResourceDefinitions (CRDs). A `PodSet` holds the pool settings the controller creates a pool's pods from, including the resource class, and the pool's warm targets. An `AgentPod` stands for one agent pod. |
| Pod phase | `AgentPod.status.phase`, the coarse occupancy of an agent pod: `warming`, `idle`, `reserved`, `claimed`, `draining`, `failed`, or `terminated` ([§6.2](../../spec/06_warm-pod-model.md#62-pod-state-machine)). An `idle` pod is warm and claimable. |
| Claim, bind, and release | A claim reserves a warm pod for a session, and bind attaches the session to that pod. Release ends the binding, at suspend, at a terminal state, at eviction, or when the session resumes on another pod. |
| Reserved hold | A recycling pod is one on a pool that sets `sessionPolicy.recycle.enabled: true`, so the pod is scrubbed and reused after a session instead of terminated. When the last session on a recycling pod ends, the gateway keeps the pod's claim in the `reserved` phase for the same tenant's next session, for up to `gateway.claimHoldTTLSeconds` ([§4.6.1](../../spec/04_system-components.md#461-warm-pool-controller-pod-lifecycle) **Reserved hold**). |
| Tenant pin and pinned idle pod | The tenant pin is the `lenny.dev/tenant-id` label that ties a pod to one tenant. A pinned idle pod is an agent pod in `idle` that carries a pin and has no claim, so only its pinned tenant can claim it (§5.2 **Pinned idle inventory.**). |
| Reserved pod (`spec.reserved`) | An `AgentPod` the WarmPoolController marks at creation as part of a tenant's capacity reservation on an owned pool, under [DR-10](../0147-tenant-derived-runtimes/change.md#dr-10-capacity-reservation). |
| Warm store and `warmCloneBytes` | A warm store is a git repository's objects that a pod fetches before any session, for an entry on its pool's warm list, under DR-11, in [DR-9, "Warm stores"](../0147-tenant-derived-runtimes/change.md#warm-stores). Every entry is a `gitRepository` entry of a runtime's `sharedAssets`: an operator's public entries on a Runtime, which reach platform pools and owned pools, and on an owned pool the `gitRepository` assets of the tenant-derived runtime, which a tenant admin writes, or a `platform-admin` through the same route, in which case the asset is `platform`-declared. The `PodSet` carries the pool's store bytes as `warmCloneBytes`, which is the `sizeLimit` of the pod's store volume `lenny-git-stores` and covers each store and its pristine tree ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)), so the pod's ephemeral storage request grows by that value. On a platform pool a `platform-admin` sets `warmCloneBytes` on the pool row. On an owned pool it is the template pool's value, which covers the base's entries, plus `maxWarmCloneBytes`, which covers the tenant's entries. The pool row copies `maxWarmCloneBytes` from the tenant's derivation grant, the per-tenant record a `platform-admin` writes to let the tenant derive runtimes ([`0147-tenant-derived-runtimes`, "Who turns it on"](../0147-tenant-derived-runtimes/change.md#who-turns-it-on)). |
| Agent pod containers | Every agent pod has the `adapter` container, Lenny's process that talks to the gateway; `netagent`, the egress and git endpoint, as a native sidecar; `keepalive`, a regular container that sleeps so that a quarantined pod keeps its volumes ([`0128-forensics-evidence-preservation`, decision 25](../0128-forensics-evidence-preservation/change.md#decisions)); one slot container `runtime-<n>` per slot, which runs the runtime under the supervisor at the slot's own UID ([PL-1](../0118-agent-pod-layout/change.md#pl-1-pod-blueprint)); and, on a pod with a warm list, the init container `lenny-store-fill`, which fills the warm repository stores before the pod reports ready ([`0127-egress-and-git`, decision 61](../0127-egress-and-git/change.md#decisions)). Lenny runs agent runtimes alone ([`0119-agent-runtimes-only`](../0119-agent-runtimes-only/change.md)), so every pod has this layout. |
| Spool volume and `spoolSizeLimitBytes` | `lenny-spool`, the pod-wide disk-backed volume that only the adapter mounts, which holds each slot's checkpoint spool, export clones, and upload staging. Its `sizeLimit` is the pool's `spoolSizeLimitBytes`, 16 GiB by default, whatever the slot count ([WM O9](../0153-workspace-materialization/change.md#open-decisions), settled 2026-11-13). |
| Pack, platform chunk set, and platform pack | A pack is an object in the object store that holds compressed checkpoint chunks. A session's packs belong to the session's tenant. A platform chunk set holds the chunks of content the platform placed on its pods from one source, a warm repository store or a runtime's shared assets, and its packs are platform packs. A session's snapshot or output file may reference platform packs of the sources it may read rather than upload those chunks again ([IC-4, "Platform chunk sets"](../0131-incremental-checkpoint/change.md#platform-chunk-sets), IC decision D1, settled 2026-11-13). A set of a source an operator declares is platform-owned, and a set of a tenant's own source is owned by that tenant. |
| Embedded stack | Embedded Mode, the local installation that `lenny up` starts on one machine, from manifests pre-rendered from the chart ([§17.4](../../spec/17_deployment-topology.md#174-local-development-mode-lenny-dev)). |
| Materialization helper | `lenny-materialize`, the program that writes a session's workspace sources into `/workspace` as the slot UID, run by the slot's supervisor ([`0153-workspace-materialization`](../0153-workspace-materialization/change.md)). |
| Isolation profile | A pool's sandboxing level for its pods: `standard`, `sandboxed`, or `microvm` ([§5.3](../../spec/05_runtime-registry-and-pool-model.md#53-isolation-profiles)). |
| RuntimeClass overhead | `overhead.podFixed` on a Kubernetes RuntimeClass: the resources a sandboxed container runtime, such as gVisor or Kata, adds to each pod. Admission copies it into the pod's `spec.overhead`, and the scheduler and quota add it to the pod's requests. |
| Native sidecar init container | A Kubernetes init container with `restartPolicy: Always`, which keeps running beside the regular containers for the pod's life. |
| tmpfs reservation | The memory a slot's memory-backed volumes can take: its `/dev/shm`, sized by the pool's `shmSizeLimitBytes` (default 64Mi) ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)). It counts against the slot container's memory limit, because the kernel charges a tmpfs page to the memory of the container whose process writes it, and the slot's runtime writes `/dev/shm`. The slot's run volume at `/run/lenny` is also memory-backed, but the adapter writes it (the manifest and the credential file, a few KiB), so its pages count against the adapter container's memory under `adapterResources` and are outside the reservation. `/workspace`, `/session`, and `/tmp` are disk-backed and count against ephemeral storage instead. |
| Billing event stream | The per-tenant, append-only billing events of [§11.2.1](../../spec/11_policy-and-controls.md#1121-billing-event-stream), which the gateway writes through the `EventStore` to the `billing_events` table. Each event carries a per-tenant `sequence_number` drawn from a Postgres sequence, so a consumer that finds a gap asks for a replay. |
| Billing fallbacks | When the Postgres write fails, the gateway writes a billing event to a per-tenant Redis stream, and when Redis also fails, to a bounded in-memory write-ahead buffer on the replica. A flusher later inserts both into Postgres. A replica crash loses its in-memory buffer. §11.2.1 calls these fallbacks Tier 1 and Tier 2, which are unrelated to test tiers. |
| `billing_correction` | A billing event that replaces the quantity fields of an earlier event, which it names by sequence number. Corrections apply in sequence order, and the latest takes precedence. A Category 1 correction is one the gateway emits automatically during routine operational reconciliation, such as crash recovery. An operator-initiated correction above `billing.dualControlThreshold` needs a second `platform-admin`'s approval, which is dual control. |
| Null/absent contract | The §11.2.1 rule that a field defined for some event types is omitted from every other event type's payload, neither present nor null, and that a consumer reads an absent field as not applicable rather than zero. |
| Billing sinks | The deployer-configured destinations, such as a webhook or a message queue, to which the gateway publishes billing events after the Postgres write (§11.2.1 **Delivery sinks**). |
| `BillingCorrectionRateHigh` | An existing alert that fires when `billing_correction` events exceed a configured share, default 5%, of all billing events in a rolling 24-hour window ([§16.5](../../spec/16_observability.md#165-alerting-rules-and-slos)). |
| `usagestore` | The store that the `GET /v1/usage` report reads. It is separate from the billing event stream, and a usage figure reaches it only through an explicit `usagestore.Record` call. |

## High-level design

Lenny records what each tenant uses so that an operator's billing system can price it, and today those records leave out most of what costs money: the time a session holds a pod, how large that pod is, warm pods kept for one tenant, and stored bytes. This design adds those quantities to Lenny's billing events. Each session reports, per pod and per hour by default, how long it held the pod and the CPU, memory, and disk the pod reserved. Warm pods that wait for one tenant are reported under that tenant, and stored data such as workspaces and checkpoints is reported as bytes held over time. A daily check compares Lenny's storage records with the object store and lowers a bill that counted bytes the store no longer holds.

Lenny records quantities, and the operator's billing system prices them. Some costs reach no tenant: warm pods on shared pools that wait for no particular tenant, node capacity no pod requests, and data held in Postgres. A pod is billed the disk it reserves whether it uses it or not, and the storage figures come from Lenny's own records, which differ from the provider's bill in ways the daily check reports and does not correct.

The rest of this section states each part in the design's terms, which "Terms" above defines.

**Resource classes in configuration (BR-1).** The chart's `resourceClasses` map holds every class, and the binaries hold none. The chart renders the map into the `lenny-resource-classes` ConfigMap, which the controller and the gateway read at startup and refuse to start without. The gateway refuses a pool or runtime write that names an undefined class, and the controller creates no pod for one. A class states the whole pod's resources.

**Session pod time (BR-2).** `session.pod_usage` reports one pod-binding window per event, cut at each release and at each usage interval boundary, with the pod's effective CPU, memory, and ephemeral storage requests and limits. The gateway records each window in `session_pod_windows` at bind and release, and the emitter turns closed windows into events. On a concurrent pod, a session's share of the pod is per slot.

**Idle pods (BR-3).** The WarmPoolController accrues the minutes of pods that serve no session in `pool_usage_accrual`, and the emitter reports them as `pool.idle_usage`. An owned pool's idle pods are attributed to its owning tenant with `pool_ownership: owned`, apart from the extra pod set a base rollout keeps on that pool, whose idle pods are attributed to the platform with `pool_ownership: owned_rollout`, and a shared pool's pinned idle pods to the pinned tenant with `pool_ownership: shared_pinned`. The unpinned idle pods of shared pools reach no tenant.

**Stored bytes (BR-4 and BR-6).** `storage.usage` reports bytes held and byte-hours per tenant, store, and artifact type: from the artifact ledger with `store: artifact`, and from the legal-hold escrow records with `store: escrow`, which continues after the tenant's deletion until the hold ends. The watermark keeps the tombstone sweep from deleting a ledger row before its last hours are billed.

**Reconciliation (BR-5).** A daily task compares the artifact ledger with the object store and reports each kind of difference as a metric. It emits a `billing_correction` only to lower a bill for bytes the store does not hold, after two consecutive runs confirm the difference. The same task sets a per-tenant estimate of Postgres-held data as a gauge, with no billing event.

**Dedicated nodes (BR-7).** A tenant whose pods run on nodes dedicated to it is reported the capacity of those nodes, whether or not its pods fill them, as a periodic `node.dedicated_usage` event (decision 17).

**Checkpoint storage and platform chunk sets.** Checkpoints and output files are stored as packs, and each pack is billed once, from its ledger row, to the tenant that owns it. A snapshot that references chunks of a platform chunk set adds nothing to its tenant's bill. The operator pays for the platform-owned sets, which are reported under the platform tenant, and a tenant pays for its own sets.

**Writing the events (BR-2).** Every periodic event carries `usage_window_key`, and both insert paths into the billing table, `Append` for the direct write and `InsertFromStream` for the flush from the Redis stream, absorb a duplicate key without drawing a sequence number, so a window retried after a failover is billed once. The emitter records progress only after it reads an event back from Postgres, so a crash delays an event and loses none.

```
 Chart resourceClasses ──> ConfigMap lenny-resource-classes ──> controller (creates pods), gateway (checks writes)

 Gateway bind and release ──> session_pod_windows ──┐
 WarmPoolController ────────> pool_usage_accrual ───┤
 WarmPoolController ────────> dedicated_node_accrual┤
 artifact_store ledger (incl. packs) ───────────────┼──> gateway emitter (leader) ──> billing_events ──> operator's billing system
 legal_hold_escrow_records ─────────────────────────┘

 Daily reconciliation: artifact_store ledger <──compare──> object store ──> metrics, alerts, billing_correction (lowers only)
```

## Design

### Resource classes in configuration

**Source.** The binaries hold no class. The chart's `values.yaml` ships a top-level `resourceClasses` map and a `defaultResourceClass`, with the values the code holds today:

```yaml
resourceClasses:
  small:
    requests: { cpu: 250m, memory: 1Gi, ephemeral-storage: 1Gi }
    limits:   { cpu: "1",  memory: 1Gi }
  medium:
    requests: { cpu: 500m, memory: 2Gi, ephemeral-storage: 1Gi }
    limits:   { cpu: "2",  memory: 2Gi }
  large:
    requests: { cpu: "1",  memory: 4Gi, ephemeral-storage: 1Gi }
    limits:   { cpu: "4",  memory: 4Gi }
defaultResourceClass: medium
```

An operator changes a class's values, adds a class, or removes one. Helm merges maps, so an operator removes a shipped class by setting it to `null`. The chart renders the map into one ConfigMap, `lenny-resource-classes`, which the controller and the gateway mount and read at startup (decision 8). The gateway and controller Deployments carry a `checksum/resource-classes` pod annotation computed from the rendered ConfigMap, so a `helm upgrade` that changes a class rolls both. The `--resource-class` flag and `controller.resourceClasses` go, and no deployment exists that needs them.

**Fields.** A class holds `requests.cpu`, `requests.memory`, `limits.cpu`, and `limits.memory`, all required, and optional `requests.ephemeral-storage` and `limits.ephemeral-storage`. The class's ephemeral storage request covers what no volume's size limit counts, the containers' writable layers and logs, and the pod builder adds it on top of the sum of the disk-backed volumes' size limits that the checkpoint design's decision D3 sets (decision 18). The shipped classes state 1 GiB, and an operator sets it per class. A class that omits it reserves nothing for the writable layers and logs. The shipped classes leave `limits.ephemeral-storage` unset. A class's name is a DNS label of at most 63 characters, because it appears as a metric label value and in billing events.

**Checks at load.** The controller and the gateway each refuse to start, with `CONFIG_INVALID` naming the class and the field, when the file is absent, the map is empty, a required field is missing, a request exceeds its limit, `defaultResourceClass` names no class, a class's CPU or memory is below the sum of the `lenny-store-fill` and `netagent` requests, or a class leaves a single slot less memory than the slot memory floor plus the tmpfs reservation. The share is computed as decision 7 maps the class, with one slot. The controller computes the reservation from the size limit the pod builder applies to the slot's `/dev/shm`.

**Checks at pool write.** A pool's slot count divides the class's remaining memory among its slots, so the gateway refuses a pool write whose class leaves any slot below the slot memory floor plus the tmpfs reservation at the pool's `maxConcurrentSessionsPerPod`, with `400 VALIDATION_ERROR` naming the class, the slot count, the per-slot memory, and the floor. The same check runs on a tenant-derived runtime's owned pool. A `platform-admin` may lower `runtimes.minSlotMemoryBytes`, which the gateway and the controller log as a warning at start, and a pool owner cannot set a pool below it ([WM O1](../0153-workspace-materialization/change.md#open-decisions)).

**Checks at write.** The gateway refuses a write that names an undefined class with `400 VALIDATION_ERROR`, naming the field and listing the defined classes. This covers a pool's `resourceClass` on `POST` and `PUT /v1/admin/pools` and on bootstrap, a runtime's `allowedResourceClasses` and `defaultPoolConfig.resourceClass`, and the equivalent fields on a tenant-derived runtime and its owned pool. The `PodSet` CRD loses its enum, because the API server cannot read deployment configuration, and §4.6.1's **CRD validation:** sentence changes to name the gateway check.

**Checks at reconcile.** A `PodSet` can name a class that a later configuration change removed. The controller creates no pod for it, sets the pool condition `ResourceClassUndefined` with the class name (§5.2 places pool conditions such as `PoolWarmingUp` on the pool's `PodSet`), and increments `lenny_resource_class_undefined_total{pool}`, and the alert `ResourceClassUndefined` fires. Running pods keep their resources. The fallback to unconstrained containers goes.

**Container mapping.** Decision 7 settles how a class maps to containers, and [SI-9](../0145-session-isolation/change.md#si-9-cpu-and-memory) states the mapping onto slot containers. A class states the pod's total, including `netagent`:

- the pod's `spec.resources` takes the class's CPU limit, so CPU bursts across slots;
- the `adapter` container takes `adapterResources`, a chart value;
- `netagent` takes its own request from the chart value `netagent.resources`, by default a request of 100m CPU and 128 MiB with a 512 MiB memory limit and no CPU limit ([`0127-egress-and-git`, decision 66](../0127-egress-and-git/change.md#decisions), settled 2026-11-13). It runs as a native sidecar, so its request adds to the pod's effective request ([`0127-egress-and-git`](../0127-egress-and-git/change.md)), and the mapping subtracts it from the class so that the pod's effective request stays the class;
- `keepalive` takes its own minimal chart request, which the mapping subtracts from the class as it subtracts `netagent`'s;
- each slot container `runtime-<n>` takes a CPU request of the remaining CPU divided by the slot count, with no CPU limit, and a memory request and limit of the remaining memory divided by the slot count;
- `lenny-store-fill` takes its own request from the chart value `storeFill.resources`. It is a regular init container that runs before the regular containers start, so under "Effective values" its request, added to `netagent`'s, counts only when that sum exceeds the regular containers' sum. The check at load refuses a class whose CPU or memory is below that sum, so the pod's effective request stays the class.

The tmpfs check runs against each slot container's memory limit. A slot's `/dev/shm` counts against its own memory, and its run volume counts against the adapter's, because the adapter writes it. The adapter carries no per-slot session-file budget, because `/session` is disk-backed ([PL-3](../0118-agent-pod-layout/change.md#pl-3-runtime-visible-filesystem-layout)).

**Materialization and restore.** The materialization helper runs in the slot container as the slot UID, so the CPU and memory of a materialization, including archive extraction and git checkout, are charged to the slot container's cgroup and come out of the slot's share of the class. The gateway no longer extracts archives, so it spends no CPU or memory on a session's workspace. A restore writes through broker descriptors from the adapter, so its page cache stays charged to the adapter ([WM-14](../0153-workspace-materialization/change.md#wm-14-memory-sizing)). Neither changes the billed quantities, which are the pod's reserved resources.

**Changing a class.** A change applies to pods created after the controller restarts with the new file. A pod keeps the resources it was created with until it ends, which is why every usage event records the pod's actual resources.

**Listing.** `GET /v1/admin/resource-classes` returns the loaded table to `platform-admin` and `tenant-admin`, so a tenant writing a derived runtime can see the names it may use.

**Embedded stack.** `lenny up` applies manifests rendered from the chart under `presets/dev.yaml`, so the embedded stack receives the same ConfigMap and the same defaults through that render, and `TestEmbeddedManifestsMatchDevProfileRender` holds the copy to the chart. The embedded catalog and agent placement name `small`, and a test checks that every class name in `pkg/embedded/stack` is defined in the rendered ConfigMap.

### Resource fields on usage events

**Carrier.** A new event type, `session.pod_usage`, carries a session's pod time, one event per pod-binding window (decision 6). A window opens when the session binds a pod and closes at the first of the release of that binding (suspend, terminal state, eviction, or a resume onto another pod) or the next boundary of `billing.usageIntervalSeconds`, default 3600 and minimum 300, aligned to UTC. A session that moves between pods produces separate windows for each pod. `session.completed` carries no `pod_minutes`.

**Fields.** `session.pod_usage` carries the common envelope (`tenant_id`, `user_id`, `session_id`, `environment_id`, `routing`, `runtime_revision`, and `labels`). `environment_id` is the existing §11.2.1 attribution field for the session's environment, and `labels` holds the client's session labels. `routing` holds the session's routing labels ([RT-3](../0141-runtime-routing/change.md#rt-3-routing-labels)), in place of the `experiment_id` and `variant_id` fields that [`0141-runtime-routing`](../0141-runtime-routing/change.md) removes. `runtime_revision` is the revision the session ran on the window's pod ([RV-2](../0140-runtime-revisions/change.md#rv-2-selection)). A session changes revision only when it resumes after its revision is retired ([RV-6](../0140-runtime-revisions/change.md#rv-6-sessions-over-time)), and that resume binds another pod and so opens a new window. The event also carries these fields:

| Field | Type | Meaning |
| :-- | :-- | :-- |
| `pod_minutes` | float64 | The session's bound time on the pod within the window |
| `window_start`, `window_end` | RFC 3339 | The window's bounds |
| `window_reason` | string | `interval` or `release` |
| `pod_uid` | string | The pod's Kubernetes UID (unique identifier), so a consumer can group a shared pod's windows |
| `pool_name` | string | The pool the pod belongs to |
| `runtime_name` | string | The runtime the session runs |
| `resource_class` | string | The class the pod was created with |
| `isolation_profile` | string | `standard`, `sandboxed`, or `microvm` |
| `cpu_request_millicores`, `cpu_limit_millicores` | uint64 | The pod's effective CPU request and limit |
| `memory_request_bytes`, `memory_limit_bytes` | uint64 | The pod's effective memory request and limit |
| `ephemeral_storage_request_bytes` | uint64 | The pod's effective ephemeral storage request, which includes the pool's `warmCloneBytes` on a platform pool or an owned pool |
| `ephemeral_storage_limit_bytes` | uint64 | Absent when no container sets one |
| `max_concurrent_sessions_per_pod` | uint32 | The pod's slot capacity: the pool's `sessionPolicy.maxConcurrentSessionsPerPod` when the pod was created, recorded on the pod so that a later pool change does not alter it |
| `usage_window_key` | string | The idempotency key described under "Writing periodic events" |

**Effective values.** The gateway reads the pod object at bind and computes each effective value with the formula Kubernetes uses for scheduling and quota (`PodRequests` and `PodLimits` in `k8s.io/component-helpers/resource`). It sums the values of the regular containers and of the native sidecar init containers. For each regular init container, it adds that container's value to the values of the native sidecar init containers declared before it. The effective value is the larger of the first sum and the largest of the init container figures, plus `spec.overhead` from the RuntimeClass. A CPU or memory value that the pod sets in `spec.resources` replaces the container figure before the overhead is added, and the overhead is added to a limit only when that limit is non-zero. It stores the values on the binding, so the release path does not read the pod again. The values are what the pod holds, whatever decision 7 settles about how a class maps to containers.

**Concurrent pods.** On a concurrent pod, one with `maxConcurrentSessionsPerPod` above 1, each session's window reports its own bound time and the pod's full resources. The apportioning rule is per slot: a session's share is its `pod_minutes` times the pod's resources divided by `max_concurrent_sessions_per_pod`, so the shares of the sessions on one pod never sum above the pod's cost. On an owned pool, the emitter computes the empty slots of each pod that serves at least one session from the pod's `session_pod_windows` rows and reports them in `pool.idle_usage` as `idle_slot_pod_minutes`. On a shared pool, empty slots stay with the operator.

**Ephemeral storage.** The bill uses the reserved ephemeral storage, which is the pod's effective request and which the scheduler reserves on the node (decision 10). The events record no measured disk use, so no component reads kubelet statistics for billing and the design adds no `nodes/stats` or `nodes/proxy` grant. The pod builder renders each disk-backed volume's `sizeLimit` and an ephemeral storage request equal to their sum ([IC decision D3](../0131-incremental-checkpoint/change.md#decisions), settled 2026-11-13; [PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction), **Ephemeral storage.**). PL-5 places that request on the adapter container. The class's own ephemeral storage request, 1 GiB in the shipped classes, adds to that sum once per pod, whatever the slot count, on the same container (decision 18):

| Volume | Per | `sizeLimit` | Default |
| :-- | :-- | :-- | :-- |
| `slot-<n>-workspace` | Slot | `workspaceSizeLimitBytes` | 10 GiB (IC decision D3) |
| `slot-<n>-session` | Slot | `sessionSizeLimitBytes` | 1 GiB (PL decision D27) |
| `slot-<n>-tmp` | Slot | `tmpSizeLimitBytes` | 1 GiB |
| `lenny-spool` | Pod | `spoolSizeLimitBytes` | 16 GiB, whatever the slot count (WM O9) |
| `lenny-git-stores` | Pod, on a pool with a warm list | `warmCloneBytes` | The pool's value |
| `lenny-assets` | Pod | The total size of the pod set's `artifact` and `inline` shared assets, the revision's `assetsBytes` plus a derived runtime's appended assets, plus 64 MiB ([PL-5](../0118-agent-pod-layout/change.md#pl-5-volumes-size-limits-and-eviction)) | The pod set's assets total plus 64 MiB |
| The class's own request | Pod | The class's `requests.ephemeral-storage` (decision 18) | 1 GiB in the shipped classes |

At the defaults, a pod with one slot requests 29 GiB of ephemeral storage plus `warmCloneBytes` and the `lenny-assets` limit, and a pod with four slots requests 65 GiB plus the same two values, because each slot adds 12 GiB and the spool and the class's 1 GiB are counted once per pod. The request sits on the adapter container (PL-5), and the container that carries it does not change the pod's effective value. A volume with no `sizeLimit`, such as the read-only `lenny-bin` volume of PL-5, adds nothing to the request or to the bill. Memory-backed volumes count against memory and are absent from this figure. Decision 10 bills the whole effective request, so the store request follows the pod's other resources. On a platform pool, which is a shared pool, a session window carries the store request of the operator's entries, a pinned idle pod reports it under `shared_pinned`, and an unpinned idle pod's request reaches no tenant. On an owned pool the owning tenant is billed for the whole request, the part that covers the base's entries and the base's assets included. The owner settled that the owning tenant pays for this part too (decision 15).

**Durability.** The gateway writes each open window to a `session_pod_windows` row (`tenant_id`, `session_id`, `pod_uid`, `opened_at`, the resource fields, `closed_at`, and `emitted_at`) in the transaction that records the binding, and sets `closed_at` in the transaction that records the release. A leader-elected task under `lenny-gateway-leader` emits each window whose interval has passed or whose `closed_at` is set. When no release recorded a close, the task closes the window at the earliest of the session's terminal or suspend transition, the same session's next binding, the time the pod was quarantined, and the pod's deletion time. A window therefore never covers quarantine, which the operator pays for under [forensics decision 16](../0128-forensics-evidence-preservation/change.md#decisions) and which that design keeps out of `pod_minutes` by stopping it at the terminal transition. A resumed session's window on its old pod also ends before its window on the new pod opens.

**Emitter progress.** The emitter sets `emitted_at` only after it reads the window's `usage_window_key` back from `billing_events` in Postgres. An `Append` that returns after the event landed in the Redis stream or the in-memory buffer leaves the window pending, because a replica crash loses the in-memory buffer, and the next cycle appends the event again under the idempotent insert in "Writing periodic events". Each emitter persists its progress per subject: `emitted_at` on each `session_pod_windows` row, an emitted mark on each `pool_usage_accrual` row, and, for `storage.usage`, a watermark per tenant, `store`, and `artifact_type`. A gateway crash therefore delays an event and loses none.

**Erasure and teardown.** §12.8 step 5 closes and emits every pending window of the erased user's sessions, so step 15 pseudonymizes those events with the user's other billing events. An emitter that writes a window for a user whose erasure has started writes the §12.8 pseudonym in place of `user_id`, which covers a window that closes after step 5. The `DeleteByUser` sequence deletes the user's `session_pod_windows` rows after emission. Tenant deletion Phase 4 deletes the tenant's `session_pod_windows`, `pool_usage_accrual`, and `dedicated_node_accrual` rows and its `storage.usage` watermarks for `store: artifact`. The emitters write events for a tenant whose `TenantState` is `disabling` as usual and write no event once `TenantState` is `deleting`, because Phase 4 deletes the tenant's billing events. The `store: escrow` emitter is the exception, and "Legal-hold escrow copies" states when it writes.

**`GET /v1/usage`.** The handler reads `usagestore`, so the emitter also calls `usagestore.Record` after each committed `session.pod_usage`, `pool.idle_usage`, and `storage.usage`, keyed by `usage_window_key` so that a retried window records once. `totalPodMinutes` and a new `podMinutes` on each `byTenant` and `byRuntime` entry sum the recorded `session.pod_usage` minutes. The report gains `idlePodMinutes` from `pool.idle_usage` and `storageByteHours` from `storage.usage` across both stores. `GET /v1/sessions/{id}/usage` and `GET /v1/admin/environments/{name}/usage` sum `pod_minutes` from the `billing_events` table, so they include `session.pod_usage` with no change to either handler.

### `pool.idle_usage`

**What it counts.** The event reports pod minutes that serve no session, per window of `billing.usageIntervalSeconds`. Its `pool_ownership` field names the subject:

- `owned`: the pods of an owned pool, attributed to the pool's `ownerTenantId` (decision 2), apart from those `owned_rollout` names.
- `owned_rollout`: the pods of a base rollout's extra pod set on an owned pool, attributed to the platform tenant, the tenant ID `platform` that §10.2 reserves, so no tenant is billed for them (decision 16). The extra pod set is the one that [`0140-runtime-revisions`, "RV-3 Pods"](../0140-runtime-revisions/change.md#rv-3-pods) defines under **Owned pools during a base rollout (D8).**: while the platform rollout is in progress, the pods of every pod set other than the one for the revision with the highest weight, the older revision on a tie. The event carries the same fields and counts as an `owned` event and names the owned pool and the pod set's revision, so the operator sees what a rollout costs on each owned pool. When the rollout ends, the remaining pod set reports as `owned` again.
- `shared_pinned`: the pinned idle pods of a shared pool (§5.2 **Pinned idle inventory.**), attributed to the tenant in each pod's `lenny.dev/tenant-id` label (decision 11). A shared pool produces one event per pinned tenant, and the event carries `idle_pod_minutes`, `unsampled_minutes`, and `pod_count_max` and none of the other counts. The unpinned pods of a shared pool reach no tenant, and the operator bears them.

`tenant_id` is the tenant the subject is attributed to, and `user_id` and `session_id` are absent. The event's fields are `pool_name`, `runtime_name`, `runtime_revision`, `pool_ownership`, `window_start`, `window_end`, `usage_window_key`, the resource fields of `session.pod_usage` without the session ones, and these counts:

| Field | Pods counted |
| :-- | :-- |
| `warming_pod_minutes` | Pods created and not yet in the `idle` phase |
| `idle_pod_minutes` | With `pool_ownership: owned` or `owned_rollout`, pods in the `idle` phase, claimable and pinned. With `pool_ownership: shared_pinned`, the tenant's pinned idle pods |
| `hold_pod_minutes` | Pods whose claim is in the `reserved` hold between sessions (§4.6.1 **Reserved hold**) |
| `draining_pod_minutes` | Pods draining with no session |
| `reserved_pod_minutes` | The part of the preceding counts on pods marked `spec.reserved` under [DR-10](../0147-tenant-derived-runtimes/change.md#dr-10-capacity-reservation) |
| `idle_slot_pod_minutes` | The empty slots of concurrent pods that serve at least one session, in pod minutes, under "Concurrent pods" |
| `unsampled_minutes` | Minutes of the window that no sample covered within `billing.idleAccrualMaxGapSeconds` (the gap cap, default 600, under "Accrual"), which bill nothing |
| `pod_count_max` | The largest number of such pods at one sample |

A pod that holds a session is billed through `session.pod_usage` and is absent here. A pod in the `failed` phase and a quarantined pod are absent, because the platform and the operator bear those (forensics decision 16). A pool whose pods carry different resources in one window, after a class change, produces one event per distinct set of resource values. A pool that keeps several pod sets during a rollout ([RV-3](../0140-runtime-revisions/change.md#rv-3-pods)) produces one event per pod set, and `runtime_revision` names the revision the pod set was built from, so an operator can tell a rollout's extra pods apart from the pool's usual ones. On an owned pool, the extra pod set's event also carries `pool_ownership: owned_rollout`.

**Accrual.** The WarmPoolController already integrates idle pods on each reconcile. It gains a durable accrual in a `pool_usage_accrual` table, keyed by pool, runtime revision, tenant, window start, and a hash of the resource values, holding `tenant_id`, `pool_ownership`, minutes per state, `unsampled_minutes`, and the last sample's time and counts. When the controller creates an accrual row, it takes the tenant from the pool row's owner on an owned pool, the platform tenant for a base rollout's extra pod set on an owned pool, and the tenant from the pod's pin label on a shared pool, so the last window of a deleted pool or a drained pinned pod still has a tenant. The controller decides at each sample which pod set of an owned pool is the extra one, from the runtime's traffic at that sample. A weight change during a window therefore moves the following minutes to the other subject, in a separate accrual row, because the key includes the tenant. Each reconcile adds the minutes since the last persisted sample, using the counts at that sample, so a restart or leader change continues the integral from the persisted sample. The following rules hold the integral under failure:

- Each write is an update conditional on the `last_sample_at` the controller read. During a leader overlap, the second writer matches no row, rereads, and adds nothing for the interval the first writer counted.
- An interval that crosses a window boundary is split at the boundary, and each part accrues to its own window.
- An interval longer than `billing.idleAccrualMaxGapSeconds`, default 600, accrues its first `billing.idleAccrualMaxGapSeconds` at the earlier counts, and the rest goes to `unsampled_minutes`, so counts that went stale during an outage do not bill the outage.
- A window is ready for emission only after a sample at or after its end, or after the pool's deletion, which the controller records as a final sample.

The controller already holds a Postgres connection for the `agent_pod_state` mirror. The gateway's leader-elected task converts each closed window into one `pool.idle_usage` event (decision 9). `lenny_warmpool_idle_pod_minutes` stays as it is.

**Ownership.** Until [DR-5](../0147-tenant-derived-runtimes/change.md#dr-5-owned-pools) lands, no pool has an owner, and every `pool.idle_usage` event carries `pool_ownership: shared_pinned`.

### `storage.usage`

**What it counts.** For each tenant, `store`, and `artifact_type` with a live row in the window or a row deleted in it, the event reports, per window of `billing.usageIntervalSeconds`:

| Field | Type | Meaning |
| :-- | :-- | :-- |
| `store` | string | `artifact` for the `artifact_store` ledger, and `escrow` for the legal-hold escrow records (decision 14) |
| `artifact_type` | string | The ledger's `artifact_type` value, or the escrow record's `resource_type` on `store: escrow` |
| `bytes_held_start`, `bytes_held_end` | uint64 | Sum of the row sizes over rows live at each bound |
| `byte_hours` | float64 | Sum over rows of the row's size times the hours of the row's life inside the window |
| `legal_hold_byte_hours` | float64 | The part of `byte_hours` on rows with `legal_hold` set, absent on `store: escrow` |
| `bytes_written`, `bytes_deleted` | uint64 | Sizes of rows created, and of rows soft-deleted or released, in the window |
| `object_count_end` | uint64 | Live rows at the window's end |
| `window_start`, `window_end`, `usage_window_key` | | As for the other periodic events |

On `store: artifact`, a row's size is `artifact_size_bytes`, and its life runs from `created_at` to `soft_deleted_at`, or to the window's end when it is live. Checkpoint reservations without an `artifact_store` row are quota reservations and are absent. A checkpoint reservation is the storage quota the gateway charges for a checkpoint before its bytes land and its row exists (§11.2 **Storage quota enforcement mechanism.**). `user_id` and `session_id` are absent.

**Checkpoint packs and platform chunk sets.** Checkpoints and output files are stored as packs, and [IC-4, "Quota"](../0131-incremental-checkpoint/change.md#quota) charges each pack once, at confirmation, to the tenant that owns it. The bill follows the same rule, so each pack is billed once, from its one ledger row, whoever references it **[design]**:

| Pack | Ledger row's tenant | `artifact_type` | Who pays |
| :-- | :-- | :-- | :-- |
| A session's pack, whether a snapshot or an output file references it | The session's tenant | `checkpoint` | The tenant |
| A pack of a tenant-owned platform chunk set, from the staged trees of a tenant-derived runtime's `gitRepository` assets, a `platform`-declared asset's included, or from its `inline` and `artifact` assets, an uploaded `artifact` asset's packs included | The owning tenant | `platform_chunks` | The tenant, once per pack |
| A pack of a platform-owned platform chunk set, from an operator's public `gitRepository` entries on a Runtime's `sharedAssets`, or the shared assets of a platform runtime, including a platform-derived runtime's `sharedAssets` append ([RV D25](../0140-runtime-revisions/change.md#decisions)) | The platform tenant | `platform_chunks` | The operator, and no customer |

A tenant's uploaded `artifact` asset has no ledger row of its own. The upload route chunks it into the packs of the runtime's tenant-owned assets set, and those packs are its only stored copy, so the tenant pays for it once, through those packs, while any reference holds them ([`0147-tenant-derived-runtimes`, "Tenant shared assets"](../0147-tenant-derived-runtimes/change.md#tenant-shared-assets)). An `inline` asset's content lives in the derived runtime's row and is not billed apart from that row, and its file reaches the bill only through the packs of the pods' contributions. A `gitRepository` asset that a `platform-admin` writes on the runtime is `platform`-declared, and its staged trees still feed the runtime's tenant-owned set, because its store serves the owner alone and holds a repository private to the tenant, which the owner confirmed on 2026-11-14 ([`0147-tenant-derived-runtimes` decision 43](../0147-tenant-derived-runtimes/change.md#decisions)).

A tenant-derived runtime's sessions match the platform-owned set of its base's assets and, when the runtime carries `inline` or `artifact` assets of its own, the tenant-owned set of those assets, which [`0131-incremental-checkpoint`, "Platform chunk sets"](../0131-incremental-checkpoint/change.md#platform-chunk-sets) keys on the runtime's owned pod set.

A snapshot's or an output file's reference to a platform pack adds nothing to its tenant's `storage.usage`, as it adds nothing to the tenant's quota. A derived session's references to its source's packs add nothing either, because derive references packs rather than copying them (IC decision D2). A pack stays billed to its owner until pack reclamation deletes it ([IC-6](../0131-incremental-checkpoint/change.md#ic-6-retention-garbage-collection-erasure-and-legal-hold)), so a platform pack that a retired source leaves behind stays on its owner's bill while snapshots reference it, and a tenant that turns `storage.platformChunkReuse` off keeps paying for its own set's packs until no snapshot references them ([`0150-tenant-security-settings`, "TSS-7"](../0150-tenant-security-settings/change.md#tss-7-changing-a-setting-on-a-live-tenant)). The operator prices or ignores the platform tenant's `platform_chunks` figure as it chooses. `DeleteByTenant` deletes a tenant-owned set's packs with the tenant's other objects, so their ledger rows leave with them.

**Rows the sweep would remove.** The tombstone sweep deletes a row 24 hours after its deletion by default, and a stalled emitter would then lose a deleted row's last hours. The sweep therefore also requires `soft_deleted_at` to precede the watermark for the row's tenant and `artifact_type`, which is the end of the last window whose `storage.usage` event the emitter has read back from `billing_events` in Postgres. The emitter advances the watermark only after that read, so an event held in the Redis stream or the in-memory buffer does not release a tombstone. A stalled emitter keeps tombstones, and `StorageUsageEmitterStalled` fires when the watermark is older than 2 windows.

**Legal-hold escrow copies.** §12.8 Phase 3.5 copies a force-deleted tenant's held resources to `legal-hold-escrow/{original_tenant_id}/{resourceType}/{resourceId}` in the region's escrow bucket and writes a `legal_hold_escrow_records` row for each copy. `storage.usage` bills those copies to the original tenant as `store: escrow`, whoever set the hold (decision 14). The record gains `escrow_object_bytes`, which the migrator writes with the size of the object it wrote, and a row's life runs from `migrated_at` to `released_at`, or to the window's end while the hold stands. The tenant's `TenantState` reaches `deleted`, and the tenant keeps its tombstone row, its tenant ID, and its billing sequence (§12.8 Phase 4), so the escrow emitter writes these events under that tenant ID after Phase 4 completes, with windows starting at the earliest `migrated_at`. Phase 4 therefore deletes none of them, and a tenant whose `billingErasurePolicy` is not `exempt` keeps only its escrow events. Under `billingErasurePolicy: exempt`, Phase 4 keeps the tenant's billing events until `billing.retentionDays` ages them out. The escrow watermark per tenant and `resource_type` sits beside the records in the regional platform Postgres, outside the stores Phase 4 deletes, and the emitter deletes it once every record of the tenant is released and its last window is read back. The escrow garbage-collection (GC) release deletes no record, so a released row stays readable for its last window.

The forensics security-hold copies are a different mechanism. [`0128-forensics-evidence-preservation`](../0128-forensics-evidence-preservation/change.md) writes them, under its proposal [FE-3](../0128-forensics-evidence-preservation/change.md#fe-3-platform-only-holds-and-a-security-retention-class), to the `security-hold/` prefix of the same bucket, keeps its own records, and makes the operator pay for them under its decision 16. The escrow emitter reads `legal_hold_escrow_records` alone, so no security-hold copy reaches `storage.usage`. The daily reconciliation below lists the artifact bucket and leaves the escrow bucket out.

**Daily reconciliation.** A leader-elected gateway task compares the ledger with the object store once a day, from `billing.storageReconciliation.source`:

- `listing`, the default: `ListObjectVersions` and `ListMultipartUploads` under each `/{tenant_id}/` prefix, rate-limited by `billing.storageReconciliation.requestsPerSecond`.
- `inventory`: the provider's inventory report (S3 Inventory, Cloud Storage inventory reports, or Azure Blob inventory), read from the location the operator configures. MinIO uses `listing`.

For each tenant and object type it reports, under `lenny_storage_reconciliation_difference_bytes{tenant_id, kind}` and `..._objects`, the kinds `missing_object` (a live row with no current object), `orphan_object` (a current object with no row), `tombstoned` (a current object whose row is soft-deleted), `size_mismatch`, `noncurrent_version`, `delete_marker`, and `incomplete_multipart`. `StorageLedgerDrift` fires when `missing_object`, `orphan_object`, or `size_mismatch` exceeds `billing.storageReconciliation.alertFraction` of the tenant's ledger bytes, default 0.01, on consecutive runs. The task writes `storage.reconciliation_completed` to the audit log with the totals.

**Stale views.** A listing or an inventory report is older than the ledger it is compared with. `cataloging.Put`, `RecordPut`, and `Copy` write the object before the row, and an inventory report lags by up to a day, so an artifact written near the snapshot appears in one source and not the other. Each run therefore records its snapshot time, which is the start of its listing or the generation time of the inventory report, and compares only rows whose `created_at` precedes the snapshot time less `billing.storageReconciliation.marginSeconds`, default 3600. A row becomes a confirmed `missing_object` or an overstated `size_mismatch` only when a direct `HEAD` on its key agrees on two consecutive runs. A run that receives any listing or inventory error for a tenant, or whose candidate `missing_object` bytes exceed `billing.storageReconciliation.maxMissingFraction` of the tenant's ledger bytes, default 0.05, aborts for that tenant, writes no correction, and fires `StorageReconciliationAborted`.

**Corrections.** A confirmed `missing_object` means the ledger billed bytes the store did not hold. The task emits a `billing_correction` with reason `STORAGE_RECONCILIATION` against each `storage.usage` event since the last run that saw the object, with the row's bytes removed, sets `reconciliation_missing_at` on the row so that later `storage.usage` events leave it out, and fires `StorageLedgerMissingObject` naming the tenant and the key. The task never deletes or soft-deletes a row. The operator decides whether to soft-delete the row through the guarded path in §12.5 (**GC concurrency model (single-writer + soft-delete guard).**), which lowers the quota counter. A confirmed `size_mismatch` with the ledger larger is corrected and alerted the same way. Reconciliation never raises a tenant's bill, so an orphan or a larger object is reported and left to the operator (decision 12).

Each correction starts from the event's current values, which are those of its latest correction when one exists and the original's otherwise, because §11.2.1 applies corrections to one original in sequence order with the latest taking precedence, and a correction computed from the original would undo an earlier one. `STORAGE_RECONCILIATION` is a Category 1 code, and a correction of a periodic event carries the full replacement set of the corrected event's quantity fields. One run can correct every hourly event since the object was last seen, so `BillingCorrectionRateHigh` computes its rate over corrections with other reason codes, and `StorageLedgerDrift` and `StorageLedgerMissingObject` alert on `STORAGE_RECONCILIATION` corrections.

**Cases the ledger misses.** The ledger counts the current object of each artifact it records. The object store bills for more, and the reconciliation reports what it can see:

- **Versioning.** A deleted or overwritten object leaves a noncurrent version for the expiry period, 1 day on MinIO under §12.5, and a delete marker. The ledger stops counting at deletion. The reconciliation reports both kinds, and the operator prices them as overhead or sets a shorter expiry.
- **Lifecycle rules and manual deletes.** An operator's lifecycle rule or a manual delete removes an object the ledger still counts. The reconciliation reports it as `missing_object`, corrects the bill once confirmed, and leaves the row to the operator.
- **Soft-deleted objects.** A soft delete tags the object and leaves it in the bucket until the tombstone sweep's hard prune, 24 hours later by default, and the ledger stops counting at `soft_deleted_at`. The provider bills those bytes, and the reconciliation reports them as `tombstoned`.
- **Abandoned multipart uploads.** A gateway that crashes during a multipart upload leaves parts the ledger never recorded, and the provider bills them until they are aborted. The chart's lifecycle Job installs no abort rule. MinIO removes stale uploads under its own `stale_uploads_expiry` setting, and a cloud store needs an `AbortIncompleteMultipartUpload` lifecycle rule or its equivalent, which the operator guide names with a 1-day period. The reconciliation reports what remains.
- **Activity evidence.** `EvidenceStore` batches are metered as `evidence.usage` by the forensics design and are absent from `storage.usage`.
- **Git mirror stores.** `lenny-git-mirror` holds repositories on persistent volumes shared across tenants. Their bytes are reported per volume by `kubelet_volume_stats_used_bytes` and reach no tenant's bill.
- **Postgres-held data.** Session messages, session logs, the session tree archive, the audit log, and agent memory (`session_messages`, `session_logs`, `session_tree_archive`, `audit_log`, and `agent_memory`) are rows in Postgres. Their size per tenant can only be estimated, because TOAST, compression, indexes, WAL, and replicas do not divide by tenant. Under decision 13, no billing event carries them. The daily reconciliation task sets the gauge `lenny_postgres_tenant_bytes_estimate{tenant_id}` from `pg_column_size` summed per tenant over those tables, reading one tenant at a time on the read replica when one is configured and on the primary otherwise, and the operator decides from monitoring whether to price it. The gauge carries one series per tenant and no table label, so its cardinality grows with tenants alone, as §16's cardinality statement requires.
- **Pod ephemeral disk.** Billed as the reserved ephemeral storage on `session.pod_usage` and `pool.idle_usage`, with no measured use (decision 10).
- **Platform chunk sets.** Billed once per pack to the set's owner under "Checkpoint packs and platform chunk sets", with the platform-owned sets under the platform tenant.
- **Forensic security-hold copies.** Security-hold copies under the `security-hold/` prefix of the escrow bucket and held evidence are paid by the operator (forensics decision 16), so they are absent from tenant events and reported by the forensics design's metrics. The §12.8 legal-hold escrow copies are billed as `store: escrow` under "Legal-hold escrow copies".

### Dedicated node capacity (BR-7)

**Requirement.** [PM-2](../0136-placement/change.md#pm-2-node-tenancy) lets the operator dedicate nodes to one tenant: a node labelled and tainted `lenny.dev/tenant=<tenantId>` carries that tenant's agent pods alone. The operator pays for such a node whether or not the tenant's pods fill it, and the placement design's decision D6 states that dedicated capacity is charged to the tenant **[source]**. The pods on the node are billed through `session.pod_usage` and `pool.idle_usage` as on any node, so what those events miss is the node capacity no pod requests. BR-7 adds a periodic event that reports, per tenant and per usage interval window, the node minutes and the allocatable CPU and memory of the nodes labelled for that tenant **[design]**.

**Carrier (decision 17).** The owner settled O1 on 2026-11-13 as option (a): a new periodic event, `node.dedicated_usage` **[design]**. The WarmPoolController, which already reads nodes for the placement drift drain ([PM-6](../0136-placement/change.md#pm-6-enforcement)), samples on each reconcile every node that carries `lenny.dev/tenant=<tenantId>` and the class label of an agent class, and accrues node minutes in a `dedicated_node_accrual` table, keyed by tenant, node class, window start, and a hash of the allocatable values, under the conditional updates, window splits, and gap cap of "Accrual". The gateway's leader-elected emitter turns each closed window into one event, as it does for `pool.idle_usage` (decision 9).

**Fields.** `tenant_id` is the tenant the nodes are dedicated to, and `user_id` and `session_id` are absent. The event carries:

| Field | Type | Meaning |
| :-- | :-- | :-- |
| `node_class` | string | The node class of the nodes ([PM-1](../0136-placement/change.md#pm-1-node-classes-and-presets)) |
| `node_minutes` | float64 | The sum over the tenant's dedicated nodes of the minutes each was present and Ready in the window |
| `node_count_max` | uint32 | The largest number of such nodes at one sample |
| `allocatable_cpu_millicores`, `allocatable_memory_bytes`, `allocatable_ephemeral_storage_bytes` | uint64 | Each node's `status.allocatable`, so the kubelet reserve and system reservations are already excluded |
| `unsampled_minutes` | float64 | Minutes no sample covered within `billing.idleAccrualMaxGapSeconds`, which bill nothing |
| `window_start`, `window_end`, `usage_window_key` | | As for the other periodic events |

Nodes of one tenant and class whose allocatable values differ produce one event per distinct set of values, as a pool whose pods differ does under `pool.idle_usage`. The event follows "Writing periodic events": a `usage_window_key`, the read-back emitter, and the null/absent contract. A node whose `lenny.dev/tenant` label names a tenant whose `TenantState` is `deleting` reaches no event, as for the other emitters. A node that carries a tenant label and no agent class label is outside every Lenny class, reaches no event, and is reported by the placement node check rather than billed. Pod usage on the same nodes is still reported by `session.pod_usage` and `pool.idle_usage`, so a consumer that prices the node does not also price the pods on it, and the operator's billing system decides which to use.

### Writing periodic events

`session.pod_usage`, `pool.idle_usage`, and `storage.usage` are appended through the `EventStore` with the per-tenant sequence of §11.2.1 and its Redis and in-memory fallbacks. Each carries `usage_window_key`, a SHA-256 over the event type, tenant, subject (session and pod, pool and revision, or store and artifact type), window start, and resource hash. The billing table gains a unique index on `(tenant_id, usage_window_key)`, partial on a present key.

`Append` and `InsertFromStream` both insert with `ON CONFLICT DO NOTHING` and no conflict target, which absorbs a duplicate on the `usage_window_key` index and on the `stream_entry_id` index alike. A named target absorbs a duplicate on its own index alone, and a duplicate on the other raises 23505, Postgres's unique-violation error. From `InsertFromStream`, `flushEntries` then stops at the rejected entry, and every later entry in the tenant's Redis billing stream waits behind it. From `Append`, the failover pipeline treats the error as a primary failure and routes the duplicate to the stream. A duplicate insert returns the committed row, and a Tier 2 test pins both paths with a duplicate key. The current code has no `usage_window_key` and therefore no second index to collide on, so this is a requirement of the design, and `BUILD-GAPS.md` carries no finding for it.

`nextval` runs before the insert, so a no-op insert would still consume a sequence number, and §11.2.1 states that a gap indicates lost events and should trigger replay. Both paths therefore look up `usage_window_key` in the insert transaction before drawing `nextval`, and a found key ends the transaction with no number drawn. Two concurrent inserts of one key can still both draw a number, and the loser leaves a gap. §11.2.1 gains the rule that a gap a replay leaves empty is benign, as a rollback gap is today. A leader that re-runs a window after a failover therefore inserts nothing twice, and the table stays insert-only. A wrong event is changed only by a `billing_correction`.

The §11.2.1 null/absent contract extends to the new fields, each present only on the event types above. §11.2.1's description of `tenant_id` as the tenant "that owns the session" becomes the tenant the event is billed to, because `pool.idle_usage` and `storage.usage` have no session.

An operator-initiated correction of a new event type always takes the dual-control path, because the `billing.dualControlThreshold` sum adds tokens and pod minutes and has no unit for bytes.

## Validation owed

- **Listing rate (decision 22).** Measure the listing time and request count of storage reconciliation at `billing.storageReconciliation.requestsPerSecond` 50 on a bucket at the artifact volume of capacity Tier 3, at test Tier 7, against S3 and MinIO, and confirm that the rate stays within each store's request limits and finishes within the daily run.
- **Class ephemeral storage request (decision 18).** Confirm on Kind that a pod of a shipped class reports an effective ephemeral storage request of the volume sum plus 1 GiB, and that the scheduler reserves it.

## Residual risks

- **Idle sampling.** Idle accrual changes only at reconciles, and a change between them is approximated by the earlier count.
- **Reserved disk.** A pod is billed its reserved ephemeral storage whether it writes nothing or fills the reservation. The request includes every disk-backed volume's `sizeLimit` for every slot, so a pod with several slots bills each slot's full disk allowance while the slot is empty. At the defaults a slot adds 12 GiB, the spool 16 GiB, and the class 1 GiB, so the 10 GiB workspace default of IC decision D3 makes each pod's disk the largest part of its bill on most price lists, and an operator who prices disk lowers `workspaceSizeLimitBytes` or `spoolSizeLimitBytes` per pool.
- **Provider bills differ.** `byte_hours` from the ledger leaves out noncurrent versions, delete markers, minimum storage durations on cold storage classes, request charges, and egress. The reconciliation reports noncurrent versions and delete markers, and the operator prices the rest.
- **Apportioning shared pods.** The per-slot share charges a session for its slot whatever the session uses, and empty slots on shared pools reach no tenant.
- **Unsampled idle time.** Idle minutes beyond the gap cap bill nothing, so a long controller outage leaves idle cost with the operator.
- **Missing rows left to the operator.** A confirmed `missing_object` keeps its row and its quota charge until the operator acts on the alert.
- **Unattributed costs.** Node-level costs and the share of a node that no pod requests reach no event on shared nodes. On dedicated nodes `node.dedicated_usage` reports the whole node.
- **Platform chunk sets.** The platform-owned sets cost the operator storage for as long as any snapshot references their packs, including the packs of a source that has left every warm list. A tenant pays for its own sets' packs whether one of its sessions or many reference them, its uploaded `artifact` assets' packs included, until garbage collection reclaims an upload no version of its runtime references.
- **Slot memory floor.** A class small enough for one slot can be refused for a pool with several slots, because the floor applies to each slot's share. A `platform-admin` who lowers the floor accepts the materialization risk that [WM-14](../0153-workspace-materialization/change.md#wm-14-memory-sizing) measured.
- **Stalled emitter.** The tombstone watermark holds rows while the emitter is stalled, so `artifact_store` grows until the alert is handled.
- **Reconciliation cost.** Listing a large bucket takes time and requests, and an inventory report lags by up to a day or more, depending on the provider, so a difference can persist for that long.
- **Visibility to tenants.** A tenant's `billing-viewer`, the role that reads its tenant's usage and metering data, reads the class sizes, pod UIDs, and pool names in its own events.
- **Postgres-held data.** Session messages, logs, the tree archive, the audit log, and agent memory reach no bill, and the per-tenant gauge is an estimate that can be far from the storage cost. The daily `pg_column_size` pass adds read load on Postgres.
- **Owned pools wait on DR-5.** `pool.idle_usage` reports subjects with `pool_ownership: shared_pinned` alone until [DR-5](../0147-tenant-derived-runtimes/change.md#dr-5-owned-pools) lands. The unpinned idle pods of shared pools stay the operator's.
- **Rollout idle cost.** The idle minutes of a base rollout's extra pod set on each owned pool reach the platform tenant rather than any customer, so the operator carries them for as long as each rollout runs.
- **Pinned idle pods.** A tenant sees a figure with `pool_ownership: shared_pinned` for pods the platform kept for it and that it did not ask to keep. The operator decides whether to price it.
- **Escrow billed after deletion.** `store: escrow` events arrive under a tenant ID whose `TenantState` is `deleted`, until the hold is cleared, so the operator's billing system keeps that account open to receive them. The tenant is billed for every escrowed hold, including one the operator set.

## Open decisions

No decision is open. BR-Q1 and O1 are kept below as the records of the choices the owner settled as decisions 18 and 17.

**BR-Q1. A class's own ephemeral storage request.** The checkpoint design's decision D3, settled on 2026-11-13, sets the pod's ephemeral storage request equal to the sum of its disk-backed volumes' size limits ([IC decision D3](../0131-incremental-checkpoint/change.md#decisions)). A class may state an optional `requests.ephemeral-storage` ("Fields" under "Resource classes in configuration"), and no decision states whether that request adds to the sum.

- (a) The class's request adds to the sum. It covers the containers' writable layers and logs, which no volume's size limit counts. The shipped classes state none, so at the defaults the request equals the sum, and the totals under "Ephemeral storage" hold.
- (b) The request equals the sum exactly, and a class carries no ephemeral storage fields. The writable layers and logs then have no reservation on the node.

**Recommendation: (a).** The kubelet counts the writable layers and logs against the node's ephemeral storage, and under (b) the scheduler reserves nothing for them. (a) gives the same request as (b) for every shipped class and gives the operator one field to reserve that space. (b) follows the wording of decision D3 literally and removes two fields from the class.

**Settled (2026-11-13): (a)** (decision 18). The owner answered "yes ~1 GiB" and asked whether the value is configurable, and then "ok; the ~1 GiB is a field on each resource class". Each resource class carries its own `requests.ephemeral-storage`, 1 GiB in the shipped classes and configurable per class, added on top of the volume sum. The shipped classes now state a request, so the totals under "Ephemeral storage" include it.

**O1. The carrier of dedicated node capacity (BR-7).**

- (a) A new periodic event, `node.dedicated_usage`, per tenant, node class, and window, emitted by the gateway's leader-elected emitter from a `dedicated_node_accrual` table that the WarmPoolController fills by sampling labelled nodes, as it accrues idle pods for `pool.idle_usage`.
- (b) A new `pool_ownership`-like subject on `pool.idle_usage` that adds the unrequested capacity of a tenant's dedicated nodes to its idle figure.
- (c) A per-tenant metric with no billing event, which the operator prices from monitoring.

**Recommendation: (a).** The quantity is node capacity, which belongs to no pool, so (b) would attribute a node to a pool arbitrarily when a tenant's dedicated nodes serve several pools. (c) leaves dedicated capacity off every bill, which the placement design's D6 rejects. (a) reuses the accrual and emitter pattern of decision 9, and the WarmPoolController already reads nodes for placement ([PM-6](../0136-placement/change.md#pm-6-enforcement)).

**Settled (2026-11-13): (a)**, in the owner's words "BR O1: node.dedicated_usage" (decision 17). The two questions (a) left are answered in BR-7: the WarmPoolController samples on each reconcile under the accrual's gap cap, and a node with a tenant label outside every agent class is not reported.

## Decisions

The owner has settled decisions 1 to 22, and the design above is written to them. Decisions 6 to 22 each state the settled option, its cost, and the alternative the owner rejected.

- **Decision 1: pricing by actual resources.** Settled. Billing lets an operator price usage by actual resources, and events record the resource class name and the pod's actual resources, because an operator can redefine a class at any time.
- **Decision 2: idle billing for owned pools.** Settled. A periodic billing event reports a tenant's owned pools' idle and reserved pod minutes, attributed to the owning tenant. This is `pool.idle_usage`. Decision 11 extends it to pinned idle pods on shared pools.
- **Decision 3: storage usage.** Settled, and amended by the owner with decision 10. A periodic `storage.usage` event per tenant and artifact type from the `artifact_store` ledger, as bytes held and byte-hours, with a daily reconciliation against the object store that reports differences as a metric and an alert and emits `billing_correction` where appropriate. The design states the cases the ledger misses, bills pod ephemeral disk by its request with sampled use, and leaves forensic escrow copies to the operator under [forensics decision 16](../0128-forensics-evidence-preservation/change.md#decisions). The amendment, in the owner's words "bill reserved disk only", bills pod ephemeral disk by its reserved request and removes sampled use. The forensic escrow copies this decision names are the security-hold copies, and decision 14 bills the separate §12.8 legal-hold escrow copies.
- **Decision 4: resource classes in configuration.** Settled, in the owner's words "Ability to override the default classes is important. In fact, I think there shouldn't be any values hardcoded in the code." The code holds no class, the chart ships `small`, `medium`, and `large` as defaults an operator changes or replaces, the embedded stack carries the same defaults, a pool naming an undefined class is refused at write, the controller checks each class against the tmpfs reservation, and the specification states the classes as chart defaults and defines the override.
- **Decision 5: resource fields on session usage.** Settled. Session usage events carrying `pod_minutes` gain the class name, the pod's actual CPU and memory requests and limits at the time, the isolation profile, and, for a pod serving several sessions, its `maxConcurrentSessions`. The field is `maxConcurrentSessionsPerPod` since the owner's rename of 2026-11-12.
